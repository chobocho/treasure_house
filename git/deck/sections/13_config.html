줄 끝 — 저장소에는 LF, 작업 트리에는 CRLF

3부에서 "blob 은 바이트 그대로" 라고 했습니다. 변환은 blob 을 만들 때(add)와 꺼낼 때(checkout) 일어납니다. 운영체제가 섞인 팀에서 * text=auto 가 흔한 까닭입니다(14부의 CRLF 함정).

1~4장 퀴즈

Q. 팀의 커밋 메시지 규칙을 .git/hooks/commit-msg 로 만들어 저장소에 커밋하려 합니다. 무엇이 문제입니까? 그리고 build/ 를 무시했는데 build/keep.txt 만 추적하고 싶다면?

A. .git/hooks 는 저장소 내용이 아니라 커밋할 수 없고, 해도 clone 에 전해지지 않으며, --no-verify 로 건너뛸 수 있습니다. 강제할 규칙은 서버 훅에 두고, 클라이언트 훅은 스크립트를 저장소에 넣은 뒤 core.hooksPath 나 설정 훅으로 각자 켜게 합니다. build/ 처럼 디렉터리째 무시하면 안의 파일을 ! 로 되살릴 수 없으니 build/* 와 !build/keep.txt 로 쓰거나, git add -f 로 그 파일만 추적합니다(추적 중인 파일에는 무시 규칙이 듣지 않습니다).

필터

clean 과 smudge

add 할 때 clean 을 거쳐 blob 이 되고, 꺼낼 때 smudge 를 거쳐 작업 트리에 씁니다. 2장의 줄 끝 변환도 같은 자리에서 일어나는 내장 필터입니다.

실행 검증

LFS 의 원리를 흉내 내기

Git LFS 도 이 필터 자리를 씁니다 — 큰 파일은 따로 된 저장소에 두고, git 에는 작은 포인터만 넣어 역사가 무거워지지 않게 합니다. 이 기계에는 git-lfs 가 없어 같은 원리를 셸 스크립트 두 개로 흉내 냈습니다. 포인터의 실제 형식은 LFS 의 것과 다릅니다.

실행 검증

꺼내면 원래대로

대가도 분명합니다 — 저장소 밖의 저장소를 잃으면 git 역사만으로는 파일을 되살릴 수 없습니다. filter.big.required=true 는 필터가 없는 기계에서 포인터를 파일인 척 꺼내지 않고 멈추게 합니다.

worktree · 서브모듈 · 서브트리

작업 트리와 저장소를 나누고 묶기

worktree — 한 저장소, 작업 트리 여럿

급한 수정을 위해 지금 작업을 stash 하지 않고 다른 디렉터리에서 다른 브랜치를 꺼내 둘 수 있습니다. HEAD·인덱스는 작업 트리마다 따로, 객체와 참조는 함께입니다.

실행 검증

같은 브랜치를 두 곳에서는 안 된다

한 브랜치를 두 곳에서 커밋하면 한쪽이 옮긴 이름표를 다른 쪽이 모르는 채 덮어씁니다. 그래서 막습니다.

실행 검증

함정 하나 — 그냥 clone 하면 비어 있다

protocol.file.allow=always 는 로컬 경로 서브모듈을 허락하는 설정입니다. CVE-2022-39253 을 고친 판부터 기본으로 막혀 있습니다(14부의 CVE 표).

실행 검증

함정 둘 — 서브모듈 안은 분리 HEAD

상위 저장소가 가리키는 것은 커밋이지 브랜치가 아니라서, 서브모듈 안에서 그냥 커밋하면 분리 HEAD 위에 쌓입니다(4부). 안에서 일하려면 먼저 브랜치로 옮깁니다.

실행 검증

함정 셋 — 라이브러리가 앞서 나가도

상위 저장소도 이 변경(가리키는 커밋이 바뀜)을 커밋해야 다른 사람이 새 판을 받습니다. 서브모듈의 변경은 늘 두 번 커밋됩니다.

실행 검증

서브트리 — 남의 역사를 내 트리 안에 통째로

서브모듈과 달리 clone 한 사람은 아무것도 따로 할 필요가 없습니다. 대신 라이브러리 역사가 섞여 들어오고, 원본으로 돌려보내는 일이 번거롭습니다. git subtree 는 git 에 딸린 기여 도구입니다.

실행 검증

store helper 는 평문으로 적는다

공식 문서도 "평문으로 저장된다" 고 경고합니다. 운영체제의 열쇠고리를 쓰는 helper 가 낫습니다.

실행 검증

SSH 키로 커밋 서명

서명은 커밋 바이트 안에 들어갑니다(3부의 gpgsig). ssh 키를 쓰는 서명은 2.34.0 에서 들어왔습니다. 검증에는 "어느 키를 누구로 믿을지" 를 적은 gpg.ssh.allowedSignersFile 이 필요합니다. 키는 실험마다 새로 만들어 버리는 것이고, 지문은 실행마다 달라 가렸습니다.

실행 검증

maintenance register — 예약할 저장소 목록

maintenance start 는 여기에 더해 운영체제의 예약 작업(cron·systemd 타이머 등)을 등록합니다. 실험이 이 기계의 예약 작업을 건드리지 않도록 register 까지만 했습니다. 등록된 저장소는 작업들(10부)이 시간마다·날마다 조금씩 돌아 큰 gc 를 피합니다.

실행 검증

GUI 와 TUI

git 에는 gitk(역사 보기)와 git gui(커밋하기)가 딸려 오지만 Tk 가 필요해 이 기계에는 깔려 있지 않습니다(17부의 명령 표). 편집기에 붙은 도구, 터미널 안의 TUI 도구도 결국 이 부까지 본 명령과 파일을 움직입니다 — 도구가 헷갈릴 때는 6부의 상태 표로 돌아가 세 영역을 확인합니다.

5~7장 퀴즈

Q. 서브모듈의 새 판을 받으려고 git submodule update --remote 를 했는데 동료에게는 옛 판이 보입니다. 왜입니까? 그리고 필터로 큰 파일을 밖에 둔 저장소를 필터 없는 기계에서 clone 하면?

A. 상위 저장소가 가리키는 커밋(160000 항목)은 아직 옛 것입니다. git add lib && git commit 으로 상위 저장소에 새 커밋을 기록하고 push 해야 합니다. 필터가 없으면 작업 트리에 포인터 글이 그대로 나오고, filter.<이름>.required=true 라면 git 이 멈춥니다.
