큰 바이너리

판마다 1 % 만 바꿔도

1 MiB 파일의 판 넷

실행 검증

왜 압축된 파일은 100 % 인가

  • 글 — 판 사이에 같은 조각이 많아 델타(10부)가 잘 먹고, zlib 도 잘 누릅니다.
  • 무작위 바이너리 — zlib 으로는 안 눌리지만 판 사이의 같은 부분은 델타가 찾아냅니다(31 %).
  • 압축된 파일(zip·jpg·mp4·docx…) — 안쪽 1 % 가 바뀌면 압축된 바이트가 거의 전부 바뀝니다. 델타도 zlib 도 먹지 않아 판마다 통째로 쌓입니다.

그리고 스냅숏 모델(2부)이라 옛 판은 역사에 영원히 남습니다 — clone 하는 모든 사람이 모든 판을 받습니다. 대책은 필터로 밖에 두기(13부의 LFS 원리), 부분 clone(11부), 그리고 압축하지 않은 원본을 커밋하기입니다.

설명용

그리고 머지할 수 없다

줄이 없으니 3-way 머지도 없습니다(7부의 바이너리 충돌). 두 사람이 같은 그림 파일을 고치면 한 사람의 작업은 버려집니다. 그래서 큰 바이너리를 다루는 팀은 파일 잠금 같은 git 밖의 약속을 둡니다.

2장

규모

파일 수, 역사의 길이

파일 수가 늘면 인덱스가 는다

인덱스는 파일마다 한 항목이라 파일 수에 비례합니다(20,000개에 1.6 MB). status·add 가 매번 이 파일을 읽고 씁니다. 트리 객체 수는 디렉터리 수(20×20 + 20 + 최상위 1 = 421)라 그대로입니다.

실제로 큰 저장소들

Windows 코드처럼 파일이 수백만인 저장소에서는 기본 git 만으로는 느려, 저장소를 가상 파일 시스템으로 필요한 만큼만 내려받는 방식이 쓰였습니다.

3장

파일 시스템의 차이

git 은 바이트, 운영체제는 제 규칙

대소문자 — 이름만 바꿨는데

리눅스(대소문자 구분)에서 core.ignorecase=true 로 대소문자를 가리지 않는 파일 시스템을 흉내 냈습니다. 셸로 README 를 readme 로 옮기고 status 를 봤습니다.

ignorecase 에서 git 은 readme 를 "기억하던 README 와 같은 파일" 로 봅니다. 대소문자만 바꾸려면 처음부터 git mv 로 해야 합니다.

실행 검증

대소문자와 보안

대소문자를 가리지 않는 파일 시스템은 git 의 보안 문제가 여러 번 나온 자리이기도 합니다. 리눅스에서는 서로 다른 두 경로가 그런 파일 시스템에서는 한 경로가 되어, 복제 중에 심볼릭 링크를 따라 엉뚱한 곳에 쓰게 되는 식입니다(6장의 CVE 표 — CVE-2021-21300 · CVE-2024-32002).

역사 근거

줄 끝 — CRLF 파일을 add 하면

한 사람은 CRLF, 한 사람은 LF 로 저장하는 팀에서 설정이 없으면 파일 전체가 바뀐 것처럼 보이는 diff 가 생깁니다. .gitattributes 에 * text=auto(와 필요한 파일에 eol=)를 두어 저장소 안의 줄 끝을 하나로 정합니다(13부).

실행 검증

유니코드 정규화 — 같은 "한글", 다른 바이트

git 은 파일 이름을 바이트로 다룹니다. 이름을 자모로 풀어 저장하는 파일 시스템(macOS 의 기본 동작)에서 만든 이름과 다른 곳에서 만든 이름이 별개의 파일이 됩니다. macOS 의 git 은 core.precomposeUnicode 로 이를 모아 줍니다.

실행 검증

한글 파일 이름이 이상하게 보일 때

core.quotepath 기본값은 ASCII 밖의 바이트를 따옴표와 8진수로 보여 줍니다. git config --global core.quotepath false 면 한글이 그대로 보입니다(앞 장).

실행 검증

빈 디렉터리는 담기지 않는다

트리는 "이름 → blob 또는 트리" 이고, 인덱스에는 파일만 적힙니다(3·5부). 항목이 없는 디렉터리를 가리킬 방법이 없습니다. .gitkeep 은 git 의 기능이 아니라 이를 피하는 관례입니다 — 이름은 아무래도 됩니다.

실행 검증

권한 비트와 링크

실행 비트를 믿을 수 없는 파일 시스템(윈도, 일부 네트워크 드라이브)에서는 git 이 저장소를 만들 때 core.fileMode=false 를 적어 둡니다. 심볼릭 링크를 만들 수 없는 곳에서는 링크 blob 이 대상 경로를 적은 보통 파일로 꺼내집니다.

1~3장 퀴즈

Q. 디자인 팀이 PSD 파일 수백 개를 매주 고쳐 커밋합니다. 1년 뒤 clone 이 수십 GB 가 되었습니다. 왜이고, 무엇을 할 수 있습니까? 그리고 macOS 사용자와 리눅스 사용자가 같은 한글 파일을 두 번 커밋하게 되는 까닭은?

A. 압축된 바이너리라 델타가 먹지 않아 판마다 통째로 쌓이고, 스냅숏 역사라 모든 판을 누구나 받습니다. 필터로 저장소 밖에 두는 LFS 류 도구, 부분 clone, 또는 그 파일들을 별도 저장소·저장소 밖 저장 공간으로 빼는 것이 대책입니다. 한글 파일은 이름의 유니코드 정규화(NFD/NFC)가 달라 git 에게는 바이트가 다른 두 이름이기 때문입니다 — macOS 쪽에 core.precomposeUnicode=true 를 둡니다.

시간대

초 하나, 얼굴 여럿

같은 순간을 여러 꼴로

커밋에는 초와 쓴 사람의 시간대가 적힙니다(3부). 기본 표시는 쓴 사람의 시간대라, 서울에서 보는 미국 동료의 커밋이 "어제 오후" 로 보입니다. --date=local 이면 내 시간대로 바꿔 보여 줍니다.

실행 검증

나머지 꼴

커밋 시각은 커밋을 만든 기계의 시계를 믿은 값입니다. 시계가 틀린 기계의 커밋은 부모보다 이른 시각을 가질 수 있어, 날짜 차례와 역사 차례가 어긋납니다.

SHA-1 에서 SHA-256 으로 (2026-09 기준)

어디까지 왔나

  • 2017-02-23 SHAttered, 2.13.0 부터 충돌 탐지 SHA-1(3부)

역사 근거

CVE 가 몰린 자리

  • 서브모듈과 재귀 복제 — 남의 저장소가 정한 이름·URL·명령을 내 기계에서 따른다(13부)

  • 로컬 복제 — 심볼릭 링크를 따라 원본 밖의 파일을 가져오게 된다
  • 남이 만든 디렉터리의 .git — 그 설정과 훅이 내 권한으로 돈다

공통점은 "저장소는 데이터이자 설정이자 실행 파일(훅)" 이라는 것입니다. 모르는 저장소를 받는 것은 모르는 프로그램을 받는 것과 가깝습니다.

설명용

safe.directory

다른 사용자가 소유한 디렉터리의 저장소를 git 은 기본으로 믿지 않습니다 — 그 설정을 읽지도, 훅을 돌리지도 않습니다. 공유 저장소처럼 일부러 그렇게 쓸 때만 safe.directory 에 경로를 적어 예외로 합니다. 셸 프롬프트가 부르는 git status 만으로 남의 설정이 실행되던 CVE-2022-24765 가 시작이었습니다.

이 기계의 실험은 모두 한 사용자로 돌아 소유자가 다른 상황을 만들 수 없어 캡처는 싣지 않았습니다.

문서 근거

받는 객체 검사하기

transfer.fsckObjects=true 면 fetch·push 로 받는 객체를 3부의 fsck 규칙으로 검사해, 형식이 틀린 트리나 수상한 경로 이름을 거절합니다. 서버라면 켜 두는 것이 좋습니다.

4~7장 퀴즈

Q. 회사가 "git 으로 경로별 권한을 나눠 외주 개발자는 src/secret/ 을 못 보게 하자" 고 합니다. 가능합니까? 그리고 SHA-256 으로 새 저장소를 만들면 기존 SHA-1 저장소와 주고받을 수 있습니까(2026-09 기준)?

A. git 만으로는 안 됩니다. clone 은 저장소 전체를 받고, sparse-checkout 은 작업 트리를 줄일 뿐 객체는 다 받습니다. 저장소를 나누는 것이 답입니다. SHA-256 저장소와 SHA-1 저장소는 2.55.0 에서 서로 주고받지 못합니다 — 실험의 fetch 가 "mismatched algorithms" 로 멈췄습니다.
