12부

원격과 협업

여럿이 한 역사를 나눠 쓰는 법

이 부에서 할 일

11부가 두 저장소의 대화였다면, 이 부는 사람들의 약속입니다. 실험은 bare 저장소 하나(hub)를 두고 alice 와 bob 이 각자 복제본에서 일합니다.

  • 먼저 push 한 사람이 이긴다 — 늦은 쪽의 선택지(merge · rebase · ff-only)
  • 강제 push 를 안전하게 — --force-with-lease
  • 원격 추적 참조와 refspec, 지워진 원격 브랜치 치우기
  • 태그 push 와 버전 이름
  • 포크 워크플로와 메일 패치 워크플로
  • 워크플로의 모양들 — 그리고 커밋 메시지의 관행
설명용

1장

먼저 push 한 사람

늦은 쪽의 거절과 pull

둘이 같은 끝에서 출발했다

alice 는 1번 줄, bob 은 3번 줄을 고쳤습니다. alice 가 먼저 push 했습니다.

hub 의 main 은 이제 alice 의 커밋입니다. bob 의 push 를 받으면 alice 의 커밋이 main 에서 떨어져 나가니 거절됩니다(11부 — 되감기가 아닌 push 의 거절).

실행 검증

그냥 pull 하면 — git 이 묻는다

pull 은 fetch + 합치기입니다. 합치는 방법을 정해 두지 않았고 되감기로 끝나지도 않으면, 지금의 git 은 멈추고 세 가지 가운데 고르라고 합니다.

실행 검증

하나 — merge

갈라진 모양이 역사에 그대로 남고 "Merge branch 'main' of …" 커밋이 생깁니다. 모두가 이렇게 pull 하면 로그가 이런 머지로 가득 찹니다.

실행 검증

둘 — rebase

bob 의 커밋을 alice 의 커밋 위로 다시 만들어(8부) 한 줄 역사가 됩니다. bob 의 커밋 이름은 바뀌지만, 아직 push 하지 않은 커밋이라 괜찮습니다.

실행 검증

셋 — ff-only

"합치기는 내가 명시적으로 하겠다" 는 정책입니다. 거절되면 git rebase origin/main 이나 git merge 를 골라서 합니다.

실행 검증

무엇을 고를까

설정역사잘 맞는 곳
pull.rebase=true한 줄각자 작은 커밋을 주 브랜치에 바로 올리는 팀
pull.rebase=false갈라진 모양 그대로브랜치 역사 자체를 보존해야 하는 곳
pull.ff=only사람이 결정풀 리퀘스트로만 주 브랜치에 들어가는 팀

어느 쪽이든 "남이 이미 받아 간 커밋은 리베이스하지 않는다"(8부)는 지킵니다 — pull --rebase 가 다시 만드는 것은 내 push 하지 않은 커밋뿐입니다.

설명용

2장

강제 push 를 안전하게

--force-with-lease

내가 본 그대로일 때만 덮어쓴다

alice 는 자기가 올린 커밋을 amend 해 다시 올립니다. hub 는 alice 가 마지막으로 본 값 그대로입니다.

--force-with-lease 는 "원격의 main 이 내 origin/main 과 같을 때만" 덮어씁니다. 4부의 비교 후 교체를 push 에 쓴 것입니다.

실행 검증

그 사이 누가 바꿨다면 — stale info

bob 은 alice 의 옛 커밋 위에서 일했고, alice 의 강제 push 를 아직 fetch 하지 않았습니다.

그냥 --force 였다면 alice 의 커밋이 조용히 사라졌을 것입니다. 단, 강제 push 전에 fetch 해 버리면 origin/main 이 최신이 되어 lease 가 통과하니, "fetch 하고 확인하고 올린다" 는 습관이 함께 필요합니다(--force-if-includes 가 그 확인을 거듭니다).

실행 검증

1~2장 퀴즈

Q. push 가 "fetch first" 로 거절됐습니다. git push --force 로 올리면 무슨 일이 생깁니까? 올바른 순서는?

A. 원격에 먼저 올라간 남의 커밋이 main 에서 떨어져 나갑니다(누구의 reflog 에도 없을 수 있습니다). 올바른 순서는 git pull --rebase(또는 merge)로 남의 커밋을 내 역사에 받은 뒤 push 하는 것입니다. 내가 이미 올린 커밋을 고쳐 다시 올려야 할 때만 --force-with-lease 를 씁니다.
설명용

3장

원격 추적 참조

refspec · prune · remote show

refspec — 무엇을 어디로 받나

  • + — 되감기가 아니어도 덮어쓴다(원격 추적 참조는 원격을 그대로 따라가야 하므로)
  • refs/heads/* — 원격의 모든 브랜치를
  • :refs/remotes/origin/* — 내 저장소의 이 이름 아래로
실행 검증

다른 refspec 으로 받아 보기

refspec 은 "원격 이름 → 내 이름" 사상일 뿐입니다. origin/main 이 특별한 것이 아니라, 이 규칙이 그 이름을 만든 것입니다.

실행 검증

원격에서 지운 브랜치

fetch 는 기본으로 원격 추적 참조를 지우지 않습니다. fetch.prune=true 로 늘 치울 수 있습니다.

실행 검증

remote show — 원격과 내 브랜치의 관계를 한눈에

"git pull 을 하면 main 이 어디와 합쳐지나", "git push 를 하면 어디로 가나" — 인자 없는 pull·push 의 답이 여기 있습니다. push 쪽은 push.default(2.0 부터 simple: 같은 이름의 upstream 으로)가 정합니다.

실행 검증

4장

태그와 버전

push 되지 않는 태그, describe

태그는 저절로 올라가지 않는다

^{} 줄은 주석 태그를 벗긴 커밋입니다(3부). --follow-tags 는 주석 태그만 따라 올립니다 — 릴리스는 주석 태그로, 개인 표시는 가벼운 태그로 쓰라는 설계입니다.

실행 검증

describe — 태그로 부르는 커밋 이름

v1.0-1-g7cda486 = "v1.0 에서 커밋 1개 뒤, 이름이 7cda486 으로 시작". 빌드에 버전을 박을 때 씁니다. 기본은 주석 태그만 셉니다.

실행 검증

5장

포크와 메일

쓰기 권한 없이 기여하기

원격 둘 — upstream 과 origin

원래 저장소에는 쓸 수 없으니 내 사본(포크)에 올리고 "가져가 달라" 고 요청합니다. 호스팅 서비스의 풀 리퀘스트가 이 요청의 화면입니다.

실행 검증

request-pull — 요청을 글로

풀 리퀘스트라는 말의 원형입니다. 메일링 리스트로 일하는 프로젝트에서는 이 글을 메일로 보냅니다.

실행 검증

패치를 메일로 — format-patch

커밋 제목이 Subject: 가 되고 본문이 메일 본문이 됩니다. git 자신도 이렇게 메일링 리스트로 개발합니다.

실행 검증

받는 쪽 — am

3부의 author 와 committer 가 둘인 까닭이 여기서 드러납니다 — 변경을 쓴 사람과 그 커밋을 만든(적용한) 사람이 다릅니다.

실행 검증

3~5장 퀴즈

Q. 원격에서 지워진 브랜치가 git branch -r 에 계속 보입니다. 왜이고 어떻게 치웁니까? 그리고 git push origin main 으로 릴리스 태그가 올라가지 않은 까닭은?

A. fetch 는 원격 추적 참조를 만들고 갱신할 뿐 지우지 않습니다. git fetch --prune(또는 fetch.prune=true)로 치웁니다. 태그는 브랜치 push 에 따라가지 않습니다 — 이름을 대거나 --follow-tags(주석 태그)를 줘야 합니다.

6장

워크플로와 관행

도구가 아니라 약속

흔한 모양 다섯

모양줄기들어가는 길
중앙 저장소main 하나모두가 pull·push (1장)
기능 브랜치main + 짧은 브랜치들브랜치를 리뷰한 뒤 머지
git-flow 류main · develop · release · hotfix정해진 브랜치 사이를 옮겨 다님
트렁크 기반main, 아주 짧은 브랜치하루 안에 작게 자주, 미완성은 설정 스위치로 숨김
포크원래 저장소 + 각자의 포크풀 리퀘스트 · 메일 패치 (5장)

git 은 어느 것도 강제하지 않습니다. 브랜치는 파일 하나, 머지는 세 스냅숏의 비교일 뿐이라, 이 모양들은 사람들의 약속과 서버의 규칙(11부 pre-receive)으로 지켜집니다.

설명용

리뷰가 쉬운 커밋

  • 커밋 하나에 목적 하나 — 이름 바꾸기와 내용 고침을 나누면 diff·머지·blame 이 모두 쉬워집니다(9부)
  • 모든 커밋이 빌드되게 — bisect 가 날카로워집니다(9부, 8부의 rebase -x)
  • 리뷰 뒤 고친 것은 fixup! 커밋으로 쌓았다가 합치기 전에 --autosquash(8부)
  • 공유한 브랜치를 고쳐 다시 올릴 때는 --force-with-lease(2장)
설명용

커밋 메시지의 모양

git 문서는 "필수는 아니지만" 50자 이하의 한 줄 요약, 빈 줄, 자세한 설명 차례로 쓰라고 권합니다. 첫 빈 줄까지가 제목이고, 제목은 git 곳곳에 쓰입니다 — log --oneline, format-patch 의 Subject:, rebase 할 일 목록.

"기능: …", "fix: …" 처럼 제목 앞에 종류를 붙이는 팀 규칙(Conventional Commits 등)은 git 이 아니라 팀이 정하는 것입니다.
