diff 알고리즘

두 스냅숏에서 변경을 계산하기 — 그리고 그 변경으로 찾기

이 부에서 할 일

git 은 diff 를 저장하지 않습니다(2부). 보여 줄 때마다 계산하고, 계산하는 방법은 여럿입니다. 같은 두 파일이 알고리즘에 따라 다른 diff 로 보입니다.

  • 편집 스크립트 — diff 가 푸는 문제
  • myers · minimal · patience · histogram — 같은 입력, 다른 답
  • 덩어리 머리 · 단어 diff · 공백 무시 · 통계
  • 이름 바꾸기와 복사 — 닮은 정도로 짐작하기
  • blame · 곡괭이(-S·-G) · log -L — 변경을 거슬러 찾기
  • bisect — 역사를 이분 탐색하기

1장

편집 스크립트

diff 가 푸는 문제

"가장 짧은 고침 목록"

줄의 목록 A 를 B 로 바꾸는 "지우기 · 더하기" 목록은 수없이 많습니다. diff 는 그 가운데 짧은 것을 고릅니다. 남기는 줄(공통 부분열)이 길수록 고침 목록은 짧아집니다.

  • A 의 각 줄은 남기거나 지운다, B 의 각 줄은 남긴 줄이거나 더한 줄이다
  • 남긴 줄들은 A 와 B 에서 같은 차례여야 한다
  • 지운 줄 + 더한 줄의 수를 가장 작게

가장 짧은 답이 여럿일 때가 많고, 어느 것을 고르느냐가 알고리즘마다 다릅니다. 짧기만 하면 되는 것이 아니라 사람이 읽기 좋아야 한다는 것이 이 부의 주제입니다.

설명용

myers — 기본값

Eugene Myers 의 O(ND) 알고리즘은 A 를 가로, B 를 세로로 한 격자(편집 그래프)에서 대각선(같은 줄)을 최대한 타며 오른쪽(지우기)과 아래(더하기) 걸음 수가 가장 적은 길을 찾습니다. N 은 두 파일의 길이, D 는 고침의 수 — 차이가 적으면 빠릅니다.

  • git 의 기본 알고리즘입니다
  • minimal 은 같은 틀에서 더 오래 찾아서라도 가장 짧은 답을 보장합니다
  • 부록 A 의 mygit 은 Python 으로 이 알고리즘을 짜고, 진짜 git 의 diff 30쌍과 바이트까지 견줍니다
문서 근거

덩어리 머리 읽기

  • @@ -1,2 +1,2 @@ — 옛 파일 1번 줄부터 2줄, 새 파일 1번 줄부터 2줄
  • 공백으로 시작하는 줄은 문맥(남긴 줄), - 는 지운 줄, + 는 더한 줄
  • index c001c15..71512b6 — 두 blob 의 이름(2부 · 6부)

실험 입력

재귀적으로 비교합니다. 흔한 괄호 줄에 끌려가지 않아 함수 단위로 읽힙니다.

histogram 은 patience 를 넓혀 "드물게 나오는" 줄도 닻으로 씁니다. minimal 은 이 입력에서 myers 와 같은 답을
냈습니다(표). 늘 다른 알고리즘을 쓰려면 diff.algorithm 을 설정합니다.

같은 길이의 답 가운데 덩어리의 경계를 어디에 둘지 고르는 기본 휴리스틱이 있습니다(diff.indentHeuristic, 기본 켬).
이 입력에서는 끄나 켜나 myers 의 답이 같았습니다. 부록 A 의 mygit 은 이 휴리스틱을 쓰지 않고, 비교할 때 진짜 git 도 끄고 돌립니다.

1~2장 퀴즈


Q. 두 판의 diff 가 myers 로는 지운 줄 11·더한 줄 10, patience 로도 11·10 입니다. 그런데 출력은 다릅니다. 어떻게
가능합니까? 그리고 둘 가운데 커밋에 "저장된" diff 는 어느 쪽입니까?



A. 가장 짧은 편집 스크립트가 여럿이라, 같은 길이의 다른 답을 고른 것입니다 — 어느 줄을 "남긴 줄" 로 짝짓느냐가 다릅니다.
커밋에는 diff 가 저장되지 않습니다. 둘 다 볼 때마다 두 스냅숏에서 계산한 것입니다(2부).

blame · 곡괭이 · log -L





blame — 줄마다 마지막으로 바꾼 커밋


blame 실험: 여섯 줄을 쓰고(base), 일곱째 줄을 더하고(append), 앞 세 줄과 뒤 세 줄의 자리를 바꾸고(move block), 일곱째 줄을
들여 썼습니다(indent). ^ 는 역사의 첫 커밋이라는 표시입니다.



자리를 옮긴 원래 1~3번 줄(지금 4~6번 자리)이 "move block" 커밋의 것으로 나옵니다. 내용은 base 때 그대로인데도요.

실행 검증






-w 와 -M




blame 의 "마지막으로 바꾼" 이 무엇을 바꿈으로 칠지를 옵션이 정합니다. 정렬·들여쓰기 커밋이 blame 을 가리면 -w,
코드를 옮긴 커밋이 가리면 -M.

실행 검증






-C — 다른 파일에서 온 줄


b.txt 는 a.txt 의 세 줄을 복사해 만든 파일입니다.




실행 검증






감지에는 문턱이 있다


옮김·복사로 인정하려면 영숫자가 -M 은 20자, -C 는 40자 이상 맞아야 합니다(숫자로 바꿀 수 있습니다).


이 덱의 첫 실험은 줄이 line 1 처럼 짧아 -M · -C -C 가 옵션 없는 blame 과 똑같은 결과를 냈습니다.
문턱을 문서에서 확인하고 줄을 길게 바꿔 다시 뜬 것이 앞 두 장입니다. 

문서 근거






곡괭이 — 이 문자열이 언제 생기고 사라졌나




"line 7" 은 append 에서 생겼습니다. indent 는 그 줄을 고쳤지만 개수(1개)는 그대로라 -S 에는 안 잡히고
-G 에는 잡힙니다. 지워진 함수가 언제 사라졌는지 찾을 때 -S 함수이름 이 가장 빠릅니다.


실행 검증






log -L — 함수 하나의 역사



-L :함수이름:파일 은 그 함수의 줄 범위를 커밋마다 따라가며 그 범위를 바꾼 커밋과 그 부분 diff 만 보여 줍니다.
함수 경계는 앞 장의 덩어리 머리와 같은 규칙(diff=cpp)으로 찾습니다.

Q. 설정 함수 load_config 가 어느 날 코드에서 사라졌습니다. 언제 누가 지웠는지 찾는 가장 빠른 명령은?
그리고 코드 정렬 도구를 돌린 커밋 때문에 blame 이 모두 그 커밋을 가리킨다면?



A. git log -S load_config — 그 문자열의 개수가 바뀐 커밋만 나오니 없어진 커밋이 바로 잡힙니다(-p 를 붙이면
변경도). 정렬 커밋은 git blame -w 로 공백 변화를 무시하거나, 그 커밋을 --ignore-rev(또는
blame.ignoreRevsFile)로 건너뜁니다.

버그를 만든 커밋을 이분 탐색으로





반씩 줄이기


좋은 커밋 하나와 나쁜 커밋 하나를 알려 주면, git 은 그 사이 커밋의 한가운데를 꺼내 줍니다. 좋은지 나쁜지 답하면 절반을 버리고
다시 한가운데로 — 커밋 N 개면 대략 log₂N 번에 찾습니다. 16개면 넷, 1,000개면 열 번 남짓입니다.


"한가운데" 는 DAG 에서 닿는 커밋 수로 셉니다. 머지가 있는 역사에서도 됩니다.

9부 정리




생각확인한 캡처


diff 는 가장 짧은 편집 스크립트를 고른다 — 답이 여럿네 알고리즘: 줄 수는 같고 출력은 둘씩 갈림


patience·histogram 은 드문 줄을 닻으로fib 통째 더함 · fact 통째 지움


이름 바꾸기는 닮은 정도로 짐작R070 · -M80% 이면 지움+더함 · 복사는 --find-copies-harder


blame 은 옵션이 "바꿈" 을 정한다-w · -M · -C -C, 영숫자 20·40자 문턱


-S 는 개수, -G 는 줄indent 커밋은 -G 에만


bisect 는 이분 탐색손으로(skip 포함) · run 으로 네 걸음



설명용






6장 퀴즈


Q. git bisect run make test 를 돌렸는데, 중간의 몇몇 커밋은 빌드조차 안 됩니다. 스크립트가 어떻게 끝나야
bisect 가 그 커밋을 제대로 다룹니까?



A. 빌드가 안 되는 커밋에서는 종료 코드 125 로 끝나야 합니다 — bisect 가 "시험할 수 없음" 으로 보고 건너뜁니다.
그냥 실패(예: 2)로 끝나면 "나쁨" 으로 판정되어 엉뚱한 커밋을 범인으로 지목할 수 있습니다. 보통 빌드 단계와 시험 단계를 나눠
빌드 실패는 exit 125 로 감쌉니다.
