왜 Git 을 밑바닥까지 보는가

Git 은 명령 몇 개를 외우면 쓸 수 있습니다. 그런데 사고가 나는 순간 — 리베이스가 꼬이고, 브랜치가 사라지고, 푸시가 거절당하는 순간 — 외운 명령은 아무것도 설명해 주지 않습니다.

그때 필요한 것은 Git 이 디스크에 무엇을 적는가에 대한 그림입니다. 객체 네 종류, 이름표 몇 장, 인덱스 파일 하나. 이 그림이 머리에 있으면 명령은 외울 것이 아니라 읽을 것이 됩니다.

이 덱의 약속 — Git 이 어떻게 동작한다고 적은 자리에는 그것을 보여 주는 진짜 git 의 실행 캡처가 붙어 있습니다. 코드는 전부 실제로 돌아가고, 형식·프로토콜을 인용한 자리에는 공식 문서와 절 제목이 배지로 붙습니다.

흔한 방식이 덱

설명용

진짜 git 이 심판이다

이 덱에서 "Git 은 이렇게 한다" 는 문장의 근거는 사람의 기억이 아니라 이 기계에 설치된 git 2.55.0 입니다.

  • 원리를 설명하는 장은 run_all.py 가 빈 저장소를 새로 만들고 진짜 git 을 돌려 남긴 캡처를 싣습니다. 캡처 첫 줄이 곧 그 명령입니다.
  • 부록의 미니 Git(mygit)이 만든 객체·인덱스·팩은 git fsck --strict, git cat-file, git index-pack --strict 가 받아들여야 통과입니다.
  • 시험에 쓰는 기준 바이트(golden/)도 진짜 git 이 먼저 만듭니다. 그래서 구현을 한 줄도 쓰기 전에 시험이 올바른 까닭으로 실패합니다.
  • 설명과 git 이 어긋나면 고치는 쪽은 설명입니다. 심판을 고치지 않습니다.

다섯 언어, 규격서 하나

부록 A 는 같은 미니 Git 을 다섯 언어로 만듭니다. 다섯 구현은 모두 git/SPEC.md 한 장을 따르고, 같은 기준 바이트로 시험받습니다.

언어맡은 일
Python이야기의 앞장 — 단계마다 파이썬으로 먼저 걸어 봅니다
Go · TypeScript · Java같은 단계를 같은 함수 이름으로 — 넷을 한 화면에 나란히 봅니다
C++zlib 도 없이 — inflate 와 deflate(저장 블록)까지 손으로 짭니다

SHA-1 은 다섯 언어 모두 손으로 짭니다. 표준 라이브러리의 해시는 시험에서 답을 맞춰 보는 데만 씁니다.

실험 환경 — 캡처를 세 번 똑같이 뜨려면

커밋 이름에는 작성자·시각·시간대가 들어갑니다. 이 가운데 하나만 새어 들어와도 덱의 모든 커밋 id 가 돌릴 때마다 달라집니다. 그래서 모든 실험은 이 파일을 먼저 읽습니다.

이 기계의 전역 설정(~/.gitconfig)은 읽지 않습니다. 브랜치 이름은 git init -b main 으로 실험마다 못 박습니다.

캡처 읽는 법 — 첫 줄이 명령이다

어두운 블록은 실험 스크립트가 빈 저장소를 만들고 진짜 git 을 돌려 남긴 것입니다. 블록의 첫 줄은 $ 와 그때 돌린 명령 그대로이고, 그 아래가 화면에 찍힌 전부입니다.

  • 실험 저장소는 이 기계의 긴 경로 대신 /work/<실험 이름> 으로 바꿔 적습니다. 바꾸는 것은 이 한 가지뿐이고, 바꾼 자리는 캡션이 밝힙니다.
  • 표준 출력과 표준 오류는 섞어서(2>&1 처럼) 한 블록에 담습니다.
실행 검증

실패도 캡처한다

명령이 0 이 아닌 코드로 끝나면 블록 끝에 [exit N] 이 붙습니다. 거절·충돌·오류 메시지도 지어내지 않고 git 이 낸 그대로 싣습니다.

이 거절이 왜 일어나는지는 11부(전송)와 12부(협업)에서 다룹니다. 여기서는 모양만 봐 두십시오 — ! 로 시작하는 줄과 끝의 종료 코드.

직접 다시 떠 보려면

캡처는 전부 git/run_all.py 한 파일이 만듭니다. 덱을 만드는 과정도, 독자가 다시 떠 보는 과정도 같은 make 대상을 씁니다.

실행 검증

세 번 떠서 같아야 싣는다

캡처가 그 실행의 우연 — 시각, 난수, 해시 테이블의 차례 — 에 기대면 독자가 같은 명령을 돌렸을 때 다른 답이 나옵니다. 그런 장은 증거가 아니라 그림입니다.

그래서 이 덱에는 걸린 시간을 적은 캡처가 없습니다. 크기는 바이트와 객체 수로, 속도는 비율로만 싣습니다.

실행 검증

기준 바이트 — golden/

부록 A 의 다섯 구현은 구현을 한 줄도 쓰기 전에 시험부터 가집니다. 그 시험의 답은 사람이 적지 않고, 진짜 git 이 먼저 만들어 golden/ 에 넣어 둡니다.

시험이 맨 처음 실패할 때 그 까닭이 "아직 안 만들었다" 여야 합니다. "답이 틀렸다" 로 실패하면 시험이 아니라 답을 의심해야 하니까요.

실행 검증

다섯 구현이 같은 답을 내는가

같은 대본(스물세 줄)을 다섯 언어의 미니 Git 에 돌리고, 명령마다 출력·종료 코드를 Python 판과 견줍니다. 끝난 저장소는 진짜 git 이 열어 fsck --strict 와 객체 목록으로 다시 봅니다.

팩 이름만은 견주지 않습니다. 팩 이름은 압축된 바이트의 해시인데, 압축 결과는 언어마다 달라도 되기 때문입니다. 대신 팩 안의 객체 목록을 견줍니다.

역사 근거

이 덱이 다루지 않는 것

  • 호스팅 서비스의 화면 — GitHub·GitLab 의 버튼과 메뉴는 자주 바뀌고, Git 자체가 아닙니다. 풀 리퀘스트는 12부에서 흐름으로만 다룹니다.

  • Git LFS 의 운영 — 원리(포인터 파일과 필터)는 13부에서 다루지만, 서버 쪽 설정은 다루지 않습니다.
  • 윈도·맥 고유의 동작 — 캡처는 리눅스에서 떴습니다. 대소문자·줄 끝처럼 운영체제가 갈리는 자리는 14부에서 설정으로 흉내 내어 보여 줍니다.

0부 퀴즈

Q. 어떤 장에 "실행 검증" 배지가 붙어 있는데, 그 장의 캡처 끝에 [exit 1] 이 찍혀 있습니다. 이 캡처는 믿어도 됩니까? 그리고 이 덱에 걸린 시간(초)을 적은 캡처가 없는 까닭은 무엇입니까?

A. 믿어도 됩니다. [exit 1] 은 명령이 실패했다는 기록이지 캡처가 잘못됐다는 뜻이 아닙니다 — 거절·충돌도 git 이 낸 그대로 싣습니다. 걸린 시간은 돌릴 때마다 달라 세 번 떠서 바이트까지 같아야 한다는 규칙을 통과할 수 없어서 싣지 않습니다. 크기는 바이트·객체 수로, 속도는 비율로 적습니다.

이 덱을 만든 기계

이 덱의 모든 실행은 접는 폰 한 대에서 돌았습니다. 그 제약이 실험의 크기를 정했습니다.

  • 남는 메모리가 적어, 기록 실행은 하나씩 차례로 돌립니다.
  • 큰 저장소 실험(수만 개 파일, 큰 바이너리)은 몇 분 안에 끝나는 크기로 줄였고, 그 크기는 표가 out/ 에서 가져와 보여 줍니다 — 본문에 손으로 적지 않습니다.
  • 걸린 시간은 본문에 적지 않습니다. 기계마다 다르기 때문입니다. 속도는 같은 기계에서 잰 비율로만 싣습니다.
  • git 저장소 자체의 역사는 전체를 받지 않고, 커밋과 트리만 담은 부분 복제(--filter=blob:none)로 살펴봅니다.

접힌 화면에서 읽기

이 덱은 갤럭시 폴드의 접힌 화면(약 374 px)에서도 잘리지 않도록 만들었습니다. 코드 블록은 72칸, 캡처는 108칸, 그림은 340 폭을 넘지 않습니다 — 조립기가 매번 잽니다.

  • ← → 이전·다음 장 (스와이프도 됩니다)
  • ↑ ↓ 한 장 안에서 스크롤
  • ☰ 목차 · 상단 선택 상자로 부 이동
  • 게임패드를 연결하면 십자키와 A·B 로도 넘길 수 있습니다
  • 마지막으로 본 장은 저장됩니다 — 다시 열면 그 자리로 돌아옵니다

코드·표가 가로로 넘칠 때는 그 블록만 밀립니다. 화면 전체가 밀리지는 않습니다.
