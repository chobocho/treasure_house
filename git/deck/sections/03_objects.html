객체 모델

blob · tree · commit · tag 의 바이트, 이름 짓기, 그리고 깨졌을 때

이 부에서 할 일

2부에서 "객체는 네 종류, 이름은 내용의 해시" 라고 했습니다. 이 부는 그 문장을 바이트 하나하나로 확인합니다.

  • 객체 파일 하나를 열어 압축을 풀고 머리와 몸을 나눈다
  • 네 종류마다 몸의 형식 — 특히 트리의 이진 형식과 정렬 규칙
  • 커밋 이름을 정하는 것 — 무엇이 한 글자만 달라도 새 이름이 되는가
  • 객체를 이름으로 부르는 여러 방법과, 짧은 이름이 겹칠 때
  • fsck 가 잡아내는 형식 오류들
  • SHA-1 에서 SHA-256 으로

부록 A 의 미니 Git 이 이 부의 규칙을 그대로 구현합니다. 이 부에는 그 Python 판의 핵심 몇 줄만 싣습니다.

파일은 어디에 있나

느슨한(loose) 객체는 객체 하나가 파일 하나입니다. 이름 40글자 가운데 앞 두 글자가 디렉터리, 나머지 38글자가 파일 이름입니다.

공식 문서는 이렇게 나누는 까닭을 "한 디렉터리에 항목이 너무 많으면 느려지는 파일 시스템이 있어서" 라고 적습니다. 앞 두 글자로 나누면 디렉터리가 최대 256개로 퍼집니다.

파일의 바이트 그대로

  • 첫 두 바이트 78 01 — zlib 스트림의 머리입니다(압축 방식 deflate, 가장 빠른 수준). git 은 느슨한 객체를 기본으로 수준 1 로 누릅니다(core.looseCompression).
  • 끝의 네 바이트 — 풀어 낸 바이트의 Adler-32 검사값입니다. 2부에서 한 바이트를 뒤집었을 때 fsck 가 "incorrect data check" 라고 한 것이 이것입니다.
  • 그 사이가 deflate 로 눌린 몸입니다. 이대로는 사람이 읽을 수 없습니다.

  • 이름의 바이트로 정렬합니다(로캘과 무관 — LC_ALL=C 와 같은 비교).

작습니다. 그래서 디렉터리 a 는 a.b 와 a=b 사이에 옵니다.

차례와 어긋나지 않습니다. / 규칙은 이 두 차례를 맞추려고 있는 셈입니다.

커밋 바이트가 달라 이름이 다릅니다.

git fsck(엄하게 보려면 --strict)가 잡습니다. 받는 쪽이
transfer.fsckObjects 를 켜 두면 주고받을 때 검사합니다(14부).

SHA-1 이 깨진 날


2017-02-23, CWI 와 Google 이 내용이 다른 두 PDF 가 같은 SHA-1 을 갖게 만든 첫 충돌(SHAttered)을
발표했습니다. 발표문이 밝힌 계산량은 SHA-1 약 9.2×10¹⁸ 번입니다.


    

  • git 은 2.13.0(2017-05-09)부터 충돌 탐지 SHA-1(sha1dc)을 기본으로 씁니다. SHAttered 같은
공격 패턴이 담긴 입력을 해시하려 하면 멈춥니다.
    • 

  • 근본 대책은 해시 함수를 바꾸는 것 — SHA-256 저장소입니다.
    •

64글자가 되니 몸도 달라집니다. 트리 항목의 이진 이름도 20바이트가 아니라 32바이트입니다.

아직 서로 섞이지 않는다



2026-09 기준 git 2.55.0 은 SHA-1 저장소와 SHA-256 저장소 사이에 객체를 주고받지 못합니다.
SHA-256 지원은 2.29.0 에서 실험 기능으로 들어왔고, Git 3.0 은 새 저장소의 기본을 SHA-256 으로
바꿀 계획입니다(출시일은 정해지지 않았습니다). 14부에서 전환의 현주소를 다시 봅니다.
