실행 검증

항목 머리 — 형식 3비트, 크기는 가변 길이

첫 바이트의 가운데 3비트가 형식, 아래 4비트가 크기의 시작입니다. 맨 위 비트가 1 이면 다음 바이트가 크기의 나머지를 7비트씩 잇습니다.

번호형식
1 · 2 · 3 · 4commit · tree · blob · tag — 온전한 객체(zlib)
6OFS_DELTA — 같은 팩 안, 몇 바이트 앞의 객체를 바탕으로 한 델타
7REF_DELTA — 이름(20바이트)으로 가리킨 객체를 바탕으로 한 델타

앞 장의 97 0d: 0x97 = 1001 0111 → 형식 1(commit), 크기 아래 4비트 7, 이어서 0x0d(13) × 16 = 208 → 크기 215.

1~2장 퀴즈


Q. 팩 항목 머리가 35(16진) 한 바이트입니다. 형식과 크기는? 그리고 OFS_DELTA 와 REF_DELTA 는 바탕을 어떻게 가리킵니까?



A. 0x35 = 0011 0101 — 맨 위 비트 0 이라 이 바이트로 끝, 형식 3(blob), 크기 5. OFS_DELTA 는 "이 항목보다
몇 바이트 앞" 이라는 거리로, REF_DELTA 는 바탕 객체의 이름(20바이트)으로 가리킵니다. 거리는 짧고 이름은 길어서 같은 팩 안에서는
OFS_DELTA 를 씁니다. REF_DELTA 는 바탕이 팩 밖에 있을 수 있는 얇은 팩(11부)에서 쓰입니다.

.idx — 이름에서 팩 안 자리로




팩은 앞에서부터만 읽을 수 있어서, 이름으로 객체를 찾으려면 색인이 필요합니다. .idx 는 이름 차례로 정렬된 표이고,
첫 바이트별 누적 개수(fanout 256칸)로 이분 탐색의 범위를 좁힙니다.



이 캡처를 처음 뜰 때 < .git/objects/pack/*.idx 의 * 를 dash 가 펼치지 않아 "cannot open" 이 찍혔습니다.
$(ls …) 로 고쳤습니다.

실행 검증






.rev — 거꾸로 찾는 색인


.idx 가 "이름 → 자리" 라면 .rev 는 "팩 안 차례 → 이름 차례" 입니다. 비트맵과 크기 계산처럼 팩을 자리 차례로 돌며
이름을 알아야 하는 일에 씁니다. 1장의 ls 에 이미 있었습니다.


문서 근거






multi-pack-index — 팩이 여럿일 때



팩이 수십 개면 객체 하나를 찾으려고 .idx 를 수십 개 열어야 합니다. MIDX 는 모든 팩을 한 색인으로 묶습니다.


실행 검증






비트맵 — "이 커밋에서 닿는 객체" 를 미리



clone·fetch 에 응할 때 서버는 "이 커밋들에서 닿는 객체 전부" 를 세야 합니다. 비트맵은 골라 둔 커밋마다 팩의 객체를 비트 하나씩으로
표시해 두어, 그래프를 걷지 않고 비트 연산으로 답합니다.


실행 검증






commit-graph — 커밋 걷기를 빠르게




커밋마다 부모·트리·세대 번호를 고정 폭 표로 담아, 커밋 객체를 풀지 않고 DAG 를 걷게 합니다. log --graph·
merge-base 가 큰 저장소에서 빨라지는 까닭입니다.

닿지 않는 커밋 하나


브랜치를 만들어 빈 커밋을 하나 쌓고 그 브랜치를 지웠습니다. 그 커밋은 이제 어느 참조에서도 닿지 않습니다(reflog 는 셈에서 뺌).




unreachable 은 닿지 않는 모든 객체, dangling 은 그 가운데 다른 닿지 않는 객체도 가리키지 않는 끝입니다.

실행 검증






정말 지우기 — reflog 를 비우고 prune




평소에는 이렇게 빨리 지워지지 않습니다. reflog 는 90일·30일 동안 커밋을 붙잡고(4부), prune 도 기본으로 두 주보다 새 객체는 남깁니다
(gc.pruneExpire). 잘못한 것을 되돌릴 시간을 주는 장치입니다.

크러프트 팩 — 지울 때까지 한 팩에




유예 기간 안의 닿지 않는 객체를 예전에는 느슨한 파일로 흩어 두었습니다. 크러프트 팩은 그것들을 팩 하나에 모으고, 객체마다의 시각을
.mtimes 에 적어 유예 기간을 계속 셉니다.

자동 gc
문턱이 실제로 계산되는 방식





문서가 말하는 문턱


gc.auto 는 "대략 이보다 많은 느슨한 객체가 있으면 git gc --auto 가 팩으로 묶는다" 이고 기본값은 6700 입니다.
커밋 같은 명령들이 가끔 gc --auto 를 부릅니다. 팩이 50개(gc.autoPackLimit)를 넘어도 합칩니다.



"대략" 이 무엇인지 실험해 봤습니다.

문서 근거






gc.auto=20 인데 30개로는 돌지 않는다





실행 검증






소스를 열어 보면 (v2.55.0)


    

  • builtin/gc.c — 문턱을 256 의 배수로 올려 씁니다. 20 은 256 이 됩니다. 소스 주석은 이것을 "옛 동작을 지키려는 이상한 규칙" 이라고 적습니다.
    • 

  • odb/source-loose.c — 느슨한 객체를 다 세지 않고 objects/17 디렉터리 하나의 수 × 256 으로 어림합니다.
이름은 해시라 256 개 디렉터리에 고르게 퍼진다는 가정입니다.
    • 



그러니 17/ 에 객체가 둘 이상(어림 512 > 256)이어야 돕니다. 30개일 때 17/ 은 비어 있었습니다.

역사 근거






17 로 시작하는 blob 둘을 넣으면





남은 둘은 어느 커밋도 가리키지 않는 새 blob 이라 유예 기간 동안 느슨하게 남습니다. 그 둘이 여전히 17/ 에 있어 어림이 512 이니
git 이 "닿지 않는 느슨한 객체가 너무 많다" 고 경고합니다.


실험은 gc.autoDetach=false 로 돌렸습니다. 기본값(true)에서는 gc --auto 가 뒤에서 돌아, 바로 뒤의 캡처가 끝나기 전 상태를 찍었습니다.

실행 검증






git maintenance



maintenance 는 gc 를 작은 작업들(commit-graph 쓰기, 느슨한 객체 묶기, 팩 조금씩 합치기 …)로 나눠 예약해 돌리는 틀입니다.
git maintenance start 가 운영체제의 예약 작업(cron·systemd 타이머 등)에 등록합니다(13부).

팩이 둘 남았습니다. 거대한 옛 역사를 한 번 잘 싸 두고 매번 다시 싸지 않게 할 때 씁니다.

5~6장 퀴즈


Q. 실수로 브랜치를 -D 로 지웠고, 곧바로 git gc 를 돌렸습니다. 커밋을 되찾을 수 있습니까? 그리고 느슨한 객체가
6,000개인데 gc --auto 가 돌았다면 왜일까요?



A. 대개 되찾습니다 — HEAD 의 reflog 가 그 커밋을 가리키고 있어 닿는 객체로 치고, 닿지 않더라도 prune 의 유예 기간(기본 두 주)
동안은 지우지 않습니다. reflog 에서 이름을 찾아 브랜치를 다시 만들면 됩니다(16부). 6,000개에서 돌았다면 objects/17 의 수 × 256 이
6,912(6,700 을 256 배수로 올린 값)를 넘었기 때문입니다 — 17/ 에 객체가 스물여덟 개 이상이었던 것입니다.
