부록 A · 만들면서 배우는 Git

같은 규격서, 다섯 언어, 진짜 git 이 채점한다

이 부에서 할 일

2~11부에서 들여다본 형식을 직접 만들어 봅니다. 이름은 mygit — git 의 작은 부분집합입니다.

  • 규격서 하나(SPEC.md)를 Python·TypeScript·Go·Java·C++ 다섯 언어로 구현했습니다.
  • 열두 단계: SHA-1 → zlib·느슨한 객체 → blob → tree → commit·참조 → 인덱스 → log·merge-base → diff → switch → merge → 팩 → 전송.
  • 채점은 진짜 git 이 합니다 — 기대 출력(golden/)은 git 2.55.0 이 만든 바이트이고, mygit 이 만든 저장소는 git fsck --strict 를 통과해야 합니다.
  • 끝에 다섯 구현의 소스 전문을 싣습니다.
설명용

한 단계를 만드는 순서

  1. 규격 — SPEC.md 의 그 절을 읽습니다. 모르는 동작은 진짜 git 으로 확인하고 규격에 적습니다.
  2. 빨강 — 모든 함수를 "아직 없음"(종료 코드 99)으로 두고 시험을 돌려, 시험이 그 이유로 실패하는지 봅니다.
  3. 초록 — 시험이 통과할 만큼만 구현합니다.
  4. 대조 — 같은 대본을 다섯 구현으로 돌려 출력이 같은지, 진짜 git 이 그 저장소를 받아들이는지 봅니다.

빨강을 거치지 않은 시험은 아무것도 시험하지 않을 수 있습니다 — 늘 초록인 시험은 아무 말도 하지 않습니다(SPEC.md §16.3).

대조표

칸마다 세 가지를 봤습니다: 명령마다의 표준 출력·표준 오류·종료 코드가 Python 과 같은가(팩 이름은 뺌 — 압축 바이트는 구현마다 달라도 된다), 진짜 git 이 그 저장소에 fsck --strict 를 통과시키는가, 객체 목록이 같은가.

다섯 구현의 소스 전문

파일 개 · 줄

전문을 읽는 법

  • 언어마다 같은 차례 — sha1 · zlib · objects · tree · commit · refs · index · worktree · walk · diff · merge · pack · transport · cli, 그리고 오류 형과 진입점.
  • 한 장의 코드는 최상위 정의가 시작되는 줄에서 끊었습니다(함수 한가운데서 자르지 않음). 오른쪽 위의 n/m 은 그 파일의 몇째 장인지입니다.
  • 모든 줄은 저장소의 실물 그대로이고, 조립기가 한 줄도 빠지지 않았는지 셉니다. 시험 코드는 발췌만 싣습니다.
  • 앞의 단계별 장에서 이미 본 함수도 여기서 한 번 더 나옵니다 — 맥락 없이 처음부터 끝까지 읽을 수 있게.
