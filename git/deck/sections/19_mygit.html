19부

부록 A · 만들면서 배우는 Git

같은 규격서, 다섯 언어, 진짜 git 이 채점한다

이 부에서 할 일

2~11부에서 들여다본 형식을 직접 만들어 봅니다. 이름은 mygit — git 의 작은 부분집합입니다.

  • 규격서 하나(SPEC.md)를 Python·TypeScript·Go·Java·C++ 다섯 언어로 구현했습니다.
  • 열두 단계: SHA-1 → zlib·느슨한 객체 → blob → tree → commit·참조 → 인덱스 → log·merge-base → diff → switch → merge → 팩 → 전송.
  • 채점은 진짜 git 이 합니다 — 기대 출력(golden/)은 git 2.55.0 이 만든 바이트이고, mygit 이 만든 저장소는 git fsck --strict 를 통과해야 합니다.
  • 끝에 다섯 구현의 소스 전문을 싣습니다.
설명용

한 단계를 만드는 순서

  1. 규격 — SPEC.md 의 그 절을 읽습니다. 모르는 동작은 진짜 git 으로 확인하고 규격에 적습니다.
  2. 빨강 — 모든 함수를 "아직 없음"(종료 코드 99)으로 두고 시험을 돌려, 시험이 그 이유로 실패하는지 봅니다.
  3. 초록 — 시험이 통과할 만큼만 구현합니다.
  4. 대조 — 같은 대본을 다섯 구현으로 돌려 출력이 같은지, 진짜 git 이 그 저장소를 받아들이는지 봅니다.

빨강을 거치지 않은 시험은 아무것도 시험하지 않을 수 있습니다 — 늘 초록인 시험은 아무 말도 하지 않습니다(SPEC.md §16.3).

설명용

1장

SHA-1 을 손으로

1단계 · SPEC §2 · 모든 이름이 여기서 나온다

무엇을 만드나

  • 입력을 64바이트 블록으로 자르고, 블록마다 80라운드로 상태 다섯 개(32비트)를 섞습니다.
  • 끝에 0x80 한 바이트, 0 들, 그리고 입력의 비트 길이(64비트)를 덧붙여 블록을 채웁니다.
  • 상태 다섯 개를 이어 붙인 20바이트가 답 — 16진으로 쓰면 git 이 보여 주는 40글자입니다.

표준 라이브러리를 부르면 한 줄이지만, 그러면 "40글자 이름이 어디서 오나" 가 블랙박스로 남습니다. 다섯 언어 모두 같은 80라운드를 직접 돌고, 표준 라이브러리는 시험에서 답을 맞춰 볼 때만 씁니다. 3부에서 본 객체 이름이 이 함수의 출력입니다.

설명용

한 블록 — 80라운드

앞 16단어는 블록 그대로, 나머지 64단어는 3·8·14·16 칸 앞의 네 단어를 XOR 해 한 비트 돌려 만듭니다. 라운드는 20개씩 네 구간으로 나뉘어 섞는 함수와 상수가 바뀝니다. 파이썬 정수는 넘치지 않으므로 & MASK 로 32비트 덧셈을 흉내 냅니다.

실행 검증

덧붙임과 마무리

남은 바이트가 55개 이하면 덧붙임이 한 블록에, 56개부터는 두 블록에 들어갑니다. 시험은 이 경계를 촘촘히 봅니다. 마무리는 사본에서 하므로 digest 를 두 번 불러도 같은 답입니다 — 인덱스와 팩의 끝 체크섬을 읽어 가며 셀 때 이 스트리밍 꼴을 씁니다(5·10부).

1장 퀴즈

Q. 입력이 55바이트일 때와 56바이트일 때, 마지막에 압축 함수를 몇 번 부릅니까? 그리고 왜 시험이 이 경계를 따로 봅니까?

A. 55바이트면 0x80 한 바이트와 길이 8바이트까지 64바이트 한 블록에 들어가 한 번, 56바이트면 0x80 을 넣고 나면 길이 8바이트가 들어갈 자리가 없어 두 블록 — 두 번입니다. 덧붙임 계산이 한 바이트만 틀려도 이 경계에서만 답이 달라지므로, 경계 양쪽을 시험하지 않으면 버그가 숨습니다.
설명용

2장

zlib 과 느슨한 객체

2단계 · SPEC §3·§4.1·§4.6 · 이름 = SHA-1(머리 + 몸)

무엇을 만드나

  • 객체의 바이트 = "<형식> <크기>\0" + 몸. 이름은 그 바이트의 SHA-1.
  • 느슨한 객체 파일 = 그 바이트를 zlib 으로 누른 것, 자리는 .git/objects/앞2글자/나머지38글자(3부).
  • 팩 안에서는 "zlib 스트림이 몇 바이트에서 끝나는가" 가 필요합니다 — 다음 항목이 거기서 시작하기 때문입니다(11단계).

Python·TypeScript·Go·Java 는 표준 zlib 을 씁니다. C++ 만은 이 기계에 zlib 이 없어 풀기(inflate)와 싸기(deflate)를 손으로 짰습니다.

설명용

이름 짓기 — 저장소를 건드리지 않고

세 줄이 git 이 "내용 주소 저장소" 인 까닭 전부입니다. 같은 내용은 어느 저장소에서 누가 만들어도 같은 이름을 얻습니다.

실행 검증

쓰기 — 임시 파일에 쓰고 이름 바꾸기

이름이 같으면 내용도 같으니 이미 있는 객체는 다시 쓰지 않습니다. 임시 파일에 다 쓴 뒤 이름을 바꿔 넣어, 도중에 죽어도 반쯤 쓴 객체가 남지 않습니다. 권한 0444 는 git 이 느슨한 객체에 주는 권한과 같습니다.

실행 검증

스트림이 끝나는 자리

먹은 수에는 zlib 의 머리 2바이트와 Adler-32 꼬리 4바이트가 들어갑니다. zlib.decompress 는 이것을 알려 주지 않아 decompressobj 의 unused_data 로 셉니다.

실행 검증

C++ — 누르지 않는 deflate

git 은 객체의 이름을 푼 바이트로 정하므로, 누르지 않고 저장 블록에 싼 객체도 똑같이 읽습니다. 그래서 C++ 의 느슨한 객체는 크지만 이름과 내용은 다른 네 구현과 같습니다. 팩 이름(팩 바이트의 SHA-1)만은 달라지는데, 대조표가 팩 이름을 견주지 않는 까닭입니다.

Q. 디렉터리 a 와 파일 a.b, a0 이 한 트리에 있습니다. 항목의 차례는? 누군가 하위 트리도 그냥 이름으로 정렬했다면 무슨 일이 생깁니까?

5장

commit · 참조 · HEAD

5단계 · SPEC §4.4·§4.5·§6

무엇을 만드나

  • tie — 지운·끼운 줄의 수는 같지만 고른 자리가 다른 쌍. 수가 같으면 합격

switch — 작업 트리 쓰기

9단계 · SPEC §9.3 · 두 갈래 합치기

무엇을 만드나

옛 커밋의 트리에서 새 커밋의 트리로 작업 트리와 인덱스를 옮깁니다. 규칙은 경로마다 하나입니다:

  • 옛 트리와 새 트리에서 같은 경로는 손대지 않는다 — 그래서 고친 파일이 새 브랜치로 따라온다(6부).

  • 옛 트리에 없던 경로에 추적 안 하는 파일이 있으면 그것도 멈춘다.

하나라도 걸리면 아무것도 바꾸지 않고 멈춥니다 — 반쯤 옮긴 작업 트리가 가장 나쁜 결과이기 때문입니다.

10장

merge — 3-way 와 충돌

10단계 · SPEC §12

두 층의 합치기

  • 트리 층 — 경로마다 세 판(기준 B·우리 O·그들 T)을 "세 줄 규칙" 으로: O = T 거나 B = T 면 O, B = O 면 T, 아니면 내용을 합친다(7부).
  • 파일 층 — git 의 xdl_merge(ZEALOUS 수준)를 따른다. B→O, B→T 의 바뀐 곳을 B 좌표로 짝지어, 겹치거나 맞닿으면 충돌 후보.

파일 층의 경계 규칙 — 맞닿으면 충돌, 한 줄 떨어지면 깨끗, 사이가 3줄 이하면 두 충돌을 하나로 붙임 — 은 모두 진짜 git merge 로 확인한 것입니다(golden/scen/merge-*.scn).

설명용

트리 층 — 세 줄 규칙

"없음" 도 값입니다. 한쪽만 지웠고 다른 쪽이 그대로면 지움이 이깁니다. 한쪽은 고치고 한쪽은 지운 경우(modify/delete)와 모드가 엇갈린 경우는 mygit 이 다루지 않는 범위라 분명한 오류로 멈춥니다.

실행 검증

파일 층 1 — 짝짓기

조건이 x[0] + x[2] < y[0](엄격히 앞섬)이라, O 의 바뀐 곳이 끝나는 바로 그 줄에서 T 의 바뀐 곳이 시작하면 — 맞닿으면 — 충돌 후보가 됩니다. 7부에서 "붙어 있는 두 줄을 따로 고쳐도 충돌" 이던 까닭이 이 부등호입니다.
