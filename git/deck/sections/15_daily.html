활용 가이드 I — 일상

좋은 커밋을 만드는 손버릇

이 부에서 할 일

2~14부가 git 의 속을 봤다면, 이 부는 날마다 손에 붙이는 레시피입니다. 모두 실제로 돌린 캡처로 확인합니다.

  • 좋은 커밋 — 한 커밋에 한 가지 일
  • 부분 스테이징 — add -p 와 reset -p
  • stash 레시피 — 파일 하나만, 브랜치로 꺼내기
  • 작업 정리 — --fixup 과 autosquash
  • 로그 탐색 레시피 — 누가·언제·무엇·어디
  • 별칭, 셸 프롬프트와 자동완성
설명용

1장

좋은 커밋

나중에 읽을 사람을 위해

커밋은 무엇을 위해 쪼개는가

커밋 하나는 되돌리기(revert), 골라 옮기기(cherry-pick), 범인 찾기(bisect)의 단위입니다(8·9부). 그래서:

  • 한 커밋에 한 가지 일 — 버그 고침과 이름 바꾸기가 섞이면 고침만 되돌릴 수 없습니다.
  • 커밋마다 빌드가 된다 — bisect 가 중간 커밋을 꺼냈을 때 "안 빌드됨" 은 판정이 아니라 잡음입니다.
  • 메시지는 왜를 적는다 — 무엇이 바뀌었는지는 diff 가 이미 말합니다.

이 장의 도구들 — 부분 스테이징, stash, fixup — 은 모두 "작업은 뒤섞여 했지만 커밋은 깔끔하게" 를 위한 것입니다.

설명용

메시지의 모양

parser: 빈 줄에서 멈추지 않게 한다

빈 줄을 만나면 파일 끝으로 여겨 뒤의 항목을 버렸다.
이제 빈 줄은 건너뛰고, 진짜 EOF 에서만 멈춘다.

git 설명서가 권하는 모양은 50자 이하의 한 줄 요약, 빈 줄, 그리고 자세한 본문입니다. 첫 줄이 log --oneline·shortlog·메일 패치의 제목(12부의 format-patch)이 되기 때문입니다.

설명용

첫 줄이 쓰이는 자리

여기 쓴 feat:·fix: 같은 머리말은 팀의 약속일 뿐 git 이 아는 것이 아닙니다. 다만 약속이 있으면 5장의 --grep 으로 골라내기 쉬워집니다.

실행 검증

2장

부분 스테이징

한 파일의 고침을 두 커밋으로

한 파일에 두 가지 일

20줄짜리 파일의 2번째 줄과 19번째 줄을 고쳤습니다. 둘은 서로 다른 일이라 따로 커밋하고 싶습니다.

두 고침 사이가 멀어 diff 는 덩어리(hunk) 둘로 나뉩니다(9부의 문맥 줄 — 기본 3줄). add -p 는 덩어리마다 올릴지 묻습니다.

실행 검증

add -p — 첫째만 y, 둘째는 n

평소엔 키보드로 답합니다. 여기서는 캡처를 위해 printf 'y\nn\n' 로 답을 흘려 넣었습니다.

실행 검증

인덱스와 작업 트리가 반씩

한 파일이 "스테이징됨" 과 "안 됨" 에 동시에 걸쳐 있습니다. 인덱스가 작업 트리와 따로 노는 셋째 사본이기 때문입니다(5부). 이제 git commit 은 2번째 줄 고침만 담습니다.

실행 검증

답의 뜻 — ? 를 누르면

앞 쪽의 둘째 물음에는 k·j 가 빠져 있었습니다 — 아직 답하지 않은 다른 덩어리가 있을 때만 보입니다. 덩어리를 더 쪼갤 수 있을 때는 s(split)가 붙습니다.

실행 검증

쪼갤 수 없을 때는 e

s 는 바뀐 줄 사이에 안 바뀐 줄이 있어야 쪼갭니다. 붙어 있는 두 줄 중 하나만 올리려면 e 로 패치를 편집기에서 직접 고칩니다:

  • 올리지 않을 + 줄은 지웁니다.
  • 올리지 않을 - 줄은 - 를 공백으로 바꿔 문맥 줄로 만듭니다.

git 은 고친 패치를 인덱스에 적용해 보고, 안 맞으면 다시 묻습니다.

설명용

반대 방향 — reset -p

너무 많이 올렸으면 reset -p 가 같은 방식으로 덩어리마다 내릴지 묻습니다.

같은 식구로 restore -p(작업 트리의 고침을 덩어리째 버리기), stash -p, checkout -p 가 있습니다.

실행 검증

3장

stash 레시피

6부의 stash 를 일상에서

파일 하나만 치우기

a.txt 와 b.txt 를 둘 다 고쳤는데, a.txt 만 잠깐 치우고 싶습니다. stash push 는 -- 뒤에 경로를 받습니다.

-m 이 없으면 목록엔 "WIP on main: 해시 제목" 만 남아, 몇 개 쌓이면 무엇이 무엇인지 모릅니다.

실행 검증

stash branch — 충돌 없이 꺼내기

stash 를 만든 그 커밋에서 새 브랜치를 만들고 그 위에 꺼냅니다. 그 사이 원래 브랜치가 많이 달라져 stash pop 이 충돌하는 경우의 탈출구입니다 — 만든 자리에서 꺼내니 충돌이 없습니다. 꺼내기에 성공하면 그 stash 는 지웁니다.

실행 검증

그 밖의 stash 선택지

선택지하는 일
-u추적 안 되는 파일도 치운다 (기본은 추적되는 파일만)
-k치우되 인덱스는 그대로 둔다 — 올린 것만으로 테스트할 때
-S인덱스에 올린 것만 치운다
-p덩어리마다 물어 고른 것만 치운다
show -p stash@{1}꺼내지 않고 내용만 본다

stash 는 커밋 객체이고 목록은 refs/stash 의 reflog 라는 것 — 그래서 drop 한 것도 16부처럼 되살릴 수 있다는 것 — 은 6부에서 봤습니다.

설명용

4장

작업 정리 — fixup

리뷰 지적을 원래 커밋에 붙이기

--fixup 커밋

feat 브랜치에 "add parser"·"add printer" 두 커밋이 있습니다. 리뷰에서 parser 의 실수를 지적받았습니다. 고친 것을 새 커밋으로 쌓지 않고 원래 커밋에 붙이도록 표시합니다.

제목이 fixup! add parser 인 커밋이 생깁니다. :/글 은 메시지가 그 글(정규식)에 맞는 가장 최근 커밋입니다 — 어느 ref 에서든 닿는 커밋 가운데서.

실행 검증

autosquash 가 제자리로 옮겨 합친다

rebase 의 할 일 목록에서 fixup! 커밋이 대상 커밋 바로 밑으로 옮겨지고 pick 이 fixup 으로 바뀝니다. 목록을 그대로 받아들이려고 GIT_SEQUENCE_EDITOR=true 를 줬습니다(8부의 그 요령).

실행 검증

메시지만 고치기 — --fixup=reword:

amend! 커밋은 합칠 때 대상의 메시지를 자기 본문으로 바꿉니다. --fixup=amend: 는 내용과 메시지를 함께, reword: 는 메시지만입니다. -m 과 함께 쓰면 git 이 거절하므로, 여기서는 편집기 자리에 sed 스크립트를 줬습니다.

실행 검증

언제 쓰는가

  • 아직 push 하지 않은 브랜치, 또는 리뷰 중이라 강제 push 를 약속한 브랜치에서(12부의 --force-with-lease).
  • 공유된 main 에서는 쓰지 않습니다 — 역사를 새로 쓰기 때문입니다(8부).
  • 리뷰어에게는 fixup 커밋을 그대로 보여 주고 "고친 것만" 보게 한 다음, 머지 직전에 autosquash 로 합치는 팀도 있습니다.

8부의 autosquash 실험(--fixup HEAD~2)과 같은 기계입니다.

실행 검증

1~4장 퀴즈

Q. 한 파일에서 버그를 고치다가 옆 함수의 이름도 바꿨습니다. 두 고침은 10줄 떨어져 있습니다. 커밋 둘로 나누는 방법은? 그리고 이미 커밋한 뒤에 버그 고침에 한 줄 빠진 것을 알았다면?

A. git add -p 로 버그 덩어리만 y, 이름 바꾸기는 n 해서 커밋하고, 나머지를 다시 커밋합니다(10줄이면 문맥 3줄을 넘어 덩어리가 나뉩니다). 빠진 한 줄은 git commit --fixup=<버그 커밋> 으로 표시한 뒤 git rebase -i --autosquash 로 제자리에 합칩니다 — push 하기 전이라면.
설명용

5장

로그 탐색 레시피

누가·무엇·어디·언제

실험 저장소

세 사람이 번갈아 커밋한 다섯 커밋입니다. 시간은 한 시간 간격입니다.

이 장의 명령은 모두 이 저장소에서 돌렸습니다. 커밋을 거르는 선택지는 log·rev-list·shortlog 가 함께 씁니다.

실행 검증

누가 — --author

--author 는 "이름 <메일>" 전체에 정규식으로 맞춥니다. 여러 번 주면 그중 하나에 맞는 커밋입니다. 커밋한 사람으로 거르려면 --committer 입니다(3부의 작성자와 커미터).

실행 검증

무엇 — --grep 과 -i

--grep 은 메시지 전체(본문 포함)를 봅니다. --author 와 같이 주면 둘 다 맞아야 하고, --grep 을 여러 번 주면 하나만 맞아도 됩니다 — 모두 맞게 하려면 --all-match.

실행 검증

어디 — 경로

-- 는 "여기서부터 경로" 라는 표시입니다. README 라는 브랜치가 있어도 헷갈리지 않습니다. 이름이 바뀐 파일을 넘어 따라가려면 --follow(9부 4장 — 이름 바꾸기와 복사)입니다.

실행 검증

언제 — --since·--until

여기선 캡처가 날마다 바뀌지 않도록 유닉스 시각을 줬습니다. 평소엔 --since="2 weeks ago"·--since=2026-09-01 처럼 씁니다. 기준은 커미터 시각이라, rebase 로 옮긴 옛 커밋은 "새" 커밋으로 잡힙니다.

실행 검증

순서와 개수

-2(= -n 2)는 거른 뒤 앞에서 두 개입니다. --reverse 와 같이 쓰면 먼저 두 개를 고르고 나서 뒤집습니다 — "처음 두 커밋" 이 아니라 "마지막 두 커밋을 옛것부터" 입니다.

실행 검증

파일을 처음 만든 커밋

--diff-filter 의 글자는 A 추가·D 삭제·M 수정·R 이름 바꿈 들입니다. 소문자로 쓰면 반대로 뺍니다. 지워진 파일을 찾는 --diff-filter=D 는 16부의 복구 장면에서 다시 씁니다.

실행 검증

코드 속 글을 찾는 곡괭이(pickaxe) — -S 와 -G

세 커밋: frotz(a); 추가 → x = frotz(a); 로 고침 → 지움.

"keep result" 는 그 줄을 고쳤지만 frotz(a) 의 개수는 1 그대로라 -S 에 안 걸립니다. "이 함수 호출이 언제 생기고 언제 사라졌나" 는 -S, "이 호출을 건드린 모든 커밋" 은 -G 입니다.

실행 검증

메시지로 커밋 하나 집기 — :/

해시를 몰라도 됩니다. 리비전 문법이라 show·diff·--fixup(4장) 어디에나 씁니다.

실행 검증

실행 검증

사람별로 세기 — shortlog

두 명령 모두 HEAD 를 적었습니다. 다음 쪽이 그 까닭입니다.

실행 검증

함정 — 리비전 없는 shortlog

리비전을 안 주고 표준 입력이 터미널이 아니면, shortlog 는 저장소가 아니라 표준 입력에서 git log 출력을 읽습니다. 스크립트·CI·별칭에서 git shortlog -sn 이 조용히 빈 출력을 내는 까닭입니다. 이 실험의 첫 판도 그렇게 빈 캡처를 냈습니다.

실행 검증

옛 커밋 속에서 찾기 — git grep

git grep 은 작업 트리 대신 커밋의 트리를 뒤질 수 있습니다. 꺼내지 않고 옛 판에서 찾습니다. 출력 앞머리의 HEAD~2: 가 어느 트리에서 찾았는지 알려 줍니다. 추적되는 파일만 보므로 빌드 산출물에 걸리지 않는 것도 grep -r 보다 나은 점입니다.

설명용

5장 퀴즈

Q. "누가 MAX_RETRY 상수를 지웠나?" 를 찾는 명령은? 그리고 CI 스크립트에 넣은 git shortlog -sn 이 빈 출력을 내는 까닭과 고치는 법은?

A. git log -S MAX_RETRY --oneline — 개수가 줄어든 커밋이 걸립니다(생긴 커밋도 같이 나오니 -p 로 확인합니다). shortlog 는 리비전이 없고 표준 입력이 터미널이 아니면 입력에서 log 를 읽으려 해서 빈 출력입니다. git shortlog -sn HEAD 처럼 리비전을 적습니다.
설명용

6장

별칭

자주 치는 것을 짧게

별칭 여섯

설정 한 줄이 명령 하나입니다. git config --global alias.st "status -sb" 처럼 전역에 두면 모든 저장소에서 씁니다. ! 로 시작하면 git 명령이 아니라 셸 명령으로 돌립니다.

실행 검증

써 보기

who 는 !git shortlog -sn --no-merges HEAD 입니다. 5장의 함정 때문에 HEAD 가 없으면 이 별칭은 파이프 안에서 빈 출력을 냅니다.

실행 검증

별칭의 규칙

  • 진짜 git 명령과 이름이 같으면 별칭은 무시됩니다 — alias.log 로 log 를 바꿀 수 없습니다.
  • 별칭 뒤에 붙인 인자는 끝에 이어 붙습니다 — git lg -3 은 log --oneline --graph --decorate -3.
  • ! 별칭은 저장소 최상위 디렉터리에서 돕니다.
  • 별칭이 다른 별칭을 부를 수 있지만, 돌고 돌면 git 이 끊습니다.
설명용

7장

프롬프트와 자동완성

git 이 싣고 오는 셸 스크립트 둘

git-prompt.sh 와 git-completion.bash

둘 다 git 소스의 contrib/completion/ 에 들어 있고, 배포판 패키지가 어딘가에 깔아 둡니다. 자리는 패키지마다 다릅니다 — 이 덱의 git 에선 git --exec-path 에서 두 단계 위의 etc/bash_completion.d 였습니다. bash 의 완성 기능을 켜 두었다면 보통 따로 할 일이 없습니다.

실행 검증

__git_ps1 부르기

실제 셸에서는 ~/.bashrc 에 PS1='\W$(__git_ps1 " (%s)")\$ ' 처럼 넣어 프롬프트마다 부릅니다. GIT_PS1_SHOW… 변수로 표시할 것을 켭니다.
