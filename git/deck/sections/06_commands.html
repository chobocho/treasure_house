6부

명령 해부

명령 하나가 세 영역의 어느 칸을 바꾸는가

이 부에서 할 일

2~5부에서 객체·참조·인덱스를 따로 봤습니다. 이 부는 날마다 쓰는 명령 스무 가지를 하나씩 돌려, HEAD · 인덱스 · 작업 트리 가운데 어느 칸이 바뀌는지 표로 확인합니다.

  • add · commit · commit -a · amend
  • rm · rm --cached · mv
  • restore(세 가지) · checkout -- 파일
  • reset --soft · --mixed · --hard · reset -- 경로
  • switch — 변경을 들고 가기와 거절
  • stash — 커밋 두세 개로 된 보관함
  • clean · 그리고 보는 명령들(status · diff · log · show)
설명용

상태 표 읽는 법

실험은 모두 같은 출발점 — 파일 a b c, 커밋 둘(둘째에서 b 를 고침) — 에서 새로 시작합니다. 명령 앞뒤로 이 도구를 돌립니다.

칸이 - 면 그 영역에 그 경로가 없다는 뜻입니다. 세 칸이 모두 같으면 그 파일은 깨끗합니다.

실행 검증

1장

add 와 commit

작업 트리 → 인덱스 → HEAD

git add — 작업 트리를 인덱스로

a 를 고친 뒤(a1 → a2) add 합니다.

바뀐 칸은 index 하나 — 작업 트리의 c1827f0 이 인덱스로 복사됐습니다. HEAD 는 그대로입니다.

실행 검증

git add — 새 파일

추적하지 않는 파일 d 를 만들고 add 합니다.

인덱스 칸이 - 에서 blob 이름으로 — 이제 d 는 추적되는 파일입니다. HEAD 에는 아직 없습니다.

실행 검증

git commit — 인덱스를 HEAD 로

a 를 고쳐 add 까지 한 상태에서 커밋합니다.

바뀐 칸은 HEAD 하나 — 인덱스의 c1827f0 이 새 커밋의 트리가 됐습니다. 작업 트리는 읽지 않습니다(2부).

실행 검증

git commit -a — 추적 중인 파일만

a 를 고치고 새 파일 d 도 만든 뒤, add 없이 -a 로 커밋합니다.

a 는 세 칸이 모두 새 값이 됐지만 d 는 그대로입니다. -a 는 "추적 중인 파일의 변경을 add 한 뒤 커밋" 이라 새 파일은 넣지 않습니다.

실행 검증

git commit --amend — 마지막 커밋 바꿔치기

a 를 고쳐 add 한 뒤 메시지는 그대로 두고 amend 합니다.

HEAD 칸이 인덱스를 따라갔고, 로그에는 여전히 커밋 둘뿐입니다 — 둘째 커밋이 새 커밋으로 바뀌었습니다(이름이 달라짐, 2부).

실행 검증

amend 가 남긴 흔적

옛 커밋 d84229d 는 사라지지 않았습니다. 이미 푸시한 커밋을 amend 하면 원격의 역사와 갈라집니다(12부).

실행 검증

1장 퀴즈

Q. 새 파일 x 와 고친 파일 y(추적 중)가 있습니다. git commit -a -m m 을 하면 커밋에 들어가는 것은 무엇이고, 그 뒤 상태 표에서 x 의 세 칸은 어떻게 보입니까?

A. y 의 변경만 들어갑니다. x 는 추적하지 않는 파일이라 -a 가 add 하지 않습니다. x 는 HEAD -, 인덱스 -, 작업 트리에만 blob 이름 — 실험의 d 와 같습니다.
설명용

2장

rm 과 mv

지우기와 옮기기도 인덱스의 일

git rm — 인덱스와 작업 트리에서

깨끗한 파일 a 를 지웁니다.

인덱스와 작업 트리 칸이 - 가 됐습니다. HEAD 에는 아직 있으니, 다음 커밋이 "a 를 지움" 이 됩니다.

실행 검증

git rm --cached — 인덱스에서만

같은 출발점에서 --cached 로 지웁니다.

인덱스 칸만 - — 파일은 디스크에 남고 추적만 멈춥니다. 실수로 커밋한 설정 파일을 저장소에서 빼되 내 디스크에는 두고 싶을 때 씁니다(그 뒤 .gitignore 에 넣습니다).

실행 검증

git rm 이 거절할 때

a 를 고쳐 둔 채(커밋도 add 도 안 함) 지우려 합니다.

세 칸이 그대로입니다. 지우면 어디에도 없는 내용(c1827f0)을 잃게 되니 git 이 멈췄습니다. 정말 지우려면 -f 입니다.

실행 검증

git mv — 지우기와 더하기를 한 번에

a 의 이름을 z 로 바꿉니다.

a 는 인덱스·작업 트리에서 사라지고 z 가 같은 blob(da0f8ed)으로 생겼습니다. git 에 "이름 바꾸기" 기록은 없고, status 의 R 는 같은 blob 을 보고 짐작한 것입니다(9부).

실행 검증

3장

restore

어디서 가져와 어디에 쓰나

출발점 — 세 칸이 모두 다른 파일

이 장의 실험은 a 를 a2 로 고쳐 add 하고, 다시 a3 으로 고쳐 둡니다. HEAD(a1) · 인덱스(a2) · 작업 트리(a3)가 셋 다 다릅니다.

restore 는 "어디서(--source) 가져와 어디에(--staged · --worktree) 쓰나" 두 질문으로 읽습니다. 기본은 인덱스에서 가져와 작업 트리에 씁니다.

실행 검증

git restore — 인덱스 → 작업 트리

옵션 없이 복원합니다.

작업 트리가 인덱스의 c1827f0 으로 돌아왔습니다. a3 은 사라졌습니다 — 어디에도 저장된 적이 없으니 되찾을 수 없습니다.

실행 검증

git restore --staged — HEAD → 인덱스

같은 출발점에서 --staged 로 복원합니다.

인덱스만 HEAD 의 da0f8ed 로 — "add 를 취소" 입니다. 작업 트리의 a3 은 그대로 남습니다.

실행 검증

git restore --staged --worktree — HEAD → 둘 다

둘을 함께 줍니다.

세 칸이 모두 HEAD 와 같아졌습니다. 이 파일의 커밋하지 않은 모든 것을 버리는 명령입니다.

실행 검증

git restore --source — 다른 커밋에서

깨끗한 상태에서 b 를 한 커밋 전 판으로 꺼냅니다.

작업 트리만 옛 판(c9c6af7 = b1)이 됐습니다. 인덱스는 그대로라 status 에는 "add 하지 않은 변경" 으로 보입니다.

실행 검증

옛 방식 — git checkout <커밋> -- 파일

같은 일을 옛 명령으로 합니다.

이번에는 인덱스와 작업 트리가 함께 바뀌었습니다. checkout 은 브랜치 옮기기와 파일 꺼내기를 한 이름으로 했고, 2.23 에서 나온 switch · restore 가 그 둘을 나눴습니다.

실행 검증

2~3장 퀴즈

Q. git add . 로 파일 열 개를 스테이징했는데 그중 secret.env 는 빼고 싶습니다(디스크의 파일은 지키면서). 어느 명령을 씁니까? git restore secret.env 를 쓰면 무슨 일이 생깁니까?

A. git restore --staged secret.env — 인덱스만 HEAD 로 되돌리고 작업 트리는 그대로 둡니다 (아직 커밋에 없는 새 파일이면 인덱스에서 빠지기만 합니다). git restore secret.env 는 인덱스의 내용으로 작업 트리를 덮어써서, 인덱스와 다른 작업 트리의 변경이 있었다면 그것을 잃습니다.
설명용

4장

reset

브랜치를 옮기고, 어디까지 따라오게 하나

출발점

a 를 고쳐 add 하고, c 는 고치기만 했습니다. 그 상태에서 reset HEAD~1 을 세 모드로 각각 합니다.

reset 은 먼저 현재 브랜치를 그 커밋으로 옮기고, 모드에 따라 인덱스와 작업 트리를 거기에 맞춥니다.

실행 검증

reset --soft — HEAD 만

첫째 커밋으로 soft reset.

HEAD 칸의 b 만 옛 값(c9c6af7)이 됐습니다. 인덱스·작업 트리는 그대로라, 둘째 커밋의 변경(b)과 스테이징해 둔 a 가 모두 "커밋할 변경" 으로 남습니다. 커밋 여럿을 하나로 합칠 때 씁니다.

실행 검증

reset --mixed(기본) — HEAD 와 인덱스

같은 출발점에서 mixed.

인덱스도 HEAD 를 따라갔습니다. 작업 트리의 변경(a2 · b2 · c2)은 모두 남되 스테이징은 풀렸습니다.

실행 검증

reset --hard — 셋 다

같은 출발점에서 hard.

세 칸이 모두 첫째 커밋과 같아졌습니다. 스테이징한 a2 는 blob 으로 남아 있어 되찾을 수 있지만, add 하지 않은 c2 는 어디에도 없습니다.

실행 검증

세 모드를 한 표로

모드HEAD(브랜치)인덱스작업 트리잃을 수 있는 것
--soft옮김그대로그대로없음
--mixed옮김맞춤그대로스테이징 구분만
--hard옮김맞춤맞춤add 안 한 변경

앞 세 장의 상태 표가 이 표의 근거입니다. 옮겨진 뒤의 옛 커밋은 ORIG_HEAD 와 reflog 로 되찾습니다(4부).

설명용

reset -- 경로 — 브랜치는 그대로, 인덱스 한 칸만

경로를 주면 브랜치를 옮기지 않습니다.

b 의 인덱스 칸만 한 커밋 전 값이 됐습니다. restore --staged --source=HEAD~1 b 와 같은 일입니다.

실행 검증

5장

switch

브랜치를 옮길 때 로컬 변경은?

변경을 들고 가기

a 를 고쳐 둔 채 한 커밋 전 브랜치 old 로 옮깁니다. 두 브랜치에서 a 는 같습니다.

HEAD·인덱스는 old 의 것(b = c9c6af7)이 됐고, a 의 작업 트리 변경은 그대로 따라왔습니다. 옮겨도 잃는 것이 없으니 git 이 허락합니다.

실행 검증

들고 갈 수 없으면 멈춘다

이번에는 두 브랜치에서 서로 다른 파일 b 를 고쳐 둔 채 옮기려 합니다.

아무 칸도 바뀌지 않았습니다. 옮기면 작업 트리의 b 를 old 의 판으로 덮어써야 하는데, 그러면 변경을 잃으니 멈춥니다. 커밋하거나, stash 하거나, switch --merge 로 합쳐서 옮깁니다.

실행 검증

6장

stash

보관함의 정체는 커밋

git stash push

a 는 스테이징, c 는 작업 트리에서만 고쳤고, 새 파일 new 도 있습니다.

a 와 c 는 HEAD 로 돌아갔고, 추적하지 않는 new 는 그대로 남았습니다(기본 stash 는 추적 중인 파일만 담습니다).

실행 검증

stash 는 커밋 두 개

WIP 커밋은 부모가 둘인 머지 모양입니다 — 첫째 부모는 그때의 HEAD, 둘째 부모는 인덱스 상태를 담은 커밋(index on main)입니다. WIP 커밋의 트리가 작업 트리 상태입니다. refs/stash 가 이 커밋을 가리키고, 여러 개는 그 reflog(stash@{n})로 쌓입니다.

실행 검증

stash 의 내용 보기

실행 검증

git stash pop --index

보관한 것을 되돌려 놓습니다. --index 는 스테이징 여부까지 되살리라는 뜻입니다.

a 는 인덱스까지(스테이징된 채로), c 는 작업 트리에만 — 보관 전 표와 같습니다. --index 가 없으면 전부 작업 트리 변경으로 돌아옵니다.

실행 검증

git stash -u — 추적 안 하는 파일도

new 하나만 있는 상태에서 -u 로 보관합니다.

new 도 사라졌습니다. 어디에 담겼을까요 — 다음 장.

실행 검증

셋째 부모

셋째 부모는 추적하지 않는 파일만 담은 커밋입니다. stash 가 "특별한 저장소" 가 아니라 커밋 몇 개와 참조 하나라는 것 — 그래서 잃어버린 stash 도 dangling 커밋으로 찾을 수 있습니다(16부).

설명용

4~8장 퀴즈

Q. 커밋 셋을 하나로 합치고 싶습니다. reset 의 어느 모드를 쓰고 그다음 무엇을 합니까? reset --hard 로 했다면 무엇을 잃을 수 있습니까? 그리고 stash 가 "커밋" 이라는 것은 어떻게 확인합니까?

A. git reset --soft HEAD~3 뒤 git commit — soft 는 인덱스·작업 트리를 그대로 두니 세 커밋의 변경이 모두 스테이징된 채 남습니다. --hard 였다면 세 커밋은 reflog 로 되찾을 수 있어도, 그때 add 하지 않은 작업 트리 변경은 잃습니다. stash 는 git cat-file -p stash@{0} 이 tree 와 parent 줄을 가진 커밋 객체를 보여 주는 것으로 확인합니다.
