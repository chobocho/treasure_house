인덱스

.git/index — 스테이징 영역의 실체

이 부에서 할 일

2부에서 인덱스를 "다음 커밋이 될 트리의 초안" 이라고 했습니다. 그 초안은 .git/index 파일 하나이고, 이 부는 그 파일을 바이트로 엽니다.

  • 머리 · 항목 · 확장 · 끝 체크섬 — 파일의 뼈대
  • 항목마다 적힌 stat 칸, 그것으로 "안 바뀐 파일" 을 빨리 가려내는 법
  • 그 믿음이 틀리는 자리 — racy git — 과 git 의 대처
  • assume-unchanged · skip-worktree · sparse-checkout · 희소 인덱스
  • 충돌 때의 단계 1·2·3, 의도만 추가(add -N)
  • 확장 다섯 — TREE · REUC · UNTR · link · sdir
설명용

1장

파일의 뼈대

DIRC · 항목 · 확장 · SHA-1

네 부분

  1. 머리 12바이트 — 서명 DIRC, 판(2·3·4), 항목 수
  2. 항목들 — 경로 차례로 정렬, 항목마다 stat 칸·모드·객체 이름·플래그·경로
  3. 확장들 — 4바이트 서명 + 4바이트 크기 + 내용. 없을 수도 있다
  4. 끝 20바이트 — 그 앞 전부의 SHA-1

수는 모두 빅 엔디언입니다. 공식 형식 문서는 DIRC 를 "dircache" 의 줄임이라고 적습니다.

머리 12바이트

44 49 52 43 = DIRC, 00 00 00 02 = 판 2, 00 00 00 04 = 항목 넷.

끝 20바이트 — 앞부분의 SHA-1

해시 값 자체는 싣지 않았습니다. 인덱스에는 ctime·inode 처럼 돌릴 때마다 다른 칸이 있어 해시도 매번 다르기 때문입니다 — "같다" 는 판정만 세 번 떠도 같습니다.

실행 검증

한 바이트를 깨면 — 누가 알아채나

첫 항목의 blob 이름 안의 한 바이트(파일 앞에서 70번째)를 뒤집었습니다.

status 는 체크섬을 검사하지 않고 읽어, 깨진 blob 이름을 "스테이징한 변경" 으로 보여 줍니다. 인덱스는 자주 읽히는 파일이라 매번 해시하지 않는 쪽을 택한 것입니다. 검사는 fsck 가 합니다.

실행 검증

인덱스는 다시 만들 수 있다

인덱스에는 객체가 없고 이름만 있습니다. 지워도 git reset 이 HEAD 의 트리로 다시 채웁니다. 잃는 것은 아직 커밋하지 않고 스테이징만 한 상태 — 어느 파일을 add 해 두었는지 — 뿐입니다 (그 blob 들도 객체 저장소에는 남아 있습니다).

실행 검증

index.lock

인덱스를 바꾸는 명령은 index.lock 에 새 인덱스를 다 쓴 뒤 이름을 바꿔 넣습니다. 4부의 참조 잠금과 같은 방식입니다. 편집기 플러그인이 뒤에서 git 을 부르는 동안 명령을 치면 이 메시지를 봅니다.

실행 검증

1장 퀴즈

Q. 경로가 hello.txt(9바이트)인 항목은 몇 바이트를 차지합니까? 경로가 ab (2바이트)라면요? 그리고 .git/index 를 지우면 무엇을 잃습니까?

A. 62 + 9 = 71 에 NUL 을 채워 8의 배수로 — 72바이트(NUL 하나). ab 는 62 + 2 = 64 인데 NUL 이 적어도 하나는 있어야 하므로 72바이트(NUL 여덟). 인덱스를 지우면 "무엇을 스테이징해 두었나" 만 잃습니다. git reset 이 HEAD 로 다시 채우고, add 했던 내용의 blob 은 객체 저장소에 남아 있습니다.
설명용

2장

stat 캐시

파일을 읽지 않고 "안 바뀌었다" 고 말하기

왜 stat 을 적어 두나

git status 가 파일 수만 개를 모두 읽어 해시하면 느립니다. 그래서 인덱스는 add 할 때의 stat (크기·시각·inode…)을 적어 두고, 다음에는 stat 만 견줍니다.

  • stat 이 같다 → 내용도 같다고 믿는다(해시하지 않음)
  • stat 이 다르다 → 그때만 읽어 해시하고 blob 이름과 견준다
실행 검증

믿음이 틀리는 자리

index 실험은 a.txt 를 같은 크기의 다른 내용(aaaa → bbbb)으로 바꾸고 mtime 을 옛 값으로 되돌렸습니다. ctime 은 보지 말라고(core.trustctime=false) 해 두었습니다.

stat 이 같으니 git 은 파일을 읽지 않았습니다. 일부러 만든 상황이지만, 시각을 되돌리는 도구 (압축 풀기, 동기화 프로그램)가 실제로 이런 일을 만듭니다.

실행 검증

stat 이 달라지면 바로 보인다

mtime 이 달라지자 git 이 파일을 읽어 해시했고, 내용이 바뀐 것을 찾았습니다. 의심스러우면 파일 시각을 건드리거나(touch) .git/index 를 지우고 git reset 하면 git 이 다시 해시합니다. 이름이 비슷한 update-index --really-refresh 는 assume-unchanged 표시를 무시할 뿐 stat 은 여전히 믿으니 이 경우를 잡지 못합니다.

실행 검증

racy git — 같은 초의 함정

파일 시각은 초(또는 더 굵은) 단위입니다. add 직후 같은 초 안에 같은 크기로 다시 고치면 stat 이 그대로라 git 이 바뀐 것을 놓칠 수 있습니다. 이런 항목을 "racily clean" 이라고 부릅니다.

  • git 의 대처 — 파일의 mtime 이 인덱스 파일 자신의 시각과 같거나 늦으면, stat 이 맞아도 내용까지 견준다.
  • 그런 항목을 담아 인덱스를 새로 쓸 때는 크기 칸을 0 으로 적어, 다음 번엔 반드시 다르게 보이게 한다.
문서 근거

이 덱을 만들다 racy 를 만났다

인덱스 실험을 두 번 돌렸더니 캡처가 달랐습니다. 한 번은 status 가 파일 내용까지 다시 읽어 인덱스를 새로 썼고, 다른 한 번은 그러지 않았습니다. 파일을 쓴 시각이 인덱스와 같은 초에 걸렸느냐(racily clean) 의 차이로 보입니다 — 앞 장의 규칙 그대로입니다.

그래서 캡처를 세 번 같게 뜨려고, 실험은 파일 시각을 과거(touch -d @1700000000)로 못 박은 뒤 git update-index --refresh 를 한 번 돌립니다. racy 한 항목이 남지 않게 하는 것입니다. 그 뒤로 여섯 번 돌려 모두 같았습니다.

믿어라 · 보지 마라

assume-unchanged · skip-worktree · sparse-checkout

assume-unchanged — "바뀌지 않았다고 믿어라"

원래 목적은 성능입니다 — stat 조차 느린 파일 시스템에서 "이 파일은 안 바꾸겠다" 고 사용자가 약속하는 것. 공식 문서는 이 비트(와 skip-worktree)로 "추적 중인 파일의 변경을 무시" 하려 하지 말라고 적습니다 — git 은 어떤 작업에서는 여전히 파일을 견주고, 그 파일을 바꿔야 하는 머지에서는 멈춥니다. 그런 설정 파일은 샘플을 저장소에 두고 복사해 쓰는 쪽을 권합니다.

실행 검증

skip-worktree — "작업 트리의 이 파일은 없는 셈 쳐라"

이 비트가 켜진 항목은 작업 트리에 파일이 없어도, 있어서 달라도 git 이 인덱스의 값을 그대로 씁니다. 판 2 항목에는 이 비트를 담을 자리가 없어서, 켜는 순간 인덱스가 판 3(확장 플래그 2바이트)이 됩니다. sparse-checkout 이 이 비트를 씁니다.

실행 검증

sparse-checkout — 일부만 풀어 두기

원뿔(cone) 모드는 최상위 파일과 고른 디렉터리만 풉니다. src/m.c 는 커밋에도 인덱스에도 그대로 있고, 작업 트리에만 없습니다.

2~3장 퀴즈

Q. 팀원이 "로컬 설정 파일의 내 변경이 자꾸 status 에 보여서 assume-unchanged 를 켰다" 고 합니다. 무엇이 문제입니까? 그리고 sparse-checkout 으로 작업 트리에서 사라진 파일은 다음 커밋에서 지워집니까?

A. assume-unchanged 는 "안 바꾸겠다" 는 성능용 약속이라, 그 파일이 바뀐 커밋을 머지하는 순간 git 이 멈추고 손으로 풀어야 합니다. 공식 문서도 변경 무시 용도로 쓰지 말라고 합니다. 저장소에는 샘플 설정만 두고, 실제 설정은 추적하지 않는 파일로 복사해 .gitignore 에 넣는 것이 맞습니다. sparse-checkout 의 파일은 지워지지 않습니다 — 인덱스에 skip-worktree 비트와 함께 그대로 있고, 커밋은 인덱스로 만들기 때문입니다.
설명용

4장

단계 번호와 의도

충돌할 때의 1·2·3, 그리고 add -N

충돌하면 한 경로가 세 항목이 된다

  • 1 — 공통 조상의 판
  • 2 — 우리(HEAD) 판
  • 3 — 그쪽(합쳐 들어오는) 판

단계 0 항목이 없으니 이 인덱스로는 트리를 만들 수 없습니다 — 커밋이 거절되는 까닭입니다.

실행 검증

세 판을 꺼내 보기

:n:경로 는 "인덱스 단계 n 의 그 경로" 입니다(3부 6장의 이름 부르기). 머지 도구들이 이 셋을 꺼내 화면에 나란히 보여 줍니다(7부).

실행 검증

해소 = 단계 0 항목 하나로

세 항목이 사라지고 단계 0 항목 하나가 됩니다. 이제 트리를 만들 수 있고, 커밋할 수 있습니다.

실행 검증

해소를 되돌리기 — REUC 확장

add 로 해소하는 순간 git 은 사라지는 세 판을 REUC(resolve undo) 확장에 적어 둡니다. 잘못 해소했으면 git checkout -m 으로 충돌 상태로 돌아갈 수 있습니다.

실행 검증

add -N — "추가할 생각이다"

인덱스에 항목은 생기지만 내용은 아직 올리지 않았다는 표시가 붙습니다. 새 파일을 git diff 와 add -p 로 조금씩 올리고 싶을 때 씁니다.

실행 검증

의도만으로는 커밋되지 않는다

git 은 "스테이징하지 않은 새 파일" 로 봅니다. 트리를 만들 때 의도만 추가된 항목은 빠지므로, 새로 넣을 것이 없어 커밋이 만들어지지 않았습니다(로그는 그대로 한 줄).

5장

확장

항목 뒤에 붙는 부록들

대문자는 건너뛰어도 되고, 소문자는 안 된다

확장은 4바이트 서명과 4바이트 크기로 시작합니다. 공식 형식은 서명의 첫 글자가 A~Z 이면 선택 확장 — 모르는 git 이 무시해도 되는 것 — 이라고 정합니다.

서명이름모르면
TREE캐시 트리무시해도 된다
REUC해소 되돌리기무시해도 된다
UNTR추적 안 하는 파일 캐시무시해도 된다
link분할 인덱스읽으면 안 된다 — 항목이 다른 파일에 있다
sdir희소 디렉터리 항목읽으면 안 된다 — 디렉터리 항목을 파일로 오해한다
문서 근거

확장을 뽑아 보는 도구

판 4 는 경로를 눌러 적어 항목 길이를 이 식으로 셀 수 없습니다. 그래서 판 2·3 에만 씁니다.

실행 검증

TREE — 디렉터리마다 트리 이름을 기억

커밋 때마다 모든 디렉터리의 트리를 다시 계산하면 느립니다. 캐시 트리는 "이 디렉터리의 트리 이름은 이것" 을 기억하고, 파일 하나가 바뀌면 그 경로의 디렉터리들만 무효로 표시합니다. 53바이트에서 15바이트로 준 것이 그 표시입니다.

실행 검증

UNTR — 추적 안 하는 파일 찾기를 빠르게

추적 안 하는 파일을 찾으려면 모든 디렉터리를 읽어야 합니다. 이 캐시는 디렉터리의 stat 과 그 안의 추적 안 하는 파일 목록을 기억해, 바뀐 디렉터리만 다시 읽게 합니다. core.untrackedCache 로 늘 켜 둘 수 있습니다.

실행 검증

link — 분할 인덱스

항목 수십만 개짜리 인덱스를 파일 하나 바꿀 때마다 통째로 다시 쓰는 것은 낭비입니다. 분할 인덱스는 큰 몫을 sharedindex.<이름> 에 두고, 앞쪽 index 에는 바뀐 항목만 적습니다.

sharedindex 파일 이름의 해시는 stat 칸 때문에 실행마다 달라 <이름> 으로 가렸습니다.

실행 검증

판 2 · 3 · 4 — 파일 2,000개로 잰 크기

판 4 는 각 경로를 "앞 항목과 겹치는 앞부분의 길이 + 나머지" 로 적어, 같은 디렉터리의 파일이 많을수록 작아집니다. 이 실험에서는 약 20 % 줄었습니다.

실행 검증

희소 인덱스 — 디렉터리 하나를 항목 하나로

sparse-checkout 만으로는 인덱스에 파일이 전부 남습니다(3장). 희소 인덱스는 풀지 않은 디렉터리를 트리 이름 하나짜리 항목으로 접어 항목 수를 줄입니다 — 40개가 13개(dir03 의 넷 + 나머지 디렉터리 아홉)가 됐습니다.

실행 검증

그래도 명령은 전체를 본다

희소 인덱스를 아는 명령은 접힌 항목을 그대로 다루고, 모르는 명령을 위해서는 git 이 필요할 때 항목을 다시 펼칩니다. 서명이 소문자 sdir 인 것은 이 확장을 모르는 git 이 이 인덱스를 읽으면 안 되기 때문입니다.

4~5장 퀴즈

Q. 인덱스 확장 이름이 FSMN 과 link 입니다. 이 확장을 모르는 옛 git 은 각각 어떻게 해야 합니까? 그리고 충돌 중인 파일을 git add 한 뒤 되돌리고 싶다면 무엇을 씁니까?

A. 첫 글자가 대문자인 FSMN 은 선택 확장이라 건너뛰어도 되고, 소문자인 link 는 필수 확장이라 모르면 그 인덱스를 읽지 말고 멈춰야 합니다(항목이 sharedindex 파일에 있으므로). add 로 해소한 충돌은 git checkout -m 경로 로 되돌립니다 — REUC 확장이 세 판을 기억합니다.
