전송 프로토콜

두 저장소가 객체를 주고받는 대화

이 부에서 할 일

clone · fetch · push 는 두 git 프로세스의 대화입니다. 받는 쪽이 "무엇을 원하고 무엇을 가졌나" 를 말하면, 주는 쪽이 그 차이만 팩 하나로 보냅니다. 2부의 내용 주소 덕에 "가졌다" 를 이름 하나로 말할 수 있습니다.

  • pkt-line — 대화의 글자 단위
  • v0 과 v2 — 광고부터 할 것인가, 물어보면 답할 것인가
  • fetch 의 협상 — want · have · ACK
  • push — 명령 줄, 결과 보고, 빨리 감기가 아닌 push 의 거절, 원자적 push, 서버 훅
  • 전송로 — 로컬·file·스마트 HTTP·dumb HTTP·bundle
  • 덜 받기 — 얕은 clone 과 부분 clone
설명용

1장

pkt-line

길이 네 자리 + 내용

줄마다 앞에 16진 길이 네 글자

  • 000e = 14 = 길이 네 글자 + version 2 와 줄바꿈 10바이트
  • 0000 — 길이 0 은 특별한 표시(flush): "여기서 한 덩이 끝"
  • v2 에는 0001(delim, 덩이 안의 구획)도 있습니다(2장)

내용에 이진 데이터도 실을 수 있고, 한 줄은 길이 칸까지 65,520바이트를 넘지 않습니다.

Q. pkt-line 0009done\n 은 올바릅니까? 그리고 fetch 에서 클라이언트가 have 를 보내지 않으면 무엇이 달라집니까?



A. 올바릅니다 — done\n 5바이트 + 길이 칸 4바이트 = 9. have 가 없으면 서버는 공통 조상을 모르니
원하는 커밋에서 닿는 객체 전부를 보냅니다(clone 처럼). 이미 가진 것까지 다시 받게 됩니다.

빨리 감기가 아닌 push 의 거절




빨리 감기가 아닌(non-fast-forward) push 는 원격에 있던 커밋을 참조에서 떼어 냅니다. 클라이언트가 한 번, 서버 설정이 또 한 번 막습니다.
--force-with-lease 는 "원격이 내가 마지막으로 본 값일 때만" 덮어쓰는 절충입니다(12부).

네 가지 통로




주소통로이 덱의 실험


../repo로컬 경로 — clone 은 팩을 만들지 않고 객체 파일을 복사(가능하면 하드 링크). 참조 목록과 fetch·push 는 여기서도 upload-pack·receive-pack 과 pkt-line 으로 대화2부 분산 · 이 부의 ls-remote trace


file://…로컬이지만 upload-pack 과 pkt-line 대화이 부의 trace 들


ssh://…ssh 로 원격의 upload-pack·receive-pack 을 실행해 표준 입출력으로 대화이 기계에서는 뜨지 않음


https://…스마트 HTTP — 같은 pkt-line 을 HTTP 요청·응답에 실음다음 장




ssh 는 대화를 싣는 관일 뿐 내용은 file:// 과 같습니다. 그래서 file:// 캡처로 대신합니다.

4~6장 퀴즈


Q. 릴리스 스크립트가 태그 v3.0 과 브랜치 release 를 함께 push 합니다. 태그만 들어가고 브랜치가 거절되면
곤란합니다. 무엇을 씁니까? 그리고 서버가 "WIP 커밋은 받지 않는다" 를 강제하려면 어디에 무엇을 둡니까?



A. git push --atomic origin v3.0 release — 하나라도 거절되면 둘 다 들어가지 않습니다(실험에서 main 이 "atomic
push failure" 로 함께 거절). 서버의 hooks/pre-receive 에 새 끝 커밋을 검사하고 0 이 아닌 값으로 끝나는 스크립트를 둡니다. 그
표준 오류가 push 한 사람에게 remote: 로 보입니다.
