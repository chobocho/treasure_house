1장

배운 것의 지도

한 장씩 되짚기

객체 넷과 이름표

무엇담는 것부
blob파일 내용만 — 이름 없음3부
tree이름·모드 → blob·tree3부
committree 하나, 부모들, 작성자·커미터, 메시지3부
tag객체 하나에 이름·만든 이·메시지(서명)를 붙인 것3·4부
ref이름 → 해시 (브랜치·태그·원격 추적), HEAD 는 ref → ref4부

모든 객체의 이름은 내용의 해시라, 한번 쓴 객체는 바뀌지 않습니다. 바뀌는 것은 이름표뿐입니다.

설명용

세 자리

자리무엇인가옮기는 명령
작업 트리보통의 파일restore ← 인덱스, switch ← 커밋
인덱스다음 커밋의 초안 — 경로마다 blob 해시add ← 작업 트리, restore --staged ← HEAD
저장소객체와 refcommit ← 인덱스

status 는 이 셋을 둘씩 견준 결과이고(5부), diff 의 세 꼴도 같은 짝입니다(9부).

설명용

명령이 움직이는 것

명령HEAD/브랜치인덱스작업 트리
commit새 커밋으로——
reset --soft옮김——
reset(--mixed)옮김맞춤—
reset --hard옮김맞춤맞춤
switchHEAD 가 다른 브랜치로맞춤맞춤(고친 것은 지킴)
restore—--staged 일 때기본

6부의 상태 도구로 명령 전후를 찍어 본 그 표입니다.

설명용

역사를 쌓는 명령과 고치는 명령

쌓는다 — 보낸 뒤에도고친다 — 보내기 전에만
commit · merge · revertcommit --amend · reset · rebase
cherry-pick(새 커밋)filter-branch · --fixup+autosquash

"고친다" 도 사실은 새 커밋을 만들고 이름표를 옮기는 일이라, 남이 옛 커밋을 가지고 있으면 역사가 갈라집니다(8·12부).

설명용

원격은 또 하나의 저장소

  • fetch — 남의 객체와 ref 를 받아 origin/* 에 적는다. 내 브랜치는 그대로(12부).
  • push — 내 객체를 보내고 남의 ref 를 옮겨 달라고 청한다. 되감기가 아니면 거절(11·12부).
  • 주고받는 것은 팩 하나 — 서로 가진 것을 알리고(have) 모자란 것만(10·11부).

흔한 오해 20가지

앞에서 찍은 캡처를 증거로

오해 1 — git 은 판 사이의 차이(diff)를 저장한다

실제 — 커밋마다 트리 전체의 스냅숏을 가리킵니다. 안 바뀐 파일은 같은 blob 을 다시 가리킬 뿐이고, 바뀐 파일은 통째로 새 blob 입니다. 차이(델타)는 팩으로 묶을 때 저장 공간을 줄이는 기법일 뿐입니다.

증거를 처음 실은 곳: 2부

실행 검증

오해 2 — 브랜치는 커밋들을 복사해 둔 것이다

실제 — 브랜치는 커밋 해시 하나를 적은 이름표입니다. 만들기도 지우기도 파일 하나를 쓰고 지우는 일이라 공짜입니다.

증거를 처음 실은 곳: 4부

실행 검증

오해 3 — HEAD 는 가장 최근 커밋이다

실제 — HEAD 는 보통 "지금 있는 브랜치" 를 가리키는 기호 ref 입니다. 커밋을 직접 가리키면 분리 HEAD 입니다.

증거를 처음 실은 곳: 4부

실행 검증

오해 4 — 커밋 해시는 파일 내용만으로 정해진다

실제 — 커밋 객체에는 트리·부모·작성자·시각·메시지가 다 들어 있고, 해시는 그 전부의 해시입니다. 메시지 한 글자만 바꿔도 새 커밋입니다.

증거를 처음 실은 곳: 2부

실행 검증

오해 5 — 같은 내용의 파일 두 개는 두 번 저장된다

실제 — blob 은 내용만의 해시라, 이름이 달라도 내용이 같으면 객체 하나를 함께 가리킵니다.

증거를 처음 실은 곳: 2부

실행 검증

오해 6 — git 은 파일 이름 바꾸기를 기록한다

실제 — 트리에는 이름과 blob 만 있습니다. "바꿈" 은 diff 가 볼 때마다 비슷한 내용을 찾아 추측하는 것입니다.

증거를 처음 실은 곳: 9부

실행 검증

오해 7 — 빈 디렉터리도 커밋할 수 있다

실제 — 트리는 파일이 있어야 생깁니다. 빈 디렉터리는 status 에도 안 보여, 흔히 빈 파일(.gitkeep 같은 이름은 관례일 뿐)을 넣습니다.

증거를 처음 실은 곳: 14부

실행 검증

오해 8 — stash 는 커밋과 다른 특별한 보관함이다

실제 — stash 는 부모가 둘 이상인 보통의 커밋이고, 목록은 refs/stash 의 reflog 입니다.

증거를 처음 실은 곳: 6부

실행 검증

오해 9 — 머지 커밋은 특별한 종류의 객체다

실제 — 부모 줄이 둘인 보통의 커밋입니다. 머지의 결과는 트리에, 합친 사실은 부모 줄에 있을 뿐입니다.

증거를 처음 실은 곳: 3부

실행 검증

오해 10 — rebase 는 커밋을 옮긴다

실제 — 새 커밋을 만들어 이름표를 옮깁니다. 옛 커밋은 그대로 남아 ORIG_HEAD·reflog 로 돌아갈 수 있습니다.

증거를 처음 실은 곳: 8부

실행 검증

오해 11 — pull 은 받아 오기만 한다

실제 — pull 은 fetch 에 이어 합치기(머지·rebase·되감기)까지 합니다. 갈라진 역사에서는 어떻게 합칠지 정하라고 멈춥니다.

증거를 처음 실은 곳: 12부

실행 검증

오해 12 — push --force 는 내 브랜치라면 안전하다

실제 — 원격에 남이 올린 커밋이 있으면 지워 버립니다. --force-with-lease 는 내가 마지막으로 본 원격 상태와 다르면 거절합니다.

증거를 처음 실은 곳: 12부

실행 검증

오해 13 — reset --hard 로 날린 커밋은 끝이다

실제 — 커밋 객체는 남아 있고 reflog 가 자리를 기억합니다. 되살릴 수 없는 것은 커밋된 적 없는 작업 트리의 고침입니다.

증거를 처음 실은 곳: 16부

실행 검증

오해 14 — .gitignore 에 넣으면 추적이 멈춘다

실제 — 무시 규칙은 아직 추적하지 않는 파일에만 듣습니다. 이미 추적 중이면 git rm --cached 로 먼저 뺍니다.

증거를 처음 실은 곳: 16부

실행 검증

오해 15 — 비밀 파일을 지우는 커밋을 하면 해결이다

실제 — 옛 커밋에는 그대로 있습니다. 역사를 고쳐도 reflog·백업·남의 사본에 남으니, 먼저 비밀을 폐기합니다.

증거를 처음 실은 곳: 16부

실행 검증

오해 16 — git add 는 파일 이름을 "올릴 목록" 에 적는다

실제 — add 는 그 순간의 내용을 blob 으로 객체 저장소에 쓰고, 인덱스에는 그 blob 의 해시를 적습니다. add 뒤에 파일을 또 고치면 인덱스의 것과 달라집니다.

증거를 처음 실은 곳: 6부

실행 검증

오해 17 — clone 은 최신 판만 받는다

실제 — 보통의 clone 은 역사 전체를 받습니다. 최신만 받으려면 --depth(얕은 clone)나 부분 clone 을 따로 청해야 합니다.

증거를 처음 실은 곳: 11부

실행 검증

오해 18 — 태그도 브랜치처럼 커밋을 따라 움직인다

실제 — 태그는 한번 붙이면 제자리입니다. 커밋할 때 움직이는 것은 HEAD 가 가리키는 브랜치뿐입니다.

설명용

오해 19 — SHA-1 이 깨졌으니 git 도 깨졌다

실제 — git 은 알려진 충돌 공격을 탐지하는 SHA-1(sha1dc)을 쓰고, SHA-256 저장소도 만들 수 있습니다(3·14부). 다만 두 형식은 아직 서로 주고받지 못합니다.

설명용

오해 20 — git 과 GitHub 은 같은 것이다

실제 — GitHub 은 git 저장소를 맡아 주는 서비스이고, 풀 리퀘스트·이슈·권한은 git 에 없는 그 서비스의 기능입니다(14부 7장).

종합 퀴즈

여러 부를 가로질러

종합 퀴즈 1

Q. 작업 트리에 고친 파일이 있는 채로 git switch other 를 했더니 거절됐습니다. 왜이고, 어떻게 합니까?

A. 그 파일이 두 브랜치에서 달라, 옮기면 고친 것이 덮어써지기 때문입니다(두 브랜치에서 같은 파일이면 고친 채로 옮겨 갑니다). 커밋하거나 git stash 로 치운 뒤 옮기고, 그 고침을 다른 브랜치로 가져가려면 옮긴 뒤 stash pop 합니다.
설명용

종합 퀴즈 2

Q. git log main..topic 과 git log main...topic 은 무엇이 다릅니까?

A. 두 점은 topic 에서 닿지만 main 에서는 닿지 않는 커밋, 세 점은 둘 중 한쪽에서만 닿는 커밋(대칭 차)입니다(4부).
설명용

종합 퀴즈 3

Q. 머지 충돌 표시 가운데 ||||||| 줄이 보이게 하려면 무엇을 켜고, 그 구역은 무엇입니까?

A. merge.conflictStyle=diff3(또는 zdiff3)입니다. 그 구역은 공통 조상(base)의 내용이라 양쪽이 각각 무엇을 바꿨는지 보입니다(7부).
설명용

종합 퀴즈 4

Q. 팩 파일 안의 객체가 델타로 저장돼 있다면 "git 은 스냅숏을 저장한다" 는 말은 틀린 것입니까?

A. 아닙니다. 모델(객체)은 스냅숏이고, 델타는 팩 안에서 바이트를 줄이는 저장 방식입니다. 꺼내면 언제나 온전한 객체가 나옵니다(10부).
설명용

종합 퀴즈 5

Q. 동료가 이미 받아 간 브랜치를 rebase 하고 강제 push 했습니다. 동료에게는 무슨 일이 생기고, 어떻게 풉니까?

A. 동료의 옛 커밋과 새 커밋이 갈라집니다. 설정 없이 그냥 pull 하면 지금의 git 은 멈추고 합칠 방법을 묻고(12부), 머지로 합치면 같은 변경이 두 번 들어간 머지가 됩니다. 동료는 git pull --rebase(옛 커밋을 알아보고 건너뜀)나 자기 작업만 새 위로 옮기는 rebase 로 맞춥니다(8·12부).
설명용

종합 퀴즈 6

Q. .gitattributes 에 *.txt text eol=lf 를 넣었는데 이미 커밋된 CRLF 파일은 그대로입니다. 어떻게 합니까?

A. git add --renormalize . 로 규칙대로 다시 올리고 그 커밋을 따로 만듭니다(16부 장면 33).
설명용

종합 퀴즈 7

Q. 누군가 "git 저장소에서 경로별로 읽기 권한을 나누자" 고 합니다. 가능합니까?

A. git 만으로는 안 됩니다. clone 은 모든 객체를 받습니다 — 저장소를 나눠야 합니다(14부).
설명용

종합 퀴즈 8

Q. git fsck 가 "dangling commit" 을 보였습니다. 고장입니까?

A. 아닙니다. 어느 이름표에서도 닿지 않는 커밋일 뿐 — 지운 브랜치나 amend 전 커밋 같은 것입니다. 필요하면 이름을 붙여 되살리고, 아니면 gc 가 기한이 지나면 치웁니다(16부 장면 38).

18부 정리

git 은 내용의 해시로 이름 붙인 바뀌지 않는 객체들과, 그 위를 옮겨 다니는 몇 개의 이름표입니다.

나머지 — 머지, rebase, 원격, 복구 — 는 모두 이 두 가지를 어떻게 만들고 옮기느냐의 이야기였습니다.
