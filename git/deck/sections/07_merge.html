7부

브랜치와 머지

갈라진 두 역사를 하나로

이 부에서 할 일

브랜치는 파일 하나라 만들기 쉽습니다(4부). 어려운 것은 갈라진 두 역사를 다시 합치는 일입니다. 이 부는 머지를 세 스냅숏의 비교로 읽습니다.

  • 브랜치 다루기 — 지우기의 안전장치, 이름 바꾸기, upstream
  • 머지 베이스 — 무엇과 무엇을 견주나
  • fast-forward 와 진짜 머지
  • 3-way 가 덩어리마다 판정하는 법
  • 충돌 — 표시, 인덱스의 세 판, 푸는 도구들, 충돌의 종류
  • 전략과 옵션 — ort · -X ours · -s ours · squash · octopus · rerere · merge-tree
설명용

1장

브랜치 다루기

지우기 · 이름 바꾸기 · 따라가기

합치지 않은 브랜치는 -d 로 못 지운다

-d 는 "이 브랜치의 끝이 현재 브랜치(또는 upstream)에서 닿는가" 를 봅니다. 닿지 않으면 지우는 순간 그 커밋들에 닿는 이름표가 없어지니 멈춥니다. 알고서 지울 때는 -D 입니다 — 그 브랜치에 있었던 적이 있다면 커밋은 HEAD 의 reflog 에 남습니다 — 브랜치 자신의 reflog 는 같이 지워집니다(4부).

머지 베이스

두 역사가 마지막으로 같았던 곳

왜 공통 조상이 필요한가

두 파일만 견주면 "우리는 이 줄이 A, 그쪽은 B" 까지만 압니다. 누가 바꿨는지는 모릅니다. 둘이 갈라지기 전의 판(머지 베이스)이 있으면 판정할 수 있습니다.

베이스우리그쪽결과
AAAA
ABAB — 우리만 바꿨다
AACC — 그쪽만 바꿨다
ABBB — 둘이 같게 바꿨다
ABC충돌 — 둘이 다르게 바꿨다

이 판정을 파일마다, 파일 안에서는 덩어리마다 합니다. 그래서 3-way 머지입니다.

베이스가 둘일 때 — ort 의 방법

서로를 번갈아 합친 역사(criss-cross)에서는 "가장 가까운" 공통 조상이 여럿입니다. 하나를 고르면 다른 하나로 이미 합쳐 둔 변경을 모르는 채 비교하게 됩니다.

기본 전략 ort 는 공통 조상들을 먼저 서로 합친 트리를 만들어 그것을 베이스로 씁니다. 공식 문서는 리눅스 커널 역사의 실제 머지로 시험해 충돌이 줄고 잘못된 머지는 늘지 않았다고 적습니다.

문서 근거

직접 해 보기 — merge-base 고르기

역사: A←B←C, A←D, M1(C,D)←G, M2(D,C)←H — 앞의 dag 실험 그대로





G 와 H 의 답이 둘(C·D)인 것이 교차 머지입니다. 진짜 git 의 merge-base --all 과 같은 답이어야 합니다.

1~4장 퀴즈


Q. 베이스에서 줄 x = 1 을 우리는 x = 2 로, 그쪽도 x = 2 로 고쳤습니다.
충돌입니까? 그리고 main 이 topic 의 조상일 때 git merge --no-ff topic 과
git merge topic 은 커밋 수가 어떻게 다릅니까?



A. 충돌이 아닙니다 — 둘이 같게 바꿨으니 결과는 x = 2 입니다(판정표 넷째 줄). 되감을 수 있는 경우
그냥 merge 는 새 커밋을 만들지 않고 main 을 옮기기만 하고, --no-ff 는 부모 둘인 머지 커밋을 하나
더 만듭니다.

19부 10단계의 합치기를 옮긴 것입니다. 우리와 그들이 고친 줄 사이에 바뀌지 않은 줄을 하나 넣어 보세요 — 충돌이 사라집니다.

실행 검증






인덱스에는 세 판이






충돌 표시는 작업 트리에 쓴 것이고, 원본 세 판은 인덱스에 그대로 있습니다(5부). 머지 도구는 여기서 읽습니다.

실행 검증






머지 중이라는 표시 — MERGE_HEAD · MERGE_MSG




MERGE_HEAD 가 있는 동안 git commit 은 부모 둘인 머지 커밋을 만듭니다. 이 파일이 "지금 머지 중" 의
실체입니다.

실행 검증






충돌 중의 git diff — 합친 diff



줄 앞 칸이 둘입니다 — 첫째 칸은 우리 판과, 둘째 칸은 그쪽 판과 견준 결과입니다. ++ 로 시작하는 충돌 표시 줄은
어느 판에도 없던 줄이라는 뜻입니다.

실행 검증






한쪽과만 견주기 — --base · --ours · --theirs


merge_during 실험은 우리가 1번 줄도 고친 경우입니다.


실행 검증






--ours 와 --theirs




세 diff 를 나란히 보면 어느 쪽에서 무엇이 왔는지가 드러납니다. --ours 에서는 1번 줄이 변화 없음,
--theirs 에서는 1번 줄이 바뀐 것으로 나옵니다 — 1번 줄은 우리 쪽에서 온 것입니다.

실행 검증






log --merge — 충돌을 만든 커밋만



큰 머지에서 "왜 여기가 충돌했나" 를 물을 때 씁니다. 두 쪽이 갈라진 뒤 충돌 경로를 바꾼 커밋만 보여 줍니다.

실행 검증






AUTO_MERGE — git 이 써 넣은 결과와 견주기




AUTO_MERGE 는 git 이 충돌 표시까지 써 넣은 트리를 가리키는 특수 참조입니다(4부의 여섯 규칙 가운데 첫째).
손으로 푼 뒤 견주면 내가 바꾼 것만 보입니다.

실행 검증






한쪽 판을 통째로 — checkout --ours · --theirs




파일 단위로 한쪽을 고를 때 씁니다. 덩어리 단위로 고르려면 머지를 다시 하며 -X ours 를 줍니다(7장).


실행 검증






풀기 전에는 커밋할 수 없다



"풀었다" 의 기준은 파일 내용이 아니라 인덱스입니다. git add 로 단계 0 항목을 만들어야 합니다(5부).

실행 검증






그만두기 — merge --abort




머지를 시작하기 전 상태(ORIG_HEAD)로 인덱스와 작업 트리를 되돌립니다. 머지 전에 커밋하지 않은 변경이 있었다면
되돌리기가 불완전할 수 있어, git 은 애초에 그런 파일을 건드리는 머지를 시작하지 않습니다.

실행 검증






충돌 표시에 베이스도 — diff3



우리와 그쪽만 보면 "누가 무엇을 바꿨나" 를 모릅니다. 베이스 판(line 4)이 함께 있으면 양쪽이 각각 무엇을 했는지
보입니다. merge.conflictStyle=diff3 로 늘 이렇게 볼 수 있습니다.

실행 검증






zdiff3



zdiff3 는 양쪽이 똑같이 바꾼 앞뒤 줄을 충돌 표시 밖으로 빼 줍니다. 이 예는 한 줄만 달라 뺄 것이 없어 diff3 와
같습니다.

5장 퀴즈


Q. 충돌 표시를 지우고 파일을 고쳤는데 git commit 이 "unmerged files" 로 거절합니다. 왜입니까?
그리고 머지를 멈춘 직후 git diff AUTO_MERGE 가 아무것도 보이지 않는 까닭은?



A. 인덱스에 아직 단계 1·2·3 항목이 남아 있기 때문입니다. git add 파일 로 단계 0 항목 하나로 바꿔야
풀린 것입니다. AUTO_MERGE 는 git 이 충돌 표시까지 써 넣은 결과의 트리이고, 멈춘 직후의 작업 트리가 바로 그 결과라 차이가
없습니다. 손으로 고친 뒤에야 차이가 보입니다.

-X ours 와 -s ours, squash, octopus

실행 검증






-s ours 는 전혀 다른 것


그쪽이 4번 줄과 8번 줄을, 우리가 4번 줄만 고친 역사에서 둘을 견줍니다.




-s ours 는 머지 커밋은 만들되 트리는 우리 것 그대로 둡니다. "저 브랜치는 합친 것으로 치고 내용은 버린다" 는
뜻이라, 옛 개발 줄기를 역사에만 묶어 둘 때 씁니다. 공식 문서도 둘이 다르다고 따로 적어 둡니다.


실행 검증






-s ours 의 역사



내용은 하나도 안 들어왔는데 역사로는 합쳐졌습니다. 이후 git merge topic 은 "이미 최신" 이라고 답합니다.
그래서 모르고 쓰면 변경이 조용히 사라진 것처럼 보입니다.

실행 검증






--squash — 결과만, 역사 없이





topic 의 커밋들은 main 의 역사에 들어오지 않습니다. 그래서 topic 을 나중에 다시 머지하면 git 은 같은 변경을 다시 합치려
합니다 — squash 한 브랜치는 지우는 것이 관례입니다.

실행 검증






octopus — 가지 셋을 한 번에





octopus 는 손으로 풀어야 하는 충돌이 있으면 아예 멈추고 거절합니다. 서로 다른 파일을 건드린 주제 브랜치들을 묶을 때 씁니다.

실행 검증






--no-commit — 합치되 커밋은 내가




머지 결과를 커밋하기 전에 시험을 돌리거나 손볼 때 씁니다. MERGE_HEAD 가 있으니 그대로 커밋하면 부모 둘인 커밋이 됩니다.

실행 검증




8장
rerere 와 merge-tree
기억하는 해결, 작업 트리 없는 머지





rerere — 한 번 푼 충돌을 기억한다




"reuse recorded resolution". 같은 충돌 모양(충돌 덩어리의 내용)을 다시 만나면 기록해 둔 해결을 그대로 씁니다. 긴 주제 브랜치를
여러 번 다시 머지·리베이스할 때 같은 충돌을 몇 번이고 푸는 일을 줄입니다.

실행 검증






두 번째 머지





git 은 여전히 "충돌" 이라고 알리고 멈춥니다 — 자동 해결을 사람이 확인하고 add 하라는 뜻입니다. 인덱스에는 단계 1·2·3 이
남아 있습니다.

실행 검증






merge-tree — 작업 트리를 건드리지 않는 머지




충돌이 있어도 충돌 표시가 든 트리를 객체로 만들어 이름을 알려 줍니다. 명령의 한 줄 설명 그대로 "인덱스나 작업 트리를
건드리지 않는 머지" 라서, 작업 트리가 없는 bare 저장소에서도 "이 두 브랜치를 합칠 수 있나" 를 물을 수 있습니다.

실행 검증






충돌이 없으면 트리 하나




이 트리로 commit-tree 를 부르고 update-ref 하면 작업 트리 없이 머지 커밋을 만들 수 있습니다 — 2부의

6~8장 퀴즈


Q. 동료가 "topic 을 -s ours 로 합쳤는데 기능이 안 들어왔다" 고 합니다. 무슨 일이고, topic 을 다시
git merge 하면 어떻게 됩니까? 원래 원했던 것은 무엇이었을까요?



A. -s ours 는 머지 커밋은 만들되 트리를 우리 것 그대로 두는 전략이라 topic 의 변경이 하나도 들어오지
않았습니다. 역사상으로는 이미 합쳐졌으므로 다시 머지하면 "Already up to date" 입니다. 원했던 것은 충돌한 덩어리만 우리 쪽을
고르는 -X ours 였을 것입니다. 되돌리려면 머지 전으로 돌아가(reset, push 전이라면) -X ours 로 다시 합칩니다. 그 머지 커밋을 revert 하는 것은 소용없습니다 — 트리가 첫째 부모와 같아 되돌릴 변경이 없습니다. 이미 push 했다면 topic 의 커밋들을 cherry-pick 하는 식으로 따로 들여와야 합니다.
