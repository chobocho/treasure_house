이 부의 목표 — 그림 한 장

Git 을 오래 써도 헷갈리는 까닭은 대개 하나입니다. 명령 이름이 머릿속의 그림과 맞지 않기 때문입니다.

이 부는 그 그림을 그립니다. 일곱 가지 생각이면 충분합니다.

  • Git 은 판마다 전체의 스냅숏을 적는다
  • 모든 것의 이름은 내용의 해시다
  • 저장소는 객체 네 종류가 서로를 가리키는 그래프다
  • 역사는 부모를 가리키는 화살표로 이은 DAG다
  • 편집은 작업 트리 · 인덱스 · HEAD 세 영역 사이를 오간다
  • 모든 복제본이 온전한 저장소다
  • 명령에는 사람용(porcelain)과 도구용(plumbing) 두 층이 있다

3~6부는 이 일곱 가지를 바이트 수준에서 하나씩 다시 엽니다.

설명용

1장

스냅숏

판마다 무엇을 적는가

판을 적는 두 가지 방법

파일 세 개짜리 프로젝트에서 하나만 고쳤다고 합시다. 새 판을 적는 방법은 둘입니다.

방식새 판으로 적는 것옛 판을 꺼낼 때
차이(델타)고친 파일에서 바뀐 줄만처음부터 차이를 차례로 적용
스냅숏그 순간 프로젝트 전체의 모습그 판의 모습을 그대로 읽음

Git 의 모델은 스냅숏입니다. 커밋 하나는 "무엇이 바뀌었나" 가 아니라 "그 순간 모든 파일이 어떤 모습이었나" 를 가리킵니다.

저장 방식과는 별개입니다 — 디스크에서는 Git 도 비슷한 객체끼리 델타로 눌러 담습니다(10부 팩파일). 모델은 스냅숏, 압축은 그 아래 층의 일입니다.
설명용

실험 — 셋 중 하나만 바꾸기

파일 셋(a.txt · b.txt · c.txt)을 커밋하고, b.txt 하나만 고쳐 다시 커밋했습니다. 첫 커밋의 트리부터 봅니다.

트리는 "이 이름에는 이 blob" 이라는 표입니다. 이름 셋에 blob 이름(해시) 셋이 붙어 있습니다.

실행 검증

두 번째 커밋의 트리

  • a.txt 와 c.txt 의 blob 이름은 앞 장과 한 글자도 다르지 않습니다.
  • b.txt 만 새 이름(b08c9b9…)을 가집니다.
  • 두 번째 커밋도 파일 셋 전부를 가리킵니다 — 스냅숏입니다. 하지만 바뀌지 않은 둘은 새로 적지 않고 같은 객체를 가리킬 뿐입니다.
실행 검증

객체 수로 확인하기

첫 커밋 뒤와 두 번째 커밋 뒤에 느슨한 객체의 수를 셌습니다.

첫 커밋은 blob 셋 + 트리 하나 + 커밋 하나 = 다섯. 두 번째 커밋이 더한 것은 셋 — 새 blob(b.txt), 새 트리, 새 커밋입니다. 안 바뀐 파일은 한 바이트도 늘리지 않았습니다.

뒤의 킬로바이트 값은 파일시스템 블록 크기라 기계마다 달라서 잘라 냈습니다.

실행 검증

이름만 바꾸면 무엇이 새로 생기나

git mv c.txt see.txt 로 이름만 바꿔 커밋했습니다.

blob 은 그대로(af17f6c…)이고 늘어난 둘은 새 트리와 새 커밋입니다. 파일 이름은 blob 이 아니라 트리에 있습니다. 그래서 이름 바꾸기는 트리만 바꿉니다.

실행 검증

커밋 안에는 diff 가 없다

커밋 객체에 적힌 것은 트리 하나, 부모 하나, 작성자·커미터, 메시지가 전부입니다. "b.txt 의 1줄을 바꿈" 같은 기록은 어디에도 없습니다.

실행 검증

diff 는 그때그때 계산한다

이 요약은 저장된 것이 아닙니다. 두 커밋의 트리를 견주면 blob 이름이 다른 항목은 b.txt 하나이고, 그 두 blob 의 내용을 줄 단위로 견준 결과입니다.

  • 그래서 같은 두 커밋이라도 diff 알고리즘을 바꾸면 다른 diff 가 나옵니다(9부).
  • 이름 바꾸기도 저장되지 않습니다. diff 가 "사라진 파일과 생긴 파일이 닮았다" 를 보고 추측합니다(7·9부).
실행 검증

스냅숏이 싼 까닭

"판마다 전체를 적는다" 는 말은 비싸게 들립니다. 실제로 싼 까닭은 앞의 실험에 다 있습니다.

  • 안 바뀐 파일은 이름(해시)이 같으니 새로 적을 것이 없습니다.
  • 안 바뀐 디렉터리도 같은 이유로 옛 트리 객체를 그대로 가리킵니다 — 바뀐 경로의 트리만 새로 생깁니다.
  • 바뀐 파일도 디스크에서는 나중에 옛 판과의 델타로 눌립니다(10부).

그래서 커밋 하나의 비용은 바뀐 것의 크기에 비례하고, 프로젝트 전체의 크기와는 거의 무관합니다.

설명용

스냅숏이 주는 것

일스냅숏 모델에서는
옛 판 꺼내기그 커밋의 트리를 읽으면 끝 — 차이를 거슬러 적용하지 않습니다
두 판 견주기트리 두 개를 견줍니다. 이름이 같은 하위 트리는 통째로 건너뜁니다
브랜치 만들기커밋 하나를 가리키는 이름표 하나를 더 만들 뿐입니다(4부)
머지세 스냅숏(공통 조상·양쪽 끝)을 견줘 새 스냅숏을 만듭니다(7부)

"이름이 같은 하위 트리는 통째로 건너뛴다" — 이것이 거대한 저장소에서도 git diff 가 빠른 까닭의 하나입니다. 내용 주소 덕분입니다(다음 장).

설명용

2장

내용 주소

이름이 곧 내용의 해시

이름을 붙이지 않고 계산한다

보통의 파일 시스템에서 이름은 사람이 붙입니다. Git 의 객체 저장소에서는 이름을 계산합니다 — 객체의 바이트를 SHA-1 에 넣은 결과가 이름입니다.

  • 같은 바이트 → 언제, 어디서, 누가 계산해도 같은 이름
  • 한 바이트라도 다르면 → 전혀 다른 이름
  • 이름을 알면 → 받은 내용이 맞는지 다시 계산해서 확인할 수 있음

이런 저장소를 내용 주소 저장소(content-addressable storage)라고 부릅니다.

설명용

저장소 밖에서 계산해도 같은 이름

앞 실험의 a.txt 내용(alpha 와 줄바꿈)을 저장소에 넣지 않고 이름만 계산해 봅니다.

a.txt 의 blob 이름 4a58007… 과 같습니다. 이름을 얻으려고 저장소에 물어볼 필요가 없습니다 — 내용만 있으면 됩니다.

실행 검증

이름이 달라도 내용이 같으면 한 객체

a.txt 와 똑같은 내용의 twin.txt 를 만들어 인덱스에 올렸습니다.

경로는 둘이지만 blob 은 하나입니다. 같은 로고 파일이 디렉터리 열 곳에 있어도 저장소에는 한 번만 들어갑니다.

실행 검증

한 글자만 바꾸면

alpha 의 마지막 글자 하나만 바꾼 alphb 의 이름입니다.

앞 장의 4a58007… 과 닮은 데가 없습니다. 해시 함수는 입력이 조금만 달라도 출력이 통째로 바뀌도록 만들어졌습니다. 그래서 이름만 보고 "거의 같은 파일" 을 알아낼 수는 없습니다 — 비슷한 것끼리 묶는 일(델타 압축, 이름 바꾸기 감지)은 따로 합니다.

실행 검증

해시에 들어가는 것 — 머리까지

blob 의 이름은 파일 내용만의 해시가 아닙니다. 앞에 blob 6 과 NUL 바이트를 붙인 것의 SHA-1 입니다.

둘이 같습니다. 머리의 형식 이름(blob)과 크기(6바이트)까지 이름에 들어가므로, 같은 바이트라도 blob 과 트리는 이름이 다릅니다. 바이트 하나하나는 3부에서 봅니다.

실행 검증

저장소가 달라도 같은 이름

hello 와 줄바꿈 여섯 바이트는 이 덱의 여러 실험에 나옵니다. 서로 다른 저장소입니다.

두 저장소 모두 같은 이름 ce01362… 으로 그 blob 을 찾습니다. 내용이 이름을 정하므로, 저장소끼리 객체를 주고받을 때 "이 이름을 가지고 있느냐" 만 물으면 됩니다(11부).

실행 검증

깨지면 알 수 있다

objects 실험에서 느슨한 객체 파일의 마지막 바이트 하나를 뒤집었습니다.

이번에는 zlib 스트림의 검사값이 먼저 잡았습니다. 압축을 통과해도 풀어 낸 바이트의 SHA-1 이 파일 이름과 다르면 역시 걸립니다. 어느 쪽이든 조용히 틀린 내용을 내주지 않습니다.

긴 줄은 fold -w 96 으로 접었습니다 — 명령 줄에 그대로 보입니다.

실행 검증

내용 주소가 강제하는 것 — 불변

이름이 내용에서 나오므로, 객체를 "고친다" 는 말이 성립하지 않습니다. 고친 내용은 다른 이름을 가진 다른 객체입니다.

  • 파일을 고치면 → 새 blob
  • 새 blob 을 가리키는 트리 → 새 트리
  • 새 트리를 가리키는 커밋 → 새 커밋
  • 부모가 달라진 커밋 → 새 커밋(부모의 이름이 커밋 바이트에 들어 있으므로)

그래서 커밋 하나의 이름은 그 커밋까지 이르는 역사 전체를 봉인합니다. 역사의 어느 한 바이트를 바꿔도 그 뒤의 모든 커밋 이름이 바뀝니다.

설명용

1~2장 퀴즈

Q. 파일 100개짜리 프로젝트에서 docs/a.md 하나만 고쳐 커밋했습니다 (docs 아래 하위 디렉터리는 없습니다). 새로 생기는 객체는 몇 개이고 무엇입니까? docs/a.md 를 고치지 않고 이름만 docs/b.md 로 바꿨다면요?

A. 고친 경우 넷 — 새 blob, 새 docs 트리, 새 최상위 트리, 새 커밋. 이름만 바꾼 경우 셋 — blob 은 그대로이고 docs 트리·최상위 트리·커밋만 새로 생깁니다. 실험에서 셋 중 하나를 고쳤을 때 5→8, 이름을 바꿨을 때 8→10 이 된 것과 같은 이치입니다 (그 실험은 하위 디렉터리가 없어 트리가 하나였습니다).
설명용

3장

객체 그래프

네 종류의 객체가 서로를 가리킨다

객체는 네 종류뿐

종류담는 것가리키는 것
blob파일 하나의 내용(이름·권한은 없다)없음
tree디렉터리 하나 — 이름·모드·객체 이름의 목록blob, 하위 tree
commit스냅숏 하나 — 최상위 트리, 부모, 누가·언제·왜tree 하나, 부모 commit 0개 이상
tag주석 붙은 태그 — 이름, 태거, 메시지객체 하나(대개 commit)

화살표는 늘 새 것에서 옛 것으로 향합니다. 객체는 자기가 만들어질 때 이미 있던 객체만 가리킬 수 있기 때문입니다 — 이름을 알아야 가리킬 수 있고, 이름은 내용이 정해져야 나옵니다.

설명용

hello 저장소를 통째로 그리면

파일 하나로 첫 커밋, 파일 둘로 두 번째 커밋, 태그 하나. 그 저장소의 객체 전부입니다.

두 커밋의 hello.txt 는 내용이 달라 blob 이 둘입니다. 커밋마다 제 트리를 가리키고, 새 커밋은 옛 커밋을 부모로 가리킵니다.

실행 검증

저장소의 객체를 모두 나열하기

아홉 개입니다 — blob 셋, tree 셋, commit 둘, tag 하나. 그림의 상자 수와 같습니다. 크기는 머리를 뺀 몸의 바이트 수입니다. hello.txt 의 첫 판(ce01362)이 6바이트, 두 번째 판(94954ab)이 12바이트입니다.

실행 검증

커밋 객체를 열어 보면

  • tree — 이 스냅숏의 최상위 디렉터리
  • parent — 앞 커밋. 첫 커밋에는 이 줄이 없습니다
  • author · committer — 이름·메일·유닉스 시각·시간대. 둘은 다를 수 있습니다(8부)
  • 빈 줄 뒤가 커밋 메시지
실행 검증

트리 객체를 열어 보면

줄마다 모드 · 종류 · 객체 이름 · 경로입니다. 040000 tree 는 하위 디렉터리, 100644 blob 은 보통 파일입니다. 실행 파일은 100755, 심볼릭 링크는 120000 입니다(3·14부).

-r 은 하위 트리 안까지, -t 는 그 하위 트리 줄도 함께 보이게 합니다.

실행 검증

태그 객체를 열어 보면

주석 붙은 태그(-a)는 제 객체를 가집니다. 가리키는 대상(object)과 그 종류, 태그 이름, 태거, 메시지입니다. 주석 없는 태그는 객체 없이 이름표만 있습니다(4부).

실행 검증

커밋은 고칠 수 없다 — amend 의 정체

커밋 메시지에 오타가 있어 git commit --amend 로 고쳤습니다. 고치기 전:

맨 위 커밋의 이름이 8c4f18e 에서 9d60673 으로 바뀌었습니다. 메시지가 커밋 바이트의 일부이니 이름이 바뀌는 것이 당연합니다.

실행 검증

옛 커밋은 어디로 갔나

옛 커밋은 그대로 있습니다. amend 는 새 커밋을 만들고 브랜치 이름표를 옮겼을 뿐입니다. 옛 커밋은 이제 어느 브랜치에서도 닿지 않을 뿐, 지워지지 않았습니다.

reflog 가 그 길을 기억합니다. 잘못 amend 했다면 HEAD@{1} 로 돌아갈 수 있습니다(16부). 닿지 않는 객체가 정말 지워지는 때는 10부(gc·prune)에서 봅니다.

실행 검증

"역사를 고친다" 의 실제 뜻

amend·rebase·filter-repo 같은 "역사 고치기" 명령은 모두 같은 일을 합니다.

  1. 원하는 모습의 새 커밋들을 만든다
  2. 브랜치 이름표를 새 커밋으로 옮긴다
  3. 옛 커밋은 그대로 둔다 — 닿지 않게 될 뿐

그래서 "고친" 역사를 이미 가져간 사람이 있으면 두 역사가 갈라집니다. 옛 커밋이 여전히 그 사람 저장소에서 살아 있기 때문입니다(8·12부).

설명용

4장

DAG

부모를 가리키는 화살표만으로 적은 역사

역사 = 부모 화살표

커밋은 부모의 이름을 품습니다. 그 화살표를 따라가면 역사가 됩니다.

  • 부모가 없는 커밋 — 뿌리(root). 보통 저장소에 하나입니다
  • 부모가 하나 — 보통 커밋
  • 부모가 둘 이상 — 머지 커밋(7부)

화살표가 늘 옛 것을 향하니 되돌아오는 고리가 생길 수 없습니다. 이런 그래프를 방향 비순환 그래프(DAG, directed acyclic graph)라고 부릅니다.

실행 검증

갈라지고 합쳐지는 역사

dag 실험은 main 과 side 가 서로를 한 번씩 합친 역사를 만듭니다.

가장 가까운 공통 조상이 하나가 아니라 둘(옅은 원)인 모양입니다. 이 모양이 머지를 어렵게 만드는 까닭은 7부에서 봅니다.

실행 검증

git 이 그린 같은 그래프

줄 하나가 커밋 하나, | / \ 가 부모 화살표입니다. 앞 장의 그림과 같은 여덟 커밋입니다. 이 덱은 --graph 그림을 손으로 그리지 않고 캡처로만 싣습니다.

실행 검증

"브랜치의 역사" = 닿을 수 있는 커밋

main 의 역사란 main 이 가리키는 커밋에서 부모 화살표를 따라 닿을 수 있는 커밋 전부입니다.

그림에서 세어 보면 main 의 끝 G 에서 H 와 옆 머지(32d4394)에는 닿지 않습니다 — 여덟 가운데 여섯. 브랜치에 "속한" 커밋이라는 목록은 어디에도 저장되어 있지 않고, 그때그때 화살표를 따라 계산합니다.

실행 검증

브랜치는 파일 하나

main 은 커밋 이름 40글자가 든 파일이고, HEAD 는 "지금은 main" 이라고 적힌 파일입니다. 브랜치를 만드는 비용은 파일 하나를 쓰는 비용입니다. 커밋하면 git 은 새 커밋을 만들고 이 파일의 내용을 새 이름으로 바꿉니다(4부).

이 캡처는 첫 커밋 직후라 main 이 첫 커밋 e8563ea 를 가리킵니다.

실행 검증

3~4장 퀴즈

Q. 동료가 "어제 amend 한 커밋 때문에 브랜치에서 커밋 하나가 사라졌다" 고 합니다. 그 커밋은 저장소에서 지워졌습니까? 그리고 main 에 "속한" 커밋의 목록은 .git 의 어디에 적혀 있습니까?

A. 지워지지 않았습니다. amend 는 새 커밋을 만들고 브랜치 이름표를 옮겼을 뿐이라, 옛 커밋은 객체 저장소에 남아 있고 reflog(HEAD@{1} 등)로 찾을 수 있습니다 — gc 가 닿지 않는 객체를 치우기 전까지는. 브랜치에 속한 커밋 목록은 어디에도 없습니다. main 파일에는 커밋 이름 하나뿐이고, 역사는 거기서 부모 화살표를 따라가며 계산합니다.
설명용

5장

세 영역

작업 트리 · 인덱스 · HEAD

파일이 사는 세 곳

  • 작업 트리 — 편집기로 여는 디스크의 파일
  • 인덱스 — .git/index. "다음 커밋은 이렇게 생길 것" 이라는 초안
  • HEAD 의 커밋 — 마지막으로 커밋한 스냅숏

명령은 거의 모두 이 셋 사이에서 무엇을 어느 쪽으로 옮기는 일입니다. 화살표와 명령의 대응은 6부에서 명령 하나씩 캡처로 확인합니다.

설명용

작업 트리에만 있을 때

빈 저장소에 hello.txt 를 만들기만 했습니다.

git 은 이 파일을 "추적하지 않는 파일" 이라고 부릅니다. 인덱스에 없기 때문입니다(아직 커밋이 없으니 HEAD 에도 없습니다). .git 안에는 아직 이 파일의 흔적이 전혀 없습니다.

실행 검증

add 가 하는 일 — blob 을 지금 만든다

git add 는 목록에 이름을 적어 두는 명령이 아닙니다. 그 순간의 내용으로 blob 을 만들어 저장소에 넣고, 인덱스에 "이 경로 = 이 blob" 을 적습니다. 그래서 add 뒤에 파일을 또 고치면, 커밋되는 것은 add 했을 때의 내용입니다.

-type f 가 아니라 ! -type d 인 까닭 — 이 기계의 find 가 읽기 전용 객체 파일을 파일로 못 알아봐서입니다. 뜻은 같습니다.

실행 검증

인덱스에 적힌 것

인덱스 한 줄은 트리의 한 줄과 거의 같습니다 — 모드, blob 이름, 경로. 가운데의 0 은 머지 충돌 때만 1·2·3 이 되는 단계 번호입니다(5·7부). 인덱스는 아직 트리 객체가 되지 않은 다음 트리입니다.

실행 검증

commit 이 하는 일 — 인덱스를 트리로

객체가 하나에서 셋이 됐습니다. 늘어난 둘은 인덱스로 만든 트리(aaa96ce)와 커밋(e8563ea)입니다. blob 은 add 때 이미 있었으니 commit 은 파일을 다시 읽지 않습니다.

실행 검증

작업 트리만 바뀌었을 때

짧은 상태 표시의 두 칸은 왼쪽 = HEAD 대 인덱스, 오른쪽 = 인덱스 대 작업 트리입니다. M 은 왼쪽이 비고 오른쪽이 M — 인덱스는 HEAD 와 같고, 작업 트리만 다르다는 뜻입니다.

실행 검증

두 칸 읽기 연습

같은 저장소에서 이어서 찍은 짧은 상태들입니다.

  • R · D — 왼쪽 칸: 인덱스가 HEAD 와 다름(이름 바뀜·지움)
  • ?? — 인덱스에 없는 파일. 가운데 캡처의 src/ 처럼 HEAD 에 있어도 인덱스에서 빠지면 ?? 입니다
  • D — 오른쪽 칸: 인덱스에는 있는데 작업 트리에서 사라짐
실행 검증

diff 도 두 가지

git diff 는 "아직 add 하지 않은 것", git diff --cached 는 "add 했지만 아직 커밋하지 않은 것" 입니다. 상태 표시의 오른쪽 칸과 왼쪽 칸에 해당합니다.

실행 검증

왜 인덱스가 따로 있나

  • 커밋을 고른다 — 고친 파일 열 개 가운데 셋만, 한 파일 안에서도 일부만 (add -p, 15부) 다음 커밋에 넣을 수 있습니다.
  • 빠르다 — 인덱스는 파일마다 크기·시각을 기억해 두어, status 가 파일을 다 읽지 않고 바뀐 것만 골라냅니다(5부).
  • 머지의 작업대 — 충돌한 경로는 인덱스에 세 판(공통 조상·우리·그쪽)으로 올라갑니다(7부).
설명용

5장 퀴즈

Q. notes.txt 를 고치고 git add notes.txt 한 뒤 한 줄을 더 고쳤습니다. git status --short 는 무엇을 보이고, 지금 git commit 하면 두 번째 고침이 들어갑니까?

A. MM notes.txt 입니다 — 왼쪽 M(인덱스가 HEAD 와 다름), 오른쪽 M(작업 트리가 인덱스와 다름). 커밋에는 들어가지 않습니다. add 는 그 순간의 내용으로 blob 을 만들어 인덱스에 적었고, 커밋은 인덱스를 트리로 만들 뿐 작업 트리를 다시 읽지 않기 때문입니다.
설명용

6장

분산

모든 복제본이 온전한 저장소다

중앙 서버가 없어도 되는 까닭

중앙 집중형 도구에서 역사는 서버에 있고, 사용자의 디스크에는 작업 사본만 있습니다. Git 의 clone 은 객체 저장소를 통째로 복사합니다.

  • 역사 보기·브랜치·커밋·diff·머지 — 전부 네트워크 없이 됩니다
  • "서버" 는 모두가 약속한 복제본 하나일 뿐, 기술적으로 특별하지 않습니다
  • 서버가 사라져도 아무 복제본에서 다시 세울 수 있습니다
설명용

clone 한 저장소

원본의 객체 여섯(커밋 둘·트리 둘·blob 둘)이 복제본의 객체 저장소에 그대로 있습니다.

로컬 경로에서 복제하면 원본의 객체 파일을 그대로 복사(또는 하드링크)합니다 — 원본이 느슨한 객체라 복제본도 느슨합니다. 원본이 팩이면 팩으로, file:// 이나 네트워크 너머에서는 늘 팩으로 옵니다(11부).

실행 검증

원격은 주소와 소식

origin 은 약속된 별명일 뿐입니다. remotes/origin/main 은 "마지막으로 받아 왔을 때 원격의 main 이 가리키던 커밋" 을 적은 이름표입니다 — 실시간이 아닙니다(12부).

실행 검증

원본을 지워도

원본 저장소 디렉터리를 통째로 지운 뒤, 복제본에서 커밋하고 검사했습니다.

원본이 없어도 역사·커밋·검사가 모두 됩니다. "하나 앞섰다" 는 원격에 물어본 결과가 아니라 복제본이 기억하는 origin/main 과 견준 것입니다.

실행 검증

7장

두 층의 명령

porcelain 과 plumbing

사람용 명령과 도구용 명령

git 의 명령 목록(command-list.txt)은 명령을 분류해 둡니다. 크게 두 층입니다.

층예성격
porcelain(사람용)add commit switch merge 여러 일을 한 번에, 출력은 사람이 읽기 좋게 — 판마다 문구가 바뀔 수 있다
plumbing(도구용)hash-object update-index write-tree commit-tree update-ref 한 가지 일만, 입출력 형식이 안정적 — 스크립트가 기대어도 된다

공식 튜토리얼은 핵심을 plumbing(배관), 그 위의 보기 좋은 인터페이스를 porcelain(도자기)이라 부르고, "porcelain 이 물을 못 내릴 때" plumbing 이 무엇을 하는지 알아 두면 좋다고 적습니다. 17부의 명령어 사전이 분류를 명령마다 적습니다.

설명용

plumbing 으로 커밋 만들기 (1) — blob

porcelain 을 하나도 쓰지 않고 커밋 하나를 쌓아 봅니다. 작업 트리에는 파일을 만들지 않습니다.

표준 입력의 세 바이트(hi 와 줄바꿈)로 blob 을 만들어 저장했습니다. 출력이 그 이름입니다.

실행 검증

(2) 인덱스에 올리기

파일을 읽지 않고, "이 경로 = 이 blob" 을 인덱스에 바로 적었습니다. git add 가 안에서 하는 일의 뒷부분입니다.

실행 검증

(3) 인덱스를 트리로

실행 검증

(4) 트리를 커밋으로, (5) 이름표 옮기기

git add 가 앞의 두 걸음(blob·인덱스)을, git commit 이 뒤의 세 걸음(트리·커밋·참조)을 한 번에 합니다. 작성자·시각은 환경 변수(0부의 gitenv.sh)에서 왔습니다.

실행 검증

작업 트리는 한 번도 건드리지 않았다

--porcelain=v2 는 이름과 달리 도구용 출력입니다 — 사람용(porcelain) 명령이 스크립트에게 약속하는 안정된 형식이라는 뜻입니다. .D 가 짧은 표시의 D, 그 뒤로 HEAD·인덱스·작업 트리의 모드, HEAD·인덱스의 객체 이름이 옵니다.

실행 검증

인덱스에서 작업 트리로

세 영역의 마지막 칸이 채워졌습니다. 이 커밋은 "작업 트리 → 인덱스 → 커밋" 이 아니라 "객체 → 인덱스 → 커밋 → 작업 트리" 순서로 태어났습니다. 세 영역이 서로 독립된 저장소라는 증거입니다.

실행 검증

2부 정리 — 일곱 가지 그림

그림확인한 캡처
스냅숏하나만 고치면 객체 5 → 8, 이름만 바꾸면 8 → 10

설명용

6~7장 퀴즈

Q. 사내 Git 서버의 디스크가 망가졌습니다. 개발자 노트북의 복제본으로 무엇을 되살릴 수 있고, 무엇은 되살릴 수 없을 수 있습니까? 그리고 사내 도구가 git status 의 출력을 파싱한다면 어떤 옵션을 써야 합니까?

A. 복제본이 마지막으로 받아 온 시점까지의 모든 커밋·트리·blob 과 그 브랜치들은 되살릴 수 있습니다 — 복제본이 온전한 저장소이기 때문입니다. 누구도 받아 가지 않은, 서버에만 푸시된 커밋이나 서버 쪽 설정·훅은 되살리지 못할 수 있습니다. 파싱에는 사람용 출력 대신 --porcelain(또는 --porcelain=v2)을 씁니다 — 판이 바뀌어도 형식을 지키기로 약속한 출력입니다.
