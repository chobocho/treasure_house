활용 가이드 II — 사고 복구

사고 → 진단 → 복구, 40 장면

이 부에서 할 일

장면마다 새 저장소에서 사고를 실제로 일으키고, 진단하고, 복구한 캡처입니다. 장면 번호는 실험 대본(exps/recovery.py)의 번호 그대로입니다.

실행 검증

먼저 물을 두 가지

  1. 이미 보냈는가(push)? — 보내지 않았다면 역사를 고쳐도(amend·reset·rebase) 됩니다. 보냈다면 되돌리는 새 커밋(revert)을 쌓는 쪽이 원칙입니다.
  2. 커밋된 적이 있는가? — 한 번이라도 커밋(또는 stash)된 것은 객체로 남아 reflog·fsck 로 찾을 수 있습니다. 커밋된 적 없는 작업 트리의 고침은 git 도 모릅니다.

그리고 겁이 날 때 할 일 하나: 아무것도 지우지 말고 git branch 살려둠 으로 지금 자리에 이름부터 붙여 둡니다.

Q. 동료가 "reset --hard 를 잘못 쳐서 어제 커밋 셋이 날아갔다" 고 합니다. 무엇부터 칩니까? 그리고 커밋하지 않은 작업 트리의 고침을 git restore . 로 버렸다면 되살릴 수 있습니까?

A. git reflog 로 reset 직전의 자리(HEAD@{1} 따위)를 찾아 git reset --hard 나 git branch 로 돌아갑니다(장면 08). 커밋은 객체로 남아 있으니까요. 반면 커밋도 stash 도 된 적 없는 고침은 git 에 객체가 없어 되살릴 수 없습니다(장면 07) — 편집기의 되돌리기나 백업을 찾아야 합니다.

사고 — 원격에서 지워진 브랜치가 내 쪽에 계속 보인다.

fetch 는 기본으로 추적 브랜치를 지우지 않습니다. 늘 그렇게 하려면 git config fetch.prune true. 내가 push 로 지웠다면 origin/gone 은 그때 같이 지워집니다 — 이 장면의 첫 판은 그래서 지울 것이 없었고, 다른 clone 에서 지우도록 고쳤습니다.

Q. 이미 push 한 main 의 커밋 하나에 API 키가 들어 있었습니다. git commit --amend 나 filter-branch 로 지우고 강제 push 하면 해결입니까?

A. 아닙니다. 이미 받아 간 사람들의 사본, 원격의 reflog·백업, 이 저장소의 refs/original·reflog(장면 17·18)에 키가 남습니다. 먼저 키를 폐기하고 새로 발급하는 것이 해결이고, 역사 정리는 그다음 — 모두에게 다시 clone 하도록 알리는 일까지가 한 묶음입니다.
