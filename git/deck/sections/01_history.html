Git 이전

파일 하나에서 저장소 하나로

SCCS 와 RCS — 파일 하나의 판

  • SCCS — M. J. Rochkind 의 Source Code Control System 논문이 1975-12 에 IEEE TSE 에 실렸습니다.
  • RCS — W. F. Tichy 의 논문이 1985-07 에 Software: Practice and Experience 에 실렸습니다.

둘 다 파일 하나의 판을 관리합니다. 파일을 고치기 전에 잠그고(lock), 고친 뒤 풀어 줍니다. 여러 파일을 묶은 "한 번의 변경" 이라는 개념은 없습니다.

설명용

CVS — 잠그지 않고 함께

  • 1986 — Dick Grune 이 셸 스크립트판 CVS 를 내놓았습니다(RCS 위의 스크립트).
  • 1990 — Brian Berliner 가 C 로 다시 짠 CVS 를 USENIX Winter 1990 에서 발표했습니다.

파일을 잠그지 않고 각자 고친 뒤 합치는 방식, 그리고 서버 하나에 모두 모이는 중앙집중 구조가 이때 자리 잡았습니다. 여전히 파일마다 따로 판을 매겨, 여러 파일에 걸친 변경을 한 단위로 되돌리기 어려웠습니다.

설명용

Subversion — 더 나은 CVS

  • 2000-10-20 — 첫 이정표(Milestone 1)
  • 2004-02-23 — 1.0.0

저장소 전체에 하나의 판 번호를 매기고, 커밋을 원자적으로 만들었습니다. 그러나 여전히 서버가 하나인 중앙집중이라, 역사를 보거나 커밋하려면 서버에 닿아야 했습니다.

2005년 4월

BitKeeper 와 헤어진 뒤의 두 주

커널과 BitKeeper

리눅스 커널은 상용 분산 버전 관리 도구 BitKeeper 를 무료판으로 쓰고 있었습니다. 2005-04-06, LWN 은 BitMover 가 무료판 지원을 거둔다고 보도했습니다 ("BitMover is now withdrawing support for the free version").

같은 날 Linus Torvalds 는 LKML 에 "Kernel SCM saga.." 를 보냈습니다.

LWN, "The kernel and BitKeeper part ways", 2005-04-06 (lwn.net/Articles/130746)

설명용

"Kernel SCM saga.."

We've been using BK for three years, and in fact, the biggest problem right now is that a number of people have gotten very very picky about their tools after having used the best.

BitKeeper 를 3년 쓴 끝에 대안을 찾아야 한다는 메일입니다. BitMover 를 탓하지 말라는 말과 함께, BitKeeper 가 커널 개발 방식을 좋은 쪽으로 바꿨다고 적었습니다. 이 메일에는 아직 "git" 이라는 이름이 없습니다.

설명용

추신 — Subversion 말고 monotone

PS. Don't bother telling me about subversion. If you must, start reading up on "monotone".

본문은 "개별 패치(individual patches)" 로 보내 달라고, 그리고 BitKeeper 가 길러 준 잘게 쪼갠 변경 추적을 잃지 않겠다고 말합니다. 중앙집중 도구로는 돌아가지 않겠다는 뜻입니다.

1.x 와 GitHub

쓸 수 있는 도구가 되기까지

1.5.0 — reflog 가 기본이 되다

reflog 는 1.4.0, git pack-refs 는 1.4.4 에 들어왔습니다(1.5.0 노트의 "Old news"). 1.5.0 은 reflog 를 작업 트리가 있는 저장소에서 기본으로 켜고, HEAD 에도 reflog 를 두고, reflog 가 가리키는 커밋을 가지치기에서 지키고, git reflog expire 를 더했습니다 — 16부의 복구가 거의 모두 기대는 모습이 이때 갖춰졌습니다.

설명용

1.6.0 과 1.7.0 — 명령 정리와 안전장치

  • 1.6.0 — 대부분의 git-xyzzy 꼴 명령이 $PATH 밖에 설치됩니다. git xyzzy 로 부르는 지금의 모습입니다.
  • 1.7.0 — bare 가 아닌 저장소의 체크아웃된 브랜치로 push 하는 것을 기본으로 거부합니다.
설명용

GitHub — 2008-04-10

GitHub 은 2008-04-10 에 정식으로 문을 열었습니다(GitHub 블로그 "We launched"). 저장소를 맡아 주고, 포크와 풀 리퀘스트로 남의 저장소에 기여하는 흐름을 웹으로 옮겼습니다. 풀 리퀘스트는 git 의 기능이 아니라 이 서비스들의 기능이라는 것은 12·14부에서 봤습니다.

창업 날짜는 1차 출처를 찾지 못해 적지 않습니다.

설명용

SHAttered 와 sha1dc

2017-02-23, CWI 와 Google 이 첫 SHA-1 충돌(SHAttered)을 발표했습니다 — SHA-1 계산 9,223,372,036,854,775,808 번이 들었다고 적었습니다. 석 달 뒤 2.13.0 에서 git 은 알려진 충돌 공격을 탐지하는 SHA-1 구현(sha1dc, Marc Stevens·Dan Shumow)을 기본으로 삼았습니다.

해시를 바꾸는 길도 열렸습니다 — 2.16.0 에 쓸 해시 함수를 정하는 기반이 들어왔고, 2.29.0 에서 SHA-256 저장소가 실험 기능으로 표시됐습니다(두 형식의 상호운용은 없음).

설명용

2.23.0 — switch 와 restore

checkout 이 하던 두 가지 일 — 브랜치 바꾸기와 파일 되돌리기 — 을 switch 와 restore 가 나눠 맡았습니다. 이 덱이 checkout 대신 두 명령을 쓰는 까닭입니다. checkout 은 그대로 남아 있습니다.

Git 3.0 의 계획

2.55.0 의 BreakingChanges 문서는 Git 3.0 에서 바꿀 것을 적어 둡니다:

  • 새 저장소의 기본 해시를 SHA-256 으로
  • 기본 참조 형식을 reftable 로
  • 기본 브랜치 이름을 main 으로
  • 빌드에 Rust 를 필수로

그리고 "There is no planned release date for this breaking version yet" — 2026-09 기준 출시일은 정해지지 않았습니다.
