8부

리베이스와 역사 재작성

커밋을 옮기고, 고치고, 되돌리기

이 부에서 할 일

2부에서 "커밋은 고칠 수 없고, 역사 고치기는 새 커밋을 만들어 이름표를 옮기는 일" 이라고 했습니다. 리베이스·체리픽·되돌리기·filter-branch 가 모두 그 한 문장의 변주입니다.

  • rebase 의 정체 — 체리픽의 반복
  • 충돌하면 — REBASE_HEAD, --continue · --skip · --abort
  • 대화형 리베이스 — squash · fixup · reword · drop · 순서 · exec
  • --onto · --update-refs · --rebase-merges
  • cherry-pick 과 revert, 머지를 되돌린 뒤의 함정
  • 역사 전체 고치기 — filter-branch 와 그 경고
설명용

1장

rebase 의 정체

커밋을 하나씩 다시 만든다

옮기기 전

git rebase main 은 "feature 의 커밋들을 main 의 끝 위에서 다시 만들어라" 입니다.

실행 검증

옮긴 뒤

F1·F2·F3 의 이름이 모두 바뀌었습니다(2736482 → fa4b5b7 …). 내용이 같아도 부모와 committer 시각이 바뀌었으니 새 커밋입니다(3부).

실행 검증

그림으로

실행 검증

reflog 가 보여 주는 순서

  1. rebase (start) — main 의 끝으로 분리 HEAD 이동
  2. rebase (pick) 셋 — 커밋마다 체리픽
  3. rebase (finish) — feature 이름표를 마지막 새 커밋으로 옮기고 브랜치로 돌아옴

리베이스 도중에는 분리 HEAD 입니다. 끝나야 브랜치가 옮겨집니다 — 그래서 중간에 멈춰도 feature 는 옛 자리에 있습니다.

실행 검증

author 시각은 남고 committer 시각은 새로

"이 변경을 누가 언제 썼나" 는 그대로, "이 커밋 객체를 누가 언제 만들었나" 만 바뀝니다(3부의 author·committer). 그래서 리베이스한 브랜치의 git log 날짜(작성자 기준)는 옛 날짜로 보입니다.

실행 검증

range-diff — 전과 후를 짝지어 견주기

= 는 "짝의 변경이 똑같다" 는 뜻입니다. 이름은 달라도 담은 변경은 같다는 확인 — 리베이스가 무엇을 바꿨는지 검토할 때 씁니다. 변경이 달라진 짝은 ! 와 함께 그 차이가 나옵니다.

실행 검증

이미 들어간 변경은 건너뛴다

main 이 feature 의 F2 를 미리 체리픽해 두었습니다.

git 은 커밋의 이름이 아니라 변경 내용의 지문(patch-id)을 견줍니다. 체리픽한 커밋은 이름이 달라도 지문이 같습니다.

리베이스 중 충돌

멈추고, 풀고, 이어 가기

F2 에서 멈췄다

실행 검증

리베이스의 상태는 파일로

리베이스는 이 디렉터리가 있는 동안 "진행 중" 입니다. 할 일 목록이 파일이라 터미널을 닫았다 열어도 --continue 로 이어집니다.

실행 검증

풀고 이어 가기

풀린 기준은 머지 때와 같습니다 — 인덱스에 단계 0 항목(7부). 이 캡처의 GIT_EDITOR=true 는 메시지 편집기를 열지 않게 한 것입니다.

실행 검증

--skip 과 --abort

--skip 은 그 커밋의 변경을 버립니다. 캡처에서 F2 가 사라졌습니다. --abort 는 feature 를 옛 자리로 되돌리고 진행 파일을 지웁니다 — 옛 이름(7e35da2 …)이 그대로입니다.

실행 검증

1~2장 퀴즈

Q. 리베이스를 하다 셋째 커밋에서 충돌이 났습니다. 이 순간 feature 브랜치 파일은 무엇을 가리킵니까? 그리고 리베이스를 끝낸 뒤 "옛 feature" 를 보려면 무엇을 씁니까?

A. 아직 옛 끝을 가리킵니다 — 리베이스 중에는 분리 HEAD 로 새 커밋을 쌓고, rebase (finish) 에서야 브랜치를 옮깁니다. 끝낸 뒤에는 ORIG_HEAD 나 feature@{1}(브랜치의 reflog)로 옛 끝을 봅니다.

목록은 위에서 아래로 실행됩니다. 줄을 지우면 그 커밋이 사라진다는 경고가 목록 끝에 적혀 있습니다.

실행 검증

squash — 두 커밋을 하나로

실행 검증

fixup! 과 --autosquash

commit --fixup X 는 제목이 fixup! <X 의 제목> 인 커밋을 만듭니다. --autosquash 가 그 제목을 보고 할 일 목록에서 X 바로 뒤로 옮겨 fixup 으로 바꿉니다.

실행 검증

순서 바꾸기와 drop

순서를 바꾸면 같은 변경이라도 다른 부모 위에 쌓이니 충돌이 날 수 있습니다. drop 한 커밋은 reflog 로만 닿습니다.

실행 검증

reword — 메시지만 고치기

GIT_SEQUENCE_EDITOR 는 할 일 목록을, GIT_EDITOR 는 커밋 메시지를 고치는 편집기입니다. 이 덱은 둘 다 스크립트로 주어 사람 없이 대화형 리베이스를 돌립니다.

실행 검증

exec — 커밋마다 명령 돌리기

git rebase -x "make test" main 은 옮긴 커밋 하나하나에서 시험을 돌리고, 실패하면 거기서 멈춥니다. 모든 커밋이 빌드되는 역사를 만드는 도구입니다(9부의 bisect 가 그 덕을 봅니다).

처음 이 캡처를 떴을 때는 명령을 큰따옴표로 감싸 그 안의 $(…) 를 리베이스 전에 바깥 셸이 먼저 펼쳤고, 세 줄이 모두 F3 였습니다. 명령 전체를 작은따옴표로 감싸 exec 가 커밋마다 새로 돌리게 했습니다.

4장

옮겨 심기의 변형

--onto · --update-refs · --rebase-merges

--onto — 일부만 떼어 다른 곳에

git rebase --onto 새바탕 옛바탕 브랜치 — "옛바탕..브랜치" 범위의 커밋을 새바탕 위에 다시 만듭니다. F1 은 옛바탕 쪽에 속해 빠졌습니다. 잘못된 브랜치에서 딴 주제 브랜치를 옮겨 심을 때 씁니다.

실행 검증

--update-refs — 쌓인 브랜치들을 함께

F1 을 가리키는 part1, F2 를 가리키는 part2 위에 feature(F3)가 쌓여 있었습니다(풀 리퀘스트를 쪼개 쌓는 흔한 모양). 이 옵션이 없으면 feature 만 옮겨지고 part1·part2 는 옛 커밋에 남습니다.

실행 검증

--rebase-merges — 머지 모양을 지키며

실행 검증

옮긴 결과 — 모양 그대로 대 한 줄로

그냥 리베이스는 머지 커밋을 버리고 그 안의 커밋들을 줄 세웁니다. 머지 모양이 의미 있는 역사라면 -r 을 줍니다.

5장

cherry-pick 과 revert

커밋 하나를 옮기고, 되돌리고

cherry-pick — 한 커밋의 변경을 여기에

체리픽은 "그 커밋과 그 부모의 차이" 를 여기에 3-way 로 적용하는 것입니다(베이스 = 그 커밋의 부모). 그래서 충돌도 머지와 같은 모양으로 납니다.

실행 검증

-x — 어디서 가져왔는지 적어 두기

릴리스 브랜치로 수정을 옮겨 올 때 -x 를 주면 나중에 "이 수정은 어느 커밋에서 왔나" 를 찾을 수 있습니다. 범위 feature~1..feature 는 4부의 두 점 범위라 feature~1 자신은 빠지고 F3 하나만 왔습니다.

실행 검증

revert — 되돌리는 새 커밋

revert 는 역사를 지우지 않습니다. 반대 변경을 담은 커밋을 하나 더 쌓을 뿐이라, 이미 공유한 브랜치에서도 안전합니다. 리베이스·amend 처럼 이름을 바꾸지 않기 때문입니다.

실행 검증

머지 커밋을 되돌리려면 -m

"되돌린다" 는 한 부모와의 차이를 거꾸로 적용하는 것이라, 머지 커밋에서는 기준 부모를 골라야 합니다. 보통 -m 1 — 합쳐 들어온 쪽의 변경을 빼는 것입니다.

실행 검증

함정 — 되돌린 머지는 다시 들어오지 않는다

topic(T1)을 머지했다가 revert 하고, topic 에 고침(T2)을 더해 다시 머지했습니다.

머지는 "베이스 이후의 변경" 을 합칩니다. T1 은 첫 머지로 이미 main 의 조상이 되었으니 베이스 앞쪽에 있고, 그 변경을 지운 revert 만 남아 있습니다. 공식 문서도 머지를 되돌리면 "그 머지가 들여온 변경을 다시는 원하지 않는다고 선언하는 것" 이라고 적습니다.

실행 검증

되돌린 것을 되돌린다

다시 원한다면 revert 커밋을 revert 합니다. 고친 topic 을 머지하기 전에 하는 것이 순서지만, 이 캡처처럼 뒤에 해도 결과 트리는 같습니다.

실행 검증

3~5장 퀴즈

Q. 공유한 main 에 잘못된 커밋 X 가 들어갔습니다. git rebase -i 로 drop 하는 것과 git revert X 의 차이는? 그리고 머지를 revert 했던 브랜치를 고쳐 다시 머지할 때 무엇을 먼저 해야 합니까?

A. drop 은 X 뒤의 모든 커밋 이름을 바꿔 역사를 새로 쓰므로, 이미 main 을 받아 간 사람들의 역사와 갈라집니다(12부). revert 는 반대 변경을 담은 새 커밋을 더할 뿐이라 이름이 바뀌지 않아 공유 브랜치에 안전합니다. 되돌린 머지의 브랜치를 다시 합칠 때는 먼저 그 revert 커밋을 revert 해야 옛 변경까지 돌아옵니다.
설명용

6장

역사 전체 고치기

모든 커밋에서 파일 하나를 지운다면

비밀이 든 커밋

파일을 지우는 새 커밋을 더해도 옛 커밋에는 남습니다. 역사에서 지우려면 그 커밋과 그 뒤의 모든 커밋을 다시 만들어야 합니다.

실행 검증

filter-branch — 그리고 첫 줄의 경고

공식 문서는 filter-branch 가 "함정 투성이" 라며 filter-repo 같은 다른 도구를 쓰라고 첫머리에 적습니다. filter-repo 는 git 에 들어 있지 않은 별도 도구이고, 이 기계에는 깔려 있지 않습니다.

실행 검증

고친 뒤

base 의 이름은 그대로입니다(바뀐 것이 없으니). 그 뒤 커밋은 전부 새 이름입니다. 옛 커밋은 백업 참조와 reflog 로 여전히 닿으므로, 비밀을 정말 없애려면 그것들을 지우고 gc 해야 하고(10부), 무엇보다 이미 퍼진 비밀은 바꿔야 합니다(16부).

실행 검증

공유한 역사를 고칠 때

  • 리베이스·amend·filter 는 커밋 이름을 바꿉니다. 옛 커밋을 받아 간 복제본들은 그대로입니다.
  • 그 위에 작업한 사람이 pull 하면 옛 커밋과 새 커밋이 둘 다 역사에 들어가 같은 변경이 두 번 보입니다.
  • 그래서 관례는 "남이 받아 간 브랜치는 고치지 않는다" 이고, 고쳐야 한다면 알리고 모두가 새 역사로 옮깁니다(12부).
문서 근거

8부 정리

도구하는 일커밋 이름
rebase커밋들을 새 바탕 위에서 다시 만든다(체리픽의 반복)바뀐다
rebase -i할 일 목록으로 squash·fixup·reword·drop·순서·exec바뀐다
cherry-pick한 커밋의 변경을 여기에 3-way 로새 커밋
revert반대 변경을 담은 새 커밋기존 그대로
filter-branch모든 커밋을 다시 만든다고친 뒤 전부 바뀐다

옛 커밋은 늘 ORIG_HEAD · reflog · refs/original 에 남아 있다가, 닿지 않게 된 뒤 gc 가 치웁니다.

설명용

6장 퀴즈

Q. 푸시한 브랜치의 옛 커밋에 비밀번호가 들어 있었습니다. filter-branch 로 역사를 고치고 강제 푸시했습니다. 이제 안전합니까?

A. 아닙니다. 옛 커밋은 내 저장소의 refs/original·reflog 에, 다른 사람들의 복제본에, 서버의 캐시나 포크에 남아 있을 수 있습니다. 역사 고치기는 앞으로 퍼지는 것을 줄일 뿐입니다. 비밀번호 자체를 바꾸는 것이 먼저입니다(16부).
