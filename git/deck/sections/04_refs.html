4부

참조

브랜치·태그·HEAD — 객체에 붙이는 이름표

이 부에서 할 일

객체의 이름은 40글자라 사람이 쓰기 어렵고, 새 커밋이 생길 때마다 바뀝니다. 그래서 git 은 "지금 이 이름을 가리키는" 이름표를 따로 둡니다. 그것이 참조(ref)입니다.

  • 참조가 디스크에 어떻게 적히는가 — 파일, packed-refs, reftable
  • HEAD 라는 특별한 참조, 그리고 분리 HEAD
  • 짧은 이름을 온전한 참조로 푸는 규칙
  • 조상과 범위 표기 — ~ ^ .. ...
  • 참조를 안전하게 바꾸기 — 잠금과 트랜잭션
  • reflog — 참조가 지나온 길
설명용

1장

참조는 파일 하나

refs/heads/main 에 든 것

브랜치 파일을 열어 보면

커밋 이름 40글자와 줄바꿈 — 41바이트가 전부입니다. "브랜치" 라는 말이 무겁게 들리지만, 디스크의 실체는 이 파일 하나입니다.

  • refs/heads/ — 브랜치
  • refs/tags/ — 태그
  • refs/remotes/<원격>/ — 원격 추적 브랜치(마지막으로 받아 온 원격의 소식)
실행 검증

브랜치 만들기 = 파일 쓰기

객체는 하나도 생기지 않았습니다. 브랜치가 수천 개여도 저장소가 무거워지지 않는 까닭입니다.

실행 검증

로그에 붙는 이름표

HEAD -> main 은 "HEAD 가 main 을 가리키고, main 이 이 커밋을 가리킨다" 는 뜻입니다. 화살표가 두 번입니다 — 다음 장에서 봅니다.

실행 검증

2장

HEAD

이름표를 가리키는 이름표

HEAD 의 내용

HEAD 는 보통 커밋이 아니라 다른 참조의 이름을 담습니다(ref: …). 이런 참조를 심볼릭 참조라고 합니다. 커밋하면 git 은 HEAD 를 따라가 main 파일을 새 커밋으로 바꿉니다 — HEAD 파일은 그대로입니다.

실행 검증

분리 HEAD — 이름표 없이 커밋에 서기

실행 검증

분리 HEAD 에서 커밋하면

분리 HEAD 에서도 커밋은 됩니다. 새 커밋이 생기고 HEAD 파일이 그 이름으로 바뀝니다. 문제는 어느 브랜치 파일도 그 커밋을 가리키지 않는다는 것입니다.

  • 다른 브랜치로 옮겨 가면 그 커밋에 닿는 이름표가 없어집니다.
  • 커밋은 지워지지 않았습니다 — reflog(7장)에 남아 있고, 브랜치를 새로 붙이면 살아납니다(16부).
  • 그래서 git checkout <커밋> 은 분리 HEAD 로 들어갈 때 긴 안내문을 찍고(--detach 를 명시한 switch 는 찍지 않습니다 — 앞 장의 캡처), 떠날 때는 어느 쪽이든 "이 커밋들을 두고 간다" 고 알립니다.
설명용

태어나지 않은 브랜치

새 저장소의 main, 또는 switch --orphan 으로 만든 브랜치는 아직 파일이 없습니다.

HEAD 가 아직 없는 파일을 가리키는 상태입니다. 첫 커밋이 그 파일을 만듭니다. 2부 5장의 git status 가 보인 "No commits yet" 가 이 상태였습니다.

실행 검증

3장

짧은 이름 풀기

main 이 refs/heads/main 이 되기까지

여섯 규칙, 먼저 맞는 것

짧은 이름 X 를 받으면 git 은 이 차례로 찾아 처음 있는 것을 씁니다.

  1. .git/X — HEAD · FETCH_HEAD · ORIG_HEAD · MERGE_HEAD 같은 특수 참조
  2. refs/X
  3. refs/tags/X
  4. refs/heads/X
  5. refs/remotes/X
  6. refs/remotes/X/HEAD

태그가 브랜치보다 먼저입니다. 다음 장에서 확인합니다.

문서 근거

태그와 브랜치가 같은 이름이면

refs 실험에서 태그 v1(커밋 B)이 있는데 브랜치 v1(커밋 C)을 하나 더 만들었습니다.

5847278 은 B, 곧 태그입니다. git switch v1 처럼 브랜치 이름이 필요한 자리에서는 브랜치를 쓰지만, 커밋을 받는 자리에서는 태그가 이깁니다. 같은 이름을 만들지 않는 것이 최선입니다.

실행 검증

원격 추적 참조

upstream 실험은 원본 저장소를 복제한 뒤 이름들을 물어봅니다.

그냥 origin 이라고 쓰면 여섯째 규칙으로 refs/remotes/origin/HEAD 가 되고, 그것이 가리키는 origin/main 이 됩니다.

실행 검증

@{u} — 이 브랜치가 따라가는 원격 브랜치

복제는 main 의 upstream 을 origin/main 으로 설정합니다. @{u} (@{upstream})는 그 설정을 읽어 풉니다. git status 의 "앞섰다·뒤졌다" 와 인자 없는 git pull 이 이 설정을 씁니다(12부).

실행 검증

@{-1} — 바로 전에 있던 브랜치

셸의 cd - 처럼 두 브랜치를 오갈 때 씁니다. 이 정보는 HEAD 의 reflog 에서 옵니다 ("checkout: moving from X to Y" 줄을 거슬러 읽습니다).

실행 검증

특수 참조 둘 — FETCH_HEAD · ORIG_HEAD

ORIG_HEAD 는 merge·rebase·reset·am 처럼 HEAD 를 크게 옮기는 명령이 옮기기 직전 위치를 남겨 두는 파일입니다. 방금 한 일을 되돌릴 때 git reset --hard ORIG_HEAD 로 씁니다.

실행 검증

1~3장 퀴즈

Q. 저장소에 태그 release 와 브랜치 release 가 둘 다 있습니다. git log release 는 어느 쪽을 보여 줍니까? 그리고 분리 HEAD 에서 커밋 셋을 만든 뒤 git switch main 하면 그 커밋들은 어디에 있습니까?

A. 태그 쪽입니다 — refs/tags/ 가 refs/heads/ 보다 먼저 찾아지고, git 은 "refname is ambiguous" 경고를 냅니다. 분리 HEAD 의 커밋 셋은 객체 저장소에 그대로 있지만 어느 브랜치도 가리키지 않습니다. HEAD 의 reflog 에 남아 있으니 git branch 살린이름 HEAD@{1} 처럼 이름표를 붙이면 되찾습니다.
설명용

4장

조상과 범위

~ · ^ · .. · ...

실험 역사

이 역사로 표기를 하나씩 풀어 봅니다. 머지 커밋의 첫째 부모는 B(main 쪽), 둘째 부모는 D(side 쪽)입니다.

실행 검증

~ 와 ^ 를 풀면

  • ~n — 첫째 부모를 n 번 따라간다. HEAD~2 = 머지를 지나 B
  • ^n — n 번째 부모로 한 번. HEAD~1^2 = 머지의 둘째 부모 D
  • ^ 는 ^1, ~ 는 ~1 — 그래서 HEAD^ = HEAD~1
  • 이어 붙일 수 있다 — HEAD~1^2~1 = 둘째 부모 D 의 첫째 부모 C
실행 검증

^@ 와 ^!

X^@ 는 X 의 부모 모두, X^! 는 "X 는 넣고 부모들은 뺀" 범위라 X 한 개가 됩니다. 머지 커밋 하나만 골라 볼 때 씁니다.

실행 검증

A..B — B 에서 닿지만 A 에서는 안 닿는 것

2부의 dag 실험 역사(서로를 한 번씩 합친 main 과 side)로 봅니다.

A..B 는 ^A B 의 줄임입니다. "B 쪽에만 있는 커밋" — 머지 전에 무엇이 들어올지, 푸시하면 무엇이 올라갈지 볼 때 씁니다.

실행 검증

A...B — 어느 한쪽에만 있는 것

A...B 는 "A 나 B 에서 닿되, 둘의 공통 조상(merge-base 전부)에서는 닿지 않는" 커밋입니다. diff 에서는 뜻이 다릅니다 — git diff A...B 는 "merge-base 에서 B 까지" 입니다.

실행 검증

범위와 @{u} 를 함께

main..@{u} 는 "받아 오면 들어올 것", 거꾸로 @{u}..main 은 "푸시하면 올라갈 것" 입니다.

실행 검증

5장

packed-refs 와 reftable

참조가 많아지면

파일 수만 개의 문제

태그가 수만 개인 저장소에서 참조마다 파일 하나면 디렉터리가 커지고, 전부 읽는 데 시간이 걸립니다. git pack-refs(gc 가 부른다)는 참조를 파일 하나에 모읍니다.

실행 검증

두 곳에서 읽는다

  • 참조를 찾을 때 git 은 낱 파일을 먼저 보고, 없으면 packed-refs 를 봅니다.
  • 모은 뒤에 브랜치가 움직이면 낱 파일이 다시 생기고, 그것이 packed-refs 의 옛 줄을 가립니다.
  • 머리줄의 peeled 는 주석 태그라면 "벗긴 커밋" 을 ^ 줄로 함께 적는다는 약속입니다 (이 실험의 v1 은 가벼운 태그라 그 줄이 없습니다).
실행 검증

reftable — 참조 저장을 통째로 바꾸기

.ref 파일은 정렬된 이진 표입니다. 참조를 하나 바꿀 때마다 작은 표가 하나 더 쌓이고, tables.list 가 읽을 차례를 적습니다. 가끔 여럿을 하나로 합칩니다.

표 파일 이름의 뒤 여덟 글자는 실행마다 다른 난수라 <조각> 으로 바꿨습니다.

실행 검증

옛 도구가 헷갈리지 않게

.git/HEAD 는 일부러 있을 수 없는 브랜치(.invalid)를 가리키고, refs/heads 는 디렉터리가 아니라 안내문이 든 파일입니다. .git 을 직접 읽던 옛 도구가 틀린 답을 내지 않고 멈추게 하려는 것입니다. 참조는 git 명령으로 읽고 쓴다 — 이 부의 교훈입니다.

실행 검증

있는 저장소를 옮기기

reftable 은 2.45.0 에서 참조 백엔드로 들어왔고, 2026-09 기준 Git 3.0 은 새 저장소의 기본을 reftable 로 바꿀 계획입니다(출시일 미정).

실행 검증

6장

참조를 안전하게 바꾸기

잠금 · 비교 후 교체 · 트랜잭션

.lock 파일

git 은 참조 X 를 바꿀 때 먼저 X.lock 을 새로 만들어야만 합니다. 이미 있으면 다른 git 이 작업 중이라고 보고 멈춥니다. 잠금 파일을 미리 만들어 두고 커밋해 봤습니다.

git 이 도중에 죽어 .lock 이 남는 일도 있습니다. 다른 git 이 정말 돌고 있지 않은지 확인한 뒤에만 지웁니다(16부).

실행 검증

옛 값이 맞을 때만 바꾸기

"읽고 → 계산하고 → 쓰는" 사이에 다른 누군가 참조를 바꿨다면 덮어쓰지 않고 멈춥니다. 스크립트가 참조를 옮길 때 셋째 인자를 주는 습관이 경쟁 조건을 막습니다. git push --force-with-lease 가 같은 생각을 원격에 적용한 것입니다(12부).

실행 검증

여럿을 한꺼번에 — 전부 아니면 전무

x 는 만들 수 있었는데도 생기지 않았습니다. --stdin 으로 준 명령들은 한 트랜잭션입니다.

4~6장 퀴즈

Q. 머지 커밋 M 의 첫째 부모가 P1, 둘째 부모가 P2 입니다. M~2 와 M^2 는 각각 무엇입니까? 그리고 git log main..feature 가 빈 결과라면 무엇을 뜻합니까?

A. M~2 는 첫째 부모를 두 번 — P1 의 첫째 부모입니다. M^2 는 둘째 부모 P2 입니다. main..feature 가 비었다면 feature 에서 닿는 커밋이 모두 main 에서도 닿는다는 뜻 — feature 는 이미 main 에 다 들어가 있습니다(머지해도 새로 들어올 것이 없음).
설명용

7장

reflog

참조가 지나온 길

HEAD 의 reflog

브랜치·원격 추적 참조·HEAD 의 값이 바뀔 때마다 git 은 "옛 값 → 새 값, 누가, 언제, 왜" 를 한 줄 적습니다(태그는 기본으로 적지 않습니다 — core.logAllRefUpdates). HEAD@{n} 은 "n 번 전의 HEAD" 입니다. 브랜치마다 제 reflog 가 따로 있습니다.

실행 검증

그림으로 — HEAD 가 오간 길

A → B → C 로 커밋하고, HEAD~2(A)로 갔다가 main(C)으로 돌아왔습니다. 브랜치 main 의 reflog 에는 뒤의 두 줄이 없습니다 — main 은 움직이지 않았기 때문입니다.

실행 검증

reflog 파일의 한 줄

  • 옛 값 · 새 값 — 첫 커밋이라 옛 값은 0 이 마흔 개
  • 누가·언제 — committer 와 같은 꼴
  • 탭 뒤에 까닭 — commit (initial): A

sed 로 둘째 공백과 탭 자리에서 줄을 나눴습니다. 원래는 한 줄입니다.

실행 검증

main@{1} — 브랜치의 한 걸음 전

main@{1} 은 B, HEAD~1 도 B 입니다. 우연입니다 — ~1 은 부모, @{1} 은 그 참조의 한 걸음 전 값입니다. amend·reset·rebase 뒤에는 둘이 갈라집니다 (2부의 amend 실험에서 HEAD@{1} 은 부모가 아니라 고치기 전의 커밋이었습니다).

실행 검증

브랜치의 reflog

브랜치를 지우면 그 브랜치의 reflog 도 함께 지워집니다. 지운 브랜치의 커밋을 찾을 때는 HEAD 의 reflog 를 봅니다 — 그 브랜치에 있었던 적이 있다면 거기 남아 있습니다(16부).

실행 검증

reflog 도 영원하지 않다

gc 는 오래된 reflog 줄을 스스로 지웁니다. 기본값은 닿는 커밋의 줄은 90일, 닿지 않는 커밋의 줄은 30일입니다(gc.reflogExpire · gc.reflogExpireUnreachable). reflog 는 이 저장소에만 있고 push·clone 으로 건너가지 않습니다.

안 되는 것까닭

9장

참조 고르기

for-each-ref 와 branch 의 거르개

for-each-ref — 참조를 도는 plumbing

%(…) 로 원하는 칸만 골라 찍습니다. %(*objecttype) 의 * 는 "태그를 벗긴 대상" 입니다. 스크립트가 브랜치를 다룰 때는 git branch 출력을 자르지 말고 이것을 씁니다.

실행 검증

--contains · --merged

"이 버그 수정이 어느 브랜치에 들어갔나"(--contains), "지워도 되는 브랜치는"(--merged main) 에 답하는 도구입니다. 둘 다 2부의 "닿는가" 계산입니다.

4부 정리

생각확인한 캡처
참조는 이름 하나가 든 파일refs/heads/main 41바이트 · 브랜치를 만들어도 객체는 0개
HEAD 는 참조를 가리키는 참조ref: refs/heads/main · 분리 HEAD 에서는 커밋 이름이 곧장
짧은 이름은 여섯 규칙으로같은 이름이면 태그가 이긴다 · origin → origin/main
~ 는 첫째 부모, ^n 은 n 번째 부모HEAD~1^2~1 = C
저장은 파일 · packed-refs · reftable어느 것이든 git 명령으로 읽고 쓴다
갱신은 잠금·비교·트랜잭션.lock 이 있으면 멈춤 · 옛 값이 틀리면 멈춤 · 하나 실패면 전부 취소
reflog 는 이 저장소만의 기록@{1} ≠ ~1 · 만료되면 비워진다

7~9장 퀴즈

Q. git reset --hard HEAD~3 을 잘못 쳤습니다. 되돌릴 방법 둘을 드십시오. 그리고 동료의 복제본에서 git reflog 로 내 실수를 찾아 줄 수 있습니까?

A. git reset --hard ORIG_HEAD(reset 이 옮기기 직전 위치를 남겨 둠) 또는 git reset --hard HEAD@{1}(HEAD 의 reflog 에서 한 걸음 전). 동료의 복제본으로는 못 합니다 — reflog 는 각 저장소에만 있고 push·clone 으로 건너가지 않습니다. 다만 그 커밋들을 동료가 받아 간 적이 있다면 동료 저장소에 객체가 있으니 이름으로 되찾을 수 있습니다.
