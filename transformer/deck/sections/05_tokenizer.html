글자를 수로

문자·바이트·UTF-8, 그리고 한글 한 음절의 무게

모델은 정수만 받는다 — 세 가지 자르는 법

4부의 임베딩은 id 로 행을 꺼냅니다. 그러니 글을 먼저 정수 id 의 열로 바꿔야 합니다. 어떤 단위로 자를지가 어휘 크기 V 와 한 줄의 길이 n 을 함께 정합니다.

단위어휘한 줄의 길이문제
글자(코드 포인트)나온 글자 종류만큼 — 한자·기호까지 끝없이짧다학습 때 못 본 글자를 표현할 수 없다
바이트정확히 256한글은 글자의 세 배문맥 길이를 바이트가 다 먹는다
바이트 BPE256 + 병합 수 — 우리가 고른다그 사이병합을 배우는 단계가 하나 더

이 덱은 셋째를 씁니다. 어떤 바이트열도 표현할 수 있으면서(못 보는 글자가 없음), 자주 나오는 덩어리는 토큰 하나로 줄입니다. 합성 과제(덧셈·정렬)는 쓰인 바이트만 담은 문자 어휘를 씁니다(SPEC §5.1).

설명용

UTF-8 — 코드 포인트를 1‥4 바이트로

정의 — UTF-8 부호화
코드 포인트바이트 수비트 모양
U+0000 ‥ U+007F10xxxxxxx
U+0080 ‥ U+07FF2110xxxxx 10xxxxxx
U+0800 ‥ U+FFFF31110xxxx 10xxxxxx 10xxxxxx
U+10000 ‥ U+10FFFF411110xxx 10xxxxxx ×3
  • 첫 바이트의 앞 비트가 길이를 알려 주고, 뒤따르는 바이트는 모두 10 으로 시작합니다.
  • 그래서 바이트열 중간에서 읽기 시작해도 글자 경계를 되찾을 수 있습니다.
  • ASCII 는 1바이트 그대로입니다. 영어 글이 바이트 수 = 글자 수인 까닭입니다.
설명용

한글 음절은 3바이트

한글 완성형 음절은 위 표의 "가"(U+AC00)부터 "힣"(U+D7A3)까지 한 구역에 모여 있고, 모두 3바이트 구간에 듭니다. "한" 을 풀어 보면 코드 포인트의 16비트가 1110·10·10 머리 뒤의 4 + 6 + 6 비트 자리에 나뉘어 들어갑니다.

  • 첫 바이트는 음절 구역 전체에서 EA‥ED 넷뿐입니다(표의 네 음절도 그렇습니다).
  • 그래서 바이트 단위로 보면 한국어 글은 첫 바이트의 종류가 적고, 둘째·셋째 바이트가 음절을 가릅니다 — 3장의 첫 병합들이 이 구조를 그대로 드러냅니다.
실행 검증

말뭉치 — 바이트와 글자

위 표의 마지막 열이 요점입니다. 영어와 합성 과제는 글자 하나가 1바이트이고, 한국어는 글자 하나가 평균 2바이트를 넘습니다. 공백·줄바꿈·문장부호가 1바이트라 3 까지는 가지 않습니다. 같은 바이트 수의 문맥에 한국어는 글자가 훨씬 적게 들어간다는 뜻입니다.

실행 검증

UTF-8 길이별로 세어 보면

한국어 묶음의 3바이트 글자 수가 앞 슬라이드 표(묶음별 크기)의 한글 음절 수보다 조금 많습니다. 음절이 아닌 3바이트 글자 — 줄표 ―, 따옴표 “ ”, 말줄임표 …, 그리고 드물게 한자 — 가 섞여 있기 때문입니다. 2바이트 글자는 드물고, 4바이트 글자(이모지 등)는 없습니다.

한국어 말뭉치의 출처

모두 위키문헌(ko.wikisource.org)에서 받은, 저작권 보호 기간이 끝난 작품입니다. corpus/SOURCES.tsv 가 작품마다 문서 주소, 받은 판의 revision id, 받은 날, 공유 저작물 근거를 적어 둡니다. 누구든 같은 판을 다시 받아 같은 바이트를 얻을 수 있어야 뒤의 모든 숫자가 재현됩니다.

실행 검증

증인 — "한" 은 바이트 셋, 되돌리면 "한"

병합이 하나도 없는 바이트 어휘에서는 토큰 id 가 곧 바이트 값입니다. 한 음절이 id 세 개가 되고, 세 id 를 이어 디코드하면 원래 음절로 돌아옵니다. BPE 는 이 출발점에서 자주 붙어 나오는 짝을 줄여 나가는 일입니다.

사전 토크나이저

병합하기 전에 어디서 자르나 — 부류표와 결정표

왜 먼저 자르나

BPE 를 글 전체에 그대로 돌리면 "다." 나 "의 " 처럼 낱말 끝 + 기호, 낱말 + 공백 이 붙은 토큰이 생깁니다. 같은 "다" 가 문장부호에 따라 다른 토큰이 되어 어휘를 낭비합니다.

  • 그래서 글을 먼저 조각으로 자르고, 병합은 조각 안에서만 일어나게 합니다(SPEC §5.2).
  • BPE 를 단어 분할에 가져온 원 논문도 낱말 경계를 넘는 짝은 세지 않았습니다 .
  • 같은 조각은 몇 번 나와도 한 번만 세고 개수로 가중하면 되므로, 학습도 빨라집니다.
  • 조각을 이어 붙이면 원문이 정확히 나와야 합니다. 자르기는 아무것도 버리지 않습니다.

부류해당 (SPEC §5.2)

WU+0009 ‥ U+000D (탭·줄바꿈 등)
D0 ‥ 9

  • 정규식의 유니코드 속성(\p{L})을 쓰지 않습니다. 파이썬과 C 가 같은 판의 유니코드 표를 가졌다고 믿을 수 없기 때문입니다.

검사 차례가 곧 우선순위입니다. 공백과 줄바꿈류를 먼저 떼고, 숫자, 그다음 ASCII 안에서 영문자인지 기호인지를 가릅니다. ASCII 범위에서 isalpha 는 영문자 52개에만 참이라, C 의 (cp | 32) 비교와 같은 답을 냅니다.

지금 글자조건조각

설명용

tokenizer.pretokenize

부류를 한 번 매겨 두고, i 에서 시작하는 조각의 끝 j 를 찾아 떼어 냅니다. j 는 늘 앞으로만 가므로 시간은 O(글자 수) 입니다. "양보" 규칙은 j -= 1 한 줄입니다.

2장 퀴즈

Q. (1) "한글" 이라는 두 음절 낱말은 바이트 BPE 의 병합이 하나도 없을 때 토큰 몇 개인가요? (2) "나는␣␣␣밥" 을 사전 토크나이저가 자르면 조각은 어떻게 되나요?

A. (1) 한글 음절은 3바이트이므로 6개입니다. (2) "나는" · "␣␣" · "␣밥". 공백 연속이 세 글자이고 뒤가 글자(L)이므로 마지막 공백 하나를 다음 낱말에 양보합니다. 양보된 공백은 결정표 첫 줄에 따라 "밥" 과 한 조각이 됩니다.

BPE 학습

가장 잦은 짝을 합치고, 영향받은 조각만 다시 센다

BPE 는 압축 알고리즘에서 왔다

바이트 짝 부호화(BPE)는 원래 Gage(1994)의 압축 기법입니다 — 열에서 가장 잦은 바이트 짝을 쓰이지 않은 바이트 하나로 바꾸기를 되풀이합니다. Sennrich 외는 이것을 단어 분할에 가져와, 바이트 대신 글자(와 글자 덩어리) 짝을 합쳤습니다 .

  • 병합 하나가 새 기호 하나를 만들고, 최종 어휘 = 처음 어휘 + 병합 수입니다. 병합 수가 유일한 조절 손잡이입니다.
  • 낱말 경계를 넘는 짝은 세지 않고, 낱말 사전에 빈도로 가중해 돌립니다.
  • 실제 구현은 모든 짝에 색인을 달고 자료구조를 조금씩 고쳐 속도를 냈다고 적습니다. 이 덱의 train_bpe 도 같은 생각입니다.

이 덱은 글자가 아니라 바이트에서 출발합니다. 그러면 기본 어휘가 256 으로 고정되고, 어떤 글도 어휘 밖으로 떨어지지 않습니다.

논문 근거

학습 절차 (SPEC §5.3)

BPE 학습
  1. 말뭉치를 조각으로 나누고, 조각(바이트열)마다 개수를 센다.
  2. 모든 조각의 이웃한 두 토큰 짝을 조각 개수로 가중해 센다.
  3. 가장 많은 짝을 고른다. 동률이면 (왼쪽 id, 오른쪽 id) 가 사전순으로 작은 짝. 개수가 2 보다 작으면 멈춘다.
  4. 모든 조각에서 그 짝을 왼쪽부터 겹치지 않게 새 id 로 바꾼다.
  5. 어휘가 목표 크기가 될 때까지 2 로.
  • 순위 r 의 병합이 만드는 토큰 id 는 256 + r 입니다(SPEC §5.1).
  • 개수 1 인 짝은 합쳐도 줄어드는 토큰이 하나뿐이고, 어휘 한 칸을 쓸 가치가 없습니다.
설명용

손으로 따라가는 예 — 동률 깨기

"abab" 와 "␣cdcd" 두 조각에서 짝 (a, b) 와 (c, d) 가 둘 다 두 번입니다. 바이트 값으로 (97, 98) 이 (99, 100) 보다 작으니 먼저 합칩니다. 그다음 (c, d) 가 합쳐지고, 남은 짝은 모두 한 번씩이라 목표 크기에 닿기 전에 멈춥니다.

실행 검증

동률 규칙이 왜 필요한가

실제 말뭉치에서도 개수가 같은 짝은 흔합니다. 규칙이 없으면 "먼저 만난 짝" 이 뽑히는데, 파이썬 dict 의 차례는 넣은 차례이고 C 의 해시표는 해시 값의 차례입니다. 둘이 다른 병합을 배우게 됩니다.

  • 병합 하나가 달라지면 그 뒤 모든 순위의 id 가 밀려, .merges 파일과 토큰 파일 전체가 달라집니다.
  • 규칙은 실행 환경이 아니라 id 값에만 기대야 합니다. 그래서 "(왼쪽, 오른쪽) 사전순" 입니다.
  • 같은 말뭉치로 두 번 학습해 같은 결과가 나오는지도 시험합니다(test_deterministic).

병합을 배우는 일은 파이썬만 합니다. C 는 배운 파일을 읽어 인코드만 합니다(6장). 그래도 규칙이 SPEC 에 박혀 있어야 누구든 같은 파일을 다시 만들 수 있습니다.

설명용

train_bpe (1) — 조각을 세고 짝에 색인을 단다

  • counts — 같은 조각은 한 번만 저장하고 개수를 셉니다. 말뭉치의 조각 수가 아니라 조각 종류 수만큼만 일합니다.
  • pc — 짝마다 조각 개수로 가중한 출현 수입니다.
  • where — 짝마다 그 짝이 든 조각 번호의 집합입니다. 병합할 때 다시 볼 조각을 바로 찾게 해 줍니다.
실행 검증

train_bpe (2) — 고르고, 합치고, 고쳐 센다

  • max 의 열쇠 (개수, −왼쪽, −오른쪽) 가 "개수가 크고, 같으면 id 가 작은" 동률 규칙입니다.
  • 합칠 짝이 든 조각마다 옛 짝을 전부 빼고, 합친 뒤의 짝을 전부 더합니다. 다른 조각은 건드리지 않습니다.
  • sorted(...) — 조각을 번호 차례로 고칩니다. 집합의 차례에 기대지 않으려는 것입니다.
실행 검증

_merge — 왼쪽부터, 겹치지 않게

"aaa" 에서 (a, a) 는 두 번 겹쳐 나옵니다. 왼쪽부터 겹치지 않게 바꾸면 [aa, a] 이지 [a, aa] 가 아닙니다. 이 규칙을 학습과 인코드가 똑같이 따라야 같은 조각이 같은 토큰열이 됩니다.

학습의 비용

조각 종류 수를 U, 조각의 평균 토큰 수를 k, 병합 수를 M, 그 순간 서로 다른 짝의 수를 P 라 합시다.

단계순진한 방법이 구현
처음 짝 세기O(U·k) 한 번
병합마다 다시 세기모든 조각 O(U·k)그 짝이 든 조각의 길이 합만
병합마다 가장 많은 짝 찾기O(P)O(P) — max 가 사전을 훑는다

다시 세기는 where 색인 덕분에 병합된 짝 주변으로 줄었지만, 최댓값 찾기는 여전히 병합마다 모든 짝을 훑습니다. 어휘 512 규모에서는 이것으로 충분합니다. 병합이 수만 개인 어휘라면 짝을 개수 순으로 든 힙 같은 구조가 필요합니다.

where 의 집합은 짝이 조각에서 사라져도 지우지 않습니다. 나중에 그 조각을 다시 보면 옛 짝을 빼고 같은 짝을 더해 그대로이므로 결과는 맞고, 일만 조금 늘어납니다.

설명용

처음 배운 병합 — 한국어와 영어

  • 영어는 처음부터 읽을 수 있는 토큰("␣t", "he", "␣the")이 나옵니다. 글자 하나가 바이트 하나이기 때문입니다.
  • 한국어의 첫 병합들은 <20 ec> 처럼 공백 + 음절의 첫 바이트이거나 <ec 9d> 처럼 음절의 앞 두 바이트입니다. 온전한 음절("다", "이", "는")은 그다음에 나옵니다.
  • <b7 b8> 는 두 바이트가 모두 10 으로 시작하는 뒤따름 바이트 — 음절의 뒤 두 바이트입니다. 여러 음절이 같은 꼬리를 나눠 쓰면 이런 토큰이 이깁니다.
실행 검증

3장 퀴즈

Q. 말뭉치가 "aaaa" 한 조각뿐일 때 train_bpe 는 첫 병합으로 무엇을 배우고, 그 뒤 조각은 어떤 토큰열이 되나요? 두 번째 병합은 일어나나요?

A. 짝 (a, a) 가 세 번(겹쳐서 셉니다) 나오므로 첫 병합은 (97, 97) → 256 입니다. 왼쪽부터 겹치지 않게 바꾸면 "aaaa" 는 [aa, aa] = [256, 256] 입니다. 이제 짝은 (256, 256) 하나가 한 번뿐이라 개수가 2 보다 작아 멈춥니다. 두 번째 병합은 없습니다. ("aaaa" 가 두 번 나오는 말뭉치였다면 개수가 2 가 되어 (256, 256) 도 합쳐집니다.)
설명용

4장

인코드와 디코드

배운 차례대로 다시 합치고, 바이트를 이어 되돌린다

인코드 규칙 — 순위가 낮은 병합부터 (SPEC §5.4)

조각마다: 이웃한 짝 가운데 순위가 가장 낮은(가장 먼저 배운) 병합을 찾아 그 짝의 모든 출현을 왼쪽부터 겹치지 않게 바꿉니다. 적용할 병합이 없을 때까지 되풀이합니다.

  • 왜 순위 차례인가 — 학습은 병합을 배운 차례로 말뭉치에 적용했습니다. 인코드가 같은 차례를 따라야 학습 때 본 토큰열이 다시 나옵니다.
  • 가장 긴 토큰부터 고르면 안 되나 — 그러면 학습 때 한 번도 만들어지지 않은 분할이 나올 수 있고, 모델은 그런 토큰열을 본 적이 없습니다.
  • 같은 조각은 늘 같은 토큰열이 되므로 결과를 기억해 두었다가 다시 씁니다.
설명용

Tokenizer — 순위표와 encode_chunk

  • base — 바이트 값 → 기본 토큰 id. 바이트 어휘에서는 항등이고, 문자 어휘에서는 쓰인 바이트만 있습니다.
  • rank — (왼쪽, 오른쪽) → 순위. 순위 k 의 병합이 만드는 id 는 n_base + k 입니다.
  • 바깥 루프 한 바퀴가 짝을 훑고 병합 하나를 적용하므로, 조각 하나의 비용은 O(길이2) 쯤입니다(바퀴 수 ≤ 길이). 조각이 짧아서 괜찮습니다.
실행 검증

encode 와 decode

디코드는 토큰의 바이트열을 이어 붙이기만 하면 됩니다. 다만 토큰 경계가 UTF-8 글자 한가운데일 수 있으므로, 토큰열의 일부만 디코드하면 깨진 글자가 생깁니다. 그 자리는 � 로 바꿔 보여 줍니다. 생성 중에 한 토큰씩 화면에 찍을 때 이 문제가 실제로 나타납니다(10부).

실행 검증

실제로 인코드해 보면

입력은 한글 13음절과 공백 2개, 곧 13×3 + 2 = 41 바이트입니다. <…> 는 UTF-8 글자의 일부만 담은 토큰을 16진수로 적은 것입니다.

  • 어휘 512 는 한국어 음절을 다 담기에 턱없이 작아, 여러 음절이 "앞 두 바이트 토큰 + 뒤 한 바이트 토큰" 으로 갈립니다.
  • 공백은 사전 토크나이저가 낱말에 붙였으므로 "공백 + 음절 앞부분" 토큰이 생길 수 있습니다.
  • 그래도 되돌린 결과는 입력과 한 바이트도 다르지 않습니다.
실행 검증

증인 — 모든 말뭉치 파일이 되돌아온다

일부러 작은 한국어 조각으로 학습한 어휘로 영어와 과제 파일까지 인코드합니다. 학습 때 못 본 글자가 잔뜩 나오지만 바이트 BPE 에서는 기본 토큰 256 개가 늘 받쳐 주므로 실패하지 않고, 디코드하면 원문과 같습니다.

실행 검증

문자 어휘와 "모르는 바이트는 실패"

덧셈 과제의 어휘는 0‥9 + = ↵ 같은 몇 바이트뿐입니다. 어휘가 작을수록 출력층도 작아 학습이 빨라집니다. 대신 어휘에 없는 바이트를 만나면 조용히 넘기지 않고 실패합니다(SPEC §5.1). 모르는 글자를 버리거나 다른 id 로 바꾸면 정확도 표가 틀린 입력으로 계산되기 때문입니다.

실행 검증

5장

어휘 크기의 트레이드오프

어휘를 키우면 줄은 짧아지고 임베딩은 커진다

무엇과 무엇을 맞바꾸나

어휘 V 를 키우면까닭
임베딩·출력층 파라미터가 V·d 로 늘어난다토큰마다 행 하나(출력층을 묶어도 한 벌)
로짓 계산이 토큰마다 O(V·d)소프트맥스·교차엔트로피가 어휘 전체를 훑는다
같은 글이 더 적은 토큰이 된다문맥 T 에 더 많은 글이 들고, 어텐션 비용 O(n2) 이 준다
드문 토큰이 많아진다한 배치에 안 나오는 행은 기울기 0 — 천천히 배운다(4부 6장)

작은 모델에서는 V·d 가 전체 파라미터의 큰 몫이 되므로 어휘를 작게 잡습니다. 이 덱의 한국어·영어 모델이 어휘 512 를 쓰는 까닭입니다.

설명용

어휘 크기와 토큰 하나가 담는 바이트

  • 어휘 256 은 병합이 없으므로 두 언어 모두 토큰 하나가 정확히 1바이트입니다.
  • 어휘를 늘릴 때마다 토큰이 담는 바이트가 늘지만 병합 하나가 늘리는 폭은 어휘가 클수록 줄어듭니다. 먼저 배운 병합일수록 자주 쓰이기 때문입니다.
  • 한국어 열이 더 크지만, 한국어는 글자 하나가 2바이트를 넘으므로(1장) 글자로 따지면 토큰 하나가 영어보다 적게 담습니다.

학습에 쓴 말뭉치를 그대로 인코드한 값입니다. 처음 보는 글에서는 조금 낮게 나옵니다.

실행 검증

음절 수와 토큰 수

위 캡처에서 토큰 수가 음절 수보다 많습니다 — 토큰에는 공백·기호도 들지만, 무엇보다 어휘 512 가운데 온전한 음절을 담은 토큰이 일부뿐이라 대부분의 음절이 토큰 둘 이상으로 쪼개지기 때문입니다. 한국어는 음절 종류가 많아(1장의 음절 구역 전체) 바이트 BPE 가 음절을 통째로 담으려면 큰 어휘가 필요합니다.

실행 검증

실제 모델들은 어휘를 얼마나 잡았나

  • 원 트랜스포머의 영어-독일어 번역은 원문·번역문이 함께 쓰는 BPE 어휘 약 37000 토큰을 썼습니다 .
  • GPT-1 은 BPE 병합 40,000 개를 썼습니다.
  • GPT-2 는 어휘 50,257 개입니다. 4부 3장의 ln V 표 마지막 행이 이 크기입니다.

수만 단위의 어휘는 d 가 수백·수천인 모델에서야 임베딩이 전체의 작은 몫이 됩니다. 이 덱의 모델은 폭이 작아 같은 어휘를 쓰면 파라미터 대부분이 임베딩이 됩니다.

GPT-1·GPT-2 의 수는 각 논문과 공개 설정 파일에서 확인했습니다(deck/claims.md).

5장 퀴즈

Q. (1) 한국어 어휘 512 로 "만드는" 을 인코드할 때 토큰이 음절 경계에서 갈리지 않는 경우가 있는 까닭은? (2) 폭 d 가 작은 모델에서 어휘를 50,257 로 잡으면 무엇이 문제인가요?

A. (1) 병합은 바이트 짝을 합칠 뿐 글자 경계를 모릅니다. 공백 + 음절 앞 두 바이트처럼 경계를 가로지르는 짝도 자주 나오면 토큰이 되고, 남은 뒤 바이트는 따로 토큰이 됩니다. 사전 토크나이저가 막는 것은 조각(공백+낱말, 숫자, 기호) 경계뿐입니다. (2) 임베딩 V·d 가 전체 파라미터 대부분을 차지하고, 로짓 계산도 토큰마다 V·d 곱셈이 됩니다. 게다가 작은 말뭉치에서는 대부분의 토큰이 드물게 나와 그 행들이 거의 배우지 못합니다.

파일 형식과 C 대조

.vocab 과 .merges — 사람이 읽을 수 있는 두 파일

파일한 줄 (SPEC §5.1)규칙
.vocabid⇥16진 바이트id 는 0 부터 빈틈없이. 한 바이트짜리 줄이 기본 토큰
.merges왼쪽id⇥오른쪽id순위 차례. 순위 r 이 만드는 id 는 기본 토큰 수 + r

바이트를 16진으로 적는 까닭: 토큰이 UTF-8 글자의 일부일 수 있어 글자로는 적을 수 없고, 탭·줄바꿈 바이트도 한 줄에 담아야 하기 때문입니다.

실행 검증

증인 — 저장하고 읽으면 같고, 첫 줄은 예측대로

이 작은 말뭉치에서는 가장 많은 짝들이 모두 두 번씩으로 동률입니다. 그러면 규칙대로 id 가 가장 작은 짝 — 공백(32)과 "한" 의 첫 바이트(0xED = 237) — 이 먼저 합쳐지고, .vocab 의 256 번 줄은 20ed 가 됩니다. 동률 규칙이 파일 내용까지 정한다는 것을 글자로 박아 둔 시험입니다.

실행 검증

.bin — uint16 리틀 엔디언, 머리말 없음

  • id 하나가 2바이트이므로 어휘는 65536 을 넘을 수 없고, 넘는 id 는 쓰기 전에 거부합니다.
  • 머리말이 없어 토큰 수는 파일 크기 ÷ 2 입니다. 학습 코드가 파일을 통째로 읽어 바로 배열로 씁니다.
  • 리틀 엔디언을 SPEC 에 박았으므로 어느 기계에서 만든 파일이든 같은 바이트입니다(SPEC §5.5).
실행 검증

C 의 사전 토크나이저 — UTF-8 을 직접 푼다

  • 첫 루프는 UTF-8 첫 바이트로 길이를 보고 코드 포인트를 조립합니다(1장의 비트 모양). 조각의 경계는 바이트 위치로 돌려줍니다.
  • 둘째 루프는 파이썬 pretokenize 의 세 갈래를 줄마다 옮긴 것입니다. 양보 규칙도 j-- 한 줄입니다.
실행 검증

C 의 순위표 — (왼쪽, 오른쪽) → 순위 해시

파이썬의 dict 대신 크기가 2의 거듭제곱인 배열에 병합 번호를 넣고, 충돌하면 다음 칸으로 갑니다. 표 크기를 병합 수의 두 배 이상으로 잡아(tfs_tok_load) 빈칸이 늘 남으므로 찾기는 반드시 끝나고, 평균 O(1) 입니다. 해시가 무엇이든 답(순위)은 같으니, 여기의 차례는 결과에 영향을 주지 않습니다.

실행 검증

C 의 encode_chunk — 제자리에서 합친다

새 리스트를 만드는 파이썬 _merge 와 달리, 읽는 자리 i 와 쓰는 자리 w 를 따로 두고 같은 배열에 덮어씁니다. w ≤ i 가 늘 성립하므로 아직 안 읽은 칸을 덮지 않습니다. 짝을 찾는 규칙과 왼쪽부터 겹치지 않게 바꾸는 규칙은 파이썬과 같습니다.

실행 검증

C 의 tfs_tok_encode — 조각마다 인코드해 이어 쓴다

모르는 바이트를 만나거나 출력 칸이 모자라면 −1 을 돌려줍니다. 파이썬의 예외에 해당하며, 틀린 토큰 파일을 반쯤 쓰고 넘어가지 않습니다. C 는 조각 결과를 기억해 두지 않습니다 — 조각이 짧고 해시 찾기가 싸서 그렇게 해도 충분합니다.

실행 검증

바이트까지 같은가 — 지문으로 견준다

파이썬은 말뭉치의 모든 파일(한국어 작품, 영어, 합성 과제의 학습·시험 파일)을 인코드해 out/parity_tokens.txt 에 파일마다 한 줄을 적습니다: 파일 이름, 어휘, 바이트 수, 토큰 수, 그리고 .bin 바이트열의 FNV-1a 64비트 지문. 캡처 전체는 이 화면에 들어가지 않을 만큼 깁니다.

허용 오차는 0 입니다(SPEC §9). 토큰이 하나만 달라도 지문이 달라지므로, 파일 전체를 싣지 않고도 "바이트까지 같다" 를 확인할 수 있습니다.

실행 검증

C 시험 — 모든 말뭉치 파일을 다시 인코드

  • 파이썬이 적은 줄을 읽어, 그 줄의 어휘로 C 가 같은 파일을 인코드합니다.
  • 토큰 수가 같고 지문이 같아야 통과합니다. 마지막 CHECK 가 견준 파일 수까지 확인해, 캡처가 잘려도 조용히 통과하지 못하게 합니다.
  • 한국어·영어 파일은 병합 256 개짜리 BPE 어휘로, 과제 파일은 병합 없는 문자 어휘로 인코드됩니다. 두 경로가 모두 시험됩니다.

6장 퀴즈

Q. (1) C 인코더가 병합을 찾을 때 해시표를 쓰는데, 해시 함수를 바꾸면 .bin 이 달라질 수 있나요? (2) 한국어 어휘를 병합 65,300 개로 키우면 .bin 형식에 무슨 일이 생기나요?

A. (1) 아닙니다. 해시표는 (왼쪽, 오른쪽) → 순위라는 같은 답을 빨리 찾는 수단일 뿐이고, 어느 병합을 적용할지는 순위로 정해집니다. 반면 학습에서 동률을 해시 차례로 깼다면 병합 자체가 달라졌을 것입니다 — 그래서 동률 규칙은 id 값으로 정합니다. (2) 어휘가 256 + 65,300 = 65,556 이 되어 uint16 에 담을 수 있는 65,536 을 넘습니다. write_bin 이 쓰기 전에 거부하고, 형식을 바꾸지 않는 한 그 어휘는 쓸 수 없습니다.
