메모리 배치와 float32

파라미터 전부가 배열 하나

파라미터는 float 배열 하나

파이썬은 텐서마다 리스트를 따로 들었습니다. C 는 모든 파라미터를 SPEC §4 체크포인트 차례대로 한 배열에 붙이고, 이름마다 시작 위치(offset)와 크기만 기억합니다.

  • 체크포인트 읽기는 머리말 뒤에서 fread 한 번입니다.
  • 기울기도 같은 모양의 배열 하나라, 0 으로 비우기는 memset 한 번입니다.
  • AdamW 는 배열 하나를 도는 루프 하나입니다(3장).
실행 검증

이름으로 텐서 찾기

커널은 P(l, "Wqkv") 처럼 이름으로 가중치를 집어 옵니다. 같은 함수가 파라미터 배열과 기울기 배열 모두에서 쓰입니다 — 배치가 같기 때문입니다.

실행 검증

왜 float32 인가

값 하나가 4바이트라 double 의 절반입니다. 메모리 대역폭이 곧 속도인 행렬곱에서는 그만큼 캐시에 더 많이 들어갑니다. 대가는 정밀도입니다.

float32 의 상대 간격 ≈ 2−23,   double 의 상대 간격 ≈ 2−52

유효 숫자가 7자리 남짓이라, O(1) 크기의 항을 수천 개 더하면 끝자리가 흔들립니다. 그래서 C 는 원칙을 하나 둡니다.

값은 float32 로 들고, 행 하나의 합은 double 로 쌓는다.
설명용

합만 double 로

소프트맥스의 분모, 레이어놈의 평균·분산, 역전파의 내적이 그런 합입니다. 원소 하나하나의 곱은 float32 로 충분합니다. 파이썬 참조가 math.fsum 으로 정확히 더하는 자리와 같은 자리입니다.

실행 검증

순전파가 남기는 것

C 에는 계산 그래프가 없습니다. 역전파가 다시 읽을 값을 순전파가 직접 배열에 남깁니다.

무엇을 남길지는 4·6부의 역전파 식이 정합니다 — 레이어놈은 x̂ 와 1/σ, 소프트맥스는 p, GELU 는 입력 x, 어텐션은 q·k·v 와 가중치.

실행 검증

활성값의 크기

배치 B, 문맥 T 에서 블록 하나가 남기는 float 수는 대략

(10d + 2dff + 2)·BT + h·B·T²

마지막 항이 어텐션 가중치입니다. 로짓과 확률은 모델 끝에서 V·BT 씩 세 벌(로짓·확률·로짓 기울기)입니다. 어휘가 크면 여기가 가장 큽니다 — 6부 6장에서 본 T² 와 함께 메모리의 두 봉우리입니다.

실행 검증

ijk — 교과서 차례

가장 안쪽 루프가 b[k * p + j] 를 k 를 바꿔 가며 읽습니다. 행 우선 배열에서 k 가 1 늘면 p 칸을 건너뜁니다. 행렬이 캐시보다 크면 거의 매번 캐시를 놓칩니다.

실행 검증

ikj — 한 행을 앞에서부터

a[i][k] 하나를 잡고 b 의 k 행을 bk[0], bk[1], … 차례로 읽습니다. 메모리를 이어서 읽으니 캐시 적중이 높고, 안쪽 루프가 단순한 덧셈의 줄이라 컴파일러가 다루기도 쉽습니다. 파이썬 참조의 tensor.matmul 도 이 차례입니다.

실행 검증

blocked — 조각이 캐시에 들게

세 행렬을 조각으로 나눠, 조각 셋이 한꺼번에 캐시에 들게 합니다. 행렬이 작으면 이득이 없고 루프 머리의 비용만 늡니다.

실행 검증

세 차례의 답은 비트까지 같습니다

(i, j) 칸 하나에 대해 세 판 모두 k 를 작은 것부터 더합니다. 더하는 차례가 같으니 부동소수 결과도 같습니다. 그래서 벤치 표는 "같은 답에 드는 시간" 만 견줍니다.

실행 검증

이 파일(bench.txt)의 두 표만 세 번 돌리면 숫자가 달라집니다. 그래서 tools/record.sh 의 재현 대조에서 빠지고, 이 덱의 산문은 속도 숫자를 옮겨 적지 않습니다. 비교해 볼 것은 세 줄의 순서와 대략의 배수입니다.
실행 검증

표를 읽는 법

  • GFLOP/s 는 초당 10억 FLOP — 곱셈 n³ 번과 덧셈 n³ 번을 2n³ FLOP 로 셉니다(7부 7장).
  • ijk 와 ikj 의 차이는 계산이 아니라 메모리 접근의 차이입니다. 곱셈 수는 셋이 같습니다.
  • blocked 가 ikj 보다 늘 빠른 것은 아닙니다. 384×384 float32 행렬 하나는 약 590 KB 이고, 그것이 캐시의 어느 층에 드느냐는 기계마다 다릅니다.
  • 이 덱의 모델은 행렬이 작아(d = 64) 학습 커널에는 ikj 만 씁니다.

Q. ikj 행렬곱의 안쪽 루프 o[j] += aik * bk[j] 를 컴파일러가 FMA (곱셈과 덧셈을 한 명령으로) 로 바꾸면 무엇이 달라집니까? 이 저장소가 -ffp-contract=off 로 막는 까닭은?

A. FMA 는 aik*bk[j] 를 반올림하지 않은 채로 o[j] 에 더하고 한 번만 반올림합니다. 두 번 반올림하던 결과와 끝자리가 달라집니다. 더 정확할 수도 있지만, 파이썬 참조·다른 기계·다른 컴파일러 설정과 비트까지 맞춰 보는 대조가 무너집니다. SPEC §8 이 "FMA 가 a*b+c 를 한 번에 계산하면 반올림이 달라진다" 며 막는 이유입니다. 세 루프 차례가 비트까지 같다는 시험도 FMA 가 한 판에만 적용되면 깨집니다.

3장 퀴즈

Q. 순전파가 GELU 의 출력만 남기고 입력을 버렸다면, 역전파에서 GELU 의 미분을 계산할 수 있습니까? ReLU 였다면요?

A. GELU 는 어렵습니다. 미분이 x 의 함수(½(1+t) + ½x(1−t²)·A(1+3Bx²))인데, GELU 는 음수 쪽에서 단조가 아니라 출력 하나에 입력이 둘일 수 있어 출력에서 x 를 되찾을 수 없습니다. 그래서 C 는 fc1(GELU 앞의 값)을 남깁니다.
ReLU 는 됩니다. 미분이 "x > 0 이면 1" 이고, 출력이 0 보다 크다는 것과 같은 말이라 출력만으로 충분합니다. 활성함수에 따라 남길 값이 달라지는 한 예입니다.

기울기 — 텐서마다

실행 검증

기준을 한 번 고쳤습니다

처음 SPEC 은 기울기도 칸마다 상대 1e-3 이라 적었습니다. C 모델 시험을 처음 돌리자 기울기 여덟 곳이 걸렸는데, 역전파의 결함이 아니었습니다.

  • 키 편향의 참 기울기는 RoPE 가 아니면 정확히 0 입니다(7부 5장). 파이썬은 반올림 잡음 수준의 0 에 가까운 값, C 는 float32 잡음 수준의 값을 냅니다 — 0 에 견준 상대 오차는 뜻이 없습니다.
  • O(1) 크기의 항 수십 개가 상쇄되어 작아진 칸은 float32 반올림만으로 절대 오차가 생깁니다.

그래서 "상대 1e-3 + 텐서 크기의 1e-5" 로 고쳤습니다. 텐서 크기에만 견주는 기준은 버렸습니다 — 작은 칸이 통째로 틀려도 통과하기 때문입니다.

스레드 정적 분할과 결정론

스레드 수가 달라도 비트까지 같게

그냥 나누면 결과가 흔들립니다

합 Σr xr 을 스레드 둘이 반씩 더한 뒤 합치면 ((x₀+x₁)+x₂)+x₃ 이 아니라 (x₀+x₁)+(x₂+x₃) 가 됩니다. 부동소수 덧셈은 결합법칙이 성립하지 않으므로 끝자리가 달라집니다. 스레드 수를 바꾸면 체크포인트가 달라지고, 재현이 무너집니다.

설명용

규칙 둘

  1. 조각 경계는 n 과 스레드 수로만 정한다: t 번 조각은 [n·t/P, n·(t+1)/P).
  2. 출력 칸 하나는 한 조각에서만, 정해진 차례로 계산한다.

둘째 규칙이 요점입니다. 선형층의 dW 를 가중치 행으로 나누고(3장), 어텐션을 (배치, 헤드) 로 나누는(6부 5장) 까닭이 이것입니다. 칸마다 더하는 차례가 스레드 수와 무관하니 결과가 같습니다.

4~6장 퀴즈

Q. 기울기 자르기 tfs_clip_grad_norm 은 모든 파라미터의 제곱합을 한 줄기로 더합니다. 이 합을 스레드로 나누고 싶다면, 결정론을 지키면서 어떻게 나눌 수 있습니까?

A. 조각마다 부분합을 따로 쌓은 뒤 조각 차례로 합치면 스레드 수가 같을 때는 결정론적이지만, 스레드 수가 바뀌면 조각 경계가 바뀌어 합의 괄호가 달라집니다 — "1 스레드와 N 스레드가 같다" 는 약속이 깨집니다. 약속을 지키려면 경계를 스레드 수와 무관한 고정 크기 블록(예: 텐서마다, 또는 원소 4096 개마다)으로 정하고, 블록 합을 블록 차례로 더해야 합니다. 그러면 1 스레드일 때도 같은 블록 합을 같은 차례로 더하게 됩니다. 이 저장소는 그 복잡함을 피해 한 줄기로 더합니다.
