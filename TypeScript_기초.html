《TypeScript로 만드는 GW-BASIC 인터프리터》는 약 4,000줄의 TypeScript 코드를 읽어 나가는 책입니다. 그런데 그 책은 TypeScript를 이미 안다고 가정하고 시작합니다.

이 덱은 그 빈칸을 메웁니다. 목표는 딱 하나입니다.

목표 — 그 책에 나오는 TypeScript 코드를 막힘없이 읽을 수 있게 만드는 것.

따라서 TypeScript의 모든 것을 다루지 않습니다. 그 책에 실제로 나오는 문법만 골라, 나오는 순서와 비슷하게 배웁니다.

제1부

TypeScript라는 도구

타입이 무엇을 해 주는지, 그리고 그것을 돌리기 위한 준비물

1장

TypeScript란 무엇인가

JavaScript + 타입. 그런데 그 “+”가 생각보다 큽니다.

1.1 JavaScript와의 관계

TypeScript는 JavaScript의 상위 집합(superset)입니다. 문법적으로 올바른 JavaScript는 전부 올바른 TypeScript입니다.

JavaScript⊂TypeScript

따라서 TypeScript를 배운다는 것은 사실상 JavaScript를 배우고 + 타입 표기를 배우는 두 가지 일입니다. 이 덱도 그 둘을 같이 다룹니다.

JavaScript
function add(a, b) {
  return a + b;
}
TypeScript
function add(a: number, b: number): number {
  return a + b;
}

차이는 : number 세 군데뿐입니다. 나머지는 완전히 같은 코드입니다.

1.2 타입은 실행 전에 사라진다

TypeScript 컴파일러 tsc가 하는 일은 두 가지입니다.

  1. 타입 검사 — 코드가 타입 규칙을 어기지 않았는지 확인하고, 어겼으면 에러를 보고한다.
  2. 타입 지우기(type erasure) — 타입 표기를 전부 걷어내고 평범한 JavaScript를 뱉는다.
입력 add.ts
function add(a: number, b: number): number {
  return a + b;
}
const x: number = add(1, 2);
출력 add.js
function add(a, b) {
  return a + b;
}
const x = add(1, 2);
핵심 — 실행 시점에는 타입이 존재하지 않습니다. 타입은 프로그램의 동작을 바꾸지 않고, 오직 컴파일 시점의 검사에만 쓰입니다.

1.3 “타입이 지워진다”가 만드는 결과

이 사실 하나에서 초보자가 겪는 혼란의 절반이 설명됩니다.

못 하는 일if (x is BasicValue) 같은 런타임 타입 검사는 불가능합니다. 그 정보는 이미 사라졌습니다.
대신 하는 일값 안에 tag: "INT" 같은 실제 필드를 넣어 두고 그것을 검사합니다. 그래서 책의 BasicValue에 tag가 있는 것입니다.
또 못 하는 일타입 오류가 있어도 tsc는 기본적으로 JS를 그래도 뱉습니다. 타입 검사는 조언이지 실행 금지가 아닙니다.
거짓말 가능as로 “이건 사실 이 타입이야”라고 우기면 컴파일러는 믿습니다. 틀렸어도 런타임에 가서야 터집니다.

1.4 왜 굳이 타입을 쓰는가

인터프리터처럼 부품이 많고 서로 정확히 맞물려야 하는 프로그램에서 타입의 값어치가 가장 큽니다.

소스 문자열→Token[]→AST→바이트코드→VM 실행

단계마다 데이터 모양이 바뀝니다. 타입이 없으면 “파서가 만든 노드에 line 필드가 있었던가?”를 매번 코드를 뒤져 확인해야 합니다. 타입이 있으면 편집기가 즉시 알려 줍니다.

  • 자동완성 — tok.만 쳐도 필드 목록이 뜬다
  • 리팩터링 안전망 — 필드 이름을 바꾸면 안 고친 곳이 전부 빨간 줄
  • 문서 — interface Host 하나가 “호스트가 제공해야 할 기능 목록” 명세서가 된다
  • 망라성 — 새 AST 노드를 추가하면 처리 안 한 switch가 컴파일 에러를 낸다

1.5 구조적 타이핑 — 이름이 아니라 모양

Java나 C#은 “implements Host라고 선언해야 Host다”라는 명목적(nominal) 타입 체계입니다. TypeScript는 다릅니다.

interface Point { x: number; y: number; }

const a = { x: 1, y: 2 };          // Point라고 말한 적 없음
const b: Point = a;                // ✔ 통과 — 모양이 맞으니까 Point다

const c = { x: 1, y: 2, z: 3 };
const d: Point = c;                // ✔ 통과 — x,y가 있으면 여분은 상관없음
구조적 타이핑 — 타입이 같은지는 이름이 아니라 구조(필드와 그 타입)로 판단합니다.

덕분에 테스트에서 가짜 Host를 만들 때 클래스를 만들 필요 없이 객체 리터럴만 던져도 됩니다. 책의 테스트 코드가 그렇게 합니다.

1.6 타입 검사기가 잡아 주는 것들

아래는 전부 JavaScript에서는 조용히 잘못된 결과를 내고 지나가는 코드입니다.

const n: number = "10";            // ① 타입 불일치
add(1);                            // ② 인자 개수 부족
function g(t: Token) { t.valeu; }  // ③ 오타 난 필드 이름
const s: string | null = find();
s.length;                          // ④ null일 수 있는데 그냥 씀
① TS2322: Type 'string' is not assignable to type 'number'. ② TS2554: Expected 2 arguments, but got 1. ③ TS2551: Property 'valeu' does not exist on type 'Token'. Did you mean 'value'? ④ TS18047: 's' is possibly 'null'.

④번이 특히 큽니다. GW-BASIC 인터프리터 코드에는 “색이 지정되지 않았으면 null” 같은 값이 잔뜩 나오는데, 그 null을 빠뜨리면 컴파일이 안 됩니다.

1.7 버전과 생태계

그 책은 TypeScript 5.4 이상, Node.js 20 이상을 전제합니다. 이 덱의 내용은 5.x는 물론 6.x에서도 그대로 통합니다 — 덱이 인용하는 컴파일러 에러 메시지 11종을 tsc 6.0으로 다시 돌려 전부 같은 문구가 나오는 것을 확인했습니다.

tsc공식 컴파일러. 타입 검사 + JS 출력.
tsx.ts 파일을 컴파일 단계 없이 바로 실행해 주는 도구. 개발 중 빠른 실행용.
esbuild초고속 번들러. 여러 .ts를 하나의 .js로 묶는다. 타입 검사는 하지 않는다.
vitest테스트 러너. ESM과 TypeScript를 그대로 이해한다.
@types/*JS로 짜인 라이브러리에 타입만 따로 붙여 주는 패키지. @types/node가 대표적.
주의 — esbuild와 tsx는 타입을 지우기만 하고 검사하지 않습니다. 검사는 별도로 tsc --noEmit을 돌려야 합니다.

2장

개발 환경 만들기

책 3장과 같은 순서로, 명령 하나하나가 무엇을 하는지 보면서

2.1 Node.js — 브라우저 밖의 JavaScript

JavaScript는 원래 브라우저 안에서만 돌았습니다. Node.js는 그 엔진(V8)을 꺼내 와 명령줄에서 JS를 실행할 수 있게 만든 런타임입니다. 파일 읽기, 표준 입출력 같은 브라우저에 없는 기능이 딸려 옵니다.

$ node --version v20.11.1 $ node -e "console.log(1 + 2)" 3

그 책은 인터프리터를 두 가지 환경에서 돌립니다. 터미널(Node)과 브라우저(Canvas)입니다. 그래서 Host라는 인터페이스로 환경 의존 부분을 분리한 것입니다.

2.2 npm과 package.json

npm은 Node에 딸려 오는 패키지 관리자입니다. package.json은 프로젝트의 신분증이자 의존성 목록입니다.

$ mkdir ts_gwbasic && cd ts_gwbasic $ npm init -y # package.json 생성 $ npm i -D typescript @types/node esbuild vitest tsx
-D--save-dev의 줄임. “개발할 때만 필요하고 배포물에는 안 들어간다”는 표시.
node_modules/실제로 내려받은 패키지가 쌓이는 곳. 절대 git에 넣지 않습니다.
package-lock.json설치된 정확한 버전 기록. 이건 git에 넣습니다.

2.3 package.json 읽는 법

package.json

{
  "name": "ts_gwbasic",
  "type": "module",
  "scripts": {
    "dev": "tsx watch src/main.ts",
    "build": "esbuild src/main.ts --bundle --outfile=dist/dist.js --format=esm",
    "test": "vitest run"
  },
  "devDependencies": {
    "typescript": "^5.4.0"
  }
}
"type": "module" — 이 줄이 프로젝트 전체를 ESM(import/export) 모드로 바꿉니다. 없으면 Node는 옛 방식인 CommonJS(require)로 해석합니다. 책의 코드가 전부 import를 쓰므로 반드시 필요합니다.

scripts에 적은 이름은 npm run dev처럼 부를 수 있습니다. ^5.4.0은 “5.4.0 이상, 6.0.0 미만”을 뜻합니다.

2.4 tsc 돌려 보기

src/main.ts

console.log("GW-BASIC TS bootstrap OK");
$ npx tsc src/main.ts # src/main.js 가 생김 $ node src/main.js GW-BASIC TS bootstrap OK $ npx tsc --noEmit # 검사만, 파일은 안 만듦 $ npx tsx src/main.ts # 컴파일 없이 바로 실행 GW-BASIC TS bootstrap OK

npx는 “node_modules/.bin에 설치된 명령을 찾아 실행”합니다. 전역 설치가 필요 없습니다.

실무 습관 — 개발 중에는 tsx로 빠르게 돌리고, 커밋 전에 tsc --noEmit으로 타입을 전수 검사합니다.

2.5 확장자와 파일 배치

.ts일반 TypeScript 소스. 책의 코드는 전부 이것입니다.
.d.ts타입 선언만 담긴 파일. 코드는 없습니다. @types/node가 이걸로 이뤄져 있습니다.
.tsxJSX(React) 문법이 섞인 TypeScript. 이 책에는 안 나옵니다.
.mts / .cts모듈 방식을 파일 단위로 강제하는 확장자. "type": "module"을 쓰면 필요 없습니다.
$ mkdir -p src/{lexer,parser,ast,compiler,vm,runtime,host} $ mkdir -p tests examples public data

책은 src/ 아래를 인터프리터 단계별로 나눕니다. 이 구조 자체가 “의존 방향은 위에서 아래로만”이라는 설계를 코드 배치로 강제하는 장치입니다.

3장

tsconfig.json 읽는 법

이 파일 한 장이 “TypeScript가 얼마나 엄격할 것인가”를 정합니다

3.1 책이 쓰는 설정 전문

tsconfig.json

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "isolatedModules": true,
    "outDir": "dist",
    "rootDir": "src",
    "lib": ["ES2022", "DOM"]
  },
  "include": ["src", "tests"]
}

이어지는 슬라이드에서 한 줄씩 뜯어봅니다. 지금 전부 이해할 필요는 없고, 나중에 에러를 만났을 때 돌아오면 됩니다.

3.2 target과 lib

target출력 JS를 어느 세대 문법으로 낮출지. ES2022면 class 필드, #private, ??, ?.를 그대로 둡니다. (arr.at() 같은 메서드가 존재하는지는 target이 아니라 lib이 정합니다.)
lib“이 환경에 어떤 내장 API가 존재한다고 믿을지”. DOM을 넣어야 document, CanvasRenderingContext2D가 타입으로 존재합니다.

책은 브라우저 호스트(CanvasHost)를 만들기 때문에 DOM이 필요합니다. 순수 Node 프로젝트라면 ["ES2022"]만으로 충분합니다.

흔한 착각 — lib에 DOM을 넣는다고 Node에서 document가 생기지는 않습니다. 타입 검사기에게 “있다고 치자”고 말할 뿐이고, 실행 시에는 없으면 그냥 터집니다.

3.3 module / moduleResolution

module: "ESNext"출력 코드가 import/export를 그대로 쓰는 ESM이 되게 합니다.
moduleResolution: "Bundler"번들러(esbuild, Vite)가 하는 방식대로 import "./lexer"의 실제 파일을 찾습니다. 즉 확장자를 안 써도 됩니다.
함정 — moduleResolution이 "NodeNext"면 ESM 규칙상 import "./lexer.js"처럼 .ts가 아니라 .js 확장자를 붙여야 합니다. 원본은 .ts인데 .js라고 쓰는 이 기묘함이 TypeScript 초심자를 가장 많이 당황하게 합니다.
Bundler — 둘 다 허용
import { lex } from "./lexer/lexer";
import { lex } from "./lexer/lexer.js";
NodeNext — .js 필수
import { lex } from "./lexer/lexer.js";
책의 소스는 .js를 붙입니다 — import { Token } from "./token.js"; 처럼요. Bundler 설정에서는 필수가 아니지만, 붙여 두면 나중에 NodeNext로 옮기거나 tsc 출력물을 Node로 바로 돌릴 때 고칠 곳이 없습니다.

3.4 strict: true가 켜는 것들

strict는 단일 옵션이 아니라 여러 옵션의 묶음입니다. 이 덱의 모든 예제는 strict가 켜진 상태를 가정합니다.

strictNullChecksnull/undefined를 별도 타입으로 취급. 가장 중요합니다.
noImplicitAny타입을 못 알아낸 자리에 몰래 any를 넣지 않고 에러를 냅니다.
strictFunctionTypes함수 타입 대입의 매개변수 방향을 엄격히 검사.
strictPropertyInitialization클래스 필드가 생성자에서 반드시 초기화되게 강제.
strictBindCallApplyfn.call(...)의 인자 타입도 검사.
useUnknownInCatchVariablescatch (e)의 e가 any가 아니라 unknown이 됩니다.

비유 — const는 “이 상자에 붙은 이름표를 떼서 다른 상자에 붙이지 마라”이지 “상자 안을 건드리지 마라”가 아닙니다.

false, 0, "", null, undefined, NaN

4.6 ==와 ===

==는 타입이 다르면 한쪽을 변환한 뒤 비교합니다. 규칙이 복잡하고 직관에 어긋납니다.

5.1 number의 실체

JavaScript의 number는 전부 IEEE 754 배정도 부동소수점(64비트)입니다. 정수도 실수도 같은 그릇에 담깁니다.

+

5.2 GW-BASIC의 세 가지 수 타입

BASIC 타입접미사원래 표현TS에서 흉내내는 법

즉 책의 코드는 “number 하나로 세 가지를 흉내내되, 어느 타입이었는지는 tag 필드에 따로 적어 둔다”는 전략을 씁니다.

export const SNG = (v: number): BasicValue => ({ tag: "SNG", v: Math.fround(v) });
export const DBL = (v: number): BasicValue => ({ tag: "DBL", v });

5.3 비트 연산과 | 0 관용구

JavaScript의 비트 연산자는 피연산자를 먼저 32비트 부호 있는 정수로 변환합니다. 이 성질을 이용한 것이 | 0 관용구입니다.

3.7 | 0        // 3      ← 소수부 버림 (0 방향으로)
-3.7 | 0       // -3
"42" | 0       // 42
(2 ** 31) | 0  // -2147483648   ← 32비트로 잘림!
& | ^ ~AND, OR, XOR, NOT
<< >>왼쪽/오른쪽 시프트 (부호 유지)
>>>부호 없는 오른쪽 시프트
더 명확한 대안 — Math.trunc(v)는 32비트 제한 없이 소수부만 버립니다. 책이 | 0을 쓰는 이유는 GW-BASIC 정수가 어차피 16비트라 잘림이 오히려 자연스럽기 때문입니다.

5.4 Math.fround — 단정도 흉내내기

Math.fround(x)는 x를 32비트 float로 변환했다가 다시 double로 되돌립니다. 결과는 “32비트로 표현 가능한 가장 가까운 값”입니다.

SNG vs DBL 정밀도

그 책이 드는 예가 이것입니다 — Math.fround(1/3)은 0.3333333432674408이 됩니다(1/3의 배정도 값 0.3333333333333333과 일곱째 자리부터 어긋납니다). 단정도 변수 A!에 넣은 값이 배정도와 미세하게 달라지는 것을 이렇게 재현합니다.

5.5 나눗셈과 나머지

7 / 2            // 3.5      — 항상 실수 나눗셈
Math.floor(7/2)  // 3        — 내림
Math.trunc(-7/2) // -3       — 0 방향 버림
7 % 2            // 1        — 나머지
-7 % 2           // -1       ← 부호가 왼쪽 피연산자를 따른다
주의 — %는 수학의 modulo가 아니라 나머지(remainder)입니다. 결과의 부호가 왼쪽 피연산자를 따르므로 음수에서 Python의 %와 다릅니다. GW-BASIC의 MOD도 부호가 피제수를 따르므로 이 점은 JavaScript와 같습니다.

책은 \(정수 나눗셈)와 MOD를 피연산자를 먼저 32비트 정수로 자른 뒤 계산합니다.

function mid(s: string, i: number, n: number): string {
  if (i < 1 || n < 0) throw new BasicError(ERR.ILLEGAL_FUNCTION_CALL, "MID$");

}

6.6 한 글자씩 훑기 — Lexer의 심장

Lexer는 소스 문자열을 왼쪽에서 오른쪽으로 딱 한 번 훑습니다. 전형적인 모양은 이렇습니다.

class Lexer {
  private i = 0;                        // 현재 위치
  constructor(private src: string) {}

  private peek(): string { return this.src[this.i] ?? ""; }
  private next(): string { return this.src[this.i++] ?? ""; }
  private eof(): boolean { return this.i >= this.src.length; }
}
  • peek() — 보기만 하고 위치는 그대로 (미리보기)
  • next() — 보고 나서 위치를 하나 전진 (소비)
  • ?? "" — 범위를 넘으면 undefined가 나오므로 빈 문자열로 바꿔 준다 (9장)
this.src[this.i++]의 i++는 “현재 값을 쓰고 나서 1 증가”입니다. ++i는 “증가시킨 뒤 그 값을 쓴다”로 순서가 다릅니다.

6.7 정규식 최소한만

책은 정규식을 문자 분류에만 가볍게 씁니다.

/[A-Za-z]/.test(c)     // 영문자인가
/^[0-9]{1,5}$/.test(s) // 전체가 1~5자리 숫자인가
^ $문자열의 시작 / 끝

\d \w \s숫자 / 단어 문자 / 공백
* + ?0회 이상 / 1회 이상 / 0 또는 1회

7.2 기본 연산

a[99]                 // undefined  (noUncheckedIndexedAccess면 타입에도 반영)

7.3 배열은 참조다

얕은 복사 — 배열 껍데기만 새로 만듭니다. 안에 든 객체는 여전히 공유됩니다. AST 노드 배열을 복사해도 노드 자체는 같은 것을 가리킵니다.

7.4 크기를 정해 두고 만들기

7.5 튜플 — 길이와 자리별 타입이 정해진 배열

const p: Pos = [10, 20];

런타임에는 그냥 배열입니다. 튜플은 순전히 타입 수준의 약속입니다.

어디에 쓰나 — 함수가 값 두 개를 돌려줄 때, 좌표를 다룰 때, Object.entries()의 결과를 받을 때. 셋 이상이면 객체로 이름을 붙이는 편이 읽기 좋습니다.

7.6 readonly 배열

객체 타입

토큰 하나, AST 노드 하나 — 전부 객체입니다

8.1 객체 리터럴과 그 타입

const tok = { type: "NUMBER", value: "10", line: 1, col: 1 };
// 추론된 타입: { type: string; value: string; line: number; col: number }

타입을 직접 적을 수도 있습니다. 세미콜론과 쉼표 둘 다 구분자로 쓸 수 있습니다.

축약 표기 — 변수 이름과 키 이름이 같으면 { line, col }으로 줄여 씁니다. 책 코드에 아주 많이 나옵니다.
const line = 1, col = 5;
const p = { line, col };     // { line: 1, col: 5 }

8.2 옵셔널 필드 ?

interface Token {
  type: TokenType;
  value: string;
  line: number;
  col: number;
  num?: number;        // 숫자 토큰일 때만 존재
}

const t: Token = { type: "OP", value: "+", line: 1, col: 3 };  // ✔ num 없어도 됨
t.num;                 // 타입: number | undefined
t.num.toFixed(2);      // ✘ 'possibly undefined'
num?: number의 진짜 뜻 — “필드가 없거나, 있으면 number”. 즉 읽었을 때 타입은 number | undefined가 됩니다. 그래서 쓰기 전에 반드시 확인해야 합니다.
if (t.num !== undefined) t.num.toFixed(2);   // ✔ 좁혀졌다
const n = t.num ?? 0;                        // ✔ 기본값

8.3 readonly 필드

interface ForRecord {
  readonly varName: string;
  readonly end: number;
  readonly step: number;
  readonly loopEnd: number;   // 종료 시 점프할 PC

8.4 초과 프로퍼티 검사

1장에서 “여분의 필드가 있어도 통과한다”고 했는데, 객체 리터럴을 곧바로 대입할 때만은 예외적으로 막습니다.

오타를 잡으려는 안전장치입니다. { collor: 1 }처럼 잘못 쓴 옵셔널 필드를 이 검사가 잡아 줍니다.

8.5 인덱스 시그니처와 Record

키 목록이 미리 정해지지 않은 “사전” 모양의 객체입니다.

}

const vars: VarTable = {};
vars["A%"] = INT(1);
vars["B$"] = STR("hi");

// 같은 뜻, 더 짧은 표기
const vars2: Record<string, BasicValue> = {};

const errs = { SYNTAX: 2, OVERFLOW: 6 };

Object.keys(errs);     // ["SYNTAX", "OVERFLOW"]   — string[]
Object.values(errs);   // [2, 6]                   — number[]
Object.entries(errs);  // [["SYNTAX", 2], ["OVERFLOW", 6]]

delete는 strict에서 막힙니다 — 옵셔널(?)로 선언된 필드에만 쓸 수 있습니다. 애초에 필드를 지우는 설계가 성능·타입 양쪽으로 손해이므로, 넣었다 뺐다 해야 하는 자료구조라면 Map을 쓰세요.

9장

null과 undefined

TypeScript를 쓰는 이유의 절반이 여기 있습니다

9.1 둘의 차이

undefined“아직 값이 없다”. 초기화 안 된 변수, 없는 필드, 반환값 없는 함수의 결과, 범위 밖 배열 접근. 기계가 만들어 낸다.
null“의도적으로 비었다”. 사람이 명시적으로 넣는다.
let a;              // undefined
const b = null;     // null
[1,2][5]            // undefined
function f() {}
f()                 // undefined
책의 관례 — “인자가 생략됨”은 null로 나타냅니다. COLOR , 3처럼 앞 인자를 비운 경우가 setColor(null, 3)이 됩니다. 이 구분이 없으면 “검정(0번)”과 “지정 안 함”을 구별할 수 없습니다.
setColor(fg: number | null, bg: number | null): void;

9.2 strictNullChecks가 바꾸는 세상

꺼짐
const s: string = null;   // ✔ 통과
s.length;                 // ✔ 통과 → 런타임 폭발
켜짐 (책의 설정)
const s: string = null;   // ✘ TS2322
const t: string | null = null;  // ✔
t.length;                 // ✘ TS18047
핵심 — null이 될 수 있다면 타입에 그렇게 적어야 하고, 쓰기 전에 확인해야 합니다. 이 두 가지가 강제되는 순간 “undefined is not a function” 부류의 런타임 에러가 거의 사라집니다.

9.3 확인하면 타입이 좁아진다

function label(s: string | null): string {
  if (s === null) return "(없음)";
  //  ↓ 여기서부터 s의 타입은 string
  return s.toUpperCase();
}

이것을 좁히기(narrowing)라고 부릅니다. TypeScript는 if, return, throw의 흐름을 따라가며 각 지점에서 변수가 어떤 타입일 수 있는지 추적합니다. 18장에서 자세히 다룹니다.

// 이른 반환(early return)으로 계단을 없애는 것이 관례
function process(t: Token | null): void {
  if (!t) return;
  if (t.type !== "NUMBER") return;
  // 여기서 t는 확실히 NUMBER 토큰
}

9.4 ?? — 널 병합 연산자

const c = this.src[this.i] ?? "";        // 범위 밖이면 ""
const color = given ?? defaultColor;
const step = ins.a ?? 1;
a ?? b는 a가 null이거나 undefined일 때만 b를 씁니다.
|| — 위험
0 || 10        // 10  ← 0이 삼켜진다
"" || "x"      // "x"
null || 10     // 10
?? — 안전
0 ?? 10        // 0   ← 0을 지켜 준다
"" ?? "x"      // ""
null ?? 10     // 10
|| vs ??

“컬럼 0”, “색 0번”, “빈 문자열”이 정상 값인 인터프리터에서는 ||가 버그의 원천입니다.

9.5 ?. — 옵셔널 체이닝

const n = node?.pos?.line;      // node나 pos가 null/undefined면 전체가 undefined
host.onError?.(msg);            // 함수가 있으면 호출, 없으면 아무 일 없음
arr?.[0];                       // 배열 인덱싱 버전
// 이것과 같은 뜻
const n = (node === null || node === undefined) ? undefined
        : (node.pos === null || node.pos === undefined) ? undefined
        : node.pos.line;
남용 금지 — a?.b?.c?.d가 늘어선 코드는 “여기 뭐가 null일 수 있는지 나도 모르겠다”는 신호입니다. 타입을 정확히 좁히는 편이 낫습니다. 책에서 ?.는 진짜 선택적인 콜백 호출에 주로 쓰입니다.

9.6 ! — 널 아님 단언

const line = this.lineMap.get(target)!;   // "없을 리 없다"고 컴파일러에 우기기
const el = document.getElementById("screen")!;
!는 검사가 아니라 침묵입니다. 런타임에 아무것도 하지 않습니다. 틀리면 그 자리에서 Cannot read properties of undefined가 납니다.

그래도 쓰는 이유는, 사람은 아는데 컴파일러는 증명할 수 없는 경우가 있기 때문입니다.

// 앞에서 has()로 확인했지만 컴파일러는 get()과 연결짓지 못한다
if (!this.lineMap.has(target)) throw new BasicError(ERR.UNDEFINED_LINE_NUMBER, "...");
const pc = this.lineMap.get(target)!;

// 더 나은 형태 — 한 번만 조회하고 그 결과를 좁힌다
const pc2 = this.lineMap.get(target);
if (pc2 === undefined) throw new BasicError(ERR.UNDEFINED_LINE_NUMBER, "...");
// 여기서 pc2는 number

9.7 정리 — 널 다루기 4단 선택지

상황쓸 것
없으면 기본값을 쓰고 계속 진행??
없으면 아무 일도 하지 않고 넘어감?.
없으면 에러이므로 즉시 중단if (x == null) throw ...
없을 리 없다고 확신 (최후의 수단)!

Q. const col = tok.col || 1; — tok.col이 number | undefined일 때 무엇이 잘못됐나?

컬럼 값이 0일 때도 1로 바뀝니다. 0은 falsy라 ||가 삼켜 버립니다. “값이 없을 때만 기본값”을 뜻하려면 tok.col ?? 1이어야 합니다.

참고로 const c = src[i] || "";처럼 문자열 한 글자를 다룰 때는 ||와 ??의 결과가 같습니다 — 한 글자짜리 문자열은 절대 falsy가 아니기 때문입니다. 그래도 의도가 “널일 때만”이라면 ??를 쓰는 편이 안전합니다.

10장

any, unknown, never, void

특별한 네 타입. 각각 정반대의 역할을 합니다

10.1 any — 검사 포기

let x: any = 1;
x = "hello";
x.whatever.deeply.nested();   // ✔ 전부 통과. 아무것도 검사하지 않는다
const n: number = x;          // ✔ 통과 — 어디로든 흘러 들어간다
any는 전염됩니다. any 값이 흘러 들어간 변수는 사실상 검사에서 벗어납니다. 타입 안전성이 한 군데서 뚫리면 그 아래 전체가 무방비가 됩니다.

noImplicitAny가 켜져 있으면 “타입을 못 알아냈다”는 이유로 몰래 any가 되는 일은 없습니다. 오직 손으로 적었을 때만 any가 됩니다.

언제 쓰나 — 기존 JS 코드를 급히 옮길 때의 임시 방편. 새로 짜는 코드에는 거의 쓸 일이 없습니다. 책의 4,000줄 중 any는 손에 꼽습니다.

10.2 unknown — 안전한 any

let x: unknown = JSON.parse(text);

x.foo;                    // ✘ TS18046: 'x' is of type 'unknown'
const n: number = x;      // ✘ 대입도 안 된다

  const n2: number = x;   // ✔ 확인했으니 통과
}
차이 — any는 “뭘 해도 된다”, unknown은 “확인하기 전엔 아무것도 못 한다”. 외부에서 들어온 정체불명의 값에는 unknown을 씁니다.
try {
  vm.run();
} catch (e) {              // strict에서 e는 unknown
  if (e instanceof BasicError) console.log(e.code);
  else if (e instanceof Error) console.log(e.message);
  else console.log(String(e));
}

catch의 변수가 unknown인 이유는, JavaScript에서는 아무거나 던질 수 있기 때문입니다. throw 42도 합법입니다.

10.3 never — 값이 존재할 수 없음

// ① 절대 정상 반환하지 않는 함수
private err(msg: string): never {
  throw new BasicError(ERR.SYNTAX, `${msg} at line ${this.line}`);
}

// ② 도달할 수 없는 코드 표시
function f(x: string | number) {
  if (typeof x === "string") return 1;
  if (typeof x === "number") return 2;
  const impossible: never = x;   // ✔ x는 여기서 never
  return impossible;
}

never는 “가능한 값이 하나도 없는 타입”입니다. 어떤 값도 never에 대입할 수 없으므로, “여기 도달했다면 무언가 빠뜨린 것”을 컴파일러에게 검사시키는 도구가 됩니다(19장 망라성 검사).

err(): never로 선언하면 if (bad) this.err("...") 뒤의 코드에서 타입이 제대로 좁혀집니다. 반환 타입이 void였다면 컴파일러는 그 함수가 흐름을 끊는다는 사실을 모릅니다.

10.4 void — 반환값을 쓰지 않음

printAt(s: string): void;
cls(mode: number): void;

function log(m: string): void {
  console.log(m);
  // return;        ✔ 허용
  // return undefined;  ✔ 허용
  // return 1;      ✘ 에러
}
void“반환값이 있어도 쓰지 마라”. 콜백 자리에서는 아무 값이나 반환해도 받아 줍니다.
undefined“정확히 undefined를 반환한다”. 더 엄격합니다.
never“반환 자체를 하지 않는다”. 항상 던지거나 무한 루프.
const cb: () => void = () => 42;   // ✔ 통과 — void는 반환값을 무시한다
arr.forEach(x => list.push(x));    // push는 number를 반환하지만 문제없음

11.1 리터럴 타입

타입 자리에 값 하나를 쓸 수 있습니다.

let a: "PRINT" = "PRINT";
a = "INPUT";        // ✘ TS2322: Type '"INPUT"' is not assignable to type '"PRINT"'

type BasicType = "INT" | "SNG" | "DBL" | "STR";
type Mode = "B" | "BF" | null;
문자열 리터럴 유니언은 enum의 자리를 대신합니다. 값이 그냥 문자열이라 디버깅할 때 그대로 보이고, JSON으로 오갈 때도 변환이 필요 없습니다. 책이 enum 대신 이 방식을 쓰는 이유입니다.
// LINE 문의 박스 모드: LINE (x1,y1)-(x2,y2), c, B  또는  BF
mode: "B" | "BF" | null;   // B=사각 테두리, BF=채운 사각형, null=직선

11.2 const와 let의 추론이 다르다

const a = "PRINT";   // 타입: "PRINT"   (리터럴 그대로)
let   b = "PRINT";   // 타입: string    (넓혀짐 = widening)

let은 나중에 다른 문자열이 들어올 수 있으니 string으로 넓힙니다. const는 바뀔 수 없으니 그대로 둡니다.

function setMode(m: "B" | "BF") { /* ... */ }

const m1 = "B";
setMode(m1);        // ✔ m1의 타입이 "B"

let m2 = "B";
setMode(m2);        // ✘ m2의 타입은 string
객체 안에서는 항상 넓혀집니다. const o = { mode: "B" }에서 o.mode의 타입은 string입니다. o.mode = "X"가 가능하기 때문입니다. 이걸 막는 것이 as const입니다.

11.3 as const

const o1 = { mode: "B" };            // { mode: string }
const o2 = { mode: "B" } as const;   // { readonly mode: "B" }

const a1 = [1, 2, 3];                // number[]
const a2 = [1, 2, 3] as const;       // readonly [1, 2, 3]  ← 튜플이 된다

as const는 “이 리터럴 안의 모든 것을 가능한 한 좁게, 그리고 readonly로 읽어라”는 지시입니다.

export const ERR = {
  SYNTAX: 2,
  OVERFLOW: 6,
  DIVISION_BY_ZERO: 11,
} as const;

ERR.SYNTAX;          // 타입: 2      (as const 없으면 number)
ERR.SYNTAX = 3;      // ✘ read-only
왜 책이 enum 대신 이걸 쓰나 — enum은 컴파일 후에도 객체가 남아 “타입이 지워진다”는 원칙을 깹니다. isolatedModules와도 궁합이 나쁩니다. as const 객체는 그냥 평범한 객체이고, 타입은 리터럴로 정확히 잡힙니다.

11.4 as const 객체에서 타입 뽑아내기

export const OP = { PUSH_NUM: 0, ADD: 1, PRINT: 2 } as const;

type OpName = keyof typeof OP;         // "PUSH_NUM" | "ADD" | "PRINT"
type OpCode = (typeof OP)[OpName];     // 0 | 1 | 2
값 OP→ typeof →타입 {PUSH_NUM:0,…}→ keyof →"PUSH_NUM"|…
이 OP 테이블은 설명을 위한 예시입니다. 책은 명령어를 숫자 코드가 아니라 문자열 판별 유니언({ op: "PUSH"; value: BasicValue } | { op: "ADD" } | …)으로 정의합니다 — 17장에서 봅니다.

typeof가 두 가지 뜻으로 쓰이는 점에 주의하세요.

값 자리typeof x === "string" — 런타임 검사, 결과는 문자열
타입 자리type T = typeof OP — 컴파일 시점, “그 값의 타입”을 가져옴

11.5 타입 단언 as

const el = document.getElementById("screen") as HTMLCanvasElement;
const raw = JSON.parse(text) as Config;
as는 변환이 아닙니다. 아무 코드도 만들어 내지 않습니다. 그냥 컴파일러에게 “내 말을 믿어라”라고 말하는 것뿐입니다. 틀리면 런타임에 터집니다.
const n = "42" as unknown as number;   // 컴파일 통과, 런타임엔 여전히 문자열
n.toFixed(2);                          // 💥 n.toFixed is not a function

바로 "42" as number는 “겹치는 부분이 없다”며 거절당합니다. 그래서 as unknown as라는 우회로를 쓰는데, 이건 거의 항상 설계가 잘못됐다는 신호입니다.

대안 — 진짜 검사가 필요하면 as 대신 타입 가드(18장)를 쓰세요. 런타임에 실제로 확인하고, 타입도 좁혀집니다.

11.6 satisfies — 검사는 하되 좁힘은 유지

// as: 타입이 넓어져 버린다
const a = { PUSH: 0, ADD: 1 } as Record<string, number>;
a.PUSH;   // number, 그런데 a.OOPS도 통과해 버린다

// satisfies: Record 규칙을 만족하는지 검사하되, 추론된 좁은 타입을 유지
const b = { PUSH: 0, ADD: 1 } satisfies Record<string, number>;
b.PUSH;   // number
b.OOPS;   // ✘ 에러 — 좁은 타입이 살아 있다

TypeScript 4.9에 들어온 연산자입니다. 책에는 나오지 않지만, as를 쓰고 싶어질 때 대부분 satisfies가 정답이므로 알아 둘 값어치가 있습니다.

12.1 세 가지 만드는 법

// ① 함수 선언문 — 호이스팅된다(정의보다 위에서 호출 가능)
function lex(src: string): Token[] {
  return new Lexer(src).run();
}

// ② 함수 표현식
const lex2 = function (src: string): Token[] { return []; };

// ③ 화살표 함수 — 가장 많이 쓴다
const lex3 = (src: string): Token[] => [];

책은 모듈 최상위 함수에 ①을, 콜백과 짧은 헬퍼에 ③을 씁니다. ②는 거의 쓰지 않습니다.

호이스팅 — function f(){}는 파일 전체에서 미리 보입니다. const f = () => {}는 그 줄에 도달해야 존재합니다. 상호 재귀하는 파서 함수들(parseExpr ↔ parsePrimary)에는 ①이 편합니다.

12.2 매개변수 — 개수가 정확해야 한다

// 기본값 — 옵셔널이면서 값까지 준다
function pad(s: string, n: number, c: string = " "): string {
  return s.padStart(n, c);
}
col?: number의 타입은 number | undefined입니다. 기본값이 있는 c: string = " "는 함수 안에서는 그냥 string입니다.

12.4 반환 타입

function add(a: number, b: number): number { return a + b; }
function log(m: string): void { console.log(m); }
function fail(m: string): never { throw new Error(m); }
function find(k: string): Token | null { return null; }

적지 않으면 추론됩니다. 그래도 공개 함수에는 적기를 권합니다. 이유는 두 가지입니다.

  • 구현을 고치다 반환 타입이 슬쩍 바뀌면 호출부가 아니라 그 함수에서 에러가 납니다. 원인 위치가 정확해집니다.
  • 재귀 함수는 반환 타입을 적지 않으면 추론이 실패할 수 있습니다.
// 반환 타입을 적어야 하는 전형적인 경우 (자기 자신을 다시 부른다)
function parseExpr(minPrec: number): Expr {
  let left = parsePrimary();
  while (prec(peek()) >= minPrec) {
    const op = next().value;
    const rhs = parseExpr(prec(op) + 1);
    left = { kind: "Binary", op, lhs: left, rhs };
  }
  return left;
}

13.2 this가 사라지는 문제

class VM {

  runAll(list: number[]) {
    list.forEach(function (x) {
      this.sp += x;        // 💥 this가 undefined
    });

    list.forEach((x) => {
      this.sp += x;        // ✔ 화살표는 바깥 this를 그대로 쓴다

규칙 — function의 this는 호출 방식에 따라 정해집니다. 화살표 함수는 this를 가지지 않고 정의된 자리의 this를 그대로 씁니다.
다행히 컴파일러가 먼저 잡습니다 — strict에 포함된 noImplicitThis 덕분에 위쪽 function 버전은 실행되기도 전에 걸립니다.

그래서 클래스 안에서 콜백을 넘길 때는 거의 항상 화살표 함수를 씁니다.

public onBeforeInstruction:
  ((pc: number, op: Op) => Promise<void> | void) | null = null;

async run(): Promise<void> {
  while (!this.halted && this.pc < this.program.code.length) {
    const ins = this.program.code[this.pc++]!;
    await this.onBeforeInstruction?.(this.pc - 1, ins);
    await this.dispatch(ins);
  }
}
타입 읽는 법 — ((pc: number, op: Op) => Promise<void> | void) | null
바깥 | null은 “훅이 없을 수도 있다”, 안쪽 Promise<void> | void는 “동기 함수를 꽂아도 되고 async 함수를 꽂아도 된다”는 뜻입니다. await는 Promise가 아닌 값에도 그냥 통과하므로 양쪽 다 동작합니다.

this.onBeforeInstruction?.(...)는 “훅이 있으면 호출, 없으면 아무 일 없음”입니다.

14.4 함수를 돌려주는 함수

// 이항 연산자 하나를 처리하는 함수를 만들어 내는 공장
function binOp(f: (a: number, b: number) => number) {
  return (l: BasicValue, r: BasicValue): BasicValue =>
    DBL(f(toNum(l), toNum(r)));
}

const addOp = binOp((a, b) => a + b);
const mulOp = binOp((a, b) => a * b);

const TABLE: Record<string, (l: BasicValue, r: BasicValue) => BasicValue> = {
  "+": addOp,
  "*": mulOp,
};
클로저 — 안쪽 화살표 함수가 바깥 매개변수 f를 계속 기억합니다. 이렇게 “환경을 붙들고 있는 함수”를 클로저라고 부릅니다. 인터프리터에서 DEF FN을 구현할 때 정확히 이 성질을 씁니다.

14.5 never를 반환하는 헬퍼

class Parser {
  private err(msg: string): never {
    throw new BasicError(ERR.SYNTAX, `${msg} (line ${this.line})`);
  }

  private expect(t: TokenType): Token {
    const tok = this.peek();
    if (tok.type !== t) this.err(`expected ${t}, got ${tok.type}`);
    return tok;      // ✔ 여기 도달했다면 tok.type === t
  }
}
err()의 반환 타입이 void였다면 컴파일러는 그 줄 이후로도 흐름이 이어진다고 보고, expect가 “Token을 반환하지 않는 경로가 있다”고 에러를 냅니다. never라고 적어 주면 “여기서 끝난다”가 전달됩니다.

파서와 VM 전반에 이 패턴이 깔려 있습니다. 에러 메시지 조립을 한곳에 모으면서 타입 흐름도 깔끔해집니다.

15.4 선언 병합 — interface만의 성질

// 모듈 안에서 전역 타입을 넓히려면 declare global 로 감싸야 한다

  interface Window { myApp: App; }   // 기존 Window에 필드를 덧붙인다
}
export {};                            // 이 파일이 모듈임을 분명히 한다
// 이제 window.myApp 이 타입 검사에 통과한다

라이브러리 타입을 확장할 때는 유용하지만, 자기 코드 안에서는 “같은 이름이 두 군데 있는데 안 겹친다”는 혼란의 원인이 되기도 합니다.

유니언과 교차

|는 “둘 중 하나”, &는 “둘 다”

맨 앞의 |는 있어도 되고 없어도 되는 장식입니다. 항목마다 줄을 맞추기 위해 관례적으로 붙입니다.

이 표기는 AST 정의에서 특히 자주 보입니다. 항목이 20개가 넘어도 세로로 늘어놓으면 읽을 만합니다.

16.3 교차 &

interface Positioned { pos: SourcePos; }
interface Named { name: string; }

type Both = Positioned & Named;
const b: Both = { pos: { line: 1, col: 1 }, name: "A" };   // 둘 다 있어야 한다
직관과 반대로 느껴지는 지점 — &는 “필드가 더 많은” 타입을 만듭니다. 집합으로 보면 “두 조건을 모두 만족하는 값들”이라 오히려 더 좁은 집합입니다. |는 필드가 적어지고 집합은 넓어집니다.
type Never = { a: number } & { a: string };   // a는 number & string = never

기본 타입끼리 교차하면 대개 never가 됩니다. 실무에서 &는 거의 객체 모양을 합칠 때만 씁니다.

16.4 유니언은 함수 인자에서 어떻게 도나

// 이렇게 쓰면 "숫자를 주면 숫자를, 문자열을 주면 문자열을"이 표현되지 않는다

17.1 문제 — 종류가 여럿인 데이터

GW-BASIC의 값은 정수·단정도·배정도·문자열 네 종류입니다. 이걸 어떻게 하나의 타입으로 표현할까요?

옵셔널 필드로 (나쁨)
interface Value {
  isStr?: boolean;
  num?: number;
  str?: string;
}
// num과 str이 동시에 있을 수도,
// 둘 다 없을 수도 있다 — 컴파일러가 못 막는다
판별 유니언으로 (좋음)
type BasicValue =
  | { tag: "INT"; v: number }
  | { tag: "SNG"; v: number }
  | { tag: "DBL"; v: number }
  | { tag: "STR"; v: string };
// 불가능한 조합은 애초에 만들 수 없다
핵심 아이디어 — 각 갈래에 서로 다른 리터럴 값을 가진 공통 필드를 하나 둡니다. 그 필드를 판별자(discriminant)라고 부릅니다. 여기서는 tag입니다.

17.2 판별자를 검사하면 타입이 좁아진다

function toStr(v: BasicValue): string {
  if (v.tag === "STR") {
    return v.v;             // v.v의 타입: string
  }
  return String(v.v);       // v.v의 타입: number
}

컴파일러가 v.tag === "STR"이라는 값 비교를 보고 “그렇다면 v는 네 갈래 중 STR 갈래”라고 추론합니다. 그 결과 v.v의 타입까지 자동으로 결정됩니다.

v: BasicValue→v.tag === "STR"→v: {tag:"STR"; v:string}

17.3 판별자는 어떤 이름이든 된다

// 책의 관례 — 세 군데 모두 문자열 리터럴을 판별자로 쓴다
type BasicValue = { tag: "INT"; v: number } | ...;      // 값에는 tag
type Expr       = { kind: "NumLit"; ... } | ...;        // AST 식에는 kind
type Stmt       = { kind: "Print"; ... } | ...;         // AST 문장에도 kind
type Op         = { op: "PUSH"; value: BasicValue }     // 바이트코드에는 op
                | { op: "ADD" } | ...;
판별자에 쓸 수 있는 것문자열 리터럴 · 숫자 리터럴 · boolean · enum 멤버
못 쓰는 것string, number 같은 넓은 타입. 값이 하나로 고정돼야 갈래를 구별할 수 있습니다.
이름 짓기 — kind, tag, type이 흔합니다. type은 예약어처럼 보여 헷갈리므로 kind를 권합니다. 다만 토큰처럼 이미 type이 자연스러운 곳에서는 그대로 씁니다.

17.4 실전 — AST 표현식 노드

src/ast/nodes.ts

export interface StrLit  { kind: "StrLit"; value: string; }
export interface VarRef  { kind: "VarRef"; name: string; }
export interface ArrayRef{ kind: "ArrayRef"; name: string; indices: Expr[]; }
export interface FnCall  { kind: "FnCall"; target: string; args: Expr[]; }
export interface UnaryExpr  { kind: "Unary";  op: string; operand: Expr; }
export interface BinaryExpr { kind: "Binary"; op: string; lhs: Expr; rhs: Expr; }

export type Expr =
  | NumLit | StrLit | VarRef | ArrayRef | FnCall | UnaryExpr | BinaryExpr;

갈래마다 interface를 따로 두고 마지막에 type으로 묶는 방식입니다. 갈래 하나를 이름으로 가리킬 수 있어 편합니다. 1 + 2 * 3은 이렇게 표현됩니다.

{
  kind: "Binary", op: "+",
  lhs: { kind: "NumLit", value: 1, numType: "INT" },
  rhs: {
    kind: "Binary", op: "*",
    lhs: { kind: "NumLit", value: 2, numType: "INT" },
    rhs: { kind: "NumLit", value: 3, numType: "INT" },

17.5 switch로 갈래마다 처리하기

src/ast/print.ts — AST를 다시 문자열로 되돌리는 함수

export function dumpExpr(e: A.Expr): string {
  switch (e.kind) {
    case "NumLit":   return String(e.value);
    case "StrLit":   return JSON.stringify(e.value);
    case "VarRef":   return e.name;
    case "ArrayRef": return `${e.name}(${e.indices.map(dumpExpr).join(",")})`;
    case "FnCall":   return `${e.target}(${e.args.map(dumpExpr).join(",")})`;
    case "Unary":    return `(${e.op} ${dumpExpr(e.operand)})`;
    case "Binary":   return `(${dumpExpr(e.lhs)} ${e.op} ${dumpExpr(e.rhs)})`;
  }
}
각 case 안에서 e는 그 갈래의 타입으로 정확히 좁혀져 있습니다. e.value가 "NumLit"에서는 number, "StrLit"에서는 string이고, "VarRef"에는 value가 아예 없다는 것을 컴파일러가 압니다.
모든 갈래가 return하므로 함수 끝에 return이 없어도 “값을 안 돌려주는 경로”가 없다고 판정됩니다. 갈래를 하나 빠뜨리면 그 순간 TS2366: Function lacks ending return statement가 납니다.

17.7 정리 — 판별 유니언이 주는 것

  1. 불가능한 상태를 표현할 수 없게 만든다. 문자열 값에 num 필드가 붙는 일이 아예 생기지 않습니다.
  2. 분기하면 타입이 자동으로 좁혀진다. 캐스팅(as)이 필요 없습니다.
  3. 갈래를 추가하면 처리 안 한 곳이 전부 드러난다 — 망라성 검사(19장)와 결합했을 때.
  4. 런타임에도 살아 있다. tag는 실제 필드라 디버깅할 때 console.log에 그대로 보입니다.

Q. { kind: string; value: number }를 갈래로 쓰면 왜 좁히기가 안 되나?

판별자가 리터럴 타입이어야 합니다. kind: string은 “아무 문자열”이므로 e.kind === "NumLit"이라는 비교로 갈래를 결정할 수 없습니다. kind: "NumLit"처럼 값 하나로 고정해야 합니다.

반환 타입을 boolean이 아니라 v is T로 적으면, 그 함수가 true를 돌려줬을 때 컴파일러가 타입을 좁혀 줍니다.

책임은 여러분에게 — 컴파일러는 함수 몸통이 정말 그 판정을 하는지 검사하지 않습니다. return true;라고만 써도 통과합니다. 잘못 쓰면 as만큼 위험합니다.

18.6 단언 함수 asserts x is T

function assertNum(v: BasicValue): asserts v is NumValue {
  if (v.tag === "STR") throw new BasicError(ERR.TYPE_MISMATCH, "Type mismatch");
}

function g(v: BasicValue) {
  assertNum(v);
  v.v.toFixed(2);      // ✔ 이 줄부터 v는 NumValue
}

is는 “true면 좁힌다”, asserts is는 “이 함수가 정상 반환했다면 좁힌다”입니다. 던지거나 통과하거나 둘 중 하나인 검증 함수에 어울립니다.

호출부에서 반드시 변수에 담아 부르거나 명시적 타입 표기가 있는 함수여야 동작합니다. const f = (v) => { ... }처럼 추론에 맡기면 단언 함수로 인정되지 않습니다.

19.1 문제 — 갈래를 하나 추가했을 때

AST에 SwapStmt를 추가했다고 합시다. 그런데 컴파일러의 switch에 case "Swap"을 넣는 걸 깜빡했습니다.

function compileStmt(s: Stmt): void {
  switch (s.kind) {
    case "Assign": /* ... */ break;
    case "Print":  /* ... */ break;
    // Swap을 빠뜨림!
  }
  // 조용히 아무 일도 안 하고 지나간다 → SWAP 문이 무시되는 버그
}

런타임에 “SWAP이 안 먹네?”로 나타납니다. 원인을 찾기까지 한참 걸립니다.

19.2 해법 — never 대입

function compileStmt(s: Stmt): void {
  switch (s.kind) {
    case "Assign": /* ... */ break;
    case "Print":  /* ... */ break;
    default: {
      const _: never = s;      // ← 여기가 방아쇠
      throw new Error(`unhandled stmt: ${JSON.stringify(s)}`);
    }
  }
}
원리 — 모든 갈래를 처리했다면 default에 도달한 s의 타입은 never입니다. 하나라도 빠뜨리면 s에 그 갈래가 남아 있으므로 never에 대입할 수 없어 컴파일 에러가 납니다.
TS2322: Type 'SwapStmt' is not assignable to type 'never'.

19.4 변형 — 헬퍼 함수로 빼기

19.5 한계와 주의점

  • if/else if 사슬에도 통한다 — 마지막 else에서 같은 기법을 씁니다.
  • 판별자가 없으면 안 통한다 — string을 switch하는 경우에는 못 씁니다.
  • default가 정말 도달 가능한 경우 — 외부 JSON에서 온 값 등은 never가 아니라 unknown으로 받고 검증해야 합니다.

else if (e.kind === "StrLit") { /* ... */ }
else { const _: never = e; throw new Error("unhandled"); }

제네릭

Map<string, BasicValue>의 꺾쇠가 무슨 뜻인지

20.1 왜 필요한가

제네릭 없이
function first(a: any[]): any {
  return a[0];
}
const t = first(tokens);   // any — 타입이 죽었다
제네릭으로
function first<T>(a: T[]): T | undefined {
  return a[0];
}
const t = first(tokens);   // Token | undefined
제네릭 = 타입을 인자로 받는 것. <T>는 “호출할 때 결정될 타입에 붙일 이름”입니다. 입력과 출력의 관계를 표현합니다.

20.2 이미 쓰고 있던 제네릭들

Array<Token>                   // = Token[]
Map<string, BasicValue>        // 키 타입, 값 타입
Set<number>
Promise<string | null>
Record<string, number>
ReadonlyArray<Op>

대부분의 경우 제네릭은 쓰기만 하고 직접 만들 일은 드뭅니다. 책의 4,000줄에도 <T>를 직접 선언하는 함수는 거의 없습니다.

읽는 법 — Map<string, BasicValue>는 “문자열을 키로, BasicValue를 값으로 갖는 Map”. 꺾쇠 안은 타입 자리이지 값 자리가 아닙니다.

20.3 타입 인자는 대개 생략한다

빈 컨테이너는 적어 두세요 — 지역 변수 const a = []는 TypeScript가 뒤따르는 a.push(1)을 보고 타입을 키워 주지만(“진화하는 배열”), 클래스 필드는 그렇지 않습니다. private toks = [];는 never[]로 굳어 this.toks.push(t)가 TS2345: Argument of type 'Token' is not assignable to parameter of type 'never'로 막힙니다. 그래서 책은 private tokens: Token[] = [];라고 적습니다.

20.4 제약 extends

function len<T extends { length: number }>(x: T): number {
  return x.length;      // ✔ length가 있다고 보장됨
}

len([1, 2]);       // 2
len(42);           // ✘ number에는 length가 없다

// 키 제약 — 실무에서 자주 보는 형태
function get<T, K extends keyof T>(o: T, k: K): T[K] {
  return o[k];
}
get(tok, "line");    // number
get(tok, "nope");    // ✘ 없는 키

21.2 자주 쓰는 유틸리티 타입

Required<T>모든 필드를 필수로
Readonly<T>모든 필드를 readonly로

21.3 예제로 감 잡기

interface Token { type: TokenType; value: string; line: number; col: number; }

type PartialTok = Partial<Token>;
// { type?: TokenType; value?: string; line?: number; col?: number }

type PosOnly = Pick<Token, "line" | "col">;
// { line: number; col: number }

type NoPos = Omit<Token, "line" | "col">;
// { type: TokenType; value: string }

type StrVal = Extract<BasicValue, { tag: "STR" }>;
// { tag: "STR"; v: string }   ← 판별 유니언에서 갈래 하나만 뽑아내기

26.1 파일 하나가 모듈 하나

import나 export가 하나라도 있으면 그 파일은 모듈이 됩니다. 모듈 안의 이름은 바깥에서 보이지 않습니다.

28.1 네 가지 반복

    switch (ins.op) {
      case "END": return;

}

32.1 왜 비동기가 필요한가

브라우저에서 JavaScript는 단일 스레드입니다. 화면 그리기, 클릭 처리, 우리 코드가 모두 한 줄에 서 있습니다.

VM 실행→INPUT 만남→키 입력 대기→VM 재개
여기서 “대기”를 루프로 막으면 브라우저 전체가 멈춥니다. 화면도 안 그려지고 키 입력 이벤트도 처리되지 않아, 영원히 입력을 받지 못합니다.

그래서 INPUT은 “여기서 멈추고, 입력이 오면 이어서 실행하라”는 비동기 형태여야 합니다.

inputLine(prompt: string): Promise<string | null>;
sound(freq: number, durationMs: number): Promise<void>;
play(mml: string): Promise<void>;

Host 인터페이스에서 Promise를 돌려주는 메서드가 정확히 이 셋인 이유입니다.

32.2 Promise의 세 가지 상태

pending→fulfilled (값) 또는rejected (에러) 
const p: Promise<string> = new Promise((resolve, reject) => {
  setTimeout(() => resolve("hello"), 1000);
});

p.then(v => console.log(v));         // 성공했을 때
p.catch(e => console.error(e));      // 실패했을 때
p.finally(() => console.log("끝"));  // 어느 쪽이든
Promise<T>의 T는 성공했을 때 나올 값의 타입입니다. Promise<void>는 “언젠가 끝나지만 값은 없다”는 뜻입니다.

32.3 콜백을 Promise로 감싸기

브라우저 호스트의 inputLine은 이렇게 생겼습니다.

inputLine(prompt: string): Promise<string | null> {
  this.printAt(prompt);
  return new Promise((resolve) => {
    this.pendingInput = resolve;      // resolve 함수를 보관해 둔다
  });
}

// 키 이벤트 핸들러에서 Enter를 받으면
private onEnter(text: string): void {
  const r = this.pendingInput;
  this.pendingInput = null;
  r?.(text);                          // 보관해 둔 resolve를 호출 → 대기가 풀린다
}
핵심 트릭 — resolve 함수를 변수에 저장해 두었다가, 나중에 이벤트가 왔을 때 호출합니다. 이 패턴 하나로 “이벤트 기반 세계”와 “순차 실행 세계”가 이어집니다.

async run(): Promise<void> {

  while (this.pc < this.code.length) {

35.3 보조 메서드 세 개

private peek(off = 0): string {
  return this.src[this.pos + off] ?? "";
}

private advance(): string {
  const ch = this.src[this.pos++] ?? "";
  if (ch === "\n") { this.line++; this.col = 1; }
  else { this.col++; }
  return ch;
}

private err(msg: string): never {
  throw new BasicError(ERR.SYNTAX, msg, { line: this.line, col: this.col });
}
  1. off = 0 — 기본값 매개변수(12장). peek()과 peek(1) 둘 다 됩니다.
  2. ?? "" — 널 병합(9장). 범위를 넘으면 undefined가 나오므로 빈 문자열로 바꿔 “문자열 아닌 것”을 아예 없앱니다.
  3. this.pos++ — 현재 값을 쓰고 나서 증가. ++this.pos와 다릅니다.
  4. : never — 절대 정상 반환하지 않음(10·14장). 호출한 자리 뒤로 흐름이 이어지지 않는다고 컴파일러에 알립니다.

    return;
  }

}

async run(): Promise<void> {
  this.pc = 0;
  this.halted = false;
  while (!this.halted && this.pc < this.program.code.length) {
    const ins = this.program.code[this.pc++]!;
    await this.dispatch(ins);

  3. ! — 널 아님 단언(9장). noUncheckedIndexedAccess 때문에 Op | undefined가 되는데, 루프 조건이 범위를 보장하므로 단언합니다.

37.4 dispatch의 반환 타입이 특이한 이유

// 동기 명령은 void를, 비동기 명령(INPUT/SOUND/PLAY/BEEP)은 Promise를 반환한다.
// async 함수로 만들면 동기 명령의 예외까지 rejected Promise로 감싸져
// 동기 호출 경로에서 조용히 사라지므로 일반 메서드로 둔다.
private dispatch(ins: Op): void | Promise<void> {
  switch (ins.op) {
    case "PUSH": this.push(ins.value); return;   // ins.value: BasicValue
    case "POP":  this.pop(); return;
    case "DUP":  this.push(this.peek()); return;
    case "ADD": { const b = this.pop(), a = this.pop(); this.push(add(a,b)); return; }
void | Promise<void> — “동기일 수도 비동기일 수도”. async를 붙이면 모든 명령이 Promise를 만들어 내는데, 명령 하나당 객체 하나가 생기는 셈이라 VM 성능에 직격입니다. 게다가 동기 예외가 rejected Promise로 감싸지는 부작용도 있습니다.

case "PUSH" 안에서만 ins.value가 존재합니다. case "ADD"에서 ins.value를 쓰면 컴파일 에러입니다 — 판별 유니언이 일하고 있는 것입니다.

  if (v === undefined) throw new BasicError(ERR.SYNTAX, "Stack underflow");
  return v;
}

private peek(off = 0): BasicValue {
  const v = this.stack[this.stack.length - 1 - off];
  if (v === undefined) throw new BasicError(ERR.SYNTAX, "Stack underflow");
  return v;
}

ADD의 const b = this.pop(), a = this.pop();에서 b가 먼저인 데 주의하세요. 스택은 나중에 넣은 것이 먼저 나오므로, a - b를 계산하려면 이 순서가 맞습니다.

      else if (ch === "\r") { this.col = 1; }

}

expect(out.join("")).toBe(" 3 \n") — GW-BASIC은 양수 앞에 공백, 숫자 뒤에도 공백을 붙입니다. 그 세부까지 테스트로 못 박아 두는 것이 이 책의 방식입니다.

B.3 판별 유니언 완전체

// ① 정의
type Node =
  | { kind: "Num"; value: number }
  | { kind: "Str"; value: string }
  | { kind: "Bin"; op: string; lhs: Node; rhs: Node };

// ② 생성자
const num = (value: number): Node => ({ kind: "Num", value });

// ③ 타입 가드
const isNum = (n: Node): n is Extract<Node, { kind: "Num" }> => n.kind === "Num";

// ④ 처리 + 망라성 검사
function evalNode(n: Node): number {
  switch (n.kind) {
    case "Num": return n.value;
    case "Str": return Number(n.value);
    case "Bin": return evalNode(n.lhs) + evalNode(n.rhs);
    default: {
      const _: never = n;
      throw new Error(`unhandled: ${JSON.stringify(n)}`);
    }
  }
}
이 네 조각이 세트입니다. 새 갈래를 추가하면 ④가 컴파일 에러로 알려 줍니다.

C.1 타입 읽기

Q1. ((pc: number, op: Op) => Promise<void> | void) | null 을 우리말로 풀면?

“pc(숫자)와 op(Op)를 받아 Promise<void> 또는 아무것도 돌려주지 않는 함수 — 또는 null”. 즉 동기·비동기 어느 쪽 함수든 꽂을 수 있고, 안 꽂아도 되는 훅입니다.

Q2. private push(type: Token["type"], value: string, extra: Partial<Token> = {}): void 에서 Token["type"]을 그냥 TokenType이라고 써도 되나?

됩니다 — 두 타입은 완전히 같습니다. Token["type"]을 쓰면 TokenType을 따로 import하지 않아도 되고, 나중에 Token.type의 타입이 바뀌면 자동으로 따라간다는 이점이 있습니다.

C.2 버그 찾기

Q3. const c = given || defaultColor; — given: number | null일 때 무엇이 잘못됐나?

given이 0(검정)일 때도 defaultColor로 바뀝니다. ||는 falsy 전부를 걸러내기 때문입니다. given ?? defaultColor로 고쳐야 합니다.

Q4. files.forEach(async f => { await load(f); }); console.log("완료"); — 무엇이 잘못됐나?

forEach는 콜백이 돌려주는 Promise를 무시합니다. “완료”가 로딩이 끝나기 전에 찍히고, 로딩 중 에러는 unhandled rejection이 됩니다. for (const f of files) await load(f); 또는 await Promise.all(files.map(f => load(f)));로 고칩니다.

Q5. lines.sort()로 GW-BASIC 줄 번호를 정렬하면?

문자열로 비교되어 10, 100, 20, 5 순서가 됩니다. lines.sort((a, b) => a - b)여야 합니다.

C.3 설계 판단

Q6. 새 AST 노드 SwapStmt를 추가했다. 처리해야 할 곳을 빠짐없이 찾으려면?

Stmt 유니언에 추가한 뒤 npx tsc --noEmit을 돌립니다. 망라성 검사(const _: never = s;)가 있는 모든 switch에서 TS2322: Type 'SwapStmt' is not assignable to type 'never'가 나옵니다. 그 목록이 곧 할 일 목록입니다.

Q7. setColor(fg: number | null, ...)에서 null 대신 옵셔널 fg?: number를 쓰면 무엇이 달라지나?

호출부에서 setColor(undefined, 3)처럼 어색해지고, “두 번째만 지정”을 표현하기 위해 결국 undefined를 명시해야 합니다. 또 “값 없음”이 undefined가 되어, 기본값 문법(= 7)과 섞이면 의도가 흐려집니다. “생략됨”이 도메인의 정식 상태라면 null로 못 박는 편이 읽기 좋습니다.
