스프라이트·팔레트·플레이어 색

256색으로 네 진영을 그리는 법,
그리고 프레임버퍼를 건드리지 않는 애니메이션

팔레트 — 256색, 성분은 0…63

Mode 13h 의 한 픽셀은 1바이트입니다. 색이 아니라 번호입니다.

번호를 색으로 바꾸는 것이 팔레트이고, VGA DAC 의 각 성분은 6비트(0…63)입니다. 24비트가 아닙니다.

fb[320 · 200]     팔레트 인덱스 (0..255)
pal[256][3]       각 성분 0..63
세 언어 모두 프레임버퍼가 1차원 정수 배열입니다. 이것이 세 구현을 바이트 단위로 비교 가능하게 만드는 유일한 이유입니다 — make parity 가 192,015바이트 PPM 을 cmp 합니다.

표를 옮겨 적지 않는다

768개의 숫자를 세 언어에 옮겨 적는 것은 틀리기 좋은 일입니다. 대신 정수식으로 만듭니다.

범위내용
0검정
1–15도스 16색 (표준 EGA 값을 0…63 로)
16–31회색 16단계
160–191플레이어 색 4벌 × 8단계
192–207UI 색
208–255지형 램프 6벌 × 8단계

결과는 golden/palette.txt 에 얼려 두고 세 언어가 대조합니다. 생성기(tools/gen_palette.py)는 독립 구현이 아니라 동결기이며, 파일 첫머리에 그렇게 적어 두었습니다 — 데이터를 두 번 구현해 봐야 같은 실수를 두 번 하거나 서로 다른 표를 갖게 될 뿐입니다.

명암표 — 시작할 때 한 번

light[l][c] = pal[c] 의 각 성분에 l/3 을 곱한 색과 가장 가까운 팔레트 항목
거리 = (dr)² + (dg)² + (db)²        최소, 동점이면 인덱스 최소

안개(15부)가 이 표를 씁니다. 어둡게 그릴 때 색 계산을 하지 않고 표에서 읽습니다.

262,144회 비교는 실측 0.065초입니다. 시작할 때 한 번이므로 문제가 되지 않고, 매 픽셀 계산으로 돌리면 프레임당 45,056번이 됩니다.

3단계(원색)가 항등이 아닙니다. 같은 색이 팔레트에 둘 있으면 인덱스가 작은 쪽으로 갑니다. 예를 들어 회색 램프의 첫 항목(16번)은 검정이라 0번으로 접힙니다. 시험이 이것을 "같은 색이면 인덱스가 작은 쪽"으로 확인합니다.

스프라이트 — 헤더 넷과 RLE

헤더: w(1) h(1) ox(1) oy(1)        ox, oy 는 발밑 기준점
본문: (count, value) 쌍. value 0 은 투명(컬러키)

기준점이 발밑인 이유는 유닛이 발밑 y 로 정렬되기 때문입니다(§23.3). 중심으로 두면 큰 유닛과 작은 유닛의 정렬이 어긋납니다.

이 엔진의 스프라이트도 정수식으로 그립니다 — 아티스트가 없으므로 그림은 소박하지만, 세 언어가 같은 바이트를 내는 것이 목적입니다.

몸통 원만은 골든 생성기가 정의(dx² + dy² ≤ r²)로 그리고 엔진은 §6.2 의 덧셈만 쓰는 span 알고리즘으로 그립니다. 두 결과가 같은지 대조하는 것이 그 알고리즘의 검증입니다.

정리 22.1 — 런 단위 클리핑

정리 22.1. 런 단위로 자르면 픽셀당 비교가 사라진다. 완전히 화면 밖인 스프라이트는 런을 하나도 훑지 않고 반환한다.

투명 런(value == 0)   →  pos += run,  건너뛴다
불투명 런             →  이 줄에 걸치는 만큼만 잘라 쓴다

16×16 스프라이트의 픽셀은 256개지만 런은 대개 30–50개입니다. 경계 검사를 픽셀에서 런으로 옮기면 검사 횟수가 다섯 배 줄어듭니다.

플레이어 색 리맵

PLAYER_BASE = 160,  플레이어당 8단계
스프라이트는 항상 160…167 로 그려져 있고, 블릿할 때 owner · 8 을 더한다

색을 여덟 벌 그리지 않습니다. 도스 시절의 표준 요령이며, 스프라이트 한 벌로 네 진영을 그립니다.

그림자(251번)는 리맵하지 않습니다. 조건이 160 ≤ val < 168 이라 자동으로 걸러집니다 — 별도의 마스크가 필요 없습니다.

이 요령이 팔레트 모드에서만 가능한 이유를 보세요. 트루컬러라면 픽셀마다 색을 계산해야 하고, 그러면 블릿이 곱셈 세 번을 더 하게 됩니다. 인덱스 하나에 8 을 더하는 것과는 비교가 안 됩니다.

5장으로 8방향

메모리와 아티스트 시간을 동시에 아끼는 요령입니다. 4부의 오토타일이 47장을 14장으로 줄인 것과 같은 종류의 절약입니다 — 대칭을 쓰는 것.

반전은 블릿 안에서 런의 순서와 각 런 안의 픽셀 순서를 뒤집어 처리합니다. 별도의 스프라이트를 만들지 않습니다.

상자 안에서 뒤집으므로 기준점이 w − 1 − 2·ox 픽셀만큼 옮겨집니다(폭 16·ox 8 이면 1px). 유닛이 서쪽을 볼 때 1픽셀 흔들립니다. 세 언어가 같은 자리에 그리는 것이 그 1픽셀보다 중요해서 그대로 두었고, 주석에 적어 두었습니다.

팔레트 사이클링 — 공짜 애니메이션

물 색 인덱스 232…239 를 8틱마다 한 칸씩 돌립니다. 프레임버퍼는 그대로입니다.

픽셀을 하나도 쓰지 않고 물이 흐릅니다. 팔레트 모드의 가장 큰 장점이었고, 폭포·용암·깜빡이는 불빛이 전부 이 요령이었습니다.

사이클 위치는 상태의 일부(pal_phase)이며 렌더 결과를 바꾸므로 PPM 비교에 영향을 줍니다. 그래서 해시에는 넣지 않되(시뮬레이션이 아니므로) 트레이스에는 넣습니다 — 파리티 검사에서 두 언어의 물 색이 다르면 잡혀야 하니까요.

6×8 폰트 — 49자

ASCII 32…126 의 자리를 두되 실제로 그린 글자는 49자입니다. 공백, A–Z, 0–9, 그리고 . , : - + / % ( ) ! ? #.

소문자가 없습니다. 도스 게임 UI 가 대문자만 쓴 이유도 대개 같았습니다 — 아티스트 시간과 ROM 공간.

글자당 8바이트 · 95자 = 760바이트
5×7 획으로 그려 6×8 칸의 왼쪽 위에 놓는다
표는 tools/gen_font.py 가 획 정의에서 만들어 16진 문자열 하나로 얼립니다. 세 언어는 그 문자열을 그대로 박습니다 — 760바이트를 세 번 옮겨 적는 것보다 문자열 하나를 세 번 붙여 넣는 편이 틀릴 자리가 적습니다.

PPM — 0…63 을 0…255 로

expand(v) = v · 4 + ⌊v / 16⌋
expand(0) = 0     expand(63) = 252 + 3 = 255

v · 255 / 63 은 나눗셈이 63 이라 세 언어의 내림이 갈릴 여지가 있습니다. 위 식은 곱셈 하나와 나눗셈 하나(2의 거듭제곱)뿐이고 양 끝이 정확히 맞습니다.

"P6\n320 200\n255\n" (15바이트) + 320·200·3 = 192,000  →  총 192,015바이트

이 숫자가 세 언어 파리티의 단위입니다. cmp 가 통과하면 모든 픽셀이 같다는 뜻입니다.

확인 문제 1

플레이어 색 리맵의 조건이 160 ≤ val < 168 이다. 스프라이트에 168번 색을 하나 쓰면 무슨 일이 일어나는가?

168 은 플레이어 1 의 첫 단계입니다. 리맵되지 않으므로 모든 플레이어의 유닛에 파란색 점이 하나 찍힙니다.

더 나쁜 경우는 플레이어 3(owner 3)의 유닛입니다. 리맵된 다른 픽셀은 160 + 24 = 184 부터인데 그 점만 168 이라 다른 진영의 색이 섞입니다.

이런 실수를 막는 방법은 스프라이트를 정수식으로 만드는 것입니다 — PLAYER_BASE + k (k = 0…6) 만 쓰도록 코드로 강제하면 168 을 쓸 방법이 없습니다. 손으로 그린 스프라이트라면 검증 도구가 필요합니다.

확인 문제 2

물 사이클을 8틱이 아니라 매 틱 돌리면 무엇이 문제인가? 더 부드러워지지 않는가?

부드러워지지 않습니다. 램프가 8단계뿐이므로 매 틱 돌리면 8틱마다 제자리로 돌아옵니다 — 18.2 Hz 에서 초당 2.3회 깜빡이는 물이 됩니다. 흐르는 것이 아니라 떨리는 것으로 보입니다.

8틱(약 0.44초)에 한 칸이면 한 바퀴에 3.5초입니다. 그 정도가 "흐른다"로 읽히는 속도입니다.

그리고 트레이스가 커집니다. 사이클 위상이 트레이스에 들어가므로 매 틱 바뀌면 압축이 덜 됩니다 — 20부의 리플레이 크기와 같은 종류의 대가입니다.
