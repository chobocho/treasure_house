픽킹 — 사각형 다음에 마스크

화면의 한 점이 어느 유닛을 가리킵니까?

1) 뷰포트 안인가                    아니면 패널·미니맵 처리로
2) 화면 → 월드 (카메라 오프셋 더하기)
3) 후보: 공간 버킷 질의 반경 2타일
4) y 내림차순, 동점이면 핸들 내림차순으로 정렬
5) AABB 안이면 스프라이트 알파 마스크 확인

4번의 정렬은 23부의 그리기 순서를 거꾸로 도는 것입니다. y 정렬로 그리면 아래쪽 유닛이 나중에(위에) 그려지므로, 픽킹은 아래쪽부터 봐야 눈에 보이는 것이 잡힙니다.

AABB 만으로 끝내지 않는 이유는 유닛이 사각형이 아니기 때문입니다. 16×16 상자 안에서 실제 몸통은 반지름 5 원이고, 모서리를 클릭하면 아무것도 잡히지 않아야 합니다. 마스크는 스프라이트의 컬러키 여부 비트를 그대로 씁니다 — 별도의 히트박스를 만들지 않습니다.

우선순위 규칙이 없으면 기지 위를 드래그했을 때 건물과 유닛이 함께 잡히고, 그다음 우클릭이 무엇을 뜻하는지 모호해집니다.

32기 상한은 도스 시절 제한을 흉내낸 것이고, 이 덱의 규칙이라고 적습니다. 당시 게임들의 상한(9기·12기·다양)은 UI 공간과 메모리에서 왔고, 우리에게는 그런 제약이 없습니다. 상한을 두는 진짜 이유는 대형 배정(14부)의 비용입니다.

선택 순서가 대형을 정한다

정렬이 핸들 오름차순인 것은 눈에 보이지 않지만 중요합니다.

선택 목록의 순서  →  14부 대형의 슬롯 배정 순서

같은 여덟 기를 다른 순서로 선택하면 다른 대형이 나옵니다. 드래그 방향에 따라 대형이 달라지면 플레이어는 그것을 버그로 읽습니다.

그래서 정렬 키가 화면 위치가 아니라 핸들입니다. 화면 위치로 정렬하면 카메라가 움직였을 때 같은 유닛들이 다른 순서를 받습니다. 핸들은 게임 내내 변하지 않습니다.

컨트롤 그룹은 핸들을 저장한다

0–9 번 그룹에 저장되는 것은 핸들입니다. 인덱스가 아닙니다.

그래서 그룹에 든 유닛이 죽어도 아무 처리가 필요 없습니다. valid(10부)가 자동으로 거릅니다 — 세대가 올라갔으니까요.

인덱스를 저장했다면:  죽은 슬롯에 새 유닛이 들어오면 그룹에 몰래 들어온다
핸들을 저장하면:      valid 가 false — 조용히 사라진다
그룹은 상태 해시에 넣지 않습니다. UI 상태이고 플레이어마다 다르며 시뮬레이션에 영향을 주지 않기 때문입니다. 그룹을 바꾸는 것만으로는 게임이 변하지 않습니다 — 명령을 내려야 변합니다.

명령 큐

Order = (kind, tx, ty, target_handle)      유닛당 큐 상한 8
kind ∈ { MOVE, ATTACK, ATTACK_MOVE, HARVEST, BUILD, STOP, HOLD, TRAIN }

기본 클릭은 큐를 비우고 하나를 넣습니다. 시프트 클릭은 뒤에 붙입니다. STOP 은 큐를 비우고 자신도 들어가지 않습니다.

TRAIN 만 유닛이 아니라 건물에게 내리는 명령입니다. 같은 자료형에 넣은 이유는 하나입니다 — UI·AI·스크립트가 모두 sim.step 의 같은 인자로 들어와야 락스텝이 성립합니다.

우클릭이 무엇을 뜻하는가

순서대상명령
1적 (유닛이든 건물이든)ATTACK
2광맥 타일HARVEST
3내 반납처 (사령부·정제소)HARVEST — 반납

판정 순서도 명세입니다. 적의 정제소를 우클릭하면 반납이 아니라 공격이어야 합니다 — 1번이 3번보다 먼저 오는 이유입니다.

이 규칙은 명세 초안에서 "내 건물이고 그것이 정제소면"이라고 적혀 있었습니다. 그런데 §25.2 는 사령부도 반납처라고 말합니다. 두 문장이 어긋난 채로 구현했으면 채집기가 사령부에 반납하지 못했을 것입니다. 명세를 고쳐 "반납처(사령부·정제소)"로 맞췄습니다.

명령은 틱 경계에서만 들어간다

UI 가 명령을 만든다
  → net 의 지연 큐 (§19)
  → ORDER_DELAY = 2 틱 뒤
  → sim.step(orders) 의 인자

UI 코드가 sim 의 상태를 직접 건드리는 경로는 존재하지 않습니다. 이 규율 하나가 락스텝을 가능하게 합니다.

"이것 하나만 예외로" 가 이 설계를 죽입니다. UI 가 w.tx[i] = ... 를 한 줄 쓰면 그 줄은 내 기계에서만 실행됩니다. 상대의 시뮬에는 그 일이 일어나지 않았고, 다음 해시 비교에서 갈립니다.

그래서 이 저장소의 프런트엔드 세 개(24·25·26부)는 전부 얇은 껍데기입니다. 그리는 것과 명령을 만드는 것 말고는 아무것도 하지 않습니다.

확인 문제 1

픽킹의 정렬을 y 오름차순으로 바꾸면 무엇이 잘못되는가?

두 유닛이 겹쳐 있을 때 뒤에 있는 유닛이 잡힙니다. 화면에서는 앞의 유닛이 뒤의 유닛을 가리고 있는데, 클릭하면 가려진 쪽이 선택됩니다.

플레이어는 이것을 "클릭이 빗나갔다"고 느낍니다. 그리고 다시 클릭해도 같은 결과가 나오므로 고칠 방법이 없다고 느낍니다.

일반화하면 이렇습니다 — 입력 판정은 출력 순서의 역순이어야 합니다. 그리기가 뒤에서 앞으로 간다면 픽킹은 앞에서 뒤로 가야 합니다. 두 순서가 같은 방향이면 반드시 어긋납니다.

확인 문제 2

명령 큐 상한을 8 에서 무제한으로 바꾸면 무슨 문제가 생기는가? 시프트 클릭을 많이 하는 것이 나쁜가?

세 가지가 생깁니다.

첫째, 상태 해시가 커집니다. 큐는 상태이므로 해시에 들어가고, 길이가 무제한이면 해시 계산 시간도 무제한입니다. 매 틱 도는 계산에 상한이 없는 것은 위험합니다.

둘째, 리플레이가 커집니다. 명령이 늘면 로그가 늘고, 20부의 1,153바이트가 무너집니다.

셋째, 플레이어가 실수를 되돌리기 어려워집니다. 40개를 큐에 넣고 나면 그중 30번째만 고치는 방법이 없습니다 — 전부 지우고 다시 넣어야 합니다. 상한은 성능 제약인 동시에 UI 설계이기도 합니다.
