난수는 하나뿐이다

시뮬레이션의 RNG 는 정확히 하나입니다. 렌더나 UI 가 그것을 한 번이라도 뽑으면 두 기계의 수열이 갈립니다.

sim.rng    피해량 · 맵 생성 · AI 의 흔들림
net.rng    네트워크 지터 전용 (§19)
tools      골든 생성기 — 엔진 밖이라 무엇을 써도 된다
"이 한 번만 random() 을" 이 락스텝을 죽입니다. 파티클 하나의 색을 정하려고 뽑은 난수가 다음 전투의 피해량을 바꿉니다 — 수열이 한 칸 밀렸으니까요.

선형 합동 생성기

s' = (22695477 · s + 1) mod 2³²
next15() = ⌊s' / 65536⌋ mod 32768        상위 15비트를 쓴다

승수 22695477 은 볼랜드 C 계열의 값입니다. 이 값을 고른 이유는 고증이 아니라 주기가 최대이기 때문입니다.

정리 3.2 (Hull–Dobell). x' = (a·x + c) mod m 의 주기가 모든 초기값에서 m 인 필요충분조건은 (1) c 와 m 이 서로소, (2) a − 1 이 m 의 모든 소인수로 나누어떨어짐, (3) m 이 4의 배수면 a − 1 도 4의 배수.

m = 2³²  ·  c = 1 (홀수, 서로소)  ·  a − 1 = 22695476 = 4 × 5673869
→ 세 조건 모두 만족 → 주기 2³²

하위 비트를 쓰면 안 되는 이유

골든 4절의 bit0 줄을 보세요. 0, 1, 0, 1 이 반복됩니다.

2의 거듭제곱 모듈러스에서 k 번째 하위 비트의 주기는 2^(k+1) 입니다. 최하위 비트는 주기 2, 그다음은 4 — 난수라고 부를 수 없습니다.

s % 6 으로 주사위를 굴리면 최하위 비트 세 개를 쓰는 셈이고, 그 비트들의 주기는 8 이하입니다. 이 엔진이 상위 15비트만 쓰는 이유이고, C 의 rand() 가 RAND_MAX = 32767 인 이유이기도 합니다.

모듈로 편향

next15() % 6 은 균등하지 않습니다.

32768 = 6 × 5461 + 2
0..32767 중  0 과 1 은 5462번,  2..5 는 5461번 나온다
편향 = 1/5461 ≈ 0.018 %

남는 2 개를 버립니다. limit = 32768 − 32768 mod n 이상이 나오면 다시 뽑습니다.

정리 3.3. roll(n) 은 0…n−1 위의 균등분포다. 증명. 기각 후 남은 구간의 크기가 n 의 배수이고 next15 가 그 위에서 균등하므로, mod n 이 균등을 보존합니다. ∎

기각 횟수도 결정론적입니다. 두 기계가 같은 횟수를 기각하고 같은 값을 얻습니다. 골든 4절이 기각 횟수를 함께 찍는 이유입니다 — 그 숫자가 다르면 수열이 갈렸다는 뜻입니다.

셀룰러 오토마타 — 동굴 만들기

1) 각 칸을 확률 45 % 로 바위:  wall = (roll(100) < 45)
2) 4세대 반복:
       w = 8이웃 중 바위 개수 (맵 밖은 바위)
       next = 1 if (cur == 1 and w >= 4) or (cur == 0 and w >= 5) else 0
3) 가장 큰 통행 성분만 남기고 나머지는 메운다

2세대면 덩어리가 덜 뭉치고, 6세대면 좁은 통로가 전부 막힙니다. 4세대가 이 맵 크기에서 통로와 개활지가 함께 남는 값입니다.

3번이 없으면 고립된 동굴이 생깁니다. 유닛이 갈 수 없는 곳에 광맥이 놓이고, 채집기가 영원히 서 있습니다(17부에서 실제로 겪은 그 버그의 다른 얼굴입니다).

다이아몬드-스퀘어 — 지형 높이

65×65 격자에서 돌리고 왼쪽 위 64×64 를 잘라 쓴다
jitter(step) = roll(2·amp + 1) − amp,   amp = ⌊step · 255 / 128⌋

네 꼭짓점에서 시작해 중앙을 채우고(다이아몬드), 마름모의 중앙을 채우고(스퀘어), 간격을 절반으로 줄이며 반복합니다.

정수 포아송 디스크 — 광맥 배치

광맥이 뭉치면 한쪽 플레이어가 유리해지고, 고르게 흩으면 격자처럼 보입니다. 포아송 디스크는 최소 간격을 지키면서 무작위인 배치입니다.

rmin = 9,  n = 12,  tries 상한 4000
거리 판정:  dx² + dy² < rmin²        ← 제곱근 없이
tries 상한이 반드시 필요합니다. 없으면 배치가 실패할 때 무한 루프가 되고, 그것은 디싱크보다 나쁩니다 — 게임이 멈추니까요. 상한에 걸려 광맥이 12개보다 적게 놓이는 것은 받아들일 수 있는 결과이고, 무한 루프는 아닙니다.

2회 대칭 — 공평한 맵

맵의 왼쪽 위 절반을 180° 돌려 오른쪽 아래에 복사합니다. 그러면 두 플레이어의 시작 조건이 정확히 같습니다.

거울 대칭(좌우 반전)이 아니라 점 대칭인 이유는 대각선 배치 때문입니다. 시작점이 (8,8) 과 (55,55) 이므로 점 대칭이 두 기지를 정확히 마주 보게 합니다.

17부에서 이 대칭이 실제로 값을 했습니다. 처음에는 두 플레이어의 건물 자리를 각자 고르게 두었는데, 정제소와 광맥의 거리가 달라 360틱에 560 대 1,460 크레딧이 되었습니다. 배치도 대칭으로 뒤집자 그 차이가 사라졌습니다. 맵이 대칭이어도 그 위의 결정이 비대칭이면 소용없습니다.

확인 문제 1

기각 표본추출 대신 next15() · n / 32768 로 범위를 줄이면 편향이 사라지는가?

사라지지 않습니다. 32768 을 n 조각으로 나눌 때 n 이 32768 을 나누지 못하면 조각의 크기가 고르지 않습니다. n = 6 이면 조각이 5461 또는 5462 개의 값을 받습니다 — 나머지 연산과 같은 크기의 편향입니다.

다만 편향의 모양은 다릅니다. 나머지 방식은 작은 값들이 유리하고, 곱셈 방식은 편향이 구간에 흩어집니다. 어느 쪽도 균등하지 않습니다.

그리고 곱셈 방식에는 함정이 하나 더 있습니다 — next15() · n 이 32비트를 넘을 수 있습니다. n 이 크면 오버플로가 나고, 그러면 편향이 아니라 완전히 틀린 값이 나옵니다. 기각 방식은 곱셈이 없습니다.

확인 문제 2

맵 생성기가 roll 을 부르는 횟수가 두 언어에서 다르면 어떻게 되는가? 결과 맵이 같다면 괜찮은가?

맵이 같아도 RNG 의 상태가 다릅니다. 맵 생성이 끝난 시점의 s 가 다르므로, 그다음에 뽑는 모든 난수가 갈립니다 — 첫 전투의 피해량부터요.

그래서 이 저장소는 맵을 파일로 얼려 둡니다(golden/map_start.txt). 시뮬레이션은 맵을 생성하지 않고 읽습니다. 생성기는 골든 맵을 만들 때만 돌고, 그때는 세 언어가 아니라 파이썬 하나만 돕니다.

절차적 맵을 게임 중에 만드는 엔진이라면 이 문제를 정면으로 다뤄야 합니다. 방법은 둘입니다 — 생성 전용 RNG 를 따로 두거나(그러면 생성 후 시뮬 RNG 를 정해진 시드로 초기화), 생성 알고리즘의 roll 호출 횟수까지 명세하거나. 후자는 사실상 불가능합니다.
