# DOS-RTS 엔진 명세 (normative)

파이썬 · 루아 · 타입스크립트 세 구현은 이 문서를 **정확히** 따른다.
어긋나면 골든 벡터가 즉시 틀어지도록 설계되어 있다.

명시적으로 "실수"라고 적지 않은 모든 연산은 **정수 연산**이다.
부동소수점이 허용되는 곳은 단 두 군데다.

* `tools/gen_prim.py` — 정수 루틴을 검증하기 위한 *독립* 참조 계산 (엔진 밖)
* `tools/gen_*.py` — 골든 데이터 생성기 (엔진 밖)

엔진 본체(`py/rts`, `lua/rts`, `ts/src`)에는 부동소수점 연산이 하나도 없다.
이 규율은 취향이 아니라 19부(락스텝)의 전제다. 부동소수점이 한 군데라도
섞이면 두 기계가 같은 명령을 먹고도 다른 상태에 도달할 수 있고, 그러면
동기 시뮬레이션 전체가 무너진다.

## 1. 정수 연산 규약

세 언어의 나눗셈·나머지·시프트 의미가 전부 다르다. 그래서 엔진은 아래 네 함수만 쓴다.
`/`, `//`, `%`, `>>`, `<<`, `&` 를 좌표나 고정소수점 값에 **직접 쓰지 않는다.**

```
floordiv(a, b)   b > 0 일 때, a/b 를 -무한대 방향으로 내림한 정수
fmod(a, b)       a - b * floordiv(a, b)   (항상 0 <= 결과 < b)
ashr(a, k)       floordiv(a, 2^k)
ashl(a, k)       a * 2^k
```

* 파이썬: `a // b`, `a % b` 가 이미 이 의미다.
* 루아 5.1: `math.floor(a / b)` — a, b 가 2^53 을 넘지 않아야 한다.
* 타입스크립트: `Math.floor(a / b)` — `>>` 는 32비트로 잘리므로 **금지**.

정수는 세 언어 모두 배정밀도 부동소수점(53비트 가수)에 정확히 담기는 범위,
즉 `|x| < 2^53` 안에서만 다룬다. 이 상계를 넘을 수 있는 곳은 §2.3(고정소수점 곱),
§3.1(LCG), §20.1(CRC), §18.4(FNV 해시) 네 곳이며 전부 분할 산술로 우회한다.

### 1.1 비트 연산의 대체

비트마스크(오토타일 8이웃, 안개 비트 플레인)는 **정수 산술로만** 다룬다.

```
bit(v, k)        fmod(floordiv(v, 2^k), 2)          k번째 비트 (0 또는 1)
setbit(v, k)     v + (1 - bit(v, k)) * 2^k          k번째 비트를 1로
clrbit(v, k)     v - bit(v, k) * 2^k                k번째 비트를 0으로
band8(a, b)      바이트 두 개의 AND — 8회 루프
```

루아 5.1 에는 비트 연산자가 없고(LuaJIT 의 `bit` 모듈은 LÖVE 에서도 쓸 수 있지만
Lua 5.1 표준이 아니다), 타입스크립트의 `&`·`|` 는 32비트로 잘린다. 산술로 쓰면
세 언어가 같은 코드 구조를 갖고, 32비트 경계 사고가 아예 생기지 않는다.
안개 비트 플레인처럼 성능이 걸리는 곳은 §14.2 에서 **바이트당 8칸** 대신
**칸당 1바이트**를 택했다 — 이유도 거기 적었다.

### 1.2 바이트 패킹

맵 한 칸은 두 배열에 나뉘어 있다. 한 배열에 비트로 우겨 넣지 않는다.

```
terrain[y * MAP_W + x]    0..255   지형 종류
pass[y * MAP_W + x]       0..255   통행 비트 (§4.3)
```

두 배열 모두 길이 `MAP_W * MAP_H = 4096` 의 1차원 정수 배열이다. 인덱스 식
`y * MAP_W + x` 는 세 언어에서 같고, 루아만 배열이 1-기반이므로 `+ 1` 을 한다.
이 `+ 1` 은 **접근자 함수 안에서 한 번만** 한다 — 호출자가 기억해야 하는 규칙을
만들면 반드시 어딘가에서 틀린다.

## 2. 고정소수점 — 모듈 `fixed`

### 2.1 표현

값 `x` 는 실수 `x / 65536` 을 뜻한다. 부호 있는 정수이며 범위는
`-2^31 <= x < 2^31` 로 제한한다(즉 실수 −32768.0 … 32768.0). 맵이 64타일 =
1024픽셀이므로 여유가 크다.

```
fp(n)        = n * 65536                 정수 → 고정소수점
fp_floor(x)  = floordiv(x, 65536)        고정소수점 → 정수 (내림)
fp_round(x)  = floordiv(x + 32768, 65536)
fp_frac(x)   = fmod(x, 65536)            항상 0 <= frac < 65536
```

`fp_floor` 가 내림(truncate 아님)인 것이 중요하다. 음수 좌표에서 truncate 를 쓰면
−0.5 와 +0.5 가 둘 다 0으로 가서 타일 경계 판정이 좌우 비대칭이 된다.

### 2.2 덧셈·뺄셈

그냥 `+`, `-` 다. 오버플로는 검사하지 않는다 — 범위 제한(§2.1)이 지켜지면
`|a| + |b| < 2^32` 라 세 언어 모두 정확하다.

### 2.3 곱셈 (분할 곱)

`fpmul(a, b) = floordiv(a * b, 65536)` 이 정의지만, `a * b` 는 최대 2^62 라
53비트 가수에 담기지 않는다. 그래서 **a 를 상·하위로 쪼갠다.**

```
ah = floordiv(a, 65536)          -- -32768 <= ah < 32768
al = fmod(a, 65536)              -- 0 <= al < 65536
fpmul(a, b) = ah * b + floordiv(al * b, 65536)
```

**정리 2.1.** 위 식은 `floordiv(a*b, 65536)` 과 항상 같다.

*증명.* `a = ah·2^16 + al` 이므로 `a·b = ah·b·2^16 + al·b`. 양변을 2^16 으로 나누고
바닥함수를 취하면 `⌊a·b/2^16⌋ = ah·b + ⌊al·b/2^16⌋` 이다. 첫 항이 정수이므로
바닥함수 밖으로 나올 수 있다. ∎

*크기.* `|ah·b| < 2^15 · 2^31 = 2^46`, `|al·b| < 2^16 · 2^31 = 2^47`.
둘 다 2^53 아래이므로 세 언어가 정확히 같은 값을 낸다.

### 2.4 나눗셈

```
fpdiv(a, b) = floordiv(a * 65536, b)          b != 0
```

`|a| < 2^31` 이므로 `|a * 65536| < 2^47` — 분할이 필요 없다. `b == 0` 은
호출자의 버그이며, 세 언어 모두 **즉시 실패**한다(파이썬 `ZeroDivisionError`,
루아 `error()`, 타입스크립트 `throw`). 조용히 0을 돌려주지 않는다.

### 2.5 정수 제곱근

```
isqrt(n)   n >= 0 인 정수에 대해 ⌊√n⌋
```

뉴턴 반복으로 구현하되 **초기값과 종료 조건을 명세로 고정**한다. 세 언어가
같은 횟수를 돌지 않아도 결과는 같지만, 성능 표(23부)를 비교하려면 같은
알고리즘이어야 한다.

```
if n < 2: return n
x = n
y = floordiv(x + 1, 2)
while y < x:
    x = y
    y = floordiv(x + floordiv(n, x), 2)
return x
```

**정리 2.2.** 위 반복은 `⌊√n⌋` 에서 멈춘다.

*증명 스케치.* `x > ⌊√n⌋` 인 동안 `f(x) = ⌊(x + ⌊n/x⌋)/2⌋ < x` 이므로 수열은
순감소한다. 정수 하한이 있으므로 유한 번에 멈춘다. 멈추는 지점 `x` 는
`f(x) >= x`, 즉 `⌊n/x⌋ >= x` 를 만족하므로 `x^2 <= n`. 순감소성에서
직전 값이 `> ⌊√n⌋` 였으므로 `x = ⌊√n⌋` 이다. ∎

`fp_sqrt(x) = isqrt(x * 65536)` — `|x| < 2^31` 이므로 `x * 65536 < 2^47`, 안전하다.

### 2.6 거리 척도

네 가지를 모두 갖춘다. 어느 것을 어디에 쓰는지가 이 덱의 6부 주제다.

```
d1(dx, dy)    = |dx| + |dy|                     L1, 맨해튼 — 4방향 이동
dinf(dx, dy)  = max(|dx|, |dy|)                 L∞, 체비셰프 — 8방향 이동, 사거리 판정
d83(dx, dy)   = mx + floordiv(3 * mn, 8)        옥타일 8분의 3 근사
doct(dx, dy)  = D_STRAIGHT * mx + (D_DIAG - D_STRAIGHT) * mn      경로 비용 단위
dab(dx, dy)   = floordiv(62943 * mx + 26072 * mn + 32768, 65536)  α-max β-min (반올림)
```

여기서 `mx = max(|dx|,|dy|)`, `mn = min(|dx|,|dy|)`.

* `dinf` 는 8방향 이동에서 **정확한** 이동 횟수다. 사거리 판정은 전부 이것을 쓴다.
* `d83` 은 √2−1 = 0.41421356… 을 3/8 = 0.375 로 바꾼 것이다. √2−1 의 연분수는
  `[0;2,2,2,…]` 이고 수렴분수는 1/2, 2/5, 5/12, 12/29, 29/70 … (펠 수의 비)이다.
  3/8 은 그 중 어느 것도 아니지만 8로 나누는 것이 시프트 세 번이라 도스 시절
  실제로 쓰였다. 45° 방향에서 참값 1.41421 대신 1.375 — **−2.8 %** 오차다.
* `doct` 는 A\*·JPS·다익스트라가 쓰는 **정수 비용**이다. 직선 10, 대각 14.
  14/10 = 1.4 이므로 √2 대비 −1.005 % 다. 이 비용 아래에서 JPS 가 A\* 와
  **정확히 같은 값**을 내는 것이 13부의 정리다.
* `dab` 은 α = 0.96043387, β = 0.39782473 을 16.16 으로 반올림한 것(62943, 26072)이다.
  최대 상대오차는 ±3.96 % 이며, `d83`(항상 과소평가)과 달리 오차가 0 을 중심으로
  흩어진다. 실측값은 `out/py_prim.txt` 1절에 있다.

  **마지막에 32768 을 더하는 것(반올림)이 없으면 안 된다.** 내림으로 두면
  `dab(1, 0) = ⌊62943/65536⌋ = 0` 이다. 거리 1 이 0 으로 나오고, 사거리 판정과
  타깃 선택이 통째로 무너진다. 이 버그는 골든 벡터를 처음 만들 때 오차 −100 % 로
  드러났다 — 6부에서 그 표를 그대로 싣는다.

**모든 거리 함수는 A\* 휴리스틱으로 쓸 수 있는가?** 아니다. 허용성(admissibility)이
필요하고, 그 증명은 §8.3 에 있다. `doct` 만 허용적이다.

### 2.7 8방향 판별 `atan8`

벡터 `(dx, dy)` 를 8방향 번호로 바꾼다. 화면 좌표계이므로 **y 는 아래로 증가**한다.

| 번호 | 이름 | (dx, dy) |
|---|---|---|
| 0 | N | (0, −1) |
| 1 | NE | (+1, −1) |
| 2 | E | (+1, 0) |
| 3 | SE | (+1, +1) |
| 4 | S | (0, +1) |
| 5 | SW | (−1, +1) |
| 6 | W | (−1, 0) |
| 7 | NW | (−1, −1) |

판별은 **비교만으로** 한다. 나눗셈도 삼각함수도 쓰지 않는다.

```
atan8(dx, dy):
    if dx == 0 and dy == 0: return 2          -- 규약: 정지 상태는 E 를 본다
    ax, ay = |dx|, |dy|
    mx, mn = max(ax, ay), min(ax, ay)
    diag = (12 * mn > 5 * mx)                 -- tan 22.5° ≈ 5/12
    ...(부호와 diag 로 8분면 결정, 구현은 py/rts/fixed.py 참조)
```

경계는 22.5° 이고 `tan 22.5° = √2 − 1 = 0.414214`. 5/12 = 0.416667 이므로
경계각은 22.62° — 참값보다 0.12° 넓다. 대각선 부채꼴이 0.24° 넓어진다는 뜻이며,
스프라이트 8방향에서는 눈에 보이지 않는다. `12·mn > 5·mx` 의 최대 크기는
`12 · 1024 = 12288` 로 어떤 언어에서도 안전하다.

**정지 상태를 E(2)로 두는 규약**은 임의의 선택이지만 명세다. 세 언어가 이걸
다르게 하면 스프라이트 방향이 갈리고, 그 갈림이 렌더 PPM 바이트 비교에서 잡힌다.

## 3. 난수 — 모듈 `rng`

### 3.1 LCG

볼랜드 C 계열 상수를 쓴다. 상태는 32비트 부호 없는 정수다.

**출처 주의(`claims.md` C22).** 승수 22695477 과 증분 1 은 여러 자료가 일치하지만,
모듈러스를 2^32 로 적는 자료와 2^31 로 적는 자료가 갈린다. 확실한 것은
`rand()` 가 돌려주는 것이 **상태의 비트 30..16**(15비트)이라는 서술이다.
이 엔진은 `m = 2^32`, 출력 비트 30..16 으로 고정하고, 덱은 이 갈림을 그대로 적는다.

```
s' = fmod(22695477 * s + 1, 4294967296)
next15(s) = fmod(floordiv(s', 65536), 32768)          -- 상위 15비트
```

`22695477 * s` 는 최대 2^24.4 · 2^32 = 2^56.4 로 **53비트를 넘는다.** 분할한다.

```
sh = floordiv(s, 65536)
sl = fmod(s, 65536)
lo = 22695477 * sl                    -- < 2^41
hi = fmod(22695477 * sh, 65536)       -- < 2^16
s' = fmod(lo + hi * 65536 + 1, 4294967296)
```

**정리 3.1.** 위 식은 `(22695477·s + 1) mod 2^32` 과 같다.

*증명.* `s = sh·2^16 + sl` 이므로 `22695477·s = 22695477·sl + 22695477·sh·2^16`.
두 번째 항을 2^32 로 나눈 나머지만 필요하므로 `22695477·sh` 의 하위 16비트,
즉 `(22695477·sh) mod 2^16` 만 살아남는다. ∎

**정리 3.2 (Hull–Dobell).** `x' = (a·x + c) mod m` 의 주기가 모든 초기값에서 m 인
필요충분조건은 (i) `gcd(c, m) = 1`, (ii) m 의 모든 소인수가 `a − 1` 을 나눔,
(iii) `4 | m` 이면 `4 | a − 1` 이다.
여기서 `m = 2^32`, `c = 1`, `a = 22695477 = 4·5673869 + 1`. (i) gcd(1, 2^32) = 1,
(ii) 유일한 소인수 2가 `a − 1 = 22695476 = 4·5673869` 를 나눔, (iii) 4 | 22695476.
셋 다 만족하므로 주기는 정확히 2^32 다.

**하위 비트의 함정.** `s mod 2^k` 의 주기는 2^k 다. 즉 최하위 비트는 0,1,0,1… 을
반복한다. 그래서 `next15` 는 **상위 15비트만** 쓴다. 7부에서 두 방식을
비트 평면으로 나란히 그려 보인다.

### 3.2 범위 난수 (모듈로 편향 제거)

```
roll(n):                              -- 0 <= 결과 < n,  1 <= n <= 32768
    if n <= 1: return 0
    limit = 32768 - fmod(32768, n)
    repeat:
        r = next15()
    until r < limit
    return fmod(r, n)
```

**정리 3.3.** `roll(n)` 은 0…n−1 위의 균등분포다.

*증명.* `next15` 가 0…32767 위 균등이라 가정한다. `limit = ⌊32768/n⌋·n` 이므로
`r < limit` 인 값은 각 잔여류마다 정확히 `⌊32768/n⌋` 개다. 조건부 분포는 균등이고,
기각 확률은 `(32768 − limit)/32768 < n/32768 <= 1/2` 이므로 기대 시도 횟수는 2 미만이다. ∎

기각 루프는 **결정론적**이다. 같은 시드에서 같은 횟수를 돈다. 이것이 락스텝에서
중요하다 — 두 기계가 난수를 서로 다른 횟수로 뽑으면 그 뒤로 모든 것이 갈린다.

### 3.3 시뮬레이션 RNG 는 하나뿐

`sim` 은 RNG 인스턴스를 **정확히 하나** 갖는다(`sim.rng`). 렌더·UI·AI 표시용
난수는 존재하지 않는다. 맵 생성기만 별도 인스턴스(`mapgen.rng`)를 쓰며, 그것은
게임 시작 전에 끝난다. 이 규칙을 어기면 관전자 클라이언트 하나가 시뮬을
어긋나게 만들 수 있다 — 19부의 실험이 정확히 그 사고를 재현한다.

## 4. 지형 맵 — 모듈 `tmap`

### 4.1 지형표

| 값 | 이름 | 통행 | 건설 | 자원 | 미니맵 색 |
|---|---|---|---|---|---|
| 0 | 모래 `SAND` | 예 | 예 | — | 216 |
| 1 | 바위 `ROCK` | 아니오 | 아니오 | — | 220 |
| 2 | 물 `WATER` | 아니오 | 아니오 | — | 232 |
| 3 | 흙 `DIRT` | 예 | 예 | — | 214 |
| 4 | 광맥 `ORE` | 예 | 아니오 | 예 | 240 |
| 5 | 언덕 `HILL` | 예 | 아니오 | — | 218 |
| 6 | 잔해 `RUBBLE` | 예 | 예 | — | 222 |
| 7 | 도로 `ROAD` | 예 | 예 | — | 226 |

지형은 8종뿐이다. 늘리고 싶으면 `terrain` 바이트에 여유가 248개 남아 있지만,
오토타일 전이 표(§4.4)가 종류의 제곱으로 커지므로 8에서 멈췄다.

### 4.2 좌표

```
idx(x, y)     = y * MAP_W + x
in_map(x, y)  = 0 <= x < MAP_W and 0 <= y < MAP_H
```

맵 밖은 **`ROCK` 으로 간주**한다(`terrain_at` 이 경계 밖에서 1을 돌려준다).
경계 검사를 호출자가 하지 않아도 되고, 오토타일 마스크가 맵 가장자리에서
자연스럽게 닫힌다.

### 4.3 통행 비트

`pass[i]` 는 지형에서 파생된 값이 아니라 **별도로 유지되는 상태**다. 건물이
서면 그 칸이 막히고, 부서지면 다시 열리기 때문이다.

| 비트 | 값 | 뜻 |
|---|---|---|
| 0 | 1 | 보병 통행 가능 |
| 1 | 2 | 차량 통행 가능 |
| 2 | 4 | 건설 가능 |
| 3 | 8 | 점유됨(건물 또는 유닛이 서 있음) |

`walkable(x, y, kind)` 는 `bit(pass[i], kind) == 1 and bit(pass[i], 3) == 0` 이다.
`kind` 는 0(보병) 또는 1(차량). 둘의 차이는 하나뿐이다 — **차량은 언덕(`HILL`)에
올라가지 못한다.** 지형 한 줄로 두 종류의 통행 그래프가 갈리고, 그래서
연결 성분(§4.6)도 두 벌이 필요하다. 경로 탐색은 점유 비트를 **보지 않는다** —
움직이는 유닛 때문에 경로가 매 틱 흔들리면 무리 이동이 무너진다. 점유는
§13 의 예약 규칙이 국소적으로 처리한다.

**건물은 다르다.** 건물이 서면 그 칸의 보병·차량 비트를 **내리고** 점유 비트를
세운다(`set_building`). 유닛과 달리 건물은 비키지 않으므로 경로 탐색이 처음부터
돌아가야 한다 — 예약만으로 막으면 유닛이 벽을 향해 24틱을 두드리다 포기한다
(§13.3). 건물이 부서지면 그 칸을 `RUBBLE` 로 바꾸는 것만으로 §4.1 의 통행표에서
비트가 복구된다.

### 4.4 오토타일 — 8이웃 비트마스크

같은 지형끼리 이어 붙일 때, 한 칸이 어떤 그림을 쓸지는 **이웃 8칸이 나와 같은가**
로 결정된다. 방향 번호(§2.7)를 그대로 비트 번호로 쓴다.

```
mask(x, y) = Σ over d in 0..7 of  2^d  if  same(x + dx[d], y + dy[d])
```

`same(u, v)` 는 `terrain_at(u, v) == terrain_at(x, y)` 다(맵 밖은 ROCK).

마스크는 256가지지만 **그림은 47가지면 충분하다.**

**정리 4.1.** 모서리 이웃 `c` 는 그 양옆의 변 이웃 두 개가 모두 같을 때만
그림에 영향을 준다. 이 규칙으로 정규화한 마스크는 정확히 **47가지**다.

*이유.* 변 이웃 하나라도 다르면 그 방향에 이미 경계선이 그려지고, 모서리 칸의
상태는 그 선에 가려 보이지 않는다. 정규화 함수는

```
canon(m):  for c in {NE, SE, SW, NW}:
               if not (bit(m, a) and bit(m, b)): m = clrbit(m, c)
           return m
```

여기서 (a, b) 는 c 의 양옆 변 방향이다. `canon` 의 상은 47원소 집합이며,
전수 확인은 `tools/gen_autotile.py` 가 256개 전부를 돌려 증명한다.

**정리 4.2.** 47개 클래스는 정사각형의 대칭군 D₄(회전 4 × 반사 2 = 8원소) 아래에서
**14개 궤도**로 떨어진다. 궤도 크기는 1, 1, 1, 2, 2, 4, 4, 4, 4, 4, 4, 4, 4, 8 이다.

그래서 도스 시절 아티스트는 47장을 다 그리지 않았다. **14장을 그리고 회전·반사**했다.
`tools/gen_autotile.py` 가 궤도 대표원소와 각 클래스를 얻는 변환을 표로 낸다.

### 4.5 4모서리 변형 (마칭 스퀘어)

타일 *중심*이 아니라 *꼭짓점*에 값을 두는 방식이다. 한 타일은 네 꼭짓점의
0/1 조합 → **16가지**. 등고선의 마칭 스퀘어와 같은 표이며, 4부에서 47-케이스와
나란히 비교한다. 이 엔진은 도로(`ROAD`)에만 16-케이스를 쓴다.

```
corner_mask(x, y) = v(x,y) + 2*v(x+1,y) + 4*v(x+1,y+1) + 8*v(x,y+1)
```

### 4.6 연결 성분 (유니온–파인드)

보병용·차량용 각각 한 벌씩, 맵 전체의 통행 가능 칸을 4방향이 아니라
**8방향**으로 묶는다(대각 이동이 있으므로).

```
find(a)      경로 압축
union(a, b)  랭크 합병
label[i]     대표 원소 인덱스
```

경로 탐색 전에 `label[start] != label[goal]` 이면 **A\* 를 아예 시작하지 않는다.**
도달 불가능한 목표에 대해 A\* 는 맵 전체를 훑고서야 실패하므로, 이 한 줄 검사가
최악의 경우를 없앤다(§8.6 의 "가장 가까운 도달점" 규칙으로 이어진다).

라벨은 지형이 바뀔 때(건물 완공·파괴) **전부 다시 계산**한다. 증분 삭제가 가능한
유니온–파인드는 복잡하고, 4096칸 재계산은 측정상 1 ms 미만이다(실측은
`out/bench.txt` 5절).

### 4.7 RLE 맵 파일

```
헤더:  "RTSM" 4바이트 · 버전 1 · MAP_W · MAP_H            (각 1바이트)
본문:  (count, value) 쌍의 나열. count 는 1..255.
        terrain 평면 먼저, 그다음 pass 평면.
꼬리:  CRC-16/CCITT-FALSE (§20.1) 2바이트, 빅 엔디언
```

`count == 0` 은 나타나지 않는다. 256칸 이상 이어지면 255씩 끊는다.

## 5. 맵 생성 — 모듈 `mapgen`

세 가지 생성기를 갖추고, 골든 맵은 그중 두 개를 쓴다.

### 5.1 셀룰러 오토마타 (동굴·바위밭)

```
1) 각 칸을 확률 45 % 로 바위로 채운다:  wall = (roll(100) < 45)
2) 4세대 반복:
       w = 8이웃 중 바위 개수 (맵 밖은 바위)
       next = 1 if (cur == 1 and w >= 4) or (cur == 0 and w >= 5) else 0
3) 유니온–파인드로 가장 큰 통행 성분만 남기고 나머지는 바위로 메운다.
```

규칙 이름으로는 **B5678/S45678** 이다. 2세대면 덩어리가 덜 뭉치고, 6세대면
좁은 통로가 전부 막힌다 — 4세대가 이 맵 크기에서 통로와 개활지가 함께 남는
자리다. 세대별 스냅샷은 7부에 실린다.

**고정점.** 완전히 채워진 판과 완전히 빈 판은 모두 이 규칙의 고정점이다.
그래서 초기 밀도 45 % 가 중요하다 — 55 % 로 시작하면 4세대 안에 전부 바위가 된다.

### 5.2 다이아몬드-스퀘어

`(2^6)+1 = 65` 칸 격자에서 돌리고, 왼쪽 위 64×64 를 잘라 쓴다.

```
h[0][0], h[0][64], h[64][0], h[64][64] = 시드 4개 (0..255)
step = 64
while step > 1:
    half = floordiv(step, 2)
    다이아몬드: 각 정사각형의 중앙 = 네 꼭짓점 평균 + jitter(step)
    스퀘어:     각 마름모의 중앙 = 상하좌우 평균(맵 밖은 건너뜀) + jitter(step)
    step = half
jitter(step) = roll(2 * amp + 1) - amp,   amp = floordiv(step * 255, 128)
```

평균은 `floordiv(합, 개수)` 다. 반올림이 아니라 내림이며, 세 언어가 같아야 하므로
명세로 못 박는다. 결과 높이는 0..255 로 자른다(`clamp`).

**임계값으로 지형 배정:**

| 높이 | 지형 |
|---|---|
| 0 … 63 | `WATER` |
| 64 … 95 | `SAND` |
| 96 … 175 | `DIRT` |
| 176 … 207 | `HILL` |
| 208 … 255 | `ROCK` |

### 5.3 정수 포아송 디스크 (자원 배치)

```
place_ore(n, rmin):
    pts = []
    tries = 0
    while len(pts) < n and tries < 4000:
        tries += 1
        x, y = roll(MAP_W), roll(MAP_H)
        if terrain is not DIRT and not SAND: continue
        if any (dx*dx + dy*dy < rmin*rmin) for p in pts: continue
        pts.append((x, y))
    각 점 주위에 반경 2 원 마스크(§6)로 ORE 를 찍는다
```

거리 판정에 제곱근을 쓰지 않는다 — `dx² + dy² < rmin²` 로 충분하다.
`rmin = 9`, `n = 12` 가 기본값이며, `tries` 상한은 결정론을 위해 반드시 필요하다
(상한이 없으면 배치 실패 시 무한 루프가 되고, 그건 디싱크보다 나쁘다).

### 5.4 2회 대칭 맵

대전 맵은 공평해야 한다. 왼쪽 위 절반만 생성하고 **180° 회전 복사**한다.

```
mirror(x, y) = (MAP_W - 1 - x, MAP_H - 1 - y)
```

시작 지점은 `(8, 8)` 과 그 상 `(55, 55)` 다. 두 지점 사이에 보병 경로가 없으면
그 시드는 버리고 다음 시드로 넘어간다(`gen_map` 은 시드를 1씩 올리며 재시도).
골든 맵은 이 재시도가 몇 번 일어났는지까지 `out/` 에 남긴다.

## 6. 원 마스크 — 모듈 `circle`

시야·스플래시·자원 스탬프가 전부 이걸 쓴다.

### 6.1 정의

```
disc(r) = { (x, y) : x² + y² <= r² }        r = 1..8
```

**정리 6.1.** `|disc(r)|` 은 가우스 원 문제의 격자점 개수 N(r) 이며
r = 1…8 에 대해 **5, 13, 29, 49, 81, 113, 149, 197** 이다.

이 여덟 숫자는 `main prim` 이 출력하고 골든과 대조된다. 원을 잘못 그리면
개수가 반드시 달라지므로, 이 한 줄이 래스터라이저 전체의 검산이 된다.

### 6.2 행 span 계산 — 곱셈도 제곱근도 없이

행 `j` 의 최대 `|i|` 를 `span[j]` 라 하자. 덧셈과 뺄셈만으로 구한다.

```
disc_spans(r):
    x, t = r, 0                     -- 불변식: t = r² − j² − x²
    span[0] = r
    for j = 1 .. r:
        t -= 2 * (j - 1) + 1        -- j² 가 2(j−1)+1 만큼 커진다
        while t < 0:
            t += 2 * x - 1          -- x² 가 2x−1 만큼 작아진다
            x -= 1
        span[j] = x
    return span
```

**정리 6.2.** 매 `j` 마다 `span[j] = ⌊√(r² − j²)⌋` 이다. 따라서
`{ (i, j) : |i| <= span[|j|] }` 는 §6.1 의 `disc(r)` 과 정확히 같은 집합이다.

*증명.* 불변식은 "`t = r² − j² − x² >= 0` 이고 `x` 는 `x² <= r² − j²` 를 만족하는
최대값"이다. `j = 0` 에서 `x = r`, `t = 0` 으로 성립한다. `j` 가 1 늘면 `j²` 이
`2(j−1)+1` 만큼 커지므로 `t` 가 그만큼 줄고, 음수가 되었다면 `x` 를 하나씩 줄이며
`t` 에 `2x−1` 을 되돌린다. 처음으로 `t >= 0` 이 되는 지점에서 멈추므로 `x` 는
여전히 최대값이다. `x` 는 결코 늘지 않으므로 전체 비용은 O(r) 이다. ∎

**고전 미드포인트 원 알고리즘은 이 답을 주지 않는다.** Bresenham(1977)의 미드포인트
원은 *외곽선*을 그리는 알고리즘이고, 그것이 고르는 픽셀은 참원에 가장 가까운 점이지
반드시 원 *안*의 점이 아니다. `r = 2` 에서 그 알고리즘은 `(2, 1)` 을 찍는데
`2² + 1² = 5 > 4` 이므로 원 밖이다. 시야 마스크로 그대로 쓰면 격자점 개수가
가우스 원 문제의 값(§6.1)과 어긋난다.

이 차이는 **처음 골든을 만들 때 검사가 잡아냈다.** 6부는 두 집합을 겹쳐 그려
어느 칸이 다른지 보인다. `py/tests/test_circle.py` 는 r = 1…64 에 대해
`disc_spans` 와 정의를 **전수 비교**한다 — 정리보다 전수 검사가 짧고,
무엇보다 반증 가능하다.

### 6.3 마스크 형식

세 언어가 같은 순서로 순회해야 하므로 오프셋 목록을 **정렬해 고정**한다.

```
offsets(r) = [(dx, dy) …]   dy 오름차순, 같은 dy 안에서 dx 오름차순
```

시야 계산은 이 목록을 그대로 돌며 참조 카운트를 올린다(§14). 순서가 다르면
카운트 결과는 같지만, 이벤트 로그의 순서가 달라져 상태 해시가 갈린다.

### 6.4 시야에는 시선 판정이 없다

이 엔진의 시야는 **반경 원 마스크뿐**이다. 벽 뒤가 보인다. 도스 RTS 대부분이
그랬고(Dune II·C&C·WC2 모두 시야에 시선 차단이 없다 — 2부의 고증 항목),
무엇보다 참조 카운트 안개(§14.3)의 증분 갱신이 성립하려면 시야 집합이
**위치만의 함수**여야 하기 때문이다. 시선 차단을 넣으면 지형이 바뀔 때마다
모든 유닛의 시야를 다시 계산해야 한다.

## 7. 엔티티와 공간 분할 — 모듈 `spatial`

### 7.1 배열 구조 (SoA)

엔티티는 **구조체의 배열이 아니라 배열의 구조체**로 둔다. 길이는 전부 `MAX_ENT`.

```
alive[i]   0/1        gen[i]     0..255      세대
owner[i]   0..3       kind[i]    유닛/건물 종류 번호
tx[i]      타일 x     ty[i]      타일 y        (건물은 좌상단)
px[i]      16.16 x    py[i]      16.16 y       (뷰포트 픽셀 좌표)
hp[i]      정수       dir[i]     0..7
state[i]   FSM 상태   target[i]  핸들 또는 0
```

세 언어에서 같은 이름의 평행 배열을 쓴다. 루아에서 테이블 하나에 필드를 담으면
가비지가 늘고, 타입스크립트에서 객체 배열을 쓰면 히든 클래스가 갈린다.
무엇보다 **직렬화 순서가 배열 순서로 자동으로 고정**되는 것이 크다 —
상태 해시(§18.4)가 언어별 필드 순서에 영향을 받지 않는다.

### 7.2 핸들 = 인덱스 + 세대

```
handle(i)   = i * 256 + gen[i]                 0 은 "없음"을 뜻하므로 쓰지 않는다
index(h)    = floordiv(h, 256)
valid(h)    = h != 0 and alive[index(h)] == 1 and fmod(h, 256) == gen[index(h)]
```

엔티티가 죽으면 `gen[i] = fmod(gen[i] + 1, 256)` 로 올린다. 슬롯이 재사용되어도
옛 핸들은 `valid` 를 통과하지 못한다. 이것이 없으면 "죽은 유닛을 계속 쫓는
미사일"류 버그가 생기고, 그 버그는 락스텝에서 디싱크로 나타난다.

`gen` 은 0 에서 시작하며, `handle` 이 0 이 되지 않도록 **슬롯 0 은 쓰지 않는다**
(`i` 는 1..255). 이 한 칸을 버리는 대가로 "없음"을 0 하나로 표현한다.

### 7.3 균일 격자 버킷

```
BUCKET = 8                     버킷 한 변 (타일)
BW = floordiv(MAP_W, 8) = 8    가로 버킷 수
bucket_of(tx, ty) = floordiv(ty, 8) * BW + floordiv(tx, 8)
```

버킷은 64개, 각 버킷은 엔티티 인덱스의 목록이다. 유닛이 타일을 넘을 때만
버킷을 갱신한다(픽셀 이동마다가 아니다).

`query(tx, ty, r)` 는 `(tx±r, ty±r)` 이 걸치는 버킷들만 훑는다. `r <= 8` 이면
최대 4개 버킷이다. 유닛 256개가 고르게 퍼져 있으면 버킷당 4개이므로
질의당 후보 16개 — 전수 검사(256개) 대비 16배다. 실측은 `out/bench.txt` 2절.

버킷 안의 목록은 **인덱스 오름차순을 유지**한다. 삽입은 선형 탐색이지만 목록이
짧고, 무엇보다 순회 순서가 결정론적이어야 한다. 순서가 흔들리면 "가장 가까운 적"
타이브레이크가 갈리고 그대로 디싱크가 된다.

## 8. 경로 탐색 I — 모듈 `path`

### 8.1 이동 그래프

8방향, 비용은 `D_STRAIGHT = 10`(직선) / `D_DIAG = 14`(대각).

**코너 컷 규칙: 허용한다.** 대각 이동 `(dx, dy)` 는 도착 칸이 통행 가능하면
legal 이다. 양옆 칸이 막혀 있어도 통과한다.

이것은 **선택**이며, 세 가지 이유로 이렇게 정했다.

1. JPS(§10)의 가지치기 규칙은 코너 컷을 허용하는 격자 위에서 정의되어 있다.
   금지하면 강제 이웃(forced neighbour) 조건이 통째로 달라지고, "JPS 의 비용이
   A\* 와 같다"는 정리도 다시 증명해야 한다. 13부에서 그 반례를 직접 그린다.
2. 흐름장(§11)과 HPA\*(§9)도 같은 격자를 써야 세 방법의 비용을 비교할 수 있다.
3. 도스 시절 구현 상당수가 도착 칸만 검사했다. 다만 이것을 고증 주장으로 쓰지는
   않는다 — 덱에서는 **"이 덱의 규칙"**이라고 적는다.

대가는 정직하게 적는다. 바위 두 개가 대각으로 놓인 틈을 유닛이 스쳐 지나간다.
벽으로 길을 막는 전술이 성립하지 않는다. 14부에서 화면으로 보인다.

### 8.2 옥타일 휴리스틱

```
h(a, b) = 10 * mx + 4 * mn        mx = max(|dx|,|dy|),  mn = min(|dx|,|dy|)
```

`14 − 10 = 4` 이므로 `doct`(§2.6)와 같은 식이다.

**정리 8.1 (허용성).** 어떤 경로든 비용이 `h` 이상이다.

*증명.* 직선 이동 s 회, 대각 이동 d 회로 이루어진 경로를 보자. 한 번의 이동이
`max(|dx|,|dy|)` 를 1 이상 줄이지 못하므로 `s + d >= mx`. 또 한 번의 이동이
`|dx| + |dy|` 를 2 이상 줄이지 못하므로 `s + 2d >= mx + mn`.
두 부등식에 각각 6과 4를 곱해 더하면

```
6(s + d) + 4(s + 2d) = 10s + 14d >= 6·mx + 4·(mx + mn) = 10·mx + 4·mn = h
```

좌변이 정확히 경로 비용이다. ∎

계수 6, 4 는 우연이 아니다. `λ + μ <= 10`, `λ + 2μ <= 14` 를 만족하면서
`λ·mx + μ·(mx+mn)` 을 최대로 하는 선형계획의 해가 `(λ, μ) = (6, 4)` 다.

### 8.3 일관성

**정리 8.2.** `h` 는 일관적(consistent)이다: 인접한 두 칸 `n`, `n'` 에 대해
`h(n) <= c(n, n') + h(n')`.

*증명.* `h` 자체가 옥타일 거리이고 옥타일 거리는 삼각부등식을 만족한다.
한 걸음의 비용 `c(n,n')` 는 그 걸음의 옥타일 거리와 같다(직선 10, 대각 14).
따라서 `h(n) <= d_oct(n, n') + h(n') = c(n,n') + h(n')`. ∎

일관적이므로 A\* 는 닫힌 목록에 들어간 노드를 **다시 열 필요가 없다.**
재개방(reopening) 코드를 아예 넣지 않았고, 그 근거가 이 정리다.

### 8.4 다익스트라 — 양동이 큐 (Dial)

간선 비용이 10 과 14 두 개뿐이므로 이진 힙이 필요 없다.

```
버킷 개수 NB = D_DIAG + 1 = 15                  (최대 간선 비용보다 커야 한다)
bucket[fmod(dist, 15)] 에 노드를 넣는다
cur 를 0 부터 올리며 빈 버킷을 건너뛴다
```

**정리 8.3.** 처리 중인 최소 거리 `cur` 와 새로 갱신되는 거리 `nd` 는 항상
`cur <= nd < cur + 15` 를 만족한다. 따라서 원형 버킷 15개로 충돌 없이 표현된다.

*증명.* `nd = dist[u] + c` 이고 `dist[u] = cur`, `10 <= c <= 14` 이므로
`cur + 10 <= nd <= cur + 14`. ∎

낡은 항목(더 짧은 거리가 이미 확정된 노드)은 꺼낼 때 `dist` 와 비교해 버린다.
감소키(decrease-key)를 구현하지 않는다.

### 8.5 A\*

같은 양동이 큐를 `f = g + h` 위에서 쓴다. `h` 의 최댓값은
`10 · 63 + 4 · 63 = 882` 이고 `f` 는 단조 증가하지 않을 수 있으므로
**A\* 는 이진 힙을 쓴다.** 힙 비교자는

```
(f, h, idx) 사전식 오름차순
```

`h` 로 타이브레이크하면 목표에 더 가까운 노드를 먼저 펴서 확장 수가 줄고,
마지막 `idx` 는 **완전한 결정론**을 위한 것이다. 세 언어의 정렬 안정성이
다르므로 비교자가 전순서여야 한다.

힙은 손으로 구현한다(`sift_up`/`sift_down`). 파이썬 `heapq`, 루아 `table.sort`,
타입스크립트 `Array.sort` 는 서로 다른 순서를 낼 수 있다.

### 8.6 도달 불가 목표

```
if label(start) != label(goal):
    goal = 같은 성분 안에서 목표에 가장 가까운 칸 (d83 최소, 동점이면 idx 최소)
```

성분 라벨(§4.6)로 먼저 거른다. 대체 목표를 찾는 것은 그 성분의 칸을 전수
훑는 것이며 4096칸이므로 충분히 빠르다. 이 규칙이 없으면 "섬 건너편 클릭"
한 번이 A\* 에게 맵 전체를 펴게 만든다.

### 8.7 경로 캐시

```
키:   (start_idx, goal_idx, kind)
값:   타일 인덱스 목록
정책: 64칸 LRU. 지형이 바뀌면 통째로 비운다.
```

LRU 순서는 상태의 일부가 **아니다** — 캐시는 같은 답을 더 빨리 줄 뿐이므로
상태 해시에 넣지 않는다. 다만 캐시가 낡은 답을 주면 그건 디싱크다. 그래서
지형 변경(건물 완공·파괴·잔해)에서 **무조건 전체 무효화**한다. 적중률 실측은
`out/bench.txt` 4절에 있다.

## 9. 계층 경로 탐색 — 모듈 `hpa`

Botea–Müller–Schaeffer(2004)의 HPA\* 를 2수준으로 구현한다.

### 9.1 클러스터

맵을 `CLUSTER = 8` 타일 정사각형으로 나눈다 → 8 × 8 = **64개 클러스터**.

### 9.2 입구(entrance)와 전이(transition)

이웃한 두 클러스터가 맞닿은 변을 훑어, **양쪽이 모두 통행 가능한 칸쌍**의
최대 연속 구간(run)을 찾는다.

```
run 길이 <= 5 : 구간 중앙 한 곳에 전이를 만든다        (중앙 = floordiv(a + b, 2))
run 길이 >  5 : 구간의 양 끝 두 곳에 전이를 만든다
```

전이는 추상 그래프의 **노드 두 개**(양쪽 클러스터에 하나씩)와 비용 `D_STRAIGHT`
인 간선 하나를 만든다.

### 9.3 클러스터 내부 간선

한 클러스터에 속한 노드들끼리, 그 클러스터 **안에서만** A\* 를 돌려 비용을 잰다.
도달 불가면 간선을 만들지 않는다. 8×8 안에서의 A\* 이므로 최악 64칸이다.

### 9.4 질의

```
1) 출발·도착 칸을 각자의 클러스터에 임시 노드로 삽입 (내부 간선 계산)
2) 추상 그래프에서 A* (휴리스틱은 §8.2 를 타일 좌표에 그대로 적용)
3) 임시 노드를 제거
4) 정련: 추상 경로의 인접 노드 쌍마다 클러스터 안 A* 로 실제 타일 열을 얻는다
```

**HPA\* 는 최적이 아니다.** 원 논문은 실측 기준 최적 대비 1 % 안팎을 보고하지만,
그 수치는 논문의 맵·클러스터 크기에서 나온 것이다. 이 엔진의 값은
**골든 맵 6장에서 직접 측정해** `out/py_prim.txt` 8절에 적고, 덱은 그 숫자만 쓴다.
"1 % 이내"라고 옮겨 적지 않는다.

정련을 하지 않은 추상 경로만으로 유닛을 움직이면 클러스터 경계마다 꺾인다.
정련을 매 클러스터 통과 직전에 lazy 하게 하는 것이 원 논문의 요령이며,
이 엔진도 그렇게 한다(`hpa.refine_next`).

## 10. 점프 포인트 탐색 — 모듈 `jps`

Harabor–Grastien(2011). 격자의 **대칭 경로**를 가지치기해 A\* 가 여는 노드 수를
줄인다. 비용은 A\* 와 **정확히 같다**.

### 10.1 가지치기 규칙 (코너 컷 허용 격자)

`p` 를 방향 `d` 로 도달한 노드라 하자.

**직선 이동** `d = (dx, 0)`:
* 자연 이웃: `(x+dx, y)`
* 강제 이웃: `t ∈ {−1, +1}` 에 대해 `(x, y+t)` 가 막혀 있고 `(x+dx, y+t)` 가
  열려 있으면 `(x+dx, y+t)` 는 강제 이웃이다.

**대각 이동** `d = (dx, dy)`:
* 자연 이웃: `(x+dx, y)`, `(x, y+dy)`, `(x+dx, y+dy)`
* 강제 이웃: `(x−dx, y)` 가 막혀 있으면 `(x−dx, y+dy)`,
  `(x, y−dy)` 가 막혀 있으면 `(x+dx, y−dy)`

### 10.2 점프

```
jump(p, d):
    n = p + d
    if n 이 막혀 있거나 맵 밖: return 없음
    if n == goal: return n
    if n 에 강제 이웃이 있다: return n
    if d 가 대각: 
        for 성분 방향 d1, d2 in {(dx,0), (0,dy)}:
            if jump(n, d1) 이 있으면: return n
    return jump(n, d)
```

대각 점프가 먼저 두 성분 방향을 재귀적으로 훑는 것이 핵심이다. 그 방향에서
점프점이 나오면 **현재 대각 칸 자체가** 점프점이 된다.

### 10.3 A\* 와의 등가

**정리 10.1.** 코너 컷을 허용하는 균일 비용 8방향 격자에서 JPS 가 찾은 경로의
비용은 A\* 의 최적 비용과 같다.

*증명 방침.* 가지치기된 이웃 `n` 에 대해 항상 같은 비용의 대체 경로가 `p` 를
지나지 않고 존재한다(대칭 경로). 따라서 최적해 하나는 반드시 점프점만을 거치는
형태로 다시 쓸 수 있다. 자세한 논증은 원 논문 정리 1–3 에 있다.

*이 저장소의 증명.* 정리를 옮겨 적는 대신 **전수 검사**한다.
`py/tests/test_jps.py` 는 골든 맵 6장의 모든 통행 가능 칸 쌍
(맵당 최대 4096² 이 아니라, 각 맵에서 고정된 200쌍을 시드로 뽑아)에 대해
A\* 비용과 JPS 비용을 비교한다. 한 건이라도 다르면 실패한다.
검사한 쌍의 수와 결과는 `out/py_tests.txt` 에 남는다.

### 10.4 무엇이 줄어드나

JPS 는 **연 노드 수**를 줄이지 확장 비용을 줄이지 않는다. 점프 자체가 격자를
훑기 때문이다. 13부는 두 방법의 (연 노드 수, 훑은 칸 수, 실제 시간)을 셋 다
`out/bench.txt` 3절에서 가져와 나란히 놓는다. 파이썬에서는 JPS 가 오히려
느릴 수 있다 — 그 결과가 나오면 그대로 싣는다.

## 11. 흐름장과 클리어런스 — 모듈 `flow`

### 11.1 적분장 (integration field)

목표 집합 `G` 에서 **역방향 다익스트라**를 돌려 모든 칸의 비용을 채운다.
양동이 큐(§8.4)를 그대로 쓴다.

```
integ[i] = G 의 어느 칸까지의 최소 비용,  도달 불가면 INF = 65535
```

`INF` 는 65535 로 **고정**한다. §8.4 의 다익스트라는 INF 가 그냥 "큰 수"이면
되지만 적분장은 덱 그림과 골든 표에 그대로 찍히므로 세 언어가 같은 수를 내야
한다. 목표가 통행 불가 칸이면 그 목표는 **무시**한다 — 닿을 수 없는 목표를
0 으로 심으면 장 전체가 그 칸 쪽으로 기울고, 그 유혹은 §8.6 의 대체 목표가
막아야 할 몫이다. 목표가 하나도 남지 않으면 전체가 INF 다.

한 번 계산하면 **유닛 수와 무관하게** 모든 유닛이 같은 장을 읽는다.
유닛 40기가 같은 곳으로 갈 때 A\* 40번 대신 다익스트라 1번이다. 그 손익분기를
`out/bench.txt` 3절에서 실측한다.

### 11.2 경사장 (flow field)

```
flow[i] = argmin over d in 0..7 of integ[i + step(d)]
          동점이면 d 가 작은 쪽 (§2.7 의 방향 번호)
```

경계 밖·막힌 칸·`integ` 가 INF 인 칸은 후보에서 제외한다. 후보가 없으면
`flow[i] = 255`(정지). 막힌 칸과 INF 칸 자신도 255 다.

동점 규칙이 명세인 이유: 대칭적인 맵에서는 동점이 흔하고, 언어별 `min` 구현이
동점을 다르게 처리하면 유닛 무리가 좌우로 갈린다. 그 갈림은 화면에서 바로 보이고
PPM 바이트 비교에서 잡힌다.

### 11.3 클리어런스 (정사각 여유)

2×2 크기 유닛이 지나갈 수 있는지 알아야 한다.

```
clear[x][y] = 0                                     막힌 칸
            = 1 + min(clear[x+1][y], clear[x][y+1], clear[x+1][y+1])   그 외
```

맵 밖은 0 으로 본다. 그래서 오른쪽·아래 가장자리의 자유 칸은 1 이 된다.
오른쪽 아래부터 한 번 훑으면 끝난다 — O(맵) 이다.

**정리 11.1.** `clear[x][y]` 는 `(x, y)` 를 좌상단으로 하는 **모두 통행 가능한
정사각형의 최대 변 길이**와 같다.

*증명.* 귀납. `k × k` 정사각형이 `(x,y)` 에 놓이려면 `(x+1,y)`, `(x,y+1)`,
`(x+1,y+1)` 각각에 `(k−1) × (k−1)` 이 놓여야 하고, 역도 성립한다. ∎

크기 `s` 인 유닛은 `clear[i] >= s` 인 칸만 통행 가능한 것으로 보고 경로를 찾는다.

### 11.4 브러시파이어 (장애물까지의 거리)

모든 막힌 칸을 거리 0 으로 놓고 다중 시작점 다익스트라(같은 10/14 비용)를 돌린다.

```
fire[i] = 가장 가까운 막힌 칸까지의 옥타일 비용,  막힌 칸이면 0
```

두 가지를 명세로 못박는다. 첫째, **맵 밖은 막힌 칸이다**(§4.2 의 `terrain_at`
규약과 같다). 그래서 가장자리 자유 칸의 `fire` 는 10 이고, AI 는 맵 끝에
건물을 붙이지 않는다. 둘째, 확장은 **통행 가능한 칸으로만** 들어간다 — 막힌
칸끼리 이어 버리면 두꺼운 바위 덩어리를 가로질러 반대편 자유 칸까지 0 이
새어 나간다.

AI 의 건물 배치(§17.4)와 "벽에서 떨어져 걷기" 가중치에 쓴다.

## 12. 선택과 명령 — 모듈 `select`

### 12.1 픽킹

마우스 한 점 `(sx, sy)` 가 어느 엔티티를 가리키는가.

```
1) 뷰포트 안인지 검사 → 아니면 패널/미니맵 처리로 넘긴다
2) 화면 좌표 → 월드 픽셀 좌표 (카메라 오프셋 더하기)
3) 후보: 공간 버킷 질의 반경 2타일
4) 후보를 y 내림차순(앞에 그려진 것 우선), 동점이면 핸들 내림차순으로 정렬
5) 각 후보의 AABB 안이면 스프라이트 알파 마스크를 확인하고, 통과하면 그것이 답
```

AABB 만으로 끝내지 않는 이유는 유닛이 사각형이 아니기 때문이다. 마스크는
스프라이트의 컬러키 여부 비트(§22.3)를 그대로 쓴다.

### 12.2 상자 선택

드래그한 사각형 `(x0,y0)-(x1,y1)` 과 겹치는 **내 유닛만** 고른다.

```
겹침 판정: AABB 교차 (not (a.r < b.l or b.r < a.l or a.b < b.t or b.b < a.t))
우선순위: 내 유닛이 하나라도 있으면 건물과 남의 유닛은 제외한다
정렬:     핸들 오름차순 — 선택 목록의 순서가 대형 배정(§13.5)을 결정한다
상한:     한 번에 32기 (도스 시절 제한을 흉내내되, 이 덱의 규칙이라고 적는다)
```

### 12.3 컨트롤 그룹

0–9 번 그룹. `set(g)` 는 현재 선택을 복사하고, `recall(g)` 는 그것으로 바꾼다.
저장되는 것은 **핸들**이므로 죽은 유닛은 `valid`(§7.2)에서 자동으로 걸러진다.

### 12.4 명령 큐

각 유닛은 명령 큐를 갖는다(길이 상한 8).

```
Order = (kind, tx, ty, target_handle)
kind ∈ { MOVE, ATTACK, ATTACK_MOVE, HARVEST, BUILD, STOP, HOLD }
```

기본 클릭은 큐를 비우고 하나를 넣는다. 시프트 클릭은 뒤에 붙인다.
`STOP` 은 큐를 비우고 이동을 멈춘다(예약 타일은 반납한다).

**우클릭의 문맥 규칙:** 목표가 적이면 `ATTACK`, 자원이면 `HARVEST`,
내 건물이고 그것이 **반납처**(§25.2 의 사령부·정제소)면 `HARVEST`(반납),
그 외에는 `MOVE`. 판정 순서도 이 순서다 — 적 정제소를 우클릭하면 반납이
아니라 공격이어야 한다.

### 12.5 명령은 틱 경계에서만 들어간다

UI 가 만든 명령은 즉시 실행되지 않는다. `net`(§19)의 지연 큐에 들어가
`ORDER_DELAY = 2` 틱 뒤에 `sim.step` 의 인자로 들어온다. **UI 코드가 `sim` 의
상태를 직접 건드리는 경로는 존재하지 않는다.** 이 규율 하나가 락스텝을 가능하게 한다.

## 13. 이동과 충돌 — 모듈 `move`

### 13.1 타일 사이 보간

유닛은 항상 "타일 `a` 에서 타일 `b` 로 가는 도중"이거나 "타일 `a` 에 서 있는" 상태다.

```
from_t, to_t     타일 인덱스 (정지 상태면 같다)
prog             0 <= prog <= FP_ONE,  현재 걸음의 진행률
```

한 틱의 진행량은 걸음의 방향에 따라 다르다.

```
step_straight = fpdiv(speed, fp(TILE))                 speed 는 16.16 px/틱
step_diag     = fpmul(step_straight, FP_DIAG)          FP_DIAG = 1/√2
```

**정리 13.1.** 이렇게 하면 유닛의 **화면상 속도**가 방향과 무관하게 일정하다.

*증명.* 대각 걸음의 기하학적 길이는 `TILE·√2` 픽셀이다. 진행률이 틱당
`step_straight/√2` 씩 늘면 한 걸음에 `√2 · TILE/speed` 틱이 걸리고,
픽셀 속도는 `TILE·√2 / (√2·TILE/speed) = speed` 다. ∎

대각 보정을 빼먹으면 유닛이 대각으로 41 % 빨라진다. 도스 게임 중에도 이 버그를
그대로 둔 것이 있었고, 그래서 플레이어들이 지그재그로 움직였다.

화면 위치는 파생값이며 상태가 아니다.

```
px = fp(tx(from_t) * TILE) + fpmul(fp((tx(to_t) - tx(from_t)) * TILE), prog)
py = 같은 식
```

### 13.2 예약 불변식

```
resv[tile]   그 타일을 점유했거나 점유하려는 엔티티 핸들, 없으면 0
```

**불변식 R.** 어떤 타일도 두 엔티티에게 동시에 예약되지 않는다.

걸음을 시작할 때:

```
if resv[next] != 0 and resv[next] != my_handle: 걸음을 시작하지 않는다 (막힘)
resv[next] = my_handle          -- 이제 두 칸을 쥔다
```

`prog` 가 `FP_ONE` 에 닿으면 `resv[from_t] = 0`, `from_t = to_t`, `prog = 0`.
**두 칸을 쥐는 구간이 있는 것이 핵심이다.** 한 칸만 쥐면 두 유닛이 서로의
칸으로 동시에 들어가 겹친다.

`STOP`(§12.4)은 걷던 걸음을 **끝까지 마친 뒤** 멈춘다. 걸음 도중에 `to_t` 의
예약을 놓으면 다른 유닛이 그 칸을 가져가고, 이쪽은 이미 절반쯤 들어와 있다 —
불변식 R 이 깨지는 유일한 경로가 그것이다. 그래서 `STOP` 이 즉시 반납하는
예약은 **아직 시작하지 않은 걸음의 것뿐**이다.

건물은 자기 발자국(2×2 또는 3×3)의 모든 타일을 영구 예약한다.

### 13.3 막힘과 교착

```
blocked[i]     연속으로 막힌 틱 수
blocked >= 8   경로를 다시 찾는다 (목표는 그대로)
blocked >= 24  명령을 포기하고 IDLE 로 (교착 해소)
```

앞을 막은 것이 **정지한 아군**이면 밀어낸다(`push`).

```
push(blocker, from_dir):
    후보 = 8방향을 from_dir 의 반대에서 시작해 시계방향으로 훑는다
    첫 번째로 통행 가능하고 resv 가 0 인 칸으로 한 걸음 명령을 준다
```

방향 훑는 순서를 명세로 고정하는 이유는 늘 같다 — 세 언어가 같은 칸을 골라야 한다.

**교착이 완전히 사라지지는 않는다.** 좁은 통로에서 마주 오는 두 무리는
`blocked >= 24` 로 풀린다. 이것은 해결이 아니라 포기이며, 덱 14부에서
그렇게 적는다. 완전한 해법(협상 기반 재배치)은 이 엔진의 범위 밖이다.

### 13.4 도착 반경

목표 타일이 이미 점유되어 있고 유닛이 목표에서 `ARRIVE_R = 2` 타일 안에 있으면
**도착으로 친다.** 이것이 없으면 무리의 마지막 한 기가 영원히 목표 칸을 두드린다.

### 13.5 대형

선택된 `n` 기를 목표 주위에 배치한다. 대형은 셋이다.

```
LINE    : 이동 방향에 수직으로 한 줄
          슬롯 k = (k - floordiv(n-1, 2),  0)
COLUMN  : 이동 방향으로 한 줄
          슬롯 k = (0,  k)
BOX     : 한 변 w = isqrt(n-1) + 1 인 정사각형 (= ceil(sqrt(n)), §2.5 의 정수 제곱근)
          슬롯 k = (fmod(k, w) - floordiv(w-1, 2),  floordiv(k, w))
```

회전 전 좌표계는 **이동 방향이 북(d = 0)일 때의 화면 좌표**다. 그래서 `LINE`
의 `ox` 는 진행 방향의 수직이고, `COLUMN` 의 `oy` 는 진행 방향의 뒤가 된다.
슬롯은 목표 타일에 더한 뒤 맵 밖이거나 통행 불가면 **그 유닛만 목표 타일
자체를 쓴다** — 슬롯을 다시 찾아 주는 재배치는 넣지 않는다(§13.3 과 같은
이유로, 반쯤 성공하는 재배치가 교착보다 더 나쁜 그림을 만든다).
슬롯을 유닛에 나눠 주는 순서는 **핸들 오름차순**이다.

기본은 `BOX`. 슬롯 오프셋 `(ox, oy)` 는 **이동 방향으로 회전**한다. 회전은
행렬이 아니라 8방향 표다.

```
rot8(d, ox, oy):   d = 0(N) 이면 (ox, oy) 그대로
                   d = 2(E) 이면 (-oy, ox)
                   d = 4(S) 이면 (-ox, -oy)
                   d = 6(W) 이면 (oy, -ox)
                   대각 방향은 인접한 두 직교 방향의 결과를 더하고 2로 내림 나눗셈
```

대각 회전을 근사로 두는 것은 45° 회전이 정수 격자를 보존하지 않기 때문이다.
정확한 회전은 소수 좌표를 낳고, 그것을 반올림하면 두 슬롯이 같은 칸에 겹친다.

슬롯 배정은 **탐욕적**이다. 유닛을 핸들 오름차순으로 훑으며, 남은 슬롯 중
`d83` 이 가장 가까운 것을 준다. 헝가리안 알고리즘이 더 좋은 배정을 주지만
O(n³) 이고, 32기에서 눈에 보이는 차이가 없다(14부에서 두 배정을 나란히 보인다).

## 14. 시야와 안개 — 모듈 `fog`

### 14.1 세 평면

플레이어마다 세 배열을 둔다. 길이는 각각 `MAP_W * MAP_H`.

```
explored[p][i]   0/1   한 번이라도 봤는가
count[p][i]      0..255 지금 이 칸을 보고 있는 유닛 수
visible(p, i)    count[p][i] > 0
```

### 14.2 왜 칸당 1바이트인가

비트 플레인(바이트당 8칸)이 메모리는 8배 적다. 그런데도 바이트를 쓴다.

* 참조 카운트는 어차피 비트로 담을 수 없다. `count` 가 바이트여야 한다면
  `explored` 만 비트로 만들어 봐야 4096바이트 아끼는 것이 전부다.
* 루아 5.1 과 타입스크립트에서 비트 연산을 산술로 흉내내면(§1.1) 칸 하나
  읽는 데 나눗셈과 나머지가 붙는다. 안개는 매 틱 수천 칸을 읽는다.

비트 플레인 자체는 15부에서 **다룬다** — 도스 시절 실제 구현이 그랬고,
`fog.pack_bits()` 가 저장·전송용으로 8칸을 1바이트로 접는다. 시뮬레이션 중에는
쓰지 않을 뿐이다.

### 14.3 증분 갱신과 불변식

```
add_sight(p, tx, ty, r):     for (dx,dy) in offsets(r): count[p][i] += 1; explored[p][i] = 1
remove_sight(p, tx, ty, r):  for (dx,dy) in offsets(r): count[p][i] -= 1
```

유닛이 타일을 넘을 때 `remove` 를 먼저, `add` 를 나중에 한다. 죽으면 `remove` 만.

**불변식 F.** 모든 `p`, `i` 에 대해
`count[p][i] = #{ 살아 있는 p 의 엔티티 e : i ∈ disc(sight(e)) + pos(e) }`.

이 불변식은 세이브를 불러온 직후와 매 100틱마다 `fog.recount()` 로 전수 검증한다
(테스트에서는 매 틱). 증분 갱신은 빠르지만 한 번 어긋나면 영원히 어긋나고,
"보이지 않는 적"이나 "영원히 밝은 칸"으로 나타난다. 전수 재계산이 4096 × 유닛 수
이므로 매 틱 돌릴 수는 없고, 그래서 검증 주기를 명세에 못 박는다.

### 14.4 4단계 렌더

```
0  미탐험      완전한 검정
1  탐험됨      지형을 명암 25 % 로
2  경계        지형을 명암 60 % 로 (가시 칸과 인접한 탐험 칸)
3  가시        원색
```

2단계는 순전히 눈을 위한 것이다. 1과 3만 있으면 안개 경계가 계단처럼 보인다.
명암 단계는 팔레트 명암표(§22.2)의 행 번호이며, 색 계산은 하지 않는다.

### 14.5 안개는 시뮬레이션에 영향을 준다

AI 는 `visible` 인 적만 볼 수 있다(§17.3). 사람 플레이어의 UI 도 마찬가지다.
그러나 **시뮬레이션 자체는 안개를 무시**한다 — 유닛은 안개 속에서도 정상적으로
움직이고 싸운다. 안개를 시뮬레이션의 일부로 만들면 플레이어마다 다른 상태가
생기고, 그러면 락스텝의 전제(모든 기계가 같은 상태)가 깨진다.

이것이 도스 RTS 의 **맵 핵**이 그토록 쉬웠던 이유다. 모든 클라이언트가 전체
맵을 가지고 있고, 안개는 그리기 단계에서만 적용되었다. 19부에서 다룬다.

## 15. 전투 — 모듈 `combat`

### 15.1 사거리와 표적 선택

사거리 판정은 **체비셰프 거리**다. 8방향 이동 격자에서 "몇 걸음 안"과 정확히 같다.

```
in_range(a, b) = dinf(tx(a) - tx(b), ty(a) - ty(b)) <= range(a)
```

표적 우선순위(먼저 맞는 것이 답):

```
1) 현재 표적이 살아 있고 사거리 안이면 그대로
2) 나를 때린 적이 사거리 안에 있으면 그것
3) 사거리 안의 적 중 d83 최소, 동점이면 핸들 오름차순
4) 없으면 사거리 + 2 안을 훑어 하나 고르고 접근한다 (ATTACK_MOVE 만)
```

3번의 동점 규칙이 명세인 이유는 지금까지와 같다. 두 적이 정확히 같은 거리에
있는 상황은 대칭 맵에서 흔하다.

### 15.2 피해 공식

Warcraft II 의 공식을 그대로 쓴다. 블리자드 공식 전략 가이드에 적힌
서술(`claims.md` C32)은 이렇다 — **최대 피해 = (기본 피해 − 방어력) + 관통 피해**,
**실제 피해는 그 최대치의 50 %에서 100 % 사이의 균등 난수**.

```
mx = basic - armour + pierce
if mx < 1: mx = 1
lo = floordiv(mx + 1, 2)              -- ceil(mx / 2), 최대치의 50 %
dmg = lo + roll(mx - lo + 1)          -- lo …  mx 균등
```

`roll` 은 §3.2 의 편향 없는 난수다. 반올림 방향(올림)은 팬 사이트의 역산 자료가
`ceil(mx/2) … mx` 로 적은 것을 따랐다. 블리자드 문서는 "50 %에서 100 % 사이"라고만
하므로, **올림이라는 부분은 2차 출처**다. 덱 16부는 이 구분을 그대로 적는다.

**정리 15.1 (기대값과 분산).** `n = mx − lo + 1` 개 값 위의 균등분포이므로

```
E[dmg] = (lo + mx) / 2 ≈ 0.75 · mx
Var[dmg] = (n² − 1) / 12
```

`mx` 가 **짝수**면 `lo = mx/2` 이므로 `E[dmg] = 0.75·mx` 로 딱 떨어지고,
**홀수**면 `lo = (mx+1)/2` 이므로 `E[dmg] = 0.75·mx + 0.25` 다. 올림이 홀수에서만
값을 한 칸 올리기 때문이며, 그래서 DPS 표의 홀수 행만 0.25 씩 위로 어긋난다.
DPS 는 `E[dmg] / cooldown` 이며 틱당 값이다. 16부의 표는 전부 이 식으로 계산하고,
같은 표를 시뮬레이션 1000회로 검증한 결과를 `out/py_prim.txt` 11절에 함께 싣는다.

**방어력이 최대 피해를 0 이하로 만들면 1 로 올린다.** 그래야 "절대 안 죽는 유닛"이
생기지 않는다. 이 하한은 블리자드 문서에 없는 **이 덱의 규칙**이다.

### 15.3 투사체 — 직선

화살·총알. **브레젠험 스테퍼**를 고정소수점으로 돌린다.

```
상태: (x, y) 16.16,  (vx, vy) 16.16 틱당 이동,  target_handle,  ttl
매 틱: x += vx; y += vy; ttl -= 1
       목표 타일에 도달했거나 ttl == 0 이면 명중 처리
```

속도 벡터는 발사 시점에 한 번 계산한다.

```
d  = isqrt(dx*dx + dy*dy)          픽셀 거리 (정수)
vx = fpdiv(fp(dx) , fp(d)) 를 speed 로 스케일 → fpmul(fpdiv(fp(dx), fp(d)), speed)
ttl = floordiv(fp(d), speed) + 2   도달 예정 틱 + 여유 2
ARROW_SPEED = fp(4)                화살·총알 4 px/틱
```

`ttl` 에 여유 2를 두는 이유는 `vx`·`vy` 가 내림으로 계산되어 투사체가 목표
타일에 **한두 틱 늦게** 닿기 때문이다. 여유가 없으면 화살이 목표 코앞에서
사라진다. `d == 0`(같은 타일)이면 발사하지 않고 즉시 명중으로 친다.

**표적을 쫓지 않는다.** 발사 시점의 위치로 날아간다. 그래서 빠른 유닛은 화살을
피할 수 있다. 이것도 이 덱의 규칙이며, 유도 투사체는 `ttl` 이 다할 때까지 매 틱
속도를 다시 계산하는 변형으로 16부에서 비교한다.

### 15.4 투사체 — 포물선

박격포. 수평은 등속, 수직은 중력만 받는다.

```
T   = 비행 시간 (틱) = max(6, floordiv(d, 24))
vx  = fpdiv(fp(x1 - x0), fp(T))
vy0 = fpdiv(fp(y1 - y0), fp(T)) - fpmul(G, fpdiv(fp(T), fp(2)))
매 틱: vy += G;  x += vx;  y += vy
G   = 1638   (0.025 px/틱², 16.16)
```

**정리 15.2.** 위 `vy0` 은 T 틱 뒤에 정확히 `y1` 에 닿는 초기 속도다.

*증명.* 이산 적분으로 `y(T) = y0 + T·vy0 + G·T(T+1)/2` 이다. 연속 근사
`y0 + T·vy0 + G·T²/2` 를 쓰면 `vy0 = (y1−y0)/T − G·T/2` 를 얻는다.
이산과 연속의 차이는 `G·T/2` 이며, T = 12, G = 1638 에서 화면 픽셀로 0.15px 다.
이 오차는 명중 판정(타일 단위)에 영향을 주지 않으므로 보정하지 않는다 —
**보정하지 않기로 한 결정**이지 놓친 것이 아니다. ∎

### 15.5 스플래시

명중 지점에서 원 마스크(§6)로 퍼진다. 감쇠는 **링 단위**다.

```
링 0 (명중 칸)       : dmg
링 1 (dinf == 1)     : floordiv(dmg, 2)
링 2 (dinf == 2)     : floordiv(dmg, 4)
링 3 이상            : 0
```

같은 유닛이 두 링에 걸치는 일은 없다 — 유닛의 대표 타일 하나로 판정한다.
아군도 맞는다(friendly fire). 이것은 AI 에게 중요한 제약이며 17부에서 쓰인다.

### 15.6 란체스터 법칙

두 부대 A, B 의 규모를 연속량으로 보는 근사다.

**제곱 법칙(조준 사격).** 모든 사수가 살아 있는 적 중 하나를 정확히 노린다.

```
dA/dt = -β·B          dB/dt = -α·A
```

**정리 15.3.** `α·A² − β·B²` 는 시간에 대해 불변이다.

*증명.* `d/dt(α·A² − β·B²) = 2α·A·A' − 2β·B·B' = 2α·A·(−β·B) − 2β·B·(−α·A) = 0`. ∎

따라서 A 가 이기는 조건은 `α·A₀² > β·B₀²` 다. **전력은 수의 제곱에 비례한다** —
수가 2배면 전투력이 4배다. RTS 에서 병력을 나눠 보내면 안 되는 이유가 이것이다.

**선형 법칙(비조준 사격).** 사수가 지역을 향해 쏘고, 밀집도에 비례해 맞는다.

```
dA/dt = -β·A·B        dB/dt = -α·A·B      →   α·A − β·B 가 불변
```

이때 전력은 수에 **비례**한다.

**정리 15.4 (섬멸 시각, 제곱 법칙).** `α·A₀² > β·B₀²` 일 때 B 가 0 이 되는 시각은

```
T = (1 / (2√(αβ))) · ln( (√α·A₀ + √β·B₀) / (√α·A₀ − √β·B₀) )
```

이 식은 **덱의 설명용**이며 엔진은 쓰지 않는다. 엔진의 `lanchester_sim` 은
정수 이산 시뮬레이터이고, 16부는 그 시뮬 결과와 위 폐형해를 나란히 놓아
**언제 근사가 무너지는지**(부대가 작을 때, 이산성이 지배할 때)를 보인다.
폐형해 계산은 `tools/gen_prim.py`(엔진 밖, 부동소수점 허용)가 한다.

```
lanchester_sim(A0, B0, α, β):        α, β 는 16.16
    A, B = fp(A0), fp(B0)
    t = 0
    while A >= FP_ONE and B >= FP_ONE and t < 10000:
        dA = fpmul(β, B);  dB = fpmul(α, A)
        A -= dA;  B -= dB
        if A < 0: A = 0
        if B < 0: B = 0
        t += 1
    return (t, fp_floor(A), fp_floor(B))
```

오일러 전진법이며 틱 크기가 1 이다. 이 조잡함이 의도적이다 — 시뮬과 폐형해의
차이가 어디서 오는지 16부에서 그대로 보여 준다.

**종료 조건이 `> 0` 이 아니라 `>= FP_ONE` 인 이유.** `dA = fpmul(β, B)` 는
내림이므로 `B` 가 작아지면 `dA` 가 0 이 되고, 그 순간 수열이 멈춘다.
`> 0` 으로 두면 A = B = 10, α = β = 0.1 인 대칭 전투가 **1만 틱을 다 돌고도
끝나지 않는다.** 이것도 골든을 처음 만들 때 드러난 함정이며, 16부의 소재다.
병사 1명 미만은 병사가 아니므로 `>= FP_ONE` 이 물리적으로도 맞다.

## 16. 경제 — 모듈 `econ`

### 16.1 자원

자원은 한 종류(`ORE`)다. 광맥 타일은 `amount[i]` 를 갖고, 다 캐면 `SAND` 가 된다.

```
ORE_PER_TILE = 500          한 칸의 매장량
LOAD_MAX     = 100          채집기 적재 상한
MINE_PER_TICK = 5           틱당 채굴량
UNLOAD_TICKS = 12           반납에 걸리는 틱
```

### 16.2 채집기 FSM

```
SEEK      → 가장 가까운 광맥 타일을 찾는다 (없으면 IDLE)
TO_ORE    → 경로 이동. 도착하면 MINE
MINE      → load += MINE_PER_TICK, amount -= 같은 값. load 가 차면 TO_BASE
TO_BASE   → 가장 가까운 정제소로. 도착하면 UNLOAD
UNLOAD    → UNLOAD_TICKS 뒤에 credits += load, load = 0, SEEK
```

"가장 가까운"은 항상 `d83` 이고 동점은 타일 인덱스 오름차순이다.

### 16.3 수입률

**정리 16.1.** 왕복 거리 `d` 타일, 속도 `v`(타일/틱)인 채집기 한 기의
정상 상태 수입률은

```
rate = LOAD_MAX / ( 2·d/v + LOAD_MAX/MINE_PER_TICK + UNLOAD_TICKS )   [크레딧/틱]
```

분모의 세 항은 왕복 이동, 채굴, 반납이다. `d` 가 0 이어도 rate 는
`100 / (20 + 12) = 3.125` 를 넘지 못한다 — **정제소를 광맥에 붙여도 상한이 있다.**

이 식과 시뮬레이션 실측(1200틱 게임의 실제 수입)을 17부에서 대조한다.
둘이 어긋나는 주된 이유는 채집기끼리의 길막(§13.3)이며, 그 차이를 그대로 싣는다.

### 16.4 생산 큐

건물마다 큐(상한 5)를 둔다.

```
enqueue(kind):  credits >= cost 면 credits -= cost, 큐에 넣는다 (선불)
매 틱:          progress += rate;  progress >= build_time 이면 완성, 다음 항목
취소:           환불은 100 % (이 덱의 규칙)
```

선불로 하는 이유는 결정론이다. 후불이면 "완성 시점에 돈이 없는" 상태가 생기고,
그 처리 규칙이 언어마다 미묘하게 갈릴 여지가 생긴다.

### 16.5 배치 판정

```
placeable(kind, x, y):
    발자국의 모든 칸이 in_map 이고
    bit(pass[i], 2) == 1 (건설 가능 지형) 이고
    resv[i] == 0 이고
    같은 소유자의 건물이 4타일 안에 하나 이상 (첫 건물 제외)
```

4타일 규칙은 기지를 한 덩어리로 유지시켜 AI 의 방어를 단순하게 만든다.

### 16.6 기술 트리 = DAG

```
노드: 유닛·건물·업그레이드
간선: "X 를 만들려면 Y 가 있어야 한다"
```

**정리 16.2.** 이 그래프는 비순환이어야 하고, 위상 정렬이 존재하는 것과 동치다.

`econ.topo_order()` 는 Kahn 알고리즘을 쓴다. 진입차수 0 인 노드를 **번호
오름차순**으로 꺼낸다(결정론). 순환이 있으면 남은 노드가 생기고, 그때는
**즉시 실패**한다. 기술 트리는 데이터이고, 데이터가 잘못되면 조용히 넘어가는
것보다 터지는 편이 낫다.

`can_build(player, kind)` 는 선행 노드가 전부 **완성된 채 살아 있는지** 본다.
병영이 부서지면 보병을 못 뽑는다.

### 16.7 인구 상한

```
supply_used  = 살아 있는 유닛의 supply 합
supply_cap   = 완성된 건물의 supply_give 합, 상한 100
```

`supply_used + cost > supply_cap` 이면 큐에 넣지 못한다.

## 17. AI — 모듈 `ai`

AI 는 **시뮬레이션의 일부**다. `sim.step` 안에서 돌고, 명령을 만들어
자기 자신의 명령 큐에 바로 넣는다(네트워크 지연을 거치지 않는다 — 모든 기계가
같은 AI 를 같은 틱에 돌리므로 결과가 같다).

### 17.1 유닛 FSM

```
IDLE → 사거리 안에 적이 있으면 ATTACK
MOVE → 경로 끝에 닿으면 IDLE. ATTACK_MOVE 면 도중에도 적을 본다
ATTACK → 표적이 죽거나 사거리를 벗어나면 IDLE (추격은 3타일까지)
FLEE → hp 가 25 % 아래인 채집기만. 가장 가까운 정제소 쪽으로
HARVEST / BUILD → §16
```

상태 전이는 매 틱 **정해진 순서로** 평가한다. 순서가 곧 우선순위다.

`state[i]` 는 §7.1 의 한 바이트 하나이고, 전투 유닛과 채집기가 **같은 칸을
나눠 쓴다.** 그래서 번호가 겹치면 안 된다 — 상태 해시(§18.4)에 그대로 들어가는
값이기 때문이다. 번호는 `const` 가 소유한다.

| 번호 | 이름 | 누가 쓰나 |
|---|---|---|
| 0 | `ST_IDLE` | 전부 |
| 1 | `ST_MOVE` | 전투 유닛 |
| 2 | `ST_ATTACK` | 전투 유닛 |
| 3 | `ST_FLEE` | 채집기 (hp 25 % 아래) |
| 4 | `ST_SEEK` | 채집기 (§16.2) |
| 5 | `ST_TO_ORE` | 채집기 |
| 6 | `ST_MINE` | 채집기 |
| 7 | `ST_TO_BASE` | 채집기 |
| 8 | `ST_UNLOAD` | 채집기 |
| 9 | `ST_BUILD` | 건설 중인 건물 |

### 17.2 영향 지도

```
seed[i] = Σ (내 유닛의 전력),  적 유닛은 음수
3회 반복: next[i] = floordiv(4*cur[i] + Σ(8이웃 cur), 12)
```

가중치 4 + 8 = 12 로 나누므로 총합이 대략 보존되면서 퍼진다. 정수 나눗셈의
내림 때문에 매 반복 조금씩 줄어드는데, 그 감쇠가 곧 "멀수록 영향이 적다"이다.
별도의 감쇠 계수를 두지 않는 이유가 이것이다.

전력은 `strength = basic + pierce + hp/4` 로 정의한다(이 덱의 규칙).

`threat[i]` 는 같은 계산을 **적 유닛만**으로 한 것이다.

### 17.3 AI 는 안개를 존중한다

AI 가 seed 에 넣는 적 유닛은 `visible(p, i)` 인 것뿐이다. 이 제약이 없으면
AI 가 전지적이 되고, 그건 게임이 아니다. 마지막으로 본 위치를 기억하는
`ghost[i]`(30틱 동안 남는다)를 두어 정찰의 가치를 만든다.

### 17.4 건물 배치

```
점수(x, y) = 100 - 3*d83(기지 중심) + 2*fire[i] - threat[i]
             fire 는 브러시파이어(§11.4) — 벽에 붙이지 않으려는 항
정제소만: 점수 += 40 - 8*d83(가장 가까운 광맥)
```

후보는 기지 중심 반경 12 안의 `placeable` 칸 전부이며, 점수 최대(동점이면
타일 인덱스 최소)를 고른다.

### 17.5 빌드 오더

스크립트다. `(조건, 행동)` 목록을 위에서부터 훑어 처음으로 조건을 만족하는
행동 하나를 실행한다.

```
채집기 < 4                → 채집기 생산
정제소 == 0 and 크레딧>=300 → 정제소 건설
병영 == 0 and 크레딧>=400   → 병영 건설
군대 < 6                   → 보병 생산
군대 >= 6 and 적 기지 알려짐 → 전군 공격
그 외                      → 방어 위치로
```

이 여섯 줄이 AI 전부다. 18부는 이 단순한 규칙이 만들어 내는 러시 타이밍을
`out/trace.jsonl` 에서 실측해 싣는다("몇 틱에 첫 공격이 나가는가").

### 17.6 정찰

미탐험 클러스터(§9.1)의 중심을 **클러스터 번호 오름차순**으로 방문한다.
정찰병이 죽으면 다음 유닛이 목록의 다음 항목부터 이어 간다.

## 18. 시뮬레이션 — 모듈 `sim`

### 18.1 유일한 진입점

```
sim.step(orders)          orders: 이번 틱에 실행할 명령 목록
```

**상태를 바꾸는 함수는 이것 하나뿐이다.** 렌더는 상태를 읽기만 하고,
UI 는 명령을 만들 뿐이다. 이 규율이 19부(락스텝)와 20부(리플레이)의 전제다.

`orders` 는 호출 전에 **정렬되어 있어야 한다.**

```
정렬 키: (player, issuer_handle, kind, tx, ty, target)
```

네트워크에서 도착 순서는 제각각이다. 정렬하지 않으면 두 기계가 같은 명령
집합을 다른 순서로 적용하고, 명령끼리 충돌하는 순간(예: 같은 칸에 두 건물)
상태가 갈린다.

### 18.2 틱의 단계

순서는 명세다. 바꾸면 골든이 전부 틀어진다.

```
1. 명령 적용        정렬된 orders 를 하나씩
2. AI               플레이어 번호 오름차순 (§17)
3. 생산·경제        건물 큐, 채집기 FSM (§16)
4. 이동             핸들 오름차순 (§13)
5. 전투             표적 선택 → 발사 → 투사체 갱신 → 피해 적용 (§15)
6. 사망 처리        hp <= 0 인 엔티티 제거, 시야 반납, 잔해 남기기
7. 시야 갱신        타일을 넘은 유닛의 remove/add (§14)
8. 트리거·승패      §18.5
9. 상태 해시        §18.4
```

**전투에서 피해를 즉시 적용하지 않고 5단계 끝에 모아서 적용한다.** 그래야
"먼저 처리된 유닛이 유리한" 편향이 없다. 두 유닛이 서로를 동시에 죽일 수 있다.

### 18.3 이벤트 로그

`sim.events` 는 이번 틱에 일어난 일의 목록이다. 렌더(폭발·소리)와 트레이스가
읽는다. 매 틱 초에 비운다.

```
(kind, a, b, c)     kind ∈ { SPAWN, DIE, HIT, BUILD_DONE, MINE, UNLOAD, ORDER, WIN }
```

이벤트는 **상태가 아니다** — 해시에 넣지 않는다. 대신 `trace.jsonl` 이 이벤트를
그대로 싣기 때문에, 세 언어의 이벤트가 다르면 트레이스 비교에서 잡힌다.

### 18.4 상태 해시 — FNV-1a 32비트

```
h = 2166136261
각 바이트 b 에 대해:  h = fmod(xor_low8(h, b) * 16777619, 4294967296)
```

**곱셈은 분할한다**(§2.3 과 같은 이유):

```
hh = floordiv(h, 65536);  hl = fmod(h, 65536)
h' = fmod(hl * 16777619 + fmod(hh * 16777619, 65536) * 65536, 4294967296)
```

`hl * 16777619 < 2^16 · 2^24.0 = 2^40`, 안전하다.

**XOR 도 비트 연산자 없이** 한다. `b < 256` 이므로 하위 8비트만 바뀐다.

```
xor_low8(h, b) = h - fmod(h, 256) + xor8(fmod(h, 256), b)
xor8(x, y)     = 8회 루프: 각 비트 자리에서 bit(x,k) + bit(y,k) 가 1이면 2^k 를 더한다
```

**해시에 들어가는 바이트 열(순서 고정):**

```
tick (4바이트, 빅 엔디언)
rng 상태 (4바이트)
플레이어별: credits(4), supply_used(2), supply_cap(2)          -- p = 0..3
엔티티 i = 1..255:
    alive(1) owner(1) kind(1) tx(1) ty(1) hp(2) dir(1) state(1)
    px(4) py(4) target(2) load(2) prog(4) from_t(2) to_t(2) cool(2) timer(2)
    (alive == 0 이면 alive 바이트 하나만 넣는다)
투사체: 개수(2), 각각 x(4) y(4) vx(4) vy(4) target(2) dmg(2)
생산 큐: 살아 있는 건물 i 마다 큐 길이(1), 항목 종류(1)×길이, 진행(2)
광맥: 칸 수(2), 각각 타일 번호(2) 남은 양(2)   -- 오름차순
map_hash (4바이트)
```

`cool`(재장전)과 `timer`(반납·건설 카운트다운)를 빼면 안 된다. 둘은 매 틱
바뀌는 상태이고, 빠져 있으면 두 기계의 재장전이 한 틱 어긋나도 해시가 같아서
**첫 발이 어긋난 다음 틱에야** 디싱크가 잡힌다. 생산 큐와 광맥 잔량도 같은
이유로 넣는다 — 화면에 보이는 것은 전부 해시에 있어야 한다.

`map_hash` 는 `terrain` 과 `pass` 평면의 FNV-1a 이며, **지형이 바뀔 때만**
다시 계산한다(`map_version` 이 오르면 무효화). 캐시지만 상태의 순수 함수다.

이 순서가 명세인 이유는 명백하다. 한 필드라도 순서가 다르면 두 언어의 해시가
다르고, 그러면 락스텝 검증이 아무것도 증명하지 못한다.

### 18.5 트리거와 승패

```
트리거 = (조건, 액션, once)
조건: TICK_GE(n) · UNIT_COUNT(p, kind, cmp, n) · BUILDING_DESTROYED(p) ·
      AREA_ENTERED(p, x, y, r) · CREDITS_GE(p, n)
액션: SPAWN(p, kind, x, y) · MESSAGE(id) · WIN(p) · LOSE(p) · REVEAL(x,y,r)
```

매 틱 8단계에서 **정의 순서대로** 평가한다. `once` 인 트리거는 한 번 발화하면
비활성으로 표시하며, 그 표시는 상태의 일부다(해시에는 넣지 않는다 —
트리거 발화는 반드시 다른 상태 변화를 낳으므로 중복이다).

기본 승리 조건: 어느 플레이어의 건물이 전부 파괴되면 그 플레이어는 패배.
남은 플레이어가 하나면 `WIN`.

### 18.6 시나리오 스크립트

골든 시나리오(`golden/script.txt`)는 손으로 쓴 명령표다. 명령을 만들 때는
핸들을 알 수 없으므로, 스크립트는 핸들 대신 **선택자**를 적는다.

```
형식:  <틱> <플레이어> <선택자> <명령> <a> <b> <c>
선택자:  A      내 유닛 전부 (건물 제외)
         F      내 전투 유닛 전부 (종류 0..3)
         K<n>   종류 n 인 내 엔티티 전부
         N      가장 최근에 생산된 내 유닛 하나
명령:    MOVE a=tx b=ty · AMOVE a=tx b=ty · HARVEST · STOP
         BUILD a=건물종류 b=tx c=ty · TRAIN a=유닛종류
```

`sim.script_orders(tick)` 이 선택자를 그 틱의 실제 핸들로 펼친다. 펼친 결과는
**핸들 오름차순**이며, 그대로 `net.send` 에 들어가 `ORDER_DELAY` 틱 뒤에
실행된다. 즉 스크립트도 사람과 똑같은 경로를 지난다 — 시뮬레이션에 특별한
뒷문을 내지 않는다.

`#` 로 시작하는 줄은 주석이다.

## 19. 락스텝 네트워크 — 모듈 `net`

### 19.1 왜 상태가 아니라 명령을 보내는가

유닛 200기의 상태는 매 틱 수 KB 다. 명령은 대개 **0개**이고, 있어도
한 줄이면 20바이트다. 28.8 kbps 모뎀에서 전자는 불가능하고 후자는 여유롭다.
대신 **모든 기계가 같은 계산을 해야 한다**는 대가를 치른다.

이 설계와 그 대가를 정리한 것이 Bettner–Terrano 의 GDC 2001 발표
"1500 Archers on a 28.8"(`claims.md` C19)이다. 저자 순서는 **Bettner 가 1저자**다.

### 19.2 모형

```
Net(n_players, latency, jitter_seed)
  send(tick, player, order)      →  deliver_tick = tick + latency + jitter
  ready(tick)                    →  모든 플레이어의 tick 몫이 도착했는가
  take(tick)                     →  그 틱의 명령을 정렬해 돌려준다
```

`latency` 는 `ORDER_DELAY = 2` 가 기본이다. `jitter` 는 0…2 틱의 추가 지연이며
**전용 RNG** 로 만든다(시뮬레이션 RNG 를 쓰면 안 된다 — §3.3).

지터가 있어도 **결과는 같아야 한다.** 명령의 실행 틱은 보낼 때 정해지고,
늦게 도착하면 그 틱을 **기다릴 뿐**이다. 늦게 도착한 명령을 앞당겨 실행하는
경로는 존재하지 않는다.

### 19.3 검증 시나리오

```
make lockstep:
  1. 시뮬 2개를 같은 시드로 만든다
  2. golden/script.txt 의 명령을 각각의 Net 에 넣는다 (양쪽 플레이어 모두)
  3. 1200틱을 돌리며 매 틱 두 시뮬의 해시를 비교한다
  4. golden/hashes.txt 와 바이트 단위로 대조한다
```

### 19.4 디싱크 주입 실험

`sim` 에 `float_bug` 플래그를 둔다. 켜면 **딱 한 군데**가 부동소수점을 쓴다.

```
fpmul(a, b)  →  Math.floor(a * b / 65536)   (파이썬·루아·TS 각각의 실수 연산)
```

`|a·b|` 가 2^53 을 넘는 순간 하위 비트가 잘리고, 그 한 비트가 유닛 하나의
위치를 1/65536 픽셀 어긋나게 하고, 몇 틱 뒤 타일 경계 판정을 뒤집고,
그 뒤로 두 시뮬은 완전히 다른 게임이 된다.

`make lockstep` 은 이 실험도 돌려 **처음 어긋난 틱 번호**를 `out/lockstep.txt` 에
남긴다. 덱 19부는 그 숫자와 두 시뮬의 화면을 나란히 싣는다.

**이것은 일부러 넣은 버그다.** 덱에서 그렇게 적는다. "부동소수점을 쓰면 반드시
디싱크한다"가 아니라 "이 조건에서 이렇게 어긋났다"가 우리가 말할 수 있는 전부다.

### 19.5 도스 시절의 실제 사정

IPX/SPX 는 브로드캐스트가 싸서 N 명 방송에 적합했다(`claims.md` A8).
모뎀 직결은 2인 전용이고 왕복 지연이 100–200 ms 였으므로, 18.2 Hz 틱에서
2–4 틱 지연이 자연스러웠다. 이 엔진의 `ORDER_DELAY = 2` 는 그 관행을 따른 값이다.

## 20. 저장·리플레이·압축 — 모듈 `replay`

### 20.1 CRC-16/CCITT-FALSE

```
poly = 0x1021,  init = 0xFFFF,  reflect 없음,  xorout = 0
crc("123456789") = 0x29B1
```

정식 이름은 **CRC-16/IBM-3740** 이고 CCITT-FALSE 는 별칭이다(`claims.md` C28).

구현은 `fixed` 모듈에 둔다. `tmap`(맵 파일 §4.7)과 `replay`(리플레이 꼬리)가
둘 다 필요하고, `fixed` 는 아무것도 참조하지 않으므로 순환이 생기지 않는다.

비트 연산자 없이 구현한다.

```
crc16(bytes):
    c = 65535
    for b in bytes:
        c = xor_low8_high(c, b)              -- 상위 바이트에 XOR
        8회: if c >= 32768: c = fmod(c * 2, 65536); c = xor16(c, 0x1021)
             else:          c = fmod(c * 2, 65536)
    return c
```

`c >= 32768` 이 "최상위 비트가 1"과 같다. 이것이 GF(2) 위의 다항식 나눗셈이며,
20부에서 그 대응을 그림으로 보인다.

### 20.2 리플레이 = 명령 로그

```
헤더:  "RTSR" · 버전(1) · 맵 시드(4) · 플레이어 수(1) · 총 틱 수(4)
본문:  틱 오름차순. 각 틱: 명령 개수(1) + 명령들
       명령: player(1) kind(1) issuer(2) tx(1) ty(1) target(2)
꼬리:  CRC-16 (2)
```

**상태는 한 바이트도 저장하지 않는다.** 리플레이를 재생한다는 것은
같은 시드로 시뮬을 새로 만들어 같은 명령을 같은 틱에 먹이는 것이고,
결과가 같다는 것은 `hashes.txt` 와의 대조로 증명한다.

1200틱 게임의 리플레이는 수백 바이트다. 같은 게임의 상태 스냅샷은 틱당 4 KB 다.
20부는 두 숫자를 나란히 놓는다.

### 20.3 RLE

`(count, value)` 쌍, `count` 는 1…255. 맵 평면과 스프라이트에 쓴다.

### 20.4 LZSS (LZ77 미니)

```
창(window) 4096, 최소 일치 3, 최대 일치 18
플래그 바이트 1개당 토큰 8개
  플래그 비트 1: 리터럴 1바이트
  플래그 비트 0: (offset 12비트, len-3 4비트) = 2바이트
```

일치 탐색은 **탐욕적**이다 — 가장 긴 일치, 동점이면 가장 가까운(offset 최소) 것.
최적 파싱(lazy matching)을 하지 않는 이유는 결정론이 아니라 단순함이며,
20부는 같은 맵을 두 방식으로 압축해 크기 차이를 실측으로 보인다.

압축률은 `out/` 의 실제 숫자만 쓴다. "보통 절반으로 줄어든다" 같은 문장을 쓰지 않는다.

## 21. PC 스피커 — 모듈 `speaker`

### 21.1 분주값

```
divisor(f) = floordiv(PIT_HZ + floordiv(f, 2), f)        반올림
actual(f)  = PIT_HZ / divisor(f)                          실제로 나는 음
cents(f)   = 1200 · log2(actual / f)                      음정 오차
```

`PIT_HZ = 1193182` 는 **반올림값**이다(`claims.md` A3). 정확한 값은
14.31818 MHz / 12 = 1,193,181.8181… Hz 다. 이 0.18 Hz 차이가 분주값에 주는
영향은 22부에서 실제로 계산해 보인다(대부분의 음에서 0).

`cents` 계산에는 로그가 필요하므로 **엔진이 아니라 `tools/gen_prim.py`** 가 한다.
엔진은 분주값과 실제 주파수(정수 나눗셈의 몫과 나머지)만 낸다.

### 21.2 음표표

C4(261.63 Hz)부터 B5 까지 24음. 주파수는 A4 = 440 Hz 12평균율이며,
**정수 Hz 로 반올림한 표를 소스에 박아 둔다**(세 언어가 같은 표를 갖는다).

### 21.3 사각파 합성

```
샘플레이트 22050, 8비트 부호 없는 모노
반주기 = floordiv(22050, 2 * f_actual)  샘플마다 진폭을 0x40 / 0xC0 로 뒤집는다
```

PIT 은 사각파만 낼 수 있었다. 음량 조절이 없었고(듀티비 고정), 그래서
도스 게임의 스피커 음악은 전부 같은 음색이다.

WAV 헤더 44바이트 + PCM. 전체 바이트의 FNV-1a 를 골든으로 두고 세 언어가 대조한다.
**소리를 재생하지는 않는다** — 헤드리스 환경이고, 바이트가 같으면 소리도 같다.

## 22. 래스터 — 모듈 `raster`

### 22.1 프레임버퍼

```
fb[320 * 200]     팔레트 인덱스 (0..255)
```

세 언어 모두 1차원 정수 배열이다. 이것이 세 구현을 **바이트 단위로 비교 가능**하게
만드는 유일한 이유다. 각 프런트엔드는 이 배열을 팔레트로 색을 입혀 화면에 올릴 뿐이다.

### 22.2 팔레트와 명암표

```
pal[256][3]       각 성분 0..63 (VGA DAC 6비트, claims.md A2)
light[L][256]     명암 단계 L(0..3)에서 색 c 가 되는 팔레트 인덱스
```

명암표는 시작할 때 한 번 만든다. `light[l][c]` 는 `pal[c]` 의 각 성분에
`l/3` 을 곱한 색과 **가장 가까운** 팔레트 항목이다.

```
거리 = (dr)² + (dg)² + (db)²          가장 작은 것, 동점이면 인덱스 최소
```

256 × 256 × 4 = 262,144 회 비교이며 시작할 때 한 번이다. 안개(§14.4)가 이 표를 쓴다.

### 22.3 스프라이트

```
헤더: w(1) h(1) ox(1) oy(1)          ox, oy 는 발밑 기준점
본문: RLE — (count, value) 쌍. value 0 은 투명(컬러키)
```

`ox, oy` 가 기준점인 이유는 유닛이 **발밑**으로 정렬되기 때문이다(§23.3).

### 22.4 클리핑 블릿

런 단위로 자른다. 픽셀마다 경계를 검사하지 않는다.

```
가시 구간 [max(0, x), min(320, x + w)) 를 먼저 구하고
각 런에 대해 그 구간과의 교집합만 쓴다
```

**정리 22.1.** 이 방식은 픽셀당 비교를 없앤다. 완전히 화면 밖인 스프라이트는
런을 하나도 훑지 않고 반환한다.

### 22.5 플레이어 색 리맵

```
PLAYER_BASE = 160,  플레이어당 8단계
스프라이트는 항상 160..167 로 그려져 있고, 블릿할 때 owner * 8 을 더한다
```

색을 여덟 벌 그리지 않는다. 도스 시절의 표준 요령이며, 8부에서 원본 한 장과
네 색 결과를 나란히 보인다.

### 22.6 팔레트 사이클링

물 색 인덱스 232…239 를 8틱마다 한 칸씩 돌린다. 프레임버퍼는 건드리지 않는다.
**공짜 애니메이션**이며, 이것이 팔레트 모드의 가장 큰 장점이었다.

사이클 위치는 상태의 일부(`pal_phase`)이며 렌더 결과를 바꾸므로 **PPM 비교에
영향을 준다.** 그래서 해시에는 넣지 않지만 트레이스에는 넣는다.

### 22.7 5방향으로 8방향 그리기

```
그려진 것: 0(N) 1(NE) 2(E) 3(SE) 4(S)
파생:      7(NW) = 1 좌우 반전,  6(W) = 2 반전,  5(SW) = 3 반전
```

메모리와 아티스트 시간을 동시에 아끼는 요령이다. 좌우 반전은 블릿 안에서
**런의 순서와 각 런 안의 픽셀 순서를 뒤집어** 처리한다.

### 22.8 6×8 비트맵 폰트

ASCII 32…126, 글자당 8바이트(각 바이트가 한 줄의 6비트). 소스에 정수 배열로 박는다.
외부 폰트 파일이 없다 — 덱이 자기완결형이어야 하듯 엔진도 그렇다.

### 22.9 더티 렉트

바뀐 사각형만 다시 그린다. 목록이 8개를 넘으면 **전체를 다시 그린다**(합치는
비용이 이득을 넘는 지점을 실측으로 정했다 — `out/bench.txt` 6절).

### 22.10 PPM 출력

```
"P6\n320 200\n255\n" (15바이트) + 320·200·3 = 192,000바이트  → 총 192,015바이트
```

팔레트 성분 0…63 을 0…255 로 펴는 식은 `v * 255 / 63` 이 아니라

```
expand(v) = v * 4 + floordiv(v, 16)
```

이다. `63 → 255`, `0 → 0` 이고 곱셈·나눗셈 하나씩이다. 세 언어가 같은 정수 식을
써야 PPM 이 바이트 단위로 같아진다.

## 23. 화면 구성 — 모듈 `render`

### 23.1 레이어 순서

```
1. 지형 타일 (뷰포트)
2. 건물·유닛 스프라이트 (y 정렬)
3. 투사체
4. 체력바·선택 표시
5. 안개 오버레이 (§14.4)
6. 우측 패널 (미니맵 + 선택 정보)
7. 하단 바 (크레딧·인구·메시지)
8. 커서
```

안개가 스프라이트 **뒤가 아니라 위**에 오는 것이 중요하다. 안개 속 유닛은
어두워지는 것이 아니라 **보이지 않아야** 하는데, 그 처리는 5단계에서 한다.

### 23.2 스크롤

```
cam_x, cam_y      뷰포트 좌상단의 월드 픽셀 좌표 (정수, 16.16 아님)
clamp:            0 <= cam_x <= MAP_W * TILE - VIEW_W = 1024 - 256 = 768
```

카메라는 **정수 픽셀**이다. 서브픽셀 스크롤은 도스 시절 흔치 않았고,
정수로 두면 타일 그리기가 오프셋 하나로 끝난다.

```
첫 타일 = floordiv(cam_x, TILE),  픽셀 오프셋 = fmod(cam_x, TILE)
그릴 타일 수 = floordiv(VIEW_W, TILE) + 1 = 17
```

가장자리 스크롤: 마우스가 화면 가장자리 8px 안에 있으면 그 방향으로 4px/틱.

### 23.3 y 정렬

스프라이트를 **발밑 y** 로 정렬한다. 동점이면 x, 그다음 핸들.

```
key = (foot_y, foot_x, handle)
```

정렬은 삽입 정렬이다. 엔티티 목록이 프레임 사이에 거의 정렬되어 있으므로
거의 O(n) 이고, 무엇보다 **안정 정렬 여부에 의존하지 않는다** — 키가 전순서다.

### 23.4 미니맵

64×64 맵을 64×64 픽셀에 그리므로 **한 타일이 한 픽셀**이다. 축소가 필요 없다.

그럼에도 축소 코드를 갖춘다(맵이 128이 되면 필요하고, 5부의 주제이기도 하다).

```
nearest(sx, sy)  = 원본 (sx * MAP_W / MINI_W, ...) 한 점
majority(sx, sy) = 그 블록에서 가장 많이 나온 지형, 동점이면 지형 번호 최소
```

미니맵 클릭의 역변환은 `tx = sx * MAP_W / MINI_W` 이고, 카메라를 그 타일이
**뷰포트 중앙**에 오도록 옮긴 뒤 클램프한다.

### 23.5 패널과 하단 바

우측 64px: 위 64px 는 미니맵, 아래 112px 는 선택된 유닛의 초상·체력·명령 버튼.
하단 24px: 크레딧, 인구, 마지막 메시지 한 줄.

숫자는 §22.8 의 6×8 폰트로 그린다. 자릿수는 고정 폭이다 — 숫자가 흔들리면
더티 렉트가 커진다.

| 0 | 보병 `INF` | 40 | 6 | 3 | 1 | 1 | 12 | 98304 (1.5) | 4 | 100 | 60 | 1 |
| 1 | 사수 `ARCHER` | 30 | 4 | 6 | 0 | 4 | 16 | 91750 (1.4) | 5 | 140 | 80 | 1 |
| 2 | 전차 `TANK` | 90 | 12 | 8 | 4 | 3 | 24 | 131072 (2.0) | 5 | 300 | 150 | 2 |
| 3 | 박격포 `MORTAR` | 35 | 10 | 12 | 0 | 6 | 40 | 65536 (1.0) | 4 | 260 | 140 | 2 |

**이동 종류**(§4.3)는 `TANK` 와 `HARV` 가 차량(`VEH_BIT`), 나머지 셋이

`MORTAR` 만 포물선 투사체(§15.4)와 스플래시(§15.5)를 쓴다. `ARCHER` 는 직선
투사체, 나머지는 즉시 명중이다. `HARV` 는 공격하지 않는다.

### 25.3 기술 트리 (DAG, §16.6)

```
HQ   → HARV, REF, BARR
BARR → INF, ARCHER, TOWER
POW  ─┐
BARR ─┴→ FACT → TANK, MORTAR
```

`FACT` 만 선행 조건이 둘이다. 위상 정렬이 실제로 필요한 유일한 자리이며,
그래서 일부러 넣었다.

### 25.4 시작 조건

```
플레이어마다: HQ 1채, HARV 2기, 크레딧 1000
HQ 는 3×3 이고 좌상단이 (시작 x − 1, 시작 y − 1) 이다 — 시작 타일이 중앙에 온다.
HARV 는 HQ 오른쪽 아래 두 칸에 놓는다.
맵: golden/map_start.txt (64×64, 2회 대칭, 시작점 (8,8) 과 (55,55))
```

시나리오는 **1200틱**(약 66초)이다. 맵 대각선이 47타일이고 보병 속도가
1.5 px/틱 = 0.094 타일/틱이므로 횡단에만 500틱이 든다. 600틱으로는 기지 하나가
무너지는 것을 볼 수 없다 — 그 계산을 하고 나서 길이를 정했다.

### 25.5 생산 속도

`progress += 1` 이 매 틱이므로 "생산틱"이 곧 걸리는 틱 수다. 발전소가 부족해도
느려지지 않는다 — 전력 개념을 넣지 않았다. C&C 의 전력 규칙은 재미있지만
이 덱이 설명하려는 수학이 아니고, 규칙 하나를 줄이면 명세 한 쪽이 줄어든다.

### 26.1 이 명세를 고치는 절차

1. `SPEC.md` 를 먼저 고친다.
2. 골든을 다시 만든다 (`make golden`).

하나가 뒤처지고, 그 사실은 골든이 이미 바뀐 뒤에야 드러난다.
