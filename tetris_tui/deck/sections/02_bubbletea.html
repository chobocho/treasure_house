Bubble Tea 첫걸음

이 부에서는 테트리스 코드가 한 줄도 안 나온다. 작은 프로그램 일곱 개로 프레임워크만 익힌다. 4부부터 게임이다.

Bubble Tea 는 Go 로 터미널 UI 를 만드는 프레임워크다. 만든 곳은 Charm 이고, 공식 설명에 따르면 Evan Czaplicki 등의 The Elm Architecture 와 TJ Holowaychuk 의 go-tea 를 바탕으로 한다.

pkg.go.dev 에 남아 있는 가장 오래된 공개 버전은 v0.7.0, 2020년 5월이다. 이 덱은 그 뒤에 나온 v2 를 쓴다.

v1 과 v2 는 모듈 경로가 다르다 v2 의 경로는 github.com/charmbracelet/bubbletea/v2 가 아니라 charm.land/bubbletea/v2 다. 앞의 것으로 받으려 하면 "module declares its path as charm.land/…" 오류가 난다. 인터넷의 예제 대부분은 v1 이니, 시그니처가 다르면 그것부터 의심하라.

Elm 아키텍처 — 고리 하나

구조가 단순해서 그림 한 장에 다 들어간다. 상태는 한 곳에만 있고, 흐름은 한 방향이다.

중요한 것은 화살표가 한 방향이라는 점이다. View 는 Model 을 못 고치고, Update 는 화면을 직접 못 건드린다. 그래서 "어디서 상태가 바뀌었지?"를 찾을 필요가 없다 — 답은 언제나 Update 다.

Model 인터페이스 — 이게 전부다

Bubble Tea 가 요구하는 것은 메서드 셋뿐이다. v2 의 실제 정의를 go doc 으로 뽑으면:

type Model interface {
	// Init 은 가장 먼저 불린다. 처음부터 시킬 일이 있으면 Cmd 로.
	Init() Cmd

	// Update 는 메시지가 올 때마다. 바뀐 모델과 (필요하면) 다음 Cmd 를 돌려준다.
	Update(Msg) (Model, Cmd)

	// View 는 Update 뒤마다 불려서 화면을 만든다.
	View() View
}
Msg아무 타입이나 된다(any). 키 입력·창 크기·타이머· 우리가 만든 타입 — 전부 메시지다
Cmdfunc() Msg. "나중에 이 메시지를 만들어 달라"는 주문서
Viewv2 에서는 구조체다. Content 가 화면 글자이고, AltScreen 같은 필드가 함께 있다
v1 과 다른 점 v1 의 View() 는 string 을 돌려줬다. v2 는 View 구조체다. 인터넷 예제를 그대로 붙이면 여기서 컴파일이 깨진다.

① 01_hello — 가장 작은 프로그램

먼저 돌려 보자.

$ go run ./examples/01_hello

글자 두 줄이 전부다. 그런데 이건 완전한 TUI 프로그램이다 — raw 모드도, 화면 지우기도, 키 파싱도 전부 프레임워크가 하고 있다.

Init — 시작할 때 딱 한 번

Init 은 프로그램이 뜰 때 한 번 불린다. 처음부터 시킬 일이 있으면 Cmd 로 돌려주고, 없으면 nil 이다.

  • 타이머를 걸고 싶다 → tea.Tick(...) 을 돌려준다 (04_tick)
  • 파일을 읽고 싶다 → 읽는 함수를 Cmd 로 감싸 돌려준다
  • 할 일 없다 → nil
Init 은 한 번만 불린다 프로그램이 시작할 때만이다. 나중에 화면을 다른 모델로 바꿔 끼우면(9부의 메뉴) 그 모델의 Init 은 우리가 직접 불러 줘야 한다. 이걸 빠뜨리면 새 화면에서 시간이 안 흐른다 — 실제로 밟는 함정이다.

Update — 사건이 오는 유일한 문

읽는 순서는 이렇다.

  1. switch msg := msg.(type) — 온 메시지가 어떤 종류인지 가른다
  2. tea.KeyPressMsg 면 msg.String() 으로 사람이 읽는 이름을 얻는다
  3. 끝낼 키면 tea.Quit 을 돌려준다
  4. 그 외에는 모델을 그대로, Cmd 는 nil 로 돌려준다

tea.Quit 은 함수를 부르는 게 아니라 값이다. 정확히는 func() Msg 타입이라 그 자체가 Cmd 다. "지금 끝내라"가 아니라 "끝내라는 메시지를 만들어 달라"는 주문서다.

View — 화면 전체를 문자열 하나로

여기에 커서를 옮기거나 화면을 지우는 코드가 한 줄도 없다는 점을 보라. 우리는 "지금 화면은 이렇게 생겼다"만 말한다. 이전 화면과 비교해서 무엇을 다시 그릴지는 Bubble Tea 가 정한다.

main 도 세 줄이다. tea.NewProgram(모델).Run() — raw 모드 전환, 신호 처리, 화면 복구가 전부 이 안에 있다.

종료할 때 화면이 한 번 더 그려진다 Quit 을 돌려주면 곧장 죽는 게 아니라, 마지막 View 가 렌더된 뒤에 내려간다. 그래서 quitting 필드를 두고 작별 인사를 띄울 수 있다.

Msg 는 무엇이든 될 수 있다

Bubble Tea 의 Msg 는 any 다. 그래서 사건의 종류가 타입으로 표현된다. 이게 이 프레임워크의 가장 큰 아이디어다.

라이브러리가 보내는 것

  • tea.KeyPressMsg · KeyReleaseMsg
  • tea.WindowSizeMsg
  • tea.MouseClickMsg 등
  • tea.FocusMsg · BlurMsg
  • tea.QuitMsg · InterruptMsg

우리가 만드는 것

  • tickMsg — 시간이 흘렀다 (04)
  • moveMsg — AI 가 수를 골랐다 (07·7부)
  • noteMsg — 기록 한 줄 (07)
  • AIMoveMsg — 어느 자리의 결과인가 (7부)

메시지 타입은 필드가 없어도 된다. type doneMsg struct{} 처럼 타입 이름 자체가 사건의 이름인 경우가 많다.

② 02_counter — 상태가 생기면

숫자 하나를 올렸다 내리는 프로그램. 여기서 Bubble Tea 의 가장 중요한 규칙을 만난다.

파일 머리 주석에 답이 이미 적혀 있다. 모델은 값이다.

모델은 값이다 — 가장 흔한 첫 실수

m.n++ 은 복사본을 늘린다. 그 복사본을 return 해야 비로소 반영된다.

이걸 빠뜨리면 화면이 영원히 0 에 머문다. 그리고 오류도, 경고도 안 난다 — 컴파일도 되고 프로그램도 잘 돈다. 숫자만 안 변한다. "왜 안 변하지?"로 하루를 날리는 자리가 정확히 여기다.

포인터 리시버(func (m *model) Update)를 쓰고 싶어지겠지만 참으라. 값이라서 얻는 것이 크다:

  • 이전 상태가 저절로 보존된다 — 실행 취소·되감기가 공짜다
  • 테스트가 쉬워진다 — 모델을 만들고 Update 를 부르면 끝이다 (8부)
  • 동시성 사고가 원천적으로 줄어든다 — 공유되는 것이 없다

02_counter — 나머지

여기까지가 "상태가 있는 프로그램"의 전부다. 앞으로 나올 모든 모델이 이 모양이다 — 필드가 늘고 switch 가 길어질 뿐이다.

③ 03_keys — 키가 실제로 어떻게 오는가

테트리스를 만들다 보면 "왜 이 키가 안 먹지?"에 반드시 부딪힌다. 답은 거의 항상 "내가 상상한 이름과 실제 이름이 다르다"이다.

그래서 규칙을 외우는 대신, 눌러 보고 확인하는 도구를 먼저 만든다.

tea.KeyPressMsg 해부

조각무엇예
String()사람이 읽는 이름. switch 에는 이걸 쓴다 "left" "ctrl+c" "a" "space"
Code눌린 키(rune). 문자이거나 tea.KeyLeft 같은 특수값 'a' · tea.KeyEscape
Text실제로 입력된 문자. 특수 키·조합 키에서는 빈 문자열"a" · ""
Modctrl/alt/shift 비트. & 로 검사 tea.ModCtrl
이 표를 외우지 말고 테스트로 못 박아라 이 프로젝트는 키 이름을 테스트로 확인해 뒀다. 라이브러리가 이름을 바꾸면 switch 가 조용히 죽는데, 테스트는 그 자리에서 빨개진다. 8부에서 그 테스트를 본다.

03_keys — 기록하고 자르기

기록에 상한을 두는 이유가 있다. 없으면 줄이 화면 밖으로 넘치고, 터미널이 스크롤되면서 이전 화면이 지저분하게 남는다. 상한은 TUI 의 기본 예의다.

그리고 이 예제에서는 q 도 "그냥 키"로 보여 줘야 하므로 ctrl+c 만 종료로 쓴다.

03_keys — 키 하나를 한 줄로

Code 를 %q 로 찍는 이유는 '\x1b' 같은 특수값도 안전하게 보이기 때문이다. 그냥 %c 로 찍으면 이스케이프가 터미널로 새어 나가 화면이 망가진다.

Mod 는 비트 묶음이라 & 로 하나씩 검사한다. 여러 개가 동시에 켜질 수 있다.

03_keys — 화면

직접 돌려서 화살표·ctrl 조합·한글을 눌러 보라. 특수 키에서 Text 가 빈다는 것을 눈으로 확인하는 게 이 예제의 목적이다.

④ 04_tick — 시간을 흐르게 하기

Bubble Tea 에는 "매 프레임 도는 루프"가 없다. 게임 엔진에서 오면 이게 제일 낯설다.

시간이 흐르게 하려면 tea.Tick 으로 "이 시간 뒤에 이 메시지를 보내 달라"고 예약한다.

04_tick — 예약하는 쪽

tea.Tick 은 (기간, 시각→메시지 함수)를 받아 Cmd 를 만든다. 이 함수를 doTick() 한 군데에 모아 두면 "예약을 빠뜨렸다"를 눈으로 잡기 쉬워진다.

틱 간격을 상수 하나로 고정한 것도 이유가 있다. 예약하는 쪽과 경과 시간을 계산하는 쪽이 서로 다른 숫자를 쓰면 화면의 시계가 조용히 틀려진다.

초보자가 반드시 한 번 밟는 함정

tea.Tick 은 한 번만 보낸다 받은 자리에서 다시 예약하지 않으면 시계가 한 번 뛰고 영영 멈춘다. 반복 타이머가 아니다.

return m, doTick() 이 사슬의 다음 고리다. 이게 빠지면 시계가 죽는다.

멈췄다 다시 시작하는 경우도 챙겨야 한다. 멈춘 동안에는 사슬을 안 이었으므로, 재개하는 자리에서 새로 시작해 줘야 한다. 그러지 않으면 space 를 눌러도 시간이 안 흐른다.

04_tick — 화면

틱 수 × 간격 = 경과 시간. 5부의 중력도 똑같이 "몇 틱 지났나"로 계산한다. 이 예제가 곧 테트리스의 시계다.

Tick 과 Every — 무엇이 다른가

tea.Tick(d, fn)부른 그 순간부터 d 만큼 센다. 간격이 정확히 d 다
tea.Every(d, fn)시스템 시계에 맞춰 센다. 1분 간격이면 12:34:20 에 걸어도 다음은 12:35:00 이다

여러 가지가 같은 박자로 뛰어야 할 때는 Every 가 편하다. 게임의 중력처럼 "예약한 시점부터 정확히"가 필요하면 Tick 이다. 이 프로젝트는 전부 Tick 을 쓴다.

둘 다 한 번만 보낸다 이름이 Every 라고 반복되는 게 아니다. 재예약은 똑같이 우리 몫이다.

⑤ 07_cmds — Cmd 는 주문서다

Cmd 의 정의는 놀랄 만큼 단순하다.

type Cmd func() Msg

함수 하나다. 부르기 전에는 아무 일도 일어나지 않는다. Update 는 "이 함수를 나중에 불러서 그 결과를 나에게 보내 달라"고 말할 뿐이다.

이 구조 덕분에 Update 가 순수하게 유지된다 — 들어온 메시지와 모델만 보고 새 모델을 만들 뿐, 파일을 읽거나 잠들거나 하지 않는다. 그게 테스트를 쉽게 만든다.

오래 걸리는 일은 밖으로

Update 안에서 시간을 쓰면 화면이 얼어붙는다 키도 안 먹고, 중력도 안 돌고, 상대 판도 멈춘다. Update 는 빨리 끝나야 하는 함수다.

think 가 돌려주는 함수 안의 코드는 Update 와 다른 고루틴에서 돈다. 그래서 규칙이 하나 붙는다:

Cmd 안에서 모델을 건드리지 마라 필요한 값은 인자로 복사해서 넘기고, 결과는 오직 반환하는 메시지로만 전달한다. 7부의 AI 탐색이 정확히 이 규칙을 지킨다 — 판을 통째로 복사해서 넘긴다.

Batch 와 Sequence

tea.Batch(a, b)둘을 동시에 띄운다. 도착 순서는 보장 안 함
tea.Sequence(a, b)a 가 끝나야 b 를 시작한다. 순서가 중요할 때

t 를 두 번 눌렀을 때 무시하는 처리도 눈여겨보라. 안 그러면 Cmd 가 겹쳐서 결과가 두 번 오고 조각이 두 번 움직인다. 7부의 AI 드라이버도 같은 이유로 "이미 생각 중이면 또 요청하지 않는다"를 지킨다.

07_cmds — 나머지와 화면

push 가 값 리시버라 새 모델을 돌려준다는 점을 보라. 이 파일의 모든 상태 변경이 그 모양이다 — m = m.push(...).

⑥ 05_window — 창 크기에 반응하기

Bubble Tea 는 시작할 때 한 번, 그리고 창이 바뀔 때마다 tea.WindowSizeMsg 를 보낸다. 필드는 둘뿐이다 — Width, Height.

주석의 두 항목이 이 예제의 전부다. 다음 장에서 하나씩 본다.

05_window — 두 가지 함정

① 크기를 아직 모를 때

첫 WindowSizeMsg 가 오기 전에도 View 가 불린다. 그때 w = h = 0 이다. 그 값으로 Place(0, 0, …) 를 부르면 안 된다.

② 너무 좁을 때

깨진 화면 대신 지금 크기와 필요한 크기를 알려 준다. "터미널을 키워 주세요"가 백 배 낫다.

lipgloss.Place 는 주어진 폭·높이 안에 내용을 놓고 나머지를 공백으로 채운다. 결과의 크기가 창과 정확히 같아야 터미널이 스크롤되지 않는다.

05_window — 화면

직접 돌려 놓고 터미널 창을 마우스로 끌어 보라. 숫자가 따라 바뀌고, 40×12 보다 작아지면 안내로 바뀐다.

5부와 7부의 게임 화면이 이 구조를 그대로 쓴다 — 갈래 셋(모름 / 좁음 / 정상)이 똑같다.

tea.NewProgram 의 옵션

지금까지는 tea.NewProgram(model{}) 만 썼다. 필요할 때 붙이는 것들:

WithInput(r) / WithOutput(w) 입출력을 바꿔 끼운다. 테스트에서 쓴다
WithoutRenderer()화면을 안 그린다. 로직만 돌릴 때
WithWindowSize(w, h)창 크기를 강제로 알려 준다
WithFPS(n)초당 몇 번까지 그릴지
WithContext(ctx)바깥에서 프로그램을 끝낼 수 있게
WithoutCatchPanics()패닉을 가로채지 않는다. 디버깅할 때
이 프로젝트는 옵션을 하나도 안 쓴다 테스트가 프로그램을 아예 안 띄우기 때문이다 — 모델이 값이라 Update 를 직접 부르면 된다. 8부에서 그 방식을 자세히 본다.

디버깅 — 화면에 print 할 수 없다

fmt.Println 을 쓰면 화면이 망가진다 Bubble Tea 가 그리는 화면 한가운데에 글자가 끼어들기 때문이다. 전체 화면 프로그램에서 표준 출력은 이미 쓰이고 있는 자원이다.

방법이 셋 있다.

  1. 파일로 남긴다 — tea.LogToFile("debug.log", "디버그") 를 부르면 표준 log 패키지의 출력이 그 파일로 간다. 다른 터미널에서 tail -f.
  2. 화면에 띄운다 — 모델에 디버그 문자열 필드를 하나 두고 View 아래에 그린다. 가장 빠르고, 게임에서는 대개 이걸로 충분하다.
  3. 테스트로 옮긴다 — 값 모델의 진짜 장점이다. "이 키를 눌렀을 때 이렇게 돼야 한다"를 테스트로 적으면 디버깅이 필요 없어진다.

2부 정리

Model상태 전부. 값이다 — Update 는 복사본을 받는다
Update메시지 하나 → 새 모델 + (필요하면) Cmd. 빨리 끝나야 한다
View모델 → 화면 글자. 커서를 옮기는 코드는 없다
Msg아무 타입이나. 타입 이름이 곧 사건의 이름
Cmdfunc() Msg. 오래 걸리는 일을 밖으로 내보내는 통로. 다른 고루틴에서 돈다
Tick한 번만 보낸다. 받은 자리에서 다시 예약해야 시계가 산다
WindowSize첫 메시지 전에는 0×0. 좁으면 이유를 말해 준다
