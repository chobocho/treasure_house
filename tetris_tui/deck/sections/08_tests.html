테스트와 기록

이 프로젝트의 테스트는 프로그램을 한 번도 안 띄운다. 터미널도, PTY 도, 가짜 입력도 없다.

Bubble Tea 모델이 값이기 때문에 가능한 일이다. 모델을 하나 만들고, Update 에 메시지를 넣고, 돌아온 모델을 들여다보면 끝이다.

패키지 16개 중 테스트가 있는 15개가 전부 통과한다 (cmd/tetris 의 pick 은 menu.Build 를 부르는 얇은 껍질이고, 그 Build 는 menu 패키지의 테스트가 전수로 본다). 가장 오래 걸리는 것이 ai 인데 그것도 2초 남짓이다 — 400조각짜리 판을 56번 두는 파리티 테스트 때문이다.

헤드리스로 모델 굴리기

headless 가 이 파일의 모든 테스트가 시작하는 자리다. 타이머를 끄고, 창 크기를 알려 주고, 모델을 돌려준다.

key(name) 헬퍼도 필요하다. 특수 키는 Code 로, 글자 키는 Code + Text 로 만들어야 String() 이 우리가 기대하는 이름을 낸다.

시드와 타이머를 시험한다

t.Skip 을 쓰는 자리를 보라. 시드 42 와 43 의 첫 상태가 우연히 같으면 그 테스트로는 아무것도 확인할 수 없다. 거짓으로 통과시키느니 건너뛴다고 말하는 편이 낫다.

틱 사슬을 테스트로 못 박기

Update 가 돌려준 cmd 를 직접 실행해서 그 결과가 다시 TickMsg 인지 본다. 프로그램을 안 띄우고도 "사슬이 이어졌는가"를 확인할 수 있다.

Cmd 를 부르는 것은 안전한가 이 경우는 그렇다. tea.Tick 이 만든 Cmd 는 잠들었다가 메시지를 돌려줄 뿐이다. 테스트가 33ms 를 기다리는 셈인데, 그 정도는 낼 만하다.

"조각이 혼자 움직이지 않는가"

키를 한 번 누르고 660ms(20틱)를 흘린다. 코어의 DAS 가 켜져 있었다면 170ms 뒤부터 자동반복이 돌아 조각이 벽까지 갔을 시간이다.

소프트드롭은 반대다 — 눌렀을 때 내려가야 하고, 한동안 조용하면 멈춰야 한다. 둘 다 확인한다.

화면을 어떻게 시험하는가

화면을 글자로 비교하면 깨지기 쉽다. 색 하나만 바뀌어도 실패한다. 그래서 이 프로젝트는 성질을 본다.

크기lipgloss.Size() 가 창을 안 넘는가
내용"다음"·"홀드"·"점수" 같은 말이 들어 있는가
안내좁을 때 지금 크기와 필요한 크기가 둘 다 적혔는가
경계딱 최소 크기면 정상, 1 작으면 안내

Cmd 를 펼쳐 가며 대전을 돌린다

tea.Program 없이 모델을 굴리는 방법이다. 틱을 넣고, 돌아온 Cmd 를 실행하고, 그 결과 메시지를 다시 넣는다.

Batch 는 펼치고, 틱은 버린다 — 틱은 우리가 직접 넣는 것이므로 모델이 예약한 틱까지 따라가면 시간이 두 배로 흐른다.

이 스무 줄이 통합 테스트 전부다 AI 가 실제로 두는지, 공격이 실제로 가는지, 라운드가 실제로 끝나는지 — 전부 이 루프 위에서 확인한다.

레이스 검출기를 못 쓸 때

이 기계에서는 go build -race 가 -race is not supported on android/arm64 로 거절한다.

그래서 설계로 막고 테스트로 확인한다 — 탐색이 Update 안이 아니라 Cmd 에서 도는지, 그 Cmd 를 실제로 실행해도 판과 stats 가 그대로인지, 두 테스트로 본다.

완벽한 대체는 아니다. 레이스 검출기는 "우연히 안 겹친 경우"도 잡지만 이 테스트는 못 잡는다. 쓸 수 있는 환경이라면 둘 다 하는 것이 맞다.

가정을 테스트로 못 박기

TestKeyNamesAreWhatWeAssume 가 이 프로젝트에서 가장 값싼 보험이다. 라이브러리가 키 이름을 바꾸면 우리 switch 가 조용히 죽는데, 이 테스트는 그 자리에서 빨개진다.

키 충돌을 세 가지로 검사한다

뒤의 세 테스트가 없으면 2인용에서 "한 키가 양쪽을 동시에 움직이는" 버그가 언제든 들어올 수 있다. 그리고 그건 눈으로 보기 전까지 안 보인다.

  1. 한 키맵 안에서 같은 키가 두 번
  2. 두 자리가 같은 키를 공유
  3. 전역 키가 자리 키와 겹침

테스트가 실제로 뭘 잡는지 확인하기

테스트가 통과하는 것만으로는 부족하다. 틀렸을 때 잡히는지를 확인해야 한다. 이 프로젝트는 두 곳에서 코드를 일부러 망가뜨려 봤다.

변이결과
ClearLines 의 y++ 제거 파리티가 잡았다 — 시드 2654435769 의 1018스텝
킥 표의 마지막 후보 한 칸 변조 파리티는 못 잡았다(그 킥을 안 밟는다). 구조 단위 테스트가 잡았다
이게 알려 주는 것 파리티는 "실제로 일어나는 일"을 넓게 훑고, 구조 테스트는 "표가 표답게 생겼는가"를 좁게 본다. 어느 한쪽만으로는 구멍이 남는다. 그리고 그 구멍은 변이를 넣어 보기 전까지 안 보인다.

화면을 기록하는 도구

덱에 "이렇게 보입니다" 하고 손으로 그린 화면을 실으면 그건 거짓말이 된다. 코드가 바뀌어도 그림은 안 바뀌기 때문이다.

그래서 화면은 전부 여기서 뽑는다 — 스크립트를 정해 두고, 진짜 모델을 돌려서, 진짜 View 문자열을 저장한다.

결정론이 이 도구의 전부다

같은 스크립트를 두 번 돌리면 파일이 바이트까지 같아야 make record 뒤의 git diff 가 비어 있고, 덱의 그림이 소스와 어긋날 수가 없다.

그래서 시각도, 난수도 여기서는 쓰지 않는다. 틱은 스크립트가 준다.

스크립트 — 세 가지 낱말

left right space   키 누르기
wait               틱 하나
wait30             틱 30번 — 프레임은 그래도 한 장만
100x40             창 크기 변경

wait30 이 왜 필요한가. AI 대 AI 한 판은 수천 틱이다. 틱마다 프레임을 남기면 JSON 이 수 MB 가 되어 덱에 실을 수가 없다.

모르는 낱말은 오류다. 조용히 무시하면 "왜 이 키가 기록에 없지?"로 한나절을 쓴다.

기록기도 Cmd 를 실행해야 한다

Cmd 를 무시하면 기록 속 AI 가 한 수도 안 둔다 AI 의 탐색은 Cmd 안에서 돈다(7부). 기록기가 Cmd 를 실행하지 않으면 "고른 수"가 영영 도착하지 않는다. 처음에 이걸 빠뜨려서 AI 모드 기록이 가만히 서 있는 화면만 나왔다.

단, 틱 메시지는 되먹이지 않는다. 틱은 스크립트가 주는 것이고, 모델이 예약한 틱까지 따라가면 시간이 두 배로 흐른다.

모드마다 틱 메시지가 다르다

game.TickMsg 와 battle.TickMsg 는 다른 타입이다. 기록기가 그 타입을 알아야 wait 를 그 모드가 알아듣는 신호로 바꿀 수 있다.

그래서 등록부가 생성자와 틱 메시지를 함께 들고 있다. 시드도 고정해 둔다 — 기록은 다시 돌렸을 때 바이트까지 같아야 하는 물건이다.

ANSI 를 HTML 로 — 왜 미리 푸는가

덱 안의 재생기를 120줄 남짓으로 유지하고 싶기 때문이다. ANSI 파서는 생각보다 손이 많이 가고, 한 번만 돌면 되는 일을 화면을 넘길 때마다 다시 할 이유가 없다.

색은 클래스가 아니라 그 터미널이 낸 색 그대로다. 덱의 배색으로 바꿔치기하면 그건 더 이상 캡처가 아니다.

바뀐 줄만 저장한다

터미널 화면은 프레임 사이에 대부분 그대로다. 조각 하나가 한 칸 내려갈 뿐인데 24줄을 전부 저장하면 파일이 열 배로 부푼다.

통째로 저장           1.49 MB
클래스 표 적용        1.20 MB
바뀐 줄만 저장        0.49 MB   ← 지금

1부에서 말한 "바뀐 줄만 다시 그린다"가 여기서 다시 나온다. Bubble Tea 의 렌더러도 같은 이유로 같은 일을 한다.

SGR 파라미터 읽기

클래스 표를 쓰는 이유는 크기다. 같은 색이 프레임마다 수백 번 되풀이되는데 그때마다 style="color:#5050a0;"(22바이트)를 적는 것과 class="a3"(10바이트)를 적는 것의 차이가 메가바이트 단위가 된다.

색 풀기 — 세 가지 표현

같은 색이 세 가지로 올 수 있다.

ESC[31m기본 16색 (30–37, 90–97)
ESC[38;5;196m256색 인덱스 — 6×6×6 큐브 + 24단계 회색
ESC[38;2;255;0;0m24비트

38/48 뒤에는 색 지정이 이어지므로, 파라미터를 하나씩 보는 게 아니라 커서를 옮겨 가며 읽어야 한다.

span 을 합치는 요령

스타일은 "글자를 쓸 때" 확정한다 이스케이프를 볼 때마다 끊으면, 리셋했다가 같은 색을 다시 켜는 흔한 패턴에서 span 이 칸 수만큼 생긴다. tmux 캡처가 딱 그렇다 — 칸마다 이스케이프를 넣는다. 그래서 글자를 쓰는 순간에만 "지금 스타일이 버퍼의 스타일과 다른가"를 본다.

처음에는 이스케이프마다 끊었더니 ████████ 하나가 span 네 개가 됐다. 합치니 하나가 된다.

줄 끝 공백은 변환 전에 지운다

변환 뒤에 지우려 하면 공백이 span 안에 갇혀 있어서 손댈 수가 없다. 그래서 변환 전에 각 줄에서 "마지막으로 눈에 보이는 글자" 뒤의 공백만 버린다.

이스케이프는 폭이 0 이므로 그대로 둔다 — 지우면 스타일 상태가 어긋난다.

폭 재기 — 다시 한 번 한글

재생기가 자리를 미리 잡으려면 화면의 칸 수를 알아야 한다. 여기서도 한글은 두 칸이다.

정확한 판정에는 유니코드 East Asian Width 표가 필요하지만, 여기서 다루는 글자는 ASCII·한글·박스 그리기 문자뿐이라 한글 영역만 두 칸으로 세면 충분하다. 그리고 블록 문자 █ 는 한 칸이다 — lipgloss 도 그렇게 센다.

변환기 진입점

입력이 .json 이면 프레임 묶음, 아니면 화면 한 장으로 다룬다. 한 장짜리는 클래스 표를 둘 곳이 없어서 인라인 style 을 쓴다 — 1.5 KB 남짓이라 그게 낫다.

덱 안의 재생기 — 120줄 남짓

// 0번부터 n번까지 덧칠해 화면 한 장을 만든다.
function frameAt(rec, n) {
  var lines = [];
  for (var i = 0; i <= n && i < rec.frames.length; i++) {
    var f = rec.frames[i];
    (f.d || []).forEach(function (d) { lines[d[0]] = d[1]; });
    lines.length = f.n;
  }
  for (var y = 0; y < lines.length; y++)
    if (lines[y] === undefined) lines[y] = '';
  return lines.join('\n');
}

뒤로 갈 때는 0번부터 다시 칠한다. 프레임이 수십 장뿐이라 그게 가장 단순하고 충분히 빠르다.

키는 [ 와 ] ←/→ 는 덱이 슬라이드를 넘기는 데 쓴다. 재생기가 그걸 가로채면 사용자가 슬라이드를 넘길 방법을 잃는다. 그래서 다른 키를 쓰고 버튼도 함께 뒀다.

tmux — 진짜 터미널에서 도는지

기록은 모델을 돌린 것이지 프로그램을 돌린 것이 아니다. raw 모드도, 렌더러도, 신호 처리도 안 거친다.

그래서 진짜 PTY 에서 한 번 더 확인한다. 에이전트 세션에는 터미널이 없으므로 tmux 로 하나 띄운다.

tmux new-session -d -s t -x 80 -y 24 "go run ./cmd/tetris -mode ai -seed 3"
sleep 5
tmux send-keys -t t Left Space
sleep 4
tmux capture-pane -e -p -t t > out/tmux_ai.txt    # -e 는 색을 남긴다
tmux kill-session -t t
tmux 가 공백 대신 탭을 넣는다 기본 스타일의 공백이 길게 이어지면 그 자리를 탭 하나로 줄여 내보낸다. 터미널에서는 결과가 같지만 <pre> 안에서는 탭 폭이 환경마다 달라 판이 어긋난다. 그래서 저장 직후에 deck/untab.py 가 칸 단위로 되돌린다.

Makefile — 전부 여기서 나온다

규칙 하나: 덱에 실리는 것은 전부 이 Makefile 이 만들어 낸 것이어야 한다. 화면도(record), 실행 증거도(tmux-smoke), 코드도(deck 이 소스에서 잘라 온다).

GOPROXY=off 로 못 박은 이유는 이 기계의 네트워크가 자주 끊기기 때문이다. 캐시만 보게 하면 "빌드 중 갑자기 멈춤"이 원천 차단된다.

Makefile — 기록과 변환

스크립트가 Makefile 에 그대로 적혀 있다. 어떤 키를 어떤 순서로 눌러서 그 화면이 나왔는지가 버전 관리에 남는다.

html 은 기록과 캡처를 덱이 읽는 형태로 바꾼다. 프레임은 재생기가 넘겨 보는 묶음으로, tmux 캡처는 한 장짜리 조각으로.

Makefile — tmux 캡처 순서

모드마다 창을 띄우고, 조금 기다리고, 키를 보내고, 화면을 긁는다. sleep 5 가 필요한 이유는 go run 이 컴파일부터 하기 때문이다.

마지막 줄이 deck/untab.py 를 부른다 — tmux 가 공백 대신 넣은 탭을 칸 단위로 되돌리는 후처리다.

Makefile — 증거 모으기와 덱 조립

make logs 가 이 덱에 "실제 출력"으로 실릴 로그들을 만든다. 지어낸 숫자를 슬라이드에 적지 않기 위한 장치다.

-count=1 이 붙어 있는 이유: 안 붙이면 Go 가 캐시된 결과를 보여 줘서 (cached) 만 잔뜩 찍힌다. 증거로는 쓸 수 없다.

make deck 이 두 단계인 것도 이유가 있다. gen_appendix.py 가 먼저 "아직 안 실린 줄"을 찾아 부록을 만들고, 그다음 build_deck.py 가 전체를 조립한다.

조립 끝에 gen_fonts.py 가 코드와 캡처에 실제로 쓰인 글자만 담은 D2Coding 서브셋(woff2)을 덱 안에 싣는다. 폰·태블릿에는 "한글 2칸·박스 1칸"을 지키는 글꼴이 없어서, 이걸 안 하면 터미널 캡처의 상자가 기기마다 다르게 깨진다.

덱이 스스로를 세는 방법

빌더가 파일마다 "몇 번째 줄이 몇 번 실렸는지"를 센다. 빠진 줄과 중복된 줄을 이름으로 찍고, 0 이 아니면 오류로 센다.

── 소스 커버리지 (덱에 실린 줄 / 전체 줄)
  Makefile                         172/172
  ai/features.go                   133/133
  ...
