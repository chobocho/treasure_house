1인용 게임 만들기

2~3부에서 배운 것들이 드디어 한자리에 모인다. 틱 재예약, 창 크기, Join, 값 의미론 — 전부 여기서 쓰인다.

그리고 이 부에는 게임 규칙이 한 줄도 없다. 회전이 되는지, 줄이 지워지는지, 점수가 얼마인지는 전부 core 가 안다. game 이 아는 것은 둘뿐이다:

어떤 키가 어떤 뜻인가

← 는 core.ActLeft. 그 뜻이 판에서 무엇을 하는지는 모른다.

지금 화면을 어떻게 그릴 것인가

core 가 준 두 층(굳은 블록·오버레이)을 ui 에 넘긴다.

키 배치를 데이터로 둔다

도움말 화면도, 입력 처리도, 이 덱의 조작표도 전부 이 한 곳을 읽는다. 세 군데에 따로 적어 두면 반드시 어긋나고, 어긋나는 쪽은 늘 도움말이라 사용자만 거짓말을 읽게 된다.

키 "이름"은 우리가 지어낸 게 아니라 Bubble Tea 의 msg.String() 이 만드는 값이다. 예제 03_keys 가 그걸 눈으로 확인하는 도구였다.

찾기와 도움말 — 같은 표에서 나온다

바인딩이 열 개 남짓이라 선형 탐색으로 충분하다. map 을 만들면 초기화 순서와 전역 상태가 늘어나는데, 키 입력은 초당 수십 번뿐이라 얻는 게 없다.

HelpLine 이 바인딩에서 문구를 자동으로 만든다. 배치를 바꾸면 도움말도 따라 바뀐다 — 손으로 적었다면 안 그랬을 것이다.

두 자리, 겹치지 않는 키

← → 이동
↓ 소프트드롭
↑ / x 시계 회전
z 반시계 회전
스페이스 하드드롭
c 홀드

회전에 ↑ 와 x 를 둘 다 두는 건 관례다. ↑ 는 직관적이고, x/z 짝은 시계·반시계를 한 손으로 누를 수 있어서 익숙해지면 더 빠르다.

왼쪽 자리의 하드드롭이 f 인 이유: 스페이스는 한 손으로 누르기 애매한 데다 오른쪽 자리가 쓴다. 두 자리가 키를 하나라도 공유하면 한 번의 입력이 양쪽 판을 동시에 움직인다.

전역 키 — 어느 자리에도 속하지 않는 것

일시정지·다시 시작·도움말·나가기는 판과 무관하다. 그래서 자리별 키맵과 따로 둔다.

전역 키가 자리 키와 겹치면 "왼쪽으로 옮기려 했는데 게임이 끝나는" 일이 벌어진다. 그래서 테스트가 세 가지 충돌을 매번 확인한다 — 한 키맵 안의 중복, 두 자리 사이의 중복, 전역과 자리 사이의 중복.

1인용 모델

틱 간격이 33ms 인 이유: 초당 30프레임쯤이다. 더 촘촘히 하면 터미널이 다시 그리는 비용만 늘고, 더 성기게 하면 레벨이 높을 때 조각이 뚝뚝 끊겨 떨어진다.

코어가 dt 를 100ms 로 자르므로 이 값이 그보다 크면 시간이 사라진다.

모델은 값, 판은 포인터

함정 — 모델은 값이지만 g 는 포인터다 그래서 Update 가 모델을 복사해도 두 복사본이 같은 판을 가리킨다. 1인용에서는 문제가 없지만(복사본이 하나뿐이므로), 7부의 두 자리에서는 이 성질이 버그의 원천이 된다. 7부에서 실제로 밟는다.

함수형 옵션(Option func(*Model))은 Go 에서 "기본값이 있는 생성자"를 만드는 관례다. 인자를 늘려도 기존 호출부가 안 깨진다.

WithoutTimer — 시간의 출처를 바꿀 수 있게

이게 이 모델을 시험 가능하게 만드는 요령이다 WithoutTimer() 를 주면 tea.Tick 을 안 건다. 그 대신 기록 도구와 테스트가 TickMsg 를 직접 밀어 넣는다. tea.Tick 은 실제로 잠들기 때문에 300프레임을 기록하려면 10초가 걸리고, 무엇보다 결과가 시계에 좌우된다.

nextSeed 가 LCG 로 시드를 한 칸 굴리는 것도 같은 이유다. 같은 시드로 다시 시작하면 죽은 판을 그대로 반복하게 되고, 시계를 쓰면 기록이 재현되지 않는다.

Update — 세 가지 메시지

04_tick 에서 배운 그대로다. return m, Tick() 이 사슬의 다음 고리이고, 이게 빠지면 중력이 한 번 뛰고 영영 멈춘다.

일시정지 중에도 사슬은 이어 둔다 끊으면 정지를 풀어도 시간이 안 흐른다. 코어가 정지 상태에서 Update 를 그냥 무시하므로, 틱을 계속 보내도 아무 일도 안 일어난다 — 안전하다.

없는 사건을 타임아웃으로 만들어 낸다

1부에서 말한 제약이 여기서 현실이 된다. 터미널은 키를 뗀 것을 안 알려 준다. 그래서 "누르고 있는 동안 빨리 떨어진다"를 그대로 구현할 수가 없다.

대신 마지막으로 ↓ 를 받은 뒤 120ms 조용하면 놓은 것으로 친다. OS 의 키 자동반복 간격보다 넉넉히 크게 잡아야 누르고 있는 도중에 끊기지 않는다. 그 간격은 운영체제 설정이라 알 수 없으므로, 흔한 값보다 두세 배 크게 잡았다.

이건 편법이다 그리고 그 사실을 코드 주석에 적어 뒀다. 문서에 "이렇게 동작합니다"라고만 쓰면 읽는 사람은 이게 제약을 우회한 결과라는 것을 끝내 모른다.

키 하나가 들어오면

전역 키를 먼저 보고 그다음 자리의 키맵을 본다. 지금은 둘이 안 겹치므로(테스트가 지킨다) 순서가 결과를 바꾸지 않지만, 나중에 누가 자리 키맵에 r 을 넣더라도 전역이 이기게 해 두는 편이 낫다 — "다시 시작이 안 먹는" 버그보다 "그 키가 자리 조작으로 안 먹는" 쪽이 훨씬 눈에 잘 띈다.

모르는 키는 조용히 무시한다. 게임 중에 오류를 띄우는 것은 최악의 선택이다.

좌우와 소프트드롭이 서로 다른 이유

좌우누르자마자 놓는다. 반복은 OS 의 키 자동반복에 맡긴다
소프트드롭눌러 둔 채로 두고, 한동안 조용하면 타임아웃으로 놓는다
나머지한 번짜리 동작이라 누르기만 하면 된다
좌우를 안 놓으면 어떻게 되는가 코어의 DAS(누른 채로 두면 자동반복)가 켜진 채로 남는다. 그러면 ← 를 한 번 눌렀을 뿐인데 조각이 혼자 벽까지 미끄러져 간다. 테스트가 이걸 지킨다 — "키를 한 번 누르고 660ms 를 흘려도 조각이 안 움직인다".

화면 — 세 갈래

05_window 의 구조를 그대로 쓴다. 갈래가 셋이다:

  1. 아직 창 크기를 모름 — 첫 WindowSizeMsg 전의 한 프레임
  2. 창이 너무 작음 — 지금 크기와 필요한 크기를 함께 알려 준다
  3. 정상

1번을 빼먹으면 첫 프레임에서 0 폭으로 계산하다 죽는다.

도움말도 키 표에서 나온다

문구를 손으로 적지 않고 ui 의 키맵에서 뽑는다. 배치를 바꿨는데 도움말이 그대로면 사용자만 거짓말을 읽게 된다.

F1 을 누르면 한 줄짜리 안내가 조작표 전체로 바뀐다. 기본은 짧게 — 80칸 터미널에서 잘리지 않아야 한다.

실행 진입점

이 파일이 하는 일은 셋뿐이다: 깃발을 읽고, 모델을 하나 고르고, tea.NewProgram 에 넘겨 돌린다. 게임에 대해 아는 것이 하나도 없다 — 그게 Elm 아키텍처로 나눈 결과다.

$ go run ./cmd/tetris                       메뉴
$ go run ./cmd/tetris -mode 1p              1인용
$ go run ./cmd/tetris -mode 1p -seed 7      같은 판을 다시

이름 하나로 화면을 고른다

깃발로 들어가든 메뉴에서 고르든 같은 함수를 지난다. 두 길이 갈라지면 "메뉴로 들어갈 때만 나는 버그"가 생긴다.

menu.Build 는 9부에서 본다.

실제로 돌려 보기

이건 그린 그림이 아니라 진짜 터미널에서 찍은 것이다. tmux 로 창을 하나 띄우고, 키를 보내고, 화면을 긁어 왔다.

tmux new-session -d -s t -x 80 -y 24 "go run ./cmd/tetris -mode 1p -seed 1"
sleep 5
tmux send-keys -t t Left Left Space
tmux capture-pane -e -p -t t > out/tmux_1p.txt   # -e 는 색을 남긴다

에이전트 세션에는 터미널이 없다. 그래서 진짜 PTY 에서 돈다는 것을 증명하는 유일한 방법이 이것이었다.

한 판을 넘겨 보기

아래는 진짜 모델을 돌려서 뽑은 기록이다. 스크립트를 정해 두고 모델에 키와 틱을 먹인 뒤, 매 단계의 화면을 저장했다.

스크립트: 80x24 left left space wait wait right right space …
같은 스크립트를 다시 돌리면 바이트까지 같은 파일이 나온다 — 그래서 이 그림이 코드와 어긋날 수가 없다.

함정 ① — 모델을 안 돌려주면

// 틀린 코드
func (m Model) Update(msg tea.Msg) (tea.Model, tea.Cmd) {
	switch msg.(type) {
	case TickMsg:
		m.advance()      // 복사본을 바꾼다
	}
	return Model{}, nil   // ← 엉뚱한 것을 돌려준다
}

컴파일도 되고 프로그램도 돈다. 화면만 안 변한다. 2부 02_counter 의 교훈이 여기서 다시 온다.

다만 이 프로젝트에는 한 가지 꼬임이 있다 — m.g 가 포인터라 advance() 의 효과는 남는다. 그래서 "화면이 반쯤 움직이는" 이상한 상태가 된다. 7부에서 이 성질을 정면으로 다룬다.

함정 ② — 틱을 다시 예약 안 하면

case TickMsg:
	m.advance()
	return m, nil      // ← Tick() 이 빠졌다

조각이 딱 한 칸 떨어지고 멈춘다. 키는 여전히 먹는다 — 그래서 "입력은 되는데 중력만 안 도는" 상태가 되고, 원인을 엉뚱한 데서 찾게 된다.

테스트로 못 박는 법 m.Update(TickMsg{}) 가 돌려준 cmd 를 실행해서 그 결과가 다시 TickMsg 인지 본다. 프로그램을 안 띄우고도 "사슬이 이어졌는가"를 확인할 수 있다.

함정 ③ — 화면이 창보다 클 때

도움말 한 줄이 80칸을 넘겼더니 터미널이 스크롤되면서 판의 윗줄이 잘려 나갔다. 실제로 밟은 함정이다.

// 잘라 내는 안전장치를 마지막에 한 번
out = lipgloss.NewStyle().MaxWidth(m.w).MaxHeight(m.h).Render(out)

도움말을 줄바꿈하면 높이가 늘어 판이 밀린다. 그래서 잘라 낸다 — 좁은 터미널에서는 뒷부분이 안 보이는 편이 판이 어긋나는 것보다 낫다.

테스트가 이걸 지킨다 여러 창 크기에서 lipgloss.Size(View().Content) 를 재고, 창보다 크면 실패시킨다. 사람이 눈으로 볼 수 없는 종류의 회귀다.

함정 ④ — 첫 프레임의 0×0

tea.WindowSizeMsg 는 프로그램이 뜬 직후에 온다. 그런데 그 전에 View 가 최소 한 번 불린다.

// 이렇게 쓰면 첫 프레임에서 죽는다
box := lipgloss.Place(m.w-4, m.h-2, ...)   // m.w=0 → -4

음수 폭을 받으면 lipgloss 가 그 자리에서 패닉한다. 그래서 갈래를 하나 더 둔다 — if m.w == 0 || m.h == 0.

05_window 예제가 이 함정만을 위해 존재한다. 작은 프로그램에서 한 번 밟아 보면 큰 프로그램에서 안 밟는다.

함정 ⑤ — 두 개의 시간

이 프로그램에는 시간이 둘 있다.

실제 시간TickInterval — tea.Tick 이 실제로 기다리는 시간
게임 시간TickMs — 코어의 Update(dtMs) 에 넘기는 숫자

이 둘을 같은 상수에서 파생시켜 1:1 로 맞춰 뒀다. 따로 두면 "화면은 30fps 인데 게임은 두 배 빠른" 상태가 되고, 그런 버그는 아무도 못 찾는다.

const TickMs = 33
const TickInterval = TickMs * time.Millisecond   // 파생시킨다

그리고 기록할 때는 실제 시간을 아예 안 쓴다 — TickMsg 를 직접 넣으므로 게임 시간만 흐른다. 그래서 300프레임을 0.1초에 뽑을 수 있다.

함정 ⑥ — 최소 크기를 어림으로 잡으면

계획 단계에서는 "2인용은 80×24 필요"라고 적어 뒀다. 그런데 실제 레이아웃을 계산해 보니 72×24 면 됐다.

MinSize(seats) = (BoardWidth + PanelWidth) × seats,  BoardHeight + 2

  1인용: (22 + 14) × 1 = 36 × 24
  2인용: (22 + 14) × 2 = 72 × 24
어림으로 크게 잡으면 72칸짜리 멀쩡한 터미널에서도 "터미널을 키워 주세요"가 뜬다. 사용자는 왜 안 되는지 모른 채 창을 늘린다. 필요한 것보다 크게 요구하는 것도 버그다.

그래서 상수에서 계산한다. 판이나 패널의 폭이 바뀌면 최소 크기도 저절로 따라간다.

함정 ⑦ — 패널이 흔들리면 판이 밀린다

점수가 999 에서 1000 이 되는 순간 패널이 한 칸 넓어지면, 옆의 판이 한 칸 밀린다. 매 프레임 그러면 화면이 떨린다.

폭을 흔드는 것들

  • 자릿수가 늘어나는 숫자
  • 있다 없다 하는 줄("생각 중…")
  • 길이가 다른 이름("AI 최종" / "AI 어려움")

막는 법

  • Width() 로 폭 고정
  • 없는 값도 - 로 채우기
  • 있다 없다 하는 줄은 빈 줄로 자리 지키기

테스트가 이걸 지킨다 — 점수를 0 · 999 · 1234567 로 바꿔 가며 lipgloss.Width 가 언제나 14 인지 확인한다.

함정 ⑧ — 제목이 테두리를 밀어낼 때

판의 위쪽 테두리에 이름을 새긴다. 그런데 "AI 어려움 (15세대)" 는 화면에서 18칸이다 — 테두리 속 폭(20칸)에 여백까지 넣으면 넘친다.

+- AI 어려움 (15세대) -+   <- 넘쳐서 폭이 22 를 초과
+--------------------+    <- 그래서 잘라 냈더니 이름이 통째로 사라짐
+- AI 어려움 --------+    <- 짧은 이름으로 고쳤다

고친 방법은 이름을 짧게 하는 것이었다. 난이도에 Short 필드를 하나 더 두고, 좁은 자리(판 제목·패널)에는 짧은 이름을, 넉넉한 자리(도움말·메뉴)에는 전체 이름을 쓴다.

"잘라 내기"는 폭이 흔들리는 것을 막을 뿐, 정보를 되돌려 주지는 않는다. 결국은 들어갈 만한 이름을 고르는 수밖에 없다.

함정 ⑨ — 한글 한 글자는 두 칸

테두리를 직접 그리려면 제목의 칸 수를 세야 한다. len() 도 []rune 도 답이 아니다.

여기서는 제목에 ASCII 와 한글만 쓰므로 한글을 2칸으로 세는 것으로 충분하다. 일반적인 폭 계산이 필요하면 lipgloss.Width 를 쓴다 — 여기서 안 쓰는 이유는 이 계산이 스타일을 거치기 전의 순수 문자열을 다루기 때문이다.

함정 ⑩ — print 로 디버깅할 수 없다

전체 화면 프로그램에서 표준 출력은 이미 쓰이고 있는 자원이다. fmt.Println 을 하면 Bubble Tea 가 그리는 화면 한가운데에 글자가 끼어든다.

이 프로젝트가 실제로 쓴 방법은 세 번째다 — 테스트로 옮기기.

m := New(WithSeed(1), WithoutTimer())
m2, _ := m.Update(tea.KeyPressMsg{Code: tea.KeyLeft})
if m2.(Model).Game().Stats().X != x0-1 { ... }

프로그램을 안 띄우고, 터미널도 없이, 궁금한 것을 그대로 물어본다. 모델이 값이라 가능한 일이고, 이게 값 의미론의 가장 큰 실용적 이득이다.
