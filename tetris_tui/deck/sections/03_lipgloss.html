Lip Gloss 로 꾸미기

Bubble Tea 는 무엇을 그릴지만 정한다. 어떻게 보일지는 Lip Gloss 의 일이다.

두 라이브러리는 문자열 하나로만 연결된다 — View 가 돌려주는 그 문자열이다. Lip Gloss 는 Bubble Tea 를 모르고, Bubble Tea 도 Lip Gloss 를 모른다.

Lip Gloss 가 하는 일

  • 색·굵기·밑줄 (이스케이프 시퀀스를 대신 적어 준다)
  • 여백·테두리·폭 고정
  • 덩어리를 가로/세로로 붙이기
  • 주어진 공간에 놓기(Place)
  • 화면 칸 수 재기 — 한글·이모지까지

안 하는 일

  • 입력 처리 (Bubble Tea 의 일)
  • 화면 갱신 (Bubble Tea 의 일)
  • 커서 위치 (그런 개념이 없다)

v2 의 경로도 charm.land/lipgloss/v2 다. v1 에서는 lipgloss.Color 가 타입이었지만 v2 에서는 함수다 — 인터넷 예제를 붙일 때 첫 번째로 깨지는 자리다.

스타일도 값이다

Bubble Tea 모델과 같은 규칙이다. Style 의 메서드는 새 Style 을 돌려주고 원본은 그대로다.

base := lipgloss.NewStyle().Bold(true)
derived := base.Italic(true)

base.GetItalic()     // false — 원본은 안 바뀐다
derived.GetBold()    // true  — 파생은 둘 다 갖는다

덕분에 "기본 스타일 하나를 두고 조금씩 바꿔 쓰기"가 안전하다. 이 프로젝트의 ui/style.go 가 정확히 그 방식이다.

색 — 가장 좋은 색만 적는다

24비트 색을 적어 두면 되는가? 된다. Bubble Tea 가 터미널의 색 능력을 알아내서 필요하면 256색·16색으로 낮춰 준다. 그래서 여기서는 "가장 좋은 색"만 적고, 낮추는 일은 라이브러리에 맡긴다.

██I
██J
██L
██O
██S
██T
██Z
██가비지

배색은 테트리스 가이드라인의 표준을 따랐다. 가비지 회색만 우리가 정했다.

칸 하나를 칠하는 함수

CellStyle 이 매번 NewStyle() 을 부르는 것은 뒤에 나올 "스타일은 패키지 변수로" 규칙의 예외다. 색이 아홉 가지뿐이라 캐시할 만큼 비싸지 않고, 캐시하면 초기화 순서에 얽힌 전역 상태가 하나 늘어난다 — 그 대가가 더 크다.

고스트는 배경 없이 글자색만 흐리게 칠한다. 착지 자리를 알려 주되 눈을 뺏지 않아야 한다.

폭은 글자 수가 아니라 칸 수다

len() 으로 폭을 재면 판이 어긋난다 Go 의 len("한글") 은 6 이다(UTF-8 바이트 수). []rune 으로 세면 2 다. 그런데 화면에서 차지하는 칸은 4 다. 셋이 전부 다르다.
lipgloss.Width("한글")   // 4  ← 화면 칸 수. 이걸 써야 한다
len("한글")              // 6  ← UTF-8 바이트 수
len([]rune("한글"))      // 2  ← 글자 수

lipgloss.Width("██")     // 2  ← 블록 문자는 한 칸씩

이 프로젝트는 ui 의 테스트가 세 글자(칸·고스트·빈칸)가 전부 폭 2 인지를 매번 확인한다. 이 전제가 깨지면 판이 통째로 어긋나기 때문이다.

폭을 고정하면 채워지고 접힌다

s := lipgloss.NewStyle().Width(10)

s.Render("짧음")
// 폭이 정확히 10 — 모자란 만큼 공백으로 채운다

s.Render("이 문장은 열 칸보다 훨씬 길어서 반드시 접힌다")
// 여러 줄로 접히고, 그래도 폭은 10 을 안 넘는다

이 성질이 레이아웃의 뼈대다. 옆에 붙는 패널의 폭을 고정해 두면, 점수가 여섯 자리가 되든 홀드가 비든 판이 좌우로 흔들리지 않는다.

Width 는 테두리를 포함한다 이 프로젝트에서 실제로 밟은 함정이다. 패널 전체 폭을 14 로 만들려고 Width(14 - 2) 라고 썼더니 완성품이 12칸이 되어 옆의 판이 두 칸 밀렸다. Width(14) 가 맞다. 테스트로 못 박아 뒀다.

여백과 테두리

스타일을 패키지 변수로 한 번만 만드는 이유: View 는 초당 수십 번 불린다. 매번 NewStyle() 을 부르면 같은 구조체를 계속 새로 짓게 된다 (값이 아홉 개뿐인 CellStyle 만 예외로 두었다).

Padding(1, 3)위아래 1, 좌우 3
Padding(1, 2, 3, 4)위·오른쪽·아래·왼쪽 (CSS 와 같은 순서)
Border(RoundedBorder())둥근 테두리. 폭·높이가 각각 2 늘어난다
BorderForeground(c)테두리 색만 따로

테두리 종류: NormalBorder · RoundedBorder · ThickBorder · DoubleBorder · ASCIIBorder · BlockBorder · HiddenBorder.

Join — 덩어리를 붙인다

JoinHorizontal(pos, a, b, …) 는 높이가 다른 덩어리를 나란히 붙이고 짧은 쪽을 공백으로 채운다. 첫 인자는 세로 정렬 기준이다.

JoinHorizontal(Top, "1\n2\n3", "a")     JoinHorizontal(Bottom, …)
   1a                                     1
   2                                      2
   3                                      3a

결과의 높이는 더 높은 쪽, 폭은 둘의 합이다. 이 프로젝트의 게임 화면은 전부 JoinHorizontal(Top, …) 한 번과 JoinVertical(Left, …) 한 번으로 끝난다.

06_lipgloss — 화면

두 패널의 폭이 정확히 같은 것을 보라. Width(18) 하나로 얻은 결과다. b 를 눌러 테두리를 끄면 전체 폭이 줄어든다 — 테두리가 폭을 2 늘리기 때문이다.

Place — 주어진 공간에 놓기

lipgloss.Place(w, h, hPos, vPos, content)

주어진 w × h 안에 내용을 원하는 위치로 놓고 나머지를 공백으로 채운다. 결과의 크기가 정확히 w × h 라는 것이 핵심이다.

  • 화면이 창보다 작으면 이전 프레임의 찌꺼기가 남는다
  • 화면이 창보다 크면 터미널이 스크롤되면서 위쪽이 잘려 나간다

그래서 전체 화면 프로그램의 View 는 거의 언제나 Place 로 끝난다.

MaxWidth/MaxHeight 는 마지막 안전장치다. 어디선가 한 칸이 새도 여기서 막힌다 — 도움말 한 줄이 창보다 길어지는 일이 실제로 있었다.

두 글자 칸 트릭 — 다시 한 번

1부에서 "칸이 세로로 길쭉하다"고 했다. Lip Gloss 로 그걸 다루는 방법이 이것이다.

규칙

  • 블록 한 칸 = 두 글자
  • 빈칸도 두 글자(공백 둘)
  • 고스트도 두 글자
  • 셋의 lipgloss.Width 가 전부 2

따라오는 것

  • 판의 속 폭 = 10 × 2 = 20칸
  • 테두리 포함 = 22칸
  • 이 숫자가 상수로 한 곳에만 있다

레이아웃 계산이 전부 이 두 상수를 쓴다. 숫자를 여기저기 흩어 놓으면 테두리를 한 번 바꿀 때마다 화면이 어긋난다.

넓은 글자를 조심하라

이 프로젝트는 블록 문자(█ U+2588, ░ U+2591)를 쓴다. 이유가 있다.

후보문제
이모지 (🟦)폰트마다 폭이 다르다. 어떤 터미널은 1칸, 어떤 곳은 2칸
전각 기호 (■ U+25A0 등)동아시아 폭 규칙(Ambiguous)에 걸려 환경마다 1칸·2칸이 흔들린다
ASCII ([])안전하지만 판이 성기게 보인다
블록 (██)거의 모든 터미널에서 한 칸. 꽉 차 보인다
완전히 안전하지는 않다 블록 문자도 유니코드 상 "동아시아 애매(Ambiguous)" 폭이다. 이론상 CJK 환경에서 두 칸으로 그려질 수 있다. 실제로는 거의 모든 터미널이 한 칸으로 그리고, lipgloss 도 한 칸으로 센다 — 이 프로젝트는 그 전제를 테스트로 못 박고 넘어간다.

판 하나를 그리는 함수

테두리를 Border 스타일로 두르지 않고 직접 그리는 이유는 제목 때문이다. 위쪽 테두리 한가운데에 "1P" 나 "AI 어려움"을 새기려면 그 줄을 우리가 만들어야 한다.

덤으로, 직접 그리면 폭이 정확히 BoardWidth 라는 것을 눈으로 확인할 수 있다.

화면 코드는 게임을 멈출 권리가 없다

at 은 층이 짧거나 nil 이어도 빈칸을 돌려준다. 데이터가 모자란다고 패닉으로 게임을 끝내는 것은 화면 코드가 할 일이 아니다.

topBorder 는 제목이 너무 길면 잘라 낸다. 폭이 흔들리는 것보다 이름이 안 보이는 편이 낫다 — 폭이 흔들리면 옆의 판까지 밀린다.

미리보기는 왜 두 줄이면 되는가

스폰 회전 상태(rot 0)의 일곱 조각은 전부 4×2 상자에 들어간다. I 조각조차 가로로 누워 있기 때문이다. 그래서 미리보기 높이가 조각마다 달라지는 일이 없고, 패널의 높이가 흔들리지 않는다.

MinSize 는 실제 레이아웃에서 계산한다. 넉넉하게 잡아 두면 멀쩡한 크기에서도 "터미널을 키워 주세요"가 뜨고, 빠듯하게 잡으면 화면이 잘린다.

패널 — 크기가 절대 변하지 않아야 한다

패널의 폭과 높이가 언제나 같아야 한다. 점수가 여섯 자리가 되거나 홀드가 비었다고 크기가 변하면, 옆에 붙어 있는 판이 매 프레임 좌우로 흔들린다.

그래서 값이 없는 자리도 - 로 채우고, 미리보기는 늘 같은 개수를 그린다.

패널 — 나머지

comboText 가 따로 있는 이유: 코어의 콤보는 -1 이 "콤보 없음", 0 이 "첫 클리어"다. 그대로 보여 주면 사람이 헷갈린다. 내부 표현과 화면 표현은 다를 수 있고, 다를 때는 화면 쪽을 고쳐야 한다.

다음 조각을 셋 보여 주는 것은 관례다 — 하나면 계획을 못 세우고, 다섯이면 패널이 판보다 길어진다.

3부 정리

Style 은 값메서드가 새 Style 을 돌려준다. 원본은 안 바뀐다
폭은 칸 수lipgloss.Width 로 잰다. len() 은 틀린 답을 준다
Width 는 테두리 포함이 프로젝트가 실제로 밟은 함정. Width(14-2) 가 아니라 Width(14)
Join가로/세로로 붙인다. 짧은 쪽은 공백으로 채워진다
Place결과 크기가 정확히 w×h. 전체 화면의 마지막 단계
두 글자 칸판이 정사각형이 된다. 판 폭 = 10×2+2 = 22칸
