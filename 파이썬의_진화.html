왜 3.7부터 시작하는가

3.7 직전까지, 오늘날 "모던 파이썬"의 기초 문법은 이미 도착해 있었습니다.

버전이미 있던 것

3.6 (2016)f-string · 변수 애너테이션 x: int · 숫자 밑줄 1_000_000 · 비동기 제너레이터
  • 즉 3.7은 "문법 도입기"가 끝나고 "정비·확장기"가 시작되는 지점입니다. 이후 8년의 변화는 그 위에서 벌어집니다.
  • 또 하나의 이유 — 2020년 1월 Python 2가 최종 은퇴했습니다. 3.7은 2 시대의 그림자 없이 설계된 첫 세대에 가깝습니다.
대상 독자 — 파이썬 기본 문법(함수·클래스·컴프리헨션)을 아는 사람. 각 버전의 새 기능을 "왜 생겼고, 언제 쓰는가"까지 예제로 확인합니다.

  • 2018년 7월, 창시자 귀도 반 로섬이 BDFL(자비로운 종신 독재자)에서 스스로 물러났습니다 — 직접적 계기가 바로 바다코끼리 연산자(PEP 572) 논쟁이었습니다.

dataclasses — 보일러플레이트의 종말

데이터를 담는 클래스를 한 줄 데코레이터로 · PEP 557

3.6까지 — 데이터 클래스 하나의 비용 3.7

점 (x, y) 하나를 "제대로" 만들려면 이만큼 써야 했습니다.

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"Point(x={self.x!r}, y={self.y!r})"

    def __eq__(self, other):
        if other.__class__ is not self.__class__:
            return NotImplemented
        return (self.x, self.y) == (other.x, other.y)
  • 필드가 하나 늘 때마다 세 곳(init·repr·eq)을 고쳐야 합니다 — 빠뜨리면 조용한 버그.
  • namedtuple은 짧지만 불변이고, 튜플과 비교되고, 기본값·메서드 추가가 어색했습니다.

3.7부터 — @dataclass 3.7

from dataclasses import dataclass

@dataclass
class Point:
    x: float
    y: float

p = Point(1.5, 2.5)
print(p)                       # Point(x=1.5, y=2.5)
print(p == Point(1.5, 2.5))    # True
p.x = 9.0                      # 가변 — 보통 클래스처럼 수정 가능
  • 클래스 본문의 타입 애너테이션이 곧 필드 선언입니다. __init__·​__repr__·​__eq__가 자동 생성됩니다.
  • 애너테이션은 문법상 필수지만 검사되지는 않습니다 — 타입을 모르면 typing.Any를 써도 됩니다.
왜 3.7의 상징인가 — 타입 힌트(3.5~3.6)가 "문서"에서 "동작을 만드는 재료"로 처음 승격된 사건입니다. 이 노선은 이후 TypedDict(3.8), 패턴 매칭(3.10)으로 이어집니다.

기본값과 field() — 가변 기본값 함정까지 해결 3.7

from dataclasses import dataclass, field

@dataclass
class Order:
    customer: str
    items: list = field(default_factory=list)  # 주문마다 새 리스트
    discount: float = 0.0

a = Order("김하나")
b = Order("이두리")
a.items.append("책")
print(a.items, b.items)   # ['책'] []  — 서로 독립
  • items: list = []처럼 쓰면 모든 인스턴스가 리스트 하나를 공유하는 고전 버그가 됩니다 — dataclass는 이를 ValueError로 아예 거부하고, default_factory를 쓰게 합니다.
  • field(repr=False), field(compare=False)로 특정 필드를 repr·비교에서 뺄 수 있습니다.

frozen과 order — 불변 값 객체 만들기 3.7

from dataclasses import dataclass, FrozenInstanceError

@dataclass(frozen=True, order=True)
class Version:
    major: int
    minor: int

v1, v2 = Version(3, 7), Version(3, 14)
print(v1 < v2)            # True — 필드 순서대로 튜플 비교
print(sorted([v2, v1]))   # [Version(major=3, minor=7), Version(major=3, minor=14)]
print({v1: "구식"})        # frozen이면 해시 가능 → dict 키로 사용 가능
try:
    v1.major = 4
except FrozenInstanceError as e:
    print("수정 불가:", e)
  • frozen=True — 대입을 막고 __hash__를 만들어 집합 원소·사전 키로 쓸 수 있게 합니다.
  • order=True — < <= > >=를 필드 선언 순서 기준으로 생성합니다.

파생 필드 — __post_init__ 3.7

from dataclasses import dataclass, field

@dataclass
class Rect:
    w: float
    h: float
    area: float = field(init=False)   # 인자로 받지 않는 필드

    def __post_init__(self):
        self.area = self.w * self.h

r = Rect(3, 4)
print(r)          # Rect(w=3, h=4, area=12)
  • __init__이 끝난 직후 __post_init__이 호출됩니다 — 검증·파생값 계산 자리입니다.
  • field(init=False)와 짝을 이루면 "입력에서 계산되는 필드"를 깔끔하게 표현합니다.

변환 도구 — asdict · astuple · replace 3.7

from dataclasses import dataclass, asdict, astuple, replace

@dataclass(frozen=True)
class Config:
    host: str
    port: int

c = Config("localhost", 8080)
print(asdict(c))              # {'host': 'localhost', 'port': 8080}
print(astuple(c))             # ('localhost', 8080)

c2 = replace(c, port=9090)    # 불변 객체의 "일부만 바꾼 복사본"
print(c2)                     # Config(host='localhost', port=9090)
  • asdict()는 중첩 dataclass까지 재귀 변환합니다 — JSON 직렬화 직전 단계로 애용됩니다.
  • replace()는 frozen 인스턴스를 다루는 표준 관용구입니다. 3.13에서 copy.replace()로 일반화됩니다(7부).

breakpoint() — 디버거 진입의 표준화 3.7

3.6까지
import pdb; pdb.set_trace()  # 매번 이 주문을 외움
3.7부터
breakpoint()   # 내장 함수 — import 불필요
def divide(a, b):
    if b == 0:
        breakpoint()      # 여기서 pdb가 열림 — 변수를 보며 원인 추적
    return a / b
  • 환경 변수로 동작을 바꿉니다 — PYTHONBREAKPOINT=0이면 전부 무시(실수로 남긴 채 배포해도 안전), PYTHONBREAKPOINT=ipdb.set_trace면 다른 디버거로 연결.
  • 내부적으로 sys.breakpointhook()을 부릅니다 — IDE가 이 훅을 바꿔치기해 자기 디버거를 띄웁니다.

이 함수의 후일담 — 3.13의 새 REPL(7부), 3.14의 원격 디버깅(8부)으로 이어집니다.

dict는 이제 "공식적으로" 삽입 순서를 지킨다 3.7

d = {}
d["하나"] = 1
d["둘"] = 2
d["셋"] = 3
print(list(d))            # ['하나', '둘', '셋'] — 항상, 어떤 구현에서도
d["하나"] = 100           # 값 갱신은 순서를 바꾸지 않음

print(d.popitem())        # ('셋', 3) — 마지막 항목부터 (LIFO 보장)
  • 3.6에서 CPython의 구현 우연이었던 것이 3.7에서 언어 명세가 됐습니다 — PyPy 등 다른 구현도 반드시 지켜야 합니다.
  • 키 삭제 후 재삽입하면 맨 뒤로 갑니다 — 순서는 "처음 삽입된 시점" 기준.

dict 순서 보장이 바꾼 코딩 습관

import json

# 1. JSON 라운드트립이 순서를 보존 — 설정 파일 diff가 깨끗해짐
cfg = json.loads('{"name": "app", "port": 8080, "debug": true}')
print(json.dumps(cfg))    # {"name": "app", "port": 8080, "debug": true}

# 2. 중복 제거 + 순서 유지 관용구
items = ["b", "a", "b", "c", "a"]
print(list(dict.fromkeys(items)))   # ['b', 'a', 'c']

# 3. **kwargs 도 함수에 적힌 순서 그대로 도착
def tag(name, **attrs):
    parts = " ".join(f'{k}="{v}"' for k, v in attrs.items())
    return f"<{name} {parts}>"
print(tag("img", src="a.png", width=10))   # <img src="a.png" width="10">
OrderedDict의 은퇴? — 절반만. 순서 유지 자체는 dict로 충분하지만, move_to_end()와 "순서까지 같아야 =="인 비교가 필요하면(예: LRU 캐시) 여전히 OrderedDict입니다.

from __future__ import annotations   # PEP 563 — opt-in

import asyncio

    await asyncio.sleep(0.01 * n)
    return n * n

    # ensure_future 대신 의도가 읽히는 이름

    t2 = asyncio.create_task(worker(3))
    print(asyncio.current_task().get_name())   # 실행 중 태스크 확인
    loop = asyncio.get_running_loop()          # 도는 루프만 반환 (없으면 오류)
    return await t1 + await t2

문제 — "계산하고, 검사하고, 또 쓰기" 3.8

3.7까지 — 두 번 계산하거나

if n > 10:

위치 전용 인자 — / 3.8

def power(base, exp, /, *, precise=False):
    return pow(base, exp)

power(2, 10)              # OK
power(2, 10, precise=True) # OK
# power(base=2, exp=10)   # TypeError — /' 앞은 이름으로 못 넘김
구간의미
/ 앞위치로만 — len(obj=x)가 안 되는 것과 같은 규칙
/와 * 사이위치·키워드 모두 가능 (기존 기본 동작)
* 뒤키워드로만 (3.0부터 있던 문법)

help(len)에서 보이던 len(obj, /) 표기 — C 함수에만 있던 이 능력이 파이썬 함수에도 열렸습니다.

위치 전용이 필요한 세 가지 이유 3.8

  1. 인자 이름을 API에서 빼기 — def dist(p, q, /)라면 훗날 이름을 p→point로 바꿔도 호출부가 깨지지 않습니다. 이름이 계약이 아니게 됩니다.
  2. **kwargs와의 충돌 방지 — 아래 예처럼 첫 인자 이름이 키워드 사전을 오염시키는 문제를 없앱니다.
  3. 이름으로 불러 봐야 뜻이 없는 인자 — setattr(obj, name, value)류의 자명한 위치 인자.
def tag(name, /, **attrs):        # name이 /' 앞이라
    inner = " ".join(f'{k}="{v}"' for k, v in attrs.items())
    return f"<{name} {inner}>"

# attrs에 'name' 키를 마음껏 쓸 수 있다!
print(tag("input", name="q", type="text"))

Protocol — 덕 타이핑의 정적 검사 3.8

"close()가 있는 아무거나"를 받고 싶을 때, 3.7까지는 상속 기반 ABC를 강요하거나 Any로 포기해야 했습니다.

from typing import Protocol

class Closeable(Protocol):
    def close(self) -> None: ...

def shutdown(res: Closeable) -> None:
    res.close()

class DB:                    # Closeable을 상속하지 않는다!
    def close(self) -> None:
        print("DB 연결 종료")

shutdown(DB())               # OK — 메서드 형태만 맞으면 통과
# shutdown(42)               # mypy: int에는 close가 없음
구조적 타이핑 — "무엇을 상속했나"(명목적)가 아니라 "무슨 모양인가"(구조적)로 판정합니다. 파이썬이 30년 해 온 덕 타이핑을, 실행 없이 검사 가능하게 만든 다리입니다.

Protocol 실전 — 표준 프로토콜과 runtime_checkable 3.8

from typing import Protocol, runtime_checkable

@runtime_checkable
class Sized(Protocol):
    def __len__(self) -> int: ...

print(isinstance([1, 2], Sized))    # True — 런타임 isinstance도 가능
print(isinstance(3.14, Sized))      # False

class Renderer(Protocol):
    def render(self, data: dict) -> str: ...

def publish(r: Renderer, data: dict) -> None:
    print(r.render(data))
  • @runtime_checkable을 붙이면 isinstance 검사가 가능해집니다 — 단, 메서드 이름의 존재만 보고 시그니처는 안 봅니다.
  • 실무 패턴 — 라이브러리가 "우리에게 넘길 객체의 요건"을 Protocol로 공표하면, 사용자는 아무것도 상속하지 않고 요건만 맞추면 됩니다. 플러그인 인터페이스의 표준 도구가 됐습니다.

functools.cached_property — 한 번 계산하는 속성 3.8

from functools import cached_property
import statistics

class Dataset:
    def __init__(self, rows):

    def stdev(self):

match / case — switch가 아니라 "모양으로 분해하기" · PEP 634·635·636

문제 — "모양 검사 + 꺼내기"의 지루한 이중주 3.10

# JSON으로 오는 명령 처리 — 3.9까지의 모습
def handle(cmd):
    if isinstance(cmd, dict) and cmd.get("op") == "move" \
            and "x" in cmd and "y" in cmd:
        go(cmd["x"], cmd["y"])
    elif isinstance(cmd, dict) and cmd.get("op") == "say" \
            and isinstance(cmd.get("text"), str):
        speak(cmd["text"])
    elif isinstance(cmd, (list, tuple)) and len(cmd) == 2:
        first, second = cmd
        combo(first, second)
    else:
        raise ValueError(cmd)
  • 검사(isinstance·​len·​in)와 추출(cmd["x"], 언패킹)이 따로 놀아서 장황하고, 둘이 어긋나면 버그입니다.
  • match 문은 이 둘을 "패턴" 하나로 통합합니다 — 값이 이 모양인가? 맞으면 이 이름들로 분해하라.

같은 코드, match로 3.10

def handle(cmd):
    match cmd:
        case {"op": "move", "x": x, "y": y}:
            go(x, y)
        case {"op": "say", "text": str(text)}:
            speak(text)
        case [first, second]:
            combo(first, second)
        case _:
            raise ValueError(cmd)
  • 각 case가 모양의 선언입니다 — 검사와 변수 바인딩이 한 줄에서 일어납니다.
  • 위에서부터 첫 번째로 맞는 case 하나만 실행됩니다. C의 switch와 달리 fall-through가 없고 break도 없습니다.
  • case _:는 무엇이든 맞는 와일드카드 — 마지막 안전망입니다(없으면 조용히 통과).

패턴 5 — 클래스 분해와 __match_args__ 3.10

from dataclasses import dataclass

@dataclass
class Point:
    x: float
    y: float

def where(p):
    match p:
        case Point(x=0, y=0):        # 키워드 형태
            return "원점"
        case Point(0, y):            # 위치 형태 — dataclass가 만들어 준
            return f"y축 위 ({y})"    # __match_args__ = ('x', 'y') 덕분
        case Point(x=x, y=y) if x == y:   # 가드 — 패턴 뒤 if
            return "대각선 위"
        case Point():
            return "일반 점"

print(where(Point(0, 5)))    # y축 위 (5)
print(where(Point(3, 3)))    # 대각선 위
  • Point(0, y)는 생성이 아니라 검사·분해입니다 — isinstance 확인 후 속성을 꺼냅니다.
  • 위치 인자 패턴은 클래스의 __match_args__ 순서를 따릅니다 — dataclass·namedtuple은 자동 제공, 일반 클래스는 직접 선언.
  • if 가드는 패턴이 맞은 뒤 추가 조건 — 캡처된 이름을 조건식에서 바로 씁니다.

# 수식 트리: ("+", 좌, 우) / ("*", 좌, 우) / 숫자
def evaluate(expr):
    match expr:
        case int() | float() as n:        # as — 매치된 값에 이름 붙이기
            return n
        case ("+", left, right):
            return evaluate(left) + evaluate(right)
        case ("*", left, right):
            return evaluate(left) * evaluate(right)
        case ("-", operand):
            return -evaluate(operand)
        case _:
            raise ValueError(f"알 수 없는 식: {expr!r}")

tree = ("+", ("*", 2, 3), ("-", 4))
print(evaluate(tree))     # 2*3 + (-4) = 2
  • 인터프리터·AST 순회·프로토콜 해석 — "태그 붙은 트리"를 다루는 코드가 match의 본진입니다. 함수형 언어의 대수적 데이터 타입 스타일이 파이썬에 이식된 셈입니다.
  • 패턴 as 이름 — 세부 패턴으로 검사하면서 전체 값도 잡아 둡니다.

ParamSpec — 데코레이터가 시그니처를 지키게 3.10

from typing import Callable, ParamSpec, TypeVar
import functools, time

P = ParamSpec("P")
R = TypeVar("R")

def timed(fn: Callable[P, R]) -> Callable[P, R]:
    @functools.wraps(fn)
    def wrap(*args: P.args, **kwargs: P.kwargs) -> R:
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__}: {time.perf_counter() - t0:.4f}s")
    return wrap

@timed
def greet(name: str, *, loud: bool = False) -> str:
    return name.upper() if loud else name

print(greet("kim", loud=True))   # KIM (+ 시간 출력)

4부 퀴즈

Q. MAX = 10일 때 match n: case MAX: ...는 왜 의도대로 동작하지 않는가?

A. case 자리의 맨몸 이름 MAX는 상수 비교가 아니라 캡처 패턴이라, 무엇이 오든 매치되고 MAX에 n이 대입됩니다(뒤에 다른 case가 있으면 도달 불가로 SyntaxError). 상수와 비교하려면 case Limits.MAX:처럼 점이 찍힌 이름을 쓰거나 case 10: 리터럴을 써야 합니다.

  2. int | None — Optional/Union의 은퇴. isinstance까지 받아 주는 런타임 유니언.
  3. 오류 메시지 혁명 — 파이썬이 "무엇이 왜 틀렸는지" 말하기 시작했다. 초심자 경험의 역대급 개선.
  4. ParamSpec·TypeGuard — 데코레이터와 사용자 정의 좁히기까지, 타입 시스템이 파이썬 관용구를 따라잡았다.

33년 제약에 도전하는 실험 · PEP 703

복습 — GIL은 무엇이고 왜 있었나

  • GIL(전역 인터프리터 잠금) — 한 프로세스에서 파이썬 바이트코드를 실행하는 스레드는 동시에 하나뿐이게 하는 잠금. 1992년부터 CPython의 심장에 있었습니다.
  • 왜 있었나 — 참조 카운트 방식 메모리 관리를 잠금 하나로 싸게 보호하고, 단일 스레드 성능과 C 확장 작성을 단순하게 유지하기 위해서입니다.
  • 대가 — CPU를 쓰는 작업은 스레드를 몇 개 만들어도 코어 하나 값만 나옵니다. 멀티코어 시대 내내 파이썬의 아킬레스건이었습니다.
import threading, time

def burn():
    n = 0
    for _ in range(10_000_000):
        n += 1

t0 = time.perf_counter()
ts = [threading.Thread(target=burn) for _ in range(4)]
for t in ts: t.start()
for t in ts: t.join()
print(f"{time.perf_counter() - t0:.2f}s")

from string.templatelib import Template, Interpolation
import html

def safe_html(t: Template) -> str:
    parts = []
    for item in t:                      # 조각을 순서대로 순회
        if isinstance(item, Interpolation):
            parts.append(html.escape(str(item.value)))   # 값만 이스케이프
        else:
            parts.append(item)          # 리터럴은 그대로
    return "".join(parts)

user_input = "<script>alert('xss')</script>"
page = safe_html(t"<p>{user_input}</p>")
print(page)
# <p>&lt;script&gt;alert(&#x27;xss&#x27;)&lt;/script&gt;</p> — 무력화!
# (html.escape는 따옴표도 &#x27;로 바꿉니다)
  • Template을 순회하면 리터럴 str과 Interpolation 객체가 번갈아 나옵니다 — 렌더러는 이 둘을 구분해 처리합니다.
  • 같은 틀로 SQL은 플레이스홀더 바인딩으로, 셸 명령은 shlex.quote로 — 맥락에 맞는 이스케이프가 라이브러리 몫이 됩니다.

실전 — 인젝션이 불가능한 SQL 헬퍼 3.14

from string.templatelib import Template, Interpolation

def build_query(t: Template) -> tuple[str, list]:
    sql_parts, params = [], []
    for item in t:
        if isinstance(item, Interpolation):
            sql_parts.append("?")           # 값 자리는 무조건 플레이스홀더
            params.append(item.value)
        else:
            sql_parts.append(item)
    return "".join(sql_parts), params

name = "Robert'); DROP TABLE students;--"   # 악명 높은 그 입력
sql, params = build_query(t"SELECT * FROM users WHERE name = {name}")
print(sql)      # SELECT * FROM users WHERE name = ?
print(params)   # ["Robert'); DROP TABLE students;--"] — 값은 값일 뿐
# cursor.execute(sql, params)  ← 안전한 실행
발상의 전환 — "위험한 문자열을 검사"하는 게 아니라, 위험한 문자열이 만들어질 경로 자체를 제거합니다. 개발자는 그냥 보간 문법을 쓰면 되고, 안전은 타입이 강제합니다 — build_query는 str을 아예 받지 않으니까요.

import json

def log(t: Template) -> None:
    message, fields = [], {}
    for item in t:
        if isinstance(item, Interpolation):
            message.append(str(item.value))
            fields[item.expression] = item.value    # 식 이름이 곧 필드 키!

프리스레딩 실전 — 원자성의 진실 3.14

import threading

counter = 0
lock = threading.Lock()

def unsafe():
    global counter
    for _ in range(100_000):
        counter += 1          # 읽기→증가→쓰기 3단계 — 원자적이지 않다!

def safe():
    global counter
    for _ in range(100_000):
        with lock:
            counter += 1

ts = [threading.Thread(target=unsafe) for _ in range(4)]
for t in ts: t.start()
for t in ts: t.join()
print(counter)    # 400000보다 작을 수 있음 — GIL 빌드에서도 원래 그랬다!
  • 중요한 진실 — +=는 GIL 아래에서도 원자적이지 않았습니다(바이트코드 사이 선점). 프리스레딩은 새 위험을 만드는 게 아니라 기존 위험의 발현 빈도를 높입니다.

낡은 코드 이주 전략 — 순서가 절반이다

  1. 먼저 경고를 켠다 — python -W error::DeprecationWarning -m pytest. 다음 버전에서 깨질 것이 오늘 보입니다.
  2. 인터프리터만 먼저 올린다 — 문법 현대화 없이 버전업 + 테스트. 3.11로만 올려도 공짜 1.25배.
  3. 자동 도구로 표기 현대화 — pyupgrade·ruff의 UP 규칙이 List[int]→list[int], %→f-string 등을 기계적으로 처리합니다.
  4. 사람 손은 구조 변화에만 — match 도입, TaskGroup 전환, dataclass화는 리뷰가 필요한 리팩터링으로 따로.
이주 지뢰 목록 — ① 3.12: distutils import ② 3.13: PEP 594 모듈(cgi·telnetlib 등) ③ 3.9→3.10: collections.abc로 옮겨진 별칭 제거(collections.Mapping) ④ 프리스레드 빌드: C 확장 휠 유무. 이 넷이 실제 이주 실패담의 대부분입니다.

Q. 8년의 변화 중 "코드를 한 줄도 안 바꾼 프로젝트"가 그냥 얻은 것 세 가지는?

9부 정리 — 하나로 꿰면

여덟 버전의 표면적 변화는 제각각이지만, 방향은 넷으로 수렴합니다.

  1. 쓰기 쉽게 — 문법이 관용구를 흡수했다 (walrus·match·제네릭·t-string).
  2. 틀리기 어렵게 — 타입·오류 메시지·경고가 실수를 실행 전에 잡는다.
  3. 더 빠르게 — 인터프리터 자체가 매년 몇 %씩, 병렬성은 구조적으로.
  4. 덜 지니고 — 죽은 배터리를 덜어내고, 살아 있는 배터리(zstd·tomllib·zoneinfo)를 채웠다.

부록 K — FAQ 1: 버전 선택

Q. 아직 3.8인데, 한 번에 3.14로 올려도 되나요?

됩니다 — 파이썬 3끼리는 파괴적 변경이 점진적이라, 중간 버전을 순회할 필요는 없습니다. 단 9부의 이주 지뢰(distutils·PEP 594 모듈·abc 별칭)를 한꺼번에 만나므로, "경고 켜고 테스트 → 지뢰 제거 → 버전업" 순서가 안전합니다.

Q. 프리스레드 빌드를 운영에 써도 되나요?

3.14에서 "공식 지원"이 됐지만, 의존하는 C 확장 전부가 cp314t 휠을 제공하는지가 실질 조건입니다. 하나라도 없으면 GIL이 도로 켜져 이득이 사라집니다. 병렬 이득이 확실한 워크로드부터 부분 도입하는 것이 정석입니다.

Q. JIT는 켜야 하나요?

아직은 선택입니다 — 3.14 기준 이득이 크지 않고 기본 꺼짐입니다. 켜는 것보다 3.11 이상으로 올리는 것이 훨씬 큰 성능 변화입니다.

부록 K — FAQ 2: 문법

Q. match는 switch인가요?

아닙니다. 값 분기만 하면 switch처럼 보이지만, 본질은 모양 검사 + 분해입니다. 분해가 필요 없으면 if/dict가 낫고(4부), fall-through·점프 테이블 최적화도 없습니다.

Q. 바다코끼리는 어디까지 써야 하나요?

세 관용구 — while-읽기, 정규식 매치, 컴프리헨션의 계산 재사용 — 에서만 쓰면 논쟁이 없습니다. 일반 대입의 대체가 아닙니다(2부).

Q. f-string과 t-string 중 뭘 쓰나요?

즉시 문자열이 필요하면 f-string(대부분의 경우), 값이 신뢰 경계를 넘으면(SQL·HTML·셸·구조적 로그) t-string + 렌더러입니다(8부).

Q. from __future__ import annotations는 지워야 하나요?

3.14 전용 코드라면 불필요합니다. 다버전 지원 코드라면 유지해도 무방하지만, 그 파일은 "문자열 의미론"으로 남는다는 점만 기억하세요(8부).

부록 K — FAQ 3: typing

Q. 타입 힌트를 달면 느려지나요?

실행 성능엔 사실상 영향이 없습니다 — 힌트는 기본적으로 검사되지 않고, 3.14부터는 평가조차 접근 전엔 안 합니다. 비용은 import 시간뿐이었는데 그마저 지연 평가로 사라졌습니다.

Q. TypeGuard와 TypeIs, 뭘 쓰나요?

기본은 TypeIs(3.13) — isinstance처럼 양방향으로 좁혀 줍니다. 입력 타입과 무관한 타입으로 "선언"해야 하는 특수한 경우만 TypeGuard(7부).

Q. 옛 List[int]·​Optional[str]을 다 고쳐야 하나요?

동작은 계속 하므로 의무는 아닙니다. 다만 ruff/pyupgrade가 자동 변환해 주므로(9부), 새 표기로 통일하는 비용이 거의 0입니다 — 스타일 혼재가 더 비쌉니다.

Q. 런타임에 타입을 강제하고 싶어요.

표준 typing은 검사하지 않습니다 — pydantic·beartype 같은 라이브러리가 그 역할이고, 3.9 Annotated·3.14 annotationlib이 그들의 공식 기반 시설입니다.

부록 M — 연습문제 14선

여덟 버전의 핵심을 문제로 복습합니다. 각 문제의 답 보기를 누르기 전에 먼저 답해 보세요.

  • 유형 1 — "어느 버전부터 도는 코드인가?" (버전 감각)
  • 유형 2 — "이 코드의 출력은?" (동작 이해)
  • 유형 3 — "왜 의도대로 안 되는가?" (함정 회피)

각 답에는 해당 부(部) 번호를 달아 두었습니다 — 틀리면 그 부로 돌아가세요.

문제 1 — 버전 감각

count = 42
print(f"{count=}")

Q. 이 코드가 도는 최소 버전과 출력은?

A. Python 3.8부터. 출력은 count=42 — = 디버그 표기는 식 원문과 값을 함께 찍습니다. (2부)

문제 2 — 출력 예측

a = {"x": 1, "y": 2}
b = {"y": 9, "z": 3}
print(a | b)

Q. 출력은?

A. {'x': 1, 'y': 9, 'z': 3} — 겹치는 키는 오른쪽이 이기고, 키 순서는 왼쪽 것 먼저 + 오른쪽 신규가 뒤. (3부)

문제 3 — 함정 회피

OK = 200
def check(status):
    match status:
        case OK:
            return "성공"
        case 404:
            return "없음"

Q. 이 함수의 문제는?

A. case OK:의 맨몸 이름은 캡처 패턴이라 무엇이든 매치됩니다 — 뒤의 case 404가 도달 불가라서 SyntaxError로 아예 거부됩니다. case 200: 리터럴이나 case HTTPStatus.OK:처럼 점 찍힌 이름을 써야 합니다. (4부)

문제 4 — 출력 예측

print("nextfile.txt".rstrip(".txt"))
print("nextfile.txt".removesuffix(".txt"))

Q. 두 줄의 출력은 각각?

A. nextfile 과 nextfile — 이번엔 우연히 같습니다! 하지만 "next.txt".rstrip(".txt")는 ne가 됩니다. rstrip은 문자 집합 {.,t,x}을 깎는 함수라 이름 끝의 t·x까지 먹습니다 — 접미사 제거는 반드시 removesuffix(3.9). (3부)

문제 5 — 동작 이해

try:
    raise ExceptionGroup("g", [ValueError("v"), KeyError("k")])
except* ValueError:
    print("V 처리")
except* KeyError:
    print("K 처리")

Q. 출력은?

A. V 처리와 K 처리 둘 다 출력됩니다. except*는 그룹에서 자기 타입의 부분 그룹을 각자 가져가므로 여러 블록이 모두 실행될 수 있습니다 — 일반 except와의 결정적 차이. (5부)

문제 6 — 함정 회피

from dataclasses import dataclass

@dataclass
class Basket:
    items: list = []

Q. 이 정의를 실행하면?

A. 클래스 정의 시점에 ValueError: mutable default ... use default_factory가 납니다. 인스턴스 간 리스트 공유 버그를 원천 차단하는 설계로, items: list = field(default_factory=list)가 정답입니다. (1부)

문제 7 — 버전 감각

type Matrix = list[list[float]]

def scale[T: (int, float)](m: list[T], k: T) -> list[T]:
    return [x * k for x in m]

Q. 최소 버전은? 그리고 type이 변수명인 기존 코드는 깨지는가?

A. Python 3.12 (PEP 695). type은 부드러운 키워드라 type = "text" 같은 기존 코드는 전혀 깨지지 않습니다 — match/case와 같은 도입 전략입니다. (6부)

문제 8 — 동작 이해

pairs = list(zip("abc", [1, 2], strict=True))

Q. 결과는? strict가 없다면?

A. ValueError — 길이가 3과 2로 달라서 즉시 검출됩니다(3.10). strict 없이는 조용히 [('a', 1), ('b', 2)]로 잘려 데이터 유실 버그가 숨습니다. 3.14에서는 map()에도 같은 strict가 생겼습니다. (4부·8부)

문제 9 — 버전 감각

def index(xs: list[str], key: str) -> int | None:
    ...

Q. import 없이 이 시그니처가 도는 최소 버전은?

A. Python 3.10. list[str]은 3.9(PEP 585)면 되지만 int | None은 3.10(PEP 604)이 필요합니다 — 둘의 조합이라 3.10. (3부·4부)

문제 10 — 동작 이해

name = "World"
result = t"Hello {name}"
print(result.upper())

Q. 마지막 줄의 결과는?

A. AttributeError — t-string의 결과는 str이 아니라 string.templatelib.Template 객체라 upper()가 없습니다. 문자열이 필요하면 렌더러 함수로 조립해야 하며, str과 자동으로 섞이지 않는 것이 바로 안전 장치입니다. (8부)

문제 11 — 동작 이해

async def main():
    async with asyncio.TaskGroup() as tg:
        tg.create_task(fast_fail())     # 0.1초 뒤 ValueError
        tg.create_task(slow_ok())       # 10초 걸리는 정상 작업

Q. main은 약 몇 초 만에 끝나고, 무엇을 던지는가?

A. 약 0.1초. fast_fail이 죽는 순간 slow_ok는 즉시 취소되고, 정리 후 ValueError를 담은 ExceptionGroup이 던져집니다(except*로 잡음). gather였다면 slow_ok가 10초를 계속 돌았을 상황입니다. (5부)

문제 12 — 함정 회피

def read_config(path):
    try:
        return parse(path)
    finally:
        return {}

Q. parse가 예외를 던지면 어떻게 되는가? 3.14의 반응은?

A. 예외가 소리 없이 사라지고 함수는 {}를 반환합니다 — finally의 return이 전파 중인 예외를 소멸시키기 때문입니다. 3.14는 이 패턴에 SyntaxWarning(PEP 765)을 냅니다. return을 try 쪽으로 옮기고 finally엔 뒷정리만 남기세요. (8부)

문제 13 — 버전 감각 (종합)

while (chunk := f.read(8192)):
    match parse(chunk):
        case {"type": "data", "rows": [first, *rest]}:
            handle(first, rest)

Q. 이 코드 조각의 최소 버전은?

A. Python 3.10 — 바다코끼리는 3.8이지만 match/case(매핑+시퀀스 중첩 패턴)가 3.10을 요구합니다. 최소 버전은 언제나 "가장 새 문법"이 결정합니다. (2부·4부)

문제 14 — 개념 확인 (최종 보스)

Q. 일반 빌드(GIL 있음)의 3.14에서 InterpreterPoolExecutor가 CPU 작업을 코어 수만큼 병렬로 처리할 수 있는 이유는?

A. 3.12의 PEP 684가 GIL을 "프로세스당 하나"에서 "인터프리터당 하나"로 바꿔 놓았기 때문입니다. 풀의 워커마다 독립 인터프리터(각자의 GIL)가 있어 서로를 막지 않습니다. 3.14의 PEP 734는 이 능력에 파이썬 API(concurrent.interpreters)를 씌운 것입니다. 이 답을 스스로 설명할 수 있다면 6~8부를 정복한 것입니다. (6부·8부)
