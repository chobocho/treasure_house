01Visitor 패턴이란?

Visitor(방문자) 패턴은 데이터 구조와 그 위에서 돌아가는 연산(알고리즘)을 분리하는 행위 디자인 패턴입니다. 데이터 클래스는 그대로 둔 채, 새로운 동작을 "방문자"라는 별도의 객체로 추가합니다.

🏛️ 비유 — 박물관의 도슨트 박물관의 전시물(그림·조각·유물)은 가만히 있습니다. 그런데 누가 방문하느냐에 따라 같은 전시물이 다르게 "처리"됩니다. 도슨트가 오면 해설을, 보존 전문가가 오면 상태 점검을, 회계사가 오면 보험 가치를 매깁니다. 전시물을 바꾸지 않고, 방문자만 바꾸면 완전히 새로운 동작이 추가되죠. 이게 Visitor 패턴입니다.

02왜 필요할까? — 표현식 문제

객체지향에서 동작을 추가하는 흔한 방법은 클래스에 메서드를 추가하는 것입니다. 도형마다 area()를 넣고, 또 draw(), toJson(), validate() … 이렇게 늘리다 보면 도형 클래스 하나하나가 온갖 관심사로 비대해집니다. 면적 계산 로직이 5개 도형 클래스에 흩어져, 한 알고리즘을 이해하려면 5개 파일을 뒤져야 하죠.

⚖️ 표현식 문제 (Expression Problem) 소프트웨어는 두 방향으로 자랍니다 — ① 새로운 타입(도형) 추가와 ② 새로운 연산(알고리즘) 추가. 한 방향을 쉽게 만들면 다른 방향이 어려워지는 근본적 트레이드오프가 존재합니다.
방식새 타입 추가새 연산 추가
일반 OOP (클래스에 메서드)😀 쉬움 — 클래스 하나 추가😖 어려움 — 모든 클래스를 수정
Visitor 패턴😖 어려움 — 모든 방문자를 수정😀 쉬움 — 방문자 하나 추가

즉 Visitor는 "타입은 안정적인데, 연산이 자주 늘어나는" 상황을 위한 패턴입니다. 그리고 그 대표적인 사례가 바로 컴파일러입니다. 언어의 문법 노드(AST)는 좀처럼 바뀌지 않지만, 그 위에서 돌아가는 패스(pass)는 끝없이 늘어나죠 — 타입 검사, 최적화, 코드 생성, 린트, 포매팅 ….

03핵심 원리: 더블 디스패치

Visitor의 심장은 더블 디스패치(double dispatch)입니다. 호출할 메서드가 두 객체의 실제 타입(어떤 요소인가 × 어떤 방문자인가)에 의해 결정되죠. 대부분의 언어는 단일 디스패치(메서드는 수신 객체 하나의 타입으로만 결정)만 지원하기 때문에, Visitor는 이를 두 번의 가상 호출로 흉내 냅니다.

🎯 두 번의 디스패치 1차 디스패치: shape.accept(v) → shape의 실제 타입에 따라 Circle.accept / Rectangle.accept 중 하나가 선택됨.
2차 디스패치: 그 accept 안에서 v.visitCircle(this)를 호출 → 이번엔 v의 실제 타입에 따라 AreaVisitor.visitCircle / DrawVisitor.visitCircle 중 하나가 선택됨.
더블 디스패치 탐색기 — 도형 × 방문자를 골라보세요

👆 요소를 바꾸면 1차 디스패치(파란색)가, 방문자를 바꾸면 2차 디스패치(보라색)가 달라집니다.

05🖥️ 컴파일러와 Visitor

Visitor 패턴이 가장 빛나는 무대가 바로 컴파일러·인터프리터입니다. 소스 코드를 파싱하면 AST(추상 구문 트리)가 만들어집니다. 노드 종류(숫자·변수·이항연산 …)는 문법이 정해지면 거의 고정이지만, 그 트리 위를 도는 패스(pass)는 끝없이 늘어나죠. 한 AST, 여러 Visitor — 이것이 현대 컴파일러의 기본 구조입니다.

08장단점과 안티패턴

👍 장점

  • 연산 추가가 쉽다 — 데이터 클래스 수정 없이 방문자만 추가
  • 관련 로직이 한곳에 — 한 알고리즘이 여러 클래스에 흩어지지 않음
  • 누적 상태 관리 — 방문자가 순회 중 상태(합계·심볼테이블)를 들고 다님
  • 타입별 분기 제거 — 거대한 if isinstance/switch type 사슬을 없앰

👎 단점 · 주의

  • 타입 추가가 어렵다 — 새 노드 1개 추가 시 모든 방문자를 수정
  • 보일러플레이트 — accept/visitXxx 짝이 장황함
  • 캡슐화 약화 — 방문자가 요소의 내부 데이터에 접근해야 함
  • 양방향 의존 — 요소↔방문자가 서로를 알아야 함
🚫 이럴 땐 쓰지 마세요 노드(타입) 종류가 자주 바뀐다면 Visitor는 독입니다 — 노드 하나 추가할 때마다 모든 방문자가 깨집니다. 또 연산이 딱 하나뿐이라면 그냥 메서드 하나가 더 간단합니다. Visitor는 "타입은 안정적, 연산은 계속 늘어남"이라는 조건이 맞을 때만 진가를 발휘합니다.

10치트시트 & 체크리스트

구현 5단계

  • 1. 요소 계층(노드)을 정의하고 공통 인터페이스에 accept(visitor)를 둔다.
  • 2. 각 구체 요소의 accept에서 visitor.visitXxx(this)를 호출한다. (1차 디스패치)
  • 3. 모든 구체 요소에 대응하는 visitXxx를 가진 Visitor 인터페이스를 만든다.
  • 4. 알고리즘 하나당 ConcreteVisitor 하나를 구현한다. (2차 디스패치)
  • 5. 클라이언트는 element.accept(visitor)만 호출한다.

"Visitor를 쓸까?" 체크리스트

  • 데이터 구조(노드 종류)가 안정적인가? → 예: 좋은 신호
  • 그 위에서 도는 연산이 계속 늘어나는가? → 예: 좋은 신호
  • 지금 타입 분기(isinstance/switch)가 여러 곳에 중복되는가? → 예: Visitor가 정리해 줌
  • 반대로 노드를 자주 추가하는가? → 예라면 Visitor는 피하라
언어요소→방문자 호출특징
Pythonv.visit_xxx(self)덕 타이핑 — 인터페이스 없이도 동작
Gov.VisitXxx(x)인터페이스로 Visitor 정의, 반환은 any
TypeScriptv.visitXxx(this)제네릭 Visitor<R>로 반환 타입 안전
C++v.visit(*this)오버로딩 + 결과 누적, 또는 std::variant
Javav.visitXxx(this)record + 제네릭, 또는 sealed + 패턴 매칭

“요소는 자신을 받아들이고, 방문자는 요소를 방문한다.”
