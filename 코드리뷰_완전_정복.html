1976년, 마이클 페이건과 IBM 인스펙션의 탄생

  • 마이클 페이건(Michael Fagan) — IBM 연구원, 1976년 IBM Systems Journal에 소프트웨어 인스펙션 방법론 발표
  • 핵심 아이디어 — 코드 검토를 개인기가 아닌 정의된 프로세스로: 계획, 개별 준비, 검토 회의, 재작업, 후속 확인
  • 역할 분담 — 모더레이터(진행), 작성자, 리더(코드 낭독), 테스터(테스트 관점)
  • 결함을 '발견'하는 회의이지 '해결'하는 회의가 아니다 — 수정은 회의 밖에서
검사를 통해 결함을 개발 초기에 찾으면, 테스트에서 찾는 것보다 훨씬 싸게 고칠 수 있다 — Fagan, 1976의 핵심 주장

페이건 인스펙션, 숫자로 증명하다

  • 결함 조기 제거율 — 인스펙션으로 전체 결함의 60~90%를 테스트 단계 이전에 제거했다고 보고
  • 재작업 비용 절감 — 결함을 코딩 단계에서 잡으면 테스트·운영 단계의 값비싼 재작업이 사라진다
  • IBM 내부 프로젝트 검증 — 일정 지연 없이 오히려 전체 개발 기간이 단축되는 사례를 제시
  • "검토에 쓰는 시간은 비용이 아니라 투자"라는 명제가 처음으로 데이터를 얻은 순간

무거운 인스펙션에서 가벼운 현대 리뷰로

  • OSS 메일링리스트 — 1990년대 리눅스 커널 등에서 패치를 메일로 보내고 답장으로 리뷰하는 비동기 리뷰가 정착

그레이스 호퍼와 1947년의 나방 — 최초의 '버그' 로그

  • 1947년 9월 9일 — 하버드 Mark II의 릴레이 70번에서 진짜 나방이 발견되어 오작동을 일으켰다
  • 로그북 기록 — 호퍼 팀은 나방을 테이프로 붙이고 "First actual case of bug being found"라고 적었다
  • '버그'라는 말 자체는 에디슨 시대부터 있었지만, 이 기록이 결함을 문서화하고 추적하는 문화의 상징이 됐다

에이다 러브레이스 — 최초의 프로그램, 최초의 검토

  • 1843년, Note G — 배비지의 해석기관으로 베르누이 수를 계산하는 절차를 기술. 흔히 '최초의 프로그램'으로 불린다
  • 서신 교정 — 러브레이스와 배비지는 편지로 원고와 표를 주고받으며 서로의 오류를 지적하고 고쳤다
  • 컴퓨터가 실물로 존재하기도 전에, 프로그램은 이미 다른 사람의 검토를 거치고 있었다

천공카드 시대의 desk checking

  • 배치 처리의 경제학 — 카드 뭉치를 제출하면 결과는 몇 시간~하루 뒤. 컴파일 한 번이 극도로 비쌌다
  • desk checking — 제출 전에 책상 위에서 코드를 손으로 따라가며 실행을 시뮬레이션하는 것이 기본 소양
  • 동료 교차 검사 — 옆자리 동료에게 카드 뭉치를 읽어달라고 부탁하는 관행도 흔했다
  • 실행이 비쌀수록 검토가 싸다 — 오늘날 리뷰 경제학의 원형

ENIAC 프로그래머들과 초기 검증 문화

  • 1940년대 ENIAC — 진 바틱, 베티 홀버튼 등 여섯 명의 프로그래머가 배선과 스위치로 프로그램을 '조립'
  • 실행 전 검증이 전부 — 잘못된 배선은 며칠의 재작업. 배선도를 종이 위에서 서로 교차 확인하는 것이 필수였다
  • 브레이크포인트의 원형 — 홀버튼은 계산을 중간에 멈춰 상태를 점검하는 기법을 고안했다
  • 최초의 프로그래머들은 처음부터 '검증하는 사람들'이었다

1968 NATO 회의와 '소프트웨어 위기'

  • 배경 — 1960년대 대형 프로젝트(대표적으로 IBM OS/360)가 줄줄이 예산 초과, 일정 지연, 결함 폭증을 겪었다
  • 1968년 가르미슈 — NATO 소프트웨어 공학 회의가 열려 이 상황을 '소프트웨어 위기'로 명명
  • 처방 — 소프트웨어 개발을 공학으로: 정의된 프로세스, 측정, 그리고 체계적 검토
  • 페이건 인스펙션(1976)은 이 위기의식에 대한 IBM의 실천적 답변이었다

마거릿 해밀턴과 아폴로 AGC

  • MIT 계기연구소 — 해밀턴은 아폴로 유도 컴퓨터(AGC) 비행 소프트웨어 개발을 이끌었다
  • 'software engineering' — 소프트웨어 개발도 하드웨어 공학과 동등한 규율이 필요하다며 이 용어를 앞장서 사용
  • 검증 문화 — 모든 코드 변경 추적, 시뮬레이션 검증, 오류 우선순위 설계 — 오늘날 안전 필수 소프트웨어 규율의 원형

아폴로 11 — 무결점을 요구받은 소프트웨어

  • 패치 불가능한 배포 — 발사 후에는 코드를 고칠 수 없다. AGC 소프트웨어는 로프 메모리에 물리적으로 '짜여' 실렸다
  • 1202 알람 — 착륙 도중 컴퓨터 과부하 경보. 우선순위 기반 실행 설계 덕에 핵심 작업만 유지하며 착륙에 성공
  • 철저한 사전 검토와 방어적 설계가 사람의 생명을 지킨 사례 — 리뷰 문화의 도덕적 근거

구현 직후, 테스트·운영보다 훨씬 앞이다. 리뷰에서 잡은 결함 하나는 운영에서 잡을 때 비용의 수십 분의 일로 처리된다. 리뷰가 '싼 보험'인 이유다.

리뷰의 효익 ① 결함 조기 발견

  • 다른 눈의 힘 — 작성자는 자기가 의도한 코드를 '읽는' 것이 아니라 '기억'한다. 제3자만 실제 코드를 읽는다
  • 테스트가 못 잡는 것 — 경계 조건, 오류 처리 누락, 동시성 가정은 테스트 케이스에 없으면 통과해 버린다

리뷰어의 눈에만 걸리는 전형적 결함 — off-by-one

for (int i = 0; i <= items.size(); i++) {  // 리뷰: <= 이면 마지막에 범위 초과 아닌가요?
    process(items.get(i));
}
  • 해피 패스 테스트는 모두 통과하다가 운영에서 IndexOutOfBoundsException — 리뷰 코멘트 한 줄이면 끝났을 결함

리뷰의 효익 ② 지식 공유와 버스 팩터

  • 버스 팩터(bus factor) — 몇 명이 버스에 치이면(=퇴사하면) 프로젝트가 멈추는가. 1이면 위험 신호
  • 리뷰 = 강제 지식 전파 — 모든 변경이 최소 2명(작성자 + 리뷰어)의 머릿속을 거친다
  • 암묵지의 문서화 — 리뷰 코멘트와 답변은 "왜 이렇게 했는가"의 기록으로 남는다
  • 리뷰를 특정인에게만 몰아주면 이 효익은 사라진다 — 리뷰어 로테이션이 필요한 이유

모든 코드를 아는 사람이 최소 2명

리뷰의 효익 ③ 일관성과 집단 코드 소유권

  • 일관성 — 같은 문제를 팀 전체가 같은 방식으로 풀게 된다. 새 코드가 기존 코드처럼 읽힌다
  • 집단 코드 소유권(collective code ownership) — XP의 원칙. "내 코드/네 코드"가 아니라 "우리 코드"
  • 리뷰가 만드는 것 — 승인한 순간 리뷰어도 그 코드의 공동 소유자가 된다
  • "이건 그 사람 코드라 못 건드려요"라는 말이 사라지는 것이 성공의 지표
코드는 개인의 작품이 아니라 팀의 자산이다. 리뷰는 소유권을 개인에서 팀으로 옮기는 의식이다 — 집단 소유권의 요지

리뷰의 효익 ④ 학습과 멘토링

  • 맞춤형 교육 — 리뷰 코멘트는 '지금 내가 쓴 바로 그 코드'에 대한 피드백. 일반 강의보다 학습 효율이 높다
  • 양방향 학습 — 주니어는 관례와 설계를 배우고, 시니어는 새 언어 기능과 신선한 접근을 배운다
  • 온보딩 가속 — 신규 입사자가 코드베이스의 규칙을 몸으로 익히는 가장 빠른 경로
  • "이렇게 고치세요"보다 "이렇게 하면 어떤 점이 좋아질까요?"가 더 오래 남는다

연구 근거 ① Microsoft 2013 — 개발자는 리뷰에서 무엇을 기대하는가

  • Bacchelli & Bird (ICSE 2013) — "Expectations, Outcomes, and Challenges of Modern Code Review". Microsoft 개발자·관리자 대상 관찰과 설문
  • 의외의 결과 — 기대 1순위는 결함 발견이 아니라 코드 개선, 그다음이 대안 탐색·지식 공유
  • 실제 코멘트 분석 — 심각한 결함 지적보다 가독성·유지보수성 개선 코멘트가 다수를 차지
  • 시사점: 리뷰를 '버그 검출기'로만 평가하면 실제 가치의 대부분을 놓친다
현대 코드리뷰의 최대 산출물은 결함 목록이 아니라 더 나은 코드와 더 아는 팀이다 — Bacchelli & Bird, 2013의 함의

Q. 1,000줄짜리 PR을 한 번에 리뷰해 달라는 요청, 어떻게 해야 하나?

쪼개 달라고 요청하는 것이 정답이다. 400 LOC를 넘으면 결함 발견율이 떨어진다는 것이 이 연구의 핵심 결론이므로, 큰 PR을 대충 훑는 것보다 작은 PR 여러 개를 제대로 보는 편이 낫다.

리뷰가 못 잡는 것 — 한계를 알아야 제대로 쓴다

  • 성능 회귀 — 눈으로 O(n²)은 잡아도 캐시 미스나 실측 지연은 못 잡는다 → 프로파일링·벤치마크가 답
  • 아키텍처 결함 — PR 단위 리뷰는 이미 정해진 구조 안의 변경만 본다 → 설계 리뷰·ADR로 앞 단계에서 다뤄야
  • 심층 보안 취약점 — 암호 구현 오류, 복잡한 권한 우회는 전문 보안 감사·도구의 영역
  • 요구사항 오해 — 코드가 스펙대로여도 스펙이 틀렸으면 리뷰는 무력하다
  • 리뷰는 품질 활동 포트폴리오의 한 축이지 전부가 아니다 — 테스트, 정적 분석, 모니터링과 역할 분담

리뷰 목표의 우선순위

정확성 > 설계 > 가독성 > 스타일

  • 1. 정확성 — 이 코드가 맞는 일을 맞게 하는가. 경계 조건, 오류 처리, 동시성
  • 2. 설계 — 이 변경이 시스템에 어울리는가. 지금이 아니면 고치기 어려워지는 것들
  • 3. 가독성 — 6개월 뒤의 동료가 읽고 이해할 수 있는가
  • 4. 스타일 — 포매팅, 관례. 중요하지만 가장 나중이고, 대부분 기계가 처리할 일
  • 우선순위가 낮은 지적으로 우선순위가 높은 논의를 덮지 말 것 — 스타일 코멘트 20개에 설계 문제 1개가 묻히는 리뷰가 최악이다

Google의 승인 원칙 — 완벽이 아니라 개선

리뷰어는 CL이 완벽하지 않더라도, 코드베이스의 전반적 품질을 확실히 개선한다면 승인해야 한다 — Google eng-practices 리뷰 가이드
  • 기준의 전환 — "내가 짰다면 이렇게 안 짰다"는 반려 사유가 아니다. "이 변경으로 코드베이스가 나아지는가"만 묻는다
  • 완벽주의 차단 — 완벽한 코드는 존재하지 않는다. 존재하는 것은 더 나은 코드뿐
  • 교착 방지 — 이 원칙이 없으면 리뷰는 취향 대결과 무한 반려의 장이 된다
  • 단, '개선'에는 예외가 없다 — 명백한 결함이나 시스템을 나쁘게 만드는 설계는 개선이 아니다

스타일 논쟁은 기계에게

  • 도구에 위임 — 들여쓰기, 줄바꿈, 임포트 순서는 포매터(Prettier, Black, gofmt)와 린터(ESLint, Checkstyle)가 CI에서 강제
  • 효과 — 탭 vs 스페이스 논쟁이 리뷰에서 사라지고, 사람은 판단이 필요한 것(정확성·설계·가독성)만 본다
  • 규칙 — 기계가 잡을 수 있는 것을 사람이 코멘트하고 있다면, 프로세스가 잘못된 것

  • 이유 ① 인지 부하 — 리뷰어가 머릿속에 유지할 수 있는 맥락에는 한계가 있다
  • 이유 ② 리뷰 지연 — 큰 PR은 "나중에 봐야지"가 되고, 나중은 오지 않는다

  • 쪼개는 축: 리팩터링과 기능 추가 분리, 기계적 변경(포맷·리네임)과 논리 변경 분리

리뷰어의 3가지 자세

  • 호기심 — 단정 대신 질문. "왜 이 방식을 택했나요?"는 지적보다 많은 것을 끌어낸다
  • 겸손 — 내가 모르는 맥락이 있을 수 있다는 전제. 틀린 지적을 할 자유가 있어야 지적이 나온다
  • 구체성 — 문제만 말하지 말고 방향이나 대안을 함께. 코드는 비판해도 사람은 비판하지 않는다

작성자의 3가지 자세

  • 방어하지 않기 — 코멘트는 코드에 대한 것이지 나에 대한 것이 아니다. 반사적 반박 전에 하루의 절반만이라도 생각할 것
  • 감사 — 리뷰는 남의 시간을 내 코드에 쓰는 일. 좋은 지적에는 "잡아줘서 고맙다"고 말하는 팀이 오래 간다
  • 설명 책임 — "왜?"라는 질문을 받았다면 답은 가급적 코드나 주석으로. 리뷰 스레드의 설명은 다음 독자에게 전달되지 않는다
  • 의견이 갈리면: 근거로 토론 → 그래도 평행선이면 스타일 가이드·제3자·팀 결정으로 에스컬레이션. 스레드에서 무한 왕복하지 않는다

응답 시간 원칙 — 1영업일

  • 기준 — 리뷰 요청에는 늦어도 1영업일 안에 첫 응답을 한다 (Google 가이드의 상한)
  • 대기 비용 — 리뷰를 기다리는 동안 작성자는 블로킹되거나, 다음 일로 넘어가 컨텍스트를 잃는다. 며칠 뒤 코멘트에 답하려면 머릿속 상태를 처음부터 재구성해야 한다
  • 지연의 복리 — 리뷰가 느린 팀은 PR을 크게 만든다("어차피 오래 걸리니 몰아서") → 큰 PR은 리뷰를 더 느리게 → 악순환
  • 지금 다 볼 수 없다면 "내일 오전에 보겠습니다"라는 응답이라도 1영업일 안에 — 침묵이 가장 나쁘다

승인(LGTM)의 의미와 책임

  • LGTM — "Looks Good To Me". 가볍게 쓰이지만 가벼운 말이 아니다
  • 승인의 의미 — "이 변경은 코드베이스를 개선하며, 나는 그 판단에 이름을 건다"는 서명
  • 공동 책임 — 승인한 코드가 장애를 내면 작성자만의 잘못이 아니다. 보지 않고 누른 LGTM은 팀에 대한 기만
  • 스탬프 리뷰 경계 — 승인은 빨랐는데 코멘트가 0인 패턴이 반복되면 리뷰가 형식화됐다는 신호
  • 확신이 없으면 범위를 정직하게: "테스트 로직 위주로 봤고, 인프라 부분은 다른 분 확인이 필요합니다"

Weinberg의 egoless programming — 1971

자아와 코드를 분리하라. 결함의 발견은 나의 실패가 아니라 코드가 좋아질 기회다 — 제럴드 와인버그, The Psychology of Computer Programming (1971)의 요지
  • 배경 — 와인버그는 프로그래머가 코드를 자아와 동일시할 때 결함 지적을 인신 공격으로 받아들인다고 관찰했다
  • egoless programming — 코드를 팀 앞에 열어 두고, 비판을 환영하는 문화. 현대 코드리뷰 에티켓의 사상적 뿌리
  • 리뷰에의 적용 — "네 코드가 틀렸다"가 아니라 "이 코드에 이런 경우가 빠졌다" — 주어를 사람에서 코드로
  • 페이건 인스펙션(1976)보다도 5년 앞서, 기술이 아니라 심리가 먼저 정리된 셈이다

리뷰 코멘트의 3분류 — 필수 / 제안 / nit

분류의미승인과의 관계
필수 (issue)결함·보안·데이터 손상 등 반드시 해결해결 전 승인 불가
제안 (suggestion)더 나은 방법 제시, 채택은 협의승인 가능, 후속 처리 합의
nit사소한 다듬기, 반영은 재량승인과 무관
issue: 이 쿼리는 사용자 입력을 그대로 연결합니다. SQL 인젝션이
  가능하니 파라미터 바인딩으로 바꿔야 합니다
suggestion: 이 분기들은 Map 조회로 바꾸면 추가 케이스에 강해질 것 같아요
nit: 오타 — recieve → receive

분류를 코멘트에 명시하면 작성자의 우선순위 판단이 즉시 끝난다 (Conventional Comments 관례와 상통)

완벽주의 함정 — better is better than perfect

  • 함정 — "이왕 고치는 김에 저것도, 그리고 저것도" — 리뷰가 리라이트 요구로 변질되는 순간 개선은 멈춘다
  • 비용 — 반려가 반복되면 작성자는 학습 대신 회피를 배운다: PR을 미루고, 몰래 합치고, 리뷰어를 골라 낸다
  • 기준 복귀 — 물을 것은 하나: "이 변경이 지금보다 코드베이스를 낫게 만드는가?" 그렇다면 나머지는 후속 이슈로
  • 단, '나중에 고치자'가 기록 없이 반복되면 부채가 된다 — 후속 작업은 반드시 이슈로 남길 것
완벽한 코드란 없다. 더 나은 코드가 있을 뿐이다 — Google eng-practices 리뷰 가이드

퀴즈 — 2장 점검

Q1. 리뷰어인 당신 눈에 "나라면 다르게 짰을" 구현이 보인다. 결함은 없고 스타일 가이드 위반도 없다. 어떻게 하는가?

승인한다. 필요하면 nit: 또는 suggestion으로 대안을 남기되 블로킹하지 않는다. 승인 기준은 '내 취향과의 일치'가 아니라 '코드베이스의 개선'이다. 근거를 들 수 없는 지적은 개인 취향이며, 취향은 강제할 수 없다.

Q2. 900 LOC짜리 PR이 리뷰 요청으로 들어왔다. 기능 구현과 대규모 리네임이 섞여 있다. 올바른 대응은?

분할을 요청한다. 400 LOC를 넘으면 결함 발견율이 떨어진다는 것이 SmartBear/Cisco 연구의 결론이고, 특히 기계적 변경(리네임)과 논리 변경(기능)이 섞이면 diff에서 위험한 부분을 골라내기 어렵다. 리네임 PR과 기능 PR로 나누면 각각 몇 분 만에 깊게 볼 수 있다.

2장 요약

  • 우선순위 — 정확성 > 설계 > 가독성 > 스타일. 낮은 우선순위 지적이 높은 논의를 덮지 않게
  • 승인 기준 — 완벽이 아니라 개선. 코드베이스가 나아지면 승인한다 (Google 원칙)
  • 역할 분담 — 스타일은 린터·포매터에게, 사람은 판단이 필요한 7가지에 집중. 사소한 것은 nit:으로 표시
  • 프로세스 — 400 LOC 이하로 쪼개고, 올리기 전 셀프 리뷰와 체크리스트, 응답은 1영업일 안에
  • 태도 — 리뷰어는 호기심·겸손·구체성, 작성자는 비방어·감사·설명 책임. 뿌리는 Weinberg의 egoless programming(1971)
  • 책임 — LGTM은 서명이다. 코멘트는 필수/제안/nit으로 분류해 우선순위를 드러낸다

완벽한 코드는 없다, 더 나아진 코드가 있을 뿐

리뷰는 요청 전에 절반이 끝난다

  • 작성자 준비 책임 — 리뷰 품질의 절반은 리뷰 요청을 누르기 전에 결정된다
  • 셀프 리뷰 먼저 — 자기 diff를 리뷰어의 눈으로 한 번 훑고 나서 요청한다
  • 셀프 리뷰에서 디버그 print, 주석 처리된 코드, 오타 커밋을 미리 걷어낸다
  • 리뷰어의 시간은 팀의 자원 — 준비 안 된 PR 한 건이 리뷰어 여러 명의 오후를 소모한다
  • Microsoft 2013 연구(Bacchelli & Bird)에서도 리뷰어의 가장 큰 어려움은 "변경 의도 이해"였다

리뷰어가 이해하기 쉽게 = 결함이 잡히기 쉽게

좋은 PR 설명 쓰기 — 무엇·왜·어떻게 테스트

❌ 이렇게 말고

제목: 버그 수정

본문: (없음)

✅ 이렇게

무엇: 주문 취소 시 포인트 이중 환불 수정

왜: 취소 웹훅이 재시도되면 환불이 2회 실행됨 (이슈 #482)

테스트: 웹훅 2회 호출 통합 테스트 추가, 스테이징에서 재현 후 확인

  • 무엇을 바꿨고, 왜 바꿨고, 어떻게 검증했는지 세 가지가 기본 골격
  • 스크린샷·이슈 링크·롤백 방법까지 있으면 리뷰어의 첫 질문이 사라진다

커밋 정리 — 논리 단위로 스토리 만들기

  • 커밋 = 논리적 변경 1개 — "리팩터링 + 기능 + 오타 수정"을 한 커밋에 섞지 않는다
  • rebase로 역사 재구성 — 작업 순서가 아니라 읽는 사람의 순서로 커밋을 배열한다
$ git rebase -i main
pick a1b2c3 리팩터링: UserRepo 인터페이스 추출
pick d4e5f6 기능: 소셜 로그인 추가
pick 789abc 테스트: 소셜 로그인 실패 경로 커버
fixup  fedcba 오타 수정          # 본 커밋에 흡수

리뷰어가 커밋 단위로 읽을 수 있으면 큰 PR도 작은 PR 여러 개처럼 읽힌다

PR 크기 전략 — 쪼개는 기술

  • 기준선 — SmartBear/Cisco 연구: 400 LOC를 넘으면 결함 발견율이 급락한다
  • 기능 플래그 — 미완성 기능도 플래그 뒤에 숨기면 작은 단위로 머지 가능
  • if (flags.newCheckout) { ... } — 꺼진 코드는 배포돼도 실행되지 않는다
  • 스택 PR — 리팩터링 PR → 기반 PR → 기능 PR 순으로 의존 사슬을 만들어 각각 리뷰
  • 1번 PR이 머지되면 2번 PR의 diff가 자동으로 줄어든다
  • 수직 분할 — "화면 전체"가 아니라 "저장 버튼 하나가 끝까지 동작"하는 단위로 자른다

쪼갤 수 없는 PR은 설계를 의심하라

🎮 리뷰 속도 계산기 — 얼마나 걸려야 정상일까

  • 연구 기준: 시간당 200~400 LOC를 넘기면 결함 발견율이 급락한다 (SmartBear·Cisco 2,500개 리뷰 분석)
  • 슬라이더를 움직여 변경 크기별 권장 리뷰 시간을 확인해 보자

수치는 연구 결과를 단순화한 근사치 — 절대값보다 "커질수록 급격히 나빠진다"는 경향이 핵심.

리뷰어 선정 — 누구에게 맡길 것인가

  • 코드 오너 — 해당 디렉터리의 CODEOWNERS는 기본 필수 리뷰어
  • 도메인 전문가 — 결제·보안·동시성처럼 전문 지식이 필요한 변경은 그 분야 경험자를 추가
  • 성장 목적 1명 — 그 코드를 앞으로 다룰 주니어를 함께 지정해 지식을 전파한다
  • Microsoft 2013 연구: 리뷰의 실질 효과 상위권은 결함 발견 못지않게 지식 공유였다
  • 리뷰어 2명 초과는 역효과 — 책임이 분산되어 아무도 깊게 읽지 않는다
  • "모두의 책임은 누구의 책임도 아니다" — 필수 승인자는 명시적으로 1~2명

리뷰어의 3-pass 읽기 전략

논문 읽기의 3-pass처럼, 코드도 세 번에 나눠 깊이를 더해 읽는다

패스목적소요
① 조망무엇을 왜 바꾸는지 파악2~5분
② 설계 훑기구조·인터페이스·테스트 확인5~15분
③ 줄 단위 정독로직·경계·오류 경로 검증변경량 비례
  • ①에서 방향이 틀렸으면 ③까지 가지 않고 바로 설계 논의로 전환 — 시간 절약의 핵심

Pass ① 조망 — 무엇을 왜 바꾸나

  • PR 설명부터 — 코드보다 설명·이슈 링크를 먼저 읽고 변경의 의도를 잡는다
  • 이슈 원문 확인 — 요구사항과 PR이 실제로 일치하는지 대조한다
  • "요청은 A인데 구현은 A'"인 어긋남은 diff에는 절대 보이지 않는다
  • 변경 통계 확인 — 파일 수·추가/삭제 라인으로 리뷰 시간을 먼저 가늠한다
  • 방향 질문 먼저 — "이 접근이 맞나?"가 의심되면 줄 단위 코멘트 전에 설계 질문을 던진다
  • 방향이 틀린 PR에 남긴 50개의 스타일 코멘트는 전부 낭비가 된다

Pass ② 설계 훑기 — 구조와 인터페이스

  • 파일 구조부터 — 어떤 파일이 새로 생기고 어떤 모듈에 손댔는지 지도를 그린다
  • 공개 인터페이스 우선 — public 함수 시그니처·API 스키마·DB 마이그레이션을 먼저 본다
  • 내부 구현은 나중에 고칠 수 있지만 공개 인터페이스는 머지 후 되돌리기 어렵다
  • 테스트를 먼저 읽는다 — 테스트는 "이 코드가 무엇을 약속하는가"의 실행 가능한 명세
  • 테스트 이름만 훑어도 커버 범위와 빠진 케이스가 드러난다

구현보다 인터페이스, 코드보다 테스트 먼저

Pass ③ 줄 단위 정독

  • 속도 상한 — SmartBear/Cisco 연구 기준 시간당 200~400 LOC를 넘기면 발견율이 떨어진다
  • 세션 상한 — 60~90분을 넘기면 집중력이 무너진다, 큰 PR은 나눠서 읽는다
  • 정독 대상 — 조건식의 경계, 오류 처리, 반복문 종료 조건, 자원 해제
  • "동작하는 행"보다 "실패하는 순간의 행"을 상상하며 읽는다
  • 스타일은 도구에 — 포매팅·린트 지적은 CI에 맡기고 사람은 로직에 집중한다

diff만 보지 말 것 — 주변 맥락 확인

# diff에 보이는 것: 반환 타입 변경 (그럴듯해 보인다)
def find_user(uid: int) -> User:
def find_user(uid: int) -> User | None:
    if uid not in _table: return None

# diff에 안 보이는 것: 다른 파일의 기존 호출부
user = find_user(uid)
send_mail(user.email)   # None이면 AttributeError!
  • 호출부 확인 — 시그니처·계약이 바뀌면 호출하는 쪽을 전부 찾아본다
  • diff는 변경된 줄만 보여준다, 버그는 변경되지 않은 줄과의 조합에서 나온다

큰 변경은 체크아웃해서 직접 실행한다

$ gh pr checkout 1234
$ npm test                # 전체 테스트 통과 확인
$ npm run dev             # 직접 눌러 본다
  • 화면 있는 변경은 화면으로 — UI·UX 변경은 diff가 아니라 실행 화면으로 판단한다
  • IDE의 힘 빌리기 — 체크아웃하면 정의 이동·참조 찾기·타입 검사를 그대로 쓸 수 있다
  • 웹 diff 뷰어에서는 안 보이던 호출 관계가 IDE에서는 한 번의 점프로 보인다
  • 경계 입력 직접 투입 — 빈 목록, 한글 이름, 아주 긴 문자열을 손으로 넣어본다

질문 목록 만들며 읽기

  • 읽으면서 바로 쏘지 않는다 — 코멘트 남발 대신 메모장에 질문을 쌓으며 끝까지 읽는다
  • 뒷부분을 읽다 보면 앞의 질문 절반은 스스로 풀린다 — 남발한 코멘트는 회수 비용이 크다
  • 다 읽고 일괄 정리 — 중복 제거, 우선순위 정렬 후 한 번에 제출한다
  • 중요도 표시 — Conventional Comments처럼 issue/suggestion/question/nitpick 라벨을 붙인다
  • Google 스타일의 nit: 접두어 — "고치면 좋지만 승인을 막지는 않는다"는 신호
  • 패턴 지적은 한 번만 — 같은 문제가 10곳이면 "전체에 동일 적용"으로 한 개의 코멘트

리뷰 라운드 관리 — 왕복을 줄인다

  • 왕복 1회의 비용 — 시차 있는 팀이면 라운드 하나가 하루를 잡아먹는다
  • 큰 것 먼저 — 1라운드에서 설계 문제를 다 꺼낸다, 다 고친 뒤에 "사실 구조가 틀렸다"는 최악
  • 한 라운드에 하나의 주제 금지 — 발견한 문제는 모아서 한 번에, 찔끔찔끔 내지 않는다
  • 라운드마다 새 문제를 하나씩 꺼내는 리뷰어는 작성자의 신뢰를 잃는다
  • 응답 시간 약속 — Google 가이드는 리뷰 요청에 1영업일 내 응답을 권고한다
  • 3라운드 넘으면 대화로 — 텍스트 왕복이 길어지면 10분 통화가 더 싸다

페어 리뷰·동기식 리뷰가 나은 경우

  • 복잡한 설계 변경 — 비동기 코멘트 왕복보다 30분 화면 공유가 빠르다
  • 온보딩 중인 동료 — 함께 읽으며 코드베이스의 암묵지를 전달한다
  • 페어로 짠 코드 — 작성 중 리뷰가 이미 이뤄졌으므로 사후 리뷰를 가볍게 갈 수 있다
  • 단, 동기식 리뷰도 결정 사항은 반드시 PR에 텍스트로 남긴다 — 기록이 없으면 없던 일

Comment의견만, 판정 유보머지에 영향 없음
  • Request changes는 강한 신호 — "취향 차이" 수준에는 Comment + nit:가 적절하다

코드리뷰 시간 확보 — 하루 리듬에 넣기

  • 리뷰 슬롯 고정 — 출근 직후·점심 직후처럼 하루 2회, 30분 리뷰 시간을 캘린더에 박는다
  • "짬 나면 리뷰"는 영원히 짬이 나지 않는다 — 대기 중인 PR이 팀 전체를 블로킹한다
  • 딥워크와 분리 — 집중 코딩 중 리뷰 알림에 즉시 반응하지 않는다, 슬롯에서 처리
  • 리뷰 우선의 근거 — 내 코드 1줄보다 동료의 블로킹 해제가 팀 처리량에 더 기여한다
  • 리뷰 대기 시간은 PR 크기와 함께 리뷰 문화의 대표 지표 — 대시보드로 추적할 가치가 있다

리뷰어 출발 전 체크리스트 🎮

저자 응답 에티켓

  • 모든 코멘트에 반응 — 수정했으면 "커밋 abc123에 반영", 반대면 근거를 적는다, 무시는 금지
  • resolve 규칙 합의 — 코멘트를 단 사람이 닫을지, 저자가 닫을지 팀 규칙을 정한다
  • 저자가 일방적으로 resolve하면 리뷰어는 반영 여부를 다시 diff에서 찾아야 한다
  • 수정은 새 커밋으로 — 리뷰 중 force-push는 리뷰어의 "이전에 어디까지 읽었는지"를 파괴한다
  • 반박은 코드베이스 기준으로 — "제 취향"이 아니라 컨벤션·데이터·문서를 근거로 논의한다
  • Google 가이드의 원칙 — 의견이 갈리면 개인 선호가 아니라 스타일 가이드와 사실이 우선

머지 기준과 머지 후 후속

CL이 완벽하지 않더라도, 코드베이스의 전반적 품질을 확실히 개선한다면 승인하라 — Google eng-practices 리뷰 가이드
  • 완벽이 아니라 개선 — "더 좋게 만들 수 있는 여지"는 머지를 막는 사유가 아니다
  • 남은 nit는 follow-up 이슈로 — 사소한 개선은 이슈 번호를 만들어 기록하고 머지한다
  • "나중에 고치자"는 이슈 트래커에 없으면 영원히 사라진다 — 번호가 곧 약속
  • 머지 후 확인 — 배포 파이프라인 통과, 모니터링 대시보드 확인까지가 저자의 책임

셀프 체크 퀴즈 — 3장

Q. 800 LOC짜리 PR의 리뷰 요청이 왔다. 가장 좋은 대응은?

먼저 분할 가능한지 저자와 논의한다. SmartBear/Cisco 연구 기준 400 LOC를 넘으면 결함 발견율이 급락하므로, 스택 PR·기능 플래그·커밋 단위 리뷰 등으로 쪼개는 것이 우선이다. 분할이 정말 불가능하면 60~90분 세션 여러 번으로 나눠 읽는다.

Q. 리뷰 1라운드에서 설계 문제를 발견했다. 줄 단위 코멘트도 같이 남겨야 할까?

아니다. 설계가 바뀌면 그 코드 대부분이 다시 작성되므로 줄 단위 코멘트는 낭비가 된다. 3-pass의 원칙대로 조망 단계에서 방향 문제를 먼저 합의하고, 구조가 확정된 뒤 정독에 들어간다.

Q. Request changes와 Comment의 차이는?

Request changes는 브랜치 보호가 켜진 저장소에서 머지를 차단하는 강한 반대 신호다. 취향 수준의 의견이나 판정을 유보한 질문은 Comment(+ nit: 라벨)로 남기는 것이 적절하다.

3장 요약

  • 작성자 — 셀프 리뷰, 무엇·왜·테스트가 담긴 PR 설명, rebase로 정리한 커밋, 400 LOC 이하 분할
  • 리뷰어 선정 — 코드 오너 + 도메인 전문가 + 성장 목적 1명, 필수 승인자는 소수 명시
  • 읽기 — 조망 → 설계 → 정독의 3-pass, 테스트 먼저, diff 밖 호출부 확인, 큰 건 체크아웃
  • 왕복 — 큰 문제 먼저 한 번에, 1영업일 응답, 3라운드 넘으면 대화로 전환
  • 마무리 — 모든 코멘트에 반응, "개선이면 승인", 남은 것은 follow-up 이슈로

준비된 PR + 전략적 읽기 = 절반의 시간, 두 배의 발견

관점 1 정확성 — 이 코드는 맞게 동작하는가 🎮

가장 우선하는 관점 — 다른 모든 장점은 코드가 맞을 때만 의미가 있다

정확성 ① 경계값과 오프바이원

// Java: 페이지 수 계산의 고전적 오프바이원
int pages = totalItems / PAGE_SIZE;              // 101건 → 10페이지, 1건 증발
int pages = (totalItems + PAGE_SIZE - 1) / PAGE_SIZE;  // 101건 → 11페이지

// 반복문 경계도 같은 부류
for (int i = 0; i <= items.size(); i++)  // IndexOutOfBounds
for (int i = 0; i < items.size(); i++)
  • 리뷰 질문 — "입력이 0개·1개·정확히 한 페이지·한 페이지+1개면 어떻게 되나?"
  • 경계는 <와 <=, 올림과 내림, 포함과 미포함 — 한 글자 차이가 전부다

정확성 ② null·빈 값·오류 경로

// JS: 낙관적 경로만 있는 코드
const items = res.data.items;        // data가 없으면? TypeError
items.forEach(render);               // items가 []이면? 화면이 그냥 빈다 - 의도인가?

// 오류 경로: catch가 상태를 되돌리는가
try { cart.add(item); await api.sync(); }
catch (e) { cart.remove(item); toast(e); }  // 롤백 없으면 화면·서버 불일치
  • 세 가지를 항상 묻는다 — 없을 때(null), 비었을 때(empty), 실패했을 때(error)
  • "빈 목록"과 "로딩 실패"를 같은 화면으로 처리하는 것은 대개 버그다

정확성 ③ 동시성과 경쟁 조건

// Java: check-then-act — 검사와 행동 사이의 틈
if (!cache.containsKey(key)) {       // 두 스레드가 동시에 통과하면
    cache.put(key, load(key));       // load()가 두 번 실행된다
}
cache.computeIfAbsent(key, k -> load(k));  // 원자적 연산으로 교체
  • 리뷰 질문 — "이 코드가 두 요청에서 동시에 실행되면?" — 웹 서버에서는 항상 그렇다
  • Therac-25(1985~87)의 방사선 과조사도 경쟁 조건이었다 — 단독 개발, 독립 리뷰 부재
  • 의심 패턴 — 읽고-수정하고-쓰기, 전역 가변 상태, 싱글턴의 지연 초기화

정확성 ④ 리소스 누수와 트랜잭션

# Python: 예외가 나면 close()에 도달하지 못한다
f = open(path)
data = parse(f.read())   # parse가 던지면 파일 핸들 누수
f.close()
with open(path) as f:    # 어떤 경로로 나가도 해제 보장
    data = parse(f.read())
  • 해제 보장 구문 확인 — Python with, Java try-with-resources, JS finally
  • 트랜잭션 경계 — "재고 차감 + 주문 생성"이 따로 커밋되면 장애 시 반쪽 상태가 남는다
  • 리뷰 질문 — "이 두 쓰기 사이에서 프로세스가 죽으면 데이터는 어떤 상태인가?"
Q. 위 Python 예시에서 with 없이도 누수가 안 나게 하려면?

try/finally로 close()를 보장하면 된다. 하지만 리뷰어라면 관용구인 with를 권하는 것이 맞다 — 짧고, 실수할 여지가 없고, 팀 전체가 같은 패턴을 공유하게 된다.

관점 2 설계 — 이 구조로 계속 가도 되는가 🎮

오늘의 diff가 아니라 6개월 뒤의 코드베이스를 상상하며 본다

설계 ① 결합도와 응집도

  • 결합도는 낮게 — 모듈 A의 내부 변경이 B의 수정을 강제하면 결합이 새고 있다
  • 신호: B가 A의 private 사정(필드 순서, 내부 포맷)을 알아야 동작하는 코드
  • 응집도는 높게 — 한 클래스 안의 메서드들이 같은 데이터를 다루는가
  • 신호: 이름이 Utils, Manager, Helper인 클래스는 대개 응집도가 낮다
  • 리뷰에서 보는 법 — "이 기능 하나 바꾸는데 파일을 몇 개나 고쳤나?" (산탄총 수술 냄새)
  • 반대 냄새도 — 한 파일에 변경이 계속 몰리면 그 파일이 너무 많은 책임을 진 것

설계 ② 중복과 DRY의 균형

  • DRY의 본뜻 — "같은 지식"의 중복 제거이지, 우연히 닮은 코드의 통합이 아니다
  • 성급한 추상화 경계 — 두 화면의 검증 로직이 지금 닮았다고 합치면, 요구사항이 갈라질 때 if 지옥이 된다
  • "잘못된 추상화보다 중복이 싸다" — Sandi Metz의 경험칙
  • Rule of Three — 두 번째 중복까지는 관찰, 세 번째가 나타나면 패턴이 보이고 그때 추상화
  • 리뷰 질문 — "이 두 코드는 같은 이유로 바뀌는가?" 그렇다면 합치고, 아니면 둔다

중복 제거의 기준은 닮은 모양이 아니라 같은 변경 이유

설계 ③ 인터페이스·API 설계 — 호출자 관점

// 호출부를 상상하며 읽는다
save(user, true, false, null);          // true? false? 6개월 뒤 아무도 모른다
save(user, { validate: true, notify: false });   // 읽는 순간 의미가 보인다
  • 호출 코드를 먼저 써 본다 — 설계가 좋은지는 정의부가 아니라 사용부에서 드러난다
  • 잘못 쓰기 어렵게 — 불법 상태를 표현할 수 없는 타입, 필수 값은 필수 인자로
  • boolean 인자 2개 이상은 거의 항상 열거형이나 옵션 객체가 낫다
  • 공개 범위 최소화 — 한번 public이 되면 영원히 호환성을 짊어진다

설계 ④ YAGNI — 과잉 설계 경계

  • YAGNI — "You Aren't Gonna Need It", 지금 요구사항에 없는 유연성은 만들지 않는다
  • 과잉 설계 신호 — 구현체가 하나뿐인 인터페이스, 쓰는 곳 없는 설정값, "나중을 위한" 추상 클래스
  • 쓰이지 않는 유연성도 유지보수 대상 — 읽는 사람마다 "이건 왜 있지?"의 비용을 낸다
  • 리뷰 질문 — "이 확장 포인트를 실제로 쓰는 두 번째 사례가 이 PR에 있는가?"
  • 반대 방향과의 균형 — 공개 API·DB 스키마처럼 되돌리기 비싼 결정만은 미리 신중하게
Q. "언젠가 다른 DB로 바꿀 수도 있으니 추상화 계층을 넣자"는 PR, 승인해야 할까?

대개 아니다. YAGNI 위반의 전형으로, 구현체가 하나뿐인 추상화는 코드만 늘린다. 단, DB 접근이 코드 전체에 흩어지는 것을 막는 얇은 저장소(repository) 계층 정도는 결합도 관점에서 정당화될 수 있다 — 근거가 "언젠가"가 아니라 "지금의 응집"이면 된다.

관점 3 가독성 — 6개월 뒤의 내가 읽을 수 있는가 🎮

코드는 한 번 쓰이고 수십 번 읽힌다 — 읽는 비용을 리뷰에서 낮춘다

가독성 ① 네이밍

❌ 이렇게 말고

def proc(d, f):
    tmp = []
    for x in d:
        if x.s and x.t > f:
            tmp.append(x)
    return tmp

✅ 이렇게

def filter_active_users(
        users, joined_after):
    return [u for u in users
            if u.is_active
            and u.joined_at > joined_after]
  • 이름은 문서다 — 좋은 이름은 주석 세 줄을 대체한다
  • 리뷰 요령 — 이름을 가리고 본문만 읽어 역할을 맞출 수 없다면 이름 탓이 아니라 함수 탓일 수도

가독성 ② 함수 길이와 중첩 깊이

  • 화면 한 번의 원칙 — 스크롤해야 다 보이는 함수는 머릿속에서도 한 번에 안 잡힌다
  • 중첩 3단 초과 주의 — if 안의 for 안의 if 안의 try는 모든 조합을 추적해야 읽힌다
  • 얼리 리턴 — 사전 조건 검사를 함수 앞에서 끝내면 본론의 들여쓰기가 평평해진다
  • if (!valid) return; 를 먼저 — 정상 경로가 왼쪽 벽을 따라 곧게 내려간다
  • 추출은 이름을 얻는 행위 — 긴 함수의 블록을 추출하면 그 블록에 이름이 생긴다
  • NASA JPL Power of Ten도 함수를 한 페이지 이내로 제한한다 — 검증 가능성 때문

가독성 ③ 주석 — 무엇이 아니라 왜

❌ 코드 번역 주석

i += 1  # i를 1 증가시킨다
retry = 3  # 재시도 3회

✅ 이유를 남기는 주석

# 결제 게이트웨이가 간헐적으로 502를
# 반환함 (2025-11 장애 보고서 #217).
# 3회 재시도로 성공률 99.9% 확보.
retry = 3
  • 코드가 못 담는 것만 주석으로 — 배경, 트레이드오프, 버그 회피, 외부 제약
  • "무엇" 주석이 필요해 보이면 코드를 고칠 신호 — 주석 대신 이름과 구조를 개선

가독성 ④ 매직 넘버와 상수화

if (file.size > 10485760) reject();     // 이 숫자는 무엇인가
setTimeout(retry, 86400000);            // 하루? 계산해 봐야 안다
const MAX_UPLOAD_BYTES = 10 * 1024 * 1024;   // 10 MiB
const RETRY_INTERVAL_MS = 24 * 60 * 60 * 1000;
if (file.size > MAX_UPLOAD_BYTES) reject();
  • 이름 + 단위 + 유도식 — 10 * 1024 * 1024는 계산 결과보다 의도를 보존한다
  • 한 곳에서 관리 — 같은 값이 두 파일에 리터럴로 있으면 언젠가 한쪽만 바뀐다
  • Mars Climate Orbiter(1999)는 단위(lbf·s vs N·s) 불일치로 소실됐다 — 단위는 이름에 담아라

관점 4 테스트 — 이 테스트를 믿어도 되는가 🎮

테스트 코드도 리뷰 대상이다 — 초록불이 거짓말일 수 있다

테스트 ① 요구사항을 검증하는가

  • 이슈와 대조 — "3회 실패 시 계정 잠금"이 요구인데 테스트는 1회 실패만 다룬다면 미완성
  • 구현 종속 테스트 경계 — 내부 함수 호출 순서를 검증하는 테스트는 리팩터링마다 깨진다
  • mock의 verify(호출횟수) 남용이 대표 신호 — 행동이 아니라 결과를 검증하라
  • 리뷰 요령 — 테스트 이름을 요구사항 문장으로 읽어본다, 안 읽히면 무엇을 검증하는지 불명
  • 좋은 예 — test_잠금된_계정은_올바른_비밀번호로도_로그인_불가()

테스트 ② 경계·예외 케이스 커버

  • 해피 패스만 있는 테스트 — 커버리지 숫자는 높아도 버그가 사는 곳은 못 지킨다
  • 경계 목록 대조 — 0개, 1개, 최대치, 최대치+1, 중복, 정렬 안 된 입력, 유니코드
  • 예외 경로 — 외부 API 타임아웃, DB 커넥션 실패, 디스크 풀 — 실패 주입 테스트가 있는가
  • Ariane 5(1996)를 떨어뜨린 것도 "실제 비행 범위 밖" 값의 64비트→16비트 변환 오버플로였다
  • 리뷰 질문 — "이 diff에서 가장 무서운 입력은 무엇인가? 그 입력의 테스트가 있는가?"

테스트 ③ 가짜 테스트 감별법

# 유형 1: assert가 없다 - 실행만 되면 초록불
def test_discount():
    calc_discount(100, 0.1)          # 아무것도 검증 안 함

# 유형 2: 구현 복제 - 구현이 틀리면 테스트도 같이 틀린다
def test_discount2():
    assert calc_discount(100, 0.1) == 100 * (1 - 0.1)

def test_discount3():
    assert calc_discount(100, 0.1) == 90   # 기대값을 독립적으로 명시
  • 돌연변이 사고 실험 — "구현에 버그를 심으면 이 테스트가 빨간불이 되나?" 아니면 가짜다

테스트 ④ 테스트 가독성도 리뷰 대상

  • 테스트는 명세서 — 새 팀원이 기능을 이해하는 첫 문서가 테스트다, 본 코드만큼 읽기 쉬워야 한다
  • Given-When-Then 구조 — 준비·실행·검증 세 덩어리가 눈에 보이게 배치한다
  • 픽스처 과잉 경계 — 5단 상속의 setUp을 따라가야 이해되는 테스트는 명세 역할을 잃는다
  • 테스트 안에서 값이 보이게 — createUser()보다 createUser(age=17)이 의도를 드러낸다
  • 실패 메시지 확인 — 깨졌을 때 "expected 90 got 100"만으로 원인을 짚을 수 있는가

관점 5 보안 — 악의적 입력을 상상하라 🎮

보안 ① 입력 검증과 인젝션

// JS: 문자열 연결 = 인젝션 초대장
db.query(`SELECT * FROM users WHERE name = '${name}'`);
// name = "' OR '1'='1" 이면 전체 테이블이 반환된다
db.query('SELECT * FROM users WHERE name = ?', [name]);
  • 연결 지점을 전부 본다 — SQL, 셸 명령, 파일 경로(../), HTML(XSS) 모두 같은 원리
  • 파라미터화가 기본 — "이스케이프 함수를 잘 쓰면"이 아니라 구조적으로 섞이지 않게
  • Heartbleed(2014)는 입력 길이 값을 검증 없이 믿은 경계 검사 누락이었다 — 입력은 항상 적대적이라 가정

보안 ② 시크릿과 로그 유출

  • diff에서 시크릿 탐지 — API 키, 비밀번호, 토큰 리터럴이 커밋에 들어오면 즉시 차단
  • 한 번 푸시된 시크릿은 히스토리에 영원히 남는다 — 삭제 커밋이 아니라 키 폐기가 정답
  • 로그 내용 검토 — logger.info("login " + user.toJson())에 비밀번호 해시·주민번호가 섞이는가
  • 에러 메시지 노출 — 스택 트레이스·SQL 문이 사용자 화면까지 흘러나오지 않는가
  • 도구와 병행 — pre-commit 시크릿 스캐너를 걸되, 리뷰어도 설정 파일 diff를 의심한다

보안 ③ 권한과 인증 확인

  • 새 엔드포인트마다 묻는다 — "로그인 없이 호출하면? 남의 리소스 ID를 넣으면?"
  • IDOR가 최다 빈출 — GET /orders/1234에서 1235로 바꿔 남의 주문이 보이는 실수
  • 리뷰 확인점 — 조회 쿼리에 WHERE user_id = 현재사용자 조건이 있는가
  • 프런트 검증은 장식 — 버튼 숨김은 UX이고, 권한 검사는 반드시 서버에서 반복한다
  • 기본값은 거부 — 권한 목록에 없으면 허용이 아니라 거부가 기본이 되게 설계됐는가

보안 ④ 의존성 취약점

  • 새 패키지 추가는 코드 추가 — package.json 한 줄 diff 뒤에 수만 줄이 들어온다
  • 리뷰 질문 — 유지보수되는가, 다운로드·기여자 규모는, 표준 라이브러리로 충분하지 않은가
  • 이름 오타 공격 — 유명 패키지와 한 글자 다른 악성 패키지(typosquatting) — 철자를 확인한다
  • LLM이 존재하지 않는 패키지명을 지어내는 것을 노린 slopsquatting도 등장 — 출처 불명 이름은 검색부터
  • 자동화 병행 — Dependabot·audit 도구로 알려진 CVE를 걸러도, "왜 이 패키지인가"는 사람이 묻는다
Q. lodash와 한 글자 다른 "lodahs"를 추가하는 diff를 봤다. 어떻게 하나?

즉시 Request changes. typosquatting 악성 패키지의 전형적 패턴으로, 설치 스크립트만으로 시크릿 탈취가 가능하다. 패키지명은 공식 저장소에서 철자·게시자·다운로드 수를 확인하고, 이미 설치·실행됐다면 해당 환경의 자격 증명 회전까지 검토한다.

관점 6 성능 — 측정 가능한 문제인가 🎮

성능 리뷰의 절반은 "느린 코드 찾기"가 아니라 "느려질 구조 찾기"다

성능 ① N+1 쿼리와 루프 내 IO

# Python: 주문 1,000건이면 쿼리 1,001번
orders = db.get_orders(since=today)
for o in orders:
    o.user = db.get_user(o.user_id)      # 루프마다 왕복
orders = db.get_orders(since=today)
users = db.get_users([o.user_id for o in orders])  # 일괄 1번
for o in orders: o.user = users[o.user_id]
  • ORM의 함정 — order.user.name 한 줄이 지연 로딩 쿼리일 수 있다, 발행 쿼리 로그로 확인
  • 개발 DB의 10건에서는 안 보인다 — "운영의 1만 건이면?"을 리뷰에서 물어야 한다

성능 ② 자료구조 선택

작업list/배열set/dict·Map

순서 유지기본 보장구조에 따라 다름
if user_id in banned_list:   # 리스트 10만 건 x 요청마다 순회
if user_id in banned_set:    # set 멤버십은 평균 O(1)
  • 이중 루프 안의 in 리스트는 조용한 O(n²) — diff에서 가장 자주 잡히는 성능 패턴

성능 ③ 조기 최적화 경계

시기상조의 최적화는 모든 악의 뿌리다 — Donald Knuth (1974)
  • 가독성을 깨는 최적화는 근거를 요구 — "빨라질 것 같아서"는 근거가 아니다, 프로파일과 수치로
  • 구조적 문제와 미시 최적화 구분 — N+1·잘못된 자료구조는 지금 고치고, 비트 트릭은 측정 후에
  • Knuth 인용의 뒷부분도 기억 — "결정적인 3%의 기회를 놓쳐서는 안 된다"
  • 리뷰 질문 — "이 복잡한 코드가 지키는 성능 예산이 무엇인가? 측정값이 PR 설명에 있는가?"

안전 필수 소프트웨어의 체크리스트 문화

심리적 안전감과 리뷰

  • 구글 아리스토텔레스 프로젝트 — 180여 개 팀을 분석한 결과, 고성과 팀의 1위 요인은 능력이 아니라 심리적 안전감이었다
  • "어리석어 보일 위험을 감수하고 질문·실수할 수 있다는 믿음"
  • 리뷰에 적용하면 — 안전감이 낮은 팀은 지적을 피하려고 리뷰가 형식화되고, "LGTM 도장 찍기"가 만연한다
  • 안전감이 높은 팀 — 주니어도 시니어 코드에 질문하고, 결함이 숨지 않고 드러난다
팀에서 누가 일하느냐보다, 팀이 어떻게 상호작용하느냐가 성과를 갈랐다 — 구글 re:Work, 아리스토텔레스 프로젝트

코멘트 기본 공식: 관찰 + 영향 + 제안

❌ 이렇게 말고

"이거 왜 이렇게 짰어요? 느려질 텐데요."

✅ 이렇게

"[관찰] 루프 안에서 매번 DB를 조회하고 있어요. [영향] 주문이 1,000건이면 쿼리도 1,000번 나갑니다. [제안] 루프 밖에서 한 번에 조회해 dict로 캐싱하면 어떨까요?"

  • 관찰 — 판단 없이 사실만: "~하고 있다"
  • 영향 — 왜 문제인지 근거: 성능·버그·유지보수
  • 제안 — 대안 또는 열린 질문으로 마무리

"나"를 주어로, 코드를 목적어로

  • 비난의 문법 — "당신은 검증을 빼먹었다"는 사람을 겨눈다. 방어 반응이 먼저 나온다
  • 관찰의 문법 — "이 코드는 null 검증이 없다"는 코드를 겨눈다. 같은 사실, 다른 온도
  • I-메시지 — "저는 이 부분이 헷갈렸어요"는 반박 불가능한 사실이라 갈등이 생기지 않는다
  • 읽는 사람이 헷갈렸다는 것 자체가 개선 근거가 된다

"당신은" 대신 "이 코드는", 그리고 "저는"

질문의 힘과 위험

❌ 추궁형 질문

"여기서 트랜잭션 안 쓴 이유가 뭐죠?"

답을 정해 놓고 몰아세우는 수사식 질문 — 질문의 탈을 쓴 비난

✅ 호기심형 질문

"두 테이블을 따로 업데이트하는데, 중간에 실패하면 어떻게 되나요? 트랜잭션이 필요한 경우인지 궁금합니다."

시나리오를 제시하고 진짜로 답을 듣고 싶은 질문

  • 질문의 힘 — 명령보다 저항이 적고, 작성자의 맥락을 끌어낸다
  • 질문의 위험 — 답을 정해 둔 질문은 오히려 더 공격적으로 읽힌다

Conventional Comments — 라벨로 의도를 표시한다

코멘트 앞에 라벨을 붙여 "이게 얼마나 중요한 말인지"를 명시하는 표준 표기법

라벨의미차단 여부
praise:잘한 점을 구체적으로 칭찬아니오
nitpick:사소한 취향·스타일, 무시해도 됨아니오
suggestion:개선 제안, 채택은 작성자 판단보통 아니오
issue:실제 문제, 해결돼야 승인 가능예
question:이해를 위한 순수 질문답변 필요
  • 예: suggestion (non-blocking): 이 함수를 둘로 나누면 테스트가 쉬워질 것 같아요

🎮 코멘트 톤 변환기 — 같은 지적, 다른 온도

  • 나쁜 코멘트를 좋은 코멘트로 바꿔 보며 5장의 원칙을 몸에 익히자 (예문 5개)

칭찬도 리뷰다

  • 리뷰 = 지적, 이라는 착각 — 좋은 패턴을 발견하고 언급하는 것도 리뷰의 산출물이다
  • praise의 세 가지 효과 — 좋은 패턴이 팀에 전파되고, 작성자가 다음에도 반복하며, 지적 코멘트의 수용성이 올라간다
  • 구체적으로 — "좋네요 👍" 보다 "에러 케이스마다 테스트를 붙인 게 좋습니다. 다음에 이 코드를 고칠 사람이 안심하겠어요"
  • 칭찬만 있는 리뷰 라운드도 정상이다 — 억지로 지적을 만들 필요 없다

praise: 도 issue: 만큼 팀을 바꾼다

텍스트의 온도 — 이모지와 완곡어

  • 텍스트는 차갑게 읽힌다 — 같은 문장도 얼굴·억양 없이 읽으면 실제 의도보다 부정적으로 해석된다
  • 완곡어의 역할 — "~하면 어떨까요", "~일 수도 있겠네요"는 우유부단함이 아니라 온도 조절 장치다
  • 이모지 한 개의 값어치 — "여기 버그 같아요 🙂"와 "여기 버그 같아요."는 다르게 읽힌다
  • 절대 금지: 비꼼 — "설마 이걸 테스트 없이 머지하려던 건 아니죠?"류는 어떤 완곡어로도 복구되지 않는다
  • 반어법·과장·유머는 텍스트에서 절반 이상 오독된다

리누스 토발즈의 2018년 사과

  • 수십 년의 독설 리뷰 — 커널 메일링리스트에서 토발즈의 인신공격성 코드 비판은 악명이 높았다
  • 2018년 9월 — "내 행동이 사람들에게 상처를 주고 커뮤니티에서 밀어냈다"며 공개 사과하고 자진 휴식에 들어갔다
  • 결과 — 리눅스 커널 커뮤니티가 행동 강령(Code of Conduct)을 채택했다
  • 세계 최고의 기술 권위자도 커뮤니케이션 방식은 바꿔야 했다

갈등이 생겼을 때 — 3회 왕복 규칙

  • 신호를 읽어라 — 같은 스레드에서 글이 3회 왕복해도 결론이 안 나면 텍스트로는 해결되지 않는 문제다
  • 채널을 바꿔라 — 통화나 대면 10분이 코멘트 20개보다 빠르고, 목소리에는 텍스트에 없는 온도가 있다
  • 결과는 기록하라 — 통화로 합의한 내용을 PR에 한 줄 요약으로 남겨야 나중에 온 사람도 맥락을 안다
  • "오프라인에서 논의 후: X 방식으로 하기로 함. 이유는 ~" 형태면 충분하다

글 3회 왕복이면 통화로 전환한다

취향 싸움을 근거 싸움으로 바꾸는 우선순위

  • 1순위: 데이터 — 벤치마크, 프로파일, 장애 이력. 측정할 수 있으면 측정한다
  • 2순위: 선례 — 코드베이스의 기존 패턴, 과거 결정 기록(ADR)
  • 3순위: 컨벤션 — 팀 스타일 가이드, 언어 공식 가이드
  • 4순위: 취향 — 여기까지 왔으면 작성자의 선택을 존중하는 것이 구글 eng-practices의 원칙이다
  • 에스컬레이션 — 그래도 안 풀리면 제3자(테크리드·아키텍트)에게 결정을 위임하고 결과에 승복한다
  • "완벽한 코드"가 아니라 "코드베이스를 개선하는 코드"면 승인하라 — 구글 리뷰 가이드

리뷰 받는 기술 ① 방어 본능 다루기

  • 코드는 내가 아니다 — 코멘트 30개는 내 인격에 대한 평가가 아니라 코드 스냅샷에 대한 관찰이다
  • 방어 본능은 정상 — 몇 시간을 들인 결과물에 대한 지적에 심박이 오르는 것은 자연스럽다. 문제는 그 상태로 답장하는 것이다
  • 10분 규칙 — 감정이 올라오면 답장을 10분 미룬다. "지적 = 공짜 디버깅"으로 재해석되는 데 걸리는 시간이다
  • 와인버그: "자아를 코드에서 분리한 프로그래머가 더 빨리 성장한다"

리뷰어는 내 코드의 적이 아니라 내 버그의 적이다

리뷰 받는 기술 ② 모든 코멘트에 응답한다

  • 무응답 수정 금지 — 코멘트 없이 커밋만 올리면 리뷰어는 무엇이 반영됐는지 diff를 다시 뒤져야 한다
  • 응답은 세 갈래뿐 — 어느 쪽인지 명시한다
  • 수용: "반영했습니다 (커밋 abc123)"
  • 반론: "이 경우엔 X라서 유지하고 싶습니다. 근거는 ~"
  • 보류: "동의하는데 이 PR 범위를 넘어서 이슈로 분리했습니다 (#456)"
  • 반론은 권리다 — 리뷰어 코멘트는 명령이 아니다. 다만 침묵하는 불복종이 아니라 근거 있는 반론이어야 한다

리뷰 받는 기술 ③ 감사와 후속 학습

  • 감사는 구체적으로 — "그 경계 조건은 저 혼자였으면 못 찾았을 거예요"는 리뷰어가 다음에도 깊게 봐줄 이유가 된다
  • 패턴 노트 — 반복해서 받는 지적(네이밍, 에러 처리, 테스트 누락)을 개인 체크리스트로 만들어 PR 올리기 전에 스스로 돈다
  • 같은 지적을 두 번 받지 않기 — 리뷰의 진짜 산출물은 고쳐진 코드가 아니라 성장한 작성자다
  • 셀프 리뷰 단계에서 자기 체크리스트를 돌리면 리뷰 왕복이 눈에 띄게 줄어든다

시차·리모트 팀의 비동기 리뷰 에티켓

  • 왕복 1회 = 하루 — 시차 9시간이면 "이게 뭐죠?" 한 줄이 24시간을 태운다. 코멘트 하나에 맥락·근거·제안을 다 담아라
  • 일괄 제출 — 코멘트를 하나씩 흘리지 말고 리뷰를 끝낸 뒤 한 번에 제출한다
  • PR 설명이 절반 — 배경·의도·스크린샷을 미리 쓰면 질문 왕복 자체가 줄어든다
  • 구글 가이드의 응답 SLA: 리뷰 요청에는 1영업일 안에 반응한다

주니어가 시니어 코드를 리뷰할 때

  • 질문도 기여다 — "이 부분이 이해가 안 됩니다"는 무지의 고백이 아니라 가독성 데이터다. 주니어가 못 읽는 코드는 6개월 뒤의 모두가 못 읽는다
  • question: 라벨을 적극 활용 — 지적할 자신이 없으면 순수 질문으로 시작해도 충분하다
  • 권위 역전은 없다 — 구글·Microsoft 모두 직급과 무관하게 리뷰 권한을 준다. 시니어 코드에서도 결함은 나온다
  • 시니어의 의무 — 주니어의 지적을 반갑게 받는 모습 자체가 팀의 심리적 안전감을 만든다
  • "이 질문 덕에 주석을 추가했다"는 답이 나오면 그 리뷰는 성공이다

침묵 리뷰의 해악

  • 고스팅 — 리뷰 요청을 받고 며칠간 무반응. 작성자는 브랜치가 썩어가는 것을 지켜보며 컨텍스트를 잃는다
  • 탬포닝(작은 지적 하나씩 흘리기) — 하루에 nitpick 하나씩 던져 리뷰가 2주짜리 고문이 되는 패턴. 한 번에 전체를 보고 일괄 제출하라
  • "바쁘면 바쁘다고" — 지금 못 보면 "목요일에 보겠다" 또는 다른 리뷰어를 지정한다. 침묵이 최악이다
  • SLA 재확인 — 첫 반응 1영업일, 리뷰 세션은 60분 이내(SmartBear: 60~90분 이후 발견율 급락), 한 번에 400 LOC 이하

느린 리뷰보다 나쁜 것은 침묵하는 리뷰다

Q. "이 함수 이름 진짜 별로네요. 다시 지으세요."를 관찰+영향+제안 공식으로 고쳐 쓰면?

예시: "[관찰] process_data라는 이름은 이 함수가 주문을 검증하고 저장까지 한다는 것을 드러내지 못합니다. [영향] 호출하는 쪽에서 저장 부수효과를 예상하기 어렵습니다. [제안] validate_and_save_order는 어떨까요? 아니면 검증과 저장을 분리할 수도 있겠습니다." — 판단("별로")을 사실(이름이 동작을 못 담는다)로 바꾸고, 명령을 제안으로 바꾸는 것이 핵심이다.

Q. 코멘트 스레드가 4번째 왕복에 접어들었다. 다음 행동은?

3회 왕복 규칙에 따라 텍스트를 중단하고 통화나 대면 대화로 전환한다. 합의 후 결과를 PR에 한 줄로 기록한다. 그래도 합의가 안 되면 데이터, 선례, 컨벤션 순으로 근거를 찾고, 마지막에는 제3자에게 에스컬레이션한다.

5장 요약

  • 리뷰는 사회적 행위 — 읽는 것은 컴파일러가 아니라 사람이다
  • 심리적 안전감 — 구글 아리스토텔레스 프로젝트가 밝힌 고성과 팀의 1위 조건
  • 코멘트 공식 — 관찰 + 영향 + 제안, 주어는 "이 코드"와 "나"
  • Conventional Comments — praise/nitpick/suggestion/issue/question으로 의도를 라벨링
  • 갈등 관리 — 3회 왕복이면 통화, 데이터 > 선례 > 컨벤션 > 취향
  • 리뷰 받기 — 코드는 내가 아니다, 모든 코멘트에 응답, 같은 지적 두 번 받지 않기
  • 침묵 금지 — 첫 반응 1영업일, 일괄 제출, 고스팅·탬포닝 금지

딥블루 — '기계가 사람을 이기는 날'

  • 1997년 — 딥블루가 세계 챔피언 카스파로프를 정식 대국에서 이겼다. "기계가 사람을 이기는 날"이 상징적으로 도래한 순간
  • 그러나 딥블루는 탐색 기계 — 초당 2억 수를 계산하는 전용 하드웨어였지, 체스를 "이해"하지 않았다
  • 오늘의 LLM 논쟁과 같은 구조 — 성능과 이해는 별개의 질문이다
  • 교훈 — 기계가 잘하는 영역에서도, 기계가 무엇을 못 하는지 아는 사람이 필요하다

LLM의 원리 한 장 요약: 다음 토큰 예측

  • 학습 — 방대한 텍스트·코드에서 "이 문맥 다음에 어떤 토큰이 올 확률이 높은가"를 배운다
  • 생성 — 확률이 높은 다음 토큰을 하나씩 이어 붙인다. 코드 생성도 본질은 같다
  • 따라서 — "그럴듯함"이 최적화 목표이지 "정확함"이 목표가 아니다

LLM은 정답 기계가 아니라 개연성 기계다

트랜스포머와 컨텍스트 창

  • 어텐션 — 입력의 모든 토큰 쌍 사이 관련성을 계산해, 멀리 떨어진 문맥도 참조한다
  • 컨텍스트 창 — 모델이 한 번에 볼 수 있는 토큰 수의 상한. 창 밖의 코드는 존재하지 않는 것과 같다
  • 거대한 코드베이스 전체를 넣을 수 없으니, AI는 늘 부분 정보로 코드를 쓴다
  • 리뷰 시사점 — AI가 "못 본" 파일과의 정합성은 사람이 확인해야 하는 몫이다

'이해'가 아니라 '패턴'

  • 사람의 코드 — 의도가 먼저 있고, 코드는 의도의 번역이다. 이상한 부분에는 대개 이유가 있다
  • AI의 코드 — 훈련 데이터에서 본 패턴의 통계적 합성이다. 이상한 부분에 이유가 없을 수 있다
  • 리뷰 질문이 달라진다 — 사람 코드엔 "왜 이렇게 했나요?"가 통하지만, AI 코드엔 물어볼 의도 자체가 없다
  • "작성자에게 의도를 묻는다"는 리뷰의 기본 수단 하나가 사라지는 것이다
AI 코드는 그럴듯해 보이는 것과 맞는 것의 간극을 사람이 메워야 하는 코드다 — 이 간극이 이 장의 주제다

2025, vibe coding의 시대

  • vibe coding — 안드레이 카르파티가 2025년에 명명한 방식: 프롬프트로 코드를 받아 "돌아가면 넘어가는" 개발. 코드를 거의 읽지 않는다
  • GitHub Copilot 연구(2023) — Copilot이 켜진 파일에서 작성 코드의 약 46%가 AI 제안으로 채워졌다
  • 추세 — 신규 코드에서 AI 산출 비중은 계속 커지고 있다. "AI 코드 리뷰"는 특수 상황이 아니라 기본 상황이 됐다
  • 작성 속도는 몇 배가 됐는데 검증 속도는 그대로 — 병목이 리뷰로 이동했다

코드의 절반이 AI라면, 리뷰의 절반도 새로 배워야 한다

AI 코드의 강점 — 먼저 인정할 것

  • 상용구(boilerplate) — CRUD, 직렬화, 설정 파일 등 정형 코드는 사람보다 빠르고 오타도 적다
  • 관례 지식 — 유명 라이브러리의 표준 사용법, 널리 쓰이는 디자인 패턴을 즉시 재현한다
  • 속도 — 초안 작성 시간이 분 단위로 줄어든다. 빈 파일 공포가 사라진다
  • 다국어 — 낯선 언어·프레임워크에서도 문법적으로 온전한 코드를 낸다
  • 강점을 인정해야 실패양식이 정확히 보인다 — 문제는 "틀리는 방식"이 사람과 다르다는 것

실패양식 ① 환각 API

존재하지 않는 함수·메서드·패키지를 자신 있게 호출한다

# AI가 생성한 코드 — 그럴듯하지만…
import pandas as pd

df = pd.read_csv("data.csv")
df.remove_duplicates(keep="first")   # AttributeError!
df.drop_duplicates(keep="first")     # 실제 API
  • 왜 생기나 — "그럴듯한 이름"을 예측하기 때문. remove_duplicates는 확률적으로 자연스러운 이름이다
  • 리뷰 대응 — 낯선 API 호출은 문서·자동완성으로 실존 여부부터 확인한다

실패양식 ② 패키지 환각과 slopsquatting

  • 패키지 환각 — LLM이 존재하지 않는 패키지명을 반복적으로 지어낸다는 연구가 여럿 있다. 같은 프롬프트에서 같은 가짜 이름이 재현되기도 한다
  • slopsquatting 공격 — 공격자가 AI가 자주 지어내는 이름을 미리 조사해, 그 이름으로 악성 패키지를 실제 등록해 둔다
  • 시나리오 — 개발자가 AI 코드의 pip install을 그대로 실행 → 악성 코드 설치 완료
  • 리뷰 대응 — 의존성 추가는 저장소(PyPI/npm)에서 다운로드 수·관리 이력·저자를 직접 확인한 뒤 통과시킨다

AI가 추천한 패키지명은 검증 전까지 미확인 물체다

실패양식 ③ 요구사항 오해

  • 증상 — 요청과 비슷하지만 다른, 그럴듯한 다른 문제를 완벽하게 풀어낸다
  • "마지막 로그인 후 30일 지난 계정 비활성화"를 요청했는데 "가입 후 30일 지난 계정"을 비활성화하는 코드가 나오는 식
  • 위험한 이유 — 코드 자체는 깔끔하고 테스트도 통과해서, 대충 읽으면 맞아 보인다
  • 리뷰 대응 — 코드 품질보다 먼저 "이 코드가 푸는 문제가 요구사항과 같은 문제인가"를 문장으로 대조한다
  • 사람 리뷰에서 배운 "의도 확인"이 AI 코드에서는 첫 번째 관문이 된다

실패양식 ④ 과잉 일반화와 불필요한 방어 코드

// 내부 전용 헬퍼에 AI가 붙인 방어 코드
function formatPrice(price) {
  if (price === null || price === undefined) return "0";
  if (typeof price === "string") price = parseFloat(price);
  if (isNaN(price)) return "0";
  if (price < 0) price = Math.abs(price);  // 음수를 조용히 뒤집는다?!
  return price.toFixed(2);
}
  • 문제 — 호출부가 항상 number를 주는데도 모든 타입을 방어하고, 심지어 오류(음수 가격)를 조용히 삼킨다
  • 리뷰 대응 — 방어 코드가 실제 호출 맥락에 필요한지, 오류를 숨기고 있지는 않은지 본다

실패양식 ⑤ 오래된 관례 재생산

  • 원인 — 훈련 데이터에는 수년 전 코드가 압도적으로 많다. 모델은 데이터가 많은 쪽, 즉 과거의 관례를 재생산한다
  • 예: 이미 deprecated된 API 사용, 구버전 문법, 새 표준 라이브러리 대신 옛 서드파티 사용
  • 훈련 시점 문제 — 모델의 지식은 훈련 데이터 마감 시점에 멈춰 있다. 그 이후의 릴리스·보안 권고를 모른다
  • 리뷰 대응 — "요즘도 이렇게 쓰나?"를 습관적으로 묻고, deprecation 경고를 CI에서 에러로 승격한다

실패양식 ⑥ 보안 취약 패턴 재현

  • 원리적 문제 — 훈련 데이터의 공개 코드에는 취약한 코드가 대량 포함돼 있고, 모델은 그 패턴도 함께 배운다
  • 연구 결과 — AI 어시스턴트 생성 코드에서 상당 비율의 보안 취약점이 발견된다는 연구가 반복 보고됐다(SQL 인젝션, 하드코딩된 비밀키, 약한 해시 등)
  • 자동화 편향까지 겹치면 — "AI가 짰으니 표준적이겠지"라는 신뢰가 검증을 건너뛰게 만든다
  • 리뷰 대응 — 입력 검증·인증·암호화 관련 AI 코드는 무조건 정밀 리뷰 대상으로 분류하고, SAST 도구를 병행한다

실패양식 ⑦ 맥락 부족 — 컨벤션 무시

  • 증상 — 팀의 에러 처리 규약, 로깅 유틸, 공통 헬퍼가 있는데도 AI는 자기 방식으로 새로 만든다
  • 이미 있는 date_utils.format_kst()를 두고 슬라이드마다 다른 수제 날짜 포맷팅이 생기는 식
  • 원인 — 컨텍스트 창의 한계. 코드베이스 전체와 팀의 암묵지가 프롬프트에 들어가지 않았다
  • 결과 — 한 저장소 안에 사투리가 늘어나고, 일관성이라는 유지보수 자산이 침식된다
  • 리뷰 대응 — "이 기능, 우리 코드베이스에 이미 있지 않나?"가 AI 코드 전용 체크 항목이 된다

실패양식 ⑧ 자신감 있는 오답

  • 사람의 불확실성 신호 — "이 부분은 자신 없는데…", "임시로 해뒀어요", TODO 주석. 리뷰어는 이 신호로 정밀 조사 지점을 고른다
  • AI에는 그 신호가 없다 — 맞는 코드와 틀린 코드를 같은 확신의 문체로 낸다. 설명을 요구해도 유창한 (때로 틀린) 근거를 붙인다
  • 리뷰 시사점 — "확신 있어 보이는 정도"를 품질 신호로 쓰던 습관이 AI 코드에서는 무효가 된다
  • 모든 부분을 같은 의심 수준으로 봐야 한다는 뜻 — 그래서 체계적 체크리스트가 더 중요해진다

  • AI 주석 — 무엇(what)을 코드 그대로 반복하고, 모든 함수에 균일한 형식의 독스트링이 붙는다

AI 코드 감별 단서 ② 부자연스러운 균일함

  • 사람 코드의 지문 — 급했던 부분과 공들인 부분의 편차, 개인 취향의 네이밍, 오래된 코드와 새 코드의 결
  • AI 코드의 균일함 — 처음부터 끝까지 같은 밀도, 같은 문체, 교과서적 네이밍. 그 자체는 장점처럼 보인다
  • 왜 단서인가 — 균일하게 매끈한 코드 안에 실패양식 ①~⑧이 섞여 있어도 표면상 이질감이 없다. 매끄러움이 결함을 은폐한다
  • 감별의 목적은 차별이 아니라 리뷰 모드 전환이다 — AI 코드로 판단되면 의도 질문 대신 검증 중심 리뷰로 바꾼다

대원칙 — 머지하는 사람이 저자다

  • 책임은 이동하지 않는다 — AI가 코드를 생성해도 커밋·머지 버튼을 누른 사람이 법적·기술적 저자다
  • "AI가 짰어요"는 면책 사유가 아니다 — 장애 회고에서 이 말은 "리뷰 없이 머지했어요"와 동의어
  • Google eng-practices의 기준은 여기도 그대로 적용된다: 코드베이스의 전반적 품질을 개선한다고 확신할 때만 승인한다
  • 따라서 이 장의 모든 기법은 한 문장으로 요약된다 — 신뢰하되, 검증하라(trust, but verify)

머지한 순간, 그 코드는 내 코드다

AI 코드 리뷰가 사람 코드 리뷰와 다른 3가지

  • ① 의도 부재 — 저자에게 "왜 이렇게 짰나요?"를 물을 수 없다. 통계적으로 그럴듯한 패턴이 있을 뿐, 설계 의도가 없다
  • ② 대량 생산 — 생성 속도가 리뷰 속도를 압도한다. GitHub 연구(2023)에서 Copilot 활성 파일의 약 46%가 AI 작성 코드였다
  • ③ 그럴듯함 — 변수명·주석·구조가 깔끔해서 틀린 코드도 맞아 보인다. 사람의 실수와 달리 오류가 "지저분해 보이지" 않는다
  • 사람 리뷰의 단서(서투른 네이밍 = 이해 부족 신호)가 AI 코드에서는 작동하지 않는다

리뷰 시작점이 다르다 — 코드가 아니라 요구사항부터

  • 사람 코드 리뷰 — 저자가 요구사항을 이해했다고 가정하고 구현의 품질을 본다
  • AI 코드 리뷰 — 그 가정이 없다. 첫 질문은 "이 코드가 좋은가?"가 아니라 "이 코드가 시킨 일을 하는가?"
  • 순서를 뒤집어라 — 요구사항을 먼저 다시 읽고, 그 다음에 diff를 연다
  • AI는 모호한 요구를 자의적으로 해석해 "가장 흔한 정답"을 내놓는다 — 우리 도메인의 정답과 다를 수 있다
  • 엣지 케이스·에러 정책·성능 요구처럼 프롬프트에 없던 조건은 대부분 구현에도 없다

프롬프트를 리뷰하라 — 무엇을 시켰는지가 스펙이다

  • 프롬프트 = 사실상의 요구사항 명세 — 프롬프트가 틀리면 완벽한 구현도 틀린 코드다
  • PR에 프롬프트를 첨부시켜라 — 리뷰어가 "무엇을 시켰는지"를 알아야 "무엇이 빠졌는지"를 판단할 수 있다
  • 프롬프트에서 확인할 것
    • 제약 조건을 명시했나 (버전, 프레임워크, 에러 정책)
    • 금지 사항을 명시했나 (새 의존성 추가 금지 등)
    • 엣지 케이스를 열거했나 (빈 입력, 동시성, 타임존)
쓰레기를 넣으면 쓰레기가 나온다 — garbage in, garbage out. 프롬프트 리뷰는 입력단의 코드 리뷰다.

  • 불일치가 최악이다 — 테스트까지 잘못된 기준으로 통과하므로 CI가 잡지 못한다
  • 표는 5분이면 만든다. AI 코드 리뷰에서 가성비가 가장 높은 5분이다

검증 ① 모든 API의 실재 확인

  • LLM은 존재하지 않는 메서드를 자신 있게 쓴다 — 여러 라이브러리의 패턴이 섞여 "있을 법한" API가 합성된다
import pandas as pd

df = pd.read_csv("sales.csv")
df.smart_fillna(strategy="auto")  # 환각: pandas에 이런 메서드 없음
df.fillna(df.mean(numeric_only=True))  # 실재하는 API로 교체
  • 3중 확인 — 공식 문서 검색 → IDE 자동완성으로 존재 확인 → 컴파일/실행
  • 동적 언어(Python/JS)는 컴파일이 못 잡는다 — 실행 경로를 실제로 태우는 스모크 테스트까지 가야 확인된다

검증 ② 의존성 검사

  • 패키지가 실재하는가 — LLM은 패키지 이름도 환각한다. import 문 하나하나 레지스트리(PyPI/npm)에서 존재를 확인한다
  • 평판 확인 — 다운로드 수, 최근 릴리스, 관리자, 이슈 대응. 지난주 생성된 다운로드 100회짜리 패키지는 경고 신호다
  • 타이포스쿼팅 주의 — requests 대신 requessts처럼 한 글자 다른 악성 패키지가 레지스트리에 실제로 올라와 있다
  • 공격자는 LLM이 자주 환각하는 이름을 미리 등록해 둔다 — 이른바 슬롭스쿼팅(slopsquatting)
  • 규칙 — AI가 추가한 의존성은 사람이 추가한 의존성보다 한 단계 높은 심사를 받는다

검증 ③ 버전 호환성

  • 모델의 지식은 훈련 시점에 멈춰 있다 — 그 이후 바뀐 API, 폐기(deprecated)된 함수, 시그니처 변경을 모른다
  • 흔한 증상
    • 구버전 문법 사용 — 최신 메이저 버전에서 제거된 인자 호출
    • 폐기 예정 API 사용 — 당장은 돌아가지만 경고가 쌓인다
    • 보안 패치 이전 버전을 requirements에 고정
  • 대응 — 프로젝트의 실제 버전을 프롬프트에 명시하고, CI에서 폐기 경고(DeprecationWarning)를 실패로 처리한다

검증 ④ 보안 스캔 필수화

  • LLM은 훈련 데이터의 취약 패턴을 재생산한다 — 공개 저장소의 흔한 실수(SQL 문자열 연결, 약한 해시)가 그대로 나온다
  • SAST 자동화 — Semgrep, CodeQL, Bandit 등을 CI 게이트로. AI 생성 코드는 예외 없이 통과시킨다
  • 시크릿 스캔 — 예시 코드에 그럴듯한 API 키·비밀번호 문자열이 섞여 나온다. gitleaks 류 스캐너를 커밋 훅에 건다
  • 사람이 볼 것 — 인젝션 경로, 인증/인가 우회, 입력 검증 누락처럼 맥락이 필요한 취약점은 도구가 놓친다
  • 순서: 도구가 1차로 거르고, 사람은 도구가 못 보는 설계 수준을 본다

검증 ⑤ 테스트로 명세를 고정하라

  • AI 코드에는 사람이 쓴 테스트를 붙인다 — 테스트가 곧 "내가 이해한 요구사항"의 실행 가능한 기록이다
  • 순서가 중요하다 — 구현을 보기 전에 기대 동작을 테스트로 먼저 적으면, 구현에 끌려가지 않는다
  • 경계값 우선 — 빈 입력·null·음수·최대치·유니코드. AI는 해피패스는 잘 짜고 경계에서 무너진다
  • 테스트가 통과하면 "이 코드가 맞다"가 아니라 "내가 명세한 범위 안에서 맞다"까지만 보장된다 — 그래서 명세를 넓히는 것이 리뷰다

테스트 = 사람이 소유한 명세

AI가 쓴 테스트의 함정 — 구현 복제 테스트

구현을 보고 테스트를 생성하면, 버그까지 함께 명세화된다

def apply_discount(price, rate):
    return price * (1 - rate / 100)  # rate=0.1을 10%로 기대한 호출자는?

# AI 생성 테스트 — 구현 로직을 그대로 베껴 와서 "항상 통과"
def test_apply_discount():
    assert apply_discount(100, 10) == 100 * (1 - 10 / 100)
  • 동어반복 테스트 — 기대값을 구현과 같은 식으로 계산하면 아무것도 검증하지 않는다
  • 리뷰 포인트 — 기대값은 반드시 리터럴(90)이나 독립 계산으로. 구현 함수를 기대값 계산에 재사용하면 반려

대량 생산 문제 — 리뷰가 병목이 된다

  • 생성 10분, 리뷰 2시간 — 500줄 생성은 몇 분, 그 500줄을 책임지고 읽는 데는 SmartBear 기준(200~400 LOC/시간)으로 1~2시간 이상
  • 병목이 코딩에서 리뷰로 이동했다 — 조직의 처리량은 이제 생성 속도가 아니라 검증 속도가 결정한다
  • 위험한 반응 — 리뷰를 얕게 해서 속도를 맞추는 것. 결함이 그대로 하류(운영)로 흘러간다
  • 올바른 반응 — 생성량 자체를 리뷰 가능한 크기로 제한한다 (다음 두 슬라이드)
  • ≤400 LOC 리뷰 상한 규칙은 AI 시대에 폐기되는 게 아니라 더 중요해진다

대응 ① 작게 생성시키기

  • 한 번에 한 함수, 한 파일 — "전체 모듈 만들어줘"가 아니라 "이 시그니처의 함수 하나 구현해줘"
  • 작은 생성의 이점
    • 리뷰 단위가 사람의 인지 한계 안에 들어온다
    • 환각·요구 누락을 조기에, 국소적으로 발견한다
    • 잘못된 방향이면 프롬프트만 고쳐 다시 생성하면 된다 — 매몰 비용이 작다
  • PR 분할 원칙도 동일 — 3장에서 배운 "작은 PR" 규칙을 생성 단계부터 적용하는 것
  • 대량 생성이 불가피하면(보일러플레이트 등) 기계 생성 부분과 로직 부분을 커밋으로 분리해 리뷰 강도를 차등화한다

대응 ② 생성 즉시 리뷰

  • 미루면 눈덩이가 된다 — 검증 안 된 생성 코드 위에 다음 생성이 쌓이면, 오류가 복리로 불어난다
  • 생성-리뷰 사이클을 분(分) 단위로 — 생성 → 읽고 수정 → 커밋, 이 루프를 짧게 유지한다
  • 맥락이 살아 있을 때 읽어라 — 방금 시킨 일이므로 요구사항이 머릿속에 선명하다. 하루 뒤에는 그 맥락 복원에만 시간이 든다
  • 셀프리뷰 먼저 — AI 코드를 PR로 올리기 전, 저자 본인이 diff 전체를 정독하는 것이 리뷰어에 대한 예의이자 1차 방어선

검증 없는 생성물은 자산이 아니라 부채다

'훑어보기 유혹'과 자동화 편향

  • 자동화 편향(automation bias) — 자동 시스템의 출력을 과신해 검증을 생략하는 인지 편향. 항공·의료에서 오래 연구된 현상이다
  • 코드 리뷰에서의 증상 — "AI가 짰으니 문법은 맞겠지" → 스크롤만 하고 승인
  • 그럴듯함이 편향을 증폭한다 — 깔끔한 형식·자신 있는 주석이 "검토 완료" 느낌을 준다. 형식 품질과 논리 품질은 별개다
  • 깨는 방법
    • "이 코드에는 결함이 있다"를 기본 가정으로 읽기 시작한다
    • 리뷰 산출물을 강제한다 — 코멘트 0개 승인 금지, 대조표 첨부 등

리뷰 강도는 사람 코드보다 높여라

  • 신뢰 이력이 없다 — 동료에게는 "이 사람은 경계 조건을 잘 챙긴다" 같은 누적된 신뢰가 있다. 모델에는 그런 이력 개념이 성립하지 않는다 — 같은 프롬프트도 매번 다른 코드가 나온다
  • 오류 분포가 다르다 — 사람은 피곤할 때 실수하고, AI는 통계가 어긋나는 곳(드문 API 조합, 최신 버전, 도메인 규칙)에서 실수한다
  • 실무 규칙
    • 시니어가 짠 코드처럼 훑지 말고, 첫 출근한 신입의 코드처럼 읽는다
    • "돌아간다"와 "맞다"를 구분한다 — 데모 성공은 검증이 아니다

AI 코드 diff 정독 순서

한정된 리뷰 에너지를 결함 밀도가 높은 곳부터 쓴다

  • 1순위: 공개 인터페이스 — 함수 시그니처, 반환 타입, 예외 계약. 여기가 틀리면 호출자 전부가 오염된다
  • 2순위: 에러 경로 — 실패 시 무엇을 하는가. AI는 에러를 삼키거나(silent except) 일반 Exception으로 뭉개는 경향이 강하다
  • 3순위: 해피패스 — 정상 흐름 로직. 역설적으로 AI가 가장 잘하는 부분이라 마지막에 본다
  • 사람 코드와 순서가 다르다 — 사람 코드는 저자가 고민한 흔적(커밋 메시지·주석)을 따라가지만, AI 코드는 위험 순서로 기계적으로 훑는다
  • 시간이 없으면 1~2순위만이라도 — 해피패스 버그는 테스트가 잡지만 계약 위반은 운영에서 터진다

과잉 방어 코드 걷어내기

AI는 "안전해 보이는" 코드를 위해 불필요한 방어를 덧바른다

try:
    result = parse_config(path)
except Exception:
    result = None  # 모든 오류를 삼킴 — 원인 추적 불가
result = parse_config(path)  # 설정 오류는 여기서 죽는 게 맞다
  • 넓은 except는 버그 은폐 장치다 — 파일 없음·권한·문법 오류가 전부 조용한 None이 된다
  • 리뷰 질문 — "이 예외를 여기서 잡아야 할 이유가 있는가? 잡아서 무엇을 할 수 있는가?" 답이 없으면 걷어낸다
  • 유사 패턴: 모든 인자에 None 체크, 도달 불가능한 else 분기, 이중 검증

중복 감지 — 추상화 대신 복붙 경향

def get_user(id):
    resp = requests.get(f"{BASE}/users/{id}", timeout=5)
    resp.raise_for_status()
    return resp.json()

def get_order(id):   # 같은 구조를 통째로 복제
    resp = requests.get(f"{BASE}/orders/{id}", timeout=5)
    resp.raise_for_status()
    return resp.json()
  • 세션 단위 생성의 부작용 — 모델은 기존 코드를 재사용하기보다 매번 완결된 코드를 새로 만든다. 대화가 바뀌면 같은 로직이 또 나온다
  • 리뷰 포인트 — 두 번 이상 반복되는 구조는 공통 함수 추출을 요구한다. 중복은 지금이 아니라 "한쪽만 수정된 6개월 뒤"에 비싸진다

데드 코드·미사용 import 정리

  • AI 코드의 흔한 잔재
    • 쓰지 않는 import — 생성 도중 계획이 바뀌어도 import는 남는다
    • 호출되지 않는 헬퍼 함수 — "혹시 필요할까 봐" 만들어 둔 코드
    • 주석 처리된 대안 구현 — 삭제 대신 주석으로 남긴 흔적
  • 데드 코드는 공짜가 아니다 — 읽는 사람의 시간을 뺏고, 검색을 오염시키고, "살아 있는 줄 알고" 수정하게 만든다
  • 도구로 강제 — ruff/ESLint의 unused 규칙을 CI 실패 조건으로. Knight Capital(2012)이 보여줬듯 죽은 코드는 언젠가 되살아나 문다

코드베이스 컨벤션 정합성

  • 모델은 우리 저장소의 관례를 모른다 — 세상에서 가장 흔한 스타일로 짤 뿐, 우리 팀의 스타일로 짜지 않는다
  • 기존 유틸 재사용 확인 — 이미 있는 retry_with_backoff()를 두고 새 재시도 로직을 짜지 않았는가. "이 기능, 우리 코드에 이미 있지 않나?"를 습관적으로 검색한다
  • 정합성 체크 항목
    • 에러 처리 방식 — 예외 vs Result 타입, 우리 팀의 선택을 따르는가
    • 로깅 — 팀 로거 대신 print/console.log를 쓰지 않았는가
    • 네이밍·디렉터리 구조 — 주변 코드와 이질감이 없는가
  • 완화책: 프롬프트에 기존 유틸 목록과 컨벤션 문서를 컨텍스트로 넣는다

주석 다이어트 — 코드를 반복하는 주석 제거

❌ 이렇게 말고

# count를 1 증가시킨다
count += 1
# 사용자 목록을 순회한다
for user in users:

✅ 이렇게

# 탈퇴 후 30일은 재가입 불가
# (약관 7.2조)
if days_since_quit < 30:
    raise RejoinBlocked()
  • AI는 "무엇을"을 설명하는 주석을 남발한다 — 코드가 이미 말하는 것을 반복하는 주석은 소음이다
  • 남길 주석은 "왜"뿐 — 비즈니스 규칙, 비직관적 선택의 이유, 함정 경고

커밋·PR에 AI 사용 표기 — 투명성 정책

  • 왜 표기하는가 — 리뷰어가 리뷰 강도를 조절할 수 있고, 장애 회고 때 원인 분석이 빨라지고, 라이선스·감사 대응이 가능해진다
  • 표기 방법 예시
    • 커밋 트레일러: Assisted-by: (도구명) 또는 Co-authored-by 관례
    • PR 템플릿 체크박스: "AI 생성 코드 포함 여부 + 검증 방법"
  • 표기는 낙인이 아니다 — 처벌용이면 아무도 안 적는다. "표기된 코드는 절차대로 검증받았다"는 신뢰 표식으로 운영해야 정착된다
  • 일부 OSS 프로젝트는 이미 AI 기여 공개를 기여 가이드라인에 명문화했다

  • 허용 범위 — 어떤 코드에 AI를 써도 되는가. 보일러플레이트·테스트는 허용, 암호화·결제 핵심 로직은 사람 작성 원칙 등 등급을 나눈다
  • 기밀 코드 정책 — 사내 소스·고객 데이터를 외부 모델에 보낼 수 있는가. 온프레미스/전용 엔드포인트 사용 조건을 명시한다
  • 검증 게이트 — AI 생성 코드가 머지되기 위한 최소 조건(사람 리뷰 1인 이상, SAST 통과, 테스트 커버리지)을 CI로 강제한다
  • 정책이 없으면 각자 알아서 쓴다 — 사고가 난 뒤의 정책은 금지 일변도가 되기 쉽다. 미리 만드는 쪽이 허용 범위도 넓다

퀴즈 — 7장 점검

Q1. AI가 생성한 함수에 대해 AI에게 테스트도 함께 생성시켰고 모두 통과했다. 이 검증의 맹점은?

구현을 본 모델이 구현 로직을 복제해 기대값을 계산하는 동어반복 테스트를 만들 수 있다. 구현에 버그가 있어도 테스트가 같은 버그를 공유하므로 항상 통과한다. 기대값은 사람이 요구사항에서 독립적으로 도출한 리터럴 값이어야 하며, 특히 경계값 케이스는 사람이 직접 작성해 명세를 고정해야 한다.

Q2. "AI 코드는 사람 코드보다 리뷰 강도를 높여야 한다"의 근거 두 가지는?

① 신뢰 이력이 없다 — 동료의 코드는 누적된 품질 이력으로 리뷰 강도를 조절할 수 있지만, 모델 출력은 매번 독립적이라 이력 기반 신뢰가 성립하지 않는다. ② 오류가 그럴듯하다 — 형식이 깔끔해 자동화 편향을 유발하며, 서투른 코드가 주는 "여기 수상함" 신호가 없어 얕은 리뷰로는 결함이 걸리지 않는다.

미래 전망 — AI가 AI를 리뷰하는 시대?

  • 이미 시작됐다 — LLM 기반 리뷰 봇이 PR에 1차 코멘트를 다는 워크플로는 보편화 단계다
  • AI 리뷰어의 강점 — 지치지 않고, 즉시 응답하고, 흔한 패턴 결함을 잘 잡는다
  • 한계도 명확하다 — 요구사항의 옳고 그름, 도메인 트레이드오프, "이 기능을 만들어야 하는가"는 판단하지 못한다. 생성 모델의 편향을 리뷰 모델이 공유할 수도 있다
  • 구도 전망 — AI가 AI를 1차 검수하되, 승인 권한과 최종 책임은 사람에게 남는다. 리뷰어의 역할이 "오타 찾기"에서 "판단과 책임"으로 상향 이동한다
도구는 책임을 질 수 없다. 책임질 수 없는 자에게 승인 권한을 주어서는 안 된다 — 이 원칙은 기술이 바뀌어도 남는다.

7장 요약

  • 대원칙 — 머지하는 사람이 저자다. 책임은 이동하지 않는다
  • 3가지 차이 — 의도 부재·대량 생산·그럴듯함. 리뷰는 요구사항과 프롬프트에서 시작한다
  • 5대 검증 — API 실재·의존성·버전 호환·보안 스캔·사람의 테스트
  • 병목 관리 — 작게 생성, 즉시 리뷰, 자동화 편향 경계, 리뷰 강도 상향
  • AI 냄새 제거 — 과잉 방어·중복·데드 코드·소음 주석
  • 조직 차원 — 사용 표기, 허용 범위·기밀·게이트 정책, 하이브리드 워크플로

왜 지금도 '맨눈 리뷰'인가

  • 도구 정전 — API 장애, 네트워크 차단, 라이선스 만료. 도구가 멈춘 날에도 릴리스는 나가야 한다
  • 기밀 환경 — 방산·금융·의료 등 외부 모델에 코드를 보낼 수 없는 환경은 생각보다 넓다. 여기서는 사람의 눈이 전부다
  • 근육 유지 — 코드를 읽는 능력은 쓰지 않으면 준다. AI 출력을 판정하는 능력의 원천이 바로 이 읽기 근육이다
  • 계산기가 있어도 산수를 배우는 이유와 같다 — 결과가 이상한지 알아채려면 스스로 계산할 줄 알아야 한다
  • 이 장의 기법들은 1970년대에 정점을 찍고 잊혔다가, AI 시대에 "검증 기술"로 다시 소환되고 있다

데스크 체킹 — 천공카드 시대의 유산

  • 기원 — 포트란 천공카드 시절, 컴파일 한 번에 하루가 걸렸다. 제출 전에 책상에서 종이 위 코드를 손으로 실행하는 것이 생존 기술이었다
  • 방법 — 자신이 CPU가 되어 한 줄씩 실행한다. 변수 값을 종이에 적고, 분기마다 어느 길로 가는지 기록한다
  • 무엇이 잡히는가 — 경계 조건(off-by-one), 초기화 누락, 루프 종료 조건, 잘못된 분기 — 실행 전에 머리로 잡는 버그들
  • 컴파일이 공짜인 지금도 유효하다 — 실행은 "결과가 틀렸다"까지만 알려주지만, 데스크 체킹은 "어디서부터 틀렸는지"를 알려준다

트레이스 테이블 실습 ① — 문제

아래 함수를 손으로 실행해 보자. mystery(4)의 반환값은?

def mystery(n):
    total = 0
    i = 1
    while i <= n:
        total += i * i
        i += 1
    return total
  • 규칙 — 실행하지 말 것. 종이에 변수별 칸을 만들고, 줄이 실행될 때마다 값을 갱신한다
  • 기록할 것 — i, total, 그리고 매 반복의 조건식 i <= n 판정 결과
  • 다음 슬라이드에서 추적표로 답을 맞춰 본다

정독 기법 — 줄별 읽기에서 무엇을 묻나

그냥 읽는 것과 질문하며 읽는 것은 다른 활동이다

  • 각 줄마다 — 이 변수는 이 시점에 어떤 값 범위를 갖는가? null/0/빈 값일 수 있는가?
  • 각 분기마다 — 반대 분기로 가는 입력을 하나 떠올릴 수 있는가? else가 없는데 괜찮은가?
  • 각 루프마다 — 0회 실행되면? 종료가 보장되는가? 마지막 반복에서 인덱스는?
  • 각 호출마다 — 실패하면 무슨 일이 생기는가? 반환값을 버려도 되는가?
  • 각 자원마다 — 열었으면 닫히는가? 예외 경로에서도?
  • 질문에 답할 수 없는 줄이 바로 코멘트를 달 자리다 — "여기서 x가 음수면 어떻게 되나요?"

페이건 인스펙션 개요 — 공식 6단계

Michael Fagan, IBM 1976 — 코드 리뷰를 측정 가능한 공정으로 만든 원형

단계내용
1. 계획(Planning)자료 준비, 참가자 선정, 진입 조건 확인
2. 개요(Overview)저자가 배경·설계 맥락을 팀에 설명
3. 준비(Preparation)각자 사전 정독 — 결함 후보를 미리 기록
4. 미팅(Inspection)모여서 결함을 공식 발견·기록
5. 재작업(Rework)저자가 기록된 결함을 수정
6. 후속(Follow-up)중재자가 수정 완료를 확인, 재검토 여부 결정
  • 핵심 통찰: 리뷰를 "선의의 습관"이 아니라 진입·종료 조건과 기록이 있는 공정으로 정의했다

인스펙션 역할극 — 4개의 모자

  • 중재자(moderator) — 회의 진행, 규칙 집행, 결함 기록 관리. 저자의 상급자가 맡지 않는 것이 원칙(평가 회의로 변질 방지)
  • 저자(author) — 질문에 답하되 변명하지 않는다. 방어가 아니라 청취가 임무다
  • 낭독자(reader) — 저자가 아닌 사람이 코드를 소리 내어 해석하며 읽는다. 저자의 의도와 코드의 실제가 갈라지는 지점이 드러난다
  • 시험자(tester) — "이 입력이면 어떻게 되나"를 집요하게 묻는 관점 담당
  • 역할 분리의 효과 — 같은 사람이 읽고 쓰고 판정하면 놓치는 사각을, 관점을 강제 배분해 없앤다. Weinberg의 에고리스 프로그래밍(1971)과 같은 뿌리다

인스펙션 미팅 규칙

  • 결함 발견만, 해결 논의 금지 — "어떻게 고칠까"가 시작되면 발견이 멈춘다. 수정은 재작업 단계에서 저자가 한다
  • 2시간 상한 — 집중력은 그 이상 유지되지 않는다. 남으면 회의를 쪼갠다. SmartBear 데이터의 60~90분 권고와 같은 이유다
  • 사람이 아니라 산출물을 검사한다 — 결함 기록에 "누가"는 없다. 결함 수를 인사 평가에 쓰는 순간 인스펙션은 죽는다
  • 속도 상한 — 시간당 검토 줄 수를 제한한다. 빨리 읽는 회의는 아무것도 못 찾는 회의다
  • 이 규칙들은 그대로 현대 PR 리뷰 문화의 조상이다 — 비동기로 형태만 바뀌었다

인스펙션의 수치 효과와 현대 경량화

  • 효과의 근거 — Fagan의 IBM 보고 이래 공식 인스펙션의 결함 제거율은 통상 60~90%로 보고되어 왔다. 테스트 단계보다 앞서, 더 싸게 잡는다
  • 그런데 왜 사라졌나 — 회의 소집 비용이 크다. 6단계 공정은 빠른 배포 주기와 충돌했다
  • 현대의 경량화 — 살아남은 유산만 추리면:
    • 사전 준비(각자 정독) → PR을 미리 읽고 코멘트
    • 결함 기록 → 리뷰 코멘트 스레드
    • 후속 확인 → resolve 및 re-request review
  • 고위험 코드(결제·암호화·안전)에는 지금도 풀 인스펙션이 비용을 정당화한다 — Therac-25는 독립 리뷰 부재의 대가였다

  • 저자가 주도하는 워크스루는 설명하는 행위 자체가 셀프리뷰가 된다 — 다음 러버덕 슬라이드의 원리와 같다

페어 프로그래밍 = 실시간 리뷰

  • 드라이버(driver) — 키보드를 잡고 구현에 집중. 전술적 사고 담당
  • 내비게이터(navigator) — 방금 쓰인 코드를 실시간으로 읽고 방향·결함·설계를 본다. 전략적 사고 담당
  • 리뷰 관점에서의 본질 — 리뷰 지연이 0인 코드 리뷰. 결함이 태어난 지 몇 초 만에 발견된다
  • 규칙 — 역할을 주기적으로 교대한다(예: 25분마다). 내비게이터가 폰을 보기 시작하면 페어가 아니라 감시다
  • 비용 논쟁: 두 명이 한 일을 하니 비싸 보이지만, 결함 감소·지식 전파·리뷰 단계 생략을 합산하면 고난도 작업에서는 이득이라는 보고가 많다
  • 도구 없는 환경에서 특히 강력하다 — 필요한 장비가 의자 하나뿐이다

러버덕 디버깅 — 설명하면 보인다

  • 기원 — 「실용주의 프로그래머(The Pragmatic Programmer)」가 퍼뜨린 기법. 고무 오리에게 코드를 한 줄씩 설명한다
  • 왜 작동하나 — 머릿속 이해는 건너뛰기가 가능하지만, 말로 하는 설명은 순차적이라 건너뛸 수 없다. "여기서 이 값이... 어라?"의 순간이 온다
  • 셀프리뷰에 적용 — PR 올리기 전, diff의 각 헝크를 오리(또는 빈 의자)에게 설명한다. 설명이 막히는 곳이 코드가 이상한 곳이다
  • 동료의 시간을 쓰기 전에 오리의 시간을 쓰는 것 — 가장 싼 1차 리뷰어다

소리 내어 읽기

  • 기법 — 코드를 자연어 문장으로 번역해 소리 내어 읽는다. "사용자 목록에서, 활성 상태인 것만 골라, 이메일을 뽑는다"
  • 판정 기준 — 문장으로 매끄럽게 읽히지 않는 코드는 나쁜 코드다
    • "어... x가 참이 아니고 y가 아니면..." → 부정 조건이 꼬여 있다는 신호
    • 문장이 세 줄을 넘어간다 → 함수가 너무 많은 일을 한다는 신호
    • 이름을 읽다가 설명을 덧붙이게 된다 → 이름이 틀렸다는 신호
  • 낭독자(reader) 역할의 개인 버전 — 인스펙션이 회의로 하던 일을 혼자서 하는 셈이다

체크리스트의 기원 — 1935년 B-17 Model 299

  • 사건 — 1935년, 보잉의 차세대 폭격기 Model 299(훗날 B-17) 시연 비행이 이륙 직후 추락. 베테랑 조종사가 거스트 락(조종면 잠금) 해제를 잊은 것이 원인이었다
  • 진단 — "조종사 한 사람이 다 기억하기에는 비행기가 너무 복잡해졌다." 더 많은 훈련이 아니라 다른 방법이 필요했다
  • 해법 — 조종사들이 이륙·비행·착륙 단계별 체크리스트를 만들었고, B-17은 이후 사고 없이 수백만 마일을 비행했다
  • 소프트웨어로의 교훈 — 복잡성이 임계점을 넘으면 기억과 실력만으로는 안 된다. 4장의 WHO 수술 체크리스트(Gawande)와 같은 계보다

체크리스트 기반 읽기(CBR)와 관점 기반 읽기(PBR)

  • 애드혹 읽기 — 기준 없이 그냥 읽기. 리뷰어의 그날 컨디션이 곧 품질이 된다
  • 체크리스트 기반 읽기(CBR) — 결함 유형 목록(경계·null·자원·동시성...)을 들고 항목별로 훑는다. 아는 결함 유형은 안정적으로 잡는다
  • 관점 기반 읽기(PBR) — 리뷰어마다 다른 관점을 배정한다: 한 명은 테스터의 눈으로, 한 명은 유지보수자의 눈으로, 한 명은 사용자(호출자)의 눈으로
  • 실험 연구들에서 PBR은 애드혹 대비 결함 발견의 중복을 줄이고 팀 합산 발견율을 높이는 것으로 보고되었다 — 관점이 겹치지 않아 사각이 줄기 때문
  • 실무 적용: 리뷰어가 2명이면 "정확성 담당"과 "유지보수성 담당"으로 나누기만 해도 PBR의 절반은 얻는다

🎮 나만의 결함 체크리스트 만들기

범용 체크리스트보다 강한 것은 "내가 실제로 낸 버그"에서 추출한 목록이다. 최근 3개월의 버그 수정 커밋을 뒤져 자주 나온 유형에 체크해 보자.

  • 3개 이상 체크됐다면 그 항목들이 여러분의 1순위 개인 체크리스트다 — 자기 버그 로그는 최고의 교재다

인쇄해서 읽기 — 화면 밖에서 보이는 것들

  • 매체를 바꾸면 뇌의 모드가 바뀐다 — 화면에서 수십 번 본 코드도 종이에서는 낯설게 보인다. 낯섦이 곧 리뷰의 자원이다
  • 화면이 숨기는 것
    • 스크롤 밖의 맥락 — 종이는 여러 장을 책상에 펼쳐 함수 사이를 한눈에 본다
    • 전체 구조 — 화면은 한 번에 40줄, 종이 여러 장은 400줄의 지형을 보여준다
  • 펜의 힘 — 밑줄·화살표·여백 메모는 IDE 코멘트보다 사고를 자유롭게 한다. 데이터 흐름을 화살표로 그리다 보면 순환이 보인다
  • 고위험 코드 최종 점검이나 장시간 디버깅 교착 상태에서 특히 효과적 — 전부 인쇄할 필요는 없다, 핵심 모듈 한 개면 된다

콜로서스와 블레츨리 — 기계 없이 기계를 검증한 사람들

  • 1944년 블레츨리 파크 — 세계 최초의 프로그래머블 전자 계산기 콜로서스가 독일군 로렌츠 암호를 해독했다
  • 검증 도구가 없던 시대 — 콜로서스의 출력을 검증할 다른 컴퓨터는 세상에 없었다. 운용자들은 통계 지식과 교차 검산, 손 계산으로 기계의 답을 판정했다
  • 교훈 — 도구보다 강한 것은 도구의 출력을 판정하는 사람의 기준이다. "기계가 그렇다니까"는 그때도 지금도 검증이 아니다
  • AI 출력을 검증하는 오늘의 우리와 정확히 같은 구도 — 80년 전에 이미 답이 있었다

패턴 인식 훈련 — 체스 마스터처럼 코드 읽기

  • 청킹(chunking) — 체스 연구(de Groot, Chase & Simon)의 발견: 마스터는 말을 하나씩 보지 않고 "의미 있는 패턴 덩어리"로 지각한다. 실전 배치는 한눈에 외우지만 무작위 배치는 초보와 다를 바 없다
  • 코드 읽기도 같다 — 숙련자는 "아, 재시도 루프 + 백오프 패턴"으로 읽고, 초보자는 줄 단위로 읽는다. 패턴 어휘가 읽기 속도와 결함 감지력을 결정한다
  • 어휘를 늘리는 법 — 좋은 코드를 많이 읽고(다음 슬라이드들), 발견한 패턴과 안티패턴에 이름을 붙여 기록한다
  • 리뷰 중 "왠지 수상하다"는 직감의 정체가 바로 이 패턴 매칭이다 — 직감은 타고나는 게 아니라 축적된다

코드 리딩 클럽·모브 리뷰 운영법

  • 코드 리딩 클럽 — 독서 모임의 코드판. 격주 1시간, 잘 알려진 OSS 코드 한 조각을 함께 읽는다
    • 진행: 사전 공지(대상 코드 100~200줄) → 각자 정독 → 모여서 줄별 토론 → 발견한 패턴 기록
    • 교재 예: 표준 라이브러리, SQLite, Redis처럼 읽기 좋기로 정평 난 코드
  • 모브 리뷰(mob review) — 팀 전체가 화면 하나에 모여 실제 PR을 함께 리뷰. 시니어의 "읽는 방법" 자체가 실시간 전수된다
  • 둘 다 리뷰 문화의 사교육이다 — 리뷰 품질의 팀 간 격차는 대개 이런 훈련의 유무에서 나온다

집중 환경 설계 — 리뷰는 딥워크다

  • 25분 타임박스 — 뽀모도로 한 칸을 리뷰 전용으로. "25분 동안 이 PR만 읽는다"는 계약이 훑어보기를 막는다
  • 알림 차단 — 메신저·메일을 끈다. 리뷰 중 방해 1회의 비용은 그 몇 초가 아니라 무너진 맥락의 재구축 시간 전체다
  • 리뷰 시간대 고정 — 하루 중 머리가 맑은 시간대(예: 오전 첫 블록)를 리뷰 슬롯으로 예약한다. 퇴근 직전 리뷰는 승인 버튼이 가까워진다
  • SmartBear 데이터가 권고한 60~90분 상한과 결합하면: 하루 리뷰는 25분 블록 2~3개가 상한이다
  • 환경 설계는 의지보다 강하다 — 집중하려고 애쓰지 말고, 집중할 수밖에 없는 조건을 만든다

맨눈 리뷰의 한계와 도구 병행 시점

  • 사람이 약한 것
    • 기계적 반복 — 500개 파일의 포맷 검사, import 정렬. 지루함은 오탐과 누락을 낳는다
    • 전역 추적 — 코드베이스 전체의 호출 관계, 미사용 심볼 탐색
    • 알려진 취약점 대조 — CVE 데이터베이스와의 대조는 암기 대상이 아니다
  • 병행 원칙 — 기계가 할 수 있는 검사는 전부 기계에게(린터·SAST·포매터), 사람은 의도·설계·도메인 판단에만 집중한다
  • 이 장의 기법이 필요한 순간 — 도구가 없는 환경, 도구가 침묵하는 결함(논리 오류·요구 불일치), 그리고 도구 출력의 최종 판정

훈련 계획 — 매일 15분 OSS 코드 읽기

  • 왜 매일인가 — 읽기 근육은 세션 길이보다 빈도에 반응한다. 주 1회 2시간보다 매일 15분이 낫다
  • 4주 커리큘럼 예시
    • 1주: 표준 라이브러리 함수 하나씩 — 작고 완결된 코드로 워밍업
    • 2주: 즐겨 쓰는 라이브러리의 핵심 모듈 — 매일 이어서 읽기
    • 3주: 그 프로젝트의 버그 수정 PR 읽기 — 결함의 실물 표본 학습
    • 4주: 진행 중인 PR을 골라 혼자 리뷰 후, 머지된 실제 리뷰와 비교
  • 기록 — 매일 한 줄: 오늘 배운 패턴 또는 발견한 냄새. 4주 뒤 이 기록이 나만의 체크리스트가 된다

퀴즈 — 8장 점검

Q1. 페이건 인스펙션 미팅에서 "해결 방안 논의 금지" 규칙을 두는 이유는?

해결 토론이 시작되면 회의의 에너지가 발견에서 설계 논쟁으로 이동해 결함 발견이 멈추기 때문이다. 발견과 수정은 인지적으로 다른 활동이며, 수정은 재작업(Rework) 단계에서 저자가 맥락을 갖고 수행하는 편이 효율적이다. 미팅은 결함의 존재를 기록하는 데만 집중해야 2시간 상한 안에 검토 범위를 소화할 수 있다.

Q2. 러버덕 디버깅과 워크스루의 공통 원리는 무엇인가?

"설명하면 보인다"는 원리다. 머릿속 이해는 아는 부분을 건너뛰지만, 청자(오리든 동료든)에게 하는 설명은 순차적이라 논리의 빈틈을 건너뛸 수 없다. 설명이 막히거나 어색해지는 지점이 곧 코드의 결함 또는 설계 모호점이며, 저자 스스로 그것을 발견하게 된다. 워크스루는 이 효과를 팀 규모로, 러버덕은 개인 규모로 얻는 기법이다.

8장 요약

  • 맨눈 리뷰의 이유 — 도구 정전·기밀 환경·읽기 근육 유지. AI 출력 판정력의 원천이다
  • 손으로 실행 — 데스크 체킹과 트레이스 테이블은 off-by-one을 가장 확실히 잡는다
  • 공정으로서의 리뷰 — 페이건 인스펙션 6단계, 4역할, 미팅 규칙(발견만·2시간 상한)
  • 가벼운 변형들 — 워크스루·페어 프로그래밍·러버덕·소리 내어 읽기
  • 읽기 기법 — B-17에서 온 체크리스트, CBR·PBR, 인쇄해서 읽기
  • 훈련 — 청킹 어휘 축적, 리딩 클럽·모브 리뷰, 25분 집중 블록, 매일 15분 OSS 읽기

CLI 에이전트형개발자가 호출할 때저장소 전체 탐색, 맞춤 지시 가능실행 결과가 사람의 프롬프트 품질에 좌우
  • 세 유형은 경쟁이 아니라 계층이다 — IDE에서 걸러지면 PR 봇이 조용해지고, PR 봇이 걸러주면 사람 리뷰가 가벼워진다.

AI 리뷰어가 잘 잡는 것

  • 오타와 이름 불일치 — recieve, 복사 후 수정 누락된 변수명 같은 기계적 실수 통과
  • 상용구 버그 — 복붙한 조건문에서 한 곳만 바꾸지 않은 패턴, off-by-one 루프 경계
  • 널/None 체크 누락 — 반환값이 널일 수 있는 경로를 diff 안에서 기계적으로 추적
  • 관례 위반 — 팀 컨벤션 문서를 프롬프트에 넣어두면 명명 규칙·에러 처리 관례 위반을 일관되게 지적
  • 지치지 않는다 — 400 LOC를 넘겨도 사람처럼 대충 훑지 않는다. SmartBear 연구가 경고한 "리뷰 피로" 구간이 없다.
  • 공통점: 정답이 diff 안에 있고, 패턴으로 정의되는 결함이다.

AI 리뷰어가 못 잡는 것

  • 도메인 규칙 — "정산은 영업일 기준 D+2"라는 사실은 코드 어디에도 없다. 모르는 규칙은 위반해도 조용하다.
  • 아키텍처 방향 — 이 모듈이 곧 분리될 예정이라 지금 여기에 의존성을 추가하면 안 된다는 판단
  • 조직 맥락 — 이 코드의 실질 소유 팀, 과거에 같은 접근으로 장애를 냈던 이력
  • 정치와 우선순위 — 지금은 출시가 급해 부채를 감수한다는 트레이드오프 합의
  • "없는 코드" — diff에 나타나지 않은, 마땅히 함께 고쳤어야 할 다른 파일
  • 공통점: 정답이 코드 밖(문서·역사·사람의 머릿속)에 있는 결함이다.

권장 파이프라인: 2단 필터

AI 1차 스크리닝 → 사람 2차 판단

  • 1차(AI) — 오타·널 체크·관례·명백한 버그를 PR 생성 직후 자동 코멘트. 목표는 "사람이 볼 필요 없는 지적의 소거".
  • 2차(사람) — 설계·도메인·테스트 전략·유지보수성. Google 가이드의 기준 그대로: "CL이 코드베이스의 전반적 품질을 개선한다면 승인하라."
  • 순서가 핵심 — AI가 먼저 훑은 diff는 기계적 노이즈가 정리된 상태라 사람의 집중력이 설계로 향한다.
  • 역순(사람 먼저, AI 나중)은 사람의 비싼 시간을 싼 결함에 쓰게 되므로 피한다.

AI 사전 리뷰: PR 올리기 전 셀프 스크리닝

  • 작성자 단계에서 한 번 더 — PR을 올리기 전에 자기 diff를 AI에 먼저 돌려보는 습관. 8장의 셀프 리뷰(러버덕)의 자동화판이다.
  • 효과 1: 리뷰어 존중 — 사소한 지적이 이미 제거된 PR은 리뷰어의 첫인상이 다르고, 왕복 횟수가 줄어든다.
  • 효과 2: 심리적 안전 — 부끄러운 실수를 사람 아닌 기계 앞에서 먼저 털어낸다.
# 커밋 전 로컬 습관 예시
git diff main... | ai-review \
  --checklist team-review.md \
  --focus "null 안전성, 에러 처리, 명명"

도구 이름은 무엇이든 좋다 — "diff를 넘기고, 기준을 함께 넘긴다"는 형태가 요점이다.

AI에게 리뷰 시키는 프롬프트 잘 쓰기

  • 관점을 지정한다 — "시니어 백엔드 리뷰어로서 동시성 문제 중심으로"처럼 역할·초점을 명시
  • 체크리스트를 제공한다 — 4장에서 만든 팀 체크리스트를 그대로 프롬프트에 넣는다
  • 출력 형식을 고정한다 — 심각도·파일·라인·근거 순으로 요구하면 검증이 쉬워진다

AI 리뷰 결과를 검증하는 법

  • 가짜 양성(false positive)을 기본값으로 가정 — AI 지적은 "확정 결함"이 아니라 "조사할 후보 목록"이다.
  • 근거를 요구한다 — "이게 왜 버그인지 재현 경로를 설명하라"에 답하지 못하는 지적은 기각 후보
  • 코드로 반증한다 — 널 체크 누락 지적이면 실제로 널이 도달 가능한지 호출 경로를 직접 확인
  • 존재하지 않는 API 경계 — 7장의 환각 문제는 리뷰 코멘트에서도 나타난다. "이 함수 대신 표준 라이브러리 X를 쓰라"는 제안의 X가 실재하는지 확인.
  • 검증 비용이 지적 가치보다 크게 느껴지기 시작하면 프롬프트나 필터를 손볼 시점이다.

자동화 편향, 다시 경계하라

AI 리뷰어가 아무 말도 하지 않았다는 것은 결함이 없다는 뜻이 아니라, 찾지 못했다는 뜻이다.
  • "봇이 통과시켰으니 됐다"의 유혹 — 7장에서 본 자동화 편향이 방향만 바꿔 돌아온다.
  • 침묵은 증거가 아니다 — AI가 못 잡는 영역(도메인·아키텍처·맥락)은 애초에 침묵 구간이다.
  • 승인 권한을 주지 않는다 — AI 코멘트는 참고 자료이고, 병합 승인 버튼은 사람만 누른다.
  • Therac-25의 교훈을 기억하라 — 독립적인 사람의 검토가 없는 시스템은 같은 실수를 조용히 반복한다.

노이즈 관리: nit 폭탄 봇 길들이기

  • 증상 — PR마다 30개씩 달리는 사소한 지적. 개발자는 곧 전부 무시하기 시작하고, 진짜 결함도 함께 묻힌다.
  • 임계값 필터 — 심각도 낮음은 코멘트 대신 요약 1줄로 접기, PR당 코멘트 상한 설정
  • 카테고리 필터 — 포매터·린터가 이미 잡는 스타일 지적은 봇에서 꺼서 중복 제거(10장과 역할 분담)
  • nit 라벨 강제 — Google 관례처럼 사소한 지적엔 nit: 접두어를 붙이게 해 필수/선택을 구분
  • 측정 기준: "봇 코멘트 중 실제 코드 변경으로 이어진 비율". 이 비율이 낮으면 설정을 조인다.

AI 리뷰 코멘트의 톤 문제

  • 기계적 지적은 맥락 없이 단정한다 — "이 코드는 잘못되었습니다"라는 봇 코멘트가 신입의 첫 PR에 달리면, 사람이 쓴 것과 같은 무게로 읽힌다.
  • 사람이 중재한다 — 봇 지적 중 유효한 것만 사람이 골라 Conventional Comments 형식(suggestion:, question:)으로 전달하는 팀도 있다.
  • 봇임을 명시 — 봇 계정 이름·아이콘을 분명히 해 "이건 기계의 1차 의견"임을 시각적으로 구분
  • 칭찬은 사람의 몫 — 5장에서 본 대로 리뷰는 관계다. 봇은 praise를 진심으로 전달할 수 없다.
  • 원칙: 봇은 사실을 말하고, 사람은 판단과 온도를 더한다.

기밀·규제 코드와 AI 리뷰

  • 코드도 데이터다 — 외부 API로 diff를 보내는 순간, 소스 코드가 조직 경계를 넘는다.

이 체크리스트를 통과하지 못하면, 그 저장소는 AI 리뷰 대상에서 제외하는 것이 정답이다.

보조 활용: 요약·릴리즈 노트·설명

  • diff 요약 생성 — 큰 PR의 "무엇이 왜 바뀌었나"를 AI가 초안 작성, 작성자가 검수. 리뷰어의 진입 비용을 낮춘다.
  • 릴리즈 노트 초안 — 병합된 커밋 목록에서 사용자 관점 변경 사항을 추출
  • 리뷰어용 안내 코멘트 — "이 PR은 어디부터 읽는 게 좋은가"를 자동 제안
  • 탐지가 아닌 요약·정리 작업은 환각 위험이 상대적으로 낮고 효용이 즉각적이라, 도입 첫 단계로 적합하다.

리뷰 학습 도구로서의 AI

  • "왜"를 물을 수 있는 리뷰어 — 사람 리뷰어에게 열 번 되묻기는 부담스럽지만, AI에게는 부담이 없다.
  • 지적을 수업으로 바꾸는 질문 — "이게 왜 문제인지, 어떤 상황에서 실제 장애로 이어지는지 예시 코드로 설명하라"
  • 리뷰 감각 훈련 — 오픈소스 diff를 놓고 "내가 먼저 리뷰 → AI 리뷰와 비교"를 반복하면 3~5장에서 배운 읽기 기법(체크리스트 기반·관점 기반 읽기)의 연습장이 된다.
  • 신입 온보딩 — 팀 컨벤션 문서를 넣은 AI에게 첫 몇 주간 사전 리뷰를 받게 하면, 사람 멘토의 반복 설명 부담이 줄어든다.
  • 단, 비교 상대가 있어야 학습이다 — AI 답을 정답지로 삼지 말고 자기 판단과의 차이를 분석하라.

비용·효과 측정: 감이 아니라 숫자로

  • 잡은 결함 수 — AI 코멘트가 실제 수정으로 이어진 건수(주/월 단위)
  • 노이즈 비율 — 전체 AI 코멘트 중 무시·기각된 비율. 경험적으로 이 비율이 절반을 크게 넘으면 개발자들이 봇을 통째로 무시하기 시작한다.
  • 리뷰 리드타임 변화 — PR 생성부터 병합까지의 시간이 도입 전후로 어떻게 움직였나
  • 사람 코멘트의 성격 변화 — 도입이 성공하면 사람 코멘트에서 스타일 지적이 줄고 설계 논의 비중이 늘어야 한다
  • 비용 — API·라이선스 비용을 "절약된 리뷰어 시간"과 비교
  • 측정 없는 도입은 6개월 뒤 "그 봇 아직 켜져 있었나?"로 끝난다.

팀 도입 단계: 파일럿 → 튜닝 → 확대

단계범위핵심 활동통과 기준
1. 파일럿저장소 1개, 4~6주기본 설정으로 운영, 전 코멘트 기록유효 지적 비율 측정 완료
2. 튜닝같은 저장소임계값·카테고리 필터, 프롬프트에 팀 체크리스트 주입노이즈 비율 목표선 이하
3. 확대팀 전체 저장소설정 표준화, 운영 책임자 지정, 분기별 지표 리뷰지표 대시보드 정착
  • 순서를 건너뛰고 전사에 일괄 적용하면, 튜닝 안 된 nit 폭탄이 첫인상을 망치고 재도입이 어려워진다.

🎮 셀프 체크: Chapter 9

Q1. AI 리뷰어가 구조적으로 잡을 수 없는 결함 유형은 무엇이고, 왜인가?

도메인 규칙·아키텍처 방향·조직 맥락처럼 정답이 코드 밖에 있는 결함. AI에게 주어진 것은 diff와 프롬프트뿐이므로, 텍스트에 없는 지식(영업일 규칙, 모듈 분리 계획, 과거 장애 이력)은 위반해도 감지할 수 없다.

Q2. "AI 봇이 아무 코멘트도 안 달았으니 이 PR은 안전하다"는 판단의 문제는?

자동화 편향이다. AI의 침묵은 결함 부재의 증거가 아니라 탐지 실패 가능성을 포함한 무정보다. 특히 AI의 사각지대(맥락·설계)는 애초에 항상 침묵하는 영역이므로, 사람 2차 판단을 생략할 근거가 될 수 없다.

Q3. nit 폭탄 봇을 길들이는 대표적 수단 두 가지는?

(1) 임계값 필터 — 저심각도 지적은 요약으로 접고 PR당 코멘트 상한을 둔다. (2) 카테고리 필터 — 포매터·린터가 이미 잡는 스타일 항목은 봇에서 끈다. 판단 기준은 "봇 코멘트가 실제 수정으로 이어진 비율"이다.

9장 요약

  • 역할 전환 — AI가 사람 코드를 1차 스크리닝하고, 사람은 설계·맥락 판단에 집중한다.
  • 강약 분담 — AI는 기계적 결함과 규모, 사람은 도메인·아키텍처·책임.
  • 프롬프트가 품질 — 관점 지정 + 체크리스트 제공 + 근거 요구가 노이즈를 줄인다.
  • 검증과 경계 — 가짜 양성을 기본값으로 가정하고, AI의 침묵을 안전의 증거로 읽지 않는다.
  • 운영 — 노이즈·톤·기밀을 관리하고, 파일럿 → 튜닝 → 확대로 숫자를 보며 도입한다.

자동화 우선 원칙

기계가 잡을 수 있으면, 사람 시간을 쓰지 않는다

  • 사람 리뷰는 희소 자원 — SmartBear/Cisco 연구 기준 사람의 유효 리뷰 속도는 200~400 LOC/h, 집중 지속은 60~90분이 한계다. 이 예산을 들여쓰기 논쟁에 쓰는 것은 낭비다.
  • 자동화의 판별 기준 — 규칙으로 적을 수 있는가? 적을 수 있으면 도구의 일, 적을 수 없으면(설계·의도·맥락) 사람의 일.
  • 이 장의 지도 — 로컬(포매터·훅) → CI(린터·테스트·SAST) → 플랫폼(봇·보호 규칙) → 사람, 순서로 방어선을 쌓는다.

포매터: 스타일 논쟁의 종말

  • gofmt(Go), Black(Python), Prettier(JS/TS) — 공통 철학은 "설정 최소화, 만장일치 대신 일률 적용"
  • 논쟁 자체를 소거 — 탭 대 스페이스, 줄바꿈 위치를 리뷰에서 다시는 이야기하지 않게 된다.
  • diff가 깨끗해진다 — 포맷 변경이 섞이지 않으니 리뷰어는 의미 있는 변경만 본다.
gofmt의 스타일은 누구의 취향도 아니다. 그러나 gofmt는 모두의 취향이다 — Rob Pike, Go Proverbs
  • 도입 팁: 전체 저장소를 한 커밋으로 일괄 포맷하고, 그 커밋을 git blame 무시 목록(.git-blame-ignore-revs)에 등록한다.

린터: 규칙 합의가 곧 팀 표준

  • ESLint, pylint, RuboCop, Checkstyle — 스타일을 넘어 "우리 팀이 금지하는 패턴"을 코드로 명문화한다.
  • 린트 규칙 = 성문화된 리뷰 코멘트 — 같은 지적이 리뷰에서 3번 나오면 규칙으로 승격하라. 그 뒤로는 도구가 대신 말한다.
  • 합의 과정이 본체 — 규칙 채택 논의 자체가 팀 표준을 세우는 일이다. 한 사람이 몰래 켜는 규칙은 반발만 산다.
// .eslintrc — 리뷰 코멘트의 규칙 승격 예
{
  "rules": {
    "no-floating-promises": "error",  // "await 빠졌어요" 지적 자동화
    "eqeqeq": "error"                 // "== 대신 ===" 지적 자동화
  }
}

정적 분석·SAST: 버그 패턴과 취약점

  • 린터보다 깊게 — 데이터 흐름을 추적해 널 역참조, 자원 누수, 도달 불능 코드를 찾는다. Apple "goto fail"(2014)의 도달 불능 코드는 정적 분석이 잡을 수 있는 전형이었다.
  • SAST — SQL 인젝션, 하드코딩된 비밀키, 경로 조작 등 보안 취약점 패턴을 스캔. Heartbleed(2014) 이후 OpenSSL류 경계 검사 누락 패턴이 주요 표적이 됐다.
  • 오탐 관리가 성패 — 오탐을 방치하면 개발자가 경고 전체를 무시한다. 기준선(baseline) 고정 후 "새 경고만 실패" 정책으로 시작하라.
  • NASA JPL "Power of Ten"(Gerard Holzmann) 규칙 10: "모든 경고를 켜고, 경고 0 상태를 유지하라" — 극단이지만 방향은 이것이다.

타입 시스템도 리뷰 도구다

TypeScript·mypy가 컴파일 단계에서 대신 잡아주는 것들 — 이 지적들은 리뷰 스레드에 나타날 필요가 없다.

# mypy가 리뷰어 대신 잡는 것
def find_user(uid: str) -> User | None: ...

name = find_user(uid).name
error: "User | None" has no attribute "name"
# 널 체크 누락 — 사람이 지적하기 전에 실패한다

total: int = sum(prices)
send_amount(str(total))
error: expected "Decimal", got "str"
  • 타입 주석은 문서이자 계약 — 리뷰어가 "이거 None 오면요?"를 묻는 대신, 시그니처가 답을 강제한다.
  • 점진 도입 가능 — 새 코드부터 strict, 레거시는 모듈 단위로 확대.

pre-commit 훅: 로컬 1차 방어

  • 커밋 순간에 실행 — CI까지 가기 전에, 내 기계에서 포맷·린트·비밀키 유출을 차단한다. 피드백 지연이 초 단위라 교정 비용이 가장 싸다.
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/psf/black
    rev: 24.4.2
    hooks: [{id: black}]
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: detect-private-key   # 비밀키 커밋 차단
      - id: trailing-whitespace
      - id: check-merge-conflict

훅은 우회(--no-verify)가 가능하므로 최종 방어선이 아니다 — 같은 검사를 CI에서 반드시 반복한다.

CI 게이트 설계: 리뷰 전에 기계 관문

  • 원칙: 빨간 불이면 사람은 보지 않는다 — 테스트·린트·빌드가 실패한 PR은 리뷰 대기열에 들어오지 못하게 한다.
  • 게이트 구성 — 빌드 → 단위 테스트 → 린트/포맷 검사 → 정적 분석 → (선택) 커버리지 기준
  • 빠른 것부터 — 수 초짜리 린트를 먼저 돌려 실패를 조기에 알린다. 30분 테스트 뒤의 포맷 실패 통보는 개발자를 화나게 한다.
  • 효과: 리뷰어가 여는 모든 PR은 "이미 초록불"이라는 신뢰가 생기고, 사람은 기계가 못 보는 것만 본다.

커버리지 게이트의 함정

  • 수치는 게임이 된다 — "80% 미만이면 실패" 게이트는 assert 없는 실행-만-하는 테스트를 양산할 수 있다. 커버리지는 "실행됐다"이지 "검증됐다"가 아니다.
  • 굿하트의 법칙 — 측정이 목표가 되는 순간 좋은 측정이기를 멈춘다. 커버리지가 목표 숫자가 되면 품질 신호로서 죽는다.
  • 덜 위험한 대안 — 전체 %보다 "이번 diff의 신규 라인 커버리지"를 보고, 미커버 라인 목록을 리뷰어에게 보여주는 방식. 숫자 게이트가 아니라 리뷰 정보로 쓴다.
  • 리뷰어의 질문은 "몇 %냐"가 아니라 "위험한 경로가 테스트됐나"여야 한다 — 이 판단은 자동화되지 않는, 사람의 일이다.

PR 템플릿과 CODEOWNERS

  • PR 템플릿 — "무엇을/왜/어떻게 테스트했나"를 빈칸으로 강제해 3장의 '리뷰 요청 준비'를 양식화한다.
  • CODEOWNERS — 경로별 소유자를 선언하면 플랫폼이 리뷰어를 자동 지정한다. "누구한테 리뷰 부탁하지?"가 사라진다.
# .github/CODEOWNERS — 뒤에 오는 규칙이 우선
*                  @org/dev-leads
/payments/         @org/payments-team
/infra/terraform/  @org/platform-team
*.sql              @org/dba-team
/docs/             @org/tech-writers

소유자 없는 경로가 없도록 첫 줄에 기본 소유자를 둔다 — 무소유 코드는 무리뷰 코드가 된다.

브랜치 보호 규칙

main에 대한 최소 방어선 — 플랫폼 설정으로 강제한다.

  • 규칙은 사람을 못 믿어서가 아니라, 급한 날의 자신으로부터 팀을 지키기 위해 존재한다.

리뷰 룰 봇: Danger와 친구들

  • Danger(JS/Ruby) — PR 메타데이터에 팀 규칙을 코드로 강제하는 봇. CI에서 실행되어 PR에 코멘트를 단다.
  • 대표 용례 — PR 크기 경고, 체인지로그 누락 지적, 테스트 파일 없는 소스 변경 경고
// dangerfile.js
if (danger.github.pr.additions + danger.github.pr.deletions > 400) {
  warn("PR이 400라인을 넘습니다. 분할을 고려하세요.");
}
const hasChangelog = danger.git.modified_files.includes("CHANGELOG.md");
if (!hasChangelog) {
  fail("CHANGELOG.md 갱신이 필요합니다.");
}

400 LOC 경고선은 SmartBear 연구의 "리뷰 효율 급락 지점"을 그대로 규칙화한 것이다.

Gerrit 스타일 리뷰: 패치셋과 점수

  • 체인지(change) 단위 — PR(브랜치 단위)이 아니라 커밋 하나가 리뷰 단위. 수정할 때마다 새 패치셋(patchset)이 쌓여 버전별 비교가 가능하다.
  • 점수 체계 — 리뷰어가 -2에서 +2 사이 점수를 준다. +2(승인 권한자)와 CI의 Verified +1이 모두 모여야 병합된다.
  • -2는 거부권 — 한 명의 -2가 있으면 병합 불가. "합의될 때까지 병합 없음"을 구조로 강제한다.
  • Google 내부 리뷰 문화(Critique)와 같은 계보로, Android·Chromium 등 대형 오픈소스가 이 모델로 돌아간다.

Gerrit 인라인 코멘트와 체인지 단위 문화

  • 라인에 대화가 붙는다 — 인라인 코멘트는 resolved 처리 전까지 병합을 막을 수 있어, "코멘트 무시하고 머지"가 구조적으로 어렵다.
  • 작은 체인지의 강제 — 커밋 하나가 리뷰 단위이므로 "커밋을 작고 완결되게 쪼개는" 습관이 문화가 아니라 도구 수준에서 강제된다.
  • 패치셋 간 diff — "지난 리뷰 이후 뭐가 바뀌었나"만 볼 수 있어 재리뷰 비용이 급감한다 — 3장에서 강조한 왕복 비용 절감의 도구적 구현.

suggested changes: 리뷰어가 직접 패치를 제안

  • 말 대신 diff — "이렇게 바꾸면 어때요?"를 산문으로 쓰지 않고, 적용 가능한 패치로 제안한다. 작성자는 버튼 한 번으로 커밋한다.
리뷰 코멘트 안의 제안 블록:
```suggestion
if (items == null || items.isEmpty()) {
    return Collections.emptyList();
}
```
  • 왕복 1회 절약 — "수정 → 재푸시 → 재확인" 사이클 하나가 통째로 사라진다.
  • 적합/부적합 — 한두 줄 교정에는 최적. 설계 변경 요구를 suggestion으로 밀어넣는 것은 5장에서 본 "리뷰어의 월권"이 된다.
  • Conventional Comments의 suggestion: 라벨과 결합하면 의도가 더 분명해진다.

머지 큐·자동 머지: 승인 후 병목 제거

  • 승인 후에도 PR은 기다린다 — "CI 다시 돌고 → 다른 PR이 먼저 들어가 충돌 → 리베이스 → 다시 CI"의 대기 행렬이 리드타임을 늘린다.
  • 자동 머지 — "조건 충족 시 병합" 예약. 승인·초록불이 갖춰지는 순간 사람 손 없이 병합된다.
  • 머지 큐 — 병합 대기 PR들을 큐에 세우고, 최신 main + 앞선 PR들을 합친 상태로 CI를 돌린 뒤 순서대로 병합. "내 PR은 통과였는데 합치니 깨짐" 문제를 구조적으로 제거한다.
  • 효과는 심리적이기도 하다 — 승인 이후를 기계에 맡기면, 사람의 일은 승인 판단에서 깔끔하게 끝난다.

리뷰 지표 대시보드

  • 리드타임 — PR 생성부터 병합까지. Google 가이드의 "응답은 1영업일 이내" 관례가 지켜지는지 여기서 드러난다.
  • 왕복 횟수 — 리뷰어-작성자 핑퐁 횟수. 높으면 PR 준비 부실이나 서면 소통 실패 신호
  • PR 크기 분포 — 400 LOC 초과 비율. 크기가 줄지 않으면 다른 지표 개선은 없다.
  • 리뷰 부하 편중 — 특정 리뷰어에게 몰리는지. CODEOWNERS 재설계의 근거가 된다.
  • 지표는 온도계, 목표 아님 — 커버리지에서 본 굿하트의 법칙이 그대로 적용된다. 개인 평가에 쓰는 순간 지표는 조작되기 시작한다.
  • 팀 회고에서 추세만 본다 — "지난 분기보다 나아졌나?"가 유일하게 안전한 질문이다.

과자동화 경계: 도구의 역설

  • 역설 — 게이트가 늘수록 "기계가 다 봤겠지"라는 안심이 자라고, 사람 리뷰가 승인 버튼 클릭 의식으로 퇴화한다.

  • 2014년 2월 — iOS·macOS의 SSL/TLS 인증서 서명 검증이 사실상 무력화된 사실 공개
  • 영향 — 중간자(MITM) 공격자가 위조 서버로 HTTPS 통신을 가로챌 수 있는 상태

  • 보안 프로토콜의 심장부 코드였지만, 결함은 문법적으로 완전히 합법이었다

goto fail — 코드로 보는 결함

실제 C 코드 재현 (sslKeyExchange.c)

if ((err = SSLHashSHA1.update(&hashCtx, &serverRandom)) != 0)
    goto fail;
if ((err = SSLHashSHA1.update(&hashCtx, &signedParams)) != 0)
    goto fail;
    goto fail;  /* 중복 — 조건과 무관하게 항상 실행 */
if ((err = SSLHashSHA1.final(&hashCtx, &hashOut)) != 0)
    goto fail;  /* 여기부터 도달 불가 — 서명 검증 생략 */
fail:
    SSLFreeBuffer(&signedHashes);
    return err;  /* err == 0, 즉 "검증 성공"으로 반환 */
  • 두 번째 goto는 if에 묶이지 않은 무조건 점프. 이후의 최종 검증 코드는 죽은 코드가 된다

goto fail — 리뷰가 물었어야 할 질문

❌ 착시를 부르는 형태

if (cond)
    goto fail;
    goto fail;

✅ 중괄호 강제

if (cond) {
    goto fail;
}
  • 들여쓰기 착시 — 사람 눈은 들여쓰기를 블록으로 읽는다. C 계열은 그렇지 않다
  • 중괄호 규칙 — 한 줄 if에도 중괄호를 강제하면 이 부류가 통째로 사라진다
  • 정적 분석 — 도달 불가 코드 경고(-Wunreachable-code)가 켜져 있었다면 기계가 잡았다
  • 사람 리뷰는 "지루한 반복 구간"에서 가장 약하다 — 그곳이 도구의 자리

  • 그런데 착륙 성공 — 우선순위 스케줄러가 저순위 작업을 버리고 핵심 유도 작업만 재시작
  • 마거릿 해밀턴 팀이 설계·검증한 과부하 보호가 "예상 못한 입력"에서도 작동한 것

잘 검증된 코드는 예상 밖에서도 버틴다

CrowdStrike 2024 — 가장 최근의 교훈

  • 2024년 7월 19일 — 보안업체 CrowdStrike의 Falcon 센서 업데이트로 전 세계 Windows 기기 약 850만 대가 블루스크린
  • 원인 — 커널에서 읽는 "채널 파일"(설정 데이터) 업데이트가 범위 밖 메모리 읽기 유발
  • 구조적 문제 — 데이터 파일은 코드보다 느슨한 검증으로 전 고객에 즉시 배포
  • 단계적 배포(staged rollout) 부재 — 1%에게 먼저 나갔다면 사고는 실험실 크기로 끝났다
  • 항공·병원·금융까지 마비 — "설정도 코드다, 배포도 코드다"의 최신 증명
  • 교훈: 코드 리뷰의 범위에 데이터 파일·배포 파이프라인·카나리 정책을 포함하라

JWST — 검증에 검증을 거듭한 성공

  • 단일 고장점 수백 개 — 전개 절차의 어느 하나만 실패해도 미션 종료인 구조

  • 리뷰와 검증은 비용이 아니라, 되돌릴 수 없는 것을 지키는 유일한 보험

협약은 분기마다 회고에서 갱신한다 — 문서가 아니라 합의가 본체다

온보딩 도구로서의 리뷰 — 첫 PR 경험 설계

  • 첫 PR은 작고 성공 확정적으로 — 문서 오타, 테스트 추가처럼 하루 안에 머지되는 과제
  • 첫 리뷰 코멘트에 반드시 칭찬 하나 — 신입의 리뷰관(觀)은 첫 경험이 결정한다
  • 리뷰를 학습 채널로 — "우리 팀은 왜 이렇게 하는가"를 코멘트에 링크로 남긴다
  • 신입에게도 리뷰어 자리를 — 2주 차부터 가벼운 PR의 부(副)리뷰어로 지정
  • 질문형 코멘트("이 부분이 이해가 안 돼요")는 신입이 낼 수 있는 가장 값진 리뷰다 — 문서화 사각지대 탐지기

리뷰어로 성장하는 로드맵

단계하는 일다음 단계 조건
1. 관찰남의 리뷰 스레드를 읽고 판단 근거를 수집좋은 코멘트 패턴 10개 수집
2. nit 리뷰오타·네이밍·소소한 개선을 안전하게 지적라벨 붙인 코멘트가 습관화
3. 관점 리뷰테스트·보안·성능 등 하나의 관점을 전담맡은 관점에서 결함 발견 실적
4. 설계 리뷰구조·인터페이스·변경 방향 자체를 논의대안 제시와 트레이드오프 설명 가능

관점 기반 읽기(perspective-based reading)를 성장 사다리로 재활용한 것

시니어의 역할 — 본보기와 방패

  • 본보기 코멘트 — 팀은 규정이 아니라 시니어의 실제 코멘트 톤을 복제한다
  • 근거 링크, 대안 코드, praise: 라벨이 달린 코멘트 하나가 교육 자료 열 장보다 낫다
  • 리뷰 시간 보호 — 캘린더에 리뷰 블록을 공식 일정으로 잡고, 회의가 침범하지 못하게 한다
  • 거절의 시범 — 큰 PR에 "분할해 주시면 오늘 안에 봅니다"라고 말하는 법을 보여준다
  • 신입 리뷰어의 뒷배 — 신입의 지적이 무시당할 때 "좋은 포인트입니다"로 지원 사격

리뷰 지표 다루기 — 참고용으로만

  • 리드타임 — PR 생성부터 머지까지. 병목 탐지에 유용
  • 왕복 횟수 — 재수정 요청 횟수. 높으면 사전 소통 부족 신호
  • PR 크기 분포 — 400줄 초과 비율. 리뷰 품질의 선행 지표
  • 대기 중 PR 수 — 쌓이면 리뷰 부채의 조기 경보
  • 모두 팀 단위 추세로만 본다. 개인 순위표를 만드는 순간 지표는 죽는다

지표는 대화의 시작점이지, 결론이 아니다

지표의 함정 — 굿하트의 법칙

측정이 목표가 되는 순간, 좋은 측정이기를 멈춘다 — Goodhart's Law

❌ 목표가 된 지표

  • "리드타임 4시간 이내" → 고무도장 승인 급증
  • "코멘트 수로 기여도 평가" → nit 폭탄

✅ 신호로 쓰는 지표

  • 리드타임 급증 → "무엇이 병목인가" 회고 안건
  • 왕복 급증 → 설계 사전 논의 도입 검토
  • 지표에 목표치를 걸고 싶다면, 왜곡됐을 때 알아챌 반대 지표를 함께 건다

리뷰 부채와 상환 — 방치된 PR 관리

  • 방치 PR의 복리 이자 — 오래된 PR일수록 충돌이 쌓이고, 작성자의 맥락도 증발한다
  • 일일 트리아지 — 스탠드업에서 "24시간 넘게 대기 중인 PR"을 매일 호명
  • 상환 규칙 — 새 PR을 열기 전에 자기에게 할당된 리뷰부터 처리 (review-before-code)
  • 좀비 PR 정리 — 2주 이상 움직임 없는 PR은 닫거나 드래프트로 전환, 죄책감 없이
  • 11장 Knight 사례의 교훈 그대로 — 방치된 것은 언젠가 비용으로 돌아온다

논쟁 아카이브 — 같은 싸움을 두 번 하지 않기

  • ADR(Architecture Decision Record) — 결정·배경·검토한 대안·트레이드오프를 한 장짜리 문서로 저장소에 커밋
  • 리뷰 스레드가 30분을 넘으면 — 논쟁을 ADR 후보로 승격하고 스레드는 종료
  • 재논쟁 방지 — 같은 주제가 다시 올라오면 코멘트 대신 ADR 링크 한 줄로 응답
  • 번복 가능 — 새 근거가 생기면 ADR을 개정하면 된다. 기록은 고집이 아니라 이력이다

근거: 성능 임계 경로는 예외 조항으로 허용

리뷰와 평가의 분리

  • 리뷰 코멘트 수를 인사평가에 쓰지 말 것 — 세는 순간 코멘트는 방어 문서가 된다
  • 지적을 받은 수를 세면 사람들은 리뷰를 피하고, 지적한 수를 세면 nit이 폭증한다
  • 평가에 반영해도 되는 것 — "리뷰에 성실히 참여하는가"라는 행동 자체 (정성 평가)
  • 리뷰 기록은 성장 대화의 재료로만 — 1:1에서 "이 코멘트 좋았다"를 짚어주는 용도
  • 실패 사례의 비난 금지 — 사고 회고는 사람이 아니라 시스템의 구멍을 찾는 자리 (blameless postmortem)

리뷰는 코드를 심판하지, 사람을 심판하지 않는다

파트타임 수리공이 아니라 문화 — 전원이 리뷰어

  • "리뷰 담당자" 한 명 체제의 실패 — 병목이 되고, 단일 관점만 남고, 그가 떠나면 붕괴한다
  • 전원이 리뷰어 — 주니어 포함 모두가 리뷰 큐에 들어간다. 관점의 수가 곧 방어선의 수
  • 로테이션 — 모듈별 고정 리뷰어 대신 주 단위 순환으로 지식 독점을 방지
  • 리뷰는 업무다 — 스프린트 계획에 리뷰 시간을 명시적으로 배정 (경험칙: 개발 시간의 10~20%)
  • Microsoft 2013 연구(Bacchelli & Bird)가 확인했듯, 리뷰의 최대 효용은 결함 발견만큼이나 지식 전파다

  • 협약 문서 — SLA·크기 상한·승인 기준·라벨·에스컬레이션을 한 장으로 합의

Q. 우리 팀에 리뷰 협약 문서가 없다면 첫 항목으로 무엇을 넣어야 할까?

  3. 한 세션 60~90분, 시간당 200~400줄 이내
  4. 완벽이 아니라 "코드베이스 개선"이 승인 기준
  5. 코드를 말하고 사람을 말하지 마라
  6. 코멘트에 라벨을 붙여라 — nit:/issue:/question:
  7. 칭찬도 리뷰다 — praise:를 아끼지 마라
  8. 스타일은 도구에, 사람은 설계에
  9. 두 번 왕복하면 화면 밖 대화로
  10. 셀프 리뷰 없이 리뷰 요청하지 마라

요약 카드 ② — AI 코드 리뷰 10계명

  1. AI 산출물은 "제안"이다 — 머지 책임은 사람에게
  2. AI가 쓴 코드일수록 사람 리뷰를 강화하라
  3. 환각을 전제하라 — 존재하지 않는 API·패키지 검증
  4. 의존성 이름은 레지스트리에서 실물 확인 (슬롭스쿼팅)
  5. AI 리뷰는 1차 필터로 — 기계가 nit을, 사람이 설계를
  6. 비밀·독점 코드를 외부 모델에 넣기 전에 정책 확인
  7. 프롬프트에 맥락을 — diff만 주면 diff 수준의 답이 온다
  8. AI의 확신 어조에 속지 마라 — 근거를 요구하라
  9. 보안 취약 패턴 재생산을 의심하라 — 학습 데이터의 그림자
  10. AI 도입 후에도 "이해 못 한 코드는 머지 금지" 원칙 유지
