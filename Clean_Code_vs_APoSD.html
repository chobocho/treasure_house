Clean Code

Robert C. Martin · 2008
23 slides

Clean Code란?

"깨끗한 코드는 한 가지를 잘한다."
— Bjarne Stroustrup (Clean Code 서문)
"깨끗한 코드는 작가가 신경 써서 작성한 흔적이 보인다.
개선할 부분을 찾으려 노력해도 찾을 수 없을 때, 그것이 깨끗한 코드다."
— Michael Feathers

코드를 읽는 시간 vs 쓰는 시간 = 10 : 1
→ 읽기 쉬운 코드가 곧 쓰기 쉬운 코드.

핵심 철학: 보이스카우트 규칙

"캠프장은 처음 왔을 때보다 깨끗하게 하고 떠나라."

코드를 체크아웃했을 때보다 더 깨끗하게 체크인하라.

실천

  • 변수 이름 하나 더 분명히
  • 긴 함수 하나 쪼개기
  • 중복 한 곳 제거
  • 복잡한 if문 단순화

효과

  • 큰 리팩토링 대신 매일 작은 개선
  • 썩어가는 코드 방지
  • 팀 문화로 자리잡음

1. 의미 있는 이름

Before

int d; // 경과 일수
List<int[]> list1 = new ArrayList<>();
for (int[] x : theList) {
  if (x[0] == 4)
    list1.add(x);
}

After

int elapsedTimeInDays;
List<Cell> flaggedCells = new ArrayList<>();
for (Cell cell : gameBoard) {
  if (cell.isFlagged())
    flaggedCells.add(cell);
}
  • 의도가 분명한 이름 (Intention-Revealing)
  • 발음 가능, 검색 가능
  • 한 개념엔 한 단어 (fetch / retrieve / get 혼용 금지)

2. 함수 — 작게, 더 작게

"함수의 첫 번째 규칙은 작아야 한다는 것이다.
두 번째 규칙은 더 작아야 한다는 것이다."
— Robert C. Martin
  • 2~4줄이 이상적이라고 Martin은 주장
  • 중괄호 안의 들여쓰기는 1~2 레벨
  • if/else, while문 안의 블록은 한 줄(주로 함수 호출)이어야 함
  • 함수가 길어진다 = 여러 일을 하고 있다

→ 이 주장은 나중에 Ousterhout와의 최대 쟁점이 된다.

함수는 한 가지 일만

여러 일을 함

public void pay() {
  for (Employee e : employees) {
    if (e.isPayday()) {
      Money pay = e.calculatePay();
      e.deliverPay(pay);
    }
  }
}

한 일씩

public void pay() {
  for (Employee e : employees)
    payIfNecessary(e);
}
private void payIfNecessary(Employee e) {
  if (e.isPayday()) calculateAndDeliver(e);
}
private void calculateAndDeliver(Employee e) {
  e.deliverPay(e.calculatePay());
}

Stepdown Rule: 위에서 아래로 추상화 수준이 한 단계씩 내려가도록.

3. 함수 인자 — 적을수록 좋다

  • 0개 (niladic) ≫ 1개 ≫ 2개 ≫ 3개 (절대 피하라)
  • 4개 이상이면 아마 객체로 묶어야 한다
  • 플래그 인자는 최악: render(true)
// 나쁨: 플래그가 함수가 두 일을 한다고 외친다
render(boolean isSuite);

// 좋음: 두 함수로 분리
renderForSuite();
renderForSingleTest();
출력 인자(Output argument) 금지: appendFooter(s)처럼 s를 변경하는 인자.
대신 report.appendFooter()처럼 객체의 메서드로.

4. 부수효과(Side Effects) 금지

public boolean checkPassword(String user, String pw) {
  User u = UserGateway.findByName(user);
  if (u != User.NULL) {
    if (HashedPassword.from(pw).equals(u.password)) {
      Session.initialize();  // ← 숨겨진 부수효과!
      return true;
    }
  }
  return false;
}

checkPassword라는 이름이 약속한 것은 비밀번호 확인뿐.
그런데 Session.initialize()까지 호출한다 → 거짓말하는 함수.

해결: 함수명을 checkPasswordAndInitializeSession()으로 바꾸거나, 두 함수로 분리.

5. 명령과 조회 분리 (CQS)

섞임

if (set("username", "alice")) {
  ...
}

set이 무엇을 반환? "설정 성공"? "기존 값이 있었음"?

분리

if (attributeExists("username")) {
  setAttribute("username", "alice");
}

조회는 조회, 명령은 명령.

Command-Query Separation (Bertrand Meyer):
함수는 무엇을 하거나 무엇을 답하거나, 둘 중 하나만.

6. 오류 처리 — 예외 사용

오류 코드 반환

if (deletePage(page) == E_OK) {
  if (registry.delete(page) == E_OK) {
    if (config.delete(page) == E_OK) {
      log("deleted");
    } else log("config fail");
  } else log("registry fail");
} else log("delete fail");

예외 + Try-Catch

try {
  deletePage(page);
  registry.delete(page);
  config.delete(page);
} catch (Exception e) {
  log(e.getMessage());
}
  • Try-Catch 블록 자체를 함수로 분리
  • 예외 처리도 "한 가지 일"이다
  • null 반환 금지, null 전달 금지

7. 주석 — "실패의 증거"

"주석은 항상 실패다. 우리가 가진 표현력이 부족해서 주석을 다는 것이다.
주석을 쓸 때마다 우리는 패배감을 느껴야 한다."
— Robert C. Martin

코드 자체가 의도를 표현해야 한다. 주석은 거짓말한다.

나쁨

// 직원이 복지 자격이 있는지 확인
if ((e.flags & HOURLY) &&
    (e.age > 65))

좋음

if (e.isEligibleForFullBenefits())

좋은 주석 vs 나쁜 주석

허용되는 주석

  • 법적 주석 (저작권)
  • 의도 설명 (왜 이렇게 했는지)
  • 경고 (성능, 보안)
  • TODO
  • 공개 API의 Javadoc

나쁜 주석

  • 중얼거리는 주석
  • 같은 말 반복 (i++; // i 증가)
  • 오해의 소지가 있는 주석
  • 이력 정보 (Git이 해줌)
  • 주석 처리된 코드 (지워라)
  • 닫는 괄호 주석 } // end while

8. 형식 맞추기

세로 형식

  • 파일 한 개 = 200줄 이내가 좋다
  • 관련 개념은 가까이
  • 변수 선언은 사용 직전에
  • 호출하는 함수 → 호출되는 함수 (위→아래)

가로 형식

  • 한 줄 120자 이내
  • 연산자 주변 공백 (가독성)
  • 들여쓰기로 계층 표현
  • 팀 규칙은 절대적 — 자동 포매터 사용

"신문 기사처럼 읽혀야 한다 — 헤드라인 → 요약 → 디테일."

9. 객체와 자료구조

객체 (Object)

  • 자료를 숨기고 함수를 노출
  • 새 객체 추가는 쉬움
  • 새 함수 추가는 어려움

자료구조 (Data Structure)

  • 자료를 노출, 함수 없음
  • 새 함수 추가는 쉬움
  • 새 객체(타입) 추가는 어려움
대칭 관계: 객체와 자료구조는 반대편. 둘 다 시도하지 마라.
"잡종(hybrid)" 객체 — 자료도 드러내고 함수도 있는 — 는 최악.

10. 디미터 법칙 (Law of Demeter)

모듈은 자기가 조작하는 객체의 속을 몰라야 한다.

// 기차 충돌(train wreck) — 디미터 위반
String outputDir = ctxt.getOptions().getScratchDir().getAbsolutePath();

// 좋음 — 묻지 말고 시켜라(Tell, Don't Ask)
BufferedOutputStream bos = ctxt.createScratchFileStream(classFileName);

메서드 f는 다음의 메서드만 호출해야 한다:

  • 자기 자신(this)
  • 자기 인자
  • 자기가 생성한 객체
  • 자기 인스턴스 변수

11. 단위 테스트 (TDD 3법칙)

  1. 실패하는 테스트를 작성하기 전에는 실제 코드를 작성하지 않는다.
  2. 컴파일은 되지만 실패하는 정도까지만 테스트를 작성한다.
  3. 현재 실패하는 테스트를 통과할 만큼만 실제 코드를 작성한다.

테스트 코드는 실제 코드만큼 깨끗해야 한다. F.I.R.S.T.:

  • Fast — 빨라야
  • Independent — 독립적
  • Repeatable — 반복 가능
  • Self-Validating — 부울 결과로 자체 검증
  • Timely — 적시에 (실제 코드 직전)

12. 클래스 — SRP

"클래스를 변경해야 하는 이유는 단 하나여야 한다."
— Single Responsibility Principle

"하는 일"이 하나가 아니라, "변경 사유"가 하나.

// SRP 위반: 변경 사유 2개
class Employee {
  double calculatePay();    // 회계팀이 요구
  String reportHours();    // HR이 요구
  void   save(DB db);        // DBA가 요구
}

→ 세 클래스로 분리: PayCalculator, HourReporter, EmployeeRepository.

SOLID — S, O

S — Single Responsibility

한 클래스는 한 가지 변경 사유만.

"액터(Actor) 하나당 모듈 하나"

O — Open/Closed

확장에는 열려있고, 수정에는 닫혀있다.

interface Shape {
  double area();
}
// 새 도형 추가 = 새 클래스만, 기존 수정 X

SOLID — L, I

L — Liskov Substitution

자식은 부모의 자리에 그대로 들어갈 수 있어야.

고전적 예: Square extends Rectangle은 LSP 위반.
setWidth가 height까지 바꿔야 하므로.

I — Interface Segregation

큰 인터페이스보다 작은 여러 인터페이스.

// 나쁨
interface Worker {
  void work();
  void eat();
}
// 좋음
interface Workable{void work();}
interface Eatable {void eat();}

SOLID — D

Dependency Inversion Principle

고수준 모듈은 저수준 모듈에 의존하면 안 된다. 둘 다 추상화에 의존해야.

// 나쁨: 비즈니스 로직이 MySQL을 직접 안다
class OrderService {
  private MySqlDb db;
}

// 좋음: 추상화에 의존
class OrderService {
  private OrderRepository repo; // 인터페이스
}
class MySqlOrderRepository implements OrderRepository {...}

핵심: 의존성의 방향이 비즈니스 규칙을 향하도록 뒤집어라.

13. 동시성

  • 동시성과 코드 정리는 별개 — 동시성 코드는 따로 격리하라
  • 공유 자료를 제한하라 — 가능하면 복사본 사용
  • 스레드는 독립적으로 — 자료 공유 없는 스레드 설계 선호
  • 라이브러리를 알아라: java.util.concurrent
Producer-Consumer, Reader-Writer, Dining Philosophers
고전 패턴들을 익혀라 — 대부분의 실무 문제는 이 셋으로 환원된다.

14. 코드 냄새와 휴리스틱 (요약)

주석 냄새

  • 부적절한 정보
  • 오래된 주석
  • 주석 처리된 코드

함수 냄새

  • 인자 너무 많음
  • 출력 인자
  • 플래그 인자
  • 죽은 함수

일반 냄새

  • 중복
  • 잘못된 추상화 수준
  • 경계를 넘는 기반 코드
  • 매직 넘버
  • 조건문 캡슐화 안 함

Martin은 책 17장에서 75개의 코드 냄새와 휴리스틱을 나열한다.

Clean Code 요약 — 5문장

  1. 의미 있는 이름이 절반이다.
  2. 함수는 작게, 한 가지만 하라.
  3. 주석은 실패의 증거 — 코드로 의도를 표현하라.
  4. SOLID를 따르고 의존성 방향을 통제하라.
  5. TDD로 깨끗한 테스트와 함께 자라라.
Clean Code는 규칙(rules)의 책이다.
구체적이고, 강하게 단언하며, 따라하기 쉬운 가이드를 준다.
바로 그 강함이 비판의 대상이기도 하다 →

APoSD란?

"내가 본 가장 중요한 기술적 주제는 복잡성을 관리하는 방법이다."
— John Ousterhout

스탠포드 대학에서 소프트웨어 설계 과목(CS 190)을 가르치며 발견한 원칙들을 정리한 책.

  • 대학원 학생들의 코드를 매주 리뷰하며 도출
  • "왜 좋은 코드를 못 짜는가"에 대한 진단
  • 2판(2021): 더 많은 예제, 코드 리뷰 챕터 추가

분량은 짧다 (~190페이지) — 그러나 밀도가 높다.

핵심 주장: 복잡성이 적이다

Complexity

시스템의 이해를 어렵게 하거나, 수정을 어렵게 하는 모든 것.

복잡성의 정의 (Ousterhout)
C = Σ (c_p × t_p)
각 부분 p의 복잡성 c_p와 개발자가 그 부분에 보내는 시간 t_p의 가중합.
→ 자주 건드리는 곳이 복잡하면 더 나쁘다.

복잡성의 3가지 증상

1. Change Amplification

간단한 변경이 여러 곳을 손대게 함.

예: 웹사이트 배경색 바꾸려고 1000곳 수정.

2. Cognitive Load

변경을 위해 알아야 할 게 너무 많음.

예: 함수 하나 고치려고 12개 파일 읽어야.

3. Unknown Unknowns

무엇을 알아야 하는지조차 모름.

예: 고친 곳이 멀리 떨어진 기능을 깨뜨림.

Unknown Unknowns가 최악이다 — 좋은 설계는 이걸 줄이는 데 집중해야.

복잡성의 2가지 원인

1. Dependencies (의존성)

한 코드가 다른 코드 없이는 이해/수정할 수 없을 때.

  • 전역 변수
  • 매개변수 순서 약속
  • API 호환성
  • 네트워크 프로토콜

완전히 없앨 수는 없다 — 줄이고 명시하는 게 목표.

2. Obscurity (불명료성)

중요한 정보가 분명하지 않을 때.

  • 모호한 변수 이름
  • 일관성 없는 패턴
  • 숨겨진 가정
  • 부족한 문서

대부분 좋은 디자인과 좋은 주석으로 해결.

복잡성은 점진적이다

"복잡성은 한 번의 큰 실수로 오지 않는다. 수많은 작은 결정들이 누적되어 생긴다."
— John Ousterhout

한 번에 망가지는 시스템은 없다. 매일 조금씩 망가진다.

대응 방법: Zero Tolerance Philosophy
"이번 하나만 봐주자"는 위험하다. 작은 복잡성도 즉시 제거하라.
이것이 Martin의 보이스카우트 규칙과 닮은 지점.

전술적 vs 전략적 프로그래밍

Tactical (전술적)

  • "동작하게 만들자"
  • 당장의 기능 완성이 목표
  • 설계는 부차적
  • 지름길과 임시방편
  • 매번 작은 부채 누적

결과: Tactical Tornado — 한 명이 빨리 코딩하지만 팀 전체를 늦춤

Strategic (전략적)

  • "좋은 설계를 만들자"
  • 코드는 자산이라 생각
  • 설계에 10~20% 추가 투자
  • 장기적 생산성에 베팅
  • 지속적 정리(투자)

결과: 지속 가능한 속도

책의 중심 개념: 모듈은 깊어야 한다

좋은 모듈 = 단순한 인터페이스 + 강력한 기능

사용자가 적은 것을 알고도 많은 것을 얻을 수 있어야 한다.

Deep vs Shallow — 실제 예제

Deep: Unix file I/O

open(path, flags)
read(fd, buf, n)
write(fd, buf, n)
close(fd)
lseek(fd, off, whence)

단 5개 함수가 수만 줄의 파일시스템 코드를 숨김.
디스크, 캐시, 권한, 동시성, 네트워크... 모두 뒤에.

Shallow: Java I/O

new BufferedReader(
  new InputStreamReader(
    new FileInputStream(path)))

3개 클래스를 알아야 파일을 한 줄 읽을 수 있음.
각 클래스는 얇은 래퍼 — 인터페이스가 구현만큼 복잡.

Ousterhout이 책에서 가장 자주 인용하는 대비.

정보 은닉 (Information Hiding)

각 모듈은 설계 결정을 캡슐화해야 한다.

그 결정이 외부에서 보이지 않아야 변경이 한 곳에 격리된다.

숨겨야 할 것
  • 자료구조 (어떤 트리/해시인지)
  • 알고리즘 (정렬 방식)
  • 임계값 (캐시 크기, 타임아웃)
  • 외부 API의 상세 (특정 라이브러리 선택)
  • 경계 조건 (null, 빈 값 처리)

정보 누출(Information Leakage): 같은 설계 결정이 여러 모듈에 흩어진 상태. APoSD가 가장 경계하는 적.

정보 누출 예제

// File1: Parser
class HttpParser {
  public Request parse(String s) {
    String[] lines = s.split("\r\n"); // HTTP 라인 종료
    ...
  }
}

// File2: Serializer
class HttpSerializer {
  public String serialize(Response r) {
    sb.append(headers).append("\r\n"); // 또 \r\n 가정
    ...
  }
}

"HTTP는 \r\n으로 줄을 나눈다"는 결정이 두 파일에 누출됨.
HTTP/2로 바꾸려면 두 곳을 동시에 고쳐야.

→ 해결: 같이 변하는 것은 같이 두라 (저수준 모듈 하나로).

시간적 분해(Temporal Decomposition)의 함정

실행 순서대로 모듈을 나누는 흔한 실수.

// 시간적 분해 — HTTP 서버
class RequestReader   { String read(Socket s); }
class RequestParser   { Request parse(String s); }
class ResponseBuilder { Response build(Result r); }
class ResponseWriter  { void write(Socket s, Response r); }

언뜻 깔끔해 보이지만 "HTTP 프로토콜"이라는 지식이 4곳에 누출됨.

해결: 지식에 따라 분해하라. HttpProtocol 모듈 하나로 묶어라.

일반 목적 모듈이 더 깊다

"지금 필요한 것만" 만들지 마라.

특수 목적

class TextDocument {
  void backspace(Cursor c);
  void deleteSelection();
  void deleteWord();
}

키 입력마다 새 메서드

일반 목적

class TextDocument {
  void delete(Position s, Position e);
  Position positionForBackspace(Cursor c);
}

모든 삭제가 같은 메서드로

"Somewhat general-purpose": 현재 요구는 충족하면서, 미래에도 쓸 수 있을 만큼만 일반적이게.

다른 계층 = 다른 추상화

인접 계층의 메서드가 같은 시그니처면 설계 오류일 수 있다.

// 의심스러운 패턴
class Wrapper {
  public void save(Doc d) {
    inner.save(d);     // 같은 메서드를 그대로 호출
  }
}

단순한 패스스루(pass-through) 메서드는 가치가 없다.
각 계층은 다른 추상화 수준에서 기능을 추가해야 한다.

Ousterhout가 비판하는 흔한 안티패턴: 추상화를 위한 추상화, 계층을 위한 계층.

핵심 격언: Pull Complexity Downwards

"복잡성을 아래로 끌어내려라."
— Ousterhout

한 사람이 어려운 것을 감수하면 N명이 편해진다.

설계 결정에서 누가 복잡성을 짊어질지 고민하라:

  • 모듈 작성자 (1명) vs 사용자 (N명)
  • 당연히 모듈 작성자가 짊어져야
  • API는 단순하게, 구현은 복잡해도 OK

Pull Down 예제 — 설정 처리

복잡성을 위로

int timeout = config.get("timeout");
if (timeout == 0) timeout = 30;
if (timeout < 1) throw ...;
if (timeout > 300) timeout = 300;

호출자가 매번 기본값/검증을 처리

복잡성을 아래로

int timeout = config.getInt(
    "timeout", 30, 1, 300);
// 기본값, 최소, 최대를 한 줄에

모듈이 검증을 처리, 사용자는 단순

사용 지점이 100곳이라면 → 모듈에서 한 번 처리하는 게 100배 이득.

같이 둘 것인가, 쪼갤 것인가?

"코드가 길면 쪼개라"는 단순 규칙은 위험하다. 같이 변하는 것은 같이 두라.

같이 둘 단서

  • 정보를 공유한다
  • 같이 사용된다
  • 인터페이스가 단순해진다
  • 중복이 제거된다

쪼갤 단서

  • 한쪽만 알아도 다른 쪽을 쓸 수 있다
  • 일반 목적 vs 특수 목적의 분리
  • 크기가 너무 커서 한눈에 안 보임
"함수당 2~4줄"의 함정: 자연스러운 연결을 부숴 shallow하게 만들 수 있음.

특수 케이스 제거하기

분기 가득

if (selection == null) {
  selection = new Selection();
}
if (selection.isEmpty()) {
  return;
}
text.delete(selection);

기본값으로 흡수

// Selection이 항상 유효, 비면 delete가 no-op
text.delete(selection);

특수 케이스를 일반 경로로 흡수.

Define errors out of existence: 예외가 생기지 않도록 API를 설계하라.
예: delete는 빈 선택영역도 받아들임. Map.get은 없으면 null/Optional 반환.

일관성(Consistency)

"비슷한 것은 비슷하게 보여야 한다. 다른 것은 분명히 달라야 한다."

일관성은 인지 부하를 극적으로 줄인다.

  • 이름 규칙 (변수, 클래스)
  • 코딩 스타일
  • 디자인 패턴의 일관적 적용
  • 인터페이스 시그니처 (예: 예외 처리 방식)
  • 커밋 메시지 형식
강제 도구를 만들어라: 린터, 포매터, CI 체크.
문서는 잘 안 읽힌다 — 도구가 강제하는 게 가장 확실.

명백함을 위한 설계 (Design for Obvious)

"코드는 명백하게 보여야 한다. 독자가 정신적 추리를 거치지 않게 하라."

좋은 이름, 좋은 주석, 좋은 구조가 명백함을 만든다.

코드가 명백하지 않은 신호:

  • 독자가 "이 변수가 뭐였지?"하고 위로 거슬러 올라간다
  • 리뷰어가 자주 같은 질문을 한다
  • 구현 세부를 알아야 호출법을 이해할 수 있다

반대로 코드 작성자에게 명백하더라도 독자에게 명백하지 않으면 그건 명백하지 않은 것.

좋은 이름의 4가지 기준

  1. 정확한가 (Precise) — 의미를 정확히 전달하는가?
  2. 일관적인가 (Consistent) — 비슷한 개념엔 비슷한 이름?
  3. 충분히 작은가 (Compact) — 짧게 의미를 담는가?
  4. 읽기 쉬운가 (Readable) — 발음/검색 가능?
이름이 안 떠오르면 = 설계가 잘못된 신호
개념이 흐릿하면 이름도 흐릿하다. 이름을 짓다 막히면 모듈 경계를 다시 보라.

Ousterhout는 Martin과 마찬가지로 이름을 매우 중요하게 본다.

핵심 주제: 주석은 필수다

"주석을 적절히 작성하지 않아서 낭비하는 시간이 어마어마하다.
내 개발 시간의 50~80%가 코드를 헤매는 데 쓰이곤 한다."
— John Ousterhout

Martin과의 가장 큰 차이.

Ousterhout이 보는 주석의 가치:

  • 코드로 표현할 수 없는 의도, 추상화, 이유
  • 인터페이스의 동작 명세 (구현이 아닌 사용자 관점)
  • 높은 수준의 설명 (구현은 안 봐도 알 수 있게)
  • 비명백함의 해소 (왜 이렇게 했는가)

주석 우선 작성 (Write Comments First)

인터페이스 주석을 코드보다 먼저 써라.

이점:

  • 주석은 설계 도구 — 추상화를 글로 명확히 함
  • 주석이 어렵다 = 추상화가 잘못됐다는 신호
  • 나중에 쓰려면 귀찮아서 안 씀 → 처음에 써야 잘 씀
  • 리뷰어가 인터페이스를 빨리 검토 가능

Martin: "주석 = 실패" ↔ Ousterhout: "주석 = 설계 도구"
철학의 정반대.

좋은 주석의 종류

종류역할예시
인터페이스사용자가 알아야 할 모든 것"인덱스 i의 요소를 삭제. 0 ≤ i < size"
자료구조 멤버각 필드의 의미"마지막 응답 시각 (UTC)"
구현부"왜" 이렇게 했는가"O(n²) 알고리즘이지만 n이 작아 충분"
크로스모듈여러 곳에 영향 주는 결정"이 ID 형식은 X 모듈도 같은 규칙 사용"

"코드가 말하지 못하는 것을 주석이 말한다."

TDD에 대한 회의

"TDD의 근본 문제는 개발자를 너무 전술적으로 일하게 만든다는 것이다.
개발 단위가 너무 작아 설계 사고를 막는다."
— John Ousterhout

Ousterhout의 입장:

  • 테스트는 가치 있다 — 하지만 TDD 사이클은 너무 잘다
  • 설계는 여러 메서드/클래스 단위에서 일어남
  • "테스트 통과만 위한 최소 코드" = 자주 잘못된 추상화
  • 대안: 먼저 설계하고, 단위 테스트로 검증

Martin과의 두 번째 큰 쟁점.

설계는 두 번 하라 (Design It Twice)

한 가지 설계로 만족하지 마라. 두 개 이상의 근본적으로 다른 접근을 시도하라.

왜?

  • 첫 설계는 거의 항상 최선이 아니다
  • 대안을 비교하면 트레이드오프가 보인다
  • 고민하는 시간 << 잘못된 설계의 비용

"이것 외에 어떤 방법이 가능할까?"를 항상 물어라.

실력 있는 개발자도 이 단계를 건너뛰는 경향이 있다 — 의식적으로 강제하라.

2판의 추가: 코드 리뷰의 가치

2판에서 강조된 새 내용.

  • 리뷰는 버그 찾기보다 설계 개선의 자리
  • "내가 쓴 게 명백한가" 자체 점검의 가장 좋은 기회
  • 주니어는 시니어 코드를 읽어야 빠르게 성장
  • 리뷰어는 "왜?"를 자주 물어 가정을 드러내야
좋은 코드 리뷰 = 좋은 설계 학습 기회.
팀의 디자인 감각은 리뷰에서 만들어진다.

APoSD 요약 — 5문장

  1. 복잡성이 모든 문제의 근원이다.
  2. 깊은 모듈을 만들어 복잡성을 아래로 내려라.
  3. 전략적 사고로 단기 속도와 장기 비용을 저울질하라.
  4. 주석은 설계 도구 — 먼저 쓰고 자주 갱신하라.
  5. 설계는 두 번, 리뷰는 학습으로.
APoSD는 휴리스틱(heuristics)의 책이다.
규칙보다 사고방식, 강요보다 질문. 작아도 밀도 높은 책.

쟁점 1: 함수는 얼마나 작아야 하나?

Martin

"함수의 첫 번째 규칙은 작아야 한다는 것. 두 번째 규칙은 더 작아야 한다는 것."
  • 2~4줄이 이상적
  • 들여쓰기 1~2 레벨
  • "Extract till you drop"

Ousterhout

"작아질수록 분할의 이점은 점점 줄어든다. 결국 사용자가 모든 내부를 알아야 하는 지경에 이른다."
  • 크기보다 인터페이스가 중요
  • 너무 작으면 shallow해짐
  • "분할의 비용"도 있음

함수 크기 — 양쪽 시각

Clean Code 시각

public void pay() {
  for (Employee e : employees)
    payIfNecessary(e);
}
private void payIfNecessary(Employee e) {
  if (e.isPayday())
    calculateAndDeliver(e);
}
private void calculateAndDeliver(Employee e) {
  e.deliverPay(e.calculatePay());
}

각 함수는 한 가지 일

APoSD 시각

public void pay() {
  for (Employee e : employees) {
    if (e.isPayday()) {
      Money pay = e.calculatePay();
      e.deliverPay(pay);
    }
  }
}

한 흐름이 한 번에 보임 — 위↔아래 점프 없음

인지 부하를 중시하면 후자가 더 읽힐 수 있다 — 한 번에 끝까지 따라가짐.

"라자냐 코드"의 위험

Lasagna Code: 얇은 추상화 층이 겹겹이 쌓여, 한 동작을 이해하려면 N개 파일을 열어야 하는 상태.

Hacker News, Lobsters, Reddit에서 Clean Code의 함수 규칙에 대한 가장 흔한 비판.

증상

  • 한 함수가 한 줄 호출만
  • 호출 체인이 5단계 이상
  • 스택 트레이스가 본질을 가림
  • 이름이 점점 길어짐

발생 원인

  • "규칙은 절대"라는 도그마
  • 리팩토링 도구의 남용
  • "함수가 길면 무조건 쪼개라"

균형점: 두 입장의 종합

좋은 함수 = 인지 부하를 줄이는 함수

실무 가이드:

  • 함수가 길어도 한 추상화 수준이면 OK
  • 분할의 결과가 독립적으로 의미를 갖는가? Yes → 분할
  • 분할 후 호출자가 둘 다 알아야 하는가? Yes → 분할 마라
  • "몇 줄"이라는 숫자는 잊고, "한 번에 따라갈 수 있나"로 판단

두 책의 진짜 메시지를 추출하면 같은 지점에 도달한다.

쟁점 2: 주석

Martin: 주석은 실패

"주석을 쓸 때마다 우리는 패배감을 느껴야 한다. 코드가 자명하지 못해 보충했기 때문."
  • 좋은 이름이 주석을 대체
  • 주석은 빠르게 거짓말이 됨
  • 공개 API Javadoc은 예외로 인정, 그 외엔 최소화

Ousterhout: 주석은 필수

"내 시간의 50~80%가 주석이 부족해서 코드를 헤매는 데 쓰인다."
  • 인터페이스는 반드시 주석
  • "왜"를 코드가 못 말함
  • 주석 먼저 쓰기 (설계 도구)

주석 — 동일한 코드, 다른 의견

public List<Employee> findEligible() {
  // 65세 이상이고 시간제 근무자만 복지 자격
  return employees.stream()
    .filter(e -> e.age >= 65 && e.hourly)
    .toList();
}

Martin: 주석 제거

employees.stream()
  .filter(e -> e.isEligibleForFullBenefits())
  .toList();

메서드명이 의도를 말함

Ousterhout: 주석 유지 + 보강

// 복지 자격 = 시간제 + 65세 이상.
// (정책 변경: 2024 HR 가이드라인)

"왜"를 코드가 영영 말 못 함

중간 입장: 주석의 진짜 역할

주석이 답해야 하는 질문MartinOusterhout
이 코드가 무엇을 하는가?코드/이름이 답인터페이스 주석
이 코드가 왜 그렇게 하는가?동의 — 주석동의 — 주석
이 코드를 어떻게 쓰는가?테스트로인터페이스 주석
이 코드의 가정은?assert주석

두 사람 모두 "왜"는 주석. 차이는 "무엇을"과 "어떻게"에서.

실무에서는 둘 다 쓰는 게 답: 좋은 이름 + 인터페이스 주석.

쟁점 3: TDD

Martin: TDD 3법칙

  • 실패하는 테스트 없이 코드 없음
  • 테스트는 컴파일만 되는 정도까지만
  • 실제 코드는 테스트 통과까지만

Red → Green → Refactor

"테스트가 설계를 이끈다"

Ousterhout: 회의

  • 단위가 너무 작다
  • 설계 사고를 막는다
  • "최소 코드"가 잘못된 추상화 양산
  • 리팩토링 단계는 거의 안 일어남

"먼저 설계, 다음 테스트"

TDD — 두 입장의 코드 흐름

Martin (TDD)

  1. 실패 테스트 1줄
  2. 최소 코드 1줄
  3. 테스트 통과
  4. 리팩토링
  5. 다음 테스트…

사이클: 분 단위

Ousterhout (Strategic)

  1. 인터페이스 설계 (주석)
  2. 구현 시도 1
  3. 구현 시도 2 (대안)
  4. 비교, 선택
  5. 테스트로 검증

사이클: 시간/일 단위

TDD가 잘 맞는 영역: 명확한 입출력 (계산기, 변환기). 잘 안 맞는 영역: 시스템 설계, 분산.

쟁점 4: 추상화

Martin — SRP 중심

"한 가지 책임만 갖는 클래스"

  • 책임 = 변경 사유
  • 변경 사유당 모듈 분리
  • 관심사 분리(SoC)
  • SOLID로 의존성 통제

Ousterhout — Deep Module

"단순한 인터페이스, 강력한 구현"

  • 인터페이스/구현 비율
  • 정보 은닉
  • 인지 부하 최소화
  • 지식 누출 방지

같은 코드, 다른 평가

class UserService {
  public User register(String email, String pw) {
    validateEmail(email);
    validatePassword(pw);
    String hash = hashPassword(pw);
    User u = createUser(email, hash);
    sendWelcomeEmail(u);
    auditLog(u);
    return u;
  }
}

Martin

SRP 위반: validate, hash, persist, email, log = 5가지 책임.
→ 5개 클래스로 쪼개라.

Ousterhout

인터페이스 단순 (email, pw → User).
인터페이스는 단순, 구현은 풍부 → 깊은 모듈.

두 가지 다른 가치관

관심사 분리 (SoC)

다른 일은 다른 모듈에서.

  • 이론적으로 깔끔
  • 테스트 단위 명확
  • 위험: 과분할로 shallow

인지 부하 (Cognitive Load)

한 번에 머릿속에 담을 수 있는가.

  • 독자 친화적
  • 실제 변경에 강함
  • 위험: 거대 모듈
현실: 둘 다 필요하다. 책임을 분리하되, 분리된 모듈 각각이 깊어야 한다.

규칙 vs 휴리스틱

Clean Code: 규칙

  • "~해야 한다" 어조
  • 구체적 수치 (2-4줄)
  • "이건 해라, 저건 마라"
  • 주니어가 따라하기 쉬움
  • 도그마화 위험

APoSD: 휴리스틱

  • "~를 고려하라" 어조
  • 판단 기준 (단순한 인터페이스?)
  • "왜"를 더 길게 설명
  • 판단력이 있어야 적용 가능
  • 경험이 필요

→ Clean Code는 주니어 시절, APoSD는 시니어로 가는 길에 더 가치 있다고 평가받음.

같이 만나는 지점

두 책이 의외로 강하게 일치하는 부분.
  • 이름은 매우 중요 — 의미 있고 일관적인 이름
  • 중복 제거 — DRY는 양쪽 다 옹호
  • 복잡성은 점진적 — 매일 작은 정리 (보이스카우트 ↔ Zero Tolerance)
  • 나쁜 설계는 비용 — 단기 속도가 장기 비용
  • 좋은 설계는 학습 — 시간과 의도적 노력 필요
  • 인지 부하를 줄여라 — 표현은 다르지만 본질 같음

AI 도입 후 코드 중복 4배 증가

2억 1100만 줄 분석 (Google, Microsoft, Meta, 엔터프라이즈):

  • 2024년 처음으로 복사/붙여넣기가 리팩토링을 초과
  • 코드 churn 2배 (작성 후 2주 내 되돌림)
  • "이동/수정/삭제" 대신 "추가" 위주의 변경
  • 코딩 속도 55% 향상이지만 유지보수성은 하락

→ AI는 깨끗한 코드를 만들지 않는다 — 빨리 더러운 코드를 만든다.

AI는 같은 실수를 더 빠르게 한다

"Clean Code의 원칙은 AI 코딩 시대에 무관해진 게 아니다 — 더 중요해졌다.
AI가 정확히 Uncle Bob이 경고한 실수들을 하기 때문이다. 더 빠르게, 더 큰 규모로."
  • 중복: AI는 비슷한 코드를 매번 새로 만든다 (DRY 위반)
  • 긴 함수: 한 번에 30~50줄 생성, 책임 섞임
  • 나쁜 이름: result, data, temp 남발
  • 예외 무시: try-catch로 감싸고 빈 블록
  • shallow 모듈: 클래스를 잘게 쪼개 인터페이스만 큼

Clean Code가 AI 시대에 다시 빛나는 이유

  • 명확한 규칙 = AI에게 줄 수 있는 명세
  • 의미 있는 이름 = AI 컨텍스트 이해의 기반
  • 작은 함수 = AI 토큰 효율 + 리뷰 용이
  • SOLID = AI 생성 코드의 구조 검증 기준
  • SRP = AI에게 "한 가지만" 시키는 프롬프트 가이드
Clean Code 규칙은 이제 AI Skills/Rules 파일로 재탄생.
Anthropic Claude Code, Google Antigravity, Cursor의 .rules에 그대로 옮겨짐.

AI에게 Clean Code 가르치기 — Skills

# ~/.claude/skills/clean-code/SKILL.md
---
name: clean-code
description: Apply Clean Code principles before writing
---

When writing functions:
- Keep them small (under 20 lines typically)
- Functions do one thing — extract if multiple verbs in name
- No flag parameters (boolean args that change behavior)
- Max 3 parameters; group into objects if more
- No side effects matching the name doesn't reveal

When naming:
- Intention-revealing (not `data`, `temp`, `obj`)
- Searchable (no single letters except loop counters)
- Avoid encodings (hungarian notation, prefixes)

Clean Code 원칙이 그대로 AI 에이전트의 행동 규약이 된다.

APoSD가 AI에게 더 어려운 이유

AI는 규칙은 따르지만 휴리스틱은 약하다.

  • "깊은 모듈"을 직관적으로 만들지 못함
  • "정보 누출"을 알아채지 못함 — 같은 결정을 곳곳에 복제
  • "전략적 사고"가 결여 — 매번 가장 가까운 패턴 복사
  • "설계 두 번"을 안 함 — 첫 답을 확정
  • "미래 변경"을 고려 못 함 — 단기 정답만
→ AI 시대에 인간이 담당해야 할 영역이 APoSD가 다루는 영역.
Ousterhout의 책은 "AI가 못하는 일"의 매뉴얼이 된다.

AI 시대의 분업

AI가 잘하는 것

  • 구문 작성, 보일러플레이트
  • 규칙 적용 (Clean Code rules)
  • 패턴 매칭, 코드 검색
  • 테스트 케이스 생성
  • 문서/주석 초안
  • 리팩토링 실행

인간이 잘하는 것

  • 모듈 경계 결정 (APoSD)
  • 인터페이스 깊이 판단
  • 전략적 vs 전술적 선택
  • 정보 누출 감지
  • 미래 변경 예측
  • 설계의 "왜"

깊은 모듈 vs AI 인터페이스

흥미로운 역설: AI에게 일을 시키려면 인터페이스가 깊을수록 좋다.

Shallow API + AI

openFile(p, mode, enc, buf, ...)
parseHeader(stream, opts, ...)
processBody(parsed, ctx, ...)

AI가 매번 12개 옵션 조립

Deep API + AI

readDocument(path)

AI도 한 줄로 정확히 호출

깊은 모듈 = 적은 컨텍스트 + 적은 실수. APoSD가 AI 시대에 더 빛난다.

주석 논쟁의 새 국면

AI 시대, 주석의 역할이 변한다.
  • Martin의 주장 약화: AI가 빠르게 주석을 갱신할 수 있음 → "거짓말" 문제 완화
  • Ousterhout의 주장 강화: 주석이 AI에게 의도를 전달하는 채널
  • 인터페이스 주석 = AI를 위한 함수 명세 (자연어 타입 시그니처)
  • "왜" 주석 = AI가 기존 설계 결정을 존중하게 만드는 가이드

결과적으로 APoSD의 "주석 우선" 방식이 AI 협업에 더 잘 맞는다.

AI 코드 리뷰의 새 기준

AI가 만든 코드를 리뷰할 때 던질 질문:

  1. (Clean Code) 함수가 한 가지 일만 하는가?
  2. (Clean Code) 이름이 의도를 드러내는가?
  3. (APoSD) 이 모듈은 깊은가, 얕은가?
  4. (APoSD) 정보가 누출되고 있지 않은가?
  5. (APoSD) 다른 방식의 설계가 가능한가? (Design It Twice)
  6. (공통) 6개월 후의 내가 이걸 이해할 수 있는가?

AI는 1, 2번에 강하다. 3~5번이 인간이 더해야 할 가치.

60/20 법칙 (Anthropic 보고서)

AI 활용 비율 60%, 완전 위임 가능 작업 0~20%.
나머지 40~80%는 인간의 "능동적 감독"이 필요.

"능동적 감독"이란?

  • 설계 결정 → APoSD의 휴리스틱
  • 리뷰 기준 → Clean Code의 규칙 + APoSD의 깊이
  • 리팩토링 방향 → 두 책 모두
  • 기술 부채 인식 → 전략적 프로그래밍

"두 책을 모르고 AI를 부리는 것 = 칼을 모르는 외과의".

AI 시대의 균형 — 한 그림

Clean Code

AI의 입력으로

  • Skills/Rules 파일
  • 명세, 검증 기준
  • 리뷰 체크리스트

APoSD

인간의 도구로

  • 설계 결정
  • 모듈 경계
  • 리뷰의 깊이

AI Agent

실행자

  • 구현
  • 리팩토링 실행
  • 테스트 자동화
인간이 설계하고 AI가 코딩하는 시대: 두 책 모두 새로운 의미를 얻는다.

미래 전망 — 2030년까지

  • 코드 작성의 80%+가 AI 기반이 될 것
  • 하지만 설계 결정은 여전히 인간 영역
  • "Senior" 개발자의 정의가 바뀐다:
    • 코드 잘 짜는 사람 → 설계를 잘 명세하는 사람
    • 구현 능력 → 판단력
  • APoSD의 휴리스틱과 트레이드오프 사고가 차별화 요소
  • Clean Code의 표준화 가능한 규칙은 AI가 흡수
예측: 5년 후 시니어 면접에서 "Deep modules" 개념이 더 자주 나올 것.
PART 5

결론과 실무 권고

9 slides

두 책에서 무엇을 가져갈까?

Clean Code에서

  • 의미 있는 이름의 습관
  • 한 가지 일만 하는 함수
  • SOLID로 의존성 통제
  • 코드 냄새 카탈로그
  • 보이스카우트 규칙
  • F.I.R.S.T. 테스트

APoSD에서

  • 복잡성을 진단하는 안목
  • 깊은 모듈 설계 감각
  • 정보 은닉/누출 분석
  • 전략적 사고방식
  • 주석을 설계 도구로
  • "설계 두 번" 습관

주니어 vs 시니어의 관점

경력먼저 읽을 책왜
1~2년차Clean Code명확한 규칙으로 기초 습관 형성
3~5년차둘 다 / 비교 토론도그마 탈출, 판단력 형성
5년차+APoSD설계 안목, 트레이드오프 사고
리드/아키텍트APoSD 반복독서모듈/시스템 경계 결정

물론 어느 시점에 보든 가치 있다 — 다만 가장 큰 효과의 시점이 다르다.

실무 권고 — 7가지

  1. 이름에 시간을 써라 — 두 책의 공통 1순위
  2. 함수 크기는 "한 추상화 수준"으로 판단 — 줄 수가 아니라
  3. 인터페이스 주석은 반드시 작성 — AI에게도 도움
  4. SOLID는 도그마가 아닌 도구 — 트레이드오프와 함께
  5. 설계는 두 번 시도 — 첫 답을 의심하라
  6. 매일 작은 정리 — 보이스카우트 + Zero Tolerance
  7. AI에게 두 책의 규칙을 주입 — Skills/Rules 활용

추천 학습 순서

  1. Clean Code 1~3장: 깨끗한 코드, 이름, 함수 (1주)
  2. APoSD 1~4장: 복잡성, 모듈 깊이 (1주)
  3. 두 책의 충돌 토론: johnousterhout/aposd-vs-clean-code 정독 (3일)
  4. 본인 코드 리뷰: 최근 PR을 두 관점으로 다시 보기 (1주)
  5. Clean Code SOLID, APoSD Deep Modules 심화 (2주)
  6. AI Skills 작성: 두 책의 원칙을 Claude/Cursor 룰로 (1주)
  7. 팀 코드 리뷰 기준 합의: 두 관점의 균형점 찾기

총 ~6주 코스. 토론 파트너가 있으면 효과 배가.

한국 개발자에게 — 특별히

  • "Clean Code 도그마"에서 한 발 빠져라 — SI 문화의 흔적
  • APoSD의 짧은 분량을 활용 — 출퇴근 1~2주면 1독
  • 영어 원서 권장 — 두 책 모두 번역체가 강함
  • 스터디 추천 — APoSD는 토론에서 진가가 나옴
  • AI 시대를 이끄는 한국 개발자 = 두 책 + AI 도구의 균형
한국 개발자의 강점: 빠른 학습과 실행.
여기에 APoSD의 전략적 사고를 더하면 글로벌 경쟁력.
