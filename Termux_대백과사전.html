이 덱이 다른 점

이 덱의 주제는 이 덱을 만든 기계입니다.

이 덱은 접는 폰의 Termux 안에서, 그 안에 띄운 리눅스 배포판(proot)에서 만들었습니다. 그래서 Termux 를 흉내 낸 예시가 아니라 Termux 자신을 증거로 쓸 수 있습니다 — 패키지 목록, 환경 변수, 링커가 읽는 헤더, API 가 돌려주는 JSON 까지 전부 이 기기에서 실제로 떠 온 것입니다.

원리를 설명할 때는 기억에 기대지 않고 upstream 소스의 줄을 보여 줍니다. 어느 저장소의 어느 커밋, 어느 파일의 몇 번째 줄인지가 배지로 붙어 있습니다.

이 덱의 약속 — 화면의 코드는 전부 실제 파일에서 잘라 왔고, 화면의 출력은 전부 이 기기에서 떴으며, 화면의 사실은 전부 출처가 있습니다. 출처를 못 찾은 문장은 미확인 표시를 달고 나옵니다.

이 책을 읽는 법

한 장에 한 가지만 담았습니다. 모르는 낱말이 나오면 17부 용어집을 보십시오 — 낱말마다 "처음 나온 자리" 로 가는 화살표가 붙어 있습니다.

  • 막혔다면 15부 문제 해결 사전에서 오류 문구로 찾으십시오.

  • 검은 바탕의 블록은 이 기기에서 실제로 뜬 출력입니다.
  • 열다섯 장쯤마다 퀴즈가 한 장씩 나옵니다. 답은 단추를 누르면 펼쳐집니다.
  • 이 문서는 자기완결형입니다 — 외부 스크립트·글꼴·이미지를 하나도 부르지 않습니다.

설명용

소스 배지 읽는 법

원리를 설명하는 장에는 청록색 둥근 배지가 붙습니다. 배지 글자는 세 부분입니다.

  • 저장소 이름 — 예컨대 termux-app, termux-exec, termux-packages.
  • @ 뒤의 일곱 글자 — 커밋 해시의 앞부분입니다. 이 덱이 인용한 순간의 커밋을 못 박습니다.
  • 경로와 줄 — 그 커밋에서 몇 번째 줄부터 몇 번째 줄까지인지.

같은 장의 코드 블록이 바로 그 줄입니다. upstream 이 나중에 코드를 바꿔도 이 덱이 보여 주는 줄은 배지의 커밋에 그대로 남아 있습니다.

배지는 조립기만 만듭니다 — 저장소가 핀 목록에 없거나 커밋이 핀과 다르거나 그 줄이 그 커밋에 없으면, 덱이 만들어지지 않습니다.
설명용

캡처의 두 종류 — 고정과 스냅샷

이 기기에서 뜬 출력은 둘로 나눠 다룹니다.

종류무엇어떻게 믿나
고정 패키지 목록, 파일이 어느 패키지 것인지, 소스 발췌, 종료 코드, 실험 프로그램의 출력 세 번 떠서 바이트까지 같은 것만 싣습니다
스냅샷 배터리, 센서, 디스크 사용량, 걸린 시간, 미러의 응답 한 번 뜨고 날짜를 박아 얼립니다. 조용히 다시 뜨지 않습니다

스냅샷 캡처 위에는 "이 기기 · 연-월 캡처" 도장이 자동으로 붙습니다. 그 숫자는 Termux 의 성질이 아니라 그날 이 폰의 상태라는 뜻입니다. 걸린 시간은 본문에 적지 않고 스냅샷 표로만 보여 줍니다.

설명용

두 쪽의 프롬프트 — $ 와 #

이 덱의 캡처는 두 세계에서 뜹니다. 어느 쪽인지 헷갈리지 않도록 프롬프트 기호를 나눴습니다.

기호어디서무엇을 보여 주나
$Termux 그 자체 안드로이드 앱의 사용자로 도는 Termux 의 셸과 패키지들
#proot 안의 리눅스 배포판 이 덱을 만든 작업 공간. 가짜 루트라 기호가 # 입니다

캡처 위 회색 줄의 오른쪽 끝에도 Termux $ 인지 proot # 인지가 적힙니다. proot 쪽 캡처는 그 장이 proot 를 다룰 때만 씁니다 — proot 에서 뜬 것을 Termux 의 모습처럼 보여 주지 않습니다.

설명용

캡처에서 지운 것 — 사용자의 폰이니까

이 덱의 캡처는 누군가의 일상용 폰에서 떴습니다. 새면 되돌릴 수 없는 것은 사람 눈이 아니라 빌드 검사가 막습니다.

  • 전화번호·기기 일련번호류·MAC 주소 — 있으면 빌드가 멈춥니다.
  • Wi-Fi 이름은 <ssid>, 공인 IP 주소는 <ip> 로 바꿉니다.
  • 위치·연락처·전자우편 주소 — 있으면 빌드가 멈춥니다.
  • 문자·통화 기록·연락처·위치·카메라·마이크를 읽는 API 명령은 한 번도 실행하지 않습니다. 그 출력 모양은 소스와 문서에서 인용합니다.

규칙의 전문과 검사 코드는 14부와 부록에 있습니다.

설명용

인용과 라이선스

원리 장의 코드 발췌는 upstream 저장소의 것입니다. 각 발췌는 45줄을 넘지 않고, 장마다 저장소·커밋·경로·줄을 배지로 밝힙니다. 가르치려는 목적의 짧은 인용이며, 출처를 밝혀 인용하는 관행 안에 있다고 판단했습니다.

저장소마다의 라이선스는 핀 목록(termux/data/repos.tsv)에 함께 적어 두고, 부록에 그 표를 그대로 싣습니다. 이 덱이 새로 짠 코드(termux/ 아래의 도구·실험)는 부록에 전문을 싣습니다.

3부

안드로이드 위의 리눅스

리눅스 커널 위에 있지만 리눅스 배포판은 아닌 곳

Termux 를 이해하는 열쇠는 "Termux 는 무엇인가" 보다 "Termux 가 어디에 사는가" 입니다. Termux 는 안드로이드 앱입니다. 그래서 안드로이드가 모든 앱에 거는 규칙을 그대로 받습니다. 이 부는 그 규칙을 하나씩 짚습니다 — 커널, 앱마다의 uid, 앱 데이터 디렉터리, C 라이브러리, SELinux, 권한, 저장소.

이 부의 캡처는 대부분 proot 안에서 뜬 것입니다. proot 가 꾸미는 값(uid·커널 이름)과 꾸미지 못하는 값(보조 그룹·파일)을 가려 읽는 법도 함께 봅니다.

1장

커널은 리눅스다

안드로이드의 맨 아래에는 리눅스 커널이 있습니다. Termux 가 돌리는 프로그램은 그 커널에 직접 시스템 호출을 합니다. 가상 머신도 에뮬레이터도 없습니다.

설명용

에뮬레이션이 아니다

termux-packages 위키의 실행 환경 문서는 첫 문단에서 이렇게 못 박습니다: Termux 는 프로그램을 안드로이드 위에서 네이티브로 실행하며, 에뮬레이션이나 컨테이너(docker·VM·chroot·proot)를 쓰지 않고, 안드로이드의 커널을 그대로 쓰며, 따로 만든 커널이 없습니다. 프로그램은 안드로이드 NDK 로 컴파일합니다.

위키의 "Getting started" 도 같은 말을 합니다 — Termux 는 가상 머신도, 에뮬레이션·시뮬레이션 환경도 아니며, 모든 패키지는 NDK 로 교차 컴파일하고 호환성 패치만 더했다고.

출처: termux-packages 위키 Termux-execution-environment 1.1 절 · wiki.termux.com Getting started 1 절 (주장 대장)

2장

앱마다 uid 하나

안드로이드는 리눅스의 사용자 개념을 "사람" 이 아니라 "앱" 에 씁니다. 앱을 설치할 때마다 새 uid 가 하나 생기고, 그 앱의 프로세스는 전부 그 uid 로 돕니다.

앱마다 uid 와 데이터 디렉터리가 하나씩 — 커널이 그 경계를 지킨다

설명용

앱 샌드박스

AOSP 의 보안 문서는 앱 샌드박스를 이렇게 설명합니다.

  • 안드로이드는 앱마다 고유한 uid 를 주고, 그 앱을 제 프로세스에서 돌립니다.
  • 그 uid 로 커널 수준의 샌드박스를 만듭니다. 앱 A 가 앱 B 의 데이터를 읽으려 하면 커널이 막습니다.
  • 샌드박스는 커널 안에 있으므로 자바 코드든 네이티브 코드든 똑같이 적용됩니다.
  • 제대로 설정된 기기에서 샌드박스를 벗어나려면 대개 커널 자체를 뚫어야 합니다.

Termux 가 돌리는 bash·python·gcc 도 "Termux 앱의 네이티브 코드" 일 뿐입니다. 예외가 없습니다.

이 기기 캡처

u0_a123 이라는 이름은 어디서 오나

안드로이드에는 /etc/passwd 가 없습니다. 이름은 bionic 이 uid 를 보고 계산합니다. bionic 의 grp_pwd.cpp 주석이 규칙을 적어 둡니다.

이름번호
u0_a12340 × 100000 + 10000 + 1234
u0_a1234_cache0 × 100000 + 20000 + 1234 (그룹 이름만)
all_a12340 × 100000 + 50000 + 1234 (그룹 이름만)
u1_system1 × 100000 + system(1000)

u0 의 0 은 안드로이드 사용자(프로필) 번호, a 는 app 입니다. 다른 사용자 번호로 돌면 그 번호가 u 뒤에 붙습니다 — 주석에는 u2_i1000 같은 예가 있습니다.

3장

앱 데이터 디렉터리

uid 가 앱마다 하나이듯, 앱이 마음대로 쓸 수 있는 디렉터리도 앱마다 하나입니다. Termux 의 "리눅스 전체" 가 바로 그 안에 삽니다.

설명용

앱 전용 내부 저장소

안드로이드 개발자 문서가 말하는 앱 전용 저장소의 성질은 셋입니다.

  • 다른 앱은 이 디렉터리에 접근할 수 없습니다(시스템이 막습니다).
  • Android 10(API 29)부터 이 디렉터리는 암호화됩니다.
  • 앱을 지우면 이 안의 파일도 함께 지워집니다.

세 번째가 Termux 사용자에게 가장 중요합니다. Termux 를 지우는 순간 $PREFIX 와 $HOME 이 통째로 사라집니다. 백업은 10부에서 다룹니다.

Termux 는 단일 사용자다

샌드박스의 규칙이 그대로 나타나는 곳입니다. Termux 안의 모든 것은 Termux 앱의 uid 하나로 돕니다.

  • 사용자 이름은 u0_a231 같은 모양이고 바꿀 수 없습니다 — uid 에서 계산되기 때문입니다.
  • 패키지는(루트 전용을 빼고) 다중 사용자·setuid·setgid 기능을 떼어 내도록 고쳐 짓습니다.
  • 서버 패키지의 기본 포트도 바꿨습니다: ftpd 8021, httpd 8080, sshd 8022.

포트를 바꾼 까닭은 8부의 주제입니다 — 앱은 1024 미만 포트를 마음대로 열 수 없습니다.

4장

bionic 과 glibc — 같은 소스, 다른 libc

리눅스 배포판의 C 라이브러리는 대개 glibc 입니다. 안드로이드의 C 라이브러리는 bionic 입니다. Termux 의 모든 프로그램은 bionic 에 링크됩니다. 같은 C 소스를 두 번 지어 차이를 봅니다.

설명용

Termux 는 bionic 을 쓴다

위키 "Differences from Linux" 2 절의 설명입니다.

  • 안드로이드와 가장 잘 맞고 별도의 툴체인을 관리하지 않으려고, 모든 패키지를 안드로이드 NDK로 컴파일합니다.
  • 그 결과물은 시스템의 bionic(/system/lib64 의 libc.so·libm.so·libdl.so)에 링크됩니다.
  • 그래서 리눅스 배포판의 프로그램을 복사해 오면 돌지 않습니다 — 링커가 있어야 할 곳(/lib)에 없고, libc 의 ABI 가 다릅니다.

6장

SELinux 와 seccomp — uid 뒤의 두 겹

uid 는 첫 번째 벽일 뿐입니다. 안드로이드는 그 뒤에 두 겹을 더 둡니다. 하나는 "무엇에 접근하나" 를 보는 SELinux, 다른 하나는 "어떤 시스템 호출을 부르나" 를 보는 seccomp 입니다.

설명용

SELinux — root 도 따르는 규칙

  • 안드로이드는 SELinux 로 모든 프로세스에 강제 접근 제어(MAC)를 겁니다. root 권한으로 도는 프로세스도 예외가 아닙니다.
  • 기본은 거부입니다. 명시적으로 허락하지 않은 것은 전부 막힙니다.
  • 안드로이드는 enforcing 모드로 나옵니다 — 거부를 기록만 하는 것이 아니라 실제로 막습니다.
  • Termux 위키는 Android 14 에 파일 문맥 형식이 92개쯤 있다고 적습니다. /system/bin 의 실행 파일마다 다른 문맥이 붙어, 앱이 부를 수 있는 것과 없는 것이 갈립니다.

출처: source.android.com "Security-Enhanced Linux in Android" 1 절 · 위키 Termux-execution-environment 1.4.1

문서 근거

seccomp — 부를 수 있는 시스템 호출의 목록

안드로이드 개발자 블로그의 설명입니다: Android O 부터 zygote 에 seccomp 필터 하나를 걸어, zygote 에서 갈라져 나오는 모든 앱이 그 필터를 물려받습니다. 쓰지 않는 시스템 호출을 앱이 부르지 못하게 해, 악성 앱이 그 호출의 허점을 이용할 길을 없앱니다.

Termux 위키는 그 결과 하나를 적어 둡니다 — 루트가 없는 Android 8 이상에서는 seccomp 필터 때문에 정적으로 링크한 프로그램이 돌지 않을 수 있습니다. 리눅스 배포판용 정적 바이너리를 가져와도 안전한 우회가 아닌 까닭입니다.

7장

Zygote 와 앱 프로세스

Termux 의 셸은 누가 낳았을까요. 거슬러 올라가면 안드로이드의 모든 앱이 공유하는 조상, Zygote 가 나옵니다.

설명용

모든 앱의 뿌리

  • Zygote 는 같은 ABI 의 모든 시스템·앱 프로세스의 뿌리인 프로세스입니다.
  • 안드로이드가 켜질 때 init 데몬이 Zygote 를 띄웁니다.
  • 앱이 프로세스를 필요로 하면 system server 가 유닉스 소켓으로 Zygote 에 부탁하고, Zygote 가 fork 한 뒤 pid·cgroup 따위를 바꿔 앱의 프로세스로 만듭니다.

그래서 앞 장의 seccomp 필터를 Zygote 에 한 번 걸면 모든 앱에 걸립니다.

출처: source.android.com "About the Zygote processes" 1 절

문서 근거

Termux 의 프로세스 나무

  • 안드로이드는 Termux 에게 주 프로세스 하나(이름 com.termux)만 만들어 줍니다.
  • 터미널 세션(TermuxSession)은 그 프로세스가 execvp() 로, 백그라운드 작업(TermuxTask)은 Runtime.exec() 로 자식을 만들어 돌립니다.
  • 세션 안의 bash 가 다시 자식을 낳습니다 — 우리가 치는 명령 전부입니다.
  • sshd·crond 처럼 스스로 데몬이 되는 프로그램은 부모가 init(pid 1)으로 바뀌어 앱 프로세스에서 떨어지고, 위키 표현으로 "더 쉽게 죽습니다".

안드로이드 12 부터 이 자식들을 세어 죽이는 규칙이 생겼습니다 — 팬텀 프로세스(8부).

PTY — 셸과 화면을 잇는 가짜 터미널

셸은 자기가 진짜 터미널에 붙어 있다고 믿어야 줄 편집과 작업 제어를 합니다. 리눅스는 그 믿음을 위해 의사 터미널(PTY)을 줍니다. 한쪽 끝(master)은 앱이, 다른 끝(slave)은 셸이 잡습니다. Termux 는 이 일을 C 코드 한 함수로 합니다.

안드로이드는 앱 데이터 디렉터리를 /data/user/<사용자>/<패키지> 로 줍니다. 주 사용자(0)의 경로가 /data/data/com.termux 입니다(옛 판에서는 링크, 요즘은 바인드 마운트).

위키에 따르면 Termux 앱은 주 사용자에만 설치할 수 있습니다 — 패키지가 /data/data/com.termux 를 전제로 지어졌기 때문입니다. 두 번째 사용자나 업무용 프로필에서는 그 경로가 달라져 바이너리의 박힌 경로와 어긋납니다.

출처: 위키 Termux-file-system-layout 1.3.1

문서 근거

uid 계산식 — 3부의 추론을 위키가 확인한다

위키는 앱 uid 를 이렇게 계산한다고 적습니다.

uid = 사용자 번호 × 100000 + 10000 + 앱 번호
  • 사용자 0, 앱 번호 160 → 10160, 이름 u0_a160
  • 사용자 10, 앱 번호 160 → 1010160, 이름 u10_a160

보조 사용자와 프로필의 번호는 10 부터 시작한다고도 적습니다. 3부에서 이 기기의 보조 그룹을 보고 앱 번호 123 을 짐작한 것이 이 식 그대로입니다.

설명용

리눅스의 경로, 안드로이드의 경로

termux-exec 의 기술 문서가 문제를 정리합니다.

  • 많은 리눅스 프로그램이 루트가 / 이고 시스템 바이너리가 /bin·/usr/bin 에 있다고 가정합니다. 셔뱅의 해석기도 /bin/sh·/usr/bin/env 입니다.

termux-packages 로 짓는 패키지는 소스의 경로를 고쳐 짓습니다(6부). 문제는 사용자가 인터넷에서 받거나 직접 쓴 스크립트입니다.

termux-exec — execve 를 가로채는 라이브러리

A. login 이 걸어 둔 termux-exec 가 execve() 를 가로채 해석기 경로 /usr/bin/python3 를 termuxPrefixPath() 로 $PREFIX/bin/python3 로 바꿨기 때문입니다. LD_PRELOAD 를 빼면 커널이 /usr/bin/python3 를 그대로 열려다 "No such file or directory" 로 실패합니다.

5장

W^X — 앱 데이터의 파일을 실행하지 말라

셔뱅보다 훨씬 큰 벽이 Android 10 에서 생겼습니다. "쓸 수 있는 곳의 코드는 실행하지 않는다"(W^X). Termux 의 모든 것은 쓸 수 있는 곳, 앱 데이터 안에 있습니다.

설명용

개발자 문서의 한 문단

Android 10 의 동작 변경 문서 "Removed execute permission for app home directory" 절입니다.

  • 쓸 수 있는 앱 홈 디렉터리의 파일을 실행하는 것은 W^X 위반이다. 앱은 APK 안에 든 바이너리만 실어야 한다.
  • Android 10 을 target 하는 신뢰되지 않은 앱은 앱 홈 디렉터리의 파일에 execve() 를 직접 부를 수 없다.

Termux 의 bash·python·gcc 는 전부 "앱 홈 디렉터리의 파일" 입니다.

출처: developer.android.com Android 10 behavior changes 1.3 절

문서 근거

정책은 SELinux 에 있다

막는 것은 커널이 아니라 SELinux 정책입니다. Android-Docs 가 인용한 AOSP 의 정책 파일:

  • app_neverallows.te — 모든 신뢰되지 않은 앱에 앱 데이터 파일의 execute_no_trans 를 금지한다. 단 untrusted_app_25·untrusted_app_27 은 뺀다 — 주석: "호환을 위해 targetApi 28 이하는 허용".
  • untrusted_app_27.te — targetApi 26·27·28 앱에 앱 홈 디렉터리 파일의 exec 를 허용한다.
  • 막히는 것은 exec() 뿐입니다. dlopen()(mmap 으로 실행 가능하게 싣기)은 targetSdk 29 이상에서도 됩니다.

링커 실행의 대가

  1. LD_PRELOAD 가 Termux 로 들어오는 모든 입구(sshd 로 붙는 것까지)에서 걸려 있어야 합니다.
  2. 실행 파일이 /system/bin/linker64 로 보여, /proc/self/exe 를 읽는 프로그램은 엉뚱한 이름을 봅니다 — 그래서 TERMUX_EXEC__PROC_SELF_EXE 를 내보냅니다.
  3. 정적으로 링크한 바이너리는 안 됩니다.
  4. execve() 시스템 호출을 직접 부르는 프로그램은 고치거나 proot 로 돌려야 합니다.
  5. Google Play 정책과 맞지 않습니다 — 스토어 밖에서 받은(또는 기기에서 컴파일한) 코드를 실행하니까요.

def ar_members(data):
    """[(이름, 바이트)]. ar 머리는 60바이트, 몸통은 짝수로 맞춘다."""
    if not data.startswith(b'!<arch>\n'):
        raise ValueError('ar 묶음이 아니다(.deb 가 아니다)')
    out, at = [], 8
    while at < len(data):
        head = data[at:at + 60]
        if len(head) < 60 or head[58:60] != b'`\n':
            raise ValueError('ar 머리가 망가졌다 (%d 바이트째)' % at)
        name = head[:16].decode('ascii').strip().rstrip('/')
        size = int(head[48:58].decode('ascii').strip())
        body = data[at + 60:at + 60 + size]
        if len(body) < size:
            raise ValueError('ar 멤버 %s 가 잘렸다' % name)
        out.append((name, body))
        at += 60 + size + (size % 2)
    return out

1장

proot 는 무엇을 흉내 내나

proot 매뉴얼의 첫 문장: "PRoot is a user-space implementation of chroot, mount --bind, and binfmt_misc." 셋 다 원래 루트가 있어야 하는 기능입니다.

원래 기능하는 일proot 의 옵션
chroot어떤 디렉터리를 새 / 로-r / --rootfs
mount --bind바깥 경로를 안쪽 자리에 붙이기-b / --bind

매뉴얼은 이어서 말합니다 — 기술적으로는 ptrace, "모든 리눅스 커널에 있는 권한 없는 시스템 호출" 에 기댄다고. 손님(guest) 프로그램이 커널에 하는 요청을 proot 가 번역해서 호스트 커널에 넘깁니다.

문서

root 처럼 보일 뿐이다

Termux 위키의 PRoot 문서가 굵게 적어 둔 경고입니다: proot 는 시스템 호출의 인자와 반환값을 꾸며 프로그램이 root 로 도는 것처럼 보이게 할 수 있지만, 진짜 권한 상승은 전혀 주지 않는다. 커널이나 하드웨어 상태를 바꾸려는 프로그램은 동작하지 않는다.

매뉴얼의 -0(--root-id) 설명도 같습니다: 패키지 관리자처럼 "기술적 이유 없이" root 를 요구하는 프로그램을 위해 신원을 꾸미고, 소유자 바꾸기 같은 일이 성공한 척 합니다. 그리고 "fakeroot 에 비하면 꽤 제한적" 이라고 덧붙입니다. 3부에서 본 대로 이 세션의 id 는 0 이지만, 보조 그룹과 SELinux 문맥은 진짜 앱의 것이었습니다.

출처: 위키 PRoot(revid 6573) · proot manual.txt -0·-i

static int add_trace_syscall(struct sock_fprog *program, word_t syscall, int flag)
{
	int status;

	/* Sanity check.  */
	if (syscall > UINT32_MAX)
		return -ERANGE;

	#define LENGTH_TRACE_SYSCALL 2
	struct sock_filter statements[LENGTH_TRACE_SYSCALL] = {
		/* Compare the accumulator with the expected syscall:
		 * skip the next statement if not equal.  */
		BPF_JUMP(BPF_JMP + BPF_JEQ + BPF_K, syscall, 0, 1),

		/* Notify the tracer.  */
		BPF_STMT(BPF_RET + BPF_K, SECCOMP_RET_TRACE + flag)
	};

	DEBUG_FILTER("FILTER:     trace if syscall == %ld\n", syscall);

	status = add_statements(program, LENGTH_TRACE_SYSCALL, statements);
	if (status < 0)
		return status;

	return 0;

# Architecture: Supplies fake /proc and /sys content that proot bind-mounts
# read-only into the container. Android restricts or blocks several /proc
# files; providing static replacements ensures distro tools that read them
# (top, htop, etc.) work correctly. The fake files live under
# containers/<name>/sysdata/ so they are removed together with the container.
#
# That directory is guest-writable: on Termux it sits under $TERMUX_PREFIX,
# which is bound read-write into every non-isolated container, so a session
# can replace any entry here between runs. Every name below is therefore
# addressed as (directory fd, entry name) with O_NOFOLLOW, never as a path:
# os.path.exists() plus open(path, "w") followed a planted symlink and
# created -- or, for a name whose target already existed, silently skipped
# -- a host file, os.makedirs(exist_ok=True) accepted one in place of
# sys_empty, and os.chmod() applied 0700 to whatever it led to. The bind
# arguments are just as bad the other way round: proot mounts what the name
# resolves to, so a symlinked `loadavg` would have handed the guest a host
# file as /proc/loadavg. An entry that is not of the type this module wrote
# is dropped and remade -- nothing else writes here, so nothing legitimate
# is lost -- and one that cannot be validated is left unbound rather than
# followed.
#
# "The type this module wrote" has to include the link count, because a
# hardlink is a regular file: it *is* another file, under a second name,
# and O_NOFOLLOW has nothing to refuse. A session that unlinks sysdata/
# loadavg and links a host file into its place leaves an entry every later
# session accepts as its own -- setup_fake_sysdata() keeps it, and
# fake_sysdata_bindings() names it as the source proot mounts at
# /proc/loadavg, where the guest can read *and write* it, since proot has
# no read-only bind. That is the persistent case this module exists to
# rule out, so a file this module wrote is one with exactly one link, and
# anything else is dropped and written again.

A. proot-distro 가 sysdata/uptime 이라는 고정 파일을 /proc/uptime 자리에 붙여 두었기 때문입니다(3장 명령줄). 진짜 값은 그 바인드 밖, 곧 네이티브 Termux 에서 읽어야 합니다 — 이 덱이 기기 정보를 tools/native_facts.sh 로 따로 모은 것과 같은 이유입니다.
