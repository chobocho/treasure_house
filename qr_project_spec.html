SECTION 00

프로젝트 개요

왜 직접 만드는가

qrcode, segno 같은 검증된 라이브러리를 두고 직접 만드는 이유는 QR 코드 안에 숨겨진 아름다운 수학을 손에 익히기 위해서다. 갈루아 필드, BCH 코드, Reed-Solomon, 그리고 1994년 덴소웨이브(토요타 계열 덴소)가 자동차 부품 추적용으로 설계한 이 코드가 어떻게 일부가 가려져도 멀쩡히 읽히는지 이해하는 것이 진짜 목적이다.

최종 산출물

  • qrgen.py — 단일 파일, 외부 의존성 없음 (표준 라이브러리만)
  • 지원: Version 1~7, Byte 모드, EC Level L/M/Q/H, 마스크 자동 선택
  • 출력: ASCII 터미널 + PGM + BMP(1비트) 이미지 (외부 그래픽 라이브러리 없이)
  • 단위 테스트 파일 test_qrgen.py (Section 06의 10개 테스트)
  • 테스트: 실제 QR 스캐너 앱(갤럭시 카메라 등)으로 디코드 검증

금지 사항

외부 QR 라이브러리 사용 금지. qrcode, segno, pyqrcode 등 어떤 QR 관련 패키지도 import 하지 않는다. 이미지 저장은 PGM(Portable GrayMap) 포맷을 직접 바이트 단위로 작성한다. 유일하게 허용되는 것은 Python 표준 라이브러리뿐.

SECTION 02

Reed-Solomon 에러 정정 — 고등학생도 이해하는 버전

QR 코드가 일부 가려지거나 더러워져도 읽히는 비결이 바로 이 Reed-Solomon이다. 개념부터 천천히 가보자.

1단계 : "점을 알면 곡선을 알 수 있다"

고등학교에서 배운 사실 하나. 서로 다른 두 점이 있으면 직선 하나가 정해진다. 세 점이 있으면 2차 곡선 하나가 정해진다. n+1개의 점이 있으면 n차 다항식이 유일하게 정해진다.

핵심 아이디어

보내고 싶은 데이터가 3개의 숫자 (a, b, c)라고 하자. 이것을 그냥 보내는 대신, 이걸 계수로 가진 다항식을 만든다:

f(x) = a·x² + b·x + c

그리고 이 다항식의 값을 5개의 서로 다른 x 값에서 계산해서 보낸다. f(1), f(2), f(3), f(4), f(5) 이렇게 5개를 받는다.

5개 중에 2개가 중간에 사라져도, 나머지 3개만 있으면 원래 2차 다항식을 복원할 수 있다. 복원만 되면 a, b, c는 그냥 계수니까 바로 읽어낼 수 있다.

구체 예시 — 데이터 (1, 2, 3)을 보낸다고 하자

이걸 다항식 f(x) = 1·x² + 2·x + 3으로 만들고, 5개 점에서 값을 계산한다.

1단계 : "점을 알면 곡선을 알 수 있다" 계속
f(1)= 1·1 + 2·1 + 3 = 6
f(2)= 1·4 + 2·2 + 3 = 11
f(3)= 1·9 + 2·3 + 3 = 18
f(4)= 1·16 + 2·4 + 3 = 27
f(5)= 1·25 + 2·5 + 3 = 38
→ 전송: [6, 11, 18, 27, 38]

이제 중간에 2개가 사라졌다고 하자. 수신측이 [6, _, 18, _, 38]만 받았다. 여기서 살아남은 점 3개 (1, 6), (3, 18), (5, 38)만으로 라그랑주 보간법을 돌리면 원래 2차 다항식이 정확히 복원된다. (정식 교육과정엔 없지만, "n+1개 점이 n차 다항식을 유일하게 결정한다"는 사실을 식으로 옮긴 것뿐이라 고등 수학 지식만으로 충분히 이해할 수 있다.)

복원된 다항식의 계수를 읽으면 (1, 2, 3). 원래 데이터다. 데이터 3개를 보내려고 5개를 보내면, 2개가 손실돼도 복원 가능 — 이게 Reed-Solomon의 본질이다.

2단계 : 그런데 왜 갈루아 필드(GF)가 필요한가?

위 아이디어를 그냥 일반 숫자(실수)로 하면 문제가 생긴다. f(1000)은 엄청 큰 숫자가 되고, 부동소수점 오차도 생긴다. 컴퓨터는 0~255 범위의 바이트로 데이터를 다루는데, 다항식 계산 결과가 이 범위를 벗어나면 곤란하다.

그래서 수학자들은 0~255 안에서만 사칙연산이 닫혀 있는 특수한 수 체계를 만들었다. 이것이 갈루아 필드 GF(256)다. 20살에 결투로 죽은 천재 수학자 갈루아의 이름을 땄다.

GF(256)의 마법 — 덧셈은 그냥 XOR

놀랍게도 GF(256)에서는 덧셈 = XOR이다. 진짜로. 음수가 없고, 빼기도 똑같이 XOR이다 (자기 자신과 XOR하면 0이 되니까 덧셈의 역원이 자기자신).

5 + 7 = 5 XOR 7 = 2 // 0b0101 ⊕ 0b0111 = 0b0010
100 + 200 = 100 XOR 200 = 172 // 범위 안에서 닫힘!
5 - 7 = 5 + 7 = 2 // 빼기도 XOR (음수 없음)
7 - 7 = 7 XOR 7 = 0 // 자기 자신과 XOR = 0
2단계 : 그런데 왜 갈루아 필드(GF)가 필요한가? 계속

곱셈은 좀 더 정교하다 — log/exp 트릭

GF(256)에서 모든 0이 아닌 수는 원시원소 α의 거듭제곱으로 표현할 수 있다. α를 2로 잡으면, α⁰=1, α¹=2, α²=4, α³=8, α⁴=16, α⁵=32, α⁶=64, α⁷=128까지는 그냥 2의 거듭제곱이다.

문제는 α⁸ = 256이 되면서 1바이트(0~255)를 넘어버린다는 점. 이때 특별한 다항식 x⁸ + x⁴ + x³ + x² + 1 (16진수 0x11D, 이진수 0b100011101)로 XOR해서 줄인다.

α⁷= 128 = 0b10000000
α⁸= 128 × 2 = 256 = 0b100000000 // 9비트, 오버플로!
0b100000000 XOR 0x11D
= 0b100000000 XOR 0b100011101
결과= 0b00011101 = 29 // GF에서 α⁸ = 29
2단계 : 그런데 왜 갈루아 필드(GF)가 필요한가? 계속

이렇게 계속 거듭제곱하면 α¹부터 α²⁵⁵까지 255개의 0이 아닌 모든 값이 한 번씩 나타난다. 이 표가 바로 우리가 만든 GF_EXP다.

그 결과 — 곱셈이 덧셈으로 변신

α의 거듭제곱으로 표현하면 곱셈이 지수의 덧셈이 된다. 학교에서 배운 지수법칙 그대로.

αi × αj = α(i+j) mod 255

예: 5 × 7을 GF(256)에서 계산해보자.

표 찾기log(5) = 50, log(7) = 198 // 즉 α⁵⁰ = 5, α¹⁹⁸ = 7
더하기50 + 198 = 248
표 찾기α²⁴⁸ = 27
결론5 × 7 = 27 in GF(256) // 일반 산술이면 35인데 GF에서는 27
2단계 : 그런데 왜 갈루아 필드(GF)가 필요한가? 계속

왜 mod 255인가? 왜 mod 256이 아니고?

α의 거듭제곱은 α¹부터 α²⁵⁵까지 255번 만에 한 바퀴 돈다 (α²⁵⁵ = 1 = α⁰). 0은 거듭제곱으로 표현 안 되니까 따로 처리한다. 그래서 mod 255다.

그리고 우리 코드는 GF_EXP를 512개로 확장해서 mod 연산 자체를 제거했다. i+j가 최대 254+254=508이라 테이블이 512개면 충분.

3단계 : 실전 — 다항식 나눗셈으로 패리티 만들기

이론은 "점에서 다항식 복원"이지만, 실제로 부호화할 땐 다항식 나눗셈의 나머지를 패리티로 사용한다. 둘이 수학적으로 동치라는 게 핵심 정리.

  1. 데이터 다항식 D(x)를 만든다 (데이터 바이트를 계수로)
  2. 생성다항식 g(x) = (x-α⁰)(x-α¹)···(x-α^(t-1))을 만든다. t는 패리티 개수.
  3. D(x)·xᵗ ÷ g(x)의 나머지를 계산한다 → 이것이 패리티
  4. 최종 전송: [데이터][패리티]

예시 — 데이터 [5, 3]에 2개의 패리티 붙이기

데이터가 2바이트 [5, 3]이고 패리티 2개(t=2)를 만든다고 하자. 먼저 생성다항식부터.

3단계 : 실전 — 다항식 나눗셈으로 패리티 만들기 계속
g(x) = (x - α⁰)(x - α¹) — GF에서 뺄셈=덧셈이므로 (x + 1)(x + 2)와 같음
전개g(x) = x² + (1+2)x + (1·2) = x² + 3x + 2 // GF에서 1+2 = 1 XOR 2 = 3
계수g = [1, 3, 2]

이제 데이터 다항식 D(x) = 5x + 3에 x²을 곱한 5x³ + 3x²을 g(x) = x² + 3x + 2로 나눈다. 일반 다항식 나눗셈과 똑같지만, 모든 연산이 GF에서 이루어진다는 점만 다르다.

3단계 : 실전 — 다항식 나눗셈으로 패리티 만들기 계속
[1단계] 최고차항 5x³을 g의 최고차항 x²로 나누면 5x
5x · g(x) = 5x · (x² + 3x + 2)
= 5x³ + (5×3)x² + (5×2)x = 5x³ + 15x² + 10x // 이 곱셈들은 자리올림이 없어 일반 곱셈과 결과가 같다
빼기(5x³ + 3x²) ⊕ (5x³ + 15x² + 10x) = (3 XOR 15)x² + 10x = 12x² + 10x
[2단계] 이제 남은 12x² + 10x를 다시 g(x)로 나눈다. 12x² ÷ x² = 12
12 · g(x) = 12x² + (12×3)x + (12×2) = 12x² + 20x + 24 // GF(256) 곱셈
빼기(12x² + 10x) ⊕ (12x² + 20x + 24) = (10 XOR 20)x + 24 = 30x + 24
결론나머지 = 30x + 24 → 패리티 = [30, 24]
전송[5, 3] + [30, 24] = [5, 3, 30, 24]
3단계 : 실전 — 다항식 나눗셈으로 패리티 만들기 계속

검증해보기

코드를 짜고 나면 rs_encode([5, 3], 2)를 호출해보자. 정확히 [30, 24]가 나와야 한다. 안 나오면 GF 곱셈 테이블이나 다항식 나눗셈 어딘가에 버그가 있는 것. 손계산으로 만든 이 예시가 가장 강력한 단위 테스트다.

왜 다항식 나눗셈이 점 보간과 동치인가?

핵심 정리: D(x)·xᵗ - r(x) (r은 나머지)는 g(x)로 나누어 떨어진다. 즉 α⁰, α¹, ..., α^(t-1) 각각을 대입하면 모두 0이다. 이게 디코더가 오류를 탐지하는 단서가 된다. (디코더 수학은 부호화보다 훨씬 까다로워서 본 프로젝트 범위 밖.)

부호화 단계에서 우리가 만든 [5, 3, 30, 24]는 수학적으로 어떤 1차 다항식(계수 2개)을 서로 다른 4개 점에서 계산한 값과 동치다. 4개 중 2개가 어디서 사라졌는지 알면(손실), 남은 2개의 점만으로 1차 다항식이 유일하게 결정되므로, 데이터 [5, 3]을 복원할 수 있다.

이렇게 만들면 받는 쪽에서 t개의 패리티로 t/2개까지의 오류를 정정할 수 있다. QR 코드 EC Level별 정정 능력:

실제 QR Version 1 EC-M의 숫자

V1 EC-M은 데이터 16바이트 + 패리티 10바이트 = 총 26바이트다. 위의 미니 예시와 똑같은 알고리즘으로 만들되 t=10, 데이터 길이 16일 뿐.

10개의 패리티로 최대 5바이트까지 손상돼도 복원 가능. 26바이트 중 5바이트면 약 19%. 그래서 "M 레벨은 15% 정정 가능"이라고 표시한다 (안전 마진 포함).

QR 코드에 로고를 넣을 수 있는 이유

이제 알 것이다. EC Level H를 쓰면 이론상 30%까지 가려도 읽힌다. 그래서 한가운데에 로고를 넣어도 스캔이 된다. 다만 30%는 다른 손상이 전혀 없을 때의 한계치이므로, 실무에서는 로고 면적을 전체의 20% 이내로 잡고 Finder/Timing 패턴을 가리지 않아야 안전하다.

00FOUNDATION

갈루아 필드 GF(256) 테이블 구축

모든 RS 연산의 기반. 한 번 만들어두면 모든 곱셈/나눗셈이 테이블 룩업으로 O(1)이다.

핵심 최적화 트릭

  • 곱셈 0 처리: if a == 0 or b == 0: return 0 가지치기로 LOG 테이블 접근 회피

왜 0x11D인가?

이 다항식은 GF(2)에서 기약(irreducible)이면서 원시(primitive)다. 쉽게 말해 인수분해되지 않고, 거듭제곱이 255개의 모든 nonzero 원소를 한 번씩 만든다. 이런 다항식이 여러 개 있지만 QR 표준이 0x11D를 골랐다. AES는 다른 걸 쓰지만(0x11B), CD/DVD의 RS 부호는 QR과 같은 0x11D를 쓴다.

01REED-SOLOMON

Reed-Solomon 부호화

생성다항식 g(x) = (x-α⁰)(x-α¹)···(x-α^(t-1))로 다항식 나눗셈. 몫은 버리고 나머지(=패리티)만 사용한다.

핵심 최적화 트릭

  • LOG 한 번 계산 후 재사용: 안쪽 루프에서 coef의 로그값을 미리 빼두면 매 반복마다 룩업 1회 절약 ~40% UP
  • 0 계수 가지치기: if coef == 0: continue — sparse한 경우 큰 효과
  • 나눗셈의 몫을 별도 배열에 안 쓰고 in-place로 처리 (메모리 할당 절약)

    gen = rs_generator_poly(nsym)
    buf = list(data) + [0] * nsym  # in-place 작업 버퍼
    for i in range(len(data)):

        if coef != 0:           # 가지치기
            lc = GF_LOG[coef]      # LOG 한번만
            for j in range(1, len(gen)):
                buf[i + j] ^= GF_EXP[GF_LOG[gen[j]] + lc]
    return buf[-nsym:]          # 나머지만 반환

03INTERLEAVING

블록 분할 + 인터리빙

버전과 EC 레벨에 따라 데이터를 여러 블록으로 나눠서 각각 RS 부호화한다 (V1~2는 항상 1블록, V3-Q부터 2블록 — QR_SPECS 테이블 참조). 그 다음 블록의 같은 위치 바이트끼리 모아서 인터리빙한다.

왜 인터리빙하는가? (이게 핵심)

QR이 일부 가려진다고 하자. 가려진 부분은 연속된 바이트 손실(burst error)이다. 만약 한 블록만 있으면 그 블록 안의 RS가 감당 못할 만큼 오류가 몰린다.

하지만 블록을 여러 개로 나누고 인터리빙해서 여러 블록의 바이트를 섞어놓으면, 연속된 손실 영역이 여러 블록에 분산된다. 각 블록당 손실은 1~2개씩으로 줄어들어 RS가 거뜬히 복구할 수 있게 된다. 

인터리빙 시각화블록A: a1 a2 a3 a4 a5
블록B: b1 b2 b3 b4 b5
블록C: c1 c2 c3 c4 c5

인터리빙 후: a1 b1 c1 | a2 b2 c2 | a3 b3 c3 | a4 b4 c4 | a5 b5 c5

→ 가운데 5바이트(c2,a3,b3,c3,a4)가 가려져도
  블록A 손실=2개(a3,a4), B=1개(b3), C=2개(c2,c3) → 각 블록 RS가 충분히 복구

    lambda r, c: (r + c) % 2 == 0,
    lambda r, c: r % 2 == 0,
    lambda r, c: c % 3 == 0,
    lambda r, c: (r + c) % 3 == 0,
    lambda r, c: (r // 2 + c // 3) % 2 == 0,
    lambda r, c: (r * c) % 2 + (r * c) % 3 == 0,
    lambda r, c: ((r * c) % 2 + (r * c) % 3) % 2 == 0,
    lambda r, c: ((r + c) % 2 + (r * c) % 3) % 2 == 0,
]

def _apply_mask(m, reserved, mask_id):
    n = len(m)
    formula = MASK_FORMULAS[mask_id]
    masked = [row[:] for row in m]  # shallow copy per row
    for r in range(n):
        for c in range(n):
            if not reserved[r][c] and formula(r, c):
                masked[r][c] ^= 1
    return masked

EC_BITS = {'L': 0b01, 'M': 0b00, 'Q': 0b11, 'H': 0b10}

FORMAT_GEN_POLY = 0b10100110111
FORMAT_MASK = 0b101010000010010  # = 0x5412

def _format_bits(ec_level, mask_id):
    """15비트 Format Info = 5비트 데이터 + 10비트 BCH ECC, 최종 XOR 마스킹"""
    data = (EC_BITS[ec_level] << 3) | mask_id  # 5비트
    rem = data << 10
    for i in range(4, -1, -1):     # BCH 나눗셈
        if rem & (1 << (i + 10)):
            rem ^= FORMAT_GEN_POLY << i
    bits = ((data << 10) | rem) ^ FORMAT_MASK
    return [(bits >> i) & 1 for i in range(14, -1, -1)]

    bits = _format_bits(ec_level, mask_id)

Version Information — V7부터 필수! (18비트 BCH)

Version 7 이상은 Format Info와 별개로 18비트 Version Information이 필요하다. 6비트 버전 번호에 생성다항식 x¹² + x¹¹ + x¹⁰ + x⁹ + x⁸ + x⁵ + x² + 1 (0x1F25)로 만든 12비트 BCH 패리티를 붙여 총 18비트. 우상단 Finder 왼쪽의 3×6 블록과 좌하단 Finder 위쪽의 6×3 블록 두 곳에 기록한다 (서로 전치 위치).

버전 번호는 매트릭스 크기에서 자명한데 왜 굳이 넣을까? 멀리서/비스듬히 찍은 사진은 모듈 수 세기가 부정확해서, 큰 QR일수록 크기 추정만으로는 버전을 틀리기 쉽기 때문이다. 이 영역은 데이터 배치 전에 반드시 채워야 한다 — 빠뜨리면 데이터 비트가 그 자리를 침범해서 비트 배치 전체가 표준과 어긋나고, V7 QR은 어떤 스캐너로도 읽히지 않는다.

    마스크와 무관한 고정값이므로 데이터 배치 전(reserved 계산 전)에 호출한다."""

    n = len(m)

    for _ in range(12):                  # BCH(18,6) 나눗셈
        rem = (rem << 1) ^ ((rem >> 11) * VERSION_GEN_POLY)

BMP의 3가지 함정

  1. Bottom-up 저장: 픽셀 데이터는 마지막 행부터 첫 행까지 거꾸로 저장한다. 1980년대 OS/2 시절의 유산이라 지금도 유지된다. 위에서 아래로 저장하면 이미지가 뒤집혀 보임
  2. 4바이트 행 정렬 (DWORD alignment): 한 행의 바이트 수는 반드시 4의 배수. 부족하면 0으로 패딩. 비트연산 (n + 3) & ~3이 가장 빠른 4의 배수 올림
  3. 1비트 픽셀은 MSB가 왼쪽: 한 바이트가 8픽셀인데, 비트 7(MSB)이 왼쪽 픽셀, 비트 0(LSB)이 오른쪽 픽셀. 헷갈리면 좌우가 뒤집힌다

성능 트릭 PERF

  • (n + 3) & ~3: 4의 배수 올림. 일반 산술 ((n+3)//4)*4와 같은 결과 (CPython에선 차이 미미, C/Go 포팅 시 유효한 관용구)
  • c >> 3 = c // 8, c & 7 = c % 8: 시프트/AND가 나눗셈/모듈로보다 빠름 (CPython에서는 차이가 작지만 C/Go 포팅 시 중요)
  • 흰색만 비트 설정: bytearray는 0으로 자동 초기화 → 검정 픽셀은 아무것도 안 함 → 분기 1개 절약

왜 1비트인가? 그리고 BGRA는 왜 거꾸로?

QR은 색이 2가지뿐이라 1비트면 충분하다. 24비트로 저장하면 픽셀당 24배 큰 파일이 된다.

BMP 팔레트가 BGR 순서인 이유는 Intel x86이 리틀엔디안이어서 메모리에 0x00FF0000을 쓰면 바이트가 00 00 FF 00 순서로 들어간다. 옛날 비트맵 로더가 이 메모리를 그대로 읽으면 자동으로 BGR이 됐고, 그게 표준이 됐다. 역사적 부산물이지만 지금도 살아있다.

  • V7은 Version Information(18비트, 우상단+좌하단 두 곳)이 필수. 빠뜨리면 데이터 비트가 그 자리를 침범해 V1~6은 되는데 V7만 스캔 실패하는 미스터리를 겪게 됨
