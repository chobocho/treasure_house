시간 쪼개기

매 프레임 20 ms 예산만큼만 계산하고 requestAnimationFrame 으로 양보한다. 개체 1~2명씩 처리 → 12명에 8프레임, 40세대에 약 320프레임 ≈ 5~8초. 그동안 화면은 60fps로 돈다.

언제 빠른가보다, 언제 양보하는가

같은 프레임 안에서 옆의 테트리스 판도 돌아간다. 예산을 20 ms로 잡은 건 16.7 ms 프레임을 한 번 넘기더라도 30fps는 지키기 위해서다.

규모가 작다조각 120개·시드 2개라 노이즈가 크다. 6부의 127.3 같은 숫자는 나오지 않는다. 여기서 볼 것은 곡선의 모양이지 절대값이 아니다.

{{N}}워커로 옮기려면

메인 스레드에서 돌린 이유는 단순함이다. 워커로 옮기면 예산 쪼개기 자체가 필요 없어진다.

외부 파일 없이 워커 만들기JavaScript · 8줄
const src = `
  self.onmessage = async (ev) => {
    const { bytes, genome, seeds, pieces } = ev.data;
    const inst = await WebAssembly.instantiate(bytes, {});
    const e = inst.instance.exports;
    new Float32Array(e.memory.buffer, e.ai_weights_ptr(), 8).set(genome);
    let atk = 0;
    for (const s of seeds) { e.ai_play(s, pieces); atk += e.ai_play_attack(); }
    self.postMessage(atk / seeds.length);
  };`;
const w = new Worker(URL.createObjectURL(new Blob([src], { type: 'text/javascript' })));

얻는 것

메인 스레드가 완전히 자유롭다. 코어 수만큼 워커를 띄우면 4~8배 빨라진다 — 개체를 병렬로 평가하면 되니 GA는 병렬화가 거의 공짜다.

치르는 것

wasm 바이트를 워커마다 복사(14 KB × N)해야 하고, 메시지 왕복 비용이 붙는다. 그리고 file:// 로 연 문서에서는 Blob URL 워커가 브라우저에 따라 막힌다 — 이 덱이 메인 스레드를 고른 결정적 이유다.

SharedArrayBuffer로 메모리를 공유하는 방법도 있지만 COOP/COEP 헤더가 필요해서 단일 HTML 파일로는 불가능하다.
