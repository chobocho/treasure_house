이 덱을 읽는 법

이 덱은 세 개의 서로 다른 질문에 답한다. 관심사에 따라 필요한 부만 골라 읽어도 된다.

질문읽을 곳성격
월마트는 AI를 어떻게 조직에 심었나1~3부사례·전략 (출처 링크 포함)
Code Puppy는 무엇이고 어떻게 생겼나4~5부실제 저장소 코드 해부
같은 것을 내가 만들 수 있나6~7부Python·Go 실행 가능 구현

원문·용어·체크리스트9부부록
6~7부의 코드는 전부 실제로 돌려 본 것이다. Python 구현은 자체 시험 96건, Go 구현은 go test 60건이 모두 통과한 상태에서 이 덱에 옮겼다. 의사코드는 한 줄도 없다.

사실과 추정을 나누는 규칙

이 덱은 외부에 공개된 자료만으로 쓰였다. 월마트 내부 문서나 비공개 정보는 쓰지 않았다. 그래서 문장의 성격을 세 가지로 구분해 표시한다.

확인된 사실 — 월마트 기술 블로그, 보도자료, 언론 보도, 공개 저장소에서 확인한 것. 해당 슬라이드에 출처 링크를 단다.
코드로 확인한 것 — github.com/mpfaffenberger/code_puppy 저장소를 직접 내려받아 읽고 인용한 것. 인용한 파일 경로를 함께 적는다.
해설·추정 — 공개된 사실에서 필자가 끌어낸 해석. "…로 보인다", "…일 것이다"로 끝나거나 해설 배지를 단다. 월마트의 공식 입장이 아니다.

전체 출처 목록은 9부 부록의 링크 총람에 모아 두었다.

한 장으로 보는 전체 구조

1부 월마트의 AX — 무엇을, 왜 2부 접근 방법 — 어떻게 조직에 심었나 3부 아이디어를 모으는 법 — 무엇을 만들지 어떻게 정하나 4부 Code Puppy 사례 — 도구 하나가 7만 5천 명에게 5부 아키텍처 해부 — 저장소 코드로 읽는 내부 6부 Python 구현 — mini-puppy, 시험 96건 통과 7부 Go 구현 — minipuppy, 시험 60건 통과 8부 도입 플레이북 — 우리 조직에 옮기기 9부 부록 — 링크·용어·체크리스트
왜 Code Puppy인가 — 월마트가 만든 수많은 AI 중에서 이것만 소스가 공개되어 있다. 전략 문서는 추상적이지만 코드는 거짓말을 하지 않는다. 조직의 판단이 함수 하나하나에 박혀 있는 것을 직접 읽을 수 있는 유일한 창구다.

1부

월마트의 AX

에이전트가 손님이 되는 세계에서 소매업은 무엇을 다시 지어야 하는가

1장

AX라는 말

UX·CX 다음에 온 세 번째 글자

AX = Agentic Experience

AX는 에이전트 경험, 즉 사람이 아니라 AI 에이전트가 서비스를 이용할 때의 경험을 가리킨다. 소매업에서 이 말이 튀어나온 이유는 단순하다. 물건을 고르고 결제하는 주체가 사람에서 에이전트로 옮겨 가기 시작했기 때문이다.

UX→ CX→ AX
약어대상최적화 목표
UX화면 앞의 사람클릭 수, 이해 속도
CX여정 전체의 고객만족, 재방문, LTV
AX고객을 대신하는 에이전트기계가 읽을 수 있는 사실의 정확도·완결성
핵심 전환 — CX는 사람을 설득하는 일이고, AX는 기계에게 사실을 정확히 넘기는 일이다. 설득의 기술이 통하지 않는 상대가 새로 생긴 것이다.

왜 지금 AX인가

2025년 하반기부터 대형 소매업체들이 같은 문장을 반복하기 시작했다. "이제 CX만으로는 부족하다. AX도 해야 한다."

  1. 대화형 AI가 상품 탐색의 첫 관문이 되기 시작했다.
  2. 에이전트가 사람 대신 장바구니를 채우고 결제까지 하는 흐름이 실험되었다.
  3. 그러자 "우리 상품이 에이전트에게 어떻게 보이는가"가 매출 변수가 되었다.
  4. 기존 SEO·광고는 사람의 눈과 감정을 노린 것이라 에이전트에게 통하지 않았다.
감성을 자극하는 예쁜 이미지는 구매를 결정하는 AI 에이전트를 움직이지 못한다. 그래서 에이전트를 위한 발견 경로를 새로 만들어야 한다.

SEO에서 AEO로

사람을 검색 결과 상단으로 끌어오는 기술(SEO)과, 에이전트가 사실을 정확히 집어 가게 만드는 기술(AEO, Agentic Engine Optimization)은 최적화 대상이 다르다.

사람을 겨냥한 최적화

매력적인 대표 이미지 · 감성 카피 · 별점 배지 · 한정 특가 배너 · 리뷰 요약 문구

에이전트를 겨냥한 최적화

구조화된 상품 피드 · 정확한 재고/치수/성분 · 명확한 반품 정책 · 가격 변동 이력 · 기계가 읽는 프로모션 규칙

둘은 대체 관계가 아니다 — 사람이 사라진 것이 아니라 채널이 하나 늘어난 것이다. 같은 상품 데이터가 두 벌의 표현을 가져야 한다.

중요한 오해 방지 — 특화 에이전트가 사라진 것이 아니다. 슈퍼 에이전트 안에서 계속 동작한다. 없어진 것은 사용자가 마주하는 입구이지 기능이 아니다.

200개 이상의 봇을 4개로 통합했다는 정리는 Stellagent의 Sparky 아키텍처 분석에 근거한다. 2차 자료

Sparky — 고객 쪽 얼굴

Sparky는 월마트 앱 안에서 이미 동작 중인 쇼핑 에이전트다. 발표 이후 계속 기능이 붙었다.

  • 탐색 — "8살 생일선물, 예산 5만원" 같은 모호한 요구를 상품으로 번역
  • 장바구니 — 여러 상품을 한 번에 담고 대안을 제시
  • 재주문 — 과거 구매에서 반복 항목을 끌어냄
  • 고객 지원 — 주문 상태·반품을 대화로 처리
2차 자료가 전하는 지표 — Sparky 사용자의 평균 주문 금액이 비사용자보다 약 35% 높다는 분석이 있다. 월마트가 직접 공표한 수치는 아니므로 참고치로만 읽는 편이 안전하다. 2차 자료

Associate Agent — 150만 명의 창구

가장 어려운 대상이 여기다. 사용자가 개발자도 아니고, 교육 시간도 없고, 손에는 스캐너와 휴대 단말뿐이다.

  1. 근무 일정 확인 — "다음 주 내 스케줄"
  2. 매출·재고 조회 — "이 구역 어제 매출"
  3. 복리후생 안내 — 별도 전문 에이전트로 연결
  4. 업무 절차 질의 — 매장 정책 문서를 근거로 답변
여기서 실패하면 전략 전체가 흔들린다 — 매장 직원이 두 번 잘못된 답을 받으면 다시 쓰지 않는다. 도입 규모가 큰 만큼 정확도 요구가 가장 높은 지점이다. 해설

Developer Agent — 이 덱의 주인공이 사는 곳

네 번째 문은 개발자를 향한다. 테스트·빌드·배포 주기를 줄이는 것이 목표로 제시되었고, 실제 구현체로 WIBEY가 공개되었다.

개발자→ WIBEY→ 도메인 에이전트들
Code Puppy와의 관계 — 공개 자료만으로는 Code Puppy가 Developer Agent/WIBEY의 공식 구성요소인지 단정할 수 없다. 확인되는 것은 둘 다 월마트 개발자를 대상으로 하고, Code Puppy는 사내에서 약 7만 5천 명이 쓴다는 사실이다. 이 덱은 둘을 같은 방향의 서로 다른 산물로 다룬다.

MCP — 도구를 꽂는 표준 구멍

MCP(Model Context Protocol)는 에이전트가 외부 시스템의 도구를 발견하고 호출하는 방법을 표준화한다. 핵심은 놀랄 만큼 단순하다. 줄 단위 JSON-RPC 2.0이 전부다.

→ {"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}
← {"jsonrpc":"2.0","id":1,"result":{"capabilities":{"tools":{}}}}
→ {"jsonrpc":"2.0","method":"notifications/initialized"}
→ {"jsonrpc":"2.0","id":2,"method":"tools/list"}
← {"jsonrpc":"2.0","id":2,"result":{"tools":[{"name":"get_inventory",...}]}}
→ {"jsonrpc":"2.0","id":3,"method":"tools/call",
   "params":{"name":"get_inventory","arguments":{"sku":"A123"}}}
← {"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"42"}]}}
6부·7부에서 이 왕복을 직접 구현한다 — Python 약 90줄, Go 약 120줄이면 완전한 stdio 클라이언트가 된다. 실제로 만들어 시험까지 통과시킨 코드를 싣는다.

A2A — 에이전트가 에이전트에게

MCP가 "에이전트 → 도구"라면, A2A(Agent-to-Agent)는 "에이전트 → 에이전트"다. WIBEY는 두 개를 역할로 나눠 쓴다.

MCPA2A

상대도구·시스템자율적인 다른 에이전트
호출 성격동기적 함수 호출에 가깝다작업 위임에 가깝다 — 오래 걸릴 수 있다
결과정해진 스키마의 반환값진행 상태를 포함한 작업 결과
구분이 흐릿해 보이는 이유 — 실제로 "도구처럼 부를 수 있는 에이전트"를 만들면 둘의 경계가 사라진다. Code Puppy에도 invoke_agent라는 도구가 있다 — 서브에이전트를 도구처럼 부른다. 6부에서 우리도 같은 방식을 쓴다.

연합 모델의 계약

도메인 팀이 각자 에이전트를 만들되 전체가 굴러가게 하려면, 플랫폼이 강제해야 할 최소 계약이 있다. 해설

  1. 이름과 설명 — 카탈로그에서 찾을 수 있어야 한다
  2. 입출력 스키마 — 기계가 검증할 수 있어야 한다
  3. 권한 선언 — 무엇을 읽고 무엇을 바꾸는가
  4. 실패 규약 — 실패를 예외가 아니라 값으로 돌려준다
  5. 관측 훅 — 호출·지연·오류가 중앙에 모인다
4번이 특히 중요하다 — 도구 실패가 예외로 터지면 에이전트 루프가 끊긴다. 실패를 모델이 읽을 수 있는 문자열로 돌려주면 모델이 스스로 다른 길을 찾는다. 6부·7부 구현에서 이 규칙을 코드로 확인한다.

이 곡선의 모양이 말해 주는 것

1,000 → 75,000은 75배다. 이런 곡선은 광고로 만들어지지 않는다. 해설

  1. 0→1,000 — 얼리어답터 엔지니어. 만든 사람 주변.
  2. 1,000→10,000 — 팀 단위 전파. "옆 사람이 쓰던데."
  3. 10,000→75,000 — 비개발자로 넘어간 구간. 여기서 곡선이 꺾인다.
3단계가 핵심이다 — 개발자만 대상이면 사용자 수가 개발자 수에서 멈춘다. 비개발자가 쓰기 시작하면 상한이 직원 수로 바뀐다. CTO의 표현대로 "기술의 힘이 민주화된" 순간이다.

  3. MCP는 도구를, A2A는 위임을 표준화한다. 둘이 있어야 중앙이 다 만들지 않는 연합 모델이 성립한다.
  4. 파운드리 사고의 결론은 "남는 유일한 제약은 아이디어"다.
  5. 가드레일은 프롬프트가 아니라 도구 목록·도구 내부·승인 관문에 걸어야 한다.
  6. 도입 곡선이 꺾이는 지점은 비개발자가 넘어오는 순간이고, 그때 상한이 직원 수로 바뀐다.

  1. 무엇으로 이해했는지 — 오해가 있으면 여기서 잡힌다
  2. 왜 이번에 안 하는지 — 우선순위인지, 부적합인지

· 금지 사항 ("legacy/는 건드리지 마라")
· 파일 배치 규칙
· 커밋 메시지 형식
· 쓰지 말아야 할 라이브러리

효과 없는 규칙

· "좋은 코드를 써라"
· "버그를 만들지 마라"
· 다시 말해 검증 불가능한 요구
· 너무 길어서 안 읽히는 것

좋은 규칙의 판별법 — 그 규칙을 지켰는지 기계가 확인할 수 있는가? 확인할 수 있으면 규칙이고, 없으면 소원이다.

실제 예 — Code Puppy 자신의 AGENTS.md에서

Code Puppy 저장소에는 자기 자신을 위한 AGENTS.md가 179줄 들어 있다. 성격을 보여 주는 항목들이다.

- 파일은 600줄 아래로 유지한다. 넘으면 쪼갤 것을 제안한다.
- 단, 줄 수를 맞추려고 응집도를 해치면서까지 쪼개지는 마라.
- 파이썬이 아니어도 Zen of Python 을 지켜라.
- edit 을 create_file 보다 선호하라. 디프는 100~300줄로 작게.
- 기존 파일은 반드시 읽고 나서 고쳐라.
"단, …쪼개지는 마라" 절이 왜 있는가 — 규칙만 주면 모델은 규칙을 기계적으로 따른다. 600줄 제한만 있으면 599줄짜리 무의미한 파일이 양산된다. 규칙에는 예외 조건을 함께 적어야 한다.

rotate_every를 얼마로 둘 것인가

값효과대가
1매 요청 교대. 부하가 가장 고르다프롬프트 캐시가 매번 깨진다

프롬프트 캐시가 결정 변수다 — 에이전트 루프는 같은 앞부분 + 늘어나는 뒷부분을 반복해 보낸다. 접두 캐시가 살아 있으면 비용과 지연이 크게 줄어든다. 매 요청 교대하면 그 이득을 버린다. rotate_every는 부하 분산과 캐시 적중의 교환 비율을 정하는 손잡이다. 해설

4부 정리 — 여섯 문장

  1. Code Puppy는 무거운 IDE와 폐쇄형 벤더 함정을 거부한다는 정체성을 시스템 프롬프트에 새긴 CLI 코딩 에이전트다.
  2. 1,000 → 7만 5천 명, 오픈소스 50만 회 내려받기. 비개발자로 넘어간 것이 곡선을 꺾었다.
  3. 설정은 ~/.code_puppy/에, 규칙은 AGENTS.md 세 곳을 이어 붙여 읽는다.
  4. JSON 파일 하나로 새 에이전트를 만들 수 있고, 도구 목록이 곧 가드레일이다.
  5. round_robin은 특별 기능이 아니라 모델의 한 종류이며, rotate_every가 부하 분산과 캐시 적중을 저울질한다.
  6. MCP 관리에 서킷 브레이커·헬스 모니터·오류 격리가 들어 있다 — 외부 도구를 붙인다는 것의 진짜 비용이다.

func setProcessGroup(cmd *exec.Cmd) {

func killTree(cmd *exec.Cmd) error {
	if cmd.Process == nil {
		return nil
	}
	if err := syscall.Kill(-cmd.Process.Pid, syscall.SIGKILL); err == nil {
		return nil
	}
	return cmd.Process.Kill()
}

# 이 저장소에서 일하는 법

## 먼저 읽을 것
- 아키텍처: docs/architecture.md
- 시험 돌리는 법: `make test` (2분)

## 반드시 지킬 것
- 고치기 전에 읽는다. 파일을 안 보고 추측하지 않는다.
- 한 번에 한 가지만 바꾼다.
- 고친 뒤 `make test` 를 돌려 확인한다. 실패하면 되돌린다.
- 의존성을 새로 추가하지 않는다. 필요하면 사람에게 묻는다.

## 이 저장소의 함정
- `legacy/` 는 손대지 않는다 — 별도 배포 주기다.
- 마이그레이션 파일은 절대 고치지 않는다. 새로 만든다.

## 금지
- 비밀·키·토큰을 파일에 쓰지 않는다.
- `git push --force` 를 쓰지 않는다.
"이 저장소의 함정" 절이 가장 값지다 — 나머지는 어느 저장소에나 해당하는 말이라 모델이 이미 안다. 새로 온 사람에게 세 번 설명한 것이 여기 들어갈 내용이다. 그것이 곧 이 파일의 목적이다.

사고가 났을 때 — 세 시간 안에 할 일

  1. 세션 파일을 확보한다 — 무엇을 시켰고 무엇을 했는지 전부 거기 있다. 이것이 로그다.
  2. 어느 겹이 뚫렸는지 정한다 — 프롬프트였나(1겹), 도구가 있었나(2겹), 사람이 승인했나(3겹)?
  3. 그 겹만 고친다 — 도구가 있었으면 인격에서 뺀다. 승인이 무뎠으면 그 동작을 4겹으로 올린다.
  4. 같은 사고를 시험으로 만든다 — "이 인격은 이 도구를 못 쓴다"를 자동으로 확인한다.
  5. 회신한다 — 무엇이 왜 일어났고 무엇을 바꿨는지. 침묵이 도입률을 가장 크게 떨어뜨린다.
사고의 값은 그 사고가 아니라 신뢰다 — 파일 하나 망친 것은 git checkout 이면 끝난다. "이거 위험하대"가 퍼지면 6개월이 날아간다. 그래서 5번이 1~4번만큼 중요하다.

8부 정리 — 여섯 문장

  1. 도구를 고를 때 기능보다 확장점 목록을 먼저 보라 — 없으면 포크 말고 길이 없다.
  2. 가드레일 네 겹 중 도구 목록이 값 대비 효과가 가장 크다.
  3. 기본값 다섯(yolo·뿌리 가둠·거부 목록·UC·헤드리스 자율도)은 첫날 다시 결정한다.
  4. 1주차에는 읽기 전용으로 신뢰를 벌고, 그다음 권한을 올린다.
  5. AGENTS.md 에서 값진 것은 "이 저장소의 함정" 절이다.
  6. 도입률이 아니라 4주 유지율·되돌림 비율·턴당 비용을 센다.

이 덱은 세 겹으로 되어 있다.

전략 (1~3부)→ 코드 (4~5부)→ 손 (6~8부)

전략만 읽으면 따라 할 수 없고, 코드만 읽으면 왜 그런지 모른다. 만들어 봐야 어느 결정이 본질이고 어느 것이 편의였는지 안다.

가장 남길 만한 한 문장 — 가드레일은 설득이 아니라 구조다. 프롬프트로 부탁한 것은 언젠가 뚫리고, 스키마에 없는 도구는 존재하지 않는다. 이 하나만 가져가도 이 덱은 값을 한다.
