{{N}}설치할 것은 하나뿐이다

이 프로젝트가 npm install 하는 패키지는 typescript 와 @types/node 둘이다. 둘 다 개발 도구고, 돌아가는 코드에는 의존성이 없다.

$ make deps
npm install --no-save typescript @types/node

$ make build      # 타입체크 + 컴파일 → dist/
$ make test       # node --test dist/test/*.test.js
$ make run        # 8인 서버 (web/ + /ws)
이 기계에서 겪은 함정npm 캐시에 tsc 라는 다른 패키지가 들어 있었다. npx tsc 가 그걸 집어 들면 "컴파일했는데 아무 일도 안 일어나는" 상태가 된다. 그래서 Makefile 이 npx --no-install tsc --version 으로 진짜가 있는지 먼저 확인하고, 없으면 명시적으로 설치한다.

{{N}}엄격 옵션은 처음부터

나중에 켜면 그때까지 쌓인 코드가 전부 빨개진다. 처음에 켜 두는 편이 훨씬 싸다.

이 코드 블록은 손으로 옮겨 적은 게 아니다덱 빌더가 실제 tsconfig.json 을 읽어 잘라 넣고, 파일의 모든 줄이 덱 어딘가에 정확히 한 번 실렸는지 세어 본다. 소스를 고치면 덱도 다시 만들어야 한다.

{{N}}네 옵션이 한 일

옵션이 프로젝트에서 실제로
strict기본. null·undefined 가 타입에 드러난다
exactOptionalPropertyTypes{ raf: undefined } 를 넘기는 것과 키를 아예 안 넘기는 것을 구분한다 — 데모가 옵션을 넘겨 줄 때 실수로 undefined 를 흘려보내면 기본값(브라우저 rAF)이 안 잡힌다
noUnusedLocals리팩터링 뒤 남은 임포트를 빌드가 세운다. 허브를 파일 밖으로 뺐을 때 실제로 네 개를 짚어 줬다
noFallthroughCasesInSwitch프로토콜 메시지 분기가 switch 투성이다. 빠뜨린 break 는 조용히 잘못 도는 형태로 나타난다
// 요약 인용 — src/demo.ts 의 pick(). 전문은 파트 3 에 있다.
function pick(o: ViewOptions) {
  return {
    ...(o.raf ? { raf: o.raf } : {}),   // 있을 때만 키를 만든다
    ...(o.now ? { now: o.now } : {}),
  };
}

파트 번호가 붙어 있는 게 이 문서의 순서다. 위에서 아래로 읽으면 의존성 방향과 같다 — 아래 것이 위 것을 알지, 그 반대는 없다.

{{N}}golden 은 build 뒤, test 는 golden 뒤

make build   →  tsc 로 dist/ 생성
make golden  →  dist 를 임포트하는 도구가 wasm 에서 정답지를 뽑는다
make test    →  정답지가 없으면 파리티 테스트가 실패한다 (건너뛰지 않는다)
make web     →  dist → web/js 번들
make deck    →  web 번들을 인라인하고 소스를 잘라 넣어 이 문서를 만든다

순서를 사람이 기억하게 두면 언젠가 틀린다. make test 는 정답지 파일이 없으면 스스로 make golden 을 먼저 부른다.

"없으면 건너뛴다"를 하지 않는 이유정답지가 없을 때 파리티 테스트를 건너뛰면 초록불이 뜬다. 그 순간 이 프로젝트의 검증 전략 전체가 조용히 무너진다 — 그래서 없으면 실패한다.

{{N}}뼈대 → 테스트 → 구현

순서한 일왜
1tsconfig·package.json·Makefile돌릴 수 있는 상태를 먼저 만든다
2C++ wasm 에서 트레이스 추출 도구정답지 없이 코어를 쓰면 나중에 어디가 틀렸는지 못 찾는다
3실패하는 테스트무엇을 만들지 코드로 먼저 적는다
4core.ts 구현테스트가 초록이 될 때까지

이 순서가 이 문서 전체에 반복된다. 새 파일을 만들 때마다 테스트를 먼저 쓰고, 실패를 확인하고, 그다음에 구현했다 — 파트 9의 라이브 학습도, 파트 14의 네트워크 층도 그랬다.

이제 코어부터 한 줄씩 읽는다.
