1. 왜 Go에서 디자인 패턴인가

디자인 패턴은 1994년 GoF(Gang of Four)가 출간한 《Design Patterns: Elements of Reusable Object-Oriented Software》에서 체계화된 객체 지향 설계 노하우의 집합이다. 하지만 Go는 클래스도, 상속도, 제너릭 이전에는 타입 매개변수도 없는 언어였다. 그렇다면 "객체 지향 패턴"을 Go에서 논하는 것이 의미가 있을까?

대답은 "있다, 단 변형이 필요하다"이다. Go는 인터페이스의 구조적 부분 타이핑(structural subtyping), 합성, 일급 함수, 그리고 채널·고루틴을 통한 동시성 원시 기능을 제공한다. 이 도구들 덕분에 동일한 문제를 자바·C++의 패턴보다 훨씬 가볍게 풀어내는 경우가 많다. 이 책은 23개의 GoF 패턴을 Go 답게 다시 쓰고, Go 커뮤니티에서만 통용되는 "함수형 옵션", "파이프라인", "Errgroup" 같은 고유 패턴까지 함께 정리한다.

2. Go의 언어 철학과 패턴 적용 원칙

Go에서 패턴을 적용할 때 항상 기억해야 할 다섯 가지 원칙:

  1. 합성을 상속보다 우선하라. Go에는 상속 자체가 없다. type 안에 다른 타입을 임베딩해 동작을 빌려온다.
  2. 인터페이스는 사용하는 쪽에서 정의하라. 패키지 경계가 작아진다.
  3. 인터페이스를 받고 구조체를 반환하라. 호출자는 유연성을 얻고, 호출자에게 제공자는 명확한 타입을 제공한다.
  4. 에러는 값이다. 예외가 없으므로 패턴이 에러를 어떻게 전달하는지 항상 명시한다.
  5. 고루틴 누수를 방지하라. 채널 기반 패턴은 종료 신호(done channel, context)를 반드시 포함한다.

4. 싱글톤 (Singleton)

개요

프로세스 전체에서 단 하나의 인스턴스만 존재함을 보장하는 패턴이다. Go에서는 sync.Once를 사용해 스레드 안전한 게으른 초기화로 구현하는 것이 표준이다.

문제

설정 객체, 로거, DB 커넥션 풀처럼 "한 번만 만들어 모든 곳에서 공유"하고 싶지만 동시에 여러 고루틴이 동시에 초기화 함수를 호출해도 단 한 번만 실행되도록 보장해야 한다. 전역 변수를 단순히 노출하면 동시성 안전성과 게으른 초기화를 둘 다 잃는다.

UML

그림 4-1. 싱글톤 — 단 하나의 인스턴스를 sync.Once로 보호한다.

Go 구현

// file: singleton/main.go
package main

import (
    "fmt"
    "sync"
)

type Config struct {
    values map[string]string
}

var (
    instance *Config
    once     sync.Once
)

// GetConfig 는 첫 호출에서만 초기화한다. 이후 호출은 동일 포인터를 돌려준다.
func GetConfig() *Config {
    once.Do(func() {
        fmt.Println("⚙️  Config 초기화 (단 한 번만 실행)")
        instance = &Config{values: map[string]string{
            "db":   "postgres://localhost:5432",
            "port": "8080",
        }}
    })
    return instance
}

func (c *Config) Get(key string) string { return c.values[key] }

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 5; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            c := GetConfig()
            fmt.Printf("[goroutine %d] port=%s addr=%p\n", id, c.Get("port"), c)
        }(i)
    }
    wg.Wait()
}

실행 결과

⚙️ Config 초기화 (단 한 번만 실행) [goroutine 4] port=8080 addr=0xc0000a4030 [goroutine 0] port=8080 addr=0xc0000a4030 [goroutine 1] port=8080 addr=0xc0000a4030 [goroutine 2] port=8080 addr=0xc0000a4030 [goroutine 3] port=8080 addr=0xc0000a4030

모든 고루틴이 동일 포인터(0xc0000a4030)를 받으며 초기화 메시지는 단 한 번만 출력된다.

장점
- 전역 자원 한 곳에서 관리
- sync.Once로 경합 조건 제거
- 게으른 초기화 가능
단점
- 전역 상태는 테스트 어렵게 만든다
- 의존성이 숨겨진다
- 가능하면 의존성 주입을 선호하라
💡 Go 관용: 정말 싱글톤이 필요한지 의심하라. 대부분의 경우 main에서 한 번 만들고 의존성을 명시적으로 주입하는 편이 낫다.

5. 팩토리 메서드 (Factory Method)

개요

객체를 직접 &T{}로 만들지 않고, 인터페이스 타입을 반환하는 함수에 위임한다. 호출자는 어떤 구체 타입이 생성되는지 알 필요가 없다.

문제

알림(Notifier) 시스템을 만들고 있다. 채널은 이메일·SMS·슬랙 세 가지이며 앞으로 더 늘어난다. 호출자가 매번 switch로 분기하면 OCP(개방-폐쇄 원칙)가 깨진다.

UML

그림 5-1. 팩토리 메서드 — kind 파라미터로 적절한 구체 타입을 반환한다.

Go 구현

// file: factory/main.go
package main

import (
    "errors"
    "fmt"
)

type Notifier interface {
    Send(to, msg string) error
}

type emailNotifier struct{}
type smsNotifier struct{}
type slackNotifier struct{ webhook string }

func (emailNotifier) Send(to, msg string) error {
    fmt.Printf("📧 EMAIL  → %s : %s\n", to, msg); return nil
}
func (smsNotifier) Send(to, msg string) error {
    fmt.Printf("📱 SMS    → %s : %s\n", to, msg); return nil
}
func (s slackNotifier) Send(to, msg string) error {
    fmt.Printf("💬 SLACK[%s] → %s : %s\n", s.webhook, to, msg); return nil
}

// 팩토리 함수: 인터페이스 타입만 노출한다.
func NewNotifier(kind string) (Notifier, error) {
    switch kind {
    case "email": return emailNotifier{}, nil
    case "sms":   return smsNotifier{}, nil
    case "slack": return slackNotifier{webhook: "ops-chan"}, nil
    default:      return nil, errors.New("unknown notifier kind: " + kind)
    }
}

func main() {
    for _, k := range []string{"email", "sms", "slack"} {
        n, _ := NewNotifier(k)
        _ = n.Send("alice@example.com", "배포 완료 🚀")
    }
}

실행 결과

📧 EMAIL → alice@example.com : 배포 완료 🚀 📱 SMS → alice@example.com : 배포 완료 🚀 💬 SLACK[ops-chan] → alice@example.com : 배포 완료 🚀
장점
- 새 종류 추가 시 호출 코드 변경 없음
- 구체 타입을 패키지 외부에 숨길 수 있다 (소문자 시작)
- 테스트 시 mock 주입 용이
단점
- switch 가 한 곳에 집중되어 코드 추적이 까다로울 수 있음
- 종류가 적다면 직접 생성자가 더 명확

6. 추상 팩토리 (Abstract Factory)

개요

"관련된 객체들의 집합"을 일관성 있게 만들어 주는 인터페이스. 예: GUI 툴킷에서 macOS용 Button·Window와 Windows용 Button·Window를 함께 묶어 만든다.

문제

OS마다 버튼·윈도우 위젯이 다르다. if os=="mac" 분기를 코드 곳곳에 흩뿌리지 않고, 시작 시 한 번만 "이건 mac 공장"을 결정한 뒤, 이후 호출은 모두 같은 공장에서 위젯을 받아오게 하고 싶다.

UML

그림 6-1. 추상 팩토리 — 한 가족의 위젯을 함께 생성한다.

Go 구현

// file: abstractfactory/main.go
package main

import "fmt"

type Button interface{ Paint() }
type Window interface{ Render() }

type GUIFactory interface {
    NewButton() Button
    NewWindow() Window
}

// Mac 패밀리
type macButton struct{}
func (macButton) Paint() { fmt.Println("🍎 Mac 버튼 그리기 (둥근 모서리)") }
type macWindow struct{}
func (macWindow) Render() { fmt.Println("🍎 Mac 창 렌더 (Aqua 스타일)") }

type MacFactory struct{}
func (MacFactory) NewButton() Button  { return macButton{} }
func (MacFactory) NewWindow() Window  { return macWindow{} }

// Windows 패밀리
type winButton struct{}
func (winButton) Paint() { fmt.Println("🪟 Win 버튼 그리기 (사각형)") }
type winWindow struct{}
func (winWindow) Render() { fmt.Println("🪟 Win 창 렌더 (Fluent 스타일)") }

type WinFactory struct{}
func (WinFactory) NewButton() Button { return winButton{} }
func (WinFactory) NewWindow() Window { return winWindow{} }

// 클라이언트는 GUIFactory 만 안다.
func renderApp(f GUIFactory) {
    f.NewWindow().Render()
    f.NewButton().Paint()
}

func main() {
    fmt.Println("--- macOS 빌드 ---")
    renderApp(MacFactory{})
    fmt.Println("--- Windows 빌드 ---")
    renderApp(WinFactory{})
}

실행 결과

--- macOS 빌드 --- 🍎 Mac 창 렌더 (Aqua 스타일) 🍎 Mac 버튼 그리기 (둥근 모서리) --- Windows 빌드 --- 🪟 Win 창 렌더 (Fluent 스타일) 🪟 Win 버튼 그리기 (사각형)
장점
- 한 가족 단위로 일관성 보장
- 런타임에 패밀리 교체 가능
단점
- 새 제품 추가 시 모든 팩토리 수정
- Go에서는 인터페이스가 가벼워 종종 과설계로 보임

7. 빌더 (Builder)

개요

필드가 많고 일부만 선택적인 복잡한 객체를 단계적으로 조립한다. Go에서는 메서드 체이닝 빌더와, Go 고유의 함수형 옵션 패턴(27장) 두 가지가 모두 쓰인다.

문제

HTTP 요청을 만들고 싶은데 URL은 필수, 메서드·헤더·바디·타임아웃은 선택. 생성자에 인자가 10개 넘어가는 "텔레스코핑 생성자"를 피해야 한다.

UML

그림 7-1. 빌더 — 단계적으로 필드를 채워 최종 객체를 만든다.

Go 구현

// file: builder/main.go
package main

import "fmt"

type Request struct {
    URL, Method, Body string
    Headers           map[string]string
}

type RequestBuilder struct{ r Request }

func NewRequest(url string) *RequestBuilder {
    return &RequestBuilder{r: Request{URL: url, Method: "GET", Headers: map[string]string{}}}
}
func (b *RequestBuilder) Method(m string) *RequestBuilder        { b.r.Method = m; return b }
func (b *RequestBuilder) Header(k, v string) *RequestBuilder     { b.r.Headers[k] = v; return b }
func (b *RequestBuilder) Body(body string) *RequestBuilder       { b.r.Body = body; return b }
func (b *RequestBuilder) Build() Request                          { return b.r }

func main() {
    req := NewRequest("https://api.example.com/users").
        Method("POST").
        Header("Content-Type", "application/json").
        Header("X-Trace", "abc-123").
        Body(`{"name":"alice"}`).
        Build()

    fmt.Printf("→ %s %s\n", req.Method, req.URL)
    for k, v := range req.Headers { fmt.Printf("  %s: %s\n", k, v) }
    fmt.Printf("  body=%s\n", req.Body)
}

실행 결과

→ POST https://api.example.com/users Content-Type: application/json X-Trace: abc-123 body={"name":"alice"}
💡 빌더의 Go식 대안인 함수형 옵션은 27장에서 다룬다. grpc-go·zap 등 널리 쓰이는 라이브러리들이 옵션 패턴을 선호한다.

8. 프로토타입 (Prototype)

개요

기존 객체를 복제(clone)해 새 객체를 만든다. 생성 비용이 큰 객체나, 런타임에 새 종류가 추가되는 시스템에서 유용하다.

문제

그래픽 에디터에서 도형 100개를 거의 같은 속성으로 깔되, 색상만 살짝 다르게 하고 싶다. 매번 NewCircle(...)에 10개 인자를 넘기는 대신 "원형 하나"를 복제해 일부만 바꾼다.

UML

그림 8-1. 프로토타입 — Clone() 만 알면 어떤 종류든 복사할 수 있다.

Go 구현

// file: prototype/main.go
package main

import "fmt"

type Shape interface {
    Clone() Shape
    Describe() string
}

type Circle struct{ Radius int; Color string }
func (c *Circle) Clone() Shape   { cp := *c; return &cp }
func (c *Circle) Describe() string { return fmt.Sprintf("Circle(r=%d, %s)", c.Radius, c.Color) }

type Rect struct{ W, H int; Color string }
func (r *Rect) Clone() Shape   { cp := *r; return &cp }
func (r *Rect) Describe() string { return fmt.Sprintf("Rect(%dx%d, %s)", r.W, r.H, r.Color) }

func main() {
    base := &Circle{Radius: 10, Color: "blue"}
    palette := []string{"red", "green", "yellow"}
    for _, c := range palette {
        clone := base.Clone().(*Circle)
        clone.Color = c
        fmt.Println(clone.Describe())
    }
    rectProto := &Rect{W: 100, H: 50, Color: "black"}
    fmt.Println(rectProto.Clone().Describe())
}

실행 결과

Circle(r=10, red) Circle(r=10, green) Circle(r=10, yellow) Rect(100x50, black)
⚠️ 얕은 복사 함정: 위 예처럼 모든 필드가 값 타입이면 cp := *c 한 줄로 충분하지만, 슬라이스·맵·포인터가 들어 있으면 append·maps.Clone 등으로 깊은 복사를 직접 해야 한다.

제2부 — GoF 구조 패턴 (Structural)

객체와 객체를 어떻게 조립할 것인가에 관한 일곱 가지 패턴이다. Go의 인터페이스 만족이 묵시적이라는 사실은 어댑터·데코레이터·프록시 패턴을 특히 가볍게 만든다.

9. 어댑터 (Adapter)

개요

기존 타입이 가진 메서드 시그니처를, 클라이언트가 기대하는 인터페이스에 맞춰 변환한다.

문제

레거시 결제 라이브러리는 Charge(amount int64, cur string) (string, error)를 노출하는데, 새 코드는 모두 Payer.Pay(req PayRequest) PayResult 형태를 쓴다. 레거시를 수정할 수 없는 상황에서 형태를 맞추고 싶다.

UML

그림 9-1. 어댑터 — 레거시 타입을 새 인터페이스에 맞추는 얇은 래퍼.

Go 구현

// file: adapter/main.go
package main

import "fmt"

// 새 코드가 기대하는 형태
type PayRequest struct{ AmountKRW int64; UserID string }
type PayResult  struct{ TxID string; OK bool }
type Payer interface{ Pay(PayRequest) PayResult }

// 수정 불가한 레거시 라이브러리
type LegacyPay struct{}
func (LegacyPay) Charge(amount int64, currency string) (string, error) {
    return fmt.Sprintf("LEGACY-TX-%d-%s", amount, currency), nil
}

// 어댑터: LegacyPay 를 Payer 로 변환
type LegacyAdapter struct{ Legacy *LegacyPay }
func (a *LegacyAdapter) Pay(req PayRequest) PayResult {
    tx, err := a.Legacy.Charge(req.AmountKRW, "KRW")
    return PayResult{TxID: tx, OK: err == nil}
}

func main() {
    var p Payer = &LegacyAdapter{Legacy: &LegacyPay{}}
    res := p.Pay(PayRequest{AmountKRW: 12000, UserID: "u-1"})
    fmt.Printf("결과: %+v\n", res)
}

실행 결과

결과: {TxID:LEGACY-TX-12000-KRW OK:true}
💡 Go의 인터페이스 만족이 묵시적이라, 만약 레거시 타입이 우연히 Pay 시그니처를 이미 가지고 있다면 어댑터가 필요 없다. 어댑터는 정확히 "시그니처가 어긋날 때"의 해결책이다.

10. 브릿지 (Bridge)

개요

11. 컴포지트 (Composite)

개요

"부분"과 "전체"를 동일한 인터페이스로 다루게 해, 트리 구조를 재귀적으로 순회할 수 있게 한다.

문제

파일 시스템 — 파일은 크기를 직접 알지만, 디렉터리는 자식들의 크기를 합산해야 한다. 호출 코드는 둘을 구분하지 않고 Size() 한 번만 호출하고 싶다.

UML

그림 11-1. 컴포지트 — 자기 자신을 자식으로 가질 수 있는 재귀 구조.

Go 구현

// file: composite/main.go
package main

import "fmt"

type Node interface {
    Name() string
    Size() int64
}

type File struct{ name string; size int64 }
func (f File) Name() string { return f.name }
func (f File) Size() int64  { return f.size }

type Directory struct{ name string; children []Node }
func (d Directory) Name() string { return d.name }
func (d Directory) Size() int64 {
    var total int64
    for _, c := range d.children { total += c.Size() }
    return total
}
func (d *Directory) Add(n Node) { d.children = append(d.children, n) }

func main() {
    root := &Directory{name: "/"}
    src := &Directory{name: "src"}
    src.Add(File{"main.go", 1200})
    src.Add(File{"util.go", 800})
    docs := &Directory{name: "docs"}
    docs.Add(File{"README.md", 4500})
    root.Add(src)
    root.Add(docs)
    root.Add(File{"go.mod", 100})

    fmt.Printf("%s = %d bytes\n", root.Name(), root.Size())
    fmt.Printf("  %s = %d bytes\n", src.Name(),  src.Size())
    fmt.Printf("  %s = %d bytes\n", docs.Name(), docs.Size())
}

12. 데코레이터 (Decorator)

개요

원본 객체를 같은 인터페이스로 감싸 동작을 덧붙인다. Go의 http.Handler 미들웨어가 가장 대표적인 사례다.

문제

HTTP 핸들러에 로깅·인증·캐싱을 끼우고 싶지만, 핸들러를 수정하지 않고 조합 가능해야 한다.

UML

그림 12-1. 데코레이터 — 같은 인터페이스를 만족하며 원본을 감싼다.

Go 구현

// file: decorator/main.go
package main

import (
    "fmt"
    "time"
)

type Handler interface {
    Handle(req string) string
}

type BaseHandler struct{}
func (BaseHandler) Handle(req string) string { return "result(" + req + ")" }

// 데코레이터 = "Handler 를 받고 Handler 를 돌려주는 함수"
type Middleware func(Handler) Handler

func Logging(name string) Middleware {
    return func(next Handler) Handler {
        return handlerFunc(func(req string) string {
            fmt.Printf("[%s] → %s\n", name, req)
            start := time.Now()
            r := next.Handle(req)
            fmt.Printf("[%s] ← %s (%v)\n", name, r, time.Since(start))
            return r
        })
    }
}

func Auth(token string) Middleware {
    return func(next Handler) Handler {
        return handlerFunc(func(req string) string {
            if token != "secret" { return "401 unauthorized" }
            return next.Handle(req)
        })
    }
}

// 함수를 Handler 로 만들어 주는 어댑터(자주 쓰는 관용구)
type handlerFunc func(string) string
func (f handlerFunc) Handle(req string) string { return f(req) }

func Chain(h Handler, mws ...Middleware) Handler {
    for i := len(mws) - 1; i >= 0; i-- {
        h = mws[i](h)
    }
    return h
}

func main() {
    h := Chain(BaseHandler{},
        Logging("OUTER"),
        Auth("secret"),
        Logging("INNER"),
    )
    fmt.Println("=>", h.Handle("/users/42"))
}

실행 결과

[OUTER] → /users/42 [INNER] → /users/42 [INNER] ← result(/users/42) (5.2µs) [OUTER] ← result(/users/42) (52.1µs) => result(/users/42)
💡 표준 라이브러리의 net/http는 정확히 이 구조다. http.Handler 인터페이스 + 미들웨어 = 데코레이터 패턴.

13. 퍼사드 (Facade)

개요

복잡한 서브시스템 여러 개를 묶어 단일한 단순 인터페이스를 제공한다.

문제

주문 처리는 재고 확인 → 결제 → 배송 라벨 발급 → 알림 발송 네 단계로 이루어지지만, 호출자는 order.Place(req) 한 줄만 쓰고 싶다.

UML

그림 13-1. 퍼사드 — 클라이언트는 단일 진입점만 본다.

// file: facade/main.go
package main

import "fmt"

type Inventory struct{}
func (Inventory) Reserve(sku string, qty int) bool { fmt.Printf("📦 %s × %d 예약\n", sku, qty); return true }

type Payment struct{}
func (Payment) Charge(user string, amount int64) string { fmt.Printf("💳 %s 에게 %d원 청구\n", user, amount); return "PAY-001" }

func (Shipping) CreateLabel(addr string) string { fmt.Printf("🚚 라벨 발급: %s\n", addr); return "LBL-9" }

type Notifier struct{}
func (Notifier) Email(user, msg string) { fmt.Printf("✉️  %s ← %s\n", user, msg) }

}

    lbl := o.ship.CreateLabel(addr)
    o.note.Email(user, fmt.Sprintf("주문 완료! TX=%s, 라벨=%s", tx, lbl))
}

}

14. 플라이웨이트 (Flyweight)

개요

다수의 비슷한 객체에서 변하지 않는 부분(intrinsic state)을 공유 인스턴스로 빼내어 메모리를 절약한다.

문제

문자 100만 개를 렌더링한다. 각 문자가 폰트·크기·색 데이터를 따로 들고 있으면 메모리가 폭발한다. 공통 글리프(Glyph)는 한 번만 만들고, 위치만 인스턴스마다 다르게.

UML

그림 14-1. 플라이웨이트 — 내재 상태는 공유, 외재 상태는 호출 시점에 전달.

Go 구현

// file: flyweight/main.go
package main

import (
    "fmt"
    "sync"
    "unsafe"
)

type Glyph struct {
    Char  rune
    Font  string
    Size  int
    Color string
}

type GlyphFactory struct {
    mu    sync.Mutex
    cache map[rune]*Glyph
}

func NewGlyphFactory() *GlyphFactory { return &GlyphFactory{cache: map[rune]*Glyph{}} }

func (f *GlyphFactory) Get(r rune) *Glyph {
    f.mu.Lock(); defer f.mu.Unlock()
    if g, ok := f.cache[r]; ok { return g }
    g := &Glyph{Char: r, Font: "NotoSerifKR", Size: 14, Color: "#222"}
    f.cache[r] = g
    return g
}

type DrawnChar struct {
    G    *Glyph
    X, Y int
}

func main() {
    factory := NewGlyphFactory()
    text := "안녕하세요 Go!"
    drawn := []DrawnChar{}
    for i, r := range text {
        drawn = append(drawn, DrawnChar{G: factory.Get(r), X: i * 16, Y: 0})
    }
    // 동일 글자는 같은 포인터를 공유한다.
    fmt.Printf("'안' 포인터 = %p\n", factory.Get('안'))
    fmt.Printf("'안' 포인터 = %p (재요청)\n", factory.Get('안'))
    fmt.Printf("총 인쇄 글자=%d, 공유 글리프=%d\n", len(drawn), len(factory.cache))
    fmt.Printf("Glyph 한 개 크기=%d bytes\n", unsafe.Sizeof(Glyph{}))
}

15. 프록시 (Proxy)

개요

실제 객체와 동일한 인터페이스를 가지면서, 호출 전후로 접근 제어·캐싱·지연 로딩·원격 통신 등의 부가 기능을 끼워 넣는다.

문제

고비용 외부 API를 호출하는 서비스가 있다. 같은 인자로의 호출은 60초 동안 캐시하고 싶다. 호출자 코드는 그대로 두고.

UML

그림 15-1. 프록시 — 같은 인터페이스로 실 객체를 감싸 캐싱·인증·로깅을 끼운다.

Go 구현

// file: proxy/main.go
package main

import (
    "fmt"
    "sync"
    "time"
)

type Service interface {
    Lookup(id string) string
}

type RealService struct{}
func (RealService) Lookup(id string) string {
    fmt.Printf("  ↳ 실제 API 호출 (id=%s)\n", id)
    time.Sleep(300 * time.Millisecond)
    return "USER-" + id
}

type entry struct{ val string; exp time.Time }

type CachingProxy struct {
    real Service
    ttl  time.Duration
    mu   sync.Mutex
    cache map[string]entry
}
func NewCachingProxy(s Service, ttl time.Duration) *CachingProxy {
    return &CachingProxy{real: s, ttl: ttl, cache: map[string]entry{}}
}
func (p *CachingProxy) Lookup(id string) string {
    p.mu.Lock()
    if e, ok := p.cache[id]; ok && time.Now().Before(e.exp) {
        p.mu.Unlock()
        fmt.Printf("  ↳ 캐시 적중 (id=%s)\n", id)
        return e.val
    }
    p.mu.Unlock()
    v := p.real.Lookup(id)
    p.mu.Lock(); p.cache[id] = entry{v, time.Now().Add(p.ttl)}; p.mu.Unlock()
    return v
}

func main() {
    var s Service = NewCachingProxy(RealService{}, 60*time.Second)
    for i := 0; i < 3; i++ {
        start := time.Now()
        v := s.Lookup("42")
        fmt.Printf("결과=%s (소요 %v)\n", v, time.Since(start))
    }
}

실행 결과

↳ 실제 API 호출 (id=42) 결과=USER-42 (소요 300.1ms) ↳ 캐시 적중 (id=42) 결과=USER-42 (소요 8.2µs) ↳ 캐시 적중 (id=42) 결과=USER-42 (소요 4.1µs)
장점
- 호출자 코드 변경 0
- 보안·로깅·캐싱을 횡단으로 적용
- gRPC 클라이언트 스텁이 정확히 이 패턴
단점
- 한 단계 더 거치므로 디버깅 추적 길어짐
- 데코레이터와 의도가 미묘하게 다름(접근 제어 vs 동작 추가)

제3부 — GoF 행위 패턴 (Behavioral)

객체들 사이의 책임 분배와 흐름 제어에 관한 11가지 패턴이다. 이 영역은 Go의 일급 함수와 채널 덕분에 GoF 원전보다 훨씬 가볍게 표현되는 경우가 많다.

16. 책임 연쇄 (Chain of Responsibility)

개요

요청을 처리할 후보 객체들을 사슬로 연결해, 누군가 처리하기 전까지 차례대로 넘긴다.

문제

웹 요청에 대한 검증 — 로그인 여부 → 권한 → 입력 검증 → 비즈니스 처리. 각 단계는 통과시키거나 즉시 반려할 수 있어야 하며, 순서를 자유롭게 재조립할 수 있어야 한다.

UML

그림 16-1. 책임 연쇄 — 통과되면 다음으로, 실패하면 즉시 종료.

Go 구현

// file: chain/main.go
package main

import (
    "errors"
    "fmt"
)

type Request struct {
    User    string
    Role    string
    Payload string
}

type Handler func(*Request) error

func Chain(handlers ...Handler) Handler {
    return func(r *Request) error {
        for _, h := range handlers {
            if err := h(r); err != nil { return err }
        }
        return nil
    }
}

func Auth(r *Request) error {
    if r.User == "" { return errors.New("401 unauthorized") }
    fmt.Println("✅ Auth OK:", r.User); return nil
}
func Permission(role string) Handler {
    return func(r *Request) error {
        if r.Role != role { return fmt.Errorf("403 need role %s", role) }
        fmt.Println("✅ Permission OK"); return nil
    }
}
func Validate(r *Request) error {
    if r.Payload == "" { return errors.New("400 empty payload") }
    fmt.Println("✅ Validate OK"); return nil
}
func Business(r *Request) error {
    fmt.Println("🎯 Business 실행:", r.Payload); return nil
}

func main() {
    pipeline := Chain(Auth, Permission("admin"), Validate, Business)
    err := pipeline(&Request{User: "alice", Role: "admin", Payload: "create-user"})
    fmt.Println("err =", err)
    err = pipeline(&Request{User: "bob", Role: "guest", Payload: "x"})
    fmt.Println("err =", err)
}

실행 결과

✅ Auth OK: alice ✅ Permission OK ✅ Validate OK 🎯 Business 실행: create-user err = <nil> ✅ Auth OK: bob err = 403 need role admin

17. 커맨드 (Command)

개요

"무엇을 할 것인가"를 객체로 캡슐화하여, 실행·되돌리기·로그·큐잉을 자유롭게 한다.

문제

텍스트 에디터에 Undo/Redo. 키보드 단축키는 "어떤 명령을 실행했는가"만 기록하면 되고, 실제 일은 명령 객체가 수행한다.

UML

그림 17-1. 커맨드 — 동작과 그 역(逆)을 함께 객체화.

Go 구현

// file: command/main.go
package main

import "fmt"

type Editor struct{ buf []rune }
func (e *Editor) String() string { return string(e.buf) }

type Command interface {
    Execute()
    Undo()
}

type InsertCmd struct{ e *Editor; pos int; ch rune }
func (c *InsertCmd) Execute() {
    c.e.buf = append(c.e.buf[:c.pos], append([]rune{c.ch}, c.e.buf[c.pos:]...)...)
}
func (c *InsertCmd) Undo() {
    c.e.buf = append(c.e.buf[:c.pos], c.e.buf[c.pos+1:]...)
}

type History struct{ stack []Command }
func (h *History) Do(c Command)  { c.Execute(); h.stack = append(h.stack, c) }
func (h *History) Undo() {
    if len(h.stack) == 0 { return }
    top := h.stack[len(h.stack)-1]
    h.stack = h.stack[:len(h.stack)-1]
    top.Undo()
}

func main() {
    e := &Editor{}
    h := &History{}
    for i, r := range "HELLO" {
        h.Do(&InsertCmd{e: e, pos: i, ch: r})
    }
    fmt.Println("입력 후:", e)
    h.Undo(); h.Undo()
    fmt.Println("Undo 2회:", e)
}

입력 후: HELLO Undo 2회: HEL

18. 반복자 (Iterator)

개요

컬렉션 내부 구조를 노출하지 않고 원소들을 차례로 접근한다. Go에서는 for range·콜백·1.23부터 도입된 range-over-func로 표현한다.

UML

그림 18-1. 반복자 — 컬렉션 내부를 감춘 채 원소만 순회.

Go 구현 (제너릭 + range-over-func)

// file: iterator/main.go  (go 1.23+)
package main

import "fmt"

type RingBuffer[T any] struct{ data []T; head, n int }

func NewRing[T any](cap int) *RingBuffer[T] { return &RingBuffer[T]{data: make([]T, cap)} }

func (r *RingBuffer[T]) Push(v T) {
    if r.n < len(r.data) {
        r.data[(r.head+r.n)%len(r.data)] = v; r.n++
    } else {
        r.data[r.head] = v; r.head = (r.head + 1) % len(r.data)
    }
}

// Go 1.23 range-over-func: func(yield func(int, T) bool)  (iter.Seq2 형태)
func (r *RingBuffer[T]) All() func(yield func(int, T) bool) {
    return func(yield func(int, T) bool) {
        for i := 0; i < r.n; i++ {
            v := r.data[(r.head+i)%len(r.data)]
            if !yield(i, v) { return }
        }
    }
}

func main() {
    r := NewRing[string](3)
    for _, w := range []string{"가", "나", "다", "라", "마"} { r.Push(w) }
    for i, v := range r.All() {
        fmt.Printf("[%d] %s\n", i, v)
    }
}

실행 결과

[0] 다 [1] 라 [2] 마
💡 Go 1.23 미만에선 chan T를 반환하거나 콜백 func(T) bool을 받는 형태로 구현해 왔다.

19. 중재자 (Mediator)

개요

문제

채팅방에서 사용자 100명이 서로 직접 메시지를 전송하면 의존이 폭증한다. 중재자(채팅방)가 한가운데 있고, 사용자는 채팅방에만 의존한다.

UML

그림 19-1. 중재자 — 모든 통신이 중심을 거친다.

// file: mediator/main.go
package main

import "fmt"

type ChatRoom struct{ users map[string]*User }

func NewChatRoom() *ChatRoom { return &ChatRoom{users: map[string]*User{}} }
func (c *ChatRoom) Join(u *User) { c.users[u.name] = u; u.room = c }
func (c *ChatRoom) Send(from, msg string) {
    for name, u := range c.users {
        if name == from { continue }
        u.Receive(from, msg)
    }
}

type User struct{ name string; room *ChatRoom }
func (u *User) Say(msg string)             { u.room.Send(u.name, msg) }
func (u *User) Receive(from, msg string)   { fmt.Printf("[%s] %s ← %s\n", u.name, from, msg) }

func main() {
    room := NewChatRoom()
    alice := &User{name: "Alice"}; bob := &User{name: "Bob"}; carol := &User{name: "Carol"}
    for _, u := range []*User{alice, bob, carol} { room.Join(u) }
    alice.Say("안녕!")
    bob.Say("점심 뭐 먹지?")
}

개요

UML

그림 24-1. 템플릿 메서드 — 상위가 흐름을 강제한다.

// file: template/main.go
package main

import "fmt"

// 가변 단계를 인터페이스로 정의
type Pipeline interface {
    Extract() []string
    Transform([]string) []string
    Load([]string)
}

// 템플릿 — 모든 파이프라인의 공통 흐름
func Run(p Pipeline) {
    raw := p.Extract()
    fmt.Println("  ① Extract:", raw)
    transformed := p.Transform(raw)
    fmt.Println("  ② Transform:", transformed)
    p.Load(transformed)
}

type CSVPipeline struct{}
func (CSVPipeline) Extract() []string             { return []string{"a,1", "b,2"} }
func (CSVPipeline) Transform(xs []string) []string {
    out := make([]string, len(xs))
    for i, x := range xs { out[i] = "[CSV] " + x }
    return out
}
func (CSVPipeline) Load(xs []string) { fmt.Println("  ③ Load(CSV):", xs) }

type JSONPipeline struct{}
func (JSONPipeline) Extract() []string             { return []string{`{"a":1}`, `{"b":2}`} }
func (JSONPipeline) Transform(xs []string) []string {
    out := make([]string, len(xs))
    for i, x := range xs { out[i] = "[JSON] " + x }
    return out
}
func (JSONPipeline) Load(xs []string) { fmt.Println("  ③ Load(JSON):", xs) }

func main() {
    fmt.Println("--- CSV ---");  Run(CSVPipeline{})
    fmt.Println("--- JSON ---"); Run(JSONPipeline{})
}

25. 방문자 (Visitor)

개요

데이터 구조와 그 위에 수행하는 알고리즘을 분리한다. 새로운 연산을 추가할 때 데이터 타입을 건드리지 않아도 된다.

문제

AST(추상 구문 트리)에 출력기·평가기·타입체커를 따로 만들고 싶다. 노드 타입에 메서드를 끝없이 추가하면 노드가 비대해진다.

UML

그림 25-1. 방문자 — Node 가 Visitor 를 받아 적절한 메서드를 다시 호출(이중 디스패치).

Go 구현

// file: visitor/main.go
package main

import "fmt"

type Visitor interface {
    VisitNum(*Num)
    VisitBinOp(*BinOp)
}

type Node interface{ Accept(Visitor) }

type Num struct{ Val float64 }
func (n *Num) Accept(v Visitor) { v.VisitNum(n) }

type BinOp struct{ Op byte; L, R Node }
func (b *BinOp) Accept(v Visitor) { v.VisitBinOp(b) }

// 1) 출력 비지터
type Printer struct{ out string }
func (p *Printer) VisitNum(n *Num)     { p.out += fmt.Sprintf("%g", n.Val) }
func (p *Printer) VisitBinOp(b *BinOp) {
    p.out += "(" ; b.L.Accept(p)
    p.out += fmt.Sprintf("%c", b.Op)
    b.R.Accept(p); p.out += ")"
}

// 2) 평가 비지터
type Eval struct{ result float64 }
func (e *Eval) VisitNum(n *Num) { e.result = n.Val }
func (e *Eval) VisitBinOp(b *BinOp) {
    lv := &Eval{}; b.L.Accept(lv)
    rv := &Eval{}; b.R.Accept(rv)
    switch b.Op {
    case '+': e.result = lv.result + rv.result
    case '*': e.result = lv.result * rv.result
    }
}

func main() {
    // (2 + 3) * 4
    ast := &BinOp{Op: '*',
        L: &BinOp{Op: '+', L: &Num{2}, R: &Num{3}},
        R: &Num{4},
    }
    p := &Printer{}; ast.Accept(p); fmt.Println("AST :", p.out)
    e := &Eval{};    ast.Accept(e); fmt.Println("값  :", e.result)
}

실행 결과

AST : ((2+3)*4) 값 : 20

26. 인터프리터 (Interpreter)

개요

특정 도메인에 맞는 문법을 정의하고, 그 문장을 해석해 실행한다. 작은 DSL(예: 검색 조건식, 라우팅 규칙)에 적합하다.

문제

"age > 18 AND country = KR" 같은 표현식을 코드 변경 없이 입력으로 받아 평가하고 싶다.

UML

그림 26-1. 인터프리터 — 문법의 각 단위가 노드.

Go 구현

// file: interpreter/main.go
package main

import "fmt"

type Ctx map[string]any

type Expr interface{ Eval(Ctx) bool }

type Eq  struct{ Key string; Val any }
type Gt  struct{ Key string; Val int }
type And struct{ L, R Expr }
type Or  struct{ L, R Expr }
type Not struct{ E Expr }

func (e Eq)  Eval(c Ctx) bool { return c[e.Key] == e.Val }
func (e Gt)  Eval(c Ctx) bool { v, _ := c[e.Key].(int); return v > e.Val }
func (a And) Eval(c Ctx) bool { return a.L.Eval(c) && a.R.Eval(c) }
func (o Or)  Eval(c Ctx) bool { return o.L.Eval(c) || o.R.Eval(c) }
func (n Not) Eval(c Ctx) bool { return !n.E.Eval(c) }

func main() {
    // age > 18 AND (country = KR OR country = JP)
    expr := And{
        L: Gt{"age", 18},
        R: Or{L: Eq{"country", "KR"}, R: Eq{"country", "JP"}},
    }
    users := []Ctx{
        {"name": "alice", "age": 25, "country": "KR"},
        {"name": "bob",   "age": 17, "country": "KR"},
        {"name": "carl",  "age": 30, "country": "US"},
    }
    for _, u := range users {
        fmt.Printf("%s → %v\n", u["name"], expr.Eval(u))
    }
}

실행 결과

alice → true bob → false carl → false
💡 실무에선 직접 손으로 AST 노드를 만들지 않고, antlr4-go·participle 같은 파서 라이브러리로 텍스트를 AST 로 만든 뒤 같은 Eval 인터페이스로 평가한다.

제4부 — Go 고유 동시성·구조 패턴

여기부터는 GoF 책에 없는, Go 커뮤니티가 직접 다듬어 온 패턴이다. 채널·고루틴·일급 함수·임베딩 같은 언어 기능에 정확히 맞춰져 있어, 다른 언어로 그대로 옮기기 어렵다.

27. 함수형 옵션 (Functional Options)

개요

생성자에 옵션을 "필드 = 값" 키워드 인자처럼 넘기는 Go의 사실상 표준 패턴. 자바·C# 의 빌더 대체재.

UML

그림 27-1. 함수형 옵션 — 옵션 자체가 일급 함수.

Go 구현

// file: options/main.go
package main

import (
    "fmt"
    "time"
)

type Server struct {
    Host    string
    Port    int
    TLS     bool
    Timeout time.Duration
    Logger  func(string)
}

type Option func(*Server)

func WithPort(p int) Option           { return func(s *Server) { s.Port = p } }
func WithTLS() Option                  { return func(s *Server) { s.TLS = true } }
func WithTimeout(d time.Duration) Option { return func(s *Server) { s.Timeout = d } }
func WithLogger(l func(string)) Option { return func(s *Server) { s.Logger = l } }

func NewServer(host string, opts ...Option) *Server {
    s := &Server{Host: host, Port: 80, Timeout: 30 * time.Second,
        Logger: func(string) {}}
    for _, o := range opts { o(s) }
    return s
}

func main() {
    s := NewServer("api.local",
        WithPort(8443),
        WithTLS(),
        WithTimeout(5*time.Second),
        WithLogger(func(m string) { fmt.Println("LOG:", m) }),
    )
    s.Logger("서버 시작")
    fmt.Printf("%+v\n", *s)
}

- 옵션이 5개 미만이면 그냥 구조체 리터럴이 더 간결

28. 임베딩 (Embedding)

개요

구조체에 다른 타입을 무명(無名)으로 포함시키면, 그 타입의 메서드와 필드가 자동으로 승격(promote)된다. Go의 "상속 대신 합성"의 가장 강력한 도구.

Go 구현

// file: embedding/main.go
package main

import "fmt"

// 공통 동작을 가진 타입
type Logger struct{ Prefix string }
func (l Logger) Log(msg string) { fmt.Printf("[%s] %s\n", l.Prefix, msg) }

// User 는 Logger 를 임베딩 → User 도 Log() 메서드를 자동으로 가짐
type User struct {
    Logger
    Name string
}

// HTTPServer 는 net/http 의 Server 를 임베딩하여 모든 메서드를 그대로 노출하면서
// 추가 필드(Stats)를 덧붙인다.
type Stats struct{ Hits int }

type Service struct {
    *Logger          // 포인터 임베딩도 가능
    Stats
    Endpoint string
}

func main() {
    u := User{Logger: Logger{Prefix: "USER"}, Name: "alice"}
    u.Log("회원가입")        // Logger 의 메서드를 직접 호출

    s := &Service{Logger: &Logger{Prefix: "API"}, Endpoint: "/v1"}
    s.Log("부팅")            // 임베딩된 로거
    s.Hits = 42              // 임베딩된 Stats.Hits
    fmt.Println("hits:", s.Hits, "ep:", s.Endpoint)
}

실행 결과

[USER] 회원가입 [API] 부팅 hits: 42 ep: /v1
⚠️ 이름 충돌: 임베딩한 두 타입이 같은 이름의 메서드를 가지면 외부에서 직접 호출 시 모호성 컴파일 에러가 난다. 명시적으로 u.Logger.Log(...)로 풀어 호출해야 한다.

29. 컨텍스트 (Context)

개요

요청 범위(request-scope)의 취소 신호·데드라인·메타데이터를 함수 호출 사슬을 따라 전파하는 표준 메커니즘. context.Context는 모든 Go 서버 코드의 첫 번째 인자다.

UML

그림 29-1. Context — 트리 형태로 파생되며 한 곳에서 취소하면 자손 전체가 종료.

Go 구현

// file: context/main.go
package main

import (
    "context"
    "errors"
    "fmt"
    "time"
)

func longJob(ctx context.Context, id int) error {
    select {
    case <-time.After(300 * time.Millisecond):
        fmt.Printf("job %d done\n", id); return nil
    case <-ctx.Done():
        return fmt.Errorf("job %d cancelled: %w", id, ctx.Err())
    }
}

func main() {
    // 200ms 후 자동 취소되는 ctx
    ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
    defer cancel()

    for i := 1; i <= 3; i++ {
        go func(i int) {
            if err := longJob(ctx, i); err != nil { fmt.Println(err) }
        }(i)
    }
    <-ctx.Done()
    fmt.Println("ctx 종료, 사유:", ctx.Err(), "  is DeadlineExceeded?",
        errors.Is(ctx.Err(), context.DeadlineExceeded))
    time.Sleep(100 * time.Millisecond) // 고루틴 출력 대기
}

실행 결과 (줄 순서는 매번 다름)

ctx 종료, 사유: context deadline exceeded is DeadlineExceeded? true job 1 cancelled: context deadline exceeded job 2 cancelled: context deadline exceeded job 3 cancelled: context deadline exceeded
📌 규칙: 함수의 첫 인자에 ctx context.Context를 두고, 구조체 필드에는 절대 저장하지 말 것. context.Background()는 최상위에서만.

30. 파이프라인 (Pipeline)

개요

각 단계가 채널을 입력으로 받고 채널을 출력으로 내보내는 처리 사슬. 단계 사이를 채널이 잇고 각 단계는 독립된 고루틴에서 돈다.

UML

그림 30-1. 파이프라인 — 단계 사이를 채널이 잇는다.

Go 구현

// file: pipeline/main.go
package main

import "fmt"

func source(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums { out <- n }
    }()
    return out
}

func square(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in { out <- n * n }
    }()
    return out
}

func filterOdd(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in { if n%2 == 1 { out <- n } }
    }()
    return out
}

func main() {
    for v := range filterOdd(square(source(1, 2, 3, 4, 5, 6))) {
        fmt.Println(v)
    }
}

실행 결과

1 9 25
💡 각 단계가 defer close(out)를 책임진다. 누군가 빠뜨리면 다운스트림이 영원히 막힌다.

31. 팬아웃·팬인 (Fan-out / Fan-in)

개요

하나의 채널을 여러 워커에게 분산(fan-out)하고, 결과를 하나로 합친다(fan-in). 병렬화로 처리량을 끌어올리는 가장 흔한 동시성 패턴.

UML

그림 31-1. 팬아웃·팬인 — 같은 채널을 여러 워커가 읽고, 결과를 하나로 합친다.

Go 구현

// file: fanout/main.go
package main

import (
    "fmt"
    "sync"
    "time"
)

func worker(id int, in <-chan int, out chan<- int) {
    for n := range in {
        time.Sleep(50 * time.Millisecond) // 작업 흉내
        fmt.Printf("worker %d processed %d\n", id, n)
        out <- n * 10
    }
}

func merge(channels ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, ch := range channels {
        wg.Add(1)
        go func(c <-chan int) {
            defer wg.Done()
            for v := range c { out <- v }
        }(ch)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

func main() {
    in := make(chan int)
    go func() {
        defer close(in)
        for i := 1; i <= 9; i++ { in <- i }
    }()

    // Fan-out: 3개의 워커
    var outs []<-chan int
    for w := 1; w <= 3; w++ {
        o := make(chan int)
        outs = append(outs, o)
        go func(id int, o chan int) {
            defer close(o)
            worker(id, in, o)
        }(w, o)
    }

    // Fan-in
    for v := range merge(outs...) {
        fmt.Println("→", v)
    }
}

실행 결과 (순서·워커 배정은 매번 다름)

worker 2 processed 1 worker 1 processed 2 worker 3 processed 3 → 10 → 20 → 30 worker 1 processed 4 ... (이하 생략)

32. 워커 풀 (Worker Pool)

개요

고정된 개수의 워커 고루틴이 작업 큐에서 일을 꺼내 처리한다. 무한 고루틴 생성으로 인한 메모리·스케줄러 부담을 막는다.

Go 구현

// file: workerpool/main.go
package main

import (
    "fmt"
    "sync"
    "time"
)

type Job struct{ ID int; Payload string }
type Result struct{ JobID int; Out string }

func runPool(workers int, jobs <-chan Job) <-chan Result {
    results := make(chan Result)
    var wg sync.WaitGroup
    for w := 1; w <= workers; w++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            for j := range jobs {
                time.Sleep(50 * time.Millisecond)
                results <- Result{JobID: j.ID, Out: fmt.Sprintf("w%d↦%s", id, j.Payload)}
            }
        }(w)
    }
    go func() { wg.Wait(); close(results) }()
    return results
}

func main() {
    jobs := make(chan Job)
    go func() {
        defer close(jobs)
        for i := 1; i <= 6; i++ { jobs <- Job{ID: i, Payload: fmt.Sprintf("task-%d", i)} }
    }()

    for r := range runPool(3, jobs) {
        fmt.Printf("✅ job %d → %s\n", r.JobID, r.Out)
    }
}

실행 결과 (완료 순서·워커 배정은 매번 다름)

✅ job 2 → w2↦task-2 ✅ job 1 → w1↦task-1 ✅ job 3 → w3↦task-3 ✅ job 4 → w1↦task-4 ✅ job 5 → w2↦task-5 ✅ job 6 → w3↦task-6

33. 발행·구독 (Pub/Sub)

개요

옵저버 패턴의 비동기·다채널 버전. 발행자는 토픽에 메시지를 던지고, 구독자들은 자기 채널로 받는다. 발행자와 구독자는 서로의 존재를 모른다.

Go 구현

// file: pubsub/main.go
package main

import (
    "fmt"
    "sync"
    "time"
)

type Broker[T any] struct {
    mu   sync.Mutex
    subs map[string][]chan T
}

func NewBroker[T any]() *Broker[T] { return &Broker[T]{subs: map[string][]chan T{}} }

func (b *Broker[T]) Subscribe(topic string, buf int) <-chan T {
    ch := make(chan T, buf)
    b.mu.Lock(); b.subs[topic] = append(b.subs[topic], ch); b.mu.Unlock()
    return ch
}

func (b *Broker[T]) Publish(topic string, msg T) {
    b.mu.Lock(); chans := append([]chan T(nil), b.subs[topic]...); b.mu.Unlock()
    for _, ch := range chans {
        select {
        case ch <- msg:
        default: // 느린 구독자는 메시지 드롭
        }
    }
}

func main() {
    br := NewBroker[string]()
    news  := br.Subscribe("news", 4)
    sport := br.Subscribe("sports", 4)

    go func() {
        for m := range news  { fmt.Println("[NEWS]",  m) }
    }()
    go func() {
        for m := range sport { fmt.Println("[SPORT]", m) }
    }()

    br.Publish("news",  "기준금리 동결")
    br.Publish("sports","KBO 개막")
    br.Publish("news",  "환율 1,320원")
    time.Sleep(100 * time.Millisecond)
}

실행 결과 (줄 순서는 매번 다름)

[NEWS] 기준금리 동결 [SPORT] KBO 개막 [NEWS] 환율 1,320원

34. Done 채널

개요

외부에서 종료 신호를 전파하는 가장 단순한 형태. close(done)가 곧 "모두 종료"를 의미한다.

Go 구현

// file: done/main.go
package main

import (
    "fmt"
    "time"
)

func tick(done <-chan struct{}, name string) {
    for {
        select {
        case <-done:
            fmt.Printf("%s 종료\n", name); return
        case t := <-time.After(80 * time.Millisecond):
            fmt.Printf("%s tick @ %v\n", name, t.Format("15:04:05.000"))
        }
    }
}

func main() {
    done := make(chan struct{})
    go tick(done, "A")
    go tick(done, "B")
    time.Sleep(250 * time.Millisecond)
    close(done) // 모든 워커에게 종료 신호
    time.Sleep(50 * time.Millisecond)
}

실행 결과 (A·B의 순서는 매번 다름)

A tick @ 12:00:00.080 B tick @ 12:00:00.080 A tick @ 12:00:00.160 B tick @ 12:00:00.160 A tick @ 12:00:00.240 B tick @ 12:00:00.240 A 종료 B 종료
💡 chan struct{}를 쓰는 이유: 데이터 자체가 의미 없고 "닫힘" 만 신호이므로 0바이트 타입을 쓴다.

35. Or 채널

개요

여러 done 채널 중 하나라도 닫히면 자기 자신도 닫히는 합성 채널. 다중 취소 소스를 하나로 합칠 때 쓴다.

Go 구현

// file: or/main.go
package main

import (
    "fmt"
    "time"
)

// 가변 개수의 done 채널을 받아 하나라도 닫히면 자기도 닫힘.
func or(channels ...<-chan struct{}) <-chan struct{} {
    switch len(channels) {
    case 0: return nil
    case 1: return channels[0]
    }
    orDone := make(chan struct{})
    go func() {
        defer close(orDone)
        switch len(channels) {
        case 2:
            select { case <-channels[0]: case <-channels[1]: }
        default:
            select {
            case <-channels[0]:
            case <-channels[1]:
            case <-channels[2]:
            case <-or(append(channels[3:], orDone)...):
            }
        }
    }()
    return orDone
}

func sig(after time.Duration) <-chan struct{} {
    c := make(chan struct{})
    go func() { time.Sleep(after); close(c) }()
    return c
}

func main() {
    start := time.Now()
    <-or(
        sig(2*time.Second),
        sig(500*time.Millisecond),  // 이게 가장 빨리 닫힘
        sig(1*time.Second),
    )
    fmt.Printf("끝났음, 경과 %v\n", time.Since(start).Round(time.Millisecond))
}

실행 결과

끝났음, 경과 500ms

36. Tee 채널

개요

유닉스의 tee처럼, 한 채널의 값을 두 채널로 동시에 복제한다. 같은 데이터로 분기 작업이 필요할 때 사용.

Go 구현

// file: tee/main.go
package main

import "fmt"

func tee(done <-chan struct{}, in <-chan int) (<-chan int, <-chan int) {
    out1, out2 := make(chan int), make(chan int)
    go func() {
        defer close(out1); defer close(out2)
        for v := range in {
            var a, b = out1, out2
            for i := 0; i < 2; i++ {
                select {
                case <-done: return
                case a <- v: a = nil
                case b <- v: b = nil
                }
            }
        }
    }()
    return out1, out2
}

func gen() <-chan int {
    c := make(chan int)
    go func() {
        defer close(c)
        for i := 1; i <= 5; i++ { c <- i }
    }()
    return c
}

func main() {
    done := make(chan struct{}); defer close(done)
    a, b := tee(done, gen())
    for v := range a {
        fmt.Printf("a=%d  b=%d\n", v, <-b)
    }
}

실행 결과

a=1 b=1 a=2 b=2 a=3 b=3 a=4 b=4 a=5 b=5

37. Bridge 채널

개요

채널들의 채널(<-chan (<-chan T))을 받아, 단일 채널처럼 평탄화한다. 동적으로 변하는 채널 스트림을 소비할 때 쓴다.

Go 구현

// file: bridge/main.go
package main

import "fmt"

func bridge(done <-chan struct{}, chs <-chan <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for {
            var stream <-chan int
            select {
            case maybe, ok := <-chs:
                if !ok { return }
                stream = maybe
            case <-done: return
            }
            for v := range stream {
                select {
                case out <- v:
                case <-done: return
                }
            }
        }
    }()
    return out
}

func genCh(vals ...int) <-chan int {
    c := make(chan int)
    go func() { defer close(c); for _, v := range vals { c <- v } }()
    return c
}

func main() {
    done := make(chan struct{}); defer close(done)
    streams := make(chan (<-chan int))
    go func() {
        defer close(streams)
        streams <- genCh(1, 2, 3)
        streams <- genCh(10, 20)
        streams <- genCh(100, 200, 300, 400)
    }()
    for v := range bridge(done, streams) {
        fmt.Print(v, " ")
    }
    fmt.Println()
}

실행 결과

1 2 3 10 20 100 200 300 400

38. Errgroup (golang.org/x/sync/errgroup)

개요

여러 고루틴 중 하나라도 에러가 나면 컨텍스트를 취소하고 첫 번째 에러를 반환하는 표준급 라이브러리. 동시에 시작·기다림·취소를 한 객체에 모은 패턴.

Go 구현

// file: errgroup/main.go  (go get golang.org/x/sync/errgroup)
package main

import (
    "context"
    "errors"
    "fmt"
    "time"

    "golang.org/x/sync/errgroup"
)

func fetch(ctx context.Context, name string, dur time.Duration, fail bool) error {
    select {
    case <-time.After(dur):
        if fail { return fmt.Errorf("%s 실패", name) }
        fmt.Printf("✅ %s 완료\n", name); return nil
    case <-ctx.Done():
        fmt.Printf("⛔ %s 취소: %v\n", name, ctx.Err()); return ctx.Err()
    }
}

func main() {
    g, ctx := errgroup.WithContext(context.Background())
    g.Go(func() error { return fetch(ctx, "users",   200*time.Millisecond, false) })
    g.Go(func() error { return fetch(ctx, "orders",  100*time.Millisecond, true) }) // 실패!
    g.Go(func() error { return fetch(ctx, "stocks",  500*time.Millisecond, false) })

    if err := g.Wait(); err != nil {
        fmt.Println("그룹 에러:", err, "  is cancel?", errors.Is(ctx.Err(), context.Canceled))
    }
}

실행 결과

⛔ stocks 취소: context canceled ⛔ users 취소: context canceled 그룹 에러: orders 실패 is cancel? true

orders 가 100ms 시점에 에러를 반환하면(실패 분기는 아무것도 출력하지 않는다) 그룹 컨텍스트가 즉시 취소되고, 아직 대기 중이던 users·stocks 는 ctx.Done() 분기로 빠져 취소 메시지를 찍는다. 두 취소 줄의 순서는 실행마다 다르다.

📌 표준에는 들어가 있지 않지만 사실상 모든 마이크로서비스 Go 코드가 쓰는 패턴이다. sync.WaitGroup은 "기다림만" 책임지지만, errgroup 은 기다림·에러 전파·취소를 한 번에 해 준다.

제5부 — Go 관용(idiomatic) 패턴

여기는 "패턴"이라기보다 Go 코드 리뷰에서 항상 거론되는 일곱 가지 관용구다. 표준 라이브러리 코드를 읽으면 모두 여기에 부합한다.

39. "인터페이스를 받고 구조체를 반환하라"

핵심 원칙

  • 받을 때는 인터페이스로 — 호출자가 자유롭게 구현을 끼울 수 있다.
  • 반환할 때는 구조체(또는 포인터)로 — 호출자는 모든 필드·메서드에 접근할 수 있다.

UML

그림 39-1. 받는 쪽=추상, 주는 쪽=구체.

Go 구현

// file: accept/main.go
package main

import "fmt"

type Store interface {
    Save(key, value string) error
}

type Receipt struct {
    ID   string
    Path string  // 구조체이므로 호출자가 .Path 같은 필드에 직접 접근 가능
}

type fileStore struct{}
func (fileStore) Save(k, v string) error { fmt.Printf("file: %s=%s\n", k, v); return nil }

type memStore struct{}
func (memStore) Save(k, v string) error  { fmt.Printf("mem:  %s=%s\n", k, v); return nil }

// 인터페이스를 받고, 구체 구조체를 반환한다.
func WriteOrder(s Store, order string) *Receipt {
    _ = s.Save("order:1", order)
    return &Receipt{ID: "order:1", Path: "/tmp/order:1"}
}

func main() {
    r := WriteOrder(fileStore{}, "USB허브 ×2")
    fmt.Printf("%+v\n", *r)
    r = WriteOrder(memStore{}, "키보드")
    fmt.Printf("%+v\n", *r)
}

40. 상속 대신 합성 (Composition over Inheritance)

개요

Go에는 상속 자체가 없다. "is-a" 관계는 인터페이스 만족으로, "has-a/has-some-of-a"는 임베딩으로 표현한다.

나쁜 예 vs 좋은 예

// 🚫 자바식 사고: "Admin은 User를 상속해야 한다"
// → Go에서는 컴파일조차 안 됨. 더 깊게 보면 잘못된 추론이다.

// ✅ Go식: User 의 기능을 그대로 빌려쓰고 권한만 더한다
package main

import "fmt"

type User struct{ Name string; Age int }
func (u User) Greet() string { return "안녕, 나는 " + u.Name }

type Admin struct {
    User              // 임베딩 — User 의 필드·메서드가 그대로 승격
    Permissions []string
}

func (a Admin) Has(p string) bool {
    for _, x := range a.Permissions { if x == p { return true } }
    return false
}

func main() {
    a := Admin{User: User{Name: "alice", Age: 30}, Permissions: []string{"read","write"}}
    fmt.Println(a.Greet())           // User 의 메서드를 그대로 사용
    fmt.Println("write?", a.Has("write"))
    fmt.Println("name :", a.Name)    // User.Name 이 승격되어 직접 접근
}

실행 결과

안녕, 나는 alice write? true name : alice

41. 에러 래핑 (errors.Is / errors.As / %w)

개요

Go 1.13 이후 표준 에러 처리. 원본 에러를 잃지 않고 컨텍스트를 덧붙인다.

Go 구현

// file: errwrap/main.go
package main

import (
    "errors"
    "fmt"
    "os"
)

// 1) 센티넬 에러
var ErrNotFound = errors.New("not found")

// 2) 커스텀 에러 타입 (errors.As 의 대상)
type ValidationError struct{ Field, Reason string }
func (e *ValidationError) Error() string { return fmt.Sprintf("invalid %s: %s", e.Field, e.Reason) }

func loadUser(id int) error {
    return fmt.Errorf("loadUser(%d): %w", id, ErrNotFound)        // 래핑
}

func parseInput(name string) error {
    return fmt.Errorf("parseInput: %w", &ValidationError{Field: "email", Reason: "missing @"})
}

func main() {
    if err := loadUser(7); err != nil {
        fmt.Println(err)
        if errors.Is(err, ErrNotFound) {
            fmt.Println("  → 404 처리")
        }
    }
    if err := parseInput("alice"); err != nil {
        var ve *ValidationError
        if errors.As(err, &ve) {
            fmt.Printf("  → 400: field=%s, reason=%s\n", ve.Field, ve.Reason)
        }
    }
    // 표준 라이브러리도 같은 약속을 따른다
    _, err := os.Open("/no/such/file")
    fmt.Println("os 에러:", errors.Is(err, os.ErrNotExist))
}

실행 결과

loadUser(7): not found → 404 처리 → 400: field=email, reason=missing @ os 에러: true
원칙
- 컨텍스트는 fmt.Errorf("X: %w", err)
- 식별은 errors.Is (값) / errors.As (타입)
- 절대 err.Error() == "..." 비교 금지
피할 것
- %v 로 원본을 잃는 래핑
- nil 에러를 한 번 더 래핑(이중 nil 함정)

42. 테이블 주도 테스트 (Table-Driven Tests)

개요

Go의 표준 테스트 양식. 입력·기대 출력 쌍을 슬라이스에 모아 한 번에 돌린다. 새 케이스 추가가 한 줄.

Go 구현

// file: table/sum_test.go
package table

import "testing"

func Sum(xs []int) int {
    s := 0
    for _, x := range xs { s += x }
    return s
}

func TestSum(t *testing.T) {
    cases := []struct{
        name string
        in   []int
        want int
    }{
        {"empty",    nil,            0},
        {"single",   []int{42},      42},
        {"three",    []int{1,2,3},   6},
        {"negative", []int{-1,1,-2}, -2},
        {"large",    []int{1_000_000, 2_000_000}, 3_000_000},
    }
    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            got := Sum(c.in)
            if got != c.want {
                t.Errorf("Sum(%v) = %d, want %d", c.in, got, c.want)
            }
        })
    }
}

43. 제로값을 유용하게 (Zero Value Useful)

개요

구조체를 var x T만으로도 의미 있는 상태로 두는 설계. 명시적 생성자를 강요하지 말 것.

Go 구현

// file: zero/main.go
package main

import (
    "bytes"
    "fmt"
    "sync"
)

func main() {
    // 1) sync.Mutex 의 제로값은 unlock 상태. 초기화 불필요.
    var mu sync.Mutex
    mu.Lock(); mu.Unlock()

    // 2) bytes.Buffer 도 제로값으로 바로 사용 가능
    var buf bytes.Buffer
    buf.WriteString("hello ")
    buf.WriteString("zero value")
    fmt.Println(buf.String())

    // 3) 우리도 같은 원칙을 따르자: nil 슬라이스에 append 가능
    var nums []int
    for i := 1; i <= 3; i++ { nums = append(nums, i) }
    fmt.Println(nums)

    // 4) 빈 맵 읽기는 안전, 쓰기는 nil 맵 패닉 → 그래서 자주 쓰는 맵 필드는 lazy-init
    type Tag struct{ kv map[string]string }
    var t Tag
    fmt.Println(t.kv["x"])  // 안전: "" 반환
}

실행 결과

hello zero value [1 2 3]

44. 센티넬 에러와 에러 타입

개요

에러를 어떻게 표현할 것인가에 대한 세 가지 도구. 상황에 맞게 골라 쓴다.

도구언제예시
센티넬 (전역 var)"종류"만 알면 충분할 때io.EOF, sql.ErrNoRows
에러 타입 (struct)추가 컨텍스트(필드)가 필요할 때*os.PathError, *json.SyntaxError
%w 래핑경로를 따라 컨텍스트를 추가할 때fmt.Errorf("read cfg: %w", err)

Go 구현

// file: sentinel/main.go
package main

import (
    "errors"
    "fmt"
)

// 1) 센티넬
var (
    ErrNotFound = errors.New("not found")
    ErrConflict = errors.New("conflict")
)

// 2) 타입
type RetryableError struct{ Op string; After int }
func (e *RetryableError) Error() string { return fmt.Sprintf("%s 일시 실패, %d초 후 재시도", e.Op, e.After) }
func (e *RetryableError) Retryable() bool { return true }

func get(id int) error {
    if id == 0 { return ErrNotFound }
    if id == 1 { return &RetryableError{Op: "GET", After: 3} }
    return nil
}

func main() {
    for _, id := range []int{0, 1, 99} {
        err := get(id)
        switch {
        case err == nil:
            fmt.Println(id, "OK")
        case errors.Is(err, ErrNotFound):
            fmt.Println(id, "404")
        default:
            var re *RetryableError
            if errors.As(err, &re) {
                fmt.Println(id, "재시도 가능:", re.Error())
            } else {
                fmt.Println(id, "기타:", err)
            }
        }
    }
}

실행 결과

0 404 1 재시도 가능: GET 일시 실패, 3초 후 재시도 99 OK

45. 빈 구조체 활용 (struct{})

개요

크기 0 바이트. "값 자체엔 정보 없음, 존재만이 의미"인 자리에 쓰는 Go의 관용 타입.

주요 용도

  1. 집합(set): map[string]struct{} — map[string]bool 보다 메모리 절약
  2. 신호 채널: chan struct{} — done/cancel 신호 전용
  3. 메서드만 가진 타입: 상태가 필요 없는 stateless 서비스

Go 구현

// file: empty/main.go
package main

import (
    "fmt"
    "unsafe"
)

// 1) 집합
type Set[T comparable] struct{ m map[T]struct{} }
func NewSet[T comparable]() *Set[T] { return &Set[T]{m: map[T]struct{}{}} }
func (s *Set[T]) Add(v T)           { s.m[v] = struct{}{} }
func (s *Set[T]) Has(v T) bool      { _, ok := s.m[v]; return ok }
func (s *Set[T]) Len() int          { return len(s.m) }

// 2) stateless 서비스
type GreetService struct{}
func (GreetService) Hello(name string) string { return "안녕, " + name }

func main() {
    fmt.Println("크기:", unsafe.Sizeof(struct{}{}), "byte")

    s := NewSet[string]()
    for _, w := range []string{"go", "rust", "go", "zig", "rust"} { s.Add(w) }
    fmt.Println("Set 크기:", s.Len(), " has go?", s.Has("go"))

    // 신호 채널
    done := make(chan struct{})
    go func() { fmt.Println("작업 중..."); close(done) }()
    <-done
    fmt.Println("완료 신호 받음")

    fmt.Println(GreetService{}.Hello("Go 개발자"))
}

실행 결과

크기: 0 byte Set 크기: 3 has go? true 작업 중... 완료 신호 받음 안녕, Go 개발자

C. Go 에서 자주 보이는 안티패턴

  1. 인터페이스 남발. "혹시 모를 미래"를 위해 만든 추상은 거의 항상 잘못된 추상이다. 실제 다른 구현이 생긴 뒤에 인터페이스를 정의하라.
  2. 패키지 한 개에 모든 인터페이스. "interfaces.go" 같은 파일은 의존성 역전 원칙을 깬다. 인터페이스는 사용하는 쪽 패키지에 둔다.
  3. init() 남발. 전역 상태와 숨겨진 부작용의 온상. 명시적 NewXxx() 함수를 선호하라.
  4. 고루틴 시작 후 종료 신호 없음. 누수의 원인. 모든 고루틴은 ctx나 done 채널과 짝을 이뤄야 한다.
  5. 에러 무시 (_ = f()). 정말 무시해도 되는지 주석으로 사유를 남겨라.
  6. panic 으로 흐름 제어. Go 의 panic 은 진짜 회복 불가능한 상황 전용이다. 일반 오류는 error 값으로.

E. 맺음말

패턴은 외워서 적용하는 카탈로그가 아니다. 같은 문제를 만난 선배 개발자들이 어떻게 풀었는지에 대한 이름 붙은 어휘다. 실무에서는 패턴 이름을 모르고도 자연스럽게 같은 구조를 짜는 경우가 많고, 반대로 패턴을 잘못 끼워 맞춰 단순한 코드를 복잡하게 만드는 일도 잦다.

Go 의 미덕은 "필요할 때까지 도입하지 않는 절제"다. 인터페이스도, 추상화도, 패턴도 마찬가지다. 이 책의 42개 패턴을 모두 자유롭게 쓸 수 있게 되었다면, 다음 단계는 언제 쓰지 말아야 할지를 익히는 것이다.
