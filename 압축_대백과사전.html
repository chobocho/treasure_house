왜 압축인가

파일을 반으로 줄이는 마법은 없다. 있는 것은 같은 말을 더 짧게 적는 방법뿐이다. 그런데 그 "더 짧게" 에는 넘을 수 없는 벽이 있고, 벽이 어디인지는 수식 한 줄로 정해진다. 이 덱은 그 벽부터 시작해서, 벽에 얼마나 가까이 가는지를 코드로 확인하며 올라간다.

gzip 이 왜 그렇게 만들어졌는지, zstd 가 왜 그보다 빠른지, JPEG 가 무엇을 버리는지 — 전부 같은 이야기의 다른 장면이다. 남이 만든 라이브러리를 부르는 대신 직접 만들어 보면 그 장면들이 하나로 이어진다.

이 덱의 약속 — 여기 실린 코드는 전부 실제로 돌아간다. 의사코드는 한 줄도 없다. 화면에 보이는 출력은 전부 이 기계에서 진짜로 받은 것이다.

다섯 언어로 쓰는 이유

알고리즘 하나를 Python · Go · C++ · Java · TypeScript 로 각각 구현하고, 다섯이 만든 파일의 바이트가 완전히 같음을 매번 기계로 확인한다.

같은 알고리즘을 다섯 번 쓰는 것은 낭비처럼 보이지만, 압축에서는 그렇지 않다. 압축 형식은 비트 하나만 어긋나도 풀리지 않는다. 다섯 구현이 같은 바이트를 낸다는 것은 "설명이 애매하지 않다" 는 가장 강한 증거다. 말로 얼버무린 자리는 반드시 갈라진다.

부수 효과 — 언어마다 다른 것(정수 크기, 부호 없는 시프트, 바이트 배열 다루기)이 저절로 드러난다. 자바에 unsigned 가 없다는 사실은 설명으로 읽을 때보다 레인지 코더가 갈라질 때 훨씬 또렷하다.

시험 자료 — 코퍼스

모든 비율·속도 숫자는 같은 파일 묶음에서 나온다. 잘 나오는 파일만 골라 자랑하지 않기 위해서다. 빈 파일, 1바이트, 전부 0인 파일, 완전 난수, 한글 산문, 영문 산문, 소스 코드, 그리고 창 크기 경계(32768·32769바이트)를 노린 파일이 들어간다.

골든 벡터 — "바이트가 같다" 를 어떻게 아나

정보량 — 놀라움을 재는 자

확률이 낮을수록 정보가 많다

"오늘 해가 떴다" 는 정보가 아니다

정보량을 정의하는 출발점은 놀라움이다. 늘 일어나는 일을 알려 주는 말은 새로 알려 주는 것이 없다. 거의 안 일어나는 일을 알려 주는 말이 많이 알려 준다.

내일 해가 뜬다≈ 1거의 0

이 "놀라움" 에 이름을 붙이면 정보량이고, 기호로는 이렇게 쓴다.

I(x) = log2(1 / p(x)) = −log2 p(x)  [비트]
문서 근거

왜 하필 로그인가

정보량이 갖춰야 할 성질을 적어 보면 로그 말고는 답이 없다.

  1. 확률이 낮을수록 크다 — 단조 감소 함수여야 한다
  2. 확률 1 이면 0 이다 — 뻔한 소식은 값이 없다
  3. 독립인 두 소식은 더해진다 — I(x·y) = I(x) + I(y)

세 번째가 결정적이다. 곱셈(확률)을 덧셈(정보량)으로 바꾸는 함수는 로그뿐이다. 밑을 2 로 잡으면 단위가 비트가 되고, "예/아니오 질문 몇 번" 과 같은 말이 된다.

밑이 e 면 내트(nat), 10 이면 하틀리(hartley) 다. 압축에서는 비트를 쓴다 — 우리가 실제로 파일에 적는 단위가 비트이기 때문이다.
문서 근거

비트는 "질문 횟수" 다

1에서 8 사이의 수를 하나 생각했다고 하자. 예/아니오 질문으로 맞히려면 몇 번 물어야 할까.

  1. "4보다 큰가?" — 후보가 8 → 4
  2. "6보다 큰가?" — 4 → 2
  3. "8인가?" — 2 → 1

세 번이다. 그리고 log2 8 = 3 이다. 후보가 반씩 줄어드니 당연하다. 정보량이 3비트라는 말은 "잘 물으면 세 번에 맞힌다" 는 말과 같다.

여기서 압축이 나온다 — 잘 물으면 세 번인 것을 여덟 번 묻는 부호가 곧 낭비하는 부호다. 압축기는 "잘 묻는 순서" 를 찾는 기계다.

2장

엔트로피

정보량의 평균 — 한 기호에 몇 비트가 드나

정의

정보량 I(x) 는 한 사건의 값이다. 파일을 다룰 때 필요한 것은 "기호 하나당 평균 몇 비트" 이고, 그것이 엔트로피다.

H(X) = Σ p(x) · I(x) = −Σ p(x) log2 p(x)

확률을 가중치로 삼은 정보량의 평균일 뿐이다. 자주 나오는 기호의 정보량이 작게 여러 번, 드문 기호의 정보량이 크게 몇 번 섞인다.

p = 0 인 기호는 합에서 뺀다. 0·log 0 은 극한으로 0 이다 — "안 나오는 기호" 는 비용이 없다.
문서 근거

동전 하나의 엔트로피

앞면 확률 p 인 동전의 엔트로피를 p 에 따라 그리면 이렇다.

H(p) = −p log p − (1−p) log (1−p)

  • p = 0.5 에서 1비트로 최대 — 가장 예측이 안 되는 상태
  • p = 0 또는 1 에서 0비트 — 결과가 정해져 있으면 알려 줄 것이 없다
  • p = 0.9 면 0.47비트 — 열 번 던져 다섯 비트면 족하다는 뜻
치우침이 곧 압축 여지다. 곡선이 가운데서만 높다는 것이 "고르게 나오는 자료는 못 줄인다" 는 말의 그림이다.

def entropy0(data):
    """바이트 하나에 든 정보량 (비트). 앞을 안 본다."""
    if not data:
        return 0.0
    counts = [0] * 256
    for b in data:
        counts[b] += 1
    total = float(len(data))
    out = 0.0
    for c in counts:
        if c:
            p = c / total
            out -= p * math.log(p, 2)
    return out

차수를 올리면 왜 내려가나

0차는 "앞을 안 본다" 는 뜻이다. 영어 산문에서 q 다음은 거의 u 인데, 0차 모델은 그것을 모른다. 앞 한 글자를 보면(1차) 그만큼 놀라움이 줄고, 값이 내려간다.

bench/entropy.py60–84문맥마다 따로 세고 가중 평균한다
def entropy_n(data, order):
    """앞 order 바이트를 문맥으로 본 조건부 엔트로피 (비트/바이트).

    문맥마다 따로 세고, 그 문맥이 나온 횟수로 가중 평균한다. 앞쪽
    order 바이트는 문맥이 모자라 세지 않는다 — 전체에 견주면 무시할
    수 있는 수이고, 억지로 채우면 없는 정보를 넣는 꼴이 된다.
    """
    if len(data) <= order:
        return 0.0
    table = {}
    for i in range(order, len(data)):
        ctx = bytes(data[i - order:i])
        row = table.get(ctx)
        if row is None:
            row = table[ctx] = [0] * 257    # 마지막 칸은 그 문맥의 합
        row[data[i]] += 1
        row[256] += 1
    total = float(len(data) - order)
    out = 0.0
    for row in table.values():
        n = float(row[256])
        for c in row[:256]:
            if c:
                out -= (n / total) * (c / n) * math.log(c / n, 2)
    return out

그런데 끝없이 내려가지는 않는다

위 표에서 random_64k.bin 의 2차 엔트로피가 0.82 다. 난수 파일이 줄어든다는 뜻일까? 아니다.

표본이 모자라서 생긴 착시다. 2차 문맥은 65,536가지인데 파일은 65,536바이트다. 문맥 하나에 표본이 평균 한 개꼴이니, 모든 문맥이 "다음은 이 바이트" 라고 100% 확신하게 된다. 외운 것이지 안 것이 아니다.

진짜 모델은 이 표를 같이 실어 보내야 한다. 그 값을 셈에 넣으면 난수 파일은 어김없이 커진다. 문맥을 늘릴 때 치르는 값 — 이것이 11부 PPM 의 출발점이다.

Q. alphabet.bin 은 4,608바이트인데 0차 엔트로피가 정확히 8.00, 2차는 0.06 이다. 2차만 보면 34바이트로 줄일 수 있다는 뜻인데, 정말 그럴까?

접두 부호란

어떤 부호도 다른 부호의 앞부분이 아니어야 한다. 그래야 구분자 없이 이어 붙여도 읽는 쪽이 어디서 끊을지 알 수 있다.

문서 근거

길이가 정해지면 자리가 정해진다

길이 L 인 부호 하나를 쓰면, 그 부호로 시작하는 모든 긴 부호가 못 쓰게 된다. 전체를 [0, 1) 구간으로 보면 2−L 만큼을 가져가는 셈이다.

길이 L 인 부호가 2^-L 만큼의 구간을 차지한다

Σ 2−L(x) ≤ 1  — 크래프트 부등식

합이 1을 넘으면 그런 접두 부호는 존재하지 않는다. 구현이 서툴러서가 아니라 자리가 없어서다.

설명용

거꾸로도 참이다

크래프트 부등식이 더 값진 이유는 역이 성립하기 때문이다.

Σ 2−L ≤ 1 을 만족하는 길이 목록이 주어지면, 그 길이를 갖는 접두 부호가 반드시 존재한다. 그것도 기계적으로 만들 수 있다.

그래서 허프만 부호를 보낼 때 부호 자체를 보낼 필요가 없다. 길이만 보내면 받는 쪽이 같은 규칙으로 같은 부호를 만들어 낸다. 4부의 캐노니컬 허프만이 이것이고, DEFLATE 가 부호표를 길이 목록으로 싣는 이유가 이것이다.

길이만 주면 부호가 정해진다

설명용

코드로 확인하기

우리 허프만 구현은 부호표를 읽을 때마다 이 합을 실제로 센다. 합이 1 을 넘거나 모자라면 그 자리에서 거절한다.

src/py/compresslib/huffman.py87–104크래프트 합을 정수로 센다
def check_complete(lengths, max_length=MAX_LENGTH):
    """크래프트 합이 1 인지. 넘치면 못 푸는 표, 모자라면 손상된 표다.

    예외가 하나 있다. **기호가 하나뿐인 표** 는 길이 1 짜리 부호 하나라
    합이 1/2 이고, 그래서 늘 "모자란" 표다. zeros_64k.bin 처럼 한 가지
    바이트만 있는 파일에서 반드시 나오는 모양이라 받아 준다. 이때
    복호기는 기호마다 비트 하나를 읽고, 1 이 나오면 손상으로 본다.
    (RFC 1951 도 거리표 하나짜리에 같은 예외를 둔다 — 9부에서 본다.)
    """
    used = [l for l in lengths if l]
    total = sum(1 << (max_length - l) for l in used)
    full = 1 << max_length
    if total > full:
        raise ValueError('부호표가 넘친다 (크래프트 합 > 1)')
    if total < full:
        if len(used) == 1 and used[0] == 1:
            return
        raise ValueError('부호표가 모자란다 (크래프트 합 < 1)')
왜 정수로 세나 — 2−L 을 실수로 더하면 언어마다 반올림이 달라진다. 1 << (15 − L) 로 더하면 다섯 언어가 같은 판정을 낸다.
실행 검증

딱 하나 봐주는 자리

기호가 하나뿐인 파일(zeros_64k.bin)을 생각해 보자. 그 기호에 1비트를 주면 크래프트 합이 1/2 다. 부등식은 만족하지만 합이 1 이 아니다.

완전한 부호표를 요구하면 이 파일은 부호화할 수 없다. 그렇다고 0비트를 줄 수도 없다 — 0비트짜리 부호는 읽을 수가 없다.

그래서 "기호가 정확히 하나" 인 경우만 예외로 받는다. 규칙을 느슨하게 푸는 것이 아니라, 그 하나의 경우를 명시하는 쪽을 골랐다. 명세에 안 적으면 다섯 언어가 갈린다.

평균 부호 길이는 엔트로피보다 짧아질 수 없다

무잡음 부호화 정리

H(X) ≤ 평균 부호 길이 < H(X) + 1

왼쪽이 못 넘는 벽이고, 오른쪽이 손해의 상한이다. 기호 하나에 비트를 정수로 배정하는 한, 엔트로피보다 짧아질 수는 없고 1비트 넘게 손해 볼 일도 없다.

  • 왼쪽은 크래프트 부등식과 젠센 부등식에서 나온다
  • 오른쪽은 L(x) = ⌈−log₂ p(x)⌉ 로 잡으면 곧바로 나온다 — 올림 때문에 최대 1비트 손해
문서 근거

"1비트 손해" 가 크게 느껴질 때

기호 하나에 1비트 손해는 작아 보이지만, 기호가 잘게 쪼개져 있으면 치명적이다.

상황엔트로피허프만 최소손해

p = 0.9 인 이진 기호0.47비트1비트113%

문서 근거

증명 — 자리를 세면 끝난다

  1. 길이 n 비트인 입력은 2n 가지다
  2. 이것들이 모두 줄어든다면, 출력은 길이 n−1 이하다
  3. 길이 n−1 이하인 문자열은 모두 합해 2n − 1 가지다
  4. 2n 개를 2n − 1 개의 자리에 넣으면 둘이 겹친다
  5. 겹치면 그 출력을 푸는 방법이 하나로 정해지지 않는다 — 무손실이 아니다

비둘기 2n 마리를 집 2n−1 개에 넣는 이야기와 같다. 알고리즘이 얼마나 똑똑한지는 이 셈에 들어오지 않는다.

부호기는 모델을 믿는다

부호기는 모델이 말한 확률 q 대로 −log₂q 비트를 쓴다. 그런데 실제 확률은 p 다. 그러면 평균 비트는 이렇게 된다.

H(p, q) = −Σ p(x) log₂ q(x)  — 교차 엔트로피

q = p 면 이 값이 H(p) 로 줄어든다. 다르면 반드시 커진다. 얼마나 커지느냐가 쿨백–라이블러 발산이다.

H(p, q) = H(p) + D(p ‖ q)    D ≥ 0

class MsbWriter:
    """첫 비트가 첫 바이트의 7번 비트에 앉는 writer."""

    def __init__(self):
        self._out = bytearray()
        self._buf = 0
        self._n = 0

    def write_bit(self, bit):
        self._buf |= (bit & 1) << (7 - self._n)
        self._n += 1
        if self._n == 8:
            self._out.append(self._buf)
            self._buf = 0
            self._n = 0

    def write_bits(self, value, count):
        """값의 낮은 count 비트를 높은 쪽부터 쓴다."""
        for i in range(count - 1, -1, -1):
            self.write_bit((value >> i) & 1)

7 - self._n 이 MSB 먼저의 전부다. 이 한 줄을 self._n 으로 바꾸면 LSB 먼저가 된다.

        self.src = src
        self.pos = pos
        self._buf = 0
        self._n = 0

    def read_bit(self):
        if self._n == 0:
            if self.pos >= len(self.src):
                raise ValueError('비트 스트림이 바닥났다')

값 v 와 매개변수 k 를 정하면, 몫 v>>k 는 단항으로, 나머지 k비트는 그대로 적는다.

  • k 가 크면 나머지가 길어지고 몫이 짧아진다
  • k 가 작으면 몫의 단항이 길어진다

def put_rice(w, v, k):
    """골룸–라이스. 단항은 **1 을 q개 쓰고 0 으로 닫는다.**

    반대 약속(0 을 q개 쓰고 1 로 닫기)도 문헌에 흔하다. 섞어 쓰면
    작은 값은 그래도 왕복이 되어, 골든 벡터를 맞출 때까지 안 보인다.
    """
    if v < 0:
        raise ValueError('rice 는 0 이상만: %d' % v)
    q = v >> k
    if q > MAX_UNARY:
        raise ValueError('rice 의 몫이 %d — k 를 잘못 골랐다' % q)
    w.write_bits((1 << q) - 1, q)
    w.write_bit(0)
    if k:
        w.write_bits(v & ((1 << k) - 1), k)

1장

런 길이 부호

가장 단순한 압축, 그래서 한계도 가장 먼저 보인다

생각은 한 줄이다

같은 바이트가 이어지면 "그 바이트와 개수" 로 적는다. AAAAAAA (7바이트) 를 7 A (2바이트) 로.

그런데 곧바로 문제가 생긴다. abcdefg 처럼 런이 없으면? "1 a 1 b 1 c …" 로 적으면 두 배가 된다.

그래서 실제로 쓰이는 RLE 는 전부 런이 아닌 구간을 그대로 싣는 길을 갖고 있다. 그 두 가지를 어떻게 가르느냐가 형식을 정한다.

문서 근거

PackBits — 제어 바이트의 부호로 가른다

제어 바이트 하나가 두 가지를 가른다

  • 제어 < 128 이면 리터럴 — 뒤 (제어+1) 바이트를 그대로
  • 제어 > 128 이면 런 — 뒤 1바이트를 (257−제어) 번
  • 제어 = 128 은 안 쓴다

애플이 1984년 매킨토시 그림 형식에 쓴 것이고, TIFF·PDF 가 아직도 쓴다.

설명용

128 을 버리는 이유

애플 원본은 제어 128 을 "아무 일도 안 함" 으로 정하고 넘어간다. 우리는 그것을 거절한다.

같은 입력을 두 가지 바이트열로 적을 수 있는 부호기는 골든 벡터를 가질 수 없다. 어느 쪽도 틀리지 않았으니, 다섯 언어가 갈려도 "누가 틀렸나" 를 말할 수 없다.

형식을 설계할 때 "해도 되고 안 해도 되는 것" 을 남기면, 그 자리가 정확히 구현들이 갈리는 자리가 된다.

def pack(src):
    """PackBits 묶음들. 헤더는 붙이지 않는다."""
    out = bytearray()
    i, n = 0, len(src)
    while i < n:
        run = _run_at(src, i)
        if run >= RUN_MIN:
            out.append(257 - run)
            out.append(src[i])
            i += run
            continue
        # 리터럴 — 런이 시작되는 자리까지, 또는 상한까지
        j = i
        while j < n and (j - i) < LIT_MAX:
            r = _run_at(src, j)
            if r >= RUN_MIN:
                break
            # 상한을 넘겨 잡으면 129바이트 묶음이 나온다. 제어 바이트에
            # 안 들어가는 길이라, 아무도 못 푸는 파일이 된다.
            j = min(j + r, i + LIT_MAX)
        out.append(j - i - 1)
        out += src[i:j]
        i = j
    return bytes(out)
실행 검증

리터럴을 어디서 끊나 — 한 줄이 형식을 정한다

리터럴을 모으다가 런을 만나면 끊어야 한다. 그런데 상한(128)도 지켜야 한다.

상한을 넘겨 잡으면 129바이트짜리 묶음이 나온다. 제어 바이트에 들어가지 않는 길이라, 아무도 못 푸는 파일이 된다. 코드의 min(j + r, i + LIT_MAX) 가 그것을 막는다.

이런 자리가 명세(SPEC §3.1)에 "문턱 3 · 런 상한 128 · 리터럴 상한 128" 로 적혀 있는 이유다. 셋 다 출력 바이트를 바꾼다.

RUNA/RUNB — 0 무더기 전용 부호

bzip2 가 쓰는, 조금 이상하게 생긴 이진 부호

MTF 뒤에는 0 이 쏟아진다

다음 장에서 볼 MTF 는 되풀이되는 글자를 0 으로 바꾼다. 그 결과 0 이 수백 개씩 이어지는 구간이 생긴다.

이것을 PackBits 로 적으면 런 하나에 2바이트, 128개마다 끊긴다. 길이를 varint 로 적으면 바이트 경계로 돌아가야 한다. 둘 다 아깝다.

RUNA/RUNB — 0 런의 길이를 이진수로 적되, 자릿수 하나를 기호 하나로 만든다. 기호 두 개로 길이 전체를 표현한다.

def zero_run_encode(symbols):
    """MTF 기호 열 → 0런이 접힌 열. 0 아닌 기호는 한 칸씩 밀린다."""
    out = []
    i, n = 0, len(symbols)
    while i < n:
        if symbols[i] != 0:
            out.append(symbols[i] + 1)
            i += 1
            continue
        j = i
        while j < n and symbols[j] == 0:
            j += 1
        length = (j - i) + 1
        while length > 1:
            out.append(RUNB if (length & 1) else RUNA)
            length >>= 1
        i = j
    return out

실행 검증

왜 이렇게까지 하나

RUNA·RUNB 는 다른 기호들과 같은 허프만 표에 들어간다. 길이를 따로 적는 것이 아니라, 알파벳의 일원이 되는 것이다.

그래서 0 런이 많은 파일에서는 RUNA 의 빈도가 치솟고, 허프만이 RUNA 에 1~2비트를 준다. 길이 1,000짜리 런이 10비트에 적히는 일이 생긴다.

10부에서 bzip2 스트림을 실제로 풀어 보며 이 부호를 다시 만난다.

MTF — 앞으로 옮기기

값을 바꾸는 것이 아니라 분포를 바꾼다

규칙

  1. 0~255 를 늘어놓은 표를 하나 둔다
  2. 입력 바이트가 표의 몇 번째인지 그 번호를 내보낸다
  3. 그 바이트를 표의 맨 앞으로 옮긴다

bbaac 를 넣었을 때 표가 움직이는 모습

방금 본 바이트가 다시 나오면 번호가 0 이다. 최근에 본 것일수록 작은 번호가 된다.

설명용

코드

src/py/compresslib/mtf.py23–32찾고, 내보내고, 앞으로 옮긴다
def transform(src):
    table = list(range(ALPHABET))
    out = bytearray()
    for b in src:
        i = table.index(b)
        out.append(i)
        if i:
            del table[i]
            table.insert(0, b)
    return bytes(out)

표를 리스트로 두고 pop/insert 하면 최악 O(256) 이다. 자료가 1 MB 면 2억 6천만 번이라, 실제로 이 책에서 가장 느린 단순 변환이다.

3부 퀴즈

Q. MTF 는 크기를 1바이트도 안 줄이고, 영어 산문에서는 엔트로피를 오히려 올린다. 그런데도 bzip2 가 MTF 를 쓰는 이유는?

A. bzip2 는 MTF 를 BWT 뒤에 쓴다. BWT 를 거친 자료는 같은 글자가 뭉쳐 있어서, MTF 를 먹이면 0 이 무더기로 쏟아진다. 그 0 무더기를 RUNA/RUNB 가 몇 기호로 줄이고, 허프만이 마무리한다.
즉 MTF 의 값어치는 혼자가 아니라 사슬 안의 자리에서 나온다. 이 책이 MTF 를 따로 모듈로 두고 비율 100% 를 그대로 보여 주는 이유이기도 하다 — "줄이는 것" 과 "줄이기 좋게 만드는 것" 은 다른 일이다.

알고리즘

  1. 기호마다 빈도를 적은 잎을 하나씩 만든다
  2. 무게가 가장 작은 둘을 골라 새 노드로 묶는다. 새 노드의 무게는 둘의 합
  3. 노드가 하나 남을 때까지 되풀이한다
  4. 뿌리에서 잎까지 내려가며 왼쪽 0, 오른쪽 1 을 붙인 것이 부호다

abracadabra 의 빈도로 실제로 자란 나무

드문 기호일수록 깊이 내려가므로 부호가 길어진다. 이 단순한 규칙이 기호마다 정수 비트를 주는 부호 중 최적임이 증명되어 있다.

설명용

최적이라는 말의 뜻

주어진 빈도에서, 기호 하나에 정수 비트를 배정하는 접두 부호 중 평균 길이가 최소다. 더 짧게 만들 수 있는 부호는 없다.

1부의 섀넌 한계와 나란히 놓으면 이렇게 된다.

"최적" 이면서도 엔트로피보다 크다. 정수 비트라는 제약 안에서 최적이기 때문이다.

문제를 바꿔 놓기

길이 제한 L 인 최적 부호 문제는 동전 수집가 문제와 같다.

  • 기호마다 액면 2−1, 2−2, … 2−L 짜리 동전이 하나씩 있다
  • 기호 s 의 동전은 무게가 freq(s) 다 (액면과 무관하게)
  • 액면 합이 정확히 m − 1 이 되도록 고르되, 무게 합이 최소가 되게
  • 기호 s 의 동전을 k 개 골랐다면 그 기호의 부호 길이가 k 다
왜 m−1 인가: 크래프트 합이 정확히 1 이어야 하고, 동전을 하나씩 세는 방식 때문에 m−1 로 떨어진다. 증명은 라모어–허쉬버그(1990).

def code_lengths(freqs, limit=MAX_LENGTH):
    """빈도 벡터 → 같은 길이의 길이 벡터. 안 쓰는 기호는 0.

    알파벳 크기는 freqs 의 길이가 정한다. 골든 코덱은 256 이지만
    DEFLATE 동적 블록은 286·30·19 세 가지를 쓴다.
    """
    used = [(f, s) for s, f in enumerate(freqs) if f]
    used.sort()
    m = len(used)
    lengths = [0] * len(freqs)
    if m == 0:
        return lengths
    if m == 1:
        lengths[used[0][1]] = 1
        return lengths
    if m > (1 << limit):
        raise ValueError('기호 %d개는 길이 %d 로 못 담는다'
                         % (m, limit))

    # 동전 하나 = (무게, 종류, 순번, 이 동전이 품은 기호 목록). 종류 0
    # 이 기호 동전, 1 이 꾸러미다 — 무게가 같으면 기호 동전이 앞선다.
    coins = [(f, 0, j, (s,)) for j, (f, s) in enumerate(used)]
    level = coins
    for _ in range(limit - 1):
        packed = [(level[2 * i][0] + level[2 * i + 1][0], 1, i,
                   level[2 * i][3] + level[2 * i + 1][3])
                  for i in range(len(level) // 2)]
        level = sorted(packed + coins)

    for _w, _k, _r, syms in level[:2 * m - 2]:
        for s in syms:
            lengths[s] += 1
    return lengths

def canonical_codes(lengths):
    """길이 벡터 → 부호 벡터. RFC 1951 §3.2.2 와 같은 규칙."""
    bl_count = [0] * (MAX_LENGTH + 1)
    for l in lengths:
        if l:
            if l > MAX_LENGTH:
                raise ValueError('길이 %d 는 상한 %d 를 넘는다'
                                 % (l, MAX_LENGTH))
            bl_count[l] += 1
    code = 0
    next_code = [0] * (MAX_LENGTH + 2)
    for bits in range(1, MAX_LENGTH + 1):
        code = (code + bl_count[bits - 1]) << 1
        next_code[bits] = code
    codes = [0] * len(lengths)
    for s in range(len(lengths)):
        l = lengths[s]
        if l:
            if next_code[l] >= (1 << l):
                raise ValueError('부호표가 넘친다 — 길이 %d' % l)
            codes[s] = next_code[l]
            next_code[l] += 1
    return codes

    복호기는 기호마다 비트 하나를 읽고, 1 이 나오면 손상으로 본다.

    if total < full:
        if len(used) == 1 and used[0] == 1:

2장

구간을 쪼개 들어간다

산술 부호화의 전부

규칙

  1. 구간 [0, 1) 에서 시작한다
  2. 기호의 확률만큼 구간을 나눠, 그 기호의 몫으로 들어간다
  3. 기호마다 되풀이한다 — 구간이 점점 좁아진다
  4. 마지막 구간 안의 아무 수나 하나 적으면 그것이 부호다

A .6 / B .3 / C .1 로 'ABA' 를 넣을 때

설명용

왜 이것이 최적인가

마지막 구간의 폭은 기호 확률들의 곱이다. 폭 w 인 구간 안의 수를 콕 집으려면 −log₂w 비트가 든다.

−log₂(p₁·p₂·…·pn) = −log₂p₁ − log₂p₂ − … = 정보량의 합

즉 이 방법은 정의상 엔트로피만큼의 비트를 쓴다. 1~2비트의 마무리 손해만 있고, 그것도 메시지 전체에 한 번뿐이다.

문서 근거

그런데 실수로는 못 만든다

1,000개 기호를 넣으면 구간 폭이 10−300 근처가 된다. 64비트 부동소수점의 바닥은 10−308 이라 곧 0 이 된다. 게다가 부동소수점 반올림은 기계마다 다를 수 있다 — 다섯 언어가 같은 바이트를 내야 하는 이 책에서는 처음부터 탈락이다.

해결은 둘이다.

  • 정수로 한다 — 구간을 [low, low+range) 인 32비트 정수 쌍으로
  • 확정된 자리는 내보낸다 — 위 바이트가 더 안 바뀌면 먼저 내보내고 구간을 넓힌다

정규화

정밀도가 바닥나기 전에 위 바이트를 내보낸다

규칙

구간 폭 range 가 224 아래로 내려가면, low 의 위 8비트를 내보내고 둘 다 8비트씩 왼쪽으로 민다.

값
구간 시작 range0xFFFFFFFF
정규화 문턱 TOP224 = 0x1000000
확률 해상도11비트 (2048단계)

이렇게 하면 range 가 늘 224 이상이라, 2048단계 확률로 나눠도 몫이 0 이 되지 않는다. 11 + 24 < 32 가 이 설계의 셈이다.

문서 근거

캐리 — 이미 내보낸 바이트를 고쳐야 할 때

low 에 더하다 보면 올림이 난다. 그런데 위 바이트는 이미 나갔다.

0xFF 이 이어진 자리에 올림이 오면 앞으로 번진다

해법: 아직 확정 안 된 0xFF 가 몇 개인지만 센다. 올림이 오면 그 개수만큼 0x00 을 내보내고 앞의 한 바이트를 +1 한다. 버퍼를 통째로 들고 있을 필요가 없다.

    def shift_low(self):
        """위 바이트 하나를 확정해 내보낸다. 캐리는 앞으로 전파한다."""
        if (self.low >> 32) or self.low < 0xFF000000:
            carry = self.low >> 32
            temp = self.cache
            while True:
                self._out.append((temp + carry) & 0xFF)
                temp = 0xFF
                self.cache_size -= 1
                if self.cache_size == 0:
                    break
            self.cache = (self.low >> 24) & 0xFF
        self.cache_size += 1
        self.low = (self.low << 8) & U32

cache 가 "앞의 한 바이트", cache_size 가 "그 뒤의 0xFF 개수+1" 이다. LZMA 가 쓰는 방식 그대로다.

확률 갱신 — 빈도를 세지 않는다

p += (2048 − p) >> 5  (0 이 나왔을 때)
p −= p >> 5  (1 이 나왔을 때)

빈도 표도, 나눗셈도 없다. 확률을 목표 쪽으로 1/32 만큼 끌어당기는 것이 전부다.

  • 최근 것에 더 큰 가중치가 붙는다 — 지수 이동 평균이다
  • 2−5 라는 속도가 곧 기억의 길이다. 크면 빨리 적응하고 시끄럽다
  • 정수 연산만 쓴다 — 다섯 언어가 같은 답을 낸다
MOVE_BITS 5 는 LZMA 의 값이다. 11부의 문맥 혼합은 문맥마다 다른 속도를 쓴다 — 처음엔 빠르게, 표본이 쌓이면 느리게.

class ByteModel:
    """0차 적응 바이트 모델 — 확률 256칸을 이진 트리처럼 쓴다.

    문맥은 1 에서 시작해 비트 하나마다 (ctx<<1)|bit 로 내려간다. 여덟 번
    지나면 256..511 이 되므로 실제로 쓰이는 자리는 1..255 뿐이고,
    0번 칸은 한 번도 안 쓴다. 그래서 배열이 257 이 아니라 256 이다.
    """

    def __init__(self):
        self.probs = [PROB_INIT] * 256

    def encode(self, enc, b):
        ctx = 1
        for i in range(7, -1, -1):
            bit = (b >> i) & 1
            enc.encode_bit(self.probs, ctx, bit)
            ctx = (ctx << 1) | bit

    def decode(self, dec):
        ctx = 1
        for _ in range(8):
            ctx = (ctx << 1) | dec.decode_bit(self.probs, ctx)
        return ctx - 256

확률 슬롯 256개를 두고, 지금까지 읽은 비트로 만든 수를 색인으로 쓴다. 첫 비트는 슬롯 1, 그 다음은 2~3, 그 다음은 4~7 … 마지막 8번째 비트는 128~255.

이 구조는 부분 문맥을 공짜로 준다. 상위 비트가 같은 바이트끼리 확률을 나눠 쓰므로, 알파벳이 뭉쳐 있는 자료(ASCII 텍스트)에서 잘 맞는다.

5부 퀴즈

Q. 레인지 코더의 확률 갱신을 >> 5 에서 >> 4 로 바꾸면 (적응이 두 배 빨라지면) 압축비는 어떻게 될까?

A. 자료에 따라 다르다 — 그리고 그게 요점이다. 성질이 자주 바뀌는 자료에서는 빨리 따라가서 이득이고, 고른 자료에서는 확률이 잡음에 흔들려 손해다.
중요한 것은 양쪽이 똑같이 바꿔야 한다는 것이다. 부호기만 고치면 복호기가 다른 확률을 쓰게 되어 파일이 전부 깨진다. 그리고 골든 벡터가 전부 달라지므로, 이 값은 형식의 일부다 (SPEC §8.2).

2장

rANS 의 생각

상태 하나에 정보를 쌓아 올린다

자릿수 올리기의 일반화

10진수에 숫자 하나를 붙이는 일을 생각해 보자. x = x*10 + d 다. 확률이 모두 1/10 인 기호 열 개를 적는 셈이다.

확률이 제각각이면? 기호마다 곱하는 수가 달라야 한다. 확률 p 인 기호를 붙이면 상태가 1/p 배가 되어야 한다 — 그래야 −log₂p 비트가 든다.

rANS 의 식이 바로 그것이다. 빈도 f, 누적 c, 합 M 일 때:

x' = ⌊x / f⌋ · M + (x mod f) + c

x 가 대략 M/f = 1/p 배가 된다. 나머지(x mod f)와 누적(c)이 "어느 기호였는지" 를 그 안에 숨긴다.

문서 근거

실제로 상태가 자라는 모습

빈도 A:3 B:1 일 때 x 가 자라는 모습

드문 기호(B)를 넣을 때 상태가 크게 뛴다. 그 뜀이 곧 "비트를 더 썼다" 는 뜻이다.

상태가 무한정 커질 수는 없으니, 어느 한계를 넘으면 아래 바이트를 내보내고 상태를 줄인다 — 레인지 코더의 정규화와 같은 일이다. 다만 방향이 반대다.
설명용

복호는 정확히 거꾸로

s = 슬롯[x mod M]   →    x' = f·⌊x/M⌋ + (x mod M) − c

상태의 아래 12비트가 곧 "어느 기호" 인지를 말해 준다. 슬롯 표 한 번 찾고 곱셈 한 번이면 끝이다.

그래서 rANS 는 스택이다. 마지막에 넣은 기호가 먼저 나온다. 부호기는 입력을 뒤에서부터 밀어 넣어야 복호기가 앞에서부터 읽는다. 이 방향을 헷갈리면 왕복은 되는데 바이트가 달라진다.

def normalise(counts):
    """세어 온 빈도를 합이 정확히 TOTAL 이 되게 고친다 (SPEC §13.3).

    나머지를 어디에 붙이느냐가 언어마다 갈리는 자리다. 남으면 가장 큰
    기호에 한꺼번에, 모자라면 가장 큰 기호에서 되풀이해 뺀다.
    동점이면 번호가 작은 쪽. 그 규칙이 전부다.
    """
    total = sum(counts)
    if total == 0:
        return [0] * ALPHABET
    f = [0] * ALPHABET
    for s in range(ALPHABET):
        if counts[s]:
            f[s] = max(1, counts[s] * TOTAL // total)
    d = TOTAL - sum(f)
    while d:
        # 가장 큰 빈도, 동점이면 작은 번호
        s = max(range(ALPHABET), key=lambda i: (f[i], -i))
        if d > 0:
            f[s] += d
            d = 0
        else:
            take = min(-d, f[s] - 1)
            if take == 0:
                raise ValueError('빈도를 TOTAL 에 못 맞춘다')
            f[s] -= take
            d += take
    return f

def encode(src):
    if not src:
        return varint.put(0)
    counts = [0] * ALPHABET
    for b in src:
        counts[b] += 1
    f = normalise(counts)
    cum = cumulative(f)

    out = bytearray()
    x = L
    # 뒤에서부터 민다. rANS 는 스택이고, 마지막에 넣은 것이 먼저 나온다.
    for b in reversed(src):
        fs = f[b]
        x_max = ((L >> TOTAL_BITS) << 8) * fs
        while x >= x_max:
            out.append(x & 0xFF)
            x >>= 8
        x = (x // fs) * TOTAL + (x % fs) + cum[b]
    for i in range(4):
        out.append((x >> (8 * i)) & 0xFF)
    out.reverse()

    head = bytearray(varint.put(len(src)))
    for s in range(ALPHABET):
        head += varint.put(f[s])
    return bytes(head + out)

def decode(src):
    n, pos = varint.get_length(src)
    if n == 0:
        if pos != len(src):
            raise ValueError('빈 입력인데 뒤에 바이트가 있다')
        return b''
    f = [0] * ALPHABET
    for s in range(ALPHABET):
        v, pos = varint.get(src, pos)
        if v > TOTAL:
            raise ValueError('빈도가 TOTAL 을 넘는다')
        f[s] = v
    if sum(f) != TOTAL:
        raise ValueError('빈도의 합이 %d 가 아니다' % TOTAL)
    cum = cumulative(f)
    slots = slot_symbols(f, cum)

    body = src[pos:]
    if len(body) < 4:
        raise ValueError('rANS 스트림이 너무 짧다')
    x = 0
    for i in range(4):
        x = (x << 8) | body[i]
    at = 4
    out = bytearray()
    mask = TOTAL - 1
    for _ in range(n):
        slot = x & mask
        s = slots[slot]
        out.append(s)
        x = f[s] * (x >> TOTAL_BITS) + slot - cum[s]
        while x < L:
            if at >= len(body):
                raise ValueError('rANS 스트림이 모자란다')
            x = (x << 8) | body[at]
            at += 1
    if at != len(body):
        raise ValueError('뒤에 남은 바이트가 있다')
    return bytes(out)

def slot_symbols(f, cum):
    """칸 번호 → 기호. 복호기가 상태의 아래 12비트로 바로 찾는다."""
    slots = [0] * TOTAL
    for s in range(ALPHABET):
        for i in range(cum[s], cum[s] + f[s]):
            slots[i] = s
    return slots

5장

tANS — 표를 만들어 두면 덧셈만 남는다

FSE 라는 이름으로 zstd 안에 들어 있는 것

생각

rANS 의 상태가 [L, L·256) 이라 값이 크다. 그런데 상태를 작은 범위(예: 4096) 로 묶고, 그 안에서 일어나는 모든 전이를 미리 표로 만들어 두면 어떨까?

부호화가 "표 보고 다음 상태 읽기 + 비트 몇 개 내보내기" 로 줄어든다. 곱셈도 나눗셈도 없다.

대가는 표를 만드는 값이다. 블록마다 빈도가 바뀌면 표도 다시 만들어야 한다.

문서 근거

def tans_table(f):
    """tANS 의 상태표를 퍼뜨려 만든다 (SPEC §13.6). 골든에는 없다."""
    table = [0] * TOTAL
    pos = 0
    for s in range(ALPHABET):
        for _ in range(f[s]):
            table[pos] = s
            pos = (pos + SPREAD_STEP) & (TOTAL - 1)
    return table
SPREAD_STEP = (M>>1) + (M>>3) + 3 = 2048 + 512 + 3 = 2563

홀수라서 2의 거듭제곱 칸을 빠짐없이 한 번씩 돈다. 같은 기호의 칸들이 표 전체에 고루 흩어지게 하는 것이 목적이다 — 뭉쳐 있으면 상태가 한쪽으로 쏠려 압축비가 떨어진다.

zstd 가 쓰는 값 그대로다. 이론적으로 최적인 배치는 따로 있지만, 이 걸음이 충분히 좋으면서 계산이 없다.

Q. rANS 부호기를 앞에서부터(정방향) 돌리도록 고쳤다. 자기 복호기도 같이 고쳤더니 왕복이 통과한다. 무엇이 잘못됐나?
