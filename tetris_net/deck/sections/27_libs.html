{{N}}반대편을 실제로 만든다

7장에서 "라이브러리를 쓰면 한 줄"이라고 말만 하고 지나갔다. 이 장에서는 그 말을 실제로 검증한다 — 같은 서버 둘을 웹소켓 라이브러리로 다시 만든다.

바꾸는 것

전송층 하나. Go 는 gorilla/websocket, 파이썬은 websockets 라이브러리가 ws.go(339줄)·ws.py(234줄)의 자리를 대신한다.

안 바꾸는 것

hub·room·프로토콜·클라이언트 전부. Go 쪽은 아예 byte-for-byte 복사로 못 박는다.

판정 기준도 그대로

기존 통합 테스트가 무수정으로 통과할 것, 그리고 진짜 웹소켓으로 8인 대전 실측이 끝까지 돌 것.

{{N}}Go — gorilla/websocket 을 들여온다

"의존성 0 이 깨진다"의 실체는 파일 두 개다. 이게 전부다 — 그리고 이제부터 첫 빌드는 네트워크를 한 번 만나야 한다(그 뒤로는 모듈 캐시가 받아 준다).

왜 gorilla 인가

Go 웹소켓의 사실상 표준이고, 그 자신도 의존성이 0이다 — go.sum 이 두 줄(모듈 하나)로 끝나는 이유.

버전을 못 박는다

v1.5.3 고정. go.sum 의 해시 덕에 같은 소스는 언제 어디서 빌드해도 같은 바이트를 받는다.

{{N}}ws_lib.go ① 겉모양은 ws.go 그대로

오프코드 표를 다시 적는 이유는 hub.go 가 OpText 를 참조하기 때문이다. gorilla 의 메시지 상수가 RFC 오프코드 값 그대로라 변환은 캐스팅 하나다.

{{N}}ws_lib.go ② 핸드셰이크 36줄 → 세 문장

{{N}}ws_lib.go ③ 읽기·쓰기·닫기

사라진 일들조각 이어붙이기, 핑→퐁 자동 응답, 마스킹 해제, close 코드 협상 — 8장에서 손으로 만들던 전부가 c.ws.ReadMessage() 한 줄 속으로 들어갔다.

{{N}}복사가 규칙이다 — make lib-copy

server_go_lib/ 의 room.go·hub.go·main.go·테스트 2종은 저장소에 없다. 빌드할 때마다 server_go 에서 새로 복사한다 — 복사본이 원본과 갈라지는 일 자체를 불가능하게 만드는, web/room.js 와 같은 규칙이다.

{{N}}테스트는 한 글자도 새로 쓰지 않았다 (Go)

복사된 room_test.go 는 골든 벡터 44스텝을, hub_test.go 는 진짜 소켓으로 붙는 통합 시나리오 5개를 그대로 돌린다. 클라이언트 쪽 Dial 도 gorilla 로 바뀌었으니 이 통과는 서버·클라이언트 양쪽의 교체 증명이다.

ws_test.go 만 못 따라온다그 파일은 프레임 바이트를 검사한다 — 라이브러리판에는 검사할 프레임 코드 자체가 없다. 테스트가 구현 계층에 붙어 있으면 계층과 함께 은퇴한다.

{{N}}파이썬 — websockets 라이브러리

pip install websockets — 파이썬 웹소켓의 사실상 표준(여기서는 17.1). asyncio 판 serve() 에 코루틴 하나를 넘기면 연결마다 그 코루틴이 뜬다. ws.py 의 serve() 와 같은 그림이다.

공짜로 얻는 것

close 코드 협상, 20초 간격 keepalive 핑, 조각 프레임 조립, max_size 읽기 상한, permessage-deflate 압축 협상 — 7장에서 "안 만든다"던 것까지 들어 있다.

값으로 치르는 것

"파이썬만 있으면 돈다"가 깨진다. 표준 라이브러리 밖의 첫 pip install 이고, 배포 절차에 단계가 하나 는다.

{{N}}server_lib.py ① 머리말

마지막 두 import 가 이 파일의 요약이다 — hub 는 그대로 쓰고, HTTP 경로 규칙(make_http)도 server.py 것을 그대로 쓴다.

{{N}}server_lib.py ② 어댑터가 전부다

계약을 옮겨 적는 것이 어댑터다ws.py 의 recv_json 은 "닫히면 None, 못 읽으면 {}"였다. 라이브러리의 예외(ConnectionClosed)를 그 계약으로 번역하는 게 이 클래스의 일의 전부다.

{{N}}server_lib.py ③ HTTP 겸용과 serve()

ws.py 가 요청줄을 직접 파싱해 가르던 "웹소켓이냐 HTTP 냐"를 라이브러리는 process_request 훅 하나로 연다. serve() 의 시그니처를 ws.serve 와 같게 맞춰 두어 실행부가 그대로 옮겨 온다.

{{N}}시험 설계 — 직접 구현으로 라이브러리를 친다

새 테스트의 클라이언트는 ws.py 의 직접 구현 connect() 그대로다. 직접 구현 클라이언트가 라이브러리 서버와 끝까지 대화하면, 양쪽 다 RFC 6455 를 지켰다는 뜻이다 — 상호운용이 곧 규격 준수의 증거다.

{{N}}실측 — 같은 8인 대전을 두 서버에

23장의 헤드리스 봇(bot_client.mjs)을 한 글자도 바꾸지 않고 라이브러리판 두 서버에 붙인다. 봇의 전송은 Node 내장 WebSocket — 즉 이 실측은 세 번째 구현(undici)까지 낀 상호운용 시험이다.
