{{N}}net.Pipe 로 프레임을 시험한다

마감을 거는 이유net.Pipe 는 버퍼가 없어 한쪽이 멈추면 반대쪽도 영원히 멈춘다. 구현이 덜 됐을 때 go test 가 매달리는 대신 실패하게 하려면 마감이 필요하다 — 실제로 스텁 상태에서 2분 타임아웃을 맞고 나서 넣었다.

{{N}}마스킹과 조각남

WriteFrame(cli, …, true) — 테스트가 "클라이언트인 척" 마스킹해 보낸다. 서버 코드와 같은 함수를 쓰므로 인코더와 디코더가 함께 검증된다.

{{N}}핑·길이·닫기

TestLengthEncoding 이 도는 값은 0 · 125 · 126 · 65535 · 65536 — 헤더가 2·2·4·4·10바이트로 바뀌는 경계 바로 양쪽이다. 경계값만 고르면 5개로 3갈래를 다 덮는다.

{{N}}서버는 마스킹하지 않는다

이 테스트가 "머리와 본문을 한 번에 쓴다"를 강제한다. 나눠 쓰면 cli.Read 가 헤더 2바이트만 받고 hello 를 못 찾는다 — 테스트가 구현 방식을 못 박은 드문 경우이고, 여기서는 그게 옳다.

{{N}}골든 벡터 하니스 — 자료형

M json.RawMessage 로 두는 게 요령이다. 메시지 내용을 Go 타입으로 풀지 않고 바이트 그대로 들고 있다가 Room.Handle 에 넘긴다 — 하니스가 프로토콜을 두 번 해석하지 않는다.

{{N}}벡터를 도는 고리

실패 메시지에 c.Why 를 그대로 끼워 넣는다. #3(무작위 모드의 난수 소비 순서 …): 출력 개수 기대 1, 실제 0 — 무엇이 깨졌는지를 표가 직접 말해 준다.

{{N}}벡터가 다루지 않는 두 가지

난수열 그 자체

벡터는 결과만 본다. 난수열이 통째로 틀렸는데 우연히 같은 타겟이 나올 수도 있다. 앞 5개를 직접 박아 둔다.

PC 4대 × 2석

요구사항 그대로의 최대 구성. 좌석 8석이 1,1,2,2,3,3,4,4 로 배분되는지, 9번째 요청이 막히는지.

{{N}}통합 테스트 — 진짜 소켓

받은 메시지를 채널에 쌓아 두는 고루틴 하나. Dial 이 있어서 Go 만으로 클라이언트 역할이 된다 — 8부에서 40줄을 더 쓴 값을 여기서 받는다.

{{N}}원하는 메시지를 기다린다

want() 가 흘려보내는 이유브로드캐스트가 섞여 온다. start 를 기다리는 동안 room 이 세 개 지나갈 수 있다. "다음 메시지가 X 여야 한다"로 쓰면 순서에 취약한 테스트가 되고, 무관한 변경에도 깨진다.

{{N}}버전 불일치

아홉 줄짜리 테스트가 두 가지를 확인한다. 거절이 err ver 로 나가는가, 그리고 그 메시지가 실제로 소켓에 닿는가. 두 번째가 finish() 를 만들게 한 테스트다.

{{N}}PC 2대 × 2석 = 4인 대전

여기서 경합이 두 번 났다① 처음엔 "좌석 4석이 찬 room"만 기다렸다. 그런데 4석이 차는 시점은 ready 보다 앞이라, 곧바로 start 를 누르면 err ready 를 받는다. 조건을 "4석 + 사람 좌석 전부 준비"로 고쳤다.
② 좌석을 i:-1(자동 배정)로 잡았더니, 연결 두 개의 seat 가 도착하는 순서에 따라 좌석 0의 주인이 뒤바뀌어 atk 가 err own 으로 막히는 일이 드물게 났다. 23부의 봇에서 겪은 것과 같은 함정이라 여기서도 좌석 번호를 명시한다 — 둘 다 테스트의 버그였지 서버의 버그가 아니었다.
