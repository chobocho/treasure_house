{{N}}stats[] — JS 와의 계약

wasm 은 함수 호출로 값을 돌려주지 않는다. 정수 배열 하나를 선형 메모리에 두고 JS 가 그 위에 Int32Array 창을 낸다. 프레임마다 30개 값을 공짜로 읽는다.

enum {
  ST_SCORE = 0, ST_LINES, ST_LEVEL, ST_COMBO, ST_B2B, ST_STATE,
  ST_HOLD, ST_NEXT0, ST_NEXT1, ST_NEXT2, ST_NEXT3, ST_NEXT4,
  ST_CLEAR, ST_TSPIN, ST_GAIN, ST_PIECES, ST_ELAPSED, ST_GRAVITY,
  ST_PIECE, ST_ROT, ST_X, ST_Y, ST_GHOST, ST_EVENT, ST_ROWMASK,
  ST_PERFECT, ST_LOCKPCT,
  ST_ATTACK,        // 이번 락으로 상대에게 보낸 줄 수 (상쇄 후)
  ST_PENDING,       // 아직 올라오지 않고 대기 중인 가비지 줄 수
  ST_GARBAGE_RECV,  // 지금까지 실제로 밀려 올라온 누적 줄 수
  ST_COUNT
};

3편이 쓰는 칸은 실질적으로 다섯이다: ST_EVENT(락이 났는가) · ST_ATTACK(얼마 보낼까) · ST_CLEAR(줄을 지웠는가) · ST_STATE(죽었는가) · ST_PENDING(대기 몇 줄).

ST_EVENT 가 핵심이다락이 날 때마다 1씩 는다. 아래층을 고치지 않고 "락 훅"을 만드는 방법이 이것뿐이다 — 부르기 전 값과 부른 뒤 값을 비교하면 된다.

상쇄가 먼저다내가 낸 공격은 내 대기열을 먼저 깎고 남은 만큼만 상대에게 간다. 그래서 맞받아치면 가비지가 아예 올라오지 않는다. 2편은 이 상쇄를 숫자 하나로 했고, 3편은 덩어리 목록에 대고 한다.

{{N}}2편의 1:1 이 8인으로 갈 때 깨지는 것

❶ 가비지가 숫자 하나였다

1:1 에서는 "누가 보냈나"가 자명하다. 8인에서는 막타를 누가 쳤는지를 알아야 등수 화면이 성립한다.

❷ 구멍을 각자 뽑았다

내 판의 구멍은 내 난수로 뽑아도 된다. 그런데 남이 내 판을 보고 있으면 그 구멍이 서로 달라진다.

❸ 화면을 보낼 일이 없었다

같은 페이지의 두 인스턴스는 메모리를 직접 읽으면 그만이다. 8인은 200칸을 초당 10번 남에게 보내야 한다.

❹ 심판이 JS 함수였다

2편의 Referee 는 같은 페이지의 객체였다. 8인의 심판은 다른 기계에서, 다른 언어로 돈다.

3부는 ❶❷❸ 을 C++ 층에서 해결하고, 5~15부가 ❹ 를 해결한다.
