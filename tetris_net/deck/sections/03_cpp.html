{{N}}아래층을 고치지 않고 층을 얹는 법

2편의 ai.cpp 는 tetris.cpp 를 #include 로 삼켰다. 3편도 같은 수를 쓴다.

  net.cpp
    └── #include "../tetris_ai/ai.cpp"
                    └── #include "tetris.cpp"

  번역 단위(translation unit)가 하나이므로 net.cpp 는
  tetris.cpp 의 static 변수(board, stats, pending_garbage…)와
  static 함수(collide, push_rows…)를 그대로 볼 수 있다.

  그런데 이 층은 일부러 그러지 않는다 — 공개 익스포트만 쓴다.
    ts_init · ts_update · ts_press · ts_release · ts_garbage · ai_plan · ai_apply
  왜? 규칙을 두 곳에서 쓰기 시작하면 그때부터 아래층을 고쳐야 하기 때문이다.
딱 한 군데 예외stats[] 배열은 직접 읽고 쓴다. stats[ST_EVENT] 로 락을 감지하고 stats[ST_ATTACK] 을 상쇄 후 값으로 덮어쓴다. 이 배열은 애초에 "바깥에 보여 주려고 만든" 공개 상태이고, JS 도 같은 배열을 TypedArray 로 읽는다.

{{N}}net.cpp — 무엇을 더하는가

Chunk 를 정수 4개짜리 평범한 구조체로 둔 이유: JS 가 Int32Array 로 대기열 전체에 창을 내어 복사 없이 게이지를 그린다. 배열이 정적이라 힙도, 할당도 없다.

{{N}}대기열은 배열 하나

ngq_pop 은 앞에서 하나 빼고 나머지를 당긴다 — O(n) 이다. 링버퍼로 만들면 O(1) 이지만 n 이 최대 24고, 부르는 건 조각을 놓을 때뿐(초당 5~10회)이다. 링버퍼는 JS 에서 Int32Array 로 순서대로 읽는 코드를 복잡하게 만든다 — 여기서는 단순한 쪽이 이긴다.

ng_sync_pending 이 하는 일대기 줄 수 합계를 stats[ST_PENDING] 에 써 둔다. JS 가 매 프레임 ng_pending() 을 부르는 대신 이미 읽고 있는 배열에서 가져가게 하려고.

{{N}}락 한 번에 일어나는 일 전부

순서가 곧 규칙이다. ①상쇄 → ②남은 몫 적립 → ③솟아오름. 이 순서를 바꾸면 "맞받아쳤는데도 줄이 올라오는" 게임이 된다.

{{N}}상쇄를 그림으로

  대기열      [ 4줄(좌석5) ][ 2줄(좌석1) ][ 3줄(좌석7) ]   합계 9줄
  내 공격     테트리스 = 4줄

  ① 앞에서부터 깎는다
              [ 4줄 ] 을 통째로 지운다            남은 공격 0
  대기열      [ 2줄(좌석1) ][ 3줄(좌석7) ]        합계 5줄

  ② 서버로 보낼 몫 = 0    → atk 메시지를 아예 보내지 않는다
  ③ 줄을 지웠으므로(clear=4) 솟지 않는다 — 단, 맨 앞 덩어리가 900ms 넘게 묵었으면 솟는다

왜 앞에서부터인가

먼저 온 게 먼저 묵는다. 뒤에서 깎으면 맨 앞 덩어리가 영원히 늙어 delay 규칙이 무의미해진다.

왜 stats[ST_ATTACK] 을 덮어쓰나

JS 가 그 값을 그대로 서버에 싣는다. 상쇄 전 값을 보내면 상쇄한 만큼 상대가 두 번 맞는다.

{{N}}락 훅 — ST_EVENT 를 지켜본다

락은 세 경로로 난다: 중력(ts_update) · 하드드롭(ts_press) · AI 착수(ai_apply). 셋을 다 감싸야 한다. 하나라도 빠뜨리면 그 경로의 가비지가 통째로 사라진다 — 테스트 두 개가 이걸 지킨다(23부).

{{N}}dt 상한을 똑같이 맞추는 이유

EXPORT(ng_update) int ng_update(int dt_ms) {
  if (dt_ms > 100) dt_ms = 100;        // 아래층과 같은 상한
  for (int i = 0; i < ngq_n; i++) ngq[i].age += dt_ms;
  int ev = stats[ST_EVENT];
  ts_update(dt_ms);
  ...

ts_update 는 안에서 dt > 100 → 100 으로 자른다(탭 전환 후 몇 초짜리 dt 를 막으려고). 이 층이 자르지 않고 원래 dt 로 나이를 더하면 탭을 5초 껐다 켰을 때 대기열만 5초 늙는다 — 판은 100ms 만 흘렀는데.

이런 종류의 버그두 층이 같은 값을 각자 해석할 때 생긴다. 고치는 방법은 둘 중 하나 — 상한을 한 곳으로 모으거나, 여기처럼 같은 상한을 명시적으로 되풀이하고 왜 그런지 주석에 적거나. 아래층을 못 고치는 상황에서는 후자뿐이다.

{{N}}서버와 주고받는 두 방향

ng_take_attack() 이 "읽으면 비워진다"인 게 중요하다. JS 가 프레임을 한 번 건너뛰어도 줄 수가 사라지지 않고 다음 프레임에 합쳐서 나간다. 프레임 드롭이 곧 공격 손실이 되면 느린 기계가 불리해진다.

{{N}}대기열이 넘치면

if (ngq_n >= NG_MAXQ) { ngq[NG_MAXQ - 1].n += n; ng_sync_pending(); return; }

덩어리 24개가 다 차면 마지막 덩어리에 합쳐 넣는다. 버리지 않는다 — 버리면 "때렸는데 안 맞았다"가 되어 대전이 이상해진다. 구멍 위치는 마지막 덩어리 것을 따라간다.

24개면 충분한가

덩어리 하나는 조각 하나를 놓을 때 생긴다. 24개가 쌓이려면 내가 조각을 한 번도 못 놓는 동안 남들이 24번 공격해야 한다. 그 전에 이미 죽는다.

왜 상한이 필요한가

정적 배열이라서다. 동적 할당을 쓰면 상한이 필요 없지만, 이 wasm 은 -nostdlib 라 malloc 자체가 없다.

{{N}}Node 에서 wasm 을 여는 최소 로더

C++ 의 enum 을 JS 에 손으로 옮겨 적은 표다. 이게 ABI 다 — 한쪽만 고치면 조용히 어긋난다. 그래서 테스트가 s[4] === 높이 같은 걸 명시적으로 확인한다.

{{N}}모듈 하나, 인스턴스 여덟

refresh() 를 부르는 이유wasm 이 메모리를 늘리면 기존 TypedArray 는 detach 되어 길이 0이 된다. 이 wasm 은 메모리를 늘리지 않지만(전부 정적), 그 가정에 기대는 코드는 언젠가 반드시 깨진다. 창을 다시 만드는 함수를 두고 메모리를 건드릴 만한 호출 뒤에 부른다.

{{N}}프로토콜 조각을 로더에 붙여 둔다

snapshot/packState 를 로더 옆에 둔 이유는 이것들이 wasm 메모리 배치를 아는 유일한 코드이기 때문이다. 프로토콜 층은 "문자열 하나와 정수 12개"만 알면 된다.

브라우저 쪽에도 같은 함수가 있다netcore_browser.js — 다른 건 Buffer 대신 btoa/atob 를 쓰는 두 줄뿐이다(16부). 두 벌을 유지하는 대신 한 벌로 합칠 수도 있지만, Node 전용 import 를 브라우저 스크립트에 끌고 들어가는 값이 더 비쌌다.
