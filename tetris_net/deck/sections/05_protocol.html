{{N}}규격을 먼저 쓴다

서버를 두 언어로 만들 작정이면 순서가 정해진다. 규격 → 검증표 → 구현 → 구현.

  ① protocol.md            사람이 읽는 규격. 메시지 표 · 난수 소비 순서 · 오류 코드
  ② protocol_vectors.json  기계가 읽는 규격. 입력 44스텝과 기대 출력
  ③ room.mjs               1번째 구현 (JS) — 벡터를 통과시킨다
  ④ room.go / room.py      2·3번째 구현 — 같은 벡터로 통과시킨다

  ②를 ③보다 먼저 손으로 쓰는 게 핵심이다. 구현에서 뽑아낸 표는 검증이 아니라 사진이다.
실제로 이 순서로 했다벡터 44스텝을 먼저 손으로 적고(난수 값만 xorshift32 를 돌려 계산했다), 그다음 room.mjs 를 썼다. 첫 실행에서 48개 검사가 전부 통과했다 — 규격이 스스로 모순이 없었다는 뜻이다.

peer 는 사람이 아니라 PC 다. 이 한 줄 때문에 "한 PC 에 2명"이 예외 처리가 아니라 규격의 일부가 된다.

{{N}}room 엔진 계약과 방 설정

{{N}}난수를 뽑는 자리는 정확히 세 곳

  방 하나 = xorshift32 하나.  seed → 순서대로 소비.

  ① start      라운드 시드   ← 모든 좌석의 7-bag 시드가 된다        1회
  ② 타겟 선택  random 으로 떨어질 때만                              0 또는 1회
  ③ 구멍 위치  grb 하나당 정확히 1회                                1회

  예) seed=7, 좌석 4석, target=random
      start           → 1892583        라운드 시드
      atk{i:0,n:2}    → 470389255 % 3 = 1  → 후보[1] = 좌석 2
                      → 3882205507 % 10 = 7 → 구멍 x=7
                      = grb {i:2, n:2, from:0, hole:7}

  ②와 ③의 순서를 바꾸면?  세 구현이 전부 다른 값을 내고, 골든 벡터가 즉시 잡는다.
왜 xorshift32 인가3줄이면 어느 언어로든 똑같이 옮겨진다. 파이썬은 무한정수라 & 0xFFFFFFFF 를, JS 는 >>> 0 을 붙여야 32비트가 된다. Go 는 uint32 라 저절로 맞는다 — 이 셋이 다르게 새는 지점이 정확히 여기다.

{{N}}실제로 오가는 메시지

가상 PC 2대가 2석씩 잡고 붙는 4인 대전의 날것 그대로의 메시지다. ▲ 는 올라가는 것, ▼ 는 내려오는 것. st 와 pong 은 너무 많아 숨겼다. 프로토콜은 정말 이게 전부다.

{{N}}왜 JSON 인가 — 그리고 언제 아닌가

JSON 을 고른 이유

세 언어(Go·파이썬·JS)에 표준 라이브러리로 들어 있다. 스키마 컴파일러도, 코드 생성도 필요 없다. 골든 벡터를 사람이 손으로 쓸 수 있다는 게 결정적이었다.

대가

같은 내용을 바이너리로 짜면 1/3 이하다. 하지만 실측 대역폭이 PC 당 1.5 KB/s 라 아낄 이유가 없다.

바이너리가 필요해지는 선

좌석이 100석을 넘거나(배틀로열), st 를 30Hz 로 올리거나, 리플레이를 통째로 저장할 때. 그때는 b 필드의 런렝스를 base64 없이 바이너리 프레임으로 보내면 33% 가 줄어든다.

남겨 둔 자리

WebSocket 은 텍스트/바이너리 프레임을 같은 연결에서 섞어 보낼 수 있다. 제어는 JSON, 화면은 바이너리로 가는 길이 열려 있다.
