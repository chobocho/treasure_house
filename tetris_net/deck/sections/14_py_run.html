{{N}}server.py — 실행 파일

Go 판과 같은 인터페이스를 유지한다: --port, --dir, /healthz, /rooms, /ws. 운영 도구가 두 서버를 구분하지 않아도 되게.

{{N}}정적 파일과 경로 탈출

.. 를 막는 법문자열에서 .. 를 찾아 지우는 건 틀린 방법이다(....//, URL 인코딩, 심볼릭 링크). os.path.realpath 로 실제 경로를 구해 루트 아래에 있는지 비교하는 게 맞다 — 심볼릭 링크까지 풀어 준다.

{{N}}시그널과 종료

loop.add_signal_handler 는 윈도우에 없다. NotImplementedError 를 받아 signal.signal 로 떨어지는 두 줄이 그 대비다.

{{N}}진입점

$ python3 server.py --port 8787 --dir ../web
듣는 중: 0.0.0.0:8787 (프로토콜 v3)

$ curl -s localhost:8787/healthz ; echo
ok
$ curl -s localhost:8787/rooms ; echo
{"v": 3, "rooms": []}

{{N}}테스트 세 층 — 파이썬 판

파일 하나에 세 층이 다 들어 있다. Go 는 파일이 셋이었는데, 파이썬은 unittest 가 클래스 단위로 나눠 주므로 굳이 쪼갤 이유가 없다 — 언어의 관습을 따르는 편이 낫다.

{{N}}골든 벡터 — subTest 로

subTest 를 쓰는 이유케이스 하나가 실패해도 나머지 아홉 개를 계속 돈다. Go 의 t.Run 서브테스트와 같은 역할이다. 실패가 여러 개일 때 한 번에 다 보이는 게 중요하다 — 난수 순서가 어긋나면 대개 세 케이스가 동시에 깨진다.

{{N}}프레임 — 바이트 배열로 직접

Go 는 net.Pipe() 로 왕복시켰고 파이썬은 만들어진 바이트를 직접 뜯어본다. 둘 다 맞다. 파이썬 쪽이 "0x81 은 FIN+텍스트"라는 규격을 더 직접적으로 보여 준다.

{{N}}비동기 테스트 준비

port=0 으로 열고 getsockname()[1] 로 실제 포트를 받는다. 고정 포트를 쓰면 테스트를 두 번 동시에 못 돌린다. Go 의 httptest.NewServer 가 해 주는 일을 손으로 하는 것뿐이다.

{{N}}간단한 세 가지

{{N}}PC 2대 × 2석 = 4인

Go 판과 같은 시나리오, 같은 단언이다: 두 PC 가 받은 seed 가 같은가, 두 PC 가 받은 grb 가 같은가, 구멍이 0~9 안인가.

{{N}}PC 가 사라지면 (파이썬)

end.order 가 [0, 1] 인지까지 본다 — 살아남은 좌석 0 이 1등, 끊긴 좌석 1 이 2등. Go 판보다 한 단계 더 확인한다.
