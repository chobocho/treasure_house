이 덱은 무엇인가

《Go로 만드는 GW-BASIC 인터프리터》는 약 6,400줄의 Go 코드를 처음부터 끝까지 읽어 나가는 책입니다. 그런데 그 책의 3장 제목은 “Go 개발 환경 구축”이고, 내용은 go mod init부터 시작합니다. 언어 자체를 가르치는 장은 없습니다.

즉 그 책은 Go를 이미 안다고 가정합니다. 이 덱은 그 빈칸을 메웁니다. 목표는 딱 하나입니다.

목표 — 그 책에 나오는 Go 코드를 막힘없이 읽을 수 있게 만드는 것.

그래서 Go의 모든 것을 다루지 않습니다. 그 책에 실제로 나오는 문법만 골라, 필요한 순서대로 배웁니다.

다루는 것 / 다루지 않는 것

✔ 다룬다

선언과 제로값 · iota 상수 블록 · 기본 타입과 명시적 변환 · 문자열/byte/rune · 제어 흐름과 switch · 슬라이스와 append · 맵 · 구조체와 임베딩 · 포인터 · 다중 반환값 · 클로저 · 메서드와 리시버 · defer/panic/recover · 인터페이스와 타입 스위치 · error 관용구 · goroutine·channel·context(최소한) · fmt 서식 · testing · go build와 크로스 컴파일

✘ 다루지 않는다

제네릭 타입 파라미터 · sync 패키지와 뮤텍스 · 워커 풀 패턴 · reflect(테스트의 DeepEqual 제외) · unsafe · cgo · 이터레이터(range over func) · 임베디드 파일(go:embed) · 웹/HTTP · 데이터베이스 · context의 취소 트리 설계

기준 — 오른쪽 항목들은 그 책의 코드에 거의 또는 전혀 나오지 않습니다. 실제로 세어 보면 제네릭 0회, sync. 0회, reflect는 테스트의 reflect.DeepEqual뿐입니다. 나중에 필요해지면 그때 배워도 늦지 않습니다.

전제로 하는 것

프로그래밍을 한 번이라도 해 봤다면 충분합니다. 변수, if, 반복문, 함수라는 말이 낯설지 않으면 됩니다. C, Java, Python, JavaScript, 심지어 BASIC이라도 좋습니다.

Go는 문법이 대단히 작은 언어입니다. 예약어가 25개뿐이고, 클래스도 상속도 예외도 없습니다. 그래서 “문법을 배우는” 시간이 짧고, 대신 왜 이렇게 생겼는지를 납득하는 시간이 깁니다. 이 덱은 뒤쪽에 무게를 둡니다.

팁 — 브라우저만 있으면 go.dev/play에서 바로 실행해 볼 수 있습니다. 설치했다면 go run . 한 줄이면 됩니다. 이 덱의 예제는 전부 실제 Go 컴파일러로 돌려 확인한 것입니다.

이 덱을 끝내면 읽히는 코드

아래는 그 책 16장에 나오는 진짜 코드입니다. 지금은 절반쯤 외계어로 보여도 정상입니다.

func (m *VM) push(v runtime.Value) { m.stack = append(m.stack, v) }

func (m *VM) pop() runtime.Value {
	n := len(m.stack) - 1
	v := m.stack[n]
	m.stack = m.stack[:n]
	return v
}

func (m *VM) Run(ctx context.Context) error {
	for !m.halted {
		if err := ctx.Err(); err != nil {
			return err
		}
		ins := m.ch.Code[m.pc]
		m.pc++
		if err := m.step(ctx, ins); err != nil {
			return err
		}
	}
	return nil
}

여기 들어 있는 개념은 포인터 리시버 (m *VM), 슬라이스와 append, 슬라이싱 s[:n], := 단축 선언, if의 초기화절, error 반환 관용구, 그리고 context입니다. 전부 이 덱에서 다룹니다.

전체 지도

이 덱은 아홉 부로 나뉩니다. 앞의 다섯 부가 언어의 본체이고, 뒤의 네 부는 “그 책을 읽는 데 필요한 나머지”입니다.

1부Go라는 도구 — 역사, go 명령, 패키지와 모듈
2부값과 타입 — 선언, 제로값, 기본 타입, 문자열, 제어 흐름
3부복합 타입 — 슬라이스, 맵, 구조체, 포인터
4부함수와 메서드 — 다중 반환, 클로저, 리시버, defer
5부인터페이스 — 암묵적 구현, 타입 어설션, 타입 스위치
6부에러 — error는 값이다
7부동시성 — 이 책이 쓰는 만큼만 (goroutine·channel·context)
8부표준 라이브러리와 도구 — fmt, strconv, testing, 빌드
9부그 책 읽기 — 실제 코드 해부와 흔한 함정
순서에 이유가 있습니다 — 3부의 슬라이스와 5부의 인터페이스가 이 덱의 두 봉우리입니다. 그 책의 VM 스택은 슬라이스이고, AST 노드 분기는 인터페이스입니다. 이 둘을 모르면 책이 안 읽히고, 이 둘을 알면 나머지는 따라옵니다.

Go라는 도구

어떤 언어이고, 어디서 왔고, 어떻게 돌리는가

1장

Go란 무엇인가

“큰 팀이 큰 프로그램을 오래 유지하는 것”이 이 언어의 설계 목표입니다.

1.1 한 문단 요약

Go는 구글에서 2007년에 시작해 2009년 11월 10일에 오픈소스로 공개된 컴파일 언어입니다. 설계자는 로버트 그리즈머, 롭 파이크, 켄 톰슨 세 사람입니다. 켄 톰슨은 유닉스와 C의 공동 창시자이고, 롭 파이크는 Plan 9와 UTF-8의 공동 설계자입니다.

목적대규모 서버 소프트웨어를 여러 사람이 오래 유지보수하기. 개인의 표현력보다 팀의 가독성을 우선합니다.
실행 방식기계어로 정적 컴파일. 런타임이 바이너리 안에 들어가므로 결과물은 의존성 없는 단일 실행 파일입니다.
메모리가비지 컬렉션. 포인터는 있지만 포인터 연산은 없습니다.
타입정적 타입. 다만 :=로 대부분 추론되므로 타이핑 양은 스크립트 언어에 가깝습니다.
동시성goroutine과 channel이 언어 문법에 들어 있습니다. 라이브러리가 아닙니다.
라이선스BSD 3-Clause. 상용 제품에 그대로 넣을 수 있습니다.
이름 — 공식 명칭은 Go입니다. 검색이 어려워 “Golang”이라 부르는 관습이 생겼고(도메인이 golang.org였습니다), 지금은 공식 사이트가 go.dev입니다. 문서와 코드에서는 Go로 씁니다.

1.2 왜 만들었나

탄생 설화가 구체적입니다. 구글 안에서 C++ 프로젝트 하나를 빌드하는 데 45분이 걸렸고, 그 45분 동안 세 사람이 “우리가 원하는 언어”를 이야기하다 시작됐다는 것입니다.

그래서 Go의 설계 결정은 대부분 무엇을 넣을까가 아니라 무엇을 빼야 빌드가 빨라지고 코드가 단순해지는가에서 나왔습니다.

뺀 것클래스 상속 · 예외(try/catch) · 함수 오버로딩 · 기본 인자 · 연산자 오버로딩 · 포인터 연산 · 헤더 파일 · 매크로 · 순환 import
넣은 것인터페이스의 암묵적 구현 · 다중 반환값 · defer · goroutine/channel · 표준 포매터 gofmt · 모듈 시스템
읽는 법 — Go 코드를 읽다가 “왜 이렇게 장황하지?”라는 생각이 들면, 대개 다른 언어라면 감춰졌을 무언가를 일부러 드러낸 것입니다. 에러 처리가 대표적입니다. 이 덱은 그 “왜”를 매번 짚습니다.

1.3 어디에 쓰이나

“네트워크 서비스와 개발 도구”라는 자리를 확실히 잡았습니다. 여러분이 매일 쓰는 도구 중 상당수가 Go로 쓰여 있습니다.

  • 컨테이너·클라우드 — Docker, Kubernetes, containerd, Terraform, etcd, Prometheus
  • 개발 도구 — Hugo(정적 사이트), gh(GitHub CLI), Delve(디버거), golangci-lint
  • 데이터베이스 — CockroachDB, InfluxDB, TiDB, Dgraph
  • 네트워크 — Caddy(웹 서버), Traefik, gRPC의 Go 구현, Tailscale

공통점이 보입니다. 여러 대의 기계에 배포해야 하고, 동시 요청을 처리해야 하고, 팀이 오래 유지해야 하는 프로그램입니다. 단일 바이너리로 떨어지는 배포 편의성이 결정적이었습니다.

그래서 — Go는 “한 줄로 뭔가 뚝딱”하는 언어가 아닙니다. 표준 라이브러리는 크지만(HTTP 서버가 기본 내장) 언어 자체는 작습니다. 화려한 트릭이 없다는 것이 장점으로 팔리는 드문 언어입니다.

1.4 버전 지도

Go에는 Go 1 호환성 약속이 있습니다. 2012년 Go 1.0에 맞춰 쓴 코드는 오늘의 컴파일러에서도 컴파일됩니다. 이 점이 다른 언어들과 크게 다릅니다.

1.0 2012호환성 약속 시작. 여기서부터 문법은 거의 그대로입니다.
1.11 2018모듈(go.mod) 도입. GOPATH 시대가 끝났습니다.
1.13 2019에러 래핑 %w, errors.Is/errors.As.
1.18 2022제네릭과 any. 언어에 추가된 가장 큰 기능입니다.
1.21 2023내장 함수 min/max/clear, 구조화 로깅 log/slog.
1.22 2024루프 변수가 반복마다 새로 만들어짐. 오래된 함정 하나가 사라졌습니다.
1.23~ 2024~이터레이터(range over func), 제네릭 타입 별칭, 그리고 계속.
이 책의 선택 — 《Go로 만드는 GW-BASIC 인터프리터》는 go.mod에 go 1.22를 적고, 외부 의존성을 하나도 쓰지 않습니다. 제네릭도 쓰지 않습니다. 그래서 이 덱도 제네릭을 다루지 않습니다. 다만 1.22의 루프 변수 변경은 반드시 알아야 하므로 13장에서 따로 짚습니다.

1.5 가장 작은 Go 프로그램

설명 전에 형태부터 봅니다. 이것이 컴파일 가능한 완전한 프로그램입니다.

main.go

package main

import "fmt"

func main() {
	fmt.Println("hello, 세계")
}
$ go run . hello, 세계

여섯 줄에 Go의 규칙이 네 개 들어 있습니다.

  1. 모든 파일은 package 선언으로 시작한다. 실행 파일이 되려면 이름이 main이어야 한다.
  2. 실행은 func main()에서 시작한다. 인자도 반환값도 없다.
  3. 쓸 것은 import로 명시한다. 안 쓰는 import는 컴파일 에러다.
  4. 다른 패키지의 것을 쓰려면 fmt.Println처럼 대문자로 시작해야 한다. 소문자는 그 패키지 밖에서 안 보인다.
세미콜론 — 문법상으로는 필요하지만 여러분이 쓰지 않습니다. 컴파일러가 줄 끝에 자동으로 넣습니다. 그래서 여는 중괄호를 다음 줄에 쓰면 안 됩니다(다음 슬라이드).

1.6 중괄호를 다음 줄에 쓰면 안 되는 이유

Go의 렉서는 줄 끝 토큰이 식별자·리터럴·)·]·}·++·--·return 등이면 그 자리에 세미콜론을 자동 삽입합니다. 이것이 “세미콜론을 안 써도 되는” 정체입니다.

✔ 이렇게
func main() {
	fmt.Println("ok")
}
✘ 이러면 에러
func main()
{
	fmt.Println("ok")
}

오른쪽은 func main() 뒤에 세미콜론이 삽입되어 본문 없는 함수 선언이 되어 버립니다.

# gv ./main.go:6:1: syntax error: unexpected semicolon or newline before {
다행히 — 이걸 외울 필요는 없습니다. gofmt가 모든 서식을 강제로 통일하므로, 저장할 때마다 자동으로 올바른 자리에 놓입니다. Go 세계에는 “들여쓰기 스타일 논쟁”이 존재하지 않습니다.

1.7 gofmt — 논쟁이 없는 언어

Go는 표준 포매터를 언어와 함께 배포합니다. 옵션이 거의 없습니다. 탭 들여쓰기, 정해진 줄바꿈 규칙, 정해진 정렬. 취향은 반영되지 않습니다.

입력 — 아무렇게나
type Token struct{
Kind TokenKind
Lex string
Line int
}
gofmt 통과 후
type Token struct {
	Kind TokenKind
	Lex  string
	Line int
}

필드 이름의 세로 정렬까지 맞춰 줍니다. 그 책의 코드가 하나같이 반듯한 이유가 이것입니다.

실무에서는 — 편집기가 저장 시 자동 실행하게 해 둡니다. 직접 부를 일은 드물지만 명령은 gofmt -w . 또는 go fmt ./...입니다. 그 책 4.3절은 “모든 코드를 gofmt로 포맷하고 go vet ./...을 통과시킨다고 가정”한다고 못박습니다.

1.9 왜 인터프리터를 Go로 짜는가

인터프리터 구현 교재는 보통 C, Java, Python, Rust로 쓰입니다. Go도 드물지는 않지만 첫 선택은 아닙니다. 그런데 이 주제에 유난히 잘 맞는 이유가 있습니다.

단일 바이너리완성된 인터프리터를 gwbasic.exe 하나로 배포할 수 있습니다. 런타임 설치가 필요 없습니다. 32장이 이 이야기입니다.
크로스 컴파일리눅스에서 GOOS=windows go build 한 줄로 윈도 실행 파일이 나옵니다. 도스 시절 프로그램을 다루는 책에 어울립니다.
switch 디스패치바이트코드 VM의 심장은 거대한 switch입니다. Go 컴파일러는 이것을 점프 테이블로 최적화합니다.
인터페이스화면·소리 출력을 Host 인터페이스 하나로 추상화하면, 터미널판·이미지판·테스트용 무동작판을 자유롭게 갈아 끼울 수 있습니다.
표준 testing외부 프레임워크 없이 go test ./...만으로 회귀 테스트가 굴러갑니다. 31장이 이 이야기입니다.
제약도 하나 — Go는 태그 유니온(합 타입)이 없습니다. 그래서 그 책의 Value는 모든 경우의 필드를 다 가진 구조체 + 태그로 표현됩니다. 이 설계가 왜 그렇게 됐는지는 10장과 25장에서 봅니다.

1.10 Go를 쓰며 치르는 대가

공정하게 짚고 갑니다. Go에는 분명히 불편한 점이 있고, 그 책의 코드에도 흔적이 남아 있습니다.

장황한 에러 처리if err != nil { return err }가 코드의 상당 부분을 차지합니다. 그 책의 Go 코드에서 != nil/== nil 검사는 290회 나옵니다.
합 타입 없음“정수이거나 문자열”을 표현하려면 태그 + 여러 필드이거나, 인터페이스 + 타입 스위치입니다. 둘 다 씁니다.
제로값의 양면성선언만 해도 값이 생기는 건 편하지만, “초기화 안 함”과 “0으로 초기화함”을 구별할 수 없습니다.
nil의 여러 얼굴nil 맵에는 읽을 수는 있어도 쓸 수 없고, nil 슬라이스에는 append할 수 있습니다. 8·9장에서 다룹니다.
덱의 태도 — 이런 것들을 “Go의 매력”이라고 포장하지 않겠습니다. 대가는 대가입니다. 다만 왜 그 대가를 치르기로 했는지는 매번 설명하겠습니다. 납득하고 쓰는 것과 참고 쓰는 것은 다릅니다.

Q. 다음 코드가 컴파일되지 않는 이유는?

package main

import (
	"fmt"
	"os"
)

func main() {
	fmt.Println("hi")
}
A. os를 import했는데 쓰지 않았기 때문입니다. Go는 안 쓰는 import를 에러로 취급합니다("os" imported and not used). 안 쓰는 지역 변수도 마찬가지로 에러입니다. 빌드 시간을 지키고 죽은 코드를 막기 위한 선택이며, 2장에서 다시 봅니다.

2장

go 명령 — 도구가 곧 언어다

Go는 컴파일러·포매터·테스트 러너·의존성 관리자를 한 명령에 묶어 배포합니다.

2.1 알아야 할 명령은 여덟 개

go help가 19개의 하위 명령을 보여 주지만, 그 책을 따라가는 데 필요한 것은 이만큼입니다.

go run .현재 디렉터리 패키지를 컴파일해 바로 실행. 실행 파일은 임시 디렉터리에 만들고 지웁니다.
go build실행 파일을 현재 디렉터리에 만듭니다. 이름은 모듈/디렉터리 이름.
go test ./...모든 하위 패키지의 테스트를 찾아 실행. ./...은 “여기부터 전부”라는 뜻입니다.
go vet ./...컴파일은 되지만 수상한 코드를 잡습니다. 서식 문자열 불일치가 대표적입니다.
go fmt ./...gofmt -l -w를 부르는 얇은 껍데기. 서식 통일.
go mod init새 모듈 시작. go.mod를 만듭니다.
go mod tidy실제 import를 훑어 go.mod/go.sum을 정리합니다.
go doc패키지·심볼 문서를 터미널에 출력. go doc strings.Builder처럼 씁니다.
./...의 정체 — 셸 와일드카드가 아니라 go 도구가 해석하는 패키지 패턴입니다. 따옴표 없이 그대로 씁니다. ./...은 현재 디렉터리와 그 아래 모든 패키지를 뜻합니다.

2.2 go run과 go build의 차이

go run — 실행만
$ go run . hello, 세계 $ ls go.mod main.go

파일이 남지 않습니다. 스크립트처럼 쓸 때.

go build — 파일이 남음
$ go build $ ls go.mod main.go gv $ ./gv hello, 세계

배포할 물건을 만들 때.

그 책 3.5절이 이 이야기를 합니다. 완성된 인터프리터는 go build ./cmd/gwbasic으로 gwbasic 실행 파일 하나가 되고, 그 파일만 복사하면 Go가 설치되지 않은 컴퓨터에서도 돕니다.

왜 그런가 — Go는 표준 라이브러리와 런타임(GC, 스케줄러 포함)을 결과물 안에 정적으로 링크합니다. 그래서 fmt.Println 한 줄짜리 “hello world”도 2.5MB쯤 됩니다(Go 1.26 기준 실측). 크기를 디스크가 아니라 배포 단순함과 맞바꾼 선택입니다.

2.3 안 쓰면 에러다

Go에서 가장 먼저 부딪히는 벽입니다. 쓰지 않는 지역 변수와 쓰지 않는 import는 경고가 아니라 컴파일 에러입니다.

package main

func main() {
	x := 42
}
# gv ./main.go:4:2: declared and not used: x

처음에는 짜증스럽지만 이유가 있습니다. 죽은 코드가 쌓이는 것을 원천 차단하고, 무엇보다 컴파일러가 확인할 것을 줄여 빌드를 빠르게 합니다.

✘ 디버깅 중이라면
import (
	"fmt"
	"os"  // 잠깐 주석 처리했더니 에러
)
✔ 빈 식별자로 눌러 두기
import (
	"fmt"
	_ "os"  // 부작용만 필요할 때의 관용구
)

var _ = x  // 변수도 같은 수법
주의 — 패키지 수준 변수(함수 밖의 var)는 안 써도 에러가 아닙니다. 규칙은 함수 안의 지역 변수에만 적용됩니다.

2.4 go vet — 컴파일러가 놓치는 것

타입은 맞지만 의도는 틀린 코드를 잡아 줍니다. 가장 흔한 사례가 Printf입니다.

fmt.Printf("%d\n", "str")   // 컴파일은 된다. 실행도 된다.

실행하면 %!d(string=str)이라는 이상한 문자열이 찍힙니다. go vet은 이것을 미리 잡습니다.

main.go:5:27: fmt.Printf format %d has arg "str" of wrong type string

go test는 테스트 실행 전에 vet의 일부 검사를 자동으로 돌립니다. 그래서 테스트를 돌리다 vet 에러로 멈추는 일이 생깁니다.

서식 불일치Printf 계열의 동사와 인자 타입/개수
구조체 태그JSON 태그 오타
잠금 복사sync.Mutex를 값으로 복사하는 실수
도달 불가 코드return 뒤의 문장
Nil 비교비교가 항상 참/거짓인 경우
그 책의 기준 — 4.3절은 “모든 코드를 gofmt로 포맷하고 go vet ./...을 통과시킨다고 가정한다”고 명시합니다. 예전 표준이던 golint는 폐기되었고, 지금은 gofmt + go vet + (선택) staticcheck가 표준 조합입니다.

2.5 문서는 코드 안에 있다

Go에는 별도의 문서 문법(Javadoc의 @param 같은 것)이 없습니다. 선언 바로 위의 주석이 곧 문서입니다.

// Tokenize는 소스 문자열 전체를 토큰 슬라이스로 변환합니다.
// 마지막 토큰은 항상 TEOF.
func Tokenize(src string) ([]Token, error) {
	l := &Lexer{src: src, line: 1, col: 1}
	return l.run()
}

이것은 그 책 9.2절의 실제 코드입니다. 관용은 대상 이름으로 문장을 시작하는 것입니다. “Tokenize는 …”, “NewEnv는 …”처럼.

$ go doc strings.Builder package strings // import "strings" type Builder struct { // Has unexported fields. } A Builder is used to efficiently build a string using Builder.Write methods. It minimizes memory copying. The zero value is ready to use. Do not copy a non-zero Builder.
오프라인에서도 — go doc은 네트워크를 쓰지 않습니다. 설치된 표준 라이브러리 소스에서 바로 읽습니다.

3장

패키지와 모듈

그 책의 디렉터리 구조를 이해하려면 이 장이 필요합니다.

3.1 패키지 — 디렉터리 하나가 패키지 하나

Go의 규칙은 단순합니다.

  1. 한 디렉터리의 모든 .go 파일은 같은 패키지에 속한다.
  2. 파일 맨 위의 package 이름은 그 디렉터리 안에서 전부 같아야 한다.
  3. 같은 패키지 안에서는 파일이 나뉘어 있어도 서로 다 보인다. import 필요 없음.

그래서 그 책의 internal/lexer/ 디렉터리에는 이런 파일들이 들어 있고, 전부 package lexer입니다.

internal/lexer/ ├── token.go // TokenKind, Token 타입 ├── keywords.go // keywordSet, IsKeyword ├── lexer.go // Lexer 구조체, Tokenize └── lexer_test.go // 테스트 (package lexer)

lexer.go는 keywords.go의 IsKeyword를 그냥 IsKeyword(s)로 부릅니다. 헤더도, import도 없습니다.

파일 이름은 자유 — Go는 “클래스 이름 = 파일 이름” 같은 규칙이 없습니다. 관용은 snake_case.go이고, _test.go로 끝나는 파일만 특별 취급(테스트 빌드에만 포함)됩니다.

3.2 대문자가 public이다

Go에는 public/private 키워드가 없습니다. 식별자의 첫 글자가 그 역할을 합니다.

Tokenize대문자 → exported. 다른 패키지에서 lexer.Tokenize로 부를 수 있음
run소문자 → unexported. lexer 패키지 안에서만 보임
Token.Kind구조체 필드도 같은 규칙
Lexer.pos소문자 필드 → 밖에서 읽지도 쓰지도 못함
type Lexer struct {
	src    string   // 밖에서 안 보임
	pos    int
	line   int
	col    int
	tokens []Token
}

func Tokenize(src string) ([]Token, error) { ... }  // 밖에서 보임
func (l *Lexer) run() ([]Token, error)     { ... }  // 안 보임

그 책 9.2절의 실제 설계입니다. Lexer 타입 자체는 대문자라 밖에서 보이지만 필드가 전부 소문자라, 바깥 패키지는 Tokenize()를 부르는 것 말고는 할 수 있는 일이 없습니다. 이것이 Go식 캡슐화입니다.

중요 — 이 규칙은 패키지 단위입니다. 같은 패키지 안에서는 소문자든 대문자든 전부 보입니다. “파일 단위 private”이 아닙니다.

3.3 모듈과 go.mod

패키지가 “디렉터리”라면 모듈은 버전 관리와 배포의 단위, 대개 저장소 하나입니다. go.mod 파일이 그 뿌리를 표시합니다.

$ go mod init github.com/chobocho/go_gwbasic

go.mod

module github.com/chobocho/go_gwbasic

go 1.22

단 두 줄입니다. 의존성이 하나도 없기 때문입니다. 그 책은 외부 라이브러리를 쓰지 않는다는 규칙을 세웠으므로, 이 파일은 끝까지 이 상태로 남습니다.

module 줄이 모듈의 import 경로 접두사. 실제 URL일 필요는 없지만 관용은 저장소 주소입니다.
go 줄이 코드가 요구하는 최소 Go 버전. 언어 기능(1.22의 루프 변수 등)의 동작이 여기에 좌우됩니다.
require외부 의존성 목록. 여기서는 비어 있습니다.
go.sum의존성의 해시 목록. 의존성이 없으면 파일 자체가 안 생깁니다.
GOPATH는 잊어도 됩니다 — 2018년 이전에는 모든 Go 코드가 $GOPATH/src 아래에 있어야 했습니다. 모듈이 그것을 끝냈습니다. 이제 아무 디렉터리에서나 go mod init으로 시작하면 됩니다.

3.4 import 경로는 모듈 경로 + 디렉터리

모듈 이름이 github.com/chobocho/go_gwbasic이므로, 그 아래 internal/lexer 디렉터리의 패키지는 이렇게 import합니다.

import (
	"strconv"   // 표준 라이브러리
	"strings"
	"unicode"

	"github.com/chobocho/go_gwbasic/internal/common"  // 같은 모듈 안
)

이것은 그 책 9.2절 lexer.go의 실제 import 블록입니다. 세 가지를 눈여겨보세요.

  1. 표준 라이브러리와 나머지를 빈 줄로 그룹 분리합니다. gofmt가 각 그룹 안에서 알파벳순 정렬합니다.
  2. 경로는 디렉터리이지만 코드에서 쓰는 이름은 package 선언의 이름입니다. 위 경로를 import하면 common.BasicError로 씁니다.
  3. 표준 라이브러리에도 .이 없는 짧은 이름(fmt, os)과 경로형(math/rand → rand., path/filepath → filepath.)이 섞여 있습니다. 마지막 조각이 이름입니다.
이름을 바꾸고 싶다면 — import rt "github.com/.../internal/runtime"처럼 별칭을 줄 수 있습니다. 그 책은 쓰지 않지만, 같은 이름의 패키지 둘을 동시에 쓸 때 필요합니다.

3.5 internal/은 컴파일러가 지키는 담장

그 책의 모든 패키지가 internal/ 아래에 있습니다. 이것은 취향이 아니라 Go 도구가 특별 취급하는 이름입니다.

규칙 — internal/ 디렉터리 안의 패키지는, internal의 부모 디렉터리를 뿌리로 하는 트리 안에서만 import할 수 있습니다. 바깥 모듈이 import하면 컴파일 에러입니다.
go_gwbasic/ ├── go.mod ├── cmd/gwbasic/main.go // internal/… import 가능 └── internal/ ├── common/ // 공통 타입 ├── lexer/ ├── parser/ ├── ast/ ├── compiler/ ├── vm/ ├── runtime/ └── host/

효과는 큽니다. 남이 이 저장소를 의존성으로 가져가도 internal/vm을 직접 건드릴 수 없으므로, 내부 구조를 마음대로 바꿔도 남의 코드가 깨지지 않습니다. 공개 API는 cmd/의 실행 파일뿐입니다.

cmd/는 관습 — internal과 달리 cmd는 도구가 특별 취급하지 않습니다. “실행 파일 하나당 디렉터리 하나”를 넣는 커뮤니티 관습일 뿐입니다.

3.6 순환 import는 불가능하다

A가 B를 import하고 B가 A를 import하면 Go는 컴파일을 거부합니다. 경고가 아니라 언어 차원의 금지입니다.

package gv/a imports gv/b from a.go imports gv/a from b.go: import cycle not allowed

그 책 4.1절의 의존 그래프가 단방향인 이유가 이것입니다.

lexer → parser → ast → compiler → vm → runtime ↑ host

“두 패키지가 서로의 타입을 알아야 할 때”가 반드시 옵니다. 그 책 4.1절은 두 가지 해법을 제시하고 후자를 택합니다.

해법 1 — 한쪽에 몰아넣기

두 패키지를 합쳐 버립니다. 간단하지만 패키지가 비대해집니다.

해법 2 — 제3의 패키지

양쪽이 의존할 internal/common을 만들어 공통 타입(SourcePos, BasicError)을 빼냅니다. 이 책의 선택.

답답함의 대가 — 처음에는 “왜 이걸 못 하지” 싶지만, 순환이 없다는 보장 덕분에 Go는 패키지를 병렬로 컴파일할 수 있고 의존 순서를 즉시 계산할 수 있습니다. 빌드 속도의 큰 축입니다.

3.7 internal/common 실물 보기

import "fmt"

// SourcePos는 소스에서 토큰/노드 위치를 나타냅니다.

	Line int
	Col  int

4.5 빈 식별자 _

“이 값은 필요 없다”고 컴파일러에게 알리는 특수 식별자입니다. 안 쓰는 변수가 에러인 언어에서 필수 장치입니다.

// ① 반환값 버리기

for _, tk := range toks { ... }

// ③ 맵 존재 확인만

import _ "net/http/pprof"

⑤는 관용구입니다. “*TermHost가 Host 인터페이스를 만족하지 않으면 컴파일을 실패시켜라”는 뜻이고, 변수는 실제로 만들어지지 않습니다. 16장에서 다시 봅니다.

4.7 타입 없는 상수 — Go에서 가장 우아한 구석

상수는 타입을 갖지 않을 수 있습니다. 그러면 쓰이는 자리에 맞춰 알아서 변합니다.

K/2는 정수 나눗셈이라 1이고, 3.0/2는 3.0이 실수 상수라 1.5입니다. 상수의 “기본 종류”가 결과를 가릅니다.

변수는 다릅니다 — 아래는 컴파일 에러입니다. 변수가 되는 순간 타입이 확정되고, Go는 암묵적 변환을 절대 하지 않기 때문입니다.

고쳐 쓰려면 float64(c) * d처럼 명시해야 합니다. 5장의 주제입니다.

4.8 iota — 자동 번호 매기기

const 블록 안에서 iota는 0부터 시작해 줄마다 1씩 늘어납니다. 그리고 표현식을 생략하면 윗줄이 반복됩니다.

type TokenKind uint8

const (
	TNumber TokenKind = iota   // 0  — 표현식 "TokenKind = iota"
	TString                    // 1  — 윗줄 반복
	TIdent                     // 2
	TKeyword                   // 3
	TOp                        // 4
	TLParen                    // 5
	TRParen                    // 6
	TComma                     // 7
	TSemicolon                 // 8
	TColon                     // 9
	TEOL                       // 10
	TEOF                       // 11
	TRemText                   // 12
)

그 책 9.1절의 실제 코드입니다. 열세 줄에 타입과 값이 다 정해집니다. 중간에 하나 끼워 넣어도 나머지가 자동으로 밀립니다.

핵심 — 첫 줄의 TokenKind = iota가 이후 모든 줄에 반복됩니다. 그래서 TString도 TokenKind 타입이고 값은 iota(=1)입니다. 타입을 한 번만 적으면 되는 이유입니다.

4.9 iota 규칙 확인하기

iota는 “몇 번째 const 줄인가”를 셉니다. 값이 아니라 줄 번호를 센다는 점이 핵심입니다.

4.10 타입 붙은 상수의 함정과 이득

TokenKind = iota로 만든 상수는 타입이 붙습니다. 그래서 다른 열거형과 섞이지 않습니다.

✔ 얻는 것 — 실수 차단

그 책은 TokenKind와 NumKind를 둘 다 uint8 기반으로 정의합니다. 값이 겹쳐도(둘 다 0부터) 타입이 달라 서로 대입되지 않으므로 안전합니다.

왜 uint8인가 — int(8바이트)가 아니라 uint8(1바이트)로 잡으면 Token 구조체가 작아집니다. 토큰이 수만 개 만들어지는 렉서에서는 의미 있는 차이입니다.

4.11 열거형에 이름 붙이기 — String()

숫자 상수를 fmt.Println에 넘기면 숫자가 찍힙니다. 사람이 읽으려면 이름이 필요합니다. Go의 답은 String() string 메서드입니다.

func (k TokenKind) String() string {
	switch k {
	case TNumber:    return "NUMBER"
	case TString:    return "STRING"
	case TIdent:     return "IDENT"
	case TKeyword:   return "KEYWORD"
	case TOp:        return "OP"
	// ... 생략 ...
	case TEOF:       return "EOF"
	case TRemText:   return "REM_TEXT"
	}
	return "?"
}

이 메서드가 있으면 fmt가 알아서 찾아 씁니다. 등록도, 설정도 없습니다.

var t Token                     // 전부 제로값
fmt.Printf("%v\n", t)
fmt.Printf("%+v\n", t)
fmt.Printf("%d %d\n", TNumber, TString)
{NUMBER 0 0} {Kind:NUMBER Lex: Num:0 Line:0} 0 1
두 가지를 읽어 내세요 — ① Kind가 0인데 NUMBER로 찍혔습니다. String()이 자동으로 불린 것입니다. ② %d를 쓰면 String()을 무시하고 숫자가 나옵니다. 서식 동사가 우선입니다. %+v는 필드 이름까지 붙여 줍니다 — 디버깅에 유용합니다.

5.2 암묵적 변환은 없다

이것이 C/Java/JavaScript에서 온 사람이 가장 많이 부딪히는 벽입니다. Go는 크기가 커지는 방향이라도 자동 변환하지 않습니다.

var a int32 = 5
var b int64 = a          // ✘
var c int = 3
var d float64 = 1.5
e := c * d               // ✘
var f int16 = 40000      // ✘
# gv ./main.go:7:16: cannot use a (variable of type int32) as int64 value in variable declaration ./main.go:10:7: invalid operation: c * d (mismatched types int and float64) ./main.go:11:16: cannot use 40000 (untyped int constant) as int16 value in variable declaration (overflows)

고치는 법은 하나뿐입니다 — 타입(값) 형태로 명시합니다.

var b int64 = int64(a)

세 번째 에러는 성격이 다릅니다. 40000은 타입 없는 상수인데 int16의 범위(−32768~32767)를 벗어나므로, 컴파일러가 컴파일 타임에 잡아냅니다. 변수였다면 조용히 잘려 나갔을 것입니다.

5.3 왜 이렇게 불편하게 만들었나

C의 암묵적 정수 승격은 버그의 고전적 원천입니다. Go는 그 비용을 작성 시점으로 옮겼습니다.

✘ C에서 흔한 사고
// C 의사코드
short s = 40000;   // 조용히 -25536
if (u - 1 >= 0)    // unsigned면 항상 참
	...

컴파일도 되고 경고도 안 나고, 몇 달 뒤 이상한 값이 나옵니다.

✔ Go
var s int16 = 40000  // 컴파일 에러

변환이 필요한 자리에는 반드시 여러분의 손이 닿습니다. 그 자리에서 “범위를 넘으면?”을 생각하게 됩니다.

그 책 17.2절의 ToInt16이 정확히 그 생각을 코드로 옮긴 것입니다.

func ToInt16(v Value) (int16, error) {
	switch v.Tag {
	case TagInt:
		return v.I, nil
	case TagSng:
		f := math.Round(float64(v.F32))
		if f < -32768 || f > 32767 {
			return 0, common.NewError(common.ErrOverflow, "Overflow")
		}
		// ... 범위 확인 후에야 int16(f)
	}
}
이것이 GW-BASIC의 ?Overflow 에러입니다 — 원본 GW-BASIC도 정수 범위를 넘으면 에러를 냅니다. Go의 명시 변환 규칙이 “여기서 검사해야 한다”는 자리를 자연스럽게 알려 준 셈입니다.

5.4 넘치면 어떻게 되나

정수 연산감싼다(wrap around). 패닉이 아닙니다. int16의 32767에 1을 더하면 −32768
정수 상수컴파일 에러. 컴파일러가 범위를 안다면 거부합니다
0으로 나누기 (정수)런타임 패닉 — integer divide by zero
0으로 나누기 (실수)+Inf / -Inf / NaN. 패닉 아님
실수 → 정수 변환 시 범위 초과정의되지 않음. 값을 믿으면 안 됩니다
var i16 int16 = 32767
i16++
fmt.Println(i16)
-32768
마지막 줄이 중요합니다 — int16(70000.0)이 무슨 값이 될지는 Go 명세가 정하지 않습니다(플랫폼에 따라 다릅니다). 그래서 그 책의 ToInt16은 변환 전에 범위를 검사합니다. 이것은 조심성이 아니라 필수입니다.

5.5 나눗셈과 나머지의 부호

Go의 정수 나눗셈은 0 방향으로 자릅니다(truncated division). 파이썬(바닥 나눗셈)과 다릅니다.

fmt.Println(7/2, -7/2, 7.0/2.0)
fmt.Println(7%3, -7%3, 7%-3)
3 -3 3.5 1 -1 1
-7/2−3 (Go, C, Java). 파이썬은 −4
-7%3−1. 나머지의 부호는 피제수를 따릅니다. 파이썬은 2
규칙(a/b)*b + a%b == a가 항상 성립합니다
GW-BASIC과 맞나 — 그 책 8.4절이 다루는 주제입니다. GW-BASIC의 \(정수 나눗셈)와 MOD도 0 방향 절단이라 Go의 동작과 일치합니다. 운이 좋았습니다 — 파이썬으로 짰다면 별도 보정이 필요했을 것입니다.
실수 나눗셈은 다릅니다 — 7.0/2.0은 3.5입니다. GW-BASIC의 /도 항상 실수 나눗셈이고, 정수 나눗셈은 별도 연산자 \입니다.

5.6 float32와 float64

이 책에서는 둘 다 필수입니다. GW-BASIC에 단정도(!)와 배정도(#)가 둘 다 있기 때문입니다.

var f32 float32 = 0.1
var f64 float64 = 0.1
fmt.Println(f32, f64, float64(f32))
fmt.Printf("%.10f %.20f\n", f32, f64)
0.1 0.1 0.10000000149011612 0.1000000015 0.10000000000000000555

같은 “0.1”인데 float32를 float64로 넓히면 오차가 드러납니다. 원래 있던 오차가 보이게 된 것일 뿐, 변환이 오차를 만든 것은 아닙니다.

float32유효 자릿수 약 7자리. GW-BASIC의 단정도(!)에 대응
float64유효 자릿수 약 15~17자리. 배정도(#)에 대응
var s float32 = 1.0 / 3.0
fmt.Println(s, float64(s))
0.33333334 0.3333333432674408
고증의 핵심 — GW-BASIC에서 PRINT 1/3은 .3333333을 찍습니다. 7자리입니다. Go에서 float32로 계산하고 fmt에게 맡기면 0.33333334가 나오는데, 그 책 17.3절의 PRINT 포맷 함수가 이 차이를 흡수합니다.

5.7 이 책의 Value — 타입 넷을 한 구조체에

Go에는 합 타입(“정수이거나 문자열”)이 없습니다. 그래서 그 책은 모든 경우의 필드를 다 가진 구조체 + 태그로 표현합니다.

internal/runtime/value.go

type ValueTag uint8

const (
	TagInt ValueTag = iota
	TagSng
	TagDbl
	TagStr
)

type Value struct {
	Tag ValueTag
	I   int16
	F32 float32
	F64 float64
	S   string
}

func IntVal(v int16) Value   { return Value{Tag: TagInt, I: v} }
func SngVal(v float32) Value { return Value{Tag: TagSng, F32: v} }
func DblVal(v float64) Value { return Value{Tag: TagDbl, F64: v} }
func StrVal(v string) Value  { return Value{Tag: TagStr, S: v} }

GW-BASIC의 네 타입이 그대로 대응합니다.

A% 정수TagInt → I int16 (−32768 ~ 32767)
A! 단정도TagSng → F32 float32
A# 배정도TagDbl → F64 float64
A$ 문자열TagStr → S string
낭비 아닌가? — 맞습니다. 정수 하나를 담아도 구조체 전체를 차지합니다. 64비트 환경에서 unsafe.Sizeof(Value{})는 32바이트입니다(태그 1 + 패딩 1 + int16 2 + float32 4 + float64 8 + string 16). Rust의 enum이나 C의 union이라면 훨씬 작습니다. 대신 필드 접근이 그냥 v.I라 빠르고, 태그를 잘못 읽어도 크래시가 아니라 제로값입니다. 10장에서 다른 선택지(인터페이스)와 비교합니다.

5.8 bool은 정수가 아니다

C에서 if (n)은 “n이 0이 아니면”이라는 뜻입니다. Go에서는 컴파일 에러입니다.

✘ 안 됨
n := 5
if n { ... }         // 에러
var x int = true     // 에러
b := (1 == 1) + 1    // 에러
✔ 명시
if n != 0 { ... }
if len(toks) > 0 { ... }
if err != nil { ... }

연산자는 &&, ||, ! 셋입니다. &&와 ||는 단축 평가합니다 — 왼쪽으로 결과가 정해지면 오른쪽을 아예 계산하지 않습니다.

// 이 관용구가 안전한 이유가 단축 평가입니다
if i < len(s) && s[i] == '"' { ... }
GW-BASIC은 반대입니다 — BASIC의 AND/OR는 비트 연산이고, 참은 −1, 거짓은 0입니다. 그래서 그 책 8.3절 “부울 동작”은 Go의 bool이 아니라 int16 비트 연산으로 구현합니다. 언어의 bool과 구현 대상의 “불린”이 다른, 흥미로운 대목입니다.

5.9 비트 연산자 — &^가 낯설 것입니다

fmt.Println(6&3, 6|3, 6^3, 6&^3, ^5)
fmt.Println(1<<10, 255>>4)
2 7 5 4 -6 1024 15
& |AND, OR — 다른 언어와 같음
^ (이항)XOR. C의 ^와 같음
^ (단항)NOT. C의 ~에 해당합니다. Go에 ~는 없습니다
&^AND NOT (비트 클리어). a &^ b는 a & (^b). Go 고유
<< >>시프트. 부호 있는 값의 >>는 산술 시프트(부호 유지)

6 &^ 3: 110 &^ 011 = 110 & 100 = 100 = 4. “3에 켜진 비트를 6에서 끈다”는 뜻이라 플래그 해제에 딱 맞습니다.

그 책에서는 — Instr.Mode uint8이 LINE/CIRCLE의 옵션 비트를 담습니다. 켤 때 mode |= flagB, 끌 때 mode &^= flagB, 확인할 때 mode&flagB != 0이 표준 삼종 세트입니다.

6.1 문자열은 불변 바이트 시퀀스다

Go의 string은 “문자의 배열”이 아니라 바이트의 배열입니다. 그리고 고칠 수 없습니다.

s := "PRINT"
fmt.Println(len(s), s[0], string(s[0]), s[1:3])
5 80 P RI
len(s)바이트 수. 문자 수가 아닙니다
s[0]byte(=uint8) 하나. 그래서 80('P'의 ASCII 코드)이 찍힙니다
string(s[0])바이트를 다시 문자열로 → "P"
s[1:3]부분 문자열. 복사가 아니라 같은 메모리를 가리킵니다
s[0] = 'p'          // ✘ cannot assign to s[0]

b := []byte(s)      // ✔ 바이트 슬라이스로 복사
b[0] = 'p'
fmt.Println(string(b), s)
pRINT PRINT
불변인 덕분에 — 부분 문자열이 공짜입니다. s[1:3]은 새 메모리를 잡지 않고 원본의 일부를 가리키는 {포인터, 길이} 쌍을 만들 뿐입니다. 그 책의 렉서가 소스 전체를 src string으로 들고 l.src[start:l.pos]로 토큰을 잘라내는 것이 값싼 이유입니다.

6.2 byte와 rune

byte = uint8

0~255. 바이트 하나. s[i]가 이것입니다.

var b byte = 'P'   // 80
rune = int32

유니코드 코드 포인트 하나. range가 주는 것.

var r rune = '가'  // 44032

한글은 UTF-8에서 3바이트를 차지합니다. 그래서 두 값이 갈라집니다.

k := "가나다"
fmt.Println(len(k), len([]rune(k)))
for i, r := range k {
	fmt.Printf("%d:%c(%d) ", i, r, r)
}
9 3 0:가(44032) 3:나(45208) 6:다(45796)
range의 인덱스에 주의 — 0, 1, 2가 아니라 0, 3, 6입니다. range는 바이트 위치와 그 자리의 룬을 줍니다. 룬의 순번이 아닙니다.

6.3 그래서 렉서는 바이트로 스캔한다

그 책 9.2절의 실제 코드입니다. 전부 byte를 다룹니다.

func (l *Lexer) peek(off int) byte {
	if l.pos+off >= len(l.src) {
		return 0
	}
	return l.src[l.pos+off]
}

func (l *Lexer) advance() byte {
	if l.pos >= len(l.src) {
		return 0
	}
	ch := l.src[l.pos]
	l.pos++
	if ch == '\n' {
		l.line++
		l.col = 1
	} else {
		l.col++
	}
	return ch
}

그 책이 이 선택을 정당화하는 문장이 9.2절 끝에 있습니다.

“Go의 바이트 인덱싱은 ASCII 범위 안에서 안전합니다. 식별자에 한글을 허용하지 않을 것이므로 byte 단위 스캐닝이 충분합니다. UTF-8 안전이 필요한 부분(문자열 리터럴)은 그대로 바이트로 보관해도 문제 없습니다.”
핵심 논리 — UTF-8은 자기 동기화됩니다. 멀티바이트 문자의 이어지는 바이트는 전부 0x80 이상이라, ASCII 문자(", ,, +)와 절대 겹치지 않습니다. 그래서 “구분자만 찾고 나머지는 그대로 복사”하는 렉서는 바이트 단위로 돌려도 한글 문자열 리터럴을 망가뜨리지 않습니다.
단, return 0에 주의 — 문자열 끝을 넘어가면 0을 돌려줍니다. Go에 “EOF 문자”가 없으므로 0을 센티널로 쓴 것입니다. 진짜 NUL 바이트가 소스에 들어 있으면 구별할 수 없지만, BASIC 소스에서는 문제가 되지 않습니다.

6.4 작은따옴표와 큰따옴표

'P'룬 리터럴. rune(=int32) 타입의 숫자입니다. 값은 80
"P"문자열 리터럴. 길이 1의 string
`P`raw 문자열. 이스케이프를 해석하지 않고 줄바꿈을 포함할 수 있습니다
if ch == '\n' { ... }        // byte/rune 비교 — 따옴표 하나
if s == "\n" { ... }         // string 비교 — 따옴표 둘

raw := `a\nb	c`
fmt.Println(raw, len(raw))
a\nb c 6

\n이 줄바꿈이 아니라 역슬래시와 n 두 글자로 남았습니다. 길이 6(a,\,n,b,탭,c)입니다.

비교가 되는 이유 — l.src[l.pos]는 byte인데 '\n'은 rune입니다. 그런데 '\n'은 타입 없는 룬 상수라 byte로 맞춰집니다(4.7절). 값 10이 byte 범위 안이므로 통과합니다. '가'(44032)와 비교했다면 컴파일 에러가 났을 것입니다.

대신 치르는 것 — 런타임에 핸들러를 갈아 끼울 수 없습니다. 디버거 훅이 필요하면 switch 바깥에 넣어야 합니다. 실제로 그 책 30.1절의 Debugger 훅은 step 함수 진입부에 있습니다.

8.1 배열 — 길이가 타입의 일부다

var arr [3]int          // 길이 3의 배열
fmt.Printf("%T\n", arr) // [3]int
[3]int과 [4]int는 다른 타입입니다. 서로 대입할 수 없고, [3]int를 받는 함수에 [4]int를 넘길 수 없습니다.

게다가 배열은 값입니다. 대입하면 통째로 복사됩니다.

arr2 := arr        // 전체 복사
arr2[0] = 9
fmt.Println(arr, arr2)
fmt.Println(arr == [3]int{0, 0, 0})
[0 0 0] [9 0 0] true

배열끼리는 ==로 비교할 수 있습니다(원소 타입이 비교 가능하면). 슬라이스는 못 합니다.

배열은 거의 안 씁니다 — 길이가 타입에 박혀 있어 유연성이 없기 때문입니다. 그 책에서 배열이 쓰인 곳은 딱 하나, Env의 defType [26]ValueTag입니다. 알파벳 26자라는 길이가 영원히 안 변하므로 배열이 정확한 선택입니다(DEFINT A-Z의 기본 타입 표).

8.2 슬라이스는 세 칸짜리 구조체다

이 한 장이 8장의 전부입니다. 슬라이스는 배열이 아니라, 어딘가의 배열을 가리키는 작은 헤더입니다.

b는 a의 1번 원소부터 시작해 길이 3이지만, 용량은 5입니다. 백킹 배열의 끝(인덱스 5)까지 남은 칸이 그만큼이기 때문입니다.

8.3 그래서 슬라이스는 서로를 덮어씁니다

a := []int{0, 1, 2, 3, 4, 5}

c := a[1:3]                 // len 2, cap 5
fmt.Println(c, len(c), cap(c))
c = append(c, 777)          // cap에 여유가 있다!
fmt.Println(a, c)

여기가 진짜 함정입니다 — c에 append했을 뿐인데 a[3]이 3에서 777로 바뀌었습니다. c의 cap에 여유가 있었으므로 새 배열을 만들지 않고 바로 다음 칸에 써 버린 것입니다.

8.4 append는 반환값을 반드시 받아야 한다

s = append(s, v)         // ✔ 항상 이 형태
append(s, v)             // ✘ 컴파일 에러 (값을 안 씀)

이유는 append가 두 가지 다른 일을 하기 때문입니다.

  1. len < cap이면 — 백킹 배열의 다음 칸에 쓰고, len만 1 늘린 새 헤더를 돌려줍니다. 원본 배열은 그대로.
  2. len == cap이면 — 더 큰 배열을 새로 할당하고, 전부 복사하고, 새 배열을 가리키는 헤더를 돌려줍니다. 이제 옛 슬라이스와 연결이 끊깁니다.
d := make([]int, 0, 2)
d = append(d, 1, 2)      // len 2, cap 2 — 꽉 참
e := append(d, 3)        // 새 배열로 이사
fmt.Println(len(d), cap(d), d, e)
e[0] = 100
fmt.Println(d, e)        // 이제 서로 남남
2 2 [1 2] [1 2 3] [1 2] [100 2 3]
이것이 핵심 위험입니다 — append 후에 두 슬라이스가 같은 배열을 공유할 수도, 안 할 수도 있습니다. 용량에 달려 있고, 용량은 눈에 잘 안 보입니다. 그래서 규칙은 하나 — append의 결과를 원래 변수에 다시 대입하고, 옛 슬라이스는 버린다.

8.5 용량은 어떻게 자라나

s := []int{}
prev := -1
for i := 0; i < 2000; i++ {
	s = append(s, i)
	if cap(s) != prev { fmt.Print(cap(s), " "); prev = cap(s) }
}
4 8 16 32 64 128 256 512 848 1280 1792 2560
작을 때대략 두 배씩 — 4, 8, 16, …, 512
클 때증가율이 완만해집니다 — 512 → 848 → 1280 → 1792 (약 1.4~1.7배)
첫 값이 1이 아닌 이유Go 할당기의 크기 클래스에 맞춰 올림합니다. int 하나(8바이트)를 요청해도 32바이트 블록을 받으므로 cap이 4가 됩니다
정확한 수치는 명세가 아닙니다 — Go 버전에 따라 달라졌고 앞으로도 달라질 수 있습니다. “대략 배로 늘어난다”까지만 믿고, 코드가 특정 cap 값에 의존하게 만들지 마세요.
미리 잡아 두기 — 개수를 알면 make([]T, 0, n)으로 시작하세요. 재할당과 복사가 사라집니다. 그 책 16.1절이 정확히 이렇게 합니다.

VM 스택이 256칸까지는 재할당 없이 굴러갑니다.

nil 슬라이스는 완전히 쓸 만합니다 — len, cap, range, append가 전부 정상 동작합니다. 그래서 그 책의 Lexer는 tokens 필드를 초기화하지 않고 그냥 l.tokens = append(l.tokens, ...)로 시작합니다. 제로값이 쓸모 있게 설계된 대표 사례입니다.
make([]int, 3)에 주의 — 이것은 “빈 슬라이스에 3칸 예약”이 아니라 0이 세 개 든 슬라이스입니다. 여기에 append하면 네 번째 원소가 됩니다. 예약이 목적이면 make([]int, 0, 3)입니다.

8.7 슬라이스로 스택 만들기 — VM의 심장

그 책 16.2절의 실제 코드입니다. 세 함수가 전부입니다.

func (m *VM) push(v runtime.Value) { m.stack = append(m.stack, v) }

func (m *VM) pop() runtime.Value {
	n := len(m.stack) - 1
	v := m.stack[n]
	m.stack = m.stack[:n]
	return v
}

func (m *VM) peek(off int) runtime.Value {
	return m.stack[len(m.stack)-1-off]
}
  1. push — append가 알아서 늘려 줍니다.
  2. pop — m.stack[:n]으로 길이만 줄입니다. 백킹 배열은 그대로 남아 있으므로, 다음 push가 그 칸을 재할당 없이 재사용합니다.
  3. peek — off=0이 꼭대기. 인덱싱뿐이라 공짜입니다.
st := []int{}
st = append(st, 10, 20, 30)
top := st[len(st)-1]
st = st[:len(st)-1]
fmt.Println(top, st, len(st), cap(st))
30 [10 20] 2 3
cap이 3으로 남은 것을 보세요 — 30이 들어 있던 칸이 아직 살아 있습니다. 이것이 “pop 후 push가 공짜”인 이유이고, 명령을 수백만 번 실행하는 VM에서 결정적입니다.
대가 — 팝된 값이 GC되지 않습니다. Value가 문자열을 들고 있으면 그 문자열도 계속 살아 있습니다. 큰 객체를 담는 스택이라면 m.stack[n] = zeroValue로 지워 줘야 하지만, 이 VM은 스택이 얕아 신경 쓰지 않습니다.

8.8 copy — 진짜로 복사해야 할 때

src := []int{1, 2, 3}
dst := make([]int, 2)

반환값실제로 복사한 개수 = min(len(dst), len(src))

흔한 관용구dst := make([]T, len(src)); copy(dst, src) — 독립된 복사본
append로도 복사할 수 있습니다 — dst := append([]int(nil), src...)가 같은 일을 합니다. 짧지만 copy보다 의도가 덜 분명해서 취향이 갈립니다.
언제 필요한가 — 그 책 18.3절의 Snapshot이 좋은 예입니다. DEF FN의 매개변수 섀도잉을 위해 현재 변수 상태를 저장했다가 복원해야 하는데, 슬라이스를 그냥 대입하면 같은 배열을 가리켜 스냅숏 의미가 사라집니다.

	return e.zeroFor(name)     // 없으면 타입별 제로값을 계산
}
두 번째 예가 왜 중요한가 — GW-BASIC에서는 선언 안 한 변수도 쓸 수 있고, 접미사에 따라 다른 제로값을 가집니다(A%는 0, A$는 ""). 맵의 제로값(Value{})은 그것과 다르므로, “없음”을 정확히 잡아내 직접 계산해야 합니다. comma-ok가 없었다면 불가능했을 것입니다.
그냥 m[k]만 쓸 때도 있습니다 — 카운터가 대표적입니다. cnt["x"]++는 키가 없어도 0에서 시작해 1이 됩니다. 이럴 땐 제로값이 정확히 원하는 동작입니다.

9.3 집합은 map[T]struct{}

Go에는 집합(set) 타입이 없습니다. 관용구는 값이 struct{}인 맵입니다.

set := map[string]struct{}{}
set["PRINT"] = struct{}{}
_, isKW := set["PRINT"]
struct{}는 크기가 0인 타입입니다 — 필드가 없으므로 메모리를 전혀 차지하지 않습니다. map[string]bool이면 값마다 1바이트가 붙지만, struct{}면 키만 저장됩니다. 그리고 “true/false” 대신 “있음/없음”이라는 의도가 분명해집니다.

그 책 9.1절의 키워드 집합입니다(전부 93개). Go 관용구가 잘 드러납니다.

var keywordSet = func() map[string]struct{} {
	list := []string{
		"AND","AS","ATN","BEEP","CHR$","CIRCLE","CINT","CLEAR","CLS","COLOR",
		"COS","CSNG","CDBL","DATA","DEF","DEFINT","DEFSNG","DEFDBL","DEFSTR",
		// ... 전부 93개 ...
		"TIMER","TO","USING","VAL","WEND","WHILE","XOR",
	}
	m := make(map[string]struct{}, len(list))
	for _, w := range list {
		m[w] = struct{}{}
	}
	return m
}()
맨 끝의 ()에 주목 — 함수를 정의하고 즉시 호출해서 그 결과를 변수에 담는 관용구입니다(즉시 실행 함수). 패키지 수준 변수는 표현식으로만 초기화할 수 있는데, 여기서는 루프가 필요하므로 이렇게 감쌉니다. func init()을 쓰는 방법도 있지만, 이쪽이 “이 변수만을 위한 코드”라는 것이 분명합니다. 13장에서 다시 봅니다.

9.4 순회 순서는 일부러 무작위다

big := map[int]int{}
for i := 0; i < 5; i++ { big[i] = i }
for round := 0; round < 3; round++ {
	for k := range big { fmt.Print(k) }
	fmt.Print(" ")
}
01234 40123 01234

같은 맵을 세 번 도는데 순서가 다릅니다. Go 런타임이 매 순회의 시작점을 무작위로 잡습니다.

왜 이렇게 만들었나 — 순서에 의존하는 코드가 “우연히 잘 돌다가” 나중에 깨지는 것을 막기 위해서입니다. 해시 맵의 순서는 원래 보장되지 않는데, 구현이 우연히 안정적이면 사람들이 그것에 의존합니다. Go는 일부러 흔들어 그 습관을 원천 차단합니다.
따라오는 규칙 — 순서가 필요하면 키를 뽑아 정렬해야 합니다. 
keys := make([]int, 0, len(m))
for k := range m { keys = append(keys, k) }
sort.Ints(keys)
for _, k := range keys { ... }
그 책에서 실제로 필요합니다 — LineMap map[int]int은 BASIC 라인 번호 → 코드 인덱스입니다. LIST 명령은 프로그램을 줄 번호 순서대로 출력해야 하므로, 맵을 그냥 돌면 안 되고 키를 정렬해야 합니다. 디스어셈블러(15.7절)도 마찬가지입니다.

9.5 맵은 참조처럼 동작한다

func mod(m map[string]int) { m["a"] = 99 }

mm := map[string]int{"a": 1}
mod(mm)
fmt.Println(mm)
map[a:99]

슬라이스와 마찬가지로, 맵 값은 내부적으로 해시 테이블을 가리키는 포인터입니다. 그래서 함수에 넘겨도 같은 테이블을 봅니다.

차이도 있습니다 — 슬라이스는 append가 재할당하면 연결이 끊기지만, 맵은 커져도 연결이 유지됩니다. 맵 헤더가 포인터 하나이고, 내부 재할당은 그 포인터 뒤에서 일어나기 때문입니다. 그래서 맵에는 “m = mapAppend(m, k, v)” 같은 것이 없습니다.
맵의 값은 주소를 얻을 수 없습니다 — 구조체를 값으로 담으면 필드를 직접 못 고칩니다. 
type S struct{ N int }
ms := map[string]S{"k": {1}}
ms["k"].N = 2        // ✘ cannot assign

t := ms["k"]         // ✔ 꺼내서
t.N = 2              //   고치고
ms["k"] = t          //   다시 넣는다
이유는 맵이 커질 때 원소가 메모리 안에서 이사하기 때문입니다. 주소를 줬다가는 무효 포인터가 됩니다.
mp := map[string]*S{"k": {1}}   // 값을 포인터로 하면
mp["k"].N = 5                    // ✔ 바로 고칠 수 있다
그래서 Env가 이렇게 생겼습니다 — scalars map[string]Value(값)와 arrays map[string]*Array(포인터). 스칼라는 작고 통째로 교체하지만, 배열은 크고 원소를 제자리에서 고쳐야 하므로 포인터입니다.

9.6 키가 될 수 있는 타입

키는 ==로 비교 가능해야 합니다.

✔ 가능

모든 숫자 · string · bool · 포인터 · 채널 · 비교 가능한 필드만 가진 구조체 · 배열

✘ 불가능

슬라이스 · 맵 · 함수 · 그리고 이들을 필드로 가진 구조체

그 책 15.1절의 Compiler에 흥미로운 줄이 있습니다.

runtime.Value가 맵의 키로 쓰였습니다. 가능한 이유는 Value의 필드가 ValueTag, int16, float32, float64, string — 전부 비교 가능하기 때문입니다.

이것이 상수 풀의 핵심 장치입니다 — 같은 값(예: 숫자 1)이 프로그램에 백 번 나와도 Consts 슬라이스에는 한 번만 들어갑니다. constsIndex[v]로 이미 있는지 확인하고, 있으면 그 인덱스를 재사용하니까요. 만약 Value에 슬라이스 필드가 하나라도 있었다면 이 설계가 불가능했을 것입니다.
실수 키의 함정 — NaN != NaN이므로 NaN을 키로 넣으면 다시 못 찾습니다. 넣을 때마다 새 항목이 생깁니다. BASIC 소스에 NaN 리터럴은 없으므로 이 책에서는 문제되지 않습니다.

10장

구조체

Go에 클래스는 없습니다. 데이터는 struct, 동작은 메서드, 추상화는 인터페이스로 나뉩니다.

10.1 정의와 생성

type SourcePos struct {
	Line int
	Col  int
}

type BasicError struct {
	Code      int
	Msg       string
	Pos       SourcePos      // 구조체를 필드로 — 중첩
	BasicLine int
}

만드는 방법은 셋입니다.

a := BasicError{Code: 2, Msg: "Syntax error"}          // ① 필드 이름 지정
b := BasicError{2, "Syntax error", SourcePos{1,5}, 0}  // ② 순서대로 전부
var c BasicError                                        // ③ 제로값
{2 Syntax error {0 0} 0} {Code:2 Msg:Syntax error Pos:{Line:1 Col:5} BasicLine:0} {0 {0 0} 0}
①을 쓰세요 — ②는 필드 순서가 바뀌거나 필드가 추가되면 조용히 깨집니다. ①은 안 적은 필드가 제로값이 되므로, 필드가 늘어도 기존 코드가 그대로 돕니다. 그 책의 모든 구조체 리터럴이 ① 형태입니다.
%v와 %+v — 디버깅할 때 %+v가 훨씬 낫습니다. 필드 이름이 붙어 어느 값이 어디 것인지 보입니다.

10.2 구조체는 값이다

슬라이스·맵과 결정적으로 다릅니다. 대입하면 전부 복사됩니다.

d := a
d.Code = 99
fmt.Println(a.Code, d.Code)
2 99

함수에 넘길 때도 같습니다. 안에서 고쳐도 호출자에게 안 보입니다.

값 복사구조체 · 배열 · 숫자 · 문자열 · bool
공유슬라이스 · 맵 · 채널 · 포인터 · 함수 (내부에 포인터가 있음)
혼합 주의 — 슬라이스 필드를 가진 구조체를 복사하면 구조체는 복사, 슬라이스가 가리키는 배열은 공유됩니다. 얕은 복사입니다. 
type Chunk struct{ Code []Instr }
c2 := c1              // 헤더만 복사
c2.Code[0] = ...      // c1.Code[0]도 바뀐다!

비교도 됩니다. 모든 필드가 비교 가능하면 ==가 필드별 비교를 합니다.

fmt.Println(a == BasicError{Code: 2, Msg: "Syntax error"})   // true
이 성질을 9.6절에서 썼습니다 — runtime.Value가 맵의 키가 될 수 있었던 것이 바로 이 덕분입니다. 필드에 슬라이스가 하나라도 있으면 ==가 컴파일 에러가 되고, 맵 키로도 못 씁니다.

10.3 &T{} — 포인터로 만들기

p := &BasicError{Code: 5}
fmt.Println(p.Code, (*p).Code)   // 둘 다 5
p.Code = 6
fmt.Println(p)
5 5 &{6 {0 0} 0}
Go는 포인터를 자동으로 따라갑니다 — p가 포인터여도 p.Code로 그냥 씁니다. C의 p->Code에 해당하는 문법이 아예 없습니다. (*p).Code라고 써도 되지만 아무도 안 씁니다.

그 책은 이 형태를 곳곳에서 씁니다.

// 4.2절

// 16.1절

언제 포인터로 만드나 — ① 구조체가 크고 여기저기 넘겨야 할 때, ② 상태를 고쳐야 할 때(Lexer가 pos를 전진시킴), ③ 하나뿐인 것을 표현할 때(VM 인스턴스). 그 책의 모든 “~를 하는 물건”은 포인터입니다.

10.4 임베딩 — 상속이 아니라 포함

필드 이름 없이 타입만 적으면 임베딩입니다. 그 타입의 필드와 메서드가 바깥으로 올라옵니다.

type Base struct{ ID int }

func (b Base) Describe() string { return fmt.Sprintf("Base(%d)", b.ID) }

type Derived struct {
	Base           // ← 필드 이름 없음
	Name string
}

x := Derived{Base: Base{ID: 7}, Name: "n"}
fmt.Println(x.ID, x.Describe(), x.Base.ID)
7 Base(7) 7
x.ID승격되어 바로 접근됩니다
x.Describe()메서드도 승격됩니다
x.Base.ID본래 경로도 그대로 씁니다. 이름이 충돌하면 이쪽으로 구별
상속과 다릅니다 — Derived는 Base가 아닙니다. Base를 받는 함수에 Derived를 넘길 수 없습니다. 오버라이드도 없습니다 — 같은 이름의 메서드를 Derived에 정의하면 가리는(shadow) 것일 뿐, Base의 메서드가 Derived의 것을 부르지 않습니다. “다형성”은 오직 인터페이스로만 얻습니다(16장).
그 책에서는 거의 안 씁니다 — 임베딩은 표준 라이브러리(bufio.ReadWriter)나 sync.Mutex를 구조체에 붙일 때 흔하지만, 이 인터프리터는 상속 구조가 필요 없습니다. 알아 두되 찾아 헤매지 마세요.

10.5 익명 구조체 — 테이블 테스트의 재료

타입 이름 없이 그 자리에서 구조체를 만들 수 있습니다. 딱 한 군데서만 쓸 형태에 유용합니다.

cases := []struct {
	i    int
	want float64
}{{0, 26}, {1, 15}, {2, 7}}

for _, c := range cases {
	if toks[c.i].Num != c.want {
		t.Errorf("toks[%d].Num = %v, want %v", c.i, toks[c.i].Num, c.want)
	}
}

그 책 9.9절 TestRadixNumbers의 실제 코드입니다. &H1A=26, &O17=15, &7=7이라는 세 케이스를 데이터로 적고 루프 하나로 검사합니다.

테이블 주도 테스트는 Go의 표준 관용구입니다. 케이스를 추가하는 데 한 줄이면 되고, 어느 케이스가 실패했는지 인덱스로 알 수 있습니다. 23장에서 본격적으로 다룹니다.
{{0, 26}, ...}의 이중 중괄호 — 바깥은 슬라이스 리터럴, 안쪽은 구조체 리터럴입니다. 원소 타입이 뻔하므로 struct{...}{0, 26}이라고 반복해 적지 않아도 됩니다. Go가 허용하는 몇 안 되는 생략 중 하나입니다.

10.6 이 책의 구조체 지도 (1) — 프론트엔드

}
설계를 읽어 보세요 — Num과 NumKind는 Kind == TNumber일 때만 의미가 있습니다. 다른 토큰에서는 제로값으로 놀고 있습니다. TypeScript라면 판별 유니온으로 “숫자일 때만 이 필드가 있다”고 표현할 수 있지만, Go에는 합 타입이 없으니 모든 필드를 다 두고 주석으로 조건을 적는 방식이 됩니다. 5.7절의 Value와 같은 타협입니다.
// 어휘 분석기 자신 (9.2절)
type Lexer struct {
	src    string
	pos    int
	line   int
	col    int
	tokens []Token
}

Lexer는 데이터가 아니라 기계입니다. pos가 전진하고 tokens가 쌓입니다. 그래서 항상 *Lexer 포인터로 다룹니다.

대비되는 두 종류 — Token은 값(작고, 복사해도 되고, 슬라이스에 담김). Lexer는 기계(상태를 가지고, 포인터로만 다룸). 구조체 하나를 볼 때 “이건 어느 쪽인가”를 먼저 판단하면 코드가 훨씬 잘 읽힙니다.

10.7 이 책의 구조체 지도 (2) — 백엔드

// 명령 하나 (14.4절)
type Instr struct {
	Op   Op
	A    int32 // 첫 번째 인자
	B    int32 // 두 번째 인자
	Mode uint8 // 비트 플래그
}

// 컴파일된 프로그램 전체
type Chunk struct {
	Code        []Instr
	Consts      []runtime.Value // PUSH의 즉치값 풀
	Names       []string        // LOAD/STORE/CALL 변수·함수명 풀
	LineMap     map[int]int     // BASIC 라인 번호 → code 인덱스
	DataPool    []runtime.Value
	DataLineMap map[int]int
	DefFns      map[string]*FnEntry
	InputDescs  []InputDesc
	SwapDescs   []SwapDesc
	LineModes   []LineMode
}
Instr가 작아야 하는 이유 — Op(1) + A(4) + B(4) + Mode(1)에 정렬 패딩이 붙어 16바이트입니다. 프로그램이 수천 명령이어도 수십 KB에 불과하고, 연속 메모리라 CPU 캐시에 잘 들어갑니다. 만약 Instr가 문자열이나 슬라이스를 직접 들고 있었다면 이 성질이 사라집니다.

그래서 풀(pool) 설계가 등장합니다. 그 책 14.4절의 설명입니다.

“변수명을 Names []string 풀에 한 번만 저장하고, 명령은 인덱스만 들고 있게 하면 캐시 친화적입니다. runtime.Value도 마찬가지로 Consts 풀에 모읍니다.”

즉 PRINT A$의 LOAD 명령은 문자열 "A$"가 아니라 A: 3(Names의 3번)만 들고 있습니다.

A.

② 간접 참조가 생깁니다 — 문자열 내용은 다른 곳에 있으므로, 명령을 읽을 때마다 메모리를 한 번 더 따라가야 합니다.
③ GC 부담 — 명령 배열이 포인터를 품게 되어 가비지 컬렉터가 매번 스캔해야 합니다. int32만 있으면 GC가 통째로 건너뜁니다.
④ 중복 저장 — 같은 변수명이 백 번 나오면 문자열도 백 번 (또는 최소한 헤더가 백 번) 저장됩니다.
이 네 가지가 풀 + 인덱스 설계를 택한 이유 전부입니다.

11.1 &와 *, 그리고 끝

x := 42
p := &x          // p는 *int — x의 주소
fmt.Println(*p)  // 42 — 역참조
*p = 43          // x를 통해서가 아니라 p를 통해 수정
fmt.Println(x)   // 43
&xx의 주소를 얻습니다. 타입은 *T
*p포인터가 가리키는 값. 읽기·쓰기 모두 가능
*int타입 표기에서의 *. “int를 가리키는 포인터”
nil포인터의 제로값. 역참조하면 패닉
Go에 없는 것들 — 포인터 산술(p+1, p++)이 없습니다. 배열과 포인터의 혼동이 없습니다. 이중 포인터 관용구가 거의 없습니다. free()가 없습니다(GC). 남은 것은 “값을 공유하고 싶다”는 딱 하나의 용도입니다.
q := new(int)    // 제로값을 하나 만들고 그 주소를 준다
*q = 7
new는 거의 안 씁니다 — new(T)는 &T{}와 사실상 같고, 구조체에는 후자가 필드를 채울 수 있어 훨씬 낫습니다. 그 책에 new(는 0회 등장합니다.

11.2 지역 변수의 주소를 반환해도 된다

C였다면 최악의 버그입니다. Go에서는 완전히 안전합니다.

func makeCounter() *int {
	n := 5
	return &n     // C에서는 댕글링 포인터. Go에서는 정상.
}
탈출 분석(escape analysis) — Go 컴파일러는 “이 변수의 주소가 함수 밖으로 나가는가”를 분석합니다. 나간다면 스택이 아니라 힙에 할당하고, GC가 관리합니다. 여러분은 스택인지 힙인지 신경 쓸 필요도, 알 방법도 없습니다(go build -gcflags=-m으로 볼 수는 있습니다).

그래서 Go에서는 이런 코드가 관용적입니다.

func Tokenize(src string) ([]Token, error) {
	l := &Lexer{src: src, line: 1, col: 1}   // 지역에서 만들고
	return l.run()                            // 포인터를 넘긴다
}

func NewEnv() *Env {
	e := &Env{ scalars: map[string]Value{}, ... }
	return e                                  // 지역 변수의 주소를 반환
}
성능은? — 힙 할당은 스택보다 비싸고 GC 부담도 생깁니다. 하지만 컴파일러가 “안 나가는” 것은 스택에 두므로, 대부분의 작은 값은 공짜입니다. 최적화가 필요해진 뒤에 프로파일링으로 확인하는 것이 순서입니다.

11.3 값이냐 포인터냐 — 판단 기준

포인터를 쓸 때
  • 수정해야 한다 — 호출자에게 변경이 보여야 함
  • 크다 — 복사 비용이 아까움 (수십 바이트 이상)
  • 하나뿐이다 — VM, Lexer, Env처럼 “그 물건”
  • “없음”이 필요하다 — nil로 표현
  • 복사하면 안 된다 — strings.Builder, 뮤텍스
값을 쓸 때
  • 작다 — Instr(16바이트), Value(32바이트), Token(56바이트)
  • 불변으로 다룬다 — 만들고 안 고침
  • 슬라이스에 담는다 — []Token이 []*Token보다 캐시에 유리
  • 맵 키로 쓴다 — Value

그 책의 선택을 표로 보면 규칙이 선명합니다.

Token값 — []Token으로 담고 복사해 씁니다
Instr값 — []Instr. VM이 ins := m.ch.Code[m.pc]로 복사해 갑니다
runtime.Value값 — 스택에 쌓고 맵 키로도 씀
*Lexer, *Parser, *Compiler, *VM포인터 — 상태를 가진 기계
*Env, *Chunk포인터 — 크고, 공유해야 함
*Array포인터 — 맵의 값으로 넣고 제자리에서 원소를 고쳐야 함 (9.5절)
*BasicError포인터 — error 인터페이스 관용구 (19장)

11.4 미리 보기 — 리시버에서 갈리는 것

14장에서 본격적으로 다루지만, 포인터를 이해했으니 여기서 한 번 봅니다.

type Counter struct{ N int }

func (c Counter) IncVal()  { c.N++ }    // 값 리시버 — 복사본을 증가
func (c *Counter) IncPtr() { c.N++ }    // 포인터 리시버 — 원본을 증가

c := Counter{}
c.IncVal(); fmt.Println(c.N)   // 0  ← 아무 일도 안 일어남
c.IncPtr(); fmt.Println(c.N)   // 1
0 1
조용한 버그입니다 — IncVal은 컴파일도 되고 실행도 되지만 아무 효과가 없습니다. Go 초보가 가장 많이 밟는 지뢰이고, go vet도 잡아 주지 않습니다.
규칙 — 그 책의 모든 “상태를 바꾸는” 메서드가 func (m *VM), func (l *Lexer), func (e *Env)처럼 포인터 리시버입니다. 실제로 그 책의 Go 코드에서 func (x *T) 형태는 174회 등장합니다.
c.IncPtr()이 되는 이유 — c는 Counter인데 메서드는 *Counter를 요구합니다. Go가 자동으로 (&c).IncPtr()로 바꿔 줍니다. 주소를 얻을 수 있는 값(변수·필드·배열 원소)에만 통합니다 — 맵의 값에는 안 통합니다(9.5절에서 본 이유와 같습니다).

11.5 nil의 여러 얼굴

Go에서 nil은 하나의 값이 아니라 여러 타입의 제로값을 부르는 이름입니다. 그리고 타입마다 동작이 다릅니다.

포인터역참조·필드 접근 → 패닉
슬라이스len/cap/range/append 전부 정상. 인덱싱만 패닉
맵읽기는 정상(제로값), 쓰기는 패닉
함수호출하면 패닉
채널송수신하면 영원히 블록. 패닉이 아님
인터페이스메서드 호출 → 패닉. 그리고 함정이 하나 더 있습니다 (19장)
가장 악명 높은 함정 — nil 포인터를 담은 인터페이스는 nil이 아닙니다. 
var p *BasicError = nil
var err error = p
fmt.Println(err == nil)     // false !!
인터페이스 값은 (타입, 값) 쌍이고, 여기서는 타입이 *BasicError로 채워져 있습니다. 값만 nil일 뿐입니다. 19장에서 이 함정이 실제로 어떻게 무는지 봅니다.
그래서 관용구가 정해져 있습니다 — 에러를 반환할 때는 *BasicError 변수를 만들어 두었다가 반환하지 말고, 성공 경로에서 return nil을 직접 쓰세요.

함수

Go 함수의 진짜 특징은 값을 여러 개 돌려준다는 것 하나입니다.

12.1 기본 형태

func Tokenize이름(src string매개변수) ([]Token, error반환값) {

타입이 이름 뒤에 옵니다. C 계열과 반대라 처음에는 어색합니다.

func add(a int, b int) int { return a + b }
func add2(a, b int) int    { return a + b }      // 타입이 같으면 묶기
func noop()                {}                     // 반환값 없음
오버로딩없습니다. 같은 이름의 함수를 두 개 만들 수 없습니다
기본 인자없습니다. 필요하면 별도 함수를 만들거나 구조체를 받습니다
이름 있는 인자없습니다. 옵션이 많으면 구조체를 넘깁니다
인자 전달전부 값 복사. 슬라이스·맵·포인터는 “가리키는 것”이 공유될 뿐
왜 타입이 뒤인가 — C의 선언 문법(int (*fp)(char*, int) 같은 것)은 왼쪽·오른쪽을 오가며 읽어야 합니다. Go는 항상 왼쪽에서 오른쪽으로 읽힙니다. Rob Pike의 “Go's Declaration Syntax” 글이 이 결정을 설명합니다.

12.2 다중 반환값 — Go를 규정하는 한 가지

12.3 명명 반환값 — 쓸 수 있지만 조심

func parse(s string) (n int, err error) {
	if s == "" {
		err = errors.New("empty")
		return              // ← naked return: n=0, err=empty
	}
	n = len(s)
	return                  // ← n=3, err=nil
}

반환값에 이름을 주면 함수 시작 시 제로값으로 선언되고, return만 써도 그 값들이 나갑니다.

✔ 쓸 만한 자리

반환값의 의미를 문서화할 때 — (n int, err error)보다 (bytesRead int, err error)가 낫습니다.

defer에서 반환값을 고쳐야 할 때(15장). 이때는 이름이 필수입니다.

✘ 피할 자리

naked return을 긴 함수에서 쓰면 “무엇이 반환되는지” 보려고 위로 스크롤해야 합니다. 값을 명시하는 편이 낫습니다.

return n, err   // 이렇게
그 책의 선택 — 명명 반환값을 쓰지 않습니다. 모든 함수가 return v, nil처럼 값을 명시합니다. 표준 라이브러리도 대체로 그렇습니다.

12.6 즉시 실행 함수

함수를 정의하고 그 자리에서 호출합니다. 맨 끝의 ()가 표식입니다.

var keywordSet = func() map[string]struct{} {
	list := []string{"AND", "AS", "ATN", /* ... */}
	m := make(map[string]struct{}, len(list))
	for _, w := range list {
		m[w] = struct{}{}
	}
	return m
}()          // ← 여기
왜 필요한가 — 패키지 수준 변수는 표현식으로만 초기화할 수 있습니다. for 루프를 쓸 수 없습니다. 함수로 감싸면 그 안에서는 무엇이든 할 수 있고, 호출 결과는 표현식입니다.
대안 — func init()
var keywordSet map[string]struct{}

func init() {
	keywordSet = make(map[string]struct{})
	for _, w := range list { ... }
}

패키지 로드 시 자동 호출됩니다.

즉시 실행이 나은 이유

초기화 코드가 변수 바로 옆에 있습니다. init()은 파일 어디에나 있을 수 있고, 여러 개 있을 수도 있어 추적이 어렵습니다.

그 책에 func init()은 0회입니다.

다른 용도 — defer func(){ ... }()도 같은 문법입니다(15장). 그쪽이 훨씬 자주 보입니다.

14.1 리시버 — 함수 이름 앞의 괄호

메서드는 리시버가 붙은 함수일 뿐입니다. 클래스 안에 들어 있는 것이 아니라, 파일 어디에나 놓을 수 있습니다.

type Lexer struct {
	src string
	pos int
}

func (l *Lexer) peek(off int) byte {
	if l.pos+off >= len(l.src) { return 0 }
	return l.src[l.pos+off]
}

func (l *Lexer) advance() byte {
	ch := l.src[l.pos]
	l.pos++
	return ch
}
리시버 이름관용은 타입 첫 글자 한두 자 — l *Lexer, m *VM, e *Env, c *Compiler. this/self는 쓰지 않습니다
정의 위치같은 패키지 안이면 어느 파일이든 가능
붙일 수 있는 타입그 패키지에서 정의한 타입만. int나 string에는 직접 못 붙입니다

14.2 값 리시버냐 포인터 리시버냐

값 리시버
func (c Counter) Inc() { c.N++ }

→ 복사본을 받는다
→ 수정이 사라진다
→ 큰 구조체면 복사 비용
vs
포인터 리시버

→ 원본의 주소
→ 수정이 남는다
→ 복사 없음
실무 규칙 — 하나의 타입에는 한 종류로 통일하세요. 어느 하나라도 포인터 리시버가 필요하면 전부 포인터 리시버로 맞춥니다. 섞으면 메서드 집합이 갈라져 인터페이스 만족 여부가 헷갈립니다(14.4절).

그 책의 실제 분포입니다.

포인터 리시버*Lexer, *Parser, *Compiler, *VM, *Env, *BasicError, *TermHost, *CLIDebugger — 174곳
값 리시버TokenKind.String(), Op.String(), NullHost의 메서드들 — 상태가 없거나 읽기만 하는 것들
NullHost가 값 리시버인 이유 — type NullHost struct{}는 필드가 없습니다. 크기 0이라 복사가 공짜이고, 고칠 상태도 없습니다. 그 책 19.2절에 func (NullHost) Print(string) {}처럼 리시버 이름조차 생략한 형태로 나옵니다 — 안 쓰니까요.

값 → 포인터 메서드자동으로 &. 단 주소를 얻을 수 있어야 합니다
포인터 → 값 메서드자동으로 *. 항상 됩니다

var _ interface{ parsePrint() string } = &Parser{}   // ✔
var _ interface{ parsePrint() string } = Parser{}    // ✘ 컴파일 에러
Parser does not implement interface{ parsePrint() string } (method parsePrint has pointer receiver)
왜 비대칭인가 — *T에서 값(*p)을 얻는 것은 항상 가능하지만, T 값에서 주소를 얻는 것은 항상 가능하지 않기 때문입니다(맵의 값, 함수 반환값…). 인터페이스에 담긴 값은 주소를 얻을 수 없는 복사본이라, 포인터 리시버 메서드를 부를 방법이 없습니다.
실전에서 나는 에러 — “분명히 메서드를 다 만들었는데 인터페이스를 만족하지 않는다”는 에러의 90%가 이것입니다. 해법은 & 하나입니다. 
var h host.Host = TermHost{}     // ✘
var h host.Host = &TermHost{}    // ✔

14.5 메서드 값과 메서드 표현식

메서드를 함수 값으로 꺼낼 수 있습니다. 두 가지 형태가 있고, 그 책은 둘 다 씁니다.

메서드 값 — 리시버가 묶임
p := &Parser{n: 7}
g := p.parsePrint      // p가 붙잡힘
fmt.Println(g())       // print@7
fmt.Printf("%T\n", g)
func() string
메서드 표현식 — 리시버가 첫 인자
f := (*Parser).parsePrint
fmt.Println(f(p))      // print@7
fmt.Printf("%T\n", f)
func(*main.Parser) string
그 책 12.1절이 오른쪽을 씁니다 — 파서 디스패치 테이블의 값 타입이 func(p *Parser) (ast.Stmt, error)이므로, 아직 리시버가 정해지지 않은 형태여야 합니다. 그래야 표를 패키지 수준 변수 하나로 만들어 모든 Parser 인스턴스가 공유할 수 있습니다.
var stmtTable = map[string]stmtParser{
	"PRINT": (*Parser).parsePrint,      // 리시버 없이 등록
	...
}

// 부를 때 리시버를 넘긴다
if fn, ok := stmtTable[t.Lex]; ok {
	return fn(p)
}
메서드 값을 썼다면 — 표를 Parser마다 새로 만들어야 합니다. 파싱할 때마다 맵 40개짜리를 짓는 셈이니 낭비입니다.

14.6 String()이 특별한 이유

Go에는 “toString을 오버라이드한다”는 개념이 없습니다. 대신 fmt가 인터페이스를 확인합니다.

// fmt 패키지에 이렇게 정의되어 있다
type Stringer interface {
	String() string
}

fmt는 값을 찍기 전에 “이거 Stringer인가?”를 묻고, 맞으면 String()을 부릅니다. 등록도 상속도 필요 없습니다.

type TokenKind uint8
func (k TokenKind) String() string { return "TK" }

var k TokenKind
fmt.Println(k)
fmt.Printf("%v %d %s\n", k, k, k)
TK TK 0 TK
%v %s PrintlnString()을 부릅니다
%d숫자 서식이므로 무시하고 원래 값
값 리시버로TokenKind 값에도, *TokenKind에도 통합니다(14.4절)
무한 재귀 함정 — String() 안에서 fmt.Sprintf("%v", k)를 쓰면 자기 자신을 다시 부릅니다. 스택 오버플로로 죽습니다. 안에서는 기본 타입으로 변환해 쓰세요 — fmt.Sprintf("%d", uint8(k)).
같은 원리의 다른 인터페이스들 — error(Error() string), sort.Interface, io.Writer. 전부 “메서드만 맞으면 자동으로 참여”하는 구조입니다. 16장의 주제입니다.

15.1 defer — 함수가 끝날 때 실행

func process(path string) error {
	f, err := os.Open(path)
	if err != nil {
		return err
	}
	defer f.Close()          // 함수가 어떻게 끝나든 반드시 실행

	// ... 중간에 return이 다섯 개 있어도 ...
	return nil
}
실행 시점함수가 반환할 때. 블록이 아니라 함수 단위입니다
순서LIFO — 나중에 등록한 것이 먼저 실행됩니다
인자 평가defer를 만나는 순간 평가됩니다. 실행은 나중이지만

루프 안의 defer를 조심하세요 — 파일 1000개를 여는 루프에서 defer f.Close()를 쓰면, 함수가 끝날 때까지 1000개가 다 열려 있습니다. 루프 본문을 별도 함수로 빼거나 명시적으로 닫아야 합니다.

15.2 defer가 반환값을 고칠 수 있다

명명 반환값일 때만 가능합니다(12.3절이 여기로 이어집니다).

func safeRun() (err error) {          // ← 이름이 있어야 한다
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered: %v", r)   // 반환값을 갈아치움
		}
	}()
	panic("boom")
}
순서를 정확히 — ① return v가 명명 반환 변수에 v를 대입 → ② defer들이 LIFO로 실행(이때 변수를 고칠 수 있음) → ③ 최종 값이 호출자에게 감. 이름 없는 반환값이면 ①에서 이미 복사가 끝나 ②가 손댈 대상이 없습니다.
그 책 27.3절이 이 패턴을 씁니다 — 그래픽 호스트가 잘못된 좌표로 패닉할 수 있는데, 그 때문에 인터프리터 전체가 죽으면 안 됩니다. recover로 잡아 ?Illegal function call 에러로 바꿔서 돌려줍니다.

15.3 panic은 예외가 아니다

panic은 “여기서 계속 갈 수 없다”는 선언입니다. 스택을 거슬러 올라가며 defer를 전부 실행하고, 아무도 recover하지 않으면 프로그램이 죽습니다.

✘ 이런 데 쓰면 안 됩니다
  • 파일이 없다
  • 사용자 입력이 잘못됐다
  • 네트워크가 끊겼다
  • BASIC 소스에 문법 오류가 있다

전부 예상되는 일입니다 → error로 반환

✔ 이럴 때 씁니다
  • 배열 인덱스 범위 초과 (런타임이 냄)
  • nil 역참조 (런타임이 냄)
  • 프로그래머의 논리 오류 — “여기 올 수 없다”
  • 초기화 실패로 아예 못 돌아갈 때

그 책의 Go 코드에서 panic은 딱 한 번 나옵니다.

panic(fmt.Sprintf("unhandled stmt: %T", s))
이것이 정당한 이유 — 컴파일러가 AST를 순회하다 모르는 문장 타입을 만난 경우입니다. 이건 사용자 잘못이 아니라 구현자가 case를 빠뜨린 것입니다. 조용히 무시하면 버그가 숨고, error로 돌려주면 “컴파일러 내부 오류”를 사용자에게 떠넘기게 됩니다. 즉시 죽는 것이 가장 정직한 대응입니다.
%T에 주목 — 값이 아니라 타입 이름을 찍는 서식입니다. *ast.SwapStmt처럼 나오므로, 어느 case를 빠뜨렸는지 즉시 알 수 있습니다.

15.4 recover — 반드시 defer 안에서

defer func() {
	if r := recover(); r != nil {
		fmt.Println("잡았다:", r)
	}
}()
위치defer된 함수 안에서 직접 불러야 합니다. 그 안에서 또 함수를 부르면 안 됩니다
반환값패닉 값(interface{}). 패닉 중이 아니면 nil
효과패닉이 멈추고, 그 함수는 정상 반환한 것처럼 됩니다
남용하지 마세요 — recover를 try/catch처럼 쓰면 Go 코드가 아니게 됩니다. 정당한 용도는 세 가지 정도입니다.
  1. 경계에서 막기 — 서버가 요청 하나 때문에 전체가 죽지 않게. 그 책은 REPL이 이 역할입니다
  2. 라이브러리 내부의 흐름 제어 — 깊은 재귀에서 빠져나올 때(encoding/json이 실제로 씁니다). 단 패키지 밖으로 새어 나가면 안 됩니다
  3. 정리 후 재패닉 — recover하고 로그를 남긴 뒤 panic(r)로 다시 던지기
인터프리터에서의 자리 — “BASIC 프로그램의 에러”와 “인터프리터 자신의 버그”는 다릅니다. 전자는 ?Syntax error로 사용자에게 보여 주고 REPL을 계속 돌려야 합니다(→ error). 후자는 panic이고, REPL 경계에서 recover해 “내부 오류”라고 알린 뒤 계속 돕니다. 둘을 섞지 않는 것이 설계의 핵심입니다.

인터페이스 기초

16.1 인터페이스는 메서드 목록이다

type Stringer interface {
	String() string
}

“이 메서드를 가진 것은 무엇이든 Stringer다”라는 뜻입니다. 그게 전부입니다.

암묵적 구현 — Java의 implements, C#의 :, Rust의 impl … for에 해당하는 것이 없습니다. 타입이 메서드를 가지면 자동으로 만족합니다. 인터페이스가 정의되기 전에 만들어진 타입도, 다른 패키지의 타입도, 심지어 표준 라이브러리의 타입도 마찬가지입니다.

←

16.4 NullHost — 인터페이스가 크면 나오는 문제

Host는 메서드가 13개입니다. 그래픽이 필요 없는 테스트에서도 13개를 다 만들어야 합니다. 그래서 “아무것도 안 하는” 기본 구현을 둡니다.

// NullHost는 호스트 인터페이스의 기본 무동작 구현. 그래픽이 없는 환경에서도
// 컴파일 가능하도록 모든 메서드를 빈 동작으로 채워 둡니다.
type NullHost struct{}

func (NullHost) Print(string)                              {}
func (NullHost) InputLine(context.Context) (string, error) { return "", nil }
func (NullHost) Cls()                                      {}
func (NullHost) SetColor(int, int, uint8) error            { return nil }
func (NullHost) Locate(int, int) error                     { return nil }
func (NullHost) SetPixel(int, int, int)                    {}
func (NullHost) DrawLine(int, int, int, int, int)          {}
// ... 나머지도 전부 빈 몸통 ...

17.1 타입 어설션 — 인터페이스에서 구체 타입 꺼내기

변환(T(x))과 다릅니다 — 변환은 컴파일 타임에 “이 타입은 저 타입이 될 수 있다”가 확정됩니다(int64(x)). 어설션은 런타임에 “안에 뭐가 들었나”를 확인합니다. 문법도 다르고(x.(T) vs T(x)) 실패 방식도 다릅니다.

17.2 타입 스위치 — 이 책의 심장

switch n := e.(type) {

	return n.Name                          // n은 *VarRef

	return "(" + walk(n.LHS) + n.Op + walk(n.RHS) + ")"

n의 타입이 case마다 다릅니다. 이것이 타입 스위치의 전부입니다. case *NumLit: 안에서 n은 *NumLit이므로 n.Value를 바로 쓸 수 있습니다. 어설션을 손으로 쓸 필요가 없습니다.

17.3 마커 인터페이스 — Go식 합 타입

문제는 이것입니다. AST 노드는 “NumLit이거나 VarRef이거나 BinaryExpr이거나…” 중 하나입니다. Go에는 합 타입이 없습니다. 어떻게 표현할까요?

// 마커 인터페이스: 컴파일러가 의도치 않은 타입을 흘려 보내지 못하게 함.
type Stmt interface{ isStmt() }

	Expr
	isLvalue()
}

	Value   float64
	NumType NumKind
}

	RHS Expr

17.4 빠뜨린 case는 누가 잡아 주나

Rust의 match는 모든 경우를 다루지 않으면 컴파일 에러입니다. Go는 그러지 않습니다.

그 책 13.1절이 이 한계를 정직하게 인정합니다 — “exhaustive switch 강제는 컴파일러가 자동으로 해 주지 않습니다. 새 노드를 추가할 때는 default: panic을 붙여 두고 정적 분석 도구(exhaustive 린터)로 검사하는 것이 일반적입니다.”
func visitStmt(s ast.Stmt) {
	switch s := s.(type) {
	case *ast.PrintStmt:
		// ...
	case *ast.AssignStmt:
		// ...
	case *ast.IfStmt:
		// ...
	default:
		panic(fmt.Sprintf("unhandled stmt: %T", s))
	}
}
default: panic이 최선의 방어입니다 — 컴파일 타임에 못 잡으면 실행 첫 순간에 잡아야 합니다. 조용히 무시하면 “SWAP이 아무 일도 안 하는데 에러도 안 나는” 최악의 버그가 됩니다. 15.3절에서 panic이 정당한 유일한 자리라고 한 것이 바로 이것입니다.
대가를 정확히 알고 쓰세요 — 마커 인터페이스는 “이 인터페이스가 될 수 있는 타입”은 막지만 “모든 경우를 다뤘는가”는 못 막습니다. 절반만 얻는 것입니다. TypeScript의 판별 유니온이나 Rust의 enum은 둘 다 얻습니다. Go를 쓰며 치르는 대가 목록(1.10절)에 이것을 추가하세요.

func DumpExpr(e Expr) string {
	switch v := e.(type) {
	case *NumLit:
		return fmt.Sprintf("%g", v.Value)
	case *StrLit:
		return fmt.Sprintf("%q", v.Value)
	case *VarRef:
		return v.Name
	case *ArrayRef:
		parts := make([]string, len(v.Indices))
		for i, x := range v.Indices {
			parts[i] = DumpExpr(x)            // 재귀
		}
		return v.Name + "(" + strings.Join(parts, ",") + ")"
	case *FnCall:
		parts := make([]string, len(v.Args))
		for i, x := range v.Args {
			parts[i] = DumpExpr(x)
		}
		return v.Target + "(" + strings.Join(parts, ",") + ")"
	case *UnaryExpr:
		return "(" + v.Op + " " + DumpExpr(v.Operand) + ")"
	case *BinaryExpr:
		return "(" + DumpExpr(v.LHS) + " " + v.Op + " " + DumpExpr(v.RHS) + ")"
	}
	return "?"
}

19.4 감싸기 — %w

fmt.Println(errors.Unwrap(e) == ErrNotFound)

errors.Unwrap(err)한 겹 벗기기. 직접 쓸 일은 드뭅니다
errors.Join(a, b) 1.20+여러 에러를 하나로. Is가 둘 다 찾습니다

그 책 29장 REPL이 이 패턴을 씁니다 — 사용자가 Ctrl+D를 누르면 ReadString이 io.EOF를 돌려주고, REPL이 조용히 끝납니다. 에러 메시지를 찍으면 안 되는 자리입니다.
언제 센티널을 만드나 — 호출자가 그 경우를 구별해 다르게 행동해야 할 때만입니다. 그냥 “실패했다”면 fmt.Errorf로 충분합니다. 센티널은 공개 API의 일부가 되어 나중에 못 바꾸므로 아껴 씁니다.

20.4 select — 먼저 오는 쪽을 받는다

그 책 19.3절 TermHost.InputLine의 실제 코드 전체입니다. 이 책 동시성의 90%가 여기 있습니다.

func (h *TermHost) InputLine(ctx context.Context) (string, error) {
	type result struct {
		s   string
		err error
	}
	ch := make(chan result, 1)
	go func() {
		s, err := h.in.ReadString('\n')
		ch <- result{s, err}
	}()
	select {
	case <-ctx.Done():
		return "", ctx.Err()
	case r := <-ch:
		return trimNewline(r.s), r.err
	}
}
  1. 결과를 담을 익명 구조체 타입을 함수 안에 정의합니다. 채널로는 값 하나만 보낼 수 있으므로 (문자열, 에러)를 묶습니다.
  2. ReadString은 취소할 수 없는 블로킹 호출입니다. 그래서 goroutine에 가둡니다.
  3. select가 둘 중 먼저 오는 쪽을 받습니다 — 입력이 왔거나, 취소됐거나.
  4. 취소되면 즉시 ctx.Err()를 반환하고 함수가 끝납니다.
버퍼 크기 1이 핵심입니다 — 취소로 함수가 먼저 끝나 버리면, 아무도 ch를 읽지 않습니다. 버퍼가 없었다면 goroutine이 ch <- result{...}에서 영원히 멈춰 누수됩니다. 버퍼가 1이면 값을 넣고 goroutine이 정상 종료합니다. 그 값은 아무도 안 읽고 GC가 치웁니다.
여전히 남는 문제 — 취소돼도 ReadString 자체는 계속 기다립니다. 그 goroutine은 사용자가 엔터를 칠 때까지 살아 있습니다. 표준 입력을 진짜로 취소할 방법이 표준 라이브러리에는 없으므로, 이것이 실용적 타협입니다.

20.7 Ctrl+C를 잡는 법 — 진입점의 전부

Q. InputLine을 이렇게 “단순화”하면 무엇이 깨질까요?

func (h *TermHost) InputLine(ctx context.Context) (string, error) {
	if err := ctx.Err(); err != nil {
		return "", err
	}
	s, err := h.in.ReadString('\n')
	return trimNewline(s), err
}
A. 기다리는 동안의 취소가 안 됩니다.
ctx.Err()는 진입 시점에 한 번만 확인합니다. 그 뒤 ReadString이 블록하면 Ctrl+C를 눌러도 아무 반응이 없습니다. 사용자가 엔터를 쳐야만 함수가 돌아오고, 그때는 이미 입력이 소비된 뒤입니다.
일반화된 교훈: ctx는 기다리는 지점에서 확인해야 의미가 있습니다. 그래서
  • 블로킹 호출(I/O)은 goroutine + select로 감싼다 → InputLine
  • 루프는 반복마다 ctx.Err()를 본다 → VM.Run
그 책이 두 방식을 각각 쓴 이유가 이것입니다.

21.1 함수 이름의 규칙

fmt의 함수 이름은 접두사 + 어간으로 조립됩니다. 스무 개를 외울 필요가 없습니다.

접두사 없음표준 출력으로 — Print, Println, Printf
S문자열을 반환 — Sprint, Sprintln, Sprintf

어간 없음인자를 이어 붙임. 피연산자 사이에 문자열이 아닌 것끼리만 공백

go vet을 습관으로 — 이런 실수는 실행 전에는 안 보이고, 실행해도 로그를 안 보면 모릅니다. go test가 자동으로 vet을 돌리는 이유입니다.

+### / ###-부호를 앞 또는 뒤에

22.1 io.Writer — 가장 중요한 인터페이스

type Writer interface {
	Write(p []byte) (n int, err error)
}

type Reader interface {
	Read(p []byte) (n int, err error)
}
메서드가 하나뿐입니다. 그래서 온갖 것이 이것을 만족합니다 — 파일, 네트워크 연결, os.Stdout, strings.Builder, bytes.Buffer, gzip 압축기, HTTP 응답… 16.4절에서 말한 “인터페이스는 작을수록 좋다”의 표본입니다.

	// ...

func (h *TermHost) Print(s string) { fmt.Fprint(h.out, s) }

math.MaxInt16 등타입 없는 상수라 어디에나 맞춰집니다 (4.7절)
math/rand별도 패키지. rand.New(rand.NewSource(seed))로 재현 가능한 난수기

Q. 이 테스트 실패 메시지가 아무 도움이 안 되는 이유는?

if found != " hello world" {
	t.Errorf("REM text = %v", found)
}
// 출력:  REM text =  hello world
A. %v는 문자열을 그대로 찍으므로 앞뒤 공백이 안 보입니다. 위 출력에서 = 다음에 공백이 두 개인지 하나인지 눈으로 구별할 수 없습니다. 이 테스트는 정확히 선행 공백 한 칸을 검사하는 것인데 말이죠.

testing — 프레임워크가 필요 없다

JUnit도 pytest도 없습니다. go test ./... 하나로 끝납니다.

23.1 규칙은 네 가지

  1. 파일 이름이 _test.go로 끝난다 → 일반 빌드에서 제외된다
  2. 함수 이름이 Test로 시작한다
  3. 인자가 t *testing.T 하나다
  4. 실패는 t.Errorf 또는 t.Fatal로 보고한다

그 책 9.9절의 실제 테스트입니다.

internal/lexer/lexer_test.go

package lexer

import (
	"reflect"
	"testing"
)

func kinds(toks []Token) []TokenKind {
	out := make([]TokenKind, len(toks))
	for i, t := range toks {
		out[i] = t.Kind
	}
	return out
}

func TestBasicTokens(t *testing.T) {
	toks, err := Tokenize(`10 PRINT "HELLO", A%+1`)
	if err != nil {
		t.Fatal(err)
	}
	want := []TokenKind{
		TNumber, TKeyword, TString, TComma,
		TIdent, TOp, TNumber, TEOF,
	}
	if !reflect.DeepEqual(kinds(toks), want) {
		t.Errorf("got %v, want %v", kinds(toks), want)
	}
	if toks[0].Num != 10 {
		t.Errorf("first num = %v, want 10", toks[0].Num)
	}
	if toks[4].Lex != "A%" {
		t.Errorf("ident lex = %q", toks[4].Lex)
	}
}
package lexer에 주목 — 테스트가 같은 패키지에 있으므로 소문자 식별자에도 접근합니다(3.2절). package lexer_test로 쓰면 외부 사용자 시점에서 exported API만 테스트하게 됩니다. 둘 다 관용이고, 그 책은 전자를 씁니다.

Q. captureHost가 host.NullHost를 임베딩하지 않았다면 무슨 일이 생길까요?

type captureHost struct {
	host.NullHost
	buf bytes.Buffer
}
func (h *captureHost) Print(s string) { h.buf.WriteString(s) }
A. host.Host를 만족하지 못해 vm.New(ch, h)가 컴파일 에러가 납니다.
Host 인터페이스는 메서드가 13개인데 captureHost에는 Print 하나뿐입니다. 나머지 12개(Cls, SetPixel, DrawCircle, Sound, PlayMML, Now…)를 전부 손으로 써야 합니다.

	ch := l.peek(0)

	// 공백 스킵 (개행 제외)

		l.advance()
		return nil

	if ch == '\n' {
		l.advance()
		l.push(TEOL, "\n")
		return nil
	}
	if ch == '\'' { return l.scanRem() }
	if isDigit(ch) || (ch == '.' && isDigit(l.peek(1))) { return l.scanNumber() }
	if ch == '&' { return l.scanRadixNumber() }
	if ch == '"' { return l.scanString() }
	if isAlpha(ch) { return l.scanIdentOrKeyword() }

	switch ch {
	case '(': l.advance(); l.push(TLParen, "("); return nil
	case ')': l.advance(); l.push(TRParen, ")"); return nil
	case ',': l.advance(); l.push(TComma, ","); return nil
	case '?': l.advance(); l.push(TKeyword, "PRINT"); return nil
	}

	two := string([]byte{ch, l.peek(1)})
	if _, ok := twoCharOps[two]; ok {
		l.advance(); l.advance()
		l.push(TOp, two)
		return nil
	}
	if _, ok := singleOps[ch]; ok {
		l.advance()
		l.push(TOp, string(ch))
		return nil
	}
	return l.errf("unexpected character %q", ch)
}
읽어 낼 것 네 가지 — ① 전부 byte 비교(6.3절). ② peek(1)로 한 글자 미리 보기 — .5와 .를 구별. ③ 두 글자 연산자를 먼저 시도(<=가 <보다 우선). ④ _, ok := m[k] 존재 확인(9.2절).
?가 PRINT가 되는 것에 주목하세요. GW-BASIC에서 ?는 PRINT의 약어입니다. 렉서가 토큰 단계에서 바꿔치기하므로 파서는 이런 게 있는 줄도 모릅니다. 특수 케이스를 가장 이른 계층에서 흡수한 좋은 예입니다.

25.4 Parser — 토큰 커서

그 책 10.2절입니다. Cursor가 “지금 어디까지 읽었나”를 들고 있습니다.

type Cursor struct {
	toks []lexer.Token
	i    int
}

func (c *Cursor) Peek(off int) lexer.Token {
	n := c.i + off
	if n >= len(c.toks) {
		return c.toks[len(c.toks)-1]      // 넘치면 마지막(EOF)을 반복
	}
	return c.toks[n]
}

func (c *Cursor) Next() lexer.Token {
	t := c.Peek(0)
	if c.i < len(c.toks) { c.i++ }
	return t
}

// Check는 확인만 (소비 X)
func (c *Cursor) Check(k lexer.TokenKind, lex ...string) bool {
	t := c.Peek(0)
	if t.Kind != k { return false }
	if len(lex) > 0 && t.Lex != lex[0] { return false }
	return true
}

// Match는 일치하면 소비하고 true
func (c *Cursor) Match(k lexer.TokenKind, lex ...string) bool {
	if !c.Check(k, lex...) { return false }
	c.Next()
	return true
}
lex ...string이 영리합니다 — 12.4절의 가변 인자를 “선택적 인자”로 쓴 것입니다. Go에는 기본 인자가 없으므로(12.1절), Check(TOp)와 Check(TOp, "=")를 한 함수로 만들려면 이 수법이 필요합니다. len(lex) > 0으로 “줬는지”를 판별합니다.
Peek가 EOF를 반복하는 것도 설계입니다. 범위 검사를 커서 안에 한 번만 두면, 파서의 나머지 코드는 “항상 토큰이 있다”고 가정하고 짤 수 있습니다. 6.3절의 peek가 0을 돌려준 것과 같은 발상입니다.

25.5 Expect — 에러가 태어나는 자리

func (c *Cursor) Expect(k lexer.TokenKind, lex ...string) (lexer.Token, error) {
	if !c.Check(k, lex...) {
		t := c.Peek(0)
		want := k.String()                   // ← TokenKind.String() (4.11절)
		if len(lex) > 0 {
			want = fmt.Sprintf("%s(%s)", want, lex[0])
		}
		return t, &common.BasicError{
			Code: common.ErrSyntax,
			Msg:  fmt.Sprintf("expected %s, got %s(%q)", want, t.Kind, t.Lex),
			Pos:  common.SourcePos{Line: t.Line, Col: t.Col},
		}
	}
	return c.Next(), nil
}
expected RPAREN, got OP("+")
4.11절의 String()이 여기서 값을 합니다 — t.Kind가 uint8인데 메시지에는 OP라고 나옵니다. %s가 String()을 자동으로 부르기 때문입니다(14.6절). 이것이 없었다면 expected 6, got 4("+")라는 쓸모없는 메시지가 됐을 것입니다.
%q도 의도적입니다(21장 퀴즈) — got OP(" ")처럼 공백 토큰이 문제일 때 따옴표가 없으면 아무것도 안 보입니다.

25.6 Pratt 파서 — 우선순위를 다루는 법

그 책 11.3절 parseExpression의 핵심입니다. 2+3*4가 2+(3*4)가 되는 곳입니다.

func (p *Parser) parseExpression(minBP int) (ast.Expr, error) {
	lhs, err := p.parsePrefix()          // 먼저 왼쪽 하나를 읽는다
	if err != nil { return nil, err }

	for {
		t := p.cur.Peek(0)
		var opName string
		switch t.Kind {
		case lexer.TOp:
			opName = t.Lex
		case lexer.TKeyword:
			switch t.Lex {
			case "AND", "OR", "XOR", "MOD":   // 키워드인 연산자들
				opName = t.Lex
			}
		}
		if opName == "" { break }

		b, ok := binBP[opName]
		if !ok || b.left < minBP { break }   // ← 여기가 우선순위 판단

		p.cur.Next()
		rhs, err := p.parseExpression(b.right)   // 재귀
		if err != nil { return nil, err }
		lhs = &ast.BinaryExpr{Op: opName, LHS: lhs, RHS: rhs}
	}
	return lhs, nil
}
b.left < minBP면 멈춘다 — 이 한 줄이 우선순위의 전부입니다. 2 + 3 * 4를 파싱할 때, +를 처리하며 parseExpression(+의 right BP)를 재귀 호출합니다. 그 안에서 *를 만나는데 *의 left BP가 +의 right BP보다 크므로 멈추지 않고 3*4를 먼저 묶습니다.
중첩 switch에 주목 — BASIC에서 AND/OR/MOD는 기호가 아니라 키워드입니다. 그래서 렉서는 TKeyword로 만들고, 파서가 “연산자로도 쓰이는 키워드”를 골라냅니다. 언어 명세의 지저분함이 코드에 그대로 드러나는 정직한 대목입니다.
결합 방향 — 좌결합이면 right = left+1, 우결합(^)이면 right = left로 둡니다. 표 하나로 우선순위와 결합성을 동시에 표현하는 것이 Pratt의 우아함입니다.

25.8 Compiler — AST를 스택 머신 코드로

그 책 15.2절 emitExpr입니다. 후위 순회(post-order)로 내려가며 명령을 뱉습니다. 규칙은 “자식 먼저, 연산 나중”입니다.

var binOpMap = map[string]vm.Op{
	"+": vm.OpAdd, "-": vm.OpSub, "*": vm.OpMul, "/": vm.OpDiv,
	"\\": vm.OpIDiv, "MOD": vm.OpMod, "^": vm.OpPow,
	"=": vm.OpEq, "<>": vm.OpNe, "<": vm.OpLt, "<=": vm.OpLe,
	">": vm.OpGt, ">=": vm.OpGe,
	"AND": vm.OpAnd, "OR": vm.OpOr, "XOR": vm.OpXor,
}

func (c *Compiler) emitExpr(e ast.Expr) error {
	switch v := e.(type) {                    // 타입 스위치 (17.2절)
	case *ast.NumLit:
		var val runtime.Value
		switch v.NumType {
		case ast.NumInt: val = runtime.IntVal(int16(v.Value))
		case ast.NumDbl: val = runtime.DblVal(v.Value)
		default:         val = runtime.SngVal(float32(v.Value))
		}
		c.emit(vm.Instr{Op: vm.OpPush, A: c.constIdx(val)})
	case *ast.VarRef:
		c.emit(vm.Instr{Op: vm.OpLoad, A: c.nameIdx(normName(v.Name))})
	case *ast.BinaryExpr:
		if err := c.emitExpr(v.LHS); err != nil { return err }   // 왼쪽
		if err := c.emitExpr(v.RHS); err != nil { return err }   // 오른쪽
		op, ok := binOpMap[v.Op]
		if !ok {
			return common.NewError(common.ErrSyntax, "unknown binary op: "+v.Op)
		}
		c.emit(vm.Instr{Op: op})                                  // 연산
	// ...
	}
	return nil
}
연산자 → 옵코드는 switch가 아니라 맵입니다 — 16개 항목의 단순 표라 binOpMap[v.Op] 한 줄이면 끝나고, ok로 “모르는 연산자”까지 잡습니다. 7.7절에서 본 “파서·컴파일러는 표, VM은 switch” 기준이 여기서도 지켜집니다.

(2 + (3 * 4))가 이렇게 됩니다.

0000 PUSH c0 ; 2 0001 PUSH c1 ; 3 0002 PUSH c2 ; 4 0003 MUL 0004 ADD 0005 STORE n0 ; A
괄호가 사라졌습니다 — 우선순위는 명령의 순서에 이미 녹아 있습니다. 스택 머신의 아름다움이고, 이것이 바이트코드 VM이 트리 순회 인터프리터보다 빠른 이유이기도 합니다.
c0, n0은 인덱스입니다 — 10.7절의 풀 설계입니다. constIdx는 constsIndex map[runtime.Value]int32를 찾아보고, 없으면 Consts 슬라이스에 추가한 뒤 인덱스를 돌려줍니다. Value가 비교 가능해서 맵 키가 될 수 있다는 것(9.6·10.2절)이 여기서 결정적입니다.

25.9 VM — 실행

func (m *VM) Run(ctx context.Context) error {
	for !m.halted {
		if err := ctx.Err(); err != nil { return err }       // 취소 확인 (20.6절)
		if m.pc < 0 || m.pc >= len(m.ch.Code) {
			return common.NewError(common.ErrSyntax, "PC out of range")
		}
		ins := m.ch.Code[m.pc]      // 값 복사 (16바이트, 싸다)
		m.pc++                       // ← 먼저 전진
		if err := m.step(ctx, ins); err != nil { return err }
	}
	return nil
}
m.pc++가 step 앞에 있습니다 — 그래서 OpJmp 핸들러는 그냥 m.pc = int(ins.A)로 덮어쓰면 됩니다. 만약 뒤에 있었다면 점프 후에도 pc가 하나 더 올라가 버립니다. 바이트코드 VM을 짤 때 가장 흔한 off-by-one 자리입니다.

func (e *Env) zeroFor(name string) Value {
	suf := suffixOf(name)
	switch suf {
	case '%': return IntVal(0)
	case '!': return SngVal(0)
	case '#': return DblVal(0)
	case '$': return StrVal("")
	}
	if len(name) == 0 { return SngVal(0) }
	c := strings.ToUpper(name)[0]
	if c < 'A' || c > 'Z' { return SngVal(0) }
	switch e.defType[c-'A'] {          // ← [26]ValueTag 배열 (8.1절)
	case TagInt: return IntVal(0)
	case TagDbl: return DblVal(0)
	case TagStr: return StrVal("")
	}
	return SngVal(0)
}

	toks[i].Line = 0
}
같은 함정의 변형 — 큰 구조체를 range로 돌면 매 반복마다 통째로 복사됩니다. Token이 56바이트이므로 토큰 수만 번의 복사가 일어납니다. 읽기만 할 때도 성능이 문제라면 for i := range toks { t := &toks[i]; … }로 포인터를 잡으세요(7.3절).

26.3 nil 맵에 쓰기

type Compiler struct {
	namesIndex map[string]int32
}
c := &Compiler{}          // namesIndex는 nil
c.namesIndex["A"] = 0     // 💥
panic: assignment to entry in nil map
규칙 — 맵 필드가 있는 구조체에는 생성 함수가 필수입니다. 그 책의 NewEnv, NewCompiler, vm.New가 전부 이 이유로 존재합니다. 슬라이스 필드는 nil이어도 append가 되므로 괜찮습니다 — 맵만 다릅니다(9.1절).

26.4 슬라이스 aliasing

a := []int{0, 1, 2, 3, 4, 5}
c := a[1:3]              // len 2, cap 5
c = append(c, 777)       // a[3]이 777로 덮어써짐!
고치는 법 — 3-인덱스 슬라이싱으로 cap을 잘라 둡니다. 
c := a[1:3:3]            // cap 2 — append하면 새 배열로 이사
함수가 슬라이스를 늘려야 한다면 반환하세요 — func f(s []int) 안의 append는 호출자에게 안 보입니다. func f(s []int) []int로 만들어야 합니다. append 자신이 값을 반환하는 이유와 같습니다(8.3~8.4절).

26.5 구체 에러 타입을 반환

✘
func f() *BasicError {
	return nil
}
var err error = f()
fmt.Println(err == nil)  // false!
✔
func f() error {
	return nil
}
인터페이스 값은 (타입, 값) 쌍이고, nil 포인터를 담으면 타입 칸이 채워집니다(16.2절). 반환 타입을 error로 두고, 성공 경로에서 return nil을 직접 쓰세요.

26.6 errors.Is 대신 ==

✘ 감싸인 에러를 놓침
if err == ErrNotFound { ... }
if e, ok := err.(*BasicError); ok { ... }
✔
if errors.Is(err, ErrNotFound) { ... }
var e *BasicError
if errors.As(err, &e) { ... }
중간 계층이 fmt.Errorf("…: %w", err)로 맥락을 덧씌우는 순간 왼쪽은 전부 실패합니다. 그리고 그 감싸기는 나중에 남이 추가할 수도 있습니다 — 처음부터 오른쪽으로 쓰세요(19.5절).

26.7 %v와 %w를 헷갈림

fmt.Errorf("compile: %v", err)    // 사슬이 끊긴다
fmt.Errorf("compile: %w", err)    // 사슬이 이어진다
출력이 똑같아서 안 보입니다 — 둘 다 compile: ?Division by zero in 100을 찍습니다. 차이는 errors.Is/errors.As가 통하느냐뿐입니다. 테스트로만 잡을 수 있습니다(19.4절).

26.8 switch 안의 break

for {
	switch cmd {
	case "QUIT":
		break          // ✘ switch만 빠져나간다. 루프는 계속!
	}
}
✔ 라벨
loop:
	for {
		switch cmd {
		case "QUIT":
			break loop
		}
	}
✔ 플래그
for !done {
	switch cmd {
	case "QUIT":
		done = true
	}
}
C에서 온 사람이 가장 헷갈리는 자리입니다. C는 switch의 break가 필수라 습관이 반대로 박혀 있습니다(7.8절).

26.9 대문자를 잊어 밖에서 안 보임

type token struct {          // ✘ 타입이 소문자
	kind tokenKind           // ✘ 필드도 소문자
}
func tokenize(s string) []token { ... }   // ✘ 함수도
실수의 신호 — “다른 패키지에서 lexer.Token을 못 찾는다”는 에러가 나면 대부분 이것입니다. 패키지 경계를 넘어야 하는 것만 대문자로 하고, 나머지는 소문자로 두는 것이 원칙입니다(3.2절).
JSON에서 특히 문제 — encoding/json은 리플렉션으로 필드를 읽는데, 소문자 필드는 아예 못 봅니다. 조용히 빈 객체가 나옵니다.

26.10 루프 안의 defer

✘ 파일 1000개가 동시에 열림
for _, p := range paths {
	f, _ := os.Open(p)
	defer f.Close()      // 함수 끝까지 안 닫힘
	process(f)
}
✔ 함수로 감싸기
for _, p := range paths {
	func() {
		f, _ := os.Open(p)
		defer f.Close()
		process(f)
	}()
}
defer는 블록이 아니라 함수 단위입니다(15.1절). 즉시 실행 함수(12.6절)로 함수 경계를 만들어 주는 것이 관용구입니다.

26.11 값을 인터페이스에 담으려 함

var h host.Host = TermHost{}      // ✘
TermHost does not implement host.Host (method Cls has pointer receiver)
var h host.Host = &TermHost{}     // ✔ — & 하나
메서드 집합 규칙 — T는 값 리시버 메서드만, *T는 전부. 인터페이스에 담긴 값은 주소를 얻을 수 없으므로 포인터 리시버 메서드를 부를 수 없습니다(14.4절). “분명 다 만들었는데 인터페이스를 만족 안 한다”의 90%가 이것입니다.

26.12 나머지 셋

맵 순회 순서에 의존무작위입니다. 순서가 필요하면 키를 뽑아 sort (9.4절)
실수 → 정수 변환의 범위 초과정의되지 않은 값. 변환 전에 범위를 검사할 것 (5.4절)
String() 안에서 %v자기 자신을 다시 불러 스택 오버플로. 기본 타입으로 변환해 쓸 것 (14.6절)
1.22 이전 코드를 읽을 때 — for i := range x { i := i; … }처럼 같은 이름으로 다시 선언하는 이상한 줄이 보이면, 루프 변수 캡처 함정을 피하던 옛 관용구입니다. 지금은 필요 없지만, go.mod의 go 줄이 1.21 이하인 프로젝트에서는 여전히 필요합니다(7.4절).

26.13 치트시트 ① — 선언과 타입

var x int              // 제로값 0
x := 42                // 함수 안에서만
const K = 3            // 타입 없는 상수
const ( A = iota; B; C )   // 0, 1, 2

int int8..int64 uint8..uint64 float32 float64 bool string
byte = uint8    rune = int32

int64(x)  float64(y)  string(b)  []byte(s)  []rune(s)   // 명시 변환만

[3]int          // 배열 — 길이가 타입의 일부, 값 복사
[]int           // 슬라이스 — {ptr, len, cap} 헤더
map[K]V         // 맵 — nil에 쓰면 패닉
*T              // 포인터
struct{...}     // 구조체 — 값
interface{...}  // 인터페이스 — (타입, 값) 쌍
func(A) B       // 함수 — nil과만 비교 가능
chan T          // 채널
제로값숫자 0 · bool false · string "" · 나머지 nil
비교 가능숫자·문자열·bool·포인터·배열·비교 가능한 필드만 가진 구조체
비교 불가슬라이스·맵·함수 (nil과만)

26.14 치트시트 ② — 슬라이스와 맵

// 슬라이스
var s []int                // nil — append 가능
s := make([]T, 0, n)       // 길이 0, 용량 n  ← 미리 잡기
s = append(s, v)           // 반드시 재대입
s = append(s, other...)    // 이어 붙이기
s[i:j]                     // 복사 없음, cap은 끝까지
s[i:j:k]                   // cap = k-i  ← aliasing 차단
s = s[:len(s)-1]           // pop
copy(dst, src)             // min(len) 만큼 복사

// 맵
m := map[K]V{}             // 또는 make(map[K]V)
v, ok := m[k]              // comma-ok
delete(m, k)
set := map[T]struct{}{}    // 집합
set[x] = struct{}{}
for k := range m { }       // 순서 무작위!
세 줄만 외운다면 — s = append(s, v)(재대입 필수) · v, ok := m[k](존재 확인) · make([]T, 0, n)(길이 0, 용량 n).

26.15 치트시트 ③ — 제어와 함수

if v, ok := f(); ok { }        // 초기화절 — 가장 중요한 관용구
for i := 0; i < n; i++ { }
for cond { }                   // while
for { }                        // 무한
for i, v := range x { }
for i := range n { }           // 1.22+ 정수 range

switch x { case 1, 2: }        // 자동 탈출. fallthrough는 명시
switch { case c1: }            // if/else if 대신
switch v := x.(type) { }       // 타입 스위치

outer:
	for { for { break outer } }

func f(a, b int) (int, error)  // 다중 반환, error는 마지막
func g(a ...int)               // 가변 인자 → 함수 안에서 []int
g(s...)                        // 슬라이스 펼치기
func(){ }()                    // 즉시 실행

defer f()                      // 함수 끝, LIFO, 인자는 지금 평가
func (t *T) M()                // 포인터 리시버
(*T).M                         // 메서드 표현식 → func(*T)

마치며

Go는 배울 것이 적은 언어입니다. 예약어 25개, 반복문 하나, 상속 없음, 예외 없음. 이 덱이 250여 장이 된 것은 문법이 많아서가 아니라, “왜 이 문법이 이렇게 생겼는가”를 매번 짚었기 때문입니다.

그 “왜”들이 대부분 같은 곳을 가리킵니다.

기능을 넣어 표현력을 얻는 대신, 빼서 읽기 쉬움을 산다.

슬라이스의 aliasing도, 에러 처리의 장황함도, 합 타입의 부재도 전부 그 거래의 결과입니다. 그 대가가 아깝다고 느끼는 순간이 분명히 옵니다. 그때 이것이 거래였다는 사실을 아는 것이, 참고 쓰는 것과 납득하고 쓰는 것의 차이입니다.
