함수 안에서 만든 String 을 다듬어 돌려줬다 — E0515

받은 글을 소문자로 바꾸고 앞뒤 공백을 떼어 &str 로 돌려주려 할 때 만납니다. 들어오는 참조가 하나라 시그니처에는 적을 것이 없고, 막히는 곳은 본문입니다.

읽는 법 — 6부에서 본 E0515 와 같은 번호입니다. 그때의 오류 첫 줄은 "지역 변수의 참조를 돌려줄 수 없다(cannot return reference to local variable)" 였고, 여기서는 "지역 변수 lower 를 참조하는 값을 돌려줄 수 없다(cannot return value referencing)" 입니다. 그때는 &loud 한 곳에 말이 하나 붙었습니다. 여기 3번 줄에는 둘입니다. 식 전체 아래: "지금 함수가 가진 데이터를 참조하는 값을 돌려준다". lower 아래: "lower 를 여기서 빌린다". 3번 줄에 & 는 없습니다. 6부에서 본 대로 메서드를 부르는 것도 빌림이고, 화면은 trim 이 돌려준 값이 그 빌림에 걸려 있다고 적었습니다. note: 도 help: 도 없습니다. 1번 줄의 시그니처는 짚이지 않았습니다.
처방 — 함수 안에서 만든 값에서 나온 것은 값으로 돌려줍니다. 6부의 새로 만든 값은 통째로 돌려준다이고, 11부의 답은 값을 통째로 돌려주는 것입니다. 고친 파일은 1번 · 3번 두 줄이 다릅니다. 반환 타입이 String 이 되고, 3번 줄 끝의 .to_string() 이 다듬은 글로 새 String 을 만듭니다. 화면의 [rust] 가 소문자가 되고 공백이 떨어진 글입니다. 반환 타입에 수명 표기를 붙이는 쪽은 길이 아닙니다(표기는 값을 오래 살게 해 주지 않는다).

반복문 안에서 만든 값을 빌려 벡터에 모았다 — E0597

반복문을 돌 때마다 글을 하나 만들고, 그 참조를 반복문 밖의 벡터에 모아 뒤에서 쓰려 할 때 만납니다.

읽는 법 — 11부에서 본 E0597 과 같은 번호이고 오류 첫 줄의 꼴도 같습니다(does not live long enough). 그때 짚은 네 자리가 여기에도 있습니다. 4번 줄: label 을 여기서 선언했다. 5번 줄: 빌린 값이 충분히 오래 살지 못한다. 6번 줄: 빌려준 채로 label 이 여기서 정리됐다. 7번 줄: 그 빌림을 나중에 여기서 쓴다. 6번 줄의 } 는 for 몸통의 끝입니다. 그때 없던 것이 셋 붙었습니다. 2번 줄: "변수 labels 를 여기서 선언했다". = note:: "labels 는 빌린 참조를 담는 컬렉션인데, label 은 거기 담길 만큼 오래 살지 못한다". = help:: "빌린 참조를 담은 버퍼를 다시 쓰려면 unsafe 코드를 쓰거나 짜임을 바꿔야 한다". 고친 줄을 보여 주는 help: 는 없습니다.
처방 — 모은 것을 반복문 뒤에서 쓸 것이면 벡터가 값을 갖게 합니다. = help: 가 말한 둘 가운데 짜임을 바꾸는 쪽입니다. 고친 파일은 2번 · 5번 두 줄이 다릅니다. 원소 타입이 String 이 되고, push 가 & 없이 label 을 받습니다. 6부에서 본 대로 넘기는 것은 이동이라 label 은 벡터의 것이 됐고, 7번 줄이 세 글을 찍었습니다. 구조체에서 같은 길을 간 것이 11부의 빌리지 않고 갖는 구조체입니다.

impl 에서 'a 를 선언하지 않고 썼다 — E0261

수명 인자가 있는 구조체에 메서드를 붙이면서, 구조체 이름 뒤에만 <'a> 를 적을 때 만납니다.

읽는 법 — 오류 첫 줄은 "선언하지 않은 수명 이름 'a 를 썼다" 입니다. 5번 줄의 'a 에 "선언하지 않은 수명(undeclared lifetime)" 이 붙었습니다. 1번 줄에도 'a 가 있는데, 5번 줄에서는 선언하지 않은 이름이라고 합니다. help: 는 "여기에 수명 'a 를 들여오라" 며 impl 바로 뒤에 <'a> 를 넣어 보입니다. + 가 넣을 글자의 자리입니다. 함수에서 같은 것을 빼먹은 파일, 곧 fn first(text: &'a str) -> &'a str 로 시작하는 파일은 'a 를 쓴 두 자리에 이 오류를 하나씩, 둘 냈습니다. 두 help: 는 같은 자리에 같은 <'a> 를 넣어 보였습니다(싣지 않은 실행).
처방 — 수명 이름은 쓰기 전에 꺾쇠 안에서 선언합니다. 11부의 impl 에도 적는다가 이 모양이고, 선언하는 자리 셋은 표기법 정리의 첫 줄에 있습니다. help: 를 그대로 따른 것이 고친 파일이고, 5번 줄만 다릅니다. 4 는 rust 의 바이트 수입니다.

수명이 있는 구조체에 트레이트를 구현하며 수명을 뺐다 — E0726

수명 인자가 있는 구조체에 Display 같은 트레이트를 구현하면서, for 뒤에 타입 이름만 적을 때 만납니다.

읽는 법 — 오류 첫 줄은 "여기서는 수명을 말없이 생략할 수 없다" 입니다. 7번 줄의 Excerpt 에 "수명 인자가 와야 한다(expected lifetime parameter)" 가 붙었습니다. 3번 줄이 Excerpt 를 <'a> 와 함께 선언했습니다. help: 는 "이름 없는 수명을 표시하라" 며 Excerpt 뒤에 <'_> 를 넣어 보입니다. 11부의 E0106 은 구조체의 필드에서 수명을 뺐을 때였고, 그 help: 는 'a 라는 이름을 지어 붙였습니다. 여기서는 번호가 다르고 help: 가 이름을 짓지 않습니다. 트레이트 없이 impl Excerpt { 로 메서드를 붙인 파일도 같은 번호와 같은 help: 를 받았습니다(싣지 않은 실행).
처방 — 11부에서 본 '_ 는 이름은 짓지 않고 수명이 있다는 것만 알립니다. help: 를 그대로 따른 것이 고친 파일이고, 7번 줄만 다릅니다. 앞 슬라이드처럼 impl<'a> fmt::Display for Excerpt<'a> 라고 이름을 지어 적은 파일도 컴파일되어 같은 [rust] 를 찍었습니다(싣지 않은 실행). 이름을 지은 쪽은 11부에서 본 대로 메서드 안에서 그 이름을 쓸 수 있습니다.

제네릭으로 받은 값을 Box<dyn Trait> 에 담아 돌려줬다 — E0310

어떤 타입이든 받아 Box<dyn Display> 에 담아 돌려주는 함수를 쓸 때 만납니다. 8번 줄이 넘기는 것은 정수 42 인데, 화면이 짚는 곳은 함수의 정의입니다.

읽는 법 — 오류 첫 줄은 "타입 인자 T 가 충분히 오래 살지 못할 수 있다" 입니다. 3번 줄의 dyn Display 에는 "이 dyn Trait 에는 적지 않아도 붙는 'static 수명 조건이 있다(implicit)" 가 붙었습니다. 4번 줄에는 말이 둘이고, 줄임표로 이어진 한 문장입니다. "T 는 'static 수명 동안 유효해야 한다 … 그래야 T 가 요구받은 수명 조건을 채운다". help: 는 "수명 조건을 드러내 적으라" 며 3번 줄의 T: Display 뒤에 + 'static 을 넣어 보입니다. 19부의 함수 둘을 이어 붙이는 클로저에서 번호만 적고 지나간 오류입니다.
처방 — help: 를 그대로 따른 것이 고친 파일이고, 3번 줄만 다릅니다. 더한 것은 11부에서 본 T: 'static 입니다. 거기서 본 대로 "잠깐 빌린 참조를 품지 않았는가" 만 묻는 조건이라, 정수 42 는 통과해 화면에 찍혔습니다. 고친 파일의 main 을 지역 String 의 참조를 넘기게 바꾼 파일은 부르는 자리에서 E0597 로 막혔습니다(싣지 않은 실행).

빌려 받은 참조를 새 스레드에 넘겼다 — E0521

&str 로 빌려 받은 글을 thread::spawn 의 클로저 안에서 쓸 때 만납니다. 15부에서 본 move 는 이미 붙였습니다.

읽는 법 — 오류 첫 줄은 "빌린 데이터가 함수 밖으로 빠져나간다" 입니다. 3번 줄에 말이 둘 붙었습니다. text 아래: "text 는 함수 몸통 안에서만 유효한 참조다". & 아래: "이 참조의 수명을 '1 이라 부르자". 이름 없는 수명에 컴파일러가 번호를 붙이는 것은 11부의 규칙이 짐작한 것과 다르면에서 봤습니다. 4번 줄의 thread::spawn(…) 전체에도 둘입니다. "text 가 여기서 함수 몸통을 빠져나간다", "인자가 '1 이 'static 만큼 살기를 요구한다(must outlive)". 15부의 E0373 화면에서 note: 가 적은 그 조건입니다. note: 도 help: 도 없습니다. 4번 줄에서 move 를 뺀 파일은 오류를 둘 냈습니다. 이 E0521 과 E0373 이고, E0373 의 help: 가 권한 move 를 붙인 것이 이 틀린 파일입니다(싣지 않은 실행). 3번 줄에 붙은 말대로 text 는 참조이고, move 로 클로저에 옮겨 간 것도 그 참조입니다.
처방 — 스레드가 가질 값을 따로 만들어 넘깁니다. 고친 파일은 틀린 파일의 3번 줄 다음에 한 줄을 더한 것만 다릅니다. 아래는 고친 파일의 줄 번호입니다. 새로 넣은 4번 줄이 text.to_string() 으로 새 String 을 만들어 같은 이름으로 가렸고, 5번 줄의 클로저는 이번에는 그 String 을 가져갑니다. 6번 줄의 join 이 기다린 그 스레드가 화면의 한 줄을 찍었습니다. 길은 둘 더 있습니다. 15부의 스코프 스레드로 바꾼 파일도, 매개변수를 &'static str 로 바꾼 파일도 컴파일되어 같은 화면을 찍었습니다(둘 다 싣지 않은 실행). 뒤의 것은 프로그램 내내 유효한 참조만 받는 함수가 됩니다.

문자열을 for 에 그대로 넣었다 — E0277

글자를 하나씩 보려고 문자열을 for 에 그대로 넣을 때 만납니다.

읽는 법 — 19부에서 본 E0277 과 오류 첫 줄의 꼴이 같습니다(… is not an iterator). 10부의 E0277 의 문장대로 타입과 트레이트를 찾으면 &str 과 Iterator 입니다. 19부의 화면은 그 말을 help: 로 적으며 구조체를 정의한 줄을 짚었고, 여기서는 = help: 한 줄입니다. 다른 것은 3번 줄에 붙은 말입니다. "&str 은 반복자가 아니다" 뒤에 ".chars() 나 .bytes() 를 불러 보라" 가 이어집니다. 고친 줄을 따로 보여 주지는 않습니다. 마지막 = note: 는 19부의 것과 같은 말로, &str 이 IntoIterator 가 되려면 그 구현이 필요하다는 것입니다. IntoIterator 는 1장의 for 로 돈 벡터에서 for 가 부르는 것으로 화면에 나온 이름입니다.
처방 — 무엇을 하나씩 받을지를 메서드로 고릅니다. 8부의 글자로 볼지 바이트로 볼지 고른다입니다. 고친 파일은 3번 줄만 다르고 .chars() 를 붙였습니다. 화면의 두 줄이 두 글자입니다. .bytes() 를 붙인 파일도 컴파일됐는데, 글자 대신 234 로 시작하는 수 여섯을 한 줄에 하나씩 찍었습니다(싣지 않은 실행).

derive 하지 않은 구조체에 clone 을 불렀다 — E0599

내가 만든 구조체의 값을 .clone() 으로 복제하려 할 때 만납니다. 6부에서 String 에 쓰던 호출입니다.

읽는 법 — 10부에서 본 E0599 와 오류 첫 줄의 꼴이 같고(no method named … found for struct …), 1번 줄과 8번 줄에 붙은 두 말도 그때의 것입니다. "이 구조체에서 메서드 clone 을 찾지 못했다", "Point 에 없는 메서드". 그때의 = note: 는 그 메서드를 찾은 다른 타입을 댔습니다. 여기서는 두 가지가 붙었습니다. = help:: "트레이트의 것은 그 트레이트가 구현돼 있고 스코프에 있어야 쓸 수 있다". = note:: "다음 트레이트가 clone 이라는 것을 정의한다. 그것을 구현해야 할 수 있다". 그 아래에 후보 1번으로 Clone 을 적었습니다. 10부의 또 다른 E0599 는 구현은 있는데 use 가 빠진 때였고, help: 가 넣을 use 줄을 보였습니다. 여기에는 고친 줄을 보여 주는 help: 가 없습니다.
처방 — = note: 가 댄 Clone 을 구조체에 구현합니다. 10부에서 본 대로 derive 로 붙습니다. 고친 파일은 맨 위에 #[derive(Clone)] 한 줄이 더해진 것만 다릅니다. 그래서 틀린 파일의 8번 줄이 고친 파일에서는 9번 줄입니다. 화면의 2 와 4 는 a 와 b 의 같은 필드끼리 더한 값입니다. 복제한 뒤에도 a 를 읽었습니다.

트레이트를 구현하며 메서드 이름을 틀렸다 — E0407

10부에서 본 기본 구현을 내 타입에 맞게 덮어쓰려다 메서드 이름의 철자를 틀릴 때 만납니다.

읽는 법 — 오류 첫 줄은 "메서드 helo 는 트레이트 Greet 의 것이 아니다" 입니다. 밑줄은 10번부터 12번 줄까지의 메서드 전체를 묶었고, 끝에 "Greet 의 것이 아니다(not a member)" 가 붙었습니다. 10번 줄의 helo 아래에는 help: 가 바로 붙어 있습니다. "비슷한 이름의 연관 함수가 있다: hello". 고친 줄을 따로 보여 주는 help: 는 없습니다. 2번 줄의 hello 에는 본문이 있습니다. 10부의 빠뜨린 것이 있다는 E0046 은 이 화면에 없습니다.
처방 — help: 가 보인 이름이 덮어쓰려던 메서드인지 트레이트의 정의와 맞춰 보고 고칩니다. 여기서는 2번 줄의 hello 입니다. 고친 파일은 10번 줄만 다릅니다. 화면의 야옹 은 11번 줄의 것이고, 3번 줄의 안녕 이 아닙니다. 16번 줄의 호출이 Cat 의 구현으로 갔습니다.

Add 를 구현하며 오른쪽 값을 참조로 받았다 — E0053

내 타입에 + 를 붙이면서, 함수를 쓸 때 하던 대로 둘째 매개변수를 & 로 받게 적을 때 만납니다.

읽는 법 — 오류 첫 줄은 "메서드 add 의 타입이 트레이트와 맞지 않다" 입니다. 7번 줄의 &Won 에 "Won 을 기대했는데 &Won 이 왔다" 가 붙었습니다. = note: 는 두 시그니처를 위아래로 적습니다. 기대한 것은 fn(Won, Won) -> Won, 적은 것은 fn(Won, &Won) -> Won 입니다. help: 는 "매개변수의 타입을 트레이트에 맞게 바꾸라" 며 7번 줄에서 & 를 뗀 모습을 보입니다. - 줄이 지울 줄, + 줄이 넣을 줄입니다. 13번 줄의 Won(300) + Won(500) 은 짚이지 않았습니다.
처방 — 트레이트의 메서드는 트레이트가 정한 시그니처대로 구현합니다. 10부의 Add 를 구현하면 + 가 된다에서도 add 는 두 값을 & 없이 받았습니다. help: 를 그대로 따른 것이 고친 파일이고, 7번 줄만 다릅니다. 800 은 300 과 500 의 합입니다.

Iterator 를 구현하며 type Item 을 빠뜨렸다 — E0046

내 타입을 반복자로 만들면서 next 만 쓰고 type Item 줄을 빠뜨릴 때 만납니다.

읽는 법 — 10부에서 본 E0046 과 같은 번호이고 오류 첫 줄의 꼴도 같습니다(not all trait items implemented, missing: …). 그때 빠진 것은 메서드 name 이었고, 여기서는 Item 입니다. 3번 줄의 impl 에 "구현에 Item 이 빠졌다" 가 붙은 것도 그때와 같습니다. 그때는 트레이트를 정의한 줄에도 말이 붙었는데, 여기에는 없습니다. 이 파일에는 Iterator 의 정의가 없습니다. 그때 없던 것은 = help: 입니다. "빠진 것을 구현하라: type Item = /* Type */;". /* Type */ 은 3장의 화면에서 본 대로 타입을 적을 자리를 비워 둔 주석입니다. 그 줄을 글자 그대로 옮긴 파일은 "타입이 와야 하는데 ; 이 왔다" 는 번호 없는 오류로 막혔고, 그 뒤에 같은 E0046 이 Item 과 next 둘이 빠졌다며 다시 나왔습니다(싣지 않은 실행).
처방 — = help: 의 빈자리에 next 가 내줄 값의 타입을 적습니다. 12부의 내 타입을 반복자로 만든다가 구현할 것으로 든 둘 가운데 앞의 것이고, 10부의 연관 타입입니다. 고친 파일은 틀린 파일의 3번 줄 다음에 type Item = u32; 한 줄을 더한 것만 다릅니다. 화면의 [3, 2, 1] 은 collect 가 모은 값입니다.

derive 한 트레이트를 손으로 또 구현했다 — E0119

#[derive(Debug)] 를 붙여 둔 타입에, 찍히는 모양을 바꾸려고 impl fmt::Debug 를 손으로 쓸 때 만납니다.

읽는 법 — 19부에서 본 E0119 과 같은 번호이고 오류 첫 줄의 꼴도 같습니다. "타입 Won 에 트레이트 Debug 의 구현이 충돌한다". 붙은 말 둘도 그때의 것입니다. "첫 구현이 여기", "Won 에 충돌하는 구현". 그때는 두 말이 모두 impl 줄에 붙었습니다. 여기서 "충돌하는 구현" 이 붙은 곳은 3번 줄의 derive 괄호 안 Debug 이고, "첫 구현" 은 6번 줄의 impl 입니다. 파일에 적힌 차례와는 거꾸로 불렀습니다. 10부에서 본 대로 #[derive(Debug)] 가 만드는 것도 impl Debug for … 입니다. note: 도 help: 도 없습니다.
처방 — 한 타입에 한 트레이트의 구현은 하나만 둡니다. 손으로 쓴 쪽을 쓸 것이면 derive 를 지웁니다. 고친 파일은 틀린 파일의 3번 줄을 지운 것만 다릅니다. 그래서 그 아래의 줄은 번호가 하나씩 당겨졌습니다. 화면의 500원 은 손으로 쓴 fmt 가 만든 모양입니다. derive 가 만드는 모양은 7부의 구조체 찍어 보기에 있습니다.

dyn Iterator 에 Item 을 적지 않았다 — E0191

반복자를 Box 에 담아 돌려주면서 반환 타입을 Box<dyn Iterator> 까지만 적을 때 만납니다.

읽는 법 — 오류 첫 줄은 "Iterator 의 연관 타입 Item 의 값을 정해 줘야 한다" 입니다. 1번 줄의 Iterator 에 밑줄만 있고 붙은 말은 없습니다. help: 는 "연관 타입을 정해 주라" 며 Iterator 뒤에 <Item = /* Type */> 을 넣어 보입니다. /* Type */ 은 타입을 적을 자리입니다. 글자 그대로 옮긴 파일은 "= 오른쪽에 타입이 빠졌다" 는 번호 없는 오류로 막혔습니다(싣지 않은 실행). 6번 줄의 Vec<u32> 는 짚이지 않았습니다.
처방 — 빈자리에 그 반복자가 내주는 값의 타입을 적습니다. 10부에서 impl Iterator<Item = u32> 로 적던 자리이고, 고친 파일은 dyn 뒤에 같은 모양을 적었습니다. 1번 줄만 다릅니다. [2, 4, 6] 은 1 부터 3 까지를 두 배 한 값입니다. Item 이 무엇인지는 10부의 연관 타입에 있습니다.

dyn Trait 을 그대로 돌려주려 했다 — E0746 · E0277

돌려주는 값의 타입을 감추려고 반환 타입에 dyn Display 를 그대로 적을 때 만납니다. 실수는 3번 줄 한 곳인데 오류는 둘입니다.

읽는 법 — 첫째 오류 E0746 이 실수한 자리를 짚습니다. 오류 첫 줄은 "반환 타입은 포인터를 거치지 않은 트레이트 객체일 수 없다" 이고, 3번 줄의 dyn Display 에 "컴파일할 때 크기를 알 수 없다" 가 붙었습니다. help: 는 둘입니다. 첫째는 "dyn Trait 대신 impl Trait 을 돌려주라" 며 3번 줄을 고쳐 보입니다. 둘째는 "아니면 반환 타입을 상자에 담고, 돌려주는 값을 모두 Box::new 로 싸라" 며 3번 · 4번 두 줄을 고쳐 보입니다. 둘째 오류 E0277 은 10부의 dyn 은 포인터 뒤에만 둘 수 있다와 오류 첫 줄의 꼴이 같고, 함수를 부른 8번 줄을 짚습니다. = help: 의 트레이트는 그때처럼 Sized 입니다. 3번 줄에 dyn Display 라고 적은 타입을 이 오류는 (dyn std::fmt::Display + 'static) 이라고 적었습니다. + 'static 은 4장의 화면이 적지 않아도 붙는다고 한 조건입니다. = note: 는 그때의 "지역 변수는" 대신 "함수의 반환 타입은 크기가 정해져 있어야 한다" 입니다. 8번 줄의 .to_string() 은 오류가 둘에서 그치게 하려고 둔 호출입니다. 그것을 뺀 파일은 같은 자리에 E0277 을 하나 더 냈습니다(싣지 않은 실행). 번호가 둘이라 끝의 안내도 두 번호를 모아 적었습니다.
처방 — 돌려주는 타입이 한 가지이면 첫 help: 의 -> impl Trait 입니다. 그대로 따른 것이 고친 파일이고, 3번 줄만 다릅니다. 한 줄을 고치자 두 오류가 함께 사라졌습니다. 둘째 help: 를 그대로 따른 파일도 컴파일되어 같은 42 를 찍었습니다(싣지 않은 실행). 갈래에 따라 String 이나 u32 를 돌려주는 함수에 같은 실수를 한 파일에서는, 첫 help: 를 따른 쪽이 10부의 E0308 로 막혔고 둘째 help: 를 따른 쪽이 컴파일됐습니다(싣지 않은 실행). 그 Box<dyn Trait> 는 14부에서 봤습니다.

상자에 든 클로저를 새 스레드로 넘겼다 — E0277

12부에서 본 Box<dyn Fn> 꼴로 적어 둔 일감을 thread::spawn 에 넘겨 돌릴 때 만납니다. 화면 끝의 help: 는 다른 이야기를 합니다.

읽는 법 — 19부에서 본 E0277 과 오류 첫 줄의 꼴이 같습니다(… cannot be sent between threads safely). = help: 의 타입은 dyn Fn() -> u32, 트레이트는 Send 입니다. 19부의 슬라이드는 화면을 그 줄까지만 실었고, 그 아래의 사슬은 24부의 상자에 든 저장소를 스레드로 보내려던 화면에서 한 번 읽었습니다. 여기서도 같은 차례입니다. = note:: "std::ptr::Unique<…> 가 Send 가 되려면 그것이 필요하다". 이어서 note: 가 셋입니다. "그것이 Box<dyn Fn() -> u32> 타입 안에 들어 있어서", "그것이 이 클로저 안에서 쓰여서"(5번 줄의 move ||), "spawn 에 걸린 조건이라서". 두 /rustc/… 줄은 이 툴체인의 표준 라이브러리 소스에서 Box 와 spawn 이 적힌 자리입니다. 뒤의 두 note: 는 15부의 Rc 화면에도 있던 것입니다. 마지막 help: 는 "이 트레이트 객체를 부르려면 괄호를 쓰라" 며 클로저를 괄호로 싸고 () 를 붙여 보입니다. 그대로 따른 파일은 다른 E0277 로 막혔습니다. "FnOnce() 클로저를 기대했는데 u32 가 왔다" 입니다(싣지 않은 실행).
처방 — = help: 가 댄 타입과 트레이트에서 시작합니다. dyn Fn() -> u32 가 Send 가 아니라는 것이고, 그 타입을 적은 곳은 4번 줄입니다. 19부에서 본 대로 스레드로 보낼 트레이트 객체에는 + Send 를 적습니다. 처방은 그때와 같고, 고친 파일은 4번 줄만 다릅니다. 42 는 새 스레드가 계산해 join 이 돌려준 값입니다.

문자열을 match 로 가르며 나머지 갈래를 두지 않았다 — E0004

문자열을 match 로 가르면서, 올 수 있는 값을 다 적었다고 보고 _ 갈래를 두지 않을 때 만납니다.

읽는 법 — 4부에서 본 E0004 와 같은 번호이고 오류 첫 줄의 꼴도 같습니다(non-exhaustive patterns: … not covered). 그때 빠졌다고 한 것은 정수의 두 범위였고, 여기서는 &_ 입니다. 4부에서 "나머지 전부" 로 읽은 _ 앞에 & 가 붙은 패턴입니다. 첫 = note: 는 그때도 있던 줄로, 가르는 값의 타입이 &str 이라는 것입니다. 둘째 = note: 는 그때 없던 말입니다. "&str 은 빠짐없이 가를 수 없으므로 무엇이든 받는 _(wildcard) 가 꼭 있어야 한다". help: 는 4부의 슬라이드가 싣지 않은 부분입니다. "무엇이든 받는 패턴이나 아래에 보인 패턴으로 갈래를 더해 모든 경우를 다루라" 며 4번 줄 아래에 &_ => todo!(), 를 넣어 보입니다. 줄 번호 옆에 ~ 가 붙은 두 줄이 고친 모습입니다. 그대로 옮긴 파일은 컴파일되어 3000 4500 을 찍은 뒤, 10번 줄의 price("xl") 에서 todo!() 가 패닉해 종료 코드 101 로 끝났습니다(싣지 않은 실행).
처방 — 둘째 = note: 대로 _ 갈래를 둡니다. 그 갈래가 낼 값은 함수의 뜻이 정합니다. 여기서는 모르는 크기에 0 을 냈습니다. 고친 파일은 틀린 파일의 4번 줄 다음에 _ => 0, 한 줄을 더한 것만 다릅니다. 화면의 0 이 price("xl") 가 그 갈래에서 받은 값입니다.

String 을 문자열 리터럴 패턴으로 갈랐다 — E0308

String 인 값을 match 에 넣고 갈래에 문자열 리터럴을 적을 때 만납니다.

읽는 법 — 5부에서 읽은 E0308 입니다. 2장의 String 자리에 문자열 리터럴을 넘겼다와는 붙은 말까지 같습니다. "String 을 기대했는데 &str 이 왔다". 그때 그 말이 붙은 곳은 함수의 인자였고, 여기서는 4번 줄의 패턴 "가람" 입니다. 3번 줄의 name 에는 "이 식의 타입이 String 이다" 가 붙었습니다. 그때 있던 note: 는 없습니다. help: 는 그때와 방향이 반대입니다. 그때는 리터럴에 .to_string() 을 붙여 String 을 만들라고 했고, 여기서는 ".as_str() 로 String 을 &str 로 바꾸라" 며 3번 줄의 name 뒤에 붙여 보입니다. 5번 줄의 _ 갈래는 짚이지 않았습니다.
처방 — 가르는 값을 패턴과 같은 &str 로 바꿉니다. as_str() 은 8부의 문자열 타입은 둘의 표에서 String 에서 &str 로 가는 쪽에 있던 메서드입니다. help: 를 그대로 따른 것이 고친 파일이고, 3번 줄만 다릅니다. 1 은 4번 줄의 갈래가 낸 값입니다.

for 의 자리에 Some(…) 패턴을 적었다 — E0005

Option 이 든 배열을 돌면서, 값이 있는 칸만 받으려고 for 바로 뒤에 Some(score) 를 적을 때 만납니다.

읽는 법 — 7부에서 본 E0005 와 같은 번호입니다. 그때의 오류 첫 줄은 "refutable pattern in local binding", 곧 let 의 자리였고, 여기서는 "for 반복문의 자리에 안 맞을 수 있는 패턴" 입니다. 4번 줄의 Some(score) 에 "패턴 None 을 다루지 않았다" 가 붙은 것은 그때와 같습니다. = note: 는 하나뿐이고, 가르는 값의 타입이 Option<i32> 라는 것입니다. 그때 있던 나머지 두 = note:, 곧 let 이 반드시 맞는 패턴을 요구한다는 말과 문서의 주소는 없습니다. let … else 를 권하던 help: 도 없습니다. 7부의 그 슬라이드의 표는 let · 매개변수 · for 가 반드시 맞는 패턴만 받는다고 했습니다. 그 가운데 for 쪽의 화면입니다.
처방 — for 의 자리에는 반드시 맞는 패턴을 두고, 안 맞을 수 있는 패턴은 몸통 안의 if let 으로 옮깁니다. 고친 파일은 틀린 파일의 4번부터 6번 줄까지가 4번부터 8번 줄까지의 다섯 줄로 바뀐 것만 다릅니다. for 는 칸을 item 으로 통째로 받고, if let 이 Some 인 칸의 값만 더합니다. 155 는 70 과 85 의 합입니다.

변형에 든 값의 수와 패턴에 적은 수가 다르다 — E0023

값을 둘 담은 변형을 match 로 가르면서 패턴의 괄호 안에 이름을 하나만 적을 때 만납니다.

읽는 법 — 오류 첫 줄은 "이 패턴은 필드(field)가 하나인데, 맞대는 튜플 변형은 필드가 둘이다" 입니다. 화면은 괄호 안의 값 하나하나를 필드라고 부릅니다. 2번 줄의 두 i32 아래에 "튜플 변형의 필드는 둘", 9번 줄의 x 에 "둘을 기대했는데 하나가 왔다" 가 붙었습니다. help: 는 "_ 로 필드마다 무시한다는 것을 드러내라" 며 9번 줄의 x 뒤에 , _ 를 넣어 보입니다. 그대로 옮긴 파일은 오류 없이 컴파일됐지만 경고가 하나 붙었습니다. 2번 줄의 둘째 필드를 읽는 곳이 없다는 것입니다(싣지 않은 실행).
처방 — 빠진 값을 쓸 것인지부터 정합니다. 쓸 것이면 이름을 붙여 받고, 쓰지 않을 것이면 7부에서 본 대로 _ 로 자리 하나를 건너뜁니다. 고친 파일은 9번 줄만 다릅니다. 둘째 값을 y 로 받아 함께 찍었습니다. 화면의 3, 4 만큼 이 그 줄이고, 멈춤 은 10번 줄의 갈래입니다. 변형이 값을 담는 모양은 7부의 변형마다 다른 데이터를 가진다에 있습니다.

필드에 이름이 있는 구조체를 괄호로 풀었다 — E0532

구조체를 let 으로 풀어 헤치면서, 중괄호로 정의한 구조체를 튜플 구조체처럼 괄호로 적을 때 만납니다.

읽는 법 — 오류 첫 줄은 "이 스코프에서 Circle 이라는 튜플 구조체나 튜플 변형을 찾을 수 없다" 입니다. 1번부터 3번 줄까지를 묶어 "Circle 은 여기 정의돼 있다" 고 짚고, 7번 줄의 Circle(r) 에는 help: 가 바로 붙어 있습니다. "구조체 패턴 문법을 쓰라: Circle { r }". = note: 는 "Circle 이라는 구조체가 다른 이름 공간에 있다" 입니다. 다른 이름 공간이라는 말은 3장의 화면에도 나왔습니다. 이름은 있는데, 괄호로 적은 패턴이 찾는 종류의 것이 아니라는 말로 읽습니다. 고친 줄을 따로 보여 주는 help: 는 없습니다.
처방 — 패턴은 그 타입을 정의한 모양대로 적습니다. 중괄호로 정의한 구조체는 7부의 let 의 왼쪽은 패턴이다에서 본 대로 중괄호로 풉니다. help: 가 적은 패턴을 그대로 옮긴 것이 고친 파일이고, 7번 줄만 다릅니다. 12 는 3.0 에 2.0 을 두 번 곱한 값입니다.

구조체 패턴에 필드 하나를 적지 않았다 — E0027

구조체에서 필요한 필드만 꺼내려고 패턴에 그 이름들만 적을 때 만납니다.

읽는 법 — 오류 첫 줄은 "패턴이 필드 d 를 말하지 않는다" 입니다. 10번 줄의 패턴 전체에 "필드 d 가 빠졌다" 가 붙었습니다. help: 는 셋이고, 모두 10번 줄을 고쳐 보입니다. 첫째: 빠진 필드를 패턴에 넣는다. 둘째: 그 필드에 관심이 없으면 d: _ 로 드러내 놓고 무시한다. 셋째: 아니면 .. 으로 빠진 필드를 언제나 무시한다. 첫째를 그대로 옮긴 파일은 컴파일은 됐지만 d 를 쓰지 않는다는 경고가 붙었고, 그 경고의 help: 가 둘째 모양을 권했습니다. 둘째를 옮긴 파일은 경고 없이 고친 파일과 같은 화면을 찍었습니다(둘 다 싣지 않은 실행). 9번 줄은 고친 파일에 d 를 읽는 곳이 하나 있게 하려고 둔 줄입니다. 그 줄을 뺀 고친 파일에는 읽지 않는 필드가 있다는 경고가 붙었습니다(싣지 않은 실행).
처방 — 쓰지 않을 필드는 7부에서 본 .. 으로 건너뜁니다. 셋째 help: 를 그대로 따른 것이 고친 파일이고, 10번 줄만 다릅니다. 깊이 5 는 9번 줄이 패턴과 상관없이 읽은 값이고, 바닥 12 는 꺼낸 두 필드의 곱입니다.

벡터를 배열 패턴으로 풀었다 — E0529

원소가 둘인 벡터를 배열에서 하던 대로 let [a, b] = … 로 풀 때 만납니다.

읽는 법 — 오류 첫 줄은 "배열이나 슬라이스를 기대했는데 Vec<{integer}> 가 왔다" 입니다. 3번 줄의 [a, b] 에 "이 패턴은 Vec<{integer}> 타입의 입력과 맞을 수 없다" 가 붙었습니다. help: 는 "여기서 슬라이스로 만들어 보라" 며 pair 뒤에 [..] 를 붙여 보입니다. 그대로 옮긴 파일은 다른 오류로 막혔습니다. 7부에서 본 E0005 입니다. 그 슬라이드의 표에서 슬라이스에 댄 [a, b] 는 안 맞을 수 있는 패턴 쪽에 있었고, 이 실행의 화면은 다루지 않은 패턴으로 [], [_], [_, _, _, ..] 셋을 댔습니다(싣지 않은 실행).
처방 — help: 대로 슬라이스로 만들되, 안 맞을 수 있는 패턴을 받는 자리로 옮깁니다. 7부의 if let 입니다. 고친 파일은 틀린 파일의 3번 · 4번 두 줄이 3번부터 5번 줄까지의 세 줄로 바뀐 것만 다릅니다. 3번 줄이 if let 이 되고 4번 줄이 그 몸통으로 들어갔습니다. 7 은 3 과 4 의 합입니다. 길이가 정해진 것이면 배열로 두는 길도 있습니다. 2번 줄만 [3, 4] 로 바꾼 파일은 3번 줄이 그대로인데 컴파일되어 같은 7 을 찍었습니다(싣지 않은 실행). 슬라이스를 길이로 가르는 패턴은 7부의 슬라이스 패턴에 있습니다.

대입의 왼쪽에 값을 적었다 — E0070

10 = limit 처럼 대입의 좌우를 바꿔 적을 때 만납니다.

읽는 법 — 오류 첫 줄은 "대입의 왼쪽이 올바르지 않다" 입니다. 4번 줄의 10 에 "이 식에는 대입할 수 없다" 가 붙었고, ^ 는 = 를 짚습니다. note: 도 help: 도 없어서, 좌우를 바꾸라는 말은 화면에 없습니다. width * height = area 처럼 왼쪽에 계산식을 둔 파일도 같은 번호와 같은 두 말을 받았습니다(싣지 않은 실행).
처방 — 대입은 왼쪽에 값을 받을 변수를, 오른쪽에 넣을 값을 적습니다. 3부의 바꿀 변수에는 mut 를 붙인다에서 값을 다시 넣던 모양입니다. 고친 파일은 4번 줄만 다릅니다. 화면의 5 는 3번 줄이, 10 은 대입 뒤의 5번 줄이 찍었습니다.

수를 as 로 bool 로 바꾸려 했다 — E0054

0 과 1 로 적어 둔 값을 as bool 로 참 · 거짓으로 바꿀 때 만납니다. 3부에서 본 불을 수로 바꾸는 as 의 반대 방향입니다.

읽는 법 — 오류 첫 줄은 "i32 를 bool 로 형변환할 수 없다" 입니다. 3번 줄의 flag as bool 전체에 밑줄만 있고 붙은 말은 없습니다. help: 는 "대신 0 과 견주라" 며 3번 줄을 고쳐 보입니다. - 줄이 지울 줄, + 줄이 넣을 줄입니다. as 가 막히는 화면은 2장의 E0606 에서도 봤고, 번호가 다릅니다. u32 를 as char 로 바꾸려 한 파일은 또 다른 번호 E0604 를 받았습니다. 그 help: 가 권한 것은 3부에서 본 char::from_u32 였고, 글자 그대로 옮긴 파일은 그 결과인 Option<char> 를 {} 로 찍을 수 없다는 E0277 로 막혔습니다(싣지 않은 실행).
처방 — 참 · 거짓은 형변환이 아니라 견주는 식으로 만듭니다. 3부의 bool 에서 본 대로 값을 견주는 식이 bool 을 냅니다. help: 를 그대로 따른 것이 고친 파일이고, 3번 줄만 다릅니다. true 는 1 이 0 과 다르다는 것입니다.

const 에 String 을 만들어 넣으려 했다 — E0015

여러 곳에서 쓸 글을 상수로 빼면서, 타입을 String 으로 적고 String::from 으로 값을 만들 때 만납니다.

읽는 법 — 5부에서 본 E0015 와 같은 번호입니다. 그때의 오류 첫 줄은 "const 가 아닌 함수 kib 를 상수에서 부를 수 없다" 였고, 여기서는 함수 자리에 "연관 함수 <String as From<&str>>::from" 이 왔습니다. 1번 줄의 String::from 을 컴파일러가 적은 이름입니다. 꺾쇠로 감싼 이 표기는 이 책에서 다루지 않고, 10부에서 본 대로 String::from 은 From 트레이트의 것이라는 데까지만 읽습니다. 밑줄은 1번 줄의 호출 전체에 있습니다. = note: 는 그때와 같은 문장입니다. "상수 안의 호출은 const 함수, 튜플 구조체, 튜플 변형으로 제한된다". 그때는 note: 가 kib 의 정의를 짚으며 const 가 아니라고 했는데, 여기에는 그 줄이 없습니다. help: 도 없습니다.
처방 — 상수에는 3부에서 본 대로 컴파일할 때 계산할 수 있는 식만 둡니다. 글이라면 문자열 리터럴이고, 그 타입은 &str 입니다. 고친 파일은 1번 줄만 다릅니다. 타입이 &str 이 되고 값이 리터럴이 됐습니다. 4번 줄은 그대로인데 같은 글을 찍었습니다.

main 이 정수를 돌려주게 적었다 — E0277

main 의 끝에서 0 을 돌려주려고 반환 타입을 i32 로 적을 때 만납니다.

읽는 법 — 오류 첫 줄은 "main 의 반환 타입 i32 가 올바르지 않다" 입니다. 번호는 E0277 이고, 10부의 E0277 의 문장에 들어갈 타입과 트레이트는 1번 줄에 붙은 말에 있습니다. "main 은 Termination 을 구현한 타입만 돌려줄 수 있다". 타입은 i32, 트레이트는 Termination 입니다. Termination 은 이 책에서 다루지 않는 이름입니다. = help: 는 대신 쓸 것 둘을 댑니다. "() 나 Result 를 써 보라". 고친 줄을 보여 주는 help: 는 없습니다. 3번 줄의 0 은 짚이지 않았습니다.
처방 — = help: 의 두 길 가운데 고릅니다. 돌려줄 것이 없으면 5부에서 본 대로 반환 타입을 적지 않습니다. 고친 파일이 그쪽입니다. 1번 줄에서 -> i32 를 지우고, 틀린 파일의 3번 줄 0 을 지웠습니다. 실패를 알릴 main 은 9부의 Result 를 돌려주는 main 입니다. 반환 타입을 Result<(), String> 으로, 3번 줄을 Ok(()) 로 바꾼 파일도 같은 끝 을 찍었습니다(싣지 않은 실행).

for_each 의 클로저 안에서 break 를 썼다 — E0267

for 로 쓰던 반복을 12부의 for_each 로 옮기면서 몸통의 break 를 그대로 둘 때 만납니다.

읽는 법 — 오류 첫 줄은 "클로저 안의 break" 입니다. 4번 줄의 |s| 에 "둘러싼 클로저(enclosing closure)", 6번 줄의 break 에 "클로저 안에서는 break 할 수 없다" 가 붙었습니다. note: 도 help: 도 없습니다. 6번 줄의 break 를 return 으로 바꾼 파일은 컴파일됐지만 245 를 찍었습니다. 40 만 뺀 세 수의 합입니다(싣지 않은 실행).
처방 — 12부의 그 슬라이드가 적은 대로, break 가 필요하면 for 입니다. 고친 파일은 4번 · 9번 두 줄이 다릅니다. 4번 줄이 for s in scores.iter() 가 되고 9번 줄의 }); 가 } 가 됐습니다. 5번부터 8번 줄까지의 몸통은 그대로입니다. 155 는 40 을 만나기 전의 70 과 85 의 합입니다. break 가 끝내는 것은 4부에서 본 대로 반복문입니다.
