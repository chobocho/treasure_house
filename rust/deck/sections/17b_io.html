fs::write — 한 번에 쓰고, 있던 내용은 바꾼다

3장의 fs::read_to_string 이 파일을 통째로 읽었듯이, fs::write 는 경로와 내용을 받아 통째로 씁니다. 같은 파일에 두 번 쓰고 그때마다 되읽어 봅니다.

읽는 법 — 6번 줄을 돌릴 때 memo.txt 는 없었습니다. fs::write 가 파일을 만들었고 7번 줄이 그 내용을 찍었습니다. 10번 줄이 같은 파일에 다시 쓴 뒤에는 11번 줄이 "빵\n" 만 찍었습니다. 처음 쓴 두 줄은 남아 있지 않습니다. 14번 줄은 글이 아닌 바이트 셋을 썼고, 3장의 fs::read 가 같은 셋을 돌려줬습니다.
덧붙이지 않는다 — fs::write 는 있던 내용을 새 내용으로 바꿉니다. 끝에 붙이는 길은 이 장의 덧붙이기에서 봅니다.

File::create — 파일도 Write 다

내용을 미리 String 하나로 만들어 두지 않고 조금씩 쓰려면 파일을 열어 둡니다. File::create 는 쓰려고 연 File 을 돌려줍니다. 1장에서 Vec<u8> 가 Write 였듯이 File 도 Write 라서, writeln! 의 첫 인자 자리에 놓습니다.

읽는 법 — 8번과 10번 줄의 writeln! 은 화면에 아무것도 찍지 않았습니다. 화면에 나온 것은 12번 줄의 memo.txt 에 썼다 뿐이고, 쓴 세 줄은 cat 이 파일에서 보여 줍니다. 서식은 println! 과 같아서 8번 줄의 {} 자리에 2 가 들어갔습니다.
let mut file — 3장에서 읽을 때 그랬듯이 쓸 때도 file 을 가변으로 빌립니다.

File::create 는 여는 순간 파일을 비운다

이름이 "만든다" 이지만, 있는 파일에 부르면 있던 내용이 사라집니다. 25 바이트짜리 파일을 File::create 로 열기만 하고 아무것도 쓰지 않았습니다.

읽으려면 File::open — 9번 줄은 한 글자도 쓰지 않았는데 10번 줄이 0 바이트를 찍었습니다. File::create 는 fs::write 처럼 있던 내용을 버리고 시작합니다. 읽을 파일을 여는 것은 3장의 File::open 입니다.

같은 함수가 화면에도 파일에도 쓴다

3장에서 읽는 함수가 impl BufRead 를 받았듯이, 쓰는 함수는 &mut impl Write 를 받습니다. 표를 쓰는 report 는 어디에 쓰는지 모릅니다. 칸을 맞추는 서식은 2부의 폭과 정렬, 정밀도 그대로입니다.

읽는 법 — 20번 줄은 report 에 표준 출력의 손잡이를 넘겨서 표가 화면에 나왔습니다. 23번 줄은 같은 함수에 File 을 넘겼고, cat 이 보여 준 scores.txt 의 다섯 줄이 화면의 다섯 줄과 같습니다. {name:<6} 이 이름을 왼쪽에, {score:>6} 이 점수를 오른쪽에 맞췄고, {mean:>6.1} 이 평균을 소수 한 자리로 찍었습니다.
어디에 쓸지는 부르는 쪽이 정한다 — 쓰는 함수가 Write 를 받으면 화면에도 파일에도 쓰입니다. 6장에서는 같은 자리에 Vec<u8> 를 넘겨 함수를 시험합니다.

OpenOptions — 있던 내용 끝에 덧붙인다

기록 파일은 돌릴 때마다 한 줄씩 늘어나야 합니다. 있던 내용을 두고 끝에 쓰는 것이 덧붙이기(append)입니다. fs::write 와 File::create 는 있던 내용을 버리므로 쓸 수 없습니다. OpenOptions 는 파일을 어떻게 열지를 하나씩 켜는 타입입니다. 조건을 이어 적고 마지막에 open 을 부릅니다.

읽는 법 — 처음 돌릴 때는 log.txt 가 없었습니다. 9번 줄의 create(true) 가 파일을 만들게 했고, cat 이 시작 한 줄을 보여 줍니다. 두 번 더 돌린 뒤에는 세 줄입니다. 돌릴 때마다 파일을 새로 열었는데도 앞서 쓴 줄이 남았고, 새 줄은 그 뒤에 붙었습니다. 10번 줄의 append(true) 로 연 결과입니다.
6번 줄 — 명령 줄 인자의 1번을 꺼내고, 없으면 9부의 unwrap_or_default 로 빈 문자열을 씁니다.

여는 조건이 없는 파일과 있는 파일을 가른다

조건 셋을 견줍니다. append 만 켠 것, create 를 함께 켠 것, 그리고 "새 파일일 때만" 을 뜻하는 create_new 입니다. 조건마다 없는 파일에 한 번, 있는 파일에 한 번 열어 보고 결과만 찍습니다.

  • append — 없는 파일은 만들지 않습니다. 3장에서 본 NotFound 가 돌아왔습니다.
  • append+create — 없으면 만들고 있으면 엽니다. 앞 슬라이드의 조건입니다.
  • create_new — 없으면 만들고, 있으면 열지 않고 AlreadyExists 로 실패합니다.
덮어쓰면 안 되는 파일 — create_new 로 엽니다. 30번 줄의 File::create_new 는 15번 줄의 조건을 줄인 이름입니다. 25번 줄이 이미 만든 append.txt 에 불렀더니 같은 AlreadyExists 가 나왔습니다.

BufWriter — 받은 글을 모아 두었다가 쓴다

3장의 BufReader 가 읽는 쪽의 버퍼였다면 BufWriter 는 쓰는 쪽의 버퍼입니다. File 을 감싸 Write 로 쓰는 것은 같은데, 쓴 글이 파일에 들어가는 때가 다릅니다. 한 줄을 쓰고 곧바로 파일의 크기를 재 봅니다.

읽는 법 — 12번 줄이 File 에 쓴 한 줄은 13번 줄에서 이미 파일에 8 바이트로 들어 있습니다. 17번 줄이 BufWriter 에 쓴 같은 한 줄은 18번 줄에서 재니 0 바이트입니다. 19번 줄의 flush 뒤에야 8 바이트가 됐습니다.
쓴 것과 파일에 든 것은 다를 수 있다 — BufWriter 에 쓴 글은 버퍼에 머뭅니다. 1장에서 표준 출력이 줄이 끝날 때까지 모아 둔 것과 같은 일이고, 내보내는 메서드도 같은 flush 입니다.

BufWriter 가 줄이는 것은 쓰기 횟수다

모아서 무엇이 달라지는지 세어 봅니다. Counter 는 Write 를 직접 구현한 타입입니다. 받은 바이트는 버리고 write 가 몇 번 불렸는지만 셉니다. 같은 천 줄을 한 번은 바로, 한 번은 BufWriter 로 감싸서 씁니다.

읽는 법 — 바로 쓰면 write 가 2000 번, 한 줄에 두 번씩 불렸습니다. BufWriter 를 거치면 같은 10893 바이트가 두 번에 건너갔습니다. 35번 줄이 찍은 flush 전 1 번 은 36번 줄의 flush 를 부르기 전에 이미 한 번 내보냈다는 뜻입니다. 버퍼가 차면 flush 없이도 나갑니다.
9번부터 18번 줄까지 — Write 를 구현하려면 write 와 flush 둘을 채웁니다. writeln! 과 BufWriter 는 그 둘만으로 일합니다. 이 화면이 보여 주는 것은 횟수뿐입니다. 표준 라이브러리 문서는 쓰기 한 번이 운영 체제를 한 번 부르는 일일 수 있다는 것을 BufWriter 를 두는 까닭으로 듭니다.

정리될 때 버퍼에 남은 글을 내보낸다

flush 를 부르지 않으면 버퍼에 남은 글은 어떻게 되는지 봅니다. 한 번은 drop 으로 일찍 정리하고, 한 번은 블록이 끝나 스코프를 벗어나게 둡니다.

읽는 법 — 11번 줄에서는 0 바이트였던 a.txt 가 13번 줄의 drop(out) 뒤에 8 바이트가 됐습니다. b.txt 는 20번 줄에서 블록이 끝난 뒤에 재니 두 줄, 19 바이트가 다 들어 있습니다.
그래도 flush 를 부르는 까닭 — BufWriter 는 정리될 때 남은 글을 내보냅니다. 그 내보내기가 실패하면 어떻게 되는지, 정리가 아예 돌지 않으면 어떻게 되는지를 다음 두 슬라이드에서 봅니다.

정리될 때의 실패는 돌아올 곳이 없다

쓰기가 늘 실패하는 Full 을 만들어 BufWriter 로 감쌉니다. io::Error::other 는 글 하나로 io::Error 를 만듭니다. BufWriter 에는 &mut disk 를 넘겼습니다. 가변 참조도 Write 라서 되고, 덕분에 정리된 뒤에 disk 를 들여다볼 수 있습니다.

읽는 법 — 23번 줄의 writeln! 은 Ok(()) 입니다. 버퍼에 담았을 뿐이기 때문입니다. 24번 줄에서 out 이 정리된 뒤 25번 줄이 찍은 쓰기 시도는 1 번입니다. 정리하면서 쓰려 했고 그 쓰기는 실패했는데, 화면에는 오류도 패닉도 없습니다. 같은 일을 30번 줄처럼 flush 로 직접 시키면 실패가 Err(Custom { kind: Other, error: "가득 찼다" }) 로 돌아옵니다.
다 쓰고 나면 flush 를 직접 부른다 — 정리 때 불리는 drop 은 fn drop(&mut self), 곧 돌려주는 값이 없는 메서드라서 실패를 전할 자리가 없습니다. 쓴 글이 나갔는지를 Result 로 받으려면 flush 를 직접 부릅니다.

process::exit 는 버퍼에 남은 글을 버린다

1장에서 process::exit 는 정리를 거치지 않고 끝낸다는 것을 봤습니다. BufWriter 가 남은 글을 내보내는 때가 정리이므로, 이 둘이 만나면 글이 사라집니다.

파일은 있는데 비었다 — 8번 줄은 result.txt 에 썼다 를 찍었고 종료 코드도 0 입니다. 그런데 wc -c 가 센 바이트는 0 입니다. 6번 줄이 파일을 만들었지만, 7번 줄이 쓴 글은 버퍼에 있다가 10번 줄에서 프로그램과 함께 사라졌습니다.
고치려면 — 끝내기 전에 out.flush()? 를 부르고, 종료 코드는 1장의 ExitCode 처럼 main 의 반환값으로 정합니다.

쓴 것을 같은 프로그램에서 되읽는다

파일에 쓰는 까닭은 나중에 다시 읽기 위해서입니다. save 는 한 줄에 이름과 점수를 하나씩 쓰고, load 는 그 모양을 되읽어 같은 벡터를 만듭니다. 줄을 쪼개는 것은 8부의 split_once, 안 맞는 줄을 건너뛰는 것은 7부의 let … else 입니다.

읽는 법 — 31번 줄이 찍은 kim 90 · lee 85 가 파일에 든 글입니다. 33번 줄은 load 가 되읽은 벡터를 찍었고, 34번 줄이 쓴 것과 견줘 true 를 냈습니다. save 의 마지막 식인 11번 줄 out.flush() 가 io::Result<()> 를 그대로 돌려주므로, 쓰기가 끝까지 됐는지가 부른 쪽에 전해집니다.
말없이 건너뛴다 — 19번과 21번 줄의 continue 는 모양이 틀린 줄을 알리지 않고 넘어갑니다. 알리려면 2장에서 틀린 줄에 번호를 붙인 것처럼 오류로 돌려줍니다.

줄마다 읽어 줄마다 쓴다

읽는 쪽 impl BufRead 와 쓰는 쪽 &mut impl Write 를 한 함수에서 만나게 합니다. copy_lines 는 설정 파일에서 빈 줄과 # 으로 시작하는 줄을 빼고 옮깁니다.

읽는 법 — app.conf 의 다섯 줄 가운데 12번 줄의 조건에 걸리지 않은 두 줄만 clean.conf 에 들어갔고, 27번 줄이 그 수를 찍었습니다. lines() 는 줄바꿈을 떼고 주므로 16번 줄의 writeln! 이 다시 붙입니다. 다 쓴 뒤 26번 줄에서 flush 를 직접 불렀습니다.
뒤에서 — 읽을 곳과 쓸 곳을 인자로 받는 이 모양이 6장의 도구들의 뼈대입니다.

복사 · 이름 바꾸기 · 지우기

내용을 들여다볼 일이 없으면 파일을 통째로 다루는 함수를 씁니다. fs::copy 는 복사, fs::rename 은 이름 바꾸기, fs::remove_file 은 지우기입니다. 셋 다 io::Result 를 돌려줍니다.

읽는 법 — 8번 줄의 fs::copy 는 복사한 바이트 수 6 을 돌려줬고 b.txt 에 같은 글이 들었습니다. 13번 줄의 rename 뒤에는 옛 이름 b.txt 가 NotFound 이고 같은 글이 c.txt 에 있습니다. 18번 줄이 그것을 지웠고, 20번 줄에서 한 번 더 지우려 하니 NotFound 입니다. 원본 a.txt 는 끝까지 그대로입니다.

쓰려고 여는 다섯 가지 길

이 장에서 파일을 쓰려고 연 방법을 "파일이 없을 때" 와 "있을 때" 로 견준 표입니다. 파일이 이미 있을 때 무슨 일이 생겨야 하는지를 먼저 정하고, 오른쪽 칸에서 그 말을 찾습니다.

  • 쓰는 함수는 &mut impl Write 를 받습니다.

퀴즈 — 파일 쓰기

Q. File 을 BufWriter 로 감싸 writeln! 으로 한 줄을 쓰고, 곧바로 그 파일을 fs::read 로 읽었더니 0 바이트입니다. 왜일까요? flush 를 부르지 않고 두면 그 글은 언제 파일에 들어갈까요? 그때의 실패는 어떻게 알 수 있을까요?

A. BufWriter 가 쓴 글을 버퍼에 모아 두기 때문입니다(모아 두었다가 쓴다). flush 를 부르지 않아도 BufWriter 가 정리될 때 남은 글이 나갑니다(정리될 때). 다만 그때의 실패는 알 길이 없고(돌아올 곳이 없다), process::exit 로 끝내면 정리가 돌지 않아 글이 사라집니다(버퍼에 남은 글). 그래서 다 쓴 뒤 flush 를 직접 부르고 그 Result 를 받습니다.

Path 와 PathBuf — 빌린 경로와 가진 경로

3장에서 "경로는 5장에서 봅니다" 라고 미뤄 둔 이야기입니다. 지금까지 파일 이름은 "memo.txt" 같은 글이었습니다. 경로(path)를 다루는 타입은 std::path 의 Path 와 PathBuf 입니다. 8부의 &str 과 String 처럼 빌린 것과 가진 것의 짝입니다.

읽는 법 — 10번 줄의 Path::new 는 글을 경로로 보는 &Path 를 줍니다. 12번 줄의 PathBuf 는 13번과 14번 줄의 push 로 늘어나 notes/2026/plan.txt 가 됐습니다. 조각 사이의 / 는 push 가 넣었고, 이 기계의 구분자(separator)입니다. 21번 줄의 to_path_buf() 는 빌린 경로에서 가진 경로를 만들고, 22번 줄이 둘이 같다고 찍었습니다.
  • 18번 줄은 &PathBuf 를 &Path 를 받는 show 에 넘겼습니다. &String 이 &str 자리에 들어가는 것과 같은 역참조 강제입니다.
  • 5번 줄이 경로를 display() 를 거쳐 찍는 까닭은 이 장의 가운데에서 봅니다.

경로를 받는 함수는 AsRef<Path> 로 받는다

3장과 4장에서는 fs::read_to_string("memo.txt") 처럼 경로 자리에 글을 넘겼습니다. 10부에서 파일 함수는 경로를 AsRef<Path> 로 받는다고 한 대로입니다. 내 함수도 같은 모양으로 적으면 같은 인자를 받습니다.

읽는 법 — 6번 줄의 size 하나가 글과 경로, 빌린 것과 가진 것을 모두 받았고 여섯 번 다 6 을 냈습니다. 7번 줄은 받은 path 를 fs::read 에 그대로 넘깁니다. 17번과 20번 줄은 값을 통째로 넘겼으므로 name 과 buf 는 그 뒤로 쓸 수 없습니다(함수에 넘기면 옮겨 간다).
고르기 — 경로 하나를 읽기만 하는 함수는 앞 슬라이드의 show 처럼 &Path 로 받아도 됩니다. 부르는 쪽이 글도 경로도 넘기게 하려면 impl AsRef<Path> 입니다.

join 과 push — 구분자를 손으로 붙이지 않는다

디렉터리와 파일 이름을 이어 경로를 만듭니다. join 은 이은 결과를 새 PathBuf 로 돌려주고, push 는 가진 경로를 그 자리에서 늘립니다. pop 은 마지막 조각을 뗍니다.

읽는 법 — 6번과 7번 줄에서 join 을 불렀지만 8번 줄이 찍은 base 는 notes 그대로입니다. 7번 줄처럼 이어 부르면 조각이 차례로 붙습니다. 12번 줄은 앞쪽이 notes/ 로 끝나는데도 결과가 notes/memo.txt 입니다. 구분자가 겹치지 않았습니다. 16번 줄의 push 로 out/logs 가 됐다가 18번 줄의 pop 으로 out 으로 돌아왔습니다.
format! 으로 잇지 않는다 — format!("{dir}/{name}") 은 구분자를 손으로 적습니다. 조각을 잇는 일은 join 에 맡깁니다.

경로의 조각 — parent · file_name · file_stem · extension

경로에서 디렉터리 쪽, 파일 이름, 확장자(extension)를 뗀 이름, 확장자를 꺼냅니다. 넷 다 Option 을 돌려줍니다. 경로 넷에 같은 네 메서드를 불렀습니다.

  • 없을 수 있다 — notes 에는 확장자가 없어 extension 이 None 이고, .. 은 파일 이름이 아니라서 file_name 부터 None 입니다.
  • 확장자는 마지막 점 뒤 — backup.tar.gz 의 extension 은 gz 이고 file_stem 은 backup.tar 입니다.
  • 조각이 하나뿐이면 — parent 는 None 이 아니라 빈 경로 Some("") 입니다.
따옴표 안의 글 — String 처럼 찍혔지만 타입은 9번부터 12번 줄에 적은 대로입니다. parent 가 Option<&Path>, 나머지 셋이 Option<&OsStr> 입니다. OsStr 이 무엇인지는 경로는 String 이 아니다에서 봅니다.

조각 하나를 바꾼 경로, 조각으로 나눈 경로

with_extension 과 with_file_name 은 조각 하나만 바꾼 새 PathBuf 를 만듭니다. components 는 반대로 경로를 조각으로 나눠 차례로 내는 반복자입니다.

읽는 법 — 6번 줄은 확장자를 bak 으로 바꿨고, 7번 줄은 빈 글을 줘서 확장자를 뗐습니다. 8번 줄은 파일 이름을 통째로 바꿨습니다. 9번 줄이 찍은 src 는 그대로입니다. 13번 줄의 components 는 맨 앞의 . 을 CurDir, .. 을 ParentDir, 이름을 Normal 로 냈습니다. 겹쳐 적은 // 는 구분자 하나로 읽혔습니다.
글자만 다룬다 — notes/../notes 가 notes 로 줄지 않았습니다. ParentDir 조각이 그대로 나왔습니다. 여기까지 쓴 메서드는 적힌 글자를 나누고 이을 뿐입니다. 이 예제들이 도는 디렉터리에 notes 는 없는데도 결과가 나왔습니다. 그 자리에 무엇이 있는지 묻는 메서드는 뒤에서 따로 봅니다.

경로는 {} 로 찍히지 않는다 — E0277

이 장의 예제는 경로를 찍을 때마다 display() 를 거쳤습니다. 거치지 않고 {path} 로 찍어 봅니다.

읽는 법 — 2부에서 본 "Display 를 구현하지 않았다" 와 같은 E0277 입니다. 이번에 구현하지 않은 타입은 Path 입니다. 5번 줄에 붙은 말이 고칠 길을 알려 줍니다 — .display() 를 부르라는 것입니다. 첫 note: 가 까닭을 적었습니다. 경로에는 유니코드가 아닌 데이터가 들어 있을 수 있으니 .display() 나 .to_string_lossy() 로 찍으라고 합니다. 다음 note: 는 {:?} 로도 찍을 수 있다고 알려 줍니다.
고치려면 — 5번 줄을 println!("{}", path.display()); 로 적습니다. 이 장의 다른 예제가 모두 그 모양입니다.

경로는 String 이 아니다 — to_str 은 Option 을 준다

8부에서 본 대로 String 은 늘 UTF-8 입니다. 앞 슬라이드의 note: 는 경로에 유니코드가 아닌 데이터가 들어 있을 수 있다고 했습니다. 그래서 경로는 String 이 아니라 OsString 과 OsStr, 곧 운영 체제의 문자열 위에 서 있습니다. 이름 둘을 인자로 넘깁니다. 둘째는 printf 로 UTF-8 이 될 수 없는 바이트 \351 을 넣은 이름입니다.

읽는 법 — 메모.txt 는 to_str 이 Some("메모.txt") 를 줬습니다. 둘째 이름에서는 None 입니다. {:?} 는 문제의 바이트를 \xE9 로 적어 보여 줬고, display() 는 그 자리를 대체 글자(replacement character, 물음표가 든 마름모) 하나로 바꿔 찍었습니다. 3장에서 UTF-8 이 아닌 파일이 String 이 되지 못한 것과 같은 사정이 이름에도 있는 것입니다. 6번 줄의 env::args_os() 는 env::args() 의 짝으로, 인자를 String 이 아니라 OsString 으로 줍니다. 이 기계에서는 그 바이트가 프로그램까지 그대로 왔습니다.
찍을 때는 display, 글이 필요하면 to_str — display() 는 사람에게 보여 주는 용도이고, 위에서 보듯 글자를 잃을 수 있습니다. 글로 써야 하면 to_str() 의 Option 을 가릅니다. 파일을 여는 데는 경로를 그대로 넘깁니다.

있는가, 파일인가, 디렉터리인가

여기부터는 경로가 가리키는 자리를 파일 시스템에 묻습니다. exists · is_file · is_dir 은 bool 을 돌려줍니다. 파일 하나, 디렉터리 하나, 없는 이름 하나에 물었습니다.

읽는 법 — 6번 줄이 만든 memo.txt 는 is_file 만 참이고, 지금 디렉터리를 뜻하는 . 은 is_dir 만 참입니다. 없는 none.txt 에는 셋 다 false 입니다.
읽을 파일이면 묻지 않고 읽는다 — exists 가 참이어도 읽기는 실패할 수 있습니다. 여기서 exists 가 참인 . 을 3장에서는 IsADirectory 로 읽지 못했습니다. 읽을 것이라면 먼저 묻지 않고 바로 읽은 다음, 그때처럼 실패의 kind() 를 봅니다.

create_dir_all — 길에 있는 디렉터리를 모두 만든다

파일은 있는 디렉터리 안에만 쓸 수 있습니다. 디렉터리를 만드는 함수는 둘입니다. fs::create_dir 은 한 단만, fs::create_dir_all 은 길에 있는 것을 모두 만듭니다. 결과에서 오류의 종류만 찍습니다.

읽는 법 — 12번 줄의 fs::write 는 NotFound 입니다. 7번 줄의 join 은 경로 값을 만들었을 뿐 디렉터리를 만들지 않았습니다. 15번 줄의 create_dir 도 위쪽 data/2026 이 없어 NotFound 입니다. 19번 줄의 create_dir_all 이 세 단을 다 만들었고, 30번 줄에서 같은 쓰기가 됐습니다.
쓰기 전에 create_dir_all — 24번 줄처럼 이미 있는 디렉터리에 create_dir 을 부르면 AlreadyExists 이지만, 27번 줄의 create_dir_all 은 또 Ok(()) 입니다. 있는지 먼저 묻지 않고 불러도 됩니다.

read_dir — 디렉터리의 항목을 하나씩 낸다

fs::read_dir 은 디렉터리에 든 항목(entry)을 차례로 내는 반복자를 줍니다. 3장의 lines() 처럼 항목마다 io::Result 에 싸여 오고, 항목의 path() 가 그 경로를 PathBuf 로 줍니다. 예제에 딸린 notes 디렉터리를 봅니다.

읽는 법 — 나온 것은 notes 바로 아래의 셋입니다. notes/2026 안에 든 것은 나오지 않았습니다. read_dir 은 한 단만 봅니다. 15번 줄이 is_dir 로 디렉터리와 파일을 갈랐습니다.
찍기 전에 정렬한다 — 표준 라이브러리 문서는 항목이 나오는 순서가 플랫폼과 파일 시스템에 달려 있다고 적습니다. 그래서 10번 줄에서 모으고 13번 줄에서 정렬한 다음에 찍습니다. 이 책의 화면이 돌릴 때마다 같으려면 필요한 일이고, 사용자에게 보여 주는 목록도 마찬가지입니다.

metadata().len() — 파일의 크기를 묻는다

4장에서는 크기를 알려고 파일을 통째로 읽어 len() 을 셌습니다. fs::metadata 는 내용을 받아 오지 않고 파일에 대한 정보를 줍니다. 그 len() 이 바이트 수이고, 파일인지 묻는 is_file 도 여기에 있습니다.

읽는 법 — 11번 줄의 meta.len() 이 준 30 과 11 이 wc -c 가 센 수와 같고, 합계도 41 로 같습니다. 10번 줄의 is_file 이 디렉터리 notes/2026 을 뺐습니다. 14번 줄의 rows.sort() 는 튜플의 앞 칸인 경로부터 견주므로 경로 순서로 놓입니다.

디렉터리 안의 디렉터리까지 — 재귀로 훑는다

read_dir 은 한 단만 봅니다. 아래까지 보려면 디렉터리를 만날 때마다 같은 함수를 다시 부릅니다. 5부에서 본 재귀입니다. find_files 는 그렇게 모은 파일을 정렬한 벡터로 돌려줍니다.

remove_dir 은 빈 디렉터리만, remove_dir_all 은 통째로

디렉터리를 지우는 함수도 둘입니다. 안에 파일이 든 tmp 와 빈 empty 를 만들어 놓고 지워 봅니다.

퀴즈 — 경로와 디렉터리

Q. let log = Path::new("data/2026/10").join("log.txt"); 바로 다음 줄에서 fs::write(&log, "ok\n") 을 불렀습니다. data 디렉터리는 아직 없습니다. 결과는 무엇일까요? 어떻게 고칠까요?

A. Err 이고 종류는 NotFound 입니다. join 은 경로 값을 만들 뿐이고 디렉터리를 만들지 않습니다. join 은 글자만 다룹니다(글자만 다룬다). 쓰기 전에 fs::create_dir_all("data/2026/10") 을 부릅니다. 길에 있는 디렉터리를 모두 만들고, 이미 있어도 Ok(()) 입니다(create_dir_all).

cat — 한 파일이 실패해도 나머지는 찍는다

이 장에서는 익숙한 명령 셋을 줄여서 만듭니다. 첫째는 파일들을 차례로 표준 출력에 옮기는 cat 입니다. 옮기는 일은 io::copy 가 합니다. 4장의 copy_lines 처럼 읽을 곳과 쓸 곳을 받아, 끝까지 읽어 그대로 씁니다.

읽는 법 — 둘째 실행에서 one.txt 의 두 줄 다음에 19번 줄이 찍은 cat: none.txt: No such file or directory (os error 2) 가 나오고, 그 뒤에 two.txt 의 셋 이 이어졌습니다. 20번 줄은 실패를 적어 두기만 하고 반복을 계속합니다. 다 돈 뒤 23번 줄이 그것을 보고 종료 코드 1 을 냈습니다. 셋째 실행처럼 > all.txt 로 받으면 화면에는 알림만 남고, 파일에는 세 줄이 알림 없이 들어갑니다.
이름은 아는 쪽이 붙인다 — 7번 줄의 cat 은 io::Result 만 돌려줍니다. 3장에서 본 대로 그 오류에는 파일 이름이 없고, 이름을 아는 main 이 19번 줄에서 도구 이름과 함께 붙입니다.

wc — 세는 함수는 어디서 읽는지 모른다

둘째는 줄 · 낱말 · 바이트를 세는 wc 입니다. 세는 일은 count 하나가 맡고, 3장의 total 처럼 impl BufRead 를 받습니다. 바이트를 빠짐없이 세야 하므로 줄바꿈을 떼는 lines() 대신 2장의 read_line 으로 읽습니다.

읽는 법 — ./wc memo.txt 가 찍은 3 · 6 · 30 이 이 기계의 wc 가 센 수와 같습니다. 다른 것은 칸의 폭뿐입니다. 20번 줄의 read_line 이 0 을 주면 입력의 끝이라 22번 줄이 센 것을 돌려줍니다. 24번 줄은 줄바꿈까지 든 바이트 수 n 을 더하고, 25번 줄은 2장에서 쓴 split_whitespace 로 낱말을 셉니다. 26번 줄은 줄바꿈으로 끝난 줄만 줄로 셉니다.
6번 줄 — 10부의 #[derive(Default)] 덕분에 15번 줄의 Counts::default() 가 셋 다 0 인 값으로 시작합니다.

파일을 주지 않으면 표준 입력을 센다

wc 의 나머지 절반입니다. 인자로 파일을 받았으면 파일마다 세고, 하나도 받지 않았으면 표준 입력을 셉니다. 두 경우 모두 앞 슬라이드의 count 를 부릅니다.

읽는 법 — 파일 셋을 준 실행은 cat 과 같은 틀입니다. 없는 none.txt 는 알림으로 넘어가고 todo.txt 까지 센 뒤 종료 코드 1 입니다. printf … | ./wc 에는 인자가 없어서 paths.is_empty() 갈래가 io::stdin().lock() 을 넘겼습니다. 마지막 줄 three 가 줄바꿈 없이 끝나서 줄 수는 1 입니다. cat memo.txt | ./wc 는 파일로 셀 때와 같은 3 · 6 · 30 을 냈습니다.
어디서 읽을지는 부르는 쪽이 정한다 — count 는 글자 하나 바꾸지 않고 파일과 표준 입력을 다 셌습니다. 3장에서 "6장의 도구들이 이 모양으로 짜입니다" 라고 한 그 모양입니다.

head — 인자를 손으로 읽는다

셋째는 앞의 몇 줄만 보여 주는 head 입니다. 줄 수를 정하는 -n 줄수 와 파일 이름을 받습니다. 인자를 읽는 일을 parse_args 로 떼어, 읽어 낸 것을 Config 에 담아 돌려주게 합니다. 틀린 인자는 Err 로 까닭을 돌려줍니다.

  • 20번과 21번 줄 — 인자 목록의 반복자를 rest 에 두고 7부의 while let 으로 하나씩 꺼냅니다. -n 을 만나면 23번 줄이 같은 반복자에서 하나를 더 꺼내 줄 수로 씁니다.
  • 23번부터 28번 줄까지 — 꺼낼 것이 없으면 let … else 가 Err 로 돌아가고, 수가 아니면 map_err 가 문제의 글을 붙입니다.
  • 17번 줄 — -n 을 주지 않았을 때의 줄 수는 10 입니다.
&[String] 을 받는 까닭 — parse_args 는 env::args() 를 직접 부르지 않습니다. 그래서 뒤의 시험에서 인자 목록을 만들어 넘길 수 있습니다. 이 함수가 내는 오류 셋은 잘못 부르면 2 로 끝낸다의 화면에 나옵니다.

앞의 n 줄만 옮긴다 — lines().take(n)

일하는 함수 head 는 읽을 곳, 쓸 곳, 줄 수를 받습니다. 12부의 take 가 줄 반복자에서 앞의 n 개만 내게 합니다. run 은 Config 를 보고 읽을 곳을 골라 head 에 넘깁니다.

읽는 법 — ./head -n 2 fruits.txt 는 다섯 줄 가운데 사과 와 배 만 찍었습니다. 파일을 주지 않은 printf … | ./head -n 1 은 run 의 None 갈래로 가서 표준 입력의 첫 줄 a 를 찍었습니다. seq 1 30 | ./head | tail -n 1 은 head 가 찍은 것의 마지막 줄이 10 임을 보여 줍니다. -n 없이는 열 줄입니다. 없는 파일에는 run 의 map_err 가 이름을 붙였고 종료 코드는 1 입니다.
match 의 두 갈래 — 한쪽은 File 을 감싼 BufReader 를, 다른 쪽은 표준 입력의 열쇠를 넘깁니다. 타입이 다른 두 가지를 같은 head 가 받고, 두 갈래가 내는 값은 똑같이 io::Result<()> 입니다.

잘못 부르면 쓰는 법을 알리고 2 로 끝낸다

head 의 main 은 1장의 얇은 main 에 한 단계를 더한 모양입니다. 먼저 parse_args 로 인자를 읽고, 그다음 run 에 일을 시킵니다. 실패가 어느 단계에서 났는지에 따라 종료 코드가 갈립니다.

읽는 법 — -n two 에서는 parse_args 의 map_err 가 만든 줄 수 `two`: invalid digit found in string 앞에 main 이 head: 를 붙였고, 한 줄 더 쓰는 법을 찍었습니다. -n 만 준 실행은 parse_args 의 let … else 갈래의 말이, 파일을 둘 준 실행은 그 마지막 else 갈래의 남는 인자 `extra.txt` 가 나왔습니다. 셋 다 종료 코드 2 이고, fruits.txt 의 내용은 한 줄도 찍히지 않았습니다.
종료 코드 셋 — 0 은 성공, 1 은 일하다 난 실패(앞 슬라이드의 없는 파일), 2 는 잘못 부른 것입니다. 알림 글을 읽지 않아도 번호만으로 셋이 갈립니다.

읽을 곳도 파일만이 아니다 — &[u8] 와 Cursor

1장에서 Vec<u8> 가 Write 임을 봤습니다. 읽는 쪽의 짝이 바이트 슬라이스 &[u8] 입니다. BufRead 를 구현합니다. io::Cursor 는 가진 데이터를 감싸 BufRead 로 만들어 줍니다. 2장과 3장의 total 을 파일도 표준 입력도 없이 불러 봅니다.

읽는 법 — 15번 줄은 6부에서 본 as_bytes() 로 글을 &[u8] 로 보고 넘겨 60 을 얻었습니다. 19번 줄은 String 을 Cursor 로 감싸 넘겨 300 입니다. 24번 줄에서 Cursor 로 한 줄을 읽자 25번 줄이 읽는 자리 2 를 찍었고, 그 Cursor 를 넘긴 26번 줄의 total 은 남은 8 만 더했습니다. 3장의 File 처럼 어디까지 읽었는지를 기억합니다.

파일도 화면도 없이 시험한다

1장에서 "화면에 찍는 함수가 무엇을 찍는지 벡터로 받아 시험합니다" 라고 한 자리입니다. head 와 parse_args 는 파일 이름도 표준 입출력도 모르므로, 13부의 시험 모듈에서 곧바로 부릅니다. head.rs 의 맨 아래입니다.

읽는 법 — 넷 다 ok 입니다. head_takes_first_lines 는 입력으로 &[u8] 를, 쓸 곳으로 Vec<u8> 를 넘기고, 벡터에 든 바이트를 기대한 글의 바이트와 assert_eq! 로 견줍니다. head_of_short_input 은 줄바꿈 없이 끝난 "a\nb" 를 넣었는데 나온 글은 "a\nb\n" 입니다. lines() 가 뗀 줄바꿈을 writeln! 이 줄마다 붙이기 때문입니다. 화면의 --test 와 --test-threads=1 은 13부의 첫 시험에서 본 것이고, -o head_test 는 실행 파일의 이름을 앞에서 만든 head 와 다르게 정합니다.
시험이 닿지 않는 곳은 얇게 — 파일을 열고 표준 입출력을 잡는 run 과 main 은 시험하지 않았습니다. 그 둘은 고르고 넘기는 일만 합니다.

이름을 담는 오류 타입 — 열거형에 io::Error 를 그대로 넣는다

세 도구는 오류를 글로 바꿔 올렸습니다. 3장에서 짚은 대로 그러면 부른 쪽이 kind() 를 물을 수 없습니다. 그때 미뤄 둔 오류 타입을 만듭니다. 재료는 9부의 셋입니다 — 열거형, Display, From.

  • 12번 줄 File — io::Error 를 글로 바꾸지 않고 값 그대로 담고, 그 옆에 파일 이름을 둡니다.
  • 17번 줄 Display — 찍을 때에야 이름: 까닭 모양의 글을 만듭니다. 3장에서 map_err 가 미리 만들던 글입니다.
  • 31번 줄 From — ? 가 io::Error 를 만나면 불러서 Io 로 바꿉니다. from 이 받는 것은 오류 하나뿐이라 파일 이름을 알 길이 없습니다. 그래서 File 변형은 From 으로 만들지 못하고, 다음 슬라이드에서 map_err 로 만듭니다.
28번 줄 — 9부처럼 본문 없는 impl Error 로 "이 타입은 오류다" 라고 표시합니다. 품은 오류를 source() 로 내주는 구현은 9부에서 본 그대로 더할 수 있습니다.

오류가 값이면 부른 쪽이 종류를 묻는다

first 는 파일마다 첫 줄을 이름과 함께 찍는 도구입니다. 없는 파일은 알리고 건너뛰되, 그 밖의 실패에서는 멈추기로 합니다. 오류가 글이었다면 이 둘을 가를 길이 없습니다.

읽는 법 — 둘째 실행의 none.txt 는 main 의 가드 source.kind() == ErrorKind::NotFound 에 맞아 first: none.txt 가 없어 건너뛴다 가 찍혔고, b.txt 까지 간 뒤 종료 코드 줄 없이 끝났습니다. 셋째 실행의 . 은 디렉터리라서 종류가 다릅니다. 마지막 갈래가 {e} 로 찍은 것이 Display 가 만든 .: Is a directory (os error 21) 이고, 거기서 1 로 끝나 b.txt 는 찍히지 않았습니다. 오류를 글로 바꾸는 일은 두 번 다 맨 끝의 main 이 했습니다.
first_line 의 ? 둘 — map_err 뒤의 ? 는 이름을 실은 ToolError::File 을 그대로 올립니다. writeln! 뒤의 ? 는 io::Error 를 올려야 하는데 반환 타입이 ToolError 입니다. 그 줄이 컴파일된 것은 앞 슬라이드의 From 덕분입니다. 이 화면의 세 실행에서는 표준 출력에 쓰는 일이 실패하지 않아서, Io 변형이 실제로 만들어진 적은 없습니다.

작은 도구가 지키는 것

이 장의 도구들이 함께 지킨 것을 모았습니다. 항목마다 그것을 화면으로 보인 슬라이드가 달려 있습니다.

  • 결과는 표준 출력, 알림은 표준 오류 — 알림에는 도구 이름과 파일 이름을 붙입니다(cat).
  • 한 파일의 실패가 나머지를 막지 않는다 — 알리고 다음 파일로 가되, 끝에서 종료 코드로 남깁니다 (cat · wc).
  • 파일을 주지 않으면 표준 입력 — 그래서 | 로 다른 명령 뒤에 이어 쓸 수 있습니다 (wc · head).
  • 종료 코드는 0 · 1 · 2 — 성공, 일하다 난 실패, 잘못 부른 것입니다(head).
  • 일하는 함수는 읽을 곳과 쓸 곳을 받는다 — impl BufRead 와 &mut impl Write 입니다. 파일 없이 시험할 수 있습니다(시험).
  • 이름은 아는 쪽이 붙인다 — map_err 로, 또는 이름을 담는 오류 타입으로 합니다 (ToolError).

퀴즈 — 작은 도구

Q. 줄을 걸러 println! 으로 찍는 함수가 있습니다. 무엇을 찍는지 #[test] 로 확인하려면 함수를 어떻게 바꿀까요? 또 ./cat one.txt none.txt two.txt 에서 none.txt 가 없을 때, 도구는 무엇을 어디에 찍고 몇 번으로 끝나야 할까요?

A. 쓸 곳을 &mut impl Write 로 받아 writeln! 으로 쓰게 바꿉니다. 시험에서는 Vec<u8> 를 넘기고 거기에 든 바이트를 견줍니다. 읽을 곳도 impl BufRead 로 받으면 &[u8] 를 넘길 수 있습니다(파일도 화면도 없이). cat 은 있는 두 파일의 내용을 표준 출력에 찍고, cat: none.txt: … 알림을 표준 오류에 찍은 다음 종료 코드 1 로 끝납니다 (cat).
