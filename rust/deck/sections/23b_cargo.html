시험 모듈 안의 보통 함수 — 시험들이 나눠 쓰는 도우미

13부의 시험 모듈에는 시험 함수만 있었습니다. 여러 시험이 같은 준비물을 쓸 때는 그 모듈 안에 보통 함수를 하나 두고 함께 부릅니다. 이 장에서는 그런 함수를 도우미라고 부릅니다. 패키지 wordbox 의 src/lib.rs 입니다.

읽는 법 — 22번 줄의 sample 에는 #[test] 가 없습니다. 28번 줄과 33번 줄의 두 시험이 그것을 불러 같은 글을 받습니다. 화면의 running 2 tests 가 센 것은 #[test] 가 붙은 둘이고, 점도 둘, 결과 줄도 2개 통과입니다. sample 은 시험으로 세지 않았습니다. --lib 은 처음 쓰는 옵션입니다. 13부의 --doc 이 문서 시험만 돌렸듯이, 이것을 붙이자 묶음이 하나만 찍혔습니다. 시험이 2개인 그 묶음이 src/lib.rs 의 단위 시험입니다. 이 패키지의 다른 묶음은 다음 슬라이드에서 봅니다.

통합 시험 파일들이 나눠 쓰는 도우미 — tests/common/mod.rs

13부에서 tests/ 아래의 파일은 따로 컴파일되는 크레이트라고 했습니다. 같은 패키지의 tests/ 에 시험 파일 둘을 두었습니다. 두 파일이 같은 도우미를 쓰도록, 도우미는 셋째 파일에 두고 두 파일이 저마다 모듈로 끌어옵니다.

읽는 법 — count.rs 2번 줄의 mod common; 은 13부의 파일을 찾는 규칙대로 같은 디렉터리의 common.rs 나 common/mod.rs 를 찾습니다. 여기 있는 것은 뒤의 것이고, 그 파일 2번 줄의 sample 이 낱말 넷을 빈칸으로 이은 글을 돌려줍니다. count.rs 6번 줄이 그 도우미를 common::sample() 로 불러 낱말이 넷인지 봅니다. --test count 도 처음 쓰는 옵션이고, tests/ 의 파일 하나를 이름으로 고릅니다. 묶음이 하나이고 1개 통과입니다. 그다음 명령은 13부에서 묶음의 이름 줄만 골라낸 그 명령입니다. 묶음은 넷이고, tests/ 의 것은 count.rs 와 longest.rs 둘입니다. common 이라는 묶음은 없습니다.
mod.rs 로 둔 까닭 — 도우미 파일을 tests/common.rs 로 두어도 mod common; 은 그것을 찾습니다. 그렇게 두면 무엇이 달라지는지를 다음 슬라이드에서 봅니다.

tests/common.rs 로 두면 Cargo 가 그것도 시험 파일로 돌린다

앞 슬라이드의 tests/common/mod.rs 를 tests/common.rs 로 옮기기만 한 쌍둥이 패키지입니다. 그 파일의 내용도, 나머지 파일도 글자까지 같습니다.

읽는 법 — find 가 보인 대로 tests/ 바로 아래에 파일이 셋입니다. --test count 는 이번에도 1개 통과입니다. mod common; 이 common.rs 를 찾았습니다. 이름 목록에는 Running tests/common.rs 가 새로 생겨 묶음이 다섯입니다. 둘째 화면이 그 묶음만 돌린 것이고 running 0 tests 입니다. #[test] 가 하나도 없는 파일이 시험 크레이트로 컴파일되어 돌았습니다. 셋째 화면은 앞 슬라이드의 패키지에서 같은 --test common 을 친 것입니다. 오류 첫 줄은 "기본으로 돌리는 패키지들에 common 이라는 시험 대상(test target)이 없다" 이고, help: 가 있는 시험 대상 둘 count 와 longest 를 댑니다. Cargo 가 낸 오류라 번호가 없고, 종료 코드는 101 입니다.
한 칸 아래에 둔다 — tests/ 바로 아래에 둔 common.rs 는 묶음이 됐고, 한 칸 아래의 common/mod.rs 는 되지 않았습니다.

should_panic(expected) — 다른 말로 패닉하면 실패다

13부의 #[should_panic] 슬라이드는 expected 에 "패닉 메시지에 들어 있어야 할 글자" 를 적는다고 했고, 통과하는 화면만 보였습니다. 여기서는 통과하지 못하는 화면을 읽습니다. 패키지 age 의 시험 셋에 같은 expected 를 달고, 13부의 이름으로 고르기로 하나씩 돌립니다.

읽는 법 — 소스를 따라가면 17번 줄의 200 은 4번 줄의 조건에 걸려 5번 줄에서 패닉합니다. 그 줄의 메시지에 expected 의 너무 많다 가 들어 있고, 첫 화면은 1개 통과입니다. 2 filtered out 은 이름으로 걸러진 나머지 둘입니다. 둘째 화면의 --- FAILED 줄이 실패한 시험의 이름이고, 까닭은 failures: 아래, 그 시험의 이름을 단 ---- … stdout ---- 줄 밑에 있습니다. 패닉 줄의 자리는 src/lib.rs 3번 줄입니다. 9부에서 본 expect 가 낸 패닉이고, 메시지 끝의 ParseIntError { … } 는 Err 안에 있던 값입니다. 패닉은 했습니다. 첫 note: 는 패닉 때마다 붙던 백트레이스 안내이고, 새로운 것은 둘째 note: 입니다. "패닉 메시지에 기대한 글이 들어 있지 않다" 이고, 그 아래 두 줄이 실제 메시지(panic message)와 기대한 조각(expected substring)을 나란히 댑니다. 둘째 failures: 는 실패한 시험의 이름 목록이고, 결과 줄은 1개 실패입니다. 마지막 error: test failed 줄은 Cargo 가 덧붙인 것으로, 다시 돌릴 때 --lib 을 주면 된다는 말입니다. 종료 코드는 13부의 실패한 시험처럼 101 입니다.
expected substring — 화면이 스스로 substring(조각)이라고 부릅니다. 소스 5번 줄대로라면 too_old 의 메시지는 나이가 너무 많다: 200 이고, expected 에는 그 가운데 조각만 적었는데 통과했습니다.

should_panic 인데 패닉하지 않으면 그것도 실패다

같은 패키지의 셋째 시험입니다. 150 은 앞 슬라이드 4번 줄의 age > 150 에 걸리지 않습니다.

읽는 법 — failures: 아래의 까닭이 한 줄입니다. "시험이 기대와 달리 패닉하지 않았다" 이고, 붙은 자리는 src/lib.rs 30번 줄, 시험 함수의 이름이 있는 줄입니다. 앞 슬라이드의 실패와 달리 패닉 줄도, 견줄 메시지 두 줄도 없습니다. 나머지는 앞 슬라이드와 같습니다. 걸러진 2개, Cargo 가 덧붙인 줄, 종료 코드 101 입니다.
이 실패가 알려 준 것 — 틀린 쪽은 parse_age 가 아니라 시험입니다. 앞 슬라이드에서 본 그 함수의 1번 줄 주석은 "150 을 넘으면 패닉한다" 이고, 150 은 넘지 않은 값입니다.

실행 파일이 할 판단을 라이브러리의 함수로 옮겨 시험한다

13부에서 일은 lib.rs 에 두고 main 은 얇은 껍데기로 둔다고 했습니다. 인자를 받고 종료 코드를 정하는 프로그램에서 그렇게 해 봅니다. 패키지 shout 는 인자들을 이어 큰 글자로 찍습니다. 인자를 보고 무엇을 찍을지 정하는 일은 lib.rs 의 run 이 하고, main 에는 찍는 일과 종료 코드만 남겼습니다.

읽는 법 — cargo run -q -- hello rust 의 -- 는 처음 씁니다. 그 뒤에 적은 것은 Cargo 가 아니라 돌리는 프로그램이 인자로 받습니다. main.rs 6번 줄이 그 둘을 모아 run 에 넘겼고 9번 줄이 HELLO RUST! 를 찍었습니다. 인자 없이 돌린 다음 명령에서는 lib.rs 4번 줄의 Err 가 돌아와 main.rs 13번 줄의 eprintln! 이 쓰는 법을 찍고, 14번 줄의 ExitCode 대로 종료 코드 2 로 끝났습니다. 마지막 명령은 tests/run.rs 의 시험 둘입니다. run.rs 4번 줄의 도우미 args 가 낱말들을 Vec<String> 으로 바꿔 주고, 10번과 16번 줄이 run 을 직접 부릅니다. 16번 줄의 unwrap_err 는 9부에서 본 unwrap 의 반대입니다. 둘 다 통과입니다.
main 에 남은 것 — run.rs 의 시험은 실행 파일을 띄우지 않습니다. main.rs 의 9번 · 13번 줄이 찍는 글과 10번 · 14번 줄의 종료 코드는 이 시험이 보지 않습니다. 다음 슬라이드가 실행 파일을 띄워 그것까지 봅니다.

통합 시험이 실행 파일을 띄운다 — env!("CARGO_BIN_EXE_shout")

main 이 찍는 글과 종료 코드까지 시험하려면 만들어진 실행 파일을 돌려야 합니다. 릴리스 노트는 Cargo 가 통합 시험 때 CARGO_BIN_EXE_<name> 에 실행 파일의 경로를 넣어 준다고 적고, env!("CARGO_BIN_EXE_my-program") 처럼 쓰는 예를 듭니다. 3장의 env! 로 그 경로를 읽고, 18부의 Command 와 output 으로 띄웁니다.

읽는 법 — 4번 줄의 EXE 가 그 경로입니다. 8번 줄은 그 글이 /target/debug/shout 로 끝나는지를 봅니다. 1장에서 실행 파일이 있던 target/debug/ 입니다. 14번 줄이 인자 둘을 주어 띄우고 (args), 15번부터 17번 줄까지가 종료 코드 0, 줄바꿈까지 넣은 표준 출력 "HELLO RUST!\n", 빈 표준 오류를 봅니다. 22번 줄은 인자 없이 띄웁니다. 23번부터 26번 줄까지가 종료 코드 2, 빈 표준 출력, 표준 오류의 쓰는 법 한 줄을 봅니다. 화면은 3개 통과입니다. 앞 슬라이드에서 셸로 돌려 눈으로 본 두 화면을 이번에는 시험이 봤습니다.

기준 파일 — 기대하는 출력을 파일에 두고 통째로 견준다

출력이 여러 줄이면 기대하는 글을 시험 소스에 문자열로 적어 두기가 번거롭습니다. 그 글을 파일에 두고, 시험이 지금의 출력을 그 파일과 견주게 합니다. 이런 파일을 기준 파일(golden file)이라고 부릅니다. 패키지 report 의 render 는 이름과 수를 줄 맞춰 적습니다.

읽는 법 — lib.rs 5번 줄의 {name:<6}{n:>4} 는 2부의 폭과 정렬입니다. cat 이 보인 두 줄이 기준 파일 tests/golden/report.txt 의 전부입니다. golden.rs 의 5번 · 6번 줄은 3장의 CARGO_MANIFEST_DIR 뒤에 concat! 으로 나머지를 이어, 그 파일의 경로를 컴파일할 때 글 하나로 만들어 둡니다. 10번 줄이 지금의 출력을 만들고, 15번 줄이 17부의 fs::read_to_string 으로 기준 파일을 읽고, 16번 줄이 둘을 통째로 견줍니다. 화면은 1개 통과입니다. 12번부터 14번 줄까지의 if 는 다음 슬라이드에서 씁니다.

출력이 바뀌면 두 글이 나란히 찍힌다 — 기준 파일을 고치는 스위치

render 가 수 뒤에 개 를 붙이도록 lib.rs 의 5번 줄만 바꾼 쌍둥이 패키지입니다. 기준 파일과 시험 파일은 앞 슬라이드의 것과 글자까지 같습니다.

읽는 법 — 첫 화면의 --- FAILED 줄이 하나뿐인 시험의 이름입니다. 패닉 줄은 tests/golden.rs 16번 줄의 assert_eq! 를 가리킵니다. 13부에서 읽은 left 와 right 그대로, left 가 지금의 출력이고 right 가 기준 파일입니다. 두 줄짜리 글이 저마다 한 줄에 찍혔습니다. 2부의 {:?} 모양이라 따옴표가 붙고 줄바꿈이 \n 으로 보입니다. left 와 right 를 견주면 3 과 12 뒤의 개 가 다릅니다. 결과 줄은 1개 실패이고, Cargo 가 덧붙인 줄은 이번에는 --test golden 을 댑니다. 종료 코드는 101 입니다. 둘째 화면의 첫 명령은 18부에서 본 이름=값 표기로 UPDATE_GOLDEN 을 주었습니다. 앞 슬라이드의 golden.rs 12번 줄에서 env::var 가 Ok 가 되어, 13번 줄이 지금의 출력을 기준 파일에 씁니다(fs::write). 15번 줄은 방금 쓴 그 파일을 읽으니 통과입니다. cat 이 보인 기준 파일에 개 가 들어갔고, 변수 없이 돌린 마지막 명령도 통과입니다. UPDATE_GOLDEN 은 이 예제가 지은 이름입니다.
스위치를 켠 실행은 아무것도 가려내지 않는다 — golden.rs 를 따라가면 13번 줄이 쓴 글을 15번 줄이 그대로 읽어 견주므로, 출력이 무엇이든 통과합니다. 그렇게 바뀐 기준 파일은 cat 으로 본 것처럼 눈으로 읽고 받아들입니다.

한 스레드로 돌리면 결과 줄이 이름 순으로 선다 — cargo test -- --test-threads=1

13부는 rustc 로 만든 시험 실행 파일에 --test-threads=1 을 주었고, 결과 줄이 소스에 적은 순서가 아니라 이름 순이라고 했습니다. cargo test 에서는 그 옵션을 -- 뒤에 적습니다. cargo run 의 -- 와 같은 꼴입니다. should_panic 의 패키지에서 시험 셋을 이번에는 한꺼번에 돌립니다.

읽는 법 — 그 슬라이드의 lib.rs 에 적은 순서는 16번 줄의 too_old, 23번 줄의 not_a_number, 30번 줄의 exactly_150 입니다. 화면은 running 3 tests 아래에 exactly_150 과 not_a_number 의 --- FAILED 가 먼저이고, 통과한 too_old 의 점이 그 뒤입니다. 이름 순입니다. -q 의 화면에서 통과는 점 하나, 실패는 이름이 적힌 한 줄입니다. 둘째 화면은 시험 실행 파일에 --help 를 주고, 그 도움말에서 두 문단만 골라낸 것입니다(sed 는 따옴표 안에 적은 두 줄 사이만 찍습니다). 첫 문단은 "기본으로는 모든 시험을 나란히(in parallel) 돌린다. --test-threads 로 바꿀 수 있다(1 을 준다)" 입니다. 둘째 문단은 "기본으로는 시험을 알파벳 순으로 돌린다" 로 시작하고, 나머지는 순서를 섞는 --shuffle 의 설명입니다. 이 책은 순서를 섞지 않습니다.
이 책이 이 옵션을 붙이는 까닭 — 이 책은 같은 예제를 다시 돌려 글자까지 같아야 싣습니다. 15부에서 말한 대로 스레드가 도는 순서는 실행마다 달라질 수 있고, 13부에서 말한 대로 옵션 없이 돌린 화면은 결과 줄의 순서가 실행마다 달라진 일이 있었습니다. 그래서 한 묶음에 이름이 적힌 줄이 둘 이상 나올 수 있으면 이 옵션을 붙입니다. 이 장의 앞 슬라이드들은 붙이지 않았습니다. 모두 통과하는 묶음은 어느 시험의 것이든 같은 점뿐이고, 실패하는 시험은 하나씩 골라 돌렸습니다. 릴리스 노트는 시험 실행 파일이 --test-threads 를 받게 된 것을 로, 그 값이 1 이면 시험마다 새 스레드를 만들지 않고 정해진 순서로 돌게 된 것을 로 적습니다.

시험 셋이 파일 하나에 썼다 — 시험마다 제 파일을 주어 떼어 놓는다

앞 슬라이드는 결과 줄의 순서를 봤습니다. 이번에는 시험들이 시험 함수 밖에 있는 것, 여기서는 파일 하나를 함께 쓰는 경우입니다. 패키지 seat 의 take_seat 은 파일에 이름 한 줄을 쓰고 그 파일을 다시 읽어 돌려줍니다. 시험 셋이 모두 seat.txt 에 씁니다.

읽는 법 — 첫 화면은 3개 통과입니다. ls 가 보인 .txt 파일은 패키지 뿌리의 seat.txt 하나이고, 거기 남은 이름은 zebra 입니다. 세 시험이 같은 파일을 차례로 덮어썼습니다. 첫 상자에서 zebra 는 14번 줄, 맨 먼저 적은 시험인데 마지막에 썼습니다. 앞 슬라이드에서 본 이름 순입니다. 쌍둥이 패키지는 15번 · 20번 · 25번 줄의 파일 이름만 zebra.txt · apple.txt · mango.txt 로 바꿨습니다. --test-threads=1 없이 돌려 3개 통과이고, 파일이 셋 생겼습니다. zebra.txt 에는 그 시험이 쓴 한 줄이 있습니다.
이 책이 돌리지 않은 것 — 첫 패키지를 --test-threads=1 없이 돌린 화면은 싣지 않았습니다. 앞 슬라이드의 도움말대로라면 세 시험이 나란히 돕니다. 한 시험이 첫 상자의 5번 줄에서 쓰고 6번 줄에서 읽는 사이에 다른 시험이 같은 파일을 덮어쓰면, 읽은 글이 제 이름이 아니어서 그 시험의 assert_eq! 가 실패합니다. 그렇게 될지가 실행마다 다를 수 있는 화면입니다.

실행 파일 여러 개와 프로필

src/bin/ 과 default-run · examples/ · 프로필과 넘침 검사 · debug_assert! · [profile.release] 고치기 · 새 프로필 · panic = "abort" · [lints] 표 · forbid · unexpected_cfgs 알리기

src/bin/ 의 파일마다 실행 파일 하나 — --bin 으로 고르거나 default-run 으로 정해 둔다

1장에서 실행 패키지가 둘인 워크스페이스는 cargo run 이 고르라고 했고, 한 패키지에 실행 파일이 여럿인 경우는 미뤄 두었습니다. 패키지 greet 는 src/main.rs 없이 src/bin/ 에 파일 둘을 두었습니다. 둘 다 같은 패키지의 lib.rs 를 패키지 이름으로 가져다 씁니다.

읽는 법 — find 가 보인 소스는 src/lib.rs 와 src/bin/ 의 둘입니다. --bin hello 가 hello.rs 의 main 을, --bin bye 가 bye.rs 의 것을 돌렸습니다. ls 가 보인 실행 파일도 target/debug/ 아래의 bye 와 hello 입니다. 파일 이름에서 .rs 를 뗀 것이 실행 파일의 이름이 됐습니다. 옵션 없는 cargo run 의 오류 첫 줄은 1장에서 읽은 그 글이고, 아랫줄의 고를 수 있는 것이 이번에는 bye, hello 입니다. 종료 코드는 101 입니다. 1장에서는 -p 로 패키지를 골랐고, 여기서는 위의 두 명령처럼 오류가 대는 --bin 으로 고릅니다.
default-run — 오류가 댄 또 하나의 길입니다. 쌍둥이 패키지의 Cargo.toml 은 [package] 에 5번 줄 하나를 더했습니다. 이 파일에도 실행 파일 둘을 적은 곳은 없습니다. 옵션 없는 cargo run -q 가 hello 를 돌렸고, --bin bye 로 다른 것도 그대로 고를 수 있습니다. 릴리스 노트는 [package] 의 default-run 을 에 적습니다.

examples/ 의 프로그램은 cargo build 가 만들지 않고 --example 로 돌린다

라이브러리 패키지에는 "이렇게 쓴다" 를 보이는 작은 프로그램을 examples/ 디렉터리에 둘 수 있습니다. src/bin/ 의 파일처럼 저마다 main 을 가지지만, 돌리는 옵션도 실행 파일이 생기는 자리도 다릅니다. 앞 슬라이드의 lib.rs 만 가져온 패키지에 그런 파일 하나를 두었습니다.

읽는 법 — demo.rs 2번 줄은 13부의 통합 시험처럼 라이브러리를 패키지 이름으로 끌어옵니다. cargo build -q 뒤에 target/debug/examples/demo 를 찾으면 없습니다. 2부에서 없는 실행 파일을 찾았을 때처럼 이 기계의 ls 가 그런 파일이 없다고 하고 종료 코드 2 로 끝났습니다. cargo run -q --example demo 는 그 파일을 컴파일해 돌렸고, 5번 줄이 demo: hi, example! 을 찍었습니다. 그 뒤의 ls 에는 그 파일이 있습니다. 자리는 target/debug/ 바로 아래가 아니라 그 안의 examples/ 입니다. 마지막 명령은 옵션 없는 cargo run 입니다. 오류는 "cargo run 에는 실행 파일 대상(bin target)이 있어야 한다" 이고 종료 코드는 101 입니다. src/main.rs 도 src/bin/ 도 없는 이 패키지에서 demo 는 --example 로만 돌았습니다.

넘침 검사는 프로필에 달려 있다 — cargo run 과 cargo run --release

3부는 같은 소스를 rustc 의 -O 로 컴파일하면 넘침이 조용히 지나간다는 것을 보였고, Cargo 에서도 같다는 것은 말로만 했습니다. 여기서 Cargo 로 돌립니다. 2부의 두 빌드를 견준 표에서 cargo build 의 프로필은 dev, --release 의 프로필은 release 였습니다. 프로필(profile)은 컴파일 설정 한 벌에 붙인 이름입니다. 패키지 level 은 3부의 예제와 같은 덧셈을 합니다.

읽는 법 — 첫 명령은 dev 프로필입니다. 7번 줄이 debug_assertions = true 를 찍고, 11번 줄의 덧셈에서 3부에서 본 attempt to add with overflow 패닉이 났습니다. 종료 코드는 101 입니다. --release 를 붙인 둘째 명령은 false 를 찍고 다음: 4 까지 갔습니다. 260 이 u8 에 들어가지 않아 4 가 된 것도 3부에서 본 그대로입니다. --release 는 Cargo 의 옵션이라 -- 앞에 적었습니다. 두 실행에서 소스는 같고 다른 것은 프로필입니다. 9번 줄은 다음 슬라이드에서 봅니다.
넘칠 수 있는 덧셈 — 프로필에 따라 달라지지 않게 적는 길은 3부의 넘칠 때를 고르는 메서드에 있습니다.

debug_assert! — dev 에서는 확인하고 release 에서는 지나갔다

앞 슬라이드 9번 줄의 debug_assert! 는 9부의 assert! 와 같은 꼴로 적는 매크로입니다. 조건과, 거짓일 때 찍을 말을 받습니다. 같은 프로그램에 이번에는 0 을 줍니다.

읽는 법 — dev 프로필의 첫 명령은 true 를 찍고 9번 줄에서 패닉했습니다. 메시지가 그 줄에 적은 0 은 받지 않는다 입니다. release 프로필의 둘째 명령은 false 를 찍고 다음: 10 까지 갔습니다. 같은 0 을 받았는데 9번 줄이 프로그램을 멈추지 않았습니다. 7번 줄의 cfg!(debug_assertions) 가 true 인 실행에서만 9번 줄이 조건을 확인했습니다. 마지막 ls 는 두 프로필의 실행 파일이 따로 있음을 보입니다. 2부에서 본 대로 target/debug/ 와 target/release/ 입니다.
release 에서는 없는 것과 같았다 — 그 빌드에서도 지켜져야 하는 조건은 debug_assert! 에 맡기지 않습니다.

[profile.release] 에 적은 키가 그 프로필의 설정을 바꾼다 — overflow-checks

13부의 구역 표는 [profile.release] 를 "빌드 설정" 이라고만 적었습니다. 앞의 두 슬라이드에서 본 것에는 저마다 프로필의 키가 있습니다. 넘침 검사가 overflow-checks, 디버그용 검사가 debug-assertions 입니다. 소스는 그대로 두고 Cargo.toml 만 고친 쌍둥이 패키지에서 release 의 넘침 검사를 켭니다.

읽는 법 — Cargo.toml 의 8번 · 9번 줄이 release 프로필의 overflow-checks 를 true 로 적었습니다. 앞에서 4 를 찍던 cargo run -q --release -- 250 이 이번에는 패닉하고 종료 코드 101 로 끝납니다. 패닉 줄이 대는 자리 src/main.rs:11 은 그 덧셈입니다. 그 위의 debug_assertions = false 는 그대로입니다. 0 을 준 둘째 명령도 앞 슬라이드의 release 와 같이 다음: 10 입니다. 넘침 검사만 켜졌고 디버그용 검사는 꺼진 채입니다. Cargo.toml 의 11번부터 13번 줄까지는 다음 슬라이드에서 봅니다.
debug_assert! 는 그대로 — 이 화면에서 overflow-checks 를 켠 것은 debug_assert! 에 닿지 않았습니다.

프로필을 새로 만든다 — inherits 와 --profile

dev 와 release 말고 이름을 지어 프로필을 더 둘 수 있습니다. 릴리스 노트는 custom profiles 를 에서 안정화했다고 적습니다. 앞 슬라이드 Cargo.toml 의 11번부터 13번 줄까지가 그런 프로필 checked 입니다.

읽는 법 — --profile checked 로 돌린 첫 화면의 두 명령은 debug_assertions = true 를 찍습니다. Cargo.toml 의 13번 줄이 켠 것입니다. 0 을 주면 debug_assert! 에서, 250 을 주면 덧셈에서 패닉합니다. 패닉 줄이 대는 자리가 src/main.rs:9 와 src/main.rs:11 이고, 종료 코드는 둘 다 101 입니다. 아래의 줄 번호는 다시 Cargo.toml 의 것입니다. checked 의 세 줄에는 overflow-checks 가 없습니다. 그 설정은 12번 줄의 inherits 가 가리킨 release 의 9번 줄에 있습니다. 그 두 줄을 뺀 쌍둥이를 돌린 것이 둘째 화면입니다. 같은 명령이 패닉하지 않고 다음: 4 를 찍습니다. debug_assertions = true 인데도 넘침은 지나갔습니다. 첫 화면으로 돌아가, cargo build --profile checked 의 Finished 줄은 프로필 이름 자리에 checked 를 적었고, 대괄호 안은 2부의 표에서 release 의 것이던 optimized 입니다. ls 가 보인 대로 실행 파일은 target/checked/ 아래에 따로 생겼습니다. target/release/ 의 것은 앞 슬라이드의 두 명령이 만든 것입니다.
inherits — 새 프로필은 물려받을 프로필을 대고, 다르게 할 키만 적었습니다. 적지 않은 넘침 검사와 optimized 가 release 에서 왔습니다.

panic = "abort" — 패닉이 Drop 을 부르지 않고 프로그램을 끝낸다

9부에서 패닉은 정리를 하고 죽는다고 했습니다. 그것도 프로필의 키 panic 으로 바꿀 수 있습니다. dev 를 물려받고 그 키 하나만 적은 프로필 hard 를 만들어, 같은 프로그램을 두 프로필로 돌립니다. Guard 는 9부의 예제처럼 정리될 때 한 줄을 찍습니다.

읽는 법 — Cargo.toml 의 9번 줄이 dev 를 물려받고 10번 줄이 panic 을 "abort" 로 적었습니다. 아래의 줄 번호는 모두 main.rs 의 것입니다. 두 명령 다 11번 줄의 일을 시작한다 부터 찍습니다. 첫 명령은 dev 프로필입니다. 12번 줄의 패닉 메시지 뒤에 5번 줄의 Guard 정리 가 찍히고 종료 코드는 101 입니다. 9부에서 본 차례입니다. --profile hard 로 돌린 둘째 명령은 패닉 메시지까지는 같고 Guard 정리 가 없습니다. 10번 줄의 _guard 가 정리되지 않은 채 프로그램이 끝났습니다. 그 자리의 Aborted 한 줄과 종료 코드 134 는 프로그램이 정한 것이 아니라 이 기계에서 그렇게 나온 것입니다.
정리에 맡긴 일도 빠진다 — 17부의 정리될 때 남은 것을 내보내는 BufWriter 처럼 마무리를 Drop 에 맡긴 값이 있다면, 이 설정에서는 패닉 때 그 마무리가 화면의 Guard 처럼 빠집니다. 그런 실행은 이 책이 따로 돌려 보이지 않았습니다.

[lints] 표 — 경고의 수준을 Cargo.toml 에서 패키지 전체에 정한다

13부의 #[allow] 는 소스의 항목 하나에 붙여 경고를 껐습니다. 이름이 붙은 경고마다 수준(level)이 있고, 그것을 소스가 아니라 Cargo.toml 에 적어 패키지 전체에 걸 수도 있습니다. 2부는 이런 것을 찾는 도구를 lint 라고 불렀고, 표의 이름이 그 낱말입니다. 릴리스 노트는 Cargo.toml 의 [lints] 를 에서 안정화했다고 적습니다. 3부에서 경고였던 쓰지 않은 변수를 오류로 올립니다.

읽는 법 — 오류 첫 줄은 "쓰지 않은 변수: spare" 입니다. 3부의 경고와 같은 글인데 맨 앞이 warning: 이 아니라 error: 이고, 번호(E…)는 없습니다. main.rs 3번 줄에 붙었고, help: 는 3부에서처럼 이름 앞에 밑줄을 붙이라고 합니다. 달라진 것은 note: 입니다. 3부에서는 "기본으로 켜진 경고" 라는 말이었고, 여기서는 "명령 줄에서 -D unused-variables 로 청했다" 입니다. 이 책이 친 명령은 cargo run -q 뿐입니다. 그 옵션은 Cargo 가 Cargo.toml 의 9번 줄을 rustc 에 건넨 것으로 읽습니다. 마지막 줄은 Cargo 가 덧붙인 말이고, 프로그램은 돌지 않은 채 종료 코드 101 로 끝났습니다.
고치는 길 — 변수를 쓰거나 help: 대로 _spare 로 적는 것은 3부에서 본 길입니다. 다음 슬라이드는 소스의 속성으로 이 수준을 한 곳에서만 푸는 길을 봅니다.

deny 는 소스의 #[allow] 가 풀었고, forbid 는 풀지 못했다 — E0453

표에 적는 수준에는 deny 말고 forbid 도 있습니다. 앞 슬라이드의 main 위에 #[allow(unused_variables)] 를 붙인 패키지를, 표의 수준이 deny 인 채로 한 번, forbid 로 바꿔 한 번 돌립니다.

읽는 법 — 첫 화면은 오류 없이 합계 3 을 찍었습니다. main.rs 5번 줄의 spare 는 여전히 쓰지 않는데, 2번 줄의 속성이 그 함수 안에서 그 경고를 껐습니다. 패키지 전체에 건 deny 를 소스의 한 항목이 풀었습니다. 둘째 화면의 오류 첫 줄은 "allow(unused_variables) 는 앞선 forbid 와 함께 쓸 수 없다" 입니다. main.rs 2번 줄의 속성에 "앞선 forbid 가 이것을 물리쳤다" 고 붙었습니다. note: 는 그 forbid 수준이 명령 줄의 -F unused_variables 로 정해졌다고 합니다. 앞 슬라이드의 -D 처럼 이 책이 친 적 없는 옵션입니다. 그 아래는 rustc --explain 안내와 Cargo 가 덧붙인 줄이고, 종료 코드는 101 입니다.
오류가 붙은 곳 — 둘째 화면의 오류는 쓰지 않은 변수가 아니라 2번 줄의 #[allow] 에 붙었습니다. forbid 로 적은 경고는 끄려고 한 것부터가 오류였습니다.

빌드 스크립트가 켜는 cfg 이름을 [lints] 표에서 알린다

3장의 뜻밖의 cfg 이름 경고는 고치는 길 셋을 댔고, 그 하나가 Cargo.toml 의 [lints.rust] 에 적을 두 줄이었습니다. 경고가 났던 그 패키지의 Cargo.toml 끝에 그 두 줄을 그대로 붙인 쌍둥이를 돌립니다. build.rs 와 main.rs 는 글자까지 같습니다.

읽는 법 — 첫 상자가 3장의 화면에 있던 help: 이고, Cargo.toml 의 8번 · 9번 줄이 그 글 그대로입니다. 변수를 주고 돌린 화면에 경고가 없습니다. === palette === 와 red green blue 만 찍혔습니다. 9번 줄은 unexpected_cfgs 라는 경고에 두 가지를 적습니다. level 은 앞의 두 슬라이드에서 낱말 하나로 적던 수준이고, check-cfg 가 "with_banner 라는 cfg 이름이 있다" 고 알리는 자리입니다. 3장의 첫 패키지는 같은 것을 build.rs 의 cargo::rustc-check-cfg 한 줄로 알렸습니다.

퀴즈 — 키 하나가 바꾸는 것

Q. main 은 실행할 때 받은 u8 값 level 로 debug_assert!(level != 0, …) 를 한 뒤 level + 10 을 찍습니다. Cargo.toml 에는 [profile.release] 의 overflow-checks = true 한 줄만 더했습니다. cargo run -q --release 에 ① 250 을 주면, ② 0 을 주면 어떻게 됩니까?

A. ① 덧셈에서 attempt to add with overflow 로 패닉하고 종료 코드는 101 입니다. 그 한 줄이 없던 처음의 release 에서는 4 를 찍었습니다. ② 다음: 10 을 찍습니다. debug_assert! 는 확인하지 않고 지나갑니다. overflow-checks 는 디버그용 검사를 켜지 않았습니다. 둘 다 [profile.release] 를 고친 화면에 있습니다.
