MyVec 의 세 필드와 그 약속 — 만드는 것과 만들지 않는 것

8부에서 벡터는 잡아 둔 자리와 넣은 개수가 따로였고, 2장에서는 앞의 몇 칸만 채운 배열을 len 으로 따로 세었습니다. 이 장은 2장의 도구만으로 그 벡터를 직접 만듭니다. 이름은 MyVec<T> 이고 필드는 포인터 ptr, 잡아 둔 칸 수 cap, 값이 든 칸 수 len 셋입니다. 세 필드는 아래 두 줄 가운데 하나의 모습이어야 하고, 메서드는 끝날 때마다 그 모습을 지킵니다.

new 는 자리를 잡지 않는다 — cap 0 과 NonNull::dangling

구조체와 new 부터 적습니다. 이 장의 파일은 모두 이 슬라이드의 코드로 시작하고, 뒤의 슬라이드는 더한 줄만 보입니다. 포인터는 2장에서 본 NonNull 로 들고 다닙니다.

읽는 법 — 4번부터 7번 줄까지의 주석이 앞 슬라이드의 표입니다. 둘째 상자의 세 메서드는 impl<T> MyVec<T> 블록 안에 있고, 다음 두 슬라이드의 메서드도 같은 블록에 이어집니다. new 는 alloc 을 부르지 않고 cap 과 len 을 0 으로 둡니다. 비워 둘 수 없는 ptr 에는 19번 줄의 NonNull::dangling() 을 넣습니다. 문서는 이 함수가 주는 포인터를 "정렬은 맞지만 매달린(dangling)" 포인터, 곧 어느 값도 가리키지 않는 포인터라고 적고, 벡터처럼 자리를 나중에 잡는 타입을 처음 만들 때 쓴다고 설명합니다. 널이 아니어서 NonNull 에 담기지만 따라가서는 안 됩니다. 5번 줄의 약속이 그것입니다. 17번 줄은 크기가 0 인 타입을 막는 줄입니다. 이 파일을 돌린 화면은 push 슬라이드에 있습니다.

자리를 늘린다 — 새로 잡고, 값을 옮기고, 옛 자리를 돌려준다

넣을 칸이 없을 때 push 가 부를 grow 입니다. 8부의 벡터가 자리가 모자라면 옮겨 간 그 일을 2장의 alloc · dealloc 과 read · write 로 적습니다.

읽는 법 — 43번부터 46번 줄까지가 새 칸 수를 정합니다. 처음에는 4 칸, 그 뒤로는 두 배입니다. 이 책이 정한 수이고, 표준 Vec 이 늘리는 방식과는 상관이 없습니다. saturating_mul 은 3부에서 본 saturating_add 의 곱셈 짝입니다. 50번 줄이 새 자리를 잡고, 51번 줄의 let … else 가 널을 거릅니다. 54번부터 61번 줄까지가 옛 자리의 값을 하나씩 read 로 꺼내 새 자리에 write 로 넣습니다. 62번 줄은 옛 자리가 있을 때만, 그 자리를 잡을 때와 같은 배치로 돌려줍니다. 68번과 69번 줄이 두 필드를 새 자리에 맞춥니다. 52번 줄은 2장의 alloc 슬라이드에서 말한 대로 이 책의 실행에서는 돌지 않았습니다.
옮긴 값은 정리하지 않는다 — 58번 줄의 read 뒤에는 같은 값이 옛 칸과 value 두 군데에 있습니다. 59번 줄이 value 를 새 칸으로 옮기고, 옛 칸은 다시 읽지도 정리하지도 않은 채 66번 줄에서 자리째 돌려줍니다. dealloc 은 값을 정리하지 않으므로 값은 새 자리에 하나만 남습니다. 그 값들이 한 번씩만 정리되는 것은 Drop 슬라이드에서 확인합니다. 위 화면은 34번 줄의 layout 을 직접 부른 쌍둥이 파일의 것입니다. u32 16 칸은 64 바이트이고, usize::MAX 칸은 Layout::array 가 Err 를 주어 37번 줄에서 패닉했습니다. 패닉 줄의 37:23 이 그 자리입니다.

push 는 len 번 칸에 write 하고 len 을 올린다

값이 든 칸은 앞의 len 칸이므로 새 값이 갈 곳은 len 번 칸입니다. 그 칸이 잡은 자리 밖이면 먼저 앞 슬라이드의 grow 를 부릅니다.

읽는 법 — 78번 줄은 대입이 아니라 write 입니다. len 번 칸은 값이 없는 칸이고, 대입은 옛 값부터 정리하려 들기 때문입니다. 85번 줄이 찍은 0 0 은 막 만든 벡터입니다. 첫 push 뒤에 1 4, 다섯째 뒤에 5 8, 아홉째 뒤에 9 16 입니다. 아홉 번 넣는 동안 cap 이 0 · 4 · 8 · 16 으로 세 번 바뀌었습니다. len 이 cap 과 같아진 다음의 push 에서만 73번 줄이 grow 를 불렀습니다.
아직 없는 것 둘 — 이 파일에는 넣은 값을 다시 읽는 길이 없습니다. Deref 로 만듭니다. 잡은 자리를 마지막에 돌려주는 코드도 없습니다. dealloc 을 부르는 곳은 앞 슬라이드의 grow 안 한 군데뿐이고, 그것은 옛 자리를 돌려줍니다. 16 칸짜리 마지막 자리는 누수이고, Drop 에서 고칩니다.

크기가 0 인 타입은 컴파일할 때 걸러 낸다 — E0080

부록의 타입의 크기 표에서 () 는 0 바이트였습니다. 그런 타입은 몇 칸을 잡아도 배치의 크기가 0 이고, 2장에서 본 대로 문서는 크기가 0 인 배치로 alloc 을 부르는 것을 정의되지 않은 동작이라고 적습니다. MyVec 는 그런 타입을 받지 않기로 하고, new 의 17번 줄에 19부에서 본 const { } 안의 단언을 적어 뒀습니다. 앞 슬라이드의 main 에서 u32 대신 () 를 넣어 봅니다.

읽는 법 — 번호와 꼴은 19부의 그 슬라이드에서 읽은 E0080 그대로입니다. 오류 첫 줄에 17번 줄에 적어 둔 글이 나오고, 실패한 상수의 이름에 MyVec::<()> 가 들어 있습니다. 마지막 note: 는 84번 줄의 MyVec::new() 를 () 용으로 만들어 내다가 만났다고 합니다. 84번 줄에는 타입을 적지 않았고, 87번 줄에서 () 를 넣어 T 가 정해졌습니다. 같은 17번 줄을 가진 앞 슬라이드의 파일은 T 가 u32 여서 컴파일됐습니다.

Deref 로 슬라이스를 빌려주면 인덱스와 iter 가 따라온다

넣은 값을 읽는 길을 냅니다. 10부의 Index 를 구현하면 v[i] 하나를 얻습니다. 여기서는 14부의 Deref 를 구현해 값이 든 칸들을 슬라이스 [T] 로 빌려줍니다. 인덱스도, 범위 검사도, iter 도 슬라이스가 이미 가진 것이어서 따로 적지 않아도 됩니다. 포인터와 길이를 슬라이스로 바꾸는 것은 2장의 from_raw_parts 입니다.

읽는 법 — MyVec 에 인덱스나 iter 를 적은 곳은 없습니다. 105번 줄의 v[0] 과 v[4] 가 10 과 50, 106번 줄의 범위가 [20, 30], 107번 줄의 합이 150 입니다. 108번 줄의 first 와 contains 도 슬라이스의 메서드입니다. 109번 줄의 true 는 같은 수를 넣은 Vec 과 내용이 같다는 것입니다. 104번 줄의 len 은 MyVec 에 적어 둔 메서드입니다. 둘째 화면의 쌍둥이는 5번 칸을 읽으려다 패닉했습니다. 8부의 Vec 이 낸 패닉과 수만 다르고 글은 같습니다.
안전: 주석 — 88번부터 90번 줄까지입니다. 막 만든 벡터에서는 ptr 이 dangling 이고 len 이 0 입니다. 문서는 길이가 0 인 슬라이스에도 널이 아니고 정렬이 맞는 포인터를 요구하고, 그런 포인터로 NonNull::dangling() 을 듭니다. 87번 줄의 시그니처는 슬라이스의 수명을 &self 에 묶습니다. 2장의 그 슬라이드가 문서에서 옮긴 "안전한 수명에 묶으라" 는 말대로입니다.

Drop — 값이 든 칸을 정리하고, 잡은 자리가 있으면 돌려준다

벡터가 사라질 때 할 일을 14부의 Drop 에 적습니다. 일은 둘이고 순서가 있습니다. 먼저 값이 든 len 칸을 drop_in_place 로 정리하고, 그다음에 자리를 돌려줍니다. 2장의 Noisy 다섯을 넣어 확인합니다.

읽는 법 — main 은 Noisy 다섯을 넣는 것으로 바꿨습니다. 다섯째 push 뒤의 5 8 에서 자리가 4 칸에서 8 칸으로 옮겨 갔습니다. 그때 정리: 줄은 찍히지 않았습니다. grow 는 값을 옮기기만 했습니다. main 끝 뒤에 a 부터 e 까지가 넣은 순서대로 한 번씩 정리됐습니다. 둘째 화면은 Drop 구현을 지운 쌍둥이 파일의 것입니다. 정리: 줄이 하나도 없습니다. 값 다섯도, 8 칸짜리 자리도 그대로 남는 누수입니다.
안전: 주석 — 99번 줄은 0 번부터 len 앞까지만 돕니다. 이 실행에서 5번부터 7번 칸은 잡아 두기만 한 칸이라 정리할 값이 없습니다. 106번 줄은 cap 이 0 이 아닐 때만 돌려줍니다. 0 이면 ptr 은 잡은 자리가 아닙니다. 107번 줄의 배치는 grow 가 그 자리를 잡을 때 쓴 것과 같은 layout(cap) 입니다.

pop 은 len 을 먼저 줄이고 그 칸을 read 로 꺼낸다

8부의 pop 은 끝의 값을 Option 으로 꺼내 줬습니다. 꺼낸 값의 주인은 부른 쪽이 되고, 벡터는 그 칸을 더는 자기 값으로 치지 않아야 합니다.

읽는 법 — 메서드를 7부에서 본 대로 따로 선 impl 블록에 적었습니다. 120번 줄이 len 을 줄이고 123번 줄이 그 칸을 read 로 꺼냅니다. 화면의 꺼낸 값 c 바로 뒤에 정리: c 가 있습니다. 144번 줄에서 last 가 스코프를 벗어났습니다. 145번 줄이 찍은 2 4 는 값이 둘, 자리는 그대로 네 칸이라는 것입니다. 148번 줄의 true 는 빈 벡터의 pop 이 117번 줄에서 None 을 줬다는 것입니다. main 끝 뒤에는 a 와 b 만 정리됐습니다. c 가 든 칸은 len 밖이어서 Drop 이 건드리지 않았습니다.
자리를 잡은 적 없는 벡터 — 147번 줄의 empty 는 push 를 한 번도 받지 않아 cap 이 0 인 채로 사라집니다. Drop 의 if self.cap != 0 이 그때 dealloc 을 건너뛰게 합니다.

IntoIterator — 통째로 넘기면 반복자가 자리의 주인이 된다

12부에서 for x in v 는 into_iter() 가 내주는 반복자로 돌았고, v 는 옮겨 갔습니다. 그 into_iter 는 IntoIterator 트레이트의 메서드입니다. 19부의 오류가 이름만 보여 준 트레이트이고, Rust 레퍼런스는 for 가 in 뒤의 값에 이 메서드를 부른다고 적습니다. MyVec 에 구현합니다. 값을 하나씩 내주는 일은 새 타입 MyIter 가 맡습니다.

읽는 법 — 137번과 138번 줄은 10부에서 본 연관 타입입니다. Item 은 내줄 값의 타입이고 IntoIter 는 반복자의 타입입니다. 140번 줄은 self 를 값으로 받아서, 부른 쪽의 MyVec 이 이 함수로 옮겨 옵니다. 141번부터 146번 줄까지가 ptr · cap · len 을 MyIter 에 그대로 넘기고 next 를 0 으로 둡니다. 128번 줄의 주석이 MyIter 의 약속입니다. 값은 next 번 칸부터 len 앞까지만 남아 있습니다. 돌린 화면은 다음 두 슬라이드에 있습니다.
149번 줄이 두 번 정리를 막는다 — 146번 줄 뒤에는 같은 자리를 가리키는 것이 self 와 iter 둘입니다. self 가 그대로 함수 끝에서 스코프를 벗어나면 MyVec 의 Drop 이 값과 자리를 정리하고, iter 는 그 뒤에 같은 자리를 또 쓰게 됩니다. 2장에서 문서가 정의되지 않은 동작이라고 적은 이미 돌려준 자리를 쓰는 것입니다. std::mem::forget(값) 은 값을 받아 정리하지 않고 없앱니다. 문서는 이 함수가 unsafe 가 아닌 까닭을, 정리 코드가 반드시 돈다는 것이 Rust 의 안전 보증에 들어 있지 않기 때문이라고 적습니다. 149번 줄을 뺀 프로그램은 돌려 보이지 않습니다.

next 는 next 번 칸을 read 로 꺼내고 한 칸 나아간다

12부에서 내 타입을 반복자로 만들 때 적은 것은 Item 과 next 둘이었습니다. MyIter 도 같습니다. 꺼내는 방법은 pop 과 같은 read 이고, 끝이 아니라 앞에서부터 꺼냅니다.

읽는 법 — 158번 줄은 next 가 len 에 닿으면 None 을 줍니다. 163번 줄이 그 칸의 값을 꺼내고 164번 줄이 next 를 올려서, 꺼낸 칸은 MyIter 의 약속에서 값이 없는 칸이 됩니다. 202번 줄이 6 8 을, 203번 줄의 pop 이 Some(60) 을 찍었습니다. 205번 줄의 for 는 nums 를 통째로 받아 남은 다섯을 넣은 순서대로 내줬고, 합은 150 입니다. 화면의 나머지 줄은 다음 슬라이드에서 읽습니다.

덜 쓴 반복자는 남은 값을 정리하고 자리를 돌려준다 — MyIter 의 Drop

for 가 끝까지 돌면 칸은 모두 비고 자리만 남습니다. 중간에 그만두면 next 번 칸부터 len 앞까지에 값이 남습니다. 어느 쪽이든 자리의 주인은 이제 MyIter 입니다. MyVec 의 Drop 이 하던 두 가지를 MyIter 가 합니다.

읽는 법 — 220번 줄에서 받은 a 와 b 는 x 가 스코프를 벗어나는 222번 줄에서 하나씩 정리됐습니다. 반복자를 버린다 뒤의 세 줄은 225번 줄의 drop 이 부른 MyIter 의 Drop 입니다. 171번 줄이 2번 칸부터 4번 칸까지를 돌아 c · d · e 를 정리했습니다. a 와 b 는 다시 찍히지 않았고, 226번 줄의 partly 끝 뒤에도 정리된 것이 없습니다. 다섯 값이 한 번씩입니다. 앞 슬라이드의 all 에서는 for 가 끝났을 때 next 와 len 이 같아서 171번 줄이 돌 칸이 없고, 178번 줄부터의 자리 돌려주기만 남습니다.
Drop 이 없으면 — 둘째 화면입니다. 컴파일은 됐고 경고가 하나 붙었습니다 — "필드 cap 을 읽는 곳이 없다". cap 은 자리를 돌려줄 때만 읽는 수입니다. note: 는 이 경고가 기본으로 켜져 있다는 말입니다. 실행한 화면에서는 반복자를 버린다 뒤에 정리: 줄이 없습니다. c · d · e 와 자리가 남는 누수입니다. forget 으로 잊은 MyVec 의 Drop 이 대신 돌아 주지도 않았습니다.

이 장의 첫 슬라이드가 말한 첫째 증거입니다. MyVec 과 Vec 에 글자까지 같은 코드를 돌리려고 1장의 매크로를 씁니다. script! 는 벡터를 만드는 식 하나를 expr 로 받고, 그 벡터에 일을 시킬 때마다 보이는 것을 글로 모아 돌려줍니다.

extern 블록의 선언마다 safe 인지 unsafe 인지 적는다

16부는 C 의 abs 와 strlen 을 unsafe extern "C" 블록에 선언하고 unsafe 블록에서 불렀습니다. 다른 언어의 함수를 부르고, 다른 언어에서 불리는 이 통로를 FFI(foreign function interface)라고 합니다. 이 장은 16부의 그 슬라이드 위에 올립니다. 먼저 선언입니다. 블록 안의 선언 하나하나에 safe 나 unsafe 를 붙일 수 있습니다.

읽는 법 — 6번 줄에서 safe 로 선언한 sqrt 는 15번 줄에서 unsafe 블록 없이 불렀고 4 를 찍었습니다. 8번 줄은 unsafe 를 적은 선언이고, 10번 줄은 16부처럼 아무것도 적지 않은 선언입니다. 18번과 20번 줄은 두 호출을 따로 감쌌습니다. 16부에서 컴파일러는 필요 없는 unsafe 블록에 경고를 붙였습니다. 20번 줄에는 경고가 없습니다. 아무것도 적지 않은 선언은 unsafe 입니다. 출력의 5 는 "hello" 의 길이, 42 는 atoi 가 글 "42" 를 읽은 수입니다.
safe 는 선언한 사람의 약속이다 — safe 라고 적으면 부르는 쪽은 어떤 인자든 넣을 수 있습니다. 그래도 정의되지 않은 동작이 없다는 것을 선언한 사람이 보증하고, 4번 줄 블록 앞의 unsafe 가 그 책임의 표시입니다. C 표준에서 sqrt 는 음수를 받아도 정의되지 않은 동작이 아닙니다. 16부가 부른 abs 는 다릅니다. C 표준은 결과가 int 에 들어가지 않을 때의 동작을 정하지 않습니다. 16부의 주석이 "-7 의 절댓값은 c_int 에 들어가고" 를 적은 까닭이고, 그런 함수는 unsafe 로 둡니다.

2024 에디션은 unsafe 없는 extern 블록을 받지 않는다 — extern blocks must be unsafe

1부가 옮겨 적은 2024 에디션의 변화 가운데 "extern 블록에 unsafe 키워드를 붙여야 한다" 가 있었습니다. 그때는 돌려 보지 않았습니다. 1부가 gen 에서 한 것처럼, 글자까지 같은 파일을 두 에디션으로 컴파일합니다.

읽는 법 — 오류 첫 줄은 "extern 블록은 unsafe 여야 한다" 이고 번호가 없습니다. 3번부터 5번 줄까지의 블록을 짚고, help: 가 extern 키워드 앞에 unsafe 가 필요하다고 합니다. 둘째 화면에서 2021 에디션은 같은 파일을 받아 7 을 찍었습니다. 화면 첫 줄의 --edition 2021 만 다릅니다.
고치려면 — 3번 줄을 앞 슬라이드의 4번 줄처럼 unsafe extern "C" { 로 적습니다. 블록 안의 선언이 C 쪽 함수와 맞는지는 컴파일러가 확인하지 못합니다. 2024 에디션은 그 책임을 블록 앞에 적게 했습니다.

c_int 와 c_long 은 대상 플랫폼이 정하는 별명이다

C 의 int 와 long 은 비트 수가 이름에 적혀 있지 않습니다. std::ffi 는 그 타입들에 맞춘 이름 c_int · c_long · c_char 를 두고, 0부에서 본 대상 플랫폼마다 알맞은 Rust 타입의 별명으로 정해 둡니다. 18부의 type_name 으로 이 기계의 답을 봅니다.

읽는 법 — 6번 줄이 i32 4 를, 7번 줄이 i64 8 을 찍었습니다. 이 책을 만든 기계에서 c_int 는 i32, c_long 은 i64 의 별명입니다. type_name 은 별명이 아니라 본래 타입의 이름을 줬습니다. 10번 줄에서 c_char 는 한 바이트입니다. 12번 줄의 true 는 *const c_void 가 usize 와 크기가 같다는 것입니다. c_void 는 C 의 void* 를 적을 때 포인터 뒤에 두는 타입입니다.
이 수는 이 기계의 것이다 — 문서는 c_long 이 대상 플랫폼에 따라 32 비트이기도 하고, c_char 가 i8 이기도 u8 이기도 하다고 적습니다. 그래서 C 의 long 이 오가는 자리에는 i64 가 아니라 c_long 이라고 적습니다. c_char 의 부호에 기대는 코드도 쓰지 않습니다.

CString — 끝에 0 을 붙여 C 에 넘길 글을 만든다

C 의 글은 길이를 들고 다니지 않고, 0 바이트가 나오는 곳에서 끝납니다. Rust 의 String 과 &str 은 주소와 길이이고 끝에 0 이 없습니다. 16부는 끝에 0 이 붙는 리터럴 c"hello" 를 썼습니다. 실행 중에 만든 글은 CString 으로 옮깁니다.

읽는 법 — 9번 줄의 글은 9 바이트입니다. 13번 줄의 CString::new 가 그 String 을 넘겨받았고, 14번 줄이 찍은 10 은 끝의 0 까지 센 바이트 수입니다. 17번 줄의 as_ptr() 가 준 포인터로 strlen 은 9 를 셌습니다. 0 앞까지입니다. 21번 줄은 가운데에 0 이 든 글이라 Err 입니다. 앞 슬라이드의 13번과 17번 줄을 줄여, CString 을 만든 자리에서 바로 as_ptr() 를 부르고 포인터만 변수에 담아 봅니다. 컴파일만 하고 돌리지는 않습니다.

#[repr(C)] 는 필드를 적은 순서대로, C 의 규칙으로 놓는다

18부는 #[repr(C)] 를 "적은 순서대로 놓게 하는 속성" 이라고만 하고 이 부로 미뤘습니다. C 와 구조체를 주고받으려면 두 언어가 필드의 자리를 똑같이 알아야 합니다. Rust 의 기본 배치는 18부에서 본 대로 필드의 순서를 약속하지 않습니다. #[repr(C)] 는 C 컴파일러가 쓰는 규칙을 따르게 합니다. 같은 필드 넷을 두 가지 순서로 적습니다.

읽는 법 — 35번 줄이 찍은 [1, 2, 4] 는 u8 · u16 · u32 의 정렬입니다. 이 기계의 수입니다. 24번 줄의 layout! 은 1장에서 본 + 반복으로 필드마다 자리를 찍고, 빗금 뒤에 전체 크기와 정렬을 찍습니다. Wide 는 0 4 8 10 / 12 4 입니다. tag 가 0, value 는 4 의 배수인 4, flag 가 8, count 는 2 의 배수인 10 입니다. 1번부터 3번까지와 9번 바이트는 18부에서 본 패딩입니다. Tight 는 0 4 6 7 / 8 4 로 빈 바이트가 없습니다. 같은 필드 넷인데 적은 순서에 따라 12 바이트와 8 바이트입니다.
적은 순서가 약속이 된다 — Rust 레퍼런스는 #[repr(C)] 구조체의 규칙을 이렇게 적습니다. 필드는 적은 순서대로, 앞 필드가 끝난 뒤 자기 정렬의 배수인 가장 가까운 자리에 놓고, 전체 크기는 가장 큰 정렬의 배수로 맞춥니다. 위의 수는 그 규칙에 세 타입의 정렬을 넣은 결과입니다. 18부의 Fixed 가 12 바이트였던 것도 같은 규칙입니다. 5번과 15번 줄의 #[allow(dead_code)] 는 읽지 않는 필드의 경고를 끈 것입니다.

Rust 함수를 C 쪽에 내놓는다 — #[unsafe(no_mangle)] 와 extern "C"

이번에는 Rust 함수가 불리는 쪽입니다. 필요한 것은 둘입니다. 하나는 콜백에서 본 extern "C" 이고, 하나는 부르는 쪽이 찾을 이름입니다. 컴파일된 함수가 링커에게 보이는 이름을 기호(symbol)라고 합니다. Rust 레퍼런스는 no_mangle 속성이 기호 이름을 바꿔 적는 일(mangling)을 끄고, 함수의 이름을 그대로 기호 이름으로 쓰게 한다고 적습니다. 1장의 두 크레이트 예제와 같은 꼴로 컴파일합니다.

읽는 법 — calc.rs 의 9번 줄이 속성이고, 10번 줄이 pub extern "C" fn 입니다. main.rs 의 4번부터 7번 줄까지는 16부에서 C 함수에 쓰던 선언 그대로입니다. 11번 줄은 calc::add 를 Rust 경로로 불렀고, 13번 줄은 calc_add 를 선언한 이름만으로 불렀습니다. 둘 다 5 입니다. 14번 줄의 calc_twice(21) 은 42 입니다. calc.rs 에서 그 함수의 이름은 double 이고, 15번 줄의 export_name 속성이 기호 이름을 따로 정했습니다. calc.rs 의 5번 줄은 wrapping_add 입니다. 내놓는 함수도 콜백처럼 패닉하지 않게 적었습니다.
부르는 쪽도 Rust 다 — 이 책의 도구는 C 컴파일러를 돌리지 않습니다. 그래서 C 프로그램 대신, C 함수를 부를 때와 같은 선언을 적은 Rust 크레이트가 불렀습니다. main.rs 가 calc_add 와 calc_twice 에 대해 아는 것은 4번부터 7번 줄에 적은 이름과 타입뿐입니다. C 프로그램이 같은 두 이름을 부르는 것은 돌려 보이지 못했습니다.

2024 에디션은 unsafe 없는 no_mangle 을 받지 않는다 — unsafe attribute used without unsafe

속성을 unsafe( ) 로 감싸는 표기도 extern 블록 앞의 unsafe 처럼 2024 에디션에서 필수가 됐습니다. 옛 표기 #[no_mangle] 로 적은 파일을 두 에디션으로 컴파일합니다.

읽는 법 — 오류 첫 줄은 "unsafe 속성을 unsafe 없이 썼다" 이고 번호가 없습니다. 3번 줄의 no_mangle 을 짚고, help: 가 unsafe(...) 로 감싼 줄을 보여 줍니다. 둘째 화면에서 2021 에디션은 같은 파일을 받아 5 를 찍었습니다.
속성인데 왜 unsafe 인가 — 에디션 안내서는 까닭을 이렇게 적습니다. no_mangle 로 내놓은 이름이 프로그램에 함께 이어지는 다른 기호, 이를테면 C 라이브러리의 함수 이름과 겹치면 정의되지 않은 동작이 될 수 있고, 컴파일러는 그 겹침을 확인해 주지 못합니다. 앞 슬라이드의 export_name 도 같은 까닭으로 unsafe( ) 안에 적었습니다. 그 예제가 이름 앞에 calc_ 를 붙인 것도 겹치지 않게 하려는 것입니다.

16부의 다섯 가지 가운데 다섯째입니다. union( 부터)은 C 의 공용체에 맞춘 타입으로, 모든 필드가 같은 자리를 함께 씁니다. 7부의 열거형과 달리, 지금 어느 필드로 값이 들어 있는지는 어디에도 적혀 있지 않습니다. 네 바이트를 u32 로도, 바이트 넷으로도 보는 union 입니다.

읽어도 되는 필드인지는 사람이 안다 — 13번 줄의 주석은 마지막으로 넣은 필드를 읽는다는 것입니다. 17번과 18번 줄의 주석은 다른 필드로 읽어도 되는 까닭을 적습니다. 네 바이트가 모두 채워져 있고, 2장에서 본 안 되는 비트 모양이 [u8; 4] 에는 없습니다. 2번 줄의 #[repr(C)] 는 C 의 공용체와 같은 배치를 약속합니다. C 와 맞출 일이 아니면 7부의 열거형을 씁니다.

static mut — 읽는 것도 고치는 것도 unsafe 인 전역 변수

다섯 가지의 셋째입니다. 3부의 static 은 프로그램 내내 한 자리에 놓이는 값이었습니다. mut 를 붙이면 어디서나 고칠 수 있는 전역 변수가 됩니다. 어느 함수에서나, 어느 스레드에서나 닿을 수 있어서 6부의 빌림 규칙을 컴파일러가 지켜 줄 수 없습니다. 그래서 닿는 일이 모두 unsafe 입니다.

읽는 법 — 7번 줄의 CALLS += 1 도, 값을 복사해 읽기만 하는 14번 줄도 unsafe 블록 안에 있습니다. 14번 줄의 블록에 "필요 없는 unsafe" 경고가 붙지 않았습니다. 읽는 것만으로도 unsafe 입니다. record 를 두 번 불러 2 가 찍혔습니다. 5번과 6번 줄의 주석이 이 프로그램에서 괜찮은 까닭을 적습니다. 스레드가 하나뿐이고, CALLS 를 가리키는 참조를 만들지 않습니다. 여러 스레드가 함께 고치면 16부의 E0133 이 꼽던 데이터 경쟁이 됩니다.

앞 슬라이드는 값을 복사해 읽었습니다. 참조를 만들면 이야기가 달라집니다. 8번 줄은 &CALLS 를 만들고, 12번 줄은 CALLS 를 println! 에 그대로 넘깁니다.

읽는 법 — 오류 첫 줄은 "바뀔 수 있는 static 을 가리키는 불변 참조를 만든다" 이고 번호가 없습니다. 첫 note: 가 까닭입니다 — "그 참조가 사는 동안 static 이 고쳐지거나 그것의 가변 참조가 만들어지면 정의되지 않은 동작". 둘째는 에디션 안내서의 주소이고, 셋째는 이 검사 static_mut_refs 가 2024 에디션에서 기본으로 오류(deny)라는 말입니다. help: 는 &raw const 로 날 포인터를 만들라고 합니다. 둘째 오류는 & 를 적지 않은 12번 줄입니다. 컴파일러는 거기서도 불변 참조가 만들어진다고 하고, help: 는 14부에서 본 내부 가변성을 가진 타입을 쓰라고 권합니다.
2021 에디션에서는 경고였다 — 셋째 화면은 같은 파일을 2021 에디션으로 컴파일한 화면의 끝입니다. 경고 둘과 함께 컴파일되어 1 1 을 찍었습니다. 릴리스 노트에 따르면 이 검사는 에 경고로 들어왔습니다. 이 파일의 두 참조는 7번과 11번 줄의 주석대로 조건을 지킵니다. 2024 에디션은 지켰는지를 가리지 않고, 참조를 만드는 것부터 막습니다.

퀴즈 — FFI

Q. C 의 strlen 에 넘길 포인터를 let p = CString::new("hello").unwrap().as_ptr(); 로 만들고, 다음 줄에서 unsafe { strlen(p) } 를 불렀습니다. 컴파일될까요? 무엇이 잘못됐고, 어떻게 고칠까요?

A. 컴파일은 됩니다. 오류가 아니라 경고가 나옵니다 — "임시 CString 이 문 끝에서 정리되므로 매달린 포인터가 만들어진다"(cstring_dangle.rs 의 화면). CString 이 변수에 담기지 않아 그 줄에서 사라졌고, p 는 이미 돌려준 자리를 가리킵니다. 그래서 그 파일은 돌리지 않았습니다. 고치려면 경고의 help: 대로 CString 을 먼저 변수에 담고, 그 변수가 살아 있는 동안 as_ptr() 를 넘깁니다. cstring.rs 의 13번과 17번 줄이 그렇게 적었고, strlen 은 9 를 돌려줬습니다.
