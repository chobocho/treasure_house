  • 1장 첫 프로그램 — 파일 하나를 rustc 로 컴파일해 돌리기, 주석·세미콜론·에디션

1장

첫 프로그램

main 함수 · rustc 로 컴파일 · 주석과 문 · 세미콜론 · 매크로의 느낌표 · 에디션

프로그램은 main 함수에서 시작한다

0부에서 화면 읽는 법의 보기로 쓴 세 줄입니다. 이번에는 줄마다 뜻을 봅니다. Rust 프로그램은 main 이라는 함수에서 시작하고, 소스 파일의 확장자는 .rs 입니다.

  • fn — 함수를 만드는 키워드입니다. 이 main 은 매개변수도 반환값도 없습니다.
  • println! — 한 줄을 찍고 줄을 바꿉니다. 끝의 ! 는 이것이 함수가 아니라 매크로라는 표시입니다.
  • 들여쓰기는 공백 네 칸이 관례입니다.

컴파일하고, 그다음에 돌린다

Rust 는 미리 컴파일하는 언어입니다. rustc 가 소스를 기계어 실행 파일로 바꿔 놓으면, 그 파일을 따로 돌립니다. 인터프리터가 없습니다.

hello.rs→ rustc→ hello (실행 파일)→ ./hello
실행 파일은 혼자 돕니다 — 만들어진 hello 는 Rust 가 설치되지 않은 같은 종류의 기계에 옮겨도 그대로 실행됩니다.

주석은 컴파일러가 읽지 않고, 문은 세미콜론으로 끝난다

컴파일러가 읽지 않는 글이 주석입니다. 문(statement)은 세미콜론으로 끝납니다.

  • let — 값에 이름을 붙이는 문입니다. 3부에서 봅니다.
  • {name} — 중괄호 안에 변수 이름을 쓰면 그 값이 들어갑니다. 서식은 3장에서 봅니다.

세미콜론을 빼먹으면

앞 슬라이드의 규칙을 일부러 어겨 봅니다. 2번 줄 끝에 세미콜론이 없습니다.

읽는 법 — 0부에서 본 대로 --> 뒤가 파일:줄:칸이고, ^ 가 문제의 자리를 가리킵니다. ; 을 기다렸는데 3번 줄의 let 을 만났다는 말입니다. help: 는 고치는 법입니다 — 그 자리에 ; 을 넣으라고 합니다. Rust 컴파일러는 대개 답을 같이 알려 줍니다.

느낌표를 빼먹으면 — E0423

println 이라는 함수는 없습니다. 있는 것은 매크로 println! 입니다.

읽는 법 — = note: 가 같은 이름의 매크로는 있다고 알려 주고, help: 아래에 고친 줄이 그대로 나옵니다. + 가 넣을 글자 ! 의 자리입니다.
오류 번호 — 0부에서 본 대로 error[E0423] 같은 번호가 붙은 오류는 rustc --explain E0423 으로 긴 설명을 볼 수 있습니다. 문법 오류(앞 슬라이드)에는 번호가 없습니다.

에디션 — 같은 컴파일러, 다른 문법 판

이 장의 명령에는 모두 --edition 2024 가 붙어 있었습니다. 에디션(edition)은 1부 4장에서 본 대로, 옛 코드를 깨지 않으려고 나눈 문법의 판입니다. 거기서 예로 든 let async = 1; 을 직접 컴파일합니다 — 2015 에디션에서는 async 가 키워드가 아닌 보통 이름이라 변수로 쓸 수 있습니다.

rustc 의 기본값은 2015 — --edition 을 주지 않으면 가장 옛 판으로 컴파일합니다. 0부에서 말한, 이 책의 명령에 --edition 2024 가 붙는 까닭이 이것입니다. cargo 로 만든 프로젝트는 설정 파일에 에디션이 적혀 있어 따로 줄 필요가 없습니다(2장).

같은 코드를 2024 에디션으로

2018 에디션부터 async 는 키워드입니다. 같은 파일이 이제는 컴파일되지 않습니다.

읽는 법 — 첫 오류가 본론입니다. 2번 줄의 async 가 키워드라 이름 자리에 올 수 없다는 말이고, help: 의 r#async 는 1부에서 본 날 식별자입니다. 둘째 오류는 3번 줄의 async 도 키워드로 읽은 탓에 따라 나온 것입니다.
에디션은 크레이트(crate)마다 고릅니다 — 이 예제에서는 파일 하나가 크레이트입니다. 1부에서 본 대로 옛 에디션으로 쓴 라이브러리와 새 에디션으로 쓴 프로그램을 한데 묶어 쓸 수 있습니다.

퀴즈 — 1장

Q. let async = 1; 이 든 같은 파일이 한 번은 컴파일되어 1 을 찍었고, 한 번은 오류가 났습니다. 두 번 사이에 무엇이 달랐습니까?

A. 에디션입니다. --edition 2015 에서는 async 가 보통 이름이고, --edition 2024 에서는 키워드라 expected identifier, found keyword 오류가 납니다. 소스도 컴파일러도 같았습니다.

2장

cargo

cargo new · Cargo.toml · build · run · --release · check · fmt · clippy

cargo new 가 프로젝트의 뼈대를 만든다

파일이 늘어나면 rustc 를 손으로 부르기가 번거롭습니다. cargo 는 프로젝트를 만들고, 컴파일하고, 돌리는 일을 한데 맡는 Rust 의 빌드 도구입니다.

  • Cargo.toml — 프로젝트를 설명하는 설정 파일입니다.
  • src/main.rs — 소스는 src/ 아래에 둡니다. 프로그램은 이 파일의 main 에서 시작합니다.
  • --vcs none — 버전 관리 저장소를 함께 만들지 말라는 옵션입니다. 화면을 짧게 하려고 붙였습니다.

Cargo.toml — 프로젝트를 설명하는 파일

방금 만들어진 두 파일의 내용입니다. 사람이 쓴 글자는 하나도 없습니다.

줄뜻
name패키지 이름 — 실행 파일의 이름도 이것
version이 프로젝트의 버전 — 0.1.0 에서 시작
edition에디션 — cargo 가 rustc 에 대신 붙여 주는 --edition 2024
[dependencies]가져다 쓸 바깥 크레이트의 목록 — 이 책은 표준 라이브러리만 쓰므로 늘 빈칸
TOML — [구역] 아래에 키 = "값" 을 한 줄씩 적는 설정 파일 형식입니다. Cargo.toml 의 나머지 항목은 13부에서 봅니다.

cargo build — 컴파일해서 target/ 아래에 둔다

같은 뼈대에서 main.rs 만 고친 프로젝트입니다. cargo build 는 Cargo.toml 을 읽고 rustc 를 대신 불러 줍니다.

  • Compiling 줄 — 패키지 이름·버전·프로젝트 자리입니다. /work 는 0부에서 본 대로 이 책이 고정해 실은 경로입니다.
  • Finished 줄 — 걸린 시간도 같은 까닭으로 0.00s 로 고정해 실었습니다.
  • 실행 파일은 target/debug/패키지이름 에 생깁니다.

cargo run — 빌드하고 바로 돌린다

실행 파일의 경로를 손으로 칠 일은 드뭅니다. cargo run 은 필요하면 빌드하고, 이어서 돌립니다.

  • 이번에는 Compiling 줄이 없습니다. 소스가 그대로라서 다시 컴파일하지 않았습니다.
  • Running 줄이 cargo 가 실제로 돌린 파일입니다. 앞 슬라이드에서 손으로 돌린 그 파일입니다.
  • -q(quiet) 를 붙이면 cargo 자신의 말은 빠지고 프로그램의 출력만 남습니다.

--release — 최적화한 실행 파일은 다른 자리에 생긴다

지금까지 만든 것은 디버그 빌드입니다. 남에게 건네거나 속도를 잴 때는 --release 를 붙여 최적화한 실행 파일을 따로 만듭니다.

cargo buildcargo build --release
프로필devrelease
Finished 줄unoptimized + debuginfooptimized
실행 파일target/debug/target/release/
cfg!(debug_assertions)truefalse
두 빌드는 동작도 조금 다릅니다 — cfg!(debug_assertions) 는 디버그용 검사가 켜져 있는지를 알려 주는 값입니다. 빌드에 따라 달라지는 대표적인 동작이 정수 넘침(overflow)이며, 3부에서 봅니다.

cargo check — 실행 파일은 만들지 않고 검사만

코드를 고치는 동안 궁금한 것은 대개 "컴파일이 되는가" 하나입니다. cargo check 는 오류 검사까지만 하고 실행 파일을 만드는 마지막 단계를 건너뜁니다.

명령하는 일실행 파일
cargo check오류 검사만없음
cargo build검사 + 실행 파일 만들기target/debug/
cargo runbuild + 실행target/debug/
cargo clean — cargo 가 만든 target/ 을 통째로 지웁니다(-q 는 여기서도 "조용히"). 앞에서 만든 실행 파일을 치우려고 먼저 돌렸습니다. 소스는 건드리지 않습니다.

cargo fmt — 코드의 모양은 도구에 맡긴다

들여쓰기와 띄어쓰기는 컴파일러가 따지지 않습니다. 그래서 사람마다 달라지기 쉬운데, Rust 는 공식 포매터 rustfmt 로 모양을 하나로 맞춥니다.

  • cargo fmt --check — 고치지 않고 차이만 보입니다. - 줄이 지금, + 줄이 고친 뒤입니다. 고칠 것이 있으면 종료 코드가 1 입니다.
  • cargo fmt — 말없이 파일을 고쳐 씁니다. 뜻은 그대로라 출력도 같습니다.
  • 이 책의 예제도 rustfmt 를 거쳤습니다. 좁은 화면에 맞추려고 한 줄을 72칸으로 줄인 것만 다릅니다. 위 예제처럼 일부러 흐트러뜨렸거나, 문법 오류를 보이려고 깨 둔 것만 그대로 두었습니다.

cargo clippy — 컴파일러가 넘어가는 것을 짚어 준다

컴파일된다고 좋은 코드인 것은 아닙니다. clippy 는 흔한 실수와 어색한 표현을 찾아 주는 검사 도구(lint)입니다.

읽는 법 — 컴파일 오류와 생김새가 같습니다. --> 가 자리, help: 가 고치는 법입니다. 빈 문자열을 지우고 println!() 로 쓰라는 뜻입니다. clippy::println_empty_string 이 이 검사의 이름이고, 그 윗줄의 주소에 긴 설명이 있습니다.

퀴즈 — 2장

Q. 패키지 이름이 hello_cargo 입니다. ① cargo build --release 뒤에 실행 파일은 어디에 있습니까? ② target/ 이 빈 상태에서 cargo check 만 했다면 target/debug/hello_cargo 는 있습니까?

A. ① target/release/hello_cargo 입니다. 디버그 빌드의 target/debug/ 와 자리가 다릅니다. ② 없습니다. check 는 검사만 하고 실행 파일을 만들지 않아, ls 가 No such file or directory 라고 답했습니다.

3장

println! 서식

{} · {:?} · {:#?} · 이름 붙인 인자 · {{ }} · 폭과 정렬 · 정밀도 · 진법 · print! · eprintln! · format! · dbg!

{} 자리에 인자가 차례로 들어간다

1장부터 뜻을 미뤄 두고 써 온 {} 를 이제 제대로 봅니다. println! 의 첫 인자는 서식 문자열입니다. 그 안의 {} 는 값이 들어갈 자리이고, 뒤따르는 인자가 왼쪽부터 하나씩 채웁니다.

  • 값을 문자열로 바꾸는 일은 println! 이 합니다. 따로 변환 함수를 부르지 않습니다.
  • {0} · {1} 처럼 번호를 쓰면 몇 번째 인자인지 직접 고릅니다. 번호는 0 부터 셉니다.

{} 로 찍을 수 없는 값도 있다 — E0277

앞 슬라이드에서는 정수·실수·불·문자를 모두 {} 로 찍었습니다. 값 여러 개를 괄호로 묶은 튜플은 그렇게 되지 않습니다. 컴파일부터 막힙니다.

읽는 법 — {} 는 "사람에게 보여 줄 모양"이 정해진 타입만 찍습니다. 그 약속의 이름이 Display 이고, 정수 둘의 튜플 ({integer}, {integer}) 에는 그것이 없다는 말입니다. 고치는 법은 = note: 줄에 있습니다 — {:?} 를 쓰라고 합니다. 이런 약속을 트레이트(trait)라고 하며 10부에서 봅니다.

{:?} — 들여다보기 위한 출력

컴파일러가 알려 준 대로 고칩니다. {:?} 는 값의 속을 개발자가 확인하라고 찍는 디버그(Debug) 출력입니다.

  • {} 는 사용자에게 보일 글, {:?} 는 개발자가 볼 글입니다.
  • 문자열을 {:?} 로 찍으면 따옴표가 붙고, 탭은 \t 로 보입니다. 눈에 안 보이는 글자를 찾을 때 씁니다.
  • 튜플과 배열 자체는 3부에서 봅니다. 여기서는 찍는 법만 봅니다.

{:#?} — 여러 줄로 펼쳐서 찍는다

속이 깊은 값은 한 줄로 찍으면 읽기 어렵습니다. ? 앞에 # 을 넣으면 한 줄에 하나씩 들여 써서 보여 줍니다.

값이 커지면 {:#?} — 7부의 구조체나 8부의 컬렉션처럼 속이 깊은 값을 확인할 때 가장 자주 쓰게 됩니다.

중괄호 안에 변수 이름을 바로 쓴다

자리와 인자가 멀어지면 짝을 맞추기 어렵습니다. 찍을 것이 변수라면 그 이름을 중괄호 안에 쓰면 됩니다. 1장에서 먼저 써 본 {name} 이 이 꼴입니다.

  • {size:?} — 이름 뒤에 : 을 찍고 서식을 씁니다. {:?} 의 앞자리에 이름이 들어간 꼴입니다.
  • area = width * height — 인자에 이름을 붙여 넘기는 방법입니다. 변수가 없어도 이름으로 가리킬 수 있습니다.

중괄호 안에 식은 쓸 수 없다

중괄호 안에 들어가는 것은 이름 하나뿐입니다. 곱셈 같은 식을 넣으면 서식 문자열이 잘못됐다는 오류가 납니다.

읽는 법 — ^ 가 가리키는 * 자리에서 닫는 중괄호를 기다렸다는 말입니다. 이름 width 까지만 읽고 } 를 찾은 것입니다. 1장의 세미콜론 오류처럼 번호가 붙지 않는 오류입니다.

식은 인자로, 중괄호 글자는 두 번

앞 슬라이드를 고친 것입니다. 식은 중괄호 밖으로 꺼내 인자로 넘깁니다. 그리고 오류의 = note: 가 알려 준 대로, 중괄호 글자 자체를 찍으려면 두 번 겹쳐 씁니다.

왜 두 번인가 — 서식 문자열에서 { 는 "여기에 값이 온다"는 뜻으로 이미 쓰입니다. 그래서 글자로서의 중괄호는 {{ 와 }} 로 구별합니다.

폭과 정렬 — {:6} · {:<6} · {:^6} · {:>6}

표처럼 줄을 맞춰 찍으려면 값이 차지할 폭을 정합니다. : 뒤의 숫자가 폭입니다.

  • 정렬을 적지 않으면 문자열은 왼쪽, 숫자는 오른쪽에 붙습니다.
  • 채움 글자는 정렬 기호 바로 앞에 한 글자만 씁니다. {:*^6} 은 "* 로 채우고 가운데, 폭 6" 입니다.
폭은 글자 수입니다 — 한글은 화면에서 두 칸을 차지하지만 한 글자로 셉니다. 출력 마지막 줄의 닫는 대괄호가 출력 첫째 줄보다 두 칸 밀린 까닭입니다. 한글이 섞인 표는 {:6} 만으로는 줄이 맞지 않습니다.

정밀도 · 부호 · 0 채움 — 숫자를 다듬어 찍는다

실수를 그대로 찍으면 자릿수가 들쭉날쭉합니다. 점(.) 뒤의 숫자로 소수 자릿수를 정합니다.

  • {:.2} 는 자르지 않고 반올림합니다. 1234.5678 이 1234.57 이 됐습니다.
  • {:05} 의 0 은 채움 글자가 아니라 별도의 표시입니다. 그래서 부호가 0 들의 앞에 옵니다 — -0042.
  • 순서는 부호 → 0 → 폭 → .정밀도 입니다. {:+010.2} 가 그 예입니다.

진법 — {:x} · {:o} · {:b} 와 접두어 #

정수는 서식 끝에 글자 하나를 붙여 16진수·8진수·2진수로 찍을 수 있습니다. 비트나 색상 값을 볼 때 씁니다.

서식뜻255
{:x} · {:X}16진수 (소문자 · 대문자)ff · FF
{:o}8진수377
{:b}2진수11111111
{:#x}접두어를 붙인다0xff
접두어도 폭에 듭니다 — {:#010b} 의 10 은 0b 두 글자를 합친 폭입니다. 여덟 자리 비트를 원하면 {:08b} 또는 {:#010b} 입니다. 서식 전체 표는 부록에 있습니다.

print! 는 줄을 바꾸지 않는다

중괄호 안에 쓰는 서식은 여기까지이고, 남은 것은 println! 곁의 매크로 넷입니다. 첫째가 print! 입니다. println! 의 ln 은 line 이고, 끝에 줄바꿈을 붙이지 않는 짝이 이것입니다. 서식 문자열의 규칙은 둘이 같습니다.

빈 줄은 println!() — 2장에서 clippy 가 권한 바로 그 꼴입니다. println!("") 처럼 빈 문자열을 넘길 필요가 없습니다.

eprintln! — 결과와 알림은 다른 길로 내보낸다

프로그램의 출력 길은 둘입니다. 결과는 표준 출력(stdout)으로, 경고와 오류 알림은 표준 오류(stderr)로 보냅니다. eprintln! 이 표준 오류로 찍는 매크로입니다.

  • 그냥 돌리면 두 줄이 한 화면에 섞여 보입니다. 이 책의 어두운 상자도 둘을 합쳐 실은 것입니다.
  • 한쪽을 /dev/null 로 버려 보면 두 줄이 서로 다른 길로 나왔음이 드러납니다.
  • 결과를 파일로 받거나 다른 프로그램에 넘길 때, 알림이 결과에 섞이지 않습니다.

format! — 찍지 않고 문자열로 돌려받는다

서식을 적용한 글을 화면이 아니라 변수에 담고 싶을 때가 있습니다. format! 은 println! 과 같은 서식 문자열을 받아, 찍는 대신 문자열을 만들어 돌려줍니다.

돌려받는 타입은 String — 프로그램이 돌면서 만들어 내는 문자열의 타입입니다. 큰따옴표로 적은 문자열과 어떻게 다른지는 8부에서 봅니다.

dbg! — 식과 값을 자리와 함께 찍는다

값을 잠깐 확인하려고 println! 을 쓰면 서식 문자열부터 적어야 합니다. dbg! 는 식을 감싸기만 하면 됩니다.

  • [dbg.rs:4:13] 은 파일:줄:칸입니다. 칸 번호는 부터 붙습니다.
  • 값을 그대로 돌려주므로 식 한가운데에 끼워 넣을 수 있습니다. b 는 여전히 11 입니다.
  • eprintln! 처럼 표준 오류로 찍습니다. 확인이 끝나면 지웁니다.

퀴즈 — 3장

Q. 다음 두 줄은 각각 무엇을 찍습니까?
① println!("[{:^6}]", 42);
② println!("{:05}", -42);

A. ① [ 42 ] — 폭 6 의 가운데에 놓고 양쪽을 공백으로 채웁니다. ② -0042 — 부호까지 합쳐 다섯 글자이고, 0 은 부호 뒤에 채워집니다. 000-42 가 아닙니다.

입력

표준 입력 한 줄 읽기 · trim 과 parse · 명령 줄 인자

read_line — 한 줄을 읽어 문자열에 붙인다

3장까지는 찍기만 했습니다. 키보드로 친 글자는 표준 입력(stdin)으로 들어오고, read_line 이 엔터를 누를 때까지의 한 줄을 읽습니다. 이 책은 키보드 대신 printf '…' | 로 같은 글자를 흘려 넣습니다.

  • use std::io; — 표준 라이브러리의 입출력 모듈을 io 라는 이름으로 쓰겠다는 선언입니다.
  • let mut 과 &mut line — read_line 이 line 을 고쳐 쓸 수 있게 내주는 표시입니다. 3부와 6부에서 봅니다.
  • .expect("…") — 읽기가 실패하면 이 글을 남기고 프로그램을 멈춥니다.
줄바꿈도 읽힙니다 — 두 글자를 쳤는데 3 바이트입니다. 엔터가 \n 으로 따라 들어왔습니다.

줄바꿈이 붙은 채로는 숫자가 되지 않는다

입력은 언제나 문자열로 옵니다. 계산에 쓰려면 parse 로 숫자로 바꿔야 하는데, 앞 슬라이드에서 본 \n 이 걸립니다.

읽는 법 — 컴파일 오류가 아니라 실행 중에 멈춘 것, 곧 0부에서 본 패닉(panic)입니다. parse_no_trim.rs:7:31 이 멈춘 자리이고, 다음 줄이 expect 에 적어 둔 글과 까닭입니다. InvalidDigit 은 숫자가 아닌 글자가 있었다는 뜻입니다. 종료 코드도 그때처럼 101 입니다.

trim 으로 떼어 내고 parse 한다

고친 것은 한 군데, .trim() 입니다. 앞뒤의 공백과 줄바꿈을 떼어 낸 다음에 숫자로 바꿉니다.

  • let n: i32 — parse 는 무엇으로 바꿀지를 이 타입 표기에서 압니다. i32 는 정수 타입입니다.
  • 이 장에서는 실패하면 expect 로 멈추기만 합니다. 멈추지 않고 다루는 법은 9부에서 봅니다.
읽은 줄을 숫자로 — line.trim().parse() 를 한 묶음으로 기억하면 됩니다.

명령 줄 인자는 env::args 로 받는다

프로그램 이름 뒤에 띄어 적은 낱말들이 명령 줄 인자입니다. 돌리는 도중에 묻지 않고, 시작할 때 값을 건네받는 길입니다.

  • 0번은 프로그램 자신(./args)이고, 사용자가 준 인자는 1번부터입니다.
  • Vec<String> 은 문자열을 여러 개 담는 목록이고(8부), collect() 는 차례로 나오는 값을 그런 목록으로 모으는 메서드입니다(12부).
  • 인자도 문자열로 옵니다. 숫자로 쓰려면 역시 parse 입니다. 줄바꿈이 붙어 오지 않으므로 trim 없이도 됐습니다.
여기까지 — 파일 하나를 컴파일해 돌리고, cargo 로 프로젝트를 다루고, 값을 찍고 읽을 수 있게 됐습니다. 3부부터는 이 도구로 문법을 하나씩 돌려 봅니다. 첫 차례는 변수와 기본 타입입니다.

퀴즈 — 4장

Q. 21 을 치고 엔터를 눌렀습니다. ① read_line 이 채운 문자열을 {:?} 로 찍으면 무엇이 보입니까? ② 그 문자열에 바로 .parse() 를 부르고 expect 로 받으면 어떻게 됩니까?

A. ① "21\n" — 줄바꿈까지 3 바이트입니다. ② InvalidDigit 으로 실패해 expect 가 패닉을 일으키고, 종료 코드 101 로 끝납니다. line.trim().parse() 로 고칩니다.
