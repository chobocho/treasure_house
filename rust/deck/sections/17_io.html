입출력과 파일

표준 출력과 오류 출력 · 표준 입력 · 파일 읽기 · 파일 쓰기 · 경로와 디렉터리 · 작은 도구

이 부에서 할 일

2부에서 println! 으로 찍고 read_line 으로 한 줄을 읽은 뒤로, 이 책의 프로그램은 거의 화면에 찍기만 했습니다. 이 부는 프로그램이 바깥과 글을 주고받는 길을 다룹니다. 표준 출력 · 표준 오류 · 표준 입력, 그리고 파일입니다. 새 문법은 없습니다. 9부의 Result 와 ?, 10부의 트레이트, 12부의 반복자를 표준 라이브러리의 std::io 와 std::fs 에서 다시 만납니다.

  • 1장 — 표준 출력과 오류 출력: 두 길, flush, writeln!, 종료 코드
  • 2장 — 표준 입력: 끝까지 읽기, 줄마다 읽기, 틀린 줄 알리기
  • 3장 — 파일 읽기: 통째로, 줄마다, 바이트로, 그리고 없는 파일
  • 4장 — 파일 쓰기: 새로 쓰기, 덧붙이기, 모아서 쓰기
  • 5장 — 경로와 디렉터리: 경로 다루기, 목록 보기, 만들고 지우기
  • 6장 — 작은 도구: cat · wc · head 를 줄여서 만들기
이 부의 화면 — 예제는 빈 디렉터리에서 돕니다. 읽을 파일은 예제에 딸려 있고, 화면에서 cat 으로 먼저 보여 줍니다. No such file or directory (os error 2) 같은 글은 Rust 가 아니라 운영 체제가 지은 말입니다. 이 책의 화면은 이 책을 만든 기계에서 나온 그대로이고, 다른 운영 체제에서도 같은 글이 나온다고는 말하지 않습니다.

1장

표준 출력과 오류 출력

두 길과 네 매크로 · 줄이 끝나야 나가는 표준 출력 · flush · writeln! 과 Write · 쓰기가 실패하면 · lock · process::exit 와 ExitCode · 얇은 main

출력 길은 둘, 매크로는 넷 — 파일로 받으면 갈린다

2부에서 print! 와 eprintln! 을 봤고, 한쪽 길을 버려서 두 길이 따로임을 확인했습니다. 이번에는 버리지 않고 파일로 받습니다. 셸의 > 는 표준 출력(standard output, stdout)을, 2> 는 표준 오류(standard error, stderr)를 파일로 돌립니다. 넷째 매크로 eprint! 는 eprintln! 의 줄바꿈 없는 짝입니다.

읽는 법 — ./report > result.txt 를 돌려도 화면에 경고 줄이 남았습니다. result.txt 에 담긴 것은 3번과 4번 줄이 찍은 합계: 42 뿐입니다. 2> log.txt 는 반대로 6번과 7번 줄이 찍은 경고만 파일로 보냈습니다.
결과는 표준 출력, 알림은 표준 오류 — 그래야 결과를 파일로 받는 사람이 알림이 섞이지 않은 결과를 얻고, 알림은 화면에서 봅니다.

표준 출력은 줄이 끝나야 나간다

소스에 적힌 순서는 "내려받는 중" 다음에 알림입니다. 화면에서는 알림이 앞에 있습니다.

읽는 법 — 3번 줄의 print! 가 찍은 내려받는 중 ... 은 줄바꿈이 없어서 나가지 않고 기다렸습니다. 6번 줄 println! 의 줄바꿈이 오고서야 끝 과 함께 나갔습니다. 5번 줄의 eprint! 도 줄바꿈이 없지만 그 사이에 먼저 나갔습니다.
모았다가 내보낸다 — 표준 출력은 찍은 글을 줄 단위로 모아 두었다가(버퍼링, buffering) 줄이 끝나면 내보냅니다. 표준 오류는 모으지 않고 곧바로 내보냅니다.

flush — 모아 둔 글을 지금 내보낸다

앞 슬라이드의 코드에 한 줄을 넣었습니다. io::stdout() 은 표준 출력을 가리키는 손잡이(handle)를 돌려주고, 그 flush() 가 모아 둔 글을 곧바로 내보냅니다.

  • use std::io::{self, Write}; — std::io 자신과 그 안의 Write 를 함께 끌어옵니다(use 의 여러 모양). flush 는 Write 트레이트의 메서드라서 Write 가 보여야 부를 수 있습니다. 빠뜨리면 다음 슬라이드의 오류가 납니다.
  • io::Result<()> — 내보내기는 실패할 수 있어서 flush 는 Result 를 돌려주고, 6번 줄이 ? 로 받습니다. io::Result<()> 는 Result<(), io::Error> 를 줄인 이름입니다. 3장에서 io::Error 와 함께 봅니다.

Write 를 끌어오지 않으면 flush 를 못 찾는다 — E0599

앞 슬라이드의 1번 줄에서 Write 를 뺐습니다. io::stdout() 이 돌려준 값에 flush 가 없다고 합니다.

읽는 법 — 10부에서 트레이트가 보여야 그 메서드를 쓸 수 있다며 본 E0599 와 같은 꼴입니다. 5번 줄의 flush 에 "Stdout 에서 메서드를 찾지 못했다" 가 붙었습니다. 마지막 help: 는 flush 를 주는 트레이트 Write 가 구현돼 있지만 스코프에 없다고 하고, 1번 줄 자리에 넣을 use std::io::Write; 를 보여 줍니다. 가운데 경로는 표준 라이브러리 소스의 자리입니다.
이 부의 첫 줄 — flush 와 다음 슬라이드의 write! · writeln! 을 쓰는 파일은 use std::io::{self, Write}; 로 시작합니다.

writeln! — 어디에 쓸지를 첫 인자로 준다

9부에서 Display 를 구현할 때 쓴 write!(f, …) 는 "화면 대신 f 에 쓴다" 였습니다. 그 첫 인자 자리에 표준 출력이나 표준 오류의 손잡이를 놓으면 그곳에 씁니다. writeln! 은 끝에 줄바꿈을 붙이는 짝입니다.

읽는 법 — 2> /dev/null 로 돌린 화면에서 빠진 경고: 빈 줄 2개 가 8번 줄 writeln!(err, …) 이 쓴 줄입니다. > /dev/null 로 돌리면 그 줄만 남습니다. 9번 줄 write! 와 10번 줄 writeln! 이 쓴 글은 한 줄로 이어졌습니다.
println! 과 다른 점 — write! 와 writeln! 은 io::Result<()> 를 돌려줍니다. 그래서 줄마다 ? 가 붙었습니다. 붙이지 않고 버리면 9부의 버려진 Result 경고가 납니다.

쓸 수 있는 곳은 Write 트레이트가 정한다

앞 슬라이드의 out 과 err 는 타입이 다릅니다(Stdout 과 Stderr). 둘 다 io::Write 트레이트를 구현하기 때문에 같은 writeln! 을 받았습니다. Vec<u8> 도 Write 를 구현합니다. 쓴 바이트가 벡터 끝에 붙습니다.

읽는 법 — 6번과 7번 줄은 화면에 아무것도 찍지 않았습니다. 두 줄이 쓴 글은 buf 에 17 바이트로 들어 있습니다. 합계 두 글자가 3바이트씩이고, 바이트 10 이 writeln! 이 붙인 줄바꿈입니다. 10번 줄은 그 바이트를 String 으로 되돌려 찍었습니다.
뒤에서 — 파일도 Write 입니다(4장). 6장에서는 이 성질을 써서, 화면에 찍는 함수가 무엇을 찍는지 벡터로 받아 시험합니다.

println! 은 쓰기에 실패하면 패닉한다

쓰기도 실패할 수 있습니다. 끝없이 y 를 찍는 프로그램의 표준 출력을 셸의 | 로 head -n 2 에 이어 줍니다. head 는 두 줄만 읽고 끝나고, 그 뒤로는 받아 줄 쪽이 없습니다.

읽는 법 — 9부의 패닉 줄과 같은 모양입니다. 다만 패닉이 난 자리가 내 소스가 아니라 표준 라이브러리의 stdio.rs 이고, 까닭은 failed printing to stdout, 곧 "표준 출력에 찍지 못했다" 입니다. 뒤의 Broken pipe (os error 32) 는 운영 체제가 알려 준 실패의 내용입니다.
종료 코드 줄이 없는 까닭 — | 로 이은 명령에서 셸이 알려 주는 종료 코드는 마지막 명령(head)의 것입니다.

writeln! 은 실패를 Result 로 돌려준다

println! 은 돌려주는 값이 없어서 실패를 알릴 길이 패닉뿐이었습니다. 같은 일을 writeln! 으로 하면 실패가 Err 로 돌아옵니다. 여기서는 표준 오류에 한 줄 남기고 반복을 그만둡니다.

읽는 법 — 패닉 줄 대신 8번 줄이 찍은 그만 찍는다: Broken pipe (os error 32) 가 나왔습니다. {e} 가 찍은 글은 앞 슬라이드의 패닉이 전한 것과 같습니다. 프로그램은 9번 줄의 break 로 반복을 나와 main 의 끝에서 평소처럼 끝났습니다.
고르는 것은 프로그램 — Result 로 받았으니 여기처럼 그만둘 수도, ? 로 올려 보낼 수도 있습니다. 출력이 다른 프로그램으로 이어질 수 있는 도구에는 writeln! 이 맞습니다.

lock — 표준 출력을 잠가 두고 쓴다

표준 출력은 프로그램에 하나뿐이고 모든 스레드가 함께 씁니다. io::stdout().lock() 은 15부의 Mutex 처럼 열쇠를 내주고, 열쇠를 쥔 동안 다른 스레드의 println! 은 기다립니다. 열쇠도 Write 라서 writeln! 의 첫 인자로 씁니다.

읽는 법 — 7번 줄에서 만든 스레드가 언제 돌기 시작하든, 그 println! 은 6번 줄의 열쇠가 살아 있는 동안 찍지 못합니다. 12번 줄의 drop(out) 이 열쇠를 놓은 뒤에야 그 줄이 찍혔습니다. 그래서 main 의 세 줄 사이에 끼어들지 못했고, 화면이 늘 같습니다.
놓고 나서 기다린다 — 12번 줄 없이 13번 줄의 join 으로 가면 main 은 스레드를, 스레드는 열쇠를 기다립니다. 15부에서 본 교착이고, 멈춰 버리는 프로그램이라 돌려 보이지는 않습니다.

process::exit — 부른 자리에서 끝낸다

9부에서 본 종료 코드는 둘이었습니다. main 이 Err 를 돌려주면 1, 패닉이면 101 입니다(1 과 101). 다른 번호로 끝내는 길 하나가 5부에서 ! 의 예로 본 process::exit 입니다. 부른 그 자리에서 프로그램이 끝납니다.

정리가 돌지 않는다 — 12번 줄의 _t 는 14부의 Drop 을 구현했는데도 임시 자료 정리 가 찍히지 않았습니다. process::exit 는 main 의 스코프를 벗어나는 길을 거치지 않고 끝냅니다. 9부에서 패닉이 나도 값은 정리됐던 것과 다릅니다.

ExitCode — main 이 종료 코드를 돌려준다

main 의 반환 타입을 ExitCode 로 적으면 돌려준 값이 종료 코드가 됩니다. main 이 평소처럼 끝까지 가서 돌아가므로 지역 변수도 정리됩니다.

읽는 법 — 앞 슬라이드에서 달라진 코드는 1번 · 11번 · 15번 줄입니다. 이번에는 7번 줄의 임시 자료 정리 가 찍혔고, 종료 코드는 똑같이 2 입니다.
종료 코드는 main 의 반환값으로 — process::exit 는 정리할 값이 남아 있지 않은 자리에서만 씁니다.

얇은 main — 일은 run 이, 알림과 종료 코드는 main 이

9부처럼 main 이 Err 를 돌려주면 오류가 디버그 서식으로 찍히고 1 로 끝났습니다. 찍을 말과 종료 코드를 직접 정하려면 일을 run 함수에 맡기고, main 은 돌아온 Result 를 가르기만 합니다. 아래는 명령 줄 인자로 받은 수를 더하는 도구입니다.

읽는 법 — ./sum 3 x 5 에서는 9번 줄의 map_err 가 만든 말에 23번 줄이 sum: 을 붙여 찍었고, 24번 줄이 종료 코드 2 를 냈습니다. 같은 명령에 2> /dev/null 을 붙이면 화면에 종료 코드만 남습니다. 알림은 표준 오류로 갔고, 표준 출력에는 아무것도 나가지 않았습니다. 성공한 첫 명령에는 종료 코드 줄이 없습니다 — ExitCode::SUCCESS 는 0 입니다.

퀴즈 — 표준 출력과 오류 출력

Q. print!("내려받는 중 ... "); 바로 다음 줄에서 eprint!("(알림) "); 을 불렀습니다. 화면에는 어느 글이 먼저 나올까요? 소스의 순서대로 나오게 하려면 무엇을 넣을까요?

A. (알림) 이 먼저 나옵니다. 표준 출력은 줄이 끝날 때까지 글을 모아 두고, 표준 오류는 곧바로 내보내기 때문입니다(줄이 끝나야 나간다). 두 줄 사이에 io::stdout().flush()?; 를 넣습니다. use std::io::Write; 가 있어야 합니다(flush).

2장

표준 입력

입력의 끝 · read_line 은 덧붙인다 · 묻고 읽기 · lines() · 줄은 Result 에 싸여 온다 · 한 줄에 수 하나 · 틀린 줄의 번호 · 칸 하나 더하기 · 통째로 읽기 · BufRead · 파일을 표준 입력으로

입력이 끝나면 read_line 은 Ok(0) 을 준다

2부에서는 read_line 으로 한 줄만 읽었습니다. 실제 입력은 몇 줄일지 모르므로, 표준 입력(standard input, stdin)이 끝날 때까지 되풀이해 읽다가 끝을 알아차려야 합니다. read_line 이 돌려주는 바이트 수가 그 신호입니다. 2부에서 expect 를 붙이던 자리에는 이제 ? 를 씁니다.

읽는 법 — 8번 줄은 네 번 돌았습니다. "kim\n" 은 줄바꿈까지 4바이트, 빈 줄은 줄바꿈 하나라 1바이트입니다. "lee" 는 입력이 줄바꿈 없이 끝나서 3바이트입니다. 넷째에는 더 읽을 것이 없어 0 이 돌아왔고 문자열도 비었습니다. 11번 줄이 그 0 을 보고 반복을 나옵니다.
0 은 빈 줄이 아니라 입력의 끝 — 빈 줄은 1 입니다. 터미널에서 직접 칠 때 입력의 끝을 알리는 방법은 터미널과 운영 체제가 정합니다(Linux 와 macOS 의 터미널에서는 Ctrl+D).

read_line 은 지우지 않고 덧붙인다

앞 슬라이드의 7번 줄 line.clear() 가 왜 있는지 봅니다. 비우지 않고 같은 String 에 두 번 읽었습니다.

앞 줄이 남아 있다 — 둘째로 찍힌 것은 "kim\nlee\n" 입니다. 2부의 슬라이드 제목이 "한 줄을 읽어 문자열에 붙인다" 였던 그대로, read_line 은 있던 내용 뒤에 붙입니다. 되풀이해 읽을 때는 읽기 전에 clear() 로 비웁니다. 그러면 String 하나를 줄마다 다시 씁니다.

묻는 말을 찍고 답을 읽는다 — flush 먼저

묻는 말 바로 옆에서 답을 받으려면 묻는 말을 줄바꿈 없이 찍습니다. 1장에서 본 대로 그런 글은 줄이 끝날 때까지 나가지 않으므로, 읽기 전에 flush 로 내보냅니다.

읽는 법 — printf 로 넣은 답은 화면에 보이지 않아서, 읽은 값을 15번 줄이 표준 오류로 따로 찍었습니다. 이름: 이 그 줄보다 앞에 있습니다. 답을 읽기 전에 묻는 말이 나갔다는 뜻입니다. 7번 줄이 없으면 묻는 말은 16번 줄의 줄바꿈이 올 때까지 나가지 않습니다.
10번 줄 — 2부의 trim 으로 줄바꿈을 떼고, 떼어 낸 글로 새 String 을 만들어 돌려줍니다.

lines() — 줄을 하나씩 내는 반복자

read_line 으로 되풀이할 때 손으로 하던 일이 셋입니다. 비우기, 끝 알아차리기, 줄바꿈 떼기입니다. io::stdin().lines() 가 그 셋을 맡습니다. 8부에서 문자열을 줄로 쪼갠 lines() 와 이름이 같고, for 로 도는 모양도 같습니다.

읽는 법 — 찍힌 세 줄 어디에도 \n 이 없습니다. 빈 줄은 "" 로 나왔고, 줄바꿈 없이 끝난 lee 도 한 줄로 나왔습니다. 입력이 끝나자 반복자가 끝났고, 10번 줄이 입력 끝 을 찍었습니다.
7번 줄 — 8부의 lines() 는 &str 을 냈지만 여기서 나오는 것은 io::Result<String> 입니다. 읽기는 줄마다 실패할 수 있기 때문입니다. ? 로 속의 String 을 꺼내 같은 이름으로 가립니다.

줄은 Result 에 싸여 온다 — E0599

앞 슬라이드의 7번 줄을 빼먹고, 반복자가 낸 것을 곧바로 문자열처럼 썼습니다.

읽는 법 — 번호는 1장의 flush 오류와 같은 E0599 입니다. 그때는 트레이트가 보이지 않아서였고, 이번에는 값이 Result 에 싸여 있어서입니다. 5번 줄의 trim 에 "Result<String, std::io::Error> 에 그 메서드가 없다" 가 붙었습니다. note: 는 trim 이 String 에는 있다고 알려 주고, help: 는 ? 로 String 을 꺼내라며 고친 5번 줄 line?.trim() 을 보여 줍니다.

한 줄에 수 하나 — ? 두 개로 읽는다

줄을 읽는 일도, 읽은 글을 수로 바꾸는 일도 실패할 수 있습니다. 두 오류는 타입이 다릅니다 (io::Error 와 ParseIntError). 9부에서 "작은 도구의 기본 틀" 이라고 한 Result<(), Box<dyn Error>> 가 둘을 다 받습니다.

읽는 법 — 첫 실행은 세 줄을 더해 60 입니다. 셋째 줄 " 30 " 의 공백은 trim 이 뗐습니다. 둘째 실행에서는 이십 을 만난 8번 줄의 둘째 ? 가 오류를 올려 보냈고, main 이 Err 로 끝나 종료 코드 1 이 됐습니다.
어느 줄인지 알 수 없다 — 오류 글에 줄 번호도, 문제가 된 글도 없습니다. 입력이 길면 틀린 줄을 찾을 길이 없습니다. 다음 슬라이드에서 고칩니다.

틀린 줄은 번호와 함께 알린다

9부에서 설정 줄에 한 것처럼 오류에 줄 번호와 문제의 글을 싣습니다. 번호는 enumerate 가 붙이고, 알림과 종료 코드는 1장의 얇은 main 이 맡습니다.

읽는 법 — 12번 줄의 map_err 가 번호와 글을 붙여 2번째 줄 "이십": … 을 만들었고, 25번 줄이 그 앞에 sum: 을 붙여 표준 오류로 찍었습니다. enumerate 는 0 부터 세므로 i + 1 이 사람이 세는 줄 번호입니다. 8번 줄은 읽기 오류를 to_string() 으로 글로 바꿔 run 의 오류 타입 String 에 맞춥니다.

칸 하나만 골라 더한다

줄마다 이름과 점수가 공백으로 나뉘어 있습니다. 8부의 split_whitespace 로 쪼개 둘째 칸만 수로 바꿉니다.

읽는 법 — 10번 줄의 nth(1) 은 둘째 조각을 Option 으로 줍니다. 빈 줄에는 조각이 없어 None 이고, let … else 가 그 줄을 continue 로 건너뜁니다. 그래서 네 줄 가운데 셋만 세어 3명, 합계 252 가 나왔습니다.

통째로 읽기 — io::read_to_string

줄마다 따로 다룰 일이 없으면 입력 전체를 String 하나로 받습니다. io::read_to_string 은 입력이 끝날 때까지 읽어 한 번에 돌려줍니다.

읽는 법 — 받은 것이 String 이므로 8부의 메서드를 그대로 씁니다. 두 줄, 세 낱말이고, 줄바꿈 둘까지 세어 9 글자입니다. 한글 세 글자가 3바이트씩이라 바이트로는 15 입니다.
줄마다 읽을까, 통째로 읽을까 — lines() 는 한 번에 한 줄을 쥐고, 이 함수는 입력 전체를 String 하나에 담습니다. 3장에서 파일을 읽을 때도 같은 둘 가운데 고릅니다.

BufRead — 줄 단위로 읽을 수 있는 것

1장의 Write 가 "쓸 수 있는 곳" 을 묶는 트레이트였듯이, lines() 와 read_line 을 주는 트레이트가 io::BufRead 입니다. 함수가 impl BufRead 를 받으면 표준 입력에 묶이지 않습니다. 표준 입력에서는 lock() 이 내주는 열쇠가 BufRead 를 구현합니다.

읽는 법 — 5번부터 11번 줄까지의 total 안에는 stdin 이라는 말이 없습니다. 7번 줄의 input.lines() 는 BufRead 의 메서드라서 2번 줄이 BufRead 를 끌어왔습니다. 1장의 Write 와 같은 사정입니다.
이미 써 온 것 — 지금까지의 io::stdin().lines() 와 io::stdin().read_line(…) 은 use std::io; 만으로 됐습니다. Stdin 이 같은 이름의 메서드를 따로 갖고 있어서입니다.

파일을 표준 입력으로 — 셸의 <

표준 입력에 이어지는 것은 키보드만이 아닙니다. 셸의 < 는 파일을 표준 입력에 이어 줍니다. 앞 슬라이드의 프로그램을 고치지 않고 파일에 든 수를 더합니다.

읽는 법 — ./total < numbers.txt 와 cat numbers.txt | ./total 이 같은 합계 60 을 냈습니다. 프로그램에는 파일 이름이 어디에도 없습니다. 표준 입력을 읽었을 뿐이고, 거기에 무엇을 이을지는 셸이 정했습니다.
다음 장 — 표준 입력만 읽는 도구도 이렇게 파일을 다룹니다. 3장에서는 프로그램이 이름으로 파일을 직접 엽니다. 그때 total 을 고치지 않고 다시 씁니다.

퀴즈 — 표준 입력

Q. read_line 이 Ok(0) 을 돌려줬습니다. 빈 줄을 읽은 것일까요? lines() 로 읽으면 빈 줄과 입력의 끝은 각각 어떻게 보일까요?

A. 빈 줄이 아니라 입력의 끝입니다. 빈 줄은 줄바꿈 하나라서 Ok(1) 입니다 (입력의 끝). lines() 에서는 빈 줄이 "" 로 나오고, 입력이 끝나면 반복자가 끝나 for 를 빠져나옵니다(lines()).

fs::read_to_string — 파일을 통째로 String 에

2장 끝에서는 셸이 파일을 표준 입력에 이어 줬습니다. 이제 프로그램이 이름으로 파일을 직접 읽습니다. std::fs 는 파일 시스템(file system)을 다루는 모듈입니다. fs::read_to_string 은 2장의 io::read_to_string 처럼 내용 전체를 String 하나로 돌려줍니다.

읽는 법 — cat 이 보여 준 세 줄이 그대로 text 에 들어왔습니다. 7번 줄이 3 줄, 30 바이트 를 찍었고, 8번 줄부터는 8부의 lines() 로 줄마다 번호를 붙였습니다.
어디의 memo.txt 인가 — 경로 없이 이름만 적으면 프로그램을 돌린 디렉터리에서 찾습니다. 경로는 5장에서 봅니다.

없는 파일을 읽으면 — io::Error

파일은 없을 수 있습니다. 그래서 fs::read_to_string 은 Result 를 돌려주고, 실패의 까닭은 std::io::Error 값에 담깁니다. 1장과 2장의 io::Result 에서 오류 자리에 있던 그 타입입니다. 없는 파일을 읽어 그 값을 네 가지로 찍어 봅니다.

  • {e} — No such file or directory (os error 2). 운영 체제가 준 설명과 오류 번호입니다.
  • {e:?} — Os 는 운영 체제에서 온 오류라는 표시이고, 그 안에 번호(code), 종류(kind), 설명(message)이 들어 있습니다.
  • e.kind() — 종류만 꺼냅니다. ErrorKind 열거형의 변형 NotFound 이고, 12번 줄처럼 == 로 견줄 수 있습니다.
글로 견주지 않는다 — 설명과 번호는 운영 체제가 정한 것이고, 이 화면은 이 책을 만든 기계에서 나온 것입니다. 프로그램이 오류를 가를 때는 글이 아니라 kind() 를 봅니다.

kind 로 오류를 가른다 — 없으면 기본값

설정 파일은 없어도 되는 파일입니다. 없으면 기본값을 쓰고, 그 밖의 실패만 오류로 올려 보냅니다. match 의 가드에서 kind() 를 봅니다.

읽는 법 — none.conf 는 없으므로 8번 줄의 갈래가 기본값 Ok("port=8080") 을 돌려줬습니다. "." 은 디렉터리라서 읽기가 실패했는데, 종류가 IsADirectory 라 8번 줄의 가드에 맞지 않고 11번 줄이 오류를 그대로 돌려줬습니다. 번호 21 과 설명 Is a directory 도 운영 체제의 것입니다.
종류는 열거형에 — 9부에서 오류의 종류를 열거형으로 나눈 것과 같은 생각입니다. io::Error 는 그 종류를 ErrorKind 로 알려 줍니다.

io::Result<T> — 오류 자리를 채워 둔 별명

이 부의 함수는 줄곧 io::Result<…> 를 돌려줬습니다. 16부에서 본 type 별명입니다. 거기서 "오류 타입을 고정한 Result<T> 별명" 의 예로 든 것이 fmt::Result 였고, io::Result<T> 는 Result<T, io::Error> 의 별명입니다.

읽는 법 — 16번 줄은 short 가 돌려준 io::Result<usize> 를 Result<usize, io::Error> 라고 적은 변수에 담았고, 17번 줄은 거꾸로 했습니다. 둘 다 컴파일됐고 찍힌 값도 같습니다. 새 타입이 아니라 같은 타입의 다른 이름입니다.
이미 써 온 것 — 13부에서 별명을 붙여 끌어온 std::io::Result 가 이 타입입니다. 이 부에서는 따로 끌어오지 않고 늘 io::Result 라고 적습니다.

io::Error 에는 파일 이름이 없다

파일 둘을 차례로 읽습니다. a.txt 는 있고 b.txt 는 없습니다. main 이 io::Result<()> 를 돌려주고 ? 로 올려 보내기만 하면 무엇이 찍히는지 봅니다.

무엇이 없다는 것인가 — Error: Os { … } 줄에는 번호와 종류와 설명뿐입니다. 어느 파일을 읽다가 난 오류인지는 적혀 있지 않습니다. io::Error 는 파일 이름을 담지 않습니다.

이름은 아는 쪽이 붙인다

파일 이름을 아는 것은 읽으라고 시킨 코드입니다. 2장에서 줄 번호를 붙인 것처럼 map_err 로 이름을 붙여 올려 보냅니다.

읽는 법 — 6번 줄이 b.txt: No such file or directory (os error 2) 를 만들었고, 14번 줄이 표준 오류로 찍었습니다. 15번 줄의 ExitCode::FAILURE 가 종료 코드 1 입니다.
잃은 것 — 오류를 글로 바꿨으므로 부른 쪽은 더는 kind() 를 물을 수 없습니다. 이름과 io::Error 를 함께 담는 오류 타입은 9부의 From 과 ? 로 만들 수 있고, 6장에서 만듭니다.

File::open — 여는 일과 읽는 일을 나눈다

fs::read_to_string 은 두 가지 일을 한 번에 합니다. 파일을 열고, 끝까지 읽습니다. 나눠서 쓰면 File::open 이 열린 파일(File)을 주고, Read 트레이트의 read_to_string 이 읽습니다. Write 가 쓰는 쪽의 트레이트였듯이 Read 는 읽는 쪽의 트레이트입니다.

읽는 법 — 9번 줄은 파일의 내용을 text 에 담고, read_line 처럼 읽은 바이트 수 30 을 돌려줬습니다. 12번 줄에서 같은 file 을 다시 읽으니 0 입니다. 열린 파일은 어디까지 읽었는지를 기억하고, 그 자리가 이미 끝이기 때문입니다. 2장에서 입력의 끝을 알린 0 과 같은 신호입니다. text 도 30 바이트 그대로입니다.
let mut file — 읽으면 읽는 자리가 움직이므로 read_to_string 은 file 을 가변으로 빌립니다.

BufReader — 파일을 줄마다 읽는다

2장에서 줄을 내주는 것은 BufRead 였습니다. File 을 BufReader::new 로 감싸면 BufRead 가 되고, io::stdin().lines() 와 같은 모양으로 lines() 를 씁니다.

읽는 법 — 8번 줄의 lines() 가 낸 것은 여기서도 io::Result<String> 이라 9번 줄이 ? 로 꺼냅니다. 줄바꿈은 떼어져 왔고, 번호는 enumerate 가 붙였습니다.
이름의 Buf — 버퍼(buffer), 곧 읽은 바이트를 모아 두는 자리입니다. BufReader 는 파일에서 읽은 바이트를 거기에 모아 두고, 줄바꿈을 찾아 한 줄씩 떼어 줍니다.

File 에 바로 lines 를 부르면 — E0599

앞 슬라이드에서 BufReader 로 감싸는 7번 줄을 빼고, File 에 곧바로 lines() 를 불렀습니다.

읽는 법 — 이 부에서 세 번째로 보는 E0599 이고, 오류 첫 줄의 말이 다릅니다. "lines 메서드가 File 에 있기는 한데, 트레이트 바운드가 채워지지 않았다". note: 가 채워지지 않은 조건을 적어 줍니다 — File: BufRead. 2번 줄에서 BufRead 를 끌어왔으니 트레이트는 보입니다. File 이 그것을 구현하지 않을 뿐입니다. 그 아래 줄은 &mut File 로 불러도 같은 조건이 걸린다는 말입니다.
고치려면 — 앞 슬라이드처럼 BufReader::new(file) 로 감싼 것에 lines() 를 부릅니다.

같은 함수가 파일도 읽는다

2장의 total 은 impl BufRead 를 받았습니다. File 을 감싼 BufReader 도 BufRead 이므로, 함수를 고치지 않고 파일을 넘깁니다.

읽는 법 — 6번부터 12번 줄까지의 total 은 2장의 것과 글자 하나 다르지 않습니다. 달라진 곳은 main 의 16번과 17번 줄입니다. 2장에서 셸이 이어 준 numbers.txt 를 이번에는 프로그램이 열었고, 합계는 같은 60 입니다.
어디서 읽을지는 부르는 쪽이 정한다 — 읽는 함수가 BufRead 를 받으면 표준 입력에도 파일에도 쓰입니다. 6장의 도구들이 이 모양으로 짜입니다.

fs::read — 바이트 그대로 읽는다

파일에 든 것은 바이트입니다. fs::read 는 그것을 글로 풀지 않고 Vec<u8> 로 돌려줍니다. 글이 아닌 파일은 이것으로 읽습니다.

읽는 법 — wc -c 가 센 11 과 7번 줄의 11 바이트 가 같습니다. 같은 파일을 글로 읽어 세면 7 글자입니다. 한글 두 글자가 3바이트씩이고(237, 149, 156 이 한), 마지막 바이트 10 은 줄바꿈입니다.

UTF-8 이 아닌 파일은 String 이 되지 못한다

8부에서 본 대로 Rust 의 문자열은 UTF-8 입니다. 그래서 fs::read_to_string 은 읽은 바이트가 올바른 UTF-8 이 아니면 실패합니다. 화면 첫 줄의 printf 가 셋째 줄 머리에 UTF-8 이 될 수 없는 바이트 둘(\377\376)을 넣은 파일을 만듭니다.

읽는 법 — 8번 줄이 찍은 글은 stream did not contain valid UTF-8 이고 종류는 InvalidData 입니다. 없는 파일 때와 달리 (os error …) 가 붙지 않았습니다. 운영 체제가 낸 오류가 아니기 때문입니다. 같은 파일이 13번 줄의 fs::read 로는 15 바이트로 읽혔습니다. 15번 줄의 valid_up_to: 10 은 앞의 10 바이트, 곧 두 줄까지는 올바른 UTF-8 이라는 말입니다.

줄마다 읽으면 깨진 줄에서만 실패한다

앞 슬라이드의 파일을 BufReader 의 lines() 로 읽습니다. 이번에는 ? 를 붙이지 않고, 줄마다 나온 Result 를 그대로 찍습니다.

읽는 법 — 통째로 읽을 때는 한 글자도 얻지 못했지만, 여기서는 깨진 줄 앞의 두 줄을 얻었습니다. lines() 가 낸 줄마다 따로 검사가 이루어진 것입니다. 12부에서 본 대로 반복자는 당길 때마다 한 걸음씩 갑니다. Err 의 속은 앞 슬라이드와 같은 종류 InvalidData 이고, Os 가 아니라 Error 로 찍혔습니다.

파일을 읽는 세 가지 길

이 장에서 쓴 읽는 법 셋을 "무엇을 돌려받는가" 로 견준 표입니다. 위의 둘은 2장에서 표준 입력에 쓴 io::read_to_string · lines() 와 짝입니다.

읽는 법돌려받는 것어울리는 때
fs::read_to_string(p)String 하나글 파일을 통째로 다룰 때
File::open(p) + BufReader + lines()줄마다 io::Result<String>줄 단위로 다룰 때, 한 번에 한 줄만 쥐고 싶을 때
fs::read(p)Vec<u8>글이 아닌 파일, UTF-8 인지 모르는 파일
  • 셋 다 실패를 io::Error 로 알립니다. 파일이 없으면 NotFound, 글로 읽으려는데 UTF-8 이 아니면 InvalidData 입니다.
  • 오류에 파일 이름은 들어 있지 않습니다. 이름은 아는 쪽이 붙입니다.
다음 장 — 읽는 쪽을 봤으니 4장에서는 반대 방향, 파일에 쓰는 법을 봅니다.

퀴즈 — 파일 읽기

Q. fs::read_to_string("data.txt") 가 Err(e) 를 돌려줬습니다. "파일이 없다" 와 "파일은 있는데 글이 아니다" 를 프로그램에서 어떻게 가를까요? 뒤의 경우에 내용을 읽을 길은 무엇일까요?

A. e.kind() 를 봅니다. 없는 파일은 ErrorKind::NotFound (없는 파일), UTF-8 이 아닌 내용은 ErrorKind::InvalidData 입니다 (UTF-8 이 아닌 파일). 뒤의 경우에도 fs::read 는 바이트를 그대로 돌려줍니다. 오류의 설명 글은 운영 체제나 라이브러리가 지은 것이라 견주는 데 쓰지 않습니다.
