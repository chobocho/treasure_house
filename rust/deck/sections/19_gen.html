impl 블록에 단 조건은 new 에도 걸린다 — E0277

값에 이름표를 붙이는 Labeled<T> 를 만듭니다. line 이 값을 {} 로 찍으려면 T: Display 가 있어야 해서, 10부에서 본 impl<T> 에 조건을 달았습니다. 정수를 담을 때는 됩니다. 벡터를 담으려 하니 값을 만드는 데서 막힙니다.

읽는 법 — 10부에서 읽은 E0277 대로 타입은 Vec<&str>, 트레이트는 Display 입니다. 새로 읽을 것은 note: 입니다. 그 조건이 Labeled::<T>::new 에 걸려 있다고 하고, 조건이 적힌 곳으로 9번 줄의 T: Display 를 짚습니다. 11번 줄의 new 본문은 값을 찍지 않습니다. 그래도 같은 블록 안에 있어서 같은 조건이 걸렸습니다.

impl 블록을 둘로 나눈다 — 어떤 T 에든 있는 것, 조건이 맞을 때만 있는 것

10부에서 impl Point<f64> 로 f64 일 때만 있는 메서드를 만들었습니다. 타입 하나를 짚는 대신 조건을 적으면 "Display 인 T 일 때만 있는 메서드" 가 됩니다. 조건이 필요 없는 new 와 value 는 조건 없는 블록으로 옮깁니다.

읽는 법 — 28번 줄에서 벡터를 담은 tags 가 만들어졌고, 29번 줄이 조건 없는 value() 로 길이 2 를 찍었습니다. 27번 줄의 port.line() 은 정수가 Display 라서 19번 줄의 블록에 든 메서드를 불렀습니다.

조건에 안 맞는 T 에서 그 메서드를 부르면 — E0599

앞 슬라이드의 tags 에서 line 을 부릅니다. 속의 타입 Vec<&str> 은 Display 가 아닙니다.

읽는 법 — 번호는 10부의 E0599 이고, 오류 첫 줄의 말은 17부에서 File 에 lines 를 부르다 처음 본 것입니다 — "메서드가 있기는 한데 트레이트 바운드가 채워지지 않았다". 그때는 채워지지 않은 조건이 글로만 적혀 있었습니다. 이번에는 조건이 내 코드에 있어서, note: 가 14번 줄의 T: Display 아래에 "채워지지 않은 조건이 여기서 들어왔다" 고 적습니다. 그 조건은 Vec<&str>: std::fmt::Display 입니다.
고치려면 — Display 인 값을 담거나, 앞 슬라이드의 29번 줄처럼 조건 없는 블록의 메서드만 씁니다.

조건은 메서드 하나에도 달 수 있다 — E0277

조건이 다른 메서드마다 impl 블록을 새로 여는 대신, 메서드의 시그니처 뒤에 10부의 where 절을 붙입니다. line 은 Display 를, is_default 는 Default 와 PartialEq 를 요구합니다. 블록은 하나입니다.

읽는 법 — 33번 줄에서 Vec<&str> 을 담은 tags 가 is_default() 를 불러 true 를 냈습니다. 빈 벡터가 Vec 의 기본값과 같습니다. 둘째 화면은 그 33번 줄의 tags.is_default() 를 tags.line() 으로만 바꾼 쌍둥이 where_method_err.rs 의 것입니다. 번호가 앞 슬라이드의 E0599 가 아니라 E0277 입니다. 조건을 메서드에 달았더니 "메서드를 찾지 못했다" 가 아니라 "line 에 걸린 조건이 안 맞는다" 로 바뀌었고, note: 가 16번 줄의 T: Display 를 짚습니다.
이미 본 꼴 — 3부에서 실수 배열에 sort() 를 부르다 본 오류의 마지막 note: 가 같은 꼴입니다. 거기서는 sort 에 걸린 조건 Ord 를 실수가 채우지 못했습니다.

트레이트 구현에도 조건을 단다 — E0277

메서드가 아니라 트레이트 구현을 조건에 걸 수도 있습니다. Summary 를 받는 report 가 있고, Labeled<T> 는 속의 값이 {} 로 찍힐 때만 요약을 만들 수 있습니다. impl<T: Display> Summary for Labeled<T> 는 "T 가 Display 이면 Labeled<T> 는 Summary 다" 입니다. 조건부 구현(conditional implementation)이라고 합니다.

읽는 법 — 33번 줄의 tags 는 만들어졌고 34번 줄이 이름표와 길이를 찍었습니다. 둘째 화면은 그 34번 줄을 report(&tags); 로만 바꾼 쌍둥이 cond_impl_err.rs 의 것입니다. 오류 첫 줄은 E0277 그대로 Vec<&str> 과 Display 입니다. 새로 읽을 것은 help: 입니다 — "트레이트 Summary 는 Labeled<T> 에 조건부로 구현돼 있다". 19번 줄의 T: Display 아래에 채워지지 않은 조건을 적었습니다. 화면 마지막 줄의 note: 는 Labeled<Vec<&str>> 이 Summary 가 되려면 그 조건이 필요하다는 말입니다.
포괄 구현과 견주면 — 10부의 포괄 구현은 for T 로 조건에 맞는 모든 타입에 걸었습니다. 여기서는 for Labeled<T> 라서 구현을 받는 것은 내 타입 하나의 여러 꼴뿐입니다.

derive 가 만드는 구현에도 조건이 달린다 — E0277

10부에서 derive 는 모든 필드가 그 트레이트를 구현해야 붙는다고 했습니다. 제네릭 구조체에서는 필드의 타입이 T 라서, 붙이는 자리에서는 그것을 알 수 없습니다. Labeled<T> 에 derive(Debug) 를 붙이고, Debug 가 아닌 Raw 를 담아 찍어 봅니다.

읽는 법 — 오류는 둘이고 둘 다 10부에서 본 Raw 와 Debug 의 E0277 입니다. 1번 줄의 derive 도, 정수를 담아 찍은 15번 줄도 걸리지 않았습니다. 첫째 오류의 help: 는 앞 슬라이드와 같은 말입니다 — "Debug 는 Labeled<T> 에 조건부로 구현돼 있다". 2번 줄의 T 아래에 채워지지 않은 조건 Raw: Debug 를 적었습니다. 둘째 오류는 21번 줄의 vec![Raw] 에서 났고, 같은 말을 Vec 에 합니다. --> 뒤의 긴 경로는 그 구현이 적힌 표준 라이브러리 소스의 자리입니다. 화면은 Vec 을 타입 인자 둘로 적었는데, 둘째 A 는 이 책에서 다루지 않습니다.
고치려면 — 화면에서 뺀 마지막 help: 가 Raw 에 #[derive(Debug)] 를 붙이라고 권합니다. 7번 줄에 그 한 줄만 더한 쌍둥이 cond_derive.rs 의 출력이 아래입니다.

T 자리에 str 이 오면 — E0277

무엇이든 {} 로 찍어 대괄호에 넣는 show 입니다. 참조로 받으니 정수의 참조도 &str 도 받을 것 같습니다. &str 인 s 를 넘기면 매개변수의 &T 와 맞춰져 T 는 str 이 됩니다.

읽는 법 — 10부에서 dyn Shape 를 지역 변수에 담으려다 본 E0277 과 같은 말이고, 트레이트도 같은 Sized 입니다. 이번 타입은 str 입니다. 6부부터 문자열 조각을 늘 &str 로, 곧 참조 뒤에 두고 썼습니다. 새로 읽을 것은 note: 입니다 — "show 의 암묵적인(implicit) Sized 조건". 3번 줄의 T 를 짚습니다. 적은 조건은 Display 하나인데, 이 T 에는 적지 않은 Sized 가 하나 더 붙어 있었습니다.
help: 가 고친 줄 — T: Display + ?Sized. "암묵적인 Sized 제한을 푼다" 고 적혀 있습니다. 다음 슬라이드입니다.

?Sized — 붙어 있던 Sized 조건을 뗀다

help: 대로 고칩니다. 다른 조건은 "이것을 할 수 있어야 한다" 를 더하는데, ?Sized 는 거꾸로 붙어 있던 조건을 뗍니다. "크기를 몰라도 된다" 로 읽습니다.

읽는 법 — 6번 줄이 18부의 type_name 으로 T 의 이름을 함께 찍습니다. 13번 줄에서 T 는 str, 15번 줄에서는 dyn core::fmt::Display 입니다. str 은 앞 슬라이드에서 크기를 알 수 없다고 한 타입이고, dyn 은 10부에서 본 대로 포인터 뒤에만 둘 수 있는 타입입니다. 5번 줄의 x 는 참조 &T 입니다. 11번 줄처럼 크기가 정해진 i32 도 그대로 받았습니다.

구조체의 T 에도 같은 조건이 붙어 있다 — E0277

무엇이든 Box 에 담아 이름표를 붙이는 Shelf<T> 입니다. 문자열 조각 str, 슬라이스 [u8], 트레이트 객체 dyn Display 를 담으려 합니다. 구조체의 타입 인자에도 ?Sized 를 적어야 합니다.

읽는 법 — 9번 · 13번 · 17번 줄에서 T 는 차례로 str, [u8], dyn Display 이고, 21번부터 23번 줄까지가 Box 속의 길이 5 와 3, 값 7 을 찍었습니다. 둘째 화면은 ?Sized 만 뺀 쌍둥이 unsized_struct_err.rs 의 첫째 오류입니다. 앞에서 읽은 E0277 과 같은 말이고, 이번에는 Shelf 의 암묵적인 Sized 조건입니다. 그 파일의 오류는 여섯이고 모두 이 꼴입니다.

포괄 구현과 따로 쓴 구현이 겹치면 — E0119

10부의 포괄 구현으로 Display 인 모든 타입에 describe 를 붙였습니다. String 만은 따옴표를 둘러 주고 싶어서 구현을 하나 더 씁니다.

읽는 법 — 오류 첫 줄은 "타입 String 에 트레이트 Describe 의 구현이 충돌한다" 입니다. 8번 줄에는 "첫 구현이 여기", 15번 줄에는 "String 에 충돌하는 구현" 이라고 붙었습니다. String 은 Display 이므로 8번 줄의 포괄 구현이 이미 String 을 덮고 있고, 15번 줄이 같은 자리에 하나를 더 놓았습니다. 이렇게 두 구현이 같은 타입을 덮는 것을 구현이 겹친다(overlap)고 합니다.
더 좁게 쓴 쪽이 이기지 않는다 — 컴파일러는 15번 줄을 8번 줄보다 앞세우지 않고 오류로 처리했습니다. 10부의 고아 규칙이 두 크레이트가 같은 구현을 따로 쓰는 일을 막았다면, 이 오류는 한 크레이트 안에서 같은 일을 막습니다.

지금 겹치지 않아도 거절한다 — E0119

이 장의 첫 슬라이드에서 Vec<&str> 은 Display 가 아니었습니다. 그러면 Vec<T> 에 따로 구현해도 포괄 구현과 겹칠 일이 없어 보입니다.

읽는 법 — 앞 슬라이드와 같은 E0119 이고 타입 자리가 Vec<_> 입니다. 새로 읽을 것은 마지막 note: 입니다 — "upstream 크레이트가 앞으로의 버전에서 Vec<_> 에 Display 구현을 더할 수 있다". upstream 은 내 크레이트가 가져다 쓰는 쪽의 크레이트를 가리키는 말입니다. note: 가 적은 트레이트와 타입이 둘 다 std:: 로 시작하니 여기서는 표준 라이브러리입니다. 그런 구현이 생기면 7번 줄과 14번 줄이 앞 슬라이드처럼 겹칩니다.
"지금은 구현하지 않는다" 는 근거가 못 된다 — 컴파일러는 Vec 이 오늘 Display 가 아니라는 것을 두 구현이 겹치지 않는 근거로 받아 주지 않았습니다.

포괄 구현의 조건을 내 표시 트레이트로 바꾼다

포괄 구현의 조건을 남의 Display 에서 내가 만든 Plain 으로 바꿉니다. Plain 은 메서드가 하나도 없는 트레이트이고, 포괄 구현을 받을 타입에만 붙입니다. 이렇게 "이 타입은 해당한다" 는 표시로만 쓰는 트레이트를 표시 트레이트(marker trait)라고 합니다.

읽는 법 — 8번 줄의 trait Plain: Display {} 는 10부의 상위 트레이트로 Display 를 둬서, 14번 줄이 {self} 로 찍을 수 있습니다. 9번과 10번 줄이 i32 와 f64 에 표시를 붙였습니다. String 과 Vec 에는 붙이지 않았습니다. 18번 줄의 String 구현과 24번 줄의 Vec<T> 구현이 이번에는 컴파일됐고, 출력의 글 "hi" 와 3칸짜리 벡터 가 그 둘이 낸 것입니다.
앞의 note 와 견주면 — 앞 슬라이드의 note: 가 걱정한 것은 upstream 크레이트가 Display 구현을 더하는 일이었습니다. Plain 은 이 파일에서 만든 트레이트이고, 붙인 곳은 9번과 10번 줄 둘뿐입니다.

반복자라는 것만으로는 내주는 값을 찍을 수 없다 — E0277

E0277 이 대는 타입은 Token, 트레이트는 Debug 입니다. 오류가 난 곳은 쓰는 쪽이 아니라 더한 구현의 30번 줄 type Output = Token; 이고, note: 가 5번 줄의 : Debug 를 짚습니다.

퀴즈 — 연관 타입과 GATs

Q. Shape 에 fn area_times<N: Into<f64>>(&self, k: N) -> f64 를 더했더니 Vec<Box<dyn Shape>> 가 컴파일되지 않습니다. 메서드를 다른 트레이트로 옮기지 않고 고치려면 무엇을 적을까요? 고친 뒤 dyn Shape 에서 area_times 를 부르면 어떻게 될까요?

A. 그 메서드에 where Self: Sized 를 답니다. 그러면 Shape 를 다시 dyn 으로 쓸 수 있습니다(where Self: Sized). dyn Shape 에서 그 메서드를 부르면 "트레이트 객체에서 부를 수 없다" 는 컴파일 오류가 나고, Square 같은 크기를 아는 타입에서는 그대로 불립니다.
