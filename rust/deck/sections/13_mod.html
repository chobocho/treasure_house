모듈·크레이트·시험·문서

mod 와 pub · 파일로 나누기 · Cargo.toml · #[test] · 문서 주석과 문서 시험

이 부에서 할 일

지금까지의 예제는 파일 하나였습니다. 프로그램이 커지면 코드를 나누고, 무엇을 밖에 보일지 정하고, 고칠 때마다 다시 확인할 시험이 필요합니다. 이 부는 그 도구들을 봅니다.

  • 1장 — 모듈: mod, pub, 경로, use
  • 2장 — 파일로 나누기, 라이브러리 크레이트와 실행 크레이트
  • 3장 — cargo 더: Cargo.toml, 기능(feature), 크레이트 저장소
  • 4장 — 시험: #[test], assert!, cargo test
  • 5장 — 문서: ///, 문서 속 예제가 시험으로 돈다, 속성 정리
낱말 둘 — 크레이트(crate)는 컴파일의 한 단위(라이브러리 하나 또는 실행 파일 하나)이고, 모듈(module)은 크레이트 안을 나누는 이름 공간입니다.

1장

모듈

mod · 기본은 비공개 · 경로 · use · 다시 내놓기 · 필드의 공개

mod — 이름 공간을 만든다

mod 이름 { … } 으로 관련된 것들을 묶습니다. 밖에서 쓸 것에는 pub 을 붙이고, 모듈::이름 으로 부릅니다.

기본은 비공개다 — E0603

pub 을 붙이지 않은 것은 그 모듈 밖에서 보이지 않습니다. Rust 는 "숨기는 쪽" 이 기본입니다.

숨긴 것은 마음대로 고칠 수 있다 — 밖에서 못 쓰는 것은 바꿔도 다른 코드가 깨지지 않습니다. 공개한 것만이 약속입니다.

경로 — crate · super · self

이름을 찾아가는 길이 경로(path)입니다. 파일 시스템의 절대 경로·상대 경로와 같은 생각입니다.

시작뜻파일 시스템에 견주면
crate::이 크레이트의 뿌리에서/
super::한 단계 위 모듈에서../
self::지금 모듈에서(생략 가능)./

use — 이름을 이 자리로 끌어온다

긴 경로를 매번 쓰지 않도록 use 로 끌어옵니다. 함수는 보통 모듈까지만 끌어와 circle::area 처럼 어디 것인지 보이게 쓰고, 타입은 이름째 끌어옵니다.

use 의 여러 모양

여럿을 한 줄에({ }), 이름이 겹치면 별명으로(as), 전부 다(*).

* 는 아껴 쓴다 — 어떤 이름이 어디서 왔는지 보이지 않게 됩니다. 시험 모듈의 use super::*; 처럼 범위가 좁을 때 씁니다.

pub use — 다시 내놓기

안쪽 모듈 구조를 숨기고 쓰기 좋은 이름만 바깥 층에 내놓습니다. 안은 마음대로 나누고, 밖에는 평평한 모양을 보여 줍니다.

구조체의 필드도 따로 공개한다 — E0616

구조체에 pub 을 붙여도 필드는 여전히 비공개입니다. 필드마다 따로 정합니다.

비공개 필드가 있으면 밖에서 만들 수 없다 — E0451

필드 하나라도 비공개면 모듈 밖에서는 Account { … } 로 값을 만들 수 없습니다. 채울 수 없는 칸이 있기 때문입니다.

그래서 생성 함수를 내준다

비공개 필드를 둔 타입은 new 같은 공개 함수로만 만들게 합니다. 값이 늘 올바른 상태로 시작하고, 바꾸는 길도 메서드로 정해집니다.

캡슐화 — 잔액이 음수가 되는 일이 없게 하고 싶다면, deposit 한 곳만 지키면 됩니다. 밖에서는 balance 에 닿을 길이 없으니까요.

pub(crate) 와 pub(super)

"전부 공개" 와 "비공개" 사이의 단계입니다. pub(crate) 는 이 크레이트 안에서만, pub(super) 는 바로 위 모듈까지만 보입니다.

자식은 부모의 비공개를 본다

비공개는 "그 모듈과 그 안쪽" 까지 보인다는 뜻입니다. 그래서 자식 모듈은 부모의 비공개 항목을 쓸 수 있습니다. 반대로 부모는 자식의 비공개 항목을 못 봅니다.

시험 모듈이 기대는 규칙 — 4장의 mod tests 가 비공개 함수를 시험할 수 있는 까닭이 이것입니다.

퀴즈 — 모듈

Q. pub struct Account { pub owner: String, balance: u64 } 를 모듈 밖에서 Account { owner: …, balance: 0 } 으로 만들 수 있을까요?

A. 없습니다. balance 가 비공개라서 E0451 이 납니다 (밖에서 만들 수 없다). 모듈이 Account::new 같은 공개 생성 함수를 내줘야 합니다.

2장

파일로 나누기

mod 이름; · 파일 이름 규칙 · 라이브러리 크레이트와 실행 크레이트

mod shapes; — 내용은 다른 파일에

중괄호 대신 세미콜론으로 끝내면 "이 모듈의 내용은 파일에 있다" 는 선언입니다. 컴파일러가 같은 이름의 파일을 찾아 읽습니다.

include 가 아니다 — 파일을 아무 데서나 끌어오는 것이 아니라, 부모 모듈이 mod 이름; 으로 선언해야 그 파일이 크레이트에 들어옵니다.

파일을 찾는 규칙

선언한 곳선언찾는 파일
main.rs (뿌리)mod shapes;shapes.rs
shapes.rspub mod circle;shapes/circle.rs
shapes/circle.rsmod util;shapes/circle/util.rs
옛 방식 — shapes.rs 대신 shapes/mod.rs 에 두는 방식도 여전히 됩니다. 오래된 코드에서 자주 봅니다.

파일이 없으면 — E0583

선언만 하고 파일을 만들지 않으면 컴파일러가 어디를 찾아봤는지 알려 줍니다.

라이브러리 크레이트와 실행 크레이트

cargo 패키지 하나에 src/lib.rs(라이브러리)와 src/main.rs(실행 파일)를 함께 둘 수 있습니다. 둘은 별개의 크레이트이고, 실행 쪽이 라이브러리를 패키지 이름으로 가져다 씁니다.

lib.rs — 일은 여기서 한다

로직을 라이브러리에 두면 시험하기 쉽고, 다른 프로그램에서도 가져다 쓸 수 있습니다. main 은 인자를 읽고 라이브러리를 부르는 얇은 껍데기로 둡니다.

실제 도구들이 이 모양 — 명령 줄 프로그램도 대개 lib.rs + 얇은 main.rs 로 짭니다. 아래쪽의 시험 모듈은 4장에서 봅니다.

퀴즈 — 파일로 나누기

Q. shapes.rs 안에 pub mod circle; 이라고 쓰면 컴파일러는 어느 파일을 찾을까요?

A. shapes/circle.rs 입니다(또는 shapes/circle/mod.rs). 모듈의 하위 모듈은 그 모듈 이름의 디렉터리 아래에 둡니다(파일을 찾는 규칙).

3장

cargo 더

Cargo.toml 의 구역들 · 기능(feature) · 크레이트 저장소와 버전

Cargo.toml 의 구역들

구역적는 것
[package]이름, 버전, 에디션
[dependencies]가져다 쓸 크레이트와 버전
[dev-dependencies]시험과 예제에서만 쓰는 크레이트
[features]켜고 끌 수 있는 기능의 이름
[profile.release] 등빌드 설정(최적화 수준 따위)
[workspace]여러 패키지를 한 묶음으로

기능(feature) — 컴파일할 때 켜고 끈다

#[cfg(feature = "이름")] 이 붙은 코드는 그 기능을 켰을 때만 컴파일됩니다. 같은 소스에서 다른 실행 파일이 나옵니다.

크레이트 저장소와 버전

공개된 크레이트는 crates.io 에 모여 있습니다(1부). [dependencies] 에 이름과 버전을 적으면 cargo 가 받아 와 함께 컴파일합니다.

버전 주.부.수올리는 때
주(major)쓰는 쪽이 고쳐야 하는 변화
부(minor)기능을 더했지만 옛 코드는 그대로 돈다
수(patch)버그만 고쳤다
  • Cargo.lock 은 실제로 쓴 정확한 버전을 적어 둡니다. 다시 빌드해도 같은 것을 씁니다.
  • 이 책은 표준 라이브러리만 쓰므로 [dependencies] 가 늘 비어 있습니다. 예제를 인터넷 없이 돌릴 수 있는 까닭입니다.

퀴즈 — cargo

Q. #[cfg(feature = "fancy")] 가 붙은 함수는 cargo run 만 하면 실행 파일에 들어 있을까요?

A. 아닙니다. 기능을 켜지 않으면 그 함수는 컴파일되지도 않습니다. cargo run --features fancy 로 켜야 합니다(기능).

4장

시험

#[test] · assert 삼형제 · 실패한 시험 읽기 · should_panic · tests 모듈 · 통합 시험

#[test] — 함수 하나가 시험 하나

시험 도구가 언어에 들어 있습니다. #[test] 를 붙인 함수가 시험이고, 패닉하지 않고 끝나면 통과입니다. --test 로 컴파일하면 시험들을 돌리는 실행 파일이 만들어집니다.

cargo 에서는 cargo test 한 번입니다. 이 장 뒤쪽에서 봅니다.

실패한 시험은 무엇이 달랐는지 말해 준다

add 에 버그를 넣었습니다. assert_eq! 는 두 값이 다르면 양쪽 값을 찍으며 패닉합니다.

읽는 법 — left 가 실제로 나온 값, right 가 기대한 값(적은 순서대로)입니다. 끝의 failures: 아래에 실패한 시험 이름이 모이고, 종료 코드는 0 이 아닙니다.

assert! · assert_eq! · assert_ne!

참이어야 한다, 같아야 한다, 달라야 한다. 뒤에 서식 문자열을 붙이면 실패했을 때 그 말이 찍힙니다.

패닉해야 통과 — #[should_panic]

"잘못된 입력에는 패닉한다" 도 시험할 약속입니다. expected 에 메시지의 일부를 적으면 엉뚱한 까닭으로 패닉한 것을 통과로 치지 않습니다.

Result 를 돌려주는 시험

시험 함수가 Result 를 돌려주면 그 안에서 ? 를 쓸 수 있습니다. Err 로 끝나면 실패입니다(9부).

오래 걸리는 시험은 #[ignore]

평소에는 건너뛰고 싶은 시험에 붙입니다. 결과 줄에 ignored 로 세어집니다.

돌리고 싶을 때 — cargo test -- --ignored 처럼 -- 뒤에 시험 실행 파일에 줄 옵션을 적습니다.

시험은 같은 파일의 tests 모듈에 둔다

관례는 시험할 코드와 같은 파일 아래쪽에 mod tests 를 두는 것입니다. #[cfg(test)] 가 붙어 있어 시험할 때만 컴파일됩니다.

비공개 함수도 시험한다 — tests 는 자식 모듈이라 부모의 비공개 함수 clean 을 부를 수 있습니다(1장). use super::*; 가 부모의 이름을 전부 끌어옵니다.

통합 시험 — tests/ 디렉터리

tests/ 아래의 파일은 따로 컴파일되는 크레이트입니다. 라이브러리를 바깥 사용자처럼 가져다 쓰므로 공개된 것만 시험할 수 있습니다.

단위 시험통합 시험
자리src/ 안의 mod teststests/*.rs
볼 수 있는 것비공개까지공개 API 만
확인하는 것조각 하나하나밖에서 쓰는 방식 그대로

cargo test — 전부 한 번에

cargo test 는 패키지의 시험을 종류별로 차례로 돌립니다. -q 를 붙여 시험 하나를 점 하나로 줄였습니다.

네 묶음 — 차례로 ① lib.rs 의 단위 시험 2개, ② main.rs 의 단위 시험 0개, ③ tests/api.rs 의 통합 시험 1개, ④ 문서 시험 0개(다음 장)입니다.

이름으로 골라 돌린다

cargo test 뒤에 글자를 주면 이름에 그 글자가 든 시험만 돕니다. 하나를 고치는 동안 전부를 기다리지 않아도 됩니다.

1 filtered out — 걸러져 돌지 않은 시험의 수입니다. 통과로 세지 않습니다.

퀴즈 — 시험

Q. assert_eq!(add(2, 3), 5) 가 실패하며 left: -1, right: 5 를 찍었습니다. 어느 쪽이 실제로 나온 값일까요?

A. left(-1)입니다. assert_eq! 에 적은 순서대로 왼쪽·오른쪽이고, 여기서는 왼쪽에 add(2, 3) 을 적었습니다(실패한 시험).

5장

문서

/// 와 //! · 문서 속 예제는 시험이다 · 속성 정리

/// 는 아래 항목의, //! 는 감싼 것의 문서

/// 는 바로 아래 항목을 설명합니다. //! 는 자기를 감싼 것 — 파일 맨 위에 쓰면 크레이트나 모듈 전체 — 를 설명합니다. 안에는 마크다운을 씁니다.

cargo doc 이 이 주석들을 모아 HTML 문서를 만듭니다. 표준 라이브러리 문서가 바로 그렇게 만든 것입니다.

문서 속 예제는 시험으로 돈다

문서 주석 안의 코드 블록은 cargo test 가 실제로 컴파일해 돌립니다. 문서의 예제가 낡아 틀리게 되면 시험이 실패합니다.

거짓말하지 않는 문서 — 이 책이 "돌려 본 예제만 싣는다" 를 도구로 강제하는 것과 같은 생각입니다. Rust 는 그것을 표준 도구에 넣어 두었습니다. should_panic 을 붙인 블록은 패닉해야 통과입니다.

속성으로 경고를 끈다 — #[allow]

#[…] 는 바로 아래 항목에 대한 지시입니다. #[allow(경고이름)] 은 그 항목 안에서 그 경고를 끕니다. 경고 이름은 경고 메시지의 note: 줄에 나옵니다.

좁게 끈다 — 파일 전체가 아니라 필요한 항목 하나에 붙입니다. 경고는 대개 옳습니다.

쓰지 말라고 알리기 — #[deprecated]

없애고 싶은 함수를 바로 지우면 쓰던 코드가 깨집니다. 먼저 이 속성을 붙여, 쓰는 쪽에 경고와 함께 갈아탈 곳을 알립니다.

1부에서 본 것 — 표준 라이브러리의 try! 가 이렇게 경고를 내고 있었습니다 (1부 3장).

조건부 컴파일 — #[cfg]

#[cfg(조건)] 이 붙은 항목은 조건이 맞을 때만 컴파일됩니다. 운영 체제마다 다른 구현을 둘 때 씁니다. 같은 조건을 값으로 얻는 것이 cfg! 매크로입니다.

지금까지 본 속성

속성하는 일본 곳
#[derive(…)]트레이트 구현을 만들어 준다7부 · 10부
#[test]시험 함수로 표시4장
#[should_panic] · #[ignore]시험의 성격4장
#[cfg(…)]조건부 컴파일3장 · 이 장
#[allow(…)]경고를 끈다이 장
#[deprecated]쓰는 쪽에 경고이 장
#[must_use]결과를 버리면 경고5부

#![…] 처럼 느낌표가 붙으면 아래 항목이 아니라 자기를 감싼 것(파일·크레이트) 전체에 걸립니다.

퀴즈 — 문서

Q. 문서 주석 안에 적은 예제 코드가 틀리면(예: 함수의 동작을 바꿨는데 문서를 안 고쳤다) 어떻게 알 수 있을까요?

A. cargo test 가 문서 속 코드 블록도 시험으로 돌리므로 거기서 실패합니다 (문서 속 예제).
