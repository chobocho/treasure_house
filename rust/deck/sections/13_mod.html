모듈·크레이트·시험·문서

mod 와 pub · 파일로 나누기 · Cargo.toml · #[test] · 문서 주석과 문서 시험

이 부에서 할 일

지금까지의 예제는 파일 하나였습니다. 프로그램이 커지면 코드를 나누고, 무엇을 밖에 보일지 정하고, 고칠 때마다 다시 확인할 시험이 필요합니다. 이 부는 그 도구들을 봅니다. use · cargo · assert! · /// 처럼 이미 써 온 것이 많습니다. 그 뒤에 있는 규칙을 여기서 채웁니다.

  • 1장 — 모듈: mod, pub, 경로, use
  • 2장 — 파일로 나누기, 라이브러리 크레이트와 실행 크레이트
  • 3장 — cargo 더: Cargo.toml, 켜고 끄는 기능, 크레이트 저장소
  • 4장 — 시험: #[test], assert!, cargo test
  • 5장 — 문서: ///, 문서 속 예제가 시험으로 돈다, 속성 정리
낱말 둘 — 크레이트(crate)는 컴파일의 한 단위(라이브러리 하나 또는 실행 파일 하나)이고, 모듈(module)은 크레이트 안을 나누는 이름 공간입니다. 크레이트는 10부의 고아 규칙이 "내 것인가" 를 가르던 그 단위입니다.

1장

모듈

mod · 기본은 비공개 · 경로 · use · 다시 내놓기 · 필드의 공개 · pub(crate) · 자식과 부모

mod — 이름 공간을 만든다

함수가 늘면 이름이 한 층에 쌓여 서로 부딪치고, 어느 것이 밖에서 써도 되는 것인지 보이지 않습니다. mod 이름 { … } 으로 관련된 것들을 묶습니다. 밖에서 쓸 것에는 pub 을 붙이고, 모듈::이름 으로 부릅니다.

이미 써 온 것 — 10부의 트레이트를 끌어와야 했던 예제에서 mod shapes { … } 와 pub 을 미리 썼습니다. 그때 넘어간 규칙을 이 장에서 봅니다.

기본은 비공개다 — E0603

pub 을 붙이지 않은 것은 그 모듈 밖에서 보이지 않습니다. Rust 는 "숨기는 쪽" 이 기본입니다. 앞 슬라이드의 도우미 double 을 이번에는 main 에서 직접 부릅니다.

읽는 법 — "함수 double 은 비공개다". 8번 줄 double 밑의 private function 이 막힌 자리이고, note: 는 그 함수가 정의된 곳(2번 줄)을 가리킵니다. 거기에 pub 이 없습니다.
숨긴 것은 마음대로 고칠 수 있다 — 밖에서 못 쓰는 것은 바꿔도 다른 코드가 깨지지 않습니다. 공개한 것만이 약속입니다.

pub 없는 메서드를 밖에서 부르면 번호가 다릅니다. 26부의 모듈 밖에서 pub 없는 메서드를 불렀다에서 봅니다.

경로 — crate · super · self

이름을 찾아가는 길이 경로(path)입니다. 파일 시스템의 절대 경로·상대 경로와 같은 생각입니다.

시작뜻파일 시스템에 견주면
crate::이 크레이트의 뿌리에서/
super::한 단계 위 모듈에서../
self::지금 모듈에서(생략 가능)./

8번 줄의 crate::version() 과 super::version() 은 같은 함수에 닿아 1.0 / 1.0 이 찍혔습니다.

use — 이름을 이 자리로 끌어온다

긴 경로를 매번 쓰지 않도록 use 로 끌어옵니다. 함수는 보통 모듈까지만 끌어와 circle::area 처럼 어디 것인지 보이게 쓰고, 타입은 이름째 끌어옵니다.

이미 써 온 것 — 8부부터 파일 첫머리에 적은 use std::collections::HashMap; 이 이 문법입니다. 경로의 마지막 이름 HashMap 을 끌어왔으니, 타입을 이름째 끌어오는 쪽입니다. 10부에서 메서드를 부르려고 트레이트를 끌어온 것도 같은 use 입니다.

use 의 여러 모양

여럿을 한 줄에 묶거나({ }), 이름이 겹칠 때 별명을 붙이거나(as), 모듈의 공개 이름을 전부 끌어올(*) 수 있습니다. 아래에서는 이름이 같은 두 Result 에 별명을 붙였습니다.

* 는 아껴 쓴다 — 어떤 이름이 어디서 왔는지 보이지 않게 됩니다. 시험 모듈의 use super::*;(4장)처럼 스코프가 좁을 때 씁니다.

pub use — 다시 내놓기

use 앞에 pub 을 붙이면 끌어온 이름을 그 자리에서 다시 공개합니다. 안쪽 모듈 구조를 숨기고 쓰기 좋은 이름만 바깥 층에 내놓습니다. 안은 마음대로 나누고, 밖에는 평평한 모양을 보여 줍니다.

구조체의 필드도 따로 공개한다 — E0616

구조체에 pub 을 붙여도 필드는 여전히 비공개입니다. 필드마다 따로 정합니다.

읽는 법 — "구조체 Account 의 필드 balance 는 비공개다". 18번 줄 a.balance 밑에 private field 가 붙었습니다. 바로 윗줄의 a.owner 에는 아무 말이 없습니다 — pub 을 붙인 필드이기 때문입니다.

비공개 필드가 있으면 밖에서 만들 수 없다 — E0451

필드 하나라도 비공개면 모듈 밖에서는 Account { … } 로 값을 만들 수 없습니다. 채울 수 없는 칸이 있기 때문입니다.

읽는 법 — 18번 줄 balance: 100 밑의 private field 가 막힌 칸이고, 16번 줄 bank::Account 밑의 in this type 이 어느 타입 이야기인지 알려 줍니다. 앞 슬라이드에서 필드를 읽을 때 난 E0616 과 번호는 달라도 까닭은 같습니다.

그래서 생성 함수를 내준다

비공개 필드를 둔 타입은 new 같은 공개 연관 함수로만 만들게 합니다. 값이 늘 올바른 상태로 시작하고, 바꾸는 길도 메서드로 정해집니다.

캡슐화 — 잔액을 바꾸는 길은 deposit 하나뿐입니다. 잔액에 규칙을 두고 싶다면 이 한 곳만 지키면 됩니다. 밖에서는 balance 필드에 닿을 길이 없기 때문입니다.

pub(crate) 와 pub(super)

"전부 공개" 와 "비공개" 사이의 단계입니다. pub(crate) 는 이 크레이트 안에서만, pub(super) 는 바로 위 모듈까지만 보입니다.

자식은 부모의 비공개를 본다

비공개는 "그 모듈과 그 안쪽" 까지 보인다는 뜻입니다. 그래서 자식 모듈은 부모의 비공개 항목을 쓸 수 있습니다. 반대로 부모는 자식의 비공개 항목을 못 봅니다 — 앞의 E0603 이 뿌리 모듈의 main 이 자식 geometry 의 double 을 부르려던 경우였습니다.

시험 모듈이 기대는 규칙 — 4장의 mod tests 가 비공개 함수를 시험할 수 있는 까닭이 이것입니다.

퀴즈 — 모듈

Q. pub struct Account { pub owner: String, balance: u64 } 를 모듈 밖에서 Account { owner: …, balance: 0 } 으로 만들 수 있을까요?

A. 없습니다. balance 가 비공개라서 E0451 이 납니다 (밖에서 만들 수 없다). 모듈이 Account::new 같은 공개 생성 함수를 내줘야 합니다.

2장

파일로 나누기

mod 이름; · 파일을 찾는 규칙 · 파일이 없을 때 · 라이브러리 크레이트와 실행 크레이트

mod shapes; — 내용은 다른 파일에

모듈이 커지면 파일 하나에 다 두기 어렵습니다. 중괄호 대신 세미콜론으로 끝내면 "이 모듈의 내용은 파일에 있다" 는 선언입니다. 컴파일러가 같은 이름의 파일을 찾아 읽습니다.

find 가 보여 주는 소스 파일은 셋입니다. rustc 에는 main.rs 하나만 넘겼는데, 다른 두 파일에 있는 shapes::area 의 12 와 shapes::circle::area 의 3.14 가 찍혔습니다.

include 가 아니다 — 파일을 아무 데서나 끌어오는 것이 아니라, 부모 모듈이 mod 이름; 으로 선언해야 그 파일이 크레이트에 들어옵니다. 세 번째 파일 shapes/circle.rs 는 다음 슬라이드에 있습니다. 선언 없이 use 만 적으면 나는 오류는 26부의 파일은 만들었는데 mod 로 선언하지 않았다에서 봅니다.

파일을 찾는 규칙

선언이 적힌 파일의 자리가 찾을 자리를 정합니다. 표의 위 두 줄이 앞 슬라이드의 예제이고, 셋째 줄은 한 단계 더 내려갈 때의 모양입니다.

선언한 곳선언찾는 파일
main.rs (뿌리)mod shapes;shapes.rs
shapes.rspub mod circle;shapes/circle.rs
shapes/circle.rsmod util; (예제에는 없음)shapes/circle/util.rs
또 하나의 자리 — shapes.rs 대신 shapes/mod.rs 에 두어도 됩니다. 다음 슬라이드의 오류 메시지가 두 이름을 나란히 댑니다.

파일이 없으면 — E0583

선언만 하고 파일을 만들지 않으면 컴파일러가 어떤 파일을 만들면 되는지 알려 줍니다.

읽는 법 — "모듈 shapes 의 파일을 찾지 못했다". 밑줄은 1번 줄의 선언 전체입니다. help: 가 만들 파일 이름 둘(shapes.rs 또는 shapes/mod.rs)을 대고, note: 는 그 모듈이 이미 다른 곳에 선언돼 있다면 mod 를 또 쓰지 말고 use 로 가져오라고 합니다.

라이브러리 크레이트와 실행 크레이트

2부의 cargo new 가 만든 소스는 src/main.rs(실행 파일) 하나였습니다. 같은 패키지에 src/lib.rs(라이브러리)를 함께 둘 수 있습니다. 둘은 별개의 크레이트이고, 실행 쪽이 라이브러리를 패키지 이름으로 가져다 씁니다. 네 번째 파일 tests/api.rs 는 4장에서 봅니다.

lib.rs — 일은 여기서 한다

일을 라이브러리에 두면 다른 크레이트가 가져다 쓸 수 있습니다. 바로 앞의 main.rs 가 그랬고, 4장의 통합 시험도 그렇게 합니다. main 은 라이브러리를 부르는 얇은 껍데기로 둡니다.

읽는 법 — 앞 슬라이드에서 main 이 넘긴 " Ferris " 의 빈칸은 clean 이 떼어 냈습니다. 그래서 화면에 안녕, Ferris! 가 찍혔습니다.
나머지는 뒤에서 — 이 파일 아래쪽의 시험 모듈은 4장에서, 맨 위의 //! 와 /// 주석은 5장에서 봅니다. 이 짜임으로 프로그램 하나를 끝까지 만드는 것은 24부의 main 은 열일곱 줄에서 봅니다.

퀴즈 — 파일로 나누기

Q. shapes.rs 안에 pub mod circle; 이라고 쓰면 컴파일러는 어느 파일을 찾을까요?

A. shapes/circle.rs 입니다(또는 shapes/circle/mod.rs). 모듈의 하위 모듈은 그 모듈 이름의 디렉터리 아래에 둡니다(파일을 찾는 규칙).

3장

cargo 더

Cargo.toml 의 구역들 · 켜고 끄는 기능 · 크레이트 저장소와 버전

Cargo.toml 의 구역들

2부에서 cargo new 가 채워 준 Cargo.toml 에는 [package] 와 빈 [dependencies] 뿐이었고, 나머지는 여기서 보기로 했습니다. 표는 자주 만나는 구역 여섯이고, 그 아래는 그 가운데 셋을 쓴 파일입니다.

구역적는 것
[package]이름, 버전, 에디션
[dependencies]가져다 쓸 크레이트와 버전
[dev-dependencies]시험과 예제에서만 쓰는 크레이트
[features]켜고 끌 수 있는 기능의 이름
[profile.release] 등빌드 설정(최적화 수준 따위)
[workspace]여러 패키지를 한 묶음으로

위 파일에 있는 구역은 [package] · [features] · [dependencies] 셋입니다. 나머지 셋은 이 부의 예제에 쓰지 않아 이름과 뜻만 적었습니다. [workspace] 는 23부의 워크스페이스에서, [profile.release] 는 프로필의 키에서 씁니다. 프로필 dev 와 release 는 2부의 --release 에서 봤고, 최적화하면 동작까지 달라지는 예는 3부의 넘침 검사에서 봤습니다.

기능(feature) — 컴파일할 때 켜고 끈다

#[cfg(feature = "이름")] 이 붙은 코드는 그 기능을 켰을 때만 컴파일됩니다. 같은 소스에서 다른 실행 파일이 나옵니다.

fancy 와 not — fancy 는 앞 슬라이드 Cargo.toml 의 [features] 에 선언한 이름입니다. not(…) 은 조건을 뒤집습니다. 둘 중 하나만 컴파일되므로 이름이 같은 함수 둘이 부딪치지 않습니다. #[cfg] 는 5장에서 다시 봅니다.

크레이트 저장소와 버전

공개된 크레이트는 crates.io 에 모여 있습니다(1부). [dependencies] 에 이름과 버전을 적으면 cargo 가 받아 와 함께 컴파일합니다. 이 책은 2부에서 말한 대로 표준 라이브러리만 써서 그 칸에 바깥 크레이트를 적지 않습니다. 그 칸에 적는 것은 23부의 path 의존성뿐입니다. 예제를 인터넷 없이 돌릴 수 있는 까닭이고, 이 슬라이드가 돌려 보지 않고 설명만 하는 까닭입니다.

버전 주.부.수올리는 때
주(major)쓰는 쪽이 고쳐야 하는 변화
부(minor)기능을 더했지만 옛 코드는 그대로 돈다
수(patch)버그만 고쳤다

버전의 세 숫자를 언제 올리기로 약속했는지입니다(semver 라고 부릅니다). 이 장의 Cargo.toml 에 적힌 0.1.0 이 이 세 칸입니다.

Cargo.lock — 실제로 쓴 정확한 버전을 적어 두는 파일입니다. 다시 빌드해도 같은 것을 씁니다.

퀴즈 — cargo

Q. #[cfg(feature = "fancy")] 가 붙은 함수는 cargo run 만 하면 실행 파일에 들어 있을까요?

A. 아닙니다. 기능을 켜지 않으면 그 함수는 컴파일되지도 않습니다. cargo run --features fancy 로 켜야 합니다(기능).

4장

시험

#[test] · 실패한 시험 읽기 · assert 삼형제 · should_panic · Result 를 돌려주는 시험 · #[ignore] · tests 모듈 · 통합 시험 · cargo test

#[test] — 함수 하나가 시험 하나

고칠 때마다 손으로 돌려 눈으로 확인할 수는 없습니다. 그 확인을 코드로 적어 둔 것이 시험이고, 도구는 언어에 들어 있습니다. #[test] 를 붙인 함수가 시험이고, 패닉하지 않고 끝나면 통과입니다. 기대한 값은 9부에서 본 assert_eq! 로 적습니다. --test 로 컴파일하면 시험들을 돌리는 실행 파일이 만들어집니다.

  • 시험 하나에 결과 한 줄입니다. 소스에 적은 순서가 아니라 이름 순으로 찍혔습니다.
  • --test-threads=1 은 시험을 한 번에 하나씩 돌리라는 옵션입니다(스레드는 15부). 이것 없이 돌렸더니 결과 줄의 순서가 실행마다 달라지는 일이 있어, 시험이 둘 이상인 예제에는 붙였습니다.
  • 마지막 줄이 요약입니다. measured 는 속도를 재는 시험의 수인데 이 책에서는 늘 0 입니다. 걸린 시간은 0부에서 본 대로 0.00s 로 맞춰 적었습니다. ignored · filtered out 과 cargo 로 한 번에 돌리는 cargo test 는 이 장 뒤쪽에서 봅니다.

실패한 시험은 무엇이 달랐는지 말해 준다

앞 슬라이드의 add 에 버그를 넣었습니다. assert_eq! 는 두 값이 다르면 양쪽 값을 찍으며 패닉합니다.

읽는 법 — 패닉 줄은 9부에서 읽은 모양 그대로입니다. panicked at test_fail.rs:7:5 가 실패한 assert_eq! 의 자리(7번 줄)이고, 스레드 이름 자리에는 시험 이름이 찍힙니다. left 는 왼쪽에 적은 식의 값(실제로 나온 -1), right 는 오른쪽에 적은 값(기대한 5)입니다. 끝의 failures: 아래에 실패한 시험 이름이 모이고, 종료 코드는 101 입니다.

assert! · assert_eq! · assert_ne!

9부에서 전제를 적는 데 쓴 assert! · assert_eq! 에 assert_ne! 를 더하면 셋입니다 — 참이어야 한다, 같아야 한다, 달라야 한다. 뒤에 서식 문자열을 붙이면 실패했을 때 그 말이 찍힙니다.

읽는 법 — 둘은 통과, 하나는 실패입니다. 결과 줄은 이름 순이라 소스의 마지막 시험 message_shows_values 가 맨 위에 왔습니다. panicked at test_asserts.rs:19:5 의 다음 줄이 19번 줄에 직접 쓴 메시지이고, {n} 자리에 7 이 들어갔습니다. 8번 줄의 메시지는 그 assert! 가 통과했으므로 찍히지 않았습니다.

패닉해야 통과 — #[should_panic]

"잘못된 입력에는 패닉한다" 도 시험할 약속입니다. expected 에는 패닉 메시지에 들어 있어야 할 글자를 적습니다. 다른 까닭의 패닉과 구별하려는 것입니다.

- should panic — 결과 줄에 이 시험의 성격이 붙어 나옵니다. rejects_zero 는 패닉했고, 그 메시지 "0 으로 나눌 수 없다" 에 expected 의 "0 으로" 가 들어 있어 ok 입니다.

패닉은 했지만 expected 와 다른 말이라 통과하지 못하는 화면은 23부의 should_panic(expected)에서 봅니다.

Result 를 돌려주는 시험

9부에서 main 이 Result 를 돌려준 것처럼 시험 함수도 Result 를 돌려줄 수 있습니다. 그러면 안에서 ? 를 쓸 수 있고, Err 로 끝나면 실패입니다.

읽는 법 — doubles_x 는 패닉하지 않았습니다. ? 가 돌려준 Err 값이 Error: 뒤에 디버그 모양으로 찍히고, 그 시험은 실패로 세어졌습니다. 종료 코드는 main 이 Err 로 끝났을 때의 1 이 아니라, 시험이 패닉으로 실패했을 때와 같은 101 입니다.

오래 걸리는 시험은 #[ignore]

평소에는 건너뛰고 싶은 시험에 붙입니다. 결과 줄에 ignored 로 세어집니다.

돌리고 싶을 때 — 시험 실행 파일에 --ignored 를 주면 건너뛰던 것만 돕니다. 이때 quick 은 1 filtered out 으로 세어졌습니다.

시험은 같은 파일의 tests 모듈에 둔다

관례는 시험할 코드와 같은 파일 아래쪽에 mod tests 를 두는 것입니다. 3장에서 본 #[cfg] 의 조건이 test 라서 시험할 때만 컴파일됩니다.

비공개 함수도 시험한다 — tests 는 자식 모듈이라 부모의 비공개 함수 clean 을 부를 수 있습니다(1장). use super::*; 가 부모의 이름을 전부 끌어옵니다.

네 묶음 — 둘째 상자는 -q 없이 돌려 묶음마다 찍히는 이름 줄만 골라낸 것입니다 (sed 는 줄 끝의 실행 파일 경로를 뗍니다). 차례로 ① lib.rs 의 단위 시험 2개, ② main.rs 의 단위 시험 0개, ③ tests/api.rs 의 통합 시험 1개, ④ 문서 시험(Doc-tests) 0개입니다. 문서 시험은 5장에서 봅니다.

이름으로 골라 돌린다

1 filtered out — 걸러져 돌지 않은 시험의 수입니다. 통과로 세지 않습니다. 첫 묶음 (lib.rs)에서는 trims_spaces 가 돌고 greets_by_name 이 걸러졌고, 셋째 묶음 (tests/api.rs)에서는 하나뿐인 시험이 걸러졌습니다. 이번에는 묶음이 셋만 찍혔습니다.

문서 속 예제는 시험으로 돈다

문서 주석 안의 코드 블록은 cargo test 가 실제로 컴파일해 돌립니다. 문서의 예제가 낡아 틀리게 되면 시험이 실패합니다.

--doc 은 문서 시험만 돌리라는 옵션입니다. should_panic 을 붙인 둘째 블록은 4장의 #[should_panic] 처럼 패닉해야 통과입니다. 마지막 줄은 문서 시험을 컴파일하고 돌리는 데 걸린 시간입니다(0.00s 로 맞춰 적었습니다).

거짓말하지 않는 문서 — 이 책이 "돌려 본 예제만 싣는다" 를 도구로 강제하는 것과 같은 생각입니다. Rust 는 그것을 표준 도구에 넣어 두었습니다.

속성으로 경고를 끈다 — #[allow]

이 장의 나머지는 속성(attribute)입니다. 5부에서 본 대로 #[…] 는 바로 아래 항목에 대한 지시이고, 이 부에서도 #[test] 와 #[cfg] 로 써 왔습니다. #[allow(경고이름)] 은 그 항목 안에서 그 경고를 끕니다.

읽는 법 — 화면에 경고가 없습니다. 경고 이름은 경고의 note: 줄에 나옵니다. 5번 줄의 unused_variables 는 3부의 쓰지 않은 변수 경고에서 본 이름이고, 다음 슬라이드의 화면에는 #[warn(deprecated)] 가 보입니다.
좁게 끈다 — 파일 전체가 아니라 필요한 항목 하나에 붙입니다. 경고는 대개 옳습니다. 경고의 수준을 Cargo.toml 에서 패키지 전체에 정하는 것은 23부의 [lints] 표에서 봅니다.

쓰지 말라고 알리기 — #[deprecated]

없애고 싶은 함수를 바로 지우면 쓰던 코드가 깨집니다. 먼저 이 속성을 붙여, 쓰는 쪽에 경고와 함께 갈아탈 곳을 알립니다.

읽는 법 — 경고는 old_api 를 부른 11번 줄을 가리키고, 경고 첫 줄의 쌍점 뒤에 note 에 적은 말이 그대로 붙습니다. 경고일 뿐이라 프로그램은 돌아 1 2 를 찍습니다. 표준 라이브러리의 try! 도 이렇게 경고를 내고 있었습니다(1부의 옛 방식의 코드가 지금도 컴파일된다).

조건부 컴파일 — #[cfg]

3장의 기능과 4장의 시험 모듈에 붙였던 속성입니다. #[cfg(조건)] 이 붙은 항목은 조건이 맞을 때만 컴파일됩니다. 운영 체제마다 다른 구현을 둘 때도 씁니다. 같은 조건을 bool 값으로 얻는 것이 cfg! 매크로입니다. 2부의 cfg!(debug_assertions) 가 그것이었고, 16부에서 다시 봅니다.

기계마다 다른 출력 — 이 화면은 이 책을 만든 기계의 것입니다. 안드로이드가 아닌 곳에서 컴파일하면 2번 줄이 아니라 7번 줄 쪽 platform 이 들어가 android 대신 그 밖 이 찍힙니다. not(…) 은 3장의 기능 예제에서 본 것과 같습니다.
