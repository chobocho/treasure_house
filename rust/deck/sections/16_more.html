1장

매크로

macro_rules! · 패턴과 펼침 · 반복 · 이름 섞임 방지 · 표준 매크로 · derive

macro_rules! — 코드를 만들어 내는 코드

매크로는 컴파일 전에 코드를 다른 코드로 펼칩니다. macro_rules! 로 만들고, 부를 때는 이름 뒤에 ! 를 붙입니다. "이런 모양이 오면 → 이런 코드로" 를 적습니다.

함수와 다른 점 — 타입을 적지 않았습니다. square!(7) 은 7 * 7 로, square!(1.5) 는 1.5 * 1.5 로 펼쳐진 뒤에 타입 검사를 받습니다.

갈래를 여럿 둔다

match 처럼 패턴을 여럿 적을 수 있습니다. 함수에는 없던 "인자 개수에 따라 다른 일" 이 매크로로는 됩니다.

몇 개든 받는다 — $( … ),*

$( … ),* 는 "쉼표로 나뉜 이것이 0번 이상" 입니다. 펼치는 쪽에서도 같은 표기로 받은 만큼 되풀이합니다. println! 과 vec! 이 인자를 몇 개든 받는 비결입니다.

나만의 vec! 만들기

반복을 써서 키 => 값 을 나열하면 맵을 만들어 주는 매크로입니다. 문법을 새로 지어낸 셈입니다.

$(,)? 는 "쉼표가 있어도 없어도" 입니다. 마지막 항목 뒤의 쉼표를 허락합니다. 바깥의 겹 중괄호 {{ … }} 는 펼친 결과를 블록 하나로 만들어 값으로 쓰게 합니다.

이름을 받아 함수를 찍어 낸다

받는 것의 종류를 : 뒤에 적습니다. expr 은 식, ident 는 이름입니다. 이름을 받으면 그 이름으로 함수나 타입을 만들어 낼 수 있습니다.

종류받는 것종류받는 것
expr식ty타입
ident이름literal리터럴
pat패턴tt토큰 한 덩이(무엇이든)

매크로 안의 이름은 바깥과 섞이지 않는다

매크로가 안에서 만든 tmp 와 부른 쪽의 tmp 는 글자가 같아도 다른 변수입니다. C 의 매크로에서 흔하던 이름 충돌이 일어나지 않습니다. 이것을 위생(hygiene)이라고 합니다.

맞는 갈래가 없으면

어느 패턴에도 맞지 않게 부르면 컴파일 오류입니다. 메시지는 매크로의 어느 자리에서 막혔는지 알려 줍니다.

표준 매크로 몇 가지

함수로는 할 수 없는 일을 하는 매크로들입니다. 식을 글자로 바꾸거나, 소스의 자리를 알려 주거나, 컴파일 조건을 값으로 줍니다.

이미 써 온 것들 — println! · format! · vec! · assert! · panic! · todo! · matches! · dbg! 도 모두 매크로입니다.

derive 도 매크로다

#[derive(Debug)] 는 구조체 정의를 읽고 impl Debug for Point { … } 를 대신 써 주는 매크로입니다. 이런 것을 절차적 매크로(procedural macro)라고 합니다.

종류모양만드는 법
선언적 매크로name!(…)macro_rules! — 이 장
derive 매크로#[derive(Name)]따로 만든 크레이트의 Rust 함수
속성 매크로#[name]〃

절차적 매크로를 직접 만드는 일은 이 책의 범위 밖입니다.

퀴즈 — 매크로

Q. println! 은 왜 함수가 아니라 매크로일까요?

A. Rust 의 함수는 인자의 개수와 타입이 정해져 있습니다(5부). 인자를 몇 개든, 어떤 타입이든 받으려면 매크로여야 합니다(몇 개든 받는다). 서식 문자열을 컴파일할 때 검사하는 것도 매크로라서 가능합니다.

2장

unsafe

컴파일러 대신 내가 보증한다 · 날 포인터 · unsafe fn · 안전한 포장 · C 함수 부르기

unsafe 가 풀어 주는 것은 다섯 가지뿐이다

컴파일러가 안전하다고 증명하지 못하지만 실제로는 괜찮은 코드가 있습니다. unsafe 는 "이 부분은 내가 보증한다" 는 표시이고, 그 안에서만 할 수 있는 일은 정해져 있습니다.

  1. 날 포인터(raw pointer)를 따라가기
  2. unsafe 함수와 메서드를 부르기
  3. 바뀔 수 있는 전역 변수(static mut)에 닿기
  4. unsafe 트레이트를 구현하기
  5. union 의 필드를 읽기
끄는 스위치가 아니다 — 빌림 검사도, 타입 검사도 그대로 돕니다. 위의 다섯 가지가 더 허락될 뿐입니다(이 장의 끝에서 확인합니다).

날 포인터는 그냥 따라갈 수 없다 — E0133

날 포인터 *const T · *mut T 는 C 의 포인터와 같습니다. 유효한지, 누가 함께 쓰는지 컴파일러가 모릅니다. 그래서 따라가는 일은 막혀 있습니다.

unsafe 블록 안에서 따라간다

만드는 것은 안전하고, 따라가는 것만 unsafe 입니다. 같은 값을 가리키는 읽기 포인터와 쓰기 포인터를 함께 두는 것 — 참조로는 못 하던 일입니다.

unsafe 함수는 unsafe 안에서만 부른다 — E0133

unsafe fn 은 "부르는 쪽이 지켜야 할 약속이 있다" 는 뜻입니다. 그 약속을 읽고 지키겠다는 표시가 unsafe 블록입니다.

안전한 포장을 씌운다

unsafe 를 쓰는 올바른 모양입니다. 위험한 부분을 작게 가두고, 약속이 지켜지는지 검사하는 안전한 함수로 감쌉니다. 바깥에서는 unsafe 없이 씁니다.

표준 라이브러리가 이렇게 생겼다 — Vec, String, Rc, Mutex 의 속에는 unsafe 가 있습니다. 우리가 쓰는 겉은 안전합니다. 잘못이 있다면 찾아볼 곳이 unsafe 블록으로 좁혀집니다.

C 함수를 부른다

다른 언어로 쓴 함수는 Rust 의 검사를 받지 않았으니 부르는 일이 unsafe 입니다. C 표준 라이브러리의 abs 와 strlen 을 불러 봅니다.

1부에서 본 것 — extern 블록 앞의 unsafe 는 2024 에디션부터 필수입니다 (1부 4장). c"hello" 는 끝에 0 바이트가 붙는 C 문자열 리터럴입니다.

unsafe 안에서도 빌림 검사는 돈다 — E0499

unsafe 블록 안에서 가변 참조를 둘 만들어 봅니다. 평소와 똑같이 막힙니다. 덤으로 "이 unsafe 는 필요 없다" 는 경고까지 받습니다.

퀴즈 — unsafe

Q. unsafe 블록 안에서는 한 값에 &mut 참조를 둘 만들어도 될까요?

A. 안 됩니다. unsafe 는 빌림 검사를 끄지 않습니다 (E0499). 풀리는 것은 날 포인터 따라가기 등 다섯 가지뿐입니다 (다섯 가지).

3장

async 맛보기

async fn 은 퓨처를 돌려준다 · 퓨처는 게으르다 · 가장 작은 실행기 · .await

async fn 을 부르면 아무 일도 일어나지 않는다

async fn 은 부르는 즉시 본문을 돌리지 않습니다. "나중에 돌릴 일" 을 담은 값, 퓨처(future)를 돌려줄 뿐입니다. 아무도 그것을 돌리지 않으면 본문의 println! 은 찍히지 않습니다.

퓨처는 게으르다 — 컴파일러의 말 그대로입니다. "퓨처는 .await 하거나 poll 하지 않으면 아무 일도 하지 않는다".

가장 작은 실행기

퓨처를 돌리는 것이 실행기(executor)입니다. 표준 라이브러리에는 실행기가 없습니다. 원리를 보려고 스무 줄 남짓으로 하나 만듭니다 — 다 됐다고 할 때까지 poll 을 되풀이할 뿐입니다.

세 가지 부품 — poll(한 걸음 진행시키기), Poll::Ready(끝났다는 답), Waker(나중에 다시 불러 달라는 호출 벨 — 여기서는 아무 일도 안 하는 것을 썼습니다).

.await — 다른 퓨처를 기다린다

async 함수 안에서 다른 퓨처 뒤에 .await 를 붙이면, 그것이 끝날 때까지 기다렸다가 값을 받습니다. 보통의 함수 호출처럼 위에서 아래로 읽힙니다.

.await 는 async 안에서만 — E0728

보통 함수에서는 .await 를 쓸 수 없습니다. 기다리는 동안 다른 일에 자리를 내줄 수 있는 것은 async 함수뿐이기 때문입니다.

그래서 맨 바깥에는 실행기가 있다 — 보통 함수와 async 세계의 경계에서 block_on 같은 것이 퓨처를 받아 돌립니다.

async 블록

async { … } 는 그 자리에서 퓨처를 만듭니다. 클로저처럼 주변 변수를 붙잡습니다. 이것도 돌리기 전에는 아무 일도 하지 않습니다.

그래서 실제로는 무엇을 쓰나

우리의 block_on 은 퓨처가 "아직" 이라고 답하면 쉬지 않고 다시 묻습니다. 진짜 실행기는 그동안 다른 퓨처를 돌리고, 네트워크나 타이머가 준비되면 Waker 로 깨움을 받습니다.

언어·표준 라이브러리가 주는 것바깥 크레이트가 주는 것
async fn · .await · Future 트레이트실행기(런타임)
Waker · Context · Pin비동기 소켓·파일·타이머
여러 퓨처를 함께 돌리는 도구
1부에서 본 선택 — Rust 는 녹색 스레드와 런타임을 언어에서 걷어 냈습니다. 그 자리에 "런타임을 라이브러리로 고른다" 가 들어왔습니다(1부). 그래서 async 를 실제로 쓰려면 런타임 크레이트를 하나 골라야 하고, 이 책은 표준 라이브러리만 쓰므로 여기까지만 봅니다.

퀴즈 — async

Q. async fn fetch() -> u32 를 fetch(); 라고만 부르면 본문은 실행될까요?

A. 실행되지 않습니다. fetch() 는 퓨처를 만들 뿐이고, 누군가 그것을 .await 하거나 실행기에 넘겨 poll 해야 본문이 돕니다 (아무 일도 일어나지 않는다). 컴파일러도 쓰지 않은 퓨처를 경고합니다.

4장

그 밖의 문법

타입 별명 · 날 식별자 · 이름표 붙은 블록 · const 블록 · _ 와 _이름

type — 타입에 별명 붙이기

길거나 자주 쓰는 타입에 이름을 붙입니다. 새 타입을 만드는 것이 아니라 같은 타입의 다른 이름입니다. 오류 타입을 고정한 Result<T> 별명은 표준 라이브러리에서도 흔히 봅니다.

r# — 키워드를 이름으로 쓰기

키워드와 글자가 같은 이름이 꼭 필요할 때 r# 를 앞에 붙입니다. 에디션이 바뀌어 키워드가 된 옛 이름을 부를 때 쓰입니다(1부의 r#try, r#gen).

이름표 붙은 블록

반복문에 붙이던 이름표(4부)를 보통 블록에도 붙일 수 있습니다. break 로 값을 들고 블록 밖으로 나옵니다. 함수를 따로 만들지 않고 "일찍 빠져나오기" 를 씁니다.

const { } — 컴파일할 때 계산되는 식

식 하나를 const { } 로 감싸면 컴파일하는 동안 계산됩니다. 이름 붙은 상수를 따로 만들지 않아도 됩니다.

_ 와 _이름 은 다르다

둘 다 "안 쓴다" 는 표시지만 뜻이 다릅니다. _이름 은 변수라서 범위 끝까지 값을 붙들고, _ 는 아무것도 붙들지 않아 값이 그 자리에서 정리됩니다.

잠금에서 실수하기 쉽다 — let _ = mutex.lock(); 은 잠그자마자 풉니다. 범위 끝까지 잠가 두려면 let _guard = … 처럼 이름을 줘야 합니다(15부).

퀴즈 — 그 밖의 문법

Q. let _ = Noisy("a"); 와 let _b = Noisy("b"); 가운데 어느 쪽이 먼저 정리될까요?

A. _ 쪽입니다. 그 줄에서 곧바로 정리됩니다. _b 는 이름이 있는 변수라 범위가 끝날 때 정리됩니다(_ 와 _이름).
