이 부에서 할 일

기초 문법은 15부까지로 한 바퀴 돌았습니다. 이 부는 남의 코드를 읽다 보면 만나는 세 가지와, 앞에서 자리를 찾지 못한 문법 몇 가지를 "무엇인지 알아볼 수 있을 만큼" 봅니다. 깊이 들어가지 않습니다.

  • 1장 — 매크로: println! 과 vec! 은 어떻게 만들어졌나

1장

매크로

macro_rules! · 갈래 여럿 · 반복 · 이름 받기 · 위생 · 맞는 갈래가 없을 때 · 표준 매크로 · derive

macro_rules! — 코드를 만들어 내는 코드

2부에서 println! 끝의 ! 는 함수가 아니라 매크로라는 표시라고만 하고 넘어왔습니다. 매크로는 컴파일의 앞 단계에서, 타입 검사보다 먼저 코드를 다른 코드로 펼칩니다. macro_rules! 로 "이런 모양이 오면 → 이런 코드로" 를 적어 만들고, 부를 때는 이름 뒤에 ! 를 붙입니다.

이 장을 마치면 — 작은 macro_rules! 를 읽고 쓸 수 있습니다. derive 같은 절차적 매크로는 무엇인지만 보고, 만드는 법은 다루지 않습니다.
함수와 다른 점 — 타입을 적지 않았습니다. square!(7) 은 7 * 7 로, square!(1.5) 는 1.5 * 1.5 로 펼쳐진 뒤에 타입 검사를 받습니다.

갈래를 여럿 둔다

match 처럼 패턴을 여럿 적을 수 있습니다. 5부에서 이름이 같은 함수 area 를 둘 만들지 못했는데, 매크로로는 "인자 개수에 따라 다른 일" 이 됩니다.

읽는 법 — area!(3) 은 첫 갈래에 맞아 3 * 3 인 9 가 되고, area!(3, 4) 는 쉼표가 있는 둘째 갈래에 맞아 12 가 됩니다.

몇 개든 받는다 — $( … ),*

$( … ),* 는 "쉼표로 나뉜 이것이 0번 이상" 입니다. 펼치는 쪽에서도 같은 표기로 받은 만큼 되풀이합니다. println! 과 vec! 이 인자를 몇 개든 받는 비결입니다.

읽는 법 — 인자가 없으면 되풀이할 것이 없어 0 만 남습니다. 셋이면 6, 다섯이면 150 입니다. 펼치는 쪽의 $(+ $x)* 가 받은 식마다 + 식 을 하나씩 찍어 냅니다.

vec! 처럼 쓰는 map! 을 만든다

8부에서는 맵을 insert 를 한 줄씩 적어 채웠습니다. 반복을 쓰면 키 => 값 을 나열하는 것만으로 맵을 만드는 매크로가 됩니다 — 7번 줄이 받은 짝마다 insert 를 찍어 냅니다. 패턴에 적은 => 는 부르는 쪽이 그대로 적어야 하는 글자입니다. 문법을 새로 지어낸 셈입니다.

$(,)? 는 "쉼표가 있어도 없어도" 입니다. 마지막 항목 뒤의 쉼표를 허락합니다. 바깥의 겹 중괄호 {{ … }} 는 펼친 결과를 블록 하나로 만들어 값으로 쓰게 합니다.

이름을 받아 함수를 찍어 낸다

받는 것의 종류를 : 뒤에 적습니다. expr 은 식, ident 는 이름입니다. 이름을 받으면 그 이름으로 함수나 타입을 만들어 낼 수 있습니다.

종류받는 것종류받는 것
expr식ty타입
ident이름literal리터럴
pat패턴tt토큰 한 덩이(무엇이든)

패턴의 $이름: 뒤에 적는 종류 가운데 여섯입니다. 이 장의 예제는 expr 과 ident 만 쓰고, ty 는 부록의 타입의 크기에서 씁니다.

매크로 안의 지역 변수는 바깥과 섞이지 않는다

매크로가 안에서 let 으로 만든 tmp 와 부른 쪽의 tmp 는 글자가 같아도 다른 변수입니다. 이것을 위생(hygiene)이라고 합니다.

22 가 나온 까닭 — 넘긴 식 tmp + 1 의 tmp 는 바깥의 10 으로 읽혀 (10 + 1) * 2 가 됐습니다. 글자만 바꿔 끼우는 매크로였다면 매크로 안의 tmp(2)가 대신 잡혔을 것입니다. 변수에만 해당합니다 — 앞 슬라이드처럼 매크로가 만든 함수는 바깥에서 그대로 보입니다.

맞는 갈래가 없으면

어느 패턴에도 맞지 않게 부르면 컴파일 오류입니다. 메시지는 매크로의 어느 자리에서 막혔는지 알려 줍니다. 이 장 첫 슬라이드의 square! 에 인자를 둘 줘 봅니다.

  • 오류 첫 줄 — "어느 규칙도 , 를 기대하지 않았다". 2부의 세미콜론 오류처럼 번호(E…)가 붙지 않습니다. 화살표는 8번 줄의 쉼표를 가리키고, 1번 줄에 붙은 말은 "이 매크로를 부르던 중" 입니다.
  • note: — 2번 줄의 $x:expr 를 맞추던 중이었다고 말합니다. 식 하나(3)는 받았는데 그 뒤에 쉼표가 올 자리가 패턴에 없습니다.
  • 고치기 — square!(3) 처럼 패턴대로 부르거나, 인자 둘을 받는 갈래를 더합니다 (갈래를 여럿 둔다).

표준 매크로 몇 가지

함수로는 할 수 없는 일을 하는 매크로들입니다. 식을 글자로 바꾸거나, 소스의 자리를 알려 주거나, 컴파일 조건을 값으로 줍니다.

  • stringify! 는 식을 계산하지 않고 적힌 글자 그대로 문자열로 만듭니다 — 출력의 x * 2 + 1 이 그것이고, 그 오른쪽 7 은 같은 식을 계산한 값입니다.
  • line! 은 자기가 적힌 줄 번호입니다. 8번 줄에 적었으니 8 입니다.
  • cfg!(debug_assertions) 가 true 인 것은 이 컴파일에서 그 설정이 켜져 있었다는 뜻입니다. 2부의 빌드 표에서 디버그는 true, 릴리스는 false 이던 값이고, 13부의 #[cfg] 와 같은 조건을 bool 로 받습니다.
이미 써 온 것 — format! · dbg! · vec! · matches! · panic! · assert! · todo! · write! 도 println! 처럼 모두 매크로입니다.

derive 도 매크로다

10부에서 #[derive(Debug)] 가 만드는 것은 impl Debug for Point 라고 했습니다. 구조체 정의를 읽고 그 구현을 대신 써 주는 것이 매크로입니다. 아래 2번 줄은 derive 할 수 있는 것들 가운데 셋을 한꺼번에 만듭니다. 라이브러리도 자기 트레이트에 쓸 derive 를 만들 수 있는데, 그 방법이 절차적 매크로(procedural macro)입니다.

종류모양만드는 법
선언적 매크로name!(…)macro_rules! — 이 장
derive 매크로 #[derive(Name)]절차적 매크로 — 토큰을 받아 토큰을 돌려주는 Rust 함수를 전용 크레이트에 쓴다
속성 매크로 #[name]〃
함수 모양 매크로 name!(…)〃 (부르는 모양은 선언적 매크로와 같다)

매크로의 네 종류를 부르는 모양과 만드는 법으로 가른 표입니다. 배지는 직접 만들 수 있게 된 버전입니다. 절차적 매크로를 만드는 일은 이 책에서 다루지 않습니다.

퀴즈 — 매크로

Q. println! 은 왜 함수가 아니라 매크로일까요?

A. Rust 의 함수는 인자의 개수와 타입이 정해져 있습니다(5부의 E0061). 인자를 몇 개든, 어떤 타입이든 받으려면 매크로여야 합니다(몇 개든 받는다). {} 로 찍을 수 없는 값을 컴파일할 때 잡아 주던 것도(2부의 E0277) 매크로가 서식 문자열을 컴파일 도중에 읽기 때문입니다.

2장

unsafe

풀리는 다섯 가지 · 날 포인터 · unsafe fn · 안전한 포장 · C 함수 부르기 · 그래도 도는 빌림 검사

unsafe 가 풀어 주는 것은 다섯 가지뿐이다

컴파일러가 안전하다고 증명하지 못하지만 실제로는 괜찮은 코드가 있습니다. unsafe 는 "이 부분은 내가 보증한다" 는 표시입니다. 그 표시가 있어야만 할 수 있는 일을 공식 입문서 The Rust Programming Language 는 다섯 가지로 꼽습니다.

  1. 날 포인터(raw pointer)를 따라가기
  2. unsafe 함수와 메서드를 부르기
  3. 바뀔 수 있는 전역 변수(static mut)를 읽거나 고치기
  4. unsafe 트레이트를 구현하기
  5. union 의 필드를 읽기
이 장을 마치면 — 남의 코드에서 unsafe 블록과 unsafe fn 을 만났을 때 무엇을 하는 자리인지 읽을 수 있습니다. 해 보는 것은 1번과 2번뿐입니다. static mut, unsafe 트레이트, union(C 의 공용체)은 이 책에서 다루지 않습니다.
끄는 스위치가 아니다 — 빌림 검사는 그대로 돕니다. 위의 다섯 가지가 더 허락될 뿐입니다(이 장의 끝에서 확인합니다).

날 포인터는 unsafe 밖에서 따라갈 수 없다 — E0133

날 포인터 *const T · *mut T 는 C 의 포인터와 같습니다. 참조와 달리 유효한지, 누가 함께 쓰는지 컴파일러가 모릅니다. 그래서 6부에서 참조에 쓰던 * 로 따라가는 일이 막혀 있습니다. 3번 줄의 &raw const n 이 n 을 가리키는 날 포인터를 만드는 식입니다.

  • 오류 첫 줄 — "날 포인터를 따라가는 것은 unsafe 이고 unsafe 블록이 필요하다". 밑줄은 4번 줄의 *p 입니다. 포인터를 만든 3번 줄은 탓하지 않습니다. 번호는 1부의 set_var 에서 본 E0133 이고, 이번에는 까닭이 날 포인터입니다.
  • note: — 까닭입니다. 날 포인터는 널(null)이거나, 사라진 값을 가리키거나(dangling), 정렬이 어긋나 있을 수 있고, 별칭 규칙을 어기거나 데이터 경쟁을 일으킬 수 있다고 합니다. 그 모두가 "정의되지 않은 동작(undefined behavior)" 입니다. 무슨 일이 벌어질지 언어가 아무것도 약속하지 않는 상태를 말합니다.

unsafe 블록 안에서 따라간다

앞 슬라이드의 오류가 요구한 대로 unsafe 블록 안에서 따라갑니다. 만드는 것은 안전하고, 따라가는 것만 unsafe 입니다. 이번 예제는 같은 값을 가리키는 쓰기 포인터와 읽기 포인터를 함께 둡니다. 6부의 불변 참조 여럿, 아니면 가변 참조 하나 때문에 참조로는 못 하던 일입니다.

읽는 법 — 포인터를 만드는 4·6번 줄은 unsafe 밖에 있는데도 컴파일됩니다. *writer += 1 로 고친 값 6 을 *reader 로 읽었습니다. 두 포인터가 가리키는 n 이 그동안 살아 있다는 것은 컴파일러가 아니라 쓴 사람이 보증합니다.

unsafe 함수는 unsafe 안에서만 부른다 — E0133

unsafe fn 은 "부르는 쪽이 지켜야 할 약속이 있다" 는 뜻입니다. 그 약속을 읽고 지키겠다는 표시가 unsafe 블록입니다. 예제의 get_unchecked 는 범위 검사 없이 칸을 꺼내는 표준 라이브러리의 unsafe 메서드입니다.

  • 오류 첫 줄 — "unsafe 함수 get_fast 를 부르는 것은 unsafe 이고 unsafe 블록이 필요하다". 밑줄은 7번 줄의 호출 전체입니다. 번호는 날 포인터 때와 같은 E0133 이고, 문장은 1부의 set_var 때와 함수 이름만 다릅니다.
  • note: — "정의되지 않은 동작을 피하는 법은 그 함수의 문서를 보라". 약속이 무엇인지는 함수마다 달라서 컴파일러가 대신 말해 줄 수 없습니다.
  • 2번 줄은 오류가 아닙니다. unsafe fn 의 본문에서도 unsafe 한 일은 unsafe 블록으로 감싸 적었습니다. 고친 모양은 다음 슬라이드에 있습니다.

안전한 포장을 씌운다

unsafe 를 쓰는 올바른 모양입니다. 위험한 부분을 작게 가두고, 약속이 지켜지는지 검사하는 안전한 함수로 감쌉니다. 바깥에서는 unsafe 없이 씁니다.

읽는 법 — 1번 칸은 범위 안이라 get_fast 까지 가서 20 을, 9번 칸은 검사에 걸려 0 을 받았습니다. 1·2번 줄의 # Safety 는 부르는 쪽이 지킬 약속을 적는 문서 주석의 관례입니다.
표준 라이브러리도 이 모양을 쓴다 — 6부에서 쓴 split_at_mut 이 그랬습니다. 속은 unsafe 로 쓰고 겉은 안전한 함수로 내놓습니다. 그러면 잘못이 있을 때 찾아볼 곳이 unsafe 블록으로 좁혀집니다.

C 함수를 부른다

다른 언어로 쓴 함수는 Rust 의 검사를 받지 않았으니 부르는 일이 unsafe 입니다. C 표준 라이브러리의 abs(절댓값)와 strlen(문자열 길이)을 불러 봅니다.

  • 선언 — 4번부터 7번 줄까지는 본문 없이 이름과 타입만 적습니다. 이 선언이 C 쪽 함수와 맞는지는 적은 사람이 책임지고, 블록 앞의 unsafe 가 그 표시입니다. c_int · c_char 는 C 의 int · char 에 맞춘 타입 이름입니다.
  • 호출 — 12번 줄에서 unsafe 블록 안에 불렀고, 왜 괜찮은지를 바로 위 주석에 적었습니다. 출력 7 은 abs(-7), 5 는 "hello" 의 길이입니다.
1부에서 본 것 — extern 블록 앞의 unsafe 는 2024 에디션부터 필수입니다. c"hello" 는 끝에 0 바이트가 붙는 C 문자열 리터럴입니다.

unsafe 안에서도 빌림 검사는 돈다 — E0499

unsafe 블록 안에서 가변 참조를 둘 만들어 봅니다. 평소와 똑같이 막힙니다. 덤으로 "이 unsafe 는 필요 없다" 는 경고까지 받습니다.

  • 경고 — 3번 줄의 unsafe 가 "필요 없는 unsafe 블록" 이라고 합니다. 안에서 다섯 가지 가운데 어느 것도 하지 않았기 때문입니다.
  • 오류 — 6부의 가변 참조는 한 번에 하나뿐이다에서 본 E0499 그대로입니다. 4번 줄이 첫 가변 빌림, 5번 줄이 둘째 가변 빌림이고, 6번 줄에서 첫 빌림을 다시 쓴다고 짚습니다.
  • 고치기 — error: aborting 줄이 "오류 1건, 경고 1건" 으로 컴파일이 멈췄다고 알립니다. 고치는 법도 6부와 같습니다 — 한 번에 하나만 빌립니다.

퀴즈 — unsafe

Q. unsafe 블록 안에서는 한 값에 &mut 참조를 둘 만들어도 될까요?

A. 안 됩니다. unsafe 는 빌림 검사를 끄지 않습니다 (E0499). 풀리는 것은 날 포인터 따라가기 등 다섯 가지뿐입니다 (다섯 가지).

async fn 을 부르면 아무 일도 일어나지 않는다

15부에서는 따로 도는 일마다 운영 체제의 스레드를 만들었습니다. async 는 다른 길로, 1부에서 본 대로 잠시 멈췄다가 멈춘 곳에서 다시 이어 가는 함수를 쓰는 문법입니다. 그런데 async fn 은 부르는 즉시 본문을 돌리지 않습니다. "나중에 돌릴 일" 을 담은 값, 퓨처(future)를 돌려줄 뿐입니다.

이 장을 마치면 — async fn 과 .await 가 든 코드를 읽고, 퓨처를 돌리는 실행기가 왜 필요한지 압니다. 소켓이나 타이머처럼 실제로 기다리는 일은 런타임 크레이트가 있어야 해서 해 보지 않습니다.
퓨처는 게으르다 — 경고의 첫 note: 그대로입니다. "퓨처는 .await 하거나 poll 하지 않으면 아무 일도 하지 않는다". 경고는 7번 줄에서 만든 퓨처를 아무도 쓰지 않았다는 것이고, 실행 결과에는 "끝" 한 줄뿐입니다. 12부의 게으른 반복자가 받은 것과 같은 꼴의 경고입니다 — 거기서 소비자가 당겨야 돌았듯, 퓨처는 .await 나 poll 이 돌립니다. 둘은 다음 두 슬라이드에서 봅니다.

가장 작은 실행기

퓨처를 돌리는 것이 실행기(executor)입니다. 표준 라이브러리는 실행기를 주지 않으므로, 원리를 보려고 열 줄짜리 함수(6번부터 15번 줄까지)로 하나 만듭니다 — 다 됐다고 할 때까지 poll 을 되풀이할 뿐입니다.

이미 써 온 것 — 6번 줄의 F: Future 는 10부의 트레이트 바운드이고, 반환 타입 F::Output 은 연관 타입입니다. 12번 줄이 돌려주는, 퓨처가 끝나며 낸 값의 타입입니다.
세 가지 부품 — poll(한 걸음 진행시키기), Poll::Ready(끝났다는 답), Waker(나중에 다시 불러 달라는 호출 벨 — 여기서는 아무 일도 안 하는 Waker::noop() 을 썼습니다). pin! 은 퓨처를 한자리에 고정합니다. poll 이 그것을 요구하는데, 까닭은 이 책에서 다루지 않습니다.

출력의 순서를 봅니다. "퓨처를 만들었다" 가 먼저이고, block_on 에 넘긴 뒤에야 "fetch 가 돈다" 가 찍힙니다.

.await 는 async 안에서만 — E0728

보통 함수에서는 .await 를 쓸 수 없습니다. .await 는 "여기서 멈췄다가 나중에 이어서 돈다" 는 뜻인데, 그렇게 멈출 수 있는 것은 퓨처가 되는 async 코드뿐이기 때문입니다.

  • 오류 첫 줄 — "await 는 async 함수와 블록 안에서만 허락된다". 밑줄은 6번 줄의 .await 입니다. async 블록은 다음 슬라이드에서 봅니다.
  • 5번 줄 — fn main() 에 "이것은 async 가 아니다" 라는 말이 붙었습니다.
  • 고치기 — 보통 함수와 async 세계의 경계에는 실행기를 둡니다. 앞 슬라이드의 main 처럼 block_on 같은 것이 퓨처를 받아 돌립니다.

async 블록 — 그 자리에서 만드는 퓨처

async { … } 는 그 자리에서 퓨처를 만듭니다. 12부의 클로저처럼 주변 변수를 붙잡습니다. 이것도 돌리기 전에는 아무 일도 하지 않습니다.

읽는 법 — 블록은 18번 줄에서 만들었지만 "아직 안 돌았다" 가 먼저 찍힙니다. 23번 줄에서 block_on 에 넘기자 "블록이 돈다" 가 나오고, 블록이 붙잡아 둔 name 으로 만든 인사말이 결과가 됩니다.

그래서 실제로는 무엇을 쓰나

우리의 block_on 은 loop 뿐이어서, 퓨처가 "아직"(Poll::Pending)이라고 답하면 쉬지 않고 다시 묻게 됩니다(가장 작은 실행기). 실제로 쓰는 실행기는 그동안 다른 퓨처를 돌리고, 기다리던 일이 준비되면 Waker 로 깨움을 받아 그 퓨처를 다시 poll 합니다.

여러 퓨처를 함께 돌리는 도구

어디까지가 표준 라이브러리이고 어디부터 런타임 크레이트인지 가른 표입니다. 이 장의 예제는 왼쪽 칸만 썼습니다.

1부에서 본 것 — Rust 는 1.0 을 앞두고 런타임을 표준 라이브러리에서 떼어 냈고 (1부 2장), async 발표문이 꼽은 런타임도 바깥 프로젝트들이었습니다 (1부 5장). 그래서 async 를 실제로 쓰려면 런타임 크레이트를 하나 골라야 하고, 이 책은 표준 라이브러리만 쓰므로 여기까지만 봅니다.

퀴즈 — async

Q. async fn fetch() -> u32 를 fetch(); 라고만 부르면 본문은 실행될까요?

A. 실행되지 않습니다. fetch() 는 퓨처를 만들 뿐이고, 누군가 그것을 .await 하거나 실행기에 넘겨 poll 해야 본문이 돕니다 (아무 일도 일어나지 않는다). 컴파일러도 쓰지 않은 퓨처를 경고합니다.

그 밖의 문법

타입 별명 · 날 식별자 · 이름표 붙은 블록 · const 블록 · _ 와 _이름

type — 타입에 별명 붙이기

9부의 Result<f64, Box<dyn Error>> 처럼 길거나 자주 쓰는 타입에 이름을 붙입니다. 10부의 한 겹 감싸기와 달리 새 타입을 만드는 것이 아니라 같은 타입의 다른 이름입니다. 오류 타입을 고정한 Result<T> 별명도 흔합니다 — 9부에서 Display 를 구현할 때 적던 fmt::Result 가 표준 라이브러리의 그런 별명입니다.

이 장을 마치면 — 남의 코드에서 type · r# · 이름표 붙은 블록 · const { } · let _ 를 만났을 때 뜻을 압니다. 다섯은 서로 이어지지 않으니 필요한 것만 골라 읽어도 됩니다. 문법마다 슬라이드 하나씩만 봅니다.
읽는 법 — 16번 줄의 Scores::new() 는 BTreeMap::new() 와 같은 호출입니다. 별명일 뿐이라 원래 타입의 함수와 메서드를 그대로 씁니다. 출력은 kim 의 최고점 Ok(95) 와, 없는 이름 lee 의 Err 입니다.

r# — 키워드를 이름으로 쓰기

키워드와 글자가 같은 이름이 꼭 필요할 때 r# 를 앞에 붙입니다. 날 식별자(raw identifier)라고 합니다. 에디션이 바뀌어 키워드가 된 옛 이름을 부를 때 쓰입니다 — 컴파일러의 help: 가 권하던 1부의 r#try · r#gen, 2부의 r#async 가 이것입니다.

이름표 붙은 블록

4부에서 반복문에 붙이던 이름표를 보통 블록에도 붙일 수 있습니다. loop 에서 하던 것처럼 break 로 값을 들고 블록 밖으로 나옵니다. 함수를 따로 만들지 않고 "일찍 빠져나오기" 를 씁니다.

const { } — 컴파일할 때 계산되는 식

식 하나를 const { } 로 감싸면 컴파일하는 동안 계산됩니다. 3부의 const 처럼 이름 붙은 상수를 따로 만들지 않아도 됩니다.

_ 와 _이름 은 다르다

둘 다 "안 쓴다" 는 표시지만 뜻이 다릅니다. _이름 은 변수라서 스코프 끝까지 값을 붙들고, _ 는 아무것도 붙들지 않아 값이 그 자리에서 정리됩니다. 그때를 보려고 14부의 Drop 으로 정리될 때 한 줄을 찍게 했습니다.

읽는 법 — _ 에 준 값은 11번 줄에서 곧바로 정리되어 "main 끝" 보다 먼저 찍히고, _kept 는 main 이 끝날 때 정리됩니다.
잠금에서 실수하기 쉽다 — lock() 이 주는 열쇠도 값이라 같은 규칙을 따릅니다. 15부에서 본 대로 열쇠가 사라지면 잠금이 풀리므로, let _ = m.lock(); 이라고 쓰면 그 줄에서 바로 풀리게 됩니다. 스코프 끝까지 잠가 두려면 let _guard = … 처럼 이름을 줍니다.
본문을 마치며 — 15부까지의 문법으로 표준 라이브러리만 쓰는 프로그램을 읽고, 컴파일러의 메시지를 따라 고쳐 가며 쓸 수 있습니다. 이 부의 매크로 · unsafe · async 는 만났을 때 무엇인지 알아볼 수 있습니다. 17부부터는 이 문법으로 표준 라이브러리를 씁니다. 첫 차례는 입출력과 파일입니다. 뒤의 부록은 찾아보는 곳입니다 — 낱말은 용어집, 다시 만난 오류 번호는 오류 번호 찾아보기, 연산자와 서식은 표에서 찾습니다.

퀴즈 — 그 밖의 문법
