얼마나 기다릴지, 한도가 얼마인지, 얼마나 걸렸는지는 모두 시간의 길이입니다. 그것을 u64 하나에 담으면 그 수가 초인지 밀리초인지는 변수 이름에만 남습니다. std::time::Duration 은 시간의 길이(duration) 하나를 담는 타입입니다. 단위는 만들 때와 꺼낼 때 함수 이름으로 고릅니다.

Instant — 순간 둘을 견주고, 그 사이의 길이를 얻는다

일이 얼마나 걸렸는지 알려면 시작과 끝, 두 순간이 있어야 합니다. Instant::now() 는 지금 이 순간(instant)을 적어 둔 값을 줍니다. 표준 라이브러리 문서는 Instant 를 서로 견주는 데만 쓰는 값이라고 하고, 거기서 초 수를 꺼내는 메서드는 없다고 적습니다. 날짜나 시각으로 찍을 수 있는 값이 아닙니다. 아래에서 쓰는 thread::sleep 은 지금 도는 스레드를 주어진 길이만큼 재웁니다.

읽는 법 — 13번 줄에서 먼저 적은 start 가 end 보다 작습니다. 15번 줄의 duration_since 는 두 순간의 차이를 Duration 으로 줬고, 17번 줄의 end - start 도 같은 값입니다. 20번 줄처럼 순간에 길이를 더하면 다시 Instant 입니다. 24번 줄의 elapsed 는 start 부터 지금까지의 길이입니다. 27번 줄은 앞뒤를 바꿔 뺐는데 패닉하지 않고 0ns 를 냈습니다( 부터). 28번 줄의 checked_duration_since 는 같은 경우에 None 입니다.
true 만 찍은 까닭 — 걸린 시간은 실행마다 다릅니다. 문서는 sleep 이 주어진 길이보다 짧게 자는 일은 없고 더 길게 잘 수는 있다고 적습니다. 그리고 Instant 는 플랫폼의 버그가 없는 한 앞서 잰 순간보다 앞서지 않는다고 적습니다. 이 화면의 다섯 true 는 그 두 약속에서 따라 나오는 것입니다. "25 밀리초 안에 깼다" 같은 위쪽 한도는 약속된 것이 아니라서 찍지 않았습니다.

SystemTime — 지금 시각은 기준 시각부터의 길이로 받는다

파일에 적을 날짜나 기록의 시각처럼 달력과 이어지는 값은 Instant 로 얻을 수 없었습니다. SystemTime::now() 가 운영 체제의 시계가 가리키는 지금 시각을 줍니다. 수로 바꾸려면 기준 시각(epoch)인 UNIX_EPOCH 와의 차이를 구합니다. 문서는 이 상수가 모든 시스템에서 1970년 1월 1일 0시(UTC)라고 적습니다. duration_since 는 Result 를 돌려줍니다.

읽는 법 — 15번 줄의 is_ok 는 true 입니다. 초 수는 실행마다 달라서 찍지 않고, 18번 줄에서 17 억 초(2023년 11월 14일)보다 큰지만 봤습니다. 21번 줄처럼 앞뒤를 바꾸면 Err 입니다. 26번 줄은 기준 시각에 사흘을 더해 시각을 만들었습니다. 4번 줄의 gap 은 Ok 와 Err 를 갈라 글로 만듭니다. 27번 줄은 Ok 갈래로 가서 259200s 뒤 입니다. 앞뒤를 바꾼 28번 줄은 Err 갈래로 갔고, 그 안의 값의 duration() 이 뒤집힌 차이 259200s 를 줬습니다. {e} 가 찍은 글은 "둘째 시각이 더 뒤다" 라는 뜻입니다.
시계에 기댄 줄 — 15번 · 18번 · 22번 · 29번 줄의 true 는 소스가 아니라 이 기계의 시계가 정합니다. 시계가 2023년 11월 14일 뒤를 가리키고 있어서 넷 다 true 입니다. 문서는 SystemTime 이 Instant 와 달리 뒤로 갈 수 있다고, 곧 나중에 잰 시각이 먼저 잰 시각보다 앞설 수 있다고 적습니다. 그래서 걸린 시간은 Instant 로 재고, SystemTime 은 날짜와 시각이 필요한 곳에만 씁니다.

고르는 법 — 값을 글로 읽어 쓸 것이면 var 를 부르고 NotUnicode 를 오류로 다룹니다. 파일 이름처럼 경로로 넘길 값이면 var_os 로 받아 그대로 넘깁니다.

env::vars — 전부를 돌되, 내가 정한 것만 골라 정렬해서 찍는다

설정이 여럿이면 이름의 앞머리를 APP_ 로 맞춰 두고 한꺼번에 모을 수 있습니다. env::vars() 는 이름과 값의 짝을 내는 반복자입니다. 12부의 filter 로 거르고 collect 로 벡터에 모읍니다.

읽는 법 — 첫 실행에서는 고른 것이 0 개입니다. 이 기계의 환경에는 APP_ 로 시작하는 변수가 없습니다. 둘째 실행의 명령에는 ZONE · DEBUG · COLOR 순서로 적었는데, 9번 줄의 sort 뒤라서 이름순으로 찍혔습니다. APP_COLOR= 는 빈 값 "" 로 들어 있습니다. 16번 줄은 두 실행 모두 true 입니다. 이 예제가 정하지 않은 변수도 환경에 들어 있습니다.
전부를 찍지 않는다 — 고르지 않은 변수는 기계마다 다르고, 이 책의 화면에 실을 것이 아닙니다. 그래서 수만 견줬습니다. vars 가 내는 순서에 기대지 않으려고 정렬한 뒤에 찍었습니다. 문서는 이름이나 값이 유니코드가 아닌 변수를 만나면 vars 의 반복자가 패닉한다고 적습니다. 그런 값까지 돌아야 하면 OsString 짝을 내는 vars_os 를 쓰라고 합니다.

Command 로 다른 프로그램을 돌린다 — status 는 끝나기를 기다려 종료 상태를 준다

돌고 있는 프로그램 하나를 프로세스(process)라고 합니다. std::process::Command 는 다른 프로그램을 새 프로세스로 띄웁니다. 띄운 쪽이 부모, 띄워진 쪽이 자식 프로세스(child process)입니다. 자식으로 쓸 프로그램 job 을 먼저 만듭니다. 인자로 받은 수를 17부의 ExitCode 로 돌려주는 것이 전부입니다.

읽는 법 — 셸에서 직접 돌린 ./job 3 은 한 줄을 찍고 종료 코드 3 으로 끝났습니다. boss 의 8번 줄에서 Command::new 가 프로그램을, arg 가 인자 하나를 정하고, status() 가 돌립니다. 돌려받은 종료 상태(exit status)의 success() 는 코드 0 에 true, 3 에 false 입니다. code() 는 Some(0) 과 Some(3) 입니다. Option 에 담겨 오는 까닭은 돌리지 못한 것과 실패로 끝난 것에서 None 이 나오는 화면으로 봅니다.
자식의 줄이 사이에 낀 까닭 — 문서는 status 로 띄운 자식이 부모의 표준 입력 · 출력 · 오류를 물려받는다고 적습니다. 그래서 job 의 줄이 화면에 바로 나왔습니다. boss 의 6번 줄은 줄이 끝나서 이미 나간 뒤이고, 9번 줄은 8번 줄이 자식을 다 기다린 뒤에야 찍습니다. 순서가 늘 같습니다.

output 은 자식의 출력을 화면 대신 바이트로 모아 준다

자식이 낸 결과를 부모가 받아 써야 하면 status 로는 안 됩니다. 결과가 화면으로 가 버리기 때문입니다. output() 은 자식의 표준 출력과 표준 오류를 따로 모아, 종료 상태와 함께 돌려줍니다. 자식 report 는 결과 42 를 표준 출력에, 알림 한 줄을 표준 오류에 찍습니다.

읽는 법 — 자식이 직접 찍은 줄은 화면에 없습니다. 8번 줄이 찍은 stdout 은 Vec<u8> 이고, [52, 50, 10] 은 글자 4 와 2, 그리고 17부에서 본 줄바꿈 10 입니다. 표준 오류로 간 41 바이트는 stderr 에 따로 들어 있습니다. 12번 줄은 8부의 String::from_utf8 로 바이트를 글로 바꿨고, 14번 줄이 trim 하고 parse 해서 15번 줄이 43 을 찍었습니다. 자식의 알림은 19번 줄에서 부모가 찍기로 해서 나온 것입니다.
status 는 흘려보내고, output 은 모은다 — 자식의 글을 사람이 그대로 보면 되는 일에는 status, 프로그램이 받아 써야 하는 일에는 output 입니다.

돌리지 못한 것과 실패로 끝난 것은 다르다 — Err 와, Ok 안의 종료 상태

status() 와 output() 이 Ok 를 돌려줬다는 것은 자식이 돌았다는 뜻일 뿐입니다. 잘못될 수 있는 곳은 둘입니다. 프로그램을 띄우지 못하면 Err 이고, 그 안에는 17부에서 본 io::Error 가 들어 있습니다. 띄웠는데 자식이 실패로 끝나면 Ok 이고, 그 사실은 종료 상태에 들어 있습니다. echo 와 sh 는 이 책을 만든 기계에 있는 프로그램입니다.

읽는 법 — 18번 줄의 echo 는 8번 줄의 갈래로 갔습니다. output 으로 돌렸으므로 echo 가 찍은 글은 화면에 없습니다. 19번 줄의 sh -c "exit 3" 은 돌기는 했으므로 Ok 이고, 9번 줄이 코드 Some(3) 을 찍었습니다. 21번 줄의 kill -9 $$ 는 이 기계의 sh 에서 셸이 자기 자신을 신호(signal)로 죽이는 명령입니다. 같은 9번 줄이 이번에는 None 을 찍었습니다. 문서는 신호로 끝난 프로세스에 code() 가 None 을 준다고 적고, 이 기계에서 그렇게 나왔습니다. 22번 줄의 없는 프로그램은 10번 줄의 가드에 걸린 NotFound 입니다. 26번 줄은 방금 쓴 글 파일을 돌리려 했고, 13번 줄이 찍은 종류는 이 기계에서 PermissionDenied 입니다.
? 하나로는 반만 본다 — status()? 의 ? 가 올려 보내는 것은 돌리지 못한 경우뿐입니다. 자식이 실패로 끝났는지는 success() 나 code() 로 따로 봐야 합니다. status 와 output 의 예제도 ? 뒤에 code() 를 따로 찍었습니다.

인자는 낱낱이 건넨다 — 셸이 하던 쪼개기와 별표 풀기는 없다

이 기계의 셸에 ./show 새 메모.txt 라고 치면 셸이 빈칸에서 쪼개 인자 둘을 만듭니다. Command 는 셸을 거치지 않습니다. 문서는 arg 에 준 글이 그대로 프로그램에 가고, 따옴표 · 낱말 쪼개기 · 별표 풀기 같은 셸 문법은 아무 일도 하지 않는다고 적습니다. 받은 인자를 번호와 함께 찍는 자식 show 로 두 길을 견줍니다.

읽는 법 — 셸에서 돌린 첫 명령에서는 새 메모.txt 가 1번과 2번 둘로 갈렸습니다. *.rs 는 그 디렉터리의 두 파일 이름으로 바뀌었고, 따옴표는 벗겨졌습니다. ./call 에서는 7번 줄의 새 메모.txt 가 1번 하나로 갔습니다. 11번 줄의 별표와 12번 줄의 따옴표도 적은 글자 그대로입니다. 9번 줄의 args 는 인자 둘을 한 번에 건넸습니다.

자식에게만 환경을 건넨다 — env · env_remove · env_clear

자식의 표준 입력에 쓴다 — Stdio::piped · spawn · wait_with_output

자식에게 글을 먹이고 결과를 받습니다. 셸의 printf … | ./sorter 가 하는 일을 부모가 직접 합니다. 자식 sorter 는 17부의 lines() 로 입력이 끝날 때까지 읽고, 정렬해 번호를 붙여 찍습니다. Stdio::piped() 는 자식의 그 길을 부모와 파이프(pipe)로 잇겠다는 표시입니다. spawn() 은 자식을 띄우기만 하고, 기다리지 않고 자식의 손잡이를 돌려줍니다.

읽는 법 — feed 의 7번과 8번 줄이 두 길을 파이프로 정하고 9번 줄이 띄웁니다. 13번 줄의 child.stdin 은 Option 이라 6부에서 본 take 로 꺼냈습니다. 꺼낸 손잡이는 Write 라서 writeln! 으로 세 줄을 썼습니다. 20번 줄의 wait_with_output 은 자식이 끝나기를 기다리며 출력을 모아, output 과 같은 모양으로 돌려줍니다. 코드는 Some(0) 이고 세 줄은 정렬돼 돌아왔습니다.
다 썼으면 닫는다 — sorter 는 입력이 끝나야 6번 줄의 반복을 나옵니다. 문서는 자식의 표준 입력 손잡이가 정리될 때 닫힌다고, 그리고 닫지 않으면 자식은 입력을, 부모는 자식을 기다리며 멈출 수 있다고 적습니다. feed 의 12번부터 17번 줄까지의 블록이 그래서 있습니다. 블록이 끝나면 stdin 이 스코프를 벗어나 정리됩니다. 닫지 않은 쪽은 끝나지 않는 프로그램이라 돌려 보이지 않습니다.

size_of 와 align_of — 구조체의 크기는 필드 크기의 합이 아닐 수 있다

3부에서 size_of 로 타입의 바이트 수를 물었고, 부록에 타입의 크기를 모아 뒀습니다. u8 하나, u32 하나, u8 하나를 묶은 구조체는 6 바이트일 것 같지만 그렇게 나오지 않습니다. 타입에는 크기 말고 정렬(alignment)이라는 수가 하나 더 있고, align_of 가 그것을 줍니다. 2장에서 줄을 세우던 정렬(sort)과는 다른 말입니다. 필드가 놓인 자리는 offset_of! 매크로( 부터)로 묻습니다.

읽는 법 — 22번과 23번 줄에서 u8 은 크기 1 · 정렬 1, u32 는 크기 4 · 정렬 4 입니다. Fixed 는 12 바이트입니다. 28번부터 30번 줄까지가 찍은 자리는 a 가 0, b 가 4, c 가 8 입니다. a 뒤의 세 바이트와 c 뒤의 세 바이트는 어느 필드의 것도 아닙니다. 이렇게 비워 둔 바이트를 패딩(padding)이라고 합니다. 문서는 align_of 가 주는 수를, 그 타입의 값이 놓이는 주소가 그 배수여야 하는 수라고 설명합니다. b 의 자리 4 와 전체 크기 12 가 4 의 배수입니다. 36번 줄의 size_of_val 은 타입 대신 값에 물었고, u16 다섯 칸은 10 바이트입니다.
Plain 의 8 은 이 툴체인의 답이다 — 31번부터 33번 줄까지에서 Plain 은 b 가 0, a 가 4, c 가 5 입니다. 적은 순서와 다르게 놓여 8 바이트에 들어갔습니다. Rust 레퍼런스는 기본 배치에서 필드의 순서를 약속하지 않는다고 적습니다. 그래서 이 수는 "이 툴체인에서는" 으로만 읽습니다. 13번 줄의 #[repr(C)] 는 적은 순서대로 놓게 하는 속성이고 21부의 #[repr(C)] 는 필드를 적은 순서대로에서 봅니다. 4번 줄의 #[allow(dead_code)] 는 읽지 않는 필드의 경고를 끈 것입니다.

type_name — 제네릭 함수 안에서 T 의 이름을 글로 얻는다

3부에서 값의 타입을 눈으로 확인하려고 type_name_of_val 을 썼습니다. 짝인 std::any::type_name 은 값 없이 타입 인자만으로 이름을 줍니다. 제네릭 함수가 알림에 타입 이름을 넣을 때 씁니다. 아래의 read 는 10부의 FromStr 를 조건으로 두고, 글을 못 읽으면 무엇으로 읽으려 했는지를 알립니다.

읽는 법 — 20번 줄의 read("300") 은 받는 쪽의 표기 Option<u8> 에서 T 가 u8 로 정해졌고, 8번 줄이 그 이름을 넣어 알렸습니다. 22번 줄에서는 bool 입니다. 25번과 26번 줄은 터보피시로 T 를 줬고, 15번 줄의 같은 식이 1 바이트와 8 바이트를 냈습니다. 10부에서 본 대로 제네릭은 타입마다 따로 컴파일됩니다.

둘 다 있을 때만, 하나만 있을 때만 — zip 과 xor

9부에서는 Option 하나를 map 과 and_then 으로 다뤘습니다. 이번에는 Option 이 둘입니다. 가로와 세로가 둘 다 있어야 넓이가 나옵니다. 쿠폰 할인과 회원 할인은 함께 쓸 수 없어서, 하나만 있을 때 그 값을 씁니다. match 로 네 경우를 적는 대신 메서드 하나로 적습니다.

자리에 든 값을 다룬다 — 없을 때만 채우고, 바꿔 넣고, 꺼낸다

변수나 필드가 Option 이면 그것은 값이 있을 수도 없을 수도 있는 자리입니다. 6부에서 그 자리의 값을 꺼내고 None 을 남기는 take 를 봤습니다. 같은 식구를 더 봅니다. 처음 필요할 때 한 번만 계산해 넣어 두는 값이 첫 쓰임새입니다. 15부의 OnceLock 이 전역 값에 하던 일을 지역 변수 하나에 합니다.

겹친 것을 편다 — transpose 는 안팎을 바꾸고, flatten 은 한 겹으로 만든다

9부에서 map 에 준 함수가 Option 을 돌려주면 결과가 Some(Some(6)) 처럼 겹쳤습니다. Result 를 돌려주는 함수를 주면 Option 안에 Result 가 듭니다. 없어도 되는 설정 값을 읽는 일이 그렇습니다. 적지 않았으면 괜찮지만, 적었다면 수여야 합니다.

flatten — 좌석표의 칸은 Option 이고, get 도 Option 을 줍니다. get 이 준 것은 칸의 참조라서, 12부에서 반복자에 쓴 copied 와 이름이 같은 메서드로 값으로 바꿨습니다. 그래서 28번부터 30번 줄까지는 Some(Some("kim")) · Some(None) · None 세 가지입니다. 칸이 비었는지 칸이 없는지를 가리지 않아도 되는 자리에서는 flatten ( 부터)이 한 겹으로 폅니다. 32번과 33번 줄이 둘 다 None 입니다. 12부에서 반복자에 쓴 flatten 과 이름이 같습니다.

꺼내면서 바꾸고, 없을 때의 답을 정한다 — map_or · is_none_or · ok_or_else

9부의 map 은 Option 을 돌려줬고, 기본값을 쓰려면 unwrap_or 를 이어 적었습니다. 이렇게 붙어 다니는 두 걸음을 한 번에 적는 메서드들입니다. map_or 와 ok_or_else 는 없을 때 쓸 것을 인자로 받고, is_none_or 는 없을 때의 답이 이름에 들어 있습니다.

  • is_none_or( 부터) — 없거나, 있으면 조건에 맞는지를 묻습니다. 25번 줄에서 한도 100 에 80 은 true, 120 은 false 이고, 26번 줄처럼 한도가 없으면 120 도 true 입니다. 9부의 is_some_and 는 27번 줄처럼 None 에 false 입니다.

Q. 없어도 되는 설정 값이 text: Option<&str> 로 들어옵니다. text.map(|s| s.parse::<u16>()) 의 결과는 어떤 모양일까요? 값이 없을 때는 넘어가고, 값이 틀렸을 때만 ? 로 오류를 올려 보내려면 무엇을 붙일까요?

A. Option 안에 Result 가 든 모양입니다. Some("8080") 이면 Some(Ok(8080)) 입니다. 끝에 .transpose() 를 붙이면 안팎이 바뀌어 Ok(Some(8080)) 이 되고, 없는 값은 Ok(None), 틀린 값은 Err 입니다. 그 뒤에 ? 를 붙입니다(겹친 것을 편다).
