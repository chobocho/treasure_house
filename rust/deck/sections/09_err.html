9부

오류 처리

panic · Option · Result · ? 연산자 · 내 오류 타입 · 언제 죽고 언제 돌려줄까

이 부에서 할 일

Rust 에는 예외(exception)가 없습니다. 실패를 다루는 길은 둘입니다 — 되살릴 수 없으면 프로그램을 멈추고(panic!), 되살릴 수 있으면 실패를 값으로 돌려줍니다(Result). "없을 수도 있음" 도 값입니다(Option). 셋 다 앞에서 이미 만났습니다. 8부까지는 대부분 그대로 찍거나 unwrap 으로 넘겼고(8부의 끝), 이 부에서 한자리에 모아 제대로 다룹니다.

  • 1장 — panic: 프로그램을 멈추는 것, 그리고 언제 그래도 되는가
  • 2장 — Option: 없을 수 있는 값을 꺼내고, 바꾸고, 잇기
  • 3장 — Result 와 ?: 실패를 값으로 넘기기
  • 4장 — 내 오류 타입: Display, Error, From, Box<dyn Error>
  • 5장 — 실전: 줄 번호가 붙은 오류, 여럿을 한꺼번에, 죽을까 돌려줄까
미리 쓰는 둘 — 8부에서처럼 예제에 |x| x + 1 꼴의 클로저가 가끔 나옵니다. "이름 없는 작은 함수" 로 읽으면 됩니다(12부). 4장은 트레이트 구현(impl … for …)을 모양대로 먼저 써 보고, 뜻은 10부에서 봅니다.

1장

panic

프로그램을 멈춘다 · 종료 코드 101 · 정리는 하고 죽는다 · assert · todo · unimplemented 와 unreachable · 언제 패닉해도 되는가

panic! — 여기서 멈춘다

패닉(panic)은 지금까지 여러 번 봤습니다. 0부에서 배열 끝을 넘어 읽었을 때, 계산이 범위를 넘었을 때, 글자 한가운데를 잘랐을 때, 맵에 없는 키를 [] 로 읽었을 때입니다. 그때는 인덱스나 계산 속에서 났고, 이번에는 panic! 매크로로 직접 냅니다. 메시지와 자리를 찍고 프로그램을 끝내며, 종료 코드는 그때와 같은 101 입니다.

읽는 법 — 화면은 0부에서 읽은 그대로입니다. panic_basic.rs:3:5 가 패닉이 난 자리(파일:줄:칸)이고, 그 아랫줄이 내가 적은 메시지입니다. note: 줄은 환경 변수 RUST_BACKTRACE=1 을 주면 거쳐 온 호출(백트레이스)을 보여 준다는 안내입니다. "시작" 은 멈추기 전에 찍혔습니다.

메시지에는 무엇이 잘못됐는지를 담는다

panic! 은 println! 과 같은 서식을 받습니다. 값을 넣어 두면 죽은 까닭을 화면만 보고 알 수 있습니다.

패닉은 정리를 하고 죽는다

6부에서 값은 스코프를 벗어나면 정리된다고 봤습니다. 패닉으로 끝날 때도 그 정리는 빠지지 않습니다. 패닉은 호출 스택을 거슬러 올라가며(되감기, unwinding) 살아 있던 값을 차례로 정리합니다. Guard 는 6부의 예제처럼 정리될 때 한 줄을 찍는 타입입니다.

읽는 법 — 패닉 메시지가 먼저 찍히고, 그 뒤에 inner 의 값, main 의 값 순서로 정리됐습니다. main 의 마지막 println! 은 실행되지 않았습니다.
안쪽부터 바깥으로 — 패닉이 나도 값은 정리됩니다. 패닉이 난 함수의 값부터, 그 함수를 부른 쪽으로 올라가며 차례로입니다. 정리될 때 할 일을 적는 impl Drop for … 는 14부에서 봅니다.

assert! — 지켜져야 하는 조건을 적는다

assert!(조건, "메시지") 는 조건이 거짓이면 패닉합니다. assert_eq! 는 두 값이 같은지 봅니다. 함수가 믿고 있는 전제를 코드로 남기는 방법입니다.

읽는 법 — 9번 줄의 assert_eq! 는 두 값이 같아 아무것도 찍지 않고 지나갔습니다. 10번 줄이 빈 목록을 넘기자 3번 줄의 assert! 가 내가 적은 메시지로 패닉했습니다.

todo! — 아직 안 쓴 자리

본문을 나중에 채울 함수에는 todo!() 를 둡니다. 어떤 반환 타입 자리에도 맞아서 컴파일은 되고, 실행이 거기 닿으면 패닉합니다.

읽는 법 — 내가 적은 말 앞에 not yet implemented: 가 붙어 나옵니다. 비슷한 매크로로 unimplemented!()("구현하지 않았다") 와 unreachable!()("여기는 올 수 없다") 이 있습니다.

unimplemented! 와 unreachable! — 패닉은 같고 머리말이 다르다

앞 슬라이드가 이름만 든 두 매크로를 돌려 봅니다. 두 파일 모두 todo! 때처럼 u32 를 돌려줘야 하는 자리에 매크로를 놓았고, 컴파일됩니다. 실행이 거기 닿으면 패닉합니다.

읽는 법 — 첫 화면의 9 는 11번 줄의 square 가 낸 값입니다. 12번 줄의 circle 은 6번 줄에 닿아, not implemented: 뒤에 내가 적은 말을 붙이고 패닉했습니다. 둘째 화면의 2 는 13번 줄이 넘긴 5월의 값이고, 14번 줄의 13 은 (13 - 1) / 3 이 4 라서 8번 줄에 닿았습니다. 이번 머리말은 internal error: entered unreachable code: 입니다. 패닉이 난 자리와 note: 줄, 종료 코드 101 은 panic! 을 직접 불렀을 때와 같습니다.
머리말이 뜻을 말한다 — 나중에 채울 자리에는 todo!, 만들지 않기로 한 자리에는 unimplemented!, 올 수 없다고 믿는 자리에는 unreachable! 을 두면 패닉 메시지가 그 사정을 먼저 말해 줍니다. unreachable! 에 닿는 것은 다음 슬라이드의 표 첫 줄, "일어날 수 없다고 믿은 일" 입니다.

언제 패닉해도 되는가

패닉은 프로그램을 통째로 멈추므로 아무 실패에나 쓰지 않습니다. 표의 위 세 줄은 패닉해도 되는 상황이고, 아래 두 줄은 실패를 값으로 돌려줘야 하는 상황입니다.

상황고를 것까닭
프로그램의 버그 — 일어날 수 없다고 믿은 일panic계속 가면 틀린 답을 낸다
부르는 쪽이 약속을 어겼다(빈 목록의 평균)panic · assert!고칠 곳은 부르는 코드다
예제·시험·한 번 쓰고 버릴 코드unwrap · expect(2장)짧게 쓰는 것이 낫다
사용자의 입력이 틀렸다Result(3장)틀릴 수 있다는 것을 안다
파일이 없다, 네트워크가 끊겼다Result부르는 쪽이 대처할 수 있다
기준은 "예상한 실패인가" — 예상한 실패는 값으로 돌려주고, 예상하지 못한 것(버그)에만 패닉합니다.

퀴즈 — panic

Q. 함수 inner 안에서 패닉이 났습니다. main 과 inner 에 각각 살아 있던 값은 정리될까요? 된다면 어느 쪽이 먼저일까요?

A. 둘 다 정리됩니다. 패닉은 스택을 거슬러 올라가며 안쪽(inner)의 값부터, 그다음 바깥(main)의 값을 정리합니다(패닉은 정리를 하고 죽는다).

2장

Option

Some 과 None · 꺼내야 쓴다 · if let 과 let else · unwrap 과 expect · 기본값 · map · and_then · ? · 묻기와 거르기

Option — 있거나(Some) 없거나(None)

7부에서 본 대로 Option<T> 는 변형이 Some(값) 과 None 둘인 열거형이고, match 는 None 갈래를 빠뜨리지 못하게 합니다. 8부의 get 이 돌려준 것도 이 타입입니다. 이 장은 그 속의 값을 꺼내고, 바꾸고, 잇는 도구를 차례로 봅니다. 출발점은 두 경우를 다 적는 match 입니다.

Option 은 속의 값이 아니다 — E0369

Option<i32> 는 i32 가 아닙니다. 꺼내지 않고는 정수처럼 쓸 수 없습니다. 컴파일러가 이 줄을 받아 주지 않으므로, "없을 수도 있다" 를 잊은 채 실행까지 갈 수 없습니다.

읽는 법 — "Option<i32> 에 정수를 더할 수 없다" 입니다. 3번 줄의 maybe 아래에 Option<i32>, 1 아래에 {integer} 라고 두 쪽의 타입을 적어 보여 줍니다. 7부의 null 대신 Option 이 컴파일 오류로 드러난 모습입니다. 고치려면 먼저 꺼내야 하고, 다음 슬라이드부터가 그 방법입니다.

한 경우만 궁금할 때 — if let 과 let else

Some 일 때만 무언가 하려는데 두 갈래를 다 적는 match 는 번거롭습니다. 7부에서 본 if let 과 let else 를 Option 에 그대로 씁니다. 표는 둘의 차이만 다시 적은 것입니다.

문법뜻
if let Some(x) = opt { … }있을 때만 블록을 실행한다. x 는 블록 안에서 쓴다
let Some(x) = opt else { return; };없으면 빠져나간다. x 는 그 아래에서 계속 쓴다
읽는 법 — None 을 넘긴 둘째 호출에서 if let 은 아무것도 찍지 않고 지나갔고, let else 는 else 블록에서 돌아갔습니다.

unwrap — 있다고 믿고 꺼낸다

갈래를 적지 않고 꺼내는 가장 짧은 길입니다. 8부에서 parse 뒤에 붙였던 unwrap() 은 Option 에도 있어서, Some 이면 속을 꺼내고 None 이면 패닉합니다.

"이 줄은 죽을 수 있다" 는 표시 — unwrap 은 실패 처리를 건너뛰는 지름길입니다. 예제에서는 편하지만, 오래 쓸 코드에서는 눈에 띌 때마다 이유를 물어야 합니다.

expect — 죽을 때 남길 말을 정한다

expect("…") 는 unwrap 과 같되, 패닉 메시지를 직접 정합니다. 2부에서 parse 뒤에 붙여 온 메서드이고 Option 에도 있습니다. "무엇이 성립한다고 믿었는가" 를 적는 것이 관례입니다.

읽는 법 — 앞 슬라이드에서 called `Option::unwrap()` on a `None` value 가 나오던 자리에 내가 적은 말이 나왔습니다.

없으면 기본값

패닉하는 대신 쓸 값을 정해 둘 수도 있습니다. 방법은 셋입니다.

  • unwrap_or(값) — 정해 둔 값을 씁니다.
  • unwrap_or_else(클로저) — 없을 때만 클로저를 불러 값을 만듭니다. (기본값을 계산한다) 는 none 쪽에서만 찍혔습니다.
  • unwrap_or_default() — 그 타입의 기본값을 씁니다(u32 는 0).

map — 꺼내지 않고 속을 바꾼다

꺼내는 길은 여기까지이고, 이제 꺼내지 않고 다루는 도구입니다. map 은 Some 이면 속의 값에 함수를 적용하고, None 이면 None 을 그대로 둡니다. match 를 쓰지 않고도 "있으면 이렇게" 를 적을 수 있습니다.

읽는 법 — 결과도 Option 입니다. 길이 6 은 Some(6) 으로 싸여 나왔고, nobody 는 None 그대로입니다.

and_then — 실패할 수 있는 일을 이어 붙인다

적용할 함수 자신이 Option 을 돌려준다면 and_then 을 씁니다. 중간에 하나라도 None 이면 끝까지 None 입니다.

읽는 법 — 12 는 6, 3 으로 두 번 다 나뉘었고, 10 은 5 에서 막혀 None 이 됐습니다. 출력 마지막 줄처럼 같은 자리에 map 을 쓰면 Some(Some(6)) 으로 겹칩니다. and_then 은 그것을 한 겹으로 펴 줍니다.

? — 없으면 여기서 돌아간다

1부에서 Result 에 붙여 본 ? 는 Option 에도 붙습니다. Option 을 돌려주는 함수 안에서 식 뒤에 붙이면, Some 이면 속을 꺼내 계속 가고 None 이면 그 자리에서 함수가 None 을 돌려줍니다.

두 줄에 넷 — next() 는 다음 것을 Option 으로 돌려주는 반복자의 메서드입니다 (12부). 그래서 이 함수에는 None 이 나올 수 있는 자리가 네 군데 있고, 그 자리마다 ? 가 붙었습니다. ? 가 없다면 match 넷이 필요했을 것입니다.

물어보기와 걸러 내기

남은 것은 꺼내지 않고 상태만 묻거나, 조건에 맞을 때만 남기는 메서드입니다.

  • is_some_and(조건) — 값이 있고 조건에도 맞는지 묻습니다. 443 은 1024 보다 작아 true 입니다.
  • filter(조건) — 조건에 안 맞으면 None 으로 바꿉니다. 443 은 1024 보다 크지 않아 None 이 됐습니다.
  • or(다른 Option) — 없을 때 대신 내놓을 Option 을 정합니다.
고르는 순서 — 대신할 값이 있으면 기본값, 속만 바꾸면 map, 실패할 수 있는 일을 이으면 and_then, 없다는 사실을 위로 넘기면 ? 입니다. unwrap · expect 는 없을 리 없다고 믿을 때만 씁니다. 하고 싶은 일로 묶은 표는 이 부의 끝에 있습니다.

퀴즈 — Option

Q. Some(10).and_then(half).and_then(half) 의 값은 무엇일까요? (half 는 짝수면 반을 Some 으로, 홀수면 None 을 돌려줍니다.)

A. None 입니다. 10 의 반은 5 이고, 5 는 홀수라 둘째 half 가 None 을 돌려줍니다. 12 로 시작하면 Some(3) 입니다(and_then).

3장

Result 와 ?

Ok 와 Err · unwrap · 버려진 Result 는 경고 · map_err · Option ↔ Result · 메서드로 잇기 · ? 연산자 · main 이 Result 를 돌려줄 때 · 종료 코드 1 과 101 · 오류의 종류가 다르면

Result — 성공(Ok)이거나 실패(Err)거나

None 은 "없다" 만 말하고 왜인지는 말하지 못합니다. 실패한 까닭까지 실어 보내는 타입이 Result<T, E> 입니다 — 성공하면 Ok(값), 실패하면 Err(까닭). 3부의 try_from 과 8부의 parse 가 돌려준 것이 이 타입입니다.

반환 타입에 적힌다 — 실패할 수 있다는 사실이 함수의 반환 타입에 적혀 있습니다. 속의 정수를 쓰려면 Ok 인지 Err 인지부터 갈라야 합니다. Err 갈래의 {e} 가 찍은 까닭 invalid digit found in string 은 "숫자가 아닌 글자가 있다" 입니다.

Result 의 unwrap — 패닉 메시지에 Err 의 속이 찍힌다

8부에서 parse 뒤에 붙여 온 unwrap 이 이것입니다. Option 의 것과 같아서, Ok 면 속을 꺼내고 Err 면 패닉합니다.

읽는 법 — 패닉 메시지 끝의 ParseIntError { kind: InvalidDigit } 가 Err 안에 있던 값입니다. Option 때는 None 이라는 말뿐이었지만 이번에는 까닭이 함께 찍혔습니다.

Result 를 보지 않고 버리면 경고한다

실패를 돌려줬는데 받는 쪽이 보지도 않으면 오류가 조용히 사라집니다. 컴파일러는 버려진 Result 를 찾아 경고합니다.

읽는 법 — 9번 줄의 Result 가 쓰이지 않았다는 경고입니다. 첫 note: 는 그 값이 Err 일 수 있으니 다뤄야 한다고 말합니다. 경고일 뿐이라 프로그램은 돌았습니다.
정말 무시하려면 — help: 줄대로 let _ = save(""); 라고 써서 "알고 버린다" 를 드러냅니다.

Result 에도 같은 도구가 있다

unwrap_or, unwrap_or_else, map 이 Result 에도 있습니다. 여기에 오류 쪽만 바꾸는 map_err 가 더해집니다. and_then 은 조금 뒤에 씁니다.

읽는 법 — Ok(6) 은 3 을 두 배 한 값이고, Err(6) 은 오류 글 "고장" 의 길이입니다(len 은 바이트). 출력 마지막 줄의 is_ok() 와 is_err() 는 꺼내지 않고 어느 쪽인지만 묻습니다.

Option 과 Result 를 오가기

"없다" 에 까닭을 붙이면 Result 가 되고(ok_or), "실패했다" 에서 까닭을 떼면 Option 이 됩니다(ok).

메서드로 잇기 — map_err 와 and_then

2장에서 Option 에 쓴 and_then 이 Result 에도 있습니다. map_err 로 오류에 설명을 덧붙이고, and_then 으로 성공한 값에 검사를 하나 더 잇습니다.

읽는 법 — " 8080 " 은 끝까지 지나 Ok(8080) 이 됐고, "0" 은 and_then 의 검사에 걸렸습니다. "99999" 는 parse 에서 실패해, map_err 가 앞에 붙인 포트 `99999`: 와 함께 나왔습니다.

실패를 위로 넘기기 — ? 없이 쓰면

함수가 스스로 대처할 수 없는 실패라면 할 일은 "나를 부른 쪽에 그대로 알리는 것" 입니다. 손으로 쓰면 실패할 수 있는 줄마다 match 와 return 이 붙습니다.

? 연산자 — Err 면 그 오류를 들고 돌아간다

앞 슬라이드의 match 를 물음표 하나로 줄입니다. 1부에서 try! 를 대신했다고 본 모양이고, 2장의 ? 와 같은 일을 합니다. Ok 면 속을 꺼내 계속 가고, Err 면 그 오류를 들고 함수에서 곧바로 돌아갑니다.

눈에 띄는 한 글자 — 출력이 앞 슬라이드와 같습니다. 그리고 오류를 들고 함수에서 돌아갈 수 있는 자리마다 ? 가 적혀 있어서, 코드를 읽는 사람이 실패의 길을 눈으로 따라갈 수 있습니다.

? 는 Result 나 Option 을 돌려주는 함수에서만 — E0277

? 는 "오류를 들고 돌아간다" 이므로, 돌아갈 때 오류를 실어 보낼 수 있는 반환 타입이 필요합니다. 아무것도 돌려주지 않는 main 에서는 쓸 수 없습니다.

읽는 법 — 8부에서 본 E0277 과 번호가 같습니다. 그때 없다던 것은 구현이었고, 이번에는 ? 를 받아 줄 반환 타입입니다. 1번 줄에는 "이 함수가 Result 나 Option 을 돌려줘야 한다", 2번 줄의 ? 에는 "() 를 돌려주는 함수에서는 쓸 수 없다" 가 붙었습니다. 첫 줄 괄호 속의 FromResidual 은 이 책에서 다루지 않습니다.
help: — main 에 반환 타입을 적고 끝에 Ok(()) 를 두라고 권합니다. main 이 Result 를 돌려주는 모양은 다음 슬라이드에서, 권한 타입 Box<dyn std::error::Error> 는 4장에서 봅니다.

main 이 Result 를 돌려주면 — Err 는 종료 코드 1

main 의 반환 타입을 Result 로 하면 그 안에서 ? 를 쓸 수 있습니다. Err 로 끝나면 오류를 Error: … 로 찍고 종료 코드 1 로 끝납니다.

1 과 101 — 같은 "사십이" 를 unwrap 했을 때는 패닉이라 자리(파일:줄:칸)와 note: 줄이 찍히고 종료 코드가 101 이었습니다. main 이 Err 를 돌려준 이번에는 스레드가 죽었다는 말도, 소스의 줄 번호도 없습니다. 오류 값을 디버그 서식으로 찍은 한 줄과 종료 코드 1 입니다.

오류의 종류가 다르면 ? 가 막힌다 — E0277

함수가 돌려주기로 한 오류는 ParseIntError 인데, 5번 줄이 내는 오류는 ParseFloatError 입니다. ? 는 하나를 다른 하나로 바꿀 방법을 모릅니다.

읽는 법 — 3부에서 본 "From 이 구현되어 있지 않다" 와 같은 꼴의 E0277 입니다. 이번에 없다는 것은 ParseFloatError 를 ParseIntError 로 바꾸는 From 입니다. 새로 읽을 것은 note: 줄로, ? 가 오류 값을 From 트레이트로 바꾼다고 알려 줍니다. 그 From 을 구현해 주면 ? 가 알아서 바꿉니다. 4장에서 그렇게 고칩니다.

퀴즈 — Result 와 ?

Q. let x = a.parse::<i32>()?; 를 ? 없이 풀어 쓰면 어떤 코드가 될까요?

A. let x = match a.parse::<i32>() { Ok(n) => n, Err(e) => return Err(e), }; 입니다(? 없이 쓰면). 정확히는 Err(e) 를 돌려보낼 때 From 으로 오류 타입을 바꾸는 일이 하나 더 들어갑니다(오류의 종류가 다르면 의 note: 줄, 그리고 4장).

4장

내 오류 타입

열거형으로 오류 나누기 · Display · Error · Error 가 요구하는 Debug · From 과 ? · Box<dyn Error> · main 의 반환 타입 · source · 고르기

오류의 종류를 열거형으로 나눈다

3장의 parse_port 처럼 문자열로 된 오류는 사람이 읽기에는 좋지만 프로그램이 갈라 다루기 어렵습니다. 오류의 경우를 데이터를 가진 변형으로 만들면 부르는 쪽이 match 로 가를 수 있습니다.

쓴 도구 — 3장 그대로입니다. 10번 줄은 ok_or 와 ? 를, 13번 줄은 map_err 를 썼습니다. 달라진 것은 오류가 글이 아니라 변형이라는 점 하나입니다.

Display 와 Error 를 구현한다

앞 슬라이드에서는 찍을 말을 main 이 변형마다 정했습니다. 그 말을 오류 타입이 스스로 갖게 합니다. 오류 타입이 갖춰야 할 것은 둘입니다. 사람에게 보일 말(Display)과, "이것은 오류다" 라는 표시(std::error::Error)입니다. Error 는 Debug 도 함께 요구하므로 #[derive(Debug)] 를 붙여 둡니다.

미리 쓰는 문법 — impl … for … 는 트레이트 구현이고 10부에서 봅니다. 지금은 "이 타입에 이 능력을 붙인다" 로 읽습니다. write! 는 println! 과 같은 서식으로 화면 대신 f 에 씁니다(Display 구현).
읽는 법 — {e} 로 찍은 숫자가 아니다: abc 와 port 항목이 없다 가 Display, {e:?} 로 찍은 BadNumber("abc") 가 Debug 입니다.

Debug 가 없는 타입에는 Error 를 구현할 수 없다 — E0277

앞 슬라이드에서 "Error 는 Debug 도 함께 요구한다" 고 했습니다. Display 만 구현하고 Debug 는 없는 작은 타입에 Error 를 구현해, 컴파일러에게 그 말을 듣습니다.

읽는 법 — 오류 첫 줄은 "Empty 는 Debug 를 구현하지 않는다" 이고, 밑줄은 12번 줄의 Empty 에 있습니다. 그 요구가 어디서 왔는지는 note: 가 말합니다 — "std::error::Error 의 조건이 요구한다". 3부에서 sort 가 Ord 를 요구한다던 것과 같은 꼴의 note: 입니다. 그 아래 /rustc/ 로 시작하는 줄은 이 컴파일러에 딸린 표준 라이브러리 소스의 자리입니다. help: 는 3번 줄 자리에 #[derive(Debug)] 를 붙이라고 합니다.
오류 타입에는 Debug 를 먼저 — 고친 파일은 컴파일되고, main 이 {} 로 찍은 빈 입력 이 나옵니다. Debug 가 쓰이는 자리 하나는 3장에서 봤습니다. main 이 Err 로 끝날 때 오류 값을 디버그 서식으로 찍었습니다.

From 을 구현하면 ? 가 바꿔 준다

3장에서 막혔던 ratio 를 고칩니다. 표준 라이브러리의 두 오류를 내 오류로 바꾸는 From 을 구현해 두면, ? 가 돌려보낼 때 그것을 불러 줍니다. From 은 10부에서 다시 봅니다.

Result 에서 ? 의 뜻을 마저 적으면 — "Err(e) 면 return Err(From::from(e))". 그래서 종류가 다른 오류들이 한 함수 안에서 한 타입으로 모이고, main 은 어느 쪽 오류인지 갈라서 찍을 수 있습니다.
빠진 것 — 화면을 줄이려고 앞에서 본 Display 와 Error 구현은 뺐습니다. ? 가 쓰는 것은 From 뿐이라 그래도 컴파일됩니다.

Box<dyn Error> — 타입을 만들지 않는 지름길

작은 프로그램에서 오류 타입을 일일이 만들기는 번거롭습니다. Box<dyn Error> 는 "오류이기만 하면 무엇이든" 을 뜻하고, 어떤 오류든 ? 로 여기에 담깁니다. 같은 ratio 가 앞 슬라이드의 열거형과 From 둘 없이 돕니다.

잃는 것 — 부르는 쪽은 오류가 "무엇인지" 를 match 로 가르기 어렵습니다. 찍거나 위로 넘기는 것만 하면 되는 곳(프로그램의 맨 바깥)에 어울립니다.
미리 쓰는 문법 — Box<dyn Error> 는 지금은 통째로 한 낱말처럼 읽습니다. dyn 은 10부, Box<dyn …> 꼴은 14부에서 봅니다.

main 과 Box<dyn Error> — 어떤 오류에든 ? 를 붙인다

3장에서 컴파일러가 권했던 모양입니다. main 이 Result<(), Box<dyn Error>> 를 돌려주면, 본문 어디서든 어떤 오류에든 ? 를 쓸 수 있습니다.

작은 도구의 기본 틀 — i32 · f64 · u8 을 읽는 parse 셋에 같은 ? 를 붙였습니다. 셋째에서 main 이 Err 로 끝나, 3장에서 본 Error: … 한 줄과 종료 코드 1 이 나왔습니다. 한 파일짜리 프로그램은 이 한 줄로 시작하면 unwrap 없이 쓸 수 있습니다.

source — 오류를 낳은 오류

앞에서 비워 두었던 Error 구현에 채울 수 있는 것이 source 입니다. "3번째 줄을 읽지 못했다" 는 무슨 일이 있었는지, invalid digit found in string 은 왜 그랬는지를 말합니다. 위의 오류가 아래의 오류를 품고, source() 로 꺼내 줍니다.

낯선 것 둘 — unwrap_err() 는 unwrap 의 반대로, Err 의 속을 꺼냅니다. source 의 반환 타입 Option<&(dyn Error + 'static)> 은 "어떤 오류든 하나를 빌려 준다, 없을 수도 있다" 로 읽습니다('static 은 11부).

오류 타입 고르기

오류 자리에 둘 타입을 이 부에서 써 본 것 가운데 셋으로 추렸습니다. 표는 각각 무엇이 좋고 어디에 어울리는지를 견준 것입니다.

오류 타입좋은 점어울리는 곳
String따로 만들 것이 없다예제, 아주 작은 함수
Box<dyn Error>오류이기만 하면 ? 로 담긴다main, 한 파일짜리 도구
내 열거형 + From부르는 쪽이 종류별로 가른다남이 쓰는 라이브러리, 큰 프로그램의 안쪽
손으로 쓴 까닭 — 이 책은 표준 라이브러리만 쓰므로 Display · Error · From 을 손으로 구현했습니다. 이 반복되는 구현을 대신 써 주는 바깥 크레이트는 이 책에서 다루지 않습니다.

퀴즈 — 내 오류 타입

Q. 반환 타입이 Result<f64, CalcError> 인 함수에서 b.parse::<f64>()? 가 컴파일되려면 무엇이 있어야 할까요?

A. impl From<ParseFloatError> for CalcError 가 있어야 합니다. ? 는 돌려보낼 때 From 으로 오류를 바꾸기 때문입니다(From 을 구현하면). 없으면 E0277 이 납니다(3장).

실전

어느 줄이 왜 틀렸는지 말해 주기

좋은 오류는 "실패했다" 가 아니라 "어디서 무엇이 왜" 를 말합니다. 줄 번호와 문제의 값을 오류에 실어 보냅니다.

쓴 도구 — ok_or 로 Option 을 Result 로, map_err 로 오류에 줄 번호를, 그리고 ? 로 위로 넘겼습니다. main 이 줄마다 match 로 받았으므로, 틀린 줄에서 멈추지 않고 네 줄을 다 읽었습니다.

하나라도 실패하면 전체 실패 — collect

앞 슬라이드는 줄마다 따로 받았습니다. 전부 성공해야 쓸모가 있는 목록이라면 Result 여럿을 Result<Vec<_>, _> 하나로 모읍니다. 전부 성공하면 값들의 목록이, 하나라도 실패하면 첫 오류가 나옵니다.

거기서 멈춘다 — 둘째 목록에서 읽는다: 는 1 과 둘 에서 끝났습니다. 3 과 넷 은 읽지도 않았습니다. 8부에서 Vec 으로 모으던 collect 가, 받는 쪽의 타입 표기에 따라 이번에는 Result 로 모았습니다(12부).

되는 것만 쓰고, 안 되는 것은 따로

전부 아니면 전무가 아니라 "성공한 것은 쓰고 실패한 것은 알려 준다" 가 필요할 때도 있습니다.

출력 마지막 줄 — filter_map 은 클로저가 Some 을 돌려준 것만 남기는 반복자 메서드입니다(12부). parse().ok() 가 실패를 None 으로 바꾸므로 성공한 수만 남았습니다.

같은 parse, 다른 처리

1장의 표에서 정한 기준 "예상한 실패인가" 를 parse 하나에 대어 봅니다. 값이 어디서 왔느냐에 따라 다루는 법이 다릅니다. 내가 쓴 상수가 틀렸다면 버그이고, 바깥에서 온 입력이 틀렸다면 예상한 일입니다.

퀴즈 — 실전

Q. ["1", "둘", "3", "넷"] 의 원소를 하나씩 parse 해서 Result<Vec<i32>, _> 로 collect 하면 무엇이 나올까요?

A. Err 하나입니다 — 첫 실패("둘")의 오류가 나오고 거기서 멈춥니다. "넷" 의 오류는 보이지 않습니다(collect). 실패를 전부 알고 싶으면 갈라 담습니다 (되는 것만 쓰고).
