9부

오류 처리

panic · Option · Result · ? 연산자 · 내 오류 타입 · 언제 죽고 언제 돌려줄까

이 부에서 할 일

Rust 에는 예외(exception)가 없습니다. 실패를 다루는 길은 둘입니다 — 되살릴 수 없으면 프로그램을 멈추고(panic!), 되살릴 수 있으면 실패를 값으로 돌려줍니다(Result). "없을 수도 있음" 도 값입니다(Option).

  • 1장 — panic: 프로그램을 멈추는 것, 그리고 언제 그래도 되는가
  • 2장 — Option: 있거나 없거나. null 이 없는 언어
  • 3장 — Result 와 ?: 실패를 값으로 넘기기
  • 4장 — 내 오류 타입: Display, Error, From, Box<dyn Error>
  • 5장 — 실전: 줄 번호가 붙은 오류, 여럿을 한꺼번에, 죽을까 돌려줄까
미리 쓰는 것 — 이 부의 예제에는 |x| x + 1 꼴의 클로저가 가끔 나옵니다. "이름 없는 작은 함수" 로만 읽으면 됩니다(12부).

1장

panic

프로그램을 멈춘다 · 종료 코드 101 · 정리는 하고 죽는다 · assert · todo

panic! — 여기서 멈춘다

panic! 은 메시지와 자리(파일:줄:칸)를 찍고 프로그램을 끝냅니다. 종료 코드는 101 입니다.

note: 줄 — 환경 변수 RUST_BACKTRACE=1 을 주고 다시 돌리면 어떤 함수들을 거쳐 여기까지 왔는지(백트레이스)를 보여 준다는 안내입니다.

메시지에는 무엇이 잘못됐는지를 담는다

panic! 은 println! 과 같은 서식을 받습니다. 값을 넣어 두면 죽은 까닭을 화면만 보고 알 수 있습니다.

패닉은 정리를 하고 죽는다

패닉이 나면 호출 스택을 거슬러 올라가며(되감기, unwinding) 살아 있던 값들을 차례로 정리합니다. 아래의 Guard 는 정리될 때 한 줄을 찍는 값입니다.

안쪽부터 바깥으로 — inner 의 값이 먼저, main 의 값이 다음에 정리됐습니다. 파일이 닫히고 잠금이 풀리는 것도 이 순서에 실려 일어납니다. Drop 은 14부에서 봅니다.

assert! — 지켜져야 하는 조건을 적는다

assert!(조건, "메시지") 는 조건이 거짓이면 패닉합니다. assert_eq! 는 두 값이 같은지 봅니다. 함수가 믿고 있는 전제를 코드로 남기는 방법입니다.

todo! — 아직 안 쓴 자리

본문을 나중에 채울 함수에는 todo!() 를 둡니다. 어떤 반환 타입 자리에도 맞아서 컴파일은 되고, 실행이 거기 닿으면 패닉합니다.

형제들 — unimplemented!() 는 "만들 계획이 없다", unreachable!() 은 "여기는 올 수 없다" 는 뜻으로 씁니다. 셋 다 닿으면 패닉합니다.

언제 패닉해도 되는가

상황고를 것까닭
프로그램의 버그 — 일어날 수 없다고 믿은 일panic계속 가면 틀린 답을 낸다
부르는 쪽이 약속을 어겼다(빈 목록의 평균)panic / assert!고칠 곳은 부르는 코드다
예제·시험·한 번 쓰고 버릴 코드unwrap / expect짧게 쓰는 것이 낫다
사용자의 입력이 틀렸다Result틀릴 수 있다는 것을 안다
파일이 없다, 네트워크가 끊겼다Result부르는 쪽이 대처할 수 있다
기준은 "예상한 실패인가" — 예상한 실패는 값으로 돌려주고, 예상하지 못한 것(버그)에만 패닉합니다.

퀴즈 — panic

Q. 함수 inner 안에서 패닉이 났습니다. main 과 inner 에 각각 살아 있던 값은 정리될까요? 된다면 어느 쪽이 먼저일까요?

A. 둘 다 정리됩니다. 패닉은 스택을 거슬러 올라가며 안쪽(inner)의 값부터, 그다음 바깥(main)의 값을 정리합니다(패닉은 정리를 하고 죽는다).

2장

Option

Some 과 None · null 이 없다 · unwrap 과 expect · 기본값 · map · and_then · ?

Option — 있거나(Some) 없거나(None)

"값이 없을 수도 있다" 를 타입으로 적은 것이 Option<T> 입니다. 값이 있으면 Some(값), 없으면 None 입니다. 꺼내려면 두 경우를 다 다뤄야 합니다.

Option 은 속의 값이 아니다 — E0369

Option<i32> 는 i32 가 아닙니다. 꺼내지 않고는 정수처럼 쓸 수 없습니다. 다른 언어의 null 은 여기서 실행 중에 터지지만, Rust 는 컴파일에서 막습니다.

null 이 없는 언어 — "없을 수 있는 값" 과 "반드시 있는 값" 이 타입으로 갈립니다. i32 라고 적혀 있으면 정말로 정수가 들어 있습니다.

unwrap — 있다고 믿고 꺼낸다

unwrap() 은 Some 이면 속을 꺼내고, None 이면 패닉합니다.

"이 줄은 죽을 수 있다" 는 표시 — unwrap 은 실패 처리를 건너뛰는 지름길입니다. 예제에서는 편하지만, 오래 쓸 코드에서는 눈에 띌 때마다 이유를 물어야 합니다.

expect — 죽을 때 남길 말을 정한다

expect("…") 는 unwrap 과 같되, 패닉 메시지를 직접 정합니다. "무엇이 성립한다고 믿었는가" 를 적는 것이 관례입니다.

없으면 기본값

죽는 대신 대신할 값을 줍니다. 세 가지가 있습니다.

  • unwrap_or(값) — 정해진 값.
  • unwrap_or_else(클로저) — 없을 때만 계산해서 만든다.
  • unwrap_or_default() — 그 타입의 기본값(수는 0, 문자열은 빈 문자열).

map — 꺼내지 않고 속을 바꾼다

map 은 Some 이면 속의 값에 함수를 적용하고, None 이면 None 을 그대로 둡니다. match 를 쓰지 않고도 "있으면 이렇게" 를 적을 수 있습니다.

and_then — 실패할 수 있는 일을 이어 붙인다

적용할 함수 자신이 Option 을 돌려준다면 and_then 을 씁니다. 중간에 하나라도 None 이면 끝까지 None 입니다.

마지막 줄 — 같은 자리에 map 을 쓰면 Some(Some(6)) 처럼 겹칩니다. and_then 은 그것을 한 겹으로 펴 줍니다.

? — 없으면 여기서 돌아간다

Option 을 돌려주는 함수 안에서는 식 뒤에 ? 를 붙일 수 있습니다. Some 이면 속을 꺼내 계속 가고, None 이면 그 자리에서 함수가 None 을 돌려줍니다.

한 줄에 넷 — 이 함수에는 실패할 수 있는 자리가 네 군데 있습니다. ? 가 없다면 match 넷이 필요했을 것입니다.

물어보기와 걸러 내기

꺼내지 않고 상태만 묻거나, 조건에 맞을 때만 남기는 메서드들입니다.

  • is_some_and(조건) — 있고, 그 값이 조건에 맞는가.
  • filter(조건) — 조건에 안 맞으면 None 으로 바꾼다.
  • or(다른 Option) — 없으면 대신 이것을.

한 경우만 궁금할 때 — if let 과 let else

Some 일 때만 무언가 하려는데 match 는 번거롭습니다. 두 가지 짧은 문법이 있습니다. 둘 다 7부에서 자세히 봤습니다.

문법뜻
if let Some(x) = opt { … }있을 때만 블록을 실행한다. x 는 블록 안에서 쓴다
let Some(x) = opt else { return; };없으면 빠져나간다. x 는 그 아래에서 계속 쓴다

퀴즈 — Option

Q. Some(10).and_then(half).and_then(half) 의 값은 무엇일까요? (half 는 짝수면 반을 Some 으로, 홀수면 None 을 돌려줍니다.)

A. None 입니다. 10 의 반은 5 이고, 5 는 홀수라 둘째 half 가 None 을 돌려줍니다. 12 로 시작하면 Some(3) 입니다(and_then).

3장

Result 와 ?

Ok 와 Err · 버려진 Result 는 경고 · ? 연산자 · main 이 Result 를 돌려줄 때

Result — 성공(Ok)이거나 실패(Err)거나

Result<T, E> 는 성공하면 Ok(값), 실패하면 Err(까닭) 입니다. Option 과 닮았지만 실패한 쪽에도 값(왜 실패했는지)이 들어 있습니다.

예외와 다른 점 — 실패할 수 있다는 사실이 함수의 반환 타입에 적혀 있습니다. 부르는 쪽은 그것을 모르고 지나칠 수 없습니다.

Result 의 unwrap

Option 과 같습니다. Ok 면 속을 꺼내고 Err 면 패닉합니다. 패닉 메시지에는 Err 안의 값이 찍힙니다.

Result 를 그냥 버리면 경고한다

실패를 돌려줬는데 받는 쪽이 보지도 않으면 오류가 조용히 사라집니다. 컴파일러는 버려진 Result 를 찾아 경고합니다.

정말 무시하려면 help: 줄대로 let _ = save(""); 라고 써서 "알고 버린다" 를 드러냅니다.

Result 에도 같은 도구가 있다

unwrap_or, map, and_then 이 Result 에도 있습니다. 여기에 오류 쪽만 바꾸는 map_err 가 더해집니다.

실패를 위로 넘기기 — ? 없이 쓰면

함수 안에서 실패가 나면 대개 할 수 있는 일은 "나를 부른 쪽에 그대로 알리는 것" 입니다. 손으로 쓰면 실패할 수 있는 줄마다 match 와 return 이 붙습니다.

? 연산자

앞 장의 match 를 물음표 하나로 줄입니다. Ok 면 속을 꺼내 계속 가고, Err 면 그 오류를 들고 함수에서 곧바로 돌아갑니다.

눈에 띄는 한 글자 — 예외와 달리, 함수가 중간에 빠져나갈 수 있는 자리마다 ? 가 적혀 있습니다. 코드를 읽는 사람이 실패의 길을 눈으로 따라갈 수 있습니다.

? 는 Result 를 돌려주는 함수에서만 — E0277

? 는 "오류를 들고 돌아간다" 이므로, 돌아갈 때 오류를 실어 보낼 수 있는 반환 타입이 필요합니다. 아무것도 돌려주지 않는 main 에서는 쓸 수 없습니다.

main 이 Result 를 돌려주면

main 의 반환 타입을 Result 로 하면 그 안에서 ? 를 쓸 수 있습니다. Err 로 끝나면 오류를 Error: … 로 찍고 종료 코드 1 로 끝납니다.

패닉(101)과 다른 끝 — 스레드가 죽었다는 말도, 소스의 줄 번호도 없습니다. 오류 값을 디버그 서식으로 찍은 한 줄과 종료 코드 1 입니다.

오류의 종류가 다르면 ? 가 막힌다 — E0277

함수의 반환 타입은 ParseIntError 인데, 둘째 줄이 내는 오류는 ParseFloatError 입니다. ? 는 하나를 다른 하나로 바꿀 방법을 모릅니다.

실마리 — 메시지가 말하는 From 을 구현해 주면 ? 가 알아서 바꿉니다. 다음 장의 주제입니다.

메서드로 잇기 — map_err 와 and_then

오류에 설명을 덧붙이고(map_err), 성공한 값에 검사를 하나 더 잇는(and_then) 모양입니다. 세 가지 입력이 세 갈래로 갈립니다.

퀴즈 — Result 와 ?

Q. let x = a.parse::<i32>()?; 를 ? 없이 풀어 쓰면 어떤 코드가 될까요?

A. let x = match a.parse::<i32>() { Ok(n) => n, Err(e) => return Err(e), }; 입니다(? 없이 쓰면). 정확히는 Err(e) 를 돌려보낼 때 From 으로 오류 타입을 바꾸는 일이 하나 더 들어갑니다(다음 장).

4장

내 오류 타입

열거형으로 오류 나누기 · Display · Error · From 과 ? · Box<dyn Error> · source

오류의 종류를 열거형으로 나눈다

문자열로 된 오류는 사람이 읽기에는 좋지만 프로그램이 갈라 다루기 어렵습니다. 오류의 경우를 열거형의 변형으로 만들면 부르는 쪽이 match 로 가를 수 있습니다.

Display 와 Error 를 구현한다

오류 타입이 갖춰야 할 것은 둘입니다. 사람에게 보일 말(Display)과, "이것은 오류다" 라는 표시(std::error::Error)입니다.

impl … for … 는 트레이트 구현입니다. 10부에서 배웁니다. 지금은 "이 타입에 이 능력을 붙인다" 로 읽으세요.

From 을 구현하면 ? 가 바꿔 준다

3장 끝에서 막혔던 문제의 답입니다. 아래 오류를 내 오류로 바꾸는 From 을 구현해 두면, ? 가 돌려보낼 때 그것을 불러 줍니다.

? 의 완전한 뜻 — "Err(e) 면 return Err(From::from(e))". 그래서 종류가 다른 오류들이 한 함수 안에서 한 타입으로 모입니다.

Box<dyn Error> — 타입을 만들지 않는 지름길

작은 프로그램에서 오류 타입을 일일이 만들기는 번거롭습니다. Box<dyn Error> 는 "오류이기만 하면 무엇이든" 을 뜻하고, 어떤 오류든 ? 로 여기에 담깁니다.

잃는 것 — 부르는 쪽은 오류가 "무엇인지" 를 match 로 가르기 어렵습니다. 찍거나 위로 넘기는 것만 하면 되는 곳(프로그램의 맨 바깥)에 어울립니다.

source — 오류를 낳은 오류

"3번째 줄을 읽지 못했다" 는 무슨 일이 있었는지, "숫자가 아닌 글자" 는 왜 그랬는지를 말합니다. 위의 오류가 아래의 오류를 품고, source() 로 꺼내 줍니다.

main 과 Box<dyn Error>

3장에서 컴파일러가 권했던 모양입니다. main 이 Result<(), Box<dyn Error>> 를 돌려주면, 본문 어디서든 어떤 오류에든 ? 를 쓸 수 있습니다.

작은 도구의 기본 틀 — 예제와 한 파일짜리 프로그램은 이 한 줄로 시작하면 unwrap 없이 쓸 수 있습니다.

오류 타입 고르기

오류 타입좋은 점어울리는 곳
String가장 쉽다예제, 아주 작은 함수
Box<dyn Error>무엇이든 ? 로 담긴다main, 한 파일짜리 도구
내 열거형 + From부르는 쪽이 종류별로 가른다남이 쓰는 라이브러리, 큰 프로그램의 안쪽
바깥 크레이트 — 실무에서는 이 반복되는 구현을 줄여 주는 크레이트를 흔히 씁니다. 이 책은 표준 라이브러리만 쓰므로 손으로 구현했고, 그 크레이트들이 대신 써 주는 것이 바로 이 장의 코드입니다.

퀴즈 — 내 오류 타입

Q. 반환 타입이 Result<f64, CalcError> 인 함수에서 b.parse::<f64>()? 가 컴파일되려면 무엇이 있어야 할까요?

A. impl From<ParseFloatError> for CalcError 가 있어야 합니다. ? 는 돌려보낼 때 From 으로 오류를 바꾸기 때문입니다(From 을 구현하면). 없으면 E0277 이 납니다(3장).

5장

실전

줄 번호가 붙은 오류 · 여럿을 한꺼번에 · Option ↔ Result · 죽을까 돌려줄까

어느 줄이 왜 틀렸는지 말해 주기

좋은 오류는 "실패했다" 가 아니라 "어디서 무엇이 왜" 를 말합니다. 줄 번호와 문제의 값을 오류에 실어 보냅니다.

쓴 도구 — ok_or 로 Option 을 Result 로, map_err 로 오류에 줄 번호를, 그리고 ? 로 위로 넘겼습니다.

하나라도 실패하면 전체 실패 — collect

Result 여럿을 Result<Vec<_>, _> 로 모을 수 있습니다. 전부 성공하면 값들의 목록이, 하나라도 실패하면 첫 오류가 나옵니다.

collect 는 반복자가 내는 값을 모으는 메서드입니다. 받는 쪽의 타입 표기에 따라 모으는 모양이 달라집니다(12부).

되는 것만 쓰고, 안 되는 것은 따로

전부 아니면 전무가 아니라 "성공한 것은 쓰고 실패한 것은 알려 준다" 가 필요할 때도 많습니다.

Option 과 Result 를 오가기

"없다" 에 까닭을 붙이면 Result 가 되고(ok_or), "실패했다" 에서 까닭을 떼면 Option 이 됩니다(ok).
