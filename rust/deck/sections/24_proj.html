프로젝트의 짜임 — 장마다 첫 슬라이드 "이 프로젝트가 쓰는 것" 이 다시 쓰는 것과 그것을 배운 슬라이드를 표로 잇습니다. 이 부는 거기서 배운 것을 다시 설명하지 않습니다. 그다음 프로그램을 단계로 나눠 키우고, 시험으로 마무리하고, 풀이 없는 과제 "더 해 볼 것" 으로 끝납니다. 단계 하나는 예제 디렉터리 하나이고 저마다 온전한 Cargo 패키지입니다. 뒤 단계의 디렉터리는 23부의 쌍둥이 디렉터리처럼, 앞 단계의 파일을 그대로 두고 줄을 더하거나 적어 둔 줄만 바꾼 사본입니다. 슬라이드는 그 단계에서 새로 생기거나 바뀐 줄만 싣습니다. 코드 상자의 꼬리표에 단계의 디렉터리 이름이 있고, N번 줄 은 그 단계의 파일에서 센 번호입니다. 같은 함수도 단계가 넘어가면 줄 번호가 달라집니다.
이 부의 화면 — 화면을 만든 방식은 23부와 같습니다. 예제 디렉터리의 사본 안에서 $ 줄의 명령을 위에서부터 차례로 돌렸고, 앞 명령이 만든 target/ 과 파일은 다음 명령 때 그대로 남아 있습니다. $ 줄은 줄마다 사본의 뿌리에서 시작합니다. Cargo 는 인터넷에 나가지 않게 해 두었고, 바깥 크레이트는 하나도 없습니다. 1장의 화면은 cargo build -q 로 한 번 빌드한 뒤, 2부에서 본 target/debug/ 의 실행 파일을 직접 부릅니다. 프로그램의 표준 입력은 그 줄에 적힌 | 나 < 로만 줍니다. 1장의 Cargo 명령에는 모두 -q 를 붙였습니다. 0부에서 말한 고정 가운데 1장의 화면에 나오는 것은 시험 결과 줄의 0.00s 하나입니다. 1장의 예제는 따라 돌리는 셸의 환경 변수를 읽지 않습니다. 화면에 나오는 (os error 2) 같은 글은 이 책을 만든 기계의 운영 체제가 준 것입니다.

이 프로젝트가 쓰는 것

17부 6장에서 줄 · 낱말 · 바이트를 세는 wc 를 파일 하나로 만들었습니다. 그 wc 는 입력을 read_line 으로 String 에 읽으며 셌고, 파일을 주지 않으면 표준 입력을 셌고, 읽지 못한 파일은 알리고 넘어가 종료 코드 1 로 끝났습니다. 이 장은 그 위에 올리는 2층입니다. 새로 하는 일은 다섯입니다 — 바이트 그대로 세어 글자 수까지 내기, 파일이 여럿일 때의 합계 줄, 찍을 칸을 고르는 옵션, 파일 이름을 담는 오류 타입, 그리고 라이브러리와 실행 파일로 나눈 패키지와 그 시험입니다. 아래 표는 그러느라 다시 쓰는 것과 그것을 배운 슬라이드입니다.

다 만들면 이렇게 돈다

마지막 단계의 패키지를 빌드해 돌린 화면입니다. 여기까지 가는 길을 여덟 단계로 나눠 걷습니다. 2부에서 본 대로 실행 파일은 target/debug/ 에 생기고, 화면은 그것을 직접 부릅니다. 입력 파일 data/sky.txt 는 한글 두 줄, data/todo.txt 는 줄바꿈 없이 끝나는 영문 두 줄, data/empty.txt 는 빈 파일입니다.

읽는 법 — cargo build -q 는 아무것도 찍지 않았습니다. 첫 실행은 파일마다 줄 · 낱말 · 바이트 수와 이름을 찍고, 파일이 둘 이상이라 total 줄을 붙였습니다. 빈 파일은 셋 다 0 입니다. -lwmc 를 준 실행에는 셋째 칸에 글자 수가 끼었습니다. 한글로 쓴 sky.txt 는 12 글자가 28 바이트이고, 영문으로 쓴 todo.txt 는 둘 다 14 입니다. 파일을 주지 않은 printf … | wc -m -c 는 표준 입력을 세어 이름 없이 5 글자 · 11 바이트를 찍었습니다. 그다음은 -w 로 낱말 수만 고르고, 없는 data/none.txt 를 끼운 실행입니다. 알림 한 줄을 내고 나머지를 마저 세어 합계 7 까지 찍은 뒤 종료 코드 1 로 끝났습니다. 알림 끝의 No such file or directory (os error 2) 는 17부에서 말한 대로 이 기계의 운영 체제가 준 글입니다. 모르는 옵션 -z 에는 쓰는 법을 알리고 종료 코드 2 입니다.
이 책의 wc 입니다 — 이름과 옵션 글자는 익숙한 명령에서 빌렸지만, 무엇을 줄 · 낱말 · 글자로 셀지와 칸의 모양은 이 장이 정합니다. 어느 기계의 wc 와 출력이 같다고 말하지 않습니다.

세는 함수는 바이트 슬라이스 하나만 받는다

17부의 count 는 읽을 곳을 받아, 읽으면서 셌습니다. 여기서는 읽기와 세기를 가릅니다. count 는 누군가 이미 읽어 둔 바이트를 &[u8] 로 받아 세기만 합니다. 첫 단계의 파일은 Cargo.toml 과 src/lib.rs 입니다.

읽는 법 — 줄 번호는 lib.rs 의 것입니다. 12번 줄은 바이트를 하나씩 보며 줄바꿈 b'\n' 과 같은 것만 남겨 셉니다. 클로저의 |&&b| 는 12부에서 본 참조 두 겹을 벗기는 패턴입니다. 14번부터 17번 줄까지는 슬라이스의 split 입니다. 18부에서 문자열의 split 에 클로저를 준 것처럼, 클로저가 참이라고 한 바이트마다 슬라이스를 쪼갭니다. 여기서 처음 쓰는 is_ascii_whitespace 는 그 바이트가 ASCII 공백인지를 답하는 u8 의 메서드입니다. 16번 줄이 빈 조각을 버리고 17번 줄이 남은 조각을 셉니다. 18번 줄은 슬라이스의 길이입니다.
이 프로그램의 정의 셋 — 줄 수는 줄바꿈 바이트의 수, 낱말 수는 ASCII 공백으로 갈라 남은 비지 않은 조각의 수, 바이트 수는 입력의 길이입니다. 다음 두 슬라이드가 이 정의를 시험으로 적어 둡니다.

정의를 시험으로 적어 둔다 — 줄바꿈 없이 끝난 줄은 세지 않는다

같은 lib.rs 의 아래쪽, 13부에서 본 시험 모듈입니다. 정의마다 시험 하나를 두었습니다. count 가 받는 것이 바이트 슬라이스라서 파일도 표준 입력도 필요 없습니다.

읽는 법 — 화면은 4개 통과입니다. 셋은 위에 보이고, 넷째는 다음 슬라이드에 있습니다. --lib 은 23부에서 본 라이브러리의 단위 시험만 돌리는 옵션입니다. 28번 줄은 줄바꿈이 둘이라 2 이고, 30번 줄이 줄 수의 정의에서 따라 나오는 일을 적어 둡니다. a\nb 는 눈으로는 두 줄이지만 줄바꿈 바이트가 하나라서 1 입니다. 31번 줄의 빈 입력은 0 입니다. 36번 줄은 앞뒤와 사이에 공백이 겹쳐 있어도 낱말이 셋임을, 38번 줄은 탭 · CR(\r) · 쪽 넘김(form feed, \x0c) 바이트에서도 갈라짐을, 39번 줄은 공백뿐인 입력에 낱말이 없음을 봅니다. 41번과 42번 줄은 split 만으로는 조각이 셋임을 보입니다. 빈칸 둘 사이에 빈 조각이 하나 끼기 때문이고, 앞 슬라이드에서 본 count 의 16번 줄이 그것을 버립니다. 47번 줄은 4 바이트이고, 48번 줄의 "가 나\n" 은 한글 둘이 3바이트씩이라 8 입니다.
b"…" 를 그대로 넘겼다 — 8부에서 본 대로 b"…" 의 타입은 배열의 참조 &[u8; N] 입니다. 6부에서 본 대로 &[T] 로 받는 함수에는 배열의 참조가 그대로 들어갑니다. 한글은 b"…" 안에 적을 수 없어서 as_bytes() 를 썼습니다.

낱말을 가르는 것은 ASCII 공백뿐이다 — 이 프로그램이 고른 것

8부의 split_whitespace 는 str 의 메서드입니다. count 가 받는 것은 글이 아니라 바이트이고, 바이트 하나하나에 ASCII 공백인지만 묻습니다. 그래서 ASCII 가 아닌 빈칸은 낱말을 가르지 않습니다. 넷째 시험이 그 차이를 한 군데에서 보입니다.

읽는 법 — 54번 줄의 \u{3000} 은 유니코드가 전각 빈칸(ideographic space)이라고 이름 붙인 글자입니다. ASCII 에는 없는 글자입니다. 55번 줄은 count 가 이 글을 낱말 하나로 셈을, 57번 줄은 같은 글을 split_whitespace 가 둘로 가름을 봅니다. 두 줄이 다 통과했습니다.
고른 까닭 — 줄과 낱말을 바이트만 보고 세면, 입력이 글로 읽히는지를 따지지 않고 셀 수 있습니다. 그 대신 전각 빈칸으로 띄운 글은 낱말 수가 split_whitespace 와 다르게 나옵니다. 어느 쪽이 옳다는 뜻이 아니라, 이 프로그램은 이렇게 정했다는 뜻입니다.

글자 수를 더한다 — 한글에서는 바이트 수와 갈린다

둘째 단계는 넷째 수를 더합니다. 8부에서 본 대로 한글 한 글자는 3바이트라서, 한글이 든 입력에서는 글자 수와 바이트 수가 다릅니다. 바이트를 글로 읽은 다음 chars() 로 셉니다. 앞 단계의 lib.rs 에 세 줄과 시험 둘을 더했습니다.

읽는 법 — 20번 줄의 String::from_utf8_lossy 는 처음 쓰는 함수입니다. 8부의 String::from_utf8 은 바이트를 검사해 Result 를 줬습니다. 이 함수는 Result 가 아니라 글을 바로 줍니다. 그 글의 char 를 센 것이 글자 수입니다. 66번 줄은 "가 나\n" 이 4 글자 · 8 바이트임을, 69번 줄은 ASCII 뿐인 "a b\n" 에서는 둘이 4 로 같음을 봅니다. 화면은 6개 통과입니다. 앞 단계의 넷에 이 시험과 다음 슬라이드의 시험이 더해졌습니다.
글자 — 여기서 글자는 char, 곧 3부에서 본 유니코드 스칼라 값 하나입니다. 화면에서 한 칸으로 보이는 것이 char 여럿일 수 있다는 것은 8부에서 봤습니다.

글로 읽히지 않는 바이트는 U+FFFD 로 바꿔 센다 — 이 프로그램이 고른 것

입력이 올바른 UTF-8 이 아닐 수도 있습니다. 17부에서 그런 파일을 String 으로 읽으면 실패하는 것을 봤습니다. 이 프로그램은 멈추지 않고 세기로 합니다. 그러려면 글이 아닌 바이트를 글자 몇 개로 칠지 정해야 합니다.

읽는 법 — 75번 줄의 입력은 ok 뒤에 UTF-8 이 될 수 없는 바이트 둘이 붙은 것이고, 글자 수는 2 에 2 를 더한 4 입니다. 깨진 바이트 하나가 한 글자로 세어졌습니다. 77번 줄은 가 의 세 바이트 가운데 앞의 둘만 잘라 냅니다. 78번 줄에서 그 두 바이트는 한 글자입니다. 79번과 80번 줄이 까닭을 보입니다. from_utf8_lossy 가 돌려준 글이 "\u{FFFD}", 곧 U+FFFD 한 글자와 같습니다. 유니코드가 대체 문자(replacement character)라고 이름 붙인 글자입니다.
이 프로그램의 정의 — 글자 수 — from_utf8_lossy 가 돌려준 글의 char 수입니다. 올바른 UTF-8 에서는 그 글의 글자 수이고, 위의 두 입력에서는 글로 읽히지 않는 자리가 U+FFFD 로 세어졌습니다. 다르게 정할 수도 있는 자리이고, 이 장은 이쪽을 골랐습니다.

일은 라이브러리의 run 이 한다 — 읽을 곳 하나와 쓸 곳 둘을 받는다

셋째 단계에서 프로그램이 처음 돕니다. 17부의 wc 는 main 이 표준 입력을 잡고 println! 과 eprintln! 으로 찍었습니다. 여기서는 그 몸통을 23부에서 한 것처럼 라이브러리의 run 으로 옮기되, 표준 입력 · 표준 출력 · 표준 오류까지 매개변수로 받습니다. lib.rs 의 count 와 시험 모듈 사이에 더한 함수입니다.

읽는 법 — 44번 줄의 Read 는 17부에서 본 읽는 쪽의 트레이트이고, 51번 줄의 read_to_end 는 거기서 쓴 read_to_string 의 바이트 쪽 짝입니다. 읽은 것을 String 이 아니라 Vec<u8> 에 담습니다. 그 슬라이드에서 본 대로 읽는 메서드는 읽을 곳을 가변으로 빌리므로 stdin 에 mut 를 붙였습니다. 57번 줄은 파일을 fs::read 로 통째로 읽습니다. 두 길 모두 읽은 바이트를 count 에 넘깁니다. 표준 입력을 센 53번 줄은 0 을 돌려줍니다. 62번부터 66번 줄까지가 읽지 못한 파일입니다. err 에 알리고 code 를 1 로 바꾼 뒤 반복을 계속합니다. 17부의 cat 과 같은 틀입니다. 파일 맨 위에는 이 함수가 쓰는 use std::fs; 와 use std::io::{self, Read, Write}; 를 더했습니다.
반환 타입 io::Result<u8> — Ok 에 든 수는 종료 코드입니다. 읽지 못한 파일은 Err 가 아니라 Ok(1) 로 끝납니다. Err 는 51번 줄의 읽기와 writeln! 뒤에 붙은 ? 에서만 나옵니다. 표준 입력을 읽거나 결과를 쓰는 일 자체가 실패한 때입니다. 입력을 통째로 읽어 두고 세는 것은 이 장이 고른 방식입니다. 조금씩 읽으며 세는 길은 더 해 볼 것에 남깁니다.

읽지 못한 파일은 알리고 넘어간다 — 결과는 표준 출력으로, 알림은 표준 오류로

세 파일 가운데 둘째가 없는 이름입니다. run 의 match 에서 Err 갈래가 도는 실행입니다. 같은 명령을 세 번 칩니다. 한 번은 그대로, 한 번은 표준 오류를 버리고, 한 번은 표준 출력을 버립니다.

읽는 법 — 옵션이 없는 첫 실행은 앞 단계와 같은 세 칸입니다. -l 은 줄 수만 남기고, 합계 줄도 한 칸입니다. -m -c 에서 글자 수가 처음 화면에 나왔습니다. sky.txt 는 12 글자에 28 바이트입니다. -cm 은 두 글자를 붙이고 순서도 뒤집었는데 화면은 같습니다. 옵션을 파일 뒤에 적은 data/sky.txt -w 도 받아들여 낱말 수 4 만 찍었습니다. 마지막 실행은 표준 입력에 네 칸을 다 켰습니다. 줄바꿈이 하나라 1, 낱말이 셋, 글자는 한글 셋에 빈칸과 줄바꿈을 더해 5, 바이트는 11 이고, 이름은 없습니다.

글이 아닌 바이트가 든 파일도 끝까지 센다

둘째 단계에서 시험으로 정해 둔 것을 실행 파일로 봅니다. 17부처럼 printf 로 UTF-8 이 아닌 바이트가 든 파일을 만듭니다. \377 처럼 적은 것은 8진수로 적은 바이트 하나입니다. 첫 줄에는 \377\376 을, 둘째 줄에는 가 와 그 세 바이트 가운데 앞의 둘(\352\260)을 넣습니다.

읽는 법 — od -An -tx1 은 이 기계의 명령으로, 파일의 바이트를 16진수로 한 줄에 적어 줍니다. 열두 바이트이고 ff fe 와 끝쪽의 ea b0 가 글이 되지 못하는 자리입니다. wc 는 멈추지 않고 2 줄 · 3 낱말 · 9 글자 · 12 바이트를 찍었습니다. 글자 9 는 첫 줄의 o k 빈칸 셋, 깨진 바이트 둘이 바뀐 둘, 줄바꿈 하나, 둘째 줄의 가 하나, 잘린 두 바이트가 바뀐 하나, 줄바꿈 하나입니다. 낱말 3 은 ok, 깨진 두 바이트, 그리고 가 에 잘린 두 바이트가 붙은 것입니다. 마지막 실행은 첫 단계의 전각 빈칸(\343\200\200)입니다. 가 와 나 사이를 띄웠는데 낱말은 1 이고, 글자는 줄바꿈까지 4 입니다.

파일 이름을 담는 오류 타입 — WcError

지금까지는 run 이 fs::read 를 직접 부르고, 손에 쥔 path 를 알림에 붙였습니다. 여섯째 단계는 "파일 하나를 읽어 센다" 를 라이브러리의 함수 count_file 로 내놓습니다. 그 함수의 오류는 누가 받든 어느 파일인지 알 수 있어야 합니다. 17부에서 글로 바꿔 붙이면 kind() 를 잃는다는 것을 봤으므로, ToolError 처럼 io::Error 를 값 그대로 담습니다.

읽는 법 — 실패의 종류가 하나뿐이라 열거형이 아니라 구조체입니다. 117번 줄의 Display 가 이름: 까닭 모양의 글을 만듭니다. 121번 줄은 9부에서처럼 본문 없는 impl Error 이고, 그것이 Debug 를 요구해서 109번 줄이 있습니다. 125번 줄의 map_err 가 io::Error 를 받아, path 를 곁에 넣은 WcError 로 바꿉니다. 128번 줄의 ? 는 그 WcError 를 그대로 들고 돌아갑니다. 읽혔으면 129번 줄이 세어 돌려줍니다. 파일 맨 위에는 use std::fmt; 한 줄을 더했습니다.
From 을 구현하지 않은 까닭 — 17부에서 본 대로 from 이 받는 것은 오류 하나뿐이라 파일 이름을 넣을 자리가 없습니다. 그래서 이름을 아는 count_file 이 map_err 로 만듭니다.

run 에서 달라진 것은 세 줄이다 — 알림의 글은 그대로다

run 의 반복문이 fs::read 대신 count_file 을 부릅니다. 읽지 못한 파일을 알리고 넘어가는 결정은 여전히 run 에 있습니다. count_file 은 실패를 돌려줄 뿐이고, 그것으로 멈출지 계속할지는 부른 쪽이 정합니다.

읽는 법 — 159번과 160번 줄이, fs::read 로 읽고 count 를 부르던 앞 단계의 세 줄을 대신합니다. 166번 줄에서는 {path}: 가 빠졌습니다. 이름은 이제 {e} 가 부르는 Display 가 붙입니다. 첫 실행의 알림은 셋째 단계의 화면과 글자까지 같습니다. 둘째 실행은 파일 자리에 디렉터리 data 를 주었습니다. 운영 체제가 준 까닭은 Is a directory (os error 21) 로 다르지만 알림의 모양은 같고, 다음 파일을 마저 세어 종료 코드 1 입니다.
돌려주는 쪽과 정하는 쪽 — 라이브러리의 count_file 은 ? 로 실패를 올려 보내기만 합니다. 알리고 계속 가는 것, 그리고 종료 코드에 남기는 것은 run 의 Err 갈래가 합니다.

오류가 값이라서 시험이 종류를 묻는다

WcError 가 io::Error 를 글로 바꾸지 않고 담았으므로, 받은 쪽은 이름도 종류도 꺼내 볼 수 있습니다. 같은 단계의 시험 모듈에 더한 시험이 그 둘을 봅니다.

읽는 법 — 279번 줄의 let … else 는 Err 일 때 그 속을 꺼냅니다. else 갈래는 없는 파일이 읽혔을 때만 도는 자리이고, 이 화면에서는 돌지 않았습니다. 282번 줄이 이름을, 283번 줄이 17부에서 본 kind() 가 NotFound 임을 봅니다. 284번 줄은 Display 가 만든 글이 이름으로 시작하는지만 봅니다. 그 뒤의 까닭은 운영 체제가 정하는 글이라 견주지 않습니다. 화면은 11개 통과입니다. 앞 단계의 열에 이 시험이 더해졌습니다.

run 을 프로세스 없이 부른다 — 표준 입력은 &[u8], 표준 출력은 Vec<u8>

일곱째 단계부터는 시험만 더합니다. run 이 읽을 곳과 쓸 곳을 매개변수로 받게 한 까닭이 여기서 나옵니다. 17부에서 본 대로 &[u8] 는 읽을 곳이고 Vec<u8> 는 쓸 곳입니다. 13부의 통합 시험 파일 tests/run.rs 가 실행 파일을 띄우지 않고 wc::run 을 부릅니다.

읽는 법 — 도우미 run_wc 는 인자와 표준 입력에 넣을 글을 받아, 종료 코드와 두 쓸 곳에 쓰인 글을 돌려줍니다. 9번 줄의 stdin.as_bytes() 가 표준 입력 자리에, 6번과 7번 줄의 두 벡터가 표준 출력과 표준 오류 자리에 들어갑니다. 17번 줄은 인자 없이 "a b\nc" 를 넣고, 18번 줄이 종료 코드 0 과 이름 없는 한 줄을, 19번 줄이 빈 표준 오류를 봅니다. 24번 줄은 옵션을 -m -l 차례로 주는데 25번 줄이 기대하는 줄은 줄 수 1 이 먼저입니다. 30번 줄의 모르는 옵션에서는 종료 코드가 2 이고 표준 출력이 비었으며, 표준 오류는 두 줄입니다. --test run 은 23부에서 본 시험 파일 하나를 고르는 옵션이고, 화면은 4개 통과입니다. 넷째 시험은 다음 슬라이드에 있습니다.
unwrap 셋 — 9번 줄의 unwrap 은 run 이 Err 를 돌려주면 패닉해서 시험을 실패로 만듭니다. 10번과 11번 줄은 벡터의 바이트를 String::from_utf8 로 글로 되돌립니다. 시험에서는 예상 밖의 값이 곧 실패여야 하므로 unwrap 을 씁니다. src/ 에서 unwrap 을 쓰는 곳은 시험 모듈뿐입니다.

패키지에 든 입력 파일로 시험한다 — 운영 체제의 글은 견주지 않는다

같은 tests/run.rs 의 넷째 시험은 파일을 실제로 읽습니다. 있는 파일 둘 사이에 없는 이름을 끼워, 나머지가 세어지고 합계가 나오고 종료 코드가 1 인지를 한 번에 봅니다.

읽는 법 — 37번 줄의 이름은 data/… 로 시작하는 상대 경로입니다. 시험이 통과했으니 두 파일이 그 이름으로 읽혔습니다. 이 화면에서 cargo test 를 친 곳이 패키지의 뿌리입니다. 40번부터 45번 줄까지는 기대하는 세 줄을 8부의 concat 으로 이어 붙입니다. todo.txt 를 먼저 주었으므로 그 줄이 먼저이고, 합계는 읽은 둘의 3 · 7 · 42 입니다. 48번 줄은 표준 오류가 wc: data/none.txt: 로 시작하는지만 봅니다.
기계마다 다른 글은 시험에 적지 않는다 — No such file or directory (os error 2) 는 운영 체제가 정하는 글입니다. 그대로 견주면 그 글이 달라지는 곳에서 시험이 깨집니다. 17부의 "글로 견주지 않는다" 를 시험에도 지킵니다.

b"…" 는 표준 입력 자리에 그대로 들어가지 않는다 — E0277

첫 단계의 시험은 count 에 b"…" 를 그대로 넘겼습니다. run 에도 그렇게 해 봅니다. tests/run.rs 끝에 시험 하나를 더한 쌍둥이 디렉터리입니다.

읽는 법 — 10부에서 본 E0277 과 같은 꼴입니다. 오류 첫 줄은 "&[u8; 4] 가 Read 를 구현하지 않는다" 이고, 55번 줄의 b"a b\n" 을 짚습니다. 같은 줄의 wc::run 아래에는 "이 호출이 들여온 조건이 요구한다" 가 붙었습니다. 첫 help: 는 Read 를 구현하는 것이 &[u8] 라고 알려 줍니다. 그 아래 /rustc/… 로 시작하는 줄은 이 툴체인의 표준 라이브러리 소스에서 그 구현이 있는 자리입니다. note: 는 그 조건이 src/lib.rs 136번 줄, 곧 run 의 mut stdin: impl Read 에서 왔다고 짚습니다. 마지막 help: 가 고친 줄을 보여 줍니다. For more information 줄은 2부에서 본 --explain 안내입니다. 끝의 error: could not compile 줄은 Cargo 가 덧붙인 것이고 종료 코드는 101 입니다. 그대로 고친 쌍둥이는 5개 통과입니다. 더한 시험의 56번과 57번 줄, 곧 종료 코드 0 과 벡터에 쓰인 한 줄도 맞았다는 뜻입니다.
count 에서는 됐던 까닭 — count 의 매개변수는 타입이 &[u8] 로 정해져 있어서 배열의 참조가 슬라이스로 바뀌어 들어갔습니다. run 의 impl Read 는 10부에서 본 트레이트 바운드를 짧게 쓴 것입니다. 오류 첫 줄에 적힌 대로, 넘긴 값의 타입 &[u8; 4] 그대로 Read 인지를 물었습니다. [..] 는 6부에서 본 전체 구간입니다. 도우미가 쓴 as_bytes() 는 처음부터 &[u8] 를 줍니다.

실행 파일을 띄워 종료 코드까지 본다 — tests/cli.rs

tests/run.rs 의 시험은 main.rs 를 거치지 않습니다. run 이 돌려준 수가 정말 종료 코드가 되는지, 두 쓸 곳이 정말 표준 출력과 표준 오류인지는 실행 파일을 돌려야 보입니다. 여덟째 단계는 23부에서 본 CARGO_BIN_EXE_… 로 실행 파일의 경로를 얻어, 18부의 Command 와 output 으로 띄웁니다.

읽는 법 — 4번 줄의 EXE 가 실행 파일의 경로입니다. 9번 줄은 -l 과 있는 파일 하나, 없는 이름 하나를 인자로 줍니다. 12번 줄이 종료 코드 1 을, 14번 줄이 표준 출력의 두 줄을, 16번 줄이 표준 오류가 알림으로 시작하는지를 봅니다. 21번 줄은 모르는 옵션 하나만 줍니다. 22번부터 25번 줄까지가 종료 코드 2, 빈 표준 출력, 쓰는 법까지 두 줄인 표준 오류를 봅니다. 25번 줄은 라이브러리의 상수 wc::USAGE 로 기대하는 글을 만듭니다. 화면은 2개 통과입니다.

칸의 폭이나 차례를 건드리면 출력의 모든 줄이 달라집니다. 그런 변화를 한 번에 잡으려고, 23부에서 본 기준 파일을 하나 둡니다. 입력 파일 셋에 네 칸을 다 켠 출력입니다.

두지 않은 것 — 23부의 시험에는 기준 파일을 새로 쓰는 스위치가 있었습니다. 이 시험에는 없습니다. 더 해 볼 것에 남깁니다.

cargo test 한 번에 여섯 묶음, 시험 열여덟

옵션 없이 cargo test -q 를 치면 13부에서 본 대로 묶음이 차례로 돕니다. 이 패키지에는 라이브러리, 실행 파일, tests/ 의 파일 셋, 문서 시험까지 여섯 묶음이 있습니다.

읽는 법 — 첫 묶음 11개는 lib.rs 의 단위 시험입니다. 여섯째 단계의 11개 통과와 같은 수입니다. 둘째 묶음은 main.rs 이고, 시험이 없어 0 입니다. 그다음 2 · 1 · 4 는 파일마다 따로 돌렸을 때의 수 그대로 cli.rs · golden.rs · run.rs 입니다. 마지막 0 은 문서 시험입니다. 통과한 시험은 모두 18 이고 실패는 없습니다.

퀴즈 — 화면을 미리 적어 보기

Q. 이 장의 wc 입니다. ./target/debug/wc 를 wc 로 줄여 적습니다. ① printf '가 나\n다' | wc -lwmc 는 수 넷을 찍습니다. 차례로 얼마이고, 줄 끝에 이름이 붙습니까? ② wc -w data/sky.txt data/none.txt data/todo.txt 에서 data/none.txt 만 없는 파일입니다. 표준 출력에는 몇 줄이 나오고, 마지막 줄의 수는 얼마이며, 종료 코드는 몇입니까? sky.txt 는 낱말이 넷, todo.txt 는 셋입니다.

A. ① 1 · 3 · 5 · 11 이고 이름은 없습니다. 줄바꿈 바이트가 하나라 줄 수는 1 입니다. 마지막의 다 는 줄바꿈 없이 끝났지만 낱말로는 셉니다. 글자는 한글 셋에 빈칸과 줄바꿈을 더해 5, 바이트는 한글이 3바이트씩이라 11 입니다. 표준 입력을 셀 때는 이름 칸이 없습니다. 다섯째 단계에서 이 명령을 그대로 돌린 화면이 옵션을 주고 돌려 본다의 마지막 실행입니다. ② 표준 출력에는 세 줄입니다. sky.txt 의 4, todo.txt 의 3, 그리고 total 의 7 입니다. 없는 파일의 알림은 표준 오류로 가고, 읽은 둘만 합계에 듭니다. 읽지 못한 것이 있으므로 종료 코드는 1 입니다. 이 명령을 그대로 돌린 화면이 다 만들면 이렇게 돈다에 있습니다. 알림이 표준 출력이 아니라 표준 오류로 간다는 것은 한 길씩 버려 본 화면이 보입니다.

더 해 볼 것

마지막 단계의 패키지를 복사해 놓고 고쳐 보는 과제입니다. 풀이는 싣지 않았습니다. 과제마다 손댈 파일과 함수를 적었고, 고치기 전에 시험부터 더하면 무엇을 만들지가 분명해집니다.

  • - 를 표준 입력으로 — 지금은 - 하나가 파일 이름으로 남습니다. lib.rs 의 run 에서 이름이 - 인 차례에 stdin 을 세게 합니다. - 를 두 번 주면 어떻게 할지도 정해야 합니다.
  • -- 뒤는 모두 파일 이름 — parse_args 에서 -- 를 만난 뒤로는 - 로 시작하는 인자도 paths 에 넣습니다. 시험은 lib.rs 의 시험 모듈에 더합니다.
  • 가장 긴 줄의 길이를 찍는 옵션 — Counts 와 count, Config 와 parse_args, format_row 에 칸 하나를 더합니다. 합계 줄에서 이 칸을 어떻게 할지는 Counts::add 에서 정합니다.
  • 조금씩 읽으며 세기 — count_file 과 run 은 입력을 통째로 읽어 둡니다. count 를 여러 번에 나눠 부를 수 있는 모양으로 바꿉니다. 낱말 하나나 한글 한 글자가 두 조각에 걸쳤을 때의 수를 시험으로 먼저 적습니다.
  • 칸의 폭을 가장 큰 수에 맞추기 — 폭 5 를 넘는 수가 나오는 입력을 만들어 지금의 줄 모양을 먼저 봅니다. 그다음 run 이 줄을 모아 두었다가 format_row 에 폭을 넘기게 합니다. tests/golden.rs 의 시험이 어떻게 되는지도 봅니다.
  • 기준 파일을 새로 쓰는 스위치 — tests/golden.rs 에 23부의 스위치를 답니다.
  • 쓰기가 실패하는 시험 — tests/run.rs 에 Write 를 구현하되 늘 Err 를 돌려주는 타입을 만들어 out 자리에 넣고, run 이 Err 를 돌려주는지 봅니다.
  • 실행 파일의 표준 입력에 쓰는 시험 — tests/cli.rs 에 18부의 자식의 표준 입력에 쓰기로, 인자 없이 띄운 wc 에 글을 먹이는 시험을 더합니다.
