이 부에서 할 일

3부에서 정수와 실수를, 8부에서 벡터와 맵을, 10부에서 트레이트와 derive 를, 12부에서 정렬을 봤습니다. 그때는 문법을 익히는 데 필요한 만큼만 썼습니다. 이 부는 표준 라이브러리에서 자주 손이 가는 도구를 더 꺼냅니다. 새 문법은 없습니다. 슬라이드마다 작은 문제 하나에서 시작해, 도구를 쓰고, 출력을 읽습니다. 장마다 끝에 "하려는 일 → 쓸 것" 표가 있습니다.

  • 1장 — 수 더 깊이: 비트 연산과 밀기, 비트 세기, 큰 정수, 진법과 바이트, 실수의 비트
  • 2장 — 비교와 정렬: Ordering, 여러 기준, 안정 정렬, 정렬된 곳에서 찾기
  • 3장 — 해시와 맵 더: 키의 규칙, entry 의 여러 길, 지우기와 고치기, 범위로 찾기
  • 4장 — 시간: 시간의 길이 Duration, 걸린 시간과 마감, 지금 시각
  • 5장 — 프로세스와 환경: 환경 변수 읽기, 다른 프로그램 돌리기, 종료 상태와 출력 받기, 자식의 인자 · 환경 · 표준 입력
  • 6장 — 그 밖의 도구: 타입의 크기와 배치, 타입 이름, Option · Result · 반복자 · 문자열과 글자의 남은 도구
이 부의 화면 — 실행할 때마다 달라질 수 있는 것은 찍지 않습니다. HashMap 의 항목은 정렬하거나 키를 짚어 꺼내서 찍고, 해시 값은 같은지만 찍습니다. 4장은 잰 시간과 지금 시각 가운데 실행마다 달라지는 값을 찍지 않고 견준 결과를 찍습니다. 5장은 환경 변수 가운데 예제가 이름을 짚은 것만 찍습니다. 자식 프로세스는 부모가 끝나기를 기다리거나 출력을 모아 받으므로 줄의 순서가 늘 같습니다. 5장은 이 책을 만든 기계의 셸과, 그 기계에 있는 echo · sh · printf 를 씁니다. 5장 말고는 파일도 표준 입력도 쓰지 않고, 5장 밖에서 명령 줄 인자를 받는 예제는 하나뿐입니다.

1장

수 더 깊이

비트 연산자 · 밀기와 돌리기 · 밀 수 있는 칸 수 · 플래그 · 비트 세기 · pow 와 u128 · rem_euclid · abs_diff 와 isqrt · 진법을 정해 읽기 · 수와 바이트 · 실수의 비트 · 실수의 도우미

비트 연산자 & | ^ ! — 자리마다 따로 셈한다

한 주 가운데 나오는 요일을 수 하나에 담습니다. 비트(bit) 하나가 요일 하나이고, 켜져 있으면(1) 나오는 날입니다. 두 사람이 함께 나오는 날, 한 사람이라도 나오는 날은 비트 연산자(bitwise operator)가 한 번에 구합니다. 10부의 연산자 표가 이름만 적어 둔 연산자들이고, 이제 돌려 봅니다. 값은 2부에서 본 {:08b} 로 찍어 비트를 봅니다.

읽는 법 — 12번 줄의 kim & lee 가 찍은 00010100 은 kim 과 lee 가 모두 1 인 자리(수 · 금)만 1 입니다. 13번 줄의 | 는 어느 한쪽이라도 1 인 자리를 켜서 00011101 이고, 15번 줄의 ^ 는 한쪽만 1 인 자리(월 · 목)를 켜서 00001001 입니다.
! 는 안 쓰는 자리도 뒤집는다 — 4부에서 bool 을 뒤집던 ! 가 정수에서는 비트를 모두 뒤집습니다. 16번 줄의 !kim 은 11101010 입니다. 요일로 쓰지 않는 맨 왼쪽 비트까지 켜졌습니다.

<< 와 >> 는 밀고, rotate_left 는 돌린다

비트를 통째로 옆으로 옮기는 연산자가 밀기(shift) << 와 >> 입니다. 오른쪽에 적는 수가 옮길 칸 수입니다. 수 하나에 나란히 담아 둔 값에서 한 토막을 꺼낼 때 쓰고, 그 쓰임은 색상 코드에서 봅니다. 먼저 밀려서 밖으로 나간 비트가 어떻게 되는지, 빈 자리에 무엇이 들어오는지를 봅니다.

읽는 법 — 5번 줄의 x << 2 는 01011000 입니다. 왼쪽 끝에 있던 10 이 사라졌고 오른쪽 두 자리는 0 입니다. 패닉은 없었습니다. 8번 줄의 rotate_left(2) 는 01011010 으로, 사라졌던 10 이 오른쪽 끝으로 돌아왔습니다. 10번 줄에서는 5 를 한 칸 밀어 10, 20 을 두 칸 밀어 5 가 됐습니다.
>> 가 채우는 값은 타입에 달렸다 — 15번 줄은 i8 값 -8(11111000)을 밀어 11111100, 곧 -4 를 냈습니다. 빈 자리에 1 이 들어왔습니다. 17번 줄은 같은 비트를 as u8 로 읽었고, 18번 줄에서 밀자 빈 자리에 0 이 들어와 124 입니다. 비트는 같고 타입만 다릅니다.

비트 수만큼은 밀 수 없다 — 적어 둔 칸 수는 컴파일 오류, 받은 칸 수는 패닉

u8 은 8 비트입니다. 8 칸을 밀라고 소스에 적으면 컴파일러가 막습니다. 3부의 범위를 넘는 리터럴처럼 번호가 없는 오류입니다.

읽는 법 — 오류 첫 줄은 "이 산술 연산은 넘친다" 입니다. 4번 줄의 one << 8 에 "8_i32 만큼 왼쪽으로 밀려 하는데, 넘친다" 가 붙었습니다. = note: 의 arithmetic_overflow 가 이 검사의 이름입니다. 3부의 화면처럼 #[deny(…)] 로 적혀 있으니, 그때 본 대로 경고와 같은 종류의 검사인데 기본이 오류인 것입니다. 그래서 error[E…] 번호가 없습니다.
받은 칸 수에는 checked_shl — 칸 수가 실행 중에 들어오면 컴파일은 됩니다. 12번 줄의 << 는 attempt to shift left with overflow 로 패닉했습니다. 3부의 넘침 패닉과 같은 꼴이고 종료 코드도 101 입니다. 10번 줄의 checked_shl(8) 은 같은 칸 수에 None 을 돌려줬습니다. 3부에서 고른 checked_add 와 같은 식구입니다.

수 하나에 스위치 여럿 — 켜기 · 끄기 · 묻기 · 뒤집기

읽기 · 쓰기 · 실행 권한처럼 켜고 끄는 값 여럿을 정수 하나에 담습니다. 이렇게 쓰는 비트를 플래그(flag)라고 합니다. 3부의 const 로 비트마다 이름을 붙여 두고, 앞에서 본 네 연산자로 다룹니다.

  • 묻기 — 7번 줄의 perm & READ != 0 은 그 비트만 남긴 값이 0 이 아닌지 봅니다. 괄호 없이 적었는데 & 가 먼저 묶여, 화면의 true · false 가 왼쪽의 비트와 맞습니다.
  • 켜기 — 19번 줄의 |= 로 001 이 111 이 됐습니다. |= 는 += 처럼 셈과 대입을 한 번에 적은 것입니다.
  • 끄기 — 22번 줄의 !WRITE 는 쓰기 비트만 0 인 값입니다. 그것과 & 해서 101 이 됐습니다.
  • 뒤집기 — 25번과 27번 줄의 ^= EXEC 두 번에 101 이 001 로 갔다가 101 로 돌아왔습니다.

비트를 세면 답이 나오는 물음 — count_ones · trailing_zeros · leading_zeros

3부의 정수의 메서드에서 같은 값 0b0010_1100 에 세 메서드를 불러 3 · 2 · 2 를 봤습니다. 이번에는 그 수가 무엇에 쓰이는지입니다. 비트가 요일이면 세 메서드는 며칠 나왔는지, 처음 나온 날과 마지막으로 나온 날이 언제인지에 답합니다.

읽는 법 — 6번 줄의 count_ones 가 켜진 비트 셋을 셌습니다. 8번 줄의 trailing_zeros 는 오른쪽에 이어진 0 이 둘이라고 했고, 그것이 처음 켜진 비트의 번호 2(수요일)입니다. 10번 줄은 비트 수 u8::BITS 에서 1 과 leading_zeros 의 2 를 빼 5(토요일)를 얻었습니다. 13번과 14번 줄의 is_power_of_two 는 비트 셋이 켜진 값에 false, 하나만 켜진 0b0010_0000 에 true 입니다.
0 은 따로 본다 — 16번 줄에서 0 의 trailing_zeros 는 8, 곧 u8 의 비트 수입니다. 0번부터 7번까지인 비트 번호를 벗어난 수입니다. "처음 켜진 비트" 로 쓰려면 값이 0 인지를 먼저 봅니다.

2 의 64 제곱은 u64 에 없다 — u128 과 i128

체스판 첫 칸에 쌀 한 알을 놓고 다음 칸마다 두 배씩 놓습니다. 64번째 칸의 쌀알은 2 의 63 제곱이고, 3부에서 본 pow 로 셉니다. 판 전체의 합은 2 의 64 제곱에서 1 을 뺀 수인데, 2 의 64 제곱부터는 u64 에 들어가지 않습니다.

읽는 법 — 7번 줄의 checked_pow(64) 는 None 입니다. 3부의 checked_add 가 넘침을 알리던 방식 그대로입니다. 9번 줄은 같은 셈을 u128 로 해서 값을 얻었고, 11번 줄에서 1 을 뺀 합은 5번 줄이 찍은 u64::MAX 와 같은 수입니다.
가장 넓은 정수 — 3부의 정수 타입 표에 있던 128 비트 타입입니다. u128::MAX 는 서른아홉 자리 수입니다. 접미사 _u128, 메서드, MAX 와 MIN 을 이 예제는 다른 정수 타입에서와 같은 모양으로 썼습니다. 17번 줄의 big as u64 도 좁히는 as 답게 아래 64 비트만 남겨 7 입니다.

돌아가는 번호에는 rem_euclid — 음수에서도 0 이상

3부에서 % 는 왼쪽의 부호를 따른다고 봤고, 늘 0 이상인 나머지가 필요하면 rem_euclid 를 쓴다고 했습니다. 그 "필요한 때" 가 요일입니다. 요일을 0(월)부터 6(일)까지의 번호로 두고 며칠 뒤와 며칠 전을 구합니다.

읽는 법 — 7번 줄은 5 5 입니다. 왼쪽이 양수인 12 에서는 둘이 같습니다. 10번 줄에서는 before 가 -3 이고 % 는 -3 을, rem_euclid 는 4 를 냈습니다. 11번 줄이 그 4 를 인덱스로 써서 12번 줄이 금요일을 찍었습니다.
짝이 되는 몫 — 16번 줄은 0 × 7 + -3, 18번 줄은 -1 × 7 + 4 이고 둘 다 -3 으로 돌아갑니다. / 의 몫은 % 의 나머지와, div_euclid 의 몫은 rem_euclid 의 나머지와 맞춰 씁니다.

abs_diff 와 isqrt — 넘치는 뺄셈도, 실수도 거치지 않는다

3부의 정수의 메서드에서 이름과 결과만 본 둘입니다(abs_diff 는 , isqrt 는 부터). 손으로 적으면 돌아가게 되는 길을 둘 다 건너뜁니다. abs_diff 는 넘칠 수 있는 뺄셈을, isqrt 는 실수로 바꿨다가 되돌리는 길을 피합니다.

읽는 법 — 5번 줄의 checked_sub 는 None 입니다. 3 에서 10 을 뺀 값은 u32 에 없습니다. 6번 줄의 abs_diff 는 어느 쪽에서 불러도 7 입니다. 8번 줄에서 i32 의 두 끝 사이는 4294967295 로, i32 에 들어가지 않는 수입니다. d 의 타입 표기 u32 가 그대로 컴파일됐으니 i32 의 abs_diff 는 u32 를 돌려준 것입니다.
f64 를 거친 제곱근 — 14번 줄의 isqrt 는 4294967295 를, 17번 줄의 (n as f64).sqrt() as u64 는 그보다 하나 큰 수를 냈습니다. 19번 줄에서 그 수를 제곱하면 u64 를 넘으므로 n 의 제곱근일 수 없습니다. 16번 줄이 까닭을 보여 줍니다. n as f64 가 이미 n 과 다른 수입니다.

from_str_radix — 진법을 정해 글을 수로 읽는다

3부의 parse 가 읽은 글은 모두 10진수였습니다. 색상 코드 ff8800 처럼 16진수로 적힌 글은 from_str_radix 로 읽습니다. 둘째 인자가 진법(radix)입니다. 찍을 때 진법을 고르던 {:x} 의 반대 방향입니다.

읽는 법 — 3번 줄이 읽은 값은 16746496 이고, 4번 줄에서 {:#08x} 로 찍으니 다시 0xff8800 입니다. 6번과 7번 줄은 밀기로 원하는 두 자리를 오른쪽 끝에 놓고 & 0xff 로 아래 8 비트만 남겼습니다. 이렇게 남길 자리만 켜 둔 값을 마스크(mask)라고 합니다. 파랑은 이미 끝에 있어 8번 줄은 밀지 않았습니다. 12번과 13번 줄은 2진수와 36진수를 읽었습니다.
읽지 못하는 글 — 15번 줄의 12 와 18번 줄의 0xff 는 InvalidDigit 입니다. 앞의 글에는 2진수에 없는 숫자 2 가, 뒤의 글에는 16진수의 숫자가 아닌 x 가 들어 있습니다. 16번 줄의 100 은 16진수로 256 이라 u8 에 넘칩니다. 3부의 parse 가 낸 것과 같은 Err 들입니다. 20번 줄에서 parse 는 ff 를 읽지 못했습니다.

수를 바이트로, 바이트를 수로 — 순서를 정해야 한다

17부에서 파일에 든 것은 바이트라고 했습니다. u32 하나를 파일에 쓰려면 바이트 넷으로 나눠야 하고, 어느 바이트를 먼저 쓸지 정해야 합니다. 큰 자리부터 쓰는 순서가 빅 엔디언(big-endian), 작은 자리부터 쓰는 순서가 리틀 엔디언(little-endian)입니다. 메서드 이름의 be 와 le 가 그것입니다.

읽는 법 — 6번 줄의 [12, 34, 56, 78] 은 0x1234_5678 을 적힌 순서대로 나눈 것이고, 7번 줄은 그 반대입니다. {be:02x?} 는 {:?} 로 찍되 원소를 폭 2 의 16진수로 찍습니다. 9번과 10번 줄처럼 쓴 순서로 읽으면 원래 수가 나옵니다. 12번 줄은 be 로 나눈 바이트를 le 로 읽어 0x78563412 를 얻었습니다.
슬라이스에서 배열로 — from_be_bytes 는 [u8; 4] 를 받습니다. 16번 줄은 슬라이스 data[..4] 를 3부의 try_into 로 배열로 바꾸고 unwrap 으로 꺼냈습니다. 17번 줄이 그 네 바이트 0, 0, 1, 2 를 258 로 읽었습니다.

to_bits — 실수의 비트를 들여다본다

3부에서 0.1 + 0.2 는 0.3 과 == 로 같지 않았고, 차이는 10 의 -17 제곱쯤이었습니다. f64::to_bits 는 실수의 64 비트를 u64 로 줍니다. 두 값이 비트로는 얼마나 다른지 봅니다.

읽는 법 — 4번과 5번 줄의 두 값은 16진수 맨 앞 자리만 3 과 b 로 다릅니다. 8번 줄이 맨 왼쪽 비트를 꺼내 보니 1.0 은 0, -1.0 은 1 입니다. 13번과 14번 줄은 끝자리만 4 와 3 으로 다르고, 15번 줄이 두 u64 의 차이를 1 로 찍었습니다.
비트에서 실수로 — 17번 줄의 f64::from_bits 는 반대 방향입니다. 0.3 의 비트에 1 을 더해 만든 실수가 0.30000000000000004 로 찍혔고, 18번 줄에서 sum 과 == 로 같았습니다.

실수의 도우미 — hypot · rem_euclid · clamp · signum

3부에서 실수의 반올림 넷과 sqrt · powi 를 봤습니다. 손으로 적다가 틀리기 쉬운 셈 넷을 더 봅니다. 두 점 사이의 거리, 한 바퀴 안으로 접은 각도, 구간에 가둔 값, 부호입니다.

  • hypot — 4번 줄의 식과 5번 줄의 hypot 은 이 실행에서 둘 다 5 를 찍었습니다. 같은 삼각형을 2 의 600 제곱 배로 키우면 10번 줄의 bx * bx 가 inf 가 되어 11번 줄의 식도 inf 입니다. 12번 줄의 hypot 은 inf 가 아닌 값을 냈고, 이 실행에서는 5 입니다.
  • rem_euclid — -90 도에 % 는 -90, rem_euclid 는 270 입니다. 정수에서 본 차이와 같습니다.

Reverse — 키를 감싸 순서를 뒤집는다

점수가 높은 사람부터, 점수가 같으면 이름순으로 세우려 합니다. 12부에서는 sort_by 안에서 b 를 앞에 적어 내림차순을 만들었습니다. sort_by_key 에서는 키를 std::cmp::Reverse 로 감쌉니다. 8부에서 BinaryHeap 이 작은 것부터 내놓게 할 때 쓴 포장입니다.

읽는 법 — 7번 줄의 정렬 뒤에 92 점이 맨 앞이고, 85 점 둘은 park · lee 로 적혀 있던 순서 그대로입니다. 10번 줄은 키가 튜플 (Reverse(score), name) 입니다. 튜플은 앞 칸부터 견주므로 점수는 내림차순이고, 점수가 같은 둘은 이름순 lee · park 로 바뀌었습니다. 14번 줄에서 1 < 2 는 참인데 Reverse(1) < Reverse(2) 는 거짓입니다.
뒤집을 칸만 감싼다 — 기준마다 방향이 다르면 10번 줄처럼 튜플 키에서 내림차순인 칸만 Reverse 로 감쌉니다. 속의 값은 17번 줄처럼 .0 으로 꺼냅니다. 16번 줄은 Reverse 로 감싼 점수의 min 으로 가장 높은 92 를 골랐습니다.

min · max · clamp — 둘 가운데 고르고, 구간에 가둔다

3부에서 정수에 a.min(b) 와 a.max(b) 를 불렀습니다. 수가 아닌 값에도 같은 메서드를 부를 수 있고, std::cmp 에는 같은 이름의 함수도 있습니다. clamp( 부터)는 값을 아래 끝과 위 끝 사이에 가둡니다.

읽는 법 — 5번 줄의 메서드와 6번 줄의 함수는 같은 답 3 8 을 냈습니다. 8번 줄은 문자열과 튜플에서 작은 쪽 apple 과 큰 쪽 (1, 'b') 를 골랐습니다. 12번 줄의 clamp 는 -5 를 0 으로, 130 을 100 으로 끌어오고 40 은 그대로 뒀습니다. 15번 줄처럼 max 와 min 을 이어 적어도 130 은 100 이 됩니다. 17번 줄은 문자에 clamp 를 불렀습니다.
여럿 가운데, 그리고 실수 — 반복자가 내는 값 가운데 가장 작은 것과 큰 것은 12부의 min · max 와 min_by_key · max_by 가 고릅니다. 실수의 clamp 는 1장에서 봤습니다.

derive 가 정하는 순서 — 열거형은 변형을 적은 순서대로

10부에서 derive(PartialOrd, Ord) 는 필드를 적은 순서대로 견준다고 봤습니다. 열거형에 붙이면 변형을 적은 순서가 작은 것부터의 순서가 됩니다. 할 일에 우선순위를 달아 정렬합니다.

읽는 법 — 17번 줄에서 Low < High 는 참이고, 18번 줄에서 Mid 를 High 와 견주면 Less 입니다. 4번부터 6번 줄까지에 적은 순서입니다. 27번 줄의 sort() 뒤에는 Low · Mid · High 순서로 섰고, High 둘은 제목순입니다. 12번 줄의 priority 가 13번 줄의 title 보다 먼저 적혀 있습니다.
급한 일이 맨 뒤에 섰다 — 31번 줄의 max() 가 고른 것이 가장 급한 일입니다. 목록의 맨 앞에 급한 일이 오게 하는 길 하나는 순서를 직접 적는 것입니다. 다음 슬라이드에서 합니다.

Ord 를 손으로 구현한다 — cmp 하나가 sort · < · min 을 정한다

앞 슬라이드의 Task 를 "먼저 할 일이 앞" 으로 세웁니다. 우선순위는 높은 쪽부터, 같으면 제목순입니다. Task 의 derive 에서 PartialOrd 와 Ord 를 떼고 직접 구현합니다. 10부에서 Display 를 직접 구현한 것과 같은 모양입니다.

읽는 법 — 19번 줄은 other 를 앞에 적어 우선순위를 거꾸로 견주고, 20번 줄이 then_with 로 제목을 잇습니다. 39번 줄의 sort() 뒤에 High 둘이 앞에 섰습니다. 43번 줄의 < 와 44번 줄의 min() 도 같은 순서를 따라 true 와 배포 를 냈습니다.
나머지 세 트레이트 — 26번 줄의 partial_cmp 는 cmp 의 답을 Some 에 담아 돌려주기만 합니다. PartialEq 와 Eq 는 10번 줄의 derive 그대로입니다. 표준 라이브러리 문서는 이 네 트레이트의 답이 서로 어긋나지 않아야 한다고 적습니다. 여기서는 cmp 가 두 필드를 모두 견주므로, cmp 가 Equal 인 두 값은 derive 한 == 로도 같습니다.

sort 는 키가 같으면 원래 순서를 지킨다 — sort_unstable 에는 그 약속이 없다

12부에서 같은 것끼리의 순서를 지키는 정렬을 안정 정렬(stable sort)이라 했고, 그 약속은 sort 계열에만 있다고 했습니다. 키가 겹치는 자료로 그 약속을 확인합니다. 접수한 순서대로 적힌 명단을 반으로 정렬합니다.

읽는 법 — 13번 줄의 sort_by_key 뒤에 2반 셋은 yoon · choi · lee 입니다. 이름순이 아니라 4번부터 8번 줄까지에 적힌 접수 순서 그대로입니다. 1반의 kim · park 도 그렇습니다. 27번 줄은 정수를 두 방법으로 정렬해 견줬고 결과가 같습니다. 원소를 통째로 견주면 같은 것끼리는 구별되지 않습니다.
sort_unstable 의 결과는 반만 찍었다 — 표준 라이브러리 문서는 sort_unstable 계열이 같은 원소의 순서를 바꿀 수 있다고, 그리고 메모리를 따로 잡지 않는다고 적습니다. 그래서 19번 줄에서 반만 꺼내 찍었습니다. [1, 1, 2, 2, 2] 까지가 약속된 것입니다. 같은 반 안의 이름 순서는 한 번 돌려 나온 것이 약속이 아니라서 이 책은 싣지 않습니다.

binary_search — 있으면 Ok(자리), 없으면 Err(넣을 자리)

정렬된 벡터에서는 binary_search 로 값을 찾습니다(이진 탐색, binary search). 찾은 자리만이 아니라, 없을 때 그 값이 들어갈 자리도 알려 줍니다. is_sorted( 부터)는 정렬돼 있는지를 묻습니다.

읽는 법 — 5번 줄의 Ok(2) 는 31 이 2번 칸에 있다는 뜻입니다. 6번 줄의 Err(3) 은 40 이 없고, 넣는다면 3번 칸이라는 뜻입니다. 어느 원소보다 작은 5 는 Err(0), 어느 원소보다 큰 99 는 길이와 같은 Err(5) 입니다. 13번 줄이 그 자리를 받아 14번 줄에서 insert 했고, 16번 줄이 찍은 벡터는 여전히 정렬돼 있습니다. 여기서 Err 는 실패가 아니라 둘째 답입니다.
정렬돼 있어야 한다 — 19번 줄의 mixed 는 is_sorted 가 false 입니다. 22번 줄의 contains 는 31 이 있다고 하는데 21번 줄의 binary_search 는 Err 를 냈습니다. 표준 라이브러리 문서는 정렬돼 있지 않은 슬라이스에서는 돌아오는 값이 정해져 있지 않고 뜻도 없다고 적습니다. Err(2) 라는 값도 이 기계의 이 컴파일러에서 나온 것일 뿐입니다.

partition_point — 조건이 참에서 거짓으로 바뀌는 자리

점수순으로 정렬해 둔 명단에서 60 점 이상 80 점 이하인 사람만 뽑으려 합니다. 꼭 60 점이나 80 점인 사람이 있는지는 모르므로 값을 찾는 binary_search 와는 물음이 다릅니다. partition_point 는 조건을 받아, 그 조건이 참인 앞쪽과 거짓인 뒤쪽이 갈리는 자리를 돌려줍니다.

읽는 법 — 11번 줄의 조건 score < 60 이 참인 원소는 맨 앞의 하나뿐이라 lo 는 1 입니다. 12번 줄의 score <= 80 은 앞의 넷에 참이라 hi 는 4 입니다. 15번 줄이 그 사이를 슬라이스로 찍었습니다. 60 점인 kim 과 lee 가 둘 다 들어 있습니다. 17번과 18번 줄은 조건이 모두 거짓일 때 0, 모두 참일 때 길이 5 를 냈습니다.
같은 값이 여럿이면 — 표준 라이브러리 문서는 같은 값이 여럿일 때 binary_search 가 그 가운데 어느 자리든 돌려줄 수 있다고 적습니다. 그 값의 첫 자리가 필요하면 11번 줄처럼 "그 값보다 작다" 를 조건으로 partition_point 를 부릅니다. 60 점 둘 가운데 앞의 것이 1번 칸입니다.

출입 기록에서 사람마다 가장 이른 기록 하나만 남기려 합니다. 8부의 dedup 은 이웃한 같은 값만 지웠습니다. dedup_by_key 는 원소 전체가 아니라 클로저가 낸 키가 같은 이웃을 지웁니다. 같은 이름을 이웃하게 모으는 일은 정렬이 맡습니다.

읽는 법 — 13번 줄은 정렬하지 않고 불렀고, 14번 줄이 찍은 길이는 6 그대로입니다. 같은 이름이 이웃해 있지 않았습니다. 17번 줄의 정렬 뒤에는 같은 이름이 모였고, lee 의 세 기록은 9 · 11 · 15 로 들어온 순서 그대로입니다. 20번 줄의 dedup_by_key 뒤에는 이름마다 맨 앞의 것, 곧 가장 이른 기록이 남았습니다.
안정 정렬이 순서를 맡았다 — "맨 앞의 것이 가장 이른 기록" 인 것은 17번 줄의 sort_by_key 가 같은 키의 순서를 지켰기 때문입니다. 시각으로 다시 정렬하지 않았습니다.

같은 값은 해시도 같아야 한다 — 그래야 따로 만든 키로 같은 항목을 찾는다

좌석을 키로 주인을 적어 둔 맵에서, 나중에 따로 만든 좌석 값으로 주인을 찾으려 합니다. 10부에서 Hash 와 Eq 를 derive 한 타입을 HashSet 에 넣었습니다. 그 Hash 가 하는 일부터 봅니다. 해시(hash)는 값에서 뽑아낸 수 하나입니다. Hash 를 구현한 값은 자기 내용을 Hasher 에 넣고, Hasher 의 finish 가 그 수를 돌려줍니다.

읽는 법 — 13번 줄이 값을 hasher 에 넣고 14번 줄의 finish 가 u64 를 돌려줍니다. 22번 줄에서 a 와 b 는 따로 만든 값인데 == 로 같고 해시도 같습니다. 23번 줄의 a 와 c 는 둘 다 다릅니다. 28번 줄은 a 를 키로 넣은 맵에서 b 로 kim 을 찾았고, c 로는 None 입니다.
키의 규칙 — 표준 라이브러리 문서는 맵의 키에, 두 키가 == 로 같으면 해시도 같을 것을 요구합니다. 둘을 함께 derive 한 Seat 은 22번 줄에서 그 규칙을 지켰습니다. 이 책은 해시 값 자체는 찍지 않고 같은지만 찍습니다. 문서는 DefaultHasher 의 셈법이 정해져 있지 않아 값에 기대면 안 된다고 적습니다.

Eq 와 Hash 가 어긋나면 같은 키가 여러 항목이 된다

이름의 대소문자를 가리지 않고 방문 횟수를 세려 합니다. String 을 10부의 newtype Name 으로 감싸고, == 는 대소문자를 무시하도록 직접 구현했습니다. Hash 는 derive 로 뒀습니다. 문서에 따르면 derive 한 Hash 는 필드마다 hash 를 불러 합칩니다. 속의 글을 철자 그대로 넣는다는 뜻입니다.

읽는 법 — 29번 줄이 어긋남을 보여 줍니다. Kim 과 KIM 은 == 로 같은데 해시는 다릅니다. 그 결과 36번 줄의 len() 은 1 이 아니라 3 입니다. 37번 줄에서 Kim 으로 찾으면 그 철자로 온 두 번만 나오고, 38번 줄의 kIM 은 == 로 같은 키가 맵에 있는데도 None 입니다. 컴파일러는 아무 말도 하지 않았습니다.
23번 줄의 FixedMap — 이 부에서 이 예제만 해시의 씨앗(seed)을 고정한 맵을 씁니다. HashMap 의 셋째 타입 인자가 해시를 만드는 방법이고, 이름은 16부에서 본 타입 별명으로 붙였습니다. 문서는 보통의 HashMap 이 무작위 씨앗에서 시작한다고 적습니다. 그러면 어긋난 키가 든 맵의 화면이 실행마다 같다고 말할 수 없습니다. 다음 슬라이드에서 키를 고치면 보통의 HashMap::new() 로 돌아갑니다.

Hash 를 손으로 구현한다 — == 가 보는 것만 넣는다

고치는 길은 규칙 그대로입니다. == 가 대소문자를 무시하니 Hash 도 대소문자를 지운 글을 넣으면 됩니다. derive(Hash) 를 떼고 impl Hash 를 씁니다.

읽는 법 — 18번 줄은 소문자로 바꾼 글의 hash 를 불러, 넘겨받은 state 에 넣습니다. 31번 줄이 이번에는 true true 입니다. 37번 줄의 len() 은 kim 과 lee 의 2 이고, 38번 줄에서 넣은 적 없는 철자 kIM 으로 찾아도 4 입니다. 42번 줄이 찍은 키는 Name("Kim") 입니다. 처음 넣은 철자가 남았고, 뒤에 온 KIM 과 kim 은 값만 올렸습니다.
Eq 를 손댔으면 Hash 도 — 둘은 같은 것을 봐야 합니다. 10부의 derive 표대로 둘 다 derive 하거나, 여기처럼 둘 다 직접 씁니다. 한쪽만 손으로 써서 어긋난 것이 앞 슬라이드입니다.

or_insert_with — 키가 없을 때만 값을 만든다

8부의 entry(…).or_insert(값) 은 "없으면 넣고, 그 자리의 가변 참조를 준다" 였습니다. 넣을 값을 만드는 데 일이 든다면 or_insert 는 아깝습니다. 인자는 부르기 전에 만들어지기 때문입니다. or_insert_with 는 값 대신 클로저를 받습니다.

읽는 법 — 14번 줄에서 db 는 이미 있는 키인데도 (db 설정을 읽는다) 가 찍혔습니다. 읽어 온 값은 쓰이지 않았고, 찍힌 것은 넣어 둔 값입니다. 16번 줄의 or_insert_with 는 같은 키에 괄호 줄 없이 넣어 둔 값을 냈습니다. 17번 줄의 web 은 없는 키라 클로저가 불렸고, 18번 줄에서 다시 부르면 불리지 않습니다. 9부의 unwrap_or 와 unwrap_or_else 와 같은 짝입니다.

and_modify 와 or_insert — 있으면 고치고, 없으면 첫 값을 넣는다

A. Kim 과 KIM 이 == 로는 같은데 해시가 다릅니다 (어긋난 키). 맵의 키는 == 로 같으면 해시도 같아야 합니다. derive 를 떼고 impl Hash 에서 소문자로 바꾼 글을 넣으면 두 해시가 같아지고, 항목은 하나로 모입니다 (Hash 를 손으로).
