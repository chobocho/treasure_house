async 블록은 만드는 자리에서 붙잡고, poll 될 때 돈다

16부에서 async 블록이 주변 변수를 붙잡는다는 것과, 돌리기 전에는 본문이 돌지 않는다는 것을 봤습니다. 붙잡는 방법은 12부의 클로저와 같습니다. 본문이 읽기만 하면 빌리고, move 를 붙이면 가져갑니다. 이 슬라이드가 더하는 것은 "언제" 입니다. 붙잡는 일은 블록을 만드는 자리에서 일어나고, 본문은 그 뒤에 poll 될 때 돕니다.

읽는 법 — 10번 줄의 블록은 name 을 읽기만 하고, 15번 줄의 블록에는 move 가 붙었습니다. 화면의 첫 줄은 21번 줄의 것입니다. 두 블록을 만든 뒤인데 본문의 println! 은 아직 하나도 돌지 않았고, name 은 main 이 그대로 읽었습니다. count 는 6부에서 본 복사되는 타입이어서, 블록이 가져간 뒤에도 main 의 count 가 남아 20번 줄이 2 로 올렸습니다. 24번 줄이 첫 블록을 묻자 "빌린 블록이 돈다: ferris" 와 Ready(6) 이 나왔습니다. 26번 줄이 둘째 블록을 묻자 "가져간 블록이 돈다: count = 1" 과 Ready(101) 이 나왔습니다. 본문은 20번 줄보다 나중에 돌았는데 블록 안의 count 는 1 입니다. 블록은 15번 줄에서, 곧 만드는 자리에서 그때의 값을 가져갔습니다.
붙잡는 때와 도는 때 사이 — 첫 블록이 붙잡은 것은 name 의 참조입니다. 그 참조는 블록이 poll 될 때 쓰이므로, 그때까지 name 이 살아 있어야 합니다. 여기서는 만든 함수 안에서 곧바로 물었으니 문제가 없었습니다. 다음 슬라이드에서는 블록을 실행기에 맡깁니다.

spawn 에 넘긴 블록이 gate 를 빌리면 — E0373

2장에서 태스크로 맡긴 블록에는 async move 가 붙어 있었습니다. 그 move 를 빼 봅니다. 2장의 둘째 실행기 파일에서 1번 태스크의 블록만 async 로 바꿨습니다.

읽는 법 — 번호는 15부의 스레드는 지역 변수를 빌릴 수 없다에서 읽은 E0373 이고, 그때의 "클로저" 자리에 "async 블록" 이 들어갔습니다. 오류 첫 줄은 "async 블록이 지금 함수보다 오래 살 수 있는데 gate 를 빌린다" 이고, 130번 줄의 async 를 짚습니다. 133번 줄의 gate.open() 에는 "여기서 빌린다" 가 붙었습니다. note: 는 앞 슬라이드에서 본 것을 적습니다. "async 블록은 곧바로 실행되지 않으므로, 쓰는 바깥 변수의 참조나 소유권 가운데 하나를 가져야 한다". help: 는 move 를 붙여 블록이 gate 를 갖게 하라며 고친 130번 줄을 적어 줍니다. 2장의 파일이 그 꼴입니다. 15부의 화면에 있던 "받는 함수가 'static 을 요구한다" 는 note: 는 이 화면에 없습니다. 소스를 보면 이 블록을 받는 2장의 spawn 도 매개변수에 'static 을 달았고, 빌린 gate 를 품은 블록은 그 조건에 맞지 않습니다.
0번 태스크의 블록은 move 없이도 컴파일됐다 — 마지막 화면은 126번 줄에서만 move 를 뺀 쌍둥이의 것이고, 2장에서 본 화면과 같은 네 줄입니다. 그 블록이 waiting 으로 하는 일은 127번 줄의 waiting.await 하나입니다. move 가 없어도 블록은 waiting 을 빌리지 않고 가져갔다는 뜻입니다. 빌렸다면 첫 화면과 같은 오류가 났을 것입니다. 12부의 클로저처럼 블록도 본문이 하는 일을 보고 붙잡습니다. 133번 줄의 open 은 &self 로 받는 메서드여서 빌리는 데 그쳤습니다.

async move 블록을 돌려주는 클로저는 seen 을 첫 호출에 내주고 만다 — E0382

이번에는 퓨처를 여러 번 만들어 내는 쪽입니다. 수를 받을 때마다 벡터 seen 에 넣는 퓨처가 필요합니다. 12부의 클로저와 16부의 async 블록을 이으면 "인자를 받아 async 블록을 돌려주는 클로저" 가 됩니다. 블록에는 앞 슬라이드의 help: 대로 move 를 붙였습니다.

읽는 법 — 오류는 둘이고 둘 다 E0382 입니다. 첫째는 12부의 FnOnce 를 두 번 부르면에서 읽은 것과 같은 글입니다. 47번 줄의 첫 호출에 "record 가 이 호출 때문에 옮겨 갔다" 가, 50번 줄의 둘째 호출에 "옮겨 간 뒤에 여기서 썼다" 가 붙었습니다. 첫 note: 가 까닭입니다. "이 클로저는 seen 을 자기 밖으로 옮겨 내므로 한 번밖에 부를 수 없다" 이고, 짚은 곳은 43번 줄의 seen 입니다. 둘째 note: 는 그래서 이 값이 FnOnce 라고 합니다. 둘째 오류는 51번 줄에서 seen 을 찍으려 한 것입니다. 12부의 가져간 뒤에는 밖에서 못 쓴다와 같은 꼴로, 41번 줄에 "값이 여기서 클로저 안으로 옮겨 갔다" 가 붙었습니다.
두 오류가 두 걸음이다 — 43번 줄의 seen.push(n) 은 async move 블록 안에 있습니다. 둘째 오류의 말로는 seen 이 41번 줄에서 클로저 안으로 옮겨 갔고, 첫째 오류의 말로는 클로저가 그것을 다시 자기 밖으로 옮겨 냅니다. 첫 호출이 만든 블록이 seen 을 가져가 버리니 둘째 호출에 줄 것이 없습니다. 여기서 바란 것은 "부를 때마다, 클로저가 가진 seen 을 잠깐 빌리는 퓨처" 였습니다. 다음 슬라이드의 문법이 그것입니다.

async 클로저 — 돌려준 퓨처가 클로저의 seen 을 빌려, 두 번 부를 수 있었다

async 를 클로저 앞에 붙인 async |n| { … } 가 async 클로저(async closure)입니다 . 부르면 본문을 돌릴 퓨처를 돌려줍니다. 앞 슬라이드의 41번 줄을 그 꼴로 바꿉니다.

읽는 법 — 41번 줄에서 async 가 |n: u32| 앞으로 왔고, move 는 없습니다. 본문이 seen 을 고치므로 12부의 고치는 클로저처럼 mut 변수에 담았습니다. 47번 줄에서 record(10) 을 부르자 퓨처가 나왔고, 48번 줄이 "퓨처를 만들었다" 를 찍었습니다. 본문에는 찍는 줄이 없어, 본문이 어디서 돌았는지는 그다음 줄로 봅니다. 49번 줄의 block_on 이 그 퓨처를 돌려 "poll 2번" 을 찍었습니다. 42번 줄의 Countdown(1) 이 낸 Pending 한 번과 끝나는 한 번이므로, 42번 줄을 기다린 것은 block_on 안에서입니다. 그다음 줄의 1 은 43번 줄이 10 을 넣은 뒤의 길이입니다. 50번 줄의 둘째 호출도 컴파일됐고, "poll 2번" 과 2 가 나왔습니다. 51번 줄이 찍은 [10, 20] 은 seen 이 main 에 남아 있다는 것입니다.
앞 슬라이드의 두 오류가 짚던 두 줄 — 50번 줄이 컴파일됐으니 첫 호출이 seen 을 가져가 버리지 않았고, 51번 줄이 컴파일됐으니 클로저도 seen 을 빌렸을 뿐입니다. 이 async 클로저를 불러 나온 퓨처는 클로저가 붙잡아 둔 seen 을 가져가지 않고 썼습니다. 블록을 돌려주는 클로저로는 이 예제에서 그렇게 되지 않았습니다.

AsyncFn · AsyncFnMut · AsyncFnOnce — async 클로저를 매개변수로 받는다

12부에서 클로저를 받는 함수는 매개변수 타입에 impl Fn(…) 이나 FnMut 나 FnOnce 를 적었습니다. async 클로저를 받는 자리에는 같은 꼴로 AsyncFn · AsyncFnMut · AsyncFnOnce 를 적습니다. 세 이름은 8부에서 본 프렐류드에 있어 use 없이 썼습니다. 이 파일의 use 는 앞 슬라이드와 같은 두 줄입니다.

읽는 법 — 38번 줄의 impl AsyncFn(u32) -> u32 에서 화살표 뒤의 u32 는 퓨처가 낼 값의 타입입니다. 39번 줄이 f(n).await 둘을 수로 더합니다. 60번 줄은 base 를 읽는 async 클로저를 넘겼습니다. 화면의 "poll 1번" 과 202 가 그것으로, 101 을 두 번 더한 값입니다. 본문에 .await 가 없어 Pending 이 없었습니다. 62번 줄은 같은 자리에 53번 줄의 async fn double 을 넘겼습니다. 12부에서 Fn 자리가 보통 함수도 받았듯 받았습니다. "poll 3번" 은 두 호출의 Countdown(1) 이 낸 Pending 둘과 끝나는 한 번이고, 16 은 8 을 두 번 더한 값입니다. 43번 줄의 AsyncFnMut 는 mut f 로 받았고, 70번 줄에서 seen 을 고치는 65번 줄의 클로저를 넘겼습니다. 다음 "poll 3번" 뒤의 2 는 45번 줄의 둘째 호출이 낸 길이이고, 71번 줄이 [10, 20] 을 찍었습니다. 49번 줄의 AsyncFnOnce 에는 74번 줄에서 name 을 가져가 그대로 내보내는 async move || name 을 넘겼습니다. 마지막 "poll 1번" 과 ferris 가 그것입니다.
이 슬라이드가 해 보지 않은 것 — 화면이 보인 것은 넘긴 넷이 그 자리에 받아들여졌다는 데까지입니다. 12부에서 본 Fn 자리에 고치는 클로저를 넘기면 같은, 맞지 않는 짝은 여기서 넘겨 보지 않았습니다.

트레이트 안의 async fn — 두 구현을 제네릭 함수 하나가 기다린다

1부에서 트레이트 안의 async fn 이 뒤늦게 들어왔다는 것까지만 봤습니다. 여기서 써 봅니다. 트레이트 Source 에 async fn fetch 를 두고 두 타입에 구현합니다. Slow 는 1장의 Countdown 을, Locked 는 Gate 를 기다린 뒤에 값을 줍니다.

읽는 법 — 124번 줄은 본문이 없는 async fn 입니다. 10부의 트레이트에서 메서드의 시그니처를 적던 자리에 async 가 붙었습니다. 131번과 144번 줄이 두 구현이고, 본문에서 .await 를 씁니다. 145번 줄은 &self 너머의 Gate 를 복제해서 기다립니다. 151번 줄의 report 는 10부의 impl Trait 매개변수로 Source 를 구현한 타입을 받고, 152번 줄에서 fetch() 가 돌려준 퓨처를 기다립니다. 163번 줄은 Locked 를, 165번 줄은 Slow 를 넘겼습니다.
화면 — poll 순서 [0, 1, 1, 1, 0] 에서 0번은 처음에 한 번 poll 됐습니다. 소스를 따라가면 145번 줄의 닫힌 문 앞입니다. 1번의 세 번은 132번 줄의 Countdown(2) 가 낸 Pending 둘과 끝나는 한 번이고, 그때 "1번 Slow: 2" 가 찍혔습니다. 1번이 166번 줄에서 문을 열자 0번이 다시 poll 되어 "0번 Locked: 7" 을 찍었습니다. 끝나지 않은 태스크는 0 입니다. 2장의 실행기는 고친 데가 없습니다. report 가 돌려준 것도 spawn 이 받는 퓨처입니다.

fetch 가 async 인 Source 는 dyn 으로 쓸 수 없었다 — E0038

1부에서 본 발표문은 트레이트 안의 async fn 을 내놓으면서 중요한 기능이 아직 빠져 있다고 적었습니다. 그 글이 꼽은 것 가운데 둘을 이 슬라이드와 다음 슬라이드에서 컴파일러의 말로 봅니다. 첫째는 10부의 트레이트 객체입니다. 앞 슬라이드의 main 에 한 줄을 더합니다.

읽는 법 — 162번 줄은 쓰지 않을 벡터여서 이름을 _all 로 뒀습니다. 오류는 10부에서 읽은 E0038 이고, "dyn 과 맞지 않는다" 는 첫 줄도, 메서드 표(vtable)를 지을 수 있어야 한다는 note: 도 같습니다. 새로 읽을 것은 그 note: 가 보여 주는 124번 줄, 곧 앞 슬라이드의 async fn fetch 에 붙은 까닭입니다. "메서드 fetch 가 async 여서". 10부에서는 반환 타입의 Self 가, 19부에서는 메서드의 타입 인자가 그 자리에 있었습니다. 첫 help: 는 10부 때처럼 그 메서드를 다른 트레이트로 옮기라고 합니다. 둘째 help: 는 Source 를 구현한 타입이 Slow 와 Locked 라고 적고, 변형마다 그 타입을 하나씩 담는 열거형을 만들어 거기에 Source 를 구현해 쓰라고 권합니다. 10부의 종류가 정해져 있으면 열거형도 답이다와 같은 방향입니다.
이 책이 본 데까지 — 같은 Source 를 제네릭으로 받은 앞 슬라이드는 컴파일됐고, dyn 으로 쓰려 한 이 줄은 막혔습니다. 둘째 help: 의 열거형은 이 책에서 만들어 보지 않았습니다.

impl Source 의 fetch 가 돌려준 퓨처는 Send 자리에 넘길 수 없었다 — E0277

둘째는 Send 입니다. 15부에서 thread::spawn 은 받는 클로저에 Send 를 요구했습니다. 여기서는 스레드를 만들지 않고, Send 인 값만 받는 함수 need_send 로 그 조건만 겁니다. 같은 꼴의 Source 를 실행기 없는 작은 파일에 옮겨 적었습니다.

읽는 법 — E0277 은 10부의 "어떤 타입이 어떤 트레이트를 구현하지 않았다" 이고, 첫 줄은 15부의 Rc 는 스레드를 건너가지 못한다와 같은 "스레드 사이로 안전하게 보낼 수 없다" 입니다. 타입 자리에 impl Future<Output = u32> 가 들어갔습니다. 18번 줄의 source.fetch() 를 짚고, 첫 help: 는 그 타입에 Send 가 구현되어 있지 않다고 합니다. note: 는 그 조건이 14번 줄의 need_send 에서 왔다는 것입니다. 둘째 help: 가 고칠 길입니다. "Send 를 Source::fetch 의 모든 구현이 지킬 약속으로 만들 수 있다" 며 2번 줄을 고쳐 적어 줍니다. async fn 대신 보통 fn 을 쓰고, 반환 타입에 퓨처를 드러내어 + Send 를 붙인 꼴입니다.
고친 쌍둥이 — 둘째 화면이 2번 줄을 그렇게 바꾼 파일의 것입니다. 컴파일됐고 23번 줄이 "컴파일됐다" 를 찍었습니다. 반환 타입의 impl Future<…> 는 10부의 -> impl Trait 을 트레이트 안에 쓴 것입니다 . help: 는 std::future::Future 라고 길게 적었는데, 쌍둥이는 프렐류드의 Future 로 짧게 적었습니다. 8번 줄의 구현은 async fn fetch 그대로 두었는데도 컴파일됐습니다. 마지막 화면은 트레이트를 고치지 않고 17번 줄이 &Fixed 만 받게 한 쌍둥이의 것이고, 이것도 컴파일됐습니다. 받는 타입이 정해져 있으면 고치지 않은 2번 줄로도 통과했고, impl Source 로 받으면 2번 줄에 + Send 가 적혀 있어야 통과했습니다.

퓨처를 버리면 거기서 그만둔다 — 멈춰 있던 .await 다음 줄은 돌지 않는다

퓨처는 값이므로 끝나기 전에 버릴 수 있습니다. 그러면 그 일은 거기서 그만입니다. 이것을 취소(cancellation)라고 부릅니다. 14부의 Noisy, 곧 정리될 때 한 줄을 찍는 값을 async fn 이 들고 있게 해서, 버릴 때 무슨 일이 일어나는지 봅니다. 퓨처는 3장의 Box::pin 으로 고정했습니다. 상자째로 14부의 drop 에 넘길 수 있습니다.

읽는 법 — "가" 는 45번과 46번 줄이 두 번 물었습니다. "가: 시작" 과 Pending, 그다음에 "가: 끝" 과 "가 정리" 와 Ready(()) 입니다. 본문이 끝까지 가서 34번 줄의 _guard 가 스코프를 벗어났습니다. "나" 는 50번 줄이 한 번만 물었습니다. "나: 시작" 과 Pending 이 찍혔고, 퓨처는 36번 줄의 .await 에서 멈춰 있습니다. 52번 줄의 drop(cut) 이 그 퓨처를 버리자 "main: 나 를 버린다" 와 "main: 버렸다" 사이에 "나 정리" 가 찍혔습니다. "나: 끝" 은 화면에 없습니다. 37번 줄은 돌지 않았습니다. "다" 는 56번 줄에서 만들고 57번 줄에서 버렸습니다. 한 번도 poll 하지 않아 "다: 시작" 도 "다 정리" 도 없고, 58번 줄의 "main: 다 도 버렸다" 만 찍혔습니다. 34번 줄이 돈 적이 없으니 정리할 Noisy 도 없습니다.
취소는 버리기 — 버려진 퓨처에게는 멈춰 있던 .await 가 마지막 줄이 됩니다. 그때까지 만든 값은 정리되고, 그 뒤의 줄은 돌지 않습니다. 꼭 해야 하는 뒷정리를 37번 줄 같은 보통 줄에 적어 두면 취소됐을 때 건너뛰게 되고, Noisy 처럼 Drop 에 적은 것은 돌았습니다. 표준 라이브러리 문서에서 Future 트레이트가 요구하는 메서드는 poll 하나이고, 퓨처에게 그만두라고 알리는 메서드는 거기에 없습니다. 그만두게 하는 길은 다시 poll 하지 않고 버리는 것입니다.

실행기를 버리면 끝나지 않은 태스크의 퓨처도 버려진다

2장은 끝나지 않은 태스크를 세기만 했습니다. 그 태스크는 실행기가 들고 있는 퓨처입니다. Noisy 를 든 채 문을 기다리는 태스크 셋을 맡기고, 그 가운데 둘의 문은 끝내 열지 않은 채로 실행기를 버립니다.

읽는 법 — 144번 · 145번 · 151번 줄의 세 태스크는 처음 poll 될 때 "문을 기다린다" 를 찍었습니다. 0번과 3번은 저마다 아무도 열지 않는 문을, 1번은 soon 을 기다립니다. 2번이 "2번: 문을 연다" 를 찍고 149번 줄에서 soon 을 열자 1번이 "1번: 문이 열렸다" 를 찍고 끝났고, 곧바로 "1번 정리" 가 찍혔습니다. 153번 줄이 찍은 poll 순서 [0, 1, 2, 3, 2, 2, 1] 에서 0번과 3번은 한 번씩입니다. 2번의 세 번은 Countdown(2) 의 Pending 둘과 끝나는 한 번입니다. 끝나지 않은 태스크는 2 입니다. 156번 줄의 drop(ex) 가 실행기를 버리자 "main: 실행기를 버린다" 와 "main: 버렸다" 사이에 "0번 정리" 와 "3번 정리" 가 찍혔습니다. "0번: 문이 열렸다" 와 "3번: 문이 열렸다" 는 화면에 없습니다.
태스크의 주인은 실행기 — 실행기의 tasks 는 퓨처를 담은 상자의 벡터입니다. 14부에서 상자가 사라질 때 속의 값도 함께 정리됐습니다. 화면의 "0번 정리" 와 "3번 정리" 는 실행기를 버릴 때 그 상자 속의 퓨처가, 그리고 퓨처가 들고 있던 _guard 가 정리됐다는 것입니다. 앞 슬라이드에서 손으로 한 drop(cut) 과 같은 일이 남은 태스크마다 일어났습니다. 이 실행기에는 태스크 하나만 골라 그만두게 하는 메서드가 없습니다.

Select2 — 둘을 함께 묻고, 먼저 Ready 를 낸 쪽의 값을 낸다

2장의 Join2 는 두 퓨처가 다 끝나기를 기다렸습니다. 반대쪽 도구는 먼저 끝나는 하나를 기다리는 것입니다. Select2 는 poll 될 때마다 a 를 묻고, 아직이면 b 를 묻습니다. 어느 쪽이든 Ready 를 내면 그 값이 Select2 의 답입니다. 16부의 표가 바깥 크레이트의 칸에 둔 "여러 퓨처를 함께 돌리는 도구" 를 하나 더 작게 만들어 보는 것입니다.

읽는 법 — 132번 줄의 Select2<A, B> 는 Join2 와 달리 제네릭이고, 139번과 140번 줄이 두 퓨처를 저마다 Box::pin 으로 고정해 둡니다. 145번부터 147번 줄까지의 where 는 A 와 B 가 퓨처이고, 10부의 연관 타입 Output 이 서로 같다는 조건입니다. 149번 줄에서 그 타입이 Select2 의 Output 이 됩니다. 156번 줄이 a 를 묻고, Ready 면 157번 줄이 그 값으로 끝냅니다. 그때 159번 줄은 돌지 않으므로 b 는 묻지 않습니다. a 가 아직이면 159번 줄이 b 의 답을 그대로 자기 답으로 냅니다. 152번 줄의 mut self 너머로 필드를 고쳐 빌리는 156번과 159번 줄은 Join2 때와 같은 길로 컴파일됐습니다. Join2 처럼 받은 cx 를 안쪽 퓨처에 그대로 건네고, 스스로 깨워 달라고 하지는 않습니다.
진 쪽을 그만두게 하는 줄은 없다 — Select2 의 poll 에는 진 쪽에 손대는 줄이 없습니다. 값을 낸 뒤에 Select2 가 버려지면 그 안의 두 상자도 함께 버려집니다. 버리면 그만둔다와 실행기를 버리면에서 본 대로라면 그것이 진 쪽의 취소입니다. 다음 슬라이드에서 화면으로 확인합니다.

먼저 끝난 쪽이 값을 내면, 진 쪽은 멈춰 있던 .await 에서 버려진다

0번 태스크는 "문이 열리기를 기다리기" 와 "Pending 을 두 번 세기" 가운데 먼저 끝나는 쪽을 기다립니다. 1번 태스크가 문을 여는 때를 바꿔 가며 두 번 돌립니다.

읽는 법 — 명령 줄 아래의 일곱 줄이 198번 줄 demo(1) 의 것이고, 그 마지막이 poll 순서 [0, 1, 0, 1, 0] 입니다. 1번이 둘째 poll 에서 "1번: 문을 연다" 를 찍었고, 이어진 0번의 셋째 poll 에서 a 가 "문 기다리기: 문이 열렸다" 를 찍고 끝났습니다. 그 _guard 가 "문 기다리기 정리" 를, 곧이어 b 의 _guard 가 "세기 정리" 를 찍었습니다. "세기: 다 셌다" 는 없습니다. 소스를 따라가면 count(2) 는 앞의 두 번에서 Pending 둘을 다 냈으므로, 셋째 poll 에서 물었다면 끝났을 것입니다. 앞 슬라이드의 poll 은 a 가 끝나면 b 를 묻지 않았고, b 는 174번 줄의 .await 에 멈춘 채 버려졌습니다. 두 "정리" 줄이 186번 줄의 "0번: 먼저 끝난 쪽은 문" 보다 먼저입니다. b 는 끝까지 간 적이 없으니 "세기 정리" 는 버려져서 찍힌 줄이고, 그래서 Select2 는 185번 줄의 .await 가 값을 내놓은 뒤, 186번 줄이 돌기 전에 버려졌습니다. 뒤의 일곱 줄이 demo(4) 입니다. 이번에는 "세기: 다 셌다" 와 "세기 정리" 다음에 "문 기다리기 정리" 가 찍혔고, 진 쪽은 166번 줄에 멈춰 있던 wait_open 입니다. poll 순서 [0, 1, 0, 1, 0, 1, 1, 1] 대로 1번은 그 뒤에 세 번 더 poll 되어 문을 열었습니다. 두 번 다 끝나지 않은 태스크는 0 입니다.
"(0번은 이미 끝났다)" 두 줄 — 2장의 Join2 화면에서 읽은, 끝난 태스크의 번호를 건너뛰는 줄입니다. 소스를 따라가면 demo(1) 에서는 count 안의 Countdown 이 해 둔 깨움과 1번이 문을 열며 한 깨움이 겹쳐, 0번이 큐에 두 번 들어가 있었습니다. demo(4) 에서는 그 줄이 "1번: 문을 연다" 다음에 나옵니다. 버려진 wait_open 이 Gate 에 맡겨 둔 Waker 가 문에 남아 있었고, 191번 줄의 open 이 그것을 깨웠습니다. 퓨처를 버려도 그 퓨처가 맡겨 둔 Waker 까지 치워지지는 않았습니다. 이 실행기는 끝난 태스크의 번호를 건너뛰는 것으로 그런 깨움을 받아 냅니다.

Rc 를 든 채 .await 를 넘는 퓨처는 Send 자리에 넘길 수 없었다

15부에서 Rc 는 Send 가 아니었고, 구조체는 필드가 전부 Send 여야 Send 였습니다. async fn 의 퓨처에는 필드를 적은 곳이 없습니다. 트레이트의 Send 슬라이드에서 쓴 need_send 에, 본문에서 Rc 를 쓰는 async fn 의 퓨처를 넘겨 봅니다.

읽는 법 — 번호가 없는 오류입니다. 첫 줄은 "퓨처를 스레드 사이로 안전하게 보낼 수 없다" 이고, 16번 줄의 job() 에 "job 이 돌려준 퓨처는 Send 가 아니다" 가 붙었습니다. help: 는 그 퓨처 안에서 Rc<usize> 에 Send 가 구현되어 있지 않다고 합니다. 첫 note: 가 까닭입니다. "이 값이 await 를 넘어 쓰이므로 퓨처가 Send 가 아니다". 9번 줄의 shared 에는 "타입이 Rc<usize> 이고 Send 가 아니다" 가, 11번 줄의 .await 에는 "await 가 여기서 일어나고, shared 는 그 뒤에 쓰일 수도 있다" 가 붙었습니다. 12번 줄은 shared 를 쓰지 않지만, shared 는 13번 줄의 닫는 중괄호까지 스코프 안에 있습니다. 둘째 note: 는 그 조건이 4번 줄의 need_send 에서 왔다는 것입니다.
오류가 짚은 것은 .await 를 넘는 값 — 3장에서 .await 너머로 들고 가는 값이 퓨처의 크기에 나타났습니다. 이 화면의 첫 note: 도 await 를 넘어 쓰이는 값을 까닭으로 댔습니다. 오류가 짚은 것은 Rc 를 만든 줄이 아니라, Rc 가 살아 있는 채로 지나가는 11번 줄의 .await 입니다.

Rc 의 스코프를 .await 앞에서 끝내니 컴파일됐다 — drop 으로는 같은 오류였다

Rc 가 .await 를 넘지 않게 두 가지로 해 봅니다. 하나는 Rc 를 쓰는 두 줄을 블록으로 감싸는 것이고, 다른 하나는 .await 앞에서 drop(shared) 를 부르는 것입니다.

읽는 법 — 첫 화면은 컴파일되어 "컴파일됐다" 를 찍었습니다. 9번부터 12번 줄까지의 블록 안에서 Rc 를 만들어 값만 꺼냈고, shared 는 12번 줄에서 스코프를 벗어나 정리됩니다. 13번 줄의 .await 를 넘는 것은 usize 인 n 뿐입니다. 둘째 화면은 drop 을 넣은 쌍둥이의 것으로, 앞 슬라이드와 같은 오류입니다. 그 파일에서는 한 줄이 늘어 .await 가 12번 줄로, job() 이 17번 줄로 밀렸을 뿐이고, shared 가 "그 뒤에 쓰일 수도 있다" 는 말까지 같습니다. 이 책의 컴파일러는 drop(shared) 로 값을 넘겨 버린 뒤에도 그 변수를 .await 를 넘는 것으로 쳤습니다.
2장의 실행기는 Send 를 요구한 적이 없다 — spawn 의 매개변수는 impl Future<Output = ()> + 'static 이고, 거기에 Send 는 없습니다. 그래서 Rc 를 든 Gate 를 기다리는 태스크가 컴파일됐습니다. 그 실행기는 스레드 하나에서 돌았습니다. 1부에서 본 발표문은 스레드 여럿이 일을 나눠 돌리는 실행기를 따로 꼽고, 거기에 쓸 트레이트에는 Send 조건을 더한다고 적습니다. 이 책은 그런 실행기를 돌려 보이지 않습니다.

Q. async fn job 의 본문은 Noisy 를 하나 만들고, "시작" 을 찍고, Countdown(1).await 를 한 다음에 "끝" 을 찍습니다. 이 퓨처를 한 번만 poll 하고 버리면 화면에 무엇이 찍히고 무엇이 찍히지 않을까요? 한 번도 poll 하지 않고 버리면 어떻게 될까요?

채널 — 큐가 비었으면 Waker 를 맡기고 Pending 을 낸다

15부의 채널에서 recv() 는 값이 올 때까지 돌아오지 않는 호출이었습니다. 스레드가 하나뿐인 이 부의 실행기에서 그렇게 기다리면, 값을 보내 줄 태스크가 poll 될 차례가 오지 않습니다. 여기서 기다리는 방법은 1장의 Gate 가 한 대로입니다. Waker 를 맡기고 Pending 을 내면, 일을 일으킨 쪽이 깨웁니다. Gate 는 "열렸다" 하나만 알렸고, 채널은 값을 큐에 실어 보냅니다.

읽는 법 — 88번 줄의 Chan 이 채널의 속이고, 94번과 95번 줄의 Sender 와 Receiver 가 그것을 Gate 처럼 Rc<RefCell<…>> 로 함께 가집니다. 108번 줄의 send 는 async 가 아닌 보통 메서드입니다. 110번 줄이 값을 큐의 뒤에 넣고, 111번 줄이 맡아 둔 Waker 가 있으면 take 로 꺼내 깨웁니다. 꺼낸 뒤에는 waiting 이 None 이어서, 받는 쪽이 다시 맡기기 전의 send 는 깨우지 않습니다. 117번 줄의 Clone 은 손으로 구현해 복제할 때마다 senders 를 올리고, 124번 줄의 Drop 이 내립니다. 0 이 됐을 때 받는 쪽이 기다리고 있으면 130번 줄의 let 사슬이 그 Waker 를 꺼내 깨웁니다. 138번 줄의 Recv 는 11부에서 본 참조를 든 구조체이고, 141번 줄의 recv 가 그것을 돌려줍니다.
poll 의 세 갈래 — 154번 줄: 큐에 값이 있으면 Ready(Some(값)) 입니다. 157번 줄: 값이 없고 보내는 쪽도 없으면 Ready(None) 입니다. 그 밖에는 161번 줄이 Waker 를 맡기고 162번 줄이 Pending 을 냅니다. 이 채널에서 "기다린다" 는 그 두 줄입니다. poll 은 곧바로 실행기로 돌아가고, 그동안 실행기는 다른 태스크를 poll 할 수 있습니다. 154번 줄이 157번 줄보다 앞이어서, 큐에 값이 남아 있으면 보내는 쪽의 수를 보기 전에 값부터 냅니다.

받는 태스크는 깨워졌을 때 poll 되고, 보내는 쪽이 다 사라지자 None 을 받았다

태스크 셋을 맡깁니다. 0번은 받고, 1번과 2번이 보냅니다. tx2 는 tx 의 복제본이어서 보내는 쪽이 둘입니다.

읽는 법 — poll 순서 [0, 1, 2, 0, 1, 2, 0, 2, 0] 을 따라갑니다. 0번의 첫 poll 은 찍은 것이 없습니다. 소스를 따라가면 빈 큐 앞에서 Waker 를 맡기고 낸 Pending 입니다. 1번이 179번 줄에서 1 을 보내고 180번 줄에서 차례를 양보했고, 2번이 185번 줄에서 10 을 보내고 양보했습니다. 0번의 둘째 poll 이 "받았다 1" 과 "받았다 10" 을 잇달아 찍었습니다. 한 번 poll 되는 동안 172번 줄의 while let 이 큐에 있던 둘을 보낸 순서대로 꺼냈습니다. 1번은 181번 줄에서 2 를 보내고 끝났고, 0번의 셋째 poll 이 "받았다 2" 를 찍었습니다. 그때 tx 는 사라졌지만 tx2 가 남아 있어 None 은 나오지 않았습니다. 2번이 더 보내지 않고 끝나자 0번이 마지막으로 poll 되어 "보내는 쪽이 모두 사라졌다" 를 찍었습니다. recv() 가 None 을 내어 while let 을 벗어난 것입니다. 15부에서 보내는 쪽이 모두 사라지면 for 가 끝난 것과 같은 약속을 손으로 만들었습니다. 끝나지 않은 태스크는 0 입니다.
0번이 poll 된 네 번 — 맡길 때 큐에 넣어 준 한 번, 179번과 181번 줄의 send 가 깨운 두 번, 그리고 2번이 끝나며 마지막 Sender 의 Drop 이 깨운 한 번입니다. 소스를 따라가면 185번 줄의 send 는 깨우지 않았습니다. 179번 줄이 Waker 를 이미 꺼내 갔기 때문입니다. 0번은 깨움 없이는 한 번도 poll 되지 않았고, 화면에 2장의 "(0번은 이미 끝났다)" 줄도 없습니다. 1번과 2번이 poll 된 횟수는 Countdown 의 Pending 한 번과 두 번에 끝나는 한 번씩을 더한 둘과 셋입니다.

시계 없는 시간 — 틱을 세는 Timer 와, 정해 둔 틱에 끝나는 Sleep

16부의 표는 타이머를 바깥 크레이트의 칸에 뒀습니다. 이 부의 예제는 시계를 읽지 않으므로, 시간을 수 하나로 대신합니다. 그 수를 틱(tick)이라고 부릅니다. Timer 는 지금의 틱과, "몇 틱에 깨워 달라" 며 맡긴 Waker 들을 가집니다. sleep(n) 은 지금부터 n 틱 뒤에 끝나는 퓨처 Sleep 을 돌려줍니다. 틱을 올리는 일은 다음 슬라이드에서 실행기가 합니다.

읽는 법 — 100번 줄의 sleepers 는 8부의 BTreeMap 입니다. 키는 (깨울 틱, Sleep 을 만든 순서) 이고, 키 순서로 서므로 맨 앞이 가장 먼저 깨울 것입니다. 105번 줄의 Timer 는 Gate 와 같은 꼴이어서 복제본이 같은 TimerState 를 봅니다. 113번 줄의 sleep 은 115번 줄에서 만든 순서를 하나 올리고, 118번 줄에서 "지금의 틱 + ticks" 를 깨울 틱으로 적습니다. 124번 줄의 advance 는 18부에서 본 first_key_value 로 가장 작은 키를 봅니다. 맡아 둔 것이 없으면 128번 줄이 false 를 돌려줍니다. 있으면 130번 줄이 now 를 그 틱으로 옮깁니다. 하나씩 세어 올라가지 않고 그 틱으로 건너뜁니다. 131번 줄의 first_entry 는 같은 첫 항목을 꺼낼 수 있는 꼴로 주고, 그 항목의 틱이 at 인 동안 134번 줄이 꺼내서 깨웁니다.
Sleep — 151번 줄: 지금의 틱이 정해 둔 틱에 닿았으면 Ready 입니다. 아니면 156번 줄이 Waker 를 자기 키로 넣고 Pending 을 냅니다. 8부에서 본 대로 같은 키에 다시 insert 하면 값이 바뀌므로, Sleep 하나가 맡겨 두는 Waker 는 하나입니다. 161번 줄의 Drop 은 4장의 취소에 대비한 것으로, 버려질 때 자기 키로 맡긴 Waker 를 지웁니다. 이 여섯 줄이 하는 일은 시간 초과 슬라이드에서 화면으로 봅니다. 이 책은 Timer 를 Gate 와 같은 꼴로 만들어 태스크에 인자로 넘깁니다. 새로 배울 것이 없고, 누가 같은 상태를 보는지가 인자에 드러납니다. Timer 는 Waker 안에 넣지 않으므로, Gate 의 상태처럼 Rc<RefCell<…>> 인 채로 컴파일됐습니다.

실행기는 큐가 비었을 때만 틱을 올린다 — 태스크는 깨울 틱의 순서로 일어난다

2장의 실행기를 두 군데 고칩니다. 필드에 timer: Timer 를 더하고(51번 줄), 번호의 큐가 비었을 때 돌아오는 대신 advance 를 부릅니다. 태스크 넷을 맡깁니다. "가" 와 "라" 는 3틱, "나" 는 1틱을 자고, "다" 는 자지 않고 차례만 두 번 양보합니다.

읽는 법 — 2장의 run 은 큐가 비면 곧바로 돌아왔습니다. 이제는 71번 줄이 advance 를 부르고, 깨운 것이 있으면 72번 줄의 continue 로 큐를 다시 봅니다. 맡아 둔 Waker 도 없으면 74번 줄에서 끝납니다. 186번 줄은 실행기의 Timer 를 복제해 두고, 태스크마다 그 복제본을 넘깁니다. 화면의 "틱 0" 여섯 줄에서 "가" · "나" · "라" 는 잔다고 찍었고, "다" 는 양보 둘과 "끝" 을 찍었습니다. "다" 가 두 번 양보하고 끝나는 동안 틱은 0 그대로입니다. 큐에 번호가 있는 동안에는 71번 줄에 닿지 않습니다. 큐가 비자 틱이 1 이 되어 "나" 가 일어났고, 그다음은 틱 3 입니다. 틱 2 에 깨울 것이 없어 건너뛰었습니다. "가" 와 "라" 는 같은 틱 3 에, Sleep 을 만든 순서대로 일어났습니다. 맡긴 순서는 가 · 나 · 다 · 라 인데 일어난 순서는 나 · 가 · 라 입니다. 192번 줄이 찍은 poll 순서 [0, 1, 2, 3, 2, 2, 1, 0, 3] 의 뒤 셋이 그 순서이고, 193번 줄이 끝나지 않은 태스크 0 과 마지막 틱 3 을 찍었습니다.
이 시간은 실행기가 올리는 수 — 화면의 틱은 시계에서 온 것이 아니라 71번 줄이 올린 수입니다. 언제 올릴지를 run 이 정하므로, 이 화면도 돌릴 때마다 같은 정해진 순서입니다. run 은 큐도 비고 Timer 가 맡아 둔 Waker 도 없을 때 돌아와, 2장 그대로 90번 줄에서 끝나지 않은 태스크를 셉니다. 이 화면에서는 0 입니다.

시간 초과 — recv 와 sleep 가운데 먼저 끝나는 쪽을 기다린다

20부의 recv_timeout 은 한도를 시계로 쟀습니다. 여기서는 4장의 Select2 로 "값 받기" 와 "3틱 자기" 를 겨루게 합니다. 값이 먼저 오면 Sleep 이, 틱이 먼저 차면 Recv 가 진 쪽이 되어 버려집니다. 보내는 쪽이 2 를 보내기 전에 자는 틱을 바꿔 두 번 돌립니다.

읽는 법 — 267번 줄의 블록은 recv 의 답을 Ok 로 감싸고, 268번 줄의 블록은 limit 틱을 잔 뒤에 Err("시간 초과") 를 냅니다. 두 블록은 move 없이 rx 와 timer 를 빌립니다. 실행기에 맡기지 않고 272번 줄에서 곧바로 기다리므로 빌려도 됐습니다. 첫 화면에서 명령 줄 아래의 여섯 줄이 demo(2) 입니다. "틱 0 · 받았다 1" 다음에 틱은 3 이 아니라 2 가 됐습니다. 0번이 다시 건 3틱보다 1번의 2틱이 먼저입니다. 1번이 "틱 2 · 2 를 보낸다" 를 찍고 끝났고, 0번은 "틱 2 · 받았다 2" 에 이어 곧바로 "틱 2 · 보내는 쪽이 사라졌다" 를 찍었습니다. poll 순서 [0, 1, 0, 1, 0] 을 보면 1번이 끝난 뒤에 0번이 poll 됐습니다. tx 가 사라진 뒤였는데도 큐에 남은 2 부터 받았습니다. 뒤 여섯 줄이 demo(5) 입니다. "받았다 1" 뒤에 틱이 3 으로 건너뛰어 294번 줄의 갈래가 "틱 3 · 시간 초과" 를 찍고 0번이 끝났습니다. 1번은 "틱 5 · 2 를 보낸다" 를 찍었는데, 그 2 를 받을 태스크는 없습니다. 그 뒤의 "(0번은 이미 끝났다)" 는 4장에서 문에 남은 Waker 와 같은 일입니다. 버려진 Recv 가 채널에 맡겨 둔 Waker 를 306번 줄의 send 가 깨웠습니다. poll 순서 는 [0, 1, 0, 0, 1] 이고, 두 번 다 끝나지 않은 태스크는 0, 마지막 틱은 2 와 5 입니다.
Sleep 의 Drop 을 빼면 — 마지막 화면이 그 쌍둥이의 demo(2) 입니다. 태스크가 찍은 네 줄과 poll 순서 는 같은데, "(0번은 이미 끝났다)" 가 두 줄 생겼고 마지막 틱이 3 입니다. 값이 이겨서 버려진 Sleep 둘이 맡긴 Waker 가 Timer 에 남아 있었습니다. 태스크가 다 끝난 뒤에 실행기가 그것을 따라 틱을 3 으로 올리고, 끝난 0번을 두 번 깨웠습니다. Drop 이 있는 첫 화면은 틱 2 에서 끝났습니다. Sleep 의 Drop 이 버려질 때 맡긴 것을 지웠습니다. 4장에서 본 대로 취소될 때 해야 하는 뒷정리는 Drop 에 적습니다. Recv 에는 Drop 을 구현하지 않았고, 그래서 demo(5) 에 그 한 줄이 남았습니다.

퀴즈 — 틱은 언제 오르는가

Q. 틱 0 에 태스크 넷을 맡겼습니다. "가" 와 "라" 는 3틱, "나" 는 1틱을 자고, "다" 는 자지 않고 차례를 두 번 양보한 뒤에 끝납니다. "다" 가 끝날 때의 틱은 몇일까요? 틱 2 에는 누가 일어날까요?

A. "다" 는 틱 0 에 끝납니다. 이 실행기는 번호의 큐가 비었을 때만 틱을 올리고, 양보한 태스크는 곧바로 큐에 다시 들어가므로 "다" 가 도는 동안 틱은 그대로입니다. 틱 2 에는 아무도 일어나지 않습니다. 화면에 "틱 2" 로 시작하는 줄이 없습니다. advance 는 하나씩 세지 않고 가장 이른 깨울 틱으로 건너뛰어, 틱은 0 에서 1 로, 1 에서 3 으로 갔습니다. "나" 가 틱 1 에, "가" 와 "라" 가 틱 3 에 일어났습니다 (큐가 비었을 때만 틱을 올린다).
