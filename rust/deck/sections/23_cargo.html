Cargo·프로젝트 심화

워크스페이스 · features · build.rs 와 컴파일 때 정보 · 시험 더 · 실행 파일 여러 개와 프로필

이 부에서 할 일

Cargo 는 두 번 봤습니다. 2부 2장이 cargo new 부터 cargo clippy 까지의 명령을, 13부 3장과 4장이 Cargo.toml 의 구역과 기능 하나, cargo test 를 가르쳤습니다. 이 부는 그 위에 올리는 2층입니다. 거기서 가르친 것은 다시 설명하지 않고 그 슬라이드로 가는 링크만 답니다. 22부까지의 예제는 대부분 파일 하나였습니다. 여기서는 패키지가 여럿인 프로젝트와, 컴파일하는 동안 정해지는 것들을 다룹니다.

  • 1장 — 워크스페이스: 뿌리의 Cargo.toml 과 멤버, path 의존성, -p, 하나뿐인 Cargo.lock 과 target/, resolver, 뿌리에서 물려받는 버전과 에디션
  • 2장 — features: default 와 명령 줄의 세 옵션, cfg! 와 #[cfg] 의 차이, 틀린 기능 이름, 의존성의 기능, 함께 빌드할 때 합쳐지는 기능
  • 3장 — build.rs 와 컴파일 때 정보: env! 와 option_env!, include_str!, 빌드 스크립트가 넘기는 환경 변수와 cfg 이름, OUT_DIR 에 만든 소스
  • 4장 — 시험 더: 시험끼리 나눠 쓰는 도우미, should_panic(expected = …), 라이브러리를 거쳐 실행 파일 시험하기, 기준 파일과 견주는 시험, --test-threads=1
  • 5장 — 실행 파일 여러 개와 프로필: src/bin/ 과 examples/, 화면으로 차이가 보이는 프로필 설정, [lints] 표
이 부의 화면 — 1장부터 3장까지의 예제는 하나만 빼고 모두 디렉터리입니다. 화면은 그 디렉터리의 사본 안에서 $ 줄의 명령을 위에서부터 차례로 친 것이고, 앞 명령이 만든 target/ 과 파일은 다음 명령 때 그대로 남아 있습니다. 사본의 경로는 0부에서 말한 대로 /work 로, 걸린 시간은 0.00s 로 고정해 실었습니다. Cargo 는 인터넷에 나가지 않게 해 두고 돌렸습니다. 바깥 크레이트는 하나도 없고, 의존성은 같은 워크스페이스의 패키지뿐입니다. 명령에는 대개 2부에서 본 -q 를 붙였고, Compiling 줄처럼 Cargo 자신이 하는 말이 근거가 되는 곳에서만 뺐습니다. 명령 앞에 적은 이름=값 은 18부에서 본 이 기계 셸의 표기입니다. Cargo 가 낸 오류에는 번호(E…)가 없어서 그런 슬라이드의 제목에도 번호가 없습니다. 슬라이드가 쌍둥이라고 부르는 디렉터리는 19부의 쌍둥이 파일처럼, 적어 둔 줄만 바꾼 사본입니다. 1장에서 패키지를 더한 워크스페이스와 물려받는 워크스페이스는 첫 워크스페이스의 .rs 파일을 그대로 두고 패키지를 더하거나 Cargo.toml 만 고친 것입니다. 3장의 한 예제는 파일 하나를 rustc 만으로 컴파일합니다.

1장

워크스페이스

뿌리의 Cargo.toml · path 의존성 · -p · 실행 파일이 둘일 때 · Cargo.lock 과 target/ · resolver · 물려받기 · 멤버가 아닌 패키지

워크스페이스 — 뿌리의 Cargo.toml 이 패키지들을 묶는다

13부는 패키지 하나에 라이브러리 크레이트와 실행 크레이트를 함께 두었고, [workspace] 는 구역 표에 이름과 뜻만 적었습니다. 여기서는 패키지를 둘로 나누고 워크스페이스(workspace) 하나로 묶습니다. 묶인 패키지를 멤버(member)라고 부릅니다.

읽는 법 — 뿌리 Cargo.toml 의 2번 줄 members 는 멤버가 든 디렉터리의 이름입니다. 첫 화면의 text-kit/ 과 app/ 이 그것이고, 저마다 자기 Cargo.toml 을 가집니다. 둘째 화면에는 2부에서 읽은 Compiling 줄이 둘입니다. 괄호 안의 자리가 /work/text-kit 과 /work/app 으로 다릅니다. 명령 하나가 두 패키지를 컴파일했습니다. Finished 줄은 2부에서 본 그대로입니다. 3번 줄의 resolver 는 resolver 줄을 뺀 슬라이드에서 봅니다.

멤버가 멤버를 가져다 쓴다 — path 의존성

[dependencies] 는 2부에서 늘 빈칸이라고 한 구역입니다. 거기에 처음으로 한 줄을 적습니다. 가져다 쓰는 크레이트를 의존성(dependency)이라고 하고, 버전 대신 디렉터리를 적은 것이 path 의존성입니다. 바깥 크레이트는 여전히 하나도 없습니다.

읽는 법 — app/Cargo.toml 7번 줄의 path 는 app/ 에서 한 칸 올라가 text-kit/ 으로 들어가는 경로입니다. 패키지 이름은 text-kit 인데 main.rs 1번 줄은 - 자리에 _ 를 적은 text_kit 으로 불렀고, 그대로 컴파일됐습니다. HELLO! 는 lib.rs 3번 줄이 만든 글입니다. 실행 파일을 내는 멤버가 app 하나라서 뿌리에서 cargo run -q 만 쳤습니다. 둘이 되면 어떻게 되는지는 실행 파일이 둘일 때에서 봅니다.
21부에서 손으로 한 일 — 두 크레이트 예제에서는 라이브러리를 먼저 컴파일하고 그 결과를 --extern 으로 넘기는 명령을 손으로 쳤습니다. 여기서는 그런 명령을 치지 않았습니다. 무엇을 먼저 컴파일할지도 적지 않았는데, 앞 슬라이드의 Compiling 줄은 text-kit 이 먼저였습니다.

-p 는 패키지 이름을 받는다

워크스페이스 뿌리에서 명령에 -p 이름 을 붙이면 그 패키지를 고릅니다. 13부의 cargo test 로 라이브러리 쪽만 시험해 봅니다. 시험 모듈은 13부에서 본 꼴 그대로입니다.

읽는 법 — 첫 명령의 묶음은 둘입니다. 13부에서 본 차례대로라면 lib.rs 의 단위 시험과 문서 시험이고, 첫 묶음의 1개가 위 상자 11번 줄의 shout_adds_mark 입니다. app 의 main.rs 를 시험한 묶음은 없습니다. 둘째 명령은 이름의 - 를 _ 로 적었습니다. 오류 첫 줄은 "text_kit 과 맞는 패키지가 없다" 이고, help: 가 비슷한 이름 text-kit 을 댑니다.
이름이 둘 — -p 에는 Cargo.toml 의 name 에 적은 text-kit 을, Rust 코드의 use 에는 앞 슬라이드처럼 text_kit 을 적었습니다.

실행 파일이 둘이면 cargo run 이 고르라고 한다

앞의 워크스페이스에 실행 패키지 tool 을 더했습니다. main.rs 하나뿐이고 다른 멤버를 쓰지 않습니다. 워크스페이스에서는 cargo run 에 패키지를 대지 않아도 됩니다( 부터). 돌릴 것이 둘이 되면 달라집니다.

읽는 법 — cargo build 의 Compiling 줄이 셋입니다. tool 은 app 의 의존성이 아닌데도 컴파일됐습니다. 뿌리에서 친 cargo build 가 members 의 셋을 다 빌드했습니다. cargo run 의 오류 첫 줄은 "어느 실행 파일을 돌릴지 정할 수 없다. --bin 옵션이나 default-run 키로 고르라" 이고, 그 아랫줄이 고를 수 있는 둘 app, tool 입니다. 여기서는 -p tool 로 패키지를 골랐고, 그 main.rs 의 2번 줄이 찍혔습니다. 한 패키지에 실행 파일이 여럿인 경우는 5장에서 봅니다.

Cargo.lock 과 target/ 은 워크스페이스에 하나씩

2부에서 target/ 은 패키지 디렉터리 안에 생겼고, 13부는 Cargo.lock 을 "실제로 쓴 정확한 버전을 적어 두는 파일" 이라고만 했습니다. 멤버가 둘인 첫 워크스페이스에서 둘이 어디에 생겼는지 봅니다. 그 전에 멤버 디렉터리 안에 들어가서도 한 번 돌립니다.

읽는 법 — 셸의 cd app 으로 멤버 안에 들어가 돌려도 HELLO! 가 찍혔습니다. 그 뒤의 ls 에서 Cargo.lock 과 target 은 뿌리(.:)에만 있고, app/ 과 text-kit/ 에는 Cargo.toml 과 src 뿐입니다. 실행 파일도 뿌리 아래의 target/debug/app 입니다. Cargo.lock 은 빌드하기 전의 목록에 없던 파일입니다. 첫 두 줄은 Cargo 가 만든 파일이니 손으로 고치지 말라는 주석입니다. [[package]] 묶음은 멤버마다 하나씩이고 이름과 버전을 적습니다. app 쪽에는 의존성 text-kit 이 더 적혀 있습니다.
version = 4 — 주석 바로 아래의 이 수는 패키지의 버전이 아니라 Cargo.lock 이라는 파일의 형식에 붙은 번호입니다. 릴리스 노트는 lockfile v4 를 에서 안정화했다고 적습니다.

resolver 줄을 빼면 Cargo 가 경고한다

첫 워크스페이스의 뿌리 Cargo.toml 3번 줄 resolver = "3" 을 미뤄 두었습니다. 그 한 줄만 뺀 쌍둥이 워크스페이스를 빌드합니다. 나머지 파일은 글자까지 같습니다.

읽는 법 — 경고 첫 줄은 "virtual workspace 는 resolver = "1" 을 기본으로 삼는다. 멤버가 2024 에디션이고 그 에디션은 resolver = "3" 을 뜻하는데도" 입니다. 첫 note: 는 지금대로 두려면 "1" 을, 둘째는 2024 에디션의 것을 쓰려면 "3" 을 뿌리에 적으라고 하고, 셋째는 설명이 있는 주소입니다. 그 뒤의 Compiling 과 Finished 줄은 첫 워크스페이스의 것과 같습니다. 이 책은 둘째 note: 를 따라 "3" 을 적었습니다.
resolver 가 무엇인가 — 릴리스 노트는 resolver 항목이 새 기능 해석기(feature resolver)를 켜려고 Cargo.toml 에 들어왔다고 적고(), resolver v3 을 에서 안정화했다고 적습니다. 2024 에디션 발표문은 그 에디션이 의존성 해석기(dependency resolver)의 기본 동작을 rust-version 항목까지 고려하도록 바꾼다고 적습니다 . 이 책의 예제는 바깥 크레이트를 받지 않아 버전을 고를 일이 없고, 그 차이를 화면으로 보이지 않습니다. 기능 쪽의 이야기는 2장의 합쳐지는 기능에서 잇습니다. Cargo 문서는 뿌리 Cargo.toml 에 [package] 가 없는 워크스페이스를 virtual workspace 라고 부릅니다.

버전과 에디션을 뿌리 한곳에 적는다 — [workspace.package]

멤버마다 version 과 edition 을 따로 적으면 올릴 때 고칠 곳이 멤버 수만큼입니다. 뿌리에 한 번 적고 멤버는 "워크스페이스의 것을 쓴다" 고만 적을 수 있습니다. 의존성의 경로도 같은 식으로 뿌리에 모읍니다.

읽는 법 — 두 멤버의 3번과 4번 줄은 값 대신 .workspace = true 를 적었습니다. 값은 뿌리의 6번과 7번 줄에 있습니다. Compiling 줄의 버전이 둘 다 v0.3.0 입니다. 0.3.0 이라는 글자는 뿌리에만 있습니다. app 의 7번 줄 text-kit.workspace = true 는 뿌리 10번 줄의 의존성을 가리킵니다. 뿌리 10번 줄의 path 는 뿌리에서 본 text-kit 이고, 멤버에 직접 적었을 때의 ../text-kit 과 다릅니다. 소스 파일은 첫 워크스페이스와 같고, 달라진 것은 Cargo.toml 셋뿐입니다.

members 에 없는 패키지는 돌지 않는다 — cargo new 는 알아서 적는다

워크스페이스 디렉터리 안에 패키지를 손으로 만들고 members 에 적는 것을 잊은 경우입니다. 실행 파일이 둘이던 워크스페이스에 그런 디렉터리 extra/ 를 넣어 두었습니다. 둘째 화면은 앞 슬라이드의 워크스페이스에서 2부의 cargo new 로 같은 이름의 패키지를 만든 것입니다.

읽는 법 — 첫 화면의 오류 첫 줄은 "이 패키지는 자기가 워크스페이스 안에 있다고 여기는데 그렇지 않다" 입니다. 다음 두 줄이 그 패키지와 워크스페이스의 Cargo.toml 이고, 그 아래가 고치는 길 셋입니다. 뿌리의 workspace.members 에 더하거나, workspace.exclude 에 적어 빼 두거나, 그 패키지에 빈 [workspace] 를 적으라고 합니다. 뿌리에서 친 cargo build 의 Compiling 줄에도 extra 는 없었습니다.
cargo new 가 한 일 — Creating 줄과 note: 줄은 2부의 화면에도 있던 것입니다. 그 사이의 Adding 줄이 extra 를 워크스페이스의 멤버로 더했다고 말하고, 뿌리 Cargo.toml 의 members 에 "extra" 가 들어갔습니다( 부터). 새 extra/Cargo.toml 의 버전과 에디션도 .workspace = true 로 적혀 나왔습니다( 부터). -p extra 로 고르자 cargo new 가 채워 둔 Hello, world! 가 찍혔습니다.

퀴즈 — 어디에 생기고, 무엇이라고 부르는가

Q. 워크스페이스의 멤버는 라이브러리 패키지 text-kit 과 실행 패키지 app 입니다. ① app/ 안에 들어가 cargo run -q 를 했습니다. 실행 파일은 어느 디렉터리 아래에 있습니까? ② 뿌리에서 cargo test -q -p text_kit 을 치면 어떻게 됩니까?

A. ① 뿌리의 target/debug/app 입니다. app/ 안에서 돌린 뒤의 ls 에서 app/ 에는 Cargo.toml 과 src 뿐이었고 target 은 뿌리에만 있었습니다. ② 시험을 돌리기 전에 Cargo 가 멈춥니다. -p 가 받는 것은 패키지 이름 text-kit 이고, 오류의 help: 가 그 이름을 댔습니다. text_kit 은 use 에 적는 크레이트 이름입니다.

2장

features

기본 기능 · 명령 줄의 세 옵션 · cfg! 와 #[cfg] · 없는 기능 이름 · 소스의 오타 · 의존성의 기능 · 합쳐지는 기능

default — 말하지 않아도 켜지는 기능

13부의 기능(feature)은 fancy = [] 하나를 선언하고 --features fancy 로 켜는 데까지였습니다. 거기서 잇습니다. [features] 에 default 라는 이름으로 목록을 적어 두면, 거기 든 기능은 아무 옵션 없이도 켜집니다. 이것을 기본 기능(default features)이라고 합니다.

읽는 법 — Cargo.toml 7번 줄이 frame 을 기본 기능으로 적었습니다. 옵션 없이 돌린 첫 명령이 frame=true 를 찍었고, main.rs 2번 줄 쪽 frame 이 컴파일되어 [ hello ] 가 나왔습니다. --no-default-features 를 붙인 둘째 명령은 frame=false 이고, main.rs 의 7번 줄 쪽 frame 이 글을 그대로 돌려줘 hello 입니다. shout 은 두 번 다 꺼져 있어 main.rs 14번 줄의 if 가 "hello" 를 골랐습니다. 그 파일의 20번부터 25번 줄까지가 세 기능이 켜졌는지를 찍습니다. loud 도 두 번 다 false 입니다.
이미 본 것 — #[cfg(feature = "…")] 와 not(…) 은 13부의 기능 예제에서 본 꼴입니다. cfg! 는 13부에서 같은 조건을 bool 값으로 얻는 매크로라고 했습니다. 여기서는 그 조건 자리에 기능을 적었습니다.

명령 줄의 세 옵션 — --features · --no-default-features · --all-features

앞 슬라이드의 패키지를 옵션만 바꿔 네 번 더 돌립니다. 소스는 그대로입니다. [features] 구역을 다시 싣습니다.

  • --features shout — frame=true 가 그대로입니다. 기본 기능은 켜 둔 채 shout 을 더했고, 글이 [ HELLO ] 가 됐습니다.
  • --no-default-features --features frame,shout — 쉼표로 둘을 적었습니다. 화면은 바로 위와 같고, loud 는 false 입니다.
  • --no-default-features --features loud — loud 하나만 댔는데 frame 과 shout 도 true 입니다. 10번 줄 loud = ["frame", "shout"] 이 "loud 를 켜면 이 둘도 켠다" 는 뜻입니다. 7번 줄의 default 와 같은 꼴입니다.
  • --all-features — 선언한 기능을 다 켭니다( 부터). 셋이 모두 true 입니다.

cfg! 로 가른 if 안은 기능이 꺼져 있어도 컴파일된다 — E0425

#[cfg] 가 붙은 항목은 조건이 맞지 않으면 컴파일에서 빠집니다. cfg! 는 true 나 false 라는 값이 될 뿐입니다. 기능이 켜졌을 때만 있는 함수를 그 값으로 가른 if 안에서 불러 봅니다.

읽는 법 — stats 를 켠 첫 명령은 두 줄을 다 찍었습니다. 옵션 없는 둘째 명령의 오류 첫 줄은 "이 스코프에서 함수 stats 를 찾을 수 없다" 로, 21부의 E0425 와 같은 꼴입니다. main.rs 의 11번 줄에 붙었습니다. 10번 줄의 조건이 false 인 컴파일인데도 그 if 안의 11번 줄이 컴파일된 것입니다. 새로운 것은 그 아래의 note: 입니다. "설정 때문에 빠진 항목을 찾았다" 이고, 2번 줄의 속성에 "이 항목은 stats 기능 뒤에 있다" 고 붙였습니다. 마지막 error: could not compile 줄은 Cargo 가 덧붙인 말입니다.

부르는 문에 #[cfg] 를 붙이면 그 문도 함께 빠진다

앞 슬라이드의 10번부터 12번 줄까지를 두 줄로 바꾼 쌍둥이 패키지입니다. if cfg!(…) 대신, 함수에 붙인 것과 같은 속성을 부르는 문에도 붙였습니다. 나머지 줄은 같습니다.

읽는 법 — 옵션 없는 첫 명령이 오류 없이 red green blue 한 줄을 찍었습니다. stats 를 켠 둘째 명령은 낱말 3개 까지 찍었습니다. 속성이 붙을 수 있는 곳은 함수 같은 항목만이 아니고, 여기서는 문 하나에 붙였습니다.
어느 쪽을 쓰는가 — 첫 예제의 main 은 두 갈래가 어느 기능에서나 컴파일되는 문자열 둘이어서 cfg! 로 골랐습니다. 여기처럼 한쪽이 기능이 켜졌을 때만 있는 이름을 부르면 #[cfg] 로 그 문을 뺍니다.

명령 줄에 없는 기능 이름을 대면 Cargo 가 멈춘다

앞 슬라이드의 패키지에서 stats 의 끝 글자를 빠뜨리고 --features stat 이라고 쳤습니다.

읽는 법 — 오류 첫 줄은 "패키지 report 에는 이 기능이 없다: stat" 이고, help: 가 비슷한 이름의 기능 stats 를 댑니다. 번호(E…)도, 소스의 자리를 가리키는 --> 줄도 없습니다. 1장의 패키지 이름 오류처럼 rustc 가 아니라 Cargo 가 낸 오류입니다. 화면에 프로그램의 출력은 없습니다.

소스에서 기능 이름을 틀리면 경고만 나고 그 코드가 빠진다

같은 오타를 이번에는 소스에 냈습니다. 고친 패키지의 10번 줄에서 "stats" 를 "stat" 으로만 바꾼 쌍둥이입니다. 명령 줄에서는 기능을 옳게 켰습니다.

읽는 법 — 첫 경고의 첫 줄은 "뜻밖의 cfg 조건 값: stat" 이고 10번 줄에 붙었습니다. 밑줄 아래의 help: 가 비슷한 이름의 값 "stats" 를 대고, 첫 note: 가 feature 에 올 수 있는 값은 stats 라고 합니다. 다음 help: 는 stat 을 Cargo.toml 에 기능으로 더하는 길을 말하고, 그 아래는 설명이 있는 주소와 이 경고의 이름 unexpected_cfgs 입니다. 둘째 경고는 "함수 stats 를 아무도 쓰지 않는다" 입니다. 13부에서 #[allow(dead_code)] 로 껐던 그 경고입니다. stats 기능이 켜져 3번 줄의 함수는 있는데, 그것을 부르던 11번 줄이 빠졌습니다. 화면 마지막 줄의 출력에 낱말 3개 가 없습니다.
오류가 아니다 — 종료 코드 줄이 없습니다. 프로그램은 컴파일되어 돌았습니다. 경고를 읽지 않으면 기능을 켰는데도 그 코드가 빠진 것을 모르고 지나갑니다. 릴리스 노트는 Cargo 의 이 검사(check-cfg)가 에서 늘 켜진 것으로 안정화됐다고 적습니다.

의존성의 기능은 가져다 쓰는 쪽이 의존성 줄에서 고른다

1장의 path 의존성 줄에 두 가지를 더 적을 수 있습니다. 라이브러리 text-kit 에 기능 둘을 달고, 그것을 쓰는 실행 패키지 app 과 plain 을 한 워크스페이스에 두었습니다.

읽는 법 — 두 실행 파일은 같은 글 hello 를 text_kit::shout 에 넘기고, 받은 글 앞에 자기 이름을 붙여 찍습니다. 그 소스는 다음 슬라이드에 있습니다. app 의 7번 줄 features = ["upper"] 는 명령 줄의 --features 처럼 기본 기능 위에 더합니다. 대문자에 느낌표까지 붙은 HELLO! 입니다. plain 의 7번 줄 default-features = false 는 --no-default-features 처럼 기본 기능을 끕니다. 아무것도 켜지지 않아 hello 그대로입니다.

함께 빌드하면 한 라이브러리의 기능이 합쳐진다

앞 슬라이드에서 plain 은 hello 를 찍었습니다. 이번에는 -p 없이 뿌리에서 워크스페이스를 통째로 빌드하고, 만들어진 plain 을 직접 돌립니다. 그 사이에 고친 파일은 없습니다.

읽는 법 — cargo build 의 Compiling 줄은 plain 하나입니다. 소스가 그대로인데 다시 컴파일됐습니다. 그렇게 나온 target/debug/plain 은 plain: HELLO! 를 찍습니다. lib.rs 의 4번 줄과 7번 줄이 둘 다 true 였다는 뜻입니다. upper 는 app 이 켠 기능이고, mark 는 app 이 끄지 않은 기본 기능입니다. plain 의 Cargo.toml 은 둘 다 청하지 않았습니다. 마지막 명령처럼 -p plain 으로 하나만 고르면 다시 plain: hello 입니다.
더하기만 하는 기능 — 릴리스 노트는 이 일을 의존성의 기능을 합친다(unifying features)고 부릅니다. resolver 항목을 들인 판()의 노트가, 기능 해석기의 2번 판은 합치는 것이 바람직하지 않은 곳에서는 합치지 않으려 한다고 적으며 쓴 말입니다. Cargo 문서는 그래서 기능을 "켜면 무엇이 더해질 뿐인 것" 으로 만들라고 권합니다. 이 예제의 mark 는 합쳐진 것이 화면에 보이도록 일부러 출력을 바꾸게 만들었습니다.

퀴즈 — 같은 화면, 다른 옵션

Q. 기능이 default = ["frame"] · frame = [] · shout = [] · loud = ["frame", "shout"] 인 패키지입니다. --features shout 와 --no-default-features --features frame,shout 는 같은 화면을 냈습니다. ① 왜 같습니까? ② 두 화면에서 loud 는 왜 false 입니까?

A. ① 앞의 것은 기본 기능 frame 을 켜 둔 채 shout 을 더했고, 뒤의 것은 기본 기능을 끄고 둘을 손으로 켰습니다. 켜진 기능이 둘 다 frame 과 shout 입니다. ② loud 의 목록은 "loud 를 켜면 이 둘도 켠다" 는 뜻이지, 둘이 켜지면 loud 가 켜진다는 뜻이 아닙니다. 네 번의 실행 가운데 loud=true 는 --features loud 와 --all-features 에서만 나왔습니다.

build.rs 와 컴파일 때 정보

env! · 없는 변수와 option_env! · include_str! · build.rs 와 rustc-env · rerun-if-changed · rustc-cfg · rustc-check-cfg · OUT_DIR 과 include!

env! — 컴파일할 때의 환경 변수를 실행 파일에 넣는다

18부의 env::var 는 프로그램이 도는 동안의 환경 변수를 읽었습니다. 매크로 env! 는 이름이 비슷하지만 컴파일할 때 읽습니다. 여기서 읽는 것은 Cargo 가 패키지를 컴파일할 때 정해 두는 CARGO_… 변수 셋입니다.

읽는 법 — 첫 실행에서 5번과 6번 줄은 Cargo.toml 의 name 과 version 을 찍었습니다. 7번 줄의 CARGO_MANIFEST_DIR 은 Cargo.toml 이 있는 디렉터리이고, /work 는 0부에서 말한 대로 이 책이 고정해 실은 경로입니다. 9번 줄의 env::var 도 Ok("1.4.2") 입니다. cargo run 으로 띄운 프로그램에는 그 변수가 있었습니다. 실행 파일을 직접 돌린 둘째 명령에서는 Err(NotPresent) 이고, 변수를 9.9.9 로 주고 돌린 셋째 명령에서는 Ok("9.9.9") 입니다.
env! 가 찍은 세 줄은 세 번 모두 같다 — 컴파일할 때 읽은 값이 실행 파일에 글자로 들어갔습니다. 돌릴 때의 환경 변수를 바꿔도 그 줄은 바뀌지 않았습니다.

없는 변수 — env! 는 컴파일을 멈추고, option_env! 는 None 을 준다

env! 는 Cargo 가 아니라 컴파일러의 매크로입니다. 첫 예제는 rustc 만으로 컴파일하며, 정해 준 적 없는 변수 GREETING 을 두 번 읽습니다. 그 아래는 같은 변수를 option_env! 로 읽는 패키지입니다.

읽는 법 — 첫 화면의 오류 둘에는 번호(E…)가 없습니다. 첫 오류의 첫 줄은 "환경 변수 GREETING 이 컴파일할 때 정의돼 있지 않다" 이고 env_missing.rs 의 2번 줄에 붙었습니다. help: 는 실행할 때 읽으려면 std::env::var("GREETING") 을 쓰라고 합니다. 둘째 오류의 첫 줄은 그 파일 3번 줄에 둘째 인자로 적은 글 그대로이고, help: 는 없습니다.
option_env! — main.rs 3번 줄에 적은 타입대로 Option<&'static str> 이 됩니다. 변수 없이 빌드한 첫 명령은 None 갈래를 찍었습니다. 둘째 명령은 18부에서 본 이름=값 표기로 변수를 주었고, Some 갈래가 hi 를 찍었습니다. 소스는 그대로인데 화면이 바뀌었습니다. 셋째 명령은 만들어진 실행 파일에 bye 를 주고 돌렸는데도 hi 입니다. 이것도 컴파일할 때 읽은 값입니다.

include_str! · include_bytes! — 파일의 내용을 실행 파일에 넣는다

17부의 fs::read_to_string 은 프로그램이 돌 때 파일을 열었습니다. include_str! 은 컴파일할 때 파일을 읽어 그 내용을 &str 로 넣고, include_bytes! 는 바이트로 넣습니다. 돌릴 때는 그 파일이 없어도 됩니다.

읽는 법 — cat 이 보인 한 줄이 src/motto.txt 의 전부입니다. 6번 줄이 그 글을 찍었고, 7번 줄이 바이트 수 38 과 처음 세 바이트를 찍었습니다. 그 셋이 한글 한 글자 천 입니다(한글은 3바이트). 셸의 rm 으로 파일을 지우고 실행 파일을 직접 돌려도 같은 두 줄입니다. 둘째 화면은 그 상태에서 다시 빌드한 것입니다. 2번 줄과 3번 줄에 같은 오류가 하나씩 붙었습니다. "src/motto.txt 를 읽을 수 없다" 이고, 콜론 뒤는 17부에서 본 운영 체제의 설명과 오류 번호입니다. 마지막 줄은 2장에서 본 대로 Cargo 가 덧붙인 말입니다.
경로의 기준 — 소스에 적은 것은 "motto.txt" 인데 오류가 댄 경로는 src/motto.txt 입니다. 1번 줄의 주석대로, 경로는 그 매크로를 적은 소스 파일이 있는 디렉터리에서 봅니다.

build.rs — 패키지보다 먼저 도는 프로그램이 컴파일에 값을 넘긴다

컴파일할 때 넣고 싶은 값이 Cargo 가 정해 주는 변수에 없을 때가 있습니다. Cargo.toml 옆에 build.rs 를 두면 Cargo 가 패키지를 컴파일하기 전에 그 파일을 먼저 컴파일해 돌립니다. 빌드 스크립트(build script)라고 부릅니다. 아래 것은 파일의 줄 수를 세어 넘깁니다.

읽는 법 — build.rs 5번 줄은 경로를 colors.txt 라고만 적었고, cat 이 보인 패키지 뿌리의 그 파일이 읽혔습니다. 6번 줄이 센 수는 3 입니다. 9번 줄이 찍는 글은 cargo::rustc-env=COLOR_COUNT=3 입니다. 패키지를 컴파일할 때 환경 변수 COLOR_COUNT 를 3 으로 해 달라는 뜻이고, main.rs 2번 줄의 env! 가 그것을 읽어 색은 3 가지 가 됐습니다. 7번 줄이 찍은 build.rs 가 3줄을 셌다 는 화면 어디에도 없습니다. Compiling 줄도 패키지 palette 의 것 하나뿐입니다. 10번 줄은 다음 슬라이드에서 봅니다.
콜론 둘 — 릴리스 노트는 빌드 스크립트가 패키지를 컴파일하는 환경에 환경 변수를 더할 수 있게 된 것을 로 적고, 예로 콜론이 하나인 cargo:rustc-env=FOO=bar 를 듭니다. 콜론이 둘인 cargo:: 표기는 에 들어왔습니다. 이 책은 콜론 둘로 적습니다.

rerun-if-changed — 적어 둔 파일이 바뀌자 빌드 스크립트가 다시 돌았다

앞 슬라이드 build.rs 의 10번 줄입니다. 릴리스 노트는 빌드 스크립트가 이 줄로 자기가 무엇에 기대는지를 알릴 수 있다고 적습니다. 앞 슬라이드의 첫 실행에 이어서 친 명령들입니다.

읽는 법 — 곧바로 다시 친 cargo run 에는 Compiling 줄이 없습니다. 2부에서 본 대로 다시 컴파일하지 않은 것입니다. 이 기계의 셸에서 echo purple >> colors.txt 는 그 파일 끝에 한 줄을 덧붙입니다. 그 뒤에 실행 파일을 직접 돌리면 아직 색은 3 가지 입니다. env! 의 값은 실행 파일에 들어 있기 때문입니다. 마지막 cargo run 에는 Compiling 줄이 다시 나오고 색은 4 가지 입니다. build.rs 도 main.rs 도 고치지 않았습니다. 4 라는 수는 build.rs 가 다시 돌아야 나옵니다.
보이지 않은 것 — 이 줄이 없는 빌드 스크립트를 Cargo 가 언제 다시 돌리는지는 이 책이 화면으로 보이지 않습니다. 환경 변수가 바뀔 때를 적는 줄은 다음 슬라이드에 있습니다.

cargo::rustc-cfg — 빌드 스크립트가 cfg 이름을 켠다

2장의 기능은 Cargo.toml 에 선언하고 명령 줄에서 켰습니다. 빌드 스크립트는 자기가 알아본 것에 따라 조건부 컴파일에 쓸 이름을 직접 켤 수 있습니다. 여기서는 빌드할 때 환경 변수 WITH_BANNER 가 있는지를 봅니다.

읽는 법 — build.rs 7번 줄의 env::var 가 Ok 일 때만 8번 줄이 cargo::rustc-cfg=with_banner 를 찍습니다. main.rs 2번 줄의 cfg!(with_banner) 는 2부의 cfg!(debug_assertions) 처럼 이름 하나짜리 조건입니다. 첫 화면의 세 실행은 변수가 있을 때만 === palette === 를 찍었습니다. build.rs 의 5번 줄은 다음 슬라이드에서 봅니다.
build.rs 의 6번 줄 — cargo::rerun-if-env-changed=WITH_BANNER 는 앞 슬라이드의 rerun-if-changed 와 짝입니다. 파일 대신 환경 변수의 이름을 적습니다. 그 줄만 뺀 쌍둥이를 돌린 것이 둘째 화면입니다. 변수를 주고 돌려도 === palette === 가 없습니다. 위 build.rs 의 8번 줄에 해당하는 글이 Cargo 에 닿지 않았다는 뜻이고, 빌드 스크립트가 다시 돌지 않은 것입니다.

rustc-check-cfg 를 빼면 뜻밖의 cfg 이름이라고 경고한다

앞 슬라이드 build.rs 의 5번 줄만 뺀 쌍둥이를 변수를 주고 돌립니다. 2장에서 소스의 오타를 잡은 unexpected_cfgs 가 이번에는 빌드 스크립트가 켜는 이름을 낯설어합니다. 릴리스 노트는 컴파일할 때 cfg 의 이름과 값을 검사하는 --check-cfg 를 에서 안정화했다고 적습니다.

읽는 법 — 경고 첫 줄은 "뜻밖의 cfg 조건 이름: with_banner" 입니다. 2장의 경고는 값이었고 이번에는 이름입니다. main.rs 2번 줄에 붙었습니다. 첫 help: 는 아는 이름으로 docsrs · feature · test 와 "그 밖 34개" 를 댑니다. 34 는 이 책의 컴파일러가 댄 수입니다. 다음 세 help: 가 고치는 길입니다. Cargo 의 기능으로 바꾸거나, Cargo.toml 의 [lints.rust] 에 적힌 대로 알리거나, build.rs 맨 위에 println!("cargo::rustc-check-cfg=cfg(with_banner)"); 를 넣으라고 합니다. 셋째가 앞 슬라이드의 5번 줄입니다. 그 아래 두 note: 는 설명이 있는 주소와 경고의 이름입니다. 경고 뒤에 === palette === 와 red green blue 가 찍혔습니다. [lints] 표는 5장에서 봅니다.

OUT_DIR 에 소스를 만들어 두고 include! 로 끼워 넣는다

rustc-env 로 넘긴 것은 글 한 줄이었습니다. 배열 같은 코드를 넘기려면 빌드 스크립트가 Rust 소스 파일을 만들고, 패키지가 그 파일을 자기 소스에 끼워 넣습니다. 만든 파일을 둘 디렉터리는 Cargo 가 환경 변수 OUT_DIR 로 알려 줍니다. colors.txt 는 앞의 세 줄짜리 그대로입니다.

읽는 법 — 첫 명령이 찍은 것이 배열 COLORS 의 길이와 내용입니다. build.rs 는 도는 프로그램이므로 16번 줄에서 OUT_DIR 을 env::var 로 읽고, 17번 줄에서 그 아래에 colors.rs 를 씁니다 (fs::write · join). main.rs 2번 줄은 같은 변수를 env! 로 읽습니다. 16부에서 써 본 concat! 이 거기에 "/colors.rs" 를 이어 경로를 만들고, include! 가 그 파일의 내용을 그 자리에 Rust 소스로 넣습니다. main.rs 5번 줄의 COLORS 가 그렇게 들어온 이름입니다. build.rs 6번 줄은 앞에서 본 줄입니다.
만들어진 파일 — 둘째 명령의 cat 이 보인 한 줄이 build.rs 10번부터 14번 줄까지가 적은 글입니다. ls 가 보인 대로 src/ 에는 main.rs 뿐이고, 만든 파일은 target/ 아래에 있습니다. 경로 가운데 palette- 뒤는 Cargo 가 붙인 글자들이라 * 로 받았습니다.

퀴즈 — 언제 정해진 값인가

Q. build.rs 가 colors.txt 의 줄 수를 세어 cargo::rustc-env=COLOR_COUNT=… 로 넘기고 cargo::rerun-if-changed=colors.txt 도 찍는 패키지입니다. cargo run 이 색은 3 가지 를 찍었습니다. colors.txt 에 한 줄을 더한 뒤 ① ./target/debug/palette 를 직접 돌리면 무엇이 찍히고, ② 이어서 cargo run 을 하면 무엇이 찍힙니까?

A. ① 색은 3 가지 그대로입니다. env! 가 읽은 값은 컴파일할 때 실행 파일에 들어갔고, 그 파일은 아직 그대로입니다. ② 색은 4 가지 입니다. Compiling 줄이 다시 나오고 새 수가 넘어옵니다. 둘 다 rerun-if-changed 의 화면에서 본 차례입니다.
