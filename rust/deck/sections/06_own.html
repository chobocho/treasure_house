6부

소유권·빌림·슬라이스

주인은 하나 · 대입하면 이동 · clone 과 Copy · &T 와 &mut T · 빌림 규칙 · 슬라이스

이 부에서 할 일

Rust 가 다른 언어와 가장 다른 곳입니다. 가비지 컬렉터 없이 메모리를 안전하게 다루려고 Rust 는 "값마다 주인이 하나" 라는 규칙을 골랐고, 뒤의 부들은 모두 이 규칙 위에 서 있습니다.

  • 1장 — 왜 소유권인가: 메모리는 누가 돌려주는가, 스택과 힙, 범위가 끝나면 정리된다
  • 2장 — 이동: 대입하고 함수에 넘기면 주인이 바뀐다, clone 과 Copy
  • 3장 — 참조와 빌림: 주인을 바꾸지 않고 읽고(&T) 고친다(&mut T)
  • 4장 — 빌림 규칙: 읽는 쪽 여럿 아니면 고치는 쪽 하나
  • 5장 — 슬라이스: 값의 한 구간만 빌리기
  • 6장 — 실전 패턴: 무엇을 받고 무엇을 돌려줄 것인가
예제의 주인공은 String — 힙에 값을 두는 타입 가운데 가장 흔해서입니다. 여기서는 소유권을 보는 데 필요한 만큼만 쓰고, 문자열 다루는 법은 8부에서 봅니다.

1장

왜 소유권인가

메모리는 누가 돌려주는가 · 스택과 힙 · 규칙 세 줄 · 범위가 끝나면 정리된다

빌린 메모리는 누가 돌려주는가

길이를 미리 알 수 없는 값은 실행 중에 메모리를 얻어 담습니다. 다 쓰면 돌려줘야 합니다. 누가, 언제 돌려주는지가 언어마다 다릅니다.

방식누가 돌려주나치르는 값
손으로
C 의 malloc·free		프로그래머잊으면 샌다. 두 번 돌려주거나 돌려준 뒤에 쓰면 프로그램이 망가진다.
가비지 컬렉터
Java·Go·Python·JavaScript		실행 중에 도는 수거기수거에 시간과 메모리가 든다. 언제 돌려줄지 정할 수 없다.
소유권
Rust		컴파일러가 넣어 둔 코드규칙을 어긴 코드는 컴파일되지 않는다.
Rust 의 답 — 값마다 주인(owner)을 하나 정하고, 주인이 사라질 때 값도 함께 정리합니다. 검사는 컴파일할 때 끝납니다.

스택과 힙

크기가 정해진 값은 스택(stack)에 놓입니다. 길이가 바뀌는 값은 힙(heap)에 자리를 얻고, 스택에는 그 자리를 가리키는 작은 머리만 둡니다. String 이 그렇습니다.

   스택                              힙
   (크기가 정해진 값)                (실행 중에 얻는 공간)

s  +----------+-----+                +---+---+---+---+---+
   | ptr      |  *--+-------------->| h | e | l | l | o |
   | len      |  5  |                +---+---+---+---+---+
   | capacity |  5  |
   +----------+-----+
n  | 42             |
   +----------------+
  • ptr 힙의 어디인가 · len 지금 몇 바이트를 쓰는가 · capacity 몇 바이트까지 얻어 두었는가 (뒤의 그림에서는 cap 으로 줄여 적습니다)
  • 정수 n 은 값 전체가 스택에 있습니다. 돌려줄 것이 없습니다.

문자열 리터럴과 String 은 다른 타입이다

지금까지 쓴 "hello" 는 실행 파일 안에 박혀 있는 글자입니다. 힙을 쓰지 않습니다. 힙에 글자를 두는 타입은 String 이고, String::from 으로 만듭니다.

&str 과 String — 리터럴의 타입 &str 은 "어딘가에 있는 글자를 가리키는 것" 이고 String 은 "글자를 직접 가진 것" 입니다. 이 부에서 차츰 분명해집니다. 출력의 alloc::string::String 은 String 을 경로까지 적은 이름입니다.

String 의 머리는 늘 세 칸이다

그림의 세 칸을 숫자로 확인합니다. 이 기계(64비트)에서 한 칸은 8바이트이므로 머리는 24바이트입니다.

len 과 capacity — 두 글자를 붙이자 힙의 자리를 10바이트로 넓혀 다시 얻었고, 그 가운데 7바이트를 씁니다. len 은 쓰는 만큼, capacity 는 얻어 둔 만큼입니다.

소유권 규칙 세 줄

힙의 글자들을 누가 돌려줄지 정하는 규칙입니다. 이 부 전체가 이 세 줄을 풀어 쓴 것입니다.

  1. 값에는 주인(owner)인 변수가 있다.
  2. 주인은 한 번에 하나뿐이다.
  3. 주인이 범위(scope)를 벗어나면 값은 정리된다.
소유권(ownership) — 어떤 값을 정리할 책임입니다. let s = String::from("hello"); 에서 s 가 그 글자들의 주인입니다. 3번은 바로 다음 슬라이드에서, 2번은 2장에서 확인합니다.

범위가 끝나면 값은 정리된다

정리되는 순간을 눈으로 보려고, 사라질 때 한 줄을 찍는 타입을 만들었습니다(struct 와 impl 은 7부). Drop 은 값이 정리될 때 할 일을 적는 트레이트이며 14부에서 봅니다.

읽는 법 — _b 는 안쪽 블록이 닫힐 때, _a 는 main 이 닫힐 때 정리됩니다. 우리가 부른 적 없는 drop 이 그 자리에서 불렸습니다. 컴파일러가 넣어 둔 것입니다.

함수가 끝날 때도 마찬가지다

함수의 본문도 범위입니다. 함수 안에서 만든 값은 함수가 돌아갈 때 정리됩니다.

String 도 똑같다 — String 의 정리는 힙의 글자들을 돌려주는 일입니다. 그래서 free 를 쓸 일이 없고, 잊을 수도 없습니다. 자원을 값에 묶어 값이 사라질 때 함께 돌려주는 이 방식을 RAII 라고 부릅니다.

퀴즈 — 왜 소유권인가

Q. 100글자짜리 String 과 5글자짜리 String 에 size_of_val 을 쓰면 값이 다를까요? 그리고 그 글자들이 차지한 힙은 언제 돌려줄까요?

A. 같습니다. size_of_val 이 세는 것은 스택의 머리 세 칸(이 기계에서 24바이트)이고, 글자는 힙에 있습니다(머리는 늘 세 칸). 힙은 주인인 변수의 범위가 끝날 때 돌려줍니다 (범위가 끝나면).

2장

이동

대입하면 주인이 바뀐다 · clone · Copy 타입 · 함수에 넘기기와 돌려받기 · 일부만 옮기기

대입하면 소유권이 옮겨 간다 — E0382

다른 언어라면 아무 일도 없는 코드입니다. Rust 에서는 let s2 = s1; 이 값의 주인을 s2 로 바꿉니다. 이것을 이동(move)이라 하고, 그 뒤로 s1 은 쓸 수 없습니다.

읽는 법 — 세 자리를 짚습니다. 2번 줄: s1 의 타입은 Copy 가 아니라서 이동한다. 3번 줄: 여기서 옮겼다. 6번 줄: 옮긴 뒤에 썼다. println! 은 값을 빌려서 찍기 때문에 "borrow of moved value" 라고 합니다.

옮겨 가는 것은 머리 세 칸이다

이동할 때 복사되는 것은 스택의 머리뿐입니다. 힙의 글자들은 그 자리에 그대로 있고, 가리키는 쪽만 s2 로 바뀝니다.

            스택                        힙

s1  +-----+-----+
    | ptr |  *  |   더 쓸 수 없다
    | len |  5  |
    | cap |  5  |
    +-----+-----+
          |
          |  머리 세 칸만 복사
          v
s2  +-----+-----+                 +---+---+---+---+---+
    | ptr |  *--+---------------->| h | e | l | l | o |
    | len |  5  |                 +---+---+---+---+---+
    | cap |  5  |                  복사하지 않는다
    +-----+-----+
s1 은 어떻게 되나 — 컴파일러가 그 이름을 더 쓰지 못하게 막습니다. 그 검사는 앞의 E0382 처럼 컴파일할 때 끝납니다.

왜 막는가 — 주인이 둘이면 두 번 정리한다

s1 과 s2 가 둘 다 주인이라면, 범위가 끝날 때 같은 힙을 두 번 돌려주게 됩니다. C 에서 이중 해제(double free)라 부르는 버그입니다. 주인이 하나이면 정리도 한 번입니다.

읽는 법 — a 가 범위를 벗어날 때는 아무 일도 일어나지 않았습니다. 값을 넘겨준 이름은 더는 주인이 아니기 때문입니다.

둘 다 쓰려면 clone 으로 복사한다

컴파일러의 help: 가 권한 방법입니다. clone() 은 힙의 글자까지 새로 만들어, 서로 상관없는 값 둘을 만듭니다.

공짜가 아니다 — help: 에 "성능 비용을 받아들일 수 있다면" 이라는 단서가 붙어 있었습니다. 글자 수만큼 힙을 새로 얻어 베낍니다. 읽기만 할 것이라면 3장의 빌림이 답입니다.

정수는 옮겨 가지 않고 복사된다

정수는 다른 변수에 대입한 뒤에도 원래 변수를 쓸 수 있습니다. 정수·실수·bool·char 는 값 전체가 스택에 있어서, 그대로 베끼면 온전한 복사본이 됩니다. 이런 타입을 Copy 타입이라 합니다.

Copy 가 되는 까닭 — 따로 돌려줄 힙이 없습니다. 주인이 둘이어도 두 번 정리할 것이 없으니 막을 이유가 없습니다.

힙을 가진 값이 하나라도 들어 있으면 Copy 가 아니다 — E0382

앞에서 튜플 (1, 2.0) 은 복사됐습니다. String 을 하나 넣으면 튜플 전체가 이동하는 타입이 됩니다.

읽는 법 — 2번 줄의 설명에 타입이 통째로 적혀 있습니다. "(i32, String) 은 Copy 가 아니다". 이동인지 복사인지는 값이 아니라 타입이 정합니다.

함수에 넘기는 것도 이동이다 — E0382

인자를 넘기는 것은 매개변수에 대입하는 것과 같습니다. String 을 넘기면 주인이 함수의 매개변수로 바뀌고, 함수가 끝날 때 거기서 정리됩니다.

읽는 법 — 7번 줄에서 옮겼고 8번 줄에서 썼습니다. note: 는 함수 쪽을 짚습니다. "이 매개변수가 소유권을 가져간다. 가질 필요가 없다면 빌리도록 바꿔라". 그 방법이 3장입니다.

돌려받으면 다시 쓸 수 있다

반환도 이동입니다. 함수가 받은 값을 돌려주면 주인이 부른 쪽으로 돌아옵니다. 길이까지 알려 주려면 튜플로 묶어야 합니다.

번거롭다 — 길이 하나 알자고 값을 줬다가 되받습니다. 돌아가기는 하지만 함수마다 이렇게 쓸 수는 없습니다. 3장의 참조가 이 불편을 없앱니다.

함수 안에서 만든 값을 돌려준다

1장에서 함수 안의 값은 함수가 끝날 때 정리된다고 했습니다. 돌려주는 값은 예외입니다. 정리되지 않고 주인만 바뀝니다.

복사도 없다 — 힙의 별들은 한 번 만들어진 그 자리에 있습니다. 부른 쪽이 받는 것은 머리 세 칸입니다.

반복문 안에서 옮기면 두 번째 바퀴가 없다 — E0382

한 번만 쓰는 것처럼 보이지만, 반복문은 같은 줄을 여러 번 지납니다. 첫 바퀴에서 넘긴 값은 둘째 바퀴에 없습니다.

읽는 법 — 옮긴 줄과 쓴 줄이 같은 8번 줄입니다. 그래서 "앞 바퀴에서 여기서 옮겼다(in previous iteration of loop)" 고 하고, 7번 줄에 "이 반복문 안" 이라는 표시를 답니다.

바퀴마다 새 값을 넘긴다

함수가 소유권을 꼭 가져가야 한다면 돌 때마다 복사본을 만들어 넘깁니다. 원본은 main 에 남습니다.

먼저 물을 것 — consume 이 정말 값을 가져야 할까요? 찍기만 한다면 빌려 받게 고치는 편이 낫습니다(3장). 복사는 그다음 수단입니다.

벡터의 칸에서 값을 빼낼 수는 없다 — E0507

names[0] 을 변수에 대입하면 이동이 되어야 합니다. 그러면 벡터의 첫 칸은 주인 없는 빈 자리가 됩니다. Rust 는 그런 벡터를 허락하지 않습니다.

읽는 법 — "인덱스로 가리킨 자리에서는 옮겨 낼 수 없다". help: 가 둘입니다. 빌리거나 (&names[0]), 복사하거나(.clone()). 까닭으로 든 것은 이번에도 "String 은 Copy 가 아니다" 입니다.

칸의 값을 얻는 네 가지 길

정수처럼 Copy 인 칸은 그냥 복사됩니다. String 이라면 복사한다, 빌린다, 꺼내서 벡터에서 뺀다, 벡터를 통째로 넘긴다 가운데서 고릅니다. 벡터 자체는 8부에서 봅니다.

3번과 4번 — remove 는 값을 내주고 뒤의 칸을 당겨 채웁니다. for name in names 는 벡터를 통째로 옮겨 받아 값을 하나씩 내줍니다.

튜플의 한 칸만 옮기면 전체는 쓸 수 없다 — E0382

튜플의 칸은 하나씩 따로 옮길 수 있습니다. 다만 한 칸이 빠진 튜플은 온전한 값이 아니므로, 전체를 쓰려 하면 막힙니다.

읽는 법 — 이번에는 "부분 이동(partial move)" 이라고 합니다. 3번 줄에서 pair.0 만 옮겨졌고, 6번 줄에서 pair 전체를 빌리려 했습니다. note: 는 그 칸의 타입이 Copy 가 아니라서 옮겨졌다고 덧붙입니다.

옮기지 않은 칸은 그대로 쓴다

컴파일러는 칸마다 따로 추적합니다. pair.0 이 떠났어도 pair.1 의 주인은 여전히 pair 입니다.

둘 다 필요하면 — 패턴으로 한 번에 풉니다. both 는 통째로 비고, a 와 b 가 한 칸씩 주인이 됩니다.

비운 변수에 새 값을 넣을 수 있다

이동으로 못 쓰게 되는 것은 값이지 변수의 자리가 아닙니다. mut 변수라면 새 값을 대입해 다시 주인으로 만들 수 있습니다.

이동은 싸다

아무리 긴 문자열도 옮길 때 복사되는 것은 머리 세 칸입니다. 값을 함수에 넘기고 돌려받는 일을 겁낼 까닭이 없습니다.

이동과 clone 의 차이 — 이동은 머리만 베끼고 앞 이름을 못 쓰게 합니다. clone 은 힙까지 베끼고 둘 다 살려 둡니다. Rust 는 비싼 쪽을 글자로 적어야만 일어나게 해 두었습니다.

퀴즈 — 이동

Q. let a = 5; let b = a; 뒤에는 a 를 쓸 수 있고, let s = String::from("x"); let t = s; 뒤에는 s 를 쓸 수 없습니다. 왜 다를까요? s 도 쓰고 싶다면 어떻게 할까요?

A. 정수는 Copy 타입이라 값이 복사되고(정수는 복사된다), String 은 힙을 가진 타입이라 소유권이 옮겨 갑니다(대입하면 이동). 둘 다 쓰려면 let t = s.clone(); 으로 힙까지 복사합니다(clone).

3장

참조와 빌림

&T 로 읽기 · &mut T 로 고치기 · * 로 따라가기 · 참조를 돌려주기 · 셋을 견준 표

& 를 붙이면 넘기지 않고 빌려준다

2장에서는 길이 하나 알자고 값을 줬다가 되받았습니다. 매개변수를 &String 으로 적으면 함수는 값을 갖지 않고 잠깐 보기만 합니다. 이것이 빌림(borrowing)이고, &s 로 만든 것이 참조(reference)입니다.

두 군데에 적는다 — 함수는 타입에 &String, 부르는 쪽은 값에 &s. 부르는 코드만 봐도 "넘기는 것이 아니라 빌려주는 것" 임이 보입니다.

참조는 주인을 가리키는 한 칸이다

참조는 값이 있는 자리를 담은 한 칸입니다. 힙의 글자를 직접 가리키지 않고, 주인의 머리를 가리킵니다.

r                  s                           힙

+-----+            +-----+-----+
|  *--+----------->| ptr |  *--+------------>+---+---+---+---+---+
+-----+            | len |  5  |             | h | e | l | l | o |
참조: 한 칸        | cap |  5  |             +---+---+---+---+---+
                   +-----+-----+
                   주인: 머리 세 칸
C 의 포인터와 다른 점 — Rust 의 참조는 늘 살아 있는 값을 가리킵니다. 그것을 컴파일러가 어떻게 지키는지가 4장과 11부입니다.

빌려준 값은 부른 쪽에 남는다

1장의 Noisy 로 견줍니다. 값을 받은 함수는 주인이 되어 그 값을 정리합니다. 참조를 받은 함수는 아무것도 정리하지 않습니다.

읽는 법 — a 정리 는 take 가 돌아가는 자리에, b 정리 는 main 끝 뒤에 찍혔습니다. 참조는 주인이 아니므로 사라져도 값은 그대로입니다.

& 로 빌린 값은 고칠 수 없다 — E0596

변수가 기본으로 불변이듯 참조도 기본으로 불변입니다. &String 으로 받은 함수는 읽을 수만 있습니다.

읽는 법 — "s 는 & 참조라서 가변으로 빌릴 수 없다". push_str 은 값을 고치는 메서드라 고칠 수 있는 참조가 필요합니다. help: 가 1번 줄의 타입을 &mut String 으로 바꾸라고 합니다.

고치려면 &mut 로 빌린다

가변 참조(mutable reference) &mut T 는 빌린 값을 고칠 수 있는 참조입니다. 이번에도 두 군데에 적습니다. 타입에 &mut String, 부르는 쪽에 &mut s.

부르는 쪽에서 보인다 — add_world(&mut s) 를 보면 이 함수가 s 를 고칠 수 있다는 것을 함수 본문을 열지 않고도 압니다.

변수가 mut 여야 &mut 로 빌려줄 수 있다 — E0596

앞의 코드에서 let mut s 의 mut 만 뺐습니다. 주인도 고칠 수 없는 값을 남에게 "고쳐도 된다" 며 빌려줄 수는 없습니다.

같은 번호, 다른 자리 — 앞의 E0596 은 "참조가 & 다" 였고 고칠 곳은 함수의 타입이었습니다. 이번은 "변수가 가변으로 선언되지 않았다" 이고 고칠 곳은 6번 줄의 let 입니다. help: 대로 고치면 앞 슬라이드의 코드가 됩니다.

* 로 참조가 가리키는 값에 닿는다

참조는 값 자체가 아니라 값을 가리키는 것입니다. 가리키는 값을 꺼내 계산하거나 고치려면 앞에 * 를 붙입니다. 역참조(dereference)라 합니다.

  • *r + 1 — 정수는 Copy 라서 참조를 따라가 값을 복사해 옵니다. a 는 그대로입니다.
  • *m += 1 — &mut 를 따라가 n 자체를 고칩니다.

메서드와 println! 은 알아서 따라간다

그런데 지금까지 s.len() 에도 println!("{s}") 에도 * 를 쓰지 않았습니다. 점(.)으로 메서드를 부를 때와 값을 찍을 때는 참조를 자동으로 따라가기 때문입니다.

그래서 * 를 쓸 일은 참조가 가리키는 값을 직접 계산하거나 대입할 때 정도입니다. 앞 슬라이드의 *r + 1, *m += 1 같은 자리입니다.

받은 &mut 를 다른 함수에 넘긴다

매개변수 x 는 이미 &mut i32 입니다. 아래 함수에 넘길 때는 &mut 를 다시 붙이지 않고 그대로 줍니다.

두 번 넘겨도 된다 — add_one(x) 를 연달아 불렀습니다. 넘길 때마다 x 를 잠깐 다시 빌려주고, 함수가 돌아오면 되찾습니다. 재빌림(reborrow)이라 하며 따로 적을 것은 없습니다.

받은 값의 안쪽을 가리키는 참조는 돌려줄 수 있다

함수가 참조를 돌려주기도 합니다. 빌려 받은 튜플의 한 칸을 골라 그 참조를 내줍니다. 가리키는 값은 부른 쪽에 있으므로 함수가 끝나도 사라지지 않습니다.

어디서 온 참조인가 — 받은 참조가 하나뿐이면 컴파일러는 돌려주는 참조가 거기서 나왔다고 봅니다. 이 관계를 따지는 개념이 수명이며 11부에서 봅니다.

함수 안에서 만든 값의 참조는 돌려줄 수 없다 — E0515

시그니처는 앞과 같은 모양입니다. 하지만 이번에 돌려주려는 것은 받은 값이 아니라 함수 안에서 새로 만든 loud 를 가리키는 참조입니다.

읽는 법 — "지역 변수 loud 의 참조를 돌려줄 수 없다 — 이 함수가 주인인 값을 가리킨다". 주인이 함수 안에 있으니 함수가 끝나면 값이 정리되고, 참조는 사라진 값을 가리키게 됩니다.

새로 만든 값은 통째로 돌려준다

반환 타입에서 & 를 떼고 값을 그대로 돌려줍니다. 2장에서 본 대로 주인이 부른 쪽으로 바뀌므로 정리되지 않습니다.

가르는 기준 — 받은 것의 일부를 가리키면 참조로, 함수 안에서 만든 것이면 값으로 돌려줍니다.

퀴즈 — 참조와 빌림

Q. fn add(s: &String) { s.push_str("!"); } 를 let s = String::from("hi"); add(&s); 로 부릅니다. 컴파일되게 하려면 몇 군데를 고쳐야 할까요?

A. 세 군데입니다. 매개변수 타입을 &mut String 으로 (& 로는 고칠 수 없다), 부르는 쪽을 add(&mut s) 로 (&mut 로 빌린다), 그리고 변수를 let mut s 로 (변수가 mut 여야).
