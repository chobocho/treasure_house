14부

스마트 포인터

Box · Deref 와 Drop · Rc · RefCell · Weak — 소유권 규칙을 넓히는 라이브러리 타입들

이 부에서 할 일

소유권의 기본 규칙은 "주인은 하나, 고치려면 혼자 빌린다" 였습니다. 실제 프로그램에는 그 틀에 안 맞는 모양이 있습니다 — 자기를 품는 타입, 여럿이 함께 갖는 값, 불변 참조 뒤에서 고치기. 그럴 때 쓰는 것이 스마트 포인터입니다. 전부 표준 라이브러리의 평범한 타입입니다.

  • 1장 — Box<T>: 값을 힙에 두기, 재귀 타입
  • 2장 — Deref 와 Drop: 포인터처럼 보이게 하는 두 트레이트
  • 3장 — Rc<T>: 주인이 여럿인 값
  • 4장 — RefCell<T> 와 Cell<T>: 내부 가변성
  • 5장 — Weak<T> 와 순환 참조, 고르는 법

1장

Box

값을 힙에 · 재귀 타입에는 Box 가 필요하다 · 수식 나무

Box — 값을 힙에 두고 주소를 가진다

Box::new(값) 은 값을 힙에 놓고, 그 자리를 가리키는 포인터를 돌려줍니다. 주인이 하나라는 규칙은 그대로입니다. Box 가 사라지면 힙의 값도 함께 정리됩니다.

마지막에 찍힌 8 — Box 자체의 크기는 속에 무엇이 들었든 포인터 하나(이 기계에서 8바이트)입니다. 다음 장이 이 성질을 씁니다.

자기를 품는 타입은 크기를 정할 수 없다 — E0072

"목록은 값 하나와 나머지 목록" 이라고 그대로 적으면, 컴파일러는 이 타입의 크기를 계산하다 끝이 나지 않습니다. List 안에 List 가, 그 안에 또 List 가 있기 때문입니다.

Box 로 끊는다

나머지 목록을 통째로 품는 대신 Box 에 넣어 가리킵니다. Box 의 크기는 정해져 있으므로 List 의 크기도 정해집니다.

16 바이트 — 정수 하나와 포인터 하나의 자리입니다. 목록이 아무리 길어도 타입의 크기는 같습니다.

나무 모양 자료 — 수식

재귀 타입이 가장 자주 쓰이는 곳은 나무입니다. 수식 (1 + 2) * 4 를 열거형으로 적고 재귀 함수로 계산합니다.

Box 도 주인은 하나다 — E0382

Box 를 다른 변수에 넣으면 이동합니다. 포인터만 옮겨 가고 힙의 값은 제자리에 있지만, 옛 이름은 더 쓸 수 없습니다.

큰 값을 싸게 넘기기 — 큰 구조체를 Box 에 넣어 두면 넘길 때 포인터 하나만 옮겨집니다.

Box<dyn Trait> — 다른 타입들을 한 그릇에

10부에서 본 트레이트 객체입니다. Circle 과 Square 는 크기가 다르지만 Box 에 넣으면 둘 다 포인터라 한 벡터에 담깁니다.

퀴즈 — Box

Q. enum List { Cons(i32, List), Nil } 은 왜 컴파일되지 않고, Cons(i32, Box<List>) 는 왜 될까요?

A. 앞의 것은 List 가 자기를 통째로 품어 크기가 끝없이 커집니다(E0072). Box 는 속이 무엇이든 포인터 하나 크기라서, 그것을 품은 List 의 크기가 정해집니다 (Box 로 끊는다).

2장

Deref 와 Drop

* 가 하는 일 · 내 타입에 * 붙이기 · 역참조 강제 · 정리되는 순서 · 미리 정리하기

참조처럼 따라간다

Box 가 "스마트 포인터" 인 까닭의 절반입니다. 참조에 하듯 * 로 속의 값에 닿고, 메서드를 부를 때는 그마저 생략합니다.

아무 타입에나 * 를 쓸 수는 없다 — E0614

값 하나를 감싼 내 구조체입니다. Box 와 닮았지만 * 를 붙이면 컴파일러가 거절합니다.

Deref 를 구현하면 * 가 된다

* 는 Deref 트레이트의 deref 메서드를 부르는 연산자입니다. 구현해 주면 내 타입도 포인터처럼 쓸 수 있습니다.

type Target = T; 는 연관 타입입니다(10부). "* 를 붙이면 무엇이 나오는가" 를 적습니다.

역참조 강제 — &String 이 &str 자리에 들어가는 까닭

&str 을 받는 함수에 &String 을 넘겨 왔습니다. 타입이 다른데도 됐던 것은 컴파일러가 Deref 를 필요한 만큼 대신 불러 주기 때문입니다.

참조에서만, 정해진 길로만 — 일어나는 것은 Deref 를 따라가는 변환뿐입니다. i32 가 i64 로 바뀌는 식의 암묵 변환은 여전히 없습니다.

Drop — 사라질 때 할 일

스마트 포인터의 나머지 절반입니다. 값이 범위를 벗어날 때 Drop 의 drop 이 불립니다. Box 는 여기서 힙을 돌려주고, 파일은 닫히고, 잠금은 풀립니다.

만든 순서의 거꾸로 — b 가 a 보다 먼저 정리됩니다. 나중에 만든 것이 먼저 만든 것을 빌리고 있을 수 있기 때문입니다.

미리 정리하려면 drop(값)

범위 끝까지 기다리지 않고 지금 정리하고 싶을 때는 함수 drop 에 값을 넘깁니다. 소유권이 그 함수로 옮겨 가고, 함수가 끝나며 정리됩니다.

drop 메서드를 직접 부를 수는 없다 — E0040

직접 부를 수 있다면 범위 끝에서 한 번 더 불려 두 번 정리될 것입니다. 그래서 막혀 있습니다.

퀴즈 — Deref 와 Drop

Q. 한 함수에서 a, b 순서로 만든 두 값은 함수가 끝날 때 어떤 순서로 정리될까요?

A. b 가 먼저, a 가 나중입니다. 만든 순서의 거꾸로입니다 (Drop). 순서를 바꾸고 싶으면 drop(a); 로 먼저 정리합니다.

3장

Rc

주인이 여럿 · 세는 포인터 · 마지막 주인이 사라질 때 · 고칠 수는 없다

두 목록이 꼬리를 함께 쓰고 싶다 — E0382

3 → 5 → 10 과 4 → 5 → 10 이 5 → 10 부분을 함께 쓰게 하려 합니다. Box 로는 안 됩니다. 꼬리의 주인은 하나뿐이라 첫 목록에 넣는 순간 옮겨 갑니다.

Rc — 주인을 세는 포인터

Rc<T>(reference counted)는 값 옆에 "주인이 몇인가" 를 적어 둡니다. Rc::clone 은 값을 복사하지 않고 그 수만 하나 올립니다.

관례 — tail.clone() 이라고 써도 같지만, 값을 통째로 복사하는 clone 과 구별하려고 Rc::clone(&tail) 로 씁니다.

수는 오르고 내린다

Rc 를 하나 더 만들면 수가 오르고, 하나가 사라지면 내립니다. Rc::strong_count 로 지금 수를 볼 수 있습니다.

마지막 주인이 사라질 때 정리된다

수가 0 이 되는 순간 값이 정리됩니다. 그 전에는 누가 사라져도 값은 남습니다.

1부에서 본 것 — Rust 는 가비지 컬렉터를 버렸습니다. 참조를 세는 방식은 필요한 값에만, 쓰는 사람이 직접 고릅니다.

Rc 속의 값은 고칠 수 없다 — E0596

주인이 여럿이라는 것은 읽는 쪽이 여럿이라는 뜻입니다. 빌림 규칙(여럿이 읽거나, 혼자 쓰거나)에 따라 Rc 는 불변 접근만 줍니다.

그래도 고쳐야 한다면 다음 장의 RefCell 과 함께 씁니다.

퀴즈 — Rc

Q. let a = Rc::new(v); let b = Rc::clone(&a); drop(a); 뒤에 v 는 정리됐을까요?

A. 아닙니다. 주인이 둘이었다가 하나(b)가 남았습니다. b 까지 사라져 수가 0 이 될 때 정리됩니다(마지막 주인).

4장

RefCell 과 Cell

내부 가변성 · 빌림 검사를 실행 중으로 · Rc<RefCell<T>> · Cell

RefCell — mut 없이 고친다

RefCell<T> 는 불변으로 보이는 값의 속을 고칠 수 있게 해 줍니다. borrow() 로 읽는 빌림을, borrow_mut() 로 쓰는 빌림을 얻습니다. 이것을 내부 가변성(interior mutability)이라고 합니다.

규칙은 그대로다 — 검사하는 때만 다르다

"여럿이 읽거나, 혼자 쓰거나" 는 여기서도 지켜져야 합니다. 다만 컴파일할 때가 아니라 실행 중에 검사합니다. 어기면 컴파일 오류가 아니라 패닉입니다.

컴파일러가 못 잡는다 — 이 파일은 경고 없이 컴파일됐습니다. RefCell 을 쓰면 빌림 오류를 찾는 일이 컴파일러에게서 시험과 실행으로 넘어옵니다.

패닉 대신 물어보기 — try_borrow_mut

try_ 가 붙은 쪽은 빌릴 수 없을 때 패닉하지 않고 Err 를 돌려줍니다. 빌림은 그것을 들고 있던 값이 사라질 때 끝납니다.

&self 메서드에서 속을 고친다

가장 흔한 쓰임새입니다. 바깥에서 보기에는 읽기만 하는 메서드(&self)인데, 안에서는 횟수를 세거나 기록을 남겨야 할 때입니다.

Cell — 빌려주지 않고 통째로 바꾼다

정수처럼 복사되는 작은 값에는 Cell<T> 가 더 간단합니다. 빌림을 내주지 않고 get 으로 값을 복사해 꺼내고 set 으로 통째로 넣습니다. 빌림이 없으니 실행 중 패닉도 없습니다.

Rc<RefCell<T>> — 여럿이 갖고, 누구든 고친다

Rc 는 여럿이 갖게 하지만 고칠 수 없고, RefCell 은 고칠 수 있게 하지만 주인은 하나입니다. 둘을 겹치면 "함께 갖고 함께 고치는 값" 이 됩니다.

읽는 순서 — 바깥이 Rc(누가 갖는가), 안쪽이 RefCell(어떻게 고치는가)입니다. 스레드 사이에서는 같은 구실을 Arc<Mutex<T>> 가 합니다(15부).

퀴즈 — RefCell

Q. let r = cell.borrow(); let w = cell.borrow_mut(); 은 컴파일될까요? 실행하면요?

A. 컴파일은 됩니다. 실행하면 둘째 줄에서 "RefCell already borrowed" 로 패닉합니다 (규칙은 그대로다). RefCell 은 빌림 규칙을 없애는 것이 아니라 검사를 실행 중으로 미룹니다.

5장

Weak 와 순환 참조

서로를 가리키면 아무도 정리되지 않는다 · 약한 참조 · 부모를 아는 나무 · 고르는 법

고리를 만들면 새어 나간다

a 가 b 를, b 가 a 를 Rc 로 가리킵니다. main 이 끝나 변수 둘이 사라져도 서로가 서로의 주인이라 수가 0 이 되지 않습니다.

"정리" 가 찍히지 않았다 — 메모리가 새었습니다(leak). 안전 규칙을 어긴 것은 아니어서 컴파일러는 막지 않습니다. Rust 가 막아 주는 것은 잘못된 접근이지, 새는 것까지는 아닙니다.

Weak — 주인이 아닌 참조

Weak<T> 는 값을 가리키되 주인 수에 들지 않습니다. 값이 이미 사라졌을 수 있으므로, 쓰려면 upgrade() 로 "아직 있는가" 를 물어야 하고 답은 Option 입니다.

부모를 아는 나무

부모는 자식을 갖고(Rc), 자식은 부모를 가리키기만 합니다(Weak). 고리가 생기지 않아 전부 정리됩니다.

"누가 누구를 갖는가" 를 먼저 정합니다. 갖는 방향은 Rc, 거꾸로 가리키는 방향은 Weak 입니다.

무엇을 고를까

타입주인고치기검사하는 때쓰는 곳
Box<T>하나보통의 mut컴파일힙에 두기, 재귀 타입
Rc<T>여럿못 한다컴파일함께 읽는 값
Weak<T>아님—실행(upgrade)거꾸로 가리키기
RefCell<T>하나& 뒤에서실행(패닉)내부 가변성
Cell<T>하나통째로 바꾸기필요 없음작은 복사형 값
Rc<RefCell<T>>여럿& 뒤에서실행(패닉)함께 갖고 고치는 값
먼저 보통의 소유권으로 — 주인 하나와 참조로 풀리면 그것이 가장 좋습니다. 이 표의 아래로 갈수록 컴파일러가 대신 봐 주던 것을 우리가 직접 챙겨야 합니다.

이 부의 타입들은 한 스레드 안에서만 쓴다

한 스레드 안에서스레드 사이에서다른 점
Rc<T>Arc<T>수를 세는 일이 원자적이다
RefCell<T>Mutex<T> · RwLock<T>패닉 대신 기다린다
Cell<T>원자 타입(AtomicU32 …)한 번에 읽고 바꾼다

Rc 를 다른 스레드로 보내려 하면 컴파일러가 막습니다. 그 화면은 15부에서 봅니다.

퀴즈 — Weak

Q. 자식이 부모를 Rc 로 가리키고 부모도 자식을 Rc 로 갖는 나무는 무엇이 문제일까요?

A. 부모와 자식이 서로의 주인이 되어 고리가 생깁니다. 바깥의 변수가 다 사라져도 수가 0 이 되지 않아 아무것도 정리되지 않습니다(고리를 만들면). 자식 → 부모 방향을 Weak 로 바꿉니다(부모를 아는 나무).
