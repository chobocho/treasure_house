속이 같은 f64 라도 단위가 다르면 더해지지 않게 한다 — E0308

이 장은 틀린 코드가 컴파일되지 않도록 타입을 짜는 모양을 모읍니다. 첫 실수는 단위입니다. 활주로는 미터로, 유도로는 피트로 잰 값이 있습니다. 둘 다 f64 로 두면 더하는 데 아무 걸림이 없고, 그래서 틀린 합이 조용히 나옵니다.

읽는 법 — 첫 화면의 1500 은 1200 미터와 300 피트를 그대로 더한 수입니다. 컴파일할 때도 실행할 때도 알림이 없습니다. unit_mix_err.rs 는 두 단위를 7부에서 본 값 하나를 감싼 튜플 구조체, 곧 10부에서 newtype 패턴이라고 부른 모양으로 가르고, 10부의 Add 를 Meters 에만 구현했습니다. 둘째 화면의 번호는 7부에서 인자 순서를 바꿨을 때와 같은 E0308 이고, 이번에 막힌 곳은 + 의 오른쪽입니다. 21번 줄의 taxi 아래에 "Meters 를 기대했는데 Feet 이 왔다", runway 아래에 "이것이 Meters 라서 그렇게 기대했다" 가 붙었습니다. 13번 줄의 add 가 rhs 를 Meters 로만 받습니다.

단위를 바꾸는 길을 하나만 열어 둔다

더하려면 단위를 맞춰야 합니다. 10부의 From 으로 "피트에서 미터를 만들 수 있다" 를 한 번 적고, 더하는 자리에서는 바꾸겠다고 적습니다. 배율 0.3048 은 그 구현 한 곳에만 있습니다.

읽는 법 — 28번 줄의 Meters::from(taxi) 가 300 피트를 미터로 바꿨고 합은 Meters(1291.44) 입니다. 29번 줄의 {total:.2?} 는 {:?} 에 소수 자릿수 .2 를 함께 적은 서식입니다. 30번 줄은 같은 변환을 into() 로 불렀고, 31번 줄이 그것을 두 번 더해 Meters(1382.88) 을 냈습니다.
섞는 줄은 막히고, 바꾸는 줄은 소스에 남는다 — 앞 슬라이드의 21번 줄은 컴파일되지 않았고, 이 슬라이드의 28번 줄에는 무엇을 무엇으로 바꾸는지가 적혀 있습니다.

검사를 통과한 값만 있는 타입을 만든다

전자우편 주소를 &str 로 넘기면, 받는 함수마다 주소가 맞는지 다시 확인하거나 누군가 확인했다고 믿어야 합니다. 주소를 감싼 타입을 만들고, 값을 만드는 길을 검사하는 연관 함수 하나로 좁힙니다. 그러면 Email 을 받는 함수는 검사가 끝난 값을 받습니다.

읽는 법 — 4번 줄의 addr 에는 pub 이 없습니다. 13부에서 본 대로 구조체의 필드는 따로 공개하므로 mail 모듈 밖에서는 이 칸에 손댈 수 없습니다. 밖에서 값을 만드는 길은 8번 줄의 parse 이고, 반환 타입은 Result 입니다. 34번 줄의 세 글 가운데 첫째만 @ 앞에 이름이 있고 뒤에 점이 있어 11번 줄의 가드를 지났습니다. 13번 줄이 소문자로 바꿔 담아서 kim@example.com 으로 찍혔습니다. 나머지 둘은 16번 줄의 갈래로 갔습니다. 29번 줄의 send 는 아무것도 확인하지 않습니다.

모듈 밖에서는 검사를 건너뛰어 만들 수도, 속을 바꿀 수도 없다 — E0451 · E0616

"Email 이 있으면 검사를 통과한 것" 이라는 약속은 다른 길로 값을 만들 수 없어야 지켜집니다. 모듈 밖에서 필드를 직접 채워 만들어 보고, 이미 만든 값의 속을 바꿔 봅니다. 32번 줄까지의 mail 모듈과 send 는 앞 슬라이드 그대로이고 main 만 다릅니다.

읽는 법 — 둘 다 13부에서 읽은 번호입니다. 첫 화면은 E0451 입니다. 37번 줄의 addr 가 비공개 필드라서 mail 밖에서는 Email { … } 로 만들 수 없습니다. 둘째 화면은 E0616 입니다. 쌍둥이 email_set_err.rs 는 main 의 본문만 다르고, parse 를 통과한 real 의 addr 에 새 글을 넣으려던 그 파일의 36번 줄이 막혔습니다.
약속을 지키는 것은 모듈의 벽이다 — mail 모듈 안에서는 앞 슬라이드의 14번 줄처럼 addr 를 직접 채웁니다. 검사를 빠뜨리지 않았는지 살필 곳이 그 모듈 하나로 줄었습니다.

구조체에 쓰지 않는 타입 인자는 둘 수 없다 — E0392

사용자 번호와 주문 번호는 둘 다 u32 입니다. 단위에서 한 것처럼 UserId 와 OrderId 를 따로 만들면 섞이지 않지만, 번호의 종류마다 같은 구조체를 또 써야 합니다. 구조체는 Id<T> 하나만 두고 "무엇의 번호인가" 를 타입 인자로 가르려 합니다.

읽는 법 — 처음 보는 번호입니다. 오류 첫 줄은 "타입 인자 T 가 한 번도 쓰이지 않았다" 이고 5번 줄의 T 를 짚습니다. 필드는 6번 줄의 u32 하나뿐이라 T 가 어느 필드의 타입에도 나오지 않습니다. 첫 help: 가 길을 셋 적습니다 — T 를 지우거나, 필드에서 T 를 쓰거나, PhantomData 같은 표시를 쓰라고 합니다. 둘째 help: 는 T 를 const 인자로 쓰려던 것이라면 그렇게 적으라는 말이고, 여기에는 해당하지 않습니다.

PhantomData<T> 필드를 두면 Id<User> 와 Id<Order> 가 갈린다 — E0308

help: 가 이름을 댄 std::marker::PhantomData<T> 는 T 타입의 값을 담지 않으면서 "이 구조체는 T 를 쓴다" 고 알리는 타입입니다. 필드 하나를 그 타입으로 두면 앞 슬라이드의 구조체가 컴파일됩니다.

읽는 법 — 9번 줄이 그 필드이고, 값을 만들 때는 16번 줄처럼 PhantomData 라고만 적습니다. 3번과 4번 줄의 User 와 Order 는 7부의 필드가 없는 구조체이고, 이 파일은 그 값을 한 번도 만들지 않습니다. 타입 인자 자리에 이름으로만 쓰였습니다. 29번과 30번 줄은 18부의 size_of 와 size_of_val 로 크기를 쟀습니다. Id<User> 는 u32 와 같은 4 바이트이고 kind 필드는 0 바이트입니다. 이 툴체인에서는 그렇습니다. 둘째 화면은 28번 줄의 두 인자만 맞바꾼 쌍둥이 phantom_mix_err.rs 의 것입니다. 7부에서 Meters 와 Seconds 를 바꿔 넣었을 때와 같은 E0308 이고, 두 인자에 expected · found 가 하나씩 붙었습니다.

derive(PartialEq) 는 표시로만 쓴 T 에도 조건을 단다 — E0369

번호 둘이 같은지 견주려고 Id<T> 에 derive(PartialEq) 를 붙였습니다. 견줄 것은 raw 하나이고, User 의 값은 어디에도 없습니다.

읽는 법 — 10부에서 == 를 쓰다 본 E0369 입니다. 그때는 견주는 구조체에 PartialEq 가 없었습니다. 이번에는 6번 줄에 derive 가 있는데도 Id<User> 에 == 를 쓸 수 없다고 하고, note: 가 까닭을 4번 줄의 User 에서 찾습니다 — "User 에 PartialEq 구현이 빠진 것 같다". 1장에서 본 대로 derive 가 만드는 구현에는 조건이 달립니다. T 가 나오는 필드가 값을 담지 않는 9번 줄의 PhantomData<T> 하나뿐인데도 그랬습니다.
고치려면 — help: 는 User 에 derive(PartialEq) 를 붙이라고 권합니다. 다른 길은 PartialEq 를 손으로 구현하면서 T 에 조건을 달지 않는 것입니다. 그렇게 쓴 phantom_derive.rs 의 구현과 출력입니다.

상태를 bool 필드로 두면 순서를 어긴 호출은 실행 중에야 드러난다

연결은 연 다음에야 보낼 수 있습니다. 열렸는지를 bool 필드로 들고 다니면 send 는 부를 때마다 그 필드를 확인해야 하고, open 을 빠뜨린 호출도 컴파일됩니다. 7부의 상태 기계도 같은 식이었습니다. 상태에 맞지 않는 행동은 match 의 마지막 갈래에서, 곧 실행 중에 걸러졌습니다.

읽는 법 — 32번 줄은 open 을 부르기 전의 send 입니다. 컴파일됐고, 실행 중에 21번 줄의 확인에 걸려 db: 열지 않은 연결 이 됐습니다. 35번 줄에서 연 뒤의 36번 줄은 보냈습니다. 이 프로그램은 Err 를 찍기라도 했습니다. 부르는 쪽이 Result 를 보지 않으면 9부에서 본 경고 하나가 남습니다.

상태를 타입으로 옮기면 순서를 어긴 호출이 컴파일되지 않는다 — E0599

상태마다 타입을 하나씩 만들고 연결을 Conn<S> 로 씁니다. send 는 10부의 impl Point<f64> 처럼 타입 하나를 짚은 impl Conn<Open> 블록에만 둡니다. 상태를 바꾸는 메서드는 self 를 가져가고 다음 상태의 값을 돌려줍니다. 이 장에서는 그런 메서드를 전이라고 부릅니다. 이런 설계가 타입 상태 패턴(typestate pattern)입니다. 1부에서 제거됐다고 읽은 언어 기능 타입 상태와는 다른 것이고, 제네릭과 소유권만으로 씁니다.

읽는 법 — 4번과 5번 줄의 상태는 필드가 없는 구조체이고, 9번 줄에서 앞의 PhantomData 로만 쓰입니다. 20번 줄의 open 은 Conn<Closed> 를 가져가 Conn<Open> 을 돌려주고, 28번 줄의 send 는 27번 줄의 블록에 있습니다. 39번부터 42번 줄까지가 열고 · 보내고 · 닫고 · 다시 열어 보냈습니다. 43번 줄에서 Conn<Open> 의 크기는 String 하나와 같은 24 바이트이고, 44번 줄에서 Open 의 크기는 0 입니다. 이 책을 만든 기계와 컴파일러 1.99 의 값입니다. 둘째 화면은 39번 줄에서 .open() 만 뺀 쌍둥이 conn_state_err.rs 의 첫째 오류입니다. 10부에서 Point<f64> 에만 둔 메서드를 정수 점에서 부르다 읽은 E0599 그대로입니다. 타입 자리가 Conn<Closed> 이고, = note: 가 그 메서드를 Conn<Open> 에서 찾았다고 알려 줍니다. 그 파일의 오류는 둘입니다. 둘째는 41번 줄의 close 에 같은 말을 합니다. close 도 27번 줄의 블록에 있습니다.
앞 슬라이드와 견주면 — 같은 실수가 거기서는 실행 중의 Err 였고 여기서는 컴파일 오류입니다. send 의 본문에는 상태를 확인하는 줄이 없고, 반환 타입도 Result 가 아닙니다.

지나간 상태의 값은 다시 쓸 수 없다 — E0382

타입을 가르는 것만으로는 모자랍니다. 닫은 뒤에는 닫기 전의 Conn<Open> 값이 손에 남아 있지 않아야 합니다. 앞 슬라이드의 close 는 self 를 가져갑니다. 닫은 뒤에 닫기 전의 변수를 써 봅니다.

읽는 법 — 6부의 E0382 입니다. 40번 줄의 close 호출이 conn 을 옮겨 갔고, 42번 줄이 그 뒤에 빌리려 했습니다. note: 는 32번 줄의 self 를 짚어 "close 는 받는 값 self 의 소유권을 가져간다" 고 적습니다. 7부의 self 의 세 가지 모양 가운데 "가져간다" 입니다.
타입 상태 패턴의 두 부품 — 상태마다 다른 타입, 그리고 self 를 가져가는 전이입니다. 앞의 것이 없는 메서드를 E0599 로 막고, 뒤의 것이 지나간 값을 E0382 로 막습니다.

꼭 채울 칸을 Option 으로 두면 빠뜨린 것은 build 가 돌 때 드러난다

요청을 만드는 빌더입니다. 7부에서 self 를 돌려줘 점으로 이어 부르는 모양으로 봤습니다. 재시도 횟수는 없어도 되고 주소는 꼭 있어야 합니다. 아직 채우지 않은 주소를 Option 으로 들고 있다가 build 에서 확인합니다.

읽는 법 — 31번 줄은 url 과 retries 를 점으로 이어 불렀고 Ok 가 나왔습니다. 34번 줄은 url 을 빠뜨렸는데 컴파일됐고, 25번 줄의 ok_or 와 ? 가 Err("url 이 없다") 를 냈습니다. 24번 줄의 반환 타입이 Result 인 까닭은 그 한 가지입니다.

꼭 채울 칸의 상태를 타입 인자로 옮기면 build 는 실패하지 않는다 — E0599

주소 칸의 상태를 타입 인자 U 로 옮깁니다. 이번 상태는 값을 품습니다. NoUrl 은 비어 있고 HasUrl 은 String 을 가집니다. build 는 Builder<HasUrl> 에만 둡니다.

읽는 법 — 17번 줄의 url 이 Builder<NoUrl> 을 가져가 Builder<HasUrl> 을 돌려줍니다. 26번 줄의 retries 는 impl<U> 블록에 있어서 42번 줄처럼 url 보다 먼저 불러도 되고, 받은 타입 Builder<U> 그대로 돌려줍니다. 34번 줄의 build 는 Result 가 아니라 String 을 돌려주고, 35번 줄이 7부의 let 패턴으로 HasUrl 속의 글을 꺼냅니다. 둘째 화면은 41번 줄에서 .url("/health") 만 뺀 쌍둥이 builder_state_err.rs 의 것입니다. 타입 상태 패턴에서 본 E0599 와 같은 꼴이고, = note: 가 build 를 Builder<HasUrl> 에서 찾았다고 알려 줍니다.
앞 슬라이드와 견주면 — 빠뜨린 url 이 거기서는 실행 중의 Err 였고 여기서는 컴파일 오류입니다.

돌려준 다음 상태를 받지 않고 버리면 — 타입에 붙이는 #[must_use]

타입 상태 패턴에서 전이는 새 값을 돌려줍니다. conn.open(); 이라고만 쓰면 원래 값은 옮겨 가고, 돌려준 Conn<Open> 은 받는 변수 없이 버려집니다. 5부에서 함수에 붙인 #[must_use] 를 이번에는 타입에 붙입니다.

읽는 법 — 경고는 32번 줄에 붙었고, 경고 첫 줄은 "반드시 써야 하는 Conn 이 쓰이지 않았다" 입니다. 속성은 17번 줄의 open 이 아니라 5번 줄, 구조체 Conn 위에 있습니다. 첫 = note: 가 5번 줄에 적어 둔 글을 그대로 보여 줍니다. help: 는 5부에서 본 let _ = 입니다. 경고일 뿐이라 프로그램은 돌았고, 33번 줄에서 받아 둔 연결로 34번 줄이 한 번 보냈습니다. 이 예제의 8번 줄은 PhantomData 대신 상태 값을 그대로 담았습니다.

공개한 트레이트는 다른 크레이트도 구현할 수 있다

단위를 다루는 라이브러리 크레이트 units 입니다. name 은 Unit 의 index 로 이름표 배열을 읽습니다. 쓴 사람은 Unit 을 구현한 타입이 Meter 와 Foot 둘뿐이라고 믿었습니다. 이 라이브러리를 가져다 쓰는 크레이트가 Mile 에 Unit 을 구현합니다.

함수의 수명 인자 하나로는 안에서 만든 값을 넘길 수 없다 — E0597

이 장은 함수와 클로저를 주고받는 자리의 타입을 봅니다. 먼저 참조를 받아 참조를 돌려주는 클로저입니다. 글을 줄 단위로 돌며, 받은 클로저 pick 이 고른 조각을 찍는 each_line 을 씁니다. pick 은 &str 를 받아 그 일부를 &str 로 돌려줍니다. 받는 참조와 돌려주는 참조의 수명이 같다고 적으려고, 11부에서 한 대로 수명에 이름 'a 를 붙여 함수의 인자로 뒀습니다.

읽는 법 — 11부의 E0597 이고 오류 첫 줄도 같은 "padded 가 충분히 오래 살지 못한다" 입니다. 새로 읽을 것은 8번 줄에 붙은 말입니다 — "인자가 padded 를 'a 동안 빌려 둘 것을 요구한다". 2번 줄 아래에는 "수명 'a 가 여기서 정의됐다", 9번 줄 아래에는 "padded 가 빌린 채로 여기서 정리된다" 가 붙었습니다. 화면이 짚은 세 곳을 이으면 이렇습니다. 'a 는 2번 줄, 곧 each_line 의 <…> 에서 정해지는 수명이고, padded 는 함수 안의 7번 줄에서 만들어져 9번 줄에서 정리됩니다.

for<'a> — 어떤 수명에든 성립해야 한다는 조건

적으려던 말은 "함수의 인자로 정해진 수명 하나에" 가 아니라 "어떤 수명의 &str 를 넣든 같은 수명의 &str 를 돌려준다" 입니다. 조건 앞에 for<'a> 를 붙이면 그렇게 읽습니다. 'a 는 함수의 인자 목록에서 빠지고 그 조건 안에서만 쓰는 이름이 됩니다. for<…> 가 붙은 조건을 고차 트레이트 바운드(higher-ranked trait bound)라고 하고, 이 부에서는 줄여서 고차 바운드라고 부릅니다.

읽는 법 — 2번 줄의 <…> 에서 'a 가 빠지고 4번 줄의 조건 앞으로 갔습니다. 본문은 앞 슬라이드와 같은데 컴파일됐습니다. 17번 줄의 클로저는 줄의 앞뒤 빈칸을 뗀 조각을, 18번 줄의 함수 first_word 는 첫 낱말을 돌려줬습니다. first_word 의 시그니처는 11부의 들어오는 참조가 하나인 모양입니다.

Fn(&str) -> &str 라고만 적어도 된다 — 두 조건은 서로를 채운다

수명을 하나도 적지 않은 Fn(&str) -> &str 도 조건으로 쓸 수 있습니다. 앞 슬라이드의 for<'a> Fn(&'a str) -> &'a str 와 어떻게 다른지 보려고, 두 조건으로 받는 함수를 하나씩 쓰고 받은 pick 을 서로에게 넘깁니다.

읽는 법 — 14번 줄은 길게 적은 조건으로 받은 pick 을 짧게 적은 each_short 에 넘겼고, 19번 줄은 거꾸로 짧게 적은 조건으로 받은 것을 each_long 에 넘겼습니다. 둘 다 컴파일됐습니다. 두 줄 모두 타입 인자 F 를 그대로 넘겼으니, 한쪽 조건을 채우는 F 는 무엇이든 다른 쪽 조건도 채웁니다. 조건으로는 두 모양이 같은 말입니다. 23번과 24번 줄이 넘긴 클로저도 앞 슬라이드처럼 앞뒤 빈칸을 뗀 조각을 돌려줬습니다.
평소에는 짧게 — for<'a> 를 손으로 적는 자리는 이 장의 클로저를 변수에 담을 때와 수명 인자를 받는 연관 타입에서 나옵니다.

참조를 돌려주는 클로저를 변수에 먼저 담으면 컴파일되지 않는다

앞의 두 슬라이드는 클로저를 조건이 걸린 인자 자리에 바로 적었습니다. 첫 낱말을 돌려주는 같은 모양의 클로저를 이번에는 변수에 먼저 담습니다. 매개변수의 타입 &str 는 적어 줬습니다.

읽는 법 — 번호가 없는 오류이고 오류 첫 줄은 "수명이 충분히 길지 않을 수 있다" 입니다. 11부에서 같은 첫 줄을 봤습니다. 3번 줄의 &str 아래에 "이 참조의 수명을 '1 이라 하자", 그 옆에 "클로저의 반환 타입은 &'2 str", 본문 아래에 "이 값을 돌려주려면 '1 이 '2 보다 오래 살아야 한다" 가 붙었습니다. 컴파일러가 받는 참조와 돌려주는 참조에 서로 다른 수명 '1 과 '2 를 줬습니다. 첫 낱말을 돌려주는 함수 first_word 는 앞에서 수명을 적지 않고도 컴파일됐습니다.

수명 인자를 받는 연관 타입의 조건에는 for<'a> 를 직접 적는다 — E0277

상수를 계산하다 넘치면 컴파일되지 않는다 — E0080

3부에서 범위를 넘는 리터럴이, 18부에서 칸 수를 소스에 적어 둔, 비트 수만큼 미는 연산이 컴파일할 때 막혔습니다. const fn 을 불러 계산한 상수가 넘칠 때도 컴파일할 때 드러납니다. 5부의 kib 에 큰 수를 넘깁니다.

읽는 법 — 처음 보는 번호입니다. 오류 첫 줄은 "4194304_u32 * 1024_u32 를 계산하려는데, 넘친다" 입니다. 7번 줄의 호출 아래에 "BIG 의 계산이 이 호출 안에서 실패했다" 가 붙었고, note: 가 kib 안의 2번 줄을 짚어 "실패가 여기서 일어났다" 고 합니다. 5번 줄의 SMALL 은 걸리지 않았습니다. 화면에서 뺀 뒤쪽은 BIG 을 쓴 10번 줄을 짚는 note: 입니다. 3부와 18부의 그 화면에는 번호가 없었고, 이 화면에는 E0080 이 붙었습니다.
실행 중이었다면 — 위 화면은 같은 수를 실행 중에 글에서 읽어 같은 kib 에 넘긴 const_overflow_run.rs 의 것입니다. 컴파일됐고, kib(4) 의 4096 을 찍은 뒤 attempt to multiply with overflow 로 패닉했습니다. 3부의 넘침 패닉입니다. 같은 함수와 같은 수가 상수 자리에서는 컴파일 오류, 실행 중에는 패닉이 됐습니다.

크기에 대한 믿음을 컴파일할 때 확인한다 — E0080

파일의 머리 부분인 구조체 Header 를 8 바이트라고 믿고 쓴 코드가 있습니다. 18부에서 본 대로 구조체의 크기는 필드 크기의 합이 아닐 수 있습니다. 그 믿음을 상수의 값 자리에 assert! 로 적어 두면, 어긋났을 때 컴파일되지 않습니다. 상수를 계산하다 패닉할 수 있게 된 것은 부터입니다. 이렇게 지켜져야 하는 조건을 코드에 적어 둔 것을 단언(assertion)이라고 합니다.

읽는 법 — 10번 줄의 const _ 는 이름을 붙이지 않은 상수이고 타입은 () 입니다. 값 자리에 9부의 assert! 를 썼습니다. 조건이 참이어서 컴파일됐고 20번 줄이 크기 8 을 찍었습니다. 이 책을 만든 기계와 컴파일러 1.99 의 값입니다. 둘째 화면은 6번 줄의 u32 를 u64 로만 바꾼 쌍둥이 const_assert_err.rs 의 것입니다. 앞 슬라이드의 E0080 이고, 오류 첫 줄이 "계산하다 패닉했다" 에 이어 실패한 조건을 그대로 적습니다. 짚은 곳은 타입을 바꾼 6번 줄이 아니라 단언을 적은 10번 줄입니다.
실행하지 않아도 걸린다 — 9부의 assert! 는 그 줄이 실행될 때 패닉했습니다. 상수의 값 자리에 둔 assert! 는 컴파일할 때 계산됐고, 거짓이 되자 컴파일이 실패했습니다.

const 인자에 건 단언은 그 값으로 쓰인 곳에서만 걸린다 — E0080

칸이 N 개인 고리 버퍼 Ring<N> 입니다. push 는 넣을 칸을 next % N 으로 고르므로 N 이 0 이면 안 됩니다. new 안에 16부에서 본 const { } 를 두고 그 안에 assert!(N > 0, …) 를 적습니다.

읽는 법 — 10번 줄의 단언은 N 을 씁니다. 24번 줄의 Ring<3> 에서는 참이라 컴파일됐고, 넷을 밀어 넣은 뒤의 칸은 [4, 2, 3] 입니다. 둘째 화면은 24번 줄 아래에 Ring<0> 을 만드는 줄과 거기에 push 하는 줄을 더한 쌍둥이 const_assert_n_err.rs 의 것입니다. 앞에서 읽은 E0080 이고, 오류 첫 줄에 10번 줄에 적어 둔 글이 그대로 나옵니다. 실패한 상수는 Ring::<0>::new::{constant#0} 라고 적혀 있습니다. 새로 읽을 것은 마지막 note: 입니다 — "위 오류는 fn Ring::<0>::new 를 만들어 내다가(instantiating) 만났다". 더한 25번 줄을 짚습니다. 컴파일러가 이름을 댄 것은 Ring::<0>::new 하나이고, 같은 파일의 24번 줄 Ring<3> 은 걸리지 않았습니다. 10부에서는 제네릭 코드의 사본이 쓰인 타입마다 따로 만들어지는 것을 봤고, 이 화면에서는 N 의 값마다 따로입니다.
단언이 없었다면 — 위 화면은 Ring<0> 을 만드는 두 줄은 두고 10번 줄의 단언만 주석으로 바꾼 const_assert_n_run.rs 의 것입니다. 컴파일됐고, 실행 중에 push 의 18번 줄 % 에서 "나누는 수가 0 인 나머지 계산" 으로 패닉했습니다.

슬라이스로 받으면 길이가 다른 호출은 실행 중에야 드러난다

1부에서 어떤 길이의 배열이든 받는 sum 을, 10부에서 N 을 가진 내 타입을 봤습니다. 이 장의 나머지는 const 제네릭( 부터)으로 "두 값의 길이가 맞아야 한다" 를 적습니다. 견줄 것을 먼저 놓습니다. 슬라이스 둘을 칸끼리 더하는 add 입니다.

읽는 법 — 2번 줄의 매개변수 타입 &[i32] 에는 길이가 적혀 있지 않습니다. 그래서 3번 줄이 부를 때마다 두 길이를 견주고, 반환 타입이 Result 입니다. 14번 줄은 세 칸끼리 더해 Ok 가 됐습니다. 15번 줄은 길이 3 과 2 를 넘겼는데 컴파일됐고, 실행 중에 Err 가 됐습니다.

두 배열의 길이가 같아야 한다는 것을 N 하나로 적는다 — E0308

같은 add 를 배열로 받습니다. 3부에서 본 대로 배열의 길이는 타입의 일부입니다. 두 매개변수에 같은 const 인자 N 을 적으면 "길이가 같다" 가 시그니처에 들어갑니다.

읽는 법 — 2번 줄은 두 매개변수와 반환 타입에 같은 N 을 적었습니다. 본문에 길이를 견주는 줄이 없고, 반환 타입도 Result 가 아닙니다. 11번 줄에서 N 은 3, 14번 줄에서는 2 이고, 돌려받은 pair 의 크기는 i32 둘인 8 바이트입니다. 둘째 화면은 11번 줄에서 세 칸과 두 칸을 넘긴 쌍둥이 cg_add_err.rs 의 것입니다. 3부의 그 슬라이드에서 읽은 E0308 과 같은 말입니다 — "크기 3 인 배열을 기대했는데 크기 2 인 배열이 왔다". note: 는 2번 줄의 둘째 매개변수 b: [i32; N] 에 밑줄을 그었습니다.
앞 슬라이드와 견주면 — 길이가 다른 호출이 거기서는 실행 중의 Err 였고 여기서는 컴파일 오류입니다.

길이가 제네릭 N 인 배열에는 Default 가 없다 — E0277

앞 슬라이드는 [0; N] 으로 배열을 만들었습니다. 이번에는 원소의 타입도 제네릭 T 로 두고, 기본값으로 채운 N 칸짜리 배열을 돌려주는 blank 를 씁니다. T 에 Default 조건을 달고 10부의 Default::default() 를 불렀습니다.

읽는 법 — E0277 이 대는 타입은 [T; N], 트레이트는 Default 입니다. = help: 가 Default 를 구현한 타입을 늘어놓습니다. [T; 0], [T; 1] 처럼 길이가 하나씩 적혀 있고 "27 개 더" 로 끝납니다.
길이를 적어도 33 부터는 — 2번 줄의 [u8; 32] 는 걸리지 않고 3번 줄의 [u8; 33] 만 같은 오류가 났습니다. 1부에서 표준 라이브러리의 배열 메서드가 길이 32 까지만 됐던 때를 읽었습니다. Default 에는 그 경계가 이 책의 컴파일러 1.99 에서도 보입니다. 길이에 기대지 않고 채우는 길이 다음 슬라이드입니다.

array::from_fn — 칸마다 클로저를 불러 길이 N 인 배열을 채운다

std::array::from_fn 은 클로저를 받아, 칸마다 그 클로저를 불러 얻은 값으로 배열을 채웁니다. 앞 슬라이드의 blank 에서 본문을 바꾸고 1번 줄에 use 를 더했습니다.

읽는 법 — 5번 줄이 T::default() 를 돌려주는 클로저를 넘겼고, 9번 줄의 String 셋과 11번 줄의 40 칸이 만들어졌습니다. 40 은 앞 슬라이드에서 Default 가 막힌 33 보다 긴 길이입니다. 클로저는 칸의 번호를 받습니다. 14번 줄은 번호의 제곱을, 16번 줄은 번호를 넣은 글을 칸마다 만들었습니다.

행과 열이 맞아야 곱해지는 행렬 — E0308

const 인자를 둘 둡니다. Matrix<R, C> 는 R 행 C 열입니다. 곱셈은 왼쪽의 열 수와 오른쪽의 행 수가 같아야 하고, 결과는 왼쪽의 행 수와 오른쪽의 열 수를 가집니다. 그 규칙을 mul 의 시그니처에 그대로 적습니다.

읽는 법 — 8번 줄에서 self 는 Matrix<R, C>, rhs 는 Matrix<C, K>, 결과는 Matrix<R, K> 입니다. C 가 두 곳에 같은 이름으로 적혀 있고, K 는 이 메서드만의 const 인자입니다. 29번 줄은 2 행 3 열에 3 행 2 열을 곱해 2 행 2 열을, 31번 줄은 순서를 바꿔 3 행 3 열을 냈습니다. 결과의 타입은 어디에도 적지 않았습니다. 둘째 화면은 29번 줄에서 a.mul(&a) 를 부른 쌍둥이 matrix_err.rs 의 것입니다. E0308 이 "3 을 기대했는데 2 가 왔다" 고 하고, = note: 가 두 타입을 나란히 적습니다. 기대한 것은 &Matrix<3, _>, 온 것은 &Matrix<2, 3> 입니다.

const 인자 자리의 계산식은 중괄호로 감싼다

2장에서 blank::<{ Name::WIDTH }>() 처럼 const 인자를 중괄호로 감싸 넘겼습니다. 감싸지 않아도 되는 것 둘과 감싸야 하는 것 하나를 나란히 놓습니다.

읽는 법 — 9번 줄의 리터럴 8 과 10번 줄의 상수 이름 WIDTH 는 그대로 적었고, 12번 줄의 계산식은 중괄호 안에 있습니다. 세 배열의 길이는 8 · 4 · 9 입니다. 둘째 화면은 12번 줄의 중괄호만 뺀 쌍둥이 cg_brace_err.rs 의 것입니다. 번호가 없는 문법 오류이고, 첫 줄은 ", 나 > 가 올 자리에 * 가 왔다" 입니다. help: 가 까닭과 고친 줄을 함께 적습니다 — "식은 중괄호로 감싸야 const 제네릭 인자로 쓸 수 있다".
제네릭 안에서 N 으로 계산하기 — 위 화면은 받은 배열보다 한 칸 긴 배열을 돌려주려고 반환 타입에 [u8; N + 1] 을 적은 cg_plus_err.rs 의 것입니다. 오류 첫 줄은 2장에서 F::WIDTH 를 길이에 쓰다 본 "제네릭 매개변수는 const 연산에 쓸 수 없다" 그대로입니다. 이번 = help: 는 "const 인자는 여기서 N 처럼 홀로만 쓸 수 있다" 입니다. 그 파일의 오류는 둘이고, 둘째는 본문의 [last; N + 1] 에 같은 말을 합니다. 맨 위 예제 12번 줄의 WIDTH 는 제네릭 인자가 아니라 1번 줄의 상수입니다. 이 책의 컴파일러 1.99 에서 그렇습니다.

const 인자의 기본값은 타입을 적은 자리에서 쓰인다 — E0284

버퍼의 크기를 const 인자로 두는데, 대부분의 자리에서는 16 이면 됩니다. 선언의 인자 뒤에 = 16 을 적으면( 부터) 타입 자리에 Buf 라고만 써도 됩니다.

퀴즈 — const 와 제네릭

Q. const fn kib(n: u32) -> u32 { n * 1024 } 가 있습니다. ① const BIG: u32 = kib(4_194_304); 와 ② 같은 수를 실행 중에 글에서 읽어 kib(n) 을 부르는 줄은 각각 어떻게 될까요?

A. 곱이 u32 를 넘습니다. ① 은 컴파일할 때 계산되므로 E0080 으로 컴파일되지 않고, note: 가 kib 안의 곱셈 줄을 짚습니다. ② 는 컴파일되고, 실행 중에 attempt to multiply with overflow 로 패닉합니다(상수를 계산하다 넘치면).
