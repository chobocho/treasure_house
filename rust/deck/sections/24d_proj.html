이 프로젝트가 쓰는 것

3장까지의 프로그램은 끝나면 아무것도 남기지 않았습니다. 이 장의 kv 는 이름을 붙여 맡긴 글을 파일에 두었다가, 다음에 띄웠을 때 그 이름으로 되찾게 합니다. 이름이 키(key), 맡긴 글이 값(value)입니다. 8부에서 HashMap 을 설명한 말 그대로입니다. 키와 값의 짝들을 맡아 두는 것을 이 장은 저장소(store)라고 부릅니다. 0부에서 "이 책의 저장소" 라고 한, 소스를 모아 둔 곳과는 다른 뜻입니다. 새로 하는 일은 넷입니다 — 한 줄에 하나씩 받는 명령, 글로 된 파일 형식을 정해 쓰고 되읽기, 저장소가 할 일을 트레이트로 적고 구현을 셋 두기, 그리고 스레드 여럿이 저장소 하나를 함께 쓰기입니다. 첫 표는 그러느라 다시 쓰는 것과 그것을 배운 슬라이드이고, 둘째 표는 앞의 세 장에서 그대로 가져온 것입니다.

두 표 모두 왼쪽이 이 장의 코드에 나오는 것입니다. 첫 표의 오른쪽은 그것을 처음 설명한 슬라이드이고, 둘째 표의 오른쪽은 1장부터 3장까지에서 그것을 만든 슬라이드입니다. 이 장은 오른쪽의 설명을 되풀이하지 않고, 달라지는 곳만 말합니다.

다 만들면 이렇게 돈다

마지막 단계의 패키지를 빌드해 돌린 화면입니다. 여기까지 가는 길을 여덟 단계로 나눠 걷습니다. 화면은 앞의 세 장처럼 target/debug/ 의 실행 파일을 직접 부릅니다. kv 는 표준 입력의 한 줄을 명령 하나로 읽습니다. 첫 인자 memo.kv 는 저장소를 둘 파일의 이름이고, 처음에는 없는 파일입니다.

읽는 법 — cargo build -q 는 아무것도 찍지 않았습니다. 이 장의 글에서는 ./target/debug/kv 를 kv 로 줄여 적습니다. 첫 실행은 명령 다섯을 받았습니다. set 둘은 아무것도 찍지 않았고, get name 은 값 보리 를 찍었습니다. get age 에는 kv: 4번째 줄: 없는 키 age 라는 알림이 나왔습니다. 넷째 줄의 명령이 받은 키가 저장소에 없다는 말입니다. list 는 가진 것 전부를 한 줄에 하나씩 찍었습니다. 키와 값 사이는 탭이고, lang 이 name 보다 먼저입니다. 알림이 하나 있었으므로 종료 코드는 1 입니다. cat 이 보인 memo.kv 에는 list 가 찍은 것과 같은 두 줄이 있습니다. 그다음 실행은 새로 띄운 프로세스인데 get lang 에 rust 를 답했습니다. 앞 실행이 파일에 둔 것을 읽었습니다. 넷째 명령은 인자가 넷입니다. 둘째 인자부터는 명령을 한 줄에 하나씩 적어 둔 파일이고, kv 는 그 명령들을 같은 저장소에 냅니다. 이때 파일마다 스레드를 하나씩 띄우는데, 그것은 화면에 보이지 않고 7단계에서 봅니다. 세 파일의 내용은 6단계에 있습니다. 찍힌 것은 파일을 준 차례대로입니다. fruit.txt 의 답 둘과 알림 하나, color.txt 의 답 둘, city.txt 의 답 둘과 알림 하나입니다. 마지막 list 에는 세 파일이 둔 키 여섯과 처음에 둔 둘이 한 저장소에 있습니다.
이 책의 저장소입니다 — 명령의 이름과 모양, 키로 받는 글, 파일의 줄 모양, 알림의 글은 모두 이 장이 정합니다. 화면의 kv: 로 시작하는 줄은 이 프로그램이 만든 글입니다. 다른 저장 도구가 어떻게 하는지는 말하지 않고, 얼마나 빠른지나 전원이 꺼졌을 때 무엇이 남는지도 이 장은 다루지 않습니다.

여덟 단계 — 단계마다 컴파일되고 돈다

앞의 세 장과 같은 방식입니다. 단계 하나가 예제 디렉터리 하나이고, 뒤 단계는 앞 단계의 파일을 그대로 두고 파일이나 줄을 더하거나 적어 둔 줄만 바꾼 사본입니다. 슬라이드가 싣지도 말하지도 않은 줄은 앞 단계의 것 그대로입니다. 소스는 3장처럼 하는 일마다 파일 하나로 나눕니다. 코드 상자의 꼬리표에는 단계의 디렉터리 이름과 파일 이름을 적습니다.

줄 하나가 답이 되기까지 — 명령, 저장소, 답

줄 하나는 세 곳을 지납니다. 글이 명령이 되고, 명령이 저장소에 가고, 저장소가 돌려준 것이 답이 됩니다. 일마다 함수 하나이고, 가운데의 저장소만 구현이 여럿입니다.

줄→ 명령→ 저장소→ 답
  • 명령(command) — 이 장에서 명령이라고 하면 kv 가 읽는 한 줄, 곧 set 키 값 · get 키 · del 키 · list 넷 가운데 하나입니다. 화면의 $ 줄에 적힌 것은 "셸의 명령" 이라고 따로 부릅니다. 줄을 명령으로 읽는 parse_command 가 1단계입니다.
  • 항목(entry) — 키 하나와 값 하나의 짝입니다. 18부에서 맵에 든 짝을 부른 말입니다. 저장소는 항목들을 가지며, 한 키에는 값이 하나입니다. 저장소가 할 줄 아는 일을 트레이트로 적는 것이 2단계이고, 항목을 파일의 한 줄로 적는 법이 3단계입니다.
  • 답 — 줄마다 하나입니다. 찾은 값이거나, 목록이거나, 알림이거나, 찍을 것이 없다는 것입니다. 명령을 저장소에 내고 답을 만드는 apply 가 4단계입니다.
  • 명령 파일 — 명령을 한 줄에 하나씩 적어 둔 글 파일입니다. 영어로는 script 라고 합니다. 6단계는 명령 파일들을 차례로 돌리고, 7단계는 파일마다 20부에서 일꾼이라고 부른 스레드 하나에 맡깁니다.
명령을 내는 쪽은 저장소가 어디에 두는지 모른다 — apply 가 아는 것은 트레이트 Storage 의 메서드 넷뿐입니다. 항목을 메모리에만 두는 구현, 파일에도 쓰는 구현, 잠그고 나서 다른 구현에 넘기는 구현이 같은 자리에 들어갑니다. 그래서 2단계의 시험 하나를 세 구현이 모두 통과해야 합니다.

줄을 명령으로 읽는다 — 첫 빈칸 앞이 이름, set 의 값은 줄의 나머지다

1단계의 파일은 셋입니다. Cargo.toml 은 패키지 이름이 kv 인 것만 1장의 그 파일과 다르고, 마지막 단계까지 바뀌지 않습니다. src/command.rs 에는 명령을 담는 열거형과, 줄 하나를 그 열거형으로 바꾸는 함수가 있습니다. 옵션을 읽던 1장과 2장의 parse_args 와 하는 일이 닮았습니다. 이번에 읽는 것은 셸이 쪼개 준 인자가 아니라 줄 하나라서, 쪼개는 일부터 합니다.

읽는 법 — 줄 번호는 command.rs 의 것입니다. Command 는 7부에서 본 데이터를 가진 열거형이고, Set 은 키와 값을, Get 과 Del 은 키를 가집니다. Skip 은 빈 줄의 자리입니다. CmdError 는 읽지 못한 까닭 넷입니다. 52번 줄은 빈 줄을 Skip 으로 돌려줍니다. 55번 줄은 8부에서 본 split_once 로 줄을 첫 빈칸에서 둘로 나눕니다. 빈칸이 없으면 None 이고, 9부에서 본 unwrap_or 가 줄 전체를 이름으로, 빈 글을 나머지로 줍니다. 57번 줄의 set 은 나머지를 한 번 더 첫 빈칸에서 나눠 앞을 키로, 뒤를 값으로 삼습니다. 63번과 64번 줄의 get 과 del 은 나머지 전체가 키입니다. 66번 줄의 가드는 줄이 list 넉 자뿐인지를 봅니다. 그 밖의 이름은 68번 줄에서 Unknown 입니다. 키는 세 군데 모두 40번 줄의 check_key 를 지납니다. 빈 글이면 NoKey, 빈칸이 들었으면 SpaceInKey 이고, 그렇지 않으면 새 String 으로 만들어 돌려줍니다. 61번 · 63번 · 64번 줄의 ? 가 그 오류를 그대로 올립니다. 둘째와 셋째 상자 사이의 줄은 CmdError 의 Display 구현입니다. 까닭마다 알림에 쓸 글 한 줄을 둔 것이고, 다음 슬라이드의 시험이 그 글을 봅니다.
이 프로그램의 정의 — 키와 값 — 키는 빈 글이 아니고 빈칸(U+0020)이 들지 않은 글입니다. 값은 키 뒤의 빈칸 하나 다음부터 줄 끝까지의 글 전부입니다. 값에는 빈칸도 들고, 값이 비어도 됩니다. 명령의 줄에서는 역슬래시도 그냥 글자 하나입니다.

정의를 시험으로 적어 둔다 — 값 속의 빈칸은 그대로이고, 키를 막는 글자는 빈칸 하나다

같은 파일의 아래쪽, 13부에서 본 시험 모듈입니다. 값이 어디서 시작해 어디서 끝나는지, 키가 될 수 없는 글이 무엇인지, 이름을 얼마나 까다롭게 맞추는지를 시험 셋으로 적습니다. 시험에 나오는 set 과 get 은 시험 모듈의 맨 위에 둔 도우미입니다. 받은 글로 Ok(Command::Set(…)) 과 Ok(Command::Get(…)) 을 만듭니다.

Box<dyn Storage> 가 Send 가 아니라서, 그것을 품은 Mutex<…> 가 Sync 가 아니고, 그래서 Arc<Mutex<…>> 가 Send 가 아닙니다. 그 Arc 가 src/shared.rs 12번 줄의 Locked 안에 있고, Locked 가 172번 줄의 클로저 안에서 쓰이고, 그 클로저에 Send 를 요구한 쪽이 spawn 입니다. /rustc/ 로 시작하는 두 경로는 이 툴체인의 표준 라이브러리 소스의 자리입니다. 1 redundant requirement hidden 은 겹치는 요구 하나를 적지 않았다는 컴파일러의 말입니다. 마지막 두 줄은 Cargo 가 붙인 것이고 종료 코드는 101 입니다.
고치려면 — 셋째 상자처럼 별명에 + Send 를 더합니다. 그러면 open_store 가 돌려주는 상자에는 Send 인 구현만 들어갈 수 있습니다. MemStore 와 FileStore 는 15부에서 본 대로 필드가 전부 Send 라서 Send 입니다. 이 한 줄을 고친 kv7_jobs 가 컴파일되는 것은 다음 슬라이드부터의 화면이 보입니다. Mutex 로 감쌌는데도 속의 타입이 Send 여야 한다는 것이 이 화면의 새 내용입니다.

Q. ./target/debug/kv 를 kv 로 줄여 적습니다. 둘 다 마지막 단계의 kv 입니다. ① printf 'set b 2\nset B 1\nset 가 3\nset a x\nlist\n' | kv 는 표준 출력에 네 줄을 찍습니다. 키는 어떤 차례로 나오고, a 의 값은 몇 글자입니까? ② printf 'k\tv\\n\nk2 v2\n' > q.kv 로 두 줄짜리 파일을 만들었습니다. 첫 줄은 k, 탭, v, 역슬래시, n 이고 둘째 줄은 k2 v2 입니다. printf 'list\n' | kv q.kv 는 무엇을 찍고 몇으로 끝납니까?

A. ① B · a · b · 가 의 차례입니다. 둔 차례가 아니라 키의 바이트 순서라서 대문자가 소문자보다 앞이고 한글이 맨 뒤입니다(목록의 순서). a 의 값은 두 글자, 빈칸과 x 입니다. 키 뒤의 빈칸 하나만 떼고 그다음 빈칸은 값에 남습니다(값의 시험). ② 표준 출력에는 아무것도 없고, 표준 오류에 kv: q.kv 2번째 줄: 탭이 없다 한 줄이 나오며 종료 코드는 2 입니다. 첫 줄은 멀쩡한 항목입니다. 값이 v 와 줄바꿈 두 글자인 항목으로 읽힙니다(unescape). 하지만 둘째 줄에 탭이 없어서 읽어 들이기가 거기서 오류로 끝나고, list 는 돌지 않습니다(틀린 저장소 파일). 1 이 아니라 2 입니다. 알림을 낸 줄이 있었던 것이 아니라 run 이 Err 를 돌려줬습니다. 세 명령은 마지막 단계 kv8_final 에서 모든 시험 다음에 돌렸습니다. 그 화면입니다.

더 해 볼 것

마지막 단계의 패키지를 복사해 놓고 고쳐 보는 과제입니다. 풀이는 싣지 않았습니다. 과제마다 손댈 파일과 함수를 적었습니다. 규칙을 바꾸는 과제는 정한 것의 표에서 어느 줄이 바뀌는지부터 적고, 그 줄을 본 시험을 먼저 고칩니다.

  • 주석 줄 — 지금은 # 으로 시작하는 줄이 모르는 명령입니다. parse_command 가 그런 줄을 Skip 으로 돌려주게 합니다. 그러면 # 으로 시작하는 키는 어떻게 되는지도 정합니다.
  • 값을 올리는 명령 — incr 키 를 더합니다. 읽고 나서 쓰기가 잠금 한 번 안에 들도록 Storage 에 메서드 하나를 더하고, 구현 셋과 Down 을 모두 고칩니다. 이 과제에서는 값이 수가 아닌 키에 부르면 알림을 내기로 정합니다. 일꾼 여럿이 같은 키를 올린 뒤의 값이 늘 같은지를 시험으로 봅니다.
  • 새 파일에 쓰고 바꿔치기 — save 가 다른 이름의 파일에 다 쓴 다음 17부의 fs::rename 으로 이름을 바꾸게 합니다. 그 이름을 무엇으로 할지, 바꾸기가 실패했을 때 무엇을 돌려줄지 정합니다.
  • 덧붙이는 기록 — 바뀔 때마다 전부를 다시 쓰는 대신, 17부의 OpenOptions 로 명령 하나를 한 줄씩 덧붙이고 열 때 처음부터 따라 읽는 구현을 하나 더 만듭니다. 지운 것을 어떤 줄로 적을지, 같은 키가 또 나온 줄을 이제 어떻게 읽을지를 먼저 정하고, check_storage 를 넷째로 부릅니다.
  • 스코프 스레드로 — run_scripts 를 15부의 스코프 스레드로 다시 짭니다. Arc 와 move 로 가져가던 것 가운데 무엇이 빌림으로 바뀌는지 봅니다.
  • 일꾼의 수에 한도 두기 — 지금은 명령 파일 하나에 스레드가 하나입니다. 20부의 번호를 붙여 맡기는 풀로 바꿔 일꾼을 정한 수만 띄우고, 화면이 준 차례대로 놓이는 것은 그대로 지킵니다.
  • 앞머리로 고르는 목록 — list 앞머리 가 그 글로 시작하는 키만 내게 합니다. Storage 의 list 를 바꿀지 메서드를 더할지 정하고, MemStore 에서는 18부의 range 를 써 봅니다.
  • 값에 줄바꿈 넣기 — 지금은 명령의 줄에서 역슬래시가 글자 하나입니다. set 의 값을 unescape 에 넘겨 \n 을 줄바꿈으로 읽게 합니다. 그러면 get 이 그 값을 어떻게 찍을지, 틀린 이스케이프를 어느 알림으로 낼지도 정해야 합니다.
  • 알림에 찍는 키 거르기 — 없는 키는 받은 그대로 알림에 찍힙니다. 탭이나 화면에 찍기 곤란한 글자가 든 키를 escape 로 바꿔 찍게 하고, 기준 파일이 어떻게 바뀌는지 봅니다.
  • UTF-8 이 아닌 인자 — 1장의 같은 과제입니다. 이 프로그램에서는 인자가 파일 이름이라서, 받은 것을 글로 바꾸지 않고 경로로 다루는 17부의 PathBuf 로 들고 다닐 수 있습니다. 그러면 알림에 이름을 어떻게 찍을지를 정해야 합니다.
