이 부에서 할 일

문법은 그것이 생긴 까닭을 알면 덜 낯섭니다. 이 부는 Rust 가 어디서 왔고, 무엇을 버렸고, 무엇을 약속했는지를 따라갑니다. 주장마다 이런 표시가 붙어 있고(누르면 근거가 된 글로 갑니다), 옛 문법이 지금 어떻게 되는지는 이 기계의 컴파일러로 직접 돌려 보입니다.

시작

고장 난 엘리베이터 · 여가 프로젝트 · 모질라의 후원 · 풀려던 문제

고장 난 엘리베이터에서 시작됐다

2006년, 모질라에서 일하던 스물아홉 살의 프로그래머 그레이든 호어(Graydon Hoare)가 집에 돌아와 보니 엘리베이터가 멈춰 있었습니다. 소프트웨어가 죽은 것이었습니다.

  • 그는 21층까지 걸어 올라가며, 이런 죽음의 상당수가 메모리를 잘못 다루는 버그에서 온다는 것을 떠올렸습니다.
  • 그리고 작고 빠르면서도 메모리 버그가 없는 코드를 쓸 수 있는 새 언어를 설계하기 시작했습니다.
이 일화의 출처 — 2023년 MIT 테크놀로지 리뷰가 호어와 초기 개발자들을 취재해 쓴 기사입니다. 이 장의 이야기는 대부분 그 기사에 기대고 있습니다.

이름은 녹병균에서 왔다

호어는 이 언어에 Rust 라는 이름을 붙였습니다. 쇠의 녹이 아니라, 유난히 끈질긴 곰팡이 무리(녹병균)에서 딴 이름입니다.

"살아남도록 과하게 설계된" — 기사가 전하는 호어의 말로, 그 균류를 두고 한 표현입니다. 죽지 않는 프로그램을 만들려는 언어의 이름으로 고른 까닭이 여기에 있습니다.

처음 몇 해는 여가 프로젝트였다

Rust 는 처음에 회사 일이 아니었습니다. 호어가 몇 해 동안 혼자 다듬었고, 다른 개발자들에게 보여 주었을 때의 반응은 엇갈렸습니다.

  • 2009년, 모질라가 Rust 를 공식 후원하기로 합니다. 언어는 오픈 소스로 두되, 엔지니어의 급여를 모질라가 댔습니다.
  • 2010년, 브리티시컬럼비아에서 열린 모질라 행사에서 이 실험적인 언어가 발표됩니다.
그래서 "몇 년생" 인가 — Rust 프로젝트 스스로도 "2010년에 구상됐다(세기에 따라서는 2006년)" 고 적습니다.

풀려던 문제는 둘이었다

Rust 팀의 설명으로는, 이 프로젝트는 두 가지 까다로운 문제를 풀려고 시작됐습니다. 안전한 시스템 프로그래밍, 그리고 고통 없는 동시성입니다.

방식얻는 것치르는 값
C · C++ — 손으로 메모리 관리속도, 작은 크기, 세밀한 제어메모리 버그, 보안 구멍
Java · Python — 가비지 컬렉터메모리 안전느려짐, 큰 메모리, 멈춤
Rust — 컴파일러가 규칙을 검사속도와 안전 둘 다배워야 할 규칙이 많다

표의 대비는 기사의 설명을 줄인 것입니다.

답은 "소유권" 이었다

모질라의 엔지니어들과 세계 곳곳의 자원자들은 몇 해에 걸쳐 핵심을 다듬었습니다. 데이터 한 조각을 가리키는 주인을 변수 하나로 정하는 소유권(ownership) 체계입니다.

  • 규칙을 어긴 코드는 컴파일러가 실행 파일로 만들어 주지 않습니다. 검사는 실행 전에 끝납니다.
  • 새 발명이라기보다 수십 년 된 연구를 쓸 수 있는 기능으로 옮긴 것이었습니다.
이 책의 6부가 통째로 이 이야기입니다 — 소유권·빌림·슬라이스.

첫 번째 쓰임새는 브라우저 엔진이었다

모질라가 Rust 에 돈을 댄 까닭은 브라우저였습니다. 브라우저는 크고 복잡해서 위험한 메모리 버그가 생길 자리가 많습니다. Rust 블로그는 Rust 의 "창립 응용" 이 실험적 브라우저 엔진 Servo 였다고 적습니다.

Rust (언어)⇄ Servo (그 언어로 쓴 브라우저 엔진)
서로를 키웠다 — 큰 프로그램을 실제로 써 보며 언어의 모자란 곳을 찾고, 언어가 바뀌면 엔진을 다시 고쳤습니다. 그 결실은 6장에서 봅니다.

석 달쯤마다 한 판씩, 세 해 동안 열두 판. 그때마다 문법이 바뀌었습니다.

믿을 수 있는 것은 둘뿐이었다 — 안전, 그리고 변화

1.0 을 앞둔 2014년 가을, Rust 팀은 그 시절을 이렇게 돌아봤습니다 — 초기부터 믿을 수 있는 것은 두 가지, 안전과 변화뿐이었다.

  • 막다른 길을 여러 번 만났고, 그때마다 언어를 바꿀 자유가 필요했습니다.
  • 0.4 에서는 0.1 의 자랑거리였던 타입 상태(typestate) 검사가 통째로 빠졌습니다.
  • 2013년에는 만든 사람인 호어가 프로젝트에서 물러납니다.

기호로 나뉘던 포인터들이 사라졌다

옛 Rust 에는 포인터 종류가 여럿이었고 기호로 구별했습니다. ~T 는 힙에 놓인 소유 값, @T 는 가비지 컬렉터가 돌보는 값이었습니다. 1.0 을 향해 가며 이 기호들은 없어지고 참조 &T 와 &mut T 만 남았습니다.

지금은 — ~T 의 자리는 라이브러리 타입 Box<T> 가 맡습니다(14부). 언어에 박혀 있던 것이 라이브러리로 나왔습니다.

가비지 컬렉터를 버렸다

초기의 Rust 에는 가비지 컬렉터가 있었습니다. 소유권 체계가 다듬어질수록 쓸 일이 줄었고, 2013년 무렵 팀은 그것을 걷어 냈습니다.

  • 의 릴리스 노트 — 한때 @ 기호로 적던, 참조를 세는 옛 GC 타입 Gc<T> 가 마침내 제거됐다.
  • 그 결정을 적은 문서가 RFC 256 입니다.
그래서 Rust 에는 지금도 GC 가 없습니다 — 값은 주인이 범위를 벗어나는 순간 정리됩니다. 여럿이 함께 가져야 하는 값은 Rc<T> 로 직접 고릅니다(14부).

녹색 스레드와 런타임도 버렸다

옛 Rust 는 언어 런타임이 관리하는 가벼운 스레드(녹색 스레드)를 갖고 있었습니다. 1.0 을 앞두고 이것을 표준 라이브러리에서 떼어 냅니다. 운영 체제의 모델에 더 가깝게 맞추기 위해서였습니다.

  • 1.0 알파()의 릴리스 노트 — Rust 에는 이제 어떤 종류의 런타임도 없고, 녹색 스레드가 아니라 OS 스레드만 지원한다.
지금은 — std::thread::spawn 은 OS 스레드를 하나 만듭니다(15부). 가벼운 작업이 필요하면 async 와 바깥 런타임 크레이트를 씁니다(16부).

int 와 uint 가 isize 와 usize 로

1.0 알파에서는 포인터 크기 정수의 이름도 바뀌었습니다. int · uint 대신 isize · usize 입니다.

컴파일러가 기억하고 있다 — help: 줄이 i32 를 권합니다. 정수 타입은 3부에서 봅니다.

fail! 은 panic! 이 됐다

옛 문서의 예제를 그대로 넣어 보면, 사라진 이름들이 지금은 "없는 매크로" 로 보고됩니다.

1.0 전의 글을 볼 때 — 2015년 5월보다 앞선 블로그 글이나 답변의 코드는 지금 거의 컴파일되지 않습니다. 날짜를 먼저 보세요.

버리고 나니 핵심 하나가 남았다

2014년 9월, 1.0 으로 가는 길을 알린 글은 이렇게 정리합니다 — 언어는 이제 소유권과 빌림(ownership and borrowing)이라는 단순한 핵심 개념 하나에 집중한다.

  • 처음에 소유권은 작업 사이에 데이터를 안전하게 넘기려는 장치였습니다.
  • 같은 장치로 온갖 것을 언어 밖 라이브러리로 내보낼 수 있다는 것을 나중에 알게 됩니다.
이 책의 순서가 그 결과입니다 — 소유권(6부)을 지나야 문자열·컬렉션(8부), 스마트 포인터(14부), 스레드(15부)가 전부 "라이브러리에 있는 평범한 타입" 으로 읽힙니다.

3장

1.0 과 안정성 약속

crates.io · 1.0 발표 · "격변의 끝" · 여섯 주 열차 · 세 채널 · RFC

1.0 은 "더는 깨지 않겠다" 는 선언이었다

2014년 9월의 글은 1.0 의 뜻을 한 줄로 못 박습니다 — 1.0 뒤의 1.x 릴리스는 뒤로 호환된다. 지금 있는 코드는 고치지 않아도 계속 컴파일된다.

  • 다음 달 글은 더 분명합니다 — 1.0 안정판에서 컴파일되는 코드는 1.x 안정판에서도 큰 수고 없이 컴파일돼야 한다.
  • 목표는 "Rust 를 올리는 일이 두렵지 않게" 하는 것이었습니다.
안정성은 멈춤이 아니다 — 새 판은 자주 내되, 올리는 일이 아프지 않게 한다는 약속입니다.

1.0 보다 먼저 온 것 — cargo 와 crates.io

2014년 11월, 패키지 저장소 crates.io 가 문을 엽니다. 빌드 도구이자 패키지 관리자인 cargo 는 Bundler 와 NPM 의 전통을 잇는 설계였습니다.

언어와 도구가 한 묶음 — Rust 는 1.0 을 내기 전에 빌드·의존성 도구부터 갖췄습니다. 그래서 오늘날 거의 모든 Rust 프로젝트가 같은 명령(cargo build, cargo test)으로 움직입니다. cargo 는 2부와 13부에서 씁니다.

1.0 이 나왔다

. Rust 코어 팀은 "오늘 Rust 1.0 을 발표하게 되어 매우 자랑스럽다" 로 시작하는 글을 올렸습니다.

  • 가비지 컬렉터도 런타임도 요구하지 않는다 — 그래서 Rust 로 쓴 라이브러리를 C 라이브러리 자리에 그대로 끼울 수 있다고 소개했습니다.
  • 세계 곳곳에서 출시를 축하하는 모임이 열렸습니다.
  • 모질라가 후원을 시작한 지 여섯 해 만이었습니다.

"1.0 은 그 격변의 끝을 뜻합니다"

발표문은 지난 실험이 언어를 더 단순하고 강하게 만들었지만, 그 때문에 Rust 로 쓴 프로젝트를 유지하기가 어려웠다고 인정합니다. 그리고 1.0 이 그 격변의 끝이라고 적습니다.

1.0 전1.0 뒤
옛 코드판마다 깨진다계속 컴파일된다
새 기능곧바로 언어에야간판에서 익힌 뒤 안정판으로
릴리스석 달쯤마다, 크게여섯 주마다, 작게

표는 발표문과 안정성 글의 내용을 간추린 것입니다.

여섯 주마다 떠나는 열차

1.0 부터 Rust 는 브라우저(Firefox·Chrome)처럼 여섯 주마다 정기 릴리스를 냅니다. 기능이 준비됐든 아니든 열차는 떠나고, 못 탄 기능은 다음 열차를 탑니다.

nightly — 매일→ beta — 여섯 주→ stable — 여섯 주
  • 채널은 셋입니다 — nightly, beta, stable.
  • 여섯 주마다 그때의 개발판에서 새 베타를 떼고, 앞의 베타가 새 안정판이 됩니다.

불안정한 기능은 야간판에만 있다

아직 다듬는 중인 기능과 API 는 야간판(nightly)에서만, 그것도 쓰겠다고 명시해야 쓸 수 있습니다. 안정판에 들어온 것은 깨지 않겠다는 약속의 대상이 됩니다.

이 책은 안정판만 씁니다 — 이 기계의 컴파일러는 안정판 이고, 책의 모든 예제는 야간판 전용 기능 없이 돕니다. 인터넷에서 #![feature(...)] 로 시작하는 코드를 보면 야간판 전용이라는 뜻입니다.

결정은 공개된 문서로 한다 — RFC

1.0 발표문은 운영 방식도 적었습니다 — Rust 의 주요 결정은 모두 RFC(의견 요청서)라는 문서로 쓰이고 공개된 자리에서 논의된다.

  • 앞 장에서 본 "런타임 제거" 가 RFC 230, "Gc<T> 제거" 가 RFC 256 이었습니다.
  • 다음 장의 에디션도 RFC 2052 에서 나왔습니다.
"왜 이렇게 생겼지?" 의 답 — 문법이 낯설 때 그 기능의 RFC 를 찾으면 동기와 버려진 대안이 적혀 있습니다.

약속은 지켜지고 있다 — 1.0 시절 코드를 돌려 본다

1.0 무렵의 방식 그대로 쓴 코드입니다. 오류를 위로 넘기는 try! 매크로를 씁니다. 지금 컴파일러도 2015 에디션으로는 이것을 받아 줍니다.

경고는 하되 깨지는 않는다 — "이제는 ? 를 쓰라" 고 알려 주지만, 실행 파일은 만들어지고 답도 맞습니다.

같은 코드의 지금 모양 — ?

에 ? 연산자가 안정화됐습니다. try!(식) 대신 식 뒤에 물음표 하나를 붙입니다.

옛 방식도, 새 방식도 같은 컴파일러가 받는다 — 호환성 약속이 실제로 뜻하는 바입니다. ? 는 9부에서 자세히 봅니다.

4장

에디션

옛 코드를 깨지 않고 문법을 바꾸는 법 · 2015 · 2018 · 2021 · 2024

깨지 않겠다고 했는데, 키워드를 늘려야 한다면

안정성 약속에는 빈틈이 하나 있습니다. 새 키워드입니다. async 를 키워드로 만들면 let async = 1; 이라고 쓴 옛 코드가 깨집니다.

  • Rust 는 이 문제를 에디션(edition)으로 풉니다. 뒤로 호환되지 않는 변화는 다음 에디션에 모읍니다.
  • 에디션은 고르는 것입니다. 옮기겠다고 하기 전까지 옛 크레이트는 옛 규칙으로 컴파일됩니다.
이미 본 것 — 2부 1장에서 같은 파일을 가장 옛 에디션과 가장 새 에디션으로 컴파일해 봤습니다.

에디션은 생태계를 가르지 않는다

에디션을 만들 때의 가장 중요한 규칙 — 한 에디션의 크레이트는 다른 에디션으로 컴파일한 크레이트와 매끄럽게 함께 쓰여야 한다.

  • 크레이트마다 Cargo.toml 에 자기 에디션을 적습니다.
  • 그래서 에디션이 바꿀 수 있는 것은 겉(문법·키워드·기본 설정)에 가깝고, 컴파일된 뒤의 모양은 같습니다.
  • 처음 제안은 "두세 해마다 한 번" 이었습니다.
파이썬 2 → 3 과의 차이 — 옛 에디션 라이브러리를 새 에디션 프로그램이 그대로 가져다 씁니다. 한꺼번에 옮길 필요가 없습니다.

2018 에디션 — 1.0 뒤 세 해의 묶음

과 함께 첫 새 에디션 "Rust 2018" 이 나왔습니다. 지난 세 해 동안 해 온 일을 한데 모아 하나의 꾸러미로 내놓는 기회라고 했습니다.

2018 이 예약한 낱말 — try

3장에서 가장 옛 에디션으로 돌렸던 try! 코드를 지금 에디션으로 컴파일합니다. 2018 에디션부터 try 는 예약어라 매크로 이름으로 쓸 수 없습니다.

빠져나갈 길도 알려 준다 — 마지막 help: 의 r#try 는 "날 식별자" 입니다. 키워드가 된 이름을 옛 이름 그대로 부르는 문법으로, 에디션을 넘나드는 다리 구실을 합니다.

2021 에디션 — 작지만 매끈하게

에 2021 에디션이 안정화됐습니다. 발표문은 스스로 "2018 에 견주면 작은 에디션" 이라고 말합니다.

  • 클로저가 변수 전체가 아니라 쓰는 필드만 붙잡는다.
  • 배열의 into_iter() 가 참조가 아니라 값을 꺼낸다.
  • TryInto · TryFrom · FromIterator 가 기본으로 보인다(프렐류드).
다음 넉 장에서 앞의 둘을 에디션만 바꿔 가며 직접 돌려 봅니다.

배열의 into_iter() — 2018 에디션에서는 참조

같은 메서드 호출이 에디션에 따라 다른 것을 돌려줍니다. 먼저 옛 동작입니다.

경고가 미리 알려 준다 — "Rust 2021 에서는 뜻이 달라진다" 는 줄을 보세요. 에디션을 옮기기 전에 컴파일러가 바뀔 자리를 짚어 줍니다.

배열의 into_iter() — 2021 에디션에서는 값 — E0382

2021 에디션에서는 배열의 원소를 값으로 꺼냅니다. 배열은 그 순간 소비되므로, 뒤에서 다시 쓰면 "이동된 값을 빌렸다" 는 오류가 납니다.

이동(move)이 무엇인지는 6부의 주제입니다. 여기서는 "에디션이 같은 줄의 뜻을 바꿀 수 있다" 는 것만 봅니다.

클로저의 붙잡기 — 2018 에디션에서는 통째로 — E0502

클로저 bump 는 p.score 만 고칩니다. 그런데 2018 에디션까지는 클로저가 p 전체를 가변으로 빌렸고, 그래서 p.name 을 빌려 둔 것과 부딪혔습니다.

클로저의 붙잡기 — 2021 에디션에서는 필드만

글자 하나 고치지 않고 에디션만 2021 로 올리면 컴파일됩니다. 클로저가 p.score 만 빌리기 때문입니다.

에디션은 더 엄격해지기만 하지 않는다 — 옛 규칙이 괜히 막던 코드를 새 에디션이 받아 주기도 합니다. 클로저는 12부에서 봅니다.

경고가 오류로 — 맨 트레이트 객체 — E0782

옛 Rust 는 트레이트 이름을 타입처럼 그대로 썼습니다(Box<Shape>). 한동안 경고였다가 2021 에디션에서 오류가 됐습니다. 지금은 dyn 을 붙여 "실행 중에 고르는 타입" 임을 드러냅니다.

2015 에디션으로는 같은 파일이 경고만 내고 돕니다(답은 9). dyn 은 10부에서 봅니다.

2024 에디션 — 가장 큰 에디션

에 2024 에디션이 안정화됐습니다. 발표문은 "지금까지 낸 에디션 가운데 가장 크다" 고 적었습니다.

  • gen 을 키워드로 예약 — 앞으로 넣을 제너레이터 블록을 위해.
  • extern 블록에 unsafe 를 붙여야 한다.
  • std::env::set_var 같은 함수가 unsafe 함수가 됐다.
  • Future · IntoFuture 가 프렐류드에.
이 책의 기준 — 모든 예제는 따로 적지 않는 한 2024 에디션입니다.

2024 가 예약한 낱말 — gen

변수 이름 gen 은 2021 에디션까지 평범한 이름이었습니다(같은 파일을 2021 로 컴파일하면 3 을 찍습니다). 2024 에디션에서는 예약어입니다.

옮기는 일은 도구가 한다 — cargo fix --edition 이 이런 이름을 r#gen 으로 바꿔 줍니다.

안전하다고 믿었던 함수가 unsafe 로 — E0133

환경 변수를 고치는 set_var 는 여러 스레드가 도는 프로그램에서 위험할 수 있습니다. 2021 에디션까지는 그냥 부를 수 있었지만(같은 파일이 Ok("rust") 를 찍습니다), 2024 에디션은 unsafe 블록을 요구합니다.

unsafe 는 "컴파일러 대신 내가 책임진다" 는 표시입니다. 16부에서 봅니다.

퀴즈 — 에디션

Q. 2015 에디션으로 쓴 라이브러리를 2024 에디션 프로그램에서 쓰려면, 라이브러리를 먼저 2024 로 옮겨야 할까요?

A. 아닙니다. 에디션은 크레이트마다 따로 고르고, 서로 다른 에디션의 크레이트는 그대로 함께 쓰입니다. 이 부의 실험에서도 같은 컴파일러가 --edition 2015 와 --edition 2024 를 모두 받았습니다.

NLL — 빌림 검사기의 두 번째 판

처음의 빌림 검사기는 빌림이 중괄호 블록의 끝까지 이어진다고 봤습니다. NLL(non-lexical lifetimes)은 빌림이 "마지막으로 쓴 곳" 에서 끝난다고 봅니다. Rust 팀은 이것을 빌림 검사기의 두 번째 판이라고 부릅니다.

  • 2018 에디션에서 먼저 켜졌고 , 에 2015 에디션에도 켜졌으며 , 1.63 에서 옛 검사기가 완전히 사라졌습니다.

async / await

에 async–await 문법이 안정판에 들어왔습니다. 바탕이 된 "비용 없는 퓨처" 의 생각은 2016년에 처음 제안됐으니, 세 해가 걸린 셈입니다.

  • 2018 에디션이 async 를 미리 키워드로 잡아 둔 까닭이 이것입니다.
  • 녹색 스레드를 언어에서 걷어 낸 자리에, 런타임을 라이브러리로 고르는 방식이 들어온 것입니다.
이 책에서는 맛보기만 — 표준 라이브러리만으로 퓨처 하나를 끝까지 돌려 봅니다 (16부).

const 제네릭 — 길이 32 의 벽이 사라졌다

배열 [T; N] 의 N 은 값입니다. 예전에는 "모든 길이의 배열" 에 대해 무언가를 한 번에 정의할 방법이 없어서, 표준 라이브러리의 배열 기능조차 길이 32 까지만 됐습니다. 1.51 이 타입 자리에 값을 받는 제네릭을 열었습니다.

let-else 와 GATs — 같은 날 들어온 작은 것과 큰 것

은 매일 쓰는 작은 문법 let … else 와, RFC 가 열린 지 여섯 해 반 만에 안정화된 제네릭 연관 타입(GATs)을 함께 실었습니다.

큰 기능은 오래 걸린다 — 안정판에 넣으면 되돌릴 수 없기 때문입니다. let … else 는 7부에서 다시 봅니다.

트레이트 안의 async fn

async fn 이 들어온 뒤에도 한동안 트레이트 안에서는 쓸 수 없었습니다. 에 이 제한이 풀렸습니다.

async fn→ 트레이트 안에서도→ 프렐류드에 Future
Rust 가 기능을 내는 방식 — 먼저 쓸 수 있는 최소한을 안정화하고, 빈 곳을 릴리스마다 메웁니다. 그래서 "이 문법은 몇 버전부터" 가 중요하고, 이 책은 그것을 배지로 표시합니다.

사람과 조직, 그리고 쓰이는 곳

Firefox · 모질라의 감원 · Rust 재단 · 안드로이드 · 리눅스 커널 · 열 돌

Firefox 에 실리다

2016년, 모질라의 한 팀이 Rust 로 쓴 브라우저 엔진 Servo 를 공개했습니다. 그리고 2017년 11월의 Firefox Quantum 에 Servo 의 CSS 엔진 Stylo 가 들어갑니다. C++ 약 16만 줄이 Rust 8만 5천 줄로 바뀌었습니다.

"두려움 없는 동시성" — 페이지 스타일 계산을 여러 스레드로 나누는 일은 C++ 로 두 번 시도했다가 실패한 일이었다고 그 글은 적습니다. Rust 가 내건 두 번째 약속이 처음으로 큰 제품에서 값을 한 사례입니다.

모질라의 감원과 홀로서기

Rust 는 1.0 과 함께 방향과 운영을 모질라에서 독립시켰지만 , 돈과 법적 지위는 여전히 모질라에 기대고 있었습니다. 2020년 8월 11일, 모질라는 약 250명을 내보내는 구조 조정을 발표합니다. Rust 를 만들던 사람들이 그 안에 있었습니다.

일주일 뒤의 답 — Rust 코어 팀은 "Rust 의 미래를 위한 기초를 놓는다" 는 글에서 재단을 세우겠다고 알렸습니다.

Rust 재단

2021년, 큰 기술 회사들이 돈을 내어 비영리 Rust 재단(Rust Foundation)을 세웠습니다.

  • 재단은 언어를 설계하지 않습니다. 설계는 여전히 RFC 와 프로젝트의 팀들이 합니다.
  • 재단이 하는 일은 사람과 기반 시설을 받치는 것 — 기여자 지원금, 서버 비용 같은 것입니다.

재단의 구실에 대한 설명은 같은 기사에서 왔습니다.

브라우저 밖으로 — 안드로이드와 리눅스 커널

언제무엇
2021년 4월구글이 안드로이드 플랫폼에서 Rust 를 지원한다고 알림
2022년 10월리눅스 6.1 에 Rust 지원이 들어감
부풀리지 않기 — 그 글은 바로 이어서 "6.1 커널을 쓰는 어떤 시스템도 아직 Rust 코드를 돌리지는 않는다" 고 적습니다. 들어간 것은 커널 개발자가 Rust 로 써 볼 수 있는 토대였습니다.

친절한 오류 메시지도 역사의 일부다

Rust 는 스택 오버플로 개발자 설문에서 일곱 해 내리 "가장 사랑받는 언어" 로 꼽혔습니다. 기사는 그 까닭의 하나로 컴파일러의 오류 메시지를 듭니다 — 무엇이 틀렸는지 말하고, 어떻게 고칠지도 정중하게 권한다.

이 책이 오류를 숨기지 않는 까닭 — 앞 장들에서 본 help: 줄이 바로 그것입니다. Rust 를 배운다는 것의 절반은 이 메시지를 읽는 법을 배우는 일입니다. 그래서 이 책은 오류가 나는 코드도 실제로 컴파일해 그 메시지를 그대로 싣습니다.

열 돌

은 1.0 이 나온 지 꼭 열 해가 되는 날에 나왔습니다. 발표문은 1.0 부터 지켜 온 한결같은 릴리스 주기를 이번에도 따랐다고 적습니다. 이 기계에 깔린 컴파일러는 입니다.

퀴즈 — 버린 것과 지킨 것

Q. 1.0 전의 Rust 에 있다가 사라진 것을 셋 대 보세요. 그리고 그것들이 사라진 자리를 지금 무엇이 맡고 있는지도요.

A. ① 기호 포인터 ~T → 라이브러리 타입 Box<T>. ② 가비지 컬렉터 (@T, Gc<T>) → 소유권과, 필요할 때 고르는 Rc<T>. ③ 녹색 스레드와 런타임 → OS 스레드와, 라이브러리로 고르는 async 런타임. 그 밖에 int·uint, fail!, 타입 상태 검사도 있습니다.
