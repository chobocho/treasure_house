Rust의 역사

여가 프로젝트에서 1.0 까지 · 안정성 약속과 여섯 주 열차 · 에디션 네 번 · 1.0 뒤의 큰 걸음 · 재단과 리눅스 커널

이 부에서 할 일

문법은 그것이 생긴 까닭을 알면 덜 낯섭니다. 이 부는 Rust 가 어디서 왔고, 무엇을 버렸고, 무엇을 약속했는지를 따라갑니다. 주장마다 0부에서 본 표시가 붙어 있고(누르면 근거가 된 글로 갑니다), 옛 문법이 지금 어떻게 되는지는 이 기계의 컴파일러로 직접 돌려 보입니다.

  • 1장 — 시작: 한 사람의 여가 프로젝트가 모질라의 연구 프로젝트가 되기까지
  • 2장 — 1.0 전의 격변: 기호 포인터, GC, 녹색 스레드를 버리다
  • 3장 — 1.0 과 안정성 약속, 여섯 주마다 떠나는 열차
  • 4장 — 에디션: 옛 코드를 깨지 않고 문법을 바꾸는 법
  • 5장 — 1.0 뒤의 큰 걸음: ? · NLL · async · const 제네릭 · let-else
  • 6장 — 사람과 조직, 그리고 쓰이는 곳
미리 쓰는 문법 — 이 부의 코드에는 아직 배우지 않은 문법이 나옵니다. "무엇이 바뀌었나" 를 보이려는 코드이므로, 지금은 어느 줄이 달라졌고 컴파일러가 무엇이라 하는지만 보면 됩니다. 문법 자체는 슬라이드마다 가리키는 부에서 배웁니다. 오류 화면을 읽는 법은 0부에서 본 그대로입니다.

시작

고장 난 엘리베이터에서 시작됐다

이 장은 Rust 가 누구의 손에서, 무엇을 풀려고 시작됐는지를 봅니다. 2006년, 모질라에서 일하던 스물아홉 살의 프로그래머 그레이든 호어(Graydon Hoare)가 집에 돌아와 보니 엘리베이터가 멈춰 있었습니다. 엘리베이터의 소프트웨어가 죽은 것이었습니다.

  • 집은 21층이었습니다. 기사에 따르면 그는 이렇게 죽는 일의 상당수가 프로그램이 메모리를 다루는 방식의 문제에서 온다는 것을 알고 있었습니다.
  • 그리고 작고 빠르면서 메모리 버그가 없는 코드를 쓸 수 있기를 바라며 새 언어를 설계하기 시작했습니다.
이 일화의 출처 — 2023년 MIT 테크놀로지 리뷰에 실린 기사입니다. 1장의 이야기는 대부분 그 기사에 기대고 있습니다.

이름은 녹병균에서 왔다

호어는 이 언어에 Rust 라는 이름을 붙였습니다. 기사에 따르면 유난히 끈질긴 균류의 한 무리(녹병균)에서 딴 이름입니다.

"살아남도록 과하게 설계된" — 기사가 전하는 호어의 말로, 그 균류를 두고 한 표현입니다.

처음 몇 해는 여가 프로젝트였다

Rust 는 처음에 여가 프로젝트(side project)였습니다. 호어는 몇 해 동안 이것을 다듬었고, 다른 개발자들에게 보여 주었을 때의 반응은 엇갈렸습니다.

  • 2009년, 모질라가 Rust 를 공식 후원하기로 합니다. 언어는 오픈 소스로 두고, 모질라는 엔지니어의 급여를 대어 첫걸음을 받쳤습니다.
  • 2010년, 브리티시컬럼비아에서 열린 모질라 행사에서 이 실험적인 언어를 다루는 발표가 열렸습니다.
그래서 "몇 년생" 인가 — Rust 프로젝트 스스로는 "2010년에(세기에 따라서는 2006년에) 모질라 리서치의 프로젝트로 구상됐다" 고 적습니다.

풀려던 문제는 둘이었다

Rust 팀의 글은 이 프로젝트가 두 가지 까다로운 문제를 풀려고 시작됐다고 적습니다. 안전한 시스템 프로그래밍은 어떻게 하는가, 그리고 동시성을 어떻게 고통 없이 만드는가입니다.

방식얻는 것치르는 값
C · C++ — 손으로 메모리 관리속도, 작은 크기, 세밀한 제어메모리 버그, 보안 구멍
Java · JavaScript · Python — 가비지 컬렉터메모리 실수가 없다세밀한 제어를 잃고, 느려지고, 메모리를 더 쓴다
Rust — 엄격한 규칙을 컴파일러가 검사두 방식의 중간 — 손으로 관리하지 않아도 메모리 안전배워야 할 규칙이 많고 쓰기가 더 어렵다

줄마다 한 방식이 얻는 것과 치르는 값을 가로로 읽습니다. 표는 기사의 설명을 줄인 것입니다.

답은 "소유권" 이었다

기사에 따르면 모질라의 엔지니어들과 세계 곳곳의 자원자들은 몇 해에 걸쳐 Rust 의 핵심을 다듬었습니다. 데이터 한 조각을 변수 하나만 가리킬 수 있게 하는 소유권(ownership) 체계입니다.

  • 규칙을 어긴 코드는 컴파일러가 실행 파일로 만들어 주지 않습니다. 검사가 실행 전에 끝난다는 뜻입니다.
  • Rust 가 쓴 기법의 많은 수는 새 생각이 아니었습니다. 초기 개발자 한 사람의 말로는 "대부분 수십 년 된 연구" 였고 , 팀은 그것을 실제로 쓸 수 있는 기능으로 옮겼습니다.
이 책에서는 — 6부 소유권·빌림·슬라이스가 통째로 이 이야기입니다.

첫 번째 쓰임새는 브라우저 엔진이었다

기사에 따르면 모질라의 경영진은 Rust 가 더 나은 브라우저 엔진을 만드는 데 도움이 되리라고 보았습니다. 브라우저는 복잡하기로 이름난 소프트웨어여서 위험한 메모리 버그가 생길 자리가 많습니다. Rust 블로그는 Rust 의 "창립 응용(founding application)" 이 실험적 브라우저 엔진 Servo 였다고 적습니다.

Rust (언어)→ Servo (그 언어로 만든 실험적 브라우저 엔진)
6장에서 이어집니다 — Servo 의 한 부분이 Firefox 에 실리는 이야기는 6장에서 봅니다.

퀴즈 — 풀려던 문제와 그 답

Q. Rust 프로젝트가 풀려던 문제 둘은 무엇이고, 팀이 몇 해에 걸쳐 다듬은 핵심은 무엇일까요?

A. 문제는 안전한 시스템 프로그래밍과, 고통 없는 동시성입니다(풀려던 문제는 둘이었다). 다듬은 핵심은 데이터 한 조각을 변수 하나만 가리킬 수 있게 하는 소유권 체계이고 , 규칙을 어긴 코드는 컴파일러가 실행 파일로 만들어 주지 않습니다(답은 "소유권" 이었다).

믿을 수 있는 것은 둘뿐이었다 — 안전, 그리고 변화

1.0 을 앞둔 2014년 10월, Rust 팀의 글은 그 시절을 이렇게 돌아봤습니다 — 초기부터 믿을 수 있는 것은 두 가지, 안전과 변화뿐이었다.

  • 같은 글은 개발하는 동안 막다른 길을 많이 만났고, 그래서 필요한 대로 언어를 바꿀 자유가 꼭 있어야 했다고 적습니다.
  • 한 예로, 0.1 의 기능 목록에 있던 타입 상태(typestate)는 의 릴리스 노트에 "제거됐다" 고 적혀 있습니다.
  • 2013년에는 언어를 처음 만든 호어가 프로젝트에서 물러납니다.

기호로 나뉘던 포인터들이 사라졌다 — E0600

옛 Rust 에는 포인터 종류가 여럿이었고 기호(sigil)로 구별했습니다. 2014년 9월의 글은 그 기호들이 사라지고 참조 &T 와 &mut T 만 남았다고 적습니다. 그런 기호의 하나가 물결표 ~ 입니다. 옛 표기를 지금 컴파일러에 넣어 봅니다.

  • 읽는 법 — 지금 컴파일러는 ~ 를 포인터 기호로 읽지 않습니다. 번호 없는 첫 오류가 단항 연산자로 쓸 수 없다고 하고, help: 에서 비트를 뒤집는 ! 를 권합니다. E0600 은 그 ! 를 문자열에는 붙일 수 없다는 둘째 오류입니다.
  • 의 릴리스 노트 — ~T 는 언어에서 제거됐고, Box<T> 타입이 그 자리를 잇는다. Box<T> 는 14부에서 봅니다.
미리 쓰는 문법 — let 은 3부, println! 은 2부에서 배웁니다. 이 장의 예제 셋에서는 3번 줄의 옛 표기와, 그것에 컴파일러가 하는 말만 봅니다.

가비지 컬렉터를 버렸다

초기의 Rust 에는 가비지 컬렉터(garbage collector, GC)가 있었습니다. 기사는 메모리 관리 체계가 나아질수록 쓸 일이 줄었고 2013년까지는 팀이 그것을 걷어 냈다고 적습니다. 릴리스 노트에서 마지막 조각이 빠지는 것은 그 이듬해입니다.

  • RFC 256 의 회고 — 오래전 Rust 는 @T 라는 표기로 자동 관리되는 메모리를 언어에 넣어 두었고 , 그 구현은 임시방편으로 참조 세기였다.
  • 의 릴리스 노트 — @T 는 언어에서 제거됐고, 표준 라이브러리의 Gc<T> 타입이 그 자리를 잇는다.
  • 의 릴리스 노트 — 한때 @ 기호로 적던, 참조를 세는 옛 GC 타입 Gc<T> 가 마침내 제거됐다. 그 제거를 제안한 문서가 RFC 256 입니다.
그래서 Rust 에는 지금도 GC 가 없습니다 — 값은 주인이 스코프(scope)를 벗어나는 순간 정리됩니다(6부). 여럿이 함께 가져야 하는 값은 Rc<T> 로 직접 고릅니다(14부).

녹색 스레드와 런타임도 버렸다

옛 Rust 의 표준 라이브러리에는 런타임이 들어 있어서, OS 스레드와 녹색 스레드(green thread — OS 가 아니라 프로그램 안의 스케줄러가 굴리는 스레드)를 둘 다 받쳤습니다. 1.0 을 앞두고 녹색 스레드 지원을 표준 라이브러리에서 떼어 바깥 패키지로 옮깁니다. Rust 의 모델을 운영 체제에 더 가깝게 맞추기 위해서였습니다.

  • 1.0 알파()의 릴리스 노트 — Rust 에는 이제 어떤 종류의 런타임도 없고, 녹색 스레드가 아니라 OS 스레드만 지원한다.
지금은 — std::thread::spawn 이 만드는 것은 OS 스레드입니다(15부). 비동기 문법 async 는 한참 뒤에 들어옵니다(5장, 16부 3장).

int 와 uint 가 isize 와 usize 로 — E0425

1.0 알파의 릴리스 노트는 정수 타입을 둘러싼 오랜 논쟁이 매듭지어졌다고 적습니다 — 포인터 크기 정수의 이름은 int · uint 가 아니라 isize · usize 다. 옛 이름을 타입 자리(let x: 뒤)에 적어 봅니다.

읽는 법 — 오류 첫 줄은 "이 스코프에서 타입 int 를 찾을 수 없다" 입니다. help: 가 권하는 것은 i32 이고, 옛 이름을 이은 isize 가 아닙니다. 같은 릴리스 노트에는 타입이 추론되지 않은 수에 i32(또는 f64)를 고른다는 줄도 있습니다. 정수 타입은 3부에서 봅니다.

fail! 은 panic! 이 됐다

같은 1.0 알파의 릴리스 노트에는 fail! 매크로의 이름을 panic! 으로 바꿨다는 줄이 있습니다. 프로그램을 그 자리에서 멈추는 매크로입니다(9부). 옛 이름을 지금 넣으면 이렇게 됩니다.

1.0 전의 글을 볼 때 — 이번에는 help: 도 없이 "그런 매크로를 찾을 수 없다" 뿐입니다. 2015년 5월의 1.0 보다 앞선 글의 코드는 이 세 예처럼 지금 컴파일러가 받지 않을 수 있습니다. 글의 날짜를 먼저 봅니다.

버리고 나니 핵심 하나가 남았다

2014년 9월, 1.0 으로 가는 길을 알린 글은 이렇게 정리합니다 — 언어는 이제 소유권과 빌림(ownership and borrowing)이라는 단순한 핵심 개념 하나에 집중한다.

  • 처음에 소유권은 태스크(task — 그때의 동시 실행 단위) 사이에 데이터를 안전하고 효율적으로 넘기려고 들인 장치였습니다.
  • 그 뒤 같은 장치로 온갖 것을 언어에서 라이브러리로 내보낼 수 있다는 것을 알게 됐다고 글은 적습니다.
이 책의 순서가 그 결과입니다 — 소유권(6부)을 지나야 문자열·컬렉션(8부), 스마트 포인터(14부), 스레드(15부)가 전부 "라이브러리에 있는 평범한 타입" 으로 읽힙니다.

퀴즈 — 왜 그렇게 자주 바꿨나

Q. 0.1 의 릴리스 노트는 앞으로의 코드가 예고 없이 깨질 것이라고 적었습니다. Rust 팀은 그 시절에 언어를 바꿀 자유가 왜 필요했다고 돌아봤을까요? 그리고 그렇게 바꾼 끝에 언어가 집중하게 된 것은 무엇일까요?

A. 개발하는 동안 막다른 길을 많이 만났기 때문입니다(믿을 수 있는 것은 둘뿐이었다). 그 끝에 언어는 소유권과 빌림이라는 단순한 핵심 개념 하나에 집중합니다(버리고 나니 핵심 하나가 남았다). 그 사이에 바뀐 것이 많아서, 이 장의 예제 셋처럼 1.0 보다 앞선 글의 코드는 지금 컴파일러가 받지 않을 수 있습니다(fail! 은 panic! 이 됐다).

3장

1.0 과 안정성 약속

안정성 약속 · cargo 와 crates.io · 1.0 발표 · "격변의 끝" · 여섯 주 열차와 세 채널 · 야간판 전용 기능 · RFC · try! 와 ?

1.0 은 안정성의 약속이었다

이 장은 1.0 이 무엇을 약속했고, 그 약속을 어떤 장치로 지키는지를 봅니다. 2014년 9월의 글은 이렇게 약속합니다 — 1.0 뒤의 1.x 릴리스는 뒤로 호환된다. 곧, 지금 있는 코드는 고치지 않아도 계속 컴파일된다(컴파일러 버그는 예외).

  • 다음 달의 글은 1.0 이 무엇보다 안정성에 대한 약속이라고 적습니다. 1.0 안정판에서 컴파일되는 코드는 1.x 안정판에서도 큰 수고 없이 컴파일돼야 한다는 것입니다.
  • 같은 글은 팀의 책임을 "Rust 를 올리는 일이 두렵지 않게 하는 것" 이라고 적습니다.
안정성은 멈춤이 아니다 — 같은 글의 설명입니다. Rust 가 진화를 멈춘다는 뜻이 아니라, 새 판을 자주 내되 올리는 일이 아프지 않게 한다는 뜻입니다.

1.0 보다 먼저 온 것 — cargo 와 crates.io

2014년 11월, 패키지 저장소 crates.io 가 문을 엽니다. 패키지 관리자 cargo 는 Bundler 와 NPM 의 전통을 잇는 설계라고 그 글은 소개했습니다.

언어보다 도구가 먼저 — crates.io 가 열린 것은 1.0 보다 여섯 달쯤 앞입니다. 1.0 발표문은 그 사이 패키지 수가 꾸준히 늘었다고 적습니다. cargo 는 2부 2장에서 쓰기 시작하고, crates.io 는 13부에서 다시 봅니다.

1.0 이 나왔다

이 나왔습니다. Rust 코어 팀은 "오늘 Rust 1.0 을 발표하게 되어 매우 자랑스럽다" 로 시작하는 글을 올렸습니다.

  • 가비지 컬렉터도 런타임도 요구하지 않으므로, Rust 로 쓴 라이브러리를 C 라이브러리 자리에 그대로 끼워 쓸 수 있다고 소개했습니다.
  • 기사는 세계 곳곳에서 출시를 축하하는 모임이 열렸다고 전합니다.
  • 모질라가 Rust 를 품에 들인 지 여섯 해 만이었습니다.

"1.0 은 그 격변의 끝을 뜻합니다"

발표문은 지난 실험 덕에 언어가 더 단순하고 강해졌지만, 언어와 표준 라이브러리가 끊임없이 바뀐 탓에 Rust 로 쓴 프로젝트를 유지하기가 어려웠다고 적습니다. 그리고 1.0 이 그 격변의 끝이라고 적습니다.

1.0 전1.0 뒤
있던 코드언어와 표준 라이브러리가 끊임없이 바뀐다깨는 변화는 대체로 하지 않는다(컴파일러 버그 같은 예외는 있다)
다듬는 중인 기능필요한 대로 언어를 바꿨다야간판에만 두고, 안정됐다고 본 것만 베타·안정판에
릴리스0.x 판(2장의 표)여섯 주마다

줄마다 1.0 전과 뒤를 가로로 견줍니다. 야간판 · 베타 · 안정판이 무엇인지는 다음 슬라이드에서 봅니다. 표는 1.0 발표문과 안정성 글의 내용을 간추린 것입니다.

여섯 주마다 떠나는 열차

1.0 부터 Rust 는 Firefox 나 Chrome 브라우저처럼 여섯 주마다 정기 릴리스를 냅니다. 안정성 글은 이 방식을, 웹 브라우저에서 처음 쓰인 "열차 모델(train model)" 의 변형이라고 부릅니다.

nightly — 매일→ beta — 여섯 주→ stable — 여섯 주
  • 채널은 셋입니다 — nightly(야간판), beta(베타), stable(안정판).
  • 매일, 그날 마지막으로 빌드에 성공한 개발판(master)이 새 야간판이 됩니다.
  • 여섯 주마다 그때의 개발판에서 새 베타를 떼고, 앞의 베타가 새 안정판이 됩니다.

불안정한 기능은 야간판에만 있다 — E0554

아직 다듬는 중인 기능과 API 는 야간판(nightly)에서만, 그것도 쓰겠다고 명시해야 쓸 수 있습니다. 베타와 안정판에는 안정됐다고 본 것만 들어가고, 그것을 쓰는 코드는 깨지 않겠다는 약속이 따라붙습니다. 그 "명시" 가 파일 맨 위에 적는 #![feature(...)] 줄입니다. 안정판 컴파일러에 넣어 봅니다.

이 책은 안정판만 씁니다 — 이 기계의 컴파일러는 안정판 이고, 오류 첫 줄의 말대로 #![feature] 는 안정 채널에서 쓸 수 없습니다. 밑줄은 2번 줄 전체입니다. 인터넷에서 이 줄로 시작하는 코드를 보면 야간판 전용이라는 뜻입니다. #! 로 시작하는 이런 줄은 속성(attribute)이고 13부에서 봅니다.

결정은 공개된 문서로 한다 — RFC

1.0 발표문은 운영 방식도 적었습니다 — 한 해 남짓 전에 RFC(의견 요청서) 절차를 들인 뒤로, Rust 의 주요 결정은 모두 RFC 로 쓰이고 공개된 자리에서 논의된다.

  • 2장에서 본 런타임 제거를 제안한 문서가 RFC 230, Gc<T> 제거를 제안한 문서가 RFC 256 입니다.
  • 4장의 에디션을 제안한 문서는 RFC 2052 입니다.
"왜 이렇게 생겼지?" 의 답 — 이 세 RFC 에는 모두 동기(Motivation) 절이 있고, RFC 256 과 2052 에는 대안(Alternatives) 절도 있습니다. 문법이 낯설 때 그 기능의 RFC 를 찾아볼 만합니다.

옛 방식의 코드가 지금도 컴파일된다 — try!

약속이 지켜지는지 하나를 돌려 봅니다. ? 연산자가 생기기 전의 방식으로 쓴 코드입니다. try!(식) 은 식이 오류면 그 오류를 들고 함수에서 바로 빠져나가고, 성공이면 값을 꺼내는 매크로입니다. 이 파일을 2015 에디션(1.0 의 문법 판 — 4장)으로 컴파일합니다.

경고는 하되 깨지는 않는다 — 컴파일러는 try 매크로가 낡았으니 ? 연산자를 쓰라고 경고합니다. 그래도 실행 파일은 만들어지고, "21" 은 Ok(42) 로, 숫자가 아닌 "x" 는 오류(Err)로 나옵니다.
미리 쓰는 문법 — Result 와 Ok · Err 는 9부 3장에서 배웁니다. 이 슬라이드와 다음 슬라이드에서는 5번 줄이 어떻게 달라지는지만 봅니다.

같은 코드의 지금 모양 — ?

에 ? 연산자가 안정화됐습니다. 릴리스 노트는 이것을 try! 매크로처럼 오류를 위로 넘기는 간단한 방법이라고 소개합니다. try!(식) 대신 식 뒤에 물음표 하나를 붙입니다.

옛 방식도, 새 방식도 같은 컴파일러가 받는다 — 앞 슬라이드는 --edition 2015, 이 슬라이드는 --edition 2024 이고, 두 프로그램이 찍는 결과는 같습니다. 이 화면에는 경고도 없습니다. ? 는 9부에서 자세히 봅니다.

퀴즈 — 약속과 채널

Q. 1.0 뒤의 1.x 릴리스에서, 이미 있는 코드는 어떻게 된다고 Rust 는 약속했을까요? 그러면 아직 다듬는 중인 기능은 어디에 둘까요?

A. 고치지 않아도 계속 컴파일된다고 약속했습니다(컴파일러 버그는 예외 — 1.0 은 안정성의 약속이었다). 이 장에서도 try! 로 쓴 옛 방식의 코드가 경고만 내고 돌았습니다(옛 방식의 코드가 지금도 컴파일된다). 다듬는 중인 기능은 야간판에서만, 쓰겠다고 명시해야 쓸 수 있습니다. 그 명시인 #![feature(...)] 줄을 안정판 컴파일러는 E0554 로 거절했습니다(불안정한 기능은 야간판에만 있다).

에디션

깨지 않겠다고 했는데, 키워드를 늘려야 한다면

뒤로 호환되지 않는 변화가 쓸모 있을 때도 있습니다. 에디션 안내서가 드는 흔한 예가 새 키워드입니다. async 를 갑자기 키워드로 만들면 let async = 1; 이라고 쓴 코드가 깨집니다.

  • Rust 는 이 문제를 에디션(edition)으로 풉니다. 뒤로 호환되지 않는 변화는 다음 에디션으로 미룹니다.
  • 에디션은 고르는 것입니다. 새 에디션으로 옮기겠다고 하기 전까지, 있던 크레이트(crate — 라이브러리 하나나 프로그램 하나에 해당하는 컴파일 단위)에는 그 변화가 적용되지 않습니다.
직접 돌려 보기 — 0부에서 본 명령의 --edition 옵션이 에디션을 고르는 자리입니다. 이 장에서 그 옵션을 바꿔 가며 여러 번 돌려 보고, 2부 1장에서는 위의 let async = 1; 을 가장 옛 에디션과 가장 새 에디션으로 컴파일해 봅니다.

에디션은 생태계를 가르지 않는다

에디션 안내서가 "가장 중대한 규칙" 이라고 부르는 것 — 한 에디션의 크레이트는 다른 에디션으로 컴파일한 크레이트와 매끄럽게 함께 쓰여야 한다.

  • 크레이트마다 Cargo.toml 에 자기 에디션을 적습니다. Cargo.toml 은 cargo 프로젝트의 설정 파일로, 2부에서 봅니다.
  • 안내서의 말로 에디션의 변화는 "겉에 머무는(skin deep)" 편이고, 어느 에디션의 코드든 컴파일러 안에서는 결국 같은 내부 표현이 됩니다.
  • 에디션을 제안한 RFC 2052 는 두세 해마다 한 번 에디션을 선언하자고 했습니다.
한꺼번에 옮길 필요가 없다 — 2018 발표문의 말로, 2018 프로젝트는 2015 의존성을 쓸 수 있고 2015 프로젝트도 2018 의존성을 쓸 수 있습니다. 언제 옮길지는 크레이트마다 따로 정합니다.

2018 이 예약한 낱말 — try

3장에서 2015 에디션으로 돌렸던 try! 코드를, 글자 하나 바꾸지 않고 지금 에디션으로 컴파일합니다. 레퍼런스에 따르면 try 는 2018 에디션에서 예약어가 됐습니다. 3장에서는 경고만 내고 돌던 코드가, 이번에는 오류 첫 줄 "낡은 try 매크로를 썼다" 에서 멈춥니다.

고치는 길 둘 — = note: 줄이 까닭(2018 에디션에서 try 는 예약어)을 말하고, 첫 help: 는 ? 로 바꾸라고, 둘째 help: 는 r#try 로 적으라고 권합니다. r# 은 키워드가 된 낱말을 이름으로 쓰게 해 주는 "날 식별자(raw identifier)" 문법입니다(16부).

2021 에디션 — 작지만 매끈하게

이 2021 에디션을 안정화했습니다. 발표문은 스스로 "특히 2018 에 견주면 작은 에디션" 이라고 말합니다. 아래는 발표문의 변화 목록 가운데 넷입니다.

  • 클로저가 변수 전체가 아니라 쓰는 필드만 붙잡는다.
  • 배열의 into_iter() 가 원소를 참조가 아니라 값으로 내준다.
  • TryInto · TryFrom · FromIterator 가 따로 들여오지 않아도 보인다(프렐류드).
  • 경고이던 것 둘이 오류가 됐다 — 그 하나가 dyn 없는 트레이트 객체(bare_trait_objects).
미리 쓰는 문법 — 다음 슬라이드 다섯에서 둘째, 첫째, 넷째를 이 순서로, 에디션을 바꿔 가며 직접 돌려 봅니다. 반복문 · 클로저 · 트레이트가 나오지만 문법은 뒤의 부에서 배웁니다. 여기서는 두 에디션이 내는 화면이 어떻게 다른지만 봅니다.

배열의 into_iter() — 2018 에디션에서는 참조

같은 메서드 호출이 에디션에 따라 다른 것을 내줍니다. 4번 줄의 for 는 배열의 원소를 하나씩 n 에 받는 반복문이고, 5번 줄은 n 의 타입이 참조(&String)가 맞는지 컴파일러에게 확인받는 줄입니다. 먼저 2018 에디션입니다.

읽는 법 — 경고가 미리 알려 줍니다. = warning: this changes meaning in Rust 2021 줄부터 봅니다. 에디션을 옮기기 전에 컴파일러가 바뀔 자리(4번 줄)를 짚고, help: 둘로 뜻이 갈리지 않는 표기를 권합니다. 경고뿐이므로 프로그램은 돌고, 7번 줄에서 배열을 다시 찍습니다.

배열의 into_iter() — 2021 에디션에서는 값 — E0382

2021 에디션에서는 같은 호출이 원소를 값으로 내줍니다. 5번 줄의 타입 표기를 String 으로 바꾼 것 말고는 앞 슬라이드와 같은 파일입니다. 배열 names 는 4번 줄의 호출에서 옮겨 가 버렸으므로, 7번 줄에서 다시 쓰려 하면 "이동된 값을 빌렸다" 는 오류가 납니다.

이 실험에서 볼 것 — "에디션이 같은 줄의 뜻을 바꿀 수 있다" 는 것 하나입니다. 이동(move)이 무엇인지는 6부에서 봅니다.

클로저의 붙잡기 — 2018 에디션에서는 통째로 — E0502

13번 줄의 || p.score += 1 은 이름 없는 함수, 곧 클로저(closure)로, 바깥의 변수 p 를 붙잡아 씁니다. 고치는 것은 p.score 하나입니다. 그런데 2021 전에는 클로저가 변수를 늘 통째로 붙잡았습니다. 그래서 p 전체를 가변으로 빌리려다, 11번 줄에서 p.name 을 빌려 둔 것과 부딪힙니다.

읽는 법 — 오류 첫 줄은 "p 를 가변으로 빌릴 수 없다, 불변으로도 빌려 있기 때문이다" 입니다. 그 아래 밑줄이 11번 줄의 불변 빌림, 13번 줄의 가변 빌림, 15번 줄에서 name 을 다시 쓰는 곳을 차례로 짚습니다. 빌림 규칙은 6부에서 배웁니다.

클로저의 붙잡기 — 2021 에디션에서는 필드만

글자 하나 고치지 않고 에디션만 2021 로 올리면 컴파일되고, 15번 줄이 kim 1 을 찍습니다. 2021 에디션의 클로저는 쓰는 필드 p.score 만 붙잡기 때문입니다.

에디션은 더 엄격해지기만 하지 않는다 — 옛 규칙이 막던 코드를 새 에디션이 받아 주기도 합니다. 클로저와 붙잡기는 12부에서 봅니다.

경고가 오류로 — 맨 트레이트 객체 — E0782

트레이트(trait)는 타입이 갖춰야 할 메서드의 목록입니다(10부). 옛 표기는 트레이트 이름을 타입 자리에 그대로 썼습니다(Box<Shape>). 2021 에디션은 이 경고(bare_trait_objects)를 오류로 올렸습니다. help: 가 권하는 대로, 지금은 dyn 을 붙여 트레이트 객체(trait object)임을 드러냅니다.

읽는 법 — 2021 에디션의 오류 첫 줄은 "타입이 올 자리에 트레이트가 왔다" 입니다. 2015 에디션으로는 경고만 내고 돕니다(답은 9). 경고는 "지금 에디션(Rust 2015)에서는 받지만 Rust 2021 에서는 오류" 라고 미리 알립니다. dyn 과 트레이트 객체는 10부에서 봅니다.

2024 에디션 — 가장 큰 에디션

에 2024 에디션이 안정화됐습니다. 발표문은 "지금까지 낸 에디션 가운데 가장 크다" 고 적었습니다. 아래는 발표문의 변화 목록 가운데 넷입니다.

  • gen 을 키워드로 예약 — 앞으로 넣을 제너레이터 블록에 대비해.
  • extern 블록에 unsafe 키워드를 붙여야 한다(16부).
  • std::env::set_var 를 비롯한 함수 셋이 unsafe 함수가 됐다.
  • Future · IntoFuture 가 프렐류드에.
이 책의 기준 — 0부에서 본 대로 이 책의 예제는 따로 적지 않는 한 2024 에디션입니다. 다음 슬라이드 둘에서 첫째와 셋째를 돌려 봅니다.

2024 가 예약한 낱말 — gen

변수 이름 gen 은 2021 에디션에서는 평범한 이름입니다(아래 둘째 화면 — 3 을 찍습니다). 2024 에디션에서는 예약어입니다. 오류는 gen 을 쓴 2번 줄과 3번 줄에 하나씩 납니다.

옮기는 일은 도구가 돕는다 — 첫 오류의 첫 줄은 "식별자가 올 자리에 예약어 gen 이 왔다" 이고, 그 help: 의 r#gen 은 try 때 본 날 식별자입니다. 2024 발표문은 많은 경우 cargo fix 가 필요한 수정을 자동으로 해 준다고 적습니다.

안전 함수였던 set_var 가 unsafe 로 — E0133

환경 변수를 고치는 std::env::set_var 는 표준 라이브러리가 처음에 안전한 함수로 정의했지만, 나중에 그것이 옳지 않다고 판단됐습니다. 여러 스레드가 도는 프로그램에서 부르면 안전하지 않을 수 있기 때문입니다. 2021 에디션에서는 그대로 부를 수 있지만(아래 둘째 화면 — Ok("rust") 를 찍습니다), 2024 에디션은 unsafe 블록을 요구합니다.

읽는 법 — 오류 첫 줄은 "unsafe 함수 set_var 를 부르는 것은 unsafe 이고 unsafe 블록이 필요하다" 입니다. 밑줄은 2번 줄의 호출 전체이고, = note: 는 정의되지 않은 동작을 피하는 법을 함수의 문서에서 찾으라는 안내입니다. unsafe 는 "이 호출이 안전한지는 컴파일러가 아니라 내가 책임진다" 는 표시입니다(16부). 에디션 안내서는 cargo fix --edition 이 이런 호출을 unsafe 블록으로 감싸 주지만 , 제대로 쓰였는지 살피는 일은 여전히 사람의 몫이라고 적습니다.

Q. 2015 에디션으로 쓴 라이브러리를 2024 에디션 프로그램에서 쓰려면, 라이브러리를 먼저 2024 로 옮겨야 할까요?

NLL — 빌림 검사기의 두 번째 판

빌림은 값을 넘겨받지 않고 잠시 가리켜 쓰는 것이고, 빌림 검사기(borrow checker)는 빌림들이 서로 부딪히지 않는지 보는 컴파일러의 한 부분입니다(6부 3장). 처음의 검사기는 빌림이 그 변수의 스코프가 끝날 때까지 — 다시 쓰지 않더라도 — 이어진다고 봤습니다. Rust 팀은 NLL(non-lexical lifetimes)을 빌림 검사기의 두 번째 판이라고 부릅니다.

  • 옛 규칙대로라면 3번 줄에서 빌린 first 가 main 끝까지 이어져, 벡터를 고치는 5번 줄과 부딪힙니다. 2018 발표문이 "전에는 거절하던 올바른 코드" 로 든 예도 이런 꼴입니다. 지금 규칙은 6부에서 "빌림은 마지막으로 쓴 곳에서 끝난다" 로 배웁니다.
  • 처음에는 2018 에디션 코드에만 켜졌고 , 2015 에디션 코드는 옛 검사기와 새 검사기를 함께 돌려 견주는 "이행 모드" 였습니다.
  • 에 2015 에디션에도 켜졌고 , 부터는 모든 Rust 코드를 NLL 로 검사합니다.

async / await — 멈췄다가 이어 가는 함수

에 async–await 문법이 안정판에 들어왔습니다. 발표문의 설명으로는, 잠시 "멈추고" 런타임에 제어를 돌려준 뒤 멈춘 곳에서 다시 이어 가는 함수를 쓰는 방법입니다(16부). 바탕이 된 "비용 없는 퓨처(zero-cost futures)" 의 핵심 생각은 2016년에 처음 제안됐다고 합니다.

  • 키워드 async 와 await 는 2018 에디션에서 더해졌습니다. 4장에서 본 let async = 1; 이 이 키워드 이야기였습니다.
  • 발표문은 이 첫 판을 "최소한으로 쓸 만한 제품(MVP)" 이라 부르고, 한동안 다듬고 넓혀 가겠다고 했습니다.
  • 발표문이 꼽는 런타임은 tokio, async-std 같은 바깥 프로젝트들로, 새 문법 지원을 더하는 중이라고 했습니다. 2장에서 본 대로 언어에는 런타임이 들어 있지 않습니다.
이 책에서는 맛보기만 — 표준 라이브러리만으로 퓨처 하나를 끝까지 돌려 봅니다 (16부).

const 제네릭 — 배열 길이를 제네릭 인자로

배열 타입 [T; N] 의 N 은 타입이 아니라 값(길이)입니다. 예전에는 "어떤 길이의 배열이든" 을 한 번에 적을 방법이 없어서 , 오랫동안 표준 라이브러리의 배열 메서드조차 길이 32 까지만 됐습니다. 그 제한은 에 풀렸고 , 부터는 우리가 쓰는 함수와 타입도 상수 값을 제네릭 인자로 받을 수 있습니다.

읽는 법 — sum 하나가 11번 줄의 길이 3 인 배열도, 12번 줄의 길이 40 인 배열도 받아 6 과 400 을 찍습니다. 2번 줄의 <const N: usize> 가 "N 은 타입이 아니라 usize 값" 이라는 선언입니다. const 제네릭은 10부에서 다시 봅니다.

let-else 와 GATs — 같은 날 들어온 작은 것과 큰 것

는 작은 문법 let … else 와 함께, RFC 가 열린 지 여섯 해 반이 넘어 안정화된 제네릭 연관 타입(GATs) 을 실었습니다. let 패턴 = 식 else { … } 는 식이 패턴에 맞지 않으면 else 블록에서 빠져나가는 문법입니다.

GATs — 트레이트의 연관 타입에 제네릭을 달 수 있게 한 것으로 , 19부에서 봅니다. 발표문은 async 나 const 제네릭처럼 GATs 도 첫 안정화에는 제한이 있고 앞으로 풀어 갈 것이라고 적습니다. let … else 는 7부에서 다시 봅니다.

트레이트 안의 async fn

async fn 이 들어온 뒤에도 한동안 트레이트 안에는 쓸 수 없었습니다. 가 그것을 받기 시작했습니다. 발표문은 그러면서도 많은 사용자에게 필요한 중요한 기능이 아직 빠져 있다고 적었습니다.

async fn→ 트레이트 안에서도→ 2024 에디션의 프렐류드에 Future
Rust 가 기능을 내는 방식 — async, const 제네릭, GATs, 트레이트 안의 async fn 의 발표문이 같은 말을 합니다. 먼저 쓸 만한 최소한을 안정화하고, 빈 곳은 뒤의 릴리스에서 메운다는 것입니다. 그래서 "이 문법은 몇 버전부터" 가 중요하고, 이 책은 그것을 0부에서 본 배지로 표시합니다.

퀴즈 — 처음부터 다 갖춰서 나왔을까

Q. async–await 문법이 안정판에 들어왔을 때, 발표문은 그 첫 판을 무엇이라고 불렀을까요? 이 장에서 본 다른 기능 둘의 발표문은 무엇이라고 적었을까요?

A. "최소한으로 쓸 만한 제품(MVP)" 이라 부르고, 한동안 다듬고 넓혀 가겠다고 했습니다(async / await). GATs 의 발표문은 첫 안정화에는 제한이 있고 앞으로 풀어 갈 것이라고 적었고(let-else 와 GATs) , 트레이트 안의 async fn 의 발표문은 많은 사용자에게 필요한 중요한 기능이 아직 빠져 있다고 적었습니다(트레이트 안의 async fn). 그래서 "이 문법은 몇 버전부터" 가 중요하고, 이 책은 그것을 배지로 표시합니다.

모질라의 감원과 홀로서기

Rust 코어 팀의 글에 따르면 Rust 는 2015년 1.0 과 함께 프로젝트의 방향과 운영을 모질라 조직에서 독립시켰고 , 그 뒤로도 모질라는 두드러진 재정적·법적 후원자였습니다. 2020년 8월 11일, 모질라는 약 250명을 내보내는 구조 조정을 발표합니다. Rust 프로젝트와 커뮤니티에서 활동하던 사람들이 그 안에 있었습니다.

일주일 뒤 — Rust 코어 팀과 모질라는 "Rust 의 미래를 위한 기초를 놓는다" 는 글에서 Rust 재단을 만들 계획을 알렸습니다. 독립된 재단을 검토하기 시작한 것은 그 전 해였다고 글은 적습니다.

Rust 재단이 세워졌다

2021년, 큰 기술 회사들이 돈을 내어 비영리 Rust 재단(Rust Foundation)을 세웠습니다. 자원해서 일하는 개발자들을 받치기 위해서입니다.

  • 계획을 알린 글이 적은 재단의 첫 과제 — Rust · Cargo · crates.io 의 상표와 도메인 이름을 넘겨받고, 거기 드는 비용을 책임진다.
  • 기사가 전하는 재단의 일 — Rust 의 주요 기능을 맡아 일하려는 개발자에게 주는 지원금, 형편이 어려워진 기여자를 위한 지원금, Rust 의 코드를 올려 두는 서버의 비용.

퀴즈 — 버린 것과 지킨 것

Q. 1.0 전의 Rust 에 있다가 사라진 것 셋은 무엇이고, 그 자리를 지금은 무엇이 맡고 있을까요?

A. ① 기호 포인터 ~T → 라이브러리 타입 Box<T>. ② 가비지 컬렉터를 붙이려던 @T 와 Gc<T> → 지금은 GC 없이 소유권으로, 여럿이 함께 가질 값은 Rc<T> 로. ③ 녹색 스레드와 런타임 → OS 스레드. 그 밖에 int·uint(→ isize·usize), fail!(→ panic!), 타입 상태도 있습니다. 모두 2장에서 봤습니다.
