11부

수명

매달린 참조를 막는 장치 · 'a 표기 · 생략 규칙 · 구조체와 수명 · 'static

이 부에서 할 일

참조는 남의 값을 잠깐 빌린 것입니다(6부). 그렇다면 그 값이 사라진 뒤에 참조를 쓰면 어떻게 될까요? Rust 는 그런 코드를 컴파일하지 않습니다. 그 검사에 쓰이는 개념이 수명(lifetime)입니다.

  • 1장 — 왜 수명인가: 매달린 참조, 그리고 컴파일러가 스스로 알 수 없는 경우
  • 2장 — 표기 'a: 무엇을 약속하는 글자인가
  • 3장 — 생략 규칙: 대부분의 함수에 표기가 없는 까닭
  • 4장 — 참조를 가진 구조체
  • 5장 — 'static, 그리고 수명 오류를 푸는 길
먼저 알아 둘 것 — 수명 표기는 값이 사는 기간을 바꾸지 않습니다. 이미 정해져 있는 관계를 컴파일러에게 설명할 뿐입니다.

1장

왜 수명인가

매달린 참조 · 값보다 오래 사는 참조는 없다 · 컴파일러가 물어볼 때

사라진 값을 가리키는 참조 — E0597

안쪽 블록의 x 를 빌려 바깥의 r 에 담았습니다. 블록이 끝나면 x 는 사라지는데 r 은 남습니다. 이렇게 사라진 값을 가리키게 된 참조를 매달린 참조(dangling reference)라 부릅니다.

읽는 법 — x 를 선언한 자리(4번 줄)에 이어 세 자리를 짚습니다. 어디서 빌렸고(5번 줄), 어디서 값이 사라졌고(6번 줄), 그 뒤 어디서 참조를 썼는지(7번 줄). "빌린 값이 충분히 오래 살지 못한다".

값이 참조보다 오래 살면 된다

규칙은 하나입니다. 참조는 자기가 가리키는 값보다 오래 살 수 없다. 값을 바깥 블록으로 옮기면 조건이 채워집니다.

수명(lifetime) — 참조가 유효한 구간을 가리키는 말입니다. 위에서 r 의 수명은 x 가 살아 있는 구간 안에 들어 있습니다.

수명을 눈으로 보면

앞의 두 예제를 구간으로 그리면 이렇습니다. 세로 막대 둘 가운데 왼쪽이 참조 r 의 구간, 오른쪽이 값 x 의 구간입니다. r 을 쓰는 자리에 x 의 막대가 없으면 오류입니다.

틀린 쪽 (dangle_scope.rs)       맞는 쪽 (dangle_fix.rs)

r 선언  --+                     x 선언  -----+
x 선언  --|--+                  r 선언  --+  |
r = &x    |  |  x 의 구간       r = &x    |  |  x 의 구간
x 끝    --|--+                  r 사용    |  |
r 사용    |  <-- x 가 없다      r 끝    --+  |
r 끝    --+                     x 끝    -----+
대부분은 컴파일러가 혼자 본다 — 한 함수 안에서는 이 구간들을 컴파일러가 전부 계산합니다. 우리가 적을 것이 없습니다.

지역 변수의 참조를 돌려주려 하면 — E0106

함수가 끝나면 그 안의 지역 변수는 사라집니다. 그것을 가리키는 참조를 돌려주면 받는 쪽은 사라진 값을 가리키게 됩니다.

읽는 법 — "반환 타입에 빌린 값이 있는데, 빌려 올 곳이 없다". 인자가 하나도 없으니 돌려줄 참조가 가리킬 만한 것이 없다는 뜻입니다. 마지막 help: 가 답입니다. 그 앞의 help: 가 말하는 'static 은 드문 경우라고 컴파일러 스스로 적었습니다 — 5장에서 봅니다.

답은 값을 통째로 돌려주는 것

참조가 아니라 String 자체를 돌려줍니다. 소유권이 부른 쪽으로 넘어가므로 사라질 것이 없습니다.

수명 오류의 가장 흔한 해법 — "빌려주지 말고 줘 버린다". 이 부의 끝에서 다시 정리합니다.

컴파일러가 물어볼 때 — E0106

두 문자열 가운데 긴 쪽을 돌려주는 함수입니다. 본문에는 잘못이 없습니다. 그런데 시그니처만 봐서는 돌려주는 참조가 a 에서 온 것인지 b 에서 온 것인지 알 수 없습니다.

왜 본문을 보지 않는가 — help: 의 말은 "시그니처가 a 에서 빌린 것인지 b 에서 빌린 것인지 말하지 않는다" 입니다. 컴파일러는 함수를 부르는 코드를 검사할 때 본문이 아니라 시그니처를 기준으로 삼습니다(2장의 약속보다 오래 쓰면에서 확인합니다). 그래서 필요한 정보는 시그니처에 적혀 있어야 합니다.

퀴즈 — 왜 수명인가

Q. fn make() -> &String { let s = String::from("hello"); &s } 는 왜 컴파일되지 않고, 어떻게 고칠까요?

A. 컴파일러는 반환 타입의 참조가 빌려 올 곳이 없다고 말합니다(E0106). 인자가 없으니 가리킬 것은 지역 변수 s 뿐인데, s 는 함수가 끝나면 사라집니다. 반환 타입을 String 으로 바꾸고 s 자체를 돌려줍니다 (값을 통째로 돌려주기).

2장

표기 'a

수명에 이름 붙이기 · 무엇을 약속하는가 · 표기는 수명을 늘리지 않는다

수명에 이름을 붙인다

컴파일러가 권한 대로 고칩니다. 작은따옴표로 시작하는 'a 가 수명의 이름입니다. 함수 이름 뒤 <'a> 에서 선언하고, & 바로 뒤에 붙여 씁니다.

읽는 법 — "a, b, 그리고 돌려주는 참조는 같은 수명 'a 를 갖는다". 이름은 보통 'a, 'b 처럼 짧게 짓습니다.

'a 가 약속하는 것

같은 'a 를 세 군데에 썼다는 것은 "돌려주는 참조는 a 와 b 가 둘 다 살아 있는 동안에만 유효하다" 는 약속입니다. 실제로는 둘 가운데 짧게 사는 쪽에 맞춰집니다.

출력 두 줄 — 첫 줄은 블록 안에서 찍은 winner, 둘째 줄은 블록 밖에서 찍은 x 입니다. y 가 사라진 뒤에는 결과를 쓰지 않았습니다.

약속보다 오래 쓰면 — E0597

결과를 y 가 사라진 뒤에 씁니다. 이번에 실제로 돌아오는 것은 x 쪽 ("apple")이지만, 컴파일러는 그것을 따지지 않습니다. 시그니처는 "y 일 수도 있다" 고 말하기 때문입니다.

보수적인 판단 — 실행하면 괜찮았을 코드를 막은 셈입니다. Rust 는 "어떤 입력에서도 안전하다" 를 증명할 수 있을 때만 통과시킵니다.

상관없는 참조에는 붙이지 않는다

이 함수는 늘 a 쪽을 돌려줍니다. 그러면 b 에는 'a 를 붙이지 않습니다. 결과는 a 에만 매이고, b 가 먼저 사라져도 괜찮습니다.

표기는 관계를 적는 것 — 어느 입력과 어느 출력이 이어져 있는지를 적습니다. 덜 묶을수록 부르는 쪽이 자유롭습니다.

시그니처와 본문이 어긋나면 — E0621

시그니처는 "결과는 a 에 매인다" 고 하는데 본문은 b 를 돌려주기도 합니다. 컴파일러는 본문이 시그니처의 약속을 지키는지도 검사합니다.

양쪽에서 조인다 — 부르는 쪽은 시그니처를 믿고, 본문은 시그니처를 지켜야 합니다. 그래서 둘을 따로 검사해도 전체가 안전합니다. help: 는 b 에도 'a 를 붙이라고 합니다. 그러면 앞에서 본 longest 와 같은 시그니처가 됩니다.

수명이 둘일 때

서로 상관없는 참조에는 다른 이름을 붙일 수 있습니다. first 에서 표기 없이 두었던 둘째 인자에 'b 라는 이름을 따로 붙이면 이런 모양입니다.

표기는 값을 오래 살게 해 주지 않는다 — E0515

1장에서 막혔던 make 에 수명 표기를 붙여 봅니다. 문법은 맞지만, s 가 함수 끝에서 사라진다는 사실은 그대로입니다. 이번에는 컴파일러가 본문을 짚습니다 — "지역 변수 s 의 참조는 돌려줄 수 없다"(6부에서 본 오류입니다).

수명 표기는 주문이 아니다 — 설명일 뿐입니다. 사실과 다른 설명을 적으면 컴파일러가 거절합니다.

표기법 정리

쓰는 곳모양
선언fn f<'a>(…) · struct S<'a> · impl<'a>
참조&'a T · &'a mut T
참조를 가진 타입Excerpt<'a>
프로그램 내내&'static str
이름 없이'_
타입 인자와 함께<'a, T> — 수명을 먼저

&'a mut T 를 뺀 나머지는 모두 이 부의 예제에 나옵니다. 구조체와 impl 의 선언, 그리고 아래 네 줄은 3~5장에서 봅니다.

퀴즈 — 표기 'a

Q. fn longest<'a>(a: &'a str, b: &'a str) -> &'a str 의 결과를, b 로 넘긴 값이 사라진 뒤에 쓸 수 있을까요? 실제로 돌아온 것이 a 쪽이라면요?

A. 쓸 수 없습니다. 실제로 무엇이 돌아왔는지와 상관없이, 시그니처가 결과를 두 입력 모두에 묶어 두었기 때문입니다(약속보다 오래 쓰면). 늘 a 만 돌려주는 함수라면 b 에서 'a 를 빼면 됩니다(상관없는 참조).

3장

생략 규칙

표기 없이도 되는 까닭 · 규칙 셋 · &self · '_

들어오는 참조가 하나면 적을 것이 없다

지금까지 참조를 받고 돌려주는 함수를 많이 썼지만 'a 는 없었습니다. 들어오는 참조가 하나뿐이면 나가는 참조가 어디서 왔는지는 뻔하기 때문입니다. 컴파일러가 표기를 채워 줍니다.

수명 생략(elision) — 수명이 없는 것이 아니라 적지 않은 것입니다. 모든 참조에는 수명이 있습니다. 본문의 split(' ').next() 는 첫 낱말을 Option 으로 꺼내는, 9부에서 본 모양입니다.

컴파일러가 채우는 규칙 셋

  1. 인자에서 생략한 수명마다 서로 다른 수명을 하나씩 준다.
  2. 인자에 쓰인 수명이 (적었든 생략했든) 딱 하나면, 생략한 나가는 수명은 모두 그 수명이다.
  3. 메서드라서 &self 나 &mut self 가 있으면, 생략한 나가는 수명은 모두 self 참조의 수명이다.
시그니처적용되는 규칙결과
fn first_word(text: &str) -> &str1, 2표기 없이 된다
fn headline(&self, prefix: &str) -> &str1, 3표기 없이 된다
fn longest(a: &str, b: &str) -> &str1 뿐정할 수 없다 → E0106
fn len(text: &str) -> usize1 뿐나가는 참조가 없으니 더 정할 것이 없다

세 규칙을 다 써도 정해지지 않으면 컴파일러는 추측하지 않고 묻습니다 (1장의 E0106).

메서드에서는 self 를 따른다

들어오는 참조가 둘(&self 와 prefix)이지만 표기가 필요 없습니다. 셋째 규칙이 나가는 참조를 self 에 묶습니다. 메서드가 대개 자기 필드를 빌려 주기 때문입니다.

규칙이 짐작한 것과 다르면

셋째 규칙은 짐작일 뿐입니다. 이 메서드는 prefix 를 돌려주기도 하는데, 규칙은 결과가 self 에서 온다고 채웠습니다. 본문이 그 약속을 어깁니다.

컴파일러가 붙여 준 이름 — 표기가 없어서 두 수명을 '1, '2 라고 부릅니다. "'2(self)의 것을 돌려주기로 했는데 '1(prefix)의 것을 돌려준다". help: 가 권하는 모양은 prefix 와 결과만 묶습니다. 이 메서드는 self.title 도 돌려주므로, 다음 슬라이드에서는 self 까지 같은 'a 로 묶습니다.

둘 다 돌려줄 수 있으면 둘 다 묶는다

이 메서드의 결과는 self 의 것일 수도, prefix 일 수도 있습니다. 2장의 longest 와 같은 처지입니다. 둘에 같은 'a 를 붙입니다.

수명을 숨기면 컴파일러가 알려 준다

참조를 품은 타입(Words<'a>)을 돌려주면서 반환 타입에 수명을 적지 않았습니다. 컴파일은 되지만 경고가 납니다 — 매개변수 쪽에서는 수명이 생략됐고 반환 타입에서는 아예 숨었다고 두 자리를 짚습니다.

읽는 법 — 6번 줄의 &str 과 Words 에 같은 수명이 걸려 있는데 적는 방식이 서로 달라 헷갈린다는 경고입니다. help: 가 권하는 것이 다음 슬라이드의 '_ 입니다.

'_ — 있다는 것만 알린다

앞 슬라이드의 경고가 권한 대로 고칩니다. '_ 는 이름은 안 짓되 "여기 수명이 있다" 를 드러냅니다. 반환 타입만 봐도 Words 가 무언가를 빌리고 있다는 것이 보입니다.

퀴즈 — 생략 규칙

Q. fn first_word(text: &str) -> &str 에는 왜 수명 표기가 없어도 될까요? 그리고 fn longest(a: &str, b: &str) -> &str 는 왜 안 될까요?

A. 앞의 것은 들어오는 참조가 하나라 나가는 참조의 수명이 그것으로 정해집니다(규칙 2). 뒤의 것은 들어오는 수명이 둘이고 self 도 없어서 어느 쪽인지 정할 규칙이 없습니다 (규칙 셋).

4장

참조를 가진 구조체

필드가 참조면 수명이 필요하다 · 구조체는 빌린 값보다 오래 못 산다 · impl<'a>

참조를 필드로 두려면 — E0106

구조체가 참조를 품으면, 그 구조체도 "무언가를 빌리고 있는 값" 이 됩니다. 얼마나 오래 빌리는지를 타입에 적어야 합니다. 구조체에는 생략 규칙이 없습니다.

구조체에 수명 붙이기

컴파일러가 권한 대로 <'a> 를 붙입니다. 이제 Excerpt 는 "어떤 글의 한 조각을 빌려 들고 있는 값" 입니다.

읽는 법 — Excerpt<'a> 는 "수명 'a 동안 유효한 무언가를 빌린 Excerpt" 입니다. 'a 가 끝나면 이 값도 쓸 수 없습니다.

구조체는 빌린 값보다 오래 살 수 없다 — E0597

1장의 매달린 참조와 같은 일이 구조체를 사이에 두고 일어납니다. novel 이 사라진 뒤에 e 를 쓰면, e 안의 참조는 사라진 글을 가리킵니다.

impl 에도 적는다

메서드를 붙일 때는 impl<'a> Excerpt<'a> 라고 씁니다. 그러면 메서드 안에서 'a 를 쓸 수 있습니다 — 결과를 self 가 아니라 원래 글에 맬 수 있습니다.

-> &'a str 라고 적은 까닭 — 'a 를 적으면 결과가 novel 에 묶여 e 보다 오래 갑니다. 생략하면 어떻게 되는지는 다음 슬라이드에서 봅니다. 첫 줄의 16 은 글자 수가 아니라 바이트 수입니다(8부).

'a 를 빼면 결과는 self 에 묶인다 — E0597

같은 코드에서 text 의 반환 타입만 &str 로 바꿨습니다. 3장의 셋째 규칙이 결과를 self, 곧 e 에 묶습니다.

읽는 법 — 오래 살지 못한다고 짚인 것은 novel 이 아니라 e 입니다. e 를 빌렸고(17번 줄), e 가 사라졌고(18번 줄), 그 뒤에 결과를 썼습니다(19번 줄).

빌리지 않고 갖는 구조체

필드를 &str 대신 String 으로 하면 구조체가 글을 스스로 갖습니다. 수명 표기가 사라지고, 원래 글이 없어져도 상관없습니다. 대가는 복사 한 번입니다.

빌릴까, 가질까

빌리는 구조체 S<'a>갖는 구조체
필드&'a str, &'a [T]String, Vec<T>
만드는 비용없음(가리키기만)복사 한 번
사는 기간원본이 살아 있는 동안만자유
함수에서 만들어 돌려주기원본이 바깥에 있을 때만언제나
어울리는 곳잠깐 쓰고 버리는 보기(view), 파서오래 들고 다니는 자료
처음에는 갖는 쪽으로 — 수명이 붙은 구조체는 impl 에도, 그것을 돌려주는 함수의 시그니처('_)에도 수명 표기가 따라다닙니다. 복사가 정말 문제가 될 때 빌리는 쪽으로 바꿔도 늦지 않습니다.

퀴즈 — 구조체와 수명

Q. struct Excerpt<'a> { part: &'a str } 의 값을 함수 안에서 만든 String 을 빌려 만든 다음, 그 함수의 반환값으로 내보낼 수 있을까요?

A. 없습니다. 그 String 은 함수가 끝날 때 사라지고, Excerpt 는 빌린 값보다 오래 살 수 없습니다(블록으로 본 같은 일 — 구조체는 빌린 값보다 오래 살 수 없다). 필드를 String 으로 바꿔 스스로 갖게 하면 됩니다(갖는 구조체).

5장

'static, 그리고 푸는 길

프로그램 내내 사는 것 · T: 'static · 수명 오류를 만났을 때

'static — 프로그램이 끝날 때까지

문자열 리터럴은 실행 파일 안에 박혀 있어서 프로그램 내내 사라지지 않습니다. 그 참조의 수명이 'static 입니다. static 으로 만든 전역 값도 마찬가지입니다.

그래서 "글자" 의 타입을 다 쓰면 &'static str 입니다.

'static 을 요구하는 자리에 지역 변수를 넘기면 — E0597

&'static str 을 받는 함수는 "프로그램 내내 유효한 참조만 받겠다" 는 뜻입니다. 지역 변수의 참조는 그렇지 못합니다. 컴파일러의 말로는 "인자가 s 를 'static 동안 빌리기를 요구한다"(8번 줄)인데, s 는 9번 줄에서 사라집니다.

1장에서 본 권고를 조심하기 — 1장의 E0106 에서 컴파일러는 'static 을 붙이는 길도 help: 로 보여 주었습니다(드문 경우라는 말과 함께). 'static 은 이 슬라이드처럼 프로그램 내내 사는 값만 통과시키는 조건이라, 지역 변수에서 나온 참조에는 맞지 않습니다. 값을 돌려주는 쪽이 보통 맞는 답입니다.

T: 'static — 잠깐 빌린 것이 들어 있지 않다

제네릭 타입에 붙은 T: 'static 은 "프로그램 내내 살아야 한다" 가 아닙니다. "T 안에 잠깐 빌린 참조가 없다" 는 뜻입니다. 스스로 가진 값은 모두 통과합니다.

빌린 참조는 T: 'static 을 못 지킨다 — E0597

지역 변수의 참조 &s 는 s 가 살아 있는 동안만 유효합니다. 그래서 T: 'static 자리에 넘길 수 없습니다. 끝의 note: 는 그 조건이 어디서 왔는지(3번 줄의 'static)를 짚어 줍니다.

어디서 만나나 — 새 스레드에 넘기는 값이 이 조건을 요구합니다. 스레드가 언제 끝날지 모르기 때문입니다(15부).

수명과 제네릭 타입을 함께

수명 인자와 타입 인자를 같이 쓸 때는 수명을 먼저 적습니다. 어떤 타입의 값이든 빌려 들 수 있는 구조체입니다.

증상먼저 해 볼 것

퀴즈 — 'static

Q. fn show<T: Display + 'static>(value: T) 에 String::from("abc") 를 넘길 수 있을까요? String 은 프로그램 내내 살지 않는데도요?

A. 넘길 수 있습니다. T: 'static 은 "영원히 산다" 가 아니라 "잠깐 빌린 참조를 품고 있지 않다" 는 뜻이고, String 은 자기 글자를 스스로 갖습니다 (T: 'static). 넘길 수 없는 것은 지역 변수의 참조 &s 입니다.
