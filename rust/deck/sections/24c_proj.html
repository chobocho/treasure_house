이 프로젝트가 쓰는 것

1장과 2장은 줄을 세고 줄을 골랐습니다. 줄에 적힌 것이 무슨 뜻인지는 따지지 않았습니다. 이 장의 calc 는 2 + 3 * 4 같은 줄을 읽어 그 값을 찍습니다. 그러려면 줄을 뜻이 있는 낱개로 끊어야 합니다. 이 장은 그 낱개를 토큰(token)이라고 부릅니다. 21부에서 컴파일러가 소스를 끊어 읽는 낱개를 부른 말과 같은 말이고, 여기서는 이 계산기가 받는 수 · 연산자 · 괄호를 가리킵니다. 이 장에서 식이라고 하면 Rust 의 식이 아니라 이 계산기가 받는 수식입니다. 새로 하는 일은 넷입니다 — 줄을 토큰으로 나누기, 토큰을 읽어 식의 나무를 짓기, 나무를 따라 계산하기, 그리고 줄의 어디가 틀렸는지를 담는 오류 타입입니다. 첫 표는 그러느라 다시 쓰는 것과 그것을 배운 슬라이드이고, 둘째 표는 앞의 두 장에서 그대로 가져온 것입니다.

두 표 모두 왼쪽이 이 장의 코드에 나오는 것입니다. 첫 표의 오른쪽은 그것을 처음 설명한 슬라이드이고, 둘째 표의 오른쪽은 1장이나 2장에서 그것을 만든 슬라이드입니다. 이 장은 오른쪽의 설명을 되풀이하지 않고, 달라지는 곳만 말합니다.

다 만들면 이렇게 돈다

마지막 단계의 패키지를 빌드해 돌린 화면입니다. 여기까지 가는 길을 아홉 단계로 나눠 걷습니다. 화면은 앞의 두 장처럼 target/debug/ 의 실행 파일을 직접 부릅니다. 입력 파일 data/sums.txt 는 한 줄에 식 하나씩 아홉 줄이고, 넷째 줄은 비었습니다. cat 으로 먼저 봅니다.

읽는 법 — cargo build -q 는 아무것도 찍지 않았습니다. 이 장의 글에서는 ./target/debug/calc 를 calc 로 줄여 적습니다. 파일을 표준 입력에 이은 실행은 줄마다 답을 냈습니다. 앞의 세 줄은 14 · 20 · 3 입니다. 곱셈을 먼저 했고, 괄호 안을 먼저 했고, 뺄셈은 왼쪽부터 했습니다. 빈 줄에는 아무것도 찍지 않았고, -7 / 2 는 -3 입니다. 나머지 네 줄은 값을 내지 못한 줄입니다. 줄마다 알림이 석 줄씩 나왔습니다. 까닭과 (자리 N), 받은 줄 그대로, 그리고 틀린 곳 아래에 ^ 를 놓은 줄입니다. 자리는 줄의 처음부터 0 으로 시작해 센 번호이고, 1단계에서 정합니다. 1 + 2 / 0 에서는 / 아래에, 닫히지 않은 괄호에서는 여는 괄호 아래에, 한글 가 가 낀 줄에서는 그 글자 아래에, 넘친 덧셈에서는 + 아래에 ^ 가 있습니다. 틀린 줄이 있어도 끝까지 갔고, 종료 코드는 1 입니다. 그다음 실행은 식을 인자로 주었습니다. 인자 하나가 한 줄이고, 답은 14 와 -20 입니다.
이 책의 계산기입니다 — 무엇을 수로 읽고, 어떤 연산을 어떤 차례로 하고, 무엇을 오류로 치고, 알림을 어떤 모양으로 찍을지는 이 장이 정합니다. 화면의 알림은 모두 이 프로그램이 만든 글입니다. 다른 계산기가 같은 줄에 무엇을 내는지는 말하지 않습니다.

아홉 단계 — 단계마다 컴파일되고 돈다

앞의 두 장과 같은 방식입니다. 단계 하나가 예제 디렉터리 하나이고, 뒤 단계는 앞 단계의 파일을 그대로 두고 파일이나 줄을 더하거나 적어 둔 줄만 바꾼 사본입니다. 슬라이드가 싣지도 말하지도 않은 줄은 앞 단계의 것 그대로입니다. 이번에는 소스가 한 파일이 아닙니다. 13부에서 본 대로 모듈을 파일로 나눠, 하는 일마다 파일 하나를 둡니다. 그래서 코드 상자의 꼬리표에는 단계의 디렉터리 이름과 함께 파일 이름을 적습니다.

줄 하나가 값이 되기까지 — 토큰, 나무, 값

줄 하나는 세 번 모양을 바꿉니다. 글이 토큰의 목록이 되고, 목록이 나무가 되고, 나무가 수 하나가 됩니다. 일마다 함수 하나이고, 그 함수가 든 파일도 하나씩입니다.

글→ 토큰의 목록→ 식의 나무→ 값
  • 토큰으로 나누기 — 글자를 앞에서부터 읽어 수 · 연산자 · 괄호로 끊습니다. 12 는 글자 둘이지만 토큰 하나입니다. 이 일을 하는 tokenize 가 1단계입니다.
  • 식의 나무 짓기 — 토큰을 차례로 읽어 "무엇과 무엇을 먼저 셈하는가" 가 드러나는 나무를 만듭니다. 14부의 수식 나무와 같은 것이고, 거기서는 손으로 지은 나무를 이번에는 parse 가 짓습니다. 2단계부터 4단계까지입니다.
  • 계산하기 — 나무를 따라 내려가며 값을 구합니다. 14부의 그 슬라이드에 있던 eval 을, 넘침과 0 으로 나누기를 오류로 돌려주게 고쳐 씁니다. 5단계입니다.
세 일이 하나의 오류 타입을 쓴다 — 어느 일에서든 틀린 곳을 만나면 "무엇이, 줄의 몇 번째 자리에서" 를 담은 값 하나를 돌려줍니다. 그래서 토큰이 저마다 제 자리를 달고 다닙니다. 그 오류 타입부터 만듭니다.

오류 타입부터 만든다 — 종류 하나와 자리 하나

1단계의 파일은 다섯입니다. Cargo.toml, 뿌리 파일 src/lib.rs, 오류 타입이 든 src/error.rs, 토큰을 만드는 src/token.rs, 그리고 본보기 프로그램 하나입니다. 먼저 세 일이 함께 쓸 오류 타입입니다. 9부에서는 오류의 경우마다 변형 하나를 두고 변형이 데이터를 가졌습니다. 여기서는 모든 오류가 똑같이 자리 하나를 가져야 하므로, 종류만 열거형으로 두고 자리는 구조체의 필드로 뺍니다.

읽는 법 — Cargo.toml 은 패키지 이름이 calc 인 것만 1장의 그 파일과 다르고, 마지막 단계까지 바뀌지 않습니다. lib.rs 의 1번과 2번 줄은 13부에서 본 mod 이름; 입니다. 내용은 find 가 보인 src/error.rs 와 src/token.rs 에 있습니다. 4번과 5번 줄의 pub use 는 그 안의 이름을 크레이트의 뿌리에 다시 내놓습니다. 그래서 바깥에서는 calc::tokenize 라고만 적습니다. 본보기 프로그램이 그렇게 부릅니다. error.rs 의 Kind 는 데이터가 없는 변형뿐인 열거형이고, 이 단계에는 토큰을 만들다 날 수 있는 둘만 있습니다. 변형은 그것을 쓰는 단계에서 하나씩 늡니다. CalcError 는 그 종류와 자리 pos 를 묶습니다. 17번부터 21번 줄까지는 7부에서 본 연관 함수 new 입니다.
이 프로그램의 정의 — 자리 — 자리(position)는 받은 줄의 처음부터 0 으로 시작해 센 바이트 번호입니다. 글자 번호도 화면의 칸 번호도 아닙니다. 그래도 되는 까닭은 자리 앞에는 ASCII 만 있다에서 소스와 시험으로 봅니다. error.rs 2번 줄의 Copy 는 종류를 값처럼 넘기려고, 2번과 11번 줄의 PartialEq 와 Debug 는 시험이 assert_eq! 로 오류를 통째로 견주려고 붙였습니다. 9부의 From 예제에도 CalcError 라는 이름이 있었는데, 이름만 같은 다른 타입입니다.

tokenize — 글자를 하나씩 꺼내고, 숫자가 이어지는지는 엿본다

src/token.rs 입니다. 열거형 Token 의 변형은 여덟이고, 데이터를 가진 것은 수뿐입니다. tokenize 는 줄을 받아 토큰과 그 자리의 짝을 벡터로 돌려줍니다. 8부에서 본 char_indices 가 글자마다 바이트 자리를 함께 주므로, 자리는 따로 세지 않습니다.

읽는 법 — 줄 번호는 두 상자 모두 token.rs 의 것입니다. 1번 줄의 crate:: 는 같은 크레이트의 error 모듈에서 두 이름을 끌어옵니다. Token 의 마지막 변형 End 는 글자가 아니라 줄이 끝난 자리를 나타냅니다. 25번 줄은 char_indices 에 12부의 peekable 을 붙였습니다. 26번 줄의 while let 이 자리와 글자를 하나씩 꺼냅니다. 27번 줄은 그 글자에 3부의 to_digit(10) 을 묻습니다. Some 이면 수의 첫 숫자입니다. 30번 줄이 다음 글자를 꺼내지 않고 엿보고, 31번 줄의 let … else 가 숫자가 아니면 안쪽 반복을 나옵니다. 엿보기만 했으므로 그 글자는 바깥 반복의 다음 차례에 그대로 나옵니다. 숫자였다면 34번 줄이 넘어가고, 35번 줄이 읽던 값 뒤에 붙입니다. 40번 줄부터는 숫자가 아닌 글자입니다. 42번 줄은 빈칸과 탭을 버리고 다음 글자로 갑니다. 43번부터 48번 줄까지가 한 글자짜리 토큰 여섯이고, 49번 줄의 나머지 갈래는 UnknownChar 를 들고 돌아갑니다. 54번 줄이 토큰을 그 첫 글자의 자리와 함께 넣습니다. 57번 줄은 맨 끝에 End 를 줄의 길이와 함께 넣습니다.
17번부터 19번 줄까지 — push_digit — 읽던 값에 10 을 곱하고 새 숫자를 더합니다. 3부에서 본 대로 checked_ 로 시작하는 메서드는 넘치면 None 을 주고, 그 슬라이드가 표 아래에 적은 대로 곱셈에도 이름의 뒤만 바꾼 것이 있습니다. 가운데의 ? 는 9부에서 본 Option 의 ? 입니다. i64::from 은 3부의 잃을 것이 없는 변환입니다. 36번 줄의 ok_or 가 그 None 을 TooBig 오류로 바꾸고, ? 가 들고 돌아갑니다. 그 오류의 자리는 넘친 숫자가 아니라 26번 줄에서 받은 pos, 곧 수의 첫 숫자입니다.

토큰마다 제 자리가 붙어 나온다 — 본보기 tokens 로 본다

라이브러리뿐이라 아직 돌릴 실행 파일이 없습니다. 23부에서 본 examples/ 에 받은 인자를 tokenize 에 넘겨 결과를 {:?} 로 찍는 프로그램을 둡니다. Token 과 CalcError 에 Debug 를 붙여 두었으므로 그대로 찍힙니다.

읽는 법 — 명령의 -- 는 23부에서 본 대로 그 뒤가 프로그램의 인자라는 표시입니다. 인자마다 두 줄이 나옵니다. 6번 줄이 받은 글을 따옴표와 함께 찍고, 7번 줄이 tokenize 의 결과를 찍습니다. 12 + 3 은 토큰 셋과 End 입니다. 글자 둘인 12 가 Num(12) 하나가 됐고 자리는 첫 글자의 0 입니다. + 는 3, 3 은 5 이고, 빈칸은 토큰이 되지 않았습니다. 끝의 (End, 6) 의 6 은 줄의 길이입니다. 붙여 쓴 (4-5) 와 6*7/8 도 글자마다 따로 토큰이 됐습니다. 세 줄에 수와 연산자 넷, 괄호 둘이 다 나왔습니다. 빈칸 하나뿐인 인자는 (End, 1) 하나입니다. 마지막 인자에서는 Ok 가 아니라 Err 입니다. 종류는 UnknownChar, 자리는 가 가 있는 4 입니다. 그 앞에서 읽은 1 과 + 는 돌려주지 않습니다.

문법 — 이 계산기가 받는 식을 네 줄로 적는다

토큰이 어떤 차례로 놓여야 식인지를 먼저 적어 둡니다. 그런 규칙을 문법(grammar)이라고 합니다. 이 계산기의 문법은 네 줄이고, 이 장이 정한 것입니다. 2단계부터 4단계까지의 parse 는 위의 세 줄을 한 줄씩 코드로 옮깁니다.

식   = 항   { ("+" | "-") 항 }
항   = 인수 { ("*" | "/") 인수 }
인수 = 수 | "-" 인수 | "(" 식 ")"
수   = 숫자 { 숫자 }
  • 읽는 법 — = 의 왼쪽이 이름이고 오른쪽이 그것의 생김새입니다. 따옴표 안은 그 글자 그대로, | 는 "또는", 중괄호는 "0 번 이상 되풀이" 입니다.
  • 식(expression) — 항 하나, 또는 항들을 + 나 - 로 이은 것입니다. 항(term) 은 인수 하나, 또는 인수들을 * 나 / 로 이은 것입니다.
  • 인수(factor) — 수 하나이거나, 앞에 - 가 붙은 인수이거나, 괄호로 싼 식입니다. 함수에 넘기는 값을 뜻하는 인자(argument)와 다른 말입니다.
  • 수 — 숫자가 하나 이상 이어진 것입니다. 이 줄은 1단계의 tokenize 가 이미 맡았습니다.
재귀로 내려가며 읽기 — 문법의 줄마다 함수를 하나씩 둡니다. parse_expr 는 식을, parse_term 은 항을, parse_factor 는 인수를 읽습니다. 문법에서 식이 항으로, 항이 인수로 적혀 있듯이 함수도 그 차례로 아래 것을 부릅니다. 인수의 줄에는 인수와 식이 다시 나오므로, 4단계의 parse_factor 는 자기 자신과 parse_expr 를 부릅니다. 5부에서 본 재귀입니다. 문법의 줄을 따라 함수가 함수를 부르며 읽는 이 방식을 영어로는 recursive descent 라고 합니다. 한 단계에 한 줄씩 갑니다. 2단계는 식 = 인수 { ("+" | "-") 인수 } 와 인수 = 수 까지만 읽고, 3단계가 항의 줄을 끼우고, 4단계가 인수의 줄을 마저 채웁니다.

main 은 2장과 같은 짜임이다 — 처음 돌려 본다

같은 단계에 src/main.rs 와 입력 파일 data/sums.txt 가 생깁니다. main 은 2장의 main 에서 도구 이름과 주석만 바꾼 것이고, 이 파일도 마지막 단계까지 바뀌지 않습니다. 다 만들면 이렇게 돈다에서 본 입력을 이 단계의 실행 파일에 넣습니다.

앞의 두 장에서 말한 것 둘은 여기서도 그대로다 — 6번 줄은 1장에서 UTF-8 이 아닌 인자에 패닉한 env::args() 이고, 이 프로그램에서는 인자가 곧 식입니다. 14번 줄의 eprintln! 도 같아서, 표준 오류에 쓰지 못하는 경우는 이 장도 다루지 않습니다. 두 경우를 calc 로 돌린 화면은 이 장에 싣지 않았습니다.

값은 표준 출력으로, 알림은 표준 오류로 간다 — 인자로 준 식, 값이 없는 줄

앞 슬라이드의 화면에서는 값과 알림이 한데 섞여 나왔습니다. 1장에서 한 것처럼 한 길씩 버려 봅니다. 그다음 식을 인자로 주고, 값이 없는 줄이 낀 입력과 빈 입력을 줍니다.

읽는 법 — 2> /dev/null 을 붙인 실행에는 값 넷만 남았고, > /dev/null 을 붙인 실행에는 알림 넷만 남았습니다. 값은 out 으로, 알림은 err 로 갔습니다. 두 실행 모두 종료 코드는 1 입니다. 알림만 남은 화면에서도 어느 줄의 알림인지는 알 수 있습니다. 알림마다 받은 줄이 들어 있기 때문입니다. 인자 둘을 준 실행은 14 와 3 입니다. 10 / 3 의 몫에서 소수점 아래가 버려졌습니다. 오류가 없으니 종료 코드는 0 이라 화면에 표시가 없습니다. 그다음 입력은 네 줄입니다. 둘째 줄은 비었고, 셋째 줄은 빈칸과 탭뿐이고, 넷째 줄은 줄바꿈 없이 끝납니다. 찍힌 것은 2 와 4 둘이고 종료 코드는 0 입니다. 값이 없는 두 줄은 답도 알림도 내지 않았고, 줄바꿈 없이 끝난 마지막 줄도 한 줄로 읽혔습니다. < /dev/null 은 빈 입력입니다. 아무것도 찍지 않고 0 으로 끝났습니다.
마지막 실행 — 틀린 줄이 먼저다 — 입력의 첫 줄 1 + 는 끊긴 식이고 둘째 줄은 2 + 2 입니다. 화면에는 알림 석 줄이 먼저, 그 아래에 4 가 나왔습니다. 틀린 줄에서 멈추지 않고 다음 줄에 답했고, 한 화면에 섞인 값과 알림의 차례는 입력의 줄 차례입니다. 종료 코드는 1 입니다. 다만 두 길을 따로 받으면 값과 알림 사이의 앞뒤는 남지 않습니다.

글이 아닌 줄을 만나면 거기서 멈추고 2 로 끝난다 — 앞 줄의 답은 이미 나갔다

표준 입력이 올바른 UTF-8 이 아닐 수도 있습니다. 17부에서 본 대로 줄마다 읽으면 깨진 줄에서만 실패합니다. 먼저 줄 끝이 \r\n 인 입력을 주고, 그다음 둘째 줄에 UTF-8 이 될 수 없는 바이트 \377 을 넣은 입력을 줍니다.

읽는 법 — 첫 실행의 두 줄은 \r\n 으로 끝납니다. 첫 줄은 2 를 냈고, 둘째 줄은 닫히지 않은 괄호의 알림을 냈습니다. 1단계에서 CR 은 모르는 글자라고 정했는데 그 알림이 아닙니다. 표준 입력을 줄로 쪼갠 lines() 도 2장에서 본 글의 lines() 처럼 줄 끝의 \r\n 을 둘 다 뗐습니다. 알림에 다시 찍힌 줄도 2 * (3 에서 끝났습니다. 둘째 실행은 첫 줄의 답 2 를 찍은 다음 calc: stream did not contain valid UTF-8 한 줄을 내고 종료 코드 2 로 끝났습니다. 셋째 줄 2 + 2 의 답은 없습니다. 이 알림은 calc: 뒤에 자리도 받은 줄도 없는 한 줄입니다. run 이 쓰는 알림은 석 줄이므로, 소스에서 이 모양을 찍는 곳은 main 의 Err 갈래에 있는 eprintln! 입니다. 그 글은 17부에서 본, 이 툴체인의 표준 라이브러리가 주는 글입니다.

퀴즈 — 값과 알림을 미리 적어 보기

Q. ./target/debug/calc 를 calc 로 줄여 적습니다. 둘 다 마지막 단계의 calc 입니다. ① printf '2 - 3 - 4\n2 * -3 + 1\n7 / 2 * 2\n' | calc 는 표준 출력에 세 줄을 찍습니다. 차례로 얼마입니까? ② calc '(1 + 2' '1 + 2)' '4 / (2 - 2)' 는 인자 셋이 모두 틀린 식입니다. 인자마다 알림의 ^ 는 어느 글자 아래에 놓이고, 표준 출력에는 무엇이 나오며, 종료 코드는 몇입니까?

A. ① -5 · -5 · 6 입니다. 첫 줄은 왼쪽부터 묶여 -1 에서 4 를 뺍니다(묶이는 방향). 오른쪽부터였다면 3 입니다. 둘째 줄의 둘째 - 는 부호라서 2 에 -3 을 곱한 -6 에 1 을 더합니다(부호). 셋째 줄은 7 을 2 로 나눈 몫 3 에 2 를 곱합니다. 소수점 아래를 버렸으므로 7 로 돌아오지 않습니다(나눗셈). ② 첫 인자는 닫히지 않은 괄호라서 자리 0 의 여는 괄호 아래입니다(Unclosed). 둘째 인자는 1 + 2 까지가 식이고 닫는 괄호가 남아, 자리 5 의 그 괄호 아래입니다. 셋째 인자는 괄호 안이 0 이 되어 0 으로 나누기이고, 자리 2 의 / 아래입니다. 0 을 만든 (2 - 2) 가 아니라 나눗셈의 연산자를 짚습니다(연산자의 자리). 값을 낸 인자가 없으니 표준 출력은 비고, 종료 코드는 1 입니다. 2 가 아닙니다. 읽고 쓰는 일은 모두 됐습니다(종료 코드 셋). 두 명령은 마지막 단계 calc9_final 에서 모든 시험 다음에 돌렸습니다. 그 화면입니다.

더 해 볼 것

마지막 단계의 패키지를 복사해 놓고 고쳐 보는 과제입니다. 풀이는 싣지 않았습니다. 과제마다 손댈 파일과 함수를 적었습니다. 문법을 키우는 과제는 문법의 네 줄에서 어느 줄이 바뀌는지부터 적고, 그 줄을 읽는 함수를 고칩니다.

  • 나머지 % — token.rs 의 Token, expr.rs 의 Op, parse_term, apply 에 한 군데씩 더합니다. 컴파일러가 빠진 갈래를 짚어 주는 곳이 어디인지 봅니다. 음수의 나머지를 3부의 어느 쪽으로 정할지, 0 으로 나눈 나머지는 무엇인지를 시험에 먼저 적습니다.
  • 거듭제곱 — 이 과제에서는 오른쪽부터 묶기로 정합니다. 문법에 줄 하나를 인수와 항 사이에 끼우고, parse.rs 에 그 줄을 읽는 메서드를 더합니다. 왼쪽부터 묶는 loop 와 다른 모양이 필요합니다. 지수가 음수일 때와 값이 넘칠 때를 apply 에서 어떻게 할지도 정합니다. 2 ^ 3 ^ 2 의 나무를 먼저 손으로 그려 봅니다.
  • 더하기 부호 — 지금은 +3 이 오류입니다. parse_factor 에 갈래 하나를 더합니다. 나무에 마디를 남길지 말지를 정합니다.
  • 이름 붙인 값 — x = 3 같은 줄을 받아, 뒤의 줄에서 x 를 쓰게 합니다. 이름과 값을 담은 8부의 HashMap 을 run 이 줄 사이에 들고 다닙니다. 없는 이름을 썼을 때의 오류와 그 자리도 정합니다.
  • 한글 이름과 자리를 짚는 줄 — 앞 과제에서 이름에 한글을 받으면 자리 앞에 ASCII 만 있다는 것이 깨집니다. 자리를 바이트로 둘지 글자로 바꿀지, 폭이 두 칸인 글자 뒤에서 ^ 를 어디에 놓을지를 시험으로 먼저 적습니다.
  • 알림에 줄 번호 — 표준 오류만 따로 받았을 때 몇째 줄의 알림인지 보이게 합니다. run 의 두 반복문에서 17부의 enumerate 로 번호를 붙여 answer 에 넘기고, tests/golden/sums.err 가 어떻게 바뀌는지 봅니다.
  • 한 줄의 오류를 모두 알리기 — 지금은 처음 만난 하나만 알립니다. tokenize 가 모르는 글자를 만나도 멈추지 않고 모아 두게 하면 무엇을 돌려줘야 하는지부터 정합니다.
  • 깨진 줄을 건너뛰기 — 지금은 글이 아닌 줄에서 멈춥니다. run 의 line? 를 match 로 바꿔 알리고 다음 줄로 가게 합니다. 그때 종료 코드를 1 로 할지 2 로 할지 정합니다.
  • 알림에 찍는 줄 거르기 — report 는 받은 줄을 그대로 다시 찍습니다. 소스를 따라가면 NUL 바이트가 든 줄도, 가운데에 CR 이 든 줄도 그렇습니다. 화면에 찍기 곤란한 글자를 다른 글자로 바꿔 찍되, ^ 가 여전히 맞는 칸에 놓이게 합니다.
  • UTF-8 이 아닌 인자 — 1장의 같은 과제입니다. 이 프로그램에서는 인자가 식이라서, 글이 아닌 인자를 받았을 때 무엇을 알릴지도 정해야 합니다.
