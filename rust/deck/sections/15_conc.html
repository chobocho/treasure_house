동시성 기초

스레드 · move 와 범위 스레드 · 채널 · Mutex 와 Arc · Send 와 Sync

이 부에서 할 일

여러 스레드가 같은 데이터를 건드리다 생기는 버그(데이터 경쟁)는 찾기도 고치기도 어렵습니다. Rust 는 그것을 소유권과 타입으로 막습니다. 새 규칙을 배우는 것이 아니라, 6부의 규칙이 스레드 사이에서도 그대로 지켜지는 것을 봅니다.

  • 1장 — 스레드: 만들기, 기다리기, 값 넘기기(move), 빌려주기(범위 스레드)
  • 2장 — 채널: 스레드 사이에 값을 보내기
  • 3장 — 공유 상태: Mutex, Arc, 원자 타입
  • 4장 — Send 와 Sync, 한 번만 만드는 전역 값
이 부의 화면 — 스레드가 도는 순서는 실행마다 다릅니다. 예제는 모두 "결과가 순서에 기대지 않도록" 짰습니다. 기다린 뒤에 찍고, 모은 뒤에 정렬합니다. 실제 프로그램에서도 같은 요령을 씁니다.

1장

스레드

spawn 과 join · 결과 받기 · move · 범위 스레드 · 스레드의 패닉

spawn 으로 만들고 join 으로 기다린다

thread::spawn 에 클로저를 주면 운영 체제의 새 스레드에서 그것을 돌립니다. 돌려받은 손잡이의 join() 은 그 스레드가 끝날 때까지 기다립니다.

join 을 빼먹으면 — main 이 끝나는 순간 프로그램 전체가 끝납니다. 다른 스레드가 일을 마쳤든 아니든 상관없습니다.

스레드의 결과를 받는다

클로저의 값이 스레드의 결과입니다. join() 이 그것을 돌려줍니다.

unwrap() 이 붙는 까닭 — join() 은 Result 를 돌려줍니다. 그 스레드가 패닉했으면 Err 입니다(이 장의 끝).

스레드는 지역 변수를 빌릴 수 없다 — E0373

새 스레드는 자기를 만든 함수보다 오래 살 수도 있습니다. 그러면 빌려 간 지역 변수가 먼저 사라집니다. 컴파일러는 그 가능성만으로 거절합니다.

11부에서 본 것 — thread::spawn 은 넘겨받는 클로저에 'static 을 요구합니다. "잠깐 빌린 참조를 품지 말라" 는 뜻이었습니다(11부).

move — 빌리지 말고 가져간다

클로저 앞에 move 를 붙이면 쓰는 변수의 소유권을 클로저가 가져갑니다. 값이 스레드와 함께 사니 매달릴 일이 없습니다.

넘긴 값은 더 쓸 수 없다 — E0382

옮겨 간 값을 원래 스레드에서 다시 쓰면 평소의 이동 오류가 납니다. 두 스레드가 같은 벡터를 동시에 건드릴 길이 타입 검사에서 막힙니다.

두려움 없는 동시성 — 새로 배울 규칙이 없습니다. 소유권 규칙을 지키면 데이터 경쟁이 생길 수 없습니다. 그래서 스레드 버그가 컴파일 오류로 나옵니다.

여러 스레드의 결과를 모은다

손잡이를 벡터에 모아 두고 차례로 join 합니다. 스레드가 끝나는 순서는 알 수 없지만, 기다리는 순서는 우리가 정합니다.

범위 스레드 — 빌려 쓰는 스레드

thread::scope 안에서 만든 스레드는 그 범위가 끝나기 전에 반드시 끝납니다. 컴파일러가 그것을 알기 때문에 지역 변수를 move 없이 빌릴 수 있습니다.

먼저 이것부터 — 잠깐 나눠 일하고 다시 모이는 계산에는 범위 스레드가 가장 간단합니다. 값을 옮길 필요도, Arc 로 감쌀 필요도 없습니다.

스레드가 패닉하면

패닉은 그 스레드만 끝냅니다. 기다리던 쪽은 join() 의 Err 로 그 사실을 압니다.

이름 없는 스레드 — 패닉 줄의 '<unnamed>' 는 스레드에 이름을 붙이지 않았다는 뜻입니다. 지금까지 본 'main' 자리입니다.

퀴즈 — 스레드

Q. thread::spawn(|| println!("{names:?}")) 는 왜 컴파일되지 않고, 고치는 길 둘은 무엇일까요?

A. 새 스레드가 names 의 주인인 함수보다 오래 살 수 있어서입니다(E0373). ① move 로 소유권을 넘기거나(move), ② thread::scope 안에서 만들어 빌려 쓰게 합니다(범위 스레드).

2장

채널

보내는 쪽과 받는 쪽 · 보내면 소유권도 간다 · 보내는 쪽이 여럿 · 닫히는 때

채널 — 스레드 사이의 우편함

mpsc::channel() 은 보내는 쪽(tx)과 받는 쪽(rx)을 한 쌍으로 만듭니다. 한 스레드가 넣은 값을 다른 스레드가 꺼냅니다.

mpsc — multiple producer, single consumer. 보내는 쪽은 여럿일 수 있고 받는 쪽은 하나입니다.

여러 개를 차례로 받는다

받는 쪽 rx 는 for 로 돌 수 있습니다. 값이 올 때마다 한 바퀴 돌고, 보내는 쪽이 모두 사라지면 반복이 끝납니다.

보낸 값은 내 것이 아니다 — E0382

send 는 값의 소유권을 채널로 옮깁니다. 보낸 뒤에 그 값을 쓰면 이동 오류입니다. 보낸 쪽과 받은 쪽이 같은 값을 동시에 쥐는 일이 없습니다.

보내는 쪽이 여럿일 때

tx 를 clone 하면 보내는 쪽이 하나 더 생깁니다. 스레드마다 하나씩 쥐여 줍니다.

원본 tx 를 버리는 줄이 없으면 받는 쪽은 "아직 보낼 사람이 있다" 고 보고 영원히 기다립니다. 그리고 도착 순서는 정해져 있지 않으므로 모은 뒤 정렬했습니다.

닫힌 채널에서 받으면

보내는 쪽이 다 사라져도 이미 들어 있던 값은 받을 수 있습니다. 그다음부터 recv() 는 Err 를 돌려줍니다.

퀴즈 — 채널

Q. for value in rx { … } 는 언제 끝날까요?

A. 보내는 쪽(tx 와 그 복제본)이 전부 사라지고, 들어 있던 값을 다 꺼냈을 때입니다 (차례로 받는다). 하나라도 남아 있으면 계속 기다립니다 (원본을 버리는 줄).

3장

공유 상태

Mutex 와 열쇠 · Rc 는 못 보낸다 · Arc<Mutex<T>> · RwLock · 원자 타입

Mutex — 한 번에 하나만

Mutex<T> 는 값을 감싸고, lock() 으로 잠근 쪽에만 "열쇠"(guard)를 줍니다. 속의 값에는 열쇠를 통해서만 닿을 수 있습니다. 열쇠가 사라지면 잠금이 풀립니다.

잠그는 것을 잊을 수 없다 — 다른 언어에서는 데이터와 잠금이 따로 있어 잠그지 않고 건드릴 수 있습니다. 여기서는 데이터가 Mutex 안에 있어서 잠그지 않으면 닿을 길이 없습니다.

Mutex 하나를 여러 스레드에 넘기려면 — E0382

Mutex 도 주인은 하나입니다. move 로 첫 스레드에 넘기면 둘째 스레드에 줄 것이 없습니다.

Rc 는 스레드를 건너가지 못한다 — E0277

여럿이 갖게 하려면 Rc 였습니다(14부). 그런데 Rc 는 주인 수를 세는 일이 스레드에 안전하지 않습니다. 컴파일러가 그것을 알고 막습니다.

Arc<Mutex<T>> — 함께 갖고, 차례로 고친다

Arc 는 수를 원자적으로 세는 Rc 입니다(atomically reference counted). 스레드마다 Arc::clone 한 것을 하나씩 가져갑니다.

답은 늘 8000 — 잠금 없이 같은 일을 하면 다른 언어에서는 실행마다 다른 수가 나옵니다. Rust 에서는 그런 코드가 컴파일되지 않습니다.

범위 스레드에서는 Arc 도 필요 없다

Arc 가 필요했던 까닭은 스레드가 언제 끝날지 몰라서였습니다. 범위 스레드는 끝나는 때가 정해져 있으니 Mutex 를 그냥 빌려 씁니다.

RwLock — 읽기는 여럿, 쓰기는 혼자

읽는 일이 대부분이면 RwLock 이 맞습니다. 읽는 잠금은 여럿이 함께 잡고, 쓰는 잠금은 혼자 잡습니다. 빌림 규칙과 같은 모양입니다.

원자 타입 — 숫자 하나에는 잠금이 과하다

횟수 세기처럼 숫자 하나를 바꾸는 일에는 원자 타입(AtomicUsize 등)을 씁니다. 읽고 더하고 쓰는 일이 끼어들 틈 없이 한 번에 일어납니다.

Ordering::Relaxed — 다른 메모리 접근과의 순서를 얼마나 엄격히 맞출지 고르는 인자입니다. 단순한 세기에는 가장 느슨한 것으로 충분합니다.

컴파일러가 못 막는 것 — 교착

데이터 경쟁은 막아 주지만 교착(deadlock)은 막지 못합니다. 두 스레드가 서로 상대가 쥔 잠금을 기다리면 둘 다 영원히 멈춥니다. 돌려 보일 수 없으니 그림으로 봅니다.

스레드 1: A 를 잠금 ---> B 를 기다림 ...(멈춤)
스레드 2: B 를 잠금 ---> A 를 기다림 ...(멈춤)
  • 잠금을 여럿 잡을 때는 모든 곳에서 같은 순서로 잡습니다(늘 A 다음 B).
  • 잠근 채로 오래 걸리는 일을 하지 않습니다. 열쇠를 빨리 놓습니다.

퀴즈 — 공유 상태

Q. 한 스레드 안의 Rc<RefCell<T>> 에 해당하는 것을 스레드 사이에서는 무엇으로 쓸까요? 왜 그대로 못 쓸까요?

A. Arc<Mutex<T>> 입니다. Rc 는 수를 세는 일이 스레드에 안전하지 않아 다른 스레드로 보낼 수 없고(E0277), RefCell 도 여러 스레드가 함께 쓸 수 없습니다(다음 장).

4장

Send 와 Sync

컴파일러가 스레드 안전을 아는 방법 · 한 번만 만드는 전역 값 · 고르는 법

두 개의 표시 — Send 와 Sync

앞의 오류들에 나온 Send 와 Sync 는 메서드가 없는 트레이트입니다. 타입에 붙는 표시일 뿐이고, 컴파일러가 대부분 알아서 붙입니다.

표시뜻아닌 것의 예
Send다른 스레드로 옮겨도 된다Rc<T>
Sync여러 스레드가 함께 참조해도 된다RefCell<T> · Cell<T>
  • 정수, String, Vec<T> 처럼 평범한 타입은 둘 다입니다.
  • 구조체는 필드가 전부 Send 면 Send 입니다. 하나라도 아니면 아닙니다.
  • thread::spawn 이 받는 클로저는 Send 여야 합니다. 그래서 위의 검사가 일어납니다.

RefCell 은 함께 쓸 수 없다 — E0277

Arc 로 감싸면 될 것 같지만, 속의 RefCell 이 Sync 가 아닙니다. 빌림을 세는 일이 스레드에 안전하지 않기 때문입니다.

OnceLock — 한 번만 만드는 값

설정처럼 처음 필요할 때 한 번 만들고 그 뒤로는 읽기만 하는 전역 값에 씁니다. 여러 스레드가 동시에 불러도 만드는 일은 한 번만 일어납니다.

LazyLock — 처음 쓸 때 계산되는 전역 값

만드는 방법을 선언할 때 함께 적어 두는 모양입니다. 처음 쓰이는 순간에 한 번 계산됩니다 — 화면에서 "main 시작" 이 먼저 찍힙니다.

퀴즈 — Send 와 Sync

Q. Arc<RefCell<i32>> 를 새 스레드로 옮기려 하면 왜 막힐까요? Arc 는 스레드에 안전한데요.

A. Arc 는 속의 값을 여러 스레드가 함께 참조하게 합니다. 그러려면 속의 타입이 Sync 여야 하는데 RefCell 은 아닙니다(E0277). Mutex 나 RwLock 으로 바꿉니다.
