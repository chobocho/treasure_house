매크로·unsafe·FFI 심화

macro_rules! 심화 · 날 포인터와 메모리 · 작은 Vec 만들기 · FFI

이 부에서 할 일

16부는 매크로와 unsafe 를 "무엇인지 알아볼 수 있을 만큼" 만 봤습니다. 이 부는 그 위에 올리는 2층입니다. 16부가 가르친 것은 다시 설명하지 않고 그 슬라이드로 가는 링크만 답니다. 앞의 두 장은 도구를 봅니다. macro_rules! 가 인자를 받는 여러 방법과, 날 포인터로 메모리를 직접 다루는 함수들입니다. 뒤의 두 장은 그 도구로 벡터를 손으로 만들고, C 로 쓴 코드와 값을 주고받습니다. 16부의 나머지 하나인 async 는 22부에서 잇습니다.

  • 1장 — macro_rules! 심화: 받는 것의 종류 tt · literal · pat · block · item, 반복 안의 반복, 재귀와 tt 떼어 내기, 내부 규칙, + 와 ?, 매크로 오류 읽기, 위생, #[macro_export] 와 $crate
  • 2장 — 날 포인터와 메모리: add 와 offset, read 와 write, NonNull, alloc 과 Layout, MaybeUninit, from_raw_parts, transmute 와 to_bits
  • 3장 — 작은 Vec 만들기: MyVec<T> 를 자리 잡기부터 push, 늘리기, Index, Drop, IntoIterator 까지 한 단계씩
  • 4장 — FFI: C 함수 더 부르기, CStr 과 CString, #[repr(C)] 구조체, Rust 함수를 C 쪽에 내놓기, union, static mut
1장과 2장의 화면 — 1장은 컴파일 오류가 많습니다. 1장에서 매크로가 인자를 받다가 낸 오류에는 번호(E…)가 없어서, 그런 슬라이드의 제목은 번호 대신 오류의 말을 적었습니다. 예제 아래에 붙인 둘째 · 셋째 화면은 대개 19부처럼 쌍둥이 파일, 곧 위의 파일에서 적어 둔 줄만 바꾼 파일의 것입니다. 1장 끝의 두 예제 (geom::square! · square_area!)만 소스 파일이 여럿이고 rustc 를 여러 번 부릅니다. 2장의 화면에는 주소가 없습니다. 주소는 두 주소의 차이로만 찍었고, 크기로 찍은 수는 u32 가 4 바이트라는 데서 나온 것뿐입니다. 바이트가 놓이는 순서처럼 기계마다 다른 것은 true 인지만 찍었습니다.
돌려 보이지 않는 것 — 2장은 정의되지 않은 동작이 있는 프로그램을 하나도 돌리지 않습니다. 그런 프로그램은 "문서는 … 적습니다" 로만 적었고, 그 문장의 근거는 화면이 아니라 표준 라이브러리 문서와 Rust 레퍼런스입니다. 까닭은 2장의 첫 슬라이드에 있습니다.

macro_rules! 심화

expr 이 못 받는 것 · tt · expr 과 tt · literal 과 갈래의 순서 · pat · block · item · 반복 안의 반복 · 재귀와 한도 · tt 떼어 내기 · 내부 규칙 · + 와 ? · local ambiguity · 펼친 뒤의 오류 · 위생 · #[macro_export] · $crate · 찾는 표

연산자는 expr 로 받을 수 없다 — no rules expected

16부의 매크로는 인자를 expr 과 ident 로만 받았습니다. 이번에는 연산자까지 인자로 받아 calc!(6, +, 2) 를 6 + 2 로 펼치려 합니다. 가운데 자리도 expr 로 적어 봅니다.

읽는 법 — 오류 첫 줄은 16부에서 맞는 갈래가 없을 때 본 말 그대로이고, 이번에 막힌 글자는 + 입니다. note: 는 3번 줄의 $op:expr 를 맞추던 중이었다고 합니다. $이름:종류 한 칸을 컴파일러는 메타변수(metavariable)라고 부릅니다. + 하나만으로는 식이 아니어서 expr 칸에 들어가지 못했습니다.
고치려면 — 종류를 tt 로 바꿉니다. 그 한 낱말만 바꾼 쌍둥이 파일은 컴파일되어 8 을 찍었습니다. tt 가 무엇을 받는지는 다음 슬라이드에서 봅니다.

tt 는 토큰 한 덩이다 — 괄호로 묶인 것은 통째로 하나

컴파일러는 소스를 먼저 이름 · 수 · 연산자 · 괄호 같은 낱개로 끊어 읽습니다. 그 낱개가 토큰(token)입니다. tt 는 토큰 하나, 또는 괄호 한 쌍과 그 안의 모든 것을 받습니다. 이것을 토큰 한 덩이(token tree)라고 합니다. 받은 덩이를 16부의 stringify! 로 하나씩 글자로 바꿔 세어 봅니다.

읽는 법 — 9번 줄의 1 + 2 * 3 은 다섯 덩이입니다. 12번 줄처럼 (1 + 2) 로 묶으면 그것이 한 덩이가 되어 모두 셋입니다. 15번 줄은 식이 아닌데도 컴파일됐고 여덟 덩이입니다. 키워드 fn, =>, 대괄호로 묶인 [a, b], 문자 'x', 빈 중괄호가 하나씩입니다. <<= 는 글자가 셋이지만 한 덩이이고, -1.5 는 - 와 1.5 두 덩이로 나뉘었습니다.
따옴표 안의 글 — 덩이를 글자로 바꾼 모양은 stringify! 가 정합니다. 12번 줄에 적은 그대로 (1 + 2) 로 찍혔지만, 띄어쓰기까지 소스와 같다는 약속으로 읽지는 않습니다.

expr 로 받은 식은 한 덩어리로 남고, tt 로 받은 것은 적힌 대로 이어진다

tt 가 무엇이든 받는다면 늘 tt 로 받으면 될 것 같습니다. 받은 것에 2 를 곱하는 매크로를 두 가지로 적어 견줍니다. 하나는 expr 하나로, 하나는 tt 여럿으로 받습니다.

읽는 법 — 9번 줄의 double!(5) 는 두 파일에서 모두 10 입니다. 10번 줄의 double!(1 + 2) 는 expr 로 받으면 6, tt 로 받으면 5 입니다. 6 은 (1 + 2) * 2 이고, 5 는 1 + 2 * 2 입니다. expr 로 받은 1 + 2 는 펼친 자리에서도 식 하나로 곱해졌고, tt 로 받은 세 덩이는 * 2 앞에 그대로 놓여 곱셈이 먼저 묶였습니다. 16부의 위생 예제에서 tmp + 1 이 (10 + 1) * 2 로 계산된 것도 같은 모습입니다. 그 매크로도 $x:expr 로 받았습니다.

literal 은 리터럴만 받는다 — 좁은 갈래를 위에 적는다

literal 은 소스에 값을 직접 적은 것, 곧 리터럴만 받습니다. 리터럴도 식이므로 expr 갈래도 그것을 받습니다. 두 갈래를 함께 두고 어느 쪽으로 가는지 봅니다.

읽는 법 — 12번부터 15번 줄까지의 정수 · 문자열 · 부호가 붙은 실수 · true 는 첫 갈래로 갔습니다. 16번 줄의 괄호로 싼 (5), 17번 줄의 덧셈, 18번 줄의 경로 i32::MAX 는 리터럴이 아니어서 둘째 갈래로 갔습니다. 앞에서 tt 로는 두 덩이이던 -1.5 가 literal 한 칸에 들어갔습니다.
순서를 바꾸면 — 둘째 화면은 3번부터 5번 줄까지의 갈래와 6번부터 8번 줄까지의 갈래를 맞바꾼 파일의 것입니다. 일곱 줄이 모두 식 입니다. 위에 놓인 expr 갈래가 리터럴까지 먼저 받았고, 아래의 literal 갈래는 한 번도 쓰이지 않았습니다. 경고도 없이 컴파일됐습니다.

-i32::MAX 는 literal 갈래에서 멈춘다 — unexpected token

앞 슬라이드의 lit_first.rs 에 한 줄을 더합니다. -i32::MAX 는 리터럴이 아니니 둘째 갈래로 가서 식 이 찍힐 것 같습니다.

읽는 법 — 오류 첫 줄은 "뜻밖의 토큰 i32" 이고, ^^^ 는 19번 줄의 - 바로 뒤 i32 를 가리킵니다. 화면이 함께 보여 주는 3번 줄의 $x:literal 에 붙은 말은 "이 literal 종류의 칸에 넣을 인자를 읽던 중" 입니다. 앞 슬라이드의 18번 줄 i32::MAX 는 첫 갈래에 맞지 않자 둘째 갈래로 넘어갔습니다. 이번에는 넘어가지 않고 오류가 됐습니다. 다른 것은 맨 앞의 - 하나입니다.
고치려면 — 인자를 괄호로 쌉니다. 괄호로 싼 것은 앞 슬라이드의 (5) 처럼 첫 갈래에 맞지 않고 둘째 갈래로 넘어갑니다. 그렇게만 바꾼 쌍둥이 파일은 마지막 줄에 식 을 찍었습니다. 갈래를 여럿 둘 때는 이런 입력이 어디서 멈추는지를 돌려서 확인합니다.

pat 는 패턴을 받는다 — expr 로 받은 것은 패턴 자리에 놓지 못한다

7부에서 쓴 matches! 는 값과 패턴을 받아 bool 을 줍니다. 같은 일을 하는 is! 를 만듭니다. 둘째 인자를 pat 로 받아 match 의 갈래 자리에 놓습니다.

읽는 법 — 13번 줄의 Some(_), 14번 줄의 범위 Some(1..=1023), 15번과 16번 줄의 | 로 이은 패턴이 모두 pat 한 칸에 들어갔습니다. Some(443) 은 Some(_) 에 맞아 true, 443 은 1..=1023 안이라 true, Some(80) 도 None 도 아니라 false, 7 은 1 · 2 · 4 가운데 없어 false 입니다.
expr 로 받으면 — 둘째 화면의 쌍둥이 파일은 13번부터 16번 줄까지 네 호출이 모두 같은 오류로 막혔습니다. 오류 첫 줄은 "패턴에는 아무 식이나 올 수 없다" 이고, note: 는 "expr 종류는 메타변수의 내용을 식으로 굳힌다" 입니다. 호출한 쪽의 글자는 같은 Some(_) 인데, 무엇으로 받았느냐에 따라 놓을 수 있는 자리가 달라졌습니다.

block 은 중괄호 블록을 받아 블록이 와야 하는 자리에 놓는다

블록도 값을 내는 식이어서 expr 로도 받을 수 있습니다. 그런데 for 의 몸통처럼 문법이 중괄호를 요구하는 자리가 있습니다. 블록을 받아 정한 횟수만큼 되풀이하는 times! 로 두 종류를 견줍니다.

읽는 법 — 10번부터 12번 줄까지의 블록이 4번 줄의 $body 자리에 놓여 세 번 돌았고, total 은 30 입니다. 둘째 화면은 같은 블록을 expr 로 받은 쌍둥이 파일의 것입니다. 호출은 받아들여졌고, 막힌 곳은 펼치는 쪽인 4번 줄입니다 — "{ 가 와야 하는데 expr 메타변수가 왔다". 그 아래에는 10번부터 12번 줄까지를 "이 매크로 호출에서" 라고 짚고, note: 가 오류가 times 매크로에서 비롯됐다고 적습니다. 괄호 안의 말은 이 책이 쓰지 않는 나이틀리(nightly) 컴파일러의 옵션입니다. help: 는 { $body } 로 한 번 더 감싸라고 권합니다.

item 은 정의 하나를 통째로 받는다

구조체 · 열거형 · 함수처럼 이름을 붙여 정의하는 것 하나하나를 항목(item)이라고 합니다. item 으로 받으면 정의를 그대로 다시 내놓으면서 앞에 무언가를 붙일 수 있습니다. 받은 정의마다 10부의 #[derive(Debug)] 를 붙이는 매크로입니다.

읽는 법 — 12번 줄의 Point 와 17번 줄의 Light 에는 derive 를 적지 않았습니다. 그런데 25번과 26번 줄이 둘을 {:?} 로 찍었습니다. 5번 줄의 속성이 받은 정의마다 붙어 나왔습니다. 25번 줄의 p.x + p.y 는 두 필드를 읽어 3 을 찍습니다. 매크로는 main 밖인 11번 줄에서 불렀습니다. 정의를 만들어 내는 이 매크로도 16부의 make_adder! 처럼 정의가 올 자리에서 불렀습니다.
expr 로 받으면 — 둘째 화면입니다. 12번 줄의 키워드 struct 에서 no rules expected 로 막혔습니다. note: 는 "반복의 첫머리를 맞추던 중" 입니다. struct Point { … } 는 식으로 시작하지 않습니다.

반복 안의 반복 — 펼치는 쪽도 받은 깊이만큼 겹친다

16부에서는 $( … ),* 를 한 겹으로만 썼습니다. 줄은 ; 로, 칸은 , 로 나눠 적는 2차원 벡터 grid! 는 반복을 두 겹으로 받습니다. * 대신 적은 + 는 "한 번 이상" 이고, 뒤에서 확인합니다.

읽는 법 — 3번 줄에서 $x 는 $( … ) 두 겹 안에 있습니다. 4번 줄도 $x 를 두 겹 안에 적었습니다. 바깥 겹이 줄마다 vec![ … ] 를 하나씩, 안쪽 겹이 그 줄의 칸을 찍어 냅니다. 9번 줄은 두 줄에 세 칸씩이고 11번 줄의 g.len() 은 2 입니다. 13번 줄처럼 줄마다 칸 수가 달라도 됩니다.
깊이가 모자라면 — 둘째 화면은 "변수 x 가 이 깊이에서는 아직 반복 중이다" 입니다. 두 겹으로 받은 것을 한 겹 안에서 썼습니다. 줄을 가르지 않고 한 벡터에 모으려 해도 겹은 둘이어야 합니다. 셋째 화면이 그렇게 적은 파일의 것이고, g.len() 이 6 입니다.

매크로가 자기를 다시 부른다 — 받은 것이 줄지 않으면 recursion limit 에 닿는다

펼친 결과 안에 매크로 호출이 또 있으면 그것도 펼쳐집니다. 자기 자신을 불러도 됩니다. 받은 덩이의 수를 세는 count! 는 맨 앞 덩이 하나를 떼고, 나머지로 자기를 다시 부릅니다.

읽는 법 — 6번 줄의 패턴은 맨 앞 덩이를 $head 로, 나머지를 $tail 로 받습니다. 7번 줄은 나머지만 넘겨 자기를 다시 부르고 1 을 더합니다. 넘길 것이 없어지면 3번 줄의 빈 갈래가 0 을 냅니다. 12번부터 14번 줄까지가 0 · 1 · 3 을 찍었습니다. 15번 줄도 3 입니다. 괄호로 묶인 것은 한 덩이입니다.
줄지 않는 재귀 — forever! 는 4번 줄에서 받은 것을 그대로 넘깁니다. 오류 첫 줄은 "forever! 를 펼치다가 재귀 한도(recursion limit)에 닿았다" 입니다. 컴파일러는 끝없이 펼치는 대신 정해 둔 깊이에서 그만뒀습니다. 화살표는 4번 줄의 호출을, 그 아래는 9번 줄을 "이 매크로 호출에서" 라고 짚습니다. help: 는 그 한도를 올리는 속성을 알려 주고, note: 는 앞에서 읽은 "이 매크로에서 비롯됐다" 입니다. 여기서 고칠 곳은 한도가 아니라 4번 줄입니다. count! 는 부를 때마다 받은 것이 하나씩 줄어서 끝났습니다.

항목을 하나씩 떼어 갈래로 가른다 — tt 떼어 내기

옵션을 verbose, level = 3 처럼 적게 하려 합니다. 이름만 적은 항목과 이름 = 값 인 항목이 섞여 있고, 모양마다 할 일이 다릅니다. 갈래는 모양마다 하나씩 적는 것이므로, 맨 앞 항목 하나를 갈래로 가려 처리하고 나머지는 tt 로 받아 자기에게 다시 넘깁니다. 앞 슬라이드의 count! 와 같은 재귀이고, 이 짜임을 tt 떼어 내기(tt muncher)라고 부릅니다.

읽는 법 — 21번 줄이 받은 것 끝에 쉼표를 하나 붙여 opts_go! 에 넘깁니다. 그래서 모든 항목이 쉼표로 끝납니다. 27번 줄의 verbose 와 dry_run 은 11번 줄의 갈래에 맞아 "true" 가 들어갔고, level = 3 과 name = "rs" 는 6번 줄의 갈래에 맞아 값이 글자로 들어갔습니다. 29번 줄의 2 + 2 는 "4" 입니다. expr 로 받아 식 하나로 계산된 다음 to_string 을 받았습니다. 찍힌 순서는 적은 순서 그대로입니다.
끝내는 갈래 — 4번 줄의 $(,)? 는 16부에서 본 "쉼표가 있어도 없어도" 입니다. 27번 줄은 항목을 다 떼고 나면 남는 것이 없고, 끝에 쉼표를 적은 29번 줄은 쉼표 하나가 남습니다. 두 호출이 모두 컴파일됐습니다. 벡터 v 는 20번 줄에서 만들어 이름째 넘겼고, 받는 쪽은 그 이름을 ident 로 받습니다.

속에서만 쓰는 갈래를 한 매크로 안에 둔다 — @go 로 시작하는 내부 규칙

앞 슬라이드는 매크로가 둘이었습니다. 부르는 쪽이 알아야 하는 것은 opts! 하나뿐입니다. 일하는 갈래들을 opts! 안으로 옮기고, 그 갈래의 패턴을 @go 로 시작하게 합니다. 16부에서 본 대로 패턴에 적은 글자는 부르는 쪽이 그대로 적어야 하는 글자이므로, 자기를 다시 부를 때 @go 를 붙이면 그 갈래로 갑니다. 이런 갈래를 내부 규칙(internal rule)이라고 합니다.

읽는 법 — 3번부터 11번 줄까지가 앞 슬라이드의 opts_go! 이던 세 갈래이고, 패턴 앞에 @go 가 붙었습니다. 15번 줄과 6번 · 10번 줄이 opts!(@go …) 로 자기를 부릅니다. 출력은 앞 슬라이드와 글자까지 같습니다. @go 는 언어가 정한 낱말이 아니라 이 매크로가 정한 표시입니다.
무엇이든 받는 갈래는 맨 아래 — 13번 줄의 패턴 $($all:tt)* 는 @go v; … 로 시작하는 것도 받습니다. 이 갈래를 맨 위로 옮긴 쌍둥이 파일은 앞에서 본 recursion limit 오류로 끝났습니다. 화살표가 가리키는 6번 줄은 옮겨 온 opts!(@go v; $($all)* ,) 호출입니다. 좁은 갈래를 위에 적는 규칙이 여기서도 같습니다.

* 는 0번 이상, + 는 한 번 이상, ? 는 있거나 없거나

반복 뒤에 붙이는 표시는 셋입니다. 16부는 * 를 썼고, $(,)? 로 마지막 쉼표를 허락했습니다. ? ( 부터)는 쉼표 하나만이 아니라 패턴의 한 부분을 묶어 "있어도 되고 없어도 되는 부분" 으로 만듭니다. 수를 하나 이상 받아 더하고, 끝에 ; base = 값 을 덧붙일 수 있는 total! 입니다.

읽는 법 — 9번 줄은 6 입니다. 끝에 쉼표를 적은 10번 줄도 6 이고, ; base = 100 을 붙인 11번 줄은 106 입니다. 4번 줄의 $(+ $base)? 는 그 부분을 받았을 때만 + 100 을 찍어 냅니다. 12번 줄처럼 수가 하나여도 됩니다.
빼거나 비우면 — 두 쌍둥이 파일의 오류 첫 줄은 똑같이 "매크로 호출이 뜻밖에 끝났다" 이고, 화살표에 붙은 말은 "인자에 토큰이 모자란다" 입니다. 둘째 화면의 화살표는 10번 줄의 마지막 쉼표 바로 뒤를 가리키고, note: 는 $x:expr 를 맞추던 중이었다고 합니다. 쉼표를 읽었으니 수가 하나 더 와야 했습니다. 셋째 화면은 수가 하나도 없는 total!() 를 + 가 받지 않은 것입니다.

있어도 없어도 되는 부분을 앞에 두면 — local ambiguity

앞 슬라이드의 total! 은 덧붙이는 부분을 맨 끝에 뒀습니다. 그것을 맨 앞으로 옮겨 total!(base = 100; 1, 2, 3) 으로 부르게 고쳐 봅니다.

읽는 법 — 오류 첫 줄은 "매크로 total 을 부르는 데 국소적인 모호함이 있다 — 읽는 길이 여럿이다" 입니다. ^^^^ 는 9번 줄의 base 를 가리킵니다. 길 하나는 x 라는 이름의 expr 이고, "그 밖의 길 하나" 가 더 있다고 합니다. 그 길이 무엇인지 화면은 적지 않습니다. 3번 줄을 보면 base 는 $(base = …)? 가 요구하는 글자이기도 하고, $x:expr 가 받을 수 있는 식의 첫머리이기도 합니다. 컴파일러는 이 토큰에서 하나를 고르지 않고 오류를 냈습니다.
고치려면 — 앞 슬라이드처럼 덧붙이는 부분을 수들 뒤에 두고 ; 로 시작하게 합니다. 그 파일은 컴파일됐고 11번 줄이 106 을 찍었습니다.

펼친 뒤의 코드가 틀리면 오류는 두 자리를 짚는다 — E0369

앞에서 본 오류 가운데 여럿은 매크로가 인자를 받는 단계에서 났습니다. 인자를 받는 데 성공하고도, 펼쳐진 코드가 타입 검사를 통과하지 못할 수 있습니다. double_expr.rs 의 10번 줄만 바꿔 double!("ab") 를 부릅니다.

읽는 법 — 번호는 9부에서 본 E0369 이고, 이번 연산은 곱셈입니다 — "&str 에 정수를 곱할 수 없다". 짚은 자리가 둘입니다. 위쪽은 매크로 정의 안인 4번 줄의 * 이고, 아래쪽은 10번 줄의 호출입니다. 호출 아래에는 인자 "ab" 의 타입 &str 과 "이 매크로 호출에서" 가 적혀 있습니다. 마지막 note: 는 block 슬라이드에서 본 "이 오류는 double 매크로에서 비롯됐다" 입니다.
  • 이 장에서 본 받는 단계의 오류 — no rules expected · unexpected end of macro invocation · unexpected token · local ambiguity. 번호가 없고 호출한 줄을 짚습니다.
  • 이 장에서 본 펼친 뒤의 오류 — 이 슬라이드의 E0369 와 expected {. 정의 안의 줄과 호출한 줄을 함께 짚고 "in this macro invocation" 이 붙습니다.

매크로가 만든 지역 변수는 부른 쪽에서 보이지 않는다 — E0425

16부에서 매크로 안의 tmp 와 바깥의 tmp 가 섞이지 않는 것을 위생(hygiene)이라고 했습니다. 그때는 이름이 겹쳐도 안전하다는 쪽을 봤습니다. 같은 규칙의 반대쪽입니다. 매크로가 let 으로 변수를 만들어 주기를 기대하고 바깥에서 그 이름을 씁니다.

읽는 법 — 번호와 오류 첫 줄은 3부에서 본 E0425 그대로입니다. 10번 줄의 answer 를 "이 스코프에서 찾을 수 없다". 새로 읽을 것은 help: 입니다 — "같은 이름의 식별자가 여기 정의돼 있지만 매크로 위생 때문에 닿을 수 없다". 4번 줄의 answer 를 짚고, 그것이 9번 줄의 호출에서 나왔다고 적습니다. note: 는 앞 슬라이드에서 읽은 말입니다.
고치려면 — 변수의 이름을 부르는 쪽이 넘깁니다. 9번 줄에서 넘긴 answer 는 부른 쪽의 이름이어서, 4번 줄의 let $name 이 만든 변수를 10번 줄이 읽고 42 를 찍었습니다. tt 떼어 내기에서 벡터의 이름 v 를 ident 로 넘긴 것도 이 방법입니다.

#[macro_export] — 매크로를 다른 크레이트가 쓰게 내놓는다

이제까지의 매크로는 정의한 파일 안에서만 썼습니다. 라이브러리 크레이트가 매크로를 내놓으려면 정의 앞에 #[macro_export] 속성을 붙입니다. 가져다 쓰는 쪽은 그 매크로를 함수처럼 13부의 use 로 가져오거나 경로로 부릅니다( 부터). 19부의 두 크레이트 예제처럼 소스 파일이 둘입니다.

읽는 법 — 화면 첫 줄의 세 명령은 19부에서 읽은 것과 같은 꼴입니다. geom.rs 를 라이브러리 크레이트로 컴파일하고, 그 결과를 --extern 으로 넘겨 main.rs 를 컴파일한 뒤 실행합니다. main.rs 의 2번 줄이 매크로를 가져왔고 5번 줄이 16 을 찍었습니다. 7번 줄은 use 에 기대지 않고 경로로 불러 25 를 찍었습니다. geom.rs 의 7번과 8번 줄이 2 + 3 을 s 에 담아 s * s 를 했습니다.
경로에 shapes 가 없다 — geom.rs 는 매크로를 2번 줄의 모듈 shapes 안에 적었습니다. 그런데 main.rs 가 적은 경로는 두 군데 모두 geom::square 입니다. 배지의 릴리스 노트는 #[macro_export] 로 내놓은 매크로가 크레이트의 뿌리 모듈에 놓인다고 적습니다.

내놓지 않은 매크로는 크레이트 밖에서 찾지 못한다 — E0432 · E0433

앞 슬라이드의 geom.rs 에서 4번 줄의 #[macro_export] 만 지운 쌍둥이 geom_hidden.rs 를 같은 이름의 크레이트로 컴파일하고, 같은 main.rs 를 다시 컴파일합니다. 한 줄이 지워져서 쌍둥이 파일에서는 매크로 이름이 4번 줄에 있습니다.

읽는 법 — 라이브러리는 컴파일됐고 경고가 붙었습니다 — "쓰이지 않는 매크로 정의 square". 이 크레이트 안에서는 아무도 부르지 않습니다. 그 note: 는 이 경고가 기본으로 켜져 있다는 말입니다. main.rs 는 오류 둘로 막혔습니다. 첫째 E0432 는 2번 줄의 use 에 "풀리지 않는 가져오기" 라고 하고, square 아래에 "뿌리에 square 가 없다" 고 적습니다. 둘째 E0433 은 7번 줄의 경로에서 "geom 안에서 square 를 찾을 수 없다" 입니다. 첫째 오류가 찾아본 곳이 "뿌리" 입니다. 앞 슬라이드의 릴리스 노트가 말한 그 자리입니다.

매크로 본문에 적은 함수 이름은 펼쳐진 곳에서 찾는다 — E0425

내놓는 매크로가 자기 크레이트의 함수를 부르는 경우입니다. 라이브러리 geom 에 넓이를 구하는 함수 area 가 있고, 매크로 square_area! 의 본문이 그 함수를 이름만 적어 부릅니다.

읽는 법 — 번호는 앞에서 본 E0425 이고, 이번에 찾지 못한 것은 값이 아니라 함수 area 입니다. 화살표는 main.rs 5번 줄의 호출 전체를 가리키고 "이 스코프에서 찾을 수 없다" 고 합니다. 그 스코프는 main.rs 입니다. note: 는 오류가 square_area 매크로에서 비롯됐다고 적습니다. geom.rs 10번 줄의 area(…) 가 main.rs 안에 펼쳐졌고, 거기에는 area 라는 함수가 없습니다. 화면 첫 줄의 첫 명령, 곧 geom.rs 의 컴파일은 오류 없이 지나갔습니다.

$crate 는 매크로가 정의된 크레이트를 가리킨다

가져다 쓰는 쪽에 마침 area 라는 함수가 있으면 앞 슬라이드의 오류는 나지 않습니다. 대신 다른 일이 벌어집니다. 둘레를 구하는 area 를 가진 main_own.rs 를 앞 슬라이드의 geom.rs 와 함께 컴파일합니다.

읽는 법 — 둘째 화면에서 10번 줄의 square_area!(3) 은 12 를 찍었습니다. 11번 줄이 이 크레이트의 area 를 직접 불러 찍은 12 와 같습니다. 라이브러리의 area 였다면 3 곱하기 3 인 9 여야 합니다. 매크로가 부른 쪽의 함수를 대신 잡았고, 컴파일러는 아무 말도 하지 않았습니다. 셋째 화면은 본문의 그 한 줄을 $crate::area 로 바꾼 라이브러리로 다시 컴파일한 것입니다. 앞 슬라이드의 main.rs 가 컴파일되어 9 를 찍었고, main_own.rs 도 10번 줄은 9, 11번 줄은 12 입니다.
위생은 지역 변수까지 — 매크로가 만든 지역 변수는 부른 쪽과 섞이지 않았습니다. 본문에 적은 함수 이름은 섞였습니다. 내놓는 매크로가 자기 크레이트의 것을 부를 때는 경로를 $crate:: 로 시작합니다.

퀴즈 — macro_rules! 심화

Q. 받은 것에 2 를 곱하는 매크로 double! 을 두 가지로 적었습니다. 하나는 ($x:expr) => { $x * 2 } 이고, 하나는 ($($x:tt)*) => { $($x)* * 2 } 입니다. double!(1 + 2) 는 각각 얼마일까요?

A. 6 과 5 입니다(두 파일의 출력). expr 로 받은 1 + 2 는 식 하나로 남아 (1 + 2) * 2 가 되고, tt 로 받은 세 덩이는 적힌 대로 놓여 1 + 2 * 2 가 됩니다. 그래서 값을 받을 때는 expr 로 받고, tt 는 식이 아닌 것을 받을 때 씁니다 — 연산자나, 다음 갈래에 그대로 넘길 나머지가 그런 것입니다.

add 는 칸 수로 센다 — 포인터를 옮겨 그 칸의 값을 읽는다

6부에서 슬라이스는 주소와 길이라고 했습니다. as_ptr() 는 그 주소, 곧 첫 칸을 가리키는 날 포인터를 줍니다. add(n) 은 거기서 n 칸 뒤를 가리키는 포인터를 만들고, offset(n) 은 음수도 받아 앞으로도 갑니다.

NonNull — 널이 아니라는 것을 타입에 적은 날 포인터

*mut T 는 널일 수 있어서, 받은 쪽이 쓸 때마다 널인지 물어야 합니다. 7부에서 Rust 는 null 대신 Option 을 쓴다고 했습니다. 날 포인터에도 같은 생각을 옮긴 것이 NonNull<T> 입니다. 널이 아닌 포인터만 담고, 없을 수도 있으면 Option<NonNull<T>> 로 적습니다.

읽는 법 — 6번 줄은 n 을 가리키는 포인터라 Some, 7번 줄은 ptr::null_mut() 이 준 널 포인터라 None 이고, 8번 줄이 true true 를 찍었습니다. 13번 줄의 true 는 Option<NonNull<i32>> 와 *mut i32 의 크기가 같다는 것입니다. 문서가 약속하는 것이고, 널이라는 값을 None 을 나타내는 데 쓴다고 설명합니다. 부록에서 Option<Box<u8>> 가 Box<u8> 와 크기가 같던 것과 같은 모습입니다. 19번 줄은 as_ptr() 로 얻은 날 포인터로 1 을 더했고, 20번 줄은 as_ref() 로 얻은 참조로 6 을 읽었습니다. 23번 줄의 n 도 6 입니다.

MaybeUninit — 값이 아직 없을 수 있는 자리를 타입으로 적는다

3부에서 컴파일러는 값을 넣기 전의 변수를 읽지 못하게 막았습니다. 날 포인터 뒤의 자리는 컴파일러가 따라가 보지 못해서, 앞의 두 슬라이드에서는 "채운 뒤에만 읽는다" 를 주석으로 지켰습니다. MaybeUninit<T> 는 "T 가 들어갈 자리인데 값이 있을 수도, 없을 수도 있다" 를 타입으로 적습니다. 아래 예제에서 만들고 채우는 줄은 안전하고, "이제 값이 있다" 고 말하는 한 줄만 unsafe 입니다.

슬라이스가 주소와 길이라면, 거꾸로 포인터 하나와 길이 하나로 슬라이스를 만들 수도 있습니다. slice::from_raw_parts(포인터, 길이) 입니다. 그 뒤로는 len · {:?} · == 처럼 슬라이스에 쓰던 것을 그대로 씁니다. 첫 칸과 마지막 칸을 뺀 가운데를 돌려주는 함수로 봅니다.

읽는 법 — 12번 줄이 한 칸 나아간 포인터와 길이 len - 2 로 슬라이스를 만듭니다. 18번 줄이 [20, 30, 40] 과 길이 3 을 찍었고, 20번 줄에서 6부의 범위로 자른 슬라이스 &xs[1..4] 와 같습니다. 21번 줄의 두 칸짜리는 12번 줄까지 가서 길이 0 인 슬라이스가 됐고, 한 칸짜리는 5번 줄에서 걸려 6번 줄의 빈 슬라이스를 받았습니다.
문서의 조건 — 포인터는 널이 아니고 정렬이 맞아야 하며, 거기서부터 그 길이만큼의 칸이 모두 한 자리 안에 있고 값이 들어 있어야 합니다. 그리고 슬라이스가 사는 동안 그 칸들이 고쳐져서는 안 됩니다. 9번부터 11번 줄까지의 주석이 그 답입니다. 문서는 돌려주는 슬라이스의 수명이 쓰는 쪽에서 정해지니 안전한 수명에 묶으라고도 적습니다. 4번 줄의 시그니처가 11부의 수명 생략으로 그것을 xs 의 수명에 묶습니다. 이 함수의 일은 20번 줄처럼 범위로 쓰면 되고, from_raw_parts 는 가진 것이 포인터와 길이뿐일 때 씁니다.

transmute 로 적으면 컴파일러가 to_bits 를 권한다

mem::transmute 는 값의 비트를 그대로 둔 채 타입만 바꿉니다. 18부에서 실수의 비트는 to_bits( 부터)로, 정수의 바이트는 to_be_bytes 들로 봤습니다. 같은 일을 transmute 로도 적어 두 결과를 견줍니다.

읽는 법 — 컴파일은 됐고 경고가 둘입니다. 둘 다 "필요 없는 transmute" 이고, help: 가 바꿔 쓸 줄을 보여 줍니다. 첫째 경고의 note: 는 이 경고가 기본으로 켜져 있다는 말입니다. 10번 줄은 f32::to_bits(x) 로, 15번 줄은 u32::to_ne_bytes(n) 으로 바꾸라고 합니다. 둘째 경고는 바이트 순서를 정하고 싶으면 to_le_bytes 와 to_be_bytes 도 있다고 덧붙입니다. 실행 결과에서 7번 줄은 1.0 의 비트 0x3f800000 과, 그것을 from_bits 로 되돌린 1 을 찍었습니다. 11번 줄의 true 는 transmute 의 결과가 to_bits 와 같다는 것입니다. 17번과 18번 줄의 true 는 네 바이트가 to_ne_bytes 와 같고, from_ne_bytes 로 되돌리면 원래 수라는 것입니다. ne 는 이 기계가 쓰는 순서라는 뜻이어서, 바이트 자체는 찍지 않았습니다.
안전한 메서드가 있으면 그것을 쓴다 — 9번과 14번 줄의 주석은 두 transmute 가 괜찮은 까닭을 적습니다. 크기가 같고, 받는 쪽 타입에 안 되는 비트 모양이 없습니다. to_bits 와 to_ne_bytes 에는 그런 주석이 필요 없습니다.

크기가 다른 타입으로는 transmute 할 수 없다 — E0512

transmute 에서 컴파일러가 확인해 주는 것은 두 타입의 크기입니다. 네 바이트인 u32 를 세 바이트인 [u8; 3] 으로 바꿔 봅니다.

읽는 법 — 오류 첫 줄은 "크기가 다른 타입 사이에서는 transmute 할 수 없다" 입니다. 두 note: 가 양쪽의 크기를 적습니다. 원래 타입 u32 는 32 비트, 바꾸려는 타입 [u8; 3] 은 24 비트입니다. 고친 모양은 앞 슬라이드의 15번 줄처럼 받는 쪽을 [u8; 4] 로 하는 것입니다.
크기가 같아도 안 되는 것 — 문서는 transmute 에 넣는 값과 나오는 값이 모두 각 타입에서 유효해야 하고, 어기면 정의되지 않은 동작이라고 적습니다. Rust 레퍼런스에 따르면 bool 은 0 과 1 만, char 는 유니코드 스칼라 값만, 열거형은 있는 변형만 유효하고, 참조는 널이 아니고 정렬이 맞으며 살아 있는 값을 가리켜야 합니다. u8 인 2 를 bool 로 바꾸는 것은 두 타입의 크기가 같아도 그 조건을 어깁니다. 돌려 보이지 않습니다.

Q. Noisy 는 정리될 때 이름을 찍습니다. p 가 Noisy("a") 가 든 자리를 가리킬 때 *p = Noisy("b"); 와 p.write(Noisy("b")); 는 화면에 무엇이 다르게 찍힐까요? 그리고 alloc 으로 막 잡은 자리에는 둘 가운데 어느 것을 써야 할까요?

A. 대입은 정리: a 를 찍고, write 는 아무것도 찍지 않습니다. 대입은 옛 값을 정리한 다음 새 값을 넣고, write 는 옛 값을 정리하지 않고 덮습니다(write_drop.rs 의 17번과 22번 줄). 막 잡은 자리에는 정리할 옛 값이 없으므로 write 를 씁니다. alloc_drop.rs 의 25번과 26번 줄이 그렇게 넣었고, 그 두 값은 뒤에서 한 번씩만 정리됐습니다.
