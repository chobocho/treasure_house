이 프로젝트가 쓰는 것

1장의 wc 는 인자를 손으로 읽어 Config 에 담고, 읽을 곳 하나와 쓸 곳 둘을 받는 run 에 일을 맡기고, 종료 코드 셋으로 끝났습니다. 이 장의 grep 은 찾을 글이 든 줄을 골라 찍는 프로그램이고, 그 틀을 그대로 가져옵니다. 이 장은 그 찾을 글을 패턴이라고 부릅니다. 7부의 패턴과는 다른 뜻이고, 맞는다는 것에서 정합니다. 새로 하는 일은 셋입니다 — 줄이 패턴에 맞는지 가리는 일, 고를 줄을 바꾸는 옵션 둘과 찍는 모양을 바꾸는 옵션 둘, 그리고 고른 줄이 있었는지까지 알리는 종료 코드입니다. 첫 표는 그러느라 다시 쓰는 것과 그것을 배운 슬라이드이고, 둘째 표는 1장에서 그대로 가져온 것입니다.

두 표 모두 왼쪽이 이 장의 코드에 나오는 것입니다. 첫 표의 오른쪽은 그것을 처음 설명한 슬라이드이고, 둘째 표의 오른쪽은 1장에서 그것을 만든 슬라이드입니다. 이 장은 오른쪽의 설명을 되풀이하지 않고, 1장과 달라지는 곳만 말합니다.

다 만들면 이렇게 돈다

마지막 단계의 패키지를 빌드해 돌린 화면입니다. 여기까지 가는 길을 여덟 단계로 나눠 걷습니다. 화면은 1장처럼 target/debug/ 의 실행 파일을 직접 부릅니다. 실행 파일의 이름이 grep 이라서, 이 기계에 깔린 같은 이름의 명령이 대신 돌지 않게 늘 경로까지 적습니다. 입력 파일은 둘이고 cat 으로 먼저 봅니다.

읽는 법 — data/memo.txt 는 다섯 줄이고 셋째 줄이 비었습니다. data/todo.txt 는 세 줄입니다. cargo build -q 는 아무것도 찍지 않았습니다. 이 장의 글에서는 ./target/debug/grep 을 grep 으로 줄여 적습니다. grep rust data/memo.txt 는 rust 가 든 두 줄을 찍었습니다. 대문자로 시작하는 Rust book 의 줄은 빠졌습니다. -in 을 주고 파일을 둘 준 실행에서는 그 줄과 learn RUST 까지 다섯 줄이 나왔고, 줄마다 앞에 파일 이름과 줄 번호가 콜론으로 붙었습니다. -vn 은 거꾸로 rust 가 없는 줄 셋을 번호 1 · 3 · 5 와 함께 찍었습니다. 빈 줄은 3: 뿐입니다. -ci 는 줄 대신 파일마다 이름과 고른 줄의 수 3 과 2 를 찍었습니다. 파일을 주지 않은 printf … | grep -n rust 는 표준 입력에서 찾아 이름 없이 2:rust 를 찍었습니다. zig 는 어느 줄에도 없어서 아무것도 찍지 않고 종료 코드 1 입니다. 없는 data/none.txt 를 끼운 실행은 알림 한 줄을 내고 나머지 파일에서 한 줄을 이름과 함께 찍었는데, 고른 줄이 있는데도 종료 코드는 2 입니다. 알림 끝의 No such file or directory (os error 2) 는 17부에서 말한 대로 이 기계의 운영 체제가 준 글입니다. 모르는 옵션 -x 에는 쓰는 법을 알리고 역시 2 입니다.
이 책의 grep 입니다 — 이름과 옵션 글자는 익숙한 명령에서 빌렸지만, 무엇을 줄로 보고 무엇을 맞는다고 할지, 줄을 어떤 모양으로 찍고 몇으로 끝낼지는 이 장이 정합니다. 어느 기계의 grep 과 출력이 같다고 말하지 않습니다.

여덟 단계 — 단계마다 컴파일되고 돈다

1장과 같은 방식입니다. 단계 하나가 예제 디렉터리 하나이고, 뒤 단계는 앞 단계의 파일을 그대로 두고 줄을 더하거나 적어 둔 줄만 바꾼 사본입니다. 슬라이드가 싣지도 말하지도 않은 줄은 앞 단계의 것 그대로입니다. 1장에서는 run 이 생긴 뒤에 Config 가 들어와 run 의 여섯 줄을 고쳐야 했습니다. 이번에는 Config 를 먼저 만듭니다.

맞는다는 것은 줄 안에 패턴이 그대로 들어 있다는 것 — 이 프로그램이 고른 것

가장 안쪽의 물음부터 함수로 만듭니다. 줄 하나와 패턴 하나를 받아 맞는지 답합니다. 8부에서 본 contains 한 줄입니다. 1단계의 파일은 Cargo.toml 과 src/lib.rs 둘입니다.

읽는 법 — Cargo.toml 은 패키지 이름만 다르고 1장의 것과 같습니다. lib.rs 의 2번 줄은 줄과 패턴을 둘 다 &str 로 받고, 3번 줄이 contains 의 답을 그대로 돌려줍니다. 한 줄짜리 일을 함수로 떼어 이름을 붙인 것은, "맞는다" 의 뜻을 정하는 곳을 이 한 군데로 두려는 것입니다.
이 프로그램의 정의 — 맞는다 — 줄 안에 패턴이 글자 그대로 들어 있으면 맞는 것입니다. 이 장에서 패턴은 grep 에 주는 찾을 글이고, 7부의 패턴을 말할 때는 "튜플 패턴" 처럼 앞에 말을 붙여 적습니다. 점이나 별표에 특별한 뜻을 주는 정규식(regular expression)은 받지 않고, 이 장은 정규식을 다루지 않습니다. 다음 슬라이드의 시험이 이 정의를 적어 둡니다.

정의를 시험으로 적어 둔다 — 낱말 속이어도 맞고, 대소문자가 다르면 안 맞는다

같은 lib.rs 의 아래쪽, 13부에서 본 시험 모듈입니다. is_match 가 받는 것이 글 둘뿐이라 파일도 인자도 필요 없습니다.

읽는 법 — 화면은 3개 통과입니다. --lib 은 23부에서 본 라이브러리의 단위 시험만 돌리는 옵션입니다. 12번 줄은 줄 가운데의 rust 를 찾습니다. 14번 줄의 trust 에도 rust 가 있습니다. 낱말의 경계는 따지지 않습니다. 16번 줄은 Rust 로 시작하는 줄에 rust 가 없다고 답함을 봅니다. 18번과 19번 줄은 점이 점 한 글자만 찾음을 봅니다. a.c 에는 점이 있고, abc 에는 a.c 가 없습니다. 24번 줄은 한글 패턴 녹이 입니다. 32번과 33번 줄은 빈 패턴이 글이 있는 줄에도 빈 줄에도 맞음을, 35번 줄은 빈 줄에 a 가 없음을 봅니다.
27번 줄 — 자모 둘로 적은 글 — \u{1100}\u{1161} 은 유니코드 표에 한글 첫소리 ㄱ(HANGUL CHOSEONG KIYEOK)과 가운뎃소리 ㅏ(HANGUL JUNGSEONG A)로 실린 두 char 이고, \u{AC00} 은 한 글자 가 입니다. 두 char 로 적은 줄에 한 글자 가 가 있느냐는 물음에 is_match 는 없다고 답했습니다. 8부에서 같아 보이는 두 é 가 == 로 같지 않았던 것과 같은 사정입니다. 자모 둘이 화면에 어떻게 그려지는지는 이 책이 싣지 않았고, 이 프로그램은 둘을 같게 만들어 주지 않습니다.

Config 를 먼저 만든다 — 옵션이 아닌 첫 인자가 패턴이다

2단계는 명령 줄입니다. 1장의 Config 와 parse_args 와 같은 틀이므로 달라진 곳만 봅니다. wc 에서는 옵션이 아닌 인자가 모두 파일 이름이었습니다. grep 에서는 그 가운데 첫째가 패턴입니다. lib.rs 의 맨 위에 상수 하나를, is_match 아래에 구조체와 함수를 더했습니다.

읽는 법 — 줄 번호는 둘째 상자의 것입니다. 26번 줄의 strip_prefix('-') 와 28번 줄의 가드, 29번부터 37번 줄까지의 글자마다 도는 반복문은 1장과 같은 꼴입니다. 이 단계가 아는 옵션은 31번과 32번 줄의 둘이고, 33번 줄의 나머지 갈래는 Err 로 돌아갑니다. 40번과 41번 줄이 옵션이 아닌 인자를 받습니다. 40번 줄의 가드는 패턴 자리가 아직 비어 있는지를 묻고, 그렇다면 그 인자가 패턴이 됩니다. 그 뒤에 오는 것은 41번 줄에서 파일 이름으로 모입니다. 44번부터 50번 줄까지는 반복이 끝난 뒤입니다. 패턴을 받았으면 cfg 에 넣어 Ok 로, 끝까지 받지 못했으면 패턴이 없다 를 Err 로 돌려줍니다. 9번 줄의 derive 셋은 1장과 같은 쓰임입니다. 첫 상자의 USAGE 는 4단계의 run 이 씁니다.
1장과 다른 두 곳 — 22번 줄은 패턴을 String 이 아니라 Option 으로 들고 시작합니다. 빈 글 "" 도 패턴으로 받기 때문에, 비어 있는지로는 "아직 없다" 를 가를 수 없습니다. 24번과 27번 줄은 -- 입니다. -- 에서 - 하나를 떼면 "-" 가 남고, 27번 줄이 그것을 만나면 flags_done 을 켭니다. 그 뒤로는 27번과 28번 줄의 가드가 둘 다 거짓이라 - 로 시작하는 인자도 40번과 41번 줄로 내려갑니다. 패턴이 - 로 시작할 수도 있어서 둔 길이고, 1장에서는 과제로 남긴 것입니다. 다음 두 슬라이드의 시험이 이 규칙들을 봅니다.

parse_args 의 시험 ① — 첫 인자가 패턴, 옵션은 어디에 와도 된다

1장의 시험처럼 목록을 만들어 넘깁니다. 같은 파일의 시험 모듈에 도우미 하나와 시험 다섯을 더했고, 이 슬라이드가 앞의 둘입니다.

읽는 법 — 92번 줄은 옵션 없이 인자 셋을 줍니다. 94번 줄이 첫째가 패턴임을, 95번 줄이 나머지 둘이 파일 이름임을, 96번 줄이 두 옵션이 꺼져 있음을 봅니다. 98번 줄은 패턴만 주고, 99번 줄이 파일 이름이 없음을 봅니다. 111번 줄은 -i 를 패턴 앞에, -v 를 파일 이름 뒤에 줍니다. 112번 줄은 읽어 낸 Config 를 104번 줄에서 만든 want 와 통째로 견줍니다. 114번 줄은 둘을 -vi 로 붙이고 -i 를 한 번 더 주는데, 115번 줄에서 같은 want 와 같습니다. 화면은 8개 통과입니다. 1단계의 셋에 이 단계의 다섯이 더해졌습니다.
109번 줄의 ..Config::default() — 7부에서 본 갱신 문법입니다. 이 단계의 Config 는 필드가 넷이고 넷을 다 적었으므로, 여기서 가져올 필드는 없습니다. 5단계와 6단계에서 필드가 하나씩 늘어도 이 시험을 고치지 않으려고 적어 둔 줄입니다.

parse_args 의 시험 ② — 빈 패턴은 패턴이고, 없는 패턴은 오류다

나머지 시험 셋은 가장자리입니다. -- 뒤에 오는 것, 패턴 자리가 빈 글일 때와 아예 없을 때, 그리고 모르는 옵션입니다.

읽는 법 — 120번 줄에서 -- 앞의 -i 는 옵션으로 읽혔고(125번 줄), 뒤의 -v 는 패턴이, -x 는 파일 이름이 됐습니다. invert 는 꺼진 채입니다. 127번 줄은 -- 를 두 번 줍니다. 첫째가 옵션을 끝내고, 둘째는 글 그대로 패턴입니다. 130번 줄의 - 하나는 -- 없이도 옵션이 아닙니다. 첫째가 패턴, 둘째가 파일 이름입니다. 137번 줄은 빈 글 하나를 주고, 그것이 패턴으로 읽힘을 봅니다. 138번 줄은 인자가 하나도 없을 때, 141번 줄은 옵션과 -- 만 있을 때입니다. 둘 다 패턴이 없다 입니다. 147번 줄의 -ix 는 i 까지 읽고 x 에서 Err 가 됩니다. 150번 줄은 패턴 뒤에 온 -x 도 옵션으로 읽힘을 봅니다. 153번 줄은 --help 를 주고, 154번 줄이 돌아온 글이 모르는 옵션 -- 임을 봅니다. parse_args 의 소스를 따라가면, - 하나를 뗀 -help 가 "-" 와 같지 않아 옵션 묶음으로 읽히고 그 첫 글자 - 가 모르는 옵션이 된 것입니다.

읽는 법 — 빈 패턴을 준 실행은 data/todo.txt 의 세 줄을 모두 찍었습니다. 빈 패턴은 어느 줄에나 맞는다는 1단계의 시험 그대로입니다. 둘째 실행의 인자는 -- 와 -v 둘입니다. -v 가 옵션으로 읽혔다면 패턴이 없어 잘못 부른 것이 됐을 것입니다. 화면은 ls -v 한 줄입니다. -v 라는 글이 든 줄을 찾은 것이고, 뒤집히지도 않았습니다.

고른 줄이 없으면 1, 잘못 부르면 2 — 종료 코드가 답을 전한다

아무것도 찍지 않은 실행은 화면만으로는 "없다" 인지 "잘못됐다" 인지 가릴 수 없습니다. 종료 코드가 그것을 가릅니다. 앞의 세 실행은 고른 줄이 없는 경우이고, 뒤의 세 실행은 잘못 부른 경우입니다.

세 파일 가운데 둘째가 없는 이름입니다. 1장의 알리고 넘어간다와 같은 틀이고, 달라진 것은 종료 코드입니다. 같은 명령을 세 번 치고, 마지막에는 파일 자리에 디렉터리를 줍니다.

6단계의 실행 파일입니다. 파일 하나에, 둘에, 다른 옵션과 함께, 표준 입력에, 그리고 고른 줄이 없을 때와 읽지 못한 파일이 있을 때입니다.

퀴즈 — 화면과 종료 코드를 미리 적어 보기

Q. ./target/debug/grep 을 grep 으로 줄여 적습니다. 둘 다 마지막 단계의 grep 입니다. ① printf 'Rust\n\nrust' | grep -vn rust 는 표준 출력에 무엇을 찍고 몇으로 끝납니까? ② grep -c RUST data/none.txt data/todo.txt 에서 data/none.txt 는 없는 파일이고, data/todo.txt 의 세 줄은 milk · rust book 읽기 · learn RUST 입니다. 표준 출력에는 무엇이 나오고 종료 코드는 몇입니까?

A. ① 1:Rust 와 2: 두 줄을 찍고 0 으로 끝납니다. -i 가 없으므로 Rust 에는 rust 가 없고, 빈 줄에도 없습니다. -v 가 그 둘을 고릅니다. 줄바꿈 없이 끝난 셋째 줄 rust 도 한 줄이지만 패턴에 맞으므로 빠집니다. 번호는 원래 글에서의 번호이고(-vn), 빈 줄은 콜론에서 끝납니다. 고른 줄이 있으니 0 입니다. ② 표준 출력에는 data/todo.txt:1 한 줄입니다. 대문자 RUST 가 든 줄은 하나이고, 이름을 둘 받았으므로 이름 칸이 붙습니다 (받은 이름의 수). 없는 파일의 알림은 표준 오류로 가고 그 파일에는 수를 쓰지 않습니다(-c 의 마지막 실행). 고른 줄이 있지만 읽지 못한 파일이 있으므로 종료 코드는 2 입니다(읽지 못한 것이 먼저다). 두 명령은 마지막 단계 grep8_final 에서 모든 시험 다음에 돌렸습니다. 그 화면입니다.

더 해 볼 것

마지막 단계의 패키지를 복사해 놓고 고쳐 보는 과제입니다. 풀이는 싣지 않았습니다. 과제마다 손댈 파일과 함수를 적었습니다. 이 장에서 "정했다" 고 한 것을 바꾸는 과제가 많으므로, 고치기 전에 어느 시험이 깨질지부터 짚어 보면 무엇을 바꾸는지가 분명해집니다.

  • 줄의 처음과 끝 — 패턴이 ^ 로 시작하면 줄의 처음에서만, $ 로 끝나면 줄의 끝에서만 맞게 합니다. lib.rs 의 is_match 한 군데를 고칩니다. ^ 라는 글자 자체를 찾을 길도 정해야 하고, 1단계의 시험에 그 경우를 먼저 적습니다.
  • 낱말로만 찾는 옵션 — trust 안의 rust 는 빼고 싶을 때의 옵션입니다. 무엇이 낱말의 경계인지부터 시험으로 적습니다. 옵션 하나가 들어오는 자리 넷을 그대로 밟습니다.
  • 유니코드의 대소문자 — selects 의 to_ascii_lowercase 를 to_lowercase 로 바꿉니다. 3단계의 시험 가운데 어느 줄이 깨지는지 먼저 봅니다.
  • 줄마다 읽기 — read_text 대신 17부의 BufReader 의 lines() 로 한 줄씩 읽으며 찾습니다. 깨진 줄 앞의 줄은 이미 찍힌 뒤입니다. 그때 무엇을 알리고 몇으로 끝낼지 정합니다.
  • 깨진 바이트를 바꿔 읽기 — read_text 가 1장처럼 String::from_utf8_lossy 로 읽어, bad.bin 의 첫째 줄과 셋째 줄이 찍히게 합니다. 깨진 둘째 줄을 고르는 패턴이 있는지도 생각해 봅니다.
  • 표준 입력의 알림에도 이름을 — 지금은 표준 입력을 읽지 못하면 main 이 이름 없이 알립니다. run 이 파일과 같은 길로 알리고 다음으로 가게 합니다.
  • - 를 표준 입력으로 — 지금은 - 하나가 파일 이름으로 남습니다. run 의 반복문이 파일 이름 자리의 - 에서 stdin 을 읽게 하고, 그 줄의 이름 칸에 무엇을 적을지 정합니다.
  • 디렉터리를 주면 그 안에서 찾기 — 지금은 디렉터리를 읽지 못한 파일로 알립니다. run 이 파일 이름을 도는 자리에서 17부의 재귀로 훑기로 그 안의 파일을 모두 찾습니다. 파일을 찾는 차례를 어떻게 정할지도 시험에 적습니다.
  • 실행 파일의 표준 입력에 쓰는 시험 — tests/cli.rs 에 18부의 자식의 표준 입력에 쓰기로, 파일 이름 없이 띄운 grep 에 글을 먹이는 시험을 더합니다.
  • UTF-8 이 아닌 인자 — 1장의 같은 과제입니다. 이 프로그램에서는 패턴도 인자라서, 글이 아닌 패턴을 받았을 때의 일도 정해야 합니다.
