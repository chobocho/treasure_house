주석이 곧 문서다

문서 주석의 기본

godoc(지금은 go doc 과 pkg.go.dev)이 선언 바로 앞의 주석을 그대로 문서로 씁니다. 그래서 이름으로 시작하는 완전한 문장을 씁니다.

rev/rev.go

// Package rev 는 문자열을 룬 단위로 뒤집는다.
package rev

// Reverse 는 s 의 룬 순서를 뒤집은 새 문자열을 돌려준다.
// 바이트가 아니라 룬 단위라 한글·이모지도 깨지지 않는다.
func Reverse(s string) string {
	r := []rune(s)
	for i, j := 0, len(r)-1; i < j; i, j = i+1, j-1 {
		r[i], r[j] = r[j], r[i]
	}
	return string(r)
}
$ go doc ./rev Reverse package rev // import "example.com/effgo/rev" func Reverse(s string) string Reverse 는 s 의 룬 순서를 뒤집은 새 문자열을 돌려준다. 바이트가 아니라 룬 단위라 한글·이모지도 깨지지 않는다.
주석과 선언 사이에 빈 줄을 넣지 말 것 — 빈 줄 하나면 문서 주석이 아니라 그냥 주석이 되어 go doc 에서 사라집니다.

Go 문법에는 세미콜론이 있습니다. 다만 렉서가 줄 끝에 자동으로 넣습니다 — 그 줄의 마지막 토큰이 식별자, 리터럴, 또는 break continue fallthrough return ++ -- ) ] } 중 하나일 때.

규칙 하나에서 Go의 중괄호 위치가 강제됩니다.

✘ 컴파일되지 않는다
if i < f()
{
	g()
}

f() 뒤에 세미콜론이 들어가 if 문이 거기서 끝나 버립니다.

✔ 여는 중괄호는 같은 줄
if i < f() {
	g()
}

취향이 아니라 문법입니다.

세미콜론을 손으로 쓸 자리 — for 의 세 절을 나눌 때, 그리고 한 줄에 짧은 문장을 여러 개 둘 때뿐입니다. 줄 끝에는 절대 쓰지 않습니다.
닫는 중괄호 앞에서는 세미콜론이 생략됩니다. 그래서 go func() { … }() 같은 한 줄 문장이 자연스럽게 쓰입니다.

5장

제어 구조

if · for · switch, 그리고 없는 것들

If

조건에 괄호가 없고, 본문에 중괄호가 반드시 있습니다. 그리고 if 는 초기화문을 받습니다.

if err := file.Chmod(0664); err != nil {
	log.Print(err)
	return err
}
// err 는 여기서 이미 스코프 밖 — 이름이 새어 나가지 않는다

if 가 return 으로 끝나면 else 를 쓰지 않는다

✘ 불필요한 else
f, err := os.Open(name)
if err != nil {
	return err
} else {
	// 본문이 통째로 한 단
	// 더 들여쓰기된다
	use(f)
}
✔ 이른 반환
f, err := os.Open(name)
if err != nil {
	return err
}
defer f.Close()
use(f)
성공 경로가 왼쪽 끝에 남는다 — 오류를 먼저 쳐내면 함수 본문이 계단처럼 들여쓰기되지 않습니다. Go 코드가 if err != nil 로 도배된 것처럼 보이는 진짜 이유입니다.

재선언과 재할당

:= 는 왼쪽에 새 변수가 하나라도 있으면 씁니다. 이미 있는 변수는 재선언이 아니라 대입됩니다.

f, err := os.Open("go.mod")   // f 새로 선언, err 새로 선언
if err != nil {
	return "", err
}
defer f.Close()

buf := make([]byte, 7)
n, err := f.Read(buf)         // n 은 새 변수, err 는 재할당
if err != nil {
	return "", err
}
return string(buf[:n]), nil
$ go run ./cmd/ctrl redeclare="module " err=<nil>
같은 스코프여야 합니다 — 안쪽 블록에서 err := … 를 쓰면 바깥 err 를 가린 새 변수가 생깁니다. 대입한 줄 알았던 값이 블록을 벗어나며 사라지는 흔한 버그입니다.

For — 반복문은 하나뿐 1.22

Go에는 while 도 do-while 도 없습니다. for 하나가 네 가지 꼴로 쓰입니다.

// 1) 세 절 (C 스타일)
for i := 0; i < 10; i++ { }

// 2) 조건만 (while 자리)
for n < limit { }

// 3) 무한
for { }

// 4) range
for k, v := range m { }

정수 범위 1.22 — 원문에 없는 다섯째 꼴

func rangeInt() []int {
	var out []int
	for i := range 5 { // 0,1,2,3,4
		out = append(out, i*i)
	}
	return out
}

// 인덱스가 필요 없으면 이렇게도 쓴다
for range 3 {
	fmt.Println("세 번")
}
$ go run ./cmd/ctrl rangeInt: [0 1 4 9 16]
go fix 의 rangeint 픽서가 세 절 반복문을 for i := range n 으로 자동 변환합니다 — 조건이 i < n 이고 본문에서 i 를 고치지 않을 때만.

루프 변수 — 오래된 함정이 사라졌다 1.22

Go 1.21까지 루프 변수는 반복 전체에서 하나였습니다. 클로저가 그것을 잡으면 전부 같은 변수를 가리켰습니다.

Go 1.21 이하 — [3 3 3]
var fns []func() int
for i := 0; i < 3; i++ {
	fns = append(fns,
		func() int { return i })
}
// i 는 변수 하나 — 끝나면 3
Go 1.22 이상 — [0 1 2]
var fns []func() int
for i := range 3 {
	fns = append(fns,
		func() int { return i })
}
// 반복마다 i 가 새로 생긴다

같은 파일을, go.mod 의 go 줄만 바꿔 가며 돌려 본 결과입니다.

$ cat go.mod module example.com/old121 go 1.21 $ go run . 3 3 3 $ sed -i 's/^go 1.21$/go 1.22/' go.mod && go run . 0 1 2
i := i 는 이제 군더더기입니다 — 예전에 습관처럼 쓰던 재선언 한 줄을 go fix 의 forvar 픽서가 지워 줍니다.
이 변화는 go.mod 의 go 줄을 따릅니다 — go 1.21 로 적힌 모듈은 옛 동작을 유지합니다. 언어 변화를 파일이 아니라 모듈 단위로 켜는 방식이라, 오래된 코드가 새 컴파일러에서 조용히 뜻을 바꾸지 않습니다.

Switch

C의 switch 보다 훨씬 넓습니다. case 값이 상수가 아니어도 되고, 조건을 아예 생략할 수 있으며, 자동으로 다음 case 로 떨어지지 않습니다.

func classify(c byte) string {
	switch { // 조건 없는 switch = if-else 사슬
	case '0' <= c && c <= '9':
		return "숫자"
	case 'a' <= c && c <= 'z', 'A' <= c && c <= 'Z': // 콤마로 여러 값
		return "글자"
	default:
		return "기타"
	}
}

C와 다른 점Go
fallthrough기본은 안 떨어진다. 원하면 fallthrough 를 명시
case 값상수가 아니어도 된다. 콤마로 여러 개
break필요 없다. 라벨과 함께 쓰면 바깥 루프를 끊는다

타입 switch

인터페이스 값 안에 든 구체 타입으로 갈래를 나눕니다. switch t := v.(type) 에서 t 는 가지마다 다른 타입을 가집니다.

func describe(v any) string {
	switch t := v.(type) {
	case nil:
		return "nil"
	case int:
		return fmt.Sprintf("int %d", t) // t 는 int
	case string:
		return fmt.Sprintf("string %q (%d바이트)", t, len(t)) // t 는 string
	case error:
		return "error " + t.Error() // 인터페이스도 case 가 된다
	default:
		return fmt.Sprintf("모르는 타입 %T", t)
	}
}

Defer

defer 는 함수가 어떻게 끝나든 — 정상 반환이든 패닉이든 — 등록한 호출을 실행합니다. 자원 해제를 여는 자리 바로 옆에 적을 수 있습니다.

f, err := os.Open(name)
if err != nil {
	return err
}
defer f.Close() // 여는 줄 바로 밑 — 어느 return 으로 나가든 닫힌다

두 가지 규칙

  1. 인자는 등록 시점에 평가된다 — 실행 시점이 아니라.
  2. LIFO — 나중에 등록한 것이 먼저 실행된다.
for i := range 3 {
	defer fmt.Print(i, " ") // i 는 등록할 때 값이 굳는다

new — 제로값을 담을 자리

new(T) 는 초기화하지 않습니다. 제로값으로 채운 저장소를 잡고 그 주소 *T 를 돌려줍니다. Go의 모든 타입에는 쓸모 있는 제로값이 정의돼 있어서, 대개 그것으로 충분합니다.

type SyncedBuffer struct {

	buf  []byte     // 제로값이 nil 슬라이스 — append 가 바로 된다
}

var p SyncedBuffer     // 바로 쓸 수 있다

p.buf = append(p.buf, 'a')
v.buf = append(v.buf, 'b')

제로값이 쓸모 있게 타입을 설계하라 — sync.Mutex, bytes.Buffer, strings.Builder, nil 슬라이스, nil 맵(읽기 전용)이 전부 그렇습니다. 생성자를 요구하지 않는 타입이 쓰기 편합니다.
Go 1.26: new 가 식을 받는다 — n := new(len(s)) 처럼 쓰면 그 값으로 초기화된 새 변수의 주소가 나옵니다. 값 하나를 포인터로 감싸려고 임시 변수를 만들던 관용구가 없어집니다.

함수에 슬라이스를 넘기면 요소는 공유됩니다 — 그래서 f(s) 안에서 s[0] = 1 은 호출자에게 보입니다. 하지만 s = append(s, x) 는 보이지 않습니다. 헤더는 복사본이니까요. 그래서 append 하는 함수는 새 슬라이스를 반환합니다.

이차원 슬라이스

Go에 진짜 2차원 슬라이스는 없습니다. 슬라이스의 슬라이스를 만드는데, 방법이 둘입니다.

줄마다 할당 — 할당 N번
grid := make([][]int, rows)
for i := range grid {
	grid[i] = make([]int, cols)

flat := make([]int, rows*cols)
grid := make([][]int, rows)
for i := range grid {
	grid[i], flat =
		flat[:cols:cols], flat[cols:]
}

Go의 상수는 컴파일 시각에 만들어지고, 대개 타입이 없습니다. 타입 없는 상수는 임의 정밀도로 계산되다가 쓰이는 자리에서 타입이 정해집니다.

const big = 1 << 40   // int 에 안 들어갈 수도 있지만 상수라서 괜찮다
var f float64 = big   // 여기서 float64 가 된다
fmt.Println(f)        // 1.099511627776e+12

iota — 열거형 만들기

type ByteSize float64

const (
	_           = iota             // 0 은 버린다
	KB ByteSize = 1 << (10 * iota) // 1 << 10
	MB                             // 앞 줄의 식이 반복된다 — 1 << 20
	GB
	TB
)

func (b ByteSize) String() string {
	switch {
	case b >= TB:
		return fmt.Sprintf("%.2fTB", b/TB)
	case b >= GB:
		return fmt.Sprintf("%.2fGB", b/GB)
	case b >= MB:
		return fmt.Sprintf("%.2fMB", b/MB)
	case b >= KB:
		return fmt.Sprintf("%.2fKB", b/KB)
	}
	return fmt.Sprintf("%.2fB", float64(b))
}
$ go run ./cmd/init 9.09TB 976.56KB 512.00B

변수 초기화 — 순서는 의존이 정한다

패키지 수준 변수는 적힌 순서가 아니라 서로 참조하는 순서로 초기화됩니다. 컴파일러가 의존 그래프를 풀어 줍니다.

var (
	c = b + 1 // 먼저 적혔지만 마지막에 평가된다
	a = 1
	b = a + 1
)
$ go run ./cmd/init a,b,c = 1 2 3
순환 참조는 컴파일 오류입니다 — a = b, b = a 는 "initialization cycle" 로 거부됩니다. C처럼 조용히 쓰레기 값이 들어가는 일이 없습니다.
함수 안의 지역 변수는 이 규칙과 무관합니다. 적힌 순서대로, 쓰기 전에 선언돼야 합니다.

init 함수

패키지마다 init() 을 여럿 둘 수 있습니다. 모든 패키지 변수가 평가된 뒤, 임포트된 패키지들이 전부 초기화된 뒤 마지막으로 돕니다.

var mode string

func init() {
	mode = "기본"
	// 여기서 플래그를 검증하거나, 계산으로만 만들 수 있는 표를 채운다
}
init 이 도는 순서
1. 임포트한 패키지들을 (재귀적으로) 먼저 초기화
2. 이 패키지의 변수들을 의존 순서대로 평가
3. 이 패키지의 init() 들을 파일 이름 순으로 실행
4. (모든 패키지가 끝난 뒤) main.main()
init 을 아껴 쓰세요 — 원문 시절보다 지금 더 그렇습니다. 순서가 눈에 보이지 않고, 테스트에서 끄기 어려우며, 프로그램 시작을 느리게 합니다. 대신 명시적인 New 나 sync.OnceValue(1.21)로 첫 사용 시점에 만드는 편이 낫습니다.
정당한 쓰임 — database/sql 드라이버 등록처럼 부수효과 임포트가 목적일 때. 13장에서 다시 봅니다.

포인터 리시버와 값 리시버

메서드는 패키지 안에서 정의한 아무 이름 있는 타입에 붙일 수 있습니다 — 구조체가 아니어도 됩니다.

type ByteSlice []byte

func (s ByteSlice) Len() int { return len(s) } // 값 리시버: 복사본을 받는다

func (p *ByteSlice) Append(data ...byte) { // 포인터 리시버: 원본을 고친다
	*p = append(*p, data...)
}

// io.Writer 를 만족시킨다 — 이제 Fprintf 의 대상이 된다
func (p *ByteSlice) Write(data []byte) (int, error) {
	*p = append(*p, data...)
	return len(data), nil
}
var b ByteSlice
b.Append('G', 'o')          // (&b).Append 로 자동 변환된다
fmt.Fprintf(&b, " %d.%d", 1, 26)
fmt.Printf("%s (len=%d)\n", b, b.Len())
$ go run ./cmd/iface Go 1.26 (len=7)

구조체가 크다포인터 — 복사 비용
sync.Mutex 등을 품는다포인터 — 값 복사는 락을 망가뜨린다 (go vet 이 경고)
작고 불변인 값값 — time.Time, ByteSize
확신이 없다한 타입 안에서는 섞지 말 것 — 전부 포인터로
메서드 집합이 다릅니다 — *T 는 값·포인터 메서드를 전부 가지지만 T 는 값 메서드만 가집니다. 그래서 Write 가 포인터 리시버면 &b 만 io.Writer 입니다. 인터페이스 만족 여부가 여기서 갈립니다.

Go 설계의 중심

인터페이스 — 만족은 선언하지 않는다

Java의 implements 도, C++의 상속도 없습니다. 메서드를 갖고 있으면 그냥 만족합니다. 그래서 인터페이스를 쓰는 쪽에서 나중에 정의할 수 있습니다.

정의 (io 패키지)
type Writer interface { Write(p []byte) (int, error) }
◀▶
구현 (내 패키지)
func (p *ByteSlice) Write( data []byte) (int, error)
인터페이스는 작을수록 좋습니다 — 표준 라이브러리에서 가장 많이 쓰이는 것이 메서드 하나짜리 io.Reader·io.Writer·fmt.Stringer·error 입니다. "인터페이스가 클수록 추상화는 약해진다"는 Go 격언이 여기서 나옵니다.
인터페이스는 쓰는 쪽에 둡니다 — 구현하는 패키지가 아니라 소비하는 패키지가 필요한 최소 메서드만 선언합니다. 원문에는 없지만 이후 커뮤니티에서 굳어진 관례입니다.

타입 변환

Go에는 암묵적 변환이 없습니다. 하지만 기반 타입이 같으면 명시적 변환이 공짜입니다.

type Sequence []int

// 표준 정렬을 쓰려고 잠시 []int 로 옷을 갈아입는다
func (s Sequence) Sorted() Sequence {
	c := slices.Clone([]int(s)) // 변환 — 복사도 재할당도 아니다
	slices.Sort(c)
	return Sequence(c)
}
원문의 이 절은 sort.IntSlice 를 씁니다 — 지금은 slices.Sort 하나면 되고, 정렬 인터페이스(Len/Less/Swap)를 손으로 구현할 일이 거의 없습니다.
people := []Person{{"윤", 31}, {"김", 24}, {"박", 45}}
slices.SortFunc(people, func(a, b Person) int { return a.Age - b.Age })

SortFunc 의 비교 함수는 bool 이 아니라 int 를 돌려줍니다 — 음수·0·양수. sort.Slice 의 less bool 과 헷갈리기 쉽습니다. 정수 뺄셈은 넘침 위험이 있으니 일반적으로는 cmp.Compare(a.Age, b.Age) 를 쓰세요.

타입 단언

인터페이스 값에서 구체 타입을 꺼냅니다. 콤마 ok 꼴을 쓰지 않으면 실패 시 패닉입니다.

func stringify(v any) string {
	if s, ok := v.(fmt.Stringer); ok { // 인터페이스로도 단언할 수 있다
		return "Stringer -> " + s.String()
	}
	if s, ok := v.(string); ok {
		return "string -> " + s
	}
	return fmt.Sprint(v)
}

임베딩

필드에 이름 없이 타입만 적으면 그 타입의 메서드가 바깥 타입으로 올라옵니다.

type Logger struct{ prefix string }

func (l *Logger) Log(msg string) string { return l.prefix + ": " + msg }

type Job struct {
	Command string
	*Logger // 임베딩 — 필드 이름이 "Logger" 가 된다
}

j := &Job{Command: "build", Logger: &Logger{prefix: "job"}}
j.Log("시작")        // Logger 의 메서드를 Job 이 그대로 쓴다
j.Logger.Log("직접") // 원래 자리로도 부를 수 있다

인터페이스도 임베딩된다

type ReadWriter interface {
	io.Reader // 메서드 목록을 적는 대신 인터페이스를 넣는다
	io.Writer
}
상속이 아닙니다 — 임베딩된 Logger 의 메서드가 Job 을 볼 수는 없습니다. 리시버는 여전히 *Logger 입니다. 가상 함수 재정의(virtual dispatch)가 아니라 자동으로 써 주는 위임 코드입니다.

이름 충돌

바깥 타입의 메서드가 더 얕은 깊이에 있으면 안쪽을 가립니다. 같은 깊이에서 충돌하면 그 이름을 쓰는 순간 컴파일 오류입니다.

func (j *Job) Log(msg string) string {
	return "[" + j.Command + "] " + j.Logger.Log(msg) // 감싸고 위임한다
}

동시성

고루틴 · 채널 · 그 뒤에 온 것들

메모리를 공유해 통신하지 말고, 통신해서 메모리를 공유하라

원문에서 가장 많이 인용되는 문장입니다. 뜻은 이렇습니다 — 값을 여러 고루틴이 동시에 만지고 락으로 지키는 대신, 값을 채널로 넘겨 한 번에 한 고루틴만 갖게 하라.

고루틴 A→ 채널→ 고루틴 B

값의 소유권이 채널을 따라 옮겨 간다 — 그 순간 경합이 존재할 수 없다

"동시성은 병렬성이 아니다" — 동시성은 독립적으로 실행되는 조각으로 문제를 구성하는 것이고, 병렬성은 그것을 실제로 동시에 돌리는 것입니다. 잘 나눈 동시적 설계는 CPU가 하나여도 옳게 돌아갑니다.
락을 쓰지 말라는 뜻은 아닙니다 — 원문도 sync.Mutex 를 씁니다. 참조 카운트나 작은 맵을 지키는 데는 뮤텍스가 더 낫습니다. 채널은 소유권과 흐름을 다룰 때 값을 합니다.

이름이 새로 필요했던 이유: 스레드도, 코루틴도, 프로세스도 아니기 때문입니다. 같은 주소 공간에서 도는, 스택이 자라는 아주 싼 실행 단위입니다.

go list.Sort() // 끝나기를 기다리지 않고 다음 줄로 간다

// 익명 함수로 감싸는 것이 흔한 꼴
go func() {
	defer close(done)
	work()
}()

채널의 채널

채널도 값이라 채널을 채널로 보낼 수 있습니다. 요청에 응답 채널을 실어 보내면 각 클라이언트가 자기 답만 받습니다 — 콜백 없는 비동기 호출입니다.

type request struct {
	args   []int
	result chan int // 응답이 돌아올 곳
}

func server(queue <-chan *request) { // 방향 있는 채널: 받기 전용
	for req := range queue {
		sum := 0
		for _, v := range req.args {
			sum += v
		}
		req.result <- sum
	}
}

queue := make(chan *request, 4)
go server(queue)

req := &request{args: []int{1, 2, 3, 4}, result: make(chan int)}
queue <- req
fmt.Println("합 =", <-req.result)

누설 버퍼

원문의 마지막 동시성 예제. 자유 목록(free list)을 채널로 만드는 요령입니다. 락도, 별도 자료 구조도 없습니다.

var freeList = make(chan *Buffer, 100)

func client() {
	var b *Buffer
	select {
	case b = <-freeList: // 재활용할 것이 있으면 가져온다
	default:
		b = new(Buffer) // 없으면 새로 만든다
	}
	load(b)
	serverChan <- b
}

func server() {
	for b := range serverChan {
		process(b)
		select {
		case freeList <- b: // 자리가 있으면 돌려준다
		default:
			// 가득 찼다 — 그냥 버린다. GC가 알아서 가져간다
		}
	}
}
select 의 default 가 핵심입니다 — 채널 연산을 절대 막히지 않게 만듭니다. "있으면 쓰고 없으면 만들고, 자리 있으면 돌려주고 없으면 버린다"는 정책이 여덟 줄에 들어갑니다. 그래서 "새는(leaky) 버퍼"입니다.
지금이라면 sync.Pool — 같은 목적의 표준 타입이 Go 1.3에 들어왔고, GC와 협력해 주기마다 비웁니다. 다만 원문의 이 예제는 select/default 관용구를 배우기에 여전히 좋은 교재입니다.

Recover

recover 는 defer 된 함수 안에서만 뜻이 있습니다. 되감기를 멈추고 패닉 값을 돌려줍니다.

func safeDivide(a, b int) (q int, err error) { // 결과에 이름이 필요하다
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("복구: %v", r) // 패닉을 에러로 바꿔 내보낸다
		}
	}()
	return a / b, nil
}
$ go run ./cmd/errs safeDivide: 0 복구: runtime error: integer divide by zero safeDivide: 3 <nil>
패턴은 하나뿐입니다 — 패키지 경계에서 패닉을 잡아 에러로 바꾸기. 재귀 파서처럼 깊은 곳에서 빠져나와야 할 때 내부적으로 panic 을 쓰고, 공개 함수에서 recover 로 감싸 error 를 돌려줍니다. encoding/json 이 실제로 이렇게 했습니다.
남의 패닉까지 삼키지 마세요 — 원문의 조언대로, 잡은 값이 내가 던진 타입인지 확인하고 아니면 panic(r) 로 다시 던지세요. 그렇지 않으면 진짜 버그(nil 역참조)가 조용히 에러로 둔갑합니다.
고루틴 경계를 넘지 못합니다 — go f() 안에서 난 패닉은 그 고루틴 안에서 잡아야 합니다. 부모의 recover 는 그것을 보지 못하고 프로그램이 죽습니다.

		Handler:           mux,

		ReadTimeout:       10 * time.Second,
		WriteTimeout:      10 * time.Second,
		IdleTimeout:       60 * time.Second,
	}
}
func main() {
	srv := newServer("127.0.0.1:8099")

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
	defer stop()

	go func() {
		slog.Info("듣는 중", "addr", srv.Addr)
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			slog.Error("서버 종료", "err", err)
			os.Exit(1)
		}
	}()

	<-ctx.Done() // Ctrl+C 를 기다린다
	slog.Info("정리 중")

	shutCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutCtx); err != nil { // 진행 중인 요청을 끝까지 처리한다
		slog.Error("정리 실패", "err", err)
	}
}

)
func Words(s string) iter.Seq[string] {
	return func(yield func(string) bool) {
		for _, w := range strings.Fields(s) {
			if !yield(w) {
				return // 소비자가 break 하면 여기로 온다
			}
		}
	}
}

func Enumerate[T any](s []T) iter.Seq2[int, T] {
	return func(yield func(int, T) bool) {
		for i, v := range s {
			if !yield(i, v) {
				return
			}
		}
	}
}

퀴즈 1

Q. Go 1.22 이상에서 아래 코드는 무엇을 찍는가? 그리고 Go 1.21에서는?

var fns []func() int
for i := range 3 {
	fns = append(fns, func() int { return i })
}
for _, f := range fns {
	fmt.Print(f(), " ")
}
A. Go 1.22 이상에서는 0 1 2. Go 1.21 이하라면 애초에 range 3 이 컴파일되지 않지만, 같은 뜻의 세 절 반복문으로 바꾸면 3 3 3 이 나옵니다. 루프 변수가 반복마다 새로 생기느냐의 차이이고, 이 동작은 go.mod 의 go 줄이 결정합니다.

퀴즈 2

Q. 아래 두 줄의 차이는? 어느 쪽이 errors.Is(err, ErrEmpty) 를 true 로 만드는가?

return fmt.Errorf("parse: %v", ErrEmpty)
return fmt.Errorf("parse: %w", ErrEmpty)
A. %w 만 true. %v 는 에러의 문자열만 베껴 넣어 원인 사슬이 끊깁니다. 겉보기 메시지는 똑같아서 눈으로는 구별되지 않고, 호출자가 errors.Is 로 분기하려는 순간에야 드러납니다. 반대로 내부 구현을 숨기고 싶다면 일부러 %v 로 끊습니다.

퀴즈 3

Q. 컨테이너에 --cpus=2 를 걸고 64코어 호스트에 배포했다. Go 1.24로 빌드한 서버와 Go 1.25로 빌드한 서버의 runtime.GOMAXPROCS(0) 은 각각 무엇인가?

A. Go 1.24는 64(NumCPU), Go 1.25는 2. 1.25부터 런타임이 cgroup CPU 쿼터와 어피니티 마스크를 함께 봅니다. 예전에는 automaxprocs 같은 라이브러리로 메웠고, 안 메우면 스케줄러가 있지도 않은 코어를 두고 컨텍스트 스위칭을 했습니다. 참고로 GOMAXPROCS 환경 변수를 주거나 runtime.GOMAXPROCS(n) 을 부르면 이 자동 조정이 꺼집니다.

퀴즈 4

Q. ByteSlice 의 Write 를 포인터 리시버로 정의했다. var b ByteSlice 일 때 fmt.Fprintf(b, …) 는 컴파일되는가?

A. 아니오. 컴파일러가 이렇게 막습니다:
cmd/mset/main.go:14:14: cannot use b (variable of slice type ByteSlice) as io.Writer value in argument to fmt.Fprintf: ByteSlice does not implement io.Writer (method Write has pointer receiver)
*ByteSlice 만 io.Writer 의 메서드 집합을 갖습니다. fmt.Fprintf(&b, …) 로 써야 합니다. b.Write(…) 처럼 직접 호출할 때는 컴파일러가 (&b).Write 로 바꿔 주지만, 인터페이스에 담을 때는 그 자동 변환이 없습니다. 주소를 얻을 수 없는 값(맵 원소 등)이 있기 때문입니다.
