클라이언트 — create_client 와 StreamResponse

메서드 열하나 → ClientConfig 여덟 칸 → 카드에서 클라이언트까지 → 막는 호출도 반복자 → 스트림은 이벤트 그대로 → 우리 httpx → 인터셉터 → 카드만 받기 → 오류는 두 갈래 → 오류 넷의 답 → 모르는 필드 실험 → 실험의 와이어 → 클라이언트는 엄격했다 → 기획 에이전트의 위임 → 정리

클라이언트 추상 메서드 열하나 — close 를 빼면 서버 처리기의 on_* 와 이름으로 짝이다

3~6부의 ask CLI 가 써 온 클라이언트를 이번에는 만드는 쪽에서 봅니다. 설치본의 추상 클래스 Client(client/client.py)에 채워야 할 메서드를 묻고, 4장의 처리기 메서드와 이름으로 짝지었습니다.

  • A2A 메서드 하나에 클라이언트 메서드 하나이고, close 만 짝이 없습니다(—). 다만 send_message 하나가 서버의 on_message_send 와 on_message_send_stream 둘을 맡습니다 — 어느 쪽으로 보낼지는 클라이언트가 고릅니다(조금 뒤).
  • 모두 async 입니다. send_message·subscribe 는 비동기 반복자, 나머지는 값 하나를 돌려줍니다. 실제 구현은 BaseClient(client/base_client.py) 하나뿐이고, 전송(JSON-RPC·REST·gRPC)은 그 안에 끼우는 부품입니다.

create_client 는 팩토리를 지어 카드를 읽고, 인터페이스를 골라 전송을 끼운다

이제 부르는 쪽입니다. 상대는 7장에서 완성할 숙소 에이전트(agents/lodging.py, 탭 뒤)이고, 같은 견적 요청을 막는 호출과 스트림으로 한 번씩 보냅니다.

막는 호출도 async for 다 — StreamResponse 하나가 나오고 끝난다

--no-stream 은 ClientConfig(streaming=False) 입니다. 답을 받은 뒤 같은 작업을 get_task 로 한 번 더 읽었습니다.

  • 전송이 돌려준 것은 SendMessageResponse(oneof task·message)인데, BaseClient 가 그것을 StreamResponse 에 옮겨 담아 하나만 내줍니다(base_client.py:80 "so that the client always sees the same iterator"). 그래서 막는 호출이든 스트림이든 받는 코드는 같습니다 — 가르는 법은 4부의 oneof payload 그대로입니다.
  • 답이 task 와 message 어느 것도 아니면 ValueError('Response has neither task nor message') 입니다(base_client.py:88).

스트림은 이벤트를 하나씩 그대로 준다 — Task 로 접어 주지 않는다

같은 요청을 스트림으로 보냈습니다. 이벤트마다 show 가 한 줄씩 찍습니다.

문서 문자열과 다르다 — Client.send_message 의 문서 문자열은 "Client will aggregate update events" 라고 적었지만(client.py:132), BaseClient 는 전송이 읽은 이벤트를 받은 차례대로 넘길 뿐입니다. 첫 task 는 SUBMITTED·아티팩트 0개 그대로이고, 끝난 모습은 get_task 로 다시 읽어야 보입니다. 스트림에서 상태와 아티팩트를 손으로 접는 법은 10부입니다.

httpx 연결은 우리가 넘길 수 있다 — 팩토리는 거기에 A2A-Version 을 심고, close 는 그것까지 닫는다

헤더를 되돌려 주는 5장의 실험 서버를 상대로, 우리가 지은 httpx.AsyncClient 를 ClientConfig(httpx_client=…) 로 넘겼습니다. 그 서버에는 카드 경로가 없어 create_client 에 카드 객체를 바로 줍니다.

  • ClientFactory 생성자가 받은 연결의 기본 헤더에 A2A-Version: 1.0 을 setdefault 로 넣습니다(client_factory.py:82). 우리 객체가 바뀐 것입니다 — 이 연결로 다른 곳을 불러도 그 헤더가 따라갑니다.
  • client.close() 는 전송의 close 를 부르고, JSON-RPC 전송은 httpx_client.aclose() 를 합니다(transports/jsonrpc.py:316). 연결 하나를 클라이언트 여럿이 나눠 쓰면 하나를 닫는 순간 모두 못 씁니다.

인터셉터는 before·after 둘 — 헤더는 context.service_parameters 에 넣는다

모든 호출에 같은 일을 끼우는 자리입니다. ClientCallInterceptor(client/interceptors.py)를 상속해 두 메서드를 채우고 create_client(…, interceptors=[…]) 로 겁니다.

  • ClientCallContext 는 호출 하나의 꾸러미입니다 — state, timeout, service_parameters. 전송은 service_parameters 를 그대로 HTTP 헤더로, timeout 을 httpx 시간 제한으로 씁니다(transports/http_helpers.py:43). 인터셉터 없이 send_message(…, context=ClientCallContext(…)) 로 호출마다 줄 수도 있습니다.
  • 앞 슬라이드 출력의 x-workshop-team=general-affairs 가 이 헤더가 서버의 call_context.state["headers"] 까지 간 증거입니다. after 가 본 것은 전송의 답 SendMessageResponse 입니다 — StreamResponse 로 옮겨 담기 전입니다.
  • SDK 가 준비한 인터셉터는 카드의 보안 스킴을 보고 토큰을 다는 AuthInterceptor 하나입니다(client/auth/interceptor.py, 12부).

카드만 받을 때는 A2ACardResolver — 팩토리를 거치지 않으면 A2A-Version 도 없다

여러 에이전트의 카드를 먼저 모아 고르고 싶을 때(15부의 기획 에이전트처럼)는 카드 읽기만 따로 씁니다: await A2ACardResolver(http, url).get_agent_card(). 숙소 에이전트 앞 탭이 이 장의 요청 열 개를 모두 봤습니다. 요청 줄과 판 헤더만 추렸습니다.

  • A2A-Version 이 없는 요청은 GET /.well-known/agent-card.json 하나뿐입니다. 오류 예제가 ③ 앞에서 맨 httpx.AsyncClient() 로 해석기를 부른 자리입니다 — 판 헤더는 해석기가 아니라 팩토리가 연결에 심는 것이라서입니다.
  • 해석기는 카드를 ignore_unknown_fields=True 로 읽고(card_resolver.py:27), 옛 v0.3 카드의 url·preferredTransport 를 supportedInterfaces 로 고쳐 읽습니다(같은 파일의 _handle_connection_fields_compatibility). 이 너그러움은 조금 뒤 결과를 읽는 쪽과 대비됩니다.

오류 넷을 일부러 — 카드가 없다, 카드 경로가 없다, 작업이 없다, 보낼 곳이 없다

무엇을 잡아야 하는지 알려면 무엇이 던져지는지부터 봐야 합니다. 모두 A2AError 로 잡고, 실제 클래스와 그것이 A2AClientError(client/errors.py) 갈래인지 찍었습니다.

오류는 두 갈래 — 전송에서 난 것은 A2AClientError, 서버가 답한 A2A 오류는 그 클래스 그대로

  • ①②는 카드 해석기의 AgentCardResolutionError, ④는 HTTP 404 를 감싼 A2AClientError 입니다. 둘 다 A2AClientError 갈래이고, ②에는 status_code 가 붙습니다.
  • ③은 서버의 JSON-RPC 오류 -32001 을 전송이 JSON_RPC_ERROR_CODE_MAP 을 거꾸로 찾아 TaskNotFoundError 로 되살린 것입니다(transports/jsonrpc.py 의 _create_jsonrpc_error) — 서버 처리기가 던지던 4장의 그 클래스입니다. 이것은 A2AClientError 가 아닙니다. 표에 없는 코드만 A2AClientError("JSON-RPC Error …") 가 됩니다.
  • 그래서 "아무 A2A 오류" 를 잡으려면 A2AError(a2a.utils.errors) 를 잡아야 합니다. 그것으로도 못 잡는 예외가 하나 더 있습니다 — 다음 실험입니다.

열린 물음 — 서버는 모르는 필드를 넘기는데, 파이썬 클라이언트는?

§5.7: "Implementations SHOULD ignore unrecognized fields in messages, allowing for forward compatibility". 세 서버가 그렇게 넘기는 것은 4부에서 봤습니다. 그런데 2장에서 본 대로 파이썬 클라이언트의 전송은 답을 ignore_unknown_fields 없이 읽습니다. 작은 서버를 세워 확인합니다.

실험 여섯 — 받은 글이 실험 이름입니다. plain 은 정상 답, envelope 는 JSON-RPC 봉투에 serverTime 키를 더합니다. 카드에도 createdAt 을 하나 넣었습니다. 클라이언트(07/strict.py)는 여섯을 막는 호출로 한 번, 스트림으로 한 번 보내고, A2AClientError 와 protobuf 의 ParseError 를 잡아 찍습니다.

와이어 — task 안에 createdAt 하나, 나머지는 정상 답과 같다

클라이언트는 실험 이름을 글 하나에 담아 보냅니다. 탭이 본 task 실험의 막는 호출에서 답 쪽만 잘랐습니다 — 스펙에 없는 필드 하나가 끼었습니다.

카드는 통과했다 — 이 주고받음 앞에 클라이언트는 createdAt 이 든 카드를 받아 아무 탈 없이 클라이언트를 만들었습니다(해석기는 너그럽게 읽습니다).

클라이언트는 엄격했다 — 모르는 필드 하나에 ParseError, 그것도 A2AClientError 가 아니다

  • 여섯 중 넷이 실패했습니다. Task 안, 그 안쪽 status, task 옆, 그리고 모르는 enum 이름(TASK_STATE_PAUSED) — 막는 호출(SendMessageResponse)과 스트림(StreamResponse)이 똑같습니다. 전송이 json_format.ParseDict(result, …) 를 옵션 없이 부르기 때문입니다(transports/jsonrpc.py:83 외 메서드마다).
  • 봉투의 serverTime 은 통과했습니다. 봉투는 JSONRPC20Response(**data) 가 받는데, 그 생성자가 모르는 키워드를 그냥 흘려 보냅니다.
  • 예외는 google.protobuf.json_format.ParseError 그대로 올라옵니다. 앞에서 권한 except A2AError 로는 잡히지 않습니다.
§5.7 의 SHOULD 를 클라이언트 쪽은 지키지 않는다 — 파이썬 SDK 1.2.2 의 서버(jsonrpc_dispatcher.py:300)와 카드 해석기는 모르는 필드를 넘기고, 결과를 읽는 클라이언트 전송만 거절합니다. 상대 서버가 더 새 판의 필드를 보내기 시작하면 파이썬 클라이언트가 먼저 멈춘다는 뜻입니다. 남의 서버를 부르는 코드라면 ParseError 도 함께 잡아 둡니다. 같은 실험을 TS·Go 클라이언트로 하는 것은 8·9부의 같은 장입니다.

기획 에이전트의 위임 — 카드로 바로, 막는 호출, 토큰은 우리 httpx 의 헤더로

완성 에이전트 가운데 클라이언트를 쓰는 것은 기획 에이전트입니다(15부). 동료에게 일을 맡기는 부분이 이 장의 손잡이를 거의 다 씁니다.

  • 카드는 이미 모아 둔 것(c)이라 create_client(c, …) 로 바로 만들고, streaming=False 로 막는 호출을 씁니다 — 끝나거나 멈춘 Task 하나면 되기 때문입니다.
  • 토큰은 인터셉터 대신 연결의 기본 헤더로 답니다. 호출마다 연결을 새로 짓고 client.close() 로 함께 닫으니 나눠 쓰는 문제가 없습니다.

6장 퀴즈

Q. 오류 처리를 이렇게 썼습니다: except A2AClientError: 다시 시도. 상대 서버가 ① 없는 작업이라고 -32001 로 답했을 때, ② 답의 Task 에 스펙에 없는 필드를 하나 더 실어 보냈을 때, 이 except 는 각각 예외를 잡습니까?

A. 둘 다 못 잡습니다. ①은 TaskNotFoundError 로 오는데 이것은 A2AError 갈래이지 A2AClientError 가 아닙니다(client_errors.py 의 ③). ②는 protobuf 의 ParseError 가 그대로 올라오고, strict.py 가 찍었듯 ParseError 는 A2AClientError 인가: False 입니다.

물음은 차례가 있는 dict 하나 — 글로 온 답은 정규식 셋으로 읽는다

완성판 머리의 물음 목록과, 되물음에 글로 답한 것을 DataPart 와 같은 dict 로 바꾸는 함수입니다. 정규식은 기획 에이전트도 쓰는 업무 규칙의 것입니다(SCENARIO §2.5).

  • dict 의 차례가 묻는 차례입니다. 빠진 것이 여럿이면 첫째만 글로 묻고, 빠진 목록 전부는 DataPart {"missing": […]} 로 함께 보냅니다 — 사람은 글을, 프로그램(기획 에이전트)은 데이터를 읽습니다.
  • 읽은 값은 문자열("30")입니다. DataPart 로 온 수(30.0)와 함께 as_ints 가 정수로 맞춥니다(2장).

3단계 실행기 — 이력을 모두 합쳐 듣고, 모자라면 INPUT_REQUIRED

  • begin 이 돌려준 task.history 에는 지난 마디와 이번 메시지가 다 있습니다. DataPart 를 먼저 합치고(data_of), 글에서 찾은 것을 그 위에 덮습니다.
  • requires_input 뒤에 return 합니다. 실행기의 약속(3장, 38–49줄)대로 다음 메시지가 오면 처리기가 execute 를 다시 부릅니다 — 실행기가 기다리며 붙들고 있는 것이 아닙니다.
  • 무엇을 들었는지 마디마다 로그로 찍게 했습니다. 다음 슬라이드에서 그 로그가 결함을 보여 줍니다.

3단계는 사용자가 말한 적 없는 날짜로 견적을 냈다

대본: 처음엔 아무것도 주지 않고("숙소 부탁합니다"), 날짜를 묻는데 인원을, 다시 묻는데 박 수를 답하고, 마지막에야 날짜(11월 6일)를 줍니다. 3단계 서버와 완성판에 같은 네 마디를 보냅니다(ask 는 작업이 끝나면 남은 말을 버립니다).

무엇을 들었나 — 셋째 마디의 이력에는 에이전트의 물음이 들어와 있었다

3단계 서버가 마디마다 찍은 "들은 것" 입니다.

  • 둘째 마디에는 "30" 하나뿐입니다. 셋째 마디에는 사용자가 한 번도 말하지 않은 "2026-10-30" 과, 사용자가 보낸 적 없는 키 "missing" 이 들어왔습니다. 첫 물음의 글 "(예: 2026-10-30)" 과 그 DataPart 를 답으로 읽은 것입니다.
  • 둘째 마디에 물음이 없던 것은 파이썬 SDK 가 지난 물음(status.message)을 다음 사용자 메시지가 저장될 때에야 이력으로 옮기기 때문입니다(5부). 결함은 언제나 있었고, 셋째 마디에 드러났을 뿐입니다.
이 결함은 실제로 있었다 — 세 언어의 완성 숙소 에이전트가 처음에는 이렇게 이력 전부를 들었고, 6부를 쓰며 맨손 서버를 대조하다 발견해 고쳤습니다. 예시가 든 물음은 흔하니, 이력을 읽는 실행기는 언제나 역할부터 거릅니다.

완성판의 실행기 — 다른 것은 heard 를 고르는 한 줄이다

agents/lodging.py 의 LodgingExecutor.execute 를 두 토막으로 실었습니다 — 들은 것을 모아 되묻는 앞(executor)과 견적을 내는 뒤(quote). 3단계와 견주면 role == Role.ROLE_USER 로 거르는 줄, 견적 요약 글 파트, 서버 로그만 다릅니다.

같은 네 마디 — 완성판은 날짜를 세 번 묻고, 11월 6일의 춘천을 골랐다

  • 빠진 목록이 ["date","nights","headcount"] → ["date","nights"] → ["date"] 로 줄고, 묻는 글은 늘 첫째인 날짜입니다. 마지막 마디의 2026-11-06 으로 끝났습니다.
  • 답은 골든의 cheapest-wins 사례(11월 6일 30명 → 춘천 5실 1,860,000원)와 같습니다. 3단계의 2,100,000원은 10월 30일의 답이었습니다.
  • 이어 말하기 뒤에 task WORKING 줄이 없는 것은 파이썬 SDK 서버에서는 이어 말하기에 Task 를 다시 싣지 않기 때문입니다(6부).

골든 열세 사례를 A2A 너머로 — 업무 규칙 시험과 같은 기대값

업무 규칙은 workshop/test_domain.py 가 이미 골든 파일(ex/fixtures/golden/domain.json)로 시험합니다. 여기서는 같은 chooseLodging 사례를 떠 있는 에이전트에 SendMessage 로 보내, 아티팩트의 DataPart(또는 거절 까닭)를 기대값과 견줍니다.

13/13 — 완료 여덟, 거절 다섯, 까닭까지 골든과 같다

  • 거절에는 두 종류가 있습니다. 문 닫은 날·넘치는 인원은 "가능한 숙소가 없습니다", 0명·0박은 업무 규칙의 입력 검사가 낸 "인원과 박 수는 1 이상이어야 합니다" 입니다. 둘 다 아티팩트 없이 REJECTED, 까닭은 상태 메시지에 있습니다(5부).
  • zero-headcount 는 되묻기에 걸리지 않습니다. 빠졌는지는 키가 있는지로 보기 때문에(k not in req), 0 은 "들었다" 로 치고 업무 규칙에 넘깁니다.

서버 로그 — 마디마다 한 줄, 묻고 고르고 거절한 것이 남는다

완성판이 이 장에서 받은 열일곱 마디(네 마디 대본 + 골든 열세 사례)의 로그입니다.

  • 완성판은 마디마다 한 줄을 찍습니다(print(…, flush=True) — 캡처가 차례를 잃지 않게). TS·Go 완성판도 같은 글을 찍도록 맞춰 두었습니다.
  • 날짜·박 수는 DataPart 로, 인원만 글로 답하는 3~6부의 대본을 이 완성판에 보낸 결과는 6부에 있습니다. 그 대본이 3×3 대조의 기준이었고(6부), 이 장의 네 마디 대본은 거기에 "물음과 어긋난 답" 을 더한 것입니다.

Q. 3단계 서버의 셋째 마디 로그에는 사용자가 보낸 적 없는 키 "missing" 이 있습니다. 이 키는 어느 메시지의 어느 파트에서 왔고, 완성판에서는 왜 생기지 않습니까?

A. 에이전트 자신이 첫 물음에 실은 DataPart {"missing": ["date","nights","headcount"]} 입니다(대본의 첫 status INPUT_REQUIRED 줄). 그 물음이 이력으로 옮겨진 뒤 3단계의 data_of(*heard) 가 이력의 모든 DataPart 를 합치면서 들어왔습니다(로그). 완성판은 heard 를 ROLE_USER 메시지로만 고르므로, 에이전트 메시지의 글("예: 2026-10-30")도 DataPart 도 듣지 않습니다.

8장

시험 — SDK 서버를 네트워크 없이 프로세스 안에서

이 venv 의 시험 도구 → 본보기는 골든 시험 → 처리기 시험 틀 → 시험 넷 → 초록불 → 3단계에 돌리면 빨간불 → HTTP 층은 TestClient → SDK 클라이언트까지 ASGITransport 로 → 두 층의 결과 → 시험에서 조심할 것 → 정리

시험 도구는 표준 라이브러리의 unittest — pytest 는 이 venv 에 없다

무엇으로 시험할지 고르기 전에, 깔려 있는 것을 물었습니다. 9장에서 쓸 선택 기능의 패키지도 함께 봅니다.

  • pytest 는 SDK 의 어느 extra 에도 없고 이 책도 깔지 않았습니다. 그래서 업무 규칙 시험(make golden)처럼 unittest 를 씁니다. 비동기 시험은 unittest.IsolatedAsyncioTestCase 입니다.
  • Starlette 의 TestClient 는 http-server extra 로 이미 와 있고, 그 밑의 httpx 는 SDK 의 의존입니다. 이 둘이 HTTP 층 시험을 맡습니다.
층무엇을 부르나도구
처리기handler.on_message_send(…) — JSON 도 HTTP 도 없이IsolatedAsyncioTestCase
ASGI 앱라우트까지 붙인 Starlette 앱에 JSON-RPC 본문starlette.testclient.TestClient
클라이언트 + 앱SDK 클라이언트 → 앱, 포트 없이httpx.ASGITransport

본보기는 업무 규칙의 골든 시험 — 사례마다 subTest 하나

세 언어의 업무 규칙은 같은 골든 파일을 읽어 시험합니다(SCENARIO §4). 파이썬 쪽 workshop/test_domain.py 의 중심입니다.

  • 사례 하나가 틀려도 나머지를 계속 봅니다(subTest). 에이전트 시험도 이 모양을 그대로 따라, 같은 chooseLodging 사례를 이번에는 요청 처리기 너머로 보냅니다.
  • 골든 파일이 기대값의 하나뿐인 원본이라, 에이전트 시험에 숫자를 다시 적지 않습니다.

시험 틀 — 시험마다 새 처리기, 말 한마디는 say() 하나

4장에서 HTTP 없이 처리기를 부른 방법을 시험 틀로 옮겼습니다. 실행기 클래스는 속성으로 두어 하위 클래스가 바꿔 끼울 수 있게 했습니다.

  • asyncSetUp 이 시험마다 새 처리기·새 메모리 저장소를 짓습니다. 시험끼리 작업을 나눠 갖지 않습니다.
  • IsolatedAsyncioTestCase 는 asyncio 를 디버그 모드로 돌립니다(unittest/async_case.py:137, Runner(debug=True, …)). 디버그 모드는 오래 걸린 콜백마다 경고를 남기는데, 이 느린 기계에서는 그 줄이 실행마다 달라 꺼 두었습니다. SDK 로거(a2a)도 ERROR 위만 남겼습니다 — 처리기는 정상 흐름에서도 타이밍에 따라 WARNING 하나("Dispatcher task is not running…", server/events/event_queue_v2.py:173)를 남깁니다.

시험 넷 — 골든, 첫 되물음, 이어 말하기, 사용자 말만 듣기

  • 답은 Task 객체 그대로입니다. 상태, 상태 메시지의 DataPart, 아티팩트를 2장의 도우미로 꺼내 견줍니다. id 는 실행마다 다르니 견주지 않습니다.
  • data == case["expected"] 는 DataPart 의 수가 실수(2100000.0)여도 참입니다 — 파이썬에서 2100000.0 == 2100000 이라서입니다(2장).

초록불 — 넷 다 ok, 골든 열세 사례는 한 시험 안에서

걸린 시간은 가렸다 — unittest 가 찍는 "Ran 4 tests in …" 뒤의 시간은 실행마다 다릅니다. 이 파일의 main() 은 그 줄의 숫자만 <초> 로 바꿔 찍는 출력 통로(NoClock)를 시험 실행기에 줍니다. 나머지 글자는 unittest 그대로입니다.

같은 시험을 3단계에 — 빨간불은 하나, 정상 대본의 시험은 결함을 못 잡았다

시험은 그대로 두고 실행기만 7장의 3단계로 바꿨습니다.

  • 골든 열세 사례와 이어 말하기 시험은 3단계에서도 통과했습니다. 물음보다 앞서 답을 다 주거나 묻는 것에 바로 답하는 대본에서는 결함이 드러나지 않기 때문입니다.
  • 물음과 어긋나게 답하는 test_hears_only_the_user 만 'gapyeong-solsup' != 'chuncheon-lake' 로 떨어졌습니다 — 7장에서 손으로 본 그 결함입니다. 다중 턴 에이전트의 시험에는 "묻는 것과 다른 것을 답하는" 대본이 하나쯤 있어야 합니다.

HTTP 층은 TestClient — 포트 없이 앱에 JSON-RPC 본문을 보낸다

처리기 시험은 라우트·직렬화를 지나지 않습니다. 와이어 모양까지 보려면 5장의 앱을 그대로 짓고, Starlette 의 TestClient 로 부릅니다. 앱은 HTTP 요청을 프로세스 안에서 받습니다.

SDK 클라이언트까지 — httpx.ASGITransport 로 클라이언트와 서버를 한 프로세스에

6장에서 본 대로 클라이언트에는 우리 httpx 연결을 넘길 수 있습니다. 그 연결의 전송을 ASGITransport(app=…) 로 바꾸면, 요청이 소켓 대신 앱으로 곧장 갑니다.

  • 카드는 make_app() 이 돌려준 객체를 그대로 줍니다. 카드의 url(http://lodging.test/)은 이름일 뿐 아무 데도 연결하지 않습니다.
  • 숙소 카드는 스트림을 켰으니 이 시험의 send_message 는 SSE 로 갑니다. ASGITransport 는 답을 다 받은 뒤 넘겨 주므로 이벤트가 "흐르는" 모습은 보이지 않지만, 순서와 내용(SUBMITTED → INPUT_REQUIRED)은 그대로입니다(httpx _transports/asgi.py:170 이 앱을 끝까지 돌린 뒤, 모은 본문으로 답을 짓습니다).

두 층 모두 초록 — 그리고 Starlette 1.8 은 TestClient 의 httpx 를 곧 바꾼다고 알린다

  • 와이어 시험은 카드의 name, 결과의 status.state, 견적 total, 모르는 메서드의 -32601 을 봤습니다. JSON 으로 읽은 total 은 2100000.0 이지만 assertEqual 은 통과합니다.
  • StarletteDeprecationWarning 은 TestClient 를 import 할 때 한 번 나옵니다. 이 판의 TestClient 는 httpx 위에서 돌지만 앞으로는 httpx2 를 쓰라는 예고입니다 — 이 시험이 기대는 것이 바뀔 수 있는 자리라 기록해 둡니다.

Q. 3단계 실행기에 시험 넷을 돌리면 몇 개가 통과합니까? 통과한 시험이 결함을 잡지 못한 까닭을 시험 대본으로 설명하십시오.

A. 셋이 통과합니다(test_naive.py: FAILED (failures=1)). 골든 사례는 첫 마디에 날짜·박 수·인원을 다 주고, 이어 말하기 시험은 묻는 것(인원)에 바로 답하고, 첫 되물음 시험은 한 마디뿐입니다. 어느 것도 에이전트의 물음이 이력에 들어온 뒤에 아직 빠진 항목이 남아 있는 상황을 만들지 않아, 물음 속 예시를 답으로 읽는 결함이 드러날 틈이 없었습니다.

9장

이 SDK 만의 것 — v0.3 호환, DB 저장소, 원격 측정

넷의 지도 → v0.3 호환 계층의 짜임 → 스위치 하나 → 옛 요청에 옛 모양으로 → 끈 서버는 -32601 → 카드가 0.3 이면 클라이언트도 옛 말로 → 그 와이어 → DB 저장소는 자리표시자 → 표와 a2a-db → 원격 측정이 붙은 곳 → 5부의 소음 다시 일으키기 → 소음의 정체 → 정리

파이썬 SDK 에만 있는 것 넷 — 둘은 이 venv 에서 돌고, 둘은 extra 가 없어 소스로만 본다

1~8장은 세 SDK 가 모두 가진 일을 파이썬으로 했습니다. 이 장은 다른 두 SDK 에서 같은 이름을 찾을 수 없는 것들입니다(TS·Go 쪽의 "그 SDK 만의 것" 은 8부·9부의 같은 장).

무엇설치본이 venv슬라이드
v0.3 호환 계층 — 옛 피어와 같은 경로에서 말하기compat/v0_3/ (8,038줄)돈다이 장
원격 측정 — 처리기·전송·큐의 OpenTelemetry spanutils/telemetry.py돈다(기록은 안 함)이 장
DB Task·푸시 설정 저장소(SQLAlchemy)server/tasks/database_*.py, server/models.pysql extra 없음이 장
스키마 이력 명령 a2a-db(Alembic)a2a_db_cli.py, migrations/db-cli extra 없음이 장
설치하지 않았다 — sqlalchemy·alembic 이 없다는 것은 8장의 optional.py 가 확인했습니다. 이 책은 venv 를 고정판으로 두므로 extra 를 더 깔지 않고, 깔리지 않은 기능이 어떻게 "없다" 고 말하는지를 봅니다. 여러 복제본용 cluster/ 와 FastAPI 도우미도 파이썬에만 있지만 17부·5장 정리의 몫입니다.

v0.3 호환 계층 — 옛 타입을 축으로 옛 와이어와 v1.0 객체를 오간다

compat/v0_3/README.md 가 이 계층의 짜임을 설명합니다. 옛 요청은 옛 모양으로 읽혀 v1.0 객체로 바뀐 뒤 우리 실행기에 닿고, 답은 거꾸로 옛 모양이 되어 나갑니다.

파일맡은 일
types.pyv0.3 JSON 스키마에서 생성한 pydantic 모델 — 번역의 축("pivot")
a2a_v0_3_pb2.py·proto_utils.pyv0.3 gRPC 의 protobuf 와 그 ↔ pydantic
conversions.pyv0.3 pydantic ↔ v1.0 protobuf (이름·enum·kind·blocking)
jsonrpc_adapter.py·rest_adapter.py·grpc_handler.py서버 쪽 — 옛 메서드를 받아 v1.0 처리기에 넘긴다
jsonrpc_transport.py·rest_transport.py·grpc_transport.py클라이언트 쪽 — 옛 서버에 옛 말로
versions.pyis_legacy_version — 0.3 이상 1.0 미만이면 옛 판
실행기는 모른다 — 번역은 처리기 바깥에서 끝납니다. 같은 QuoteExecutor 가 v0.3 요청에도 v1.0 객체만 받습니다. v0.3 과 v1.0 의 차이 자체는 1부, 판 협상(A2A-Version)은 14부가 다룹니다.

서버는 스위치 하나 — create_jsonrpc_routes(…, enable_v0_3_compat=True)

2단계 견적 에이전트를 스위치를 켜고(10770) 끄고(10771) 띄우는 서버입니다. 다른 곳은 5장과 같습니다.

  • 켜면 디스패처가 v0.3 어댑터를 하나 더 쥡니다. 요청이 오면 먼저 메서드 이름을 보고, message/send·tasks/get 같은 옛 이름이면 어댑터로, 아니면 v1.0 길로 보냅니다(jsonrpc_dispatcher.py:277, 어댑터의 이름 목록은 compat/v0_3/jsonrpc_adapter.py:54). 같은 경로 / 하나가 두 판을 다 받습니다.
  • REST 도 같은 이름의 인자가 있습니다(create_rest_routes(…, enable_v0_3_compat=), 13부).

켠 서버 — 옛 요청에는 옛 모양(kind·"completed")으로, 새 요청에는 새 모양으로

켠 서버에 v0.3 꼴 요청(ex/run/07/rpc/v03_send.json, 판 헤더 없음)과 v1.0 요청을 차례로 보냈습니다. 와이어 탭이 본 두 주고받음에서 메서드·kind·역할·상태 줄만 추렸습니다.

  • 첫 답은 v0.3 모양입니다 — "kind": "task", 파트마다 "kind": "data", 상태 "completed", 역할 "user". 둘째 답은 4·5부에서 본 v1.0 모양(TASK_STATE_COMPLETED, ROLE_USER)입니다.
  • v0.3 답에도 수는 2100000.0 으로 나갔습니다. 옛 모양으로 바꾸기 전에 이미 protobuf Value 를 지났기 때문입니다(2장).

끈 서버 — 같은 옛 요청이 -32601 Method not found

  • 기본값(False)인 서버에게 message/send 는 그냥 모르는 메서드입니다. 옛 클라이언트는 메서드 이름에서 이미 막히므로, 판 헤더를 보고 "지원하지 않는 판" 이라고 알려 줄 기회도 없습니다.
  • 이 한 줄(Request Error (ID: …))은 디스패처의 _generate_error_response 가 WARNING 으로 남깁니다(jsonrpc_dispatcher.py:198). 모든 오류 응답이 이 길을 지나지는 않습니다 — 막는 호출에서 처리기가 던진 A2A 오류는 로그 없이 응답만 짓습니다(:332). 원격 측정 실험에서 거절 둘에 Request Error 가 한 건뿐인 것도 그래서입니다(스트림 쪽 거절만 남았습니다).

카드가 0.3 이라고 하면 — 클라이언트 팩토리가 옛 전송을 골라 끼운다

진짜 카드를 받아 인터페이스의 protocol_version 만 "0.3" 으로 고친 뒤 클라이언트를 만들었습니다. 우리 코드는 여전히 v1.0 타입만 씁니다.

고르는 곳 — ClientFactory 의 JSON-RPC 전송 생산자가 고른 인터페이스의 판을 is_legacy_version 으로 보고, 옛 판이면 CompatJsonRpcTransport 를 끼웁니다(client_factory.py:112). 이 전송은 v0.3 에 없는 메서드를 막습니다 — 예를 들어 list_tasks 는 "ListTasks is not supported in A2A v0.3 JSONRPC." 입니다(compat/v0_3/jsonrpc_transport.py:179).

옛 전송의 와이어 — A2A-Version: 0.3, message/send, blocking: true

  • 팩토리가 연결에 심은 A2A-Version: 1.0(6장)을 옛 전송이 요청마다 0.3 으로 덮어 씁니다(compat/v0_3/jsonrpc_transport.py:487, 스트림은 :425).
  • v1.0 의 returnImmediately 가 꺼진 것이 v0.3 의 "blocking": true 로 바뀌었습니다(conversions.py:343). 메시지와 파트에는 kind 가, 역할에는 "user" 가 붙었습니다.

DB 저장소는 import 는 되고 만들면 막힌다 — 이름 자리에 자리표시자가 있다

SQLAlchemy 로 Task 와 푸시 설정을 DB 에 두는 저장소 둘이 a2a.server.tasks 에 있습니다. extra 없이 불러 봤습니다.

  • server/tasks/__init__.py 는 진짜 클래스를 불러오다 실패하면 같은 이름의 자리표시자 클래스를 둡니다. 그래서 import 는 늘 되고, 만들 때 "어느 extra 를 깔라" 는 ImportError 가 납니다.
  • DatabaseTaskStore 의 까닭 을 보십시오. 원인이 DatabasePushNotificationConfigStore requires … 로 나옵니다. 두 자리표시자가 같은 모듈 변수 _original_error 를 만들 때마다 원인으로 읽는데(server/tasks/__init__.py:46·:68), 둘째 try 가 그 변수를 덮어 둔 뒤이기 때문입니다 — 설치본의 작은 결함입니다(메시지가 extra 를 바로 알려 주니 실제로 해롭지는 않습니다).

tasks 표의 열과 이력 셋 — 그리고 a2a-db 는 Alembic 없이는 시작도 못 한다

import 할 수 없는 모듈은 글로 읽었습니다. server/models.py 의 TaskMixin 과 migrations/versions/ 의 문서 문자열, 그리고 패키지가 등록한 명령입니다.

  • Task 는 행 하나입니다. status·artifacts·history 는 JSON 열이고, 여기에 metadata 열이 하나 더 있습니다(이름 충돌을 피해 task_metadata 라는 메서드로 정의돼 위 목록에 안 잡혔습니다). owner 열이 4장의 소유자별 분리를 DB 에서 맡습니다.
  • 스키마 이력은 셋 — owner·last_updated 열, protocol_version 열, 그리고 task_versions·task_events 표(여러 복제본용, 17부)입니다. a2a-db 는 이 이력을 upgrade·downgrade·current 로 옮기는 명령인데, 모듈 머리에서 Alembic 을 import 하므로 db-cli extra 없이는 도움말조차 안 나옵니다.
  • 만들 때는 DatabaseTaskStore(engine, create_table=True, table_name="tasks", owner_resolver=…) 입니다. 우리 저장소(파일)를 TaskStore 로 직접 짓는 일은 17부입니다.

원격 측정은 처리기·큐·전송에 붙어 있다 — 이 venv 에서는 켜져 있되 아무것도 기록하지 않는다

utils/telemetry.py 의 장식자 @trace_class·@trace_function 이 붙은 곳과, 지금 그것이 무엇을 하는지 물었습니다.

  • 스위치는 환경 변수 OTEL_INSTRUMENTATION_A2A_SDK_ENABLED(기본 true)이고, opentelemetry 가 import 되면 켜집니다. 그런데 이 venv 의 opentelemetry-api 는 telemetry extra 가 아니라 몸통 의존인 google-api-core 가 데려온 것입니다(8장 optional.py 의 google-api-core 가 요구: …). 그래서 아무도 고르지 않았는데 켜져 있습니다.
  • OpenTelemetry SDK 가 없으니 공급자는 ProxyTracerProvider, span 은 NonRecordingSpan 입니다. 기록은 하지 않지만 장식자는 호출마다 span 을 열고 맥락(context)을 붙였다 뗍니다.

5부의 소음을 다시 — 끝난 작업에 곧바로 한마디, 남은 로그를 센다

5부는 이 경로에서 파이썬 서버가 흘린 traceback 을 stderr=drop 으로 버렸습니다(5부). 이번에는 서버(uvicorn)와 클라이언트를 한 프로세스에 두고, 로그를 로거 이름과 첫 줄로 셉니다. 스위치는 SDK 를 import 하기 전에 환경 변수로 넣어야 합니다.

소음의 정체 — SDK 가 버린 작업 둘, 원격 측정은 그것을 traceback 으로 키웠다

  • 두 실행 모두 asyncio 가 "Task was destroyed but it is pending!" 을 둘 남겼습니다. 끝난 작업에 온 요청을 거절할 때 처리기가 만든 이벤트 큐의 EventQueueSource._dispatch_loop 작업이 끝나지 않은 채 버려진 것입니다 — 원격 측정과 상관없는, SDK 1.2.2 의 뒷정리 문제입니다.
  • 켠 쪽에만 "Failed to detach context" 가 둘 더 있습니다. 버려진 코루틴을 거둘 때 그 안의 with start_as_current_span(…)(telemetry.py:232)이 다른 맥락에서 닫히고, OpenTelemetry 가 그 실패를 traceback 과 함께 로그로 남깁니다. 5부의 캡처를 흔들던 메모리 주소가 그 traceback 에 있었습니다.
권하는 설정 — 트레이스를 실제로 모으지 않는다면 서버를 OTEL_INSTRUMENTATION_A2A_SDK_ENABLED=false 로 띄웁니다. traceback 은 사라지지만 버려진 작업 경고는 남으니, 그것은 SDK 의 몫으로 기록해 둡니다. 이 책의 다른 캡처는 기본값 그대로 두었습니다.

9장 퀴즈

Q. v0.3 클라이언트만 쓰는 협력사를 위해 견적 에이전트의 create_jsonrpc_routes 에 enable_v0_3_compat=True 를 켰습니다. 그 뒤 우리 v1.0 클라이언트의 요청은 어떻게 됩니까? 그리고 스위치를 켜기 전, 협력사의 message/send 는 무슨 답을 받았습니까?

A. v1.0 요청은 그대로 v1.0 길로 갑니다. 디스패처가 메서드 이름으로 가르므로, SendMessage 는 어댑터를 거치지 않고 v1.0 모양(TASK_STATE_COMPLETED)으로 답을 받습니다(켠 서버의 둘째 주고받음). 켜기 전에는 -32601 "Method not found" 였습니다(끈 서버).

7부 정리 — 메아리에서 숙소 에이전트까지, 파이썬 SDK 로

장한 줄

다음 — 8부는 같은 숙소 에이전트를 공식 TypeScript SDK(@a2a-js/sdk)로 짓습니다. 8부와 9부(Go)는 이 부와 장 번호가 같으니, 견주고 싶은 장을 같은 번호로 펴십시오 — 각 장 끝의 "정리" 표 왼쪽 열도 같습니다.
