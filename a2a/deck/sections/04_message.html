4부

Message·Part·Role·contextId

Message 해부 → Part 네 가지 → 메시지만 돌려주는 에이전트 → DataPart 로 구조화 입력 → FilePart → contextId 규칙 → messageId 와 멱등성 → ProtoJSON 규칙

카드를 읽었으면 이제 말을 건다 — 그 말의 단위가 Message 다

3부의 카드는 "어디로, 어떤 바인딩으로" 를 알려 줬습니다. 이 부는 그 주소로 실제로 보내는 것, 곧 메시지(Message)와 그 안의 파트(Part)를 와이어에서 한 필드씩 읽습니다.

장무엇을
1장Message 해부 — 필드 여덟, 서버가 채우는 것, 필수 필드를 빼면
2장Part 네 가지 — text·raw·url·data, kind 가 사라진 이유, 세 SDK 로 만들고 읽기
3장메시지만 돌려주는 에이전트 — Message 응답과 Task 응답
4장DataPart 로 구조화 입력 — 숙소 요청 ×3 과 30.0
5장FilePart — raw 와 url, 큰 파일은 url 로, 미디어 타입 협상
6장contextId 규칙 — 서버가 만들고, 지키고, 어긋나면 거절한다
7장messageId 와 멱등성 — 같은 메시지가 두 번 오면
8장ProtoJSON 규칙 — camelCase, enum 문자열, 빠진 필드
이 부의 방식 — 3부처럼 완성 에이전트(숙소)를 블랙박스로 띄우고, 그 앞에 와이어 탭을 세웁니다. 새로 쓰는 것은 작은 실험용 에이전트 둘뿐입니다 — 파트를 보는 파트 확인 에이전트(2장)와 입력 미디어 타입을 따지는 접수 에이전트(5장), 둘 다 세 언어로.

1장

Message 해부

필드 여덟 → 여섯을 채운 요청 → 서버가 저장한 사용자 메시지 → 에이전트의 메시지와 contextId → 둘째 턴의 taskId → referenceTaskIds → extensions·metadata → 세 서버의 저장 방식 → 필수 필드를 빼면 ×3

Message 의 필드는 여덟, 필수는 셋이다

proto 의 설명은 한 줄입니다: "`Message` is one unit of communication between client and server." 스펙 §4.1.4 의 표도 이 proto 에서 나옵니다. (google.api.field_behavior) = REQUIRED 가 붙은 것은 셋뿐입니다.

필드(와이어 이름)필수누가 채우나이 장의 슬라이드
messageId예보내는 쪽 — "created by the message creator"요청
role예보내는 쪽 — ROLE_USER 또는 ROLE_AGENT요청
parts예보내는 쪽 — 내용(2장)필수
contextId처음엔 비우고, 서버가 만든 것을 이어 쓴다에이전트 메시지
taskId이어 말할 때 — 서버가 만든 작업 id둘째 턴
referenceTaskIds보내는 쪽 — 참고할 다른 작업참조
extensions·metadata보내는 쪽 — 확장의 URI 와 덧붙일 값확장·메타
role 은 enum — proto 의 Role 은 ROLE_UNSPECIFIED(0)·ROLE_USER(1, "from the client to the server")·ROLE_AGENT(2, "from the server to the client") 셋입니다. 와이어에 이름 문자열로 적는 규칙은 8장(ProtoJSON)에서 봅니다.

여섯 필드를 채운 요청 — 처음 말할 때는 contextId·taskId 가 없다

숙소 에이전트 셋(py·ts·go) 앞에 탭을 하나씩 세우고, 같은 본문(rpc/full.json)을 curl 로 보냈습니다. 인원을 일부러 빼서, 에이전트가 되묻게 했습니다.

서버는 받은 메시지를 이력에 넣으며 contextId·taskId 를 채웠다

파이썬 서버의 답은 Task 였고(3장), 그 history 에 우리가 보낸 메시지가 들어 있습니다. 보낸 것과 견줘 보면 두 필드가 늘었습니다.

  • messageId 는 우리가 정한 m-1 그대로입니다. 메시지 id 는 만든 쪽의 것이라 서버가 바꾸지 않습니다.
  • contextId·taskId 는 우리가 보내지 않았는데 들어 있습니다 — 서버가 새로 만든 작업(<id1>)과 맥락(<id2>)에 이 메시지를 묶은 것입니다.
  • metadata·extensions·referenceTaskIds 는 손대지 않고 보관했습니다.

에이전트의 메시지 — role 은 ROLE_AGENT, contextId 는 반드시 있다

되묻는 말은 작업의 상태(status.message)에 실려 왔습니다. 이것도 Message 이고, 이번에는 서버가 만든 메시지입니다.

  • messageId 는 서버가 만든 값(<id3>), role 은 ROLE_AGENT 입니다.
  • proto 의 Message 설명: "For server messages, context_id must be provided, and task_id only if a task was created." — 여기서는 작업을 만들었으므로 둘 다 있습니다.
  • §3.4.1: 에이전트가 새 contextId 를 만들었다면 "it MUST be included in the response" — result.task.contextId 와 이 메시지의 contextId 가 같은 <id2> 입니다. 클라이언트가 contextId 를 정해 보내면 어떻게 되는지는 6장에서 봅니다.

둘째 턴의 메시지는 taskId·contextId 를 단다

되물음에 답할 때는 같은 작업에 이어 말해야 합니다. 총무팀 CLI(agents/ask.py)가 Go 숙소 에이전트와 두 마디를 주고받았습니다.

  • 첫 답의 result.task.id(<id2>)가 taskId 로, result.task.contextId(<id3>)가 contextId 로 돌아갔습니다.
  • §3.4.2: 클라이언트가 단 taskId 는 "MUST reference an existing task". 이 흐름(INPUT_REQUIRED 다중 턴) 자체는 5부의 몫입니다.

referenceTaskIds — 다른 작업을 "참고하라" 고 가리킨다

§3.4.3: "Clients SHOULD use the referenceTaskIds field in Message to explicitly reference related tasks." taskId 가 "이 작업에 이어 말한다" 라면, 이것은 "저 작업들을 참고하라" 입니다.

  • 요청에 넣은 t-earlier 는 없는 작업입니다. TS 서버만 위처럼 "not found" 를 찍었고, 세 서버 모두 오류 없이 처리를 이어 갔습니다 — 참조는 taskId 와 달리 존재가 의무가 아닙니다.
  • 파이썬 SDK 는 참조한 작업을 실행기에 넘겨 주는 기능을 꺼 둔 채로 시작합니다(SimpleRequestContextBuilder(should_populate_referred_tasks=False)). 기획 에이전트가 정산 에이전트에 세 견적의 작업을 가리키는 장면은 15부에서 봅니다.

extensions·metadata — 서버는 모르는 것도 그대로 보관했다

extensions 는 이 메시지에 쓰인 확장의 URI 목록, metadata 는 덧붙이는 키-값입니다. §3.2.5: "Metadata keys and are strings and values can be any valid value that can be represented in JSON."

  • 숙소 에이전트의 카드에는 확장이 하나도 없는데(3부), 세 서버 모두 예산 확장 URI 를 거절하지 않고 이력에 넣었습니다. 확장을 선언하고 요구하는 규칙(A2A-Extensions 머리글, required)은 14부에서 봅니다.
  • 위는 Go 서버의 이력입니다. 키가 Go 구조체에 선언된 차례(messageId·contextId 다음은 알파벳순)이고, contextId·taskId 가 없습니다 — 다음 슬라이드.

세 서버 비교 — 같은 메시지를 이력에 넣는 방식이 다르다

세 와이어의 result.task.history 를 나란히 놓았습니다. 받은 필드는 셋 다 지켰지만, 덧붙이는 것이 다릅니다.

§3.7 이 허락한 차이 — "The agent is responsible to determine which Messages are persisted in the Task History." 이력에 무엇을 남길지는 에이전트(SDK)가 정합니다. 위는 TS 서버가 이력 끝에 덧붙인 되묻는 말입니다.

필수 필드를 빼면 — 파이썬은 -32602 와 함께 빠진 필드를 적는다

messageId·role·parts 를 하나씩 뺀 본문 셋(rpc/no_id.json·no_role.json·no_parts.json, parts 는 빈 배열)을 세 숙소 에이전트에 보냈습니다. 아래는 파이썬 서버가 messageId 없는 요청에 준 답입니다.

나머지 둘(role 없음, 빈 parts)의 답에서 fieldViolations 만 골랐습니다.

  • -32602 는 JSON-RPC 의 Invalid params(2부)입니다. 빈 배열도 "빠짐" 으로 봅니다 — "Field must contain at least one element."
  • 필드 이름이 와이어의 messageId 가 아니라 proto 의 message.message_id 입니다.

Go 도 셋 다 -32602 로 거절한다

같은 세 본문에 대한 Go 서버의 답에서 오류 코드와 문구만 골랐습니다.

문구는 SDK 마다 다르다 — 코드는 셋 다 -32602 이지만 파이썬은 Validation failed + 필드 목록, Go 는 message role is required: invalid params 처럼 문장 하나입니다. 클라이언트는 문구가 아니라 코드로 가려야 합니다.

TS 는 messageId 만 검사한다 — role·parts 가 없어도 받는다

TS 서버의 세 답에서 상태와 오류만 골랐습니다. messageId 없는 요청은 거절했지만, role 이 빠진 요청과 빈 parts 는 받아서 작업을 만들었습니다. 둘 다 되물음(INPUT_REQUIRED)으로 끝난 것은 숙소 에이전트 쪽 사정입니다 — 에이전트는 사용자(ROLE_USER)의 말만 읽으므로, 역할 없는 "2026-10-30 1박 30명" 은 못 들은 말이 됐습니다.

느슨한 서버의 함정 — 받는 쪽이 느슨하면 보내는 쪽은 틀린 줄 모릅니다. 이력의 메시지에는 role 이 아예 없습니다. 오류 대신 "날짜·박 수·인원이 다 빠졌다" 는 되물음이 돌아왔으니, 보낸 쪽은 무엇이 틀렸는지 알 길이 없습니다. 어느 서버에 보내도 통하도록, 보내는 쪽이 세 필수 필드를 지켜야 합니다.

1장 퀴즈

Q. 요청에 contextId 를 넣지 않았는데, 파이썬 서버가 돌려준 이력의 사용자 메시지에는 contextId 가 있습니다. 그 값은 어디서 왔고, 응답의 어느 필드와 같습니까? Go 서버의 이력은 어떻습니까?

A. 서버가 새 작업을 만들며 지은 맥락 id 입니다. 파이썬 이력의 contextId 는 <id2> 로, result.task.contextId 와 되묻는 메시지의 contextId(에이전트 메시지)와 같습니다. Go 서버의 이력에는 받은 그대로 저장해 contextId·taskId 가 없습니다.

2장

Part 네 가지

oneof 하나와 공통 필드 셋 → kind 가 사라진 v1.0 → 파트 만들기 ×3 → 와이어 → 세 와이어 비교 → raw 는 base64 → 파트 읽기 ×3 → v0.3 모양을 보내면 → 내용이 둘인 파트 → 세 SDK 비교

Part 는 내용 필드 넷 중 하나만 갖는다 — proto 의 oneof

proto 의 설명: "Parts can be purely textual, some sort of file (image, video, etc) or a structured data blob (i.e. JSON)." 내용은 oneof content 로 묶인 네 필드 중 하나이고, 나머지 셋은 어느 종류에나 붙습니다.

v1.0 은 kind 를 버렸다 — 어느 필드가 있느냐가 곧 종류다

whats-new-v1.md 의 첫 항목 중 하나가 "Removal of discriminator kind fields in favor of JSON member-based polymorphism" 입니다. v0.3 에는 파트 타입이 셋 따로 있었고, 종류를 kind 값으로 적었습니다.

  • 읽는 쪽 코드는 part.kind === "text" 대신 "text" in part 를 봅니다(같은 문서의 이행 예). 세 SDK 가 이것을 어떻게 타입으로 옮겼는지가 이 장의 나머지입니다.

파이썬 — Part(text=…) 처럼 oneof 의 필드 하나를 이름으로 준다

파이썬 SDK 의 타입은 protobuf 메시지입니다(a2a.types.Part). 생성자에 넣은 필드가 곧 oneof 의 선택이고, new_*_part 도우미는 같은 필드를 채워 줄 뿐입니다.

  • new_raw_part(raw, media_type, filename)·new_url_part(url, media_type, filename) 은 순서가 같습니다(a2a/helpers/proto_helpers.py).
  • new_data_part 는 파이썬 값을 ParseDict(data, struct_pb2.Value()) 로 Value 에 옮깁니다 — 4장의 30.0 이 여기서 시작됩니다.

TypeScript — content: {$case, value} 하나에 종류와 값을 담는다

TS SDK 의 타입은 ts-proto 가 proto 에서 만든 것입니다. oneof 는 content 필드 하나가 되고, 종류는 $case 문자열입니다. SDK 에 파트 도우미 함수는 없습니다.

  • Part 인터페이스는 filename: string·mediaType: string·metadata 를 선택이 아닌 필드로 선언합니다. 그래서 빈 값(none)을 펼쳐 넣었습니다.
  • raw 의 값 타입은 Buffer 입니다.

Go — Content 필드에 Text·Raw·URL·Data 중 한 타입을 넣는다

Go SDK 의 a2a.Part 는 Content PartContent 를 가진 구조체이고, PartContent 는 네 타입(a2a.Text·a2a.Raw·a2a.URL·a2a.Data)만 들어가는 봉인된 인터페이스입니다.

  • 생성 함수의 인자가 제각각입니다 — NewRawPart(raw) 는 바이트만, NewFileURLPart(url, mimeType) 는 미디어 타입까지 받습니다. 나머지는 필드에 직접 씁니다.
  • NewDataPart 는 any 를 받습니다. 4장에서는 여기에 구조체를 넣습니다.

와이어 — 파트마다 내용 필드는 하나, kind 는 없다

세 언어의 클라이언트가 같은 언어의 파트 확인 에이전트에 파트 넷을 보냈습니다(받은 파트를 읽는 코드는 이 장 뒤쪽, 실행기는 3장). 아래는 파이썬 클라이언트의 요청입니다.

menu.md 의 내용 "# 식단\n- 숯불 바비큐\n" 은 한글 일곱 자(3바이트씩 21바이트)와 ASCII 일곱 자(#·-·빈칸 셋·줄바꿈 둘), 모두 28바이트입니다. JSON 문자열에는 아무 바이트나 넣을 수 없어서 base64 로 적습니다.

  • base64 는 3바이트를 4글자로 적습니다. 28바이트 → 40글자(끝의 == 는 모자란 자리 채움). 크기가 3분의 1쯤 늘어나는 셈이라, 큰 파일은 url 로 보내라는 이야기가 5장에서 나옵니다.
  • 세 언어 모두 프로그램 안에서는 바이트로 다룹니다 — 파이썬 bytes, TS Buffer, Go a2a.Raw([]byte). base64 바꾸기는 SDK 가 직렬화할 때 합니다. 받는 쪽 세 에이전트가 모두 "28바이트" 로 셌습니다(다음 슬라이드들).

파이썬에서 읽기 — WhichOneof("content") 가 종류를 알려 준다

파트 확인 에이전트는 받은 파트마다 종류와 값을 한 줄로 적어 돌려줍니다. 데이터 파트는 그 언어가 읽은 타입 이름까지 적습니다.

TypeScript 에서 읽기 — content?.$case 로 가르면 value 의 타입이 좁혀진다

$case 를 비교하면 TS 가 value 의 타입(string·Buffer·any)을 알아서 좁혀 줍니다.

배열의 typeof 는 object — JS 에서 typeof [] 는 "object" 입니다. 데이터가 배열인지 보려면 Array.isArray 를 씁니다.

Go 에서 읽기 — Content 를 타입 스위치로 가른다

Go 는 p.Content.(type) 로 가르거나, p.Text()·p.Raw()·p.URL()·p.Data() 접근자를 씁니다(종류가 다르면 빈 값을 돌려줍니다).

v0.3 모양을 보내면 — kind 는 무시되고, file 은 내용 없는 파트가 된다

세 파트 확인 에이전트에 v0.3 모양의 파트 둘을 curl 로 보냈습니다 — kind 를 붙인 글 파트(rpc/v03_text.json)와, v0.3 파일 파트의 내용인 file 객체(rpc/v03_file.json). 아래는 세 탭에서 파트와 답만 고른 줄입니다(파이썬·TS·Go 차례).

  • kind: "text" 는 셋 다 모르는 필드로 넘기고 text 를 읽었습니다.
  • file 객체는 v1.0 에 없는 필드라, 파이썬·TS 는 내용 필드가 하나도 없는 파트로 받았습니다. Go 만 거절했는데, 코드가 -32700(Parse error — JSON 자체가 틀렸다는 코드)입니다. JSON 은 멀쩡하므로 -32602 가 맞는 자리입니다.

내용 필드가 둘인 파트 — 파이썬·Go 는 거절, TS 는 앞의 것을 고른다

text 와 data 를 한 파트에 함께 넣었습니다(rpc/two.json). oneof 는 "하나만" 이라는 뜻이므로 틀린 파트입니다.

  • 파이썬은 protobuf 의 JSON 해석기(ParseDict)가 막고 -32602 를 돌려줍니다. 서버 로그(터미널 1)에 남은 까닭은 Message type "lf.a2a.v1.Part" should not have multiple "content" oneof fields 입니다.
  • TS 의 Part.fromJSON 은 text→raw→url→data 차례로 처음 보이는 것 하나만 집습니다 — data 는 소리 없이 버려졌습니다.
  • Go 는 다시 -32700 입니다.

2장 퀴즈

Q. v0.3 클라이언트가 kind 를 붙인 글 파트 {kind: "text", text: "안녕하세요"} 를 v1.0 서버 셋에 보냈습니다. 몇 곳이 받아들였고, 서버는 무엇을 읽었습니까? 내용이 file 객체에 든 v0.3 파일 파트라면 어떻습니까?

A. 글 파트는 세 곳 모두 받아 text 를 읽었습니다 — kind 는 모르는 필드로 넘어갑니다(v0.3 모양). 파일 파트는 v1.0 에 없는 file 객체에 내용이 들어 있어, 파이썬·TS 는 "(내용 없음)" 파트로 받았고 Go 는 -32700 으로 거절했습니다. 어느 쪽이든 파일은 전달되지 않습니다.

3장

메시지만 돌려주는 에이전트

답은 Task 이거나 Message → 즉답 에이전트 ×3 → Message 응답의 와이어 → 세 서버 비교 → 같은 말, 두 가지 답 → Task 가 더 가진 것과 §3.7 → 클라이언트가 가르는 법 ×3 → 언제 무엇을

SendMessage 의 답은 Task 이거나 Message 다

§3.1.1 은 출력을 둘로 적습니다: "A task object representing the processing of the message, OR A direct response message (for simple interactions that don't require task tracking)".

  • Behavior: "The agent MAY create a new Task to process the provided message asynchronously or MAY return a direct Message response for simple interactions." 어느 쪽이든 정하는 것은 에이전트입니다.
  • 와이어에서는 result 아래 키 하나로 갈립니다 — result.task 이거나 result.message. 1장의 숙소 에이전트는 늘 task 였습니다.
  • 스트림으로 물어도 같습니다. §3.1.2: Message 로 답하면 "the stream MUST contain exactly one Message object and then close immediately" — 스트림은 10부에서 봅니다.
3부에서 이미 봤다 — 기능 없는 안내 에이전트(3부)가 인사 한마디를 Message 로 돌려줬습니다. 이 장은 그 즉답형을 Task 응답과 나란히 놓고 읽습니다.

파이썬 — Message 하나를 이벤트 큐에 넣고 끝낸다

2장에서 써 온 파트 확인 에이전트가 즉답형입니다. 실행기는 Task 를 만들지 않고, 에이전트 쪽 Message 하나를 큐에 넣습니다.

  • new_message 는 message_id 를 uuid4 로 짓고 role 기본값을 ROLE_AGENT 로 둡니다(proto_helpers.py).
  • context_id=ctx.context_id — 요청 맥락의 id 를 그대로 답에 답니다. 서버 메시지에는 contextId 가 있어야 합니다(1장).

TypeScript — AgentEvent.message 를 버스에 싣고 finished()

TS 의 실행기는 이벤트 버스에 싣습니다. Message 를 실은 뒤 bus.finished() 로 이 실행이 끝났다고 알립니다.

  • Message 인터페이스의 필드는 모두 적어야 해서 taskId: ""·extensions: [] 처럼 빈 값을 넣었습니다. 빈 값은 와이어에 나가지 않습니다(Message.toJSON 이 뺍니다).
  • messageId 는 직접 지었습니다(randomUUID()).

Go — Message 하나를 yield 하고 반복자를 닫는다

Go 의 실행기는 이벤트를 내보내는 반복자(iter.Seq2[a2a.Event, error])입니다. *a2a.Message 도 a2a.Event 이므로 그대로 내보냅니다.

  • a2a.NewMessage 가 ID 를 짓습니다(NewMessageID(), uuid). ContextID 는 실행 문맥(ec.ContextID)에서 옮겼습니다.
  • 작업에 묶인 메시지라면 a2a.NewMessageForTask 가 TaskID·ContextID 를 함께 채웁니다 — 숙소 에이전트의 되묻는 말이 그 길입니다.

Message 응답의 와이어 — result.message, 그리고 taskId 가 없다

총무팀 CLI 로 파트 확인 에이전트(py)와 숙소 에이전트(py)에 같은 말을 했습니다. 먼저 파트 확인 에이전트 쪽입니다.

  • role 은 ROLE_AGENT, contextId 는 서버가 지은 <id3> 입니다. taskId 는 없습니다 — 만든 작업이 없으니까요.
  • 남는 것이 없습니다. 이 답에는 나중에 GetTask 로 다시 물을 id 도, 상태도, 이력도 없습니다.

세 서버 비교 — 같은 즉답, 실어 보내는 방법만 다르다

2장의 parts 명세에서 TS·Go 파트 확인 에이전트도 같은 모양의 result.message 를 돌려줬습니다. 아래는 Go 서버의 답입니다.

같은 말, 두 가지 답 — "message:" 와 "task COMPLETED"

총무팀 CLI 는 답의 종류에 따라 다르게 찍습니다. 같은 말 2026-10-30 1박 30명 에 파트 확인 에이전트는 Message 로, 숙소 에이전트는 Task 로 답했습니다.

숙소는 왜 Task 인가 — 되물을 수도(INPUT_REQUIRED), 거절할 수도(REJECTED) 있고, 결과물(견적)이 있기 때문입니다. 상태가 바뀌는 일에는 상태를 담을 그릇이 필요합니다 — 그 그릇이 Task 이고, 5부의 주제입니다.

Task 는 id·상태·아티팩트·이력을 가진다 — 결과는 아티팩트로

숙소 에이전트의 답입니다. 견적은 메시지가 아니라 artifacts 에 들어 있습니다.

  • §3.7: "Messages SHOULD NOT be used to deliver task outputs. Results SHOULD BE returned using Artifacts associated with a Task." 메시지는 소통(되묻기·진행 알림), 아티팩트는 결과물입니다.
  • 그래서 숙소 에이전트는 되물을 때는 status.message 에(1장), 견적은 아티팩트 숙소 견적 에 넣습니다. 파트 확인 에이전트의 답은 결과물이 아니라 "받은 것을 말해 주는" 소통이라 Message 로 충분합니다.
  • 수가 30.0·2100000.0 으로 적혀 있습니다. 파이썬 서버의 데이터 파트입니다 — 4장의 주제입니다.

클라이언트가 가르는 법 ×3 — oneof 이름, 필드 유무, 타입 스위치

4장의 숙소 요청 클라이언트는 답이 Task 면 견적을, Message 면 글을 찍습니다. 갈림길만 잘라 왔습니다.

  • 파이썬의 send_message 는 막는 호출이어도 StreamResponse 를 하나 내주는 비동기 반복자입니다. 종류는 oneof 이름(payload)으로 묻습니다.
  • TS 의 sendMessage 는 와이어의 {task}/{message} 껍질을 벗겨 Message | Task 를 줍니다(JSON-RPC 전송의 sendMessage 가 response.payload.value 를 돌려줌). 꼬리표가 남지 않아, Task 에만 있는 status 가 있는지로 가렸습니다.

언제 Message 로, 언제 Task 로 답하나

이 장의 두 에이전트를 줄마다 견줬습니다. 마지막 줄이 보물상사 에이전트들의 실제 갈래입니다.

3장 퀴즈

Q. 파트 확인 에이전트의 답을 받은 뒤, 그 일의 상태를 GetTask 로 다시 물을 수 있습니까? 와이어에서 무엇을 보면 알 수 있습니까?

A. 물을 수 없습니다. 답은 result.message 이고, 그 안에 taskId 가 없습니다 — 작업이 만들어지지 않았으니 물을 id 가 없습니다. 같은 말을 받은 숙소 에이전트는 result.task.id(<id5>)가 있는 Task 로 답했습니다.

4장

DataPart 로 구조화 입력

글 대신 데이터 → 숙소 요청 보내기 ×3 → 와이어의 30 과 30.0 → 파이썬 서버가 돌려준 수 → 세 클라이언트가 읽은 수 → 3×3: 받는 쪽 언어가 타입을 정한다 → Go 의 정수 칸 → 세 언어 비교

숙소 요청을 데이터 파트로 — 파이썬은 dict 를 Value 로 옮긴다

숙소 에이전트의 카드는 application/json 입력을 받고, 스킬 예시로 {date, nights, headcount} 모양을 적어 두었습니다(3부). 글("30명")은 에이전트가 정규식으로 뜯어야 하지만, 데이터 파트는 이름 붙은 값을 그대로 건넵니다.

new_data_part 는 ParseDict(data, struct_pb2.Value()) 입니다(2장). protobuf 의 Value 에서 수는 double number_value 하나뿐이라(struct.proto: "Represents a JSON number"), 정수 30 도 실수로 들어갑니다.

TypeScript — 객체를 value 에 그대로 넣는다

ts-proto 의 data 값 타입은 any 입니다. 우리가 넣은 객체가 거의 그대로 JSON.stringify 를 거쳐 와이어에 나갑니다.

Go — 정수 칸을 가진 구조체를 그대로 넣는다

a2a.NewDataPart 는 any 를 받으므로 타입이 있는 구조체를 넣을 수 있습니다. 직렬화는 encoding/json 이 하고, int 칸은 30 으로 적힙니다.

와이어의 30 과 30.0 — 파이썬만 소수점을 붙인다

세 클라이언트가 파이썬 숙소 에이전트에 요청을 보냈습니다(data 명세). 세 요청의 데이터 파트만 잘라 차례로 놓았습니다.

JSON 쪽 이야기는 2부에서 — 30 과 30.0 이 JSON 에서는 같은 수이고 읽는 언어가 대접을 정한다는 것은 2부에서 봤습니다. 새로운 것은 A2A SDK 가 그 차이를 만들어 낸다는 점입니다 — 파이썬 SDK 는 데이터 파트를 protobuf Value 에 담고, json_format 이 그 double 을 파이썬 float 로 꺼내 30.0 으로 적습니다.

파이썬 서버는 받은 30 도 30.0 으로 돌려준다

TS 클라이언트는 30 을 보냈습니다. 파이썬 숙소 에이전트의 답을 보면 견적도, 이력에 저장된 TS 의 요청도 소수점이 붙어 있습니다.

  • 서버가 받은 요청을 Message(protobuf)로 읽는 순간 30 은 double 이 되고, 다시 JSON 으로 쓸 때 30.0 이 됩니다.
  • 견적의 rooms·total 은 업무 규칙(workshop.domain)이 파이썬 int 로 계산한 값인데도 8.0·2100000.0 입니다. 데이터 파트에 넣는 순간 같은 길을 지나기 때문입니다.

세 클라이언트가 읽은 수 — float·number·float64

같은 답(2100000.0)을 세 클라이언트가 각자의 타입으로 읽었습니다.

  • 파이썬은 float, TS 는 number(정수·실수 구별 없음), Go 는 데이터 파트가 any 라서 float64 입니다.
  • Go 의 %v 는 큰 float64 를 지수꼴로 찍습니다 — 2.1e+06. 돈을 그대로 화면에 찍으면 이렇게 됩니다.

3×3 — 수의 타입은 보낸 쪽이 아니라 받는 쪽 언어가 정한다

세 클라이언트가 세 파트 확인 에이전트에 같은 요청을 보냈습니다. 에이전트는 받은 값의 타입을 제 언어로 말합니다.

  • 파이썬 에이전트는 TS·Go 가 보낸 30 도 float 30.0 으로 읽었고, TS·Go 에이전트는 파이썬이 보낸 30.0 도 number 30·float64 30 으로 읽었습니다.
  • 세 줄씩 묶으면 보낸 언어가 바뀌어도 답이 똑같습니다. 와이어의 소수점은 받는 SDK 의 타입 변환에서 사라지거나 생깁니다 — 어느 SDK 도 정수 타입으로 넘겨주지 않습니다.

Go 의 정수 칸 — 바이트를 곧장 풀면 30.0 에서 실패한다

2부에서 Go 의 int 칸은 30.0 을 거절했습니다. 파이썬 SDK 가 실제로 그 30.0 을 보내므로, Go 쪽에서 언제 이 일이 생기는지 갈라 봤습니다.

  • ①: 와이어의 바이트를 구조체로 곧장 풀면(맨손 구현이 하기 쉬운 일) 실패합니다.
  • ②·③: SDK 를 거치면 값은 이미 float64 30 이고, 다시 JSON 으로 쓰면 30 이 되어 정수 칸에 들어갑니다.

세 언어 비교 — 그래서 에이전트는 받은 수를 정수로 되돌린다

와이어 줄은 파이썬만 다르고, 받은 수의 타입 줄에는 셋 다 정수 타입이 없습니다.

4장 퀴즈

Q. Go 클라이언트가 headcount 를 int 칸 30 으로 보내고, 파이썬 숙소 에이전트가 답했습니다. 답의 견적에서 total 은 와이어에 어떻게 적혔고, Go 클라이언트는 그것을 어떤 타입·어떤 모양으로 찍었습니까?

A. 파이썬 서버는 데이터 파트의 수를 protobuf double 로 담아 "total": 2100000.0 으로 적습니다(서버의 답). Go 클라이언트의 데이터 파트는 any 라 float64 로 읽고, %v 로 찍으면 2.1e+06 입니다(클라이언트가 읽은 수). 보낸 쪽이 정수였는지는 상관없습니다(3×3).
