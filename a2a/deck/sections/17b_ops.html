로깅·추적 — 요청 id, contextId 로 흐름 잇기

잇는 열쇠 넷 → SDK 가 스스로 적는 것 → 그 기록의 빈 곳 → 우리 한 줄 → 파이썬 → TypeScript → Go → 세 언어 비교 → 섞인 메시에 달기 → contextId 하나로 다섯 로그 → 트레이스 문맥

로그를 잇는 열쇠는 넷 — 가리키는 범위가 저마다 다르다

워크숍 이야기 한 문장은 HTTP 요청 열넷이 됩니다(15부). 어느 에이전트에서 무엇이 잘못됐는지 찾으려면 다섯 에이전트의 로그를 이어 읽어야 하고, 이을 열쇠는 와이어에 이미 있습니다.

열쇠누가 짓나하나가 가리키는 것다섯 에이전트를 잇나
JSON-RPC id요청을 보내는 쪽HTTP 요청 하나(응답과 짝짓기)못 한다 — 짓는 쪽마다 따로, TS 클라이언트는 늘 1(16부)
messageId메시지를 보내는 쪽메시지 하나(4부)못 한다 — 기획 에이전트가 맡길 때마다 새로 짓는다
taskId서버그 서버의 작업 하나못 한다 — 에이전트마다 제 작업
contextId첫 서버(또는 클라이언트)대화 하나잇는다 — 기획 에이전트가 제 맥락을 넷에게 그대로 넘긴다(15부)
contextId 가 열쇠가 된 것은 우리 기획 에이전트의 선택이다 — 맡기는 쪽이 맥락을 넘기지 않으면 동료마다 새 contextId 를 짓습니다(15부). 그때는 맡긴 쪽의 로그에 상대의 taskId 를 함께 적어 두어야 이어집니다.

SDK 가 스스로 적는 것 — 파이썬은 받은 본문, TS 는 없음, Go 는 가로채기를 달아야 두 줄

교통 에이전트 셋에 막는 SendMessage 를 하나씩 보냈습니다(17/sdklog 명세). 파이썬은 logging 을 INFO 로 켜고 JSON-RPC 를 받는 모듈 하나만 DEBUG 로, TS 는 완성 에이전트 그대로, Go 는 SDK 의 로깅 가로채기와 slog JSON 기록기를 달았습니다.

  • 파이썬 — 모듈마다 logging.getLogger(__name__) 입니다. INFO 로는 한 요청에 한 줄도 나오지 않았고, jsonrpc_dispatcher 를 DEBUG 로 켜자 받은 본문이 파트의 데이터까지 통째로 찍혔습니다(routes/jsonrpc_dispatcher.py:241 — 화면 폭 때문에 우리 형식이 170자에서 잘랐다).
  • TS — 로거가 없습니다. console.warn·console.error 가 경고·오류 길에 있고(15부의 "Reference task … not found." 따위), 성공 길에서는 푸시를 보낸 뒤의 console.info 하나뿐입니다(server/index.js:2694). 켤 스위치도 없습니다. 서버 출력은 우리 [교통] 줄뿐입니다.
  • Go — a2asrv.NewLoggingInterceptor(a2asrv/logging.go:43)가 a2a call started·finished 두 줄을 씁니다. 달지 않으면 오류 때만 적습니다(9부).

SDK 기록의 빈 곳 — Go 의 request_id 는 새 UUID, task_id 는 비었고, 파이썬 DEBUG 는 토큰까지 적는다

앞 슬라이드의 Go 두 줄과 파이썬 한 줄을 "다른 에이전트의 로그와 이을 수 있는가" 로 읽었습니다.

  • request_id 는 클라이언트가 보낸 JSON-RPC id 가 아니라 Go SDK 가 호출마다 새로 짓는 UUID 입니다(a2asrv/intercepted_handler.go:283). 같은 요청을 보낸 클라이언트의 로그에는 이 값이 없습니다.
  • task_id·context_id 가 빈 문자열입니다. SDK 는 클라이언트가 보낸 메시지의 값을 적을 뿐이라(intercepted_handler.go:77-82), 새 작업이면 비고, 서버가 지은 taskId 는 이 기록에 오지 않습니다. 걸린 시간은 나노초 정수(duration_ns)로 적혀서, 캡처가 흔들리지 않게 ReplaceAttr 로 "…ms" 글자로 바꿨습니다(17/busops).
  • 파이썬의 active_task 모듈은 DEBUG 에서 호출 맥락을 통째로 적고(agent_execution/active_task.py:517), 그 맥락의 state["headers"] 에는 요청 헤더가 전부 있습니다(routes/common.py:115). 정산 에이전트라면 Authorization: Bearer … 가 로그에 남습니다.
§13.4 "Logs MUST NOT include sensitive information (credentials, personal data)" — SDK 의 DEBUG 기록은 받은 본문과 헤더를 그대로 적습니다. 운영에서는 a2a 로거를 DEBUG 로 켜지 않습니다. 메시지 내용도 "SHOULD minimize logging of sensitive or personal information" 입니다.

우리 한 줄 — 요청 하나에 JSON 객체 하나, 요청이 끝날 때 적는다

세 SDK 의 기록은 모양도 담는 것도 다릅니다. 잇는 데 필요한 것만 세 언어가 같은 모양으로 적게 합니다. 아래는 파이썬 판의 두 함수 — 요청에서 열쇠를 꺼내고, 응답으로 채웁니다.

키값

파이썬 — 앱 바깥에 ASGI 미들웨어, 받는 본문과 내보내는 본문을 흘려 보내며 베낀다

ASGI 앱은 (scope, receive, send) 를 받는 함수입니다. receive 와 send 를 감싸면 SDK 를 건드리지 않고 오가는 바이트를 봅니다.

  • 경로가 / 인 POST 만 적습니다 — 카드 GET 과 정산의 /oauth/token 은 지나갑니다.
  • finally 에서 적으므로 클라이언트가 끊어도(1장) 줄은 남습니다. 스트림이면 마지막 이벤트까지 받은 뒤 한 줄입니다.
  • 완성 에이전트를 고치지 않으려고 uvicorn.run 을 바꿔 끼웠습니다. 제 서버라면 serve(…, middleware=…)(agents/common.py)나 Starlette 의 middleware= 로 넘기면 됩니다. SDK 쪽에서는 JSON-RPC id 가 ServerCallContext.state["request_id"] 에 들어 있습니다(jsonrpc_dispatcher.py:313).

TypeScript — express 미들웨어, 응답은 res.write·end 를 감싸 베낀다

8부에서 본 미들웨어 사슬(8부)의 맨 앞에 섭니다. 요청 본문은 직접 읽지 않고, 응답이 닫힐 때(close) SDK 가 읽어 둔 req.body 를 씁니다.

  • req.body 는 SDK 의 JSON-RPC 라우터가 express.json() 으로 채웁니다(server/express/index.js:3409).
  • express 의 req.path·res.get 대신 Node 의 req.url·res.getHeader 를 씁니다. 완성 에이전트를 감싸려고 이 미들웨어를 앱의 입구(app.handle)에 끼웠는데, 그 자리에서는 express 가 요청·응답에 제 메서드를 아직 붙이기 전이기 때문입니다(express/lib/application.js 의 handle 이 setPrototypeOf 로 붙인다).
  • 입구를 바꿔 끼운 것이 둘째 코드(17/logged.ts)입니다. 제 서버라면 app.use(jsonLog("이름")) 를 JSON-RPC 처리기보다 먼저 부르면 됩니다.

Go — HTTP 미들웨어가 줄을 열고 닫고, CallInterceptor 가 형 있는 값으로 채운다

Go SDK 의 가로채기(9부)는 요청·응답을 a2a 패키지의 형으로 받습니다. 바이트를 파싱할 필요가 없는 대신, JSON-RPC id 는 거기까지 오지 않습니다. 그래서 두 층에 하나씩 둡니다.

  • 줄을 여는 것은 같은 파일의 Middleware 입니다 — 본문에서 id 만 읽고 본문을 되돌려 놓은 뒤, 줄을 context 에 실어 보냅니다. 처리기가 끝나면 적습니다.
  • 스트림이면 After 가 이벤트마다 불립니다(a2asrv/intercepted_handler.go:118). 마지막 이벤트의 상태가 남습니다.
  • 오류는 Go 의 error 로 와서 JSON-RPC 코드가 아니라 오류 글을 적습니다. 코드로 바꾸는 함수(ToJSONRPCError)는 SDK 의 internal/jsonrpc/jsonrpc.go:145 에 있어 가져다 쓸 수 없습니다.
  • 완성 에이전트는 main 패키지라 감쌀 수 없어서, 교통 실행기를 옮겨 온 17/busops 에 달았습니다. common.Serve 의 Guard(JSON-RPC 앞 HTTP 층)와 Handler(SDK 옵션) 자리입니다.

Go 의 두 자리 — Guard 에 미들웨어, WithCallInterceptors 에 가로채기

카드 경로는 빠진다 — Guard 는 common.Serve 가 JSON-RPC 처리기에만 씌우는 자리라(12부의 Bearer 검사와 같은 자리) 카드 GET 은 적지 않습니다. 파이썬·TS 미들웨어가 경로로 거른 것과 같은 결과입니다.

섞인 메시 다섯 모두에 로그를 달고 — 이야기 한 문장, 그리고 "승인"

기획 TS · 숙소 파이썬 · 식사 TS · 교통 Go(17/busops) · 정산 파이썬입니다. 완성 에이전트 넷은 파일 그대로 17/logged 가 감쌌습니다. 탭은 세우지 않았습니다 — 이번 증거는 와이어가 아니라 로그입니다.

결과는 15부와 같다 — 합계 4,842,000원, 남은 예산 1,158,000원, COMPLETED 입니다(캡처의 ask 출력). 로그를 단 것이 결과를 바꾸지 않았습니다.

contextId 하나로 다섯 로그를 훑었다 — 일곱 줄, 에이전트마다 다른 task

follow 는 기획 에이전트 로그의 첫 줄(바깥에서 들어온 요청)의 ctx 를 열쇠로 다섯 파일을 차례로 훑습니다. grep 한 번과 같은 일입니다.

  • ctx <id2> 하나가 다섯 파일 모두에 있습니다. 다른 맥락의 줄은 없었습니다.
  • task 는 에이전트마다 다릅니다(<id3>, <id5>…). 기획의 두 줄과 정산의 두 줄은 각각 같은 작업에 이어 말한 것입니다 — AUTH_REQUIRED 뒤 COMPLETED.
  • rpc 열: 바깥의 ask(파이썬)가 보낸 두 요청은 UUID 둘, 기획 에이전트(TS)가 동료에게 보낸 다섯 요청은 모두 1 입니다. JSON-RPC id 는 요청과 응답을 짝짓는 값이지 에이전트를 가로질러 잇는 값이 아닙니다.

트레이스 문맥(W3C Trace Context)은 세 SDK 어디에서도 실려 가지 않는다

A2A 문서의 기업 운영 안내(topics/enterprise-ready.md)는 "A2A Clients and Servers should participate in distributed tracing systems. For example, use OpenTelemetry to propagate trace context … such as W3C Trace Context headers" 라고 씁니다. 스펙 본문에는 §1 의 원칙 한 줄("tracing, and monitoring")뿐입니다. 설치된 세 SDK 의 소스에서 낱말을 셌습니다.

  • 파이썬만 OpenTelemetry 를 씁니다 — utils/telemetry.py 한 파일의 장식자가 처리기·전송·큐에 span 을 엽니다(7부). 이 venv 에는 OpenTelemetry SDK 가 없어 기록하지 않는 span 입니다.
  • 세 SDK 모두 traceparent·tracestate 헤더를 보내지도 읽지도 않습니다. 파이썬 span 도 프로세스를 넘어 이어지지 않으니, 에이전트마다 따로 떨어진 트레이스가 됩니다.
  • Go 의 확장 전파 짝(9부)은 HeaderPredicate 로 넘길 헤더를 고르게 해 둡니다(a2aext/propagator.go:46). 트레이스 헤더를 아래로 넘기는 문은 되지만, 이 책은 시험하지 않았습니다.
그때까지는 contextId 가 가난한 사람의 트레이스다 — 맡기는 쪽이 맥락을 넘기는 한, 이 장의 한 줄과 grep 으로 다섯 에이전트를 잇습니다. 걸린 시간의 부모·자식 관계(어느 호출이 어느 호출 안에 있었나)는 트레이스만 줍니다.

3장 정리 — 잇는 열쇠는 contextId, SDK 기록은 그것을 잇지 못한다

  • JSON-RPC id·messageId·taskId 는 한 구간만 가리킵니다. 다섯 에이전트를 잇는 것은 기획 에이전트가 넘긴 contextId 입니다.
  • SDK 의 기본 기록: 파이썬은 DEBUG 에서만 요청마다(본문과 헤더까지 — §13.4 위반이 되기 쉽다), TS 는 오류 때만, Go 는 로깅 가로채기를 달면 두 줄이지만 서버가 지은 taskId 가 없고 request_id 는 새 UUID 입니다.
  • 우리 한 줄 ×3: 파이썬·TS 는 HTTP 미들웨어, Go 는 미들웨어 + CallInterceptor. 섞인 메시에서 ctx 하나로 일곱 줄을 이었습니다.
  • W3C 트레이스 헤더는 세 SDK 모두 다루지 않습니다.

3장 퀴즈

Q. 기획 에이전트의 로그에서 바깥 요청의 줄(rpc <id1>, task <id3>)을 찾았습니다. 숙소 에이전트의 로그에서 그 요청 때문에 생긴 줄을 찾으려면 어느 키로 찾아야 합니까? rpc 나 task 로는 왜 찾지 못합니까?

A. ctx 로 찾습니다 — 숙소의 줄도 <id2> 입니다(follow 의 출력). rpc 는 요청을 보낸 쪽이 짓는 값이라 숙소의 줄에는 기획 에이전트(TS)가 지은 1 이 있고, task 는 숙소 에이전트가 제 작업으로 새로 지은 <id5> 입니다.

4장

배포 체크리스트 — HTTPS, 카드 url, 캐시, 키 교체

HTTPS → 카드의 url → 카드 캐시 머리글 달기 → 조건부 GET 실행 → ETag 과 서명 → 키 교체의 순서 → 겹침 실행 → 키 공급자의 함정 → 본문 한도 달기 → 큰 본문 실행 → 서버 점검표 → 클라이언트 점검표

운영은 HTTPS — 이 책의 루프백 http 는 앞단 TLS 로 바꾼다

이 책의 에이전트는 모두 127.0.0.1 에 http 로 붙었습니다. 바깥에 내놓을 때 지켜야 할 것은 §13.4 의 "Transport Security" 넷입니다.

§13.4세기이 책에서
HTTPS(gRPC 는 TLS)로만MUST앞단 프록시가 TLS 를 끝내고 루프백으로 넘기는 그림(12부)
TLS 1.3 이상 권장, 강한 암호 묶음SHOULD서버의 TLS 는 SDK 밖 — uvicorn·express·net/http, 또는 앞단의 설정(12부)
HSTS(Strict-Transport-Security) 머리글SHOULD어느 서버 SDK 도 달지 않는다(12부) — 앞단이 단다
SSLv3·TLS 1.0·1.1 끄기SHOULD앞단의 설정
키·토큰도 HTTPS 를 전제한다 — Bearer 토큰(12부), 서명 검증용 공개 키(§8.4.3 "SHOULD be retrieved over secure channels"), 웹훅의 토큰(11부)이 모두 평문 http 에서는 지켜지지 않습니다.

카드의 url 은 바깥에서 닿는 주소 — 3부의 세 실험이 그 까닭이다

에이전트가 아는 자기 주소(127.0.0.1:포트)를 카드에 적으면, 클라이언트는 카드를 프록시에서 받고도 대화는 카드의 주소로 갑니다.

카드의 url무슨 일이증거
안쪽 주소인데 닿는다요청이 프록시를 건너뛴다 — TLS·인증·로그가 빠진다3부
안쪽 주소인데 닿지 않는다카드는 오고 대화는 연결 실패3부
바깥 주소(--url)모든 요청이 프록시를 지난다3부
배포 때 바꿀 곳 — supportedInterfaces[].url 을 바깥의 https:// 주소로, 서명한 카드라면 그 주소로 다시 서명합니다(12부). 이 책의 메시가 모두 --url 로 탭의 주소를 적은 것도 같은 까닭입니다(3부).

카드 캐시 머리글 — 파이썬은 인자 하나, TS 는 이미 있고, Go 는 처리기를 감싼다

§8.6.1 은 카드 응답에 Cache-Control(max-age)과 ETag 을 SHOULD 로 둡니다. 3부에서 잰 대로 둘 다 다는 것은 TS 뿐이었고(3부), TCK 도 같은 자리를 짚었습니다(16부).

  • 파이썬 — create_agent_card_routes(…, cache_control=) 입니다. 문서 문자열의 말로는 max-age 는 "only the deployment knows" 라 기본값이 없고, ETag 은 늘 답니다(routes/agent_card_routes.py:87).
  • TS — agentCardHandler({…, cache: {maxAge}}), 주지 않으면 3600초입니다(server/express/index.js:5880). 고칠 것이 없어 완성 에이전트 그대로 씁니다.
  • Go — SDK 의 카드 처리기에는 둘 다 없어, 응답을 받아 두고 본문 해시로 ETag 을 짓는 미들웨어로 감쌌습니다(17/busops 의 --cache-age).

다섯 서버에 카드를 두 번 — 머리글을 단 파이썬·Go 도 304 를 돌려준다

완성 교통 에이전트 셋(그대로)과, max-age 600초를 단 파이썬·Go 둘입니다(17/edge 명세). 카드를 받고, 받은 ETag 을 If-None-Match 에 실어 다시 물었습니다.

  • 완성 Go 에이전트(bus-go)는 ETag 이 없어 조건부로 물을 수조차 없습니다. 감싼 뒤(ops-go)에는 304 입니다.
  • ETag 의 길이가 다릅니다 — 파이썬은 SHA-256 전체, TS 와 우리 Go 는 앞 16글자입니다. ETag 은 그 서버만 대 보는 값이라 모양은 상관없습니다.
  • max-age 는 클라이언트가 묻지도 않고 카드를 쓰는 시간입니다. 카드를 바꾸면(키 교체 포함) 그만큼 늦게 퍼집니다 — 다음 슬라이드들의 겹침 기간을 이보다 길게 잡습니다.

파이썬의 ETag 은 서명을 빼고 짓는다 — 서명만 바꾼 카드는 304 로 끝난다

세 ETag 이 카드의 어느 부분으로 지어지는지는 키 교체 때 갈립니다.

무엇의 해시서명만 바뀌면
파이썬signatures 를 뺀 카드(routes/agent_card_routes.py:57-59)ETag 그대로 → 304 → 클라이언트는 옛 서명을 쥔다
TS보낼 JSON 본문 전체(server/express/index.js:5875)ETag 바뀜 → 200, 새 서명
우리 Go보낼 본문 전체(17/deploy)ETag 바뀜 → 200, 새 서명
파이썬은 일부러 그랬다 — 문서 문자열은 ES256 처럼 서명마다 값이 달라지는 알고리즘에서도 304 가 되게 하려고 서명을 뺐고, 그 대가로 "a 304 leaves the client on the signature it already holds" 라고 적습니다(agent_card_routes.py:40-50). 키를 바꿀 때는 카드의 version 도 함께 올려 ETag 을 바꿉니다. 그래야 옛 키를 거둘 때 옛 서명만 쥔 클라이언트가 남지 않습니다.

서명 키 교체 — 새 키로 서명을 더하고, 키 저장소가 퍼진 뒤에 옛 키를 거둔다

16부의 점검표에서 비워 둔 줄입니다 — "만료·폐기된 키로 검증하지 않기"(16부). §8.4.3 은 "Expired or revoked keys MUST NOT be used for verification" 과 함께 "Multiple signatures MAY be present to support key rotation" 이라고 씁니다.

 ① 지금      카드 서명: 옛 키            클라이언트 키 저장소: 옛
 ② 겹침      카드 서명: 옛 키 + 새 키     저장소: 옛 (아직) / 옛+새
 ③ 겹침 뒤   카드 서명: 새 키            저장소: 새 (옛 키는 거둔다)
 ④ 폐기 뒤   누가 ① 의 카드를 다시 내밀어도 → 옛 키가 없으니 틀림

 겹침 기간 ≥ 카드의 max-age + 클라이언트가 키 저장소를 새로 받는 주기
키를 고르는 것은 검증하는 쪽 — 12부에서 본 대로 우리 클라이언트는 jku 를 따라가지 않고 미리 받아 둔 키만 믿습니다(12부). 그러니 교체는 "그 저장소에 새 키를 먼저 넣고, 옛 키를 나중에 뺀다" 의 차례입니다.

같은 카드에 kid 마다 서명 하나 — 서명기를 두 번 부르면 서명 둘

파이썬 SDK 의 서명기는 카드의 signatures 에 서명을 하나 덧붙입니다(utils/signing.py:95). 정산 에이전트의 키(settlement-2026)와 이 장의 시험용 새 키(settlement-2027)로 두 번 부릅니다.

  • 검증기는 서명을 차례로 대 보고 하나라도 맞으면 통과입니다(utils/signing.py:139-160). 그래서 겹침 동안 옛 키만 아는 클라이언트도 통과합니다.
  • 키 공급자가 모르는 kid 에 PyJWKError 를 던지면 검증기는 "이 서명은 틀림" 으로 보고 다음 서명으로 넘어갑니다.

네 단계를 돌렸다 — 겹침 동안엔 누구나 맞음, 겹침 뒤엔 옛 키만 아는 쪽이 틀림

  • ② 서명 둘인 카드는 옛 키만 아는 쪽과 둘을 받은 쪽 모두에게 맞음 — 이 기간에 클라이언트들이 새 키를 받습니다.
  • ③ 옛 서명을 거둔 뒤에도 옛 키만 쥔 클라이언트는 틀림입니다. 겹침이 짧으면 생기는 일이고, 그 클라이언트는 카드를 믿지 못합니다(12부의 가짜 카드와 같은 판정).
  • ④ 옛 키를 저장소에서 뺀 클라이언트에게는 ① 의 카드를 다시 내밀어도 틀림입니다. 이것이 §8.4.3 의 "revoked keys MUST NOT be used" 를 지키는 방법입니다 — 검증기가 아니라 키 저장소에서.

⑤ 모르는 kid 에 KeyError 를 내는 키 공급자 — 검증기 밖으로 새어 나온다

⑤ 는 ③ 과 같은 카드·같은 저장소인데, 키 공급자가 keys[kid] 로만 찾습니다. 결과는 "틀림" 이 아니라 KeyError 입니다.

  • 파이썬 검증기의 고리는 PyJWTError 만 잡습니다(utils/signing.py:158). 그 밖의 예외는 SignatureVerificationError 로 바뀌지 않고 그대로 올라옵니다. SignatureVerificationError 만 잡는 호출자는 그 자리에서 깨집니다.
  • 12부의 verify.py 와 완성 기획 에이전트(파이썬)의 키 공급자가 이 모양입니다(agents/planner.py:104). 지금은 kid 가 하나뿐이라 드러나지 않았고, 정산 에이전트가 새 키로만 서명하는 날 드러납니다. 이 책은 완성 에이전트를 고치지 않고 이 자리에 적어 둡니다.
모르는 kid 는 "틀림" 으로 — 키 공급자는 모르는 kid 에 PyJWKError(또는 그 하위 예외)를 던집니다. 그래야 서명이 여럿인 카드에서 다음 서명으로 넘어가고, 모두 틀리면 InvalidSignaturesError 하나로 끝납니다.

본문 한도 — TS 만 100KB 가 있고, 파이썬·Go 는 우리가 단다

§13.4 "Agents SHOULD implement appropriate limits on message sizes, file sizes, and request complexity". 4부에서 TS 서버만 102,400바이트에서 413 을 냈습니다(4부). 파이썬·Go 에는 SDK 앞에 미들웨어를 하나씩 세웁니다(한도 100,000바이트).

스펙에 "너무 크다" 는 오류가 없다 — 둘 다 HTTP 413 에 JSON-RPC 의 Invalid Request(-32600)를 실었습니다. 우리가 고른 것입니다. TS 의 413 에는 JSON-RPC 객체가 없습니다.

150KB 를 두 가지로 — 길이를 밝히면 셋 다 413, chunked 면 파이썬은 지나가고 Go 는 "parse error"

같은 다섯 서버에 150,238바이트 SendMessage 를 두 번 보냈습니다 — Content-Length 를 밝혀서 한 번, Transfer-Encoding: chunked 로 한 번.

  • 한도가 없는 완성 파이썬·Go 는 둘 다 받아 배차까지 끝냈습니다(COMPLETED).
  • 파이썬 — 우리 BodyLimit 는 Content-Length 만 봐서 chunked 는 지나갔습니다. 문서 문자열에 적은 그 빈틈입니다. 막으려면 receive 를 감싸 받은 바이트를 셉니다.
  • Go — chunked 는 MaxBytesReader 가 100,000바이트에서 읽기를 끊었고, SDK 는 그 오류를 해독 실패로 보아 -32700 parse error 를 HTTP 200 으로 돌려줬습니다(a2asrv/jsonrpc.go:373). 클라이언트는 제 JSON 이 깨진 줄 압니다.
  • TS — express 의 본문 읽기가 길이를 세므로 두 방식 모두 413 입니다(본문은 HTML).

4장 퀴즈

Q. 본문 한도 100,000바이트를 단 Go 교통 에이전트에 150KB 요청을 chunked 로 보낸 클라이언트가 -32700 parse error: unexpected EOF 를 받았습니다. 클라이언트의 JSON 이 깨졌던 것입니까? 같은 본문을 Content-Length 를 밝혀 보내면 무엇을 받습니까?

A. 아닙니다. 같은 본문을 한도가 없는 Go 서버는 받아 COMPLETED 까지 갔습니다. MaxBytesReader 가 100,000바이트에서 읽기를 끊었고 SDK 가 그 오류를 해독 실패로 보아 -32700 을 HTTP 200 으로 돌려준 것입니다. 길이를 밝히면 우리 미들웨어가 읽기 전에 413 과 -32600 요청 본문이 너무 큽니다 를 돌려줍니다(실행).
