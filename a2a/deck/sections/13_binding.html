13부

전송 바인딩 — JSON-RPC·HTTP+JSON·gRPC

세 바인딩의 동등성과 메서드 대응표 → HTTP+JSON(REST) ×3 → gRPC ×3 → 한 서버 세 바인딩 → 스펙의 어긋남

같은 작업, 다른 겉옷 — 이 부는 메서드가 와이어에 실리는 세 가지 방식이다

12부까지의 요청은 모두 JSON-RPC 였습니다. A2A 의 연산(§3)과 데이터 모델(§4)은 바인딩과 따로 정의되어 있고, 스펙은 그것을 와이어에 싣는 표준 바인딩(binding)을 셋 둡니다 — JSON-RPC(§9), gRPC(§10), HTTP+JSON/REST(§11). 이 부는 나머지 둘을 세 SDK 로 돌려 봅니다.

장무엇을
1장세 바인딩의 동등성(§5.1)과 메서드 대응표(§5.3) — proto 의 HTTP 주석, 같은 요청을 두 바인딩으로
2장HTTP+JSON(REST) ×3 — 서버 셋·경로와 동사·응답 모양·오류 → HTTP 상태·SSE 스트림·클라이언트 셋과 3×3
3장gRPC ×3 — proto, 서버·클라이언트, 스트리밍, 오류 → gRPC status
4장한 서버 세 바인딩 — supportedInterfaces 여러 개, 클라이언트의 선택
5장스펙의 어긋남 — SubscribeToTask 의 REST 동사(proto GET, §5.3 POST)와 SDK 의 실제 동작
이 부의 방식 — 완성 에이전트의 카드와 실행기를 고치지 않고 빌려, 바인딩만 바꿔 띄웁니다. 실행기가 같으니 와이어에서 달라지는 것은 모두 바인딩의 몫입니다.

1장

세 바인딩의 동등성과 메서드 대응표

동등성의 네 가지 MUST → 바인딩이 정하는 것 → §5.3 대응표 → proto 의 HTTP 주석 → 본문·쿼리·tenant 짝 → 같은 요청 두 바인딩: 명세 → 요청 → 응답 → 오류 → 같은 것과 다른 것

여러 바인딩을 열면 넷이 같아야 한다 — 기능·동작·오류·인증 (§5.1 MUST)

바인딩은 고를 수 있는 겉옷입니다. 그래서 스펙은 한 에이전트가 여러 바인딩을 열 때 "어느 문으로 들어와도 같은 에이전트" 이기를 요구합니다.

자리스펙의 말세기
§5.1Identical Functionality — "the same set of operations and capabilities"MUST
§5.1Consistent Behavior — "semantically equivalent results for the same requests"MUST
§5.1Same Error Handling — "Map errors consistently using appropriate protocol-specific codes"MUST
§5.1Equivalent Authentication — 카드에 적은 같은 인증 스킴MUST
§5.2지원하는 프로토콜은 모두 카드에 적는다 / 클라이언트는 그 가운데 아무것이나 / 대체(fallback) 논리MUST / MAY / SHOULD
"semantically equivalent" — 바이트가 같으라는 말이 아닙니다. 봉투와 오류 표현은 바인딩마다 다르고(§5.4), 그 안의 작업·메시지·오류의 뜻이 같아야 합니다. 이 장의 끝에서 같은 요청을 두 바인딩으로 보내 그 선을 눈으로 긋습니다. 카드에 여럿을 적고 고르는 §5.2 는 4장의 몫입니다.

바인딩이 정하는 것은 다섯 자리 — 메서드 이름, 매개변수, 서비스 매개변수, 오류, 스트림

연산(SendMessage …)과 메시지 모양(Task …)은 셋이 같습니다. 바인딩 절(§9–§11)이 따로 정하는 자리만 모으면 이렇습니다.

§5.3 대응표 — 열한 연산이 바인딩마다 어떤 이름인가

JSON-RPC 메서드와 gRPC 메서드는 이름이 같습니다(§9.1 "PascalCase method names matching gRPC conventions"). REST 는 동사와 경로로 같은 연산을 고릅니다.

콜론 뒤의 낱말 — /tasks/{id}:cancel 처럼 자원 경로 끝의 :낱말 이 연산을 고릅니다. §10 첫머리는 gRPC 와 HTTP 사이의 대응에 Google 의 API 지침(API guidelines)을 쓴다고 밝히는데, 이 경로 꼴이 그 대응에서 나옵니다.

proto 에도 대응표가 있다 — 각 rpc 에 붙은 HTTP 주석을 SDK 에서 읽는다

규범인 proto(§10.1)의 rpc 마다 google.api.http 주석이 붙어 있습니다. 파이썬 SDK 의 a2a_pb2 는 그 proto 를 컴파일한 것이라 주석까지 들고 있으므로, 표를 손으로 옮기지 않고 SDK 에서 뽑았습니다.

  • §5.3 의 표와 열한 줄 가운데 열 줄이 같습니다. 하나 다른 것이 SubscribeToTask — proto 는 GET, §5.3·§11.3.2 는 POST 입니다. 세 SDK 가 이 어긋남을 어떻게 받는지는 5장에서 봅니다.
  • gRPC 의 메서드 경로는 패키지와 서비스 이름이 붙은 /lf.a2a.v1.A2AService/SendMessage 꼴입니다(3장).

본문이 없는 동사는 경로와 쿼리로 — 그리고 모든 경로에 /{tenant} 짝이 있다

주석의 body: "*" 는 "요청 메시지 전체가 본문" 이라는 뜻입니다(위 출력의 [본문]). GET·DELETE 에는 본문이 없으니 경로에 넣은 필드({id}) 밖의 필드는 쿼리로 갑니다.

§11.5 의 규칙세기
GET·DELETE 의 매개변수는 경로나 쿼리로MUST
쿼리 이름은 JSON 과 같은 camelCase(contextId, historyLength)MUST
열거값은 이름(status=TASK_STATE_WORKING), 불은 true/false(규칙)
중첩 객체는 쿼리에 못 싣는다 — 그런 연산은 POST 와 본문MUST
스펙의 표에 없는 짝 — proto 의 열한 규칙은 모두 같은 경로를 /{tenant} 아래에 한 번 더 둡니다(additional_bindings, 위 출력의 "11/11"). §5.3 과 §11.3 의 표에는 이 꼴이 없습니다. 카드의 인터페이스에 적는 tenant(3부)가 REST 에서는 경로의 첫 마디가 되는 자리입니다. 세 서버가 이 짝을 실제로 받는지는 2장에서 봅니다.

같은 실행기, 두 바인딩 — 완성 숙소 에이전트와 그 REST 판을 나란히 띄운다

rpc 는 완성 숙소 에이전트 그대로입니다. rest 는 그 카드와 실행기를 빌려 HTTP+JSON 문 하나로 띄운 13/rest_agent.py 입니다(2장). 둘 다 탭 뒤에 두고, 같은 메시지와 없는 작업 조회를 보냅니다.

견적 줄은 같다 — 실행기가 찍는 줄은 바인딩과 상관없이 같습니다. REST 판에만 있는 Request error: … 줄은 SDK 의 REST 오류 처리기가 남기는 기록입니다(utils/error_handlers.py:142). JSON-RPC 쪽은 같은 "없는 작업" 에 아무것도 찍지 않았습니다.

요청 — JSON-RPC 의 params 가 REST 에서는 본문 전체가 된다

메시지 부분은 글자까지 같습니다. JSON-RPC 는 봉투(jsonrpc·id·method)로 연산을 고르고, REST 는 POST /message:send 로 고릅니다.

REST 본문 = SendMessageRequest — §11.4 "structurally equivalent to the Protocol Buffer definitions". JSON-RPC 의 params 도 같은 메시지입니다(§9.4.1). REST 에는 id 가 없으니, 요청과 응답을 잇는 것은 HTTP 연결 그 자체입니다.

응답 — JSON-RPC 의 result 가 REST 에서는 본문 전체가 된다

두 응답 모두 SendMessageResponse({"task": …})입니다. 다른 것은 바깥 한 겹과 Content-Type 뿐입니다.

  • REST 판은 Content-Type: application/a2a+json 으로 답했습니다(§11.1 SHOULD). JSON-RPC 쪽은 §9.1 대로 application/json 입니다.
  • 그 아래 아티팩트·이력은 두 와이어에서 id 만 빼고 같습니다 — DataPart 의 30.0 까지(4부). 같은 SDK 의 같은 직렬화기를 지나기 때문입니다.

오류 — 같은 ErrorInfo, 다른 그릇: -32001 과 404

없는 작업을 물었습니다. §5.4 의 표에서 TaskNotFoundError 는 JSON-RPC -32001, gRPC NOT_FOUND, HTTP 404 Not Found 입니다.

  • JSON-RPC 는 HTTP 로는 성공(200 OK)이고 오류는 error.code 에 있습니다. REST 는 HTTP 상태 자체가 오류이고, 본문의 error.code 는 그 상태 번호(404)를, error.status 는 gRPC 의 이름(NOT_FOUND)을 되풀이합니다.
  • 뜻을 실은 ErrorInfo(reason: TASK_NOT_FOUND, domain: a2a-protocol.org)는 같습니다 — JSON-RPC 는 data 배열에, REST 는 details 배열에 둡니다(§9.5·§11.6).

1장 퀴즈

Q. 1장의 실험에서 없는 작업을 물었을 때, JSON-RPC 쪽 HTTP 상태 줄은 무엇이었고 REST 쪽은 무엇이었습니까? 클라이언트가 "작업이 없다" 는 뜻을 바인딩과 상관없이 같은 방법으로 읽으려면 어디를 보면 됩니까?

A. JSON-RPC 는 200 OK(오류는 본문의 error.code: -32001), REST 는 404 Not Found 였습니다(오류 슬라이드). 두 쪽 모두 google.rpc.ErrorInfo 를 실었고 그 reason 이 TASK_NOT_FOUND 입니다 — JSON-RPC 는 error.data, REST 는 error.details 배열 안입니다.

2장

HTTP+JSON(REST) ×3

§11 의 요구 → 파이썬 서버 → TypeScript 서버 → Go 서버 → 완성 에이전트를 빌린 방법 → 세 서버의 경로 표 → 맨손 요청 여덟 → 보내기 → 세 서버의 응답 → 읽기 → 목록 → 취소 오류 → 오류 본문 → 깨진 JSON → 없는 경로 → tenant 경로 → 스트림 명세 → SSE → 세 서버의 SSE → 스트림 오류 → 클라이언트 ×3 → 클라이언트의 머리글 → 3×3 → Go 클라이언트의 server error → 사라지는 스트림 오류 → 세 SDK 비교

HTTP+JSON 바인딩의 약속 — 동사와 경로, a2a+json, 머리글, SSE (§11)

REST 바인딩의 절(§11)은 짧습니다. 메시지 모양은 proto 에 맡기고, HTTP 쪽 약속만 적습니다.

자리스펙의 말세기
§11.1요청·응답의 Content-Type 은 application/a2a+jsonSHOULD
§11.1"Standard HTTP verbs (GET, POST, PUT, DELETE)", 자원 꼴 URL, 스트림은 SSE—
§11.2서비스 매개변수(A2A-Version·A2A-Extensions)는 HTTP 머리글로MUST
§11.4요청·응답은 "structurally equivalent to the Protocol Buffer definitions"—
§11.6오류는 google.rpc.Status JSON, A2A 오류는 details 에 ErrorInfoMUST

PUT 은 쓰지 않는다 — §11.1 이 PUT 을 꼽지만, 대응표(1장)의 열한 연산에는 PUT 이 없습니다. 실제로 쓰는 동사는 GET·POST·DELETE 셋입니다.

파이썬 서버 — create_jsonrpc_routes 자리에 create_rest_routes 한 줄

13/rest_agent.py 는 완성 숙소·식사 에이전트 모듈에서 card(url) 과 실행기 클래스를 가져와(3부의 two_doors.py 와 같은 방법) 바인딩만 바꿔 띄웁니다.

  • 요청 처리기(DefaultRequestHandler)는 JSON-RPC 판과 같습니다. 바뀐 것은 경로 목록과 카드의 protocolBinding 하나입니다.
  • create_rest_routes(handler) 는 path_prefix 를 주지 않으면 뿌리(/message:send …)에 답니다. 그래서 카드의 주소 http://…/ 뒤에 §5.3 의 경로가 그대로 붙습니다.

TypeScript 서버 — jsonRpcHandler 자리에 restHandler

TS 의 완성 에이전트는 공용 모듈의 serve(card, executor, port) 를 부릅니다. 13/rest_common.ts 는 그 serve 의 REST 판입니다.

express Router 하나 — restHandler 는 Router 를 돌려주고, 그 안에서 본문 파서(express.json)와 Content-Type 검사까지 직접 답니다(server/express/index.js:6079). JSON-RPC 처리기와 마찬가지로 앞에 따로 파서를 두지 않아도 됩니다.

Go 서버 — NewJSONRPCHandler 자리에 NewRESTHandler

13/restmount 는 완성 에이전트의 common.Serve 의 REST 판입니다. Go 의 전송 처리기는 그냥 http.Handler 라서, 표준 ServeMux 에 꽂습니다(9부).

뿌리 / 에 통째로 — REST 처리기는 안에 제 ServeMux 를 두고 경로를 가립니다(a2asrv/rest.go:48). 그래서 바깥 mux 에는 "/" 하나만 걸고, 카드 경로는 더 긴 패턴이라 먼저 잡힙니다.

완성 에이전트를 고치지 않고 빌린 방법 — TS 는 해석 훅, Go 는 같은 패키지

파이썬 에이전트는 import 할 수 있지만, TS 의 에이전트 파일은 아무것도 내보내지 않고 모듈 맨 위에서 곧장 서버를 띄우고, Go 의 에이전트는 package main 이라 import 할 수 없습니다. 두 언어에서 실행기를 그대로 쓰려고 고른 방법입니다.

  • TS — module.registerHooks(Node 24)의 해석 훅이 에이전트 파일의 import … from "./common.ts" 만 가로챕니다. rest_common.ts 는 진짜 common.ts 를 export * 하고 serve 하나만 덮습니다(8부의 mock.module 과 같은 생각인데, 실험 플래그가 필요 없다).
  • Go — 13/rest_lodging/agent.go 는 agents/lodging/main.go 를 가리키는 심볼릭 링크입니다. 같은 디렉터리라 같은 패키지가 되어 소문자 card·executor 가 보이고, init() 이 서버를 띄운 채 돌아오지 않으니 그 파일의 main() 은 불리지 않습니다.

실험 — 세 서버에 SDK 없이 같은 요청 여덟 개

세 언어의 REST 숙소 에이전트를 탭 뒤에 두고, 13/rest_raw.py 가 httpx 로 맨 HTTP 요청을 보냅니다. 화면에는 요청마다 한 줄 요약만 찍고, 몸통은 탭이 적습니다.

tenant 경로 — 마지막 요청의 /bosang-hq/… 는 이 카드에 없는 경로입니다. proto 의 /{tenant} 짝(1장)을 서버가 받는지 보려고 일부러 보냅니다.

여덟 요청의 요약 — 앞의 다섯은 상태와 reason 이 같고, 뒤의 셋에서 서버가 갈린다

  • 같은 것 — 보내기·읽기·목록은 200, COMPLETED 취소는 400 FAILED_PRECONDITION + TASK_NOT_CANCELABLE, 없는 작업은 404 NOT_FOUND + TASK_NOT_FOUND. §5.4 의 표 그대로입니다.
  • 다른 것 — Content-Type(Go 는 늘 application/json, 파이썬은 오류만 application/json), 깨진 JSON 의 reason 셋, 없는 경로(파이썬은 307), tenant 경로(Go 만 404). 아래에서 하나씩 봅니다.

보내기 — POST /message:send, 본문은 메시지, 답은 {"task": …}

파이썬 서버와 주고받은 첫 요청입니다. 1장의 REST 판과 같은 모양을 이번에는 세 서버에 견줍니다.

요청에는 A2A-Version 만 붙였다 — §11.2 의 서비스 매개변수는 머리글로 갑니다. 이 실험은 Content-Type 을 application/json(httpx 의 기본)으로 보냈는데, 세 서버 모두 받아 줬습니다. §11.1 의 application/a2a+json 은 SHOULD 입니다.

세 서버의 응답 — 같은 Task, 다른 Content-Type·숫자·키 차례

  • Go 서버만 application/json 입니다(rest.go:63). 파이썬과 TS 는 a2a+json 이고, TS 는 charset=utf-8 을 붙입니다.
  • DataPart 의 수는 파이썬만 30.0(4부), TS·Go 는 30 입니다. Go 는 키를 id 다음 가나다순으로 쓰고, 이력의 사용자 메시지에 contextId·taskId 를 채우지 않습니다 — 받은 메시지를 그대로 저장하기 때문입니다(4부의 이력 저장 비교).

읽기와 목록 — GET 의 매개변수는 쿼리로, 답은 Task 그 자체

GetTask 의 historyLength 와 ListTasks 의 contextId 는 본문이 아니라 쿼리입니다(§11.5). 경로의 {id} 가 GetTaskRequest.id 입니다.

  • GET /tasks/{id} 의 답은 {"task": …} 로 감싸지 않은 Task 입니다 — proto 의 rpc GetTask(GetTaskRequest) returns (Task) 그대로입니다. JSON-RPC 의 result 도 같은 반환형이라 Task 그 자체입니다.
  • historyLength=0 에 세 서버 모두 이력 없이 답했습니다(요약의 history: 0). 목록의 본문은 JSON-RPC 때와 같습니다 — 파이썬 목록에만 기본값 필드가 붙는 것까지(11부).

끝난 작업 취소 — 셋 다 400 과 TASK_NOT_CANCELABLE, 말과 metadata 는 제각각

  • error.code(400)·error.status(FAILED_PRECONDITION)·reason 은 셋이 같습니다 — 클라이언트가 기댈 자리는 여기입니다.
  • message 는 사람이 읽는 글이라 셋이 다릅니다. Go 는 SDK 안의 감싼 오류 사슬을 그대로 내보냅니다. metadata 는 파이썬 {}, TS 없음, Go taskId·timestamp — JSON-RPC 때(5부)와 같은 버릇입니다.

오류 본문은 google.rpc.Status — details 의 ErrorInfo 가 A2A 오류의 이름표다

§11.6 은 HTTP 상태만으로는 모자란다고 말합니다. TaskNotCancelableError 와 PushNotificationNotSupportedError 가 둘 다 400 이기 때문입니다. 그래서 A2A 오류에는 ErrorInfo 를 반드시(MUST) 싣습니다.

"Error Code" 가 두 번 — §11.6 은 A2A 의 오류 코드를 "HTTP status code and the error.code field" 로 옮기라고 합니다. 그래서 404 가 상태 줄과 본문에 두 번 나옵니다. 오류의 종류를 가르는 것은 숫자가 아니라 reason 입니다.

깨진 JSON — 400 은 같고, reason 은 셋이 다 다르다

닫히지 않은 JSON 을 보냈습니다. 이것은 A2A 오류(§3.3.2 의 표)가 아니라 JSON-RPC 라면 -32700 인 일반 오류입니다. §5.4 와 §11.6 은 A2A 오류의 reason 만 정하고, 이런 오류의 reason 은 정하지 않습니다.

  • 파이썬은 protobuf 의 파서 오류를 INVALID_REQUEST 로(error_handlers.py:120), TS 는 RequestMalformedError 의 INVALID_PARAMS 로, Go 는 ErrParseError 의 PARSE_ERROR 로 답했습니다.
  • 세 이름 모두 JSON-RPC 표준 오류의 이름을 빌린 것이지만 고른 것이 다릅니다. §3.3.2 는 검증 오류의 예로 "HTTP 400 Bad Request, gRPC INVALID_ARGUMENT" 만 들므로, 클라이언트는 status 까지만 기댈 수 있습니다.

없는 경로 — 셋 다 google.rpc.Status 가 아니고, 파이썬은 307 로 돌려보낸다

REST 처리기는 경로가 맞아야 불립니다. 맞는 경로가 없으면 그 밑의 웹 틀(Starlette·express·net/http)이 답합니다.

307 의 까닭 — 파이썬 경로 목록 끝의 Mount('/{tenant}') 가 /nope/ 와는 맞습니다. Starlette 는 맞는 경로가 없을 때 끝에 / 를 붙여 맞으면 그리로 돌려보냅니다(redirect_slashes, starlette/routing.py:713). 오타 난 경로가 "없다" 대신 "저리로 가라" 를 받는 셈입니다.

tenant 경로 — 파이썬·TS 는 받고, Go 의 NewRESTHandler 는 모른다

proto 의 /{tenant}/message:send 짝(1장)으로 보냈습니다. 카드에는 tenant 가 없는데도 파이썬·TS 는 견적을 냈습니다.

  • 파이썬은 경로의 값을 호출 맥락의 tenant 로(rest_dispatcher.py:109), TS 는 본문·쿼리의 tenant 에 덮어써서(index.js:6185) 넘깁니다. 어느 쪽도 카드에 적은 tenant 와 견주지 않았습니다.
  • Go 는 NewRESTHandler 에 tenant 경로가 없고(// TODO: handle tenant, rest.go:50), 경로 틀을 받는 NewTenantRESTHandler("/{*}", …) 를 따로 둡니다(rest.go:76). tenant 를 쓰는 Go 에이전트는 그것을 골라 달아야 합니다.

REST 의 스트림 — 식사 에이전트 셋에 POST /message:stream

스트림은 완성 식사 에이전트(10부)를 같은 방법으로 REST 문에 올려 봅니다. 정상 요청 하나, 그리고 없는 작업(taskId: t-nope)에 잇는 요청 하나를 세 서버에 차례로 보냅니다.

SSE 의 data 하나에 StreamResponse 하나 — JSON-RPC 봉투가 없다

파이썬 서버의 스트림에서 이벤트마다 첫 키만 골라 냈습니다. 순서와 종류는 10부의 JSON-RPC 스트림과 같습니다.

  • JSON-RPC 의 SSE 는 data 마다 {"jsonrpc": "2.0", "id": …, "result": {…}} 였습니다. REST 는 그 result 자리의 StreamResponse(task·statusUpdate·artifactUpdate 가운데 하나)만 씁니다(§11.7).
  • 첫 이벤트는 SUBMITTED 의 Task, 마지막은 COMPLETED 의 statusUpdate — §11.7 의 "first a Task …, then zero or more status or artifact update events" 그대로입니다.

스트림 오류 — 파이썬·TS 는 404 JSON, Go 는 200 SSE 안의 {"error": …}

없는 작업에 잇는 스트림 요청입니다. 오류는 첫 이벤트보다 먼저 났습니다.

  • 파이썬·TS 는 첫 이벤트를 먼저 꺼내 본 뒤에야 SSE 머리를 씁니다(rest_dispatcher.py:147, TS 의 sendStreamResponse). 그래서 시작 전 오류는 보통의 404 오류 응답이 됩니다.
  • Go 는 머리부터 씁니다(sseWriter.WriteHeaders(), rest.go:277). 그 뒤의 오류는 data 에 {"error": …} 를 실어 보낼 수밖에 없고, event: error 표시도 붙이지 않습니다. 파이썬·TS 서버는 도중의 오류에 event: error 를 붙입니다(rest_dispatcher.py:163, formatSSEErrorEvent). §11.7 은 스트림 속 오류의 모양을 정하지 않습니다.

파이썬 클라이언트 — HTTP+JSON 을 쓰겠다고 말해야 한다

이제 SDK 클라이언트로 같은 REST 서버들을 부릅니다. 세 클라이언트는 같은 세 가지를 합니다 — 막는 SendMessage, 없는 작업 GetTask, 없는 작업에 잇는 스트림.

  • supported_protocol_bindings 가 비면 JSON-RPC 만 압니다(client/client.py:56 의 주석 "Empty implies JSONRPC only"). 카드에 HTTP+JSON 문만 있으니 이 줄이 없으면 맞는 전송을 못 찾습니다(3부).
  • 막는 호출과 스트림을 가르는 것은 streaming 설정이라, 클라이언트를 둘 지었습니다(7부). 그래서 탭에는 카드 요청이 두 번 찍힙니다.

TypeScript 클라이언트 — 공장이 기본으로 REST 를 안다

바뀐 것이 없다 — ClientFactory 의 기본 전송은 [JsonRpcTransportFactory, RestTransportFactory] 입니다(3부). 카드가 HTTP+JSON 문만 적었으니 공장이 RestTransport 를 짓고, 코드는 JSON-RPC 때와 한 글자도 다르지 않습니다.

Go 클라이언트 — 해석기와 공장, 그리고 표지 오류로 가르기

오류는 errors.Is 로 — Go 의 REST 전송은 받은 ErrorInfo.reason 을 표지 오류로 되돌립니다(internal/rest/rest.go 의 ConvertErrorBody). kindOf 는 그 표지 가운데 무엇에 걸리는지 찍습니다.

세 클라이언트의 머리글 — 셋 다 application/json 으로 보낸다

파이썬 서버 앞의 탭이 본 보내기 요청의 머리입니다(파이썬 → TS → Go 차례).

  • §11.1 의 application/a2a+json(SHOULD)으로 보내는 클라이언트는 없습니다. Accept 는 파이썬 */*, TS 둘 다, Go application/json 만입니다.
  • TS 는 본문이 없는 GET 에도 Content-Type 을 붙입니다(_buildHeaders, client/index.js:6311). 서버 셋 모두 문제 삼지 않았습니다.

3×3 — 보내기는 아홉 칸 모두 되고, 오류는 세 짝에서 어긋난다

세 클라이언트가 세 REST 서버를 차례로 부릅니다. 탭은 파이썬 서버 앞에만 두었습니다.

  • Go 클라이언트 × TS 서버 — 없는 작업도, 스트림 잇기도 "task not found" 가 아니라 "server error" 로 왔습니다(다음 슬라이드).
  • 파이썬·TS 클라이언트 × Go 서버의 스트림 — 파이썬은 ParseError, TS 는 오류 없이 끝났습니다(그다음 슬라이드). 같은 오류가 다른 칸에서는 TaskNotFoundError 입니다.

Go 클라이언트는 application/json 오류만 읽는다 — TS 서버의 a2a+json 오류는 "server error"

TS 서버는 오류도 application/a2a+json 으로 보냅니다(경로 표). §11.1 대로입니다. 그런데 Go 의 REST 전송은 오류 본문을 읽기 전에 Content-Type 부터 봅니다.

Go 서버의 스트림 오류 — 파이썬은 깨진 이벤트로, TS 는 아무 일도 없던 것으로 읽는다

Q. TS 클라이언트로 Go REST 서버에 "없는 작업에 잇는 스트림" 을 보냈더니 성공 이 찍혔습니다. 서버는 무엇을 보냈고, 왜 TS 클라이언트는 그것을 오류로 알아보지 못했습니까?

A. Go 서버는 SSE 머리를 먼저 써서 200 OK + text/event-stream 으로 답하고, 오류를 data: {"error": {… "reason": "TASK_NOT_FOUND"}} 로 실었습니다 — event: error 줄 없이(스트림 오류). TS 클라이언트는 event: error 인 이벤트만 오류로 보므로 이것을 보통 이벤트로 읽었고, StreamResponse.fromJSON 이 모르는 키 error 를 버려 빈 이벤트가 되었습니다(어긋남 표).
