5장

스코프 — 조회와 결재

두 스코프, 두 자리 → 다섯 가지 토큰 → 결재 스코프만 든 토큰 → 결함의 까닭 → 고친 문지기 ×3 → 고친 뒤 → 기획 에이전트의 결재 토큰 → 401·403·AUTH_REQUIRED

스코프는 두 자리에서 본다 — payment:read 는 문지기가, payment:approve 는 실행기가

카드의 securityRequirements 는 "모든 요청에 payment:read" 를 요구합니다(2장). 결재 스코프는 요구에 없습니다 — 3,000,000원이 넘는 정산에만 필요하고, 그 판단은 견적을 읽은 실행기만 할 수 있기 때문입니다(SCENARIO §2.4).

 요청 POST /  Authorization: Bearer tok-…
   │
   ▼  문지기(HTTP 층)          토큰이 없거나 모른다  ─▶ 401
   │  카드의 요구를 본다       payment:read 가 없다  ─▶ 403
   ▼
 SDK JSON-RPC 처리기 ─▶ 실행기
   │  합계 > 3,000,000원 이고 payment:approve 가 없다
   └──────────────────▶ 작업을 AUTH_REQUIRED 로(7장)
§7.5 는 정책을 서버에 맡긴다 — 인가는 "implementation-specific" 이고, 고려해도 되는 것(MAY)으로 요청한 스킬, 작업 안의 동작, 데이터 정책, "OAuth scopes" 를 듭니다. 문지기는 카드가 약속한 것을, 실행기는 그 일의 내용이 요구하는 것을 봅니다.

다섯 가지 토큰 가운데 넷 — intern 은 조회까지, planner 는 결재 스코프를 가져와야 결재까지

12/scope_try.py 는 토큰을 스코프를 골라 받은 뒤(3장) 정산을 하나 맡기고, HTTP 상태와 작업 상태를 찍습니다. 작은 정산은 2,100,000원, 큰 정산은 이야기의 합계 4,842,000원입니다.

  • ①② intern — 작은 돈은 approvedBy=intern 으로 끝나고, 큰 돈은 AUTH_REQUIRED 에서 멈춥니다. ③ planner 도 조회 스코프만 받아 왔으면 같습니다. 스코프는 사람이 아니라 토큰에 붙습니다.
  • ④ 두 스코프를 다 받은 토큰만 큰 돈을 끝냅니다. TS·Go 서버의 ①~④ 도 글자까지 같습니다(같은 캡처의 다른 두 구역).

결재 스코프만 든 토큰은? — 고치기 전의 정산 에이전트는 4,842,000원을 결재해 주었다

⑤ 는 planner 가 scope=payment:approve 하나만 달라고 해서 받은 토큰입니다. 카드는 모든 요청에 payment:read 를 요구하는데(2장), 이 토큰에는 그 스코프가 없습니다. 고치기 전의 문지기를 그대로 옮겨 둔 12/bearer_old.py 에 보냈습니다.

인증만 묻는 문지기 — 세 언어의 완성 정산 에이전트가 처음에는 이 문지기였습니다. RequireBearer 는 "토큰이 있느냐"(인증)만 묻고, "카드가 요구한 스코프가 있느냐" 는 묻지 않았습니다. 그래서 ⑤ 는 문지기를 지났고, 실행기는 payment:approve 를 보고 결재했습니다. 세 언어 모두 이 장에서 고칩니다.

무엇을 어겼나 — 카드가 선언한 요구는 서버가 지켜야 하는 약속이다

§7.4 는 서버가 모든 요청을 "its declared authentication requirements" 에 비추어 인증하라고 합니다(MUST). 정산 카드가 선언한 요구는 "oauth 스킴, payment:read 스코프" 였습니다. 토큰이 진짜라는 것만으로는 그 요구를 채우지 못합니다.

물음고치기 전고친 뒤
토큰이 발급 기록에 있나본다 → 없으면 401본다 → 없으면 401
카드가 요구한 스코프가 토큰에 있나보지 않는다본다 → 없으면 403
결재 스코프가 있나(큰 돈)실행기가 본다실행기가 본다(그대로)
요구와 검사를 한 곳에서 — 고친 세 언어는 요구 스코프를 상수 하나(NEEDED·needed)로 두고, 카드의 securityRequirements 와 문지기가 그 상수를 함께 씁니다. 카드에 스코프를 더하면 검사도 따라 바뀝니다. SDK 가 카드를 읽어 막아 주지 않으므로(4장) 이렇게 묶어 두는 것이 우리 몫입니다.

고친 문지기 — 파이썬: 인증한 사용자의 스코프에 NEEDED 가 없으면 403

RequireBearer 의 401 다음에 세 줄을 더했습니다 — if rpc and not set(NEEDED) <= set(scope["auth"].scopes) 이면 아래 insufficient 로 답합니다(4장 bearer 구역). scope["auth"] 는 BearerBackend 가 붙인 AuthCredentials 입니다.

  • RFC 6750 §3.1 의 insufficient_scope 는 403 이고, 모자란 스코프를 scope 속성으로 알릴 수 있습니다(MAY). §3.3.2 의 "SHOULD indicate what permission or scope is missing" 과 같은 말입니다.
  • 몸통은 401 때와 같은 모양 {"error": …} — JSON-RPC 처리기에 닿기 전에 끝나므로 JSON-RPC 오류가 아닙니다.

TypeScript — lacks(user.scopes) 면 insufficient(res)

requireBearer 의 첫 줄이 bearer(req) 를 한 번 부르고, 사용자가 있는데 스코프가 모자라면 403, 있으면 next() 로 바뀌었습니다(4장 bearer 구역).

카드도 같은 상수 — securityRequirements: [{ schemes: { oauth: { list: NEEDED } } }](2장). 카드의 바이트는 고치기 전과 같습니다 — 같은 값이 들어가기 때문입니다.

Go — lookup 이 찾은 grant 의 스코프로 lacks

requireBearer 가 if g, ok := lookup(…); ok 안에서 lacks(g.scopes) 를 먼저 봅니다(4장 bearer 구역). 실행기에 사용자를 싣는 bearerUser 는 그대로입니다 — 403 이면 요청이 SDK 에 닿지 않기 때문입니다.

머리글 이름은 여전히 Www-Authenticate — w.Header().Set 이 이름을 정규 모양으로 바꾸는 것은 401 때와 같습니다(4장).

고친 뒤 — ⑤ 만 403 으로 바뀌었다, 세 서버 모두

같은 다섯 가지 토큰을 고친 세 정산 에이전트에 보냈습니다. ①~④ 는 고치기 전과 같고, ⑤ 만 실행기에 닿지 않습니다.

바뀐 답은 ⑤ 뿐 — 결재 스코프만 든 토큰은 이 장의 ⑤ 가 처음이라, 앞 장들의 답은 고친 뒤에도 같습니다. 정산 에이전트의 서버 출력에도 ⑤ 는 토큰 발급 한 줄만 남습니다 — 결재도, 결재 요청도 찍히지 않았습니다.

결함의 다른 반쪽 — 기획 에이전트도 결재 토큰에 payment:approve 하나만 달라고 했다

기획 에이전트는 결재할 때 새 토큰을 받습니다(7장). 처음에는 scope=payment:approve 하나만 달라고 했습니다 — 바로 ⑤ 의 토큰입니다. 문지기만 고쳤다면 이야기의 마지막 결재가 403 으로 막혔을 것입니다. 세 언어의 기획 에이전트가 이제 두 스코프를 함께 받습니다.

두 쪽이 서로를 가렸다 — 문지기가 스코프를 보지 않으니 기획 에이전트의 좁은 토큰이 통했고, 그 토큰이 통하니 문지기의 빈틈이 드러나지 않았습니다. 카드의 요구를 읽는 쪽(클라이언트)과 지키는 쪽(서버)이 둘 다 카드를 보지 않으면 이렇게 됩니다.

401·403·AUTH_REQUIRED — 무엇이 모자란지에 따라 답이 셋

왼쪽 열의 모자란 것에 따라 답이 갈립니다. 위 두 줄은 HTTP 층에서 거절하고, 마지막 줄은 작업 안에서 묻습니다.

모자란 것정산 에이전트의 답스펙의 자리
자격 증명(토큰이 없거나 모른다)HTTP 401 + WWW-Authenticate: Bearer realm=…§3.3.2 Authentication Errors — "HTTP 401, gRPC UNAUTHENTICATED, JSON-RPC custom error"
카드가 요구한 스코프HTTP 403 + error="insufficient_scope"§3.3.2 Authorization Errors — "HTTP 403, gRPC PERMISSION_DENIED, JSON-RPC custom error", 예: "insufficient OAuth scopes"
이 일에만 필요한 권한(큰 돈)HTTP 200, 작업 상태 AUTH_REQUIRED§7.6 In-Task Authorization(7장)
  • "JSON-RPC custom error" 의 코드를 스펙은 정하지 않습니다. 세 SDK 가운데 Go 만 정해 두었습니다 — a2a.ErrUnauthenticated → -31401, a2a.ErrUnauthorized → -31403(internal/jsonrpc/jsonrpc.go:84-85). 파이썬·TS SDK 의 오류 목록에는 인증·인가 오류가 없습니다(a2a/utils/errors.py, TS A2A_ERROR_SPECS).
  • 403 과 AUTH_REQUIRED 의 갈림 — 403 은 요청을 받지 않고 작업도 만들지 않습니다. AUTH_REQUIRED 는 작업을 만들어 두고 이어 말하기를 기다립니다. 결재처럼 "받을 수 있는 권한" 이면 뒤의 것이 클라이언트에게 길을 열어 줍니다.

5장 퀴즈

Q. 고친 정산 에이전트에 intern 의 토큰(payment:read)으로 4,842,000원 정산을 보내면 HTTP 상태와 작업 상태는 무엇입니까? 같은 요청을 planner 가 scope=payment:approve 로 받은 토큰으로 보내면 어떻습니까?

A. intern 은 HTTP 200 에 작업 AUTH_REQUIRED 입니다 — 카드의 요구(payment:read)는 채워 문지기를 지났고, 실행기가 결재 스코프가 없어 멈췄습니다(②). planner 의 결재 전용 토큰은 HTTP 403 입니다 — 카드가 요구한 payment:read 가 없어 실행기에 닿지 않습니다(⑤, error="insufficient_scope", scope="payment:read"). 고치기 전에는 이 요청이 COMPLETED 였습니다(결함).

6장

확장 카드 — GetExtendedAgentCard

스펙의 요구 → 확장 카드의 와이어 → 문지기를 지난다 → 파이썬 → TypeScript → Go → 세 언어 비교 → 사람마다 다른 카드

로그인한 클라이언트에게만 더 보여 주는 카드 — 카드에 extendedAgentCard: true 를 적는다

공개 카드는 누구나 읽으니(4장) 숨길 것을 적을 수 없습니다. 인증한 클라이언트에게만 보여 줄 것은 JSON-RPC 메서드 GetExtendedAgentCard 로 따로 줍니다.

자리스펙의 말
§3.1.11"available only if AgentCard.capabilities.extendedAgentCard is true". 돌려주는 것은 "additional details or skills not present in the public card" 를 담을 수 있는 카드 전체
§13.3"MUST require authentication", 공개 카드의 스킴으로 인증(MUST), 클라이언트에 따라 다른 내용(MAY), 새어도 되는 것만 담을 것(SHOULD NOT … sensitive information)
§3.1.11·§13.3클라이언트는 인증한 세션 동안 가진 공개 카드를 확장 카드로 바꿔 쓴다(SHOULD)
§3.3.4·§13.3기능이 없으면 UnsupportedOperationError, 기능은 있는데 확장 카드가 없으면 ExtendedAgentCardNotConfiguredError(3부)
요청에는 몸통이 거의 없다 — GetExtendedAgentCardRequest 의 필드는 tenant 하나뿐입니다(a2a.proto). §9.4.8 의 예시는 params 도 없이 {"method": "GetExtendedAgentCard"} 입니다. 누구에게 무엇을 보여 줄지는 오직 요청의 자격 증명이 정합니다.

공개 카드의 스킬은 하나, 확장 카드는 둘 — settle-budget 은 로그인한 클라이언트에게만

정산 에이전트는 같은 card() 함수로 두 카드를 짓습니다. extended=True 면 스킬 settle-budget 을 더할 뿐입니다(2장의 card 구역). 탭 너머로 intern 의 토큰을 달아 GetExtendedAgentCard 를 불렀습니다.

  • 요청은 "params": {} 뿐이고, 응답의 result 가 카드 그 자체입니다. 공개 카드와 같은 이름·주소·보안 필드에 스킬이 하나 더 있습니다.
  • 확장 카드에는 signatures 가 없습니다. 세 언어 모두 공개 카드에만 서명합니다(8장). §13.3 은 확장 카드의 서명을 말하지 않습니다.

확장 카드도 문지기를 지난다 — 토큰 없으면 401, 카드의 스코프가 없으면 403

GetExtendedAgentCard 는 경로 / 의 JSON-RPC 메서드라, 4장의 문지기와 5장에서 고친 스코프 검사를 그대로 지납니다. 같은 실행의 첫 요청(토큰 없음)과 마지막 curl(결재 스코프만 든 tok-planner-1)입니다.

§13.3 의 MUST 를 문지기가 채운다 — "MUST require authentication", 그것도 공개 카드에 선언한 스킴 가운데 하나로(MUST). 서버 SDK 는 확장 카드를 달라는 요청의 인증을 보지 않으니(사람마다 다른 확장 카드) 이 검사가 없으면 누구나 확장 카드를 받습니다.

파이썬 클라이언트 — get_extended_agent_card, 받은 카드로 갈아 낀다

토큰은 5장처럼 AuthInterceptor 가 답니다. 메서드는 Client.get_extended_agent_card(GetExtendedAgentCardRequest(), context=…) 입니다.

  • ③ — 클라이언트가 들고 있던 카드가 확장 카드로 바뀌었습니다(client/base_client.py:368 의 self._card = card). §3.1.11 의 "SHOULD replace their cached public Agent Card" 를 SDK 가 해 줍니다.
  • 카드에 extendedAgentCard 가 없으면 JSON-RPC 전송은 묻지 않고 가진 카드를 돌려줍니다(client/transports/jsonrpc.py:288, 3부).

TypeScript 클라이언트 — 따로 부르는 메서드가 없다, getAgentCard() 가 알아서

Client.getAgentCard() 는 가진 카드에 extendedAgentCard 가 켜져 있으면 GetExtendedAgentCard 를 부르고, 아니면 가진 카드를 돌려줍니다(client/index.js:5428).

받은 카드로 갈아 낀다 — 파이썬처럼 this.agentCard = agentCard 입니다. 두 번째 인자로 서명 검증 함수를 받을 수도 있습니다(getAgentCard(options, verifySignature)) — 서명이 없는 확장 카드에 주면 검증이 실패하니(dist/index.js:1596 "No signatures found") 주지 않았습니다.

Go 클라이언트 — GetExtendedAgentCard 는 돌려줄 뿐, 가진 카드는 그대로

메서드 이름은 스펙 그대로이고, 세션 id 를 붙인 ctx 로 부르면 AuthInterceptor 가 토큰을 답니다(4장).

③ 이 공개 카드 그대로 — Client.GetExtendedAgentCard 는 받은 카드를 돌려줄 뿐 c.card 를 바꾸지 않습니다(a2aclient/client.go:209-215). §3.1.11 의 SHOULD 를 따르려면 받은 카드로 client.UpdateCard(extended) 를 직접 불러야 합니다.

7장

AUTH_REQUIRED — 작업 중의 권한

스펙의 요구 → 실행기 ×3 → 결재 토큰으로 이어 말하기 ×3 → 와이어 → 스트림과 구독 → 세 서버 비교 → 사슬 — 기획 에이전트가 넘겨받아 묻는다 → 자격 증명은 어느 길로

권한이 모자라면 작업을 멈추고 묻는다 — §7.6 In-Task Authorization

문지기를 지난 요청이라도, 일을 하다 보니 더 큰 권한이 필요할 수 있습니다. 거절(403)하는 대신 작업을 TASK_STATE_AUTH_REQUIRED 로 두고 클라이언트에게 해결을 맡기는 길이 §7.6 입니다.

자리스펙의 말
§7.6.1에이전트는 Task 로 일을 추적하고(MUST), 상태를 AUTH_REQUIRED 로 바꾸고(MUST), 무엇이 필요한지 상태 메시지로 알린다(MUST — 다른 길로 합의했다면 예외)
§7.6.1자격 증명은 "out-of-band" 로 받을 준비를 한다(MUST — 합의된 다른 길이 없다면). 그 경우 열린 스트림을 유지하고(SHOULD), 받으면 후속 메시지 없이 이어 가도 된다(MAY)
§7.6.1AUTH_REQUIRED 인 작업으로 오는 메시지를 받을 것(SHOULD) — 협상·정정·거절을 위해
§7.6.2클라이언트가 스스로 A2A 에이전트면 제 작업도 AUTH_REQUIRED 로 바꿔 위로 넘길 수 있다 — "a chain of Tasks"
§7.6.2스트림이 없으면 구독·웹훅·폴링 가운데 하나로 지켜볼 것(SHOULD)
AUTH_REQUIRED 는 "중단" 상태 — proto 의 주석은 "Indicates that authentication is required to proceed. This is an interrupted state." 입니다. §7.6 은 같은 상태를 인가(authorization)의 뜻으로 씁니다 — 정산 에이전트의 경우도 토큰은 이미 있고, 모자란 것은 결재 권한입니다.

파이썬 실행기 — 결재가 필요하면 requires_auth 하고 돌아간다

agents/settlement.py 의 실행기입니다. 스코프는 문지기가 붙인 call_context.state["auth"] 에서 읽고(4장), 도메인 규칙 settle 이 "auth-required" 를 내면 무엇이 필요한지 글과 데이터로 알립니다(§7.6.1 의 세 번째 MUST).

이어 말하기는 새 실행 — 실행기는 AUTH_REQUIRED 를 알리고 끝납니다. 결재 토큰을 단 다음 메시지가 오면 SDK 가 같은 작업으로 실행기를 다시 부르고, task.history 에서 처음 보낸 견적(data_of)을, 새 요청의 토큰에서 결재 스코프를 읽습니다. 그래서 approvedBy 는 결재 토큰의 주인입니다.

TypeScript 실행기 — 같은 흐름, 상태는 up.status(AUTH_REQUIRED, parts)

스코프는 userBuilder 가 세운 BearerUser 에서 읽습니다(4장). 견적은 작업의 history 와 이번 메시지(ctx.userMessage)를 함께 훑어 찾습니다.

버스는 닫는다 — TS SDK 는 기본값으로 AUTH_REQUIRED 에서 이벤트 버스를 살려 두어 스트림이 열린 채입니다(10부). 결재 토큰은 새 메시지로 오므로, 완성 에이전트의 serve 가 keepBusAliveStates: [INPUT_REQUIRED] 로 바꿔 AUTH_REQUIRED 에서도 닫습니다(10부).

Go 실행기 — 돌아가지 않고 AwaitReply 로 기다린다

Go SDK 는 AUTH_REQUIRED 를 "실행이 살아서 기다리는 상태" 로 보고, 그 작업으로 온 새 메시지를 "execution is already in progress" 로 거절합니다(5부, internal/taskexec/local_manager.go:37). 그래서 Go 정산 에이전트는 실행기를 멈춰 세워 두고(common/park.go), 새 메시지가 오면 그 실행기에 넘깁니다.

멈춘 실행에 넘긴다 — 첫 스트림은 park.go 의 waiter 가 AUTH_REQUIRED 뒤에 닫고(10부), 결재 토큰은 파이썬·TS 와 같은 "작업으로 보낸 새 메시지" 로 옵니다. 실행기는 for 를 한 바퀴 더 돌며 그 요청의 사용자(r.User)에서 스코프를 다시 읽습니다.

결재 토큰으로 이어 말하기 — 파이썬 클라이언트: 저장소의 토큰만 바꾼다

12/approve.py 는 조회 토큰으로 큰 정산을 맡겨 AUTH_REQUIRED 를 받고, 두 스코프를 다 받은 새 토큰을 같은 세션에 넣은 뒤 같은 taskId·contextId 로 "결재합니다" 를 보냅니다.

자격 증명은 HTTP 머리글로 — 결재의 증거는 메시지 내용이 아니라 이 요청의 Authorization 입니다. set_credentials 를 다시 부르면 같은 세션·스킴의 토큰이 바뀌고, 클라이언트 객체는 그대로 씁니다.

TypeScript 클라이언트 — fetch 가 다는 토큰을 바꾼다

TS 에는 자격 증명 저장소가 없으니, 감싼 fetch 의 headers() 가 매번 읽는 변수 current 를 바꿉니다(8부).

Go 클라이언트 — store.Set 으로 같은 세션의 토큰을 덮어쓴다

이어 말할 메시지는 a2a.NewMessageForTask(role, task, …) 가 받은 작업의 taskId·contextId 를 채워 줍니다.

세 서버·세 클라이언트가 같은 세 줄 — 토큰 번호까지 같습니다. 서버마다 발급 기록이 따로라 각자 tok-planner-1 에서 시작하기 때문입니다(3장).

와이어 — 멈춘 작업의 상태 메시지와, 토큰만 바뀐 이어 말하기

파이썬 클라이언트 → 파이썬 서버의 탭입니다. 첫 SendMessage 의 답과 둘째 SendMessage 의 요청·상태만 골랐습니다.

  • 상태 메시지에는 글("결재가 필요합니다…")과 도메인 결과(total 등)가 함께 실립니다. 파이썬 서버라 숫자가 4842000.0 으로 나갑니다(4부).
  • 둘째 요청은 Authorization 의 토큰이 tok-planner-2 로 바뀌었고, 메시지에 첫 답의 taskId·contextId 가 실렸습니다(내용은 "결재합니다"). 같은 작업이 TASK_STATE_COMPLETED 로 끝났습니다.

스트림과 구독 — AUTH_REQUIRED 에서 스트림은 셋 다 닫혔고, 구독은 셋이 다 달랐다

12/auth_watch.py 는 ① SendStreamingMessage 로 AUTH_REQUIRED 를 받고, 그 작업에 SubscribeToTask 를 열어 첫 이벤트를 받은 다음 ② 결재 토큰으로 이어 말하고, ③ 구독이 본 것을 찍습니다. 3초 동안 아무것도 오지 않으면 끊습니다.

  • ① 세 서버 모두 statusUpdate AUTH_REQUIRED 를 보내고 닫았습니다 — 완성 에이전트가 맞춘 대로입니다(10부). SDK 기본값이었다면 TS·Go 는 열린 채였습니다(10부).
  • ③ 파이썬은 구독에 결재 뒤의 아티팩트와 COMPLETED 를 흘렸고, Go 는 다시 WORKING 이 된 작업까지 흘렸습니다. TS 는 작업 하나를 주고 곧 닫았습니다 — TS 서버는 멈춘 작업의 구독을 버스가 살아 있는 동안만 열어 두는데(10부), 이 에이전트는 AUTH_REQUIRED 에서 버스를 닫았습니다.

세 서버 비교 — §7.6.2 의 "구독해 지켜보라" 는 TS 서버에서 통하지 않는다

갈리는 것은 "멈춘 작업을 구독하면" 줄입니다 — TS 서버에서만 결재 뒤의 이벤트가 오지 않습니다.

AUTH_REQUIRED 의 사슬 — 기획 에이전트가 제 작업도 AUTH_REQUIRED 로 바꿔 사람에게 묻는다

§7.6.2: 클라이언트가 A2A 에이전트라면 받은 AUTH_REQUIRED 를 제 클라이언트에게 넘길 수 있습니다 — "a chain of Tasks". 파이썬 에이전트 다섯을 띄우고 ask 로 워크숍을 맡긴 뒤 "승인" 으로 답했습니다.

  • 사람(ask)은 정산 에이전트를 모릅니다. 기획 에이전트가 정산의 AUTH_REQUIRED 를 받아 제 작업을 AUTH_REQUIRED 로 바꾸고, "승인" 을 받자 결재 토큰을 새로 받아 정산 작업에 이어 말했습니다(5장의 토큰 두 번).
  • 자격 증명은 사슬을 타고 내려가지 않았습니다 — 사람은 "승인" 이라는 말만, 결재 토큰은 기획 에이전트가 발급기에서 직접 받았습니다. 기획 에이전트가 어떻게 계획을 짜는지는 15부의 몫입니다.
다섯을 띄운 법 — 기획 에이전트의 --agents 는 동료 주소 넷을 쉼표로 잇는데, 명세 한 줄(72칸)에 들어가지 않습니다. 그래서 포트만 받아 기획 에이전트를 그대로 띄우는 감싸개를 썼습니다.

자격 증명은 어느 길로 — 이 책은 "작업으로 보낸 새 요청의 Bearer 토큰"

§7.6.1 은 자격 증명을 "out-of-band" 로 받으라고 하고(MUST — 다른 길을 합의하지 않았다면), §7.6.3 은 메시지 안에 실어 나르는 "in-band" 교환이 사슬의 모든 에이전트에게 자격 증명을 드러낸다고 경고합니다.

길모양이 책에서
out-of-band에이전트가 따로 받는다(사람의 승인 화면, 인가 서버 콜백…). 받으면 스트림을 유지한 채 이어 가도 된다(MAY)쓰지 않았다

이 책메시지 내용은 "결재합니다" 뿐, 결재 권한은 그 요청의 Authorization 토큰 — 4장의 문지기가 검사하는 같은 길정산 에이전트 ×3
세 번째 길의 값 — 토큰이 메시지 기록(history)에 남지 않고, 사슬의 위쪽 에이전트에게도 보이지 않습니다(사슬). 대신 결재 토큰은 정산 에이전트를 부르는 클라이언트(기획 에이전트)가 직접 받을 수 있어야 합니다. 이 책은 그 둘을 같은 발급기에서 해결했습니다.

Q. 정산 작업이 AUTH_REQUIRED 일 때 SubscribeToTask 로 구독을 열어 두고, 다른 연결에서 결재 토큰으로 이어 말했습니다. 파이썬·TS·Go 서버의 구독자는 각각 COMPLETED 를 봅니까?

서명된 카드 — JCS + JWS

왜 서명하나 → 손으로 풀기 → 기본값 빼기 ×3 → 파이썬 → TypeScript → Go 와 알파벳순 키 → 세 서버의 같은 서명 → 가짜 카드 → 검증 ×3 → 세 검증기 비교 → jku 를 따라가면 → SDK 가 주는 것

카드에 서명하는 까닭 — 카드는 토큰을 어디로 보낼지까지 정한다

클라이언트는 카드의 tokenUrl 로 비밀을 보내고(3장), 카드의 인터페이스 주소로 일을 맡깁니다. 카드를 바꿔치기한 쪽은 비밀과 일을 함께 받습니다. HTTPS 는 "이 서버가 보냈다" 까지만 보증하므로(1장), 카드를 옮겨 싣는 레지스트리나 캐시를 거치면 그 보증이 끊깁니다.

자리스펙의 말
§8.4카드는 JWS(RFC 7515)로 서명할 수 있다(MAY) — "authenticity and integrity"
§8.4.1서명하기 전에 JCS(RFC 8785)로 정규화(MUST). 기본값인 필드는 빼고, signatures 는 서명 대상에서 뺀다(MUST)
§8.4.2보호 머리글에 alg·typ·kid(MUST — typ 은 "JOSE" 를 SHOULD), jku(MAY)
§8.4.3클라이언트는 신뢰하기 전에 서명 하나 이상을 확인(SHOULD), 공개 키는 안전한 길로(SHOULD), "trusted key store" 를 둘 수 있다(MAY)
ES256 이 아니라 EdDSA — §8.4.2 는 alg 의 예로 "ES256", "RS256" 을 들 뿐 정하지 않습니다. 이 책은 Ed25519(RFC 8037 의 EdDSA)를 씁니다. Ed25519 서명은 결정적이라 같은 카드·같은 키면 언제나 같은 바이트가 나오고, 그래서 캡처가 흔들리지 않습니다. ES256(ECDSA)은 서명할 때 난수를 쓰므로(Go 서명기도 rand.Reader 를 넘깁니다 — a2acrypto/sign.go:110) 같은 카드라도 값이 달라집니다. 세 SDK 모두 Ed25519 를 받습니다(SDK 표).

서명을 손으로 풀기 — 보호 머리글, JCS 로 편 카드, 서명할 입력, Ed25519 로 확인

12/jcs.py 는 파이썬 정산 에이전트의 카드에서 서명 하나를 꺼내 §8.4.2 의 순서를 거꾸로 밟습니다. 정규화는 SDK 의 서명기·검증기가 쓰는 비공개 함수를 그대로 불렀습니다.

  • ② JCS 로 편 카드는 빈칸 없이, 키가 알파벳순(코드 단위 차례)입니다. signatures 는 없습니다 — 서명이 제 자신을 덮을 수는 없기 때문입니다(§8.4.1).
  • ③ 서명하는 것은 카드 JSON 이 아니라 BASE64URL(보호 머리글) . BASE64URL(카드) 라는 글자열입니다(§8.4.2 의 셋째 단계 "JWS Signing Input"). 카드 쪽 절반은 카드에 싣지 않습니다 — 받는 쪽이 받은 카드로 다시 만듭니다.
  • ④ Ed25519 서명은 늘 64바이트이고, jwks.json 의 공개 키 32바이트로 SDK 없이도 확인됩니다.

JCS 앞의 한 걸음 — "기본값을 뺀다" 를 세 SDK 가 각자 한다

RFC 8785 는 키 차례·숫자·글자의 쓰는 법을 정할 뿐, 어떤 필드를 넣을지는 정하지 않습니다. 그것은 §8.4.1 의 몫인데, 세 SDK 가 하는 일이 같지 않습니다(설치본 소스).

§8.4.1 의 규칙은 proto 의 optional 을 따진다 — optional 필드는 명시한 기본값도 남기고, 아닌 필드는 기본값을 뺍니다. 파이썬·TS 의 정리 함수는 그것을 묻지 않고 빈 글자·목록·객체만 빼며 false·0 은 남깁니다. Go 는 아무것도 빼지 않으니, Go 로 서명할 카드는 우리가 기본값을 빼 둔 바이트로 만들었습니다(Go 서명).

파이썬 서명 — create_agent_card_signer, 보호 머리글은 우리가 적는다

agents/settlement.py 의 sign 구역입니다. 개인 키 PEM 과 보호 머리글을 주면, 카드를 받아 signatures 에 하나를 더해 돌려주는 함수가 나옵니다. signing extra(선택 설치 묶음)가 PyJWT 를 끌어옵니다.

  • jku 는 이 서버의 /.well-known/jwks.json — 문지기가 열어 두는 경로입니다(4장). 내보내는 키는 ex/fixtures/keys/jwks.json 그대로입니다.
  • PyJWT 는 보호 머리글의 키를 정렬해 씁니다 — alg, jku, kid, typ. 손으로 푼 머리글(①)가 그 차례입니다.

TypeScript 서명 — generateAgentCardSignature, 머리글은 넣은 차례대로

jose 의 FlattenedSign 으로 서명합니다(dist/index.js:1575). 키는 node:crypto 의 createPrivateKey 로 읽은 KeyObject 입니다.

머리글의 차례를 맞춘 까닭 — jose 는 보호 머리글을 넣은 차례대로 직렬화합니다. 보호 머리글은 그 바이트가 서명 입력이 되므로, 파이썬과 같은 서명값을 내려면 같은 차례(alg, jku, kid, typ)로 넣어야 합니다. 차례가 달라도 서명은 유효하고, 값만 다릅니다.

Go 서명 — a2acrypto.Signer, 그리고 카드의 키가 알파벳순인 까닭

a2acrypto.NewSigner 로 서명기를 만들고 Sign(ctx, 바이트) 에 카드 JSON 을 줍니다. 2장에서 미뤄 둔 물음의 답이 이 구역에 있습니다(2장).

  • Go 검증기는 받은 바이트를 기본값 빼기 없이 정규화합니다(기본값 빼기 표). 그래서 서명한 바이트와 내보내는 바이트가 같아야 하고, 그 바이트에서 파이썬·TS 처럼 기본값이 빠져 있어야 세 언어의 검증기가 같은 정규형을 봅니다.
  • 기본값을 빼는 common.ProtoJSON 은 카드를 map[string]any 로 풀어 빈 값을 지우고 다시 씁니다. Go 의 encoding/json 은 맵의 키를 정렬해 쓰므로, 그 바이트의 키가 알파벳순이 됩니다. 정렬은 목적이 아니라 맵을 거친 흔적입니다.
  • SDK 의 a2asrv.NewSignedCardProducer 는 SDK 가 json.Marshal 한 카드 — "pushNotifications": false 까지 든(6장) — 에 서명합니다(a2asrv/signed_card.go:50). 코드의 주석은 그 모양이 파이썬·TS 검증기와 맞지 않아 쓰지 않았다고 적었지만, 이 책은 그것을 재 보지 않았습니다. push_notifications 는 proto 에서 optional 이라, 명시한 false 는 §8.4.1 에 따라 정규형에 남아야 하는 값입니다 — 주석의 말은 확인이 필요합니다.

세 서버의 서명이 한 글자도 다르지 않다 — 같은 정규형, 같은 머리글, 결정적인 Ed25519

세 정산 에이전트에게 같은 바깥 주소(--url http://127.0.0.1:11280/)를 주어 카드 내용과 jku 를 같게 했습니다. 각 서버의 카드에서 서명값만 뽑았습니다.

세 SDK 의 정규화가 같은 바이트를 냈다는 증거 — 서명 입력의 한 글자만 달라도 Ed25519 서명은 전혀 다른 값이 됩니다. 2장의 카드 실행에서 세 서명이 달랐던 것은 서버마다 카드의 주소(인터페이스·tokenUrl·jku)가 달랐기 때문입니다(2장).

가짜 정산 에이전트 — 같은 이름·스킬, 토큰 주소는 자기, 서명은 다른 키로

12/impostor.py 는 진짜와 같은 card() 로 카드를 짓되 주소를 자기로, 서명 키를 impostor-ed25519.pem 으로 바꿨습니다. kid 는 진짜 키의 이름 settlement-2026 을 사칭하고, jku 는 가짜 키를 내주는 자기 JWKS 입니다.

이 카드를 믿은 클라이언트 — 3장의 흐름대로 tokenUrl 에 client_secret 을 보내고(3장), 정산을 가짜에게 맡깁니다. 서명이 있다는 것만으로는 아무것도 증명되지 않습니다 — 누구의 키로 검증하느냐가 전부입니다.

파이썬 검증 — create_signature_verifier, 키는 key_provider(kid, jku) 가 고른다

12/verify.py 는 검증기를 둘 만듭니다. pinned 는 미리 받아 둔 jwks.json 의 키만, trusting 은 카드가 가리키는 jku 의 키를 씁니다. 다섯 가지 카드를 넣었습니다.

  • algorithms=["EdDSA"] 는 반드시 줘야 합니다 — 머리글의 alg 를 믿지 않으려는 PyJWT 의 장치입니다(utils/signing.py:112 "prevent algorithm confusion attacks").
  • ② 는 tokenUrl 하나를 바꾼 진짜 카드, ③ 은 모르는 필드 note 를 더한 진짜 카드입니다(같은 파일의 main 구역).
  • ④ 가 "틀림" 으로 끝난 것은 가짜가 진짜의 kid 를 사칭했기 때문입니다. 모르는 kid 면 keys[kid] 가 KeyError 를 냅니다. SDK 검증기는 서명마다 PyJWTError 만 잡으므로(utils/signing.py:158) 그 오류는 검증기 밖으로 새고, 이 예제의 check 도 받지 못합니다. 실제 키 고르기는 모르는 kid 에 jwt.PyJWKError(PyJWTError 의 하위 클래스) 같은 오류를 던져야 합니다 — TS·Go 예제의 "모르는 키" 처럼. 키를 바꿀 때 이 차이가 무엇을 가르는지는 17부에서 봅니다.

TypeScript 검증 — verifyAgentCardSignature, 키는 (kid, jku) 콜백

공개 키는 JWK 를 createPublicKey({key, format: "jwk"}) 로 읽은 KeyObject 입니다. 카드는 받은 JSON 객체를 그대로 넘깁니다 — SDK 가 fromJSON 을 거쳐 정규화합니다.

틀린 서명마다 console.debug — SDK 는 실패한 서명 하나마다 그 서명과 오류를 통째로 console.debug 로 찍습니다(dist/index.js:1617). 표준 출력이 넘쳐 예제는 꺼 두었습니다. 머리글에 kid·typ·alg 가 다 있어야 한다는 검사도 TS 에만 있습니다(:1604).

Go 검증 — a2acrypto.Verifier, 받은 바이트와 KeyResolver

Verify(ctx, 바이트, 서명) 은 카드 바이트를 그대로 받습니다. 키는 KeyResolver 가 고르는데, KeyResolverFunc 은 kid 만 받아 jku 를 볼 수조차 없습니다.

trusting 은 SDK 의 허용 목록을 일부러 무른 것 — NewJWKSKeyResolver 는 검증하는 쪽이 정한 JWKS 주소 목록에 든 jku 만 받습니다(a2acrypto/keyresolver.go:87). 카드가 대는 jku 를 그 목록에 넣으면 아무 jku 나 믿는 셈이 됩니다.

  • 더한 필드를 믿고 쓰는 쪽(원시 JSON 을 읽는 앱)이 있다면, 파이썬·TS 의 "맞음" 은 그 필드를 보증하지 않습니다.

⑤ 가 맞음인 까닭 — 서명은 "이 키의 주인이 썼다" 일 뿐, 키를 고르는 것은 검증하는 쪽이다

가짜 카드의 서명은 가짜 키로 올바르게 만든 것입니다. jku 를 따라가면 그 가짜 키가 나오니 수학적으로는 맞습니다. 막는 것은 오직 "어느 키를 믿을지" 를 카드 밖에서 정해 두는 일입니다.

  • §8.4.3 — 공개 키는 "using the kid and jku (or from a trusted key store)" 로 얻는다고만 하고, jku 를 믿지 말라는 말은 없습니다. 클라이언트는 "MAY maintain a trusted key store" 입니다.
  • Go SDK 의 주석은 더 단호합니다 — kid·jku 는 "attacker-controlled", jku 로 키를 받아 신뢰를 세우면 "MUST NOT"(a2acrypto/keyresolver.go:30-43). 파이썬·TS SDK 는 콜백에 jku 를 그대로 건넵니다.
  • 완성 기획 에이전트는 세 언어 모두 미리 받아 둔 키(pinned)로만 검증합니다(15부). HTTPS 로 jku 를 받아도 소용없습니다 — 가짜 서버도 제 인증서를 가질 수 있습니다.

8장 퀴즈

Q. 진짜 정산 카드에 "note": "덧붙임" 을 더해 검증했더니 파이썬·TS 는 "맞음", Go 는 "틀림" 이었습니다. 무엇이 둘을 가릅니까?

A. 정규화하는 대상입니다. 파이썬은 카드를 protobuf 로, TS 는 AgentCard.fromJSON 으로 읽은 뒤 정규화하므로 타입에 없는 note 가 빠지고, 남은 정규형은 서명할 때와 같습니다. Go 의 Verifier.Verify 는 받은 바이트를 그대로 정규화하므로 note 가 들어가 서명 입력이 달라집니다(③, 정규화 표).

12부 정리 — 누구냐(인증), 무엇까지냐(인가), 믿을 만하냐(서명)

장한 줄
1운영은 HTTPS(MUST). 인증서는 SDK 가 아니라 HTTP 라이브러리가 보고, 셋 다 기본으로 거절한다
2보안 스킴 다섯과 요구의 proto 꼴. 옛 꼴은 SDK 마다 말없이 잃는다
3client_credentials 발급기 ×3 — 같은 바이트, RFC 에서 줄인 것 셋, 맞힐 수 있는 순번 토큰
4문지기는 HTTP 층에서 401 + WWW-Authenticate. 서버 SDK 는 카드의 보안 필드를 읽지 않는다
5카드의 스코프는 문지기가(403), 결재는 실행기가. 스코프를 보지 않던 결함을 세 언어에서 고쳤다
6확장 카드는 문지기를 지난 클라이언트에게. Go 클라이언트만 받은 카드로 갈아 끼우지 않는다
7AUTH_REQUIRED 는 결재 토큰을 단 이어 말하기로 풀린다. 구독자가 끝을 보는지는 서버마다 다르다
8JCS + Ed25519 서명은 세 SDK 가 바이트까지 같다. 가짜를 잡는 것은 미리 받아 둔 키뿐
다음 — 이 부의 모든 요청은 JSON-RPC 였고, 문지기도 경로 / 하나만 지켰습니다. 13부는 전송 바인딩입니다 — 같은 메서드를 HTTP+JSON(REST)과 gRPC 로 보내고, 오류가 HTTP 상태와 gRPC status 로 어떻게 옮겨 가는지 봅니다. 바인딩이 셋이면 지켜야 할 문도 셋입니다.
