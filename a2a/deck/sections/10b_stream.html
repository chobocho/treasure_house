접는 규칙은 proto 주석 두 줄 — append 면 파트를 잇고, 아니면 바꿔 끼운다

세 SDK 클라이언트는 스트림을 Task 로 접어 주지 않습니다(7부·8부·9부). 접는 규칙은 스펙 본문에 따로 없고, §4.2.2 의 표가 옮겨 온 proto 주석이 전부입니다 — append: "appended to a previously sent artifact with the same ID", lastChunk: "the final chunk of the artifact".

  • 잇는 것은 파트입니다. 글 조각 셋을 글 하나로 합치지 않습니다 — 막는 호출로 받은 Task 에도 식단표 는 글 파트 셋이었습니다(5부).
  • id 가 "같은 아티팩트" 의 열쇠입니다. proto 는 artifact_id 를 "unique within a task" 로 정했습니다. 이름(name)은 사람이 읽으라고 있는 것입니다.

세 SDK 서버도 저장소에서 같은 규칙으로 접는다 — 갈리는 곳은 "없는 id 에 append"

스트림의 조각은 서버 저장소에도 접혀 들어갑니다. 그래서 GetTask 가 합친 Task 를 줍니다. 세 SDK 의 그 함수입니다.

파이썬 — 접기 함수는 서버 패키지에서 빌린다

10/fold.py 의 접기입니다. 보기는 빈 Task() 에서 시작해 이벤트 하나마다 fold 를 부릅니다.

  • append_artifact_to_task 는 SDK 서버가 저장소의 Task 에 쓰는 바로 그 함수입니다. 클라이언트 코드가 a2a.server 를 가져오는 셈이지만, 같은 a2a-sdk 패키지 안에 있으니 따로 설치할 것은 없습니다.
  • 상태는 CopyFrom 으로 바꿔 끼울 뿐, 지난 상태 메시지를 이력으로 옮기지는 않습니다. 이 장은 아티팩트와 상태만 맞춥니다.

접은 Task 는 GetTask 의 아티팩트와 같다 — 식단표는 파트 셋

세 언어의 접기 예제를 다른 언어의 식사 에이전트에 붙였습니다 — 파이썬 → Go 서버, TS → 파이썬 서버, Go → TS 서버. 스트림이 끝나면 접은 보기를 찍고, GetTask 의 아티팩트와 견줍니다.

이벤트 열 개 → 아티팩트 셋 — meal-plan 은 조각 셋이 이어져 파트 셋, menu-file·meal-quote 는 하나씩. 서버가 저장소에서 접은 것과 클라이언트가 스트림에서 접은 것이 같습니다(True). 파일·견적 두 줄은 6장에서 읽습니다.

TypeScript — 도우미가 없으니 규칙을 손으로 쓴다

10/fold.ts 의 접기입니다. 규칙의 표가 그대로 조건문이 됩니다.

  • 첫 Task 는 structuredClone 으로 복사해 둡니다. 그 뒤로는 보기를 제자리에서 고칩니다.
  • 없는 id 에 append 면 던집니다 — TS SDK 서버라면 새 아티팩트로 더했을 자리입니다(앞 표). 첫 조각을 놓친 것이니, 조용히 반쪽 식단표를 만드는 것보다 알리는 편이 낫습니다.

TS 도 같은 Task — 견줄 때는 키 차례를 보지 않는다

문자열로 견주면 틀린다 — 상대가 파이썬 서버라, 같은 견적 data 의 키 차례가 스트림 때와 GetTask 때 달랐습니다(파이썬 SDK 의 맵 차례는 프로세스 안에서도 바뀝니다 — 0부). 처음에 JSON.stringify 두 개를 === 로 견줬더니 false 였습니다. 그래서 키 차례를 보지 않는 isDeepStrictEqual 로 견줍니다.

Go — a2aevent.ApplyUpdate 가 새 Task 를 돌려준다

10/fold 의 접기입니다. SDK 의 공개 함수가 상태·아티팩트 이벤트를 다 맡습니다.

  • 첫 Task 는 손으로 — ApplyUpdate 는 보기와 이벤트의 taskId·contextId 가 같은지 먼저 봅니다. 빈 보기에 첫 Task 를 넘기면 "task IDs don't match" 이니, Task 이벤트는 그대로 보기로 삼습니다.
  • 상태는 이력까지 — ApplyUpdate 는 상태를 바꾸기 전에 지난 상태 메시지를 History 로 옮깁니다(a2aevent/event.go:121). 파이썬·TS 의 손 접기와 다른 점입니다.

Go 의 접기는 gob 등록이 있어야 돈다 — 저장소 패키지가 해 주던 일

ApplyUpdate 는 넘긴 Task 를 고치지 않으려고 gob 으로 깊은 복사를 합니다(internal/utils/utils.go:36). DataPart 의 JSON 객체(map[string]any)를 gob 에 등록하는 곳은 SDK 안에서 a2asrv/taskstore/inmemory.go:60 하나뿐입니다. 서버는 그 패키지를 쓰니 문제가 없지만, 클라이언트는 그렇지 않습니다.

둘째 이벤트에서 넘어진다 — 첫 Task 의 이력에 요청의 DataPart({"nights":1,…})가 있으니, 그 Task 를 복사하려는 첫 ApplyUpdate 가 실패합니다. DataPart 를 주고받는 Go 클라이언트가 a2aevent 를 쓰려면 gob.Register(map[string]any{})·gob.Register([]any{}) 를 직접 하거나 taskstore 패키지를 가져와야 합니다. SDK 문서에는 없는 조건입니다. 서버 쪽에서 같은 gob 사본이 구조체를 못 다루는 모습은 9부에서 봤습니다.

잘못 접으면 — append 를 안 보면 식단표는 점심 한 줄만 남는다

흔한 실수는 "같은 id 면 덮어쓴다" 하나로 끝내는 것입니다. 파이썬 예제는 같은 스트림을 그렇게도 접어 봤습니다.

  • 조각 셋이 차례로 서로를 덮어, 마지막 조각(2일차 점심)만 남았습니다. 오류도 경고도 없습니다 — 보기만 틀립니다.
  • 반대 실수는 append 를 보고 글을 하나로 이어 붙이는 것입니다. 사람에게 보여 주기에는 같지만, 파트 수가 GetTask(파트 셋)와 달라져 서버의 Task 와 견줄 수 없게 됩니다.
  • 셋째 실수 — 첫 Task 를 건너뛰고 접기 — 는 다시 붙을 때 드러납니다(5장).

lastChunk 는 식단표에만 — 파일·견적이 끝났는지는 작업이 끝나야 안다

1장의 SDK 없는 읽기가 찍은 조각 표시를 다시 봅니다.

  • 식단표는 셋째 조각에 lastChunk=true 가 있어, 그 이벤트에서 "식단표 완성" 을 알 수 있습니다.
  • menu-file·meal-quote 는 둘 다 lastChunk 가 없습니다. proto 의 말로는 "마지막 조각" 이 아직 안 왔으니, 같은 id 로 append 가 더 올 수도 있습니다. 한 번에 보낸 아티팩트라도 받는 쪽은 작업이 종료 상태가 될 때(스트림이 닫힐 때) 완성으로 칩니다.
  • 보내는 쪽에서 고칠 수 있는 자리이기도 합니다 — 한 번에 싣는 아티팩트에 lastChunk 를 달면 받는 쪽이 더 일찍 쓸 수 있습니다. 세 언어의 식사 에이전트는 달지 않았습니다(2장).

4장 퀴즈

Q. 어떤 클라이언트가 artifactUpdate 를 받을 때마다 artifacts[artifact.name] = artifact 로 저장합니다. 식사 에이전트의 스트림이 끝나면 식단표 에는 무엇이 남고, 왜 그렇습니까?

A. 마지막 조각 "2일차 점심: 막국수와 수육 28명, 산채 비빔밥 2명" 한 줄(파트 하나)만 남습니다. append 를 보지 않고 덮어쓰므로 조각 셋이 서로를 지웠습니다 — 파이썬 예제의 잘못된 접기가 그대로 보여 줍니다(덮어쓰기만 하면 meal-plan×1). 게다가 열쇠를 name 으로 삼았으니, 이름이 같은 다른 아티팩트가 오면 그것까지 섞입니다. 열쇠는 artifactId, 동작은 append 가 정합니다.

SubscribeToTask — 끊긴 뒤 다시 붙기

§3.1.6 → 여러 구독자(§3.5.2) → 실험 → 파이썬 서버 → 다시 붙은 첫 이벤트 → 끊어도 작업은 간다 → TS·Go 서버 → 끝난 작업·없는 작업 → 멈춘 작업에 다시 붙기 → 왜 열린 채인가 → SDK 클라이언트 ×3 → 세 SDK 비교

SubscribeToTask — 있는 작업의 스트림을 새로 연다, 첫 이벤트는 그때의 Task

§3.1.6 "Establishes a streaming connection to receive updates for an existing task." 요청은 id 하나(proto SubscribeToTaskRequest, 그리고 tenant)이고, 답은 SendStreamingMessage 와 같은 SSE 입니다(§9.4.6).

§3.1.6 의 말뜻
"MUST return a Task object as the first event … the current state of the task at the time of subscription"다시 붙으면 먼저 지금까지의 모습 하나 — "GetTask 와 구독 사이에 잃는 것이 없게"
"The stream MUST terminate when the task reaches a terminal state"닫히는 때는 3장의 §3.1.2 와 같은 말 — 중단 상태는 말하지 않는다
Errors: UnsupportedOperationError ×2, TaskNotFoundError스트리밍을 안 하는 에이전트(7장), 종료 상태의 작업, 없는(볼 수 없는) 작업
바인딩마다 이름이 다르다 — JSON-RPC 메서드는 SubscribeToTask, REST 는 §5.3 의 표가 POST /tasks/{id}:subscribe 인데 proto 의 HTTP 주석은 GET 입니다. 그 어긋남은 13부에서 봅니다. 이 장은 JSON-RPC 만 씁니다.

한 작업에 스트림 여럿 — 같은 이벤트, 같은 차례, 하나를 닫아도 나머지는 산다

§3.5.2 "An agent MAY serve multiple concurrent streams to one or more clients for the same task." 여러 스트림을 허락한다면 지킬 것이 넷입니다.

  • "Events MUST be broadcast to all active streams for that task"
  • "Each stream MUST receive the same events in the same order"
  • "Closing one stream MUST NOT affect other active streams for the same task"
  • "The task lifecycle is independent of any individual stream's lifecycle"
끊긴 클라이언트의 길 — §3.5.2 가 든 쓰임새 가운데 하나가 "A client reconnecting to a task after a network interruption by opening a new stream" 입니다. 원래 스트림이 끊겨도 작업은 서버에서 계속되고, 새 스트림이 첫 Task 로 빈틈을 메웁니다. 다음 실험이 넷 다를 한 번에 시험합니다.

실험 — 첫 조각 뒤에 구독자 둘을 붙이고, 원래 스트림을 끊는다

10/resub.py 는 SDK 없이 식사 에이전트에 스트림을 열고, 첫 조각을 받자마자 SubscribeToTask 를 두 번 보낸 뒤 원래 스트림을 닫습니다. 구독 1 은 이벤트 셋을 읽고 끊고, 구독 2 는 끝까지 읽습니다.

끼니 사이 3초 — 식사 에이전트를 --step-ms 3000 으로 띄웠습니다(다음 슬라이드의 명세). 구독 요청이 다음 이벤트보다 먼저 닿게 하려는 여유입니다 — 1초로는 이 기계가 바쁠 때 구독이 늦어, 첫 Task 에 조각이 둘 든 적이 있습니다. 구독 둘을 한 프로세스에서 차례로 읽어도 되는 것은, 서버가 보낸 이벤트가 그동안 소켓에 쌓여 있기 때문입니다.

파이썬 서버 — 두 구독 모두 WORKING Task 로 시작해 같은 차례로 이어 받았다

  • 두 구독의 첫 이벤트가 같은 task WORKING [meal-plan×1] — 구독한 때의 모습입니다. 그 뒤는 원래 스트림이 받았을 2/3 부터의 이벤트가 같은 차례로 왔습니다.
  • 원래 스트림을 끊고, 구독 1 도 끊었지만 구독 2 는 COMPLETED 까지 받고 서버가 닫았습니다. GetTask 도 COMPLETED — 작업은 스트림과 따로 살았습니다(§3.5.2 의 넷째 줄).

다시 붙은 첫 이벤트 — 지금까지 접힌 Task, 첫 조각이 이미 들어 있다

구독 1 의 첫 이벤트를 파이썬 서버 앞 탭에서 꺼냈습니다.

  • 상태는 마지막 상태 갱신(식단 짜는 중 1/3), 아티팩트에는 첫 조각까지 접힌 meal-plan, 이력에는 처음 보낸 메시지 — 서버 저장소가 4장의 규칙으로 접어 둔 그대로입니다.
  • 그래서 구독자는 이 Task 를 보기로 삼고, 뒤이어 오는 append 조각을 그대로 이어 붙이면 됩니다. 원래 스트림에서 놓친 이벤트를 다시 받을 필요가 없습니다.

TS·Go 서버도 같은 대본 — 갈린 것은 오류의 문구뿐

세 서버에 같은 실험을 했습니다. 이벤트 줄은 세 대본이 글자까지 같아서, Go 서버의 것만 싣습니다.

세 SDK 모두 §3.5.2 를 지켰다 — 두 구독이 같은 이벤트를 같은 차례로 받았고, 원래 스트림과 구독 1 을 닫아도 구독 2 와 작업은 이어졌습니다. 클라이언트가 끊어도 실행기를 멈추지 않는 것은 Go 소스의 주석이 밝힙니다: "Execute starts two goroutine in a detached context"(internal/taskexec/local_manager.go:150).

끝난 작업에 구독하면 -32004, 없는 작업이면 -32001 — 셋 다 스펙대로

실험의 끝에서 COMPLETED 가 된 그 작업과, 없는 id 에 다시 구독했습니다(after 구역).

  • 코드는 셋이 같습니다 — §3.1.6 대로 종료 상태는 UnsupportedOperationError, 없는 작업은 TaskNotFoundError.
  • 문구는 제각각입니다. TS 는 상태를 enum 숫자 (3) 로 적었고, Go 는 없는 작업에 SDK 안쪽 사정 no active execution 을 붙였습니다(a2asrv/handler.go:375).
  • 오류를 싣는 꼴도 3부·3장과 같습니다 — 파이썬·TS 는 보통 JSON 응답, Go 는 SSE 이벤트 하나(3부).

멈춘 작업에 다시 붙으면 — 실행기가 없어도 스트림이 열린 채일 수 있다

3장에서 끊고 나온 작업들(INPUT_REQUIRED·AUTH_REQUIRED·WORKING)에 다시 붙어 봤습니다. 10/paused.py 는 종료 실험 에이전트의 스트림을 끝까지(또는 2초) 읽고, 그 작업에 SubscribeToTask 를 2초 제한으로 엽니다. 실행기는 이미 돌아갔습니다.

  • 첫 이벤트는 모두 그 상태의 Task 입니다. 그다음이 갈렸습니다 — 아홉 가운데 서버가 닫은 것은 둘(TS 의 WORKING, Go 의 INPUT_REQUIRED)뿐이고 일곱은 열린 채였습니다.
  • 파이썬은 셋 다 열린 채입니다. 처음 스트림은 닫았던 서버가, 다시 붙은 스트림은 붙들고 있습니다.

왜 열린 채인가 — 세 SDK 가 "아직 이어질 실행" 을 보는 눈이 다르다

설치된 소스에서 구독이 첫 Task 뒤에 무엇을 기다리는지 읽었습니다.

SDK첫 Task 다음그래서 열린 채인 상태
파이썬저장된 작업에 실행 객체를 붙여(create_task_if_missing=False) 그 구독을 넘긴다(default_request_handler_v2.py:569)세 중단·진행 상태 모두
TS그 작업의 이벤트 버스가 살아 있으면 거기에 붙고, 없으면 바로 닫는다(server/index.js:3341·:3354)버스를 살려 두는 keepBusAliveStates(기본: 중단 둘)
Go실행이 아직 등록되어 있으면 그 구독, 아니면 저장된 Task 하나를 주고 닫는다(a2asrv/handler.go:371·:382)실행이 끝나지 않은 AUTH_REQUIRED·WORKING(3장)

파이썬 SDK 클라이언트 — client.subscribe, 첫 Task 를 버리면 접기가 깨진다

4장의 접기 예제에 --cut 을 주면 첫 조각 뒤에 스트림을 끊고 같은 taskId 로 다시 붙어 이어 접습니다. 다시 붙는 부분입니다.

  • 이벤트 셋 + 구독 여덟 = 열하나. 원래 스트림의 열 개보다 하나 많은 것은 다시 붙은 첫 Task 입니다. 그것으로 보기를 통째로 바꾸니 GetTask 와 같아졌습니다.
  • 첫 Task 를 버리고 빈 Task 에 접으면, 둘째 조각의 append 가 이을 곳이 없어 InvalidAgentResponseError 입니다(4장). 끊기 전의 보기에 이어 접어도 되지만, 그 사이에 놓친 이벤트가 있을 수 있으니 첫 Task 로 바꾸는 쪽이 맞습니다.

파이썬에서 "끊기" 는 aclosing 으로 — break 만으로는 바로 닫히지 않을 수 있다

끊는 쪽 코드입니다. send_message 가 돌려주는 것은 비동기 생성기입니다.

생성기를 그 자리에서 닫는다 — async for 를 break 로 빠져나와도 비동기 생성기의 aclose() 는 불리지 않고, 생성기가 버려질 때까지 응답이 열려 있을 수 있습니다. contextlib.aclosing 이 블록을 나올 때 aclose() 를 불러 SDK 의 HTTP 응답을 닫습니다. TS 의 for await 는 break 때 생성기의 return() 을 부르고, Go 는 yield 가 false 를 받으면 SDK 가 본문을 닫습니다(9부).

TypeScript — 이름은 resubscribeTask, 요청은 {tenant, id}

메서드 이름이 옛 것 — TS 클라이언트의 메서드는 v0.3 의 tasks/resubscribe 에서 온 resubscribeTask 이지만, 와이어에는 v1.0 의 SubscribeToTask 를 보냅니다(client/index.js:5943). 파일 조각이 이벤트로 왔으니 raw 는 Buffer 입니다(6장).

Go — SubscribeToTask 도 iter.Seq2, 첫 Task 는 보기를 바꾼다

fold 가 첫 Task 를 맡는다 — Go 의 접기는 Task 이벤트를 그대로 보기로 삼으므로(4장), 다시 붙은 첫 Task 도 따로 다룰 것이 없습니다. ApplyUpdate 에 그 Task 를 넘겨도 taskId 가 같으니 그 Task 의 깊은 복사본을 돌려줍니다(a2aevent/event.go:43) — 빈 보기일 때만 손으로 맡으면 됩니다.

5장 퀴즈

Q. 식단표의 첫 조각까지 받은 클라이언트가 끊겼다가 SubscribeToTask 로 다시 붙었습니다. 다시 붙은 스트림의 첫 이벤트에서 meal-plan 아티팩트는 파트 몇 개이고, 다음 조각(append)은 어디에 이어 붙입니까?

A. 파트 하나입니다. 첫 이벤트는 구독한 때의 Task 이고, 서버 저장소가 첫 조각까지 접어 두었습니다(구독 1·2 의 task WORKING [meal-plan×1]). 다음 append 조각은 그 Task 의 meal-plan 뒤에 잇습니다. 첫 Task 를 버리고 빈 보기에 이으려 하면 이을 곳이 없어 파이썬 서버 함수는 InvalidAgentResponseError 를 냅니다(파이썬 클라이언트).

와이어의 파일 파트 — base64 문자열 옆에 이름과 미디어 타입

1장의 파이썬 서버 탭에서 menu-file 이벤트를 꺼냈습니다.

  • raw 는 195바이트 파일의 base64(260글자)입니다 — proto: "In JSON serialization, this is encoded as a base64 string". 1장에서 본 대로 세 서버가 같은 글자를 냈습니다.

  • data 는 proto 의 google.protobuf.Value 라 수는 모두 double 입니다. 파이썬 SDK 는 그것을 28.0·1542000.0 으로 쓰고, TS·Go 는 1542000 으로 씁니다 — 4부에서 본 차이가 스트림에서도 그대로입니다.
  • 키가 알파벳순으로 보이는 것은 탭이 정렬해 둔 것입니다. 파이썬 서버의 맵 차례는 프로세스마다 바뀌기 때문입니다(0부).

%v 는 1.542e+06 — encoding/json 이 푼 JSON 수는 float64 이고, fmt 의 %v 는 큰 실수를 지수 꼴로 찍습니다(4부). 금액으로 쓸 때는 int64(total.(float64)) 처럼 바꿉니다.

스트림 속의 raw 와 url — 큰 파일은 이벤트 한 줄을 키운다

식사 에이전트는 파일을 raw 로 보냈습니다. url 이었다면 이벤트에는 주소 하나만 실리고, 클라이언트가 그 주소에서 직접 가져옵니다(4부). 스트림에서는 고를 때 따질 것이 하나 더 있습니다.

  • 이벤트 하나가 커진다 — raw 파일은 SSE 이벤트 하나의 data: 안에 통째로 들어갑니다. Go SDK 클라이언트는 data: 한 줄을 10MB 까지만 읽습니다(internal/sse/sse.go:39 MaxSSETokenSize). base64 로 4/3 배가 되니 7.5MB 남짓을 넘는 파일이면 Go 클라이언트가 그 이벤트를 못 읽습니다(소스로 읽은 것 — 이 덱에서 돌려 보지는 않았습니다).
  • 본문 한도와는 방향이 다르다 — 4부의 TS 서버 100KB 한도(4부)는 express.json() 이 요청 본문에 거는 것입니다. 스트림의 응답에는 걸리지 않습니다.
  • 조각으로 나누려면 — raw 파트를 여러 append 조각에 나눠 실을 수는 있지만, 접으면 파트가 여럿인 아티팩트가 될 뿐 바이트를 하나로 잇는 규칙은 없습니다(4장). 큰 파일은 url 로 보내는 편이 스펙의 모양에 맞습니다.

6장 퀴즈

Q. 세 언어의 접기 예제가 같은 견적을 꺼내 total 을 찍었더니 1542000.0, 1542000, 1.542e+06 이 나왔습니다. 서버가 보낸 수가 셋이 달랐던 것입니까?

A. 아닙니다. 파이썬 클라이언트의 상대는 Go 서버였고, Go 서버는 1542000 을 보냈습니다(Go 서버의 탭). 그래도 파이썬은 Value 의 수를 float 로 주어 1542000.0, Go 는 float64 를 %v 로 찍어 1.542e+06 입니다(비교). 값은 셋 다 같은 double 1,542,000 이고, 다른 것은 각 언어가 그 수를 담는 타입과 찍는 방식입니다.

스트리밍 미지원 카드에 스트림 요청

§3.3.4 의 두 메서드 → SubscribeToTask 를 맨손으로 → 검사를 끈 Go → 보내기는 내려간다 → 구독: 파이썬 → TypeScript → Go → Go 가 아무것도 못 본 까닭 → 세 SDK 비교

카드에 streaming 이 없으면 스트림 메서드 둘 다 -32004

§3.3.4 "If AgentCard.capabilities.streaming is false or not present, attempts to use SendStreamingMessage or SubscribeToTask operations MUST return UnsupportedOperationError." §3.1.6 의 오류 목록도 이것을 맨 앞에 둡니다.

바인딩UnsupportedOperationError 의 꼴(§5.4)

  • SendStreamingMessage 쪽은 3부에서 이미 봤습니다 — 세 서버 모두 -32004, Go 만 SSE 이벤트로(3부).
  • 이 장은 남은 하나, SubscribeToTask 와 그것을 부르는 SDK 클라이언트를 봅니다. 실험 대상은 3부의 안내 에이전트(기능을 하나도 켜지 않은 카드)입니다.

없는 작업에 구독해도 -32004 — 기능 검사가 작업 찾기보다 먼저다

안내 에이전트 셋(과 기능 검사를 끈 Go 판) 앞에 탭을 세우고, curl 로 SubscribeToTask(id: "t-1", 그런 작업은 없다)를 보냈습니다.

  • 셋 다 -32004 입니다. "작업이 없다"(-32001)가 아니니 카드 검사가 먼저입니다 — 3부의 푸시 설정과 같은 차례입니다(3부).
  • TS 의 문구는 "Streaming (and thus resubscription) is not supported." — 구독이 스트리밍에 딸린 기능이라는 뜻을 문구에 담았습니다(server/index.js:3337).

기능 검사를 끈 Go 서버는 작업을 찾으러 간다 — -32001

  • Go 의 기능 검사는 WithCapabilityChecks 를 줄 때만 돕니다(3부). 빼면 SubscribeToTask 는 실행 관리자에게 그 작업을 묻고, 없으니 -32001 입니다(a2asrv/handler.go:362·:371).
  • 카드는 "스트리밍 없음" 이라고 하는데 서버는 구독을 받아 준 셈이라, 작업이 있었다면 스트림이 열렸을 것입니다 — 3부의 스트림 보내기와 같은 어긋남입니다.

스트림으로 보내기는 SDK 클라이언트가 막는 호출로 바꾼다 — 이미 본 것

세 SDK 클라이언트로 같은 에이전트에 스트림을 청했습니다(10/nosub ×3, 상대는 파이썬 안내 에이전트). 셋 다 이벤트 하나 — Message 하나를 받았습니다.

SDK카드를 보고 SendMessage 로 내려가는 곳처음 본 곳
파이썬a2a/client/base_client.py:703부

받는 쪽 코드는 그대로 돈다 — 내려간 호출의 답(Task 또는 Message)을 스트림 이벤트 하나로 감싸 주니, 4장의 접기도 바꿀 것이 없습니다. 첫 이벤트가 Task 면 보기를 통째로 바꾸고 끝입니다. 다만 끝날 때까지 아무 이벤트도 오지 않으니, 진행 표시가 필요하면 GetTask 로 묻습니다(11부).

파이썬 — 구독은 보내지도 않는다, NotImplementedError

같은 예제의 둘째 단계는 SubscribeToTask 입니다. 내려갈 막는 호출이 없는 메서드라 세 SDK 가 셋으로 갈립니다.

클라이언트가 카드를 보고 막았다 — BaseClient.subscribe 는 설정이나 카드에 스트리밍이 없으면 요청 없이 NotImplementedError 를 던집니다(a2a/client/base_client.py:322). A2A 오류(A2AError)가 아니라 파이썬의 기본 예외입니다. 파이썬 서버 앞 탭의 메서드 줄에도 curl 의 것을 빼면 SubscribeToTask 가 둘(TS·Go)뿐입니다.

TypeScript — 그대로 보내고, 서버의 -32004 를 오류 클래스로 받는다

  • Client.resubscribeTask 에는 카드 검사가 없습니다(client/index.js:5588) — 스트림 보내기는 내려가는데, 구독은 그냥 보냅니다.
  • 서버가 첫 이벤트 전에 JSON 오류로 답했으니, 8부의 "SSE 이벤트 속 오류" 와 달리 cause 로 감싸지 않은 JsonRpcUnsupportedOperationError 가 바로 왔습니다(8부). 예제는 두 경우를 다 받으려고 cause ?? err 를 봅니다.

Go — 파이썬 서버에 구독하면 오류도 이벤트도 없다

  • Go 의 SubscribeToTask 에도 카드 검사가 없습니다(a2aclient/client.go:141). 요청은 나갔습니다.
  • 상대가 Go 서버(:11076)면 SSE 로 온 -32004 를 받아 errors.Is(err, a2a.ErrUnsupportedOperation) 가 참입니다. 상대가 파이썬 서버(:11074)면 반복이 아무것도 내지 않고 끝났습니다 — ②가 한 줄도 없습니다.

Go 클라이언트는 스트림 응답의 Content-Type 을 보지 않는다 — JSON 오류가 사라진다

파이썬 서버 앞 탭의 마지막 주고받음(Go 클라이언트의 구독)입니다.

  • 서버는 application/json 으로 -32004 를 정확히 답했습니다. Go 의 JSON-RPC 전송은 스트림 메서드의 응답을 머리와 상관없이 SSE 해석기에 넣고(a2aclient/jsonrpc.go:213), 해석기는 data: 로 시작하지 않는 줄을 건너뜁니다(internal/sse/sse.go:120). JSON 본문에는 그런 줄이 없으니 이벤트도 오류도 없이 끝납니다.
  • 같은 길을 SendStreamingMessage 도 지납니다. 파이썬·TS 서버는 첫 이벤트 전의 오류를 JSON 으로 답하므로(3장), Go 클라이언트는 그런 오류를 "빈 스트림" 으로 받게 됩니다(소스로 읽은 것 — 이 장의 캡처는 구독만 보였습니다).
Go 로 스트림을 받는 코드 — 이벤트가 하나도 없이 끝난 스트림은 정상이 아닙니다(§3.1.2 는 Message 하나나 Task 로 시작하라고 합니다). "첫 이벤트를 못 받았으면 오류" 로 다루고 GetTask 등으로 다시 확인합니다.

Q. Go SDK 클라이언트로 스트리밍을 켜지 않은 파이썬 에이전트에 SubscribeToTask 를 불렀더니, for ev, err := range 가 한 번도 돌지 않고 끝났습니다. 서버가 스트림을 열었다가 바로 닫은 것입니까?

A. 아닙니다. 파이썬 서버는 스트림을 열지 않고 application/json 으로 -32004 오류를 답했습니다(탭). Go 클라이언트가 그 본문을 SSE 로 읽다가 data: 줄을 하나도 못 찾아 이벤트도 오류도 없이 끝낸 것입니다. 같은 클라이언트가 Go 서버에서는 SSE 로 온 오류를 받아 errors.Is(err, a2a.ErrUnsupportedOperation) 가 참이었습니다(Go).
