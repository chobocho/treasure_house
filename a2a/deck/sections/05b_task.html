REJECTED·FAILED·CANCELED

세 가지 "잘 안 됨" → 무엇을 고르나 → 거절 실험 → 숙소(파이썬)의 거절 → 교통(TS)·식사(Go)의 거절 → 실패 실험(고장 에이전트) → 파이썬 → TypeScript → Go → 와이어 → 세 SDK 비교 → 취소 실험 → 세 서버의 취소 → 취소의 와이어 → 두 번째 취소 → 스펙의 두 문장 → 장 정리

거절 실험 — 세 에이전트에 하나씩, 규칙에 안 맞는 요청을

언어마다 다른 에이전트를 골라 세 SDK 를 한 번에 봅니다. 숙소(파이썬)에는 모든 숙소가 문 닫는 12월 31일, 교통(TS)에는 0명, 식사(Go)에는 채식 점심이 들어갈 수 없는 점심 상한 11,000원(산채 비빔밥이 12,000원)을 보냅니다.

숙소(파이썬)의 거절 — 상태는 REJECTED, 까닭은 status.message, 아티팩트는 없다

파이썬 서버의 답입니다. 막는 호출이라 종료 상태에서 돌아왔습니다(§3.2.2).

  • status.message 의 글이 가능한 숙소가 없습니다 입니다 — 숙소 에이전트가 TaskUpdater.reject(message) 로 실은 것입니다.
  • artifacts 키가 없고, history 에는 보낸 메시지 하나뿐입니다. 거절은 결과물이 없는 끝입니다.

교통(TS)·식사(Go)의 거절 — 같은 모양, TS 만 까닭을 이력에도 넣었다

두 서버의 답에서 맨 윗단 키, 상태, 글만 골랐습니다.

  • TS 서버는 거절 메시지를 status.message 와 history 에 함께 넣었습니다 — 상태 갱신의 메시지를 곧장 이력에 붙이는 TS SDK 의 방식입니다(5장). 파이썬·Go 서버의 이력에는 사용자 메시지 하나뿐입니다.
  • 세 에이전트 모두 일을 시작하지 않았습니다. 다시 보내도 같은 답이니, 클라이언트는 날짜·인원·상한을 고쳐야 합니다.

실패 실험 — 고장 에이전트가 세 가지로 실패한다

세 언어로 "고장 에이전트" 를 썼습니다. 받은 글에 따라 직접(실행기가 FAILED 를 싣는다), 나중(Task·WORKING 을 실은 뒤 예외), 먼저(아무것도 싣기 전에 예외)로 실패합니다. 맨손 클라이언트 outcome.py 가 세 마디를 차례로 보냅니다.

오류였으면 ListTasks 로 찾는다 — 답이 JSON-RPC 오류면 클라이언트는 작업 id 를 모릅니다. 그래서 마디마다 맥락 id(ctx-1…)를 지어 보내고(4부), 오류일 때 그 맥락의 작업을 ListTasks 로 찾습니다. ListTasks 자체는 11부에서 다룹니다.

파이썬 — 실행기가 던지면 SDK 가 작업을 FAILED 로 저장하고, 클라이언트에는 -32603 을 준다

직접 은 TaskUpdater.failed(message) 입니다. 나중·먼저 는 raise 입니다.

  • 예외를 던지면 막는 호출의 답이 Task 가 아니라 JSON-RPC 오류 -32603(Internal error)입니다. 그런데 저장소에는 FAILED 작업이 남았습니다 — 먼저 에서도. SDK 가 실패를 적으려고 작업을 만들어 넣었기 때문입니다(active_task.py 의 _run_producer: ensure_task_id 뒤 TASK_STATE_FAILED).
  • SDK 는 저장된 작업의 상태만 FAILED 로 바꾸고 메시지는 싣지 않습니다(같은 곳). 예외의 글은 오류 응답의 message 로만 갔습니다.

TypeScript — 던지면 SDK 가 FAILED Task 를 지어 돌려주고, 까닭에 예외 글을 싣는다

TS 실행기는 async execute 라, 던진 예외는 거부된 Promise 가 됩니다. 요청 처리기가 그것을 잡습니다.

  • 셋 다 Task 로 답했습니다. 먼저 처럼 실행기가 Task 를 하나도 싣지 않았어도, SDK 가 FAILED Task 를 지어 싣습니다(dist/server/index.js 의 _runExecutor: "publishes a synthetic Task + statusUpdate(FAILED)").
  • 까닭은 Agent execution error: 뒤에 예외의 글을 붙인 것입니다. 서버 출력에는 Agent execution failed for message … 와 스택 트레이스가 찍힙니다.

Go — 오류를 내보내면 Task 가 있을 때만 FAILED, 까닭은 일부러 싣지 않는다

Go 실행기는 yield(nil, err) 로 오류를 내보냅니다(2부의 iter.Seq2).

  • 나중 은 FAILED Task 인데 까닭이 비었습니다. SDK 주석이 이유를 적었습니다 — "do not store cause.Error() as part of status to not disclose the cause to clients"(internal/taskupdate/manager.go 의 SetTaskFailed).
  • 먼저 는 저장된 Task 가 없어 FAILED 로 옮길 것이 없습니다 — "execution failed before a task was created". 답은 -32603 이고, 저장된 작업도 없습니다.

와이어 — 파이썬의 -32603 에는 data 가 없고, Go 의 -32603 에는 있다

나중 에 대한 파이썬 서버의 답과 먼저 에 대한 Go 서버의 답입니다.

  • 파이썬의 오류 객체는 code·message 뿐이고 키 차례도 error·id·jsonrpc 입니다. Go 는 §9.5 의 권고대로 data 배열에 google.rpc.ErrorInfo 를 실었습니다. 오류의 data 모양은 9장에서 셋을 견줍니다.
  • Go 는 Task 에는 까닭을 숨겼지만(앞 슬라이드), Task 가 없을 때의 오류 message 에는 예외 글을 그대로 내보냈습니다.

취소 실험 — 배차의 첫 단계가 지나면 곧 CancelTask

교통 에이전트(단계 하나 2초)에 returnImmediately 로 배차를 맡기고, 상태가 WORKING(첫 단계 "배차 요청 접수")이 되면 취소합니다. 취소를 한 번 더 보내고, 0.5초 뒤 GetTask 로 남은 상태를 봅니다.

엿보기는 탭을 비켜 간다 — 첫 단계가 지났는지 GetTask 로 몇 번 엿볼지는 기계의 빠르기에 달려 있습니다. 그래서 엿보기는 서버에 곧장(둘째 인자), 나머지는 탭을 거쳐(첫 인자) 보내, 와이어 기록에는 네 번의 주고받음만 남깁니다. 시간을 재어 기다리는 방식은 이 기계에서 한 번 어긋났습니다.

세 서버 모두 첫 단계 뒤에 CANCELED, 실행기도 거기서 멈췄다

클라이언트의 출력과 세 서버의 출력입니다.

  • 첫 CancelTask 의 답이 셋 다 CANCELED 이고, 까닭은 교통 에이전트의 취소 처리기(cancel·cancelTask·Cancel)가 실은 배차를 취소했습니다 입니다.
  • 명세 끝의 3초 동안 둘째 단계(기사 배정)가 찍히지 않았습니다. 실행기가 쉬던 자리에서 끊겼습니다 — 파이썬은 asyncio.sleep 의 취소, TS 는 AbortSignal, Go 는 ctx 로.
  • 둘째 CancelTask 만 갈렸습니다(뒤에서).

CancelTask 의 답은 Task 그 자체 — SendMessage 처럼 task 로 감싸지 않는다

파이썬 서버 앞 탭의 둘째 주고받음(첫 CancelTask)입니다.

  • result 바로 아래가 id 입니다. SendMessage 의 답은 result.task 였습니다(4장) — 답이 Task 나 Message 둘 중 하나라 감싸야 했지만, CancelTask·GetTask 는 늘 Task 를 돌려줍니다(§3.1.3·§3.1.5 의 Outputs).
  • 이력에 배차 요청 접수 가 들어 있습니다. WORKING 의 메시지가 다음 상태(CANCELED)에 밀려 이력으로 옮겨진 것입니다 — 7장에서 이 규칙을 세 SDK 로 봅니다.

두 번째 취소 — 파이썬은 -32002, TS·Go 는 같은 Task 를 다시 준다

이미 CANCELED 인 작업에 CancelTask 를 또 보냈을 때의 세 답입니다.

  • 파이썬 SDK: "Terminal tasks, including already cancelled ones, are not cancelable."(default_request_handler_v2.py 의 주석) — 그래서 TaskNotCancelableError.
  • TS SDK 는 if (currentState === 5 /* TASK_STATE_CANCELED */) return task;(dist/server/index.js 의 cancelTask), Go SDK 는 task.Status.State.Terminal() && task.Status.State != a2a.TaskStateCanceled 일 때만 거절합니다(a2asrv/agentexec.go 의 CreateCanceler). 두 SDK 모두 실행기의 취소 처리기를 다시 부르지 않았습니다 — 서버 출력의 [교통] 취소 는 한 번뿐입니다.

6장 퀴즈

Q. 정산 에이전트를 만드는 중입니다. 예산 파일을 읽다가 예외가 나면 그냥 던지도록 두었습니다. 파이썬·TS·Go 서버에서 클라이언트는 각각 무엇을 받습니까? 그리고 어떻게 고쳐야 셋이 같아집니까?

A. Task 를 실은 뒤에 던졌다면 파이썬은 Task 없이 JSON-RPC 오류 -32603(저장소에는 FAILED), TS 는 Agent execution error: … 를 단 FAILED Task, Go 는 까닭 없는 FAILED Task 를 줍니다(비교의 "나중"). 실행기가 예외를 잡아 FAILED 상태와 까닭 메시지를 직접 실으면 세 서버 모두 같은 FAILED Task 와 까닭을 돌려줍니다(파이썬·TS·Go의 "직접").

7장

GetTask 와 historyLength

§3.2.4 의 세 경우 → 실험 명세와 파이썬 클라이언트 → 세 클라이언트의 출력 → TypeScript → Go → 와이어의 0 과 1 → 음수를 주면 → 이력에는 무엇이 쌓이나 → Go 서버의 이력이 짧았던 까닭 → 세 SDK 비교

historyLength — 안 주면 서버 마음, 0 이면 이력 없이, N 이면 최근 N 개까지

GetTask(§3.1.3)는 작업의 지금 상태·아티팩트와 "optionally history" 를 돌려줍니다. 이력의 양은 요청의 historyLength 가 정합니다 — §3.2.4 "History Length Semantics".

historyLength§3.2.4
없음(unset)"No limit imposed; server returns its default amount of history (implementation-defined, may be all history)"
0"No history should be returned; the history field SHOULD be omitted"
> 0"Return at most this many recent messages from the task's history"
"없음" 과 0 을 가려야 한다 — proto 는 이 필드를 optional int32 history_length 로 두어 "안 줌" 과 "0 을 줌" 을 구별합니다. 주석은 한 줄 더 붙입니다 — "The server MUST NOT return more messages than the provided value, but MAY apply a lower limit." 같은 필드가 SendMessageConfiguration 에도 있습니다 — "… to retrieve in the response". SendMessage 의 답으로 받는 Task 의 이력 수를 정합니다.

배차 하나를 끝낸 뒤, 같은 작업을 여섯 번 묻는다

교통 에이전트는 단계마다 WORKING 메시지를 실으므로 끝난 작업에 이력이 쌓입니다. 세 언어의 SDK 클라이언트가 제 언어의 서버에 막는 호출로 배차를 맡기고, historyLength 를 없음·0·1·2·10·-1 로 바꿔 GetTask 합니다.

세 서버의 답이 같다 — 넷, 없음, 가장 최근 하나, 최근 둘, 넷 — 그리고 -1 에서 갈린다

줄마다 받은 이력의 개수와 내용입니다. (데이터) 는 사용자가 보낸 데이터 파트(배차 요청)입니다.

  • 없음과 10 은 넷 전부, 0 은 하나도 없이, 1·2 는 뒤에서부터 그만큼입니다 — "recent messages". 세 서버 모두 §3.2.4 대로입니다.
  • -1 만 다릅니다. 파이썬 서버는 -32602 로 거절했고, TS·Go 서버는 이력 없이 답했습니다(뒤에서).

TypeScript — historyLength 는 선택 필드, 빼면 "없음" 이다

ts-proto 의 GetTaskRequest 에서 historyLength?: number | undefined 만 선택이고 tenant·id 는 꼭 적어야 합니다.

0 을 넣으면 와이어에 0 이 간다 — undefined 일 때만 키가 빠집니다(GetTaskRequest.toJSON 의 if (message.historyLength !== void 0)). 파이썬은 proto3 의 optional 이라 history_length=0 을 넣으면 "준 것" 으로 셉니다(HasField).

Go — HistoryLength 는 *int, nil 과 &0 이 다르다

Go 구조체는 "안 줌" 을 포인터로 나타냅니다. 태그가 json:"historyLength,omitempty" 라 nil 이면 키가 빠지고, &n 이면 0 이어도 실립니다.

루프 변수의 주소 — HistoryLength: &n 은 Go 1.22 부터 안전합니다. 반복마다 n 이 새 변수라, 여섯 요청이 각자의 값을 가리킵니다.

와이어 — 0 이면 history 키가 아예 없고, 1 이면 마지막 메시지 하나

파이썬 서버 앞 탭에서 historyLength 0 과 1 의 주고받음입니다(맨 윗단 키와 글만 — 첫 글은 아티팩트의 것).

  • 0 의 답에는 status·artifacts 만 있고 history 가 없습니다 — "SHOULD be omitted". TS·Go 서버도 키를 뺐습니다(다음 슬라이드의 맨 윗단 키).
  • 1 의 답에는 차량 확정 하나가 남았습니다. 사용자의 요청은 가장 오래된 것이라 잘렸습니다.

음수를 주면 — 파이썬은 -32602, TS·Go 는 0 처럼 다룬다

스펙은 음수를 말하지 않습니다. 세 SDK 가 각자 정했습니다.

  • 파이썬: validate_history_length 가 "history length must be non-negative" 로 거절합니다(utils/task.py). §3.3.2 의 검증 오류("Servers MUST validate all input parameters")에 가깝습니다.
  • TS: if (params.historyLength <= 0) task.history = [];(_applyHistoryLengthSemantics). Go: if historyLength <= 0 { task.History = []*a2a.Message{} }(a2asrv/handler.go). 빈 목록이라 직렬화 때 키째 빠집니다.

이력에 쌓이는 것 — 사용자 메시지, 그리고 지나간 상태의 메시지

배차 작업의 이력 넷 중 셋은 에이전트의 WORKING 메시지였습니다. 6장의 취소된 작업을 GetTask 로 본 답에서 상태와 이력의 메시지만 골랐습니다.

  • 파이썬·Go 는 상태가 바뀔 때 앞 상태의 메시지를 이력으로 옮깁니다(server/tasks/task_manager.py 의 save_task_event, Go 의 a2aevent/event.go 의 applyStatusUpdate: task.History = append(task.History, task.Status.Message)). 그래서 지금 상태의 배차를 취소했습니다 는 아직 이력에 없습니다.
  • TS 는 상태 갱신을 받는 즉시 그 메시지를 이력에도 붙여, 지금 상태의 메시지가 두 곳에 있습니다(5장의 applyStatusUpdate).

Go 에서 Task 를 다시 실을 때 — 지난 물음을 먼저 이력으로 옮겨 둔다

Go SDK 도 앞 상태의 메시지를 이력으로 옮기지만(앞 슬라이드), 그것은 상태 갱신 이벤트일 때입니다. Task 이벤트는 받은 그대로 저장합니다(internal/taskupdate/manager.go 의 Process). 이어 말하기의 첫 이벤트로 Task 를 다시 싣는 이 책의 common.Begin(5장)은 그래서 한 가지를 더 합니다.

  • working() 은 상태를 WORKING 으로 바꾸기 전에 지난 status.message(되물은 말)를 이력에 넣습니다. 이 줄이 없으면 상태가 통째로 바뀌며 물음이 이력에 가지 못하고 지워집니다.
  • SDK 가 이번 메시지를 이미 끝에 붙였으면 물음을 그 앞에 둡니다. 같은 messageId 로 다시 온 메시지는 SDK 가 붙이지 않으므로(4부) id 가 아니라 같은 값인지(h[n-1] == cur)로 가립니다.
  • TS 의 begin 은 이 일이 필요 없습니다 — TS SDK 가 물음을 이미 이력에 붙여 두었습니다. 파이썬 begin 은 이어 말하기에 Task 를 다시 싣지 않습니다.

7장 퀴즈

Q. 배차 작업을 GetTask 로 물을 때 마지막 진행 알림 하나만 받고 싶습니다. historyLength 를 얼마로 주면 됩니까? 그리고 클라이언트 코드가 실수로 -1 을 보내면 세 서버는 각각 어떻게 답합니까?

A. 1 입니다 — 세 서버 모두 가장 최근 메시지 차량 확정 하나를 돌려줬습니다(출력). -1 은 파이썬 서버가 -32602("history length must be non-negative")로 거절하고, TS·Go 서버는 0 처럼 이력 없이 답합니다(음수). 스펙이 음수를 정하지 않아 SDK 마다 다릅니다.

Q. 식사 에이전트는 식단표를 세 조각으로 실었습니다. 막는 호출로 받은 Task 에서 식단표 아티팩트는 몇 개이고 파트는 몇 개입니까? 그 아티팩트의 id 는 누가 정했습니까?

9장

작업 둘레의 오류

세 연산이 낼 수 있는 오류 → 실험 명세 → 없는 작업(-32001) → 끝난 작업에 이어 말하기(-32004) → 끝난 작업의 취소(-32002) → data 의 규칙(§9.5) → 파이썬의 data → TypeScript → Go → 장 정리 표

작업을 다루는 세 연산이 낼 수 있는 A2A 오류는 셋 — -32001·-32002·-32004

각 연산의 "Errors" 목록(§3.1.1·§3.1.3·§3.1.5)에서 작업에 걸린 것만 모으고, JSON-RPC 코드는 §5.4 의 대응표에서 옮겼습니다.

연산오류코드언제
GetTaskTaskNotFoundError-32001"The task ID does not exist or is not accessible."
CancelTaskTaskNotFoundError-32001같음
TaskNotCancelableError-32002"not in a cancelable state (e.g., already completed, failed, or canceled)"
SendMessageTaskNotFoundError-32001없는 taskId 로 이어 말할 때(4부)
UnsupportedOperationError-32004"Messages sent to Tasks that are in a terminal state … cannot accept further messages."
"not accessible" 도 -32001 — §3.3.2 는 "Servers SHOULD NOT distinguish between 'does not exist' and 'not authorized'" 라 합니다. 남의 작업을 물어도 "없다" 로 답해, 있다는 사실조차 흘리지 않습니다. 사용자별 작업 범위는 12부에서 봅니다.

오류 여섯 번 — 없는 작업에 셋, 끝난 작업에 셋

숙소 에이전트 셋에 맨손 클라이언트 errors.py 를 붙였습니다. 없는 id t-없는-작업 에 GetTask·CancelTask·SendMessage, 그다음 COMPLETED 작업과 REJECTED 작업을 만들어 이어 말하고 취소합니다.

이 명세에는 탭이 없다 — 클라이언트가 오류의 data 를 키까지 찍으므로 와이어를 따로 볼 필요가 없습니다. 게다가 파이썬 숙소 에이전트 앞에 탭을 끼우면, 끝난 작업에 이어 말할 때 서버가 OpenTelemetry 의 "Failed to detach context" 트레이스를 메모리 주소와 함께 찍어 캡처가 실행마다 달라졌습니다.

없는 작업 — 세 연산, 세 서버 모두 -32001, 문구만 셋

①②③ 의 코드와 message 입니다(파이썬·TS·Go 서버 차례).

  • 코드는 아홉 번 모두 -32001 입니다. 클라이언트는 코드로 가르고, message 는 사람에게 보여 주는 데만 씁니다.
  • Go 의 문구는 SDK 안의 오류가 겹겹이 감싸인 것입니다(failed to cancel: cancelation failed: canceler setup failed: …). 파이썬은 GetTask·CancelTask 에 id 를 넣지 않았고, TS 는 셋 다 id 를 붙였습니다.

끝난 작업에 이어 말하기 — COMPLETED 에도 REJECTED 에도 -32004

④는 견적까지 끝난 작업에 "1명 더", ⑥은 거절된 작업에 "다시" 를 같은 taskId 로 보냈습니다.

  • 셋 다 -32004 UnsupportedOperationError 로 §3.1.1 을 지켰습니다. 실행기는 불리지 않았습니다 — 서버 출력의 [숙소] 줄은 작업을 만든 두 번(견적·거절)뿐입니다. TS 의 문구는 상태를 수로 적었습니다 — (3) 은 COMPLETED, (7) 은 REJECTED(2장의 표).
  • 파이썬 SDK 에는 이 경우의 문구가 둘 있습니다 — 끝난 실행이 아직 메모리에 있으면 "Task … is already completed.", 그것을 치운 뒤 저장소에서 다시 불러왔으면 "Task … is in terminal state: TASK_STATE_…"(active_task.py). 둘 중 어느 것이 나올지는 때에 달려서, errors.py 는 ④⑥ 앞에서 1초 기다려 늘 뒤의 것을 봅니다. 문구에 기대지 말고 코드로 가릅니다.
  • 뒤의 경로에서 파이썬 서버는 stderr 에 OpenTelemetry 경고("Failed to detach context" traceback, 메모리 주소가 든)를 흘립니다. 캡처가 매번 달라지므로 이 명세만 파이썬 서버의 stderr 를 버렸습니다 — 명령 줄의 2>/dev/null 이 그 표시입니다.

끝난 작업의 취소 — 셋 다 -32002, CANCELED 의 재취소와는 다르다

⑤는 COMPLETED 작업에 CancelTask 를 보냈습니다.

  • 여기서는 세 서버가 같습니다 — 끝난 일을 취소할 수는 없습니다(§3.1.5).
  • TS·Go 가 같은 Task 를 돌려준 것은 이미 CANCELED 인 작업을 다시 취소했을 때뿐입니다(6장). 두 SDK 의 코드도 CANCELED 하나만 따로 빼고 나머지 종료 상태는 -32002 로 막습니다.

오류의 data 는 @type 을 단 객체의 배열 — google.rpc.ErrorInfo 를 권한다

§3.3.2 는 오류가 코드·메시지에 더해 "Error Details (optional): An array of objects" 를 실을 수 있다고 하고, §9.5 가 JSON-RPC 에서는 그것을 error.data 에 둔다고 정합니다.

규칙스펙의 말
모양"error.data (array of objects, each containing a @type key, using ProtoJSON Any representation)"
무슨 타입"Implementations SHOULD use well-known types such as google.rpc.ErrorInfo … or google.rpc.BadRequest"
§9.5 의 예-32001 에 ErrorInfo — reason TASK_NOT_FOUND, domain a2a-protocol.org, metadata 에 taskId·timestamp
reason 은 오류 이름의 대문자 꼴 — 이 장의 캡처에서 TASK_NOT_FOUND·TASK_NOT_CANCELABLE·UNSUPPORTED_OPERATION, 7장에서 INVALID_PARAMS, 6장에서 INTERNAL_ERROR 를 봤습니다. 이제 세 서버가 무엇을 실었는지 하나씩 봅니다.

파이썬 — ErrorInfo 하나, metadata 는 빈 객체, 예외에서 온 -32603 에는 data 가 없다

파이썬 서버에 보낸 여섯 요청의 data 입니다.

  • 여섯 번 모두 google.rpc.ErrorInfo 하나에 metadata: {} 입니다. SDK 는 오류 객체의 data 를 metadata 로 옮기는데(utils/error_handlers.py 의 build_error_details), 이 오류들에는 실을 것이 없었습니다. §9.5 의 예처럼 taskId 를 넣지는 않습니다.
  • 실행기가 던진 예외는 A2A 오류가 아니라 -32603 에 data 가 아예 없습니다(6장의 와이어).

TypeScript — ErrorInfo 에 metadata 키가 없다

TS 서버에 보낸 여섯 요청의 data 입니다.

  • A2AError.toErrorInfo() 는 metadata 가 비면 키를 아예 빼고 @type·reason·domain 만 싣습니다(dist/server/express/index.js).
  • 대신 message 에 작업 id 를 넣었습니다(앞에서). 기계가 읽을 자리(metadata.taskId)가 아니라 사람이 읽을 자리입니다.

Go — 모든 오류의 ErrorInfo 에 metadata.timestamp 를 단다

Go 서버에 보낸 여섯 요청의 data 입니다.

  • JSON-RPC 오류를 만들 때 "timestamp": time.Now().UTC().Format(time.RFC3339) 을 늘 넣습니다(internal/jsonrpc/jsonrpc.go). §9.5 의 예에 있는 두 키 중 timestamp 만 채운 셈입니다.
  • A2A 오류가 아닌 실패에도 INTERNAL_ERROR 로 ErrorInfo 를 붙였습니다(6장). 세 SDK 중 data 가 빠지는 일이 없는 것은 Go 하나입니다.

9장 퀴즈

Q. 기획 에이전트가 숙소 작업에 이어 말했는데 -32004 를 받았습니다. 숙소 작업은 어떤 상태일 수 있고, 기획 에이전트는 무엇을 해야 합니까? message 의 문구로 COMPLETED 와 REJECTED 를 가를 수 있습니까?

A. 종료 상태(COMPLETED·FAILED·CANCELED·REJECTED) 중 하나입니다 — 세 서버 모두 COMPLETED 와 REJECTED 작업에 -32004 를 줬습니다(④⑥). 이어 말할 수 없으니 GetTask 로 상태를 확인하고, 필요하면 같은 contextId 로 새 작업을 만듭니다. 문구로는 가를 수 없습니다 — 파이썬 서버는 REJECTED 작업에도 "is already completed." 라고 답했습니다. 상태는 GetTask 의 status.state 로 봅니다.

5부 정리

장한 줄
1·2Task 는 필드 여섯의 일 단위, 상태는 아홉 — 종료 넷·중단 둘. 전이 표는 스펙에도 SDK 에도 없어 실행기가 지킨다
3·4막는 호출은 끝나거나 멈출 때까지, returnImmediately 는 SUBMITTED 로 곧장. 결과는 artifacts, 상태는 status.state
5INPUT_REQUIRED 에는 같은 taskId 로 답한다. 이력과 스트림 첫머리는 서버마다 다르다
6REJECTED 는 "안 하겠다", FAILED 는 "하다 깨졌다", CANCELED 는 "그만" — 까닭은 status.message 에, 예외로 흘리면 셋이 달라진다
7historyLength 없음·0·N 은 셋 다 §3.2.4 대로, 음수와 이력에 쌓이는 메시지가 다르다
8아티팩트는 id·이름·파트, 한 작업에 여럿. 이어 붙일 것은 id 를 정해 둔다
9-32001·-32002·-32004 는 셋이 같고, data 와 문구가 다르다 — 코드로 가른다
다음 — 3~5부는 완성 에이전트를 블랙박스로 두고 와이어만 읽었습니다. 그 와이어를 서버 쪽에서 직접 만들어 볼 차례입니다. 6부는 SDK 없이 표준 라이브러리만으로 숙소 에이전트 축소판을 세 언어로 짓습니다 — JSON-RPC 디스패치, Task 저장소와 상태 전이, SendMessage·GetTask·CancelTask, 그리고 이 부에서 본 오류 코드를 손으로 돌려주는 일입니다.
