5장

skills — 무엇을 맡길 수 있나

스킬의 필드 → 다섯 에이전트의 스킬과 태그 → 입출력 모드는 기본값을 덮어쓴다 → 요청에는 스킬을 적는 자리가 없다 → 태그로 고르기: 파이썬 → 실행 → TypeScript → Go → 세 언어 비교

스킬 하나 = 필수 넷 + 선택 넷

1장에서 숙소 에이전트의 스킬 find-lodging 을 봤습니다. 이번에는 AgentSkill 의 필드 전부를 proto 에서 옮깁니다.

  • examples 는 문자열 목록입니다. 숙소 에이전트는 DataPart 로 보낼 JSON 을 글자로 적어 두었습니다(1장).

다섯 스킬 — 공통 태그 하나, 역할 태그 하나

다섯 에이전트를 세 언어로 섞어 띄우고(숙소 py·식사 ts·교통 go·정산 py·기획 go), 이 장의 고르기 프로그램에 태그 workshop 을 줬습니다. 다섯 카드가 모두 걸립니다.

  • 대괄호 안이 스킬의 tags, 화살표 뒤가 그 스킬의 출력 모드입니다. workshop 은 다섯 모두에 있고, 나머지 한 태그(lodging·meals·transport·budget·orchestration)가 역할을 가릅니다.
  • 정산 에이전트의 공개 카드에는 check-budget 하나뿐입니다. 결재까지 하는 settle-budget 은 로그인한 클라이언트가 받는 확장 카드에만 있습니다(12부).

스킬의 입출력 모드는 카드의 기본값을 덮어쓴다

카드의 defaultInputModes·defaultOutputModes(1장)는 "across all skills" 의 기본값이고, 스킬에 inputModes·outputModes 를 적으면 그 스킬만은 그 값을 씁니다. 그래서 어떤 스킬의 실제 모드는 이렇게 구합니다.

 스킬의 outputModes 가 비어 있지 않다 → 그 목록
 비어 있다(안 적었다)                 → 카드의 defaultOutputModes
  • 보물상사의 다섯 스킬은 모두 모드를 안 적었습니다. 앞 슬라이드에서 식사 에이전트가 application/json,text/markdown 으로 나온 것은 카드의 defaultOutputModes 입니다.
  • 서버가 들어온 파트의 미디어 타입을 이 목록과 대 보는지는 SDK 마다 다르고, 셋 다 기본은 대 보지 않습니다.

요청에는 스킬을 적는 자리가 없다 — 스킬은 고를 때만 쓴다

SendMessageRequest 의 필드는 tenant·message·configuration·metadata 뿐이고, 메시지(4부)에도 스킬 id 를 적는 필드가 없습니다. 클라이언트는 "이 스킬을 써 달라" 고 말할 수 없습니다.

  • 그래서 스킬은 에이전트를 고르는 데 씁니다. 고른 다음에는 메시지만 보내고, 무슨 일을 할지는 에이전트가 메시지를 읽고 정합니다.
  • 파이썬 SDK 의 입력 모드 검사기 주석도 같은 말을 합니다: "A request does not name the skill that will serve it, so the union is the most that can be decided here" — 앞 슬라이드 표에서 파이썬이 합집합으로 검사하는 까닭입니다.
  • examples 는 이 빈자리를 메웁니다. 고른 쪽이 메시지를 어떤 꼴로 만들지 보여 주는 견본입니다.
스킬이 여럿인 에이전트 — 한 카드에 스킬을 여럿 적을 수 있지만, 고르는 쪽이 아는 것은 "이 에이전트가 이런 일들을 한다" 까지입니다. 일을 가르는 것은 메시지 내용입니다.

태그로 고르기 — 태그가 맞고, 원하는 출력 모드를 내는 스킬

카드 주소 목록을 받아 카드를 하나씩 받고, 스킬마다 두 가지를 봅니다: 찾는 태그가 tags 에 있는가, (주었다면) 원하는 출력 모드가 그 스킬의 실제 모드에 있는가. 파이썬은 SDK 의 A2ACardResolver 로 카드를 받습니다.

15부의 기획 에이전트 — 이것을 역할마다 한 번씩 합니다 — 태그 lodging 이면 숙소 역할, meals 면 식사 역할. 이 장은 그 고르기 한 번만 떼어 봅니다.

세 질문 — 다섯 곳, 한 곳, 두 곳

카드는 SDK 가 받아 proto 메시지(AgentCard)로 돌려줍니다. 필드 이름은 snake_case(output_modes·default_output_modes)입니다.

  • lodging 은 숙소 하나만 고릅니다. 역할 태그가 하나씩이라 "누구에게 맡길까" 가 한 줄로 정해집니다.
  • --out text/markdown 을 더하면 workshop 다섯 가운데 마크다운을 내는 식사·기획 둘만 남습니다.

TypeScript — resolve() 는 받은 JSON 을 거의 그대로 준다

TS 는 DefaultAgentCardResolver 의 resolve(url) 로 카드를 받습니다. 결과의 타입은 AgentCard 이고, 그 타입에서 outputModes 는 string[] 입니다. 그런데 카드에 없으면 실제 값은 undefined 입니다.

타입과 값이 다른 까닭 — 설치본 dist/client/index.js 의 normalizeAgentCard 는 카드가 proto 꼴 보안 필드(securitySchemes 값에 "type" 이 없는 꼴 등)를 가질 때만 AgentCard.fromJSON 으로 기본값을 채우고, 아니면 받은 JSON 을 그대로 돌려줍니다. 그래서 ?? [] 를 붙였습니다.

Go — 구조체라서 빈 목록은 nil

Go 는 agentcard.NewResolver(…).Resolve(ctx, url) 로 *a2a.AgentCard 를 받습니다. 카드에 없는 outputModes 는 nil 슬라이스이고, len(nil) 은 0 이라 따로 막을 것이 없습니다.

세 언어 비교 — 같은 질문에 같은 답

세 프로그램은 질문 셋 모두에서 한 글자도 다르지 않은 답을 냈습니다(pick_skill 캡처의 터미널 6). 다른 것은 카드를 담는 그릇입니다.

5장 퀴즈

Q. --out text/markdown workshop 질문에 식사 에이전트(plan-meals)가 뽑혔습니다. 뽑힌 근거인 text/markdown 은 스킬과 카드 중 어디에 적힌 값입니까?

A. 카드의 defaultOutputModes 입니다. plan-meals 스킬은 outputModes 를 적지 않았으므로 카드의 기본값을 씁니다(덮어쓰기 규칙). 실행 결과의 화살표 뒤 application/json,text/markdown(세 질문)이 식사 카드의 기본값 그대로입니다.

6장

capabilities — 카드에 없는 기능을 부르면

기능 넷 → §3.3.4 의 규칙 → 기능 없는 안내 에이전트 → "없음" 을 적는 두 가지 → 스트림을 부르면 → 푸시 설정을 만들면 → 확장 카드를 달라면 → 세 서버 비교 → Go 는 넘겨받아야 검사한다 → 검사를 끄면 → 클라이언트는 카드를 먼저 본다: 파이썬 → 와이어 → TypeScript → Go → 세 클라이언트 비교

기능 넷 — 켜 두면 약속, 빠지면 "없음"

AgentCapabilities 의 필드는 넷입니다(1장). 셋은 optional bool, 하나는 목록입니다.

필드proto 주석켠 에이전트자세히
streaming"supports streaming responses"다섯 모두10부
pushNotifications"supports sending push notifications"교통11부
extensions"A list of protocol extensions supported"—14부
extendedAgentCard"supports providing an extended agent card when authenticated"정산12부

"켠 에이전트" 는 1장의 다섯 카드 요약에서 옮겼습니다. 이 장은 각 기능의 쓰임새가 아니라, 켜지 않은 기능을 누군가 부를 때 일어나는 일만 봅니다.

§3.3.4 — 선언하지 않은 기능은 오류로 답해야 한다

"When clients attempt to use operations or features that require capabilities not declared as supported in the Agent Card, the agent MUST return an appropriate error response." 기능마다 오류가 정해져 있습니다(코드는 §5.4 의 표).

클라이언트 쪽은 SHOULD — "Clients SHOULD validate capability support by examining the Agent Card before attempting operations that require optional capabilities." 서버는 막아야 하고, 클라이언트는 미리 보는 것이 좋습니다. 이 장은 둘 다 실험합니다.

실험 도구 — 기능을 하나도 켜지 않은 안내 에이전트

보물상사의 다섯은 모두 스트리밍을 켰으므로, 인사만 하는 작은 에이전트를 세 언어로 만들었습니다. capabilities 는 빈 객체입니다. 서버 조립은 다섯 에이전트의 공용 코드(agents/common)를 그대로 씁니다.

TS(03/no_caps.ts)·Go(03/no_caps)의 카드도 같습니다. 세 서버 앞에 탭을 하나씩 세우고, 같은 JSON-RPC 요청 넷을 curl 로 보냈습니다 — 보통 SendMessage(대조군), 스트림, 푸시 설정, 확장 카드.

"없음" 을 적는 두 가지 — 빈 객체와 false

TS 판의 카드도 capabilities: {} 입니다. 요청 넷을 보낸 뒤 세 서버에서 카드를 받아 capabilities 줄만 봤습니다.

둘 다 "지원하지 않음" — 파이썬·TS 는 빈 객체, Go 는 false 둘을 적었습니다(Go 구조체 태그에 omitempty 가 없는 두 필드, 2장). §3.3.4 가 "is false or not present" 를 한데 묶으므로 뜻은 같습니다.

스트림을 부르면 -32004 — Go 만 SSE 로 감싸 준다

대조군 SendMessage 는 세 서버 모두 인사로 답했습니다. 같은 메시지를 SendStreamingMessage 로 보내면 셋 다 -32004 입니다. 파이썬과 Go 의 응답입니다.

같은 오류, 다른 꼴 — 파이썬·TS 는 보통 JSON 응답(application/json)으로, Go 는 text/event-stream 의 이벤트 하나로 오류를 실었습니다. TS 의 문구는 "Streaming is not supported." 입니다.

푸시 설정을 만들면 -32003 — 작업이 있는지 보기도 전에

CreateTaskPushNotificationConfig 에 있지도 않은 작업 t-1 을 적었습니다. 세 서버 모두 "그런 작업이 없다"(-32001)가 아니라 "푸시를 지원하지 않는다" 로 답했습니다 — 기능 검사가 먼저입니다.

오류 이름은 data 에도 있다 — 세 서버 모두 error.data 에 google.rpc.ErrorInfo 하나를 싣고 "reason": "PUSH_NOTIFICATION_NOT_SUPPORTED" 를 적었습니다. 문구는 셋이 다르니, 프로그램은 code 나 reason 으로 가립니다.

확장 카드를 달라면 -32004 — "준비 안 됨"(-32007)이 아니다

GetExtendedAgentCard 를 불렀습니다. §3.3.4 는 두 경우를 가릅니다: 카드에 기능이 없으면 UnsupportedOperationError, 기능은 켰는데 확장 카드를 안 뒀으면 ExtendedAgentCardNotConfiguredError.

기능 검사가 먼저 — 세 서버 모두 앞의 경우로 답했습니다. 이 에이전트는 기능도, 확장 카드도 없으니 둘 다 해당하는 것 같지만, 순서상 기능 검사가 먼저입니다. -32007 이 나오는 경우는 조금 뒤에 봅니다.

오류 코드는 위 세 줄 모두 셋이 같고, 꼴은 Go 의 스트림만 다릅니다. 아래 세 줄은 SDK 마다 다릅니다.

Go SDK 는 카드의 기능을 넘겨받아야 검사한다

파이썬·TS 의 요청 처리기는 카드 자체를 받으므로 기능을 늘 압니다. Go 의 a2asrv.NewHandler 는 카드를 받지 않고, 옵션 WithCapabilityChecks(&card.Capabilities) 를 줘야 검사합니다. 다섯 에이전트의 공용 코드(agents/common/serve.go)는 이 옵션을 답니다.

실험용 스위치 — --no-checks 는 같은 옵션을 nil 로 한 번 더 줘서 덮습니다. 카드는 그대로 "아무것도 안 켰다" 입니다.

검사를 끄면 — 카드와 다르게 스트림이 열린다

--no-checks 로 띄운 Go 안내 에이전트에 스트림·푸시·확장 카드를 다시 보냈습니다(no_checks 명세).

  • 스트림 — 카드에 streaming 이 없는데 SSE 로 인사가 왔습니다. §3.3.4 의 MUST 를 어긴 서버입니다.
  • 푸시 — 여전히 -32003. 푸시 저장소·전송기를 달지 않았으므로 기능 검사가 아니라 "준비가 없어서" 막혔습니다.
  • 확장 카드 — 이번에는 -32007 extended card not configured. 확장 카드 생산자가 없어서입니다.
Go 로 서버를 짤 때 — WithCapabilityChecks 를 빼먹으면 카드가 하는 말과 서버가 하는 일이 어긋납니다. 카드를 만든 그 값(&card.Capabilities)을 넘기면 둘이 함께 움직입니다.

클라이언트도 카드를 먼저 본다 — 파이썬

§3.3.4 의 SHOULD 를 SDK 클라이언트는 어떻게 지킬까요. 세 언어의 SDK 클라이언트로 같은 셋을 불러 봤습니다: 메시지 보내기(스트림을 바라는 기본 설정), 푸시 설정 만들기, 확장 카드 받기. 상대는 탭 뒤의 파이썬 안내 에이전트입니다(caps_probe 명세).

①은 스트림이 아니었다 — send_message 는 카드에 streaming 이 없으면 막는 호출로 바꿉니다(설치본 client/base_client.py: if not self._config.streaming or not self._card.capabilities.streaming). ③은 오류 없이 공개 카드를 돌려받았습니다.

탭이 본 것 — 누가 실제로 서버까지 갔나

세 클라이언트가 차례로 지나간 뒤 탭의 요청 줄과 메서드만 추렸습니다. 카드 요청(GET)이 클라이언트 하나가 시작하는 곳입니다.

  • 셋 다 메서드가 SendStreamingMessage 가 아니라 SendMessage 입니다. 카드를 보고 막는 호출로 내려갔습니다.
  • GetExtendedAgentCard 는 한 번도 없습니다. 세 클라이언트 모두 서버에 묻지 않고 카드만 보고 끝냈습니다.
  • CreateTaskPushNotificationConfig 는 두 번 — 파이썬과 Go 는 보냈고, TS 는 보내지 않았습니다.

TypeScript — 푸시는 보내기 전에 막고, 확장 카드는 묻지 않는다

TS 클라이언트에는 확장 카드만 따로 부르는 메서드가 없습니다. getAgentCard() 가 카드의 extendedAgentCard 를 보고, 켜져 있을 때만 서버에 GetExtendedAgentCard 를 보냅니다.

②의 오류는 클라이언트가 만들었다 — 설치본 dist/client/index.js 의 createTaskPushNotificationConfig 는 카드에 pushNotifications 가 없으면 요청 없이 PushNotificationNotSupportedError 를 던집니다. 문구 Push Notification is not supported 도 TS SDK 의 것입니다.

Go — 확장 카드는 클라이언트가 -32007 로 막는다

Go 클라이언트는 푸시 설정을 그대로 보내고 서버의 오류 문구를 받았습니다. 확장 카드는 보내지 않고 클라이언트가 직접 오류를 냈습니다.

오류의 종류가 스펙과 다르다 — 설치본 a2aclient/client.go 의 GetExtendedAgentCard 는 카드에 기능이 없으면 a2a.ErrExtendedCardNotConfigured 를 돌려줍니다. 같은 상황에서 서버라면 §3.3.4 대로 UnsupportedOperationError 여야 합니다(세 서버의 답). 오류로 갈래를 탈 때 주의할 자리입니다.

세 클라이언트 비교 — 카드를 얼마나 믿나

셋이 갈리는 것은 푸시 설정 줄과 확장 카드 줄의 Go 칸입니다.

6장 퀴즈

Q. 기능이 하나도 없는 에이전트에 SDK 클라이언트로 스트리밍 메시지를 보냈는데, 서버 기록에 -32004 가 없고 대답도 잘 왔습니다. 서버가 §3.3.4 를 어긴 것입니까?

A. 아닙니다. 세 SDK 클라이언트는 카드에 streaming 이 없으면 SendStreamingMessage 대신 SendMessage 를 보냅니다(탭의 메서드 줄). 서버는 스트림 요청을 받은 적이 없으니 -32004 를 낼 일도 없었습니다. 서버가 스트림 요청을 받으면 -32004 로 답하는 것은 curl 로 직접 보낸 실험이 보여 줍니다.

7장

카드 캐싱 — 같은 카드를 몇 번이나 받나

§8.6 의 규칙 → 세 SDK 가 붙이는 머리글 → 머리글을 만드는 곳 → 조건부 GET: 파이썬 → 실행 → TypeScript 만 200 → fetch 가 덧붙이는 것 → Go → 세 서버 × 세 클라이언트 → SDK 클라이언트는 캐시하지 않는다

§8.6 — 카드는 HTTP 캐시로 아낀다

"Agent Card content changes infrequently relative to the frequency at which clients may fetch it. Servers and clients SHOULD use standard HTTP caching mechanisms." 카드는 거의 안 바뀌는데 클라이언트는 자주 받으니, HTTP 가 이미 가진 캐시 장치를 쓰라는 것입니다.

클라이언트 §8.6.2RFC 9111 의 캐시 규칙을 따른다(SHOULD) · 만료되면 If-None-Match(받아 둔 ETag)나 If-Modified-Since 로 조건부 요청(SHOULD) · 서버가 캐시 머리글을 안 주면 제 기본 기간을 써도 된다(MAY)

세 SDK 가 실제로 붙이는 머리글 — 셋이 다 다르다

세 언어의 숙소 에이전트를 띄우고 curl 로 카드 응답의 머리글만 받았습니다(cache 명세, 시각이 든 Date 줄만 뺐습니다). 차례로 파이썬·TS·Go 입니다.

  • ETag — 파이썬과 TS 는 있고, Go 는 없습니다.
  • Cache-Control — TS 만 public, max-age=3600(한 시간)을 답니다.
  • Last-Modified(MAY)는 셋 다 없습니다. 파이썬(uvicorn)은 머리글 이름을 소문자로 씁니다 — HTTP 머리글 이름은 대소문자를 가리지 않습니다.

  • 다섯 에이전트의 공용 코드는 세 언어 모두 SDK 기본값으로 카드 처리기를 답니다(파이썬은 cache_control 을 주지 않음). 앞 슬라이드의 머리글이 그 기본값입니다.

조건부 GET — 받아 둔 ETag 을 If-None-Match 로 돌려보낸다

카드를 한 번 받고, 응답의 ETag 을 If-None-Match 에 실어 한 번 더 묻는 프로그램을 표준 라이브러리로 만들었습니다. 파이썬 urllib 은 304 도 예외(HTTPError)로 올리므로 그것을 받아 상태 코드만 꺼냅니다.

파이썬 클라이언트 — 파이썬·TS 서버는 304, Go 서버는 물을 길이 없다

세 숙소 에이전트에 차례로 물었습니다.

  • 파이썬·TS 서버 — 둘째 요청에 304 Not Modified. 본문 없이 "받아 둔 카드가 그대로 맞다" 는 답입니다.
  • Go 서버 — ETag 이 없으니 조건부로 물을 수 없습니다. 클라이언트가 할 수 있는 것은 다시 다 받거나, §8.6.2 의 MAY 대로 제 기본 기간 동안 받아 둔 것을 쓰는 것뿐입니다.

TypeScript 클라이언트 — TS 서버에서만 304 가 아니라 200

fetch 로 같은 일을 합니다. 그런데 결과가 하나 다릅니다.

같은 ETag, 같은 서버인데 200 — 파이썬 클라이언트는 TS 서버(10371)에서 304 를 받았는데(앞 슬라이드), TS 클라이언트는 200 을 받았습니다. 파이썬 서버(10370)에서는 TS 클라이언트도 304 입니다. 무엇이 다른지 다음 슬라이드에서 요청 머리글을 봅니다.

fetch 는 조건부 요청에 no-cache 를 덧붙인다

요청 머리글을 찍기만 하는 작은 서버(echo_etag, 늘 ETag: W/"echo" 로 200)에 세 클라이언트를 차례로 보냈습니다. 줄마다 서버가 받은 요청 하나입니다(파이썬 두 줄, TS 두 줄, Go 두 줄).

  • TS(Node 의 fetch)만 둘째 요청에 Cache-Control: no-cache·Pragma: no-cache 를 덧붙였습니다. 우리 코드(앞 슬라이드의 get)는 If-None-Match 만 달았으니, 두 머리글은 Node 의 fetch 가 붙인 것입니다. 첫 요청에는 붙이지 않았습니다.
  • TS 서버의 304 판단은 express 의 req.fresh → fresh 패키지이고, 그 검사 가운데 하나가 "Always return stale when Cache-Control: no-cache" 입니다(설치본 node_modules/fresh/index.js). 파이썬 서버의 판단(_if_none_match_hits)은 Cache-Control 을 보지 않습니다.
304 는 따라오는 이점이다 — 같은 요청에도 서버 구현에 따라 304 대신 200 이 옵니다. 클라이언트는 200 이 와도 그 카드를 쓰면 되고, 304 에만 기대는 코드를 짜면 안 됩니다.

Go 클라이언트 — 304 를 그대로 돌려받는다

net/http 의 Client.Do 는 304 를 오류로 보지 않고 응답으로 돌려줍니다. 본문을 끝까지 읽고 닫아야 연결이 다시 쓰입니다.

세 서버 × 세 클라이언트 — 둘째 요청의 답

304 가 아닌 곳은 Go 서버 열 전부와, TS 클라이언트가 TS 서버에 물은 칸입니다.

클라이언트 ＼ 서버파이썬(10370)TS(10371)Go(10372)
파이썬 urllib304304묻지 못함
TS fetch304200묻지 못함
Go net/http304304묻지 못함
  • "묻지 못함" — Go 카드 처리기가 ETag 을 주지 않아서(머리글). 카드 응답이 늘 200 이고 본문 714바이트를 매번 보냅니다.
  • TS 의 200 — fetch 가 붙인 no-cache 를 express 가 존중해서(앞 슬라이드). 어느 쪽도 틀리지 않았고, 둘이 만나면 304 가 사라집니다.
Go 로 카드를 내줄 때 — SDK 처리기를 감싸 ETag·Cache-Control 을 다는 것은 운영의 일입니다(17부의 배포 체크리스트).

SDK 클라이언트는 카드를 캐시하지 않는다

세 SDK 의 카드 받기(5장의 비교 표)는 부를 때마다 GET 을 한 번 보내고, ETag 을 기억하거나 If-None-Match 를 보내는 코드가 없습니다(설치본 client/card_resolver.py·DefaultAgentCardResolver·a2aclient/agentcard 에 cache·etag 라는 말이 한 번도 나오지 않습니다).

  • 그래서 §8.6.2 의 캐시는 SDK 를 쓰는 쪽의 몫입니다. 가장 작은 캐시는 "한 번 받은 카드를 클라이언트가 살아 있는 동안 들고 있기" 입니다. 세 SDK 의 클라이언트 객체가 이미 그렇게 합니다 — 카드를 받아 만들고, 그 카드로 바인딩을 고르고 기능을 봅니다(세 클라이언트 비교).
  • 오래 사는 프로그램이 카드를 들고 있다가 다시 받아야 할 때 쓰는 것이 이 장의 조건부 GET 입니다. 15부의 기획 에이전트는 아직 그렇게 하지 않습니다. 요청마다 발견을 처음부터 다시 돌려 명단의 카드를 모두 새로 받습니다. 받은 카드를 들고 있지도, If-None-Match 를 보내지도 않습니다(15부 2장).

7장 퀴즈

Q. 파이썬 숙소 에이전트의 카드에 대해 클라이언트가 If-None-Match 로 받아 둔 ETag 을 보냈는데 200 과 새 카드가 왔습니다. 카드가 바뀌었다는 뜻입니까?

A. 파이썬 서버라면 그렇습니다. 파이썬 처리기는 Cache-Control 을 보지 않고 ETag 만 대 보므로(fetch 실험), 세 클라이언트 모두 304 를 받았습니다(표의 첫 열). 200 이면 카드 내용(서명 빼고)의 해시가 달라진 것입니다. 같은 일이 TS 서버에서 TS 클라이언트로 일어났다면 카드는 그대로일 수 있습니다 — no-cache 때문에 200 이 온 것입니다.

빈 것은 없는 것 — 필수 필드 검사

proto3 에서 목록·문자열 필드는 "비었다" 와 "없다" 가 같은 값입니다. 그래서 ProtoJSON 은 보통 빈 값을 적지 않습니다(4부). "skills": [] 인 카드와 skills 가 없는 카드는 proto 메시지로 읽으면 같은 카드가 됩니다. 검증기는 둘을 한 가지로 봅니다. 단 capabilities 는 메시지 필드라 빈 객체 {} 도 "있음" 입니다(6장).

필수 목록은 손으로 옮겼다 — CARD·IFACE·SKILL 은 a2a.proto 의 (google.api.field_behavior) = REQUIRED 표시를 옮긴 것입니다. 스펙 판이 바뀌면 함께 고쳐야 합니다.

인터페이스 검사 — 판 번호, 닿는가, 어디를 가리키나

인터페이스마다 셋을 봅니다. "닿는가" 는 그 url 로 GET 을 한 번 보내 어떤 답이든 오면 닿은 것으로 칩니다. JSON-RPC 끝점은 POST 를 받는 곳이라 GET 에 성공으로 답하지 않을 수 있지만, 답이 왔다면 거기 서버가 있다는 뜻입니다.

"다르다" 가 경고인 까닭 — 카드를 카탈로그에서 받거나, 카드만 다른 곳에 두는 배치도 있습니다(§8.2 의 다른 길). 그래서 막지 않고 알리기만 합니다.

망가진 카드 셋 — 정적 파일로 내준다

망가진 카드는 ex/run/03/cards/ 의 JSON 파일이고, 파이썬의 http.server 가 정적 파일로 내줍니다(포트 10380). 둘을 보입니다. 셋째(url.json)는 멀쩡한 카드에 아무도 듣지 않는 10399 를 적은 것입니다.

카드 여섯을 검사한다 — 좋은 카드 셋, 망가진 카드 셋

  • missing.json 은 오류 셋, empty.json 은 오류 하나와 경고 하나, url.json 은 오류 하나와 경고 하나. 오류가 있으니 [종료 코드 1] 입니다.

TypeScript — 답이 오면 닿은 것, 본문은 버린다

fetch 는 404·405 에도 예외 없이 응답을 주고, 연결이 안 될 때만 거절(reject)합니다. 그래서 성공·실패 두 갈래가 곧 "닿음·안 닿음" 입니다. 2초 제한은 AbortSignal.timeout 으로 겁니다.

출력은 카드 여섯 모두 파이썬과 글자 하나 다르지 않습니다. 위는 마지막 카드(url.json)입니다.

Go — 형(type)으로 "비었다" 를 가린다

Go 는 카드를 map[string]any 로 풉니다. JSON 문자열은 string, 배열은 []any, 객체는 map[string]any 가 되므로, 형에 따라 "비었다" 를 정합니다. 객체는 비어도 "있음" 이라 capabilities 를 따로 다룰 필요가 없습니다.

세 언어 비교 — 같은 규칙, 다른 "비었다"

검사 규칙은 같고, 갈리는 것은 "없거나 비었다" 와 capabilities: {} 줄입니다.

8장 퀴즈

Q. 어떤 카드의 스킬에 "tags": [] 라고 빈 목록을 적었습니다. 검증기는 이것을 tags 가 아예 없는 카드와 같게 봅니다. 왜 그래도 됩니까?

A. proto3 에서 목록 필드는 빈 목록과 없는 목록이 같은 값이라(빈 것은 없는 것), proto 메시지로 읽으면 둘은 구별되지 않습니다. 둘 다 proto 가 REQUIRED 로 표시한 필드를 채우지 않은 것입니다. 검증기는 둘 다 skills[0].tags: 필수인데 없거나 비었다 로 알립니다(실행 결과의 missing.json). 태그가 없는 스킬은 5장의 고르기에도 걸리지 않습니다.
