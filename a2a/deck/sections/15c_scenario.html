숙소가 거절하면 — 기획 작업도 REJECTED, 까닭은 "숙소: " 를 붙인 동료의 글

1·2번 문장입니다. 파이썬 메시의 ask 화면과 숙소 서버의 기록입니다.

  • 발견까지는 6장과 같고, 견적 알림이 하나도 없이 끝납니다. 알리는 차례의 맨 앞이 숙소라 첫 결과에서 멈춥니다.
  • 두 문장의 까닭이 같습니다 — 숙소 에이전트는 "쉬는 날" 과 "자리가 모자람" 을 가르지 않고 가능한 숙소가 없습니다 하나로 답합니다(SCENARIO §2.1). 기획 에이전트도 더 말할 것이 없습니다.

거절의 와이어 — 숙소의 답은 result.task, 상태 REJECTED 에 글 파트 하나

숙소 탭의 둘째 주고받음(1번 문장의 SendMessage)에서 상태와 글만 골랐습니다.

  • 막는 SendMessage 라 숙소는 끝난 Task 를 돌려줍니다 — §3.2.2 는 막는 호출이 "terminal state … or an interrupted state" 까지 기다린다고 합니다. 거절은 오류(JSON-RPC error)가 아니라 정상 응답 안의 상태입니다(5부).
  • 까닭은 status.message 의 TextPart 입니다. 아티팩트는 없습니다 — 기획 에이전트는 견적을 꺼내기 전에 상태부터 봅니다.

거절이 넘어가는 길 — 동료의 메시지를 옮기지 않고, 글만 꺼내 새 메시지를 짓는다

기획 에이전트는 동료의 Task 를 자기 사용자에게 그대로 넘기지 않습니다. 두 작업은 서로 다른 서버의 다른 작업입니다.

 숙소 작업(숙소 서버)              기획 작업(기획 서버)
 state  REJECTED          ──→  state  REJECTED       같은 상태
 message 의 글            ──→  "숙소: " + 그 글       새 메시지
 message.messageId·taskId  ✗    기획 쪽의 id          옮기지 않음
  • 상태는 같은 REJECTED 로 잇고, 글은 get_message_text·textOf·TextOf 로 꺼내 역할 이름을 앞에 붙입니다(3장의 plan 구역). 동료의 messageId·taskId 는 기획 작업의 이력에 들어가지 않습니다.
  • 사용자는 숙소 작업의 id 를 받지 못합니다. 숙소 작업을 따로 들여다볼 길은 기획 에이전트의 기록뿐입니다 — 이 이야기의 사용자에게는 그것으로 충분하다고 본 설계입니다.

숙소가 거절한 뒤에도 — 식사는 견적을 냈고 교통은 배차까지 확정했다

셋에 동시에 맡기고 셋이 다 끝나길 기다리므로(3장), 숙소의 거절은 나머지 둘을 멈추지 않습니다.

  • 2번 문장(70명)에서 교통은 45인승과 25인승을 한 대씩, 이틀에 2,100,000원으로 확정했습니다(SCENARIO §2.3, 골든의 70명 경우). 숙소가 없으니 쓰지 못할 배차입니다.
  • 기획 에이전트는 이 두 작업을 CancelTask 로 거두지 않습니다. 숙소의 거절을 받은 때에는 교통이 이미 끝나 있었으니 거둘 수도 없었습니다 — 셋을 함께 기다리는 설계의 값입니다. 첫 실패에서 나머지를 거두려면 기다리는 방식부터 바꿔야 합니다(고치지 않았다).

식사가 거절하면 — 숙소 견적까지 알리고 멈춘다, 교통 견적은 알려지지 않는다

3번 문장(30명(채식 40명))입니다.

  • 알림은 숙소 → 식사 → 교통의 차례라, 숙소 견적 한 줄이 먼저 나가고 식사에서 멈춥니다. 교통은 이번에도 끝까지 일했지만(교통 서버의 완료) 사용자는 그 견적을 보지 못합니다.
  • 골든의 다른 식사 거절 — 상한(caps)이 채식 메뉴를 모두 막는 경우 — 은 기획 에이전트로는 일으킬 수 없습니다. 한 문장 풀이에 상한이 없기 때문입니다(1장의 풀이). 그 거절은 식사 에이전트를 바로 부른 10부에서 보았습니다(10부).

예산이 모자라면 — 결재를 묻지 않고 곧바로 REJECTED "정산: 예산을 초과합니다"

4번 문장(예산 4,000,000원)입니다. 견적 셋은 이야기와 같고 합계는 4,842,000원입니다.

  • 합계가 결재 기준(3,000,000원)을 넘는데도 AUTH_REQUIRED 가 오지 않았습니다. 정산은 예산 초과를 결재보다 먼저 봅니다(SCENARIO §2.7 "settle checks over-budget before approval") — 사람에게 묻기 전에 끝나는 실패입니다.
  • 기획 에이전트의 finish 가 정산의 까닭(예산을 초과합니다 (842,000원))에 정산: 을 붙였습니다(5장). 넘친 금액이 까닭 안에 있어, 사용자는 얼마를 줄여야 하는지 압니다.

예산 초과의 와이어 — 토큰은 하나(payment:read), 정산 작업은 REJECTED 로 끝

정산 탭에서 4번 문장의 토큰 요청과 SendMessage 입니다.

  • 결재 토큰(payment:approve)을 받을 일이 없었습니다. 정산의 답은 끝 상태(REJECTED)라 이어 말할 작업도 남지 않습니다.
  • 요청의 숫자는 파이썬 Struct 의 double(4000000.0)입니다(6장). 정산은 정수로 바꿔 계산합니다.

달리는 배차를 남이 취소하기 — 시간이 아니라 "첫 단계를 알렸다" 는 상태를 기다린다

6번입니다. 문장은 이야기 그대로이고, 기획 에이전트가 교통에 맡긴 배차를 다른 클라이언트가 도중에 취소합니다. 취소하는 쪽은 교통 서버에 곧장 묻습니다 — 교통에는 --url 을 주지 않아 카드의 url 이 서버 포트 그대로입니다.

  • cancel_first_step 은 WORKING 작업의 상태 메시지가 배차 요청 접수 가 될 때까지 ListTasks 를 0.05초마다 다시 묻습니다. 묻는 횟수는 매번 다르지만 출력에 나오지 않습니다.
  • 남는 가정은 하나 — 첫 단계를 본 뒤 둘째 단계(2초, --step-ms 2000)가 끝나기 전에 CancelTask 가 닿는다는 것입니다. 11부의 취소(11부)와 같은 수법입니다.
  • 두 흐름의 출력은 섞이지 않게 모았다가, 둘 다 끝난 뒤 정한 차례(취소 → 기획의 스트림)로 찍습니다.

취소의 실행 — 교통은 CANCELED, 기획 작업은 REJECTED "교통: 배차를 취소했습니다"

  • 교통의 막는 SendMessage 는 CANCELED 가 된 Task 를 들고 돌아왔습니다 — §3.2.2 의 "terminal state" 하나입니다. 기획 에이전트는 그 상태 메시지(배차를 취소했습니다, 교통 실행기의 cancel 이 실은 글)를 까닭으로 옮겼습니다.
  • 숙소·식사 견적은 알렸고, 교통 자리에서 멈췄습니다. 정산까지 가지 않으니 정산 서버에는 이 문장의 작업이 없습니다.

남은 결함 — 동료의 CANCELED 가 기획 작업의 REJECTED 가 된다

알림 고리는 COMPLETED 가 아닌 것을 모두 거절로 바꿉니다(실패를 잡는 자리). 이 책이 2장에서 정한 기준(2장)으로 보면 이 경우는 맞지 않습니다.

  • 세 언어가 모두 같은 모양이라 상호운용 문제는 아니고, 우리 기획 에이전트의 상태 고르기 문제입니다. 고치지 않고 기록해 둡니다 — 고친다면 CANCELED 를 따로 받아 FAILED 교통 작업이 도중에 취소되었습니다 처럼 짓는 자리입니다.

결재 반려 — 이 결함은 실제로 있었다: 반려 뒤에도 정산 작업이 AUTH_REQUIRED 로 남았다

5번입니다. 고치기 전의 사본(15/planner_old.py, 2장)으로 이야기를 돌리고 "안 됩니다" 라고 답한 뒤, 정산 에이전트에 남은 작업을 상태별로 셉니다.

기획 작업은 끝났는데 정산 작업은 끝나지 않았다 — 사용자는 REJECTED 를 받았지만, 기획 에이전트가 정산에 맡긴 작업은 결재를 기다리는 채로 남았습니다. 기획 쪽의 기다림(waiting 항목)은 pop 으로 지웠으니, 그 정산 작업을 다시 가리킬 것은 기획 에이전트 어디에도 없습니다.

왜 거둬야 하나 — 결재 대기는 끝 상태가 아니라서, 아무도 닫지 않으면 영원히 열려 있다

AUTH_REQUIRED 는 "interrupted state" 입니다(5부). 정산 에이전트는 같은 작업으로 올 다음 메시지를 기다립니다.

  • 정산 서버 쪽에서는 그 작업이 목록(ListTasks)에 영원히 "결재 대기" 로 남고, Go 정산은 그 작업의 실행 하나가 AwaitReply 에서 기다립니다(12부).
  • §7.6.2 는 AUTH_REQUIRED 를 받은 클라이언트가 할 수 있는 일로 "Send a response message to the Task to negotiate, correct, or reject the authorization request" 를 듭니다. 우리 정산 실행기는 이어 온 메시지를 모두 결재 시도로 읽어(12부의 실행기) "반려" 라는 말을 알아듣지 못합니다.
  • 그래서 어느 서버나 아는 방법, CancelTask(§3.1.5)로 거둡니다. 동료의 말뜻에 기대지 않고 작업의 생애주기로 끝내는 길입니다.

두 작업의 끝 상태 — 기획은 REJECTED, 정산은 CANCELED

한 번의 반려로 두 서버의 작업 둘이 끝납니다. 끝 상태가 다른 것은 끝낸 쪽이 다르기 때문입니다.

작업끝 상태proto 의 설명까닭
정산 작업(정산 서버)TASK_STATE_CANCELED"a task was canceled before completion"그 작업의 클라이언트(기획 에이전트)가 CancelTask 로 멈췄다 — 정산이 판단한 것이 아니다
기획 작업(기획 서버)TASK_STATE_REJECTED"the agent has decided to not perform the task"이 요청(이 금액)에 대한 결재권자의 판단 — 2장의 표에 이미 "결재 반려" 로 적었다(2장)
  • 기획 작업을 CANCELED 로 하지 않은 까닭: 사용자는 CancelTask 를 부르지 않았고 대화 안에서 "안 됩니다" 라고 답했습니다. FAILED 도 아닙니다 — 고칠 것이 기획 에이전트 쪽 환경(명단·연결)이 아니라 요청(금액)이고, 2장의 기준에서 요청에 대한 판단은 REJECTED 입니다.
  • 그래서 기획 작업의 상태와 글은 고치기 전과 같습니다. 바뀐 것은 정산 작업을 거두는 한 걸음뿐입니다.

고친 코드 — 파이썬: withdraw 가 토큰을 받아 CancelTask, 반려를 알리기 전에 부른다

  • 정산의 문지기는 모든 JSON-RPC 요청에 payment:read 를 요구하므로(12부) 취소에도 새 토큰을 받습니다. 기다림에는 토큰을 넣어 두지 않습니다 — 결재가 언제 올지 몰라, 받아 둔 토큰(expires_in 이 있다)이 그때까지 살아 있다고 기댈 수 없습니다.
  • 거두지 못해도(닿지 않음·오류) 반려는 반려입니다. 까닭은 서버 기록에만 남기고 사용자에게는 같은 REJECTED 를 냅니다 — 사용자가 고칠 수 있는 일이 아니라서입니다(2장의 규칙).

TypeScript·Go — 같은 이름, 같은 차례(토큰 → CancelTask → 기록)

  • 부르는 자리는 셋 다 반려 가지의 첫 줄입니다 — TypeScript 는 resume(4장), Go 는 settle 안의 AwaitReply 다음(4장).
  • TS 클라이언트의 메서드는 cancelTask(params, options) 이고 헤더는 serviceParameters 로 답니다(send 와 같다). Go 는 a2aclient.Client.CancelTask 에 토큰을 실은 HTTPClient 를 씁니다.

고친 뒤의 실행 — 같은 반려, 이제 정산에 남은 AUTH_REQUIRED 는 0, CANCELED 1

세 메시의 5번 문장과 그 뒤의 settle_left.py 입니다. 파이썬 메시를 통째로, TS·Go 메시는 끝 줄만 실었습니다.

  • 사용자가 보는 것은 고치기 전과 같습니다(전). 다른 것은 정산 쪽 — AUTH_REQUIRED 0, CANCELED 1 입니다. REJECTED 1 은 4번 문장(예산 초과)의 정산 작업입니다.
  • > 안 됩니다 뒤의 task WORKING 은 TS·Go 기획 에이전트가 이어 말하기의 스트림을 작업 전체로 시작한 줄입니다(5장).

CancelTask 의 와이어 — 새 토큰, params.id 는 정산 작업, 답은 CANCELED 가 된 Task

정산 탭에서 5번 문장의 마지막 두 주고받음(취소용 토큰, CancelTask)입니다.

  • CancelTask 의 결과는 Task 그 자체입니다(result.task 가 아니라 result — §3.1.5 "Updated Task"). 이력에는 기획 에이전트가 보낸 견적 셋과 정산의 결재 요청이 그대로 남아 있습니다.
  • 세 정산 서버 모두 CANCELED 로 답했고, 상태 메시지는 TypeScript 만 달았습니다 — 다음 슬라이드.

시험 ×3 — "반려하면 정산이 CancelTask 를 받는다", 고치기 전에 먼저 써서 셋 다 실패했다

가짜 정산(토큰을 주고, 받은 JSON-RPC 메서드를 적어 두는 작은 HTTP 서버)을 세우고 반려를 보냅니다. TypeScript 판입니다.

  • 고치기 전에는 세 언어 모두 상태(REJECTED)는 맞고, 가짜 정산이 받은 것을 보는 단언에서 실패했습니다 — 가짜 정산에 CancelTask 가 오지 않았습니다(파이썬 [] != [('CancelTask', 'settle-1')], Go 는 첫 정산 요청뿐인 ["SendMessage "]). withdraw 를 넣은 뒤 셋 다 통과합니다.
  • waiting.size 가 0 인지도 봅니다 — 이것은 고치기 전에도 통과했습니다. 파이썬·TS 는 답을 받는 첫 줄에서 기다림을 꺼내 지웠습니다(4장). 남겨진 것은 기획 쪽이 아니라 정산 쪽이었습니다.

Go 의 시험만 서버를 띄운다 — 결재 대기가 실행 안에 있어서

파이썬·TS 는 waiting 에 항목 하나를 넣고 답만 보내면 됩니다. Go 는 기다림이 settle 의 지역 변수와 멈춘 실행이라(4장), 시험도 실행을 거기까지 데려가야 합니다.

  • Go 시험은 이 실행기를 common.Serve 로 포트 11566 에 띄우고, 스트림으로 AUTH_REQUIRED 까지 간 뒤 같은 taskId 로 "안 됩니다" 를 보냅니다 — 답을 멈춘 실행에 넘기는 waiter 가 Serve 안에만 있기 때문입니다(agents/common/park.go).
  • 가짜 정산은 첫 SendMessage 에 AUTH_REQUIRED 로 답하고, 받은 차례를 ["SendMessage ", "CancelTask settle-1"] 로 남깁니다.

7장 퀴즈

Q. 결재 반려를 고치기 전에도 기획 에이전트의 waiting 은 비었습니다. 그런데도 무엇이 남았고, 그것을 어떻게 셌습니까? 고친 뒤 TypeScript 메시에서 정산 작업의 상태 메시지는 무엇이었고, 누가 썼습니까?

A. 정산 서버의 작업이 AUTH_REQUIRED 로 남았습니다 — settle_left.py 가 정산 에이전트에 상태별 ListTasks 를 보내 AUTH_REQUIRED 1 을 셌습니다(전). 고친 뒤에는 AUTH_REQUIRED 0·CANCELED 1 입니다(뒤). TS 정산 작업의 글은 Task cancellation requested by user. 이고, 우리 실행기가 아니라 TS SDK 가 썼습니다 — 실행이 이미 끝나 이벤트 버스가 없었기 때문입니다(비교).
