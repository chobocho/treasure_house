코드는 열넷 — 대부분은 앞 부에서 한 번씩 봤다

§9.5 의 JSON-RPC 표준 다섯과 §5.4 의 A2A 아홉입니다. 처음 본 자리를 적었습니다. 이 장은 같은 탐침으로 세 서버를 한 줄씩 두드려 빈칸을 채우고, 한 표로 모읍니다.

탐침 한 줄 = 서버 · 경우 · HTTP 상태 · 꼴 · code · reason · message

SDK 클라이언트는 오류를 예외로 바꾸며 와이어의 일부를 감춥니다(7부). 그래서 맨손 httpx 로 보내고, 서버·경우 뒤에 답의 다섯 자리(HTTP 상태·꼴·code·reason·message)만 찍습니다.

  • 스트림 메서드의 답이 text/event-stream 이면 첫 data: 줄 하나만 읽습니다 — Go 는 스트림 요청의 오류를 SSE 이벤트에 싣습니다(10부).
  • reason 은 data 배열에서 reason 을 가진 첫 객체(ErrorInfo)의 것, 없으면 - 입니다. 오류가 아니면 result 와 작업 상태를 찍습니다.

명세 다섯 — 완성 숙소 셋, 시험대 셋, 빌려 온 여섯, REST 셋, 그리고 시험

완성 에이전트로 일으킬 수 있는 것은 숙소 에이전트 셋에 보냅니다. 경우의 묶음(std·data·a2a)은 탐침의 인자입니다.

-32700 — 코드는 같고, 글은 파서의 말 그대로, ErrorInfo 는 Go 만

닫히지 않은 JSON({"jsonrpc": "2.0", "id": 1, "method": )을 보냈습니다.

  • §9.5 표의 "Standard Message" 는 Invalid JSON payload 입니다. TS 만 그 글(끝에 마침표)이고, 파이썬은 json 모듈의 글, Go 는 encoding/json 의 글입니다.
  • data 는 Go 만 실었습니다(PARSE_ERROR). §3.3.2 에서 Error Details 는 "(optional)" 이라 셋 다 스펙 안입니다.

-32600 — 파이썬은 셋 다 -32600, TS 는 셋 다 -32602, Go 는 둘만

객체가 아닌 본문([]), "jsonrpc": "1.0", method 없음 — JSON-RPC 2.0 이 "Invalid Request" 로 정한 경우들입니다(2부).

  • TS — v1.0 처리기는 모양이 틀린 요청에 RequestMalformedError 를 던지고, 이것이 -32602 INVALID_PARAMS 가 됩니다(server/express/index.js:1908). 같은 파일의 v0.3 처리기는 같은 자리에서 invalidRequest(-32600)를 씁니다(:2997). 이 SDK 의 v1.0 경로에서 -32600 은 나오지 않습니다.
  • Go — 본문을 요청 구조체로 풀 때의 타입 오류를 모두 ErrInvalidParams 로 옮깁니다(a2asrv/jsonrpc.go:371). 그래서 [] 만 -32602 이고, 글에 Go 의 타입 이름(jsonrpc.ServerRequest)이 나옵니다.
받는 쪽 — "요청이 틀렸다" 를 -32600 과 -32602 로 나눠 다르게 다루지 않습니다. 둘 다 "고쳐서 다시" 이고, 어느 쪽이 올지는 서버의 SDK 가 정합니다.

-32601 — 코드는 셋이 같고, 표준 글은 파이썬만

메서드 표에 없는 이름 NoSuchMethod 입니다.

  • 파이썬의 Method not found 가 §9.5 의 Standard Message 그대로입니다. TS 는 Invalid method.(server/express/index.js:2017), Go 는 소문자 글에 ErrorInfo METHOD_NOT_FOUND 까지 답니다.
  • v0.3 의 메서드 이름(message/send)이 v1.0 서버에서 어떻게 되는지는 14부가 봤습니다.

-32602 — 빠진 id 는 셋이 같고, 수 id 와 큰 pageSize 에서 갈린다

GetTask 에 params: {}, "id": 5, 그리고 ListTasks 에 "pageSize": 1000 입니다.

  • 수 id — 파이썬·Go 는 타입을 따져 -32602, TS 는 따지지 않고 5 를 id 로 찾아 -32001 Task not found: 5 입니다. 맨손 Go 서버가 고치기 전에 같은 자리에서 미끄러졌습니다(6부).
  • pageSize — Go 만 -32600 INVALID_REQUEST 입니다. 11부의 101 과 같은 갈림입니다(11부). 모양은 맞고 값이 틀렸으니 JSON-RPC 의 뜻으로는 -32602 입니다.
  • 파이썬의 Validation failed 는 무엇이 빠졌는지를 data 의 BadRequest 에 적습니다(4부).

-32001·-32002·-32003 — 네 요청, 열두 칸의 코드와 reason 이 같다

없는 작업에 GetTask·CancelTask, 끝난 작업(setup 줄이 만든 COMPLETED)에 CancelTask, 푸시 기능이 없는 카드에 CreateTaskPushNotificationConfig 입니다.

  • 코드·reason 은 5부·3부에서 본 그대로입니다(5부, 5부, 3부). 푸시 설정은 작업이 있어도 기능 검사가 먼저입니다.
  • 글의 버릇도 그대로 — 파이썬은 작업 id 를 붙이지 않고, TS 는 붙이고, Go 는 SDK 안쪽 단계를 겹겹이 적습니다(failed to cancel: cancelation failed: …).

-32004 — 확장 카드·끝난 작업에 이어 말하기·구독, 열두 칸이 같은 코드

확장 카드 기능이 없는 숙소 카드에 GetExtendedAgentCard, 끝난 작업에 SendMessage·SendStreamingMessage·SubscribeToTask 입니다.

  • 확장 카드는 §3.3.4 대로 UnsupportedOperationError(3부), 끝난 작업은 §3.1.1·§3.1.2·§3.1.6 대로입니다(5부, 10부).
  • 꼴이 갈립니다 — Go 는 스트림 요청 둘을 sse(200 text/event-stream 안의 오류 이벤트)로 답했습니다. 뒤 슬라이드에서 모아 봅니다.

-32005 — 4부의 접수 에이전트 셋: 코드는 같고, 막은 자리가 다르다

카드의 입력 모드(text/plain·application/json)에 없는 image/png 파트입니다. 완성 에이전트는 이 검사를 켜지 않아서 4부의 접수 에이전트를 빌렸습니다(16/borrow.run).

  • 파이썬(validate_input_modes=True)과 TS(validateInputModes: true)는 SDK 가 막고, Go 는 우리 실행기가 a2a.ErrUnsupportedContentType 을 돌려줍니다(4부).
  • Go SDK 의 서버 쪽(a2asrv)에는 입력 모드를 보는 코드가 없습니다 — 그 패키지에 InputModes 를 읽는 파일이 하나도 없습니다. 실행기가 하지 않으면 -32005 는 나오지 않습니다.

시험대 에이전트 — 확장 카드를 "준다" 고만 적고, 받은 글로 규칙을 어긴다

남은 세 코드는 완성 에이전트로 일으킬 수 없습니다 — 우리 실행기는 차례를 지키고, 확장 카드 기능을 켠 정산 에이전트는 카드도 둡니다. 그래서 작은 서버를 세 언어로 썼습니다. 카드에는 AgentCapabilities(streaming=True, extended_agent_card=True) 를 적고 처리기에는 확장 카드를 넘기지 않습니다.

  • "차례 위반" — Task 를 싣기 전에 start_work()(WORKING 상태 갱신)부터. 7부의 StatusFirst 와 같은 반칙입니다(7부).
  • "고장" — 실행기가 예외를 던집니다. 그 밖의 글은 그대로 Message 로 돌려줍니다.

TypeScript·Go — 같은 세 갈래, 다른 것은 "고장" 을 알리는 법

Go 에는 던질 예외가 없다 — 실행기는 iter.Seq2[a2a.Event, error] 이므로 "고장" 은 yield(nil, err) 입니다(9부). TS 는 throw, 파이썬은 raise. 세 SDK 가 이것을 와이어에서 어떻게 보이는지가 -32603 슬라이드입니다.

-32006 — 파이썬·Go 는 스펙대로, TS 는 막는 호출 -32603 · 스트림 -32004

"차례 위반" 을 막는 호출(order)과 스트림(order-sse)으로 보냈습니다. §3.3.2 의 InvalidAgentResponseError 는 "An agent returned a response that does not conform to the specification for the current method" 입니다.

  • 파이썬·Go — -32006 INVALID_AGENT_RESPONSE. 7·9부에서 프로세스 안에서 본 차례 검사(7부, 9부)가 와이어에 그대로 나왔습니다. 파이썬은 스트림 요청에도 json 한 덩이 — 첫 이벤트 전에 실패해 스트림을 열지 않았습니다.
  • TS — 막는 호출은 -32603 "Agent execution finished without a result"(server/index.js:3114), 스트림은 -32004 "Received statusUpdate before initial…"(:3481). 서버 번들에 InvalidAgentResponseError 는 정의와 코드 표(:439·:593)에만 있고 그것을 던지는 곳이 없습니다 — TS 서버에서 -32006 은 나오지 않습니다.

-32007 — 기능은 켜고 카드는 없다: 세 서버 모두 스펙대로

시험대의 카드는 extendedAgentCard: true 인데 처리기에 확장 카드가 없습니다. §3.3.4: "If the agent declares support but has not configured an extended card, it MUST return ExtendedAgentCardNotConfiguredError".

  • 검사하는 곳 — 파이썬 default_request_handler_v2.py:679, TS server/index.js:2738, Go a2asrv/handler.go:485. 셋 다 먼저 기능을 보고(없으면 -32004), 그다음 카드를 봅니다.
  • 3부에서 본 -32007 은 기능 검사를 끈 Go 서버가 기능 없는 카드로 낸 것이었습니다(3부) — 그 카드라면 §3.3.4 의 답은 -32004 입니다. 기능을 켠 카드로 낸 -32007 은 여기가 처음입니다.

-32008 — 14부의 예산 확장을 required 로 띄우고 머리글 없이 보낸다

14부의 숙소 에이전트를 --required 로 빌렸습니다(16/borrow.run). 요청은 보통 견적 요청 그대로, A2A-Extensions 머리글이 없습니다.

  • 파이썬의 글 "… 필요" 는 SDK 가 아니라 14부의 겉층이 던진 것입니다 — 파이썬 SDK 1.2.2 는 required 확장을 검사하지 못합니다(14부). TS·Go 는 SDK 가 막습니다.
  • Go 는 WithCapabilityChecks 를 켜면 이 검사를 모든 메서드에 겁니다 — 머리글 없는 GetTask 도 -32008 입니다(14부).

-32009 — 파이썬·TS 는 9.9 도 빈 머리글도 거절, Go 는 둘 다 처리했다

없는 작업을 A2A-Version: 9.9 로, 그리고 머리글 없이 물었습니다. 머리글이 비면 0.3 으로 봅니다(§3.6.1).

  • 파이썬·TS 의 글에 '0.3' 이 보입니다 — 빈 머리글을 스펙대로 0.3 으로 읽고, 지원하지 않는 판으로 거절했습니다.
  • Go 는 판을 보지 않고 GetTask 를 처리해 -32001 입니다. a2a.ErrVersionNotSupported 는 정의(a2a/errors.go:74)와 코드 표(internal/jsonrpc/jsonrpc.go:83)에만 있고, 서버(a2asrv)에는 그것을 돌려주는 코드가 없습니다. §3.6.2 의 MUST 를 지키려면 우리가 앞에 검사를 세워야 합니다(9부, 14부).

-32603 — 실행기가 예외를 내면 파이썬·Go 는 오류, TS 는 FAILED 작업

"고장" 을 막는 호출(crash)과 스트림(crash-sse)으로 보냈습니다.

  • 파이썬·Go 의 message 는 실행기의 예외 글 그대로("시험대가 고장 났습니다")입니다. 실행기 안의 문장이 그대로 클라이언트에게 갑니다 — 진짜 에이전트라면 파일 경로나 내부 주소가 섞일 수 있는 자리입니다(15부에서 기획 에이전트가 그랬습니다).
  • TS 는 오류 대신 TASK_STATE_FAILED 작업을 돌려줍니다 — 상태 메시지 "Agent execution error: …"(server/index.js:2931, 5부). TS 에서 -32603 은 실행기가 아무것도 싣지 않고 끝났을 때 나옵니다(앞의 order, 8부).

틀린 DataPart — 파이썬은 -32603 에 int() 의 글을, TS 는 "NaN원" 견적을 냈다

탐침의 data 경우는 숙소 에이전트에 {"headcount": "서른"} 을 보냅니다. 고치기 전의 손질 함수로는 세 언어의 답이 셋으로 갈립니다 — 파이썬 -32603, TS COMPLETED, Go REJECTED. 캡처는 고치기 전 판(16/ints_old.{py,ts})에 같은 시험을 돌린 것입니다.

  • 파이썬 — as_ints 의 int("서른") 이 ValueError 를 내고, SDK 는 실행기의 예외를 -32603 으로 옮기며 그 글을 message 에 싣습니다(앞 슬라이드와 같은 길).
  • TS — Number("서른") 은 NaN, Math.trunc(NaN) 도 NaN 이고, NaN < 1 은 거짓이라 인원 검사를 지나 "NaN원" 견적이 나옵니다. 둘째 시험의 null 은 보고기가 NaN 을 JSON 으로 적은 것입니다.
  • Go — common.Int 는 처음부터 수가 아니면 0 이라, 업무 규칙이 "인원과 박 수는 1 이상이어야 합니다" 로 거절했습니다.
우리 결함 — 같은 요청에 세 언어가 세 답을 냈고, 그중 둘이 틀렸습니다. 하나는 내부 글을 흘렸고, 하나는 말이 안 되는 견적을 "완료" 했습니다. 3×3 매트릭스(1장)는 올바른 요청만 보내서 이것을 보지 못했습니다.

고친 것 — 수로 읽을 수 없으면 0, 거절은 업무 규칙이 한다(Go 와 같은 약속)

  • Go 의 common.Int(agents/common/common.go:122)는 고치지 않았습니다. float64·int 는 정수로, 문자열은 strconv.Atoi 로 읽고(읽지 못하면 0), 그 밖의 꼴은 0 입니다.
  • 시험은 다음 두 슬라이드에 있습니다. 세 언어가 같은 세 줄을 시험하고, 고치기 전 판을 남겨 RED 를 캡처에 둡니다.

시험 셋 — "수는 정수로", "수가 아니면 0", "숙소 규칙이 거절한다"

파이썬·TS 의 같은 세 시험입니다. Go 는 같은 세 줄을 16/intstest/ints_test.go 에 두었습니다(common.Int 와 workshop.ChooseLodging).

견적이 나오면 총액을 적는다 — TS 의 셋째 시험은 견적 전체 대신 "NaN원 견적" 같은 한 줄을 견줍니다. 실패 글이 짧아져 RED 캡처에서 NaN 이 그대로 보입니다.

고치기 전 판을 남겨 둔다 — 같은 시험을 두 판에 돌려 RED 와 GREEN 을 한 캡처에

고친 뒤에는 RED 를 다시 볼 수 없으니, 고치기 전 함수를 옮겨 두고 같은 시험이 그것을 부르게 했습니다(15부의 planner_old 와 같은 방법).

RED → GREEN — 고치기 전 판은 둘씩 실패, 고친 판과 Go 는 셋 다 통과

공용 모듈의 수정 — agents/common.{py,ts} 는 다섯 에이전트가 함께 씁니다. 그것을 쓰는 캡처 가운데 바뀐 것은 이 장의 것뿐입니다. TS 파일은 주석 한 줄을 고쳐 써 줄 수를 지켰습니다 — 다른 부가 줄 번호로 자른 곳이 밀리지 않습니다.

HTTP+JSON 문 — 상태는 §5.4 그대로, 갈린 것은 Go 의 판 검사 하나

13부의 REST 숙소 서버 셋(13/rest_*)에 같은 경우를 HTTP+JSON 으로 보냈습니다(16/rest_errs.run). 바인딩 자체는 13부의 몫이고, 여기서는 상태만 봅니다. 줄 = 서버 · 경우 · HTTP 상태 · error.status · reason · message.

  • 404 NOT_FOUND(작업 없음), 400 FAILED_PRECONDITION(취소 불가·푸시·미지원·판) — §5.4 의 HTTP 열과 gRPC 이름 그대로이고 셋이 같습니다.
  • pageSize 는 400 INVALID_ARGUMENT 로 같지만 reason 은 JSON-RPC 쪽 버릇을 따라 Go 만 INVALID_REQUEST 입니다. 판 9.9 는 Go 가 처리해 404 입니다.

스트림 요청의 오류 — 파이썬·TS 는 JSON 한 덩이, Go 는 200 SSE 안의 이벤트

이 장의 스트림 메서드(SendStreamingMessage·SubscribeToTask) 줄만 모았습니다.

  • §9.4.2 는 스트림의 답을 "HTTP 200 with Content-Type: text/event-stream" 과 result 이벤트로만 보여 주고, 오류의 꼴은 적지 않았습니다. REST 쪽의 같은 빈자리를 13부에서 봤습니다.
  • 그래서 같은 오류가 Go 에서는 "성공한 HTTP 응답 속의 오류 이벤트" 입니다. TS 의 crash-sse 는 오류가 아니라 FAILED 작업 이벤트입니다.
받는 쪽이 견딜 것 — 스트림을 청했어도 Content-Type 을 먼저 봅니다. application/json 이면 오류 한 덩이, text/event-stream 이면 첫 이벤트가 error 일 수 있습니다(2장).

3장 정리 — 열네 코드, 세 서버, 빈칸은 둘

  • A2A 아홉 코드는 스물일곱 칸 중 스물다섯에서 스펙의 코드가 나왔습니다. 빈 둘은 TS 의 -32006, Go 의 -32009 입니다. HTTP+JSON 의 상태는 판 9.9 를 Go 가 처리해 404 가 된 칸 하나를 빼면 §5.4 그대로였습니다.
  • JSON-RPC 표준 다섯은 덜 고릅니다 — 아홉 경우 중 셋만 세 서버의 코드가 같았습니다. 글(message)과 ErrorInfo 의 유무는 거의 모든 줄에서 갈립니다.
  • 틀린 DataPart 하나가 우리 결함을 드러냈습니다 — 파이썬 -32603, TS NaN 견적. 정수 손질을 Go 와 같은 약속(수가 아니면 0)으로 고쳐 세 언어가 REJECTED 로 맞았습니다.

3장 퀴즈

Q. "jsonrpc": "1.0" 인 요청을 TS 서버에 보내면 어떤 코드가 옵니까? 그리고 Go 서버에 A2A-Version: 9.9 머리글로 없는 작업을 물으면 무엇이 옵니까?

A. TS 는 -32602(reason INVALID_PARAMS, "Invalid JSON-RPC Request.")입니다 — v1.0 처리기가 모양 오류를 RequestMalformedError 로 던지기 때문입니다(-32600). Go 는 판을 읽지 않으므로 요청을 그대로 처리해 -32001 TASK_NOT_FOUND 를 돌려줍니다(-32009).

적합성 시험 — 공식 TCK 를 세 서버에, 그리고 TCK 가 보지 않는 것

설치한 TCK — 2026-09-01 의 main, 그 안의 스펙 사본은 v1.0.0 가지

이 기계에서 GitHub 에 닿아 git clone --depth 1 로 받고, 저장소 밖(scratch/tck, 커밋하지 않는다)에 따로 만든 venv 에 pip install -e 로 설치했습니다. SDK 의 venv(.venv)는 건드리지 않았습니다.

  • TCK 는 스펙 파일을 사본으로 싣고 다니며, 그 출처를 specification/version.json 에 적어 둡니다 — A2A 저장소의 v1.0.0 가지, 커밋 1736957….
  • 이 책의 스펙은 v1.0.1 태그입니다(0부). 둘의 차이가 결과에 드러나는지는 갈래 ②에서 봅니다.

명세 — 13부의 세 문 서버에 TCK 한 판, 보고서는 우리 요약기로

서버는 13부 4장의 "한 서버 세 바인딩" 숙소 에이전트입니다(13부). 카드에 JSONRPC·HTTP+JSON·GRPC 를 모두 적었으니 TCK 가 세 바인딩을 다 시험합니다. TS·Go 명세(16/tck_ts.run·tck_go.run)는 서버 줄만 다릅니다.

왜 플러그인이 필요한가 — TCK 는 id 끝에 실행마다 다른 여덟 자리(uuid4 의 앞부분)를 붙이고, 세 문 서버는 받은 경로를 찍습니다. 그 여덟 자리만 고정했습니다(시험의 내용은 같습니다). 요약기 16/tck_sum.py 는 보고서 둘에서 판정 × 수준, 시험 수, 건너뜀 사유, FAIL 목록을 뽑습니다.

파이썬 서버 — MUST 실패 넷, 그중 둘은 대본·둘은 스펙 판

16/tck_py.run 의 요약입니다. 위는 129개 요구사항의 판정 × 수준, 아래는 FAIL 인 요구사항과 실패한 시험의 바인딩입니다.

  • NOT TESTED 서른여섯은 판정이 나지 않은 요구사항입니다 — 시험이 없거나 앞 단계에서 멈춘 것으로, TCK 가 시험하지 않는 것에서 둘로 나눕니다. SKIPPED 열넷은 카드에 없는 기능(푸시·확장 카드)과 대본 때문입니다.
  • STREAM-SUB-002 는 파이썬에서 판정이 나지 않았습니다 — 되묻는 작업에 붙은 구독이 10초 안에 닫히지 않아 TCK 가 건너뛰었습니다(SubscribeToTask timed out, 10부에서 본 "열린 채").

TypeScript 서버 — MUST 실패 일곱, 넷이 스펙 판(Content-Type·gRPC·415)

  • 카드 캐시는 셋 가운데 TS 만 Cache-Control·ETag 를 모두 달아(3부) CARD-CACHE-001·002 를 지났습니다. Last-Modified(MAY)는 셋 다 없습니다.
  • HTTP+JSON 의 Content-Type 두 줄(SVC-001·ERR-001)과 STATUS-001(415 를 기대)이 이 서버에서만 셋입니다 — 이유는 갈래 ②.

Go 서버 — MUST 실패 열셋, 판 검사·빈 목록·SSE 오류가 SDK 쪽

  • VER-SERVER-002·JSONRPC-SSE-002·HTTP_JSON-STATUS-001 은 한 가지 — 판을 읽지 않는다(3장). CORE-LIST 다섯도 한 가지 — 빈 목록이 null(갈래 ③).
  • CORE-HIST-003(SHOULD)은 SendMessage 의 historyLength: 0 에 이력 셋을 돌려준 것, STREAM-SUB-004 는 없는 작업의 구독이 200 SSE 로 "성공" 한 것입니다(3장).

갈래 ① 대본 — 우리 숙소 에이전트는 "tck-complete-task" 에도 되묻는다

TCK 는 messageId 의 접두사로 SUT 의 행동을 고르지만(공식 TCK), 우리 실행기는 messageId 를 보지 않고 날짜·박·인원을 찾습니다. TCK 의 글("TCK prerequisite task creation" 따위)에는 그것이 없으니 늘 INPUT_REQUIRED 로 되묻습니다. TS 서버 판의 줄입니다.

  • TCK 는 완료된 작업을 전제로 하는 시험 서른 개를 "Expected task state 'TASK_STATE_COMPLETED' but got 'TASK_STATE_INPUT_REQUIRED'" 로 건너뛰었습니다(세 서버 모두).
  • DM-ART-001 은 tck-artifact-* 에 아티팩트를, DM-MSG-001 은 tck-message-response 에 Message 를 기대합니다(scenarios/core_operations.feature:34~:61).
  • STREAM-SUB-002 는 되묻는 작업에 구독한 뒤 "Complete" 를 보냅니다(tests/compatibility/core_operations/test_task_lifecycle.py:389). 우리 에이전트는 "Complete" 에도 또 되물어 작업이 끝나지 않고, TS·Go 서버의 구독은 종료 상태 없이 닫혔습니다(TCK 의 글).
SDK 의 결함이 아니다 — 이 갈래의 줄은 대본을 아는 SUT 로 돌려야 뜻이 있습니다. 대본을 실행기에 넣으면 업무 규칙과 시험용 분기가 섞이므로 시나리오 에이전트에는 넣지 않았습니다.

갈래 ② 스펙 판 — TCK 의 사본(v1.0.0)과 v1.0.1 은 오류 표 여섯 줄과 Content-Type 이 다르다

16/tck_spec.run 의 둘째 명령입니다. 위가 TCK 의 사본, 아래가 이 책의 v1.0.1 입니다(§5.4 의 여섯 줄과 Content-Type 을 정한 두 줄, 줄 번호는 §9.1·§11.1).

  • v1.0.1 은 gRPC 이름 셋(UNIMPLEMENTED → FAILED_PRECONDITION)과 HTTP 상태 셋(409·415·502 → 400·400·500), REST 의 Content-Type(application/json → application/a2a+json SHOULD)을 바꿨습니다. 세 SDK 는 모두 v1.0.1 쪽을 따랐고, TCK 는 사본으로 채점해 GRPC-ERR-002·HTTP_JSON-SVC-001·ERR-001·STATUS-001 을 FAIL 로 적었습니다.
  • Go 가 Content-Type 두 줄을 지난 것은 그 REST 문이 늘 application/json 이기 때문입니다(13부) — v1.0.1 의 SHOULD 와는 어긋나는 쪽입니다.
판정을 옮기기 전에 판을 본다 — TCK 의 FAIL 을 그대로 "비호환" 으로 적으면 스펙을 따른 SDK 를 탓하게 됩니다. 요구사항 id 옆의 §가 어느 판의 문장인지부터 맞춥니다.

갈래 ③ SDK — TCK 가 잡은 셋을 맨손으로 다시: 캐시 머리글, 빈 목록, historyLength

완성 숙소 에이전트 셋에 카드 GET, 결과가 없는 ListTasks, configuration.historyLength: 0 을 단 SendMessage 를 보냈습니다(16/tck_why.run).

  • 카드 캐시(§8.6.1, SHOULD) — Cache-Control 은 TS 만, ETag 은 파이썬·TS. 3부에서 본 그대로입니다(3부).
  • 빈 목록 — Go 만 "tasks": null. proto 는 repeated Task tasks = 1 [(google.api.field_behavior) = REQUIRED] 이고, ProtoJSON 에서 repeated 필드는 배열이지 null 이 아닙니다. 받는 쪽은 null 도 빈 목록으로 읽어야 합니다.
  • historyLength 0(§3.2.4) — 파이썬·TS 는 이력 없이, Go 는 이력 하나를 실어 답했습니다(TCK 의 작업은 이력이 셋이었습니다).

4장 정리 — TCK 는 돌았고, FAIL 은 대본·스펙 판·SDK 셋으로 갈렸다

  • 공식 TCK(2026-09-01 의 main)는 이 기계에 설치되어 세 서버의 세 바인딩을 모두 시험했습니다. 다만 그 안의 스펙 사본은 v1.0.0 가지입니다.
  • FAIL 인 요구사항 열아홉 가운데 대본(우리 에이전트는 TCK 의 접두사를 모른다)과 스펙 판(v1.0.0 의 오류 표·Content-Type)을 빼면, 남는 것은 SDK 의 어긋남입니다 — Go 의 판 검사·빈 목록 null·SendMessage 의 historyLength, 파이썬·Go 의 gRPC 판 검사, 카드 캐시 머리글.
  • 우리 에이전트의 결함은 TCK 에서 나오지 않았습니다. 3장의 틀린 DataPart 처럼 업무 데이터의 결함은 TCK 가 보내지 않는 요청에서만 드러납니다.
  • TCK 에 시험이 없는 서명·인증·판·바인딩 동등성은 앞 부의 캡처로 점검표를 만들었습니다.

4장 퀴즈

Q. TCK 는 세 서버 모두에서 GRPC-ERR-002 를 FAIL 로 적었습니다. 푸시 기능이 없는 서버에 푸시 설정을 만들면 세 서버는 gRPC 로 무엇을 답했고, 그것은 왜 FAIL 이 됐습니까? 이 FAIL 은 SDK 의 결함입니까?

A. 셋 다 FAILED_PRECONDITION 입니다(파이썬·TS·Go 의 오류 글). v1.0.1 의 §5.4 가 정한 그대로입니다. TCK 는 제가 싣고 다니는 v1.0.0 가지의 사본으로 채점하는데, 그 표는 UNIMPLEMENTED 였습니다(갈래 ②). 그러니 SDK 의 결함이 아니라 스펙 판의 차이입니다. 다만 같은 요구사항의 둘째 줄 — 파이썬·Go 의 gRPC 가 판을 검사하지 않는 것 — 은 SDK 쪽입니다.
