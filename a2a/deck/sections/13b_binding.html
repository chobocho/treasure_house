gRPC 바인딩의 약속 — proto 그대로, 서비스 매개변수는 메타데이터, 오류는 status + ErrorInfo (§10)

gRPC 바인딩(§10)은 HTTP+JSON 보다도 짧습니다. 메시지와 메서드는 규범인 proto 가 모두 정해 두었기 때문입니다.

자리스펙의 말세기
§10.1"gRPC over HTTP/2 with TLS", 정의는 specification/a2a.proto, protobuf 3, 서비스 A2AService—
§10.2서비스 매개변수(A2A-Version·A2A-Extensions)는 gRPC 메타데이터로. 키는 소문자로 바뀐다MUST
§10.2서버는 메타데이터에서 꺼내 처리한다 / A2A-Version 같은 필수 값을 검사한다MUST / SHOULD
§10.6오류는 gRPC status(code·message·details). A2A 오류는 details 에 google.rpc.ErrorInfo(reason·domain: "a2a-protocol.org")MUST
§10.7스트림은 서버 스트리밍 rpc, 메시지 하나에 StreamResponse 하나—
TLS 는 운영의 몫 — §10.1 과 §7.1 은 gRPC 에도 TLS 를 요구합니다. 이 장의 실험은 모두 루프백의 평문(insecure) 채널입니다. 12부에서 HTTPS 를 따로 다룬 것과 같은 선택입니다(12부 1장).

서비스는 rpc 열하나 — 이름은 JSON-RPC 메서드와 같고, 둘은 서버 스트리밍이다

§10.3·§10.4 의 표는 스펙 원문에서 proto 를 읽어 만드는 자리입니다({{ proto_service_to_table("A2AService") }}). 그래서 우리도 SDK 에 든 컴파일된 proto 에서 직접 읽었습니다(1장의 http_rules.py 와 같은 방법).

  • 요청·응답 타입이 곧 JSON-RPC 의 params·result 이고 REST 의 본문입니다. 바인딩이 바꾸는 것은 그것을 싣는 방법뿐입니다.
  • gRPC 만의 타입은 TaskPushNotificationConfig(§10.5.1)와 DeleteTaskPushNotificationConfig 의 Empty 입니다. 다른 두 바인딩도 같은 proto 를 쓰므로 실제로는 셋이 같은 메시지를 씁니다.

설치한 것 — 파이썬은 extra 로 이미 있었고, TS 와 Go 는 이 장에서 더했다

gRPC 는 세 SDK 모두 선택 기능입니다. 파이썬은 처음부터 a2a-sdk[grpc] extra(선택 설치 묶음)로 설치했고, TS·Go 는 gRPC 라이브러리를 이 장에서 들였습니다(설치본에 맞춘 정확한 판).

파이썬 서버 — GrpcHandler(handler) 를 grpc.aio 서버에 단다

13/grpc_agent.py 는 2장의 rest_agent.py 처럼 완성 숙소·식사 에이전트의 카드와 실행기를 가져옵니다. 다른 점은 문이 둘이라는 것 — gRPC 포트와, 카드를 내주는 HTTP 포트입니다.

  • GrpcHandler 는 생성 코드의 A2AServiceServicer 를 상속한 번역기입니다. 요청 처리기(DefaultRequestHandler)는 JSON-RPC·REST 판과 같습니다.
  • 카드의 gRPC 주소는 127.0.0.1:포트 — URL 이 아니라 gRPC 의 대상(target) 꼴입니다. 스펙의 카드 예는 https://… 꼴인데, 그 차이는 5장에서 재 봅니다.

TypeScript 서버 — grpcService({requestHandler, userBuilder}) 를 grpc-js 서버에

13/grpc_common.ts 는 완성 에이전트의 serve 를 gRPC 판으로 바꾼 것입니다(빌린 방법은 뒤에서 봅니다).

GRPC 문 없는 카드 — 카드에 GRPC 문이 없으면 모든 호출이 거절됩니다. TS 의 gRPC 처리기는 요청마다 a2a-version 메타데이터를 카드의 GRPC 인터페이스들이 적은 protocolVersion 과 견줍니다(validateVersion(…, "GRPC"), server/grpc/index.js:952). JSON-RPC 문만 적은 카드로 gRPC 서버를 띄우면 지원 판이 빈 집합이 되어 무엇이든 VERSION_NOT_SUPPORTED 입니다(소스로 읽은 것).

Go 서버 — a2agrpc.NewHandler(h).RegisterWith(server)

13/grpcmount 는 2장의 restmount 의 gRPC 판입니다. 요청 처리기 h 를 만드는 부분은 그대로이고, 표준 grpc.Server 에 등록합니다.

Go 는 grpc-go 를 그대로 쓴다 — a2agrpc 의 Handler 는 생성 코드의 A2AServiceServer 를 구현하고(a2agrpc/v1/handler.go:35), 서버 생성·포트·가로채기는 모두 grpc-go 의 것입니다. 4장의 기록용 가로채기도 grpc-go 의 옵션 하나로 답니다.

완성 에이전트를 빌린 방법 — 2장의 해석 훅·같은 패키지를 gRPC 에도

2장과 같은 두 수법입니다. TS 는 바꿔 끼울 모듈 이름을 인자로 받도록 훅을 일반화했고(4장의 세 문 판도 이것으로 띄웁니다), Go 는 패키지 변수로 플래그를 더 등록합니다.

에이전트가 모르는 옵션 — TS 에이전트의 parseCli 는 모르는 옵션을 거절하므로, grpc_common.ts 가 모듈을 읽히는 순간 --grpc-port 를 process.argv 에서 떼어 냅니다(에이전트 본문보다 먼저 돕니다). Go 는 grpcmount 의 패키지 변수가 init() 보다 먼저 플래그를 등록해 ParseArgs 가 함께 읽습니다.

gRPC 를 보는 창 — HTTP/1.1 탭 대신 gRPC 로 받아 gRPC 로 넘기는 탭

지금까지의 와이어 탭(tools/wiretap.py)은 HTTP/1.1 만 읽어서 HTTP/2 위의 gRPC 를 넘기지 못합니다. 그래서 13/grpc_tap.py 를 따로 두었습니다 — 메서드를 가리지 않고 받아(GenericRpcHandler) 바이트 그대로 서버에 넘기고, 오가는 것을 찍습니다.

  • 메시지는 proto 이진이라, 탭이 서비스 정의에서 요청·응답 타입을 찾아 풀고 JSON 으로 찍습니다. 와이어의 글자를 그대로 보여 주는 HTTP 탭과 달리 탭이 해석한 모습입니다.
  • 보이는 메타데이터는 a2a-version·a2a-extensions·authorization·user-agent 넷으로 줄였고, 응답의 머리글·꼬리 메타데이터는 모두 찍습니다(grpc-js 의 date 는 매번 달라 뺐습니다). 꼬리의 grpc-status-details-bin 은 google.rpc.Status 로 풀어 찍습니다.

실험 — 세 gRPC 서버에 SDK 클라이언트 없이 같은 호출 아홉 개

세 언어의 gRPC 숙소 에이전트 앞에 탭을 하나씩 두고, 13/grpc_raw.py 가 생성 코드의 스텁(A2AServiceStub)으로 부릅니다. 2장의 맨손 요청 여덟과 짝을 맞췄습니다.

바이트로 보내는 둘 — "깨진 메시지" 와 "없는 메서드" 는 직렬화 없이 바이트를 그대로 싣는 ch.unary_unary(경로) 로 보냅니다. 스텁으로는 깨진 메시지를 만들 수 없기 때문입니다.

아홉 호출의 요약 — A2A 오류 넷은 셋이 같고, 판·깨진 메시지에서 갈린다

  • 같은 것 — 보내기·읽기, 끝난 작업 취소 FAILED_PRECONDITION + TASK_NOT_CANCELABLE, 없는 작업 NOT_FOUND + TASK_NOT_FOUND(§5.4 의 표 그대로), 없는 메서드 UNIMPLEMENTED, tenant 필드는 셋 다 받습니다.
  • 다른 것 — a2a-version 이 없거나 9.9 일 때 TS 만 VERSION_NOT_SUPPORTED(메타데이터), 깨진 메시지는 파이썬 UNKNOWN, TS·Go INTERNAL.
REST 와 견주면 — 2장의 여덟 요청은 앞의 다섯만 같았습니다(2장 요약). gRPC 에서는 없는 경로에 해당하는 "없는 메서드" 와 tenant 가 셋이 같아졌습니다. 없는 메서드에는 SDK 가 아니라 gRPC 라이브러리가 답하고, tenant 는 경로가 아니라 요청 메시지의 필드이기 때문입니다.

보내기 — 메서드는 경로 /lf.a2a.v1.A2AService/SendMessage, 몸통은 SendMessageRequest 이진

파이썬 서버 앞 탭이 본 첫 호출입니다. 메서드는 HTTP/2 의 경로(:path)가, A2A-Version 은 소문자 메타데이터 a2a-version 이 실어 갑니다(§10.2).

  • 요청 몸통은 1장의 REST 본문과 같은 SendMessageRequest, 응답은 {"task": …} 인 SendMessageResponse 입니다. 봉투(jsonrpc·id)도 HTTP 상태 줄도 없고, 성공은 꼬리의 status OK 가 알립니다.
  • DataPart 의 30.0 은 탭(파이썬)이 JSON 으로 풀 때의 모양입니다. proto 의 google.protobuf.Value 는 숫자를 double 하나로만 담으므로, gRPC 에서는 세 언어 모두 같은 8바이트 double 이 오갑니다. JSON 바인딩에서 본 30·30.0 의 갈림(4부)이 이 바인딩에는 없습니다.

오류 — status NOT_FOUND, 그리고 꼬리의 grpc-status-details-bin 안에 ErrorInfo

없는 작업을 물었습니다. gRPC 의 오류는 응답 메시지가 아니라 꼬리 메타데이터(trailer)에 옵니다 — 상태 코드와 글(grpc-status·grpc-message), 그리고 google.rpc.Status 를 통째로 이진으로 담은 grpc-status-details-bin.

  • code: 5 가 NOT_FOUND 이고, details 의 google.rpc.ErrorInfo 가 reason: TASK_NOT_FOUND·domain: a2a-protocol.org 입니다 — §10.6 의 MUST 와 §5.4 의 표 그대로이고, REST 의 details(2장)와 같은 메시지입니다.
  • gRPC 라이브러리는 상태 코드와 글만 읽습니다. details 를 꺼내 A2A 오류로 되돌리는 것은 SDK 클라이언트의 몫입니다(파이썬 status_from_call, utils/grpc_status.py:46).

메타데이터 — a2a-version 이 없거나 틀리면 TS 만 거절한다

§10.2 는 서비스 매개변수를 메타데이터에서 꺼내라고(MUST), A2A-Version 을 검사하라고(SHOULD) 합니다. 맨손 호출의 "A2A-Version 없음"·"A2A-Version 9.9" 가 그것을 시험했습니다(요약).

  • TS 는 빈 값을 '0.3' 으로 읽고(§3.6.1 의 "0.3 will be assumed for empty header") 카드의 GRPC 인터페이스 판(1.0)과 맞지 않아 FAILED_PRECONDITION + VERSION_NOT_SUPPORTED 로 답했습니다. 9.9 도 같습니다.
  • 파이썬·Go 는 둘 다 OK 였습니다. 파이썬 SDK 는 JSON-RPC·REST 처리에는 @validate_version 을 달았지만(server/routes/rest_dispatcher.py:177 등) GrpcHandler 에는 없고, Go SDK 에는 ErrVersionNotSupported 를 만드는 서버 코드가 없습니다(대응표에만 있습니다). §3.6.2 는 지원하지 않는 판에 VersionNotSupportedError 를 MUST 로 둡니다. 버전 협상 자체는 14부의 몫입니다.
켜진 확장은 어디로 돌아오나 — 서버가 실제로 쓴 확장(A2A-Extensions)을 알리는 자리도 SDK 마다 다릅니다(소스): TS 는 머리글 메타데이터(buildMetadata → call.sendMetadata, server/grpc/index.js:955), Go 는 꼬리 메타데이터(toTrailer → grpc.SetTrailer, a2agrpc/v1/handler.go:313), 파이썬 GrpcHandler 는 돌려보내지 않습니다. 이 장의 에이전트는 확장이 없어 와이어에는 나타나지 않습니다.

서버 스트리밍 — SSE 대신 rpc 하나가 StreamResponse 를 여러 개 돌려준다

완성 식사 에이전트 셋을 gRPC 로 띄우고 SendStreamingMessage 를 보냈습니다(13/grpc_stream.py). 받은 메시지마다 어떤 이벤트인지 한 줄씩 찍습니다.

열 개의 이벤트가 같은 차례로 — 세 서버 모두 task 하나, 상태 갱신 넷, 아티팩트 갱신 다섯(식단표 조각 셋·파일·견적)이 같은 차례로 왔습니다(캡처의 터미널 7 세 묶음). 10부의 SSE 와 같은 이벤트이고(10부), 다른 것은 SSE 의 data: 줄 대신 gRPC 메시지 하나가 하나를 싣는다는 것뿐입니다.

스트림의 메시지 — oneof payload 의 이름 하나가 이벤트의 종류다

  • StreamResponse 의 payload 는 task·message·statusUpdate·artifactUpdate 가운데 하나입니다(§10.7). JSON 바인딩은 이것을 JSON 키로, gRPC 는 proto 필드 번호로 가릅니다.
  • 스트림의 끝은 마지막 메시지가 아니라 꼬리의 status OK 입니다. SSE 처럼 연결을 끊어서 알리지 않습니다.

스트림 속 오류 — 메시지 0개 + status NOT_FOUND, 셋이 같다

없는 작업에 SubscribeToTask 를 걸었습니다. 2장에서 REST 의 같은 오류는 Go 서버만 200 SSE 안의 {"error"} 로 보냈습니다(2장).

  • 세 서버 모두 메시지를 하나도 보내지 않고 NOT_FOUND + TASK_NOT_FOUND 로 닫았습니다(터미널 7 의 "잇기" 줄). gRPC 의 서버 스트리밍은 스트림이 시작된 뒤에도 끝의 status 로 오류를 말할 수 있습니다. 그래서 "이미 200 을 보냈으니 본문에 오류를 싣는다" 같은 고민이 생기지 않습니다.
  • Go 의 글 no active execution 은 SDK 가 "실행 중인 작업이 없다" 로 판단했다는 뜻입니다. reason 은 셋 다 TASK_NOT_FOUND 입니다.

파이썬 클라이언트 — GRPC 를 알리고, 채널을 여는 함수도 준다

이제 SDK 클라이언트입니다. 세 클라이언트는 2장과 같은 세 가지를 합니다 — 막는 SendMessage, 없는 작업 GetTask, 없는 작업에 잇는 스트림.

  • grpc_channel_factory 가 없으면 전송을 만들 때 ValueError('grpc_channel_factory is required when using gRPC') 입니다(client/transports/grpc.py:132). 카드의 주소 문자열을 그대로 이 함수에 넘기므로, TLS 를 쓸지·어떤 자격 증명을 쓸지는 이 함수가 정합니다.
  • 오류는 꼬리의 ErrorInfo reason 으로 SDK 예외(TaskNotFoundError)를 고릅니다(_map_grpc_error, :57).

TypeScript 클라이언트 — 기본 팩토리에 GrpcTransportFactory 를 더한다

기본으로는 모른다 — 기본 전송은 JSON-RPC·REST 둘입니다(3부). gRPC 팩토리는 @grpc/grpc-js 를 끌어오므로 따로 들여와 ClientFactoryOptions.createFrom 으로 더합니다. 채널 자격 증명을 주지 않으면 평문입니다(grpc.credentials.createInsecure(), client/transports/grpc/index.js:9671). 오류는 TaskNotFoundError 를 상속한 GrpcTaskNotFoundError 로 옵니다(:4282).

Go 클라이언트 — a2agrpc.WithGRPCTransport(dial 옵션)

dial 옵션을 그대로 넘긴다 — WithGRPCTransport 는 받은 grpc.DialOption 으로 grpc.NewClient(iface.URL, …) 를 부릅니다(a2agrpc/v1/client.go:37). 평문은 insecure.NewCredentials() 로 직접 고릅니다. 오류는 FromGRPCError 가 ErrorInfo 의 reason 과 상태 코드가 둘 다 맞는 표지 오류로 되돌립니다(internal/grpcutil/errors.go:132·:166).

3×3 — gRPC 에서는 아홉 칸이 모두 맞는다

세 클라이언트가 세 gRPC 서버를 차례로 부릅니다. 탭은 파이썬 서버 앞에만 두었습니다.

  • 보내기·없는 작업·잇기 모두 아홉 칸이 같은 뜻입니다 — 이름은 SDK 마다 다르지만(TaskNotFoundError·GrpcTaskNotFoundError·"task not found") 셋 다 "작업이 없다" 입니다. REST 의 3×3 에서 어긋난 세 짝(2장)이 여기에는 없습니다.
  • 어긋남의 원인이었던 Content-Type 과 스트림 속 오류의 꼴을 gRPC 에서는 프로토콜 자체가 정해 두었기 때문입니다.

세 클라이언트의 메타데이터 — 셋 다 a2a-version: 1.0, 다른 것은 user-agent 와 빈 configuration

  • 세 SDK 클라이언트 모두 a2a-version 을 실었습니다 — 파이썬은 전송이 늘 붙이고(_get_grpc_metadata, client/transports/grpc.py:299), TS·Go 는 클라이언트가 고른 인터페이스의 판을 서비스 매개변수에 넣어 전송에 넘깁니다(TS withNormalizedHeaders, client/index.js:5657 · Go a2aclient/client.go:270).
  • 파이썬·TS 는 비어 있는 configuration 메시지를 실어 보내고 Go 는 빼고 보냅니다. 서버에는 차이가 없습니다(셋 다 같은 답).

3장 퀴즈

Q. 없는 작업에 잇는 스트림이 REST 에서는 Go 서버만 200 OK 로 답했습니다. gRPC 에서 세 서버는 무엇을 보냈고, 그 오류는 응답의 어디에 실렸습니까?

A. 세 서버 모두 스트림 메시지를 하나도 보내지 않고 status NOT_FOUND 로 끝냈습니다(스트림 속 오류). 오류는 꼬리 메타데이터 — grpc-status·grpc-message 와, google.rpc.Status 를 담은 grpc-status-details-bin — 에 실렸고, 그 details 의 ErrorInfo 가 reason: TASK_NOT_FOUND 였습니다.

4장

한 서버 세 바인딩

세 문을 카드에 → 파이썬 서버 → TypeScript 서버 → Go 서버 → 한 작업 세 문: 명세 → 결과 → 클라이언트의 설정 셋 → 고른 문 → 닫힌 문과 대체

세 문은 모두 카드에 — supportedInterfaces 의 차례가 서버의 선호다 (§5.2)

§5.2 는 지원하는 프로토콜을 모두 카드에 적으라고 합니다(MUST). 세 문을 연 파이썬 서버의 카드를 탭 너머로 받았습니다.

  • JSON-RPC 는 뿌리 /, HTTP+JSON 은 /rest 아래, gRPC 는 다른 포트입니다. 문마다 protocolVersion 을 따로 적습니다.
  • 세 문 뒤에는 요청 처리기와 작업 저장소가 하나입니다. §5.1 의 "같은 기능·같은 동작"(1장)을 가장 싸게 지키는 길입니다 — 다음 세 슬라이드가 세 SDK 에서 그렇게 짓습니다.

파이썬 — 경로 목록에 둘, gRPC 서버에 하나, 처리기는 하나

13/doors.py 는 완성 숙소 에이전트의 카드와 실행기로 세 문을 엽니다. 들어온 문을 한 줄씩 찍는 기록기(ASGI 함수·gRPC 가로채기)는 실험을 위한 것입니다.

REST 를 /rest 아래로 — create_rest_routes(…, path_prefix="/rest") 로 JSON-RPC 의 / 와 갈랐습니다. REST 경로(/message:send …)는 / 와 겹치지 않으니 같은 뿌리에 달 수도 있지만, 나눠 두면 카드의 두 URL 과 서버의 기록에서 문이 한눈에 갈립니다.

TypeScript — express 에 두 Router, grpc-js 에 서비스 하나

순서가 뜻을 가진다 — jsonRpcHandler 를 "/" 에 달기 전에 "/rest" 를 먼저 답니다. express 는 먼저 단 Router 부터 맞춰 보기 때문입니다. 띄우는 법은 3장과 같은 node 13/bind_agent.ts doors lodging … 입니다(해석 훅).

Go — ServeMux 에 둘(/rest/ 는 StripPrefix), grpc.Server 에 하나

기록은 grpc-go 의 가로채기로 — grpc.UnaryInterceptor·grpc.StreamInterceptor 가 info.FullMethod 를 찍습니다. HTTP 쪽은 mux 전체를 감싼 logHTTP 입니다.

실험 — 카드에서 세 주소를 읽어, JSON-RPC 로 만든 작업을 REST 와 gRPC 로 읽는다

세 언어의 세 문 서버를 띄우고, 13/one_task.py 가 카드의 supportedInterfaces 를 protocolBinding → url 표로 바꿔 세 문을 차례로 씁니다.

한 작업, 세 문 — 셋 다 같은 작업을 보고, 서버의 기록에 세 문이 차례로 남았다

  • JSON-RPC 로 만든 작업을 HTTP+JSON 의 GET /rest/tasks/{id} 와 gRPC 의 GetTask 가 같은 id 로 읽었습니다. 세 언어의 서버가 모두 그랬습니다(TS·Go 서버의 기록도 [JSONRPC] → [HTTP+JSON] → [GRPC] 차례).
  • 문을 바꿔도 작업이 이어지는 것은 저장소가 하나이기 때문입니다. 문마다 저장소를 따로 두면 §5.1 의 "Consistent Behavior" 가 깨집니다.

클라이언트의 설정 셋 — 기본, "GRPC·HTTP+JSON 만 안다", "GRPC 우선"

고르는 규칙은 3부에서 소스로 읽었습니다(고르는 차례) — 기본은 카드 순서에서 아는 첫째, 클라이언트 선호를 주면 그것이 먼저. 이번에는 gRPC 를 넣은 같은 설정 셋을 세 SDK 로 지었습니다.

"아는 것" 과 "선호" 가 갈린 곳 — 파이썬의 supported_protocol_bindings 는 "선호 순서" 라는 주석이 붙어 있지만(client/client.py:61), use_client_preference 가 꺼져 있으면 아는 목록으로만 쓰입니다. TS·Go 는 아는 것(transports·팩토리 옵션)과 선호(preferredTransports·PreferredTransports)가 따로 있습니다.

고른 문 — 세 SDK 가 설정마다 같은 문을 골랐다

세 문 서버(doors) 하나에 세 언어의 클라이언트가 설정 셋으로 차례로 보냈습니다. 화면에는 결과만, 고른 문은 서버의 기록에 남습니다.

닫힌 문 — 카드의 gRPC 주소가 죽어 있으면 셋 다 실패하고, 다른 문으로 옮기지 않는다

§5.2 는 클라이언트가 다른 프로토콜로 옮겨 가는 대체(fallback) 논리를 갖추라고 합니다(SHOULD). 두 번째 서버(dead)는 카드의 gRPC 주소에 아무도 듣지 않는 포트를 적었습니다.

  • "GRPC 우선" 에서 세 SDK 모두 오류를 그대로 돌려주었고, 카드에 살아 있는 JSON-RPC·HTTP+JSON 문으로 다시 보내지 않았습니다. 대체는 SDK 가 해 주지 않으므로 부르는 쪽이 짜야 합니다.
  • Go 의 팩토리는 후보를 차례로 시도하는 고리가 있지만(a2aclient/factory.go:154), 그것은 전송을 만들 때의 실패만 넘깁니다. 만들 때 실패했다면 팩토리가 붙이는 failed to connect to … 앞부분(:161)이 오류에 있었을 것입니다. 위 Go 의 오류에는 그것이 없습니다 — grpc.NewClient(3장)는 만들 때 연결하지 않고, 첫 호출에서 실패했습니다. 주소의 꼴이 틀린 경우도 같습니다(5장).

4장 퀴즈

Q. 파이썬 클라이언트에 supported_protocol_bindings=["GRPC", "HTTP+JSON"] 만 주었더니 gRPC 가 아니라 HTTP+JSON 으로 갔습니다. 왜이고, gRPC 로 가게 하려면 무엇을 더해야 했습니까?

A. use_client_preference 가 기본으로 꺼져 있어, 목록은 "아는 것" 으로만 쓰이고 차례는 카드가 정합니다. 카드는 JSON-RPC → HTTP+JSON → GRPC 순서였고, 클라이언트가 아는 첫째가 HTTP+JSON 이었습니다(고른 문). use_client_preference=True 를 더한 "GRPC 우선" 설정이 [GRPC] 로 갔습니다.

스펙의 어긋남

SubscribeToTask 의 REST 동사: 세 서버 → 세 클라이언트 → 와이어 → gRPC 인터페이스의 url → 어긋남 모음

:subscribe 의 동사 — proto 는 GET, §5.3·§11.3.2 는 POST, 세 서버는 둘 다 받는다

1장에서 SDK 의 proto 주석을 뽑았을 때 열한 규칙 가운데 하나만 스펙의 표와 달랐습니다(1장). 세 REST 서버에 없는 작업의 :subscribe 를 동사 셋으로 보냈습니다.

  • GET 과 POST 는 세 서버 모두 처리기까지 갔습니다 — 파이썬·TS 는 404 + A2A 오류 JSON, Go 는 2장에서 본 200 SSE 안의 오류. 등록하지 않은 PUT 은 파이썬 404 글, TS 404 HTML, Go 405 입니다.
  • 설치본도 같습니다: 파이썬 ('/tasks/{id}:subscribe', 'GET')·'POST'(server/routes/rest_routes.py:87), TS registerRoute("get"…)·("post"…)(server/express/index.js:6249), Go GET /tasks/{idAndAction}·POST /tasks/{idAndAction} 가 둘 다 :subscribe 를 가릅니다(a2asrv/rest.go:54·:222·:231).

세 클라이언트의 SubscribeToTask — 같은 일 한 번씩

서버가 둘 다 받으니 클라이언트가 어느 쪽을 쓰는지가 남습니다. 세 SDK 의 REST 클라이언트로 없는 작업에 잇기만 했습니다.

세 클라이언트는 모두 POST — 스펙의 표를 따르고 proto 를 따르지 않는다

표의 가운데 열은 각 SDK 클라이언트가 보내는 동사, 오른쪽 열은 그 SDK 서버가 받는 동사입니다.

보내는 동사(설치본)받는 동사
파이썬'POST'(client/transports/rest.py:308)GET·POST
TypeScriptmethod: "POST"(_sendStreamingRequest, client/index.js:6378)GET·POST
Gomethod: "POST"(a2aclient/rest.go:320)GET·POST
엄격하게 보내고 너그럽게 받는다 — 세 SDK 는 보낼 때 §5.3 의 POST 를 쓰고, 받을 때는 proto 의 GET 도 받아 어느 쪽을 따른 상대와도 맞습니다. 위험한 것은 proto 주석에서 경로를 만들어 내는 다른 도구(gRPC-HTTP 게이트웨이 등)입니다 — 그런 서버는 GET 만 받아, 세 SDK 클라이언트의 POST 를 거절할 것입니다(이 장에서 재 보지는 않았습니다).

gRPC 인터페이스의 url — 스펙의 예는 https://…, 세 SDK 클라이언트는 호스트:포트 만 연다

proto 의 AgentInterface.url 주석은 "Must be a valid absolute HTTPS URL in production" 이고 예로 "https://grpc.example.com/a2a" 를 듭니다. §8.5 의 견본 카드도 gRPC 문을 "https://georoute-agent.example.com/a2a/grpc" 로 적습니다. 3장의 서버는 127.0.0.1:포트 로 적었습니다. 스킴을 붙인 카드(http://127.0.0.1:11395, TLS 를 섞지 않으려고 http)로 3장의 클라이언트 셋을 붙여 봤습니다.

  • 셋 다 카드의 문자열을 gRPC 의 대상(target)으로 그대로 넘겼고, 셋 다 그것을 주소로 읽지 못했습니다 — 파이썬·TS 는 이름 풀기에서(UNAVAILABLE), Go 는 대상 주소를 가르다가(invalid target address) 실패했습니다. 스킴과 경로를 떼어 내는 SDK 는 없었습니다. Go 의 오류에도 팩토리의 failed to connect to … 앞부분(a2aclient/factory.go:161)이 없습니다. 그러니 전송은 만들어졌고 첫 호출에서 실패한 것입니다 — 카드에 다른 문이 더 있었어도 팩토리가 넘어갈 자리가 아닙니다.
  • gRPC 에는 URL 의 경로 자리가 없습니다(메서드가 /lf.a2a.v1.A2AService/… 경로를 씁니다). 스펙의 예처럼 /a2a/grpc 를 붙인 주소는 프록시가 경로를 갈라 주지 않는 한 뜻이 없습니다. 이 책의 gRPC 카드가 호스트:포트 를 쓰는 까닭입니다.

5장 퀴즈

Q. proto 주석만 보고 SubscribeToTask 를 GET /tasks/{id}:subscribe 로만 받는 서버를 새로 만들었다고 합시다. 이 장의 세 SDK 클라이언트로 그 서버에 다시 잇기를 하면 어떻게 되겠습니까? 근거가 되는 캡처는 무엇입니까?

A. 세 클라이언트 모두 POST /tasks/{id}:subscribe 를 보내므로(와이어) 그 서버의 라우터에서 거절됩니다 — 등록하지 않은 동사에 대한 응답(405 나 404)이지, A2A 오류가 아닙니다. 이 장의 서버들은 PUT 에 대해 그렇게 답했습니다(동사 셋). 지금 세 SDK 끼리 맞는 것은 서버 쪽이 GET 과 POST 를 둘 다 받아 주기 때문입니다.
