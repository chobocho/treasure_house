보안 — 인증 스킴·OAuth2·확장 카드·서명

전송 보안 → 보안 스킴과 요구 → 토큰 발급기 ×3 → Bearer 검사 ×3 → 스코프 → 확장 카드 → AUTH_REQUIRED → 서명된 카드

정산 에이전트는 아무에게나 결재해 주지 않는다 — 이 부는 "누구냐" 와 "믿을 만하냐" 다

지금까지의 에이전트는 묻는 사람이 누구든 답했습니다. 정산 에이전트는 다릅니다. 카드에 "OAuth2 토큰을 가져오라" 고 적고(보안 스킴), 같은 서버의 토큰 발급기가 토큰을 내주고, 토큰이 없으면 401 로 돌려보내고, 큰 돈은 결재 스코프가 있어야 처리합니다. 카드에는 서명까지 붙습니다.

1장

전송 보안 — HTTPS 와 이 책의 http

스펙의 요구 → 이 책이 http 인 까닭 → TLS 앞단 → 앞단의 TLS 설정 → 실행 명세 → 파이썬 → TypeScript → Go → 세 언어 비교 → SDK 가 검사하지 않는 것

운영에서는 HTTPS 가 MUST — 서버의 인증서는 클라이언트가 확인한다(SHOULD)

A2A 는 인증을 프로토콜 안에 새로 만들지 않습니다. §7 의 첫 문장이 "relying on established web security practices" 이고, 그 바탕이 암호화된 연결입니다.

자리스펙의 말세기
§7.1"Production deployments MUST use encrypted communication (HTTPS for HTTP-based bindings, TLS for gRPC)"MUST
§7.1"modern TLS configurations (TLS 1.3+ recommended) with strong cipher suites"SHOULD
§7.2클라이언트는 "validating its TLS certificate against trusted certificate authorities" 로 서버가 누구인지 확인SHOULD
§13.4HSTS 머리글, SSLv3·TLS 1.0·1.1 끄기SHOULD
§13.4"Credentials SHOULD be transmitted only over encrypted connections"SHOULD
§7.1 과 §13.4 가 같은 말을 두 번 — 13.4 의 "Transport Security" 첫 두 줄은 7.1 의 두 문장을 그대로 되풀이합니다. 새로 보태는 것은 HSTS 와 낡은 판 끄기입니다.

이 책이 http 인 까닭 — 루프백 안에서만 돌고, 와이어 탭이 평문을 읽어야 해서

이 책의 서버는 모두 127.0.0.1 에만 귀를 엽니다(SCENARIO §3). 바깥에서 닿지 않는 시험 무대라서 "Production deployments" 가 아닙니다. 그리고 와이어 탭(2부)은 바이트를 읽어 적는 프록시라, TLS 를 쓰면 탭이 볼 것이 암호문뿐입니다.

  • 그 대가 — http 위의 토큰과 비밀번호는 누구나 읽습니다. 탭이 읽는 그대로입니다. 3장의 토큰 요청에는 client_secret=planner-secret 이, 4장의 요청에는 Authorization: Bearer tok-… 가 글자 그대로 보입니다.
  • Bearer 토큰은 가진 사람이 주인 — 엿본 토큰을 그대로 붙이면 그 사람이 됩니다. 이 위험이 실제로 어떻게 생겼는지는 3장에서 봅니다.
  • 그래서 이 장은 한 번만 진짜 TLS 를 세웁니다 — 에이전트 앞에 TLS 앞단을 두고, 세 SDK 클라이언트가 인증서를 어떻게 다루는지 봅니다.

TLS 앞단 — HTTPS 를 받아 풀고 뒤의 http 에이전트에 넘긴다

운영에서도 흔한 모양입니다 — TLS 는 리버스 프록시가 끝내고, 에이전트는 안쪽에서 http 로 돕니다. 12/tls_front.py 는 표준 라이브러리만 쓴 그 축소판입니다. 받은 요청을 그대로 넘기는 부분입니다.

안쪽은 다시 평문 — 앞단 뒤의 구간(여기서는 같은 기계의 루프백)은 암호화되지 않습니다. §7.1 은 "encrypted communication" 을 요구할 뿐 앞단 뒤의 구간을 따로 말하지 않으니, 그 구간을 어떻게 지킬지는 운영의 몫입니다. 스트림(SSE)은 이 앞단이 넘기지 않습니다 — 몸통을 다 읽고 넘기기 때문입니다.

앞단의 TLS 설정 — 인증서·개인키 한 쌍, 최소 판 TLS 1.3

§7.1 이 권하는 TLS 1.3 을 바닥으로 정했습니다. 인증서는 ex/run/12/tls/ 의 시험용입니다 — 시험 CA 가 127.0.0.1 에 서명한 것으로, CA 의 개인키는 만들고 곧 지웠습니다.

저장소에 든 개인키 — server-key.pem 은 누구나 읽을 수 있으니, 이 인증서가 지키는 것은 없습니다. 이 기계의 루프백에서 TLS 의 모양을 보려는 것뿐입니다. 운영의 키는 저장소에 두지 않습니다(§13.4 "MUST be treated as secrets").

실행 명세 — 카드의 주소를 https 로 알리고, 앞단 뒤에 정산 에이전트

정산 에이전트에 --url https://127.0.0.1:11201/ 을 주면 카드의 인터페이스 주소와 토큰 주소가 앞단의 https 주소가 됩니다. 클라이언트 셋은 같은 일을 합니다 — 기본 신뢰 목록으로 카드를 한 번, 시험 CA 를 믿게 하고 한 번 읽습니다.

요청 줄이 셋인 까닭 — 클라이언트는 여섯 번 붙었지만, 기본 신뢰 목록으로 붙은 세 번은 TLS 악수(handshake)에서 클라이언트가 끊었습니다. HTTP 요청은 한 줄도 오가지 않았습니다.

파이썬 — 인증서 검사는 httpx 가, 신뢰 목록은 certifi 가 정한다

SDK 의 A2ACardResolver 는 받은 httpx 클라이언트로 GET 할 뿐입니다. 검사의 손잡이는 httpx 의 verify 입니다.

  • verify=True 는 httpx 가 certifi 의 공인 CA 목록으로 만든 설정입니다(httpx/_config.py:40). 시험 CA 가 없으니 CERTIFICATE_VERIFY_FAILED — SDK 는 이것을 AgentCardResolutionError 로 감쌉니다.
  • ssl.create_default_context(cafile=…) 는 이름 확인(check_hostname)도 켭니다. 인증서의 이름이 IP:127.0.0.1 이라 주소와 맞습니다.

TypeScript — 검사는 Node 의 fetch 가, 신뢰 목록은 Node 에 든 것

DefaultAgentCardResolver 는 전역 fetch 를 씁니다. 시험 CA 를 믿게 하려고 Node 24 의 tls.setDefaultCACertificates 로 이 프로세스의 기본 CA 를 바꿨습니다.

  • 실패는 TypeError: fetch failed 하나이고, 까닭은 cause.code 의 UNABLE_TO_VERIFY_LEAF_SIGNATURE 에 있습니다. SDK 는 이 오류를 감싸지 않고 그대로 던집니다.
  • 리졸버는 proto 꼴 보안 스킴이 든 카드만 AgentCard.fromJSON 을 거쳐 돌려줍니다(3부·8부). 정산 카드가 바로 그 경우라 oneof 를 $case 로 읽습니다. 그 객체를 한 번 더 fromJSON 하면 스킴이 사라집니다 — fromJSON 은 JSON 의 키(oauth2SecurityScheme)만 찾기 때문입니다(dist/index.js:760).

Go — 검사는 net/http 가, 신뢰 목록은 http.Client 의 RootCAs

agentcard.NewResolver 는 받은 *http.Client 로 GET 합니다. 시험 CA 는 tls.Config{RootCAs: pool} 로 넣습니다.

  • 오류는 errors.As 로 x509.UnknownAuthorityError 까지 풀립니다 — 리졸버가 돌려준 오류의 사슬 안에 그대로 있습니다.
  • 보안 스킴은 Go 의 인터페이스 값입니다. SecuritySchemes["oauth"].(a2a.OAuth2SecurityScheme), 그 안의 흐름도 .(a2a.ClientCredentialsOAuthFlow) 로 꺼냅니다.

SDK 가 보지 않는 것 — https 인지, HSTS 인지

1장 퀴즈

Q. 1장의 명세에서 클라이언트는 앞단에 여섯 번 붙었는데, 앞단의 출력에는 GET /.well-known/agent-card.json 이 세 줄뿐입니다. 나머지 세 번은 어디서 끝났고, 왜 서버 쪽에는 흔적이 없습니까?

A. TLS 악수에서 끝났습니다. 기본 신뢰 목록에는 시험 CA 가 없어 세 클라이언트가 서버의 인증서를 거절하고 끊었습니다(파이썬의 CERTIFICATE_VERIFY_FAILED, TS의 UNABLE_TO_VERIFY_LEAF_SIGNATURE, Go의 unknown authority). HTTP 요청은 암호화된 연결이 선 뒤에야 오가므로, 앞단의 요청 기록(log_message)까지 닿지 않았습니다(앞단의 출력).

securitySchemes·securityRequirements

다섯 스킴 → OAuth2 의 다섯 흐름 → 정산 카드의 와이어 → 파이썬 → TypeScript → $case 가 새는 자리 → Go → 세 서버 비교 → 요구의 모양 → 세 가지 꼴 풀기 ×3 → AND 와 OR → 가로채기로 재 보기 → 클라이언트가 스킴을 읽는 법

보안 스킴(security scheme)은 다섯 가지 — proto 의 oneof 하나에 하나씩

카드의 securitySchemes 는 "이름 → 스킴" 의 맵입니다(map<string, SecurityScheme> security_schemes = 8). 스킴 하나는 다섯 가운데 하나만 고르는 oneof 이고, proto 주석은 "based on the OpenAPI 3.2 Security Scheme Object" 라고 밝힙니다.

정산 카드의 와이어 — 스킴 이름은 oauth, 요구는 payment:read

세 정산 에이전트의 공개 카드를 탭 너머로 읽었습니다. 파이썬 서버의 카드에서 보안 두 필드만 잘랐습니다.

  • securitySchemes.oauth — "이 에이전트는 oauth 라는 이름의 OAuth2 스킴을 안다". 토큰은 tokenUrl 에서, 스코프는 둘(payment:read 정산 조회, payment:approve 결재 승인).
  • securityRequirements — "부르려면 oauth 스킴으로, payment:read 스코프를 가지고 오라". 결재 스코프는 요구에 없습니다 — 큰 돈을 처리할 때만 작업 안에서 따로 묻습니다(7장).

파이썬 — SecurityScheme(oauth2_security_scheme=…), 요구는 StringList

agents/settlement.py 의 카드입니다. protobuf 메시지를 그대로 짓습니다 — oneof 는 고른 필드 하나에 값을 주는 것으로 정해집니다. 요구의 NEEDED 는 ["payment:read"] — 문지기도 같은 상수를 봅니다(5장).

토큰 주소는 카드의 주소에서 — url + "oauth/token". 1장에서 --url https://… 를 주었더니 토큰 주소도 https 가 된 까닭입니다(1장).

TypeScript — 카드는 와이어 모양 객체, 보안 스킴도 JSON 의 키 그대로

agents/settlement.ts 의 카드입니다. 숙소 카드처럼(3부) ts-proto 타입이 아니라 camelCase JSON 모양으로 적습니다 — oauth2SecurityScheme: {flows: {clientCredentials: …}}.

요구의 {list: [...]} — JSON 모양이라 StringList 의 감싸개도 손으로 적습니다(NEEDED 는 ["payment:read"], 5장). 서버를 띄우는 common.ts 가 이 객체를 AgentCard.fromJSON 으로 읽고 toJSON 으로 되돌려 내보냅니다(3부). 그렇게 하지 않으면 어떻게 되는지가 다음 슬라이드입니다.

ts-proto 객체를 그대로 내보내면 $case 가 와이어에 샌다

3부에서 미뤄 둔 이야기입니다 — SDK 의 카드 처리기는 받은 객체를 JSON.stringify 할 뿐이라(3부), oneof 가 있는 카드를 ts-proto 객체로 주면 이렇게 나갑니다.

  • oneof 가 {"scheme": {"$case": …, "value": …}} 로, 빈 기본값이 "description": ""·"refreshUrl": "" 로 나갑니다. 이 카드를 받은 파이썬 클라이언트는 모르는 키 scheme 을 버려(ignore_unknown_fields=True, client/card_resolver.py:27) oauth 스킴의 종류를 잃고, Go 클라이언트는 카드 해석부터 실패합니다(a2a/auth.go:200 "unknown security scheme type").
  • AgentCard.toJSON 을 거치면 와이어 모양으로 돌아옵니다. 그래서 common.ts 는 늘 toJSON 한 것을 처리기에 줍니다.

Go — 스킴은 인터페이스 값, 요구는 {"oauth": needed}

agents/settlement/main.go 의 카드입니다. a2a.SecurityScheme 와 a2a.OAuthFlows 는 봉인된 인터페이스라, 구조체 값 하나를 넣는 것으로 oneof 를 고릅니다(a2a/auth.go:212). needed 는 []string{"payment:read"} — 문지기도 같은 변수를 봅니다(5장).

Go 타입에는 list 가 없다 — SecurityRequirements 는 map[이름][]string 입니다. 와이어의 {"list": [...]} 는 직렬화할 때 SDK 가 감쌉니다(securityScopeList.MarshalJSON, a2a/auth.go:63).

세 서버 비교 — 같은 보안 필드, Go 만 키가 알파벳순

TS 서버의 카드는 파이썬 서버의 것과 포트·서명값·Content-Type 의 charset 만 다릅니다. Go 서버의 같은 자리입니다.

  • Go 정산 에이전트는 서명한 바이트를 그대로 내보냅니다. 그 바이트는 카드를 맵으로 한 번 풀었다가 다시 쓴 것이라(common.ProtoJSON) 키가 알파벳순입니다 — 숙소 카드의 "구조체 필드 순"(3부)과 다릅니다. 까닭은 서명을 다루는 8장의 몫입니다.
  • JSON 객체의 키 순서에는 뜻이 없으니, 세 카드가 말하는 보안은 같습니다.

요구의 모양 — proto 는 {"schemes": {이름: {"list": [...]}}}, 스펙 본문은 아직 옛 꼴

v1.0.1 proto 의 SecurityRequirement 는 "A map of security schemes to the required scopes" — 맵의 값이 문자열 목록이 아니라 StringList 메시지라서 list 한 겹이 더 있습니다. 그런데 스펙 본문 몇 곳은 v0.3 의 이름과 모양을 그대로 씁니다.

세 가지 꼴 풀기 — 파이썬은 옛 security 를 고쳐 읽고, 감싸개 없는 목록은 버린다

  • ③ 은 살아남습니다 — parse_agent_card 가 security 를 꺼내 {"schemes": {이름: {"list": …}}} 로 바꿔 넣습니다(_map_legacy_security).
  • ② 는 오류 없이 스코프가 사라집니다. protobuf 의 JSON 해석이 목록의 원소 "payment:read" 를 StringList 의 필드 이름으로 보고, 그런 필드가 없으니 버렸습니다 — parse_agent_card 가 ignore_unknown_fields=True 로 부르기 때문입니다(client/card_resolver.py:27).

요구 목록은 OR, 요구 하나 안의 스킴은 AND — 스펙이 아니라 OpenAPI 와 Go SDK 가 말한다

v1.0.1 의 스펙 본문과 proto 주석은 목록 여러 개, 스킴 여러 개를 어떻게 엮는지 말하지 않습니다. 근거는 proto 가 기대는 OpenAPI 의 뜻과, 그것을 적어 둔 Go SDK 의 주석입니다.

카드의 요구뜻
[{"schemes": {"oauth": …}}]oauth 토큰 하나 — 정산 에이전트
[{"schemes": {"oauth": …}}, {"schemes": {"key": …}}]oauth 또는 API 키

  • Go a2a/agent.go:176-178: "this list represents a logical OR of security requirement objects. Each object is a set of security schemes that must be used together (a logical AND)."
  • 같은 SDK 의 a2a/auth.go:39-46 은 "OAuth OR an API Key AND mTLS" 라 적고, 예시로는 apiKey 와 oauth2 를 한 요구 안에 넣었습니다 — 글로는 OR, 코드로는 AND 인 주석입니다.
  • 스펙 §3.1.11·§13.3 은 클라이언트가 "one of the schemes declared" 로 인증한다고만 적습니다 — 한 요구 안의 AND 와는 맞지 않는 말입니다(게다가 필드 이름은 옛 security — 요구의 모양).
  • 스킬마다 따로 요구를 둘 수도 있습니다(AgentSkill.security_requirements, 8번). 정산 카드는 쓰지 않습니다.

가로채기로 재 보기 — AND 를 요구해도 SDK 는 머리글을 하나만 단다

파이썬·Go SDK 에는 카드의 요구를 읽어 머리글을 다는 AuthInterceptor 가 있습니다(TS 에는 없습니다). 두 자격 증명을 다 쥐여 주고 before 만 불렀습니다.

  • 두 SDK 모두 첫 자격 증명을 찾는 순간 return 합니다(파이썬 client/auth/interceptor.py:63, Go a2aclient/auth.go:94). 그래서 AND 요구에는 언제나 하나뿐이고, 무엇이 붙을지는 맵(schemes)을 도는 차례에 달렸습니다. Go 는 같은 프로세스 안에서도 부를 때마다 달라졌습니다. 파이썬은 protobuf 맵의 차례를 따르는데, 그 차례가 프로세스마다 바뀔 수 있어 수만 찍었습니다.
  • OR 요구에서는 목록의 앞쪽(oauth)이 이깁니다. 클라이언트의 선택이 아니라 카드의 차례입니다.

2장 퀴즈

Q. 스펙 §8.5 의 예시를 본떠 카드에 "security": [{"oauth": ["payment:read"]}] 라고 적었습니다. 파이썬·TS·Go 클라이언트는 이 카드에서 보안 요구를 몇 개씩 읽습니까?

A. 파이썬 1개, TS 0개, Go 0개입니다(파이썬·TS·Go의 ③). 파이썬 클라이언트만 옛 security 필드를 v1.0 의 securityRequirements 로 고쳐 읽습니다. TS·Go 는 모르는 필드로 보고 버리며, 오류도 내지 않습니다. v1.0.1 의 기준인 proto 꼴(securityRequirements + {"list": […]})로 적어야 세 SDK 가 같게 읽습니다.

client_credentials — 프로그램이 제 이름과 비밀로 토큰을 받는다

기획 에이전트가 정산 에이전트를 부르기 전의 한 걸음입니다(RFC 6749 §4.4). 토큰을 어디서 받을지는 카드가 알려 줍니다 — flows.clientCredentials.tokenUrl(2장).

발급기가 같은 서버에 있는 까닭 — 시험 무대를 하나로 줄이려는 것입니다(SCENARIO §3). 운영에서는 따로 선 인가 서버(authorization server)가 토큰을 내고, 에이전트는 그 토큰을 검사만 합니다. 스펙도 자격 증명을 얻는 일을 "out-of-band" 라고만 합니다(§7.3).

  • 발급기는 스코프를 주기만 합니다. 받은 스코프로 무엇을 할 수 있는지는 정산 에이전트가 정하고, 그것은 5장의 몫입니다.

파이썬 — Starlette 경로 하나, 폼은 urllib.parse 로 푼다

agents/settlement.py 의 발급기입니다. serve(…, routes=[Route("/oauth/token", …, methods=["POST"])]) 로 SDK 의 경로 옆에 붙습니다.

폼을 손으로 푸는 까닭 — Starlette 의 request.form() 은 python-multipart 패키지가 있어야 하는데, 이 venv 에는 깔려 있지 않습니다(SDK 의 extra 가 끌어오지 않습니다). 그래서 몸통을 읽어 parse_qs 합니다.

TypeScript — express 경로 하나, 폼은 URLSearchParams

agents/settlement.ts 의 같은 자리입니다. 경로를 다는 곳에서 몸통을 글 그대로 받게 했습니다(express.text({type: () => true})).

스코프 쪼개기 — split(/\s+/).filter(Boolean). 파이썬의 str.split(), Go 의 strings.Fields 처럼 빈칸 여러 개와 빈 문자열을 같은 뜻으로 다룹니다. OAuth 의 scope 는 빈칸으로 가른 목록입니다.

Go — r.ParseForm, 맵은 뮤텍스 안에서, 응답은 구조체로

agents/settlement/main.go 의 같은 자리입니다. net/http 의 핸들러는 요청마다 따로 도니 발급 기록을 sync.Mutex 로 지킵니다.

왜 구조체(tokenJSON)인가 — Go 의 map 을 직렬화하면 키가 정렬됩니다. 구조체로 써야 필드가 access_token·token_type·expires_in·scope 차례로 나가, 파이썬·TS 의 응답과 바이트까지 같습니다(세 서버 비교).

와이어 — 폼 한 줄이 가고, JSON 넷이 온다. 비밀은 평문 그대로

세 정산 에이전트 앞에 탭을 두고 planner 의 토큰을 받았습니다. 파이썬 서버의 주고받음입니다.

  • access_token 과 token_type(Bearer)이 핵심이고, expires_in(초)과 scope(받은 스코프)가 곁들여집니다(RFC 6749 §5.1).
  • client_secret=planner-secret 이 탭에 글자 그대로 찍혔습니다. 1장이 말한 http 의 대가입니다(1장).

세 서버 비교 — 같은 몸통, 다른 것은 TS 의 charset 뿐

TS·Go 서버의 응답입니다. 표의 위 세 줄은 짜는 법이고, 와이어에서 갈리는 것은 마지막 Content-Type 줄의 TS 칸뿐입니다.

맞는 요청 둘, 틀린 요청 다섯 — 세 발급기의 답이 글자까지 같다

12/token_try.py 가 세 발급기에 일곱 가지 폼을 보냅니다. ⑦ 만 비밀을 폼이 아니라 HTTP Basic 머리글(Authorization: Basic …)로 보냅니다.

①②의 토큰이 2·3번 — 앞의 curl 이 1번을 가져갔기 때문입니다. ② 처럼 스코프를 좁혀 받은 토큰은 "scope": "payment:read" 만 가집니다 — 결재가 필요 없는 일에는 좁은 토큰을 쓰라는 것이 최소 권한의 원칙입니다.

RFC 6749 와 §13.4 에 견주면 — 오류의 모양은 맞고, 줄인 것이 여럿

오류 응답은 {"error": "…"} 하나, 코드는 RFC 6749 §5.2 의 이름입니다. 그러나 이 발급기는 시험용이라 RFC 와 스펙이 요구하는 몇 가지를 빼먹었습니다. 앞 슬라이드의 답과 세 언어의 tokens 구역이 그 증거입니다.

순번 토큰은 맞힐 수 있다 — 비밀 없이 tok-planner-1 을 붙였더니 planner 의 정산서

토큰 이름이 tok-<client_id>-<n> 이라는 것만 알면 비밀번호가 필요 없습니다. 명세의 마지막 curl 은 토큰을 받은 적 없이 Authorization: Bearer tok-planner-1 만 달았습니다.

  • 정산 에이전트는 토큰이 발급 기록에 있는지와 그 토큰의 스코프만 봅니다(4장·5장) — 누가 내밀었는지는 묻지 않습니다. 그러니 이 요청은 planner 의 이름으로 처리되어 approvedBy: planner 가 찍혔습니다.
  • 세 언어의 발급기가 모두 일부러 이렇게 짰습니다 — 주석의 "캡처가 매번 같도록". 덕분에 이 책의 캡처는 돌릴 때마다 같지만, 같은 까닭으로 남도 토큰을 맞힙니다.

진짜 토큰 ×3 — 운영체제의 난수 256비트, URL 에 안전한 43글자

RFC 6749 §10.10 은 토큰을 맞힐 확률을 아주 작게(2-128 이하) 만들라고 합니다. 세 언어 모두 표준 라이브러리 한 줄입니다. 값은 실행마다 달라 모양만 찍었습니다.

난수만으로는 모자라다 — 토큰은 맞히기 어려워야 하고, 또 엿보이지 않아야 합니다(HTTPS, 1장). 서명된 토큰(JWT)을 쓰면 발급 기록 없이도 검사할 수 있지만, 그것은 이 책의 범위 밖입니다.

3장 퀴즈

Q. intern 이 scope=payment:approve 로 토큰을 달라고 하면 무엇을 받습니까? 그리고 planner 가 scope 를 아예 빼고 달라고 하면 받은 토큰의 scope 는 무엇입니까?

A. 첫째는 HTTP 400 {"error":"invalid_scope"} 입니다 — intern 이 가진 스코프는 payment:read 뿐입니다(③, 세 발급기가 같습니다). 둘째는 payment:read payment:approve 입니다 — 스코프를 적지 않으면 그 클라이언트의 스코프 전부를 줍니다(①, 파이썬의 or who["scopes"]).

4장

정산 에이전트의 Bearer 검사 ×3

스펙의 요구 → 문지기의 자리 → 파이썬 → TypeScript → Go → 네 가지 머리글 → 세 서버 비교 → 사용자를 실행기까지 → SDK 클라이언트 ×3 → 세 클라이언트 비교 → 카드만으로는 막지 못한다

모든 요청을 인증하라(MUST) — 거절할 때는 무엇이 필요한지 알려 주라(SHOULD)

카드가 말한 요구(2장)를 실제로 지키게 하는 것은 서버입니다. 스펙은 서버의 몫을 두 곳에 적었습니다.

자리스펙의 말
§7.4"MUST authenticate every incoming request based on the provided credentials and its declared authentication requirements"
§7.4"SHOULD use appropriate binding-specific error codes", "SHOULD provide relevant authentication challenge information"
§3.3.2Authentication Errors — "MUST reject requests with invalid or missing authentication credentials", 예: "HTTP 401 Unauthorized, gRPC UNAUTHENTICATED, JSON-RPC custom error"
도전(challenge)은 WWW-Authenticate — HTTP 의 401 은 이 머리글로 "이 방식으로 다시 오라" 를 알립니다. Bearer 토큰의 머리글 모양(realm, error="invalid_token")은 RFC 6750 §3 이 정합니다. 정산 에이전트는 JSON-RPC 오류가 아니라 이 HTTP 의 길을 씁니다.

문지기는 HTTP 층에, 경로 / 하나만 — 카드·JWKS·토큰 발급은 열어 둔다

세 언어 모두 SDK 의 JSON-RPC 처리기 앞에 우리 코드 한 겹을 둡니다. 토큰이 없으면 SDK 까지 가지 않고 401 로 끝납니다.

 요청 ─▶ POST /  ─▶ [문지기: 토큰 확인] ─없다▶ 401 + WWW-Authenticate
                         │ 있다
                         ▼
                   SDK JSON-RPC 처리기 ─▶ [사용자 세우기] ─▶ 실행기
 요청 ─▶ GET /.well-known/agent-card.json ─▶ 카드      (누구나)
 요청 ─▶ GET /.well-known/jwks.json       ─▶ 공개 키   (누구나, 8장)
 요청 ─▶ POST /oauth/token               ─▶ 토큰 발급 (누구나, 3장)
카드를 막으면 아무도 못 들어온다 — 토큰을 어디서 받는지가 카드에 있으니, 카드와 토큰 발급은 토큰 없이 닿아야 합니다. 로그인한 사람만 보는 카드는 따로 있습니다(6장, GetExtendedAgentCard — 경로 / 의 JSON-RPC 메서드라 문지기를 지납니다).

파이썬 — Starlette 의 AuthenticationMiddleware 와 우리 RequireBearer

두 겹입니다. BearerBackend 가 토큰으로 사용자와 스코프를 붙이고(익명이면 None), RequireBearer 가 경로 / 에서 익명을 401 로 돌려보냅니다. 토큰은 맞는데 카드가 요구한 스코프가 없으면 403 — 처음에는 없던, 5장에서 고친 갈래입니다.

  • 미들웨어는 serve(…, middleware=[Middleware(AuthenticationMiddleware, backend=BearerBackend()), Middleware(RequireBearer)]) 로 겁니다 — 앞의 것이 먼저 돕니다.
  • 토큰이 아예 없으면 error 를 붙이지 않습니다. 주석이 말하는 RFC 6750 의 규칙입니다.

TypeScript — express 미들웨어 하나, 같은 bearer(req) 를 두 번 부른다

app.all("/", requireBearer) 가 SDK 의 jsonRpcHandler 보다 먼저 걸립니다. 통과한 요청에서는 userBuilder 가 같은 bearer(req) 로 사용자를 다시 세웁니다. lacks·insufficient(403)는 5장에서 고치며 더한 것입니다.

사용자 클래스를 우리가 — SDK 의 User 인터페이스는 userName 과 isAuthenticated 뿐이라, 스코프를 실어 나르려고 BearerUser 를 만들었습니다. 실행기는 user instanceof BearerUser 로 꺼냅니다.

Go — http.Handler 를 감싸는 문지기와 SDK 의 호출 가로채기

requireBearer 는 JSON-RPC 처리기를 감싸는 보통의 Go 미들웨어입니다(common.Options.Guard — mux.Handle("/{$}", …) 의 앞). 통과한 요청에서는 bearerUser.Before 가 CallContext.User 를 바꿉니다. lacks(g.scopes) 갈래(403)는 5장에서 고치며 더한 것입니다.

머리글은 ServiceParams 에서 — 가로채기는 *http.Request 를 받지 않습니다. JSON-RPC 처리기가 HTTP 머리글을 ServiceParams 에 옮겨 담아 주므로(9부) 거기서 authorization 을 읽습니다.

네 가지 머리글 — 없으면 realm 만, 있는데 틀리면 error="invalid_token"

세 정산 에이전트에 같은 SendMessage 를 머리글 네 가지로 보냈습니다 — 인증 머리글 없음, Basic, 토큰 없는 Bearer, 발급한 적 없는 tok-planner-9. 파이썬 서버의 탭입니다.

Basic 에도 invalid_token — 세 언어의 문지기는 Authorization 머리글이 있으면 무엇이든 error="invalid_token" 을 답니다. RFC 6750 §3.1 은 지원하지 않는 방식으로 온 요청도 "인증 정보가 없는" 경우로 보아 error 를 붙이지 말라고 합니다(SHOULD NOT). 이 책의 에이전트가 줄인 자리입니다.

세 서버 비교 — 같은 401 과 같은 몸통, 머리글 이름의 글자 모양만 셋

TS·Go 서버의 탭도 같은 네 답을 남겼습니다. 탭은 머리글 이름을 한 가지 모양으로 적으므로, 마지막 차이는 탭을 거치지 않은 curl 로 봤습니다.

  • 파이썬(uvicorn)은 머리글 이름을 소문자로, TS(Node)는 우리가 쓴 그대로, Go 는 Www-Authenticate 로 바꿔 보냅니다(net/http 의 정규 모양). HTTP 머리글 이름은 대소문자를 가리지 않으니 뜻은 같습니다.
  • 401 의 몸통은 {"error": "unauthorized"} 또는 {"error": "invalid_token"} — JSON-RPC 의 error 객체가 아닙니다. JSON-RPC 처리기에 닿기 전에 끝났기 때문입니다. 클라이언트가 이것을 어떻게 받는지는 SDK 클라이언트 ×3에서 봅니다.

사용자를 실행기까지 — 세 SDK 의 갈고리에 토큰의 주인을 싣는다

문지기를 지난 요청의 "누구" 는 SDK 가 정한 자리로 실행기에 갑니다. 그 자리는 7~9부 5장에서 봤고(7부·8부·9부), 정산 에이전트는 거기에 토큰의 클라이언트와 스코프를 싣습니다.

파이썬 클라이언트 — 401 은 A2AClientError, 토큰은 AuthInterceptor 가 단다

12/settle_client.py 는 카드를 읽고, 빈 자격 증명 저장소로 한 번 보내고, 카드의 tokenUrl 에서 받은 토큰을 저장소에 넣고 다시 보냅니다.

WWW-Authenticate 는 클라이언트에 닿지 않는다 — 오류 문구는 httpx 의 것이고(401 Unauthorized 와 MDN 주소), 서버가 보낸 realm 은 예외에 없습니다. 토큰을 받는 get_token 은 3장의 폼을 httpx 로 보내는 열 줄입니다(같은 파일의 token 구역).

TypeScript 클라이언트 — 401 을 본 뒤에야 토큰을 받으러 간다

TS SDK 에는 카드를 읽는 가로채기가 없으니, createAuthenticatingFetchWithRetry(8부)의 shouldRetryWithHeaders 안에서 토큰을 받습니다.

401 이 한 번 더 — 감싼 fetch 는 처음에 토큰이 없으니 한 번 401 을 맞고, 그다음 토큰을 받아 다시 보냅니다. 첫 실패를 아끼려면 카드의 요구를 보고 미리 받아 두면 됩니다 — 파이썬·Go 처럼.

Go 클라이언트 — 401 은 "unexpected HTTP status", 토큰은 세션에 넣는다

a2aclient.AuthInterceptor 는 ctx 에 붙은 세션 id 로 저장소를 찾습니다(2장). 같은 클라이언트도 세션 없는 ctx 로 부르면 토큰을 달지 않습니다.

상태 코드만 남는다 — 오류는 unexpected HTTP status: 401 Unauthorized 한 줄입니다. 몸통({"error":"unauthorized"})도 WWW-Authenticate 도 오류에 없습니다.

카드만으로는 막지 못한다 — 문지기를 빼면 토큰 없이도 정산서가 나온다

12/card_only.py 는 완성 정산 에이전트의 카드와 실행기를 그대로 가져다 쓰고 미들웨어만 뺐습니다. 카드는 여전히 oauth·payment:read 를 요구합니다.

  • 요청에는 Authorization 이 없는데 COMPLETED 가 왔고, 결재자는 빈 이름입니다. 서버 SDK 는 카드의 securitySchemes·securityRequirements 를 읽어 요청을 막지 않습니다 — 파이썬 a2a/server/ 와 Go a2asrv/ 에는 그 낱말이 없고, TS 서버 묶음은 카드를 JSON 으로 바꿀 때만 씁니다.
  • 카드의 보안 필드는 클라이언트에게 하는 안내입니다. 지키게 하는 것은 서버를 짠 사람의 몫입니다(§7.4 의 MUST).

4장 퀴즈

Q. TS 클라이언트로 정산을 맡겼더니 탭에 401 이 두 번 찍혔습니다. 파이썬·Go 클라이언트는 한 번인데 왜 TS 만 두 번이고, 두 번째 401 은 어느 요청의 것입니까?

A. 첫 401 은 세 언어 공통의 ① — 일부러 토큰 없이 보낸 요청입니다. TS 의 두 번째 401 은 ③ 의 첫 시도입니다. TS 클라이언트는 카드의 요구를 미리 읽어 토큰을 받는 대신, 감싼 fetch 가 401 을 본 뒤에 shouldRetryWithHeaders 에서 토큰을 받아 다시 보내기 때문입니다(TS 클라이언트의 와이어: 401 → POST /oauth/token → Authorization: Bearer tok-planner-1 로 200). 파이썬·Go 는 토큰을 먼저 저장소에 넣고 보냈습니다(비교).
