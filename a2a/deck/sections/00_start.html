이 책은 A2A(Agent2Agent) 프로토콜을 세 언어의 공식 SDK 와 맨손 구현으로 직접 돌려 보며 배웁니다. 0부는 그 돌린 결과를 어떻게 믿고 어떻게 읽는지를 정해 둡니다. 뒤의 부들이 "0부" 라고 가리키는 규칙은 모두 여기에 있습니다.

1장

이 책의 약속

돌아가는 코드만 → 캡처가 증거 → 규칙만 쓰는 에이전트(LLM 없음) → 스펙 v1.0.1 → SDK 판과 2026-10 기준

화면의 코드는 모두 저장소의 진짜 파일에서 잘라 왔다

덱은 손으로 쓰지 않고 조립합니다. 슬라이드 조각에는 "이 파일의 이 구역" 이라는 표시만 있고, 조립기(deck/build_deck.py)가 ex/ 아래 파일에서 그 줄을 잘라 붙입니다. 코드 위의 이름표가 그 파일입니다.

화면에 보이는 것어디서 오나
코드 블록ex/py·ex/ts·ex/go 의 파일 — 이름표에 경로, 구역(region)만 잘랐으면 그 줄만
실행 결과·와이어out/NN/ 의 캡처 — tools/a2arun.py 가 이 기계에서 돌려 남긴 화면
실행 명세ex/run/NN/*.run — 서버·탭·클라이언트를 어떤 차례로 띄웠나
상자 그림손으로 그린 <pre class="fig"> — 코드·JSON 이 섞이면 조립기가 거절
의사코드가 없다 — 조립기는 조각에 손으로 쓴 <pre> 가 있으면 덱을 만들지 않습니다. 그래서 이 책의 JSON 한 줄, HTTP 머리 한 줄도 누가 친 것이 아니라 프로그램이 주고받은 것입니다.

캡처가 증거다 — 낡았거나 손댄 캡처는 장부가 잡는다

캡처마다 그것을 만든 입력의 해시가 장부(out/MANIFEST.tsv)에 남습니다. 예제·명세·공유 소스·고정 자료(ex/fixtures)·와이어 탭 가운데 하나라도 바뀌면 그 캡처는 "낡았다" 고 표시됩니다.

명령하는 일
python3 tools/a2arun.py 예제돌려서 out/ 에 캡처를 쓰고 장부를 고친다
… --check 예제다시 돌려 이미 있는 캡처와 글자까지 같은지만 본다
… --manifest-check돌리지 않고 입력·캡처의 해시를 장부와 대조 — "캡처가 손으로 고쳐졌다" 도 여기서 걸린다
  • 이 책을 쓰는 규칙은 캡처마다 --check 를 두 번 통과시킨 뒤에 싣는 것입니다. 실행마다 달라지는 것(시각·UUID 따위)은 4장의 정규화 표가 정한 다섯 가지만 지웁니다.
  • 캡처가 기대와 다르면 캡처가 맞고 글이 틀린 것입니다. 이 책은 그럴 때 글을 고쳤습니다.

에이전트는 규칙으로만 답한다 — 모델 호출도, API 키도 없다

다섯 에이전트는 시나리오의 업무 규칙(가장 싼 숙소, 예산 안의 메뉴 …)을 계산하는 함수입니다. 같은 입력에는 같은 답이 나오므로 캡처를 다시 찍어도 글자까지 같고, 세 언어의 답을 나란히 견줄 수 있습니다.

  • LLM 이 들어간다면 그 자리는 실행기(AgentExecutor) 안입니다 — 파이썬 7부 3장, TypeScript 8부 3장, Go 9부 3장. 실행기 바깥의 와이어는 규칙이든 모델이든 같습니다(1부).
  • A2A 가 상대의 속을 묻지 않는다는 원칙(불투명 실행, 1부 2장)이 바로 이 바꿔 끼우기를 허락합니다.

기준 스펙은 A2A v1.0.1 — 규범은 proto, 어긋나면 둘 다 적는다

이 책이 따르는 스펙은 태그 v1.0.1 입니다. GitHub 릴리스는 2026-05-28 에 게시됐습니다. 스펙 저장소는 make docs 가 태그 묶음 하나로 받아 docs/spec/ 에 풉니다(저장소에는 넣지 않습니다).

읽는 곳이 책에서
specification/a2a.proto이름·필드·필수 여부 — 규범(1부 6장)
docs/specification.mdMUST·SHOULD 와 절 번호 — 슬라이드의 "§3.2.2" 는 이 파일의 절
세 SDK 의 설치본 소스실제로 무엇을 하나 — 기억이 아니라 설치된 파일과 캡처로
문서끼리도 어긋난다 — v1.0.1 저장소의 specification.md 머리에는 "Latest Released Version 1.0.0" 이 적혀 있는 식입니다. 이런 어긋남은 1부에 모았고, 스펙 본문과 proto 가 다를 때는 SDK 가 실제로 어떻게 하는지 캡처로 보였습니다(예: 13부 5장).

SDK 판은 셋이 제각각, 프로토콜 판은 셋 다 1.0 — 2026-10 기준

세 SDK 는 판을 따로 매기지만, 저마다 상수 하나로 "구현한 프로토콜 판" 을 밝힙니다. 아래는 3장의 판 확인 예제가 설치본에게 물어 찍은 줄입니다.

1장 퀴즈

Q. SDK 판은 1.2.2·1.3.0·v2.6.0 으로 제각각입니다. 그런데도 세 SDK 가 서로 말이 통하리라고 기대할 근거는 이 장의 캡처 어디에 있습니까?

A. 판 슬라이드의 프로토콜 줄입니다. 파이썬 PROTOCOL_VERSION_CURRENT, TypeScript A2A_PROTOCOL_VERSION, Go a2a.Version 이 모두 1.0 입니다. SDK 판은 라이브러리의 판이고, 서로 맞아야 하는 것은 프로토콜 판입니다. 요청마다 실려 가는 A2A-Version 헤더가 이 값이며(14부 3장), 실제로 통하는지는 16부의 3×3이 보입니다.

2장

시나리오 한눈에 — 보물상사 가을 워크숍

이야기 한 문장과 끝까지 돈 화면 → 다섯 에이전트 → 기능 지도 ①숙소·식사·교통 ②정산·기획·확장 → 정답 숫자와 골든 벡터 → 코드가 놓인 자리

총무팀의 한 문장이 다섯 에이전트를 움직인다

보물상사(가상의 회사) 총무팀이 기획 에이전트에게 "2026-10-30부터 1박 2일, 30명(채식 2명), 예산 6,000,000원, 출발 강남역" 이라고 말합니다. 기획 에이전트는 카드로 동료를 찾고, 숙소·식사·교통에 동시에 맡기고, 세 견적을 정산 에이전트에 넘겨 결재를 받은 뒤 계획서를 돌려줍니다. 아래는 15부에서 다섯 에이전트를 모두 띄워 끝까지 돌린 화면입니다.

중간의 > 승인 — 합계가 결재 기준(3,000,000원)을 넘어 작업이 AUTH_REQUIRED 에서 멈추자, 대본의 다음 줄 "승인" 을 같은 작업에 이어 보낸 것입니다. 이 한 판이 어떻게 짜였는지가 15부 6장입니다.

다섯 에이전트 — 넷은 한 가지 일, 기획은 그 넷의 클라이언트

에이전트마다 카드에 스킬 하나를 적습니다. 실행할 때는 --port P 로 127.0.0.1:P 에 붙고, 카드는 /.well-known/agent-card.json 에서 내줍니다.

정답 숫자는 정해져 있다 — 골든 벡터에 세 언어가 동의한다

코드는 세 언어가 같은 모양으로 놓였다 — 부마다 디렉터리 하나

어느 언어든 업무 규칙, 고정 자료 읽기, 골든 시험, 완성 에이전트가 같은 자리에 있습니다. 부(NN)마다 작은 예제는 ex/<언어>/NN/ 에 따로 둡니다.

  • 포트는 부마다 백 개씩 — NN부는 10000 + NN×100 + k. 0부는 10000–10099, 15부는 11500–11599 입니다. 범위 밖의 포트는 러너가 거절합니다.
  • 3~5부는 완성 에이전트를 블랙박스로 띄워 와이어만 읽고, 만드는 법은 6부(맨손)와 7~9부(SDK)가, 완성판의 해설은 15부가 맡습니다.

Q. 이야기 화면에서 기획 작업이 AUTH_REQUIRED 로 멈춘 까닭은 무엇입니까? 예산이 4,000,000원이었다면 어떻게 됐겠습니까?

A. 합계 4,842,000원이 결재 기준 3,000,000원을 넘었기 때문입니다(화면의 "팀장 결재가 필요합니다(합계 4,842,000원)"). 예산이 4,000,000원이면 합계가 예산을 넘습니다. 정산 규칙은 결재보다 예산 초과를 먼저 보므로 결재를 묻지 않고 거절합니다 — 기획 작업도 REJECTED "정산: 예산을 초과합니다" 로 끝나는 것을 15부 7장이 보입니다.

파이썬 — venv 하나에 a2a-sdk 1.2.2 와 선택 설치 묶음 셋

SDK 는 a2a-sdk[http-server,grpc,signing] 로 깝니다. 대괄호 안이 extra(선택 설치 묶음)로, 서버(Starlette)·gRPC·카드 서명에 필요한 것을 더 데려옵니다. 판 확인 예제는 설치본의 메타데이터에게 그 목록을 직접 묻습니다.

화면의 python — 캡처의 python 은 언제나 a2a/.venv 의 파이썬입니다. 러너가 그 파이썬을 가리키는 python 을 PATH 맨 앞에 둡니다. 서명 묶음(signing)이 데려오는 것은 pyjwt 하나뿐이고, Ed25519 에 쓰는 cryptography 는 google-auth 를 따라 들어와 있습니다(판은 requirements.txt 에 고정).

TypeScript — Node 24 가 .ts 를 그대로 돌리고, tsc 는 검사만 한다

Node 24 는 TypeScript 파일의 타입 표기를 지우고 바로 실행합니다(type stripping). 그래서 캡처의 명령은 node NN/x.ts 이고, 빌드 단계가 없습니다. 타입 검사는 따로 make ts-check(tsc -p ., noEmit)가 합니다.

  • 지울 수만 있는 문법만 씁니다 — tsconfig.json 의 erasableSyntaxOnly 가 enum·namespace 같은 "지우면 뜻이 바뀌는" 문법을 막습니다.
  • 아래 두 줄(찾는 이름·실제 내용)이 다음 슬라이드의 이야기입니다.

tsc 7 의 사연 — 안드로이드용 패키지 자리에 리눅스용을 별칭으로 넣었다

TypeScript 7 의 tsc 는 네이티브 실행 파일이고, typescript 패키지는 @typescript/typescript-${process.platform}-${process.arch} 라는 이름의 패키지에서 그것을 찾습니다(lib/getExePath.js). 이 기계의 Node 는 android·arm64 라고 답하는데, 그런 패키지는 선택 의존성 목록에 없습니다.

  • 별칭 — package.json 이 typescript-android-arm64 라는 이름에 npm:@typescript/typescript-linux-arm64@7.0.2 를 걸었습니다. 리눅스용 실행 파일이 이 기계에서 돕니다.
  • --force — 리눅스용 패키지는 제 package.json 에 "os": ["linux"] 를 적어 둬서, npm 은 android 에는 깔기를 거절합니다. 그 검사를 넘기는 것이 npm install --force 입니다.
보통의 리눅스·맥에서는 — 이 별칭이 필요 없습니다. 거기서는 typescript-linux-x64 따위가 선택 의존성으로 저절로 깔리므로, 별칭 줄을 지우고 --force 없이 깔면 됩니다.

Go — 모듈 하나(example.com/workshop)에 a2a-go v2.6.0

ex/go 가 모듈 하나이고, 예제마다 main 패키지 디렉터리 하나입니다. 판 확인 예제는 go build 가 바이너리에 새겨 둔 모듈 정보(debug.ReadBuildInfo)를 읽습니다.

  • 캡처에는 go run ./NN/x 로 보이지만, 러너는 먼저 go build -p 1 로 바이너리를 scratch/bin/ 에 지어 두고(입력이 그대로면 다시 짓지 않습니다) 그 바이너리를 띄웁니다.
  • android/arm64 — 이 책의 캡처는 갤럭시 폴드의 Termux 에서 찍었습니다. 메모리가 빠듯해 컴파일은 한 번에 하나(-p 1), 러너도 한 번에 하나만 돕니다.

3장 퀴즈

Q. npm ls 의 @typescript/typescript-android-arm64@npm:@typescript/typescript-linux-arm64@7.0.2 한 줄에서 앞의 이름은 누가 정한 것이고, 왜 하필 android-arm64 여야 합니까?

A. 앞의 이름은 tsc 가 찾는 이름입니다. typescript 패키지는 process.platform·process.arch 로 패키지 이름을 지어 실행 파일을 찾는데, 판 확인 캡처의 찾는 이름 @typescript/typescript-android-arm64 가 이 기계의 답입니다. 그 이름 아래 실제로 들어 있는 것은 실제 내용 @typescript/typescript-linux-arm64 7.0.2, 즉 별칭으로 넣은 리눅스용 패키지입니다.

명세 한 장이 터미널 여럿 — [터미널 N] 은 띄운 차례다

서버·탭·클라이언트가 함께 도는 실험은 실행 명세(ex/run/NN/*.run) 한 장으로 적습니다. 이 장의 실험은 숙소 에이전트(파이썬) 하나 앞에 와이어 탭을 세우고, 총무팀의 명령줄 클라이언트 ask 로 한 번 묻습니다.

  • serve·tap 줄마다 터미널을 하나씩 열어 1, 2… 를 매기고, run 줄은 모두 그다음 번호(여기서는 3) 한 터미널에서 차례로 칩니다. 명세의 동사는 다섯 — serve·tap·run·wait·restart.
  • 클라이언트 화면이 끝나면 터미널 1 (lodging) 출력 머리줄 아래에 서버가 찍은 것이, 와이어 (lodging-wire) 머리줄 아래에 탭이 적은 것이 모입니다. 슬라이드에는 흔히 그중 한 구역만 잘라 싣습니다.
  • 러너는 끝나면 성공이든 실패든 띄운 프로세스를 모두 내립니다(SIGTERM, 3초 뒤 SIGKILL).

와이어 탭은 받은 대로 넘기고, 정해 둔 것만 적는다

탭(tools/wiretap.py)은 표준 라이브러리만으로 만든 역방향 프록시입니다. 요청과 응답을 바꾸지 않고 넘기면서, 주고받음 하나를 →(요청)·←(응답) 덩어리로 적습니다. 처음 쓴 곳은 2부 1장입니다.

적는 것규칙
헤더여덟만, 이 차례·이 철자로 — Content-Type, A2A-Version, A2A-Extensions, Authorization, Accept, X-A2A-Notification-Token, WWW-Authenticate, Location
JSON 본문두 칸 들여 펴고, 키 차례는 보낸 그대로(예외는 뒤에서)
그 밖의 본문글은 그대로, 이진은 <N bytes>
SSE 응답모으지 않고 이벤트 하나가 끝날 때마다 흘려 보내며 적는다 — data: 의 JSON 도 편다
안 적는 것 — Host·User-Agent·Date·Content-Length·Transfer-Encoding 같은 운반용 머리. 길이나 클라이언트 이름이 언어마다 달라 세 언어의 와이어를 나란히 견줄 수 없게 만들기 때문입니다. Go 가 A2a-Version 으로 바꿔 쓰는 철자도 탭이 A2A-Version 으로 맞춰 적습니다. Authorization 값은 그대로 적습니다 — 이 책의 토큰은 모두 이 기계 안의 가짜입니다.

--url 로 카드에 탭 주소를 적게 하면 대화 전체가 탭을 지난다

서버는 10050 에서 듣지만, --url http://127.0.0.1:10001/ 로 띄웠으므로 카드에는 탭의 주소가 적힙니다. 클라이언트는 카드의 url 로 말을 걸므로, 카드를 읽은 뒤의 SendMessage 도 탭을 지납니다.

  • --url 이 없으면 카드는 서버 자신의 주소(10050)를 알리고, 클라이언트는 카드만 탭으로 받은 뒤 서버로 곧장 갑니다 — 와이어에 카드 한 번만 남습니다. 그 실험과 "카드의 url 은 바깥 주소" 라는 규칙은 3부 4장의 몫입니다.
  • 다섯 에이전트 모두 --port P 와 --url U 를 받습니다(2장).

와이어 속의 <id1> — 같은 번호는 같은 값, 그 이상의 뜻은 없다

SendMessage 의 요청과 응답에서 식별자와 시각만 골랐습니다. 번호는 캡처 파일 하나 안에서 UUID 가 처음 나온 차례입니다.

  • "id": "<id1>" 이 요청 끝과 응답 끝에 함께 있습니다 — 파이썬 SDK 클라이언트는 JSON-RPC id 로 UUID 를 쓰고, 서버는 그 값을 그대로 돌려줍니다(2부 3장).
  • 서버가 지은 작업 id 가 <id2>, 맥락이 <id3> 이고, history 의 메시지에도 같은 둘이 taskId·contextId 로 붙어 있습니다.
  • 다른 캡처의 <id1> 은 이것과 아무 관계가 없습니다. 번호는 "이 파일 안에서 같은가" 만 알려 줍니다.

정규화 표 — 캡처에서 바꾸는 것은 이 다섯 가지뿐이다

실행마다, 기계마다 달라지는 글자를 그대로 두면 --check 가 매번 실패합니다. 러너(tools/a2arun.py 의 RULES)는 캡처 파일 하나를 통째로 받아 이 차례로 바꾸고, 그 밖의 글자는 건드리지 않습니다.

Q. 와이어 속의 식별자에서 history 메시지의 taskId 가 <id2> 라는 것만으로, 그것이 응답 머리의 작업 id 와 같은 값이라고 말할 수 있습니까? 두 캡처 파일에 똑같이 <id2> 가 있다면 어떻습니까?

A. 한 파일 안이라면 그렇습니다. 러너는 캡처 파일 하나를 통째로 정규화하며, 같은 UUID(대소문자 무시)에는 언제나 같은 번호를 줍니다 — 그래서 요청과 응답의 "id": "<id1>" 도 같은 값입니다. 서로 다른 파일의 <id2> 는 각 파일에서 "두 번째로 처음 나온 UUID" 일 뿐이라 같은 값이라는 보장이 없습니다.
