클라이언트 — a2aclient 와 반복자

메서드 열넷과 공장의 옵션 → 설정은 세 곳 → 해석기와 공장 → 막는 호출은 값 하나 → 스트림은 range → 스트림을 안 하는 카드 → 우리 http.Client 와 가로채기 → 판 머리글은 둘이 된다 → 카드만 받기 → 오류 넷 → 오류는 errors.Is 로 → 모르는 필드 실험 → 클라이언트는 너그러웠다 → 기획 에이전트의 위임 → 정리

클라이언트 메서드 열하나가 JSON-RPC 메서드와 짝이고, 셋은 와이어가 없다

파이썬(7부)·TS(8부)처럼 SDK 에게 직접 보내게 했습니다. 요청 본문의 method 만 적는 가짜 RoundTripper 를 끼우고, *a2aclient.Client 의 메서드를 reflect 로 모두 돌며 불렀습니다. 서버는 없습니다.

  • 메서드 이름이 와이어와 갈리는 것은 푸시 넷입니다 — …PushConfig 가 …PushNotificationConfig 로 나갑니다. 서버 처리기의 이름과 같은 줄임입니다(4장). 스트림 둘(SendStreamingMessage·SubscribeToTask)은 iter.Seq2[a2a.Event, error] 를 돌려줘 range 로 돌아야 요청이 나갑니다.
  • Card·UpdateCard·Destroy 는 클라이언트 자신의 일입니다. Destroy 가 파이썬의 close 자리이고, UpdateCard 는 새 카드에 지금 쓰는 인터페이스가 그대로 있을 때만 받아들입니다(a2aclient/client.go:218).

설정은 세 곳 — 공장의 옵션, Config 네 칸, 호출마다의 context

파이썬은 ClientConfig 한 곳에(7부), TS 는 셋으로(8부) 나눴습니다. Go 는 TS 와 같은 세 겹이고, 호출마다의 값은 context.Context 에 싣습니다. 앞 프로그램의 끝은 FactoryOption 을 돌려주는 함수 목록입니다.

막는 호출을 바꾸는 칸이 없다 — 파이썬의 streaming, TS 의 polling 같은 칸이 Config(a2aclient/client.go:29)에 없습니다. 스트림은 부르는 메서드로 고르고, returnImmediately 는 요청의 Config 에 직접 적습니다. 요청에 설정이 없고 Config 도 비었으면 configuration 을 아예 싣지 않습니다(withDefaultSendConfig, :244 — 6부에서 본 "Go 는 뺀다").

카드는 해석기가 받고, 클라이언트는 공장이 짓는다 — Go 는 두 단계를 따로 부른다

상대는 7장에서 완성할 숙소 에이전트(agents/lodging, 탭 뒤)입니다. 파이썬의 create_client(url), TS 의 createFromUrl 처럼 URL 하나로 끝내는 함수가 없어, 받기와 짓기를 차례로 부릅니다.

막는 호출은 값 하나 — SendMessageResult 를 타입 스위치로 가른다

-no-stream 이면 SendMessage 를 씁니다. 답을 받은 뒤 같은 작업을 GetTask 로 한 번 더 읽었습니다.

  • 돌려받는 a2a.SendMessageResult 는 *a2a.Task 와 *a2a.Message 만 들어가는 닫힌 인터페이스입니다(2장). TS 처럼 감싸이지 않은 값 하나이고, 가르는 법은 "필드 유무" 대신 타입 단언(res.(*a2a.Task))입니다.
  • 그 값이 a2a.Event 이기도 해서 스트림과 같은 show 로 찍었습니다. Task·Message 가 두 인터페이스를 다 구현하기 때문입니다(a2a/core.go).

스트림은 이벤트를 하나씩 그대로 준다 — range 를 돌면 요청이 나간다

같은 요청을 SendStreamingMessage 로 보냈습니다. 돌려받은 반복자를 for ev, err := range 로 돌며 이벤트마다 show 를 부릅니다.

세 SDK 가 같은 모습 — 첫 Task 는 SUBMITTED·아티팩트 0개이고, 끝난 모습은 GetTask 로 다시 읽어야 보입니다(7부·8부). 반복자는 서버의 실행기와 같은 iter.Seq2 라(3장), 받는 쪽이 break 하면 SDK 가 응답 본문을 닫습니다. 오류는 둘째 값으로 오고 그 뒤로는 이벤트가 없습니다.

스트림을 안 하는 카드에 SendStreamingMessage — SDK 가 SendMessage 로 바꿔 보낸다

같은 스트림 코드로 5장의 2단계 견적 서버를 불렀습니다. 그 카드는 capabilities.streaming 이 없습니다.

  • SendStreamingMessage 는 카드에 Streaming 이 없으면 전송의 SendMessage 를 부르고 그 답을 이벤트 하나로 냅니다(a2aclient/client.go:110). TS 와 같은 판단이고(8부), 그래서 Go 의 ask CLI 도 늘 스트림 쪽을 부릅니다(agents/ask 의 send).
  • 막는 호출에는 Accept 머리글이 없습니다. 스트림 요청에만 Accept: text/event-stream 을 답니다(a2aclient/jsonrpc.go:146).

갈고리 둘 — 전송에 우리 http.Client 를, 모든 호출에 가로채기를

파이썬은 httpx 연결을(7부), TS 는 fetchImpl 을(8부) 넘겼습니다. Go 에서는 WithJSONRPCTransport(*http.Client) 이고, 그 클라이언트의 RoundTripper 가 보내는 머리글을 그대로 봅니다. 상대는 받은 것을 돌려주는 5장의 실험 서버입니다.

  • a2aclient.CallInterceptor 는 Before·After 둘이고, PassthroughInterceptor 를 박아 넣으면 하나만 써도 됩니다. Before 가 결과나 오류를 돌려주면 전송을 부르지 않고 그것으로 끝납니다(a2aclient/middleware.go:100) — 파이썬·TS 의 early_return 자리입니다.
  • 머리글은 req.ServiceParams 에 Append 합니다. 열쇠는 소문자로 바뀌고, 전송이 값마다 Header.Add 로 답니다(a2aclient/jsonrpc.go:98).

손으로 적은 판 0.3 은 덮이지 않았다 — A2A-Version 이 둘 실려 나갔다

  • 가로채기는 판 값으로 ["0.3"] 하나를 봤는데, 와이어에는 "0.3" 과 "1.0" 이 함께 나갔습니다. SDK 는 판을 serviceParams["A2A-Version"] 에 대문자 그대로 넣고(a2aclient/client.go:270), AttachServiceParams 는 열쇠를 소문자 "a2a-version" 으로 넣습니다 — 한 맵에 두 열쇠가 생겨 둘 다 나갑니다. 차례는 맵을 도는 차례라 실행마다 다릅니다(그래서 정렬해 찍었습니다).
  • TS 는 호출의 판을 지우고 1.0 으로 덮었습니다(8부). Go 에서 판 머리글을 손으로 다는 일은 하지 않습니다. 판은 고른 인터페이스의 protocolVersion 이 정합니다. 이 서버(Go)는 어차피 판을 읽지 않습니다(5장).

카드만 받을 때는 agentcard.Resolver — 판 머리글 없이, file:// 도 읽는다

카드를 먼저 모아 고르는 기획 에이전트(15부)가 이 길을 씁니다. 숙소 에이전트 앞 탭이 본 첫 카드 요청과, 오류 ②(조금 뒤)의 카드 요청입니다. 탭은 정해 둔 머리글이 있으면 요청 줄 아래에 적습니다.

  • 카드 GET 에는 A2A-Version 도 Accept 도 없습니다(fetchCard, agentcard/resolver.go:150) — 3부에서 본 그대로입니다. 파이썬 공장·TS 해석기는 판 머리글을 달았습니다(7부·8부). 붙이려면 Resolve(ctx, url, agentcard.WithRequestHeader(…)) 입니다.
  • ②의 GET /nothing/ 은 오타가 아닙니다. 기본 주소에 경로가 있으면 해석기는 그 주소 자체를 카드 주소로 씁니다(buildURL, :127 — 3부). 주소가 file:// 이면 디스크의 카드 파일을 읽습니다(:106) — 세 SDK 가운데 Go 해석기만의 길입니다. 서명 검사(Verifier)는 12부입니다.

오류 넷을 일부러 — 카드가 없다, 카드 경로가 없다, 작업이 없다, 보낼 곳이 없다

7부·8부와 같은 넷입니다. Go 에는 예외가 없으니 오류 값의 겉 타입과, errors.Is·errors.As 로 가를 수 있는 것을 찍었습니다.

오류는 사슬이다 — 서버 답은 a2a 표지 오류로, 카드 404 는 타입으로, 나머지는 글로

  • ③은 JSON-RPC 오류 -32001 을 전송이 *a2a.Error 로 되살린 것이고, 안쪽 Err 가 표지 오류 a2a.ErrTaskNotFound 라 errors.Is 가 맞습니다(FromJSONRPCError, internal/jsonrpc/jsonrpc.go:89). 서버가 짓는 그 표지 오류(4장)와 같은 값입니다.
  • ①은 fmt.Errorf("…%w") 사슬 끝의 syscall.ECONNREFUSED 까지 errors.Is 로 닿습니다. ②는 카드 해석기의 *agentcard.ErrStatusNotOK 라 상태 코드가 필드에 있습니다. ④만 "unexpected HTTP status: 404 Not Found" 글 한 줄이고(a2aclient/jsonrpc.go:125), 상태 코드를 꺼낼 타입이 없습니다.
세 SDK — 파이썬은 A2AClientError 와 서버 오류 클래스(7부), TS 는 A2AError 하나와 맨 Error(8부)였습니다. Go 는 클래스 대신 사슬을 풀어 봅니다 — 다시 시도할지는 ① 같은 연결 오류를 errors.Is 로 고릅니다.

같은 실험을 Go 클라이언트로 — 8부의 실험 서버에 일곱 가지

파이썬 클라이언트는 모르는 필드 하나에 멈췄고(7부), TS 는 버렸습니다(8부). 서버는 8부의 TS 실험 서버를 그대로 띄웠습니다. 받은 글(실험 이름)대로 Task·status·result·봉투 겉에 모르는 필드를 끼우고, enum 은 없는 상태를, error 는 막는 호출에 JSON-RPC 오류를, 스트림에 Task 다음의 오류 이벤트를 보냅니다.

클라이언트는 너그러웠다 — 모르는 필드는 버리고, 모르는 상태는 문자열 그대로

  • 여섯 모두 받았습니다. encoding/json 은 구조체에 없는 키를 버립니다(2장) — §5.7 의 "SHOULD ignore" 쪽으로 TS 와 같습니다. 카드의 createdAt 도 구조체에 자리가 없어 남지 않습니다(TS 해석기는 남겼습니다).
  • TASK_STATE_PAUSED 는 오류도 -1 도 아니고 그 문자열 그대로입니다. enum 이 문자열 타입이기 때문이고(2장), 상태로 가르는 switch 는 default 를 꼭 둡니다.
  • 스트림 도중의 오류도 막는 호출과 같은 *a2a.Error 이고 errors.Is 가 맞습니다. TS 는 맨 Error 로 감싸 cause 를 봐야 했습니다(8부). 오류 앞의 Task 이벤트는 받은 그대로 먼저 나옵니다.

기획 에이전트의 위임 — 카드로 바로, 막는 호출, 토큰은 우리 http.Client 가

완성 에이전트 가운데 클라이언트를 쓰는 것은 기획 에이전트입니다(15부). 동료에게 일을 맡기는 부분이 이 장의 손잡이를 거의 다 씁니다.

  • 모아 둔 카드로 NewFromCard, 막는 호출 SendMessage, 다 쓰면 defer client.Destroy() 입니다. 토큰은 가로채기 대신 common.HTTPClient(token) 의 RoundTripper 가 요청마다 Authorization 을 답니다(agents/common/client.go).
  • 그 클라이언트는 Timeout 을 두지 않습니다. SDK 기본 HTTP 클라이언트는 Timeout: 3분(a2aclient/transport.go:26)이라 본문 읽기까지 재므로, 3분 넘게 열린 스트림을 끊습니다. 그래서 응답 머리글까지만 30초를 기다립니다(ResponseHeaderTimeout).

6장 퀴즈

Q. 8부의 퀴즈와 같은 코드를 Go 로 옮겼습니다 — if errors.Is(err, a2a.ErrTaskNotFound) { 포기 } else { 다시 시도 }. 상대가 없는 작업이라고 답할 때, 이 코드는 SendMessage 와 SendStreamingMessage 에서 각각 포기합니까?

A. 둘 다 포기합니다. 막는 호출의 error 도, 스트림 반복자가 둘째 값으로 낸 오류도 같은 *a2a.Error 이고 안쪽이 ErrTaskNotFound 입니다(strict 의 두 error 줄, ErrTaskNotFound=true). TS 는 스트림 쪽을 맨 Error 로 감싸 cause 까지 봐야 했지만, Go 의 SSE 해석은 오류 이벤트를 FromJSONRPCError 로 바로 되살립니다.

시험 — go test 로, SDK 서버를 프로세스 안에서

이 모듈의 시험 도구 → 본보기는 골든 시험 → package main 은 import 할 수 없다 → 시험 틀 → 시험 넷 → go test 를 프로그램으로 → 초록불 → 3단계에 돌리면 빨간불 → HTTP 층은 소켓 없이, 클라이언트는 빈 포트로 → 세 층의 결과 → 시험에서 조심할 것 → 정리

시험 도구는 표준 라이브러리 — testing 과 net/http/httptest, testify 는 없다

무엇으로 시험할지 고르기 전에 깔려 있는 것을 물었습니다. 파이썬에서 unittest 를(7부), TS 에서 node:test 를(8부) 고른 것과 같은 판단입니다.

  • go test 와 testing 패키지가 실행기·하위 시험(t.Run)·정리(t.Cleanup)를 다 갖고 있고, HTTP 시험 도구 httptest 도 표준입니다. 업무 규칙 시험(make golden)이 이미 이것으로 돕니다.
  • go-cmp·goleak 은 SDK 자신의 시험이 쓰는 모듈이라 go.sum 에 해시가 있지만, 우리 코드는 가져오지 않습니다. 단언 도우미 없이 if … { t.Errorf(…) } 로 씁니다.

본보기는 업무 규칙의 골든 시험 — 사례마다 t.Run 하나

세 언어의 업무 규칙은 같은 골든 파일을 읽어 시험합니다(SCENARIO §4). Go 쪽 workshop/domain_test.go 의 중심입니다.

  • 사례 하나가 틀려도 나머지를 계속 봅니다 — 파이썬의 subTest, TS 의 t.test 자리가 t.Run(이름, …) 입니다. 하위 시험 이름의 빈칸은 go test 가 _ 로 바꿔 적습니다(곧 결과에서 봅니다).
  • 골든 파일이 기대값의 하나뿐인 원본이라, 에이전트 시험에도 숫자를 다시 적지 않습니다.

package main 은 import 할 수 없다 — 시험 파일을 그 패키지 안에 둔다

완성판의 실행기 executor 는 package main 안의 소문자 이름이라 밖에서 쓸 길이 없습니다(7장). Go 의 답은 시험 파일(_test.go)을 같은 디렉터리·같은 패키지에 두는 것입니다. 이 책은 3~6부가 띄운 그 디렉터리에 파일을 더하지 않으려고, go test -overlay 로 시험할 때만 놓이게 했습니다.

  • -overlay 는 go 명령에 "디스크의 이 경로에 저 파일이 있는 것으로 하라" 는 표를 주는 플래그입니다. 09/testdata/lodging_test.go 가 agents/lodging/lodging_test.go 인 것처럼 컴파일되어, 소문자 executor{} 가 보입니다. testdata 디렉터리는 go 명령이 패키지로 보지 않으므로 평소 빌드에 끼지 않습니다.
  • 보통의 프로젝트라면 agents/lodging/main_test.go 를 그냥 둡니다 — TS 의 mock.module(8부) 같은 우회가 필요 없는 것이 Go 의 길입니다. 3단계는 그렇게 했습니다(09/step3_ask/main_test.go, 조금 뒤).

시험 틀 — 실행기를 받는 함수 하나, 시험마다 새 처리기, 말 한마디는 say()

4장에서 HTTP 없이 처리기를 부른 방법을 시험 틀로 옮겼습니다. 묶음은 보통 패키지 09/lodgingsuite 에 두어, 완성판과 3단계의 시험 파일이 함께 import 합니다.

  • a2asrv.NewHandler(exec) 만으로 메모리 저장소가 붙습니다(4장). 호출 맥락은 처리기가 익명으로 붙이니 context.Background() 에서 시작합니다. 보낼 messageId 는 시험이 정합니다(m-1…).
  • Go 처리기는 침묵하는 실행기를 영영 기다리므로(4장) 호출마다 context.WithTimeout 을 씌웠습니다. 파이썬의 asyncio.wait_for 자리입니다.

시험 넷 — 골든, 첫 되물음, 이어 말하기, 사용자 말만 듣기

7·8부와 같은 넷입니다. 시험 이름도 그대로 영어로 두었습니다.

  • 시험 목록은 맵이 아닌 슬라이스입니다 — 맵으로 두면 도는 차례가 실행마다 바뀌어 결과의 차례도 흔들립니다(7장과 같은 까닭).
  • 기대값의 수는 2_100_000.0, 박 수는 1.0 입니다. DataPart 의 수가 float64 라(2장), any 끼리의 != 는 형까지 봅니다 — int 2100000 과는 다릅니다.

go test 를 프로그램으로 — -json 을 읽어 걸린 시간 없이 찍는다

go test 는 패키지마다 걸린 시간(ok … 0.231s)을 찍어 실행마다 글자가 달라집니다. 파이썬의 NoClock(7부), TS 의 보고기(8부)처럼, go test -json 이 내는 이벤트를 읽어 우리 모양으로 찍습니다.

하는 일은 go test 와 같다 — -p 1(이 기계는 빌드 하나씩), -count=1(시험 결과 캐시를 쓰지 않는다)을 붙여 부를 뿐입니다. 시험이 찍는 에이전트 로그([숙소] …)는 버리고, t.Errorf 가 남긴 들여 쓴 줄만 그 시험 아래에 붙입니다. 시험 결과 캐시는 Go 만의 함정입니다 — 입력이 같으면 go test 는 돌리지 않고 지난 결과를 (cached) 로 보여 줍니다.

HTTP 층은 소켓 없이 — httptest.NewRecorder 가 http.Handler 의 답을 받아 적는다

처리기 시험은 JSON-RPC 해석·직렬화를 지나지 않습니다. Go 의 SDK 처리기는 모두 http.Handler 라(5장), 파이썬의 TestClient 처럼 포트 없이 ServeHTTP 를 바로 부를 수 있습니다.

  • app 은 common.Serve 의 짜임을 옮겨 적었습니다. Serve 가 짓기와 듣기(ListenAndServe)를 한 함수에서 하기 때문입니다 — 새로 짓는다면 http.Handler 를 돌려주는 함수를 따로 두는 편이 낫습니다.
  • httptest.NewRequest 로 요청을 짓고 NewRecorder 에 답을 받습니다. 네트워크도 고루틴 경계도 없이, 같은 함수 호출입니다.

와이어 시험 둘과 SDK 클라이언트 시험 하나 — 클라이언트는 httptest.NewServer 의 빈 포트로

세 층이 모두 초록 — 처리기, 와이어, 클라이언트

  • 와이어 시험은 결과의 "TASK_STATE_COMPLETED", 견적 "total":2100000 이 JSON 에서 정수로 나가는지, 모르는 메서드의 -32601 을 봤습니다. Go 의 float64 2100000 은 encoding/json 이 지수 없이 정수 꼴로 씁니다.
  • 클라이언트 시험은 카드를 받아 스트림으로 묻고, 이벤트가 SUBMITTED Task → INPUT_REQUIRED 상태 갱신 차례인지 봤습니다(6장). httptest.NewServer 는 127.0.0.1 의 빈 포트에 같은 프로세스 안에서 듣습니다 — 파이썬의 ASGITransport(7부)와 달리 소켓은 진짜입니다. 카드 url 이 그 주소여야 해서, 처리기를 서버가 뜬 뒤에 짓습니다.

서버 가로채기 둘과 일찍 답하기 — Before 가 결과를 돌려주면 실행기는 돌지 않는다

9장의 실험 서버(09/only_server) 하나에 이 장의 손잡이를 경로마다 하나씩 달았습니다. 먼저 /audit 입니다. 이름을 찍는 가로채기 둘과, "핑" 에 처리기 없이 "퐁" 으로 답하는 가로채기를 차례로 답니다.

Before 는 단 차례로, After 는 거꾸로 — 일찍 답한 호출에도 바깥의 After 가 돈다

  • 두 요청 모두 바깥 → 안쪽 으로 들어가 안쪽 → 바깥 으로 나왔습니다(middleware.go:90 의 주석 그대로). "핑" 은 셋째 가로채기가 퐁 을 돌려줘 메아리 실행기가 돌지 않았는데도, 그때까지 지난 가로채기의 After 가 거꾸로 돌았습니다(interceptBefore, intercepted_handler.go:231).
  • 일찍 낸 답은 처리기를 거치지 않으니 우리가 지은 그대로입니다 — contextId 가 없습니다. 메아리 실행기의 답에는 ec.ContextID 로 채운 contextId 가 있었습니다(3장). 캐시·점검 중 응답처럼 일찍 답할 때는 필요한 id 를 가로채기가 채웁니다.

panic 하는 실행기 — 서버는 살아남고, 처리기 옵션으로 오류를 정한다

Go 실행기는 예외 대신 panic 으로 무너질 수 있습니다. 첫 이벤트도 내기 전에 panic 하는 실행기를 /panic(옵션 없이)과 /panic2(WithExecutionPanicHandler)에 달고, SDK 클라이언트로 두 번·한 번 물었습니다.

옵션이 없으면 panic 의 스택 21줄이 그대로 클라이언트에게 간다

  • 셋 다 -32603 이고, 셋째 요청이 답을 받았으니 서버는 죽지 않았습니다. SDK 가 실행기 고루틴의 panic 을 recover 하기 때문입니다(internal/taskexec/execution_handler.go:199).
  • 옵션이 없으면 그 값을 fmt.Errorf("event producer panic: %v\n%s", r, debug.Stack()) 로 지어 돌려주고, 표지 오류가 아닌 오류는 글 그대로 -32603 의 message 가 됩니다(4장). 서버 소스 경로와 고루틴 스택이 상대 에이전트에게 가는 것입니다. /panic2 처럼 처리기를 두면 우리가 고른 글 한 줄만 갑니다.
운영에서는 늘 단다 — WithExecutionPanicHandler 로 까닭을 서버 기록에만 남기고, 상대에게는 a2a.ErrInternalError 를 감싼 짧은 글을 줍니다. 같은 일을 HTTP 층에서 하는 WithTransportPanicHandler(a2asrv/transport.go:30)도 있습니다 — 이쪽은 없으면 panic 을 다시 일으킵니다(jsonrpc.go:89).

확장을 아래로 넘기는 짝 — 서버 쪽이 받아 두고, 클라이언트 쪽이 싣는다

기획 에이전트처럼 받은 일을 다른 에이전트에 맡길 때, 사용자가 켠 확장(14부의 예산 확장)과 그 metadata 를 아래로 넘겨야 할 때가 있습니다. /relay 는 받은 말을 아래 에이전트 둘에게 넘깁니다 — 카드 하나는 예산 확장을 적었고, 하나는 적지 않았습니다. 아래 에이전트(/who)는 받은 확장과 metadata 의 열쇠를 말합니다.

짝의 일 — 서버 쪽 a2aext.NewServerPropagator 가 Before 에서 요청의 A2A-Extensions 값과, 요청한 확장 URI 와 같은 이름의 metadata 를 맥락에 넣어 둡니다. 실행기가 그 맥락(ctx)으로 부른 클라이언트의 NewClientPropagator 가 그것을 꺼내, 상대 카드가 적은 확장만 머리글과 metadata 에 싣습니다(a2aext/propagator.go:148·:180). 실행기 ctx 는 요청 맥락을 WithoutCancel 로 이은 것이라 값이 남아 있습니다(internal/taskexec/local_manager.go:182).

두 줄로 보낸 확장 — 예산을 적은 카드에만 머리글과 metadata 가 넘어갔다

둘째 요청은 A2A-Extensions 를 두 줄로 적었습니다(rpc/relay2.headers — 예산 확장 한 줄, 다른 확장 한 줄. 탭은 같은 이름의 머리글을 한 줄만 적습니다). metadata 에는 예산 확장 이름의 값과 note 가 있습니다.

  • 예산 확장을 적은 카드로 간 요청에만 A2A-Extensions 머리글과 metadata 의 예산 값이 실렸고, note 는 확장 이름이 아니라 빠졌습니다. 다른 확장(other.example)은 두 카드 어디에도 없어 넘어가지 않았습니다.
  • relay 의 실행기는 머리글도 metadata 도 손대지 않았습니다. 기본 조건(nil 설정)은 "요청된 확장이고, 상대가 적은 확장" 이고, 바꾸려면 ClientPropagatorConfig·ServerPropagatorConfig 의 조건 함수를 줍니다.

스펙대로 쉼표 한 줄로 보내면 아무것도 넘어가지 않는다

첫째 요청은 같은 두 확장을 스펙의 꼴대로 한 줄에 쉼표로 적었습니다(rpc/relay.headers). 아래 에이전트 둘의 답입니다.

  • 두 카드 모두 확장=[] metadata=[] 입니다. Go 서버의 RequestedURIs() 는 머리글 값을 쉼표로 나누지 않고 받은 줄 그대로 돌려줍니다(a2asrv/extensions.go:64). 그래서 "…/budget/v1, https://other.example/ext/x" 가 통째로 한 URI 가 되어, 카드의 확장과도 metadata 의 열쇠와도 맞지 않습니다.
  • 스펙은 여러 값을 "SHOULD be comma-separated in a single header field" 라 하고(§9.2), 머리글을 "comma-separated list" 로 정합니다(§14.2.2). 파이썬 SDK 는 쉼표로 나눕니다(a2a/extensions/common.py:7). Go 클라이언트는 거꾸로 값마다 머리글 줄을 하나씩 답니다(Header.Add, a2aclient/jsonrpc.go:98) — Go 끼리는 맞지만, 스펙대로 보내는 상대에게서 받은 확장은 놓칩니다.

Q. 기획 에이전트(Go)에 a2aext 의 짝을 달았는데, 다른 SDK 의 클라이언트가 스펙대로 A2A-Extensions: …/budget/v1, …/other 를 한 줄로 보내자 예산 metadata 가 숙소 에이전트에 넘어가지 않았습니다. 왜입니까? 같은 두 확장을 Go 클라이언트가 보냈다면 어땠습니까?

A. Go 서버의 RequestedURIs() 가 쉼표를 나누지 않아, 두 URI 가 붙은 한 줄이 통째로 한 확장 이름이 되기 때문입니다. 서버 쪽 짝은 그 이름과 같은 metadata 열쇠만 넘기므로 예산 값이 걸러졌습니다(쉼표 한 줄, 두 카드 모두 확장=[] metadata=[]). Go 클라이언트는 값마다 머리글 줄을 따로 달아 보내므로 넘어갑니다(두 줄, 예산을 적은 카드에 metadata=[…/budget/v1]).
