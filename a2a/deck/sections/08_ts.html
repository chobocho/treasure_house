1장

패키지 지도 — 설치본에서 읽는다

진입점 열다섯과 선택 peer → 번들 열다섯에 원본 97개 → 번들마다 다른 사본 → 서버 쪽 칸 → 요청 하나가 지나는 길 → 완성 에이전트가 쓰는 이름 28개 → 이름에서 파일·줄 찾기 → 정리

@a2a-js/sdk 는 진입점 열다섯 — 늘 깔리는 의존은 jose 하나다

파이썬 SDK 가 extra(선택 설치 묶음)로 나눈 것(7부)을 이 SDK 는 package.json 의 exports 진입점(subpath)으로 나눕니다. 진입점마다 번들 파일이 import 하는 바깥 패키지를 모으고, 이 node_modules 에 있는지 표시했습니다(O 있음, . 없음).

  • express·gRPC·DB 드라이버는 모두 선택 peer 입니다. 이 책은 express 와, 13부의 gRPC 바인딩을 위한 @grpc/grpc-js·@bufbuild/protobuf 를 깔았고(ex/ts/package.json, 13부), DB 드라이버는 깔지 않았습니다. 12부까지는 ./server/express 만 씁니다.
  • jose 는 카드 서명(12부) 때문에 들어 있습니다. 몸통(.)에 generateAgentCardSignature 가 있어서입니다.

dist 는 번들 열다섯 — 원본 97개를 진입점마다 한 파일에 담았다

설치본에는 src/ 가 없고 dist/ 의 번들만 있습니다. 번들 도구(tsup)가 원본 파일마다 남긴 // src/… 머리 줄로 어느 원본이 어느 번들에 들었는지 셌습니다.

  • 서버를 세우는 데 드는 것은 ./server(3,885줄)와 ./server/express(6,342줄)입니다. 이 부 3~5장이 여기서 삽니다.
  • compat/v0_3 무리 여섯이 v0.3 피어와 말하기 위한 계층입니다(9장, 14부). 파이썬 SDK 의 compat/(7부)와 같은 몫입니다.

번들마다 클래스의 사본이 따로 있다 — 오류만은 표식으로 instanceof 를 지킨다

번들은 서로를 import 하지 않습니다(앞의 표에 @a2a-js/sdk/… 가 하나도 없습니다). 그래서 오류 클래스는 몇 벌씩 들어 있습니다 — src/errors/base.ts 는 번들 14개에 있습니다.

클래스는 달라도 instanceof 는 참 — 처리기(./server 번들)가 던진 TaskNotFoundError 와 ./errors 에서 가져온 것은 다른 클래스입니다. 그래도 instanceof 가 맞는 것은 A2AError 가 Symbol.for("@a2a-js/sdk.A2AError") 표식과 Symbol.hasInstance 로 이름을 견주기 때문입니다(dist/errors/index.js:4, 주석: "immune to this module being duplicated across entry-point bundles"). err.constructor === 로 견주는 코드는 틀립니다.

이름만 같은 우리 클래스는 SDK 오류가 아니다 — -32603 이 된다

표식이 하는 일을 거꾸로 확인했습니다. SDK 의 TaskNotFoundError 와, name 만 같게 지은 우리 클래스를 JSON-RPC 오류로 옮기는 함수(JsonRpcTransportHandler.mapToJSONRPCError)에 넣었습니다.

오류는 SDK 에서 가져와 던진다 — 실행기에서 A2A 오류를 내려면 @a2a-js/sdk/errors 의 클래스를 씁니다. 표식이 없는 예외는 모두 -32603 Internal error 입니다. 오류 클래스와 코드 표는 4장에서 폅니다.

서버 쪽 칸 — 우리가 채우는 칸은 실행기 하나다

./server 와 ./server/express 번들의 // src/server/… 머리 줄을 하는 일로 묶어, 이 부의 장과 짝지었습니다. 파이썬 SDK 의 여섯 칸(7부)과 거의 같은 나눔입니다.

완성 에이전트가 쓰는 SDK 이름은 28개뿐이다

완성 에이전트(agents/*.ts)의 import { … } from "@a2a-js/…" 를 모아, 이름마다 몇 파일이 쓰는지 셌습니다(파이썬은 38개 — 7부).

  • 타입 쪽은 몸통(@a2a-js/sdk)에서, 서버 쪽은 ./server 와 ./server/express 에서 가져옵니다. 파이썬 SDK 의 TaskUpdater·new_* 도우미에 해당하는 이름이 없습니다 — 그 몫은 우리 agents/common.ts 가 짊어집니다(3장).
  • ./client 넷은 기획 에이전트와 ask CLI 가 씁니다(6장).

이름에서 파일과 줄로 — 번들의 줄과, 그 위의 원본 이름

편집기의 "정의로 가기" 는 a2a-CJdXl9vi.d.ts 같은 해시 이름의 타입 파일로 갑니다. 동작을 읽으려면 번들(.js)에서 정의 줄을 찾고, 그 위의 // src/… 머리 줄로 원본 파일 이름을 압니다.

인터페이스는 .js 에 없다 — AgentExecutor 처럼 타입만 있는 이름은 번들에 흔적이 없어 .d.ts 에서 찾았습니다. 이 부가 인용하는 줄 번호(dist/server/index.js:2702 같은)는 모두 이 방법으로 찾은 것입니다.

1장 퀴즈

Q. 클라이언트 코드에서 SDK 가 던진 오류를 if (err.constructor === TaskNotFoundError) 로 가르려고 TaskNotFoundError 를 @a2a-js/sdk/errors 에서 가져왔습니다. 이 검사는 맞게 동작합니까? 맞게 고치면 어떻게 씁니까?

A. 동작하지 않습니다. 오류를 던진 번들(./client, 서버라면 ./server)은 제 사본의 클래스를 쓰므로 constructor 가 다릅니다 — bundles.ts 의 "같은 클래스인가: false" 가 그것입니다. err instanceof TaskNotFoundError 로 쓰면 SDK 의 표식(Symbol.hasInstance)이 이름으로 견줘 참이 됩니다.

2장

타입 — ts-proto 의 인터페이스와 fromJSON·toJSON

이름 71개의 다섯 무리 → enum 은 TS enum → 객체 글자와 fromJSON → 와이어 모양은 toJSON → 대입은 되고, 넣으면 참조 → 깊은 사본의 Buffer → "" 와 undefined → oneof 와 enum 의 너그러움 → DataPart 의 value → Task 짓기 → Task 읽기 → SDK 안의 모양과 와이어 → 정리

타입은 인터페이스, 값은 fromJSON·toJSON 두 함수짜리 객체다

몸통 @a2a-js/sdk 가 내보내는 이름을 값의 종류로 나눴습니다. Message 같은 이름 하나가 타입(interface)이면서 같은 이름의 값(객체)이기도 합니다.

  • proto 에서 생성한 타입이지만 손잡이는 fromJSON·toJSON 둘뿐입니다. 이진 인코딩(encode·decode)도, 기본값을 채워 주는 create 도 없습니다 — 원본 파일 이름부터 src/types/protojson.ts 입니다(1장).
  • 파이썬 SDK 의 protobuf 메시지(7부)와 달리 이 값들은 보통 JavaScript 객체입니다. 클래스도, 메서드도, 필드 검사도 없습니다. 이 장의 나머지가 모두 그 결과입니다.

enum 은 TS enum — 수가 값이고, 와이어의 이름은 xxxToJSON 이 만든다

TaskState·Role 은 SDK 쪽에서 컴파일된 TS enum 객체입니다. 이름과 수를 오가는 길을 모두 찍었습니다.

  • 객체에 이름 → 수와 수 → 이름이 함께 들어 있어 키가 20개입니다(값 9개 + UNRECOGNIZED, 두 방향). Object.keys(TaskState) 로 상태 목록을 만들면 "0"~"8" 이 섞입니다.
  • 모르는 이름·수는 오류가 아니라 -1(UNRECOGNIZED)입니다. 우리 코드는 enum 을 새로 선언할 수 없지만(tsconfig.json 의 erasableSyntaxOnly — Node 가 타입만 지우고 돌리므로), SDK 의 enum 은 이미 JavaScript 객체라 그대로 씁니다.

메시지는 객체 글자로 — 타입이 필드 여덟을 모두 요구한다

같은 사용자 메시지를 두 길로 만들었습니다. 타입을 단 객체 글자(literal)와, 와이어 모양 JSON 을 Message.fromJSON 에 넣는 길입니다.

  • ts-proto 의 인터페이스는 선택 필드도 "있어야 하는" 필드로 적습니다(contextId: string, metadata: … | undefined). 그래서 객체 글자에는 ""·[]·undefined 를 하나하나 적어야 tsc 를 통과합니다 — 완성 에이전트의 textPart·dataPart(agents/common.ts)가 그 일을 맡습니다.
  • fromJSON 은 빠진 필드를 기본값으로 채워, 두 결과가 깊이 같습니다(isDeepStrictEqual). role 은 수 1 입니다.

JSON.stringify 는 SDK 안의 모양을, toJSON 은 와이어 모양을 낸다

파이썬의 json_format(7부) 자리에 있는 것이 Message.toJSON 입니다. 같은 객체를 두 길로 찍었습니다.

그대로 내보내면 $case 가 샌다 — JSON.stringify 는 content: {"$case", "value"} 와 수 role: 1, 빈 필드를 그대로 씁니다. 와이어에 내기 전에는 반드시 toJSON 을 거칩니다. SDK 의 처리기는 그렇게 하지만, 카드 처리기는 받은 객체를 JSON.stringify 할 뿐입니다 — 5장에서 그 결과를 봅니다.

= 로 넣을 수 있고, 넣은 것은 참조다 — 파이썬과 거꾸로

파이썬 protobuf 는 하위 메시지에 대입을 막고 반복 필드에 넣을 때 복사했습니다(7부). 보통 객체인 TS 타입에서는 둘 다 반대입니다.

  • history.push(msg) 는 그 객체를 넣습니다 — 넣은 뒤 msg 를 "40명" 으로 고치면 이력도 바뀝니다.
  • 펼치기({ ...task })는 겉만 복사해 history 배열을 함께 씁니다. 따로 두려면 structuredClone 입니다. 완성 에이전트의 begin 이 { ...ctx.task, status: working } 로 겉만 바꾸는 것은 status 하나만 새로 끼우기 때문입니다(3장).

structuredClone 은 Buffer 를 Uint8Array 로 바꾼다 — 타입은 여전히 Buffer 라고 한다

raw 파트의 value 는 타입으로는 Buffer 입니다(4부). 그것을 깊은 사본으로 떠 봤습니다.

SDK 가 곳곳에서 structuredClone 을 쓴다 — RequestContext 생성자, ResultManager, InMemoryTaskStore 의 load·save 가 모두 그렇습니다(dist/server/index.js:13·:3562). 그래서 저장소를 거친 raw 파트는 Uint8Array 이고, value.toString("utf8") 은 글이 아니라 수 목록을 냅니다. 읽을 때는 Buffer.from(value) 로 감쌉니다. 와이어로 나갈 때는 Part.toJSON 이 Buffer.from 을 거치므로 문제가 없습니다. 저장소에서 확인하는 것은 4장입니다.

"없음" 은 두 가지 — 문자열·배열은 빈 값, 하위 메시지·선택 필드는 undefined

contextId 없이 온 메시지, status 없는 Task, historyLength 가 있고 없는 GetTask 요청을 fromJSON 으로 읽었습니다.

  • "안 보냄" 이 "" 로 오므로 ?? 는 기본값을 넣지 못합니다. 검사는 if (!msg.contextId), 기본값은 || 입니다 — SDK 도 incomingMessage.contextId || task?.contextId || crypto.randomUUID() 로 씁니다(dist/server/index.js 의 _createRequestContext).
  • historyLength 처럼 proto 에서 optional 인 필드만 ?: number 이고, "없음" 과 0 이 갈립니다(5부).

fromJSON 은 너그럽다 — 내용 둘은 text 가 이기고, 모르는 enum 은 -1 이 된다

와이어에서 TS 서버가 "앞의 것" 을 골랐던 일(4부)과 ProtoJSON 의 너그러움(4부)이 타입 층에서는 이렇게 생깁니다.

  • "앞" 은 JSON 의 키 차례가 아니라 Part.fromJSON 이 묻는 차례 — text, raw, url, data — 입니다(dist/index.js:202). url 을 먼저 적어도 text 가 남았습니다.
  • "user" 같은 v0.3 의 역할 이름은 오류 없이 UNRECOGNIZED 가 됩니다. 사용자 말만 듣는 숙소 에이전트에는 그런 메시지가 "들리지 않습니다"(4부). snake_case 키는 받고, 모르는 키는 소리 없이 버립니다.

DataPart 의 value 는 넣은 JS 값 그대로 — 30 은 30, null 은 사라진다

숙소 요청을 data 파트에 넣어 와이어로 바꾸고 다시 읽었습니다. 파이썬에서 30.0 이 되던 자리(7부)입니다.

  • Value 를 거치지 않으니 수는 정수 그대로, 키 차례는 넣은 차례 그대로입니다(4부). 대신 value 의 타입이 any 라서 모양 검사는 우리 몫입니다 — 완성 에이전트의 dataOf 가 객체인지부터 봅니다.
  • proto 의 google.protobuf.Value data = 4(a2a.proto:233)는 null 도 담을 수 있는 자리인데, fromJSON 은 isSet(null) 이 거짓이라 내용 없는 파트로 읽습니다.

Task 를 짓는 도우미는 없다 — 객체 글자 하나를 함수로 감싼다

파이썬의 new_task_from_user_message(7부) 같은 것이 TS SDK 에는 없습니다. 아홉 필드를 직접 채웁니다.

검사도 없다 — 파이썬 도우미는 역할이 사용자가 아니거나 파트가 비면 ValueError 를 냈지만, 이 함수는 무엇이든 받습니다. id 는 처리기가 지어 ctx.taskId 로 넘겨 주므로(3장) 실행기는 그 값을 씁니다. 완성 에이전트에서는 begin 이 이 일을 합니다.

받은 JSON 은 Task.fromJSON 으로 — 모르는 필드는 오류 없이 버린다

클라이언트 쪽 일입니다. 스펙에 없는 createdAt(5부)과 base64 raw 파트가 든 Task JSON 을 읽었습니다.

파이썬과 반대 — 파이썬 ParseDict 는 옵션 없이는 모르는 필드에서 오류였습니다(7부). TS 의 fromJSON 은 언제나 너그럽고, 대신 아무것도 검사하지 않습니다 — 빈 JSON 도 기본값이 가득한 Task 가 됩니다(5부). raw 는 base64 를 풀어 Buffer 로 줍니다.

SDK 안의 모양과 와이어 모양 — 다섯 군데가 다르다

TS 코드에서 만지는 객체와 와이어의 JSON 이 다른 자리를 모았습니다. 오른쪽으로 바꾸는 것은 언제나 toJSON, 왼쪽으로는 fromJSON 입니다.

2장 퀴즈

Q. 실행기에서 const ask = up.message([textPart("인원은?")])(agents/common.ts 의 Updater)로 에이전트 말을 만들어 task.history.push(ask) 한 뒤, 깜빡한 말을 보태려고 ask.parts.push(textPart("예: 30명")) 을 했습니다. task.history 의 마지막 메시지에는 파트가 몇 개 있습니까? 7부의 같은 퀴즈와 답이 같습니까?

A. 둘입니다. TS 의 push 는 객체 그 자체를 넣으므로, 넣은 뒤 ask 를 고치면 이력의 메시지도 바뀝니다 — types_fields.ts 에서 넣은 뒤 "40명" 으로 고치자 이력도 "40명" 이었습니다. 파이썬은 넣을 때 복사해 처음 그대로(하나)였으니 답이 거꾸로입니다.

3장

실행기(AgentExecutor) — 이벤트를 버스에 싣는 일

채울 함수 둘과 버스 → 타입 파일의 약속 → RequestContext 에서 읽는 것 → 메아리 실행기 → 서버 없이 돌리는 버스 → 실을 수 있는 이벤트 넷 → 견적 실행기 → 견적이 낸 이벤트 → 갱신기가 없는 자리 → 이어 말하기의 ctx.task → 정리

실행기는 함수 둘 — execute 와 cancelTask, 결과는 버스에 싣는다

TS SDK 에서 "에이전트를 만든다" 는 것은 AgentExecutor 인터페이스를 구현하는 것입니다. 파이썬처럼 상속할 추상 클래스는 없습니다. 설치본의 타입 파일에서 두 인터페이스를 읽었습니다(문서 주석은 뺐습니다).

  • cancelTask 는 ctx 가 아니라 taskId 하나만 받습니다. 돌고 있는 execute 를 멈추려면 실행기가 taskId → 멈춤 신호를 따로 쥐고 있어야 합니다 — 완성 에이전트의 live 맵(agents/common.ts)이 그 일을 합니다.
  • 버스에서 실행기가 쓰는 것은 publish 하나입니다. on·off·once 는 처리기 쪽이 듣는 손잡이입니다.

execute 의 약속 — 타입 파일의 문서 주석이 정한 것

파이썬은 execute 의 문서 문자열에 계약을 적었습니다(7부). TS SDK 는 그것을 dist/server/index.d.ts 의 주석 여러 곳에 나눠 적었습니다.

줄약속이 책에서
131–134매 호출의 첫 이벤트는 task 나 message — ctx.task 가 있는 이어 말하기에서도. 서버가 그 차례를 강제하고 statusUpdate·artifactUpdate 로 시작하는 스트림을 거절한다이 장, 4장
136–137테넌트는 requestContext.context.tenant 에서 읽는다13부
141–142cancelTask 는 실행을 멈추고 마지막 canceled 상태를 버스에 싣는다앞 슬라이드, 11부
255–257처리기의 큐는 Message, 종료 상태, INPUT_REQUIRED 에서 멈춘다. AUTH_REQUIRED 에서는 멈추지 않는다 — 같은 실행이 이어지기를 기다린다4장, 12부
270실행기가 돌아간 뒤에도 버스를 살려 두는 상태 — 기본 INPUT_REQUIRED·AUTH_REQUIRED4장

돌려주는 값도, 끝내는 신호도 처리기가 챙긴다 — execute 가 돌려주는 Promise 가 풀리면 처리기가 버스를 정리합니다(_settleBus, dist/server/index.js:2978). 실행기가 bus.finished() 를 부르지 않아도 된다는 뜻입니다 — 4부의 예제는 불렀고, 이 부의 예제는 부르지 않습니다.

RequestContext — 처리기가 다 채워 넘기는 요청 한 건

실행기가 읽는 것은 ctx 에 있습니다(src/server/agent_execution/request_context.ts, dist/server/index.js:2). 파이썬의 RequestContext(7부)와 달리 이 클래스는 아무것도 짓지 않고 받은 대로 담기만 합니다.

속성무엇누가 채우나
userMessage이번에 받은 Message (request.message 의 별명)처리기가 taskId·contextId 를 써 넣은 사본
taskId, contextId이번 요청의 id처리기 — 없으면 crypto.randomUUID()
task저장소에 있던 Task, 첫 마디면 undefined처리기 — 이번 메시지를 이력에 붙여 저장한 뒤(이 장 끝)
referenceTasksreferenceTaskIds 의 작업들처리기 — 채운다(없는 id 는 console.warn). 파이썬 기본 처리기는 비워 둔다 — 15부
request요청 전체 — configuration·metadata·tenant생성자가 structuredClone
contextServerCallContext — 사용자·헤더·확장·테넌트express 처리기(5장)

메아리 실행기 — Message 하나를 실으면 그것이 답이다

1단계 에이전트입니다. 받은 글 앞에 "받은 말:" 을 붙여 에이전트 Message 하나를 버스에 싣고 끝냅니다. 7부의 메아리와 하는 일이 같습니다.

  • 도우미가 없어 Message 의 여덟 필드를 다 적습니다(2장). messageId 는 randomUUID(), contextId 는 처리기가 넘긴 것입니다.
  • 취소할 작업이 없으니 cancelTask 는 @a2a-js/sdk/errors 의 UnsupportedOperationError 를 던집니다(1장: SDK 의 오류 클래스여야 코드가 맞게 나갑니다).

서버 없이 실행기 돌리기 — 버스에 듣는 쪽 하나를 달면 된다

실행기는 보통의 비동기 함수입니다. SDK 가 내보내는 DefaultExecutionEventBus(EventTarget)에 'event' 를 듣는 함수를 달고, RequestContext 를 손으로 지어 넘깁니다.

하위 클래스가 필요 없다 — 파이썬은 EventQueue 를 상속해 enqueue_event 를 채웠습니다(7부). TS 의 버스는 이미 쓸 수 있는 클래스라서 듣는 함수만 답니다. 대신 RequestContext 가 id 를 짓지 않으므로 randomUUID() 둘을 직접 넘깁니다. SDK 서버를 통째로 프로세스 안에서 시험하는 법은 8장입니다.

실을 수 있는 것은 넷 — AgentEvent 의 함수 넷이 kind 를 붙인다

버스에 싣는 값은 {kind, data} 꾸러미입니다(AgentExecutionEvent). 손으로 짓지 말고 AgentEvent.message(…) 처럼 씁니다(타입 파일의 권고: "Prefer these over constructing the wrapper object literals directly").

흐름싣는 것클라이언트가 받는 것
즉답AgentEvent.message(m) 하나result.message
작업AgentEvent.task(t) 먼저, 그다음 statusUpdate·artifactUpdate 여럿result.task(막는 호출) 또는 이벤트 스트림(10부)
차례 검사는 처리기가, 그것도 스트림에서만 — 이 버스는 무엇이든 받습니다(5부). 진짜 처리기가 차례를 어떻게 다루는지는 4장에서 봅니다 — 막는 호출과 스트림의 답이 다릅니다.

견적 실행기 — Task 를 먼저 싣고, 상태·아티팩트 갱신을 잇는다

2단계 에이전트는 DataPart 로 날짜·박 수·인원을 받아 업무 규칙 chooseLodging 을 부릅니다. 결과에 따라 아티팩트를 내고 끝내거나, 까닭을 달아 거절합니다. 흐름은 7부와 한 줄씩 같습니다.

  • newTask·update·agentSays 는 이 파일의 작은 함수입니다(조금 뒤). 파이썬의 TaskUpdater 자리를 채웁니다.
  • requestOf 는 DataPart 를 합치기만 합니다. 수가 정수 그대로 오므로(2장) 파이썬처럼 int 로 되돌릴 일이 없습니다. 빠진 항목을 되묻는 일은 7장의 완성판이 합니다.

견적이 낸 이벤트 — Task, WORKING, 아티팩트, COMPLETED

같은 버스로 견적 실행기를 두 번 돌렸습니다. 10월 30일 30명과, 세 숙소가 모두 쉬는 12월 31일입니다.

  • Task 의 id(<id3>)가 ctx.taskId 와 같습니다. newTask 가 ctx.taskId 를 그대로 썼기 때문입니다 — 파이썬처럼 메시지에서 꺼내 오는 길은 없습니다(메시지의 taskId 는 "").
  • 거절은 아티팩트 없이 REJECTED 하나로 끝나고, 까닭은 상태 메시지에 실렸습니다. 출력이 7부와 글자까지 같습니다.

TaskUpdater 가 없다 — 이벤트 객체를 짓는 함수를 우리가 둔다

TS SDK 에는 상태·아티팩트 이벤트를 지어 주는 갱신기가 없습니다(1장의 이름 목록). 견적 에이전트는 함수 셋으로 그 자리를 채웠습니다.

완성 에이전트는 클래스 하나로 — agents/common.ts 의 Updater 가 message·status·artifact·pause 를 한데 묶고, 종료 상태가 되면 live 맵에서 자신을 지웁니다. 파이썬 갱신기처럼 "종료 뒤 갱신" 을 막는 장치는 없습니다. 대신 처리기의 큐가 종료 상태에서 멈추고(5부), 저장 쪽(ResultManager)도 종료된 작업에 온 다른 상태를 경고만 남기고 버립니다(dist/server/index.js:2355).

이어 말하기 — ctx.task 에는 이번 메시지가 이미 들어 있다

같은 taskId 로 두 번째 메시지가 오면 처리기는 저장된 Task 를 ctx.task 로 넘깁니다. 첫 마디에 되묻고 둘째 마디에 끝내는 실행기로, 둘째 execute 가 받은 ctx.task 를 찍었습니다(처리기를 직접 부르는 법은 4장).

  • 처리기는 execute 를 부르기 전에 이번 메시지를 이력에 붙여 저장합니다(dist/server/index.js:2799). 파이썬은 그 반대였습니다(7부: 첫 갱신 때 저장). 에이전트의 질문(q-1)도 상태를 낼 때 바로 이력에 들어갔습니다(5부).
  • 완성 에이전트의 begin 은 이어 말하기에도 Task 를 WORKING 으로 다시 싣습니다(5부). 숙소 실행기는 [...task.history, ctx.userMessage] 로 이번 메시지를 한 번 더 붙여 읽는데, 같은 DataPart 를 두 번 합칠 뿐이라 결과는 같습니다.

3장 퀴즈

Q. 되묻기 에이전트의 둘째 마디에서 "사용자가 지금까지 한 말" 을 모으려고 [...ctx.task.history, ctx.userMessage] 의 사용자 메시지를 셌더니, 사용자가 두 번 말했는데 셋이 나왔습니다. 왜 그렇고, 파이썬 SDK(7부)에서도 셋입니까?

A. TS 처리기는 execute 를 부르기 전에 이번 메시지를 이력에 붙여 저장하므로, ctx.task.history 에 이미 둘째 말(m-2)이 있습니다 — follow.ts 의 "이번 메시지가 이미 있나: true" 입니다. 여기에 ctx.userMessage 를 또 붙이면 둘째 말이 두 번 셉니다. 파이썬의 current_task 에는 이번 메시지가 아직 없으니 둘입니다.

4장

요청 처리기와 Task 저장소

메서드 열하나 → 위치 인자 아홉 → HTTP 없이 처리기 부르기 → 막는 호출은 언제 돌아오나 → 반칙하는 실행기 일곱 → 차례 반칙의 결과 → 침묵과 예외 → A2A 오류 열 → 테넌트·소유자별 저장소 → 꺼내면 사본 → 정리

요청 처리기는 A2A 메서드 열하나를 메서드 열하나로 받는다

JSON-RPC 전송 처리기(JsonRpcTransportHandler)의 switch 를 읽어, 메서드 이름마다 처리기의 어느 메서드를 부르는지 짝지었습니다.

  • 이름이 늘 짝이 맞지는 않습니다 — SubscribeToTask 는 resubscribe, GetExtendedAgentCard 는 getAuthenticatedExtendedAgentCard 입니다. 파이썬의 on_* 열하나(7부)와 같은 몫입니다.
  • 전송 처리기가 params 를 XxxRequest.fromJSON 으로 읽어 넘기고, 답은 toJSON 으로 바꿉니다(2장). REST 처리기도 같은 객체의 같은 메서드를 부릅니다(13부).

HTTP 없이 처리기 부르기 — ServerCallContext 하나면 된다

2단계 견적 실행기로 처리기를 만들고, SendMessage·GetTask·ListTasks 와 스트림을 직접 불렀습니다. 7부의 direct.py 와 한 줄씩 같은 일입니다.

ServerCallContext — "누가, 어떤 요청으로" 를 담는 클래스입니다(src/server/context.ts: user·tenant·state·requestedExtensions·requestedVersion). express 처리기가 HTTP 요청마다 지어 넘기고(5장), 여기서는 빈 것(익명)을 씁니다.

막는 호출은 큐가 멈출 때 돌아온다 — returnImmediately 면 첫 Task 에서

  • sendMessage 는 버스의 이벤트를 큐로 따라가다가 큐가 멈추면 그때의 Task 를 답으로 줍니다. 큐는 Message, 종료 상태, INPUT_REQUIRED 에서 멈춥니다(3장의 약속 표). AUTH_REQUIRED 는 그 자리의 사본(snapshot)을 먼저 돌려주고 큐는 뒤에서 계속 비웁니다(dist/server/index.js:3096).
  • returnImmediately 면 첫 Task(SUBMITTED)에서 답하고 실행기는 뒤에서 마저 돕니다 — 결과가 파이썬과 같습니다. 와이어에서 본 모습은 5부입니다.
  • 스트림은 카드의 capabilities.streaming 이 꺼져 있어 막혔습니다(:3141). 파이썬과 달리 기록(log)은 남기지 않습니다.

반칙하는 실행기 일곱 — 차례 넷, 침묵 하나, 예외 둘

7부와 같은 일곱을 TS 로 썼습니다. 각각을 새 처리기에 물려 막는 SendMessage 와 스트림을 2초까지 기다리고, 답과 저장소에 남은 작업과 스트림이 낸 이벤트를 찍습니다.

차례 검사는 스트림에만 있다 — 막는 호출은 반칙을 소리 없이 넘긴다

  • 차례 검사(_advanceStreamPattern)는 sendMessageStream 안에서만 불립니다(dist/server/index.js:3162). 그래서 스트림은 반칙을 -32004 로 끊고, 막는 호출은 그냥 지나갑니다 — Message 둘이면 앞의 것, Task 뒤의 Message 면 그 Message 가 답이 되고 저장소에는 SUBMITTED 작업이 영영 남습니다.
  • 스트림이 쓰는 코드는 -32004 UnsupportedOperation 입니다. 파이썬은 같은 반칙에 -32006 InvalidAgentResponse 였습니다(7부) — §3.3.2 의 표는 InvalidAgentResponseError 를 "An agent returned a response that does not conform to the specification" 이라 적으니 후자가 맞는 코드입니다.
  • OtherId 는 TS 에서 반칙이 아닙니다 — 실행기가 지은 id 그대로 저장되고 답에 나갑니다(파이썬은 -32602).

침묵은 곧바로 -32603, 예외는 오류가 아니라 FAILED Task 가 된다

  • Silent — 실행기가 돌아가면 처리기가 버스를 닫고(3장), 결과가 없으니 "Agent execution finished without a result" 로 끝냅니다. 파이썬처럼 끝없이 붙잡지 않습니다(7부). 오류 이름 _A2AError 는 번들 도구가 바꾼 기반 클래스 이름입니다(dist/errors/index.js:5, class _A2AError).
  • Refuses·Crashes — A2A 오류든 아무 예외든, execute 가 던지면 처리기가 FAILED Task 를 지어 답합니다(5부). 실행기에서 던진 RequestMalformedError 는 -32602 가 되지 않습니다. 거절이 목적이면 REJECTED 상태를 싣습니다(3장).

A2A 오류 클래스는 열 — 처리기가 던지는 것이 코드가 된다

@a2a-js/sdk/errors 의 클래스마다 JSON-RPC 코드와 HTTP+JSON 바인딩의 상태를 SDK 의 변환 함수(toJsonRpcError·restStatusFor)에 물었습니다.

파이썬보다 셋 적다 — JSON-RPC 의 -32600·-32601·-32603·-32700 은 클래스가 아니라 전송 처리기가 직접 짓는 코드입니다. -32602 는 RequestMalformedError(reason INVALID_PARAMS) 하나가 맡습니다. 이 표가 쓰이는 곳은 처리기가 스스로 던지는 오류(작업 없음 -32001, 스트림 미지원 -32004, 판 불일치 -32009)이고, execute 가 던진 것은 앞 슬라이드처럼 FAILED Task 가 됩니다.

InMemoryTaskStore 는 테넌트 → 소유자 → taskId 로 나뉜다 — 익명은 "unknown"

저장소 인터페이스(TaskStore)는 save·load·list 셋이고, 모두 호출자(ServerCallContext)를 받습니다. 직원 둘, 익명, 이름이 unknown 인 사용자, 다른 테넌트의 kim 으로 찾아봤습니다.

  • 칸은 tenant 다음 owner 입니다(ScopedStore, dist/server/index.js:2090). 같은 kim 이라도 테넌트 b 에서는 작업이 없습니다.
  • 소유자 이름은 context.user?.userName || "unknown" 입니다(resolveUserScope, :307). 익명의 userName 은 "" 이라 "unknown" 칸에 들어가고, 그래서 이름이 unknown 인 사용자는 익명의 작업을 봅니다. 파이썬은 익명 칸이 "" 였습니다(7부). 사용자를 세우는 일은 12부입니다.

꺼낸 Task 는 structuredClone 사본이다 — 끄는 스위치도, delete 도 없다

꺼낸 Task 를 save 없이 고친 뒤 다시 꺼냈고, raw 파트가 든 Task 를 넣었다 꺼냈습니다.

  • load·save 가 늘 structuredClone 을 거쳐, 고친 것은 save 해야 남습니다. 파이썬의 use_copying=False(7부) 같은 스위치는 없고, 메서드는 load·save·list 뿐 지우는 것이 없습니다.
  • 저장소를 거친 raw 는 Uint8Array 입니다(2장). ctx.task 도 이 저장소에서 꺼낸 것이라, 이어 말하기에서 이전 파일을 읽을 때는 Buffer.from(value) 로 감쌉니다.

4장 퀴즈

Q. 숙소 실행기의 한 갈래에서 실수로 Task 를 실은 뒤 상태 대신 Message 를 실었습니다. 막는 SendMessage 를 보낸 클라이언트는 무엇을 받고, 나중에 GetTask 하면 작업은 어떤 상태입니까? 같은 요청을 SendStreamingMessage 로 보내면 어떻게 됩니까?

A. 막는 호출은 그 Message 를 답으로 받습니다. 저장소의 작업은 SUBMITTED 로 남아 끝나지 않습니다 — rules.ts 의 MessageAfterTask 가 "막는 호출 Message", "저장 [TASK_STATE_SUBMITTED]" 였습니다. 스트림은 task 하나를 낸 뒤 UnsupportedOperationError(-32004) "Stream ordering violation" 으로 끊깁니다. 막는 호출에는 차례 검사가 없기 때문입니다.

5장

서버 띄우기 — express 처리기 셋과 카드

처리기 셋은 express Router → 앱은 express(), 띄우는 것은 listen → 서버 셋을 탭 뒤에 → 처리기를 카드 공급자로 주면 → toJSON 으로 준 카드 → 메아리의 답 → 견적의 답 → 경로 밖의 요청 → 판 머리글과 Content-Type → 사용자와 헤더가 실행기에 닿는 길 → 정리

express 처리기 셋은 Router 를 돌려줄 뿐이다 — 앱과 포트는 우리 몫

./server/express 의 jsonRpcHandler·agentCardHandler·restHandler 는 express Router 를 만들어 돌려줍니다. 그 안의 층(layer)을 펴 봤습니다.

  • JSON-RPC 는 POST / 하나 앞에 미들웨어 셋 — Content-Type 검사, express.json()(본문 한도 100 KB — 4부), JSON 깨짐 처리 — 이 있습니다. 카드는 GET / 하나라, 어느 경로에 달지는 app.use 가 정합니다.
  • REST 는 열두 경로에 같은 열둘을 /:tenant/… 아래에 한 번 더 답니다. :subscribe 를 GET 과 POST 둘 다 받는 것도 파이썬과 같습니다(7부) — 13부의 몫입니다.

앱은 express() 하나 — Router 를 경로에 달고 listen

1단계 메아리 에이전트의 main 입니다. 카드·저장소·실행기로 처리기를 짓고(4장), 카드 경로와 JSON-RPC 경로를 express 앱에 달아 띄웁니다.

  • 카드의 url 은 바깥에서 닿는 주소라서(3부) --url 을 따로 받습니다. 다음 슬라이드에서 탭의 주소를 넣습니다.
  • userBuilder 는 필수 옵션입니다. 로그인이 없으면 UserBuilder.noAuthentication 을 줍니다(조금 뒤). 끌 때는 app.listen 이 돌려주는 HTTP 서버를 close() 합니다 — 처리기에는 끄는 메서드가 없습니다(4장).

서버 셋을 탭 뒤에 — 메아리는 /, 견적은 /a2a

7부와 같은 짜임입니다. 1단계 메아리, 2단계 견적(JSON-RPC 를 /a2a 에), 헤더를 되돌려 주는 실험 서버를 띄우고 각각 앞에 와이어 탭을 세웠습니다. 요청 본문은 ex/run/08/rpc/*.json 입니다.

견적 서버만 다르게 한 것 — 카드를 AgentCard.toJSON 으로 바꿔 주고, JSON-RPC 를 --path 에 답니다(조금 뒤). POST /·GET /a2a 두 요청과, 판 머리글 없이 보낸 요청·text/plain 으로 보낸 요청은 일부러 틀리게 보낸 것입니다.

처리기를 카드 공급자로 주면 빈 필드까지 나간다

SDK 설명서의 예(agentCardProvider: a2aRequestHandler, dist/agent_card_handler-DdsMrp1N.d.ts)대로 단 메아리 서버의 카드입니다.

  • agentCardHandler 는 받은 객체를 JSON.stringify 할 뿐입니다(dist/server/express/index.js:5888). 처리기가 주는 것은 fromJSON 이 지은 TS 객체라서 "tenant": "", "extensions": [], "signatures": [] 같은 기본값이 그대로 나갑니다(2장, 3부).
  • oneof 가 있는 카드(보안 스킴)라면 {"$case": …} 까지 샙니다 — 그래서 완성 에이전트는 카드를 toJSON 해서 줍니다(agents/common.ts 의 serve). 이 경로는 약한 ETag 와 Cache-Control: public, max-age=3600 을 답니다(3부).

toJSON 한 카드를 주면 와이어 모양 그대로다

2단계 견적 서버는 AgentCard.toJSON(agentCard) 를 돌려주는 함수를 공급자로 줍니다(조금 뒤의 코드).

카드는 언제나 toJSON 을 거쳐 준다 — 기본값이 빠져 파이썬·Go 서버의 카드와 같은 모양이 됩니다. 서명할 카드도 이 모양 위에서 서명합니다 — 완성 에이전트가 왜 그렇게 하는지는 12부에서 봅니다.

메아리의 답은 result.message — 실행기가 실은 Message 그대로

  • 전송 처리기가 Message 와 Task 를 "messageId" in result 로 갈라 {"message": …} 로 감쌌습니다(JsonRpcTransportHandler). 빈 taskId: "" 는 toJSON 이 뺐습니다.
  • contextId 는 처리기가 지어 ctx.contextId 로 넘긴 것입니다(3장). Task 가 없으니 이 서버에 GetTask 해도 찾을 작업이 없습니다.

견적의 답은 result.task — 이벤트 넷이 Task 하나로 접혔다

2단계 서버에 같은 DataPart 요청을 보냈습니다. 응답 쪽만 잘랐습니다.

  • 3장에서 실행기가 낸 이벤트는 넷이었지만 막는 호출의 답은 마지막 상태의 Task 하나입니다. 이벤트를 하나하나 받으려면 스트림(10부)입니다.
  • 수는 30·2100000 정수 그대로이고(2장), 이력의 사용자 메시지에는 처리기가 채운 contextId·taskId 가 붙었습니다(3장).

JSON-RPC 경로는 app.use 의 첫 인자 — 경로 밖의 요청은 express 의 HTML 404

2단계는 --path /a2a 로 Router 를 /a2a 에 달고, 카드의 url 도 같은 경로로 적습니다. 경로를 벗어난 요청 둘(POST /, GET /a2a)의 답입니다.

JSON-RPC 오류가 아니다 — 경로가 없는 요청은 express 의 기본 처리가 404 와 HTML 한 쪽으로 돌려보냅니다. Router 에 POST / 만 있어 GET /a2a 도 405 가 아니라 404 입니다(파이썬 Starlette 는 405 — 7부). 카드의 url 을 잘못 적으면 클라이언트가 받는 것이 이것입니다(3부).

판 머리글이 없으면 -32009, JSON 이 아니면 -32005 — 처리기에 닿기 전에

같은 요청을 A2A-Version 머리글 없이, 그리고 Content-Type: text/plain 으로 보냈습니다. 손으로 curl 을 칠 때 가장 먼저 만나는 두 오류입니다.

  • 머리글이 없으면 판을 '0.3' 으로 보고(ABSENT_HEADER_VERSION, src/server/context.ts) 카드의 protocolVersion 과 글자 그대로 견줍니다 — 판 검사의 세 SDK 비교는 6부입니다. 이 흔한 클라이언트 실수에 서버는 stderr 로 "Unhandled error" 와 추적 정보를 남깁니다(dist/server/express/index.js:3510).
  • Content-Type 검사(contentTypeGuard)는 HTTP 머리글의 잘못에 -32005 ContentTypeNotSupported 를 씁니다. 스펙의 -32005 는 메시지 파트의 미디어 형식을 위한 코드입니다(§3.3.2, 4부).

사용자는 userBuilder 가, 헤더는 context.state 가 실행기까지 나른다

express 처리기는 HTTP 요청마다 userBuilder(req) 로 사용자를 세우고, ServerCallContext 를 지어 처리기에 넘깁니다. 그것이 ctx.context 로 실행기까지 옵니다. 받은 것을 파트 다섯으로 돌려주는 실행기에, 머리글로 사용자를 세우는 실험용 userBuilder 를 달았습니다.

  • 기본 빌더(defaultServerCallContextBuilder)는 express 의 req.headers(소문자 키)를 state.get("headers") 에 담습니다. 바꾸려면 jsonRpcHandler({…, contextBuilder}) 입니다. 저장소의 소유자 칸도 이 사용자 이름으로 갈립니다(4장).
  • 확장이 비었습니다 — A2A-Extensions 머리글을 보냈는데도 [] 입니다. 처리기가 카드의 capabilities.extensions 에 없는 것을 걸러 냅니다(dist/server/index.js:2818). 파이썬은 받은 그대로 넘겼습니다(7부). 확장은 14부입니다.

5장 정리 — 서버를 세우는 손잡이

할 일TypeScript SDK

Q. 견적 서버를 띄운 뒤 동료가 curl --json @quote.json http://127.0.0.1:10812/a2a 로 시험했더니 오류가 왔다고 합니다. 경로도 본문도 맞습니다. 무엇이 빠졌고, 답은 어떤 코드입니까? 파이썬 SDK 서버(7부)였다면 같습니까?

A. A2A-Version: 1.0 머리글이 빠졌습니다. 머리글이 없으면 판을 0.3 으로 보므로 -32009 "The requested A2A protocol version '0.3' is not supported" 가 옵니다 — serve 캡처의 "code": -32009 입니다. 파이썬 SDK 서버도 머리글이 없으면 -32009 입니다(6부의 표, "헤더 없음" 열).
