referenceTaskIds 로 정산 요청

정산에 가는 것 → 파이썬 → TypeScript → Go → 세 언어 비교 → 근거는 동료의 작업 id → 세 요청의 차림 → 정산 서버가 한 일 → SDK 는 풀어 주나 ×3 → 남의 서버의 작업 → 결재 뒤 이어 가기 ×3 → 이어 말하기의 와이어 → 정리

정산에 가는 것 — 견적 셋은 본문으로, 그 견적을 낸 작업 셋은 referenceTaskIds 로

3장의 위임이 끝나면 기획 에이전트에는 동료의 작업(Task) 셋이 남습니다. 정산 요청은 그 작업들에서 꺼낸 금액을 본문에 싣고, 작업 자체는 id 로 가리킵니다.

 기획 에이전트 — 작업 T, 맥락 C
   │ ① 토큰 받기  scope=payment:read
   │ ② SendMessage(맥락 C) ─────────────→ 정산
   │      parts            [DataPart {items 셋, budget}]
   │      referenceTaskIds [숙소의 작업, 식사의 작업, 교통의 작업]
   │      Authorization    Bearer (①의 토큰)
   │←── AUTH_REQUIRED ── 결재가 필요하다
  • §3.4.3: "Clients SHOULD use the referenceTaskIds field in Message to explicitly reference related tasks", 그리고 "Agents SHOULD use referenced tasks to understand the context and intent of follow-up requests". proto 의 설명은 "A list of task IDs that this message references for additional context" 입니다(4부).
  • 맥락은 3장과 같은 기획 작업의 contextId 이고, 토큰은 기획 에이전트 자신의 이름(planner)으로 받습니다(12부). 결재가 필요하다는 답(AUTH_REQUIRED)부터는 이 장의 뒤쪽입니다.

파이썬 — plan 의 뒤쪽, 토큰을 받아 작업 셋의 id 를 refs 로

  • refs=[lodging.id, meals.id, bus.id] — gather 가 돌려준 작업 셋의 id 입니다. delegate 가 그것을 ask_message 에 넘기고, 거기서 m.reference_task_ids.extend(refs) 로 메시지에 붙습니다(delegate 구역, 7부).
  • 토큰 받기와 정산 위임을 한 try 로 감쌌습니다. 어느 쪽이 실패해도 cannot 으로 FAILED "정산 에이전트에게 맡기지 못했습니다" 입니다(2장).
  • AUTH_REQUIRED 면 이어 가는 데 필요한 넷(카드·풀이·견적·정산 작업)을 self.waiting[task.id] 에 적고, 자기 작업도 AUTH_REQUIRED 로 바꾼 뒤 실행기를 끝냅니다. 사람의 답은 새 실행으로 옵니다(뒤에서).

TypeScript — 따로 된 settle 메서드, done.map(t => t.id)

  • refs 는 delegate 의 선택 인자 { token, refs } 로 넘어가, Message.fromJSON 에 들어갈 referenceTaskIds 가 됩니다(delegate 구역). 동료 셋에게 맡길 때는 refs 가 없어 빈 배열입니다.
  • 견적은 quoteOf 로 아티팩트의 첫 DataPart 에서 꺼내고 Math.trunc 로 정수를 만듭니다. 기다림은 this.waiting(Map)에 적고 실행기가 돌아갑니다 — 파이썬과 같은 모양입니다.

Go — 가변 인자 refs ...a2a.TaskID, 필드 이름은 ReferenceTasks

Go 의 settle 은 구역이 한 화면을 넘어 둘로 잘랐습니다. 앞쪽 — 토큰을 받고 정산에 맡기는 데까지입니다.

  • Go 이름 ReferenceTasks 가 와이어의 referenceTaskIds 입니다(9부에서 본 이름 차이). refs[0].ID, refs[1].ID, refs[2].ID 의 차례는 fanOut 이 정한 자리의 차례입니다.
  • Go 에는 waiting 이 없습니다 — AUTH_REQUIRED 를 받으면 이 함수 안에서 그대로 기다립니다(뒤에서).

와이어 — 정산이 받은 referenceTaskIds 셋은 동료 셋이 지은 작업 id 다

6장의 파이썬 메시(15/mesh_py.run)는 다섯 에이전트 앞에 모두 탭을 두었습니다. 같은 캡처 안에서 같은 값은 같은 <idN> 입니다. 동료 셋의 답에서 작업 id 만, 정산 요청에서 근거와 맥락만 골랐습니다.

  • 숙소 <id4>, 식사 <id8>, 교통 <id14> 이 그대로 정산 요청의 referenceTaskIds 에 정한 차례로 들어갔습니다. 맥락 <id2> 는 동료 셋이 받은 것과 같습니다(3장).
  • 근거는 id 뿐입니다. 정산이 계산하는 금액은 본문의 items 에 따로 실려 갑니다.

정산은 셋 다 받았다 — 세 메시 모두 같은 AUTH_REQUIRED 를 돌려받았습니다(6장). 실수로 온 금액은 정산 에이전트가 정수로 되돌립니다(4부). TS 의 "id": 1 은 JSON-RPC 요청마다 같은 값인데, 요청이 HTTP 하나에 하나뿐이라 답을 짝짓는 데 문제가 없습니다.

정산 서버는 근거로 무엇을 했나 — TypeScript 만 찾아보고 "not found", 셋 다 이력에 남겼다

세 메시의 정산 에이전트 출력입니다. 정산 실행기는 근거를 읽지 않습니다 — 금액은 본문에 있으니까요. 그래도 SDK 가 하는 일이 있습니다.

  • TS 의 요청 처리기는 referenceTaskIds 의 id 마다 자기 작업 저장소를 뒤지고, 없으면 console.warn(`Reference task ${refId} not found.`) 을 남깁니다(server/index.js:2803–2812). 세 id 는 숙소·식사·교통 서버에서 지어졌으니 정산 서버의 저장소에는 없습니다.
  • 파이썬·Go 는 조용합니다 — 기본 처리기가 근거를 찾아보지 않기 때문입니다(다음 슬라이드).
근거는 이력에 남는다 — 끝난 정산 작업의 history 첫 메시지에 referenceTaskIds 셋이 그대로 있습니다(TS·Go 정산의 답도 같습니다). 정산 작업을 나중에 GetTask 로 읽는 쪽은 "이 정산이 어느 견적들에서 왔는가" 를 id 로 압니다.

SDK 는 근거를 작업으로 풀어 주나 — 파이썬은 켜야 하고, 켜도 자기 저장소만 본다

7부에서 본 related_tasks(7부)를 직접 시험합니다. 처리기를 HTTP 없이 부르고, 다른 처리기(다른 서버 몫)의 작업 하나와 같은 처리기의 작업 하나를 근거로 보냅니다.

  • 기본 처리기는 SimpleRequestContextBuilder(should_populate_referred_tasks=False, task_store=None) 을 씁니다(default_request_handler_v2.py:155). 저장소조차 넘기지 않으니, 켜려면 이 예제처럼 빌더를 직접 만들어 request_context_builder 로 줘야 합니다.
  • 켜면 id 마다 task_store.get 을 부르고 없는 것은 빼 버립니다(simple_request_context_builder.py:63–75) — 다른 서버의 <id1> 은 조용히 사라지고 <id3> 하나만 남았습니다.

TypeScript — 늘 채운다, 스위치가 없다, 못 찾으면 경고 한 줄

  • 같은 실험을 TS 의 기본 처리기로 — 처리기에 넘긴 저장소에서 찾아 ctx.referenceTasks 에 넣습니다. 끄는 옵션은 없습니다.
  • 다른 서버의 <id1> 에 대해 정산 서버와 똑같은 경고가 나왔습니다. 찾은 것만 들어가는 것은 파이썬과 같습니다.

Go — 가로채기 ReferencedTasksLoader 를 달아야 채운다

  • a2asrv.ReferencedTasksLoader{Store: store} 는 실행기 맥락 가로채기(ExecutorContextInterceptor)입니다. id 마다 Store.Get 하고, 실패하면 log.Info(… "failed to get a referenced task" …) 를 남기고 넘어갑니다(a2asrv/exectx.go:78–100) — 출력의 INFO 줄입니다.
  • WithExecutorContextInterceptor 의 문서는 "overrides the default ExecutorContextInterceptor" 라고 하지만, 코드는 목록에 덧붙입니다(exectx.go:32–35).

이 이야기에서 근거의 뜻 — 작업 id 는 서버가 짓고(§3.4.2 "server-generated") 그 서버 안에서만 뜻이 있습니다. 스펙은 근거가 같은 서버의 작업이어야 한다고도, 다른 서버의 작업을 어떻게 찾으라고도 하지 않습니다. 그래서 기획 에이전트의 근거는 추적용 표지이고, 정산이 계산에 쓰는 것은 본문의 items 입니다. 정산이 견적을 직접 확인하게 하려면 근거와 함께 그 작업이 있는 서버를 알려 줄 약속(예: 메시지 metadata)이 따로 필요합니다.

결재 뒤 이어 가기 — 파이썬은 새 실행이 waiting 에서 꺼내 정산 작업에 이어 말한다

사람이 "승인" 이라고 답하면, 그 답은 기획 작업(같은 taskId)으로 온 새 메시지입니다. 실행기의 첫머리가 task.id in self.waiting 을 보고 여기로 보냅니다(1장). 사슬 전체는 12부에서 보았으니(12부), 기획 에이전트의 코드만 봅니다.

  • pop 으로 꺼내므로 같은 작업의 두 번째 답은 다시 처음부터(풀이) 갑니다. 기다림은 프로세스의 메모리에만 있습니다 — 기획 에이전트가 다시 뜨면 결재 대기는 사라집니다.
  • "승인" 이 없으면 REJECTED "결재가 반려되어 멈춥니다" 입니다. 정산 작업은 AUTH_REQUIRED 로 남고, 기획 에이전트는 그 작업을 취소하지 않습니다(실패 경로는 7장).
  • 결재 토큰은 payment:read payment:approve 두 스코프로 새로 받습니다(12부의 결함). 이어 말하는 follow_up 은 정산 작업의 taskId·contextId 를 답니다 — 근거(refs)는 다시 싣지 않습니다.

TypeScript — 같은 모양, Map 에서 꺼내고 지운다

  • get 다음 delete — 파이썬의 pop 과 같습니다. 답은 ctx.userMessage, 곧 이번 메시지에서 읽습니다.
  • 이 실행은 새 실행이라 begin() 이 작업을 WORKING 으로 다시 싣고 시작합니다(1장의 task WORKING 한 줄). 5장의 스트림에서 그 이벤트를 봅니다.

Go — 멈춘 실행이 AwaitReply 에서 답을 받아, 같은 함수 안에서 이어 간다

  • up.AwaitReply 는 상태를 AUTH_REQUIRED 로 알리고, 같은 작업으로 올 다음 메시지를 채널에서 기다립니다(agents/common/park.go, 12부). 그래서 c·req·quotes·settle 은 지역 변수 그대로 남아 있고, waiting 이 없습니다.
  • 기다리는 동안 고루틴 하나가 살아 있습니다. 사람이 끝내 답하지 않으면 ctx 가 끝날 때까지입니다 — 파이썬·TS 의 waiting 항목이 영원히 남는 것과 같은 문제의 다른 모양입니다.

이어 말하기의 와이어 — 결재 토큰, 정산 작업의 taskId, 근거는 없다

세 메시의 정산 탭에서 다섯째 주고받음(결재 토큰을 단 SendMessage)입니다. 파이썬 기획 에이전트의 것은 12부에서 보았으니(12부) TypeScript·Go 의 것만 싣습니다.

  • 두 기획 에이전트 모두 tok-planner-2(두 스코프) 를 달고, 정산 작업의 taskId 와 같은 맥락으로 결재합니다 한마디를 보냈습니다. 정산은 COMPLETED 와 remaining 1,158,000 을 담은 정산서로 답했습니다.
  • 근거(referenceTaskIds)는 첫 요청에만 있습니다. 이어 말하기는 taskId 가 이미 그 작업을 가리키니 따로 달 까닭이 없습니다.

4장 퀴즈

Q. TypeScript 메시의 정산 에이전트는 "Reference task … not found." 를 세 번 찍었습니다. 정산 서버의 처리기가 이 id 들을 찾지 못한 까닭은 무엇이고, 파이썬 정산 서버에서 should_populate_referred_tasks 를 켰다면 실행기는 몇 개의 작업을 받았겠습니까?

A. 세 id 는 숙소·식사·교통 서버가 지은 작업이라(와이어) 정산 서버의 저장소에는 없습니다. TS 처리기는 자기 저장소만 뒤지고 없으면 경고합니다(출력). 파이썬도 켜면 자기 저장소에서 get 하고 없는 것은 빼므로 0개입니다 — 15/refs.py 에서 다른 처리기의 작업이 조용히 빠진 것과 같습니다(파이썬).

5장

진행 상황 스트리밍 — 기획 에이전트 자신의 SSE

스트림 둘의 이벤트 → say ×3 → 상태 갱신 하나의 와이어 → ask 가 보이는 것 ×3 → AUTH_REQUIRED 에서 닫힌다 → 둘째 스트림의 첫 이벤트 → 계획서 ×3 → 계획서의 와이어 → 정리

사용자가 받는 스트림은 둘 — 결재에서 한 번 닫히고, "승인" 으로 다시 열린다

6장의 파이썬 메시에서 ask 와 기획 에이전트 사이의 탭입니다. 두 SendStreamingMessage 의 이벤트 종류와 상태만 골랐습니다.

  • 첫 스트림: task(SUBMITTED) 하나, 걸음마다 statusUpdate WORKING 다섯, 결재를 묻는 statusUpdate AUTH_REQUIRED 로 끝납니다. 걸음 사이의 동료 호출은 사용자에게 보이지 않습니다 — 보이는 것은 기획 에이전트가 고른 문장뿐입니다.
  • 둘째 스트림: 계획서 artifactUpdate, WORKING 한 번, COMPLETED. 같은 작업 id 의 두 스트림입니다.

say ×3 — 서버 기록에 한 줄, 스트림에 상태 갱신 하나

진행 알림은 세 언어 모두 한 메서드입니다. 걸음마다 부르고, 끝맺는 상태(FAILED·AUTH_REQUIRED)도 이것으로 냅니다.

  • 파이썬은 SDK 의 TaskUpdater.update_status, TypeScript·Go 는 완성 에이전트의 공용 Updater.status·Status 가 statusUpdate 이벤트를 짓습니다(10부의 식사 에이전트와 같은 부품).
  • Go 의 say 는 yield 의 결과(bool)를 돌려주지만 plan 은 그 값을 보지 않고 다음 걸음으로 갑니다(3장의 plan). 공용 Updater 의 주석은 "메서드가 false 를 돌려주면 받는 쪽이 끝난 것이니 실행을 멈춘다" 인데(agents/common/begin.go), 기획 에이전트는 그 약속을 지키지 않는 셈입니다. 이 장의 실행에서는 받는 쪽이 먼저 끝나지 않아 드러나지 않았습니다.

상태 갱신 하나 — 에이전트 메시지에 새 messageId, 맥락은 동료가 받은 것과 같다

첫 스트림의 넷째 이벤트(숙소 견적)입니다.

  • status.message 는 ROLE_AGENT 메시지 하나이고, say 를 부를 때마다 새 messageId 입니다. taskId 는 기획 작업, contextId <id2> 는 3장에서 동료 셋이 받은 맥락 그 값입니다.
  • 견적은 글 한 줄로만 갑니다. 견적의 DataPart 를 사용자에게 흘리지 않고, 끝의 계획서에 모읍니다.

ask 가 보인 것 ×3 — 첫 스트림은 글자까지 같고, 둘째 스트림의 첫 줄만 다르다

세 메시의 ask 화면입니다. 파이썬은 통째로, TypeScript·Go 는 다른 줄이 드러나게 앞뒤만 골랐습니다.

낯익은 한 줄 — > 승인 뒤의 task WORKING 은 1장의 되묻기에서 본 그 줄입니다(1장). TS·Go 의 begin() 이 이어 말하기마다 작업을 다시 싣기 때문입니다. ask 는 DataPart 의 실수를 정수로 보이므로(tidy) 파이썬 요약의 30.0 도 30 으로 찍혔습니다.

AUTH_REQUIRED 에서 스트림이 닫혀야 ask 가 "승인" 을 보낸다

ask 는 스트림이 끝나야 다음 답을 보냅니다. 마지막 상태가 멈춤(INPUT_REQUIRED·AUTH_REQUIRED)이면 남은 답을 같은 taskId·contextId 의 새 메시지로 보냅니다.

  • SDK 의 기본값이라면 TypeScript·Go 서버는 AUTH_REQUIRED 뒤에도 스트림을 열어 둡니다(10부). 그러면 async for 가 끝나지 않아 ask 는 "승인" 을 보내지 못한 채 기다립니다.
  • 완성 에이전트는 셋 다 AUTH_REQUIRED 에서 닫히게 맞춰 두었고(10부 — TS keepBusAliveStates, Go waiter), 기획 에이전트도 그 serve·Serve 로 뜹니다. 그래서 세 메시 모두 AUTH_REQUIRED 이벤트 다음이 곧 둘째 POST 입니다.
  • Go 는 실행기가 AwaitReply 에 멈춘 채 첫 스트림만 닫힙니다. 둘째 요청은 waiter 가 받아 그 실행기에 넘기고, 이어지는 이벤트를 새 스트림으로 흘립니다.

둘째 스트림의 첫 이벤트 — 파이썬은 아티팩트, TypeScript·Go 는 작업 전체

  • §3.1.2: 작업 스트림은 "the stream MUST begin with the Task object" 입니다. TS·Go 는 이어 말하기에서도 지금의 작업(WORKING, 이력 포함)을 먼저 싣고, 파이썬은 싣지 않습니다 — 파이썬 SDK 1.2.2 가 이어 말하기에서 다시 실은 Task 를 받으면 이번 사용자 메시지를 이력에서 버리기 때문입니다(agents/common.py 의 begin 주석, 5부).
  • Go·TS 의 이력에는 사용자의 두 말 사이에 say 가 낸 에이전트 메시지 여섯이 들었습니다. 넣는 때는 다릅니다 — TS SDK 는 상태 갱신이 올 때 그 메시지를 곧바로 덧붙이고(server/index.js:2368–2373), Go SDK 는 다음 상태 갱신이 올 때 앞의 메시지를 옮깁니다(a2aevent/event.go:119). 마지막 AUTH_REQUIRED 메시지는 완성 에이전트의 working 이 옮겼습니다(agents/common/begin.go).

계획서 — 아티팩트 하나에 파트 둘, 사람이 읽을 마크다운과 프로그램이 읽을 요약

정산이 COMPLETED 면 finish 가 계획서를 짓습니다. 카드의 defaultOutputModes(text/markdown·application/json, 1장)가 바로 이 두 파트입니다. 파이썬판입니다.

  • 정산이 COMPLETED 가 아니면(반려·예산 초과) 정산의 까닭을 붙여 REJECTED 입니다 — 7장의 몫입니다.
  • 마크다운은 plan_markdown 이 견적 셋과 정산서로 씁니다. TextPart 에 media_type="text/markdown" 을 달아 "글이지만 마크다운" 임을 알립니다.
  • 요약 DataPart 는 풀이 결과(req)에 정산서의 total 하나를 더한 것입니다. 숙소·식사·교통의 금액은 요약에 없고 마크다운에만 있습니다.
  • 아티팩트 id 는 정해진 workshop-plan 입니다. 한 작업에 계획서는 하나뿐이라 겹칠 일이 없습니다.

TypeScript·Go — 같은 두 파트, Go 는 요약을 구조체에서 map 으로 바꿔 싣는다

  • TypeScript 는 { ...req, total } 로 파이썬과 같은 꼴을, Go 는 common.Plain(req) 로 workshop.Parsed 구조체를 JSON 꼴의 map 으로 바꾼 뒤 total 을 더합니다.
  • 세 언어 모두 아티팩트 다음에 WORKING "계획서를 완성했습니다", 그다음 COMPLETED 를 냅니다 — 스트림 둘의 끝 세 이벤트입니다.

계획서의 와이어 — mediaType 이 달린 글 파트와, 언어마다 숫자가 다른 요약

둘째 스트림의 artifactUpdate 입니다. 마크다운 글은 한 줄이 너무 길어 뺐습니다(ask 의 화면에 그대로 있습니다).

  • 파이썬의 요약은 30.0·4842000.0 입니다 — 기획 에이전트가 int(sheet["total"]) 로 정수를 넣어도 Struct 를 지나며 double 이 됩니다(4부). Go·TS 는 30·4842000 입니다. 6장의 대조기는 그래서 수의 값으로 견줍니다.
  • append·lastChunk 가 없습니다 — 한 번에 다 보낸 아티팩트라 둘 다 기본값(false)이고, 세 SDK 모두 기본값을 적지 않습니다(10부).

대조기의 기댓값은 골든 파일에서 — 손으로 적은 숫자가 없다

세 언어의 workshop 이 지키는 골든 벡터(ex/fixtures/golden/domain.json)에서 이야기 한 문장의 경우를 꺼내, 계획서에 있어야 할 글로 바꿉니다.

대조기 — 이야기를 다시 돌리지 않고, ListTasks 로 끝난 작업의 계획서를 읽는다

  • status=TASK_STATE_COMPLETED 로 거르고 include_artifacts=True 를 줍니다 — 주지 않으면 서버는 artifacts 를 빼야 합니다(11부). 대본 하나를 끝낸 기획 에이전트에는 끝난 작업이 하나뿐이라 [task] = 로 받습니다.
  • 마크다운은 줄 머리(- 숙소: …)마다 기댓값의 글이 다 들었는지, 요약은 키마다 같은 값인지 봅니다. 하나라도 틀리면 종료 코드 1 이라 명세가 실패합니다.
  • ListTasks 도 카드의 주소로 갑니다. 기획 에이전트 앞에 탭이 있는 단일 메시에서는 탭에 이 요청이 하나 더 찍힙니다(와이어 요약).

파이썬 메시 — 다섯 에이전트 앞에 탭 다섯, 대조기는 여섯 줄 모두 ✓

4·5장의 와이어가 모두 이 명세에서 나왔습니다. 동료는 카드의 url 을 탭으로 알리고, 기획 에이전트는 탭 포트만 받는 겉층(15/planner_via.py)으로 띄웁니다.

ask 의 화면은 5장에 통째로 있습니다. 계획서의 마크다운 네 줄과 요약 여덟 키가 골든과 맞았습니다.

TypeScript 메시 — 같은 명세에 언어만 바꿔, 대조기는 같은 여섯 줄

  • 명세는 파이썬 메시에서 포트와 언어 머리(ts:)만 바꾼 꼴입니다. 대조기는 언제나 파이썬입니다 — 기획 에이전트가 어느 언어든 같은 A2A 로 묻습니다.
  • TS 요약의 숫자는 30, 파이썬 요약은 30.0 이었지만(5장) 둘 다 같은 값으로 맞았습니다.

Go 메시 — 다섯 Go 프로그램과 겉층 하나, 역시 여섯 줄

겉층의 수법 — 2장의 15/planner_at 과 같이, 완성 기획 에이전트 파일의 심볼릭 링크(agent.go)와 같은 package 에서 init() 이 os.Args 를 바꿉니다(2장).

섞인 메시 ② 기획 TypeScript → 숙소 파이썬 · 식사 Go · 교통 TypeScript · 정산 파이썬

근거 경고는 정산 서버의 것 — TS 기획 에이전트가 근거 셋을 보냈지만 정산이 파이썬이라 "not found" 가 없습니다. 경고를 내는 것은 보내는 쪽이 아니라 받는 TS 처리기입니다(4장). 명세의 끝 네 줄(ask·대조기)은 ① 과 같은 꼴이라 뺐습니다.

섞인 메시 ③ 기획 Go → 숙소 TypeScript · 식사 파이썬 · 교통 Go · 정산 TypeScript

세 언어 모두 기획을 맡았다 — ①②③ 의 기획 에이전트가 파이썬·TypeScript·Go 하나씩이고, 셋 다 같은 계획서를 냈습니다. 정산이 TS 인 판(mesh_ts, ③)에서만 근거 경고가 찍혔습니다.

언어가 갈리는 정산 요청 — 파이썬의 2100000.0 을 Go 정산이 2100000 으로 저장했다

① 의 정산 탭입니다. 파이썬 기획 에이전트가 보낸 금액과, Go 정산 에이전트가 답에 실은 이력의 같은 금액을 골랐습니다.

  • 요청의 숫자는 파이썬 Struct 의 double 이고, Go 정산이 저장해 되돌려 준 이력에는 정수 꼴입니다 — Go 는 JSON 수를 float64 로 읽고, 소수부가 없는 값을 다시 쓸 때 .0 을 붙이지 않습니다. 둘은 JSON 으로 같은 수입니다.
  • Go 정산은 itemsOf 의 주석대로 "amount 는 30.0 꼴일 수 있다" 를 알고 정수로 바꿔 계산합니다. 그래서 AUTH_REQUIRED 의 합계가 같은 4,842,000 이었습니다.

6장 퀴즈

Q. 섞인 메시 ② 에서 TS 기획 에이전트는 정산에 근거 셋을 보냈는데 "Reference task … not found." 가 찍히지 않았고, ③ 에서는 찍혔습니다. 무엇이 갈랐습니까? 대조기의 결과는 두 판에서 어땠습니까?

A. 정산 에이전트의 언어입니다. 경고는 근거를 자기 저장소에서 찾아보는 TS 요청 처리기가 받는 쪽에서 냅니다 — ② 의 정산은 파이썬, ③ 의 정산은 TS 였습니다(②·③). 대조기는 두 판 모두 여섯 줄 ✓ 였습니다 — 근거는 정산의 계산에 쓰이지 않습니다(4장).
