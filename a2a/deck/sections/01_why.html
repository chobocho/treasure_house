1부

왜 A2A인가 — MCP와의 관계·역사

문제, 원칙, 이웃 프로토콜, 연표, v0.3 → v1.0, 스펙의 지도 — 뒤의 부에서 찍은 캡처로 확인합니다

이 부는 "왜" 를 다룬다 — 주장마다 출처나 캡처가 붙는다

2부부터는 와이어와 코드를 읽습니다. 그 전에 A2A 가 무슨 문제를 풀려고 나왔고, 어떤 원칙으로 짜였고, MCP 와 어떻게 나뉘며, 어떤 판을 거쳐 v1.0.1 에 왔는지를 봅니다. 이 부는 2~17부보다 나중에 썼습니다. 그래서 원칙 하나하나를 그것을 보여 준 뒤쪽 슬라이드의 캡처로 확인합니다.

장무엇을증거
1장문제 — 표준이 없을 때의 점대점 통합, 도구로 감싸기, 불투명한 상대16부 3×3, 15부 섞인 메시
2장설계 원칙 — 스펙 §1.1·§1.2원칙마다 뒤쪽 캡처 하나
3장MCP 와 A2A — 도구 호출과 동료 위임출처 문서(Anthropic·A2A)
4장역사 — 발표, 리눅스 재단, 0.2·0.3, 1.0, 1.0.1출처 문서와 CHANGELOG·릴리스 기록
5장v0.3 → v1.0 — 메서드 이름, enum, kind, 카드변경마다 그것을 쓴 부의 캡처
6장스펙 문서의 구조 — 세 층, proto 가 규범13부의 "한 작업, 세 문"
이 부의 규칙 — 날짜·판·조직에 대한 말은 받아 둔 출처 글에서 근거 문장이 맞아야만 씁니다(링크 "출처" 에 그 문장이 들어 있습니다). MCP 에 대해서는 출처 문서가 말하는 만큼만 말합니다. 동작에 대한 말은 이 책이 이 기계에서 찍은 캡처로 보입니다.

1장

문제 — 에이전트끼리 말하는 표준이 없을 때

워크숍 이야기의 모양 → 점대점 통합(N×M) → 표준 하나면 N+M: 3×3 실측 → 에이전트를 도구로 감싸면 → 속을 모르는 상대 → A2A 가 정한 것 네 가지

일을 혼자 하지 않는 에이전트 — 기획 에이전트는 동료 넷에게 맡겨야 한다

이 책의 이야기는 A2A 문서가 드는 "해외 여행 계획" 예(항공·호텔·투어·환전 에이전트)와 같은 모양입니다. 보물상사 기획 에이전트는 숙소·식사·교통·정산을 각자 잘하는 에이전트에 맡깁니다. 아래는 다섯 에이전트가 카드에 적은 스킬입니다.

여기서 생기는 물음 — 기획 에이전트는 어떻게 동료를 찾고(발견), 어떤 모양으로 일을 넘기고(메시지), 오래 걸리는 일의 진행을 어떻게 받고(작업과 상태), 결과를 무엇으로 받는가(아티팩트). 문서는 표준이 없으면 이 에이전트들이 "isolated" 로 남는다고 적습니다.

표준이 없으면 점대점(point-to-point) 통합을 짠다 — N 곳이 M 곳에 맡기면 N×M 개

A2A 문서는 표준 없는 통합의 첫 문제를 이렇게 적습니다 — "Each interaction requires custom, point-to-point solutions, creating significant engineering overhead". 맡기는 쪽과 맡는 쪽이 각자 제 방식을 쓰면, 짝 하나마다 어댑터가 하나씩 생깁니다.

 표준이 없을 때 — 짝마다 어댑터     표준이 있을 때 — 각자 한 번
  기획 py ─┬─ 숙소 go               기획 py ─┐
  기획 ts ─┼─ 식사 ts               기획 ts ─┼─ A2A ─┬─ 숙소
  기획 go ─┴─ 교통 py               기획 go ─┘       ├─ 식사
  선마다 따로 짠 통합: 3×3 = 9                        └─ 교통
                                    한 번씩만 구현: 3+3 = 6
같은 논리, 다른 대상 — MCP 를 발표한 글도 데이터 쪽에서 같은 말을 했습니다 — "Every new data source requires its own custom implementation, making truly connected systems difficult to scale". 둘의 차이는 3장에서 봅니다.

표준 하나면 짝마다 짤 것이 없다 — 세 클라이언트 × 세 서버, 아홉 칸이 같은 견적

16부의 3×3 매트릭스 가운데 숙소 에이전트 줄입니다. 파이썬·TS·Go 로 쓴 총무팀 CLI(ask) 셋이, 파이썬·TS·Go 로 쓴 숙소 에이전트 셋에 같은 일을 맡겼습니다. 짝에 맞춘 코드는 한 줄도 없습니다.

N×M 이 N+M 으로 — 클라이언트 셋, 서버 셋을 각자 A2A 에 맞춰 한 번씩 썼을 뿐인데 아홉 짝이 모두 되묻기 한 번과 "total": 2100000 으로 끝났습니다. 다섯 에이전트 45칸 전체는 16부에 있습니다.

에이전트를 도구로 감싸면 되묻지 못한다 — 숙소 에이전트는 세 번 되물었다

표준이 없을 때 흔한 길은 상대 에이전트를 함수 하나("도구")로 감싸는 것입니다. A2A 문서는 "Wrapping agents as tools limits their capabilities" 라고 합니다. 발표 글도 "without limiting an agent to a 'tool'" 을 원칙으로 들었습니다. 무엇이 제한되는지는 대화 한 번으로 보입니다.

입력이 모자라면 일이 멈추고 묻는다 — 날짜·박 수·인원이 빠지자 에이전트는 실패하지 않고 INPUT_REQUIRED 로 되물었고, 같은 작업이 세 번의 답 뒤에 COMPLETED 가 됐습니다(5부 5장). 인자를 받아 값을 돌려주는 함수 꼴에는 이 "멈추고 묻기" 를 담을 자리가 없습니다.

상대의 속은 모른다 — 기획 에이전트는 동료가 무슨 언어인지도 모른 채 맡겼다

다른 회사의 에이전트라면 코드도, 쓰는 모델도, 내부 도구도 볼 수 없습니다. A2A 는 이것을 전제로 짭니다(§1 "independent, potentially opaque AI agent systems"). 15부의 섞인 메시 ① 에서 파이썬 기획 에이전트가 맡긴 동료들입니다.

본 것은 카드와 와이어뿐 — 기획 에이전트 코드는 동료의 언어를 묻지 않고, 카드의 스킬 태그로 고르고 메시지로 맡겼습니다(15부). 세 언어가 섞인 메시가 단일 언어 메시와 같은 계획서를 냈습니다.

A2A 가 정한 것은 넷 — 카드, 작업, 메시지, 파트

처음 발표한 글은 A2A 를 "client" 에이전트와 "remote" 에이전트 사이의 통신으로 설명했습니다. 이 책의 첫 요청 하나에 그 뼈대가 다 들어 있습니다.

발표 글의 말v1.0 에서이 책
Capability discovery — "Agent Card"에이전트 카드(Agent Card)3부
Task management작업(Task)·상태 기계5부
Collaboration — messages메시지(Message), role4부
User experience negotiation — "parts"파트(Part) — 글·파일·데이터4부 2장

1장 퀴즈

Q. 숙소 에이전트 구현이 넷(파이썬·TS·Go·맨손)이고, 그것을 부르는 클라이언트 구현이 넷이라고 합시다. 점대점 통합을 짜면 몇 개를 짜야 하고, 모두 A2A 를 따르면 몇 개를 짜면 됩니까? 이 책의 어느 캡처가 그 계산을 받쳐 줍니까?

A. 점대점이면 4×4 = 16 개, A2A 를 따르면 각자 한 번씩 4+4 = 8 개입니다. 3×3 캡처가 받쳐 줍니다 — 클라이언트 셋과 서버 셋을 짝을 의식하지 않고 썼는데 아홉 칸이 모두 되묻기 한 번과 "total": 2100000 으로 끝났습니다. 맨손 구현까지 섞은 교차 시험은 6부 7장에 있습니다.

2장

A2A 의 설계 원칙 — §1.1·§1.2

목표 여섯 → 원칙 다섯 → 발표 때의 원칙과 견주기 → Simple: 빌려 쓴 표준 → Enterprise Ready: HTTP 인증 그대로 → Async First: 기다리지 않는 작업 → Modality Agnostic: 파트 셋 → Opaque Execution: 카드만 본다 → 불투명성의 값

스펙의 목표는 여섯 — 이 책의 부들이 하나씩 맡는다

스펙 §1.1 "Key Goals of A2A" 의 여섯 줄입니다. 목표마다 그것을 실제로 돌려 본 부를 붙였습니다.

짝은 이 책이 지은 것 — 출처 두 곳은 서로를 가리키지 않습니다. 위의 짝짓기는 뜻이 가까운 것끼리 이 책이 맞춘 것입니다. 오디오·비디오를 두고 발표 글은 "streaming" 을, v1.0.1 §1.2 는 "via file references" 를 적습니다.

Simple — 스트림은 그냥 SSE 다: text/event-stream 에 이벤트 열 개

A2A 는 전송을 새로 만들지 않았습니다. 10부에서 식사 에이전트 셋의 스트림을 SDK 없이 읽은 결과입니다 — HTTP 응답의 Content-Type 은 SSE 그대로이고, 이벤트 하나가 data: 하나입니다.

빌려 쓴 셋 — 요청은 JSON-RPC 2.0 봉투(2부 3장), 스트림은 SSE(2부 4장), 그 아래는 평범한 HTTP 입니다. 그래서 2부는 A2A 없이 이 셋만 손에 익히고, 3부부터의 와이어는 그 위에 올린 이름과 필드만 새로 배웁니다.

Enterprise Ready — 인증은 HTTP 의 것을 그대로: 401, WWW-Authenticate, Bearer

§1.2 는 인증·인가를 "established enterprise practices" 에 맞춘다고 합니다. 12부의 정산 에이전트 셋은 토큰 없는 요청에 HTTP 의 401 과 표준 머리글로 답했고, 클라이언트는 OAuth2 토큰을 받아 다시 보냈습니다.

A2A 가 새로 정한 것은 "어디에 적나" 뿐 — 어떤 스킴을 쓰는지는 카드의 securitySchemes 에 적고(12부 2장), 토큰 자체는 OAuth2 그대로입니다(3장). 추적·감시 쪽은 17부 3장이 SDK 마다 무엇이 있는지 확인했습니다.

Async First — 맡기고 바로 돌아오고, 소식은 나중에 웹훅으로 받는다

교통 에이전트의 배차는 단계가 셋인 긴 일입니다. 5부에서 returnImmediately 로 맡기자 세 클라이언트 모두 SUBMITTED 를 곧장 받았고, 11부에서는 연결 없이 웹훅으로 단계마다 소식을 받았습니다.

기다리는 쪽이 연결을 붙들지 않는다 — §1.2 의 "Async First: Designed for (potentially very) long-running tasks and human-in-the-loop interactions". 사람을 기다리는 쪽은 12부의 AUTH_REQUIRED(팀장 결재)가 보였습니다.

Modality Agnostic — 글·파일·데이터를 한 메시지에: 식단표는 menu.md 파일로 왔다

파트(Part)는 내용 필드 넷(text·raw·url·data) 가운데 하나를 갖고, 옆에 mediaType 을 답니다(4부 2장). 식사 에이전트가 낸 아티팩트 가운데 파일 하나입니다.

§1.2 가 든 것과 이 책이 쓴 것 — §1.2 는 "text, audio/video (via file references), structured data/forms, and potentially embedded UI components" 를 듭니다. 이 책의 에이전트는 글, text/markdown 파일, JSON 데이터만 씁니다. 오디오·비디오도 같은 raw/url 파트에 mediaType 만 다르게 실립니다.

Opaque Execution — 기획 에이전트가 동료에 대해 아는 것은 카드의 몇 줄이다

§1.2 "Agents collaborate based on declared capabilities and exchanged information, without needing to share their internal thoughts, plans, or tool implementations". 15부의 기획 에이전트가 동료를 고를 때 읽는 것은 이것뿐입니다.

"declared capabilities" 의 실제 — 기획 에이전트는 workshop 이 아닌 태그(lodging·meals·transport·budget)로 역할을 고릅니다(15부 역할표). 숙소 에이전트가 견적을 무엇으로 계산하는지(workshop 모듈)는 카드에도, 와이어에도 없습니다. 정산 에이전트는 실제 정산 스킬을 공개 카드에 적지도 않습니다(12부 확장 카드).

불투명성의 값 — 거절의 까닭은 상대가 적어 준 글 한 줄이 전부다

속을 감추면 실패의 속도 감춰집니다. 15부의 실패 경로에서 숙소 에이전트가 거절하자, 기획 에이전트가 사용자에게 전할 수 있었던 것은 숙소가 status.message 에 적은 글뿐이었습니다.

까닭이 둘인데 글은 같다 — 첫 요청은 날짜(모든 숙소가 쉬는 날) 탓이고 둘째는 인원(70명) 탓인데, 둘 다 "가능한 숙소가 없습니다" 입니다. 왜 안 되는지를 더 알리려면 맡는 쪽이 데이터 파트 같은 것으로 스스로 밝혀야 합니다 — 숙소 에이전트는 되물을 때 {"missing": [...]} 를 그렇게 실었습니다(1장).

2장 퀴즈

Q. 교통 에이전트에 returnImmediately 로 배차를 맡긴 클라이언트가, 그 뒤 연결을 하나도 열어 두지 않고 "차량 확정" 단계를 알았습니다. 어떤 길로 알았고, 그 길에서 받은 이벤트는 몇 개입니까? 폴링으로 2초마다 물었다면 무엇이 달랐습니까?

A. 푸시 알림(웹훅)입니다. 수신기 캡처에 #1~#6 여섯 이벤트가 왔고, #4 가 차량 확정 입니다. 2초 폴링은 일곱 번 물었는데 그중 셋은 바뀐 것 없는 답이었고, 차량 확정 은 한 번도 보지 못했습니다(11부 2장).

3장

MCP 와 A2A — 도구 호출과 동료 위임

MCP 는 무엇인가(출처가 말하는 만큼) → 도구와 동료의 차이 → "보완한다" 는 말의 이력 → 함께 쓰는 그림 → 정비소 예를 워크숍에 → 이 책에서 MCP 가 들어갈 자리 → 스킬을 도구로 내놓기

MCP 는 에이전트를 데이터와 도구에 잇는 표준이다 — Anthropic 이 먼저 공개했다

Anthropic 은 MCP(Model Context Protocol)를 공개하며 "Today, we're open-sourcing the Model Context Protocol (MCP)" 라고 썼습니다. 같은 글이 밝힌 대상은 "AI assistants" 와 "the systems where data lives" — 콘텐츠 저장소, 업무 도구, 개발 환경입니다.

발표 글의 말뜻
"developers can either expose their data through MCP servers or build AI applications (MCP clients) that connect to these servers"데이터를 내놓는 쪽이 MCP 서버, 그것을 쓰는 AI 앱이 MCP 클라이언트
"replacing fragmented integrations with a single protocol"1장의 N×M 과 같은 논리를 데이터 쪽에 쓴 것
이 책이 MCP 에 대해 말하는 범위 — MCP 의 와이어나 메서드는 다루지 않습니다. 이 장의 MCP 이야기는 위 발표 글과 A2A 쪽 문서(주제 문서 "A2A and MCP", 스펙 부록 B, v1.0 안내)가 적은 것에서 멈춥니다.

도구는 입력을 받아 값을 낸다, 동료는 일을 맡아 상태를 가진다

A2A 문서의 비교 주제 문서는 무엇과 상호작용하느냐로 둘을 가릅니다.

도구·자원 — MCP 의 영역에이전트 — A2A 의 영역
성격입출력이 잘 정의된 기본 단위, "They perform specific, often stateless, functions"추론하고 계획하고 여러 도구를 쓰며, 긴 상호작용 동안 상태를 지닌다
예계산기, DB 조회 API, 날씨 조회청구 에이전트에 문의를 넘기는 상담 에이전트, 항공·호텔 에이전트를 엮는 여행 에이전트
한 줄"A2A focuses on agents partnering on tasks, whereas MCP focuses on agents using capabilities"
이 책에서 "상태" 는 작업이다 — 숙소 에이전트에게 맡긴 일은 INPUT_REQUIRED 에서 멈췄다가 같은 작업 id 로 이어졌습니다(5부). "동료" 쪽의 특징인 여러 턴의 대화가 와이어에서는 이 작업 하나로 보입니다.

A2A 는 처음부터 "MCP 를 보완한다" 고 했고, 1.0 에서 다시 말해야 했다

발표 글: "A2A is an open protocol that complements Anthropic's Model Context Protocol (MCP), which provides helpful tools and context to agents". 1.0 발표 글은 같은 말을 따로 한 절로 다시 적었습니다.

문서말
1.0 발표 — 절 제목 "Complementary to MCP, not a replacement""a point that has generated confusion in early ecosystem discussions"
1.0 발표"MCP and A2A solve different layers of the problem"
whats-new-v1.md"MCP handles tool/resource integration, A2A handles agent-to-agent coordination"
헷갈림이 있었다는 것까지가 출처의 말 — 누가 어떻게 헷갈렸는지, 어느 쪽이 더 쓰이는지는 출처가 말하지 않으므로 이 책도 말하지 않습니다.

함께 쓰는 그림 — 에이전트 사이는 A2A, 에이전트 안쪽은 MCP

1.0 발표 글의 한 줄 요약은 "In practice, many systems will use both: MCP inside agents, A2A between agents" 입니다. 스펙 부록 B 도 같은 그림을 그립니다 — "The Server agent, in turn, might use MCP to interact with several underlying tools, APIs, or data sources".

 사용자 ── A2A ──→ 에이전트 A ── A2A ──→ 에이전트 B
                   (클라이언트)            (서버)
                                            │ MCP
                                     ┌──────┴──────┐
                                   도구 1        도구 2
층이 다르다 — A2A 의 상대는 "속을 모르는 동료"(2장)이고, MCP 의 상대는 그 동료가 제 일을 하려고 쥐는 도구입니다. 그래서 A 는 B 가 MCP 를 쓰는지조차 알 필요가 없습니다.

정비소 예를 워크숍에 옮기면 — 대화와 위임은 A2A, 진단기 호출은 MCP

주제 문서는 "Consider an auto repair shop staffed by autonomous AI agent 'mechanics'" 로 예를 듭니다. 장면마다 쓰는 프로토콜을 적고, 이 책의 이야기에서 같은 자리를 찾았습니다.

정비소(주제 문서)프로토콜워크숍(이 책)
손님 → 정비소 관리 에이전트 "덜컹거려요"A2A총무팀 ask → 기획 에이전트
관리 에이전트의 여러 턴 진단 대화A2A기획·숙소 에이전트의 되묻기(15부)
정비공 에이전트가 진단기·정비 매뉴얼·리프트를 부름MCP숙소 에이전트 안의 workshop.choose_lodging — 이 책은 MCP 없이 함수로 부른다
정비공 → 부품 공급 에이전트에 주문A2A기획 → 숙소·식사·교통·정산(15부)

이 책에서 MCP 가 들어갈 자리는 실행기 안이다 — 와이어에는 흔적이 없다

숙소 에이전트(파이썬)의 실행기에서 견적을 내는 부분입니다. 계산은 domain.choose_lodging 함수 하나가 하고, A2A 가 보는 것은 그 결과를 실은 아티팩트와 상태뿐입니다(7부).

바꿔 끼울 수 있는 자리 — 이 함수 호출이 실제 숙소 예약 시스템이었다면, 스펙 부록 B 의 그림대로 그것을 MCP 도구로 부르는 것이 이 자리입니다. 어느 쪽이든 up.add_artifact·up.complete 아래의 와이어는 같습니다. 이 책이 MCP 를 돌리지 않는 까닭은 에이전트를 규칙으로만 짠 데 있습니다(0부).

거꾸로, A2A 에이전트의 스킬을 MCP 도구로 내놓을 수도 있다 — 단, 잃는 것이 있다

주제 문서는 이 길도 적습니다 — "An A2A server could expose some of its skills as MCP-compatible resources", 특히 잘 정의되고 상태 없이 부를 수 있는 스킬이라면. 바로 뒤에 A2A 의 강점은 그 너머의 "flexible, stateful, and collaborative interactions" 라고 덧붙입니다.

이 책의 스킬도구로 감싸기 쉬운가까닭(캡처)
숙소 find-lodging입력이 다 있으면 쉽다날짜·박 수·인원을 다 주면 한 번에 끝난다(5부), 모자라면 되묻는다(1장)
교통 book-bus어렵다단계가 셋인 긴 일, 취소 가능(11부)
정산 settle-budget어렵다도중에 사람의 결재를 기다린다(12부)
표는 이 책의 판단 — 어느 스킬을 도구로 내놓을지는 문서가 정하지 않습니다. 기준은 문서가 든 두 말, "well-defined" 와 "stateless" 입니다.

3장 퀴즈

Q. 기획 에이전트가 숙소 에이전트에 일을 맡기는데, 숙소 에이전트가 견적 계산을 MCP 도구 호출로 바꿨습니다. 기획 에이전트 쪽 코드나 와이어에서 달라지는 것이 있습니까?

A. 없습니다. 기획 에이전트가 보는 것은 카드(2장)와 작업의 상태·아티팩트이고, 견적 계산은 실행기 안의 일입니다. 15부의 섞인 메시에서 동료의 언어가 바뀌어도 기획 쪽 화면에 드러나지 않은 것(1장)과 같은 까닭입니다 — "MCP inside agents, A2A between agents".

4장 퀴즈

Q. 어떤 글이 "A2A v0.2.0 은 2025-06-09 에 나왔다" 고 적었습니다. 이 책의 출처로 보아 이 문장의 문제는 무엇입니까? 그리고 오늘 서버에 /.well-known/agent.json 을 물어 404 를 받았다면, 그 클라이언트는 어느 판 이전의 규칙을 따른 것입니까?

A. 2025-06-09 는 GitHub 에 릴리스가 올라온 날일 뿐입니다 — 뒤 판인 v0.2.1 이 이미 2025-05-27 에 나왔으므로 나중에 채워 넣은 기록입니다(날짜 함정). 카드 경로를 agent-card.json 으로 바꾼 것은 0.3.0 이니(0.3.0), 그 클라이언트는 0.3.0 이전의 이름을 쓴 것입니다.

v0.3 → v1.0 — 무엇이 바뀌었나

enum 값 — "user" 는 "ROLE_USER" 로: 옛 값을 보내면 세 서버가 세 가지로 받았다

"Enum values changed from kebab-case to SCREAMING_SNAKE_CASE for compliance with the ProtoJSON specification". CHANGELOG 의 말로는 "Align enum format with ADR-001 ProtoJSON specification" 입니다. 4부에서 v0.3 의 "role": "user" 를 v1.0 서버 셋에 보냈습니다.

  • v0.3 의 "user" — 파이썬은 거절, TS 는 UNRECOGNIZED 로 받고 일했고, Go 는 글자 그대로 user 를 받았습니다(4부 8장).
  • 작업 상태도 같습니다 — "completed" → "TASK_STATE_COMPLETED", "input-required" → "TASK_STATE_INPUT_REQUIRED"(5부 2장).

kind 가 사라졌다 — 들어 있는 필드가 곧 종류이고, 옛 kind 는 그냥 무시된다

"Removal of discriminator kind fields in favor of JSON member-based polymorphism". 4부에서 kind 를 붙인 v0.3 꼴 파트를 v1.0 서버(파이썬)에 보낸 와이어입니다.

카드의 문 — 꼭대기의 url·protocolVersion 이 supportedInterfaces 안으로

"preferredTransport and additionalInterfaces consolidated into supportedInterfaces[]", "protocolVersion moved from AgentCard to individual AgentInterface objects". 식사 에이전트 카드의 해당 줄입니다.

  • 문마다 주소·바인딩·판이 따로입니다. 그래서 한 카드에 v0.3 문과 v1.0 문을, JSON-RPC 문과 gRPC 문을 함께 적을 수 있습니다(3부 3장, 13부 4장).

REST 경로에서 /v1 이 빠졌고, 오류는 google.rpc.Status 모양이 됐다

"Removed /v1 prefix from HTTP+JSON URL paths", 그리고 HTTP+JSON 오류는 RFC 9457 대신 "the ProtoJSON representation of google.rpc.Status" 를 씁니다. 13부에서 Go REST 서버에 없는 작업을 물은 와이어입니다.

세 바인딩이 같은 이름표를 단다 — details 의 ErrorInfo 에 reason(TASK_NOT_FOUND)과 domain(a2a-protocol.org)이 붙습니다. JSON-RPC 에서는 같은 것이 error.data 에(5부 9장), gRPC 에서는 상태의 꼬리에 실립니다(13부 3장).

옛 피어와도 말한다 — 카드가 0.3 문만 알리면 v1.0 SDK 클라이언트도 message/send 를 보냈다

1.0 발표 글은 와이어를 깨되 카드는 "both existing v0.3 protocol behavior and v1.0 simultaneously" 를 알릴 수 있게 했다고 합니다. 14부에서 v0.3 문 하나만 가진 숙소 에이전트에 세 v1.0 SDK 클라이언트를 붙였습니다(파이썬 서버 쪽 탭).

판은 머리글로 알린다 — 요청의 A2A-Version: 0.3 과 "method": "message/send" 는 SDK 의 호환 계층이 고른 것입니다. 머리글이 빈 요청은 0.3 으로 읽어야 합니다(§3.6.2 "Agents MUST interpret empty value as 0.3 version", 14부 3장). 아홉 칸 모두 같은 견적을 받았습니다(14부 4장).

5장 퀴즈

Q. v0.3 클라이언트가 v1.0 전용 서버에 {"kind": "text", "text": "숙소"} 파트를 보냈습니다. 파이썬 서버는 이 파트를 어떻게 읽었습니까? 같은 클라이언트가 "role": "user" 를 보냈다면 파이썬 서버의 답은 무엇입니까?

A. kind 는 모르는 필드로 넘기고 text 를 읽었습니다 — 와이어의 답 "1. text '안녕하세요'" 처럼 글 파트가 됩니다. 그러나 "role": "user" 는 v1.0 enum 이름이 아니라서 파이썬은 -32602 Validation failed, message.role: Field is required. 로 거절했습니다(enum 캡처). 둘을 함께 보냈다면 요청 전체가 거절됩니다.

스펙 문서의 구조 — 세 층, 그리고 proto 가 규범

데이터 모델·추상 연산·바인딩 → 절마다 이 책의 어느 부 → proto 가 규범이라는 말의 뜻 → 같은 연산, 세 겉옷 → 문서끼리 어긋나는 곳 → 이 책이 스펙을 읽는 순서

스펙은 세 층이다 — 무엇을 주고받나, 무엇을 할 수 있나, 와이어에 어떻게 싣나

§1.3: "This specification is organized into three distinct layers". 1.0.0 의 CHANGELOG 가 "Large refactor of specification to separate application protocol definition from mapping to transports" 라고 적은 것이 이 나눔입니다.

층이 나뉜 덕 — §1.3 이 드는 까닭은 "New protocol bindings can be added without changing the fundamental data model" 등입니다. 이 책도 그 순서로 갑니다 — 3~5부가 층 1, 5·10·11부가 층 2, 13부가 층 3.

proto 가 규범이다 — 글과 proto 가 다르면 proto 를 믿는다

§1.4: "the file spec/a2a.proto is the single authoritative normative definition of all protocol data objects and request/response messages". 안내 문서는 이것을 v1.0 의 첫 변경으로 꼽습니다 — "Elevate a2a.proto from being a gRPC-specific implementation file to the universal, normative source of truth".

이 책이 proto 에서 읽은 것어디서
필수 필드 — REQUIRED 표시3부 1장
Part 의 oneof, enum 이름과 수4부 2장, 5부 2장
REST 경로 — rpc 마다 붙은 HTTP 주석13부 1장
스펙 글과 proto 가 다른 곳 — :subscribe 의 동사13부 5장
규범과 SDK — §1.4 는 SDK 의 타입도 proto 에서 다시 만들라(MUST)고 합니다. 파이썬(protobuf, 7부 2장)과 TS(ts-proto, 8부 2장)는 그렇게 만들었고, Go SDK 의 핵심 타입은 사람이 쓴 구조체입니다(9부 2장, proto 생성 타입은 gRPC 용으로 따로). enum 을 수로 보냈을 때 Go 만 거절한 것(4부 8장)이 이 차이에서 나왔습니다. 그리고 파일의 실제 자리는 spec/ 이 아니라 specification/a2a.proto 입니다.

같은 연산, 세 겉옷 — JSON-RPC 로 만든 작업을 REST 와 gRPC 로 읽었다

층 2 의 연산은 하나이고 층 3 의 바인딩은 그것을 실어 나를 뿐이라면, 한 바인딩으로 만든 작업을 다른 바인딩으로 읽을 수 있어야 합니다. 13부에서 문이 셋 달린 숙소 에이전트(파이썬·TS·Go)로 확인했습니다.

§5.1 의 동등성 — 여러 바인딩을 열면 기능·동작·오류·인증이 같아야 합니다(13부 1장). 세 서버 모두 "세 문의 작업 id 가 같다: True" 였습니다(13부 4장).

문서끼리도 어긋난다 — v1.0.1 저장소 안에서 찾은 것들

스펙 머리의 안내 상자는 v1.0.1 태그의 문서인데도 "Latest Released Version 1.0.0" 이라고 적습니다. 이 책이 지나며 찾은 어긋남을 한곳에 모았습니다.

이 책이 스펙을 읽는 순서 — proto, 본문의 MUST, 그리고 캡처

문서가 어긋날 수 있으니 무엇을 먼저 믿을지 정해 둡니다. §2.1 은 MUST·SHOULD·MAY 를 RFC 2119 의 뜻으로 읽으라고 합니다.

proto — 이름·필드·필수→ 본문 §3·§5·§7 — MUST·SHOULD→ §6 예시·주제 문서·안내→ SDK 소스와 캡처 — 실제로 무엇을 하나
  • 앞의 셋이 무엇이 맞는가를 정하고, 마지막이 세 SDK 가 실제로 무엇을 하는가를 보입니다. 둘이 다르면 슬라이드에 둘 다 적었습니다(예: 16부 3장의 오류 표, 4장의 TCK).
  • 슬라이드의 영어 따옴표는 스펙에서 옮긴 그대로이고, 번호(§)는 v1.0.1 specification.md 의 절입니다.

6장 퀴즈

Q. 스펙 본문의 표는 REST SubscribeToTask 를 POST 라 하고 proto 의 HTTP 주석은 GET 이라 합니다. §1.4 에 따르면 어느 쪽이 규범입니까? 그런데도 이 책의 세 서버에서 클라이언트가 어느 쪽을 써도 문제가 없었던 까닭은 무엇입니까?

A. §1.4 는 proto 를 "the single authoritative normative definition" 이라 하므로 proto(GET)입니다(proto 가 규범). 다만 13부에서 세 서버가 GET 과 POST 를 모두 받았고, 세 SDK 클라이언트는 모두 POST 를 보냈습니다(13부 5장). 서버가 둘 다 받아 주는 동안은 어긋남이 와이어에 드러나지 않습니다.
