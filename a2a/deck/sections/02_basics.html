2부

바탕 지식 — HTTP·JSON-RPC 2.0·SSE (맨손, 3언어)

A2A 가 빌려 쓰는 세 표준을 표준 라이브러리만으로 직접 만져 봅니다

A2A 는 새 전송 기술을 만들지 않았다

스펙 §1.2 의 첫 원칙은 "Simple: Reuse existing, well-understood standards (HTTP, JSON-RPC 2.0, Server-Sent Events)" 입니다. 이 세 가지를 손에 익혀 두면 3부부터 나오는 와이어가 전부 읽힙니다.

장무엇을세 언어
1장HTTP 한 장 요약, curl, 와이어 탭 읽는 법파이썬
2장JSON — 직렬화, camelCase, 큰 정수와 30.0, null 과 빠진 필드py·ts·go
3장JSON-RPC 2.0 — 요청·응답·오류·알림·배치py·ts·go
4장SSE — text/event-stream 서버와 클라이언트py·ts·go
5장비동기 모델 — asyncio·Promise·goroutinepy·ts·go
이 부의 규칙 — SDK 도, express 도 쓰지 않습니다. 파이썬 http.server·json·urllib·asyncio, Node node:http·fetch, Go net/http·encoding/json 만 씁니다. 다루는 자료는 보물상사 워크숍의 숙소·식사 견적이지만, A2A 객체의 뜻은 3~5부가 풉니다.

1장

HTTP 한 장 요약과 curl

요청 줄·헤더·빈 줄·본문 → 표준 라이브러리 서버 → curl → 와이어 탭 읽기 → 상태 코드 → HTTP 층과 업무 층

HTTP 요청은 글자 몇 줄과 본문 하나다

라이브러리를 걷어 내면 HTTP 는 소켓에 쓰는 글자입니다. 숙소 견적 요청을 손으로 조립해 보면 모양이 그대로 드러납니다.

  • 요청 줄 — 메서드(POST), 경로(/quote), 판(HTTP/1.1).
  • 헤더 — 이름: 값 한 줄씩. 줄 끝은 CR LF(\r\n).
  • 빈 줄 — 헤더가 끝났다는 표시. 그 뒤가 본문이고, 길이는 Content-Length 가 알려 줍니다.

응답도 같은 모양 — 상태 줄, 헤더, 빈 줄, 본문

위 바이트를 견적 서버에 보내고, 돌아온 바이트를 그대로 찍었습니다(\r\n 은 눈에 보이게 바꾼 줄 끝).

상태 줄 — HTTP/1.1 200 OK 는 판·상태 코드·이유 문구입니다. 본문이 JSON 이라는 것은 Content-Type: application/json 이 알려 줍니다.

표준 라이브러리 서버 — 메서드마다 do_GET·do_POST

파이썬 http.server 는 요청 줄과 헤더를 읽어 주고, 메서드 이름에 맞는 do_* 를 부릅니다. 견적 계산은 시나리오의 workshop 모듈(choose_lodging)이 합니다.

본문은 먼저 다 읽는다 — do_POST 는 경로를 보기 전에 Content-Length 만큼 읽습니다. HTTP/1.1 서버는 같은 연결에서 다음 요청을 이어 읽으므로, 404 를 돌려주며 본문을 남겨 두면 그 본문이 다음 요청의 첫 줄로 읽힙니다.

curl 로 다섯 번 묻기 — 화면에는 응답 본문만

손으로 소켓을 여는 대신 curl 을 씁니다. 이 덱에서 서버를 두드리는 기본 도구입니다.

옵션뜻
-s진행 막대를 끈다
--json '…'본문을 보내며 POST, Content-Type·Accept 를 application/json 으로

와이어 탭 — 둘 사이에 끼어 오간 것을 적는 프록시

curl 화면에는 요청이 안 보입니다. 그래서 이 덱은 클라이언트와 서버 사이에 와이어 탭(tools/wiretap.py)을 세웁니다. 받은 요청을 그대로 넘기고, 응답을 그대로 돌려주며, 그 사이에 양쪽을 적습니다.

 curl ──────→ 탭 127.0.0.1:10201 ──────→ 견적 서버 :10251
      ←──────   (오간 것을 적는다) ←──────
캡처의 [터미널 N] — 실행 명세(.run)의 줄마다 터미널 하나입니다. 서버(1), 탭(2), 클라이언트(3) 차례로 띄웠고, 서버가 찍은 것은 터미널 1 (quote) 출력 머리줄 아래, 탭이 적은 것은 와이어 (quote-wire) 머리줄 아래에 모입니다. 화면에 따로 실을 때는 그 구역만 잘라 이름표를 붙입니다.

와이어 읽는 법 — → 는 요청, ← 는 응답

  • → 줄은 요청 줄, ← 줄은 상태 코드와 이유 문구입니다. 그 아래 두 칸 들여 쓴 것이 헤더와 본문입니다.
  • JSON 본문은 탭이 두 칸 들여 펴 줍니다. 키 순서는 보낸 그대로입니다 — curl 화면의 한 줄짜리 JSON 과 견줘 보십시오.
  • 헤더는 정해 둔 것만 적습니다. 소켓으로 받은 응답에 있던 Content-Length: 142 가 여기에는 없습니다. 길이·호스트 같은 헤더를 빼야 세 언어의 와이어를 나란히 견줄 수 있어서입니다.

상태 코드는 HTTP 층이 내린 판정이다

메서드가 틀리면 405, 경로가 없으면 404, 본문이 JSON 이 아니면 400. 셋 다 견적 계산까지 가지도 못한 요청입니다.

범위뜻여기서 본 것
2xx받아서 처리했다200 OK
4xx요청이 틀렸다400·404·405
5xx서버가 실패했다(이 장에는 없음)

200 OK 인데 숙소는 없다 — HTTP 층과 업무 층은 다르다

12월 31일은 세 숙소가 모두 쉬는 날입니다. 요청은 멀쩡히 전달됐으므로 HTTP 는 200 OK 이고, "숙소가 없다"는 결과는 본문이 말합니다.

두 층을 섞지 않는다 — 상태 코드는 "전달과 해석"의 결과, 본문은 "일"의 결과입니다. 3장의 JSON-RPC 는 이 생각을 한 걸음 더 밀어, 일의 성공과 실패를 본문의 result 와 error 로 나눕니다.

1장 퀴즈

Q. 견적 응답의 Content-Length 는 142 입니다. 그런데 본문을 글자 수로 세면 142 보다 적습니다. 왜 그렇고, 차이는 얼마입니까?

A. Content-Length 는 글자 수가 아니라 바이트 수입니다(서버 코드가 len(data), 즉 UTF-8 로 바꾼 뒤의 길이를 적습니다). 본문의 한글 "가평 솔숲 리조트" 일곱 글자는 UTF-8 로 글자마다 3바이트, 21바이트이므로 글자 수보다 14 가 큽니다.

2장

JSON 다루기 — 세 언어

여섯 가지 값 → 쓰고 읽기 ×3 → camelCase → 수: 정수·실수·2^53 ×3 → null 과 빠진 필드 ×3

JSON 의 값은 여섯 가지뿐이다

JSON-RPC 2.0 명세의 말로는 "four primitive types (Strings, Numbers, Booleans, and Null) and two structured types (Objects and Arrays)". 세 언어는 이 여섯을 저마다의 타입으로 옮깁니다.

number 칸을 눈여겨보십시오 — 같은 30 이 파이썬에서는 int, JS 에서는 number, Go 의 any 에서는 float64 가 됩니다. 이 차이가 수 이야기의 출발점입니다.

파이썬 — 기본값은 빈칸을 넣고 한글을 \uXXXX 로 바꾼다

교통 견적 요청 {headcount, nights, depart} 를 쓰고 다시 읽습니다. json.dumps 의 기본 출력은 다른 두 언어와 글자가 다릅니다.

두 옵션으로 맞춘다 — ensure_ascii=False 는 한글을 그대로, separators=(",", ":") 는 빈칸을 뺍니다. 뜻은 같지만, 바이트를 견주거나 서명할 때는 글자가 같아야 합니다.

TypeScript — JSON.parse 는 모양을 확인하지 않는다

JSON.stringify 는 처음부터 빈칸 없이, 한글을 그대로 씁니다. 읽을 때 JSON.parse 의 결과 타입은 any 라서, 모양은 as 로 "믿는다"고 적을 뿐입니다.

as 는 검사가 아니다 — 실행 중에는 아무것도 확인하지 않습니다. 남이 보낸 JSON 을 믿으려면 필드를 직접 확인해야 합니다(3장의 서버가 그렇게 합니다).

Go — 읽을 모양(구조체)을 먼저 정한다

Go 는 json.Unmarshal 에 채울 그릇을 넘깁니다. 같은 값을 구조체·태그 없는 구조체·map 으로 써 보면 세 가지 글자가 나옵니다.

camelCase 는 언어가 아니라 JSON 쪽의 약속이다

파이썬 dict 와 JS 객체는 키를 적은 그대로 내보냅니다. Go 는 필드 이름이 대문자로 시작해야 해서, 태그가 없으면 Headcount 처럼 나갑니다.

  • 이 덱의 시나리오 자료는 필드 이름이 전부 camelCase 입니다(pricePerPersonNight, venueId).
  • A2A 도 같습니다. 스펙 §5.5 는 "All JSON serializations of the A2A protocol data model MUST use camelCase naming for field names" 라고 적습니다. 그 나머지 규칙은 4부에서 다룹니다.
Go 의 map 은 키를 정렬해 씁니다 — 위 Go 출력의 map 줄은 depart 가 맨 앞입니다. 뜻은 같지만 순서를 지키려면 구조체를 씁니다.

뜻이 같아도 글자는 다르다 — 세 언어의 서버가 같은 JSON 을 내려면 이 표의 기본값을 하나하나 맞춰야 합니다. 3장의 JSON-RPC 서버 셋은 그렇게 맞춰서 와이어가 같습니다.

JSON 의 수에는 정수와 실수의 구별이 없다

JSON 문법에는 number 하나뿐입니다. 30 과 30.0 은 글자만 다를 뿐 같은 수이고, 그것을 정수로 볼지 실수로 볼지는 읽는 쪽 언어가 정합니다.

 64비트 실수(float64·JS number)가 빈틈없이 나타내는 정수

   0 … 2^53 = 9,007,199,254,740,992   여기까지는 정확하다
   2^53 + 1 = 9,007,199,254,740,993   이웃 값으로 바뀐다

 보물상사의 돈(예산 6,000,000원)은 이 한계보다 훨씬 작다
  • 파이썬 int 와 Go int64 는 2^53 을 넘어도 정확합니다. JS number 와 Go 의 any(float64)는 아닙니다.
  • 다음 세 장에서 같은 일을 시킵니다 — 30·30.0 쓰기, 30.0 읽기, 2^53+1 읽기.

파이썬 — 30.0 은 float 로 읽고 float 로 쓴다

파이썬은 소수점이 있으면 float, 없으면 int 로 읽습니다. 쓸 때도 그 구별을 지켜 30.0 을 씁니다.

TypeScript — 30 과 30.0 은 같은 값, 2^53+1 은 이웃 값

JS 에는 number 하나뿐이라 30.0 을 써도 30 이 나갑니다. 대신 2^53 을 넘는 정수는 읽는 순간 바뀝니다.

Go — int 필드는 30.0 을 거절한다

Go 는 그릇의 타입대로 읽습니다. int 필드에 30.0 이 오면 값이 정수여도 오류이고, 타입을 정하지 않으면(any) float64 가 됩니다.

null 과 빠진 필드는 다른 말이다 — 파이썬

식사 요청의 caps(끼니별 1인 상한)는 없으면 기본 상한을 씁니다. "caps 를 안 보냄"과 "caps 가 null"은 뜻이 다를 수 있는데, 파이썬의 .get 은 둘 다 None 을 줍니다.

A2A 도 이 구별을 씁니다 — 스펙 §5.7 은 "explicitly set versus omitted" 의 구별이 기본값 적용과 카드 서명에 "critical" 하다고 적습니다(서명은 12부).

TypeScript — 빠지면 undefined, null 이면 null

JS 는 값만 봐도 둘이 구별됩니다. 쓸 때는 반대로, undefined 인 필드가 출력에서 사라집니다.

Go — 빠짐도 null 도 영값, omitempty 면 0 이 사라진다

구조체로 읽으면 빠진 필드와 null 이 똑같이 영값(nil, 0)이 됩니다. 쓸 때 omitempty 를 붙인 vegetarians 는 0 이면 아예 나가지 않습니다.

"채식 0명"을 보냈는데 받는 쪽에는 "안 보냄"으로 간다 — omitempty 는 0 과 빠짐을 같게 만듭니다. 구별해야 하면 포인터(*int)나 json.RawMessage 로 받습니다.

2장 퀴즈

Q. 파이썬 쪽이 {"headcount":30.0} 을 보냈습니다. 받는 쪽이 (가) TypeScript, (나) Headcount int 필드를 가진 Go 구조체라면 각각 무엇을 얻습니까?

A. (가) number 30 — TS 캡처의 30 number true. (나) 오류 — Go 캡처의 json: cannot unmarshal number 30.0 into Go struct field Req.headcount of type int. 값이 정수여도 글자에 소수점이 있으면 Go 의 int 는 받지 않습니다.

3장

JSON-RPC 2.0 — 세 언어

봉투의 네 필드 → A2A 요청의 겉모양 → 오류 코드 → 서버 ×3 → 성공·실패·null id → 알림 → 배치 → A2A 와 배치 → 클라이언트 ×3

JSON-RPC 는 "무엇을 부르는가"를 본문에 적는다

1장의 견적 서버는 경로(/quote)로 일을 골랐습니다. JSON-RPC 2.0 은 HTTP 를 한 경로·한 메서드(POST)로 두고, 부를 메서드와 인자를 JSON 본문에 적습니다.

id문자열·수·null. 응답이 같은 값을 돌려준다. 없으면 알림

A2A 의 요청도 이 봉투에 담긴다

A2A 의 JSON-RPC 바인딩(§9)은 메서드 이름을 SendMessage 처럼 PascalCase 로 짓습니다(§9.1 "PascalCase method names matching gRPC conventions"). 맨 처음 만날 요청을 표준 라이브러리로 그대로 써 보면 겉은 JSON-RPC 그 자체입니다.

스펙 안의 어긋남 — §9.3 "Base Request Structure" 의 틀은 아직 "method": "category/action" 이라고 적습니다. v0.3 의 message/send 꼴이고, whats-new-v1.md 는 이것이 SendMessage 로 바뀌었다고 적습니다. 이 책은 §9.1·§9.4 의 PascalCase 를 따릅니다.

오류 코드 다섯 개는 JSON-RPC 가 정했다

JSON-RPC 2.0 은 −32768 ~ −32000 을 미리 정한 오류에 남겨 두고, 그중 다섯을 정했습니다. A2A §9.5 도 같은 다섯 코드를 씁니다 — 다만 "Standard Message" 문구는 JSON-RPC 명세와 다르게 적었습니다.

파이썬 서버 — 요청 객체 하나를 처리하는 call

메서드는 ChooseLodging 하나, 일은 1장과 같은 choose_lodging 입니다. 인자 검사(lodging_params)는 date 가 문자열, nights·headcount 가 정수인지만 봅니다.

알림도 일은 한다 — id 가 없어도 메서드는 부르고, 응답만 버립니다. 서버 기록에 무엇을 했는지 한 줄씩 남겨 와이어와 견줘 볼 수 있게 했습니다.

본문 하나 → 단건 응답·배열 응답·무응답

본문을 JSON 으로 읽지 못하면 −32700, 배열이면 배치, 아니면 단건입니다. 보낼 것이 없으면(알림) HTTP 는 204 No Content 로 닫습니다.

시험 본문 여덟 가지 — 서버 셋에 똑같이 보낸다

파이썬·TypeScript·Go 서버에 이 목록을 차례로 보내고 와이어를 적었습니다(rpc_py·rpc_ts·rpc_go 명세). 시험 쪽은 HTTP 상태만 찍습니다.

성공 — result 에 답, id 는 받은 그대로

"id": 1 로 묻고 "id": 1 로 답한다 — 클라이언트는 이 값으로 "어느 요청의 답인가"를 맞춥니다. result 안은 메서드가 정한 모양(여기서는 숙소 견적)이고 JSON-RPC 는 관여하지 않습니다.

실패 — error 에 code 와 message, HTTP 는 여전히 200

층이 하나 더 생겼다 — 1장에서는 상태 코드가 실패를 알렸습니다. 여기서는 HTTP 는 200 OK("봉투는 잘 받았다")이고, 실패는 error.code 가 알립니다(-32601 없는 메서드, -32602 인자 모자람).

id 를 읽지 못하면 응답의 id 는 null

본문이 깨졌거나(−32700) 요청 객체가 아니면(−32600, method 가 수) 서버는 id 를 믿을 수 없습니다. JSON-RPC 2.0 은 이때 "it MUST be Null" 이라고 정합니다.

알림 — id 가 없으면 서버는 답하지 않는다

명세: "The Server MUST NOT reply to a Notification". 그래도 HTTP 는 무언가 돌려줘야 하므로 이 서버들은 본문 없는 204 No Content 를 보냅니다.

알림은 성공했는지 알 길이 없다 — 서버 기록에는 ChooseLodging 알림 → 응답 안 함 이 남았지만, 보낸 쪽은 오류가 나도 모릅니다. 결과가 필요한 호출에는 늘 id 를 붙입니다.

배치 — 요청 객체를 배열에 담아 한 번에

셋을 한 본문에 담았습니다 — 보통 요청(id 5), 알림, 없는 메서드(id 6, params 없음).

배치의 답은 배열 — 알림 몫은 빠지고, 빈 배치는 단건 오류

명세가 정한 그대로 — 알림에는 응답 객체가 없어야 하고(SHOULD NOT), 응답이 하나도 없으면 빈 배열이 아니라 아무것도 돌려주지 않으며(MUST NOT return an empty Array), 빈 배열 [] 은 단건 -32600 입니다. 명세는 배치의 답이 순서를 바꿔도 된다고(MAY) 하므로 클라이언트는 id 로 짝을 맞춥니다.

A2A 스펙은 배치를 말하지 않는다

A2A v1.0.1 스펙 본문(specification.md)에는 "batch" 라는 낱말이 한 번도 나오지 않습니다. JSON-RPC 바인딩 §9.3 은 "All JSON-RPC requests MUST follow the standard JSON-RPC 2.0 format" 이라고만 하고, 보기는 객체 하나뿐입니다.

  • §9.4 의 메서드마다 요청 하나·응답 하나(스트리밍은 SSE 하나)로 적혀 있습니다.
  • 그러니 이 책의 A2A 클라이언트는 HTTP 요청 하나에 JSON-RPC 요청 하나만 담습니다. 배치를 받는지는 서버 구현마다 다를 수 있고, 스펙이 보장하지 않습니다.
배치·알림은 JSON-RPC 의 기능이지 A2A 의 기능이 아니다 — 이 장에서 만든 것은 JSON-RPC 를 알기 위한 것입니다. 스펙 §9.3 의 기본 요청 구조에는 id 가 있고, 이 책은 A2A 메서드를 언제나 id 를 붙여 부르고 답을 받습니다.

TypeScript 서버 — 같은 call, 같은 기록

구조는 파이썬과 같습니다. 알림 판별은 !("id" in req), 정수 검사는 Number.isInteger, 무응답은 res.writeHead(204).end() 입니다.

Go 서버 — id 는 json.RawMessage 로 받아 그대로 돌려준다

id 는 문자열일 수도 수일 수도 있습니다. Go 는 json.RawMessage(해석하지 않은 JSON 바이트)로 받아 그대로 되돌리고, 필드가 없으면 nil 이라 알림을 가를 수 있습니다.

세 서버 비교 — 와이어는 첫 글자부터 끝까지 같다

세 명세의 캡처(out/02/rpc_py.txt·rpc_ts.txt·rpc_go.txt)는 실행 명령과 서버 이름 줄을 빼면 서버 기록도 와이어도 글자까지 같습니다(diff 로 확인). 같게 만든 자리는 이렇습니다.

3장 퀴즈

Q. 요청 셋(id 5 성공, 알림, id 6 없는 메서드)을 배치로 보냈습니다. 응답 배열에는 원소가 몇 개이고, 서버 기록에는 몇 줄이 남습니까?

A. 응답은 둘("id": 5 의 result, "id": 6 의 -32601) — 배치 응답. 서버 기록은 셋입니다 — 알림 슬라이드의 기록에서 ChooseLodging id=5 → result, ChooseLodging 알림 → 응답 안 함, BookLodging id=6 → -32601. 알림도 실행은 되고 답만 없습니다.

4장

SSE — 세 언어

닫지 않는 응답 → 읽는 규칙 → 서버 ×3 → curl 로 본 날것과 와이어 → 클라이언트 ×3 → 비교 → 스트림의 끝

SSE 는 끝나지 않은 HTTP 응답에 이벤트를 줄줄이 흘린다

보통 응답은 본문을 다 만든 뒤 한 번에 보냅니다. Server-Sent Events 는 응답을 열어 둔 채 Content-Type: text/event-stream 으로 "이벤트(event)"을 생기는 대로 보냅니다. A2A 의 스트리밍 메서드가 이것을 씁니다(§9.4.2 "HTTP 200 with Content-Type: text/event-stream").

 클라이언트                              서버
   │ POST /meals  (요청은 보통 HTTP)       │
   │ ────────────────────────────────────→ │
   │ 200 OK, text/event-stream             │  머리만 먼저
   │ ←──────────────────────────────────── │
   │ data: 첫 끼니          (빈 줄)        │  생길 때마다
   │ ←──────────────────────────────────── │
   │ data: 둘째 끼니        (빈 줄)        │
   │ ←──────────────────────────────────── │
   │            …  연결을 닫음             │  닫힘 = 끝
형식의 출처 — SSE 는 WHATWG HTML 표준 §9.2 "Server-sent events" 가 정합니다. 읽는 규칙은 §9.2.6 "Interpreting an event stream" 에 있고, 다음 장이 그것을 요약합니다.

읽는 규칙 — 줄 단위, 빈 줄이 이벤트의 끝

줄읽는 쪽이 할 일 (HTML §9.2.6)
빈 줄모아 둔 data 로 이벤트 하나를 내보낸다
data: 값콜론 뒤 빈칸 하나를 떼고 data 에 덧붙인다. 여러 줄이면 줄바꿈(LF)으로 잇는다

event:·id:·retry:이벤트 이름·마지막 이벤트 id·다시 붙을 간격
스트림이 끝남빈 줄로 닫히지 않은 조각은 버린다("any pending data must be discarded")
  • 줄 끝은 CRLF·LF·CR 어느 것이든 되고, 글자는 언제나 UTF-8 입니다.
  • A2A 스펙의 스트림 보기(§9.4.2, §11.7)는 data: 줄만 씁니다. 그래서 이 장의 서버도 data: 만 보내고, 클라이언트는 나머지 필드를 읽고 버립니다.

파이썬 서버 — 머리를 보내고, 이벤트마다 write·flush

식사 요청(1박, 30명, 채식 2명)을 받아 plan_meals 로 식단을 짜고, 끼니마다 이벤트 하나, 끝에 합계 이벤트 하나를 보냅니다. Content-Length 를 모르므로 다 보내고 연결을 닫는 것으로 끝을 알립니다.

curl -N 으로 본 날것 — data 줄, 빈 줄, data 줄, 빈 줄

-N 은 curl 이 출력을 모아 두지 않게 합니다. 화면에 찍힌 것이 바로 서버가 쓴 바이트입니다.

이벤트마다 빈 줄 하나 — 끼니 셋과 합계 하나, 이벤트 넷입니다. 식단 합계 1,542,000원은 시나리오의 골든 값과 같습니다.

와이어 탭은 이벤트 하나가 끝날 때마다 적는다

탭은 SSE 응답을 모았다가 넘기지 않습니다. 빈 줄을 만날 때마다 그 이벤트를 곧장 넘기고 적으며, data 가 JSON 이면 펴서 적습니다. 빈 줄은 적지 않고, data: 머리가 이벤트의 시작을 알립니다.

TypeScript 서버 — res.write 가 곧 내보내기

Node 의 res.write 는 쓰는 대로 내보내므로 flush 가 따로 없습니다. res.end() 가 응답의 끝, 곧 스트림의 끝입니다.

Go 서버 — http.Flusher 로 이벤트마다 밀어낸다

Go 의 ResponseWriter 는 버퍼를 둡니다. 이벤트마다 Flush() 를 불러야 클라이언트가 그때그때 받습니다. 처리기 함수가 돌아가면 응답이 끝납니다.

파이썬 클라이언트 — 줄을 읽어 빈 줄에서 이벤트를 낸다

urlopen 의 응답을 줄 단위로 돌면 줄이 도착하는 대로 받습니다. 규칙표 그대로 — 빈 줄이면 내보내고, : 줄은 버리고, data 는 모읍니다.

TypeScript 클라이언트 — 조각을 이어 붙여 줄로 자른다

fetch 의 본문은 바이트 조각의 스트림입니다. 조각은 줄 가운데서 끊길 수 있으므로, 버퍼에 붙여 두고 \n 이 나올 때마다 한 줄씩 잘라 읽습니다.

Go 클라이언트 — bufio.Scanner 와 iter.Seq

bufio.Scanner 가 줄을 잘라 주고, 이벤트는 iter.Seq[string] 으로 돌려줘 for data := range … 로 받습니다. 이 모양은 5장과 9부에서 다시 나옵니다.

세 명세(sse_py·sse_ts·sse_go)의 curl 화면·클라이언트 출력·와이어는 실행 명령과 서버 이름 줄을 빼면 같습니다.

스트림의 끝은 "끝" 이벤트가 아니라 연결이 닫히는 것이다

SSE 형식에는 끝을 알리는 표시가 없습니다. 서버가 다 보냈으면 응답을 닫고, 클라이언트는 본문이 끝난 것으로 끝을 압니다.

  • A2A 도 같습니다 — §11.7 은 작업이 끝나거나 멈추는 상태에 이르면 "at which point the stream closes" 라고 적습니다. 어떤 상태에서 닫히는지는 10부의 몫입니다.
  • JSON-RPC 바인딩에서는 이벤트 하나의 data 가 JSON-RPC 응답 하나이고, 모두 요청과 같은 id 를 가집니다(§9.4.2 의 보기).

비동기 모델 비교

4장의 스트림처럼 이벤트가 띄엄띄엄 오고, 기획 에이전트는 숙소·식사·교통 에이전트의 답을 동시에 기다려야 합니다. 세 언어는 이 "기다림"을 서로 다른 도구로 다룹니다.

파이썬 asyncio — async for 와 gather

async def 안의 await 가 "여기서 기다리는 동안 다른 일을 해도 된다"는 자리입니다. 스레드 하나의 이벤트 루프가 기다림이 풀린 일부터 이어 갑니다.

TypeScript — for await 와 Promise.all

구조는 파이썬과 같습니다. async function* 은 비동기 제너레이터, Promise.all 이 gather 자리입니다. Node 도 스레드 하나의 이벤트 루프로 돌고, ES 모듈이라 맨 바깥에서 바로 await 할 수 있습니다.

Go (1) — iter.Seq2: yield 하는 함수를 for 로 돈다

Go 에는 async·await 가 없습니다. 이벤트를 하나씩 내놓는 쪽은 yield 함수를 받는 함수(iter.Seq2)로 쓰고, 받는 쪽은 for s, err := range steps() 로 돕니다.

값 둘(Seq2)인 까닭 — 둘째 값 error 로 "도중에 실패했다"를 같은 흐름에 실어 보냅니다. 9부의 Go SDK 가 바로 이 모양을 씁니다(아래 표).

Go (2) — goroutine 셋, channel 하나, WaitGroup

wg.Go 가 goroutine 을 띄웁니다. goroutine 은 정말로 동시에(여러 스레드에서) 돌 수 있으므로, 끝난 차례는 채널 done 으로 받고, 결과는 미리 정한 자리(totals[i])에 둡니다.
