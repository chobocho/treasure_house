스트리밍·아티팩트 청크·재구독

SendStreamingMessage 의 와이어 → 식사 에이전트 ×3 → 스트림 종료 규칙 → 청크 다시 붙이기 → SubscribeToTask → FilePart·DataPart → 스트리밍 미지원 카드

막는 호출은 끝난 뒤의 모습을, 스트림은 그 사이를 보여 준다

식사 에이전트는 끼니 하나를 정할 때마다 "식단 짜는 중 1/3" 을 알리고 식단표를 한 줄씩 보냅니다. 막는 호출로 받으면 그 조각들이 이미 합쳐진 Task 하나뿐이었습니다(5부). 이 부는 그 사이에 오가는 이벤트를 하나씩 봅니다 — 무엇이 어떤 차례로 오고, 언제 끝나고, 끊기면 어떻게 다시 붙는지.

장무엇을
1장SendStreamingMessage 의 와이어 — StreamResponse 넷, 세 SDK 서버가 내는 차례, 첫 이벤트, 사라진 final
2장식사 에이전트 ×3 — 끼니마다 상태, 식단표 조각(append·lastChunk), 세 서버의 스트림 견주기
3장스트림 종료 규칙 — 종료 상태와 중단 상태, §3.1.2 와 §11.7, SDK 마다 닫는 때, 도중의 오류
4장클라이언트에서 청크 다시 붙이기 ×3
5장SubscribeToTask — 끊긴 뒤 다시 붙기, 여러 구독자(§3.5.2)
6장FilePart(menu.md) + DataPart 견적
7장스트리밍 미지원 카드에 스트림 요청 → UnsupportedOperation
이 부의 방식 — 3~5부처럼 완성 에이전트(식사)를 블랙박스로 띄우고 와이어를 읽습니다. 바이트 규칙(2부)과 맨손 SSE 서버(6부), 세 SDK 클라이언트의 스트림 손잡이(7부·8부·9부)는 이미 봤으니, 여기서는 이벤트의 뜻과 차례만 다룹니다. 새로 쓰는 에이전트는 실험용 하나 — 고른 상태에서 실행을 끝내는 종료 실험 에이전트(3장, 세 언어)입니다.

1장

SendStreamingMessage 의 와이어

StreamResponse 넷 → 두 이벤트의 필드 → 스트림의 두 꼴 → 사라진 final → 옛 클라이언트의 final → 요청 → SDK 없이 읽기 → 파이썬 서버 → TS·Go 서버 → 조각 하나를 통째로 → 첫 이벤트 → 세 서버 비교

스트림의 이벤트 하나는 StreamResponse — 넷 중 하나만 채운 봉투

proto 의 rpc SendStreamingMessage(SendMessageRequest) returns (stream StreamResponse) 입니다. 요청은 SendMessage 와 같고(§9.4.2 "Same as SendMessage"), 답이 StreamResponse 의 흐름입니다. StreamResponse 는 oneof payload 하나뿐입니다.

proto 필드와이어 이름타입proto 주석

message = 2messageMessage"a message from the agent"
status_update = 3statusUpdateTaskStatusUpdateEvent"a task status update"
artifact_update = 4artifactUpdateTaskArtifactUpdateEvent"a task artifact update"
  • 종류를 가르는 것은 키 이름 — v0.3 의 kind 는 없어졌습니다. result 안의 유일한 키가 곧 종류입니다(6부의 맨손 서버도 그렇게 썼습니다).
  • 안내 문서의 이름은 틀렸다 — whats-new-v1.md 의 v1.0 예시는 "taskStatusUpdate" 라고 적었지만, proto 의 필드 이름 status_update 에서 나오는 JSON 이름은 statusUpdate 이고, 스펙 §6.2 의 예시와 세 SDK 의 와이어(이 장 뒤쪽)도 statusUpdate 입니다.

상태 이벤트는 필드 넷, 아티팩트 이벤트는 여섯 — 조각 표시 둘이 여기 있다

§4.2.1·§4.2.2 의 표는 proto 의 두 메시지에서 만들어집니다. REQUIRED 는 둘 다 taskId·contextId 와 실은 것(status 또는 artifact)입니다.

스트림의 꼴은 둘 — Message 하나로 끝나거나, Task 로 시작하거나

§3.1.2 의 Behavior 는 스트림이 "MUST follow one of these patterns" 라며 둘을 듭니다.

꼴§3.1.2 의 말이 부에서
Message 하나"exactly one Message object and then close immediately"3장의 MESSAGE
Task 생애"MUST begin with the Task object, followed by zero or more" 상태·아티팩트 이벤트식사 에이전트 전부
  • Task 꼴에서 task 는 첫 자리에만 옵니다. 그 뒤는 statusUpdate·artifactUpdate 의 섞임이고, 순서는 "the order they were generated" 그대로여야 합니다(§3.5.2 "MUST NOT be reordered").
  • §11.7 은 하나를 더 허락합니다 — "MAY optionally resend a final Task snapshot before closing". 세 SDK 가 그렇게 하는지는 이 장의 캡처로 봅니다.

final 은 v1.0 에서 빠졌다 — 끝은 스트림이 닫히는 것으로 안다

v0.3 의 상태 이벤트에는 "final": true 가 있었습니다. CHANGELOG 는 "Remove redundant final field from TaskStatusUpdateEvent (#1308)" 이라고 적었고, 안내 문서는 "Leverage protocol binding specific stream closure mechanism instead" 라고 합니다.

곳지금 남은 흔적
protoTaskStatusUpdateEvent 필드 1~4 — final 도, reserved 표시도 없다
§3.1.2 Outputs여전히 "Final completion indicator" 라는 줄이 있다 — 그것이 무엇인지는 적지 않았다
v0.3 호환 변환세 SDK 가 옛 클라이언트에게는 final 을 다시 만들어 준다(다음 슬라이드)
그래서 닫힘이 신호다 — v1.0 클라이언트는 "마지막 이벤트" 를 필드로 알 수 없고, 연결이 닫히는 것(SSE 라면 응답 본문의 끝)으로 압니다. 그러니 서버가 언제 닫는지가 규칙의 전부가 되고, 그것이 3장입니다.

옛 클라이언트에게 되살린 final — 무엇을 끝으로 볼지 SDK 마다 다르다

v0.3 클라이언트와 말하는 호환 계층(7부·8부·9부)은 v1.0 상태 이벤트를 옛 모양으로 바꿀 때 final 을 계산해 넣습니다. 설치된 소스의 그 식입니다.

요청은 SendMessage 와 같은 몸 — 다른 것은 method 와 Accept 뿐

총무팀 CLI(ask)를 세 언어로 같은 파이썬 식사 에이전트에 붙였습니다(2장의 실행). 서버 앞 탭에 남은 세 SDK 클라이언트의 요청 머리입니다.

  • 세 SDK 모두 Accept: text/event-stream 을 답니다(파이썬은 a2a/client/transports/http_helpers.py:179 의 setdefault). 스펙은 §9.4.2 에서 응답의 Content-Type 만 정했고 이 머리를 요구하지는 않습니다.
  • 몸은 4부의 SendMessage 그대로입니다. JSON-RPC id 가 UUID(파이썬·Go)냐 1(TS)이냐, configuration: {} 이 붙느냐는 6부에서 본 차이 그대로입니다.

SDK 없이 읽어 보기 — 이벤트마다 종류와 조각 표시를 와이어 그대로 찍는다

SDK 클라이언트는 받은 JSON 을 타입으로 바꾸며 빠진 필드를 기본값으로 채웁니다. 서버가 실제로 무엇을 썼는지 보려고, 시험 쪽 10/events.py 는 urllib 으로 SSE 를 읽어(2부의 규칙) 와이어의 키를 그대로 봅니다.

없음과 false 는 다르다 — flag 는 키가 없으면 "없음", 있으면 JSON 값을 찍습니다. ProtoJSON 은 기본값(false)을 빼고 쓰는 것이 기본이라, 첫 조각의 append 는 "없음" 으로 나올 것입니다.

파이썬 서버의 스트림 — 이벤트 열 개, 마지막 Task 는 다시 보내지 않는다

식사 에이전트 셋 앞에 탭을 하나씩 세우고 events.py 를 붙였습니다. 먼저 파이썬 서버입니다.

  • 2장의 약속대로 task 하나, 끼니마다 statusUpdate·artifactUpdate, 파일·견적, 끝의 COMPLETED — 열 개입니다.
  • COMPLETED 뒤에 Task 를 한 번 더 보내지 않았습니다. §11.7 의 "MAY optionally resend a final Task snapshot" 은 쓰지 않은 것입니다.

TypeScript·Go 서버도 같은 열 개, 같은 차례 — 다른 것은 Content-Type 한 줄

  • 세 서버의 이벤트 줄은 글자까지 같습니다. 세 언어의 실행기가 같은 차례로 싣고(2장), 세 SDK 가 그 차례를 바꾸지 않았습니다 — §3.5.2 "MUST NOT be reordered".
  • 파이썬만 text/event-stream; charset=utf-8 입니다. 클라이언트는 Content-Type 을 == 가 아니라 앞부분으로 견줘야 합니다(TS SDK 클라이언트는 startsWith("text/event-stream"), client/index.js:2913).
  • 첫 조각의 append·lastChunk, 파일·견적 조각의 둘은 세 서버 모두 쓰지 않았습니다(TS 의 Updater 는 false 를 채웠지만 직렬화가 기본값을 뺐습니다).

조각 하나를 통째로 — 같은 이벤트, 다른 봉투

마지막 식단표 조각(append·lastChunk 둘 다 참)을 파이썬과 Go 의 탭에서 꺼냈습니다.

  • Go 는 이벤트마다 id: 줄을 붙입니다 — 새 UUID 하나씩(internal/sse/sse.go:77 WriteData). 파이썬·TS 는 data: 만 씁니다. SSE 의 id 는 다시 붙을 때 Last-Event-ID 로 돌려보내라고 있는 필드지만(2부), 매번 새로 지은 UUID 라 이어 받기의 표지로 쓰기는 어렵습니다(다시 붙기는 5장).
  • 키 차례는 서버마다 — 파이썬은 봉투가 result·id·jsonrpc 차례, Go 의 artifactUpdate 는 가나다(알파벳)순입니다. 읽는 쪽은 차례가 아니라 이름으로 읽습니다.

첫 이벤트는 SUBMITTED Task — 아티팩트 0개, 이력에는 보낸 메시지 하나

§3.1.2 "MUST begin with the Task object". 세 서버 모두 task SUBMITTED history 1 artifacts 0 으로 시작했습니다. Go 서버의 첫 이벤트입니다.

  • 첫 Task 는 "일을 받았다" 는 표지입니다. 이 뒤의 이벤트는 모두 이 id 를 taskId 로 답니다 — 받는 쪽은 첫 이벤트에서 손잡이를 쥡니다.
  • 이력의 메시지에 Go 는 contextId·taskId 를 채우지 않았고(파이썬·TS 는 채운다), 파이썬은 DataPart 수를 30.0 으로 냅니다(4부).
  • 이어 말하기 스트림의 첫 이벤트는 언어마다 다릅니다 — 파이썬 판 에이전트는 Task 를 다시 싣지 않고(실으면 SDK 가 사용자의 답을 이력에서 버린다), TS·Go 판 에이전트는 WORKING Task 를 다시 싣습니다(6부, 16부).

1장 퀴즈

Q. 어떤 클라이언트가 "artifactUpdate 에 append 키가 있으면 이어 붙이고, 없으면 오류" 로 짰습니다. 식사 에이전트의 첫 조각에서 무슨 일이 납니까?

A. 첫 조각(meal-plan)과 파일·견적 조각에서 오류가 납니다. 세 서버 모두 append 가 거짓인 조각에는 그 키를 아예 쓰지 않았습니다(파이썬·TS·Go 의 append=없음). ProtoJSON 은 기본값을 빼고 쓰니, 받는 쪽은 "키가 없으면 false" 로 읽어야 합니다.

식사 에이전트 ×3

계약 → 파이썬 → TypeScript → TS 의 조각 하나 → Go → Go 의 조각 하나 → 세 언어 비교 → ask 로 받기 → 실행 명세 → 다섯 번의 대본 → 2박이면 → 거절 스트림

식사 에이전트의 약속 — 끼니마다 상태 하나와 식단표 한 줄

deck/SCENARIO.md 가 정한 식사 에이전트의 몫입니다. 끼니 수는 2 × nights + 1(1박이면 저녁·아침·점심 셋)이고, 메뉴를 고르는 규칙은 workshop 의 plan_meals 입니다.

차례무엇을 싣나A2A 로는
처음받은 일task — SUBMITTED
끼니마다"식단 짜는 중 i/n"statusUpdate — WORKING + 글 파트

1박이면 이벤트 열 개 — task 1 + 끼니 3 × 2 + 파일·견적 2 + 끝 1. 끼니 사이에는 --step-ms(기본 100ms)만큼 쉬어, 이벤트가 정말 하나씩 흘러나오게 합니다. 파일 파트와 데이터 파트의 속은 6장에서 다룹니다.

파이썬 — TaskUpdater 의 두 손: update_status 와 add_artifact

agents/catering.py 의 끼니 고리입니다. 앞부분(begin 으로 Task 를 싣고 요청을 읽는 곳)은 7부의 숙소 에이전트와 같은 모양입니다.

  • append=i > 1·last_chunk=i == len(rows) — 첫 조각은 새 아티팩트, 둘째부터 "같은 id 에 이어 붙여라", 마지막 조각에 "이것으로 끝" 을 답니다. 세 조각 모두 같은 artifact_id="meal-plan" 입니다.
  • add_artifact 는 받은 그대로 TaskArtifactUpdateEvent 하나를 큐에 넣습니다(a2a/server/tasks/task_updater.py:141). 합치는 일은 하지 않습니다.

TypeScript — 같은 고리, 조각 표시는 객체 하나로

agents/catering.ts 의 같은 자리입니다. TS SDK 에는 TaskUpdater 가 없어서(8부) agents/common.ts 의 Updater 가 그 몫을 합니다.

  • rows.entries() 는 0 부터 세므로 append: i > 0, lastChunk: i === rows.length - 1 입니다. 파이썬과 뜻은 같습니다.
  • up.pause 는 쉬는 동안 취소되면 false 를 돌려줍니다 — 취소는 11부입니다.

TS 의 조각 하나 — artifactUpdate 를 손으로 빚어 버스에 싣는다

Updater.artifact 입니다. AgentEvent.artifactUpdate 는 이벤트의 이름표만 붙이고, 필드는 우리가 다 채웁니다.

빈 값도 채운다 — ts-proto 타입은 description·extensions 같은 필드를 빼 둘 수 없어서 ""·[] 를 넣었습니다. append·lastChunk 도 !! 로 늘 true/false 가 됩니다. 와이어에 무엇이 나가는지는 1장에서 봤습니다 — false 는 와이어에 나가지 않았습니다.

Go — yield 로 하나씩, 조각 표시는 common.Chunk

agents/catering/main.go 의 끼니 고리입니다. 실행기가 돌려준 반복자 안에서 이벤트마다 yield 합니다(9부).

  • common.Sleep 은 쉬는 동안 ctx 가 취소되면 false — TS 의 pause 와 같은 자리입니다.
  • up.Status·up.Artifact 는 yield 의 결과를 돌려주지만, 이 고리는 그것을 보지 않고 Sleep 의 ctx 검사에 기댑니다. false 를 받은 뒤 또 yield 하면 panic 이니(9부), 엄밀하게는 돌려받은 값을 보아야 할 자리입니다 — 3장의 실험 에이전트는 그렇게 짰습니다.

Go 의 조각 하나 — SDK 의 NewArtifactEvent 에 id·이름·표시를 덧칠한다

agents/common/begin.go 의 Chunk 와 Updater.Artifact 입니다.

id 를 주지 않으면 새로 짓는다 — a2a.NewArtifactEvent 는 아티팩트 id 를 새로 만들어 넣습니다. 조각을 이어 붙이려면 같은 id 여야 하니, Chunk.ID 가 있으면 덮어씁니다. 파이썬은 artifact_id 인자, TS 는 o.id ?? randomUUID() 로 같은 일을 합니다.

파이썬 — begin 으로 Task 를 먼저, 그다음 고른 상태들, 그리고 돌아간다

  • 서버는 agents.common.serve 그대로입니다 — 파이썬 쪽에서는 그것이 SDK 기본값입니다(DefaultRequestHandler 에 옵션을 주지 않는다).
  • "실행기가 돌아갔다" 를 서버 출력에 찍어, 스트림이 닫힌 때와 실행이 끝난 때를 견줄 수 있게 했습니다.

TypeScript — 같은 실행기, 상태 이름은 TaskState 의 키로

Message 는 손으로 — TS 에는 new_text_message 같은 도우미가 없어, AgentEvent.message 에 넣을 Message 의 필드를 다 채웁니다. BOOM 은 throw 입니다.

TS 서버는 SDK 기본값으로 — 완성 에이전트의 serve 를 쓰지 않는 까닭

완성 에이전트가 쓰는 agents/common.ts 의 serve 는 처리기의 아홉째 인자로 keepBusAliveStates: [INPUT_REQUIRED] 를 줍니다(8부). 그 옵션이 바로 닫는 때를 바꾸므로, 실험 에이전트는 처리기를 직접 만듭니다.

Go — yield 가 false 면 멈춘다, 오류는 둘째 값으로

  • BOOM 은 yield(nil, err) — Go 실행기가 오류를 내는 길입니다(9부).
  • 서버는 a2asrv.NewHandler(closer{}) 에 옵션 없이 — agents/common 의 Serve 는 처리기를 waiter 로 감싸 AUTH_REQUIRED 에서 스트림을 닫으므로(agents/common/park.go) 쓰지 않았습니다.

시험 쪽 — 2초 동안 아무것도 안 오면 "열린 채" 로 적고 끊는다

10/closes.py 의 한 번 읽기입니다. 소켓 읽기 시간 제한(timeout=2)이 걸리면 서버가 아직 닫지 않은 것입니다.

그다음 GetTask — 스트림이 끝나면 1초 기다렸다가(늦게 실리는 상태가 저장될 틈) GetTask 로 저장된 상태를 묻습니다. 스트림이 본 끝과 저장소가 본 끝이 같은지 견주려는 것입니다.

파이썬 서버 — 일곱 번 모두 닫았다, 실행기가 돌아갈 때

  • AUTH_REQUIRED 도, 끝 상태 없는 WORKING 도 닫혔습니다. 실행기가 돌아갔기 때문입니다 — 상태가 아니라 실행이 기준이라는 소스 그대로입니다. WORKING 에서 닫힌 스트림은 §3.1.2 의 어느 꼴에도 맞지 않는 끝입니다.
  • LATE 는 INPUT_REQUIRED 뒤의 WORKING·COMPLETED 까지 받았고, 저장된 상태도 COMPLETED 입니다. 중단 상태에서도 닫지 않은 것이니 §11.7 과 어긋납니다.

TS 서버 — AUTH_REQUIRED 에서 열린 채, INPUT_REQUIRED 에서는 칼같이 닫는다

  • AUTH_REQUIRED — 실행기는 돌아갔는데 스트림은 2초 동안 열려 있었습니다. 기본 keepBusAliveStates 가 버스를 살려 두어, 같은 실행이 더 싣기를 기다립니다.
  • WORKING — 실행기가 돌아가자 버스가 끝나 닫혔습니다(마지막 상태가 살려 둘 목록에 없다).
  • LATE — INPUT_REQUIRED 에서 닫혔고, 저장된 상태도 INPUT_REQUIRED 입니다. 실행기는 끝까지 돌았는데(다음 슬라이드) 뒤의 둘은 어디에도 남지 않았습니다.

Go 서버 — 끝 상태 없이 돌아간 실행기도 스트림을 붙든다

  • AUTH_REQUIRED·WORKING 둘 다 열린 채였습니다. IsFinal 이 아닌 이벤트 뒤에 실행기가 돌아가면, 구독은 실행의 결과를 기다리는데, 이 실험의 2초 안에는 오지 않았습니다 — 9부의 "Silent" 실행기와 같은 자리입니다.
  • LATE 는 TS 와 같이 INPUT_REQUIRED 에서 닫히고 그 상태로 저장되었습니다.
  • BOOM 의 마지막은 statusUpdate 가 아니라 FAILED task 입니다 — §11.7 이 말한 "final Task snapshot" 을 Go 만, 오류 때에만 보낸 셈입니다(뒤에서).

INPUT_REQUIRED 뒤에 실은 것은 TS·Go 에서 사라진다 — 실행기는 그것을 모른다

LATE 의 실행기는 세 서버 모두에서 끝까지 돌았습니다. 서버 출력입니다.

  • TS·Go 는 INPUT_REQUIRED 에서 "이 실행은 끝났다" 로 보고, 그 뒤의 WORKING·COMPLETED 를 스트림에도 저장소에도 싣지 않았습니다(GetTask → INPUT_REQUIRED). TS 버스의 publish 는 아무 말이 없고, Go 의 yield 는 false 를 돌려줄 수도 있지만 그때그때 달라 이 실험은 그것에 기대지 않았습니다.
  • 파이썬은 같은 실행기의 늦은 상태를 다 받았습니다. 그래서 중단 상태를 낸 실행기는 곧 돌아가야 세 SDK 에서 같은 결과가 납니다. 완성 에이전트들이 되묻고 나서 바로 return 하는 것이 그 모양입니다(7부).

완성 에이전트는 기본값을 바꿔 셋을 맞췄다 — AUTH_REQUIRED 에서도 닫는다

정산 에이전트는 AUTH_REQUIRED 로 결재를 묻고, 결재 토큰은 같은 taskId 의 새 메시지로 옵니다(12부). 스트림이 열린 채면 기획 에이전트가 기다리기만 하므로, 세 언어의 완성 에이전트는 AUTH_REQUIRED 에서도 닫히도록 맞췄습니다.

열린 채인 스트림 — 클라이언트는 시간 제한을 스스로 둬야 한다

TS·Go 의 AUTH_REQUIRED, Go 의 WORKING 은 서버가 닫지 않았습니다. 이벤트도 오지 않고 끝도 오지 않으니, 끊는 것은 클라이언트 몫입니다.

  • 이 장의 시험 쪽은 2초에 끊었습니다. 세 SDK 클라이언트의 기본은 다릅니다 — Go SDK 의 HTTP 클라이언트는 3분이면 스트림도 끊고(9부), 총무팀 CLI 는 httpx 에 timeout=30 을 주었습니다(agents/ask.py:113).
  • 끊는 기준은 "마지막 이벤트 뒤로 얼마나 조용했나" 가 맞습니다. 식사 에이전트처럼 끼니마다 이벤트가 오는 스트림은 길어도 끊을 까닭이 없습니다.
  • 끊은 뒤에도 작업은 서버에 그대로 있습니다(GetTask → AUTH_REQUIRED·WORKING). 다시 붙는 길이 SubscribeToTask 입니다 — 5장에서 이 작업들에 다시 붙어 봅니다(그 스트림도 열린 채일 수 있습니다).

도중의 오류 — 파이썬은 event: error, TS 는 FAILED 상태, Go 는 FAILED Task

BOOM 은 Task·WORKING 을 낸 뒤 실행기가 예외로 죽습니다. 세 서버의 그 스트림에서 상태·오류 줄만 골랐습니다.

  • 파이썬: JSON-RPC 오류 -32603 을 event: error 이벤트에 싣고 닫습니다(a2a/server/routes/jsonrpc_dispatcher.py:601). 저장된 작업은 FAILED(앞 캡처의 GetTask).
  • TS: 오류 대신 statusUpdate FAILED 를 지어 보냅니다 — 메시지 "Agent execution error: 실행기가 죽었다". 클라이언트에게는 정상적인 Task 스트림의 끝입니다.
  • Go: FAILED 상태의 task 하나를 보냅니다. 상태 메시지도 오류 글도 없습니다 — 서버 기록(WARN)에만 남습니다.

HTTP 에서 본 끝 — 길이 0 청크, 연결은 남는다

"스트림이 닫힌다" 는 TCP 연결이 끊긴다는 뜻이 아닙니다. 시험 쪽 10/frames.py 는 탭 없이 소켓으로 COMPLETED 를 청하고, 6부처럼 청크를 손으로 풉니다. 다만 이번에는 Connection: close 를 보내지 않습니다.

세 SDK 서버 모두 청크 하나에 이벤트 하나, 끝은 길이 0 청크

  • 세 서버 모두 HTTP/1.1 chunked, keep-alive 이고, 응답 본문이 끝난 뒤에도 연결을 닫지 않았습니다. 클라이언트에게 "스트림의 끝" 은 길이 0 청크(응답의 끝)입니다. HTTP/1.0 으로 닫아 끝을 알린 맨손 파이썬 서버와 다릅니다.
  • 줄 끝도 다릅니다 — 파이썬(sse-starlette)은 CRLF, TS·Go 는 LF. SSE 는 둘 다 허락하므로(2부) 손으로 읽는 클라이언트는 \r 을 떼야 합니다.

3장 퀴즈

Q. 어떤 실행기가 "INPUT_REQUIRED 로 되묻고, 답을 기다리지 않은 채 0.3초 뒤 기본값으로 COMPLETED" 를 냅니다. 클라이언트가 스트림으로 받는다면 세 SDK 서버에서 각각 무엇을 보고, 저장소에는 무엇이 남습니까?

A. 실험의 LATE 가 바로 그것입니다. 파이썬 서버는 INPUT_REQUIRED 뒤에도 스트림을 열어 두어 WORKING·COMPLETED 까지 보내고 COMPLETED 로 저장합니다. TS·Go 서버는 INPUT_REQUIRED 에서 스트림을 닫고, 뒤의 둘은 버려져 저장소에도 INPUT_REQUIRED 가 남습니다(파이썬·TS·Go). 그런 실행기는 세 SDK 에서 다른 작업을 만듭니다 — 중단 상태를 냈으면 곧 돌아가야 합니다.
