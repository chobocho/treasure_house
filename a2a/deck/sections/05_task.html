5부

Task 생애주기·상태 기계·다중 턴

왜 Task 인가 → TaskState 아홉 가지 → blocking 과 returnImmediately → 숙소 에이전트의 COMPLETED Task → INPUT_REQUIRED 다중 턴 → REJECTED·FAILED·CANCELED → GetTask 와 historyLength → Artifact → 오류

Message 가 말 한마디라면, Task 는 그 말로 시작된 일 하나다

4부에서 SendMessage 의 답이 Message 이거나 Task 라는 것을 봤습니다. 이 부는 Task 쪽으로 들어가, 그 일이 어떤 상태를 거쳐 어디서 끝나는지, 중간에 되물으면 어떻게 이어 말하는지를 세 서버에서 확인합니다.

장무엇을
1장왜 Task 인가 — 상태가 있는 일 단위, 필드 여섯, 세 SDK 의 Task 타입
2장TaskState 아홉 가지 — 상태 기계 그림, 종료와 중단, SDK 가 막는 전이
3장blocking 과 returnImmediately — 교통 에이전트 ×3, GetTask 폴링
4장숙소 에이전트의 COMPLETED Task — 한 필드씩, 와이어와 세 SDK 타입으로
5장INPUT_REQUIRED 다중 턴 — 날짜 → 박 수 → 인원, 같은 taskId·contextId
6장REJECTED·FAILED·CANCELED — 차이와 실제 응답
7장GetTask 와 historyLength — §3.2.4 세 경우
8장Artifact — artifactId·name·parts, 결과는 아티팩트로
9장오류 — TaskNotFound(-32001), 끝난 작업에 메시지 보내기
이 부의 방식 — 3·4부처럼 완성 에이전트(숙소·교통)를 블랙박스로 띄우고 와이어를 읽습니다. 새로 쓰는 에이전트는 실험용 둘뿐입니다 — 상태를 마음대로 옮겨 보는 고집 에이전트(2장, 세 언어)와 이어 말하기를 견주는 파이썬 접수 에이전트(5장).

1장

왜 Task 인가

상태가 있는 일 단위 → Task 의 필드 여섯 → 파이썬의 Task 타입 → TypeScript → Go → 세 SDK 비교 → 시각은 status 에만 있다

Task 는 "상태가 있는 일 단위" 다 — 나중에 다시 찾고, 이어 말할 수 있다

§3.4.2 는 Task 를 "a stateful unit of work with a defined lifecycle" 이라고 부릅니다. 같은 말에 Message 로 답하는 에이전트와 Task 로 답하는 에이전트는 4부에서 나란히 봤으니, 여기서는 Task 만 가진 것을 꼽습니다.

Task 가 주는 것필드·연산이 부의 장
다시 찾기id — 서버가 짓는다(§3.4.2), GetTask 로 묻는다3장
지금 어디쯤인가status.state — 아홉 값 중 하나2장
기다리지 않기returnImmediately — 만든 즉시 돌려받기3장
결과물artifacts — 메시지가 아니라 아티팩트로(§3.7)4장
이어 말하기taskId 를 단 다음 메시지, history5장
Message 응답에는 이것이 없다 — 4부의 Message 응답에는 taskId 가 없었습니다. 다시 물을 손잡이가 없으니, 즉답으로 끝나는 일에만 맞습니다(언제 무엇으로).

Task 의 필드는 여섯, 그중 상태(status)는 다시 필드 셋을 가진다

스펙 §4.1.1·§4.1.2 의 표는 proto 의 Task·TaskStatus 에서 만들어집니다. REQUIRED 가 붙은 것은 id·status·state 셋입니다.

파이썬 — protobuf 설명자(DESCRIPTOR)가 필드 번호와 와이어 이름을 안다

파이썬 SDK 의 a2a.types.Task 는 proto 에서 생성된 protobuf 메시지입니다. 클래스의 DESCRIPTOR.fields 를 돌면 필드가 proto 에 적힌 차례로 나옵니다.

  • json_name 이 와이어 이름(contextId)입니다. 파이썬 속성 이름은 context_id 입니다.
  • 필드는 proto 와 똑같이 여섯·셋입니다. SDK 가 보탠 시각 필드는 없습니다.

TypeScript — 빈 JSON 을 fromJSON 에 읽히면 필드가 다 기본값으로 채워진다

TS 의 Task 는 인터페이스라 실행 때 사라집니다. 대신 ts-proto 가 만든 Task.fromJSON 이 모든 필드를 채운 객체를 돌려주므로, 그 키가 필드 목록입니다.

  • 문자열은 "", 목록은 [], 메시지(status·message)와 Struct·시각은 undefined 입니다. "빠졌다" 를 묻는 법이 필드 종류마다 다릅니다.
  • state 의 기본값은 수 0(TASK_STATE_UNSPECIFIED)입니다. TS 는 enum 을 수로 듭니다(이름은 taskStateToJSON).

Go — 구조체 필드는 ID 다음이 알파벳 차례, 와이어의 키도 이 차례다

Go SDK 의 a2a.Task 는 손으로 쓴 구조체입니다. reflect 로 선언 차례를 훑고, json 태그에서 와이어 이름을 꺼냈습니다.

  • encoding/json 은 선언 차례대로 적습니다. Go 서버의 Task JSON 에서 status 가 맨 끝에 오는 까닭입니다(4부에서 본 메시지의 키 순서와 같은 이유).
  • Status 는 포인터가 아닌 값이라 늘 있고, Timestamp·Message 는 포인터라 없을 수 있습니다. Metadata 는 map[string]any 입니다.

세 SDK 비교 — 같은 여섯 필드, "없음" 을 나타내는 방법은 셋

세 캡처의 필드 이름은 같고 시각 필드를 더한 SDK 도 없습니다. 다른 것은 타입의 모양입니다.

시각은 상태에만 붙는다 — 그리고 SUBMITTED 에는 세 서버 모두 시각이 없었다

status.timestamp 는 "그 상태가 기록된 시각" 이지 작업을 만든 시각이 아닙니다. 상태가 바뀌면 함께 바뀝니다. 3장의 교통 에이전트가 막 만든 작업(SUBMITTED)을 돌려준 응답에서 status 만 골랐습니다.

  • TS 서버의 답도 같습니다(3장). 세 서버 모두 첫 Task 에 시각을 넣지 않았고, 시각은 이어지는 상태 갱신부터 붙습니다(4장의 COMPLETED 에는 있다).
  • 시각의 자릿수와 시간대가 SDK 마다 다르다는 것은 4부에서 봤습니다.

1장 퀴즈

Q. 총무팀이 "이 작업이 언제 만들어졌는지" 알고 싶어 합니다. Task 의 어느 필드를 보면 됩니까?

A. 그런 필드는 없습니다. proto 의 Task 는 id·contextId·status·artifacts·history·metadata 여섯뿐이고, 세 SDK 의 타입도 똑같았습니다(파이썬·TS·Go). 시각은 status.timestamp 하나로 "지금 상태가 기록된 시각" 이며, 막 만든 SUBMITTED 작업에는 그마저 없었습니다(시각). 만든 시각이 필요하면 클라이언트가 보낸 때를 적어 두거나 metadata 에 싣기로 서로 정해야 합니다.

2장

TaskState 아홉 가지

아홉 값과 네 무리 → 상태 기계 그림 → 스펙이 정한 것, 정하지 않은 것 → SDK 가 쓰는 무리 → 고집 에이전트 실험 → 파이썬 → TypeScript → Go → GetTask 로 확인 → 세 SDK 비교

상태는 아홉 — 시작 둘, 중단 둘, 종료 넷, 그리고 "모름"

proto 의 enum TaskState 입니다. 주석이 스스로 "terminal state"(종료 상태)와 "interrupted state"(중단 상태)를 밝힌 값이 있습니다.

수값무리proto 주석(줄임)
0TASK_STATE_UNSPECIFIED모름"unknown or indeterminate state"
1TASK_STATE_SUBMITTED시작"submitted and acknowledged"
2TASK_STATE_WORKING시작"actively being processed"
3TASK_STATE_COMPLETED종료"finished successfully"
4TASK_STATE_FAILED종료"finished with an error"
5TASK_STATE_CANCELED종료"canceled before completion"
6TASK_STATE_INPUT_REQUIRED중단"requires additional user input"
7TASK_STATE_REJECTED종료"decided to not perform the task" — 처음에도, 하다가도
8TASK_STATE_AUTH_REQUIRED중단"authentication is required"
수는 와이어에 나오지 않는다 — 와이어에는 이름 문자열이 실립니다(4부). 수의 차례도 생애의 차례가 아닙니다 — 종료 상태인 REJECTED 가 7, 중단 상태인 AUTH_REQUIRED 가 8 입니다.

상태 기계 — 중단 상태에서는 같은 taskId 로 답하면 다시 일한다

흔한 길을 그렸습니다. 종료 넷에서는 더 나갈 곳이 없고, 중단 둘에서는 클라이언트의 다음 메시지를 기다립니다.

 SUBMITTED ──→ WORKING ──┬──→ COMPLETED          종료 — 끝냈다
     │            ↑      ├──→ FAILED             종료 — 실패했다
     │            │      ├──→ CANCELED           종료 — 취소됐다
     │            │      ├──→ INPUT_REQUIRED ─┐  중단 — 되묻는다
     │            │      └──→ AUTH_REQUIRED ──┤  중단 — 권한을 묻는다
     │            └───────────────────────────┘  같은 taskId 로 답하면
     └────────────────────→ REJECTED             종료 — 안 하겠다
  • 이 그림은 스펙의 표가 아니라 이 책의 요약입니다. 취소는 "an ongoing task" 면 어디서든 청할 수 있고(§3.1.5, 11부), REJECTED 도 "하다가" 올 수 있습니다(proto 주석).
  • 중단에서 다시 일하는 길은 5장(INPUT_REQUIRED)과 12부(AUTH_REQUIRED)가 실제로 보여 줍니다.

스펙에는 전이 표가 없다 — 정한 것은 "어디서 멈추고, 어디서 끝나나" 다

스펙 어디에도 "WORKING 에서 SUBMITTED 로 갈 수 없다" 같은 표는 없습니다. 상태에 걸린 규칙은 넷입니다.

조항규칙
§3.1.1종료 상태(COMPLETED·FAILED·CANCELED·REJECTED)의 작업은 "cannot accept further messages" — UnsupportedOperationError. 실제 응답은 9장에서 봅니다.
§3.1.2스트림은 Task 로 시작하고, 작업이 종료 상태에 이르면 "MUST close".
§3.2.2막는 호출은 종료 상태 "or an interrupted state (INPUT_REQUIRED, AUTH_REQUIRED)" 에 이를 때까지 기다린다(3장).
§3.4.3에이전트는 작업을 "the input-required state" 로 옮겨 입력을 더 청할 수 있다(5장).
§3.4.3 의 input-required — v0.3 시절의 소문자 이름이 v1.0.1 본문에 남아 있습니다. v1.0 의 와이어 값은 TASK_STATE_INPUT_REQUIRED 이고, 세 SDK 도 이 이름만 씁니다.

세 SDK 도 "종료 넷" 은 같게 묶는다 — AUTH_REQUIRED 를 어디에 두느냐가 다르다

설치본의 소스에서 상태 무리를 찾았습니다. 종료 넷은 셋 다 같고, "이번 실행은 여기서 멈춘다" 로 보는 중단 상태가 다릅니다.

SDK종료실행을 멈추는 중단 상태어디(설치본)
파이썬TERMINAL_TASK_STATES 넷INTERRUPTED_TASK_STATES — INPUT_REQUIRED·AUTH_REQUIREDserver/agent_execution/active_task.py

실험 — 끝낸 작업을 또 옮기려 하면 SDK 가 막아 주는가

"고집 에이전트" 를 세 언어로 썼습니다. 실행기가 SUBMITTED Task 를 실은 뒤 WORKING → SUBMITTED(뒤로) → COMPLETED 로 옮기고, 0.2초 쉬었다가 WORKING 을 또 싣습니다. 맨손 클라이언트(05/poke.py)는 막는 SendMessage 뒤 0.5초 쉬고 GetTask 로 상태를 봅니다.

왜 맨손 클라이언트인가 — SDK 클라이언트는 받은 것을 제 타입으로 바꿔 보여 줍니다. 서버가 저장한 상태를 있는 그대로 보려고 urllib 로 JSON-RPC 를 보냅니다(4부의 dup.py 와 같은 방식).

파이썬 — 갱신기(TaskUpdater)는 끝난 뒤의 갱신을 RuntimeError 로 막는다, 갱신기 하나 안에서만

상태는 SDK 의 TaskUpdater.update_status 로 실었습니다. 끝난 뒤에 같은 갱신기로 한 번, 새로 만든 갱신기로 한 번 더 옮겨 봤습니다.

  • 뒤로 가는 SUBMITTED 는 그냥 실렸습니다. 막는 것은 "종료 뒤" 뿐입니다.
  • 그 검사는 갱신기 객체의 깃발(_terminal_state_reached)입니다. 새 갱신기는 그 깃발을 모르니 WORKING 이 실렸습니다 — 서버가 그것을 어떻게 했는지는 GetTask가 보여 줍니다.

TypeScript — 갱신기가 없다, 버스는 무엇이든 받는다

TS SDK 에는 파이썬의 TaskUpdater 같은 도우미가 없어, 이벤트를 AgentEvent.statusUpdate 로 만들어 버스에 직접 싣습니다.

  • bus.publish 는 돌려주는 값도 예외도 없어 실행기는 거절을 알 길이 없습니다 — 넷 다 "실음" 입니다.
  • 요청 처리기는 종료 상태를 받으면 그 실행의 이벤트 읽기를 멈춥니다(ExecutionEventQueue.events). 늦게 실은 WORKING 은 읽히지 않습니다.

Go — 종료 이벤트를 처리하면 SDK 가 실행기의 ctx 를 취소한다

Go 실행기는 이벤트를 yield 로 내보내는 반복자입니다(2부). SDK 쪽 사정은 두 곳에서 알 수 있습니다 — 실행기에 넘어온 ctx, 그리고 yield 가 돌려주는 값.

  • SDK 는 종료 이벤트를 받으면 결과를 내고 실행을 거두며, 그때 실행기의 ctx 를 취소합니다(internal/taskexec/execution_handler.go: "cancel producer context"). 0.2초 뒤의 ctx.Err() 가 context canceled 입니다.
  • 그 뒤에 yield 를 부르면 true 가 나올 수도 있습니다. 이벤트 통로에 쓰는 Write 가 select 로 "통로에 넣기" 와 "취소" 를 함께 기다려, 둘 다 되면 Go 가 아무것이나 고르기 때문입니다(internal/eventpipe/local.go). 그래서 ctx 를 먼저 봤습니다.

GetTask 로 확인 — 파이썬 서버만 끝난 작업을 WORKING 으로 되돌려 저장했다

세 서버 모두 막는 호출에는 COMPLETED 로 답했습니다. 0.5초 뒤에 물은 상태가 갈립니다.

종료 상태가 되살아났다 — 파이썬 서버는 새 갱신기가 실은 WORKING 을 저장소에 그대로 썼습니다. 클라이언트는 COMPLETED 로 끝났다고 들었는데, 나중에 물으면 일하는 중입니다. TS·Go 서버는 COMPLETED 를 지켰습니다.

세 SDK 비교 — 전이를 지키는 것은 결국 실행기다

세 SDK 모두 "뒤로 가기" 는 막지 않았고, "종료 뒤" 는 셋이 셋 다르게 다뤘습니다.

2장 퀴즈

Q. 고집 에이전트는 세 언어 모두 WORKING 다음에 SUBMITTED 를 실었습니다. 어느 SDK 가 이것을 거절했습니까? 그리고 스펙은 이 전이를 금합니까?

A. 아무도 거절하지 않았습니다 — 세 서버 출력 모두 SUBMITTED 실음 입니다(파이썬·TS·Go). 스펙에도 전이 표가 없어 금하는 조항이 없습니다(규칙 넷). SDK 가 손을 대는 것은 종료 상태 뒤의 갱신뿐이고, 그마저 파이썬 서버는 새 갱신기가 실은 WORKING 을 저장했습니다(GetTask).

3장

blocking 과 returnImmediately

§3.2.2 의 두 실행 방식 → 실험 명세 → 파이썬 클라이언트 → TypeScript → Go → 세 클라이언트의 출력 → 와이어의 returnImmediately → 세 서버의 첫 Task → 일은 뒤에서 계속된다 → 세 SDK 비교

막는 호출은 끝나거나 멈출 때까지 기다리고, returnImmediately 는 만들자마자 돌아온다

§3.2.2 "Operations are blocking by default". 요청의 configuration.returnImmediately 하나가 둘을 가릅니다.

막는 호출(기본)returnImmediately: true
언제 돌아오나종료 상태 또는 중단 상태(INPUT_REQUIRED·AUTH_REQUIRED)에 이를 때 — MUST wait"MUST return immediately after creating the task"
답의 상태"the latest task state with all artifacts""an in-progress state (e.g., TASK_STATE_WORKING, TASK_STATE_INPUT_REQUIRED)"
그다음—"the caller's responsibility to poll … subscribe … or receive updates via push notifications"
효과가 없는 때 — 답이 Message 일 때, 스트리밍 호출일 때(늘 실시간), 푸시 알림 설정(실행 방식과 따로 간다)에는 이 필드가 아무 일도 하지 않는다고 §3.2.2 가 못 박습니다. 스트림은 10부, 푸시는 11부입니다.

교통 에이전트 셋에 같은 배차 요청을 두 방식으로

교통 에이전트는 배차에 세 단계를 거칩니다(단계마다 0.5초, --step-ms 500). 클라이언트 modes 를 세 언어로 써서 제 언어의 서버에 붙였습니다. 막는 호출 한 번, returnImmediately 한 번, 그리고 둘째 작업을 GetTask 로 끝날 때까지 지켜봅니다.

폴링은 탭에 걸지 않았다 — GetTask 를 몇 번 묻게 될지는 기계의 빠르기에 따라 달라, 캡처가 실행마다 달라집니다. 그래서 클라이언트는 상태가 바뀔 때만 찍고, 와이어는 마지막 curl 한 번으로 따로 봅니다.

파이썬 — SendMessageConfiguration(return_immediately=…) 을 요청에 단다

보내는 함수 하나에 now 만 바꿔 두 번 부릅니다. 막는 호출이어도 send_message 는 비동기 반복자라, 답 하나를 꺼내 돌려줍니다(4부).

지름길 — ClientConfig(polling=True) 로 만든 클라이언트는 모든 요청에 return_immediately 를 켭니다(client/base_client.py: request.configuration.return_immediately |= self._config.polling). 이 예제는 요청마다 다르게 하려고 직접 달았습니다.

TypeScript — configuration 객체에 returnImmediately: true

ts-proto 타입이라 SendMessageConfiguration 의 필드를 다 적었습니다(선택 필드는 historyLength? 하나뿐, 나머지 셋은 빠뜨리면 타입 검사에 걸린다). 폴링은 client.getTask({tenant, id}) 입니다.

Go — SendMessageConfig{ReturnImmediately: true}, 끝났는지는 Terminal() 로

Go 는 요청의 Config 필드(와이어 이름 configuration)에 담습니다. 종료 상태를 묻는 메서드가 상태 타입에 붙어 있어, 종료 목록을 손으로 적지 않아도 됩니다.

세 클라이언트의 출력이 같다 — 막는 호출은 COMPLETED, returnImmediately 는 SUBMITTED

줄 끝의 수는 받은 Task 의 아티팩트 개수입니다.

  • 막는 호출은 세 단계를 다 기다려 COMPLETED 와 아티팩트 1개를 받았습니다.
  • returnImmediately 는 아티팩트 0개의 SUBMITTED 를 곧장 받았습니다. 스펙의 예시(WORKING·INPUT_REQUIRED)와 다르지만 SUBMITTED 도 진행 중 상태입니다. 그 뒤 GetTask 가 WORKING → COMPLETED 를 따라갔습니다.

와이어 — 요청의 configuration 에 returnImmediately, 답은 SUBMITTED Task

마지막 curl(rpc/bus_now.json)이 파이썬 서버 앞의 탭을 지난 모습입니다.

  • params.configuration.returnImmediately 는 message 옆에 있습니다. 메시지가 아니라 요청에 붙는 설정입니다.
  • 답에는 artifacts 가 아예 없고, status 에 시각도 없습니다(1장).

세 서버의 첫 Task — 상태는 셋 다 SUBMITTED, 키 차례만 다르다

같은 curl 에 대한 세 답에서 Task 의 맨 윗단 키와 상태만 골랐습니다.

세 SDK 가 모두 첫 이벤트를 돌려줬다 — 교통 에이전트의 실행기는 첫 이벤트로 SUBMITTED Task 를 싣고 0.5초를 쉽니다. 세 요청 처리기는 returnImmediately 일 때 그 첫 Task 에서 답을 냈습니다(파이썬은 default_request_handler_v2.py 에서 return_immediately 를 보고 첫 Task 에서 멈춘다).

returnImmediately 는 일을 줄이지 않는다 — 기다림만 줄인다

Go 서버의 출력입니다. 클라이언트가 이미 답을 받아 간 뒤에도 실행기는 세 단계를 끝까지 밟았습니다.

  • 첫 넷은 막는 호출, 다음 넷은 returnImmediately + 폴링, 마지막 넷은 탭 앞 curl 의 작업입니다. 세 작업 모두 같은 일을 했습니다.
  • 명세 끝의 wait ms=2500 은 curl 이 남긴 작업이 끝나기를 기다리는 줄입니다. 서버를 그 전에 끄면 마지막 넷이 잘립니다.

3장 퀴즈

Q. returnImmediately 로 받은 답이 SUBMITTED 였습니다. 그 작업은 아직 시작도 안 한 것입니까? 서버는 그 뒤에 무엇을 했습니까?

A. 일은 서버에서 계속됐습니다. SUBMITTED 는 실행기가 처음 실은 Task 의 상태일 뿐이고(세 서버의 첫 Task), 클라이언트가 그 답을 받은 뒤에도 GetTask 가 WORKING → COMPLETED 를 봤으며(출력) 서버는 세 단계를 끝까지 밟았습니다(Go 서버 출력). returnImmediately 는 클라이언트의 기다림만 없앱니다.

숙소 에이전트의 COMPLETED Task

빠짐없는 요청을 세 서버에 → id·contextId·status·artifacts → history·metadata → TS 서버의 같은 Task → Go 서버의 같은 Task → 파이썬 SDK 로 읽기 → TypeScript → Go → 세 SDK 비교

날짜·박 수·인원을 다 주면 숙소 에이전트는 한 번에 끝낸다

세 숙소 에이전트 앞에 탭을 세우고, 같은 본문을 curl 로 보냈습니다(막는 호출). 이어서 세 언어의 SDK 클라이언트(read_task)가 제 언어의 서버에 같은 요청을 보내고 받은 Task 를 필드별로 찍습니다.

위에서부터 — id·contextId 는 서버가 지었고, 상태는 COMPLETED, 결과는 artifacts 에

파이썬 서버의 답에서 history 앞까지입니다.

  • id·contextId — 요청에 없던 것을 서버가 지었습니다(§3.4.1·§3.4.2).
  • status — state 와 timestamp 뿐, message 가 없습니다. 끝낼 때 할 말이 없으면 비워 둡니다. 되물을 때는 여기에 질문이 실립니다(5장).
  • artifacts — 아티팩트 하나(숙소 견적)에 데이터 파트와 글 파트. artifactId 와 이름·파트의 규칙은 8장에서 봅니다.

아래 — history 에는 우리가 보낸 메시지 하나, metadata 는 없다

같은 답의 나머지입니다.

  • 한 마디로 끝난 작업이라 이력은 사용자 메시지 하나입니다. 파이썬 서버는 받은 메시지에 contextId·taskId 를 채워 넣었습니다(4부).
  • headcount 가 30.0 — 파이썬 서버를 지나면 수가 실수가 됩니다(4부).
  • metadata 는 키째 없습니다. 값이 없는 필드는 적지 않았고, TS·Go 서버의 Task 도 같았습니다(다음 두 슬라이드의 맨 윗단 키).

TS 서버의 같은 Task — 필드와 차례는 파이썬과 같고, 수는 정수 그대로

TS 서버의 답에서 맨 윗단 키, 상태, 수, 이력의 id 만 골랐습니다.

  • 키 차례는 proto 번호 차례(id·contextId·status·artifacts·history)로 파이썬과 같습니다.
  • 이력의 사용자 메시지에 contextId·taskId 를 채운 것도 파이썬과 같습니다. 수는 보낸 그대로 30 입니다.

Go 서버의 같은 Task — status 가 맨 끝, 이력의 메시지는 받은 그대로

같은 방식으로 골랐습니다.

  • 키 차례가 id·artifacts·contextId·history·status — 1장에서 본 구조체 선언 차례 그대로입니다.
  • 이력의 메시지에 contextId·taskId 가 없습니다. Go 서버는 받은 메시지를 그대로 저장합니다(4부).

파이썬 SDK 로 읽기 — 빠진 메시지 필드도 빈 값을 주니, 있는지는 HasField 로 묻는다

세 클라이언트는 같은 순서로 같은 것을 찍습니다. 다른 것은 "없음" 을 묻는 방법입니다.

HasField 를 빼먹으면 — t.status.message.parts 는 오류 없이 빈 목록을 줍니다. "말이 없었다" 와 "빈 말을 했다" 를 가르려면 HasField("message") 가 필요합니다. 파트의 종류는 WhichOneof("content") 로 물었습니다(4부).

TypeScript 로 읽기 — 와이어에 없던 메시지 필드는 undefined

  • timestamp 가 string 입니다. 날짜 계산을 하려면 new Date(…) 로 바꿔야 합니다.
  • state 는 수라 taskStateToJSON 으로 이름을 얻었습니다. role 도 마찬가지(roleToJSON).

Go 로 읽기 — 없을 수 있는 것은 포인터나 맵, nil 로 가린다

  • 매 마디의 답이 Task 입니다. 상태만 바뀌고 작업은 하나입니다(같은 id).

TS·Go CLI 도 글자까지 같은 대화를 했다

두 CLI 는 제 언어의 서버와 이야기했습니다. 견적 본문은 같아서 빼고 물음과 답만 골랐습니다.

막는 호출에서는 서버 언어가 드러나지 않는다 — 세 서버가 이력을 쌓는 방식은 다르지만(뒤에서), 마디마다 돌려준 상태와 물음은 같았습니다. 서버의 차이가 화면에 드러나는 것은 스트림에서입니다(뒤에서).

둘째 마디의 와이어 — 요청에 taskId·contextId, 답의 status 에 다음 물음

파이썬 서버 앞의 탭에서 둘째 주고받음(첫 POST 다음)입니다.

  • 요청의 taskId·contextId 는 첫 답의 result.task.id·contextId 입니다. 둘 다 서버가 지은 것을 돌려보냈습니다.
  • 물음은 status.message 에 ROLE_AGENT 메시지로 실립니다(4부).

네 번 주고받아도 작업 id 와 맥락 id 는 하나다

Go 서버 앞의 탭에서 네 POST 의 id 와 상태만 골랐습니다(Go CLI 의 요청).

contextId 를 빼고 taskId 만 보내도 된다 — §3.4.3 "Agents MUST infer contextId from the task if only taskId is provided". 세 서버가 실제로 그랬다는 것은 4부에서 확인했습니다. 세 CLI 는 둘 다 보냅니다.

이력에 무엇이 남나 — 세 서버 모두 물음과 답이 번갈아 일곱

마지막 답(COMPLETED)의 history 에서 역할과 글만 골랐습니다.

물음은 상태가 바뀔 때 이력으로 간다 — 되물은 말은 처음에는 그때의 status.message 에만 있다가, 다음 상태로 넘어갈 때 이력으로 옮겨집니다. 옮기는 때는 SDK 마다 다릅니다(다음 슬라이드). Go 에서는 에이전트 코드가 거들어야 했던 까닭을 7장에서 봅니다.

세 서버 비교 — 물음을 이력에 옮기는 때가 다르다

셋 다 §3.7 "The agent is responsible to determine which Messages are persisted in the Task History" 안에 있습니다. 설치본에서 찾은 자리입니다.

스트림으로 이어 말하면 — TS·Go 서버만 Task 를 먼저 다시 보낸다

같은 파이썬 CLI 를 스트림 모드로 세 서버에 붙였습니다. task 로 시작하는 줄은 스트림 이벤트가 Task 일 때, status·artifact 는 상태·아티팩트 갱신일 때입니다(스트림의 이벤트 종류는 10부).

§3.1.2 — "If the agent returns a Task, the stream MUST begin with the Task object, followed by zero or more TaskStatusUpdateEvent or TaskArtifactUpdateEvent objects." 이어 말하기의 스트림도 Task 스트림입니다. 파이썬 서버(첫 줄)의 둘째 스트림은 Task 없이 아티팩트로 시작했습니다.

와이어로 확인 — 둘째 스트림의 첫 data 가 artifactUpdate 냐 task 냐

"30명" 을 보낸 스트림 요청과 그 SSE 이벤트들의 종류만 골랐습니다.

  • TS·Go 서버는 지금의 Task 를 TASK_STATE_WORKING 으로 먼저 보냈습니다 — 앞 화면의 task WORKING 줄입니다.
  • 첫 스트림(SUBMITTED Task 로 시작)은 세 서버 모두 규칙대로였습니다. 어긋남은 이어 말하기에서만 납니다.

왜 파이썬만 — 파이썬 SDK 는 이어 말하기의 Task 를 받지 않고, 사용자의 답을 버린다

작은 접수 에이전트(파이썬)를 두 판으로 띄웠습니다. --always 1 판은 이어 말하기에도 Task 를 먼저 싣습니다(§3.1.2 대로). 맨손 클라이언트 twice.py 가 "워크숍 접수" → "30명" 두 마디 뒤 GetTask 로 이력을 봅니다.

"30명" 이 이력에서 사라졌다 — SDK 는 이미 있는 작업의 Task 를 받으면 Task … already exists. Ignoring task replacement. 를 남기고, 그 실행에서 저장할 사용자 메시지를 지웁니다(active_task.py 의 _handle_initial_task 가 message_to_save = None). 그래서 이 책의 파이썬 에이전트는 첫 마디에만 Task 를 싣습니다(agents/common.py 의 begin) — 스트림 규칙을 어기는 쪽을 골랐습니다.

TS·Go 쪽의 선택 — 이어 말하기에도 Task 를, 상태는 WORKING 으로

TS 에이전트들의 begin 입니다. Go 의 common.Begin 도 같은 일을 합니다.

  • TS SDK 는 스트림의 첫 이벤트가 Task·Message 가 아니면 거절합니다 — _advanceStreamPattern 의 "Received … before initial 'Message'/'Task' event."(dist/server/index.js). 그래서 다시 실어야 합니다.
  • Go SDK 는 이미 저장된 작업이면 첫 이벤트를 묻지 않습니다(internal/taskupdate/manager.go 는 저장된 작업이 없을 때만 "first event must be a Task or a message"). 그래도 §3.1.2 를 따르려고 다시 싣습니다.
  • 상태를 WORKING 으로 바꿔 싣는 까닭은 주석에 있습니다 — 멈춘 상태(INPUT_REQUIRED) 그대로 실으면 막는 호출이 그것을 "멈춤" 으로 보고 곧장 돌아갑니다.

세 서버 비교 — 다중 턴은 셋 다 되고, 이력과 스트림의 첫머리가 다르다

이 장에서 본 것을 모았습니다. 다섯 에이전트 × 세 클라이언트 언어로 넓힌 그림은 16부에 있습니다.

5장 퀴즈

Q. 파이썬 숙소 에이전트에 스트림으로 이어 말했더니 둘째 스트림이 Task 없이 시작했습니다. 실행기가 그때도 Task 를 먼저 실으면 스트림 규칙은 지켜질 텐데, 왜 그렇게 하지 않습니까?

A. 파이썬 SDK 1.2.2 가 이미 있는 작업의 Task 를 다시 받으면 "already exists. Ignoring task replacement." 를 남기고 그 실행의 사용자 메시지를 이력에 넣지 않기 때문입니다. --always 1 판에서는 GetTask 의 이력에 "30명" 이 없었습니다(실험). 답을 잃는 것보다 첫 이벤트 규칙(§3.1.2)을 어기는 쪽을 골랐고, 그 결과가 artifactUpdate 로 시작하는 스트림입니다.
