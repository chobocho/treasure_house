기획 에이전트 설계

다섯 걸음 → 걸음과 구역 → 카드 → 세 카드 비교 → 한 문장 풀이 → 일곱 문장 ×3 → 전각 숫자 — 찾고 고치기 → 실행기의 첫머리 ×3 → 되묻기 실행 → 되묻기의 와이어 → 세 서버 비교 → 이번 메시지가 두 번 — 찾고 고치기

기획 에이전트의 일은 다섯 걸음 — 풀이, 발견, 위임, 정산, 계획서

총무팀은 ask 로 한 문장만 보냅니다. 기획 에이전트는 그 문장을 풀고, 동료를 찾아 맡기고, 견적을 모아 결재를 받은 뒤 계획서를 돌려줍니다. 사람에게 되묻는 자리가 두 군데 있습니다.

 ask(총무팀)          기획 에이전트             동료
   │ 한 문장             │
   │──────────────────→ │ ① 풀이 — 빠지면 되묻는다
   │←─ INPUT_REQUIRED ─ │
   │                    │ ② 발견 — 카드 GET ─→ 넷
   │                    │ ③ 위임 — 동시에 ───→ 숙소·식사·교통
   │                    │ ④ 정산 — 견적 셋 ──→ 정산
   │←─ AUTH_REQUIRED ── │    결재가 필요하면 되묻는다
   │ 승인               │
   │──────────────────→ │ ⑤ 계획서 — 아티팩트
   │←─ COMPLETED ────── │
되묻기 둘 — ① 의 INPUT_REQUIRED 는 기획 에이전트 자신의 판단이고, ④ 의 AUTH_REQUIRED 는 정산 에이전트의 요구를 사람에게 넘기는 것입니다(12부의 AUTH_REQUIRED 사슬). 이 장은 ①, 2장은 ②, 3장은 ③ 입니다.

기획 에이전트의 카드 — 글 한 문장을 받고, 마크다운과 JSON 을 낸다

기획 에이전트도 에이전트 하나입니다. ask 가 먼저 하는 일은 다른 에이전트 때와 같이 카드를 받는 것입니다. 파이썬 기획 에이전트 앞의 탭입니다.

  • defaultInputModes 가 text/plain 하나 — 사람의 문장을 받습니다. defaultOutputModes 는 계획서(text/markdown)와 요약(application/json)입니다.
  • capabilities.streaming 이 참이라 ask 는 SendStreamingMessage 로 말을 겁니다. 진행 상황을 흘리는 법은 5장입니다.
  • 스킬 plan-workshop 의 examples 에 이야기의 한 문장을 그대로 실었습니다. 요청에는 스킬을 고르는 자리가 없으니(3부), 견본이 보낼 메시지의 꼴을 알려 줍니다.
  • securitySchemes 가 없습니다. 정산에 내는 토큰은 기획 에이전트가 자기 이름(planner)으로 받습니다 — 사용자의 자격이 아닙니다(4장).

한 문장 풀이는 정규식 여섯 개 — 채식 인원을 먼저 찾아 지운다

기획 에이전트는 LLM 이 아니라 규칙으로 문장을 풉니다(SCENARIO §2.5). 풀이는 기획 에이전트가 아니라 공용 도메인 모듈 workshop 에 있고, 세 언어가 같은 정규식을 씁니다. 파이썬판입니다.

  • (\d+)명 이 채식 2명 의 2 를 먼저 잡지 않도록, 채식 인원을 찾은 뒤 그 첫 번째를 지우고 전체 인원을 찾습니다. Go 의 RE2 에 뒤보기(lookbehind)가 없어서 고른 길이라고 주석이 말합니다.
  • 정규식마다 붙은 ASCII(re.ASCII)는 이 장에서 찾은 결함을 고친 자리입니다(전각 숫자).
  • 필수 셋(date·nights·headcount)이 없으면 {"ok": false, "missing": […]} 를 이 차례로 돌려줍니다. 예산·출발지는 없으면 null 입니다.
  • LLM 을 붙인다면 이 함수 자리입니다 — 문장을 받아 같은 모양의 dict 를 내면 나머지는 그대로 돕니다.

일곱 문장을 풀어 보면 — 언제나 첫 번째로 맞는 것이 이긴다

골든 벡터(ex/fixtures/golden/domain.json 의 parseRequest 일곱 경우 — 일곱째 fullwidth-digits 는 다음 슬라이드의 결함을 고치며 더했습니다)가 세 언어의 답을 묶어 둡니다. 여기서는 골든에 없는 문장도 섞었습니다.

  • 1박 2일 의 2일 은 어느 정규식에도 맞지 않아 박 수는 1 입니다. 채식 2명 포함 30명 은 30명입니다.
  • 30명, 아니 40명 은 30명입니다 — 첫 번째 (\d+)명 이 이깁니다. 사람이 고쳐 말해도 풀이는 그 말을 듣지 않습니다. 기획 에이전트가 대화 전체를 이어 붙여 다시 풀기 때문에(뒤의 실행기), 다중 턴에서도 마찬가지입니다.

전각 숫자 ３０명 — 파이썬만 30명으로 읽었고, re.ASCII 로 고쳤다

같은 일곱 문장을 TypeScript·Go 의 workshop 에 넣었더니 처음에는 한 줄이 달랐습니다. TypeScript·Go 는 ３０명 을 인원으로 보지 않는데, 고치기 전의 파이썬은 {"headcount":30,…} 로 풀었습니다. 그 까닭만 떼어 낸 예제입니다.

  • 파이썬 re 의 \d 는 str 패턴에서 "the whole range of Unicode digits" 를 받고(/usr/lib/python3.14/re/__init__.py 의 설명), int() 도 '３０' 을 30 으로 읽습니다 — 두 단계가 다 통과시켰습니다. Go RE2 의 \d 는 [0-9] 이고(regexp/syntax/doc.go), JavaScript 도 [0-9] 만 받습니다.
  • 고친 곳은 workshop/domain.py 의 정규식 여섯에 re.ASCII 를 준 것입니다(풀이 코드). SCENARIO §2.5 의 "RE2-compatible" 을 파이썬 쪽에서 지킨 셈입니다. 고친 뒤 세 언어의 그 줄입니다.
이 결함은 실제로 있었다 — 골든 여섯 경우가 모두 아스키 숫자라, 세 구현이 골든을 다 통과하면서도 이 문장에서 갈렸습니다. 그래서 고치는 차례도 시험이 먼저였습니다: 골든에 fullwidth-digits(３０명 → {"ok":false,"missing":["headcount"]})를 더하자 파이썬의 골든 시험만 실패했고(TS·Go 는 처음부터 통과), re.ASCII 를 준 뒤 셋 다 통과했습니다.

실행기의 첫머리 — 이력 속 사용자의 말을 전부 이어 붙여 다시 푼다

기획 에이전트의 execute 는 메시지 하나가 아니라 작업 전체의 대화를 풉니다. 되물어서 받은 답이 앞 문장에 덧붙어, 필수 항목이 다 찰 때까지 같은 작업이 이어집니다. 파이썬판입니다.

  • task.history 에서 ROLE_USER 메시지의 글만 모아 빈칸으로 잇습니다. 주석대로 begin() 이 이번 메시지까지 이력에 넣어 두었습니다.
  • 풀이는 예산을 필수로 보지 않지만, 기획 에이전트는 예산이 없어도 되묻습니다 — 4장의 정산에 예산이 들어가기 때문입니다.
  • 되묻는 메시지는 파트 둘입니다. 사람이 읽을 글, 그리고 프로그램이 읽을 DataPart {"missing": […]}. 상태는 requires_input 로 INPUT_REQUIRED 가 됩니다(5부).
  • 맨 앞의 waiting 검사는 결재를 기다리던 작업의 이어 말하기입니다(4장).

TypeScript — 이력만 읽는다, 처음에는 이번 메시지를 한 번 더 붙였다

모양은 파이썬과 같습니다. 대화를 모으는 첫 줄이 이 장에서 고친 자리입니다.

  • 지금은 task.history 만 읽습니다. 첫 턴에는 begin() 이 새 Task 의 history 를 [ctx.userMessage] 로 짓고(agents/common.ts), 이어지는 턴에는 SDK 가 저장된 작업의 이력에 이번 메시지를 이미 붙여 둡니다(server/index.js:2799 의 task.history = [...task.history || [], incomingMessage]).
  • 처음에는 [...task.history, ctx.userMessage] 였습니다 — 그래서 이번 메시지가 두 번 들어갔습니다. 이 장의 끝에서 그 결과와 고친 뒤를 봅니다.
  • parseRequest 의 답은 ok 로 갈리는 합집합 타입이라, req.ok 를 검사한 뒤에야 req.budget 을 읽을 수 있습니다.

Go — 같은 흐름에, 실패를 이벤트 시퀀스의 오류로 돌려준다

Go 의 실행기는 iter.Seq2[a2a.Event, error] 입니다(9부). 풀이와 되묻기는 같고, 끝이 다릅니다.

  • common.Begin 이 이력의 차례를 맞춰 두므로(이전 질문 → 이번 답) task.History 만 읽습니다. 이번 메시지를 따로 붙이지 않습니다.
  • ParseRequest 는 값 둘을 돌려줍니다 — 풀린 결과와, 모자라면 *Missing.
  • 마지막 줄 e.plan(…) 은 값을 돌려주지 않습니다. 처음에는 plan 이 오류를 돌려주면 yield(nil, err) 로 넘겨 SDK 가 까닭 없는 FAILED 로 바꿨는데, 2장에서 고친 뒤로는 실패도 plan 이 까닭을 단 상태로 직접 알립니다(2장).

모자란 문장으로 말을 걸면 — 두 번 되묻고, 셋째 답에서 일을 시작한다

세 기획 에이전트에 같은 대본을 보냈습니다. 첫말 1박 2일, 30명(채식 2명) 에는 날짜와 예산이 없습니다. 명단(--agents)에는 아무도 없는 주소 하나만 주었습니다 — 셋째 답 뒤의 일은 2장에서 봅니다.

  • 첫 되묻기는 날짜만입니다 — 필수 셋 가운데 빠진 것이 날짜뿐이기 때문입니다. 예산은 필수 셋이 다 찬 뒤에 따로 묻습니다(실행기의 두 단계).
  • 2026-10-30부터 라는 짧은 답이 통하는 것은 기획 에이전트가 앞 문장과 이어 붙여 다시 풀기 때문입니다.
  • 셋째 답으로 문장이 다 차자 상태가 WORKING 으로 바뀌고 동료 에이전트를 찾는 중 이 옵니다.

되묻기의 와이어 — 글 파트는 사람에게, DataPart 는 프로그램에게

Go 에서는 nil 카드 — 정산 자리에서는 SDK 가 패닉을 받아 주지만, 위임 자리에서는 아니다

Go 의 맵은 없는 열쇠에 zero 값(nil)을 돌려줍니다. 기획 에이전트의 함수에 그 nil 카드를 넣어 보는 예제입니다. agent.go 는 완성 기획 에이전트 파일의 링크라 getToken·delegate 는 진짜입니다.

  • 정산 자리(앞 슬라이드) — getToken 의 패닉은 실행기 고루틴에서 납니다. Go SDK 는 그 고루틴을 recover() 로 감싸 "event producer panic" 을 오류로 바꾸고(internal/taskexec/execution_handler.go:198), 작업은 FAILED 가 됩니다.
  • 위임 자리 — 숙소가 빠지면 nil 카드는 wg.Go 로 띄운 다른 고루틴의 delegate 로 들어갑니다(3장). WaitGroup.Go 의 문서는 "The function f must not panic" 이고(src/sync/waitgroup.go:223), 그 고루틴 안에서 아무도 되살리지 않은 패닉은 "the program is terminated with a non-zero exit code"(src/builtin/builtin.go:281) — 기획 에이전트 프로세스가 통째로 끝납니다.
그래서 두 겹으로 고쳤다 — 맞는 자리는 발견 직후입니다: 빠진 역할을 이름으로 알리고 일을 맡기기 전에 끝냅니다(lost 구역). 그 검사를 지난 뒤에는 cards[역할] 이 nil 일 수 없지만, Go 는 wg.Go 고루틴 첫머리에 recover() 도 두어 어떤 패닉이든 그 자리의 오류로 바꿉니다(3장의 fan 구역). 이 예제의 getToken·delegate 는 고치지 않았으니 지금도 nil 카드에 패닉합니다 — 막는 것은 부르는 쪽입니다.

파이썬 — asyncio.gather 로 셋을 띄우고, 결과는 넣은 차례로 받는다

  • gather 는 "results (in the order of the original sequence, not necessarily the order of results arrival)" 를 돌려줍니다(/usr/lib/python3.14/asyncio/tasks.py:777). 그래서 lodging, meals, bus 로 바로 풀어 받습니다.
  • 견적을 알리는 for 는 정한 차례 — 주석이 말하는 "알릴 때는 정한 순서대로" 입니다. 결과 자리에 예외가 있으면 cannot 으로 FAILED(2장), COMPLETED 가 아니면 그 까닭으로 거절(REJECTED)합니다(7장).
  • return_exceptions=True — "exceptions in the tasks are treated the same as successful results, and gathered in the result list" 입니다(같은 파일 :778). 하나가 실패해도 셋이 다 끝날 때까지 기다리고, 실패도 정한 차례로 알립니다. 처음에는 이 인자가 없어 첫 예외가 "immediately propagated" 되었습니다.

TypeScript — Promise.allSettled, 배열의 차례가 곧 결과의 차례

  • Promise.allSettled([…]) 은 넣은 배열과 같은 차례의 배열로 풀립니다. done.entries() 의 i 로 labels[i] 를 붙여 정한 차례로 알립니다.
  • Promise.allSettled 의 타입 정의는 "resolved with an array of results when all of the provided Promises resolve or reject"(lib.es2020.promise.d.ts:31) — 거부도 {status: "rejected"} 로 제 자리에 남습니다. 처음에는 Promise.all 이라 하나가 거부되면 곧바로 거부되었습니다.
  • need(role) 의 ! 는 "있다고 믿겠다" 는 표시일 뿐 검사가 아닙니다. 그 믿음을 바로 위의 lostRoles 검사가 받쳐 줍니다 — 처음에는 그 검사가 없었습니다(2장).

Go — sync.WaitGroup.Go 와 자리를 정한 슬라이스, 오류도 자리마다

  • errgroup 이 아니라 표준 라이브러리의 WaitGroup.Go 입니다. 결과와 오류를 tasks[i]·errs[i] — 미리 정한 자리에 넣으니 도착 순서와 상관없이 차례가 정해집니다.
  • wg.Wait() 는 셋이 다 끝나야 돌아옵니다. 그다음 정한 차례로 훑어 첫 오류의 자리를 cannot 으로 알립니다. 고친 파이썬·TypeScript 도 이제 같이 기다립니다.
  • 고루틴 첫머리의 defer … recover() 는 고치며 더한 것입니다 — wg.Go 안의 패닉은 아무도 받지 않아 프로세스를 끝내므로(2장), 그 자리의 오류로 바꿉니다.
  • Go 1.22 부터 for 의 i·role 은 반복마다 새 변수라(go.mod 는 go 1.27.1), 고루틴이 그대로 잡아도 됩니다.

차례는 코드가 정한다 — 세 기획 에이전트 모두 도착 차례와 상관없이 숙소 → 식사 → 교통으로 알렸습니다. 결과를 넣은 차례(gather·Promise.allSettled)나 정한 자리(Go)로 받기 때문입니다. 그래서 동시 위임을 해도 이 캡처는 매번 같고, 세 언어가 같은 줄을 냅니다. 견적 셋을 합친 합계 4,842,000원 이 SCENARIO §2.6 의 값입니다.

세 동료가 받은 contextId 가 하나다 — 기획 에이전트 자기 작업의 맥락

파이썬 기획 에이전트가 보낸 SendMessage 셋을 세 탭에서 하나씩 골랐습니다. 캡처의 <idN> 은 한 파일 안에서 같은 값이면 같은 번호입니다.

  • messageId 는 셋이 다르고(ask_message 가 매번 새로 짓는다) contextId 는 셋 다 <id2> 입니다. 세 동료는 그 맥락을 그대로 받아 각자의 새 작업(id 셋이 다르다)에 붙였습니다.
  • 값은 plan 의 ctx_id = task.context_id — 사용자와 기획 에이전트 사이의 대화 맥락입니다.

동료에게 그 맥락은 "남이 지은 contextId" — 스펙은 SHOULD NOT 이라 한다

세 동료 서버 입장에서 <id2> 는 자기가 지은 적 없는 값입니다. §3.4.1 이 바로 이 경우를 다룹니다.

세 동료가 받은 DataPart 는 풀이 결과 통째로 — 예산까지 간다

같은 요청의 본문입니다. 기획 에이전트는 동료마다 따로 고르지 않고 parse_request 의 답(req)을 그대로 실었습니다.

  • 파이썬이 보낸 숫자는 30.0·6000000.0 입니다 — 4부에서 본 Struct 의 double(4부). TypeScript·Go 는 30 입니다. 어느 쪽이든 동료는 같은 견적을 냈습니다 — 숙소 에이전트의 출력이 세 판 모두 8실, 2,100,000원 입니다.
  • 숙소에는 budget·vegetarians·depart·ok 가, 교통에는 budget 이 쓸모없이 갑니다. 동료는 모르는 키를 무시하지만, 예산은 정산만 알면 되는 값입니다.
예산 확장은 쓰지 않는다 — 14부의 예산 확장(14부)은 상한을 메시지 metadata 에 싣는 계약입니다. 완성 기획 에이전트는 그 확장을 켜지 않고, 이 부도 그것을 요구하지 않습니다. 쓴다면 숙소 위임에만 A2A-Extensions 머리글과 metadata 를 함께 달아야 합니다 — Go 의 a2aext 전파기가 옮기는 것은 요청의 params.metadata 이지 메시지 metadata 가 아닙니다(9부).

3장 퀴즈

Q. 관문은 응답을 교통 → 식사 → 숙소 차례로 돌려주었습니다. 그런데 세 기획 에이전트가 흘린 진행 상황은 어떤 차례였고, 왜 그렇습니까? 기획 에이전트가 셋을 차례로 맡겼다면 관문에서는 무슨 일이 났겠습니까?

A. 셋 다 숙소 → 식사 → 교통이었습니다(차례). 결과를 도착 차례가 아니라 넣은 차례(gather·Promise.allSettled)나 미리 정한 자리(Go 의 tasks[i])로 받고, 알리는 for 가 그 차례로 돌기 때문입니다. 차례로 맡겼다면 첫 요청이 관문에서 짝 없이 10초를 기다리다 504 를 받았을 것입니다 — 명세 끝의 curl 이 받은 그대로입니다(관문).
