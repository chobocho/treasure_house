17부

운영 — 타임아웃·재시도·영속 저장소·로깅

답이 늦게 오거나 오지 않을 때, 서버가 죽었다 다시 뜰 때 — 프로토콜 밖에서 일어나는 일을 세 SDK 로 재 봅니다

16부까지는 "잘 될 때" 를 보였다 — 이 부는 끊기고, 늦고, 죽을 때다

스펙은 와이어의 모양을 정할 뿐, 클라이언트가 얼마나 기다릴지, 실패하면 다시 보낼지, 서버가 Task 를 어디에 둘지는 말하지 않습니다. 그 빈자리를 세 SDK 가 어떤 기본값으로 채웠는지 재고, 우리 손으로 채우는 법을 봅니다.

장무엇을증거
1장타임아웃·재시도·멱등성 — 끊긴 뒤 서버에서 일어나는 일, 다시 해도 되는 실패, 다시 보내지 않고 이어 받기실행 명세 다섯(17/*.run), 예제 다섯 ×3

3장로깅·추적 — 요청 id, contextId 로 흐름 잇기(이 부의 뒤 절반)
4장배포 체크리스트 — HTTPS, 카드 url, 캐시, 키 교체(이 부의 뒤 절반)
과녁은 교통 에이전트 — 배차 세 단계마다 쉬는 교통 에이전트(11부)를 --step-ms 로 느리게 띄워 씁니다. 한 단계 1초면 막는 호출 하나가 3초 걸립니다.

1장

타임아웃·재시도·멱등성 ×3

SDK 기본값 → 파이썬 → TypeScript → Go → 끊고 다시 보내기 → 서버는 계속한다 → 스트림의 시간 제한 → 세 언어 비교 → 다시 해도 되는 실패 → 재시도 ×3 → 실행 → 다시 보내지 않고 이어 받기

시간 제한을 주지 않으면 SDK 가 HTTP 클라이언트를 대신 짓는다 — 그 기본값이 셋 다 다르다

스펙이 숫자로 적은 시간 제한은 에이전트가 웹훅에 POST 할 때의 "recommended: 10-30 seconds"(§4.3.3, §13.2) 하나뿐입니다. 클라이언트가 에이전트를 얼마나 기다릴지는 SDK 의 기본값이 정합니다. 세 언어의 17/defaults 는 클라이언트를 가장 짧게 짓습니다.

SDK 가 짓는 것그 기본 제한
파이썬httpx.AsyncClient()(client_factory.py:81)httpx 의 5초(httpx/_config.py:246)
TS전역 fetch, signal 은 호출이 준 것만(client/index.js:6021)SDK 는 걸지 않는다
Gohttp.Client{Timeout: defaultRequestTimeout}(jsonrpc.go:64)3분(a2aclient/transport.go:26), 본문 읽기까지

SDK 기본값 그대로 6초짜리 일을 맡기면 — 파이썬만 5초에 끊는다

교통 에이전트를 단계 2초(합 6초)로 띄우고, 세 언어 클라이언트가 시간 제한을 하나도 주지 않은 막는 SendMessage 를 보냈습니다(17/defaults ×3).

파이썬은 5초가 넘는 막는 호출을 기본으로는 받지 못한다 — 원인이 ReadTimeout 입니다. 서버는 그 사이에도 배차를 끝까지 했습니다(같은 캡처의 서버 출력 [교통] 완료). 총무팀 CLI 와 기획 에이전트가 httpx 에 timeout=30 을 준 까닭입니다(agents/ask.py:113, agents/planner.py:169).

파이썬 — 클라이언트 전체는 httpx 에, 호출 하나는 ClientCallContext(timeout=) 에

손잡이가 둘입니다. 클라이언트를 지을 때 ClientConfig(httpx_client=httpx.AsyncClient(timeout=…)) 를 넘기거나, 호출마다 context= 로 제한을 줍니다.

  • 호출의 timeout 은 전송이 httpx.Timeout(context.timeout) 으로 바꿔 그 요청에만 겁니다(transports/http_helpers.py:48).
  • httpx 의 Timeout 은 연결·읽기·쓰기·풀(pool) 네 가지를 따로 잽니다(httpx/_config.py 의 Timeout). 읽기 제한은 "소켓에서 한 번 읽을 때" 의 기다림입니다 — 스트림에서 이 차이가 드러납니다(뒤).
  • 넘으면 httpx.TimeoutException 이 A2AClientTimeoutError("Client Request timed out") 로 바뀝니다(http_helpers.py:31).

TypeScript — 클라이언트 단위의 손잡이는 없다, 호출마다 signal

TS SDK 의 호출은 모두 둘째 인자로 RequestOptions 를 받고, 그 안의 signal?: AbortSignal 을 fetch 에 그대로 넘깁니다. ClientConfig 에는 시간 제한이 없습니다.

  • AbortSignal.timeout(ms) 는 그 시각에 스스로 끊기는 신호입니다. 한 번 끊긴 신호는 다시 쓸 수 없어, 재시도할 때는 시도마다 새로 만들어야 합니다(재시도).
  • 끊기면 fetch 가 던진 DOMException(이름 TimeoutError)이 SDK 를 그대로 지나 나옵니다 — SDK 는 전송 오류를 감싸지 않습니다.
  • 모든 호출에 같은 제한을 걸 자리는 ClientConfig 에 없습니다. 전송 옵션의 fetchImpl 을 감싸 넘기는 길이 남습니다.

Go — 호출 하나는 context.WithTimeout, 클라이언트 전체는 http.Client.Timeout

Go 의 모든 호출은 ctx 를 받습니다. 그 ctx 의 기한이 지나면 HTTP 요청도 끊깁니다. 클라이언트 전체의 제한은 WithJSONRPCTransport(&http.Client{Timeout: …}) 로 줍니다.

  • 전송을 고르지 않으면 SDK 가 WithJSONRPCTransport(nil) 로 시작하고(factory.go:64), nil 이면 http.Client{Timeout: defaultRequestTimeout}, 곧 3분을 짓습니다(jsonrpc.go:64).
  • 오류는 감싼 문장 하나입니다 — errors.Is(err, context.DeadlineExceeded) 로 알아봅니다.

1.5초에 끊고 같은 messageId 로 다시 — 세 서버 모두 작업이 둘이 됐다

17/resend ×3 입니다. ① 단계 1초(합 3초)인 교통 에이전트에 1.5초 제한으로 보내 끊기고, ② 같은 messageId m-resend 로 10초 제한을 주어 다시 보내고, ③ 그 맥락의 작업을 ListTasks 로 셉니다.

  • ① 의 오류는 셋이 셋입니다 — A2AClientTimeoutError, TimeoutError, context deadline exceeded. 어느 것도 "요청이 서버에 닿았는지" 는 알려 주지 않습니다.
  • ③ 은 셋 다 2건, 둘 다 COMPLETED, 둘 다 첫 메시지가 m-resend 입니다. 같은 messageId 를 새 메시지로 두 번 보내면 작업이 둘 생긴다는 4부의 결과가 시간 초과에서 그대로 일어났습니다.

클라이언트가 떠나도 서버는 끝까지 한다 — 배차가 두 번 끝났다

같은 실행의 서버 출력입니다(파이썬 서버). TS·Go 서버의 출력도 줄마다 같습니다.

  • [교통] 완료 가 두 줄 — 버스 두 대를 잡았습니다. 첫 작업의 단계가 1·2·3초, 다시 보낸 작업의 단계가 그 0.5초 뒤마다 섞여 찍혔습니다.
  • 세 SDK 모두 실행기를 요청과 떼어 돌립니다. 파이썬은 생산자를 따로 asyncio.create_task 로(active_task.py:548), TS 는 execute() 를 기다리지 않고(server/index.js:2916), Go 는 context.WithoutCancel(ctx) 로 요청의 취소를 끊어 냅니다(internal/taskexec/local_manager.go:182).
시간 초과는 "실패" 가 아니라 "모름" 이다 — 클라이언트가 포기한 순간에도 일은 서버에서 계속됩니다. 그 상태에서 같은 요청을 다시 보내는 것이 이 실행의 이중 배차입니다.

스트림에 거는 1.5초 — 파이썬·Go 는 클라이언트에, TS 는 그 호출에

17/stream_to ×3 에서 제한을 거는 자리만 잘랐습니다. 나머지는 이벤트를 한 줄씩 찍고, 끊기면 3초 뒤 GetTask 로 작업을 보는 같은 코드입니다.

같은 숫자, 같은 과녁 — 셋 다 1.5초이고, 교통 에이전트(단계 1초)는 이벤트를 1초마다 하나씩, 3초 동안 보냅니다. 다른 것은 "무엇의 1.5초인가" 하나뿐입니다.

스트림에 1.5초 제한 — 파이썬은 끝까지 받고, TS·Go 는 1.5초에 끊는다

같은 교통 에이전트(단계 1초)에 SendStreamingMessage 를 열었습니다. 클라이언트는 서버와 같은 언어입니다.

  • 파이썬의 httpx.AsyncClient(timeout=1.5) 는 읽기 한 번마다 1.5초입니다. 이벤트가 1초마다 오니 한 번도 넘지 않았고, 3초짜리 스트림을 끝까지 받았습니다.
  • TS 의 AbortSignal.timeout(1500) 과 Go 의 http.Client{Timeout: 1.5초} 는 호출 전체의 시간입니다. 둘째 이벤트 뒤에서 끊겼고, Go 의 오류 글이 그것을 말합니다 — "Client.Timeout … while reading body".
  • 세 서버 모두 끊긴 뒤에도 배차를 끝냈습니다(3초 뒤 GetTask → COMPLETED).

다시 해도 되는 실패는 둘 — 요청이 떠나지 못했거나, 두 번 해도 같은 호출이거나

§3.3.1 은 "Get operations … are naturally idempotent", "Cancel Task operations are idempotent" 라 못 박고, Send Message 는 "MAY be idempotent" 로만 둡니다. 세 SDK 서버 모두 SendMessage 를 멱등으로 만들지 않았습니다(4부).

실패요청은 서버에 갔나GetTask·ListTasks·CancelTaskSendMessage
연결 거절(서버 없음)안 갔다다시다시
시간 초과·연결 끊김모른다다시다시 보내지 않는다 — 찾아서 이어 받는다(뒤)
A2A 오류(-32001 따위)갔고, 답했다다시 하지 않는다 — 같은 답이 온다
서버가 줄 수 있는 귀띔 — §3.3.2 는 서버에 "temporary failures vs. permanent errors" 를 가르라는 SHOULD 와 "Retry-After" 를 실어도 된다는 MAY 를 둡니다. 세 SDK 설치본 어디에도 Retry-After 를 읽는 코드가 없으니(낱말로 찾아 0건), 쓰려면 재시도 함수가 직접 읽어야 합니다.
간격은 늘려 가며 — 0.1초, 0.2초, 0.4초처럼 두 배씩(지수 백오프) 늘리면 죽은 서버에 요청이 몰리지 않습니다. 실제로는 여기에 지터(jitter, 무작위로 조금씩 어긋나게 하는 값)를 더해 여러 클라이언트가 같은 박자로 두드리지 않게 합니다. 캡처를 고정하려고 이 장의 예제에서는 뺐습니다.

파이썬 — 오류의 클래스만으로는 모른다, __cause__ 의 httpx 예외를 본다

retry 는 호출 하나와 "두 번 해도 같은가(safe)" 를 받습니다. 연결 실패는 늘, 그 밖의 전송 실패는 safe 일 때만 다시 합니다.

  • 전송 오류는 모두 A2AClientError 로 바뀌어 나오지만, 그 클래스는 HTTP 상태 오류와 모르는 JSON-RPC 코드에도 쓰입니다(transports/jsonrpc.py:337). 그래서 클래스가 아니라 감싼 원인(__cause__)이 httpx.ConnectError 인지, httpx.TransportError 인지를 봅니다.
  • 서버의 A2A 오류는 TaskNotFoundError 처럼 제 클래스로 오고 원인이 없습니다 — 다시 하지 않습니다.

TypeScript — 전송 오류는 fetch 의 것 그대로, 원인의 code 로 가른다

TS SDK 는 fetch 의 실패를 감싸지 않습니다. 연결 거절은 fetch 가 던진 오류의 cause.code 가 ECONNREFUSED 인 것으로 알아봅니다.

  • 시간 초과는 이름이 TimeoutError 인 오류, 서버의 A2A 오류는 SDK 의 오류 클래스(TaskNotFoundError)로 옵니다.
  • 재시도하는 호출은 함수로 받습니다. 그래야 시도마다 AbortSignal.timeout() 을 새로 지을 수 있습니다(retry.ts 의 first).

Go — errors.As 로 *net.OpError 의 dial, errors.Is 로 기한 초과

Go SDK 는 전송 오류를 %w 로 감싸 돌려줍니다. 감싼 사슬에서 연결 단계(Op == "dial")의 실패인지, ctx 기한이 지난 것인지를 꺼내 봅니다.

  • 서버의 A2A 오류는 a2a.ErrTaskNotFound 같은 표지 오류로 옵니다(9부의 표지 오류). 이 함수는 그것을 "전송이 아니다" 로만 보고 그만둡니다.
  • 재시도 함수가 호출을 클로저로 받는 것은 TS 와 같은 까닭입니다 — 시도마다 새 context.WithTimeout.

실행 — 없는 작업도, 끊긴 SendMessage 도 한 번에 그만, 죽은 주소만 네 번

17/retry ×3 을 교통 에이전트 셋(단계 1초)에 붙였습니다. ③ 은 카드를 받은 뒤 그 주소만 아무도 듣지 않는 11799 로 바꿔 끼운 클라이언트입니다.

  • ① 서버가 "없다" 고 답한 것은 다시 물어도 같습니다. ② 1.5초에 끊긴 SendMessage 는 safe=False 라 다시 보내지 않았습니다 — 앞의 이중 배차를 막는 자리입니다.
  • ③ 은 0.1·0.2·0.4초를 쉬며 네 번 두드리고 그만뒀습니다. 세 언어가 같은 박자입니다.

끊긴 SendMessage 는 다시 보내지 말고 찾는다 — 열쇠는 클라이언트가 정한 contextId

시간 초과 뒤 클라이언트가 모르는 것은 "작업이 생겼나" 하나입니다. 보내기 전에 열쇠를 정해 두면 서버에 물어 확인할 수 있습니다.

때할 일
보내기 전contextId 를 클라이언트가 짓는다(4부: 세 서버 모두 그대로 받는다)
끊기면ListTasks(contextId) 로 찾는다. 있으면 다시 보내지 않는다
찾았으면그 taskId 에 SubscribeToTask(10부)나 GetTask 폴링(11부)
없으면그때 처음으로 다시 보낸다 — 요청이 서버에 닿지 않았다
처음부터 막지 않는 길 — returnImmediately: true(5부)면 서버가 Task 를 만들자마자 taskId 를 돌려줍니다. 긴 일을 막는 호출로 기다리지 않으니 끊길 일이 줄고, 끊겨도 이미 taskId 가 손에 있습니다.

파이썬 — 끊기면 ListTasks 로 찾고, 찾은 작업에 다시 붙는다

17/safe.py 입니다. 맥락 ctx-safe 를 메시지에 실어 1.5초 제한으로 보내고, 끊긴 뒤에는 다시 보내지 않습니다.

클라이언트가 둘 — 파이썬 SDK 의 subscribe 는 ClientConfig(streaming=True) 인 클라이언트에서만 됩니다(base_client.py:322). 그런데 그 클라이언트는 send_message 도 스트림으로 보내 버려, 막는 호출용 once 와 구독용 sub 을 따로 지었습니다. TS(resubscribeTask)·Go(SubscribeToTask)는 클라이언트 하나로 됩니다.

세 언어 모두 작업은 하나 — 끊긴 뒤 WORKING 을 찾아 붙고, COMPLETED 까지 받았다

17/safe ×3 을 교통 에이전트 셋(단계 1초)에 붙였습니다. 클라이언트는 서버와 같은 언어이고, TS·Go 의 다시 붙는 자리는 아래 두 토막입니다.

  • ② 1.5초에 끊긴 순간 작업은 첫 단계(배차 요청 접수)를 지나 WORKING 이었습니다. ④ 끝난 뒤에도 그 맥락의 작업은 1건 — 다시 보낸 실행의 2건과 견줘 보십시오.
  • 구독의 첫 이벤트는 그때까지의 Task(WORKING), 마지막은 COMPLETED 입니다(10부의 규칙 그대로). 서버 출력의 [교통] 완료 도 서버마다 한 줄입니다.

1장 정리 — 시간 초과는 "모름", SendMessage 는 다시 보내지 말고 찾는다

  • SDK 기본 제한은 파이썬 5초(httpx), TS 없음, Go 3분입니다. 파이썬은 기본값으로 5초 넘는 막는 호출을 받지 못합니다.
  • 같은 "1.5초" 가 파이썬에서는 읽기 한 번, TS·Go 에서는 호출 전체입니다. 스트림에서는 이 차이가 "끝까지 받음" 과 "1.5초에 끊김" 으로 갈립니다.
  • 클라이언트가 끊어도 세 서버 모두 실행기를 끝까지 돌립니다. 그래서 같은 messageId 로 다시 보내면 작업이 둘, 배차가 두 번입니다.
  • 다시 하는 것은 연결 실패와 멱등 호출(Get·List·Cancel)의 전송 실패뿐, 간격은 두 배씩. 끊긴 SendMessage 는 클라이언트가 정한 contextId 로 찾아 구독하거나, 처음부터 returnImmediately 로 taskId 를 받습니다.

1장 퀴즈

Q. 이벤트가 1초마다 오는 3초짜리 스트림에 파이썬은 httpx.AsyncClient(timeout=1.5), Go 는 http.Client{Timeout: 1.5초} 를 걸었습니다. 각각 스트림을 어디까지 받았고, 서버의 작업은 어떻게 됐습니까?

A. 파이썬은 끝까지 받았습니다 — httpx 의 읽기 제한은 읽기 한 번마다라 1초 간격을 넘지 않습니다. Go 는 Task SUBMITTED 와 첫 WORKING 뒤에 "Client.Timeout … while reading body" 로 끊겼습니다 — 본문 읽기까지 잰 호출 전체의 제한입니다. 서버의 작업은 두 경우 모두 끝까지 가서 3초 뒤 GetTask 가 COMPLETED 였습니다(스트림 실험).

죽이는 명세 — restart 는 SIGKILL 뒤 같은 명령으로 다시 띄운다

  • start 는 returnImmediately 로 맡기고 첫 단계(WORKING)를 본 순간 나옵니다. 둘째 단계(1초 뒤)가 오기 전에 죽입니다.

복구 규칙 — 다시 뜰 때 SUBMITTED·WORKING 을 FAILED 로 닫는다

실행기가 없는 달리던 작업은 둘 중 하나입니다 — 다시 돌리거나, 끝났다고 알리거나. 교통 에이전트의 배차는 두 번 하면 안 되는 일이라(1장) 다시 돌리지 않고 닫습니다.

  • INPUT_REQUIRED·AUTH_REQUIRED 는 닫지 않습니다. 클라이언트의 다음 메시지를 기다리는 상태이고, 그 메시지가 오면 처리기가 저장소의 Task 로 실행기를 새로 부릅니다(5부). 다만 15부의 결재 대기처럼 실행기가 기다림을 메모리에 잡아 두는 에이전트라면 그것도 잃습니다(15부).
  • CANCELED 가 아니라 FAILED 입니다 — 아무도 취소를 청하지 않았고, 일을 마치지 못한 것은 서버의 탓입니다. 상태 메시지에 까닭을 적어 클라이언트가 다시 맡길지 정하게 합니다.
  • 다시 돌려도 되는 일(멱등인 실행기)이라면 FAILED 대신 같은 메시지로 실행기를 다시 부르는 규칙도 됩니다. 어느 쪽이든 서버를 띄울 때 한 번, 요청을 받기 전에 합니다. TS·Go 의 recover·Recover 도 같은 일을 합니다.

세 언어 모두 — 죽은 뒤의 WORKING 이 다시 뜨자마자 FAILED 가 됐다

17/recover.run 은 세 서버를 --recover 로 띄우고(처음엔 빈 디렉터리라 할 일이 없다), 서버마다 첫 단계의 작업을 남긴 채 죽입니다. 아래는 다시 띄운 뒤의 ListTasks 셋입니다(파이썬·TS·Go 서버 차례).

클라이언트가 할 일도 생긴다 — FAILED 와 그 문장을 본 클라이언트는 이것이 "업무의 거절"(REJECTED)이 아니라 "서버의 사고" 라는 것을 압니다. 같은 요청을 다시 맡길지는 클라이언트가 정합니다. 그 작업이 끝까지 가지 못했다는 것은 이제 확실하니, 1장의 "모름" 과는 다릅니다.

Q. 파일 저장소를 끼운 교통 에이전트가 배차 첫 단계에서 죽었다 다시 떴습니다(복구 규칙 없음). 3초 뒤 GetTask 의 상태는 무엇이고, 그 작업에 SubscribeToTask 를 열면 파이썬 서버와 Go 서버는 각각 무엇을 돌려줍니까? 죽기 전에 달아 둔 푸시 설정은 어떻게 됐습니까?

A. 상태는 그대로 WORKING, 메시지는 배차 요청 접수 입니다 — 끝낼 실행기가 없습니다(실행). 구독하면 파이썬은 Task 하나 뒤로 아무것도 보내지 않고(2초 동안 더 오지 않음), Go 는 저장된 Task 하나를 주고 스트림을 닫습니다(구독과 취소). 푸시 설정은 메모리 저장소에 있었으므로 1개에서 0개가 됐습니다.
