클라이언트 — ClientFactory 와 맨 Task

메서드 열하나 → 설정은 세 곳 → 카드에서 클라이언트까지 → 막는 호출은 값 하나 → 스트림은 이벤트 그대로 → 스트림을 안 하는 카드 → 우리 fetch 와 인터셉터 → 판 헤더는 덮어 쓴다 → 카드만 받기 → 오류 넷 → 오류는 거의 맨 Error → 모르는 필드 실험 → 클라이언트는 너그러웠다 → 스트림 속 오류는 감싸인다 → 기획 에이전트의 위임 → 정리

클라이언트 메서드 열하나는 JSON-RPC 메서드와 하나씩 짝이다 — 스트림은 따로 있다

메서드 이름만으로 짝을 짓지 않고 SDK 에게 직접 보내게 했습니다. 가짜 fetch 를 끼운 클라이언트로 Client.prototype 의 메서드를 하나씩 부르고, 요청 본문의 method 를 적었습니다. 서버는 없습니다.

  • 파이썬은 send_message 하나가 설정을 보고 둘 중 하나를 보냈지만(7부), TS 는 sendMessage 와 sendMessageStream 이 따로입니다. 이름이 어긋난 곳은 4장의 처리기와 같은 자리 — resubscribeTask → SubscribeToTask — 에 하나 더, listTaskPushNotificationConfig → ListTaskPushNotificationConfigs 입니다.
  • 아래 다섯은 private 메서드입니다. TS 의 private 는 타입 검사에만 있어 실행 중에는 보입니다. close 는 없습니다 — 전송이 fetch 를 부를 뿐 쥐고 있는 연결이 없기 때문입니다.

설정은 세 곳 — 공장의 옵션, 클라이언트 설정, 호출마다의 RequestOptions

파이썬은 ClientConfig 한 곳에 여덟 칸을 모았습니다(7부). TS 는 설치본의 타입 파일(dist/client/index.d.ts, dist/multitransport-client-Bq8elQ1W.d.ts)에서 보듯 셋으로 나눕니다.

createFromUrl 은 카드를 받아, 전송 하나를 골라 Client 에 끼운다

상대는 7장에서 완성할 숙소 에이전트(agents/lodging.ts, 탭 뒤)입니다. 같은 견적 요청을 막는 호출과 스트림으로 한 번씩 보내고, 끝에 GetTask 로 다시 읽습니다.

막는 호출은 값 하나 — Task 나 Message 가 감싸이지 않고 온다

--no-stream 이면 sendMessage 를 씁니다. 답을 받은 뒤 같은 작업을 getTask 로 한 번 더 읽었습니다.

  • 와이어의 {"task": …} 를 전송이 SendMessageResponse.fromJSON 으로 읽고 payload.value 만 돌려줍니다(client/index.js:5882). 그래서 Promise<Task | Message> 이고, 가르는 법은 4부의 "필드 유무" — "messageId" in r 이면 Message 입니다.
  • 파이썬은 막는 호출도 StreamResponse 하나를 내는 반복자였습니다(7부). TS 에서 두 경우를 한 코드로 받고 싶으면 sendMessageStream 을 씁니다 — 스트림을 안 하는 카드에도 맞습니다(조금 뒤).

스트림은 이벤트를 하나씩 그대로 준다 — Task 로 접어 주지 않는다

같은 요청을 sendMessageStream 으로 보냈습니다. for await 가 StreamResponse 를 하나씩 받고, show 가 한 줄씩 찍습니다.

파이썬과 같은 모습 — 첫 task 는 SUBMITTED·아티팩트 0개이고, 끝난 모습은 getTask 로 다시 읽어야 보입니다(7부). 갈래 이름은 와이어의 키 그대로 statusUpdate·artifactUpdate 입니다(2장). 스트림에서 상태와 아티팩트를 손으로 접는 법은 10부입니다.

스트림을 안 하는 카드에 sendMessageStream — SDK 가 SendMessage 로 바꿔 보낸다

같은 스트림 코드로 5장의 2단계 견적 서버를 불렀습니다. 그 카드는 capabilities 가 비어 있습니다.

  • sendMessageStream 은 카드에 streaming 이 없으면 transport.sendMessage 를 부르고, 그 답을 {payload: {$case: "task", …}} 로 감싸 한 번 냅니다(client/index.js:5480, 문서 주석 "Falls back to non-streaming"). 이벤트는 COMPLETED Task 하나입니다.
  • 그래서 상대 카드를 모를 때는 sendMessageStream 쪽이 어느 서버에나 맞는 코드입니다 — ask CLI 가 그렇게 씁니다(agents/ask.ts 의 send). 파이썬은 같은 판단을 ClientConfig.streaming 과 카드로 했습니다(7부).

갈고리 둘 — 전송이 부를 fetch 를 넘기고, 인터셉터로 호출 앞뒤에 끼운다

파이썬은 우리 httpx 연결을 넘겼습니다(7부). TS 에서 그 자리는 전송 공장의 fetchImpl 입니다. 상대는 받은 헤더를 되돌려 주는 5장의 실험 서버입니다.

  • CallInterceptor 는 before·after 둘입니다. args.input(메서드와 요청)과 args.options 를 고칠 수 있고, args.earlyReturn 에 값을 넣으면 전송을 부르지 않고 그 값으로 끝냅니다(타입 파일의 BeforeArgs 주석). 파이썬 인터셉터도 같은 두 메서드와 early_return 을 가졌습니다.
  • 헤더는 serviceParameters 에 넣습니다. JSON-RPC 전송이 그것을 그대로 fetch 의 headers 에 펼칩니다(_fetchRpc).

손으로 적은 A2A-Version: 0.3 은 1.0 으로 덮였고, 인터셉터의 헤더는 그대로 갔다

  • 호출에 준 "A2A-Version": "0.3" 이 서버에 requestedVersion=1.0 으로 닿았습니다. withNormalizedHeaders(:5657)가 전송의 판을 헤더에 넣으며 "overriding any caller-supplied value" 하기 때문입니다 — 판은 고른 인터페이스가 정하지, 호출이 정하지 않습니다.
  • 인터셉터는 그 정리 뒤에 돕니다(executeWithInterceptors, :5701). 차례는 before → fetch → after 이고, after 가 본 것은 맨 Message 입니다. 공장 옵션은 ClientFactoryOptions.createFrom 이 기본값과 합칩니다 — 전송은 이름별로 바꿔 끼우고 인터셉터는 이어 붙입니다.

카드만 받을 때는 AgentCardResolver — 판 헤더는 해석기가 직접 단다

카드를 먼저 모아 고를 때는 AgentCardResolver.default.resolve(url) 를 씁니다(15부의 기획 에이전트). 숙소 에이전트 앞 탭이 본 요청 줄과 판 헤더만 추렸습니다.

  • 카드 GET 넷이 모두 A2A-Version: 1.0 을 달았습니다. 해석기의 resolve 가 요청에 직접 넣기 때문입니다(:5313). 파이썬은 공장이 연결에 심어, 맨 연결로 부른 해석기는 판 헤더가 없었습니다(7부).
  • 해석기는 받은 JSON 을 거의 그대로 돌려줍니다 — 보안 스킴이 proto 모양일 때만 AgentCard.fromJSON 을 거칩니다(normalizeAgentCard, 3부). 그래서 카드의 모르는 필드는 남습니다(조금 뒤).

오류 넷을 일부러 — 카드가 없다, 카드 경로가 없다, 작업이 없다, 보낼 곳이 없다

7부와 같은 넷입니다. 무엇이 던져지는지, 그것이 SDK 의 A2AError 갈래인지, 원인(cause)이 붙었는지 찍었습니다.

SDK 오류는 서버가 답한 하나뿐 — 나머지는 맨 Error·TypeError 다

  • ③만 TaskNotFoundError 입니다. JSON-RPC 오류 -32001 을 전송이 fromJsonRpcErrorResponse(:1899)로 되살린 것이고, 서버 처리기가 던지던 4장의 그 클래스입니다(1장의 표식 덕에 instanceof 가 맞습니다).
  • ①은 Node fetch 의 TypeError("fetch failed") 에 ECONNREFUSED 원인, ②는 Error("Failed to fetch Agent Card from … : 404")(:5317), ④는 express 의 HTML 404 를 JSON 으로 읽다 난 SyntaxError 를 원인으로 단 Error 입니다. 상태 코드는 글 속에만 있습니다.
클라이언트 오류 클래스가 없다 — 파이썬은 전송 쪽 실패를 A2AClientError 로 묶었습니다(7부). TS 에서 가를 수 있는 것은 "A2A 오류인가(instanceof A2AError) 아닌가" 하나입니다. 다시 시도할지는 맨 Error 쪽에서 정합니다.

같은 실험을 TS 클라이언트로 — 모르는 필드 여섯과, 스트림 도중의 오류 하나

파이썬 클라이언트는 답의 모르는 필드 하나에 ParseError 로 멈췄습니다(7부). 같은 여섯 실험을 하는 작은 express 서버를 TS 로 세우고, 하나를 더했습니다 — error 는 막는 호출에는 JSON-RPC 오류로, 스트림에는 Task 다음의 오류 이벤트로 답합니다.

클라이언트 — 08/strict.ts 가 일곱을 막는 호출로 한 번, 스트림으로 한 번 보내고, 받은 상태 이름과 Task 에 createdAt 이 남았는지, 오류면 그 클래스와 instanceof 결과(caught)를 찍습니다. 카드에도 createdAt 을 하나 넣었습니다.

클라이언트는 너그러웠다 — 모르는 필드는 버리고, 모르는 상태는 UNRECOGNIZED

  • 여섯 모두 받았습니다. 전송이 결과를 fromJSON 으로 읽어 모르는 키를 버리기 때문입니다(2장) — createdAt 은 Task 에 남지 않았습니다. §5.7 의 "SHOULD ignore unrecognized fields" 를 지키는 쪽으로, 파이썬 클라이언트와 반대입니다.
  • TASK_STATE_PAUSED 는 오류 없이 -1, 곧 UNRECOGNIZED 가 되었습니다(2장). 상태로 갈래를 나누는 코드는 이 값을 따로 다뤄야 합니다 — 끝난 것도 멈춘 것도 아닙니다.
  • 카드에는 createdAt 이 남았습니다. 해석기가 받은 JSON 을 그대로 주기 때문입니다(앞에서). 결과는 버리고 카드는 남기는, 같은 SDK 안의 두 태도입니다.

스트림 도중의 오류는 맨 Error 로 감싸인다 — 진짜 오류는 cause 에 있다

앞 슬라이드의 error 두 줄을 와이어와 함께 봅니다. 스트림은 Task 이벤트 하나를 낸 뒤 event: error 를 받았습니다.

  • 막는 호출은 TaskNotFoundError 를 받았지만, 스트림에서는 Error("SSE event contained an error: …", {cause}) 이고 TaskNotFoundError 는 그 cause 에 있습니다(client/index.js:6094). 그래서 e instanceof TaskNotFoundError 는 거짓입니다.
  • TS SDK 서버가 바로 이 모양으로 보냅니다 — 첫 이벤트를 낸 뒤의 오류(예: 4장의 차례 위반)는 event: error 로 실립니다(server/express/index.js:3498). 스트림을 쓰는 코드는 e instanceof A2AError || e.cause instanceof A2AError 로 봅니다.

기획 에이전트의 위임 — 카드로 바로, 막는 호출, 토큰은 호출마다의 헤더로

완성 에이전트 가운데 클라이언트를 쓰는 것은 기획 에이전트입니다(15부). 동료에게 일을 맡기는 부분이 이 장의 손잡이를 거의 다 씁니다.

  • 모아 둔 카드(c)로 createFromAgentCard 를 부르고, sendMessage 로 막는 호출을 씁니다 — 끝나거나 멈춘 Task 하나면 되기 때문입니다. Task 인지는 "status" in r 로 봅니다.
  • 토큰은 인터셉터 대신 그 호출의 serviceParameters 로 답니다. 시간 제한 옵션은 따로 없어 signal: AbortSignal.timeout(30_000) 으로 끊습니다. 닫을 연결이 없으니 파이썬처럼 close 를 챙길 일도 없습니다.

6장 퀴즈

Q. 다시 시도할지 가르려고 catch (e) { if (e instanceof TaskNotFoundError) 포기; else 다시 시도 } 를 썼습니다. 상대가 없는 작업이라고 답했을 때, 이 코드는 sendMessage 와 sendMessageStream 에서 각각 포기합니까?

A. sendMessage 에서만 포기합니다. 막는 호출은 TaskNotFoundError 를 그대로 던지지만(strict.ts 의 막는 호출 error 줄, TaskNotFound=true), 스트림 도중의 오류는 맨 Error 로 감싸여 TaskNotFound=false cause=TaskNotFoundError 입니다. 스트림 쪽은 없는 작업에 계속 다시 시도하게 됩니다 — e.cause 도 봐야 합니다.

3단계는 베껴 왔다 — 08/step3_ask.ts 는 앞의 셋을 갖추고 넷째가 없는 판입니다. 파이썬 3단계는 완성판에서 물음 목록·카드를 import 했지만, agents/lodging.ts 는 아무것도 내보내지 않고 모듈 맨 위에서 serve(…) 를 부릅니다 — import 하는 순간 서버가 뜹니다. 그래서 그 셋을 옮겨 적었습니다. 이 문제를 시험에서 어떻게 넘는지는 8장입니다.

물음은 차례가 있는 객체 하나 — 글로 온 답은 정규식 셋으로 읽는다

완성판 머리의 물음 목록과, 되물음에 글로 답한 것을 DataPart 와 같은 모양으로 바꾸는 함수입니다. 정규식은 기획 에이전트도 쓰는 업무 규칙의 것입니다(SCENARIO §2.5).

  • JavaScript 객체는 문자열 키를 넣은 차례대로 돌려주므로 Object.keys(QUESTIONS) 의 차례가 곧 묻는 차례입니다. 첫째만 글로 묻고, 빠진 목록 전부는 DataPart {missing: […]} 로 함께 보냅니다.
  • 읽은 값은 문자열("30")입니다. DataPart 의 수는 이미 정수지만(2장), 글에서 온 것 때문에 asInts 가 한 번 더 정수로 맞춥니다.

begin 과 Updater — 이어 말하기에도 Task 를 먼저, 상태는 WORKING 으로

다섯 완성 에이전트가 함께 쓰는 agents/common.ts 의 첫 단추입니다. TS SDK 는 실행마다 첫 이벤트가 Task 이기를 강제하므로(3장), 이어 말하기에도 지금의 Task 를 다시 싣습니다.

  • 첫 마디면 SUBMITTED Task 를 새로 짓고, 이어 말하기면 ctx.task 의 status 만 WORKING 으로 바꿔 싣습니다. 멈춘 상태 그대로 실으면 막는 호출이 그 자리에서 돌아갑니다(5부).
  • 돌려주는 up 이 3장의 갱신기입니다. live 맵에 taskId 로 넣어 두어, taskId 만 받는 cancelTask 가 실행 중인 것을 찾아 멈춥니다.

3단계 실행기 — 이력을 모두 합쳐 듣고, 모자라면 INPUT_REQUIRED

  • task.history 에는 지난 마디와 이번 메시지가 이미 다 있고(3장), 거기에 ctx.userMessage 를 한 번 더 붙였습니다. 완성판도 같은 모양이라 같은 DataPart 를 두 번 합칠 뿐입니다.
  • up.status(…INPUT_REQUIRED…) 뒤에 return 합니다. 다음 메시지가 오면 처리기가 execute 를 다시 부릅니다. 무엇을 들었는지 마디마다 로그로 찍게 했습니다.

3단계는 둘째 마디에서 벌써 어긋났다 — 날짜를 묻지 않고 박 수를 물었다

대본은 7부와 같습니다. 처음엔 아무것도 주지 않고, 날짜를 묻는데 인원을, 다시 묻는데 박 수를 답하고, 마지막에야 날짜(11월 6일)를 줍니다. 3단계 서버와 완성판에 같은 네 마디를 보냅니다(이번에는 TS 의 ask 입니다).

무엇을 들었나 — 둘째 마디의 이력에 에이전트의 물음이 벌써 있었다

3단계 서버가 마디마다 찍은 "들은 것" 입니다.

  • 둘째 마디에 사용자가 말한 적 없는 "2026-10-30" 과 키 "missing" 이 들어왔습니다. 첫 물음의 글 "(예: 2026-10-30)" 과 그 DataPart 입니다. 그래서 날짜는 "들은" 것이 되고, 남은 박 수를 물었고, 셋째 마디의 "1박" 으로 10월 30일 견적을 냈습니다.
  • 파이썬 3단계는 셋째 마디에야 어긋났습니다(7부). TS 처리기는 에이전트의 물음을 상태를 낼 때 바로 이력에 넣고, 파이썬은 다음 사용자 메시지가 올 때 옮기기 때문입니다(5부). 같은 결함이 SDK 에 따라 한 마디 일찍 드러납니다 — 이 결함이 실제로 있었던 이야기는 7부의 그 슬라이드에 있습니다.

완성판의 실행기 — 다른 것은 heard 를 고르는 filter 한 줄이다

agents/lodging.ts 의 LodgingExecutor 를 통째로 실었습니다. 3단계와 견주면 m.role === Role.ROLE_USER 로 거르는 filter, 견적 요약 글 파트, 서버 로그만 다릅니다.

같은 네 마디 — 완성판은 날짜를 세 번 묻고, 11월 6일의 춘천을 골랐다

  • 빠진 목록이 ["date","nights","headcount"] → ["date","nights"] → ["date"] 로 줄고, 마지막 마디의 2026-11-06 으로 끝났습니다. 답은 골든의 cheapest-wins 사례(춘천 5실 1,860,000원)와 같습니다.
  • 답(> …)마다 task WORKING 줄이 하나씩 있습니다. begin 이 이어 말하기의 스트림을 Task 로 시작했기 때문이고, 파이썬 완성판의 대본(7부)과 다른 것은 이 줄뿐입니다(6부).

골든 열세 사례를 A2A 너머로 — 업무 규칙 시험과 같은 기대값

업무 규칙은 workshop/domain.test.ts 가 이미 골든 파일로 시험합니다(make golden). 같은 chooseLodging 사례를 떠 있는 에이전트에 막는 호출로 보내, 아티팩트의 DataPart(또는 거절 까닭)를 기대값과 견줍니다.

정수로 되돌릴 일이 없다 — 파이썬판은 Value 를 지나 실수가 된 수를 tidy 로 정수로 바꿨습니다(7부). TS 의 DataPart 는 넣은 값 그대로라 isDeepStrictEqual 로 바로 견줍니다 — 키 차례는 따지지 않습니다.

13/13 — 거절 다섯은 까닭까지, 서버 로그는 파이썬 완성판과 한 줄도 다르지 않다

  • 거절은 아티팩트 없이 REJECTED, 까닭은 상태 메시지에 있습니다 — 문 닫은 날·넘치는 인원은 "가능한 숙소가 없습니다", 0명·0박은 업무 규칙의 입력 검사입니다. zero-headcount 는 키가 있으니 되묻지 않고 넘깁니다(7부와 같은 까닭).
  • 로그 열일곱 줄은 7부의 파이썬 완성판 로그와 글자까지 같습니다. pyList 가 빠진 목록을 파이썬 리스트 모양(['date', 'nights'])으로, comma 가 천 단위 쉼표를 맞춘 덕입니다.

7장 퀴즈

Q. 같은 3단계 실행기와 같은 네 마디 대본인데, 파이썬 서버는 셋째 마디에서, TS 서버는 둘째 마디에서 어긋났습니다. 둘째 마디에서 TS 의 3단계가 들은 "2026-10-30" 은 어디서 왔고, 왜 파이썬에서는 그 마디에 없었습니까?

A. 에이전트 자신의 첫 물음 "날짜는 언제입니까? (예: 2026-10-30)" 에서 왔습니다(3단계 로그의 둘째 줄). TS 처리기는 에이전트가 INPUT_REQUIRED 와 함께 낸 물음을 그때 바로 이력에 넣어, 둘째 execute 의 ctx.task.history 에 이미 있습니다. 파이썬 SDK 는 지난 물음(status.message)을 다음 사용자 메시지가 저장될 때에야 이력으로 옮기므로, 둘째 마디의 실행기에는 아직 보이지 않았습니다(5부).

8장

시험 — node:test 로, SDK 서버를 프로세스 안에서

이 node_modules 의 시험 도구 → 본보기는 골든 시험 → import 하면 뜨는 에이전트를 mock.module 로 → 처리기 시험 틀 → 시험 넷 → 시간을 찍지 않는 실행기 → 초록불 → 3단계에 돌리면 빨간불 → HTTP 층은 포트 0 → 세 층의 결과 → 시험에서 조심할 것 → 정리

시험 도구는 내장 node:test — jest·vitest·supertest 는 이 node_modules 에 없다

무엇으로 시험할지 고르기 전에, 깔려 있는 것을 물었습니다. 파이썬에서 pytest 없이 unittest 를 쓴 것(7부)과 같은 판단입니다.

  • Node 24 에는 시험 실행기(node --test)와 describe·test·훅·mock 이 들어 있고, 단언은 node:assert/strict 입니다. 업무 규칙 시험(make golden)이 이미 이것으로 돕니다. 이 책은 시험 도구를 따로 깔지 않습니다.
  • mock.module 이 undefined 인 것을 기억해 두십시오. 모듈을 바꿔 끼우는 이 기능은 Node 24 에서 실험 기능이라 --experimental-test-module-mocks 를 줘야 생깁니다 — 곧 그것이 필요합니다.

본보기는 업무 규칙의 골든 시험 — 사례마다 test 하나

세 언어의 업무 규칙은 같은 골든 파일을 읽어 시험합니다(SCENARIO §4). TS 쪽 workshop/domain.test.ts 의 중심입니다.

  • 사례 하나가 틀려도 나머지를 계속 봅니다 — 파이썬의 subTest 자리를 시험 이름(chooseLodging/story)이 맡았습니다. 에이전트 시험에서는 한 시험 안의 하위 시험(t.test)으로 같은 일을 합니다.
  • 골든 파일이 기대값의 하나뿐인 원본이라, 에이전트 시험에도 숫자를 다시 적지 않습니다.

import 하면 뜨는 에이전트 — mock.module 로 serve 를 가로챈다

완성판 agents/lodging.ts 는 실행기를 내보내지 않고, 모듈 맨 위에서 parseCli() 와 serve(…) 를 부릅니다(7장). 파일은 고치지 않고, 그 둘이 사는 agents/common.ts 를 시험 안에서만 바꿔 끼웁니다.

  • mock.module(경로, {exports}) 뒤에 그 모듈을 import 하는 코드는 진짜 대신 exports 를 받습니다. 진짜 모듈을 먼저 import * as real 로 불러 두고 펼쳐 넣었으니, 바꾼 것은 둘뿐입니다.
  • serve 는 받은 카드와 실행기를 쥐기만 하고 포트를 열지 않습니다. 파이썬은 if __name__ == "__main__" 덕에 from agents.lodging import LodgingExecutor 한 줄이었습니다(7부). 새로 짓는 에이전트라면 실행기를 내보내고 import.meta.main 일 때만 띄우는 편이 낫습니다 — 이 장의 3단계(08/step3_ask.ts)가 그렇게 했습니다.

시험 틀 — 실행기를 받는 함수 하나, 시험마다 새 처리기, 말 한마디는 say()

4장에서 HTTP 없이 처리기를 부른 방법을 시험 틀로 옮겼습니다. 묶음 전체가 lodgingSuite(이름, 실행기, 카드) 라는 함수 안에 있어, 같은 시험을 다른 실행기에 돌릴 수 있습니다.

  • beforeEach 가 시험마다 새 처리기·새 메모리 저장소를 짓습니다. 실행기는 하나를 함께 씁니다 — 숙소 실행기는 상태가 없고, 실행 중 작업을 적는 live 맵만 모듈에 있습니다.
  • 요청은 와이어 모양 JSON 을 SendMessageRequest.fromJSON 에 넣어 짓습니다(2장). 빈 필드를 하나하나 적지 않아도 됩니다. 보낼 messageId 는 시험이 정합니다(m-1…).

시험 넷 — 골든, 첫 되물음, 이어 말하기, 사용자 말만 듣기

7부와 같은 넷입니다. 시험 이름도 그대로 영어로 두어, 두 부의 결과를 나란히 볼 수 있게 했습니다.

  • golden 은 사례마다 하위 시험(t.test)을 엽니다. 답은 Task 객체 그대로이고, 상태·상태 메시지의 DataPart·아티팩트를 꺼내 견줍니다. id 는 실행마다 다르니 견주지 않습니다.
  • assert.deepEqual 은 node:assert/strict 의 것이라 깊은 엄격 비교입니다. DataPart 의 수가 정수 그대로라(2장) 형까지 맞습니다 — 파이썬에서 2100000.0 == 2100000 에 기대던 자리입니다.

node --test 를 프로그램으로 — 걸린 시간을 찍지 않는 보고기를 단다

내장 보고기는 시험마다 걸린 시간((3.7ms))을 찍어 실행마다 글자가 달라집니다. 파이썬에서 NoClock 으로 시간을 가린 것처럼(7부), node:test 의 run() 이 내는 이벤트를 받아 우리 모양으로 찍습니다.

하는 일은 node --test 와 같다 — run({files, execArgv}) 는 node --test --experimental-test-module-mocks 파일 처럼 시험 파일마다 프로세스를 하나 띄우고, 그 결과를 test:start·test:pass·test:fail 이벤트로 알립니다. 같은 일을 --test-reporter=파일 로 줄 수도 있습니다. 에이전트가 찍는 서버 로그(test:stdout)는 버리고, stderr 는 프로세스 번호만 가려 남깁니다.

초록불 — 넷 다 통과, 골든 열세 사례는 golden 아래 하위 시험으로

  • "시험 16" 은 잎 시험의 수입니다 — 골든 열셋에 나머지 셋. golden·완성판 은 묶음이라 세지 않았습니다.
  • 맨 위 두 줄은 시험 프로세스의 stderr 입니다. mock.module 이 실험 기능이라는 경고이고, 시험이 실패한 것이 아닙니다.

같은 시험을 3단계에 — 빨간불은 하나, 이번에도 "어긋난 답" 시험만 잡았다

시험은 그대로 두고 실행기만 7장의 3단계로 바꿨습니다. 3단계는 실행기를 내보내므로 mock.module 없이 그냥 import 합니다.

  • 골든 열세 사례와 이어 말하기 시험은 3단계에서도 통과했습니다. follow-up completes 의 물음 "인원은 몇 명입니까?" 에는 예시가 없어, 이력에 들어와도 읽을 것이 없습니다.
  • 떨어진 것은 hears only the user 하나 — 실제 "gapyeong-solsup", 기대 "chuncheon-lake". 7장에서 손으로 본 결함이고, 7부와 같은 시험이 같은 값으로 떨어졌습니다. TS 에서는 둘째 마디에 어긋났지만, 시험은 마지막 답만 보므로 결과가 같습니다.

HTTP 층은 포트 0 — 같은 프로세스 안에 express 앱을 띄우고 fetch 로 부른다

처리기 시험은 express 처리기·직렬화를 지나지 않습니다. 파이썬의 TestClient 처럼 소켓 없이 앱을 부르는 도구가 이 node_modules 에는 없어, 앱을 127.0.0.1 의 포트 0(운영체제가 고른 빈 포트)에 같은 시험 프로세스 안에서 띄웁니다.

  • 카드의 url 이 실제 주소여야 SDK 클라이언트가 그리로 갑니다. 그래서 먼저 듣기 시작해 포트를 알아낸 뒤, 그 주소로 완성판을 불러오고(loadLodging(base)), 앱을 server.on("request", app) 으로 답니다.
  • 앱의 짜임은 완성판의 serve 와 같습니다 — 카드는 toJSON 해서(5장), JSON-RPC 는 / 에.

와이어 시험 둘과 SDK 클라이언트 시험 하나 — 세 층이 모두 초록

무엇을 봤나 — 와이어 시험은 결과의 status.state, 견적 total 이 JSON 에서도 정수인지, 모르는 메서드의 -32601 을 봤습니다. 클라이언트 시험은 카드를 받아 스트림으로 묻고, 이벤트가 SUBMITTED Task → INPUT_REQUIRED 상태 갱신 차례인지 봤습니다(6장).

이 SDK 만의 것 — 두 모듈 체계, 다중 전송, express 미들웨어, 인증 fetch

TS SDK 에서 두드러지는 것 — 둘은 이 SDK 에만 있고, 셋은 있되 모양이 다르다

1~8장은 세 SDK 가 모두 가진 일을 TS 로 했습니다. 이 장은 다른 SDK 에 같은 것이 없거나, 같은 이름이라도 갈리는 자리가 다른 것들입니다(파이썬 쪽은 7부, Go 쪽은 9부의 같은 장).

무엇설치본다른 SDK 에서는슬라이드
ESM·CommonJS 두 벌진입점마다 .js·.cjsJavaScript 만의 일이 장
401 이면 헤더를 바꿔 한 번 더 — 인증 fetchcreateAuthenticatingFetchWithRetry(client/index.js:2)파이썬 AuthInterceptor·Go CredentialsService 는 다시 하지 않는다이 장
다중 전송 — 기본 공장이 바인딩 둘을 안다ClientFactoryOptions.default, restHandler파이썬 클라이언트는 기본이 JSON-RPC 하나(3부)이 장

없는 것도 있다 — 설치본 dist/ 어디에도 OpenTelemetry 가 없습니다. 파이썬 SDK 의 원격 측정(7부) 같은 것은 우리 미들웨어가 맡을 몫입니다. DB 저장소는 peer 인 kysely 를 깔지 않아(1장) 이 책에서는 돌리지 않습니다. 사용자를 세우는 UserBuilder 는 5장, 인증은 12부입니다.

한 패키지에 ESM 과 CommonJS 두 벌 — 클래스는 둘이어도 instanceof 는 맞는다

package.json 의 진입점마다 "import" 와 "require" 가 따로 있습니다. 이 책은 import 만 쓰지만, 옛 CommonJS 코드가 require 로 같은 SDK 를 부르면 한 프로세스에 두 벌이 함께 섭니다.

  • 두 벌은 클래스·enum 객체가 서로 다릅니다. 그래도 CommonJS 쪽에서 던진 오류를 ESM 클래스로 instanceof 하면 참입니다 — 1장에서 본 표식(Symbol.for)이 번들 사이뿐 아니라 두 모듈 체계 사이에서도 일합니다.
  • enum 은 값이 수라서 두 벌을 섞어도 견줌이 맞습니다. 견주면 틀리는 것은 객체 자체(===)와 constructor 입니다.

한 express 앱에 바인딩 둘 — 같은 처리기를 /rpc 와 /rest 에 단다

9장의 실험 서버(08/only_server.ts) 하나에 이 장의 손잡이를 모두 달았습니다. 먼저 다중 전송입니다. 카드에 인터페이스 둘을 적고, 같은 요청 처리기를 JSON-RPC Router 와 REST Router 에 넘깁니다.

클라이언트가 고르는 문 — 카드 차례, 내 선호, 아는 전송

  • 기본은 카드의 차례대로 첫째인 JSON-RPC 입니다. preferredTransports 를 주면 그것이 앞서고, 공장이 REST 만 알면 카드 차례와 상관없이 REST 입니다(createFromNormalizedAgentCard, client/index.js:6515).
  • REST 문은 POST /rest/message:send 이고, 답은 application/a2a+json 입니다. 같은 실행기의 같은 답이 바인딩만 바꿔 나갔습니다. 바인딩끼리의 차이는 13부입니다.

SDK 처리기는 express Router — 그 앞에 우리 미들웨어와 우리 파서를 끼운다

앱 맨 앞에 요청을 찍는 미들웨어를 두고, /big 에는 본문 한도 1 MB 인 우리 express.json 을 SDK Router 앞에 끼웠습니다. 150 KB 요청과 끝이 잘린 JSON 을 /rpc(SDK 그대로)와 /big 에 보냅니다(이 둘만 탭을 거치지 않았습니다 — 150 KB 가 캡처에 실리지 않게).

우리 파서가 이겼다 — 150 KB 는 통과, 대신 깨진 JSON 은 -32700 이 아닌 HTML 400

  • /rpc 의 150 KB 는 SDK Router 안의 express.json()(한도 102,400 바이트)이 413 HTML 로 돌려보냈습니다(4부). /big 에서는 우리 파서가 먼저 읽었고, body-parser 는 이미 읽힌 본문을 건너뛰므로 SDK 쪽 한도가 걸리지 않았습니다.
  • 대신 깨진 JSON 의 답이 바뀌었습니다. SDK 파서 뒤에는 JSON-RPC 오류 -32700 을 짓는 처리(jsonErrorHandler, server/express/index.js:3409)가 있지만, 우리 파서의 오류는 그 Router 에 닿지 않고 express 기본 처리기의 400 HTML 이 됩니다. 앞에 파서를 둘 때는 그 오류도 JSON-RPC 로 바꾸는 처리기를 함께 둡니다.
  • 맨 앞의 [mw] 줄은 SDK 가 거절한 요청까지 모두 찍혔습니다. 로그·속도 제한·인증처럼 "모든 요청" 에 할 일은 이 자리에 둡니다.

401 이면 한 번 더 — createAuthenticatingFetchWithRetry 는 fetch 를 감싼다

문지기 미들웨어가 Authorization: Bearer workshop-demo 가 없으면 401 과 WWW-Authenticate 로 돌려보냅니다. 클라이언트는 SDK 의 인증 fetch 로 그 답을 보고 헤더를 바꿔 다시 보냅니다. 토큰을 실제로 받아 오는 일(OAuth2)은 12부이고, 여기서는 정해 둔 값을 씁니다.

세 갈고리 — headers() 는 요청마다 붙일 헤더, shouldRetryWithHeaders(req, res) 는 답을 보고 다시 할 헤더(아니면 undefined), onSuccessfulRetry 는 다시 해서 됐을 때 그 헤더를 쥐어 둘 기회입니다(dist/client/index.d.ts 의 AuthenticationHandler). 감싼 fetch 는 전송 공장의 fetchImpl 로 넘깁니다 — 6장의 그 자리입니다.

첫 요청은 401 뒤에 다시 보내 성공, 둘째 요청은 처음부터 토큰을 달았다

  • 요청 1 은 와이어에 둘입니다 — Authorization 없이 한 번(401), 있게 한 번(200). SDK 클라이언트는 401 을 본 적이 없습니다. 다시 보내기는 fetch 안에서 끝났기 때문입니다.
  • 요청 2 는 onSuccessfulRetry 가 쥐어 둔 토큰을 headers() 가 처음부터 달아 한 번에 갔습니다. 다시 하는 것은 한 번뿐입니다 — 그 답도 401 이면 그대로 돌려줍니다(authFetch, client/index.js:2).

v0.3 호환은 판 헤더로 갈린다 — 그리고 카드에 판 0.3 인터페이스가 있어야 한다

jsonRpcHandler 의 legacyCompat: {enabled: true} 가 파이썬의 enable_v0_3_compat(7부) 자리입니다. 견적 에이전트를 스위치만 켠 /old1 과, 카드에 판 0.3 인터페이스를 하나 더 적은 /old 에 달았습니다.

갈림길 — express 처리기는 A2A-Version 머리글이 없거나 0.3 이면 옛 처리기로 보냅니다(server/express/index.js:3411) — §3.6.2 의 "Agents MUST interpret empty value as 0.3 version" 그대로입니다. 그다음 머리글의 판을 카드의 그 바인딩 인터페이스들이 적은 판과 견줍니다(validateVersion, :2164). 파이썬은 메서드 이름(message/send)으로 갈랐습니다.

네 요청의 답 — 스위치만으로는 -32009, 머리글 없는 v1.0 요청은 -32601

v0.3 꼴 요청(ex/run/08/rpc/v03_send.json, 7부와 같은 것)을 /old1 과 /old 에, v1.0 요청을 /old 에 머리글 없이 한 번, A2A-Version: 1.0 으로 한 번 보냈습니다.

  • ① /old1: 스위치를 켰어도 -32009 "'0.3' is not supported" 입니다. 옛 처리기로 가기 전에 판 검사에서 막혔습니다 — 옛 피어를 받으려면 카드에 그 판을 적어야 합니다. ② /old: 옛 모양("kind": "task", "completed")으로 답했습니다.
  • ③ 머리글 없는 v1.0 요청은 옛 처리기로 가서 -32601 "Method not found: SendMessage" 입니다. 스위치가 꺼진 서버라면 -32009 였습니다(5장). ④ 머리글을 달면 v1.0 답입니다. 호환을 켠 TS 서버에서는 v1.0 클라이언트가 판 머리글을 빠뜨리지 않는 것이 더 중요해집니다.

Q. 협력사의 v0.3 클라이언트를 받으려고 견적 에이전트의 jsonRpcHandler 에 legacyCompat: {enabled: true} 만 켰습니다. 협력사의 message/send 는 무슨 답을 받습니까? 고친 뒤, 우리 v1.0 클라이언트가 curl 로 판 머리글 없이 SendMessage 를 보내면 어떻게 됩니까?

A. 협력사는 -32009 "The requested A2A protocol version '0.3' is not supported" 를 받습니다 — 판 검사가 카드의 인터페이스를 보는데 카드에 판 0.3 이 없기 때문입니다(/old1). 카드에 판 0.3 인터페이스를 더하면 옛 모양으로 답합니다. 그 서버에 머리글 없이 보낸 SendMessage 는 옛 처리기로 가서 -32601 "Method not found: SendMessage" 입니다(같은 슬라이드의 ③). 파이썬은 메서드 이름으로 갈라 이런 일이 없었습니다.
