SendMessage·GetTask·CancelTask

요청 하나의 길 → 업무(work) ×3 → 실행기와 견주기 → 메시지 검사 → begin 의 문 넷 → 막는 호출 → TypeScript → Go → 세 언어 비교 → 일곱 번 두드리기 → 와이어 → SDK 와 견주기 → GetTask 와 historyLength → CancelTask 와 두 번째 취소 → 정리

Send 두 메서드는 앞부분(begin)과 업무(work)를 함께 쓴다

막는 호출이든 스트림이든 "메시지를 받아 작업에 붙이고, 숙소 일을 한다" 는 같습니다. 다른 것은 끝에서 무엇을 돌려주느냐 하나입니다.

상태는 저장소에, 이벤트는 소식일 뿐 — 업무 코드는 저장소의 Task 를 옮기면서(3장의 move) 그 일을 알리는 이벤트를 하나씩 돌려받습니다. 막는 호출은 그 소식이 필요 없고, 끝난 Task 만 읽으면 됩니다.

업무는 이벤트 목록을 돌려주는 함수 하나 — 되묻기·거절·견적

완성 에이전트에서 실행기(AgentExecutor)가 하던 일입니다. 들은 것으로 요청을 맞춰 보고, 셋 가운데 하나로 끝냅니다.

  • 되묻기 — 빠진 첫 항목을 글로 묻고, 빠진 목록 전부를 DataPart 로 함께 싣습니다. 상태 메시지(status.message)로 갑니다.
  • 견적 — 아티팩트를 먼저 붙이고 COMPLETED 로 옮깁니다. 이벤트도 그 차례(artifactUpdate → statusUpdate)로 나갑니다.

들은 것은 사용자의 말만 — DataPart 먼저, 글이 덮는다

이어 말하기에서는 이력 전체가 "지금까지의 대화" 입니다. 그 안에는 에이전트 자신의 물음도 있습니다.

  • ROLE_USER 만 — 물음의 보기 "(예: 1박)" 을 정규식이 답으로 읽으면, 묻지도 않은 박 수를 들은 셈이 됩니다. 업무 코드가 이력을 읽을 때 role 을 거르는 까닭입니다.
  • 합치는 차례 — 모든 DataPart 를 먼저 합치고, 글에서 읽은 값이 그 위를 덮습니다. 정규식(domain.DATE 따위)은 완성 에이전트와 같은 workshop 의 것입니다.

TypeScript — 서버 기록까지 파이썬과 같게 맞춘다

흐름은 같습니다. 다른 곳은 숫자를 다루는 법과, 파이썬이 저절로 해 주던 글꼴 맞추기입니다.

  • Math.trunc(Number(…)) — DataPart 에서 온 30 도, 글에서 읽은 "30" 도 정수 30 이 됩니다.
  • pyList·comma — 파이썬의 print(missing) 이 찍는 ['headcount'] 꼴과 {:,} 의 천 단위 쉼표를 손으로 만듭니다. 세 서버의 기록 줄이 같아야 캡처를 견줄 수 있어서입니다.

Go — 옮기기가 실패할 수 있으니 이벤트와 오류를 함께 돌려준다

bs.Move 는 전이 표를 어기면 IllegalMove 를 값으로 돌려줍니다(3장). 그래서 lodging 도 ([]bs.Event, error) 입니다.

  • toInt(helpers 구역) — encoding/json 은 맵 속 수를 float64 로 읽고, 글에서 읽은 것은 문자열입니다. 둘 다 받아 int 로 바꿉니다.
  • 빠진 항목의 차례 — Go 의 맵은 도는 차례가 정해져 있지 않아, 묻는 차례를 order 슬라이스에 따로 적어 두고 그것으로 돕니다.

SDK 판 실행기와 견주면 — 이벤트를 "넣느냐" "돌려주느냐"

완성 숙소 에이전트(agents/lodging.*)의 실행기도 같은 세 갈래로 끝납니다. 다른 것은 이벤트를 내보내는 손잡이입니다.

이벤트를 내는 법되묻기견적

TS SDK이벤트 버스에 싣는다up.status(…INPUT_REQUIRED, ask)up.artifact(…) → up.status(…COMPLETED)

SDK 는 이벤트로 저장소를 고친다 — SDK 판에서는 실행기가 낸 이벤트를 요청 처리기가 받아 저장된 Task 에 반영합니다. 맨손은 거꾸로, 저장소를 먼저 고치고 이벤트는 그 결과로 받습니다. (up 은 파이썬에서는 SDK 의 TaskUpdater, TS·Go 에서는 그 몫을 하는 우리 공용 코드의 Updater 입니다. 각 SDK 의 실행기·이벤트 큐는 7~9부에서 엽니다.)

메시지 검사 — 필수 넷과 Part 의 oneof, 틀리면 어느 필드인지 알린다

§5.7 의 필수 필드(messageId·role·parts)와, Part 에 내용 키가 꼭 하나만 있어야 한다는 규칙(4부)을 봅니다. 그리고 작업을 찾는 find 입니다.

  • 사용자 메시지만 — 클라이언트가 보내는 메시지의 role 은 ROLE_USER 입니다. 비었거나 ROLE_AGENT 면 message.role 을 짚어 -32602.
  • find — 문자열이 아닌 id 도 "없는 작업" 으로 답합니다. §3.4.2: "Agents MUST return a TaskNotFoundError if the provided taskId does not correspond to an existing task".

begin — taskId 가 없으면 새 작업, 있으면 문 셋을 지나 WORKING 으로

두 Send 메서드가 똑같이 부르는 앞부분입니다. 이어 말하기의 규칙이 모두 여기 모여 있습니다.

문걸리면근거

contextId 가 작업의 것과 다르다-32602 message.contextId§3.4.3 "MUST reject messages containing mismatching contextId and taskId"

  • WORKING 으로 먼저, 메시지는 그다음 — 그래야 지난 물음이 이력에 먼저 내려가고 답이 그 뒤에 붙습니다(3장).

막는 호출 — 다 하고 나서 Task 하나를 {"task": …} 로 감싼다

SendMessage 의 처리 함수는 다섯 줄입니다. 업무가 기다릴 것이 없으니(5부의 "끝나거나 멈출 때까지") 부르고 돌아오면 끝입니다.

  • historyLength 를 먼저 본다 — 틀린 값이면 작업을 만들기 전에 -32602 로 돌려보냅니다. 거꾸로 하면 오류로 답하고도 저장소에는 작업이 하나 남습니다.
  • 결과는 {"task": …} — SendMessageResponse 는 task 와 message 가운데 하나를 고르는 oneof 이고, 이 서버는 늘 task 쪽입니다(4부).
  • returnImmediately 는 읽지 않습니다 — 기다릴 일이 없어 받자마자 끝난 Task 를 줄 수 있으니까요.

TypeScript — 같은 begin, 빈 문자열도 "없음"

구조는 파이썬과 한 줄씩 짝이 맞습니다.

  • !msg.taskId·msg.contextId || task.contextId — "" 를 빠진 것과 같게 칩니다. 파이썬의 or·not 과 같은 판정입니다.
  • params.configuration ?? {} — configuration 이 없거나 null 이면 빈 객체로 읽습니다.

Go — 메시지는 값으로 받고, 오류는 줄마다 확인한다

Go 의 begin 은 이미 풀어 둔 bs.Message 를 값으로 받습니다. 풀고 검사하는 일은 readSend(check 구역)가 먼저 합니다.

  • 빈 문자열 = 없음 — 구조체 필드는 키가 없으면 "" 입니다. omitempty 와 같은 이치로, Go 에서는 "없음" 과 "빈 값" 을 가르지 못하고 가를 필요도 없습니다.
  • bs.Move(t, bs.Working) 의 오류를 버리는 까닭 — 바로 위에서 CanMove 로 같은 것을 물었기 때문입니다.

Go 의 막는 호출 — historyLength 는 *int 로 "없음" 과 0 을 가른다

파이썬의 다섯 줄이 Go 에서는 오류 확인 넷을 더해 스무 줄 남짓입니다.

  • sendParams(check 구역) — Configuration.HistoryLength *int. 키가 없으면 nil, 0 이면 0 을 가리키는 포인터입니다. 5부에서 본 Go SDK 의 HistoryLength 와 같은 수입니다.
  • 결과는 맵 — map[string]any{"task": …}. 키가 하나라 차례 걱정이 없습니다.

일곱 번 두드린다 — 새 작업, 이어 말하기, 그리고 begin 의 세 문

시험 쪽(turns.py)은 urllib 로 SendMessage 만 보냅니다. 세 맨손 서버 앞에 탭을 하나씩 두고 같은 프로그램을 차례로 돌렸습니다.

  • ②·③ 은 ① 의 taskId·contextId 로, ⑤ 는 ④ 의 작업에 ① 의 맥락을 섞어서, ⑥ 은 taskId 만 달아 보냅니다.
  • send·show(rpc 구역)는 봉투를 싸고, 답을 "상태와 에이전트의 말" 또는 "code 와 이름" 한 줄로 줄입니다.

세 서버의 일곱 줄이 같다

파이썬 서버(탭 너머)의 결과입니다. TS·Go 서버의 일곱 줄도 글자까지 같았습니다.

  • ⑥ 은 "2026-11-06 1박 30명" 한 마디로 빠진 셋을 다 채워 곧장 COMPLETED — 날짜를 바꾸니 춘천 호수 펜션촌이 가장 쌉니다.
  • 서버 기록(Go)에 오류 셋은 없습니다 — begin 에서 걸린 요청은 업무까지 가지 않습니다.

와이어 — 이어 말하기의 답에 이력이 물음 → 답 차례로

② 의 주고받음에서 id·상태·이력의 role 과 글만 골랐습니다.

이력 셋 — ① 의 사용자 메시지, 에이전트의 물음(ROLE_AGENT, "인원은 몇 명입니까?"), 그리고 방금 보낸 "30명". begin 이 WORKING 으로 옮기며 물음을 내리고(3장) 그 뒤에 답을 붙였기 때문입니다. 물음이 내려가 status 에는 이제 message 가 없습니다.

와이어 — 세 문의 답에는 무엇이 걸렸는지가 실린다

③(끝난 작업)·⑤(어긋난 맥락)·⑦(없는 작업)의 답에서 code 와 data 만 골랐습니다.

  • ③ 의 "taskId" 는 둘 — 요청 메시지의 것과, 답의 ErrorInfo metadata.taskId. ⑦ 은 물어본 "nope" 를 그대로 돌려줍니다(2장).

GetTask — 찾고, 이력을 잘라 뜬다

historyLength 의 세 경우(§3.2.4: 없음·0·N)를 실제로 가르는 곳은 저장소의 view 입니다. 처리 함수는 값을 검사해 넘기기만 합니다.

  • 없으면 전부 — §3.2.4 는 "server returns its default amount of history" 라고 서버에 맡깁니다. 이 서버의 기본은 전부입니다.
  • 0 이면 키째로 뺀다 — "the history field SHOULD be omitted". 빈 목록은 if hist: 에서 걸러집니다.
  • type(raw) is not int — isinstance 로 물으면 True(bool 은 int 의 하위 클래스)도 통과합니다.

TypeScript 는 Number.isInteger, Go 는 -1 을 "전부" 의 표시로

값 검사와 자르기의 손잡이만 다릅니다.

  • TS — slice(-n) 은 n 이 0 이면 전부를 주므로, view 는 0 을 따로 빈 목록으로 다룹니다.
  • Go — length 가 nil 을 -1 로 바꿔 넘기고, View(t, n) 은 n < 0 이면 자르지 않습니다(3장의 복사본 뜨기와 같은 함수).

historyLength 여섯 가지 — 세 서버의 답이 같다

시험 쪽(get_cancel.py)은 견적까지 끝낸 작업 하나(이력 셋)를 여섯 가지로 묻습니다.

  • 1 은 가장 최근 하나(답 "30명"), 2 는 물음과 답, 5 는 있는 만큼(셋) — 5부의 SDK 서버 셋과 같은 자르기입니다.
  • 음수는 셋 다 -32602 — SDK 서버는 파이썬만 그랬고 TS·Go 는 0 처럼 다뤘습니다(5부). 스펙은 음수를 말하지 않으니, 맨손 서버는 "틀린 인자" 쪽을 골랐습니다.

와이어 — 0 이면 history 키가 없고, 1 이면 마지막 하나

historyLength 0 과 1 의 주고받음에서 요청의 값과 답의 이력만 골랐습니다.

GetTask 의 답은 Task 그 자체 — result 바로 아래가 id 입니다. SendMessage 처럼 {"task": …} 로 감싸지 않는 것은 SDK 서버도 같았습니다(5부).

CancelTask — 이미 CANCELED 면 그대로, 갈 수 없으면 -32002

취소는 상태 하나를 옮기는 일이라 짧습니다. 고민은 "두 번째 취소에 무엇을 답하나" 하나입니다.

  • 멈춰 있는 작업만 취소된다 — 숙소 일은 요청 안에서 끝나므로, 취소할 수 있는 때는 INPUT_REQUIRED 로 기다리는 동안뿐입니다. 진행 중인 일을 멈추는 취소는 11부의 교통 에이전트가 보여 줍니다.
  • 두 번째 취소 — §3.3.1 "Cancel Task operations are idempotent" 를 따라 같은 Task 를 줍니다. §3.1.5 는 "already … canceled" 를 TaskNotCancelableError 의 보기로 들어, 스펙 안에서 두 문장이 부딪칩니다(5부).
  • TS(cancelTask)·Go(cancelTask)도 같은 모양입니다 — Go 는 View(t, -1) 로 전부를 뜹니다.

취소 다섯 번 — 기다리는 작업, 한 번 더, 그 뒤의 말, 끝난 작업, 없는 작업

  • "두 답이 같다: True" — 두 번째 취소는 상태도, 시각도 바꾸지 않았습니다. move 를 부르지 않았으니까요.
  • 이력이 USER AGENT — CANCELED 로 옮길 때 기다리던 물음이 이력으로 내려갔습니다. 취소된 작업에 말을 걸면 끝난 작업이라 -32004 입니다.

와이어 — 두 번째 취소의 답과 끝난 작업의 -32002

두 번째 CancelTask 와 COMPLETED 작업의 CancelTask 에서 메서드·상태·오류만 골랐습니다.

4장 퀴즈

Q. INPUT_REQUIRED 로 기다리는 작업에 taskId 는 맞게, contextId 는 다른 작업의 것으로 달아 "1박" 이라고 보냈습니다. 맨손 서버는 무엇으로 답하고, 그 작업의 상태는 어떻게 됩니까?

A. -32602 Invalid parameters 에 BadRequest(message.contextId, "작업의 contextId 와 다릅니다")로 답합니다 — ⑤ 줄과 와이어. begin 은 맥락 검사에서 멈추므로 WORKING 으로 옮기지도, 메시지를 이력에 붙이지도 않습니다. 작업은 INPUT_REQUIRED 그대로였고, 그래서 이어진 ⑥ 이 같은 작업을 COMPLETED 로 끝낼 수 있었습니다.

5장

SendStreamingMessage — SSE 를 손으로

스트림 하나의 모양 → 첫 이벤트는 일하기 전의 Task → 이어 말하기도 Task 부터 → 와이어 → 파이썬: HTTP/1.0 과 닫힘 → TypeScript: res.write → Go: Flusher → 날 바이트로 보기 → 세 서버의 프레이밍 → 시험 쪽 → 네 번 열어 보기 → 언제 닫나 → 첫 이벤트 전의 오류 → 세 언어 비교

스트림은 JSON-RPC 응답 여러 개 — 모두 요청의 id 를 단다

SSE 의 바이트 규칙은 2부에서 봤습니다. A2A 의 JSON-RPC 바인딩은 그 data 하나에 응답 하나를 싣고, result 에 StreamResponse 를 넣습니다(§9.4.2).

보낸 것이 서버의 스트림
새 작업, 정보가 모자람task(SUBMITTED) → statusUpdate(INPUT_REQUIRED)
이어 말하기, 정보가 다 참task(WORKING) → artifactUpdate → statusUpdate(COMPLETED)
새 작업, 숙소가 없음task(SUBMITTED) → statusUpdate(REJECTED)
begin 에서 걸림스트림이 아니다 — JSON 응답 하나(뒤에서)
처리 함수는 목록만 만든다 — send_streaming_message 는 StreamResponse 의 목록을 돌려주고(1장의 stream 구역), dispatch 가 각각을 같은 id 의 응답으로 쌉니다(2장). SSE 로 쓰는 것은 HTTP 쪽의 몫입니다. 스트림의 뜻(청크·재구독)은 10부가 다룹니다.

첫 이벤트는 일하기 전에 떠 둔 Task — 다 쓴 뒤에도 SUBMITTED 그대로

숙소 일은 기다릴 것이 없어, 맨손 서버는 이벤트를 다 만든 뒤에 씁니다. 그때 저장소의 작업은 이미 끝나 있습니다. 그런데도 첫 이벤트는 처음 모습을 보여야 합니다.

  • 떠 두기 — first = {"task": view(task)} 를 업무보다 먼저 부릅니다. view 는 목록을 새로 담고, move 는 status 를 고치지 않고 갈아 끼웁니다(3장). 그래서 뒤의 REJECTED 가 앞서 뜬 모습에 스며들지 않습니다.
  • 떠 두지 않고 마지막에 view 했다면 첫 이벤트부터 REJECTED 였을 것이고, "Task 다음에 상태 변화" 라는 이야기가 거꾸로 됩니다.

이어 말하기의 스트림도 Task 부터 — 상태는 WORKING, 이력엔 물음과 답

§3.1.2: Task 스트림은 "MUST begin with the Task object". 이어 말하기라고 예외가 없습니다. 둘째 스트림의 와이어에서 이벤트 종류·상태·이력의 role 만 골랐습니다.

  • 첫 이벤트의 이력은 USER·AGENT·USER — begin 이 WORKING 으로 옮기며 물음을 내리고 "30명" 을 붙인 뒤에 떴습니다.
  • SDK 판과 견주면 — 파이썬 SDK 판 완성 에이전트는 이어 말하기에서 Task 를 다시 싣지 않습니다. 실으면 SDK 가 사용자의 답을 이력에서 버리기 때문입니다(5부, 까닭). TS·Go 판은 맨손과 같이 WORKING Task 로 시작합니다(5부).

와이어 — data 하나에 응답 하나, id 는 모두 요청의 1

첫 스트림(새 작업)의 답입니다. 머리와 이벤트 경계(data:), id, 종류, 상태, 글만 골랐습니다.

JSON-RPC 의 "응답 하나" 규칙을 어긴 것이 아니다 — 요청 하나에 응답이 둘이지만, §9.4.2 가 SSE 위에서 그렇게 하라고 정했습니다(2부). 클라이언트는 같은 id 로 모두 한 요청의 것임을 압니다.

파이썬 — HTTP/1.0, 길이 없음, 연결이 닫히는 곳이 스트림의 끝

http 구역(2장)의 SSE 쪽은 머리에 Content-Length 를 달지 않고 이벤트마다 data: …\n\n 을 씁니다. 그 응답을 소켓에서 날 바이트로 받아 보면 이렇습니다.

  • 상태 줄이 HTTP/1.0 — BaseHTTPRequestHandler.protocol_version 의 기본값이 "HTTP/1.0" 입니다. 1.0 에는 청크가 없으니 길이 없는 본문의 끝은 연결을 닫는 것으로만 알립니다.
  • flush() 는 할 일이 없다 — StreamRequestHandler.wbufsize = 0 이라 wfile 은 _SocketWriter 이고, 그 설명이 "Does not hold data in a buffer, avoiding any need to call flush()" 입니다(설치된 socketserver.py). write 가 곧 sendall 입니다.

TypeScript — res.write 한 번이 청크 하나, res.end 가 끝

Node 의 SSE 쪽은 머리를 쓰고, 이벤트마다 res.write, 끝에 res.end() 입니다(2부와 같은 손잡이). 처리 함수(stream 구역)는 파이썬과 같습니다.

  • 길이를 모르면 청크로 — HTTP/1.1 응답에 Content-Length 가 없으니 Node 가 Transfer-Encoding: chunked 를 붙입니다(날 바이트).
  • req.setEncoding("utf8") — 요청 본문의 조각을 바이트(Buffer)로 받아 하나씩 문자열로 바꾸면, 조각 경계에 걸린 한글 한 글자가 깨집니다. 문자열로 받게 해 두면 Node 가 경계를 이어 붙여 읽습니다. (이 장을 쓰며 찾은 결함입니다 — 큰 한글 본문에서 U+FFFD 가 생겼습니다.)

Go — 이벤트마다 Flush, 처리 함수가 돌아가면 끝

Go 의 ResponseWriter 는 버퍼를 둡니다(2부). 이벤트를 쓸 때마다 http.Flusher 로 밀어냅니다.

  • w.(http.Flusher) — 값 하나짜리 타입 단언이라, 응답을 감싼 미들웨어가 Flush 를 숨기면 panic 입니다. 맨손 서버는 net/http 의 응답을 그대로 받아 단언만 했습니다. Go SDK 는 확인부터 합니다 — 설치본 internal/sse/sse.go 의 NewWriter 가 flusher, ok := w.(http.Flusher) 로 묻고, 안 되면 "streaming not supported" 오류를 돌려줍니다.
  • 자물쇠는 이미 놓였다 — 이벤트 목록은 call 이 잠근 동안 만들어졌고, 쓰기는 놓은 뒤입니다(3장).

날 바이트로 보기 — 소켓을 열고, 닫힐 때까지 읽고, 청크를 손으로 푼다

와이어 탭은 HTTP 의 운반용 머리(Transfer-Encoding 따위)를 적지 않습니다(0부). 그래서 시험 쪽(frames.py)이 소켓으로 요청을 쓰고, Connection: close 로 "다 보내면 닫아 달라" 고 한 뒤 받은 바이트를 풉니다.

청크 — 16진수 길이 한 줄, 그 길이만큼의 바이트, CRLF. 길이 0 인 청크가 본문의 끝입니다(RFC 9112 §7.1). 각 청크·이벤트에 무엇이 실렸는지는 result 의 첫 키로 찍습니다.

TS·Go 는 HTTP/1.1 청크, 이벤트 하나가 청크 하나

같은 요청(30명, 2026-10-30, 1박)을 TS·Go 서버에 보냈습니다.

  • 청크 경계 = 이벤트 경계 — Node 는 res.write 마다, Go 는 Flush 마다 청크 하나를 냈습니다. 이벤트 사이를 기다리는 서버라면 클라이언트가 이벤트를 그때그때 받는 이유가 이것입니다.
  • 두 서버의 청크 길이가 같다 — 둘 다 빈칸 없이 JSON 을 씁니다. Go 는 봉투의 키 차례(id·jsonrpc·result)가 다를 뿐 글자 수는 같습니다. 파이썬은 ", "·": " 의 빈칸만큼 이벤트마다 14~32바이트 깁니다.

시험 쪽 — Content-Type 을 먼저 보고, 스트림이면 줄을 읽어 자른다

stream_turns.py 는 urllib 으로 SendStreamingMessage 를 보내고, 받은 응답 하나마다 한 줄을 찍습니다.

  • Content-Type 이 갈림길 — text/event-stream 이 아니면 JSON 하나로 읽습니다. 맨손 서버는 begin 에서 걸린 오류를 그렇게 보냅니다.
  • 읽는 규칙은 2부의 파이썬 클라이언트와 같습니다. 6장에서 세 언어의 맨손 클라이언트로 다시 짭니다.

네 번 열었다 — 세 서버의 스트림이 같다

새 작업, 이어 말하기, 끝난 작업에 또, 문 닫은 날(12-31) 입니다. 파이썬 서버(탭 너머)의 결과이고 TS·Go 서버도 글자까지 같았습니다.

응답 수가 곧 이벤트 수 — 2개·3개·1개·2개. ③ 만 application/json 이고, 그 요청은 업무까지 가지 않아 서버 기록에 줄이 없습니다(견적 하나, 되묻기 하나, 거절 하나).

언제 닫나 — 끝난 상태뿐 아니라 INPUT_REQUIRED 에서도

①(INPUT_REQUIRED)·②(COMPLETED)·④(REJECTED) 모두 마지막 이벤트 뒤에 스트림이 닫혔습니다. 업무가 늘 종료 상태나 중단 상태로 끝나고, 이벤트 목록이 거기서 끝나기 때문입니다.

스펙의 문장닫는 때
§3.1.2"The stream MUST close when the task reaches a terminal state" — 종료 넷
§11.7"until the task reaches a terminal or interrupted state, at which point the stream closes" — 종료 넷 + 중단 둘
  • INPUT_REQUIRED 에서 닫는 것은 §11.7 쪽 — §3.1.2 는 중단 상태를 말하지 않습니다. 사용자의 답은 새 요청(새 스트림)으로 오니, 열어 둘 까닭이 없습니다.
  • 기다리는 동안 이벤트를 흘려야 하는 에이전트(식사·교통)라면 목록을 다 만든 뒤 쓰는 이 구조로는 안 됩니다 — 이벤트가 생길 때마다 써야 합니다.

첫 이벤트 전의 오류는 JSON 하나로 — 머리를 쓰기 전이라 고를 수 있다

③ 의 와이어입니다. 스트림을 청했지만 답은 application/json 의 JSON-RPC 오류 하나입니다.

  • 왜 가능한가 — 맨손 서버는 처리 함수가 끝까지 돈 뒤에야 머리를 씁니다. begin 이 던지면 dispatch 가 "JSON 응답, 이벤트 없음" 을 돌려주고, HTTP 쪽은 보통 JSON 응답을 씁니다.
  • 스펙은 꼴을 정하지 않았다 — §9.4.2 는 성공한 스트림의 모양만 보입니다. SDK 서버도 갈렸습니다: 파이썬·TS 는 JSON, Go 는 SSE 이벤트 하나로 오류를 실었습니다(3부). 그래서 클라이언트는 Content-Type 으로 가려 읽어야 합니다(시험 쪽).

Q. 끝난 작업에 SendStreamingMessage 로 이어 말하면 맨손 서버는 무엇을 돌려줍니까? 같은 일을 정상으로 이어 말한 스트림의 첫 이벤트는 무엇이었습니까?

A. 스트림이 아니라 Content-Type: application/json 의 JSON-RPC 오류 하나, -32004(UNSUPPORTED_OPERATION)입니다 — ③ 줄과 와이어. begin 이 머리를 쓰기 전에 걸렀기 때문입니다. 정상 이어 말하기(②)의 첫 이벤트는 상태가 TASK_STATE_WORKING 인 task 였습니다(와이어) — §3.1.2 대로 이어 말하기도 Task 로 시작합니다.
