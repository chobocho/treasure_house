블랙박스였던 숙소 에이전트를 SDK 없이 직접 만든다

3~5부는 완성 에이전트를 띄워 놓고 와이어만 읽었습니다. 이 부는 그 상자를 엽니다 — A2A 서버가 "기계적으로" 해야 하는 일을 세 언어의 표준 라이브러리로 하나씩 짭니다. SDK 가 해 주는 일이 무엇인지는 손으로 해 봐야 보입니다.

목표 대본 — 완성 에이전트(SDK)는 이렇게 답한다

총무팀 CLI(ask, 5부에서 쓴 파이썬 SDK 클라이언트)를 완성 숙소 에이전트에 붙였습니다. 날짜·박 수는 DataPart 로 주고, 인원은 되물음에 글로 답합니다. 끝으로 막는 호출로 문 닫은 날을 묻습니다.

맨손 서버의 합격선 — 같은 CLI 를 붙였을 때 이 줄들이 그대로 나오면, 맨손 서버가 SDK 클라이언트와 말이 통한다는 첫 증거입니다. 세 언어의 클라이언트 × 세 서버를 다 맞춰 보는 것은 7장입니다.

카드는 완성 에이전트와 같은 dict 한 장

3부의 맨손 카드는 필수 필드만 적었습니다. 이번에는 SDK 판 숙소 에이전트의 카드와 같은 아홉 키를 적습니다 — SDK 클라이언트가 같은 인터페이스를 고르고, streaming: true 를 보고 스트림으로 부르게 하려고요.

url 은 --url 로 — 안 주면 붙는 주소(http://127.0.0.1:P/)를 적습니다. 바깥 주소를 적어야 하는 까닭은 3부에서 봤습니다.

네 카드의 뜻은 같다 — 바이트까지 같은 것은 TS 하나

완성 에이전트와 맨손 셋을 같은 --url 로 띄우고, 카드를 받아 첫 장과 견줬습니다. 뜻은 JSON 을 읽은 객체로, 바이트는 받은 그대로 비교합니다.

  • 파이썬 맨손 — 키 차례는 같지만 json.dumps 의 기본값이 쉼표·쌍점 뒤에 빈칸을 넣습니다(2부).
  • Go 맨손 — 카드를 맵으로 만들었고, encoding/json 은 맵의 키를 알파벳 차례로 씁니다(2부). 그래서 첫 키가 capabilities 입니다.
  • TS 맨손 — JSON.stringify 는 빈칸 없이, 넣은 차례대로 씁니다. 그 바이트가 SDK 판 카드와 같았습니다.

맨손 서버 셋에 같은 대본 — 한 줄만 다르다

같은 CLI 를 맨손 서버 셋에 차례로 붙였습니다. 파이썬 서버는 전부, TS·Go 서버는 상태 줄만 골라 실었습니다.

  • 견적의 숫자·이름·되물음의 글이 목표 대본과 같습니다. 카드의 streaming: true 를 보고 CLI 가 스트림으로 불렀으니 SSE 응답도 SDK 클라이언트가 읽어 냈습니다.
  • 다른 줄은 > 30명 다음의 task WORKING 하나입니다 — 다음 장에서 봅니다.

task WORKING — 맨손 서버는 이어 말하기의 스트림도 Task 로 시작한다

§3.1.2: "the stream MUST begin with the Task object". 5부에서 SDK 판 파이썬 서버만 이어 말하기에서 이 규칙을 못 지켰고, 그 까닭은 SDK 의 사정이었습니다(5부). 맨손 서버에는 애초에 SDK 가 없으니 스펙대로 갑니다.

  • 첫 이벤트는 상태를 WORKING 으로 옮긴 지금의 Task 입니다 — TS·Go 완성 에이전트와 같은 선택(5부)이라, 맨손 서버의 대본은 TS·Go 완성 에이전트의 대본과 같습니다.
  • 서버 쪽 기록 줄은 완성 에이전트와 같습니다 — 아래는 완성(파이썬)과 맨손(Go).

1장 퀴즈

Q. 같은 CLI 로 "30명" 이라고 이어 말했더니 맨손 서버에서는 task WORKING 줄이 하나 더 찍혔습니다. 이 줄은 무엇이고, 완성 에이전트(파이썬 SDK)에서는 왜 안 찍혔습니까?

A. 둘째 스트림의 첫 이벤트로 온 Task 입니다 — §3.1.2 는 Task 스트림이 Task 로 시작해야 한다고 정하고, 맨손 서버는 상태를 WORKING 으로 옮긴 Task 를 먼저 보냅니다(첫 실행, stream 구역). 파이썬 SDK 1.2.2 는 이어 말하기에서 Task 를 다시 실으면 사용자의 답을 이력에서 버리므로, 완성 에이전트는 첫 마디에만 Task 를 싣습니다(5부).

2장

라우팅·JSON-RPC 디스패치·오류 코드

요청 하나가 지나는 길 — 문마다 걸리면 돌려줄 오류가 정해져 있다

바깥 문 — 경로 둘만 받는다, 나머지는 404

파이썬 http.server 의 처리기입니다. 카드는 GET, JSON-RPC 는 POST / 하나로 들어옵니다. 본문은 dispatch 에 넘기고, 돌아온 것이 JSON 하나면 그대로, 이벤트 목록이면 SSE 로 씁니다(SSE 는 5장).

  • protocol_version 을 바꾸지 않았으니 응답은 HTTP/1.0 — 답 하나를 쓰면 연결을 닫습니다. 스트림의 끝을 연결의 끝으로 알리기에 편합니다.
  • log_message 를 비워 요청마다 찍히는 접속 기록을 껐습니다. 서버 기록에는 업무 줄([숙소] …)만 남습니다.

이 서버가 내는 오류는 아홉 — JSON-RPC 다섯, A2A 넷

문구는 JSON-RPC 쪽은 §9.5 의 "Standard Message" 를 그대로 썼습니다. A2A 오류의 문구는 스펙이 정하지 않아(§9.5 의 보기에 "Task not found" 하나) 짧게 지었습니다.

오류는 예외 하나 — 어디서 던져도 dispatch 가 봉투에 싼다

처리 함수는 몇 겹 아래에서든 RpcError 를 던지기만 합니다. 받아서 {"jsonrpc", "id", "error"} 로 싸는 곳은 dispatch 한 곳입니다.

data 는 있을 때만 — §9.5 는 error.data 를 "array of objects, each containing a @type key" 로 정합니다. 표준 다섯 가운데 -32602 만 어느 필드가 틀렸는지를 싣고, 나머지는 code·message 둘입니다.

A2A 오류는 data 에 ErrorInfo 를 — reason·domain·metadata

§9.5 는 google.rpc.ErrorInfo 를 쓰라고 권하고(SHOULD), §10.6 은 reason 을 "The A2A error type in UPPER_SNAKE_CASE without the "Error" suffix", domain 을 "a2a-protocol.org" 로 정합니다. 틀린 인자는 §9.5 의 보기처럼 google.rpc.BadRequest 로 싣습니다.

metadata 에 taskId — §9.5 의 보기는 metadata 에 taskId 를 담습니다. 5부에서 본 세 SDK 는 그렇게 하지 않았는데, 맨손 서버는 보기대로 합니다. 판 오류에는 읽은 판을 담습니다.

판 헤더 — 비어 있으면 0.3, 1.0 이 아니면 -32009

§3.6.2: "If the version is not supported by the interface, agents MUST return a VersionNotSupportedError." 그리고 "Agents MUST interpret empty value as 0.3 version." 패치 번호는 §3.6 이 "MUST not be considered" 라고 합니다.

  • 이 서버의 카드는 protocolVersion: "1.0" 인터페이스 하나뿐이라, 받는 판도 1.0 하나입니다.
  • 판을 메서드보다 먼저 본다 — v0.3 의 메서드 이름은 message/send·tasks/get 이었습니다(스펙 저장소의 whats-new-v1.md). 판을 알아야 메서드 이름을 어떻게 읽을지 정해집니다.
  • 판이 여럿인 서버와 협상은 14부의 몫입니다.

봉투 검사 — 요청 객체 하나, id 는 꼭

dispatch 는 JSON 을 읽고 봉투만 봅니다. 봉투가 틀리면 id 를 믿을 수 없으니 응답의 id 는 null 입니다(2부).

  • 배치와 알림은 받지 않는다 — A2A 스펙은 배치를 말하지 않고(2부), A2A 의 메서드는 모두 답을 돌려줍니다. 그래서 배열도, id 없는 요청도 -32600 입니다.
  • 버그는 -32603 — 예상한 예외(전이 표 위반 IllegalMove, 이상한 입력값의 ValueError 따위)는 stderr 에 적고 Internal error 로 답합니다.

판 → 메서드 → params — 그다음에야 처리 함수

call 이 문 셋을 차례로 검사합니다. 메서드 표는 이름 하나에 처리 함수와 "답이 SSE 인가" 를 짝지은 dict 입니다.

메서드 표가 곧 이 서버의 능력 목록 — 이름은 §9.4 의 PascalCase 그대로입니다. 표에 없는 ListTasks 를 부르면 -32601 이고, 메서드를 하나 더하려면 함수 하나와 표의 한 줄이면 됩니다.

TypeScript — 같은 길, 메서드 표에는 Object.hasOwn

구조는 파이썬과 같습니다(dispatch 가 봉투, call 이 판·메서드·인자). 다른 점만 봅니다.

  • Object.hasOwn — 메서드 표는 평범한 객체라 METHODS["toString"] 처럼 물려받은 이름도 값을 줍니다. 자기 키인지 먼저 물어야 "toString" 이 -32601 이 됩니다.
  • 헤더 이름은 소문자 — Node 는 받은 헤더 이름을 소문자로 바꿔 둡니다. version 구역은 headers["a2a-version"] 를 읽습니다.
  • 오류는 throw, 받는 쪽은 e instanceof RpcError 로 가릅니다. 그 밖의 예외는 모두 -32603 입니다.

Go — id 는 받은 바이트 그대로, 오류는 돌려주는 값

Go 판의 dispatch 입니다. 판·메서드·인자 검사(call)는 3장에서 잠금과 함께 봅니다.

  • json.RawMessage — id 를 풀지 않고 바이트로 들고 있다가 응답에 그대로 넣습니다. 1 은 1 로, "a" 는 "a" 로 돌아갑니다(2부와 같은 수).
  • 오류는 값 — 처리 함수는 (any, error) 를 돌려주고, *rpcError 가 error 를 구현합니다. 예외가 없으니 "버그" 는 *rpcError 가 아닌 error 로 가립니다.

세 언어 비교 — 같은 문, 다른 자물쇠

문의 차례와 오류 코드는 셋이 같습니다. 다른 것은 각 언어가 "틀렸다" 를 알아채고 전하는 방법입니다.

틀린 요청 열 가지 — SDK 를 거치지 않은 바이트로

시험 쪽(rpc_probe.py)은 urllib 로 본문을 그대로 보내고, 답의 오류만 한 줄씩 찍습니다. 세 맨손 서버에 같은 열 가지를 보냅니다(파이썬 서버 앞에는 와이어 탭).

세 서버의 답이 줄마다 같다

한 줄 = HTTP 상태, error.code, error.message, ErrorInfo 의 reason 또는 BadRequest 의 틀린 필드, 그리고 어느 경우인지.

  • 판이 먼저 — "판 0.3 + 옛 이름" 은 -32601 이 아니라 -32009 입니다. "v1.0 에 옛 이름" 에서야 -32601 이 나옵니다.
  • 판 1.0.1 은 통과했습니다 — 패치 번호를 보지 않으니 없는 작업까지 가서 -32001.

판 헤더가 없는 요청 — 서버는 0.3 으로 읽고 -32009

탭이 본 첫 주고받음입니다. 요청 헤더에 A2A-Version 줄이 없습니다.

metadata.version 이 "0.3" — 빈 값을 0.3 으로 읽었다는 기록입니다. id 는 받은 1 그대로입니다 — 봉투는 맞았으니까요.

같은 옛 이름 message/send — 판에 따라 -32009 와 -32601

셋째(판 0.3)와 여덟째(판 1.0) 주고받음에서 판·메서드·답의 code 만 골랐습니다.

판을 모르면 이름을 해석할 수 없다 — 0.3 클라이언트에게 "그런 메서드 없다"(-32601)는 틀린 진단입니다. "그 판은 안 쓴다"(-32009)가 클라이언트가 고칠 수 있는 답입니다.

봉투가 틀리면 id 는 null — 깨진 JSON, 배치, 알림

다섯째(깨진 JSON)는 통째로, 여섯째(배치)·일곱째(알림)는 요청 줄과 답만 골랐습니다.

배치의 답이 배열이 아니다 — 배열을 요청 객체로 받지 않았으니 단건 오류 하나로 답했습니다. 알림(id 없음)에도 답했습니다 — JSON-RPC 서버라면 알림에 답하지 않지만(2부), 이 서버는 알림을 "틀린 요청" 으로 정했습니다.

A2A 오류엔 ErrorInfo, 틀린 인자엔 BadRequest

넷째(없는 작업)와 열째(파트가 없는 메시지)의 답만 골랐습니다.

  • -32001 의 data[0] — @type 이 …google.rpc.ErrorInfo, reason 이 TASK_NOT_FOUND, metadata.taskId 가 물어본 "nope".
  • -32602 의 data[0] — fieldViolations 에 message.parts 와 그 까닭. §3.3.2 "Servers SHOULD specify which parameter(s) failed validation and why" 를 따른 것입니다.

2장 퀴즈

Q. A2A-Version 헤더 없이 {"jsonrpc":"2.0","id":1,"method":"message/send",…} 를 맨손 서버에 보내면 어떤 code 가 옵니까? 헤더를 1.0 으로 달면요?

A. 헤더가 없으면 0.3 으로 읽으므로 메서드를 보기도 전에 -32009(Version not supported)입니다 — "판 헤더 없음" 과 "판 0.3 + 옛 이름" 줄이 둘 다 -32009 였습니다(세 서버의 답). 1.0 을 달면 판 문을 지나 메서드 표에서 걸려 -32601(Method not found)입니다(와이어).

Task 저장소와 상태 전이

저장소가 할 일 → 파이썬 저장소 → id 와 시각 ×3 → 상태를 옮기며 물음을 이력으로 → 전이 표를 정한다 → 표의 코드 → 표가 답하는 세 질문 → 시험 → TypeScript → Go → 동시성 ×3 → 세 언어 비교

저장소는 taskId 로 찾는 맵 하나 — 연산은 다섯

작업은 프로세스의 메모리에만 삽니다. 서버를 다시 띄우면 사라집니다 — 디스크에 두는 저장소는 17부에서 만듭니다.

연산하는 일누가 부르나
create첫 메시지로 Task 를 짓는다 — id·contextId, 상태 SUBMITTED, 이력에 그 메시지새 작업의 SendMessage
gettaskId → Task, 없으면 없음이어 말하기·GetTask·CancelTask

파이썬 — dict 하나, Task 도 dict

Task 는 와이어의 JSON 모양 그대로 dict 로 둡니다. 내보낼 때 다시 짜 맞출 필요가 없습니다.

  • contextId — 클라이언트가 정해 온 맥락은 그대로 씁니다. 4부에서 세 SDK 서버가 그렇게 했습니다.
  • ids | msg | ids — 첫 ids 가 키의 차례(messageId·contextId·taskId)를 정하고, 끝의 ids 가 값을 덮습니다. 클라이언트가 보낸 taskId·contextId 가 무엇이었든 저장소의 값이 남습니다.

id 는 UUID 판 4, 시각은 §5.6.1 의 꼴 — 세 언어

taskId 는 "server-generated" 이고 "MUST generate a unique taskId"(§3.4.2) 입니다. 무작위 128비트 중 122비트를 쓰는 UUID 판 4 로 짓습니다. 시각은 §5.6.1 의 "YYYY-MM-DDTHH:mm:ss.sssZ" 입니다.

캡처에서는 <id1>·<시각> — 실행마다 바뀌는 값이라 캡처 도구가 바꿔 적습니다(0부). 맨손 서버도 SDK 서버처럼 UUID 를 쓰므로 같은 규칙으로 읽힙니다.

상태를 옮길 때 지난 물음을 이력으로 내린다

move 는 상태를 바꾸는 유일한 길입니다. 먼저 전이 표를 묻고, 지금 status.message(에이전트의 물음)가 있으면 이력 끝에 붙인 뒤 새 상태로 갈아 끼웁니다.

  • 물음을 옮기는 때 — 다음 상태가 올 때. 파이썬·Go SDK 와 같은 쪽입니다(TS SDK 는 받는 즉시 이력에도, 5부). 이어 말하기는 WORKING 으로 먼저 옮긴 뒤 사용자 메시지를 붙이므로 이력이 물음 → 답 차례가 됩니다(시험은 뒤에서).
  • 갈아 끼운다 — 지난 status dict 를 고치지 않고 새 dict 를 넣습니다. 앞서 돌려준 이벤트가 붙들고 있는 상태가 뒤에서 바뀌지 않습니다.

어떤 전이를 허락할지는 우리가 정한다 — SDK 는 다 받았다

스펙에는 전이 표가 없고(5부), 세 SDK 는 WORKING → SUBMITTED 도 그대로 실었습니다(5부). 맨손 서버는 표를 하나 정해 저장소에 박아 둡니다.

전이 표는 dict 하나 — 종료 상태는 키가 없다

"갈 곳이 없다" 를 따로 적지 않습니다. 종료 넷을 표의 키에서 빼 두면 ALLOWED.get(src, ()) 가 빈 튜플을 주고, 어디로도 못 갑니다.

위반은 버그다 — 표를 어기는 것은 요청이 아니라 우리 업무 코드입니다. 그래서 IllegalMove 는 RpcError 가 아니고, 새어 나가면 dispatch 가 -32603 으로 바꿉니다(2장).

표 하나가 세 질문에 답한다

서버의 세 곳이 can_move 를 묻습니다. 셋 다 "그 상태에서 나갈 길이 있나" 이고, 답에 따라 다른 오류가 나갑니다.

시험 — 작업 하나를 이리저리 옮겨 본다

저장소만 가져다 쓰는 작은 프로그램입니다. 되묻고, 답 전에 끝내려 하고, 답을 받고, 뒤로 가려 하고, 끝낸 뒤 다시 움직이려 합니다.

  • INPUT_REQUIRED → COMPLETED, WORKING → SUBMITTED, COMPLETED → WORKING·CANCELED 가 거부됐습니다.
  • WORKING 으로 옮기자 이력이 USER AGENT 가 됐고(물음이 내려옴), 답을 붙이자 USER AGENT USER 입니다.

TypeScript — Map 과 펼침(...)으로 키의 차례를 맞춘다

구조는 같고, Task 의 모양을 타입으로 적었습니다(types 구역). 파이썬과 다른 곳만 봅니다.

  • Map — 평범한 객체를 맵으로 쓰면 "__proto__" 같은 키가 말썽입니다. taskId 는 클라이언트가 보내 오는 글자이니 Map 이 안전합니다.
  • 펼침의 차례 — 객체 리터럴에서 같은 키가 다시 나오면 값만 바뀌고 자리는 처음 그대로입니다. 파이썬의 ids | msg | ids 와 같은 결과입니다.
  • msg.contextId || newId() — 빈 문자열도 "없음" 으로 칩니다.

Go — 구조체와 포인터 맵, 그리고 자물쇠 Mu

Task·Message 는 구조체이고(필드 차례 = 와이어의 키 차례), 저장소는 map[string]*Task 입니다. 파이썬·TS 에 없는 것이 하나 있습니다 — sync.Mutex.

  • 값 복사 — Append 의 msg 는 값으로 넘어온 복사본이라 두 id 를 채워도 부른 쪽의 메시지는 그대로입니다.
  • Mu 는 부르는 쪽이 잡는다 — 저장소 연산 하나하나가 아니라 "요청 하나를 처리하는 동안" 을 잠가야 하기 때문입니다. 다음 장에서 봅니다.

"찾고 → 상태를 보고 → 옮기는" 세 걸음 사이에 다른 요청이 끼면, 같은 작업을 두 번 옮길 수 있습니다. 세 서버가 이것을 막는 방법이 다릅니다.

A. 전이 표에서 INPUT_REQUIRED 가 갈 곳은 WORKING·CANCELED 뿐이라 IllegalMove 로 거부합니다 — 시험의 COMPLETED 거부 — TASK_STATE_INPUT_REQUIRED → TASK_STATE_COMPLETED 줄(시험). 이 예외는 RpcError 가 아니므로 dispatch 가 받아 -32603 Internal error 로 답합니다(2장) — 요청이 아니라 서버 코드가 틀렸다는 뜻입니다.
