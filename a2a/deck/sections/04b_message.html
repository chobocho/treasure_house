파일은 두 길로 간다 — 바이트를 싣거나(raw), 주소를 싣거나(url)

v1.0 에는 "파일 파트" 라는 타입이 따로 없습니다. 2장의 oneof 에서 raw 나 url 을 고르고, 옆에 filename·mediaType 을 붙이면 그것이 파일입니다. 두 길은 성격이 다릅니다.

식사 에이전트는 식단표를 menu.md 파일 파트로 돌려준다

총무팀이 식사 에이전트에 막는 호출로 "1박, 30명, 채식 2명" 을 물었습니다(files 명세, 파이썬 쪽에만 탭). 답은 아티팩트 셋인데, 둘째가 파일입니다.

  • raw 옆에 filename(menu.md)과 mediaType(text/markdown)이 붙었습니다. 받는 쪽은 이 둘로 저장할 이름과 여는 방법을 정합니다.
  • 나머지 두 아티팩트는 식단표(글 파트 셋)와 식사 견적(데이터 파트)입니다. 식단표가 왜 글 파트 셋인지 — 스트림으로 한 줄씩 이어 붙인 청크(append·lastChunk) — 는 10부에서 봅니다.

파이썬 — p.raw 는 이미 bytes 다, 이름과 타입은 옆 필드에

세 언어의 클라이언트가 같은 언어의 식사 에이전트에 같은 것을 묻고, 아티팩트를 돌며 파일 파트를 꺼냅니다. 먼저 파이썬입니다.

  • 와이어의 base64 는 SDK(protobuf 의 JSON 해석기)가 이미 풀었습니다. p.raw 는 bytes 이고, 길이 195 는 파일의 바이트 수입니다.
  • 필드 이름이 proto 쪽 이름입니다 — 와이어의 mediaType 이 파이썬에서는 media_type. 두 이름의 관계는 8장에서 봅니다.

TypeScript — $case 가 "raw" 면 value 는 Buffer 다

TS 는 2장처럼 content?.$case 로 가릅니다. "raw" 로 좁혀지면 value 의 타입이 Buffer 라서 toString("utf-8") 로 바로 글이 됩니다.

빈 문자열이 "없음" — ts-proto 의 Part 는 filename·mediaType 을 늘 string 으로 들고, 와이어에 없으면 "" 입니다. "이름이 없는 파일" 은 p.filename === "" 로 가립니다.

Go — Content 가 a2a.Raw 인지 타입 단언으로 묻는다

Go 는 p.Content.(a2a.Raw) 로 묻고, 맞으면 []byte 를 손에 쥡니다. Filename·MediaType 은 Part 구조체의 필드입니다.

세 에이전트, 같은 파일 — 파이썬·TS·Go 식사 에이전트가 낸 menu.md 가 모두 195바이트, 내용도 한 글자까지 같습니다. 업무 규칙이 골든 벡터를 따르기 때문입니다(0부).

큰 raw 는 서버의 본문 한도에 걸린다 — TS 서버는 100KB 에서 413

0 바이트로 채운 파일 둘(70,000·80,000바이트)을 raw 파트에 실어, 2장의 파트 확인 에이전트 셋에 SDK 없이 보냈습니다(big 명세 — 포트 10454 파이썬, 10455 TS, 10456 Go). 본문이 커서 탭은 세우지 않았습니다.

  • 80,000바이트 파일은 base64 로 106,668글자가 되어 본문이 106,865바이트입니다. TS 서버의 로그에 한도가 적혀 있습니다 — limit: 102400(100KB). TS SDK 의 JSON-RPC 처리기가 express 의 express.json() 을 기본값 그대로 씁니다.
  • 413 은 HTTP 상태일 뿐, JSON-RPC 오류 객체가 없습니다. 클라이언트는 A2A 오류 코드를 받지 못합니다.
  • 파이썬·Go 서버는 두 크기를 다 받았습니다(서버 쪽 SDK 에 한도를 거는 설정이 없음).

url 파트를 받은 쪽은 주소 하나를 받는다 — 가져오기도, 그 위험도 받는 쪽 몫

세 SDK 는 url 파트의 주소를 가져오지 않습니다. 2장의 파트 확인 에이전트가 받은 것은 주소 문자열이었습니다(파이썬·TS·Go 차례).

  • 내용이 필요하면 에이전트가 그 주소로 직접 요청합니다. 그 주소는 받는 쪽에서 닿아야 합니다 — 3부의 카드 url 처럼(3부) "보내는 쪽에서 보이는 주소" 와 "받는 쪽에서 닿는 주소" 는 다를 수 있습니다.
  • 스펙 §14.1.1: "File references within A2A messages MUST be validated to prevent server-side request forgery (SSRF)". 모르는 상대가 보낸 주소를 그대로 가져오면, 상대가 에이전트를 시켜 127.0.0.1 이나 사내망 주소를 대신 두드리게 할 수 있습니다. 푸시 알림의 웹훅 주소도 같은 문제를 갖습니다(11부).
크면 url, 작으면 raw — url 은 본문 한도와 무관하고 이력도 가볍지만, 받는 쪽이 가져와야 하고 주소를 검증해야 합니다. raw 는 받는 쪽이 할 일이 없지만 4/3 로 부풀어 한도에 걸립니다(TS 서버 100KB).

acceptedOutputModes — "이 미디어 타입만 받겠다" 를 요청에 적는다

proto 의 SendMessageConfiguration.accepted_output_modes: "A list of media types the client is prepared to accept for response parts. Agents SHOULD use this to tailor their output." 앞의 클라이언트 셋은 모두 text/markdown 하나만 적었습니다.

와이어에서는 params.configuration.acceptedOutputModes 입니다(파이썬 클라이언트의 요청).

세 서버 모두 걸러 내지 않았다 — JSON 견적까지 그대로 왔다

클라이언트는 text/markdown 만 받겠다고 했지만, 세 식사 에이전트 모두 글 파트와 데이터 파트(JSON 견적)까지 보냈습니다. 세 클라이언트의 첫·둘째·끝 줄입니다.

  • 세 SDK 의 요청 처리기는 이 값을 읽지 않습니다 — 설치본에서 accepted_output_modes·acceptedOutputModes·AcceptedOutputModes 를 쓰는 곳은 직렬화와 클라이언트 쪽뿐입니다. SHOULD 를 지키는 것은 실행기(에이전트)의 몫이고, 보물상사 식사 에이전트는 지키지 않습니다.
  • 오류도 없습니다. §3.3.2 의 ContentTypeNotSupportedError 설명에는 "or implied for an artifact" 도 들어 있지만, 어느 SDK 도 출력 쪽에서 이 오류를 스스로 내지 않았습니다.
받는 쪽이 모르는 파트를 견뎌야 한다 — acceptedOutputModes 를 적었다고 그 타입만 온다고 믿으면 안 됩니다. 클라이언트는 모르는 미디어 타입의 파트를 건너뛸 수 있어야 합니다.

입력 쪽은 거절할 수 있다 — -32005 ContentTypeNotSupportedError

§3.3.2: "A Media Type provided in the request's message parts … is not supported by the agent". 3부에서 본 대로 파이썬·TS 는 이 검사를 스위치로 켜고(기본 꺼짐) Go 는 검사가 없습니다. 그래서 검사를 켠 작은 접수 에이전트를 세 언어로 썼습니다 — 카드의 입력 모드는 text/plain·application/json, 인원("30명")을 받으면 접수증을 내고 없으면 되묻습니다(6·7·8장도 이 에이전트를 씁니다).

세 접수 에이전트 — 스위치, 옵션, 그리고 실행기 안의 검사

TS·Go 서버의 답에서 오류만 골랐습니다.

Go 는 실행기에서 막는다 — a2a.ErrUnsupportedContentType 을 이벤트보다 먼저 돌려주면 작업이 만들어지지 않고, SDK 가 그 오류를 -32005 로 옮깁니다(internal/jsonrpc 의 대응표).

둘째 요청(rpc/nomt.json)은 같은 파트에서 mediaType 만 뺐습니다. 세 서버 모두 받아 접수했습니다(파이썬·TS·Go 차례).

5장 퀴즈

Q. 총무팀이 숙소 안내 PDF(90,000바이트)를 raw 파트에 실어 TS 로 만든 에이전트에 보냅니다. 본문은 대략 몇 바이트가 되고, 어떤 답을 받습니까? 파이썬 서버라면 어떻습니까?

A. base64 로 약 4/3 이 되어 본문이 12만 바이트쯤입니다. TS SDK 의 JSON-RPC 처리기는 express 기본 한도 102,400바이트(limit: 102400)를 넘는 본문을 413 Payload Too Large 로 돌려보냅니다 — JSON-RPC 오류 객체도 없습니다(본문 한도, 80,000바이트 파일이 이미 106,865바이트 본문으로 413). 파이썬 서버는 같은 실험에서 두 크기를 다 받았습니다. 이런 파일은 url 파트로 보내는 것이 맞습니다.

contextId 규칙

§3.4 의 규칙 여덟 → 여섯 번 두드리기 → 파이썬 → TypeScript → Go → 같은 맥락에 새 작업 → 어긋난 contextId 는 거절 → taskId 만 주면 맥락을 찾아 준다 → 없는 taskId 는 -32001 → 클라이언트가 지은 contextId → 세 서버 비교

contextId 는 서버가 짓고, 지키고, 어긋나면 거절한다 — §3.4 의 규칙

contextId 는 "logically groups multiple related Task and Message objects"(§3.4.1) — 여러 작업과 메시지를 한 대화로 묶는 꼬리표입니다. taskId 는 그 안의 작업 하나입니다(1장). 이 장에서 시험할 규칙입니다.

contextId 없는 메시지면 에이전트가 새로 지을 수 있고(MAY), 지었으면 답에 넣어야 한다(MUST)§3.4.1①
"Clients MAY use contextId without taskId to start a new task within an existing conversation context"§3.4.3②

여섯 번 두드린다 — 같은 대본을 세 언어의 SDK 클라이언트로

세 언어의 클라이언트가 같은 언어의 접수 에이전트(5장)에 같은 대본을 보냅니다. 파이썬 쪽 대본입니다. ①의 답(인원을 되묻는 작업 t1)을 뒤의 세 번이 다시 씁니다.

순서가 뜻을 가진다 — ③(어긋난 맥락)은 ④보다 먼저입니다. ④에서 t1 이 접수를 마치면(COMPLETED) 그 뒤로는 종료된 작업이라, 어긋남이 아니라 "종료된 작업" 이라는 다른 오류가 납니다(5부).

파이썬 — Message 의 task_id·context_id 를 채우면 와이어에 실린다

빈 문자열이면 와이어에 나가지 않습니다(proto3 의 문자열은 "" 가 곧 없음 — 8장). 오류는 SDK 의 예외 클래스로 옵니다.

TypeScript — 메시지 객체에 taskId·contextId 를 적는다

ts-proto 의 Message 는 두 필드를 늘 string 으로 들고, "" 면 직렬화에서 뺍니다. 오류는 JsonRpc…Error 클래스로 옵니다.

Go — msg.TaskID·msg.ContextID 를 채운다, 오류는 문장 하나

TaskID 는 a2a.TaskID 타입, ContextID 는 string 입니다. 둘 다 omitempty 라 빈 값은 빠집니다.

Go 클라이언트의 오류는 서버 문구 그대로 — executor setup failed: failed to load exec ctx: … 는 Go 서버가 와이어에 적은 error.message 입니다. 코드는 셋 다 같습니다 — 다음 슬라이드들.

② 같은 맥락에 새 작업 — contextId 만 주면 작업 id 는 새로 생긴다

②는 ①의 맥락(<id2>)을 달고 taskId 없이 보냈습니다. 파이썬 서버의 주고받음입니다.

  • 새 작업 <id3> 이 같은 맥락 <id2> 에 들어갔습니다. TS·Go 도 같았습니다(TS·Go 의 ②줄).
  • 새 작업의 이력에는 이번 메시지만 있습니다. 같은 맥락의 앞 작업을 참고할지는 에이전트가 정합니다 — §3.4.1: "Agents MAY use the contextId to maintain internal state, conversational history, or LLM context". 기획 에이전트가 세 에이전트에 한 맥락으로 일을 나눠 주는 장면은 15부에서 봅니다.

③ 어긋난 contextId 는 세 서버 모두 -32602 로 거절했다

③은 t1 의 taskId 에 엉뚱한 맥락 ctx-다른-맥락 을 붙였습니다. 세 서버의 답에서 오류만 골랐습니다(파이썬·TS·Go 차례).

  • §3.4.3 의 MUST 를 셋 다 지켰고, 코드도 같은 -32602(Invalid params) 입니다. 전용 A2A 오류 코드가 없어서 JSON-RPC 의 일반 코드를 씁니다.
  • 문구는 제각각입니다. 파이썬·TS 는 두 맥락 id 를 다 적고, Go 는 SDK 안쪽 단계 이름(executor setup failed)까지 드러냅니다.

④ taskId 만 주면 서버가 그 작업의 맥락을 찾아 준다

④는 t1 의 taskId 만 달고 contextId 는 비웠습니다. 파이썬 서버의 요청과 답의 앞부분입니다.

  • 요청에 없던 contextId 가 답에는 ①의 <id2> 로 왔습니다 — "Agents MUST infer contextId from the task". 작업 <id1> 은 인원을 받아 COMPLETED 가 됐습니다.
  • TS·Go 도 ④에서 ①의 맥락을 돌려줬습니다. 그래서 이어 말할 때 클라이언트가 contextId 를 꼭 들고 다닐 필요는 없습니다 — 다만 달았다면 맞아야 합니다(③).

⑤ 없는 taskId 는 -32001 TaskNotFoundError — 작업 id 는 클라이언트가 못 짓는다

⑤는 서버가 만든 적 없는 t-없는-작업 을 taskId 로 보냈습니다. 세 서버의 오류입니다(파이썬·TS·Go 차례).

  • 셋 다 -32001 입니다. §3.4.2: "Agents MUST return a TaskNotFoundError if the provided taskId does not correspond to an existing task".
  • "이 id 로 새 작업을 만들어 달라" 는 뜻으로 보낸 것이어도 같습니다 — "Client-provided taskId values for creating new tasks is NOT supported". 작업 id 는 서버가 짓습니다(§3.4.2 "server-generated").

⑥ 클라이언트가 지은 contextId — 세 서버 모두 받아서 그대로 썼다

⑥은 처음 보는 맥락 ctx-워크숍 을 클라이언트가 지어 보냈습니다. 세 언어 모두 ctx=ctx-워크숍 인 새 작업을 받았습니다. 아래는 Go 서버의 주고받음에서 id 들만 고른 것입니다.

  • §3.4.1 은 이것을 허락(MAY accept and preserve)하면서도, 클라이언트에게는 "SHOULD NOT provide a client-generated contextId to a server unless they understand how the server will process that contextId" 라고 적습니다. 세 SDK 의 기본 처리기는 모르는 맥락 id 도 새 맥락으로 받아들입니다.
  • 받지 않기로 한 서버라면 거절해야 하고, 그때 "MUST NOT generate a new contextId for the response" — 몰래 새 id 로 바꿔 답하면 안 됩니다.
맥락 id 는 이름표가 아니다 — 클라이언트가 ctx-워크숍 처럼 읽기 쉬운 이름을 지으면, 다른 클라이언트가 같은 이름을 지어 남의 맥락에 끼어들 수 있습니다. 서버가 지은 id 는 "opaque identifiers" 로 다루라는 것(§3.4.1)도 같은 까닭입니다.

6장 퀴즈

Q. 인원을 되묻는 작업 t1(맥락 c1)이 있습니다. 클라이언트가 실수로 다른 대화의 맥락 c2 를 달고 t1 에 "30명" 이라고 보내면 어떻게 됩니까? contextId 를 아예 빼고 보내면요?

A. 세 서버 모두 -32602 로 거절합니다(③) — §3.4.3 의 "MUST reject messages containing mismatching contextId and taskId". contextId 를 빼면 서버가 t1 의 맥락 c1 을 찾아 쓰고, 작업은 접수를 마칩니다(④, 답의 contextId 가 ①의 것).

7장

messageId 와 멱등성

스펙은 MAY 한 줄 → 같은 messageId 로 새 메시지 두 번 ×3 → 이어 말하기에 같은 messageId → 실행기는 두 번 돌았다 → 세 서버 비교

같은 메시지가 두 번 올 수 있다 — 스펙은 "감지해도 된다(MAY)" 까지만 말한다

클라이언트가 보낸 뒤 답을 못 받으면(시간 초과, 연결 끊김) 같은 메시지를 다시 보냅니다. 서버는 첫 요청을 이미 처리했을 수도 있습니다.

  • §3.3.1: "Send Message operations MAY be idempotent. Agents may utilize the messageId to detect duplicate messages." 반면 Get 계열은 "naturally idempotent", CancelTask 는 "idempotent" 라고 못 박습니다.
  • proto 의 message_id 설명: "The unique identifier (e.g. UUID) of the message. This is created by the message creator." 같은 id 로 다시 보내는 것이 "같은 메시지" 라는 신호가 될 수 있는 까닭입니다.
  • MAY 이므로 서버마다 다를 수 있습니다. 세 SDK 서버에 실제로 두 번 보내 봤습니다.

새 메시지로 두 번 — 세 서버 모두 작업을 둘 만들었다

어느 SDK 의 클라이언트 손도 타지 않게, urllib 로 JSON-RPC 를 직접 보내는 dup.py 를 접수 에이전트 셋에 차례로 붙였습니다. ①②는 m-dup 을 새 메시지로 두 번 보냅니다.

재시도가 일을 두 번 시킨다 — 세 서버 모두 둘째 m-dup 을 새 일로 받아 다른 작업 id 를 지었습니다. 숙소 예약처럼 두 번 하면 안 되는 일이라면, 같은 messageId 로 다시 보내는 것만으로는 막히지 않습니다.

이어 말하기에 같은 messageId — 이력에 다시 넣느냐가 SDK 마다 다르다

③은 인원 없이 보내 되묻는 작업을 만들고, ④는 그 작업에 ③과 같은 messageId(m-ask)로 다시 말합니다. 끝에 GetTask 로 이력의 messageId 를 찍었습니다(파이썬·TS·Go 차례).

  • 파이썬: 이력에 m-ask 가 한 번 — 같은 id 의 메시지가 이미 있으면 다시 넣지 않습니다(active_task.py 의 message_already_saved). 뒤의 <id4> 는 에이전트가 되물은 말입니다(서버가 지은 id).
  • TS: m-ask 가 두 번 — 요청 처리기가 이어 말하기 메시지를 이력 끝에 조건 없이 붙입니다(_createRequestContext). 되물은 말 둘도 함께 남았습니다.
  • Go: m-ask 한 번 — "message will already be present if we're retrying execution" 이라는 주석과 함께 같은 id 를 건너뜁니다(agentexec.go). 뒤의 <id13> 은 파이썬처럼 되물은 말입니다.

이력은 걸러도 일은 다시 한다 — 세 실행기 모두 네 번 돌았다

접수 에이전트는 실행될 때마다 한 줄을 찍습니다. 세 서버의 로그입니다(파이썬·TS·Go 차례).

  • 네 번 보냈고 네 번 실행됐습니다. ②의 m-dup 도, ④의 m-ask 도 실행기까지 갔습니다.
  • 파이썬·Go 가 messageId 로 걸러 낸 것은 이력에 넣는 일뿐입니다. §3.3.1 의 "detect duplicate messages" — 중복이면 다시 처리하지 않는 것 — 은 세 SDK 모두 기본으로 하지 않습니다.

세 서버 비교 — 멱등성은 에이전트가 만들어야 한다

같은 messageId파이썬TypeScriptGo
새 메시지로 두 번작업 둘, 실행 두 번
같은 작업에 두 번 — 이력한 번만두 번한 번만
같은 작업에 두 번 — 실행두 번
보내는 쪽은 메시지마다 새 messageId, 받는 쪽은 필요하면 직접 기억 — 클라이언트는 새 말마다 새 id 를 짓습니다(1장의 ask-N, 이 장의 ctx-py-N). "같은 요청의 재시도" 를 한 번만 처리하려면, 에이전트가 처리한 messageId 를 기억해 두고 이미 본 id 면 저장된 작업을 돌려주는 식으로 직접 만들어야 합니다. 시간 초과·재시도 전략은 17부에서 다룹니다.

7장 퀴즈

Q. 클라이언트가 SendMessage 의 답을 기다리다 시간 초과로 같은 요청(같은 messageId)을 한 번 더 보냈습니다. 서버가 세 SDK 중 어느 것이든, 실행기는 몇 번 돌고 작업은 몇 개 생깁니까?

A. 첫 요청이 서버에 닿았다면 실행기는 두 번 돌고 작업도 둘 생깁니다. 세 SDK 모두 새 메시지의 messageId 로 중복을 거르지 않습니다(①②의 서로 다른 작업 id, 서버 로그의 두 줄). §3.3.1 은 감지를 MAY 로만 둡니다.

ProtoJSON 규칙

camelCase·enum 이름·시각·빠진 필드 → 일곱 가지로 비튼 요청 → snake_case 필드 이름 → role 을 "user"·1 로 → 왜 그렇게 받았나 → TaskState 를 입력으로 → null·""·모르는 필드 → 시각의 자릿수 → Go 의 시간대 → 세 서버 비교

와이어 JSON 의 규칙은 ProtoJSON 이다 — 스펙 §5.5–5.7

A2A 의 JSON 은 proto 정의를 ProtoJSON(protobuf 의 JSON 표기 규칙)으로 적은 것입니다. 스펙이 따로 못 박은 것은 넷입니다.

일곱 가지로 비튼 요청 — 맨손 클라이언트가 받음·거절만 찍는다

본문은 모두 "30명" 한 마디(접수 에이전트가 바로 접수)이고, 하나씩만 비틀었습니다. protojson.py 가 urllib 로 보내고, 받았으면 상태와 이력에 저장된 role 을, 거절이면 코드와 문구를 찍습니다.

snake_case 필드 이름 — 파이썬·TS 는 받고, Go 는 "messageId 가 없다"

포트 10486 이 파이썬, 10487 이 TS, 10488 이 Go 입니다.

  • 파이썬은 protobuf 의 JSON 해석기가 proto 이름(message_id)과 JSON 이름(messageId)을 둘 다 받습니다. TS 의 ts-proto 생성 코드도 object.messageId 가 없으면 object.message_id 를 봅니다(Message.fromJSON).
  • Go 의 구조체 태그는 json:"messageId" 하나뿐이라 message_id 는 모르는 필드로 버려지고, 필수 검사에서 걸립니다.
받아 준다고 써도 되는 것은 아니다 — §5.5 의 MUST 는 보내는 쪽 규칙입니다. snake_case 로 보내면 Go 서버에서 바로 깨집니다.

role 을 "user"·1 로 — 세 서버가 세 가지로 받았다

v03 은 v0.3 의 "role": "user", number 는 enum 의 수 1(ROLE_USER)입니다.

"user"거절 — message.role: Field is required.받음 — 이력에 UNRECOGNIZED받음 — 이력에 "user" 그대로

수는 proto 에서 온 해석기만 읽었다 — proto 정의에서 만든 해석기(파이썬 protobuf, TS ts-proto)는 enum 을 이름으로도 수로도 받았습니다. enum 을 손으로 쓴 문자열 타입으로 둔 Go 만 수를 못 읽습니다.

왜 그렇게 받았나 — 모르는 enum 값을 다루는 세 가지 방법

세 SDK 의 설치본에서 role 을 읽는 곳을 찾았습니다.

  • 파이썬: JSON-RPC 디스패처가 ParseDict(…, ignore_unknown_fields=True) 로 읽습니다. 이 설정은 모르는 enum 이름도 "모르는 것" 으로 버려서, role 이 빠진 메시지가 되고 필수 검사(1장)에 걸렸습니다.
  • TS: roleFromJSON 의 switch 가 0·1·2 와 세 이름만 알고, 나머지는 default 로 -1(UNRECOGNIZED)을 돌려줍니다. 그 뒤로 role 을 검사하지 않아(1장) 그대로 처리됐습니다.
  • Go: MessageRole 은 string 타입이고 UnmarshalJSON 은 어떤 문자열이든 담습니다(ROLE_UNSPECIFIED 만 빈 값으로). 필수 검사는 빈 값만 보니 "user" 가 통과했고, 쓸 때도 그대로 씁니다.
v0.3 클라이언트의 "user" 는 세 곳에서 세 결과 — 거절, 알 수 없는 role, 그대로 저장. v0.3 피어와 함께 사는 법(SDK 의 호환 계층)은 14부에서 봅니다.

TaskState 를 입력으로 — 파이썬은 모르는 값을 "필터 없음" 으로 읽었다

클라이언트가 TaskState 를 보내는 곳은 ListTasks 의 status 필터입니다(목록 자체는 11부). 일곱 요청 뒤에 세 모양으로 "되묻는 중인 작업" 을 찾았습니다. 그때 서버에는 접수를 마친 작업만 있었으므로 맞는 답은 "없음" 입니다.

  • 파이썬: v0.3 꼴 "input-required" 를 모르는 enum 으로 버리고 필터 없이 작업 여섯을 다 돌려줬습니다 — 오류도 없이 틀린 답입니다.
  • TS: 같은 값을 -32602 Invalid status filter: -1 로 거절했습니다(UNRECOGNIZED = -1). Go: 아무 문자열이나 상태로 받아 맞는 작업이 없었고, 수 6 은 읽지 못했습니다.
  • 빈 목록도 셋이 다르게 적습니다 — 파이썬·TS 는 [], Go 는 null. 빈 목록과 "없음" 을 가르지 않는 클라이언트라면 둘 다 견뎌야 합니다(2부).

null·빈 문자열·모르는 필드 — 셋 다 세 서버가 받았다

null 은 taskId·metadata 를 null 로, empty 는 taskId·contextId 를 "" 로, unknown 은 모르는 필드 priority 를 넣었습니다.

  • "" 인 taskId 를 셋 다 "없음" 으로 읽어 새 작업을 만들었습니다. proto3 의 문자열에는 "설정됨" 표시가 없어서(§5.7 의 optional 이 아닌 필드) 빈 값과 빠진 값이 같습니다 — 6장에서 "" 를 "안 보냄" 으로 쓴 까닭입니다.
  • null 도 "없음" 이었습니다. 모르는 필드는 §5.7 의 "SHOULD ignore unrecognized fields" 대로 셋 다 넘겼습니다 — 다만 파트 안의 모르는 내용 필드는 Go 가 거절했었습니다(2장).

시각의 자릿수 — 밀리초·마이크로초·나노초, 셋이 다르다

캡처는 시각을 <시각> 으로 지우므로(0부), protojson.py 는 받은 답들의 status.timestamp 에서 꼴만 찍습니다(끝자리 0 을 지우는 SDK 가 있어 가장 긴 것을 봅니다) — 소수부를 몇 자리까지 적었나와 시간대.

  • 셋 다 UTC 의 Z 입니다. 자릿수는 TS 가 스펙의 견본(.sssZ, "Millisecond precision SHOULD be used")과 같고, 파이썬은 datetime 의 마이크로초, Go 는 time.Time 의 나노초까지 적습니다.
  • 스펙은 받는 쪽에 "MUST parse and generate ISO 8601 timestamps correctly" 를 요구합니다. 자릿수가 다른 세 꼴을 모두 읽을 수 있어야 합니다.

Go SDK 의 시각은 서버 기계의 시간대를 따른다 — 서울에 두면 +09:00

이 기계는 UTC 라 Go 서버도 Z 를 적었습니다. Go SDK 의 NewStatusUpdateEvent 는 time.Now() 를 그대로 담고(a2a/core.go), encoding/json 은 지역 시간대를 붙여 씁니다. 프로세스 안에서 time.Local 을 바꿔 봤습니다.

  • 지역 시간대가 KST 인 기계에서는 +09:00 이 붙습니다. §5.6.1 의 "Timestamps MUST NOT include timezone offsets other than 'Z'" 를 어깁니다.
  • 파이썬 SDK 는 datetime.now(timezone.utc), TS 는 toISOString() 이라 늘 Z 입니다. Go 서버는 UTC 로 두거나(TZ=UTC), 시각을 .UTC() 로 바꿔 담아야 합니다.

8장 퀴즈

Q. v0.3 시절 코드를 고치다 만 클라이언트가 "role": "user" 로 메시지를 보냅니다. 파이썬·TS·Go 서버는 각각 어떻게 답합니까? 셋 중 오류 없이 지나가서 더 위험한 것은 어디입니까?

A. 파이썬은 모르는 enum 이름을 버려 role 이 빠진 메시지가 되고 -32602(message.role: Field is required.)로 거절합니다. TS 는 UNRECOGNIZED 로, Go 는 "user" 그대로 받아 접수까지 마쳤습니다(role 시험). 오류 없이 지나간 TS·Go 쪽이 더 위험합니다 — 이력에 규칙 밖의 role 이 남고, 그 이력을 읽는 다른 언어의 클라이언트가 깨질 수 있습니다.
