3×3 상호운용·적합성·오류 처리

다섯 에이전트를 세 언어의 서버와 세 언어의 클라이언트로 모두 맞붙이고, 그 사이를 지난 바이트의 차이를 따집니다

15부까지는 "된다" 를 보였다 — 이 부는 "모든 조합에서 된다" 를 센다

15부의 메시 여섯 판은 클라이언트가 파이썬 ask 하나였습니다. 이 부는 에이전트마다 서버 셋 × 클라이언트 셋을 모두 돌려 칸을 세고, 칸 사이에서 갈린 바이트를 목록으로 만듭니다.

다른 명세도 같은 틀 — 식사·교통 푸시는 같은 모양, 폴링이 섞인 교통 ①·③ 은 물음 수가 매번 달라 탭을 빼고, 정산은 토큰 번호가 서버의 발급 순번이라 클라이언트 언어마다 명세를 나눴고(16/settle_{py,ts,go}.run), 기획은 서버 언어마다 동료 넷까지 한 언어로 띄웠습니다(16/planner_{py,ts,go}.run). 포트는 11600~11692.

스트림 한 칸 — 이벤트 차례까지 아홉 칸이 같다

파이썬 클라이언트 → 파이썬 서버 칸의 앞부분입니다. 식단표 조각의 +(append)와 (끝)(lastChunk) 표시가 10부와 같은 자리에 붙습니다.

10부보다 넓다 — 10부 2장은 파이썬 ask 를 세 서버에, TS·Go ask 는 파이썬 서버에만 붙였습니다(다섯 칸). 남은 네 칸(TS·Go 클라이언트 × TS·Go 서버)도 같은 대본이었습니다.

교통 ① — returnImmediately 와 GetTask, 아홉 칸이 같은 상태 차례

5부의 modes 세 벌입니다. 막는 호출로 한 번, returnImmediately 로 한 번 보내고, 둘째를 GetTask 로 지켜보며 상태가 바뀔 때만 찍습니다(단계 하나 0.5초).

5부는 같은 언어끼리만 — 5부의 명세는 클라이언트와 서버의 언어가 같은 세 칸이었습니다. 엇갈린 여섯 칸에서도 SUBMITTED 0 → WORKING → COMPLETED 가 같습니다.

교통 ② — 푸시 설정 둘, 웹훅에 온 이벤트가 아홉 칸에서 같다

11부 3장의 setup 세 벌입니다. 요청에 실은 설정(tok-inline)과 Create 한 설정(tok-create)으로 각각 무엇이 왔는지 중계기에 묻습니다.

  • 아홉 칸 모두 tok-inline 은 task SUBMITTED 부터 다섯 건 더, tok-create 는 SUBMITTED 없이 다섯 건입니다 — Create 는 작업이 생긴 뒤라서(11부). 줄이 갈리는 곳은 정규화된 작업 id(<id1>…)뿐입니다.
  • 푸시는 서버가 웹훅으로 보내는 길이라, 이 칸의 "클라이언트" 는 설정을 다는 쪽입니다. 받는 쪽(중계기)은 하나로 고정했습니다.

교통 ③ — 새로 쓴 대본 하나: WORKING 을 본 뒤 CancelTask

달리는 배차를 TS·Go 클라이언트로 취소한 예제는 아직 없었습니다(5부·11부의 취소는 파이썬 클라이언트, 15부의 TS·Go 기획 에이전트가 취소한 것은 결재를 기다리던 정산 작업). 그래서 세 벌을 썼습니다. 단계 하나는 2초입니다.

시간이 아니라 상태를 기다린다 — 첫 GetTask 가 WORKING 을 볼 때까지 0.05초마다 묻습니다. 묻는 횟수가 실행마다 달라 이 명세에는 탭을 두지 않았습니다.

TypeScript·Go — 같은 차례, 다른 것은 요청 객체의 차림뿐

취소 부분만 실었습니다. 앞쪽(카드 읽기, returnImmediately 보내기)은 5부의 modes 와 같습니다.

TS 는 필드를 다 적는다 — ts-proto 타입이 tenant·metadata 를 요구해 ask 객체에 함께 둡니다(8부). Go 는 a2a.CancelTaskRequest{ID: …} 하나입니다.

취소 아홉 칸 — CancelTask 의 답은 CANCELED, 2.5초 뒤에도 아티팩트 0

명령 머리, CancelTask 의 답, 한 단계보다 길게 기다린 뒤의 GetTask 를 골랐습니다(포트 11630·11631·11632 = 파이썬·TS·Go 서버).

실행기가 정말 멈췄다 — 서버 로그는 세 서버 모두 배차 요청 접수 다음이 취소 이고, 기사 배정 이 없습니다(위는 TS 서버). 취소가 상태만 바꾸고 일은 계속되는 칸은 없었습니다.

정산 ① — 토큰, AUTH_REQUIRED, 결재 토큰: 아홉 칸이 같은 두 줄

12부 7장의 approve 세 벌입니다. 조회 토큰으로 큰 정산을 맡겨 AUTH_REQUIRED 를 받고, 결재 스코프가 든 새 토큰으로 같은 작업에 이어 말합니다. 정산 명세는 클라이언트 언어마다 하나라, 토큰 번호도 칸마다 1·2 입니다.

멈춘 까닭의 글도 같다 — AUTH_REQUIRED 상태 메시지("합계 4,842,000원은 결재가 필요합니다…")는 세 서버가 같은 글자이고, 끝난 정산서의 approvedBy 도 셋 다 planner 입니다.

정산 ② — 확장 카드는 아홉 칸 모두 스킬 둘, 갈아 끼우기는 클라이언트 줄을 따른다

12부 6장의 xcard 세 벌의 ③ 줄입니다 — 확장 카드를 받은 뒤 클라이언트가 들고 있는 카드. ①(공개 카드: 스킬 하나·서명 1개)과 ②(확장 카드: 스킬 둘·서명 0개)는 아홉 칸이 같았습니다.

Go 줄만 공개 카드 그대로 — Go 의 GetExtendedAgentCard 는 받은 카드를 돌려줄 뿐 클라이언트의 카드를 바꾸지 않습니다(12부). 서버 셋 모두에서 같으니 서버 탓이 아니라 클라이언트 SDK 의 선택입니다. TS 줄은 파이썬과 같았습니다.

정산 ③ — 서명된 카드: 진짜 카드는 아홉 칸 모두 맞음

12부 8장의 verify 세 벌입니다. 12부에서는 세 서버가 같은 주소를 적어 서명까지 같게 했지만, 여기서는 서버마다 제 탭 주소를 적었습니다 — 카드도 서명도 셋이 다릅니다. 그래도 고정해 둔 공개 키로 셋 다 검증됩니다.

  • ①은 아홉 칸 모두 맞음입니다. Go 서버가 서명한 카드도 파이썬·TS 검증기를 지났습니다.
  • ③(모르는 필드를 더한 카드)은 Go 클라이언트 줄만 틀림 — 받은 바이트를 그대로 정규화하기 때문이고(12부), 서버 셋에서 같았습니다. ②·④ 의 오류 글도 클라이언트 언어마다 다를 뿐 서버를 따르지 않습니다.

기획 — 파이썬 메시에 세 클라이언트, 숫자는 같고 "승인" 뒤 task 줄이 없다

동료 넷과 기획 에이전트가 모두 파이썬인 메시(16/planner_py.run)에 세 언어의 ask 가 같은 문장과 "승인" 을 보냈습니다. 결재 물음, 답, 계획서의 합계 줄, 끝만 골랐습니다.

여기에 없는 줄 — 다른 두 메시에서는 "> 승인" 다음에 task WORKING 이 옵니다(다음 슬라이드). 파이썬 서버의 둘째 스트림은 Task 가 아니라 아티팩트로 시작하기 때문입니다(15부). 세 클라이언트가 똑같이 없으니 서버 열의 차이입니다.

TypeScript·Go 메시 — 여섯 칸이 같은 대본, "승인" 다음에 task WORKING

15부와 다른 점 — 15부의 메시는 파이썬 ask 하나로 끝까지 갔습니다. TS·Go ask 도 결재에서 멈춘 기획 작업에 같은 taskId 로 "승인" 을 이어 보내 끝냈습니다.

기획 한 칸을 통째로 — 계획서의 숫자가 SCENARIO §2.6 과 같다

TypeScript 클라이언트 → TypeScript 메시 칸입니다. 다른 여덟 칸도 계획서와 요약 DataPart 가 이 칸과 글자까지 같았습니다.

골든과 대조 — 숙소 2,100,000 · 식사 1,542,000 · 교통 1,200,000 · 합계 4,842,000 · 남음 1,158,000. 15부의 여섯 판과 같은 숫자를, 이번에는 세 언어의 클라이언트가 받았습니다.

갈린 줄은 셋 — 모두 한 열이나 한 줄 전체가 같이 갈렸다

대본이 같다고 와이어가 같은 것은 아니다 — ask 가 차이를 지운다

아홉 칸의 대본이 글자까지 같은 데는 까닭이 둘 있습니다. 업무 규칙은 세 언어가 같은 골든을 지키는 workshop 모듈이 정하고, 출력은 ask 가 한 꼴로 찍습니다.

그래서 2장 — tidy 는 30.0 을 30 으로, sort_keys 는 키 차례를 지웁니다. 와이어에는 그 차이가 그대로 남아 있습니다. 2장은 탭 기록에서 그것을 꺼냅니다.

1장 퀴즈

Q. 교통 ② 칸에서 tok-create 로 온 이벤트에는 task SUBMITTED 가 없습니다. 이것은 어느 클라이언트·서버 짝의 결함입니까?

A. 어느 짝의 결함도 아닙니다. 교통 ②의 아홉 칸 모두 tok-create 에 SUBMITTED 가 없고 tok-inline 에는 있습니다 — 차이가 칸이 아니라 "설정을 언제 달았나" 에 따라 갈립니다. Create 는 작업이 SUBMITTED 로 생긴 뒤에 보내므로, 그 설정으로는 이미 지나간 이벤트가 가지 않습니다.

수 — 파이썬이 보내면 1.0, 받아 다시 쓰는 서버의 언어가 꼴을 정한다

숙소 칸의 첫 DataPart {"nights": 1} 입니다. TS 서버 앞 탭에서 파이썬 클라이언트의 것(주고받음 2)을, 파이썬 서버 앞 탭에서 TS 클라이언트의 것(5)을, 파이썬·Go 서버 앞 탭에서 견적의 수를 골랐습니다.

소수점은 쓰는 쪽이 붙인다 — 파이썬이 보낸 1.0 을 TS 서버는 이력에 1 로, TS 가 보낸 1 을 파이썬 서버는 1.0 으로 되돌려 씁니다. 견적의 8.0·2100000.0 도 파이썬 서버만입니다.

왜 통하나 — DataPart 의 값은 JSON 값이고, JSON 의 수에는 정수 타입이 없다

proto 는 Part.data 를 google.protobuf.Value 로 두고 "Arbitrary structured data as a JSON value" 라고 적었습니다(a2a.proto 의 message Part). Value 의 수는 double 하나뿐이라, 파이썬 SDK 는 그 double 을 1.0 으로 적습니다(7부).

  • 값은 같다 — JSON 에서 1 과 1.0 은 같은 수입니다(2부). 1장의 아홉 칸이 같은 견적을 낸 것이 그 증거입니다.
  • 깨지는 곳은 받는 쪽의 타입 — Go 에서 1.0 을 int 필드로 바로 풀면 오류입니다(2부). DataPart 를 받는 SDK 는 셋 다 실수(float·number·float64)로 넘깁니다(4부).
받는 쪽이 견딜 것 — 정수가 필요한 자리는 받은 뒤 정수로 되돌립니다. 다섯 에이전트의 as_ints·asInts·common.Int 가 그 일을 합니다(4부) — 소수부는 잘라 내고, 수가 아닌 값은 0 으로 두어 업무 규칙이 거절하게 합니다(3장). 2^53 을 넘는 수는 DataPart 에 수로 싣지 않습니다.

빈 값 — 같은 "없음" 을 셋이 다르게 적는다

세 가지를 골랐습니다. 숙소 칸의 configuration(TS 서버 앞, 클라이언트 파이썬 → TS → Go 차례), 교통 ② 칸의 Go 클라이언트가 실은 푸시 설정, Go 서버의 카드입니다.

  • 파이썬·TS 클라이언트는 빈 "configuration": {} 을 싣고, Go 는 아예 뺍니다.
  • Go 는 거꾸로 빈 문자열 "taskId": "" 을 적습니다 — a2a/push.go:71 의 태그에 omitempty 가 없어서입니다. 파이썬·TS 의 같은 요청에는 taskId 가 없습니다. 카드의 "pushNotifications": false 도 Go 서버만 적습니다(3부).

왜 통하나 — proto3 의 보통 필드에서는 빈 값과 빠진 값이 같은 뜻이다

A2A 의 JSON 은 ProtoJSON 입니다(4부). optional 이 아닌 문자열·불·메시지 필드에는 "설정됨" 표시가 없어서, ""·false·빈 객체는 빠진 것과 같게 읽힙니다 — 세 서버가 "" 인 taskId 를 "없음" 으로 읽은 것을 4부에서 봤습니다.

  • 예외는 optional 필드 — §5.7 은 optional 로 "explicitly set versus omitted" 를 가른다고 합니다. historyLength 의 0 은 빠진 것과 다릅니다(5부).
  • 카드의 서명 — 카드의 pushNotifications 도 optional 이라, §8.4.1 은 명시한 false 를 정규화한 바이트에 남기라고 합니다("even if that value matches a default"). 읽는 뜻은 빠진 것과 같아도 서명할 바이트는 다릅니다(12부).
받는 쪽이 견딜 것 — 보통 필드는 "키가 있나" 가 아니라 "값이 기본값인가" 로 봅니다. "taskId": "" 을 "작업 id 가 빈 문자열인 작업" 으로 찾지 않습니다. 빼는 것이 쓰는 쪽의 바른 기본이고, 받는 쪽은 둘 다 받습니다.

키 차례 — 봉투도, Task 도, 메시지도 서버·클라이언트마다

숙소 칸의 첫 SendMessage 를 두 쌍 골랐습니다. 파이썬 클라이언트 → 파이썬 서버, Go 클라이언트 → Go 서버. 위 세 단계 깊이의 키 이름만 남겼습니다.

  • 파이썬은 봉투를 method·params·id·jsonrpc, 답을 result·id·jsonrpc 차례로 씁니다. Go 는 jsonrpc 부터, 메시지는 parts 가 role 앞, Task 는 history 가 status 앞입니다(5부).
  • 왜 통하나 — JSON 객체의 키에는 차례의 뜻이 없고, 세 SDK 모두 이름으로 읽습니다(2부). 파이썬 서버의 Struct(data·metadata) 안쪽은 프로세스마다 차례가 바뀌기까지 합니다(7부).
받는 쪽이 견딜 것 — 이름으로 읽고, 받은 바이트를 그대로 견주거나 해시하지 않습니다. 바이트가 같아야 하는 서명은 JCS 로 정규화한 뒤에 견줍니다(12부).

요청의 머리와 id — 클라이언트마다 Accept 가 셋, Go 는 카드를 판 머리 없이 받는다

파이썬 서버 앞 탭의 숙소 칸 아홉 요청(클라이언트 파이썬 → TS → Go 차례로 카드 GET, SendMessage 둘)의 머리, 그리고 TS 클라이언트의 JSON-RPC id 입니다.

  • Accept — 파이썬 */*, TS 는 SendMessage 에 application/json, Go 는 없음. 스펙 §9.1 은 요청·응답의 Content-Type 만 정하고 Accept 는 요구하지 않습니다.
  • 카드 GET 의 A2A-Version — Go 만 없습니다. §3.6.1 은 "Clients MUST send the A2A-Version header with each request" 라고 하지만, 판 검사는 A2A 메서드에서 하는 일이라 세 서버 모두 카드를 줬습니다(3부).
  • JSON-RPC id — TS 는 늘 수 1, 파이썬·Go 는 UUID 문자열입니다. JSON-RPC 2.0 의 id 는 문자열·수·null 어느 것이든 되고(2부), 서버는 받은 값을 그대로 돌려줍니다(2부) — 위 답의 "id": 1 처럼.

날 머리 — 파이썬은 소문자, TS 는 charset 을 붙인다

와이어 탭은 정해 둔 머리만(2부), 정해 둔 이름 꼴로 고쳐 적습니다(tools/wiretap.py 의 HEADERS). 그래서 이 슬라이드만 탭 없이 curl 로 숙소 서버 셋(파이썬·TS·Go 차례)의 날 머리를 찍었습니다. 위는 카드, 아래는 없는 작업을 물은 GetTask 의 답입니다.

왜 통하나 — §9.2 "Service parameter keys are case-insensitive per HTTP specification", 머리 이름 전체가 그렇습니다. ; charset=utf-8 은 미디어 타입의 매개변수라 application/json 은 그대로입니다. 받는 쪽이 견딜 것: 머리는 대소문자 없이 찾고, 미디어 타입은 매개변수를 떼고 견줍니다(6부의 startsWith).

SSE — Go 는 이벤트마다 id: 줄, 파이썬은 charset, 읽는 쪽은 data: 만 본다

식사 칸의 첫 스트림에서 응답 머리와 앞쪽 SSE 필드 줄만 골랐습니다(파이썬 클라이언트 → 파이썬 서버, → Go 서버).

  • Go 의 id: 는 이벤트마다 새 UUID 이고, 파이썬의 줄 끝은 CRLF 입니다(10부). TS 서버는 data: 만, charset 없이 보냅니다.
  • 왜 통하나 — SSE 의 읽는 규칙은 id: 를 "마지막 이벤트 id" 로 기억할 뿐 data 와 섞지 않고, 줄 끝은 CRLF·LF·CR 어느 것이든 됩니다(2부). 1장의 식사 아홉 칸이 같은 이벤트 차례를 받았습니다.
받는 쪽이 견딜 것 — 손으로 SSE 를 자른다면 줄 끝 셋과 모르는 필드를 모두 받습니다. A2A 의 이벤트는 data: 에만 있습니다.

이력 — 같은 INPUT_REQUIRED 인데 history 의 길이와 채운 칸이 다르다

숙소 칸 첫 답의 응답 쪽에서 history·role·id 줄만 골랐습니다(파이썬 클라이언트가 보낸 같은 요청, 서버 셋).

  • TS 는 에이전트의 물음을 곧바로 이력에 넣고, 파이썬·Go 는 상태 메시지에만 둡니다. Go 는 이력의 사용자 메시지에 contextId·taskId 를 채우지 않습니다(4부, 5부).
  • 이것은 직렬화가 아니라 서버의 저장 방식 차이입니다. 상태(TASK_STATE_INPUT_REQUIRED)와 물음(status.message)은 셋이 같습니다.
받는 쪽이 견딜 것 — 에이전트의 물음은 status.message 에서 읽습니다(ask 가 그렇게 해서 1장의 대본이 같았습니다). 이력의 길이나 마지막 항목에 기대지 않습니다.

오류 — 코드와 reason 은 같고, 글과 metadata 는 셋이 다르다

없는 작업을 GetTask 로 물은 답의 본문입니다(파이썬·TS·Go 서버 차례, 앞 슬라이드의 명세). 봉투의 뼈대와 코드·글·ErrorInfo 줄만 골랐습니다.

  • 글은 Task not found / Task not found: no-such-task / failed to get task: task not found 셋입니다(5부와 같은 버릇).
  • ErrorInfo 의 metadata 는 파이썬이 빈 맵 {} 을 적고, TS 는 빼고, Go 는 timestamp 하나를 답니다. §9.5 의 보기는 taskId·timestamp 를 둡니다.
왜 통하나 — §9.5 는 error.message 를 "human-readable string" 으로 두고, 기계가 가를 것은 code 와 ErrorInfo 의 reason(TASK_NOT_FOUND)입니다. 받는 쪽이 견딜 것: 코드로 가르고, 글은 보여 주기만 합니다. 코드 하나하나를 일으켜 보는 일은 이 부의 3장이 합니다.

2장 정리 — 차이는 여덟 가지, 깨진 칸은 0

  • 1장의 탭 기록에서 수·빈 값·키 차례·요청 머리와 id·날 머리·SSE·이력·오류 글의 차이를 다시 확인했습니다. 새로 본 것은 Go 클라이언트의 "taskId": ""(a2a/push.go:71)와 파이썬 서버 ErrorInfo 의 빈 metadata 입니다.
  • 차이는 모두 스펙이 정하지 않았거나 "같은 뜻" 으로 둔 자리에 있습니다. 이름·enum·메서드·코드·상태 차례는 45칸 내내 같았습니다.
  • 쓰는 쪽은 스펙의 꼴(빼기, camelCase, 정수는 정수로)을, 받는 쪽은 점검표의 너그러움을 — 둘 다 지키는 쪽이 어느 짝과도 통합니다.

2장 퀴즈

Q. 파이썬 클라이언트가 보낸 {"nights": 1.0} 을 TS 서버는 이력에 무엇으로 적었고, TS 클라이언트가 보낸 1 을 파이썬 서버는 무엇으로 적었습니까? 이 결과에서 "소수점을 정하는 쪽" 은 누구입니까?

A. TS 서버는 1, 파이썬 서버는 1.0 으로 적었습니다(수의 두 캡처). 받은 값을 다시 JSON 으로 쓰는 쪽의 SDK 가 꼴을 정합니다 — 파이썬 SDK 는 Value 의 double 을 늘 소수점과 함께 씁니다. 값은 같으니 받는 쪽은 값으로 읽고, 정수가 필요하면 되돌립니다.
