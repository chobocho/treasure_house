확장과 버전 협상 (v0.3 호환 포함)

확장 선언과 활성화 → 예산 확장 ×3 → A2A-Version 협상 → v0.3 피어와 공존

스펙이 정하지 않은 것을 싣는 길과, 스펙의 판이 다른 상대와 말하는 길

13부까지는 v1.0 스펙 안의 것만 주고받았습니다. 이 부는 그 바깥 두 가지입니다 — 스펙에 없는 데이터·규칙을 확장(extension)으로 얹는 법(§4.6), 그리고 판(version)이 다른 상대와 A2A-Version 으로 말을 맞추는 법(§3.6)입니다.

장무엇을
1장확장 선언·활성화 — AgentExtension, A2A-Extensions 머리글, required, 세 SDK 의 손잡이
2장예산 확장 ×3 — 이 책의 확장 budget/v1 을 완성 숙소 에이전트에 씌우고, 와이어·필수 확장(-32008)·3×3
3장버전 — A2A-Version, 빈 값 = 0.3, VersionNotSupported(-32009), 세 SDK 의 서버·클라이언트 표
4장v0.3 피어와 공존 — 세 SDK 의 호환 계층, 옛 카드·옛 요청, v0.3 전송 3×3
이 부의 방식 — 13부처럼 완성 에이전트(agents/)의 카드와 실행기를 고치지 않고 빌립니다. 확장은 실행기를 감싸는 겉층으로, v0.3 호환은 서버를 띄우는 겉층으로 얹습니다.

1장

확장 선언·활성화

확장이 할 수 있는 것 → 카드의 AgentExtension → 데이터를 싣는 자리 → 활성화 세 걸음 → 바인딩별 전달 → 모르는 확장 ×3 → required 와 판 → SDK 의 서버 쪽 → 클라이언트 쪽

확장은 새 필드를 만들지 않는다 — URI 로 이름 붙인 metadata 와 규칙이다

§4.6 은 확장을 "핵심 스펙을 고치지 않고 기능이나 데이터를 더하는 길" 로 둡니다. 스펙 저장소의 topics/extensions.md 가 그 범위와 한계를 적었습니다.

종류(topics/extensions.md)하는 일
데이터만 더하는 확장(data-only)카드에 구조화된 정보를 더한다 — 요청·응답의 흐름은 그대로
프로필 확장(profile)핵심 메시지 위에 구조와 상태 규칙을 덧씌운다 — 예: 정해진 꼴의 DataPart 만 받기, 상태 메시지의 metadata 로 하위 상태
메서드 확장(extended skills)새 RPC 메서드를 더한다
상태 기계 확장작업 상태 기계에 상태나 전이를 더한다
한계 — 같은 문서의 "Limitations": 핵심 데이터 구조에 필드를 더하거나 필수 필드를 빼는 일은 확장이 할 수 없고, 사용자 정의 속성은 metadata 에 둡니다. 그래서 확장의 실체는 URI 하나와, 그 URI 를 열쇠로 한 metadata 의 모양, 그리고 그 둘을 어떻게 다루는지의 규칙입니다. 같은 문서가 "열거형에 새 값을 더하지 말라" 고 하면서 상태 기계 확장(새 상태)을 꼽는 것은 문서 안의 긴장입니다. 이 장은 그 URI 가 카드와 요청에서 어떻게 오가는지를 봅니다.

에이전트는 카드의 capabilities.extensions 에 확장을 적는다 — 필드는 넷

proto 의 AgentExtension(§4.4.4)은 uri·description·required·params 넷뿐입니다. 2장에서 띄울 예산 확장 에이전트(파이썬)의 카드를 탭 너머로 받았습니다.

필드proto 의 설명
uri확장을 가리키는 유일한 URI
description이 에이전트가 그 확장을 어떻게 쓰는지(확장 자체의 설명이 아니다)
required참이면 클라이언트가 그 확장을 이해하고 따라야 한다
params확장마다 정하는 설정값(Struct)
required 가 안 보인다 — 거짓이라 세 서버 모두 생략했습니다(proto3 의 기본값). Go 서버의 카드는 키가 알파벳 차례(description·params·uri)였습니다. 확장의 버전은 URI 에 넣으라는 것이 §4.6.3 의 SHOULD 이고, 그래서 이 책의 URI 끝이 /v1 입니다.

확장의 데이터는 Message·Artifact 에 — extensions 에 URI, metadata 에 URI 를 열쇠로

§4.6.2 가 꼽는 자리(extension point)는 둘입니다. 둘 다 proto 에 같은 꼴의 두 필드가 있습니다.

자리proto 필드§4.6.2 의 쓰임
Messagerepeated string extensions = 7 + metadata클라이언트가 요청에 강하게 형이 정해진 맥락을 더한다. 상태 메시지에 진행 정보를 더할 수도 있다
Artifactrepeated string extensions = 6 + metadata만든 결과에 대한 정보를 더한다(예: 인용 출처)
  • proto 의 주석은 extensions 를 "이 메시지에 들어 있거나 기여한 확장의 URI" 라고 합니다. 켜 달라는 요청이 아니라 표시입니다. 켜 달라는 요청은 다음 슬라이드의 머리글이 합니다.
  • 두 문서의 자리가 다르다 — §4.6.1·§4.6.2 의 예는 message.metadata["…/geolocation/v1"] 에 값을 두고, topics/extensions.md 의 활성화 예는 요청의 params.metadata["…/konami-code/v1/code"] 에 둡니다. 9부에서 본 Go 의 전파기(9부)도 요청 쪽 metadata 를 옮깁니다. 이 책의 예산 확장은 스펙 본문(§4.6.1)을 따라 메시지 쪽에 둡니다.

활성화는 요청마다 세 걸음 — 요청 머리글, 에이전트의 판단, 응답 머리글

"Extensions default to being inactive" — 확장은 꺼진 채로 시작하고, 요청 하나마다 켜집니다(topics/extensions.md, Extension Activation).

  • 스펙 본문(specification.md)이 정하는 것은 ① 뿐입니다 — A2A-Extensions 는 "클라이언트가 이 요청에 쓰고 싶은 확장 URI 의 쉼표 목록"(§3.2.6, §14.2.2). ② 와 ③ 의 응답 머리글(SHOULD)은 topics/extensions.md 에만 있습니다.
  • 모르는 확장을 청하면 "SHOULD ignore the extension … and proceed without it" 입니다(§4.6.3). 예외가 required — 이 장의 끝에서 봅니다.

머리글은 바인딩마다 같은 이름 — HTTP 머리글 또는 gRPC 메타데이터, 여러 값은 쉼표 한 줄

  • §3.2.6 은 서비스 매개변수(service parameter)의 이름에 모두 a2a- 를 붙인다고 합니다 — 다른 계층의 머리글과 섞여도 겹치지 않게입니다. 13부의 gRPC 3장에서 응답 쪽(켜진 확장)은 TS 가 머리 메타데이터, Go 가 꼬리 메타데이터에 실었습니다(13부).
  • 스펙의 작은 어긋남 — §14.2.1·§14.2.2 의 등록 항목은 근거를 "Section 3.2.5" 로 적었지만, 서비스 매개변수는 §3.2.6 입니다(§3.2.5 는 Metadata).

모르는 확장을 청해도 세 서버는 그냥 일한다 — 응답에 켜진 확장도 없다

확장을 하나도 적지 않은 완성 숙소 에이전트 셋에 A2A-Extensions: https://other.example/ext/x/v1 을 달고, 예산 metadata 가 든 메시지(2장의 것)를 보냈습니다.

§4.6.3 의 SHOULD 그대로 — 셋 다 TASK_STATE_COMPLETED 이고 응답에 A2A-Extensions 가 없습니다. 메시지의 extensions·metadata 도 거절하지 않고 이력에 그대로 두었습니다(4부에서 본 것, 4부). 확장을 모르는 에이전트에게 확장 데이터는 그저 짐입니다.

required: true 면 켜지 않은 요청을 거절해야 한다 — ExtensionSupportRequiredError(-32008)

1장 퀴즈

Q. 확장을 하나도 적지 않은 세 서버에 A2A-Extensions 머리글로 모르는 확장을 청했습니다. 세 서버는 무엇을 돌려주었고, 응답에 A2A-Extensions 머리글이 있었습니까? 그것이 스펙의 어느 문장과 맞습니까?

A. 셋 다 TASK_STATE_COMPLETED 인 Task 를 돌려주었고, 응답에는 A2A-Extensions 가 없었습니다(실험). 지원하지 않는 확장은 "SHOULD ignore the extension for that interaction and proceed without it"(§4.6.3)이고, 켠 것이 없으니 켜진 목록을 알릴 것도 없습니다.

예산 확장 budget/v1 의 계약 — 메시지에 상한을 싣고, 견적에 판정을 받는다

확장의 명세는 확장을 만든 쪽이 씁니다(topics/extensions.md 의 Extension Specification — URI, params 의 뜻, 오가는 데이터의 모양, 흐름). 이 책의 것은 이렇습니다.

실행기에서 올린 A2A 오류 — ExtensionSupportRequiredError·InvalidParamsError 는 그대로 JSON-RPC 오류가 되어 클라이언트에 가지만, 저장소에는 그 요청의 작업이 FAILED 로 남습니다(7부). 서버 stderr 에는 생산자·소비자의 추적 정보(traceback)가 두 벌 찍힙니다. TS·Go 는 이 검사를 실행기 앞에서 합니다.

바꿔 끼우는 모듈 — 14/budget_common.ts 는 진짜 agents/common.ts 를 모두 다시 내보내고 serve 만 바꿉니다. 그 serve 가 declare(card) 뒤 실행기를 Budget 으로 감싸 진짜 serve 에 넘깁니다. 해석 훅은 13부의 것과 같습니다(13부).

TypeScript — 버스를 Proxy 로 감싸고, addActivatedExtension 으로 켰다고 알린다

SDK 가 먼저 한 일 — requestedExtensions 에는 카드에 적은 것만 남아 있고(server/index.js:2816), 필수 확장을 청하지 않은 요청은 실행기에 오기 전에 -32008 로 돌아갔습니다(:2776). addActivatedExtension 은 express 처리기가 응답 머리글로 옮깁니다(server/express/index.js:3428).

Go — a2a.AgentExtension 을 카드에, 이벤트 타입 스위치로 아티팩트에

map[string]any 만 — 작업 저장소가 gob 으로 깊은 복사를 하므로 metadata 에는 JSON 그대로의 값(맵·float64·bool)만 넣습니다(9부). 상한은 요청 JSON 에서 온 float64 그대로입니다.

Go — 실행기의 이벤트 열(iter.Seq2)을 한 겹 감싼다

필수 검사는 SDK 가 — common.Serve 가 카드의 Capabilities 를 WithCapabilityChecks 로 넘기므로, Declare 가 적은 Required 를 SDK 가 봅니다(a2asrv/intercepted_handler.go:328). Activate 는 JSON-RPC 에서는 아무 데도 나가지 않습니다(1장) — 그래도 부르는 것은 gRPC 로 띄우면 꼬리 메타데이터가 되기 때문입니다.

머리글 없이 보내면 셋 다 판정하지 않는다 — metadata 는 이력에만 남는다

세 서버를 띄우고 카드를 읽은 뒤, 같은 메시지(rpc/budget.json — 상한 2,000,000원)를 A2A-Extensions 없이 한 번, 달고 한 번, 마지막으로 머리글은 달았는데 limit 이 없는 메시지(rpc/nolimit.json)를 보냈습니다.

켜지 않은 확장은 없는 확장 — 셋 다 견적 아티팩트("name": "숙소 견적")에 within 이 없습니다. 실행기의 첫 갈림(requested_extensions 등)이 머리글만 보았기 때문입니다. 메시지의 extensions 와 metadata 는 이력에 그대로 남았습니다.

머리글을 달면 견적에 판정이 붙는다 — 2,100,000원은 상한 2,000,000원을 넘는다

같은 메시지에 A2A-Extensions: …/budget/v1 를 달았습니다(rpc/budget.headers). 파이썬 서버의 주고받음에서 머리글·상태·견적 아티팩트의 확장 칸만 골랐습니다.

  • 아티팩트에 "extensions": [URI] 와 metadata[URI] = {"limit": 2000000.0, "within": false} 가 붙었습니다. 견적의 total(2,100,000)은 실행기가 낸 그대로입니다 — 확장은 견적을 바꾸지 않고 판정만 더했습니다.
  • 응답에 A2A-Extensions 머리글이 없습니다. 파이썬 SDK 에는 켰다고 알릴 길이 없기 때문입니다(1장).

TS 서버만 응답 머리글로 켜진 확장을 알렸다 — 판정은 셋이 같다

  • TS 는 addActivatedExtension 이 응답 머리글 A2A-Extensions: …/budget/v1 이 되었습니다(topics/extensions.md 의 SHOULD). Go 의 Activate 는 JSON-RPC 응답에 나가지 않았습니다.
  • 상한은 TS·Go 가 2000000, 파이썬이 2000000.0 입니다 — 확장의 데이터도 Struct 를 거치면 숫자가 실수가 됩니다. 계약에 "정수" 라고 적었다면 받는 쪽은 2000000.0 도 정수로 읽어야 합니다.

켰는데 상한이 없으면 — 파이썬·Go 는 -32602, TS 는 FAILED 작업

셋째 요청은 머리글로 확장을 켰지만 metadata 가 없습니다. 세 겉층 모두 같은 자리(limit 검사)에서 같은 뜻의 오류를 냈는데, 와이어에 나간 모양이 갈렸습니다.

TS 실행기는 오류 코드를 낼 수 없다 — TS SDK 는 execute 안의 어떤 throw 도 FAILED Task 로 바꿉니다(8부). 확장의 규칙을 어긴 요청을 JSON-RPC 오류로 거절하려면, TS 에서는 실행기보다 앞(express 미들웨어나 요청 처리기)에서 막아야 합니다. Go 는 감싼 오류의 글(err.Error())을 그대로 message 에 실었습니다.

필수로 띄우고 머리글 없이 보내면 셋 다 -32008 — 막은 자리와 글이 다르다

같은 세 서버를 --required 로 띄워 카드에 "required": true 를 적었습니다. 머리글 없는 SendMessage, 머리글을 단 SendMessage, 머리글 없는 GetTask 를 보냈습니다.

§3.3.4 의 MUST 는 셋 다 지켰다 — 다만 파이썬은 SDK 가 아니라 우리 겉층의 raise 입니다. 머리글을 달면 필수 확장도 선택일 때와 똑같이 판정이 붙습니다.

필수 확장은 어느 메서드까지 막나 — Go 는 GetTask 도 막았다

셋째 요청은 없는 작업을 묻는 GetTask 입니다. 확장과 아무 상관 없는 조회인데, 답이 갈렸습니다.

  • 파이썬·TS 는 -32001(작업 없음) — 필수 검사가 메시지를 받는 길에만 있어(파이썬은 우리 실행기, TS 는 _createRequestContext) 다른 메서드는 막지 않습니다. Go 는 -32008 — checkRequiredExtensions 가 처리기의 모든 메서드에 걸려 있습니다(intercepted_handler.go:93·134·193·320).
  • 스펙(§3.3.4)은 "client does not declare support for it" 일 때라고만 하고 메서드를 가리지 않습니다. 필수 확장을 단 Go 에이전트에게는 GetTask·CancelTask·ListTasks 에도 머리글을 실어야 합니다 — 클라이언트 쪽 활성기(a2aext.NewActivator)는 호출마다 싣습니다.

클라이언트 — 파이썬: 카드를 보고, metadata 를 싣고, 머리글은 호출 맥락으로

Q. 어떤 클라이언트가 패치 번호까지 붙여 A2A-Version: 1.0.1 을 보낸다고 합시다. 이 장의 여섯 서버 가운데 어느 것이 거절했고, 그 거절은 스펙의 어느 문장과 어긋납니까?

옛 판 에이전트 흉내 ① 파이썬 — 카드에 0.3 문 하나, 라우트에 호환 스위치

세 서버 모두 완성 숙소 에이전트의 카드와 실행기를 빌려, 카드에는 같은 주소의 판 0.3 JSON-RPC 문 하나만 적습니다. v0.3 만 아는 옛 에이전트처럼 보이게 하되, 뒤의 처리기는 v1.0 그대로입니다.

카드 경로는 그대로 — create_agent_card_routes 가 카드를 내보낼 때 0.3 인터페이스를 찾아 v0.3 의 꼭대기 칸(url·preferredTransport·protocolVersion)을 섞어 넣습니다(agent_card_to_dict). 우리가 따로 할 일이 없습니다.

② TypeScript — 카드 경로에 옛 카드 라우터를 먼저, JSON-RPC 에 legacyCompat

8부의 교훈 — 스위치만 켜고 카드에 0.3 인터페이스가 없으면 옛 요청이 판 검사에서 -32009 로 막혔습니다(8부). 여기서는 카드의 문이 0.3 하나뿐이라, 거꾸로 A2A-Version: 1.0 요청이 막힙니다 — validateVersion 이 카드의 판과 견주기 때문입니다(server/express/index.js:2164, 소스로 읽은 것 — 이 장에서는 보내지 않았다). 띄우는 것은 13부와 같은 해석 훅입니다.

③ Go — 처리기 하나에 두 문, 판 머리글로 가르는 것은 우리가

SDK 는 문을 둘 줄 뿐 — a2asrv.NewJSONRPCHandler 와 a2av0.NewJSONRPCHandler 는 같은 요청 처리기를 받는 서로 다른 http.Handler 입니다. 9부의 소스 읽기처럼 경로를 나눠 달면 되지만, 파이썬·TS 처럼 한 주소로 받으려고 판 머리글로 가르는 함수를 우리가 썼습니다(빈 값이나 0.3 이면 옛 처리기 — §3.6.2).

옛 카드 — 파이썬·Go 는 늘 두 판을 섞고, TS 는 판 머리글에 따라 바꾼다

세 서버의 카드를 판 머리글 없이(v0.3 클라이언트처럼) 한 번, A2A-Version: 1.0 으로 한 번 받았습니다. 주소와 판에 관한 칸만 골랐습니다.

  • TS 는 머리글이 없으면 v0.3 모양(꼭대기에 url·preferredTransport·protocolVersion, 그 뒤에 supportedInterfaces 도 함께 — embedV1Interfaces), 1.0 이면 v1.0 카드만 냈습니다. 판 머리글이 카드의 모양까지 고르는 것은 TS 뿐입니다.
  • 파이썬과 Go(go-wire)는 두 번 모두 같은 섞인 카드 — v1.0 의 supportedInterfaces 와 v0.3 의 꼭대기 칸이 한 JSON 에 있습니다. v0.3 클라이언트는 모르는 칸을 버리고, v1.0 클라이언트는 supportedInterfaces 를 읽습니다.

맨손 v0.3 요청 — 세 서버 모두 v0.3 의 말로 답했다

v0.3 꼴 요청(rpc/v03_send.json — message/send, kind, "role": "user")을 판 머리글 없이 보냈습니다.

실행기는 v1.0 그대로 — 숙소 실행기는 세 서버 모두 v1.0 객체만 받았고(서버 출력의 [숙소] 견적 줄), 번역은 처리기 바깥의 호환 계층이 했습니다(7부). 답은 "kind": "task", "state": "completed" — v0.3 의 모양입니다.

v1.0 SDK 클라이언트로 옛 피어에게 — 파이썬은 그대로, TS 는 두 곳에 legacyCompat

Go — 팩토리에 a2av0.WithJSONRPCTransport 를 끼운다

판 0.3 짝의 전송 — 이 옵션은 WithCompatTransport("0.3", JSONRPC, …) 로 팩토리의 전송 표에 (판, 바인딩) 짝 하나를 더합니다(a2acompat/a2av0/jsonrpc_client.go:37). 팩토리는 카드 인터페이스의 판·바인딩으로 이 표를 찾고, 정확한 짝이 없으면 같은 Major 의 전송을 씁니다(a2aclient/factory.go:179).

3×3 — 아홉 칸 모두 v0.3 으로 말해 같은 견적을 받았다

  • 세 클라이언트 모두 "method": "message/send" 와 A2A-Version: 0.3 을 보냈습니다. 파이썬은 설정 없이, TS·Go 는 켠 호환 전송으로 — 카드의 판이 0.3 하나뿐이라 셋 다 그것을 골랐습니다.
  • 카드를 받을 때는 파이썬·TS 가 A2A-Version: 1.0 을, Go 는 아무 판도 싣지 않았습니다(9부). 그래서 TS 서버는 Go 클라이언트에게 v0.3 모양의 카드를 주었고(ts-wire), Go 의 해석기는 그 안의 supportedInterfaces 를 읽어 문제없이 이어 갔습니다.

Q. 이 장의 TS 서버에서 카드를 curl 로 받는데, 한 번은 머리글 없이, 한 번은 -H 'A2A-Version: 1.0' 을 달았습니다. 두 응답에서 카드 꼭대기의 url 칸은 어떻게 달랐고, 왜 그렇습니까?
