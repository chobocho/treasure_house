파이썬 — 요청마다 제 타입, Delete 를 두 번

11/crud.py 는 설정 둘(요청에 실은 hook-1·tok-1, Create 한 hook-2·tok-2)을 단 작업에 아래를 차례로 합니다. 끝에는 중계기(4장)가 받은 것을 토큰마다 셉니다.

줄 세우는 까닭 — §3.1.9 는 목록의 차례를 정하지 않습니다. Go 서버는 설정을 맵에서 꺼내 실행마다 차례가 다르므로(3장), 세 클라이언트 모두 찍기 전에 토큰으로 줄 세웁니다. 캡처가 실행마다 같게 하려는 것이고, 서버가 준 차례는 아닙니다.

TypeScript — List 만 이름이 홑수, listTaskPushNotificationConfig

  • TS 클라이언트의 메서드 이름은 listTaskPushNotificationConfig — 스펙의 메서드 이름(…Configs)과 달리 끝에 s 가 없습니다(client/index.d.ts:123). 요청 타입은 ListTaskPushNotificationConfigsRequest 입니다.
  • 요청 타입의 pageSize·pageToken 은 선택 필드가 아니라 0·"" 까지 적어야 타입 검사를 지납니다. 서버가 그 둘로 무엇을 하는지는 설정 목록의 페이지에서 봅니다.

Go — ListTaskPushConfigs 는 설정 슬라이스만 돌려준다

  • Go 클라이언트의 ListTaskPushConfigs 는 []*a2a.PushConfig 를 돌려줍니다(a2aclient/client.go:181). 응답의 nextPageToken 은 호출하는 쪽에 닿지 않습니다 — 서버가 페이지를 나눠도 다음 페이지를 청할 길이 없습니다.
  • 오류는 errors.Is 로 갈라 봅니다(9부) — 마지막 Get 이 어느 오류로 돌아왔는지는 없는 설정에는 Go 만 -32603 에서 봅니다.

지운 설정에는 알림이 가지 않고, 두 번 지워도 오류가 없다

교통 에이전트 셋(단계 하나 2초)에 제 언어의 클라이언트를 붙였습니다. 파이썬 클라이언트 → 파이썬 서버의 출력입니다.

  • tok-1 은 SUBMITTED Task 한 건만 받았습니다 — 요청에 실은 설정이라 첫 Task 는 받았고(3장), 첫 단계(2초 뒤) 전에 지워져 그 뒤로는 받지 못했습니다. §3.1.10 의 "No further notifications" 그대로입니다.
  • 둘째 Delete 도 오류 없이 지나갔습니다 — "MUST be idempotent". 지운 뒤의 Get 은 TaskNotFoundError 입니다.
2초는 여유다 — Delete 가 첫 단계보다 먼저 닿는다는 것은 이벤트로 맞춘 것이 아니라 단계 사이 2초에 기댄 것입니다(3장과 같은 여유). 기계가 2초 넘게 멈추면 tok-1 이 한 건 더 받습니다.

세 서버가 같다 — 다른 것은 지운 설정을 다시 Get 했을 때의 답

  • 목록 둘 → 지우기 둘 → 목록 하나, 지운 tok-1 은 한 건 — 세 서버의 줄이 같습니다.
  • 지운 설정의 Get 만 갈렸습니다. TS 는 어느 설정이 없는지까지 적고, Go 는 push config not found 를 내부 오류로 돌려줬습니다(ErrInternalError: true). 까닭은 없는 설정에는 Go 만 -32603 에서 봅니다.

와이어의 List 와 Delete — 목록에 nextPageToken 이 없고, 지우기의 답은 null

파이썬 서버 앞 탭의 첫 List 와 첫 Delete 입니다.

  • 답은 configs 하나뿐 — TS 서버도 같은 모양입니다. 파이썬은 토큰을 채우지 않고, TS 는 nextPageToken: "" 를 채우지만(server/index.js:3320) 빈 문자열은 ProtoJSON 에서 빠집니다.
  • Delete 의 답은 파이썬·TS 모두 "result": null 입니다. Go 서버는 이 실행에서 탭 밖인데, 설치본은 Delete 의 결과를 비워 두고(a2asrv/jsonrpc.go:122) result 필드에 omitempty 를 달아(internal/jsonrpc/jsonrpc.go:229) result 키 없이 답합니다. §3.1.10 이 "implementation-specific" 이라 한 자리를 셋 다 비워 뒀습니다.

설정 목록의 페이지는 아무도 나누지 않는다 — 스펙의 MAY

요청에는 pageSize·pageToken 이 있습니다(proto ListTaskPushNotificationConfigsRequest). 세 SDK 서버가 그것으로 무엇을 하는지는 설치본에서 읽었습니다.

Q. 웹훅을 바꾸려는 클라이언트가 옛 설정을 Delete 하고, 응답을 못 받아 같은 Delete 를 한 번 더 보냈습니다. 둘째 Delete 의 답은 무엇이고, 옛 웹훅은 그 뒤에 알림을 받습니까?

A. 세 서버 모두 둘째 Delete 에도 오류를 내지 않습니다(답은 파이썬·TS 가 "result": null, Go 는 result 키 없이 — 와이어) — §3.1.10 의 "MUST be idempotent"(실행의 Delete hook-1 (2) → 오류 없음). 옛 웹훅은 지운 뒤로 아무것도 받지 않습니다 — 지운 tok-1 은 세 서버 모두 지우기 전의 SUBMITTED Task 한 건뿐이었습니다(세 서버).

5부에서 본 것 → 세 취소 처리기 → SDK 가 실행기를 멈추는 길 → 이벤트에 맞춘 실험 → 파이썬 → TS·Go → 같은 CANCELED 두 번 → 정리

세 취소 처리기 — 하는 일은 CANCELED 를 싣는 것 하나

교통 에이전트의 취소 처리기입니다. 1장에서 미뤄 둔 자리입니다.

멈추게 하는 것은 셋이 다르다 — 파이썬·Go 의 처리기는 상태만 싣고, 달리던 execute 를 멈추는 것은 SDK 입니다(다음 슬라이드). TS 만 우리 손으로 멈춥니다 — common.ts 의 cancel 이 up.stop.abort() 를 부르면 pause 가 false 를 돌려줍니다(1장).

SDK 가 실행기를 멈추는 길 — 파이썬은 작업을 취소하고, Go 는 ctx 를 닫는다

CancelTask 를 받은 세 요청 처리기가 하는 일을 설치본에서 따라갔습니다.

실험 — 구독 스트림에 첫 WORKING 이 오면 취소한다

11/cancel_watch.py 는 SDK 없이, 웹훅 설정을 실어 배차를 맡기고 SubscribeToTask 스트림을 엽니다. 스트림을 읽는 스레드입니다.

시간이 아니라 이벤트 — 취소하는 때는 "첫 WORKING 이 스트림에 왔다" 입니다(working.set()). 몇 초 쉬어 보지 않고, 5부의 GetTask 엿보기와 달리 묻지도 않습니다. 끝은 스트림이 닫히는 것과 중계기의 /wait 로 맞추고, timeout=8 은 스트림이 닫히지 않을 때를 위한 안전판일 뿐입니다. 취소 전에는 첫 WORKING 푸시가 중계기에 닿았는지도 봅니다(hooked, 중계기의 /seen 을 0.05초마다). TS 서버가 푸시를 보낸 뒤 찍는 줄이 [교통] 취소 와 자리를 바꾸지 않게 하려는, 이 장에서 하나뿐인 짧은 쉼입니다.

파이썬 서버 — 구독자도 웹훅도 CANCELED 를 받았고, 스트림은 닫혔다

  • 스트림은 task SUBMITTED → 첫 단계 → statusUpdate CANCELED 배차를 취소했습니다 로 끝나고 닫혔습니다. SDK 설명의 "not guaranteed" 는 이 실행에서는 일어나지 않았습니다. SDK 는 실행기의 cancel 을 먼저 기다려 "the still-open event queue" 에 끝 상태가 실리게 한다고 적었습니다(active_task.py:813 의 주석, SDK 가 멈추는 길). 그래도 구독자는 CANCELED 가 안 올 수 있다고 보고, 스트림이 닫히면 GetTask 로 확인합니다.
  • 웹훅도 같은 세 이벤트를 받았습니다. 서버 출력에는 둘째 단계가 없습니다 — 실행기가 첫 쉼에서 멈췄습니다.

TS·Go 서버 — 스트림은 같고, TS 의 웹훅만 CANCELED 를 두 번 받았다

  • 세 서버의 구독 스트림이 줄까지 같습니다 — 취소도 스트림에서는 상태 이벤트 하나입니다(10부의 닫힘 규칙 그대로).
  • TS 서버만 웹훅에 statusUpdate CANCELED 를 두 번 보냈습니다. 그래서 이 실행만 끝 알림 둘을 기다리게 했습니다(명령 끝의 2) — 한 건만 기다리면 둘째가 클라이언트가 묻는 때에 따라 보이기도 하고 안 보이기도 합니다.

같은 CANCELED 두 번 — TS SDK 는 한 이벤트를 두 고리가 처리한다

중계기 앞 탭에 남은 TS 서버의 마지막 두 POST 입니다.

  • 두 몸통의 messageId(<id7>)까지 같습니다 — 같은 이벤트를 두 번 보낸 것입니다. 실행을 처리하던 고리(_processEvents, server/index.js:2833)와, cancelTask 가 같은 버스에 새로 붙인 고리(:3227)가 이벤트마다 푸시를 보내기 때문입니다.
  • 스펙은 이것을 미리 말해 둡니다 — 수신기는 "SHOULD process notifications idempotently, as duplicate deliveries may occur"(§4.3.3). 상태 메시지의 messageId 가 같으면 같은 알림으로 볼 수 있습니다.

Q. 웹훅으로 받은 CANCELED 마다 "취소 안내 메일" 을 보내는 수신기가 있습니다. TS 교통 에이전트의 작업을 하나 취소하면 메일은 몇 통 나가고, 어떻게 막습니까?

필수 필드가 많다 — ts-proto 의 ListTasksRequest 는 tenant·contextId·status·pageToken·statusTimestampAfter 가 선택이 아닙니다. "필터 없음" 도 빈 값으로 적어야 합니다 — 그래서 ALL 을 하나 두었습니다.

Go — ListTasks(ctx, &a2a.ListTasksRequest{…}), 이력 길이만 포인터

HistoryLength *int — "주지 않음" 과 "0" 을 가르려고 포인터입니다(a2a/core.go:858). PageSize 는 포인터가 아닌 int 라 0 을 보내면 "주지 않음" 이 됩니다. 그 대가는 pageSize 0 과 101 에서 봅니다.

새것부터 셋 — 걸러도, 한 페이지씩 넘겨도 차례가 같다

단계 0.1초의 교통 에이전트 셋에 제 언어의 클라이언트를 붙였습니다. 파이썬 서버입니다.

  • 차례는 list-c → list-b → list-a, 마지막에 만든 것부터입니다. pageSize=1 로 넘겨도 같은 차례이고, 셋째 페이지에서 next "" — §3.1.4 의 "empty string" 이 끝 표시입니다.
  • 아티팩트는 청하지 않으면 0, includeArtifacts 를 켜면 배차 확인서 하나씩(거절한 list-b 는 0). historyLength=0 이면 이력이 비어 첫 메시지 자리가 - 입니다.

세 서버가 같은 목록 — 다른 것은 거절한 작업의 이력 수 하나

  • 필터·차례·페이지·totalSize 가 세 서버에서 같습니다.
  • 거절한 list-b 의 이력이 TS 만 둘입니다 — TS 는 거절 메시지를 받자마자 이력에도 붙입니다(5부). 파이썬·Go 는 사용자 메시지 하나뿐입니다.

와이어의 목록 — nextPageToken: "" 은 셋 다 싣고, artifacts 는 셋 다 뺀다

끝의 curl 이 {"contextId": "ctx-b", "historyLength": 1} 로 물은 답입니다.

  • "MUST always be present" 를 셋 다 지켰습니다. ProtoJSON 은 빈 문자열을 빼는데, 파이썬은 목록에서만 기본값까지 다 찍게 바꿔 이것을 지킵니다(always_print_fields_with_no_presence=True, server/routes/common.py:39).
  • 그 대가로 파이썬의 목록 속 메시지에만 "filename": ""·"mediaType": ""·"extensions": [] 가 붙었습니다 — GetTask 로 받은 같은 메시지(1장)에는 없던 것입니다. artifacts 는 그 뒤에 따로 지웁니다(:43).

pageSize 0 과 101 — 파이썬·TS 는 -32602, Go 는 0 을 "50" 으로, 101 은 -32600

같은 curl 의 둘째·셋째("pageSize": 0·101)입니다.

  • proto 는 optional int32 page_size 에 "The minimum value is 1" 이라 적었습니다. 0 을 보낸 것은 "주지 않음" 과 다릅니다 — 파이썬·TS 는 그렇게 읽어 거절했고, Go 는 필드가 int 라 0 과 없음을 가르지 못해 기본 50 으로 셋을 다 줬습니다(taskstore/inmemory.go:197).
  • 101 은 셋 다 거절했지만 코드가 갈립니다 — Go 는 a2a.ErrInvalidRequest(-32600), 둘은 -32602. 요청 모양은 맞고 값이 틀렸으니 JSON-RPC 의 뜻으로는 -32602 가 맞습니다.

Q. 클라이언트가 pageSize 를 정하지 않으려고 0 을 보냈습니다. 세 서버의 답은 어떻게 다르고, 클라이언트는 어떻게 보내야 합니까?

A. 파이썬·TS 서버는 -32602("minimum page size is 1", "pageSize must be between 1 and 100")로 거절하고, Go 서버만 기본 50 으로 목록을 줍니다(pageSize 0·101). "정하지 않음" 은 0 이 아니라 필드를 아예 빼는 것입니다 — optional int32 이고, 빼면 "at most 50"(§3.1.4)입니다.

웹훅 보안

양쪽의 의무 → SSRF → 파이썬의 검사기 → 검사를 켠 에이전트 → Go SDK 의 보내기 → 세 SDK 의 SSRF → 토큰과 Authorization → 서명 → 다시 보내기 → 우리 Go 보내기의 결함 → 고친 코드 → 고친 뒤의 와이어 → 정리

웹훅은 양쪽이 서로를 의심해야 한다 — §13.2 의 두 목록

푸시에서는 에이전트가 클라이언트가 준 주소로 먼저 연결합니다. 보내는 쪽은 주소를 믿을 수 없고, 받는 쪽은 보낸 이를 믿을 수 없습니다.

에이전트(보내는 쪽)클라이언트(받는 쪽)
"MUST include authentication credentials … as specified in PushNotificationConfig.authentication""MUST validate webhook authenticity using the provided authentication credentials"
"SHOULD validate webhook URLs to prevent SSRF" — 사설 대역·localhost·링크 로컬 거절, 허용 목록"SHOULD verify the task ID in the payload matches an expected task"
시간 제한 SHOULD(10~30초), 지수 백오프 재시도 SHOULD2xx MUST, 멱등 SHOULD, 속도 제한 SHOULD, HTTPS SHOULD
§4.3.3 과 조금 다르다 — 같은 일을 §4.3.3 은 "Clients MUST validate the task ID"(4장), §13.2 는 SHOULD 로 적었습니다. 재시도도 §4.3.3 은 MAY, §13.2 는 SHOULD 입니다. 이 장은 둘 중 엄한 쪽을 기준으로 봅니다.

SSRF — 에이전트가 제 안쪽 망으로 POST 하게 만드는 웹훅 주소

서버 쪽 요청 위조(Server-Side Request Forgery)입니다. 웹훅 주소는 클라이언트가 마음대로 적습니다. 그 주소가 http://169.254.169.254/…(클라우드 메타데이터)나 사내 관리 화면이면, 바깥에서는 닿지 못할 곳에 에이전트가 대신 요청을 보냅니다. 표의 기본값 열에서 세 SDK 가 셋으로 갈립니다.

기본값설치본
파이썬 SDK검사하지 않는다 — push_url_validator=None. 검사 함수 validate_push_notification_url 은 들어 있고, 켜는 것은 우리 몫utils/push_url_validator.py:46
TS SDK검사가 없다 — 보내기는 받은 주소로 곧장 fetch 한다server/index.js:2682, dist/ 에 사설 대역 검사 없음(grep)
Go SDK막는다 — HTTPPushSender 의 AllowPrivateNetworks 기본 falsea2asrv/push/sender.go:60
모두 루프백 웹훅 —이 책의 에이전트는 모두 루프백 웹훅에 보냅니다. 한 기계에서 돌리기 때문입니다. 파이썬·TS 는 기본값이 그것을 허락했고, Go 는 SDK 의 보내기를 쓰지 않아(4장) 검사를 건너뛰었습니다. 바깥에 내놓는 에이전트라면 셋 다 검사를 켜야 합니다.

파이썬의 검사기 — 이름을 풀어 사설·루프백·메타데이터 주소를 거절한다

  • 이름(localhost)은 풀어 본 주소로 가립니다. 풀리지 않는 이름도 거절합니다 — "failing closed"(같은 파일의 설명).
  • [::ffff:127.0.0.1] 처럼 IPv6 에 싼 루프백도 걸렀습니다. http·https 가 아닌 주소도 거절했고, 공인 주소만 받았습니다. 연결은 한 번도 하지 않았습니다.

검사를 켠 교통 에이전트 — 루프백 웹훅을 단 SendMessage 는 -32602

11/guarded.py 는 완성 교통 에이전트의 실행기와 카드를 그대로 쓰고, 검사기를 두 자리에 답니다.

받을 때와 보낼 때 두 번 — 처리기의 검사기는 SendMessage·Create 에서 설정을 저장하기 전에(default_request_handler_v2.py:367·:501), 보내는 것의 검사기는 POST 하기 직전에(base_push_notification_sender.py:95) 봅니다. 저장할 때 공인 주소로 풀리던 이름이 나중에 사설 주소로 바뀌어도(DNS 다시 묶기) 보낼 때 다시 걸립니다. 다만 검사한 뒤 httpx 가 이름을 한 번 더 풀어 연결하므로, 그 사이의 틈까지 막지는 못합니다 — Go SDK 와 다른 점입니다(막는 자리는 연결하는 순간).

Go SDK 의 보내기 — 기본값은 막고, 열면 Bearer·Basic 만 싣는다

11/guard 는 push.HTTPPushSender 를 직접 불러 넷을 보냅니다(설정의 토큰은 tok-ok, 인증은 Bearer).

막는 자리는 연결하는 순간 — 그리고 토큰 머리글은 X- 없이

  • ①은 연결하기 전에 막혔습니다(dial tcp … blocked address range). 주소를 문자열로 보지 않고, 연결할 때 실제로 고른 IP 를 봅니다(sender.go:97·:99) — 이름을 다시 묶거나 다른 곳으로 넘겨도(redirect) 넘어갈 때마다 다시 봅니다.
  • ②의 Authorization: Bearer hook-secret, ③(Digest)에는 Authorization 이 없습니다 — switch strings.ToLower(config.Auth.Scheme) 가 bearer·basic 만 압니다(sender.go:175).
  • ②·③에 토큰 머리글이 안 보이는 것은 SDK 가 A2A-Notification-Token 에 싣기 때문입니다(sender.go:40) — 와이어 탭은 정해 둔 머리글만 찍고 그 이름은 목록에 없습니다. 대신 ④가 증거입니다: 맞는 토큰을 실었는데도 X-A2A-Notification-Token 을 보는 수신기가 401 을 줬습니다.

둘 다 보내는 것이 스펙에 맞다 — 스펙 어디에도 "authentication 이 있으면 token 을 빼라" 는 말이 없고, 스킴을 bearer·basic 으로 좁히라는 말도 없습니다(proto 주석은 IANA 등록부의 스킴, "case-insensitive"). 그래서 우리 Go 보내기는 파이썬 SDK 와 같은 모양을 골랐습니다.

서명은 스펙에 없다 — 주제 문서의 JWT + JWKS 는 권고일 뿐이고, 세 SDK 모두 하지 않는다

specification.md 에서 웹훅 몸통의 서명을 찾으면 없습니다. 서명(§8.4)은 에이전트 카드의 것입니다.

  • 주제 문서 "Streaming & Asynchronous Operations"(docs/topics/streaming-and-async.md)가 "Example Asymmetric Key Flow (JWT + JWKS)" 를 듭니다 — 에이전트가 알림마다 iss·aud·iat·exp·jti·taskId 를 담은 JWT 를 서명해 Authorization 에 싣고, 수신기는 JWKS 로 검증합니다. HMAC 서명도 예로 듭니다.
  • 세 SDK 의 보내기는 설정에 받은 문자열을 그대로 싣기만 합니다(파이썬 base_push_notification_sender.py, TS _buildAuthHeaders, Go sender.go — 어디에도 jwt·jwks·hmac 이 없습니다).
  • 그래서 지금의 Authorization 은 클라이언트가 정해 준 고정된 비밀입니다. 새면 누구나 같은 머리글로 알림을 위조할 수 있고, 몸통이 바뀌어도 알 수 없습니다. 서명하는 보내기는 12부에서 볼 JWS 로 짤 수 있지만, 수신기와 약속을 따로 해야 합니다.

다시 보내기 — 같은 알림을 두 번 보내도 토큰 검사는 둘 다 통과시킨다

명세 끝의 curl 은 토큰 tok-ok 를 단 같은 몸통(rpc/push_replay.json)을 두 번 보냈습니다.

  • 토큰은 "누가" 만 증명합니다. 엿들은 알림을 그대로 다시 보내면 수신기는 가려내지 못합니다. 주제 문서는 "Notifications SHOULD include a timestamp. The webhook SHOULD reject notifications that are too old" 와 일회용 id(jti)를 권합니다.
  • 몸통에 쓸 만한 것은 statusUpdate.status.timestamp 정도입니다 — 막 만든 SUBMITTED Task 에는 시각이 없었고(5부), TaskArtifactUpdateEvent 에는 시각 필드가 아예 없습니다(proto). 멱등 처리(6장)가 다시 보내기의 피해도 줄입니다.

우리 Go 보내기의 결함 — authentication 을 버리고, 401 에도 말이 없었다

4장에서 탭으로 드러난 두 가지(AuthenticationInfo·401)입니다. 고치기 전의 hookSender 를 그대로 옮겨 둔 11/hookold 로 다시 봅니다 — 설정에 Bearer 와 틀린 토큰을 함께 실었습니다.

직접 짠 보내기의 값 — 이 코드는 §4.3.3 의 MUST 를 어기고(Authorization 없음), 수신기가 401 을 줘도 SendPush → <nil> 뿐 기록 한 줄 없습니다. 보내기를 직접 짜면 SDK 가 해 주던 일을 다 떠안습니다.

고친 hookSender — Authorization 을 싣고, 2xx 가 아니면 적는다

  • 더한 것은 두 토막입니다. cfg.Auth 에 스킴과 자격 증명이 다 있으면 Authorization: {scheme} {credentials}(§4.3.3 의 견본), 스킴만 있으면 싣지 않습니다 — 파이썬 SDK 도 싣지 않고 경고만 남깁니다(base_push_notification_sender.py:109).
  • 2xx 가 아니면 slog.Warn("push rejected", …) — 그래도 nil 을 돌려줘 작업은 계속합니다. 오류를 돌려주면 SDK 가 작업을 FAILED 로 바꾸기 때문이고(4장), 파이썬·TS 도 적기만 합니다.

고친 뒤 — 4장의 같은 실행에 Authorization 이 실리고, 401 마다 한 줄씩

4장의 auth.run 캡처는 고친 에이전트의 것입니다. 그 가운데 Go 쪽 두 자리입니다.

우리 Go 는 파이썬 SDK 처럼 — 파이썬 SDK·우리 Go 는 토큰과 Authorization 을 둘 다 싣고, 거절당하면 적습니다. TS SDK 만 authentication 이 있으면 토큰을 버립니다(4장). 그래서 수신기는 토큰과 Authorization 중 하나만 기대하지 말고, 둘 다 볼 줄 알아야 합니다.

8장 퀴즈

Q. 클라이언트가 웹훅 주소로 http://169.254.169.254/latest/meta-data/ 를 적어 보냈습니다. 파이썬 SDK 의 기본 설정과, 검사기를 켠 판(guarded.py), Go SDK 의 HTTPPushSender 기본값은 각각 어떻게 합니까?

A. 파이썬 SDK 의 기본값(push_url_validator=None)은 검사하지 않고 그 주소로 POST 합니다(SSRF). 검사기를 켜면 그 주소는 거절되고(검사기의 거절 http://169.254.169.254/…), SendMessage 는 -32602 Invalid push notification URL 로 돌아옵니다(켠 판). Go SDK 의 기본값은 연결하는 순간 링크 로컬 주소를 막습니다(①, isBlockedIP).
