7부

공식 SDK — Python

패키지 지도 → 타입 → 실행기(AgentExecutor) → 요청 처리기와 Task 저장소 → 서버 띄우기 → 클라이언트 → 숙소 에이전트 완성판 → 시험 → 이 SDK 만의 것

6부에서 손으로 한 일을, 이번에는 a2a-sdk 로 짓는다

3~5부는 완성 에이전트를 밖에서 두드렸고, 6부는 SDK 없이 같은 일을 손으로 했습니다. 이 부는 파이썬으로 A2A 에이전트를 만들 사람을 위한 부입니다 — 설치된 a2a-sdk 1.2.2 의 소스를 열어 가며, 메아리 에이전트에서 시작해 숙소 에이전트 완성판까지 SDK 로 쌓아 올립니다.

장무엇을

2장타입 — protobuf 메시지로 Message·Part·Task 만들고 읽기
3장실행기(AgentExecutor) — 이벤트 큐에 넣는 일, TaskUpdater
4장요청 처리기와 Task 저장소 — DefaultRequestHandler, InMemoryTaskStore
5장서버 띄우기 — 라우트 팩토리, Starlette 와 uvicorn, 카드
6장클라이언트 — create_client, 막는 호출과 스트림, 답 읽기
7장숙소 에이전트 완성판 — INPUT_REQUIRED·REJECTED, 골든 대조

세 부가 같은 뼈대 — 8부(TypeScript)와 9부(Go)는 이 부와 장 번호·장 제목이 같습니다. 한 언어만 따라가도 되고, 견주고 싶으면 같은 번호의 장을 나란히 펴면 됩니다. 장마다 끝의 "정리" 표가 그 언어의 이름을 같은 줄에 모읍니다. 예제는 ex/py/07/ 에 있고, 단계 파일(step1_echo.py, step2_task.py, …)이 완성 에이전트(ex/py/agents/)로 수렴합니다.

1장

패키지 지도 — 설치본에서 읽는다

몸통과 extra 열한 가지 → 하위 패키지와 줄 수 → 서버 쪽 여섯 칸 → 요청 하나가 지나는 길 → 완성 에이전트가 쓰는 이름 38개 → 이름에서 파일·줄 찾기 → 정리

a2a-sdk 는 몸통 하나에 extra(선택 설치 묶음) 열한 가지다

무엇을 깔았는지부터 셉니다. 패키지 메타데이터(Requires-Dist)를 읽어 늘 따라오는 의존과, extra 이름마다 더 까는 패키지를 나누고, 이 venv 에 있는지 표시했습니다(O 있음, . 없음).

  • 이 책은 a2a-sdk[http-server,grpc,signing]==1.2.2 를 깔았습니다(ex/py/requirements.txt). 서버를 띄우려면 http-server(Starlette·sse-starlette)가 있어야 합니다.
  • 몸통에 protobuf 가 있는 것이 이 SDK 의 성격을 말해 줍니다 — 타입이 proto 에서 생성된 메시지입니다(2장).
  • uvicorn 은 어느 extra 에도 없습니다. ASGI 서버는 따로 고르라는 뜻이고, 이 책은 uvicorn 을 따로 깔았습니다(5장). sql 무리(sqlalchemy)는 이 venv 에 없어 DB 저장소는 9장에서 소스로만 봅니다.

설치본 2만 7천 줄 — 서버가 4할, v0.3 호환이 3할

하위 패키지마다 파이썬 파일 수와 줄 수를 세고, __init__.py 의 문서 문자열 첫 줄을 옆에 붙였습니다. 서버 쪽은 한 층 더 내려갔습니다.

  • server/ 10,663줄 — 이 부 3~5장이 여기서 삽니다. client/ 3,390줄은 6장입니다.
  • compat/ 8,038줄은 v0.3 피어와 말하기 위한 계층입니다(9장, 14부). migrations/ 는 DB 저장소의 스키마 이력입니다.
  • types/ 가 985줄뿐인 것은 생성된 a2a_pb2.py 가 proto 설명자를 바이트로 품고 있어서입니다. 필드 목록은 옆의 a2a_pb2.pyi(편집기용 타입 힌트)에 있습니다.

서버 쪽 여섯 칸 — 우리가 채우는 칸은 하나다

server/ 아래 여섯 하위 패키지가 맡은 일을 이 부의 장과 짝지었습니다. 에이전트를 만드는 사람이 직접 쓰는 것은 실행기 하나이고, 나머지는 조립합니다.

하위 패키지대표 이름하는 일어디서

요청 하나가 지나는 길 — 경로 → 처리기 → 실행기 → 저장소

SendMessage 한 번이 서버 안에서 거치는 칸을 위에서 아래로 그렸습니다. 6부의 맨손 서버가 한 파일에서 하던 일을 SDK 는 이렇게 나눠 맡깁니다.

이벤트가 저장소를 고친다 — 6부에서 본 대로 SDK 판에서는 실행기가 Task 를 직접 저장하지 않습니다. 이벤트를 큐에 넣으면 처리기 쪽(server/agent_execution/active_task.py)이 그것을 받아 저장된 Task 에 반영합니다. 4장에서 이 길을 HTTP 없이 직접 불러 봅니다.

완성 에이전트 다섯이 쓰는 SDK 이름은 38개뿐이다

2만 7천 줄을 다 알아야 에이전트를 만들 수 있는 것은 아닙니다. 완성 에이전트(agents/*.py)의 from a2a… import 를 ast 로 모아, 이름마다 몇 파일이 쓰는지 셌습니다.

  • 서버를 세우는 데 드는 것은 server.* 의 열 개입니다 — 실행기·큐·갱신기·처리기·저장소·경로 둘. 푸시 둘은 교통 에이전트(11부)의 것입니다.
  • client 셋은 기획 에이전트와 ask CLI 가 씁니다(6장). utils.signing 둘은 서명된 카드(12부)입니다.

이름에서 파일과 줄로 — DefaultRequestHandler 의 진짜 이름은 V2 다

소스를 읽으려면 그 이름이 어디 있는지 알아야 합니다. inspect.getsourcefile·getsourcelines 로 이 부에서 쓸 이름의 자리를 찾았습니다.

  • request_handlers/__init__.py 에 DefaultRequestHandler = DefaultRequestHandlerV2 가 있습니다. 옛 처리기는 같은 폴더의 default_request_handler.py 에 LegacyRequestHandler 라는 이름으로 남아 있습니다 — 파일 이름만 보고 열면 다른 클래스를 읽게 됩니다.
  • protobuf 타입은 소스가 없습니다. a2a.proto 의 lf.a2a.v1 패키지에서 생성됐다는 것만 설명자가 알려 줍니다.

1장 퀴즈

Q. DefaultRequestHandler 가 SendMessage 를 어떻게 처리하는지 보려고 server/request_handlers/default_request_handler.py 를 열었습니다. 이 파일을 읽으면 무엇이 잘못되고, 어느 파일의 몇째 줄부터 읽어야 합니까?

A. 그 파일의 클래스는 옛 처리기 LegacyRequestHandler 입니다. 우리가 쓰는 DefaultRequestHandler 는 DefaultRequestHandlerV2 의 별명이고, where.py 가 찾은 자리는 a2a/server/request_handlers/default_request_handler_v2.py:90 입니다(그 줄은 클래스에 붙은 장식자에서 시작합니다).

2장

타입 — protobuf 메시지로 Message·Part·Task 다루기

a2a.types 의 세 무리 → enum 은 int → 메시지를 만드는 세 길 → 와이어 이름은 json_format → = 로 못 넣는 필드 → 넣으면 복사, 꺼내면 참조 → None 대신 빈 값 → oneof 와 enum 의 느슨함 → DataPart 와 Value → Task 만들기 → Task 읽기 → 정리

a2a.types 는 proto 에서 나온 메시지 44개, enum 둘, 오류 13개다

파이썬 SDK 의 타입은 손으로 쓴 클래스가 아니라 a2a.proto 를 protoc 로 돌려 생성한 protobuf 메시지입니다. a2a.types.__all__ 의 이름을 종류별로 나눴습니다.

  • 오류 13개는 a2a.utils.errors 의 예외 클래스를 다시 내보낸 것입니다. 실행기에서 던지면 JSON-RPC 오류 코드가 됩니다(4장).
  • A2ARequest 는 요청 타입 여럿을 | 로 묶은 별명입니다(types/__init__.py). 그 묶음에 ListTasksRequest 는 빠져 있습니다 — 이름을 믿고 "모든 요청" 으로 쓰면 안 됩니다.

enum 값은 int 다 — 사람이 읽을 이름은 Name() 으로 얻는다

enum 두 개의 이름과 수를 폈습니다. proto3 규칙대로 0 은 …_UNSPECIFIED 이고, 와이어에는 수가 아니라 이름이 갑니다(4부).

찍을 때는 이름으로 — 끝난 작업의 print(task.status.state) 는 3 을 찍습니다. 로그에는 TaskState.Name(state), 문자열에서 되돌릴 때는 TaskState.Value("TASK_STATE_COMPLETED") 를 씁니다. 이 부의 예제가 모두 그렇게 찍습니다.

메시지는 키워드 생성자로 — 필드 이름은 proto 의 snake_case

같은 사용자 메시지를 세 길로 만들었습니다. 생성자, 빈 메시지에 채우기, 그리고 a2a.helpers 의 도우미입니다.

  • protobuf 메시지는 값으로 비교합니다 — 생성자로 만든 a 와 하나씩 채운 b 가 같습니다.
  • parts.add(text=…) 는 반복 필드에 새 Part 를 만들어 붙이고 그것을 돌려줍니다.
  • new_text_message 의 role 기본값은 ROLE_AGENT 입니다(helpers/proto_helpers.py:44). 에이전트가 답을 지을 때를 위한 도우미라서, 사용자 메시지를 만들 때는 role=Role.ROLE_USER 를 꼭 줍니다.

와이어 모양(camelCase·enum 이름)은 json_format 이 만든다

파이썬 속성은 message_id, 와이어 필드는 messageId 입니다. 둘 사이를 잇는 것은 protobuf 의 json_format 이고, SDK 도 같은 함수로 주고받습니다(server/routes/jsonrpc_dispatcher.py 의 MessageToDict·ParseDict).

두 이름을 섞지 않는다 — 파이썬 코드에서는 언제나 snake_case, JSON 에서는 언제나 camelCase 입니다. 생성자에 와이어 이름을 주면 ValueError 입니다. ensure_ascii=False 를 빼면 한글이 숙 꼴로 나옵니다.

메시지 필드에는 = 로 넣을 수 없다 — 안쪽을 채우거나 CopyFrom

파이썬 객체처럼 task.status = TaskStatus(…) 로 쓰고 싶어지지만, protobuf 메시지의 하위 메시지 필드는 대입을 받지 않습니다.

  • task.status.state = … 처럼 안쪽 스칼라에 넣으면 status 가 저절로 생깁니다.
  • 통째로 바꿀 때는 CopyFrom, 일부만 덮을 때는 MergeFrom 입니다. TaskUpdater.update_status 도 status.message.CopyFrom(message) 로 상태 메시지를 넣습니다(server/tasks/task_updater.py).

넣으면 복사, 꺼내면 참조 — 따로 두려면 CopyFrom

이력에 메시지를 넣은 뒤 원본을 고치고, 이력에서 꺼낸 것을 고치고, 사본을 떠 둔 뒤 또 고쳤습니다.

  • append 는 넣는 순간의 값을 복사합니다 — 넣은 뒤 msg 를 "40명" 으로 바꿔도 이력은 "30명" 입니다.
  • task.history[0] 은 task 안의 그 객체입니다 — 고치면 task 가 바뀝니다("50명").
  • 완성 에이전트의 begin 이 ctx.current_task 를 바로 고치지 않고 Task() 에 CopyFrom 한 다음 쓰는 까닭입니다(3장).

None 이 없는 세계 — 안 채운 문자열은 "" 이고, 스칼라에는 HasField 가 없다

contextId 없이 온 메시지의 context_id 를 읽으면 무엇이 나올까요. "없음" 을 묻는 법도 필드 종류마다 다릅니다.

  • proto3 의 보통 스칼라는 "안 보냄" 과 "빈 값" 을 가르지 않습니다. 그래서 검사는 if not msg.context_id: 입니다 — SDK 도 그렇게 씁니다(params.message.task_id or None, default_request_handler_v2.py 의 _setup_active_task).
  • 하위 메시지는 HasField 로 묻고, 읽기만 해서는 생기지 않습니다. 반대로 생성자에 None 을 주면 안 준 것과 같습니다 — 도우미 new_message 가 task_id=None 을 그대로 넘기는 것이 그 덕입니다(proto_helpers.py:28).

oneof 는 마지막에 넣은 것만 남고, enum 필드는 아무 수나 받는다

Part 의 내용(text·raw·url·data)은 oneof content 입니다(4부). 하나를 넣은 뒤 다른 것을 넣고, enum 필드에 이름과 모르는 수를 넣어 봤습니다.

  • url 을 넣자 text 가 소리 없이 지워졌습니다. 와이어에서 두 내용을 함께 보내면 파이썬 서버는 -32602 로 거절하지만(4부), 파이썬 객체 안에서는 경고 없이 바뀝니다.
  • enum 필드는 이름 문자열도, 정의에 없는 99 도 받습니다. 값 검사는 우리 몫입니다.

DataPart 의 dict 는 Value 를 지나 float 로 돌아온다

숙소 요청을 new_data_part 로 넣고 get_data_parts 로 꺼냈습니다. 와이어에서 본 30.0(4부)이 타입 층에서는 이렇게 생깁니다.

  • 안쪽은 struct_value.fields 라는 map 이고 수는 number_value(double) 하나뿐입니다. 꺼내면 float 입니다.
  • back == req 가 참이라 놓치기 쉽습니다 — 파이썬에서 30.0 == 30 이니까요. 그러나 range(30.0) 은 TypeError 이고, 업무 규칙 choose_lodging 도 그래서 정수를 요구합니다. 견적 실행기(3장)와 완성 에이전트의 as_ints 가 정수로 되돌립니다.
  • Struct 의 키 차례는 프로세스마다 다를 수 있어 sort_keys=True 로 찍었습니다. 와이어 탭이 data·metadata 아래 키를 정렬해 적는 것도 같은 까닭입니다(0부의 정규화 표).

Task 는 new_task_from_user_message 로 — 사용자 메시지가 아니면 거절한다

에이전트 쪽에서 Task 를 짓는 도우미입니다. SUBMITTED 상태, 이력에 그 메시지 하나, id 와 contextId 는 메시지에 있으면 그것을 쓰고 없으면 uuid4 를 짓습니다(proto_helpers.py:277).

세 가지를 검사한다 — 역할이 ROLE_USER 가 아니면, 파트가 없으면, 빈 글 파트가 있으면 ValueError 입니다. 서버 안에서는 처리기가 메시지에 taskId·contextId 를 미리 채워 두므로(3장), 이 도우미가 지은 Task 의 id 는 요청의 것과 같아집니다.

받은 JSON 은 ParseDict 로 — 모르는 필드는 오류, 너그럽게 읽으려면 ignore_unknown_fields

클라이언트 쪽 일입니다. 서버가 보낼 모양(MessageToDict)을 다시 Task 로 읽고, 거기에 스펙에 없는 createdAt 을 하나 끼워 봤습니다(5부에서 본, 어느 SDK 도 안 쓰는 필드입니다).

SDK 안에서도 둘로 갈린다 — 설치본을 보면 서버의 JSON-RPC 디스패처(jsonrpc_dispatcher.py:300)와 카드 읽기(client/card_resolver.py:27)는 ignore_unknown_fields=True 로 읽고, 클라이언트가 JSON-RPC 응답을 읽는 곳(client/transports/jsonrpc.py:83 등)은 그 옵션 없이 읽습니다. 서버가 새 필드를 보태면 파이썬 클라이언트 쪽이 먼저 걸릴 수 있다는 뜻입니다 — 6장에서 클라이언트를 열 때 다시 봅니다.

2장 퀴즈

Q. 실행기에서 ask = up.new_agent_message([…]) 를 만들어 task.history.append(ask) 한 뒤, 깜빡한 말을 보태려고 ask.parts.append(new_text_part("예: 30명")) 을 했습니다. task.history 의 마지막 메시지에는 파트가 몇 개 있습니까?

A. 처음 넣은 그대로입니다. 반복 필드의 append 는 넣는 순간의 값을 복사하므로, 그 뒤에 ask 를 고쳐도 이력의 사본은 바뀌지 않습니다 — types_fields.py 에서 "40명" 으로 고친 뒤에도 이력이 "30명" 이었던 것과 같습니다. 고치려면 task.history[-1] 을 꺼내 고쳐야 합니다(꺼낸 것은 참조).

3장

실행기(AgentExecutor) — 이벤트를 큐에 넣는 일

채울 메서드 둘 → 문서 문자열의 약속 → RequestContext 에서 읽는 것 → 메아리 실행기 → 서버 없이 돌리는 큐 → 넣을 수 있는 이벤트 넷 → 견적 실행기 → 견적이 낸 이벤트 → TaskUpdater 의 손잡이 → 이어 말하기의 begin → 정리

실행기는 메서드 둘 — execute 와 cancel, 둘 다 큐에 이벤트를 넣는다

"에이전트를 만든다" 는 말의 파이썬 SDK 판 뜻은 AgentExecutor 를 상속해 추상 메서드를 채우는 것입니다. 무엇을 채워야 하는지 설치본의 추상 클래스에 물었습니다.

  • 두 메서드 모두 돌려주는 값이 없습니다. 실행기의 결과는 event_queue 에 넣은 이벤트뿐입니다 — 6부 맨손 서버가 목록에 담아 return 하던 것(6부)을 여기서는 큐에 넣습니다.
  • EventQueue 도 우리 쪽에서 보면 메서드 하나(enqueue_event)짜리입니다. 꺼내는 쪽은 처리기가 쥐고 있습니다(server/events/event_queue.py: "The consumer is framework-managed").

execute 의 약속 — 설치본 문서 문자열이 정한 것

server/agent_execution/agent_executor.py 의 execute 문서 문자열은 실행기와 SDK 사이의 계약서입니다. 줄 번호와 함께 옮깁니다.

실행기가 읽는 것은 거의 다 ctx 에 있습니다. 속성 열 개를 쓰임새로 묶었습니다(server/agent_execution/context.py).

메아리 실행기 — Message 하나를 넣으면 그것이 답이다

1단계 에이전트입니다. 받은 글 앞에 "받은 말:" 을 붙여 에이전트 Message 하나를 큐에 넣고 끝냅니다. Task 를 만들지 않으니 즉답형(4부)입니다.

  • new_text_message 는 role 을 ROLE_AGENT 로, messageId 를 uuid4 로 채웁니다. context_id 만 요청의 것을 넘깁니다(4부: 서버 메시지에는 contextId 가 있어야 합니다).
  • Message 만 내는 에이전트에는 취소할 작업이 없으니 cancel 은 UnsupportedOperationError 를 던집니다 — 메서드가 추상이라 비워 둘 수는 없습니다.

서버 없이 실행기 돌리기 — enqueue_event 하나만 채운 큐

실행기는 보통 함수입니다. EventQueue 의 문서 문자열이 길을 알려 줍니다: "To run an executor outside the framework, write a custom subclass"(event_queue.py:34). 받은 이벤트를 찍기만 하는 큐와, 손으로 만든 RequestContext 로 돌립니다.

EventQueue() 를 바로 만들지 않는다 — 추상 클래스를 그대로 부르면 경고와 함께 옛 구현 EventQueueLegacy 가 나옵니다(event_queue.py 의 __new__, "will be removed in a future release"). 실행기를 시험 삼아 돌릴 때는 이렇게 하위 클래스를 씁니다. SDK 서버를 통째로 프로세스 안에서 시험하는 법은 8장입니다.

큐에 넣을 수 있는 것은 넷 — Message 하나, 또는 Task 와 그 갱신들

Event 는 네 타입의 합집합입니다(앞 슬라이드의 출력). 넣는 차례에 따라 두 흐름으로 갈립니다.

흐름넣는 것클라이언트가 받는 것
즉답Message 하나 — 그 뒤엔 아무것도result.message
작업Task 먼저, 그다음 TaskStatusUpdateEvent·TaskArtifactUpdateEvent 여럿result.task(막는 호출) 또는 이벤트 스트림(10부)
차례는 처리기가 검사한다 — 이 PrintQueue 는 무엇이든 받지만, 진짜 처리기는 Message 를 두 번 넣거나 Task 보다 상태를 먼저 넣으면 거절합니다. 일곱 가지 반칙과 그 결과는 4장에서 봅니다.

견적 실행기 — Task 를 먼저 싣고, 나머지는 갱신기(TaskUpdater)로

2단계 에이전트는 DataPart 로 날짜·박 수·인원을 받아 업무 규칙 choose_lodging 을 부릅니다. 결과에 따라 아티팩트를 내고 끝내거나, 까닭을 달아 거절합니다.

  • TaskUpdater(queue, task.id, task.context_id) 는 그 작업의 상태·아티팩트 이벤트를 지어 같은 큐에 넣어 주는 도우미입니다. 큐와 id 만 쥐고 있을 뿐 저장소는 모릅니다.
  • request_of 는 DataPart 를 합치고 nights·headcount 를 정수로 되돌립니다(2장). 빠진 항목을 되묻는 일은 7장의 완성판이 합니다.

견적이 낸 이벤트 — Task, WORKING, 아티팩트, COMPLETED

같은 PrintQueue 로 견적 실행기를 두 번 돌렸습니다. 10월 30일 30명과, 세 숙소가 모두 쉬는 12월 31일입니다.

  • Task 의 id(<id3>)가 ctx.task_id 와 같습니다. RequestContext 가 지은 id 를 메시지에 써 넣었고, new_task_from_user_message 가 메시지의 것을 썼기 때문입니다.
  • 거절은 아티팩트 없이 REJECTED 상태 하나로 끝납니다. 까닭("가능한 숙소가 없습니다")은 상태 메시지에 실렸습니다(5부).

TaskUpdater 의 손잡이 — 상태 하나에 메서드 하나

server/tasks/task_updater.py 의 메서드를 모았습니다. 상태 메서드는 모두 update_status(state, message) 를 부르는 한 줄짜리입니다.

메서드내는 이벤트
submit·start_work상태 SUBMITTED·WORKING
requires_input·requires_authINPUT_REQUIRED·AUTH_REQUIRED (중단 상태 — 7장, 12부)
complete·failed·reject·cancel종료 상태 넷
update_status(state, message, timestamp, metadata)아무 상태나 — 시각을 안 주면 지금(UTC)
add_artifact(parts, artifact_id, name, metadata, append, last_chunk, extensions)아티팩트 갱신 — id 를 안 주면 uuid, 청크는 10부
new_agent_message(parts, metadata)이벤트 아님 — taskId·contextId 를 단 에이전트 Message 를 지어 돌려줄 뿐
종료 뒤의 갱신 — 갱신기는 종료 상태를 한 번 내면 그 뒤의 update_status 를 RuntimeError 로 막습니다. 그러나 그 표시는 갱신기 객체 하나에만 있어서, 새 갱신기로 보내면 저장소의 작업이 WORKING 으로 "되살아납니다"(5부). 실행기 하나에는 갱신기 하나만 둡니다.

이어 말하기 — current_task 를 복사해 쓰고, Task 는 다시 싣지 않는다

같은 taskId 로 두 번째 메시지가 오면 처리기는 저장된 Task 를 ctx.current_task 에 넣어 execute 를 다시 부릅니다. 완성 에이전트 다섯이 함께 쓰는 시작 코드가 그 경우를 가릅니다.

  • current_task 의 이력에는 이번 메시지가 아직 없습니다. SDK 는 그것을 실행기의 첫 상태·아티팩트 갱신이 올 때 저장합니다(active_task.py 의 message_to_save). 그래서 사본(2장)에 직접 붙여 씁니다.
  • 이어 말하기에서 Task 를 다시 큐에 넣으면 SDK 가 "already exists" 를 남기고 이번 사용자 메시지를 이력에서 버립니다 — 5부에서 확인한 이 SDK 의 결함입니다. 숙소 에이전트를 끝까지 짓는 것은 7장입니다.

3장 퀴즈

Q. 견적 실행기는 Task 의 id 를 직접 짓지 않습니다. 그런데 출력에서 Task 의 id 는 어떻게 task_id 줄의 값과 같았습니까? 누가, 언제 지은 id 입니까?

A. RequestContext 의 생성자가 지었습니다. 요청 메시지에 taskId 가 없으면 uuid 를 지어 ctx.task_id 로 두고 메시지의 task_id 에도 써 넣습니다(context.py 의 _check_or_generate_task_id). new_task_from_user_message 는 메시지의 task_id 가 있으면 그것을 쓰므로, 출력의 task_id <id3> 과 Task <id3> 이 같아졌습니다. 서버 안에서는 처리기가 이 생성자를 부르고, Task 의 id 가 다르면 거절합니다(4장의 OtherId).

HTTP 없이 처리기 부르기 — ServerCallContext 하나면 된다

처리기는 보통의 비동기 객체입니다. 2단계 견적 실행기로 처리기를 만들고, SendMessage·GetTask·ListTasks 와 스트림을 직접 불렀습니다. HTTP 서버도, JSON 도 없습니다.

ServerCallContext — "누가, 어떤 HTTP 요청으로" 를 담는 pydantic 모델입니다(server/context.py: state·user·tenant·requested_extensions). 서버에서는 경로가 HTTP 요청으로 지어 넘기고(5장), 여기서는 빈 것(익명)을 씁니다.

막는 호출은 Task 가 종료·중단 상태가 될 때 돌아온다 — returnImmediately 면 첫 Task 에서

  • on_message_send 는 실행기가 낸 이벤트를 따라가다가, Task 의 상태가 종료 넷이나 중단 둘이 되면 그 Task 를 답으로 고릅니다. return_immediately 면 첫 Task(SUBMITTED)에서 멈추고, 실행기는 뒤에서 마저 돕니다(default_request_handler_v2.py 의 on_message_send). 와이어에서 본 모습은 5부입니다.
  • 스트림은 카드의 capabilities.streaming 이 꺼져 있어 처리기가 막았습니다. 그 검사(@validate)는 거절하기 전에 Validation failure: … 를 오류 수준으로 기록합니다(request_handler.py:374).

반칙하는 실행기 일곱 — 차례 넷, 침묵 하나, 예외 둘

3장의 두 흐름을 일부러 어기는 실행기를 썼습니다. 각각을 새 처리기에 물려 SendMessage 를 2초까지 기다리고, 답과 저장소에 남은 작업의 상태를 찍습니다.

차례를 어기면 InvalidAgentResponseError — 저장소에는 FAILED 가 남거나 아무것도 없다

  • 차례 검사는 처리기 쪽 소비자가 합니다(active_task.py 의 _handle_message_event·_handle_task_modification_event). 와이어에서는 -32006 입니다(오류 표).
  • Task 를 이미 저장한 뒤의 반칙(MessageAfterTask)은 그 작업을 FAILED 로 남깁니다. Task 를 싣기 전의 반칙은 아무것도 남기지 않습니다.
  • OtherId 는 실행기의 잘못인데 InvalidParamsError, 와이어로는 -32602 Invalid params 입니다 — 클라이언트의 인자가 틀렸다는 코드입니다. 검사하는 곳이 server/tasks/task_manager.py:229 라서 그렇습니다.

아무것도 내지 않은 실행기는 막는 호출을 끝없이 붙잡는다

  • Silent — 이벤트 없이 돌아간 실행기에 대해 처리기는 "Task 가 만들어지기를" 기다립니다(active_task.py:967, await self._task_created.wait()). 아무도 만들지 않으니 2초 제한을 건 이 예제가 아니면 답이 오지 않습니다. 실행기의 모든 갈래가 무언가를 넣는지 꼭 확인합니다.
  • Refuses — A2A 오류를 던지면 그 오류가 그대로 클라이언트에게 갑니다(와이어로는 -32602). 그러나 저장소에는 FAILED 작업이 남습니다. 거절이 목적이면 오류보다 up.reject(…)(3장)가 맞습니다.
  • Crashes — 아무 예외는 -32603 이 되고 작업은 FAILED 로 남습니다(5부).

던질 수 있는 A2A 오류 열셋 — 클래스가 곧 와이어의 코드다

SDK 는 오류 클래스마다 JSON-RPC 코드와, HTTP+JSON 바인딩의 상태·이유(reason)를 표로 둡니다(a2a/utils/errors.py 의 JSON_RPC_ERROR_CODE_MAP·A2A_ERROR_MAPPING).

실행기와 처리기 모두 같은 표를 쓴다 — 처리기가 스스로 던지는 것(작업 없음 -32001, 스트림 미지원 -32004)도, 실행기가 던진 것도 이 표로 옮겨집니다. 표에 없는 예외는 -32603 입니다. 코드 하나하나를 일부러 일으키는 것은 16부입니다.

InMemoryTaskStore 는 소유자별로 나뉜다 — 남의 작업은 "없다"

저장소 인터페이스(server/tasks/task_store.py)는 save·get·list·delete 넷이고, 모두 호출자(ServerCallContext)를 받습니다. 메모리 저장소는 그 호출자로 칸을 나눕니다.

  • 칸의 이름은 context.user.user_name 입니다(server/owner_resolver.py 의 resolve_user_scope). 다른 사람이 같은 taskId 로 GetTask 를 하면 작업이 없다(-32001)는 답을 받습니다.
  • 익명 호출자의 이름은 "" 이라 익명끼리는 한 칸을 나눠 씁니다 — 지금까지 이 책의 에이전트가 그랬습니다. 로그인으로 사용자를 세우는 일은 12부입니다.

꺼낸 Task 는 사본이다 — 고쳤으면 save 해야 남는다

꺼낸 Task 를 save 없이 COMPLETED 로 고친 뒤 다시 꺼냈습니다. 기본값(use_copying=True)과 끈 경우입니다.

기본은 사본 — CopyingTaskStoreAdapter 가 넣을 때와 꺼낼 때 CopyFrom 으로 사본을 뜹니다. 문서 문자열의 말로는 "hides missing save calls" 를 막으려는 것이고, DB 저장소와 같은 동작이 되게 하려는 것입니다(inmemory_task_store.py). 우리 저장소를 쓸 때(17부)도 이 성질을 지켜야 메모리 저장소에서 통과한 코드가 DB 에서도 돕니다.

4장 퀴즈

Q. 숙소 실행기의 한 갈래에서 실수로 return 만 하고 아무 이벤트도 넣지 않았습니다. 그 갈래로 가는 SendMessage(막는 호출)를 보낸 클라이언트에게는 무슨 일이 생기고, 저장소에는 무엇이 남습니까?

A. 답이 오지 않습니다. 처리기는 Task 가 만들어지기를 기다리는데(active_task.py:967) 아무도 만들지 않습니다 — rules.py 의 Silent 는 2초 제한에 걸려 TimeoutError 로 끝났고, 저장소는 비어 있었습니다(저장 []). 클라이언트 쪽 시간 제한만이 그 호출을 끝냅니다.

5장

서버 띄우기 — 라우트 팩토리, Starlette, uvicorn

라우트 팩토리 셋 → 앱은 경로 목록, 띄우는 것은 uvicorn → 서버 셋을 탭 뒤에 → 카드 경로 → 메아리의 답 → 견적의 답 → JSON-RPC 경로 옮기기 → 헤더가 실행기에 닿는 길 → 정리

라우트 팩토리는 Starlette Route 목록을 돌려줄 뿐이다

SDK 는 웹 서버를 띄우지 않습니다. a2a.server.routes 의 함수 셋이 처리기를 HTTP 경로에 묶은 Route 목록을 만들어 줄 뿐이고, 앱을 짓고 띄우는 것은 우리 몫입니다.

  • JSON-RPC 는 경로 하나(POST), 카드도 하나(GET)입니다. REST(HTTP+JSON) 는 열둘에, 같은 열둘을 /{tenant} 아래에 한 번 더 답니다 — 13부의 몫입니다.
  • SubscribeToTask 의 REST 경로는 GET 과 POST 둘 다 받습니다. proto(GET)와 스펙 §5.3 표(POST)가 엇갈리는 자리를 SDK 가 둘 다 받아 넘긴 것입니다(13부).

앱은 경로 목록을 이어 붙인 Starlette 하나 — 띄우는 것은 uvicorn

1단계 메아리 에이전트의 main 입니다. 실행기·저장소·카드로 처리기를 짓고(4장), 카드 경로와 JSON-RPC 경로를 한 Starlette 앱에 담아 uvicorn 으로 띄웁니다.

  • 카드의 url 은 바깥에서 닿는 주소입니다(3부). 그래서 --url 을 따로 받습니다 — 다음 슬라이드에서 탭의 주소를 넣습니다.
  • uvicorn 은 SDK 의 의존이 아니라서(1장) 따로 깔았습니다. log_level="warning" 은 요청마다 찍는 접근 기록을 끕니다. 끌 때 돌던 작업을 정리하려면 Starlette 의 lifespan 에 handler.aclose() 를 답니다(default_request_handler_v2.py:176).

서버 셋을 탭 뒤에 — 메아리는 /, 견적은 /a2a

1단계 메아리, 2단계 견적(JSON-RPC 를 /a2a 에), 그리고 헤더를 되돌려 주는 실험 서버를 띄우고 각각 앞에 와이어 탭을 세웠습니다. 요청 본문은 ex/run/07/rpc/*.json 입니다.

세 서버 모두 uvicorn.run 하나 — 2단계가 1단계와 다른 것은 실행기와 카드, 그리고 create_jsonrpc_routes(handler, args.path) 의 경로 인자뿐입니다(조금 뒤).

카드 경로는 create_agent_card_routes 가 — 빈 필드는 적지 않는다

  • 경로는 AGENT_CARD_WELL_KNOWN_PATH(/.well-known/agent-card.json, utils/constants.py)이고, card_url= 로 바꿀 수 있습니다.
  • 기능을 하나도 켜지 않은 카드라 "capabilities": {} 입니다. 이 경로는 약한 ETag 를 달고, cache_control= 을 주면 Cache-Control 도 답니다 — 캐시 이야기는 3부입니다.

메아리의 답은 result.message — 실행기가 넣은 Message 그대로

  • result.message 의 messageId 는 new_text_message 가 지은 uuid, contextId 는 처리기가 지어 ctx.context_id 로 넘긴 것입니다(3장).
  • Task 를 만들지 않았으니 이 답에는 taskId 가 없습니다. 같은 서버에 GetTask 를 해도 찾을 작업이 없습니다.

견적의 답은 result.task — 이벤트 넷이 Task 하나로 접혔다

2단계 서버에 같은 DataPart 요청을 보냈습니다. 응답 쪽만 잘랐습니다.

  • 3장에서 실행기가 낸 이벤트는 넷이었지만, 막는 호출의 답은 마지막 상태의 Task 하나입니다. WORKING 은 저장소를 거쳐 지나갔을 뿐 답에는 없습니다 — 이벤트를 하나하나 받으려면 스트림(10부)입니다.
  • 견적의 8.0·2100000.0 은 2장의 Value 가 와이어에 나타난 모습입니다(4부).

JSON-RPC 경로는 create_jsonrpc_routes 의 둘째 인자 — 카드의 url 과 같아야 한다

2단계는 --path /a2a 로 JSON-RPC 를 /a2a 에 달고, 카드의 url 도 같은 경로로 적습니다. 경로를 벗어난 요청 둘(POST /, GET /a2a)의 답입니다.

JSON-RPC 오류가 아니다 — 경로가 없거나(404) 메서드가 틀린(405) 요청은 Starlette 가 글 한 줄로 돌려보냅니다. 처리기까지 가지 못했으니 -32601 같은 JSON-RPC 오류도 없습니다. 카드의 url 을 잘못 적으면 클라이언트가 받는 것이 이것입니다(3부).

HTTP 헤더는 call_context.state 로 실행기에 닿는다

경로는 HTTP 요청마다 ServerCallContext 를 지어 처리기에 넘기고, 그것이 ctx.call_context 로 실행기까지 옵니다. 받은 것을 파트 다섯으로 돌려주는 실행기를 띄우고, 헤더 셋을 달아 불렀습니다.

  • 기본 빌더(server/routes/common.py 의 DefaultServerCallContextBuilder)는 헤더 전부를 소문자 키의 dict 로 state["headers"] 에 담고, A2A-Extensions 헤더를 풀어 requested_extensions 에 넣습니다(14부).
  • 사용자는 Starlette 의 request.user 가 있을 때만 세웁니다. 인증 미들웨어가 없으니 익명('', False)입니다 — 미들웨어로 사용자를 세우는 것은 12부입니다. 빌더를 바꾸려면 create_jsonrpc_routes(…, context_builder=…) 입니다.

5장 퀴즈

Q. 견적 서버를 --path /a2a 로 띄우면서 카드의 url 만 http://127.0.0.1:10712/ 로 잘못 적었습니다. 이 카드를 읽고 SendMessage 를 보낸 클라이언트는 어떤 HTTP 응답을 받고, 그 본문은 JSON-RPC 오류입니까?

A. POST / 에는 경로가 없으니 Starlette 가 404 Not Found 와 text/plain 본문 "Not Found" 로 답합니다 — serve 캡처에서 POST / 에 돌아온 답이 바로 그것입니다. 요청이 처리기까지 가지 못했으므로 JSON-RPC 오류 객체(error.code)는 없습니다.
