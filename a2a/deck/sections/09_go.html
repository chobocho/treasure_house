1장

패키지 지도 — 모듈 캐시의 소스에서 읽는다

모듈 하나에 패키지 서른셋 → 받지 않은 모듈 → internal 열둘은 못 가져온다 → 서버 쪽 칸 → 요청 하나가 지나는 길 → 완성 에이전트가 쓰는 이름 81개 → 이름에서 파일·줄 찾기 → 정리

a2a-go 는 모듈 하나에 패키지 서른셋 — internal 밖이 스물하나다

파이썬 SDK 는 extra(선택 설치 묶음)로(7부), TS SDK 는 진입점으로(8부) 나눴습니다. Go 는 모듈 하나 안의 패키지(디렉터리)로 나눕니다. 설치본의 디렉터리를 돌며 패키지마다 시험 아닌 .go 파일과 줄 수, 가져오는 바깥 모듈을 셌습니다.

  • 서버를 세우는 것은 a2asrv(3,287줄)와 그 아래 다섯, 타입은 a2a(1,954줄)입니다. 이 부 2~5장이 여기서 삽니다. 클라이언트 a2aclient 는 6장입니다.
  • 모듈 경로의 /v2 는 Go 의 큰판(major version) 규칙입니다. v0.3 시절의 SDK 는 github.com/a2aproject/a2a-go(v0.3.15)라는 다른 모듈이고, a2acompat/a2av0 이 그것을 가져옵니다(14부).

쓰지 않는 패키지의 의존은 받지도 않는다 — import 하는 예제가 생길 때 go.sum 에 들어온다

앞 표의 ✗ 는 우리 모듈(ex/go)의 go.sum 에 내용 해시가 없는 모듈입니다. SDK 의 go.mod 는 grpc·protobuf·genproto 와 옛 SDK 를 요구하지만, 우리는 쓰는 것만 받았습니다. 이 캡처는 13부에서 gRPC 바인딩을 쓰려고 grpc 를(13부), 14부에서 v0.3 호환을 돌리려고 옛 SDK 를(14부) 받은 뒤의 것이라 ✗ 가 하나도 남지 않았습니다.

  • Go 는 import 한 패키지가 닿는 모듈만 내려받습니다. 7~12부의 에이전트는 a2agrpc·a2apb 를 가져오지 않아서 의존이 uuid·x/mod·x/sync 셋이었고, 13부의 gRPC 예제가 a2agrpc/v1 을 import 하자 grpc·protobuf·genproto 가 go.mod 에 들어왔습니다.
  • 파이썬의 extra 와 TS 의 선택 peer 가 사람이 고르는 것이라면, Go 에서는 import 문이 고릅니다. a2acompat/a2av0 도 같아서, v0.3 호환을 쓰려면 옛 모듈(a2aproject/a2a-go)을 따로 받아야 합니다 — 14부가 go get …@v0.3.15 로 받기 전에는 이 줄에 ✗ 가 붙어 있었습니다.

internal 아래 열두 패키지는 가져올 수 없다 — 실행 엔진은 SDK 안에 갇혀 있다

Go 는 internal/ 아래 패키지를 그 모듈 밖에서 import 하지 못하게 컴파일러가 막습니다. 같은 지도의 아랫부분입니다.

  • 실행기를 고루틴에 띄우고 이벤트를 받아 Task 를 고치는 엔진 — taskexec(1,571줄)·eventpipe·taskupdate — 이 모두 internal 입니다. JSON-RPC 의 메서드 이름·오류 코드 표(internal/jsonrpc)도 그렇습니다.
  • 그래서 Go 에서는 엔진을 고쳐 쓸 수 없고, SDK 가 열어 둔 옵션(a2asrv.With…, 4장)과 인터페이스(실행기·저장소·가로채기)로만 끼어듭니다. TS SDK 가 번들마다 사본을 둔 것(8부)과 달리, 여기서는 한 벌이 한 자리에 있습니다.

완성 에이전트가 쓰는 SDK 이름은 81개 — 반이 넘게 a2a 의 타입이다

완성 에이전트(agents/*/*.go, 열두 파일)를 go/parser 로 읽어, SDK 패키지 이름이 붙은 식(a2a.Task, a2asrv.NewHandler)을 모으고 이름마다 몇 파일이 쓰는지 셌습니다. 파이썬은 37개(7부), TS 는 28개(8부)였습니다.

  • 많은 것은 Go 가 상수와 생성 함수를 따로 이름 짓기 때문입니다 — 상태 하나가 a2a.TaskStateCompleted 처럼 이름 하나입니다. 파이썬의 TaskUpdater 같은 갱신기 대신 a2a.NewStatusUpdateEvent·NewArtifactEvent 가 있고(3장), 그 위의 작은 갱신기는 우리 agents/common 이 둡니다.
  • a2aclient 셋은 기획 에이전트와 ask CLI 가, a2acrypto 다섯은 정산 카드의 서명(12부)이 씁니다.

이름에서 파일과 줄로 — 소스가 그대로 있으니 선언을 찾으면 된다

TS 는 번들의 줄에서 원본 이름을 거꾸로 찾아야 했습니다(8부). Go 설치본은 원본 그대로라, 패키지를 go/parser 로 읽어 맨 윗단 선언을 찾으면 끝입니다. 위치는 go list -m -f {{.Dir}} 가 알려 준 모듈 디렉터리에서 본 경로입니다.

이 부의 줄 번호 — 슬라이드가 인용하는 a2asrv/handler.go:197 같은 자리는 모두 이 설치본(v2.6.0)의 것입니다. 편집기의 "정의로 가기" 도 같은 파일로 갑니다 — 모듈 캐시는 읽기 전용이라 고칠 수는 없습니다.

1장 퀴즈

Q. 동료가 "실행기가 내놓은 이벤트를 저장되기 전에 하나씩 들여다보고 싶다" 며 import "github.com/a2aproject/a2a-go/v2/internal/taskupdate" 를 적었습니다. 빌드가 됩니까? 안 된다면 어디서 끼어들어야 합니까?

A. 안 됩니다. sdk_map 이 보여 준 internal/ 아래 패키지는 그 모듈(a2a-go/v2) 밖에서 import 할 수 없고, 컴파일러가 막습니다. 끼어들 자리는 SDK 가 열어 둔 인터페이스입니다. 이벤트라면 실행기를 감싸는 실행기를 하나 더 두어 안쪽 Execute 의 반복자를 돌며 보고 다시 내놓으면 되고(3장의 range), 요청·응답이라면 a2asrv.WithCallInterceptors 입니다(서버 쪽 칸의 middleware.go).

2장

타입 — 손으로 쓴 구조체와 encoding/json

구조체 42개와 string 바탕 타입 → enum 은 문자열 → 생성 함수·구조체 글자·Unmarshal → json.Marshal 이 곧 와이어 → Part 의 메서드 넷 → 포인터로 넣고, 겉만 복사된다 → 영값과 nil → 거절하는 것과 받아 주는 것 → DataPart 의 Value → Task 짓기 → Task 읽기 → SDK 안의 모양과 와이어 → 정리

타입은 생성기가 아니라 사람이 쓴 Go 구조체다 — proto 는 없다

a2a 패키지의 맨 윗단 선언을 종류로 나눴습니다. 파이썬은 protobuf 메시지(7부), TS 는 ts-proto 의 인터페이스(8부)였습니다.

  • a2a/core.go 의 Message·Task 는 json 태그를 단 보통 구조체입니다. proto 에서 만든 Go 타입은 따로 a2apb/v1 에 있고(1장), gRPC 바인딩만 그것을 거쳐 이 구조체로 옮깁니다(a2apb/v1/pbconv).
  • 인터페이스 일곱 가운데 Event·SendMessageResult·PartContent 는 "이 가운데 하나" 를 나타내는 닫힌 합(sealed union)입니다. 소문자 메서드(isEvent())를 하나 두어 패키지 밖에서는 새 갈래를 만들 수 없게 했습니다(a2a/core.go:76).

enum 은 문자열 — 값이 곧 와이어의 이름이고, 모르는 값도 받아 둔다

TaskState·MessageRole 은 type TaskState string 입니다(a2a/core.go:280). 상태 아홉을 Go 값, json.Marshal 결과, Terminal() 로 찍었습니다.

  • 수가 아니라 이름이 값이라, 파이썬의 TaskState.Name(n) 이나 TS 의 taskStateToJSON(8부) 같은 변환이 없습니다. 예외는 영값 "" 하나 — 내보낼 때 MarshalJSON 이 "TASK_STATE_UNSPECIFIED" 로 바꿉니다.
  • UnmarshalJSON 은 받은 문자열을 그대로 담습니다. v0.3 의 "user" 도 오류 없이 MessageRole("user") 이 됩니다 — TS 는 -1(8부)이었습니다. 와이어에서 세 서버가 이 입력에 갈린 모습은 4부입니다. Terminal() 은 이 SDK 의 도우미로, 끝난 넷에서만 참입니다(INPUT_REQUIRED 는 거짓 — 5부 Terminal() 로).

메시지를 짓는 세 길 — 생성 함수, 구조체 글자, Unmarshal 이 같은 값을 낸다

같은 사용자 메시지를 세 길로 만들어 reflect.DeepEqual 로 견줬습니다. NewMessage 는 id 를 지어 주므로 견주려고 고정했습니다.

  • 구조체 글자는 필요한 필드만 적습니다 — 안 적은 것은 영값("", nil)입니다. TS 처럼 여덟 필드를 다 적을 일(8부)이 없습니다. 대신 Go 이름이 와이어 이름과 다른 곳이 있습니다: ID(messageId), ReferenceTasks(referenceTaskIds).
  • Part 를 짓는 생성 함수는 넷입니다 — NewTextPart·NewDataPart·NewRawPart·NewFileURLPart(조금 뒤).

json.Marshal 이 곧 와이어 모양이다 — Part 만 손으로 펼친다

같은 메시지를 json.Marshal 과 %+v 로 찍었습니다. 파이썬의 json_format(7부), TS 의 toJSON(8부) 같은 변환 층이 따로 없습니다.

  • 키 차례는 구조체 필드 차례입니다 — messageId 다음 알파벳 차례(parts, role)라 5부에서 본 Go 서버의 키 차례가 여기서 나옵니다. 빈 필드는 omitempty 태그로 빠집니다.
  • SDK 안의 Part 는 Content 하나에 a2a.Text 같은 타입을 담습니다. 와이어의 "text": … 로 펼치는 일은 Part.MarshalJSON(a2a/core.go:694)이 손으로 합니다. TS 의 $case 가 새던 일(8부)은 생기지 않습니다.

Part 의 메서드 넷은 다른 종류면 영값을 준다 — 종류는 타입 스위치로 묻는다

4부에서 Content 를 타입 스위치로 갈랐습니다. SDK 는 그 위에 Text()·Data()·Raw()·URL() 를 둡니다(a2a/core.go:620). 다섯 파트에 넷을 모두 불러 봤습니다.

Text() 가 "" 라고 글 파트가 아닌 것은 아니다 — 마지막 파트는 빈 글이고, 둘째는 데이터인데 둘 다 Text() 가 "" 입니다. 메서드는 "있으면 꺼내기" 로만 쓰고, 종류를 가를 때는 p.Content.(type) 을 씁니다. 파이썬의 WhichOneof, TS 의 content?.$case 자리입니다.

이력에는 포인터가 들어가고, 구조체 복사는 겉만이다 — TS 와 같은 쪽

History 는 []*Message, Status 는 값입니다. 넣은 뒤 고치기, 구조체 복사 뒤 고치기, JSON 왕복 사본 고치기를 해 봤습니다.

  • 넣은 뒤 msg 를 "40명" 으로 고치자 이력도 바뀌었습니다 — 파이썬은 넣을 때 복사했고(7부), TS 는 Go 와 같았습니다(8부).
  • shallow := *task 의 Status 는 값이라 따로 놀지만, History 슬라이스는 같은 배열을 봅니다. 깊은 사본 함수는 SDK 의 internal/utils.DeepCopy(gob) 뿐이라 우리는 못 씁니다(1장). 저장소가 그것으로 사본을 뜨는 모습은 4장입니다.

"없음" 은 영값과 nil — 그리고 omitempty 가 없는 필드는 영값으로 나간다

contextId 없이 온 메시지, 아무것도 안 채운 Message{}·Task{}, historyLength 가 있고 없는 GetTask 요청입니다.

  • 문자열은 "", 맵·슬라이스·포인터는 nil 이 "안 보냄" 입니다. 검사는 if m.ContextID == "". 선택 정수는 *int 라서 nil 과 &0 이 갈립니다(5부).
  • parts·role·status 처럼 태그에 omitempty 가 없는 필드는 비어도 나갑니다 — "parts":null, "role":"ROLE_UNSPECIFIED". 짓다 만 구조체를 내보내면 이런 JSON 이 와이어로 갑니다. 빈 목록이 Go 서버에서만 null 이던 일(4부)도 같은 까닭입니다.

Part 는 엄격하고 enum·키는 너그럽다 — 거절과 수용이 한 패키지에 섞여 있다

와이어에서 Go 서버가 내용 둘인 파트를 거절한 일(4부)과 ProtoJSON 의 너그러움(4부)이 타입 층에서는 이렇게 생깁니다.

  • Part.UnmarshalJSON 은 내용이 정확히 하나여야 합니다(a2a/core.go:717). {"data":null} 과 빈 url 도 "내용 없음" 이라 오류인데, NewDataPart(nil) 은 {"data":null} 을 써 냅니다(다음) — 제가 쓴 것을 제가 못 읽습니다. 오류는 json.Unmarshal 이 내므로 서버에서는 -32700 이 됩니다(4부).
  • 모르는 상태 이름은 그대로 받아 둡니다. 키 맞추기는 encoding/json 의 규칙대로 대소문자를 가리지 않아 MESSAGEID 가 맞고, snake_case 는 맞지 않습니다. 모르는 키는 버리되, Decoder.DisallowUnknownFields 로 오류로 바꿀 수 있습니다.

DataPart 의 Value 는 any — 넣을 때는 구조체, 받으면 map 과 float64

숙소 요청을 업무 패키지의 구조체(workshop.LodgingRequest) 그대로 data 파트에 넣어 와이어로 바꾸고 다시 읽었습니다. 파이썬에서 30.0, TS 에서 30 이던 자리(7부·8부)입니다.

  • 보내는 쪽은 정수 30 을, 키는 구조체 태그의 차례 그대로 냅니다. 받는 쪽은 encoding/json 의 규칙대로 map[string]any 와 float64 입니다. 구조체로 받으려면 한 번 더 Marshal → Unmarshal 해야 하고, 그때 30.0 을 보낸 파이썬 서버의 값이 정수 칸에서 실패하던 일이 4부입니다.
  • Value 에는 목록·문자열·수·nil 도 들어가고 그대로 나갑니다. 넣은 값이 저장소의 사본(gob)을 거칠 때의 제약은 4장에서 봅니다.

Task 는 NewSubmittedTask 로 — 첫 인자는 id 둘을 알려 주는 무엇이든

파이썬의 new_task_from_user_message(7부) 자리입니다. 첫 인자 TaskInfoProvider 는 TaskInfo() 메서드 하나짜리 인터페이스라, a2a.TaskInfo 값도, 실행기가 받는 ExecutorContext 도 됩니다(3장).

  • 상태는 SUBMITTED, 이력은 받은 메시지 하나, status.timestamp 는 없습니다 — 세 서버 모두 SUBMITTED 에 시각이 없던 일(5부)의 Go 쪽 출처가 이 함수입니다(a2a/core.go:365). 검사는 하지 않습니다.
  • id 를 비워 주면 새로 짓는데, UUID 판(version) 자리가 7 — 시각 순 UUIDv7 입니다(a2a/core.go:816, "Time-based UUID generally improves index update performance"). ExecutorContext.TaskID 의 주석은 "UUIDv4" 라고 적었습니다(a2asrv/exectx.go:43) — 주석이 낡았습니다.

받은 JSON 은 json.Unmarshal 로 — 모르는 필드는 버리고 raw 는 base64 를 푼다

클라이언트 쪽 일입니다. 스펙에 없는 createdAt(5부)과 base64 raw 파트가 든 Task JSON 을 읽었습니다. 8부와 같은 입력입니다.

yield 가 false 면 곧바로 돌아간다 — 안 지키면 런타임이 panic 을 낸다

반복자의 규칙은 하나입니다. 받는 쪽이 그만 받겠다고 하면(yield 가 false) 다시 yield 를 부르지 않는다. 받는 쪽이 둘째 이벤트에서 멈출 때, 견적 실행기와 답을 버리는 실행기를 견줬습니다.

  • 견적 실행기는 if !yield(…) { return } 으로 멈췄습니다. careless 는 셋째 yield 에서 "range function continued iteration after function for loop body returned false" panic 을 냈습니다 — 큐·버스에는 없는, Go 반복자만의 계약입니다.
  • SDK 가 받기를 그만두는 때는 종료 이벤트를 처리한 뒤입니다. 그때 실행기의 ctx 도 취소되고, yield 의 답은 경합에 따라 갈립니다(5부). 그래서 오래 도는 실행기는 ctx.Err() 와 yield 의 답을 둘 다 봅니다.

갱신기는 없고 생성 함수가 있다 — yield 를 품는 작은 갱신기는 우리가 둔다

Go SDK 에는 파이썬의 TaskUpdater 같은 객체가 없습니다(1장의 이름 목록). 생성 함수로 충분하지만, 완성 에이전트는 yield 와 ec 를 한데 쥔 갱신기를 하나 둡니다.

메서드가 bool 을 돌려주는 까닭 — Status 는 yield 의 답을 그대로 돌려줍니다. 부르는 쪽이 if !up.Status(…) { return } 으로 앞 슬라이드의 규칙을 지키게 하려는 것입니다. 파이썬 갱신기처럼 "종료 뒤 갱신" 을 막는 장치는 없고, 저장 쪽(taskupdate.Manager.Process)이 종료된 작업에 온 갱신을 ErrInvalidAgentResponse 로 거절합니다(internal/taskupdate/manager.go).

이어 말하기 — StoredTask 에는 이번 메시지가 이미 있고, 질문은 그 뒤에 붙는다

같은 taskId 로 두 번째 메시지가 오면 처리기는 저장된 Task 를 ec.StoredTask 로 넘깁니다. 첫 마디에 되묻고 둘째 마디에 끝내는 실행기로, 둘째 Execute 가 받은 것과 끝난 뒤 저장된 이력을 찍었습니다(처리기를 직접 부르는 법은 4장).

  • 처리기는 Execute 전에 이번 메시지(m-2)를 이력에 붙여 저장합니다(a2asrv/agentexec.go:236) — TS 와 같고 파이썬과 반대입니다(8부). 그런데 질문 q-1 은 아직 이력에 없습니다. Go SDK 는 상태 메시지를 다음 상태 갱신 때 이력으로 옮기기 때문입니다(a2aevent/event.go:121).
  • 그래서 끝난 뒤의 이력은 답(m-2) 다음에 질문(q-1)이 옵니다. 완성 에이전트의 working(agents/common/begin.go)이 질문을 답 앞으로 옮겨 다시 싣는 까닭이 이것입니다(5부의 세 서버 비교, 5부).

3장 퀴즈

Q. 되묻기 에이전트의 둘째 마디에서 "사용자가 지금까지 한 말" 을 모으려고 append(ec.StoredTask.History, ec.Message) 의 사용자 메시지를 셌더니, 사용자는 두 번 말했는데 셋이 나왔습니다. 왜 그렇습니까? 8부의 같은 퀴즈와 답이 같습니까?

A. Go 처리기는 Execute 를 부르기 전에 이번 메시지를 이력에 붙여 저장하므로, StoredTask.History 에 이미 둘째 말(m-2)이 있습니다 — follow 의 "이번 메시지가 이미 있나: true" 입니다. 여기에 ec.Message 를 또 붙이면 둘째 말을 두 번 셉니다. TS 와 같은 답이고, 파이썬만 둘입니다. 완성 에이전트의 Begin 주석도 "이번 메시지까지 들어 있다" 고 적었습니다.

요청 처리기와 Task 저장소

메서드 열하나 → 옵션 열셋 → HTTP 없이 처리기 부르기 → 막는 호출은 언제 돌아오나 → 반칙하는 실행기 일곱 → 차례 반칙의 결과 → 침묵과 오류, 그리고 시간 한도 → 세 SDK 비교 → 표지 오류와 코드 → 주인별 저장소 → 꺼내면 gob 사본 → 판 번호 → 정리

요청 처리기는 인터페이스 하나 — A2A 메서드 열하나가 Go 메서드 열하나다

a2asrv.RequestHandler(a2asrv/handler.go:41)의 메서드마다 문서 주석이 "handles the 'GetTask' protocol method" 처럼 맡은 A2A 메서드를 적었습니다. 그것을 읽어 짝지었습니다.

  • 푸시 넷만 이름이 짧습니다(GetTaskPushConfig ← GetTaskPushNotificationConfig). 파이썬의 on_*(7부), TS 의 resubscribe(8부)와 같은 몫입니다. 스트림 둘은 iter.Seq2[a2a.Event, error] 를 돌려줍니다 — 실행기와 같은 모양입니다.
  • 인터페이스라서 우리가 구현할 수도 있습니다. 이 장 뒤에서 오류만 돌려주는 가짜 처리기를 만들고(표지 오류), 완성 에이전트는 SDK 처리기의 안쪽을 감싸 결재 대기를 잇습니다(agents/common/serve.go, 12부).

NewHandler 는 실행기 하나와 옵션 함수들 — 필수 인자는 실행기뿐이다

TS 는 위치 인자 아홉(8부), 파이썬은 키워드 인자(7부)였습니다. Go 는 NewHandler(executor, options ...RequestHandlerOption) 의 함수형 옵션입니다. RequestHandlerOption 을 돌려주는 함수를 모두 찾았습니다.

HTTP 없이 처리기 부르기 — context.Background() 하나면 된다

2단계 견적 실행기로 처리기를 만들고, SendMessage·GetTask·ListTasks 와 스트림을 직접 불렀습니다. 7부·8부의 direct 와 한 줄씩 같은 일입니다.

호출 맥락은 처리기가 붙인다 — NewHandler 가 돌려주는 것은 *InterceptedHandler 입니다. 메서드마다 ctx 에 CallContext 가 없으면 익명 사용자로 하나 붙이고(intercepted_handler.go:296), 가로채기를 거쳐 안쪽 처리기를 부릅니다. 파이썬·TS 처럼 호출 맥락 객체를 따로 넘기지 않고 context.Context 에 싣는 것이 Go 의 길입니다.

막는 호출은 끝 이벤트에서 돌아온다 — 그리고 익명은 목록을 못 본다

  • SendMessage 는 이벤트를 따라가다 Message, 종료 상태, INPUT_REQUIRED 에서 그때의 Task 를 답으로 줍니다(3장의 약속, internal/taskupdate/final.go). AUTH_REQUIRED 는 저장된 Task 를 곧바로 돌려주고 실행은 뒤에서 이어집니다(shouldInterruptNonStreaming, handler.go:490) — 그 모델 차이가 완성 에이전트의 park.go 를 낳았습니다(12부).
  • ReturnImmediately 면 첫 Task(SUBMITTED)에서 답하고 실행기는 뒤에서 마저 돕니다 — 세 SDK 가 같습니다(5부).
  • ListTasks 가 unauthenticated 입니다. 기본 저장소는 이름 없는 호출자에게 목록을 주지 않습니다(taskstore/inmemory.go:192) — 파이썬·TS 는 익명에게도 줬습니다. 완성 에이전트가 익명을 "anonymous" 로 세우는 까닭입니다(agents/common/serve.go 의 owner). 스트림은 WithCapabilityChecks 로 넘긴 카드에 streaming 이 없어 막혔습니다.

반칙하는 실행기 일곱 — 차례 넷, 침묵 하나, 오류 둘

7부·8부와 같은 일곱을 Go 로 썼습니다. 각각을 새 처리기에 물려 JSON-RPC 처리기(NewJSONRPCHandler)를 httptest.ResponseRecorder 로 — 네트워크 없이 — 부르고, 막는 SendMessage 와 스트림을 2초까지 기다립니다. 저장소는 목록을 보려고 주인을 한 사람(kim)으로 정했습니다.

차례 검사는 두 길 모두에 있다 — 반칙의 값은 -32006, 또는 FAILED

  • 검사는 저장 쪽(taskupdate.Manager.Process)에 있어 막는 호출과 스트림이 같은 답을 받습니다. TS 는 스트림에만 있었습니다(8부). Task 없이 상태부터 오면 -32006 InvalidAgentResponse — §3.3.2 가 정한 그 코드이고, 파이썬과 같습니다.
  • Task 를 낸 뒤의 반칙(MessageAfterTask)은 오류가 아니라 작업을 FAILED 로 만들어 답합니다(processor.setTaskFailed, agentexec.go). Message 둘이면 첫 Message 에서 끝이라 둘째는 버려집니다.
  • OtherId 의 "task IDs don't match" 는 표지 오류를 감싸지 않아 -32603 입니다(파이썬 -32602, TS 는 통과). 답의 message 에 SDK 안쪽의 오류 문장("processor error: execution failed …")이 그대로 나갑니다.

침묵은 끝없이 기다린다 — 한도를 거는 옵션이 있고, 오류는 코드를 지킨다

  • Silent — 실행기가 돌아가도 이벤트를 받는 쪽은 종료 이벤트를 기다립니다("Event consumer continues to run waiting for a terminal event", internal/taskexec/doc.go:29). 2초 뒤 우리가 요청을 거두자 -32603 queue read failed: context canceled 이 나왔습니다 — 파이썬처럼 붙잡히고(7부), TS 처럼 곧바로 끝나지 않습니다. WithAgentInactivityTimeout 을 걸면 "agent inactivity timeout" 으로 끝납니다.
  • Refuses·Crashes — Task 를 내기 전의 오류는 그대로 JSON-RPC 오류가 되고, %w 로 감싼 표지 오류는 코드(-32602)를 지킵니다. 작업은 저장되지 않습니다. Task 를 낸 뒤의 오류는 FAILED 작업입니다(5부). 오류 문장은 클라이언트에 그대로 가니, 감출 것은 넣지 않습니다.

a2a 의 Err… 표지 오류(sentinel)마다 JSON-RPC 코드와 HTTP+JSON 상태를 SDK 의 전송 처리기에 물었습니다. GetTask 만 오류를 돌려주는 가짜 RequestHandler 를 물렸습니다.

  • 코드는 errors.Is 로 고르므로 fmt.Errorf("…: %w", a2a.ErrTaskNotFound) 도 -32001 입니다. 표지가 없으면 -32603·500. -31401·-31403 은 SDK 가 정한 번호입니다 — 스펙은 인증 오류의 JSON-RPC 코드를 "JSON-RPC custom error" 라고만 적었습니다(§3.3.2 의 범주 목록).
  • 표지 둘을 함께 감싸면 JSON-RPC 코드는 부를 때마다 -32602 또는 -32001 입니다. 변환 함수가 코드 표를 Go 맵으로 돌기 때문입니다(internal/jsonrpc/jsonrpc.go:163, 맵의 차례는 매번 다르다). HTTP+JSON 쪽은 표가 슬라이스라 늘 400 입니다(internal/rest/rest.go:192). 오류 하나에는 표지 하나만 감쌉니다.

taskstore.InMemory 는 taskId 와 주인으로만 나뉜다 — 테넌트는 보지 않는다

저장소 인터페이스(taskstore.Store)는 Create·Update·Get·List 넷이고, 주인은 Authenticator 함수가 ctx 에서 꺼냅니다. SDK 기본과 같은 a2asrv.NewTaskStoreAuthenticator() 로, kim·lee·익명이 서로의 작업을 찾아봤습니다.

  • 남의 작업은 task not found 입니다 — "Mask ownership mismatch as ErrTaskNotFound per A2A spec §3.3.2"(inmemory.go:171). 익명("")도 제 작업은 찾지만 목록은 unauthenticated 입니다(앞).
  • 테넌트 b 를 달아도 kim 의 작업이 나왔습니다. 맵의 열쇠가 a2a.TaskID 하나라(inmemory.go:52) 테넌트는 칸을 나누지 않습니다 — TS 는 테넌트 → 주인 차례로 나눴고(8부), 파이썬은 주인만 봤습니다(7부). 테넌트는 13부입니다.

  • 저장소는 넣을 때와 꺼낼 때 모두 encoding/gob 으로 깊은 사본을 뜹니다(internal/utils.DeepCopy). 고친 것은 Update 해야 남습니다 — 파이썬의 use_copying=False 같은 스위치는 없습니다(7부).

저장소에는 판 번호가 있다 — 앞 판이 맞아야 고쳐 쓴다

세 SDK 가운데 Go 저장소만 Task 마다 판(TaskVersion)을 셉니다. 3장 약속 표의 "낙관적 동시성 제어"(3장)가 이것입니다. 같은 앞 판으로 두 번 고쳐 썼습니다.

왜 있나 — 실행과 취소가 서로 다른 고루틴(클러스터라면 다른 서버)에서 같은 Task 를 고칠 수 있기 때문입니다. 늦게 온 쪽은 ErrConcurrentModification 을 받고, SDK 는 저장소에서 다시 읽어 종료 상태면 그것을 답으로 씁니다(agentexec.go 의 processor.Process). 저장소를 직접 구현한다면(17부) 이 계약을 지켜야 합니다 — 인터페이스 주석이 MUST 로 적었습니다(taskstore/api.go 의 ErrConcurrentModification).

4장 퀴즈

Q. 숙소 실행기의 한 갈래에서 실수로 Task 를 낸 뒤 상태 대신 Message 를 냈습니다. Go 서버에 막는 SendMessage 를 보낸 클라이언트는 무엇을 받고, 나중에 GetTask 하면 작업은 어떤 상태입니까? 8부의 TS 서버와 견주면?

A. FAILED 상태의 Task 를 받고, 저장된 작업도 FAILED 입니다 — rules 의 MessageAfterTask 가 "막는 호출 task TASK_STATE_FAILED", "저장 [TASK_STATE_FAILED]" 였습니다. 스트림이면 task 둘(SUBMITTED, FAILED)을 받습니다. TS 서버는 막는 호출에 그 Message 를 답하고 작업을 SUBMITTED 로 남겼으며, 스트림만 -32004 로 끊었습니다.

5장

서버 띄우기 — net/http 에 처리기 둘

처리기 셋은 http.Handler 일 뿐 → 앱은 ServeMux, 띄우는 것은 ListenAndServe → 서버 셋을 탭 뒤에 → 메아리의 답 → 견적의 답 → 경로 밖의 요청 → 판 머리글도 Content-Type 도 묻지 않는다 → 사용자와 헤더가 실행기에 닿는 길 → 정리

SDK 의 HTTP 처리기는 http.Handler 일 뿐이다 — 경로와 방법은 우리가 가린다

TS 처리기는 express Router 를(8부), 파이썬은 Starlette 경로 목록을(7부) 돌려줬습니다. Go 의 NewJSONRPCHandler·NewStaticAgentCardHandler·NewRESTHandler 는 표준 http.Handler 입니다. 서버 없이 httptest 로 요청 몇 개를 넣어 봤습니다.

  • JSON-RPC 처리기는 경로를 보지 않고 무엇이든 받습니다. POST 가 아니면 HTTP 200 에 -32600 Invalid Request 를 답합니다(jsonrpc.go:52). 카드 처리기도 경로를 보지 않고, GET·OPTIONS 만 받습니다(agentcard.go:87).
  • REST 처리기만 안에 제 ServeMux 를 두고 GET /tasks/{idAndAction} 같은 길을 가립니다(rest.go:54). 그 밖의 길은 net/http 의 404 page not found 입니다 — 13부.

앱은 http.ServeMux 하나 — 카드 길과 JSON-RPC 길을 달고 ListenAndServe

1단계 메아리 에이전트의 main 입니다. 실행기로 처리기를 짓고(4장), 카드 처리기와 JSON-RPC 처리기를 표준 라이브러리의 ServeMux 에 달아 띄웁니다. 웹 프레임워크도, 따로 까는 서버(uvicorn·express)도 없습니다.

  • 카드 길은 SDK 상수 a2asrv.WellKnownAgentCardPath, 처리기는 처음 한 번 json.Marshal 한 바이트를 늘 쓰는 NewStaticAgentCardHandler 입니다 — 3부에서 본 그대로이고, "pushNotifications":false 가 적히는 까닭도 거기 있습니다(3부). 캐시 머리글은 없습니다(3부).
  • 카드의 url 은 바깥에서 닿는 주소라(3부) --url 을 따로 받습니다. 끌 때는 http.Server 의 Shutdown 입니다 — 처리기에는 끄는 메서드가 없습니다(4장 정리).

서버 셋을 탭 뒤에 — 메아리는 /, 견적은 POST /a2a

7부·8부와 같은 짜임입니다. 1단계 메아리, 2단계 견적(JSON-RPC 를 POST /a2a 에), 헤더를 되돌려 주는 실험 서버를 띄우고 각각 앞에 와이어 탭을 세웠습니다. 요청 본문은 ex/run/09/rpc/*.json 으로, 8부와 같은 파일입니다.

일부러 틀리게 보내는 넷 — 셋째 줄은 경로 밖(POST /, GET /a2a)으로, 넷째 줄은 판 머리글 없이 그리고 text/plain 으로 보냅니다. 모두 -o /dev/null 이라 답은 탭에서 읽습니다.

메아리의 답은 result.message — 실행기가 내놓은 Message 그대로

  • JSON-RPC 처리기가 결과를 a2a.StreamResponse{Event: res} 로 감싸(jsonrpc.go 의 handleRequest) {"message": …} 가 되었습니다(2장). 키는 구조체 차례라 role 이 끝에 옵니다.
  • contextId 는 처리기가 지어 ec.ContextID 로 넘긴 것입니다(3장). Task 가 없으니 이 서버에 GetTask 해도 찾을 작업이 없습니다.

견적의 답은 result.task — 이벤트 넷이 Task 하나로 접혔다

2단계 서버에 같은 DataPart 요청을 보냈습니다. 응답 쪽 앞부분입니다.

  • 3장에서 실행기가 낸 이벤트는 넷이지만 막는 호출의 답은 마지막 상태의 Task 하나입니다. Task 의 키도 구조체 차례라 artifacts 가 contextId 앞에 옵니다(5부).
  • 아티팩트의 수는 30·2100000 정수입니다 — Plain 을 거친 float64 를 encoding/json 이 소수점 없이 씁니다. 파이썬 서버의 8.0·2100000.0(7부)과 다릅니다.

방법과 경로는 ServeMux 패턴으로 — 경로 밖은 404, 방법이 틀리면 405

2단계는 "POST " + path 패턴(Go 1.22 의 ServeMux)으로 JSON-RPC 를 답니다. 경로를 벗어난 요청 둘(POST /, GET /a2a)의 답입니다.

JSON-RPC 오류가 아니다 — 패턴에 맞지 않는 요청은 처리기에 닿지 않고 net/http 가 글 한 줄로 돌려보냅니다. GET /a2a 는 길은 있고 방법이 틀려 405(Allow: POST)입니다 — 파이썬 Starlette 와 같고, express 의 404 와 다릅니다(8부). 패턴 없이 mux.Handle("/a2a", rpc) 로 달면 GET 은 처리기가 받아 HTTP 200 의 -32600 이 됩니다(앞).

판 머리글도 Content-Type 도 묻지 않는다 — 둘 다 COMPLETED 로 답했다

TS 서버가 -32009·-32005 로 막았던 두 요청(8부)을 Go 서버에 보냈습니다 — A2A-Version 없이, 그리고 Content-Type: text/plain 으로.

  • JSON-RPC 처리기는 A2A-Version 을 읽지 않습니다 — 6부에서 와이어로 본 일(6부)의 출처가 jsonrpc.go 의 ServeHTTP 입니다. 스펙은 빈 머리글을 0.3 으로 보라 하고(§3.6.1), 서버는 요청한 판의 뜻대로 처리하되 지원하지 않는 판에는 VersionNotSupportedError 를 내야 합니다(§3.6.2, MUST). Go 서버에서 판을 따지려면 우리가 가로채기(다음)나 HTTP 미들웨어로 검사합니다.
  • 본문은 Content-Type 과 상관없이 json.NewDecoder(req.Body) 로 읽습니다. TS 가 HTTP 머리글에 -32005 를 쓴 것보다는 스펙의 뜻(파트의 미디어 형식, §3.3.2)에 덜 어긋나지만, 아무것도 검사하지 않는 쪽입니다.

사용자는 호출 가로채기가, 헤더는 ServiceParams 가 실행기까지 나른다

JSON-RPC 처리기는 HTTP 요청마다 머리글로 ServiceParams 를 만들어 CallContext 에 싣습니다(jsonrpc.go:50). 사용자는 익명으로 시작하고, CallInterceptor 의 Before 에서 바꿀 수 있습니다. 받은 것을 파트 다섯으로 돌려주는 실행기에, 머리글로 사용자를 세우는 실험용 가로채기를 달았습니다.

  • 가로채기는 a2asrv.WithCallInterceptors(…) 로 처리기에 답니다(4장). 같은 사용자 이름이 저장소의 주인 칸도 정합니다(4장). ServiceParams 의 열쇠는 소문자로 바뀌어 대소문자를 가리지 않고, 값은 목록([]string)입니다.
  • 확장은 받은 그대로입니다 — 카드에 없는 확장도 RequestedURIs() 에 들어왔습니다. 파이썬과 같고, 카드의 것만 남기는 TS(8부)와 다릅니다. 확장은 14부, 진짜 인증(토큰)은 12부입니다.

Q. 견적 서버를 띄운 뒤 동료가 curl --json @quote.json http://127.0.0.1:10912/a2a 로 시험했습니다(판 머리글 없음). TS 서버였다면 -32009 였을 이 요청에 Go 서버는 무엇을 답합니까? 같은 동료가 브라우저로 http://127.0.0.1:10912/a2a 를 열면 무엇을 봅니까?

A. COMPLETED Task 를 답합니다. Go 의 JSON-RPC 처리기는 A2A-Version 을 읽지 않습니다 — serve 캡처에서 머리글 없는 요청의 상태가 TASK_STATE_COMPLETED 였습니다. 브라우저(GET)는 405 Method Not Allowed 글 한 줄을 봅니다. 견적 서버는 "POST /a2a" 패턴으로 달아, GET 은 처리기에 닿기 전에 ServeMux 가 거절합니다(경로 밖).
