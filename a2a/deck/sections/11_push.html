TypeScript — up.pause 가 false 면 그대로 돌아간다

agents/bus.ts 의 같은 자리입니다. Updater(10부)의 status·artifact 는 버스에 싣고 곧 돌아옵니다.

쉬는 자리가 취소를 듣는 자리 — 파이썬은 asyncio.sleep 이 취소되며 끊기고, TS 는 pause 가 false 를 돌려주면 실행기가 스스로 돌아갑니다. 취소가 실제로 어떻게 닿는지는 6장의 몫입니다.

Go — common.Sleep(ctx, …) 이 false 면 멈춘다

agents/bus/main.go 의 Execute 입니다. 반복자 안에서 단계마다 up.Status 로 이벤트를 yield 합니다(9부).

  • 요청의 depart 는 req["depart"].(string) — 없거나 null 이면 빈 문자열이 되어 미정 으로 바뀝니다. 파이썬·TS 는 or·|| 한 번입니다.
  • 세 언어 모두 단계 줄을 상태를 싣기 전에 서버 출력에 찍습니다. 출력 줄이 곧 "이 단계에 들어섰다" 입니다.

푸시 배선은 서버를 띄우는 자리에 — 설정 저장소 하나와 보내는 것 하나

실행기는 푸시를 모릅니다. 실행기가 실은 이벤트를 요청 처리기가 저장하고, 설정이 있으면 웹훅에 보냅니다. 세 언어의 main 입니다.

Go 만 보내는 것이 우리 코드 — 파이썬·TS 는 SDK 의 기본 보내기(BasePushNotificationSender·DefaultPushNotificationSender)를 쓰고, Go 는 SDK 의 HTTPPushSender 대신 직접 짠 hookSender 를 씁니다. 까닭과 그 대가는 4장에서 봅니다.

다른 요청 둘 — 70명이면 두 대·사흘, 0명이면 Task 다음에 바로 REJECTED

Go 서버에 70명·2박(출발지 없음)을, 파이썬 서버에 0명을 보냈습니다.

  • 70명은 45인승과 25인승 한 대씩(하루 1,050,000원 × 3일) — vehicles 는 45인승을 앞에 둡니다(SCENARIO §2.7). 출발지가 없으면 출발 미정.
  • 0명은 단계를 하나도 밟지 않았습니다. choose_buses 가 먼저 거절하니, 실행기가 쉬지도 않고 REJECTED 를 싣습니다 — 거절은 오래 걸리지 않습니다.

저장된 Task 셋 — 같은 COMPLETED, 이력 넷, 다른 것은 수의 모양

2장의 폴러가 마지막에 받은 GetTask 답(이력 제한 없음)입니다. 파이썬 서버의 아티팩트와, Go 서버의 같은 자리입니다.

  • 파이썬 서버는 데이터 파트의 수를 600000.0·2.0 으로 냅니다 — protobuf Struct 의 수는 double 입니다(4부). TS·Go 는 600000.
  • 이력은 셋 다 넷 — 사용자 메시지 하나와 단계 글 셋입니다. 단계 글을 이력에 언제 옮기는지는 서버마다 달라(5부), 도중에 물으면 이력의 길이가 다릅니다(2장).

1장 퀴즈

Q. 교통 에이전트에 0명을 맡기면서 returnImmediately 를 켜면, 클라이언트가 받는 Task 의 상태는 무엇이고 그 뒤에 무엇이 일어납니까?

A. 받는 것은 SUBMITTED 입니다 — 세 서버 모두 실행기의 첫 Task 에서 답을 냅니다(5부). 그 직후 실행기가 쉬지 않고 REJECTED 를 싣습니다(0명의 대본에서 task SUBMITTED 바로 다음이 status REJECTED). 그러니 클라이언트는 다음에 물을 때 이미 끝난 작업을 보게 됩니다.

2장

폴링 — GetTask 반복과 그 비용

스펙의 폴링 → 계획표로 묻는 폴러 → 실행 명세 → 2초마다 → 못 본 단계 → 세 서버 → 8초마다 → 탭의 한 번 → historyLength 0 → 값의 표

폴링은 가장 쉬운 길이고, 스펙도 그 값을 적어 두었다 — 늦고, 헛물음이 생긴다

§3.1.3 은 GetTask 를 "typically used for polling the status of a task initiated with Send Message" 라고 소개합니다. §3.5.1 은 세 전달 방식을 나란히 놓고 폴링을 이렇게 적습니다.

§3.5.1 Polling (Get Task)이 장에서 재는 것
"Client periodically calls Get Task"물음의 간격 — 2초와 8초
"Simple to implement, works with all protocol bindings"폴러는 JSON-RPC 요청 두 가지(SendMessage·GetTask)뿐
"Higher latency, potential for unnecessary requests"단계를 늦게 보거나 아예 못 보는 것, 바뀐 것 없는 답
"Best for: Simple integrations, infrequent updates, clients behind restrictive firewalls"들어오는 연결을 받을 수 없는 클라이언트 — 웹훅과의 차이(4장)
시계로 재지 않는다 — "얼마나 늦나" 를 밀리초로 찍으면 이 기계에서는 실행마다 달라집니다. 이 장은 몇 번 물었고, 그중 몇 번이 새 소식이었고, 몇 바이트를 받았나를 셉니다. 그 수가 실행마다 같도록 묻는 때를 계획표로 정합니다(다음 슬라이드).

계획표로 묻는 폴러 — n 번째 물음은 받은 뒤 1초 + n × 간격

11/poll.py 는 SDK 없이 urllib 으로 SendMessage(returnImmediately) 한 번, 그다음 GetTask 를 되풀이합니다. 묻는 고리입니다.

  • 교통 에이전트는 단계 하나에 4초(--step-ms 4000), 물음은 받은 뒤 1초부터 2초의 배수마다 — 물음과 단계 경계가 늘 1초 떨어집니다. 이 기계가 잠깐 느려져도 어느 물음이 어느 단계를 보는지가 바뀌지 않게 하려는 것입니다.
  • 몸통의 바이트 수는 "timestamp" 를 빼고 셉니다 — 시각 문자열은 끝의 0 을 줄여 써서(4부) 순간마다 길이가 다릅니다.

실행 명세 — 서버 셋에 세 가지로 묻는다

2초마다·8초마다·historyLength 0 으로 2초마다. 8초마다 묻는 것만 탭을 지나 와이어를 남깁니다.

먼저 한 번 데운다 — 서버의 첫 작업은 답이 늦게 나와(처음 쓰는 길을 데우는 중) 계획표가 밀릴 수 있습니다. 그래서 폴러는 시작하자마자 곧장 거절될 0명 요청을 한 번 보냅니다. 서버 출력의 [교통] 거절 줄이 그것입니다.

2초마다 물으면 일곱 번 — 그중 셋은 바뀐 것 없는 답이다

파이썬 서버에 2초 간격으로 물은 결과입니다. 줄마다 물음 번호, 받은 몸통 바이트, 이력의 메시지 수, 새 소식인지, 상태와 글입니다.

  • 1·2번은 SUBMITTED, 3·4번은 배차 요청 접수, 5·6번은 기사 배정 — 짝수 번째 물음은 모두 그대로 입니다. 단계 하나(4초)에 두 번 물으니 하나는 헛물음입니다.
  • 답은 물을수록 무거워집니다 — 397B 에서 1280B. 끝의 GetTask 는 아티팩트와 이력 넷을 통째로 싣습니다.

차량 확정 은 한 번도 보지 못했다 — 폴링은 지나간 상태를 놓친다

세 번째 단계 글은 1장의 스트림에는 있었는데(ask) 폴러의 일곱 줄에는 없습니다.

받은 뒤서버에서 일어난 일폴러가 본 것
0초SUBMITTED(1초·3초) SUBMITTED
4초WORKING 배차 요청 접수(5초·7초) 그것
8초WORKING 기사 배정(9초·11초) 그것
12초WORKING 차량 확정 → 배차 확인서 → COMPLETED — 한꺼번에(13초) COMPLETED
GetTask 는 "지금" 만 준다 — 마지막 단계는 실행기가 쉬지 않고 아티팩트와 COMPLETED 를 이어 싣기 때문에 1밀리초도 "지금" 이었던 적이 없습니다. 폴러가 아무리 자주 물어도 그 사이에 끼어들 수 없습니다. 지나간 단계 글은 이력에 남아 있을 뿐입니다(13초의 history 4).

세 서버 — 같은 일곱 번, 이력의 길이와 바이트는 서버마다

TS·Go 서버에 같은 계획표로 물었습니다.

  • TS 는 3번(첫 WORKING)부터 이력이 둘 — 상태 글을 받는 즉시 이력에도 붙이기 때문입니다(5부). 그래서 TS 의 GetTask 는 지금의 단계 글을 status.message 와 history 에 두 번 싣습니다(탭). 파이썬·Go 는 다음 상태가 올 때 옮깁니다.
  • Go 가 가장 가볍습니다(합계 4246B). 같은 3번 답이 파이썬 620B, Go 518B — 차이의 대부분은 Go 가 이력의 사용자 메시지에 contextId·taskId 를 채우지 않는 것(10부)과 파이썬의 30.0 입니다.

8초마다 물으면 세 번 — 물음은 줄지만 단계 둘을 놓치고, 끝도 늦게 안다

간격만 8초로 바꿨습니다(탭을 지나는 판).

  • 세 서버 모두 SUBMITTED → 기사 배정 → COMPLETED. 배차 요청 접수 와 차량 확정 은 못 봤습니다.
  • 헛물음은 없어졌지만, 작업은 12초에 끝났는데 폴러는 17초에야 압니다. 간격이 길수록 끝을 아는 것이 최대 그 간격만큼 늦습니다 — §3.5.1 의 "Higher latency" 입니다.

탭에 남은 GetTask 한 번 — 요청은 id 하나, 답은 Task 통째

TS 서버에 둘째로 물은 GetTask(기사 배정)입니다.

바뀐 것이 없어도 통째로 — GetTask 에는 "지난번 이후로 바뀐 것만" 을 청하는 필드가 없습니다(GetTaskRequest 는 tenant·id·history_length 셋). 줄일 수 있는 것은 이력뿐이고, 그것이 다음 슬라이드입니다.

historyLength: 0 이면 몸통이 절반 아래로 — 줄이는 것은 이력뿐

같은 2초 계획표에 "historyLength": 0 을 붙였습니다. §3.2.4 "0: No history should be returned" — 세 서버의 그 뜻은 5부에서 봤습니다.

  • 세 서버 모두 history 0, 합계는 4968·5774·4246B 에서 2337·2329·2336B 로 — 서버마다 달랐던 무게가 거의 같아졌습니다. 이력의 모양 차이가 사라졌기 때문입니다.
  • 남는 차이는 마지막 답의 아티팩트(427·419·420B)뿐 — 파이썬의 600000.0 같은 수 모양입니다.

실행과 도착 — 요청에 실은 설정은 여섯 건, Create 한 설정은 다섯 건

웹훅 자리에는 시험 쪽 중계기(11/relay.py, 4장)를 두고, 클라이언트는 두 설정의 끝 알림이 다 지나간 뒤 중계기가 받은 것을 토큰별로 찍습니다. 단계 하나는 2초 — Create 가 첫 단계보다 먼저 닿게 하는 여유입니다.

세 서버가 같다 — Create 한 설정은 SUBMITTED Task 를 받지 못한다

  • tok-inline 은 task SUBMITTED 부터 여섯 건, tok-create 는 WORKING 부터 다섯 건 — 설정이 생기기 전의 이벤트는 다시 보내 주지 않습니다. 첫 Task 를 놓치지 않으려면 요청에 실어야 합니다.
  • 두 설정이 있으면 이벤트마다 두 번 POST 합니다. 클라이언트가 토큰으로 모아 찍은 까닭은 두 설정 사이의 도착 차례가 섞이기 때문입니다 — 파이썬은 asyncio.gather, TS 는 Promise.all 로 동시에 보내고(base_push_notification_sender.py:80, server/index.js:2591), Go 는 하나씩 보내되 설정을 맵에서 꺼내는 차례가 그때그때입니다.

와이어의 설정 — configuration 안에 returnImmediately 와 나란히

세 클라이언트가 보낸 SendMessage 의 configuration 입니다.

  • 세 클라이언트 모두 같은 두 필드(url·token)를 보냈습니다. 빈 값을 쓰는지만 다릅니다 — Go 는 "taskId": "" 를 내보냅니다. 서버는 어차피 그 자리를 새 작업 id 로 채웁니다(TS 는 pushConfig.taskId = taskId, server/index.js:3086).
  • 답은 5부와 같은 SUBMITTED Task 입니다. 설정을 받았다는 표시는 답에 없습니다.

Create 의 답은 저장된 설정 그대로 — 세 서버 모두 클라이언트가 준 id 를 지켰다

  • §3.1.7 Outputs: "Created configuration with assigned ID". id 를 준 요청에는 세 서버 모두 그 hook-2 를 그대로 돌려줬습니다.
  • Go 의 답만 키 차례가 taskId·id·token·url — 구조체 필드 차례입니다(3부에서 본 Go 카드와 같은 까닭).

id 를 주지 않으면 — 파이썬 서버는 작업 id 를 붙여, 둘째 설정이 첫째를 덮는다

Create 에도 id 를 주지 않고(--no-id) 파이썬 서버에 같은 일을 했습니다.

  • 답의 id 가 작업 id 와 같습니다. 파이썬 SDK 는 빈 id 를 작업 id 로 채웁니다(server/tasks/push_notification_config_store.py:19) — 요청에 실은 첫 설정도 같은 id 를 받았고, 저장소는 "같은 id 면 지우고 새로" 둡니다(inmemory_push_notification_config_store.py:56).
  • 그래서 tok-inline 은 첫 Task 하나만 받고 끊겼습니다. TS 는 crypto.randomUUID()(server/index.js:2488), Go 는 새 UUID(a2asrv/push/store.go:80)를 붙이므로 둘 다 남습니다.
설정 id 는 클라이언트가 정해 두자 — 스펙은 빈 id 를 어떻게 채울지 정하지 않았습니다. 한 작업에 설정을 여럿 단다면 id 를 직접 주어야 서버에 따라 하나가 사라지지 않습니다. 설정 목록으로 이것을 다시 보는 것은 5장입니다.

Q. 클라이언트가 returnImmediately 로 작업 id 를 받자마자 Create 로 웹훅을 걸었습니다. 웹훅이 받는 첫 알림은 무엇이고, SUBMITTED 를 받으려면 어떻게 해야 합니까?

시험 쪽 중계기 — 수신기 앞에서 "끝 알림이 지나갔다" 를 알려 준다

푸시는 작업이 저장된 뒤에 갑니다(파이썬 active_task.py:231→:235, Go agentexec.go:427→:461). 그래서 GetTask 가 COMPLETED 를 봤을 때 마지막 푸시는 아직 날아가는 중일 수 있습니다. 몇 초 쉬어 보는 대신, 수신기 앞에 둔 중계기에 묻습니다.

넘기고 나서 적는다 — forward 가 수신기의 답을 받은 뒤에야 기록하고 깨우므로, /wait 가 돌아왔다면 수신기는 이미 그 줄을 찍었습니다. 경로 /11141 처럼 포트를 적으면 그 수신기로 넘깁니다. 이 장의 실행은 모두 이 장치로 끝을 맞춥니다.

실행 — 에이전트 셋, 탭 셋, 중계기 하나, 수신기 셋

교통 에이전트는 같은 언어의 수신기에 보냅니다. 시험 쪽(11/notify.py)은 SDK 없이 설정을 실은 SendMessage 를 보내고, 중계기에서 끝 알림을 기다린 뒤 GetTask 로 작업의 끝을 봅니다.

수신기 셋이 같은 여섯 줄 — 스트림과 같은 이벤트, 같은 차례

  • 여섯 줄은 1장의 스트림 대본과 같은 이벤트, 같은 차례입니다 — §4.3.3 "allowing push notifications to deliver the same event types as real-time streams". 폴링이 놓친 차량 확정 도 왔습니다(2장).
  • 변화 하나에 POST 하나 — 헛물음이 없습니다. 대신 클라이언트가 HTTP 서버를 열어 두고, 에이전트가 거기에 닿을 수 있어야 합니다.

파이썬 SDK 서버가 보낸 POST — application/json, 토큰은 X-A2A-Notification-Token

파이썬 에이전트 앞 탭에 남은 둘째 POST(첫 단계)입니다. 첫 POST 의 Task 는 뒤에서 견줍니다.

  • 몸통은 {"statusUpdate": …} — JSON-RPC 봉투(jsonrpc·id·result)가 없습니다. 스트림의 result 안쪽만 옵니다.
  • 머리의 이름은 SDK 의 것입니다(base_push_notification_sender.py:102). Content-Type 은 httpx 의 json= 이 붙인 application/json — §4.3.3 견본의 application/a2a+json 이 아닙니다.

TS SDK 서버 — application/a2a+json, 보낼 때마다 "보냈다" 한 줄

  • Content-Type 은 SDK 상수 A2A_CONTENT_TYPE(server/index.js:2036)이고, 토큰 머리 이름은 바꿀 수 있는 옵션 tokenHeaderName 의 기본값입니다(:2554).
  • TS 는 푸시를 "보내고 잊는다" — 응답을 기다리지 않고 다음 이벤트로 갑니다(_sendPushNotificationIfNeeded, :3415). 한 작업 안의 차례는 작업마다 이은 약속 사슬(notificationChain)이 지킵니다. 마지막 셋의 "보냈다" 가 [교통] 완료 뒤에 몰린 까닭입니다.

Go — SDK 의 보내기를 쓰지 않았다, 우리 hookSender 가 보낸다

Go SDK 의 push.HTTPPushSender 는 토큰을 A2A-Notification-Token(X- 없이)에 싣고, 기본값으로 루프백·사설망 주소를 막습니다(a2asrv/push/sender.go:40·:60). 이 덱의 웹훅은 127.0.0.1 이니 그대로는 닿지 않습니다. 그래서 교통 에이전트는 직접 짠 보내기를 씁니다.

AuthenticationInfo 를 주면 — 파이썬과 우리 Go 는 둘 다, TS 는 Authorization 만

설정에 "authentication": {"scheme": "Bearer", "credentials": "hook-secret"} 과 토큰을 함께 실었습니다(--auth Bearer:hook-secret). 받는 쪽은 기록만 하는 중계기, 앞에 탭 하나입니다.

  • TS 는 토큰을 버렸다 — authentication 이 있으면 Authorization 을 붙이고 토큰 머리는 붙이지 않습니다(_buildAuthHeaders, server/index.js:2665). 토큰으로 문을 지키는 수신기는 TS 에이전트의 알림을 모두 거절하게 됩니다.
  • 우리 Go 보내기는 처음에 §4.3.3 의 MUST 를 어겼다 — hookSender 가 cfg.Auth 를 읽지 않아 토큰만 실었습니다. 이 탭에서 드러나 8장에서 고쳤고, 위 캡처와 위 코드는 고친 뒤의 것입니다. SDK 의 HTTPPushSender 는 scheme 이 bearer·basic 일 때만 붙입니다(sender.go:175). 파이썬은 scheme 과 credentials 가 다 있으면 무엇이든 붙입니다(base_push_notification_sender.py:104).

토큰을 확인하는 수신기 — 다르면 401, 견주기는 걸린 시간이 새지 않게

완성 수신기는 찍기만 했습니다. 11/hook_check 는 시작할 때 받은 토큰(--token tok-ok)과 머리의 토큰을 견줘, 다르면 401 로 돌려보냅니다. 파이썬과 TS 입니다.

Go 판과 실행 — 맞는 토큰은 204 여섯, 틀린 토큰은 401 여섯

  • 세 판 모두 일정 시간 견주기(hmac.compare_digest·timingSafeEqual·subtle.ConstantTimeCompare)를 씁니다. == 는 다른 글자를 만나는 즉시 멈춰, 걸린 시간으로 앞 글자부터 맞혀 볼 틈을 줍니다.
  • §4.3.3 의 다른 MUST — "validate the task ID matches an expected task" — 는 이 수신기가 하지 않습니다. 토큰만으로는 어느 작업의 알림인지 가리지 못하니, 작업마다 다른 토큰을 주는 것이 첫걸음입니다(proto: "A token unique for this task or session"). 서명까지는 8장입니다.

401 을 받은 에이전트 — 셋 다 작업은 끝까지, 다시 보내지도 않는다

틀린 토큰의 세 실행(파이썬 → TS 수신기, TS → Go, Go → 파이썬)입니다.

  • 여섯 번 모두 401 이어도 GetTask 는 COMPLETED — 푸시가 실패해도 작업은 실패하지 않습니다. 셋 다 재시도하지 않습니다(§4.3.3 의 MAY).
  • 파이썬·TS 는 실패를 서버 출력에 적습니다(스택까지). 우리 Go hookSender 는 처음에 상태 코드를 보지 않아 아무것도 적지 않았고, 8장에서 고친 뒤로는 거절마다 push rejected 한 줄을 적습니다(고친 뒤). Go SDK 의 HTTPPushSender 는 2xx 가 아니면 기록하고, FailOnError 를 켜면 오류를 돌려줘 처리기가 작업을 FAILED 로 바꿉니다(sender.go:193·:201, agentexec.go:462).

4장 퀴즈

Q. 토큰으로 문을 지키는 hook_check 앞에 TS 교통 에이전트를 붙이고, 설정에 토큰 tok-ok 와 authentication(Bearer) 을 둘 다 실었습니다. 수신기는 무엇을 찍고, 작업은 어떻게 끝납니까?

A. 여섯 번 모두 거절 401: token=- 을 찍습니다. TS SDK 서버는 authentication 이 있으면 Authorization 만 붙이고 토큰 머리를 붙이지 않기 때문입니다(탭의 TS 요청에 X-A2A-Notification-Token 이 없다). 작업은 그래도 COMPLETED 로 끝납니다 — 401 은 작업을 멈추지 않습니다(401 을 받은 에이전트). 이런 수신기는 Authorization 도 볼 줄 알아야 합니다.
