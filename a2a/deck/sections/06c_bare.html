카드를 받아 고른다 — JSONRPC 이고 판이 1.0 인 첫 인터페이스

§8.3.2: "Parse supportedInterfaces if present, and select the first supported transport", "Prefer earlier entries". 이 클라이언트가 아는 것은 JSON-RPC 의 1.0 하나라, 그것과 맞는 첫 칸이 답입니다.

  • 판은 Major.Minor 만 — §3.6 이 패치 번호를 "MUST not be considered" 라고 하니 split(".")[:2] 로 둘만 견줍니다. 서버 쪽의 판 검사와 같은 규칙입니다.
  • 카드 경로 — 받은 주소 끝의 / 를 떼고 붙입니다. 주소에 경로가 있을 때 SDK 셋이 서로 달랐던 자리입니다(3부).

봉투와 판 헤더 — 요청은 받은 주소가 아니라 고른 인터페이스의 url 로

§3.6.1: "Clients MUST send the A2A-Version header with each request". 헤더가 없으면 서버는 0.3 으로 읽습니다(2장).

  • iface["url"] — 카드를 받은 주소와 같을 까닭이 없습니다(§8.3.2 "Use the correct URL for the selected transport"). 뒤의 시험은 이 점을 써서 요청을 와이어 탭으로 돌립니다(와이어).
  • tenant — 고른 인터페이스에 있으면 params.tenant 에 그대로(§8.3.2 넷째 규칙, 3부). 숙소 카드에는 없어 실리지 않습니다.
  • 이어 말하기 — message(text, ids) 가 앞 답의 두 id 를 메시지에 붙입니다.

스트림 — Content-Type 이 갈림길, data 하나가 JSON-RPC 응답 하나

SSE 파서는 2부의 것에서 data: 줄만 남겼습니다. 새로운 것은 그 앞의 갈림길과, 이벤트마다 result 를 꺼내는 일입니다.

  • get_content_type() — 스트림을 청해도 첫 이벤트 전의 오류는 application/json 하나로 옵니다(5장, 파이썬·TS SDK 도 그랬다). 그때는 JSON 으로 읽어 result 가 오류를 알립니다.
  • 이벤트마다 봉투 — data 에는 {"jsonrpc", "id", "result"} 가 통째로 실립니다(5장). 꺼낸 result 가 StreamResponse 입니다.

StreamResponse 는 키 하나짜리 객체 — 그 키가 곧 종류다

막는 호출의 result({"task": …})는 task·message 둘 가운데, 스트림의 이벤트는 넷 가운데 하나만 가진 oneof 입니다. 그래서 같은 show 하나로 둘 다 읽습니다.

  • id 를 담은 필드가 다르다 — task 는 id, statusUpdate·artifactUpdate 는 taskId. 이어 말하려면 어느 이벤트에서든 두 id 를 주워야 합니다(퀴즈).
  • 글 파트만 — 견적의 DataPart 는 건너뜁니다. 서버마다 수의 꼴이 달라(4부) 세 언어의 출력이 갈리기 때문입니다.

대본 넷 — 막는 호출로 한 작업, 스트림으로 또 한 작업

①② 는 SendMessage 로 되물음에 답해 끝내고, ③④ 는 SendStreamingMessage 로 날짜를 바꿔 같은 일을 합니다. 아래는 파이썬 SDK 판 완성 에이전트(탭 너머)에 붙인 결과입니다.

④ 에 task 줄이 없다 — 파이썬 SDK 판 에이전트는 이어 말하기의 스트림을 Task 없이 시작합니다(5부). 그래도 클라이언트는 artifactUpdate 의 taskId 로 같은 작업을 따라갑니다. 20명·11-06 은 양평이 가장 쌉니다.

TypeScript — fetch 의 본문은 ReadableStream, 글로 바꿔 줄을 자른다

구조는 파이썬과 같습니다(card·rpc·show·main 구역). 다른 곳이 몰린 stream 구역입니다.

  • TextDecoderStream — 바이트 조각을 UTF-8 글로 바꾸며 조각 경계에 걸린 한글을 이어 줍니다. 서버 쪽에서 setEncoding 으로 막았던 그 문제입니다(5장).
  • 헤더 이름 — res.headers.get("content-type") 는 대소문자를 가리지 않고, 값에 ; charset=utf-8 이 붙을 수 있어 startsWith 로 봅니다.
  • ...ids — 새 작업이면 ids 가 undefined 이고, 펼침은 아무 키도 넣지 않습니다(message, rpc 구역).

Go — 읽을 것만 구조체로, oneof 는 포인터 넷

map[string]any 로 읽으면 단언이 줄마다 붙습니다. 와이어에서 쓰는 필드만 구조체로 적고 나머지는 Unmarshal 이 버리게 둡니다.

  • oneof = nil 이 아닌 포인터 하나 — show 는 switch 로 ev.Task != nil 부터 차례로 묻습니다.
  • 묻어 넣은 ids — statusUpdate·artifactUpdate 의 taskId·contextId 가 바깥 구조체의 필드처럼 풀립니다.
  • Text *string — 글 파트가 아니면 nil. 빈 글("")과 "글이 아님" 을 가릅니다.

Go 가 보내는 메시지 — 빈 id 는 omitempty 로 뺀다

새 작업에 "taskId": "" 를 보내도 세 SDK 서버는 "없음" 으로 읽었습니다(4부). 그래도 보내지 않는 쪽이 깔끔합니다.

  • 같은 ids 를 받을 때도, 보낼 때도 씁니다 — 태그의 omitempty 는 읽을 때는 아무 일도 하지 않습니다.
  • 키의 차례는 구조체 필드의 차례입니다(messageId·role·taskId·contextId·parts). 봉투는 맵이라 알파벳 차례가 됩니다(와이어).
  • 스트림은 2부처럼 iter.Seq 로 내주고, 오류 응답이면 이벤트 하나를 내고 끝납니다(stream 구역).

여섯 서버에 같은 대본 — SDK 셋, 맨손 셋, 다른 줄은 하나

파이썬 클라이언트를 완성 에이전트(SDK) 셋과 맨손 서버 셋에 차례로 붙였습니다. 포트 10686 은 파이썬 SDK 서버 앞의 탭, 10681·10682 는 TS·Go SDK, 10683~10685 는 맨손 파이썬·TS·Go 입니다. 머리줄과 task WORKING 줄만 골랐습니다.

  • 나머지 줄(견적의 숙소·금액, 되물음의 글)은 여섯 번 모두 같았습니다. TS·Go 클라이언트의 열두 번도 같았습니다 — 셋을 다 펼친 표는 7장.
  • task WORKING 이 없는 한 번이 파이썬 SDK 서버입니다. 맨손 서버 셋은 TS·Go SDK 서버와 같은 쪽입니다(1장).

와이어로 본 세 요청 — 뜻은 같고, 키 차례와 Accept 가 다르다

파이썬 SDK 서버는 카드에 탭의 주소(--url http://127.0.0.1:10686/)를 적었고, 세 클라이언트는 카드의 url 을 따랐으니 요청이 모두 탭을 지났습니다. 각 클라이언트의 첫 SendMessage 입니다.

  • Accept: */* — 코드에 없는 헤더를 Node 의 fetch 가 붙였습니다. urllib·net/http 는 붙이지 않습니다.
  • Go 의 봉투는 id 부터 — 맵이라 키가 알파벳 차례입니다. 메시지는 구조체라 적은 차례 그대로입니다.

6장 퀴즈

Q. 파이썬 SDK 서버에 ④ 를 스트림으로 이어 말했더니 task 이벤트 없이 artifactUpdate 로 시작했습니다. 맨손 클라이언트가 Task 에서만 두 id 를 주웠다면 ④ 다음에 한 번 더 이어 말할 수 있었겠습니까? 실제 클라이언트는 어떻게 합니까?

A. ④ 의 이벤트는 artifactUpdate 와 statusUpdate 뿐이었으니(대본) Task 에서만 주웠다면 ④ 에서는 새 id 를 하나도 얻지 못합니다 — 이번에는 ③ 의 id 가 남아 있어 같은 작업이지만, 첫 마디부터 스트림이 Task 없이 오는 서버라면 이어 말할 길이 없습니다. 그래서 show 는 갱신 이벤트의 taskId·contextId 에서도 id 를 줍습니다(show 구역) — Task 로 시작하지 않는 스트림(5부)을 견디는 방법입니다.

7장

맨손 구현을 SDK 로 두드려 보기 — 교차 3×3 두 벌

무엇을 견주나 → SDK 클라이언트 × 여섯 서버 → 대본은 두 가지뿐 → 다른 한 줄의 까닭 → 맨손 클라이언트 × 여섯 서버 → SDK 클라이언트의 요청 셋 → 정리

두 벌의 교차표 — 클라이언트 셋 × 서버 여섯

맨손 서버가 "A2A 서버" 라면 어느 SDK 클라이언트가 붙어도 SDK 서버와 같은 대화가 나와야 하고, 맨손 클라이언트도 어느 SDK 서버와든 말이 통해야 합니다. 서버 여섯(SDK 셋 + 맨손 셋)을 띄워 두고 두 번 돌렸습니다.

가 — SDK 클라이언트 셋 × 서버 여섯, task WORKING 이 없는 칸은 셋

열여덟 번의 머리줄과, 이어 말한 뒤에 찍힌 task WORKING 줄만 골랐습니다. 나머지 줄은 아래 두 대본 가운데 하나와 같습니다.

빠진 칸은 모두 10680(파이썬 SDK 서버) — 클라이언트의 언어와 상관없이 서버가 정합니다. 맨손 서버 셋(10686·10684·10685)은 세 SDK 클라이언트 모두에게 TS·Go SDK 서버와 같은 대본으로 답했습니다.

대본은 두 가지뿐 — 열여덟 칸이 둘 가운데 하나와 글자까지 같다

파이썬 SDK 서버의 대본과 맨손 Go 서버의 대본입니다(둘 다 파이썬 ask). 다른 열여섯 칸은 서버에 따라 이 둘 가운데 하나와 같았습니다.

1장의 합격선을 넘었다 — 목표 대본은 파이썬 ask 하나와 맨손 서버 셋이었습니다. 이번에는 세 언어의 SDK 클라이언트 모두가 맨손 서버 셋과 같은 줄을 주고받았습니다. 숫자와 말이 같은 것은 업무를 workshop 모듈이 정하기 때문입니다.

다른 한 줄 — 이어 말하기의 스트림을 Task 로 시작하느냐

"30명" 다음의 task WORKING 은 둘째 스트림의 첫 이벤트입니다. 서버 여섯이 두 쪽으로 갈립니다.

나 — 맨손 클라이언트 셋 × 서버 여섯, 같은 자리에 같은 빈칸

6장의 클라이언트 셋을 같은 서버 여섯에 붙였습니다. 여기서도 머리줄과 task WORKING 줄만 골랐습니다. 10686 은 파이썬 SDK 서버 앞의 탭입니다.

SDK 없이도 SDK 서버 셋과 통했다 — 카드 읽기, 인터페이스 고르기, 막는 호출, 이어 말하기, 스트림 두 번이 열여덟 번 모두 끝까지 갔고, 빠진 줄은 파이썬 SDK 서버 앞에서만입니다(6장의 대본).

SDK 클라이언트 셋의 요청 — 맨손 서버는 셋 다 받았다

맨손 파이썬 서버 앞의 탭이 본 첫 스트림 요청입니다(파이썬·TS·Go ask 차례). 메서드·configuration·id·role 줄과 헤더만 골랐습니다.

  • JSON-RPC id — 파이썬·Go SDK 는 UUID 문자열, TS 는 수 1. 맨손 서버는 둘 다 받아 그대로 돌려줍니다(2장).
  • "configuration": {} — 파이썬·TS 는 빈 설정을 싣고 Go 는 뺍니다. 맨손 서버는 historyLength 하나만 읽으니 상관없습니다.
  • Accept: text/event-stream — 세 SDK 모두 스트림 요청에 붙였습니다. 6장의 맨손 클라이언트는 붙이지 않았고, 서버 여섯 모두 그래도 SSE 로 답했습니다.

Q. Go ask 를 맨손 Go 서버에 붙인 칸에는 "30명" 다음에 task WORKING 이 찍혔고, 같은 Go ask 를 파이썬 SDK 서버에 붙인 칸에는 없었습니다. 이 차이를 만든 것은 클라이언트입니까, 서버입니까? 어떻게 알 수 있습니까?

A. 서버입니다. 파이썬 SDK 서버(10680) 앞에서는 파이썬·TS·Go ask 셋 모두 그 줄이 없었고, 다른 다섯 서버 앞에서는 셋 모두 있었습니다(가 벌). 맨손 클라이언트 셋으로 바꿔도 같은 자리만 비었습니다(나 벌). 파이썬 SDK 서버가 이어 말하기의 스트림을 Task 없이 시작하기 때문입니다(5부).

느린 연결 하나 — 파이썬 맨손 서버는 그동안 아무에게도 답하지 않는다

왜 파이썬만 — 연결을 받는 방식이 셋이 다르다

3장에서 본 "한 번에 하나" 의 값입니다. 자물쇠가 필요 없던 까닭이 곧 이 약점입니다.

서버연결을 받는 방식반쪽 머리 하나에

Node node:http스레드 하나지만 읽기를 기다리며 막히지 않는다다른 연결을 그대로 처리

  • ThreadingHTTPServer 에 자물쇠를 더한 서버는 11부의 웹훅 수신기에서 봅니다. 17부(운영)의 시간 제한은 클라이언트 쪽 기한이고, 서버가 느린 클라이언트를 끊는 설정은 이 책에서 다루지 않습니다.

ProtoJSON 의 정수 — int32 는 "2" 도 받는다

A2A 의 JSON 은 ProtoJSON 입니다(4부). historyLength 는 proto 에서 optional int32 history_length = 3;(a2a.proto 의 GetTaskRequest)이고, ProtoJSON 의 표는 int32 를 이렇게 적습니다.

proto 타입JSONprotobuf.dev/programming-guides/json 의 설명
int32, fixed32, uint32number"JSON value will be a number. Either numbers or strings are accepted. Empty strings are invalid. Exponent notation (such as 1e2) is accepted in both quoted and unquoted forms."
  • 쓰는 쪽은 수, 읽는 쪽은 둘 다 — "historyLength": "2" 는 ProtoJSON 으로 맞는 입력입니다.
  • 맨손 셋은 받지 않는다 — 파이썬 type(raw) is not int, TS Number.isInteger(4장), Go *int 로의 Unmarshal. 셋 다 ProtoJSON 보다 좁습니다. 그런데 Go 는 좁기만 한 것이 아니었습니다 — 다음 슬라이드.

오류를 버린 Unmarshal — "2" 는 &0 이 되고, 수 id 는 "" 가 됐다

고치기 전의 Go 맨손 서버는 getTask·cancelTask 에서 json.Unmarshal(raw, &p) 의 오류를 버렸습니다. 그 구조체(ID string, HistoryLength *int)에 문제의 입력을 넣어 무엇이 남는지 봤습니다.

  • 오류가 나도 끝까지 채운다 — "historyLength":"2" 뒤의 id 도 읽혔습니다. 그리고 HistoryLength 는 nil 이 아니라 &0 — 포인터를 먼저 만든 뒤 타입이 맞지 않음을 알았습니다.
  • 그래서 고치기 전 서버는 — "이력 2개" 를 청한 요청에 View(t, 0), 곧 history 키가 없는 답(4장의 0 과 같은 꼴)을, "id": 5 에는 find("") 의 -32001 과 taskId "" 를 돌려줬습니다. 파이썬·TS 맨손은 같은 두 요청에 -32602 와, taskId "5" 를 실은 -32001 로 답했습니다(고친 뒤의 Go 와 같다). 이 부를 쓰며 찾은 결함입니다.

고친 코드 — 오류를 -32602 로, id 는 바이트로 받아 손으로

새 params 구역입니다. getTask 는 readTask 와 findRaw 를, cancelTask 는 findRaw 를 부릅니다(4장의 get 구역도 바뀌었다).

  • id 를 json.RawMessage 로 — 그러면 Unmarshal 이 실패할 수 있는 필드는 historyLength 하나뿐이고, 오류의 뜻이 하나로 정해집니다.
  • 수 id 는 "없는 작업" — 파이썬(str(5))·TS(String(5)) 맨손과 같은 답을 고르려고, 받은 글자 5 를 그대로 taskId 로 알립니다.

고친 뒤 — 맨손 셋이 줄마다 같다

끝난 작업(이력 셋) 하나에 GetTask 를 historyLength 2 와 "2" 로, 그리고 GetTask·CancelTask 를 "id": 5 로 보냈습니다. 고친 뒤 Go 서버를 쓰는 6부의 캡처는 모두 다시 떠서 달라지지 않았음을 확인했습니다.

오류는 버리지 않는다 — Go 의 Unmarshal 은 실패해도 구조체를 반쯤 채워 둡니다. 버린 오류 하나가 "이력 2개" 를 "이력 0개" 로 바꿨습니다.

SDK 셋의 답 — "2" 를 받은 것은 proto 에서 만든 해석기

Q. 고치기 전의 Go 맨손 서버에 {"id": "…", "historyLength": "2"} 로 GetTask 를 보내면 이력이 몇 개 왔겠습니까? 고친 뒤에는 무엇이 옵니까? ProtoJSON 으로 보면 어느 쪽도 맞는 답이 아닌 까닭은?

A. 0개(history 키 없음)입니다 — Unmarshal 이 오류를 내면서도 HistoryLength 를 &0 으로 남겼고(lax_params), 서버는 오류를 버리고 0 으로 잘랐습니다. 고친 뒤에는 -32602 Invalid parameters(historyLength)입니다(고친 뒤). ProtoJSON 은 int32 에 "numbers or strings are accepted" 라고 하므로(표) 맞는 답은 이력 2개 — 파이썬·TS SDK 의 답입니다(SDK 셋).
