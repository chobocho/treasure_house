원리 I: 앱

termux-app 의 소스를 따라 터미널 한 장이 뜨기까지

Termux 앱이 하는 일은 생각보다 적습니다. 화면에 글자를 그리고, 가상 터미널(PTY) 하나를 열어 셸을 붙이고, 앱이 죽지 않게 붙들고, 처음 켤 때 리눅스 유저랜드를 풀어 놓습니다. 나머지는 전부 패키지의 일입니다. 이 부는 그 적은 일을 핀 고정한 termux-app 소스로 봅니다.

2장

터미널 에뮬레이터 — 글자를 해석하는 곳

셸이 내보내는 것은 글자만이 아닙니다. "커서를 3행으로", "빨간색으로", "화면 지우기" 같은 명령이 이스케이프 시퀀스로 섞여 옵니다. 그것을 해석하는 것이 에뮬레이터입니다.

설명용

무엇을 흉내 내나

TerminalEmulator.java 의 머리 주석은 이 클래스가 "X 윈도 시스템의 xterm 의 일부를 흉내 내고, xterm 은 DEC 의 VT100 의 일부를 흉내 낸다" 고 적습니다. 참고 문서로 xterm 의 제어 시퀀스 목록, ANSI 이스케이프 코드, VT220·VT510 참고서 등을 꼽습니다.

그래서 앱은 셸 환경에 TERM=xterm-256color 를 넣습니다(AndroidShellEnvironment.java 41행). 256색 표는 TerminalColorScheme.java 에 있고, 이 덱의 캡처 배색도 그 첫 16색에서 가져왔습니다.

3장

PTY — 셸과 화면을 잇는 가짜 터미널

셸은 자기가 진짜 터미널에 붙어 있다고 믿어야 줄 편집과 작업 제어를 합니다. 리눅스는 그 믿음을 위해 의사 터미널(PTY)을 줍니다. 한쪽 끝(master)은 앱이, 다른 끝(slave)은 셸이 잡습니다. Termux 는 이 일을 C 코드 한 함수로 합니다.

설명용

create_subprocess ① — PTY 를 연다

/dev/ptmx 를 열면 master 가 생기고, grantpt·unlockpt·ptsname_r 로 짝이 되는 slave 의 이름을 얻습니다. 그리고 두 가지를 켜고 끕니다: UTF-8 모드(IUTF8)를 켜고, 흐름 제어 (IXON·IXOFF)를 끕니다 — 주석대로 Ctrl+S 가 화면을 멈추지 않게 하려는 것입니다.

소스 발췌

create_subprocess ② — 자식이 slave 를 잡는다

  • 부모(앱)는 자식의 pid 와 master 를 들고 돌아갑니다.
  • 자식은 안드로이드의 자바 프로세스가 막아 둔 시그널을 전부 풀고, setsid() 로 새 세션의 우두머리가 된 뒤 slave 를 열어 표준 입력·출력·오류(0·1·2)에 붙입니다.
소스 발췌

create_subprocess ③ — 환경을 갈고 셸이 된다

앱의 환경을 통째로 지우고(clearenv) Termux 의 환경으로 채운 뒤, 작업 디렉터리로 옮기고 execvp 로 셸이 됩니다. 실패하면 그 오류를 터미널에 찍고 끝납니다. 3부 7장에서 말한 "세션은 execvp() 로 자식을 만든다" 가 바로 이 줄입니다.

소스 발췌

무엇을 execvp 하나

세션을 열 때 앱은 $PREFIX/bin 에서 셸을 고릅니다(5부 4장의 발췌: login·bash· zsh·fish·sh 순). 다섯이 다 없거나 안전(failsafe) 세션을 열면 마지막 수단으로 안드로이드의 /system/bin/sh 를 씁니다 — 로그인 셸로 띄우지 않는 까닭도 주석에 있습니다: 망가진 ~/.profile 이 시작을 막을 수 있기 때문입니다.

망가진 환경을 고칠 때 안전 세션을 쓰는 법은 15부에서 다룹니다.

소스 발췌

1~3장 퀴즈

Q. Termux 에서 긴 출력을 보다가 무심코 Ctrl+S 를 눌렀습니다. 일반 리눅스 터미널이라면 화면이 멈췄을 텐데 Termux 에서는 어떻습니까? 그 까닭은 어느 코드에 있습니까?

A. 멈추지 않습니다. create_subprocess() 가 PTY 를 만들 때 termios 의 흐름 제어 (IXON·IXOFF)를 꺼 둡니다 — 주석에 "Ctrl+S 가 화면을 멈추지 않게" 라고 적혀 있습니다 (terminal-emulator/src/main/jni/termux.c).
설명용

4장

TermuxService — 앱이 죽지 않게 붙드는 것

화면(액티비티)은 사용자가 다른 앱으로 가면 언제든 사라질 수 있습니다. 그래서 세션은 액티비티가 아니라 서비스가 들고 있습니다.

설명용

포그라운드 서비스와 알림

포그라운드 서비스는 알림을 하나 띄워야 합니다. Termux 를 켜면 알림 줄에 늘 떠 있는 그 알림이 이것입니다. 매니페스트의 FOREGROUND_SERVICE 권한(3부)도 이것 때문입니다. 알림이 있는 동안 안드로이드는 이 프로세스를 함부로 치우지 않지만, 팬텀 프로세스 킬러는 다른 이야기입니다(8부).

소스 발췌

웨이크락 — CPU 가 잠들지 않게

알림의 "Acquire wakelock" 을 누르거나 termux-wake-lock 을 치면 이 함수가 돕니다. CPU 를 깨워 두는 부분 웨이크락과 와이파이를 계속 쓰게 하는 와이파이 락을 함께 잡고, 배터리 최적화가 켜져 있으면 해제를 요청합니다. 배터리를 쓰는 만큼 필요할 때만 잡습니다(11부).

소스 발췌

5장

부트스트랩 — 처음 켤 때 풀려 나오는 리눅스

Termux 를 설치하고 처음 켜면 "Installing…" 이 잠깐 뜹니다. 그 몇 초 동안 $PREFIX 전체가 생깁니다.

설명용

설치기의 머리 주석

(1)이 중요합니다. $PREFIX 가 이미 있으면 맞다고 믿고 아무것도 하지 않습니다. 그래서 설치기는 망가진 $PREFIX 를 남기지 않으려고 스테이징 디렉터리에 먼저 풀고 마지막에 옮깁니다.

소스 발췌

zip 은 APK 의 네이티브 라이브러리 안에 있다

어셈블리의 .incbin 은 파일을 그대로 바이트로 박아 넣는 지시입니다. 컴파일러가 아키텍처를 보고 그 아키텍처의 부트스트랩 zip 하나를 공유 라이브러리에 싣고, 자바 쪽은 JNI 로 그 바이트를 받아(getZip) 풉니다. README 가 말하는 "앱과 함께 실려 오는 최소 패키지" 가 이렇게 실려 옵니다. zip 자체는 termux-packages 의 릴리스로 만들어집니다(6부).

소스 발췌

링크는 목록으로 오고, 마지막에 옮긴다

zip 은 심볼릭 링크를 담지 못합니다. 그래서 링크는 SYMLINKS.txt 라는 목록으로 오고, 설치기가 Os.symlink 로 하나씩 세웁니다. 목록이 없으면 실패로 봅니다. 다 되면 스테이징 디렉터리를 이름만 바꿔(renameTo) 접두사로 만듭니다 — 이름 바꾸기는 한 번에 일어나므로 반쯤 된 $PREFIX 가 남지 않습니다.

소스 발췌

6장

sharedUserId — 플러그인이 같은 uid 로 도는 법

Termux:API·Boot·Widget 같은 플러그인은 별개의 앱입니다. 그런데 Termux 의 파일을 읽고 Termux 의 셸을 부릅니다. 3부의 샌드박스 규칙대로라면 불가능한 일입니다.

설명용

같은 uid 를 나눠 쓴다

  • 안드로이드 문서: 둘 이상의 앱이 같은 sharedUserId 를 쓰고 인증서가 같으면 같은 uid 를 받고, 서로의 데이터에 접근할 수 있다.
  • Termux 와 모든 플러그인은 com.termux 를 씁니다(${TERMUX_PACKAGE_NAME} 가 빌드 때 채워짐).
  • 그래서 README 는 설치처(F-Droid·GitHub·Play)를 섞지 말라고 합니다 — 설치처마다 서명 키가 달라, 섞으면 같은 uid 를 못 받습니다.

출처: 캡처 · developer.android.com manifest-element(sharedUserId) · termux-app README 1.3

소스 발췌

그런데 sharedUserId 는 폐지 예정이다

개발자 문서는 sharedUserId 를 API 29 부터 폐지 예정(deprecated) 으로 표시하고, 쓰지 말라고 강하게 권합니다. 다만 이미 쓰는 앱은 이 값을 지울 수 없다고도 적습니다 — 옮겨 갈 길이 없기 때문입니다. API 33 에는 새로 설치할 때부터 무시하게 하는 sharedUserMaxSdkVersion 이 생겼습니다.

README 에 따르면 Google Play 판은 sharedUserId 를 뺐고, 그래서 F-Droid 판 위에 Play 판을 덮어 설치하면 실패합니다(1·2부).

출처: developer.android.com manifest-element · termux-app README 1.3.3

문서 근거

7장

RUN_COMMAND — 다른 앱이 Termux 에 일을 시킨다

플러그인이 아닌 앱(예: Tasker)도 Termux 의 셸로 명령을 돌릴 수 있습니다. 그 문이 RUN_COMMAND 인텐트입니다. 문이 넓은 만큼 자물쇠가 둘입니다.

설명용

문과 두 자물쇠

  • termux-app 위키: 0.95 부터 Termux 세계에 속하지 않은 서드파티 앱이 RunCommandService 로 인텐트를 보내 Termux 앱의 문맥에서 명령을 돌릴 수 있다.
  • 자물쇠 ① — 부르는 앱이 com.termux.permission.RUN_COMMAND 권한을 받아야 한다(필수).
  • 자물쇠 ② — 사용자가 ~/.termux/termux.properties 에 allow-external-apps = true 를 적어야 한다(필수).

출처: termux-app 위키 RUN_COMMAND-Intent 1·1.2.1·1.2.2 · 캡처

소스 발췌

왜 둘 다인가

권한은 사용자가 안드로이드 설정에서 그 앱에 따로 허락해야 하고(보호 수준 dangerous), 거기에 더해 allow-external-apps 는 사용자가 Termux 안에서 직접 적어야 합니다. 권한을 가진 앱이 있더라도 사용자의 명시적 선택 없이는 Termux 의 셸을 쓸 수 없게 한 것입니다. 5부 1장 표의 "틈 세 개" 중 하나가 이 API 이고, 위키는 이런 API 가 넓은 접근을 줄 때 이중으로 보호한다고 적습니다. 보안은 14부에서 다시 봅니다.

출처: 위키 Termux-file-system-layout 1.3.1

8장

termux.properties — 앱의 설정 파일

Termux 앱의 설정 화면은 작습니다. 대부분의 설정은 텍스트 파일 하나에 적습니다.

설명용

키는 소스에 정의돼 있다

추가 키 줄(extra-keys), 종 소리(bell-character), 스크롤백 줄 수(terminal-transcript-rows), 뒤로 가기 키의 동작(back-key) 등이 있습니다. 설정 파일을 고친 뒤에는 termux-reload-settings 를 부르거나 앱을 다시 열어야 적용됩니다(15부의 enforce-char-based-input 예).

소스 발췌

이 기기의 ~/.termux

이 기기에는 termux.properties 하나만 있습니다. 글꼴(font.ttf)이나 배색(colors.properties)을 바꾸면 이 디렉터리에 파일이 늡니다(7부 Termux:Styling). 설정을 고친 뒤에는 termux-reload-settings 로 다시 읽힙니다.

4~9장 퀴즈

Q. 설치 중에 전원이 꺼져 $PREFIX 가 반쯤 만들어졌다면, 다음에 켤 때 설치기는 어떻게 합니까? 설치기가 그런 일을 피하려고 쓰는 두 장치는?

A. 설치기는 $PREFIX 가 있으면 맞다고 믿고 설치를 건너뜁니다(머리 주석 (1)). 그래서 반쯤 된 $PREFIX 가 생기지 않게 ① 먼저 스테이징 디렉터리에 풀고(남은 것이 있으면 지우고 시작, (3)), ② 다 끝난 뒤 renameTo 로 이름만 한 번에 바꿔 접두사로 만듭니다. 전원이 나가도 남는 것은 스테이징뿐입니다.
