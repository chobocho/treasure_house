보안과 개인정보

무엇을 열어 두고, 무엇을 지키나

Termux 는 폰 안에서 가장 힘이 센 앱 가운데 하나가 되기 쉽습니다 — 셸이 있고, 네트워크가 있고, 다른 앱이 명령을 부탁할 문이 있습니다. 이 부는 그 문들과 자물쇠, 실제로 뚫렸던 사례, 그리고 이 덱이 사용자의 폰에서 캡처를 뜨며 지킨 규칙을 봅니다.

1장

무엇을 지키나 — 위협 모델

같은 키로 서명된 앱(sharedUserId), 열어 둔 서버, 읽지 않고 실행한 스크립트, 다른 앱, 공유 저장소. 다섯 문은 이 덱의 앞 부들이 하나씩 보였습니다(4·10·5·7·3부).

설명용

다른 앱에게 여는 문과 자물쇠

RUN_COMMAND 권한의 보호 수준은 dangerous — 사용자가 앱마다 직접 허락해야 합니다(4부). 파일을 내주는 프로바이더(…files)와 명령 서비스가 같은 권한을 요구하고, 문서 프로바이더(…documents)는 MANAGE_DOCUMENTS 를 요구합니다.

이 기기 캡처

GitHub 판의 서명 키는 공개돼 있다

README 의 보안 경고: GitHub 의 APK 는 커뮤니티와 공유된 테스트 키(testkey_untrusted.jks)로 서명된다. 공식 개발자 키가 아니며 누구나 이 키로 릴리스를 만들 수 있다 — 곧 GitHub 판 위에 설치되는 악성 "업데이트" 를 누구나 위조할 수 있다. termux/termux-app 이 아닌 곳(텔레그램 등)에서 받은 GitHub 판은 조심하라.

위조 업데이트가 설치되면 그것이 곧 Termux 이고, 같은 키로 서명된 것이니 4부의 sharedUserId 규칙도 막지 못합니다.

문서

① Tasker — ../../../usr/bin/bash

Termux:Tasker 는 ~/.termux/tasker/ 의 스크립트만 돌리게 되어 있었지만, 받은 실행 파일 경로의 정규 경로를 확인하지 않았습니다. 그래서 ../../../usr/bin/bash 를 이름으로 주면 아무 명령이나 Termux 문맥(루팅했다면 root 문맥)에서 돌았고, 플러그인 호스트가 아닌 아무 앱이나 그 인텐트를 보낼 수 있었습니다.

고친 것: ① 호출하는 앱에 RUN_COMMAND(dangerous 권한)을 요구 ② 정규 경로를 먼저 구하고, 폴더 밖 경로는 allow-external-apps=true 일 때만. 글은 이 "안드로이드 권한 + 앱 설정" 이중 모델이 신뢰하지 않는 앱에 권한을 주지 않는 한 적당한 방어라고 적습니다 — 7부에서 본 README 의 두 문이 여기서 왔습니다.

문서

② Widget — 런처가 쥔 토큰

Termux:Widget 은 토큰을 만들어 두고, 정적 바로가기를 만들 때마다 런처 앱에 그 토큰을 건넸습니다. 토큰을 쥔 런처나, 바로가기 선택 화면을 띄운 악성 앱은 스크립트를 돌릴 수 있었습니다.

고친 것: Android 8 이상에서는 고정(pinned) 바로가기 API — 안드로이드가 바로가기 데이터를 보관해 런처도 토큰을 모른다. 옛 토큰과 바로가기를 무효로 하고, 정규 경로가 ~/.shortcuts·~/.termux 밖이거나 깨진 링크인 것은 보이지 않게 했다 — 7부에서 본 Widget README 의 규칙입니다.

문서

③ 모든 파일을 누구나 읽었다

파일 프로바이더의 readPermission 이 android.permission.permRead 였는데, Termux 는 그 권한을 선언한 적이 없었습니다. 글은 튜토리얼이나 질의응답에서 베껴 온 가짜 권한으로 보인다고 적습니다. 결과는 /data/data/com.termux/files 아래의 모든 파일을 어떤 앱이든 읽을 수 있는 상태 — 쓰기는 읽기 전용 모드라 막혔습니다.

고친 것: 읽기 권한을 RUN_COMMAND 로 조용히 바꾸고, 파일을 여는 모드도 읽기 전용에서 읽기·쓰기로 넓혔습니다. 앞 장의 캡처에서 …files 프로바이더가 요구하는 권한이 바로 그것입니다.

신고와 공개의 약속

Termux 의 보안 정책:

  • 외부 신고는 선별 뒤, 유효하면 보통 영업일 3일 안에 확인 답을 한다.
  • 수정은 보통 90일 안에, 실제로 악용되고 있으면 7일 안을 목표로.
  • 수정이 배포되고 30일 뒤 GitHub 보안 권고나 termux.dev 의 보안 글로 공개한다.
  • 보상 프로그램은 없다 — 서비스가 무료이고 후원금으로는 개발비도 못 채운다. 다만 심각한 취약점에는 소액 보상을 예외로 줄 수 있다.

앞 장의 글이 그 공개의 예입니다 — 글 스스로 "0.118.0 릴리스 30일 뒤" 라고 적습니다(표의 날짜로는 38일 뒤).

4장

내가 여는 문 — sshd 와 서버

10·11부에서 본 대로: sshd 는 처음에 비밀번호 인증이 켜져 있습니다. 위키는 공개 키 인증을 "권장" 으로 적고, 키를 올린 뒤 PasswordAuthentication no 로 끄라고 합니다. 바깥에 내놓아야 한다면 위키가 가장 안전하다고 꼽는 것은 Tor 어니언 서비스입니다. 이 덱의 서버 실험은 모두 127.0.0.1 에서 끝났습니다.

14부 퀴즈

Q. 어떤 자동화 앱이 "Termux 명령 실행" 권한을 요구합니다. 허락하면 무엇을 할 수 있게 되고, 그 앱이 할 수 있는 일을 줄이려면 Termux 쪽에서 무엇을 확인해야 합니까?

A. 권한을 받은 앱은 0.118 부터 파일 프로바이더로 Termux 의 파일을 읽고 쓸 수 있습니다(2장 ③). 명령을 직접 돌리는 RUN_COMMAND 인텐트는 여기에 더해 ~/.termux/termux.properties 의 allow-external-apps=true 도 요구하고(4부), Termux:Tasker 도 정해진 디렉터리 밖의 실행에는 그 값이 필요합니다. 그러니 그 값을 켜 두지 않는 것이 첫째입니다.
