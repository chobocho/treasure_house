9부

proot 와 리눅스 배포판

루트 없이 다른 배포판을 띄우는 법 — 이 덱이 태어난 곳

이 덱은 폰 위의 Termux 안, 그 안에 띄운 우분투(proot) 안에서 만들어졌습니다. proot 는 루트 권한 없이 "다른 배포판의 뿌리 디렉터리" 에 들어가 있는 것처럼 보이게 해 주는 프로그램입니다. 어떻게 속이는지, 무엇을 못 속이는지, 그리고 그 값이 얼마인지를 이 세션 자신을 재료로 봅니다.

이 부의 캡처는 대부분 proot 쪽(#) 에서 떴습니다. "Termux 쪽($)" 캡처도 사실은 이 proot 의 추적을 받는 Termux 프로그램입니다(3부 "누가 이 셸을 지켜보고 있다").

1장

proot 는 무엇을 흉내 내나

proot 매뉴얼의 첫 문장: "PRoot is a user-space implementation of chroot, mount --bind, and binfmt_misc." 셋 다 원래 루트가 있어야 하는 기능입니다.

원래 기능하는 일proot 의 옵션
chroot어떤 디렉터리를 새 / 로-r / --rootfs
mount --bind바깥 경로를 안쪽 자리에 붙이기-b / --bind
binfmt_misc다른 CPU 용 프로그램을 에뮬레이터로-q (QEMU)

매뉴얼은 이어서 말합니다 — 기술적으로는 ptrace, "모든 리눅스 커널에 있는 권한 없는 시스템 호출" 에 기댄다고. 손님(guest) 프로그램이 커널에 하는 요청을 proot 가 번역해서 호스트 커널에 넘깁니다.

출처: proot doc/proot/manual.txt Description·Options

문서

root 처럼 보일 뿐이다

Termux 위키의 PRoot 문서가 굵게 적어 둔 경고입니다: proot 는 시스템 호출의 인자와 반환값을 꾸며 프로그램이 root 로 도는 것처럼 보이게 할 수 있지만, 진짜 권한 상승은 전혀 주지 않는다. 커널이나 하드웨어 상태를 바꾸려는 프로그램은 동작하지 않는다.

매뉴얼의 -0(--root-id) 설명도 같습니다: 패키지 관리자처럼 "기술적 이유 없이" root 를 요구하는 프로그램을 위해 신원을 꾸미고, 소유자 바꾸기 같은 일이 성공한 척 합니다. 그리고 "fakeroot 에 비하면 꽤 제한적" 이라고 덧붙입니다. 3부에서 본 대로 이 세션의 id 는 0 이지만 보조 그룹은, 5부에서 본 대로 SELinux 문맥은 진짜 앱의 것이었습니다.

출처: 위키 PRoot(revid 6573) · proot manual.txt -0·-i

문서

시작 — 스스로 추적받겠다고 선언한다

proot 는 fork 한 자식에서 PTRACE_TRACEME 로 "부모가 나를 추적한다" 고 선언하고, 스스로 멈춘 뒤 (SIGSTOP), seccomp 필터를 걸고 나서야 손님 프로그램을 exec 합니다. 그 뒤로 이 자식과 그 자손은 모두 proot 의 추적을 받습니다.

이 기기 캡처

2장

전부 가로채지는 않는다

ptrace 만 쓰면 추적자는 모든 시스템 호출마다 두 번 — proot 소스의 말로 sysenter 와 sysexit — 깨어납니다. proot 는 앞 장의 발췌에 있던 한 줄 — "seccomp mode 2 로 성능을 높인다" — 로 이 비용을 줄입니다. 커널 안에 작은 필터 프로그램(BPF) 을 넣어, 목록에 있는 호출만 추적자에게 넘기고 나머지는 커널이 바로 처리하게 합니다.

설명용

필터의 문장 두 개

호출 번호를 비교해 같으면 SECCOMP_RET_TRACE, 아니면 다음 비교로 건너뜁니다. 목록 끝까지 맞는 것이 없으면 마지막 문장(화면 밖 136행, end_arch_section)이 SECCOMP_RET_ALLOW — 추적자를 깨우지 않고 통과입니다.

소스 발췌

목록에는 98개가 있다 — getpid 는 없다

목록은 대부분 경로를 받는 호출(open·stat·execve·chdir· getcwd…)과 소켓·uname·wait4 같은 것입니다. 경로를 rootfs 안으로 바꿔야 하는 호출만 멈추면 되기 때문입니다. 확장(--link2symlink·--sysvipc·-0 등)이 켜지면 각자의 목록이 여기에 더해집니다.

이 기기 캡처

목록을 필터로 펼친다

호출 번호는 아키텍처마다 다르므로(arm64 의 openat 과 x86-64 의 openat 은 번호가 다르다) 아키텍처 구역마다 목록을 다시 펼칩니다. 필터는 prctl(PR_SET_SECCOMP, …) 한 번으로 걸리고, 한 번 걸린 필터는 자손에게 그대로 물려집니다.

소스 발췌

getcwd 를 가로채면 — 들어갈 때

손님이 getcwd 를 부르면 proot 는 커널에 그 호출을 넘기지 않습니다. 호출 번호를 "아무것도 안 하는 호출" 로 바꿔 버립니다. 진짜 커널의 현재 디렉터리는 호스트 경로(…/rootfs/root 같은)라 손님에게 보여 줄 수 없기 때문입니다.

소스 발췌

getcwd 를 가로채면 — 나올 때

나올 때 proot 는 자기가 기억해 둔 손님 쪽 경로(tracee->fs->cwd)를 손님 프로세스의 메모리에 직접 써 넣고(write_data) 길이를 반환값으로 돌려줍니다. 손님은 진짜 커널이 답한 줄 압니다.

소스 발췌

값을 재 보자 — 가로채는 호출과 아닌 호출

같은 프로그램(exp/syscall_loop.c)이 같은 횟수를 부릅니다. 다른 것은 호출 하나뿐입니다.

필터를 끄는 스위치

1장의 발췌에서 필터는 환경 변수 PROOT_NO_SECCOMP 가 없을 때만 걸렸습니다. 이 변수를 두면 모든 호출이 추적자를 거칩니다. 실행(execve)이 EPERM 으로 실패하면 proot 는 커널 버그를 의심하며 이 변수를 1 로 두라고 알려 줍니다.

이 세션은 필터를 끈 상태를 재지 않았습니다 — 이 세션을 띄운 proot 자신의 설정을 바꿔야 하기 때문입니다.

소스 발췌

1~2장 퀴즈

Q. proot 안에서 파이썬 프로그램이 느립니다. 한쪽은 숫자 계산만 하는 반복문, 다른 쪽은 작은 파일 만 개를 os.stat() 하는 반복문입니다. 어느 쪽이 네이티브보다 크게 느려질까요?

A. os.stat() 쪽입니다. stat 계열은 경로를 받으니 98개 목록에 있고, 부를 때마다 proot 가 깨어나 경로를 번역합니다. 계산만 하는 반복문은 시스템 호출을 거의 하지 않아 seccomp 필터가 통과시키고, 추적자가 끼어들 일이 없습니다.

proot-distro 해부

proot 를 직접 부르려면 옵션이 수십 개 필요합니다. proot-distro 는 배포판을 받아 풀고, 그 긴 명령줄을 대신 조립해 주는 파이썬 프로그램입니다. README 의 소개: 루트도, 커널 모듈도, Docker 데몬도 없이 Docker/OCI 이미지로 된 리눅스 사용자 공간을 띄운다.

문서

배포판은 OCI 이미지에서 온다

README 1.4.1 이 적는 설치 과정:

  • 표준 OCI Distribution 프로토콜을 파이썬 urllib 로 직접 말한다. Docker Hub 의 공개 이미지는 옵션 없이.
  • 여러 아키텍처 목록(manifest list)에서 이 CPU 에 맞는 것을 고른다.
  • 층(layer)마다 SHA-256 을 확인한 뒤 캐시에 올린다. 같은 이미지를 다시 설치할 때는 오프라인.
  • 빈 rootfs 위에 층을 차례로 풀고, 하드 링크는 복사본으로, 블록·문자 장치와 FIFO 는 건너뛴다.

위키(revid 6573)는 아직 "Ubuntu (22.04)" 같은 고정 목록을 적고 있습니다 — 위키가 README 보다 오래됐습니다.

소스 발췌

Termux 에서만 붙이는 확장

일반 리눅스 호스트에서는 아무것도 붙이지 않고 돌아갑니다(if not IS_TERMUX: return). 하드 링크 흉내(--link2symlink)는 Termux 형 컨테이너가 아닐 때만, System V IPC 흉내(--sysvipc)와 가짜 커널 판은 --minimal 이 아닐 때만 붙습니다.

소스 발췌

이 세션을 띄운 명령줄

앞의 조립 순서 그대로입니다 — 확장 다섯, --change-id=0:0, --rootfs=., 기본 바인드 셋, 안드로이드 경로들, Termux 의 $PREFIX, 그리고 사용자가 직접 붙인 바인드 하나(<home>/… — 개인정보 검사가 사용자 홈 아래 경로를 가렸습니다). 포트를 옮기는 -p 는 없습니다.

이 기기 캡처

가짜 /proc 파일들

아홉 개의 파일이 /proc 의 자리에, 빈 디렉터리 하나가 /sys/fs/selinux 에 붙어 있습니다. 그래서 proot 안의 uptime 이나 /proc/stat 은 진짜 기기의 값이 아닙니다. 왜 이런 일을 하는지는 다음 슬라이드의 주석에 있습니다.

이 기기 캡처

왜 가짜를, 그리고 왜 그렇게 조심스럽게

첫 단락: 안드로이드가 여러 /proc 파일을 막거나 제한하므로, top·htop 같은 도구가 돌도록 고정된 대체물을 준다. 나머지 단락은 보안 이야기입니다 — 이 디렉터리는 손님이 쓸 수 있는 곳($PREFIX 가 읽기·쓰기로 붙어 있으므로)이라, 심볼릭 링크나 하드 링크로 바꿔치기해 호스트 파일을 /proc/loadavg 자리에 끌어올 수 있었다. 그래서 이름이 아니라 디렉터리 fd 와 O_NOFOLLOW, 링크 수 1 을 확인한다. 곁들여 적힌 사실 하나 — proot 에는 읽기 전용 바인드가 없다.

소스 발췌

커널 판도 가짜다

3부에서 본 6.17.0-PRoot-Distro 의 출처입니다. uname 은 --kernel-release 확장이, /proc/version 은 가짜 파일이 같은 값으로 답합니다. 두 길을 모두 막아야 프로그램이 서로 다른 답을 보지 않습니다.

이 기기 캡처

/sys/fs/selinux 는 비어 있다

명령줄의 sysdata/sys_empty:/sys/fs/selinux 입니다. 배포판의 도구들은 이 디렉터리가 비어 있으면 "SELinux 가 꺼진 시스템" 으로 여깁니다. 그러나 5부에서 본 대로 이 프로세스들의 진짜 SELinux 문맥은 untrusted_app 이고, 커널은 그 규칙을 그대로 집행합니다. 보이지 않을 뿐 꺼진 것이 아닙니다.

이 기기 캡처

proot 의 옵션 한 줄씩

proot-distro 가 쓰는 것: -r·-b·-w(--cwd)·--kill-on-exit· --kernel-release·-i(--change-id)·--link2symlink·--sysvipc· -L, 그리고 포트 옮기기를 켰을 때만 -p. 이 중 --kill-on-exit·--link2symlink·--sysvipc·-L·-p 와, 쓰지 않는 --ashmem-memfd·-H 는 저장소에 든 매뉴얼(5.1.0, 2014-12-12)에 없고 proot.h 에만 있습니다 — 매뉴얼 뒤에 더해진 것들입니다.

이 기기 캡처

4장

하드 링크를 흉내 내기

proot-distro 는 Termux 형이 아닌 모든 컨테이너에 --link2symlink 를 붙였습니다. proot.h 의 설명은 "하드 링크를 심볼릭 링크로 바꾸고, 진짜 하드 링크인 척한다". 이 세션에서 직접 해 봅니다.

안드로이드의 앱 저장소에서 하드 링크가 왜 따로 흉내 내야 하는 대상인지는 이 덱이 출처를 찾지 못했습니다 — 미확인

설명용

ln 은 성공하고, 링크 수는 2 다

손님이 보기에는 평범한 하드 링크입니다. 실제로는 /.l2s/ 에 중간 심볼릭 링크(.l2s.x0001)와 내용을 가진 파일(.l2s.x0001.0002)이 생기고, x·y 는 그것을 가리키는 심볼릭 링크가 됩니다. proot 가 stat 결과를 고쳐 "보통 파일, 링크 2" 로 보여 줍니다.

이 기기 캡처

이 컨테이너가 쌓은 것

만 개가 넘습니다 — 이 컨테이너에서 지금까지 만들어진 하드 링크의 흔적입니다. proot-distro README 는 이 디렉터리를 "link2symlink 의 뒷받침 저장소" 로 적습니다. 심볼릭 링크들이 rootfs 의 절대 경로를 가리키므로 컨테이너 이름을 바꾸거나 옮기면 모두 깨지고, 그래서 proot-distro 에는 이 링크들을 고쳐 쓰는 모듈(l2s.py) 이 따로 있습니다. 두 이름을 모두 지우면 중간 항목도 함께 사라집니다.

출처: proot-distro README 1.5 · l2s.py 머리 주석 · 스냅샷

이 기기 캡처

5장

proot 가 못 속이는 것

proot 는 경로와 신원을 번역할 뿐, 커널의 결정을 바꾸지는 못합니다. 이 세션에서 부딪친 벽들입니다.

설명용

getprop 이 거부된다

/system 은 바인드되어 있어 파일은 보입니다. 그런데 실행하면 "Operation not permitted" 로 126 이 돌아옵니다. 그래서 이 덱은 안드로이드 판·SDK·기기 이름을 이 세션에서 읽을 수 없었고, 사용자가 네이티브 Termux 에서 한 번 돌릴 스크립트(tools/native_facts.sh)를 따로 만들었습니다. 거기서는 같은 getprop 이 답했습니다(0부 "이 기기").

왜 거부되는지 — 미확인.

이 기기 캡처

Termux:API 가 답하지 않는다

7부에서 본 벽입니다. 스크립트와 termux-api 실행 파일은 돌지만 앱의 답이 오지 않아 timeout 이 124 로 끊었습니다. 원인은 미확인.

이 기기 캡처

1024 미만 포트 — -p 의 규칙

-p 를 켜면 1024 미만 포트에 2000 을 더합니다 — bind 는 언제나, connect·sendto 는 localhost 로 갈 때만(port_switch.c 주석). 이 세션의 명령줄에는 -p 가 없었습니다. 그런데 실험 4 는 이 세션에서 80·443 같은 몇 포트가 그냥 열렸음을 보여 줍니다 — 그 결과는 8부 4장에 있고, 까닭은 아직 미확인입니다.

이 기기 캡처

root 가 아니다 — 3부의 id 를 우분투 쪽에서

uid=0(root) 옆에 aid_u0_a123_cache·aid_inet 같은 보조 그룹이 붙어 있습니다. 3장의 /etc/group 손질이 aid_ 이름을 붙였지만 1077 은 이름이 없어 id 가 경고를 냅니다. 그룹 자체는 안드로이드가 이 앱에 준 진짜 값입니다. 신원은 꾸며도 커널이 보는 자격은 그대로입니다.

이 기기 캡처

termux-exec 와 부딪친다

위키의 proot 사용 예는 첫 줄이 unset LD_PRELOAD 입니다. 5부의 termux-exec 가 execve 를 가로채 경로에 $PREFIX 를 붙이는데(위키: "Termux-exec, execve() hook, conflicts with PRoot"), 그렇게 붙은 경로가 rootfs 안에는 없을 수 있습니다. 3장의 명령줄이 $PREFIX 를 같은 경로에 바인드해 두는 것도 Termux 의 도구를 안에서 부를 수 있게 하려는 것입니다(README 1.3.5.1).

출처: 위키 PRoot 1절 · proot-distro README 1.3.5.1

설명용

루트가 있다면 — chroot

위키가 proot 를 "chroot 의 사용자 공간 구현" 이라 부르는 것은 진짜 chroot 가 권한을 요구하기 때문입니다. 루팅한 기기라면 진짜 chroot 로 같은 rootfs 에 들어갈 수 있고, 그때는 시스템 호출을 가로채는 추적자가 없습니다. 이 덱의 기기는 루팅되지 않아 그 길을 재지 않았습니다.

출처: 위키 PRoot · proot 매뉴얼 부제("without privilege/setup")·Description

3~6장 퀴즈

Q. proot 안에서 cat /proc/uptime 이 매번 같은 값을 낸다면, 무엇 때문일까요? 진짜 가동 시간은 어떻게 알 수 있을까요?

A. proot-distro 가 sysdata/uptime 이라는 고정 파일을 /proc/uptime 자리에 붙여 두었기 때문입니다(3장 명령줄). 진짜 값은 그 바인드 밖에서 읽어야 하는데, 안드로이드는 네이티브에서도 /proc/uptime 을 막을 수 있습니다(15부) — 이 덱이 기기 정보를 tools/native_facts.sh 로 따로 모은 것과 같은 까닭입니다.
