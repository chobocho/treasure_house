활용 IV: AI 에이전트와 이 저장소

이 덱은 어떻게 폰 안에서 만들어졌나

이 덱은 폰 안에서, AI 코딩 에이전트(Claude Code)가 사용자의 지시를 받아 만들었습니다. 이 부는 그 작업장을 증거로 봅니다 — 메모리, 프로세스, 규칙 파일, 그리고 이 덱이 도는 컨테이너를 띄운 프로그램마저 같은 도구의 손을 탔다는 사실.

1장

작업장 — 이 세션의 메모리

15GB 의 램 대부분과 스왑의 대부분이 차 있습니다. 이 조건에서 무거운 일을 여럿 돌리면 안드로이드가 앱째로 죽입니다 (8부의 팬텀 프로세스 킬러와 저메모리 킬러). 그래서 이 덱의 계획서는 스스로에게 제한을 걸었습니다 — 동시에 도는 보조 에이전트는 둘까지, JVM 없음, 큰 패키지 빌드 없음, 무거운 일 전에 free -m.

맨 위는 claude 둘 — 이 기기에서는 두 작업 세션(이 덱과 다른 덱)이 함께 돌고 있었습니다(8부의 프로세스 캡처와 같은 모습). 그 아래는 캡처하던 순간 다른 세션이 돌리던 시험(go)과 이 덱의 python3 입니다.

이 기기 캡처

에이전트가 쓴 도구는 어느 쪽 것인가

에이전트는 proot 우분투의 셸에서 일했지만, 덱을 검사한 node 와 커밋한 git 은 PATH 끝에 붙은 Termux 의 것이었습니다(10부). 파이썬과 gcc 는 우분투의 것, 실험의 clang 은 tools/tmx.sh 를 거친 Termux 의 것 — 한 작업 안에서 두 세계를 오갔습니다.

2장

규칙 파일 — 에이전트에게 주는 지시서

이 저장소 맨 위의 CLAUDE.md 는 사람이 에이전트에게 주는 운용 지침입니다 — 덱의 필수 요건(자기완결·키보드 조작·접힌 폰 폭), 작업 순서, 하지 말 것. 이 덱의 PLAN.md 는 그 아래의 더 자세한 계획서이고, 결정 12건은 사용자가 확정해 다시 묻지 않도록 적혀 있습니다.

이 기기 캡처

upstream 도 같은 방식이다 — proot-distro

9부에서 본 proot-distro 저장소에도 2천 줄이 넘는 CLAUDE.md 가 있고, proot_cmd.py 의 머리에는 "Development assisted by Claude Code" 라는 줄이 있습니다. 이 덱이 도는 컨테이너를 띄운 프로그램, 그 컨테이너 안에서 이 덱을 쓴 도구, 그 도구가 읽은 upstream 소스가 같은 방식으로 만들어지고 있습니다(2026-09 기준).

이 기기 캡처

폰에서 에이전트를 오래 돌리려면 — 이 덱이 배운 것

  • 팬텀 프로세스 킬러를 끈다(8부 — 안드로이드 판마다 방법이 다르다). 에이전트는 셸·node·컴파일러를 쉬지 않고 띄운다.
  • 화면을 켜 두고 Termux 를 앞에 둔다 — 화면 밖 앱은 CPU 를 덜 받는다(12부의 README 경고와 같은 규칙).
  • 무거운 일은 하나씩, 보조 에이전트는 적게. 결과는 파일로 남겨 끊겨도 이어 가게.
  • 기기와 닿는 문은 하나로(tools/tmx.sh), 개인정보는 빌드가 막게(14부).

13부 퀴즈

Q. 이 세션에서 node deck/check_deck.js 가 돌았습니다. 이 node 는 bionic 과 glibc 중 어느 libc 에 링크되어 있을까요? 그 근거는?

A. bionic 입니다. 우분투 쪽에는 node 가 없고(캡처), proot-distro 가 PATH 끝에 붙인 $PREFIX/bin 의 Termux node 가 쓰였습니다 — Termux 의 주 저장소(main) 패키지는 NDK 로 지어 bionic 에 링크됩니다(3부). proot 가 /system 을 바인드해 linker64 가 보이므로 우분투 안에서도 돕니다.
