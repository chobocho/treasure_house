6부

원리 III: 패키지 시스템

데비안의 apt·dpkg 가 안드로이드의 앱 데이터 안에서 도는 법

Termux 의 패키지는 데비안과 같은 .deb 이고, 관리자도 데비안의 apt·dpkg 입니다. 다만 모든 패키지가 /data/data/com.termux/files/usr 에 깔리도록 지어졌고, 그것을 짓는 공장(termux-packages)이 따로 있습니다. 이 부는 폰의 pkg 명령에서 시작해 공장까지 거슬러 올라갑니다.

1장

dpkg — 이 기기에 무엇이 깔려 있나

dpkg 는 설치한 모든 패키지를 $PREFIX/var/lib/dpkg/status 한 파일에 적습니다. 그 파일을 4부의 도구 py/pkgstat.py 로 셉니다.

설명용

설치된 패키지

이 기기는 개발 도구를 많이 깔아 큰 편입니다. Maintainer 가 @termux 인 것이 대부분이고, 나머지는 TUR 같은 다른 저장소에서 왔습니다(3장). Essential: yes 는 지우면 Termux 가 망가지는 필수 패키지입니다.

이 기기 캡처

크기로 나눠 보면

절반 넘게가 1 MiB 아래입니다. 크기는 몇 안 되는 큰 도구(code-server·rust·golang·clang)가 차지합니다.

이 기기 캡처

status 파일을 세는 코드

지웠어도 설정 파일이 남으면 deinstall ok config-files 로 문단이 남습니다. 그래서 install ok installed 인 것만 셉니다.

이 기기 캡처

termux-* 명령은 누구 것인가

84개 중 57개가 termux-api 패키지 것입니다(7부). 나머지는 기본 도구(termux-tools), 실행 환경 (termux-core·termux-exec), 앱과 이야기하는 termux-am, 그리고 proot 의 termux-chroot 입니다. 전체 목록은 17부 부록의 명령 색인에 있습니다.

이 기기 캡처

2장

pkg — apt 를 감싼 셸 스크립트

Termux 에서는 apt 대신 pkg 를 쓰라고 합니다. pkg 는 따로 짠 관리자가 아니라, apt 를 부르기 전에 몇 가지를 챙기는 bash 스크립트입니다.

이 기기 캡처

인용하는 소스가 곧 돌고 있는 것

이 덱은 termux-tools 를 설치본과 같은 태그(v1.45.0)에 핀 고정했습니다. 자리표시 넷을 채우고 비교하면 첫 줄 하나만 다릅니다 — #!/bin/bash 가 #!$PREFIX/bin/bash 로. 누가 고쳤는지는 4장에서 봅니다. 그래서 아래 발췌들은 이 폰에서 실제로 도는 pkg 의 줄입니다.

이 기기 캡처

1.46.0+really1.45.0 이라는 판

패키지 판 문자열에는 1.46.0 과 1.45.0 이 함께 들어 있고, 실제로 받는 소스는 v1.45.0 태그입니다 — 레시피의 TERMUX_PKG_VERSION 과 TERMUX_PKG_SRCURL 두 줄이 그것을 말합니다. 레시피 하나가 판·소스 주소· 해시·의존을 전부 적는 것이 termux-packages 의 방식입니다(4장). TERMUX_PKG_ESSENTIAL=true 도 보입니다.

소스 발췌

pkg 는 root 를 거부한다

id -u 가 0 이면 멈춥니다. proot 는 uid 를 0 으로 보여 주므로, 이 덱을 만든 proot 세션에서는 pkg 가 돌지 않습니다. apt 도 마찬가지입니다(3장). 그래서 이 덱은 패키지를 하나도 설치하지 않았습니다.

소스 발췌

pkg 의 하위 명령 → apt

하위 명령을 앞 글자로 받습니다 — pkg in·pkg i·pkg install 이 모두 i* 입니다. up 은 apt update 후 apt full-upgrade 입니다. 아래쪽의 같은 모양 블록은 pacman 용입니다 — Termux 는 apt 대신 pacman 을 쓰는 부트스트랩도 만들 수 있습니다(5장).

소스 발췌

직접 해 보기 — pkg 의 하위 명령은 무엇이 되나

앞 장의 case(apt 갈래)를 위에서부터 차례로 맞춥니다. 처음 맞는 줄에서 멈추므로 info 는 i* 가 아니라 그 위의 inf* 에, update 는 up 이 아니라 upd* 에 걸립니다.

pkg 해석기
실행 검증

install 앞에서 목록을 새로 받을지 정한다

캐시나 목록 파일이 없거나, sources.list 가 캐시보다 새롭거나, 캐시가 1200초(20분)보다 오래되면 apt update 를 먼저 합니다(last_modified 는 초 단위 나이를 돌려줍니다, 102–109행). 그래서 pkg install 은 apt install 보다 "목록이 낡았다" 오류를 덜 냅니다.

소스 발췌

1~2장 퀴즈

Q. pkg rem vim 과 pkg un vim 은 각각 무엇을 할까요? 그리고 pkg up 을 치면 apt 에게는 어떤 명령이 몇 번 갑니까?

A. 둘 다 un*|rem*|rm|del* 에 걸려 apt remove vim 입니다. pkg up 은 up|upg* 에 걸려 미러를 고른 뒤 apt update 와 apt full-upgrade, 두 번 갑니다(pkg.in 409–425).
설명용

3장

저장소 · 미러 · 서명 키

apt 가 패키지를 받는 곳은 $PREFIX/etc/apt/sources.list 에 적혀 있습니다. 공식 저장소는 셋이고, Termux 밖의 사용자 저장소(TUR)와 glibc 저장소가 더해집니다.

설명용

공식 채널 셋

소스 저장소의 디렉터리(packages/·root-packages/·x11-packages/)가 곧 apt 저장소의 채널입니다. root·x11 채널은 root-repo·x11-repo 패키지를 설치하면 켜집니다 — 그 패키지가 하는 일은 sources.list.d 에 한 줄을 넣는 것뿐입니다(data/repos_apt.tsv 의 출처 칸).

소스 발췌

이 기기의 sources.list

기본 저장소가 packages.termux.dev 가 아니라 미러로 바뀌어 있습니다 — termux-change-repo 로 고른 결과입니다. TUR 은 tur-repo 패키지가 넣은 줄입니다.

이 기기 캡처

미러는 어디에 있나

termux-packages 위키의 미러 목록은 대륙별로 나뉩니다 — 아시아, 중국 본토, 유럽, 북아메리카, 오세아니아, 러시아. 대학·재단·개인이 운영합니다. 주 호스트(packages.termux.dev)와 CDN 주소 (packages-cf.termux.dev)도 같은 문서에 있고, 문서는 포크가 이 호스트를 쓰지 말고 저장소를 따로 세우라고 부탁합니다.

pkg 는 $PREFIX/etc/termux/mirrors 의 미러 파일과 그 무게(WEIGHT)로 미러를 고릅니다(pkg.in select_mirror). 1부에서 고르는 법을 봅니다.

출처: 위키 Mirrors 2.2·2.3 · termux-tools@a62f7b2 scripts/pkg.in 13·173–200

문서 근거

apt 가 보는 우선순위 (스냅샷)

설치된 것(dpkg/status)은 100, 저장소는 500 입니다. 같은 이름의 패키지가 여러 저장소에 있으면 우선순위와 판으로 고릅니다. 이 캡처는 날짜가 박힌 스냅샷입니다 — 저장소 목록은 받을 때마다 바뀝니다.

이 기기 캡처

서명 키 — 누구를 믿나

apt 는 저장소의 목록 파일에 붙은 서명을 이 키들로 확인합니다. 키는 termux-keyring 패키지가 넣고(메인테이너 개인 키와 자동 빌드 키), TUR 의 키는 tur-repo 가 넣습니다. 이 덱의 proot 쪽에는 gpg 가 없어 지문은 찍지 않았습니다(data/repos_apt.tsv 의 빈 칸).

출처: termux-packages@7d5b4d3 packages/termux-keyring·tur-repo 디렉터리의 파일

이 기기 캡처

apt 는 root 를 거부한다 — 패치 한 벌

Termux 는 apt·apt-get·apt-mark 의 main() 첫머리에 getuid() == 0 검사를 넣어 짓습니다. Termux 의 apt 가 root 로 돌면 파일 소유가 어긋나 환경이 망가지기 쉽기 때문일 것입니다 — 패치 파일에는 그 까닭이 적혀 있지 않아 이 덱은 추측으로 남깁니다(미확인).

소스 발췌

4장

termux-packages — 패키지를 짓는 공장

저장소의 모든 .deb 는 termux-packages 저장소에서 지어집니다. 패키지마다 디렉터리 하나, 그 안의 build.sh(레시피) 하나와 필요하면 *.patch 들이 있고, build-package.sh 가 레시피를 읽어 짓습니다.

설명용

build-package.sh 의 단계 ① — 준비에서 configure 전까지

단계마다 함수 하나(termux_step_*)이고, 각 함수는 scripts/build/ 의 같은 이름 파일에 있습니다. 레시피가 같은 이름의 함수를 정의하면 그 단계를 바꿔 끼웁니다(termux_step_pre_configure 따위). termux_step_patch_package 가 레시피 디렉터리의 패치를 겁니다.

소스 발췌

build-package.sh 의 단계 ② — configure 에서 massage 까지

설치는 진짜 $PREFIX 가 아니라 빌드용 디렉터리에 하고, 그것을 "massage(주무르기)" 디렉터리로 옮겨 손질한 뒤 .deb(또는 pacman 패키지)로 묶습니다(804–806행).

소스 발췌

massage 단계가 셔뱅을 고친다

패키지의 모든 파일에서 첫 줄이 #!…/bin/… 이면 #!$TERMUX_PREFIX/bin/… 로 바꿉니다(이미 /system/ 이나 접두사로 시작하면 건너뜁니다). 2장에서 pkg 의 첫 줄만 소스와 달랐던 까닭이 이것입니다. 5부의 termux-fix-shebang 과 같은 sed 식이 공장 안에서도 돌고 있는 셈입니다. massage 는 그 밖에도 ELF 의 심벌을 떼고(strip) 안드로이드 링커가 싫어하는 항목을 지웁니다(termux_step_elf_cleaner).

소스 발췌

교차 컴파일 — 폰이 아니라 PC 에서 짓는다

공식 빌드는 PC 에서 NDK 로 교차 컴파일합니다 — 3부에서 본 NDK 헤더 패치의 머리에 적힌 경로 (android-ndk-r28b/toolchains/llvm/prebuilt/linux-x86_64)가 x86-64 리눅스 호스트의 흔적입니다. 위키는 공식 Docker 이미지를 권합니다 — 메인테이너와 같은 환경이라 빌드가 재현되기 때문입니다. 5부에서 본 툴체인 설정이 이때 -Wl,-rpath 를 넣습니다.

이 덱은 이 공장을 돌리지 않았습니다(Docker 도, 큰 빌드도 이 폰에서는 불가 — §9 결정 11). 소스를 읽고, 손으로 .deb 하나를 만드는 것(7장)으로 대신합니다.

출처: 위키 Build-environment 1.3.1 · 5부 8장의 발췌

문서 근거

5장

부트스트랩 zip 이 만들어지는 곳

4부에서 APK 에 .incbin 으로 실려 오던 zip 은 termux-packages 의 스크립트가 만듭니다.

설명용

generate-bootstraps.sh

이미 저장소에 올라간 패키지를 받아 아키텍처 넷(aarch64·arm·i686·x86_64)마다 zip 을 묶습니다. 관리자는 apt 가 기본이고 pacman 으로도 만들 수 있습니다. 주석대로 기본 부트스트랩은 Android 7.0 이상, 10 미만과 호환되게 만듭니다(BOOTSTRAP_ANDROID10_COMPATIBLE=false) — 5부의 W^X 이야기와 이어집니다. README 는 부트스트랩 zip 이 termux-packages 의 릴리스로 나온다고 적습니다.

소스 발췌

6장

새 패키지를 올리려면

termux-packages 위키 "Creating new package" 가 레시피를 쓰는 법을 정리합니다. 첫머리의 요건 셋이 Termux 라는 환경을 잘 보여 줍니다.

  • root 권한이 필요한 일을 하지 않는다.
  • 빌드 디렉터리와 $TERMUX__PREFIX 밖의 파일을 고치지 않는다.
  • 스크립트는 코딩 지침대로 쓴다.

레시피(build.sh)는 bash 스크립트이고 변수(판·소스 주소·해시·의존…)와 필요하면 단계 덮어쓰기 함수를 담습니다 — 2장의 termux-tools 레시피가 그 예입니다.

출처: 위키 Creating-new-package 1.2·1.3

문서 근거

7장

.deb 를 손으로 만든다 (실험 6)

공장을 못 돌리는 대신, 파일 세 개로 가장 작은 Termux 패키지를 만들어 이 폰에 설치했다가 지웁니다. 설치될 경로가 /data/data/com.termux/files/usr/… 라는 것만 빼면 데비안과 같습니다.

설명용

재료 — control 과 스크립트 둘

이 기기 캡처

짓는 스크립트

준비 디렉터리 안에 data/data/com.termux/files/usr/bin 을 통째로 만드는 것이 요점입니다. 소유자를 root 로 적어(--root-owner-group) 만든 사람의 uid 가 패키지에 새지 않게 합니다.

이 기기 캡처

dpkg-deb 로 들여다보기

4부에서 만든 py/deb.py 로도 같은 것을 읽습니다 — .deb 는 ar 묶음 안의 tar 두 개이기 때문입니다.

이 기기 캡처

설치하고, 돌리고, 지운다

proot 의 가짜 root 에서도 dpkg 는 돌았습니다 — apt 와 달리 root 검사 패치가 없습니다. 이 덱이 호스트에 설치한 것은 이 패키지 하나뿐이고, 캡처 안에서 곧바로 지웠습니다(PLAN §8).

이 기기 캡처

dpkg 가 기억하는 것

dpkg 는 패키지가 깐 파일과 디렉터리를 모두 기억해 두었다가 지울 때 씁니다. 디렉터리 /data/data/com.termux/files/usr/bin 은 다른 패키지도 쓰므로 지우지 않고, 파일만 지웁니다.

이 기기 캡처

8장

기기 안에서 짓기

termux-packages 의 빌드 시스템은 Termux 앱 안에서도 돕니다(scripts/setup-termux.sh). 위키의 단서:

  • 모든 패키지가 되지는 않습니다 — 되지 않는 것은 레시피에 TERMUX_PKG_ON_DEVICE_BUILD_NOT_SUPPORTED.
  • termux-exec 가 동작하지 않는 기기는 지원하지 않습니다(5부).
  • 빌드 중에 생긴 파일은 $TERMUX__PREFIX 에 깔리지만 패키지 관리자가 추적하지 않습니다. 그래서 짓기 전에 $HOME 과 $PREFIX 를 백업하라고 권합니다(10부).

3~8장 퀴즈

Q. 어떤 사람이 PC 에서 파이썬 스크립트를 #!/usr/bin/python3 로 써서 Termux 패키지로 만들었습니다. 공식 저장소를 거쳐 설치됐다면 설치된 파일의 첫 줄은 무엇이고, 누가 바꿨습니까? 7장처럼 손으로 만든 .deb 로 설치했다면?

A. 공식 경로로 지었다면 massage 단계의 sed 가 #!/data/data/com.termux/files/usr/bin/python3 로 바꿔 둡니다. 손으로 만든 .deb 에는 그 단계가 없으니 #!/usr/bin/python3 가 그대로 깔리고, 실행될지는 termux-exec 가 걸려 있는지에 달려 있습니다(5부). 그래서 실험 6 의 스크립트는 처음부터 $PREFIX 셔뱅으로 썼습니다.
