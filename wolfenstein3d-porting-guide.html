서문

왜 지금, 울펜스타인 3D를 포팅하는가

이 책은 1992년 id Software가 만든 Wolfenstein 3D의 공개 소스 코드를 직접 받아서, 2026년의 컴퓨터에서 다시 돌아가게 만드는 과정을 한 단계씩 안내합니다. C 언어를 약간 읽을 줄 알고, 명령줄에서 명령어를 칠 수 있다면 충분히 따라올 수 있습니다.

왜 굳이 30년 전 게임일까요? 세 가지 이유입니다.

① 작고 완전하다

전체 코드가 약 2.7만 줄. 한 사람이 한 달이면 전부 읽을 수 있는 분량입니다. "게임 한 편 전체가 머릿속에 들어온다"는 경험은 매우 드뭅니다.

② 원리가 단순하다

레이캐스팅, 고정소수점 수학, VGA 직접 접근, 어셈블리 보조 루프 — 컴퓨터의 밑바닥을 그대로 마주합니다. 추상화 뒤에 가려진 진짜 그림을 봅니다.

③ 포팅의 모든 과제가 압축돼 있다

실모드 16비트 → 보호모드/64비트, DOS → POSIX/Windows, 직접 I/O → SDL, 사운드 카드 → 추상 오디오. 현대 포팅 기법의 거의 모든 사례가 들어 있습니다.

이 가이드를 읽고 나면 할 수 있는 것

  • Wolf3D 원본 소스를 받아서 Windows 11, Linux, Termux(안드로이드) 세 환경에서 실제로 빌드해 실행할 수 있다.
  • 레이캐스팅 렌더러가 어떻게 한 픽셀씩 화면을 그려내는지 코드 단위로 설명할 수 있다.
  • 플랫폼 의존 코드(DOS 인터럽트, VGA, Adlib)를 식별하고 추상 계층으로 분리하는 절차를 안다.
  • 다른 레트로 코드(Doom, Quake, Heretic 등)도 같은 방법론으로 포팅에 착수할 수 있다.

포팅이란 무엇인가 — 원리부터 잡기

"포팅(porting)"이라는 단어는 마치 무거운 짐을 이쪽 항구에서 저쪽 항구로 옮기는 모습을 떠올리게 합니다. 실제로 그렇습니다. 코드라는 짐을 한 운영체제/하드웨어 환경에서 다른 환경으로 옮겨, 같은 동작을 하도록 만드는 일입니다. 그런데 단순히 파일을 복사하는 일이 아니라, 짐 속에 들어 있는 도구들이 새 항구에서도 작동하는지 하나하나 점검하고, 없는 도구는 새로 만들어 끼워 넣는 일입니다.

1.1 컴파일·실행 모델: 무엇이 이식을 어렵게 하는가

C 프로그램은 마치 약속의 종이처럼 보입니다. "이런 입력을 받으면 이런 결과를 내라"라는 약속이죠. 그러나 실제로 그 약속을 지키는 것은 컴파일러가 만들어낸 기계어이고, 기계어는 결국 어떤 CPU 위에서, 어떤 운영체제의 보호 아래, 어떤 라이브러리의 도움을 받아 실행됩니다. 그래서 같은 C 코드도 다음 네 층에서 모두 환경이 다르면 작동하지 않을 수 있습니다.

┌───────────────────────────────────────────┐ │ 4. 라이브러리/툴킷 (libc, SDL, DirectX...) │ ├───────────────────────────────────────────┤ │ 3. 운영체제 ABI (시스템 콜, 파일, 메모리) │ ├───────────────────────────────────────────┤ │ 2. 컴파일러 (GCC, MSVC, Clang) │ ├───────────────────────────────────────────┤ │ 1. 하드웨어 (x86 실모드 ↔ x86_64, ARM…) │ └───────────────────────────────────────────┘ ↑ 각 층마다 "다른 항구"가 될 수 있다

Wolfenstein 3D 원본은 이 네 층이 모두 다릅니다. 1992년 당시 컴퓨터로 가 봅시다.

1.1.1 1992년의 PC: 16비트 실모드 DOS

  • CPU는 Intel 386/486이지만, 실모드(real mode)로 사용. 주소를 세그먼트:오프셋 형태로 16비트씩 두 개로 다룬다.
  • 운영체제는 MS-DOS. 멀티태스킹 없음. 한 프로그램이 메모리 1MB(실제로는 640KB)를 사실상 독점.
  • 그래픽은 VGA 카드를 직접 제어. 0xA0000번지에 픽셀을 쓰면 화면이 바뀜.
  • 소리는 Adlib/Sound Blaster의 OPL2 칩에 레지스터를 직접 쓰는 방식.
  • 키보드/마우스는 인터럽트 핸들러를 직접 가로채는 방식(int 9h 등).
  • 컴파일러는 보통 Borland C++ 3.1 또는 Watcom C. 인라인 어셈블리, far/near 포인터, __far 키워드 등 표준 C가 아닌 확장이 가득.

2026년의 컴퓨터에서는 위 다섯 가지가 전부 사라졌습니다. 그래서 우리가 해야 할 일은:

  1. 실모드 16비트 코드를 64비트(또는 32비트) 보호모드 코드로 옮긴다.
  2. DOS의 BIOS·인터럽트 호출을 OS 라이브러리(POSIX/Win32) 호출로 바꾼다.
  3. VGA 직접 접근을 SDL 같은 추상 그래픽 라이브러리로 바꾼다.
  4. OPL2 직접 제어를 PCM 출력(또는 OPL 에뮬레이터)로 바꾼다.
  5. 컴파일러 확장을 ANSI/ISO C 표준으로 정리한다.

이 다섯 가지가 곧 이 가이드의 큰 줄기입니다.

1.2 두 가지 포팅 전략: "재작성" vs "감싸기"

오래된 코드를 옮기는 방법은 크게 두 갈래입니다.

A. 재작성(Rewrite)

모든 OS 의존 부분을 직접 새 API로 다시 짠다. 코드가 깨끗해지고, 신기능을 넣기 좋다. 그러나 시간이 오래 걸리고 버그가 많이 생긴다.

예: Wolf4SDL — 원본 Wolf3D의 VGA/Adlib/DOS 의존을 모두 SDL 콜로 교체. 결과적으로 "공식 포팅"의 표준이 되었다.

B. 감싸기(Wrap / Emulate)

원본 코드를 거의 그대로 두고, "DOS인 척 흉내 내는" 얇은 계층을 만든다. 빠르고 호환성이 높지만, 새로운 플랫폼 기능을 쓰기 어렵다.

예: DOSBox에서 원본 EXE를 그대로 실행. 코드는 한 줄도 바꾸지 않는다.

이 가이드는 A 전략에 따른 실습입니다. Wolf4SDL이라는 잘 만든 결과물이 이미 있으니, 우리는 그것을 받아 새 환경(Win11, Linux, Termux)에서 다시 빌드하면서, 코드를 따라 읽고 "왜 이렇게 바꿨는지" 이해하는 길을 갑니다.

소스 코드의 역사와 라이선스

코드를 받기 전에, "이 코드는 어디서 왔고, 누가 무엇을 허용했는가"를 알고 가야 합니다. 라이선스를 잘못 이해하면 만든 결과물을 배포할 때 곤란해질 수 있고, 무엇보다 원작자의 의도를 존중하는 일이기도 합니다.

2.1 짧은 연표

연도사건
1992id Software (John Carmack, John Romero 등)가 Wolfenstein 3D 출시. Apogee 퍼블리싱.
1995id Software가 소스 코드를 공개. 처음에는 비상업 라이선스.
1996~2000년대커뮤니티 포팅 시작: NewWolf, Wolf4GW, Wolf4SDL 등 다수.
2007id Software가 라이선스를 GPLv2로 변경 — 자유 소프트웨어로 재배포 가능.
현재GitHub에 여러 미러와 포크가 존재. Wolf4SDL이 사실상 표준 베이스라인.

2.2 GPLv2가 의미하는 것 — 짧고 정확하게

GPLv2(General Public License v2)는 "자유"를 보장하기 위한 라이선스입니다. 다섯 가지로 요약하면:

  • 사용: 누구나, 어떤 목적으로든 사용할 수 있다.
  • 학습: 소스 코드를 읽을 수 있다.
  • 수정: 자신의 목적에 맞게 바꿀 수 있다.
  • 배포: 원본 또는 수정본을 배포할 수 있다. 단, 같은 GPLv2로.
  • 출처 표기: 원본 저작권자 표기를 유지해야 한다.
"전염성(copyleft)" · 우리가 Wolf3D 코드와 결합한 새 코드를 배포할 때, 그 결합물도 GPLv2여야 합니다. 그래서 만약 상업 게임에 Wolf3D 코드를 그대로 가져다 쓰면 문제가 생깁니다. 학습·개인 사용은 전혀 문제가 없습니다.

2.3 코드 ≠ 데이터: 두 개를 분리해서 이해하기

여기서 매우 중요한 구분이 나옵니다. id Software가 공개한 것은 코드뿐이고, 맵·그림·소리는 별개의 저작권을 가진 자산입니다.

분류예시 파일라이선스
코드 (소스).c, .hGPLv2 — 자유
셰어웨어 데이터WOLF3D 1.4 셰어웨어판의 VSWAP.WL1 등무료 배포 허용(원본 그대로)
상용 데이터VSWAP.WL6, MAPHEAD.WL6, GAMEMAPS.WL6, AUDIOHED.WL6, AUDIOT.WL6, VGAGRAPH.WL6 등 (6 episodes)유료 — 직접 구매 필요(Steam/GOG)

이 가이드 실습에서는 셰어웨어 데이터(.WL1)를 사용합니다. 셰어웨어판은 1992년부터 무료로 배포되어 왔으며, id Software 측에서도 학습 목적 사용을 묵인해 왔습니다. 그러나 상업적 재배포는 여전히 불가입니다.

2.4 어떤 포크/포트를 베이스로 할까

"Wolf3D"라는 이름이 붙은 GitHub 저장소가 수십 개 있습니다. 그 중 학습에 가장 적합한 것은 두 가지입니다.

① Wolf4SDL

  • SDL1.2 또는 SDL2로 포팅된 가장 잘 알려진 버전
  • 크로스 플랫폼: Win/Linux/Mac/안드로이드 모두 보고됨
  • 약 4만 줄 — 원본 + 추상 계층
  • 저장소 예: github.com/fabiensanglard/wolf3d, github.com/mozzwald/wolf4sdl 등

② Chocolate-Wolfenstein-3D

  • "Chocolate Doom" 계열의 보수적 포팅
  • 원본 거동을 최대한 보존
  • SDL2 기반, 모던한 빌드 시스템
  • 저장소: github.com/fabiensanglard/Chocolate-Wolfenstein-3D

이 가이드는 Wolf4SDL(SDL1.2 또는 SDL2 분기)을 표준으로 삼되, 핵심 원리 설명은 원본 1992년 코드를 함께 다룹니다.

2.5 이번 장 실습

  • "코드는 GPLv2, 데이터는 별도 저작권"이라는 원칙을 노트에 적어두기
  • 셰어웨어 v1.4 데이터(.WL1 파일들)의 합법적 배포처를 한 곳 알아 두기
  • 자신이 작업할 베이스 — Wolf4SDL — 의 GitHub 페이지를 북마크

개발 환경 준비 — 세 운영체제 모두

"준비"가 사실 가장 큰 산입니다. 한 번 환경을 잘 갖춰 두면 그 뒤로는 매우 빠르게 진행됩니다. 이 장에서 Windows 11, Linux, Termux 세 환경의 기본 도구를 모두 설치합니다. 자신이 쓰는 운영체제 탭만 따라 하면 됩니다.

3.1 공통 준비물

  • 인터넷 연결
  • 관리자(또는 sudo) 권한
  • 여유 공간 약 3GB (도구 + 소스 + 데이터)
  • 텍스트 에디터 — VS Code 권장(세 OS 모두 무료)

3.2 OS별 설치 — 탭으로 분기

Windows 11 환경 구성

4.5 파일명 대·소문자 함정

DOS·Windows는 대소문자를 구별하지 않습니다. 그래서 원본 데이터 파일은 모두 대문자 이름입니다. 그러나 Linux·Termux·macOS는 대소문자를 구별합니다. 코드는 "vswap.wl1"으로 열고, 파일은 VSWAP.WL1이라면 "파일이 없다"는 에러가 나옵니다.

# Linux/Termux에서 안전하게: 전부 소문자로 통일
cd ~/wolf3d-port/data
for f in *.WL1; do mv "$f" "$(echo $f | tr 'A-Z' 'a-z')"; done

Wolf4SDL은 보통 소문자 파일명을 가정합니다. 위 명령으로 한 번에 정리해 두세요.

5.3 헤더 파일들의 관계

거의 모든 .c 파일은 wl_def.h를 인클루드합니다. 그것이 게임 전체의 "공용 사전" 역할을 합니다. wl_def.h가 또 여러 헤더를 끌어들이고, 그렇게 의존 트리가 만들어집니다.

wl_def.h ├─ id_ca.h ├─ id_in.h ├─ id_pm.h ├─ id_sd.h ├─ id_us.h ├─ id_vh.h ├─ id_vl.h └─ version.h │ └─ (실제 .c 파일 50여 개에서 #include "wl_def.h")

5.4 자료(데이터) 파일의 코드 표현

코드 안에서 데이터 파일은 보통 다음 변수들로 가리킵니다.

  • extension — "WL1" 또는 "WL6"로 컴파일타임에 정해진 문자열
  • graphext / audioext / mapext — 그래픽·사운드·맵별 확장자
  • 실제 열기는 OpenAudioFile(), OpenGraphFile(), OpenMapFile()에서 일어남

버전 선택은 version.h의 매크로 — UPLOAD(셰어웨어), GOODTIMES(정식판), SPEAR(Spear of Destiny) — 로 결정됩니다.

소스 코드 읽기 전략 — 효율적으로 머리에 넣는 법

큰 코드를 처음부터 끝까지 한 줄씩 읽는 것은 비효율적이고, 사실 누구도 그렇게 안 합니다. 숙련자가 새 코드베이스를 만났을 때 어떤 순서로 읽는지, 어떤 도구를 쓰는지를 배웁시다.

6.1 "위에서 아래로 vs 안에서 밖으로" — 두 가지 독해 방향

① Top-down (위에서 아래)

main()에서 시작해서 호출하는 함수를 하나씩 따라 내려간다. 게임 흐름을 이해할 때 유리.

약점: 빠르게 깊어져서 길을 잃기 쉽다.

② Bottom-up (밑바닥부터)

가장 작은 유틸 함수부터 시작해서 "이 도구가 무엇을 하는지" 익힌 다음, 점차 큰 함수로 올라간다. 알고리즘을 이해할 때 유리.

약점: 큰 그림이 늦게 잡힌다.

현실에서는 둘을 번갈아 씁니다. 이 가이드에서는 "main()부터 한 프레임이 그려지기까지의 흐름"은 위→아래로(7~9장), "레이캐스팅·텍스처 매핑의 수학"은 아래→위로(10~12장) 다룹니다.

6.5 "왜?" 다섯 번 묻기

읽다가 이상한 코드를 만나면 "왜?"를 다섯 번 물어보세요. 예:

FixedMul(...)  // 왜 그냥 * 가 아니지?
  → 고정소수점 곱셈이라서. 왜 고정소수점?
  → 1992년 386에는 FPU(부동소수점)가 옵션이라서. 왜 옵션?
  → 가격 때문에. 부동소수점 연산이 느리거나 없는 환경이 많았다.
  → 그래서 정수만으로 분수 연산을 흉내 내는 트릭이 표준이었다.
  → 그래서 모든 거리·각도 계산이 정수 기반이다. (납득!)

한 번의 "왜?"가 다섯 번의 깨달음을 줍니다. 코드는 단순한 명령의 모음이 아니라, 그 시대의 제약을 압축한 결정의 기록입니다.

  5. CA_Startup() — 캐시 매니저(데이터 파일 인덱스 읽기)

8.1 GameLoop의 본체

void GameLoop(void)
{
    SetupGameLevel();   // 맵 로드, 적 배치, 변수 초기화
    StartMusic();
    PM_CheckMainMem();
    fizzlein = true;    // "치직" 페이드인 효과

    while (1) {
        PlayLoop();     // ★ 한 레벨이 끝날 때까지 매 프레임 호출
        switch (playstate) {
          case ex_completed:        LevelCompleted(); break;
          case ex_died:             Died();           break;
          case ex_victorious:       Victory();        return;
          case ex_warped:           continue;
        }
    }
}

핵심은 PlayLoop()입니다. 한 프레임 = PlayLoop의 한 회 실행. 모든 비밀이 그 안에 있습니다.

8.2 PlayLoop의 시간 모델 — 70Hz 틱

원본 Wolf3D는 PC의 타이머를 초당 70번 끼어들도록 설정합니다(원래 18.2Hz였던 것을 가속). 그래서 게임 내부의 모든 시간 단위는 "틱" — 1틱 = 1/70초입니다.

// 원본의 시간 측정
tics = TimeCount - lasttimecount;   // 지난 호출 이후 흐른 틱 수
lasttimecount = TimeCount;
if (tics > MAXTICS) tics = MAXTICS; // 너무 큰 점프 방지

SDL 포팅판에서는 SDL_GetTicks()가 밀리초 단위이므로, 70Hz로 변환하는 어댑터가 들어갑니다.

// Wolf4SDL의 시간 어댑터(개념)
uint32_t now = SDL_GetTicks();
TimeCount = (now * 70) / 1000;

8.3 PlayLoop의 단계별 분해

PlayLoop()가 한 번 도는 동안 어떤 일이 일어나는지, 순서대로 봅시다.

  1. tics 계산 — 위에서 본 그대로. 지난 프레임 이후 흐른 시간.
  2. 입력 폴링 — PollControls() 또는 ControlMovement(). 키보드/마우스/조이스틱을 읽어 player_t 구조체에 의도(이동 벡터, 회전, 발사)를 기록.
  3. 플레이어 이동/회전 — Thrust(angle, speed)로 충돌 처리하며 이동. 벽을 통과하지 않도록 격자 검사.
  4. 적·문·푸시월 이동 — DoActor()가 모든 액터(적·도어·푸시월) 리스트를 돌며 각자의 상태 함수를 호출.
  5. 3D 화면 갱신 — ThreeDRefresh(). 레이캐스팅(WallRefresh) → 스프라이트(DrawScaleds) → 무기(DrawPlayerWeapon).
  6. HUD 그리기 — 체력·탄약·점수.
  7. 사운드 위치 업데이트 — 적의 발자국 소리 등 거리 기반 볼륨 조정.
  8. 화면 플립 — 백 버퍼를 프런트로. SDL 포팅판에서는 SDL_RenderPresent().

8.4 게임 상태(playstate) — 무엇이 루프를 깨뜨리나

위 4번 단계에서 어떤 일(플레이어 사망, 출구 도달, 워프 치트, 승리)이 일어나면 playstate가 바뀝니다. PlayLoop()는 그 값을 보고 자기 자신을 빠져나갑니다.

값의미

ex_completed레벨 클리어 → 점수 화면
ex_died플레이어 사망 → 사망 처리

8.5 가변 프레임률의 함정

원본 Wolf3D는 386에서 60~70fps가 거의 한계였고, 모든 이동 속도가 "1틱당 얼마"로 정의되었습니다. 그런데 현대 컴퓨터에서는 같은 코드가 수천 fps로 돌아갑니다. 그러면 어떻게 되죠?

다행히도 Wolf3D는 tics를 곱해서 이동량을 계산하므로, "1틱당 거리 × 흐른 틱 수"가 됩니다. 따라서 빠른 컴퓨터에서도 같은 속도로 움직입니다. 다만 tics가 0이 되지 않도록 SDL 포팅판은 SDL_Delay()로 프레임을 70Hz로 고정합니다.

// Wolf4SDL의 프레임 캡
while ((now = SDL_GetTicks()) - lasttime < 1000/70) {
    SDL_Delay(1);
}
왜 70Hz? · 70Hz는 원래 VGA 텍스트 모드의 수직 동기 주파수입니다. id Software는 그 주파수에 맞춰 부드러운 vsync 느낌을 내려고 했습니다.

  • playstate가 바뀌어야 PlayLoop가 끝남을 이해

9.1 좌표 단위 — 1 타일 = 65536

맵은 64×64의 격자(타일)로 이루어집니다. 각 타일의 한 변 길이를 65536(2^16)으로 잡습니다. 왜? 고정소수점이기 때문입니다. 정수 65536은 "1.0"을 의미하고, 32768은 "0.5"를 의미합니다.

#define TILESHIFT  16
#define TILEGLOBAL (1L << TILESHIFT)   // 65536, 한 타일의 한 변
#define MAPSIZE    64                  // 64x64 격자
#define MAXTICS    10                  // 한 프레임 최대 틱

그래서 플레이어 좌표 player->x = 2 * TILEGLOBAL + TILEGLOBAL/2 라면 "타일 (2,?)의 중앙"이라는 의미입니다.

9.3 액터 구조체 ─ objtype

적, 플레이어, 아이템, 문은 모두 objtype이라는 한 구조체로 표현됩니다.

typedef struct objstruct {
    activetype  active;     // 활성 상태(0/1, 또는 always)
    short       ticcount;   // 상태 잔여 틱
    classtype   obclass;    // 종류 (guardobj, ssobj, dogobj ...)
    statetype  *state;      // 현재 상태(애니메이션 프레임 + 행동)
    byte        flags;      // 비트 플래그 (shootable, bonus, ...)
    int32_t     distance;   // 다음 타일까지 남은 거리
    dirtype     dir;        // 이동 방향
    fixed       x, y;       // 월드 좌표 (Q16.16)
    word        tilex, tiley;  // 격자 좌표
    short       angle;      // 바라보는 각도 (0~359)
    int         hitpoints;  // 체력
    int32_t     speed;      // 이동 속도
    short       temp1, temp2, hidden;
    struct objstruct *next, *prev;
} objtype;

모든 적이 같은 구조체라는 점이 매우 중요합니다. "친위대 병사"와 "셰퍼드 개"의 차이는 obclass와 state에 들어 있고, 행동은 결국 state->think가 가리키는 함수가 결정합니다. 이것이 곧 상태 머신 패턴입니다.

9.4 statetype — 작은 천재 발명

typedef struct statestruct {
    boolean  rotate;          // 방향에 따라 스프라이트가 바뀌는가
    short    shapenum;        // 어떤 그림을 그릴까
    short    tictime;         // 이 상태에서 머무는 틱 수
    void   (*think)(objstruct *);  // 매 틱 호출되는 함수
    void   (*action)(objstruct *); // 상태 진입 시 한 번 호출
    struct statestruct *next; // 다음 상태
} statetype;

이 한 구조체로 "친위대 병사가 걷고 → 보고 → 쏘고 → 죽고 → 사라진다"의 전체 시퀀스가 표현됩니다. tictime이 0이 되면 자동으로 next로 넘어갑니다.

예: s_grdshoot1 → s_grdshoot2 → s_grdshoot3 → s_grdchase1 처럼 next 포인터로 사슬을 만듭니다.

9.5 맵 데이터 — 두 평면

맵 파일(GAMEMAPS)에는 한 레벨당 두 개의 64×64 평면이 들어 있습니다.

  • 평면 0: 벽/문/바닥 타일. 코드의 tilemap[][]로 들어옴.
  • 평면 1: 액터·아이템·플레이어 시작점. SpawnNewObj() 등으로 변환.

두 평면이 모두 RLEW(Run-Length-Encoded Word) 압축되어 있어, CA_RLEWexpand()로 풀어 씁니다.

  • objtype이 적·아이템·문 공통 구조체임을 이해
  • statetype이 상태 머신을 표현하는 노드임을 이해
  • 맵이 두 평면(타일·액터)으로 구성됨을 이해

VGA, 픽셀, 그리고 화면 출력의 원리

3D 게임의 본질은 결국 "어떤 픽셀을 어떤 색으로 칠할까?"의 결정입니다. 이 결정을 가장 빠르고 영리하게 내리는 방법이 곧 게임 엔진입니다. 그래서 픽셀 출력의 밑바닥을 이해해야 합니다.

10.1 VGA의 320×200 256색 모드 — Mode 13h

1992년 PC 게임의 사실상 표준은 Mode 13h였습니다. 320×200 해상도에 256색 팔레트. 한 픽셀 = 1바이트 = 0~255 중 하나의 팔레트 인덱스.

// 옛날 Wolf3D의 픽셀 쓰기 (개념)
char far *vga = (char far *)0xA0000000L;
vga[y * 320 + x] = color_index;

이 한 줄이 곧 화면 출력의 전부였습니다. 0xA0000은 비디오 메모리의 시작 주소. 거기에 쓰면 즉시 화면에 보입니다. 라이브러리도, 윈도우 시스템도, 합성기(compositor)도 없습니다.

10.2 팔레트(Palette)란 무엇인가

256색 모드에서는 "색"이 직접 비트맵에 들어가지 않습니다. 대신 0~255 중 한 인덱스가 들어가고, VGA 카드 안에 있는 256개짜리 RGB 표(팔레트)에서 진짜 색을 찾아옵니다.

픽셀 데이터: [42] [17] [42] [99] ... ↓ ↓ ↓ ↓ 팔레트 RAM: [0]=(0,0,0) [1]=(0,0,170) ... [17]=(170,85,0) [42]=(255,255,170) ← 보이는 색 [99]=(85,0,170)

이렇게 하면 픽셀 데이터 크기가 1/3(24비트 RGB 대비)이 됩니다. 1992년의 VGA 메모리가 64KB뿐이었기 때문에 절약이 필수였죠.

10.3 더블 버퍼링 — "그리는 동안 보여 주지 않기"

화면에 직접 그리면, 그리는 중간 단계가 사용자 눈에 보입니다. 그러면 깜빡임(flicker)이 생기죠. 해결책: 메모리에 "보이지 않는 버퍼"를 두고 거기에 다 그린 다음, 한 번에 화면에 복사합니다.

앞 버퍼(보이는) 뒷 버퍼(작업 중) ┌──────────┐ ┌──────────┐ │ 보여 줌 │ ←── │ 그리는중 │ └──────────┘ 복사 └──────────┘

SDL 포팅판에서는 SDL_Surface *screenBuffer가 뒷 버퍼 역할을 하고, 매 프레임 끝에 SDL_BlitSurface → SDL_UpdateTexture → SDL_RenderCopy → SDL_RenderPresent 의 사슬로 화면에 올립니다.

10.4 어떻게 원본 코드를 SDL로 옮겼는가

핵심 아이디어: "가짜 VGA 메모리"를 만든다. 코드가 여전히 vga[y*320+x] = c처럼 동작하지만, 그 vga는 SDL_Surface의 픽셀 버퍼를 가리킨다.

// Wolf4SDL의 추상화
SDL_Surface *screenBuffer; // 8-bit 320x200 (or scaled)
byte *gfxbuf = (byte *)screenBuffer->pixels;

// 픽셀 쓰기는 원본과 똑같이
gfxbuf[y * screenBuffer->pitch + x] = color;

// 프레임 끝
SDL_LockSurface(screenBuffer);
// ... 그리기 ...
SDL_UnlockSurface(screenBuffer);
SDL_BlitScaled(screenBuffer, NULL, screen, NULL);
SDL_UpdateWindowSurface(window);

이 트릭 덕분에 1992년에 쓰인 그리기 코드 대부분이 거의 그대로 살아남았습니다. VL_Plot(), VL_Hlin(), VL_Bar() 같은 함수의 본체만 SDL surface에 쓰도록 바꾸면 끝입니다.

10.5 색상 확장 — 256색 팔레트에서 32비트로

현대 모니터는 24/32비트 컬러를 씁니다. 그러면 256색 팔레트는 어떻게 살리나요? SDL이 도와줍니다.

// 팔레트 등록
SDL_Color palette[256];
for (i = 0; i < 256; i++) {
    palette[i].r = gamepal[i*3+0] * 4;  // 원본은 0~63
    palette[i].g = gamepal[i*3+1] * 4;
    palette[i].b = gamepal[i*3+2] * 4;
    palette[i].a = 255;
}
SDL_SetPaletteColors(screenBuffer->format->palette, palette, 0, 256);

이제 8비트 surface(screenBuffer)에 인덱스로 그리면, SDL이 알아서 24/32비트로 변환해 줍니다.

왜 ×4? · 원본 VGA 팔레트는 채널당 6비트(0~63). 8비트(0~255)로 늘리려면 4를 곱하면 거의 같은 비율이 됩니다. 정확하게는 (v << 2) | (v >> 4)가 이상적이지만, 게임 외관상 차이는 거의 없습니다.

10.6 원본의 평면(planar) 모드 ─ ModeY의 함정

Wolf3D 원본은 사실 순수 Mode 13h가 아니라 ModeY(또는 ModeX의 변형)라는 비표준 모드를 씁니다. 같은 320×200×256색이지만, 4개의 평면(plane)에 픽셀이 인터리브로 저장됩니다.

화면 좌표 x: 0 1 2 3 4 5 6 7 평면(plane): 0 1 2 3 0 1 2 3 ← x % 4 오프셋: 0 0 0 0 1 1 1 1 ← x / 4

왜 이렇게 복잡하게? VGA 카드의 4개 평면을 동시에 쓰면 4픽셀을 한 번에 쓸 수 있어서입니다. 1992년 386에서 이 트릭이 없으면 60fps가 나오지 않았습니다.

SDL 포팅 시에는 ModeY를 흉내 낼 필요가 없습니다. 그냥 선형 320×200 버퍼를 쓰고, ModeY 가정으로 짠 코드(id_vl.c 일부)는 평면 인터리브 해제 코드를 한 번 거쳐 선형 버퍼로 복사합니다. 이 변환 코드를 보고 싶다면 Wolf4SDL의 VH_UpdateScreen()을 확인하세요.

10.7 진행 체크

  • Mode 13h가 320×200×256색임을 외움
  • 팔레트 인덱스와 실제 RGB의 관계를 그릴 수 있음
  • 더블 버퍼링의 의미를 자기 말로 설명할 수 있음
  • SDL_Surface가 "가짜 VGA 메모리" 역할을 함을 이해

레이캐스팅 ─ Wolfenstein 3D의 심장

이제 이 책의 절정에 다다랐습니다. 30년 전에 처음으로 PC에서 부드러운 1인칭 3D를 만들어낸 마법, 레이캐스팅의 원리를 설명합니다.

11.1 진짜 3D가 아니다 ─ "유사 3D"

Wolfenstein 3D는 사실 3D가 아닙니다. 정확히는 "2D 맵에서 광선을 쏴서 본 듯한 그림을 그리는 기법"입니다. 이걸 알면 갑자기 모든 게 단순해집니다.

  • 맵은 평면. 모든 벽이 같은 높이, 90° 수직.
  • 플레이어는 위·아래를 볼 수 없음(고개 끄덕 모션이 없음).
  • 층 개념 없음(2층 건물 표현 불가).

이 제약 덕분에 모든 광선이 "수평면 위의 광선"이 됩니다. 즉, 한 픽셀 수직 열을 그리는 데 광선 하나만 있으면 충분합니다. 화면이 320 픽셀 가로면 광선이 320개. 1프레임에 광선 320개로 끝나는 단순함.

11.2 한 광선의 여정 ─ DDA로 격자 따라가기

플레이어가 (5.5, 7.2)에 있고 어떤 각도로 광선을 발사한다고 합시다. 광선이 어떤 격자 칸을 지나는지 어떻게 효율적으로 찾을까요?

핵심 아이디어: 한 번에 격자 한 칸씩 건너뛰기. 광선이 X 격자선과 만나는 지점, Y 격자선과 만나는 지점을 번갈아 보면서, 더 가까운 쪽으로 이동.

│ │ │ │ ────┼───┼───┼───┼──── │ │ • │ │ ← 광선이 다음에 만날 격자선 │ ↗│ │ │ ────┼───┼───┼───┼──── │ ↗ │ │ │ │↗ │ │ │ ← 플레이어 ────┼───┼───┼───┼────

이 알고리즘이 DDA(Digital Differential Analyzer)입니다. 한 칸 이동에 곱셈·나눗셈이 거의 없고, 누적 덧셈만으로 풀립니다.

// 의사 코드 (수평 격자선 검사)
xstep, ystep = sin(angle), cos(angle)  // 단위 벡터
xinter = 다음 X 격자선의 좌표
yinter = 다음 Y 격자선의 좌표
while (true) {
    if (xinter <= yinter) {
        // X 격자선 먼저 도달
        if (tilemap[tilex][tiley] != 0) {  // 벽?
            return 거리 = xinter
        }
        xinter += xstep
        tilex  += dx
    } else {
        if (tilemap[tilex][tiley] != 0) {
            return 거리 = yinter
        }
        yinter += ystep
        tiley  += dy
    }
}

이게 wl_draw.c의 AsmRefresh()(원본은 어셈블리)의 본질입니다.

11.3 거리에서 벽 높이로

광선이 벽에 닿은 거리를 알면, 벽이 화면에 얼마나 높게 보일지를 계산할 수 있습니다.

벽 높이(픽셀) = 화면 높이 × (실제 벽 높이 / 거리)
            ≈ heightnumerator / distance

여기서 heightnumerator는 scale × TILEGLOBAL / 2 같은 고정 상수입니다. 거리가 두 배가 되면 벽 높이는 절반이 됩니다. 이것이 원근감의 핵심 공식입니다.

11.4 어안 왜곡 보정

단순히 광선 길이를 그대로 쓰면 "어안 렌즈" 효과가 생깁니다 — 정면 벽이 가운데가 부풀어 보이는 효과. 왜냐하면 화면 가장자리로 갈수록 광선 자체가 길어지기 때문입니다.

해결책: 광선 거리를 플레이어 정면 방향으로 투영합니다.

// 보정 전(잘못)
height = HEIGHT_NUM / raylen

// 보정 후(올바름)
double project = raylen * cos(angle_from_center)
height = HEIGHT_NUM / project

Wolf3D는 이걸 미리 계산한 테이블 fineviewangle[](또는 pixelangle[])로 처리합니다. 광선마다 자신의 화면 열에 해당하는 사전 보정값을 적용하는 식이죠.

11.5 텍스처 좌표 계산

벽에 닿은 지점이 X 격자선이라면 광선이 Y 좌표로 그 위치를 "긁고" 들어왔습니다. 그 Y 좌표의 분수부(yinter % TILEGLOBAL)가 곧 텍스처의 가로 좌표가 됩니다.

// 벽이 X-격자선이면 (수직 벽)
texX = (yinter & (TILEGLOBAL - 1)) >> (TILESHIFT - 6)  // 0~63
// 벽이 Y-격자선이면 (수평 벽)
texX = (xinter & (TILEGLOBAL - 1)) >> (TILESHIFT - 6)

64는 텍스처 한 변의 픽셀 수입니다. 이렇게 구한 texX는 "텍스처의 어느 세로줄을 가져올 것인가"를 가리킵니다.

11.6 한 세로줄을 그리는 ScaleLine

이제 한 광선이 끝나면 "텍스처의 64픽셀짜리 세로줄을, 화면의 N픽셀짜리 세로줄로 늘려서/줄여서 그리기"만 하면 됩니다. 이 작업이 ScaleLine() 또는 ScalePost()입니다.

// 의사 코드: 64픽셀을 화면 height픽셀로 스케일링
fixed dy = (64 << 16) / height  // 한 화면 픽셀마다 텍스처가 얼마나 진행
fixed ty = 0
for (sy = top; sy < bottom; sy++) {
    color = texture[texX * 64 + (ty >> 16)]
    screen[sy * 320 + x] = color
    ty += dy
}

원본은 이 루프가 너무 자주 호출되어, 매번 인터프리트하면 느렸습니다. 그래서 자가 수정 코드(self-modifying code)로 매 프레임 직접 어셈블리를 생성해서 실행했습니다. 무서운 트릭이죠.

SDL 포팅판은 단순화 · 현대 CPU는 캐시 라인을 일관성 유지해야 해서 자가 수정 코드가 오히려 느립니다. Wolf4SDL은 단순 C 루프로 다시 썼습니다 — 어차피 빠르니까요.

11.7 핵심 함수의 호출 흐름

  • DDA의 직관 (격자선 따라 한 칸씩 점프)

12장

스프라이트와 텍스처 매핑

벽은 끝났습니다. 이제 적 병사와 보스, 그리고 보너스 아이템을 그릴 차례입니다. 이들은 스프라이트 — 2D 비트맵 — 로 표현됩니다. 1992년 PC에서 진짜 3D 모델은 불가능했고, 사실 필요도 없었습니다.

12.1 스프라이트의 데이터 구조

Wolf3D의 스프라이트는 모두 64×64 픽셀. VSWAP 파일 안에 압축되어 들어 있습니다. 압축 방식은 "투명 픽셀을 건너뛰는 RLE"의 변형으로, 정확한 이름은 없지만 흔히 "id sprite format"으로 부릅니다.

// 스프라이트 헤더 (개념)
struct sprite_t {
    word leftpix;       // 가장 왼쪽 비투명 열
    word rightpix;      // 가장 오른쪽 비투명 열
    word dataofs[];     // 각 열의 데이터 시작 위치
    // ... 그 뒤에 열별 픽셀 데이터
};

이 구조는 "투명한 영역을 건너뛰면서 비투명 열만 빠르게 접근"하기 위함입니다. 왜냐하면 스프라이트도 결국 화면 한 세로열씩 그리는 방식으로 처리되기 때문입니다 — 벽과 똑같이.

12.2 스프라이트의 거리·각도 계산

이번 프레임에 보이는 모든 액터 중에서, 스프라이트로 그릴 후보를 모읍니다.

// 의사 코드
visspr_count = 0
for each obj in objlist:
    if (obj->flags & FL_VISIBLE):
        // 카메라 좌표계로 변환
        gx = obj->x - player->x
        gy = obj->y - player->y
        rotate by (-player->angle)
        if (gz_rotated > near && in view cone):
            visspr[visspr_count++] = { obj, transx, transy }
// 멀리 있는 것부터 그리기 위해 거리순 정렬
sort visspr by transz desc

왜 정렬? 먼 것을 먼저 그려야 가까운 것이 위에 덮어 그려져 올바른 가림(occlusion) 효과가 나옵니다. 이를 "화가의 알고리즘(painter's algorithm)"이라고 부릅니다.

12.3 한 스프라이트를 화면에 박기

// 한 스프라이트의 화면 위치/크기
height = HEIGHT_NUM / transz
screenX = halfview + (transy / transz) * scale
// 그릴 열 범위
startX = screenX - height/2
endX   = screenX + height/2

그런 다음 벽 깊이 버퍼(wallheight[])와 비교해서, 그 열이 벽보다 앞이면 그리고, 벽보다 뒤면 건너뜁니다.

for (col = startX; col < endX; col++) {
    if (wallheight[col] >= sprite_z) continue;  // 벽이 앞이면 가려짐
    DrawSpriteColumn(...)
}

12.4 무기 그리기 — 가장 단순한 스프라이트

플레이어가 든 무기는 항상 화면 정해진 위치에 같은 크기로 그려집니다. 거리·각도 계산도 필요 없습니다.

void DrawPlayerWeapon(void) {
    int shape = weaponstate < gd_shootingframe
                ? gamestate.weapon  // 평소
                : weaponstate;       // 발사 애니메이션
    SimpleScaleShape(viewwidth/2, weapon_shape[shape], viewheight);
}

12.5 바닥·천장 텍스처? — 원본은 없다

Wolf3D 원본은 바닥과 천장이 단색입니다. 텍스처가 없습니다. 회색 천장, 갈색 바닥. 끝.

왜? 바닥/천장 텍스처를 그리려면 광선마다가 아니라 픽셀마다 텍스처 좌표를 새로 계산해야 합니다. 1992년 CPU로는 그게 너무 느렸습니다. Doom(1993)에서야 가능해졌죠.

현대 포팅판에는 옵션으로 바닥/천장 텍스처가 있는 것도 있습니다(Wolf3D Redux 등). 그러나 학습용으로는 단색이 코드가 훨씬 단순합니다.

12.6 광원 효과 ─ "거리에 따른 어둠"

원본 Wolf3D는 광원이 없습니다(모든 벽이 같은 밝기). 그러나 일부 포팅판은 거리에 따라 어두워지는 효과를 추가했습니다.

// 라이트 테이블 (LIGHT[64][256])
shaded_color = LIGHT[distance_idx][original_color]

이 테이블은 미리 계산해 두고, 그리기 루프에서 한 번의 배열 조회로 끝냅니다. Doom의 트레이드마크 기법이고, Wolf3D에서는 보너스로 종종 채용됩니다.

12.7 진행 체크

  • 스프라이트가 64×64 비트맵임을 외움
  • 멀리 있는 것부터 그리는 이유(가림 처리)를 이해
  • 벽 깊이 버퍼와 스프라이트의 비교를 이해
  • 바닥/천장이 단색인 이유(성능)를 이해
13장

사운드 시스템 ─ Adlib과 디지털, 그리고 SDL_mixer

Wolf3D의 사운드는 세 갈래입니다: PC 스피커, Adlib(FM 합성), 디지털 효과음(Sound Blaster). 각각이 별개의 코드 경로로 처리되었고, 오늘날의 포팅판은 이 모두를 SDL_mixer 한 곳으로 흘려보냅니다.

13.1 PC 스피커 ─ 가장 원시적인 출력

PC 스피커는 0/1 두 상태밖에 없는 비프 출력기입니다. 음악도, 효과음도 모두 "특정 주파수의 방형파"로 만들어졌습니다. 코드에서는 단순한 음정 시퀀스로 표현됩니다.

// 의사 표현
PCSound = { freq=440, dur=10 }, { freq=880, dur=5 }, ...

이 데이터를 PIT(프로그래머블 인터벌 타이머)에 직접 써서 스피커를 진동시키는 방식이었습니다.

13.2 Adlib ─ OPL2 FM 합성

Adlib 카드는 Yamaha의 YM3812(OPL2) 칩을 씁니다. 이 칩은 9개의 채널을 가지고, 각 채널이 두 개의 사인파 오실레이터(operator)를 FM(주파수 변조)으로 결합해 음색을 만듭니다.

┌── Operator 1 (modulator) ──┐ │ │ ──→ Channel 출력 └── Operator 2 (carrier) ────┘ (FM 변조 결과) 각 operator는 ADSR, 주파수, 감쇠 등 ~10개 파라미터

음악(IMF 포맷)은 "이 시간에 이 레지스터에 이 값을 써라"의 시퀀스로 저장됩니다. 매우 작고(곡 1개가 2~5KB), 표현력은 풍부합니다.

13.3 OPL을 어떻게 재현하나 ─ 두 가지 길

현대 시스템에는 OPL 칩이 없으니, 다음 둘 중 하나를 합니다.

A. OPL 에뮬레이션

소프트웨어로 OPL2의 동작을 재현. 한 샘플마다 9채널×2 operator의 사인파를 계산해 합성. 음질이 원본과 거의 같음.

대표 구현: DOSBox OPL emulator(MIT), fmopl(MAME 유래), YMF262/Nuked OPL3.

B. MIDI 변환

IMF 시퀀스를 MIDI로 일괄 변환. 시스템 MIDI 출력으로 재생. 음색이 완전히 달라짐.

음악적 정확성이 떨어져 잘 쓰이지 않음. Wolf4SDL은 A를 택함.

13.4 SDL_mixer와의 결합

Wolf4SDL은 다음 흐름으로 OPL 에뮬레이션을 SDL에 붙입니다.

  1. SDL_mixer를 초기화: Mix_OpenAudio(44100, AUDIO_S16, 2, 1024).
  2. 음악 시작 시 Mix_HookMusic(MusicCallback, NULL)로 콜백 등록.
  3. SDL이 일정 간격으로 콜백을 호출 → 그 안에서 OPL 에뮬레이터에게 "N 샘플 합성해" 라고 요청 → 결과를 SDL이 준 버퍼에 채움.
  4. SDL이 그 버퍼를 OS 오디오 드라이버로 흘려보냄.
// 콜백 (개념)
void MusicCallback(void *unused, Uint8 *stream, int len) {
    int samples = len / 4;  // 스테레오 16비트
    YM3812UpdateOne(opl, (int16_t *)stream, samples);
    // 동시에 IMF 시퀀스의 다음 명령을 처리해서 OPL 레지스터에 쓰기
    PlayIMF(samples);
}

13.5 디지털 사운드 효과 ─ "어흑!"

친위대가 죽을 때 "Mein Leben!"이라고 외치는 그 디지털 보이스. 이건 PCM 샘플(8비트, 7000Hz쯤)로 저장돼 있습니다.

SDL_mixer에서는 단순히 Mix_Chunk *를 만들어 Mix_PlayChannel()로 재생합니다.

// 단순화
Mix_Chunk *snd = Mix_LoadWAV("snd_die.wav");
Mix_PlayChannel(-1, snd, 0);  // -1 = 빈 채널 선택, 0 = 한 번만

원본 데이터는 WAV가 아니라 raw PCM이므로, 로딩 시 SDL Mixer 포맷에 맞는 RIFF 헤더를 붙이거나 Mix_QuickLoad_RAW를 씁니다.

13.6 3D 사운드 ─ 거리·각도 기반 볼륨

적이 멀리 있으면 발자국 소리가 작게, 등 뒤에 있으면 한쪽 채널로 더 크게. 이런 효과는 SDL_mixer의 Mix_SetPanning()과 Mix_Volume()로 처리합니다.

// 적 obj의 발소리 갱신
distance = hypot(player->x - obj->x, player->y - obj->y)
volume   = 255 * MAX(0, 1 - distance/MAXAUDIOLEN)
angle    = atan2(...)  // 플레이어 시선 기준 좌우 각도
left = volume * (1 - sin(angle))/2
right= volume * (1 + sin(angle))/2
Mix_SetPanning(channel, left, right)

  • PC speaker / Adlib / 디지털, 세 가지 사운드 경로의 차이를 이해
  • OPL2 에뮬레이션이 콜백 안에서 실시간으로 동작함을 이해
  • Mix_PlayChannel, Mix_SetPanning의 역할을 외움
14장

입력 시스템 ─ 키보드, 마우스, 조이스틱

입력은 가장 단순해 보이지만, 게임의 "느낌"을 좌우하는 가장 민감한 부분입니다. 1992년의 DOS 입력 코드와 SDL 입력 코드는 모양이 매우 다릅니다.

14.1 원본의 키보드 ─ 인터럽트 후킹

DOS Wolf3D는 BIOS의 int 16h를 쓰지 않고, 키보드 인터럽트(int 9h)를 직접 가로챕니다. 이유는 두 가지.

  • BIOS 키보드 버퍼는 키 누름만 알려 주고, "지금 누른 상태인가?"는 모른다 → 부드러운 이동 불가.
  • 여러 키를 동시에 처리할 수 없다(예: 앞으로+왼쪽+발사).

그래서 인터럽트 핸들러가 스캔코드를 직접 받아 Keyboard[128] 배열에 1/0으로 기록합니다.

// 원본 (개념)
void interrupt KbdISR(void) {
    byte scan = inportb(0x60);
    if (scan & 0x80) Keyboard[scan & 0x7F] = 0;  // 떼기
    else             Keyboard[scan] = 1;          // 누르기
    outportb(0x20, 0x20);                          // 인터럽트 종료
}

14.2 SDL로의 번역

SDL은 같은 동작을 다음과 같이 제공합니다.

SDL_Event ev;
while (SDL_PollEvent(&ev)) {
    if (ev.type == SDL_KEYDOWN) Keyboard[scancode_of(ev)] = 1;
    if (ev.type == SDL_KEYUP)   Keyboard[scancode_of(ev)] = 0;
    if (ev.type == SDL_QUIT)    Quit(NULL);
}

또는 더 간단하게:

const Uint8 *kbd = SDL_GetKeyboardState(NULL);
if (kbd[SDL_SCANCODE_W]) move_forward();

14.3 스캔코드 매핑 ─ 가장 흔한 버그

원본은 DOS 스캔코드(0x11=W, 0x1F=S, ...)를 가정합니다. SDL은 SDL_SCANCODE_W처럼 별도의 enum을 씁니다. 이 둘을 잇는 매핑 테이블이 필요합니다.

// Wolf4SDL의 매핑 (발췌)
static int scanmap[SDL_NUM_SCANCODES];
scanmap[SDL_SCANCODE_W] = sc_W;
scanmap[SDL_SCANCODE_A] = sc_A;
scanmap[SDL_SCANCODE_UP] = sc_UpArrow;
// ... 80여 키

이 테이블이 잘못되면, 키를 눌러도 게임이 반응 안 하거나 엉뚱한 동작을 합니다. "포팅했는데 안 움직여요" 문제의 70%가 여기서 옵니다.

14.4 마우스 ─ 상대 좌표 모드

1인칭 게임의 마우스는 상대 모드여야 합니다(화면 가장자리에서 멈추면 안 됨). SDL2는 다음 한 줄로 처리.

SDL_SetRelativeMouseMode(SDL_TRUE);
// 그 뒤로 SDL_MouseMotion 이벤트의 xrel/yrel이 누적 델타가 됨

마우스 감도는 mouseturn = xrel * mouseadjustment로 회전에 더해집니다.

14.5 조이스틱·게임패드 ─ 선택 사항

Wolf4SDL은 SDL2 게임패드 API를 지원합니다.

SDL_Joystick *joy = SDL_JoystickOpen(0);
int xaxis = SDL_JoystickGetAxis(joy, 0);  // -32768~32767
int btn0  = SDL_JoystickGetButton(joy, 0);

14.6 입력 시스템 통합 ─ ControlInfo

원본의 깔끔한 추상화: ControlInfo 구조체. 어떤 입력 장치에서 왔든 동일한 형태.

typedef struct {
    short button0, button1, button2, button3;
    int xaxis, yaxis;  // -1, 0, 1
    Direction dir;
} ControlInfo;
void ReadAnyControl(ControlInfo *info);  // 키/마우스/조이스틱 통합

이 추상화 덕분에 게임 로직(wl_play.c, wl_agent.c)은 입력 장치의 종류를 신경 쓰지 않습니다.

14.7 진행 체크

  • SDL은 폴링 또는 키 상태 배열 두 방식이 있음을 외움
  • 스캔코드 매핑이 흔한 버그 원인임을 기억
  • 마우스는 상대 모드로 두어야 함을 외움

Windows 11에서 빌드하기 Win

이제 이론은 충분합니다. 실제로 컴파일해서 게임을 띄워 봅시다. Windows 11 환경, MSYS2 MINGW64 셸 기준입니다.

15.1 준비 사항 점검

  • MSYS2가 설치되어 MINGW64 셸이 열린다
  • gcc --version이 동작
  • pkg-config --modversion sdl2가 2.x를 출력
  • ~/wolf3d-port/src/에 소스 코드, ~/wolf3d-port/data/에 데이터 파일 준비됨

모두 체크되었다면 다음 단계로.

15.2 빌드 방법 ① ─ Makefile 사용

Wolf4SDL은 보통 Makefile을 함께 제공합니다. 가장 간단한 빌드 방법.

Step 1. 소스 폴더로 이동

cd ~/wolf3d-port/src

Step 2. Makefile 확인

ls Makefile
cat Makefile | head -40   # 빌드 설정 확인

Makefile 상단에 다음과 비슷한 변수가 보일 겁니다.

CC      = gcc
CFLAGS  = -Wall -O2 `pkg-config --cflags sdl2 SDL2_mixer`
LDFLAGS = `pkg-config --libs sdl2 SDL2_mixer`
TARGET  = wolf3d
SRCS    = $(wildcard *.c)
OBJS    = $(SRCS:.c=.o)

Step 3. 컴파일 실행

make

처음에는 50~100개의 컴파일 명령이 흘러갑니다. 1~3분 정도. 끝나면 wolf3d.exe가 생깁니다.

에러가 나면 · 첫 에러 메시지의 처음 부분을 읽으세요. 보통 헤더를 못 찾는 경우 — pacman -S mingw-w64-x86_64-SDL2가 빠진 것입니다. fatal error: ... .h: No such file이 대표적 단서.

15.3 빌드 방법 ② ─ CMake 사용

Chocolate-Wolfenstein-3D처럼 CMakeLists.txt를 제공하는 분기는 CMake 방식이 더 깔끔합니다.

cd ~/wolf3d-port/src
mkdir -p build && cd build
cmake -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release ..
mingw32-make -j4

-j4는 동시에 4개 컴파일러 인스턴스를 실행해 빠르게 빌드합니다. CPU 코어 수에 맞춰 조정하세요.

15.4 빌드 방법 ③ ─ 수동 한 줄

Makefile이 없거나 부서졌다면, 모든 .c를 한 줄로 컴파일할 수도 있습니다.

gcc -O2 -Wall *.c \
    `pkg-config --cflags --libs sdl2 SDL2_mixer` \
    -o wolf3d.exe

15.5 데이터 파일 위치 설정

빌드된 wolf3d.exe를 실행하면, 게임은 현재 디렉터리에서 데이터 파일(vswap.wl1 등)을 찾습니다. 두 가지 방법.

A. EXE를 data 폴더로 옮긴다

cp wolf3d.exe ../data/
cd ../data
./wolf3d.exe

B. 데이터 파일을 src로 가져온다

cp ../data/*.wl1 .
./wolf3d.exe

15.6 첫 실행 ─ 무엇이 나와야 정상인가

  1. SDL 창이 열린다(보통 640×400 또는 그 배수).
  2. "PG-13" 경고 화면 → "PROFOUND CARNAGE" 등의 메시지.
  3. id Software 로고 → Apogee 로고.
  4. 타이틀 화면(BJ Blazkowicz 그림).
  5. 몇 초 후 데모(자동 플레이) 시작.
  6. 아무 키나 누르면 메인 메뉴.

여기까지 보이면 포팅 성공입니다. 축하합니다!

Linux에서 빌드하기 Linux

리눅스는 사실 Wolf4SDL의 "고향"입니다. 가장 매끄럽게 빌드됩니다. 우분투/데비안 기준으로 설명하지만, 다른 배포판도 패키지 이름만 다를 뿐 흐름은 동일합니다.

16.1 준비 확인

gcc --version          # 11.0 이상이면 좋음
pkg-config --modversion sdl2     # 2.0 이상
pkg-config --modversion SDL2_mixer
ls ~/wolf3d-port/data/*.wl1      # 데이터 파일 확인

16.2 빌드 진행

Step 1. 소스 폴더로

cd ~/wolf3d-port/src

Step 2. (필요 시) Makefile 수정

일부 오래된 Makefile은 SDL1.2를 가정합니다. 다음으로 바꿉니다.

# 변경 전
SDLCFLAGS = `sdl-config --cflags`
SDLLIBS   = `sdl-config --libs` -lSDL_mixer

# 변경 후
SDLCFLAGS = `pkg-config --cflags sdl2 SDL2_mixer`
SDLLIBS   = `pkg-config --libs sdl2 SDL2_mixer`

Step 3. 빌드

make -j$(nproc)

$(nproc)는 CPU 코어 수입니다. 4코어면 4배, 8코어면 8배 빠르게 빌드.

Step 4. 데이터 파일과 함께 실행

cp wolf3d ../data/
cd ../data
./wolf3d

16.3 CMake로 빌드

cd ~/wolf3d-port/src
mkdir -p build && cd build
cmake -DCMAKE_BUILD_TYPE=Release ..
make -j$(nproc)
./wolf3d

16.4 데스크톱 환경별 작은 차이

환경참고
X11 (Xorg)기본 동작. 문제 없음.
WaylandSDL2 2.0.20+ 권장. SDL_VIDEODRIVER=wayland ./wolf3d로 강제 지정 가능.
WSL2WSLg 활성화 필요(Windows 11은 기본). $DISPLAY 변수 자동 설정.
Headless 서버SDL_VIDEODRIVER=dummy로 사운드/입력만 가능 — 시각 출력 불가.

16.5 .desktop 항목 만들기 (선택)

GUI 메뉴에 등록하고 싶다면:

cat > ~/.local/share/applications/wolf3d.desktop <<'EOF'

16.7 32비트 정수 가정 코드와의 충돌 (64비트 OS)

원본 코드 일부는 long이 32비트라고 가정합니다. 64비트 리눅스에서는 long이 64비트(LP64)라서 충돌 가능. Wolf4SDL은 거의 다 정리되었지만, 자기 포크가 옛 코드라면 int32_t로 명시적 캐스팅이 필요할 수 있습니다.

// 원본 (32비트 가정)
long heightnumerator;

// 수정 (모든 OS에서 32비트)
int32_t heightnumerator;

Termux(안드로이드)에서 빌드하기 Termux

안드로이드 폰만으로 Wolf3D를 빌드해 돌리는 경험은, 1992년의 데스크톱 게임이 어느새 30년 후 주머니 컴퓨터에서 돌아간다는 묘한 감동을 줍니다.

17.1 X 서버 준비

Termux 자체는 그래픽 출력이 없습니다. Wolf3D 같은 SDL 앱을 보려면 별도의 X 서버 앱이 필요합니다.

  1. F-Droid에서 Termux:X11 앱 설치.
  2. Termux에서 pkg install termux-x11-nightly.
  3. Termux:X11 앱을 실행해 검은 X 창을 띄움.
  4. Termux 셸에서 export DISPLAY=:0.

17.2 패키지 확인

pkg install -y clang make git pkg-config sdl2 sdl2-mixer
clang --version

Termux의 컴파일러는 GCC가 아니라 Clang입니다. 거의 호환되지만 일부 GCC 확장은 다릅니다.

17.3 소스 / 데이터 가져오기

cd ~
mkdir -p wolf3d-port/{src,data}
cd wolf3d-port
git clone https://github.com/mozzwald/wolf4sdl src
# 데이터 파일은 storage 권한 후 옮기기
termux-setup-storage
cp /sdcard/Download/*.WL1 data/
cd data && for f in *.WL1; do mv "$f" "$(echo $f | tr A-Z a-z)"; done

17.4 빌드

Termux의 Clang에서 다음 조정이 필요할 수 있습니다.

cd ~/wolf3d-port/src
# Makefile에서 CC=gcc → CC=clang 으로 (또는 그냥 환경변수)
make CC=clang -j4

또는 직접:

clang -O2 *.c \
    $(pkg-config --cflags --libs sdl2 SDL2_mixer) \
    -o wolf3d

디버깅 ─ "왜 안 돌지?"를 풀어내는 기술

실제 포팅에서는 항상 무언가가 어긋납니다. 그 순간이 사실 가장 큰 학습의 기회입니다. 이 장은 디버깅의 일반 원칙과, Wolf3D 포팅에서 자주 나오는 구체적 사례를 모았습니다.

18.1 디버깅의 5단계 사고

  1. 재현 ─ 매번 같은 증상이 나오는지 확인. 가끔 나오면 더 어렵다.
  2. 국소화 ─ 문제가 일어나는 정확한 함수/코드 줄을 좁힌다.
  3. 가설 ─ "왜 이렇게 됐는지" 추측. 한 번에 하나씩.
  4. 실험 ─ 그 가설이 맞다면 어떤 변화가 일어날지 예측 → 실제로 그렇게 되는지 시험.
  5. 수정 + 재발 방지 ─ 고치고, 같은 종류 버그가 또 안 생기게 코드/테스트를 다듬는다.

18.2 printf 디버깅 ─ 가장 단순하고 강력하다

고급 디버거가 없는 환경(특히 Termux)에서는 printf + fflush(stdout)가 왕도입니다.

fprintf(stderr, "[%s:%d] obj=%p x=%d y=%d\n",
        __FILE__, __LINE__, obj, obj->x, obj->y);
fflush(stderr);

stderr는 라인 버퍼링이라 더 즉시 보입니다. stdout은 종료 시까지 안 보일 수 있어요.

18.3 GDB 5분 강의

리눅스(또는 MSYS2)에서 디버그 빌드:

make clean
make CFLAGS='-g -O0'      # 디버그 정보, 최적화 끔
gdb ./wolf3d
GDB 명령의미
run 또는 r프로그램 실행
break ThreeDRefresh함수 시작점에 중단
break wl_draw.c:123특정 줄에 중단
continue 또는 c다음 중단점까지
next 또는 n한 줄 실행(함수 안 안 들어감)
step 또는 s한 줄 실행(들어감)

backtrace 또는 bt호출 스택

처음에는 run, break, print, continue, bt 다섯 개만 알면 80%는 처리할 수 있습니다.

18.4 크래시 분석 ─ "Segmentation fault"

가장 흔한 충돌. 원인은 거의 항상 다음 셋 중 하나입니다.

  • 널 포인터 역참조 (obj->x인데 obj == NULL)
  • 해제된 메모리 접근 (use-after-free)
  • 배열 범위 밖 (tilemap[64][64]인데 tilemap[65][3])

GDB로 충돌 위치를 즉시 알 수 있습니다.

(gdb) run
... segfault ...
(gdb) bt          # 어디서 죽었나
(gdb) frame 0     # 가장 위 프레임으로
(gdb) info locals # 그 시점의 변수들

또는 valgrind ./wolf3d(리눅스) — 메모리 오류를 매우 자세히 보여 줍니다.

18.5 자주 만나는 구체적 함정

① 바이트 순서 (엔디안)

원본 데이터는 리틀 엔디안(x86)으로 저장되어 있습니다. 빌드 대상이 x86/ARM이면 문제 없지만, PowerPC 같은 빅 엔디안에서는 모든 word·dword를 뒤집어야 합니다.

#define READ_LE16(p) ((p)[0] | ((p)[1] << 8))
#define READ_LE32(p) ((p)[0] | ((p)[1]<<8) | ((p)[2]<<16) | ((p)[3]<<24))

최근의 안드로이드/맥/PC는 모두 리틀 엔디안이라 보통 신경 안 써도 됩니다.

② 정렬(alignment)

ARM은 4바이트 정렬되지 않은 4바이트 읽기에서 SIGBUS로 죽을 수 있습니다. 원본 Wolf3D는 데이터 파일에서 임의 오프셋의 워드를 직접 캐스팅해서 읽는 경우가 있는데, ARM/Termux 빌드에서 이게 문제가 됩니다.

// 나쁜 예 (x86에서만 안전)
word val = *(word *)(buf + off);

// 좋은 예
word val = buf[off] | (buf[off+1] << 8);
// 또는
word val; memcpy(&val, buf+off, 2);

③ signed char vs unsigned char

x86 GCC는 기본 signed지만, ARM은 기본 unsigned일 수 있습니다. 다음 코드가 다르게 동작합니다.

char c = 0xFF;
if (c < 0)   // x86: 참, ARM: 거짓!

해결: -fsigned-char 컴파일 플래그를 추가하거나, 명시적으로 int8_t/uint8_t를 씁니다.

18.6 데이터 파싱 디버깅 ─ "다 깨져 보여요"

맵이나 텍스처가 깨져 보이면, 보통 압축 해제 오프셋이 한 바이트 어긋난 경우입니다. 가장 좋은 방법: VSWAP 파일의 첫 텍스처를 별도 PNG로 덤프하는 작은 프로그램을 짜서, 눈으로 확인합니다.

// dump_vswap.c (개념)
fread(header, ...);
chunk_count = header[0];
for (i = 0; i < chunk_count; i++) {
    seek(file, offsets[i]);
    fread(pixels, 1, 64*64, file);
    save_as_png("tex_%03d.png", i, pixels, palette);
}

그림이 제대로 보이면 압축 해제는 OK, 그래도 게임에서 깨지면 렌더러 코드의 문제입니다.

18.7 디버깅용 화면 출력

코드 흐름이 잘못된 위치를 화면에 표시하면 진단이 빠릅니다.

// 화면 한 구석에 색을 칠해 "여기까지 왔다" 표시
gfxbuf[10 * 320 + 10] = 15;   // 노랑색 (팔레트 15)

매 프레임 다른 색을 칠하면 프레임률도 어림짐작 가능.

최적화와 확장 ─ "내 포팅판"을 만들기

일단 동작하기 시작하면, 마음껏 손을 댈 차례입니다. 이 장은 자신의 포팅에 추가해 볼 만한 개선·확장 아이디어를 모았습니다.

19.1 해상도 끌어올리기

원본은 320×200 또는 320×240(스트레치). 현대 모니터에선 너무 작아 보입니다. 두 가지 방법.

A. 정수 배율 확대

320×200을 4배(1280×800) 또는 6배(1920×1200)로 확대. SDL의 SDL_BlitScaled나 SDL_RenderSetLogicalSize로 한 줄. 픽셀 모양 그대로 보존.

B. 네이티브 고해상도 렌더링

광선 수를 화면 너비에 맞춰 늘림. viewwidth = 1920처럼 큰 값을 쓰고, 모든 그리기를 그 해상도로 직접 수행. 진짜 1080p 게임이 됨.

B 방식은 코드 안의 viewwidth, viewheight를 동적으로 만들면 됩니다. pixelangle[viewwidth] 같은 테이블 크기도 늘려야 합니다.

19.2 와이드스크린(16:9)

원본은 4:3을 가정합니다. 16:9에서는 시야각(FOV)을 늘려 좌우로 더 보이게 합니다.

// 4:3 기준 FOV 60° → 16:9에서는 약 80°
focallength = (viewwidth/2) / tan(FOV/2)

19.3 60Hz 또는 그 이상

원본은 70Hz 틱. 60Hz 모니터의 vsync와 맞지 않아 화면 떨림이 미세하게 있습니다. 두 가지 해결:

  • 틱 주파수를 60Hz로 바꾸고, 이동 속도 상수들도 비례 조정.
  • 혹은 게임 로직은 70Hz로 두고, 렌더링만 모니터 vsync에 맞춤. 약간 복잡.

19.4 마우스룩 활성화

원본은 키보드만 가정합니다. SDL 포팅판에 마우스룩을 매끄럽게 추가합시다.

// SDL_MouseMotion 이벤트에서
int mousex; SDL_GetRelativeMouseState(&mousex, NULL);
player->angle -= mousex * mouseSensitivity;
if (player->angle < 0) player->angle += ANGLES;
if (player->angle >= ANGLES) player->angle -= ANGLES;

19.5 OPL 대신 MP3/Ogg 음악

리믹스된 음원을 쓰고 싶다면, StartMusic()을 가로채 Mix_LoadMUS로 외부 파일을 재생합니다.

빌드 시스템 깊이 ─ Make, CMake, 링크의 비밀

"make" 한 줄로 빌드가 끝나는 건 마법이 아니라 수십 개의 작은 단계가 정해진 순서대로 실행되는 결과입니다. 이 장에서는 그 안에서 무엇이 일어나는지를 처음 보는 사람도 알 수 있게 풀어 봅니다.

21.1 컴파일이라는 4단계 파이프라인

C 소스 한 파일이 실행 파일이 되기까지는 네 단계를 거칩니다.

[1] 전처리(preprocess) .c + .h → .i (한 줄에 다 풀린 C) [2] 컴파일(compile) .i → .s (어셈블리) [3] 어셈블(assemble) .s → .o (오브젝트 = 기계어 + 심볼표) [4] 링크(link) 여러 .o → 실행 파일 (모든 심볼을 주소로 묶음)

각 단계를 직접 시켜 볼 수도 있습니다.

gcc -E wl_main.c -o wl_main.i      # 1단계만
gcc -S wl_main.i -o wl_main.s      # 2단계만
gcc -c wl_main.s -o wl_main.o      # 3단계만
gcc wl_main.o id_ca.o ... -o wolf3d -lSDL2  # 4단계만

보통 gcc 한 번 호출이 이 네 단계를 묶어 처리합니다. 그러나 빌드 에러를 디버그할 때 단계를 나눠 보면 어느 단계에서 실패했는지 명확히 보입니다.

21.2 헤더 파일과 인클루드 가드

왜 모든 헤더 파일에 다음 같은 가드가 있을까요?

#ifndef WL_DEF_H
#define WL_DEF_H
// ... 헤더 본문 ...
#endif

전처리 단계에서 #include는 그 파일 전체를 통째로 붙여넣기 합니다. 만약 한 .c가 같은 헤더를 두 번 인클루드하면, 같은 정의가 두 번 등장해 컴파일 에러가 납니다. 가드는 "이미 정의됐으면 두 번째는 무시" 해 줍니다.

현대 컴파일러는 #pragma once도 지원합니다. 한 줄로 끝나지만, 모든 컴파일러가 지원하진 않으므로 Wolf3D 코드처럼 옛 코드에서는 #ifndef 가드를 씁니다.

21.3 Makefile의 본질

Make의 한 줄짜리 정의: "이 출력 파일은 이런 입력 파일들에서, 이런 명령으로 만든다"의 규칙 집합입니다.

wl_main.o: wl_main.c wl_def.h        ← "wl_main.o는 이 둘에 의존"
	gcc -c wl_main.c -o wl_main.o    ← 만들 때 실행할 명령

Make는 출력 파일이 입력보다 최신이면 다시 빌드하지 않습니다. 그래서 두 번째 make가 첫 번째보다 훨씬 빠르죠.

21.3.1 자동 변수와 패턴 규칙

# 모든 .o를 같은 이름 .c에서 만드는 패턴 규칙
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

# $< = 첫 번째 의존 파일
# $@ = 출력 파일
# $^ = 모든 의존 파일

21.3.2 변수 대입 방식

Make의 함정: =와 :=가 다릅니다.

  • FOO = bar ─ 지연 평가. $(FOO)를 쓸 때마다 매번 풀어 봄.
  • FOO := bar ─ 즉시 평가. 정의 시점에 한 번만 풀어 둠.

pkg-config 같은 외부 명령을 호출할 때 :=로 두면 make 한 번에 한 번만 호출돼 빨라집니다.

21.4 의존 자동 생성

위 예에서 wl_main.o: wl_main.c wl_def.h를 사람이 일일이 적기는 번거롭습니다. GCC가 자동 생성해 줍니다.

gcc -MMD -MP -c wl_main.c -o wl_main.o
# 부산물로 wl_main.d 생성됨. 내용:
# wl_main.o: wl_main.c wl_def.h id_ca.h ...

Makefile 끝에 -include $(OBJS:.o=.d)를 두면, 헤더 변경 시 의존하는 .c만 자동으로 다시 빌드됩니다.

21.5 CMake가 하는 일

Make는 단일 OS에 맞춰 작성됩니다. 윈도우에서는 nmake, 리눅스에서는 make, 맥에서는 또 다른 도구. CMake는 이런 차이를 흡수하는 메타 빌드 시스템입니다.

CMakeLists.txt ↓ cmake 실행 [리눅스] Makefile ─ make [Windows MinGW] Makefile ─ mingw32-make [Windows MSVC] .sln ─ msbuild / Visual Studio [Xcode] .xcodeproj [Ninja] build.ninja ─ ninja

한 번 CMakeLists.txt를 만들어 두면, 어디서든 같은 방식으로 빌드 파일이 생성됩니다.

# 간단한 CMakeLists.txt
cmake_minimum_required(VERSION 3.15)
project(wolf3d C)
set(CMAKE_C_STANDARD 99)

find_package(SDL2 REQUIRED)
find_package(SDL2_mixer REQUIRED)

file(GLOB SOURCES *.c)
add_executable(wolf3d ${SOURCES})
target_link_libraries(wolf3d SDL2::SDL2 SDL2_mixer::SDL2_mixer)

21.6 링크 단계의 디테일

"링크"는 모든 .o 파일의 심볼(함수·전역 변수 이름)을 실제 메모리 주소로 연결하는 작업입니다. 가장 자주 보는 에러는 두 가지.

에러의미해결
undefined reference to 'foo'어떤 .o도 foo를 정의하지 않음. 또는 라이브러리 누락.구현된 .c가 빌드에 포함됐는지, 라이브러리(-l) 인자가 있는지 확인
multiple definition of 'bar'둘 이상의 .o가 같은 전역 bar를 정의헤더의 정의를 extern 선언으로 바꾸고, 정의는 한 .c에만 둠

21.7 -l과 -L, -I의 차이

플래그역할
-Idir헤더 파일 검색 경로 추가 (전처리 시)
-Ldir라이브러리 검색 경로 추가 (링크 시)
-lnamelibname.so 또는 libname.a와 링크

예: gcc -I/opt/sdl2/include -L/opt/sdl2/lib -lSDL2 -lSDL2_mixer ...

21.8 정적 라이브러리 vs 동적 라이브러리

정적(.a / .lib)

실행 파일 안에 라이브러리 코드가 합쳐 들어감. 배포 단순, 파일 큼, 업데이트 어려움.

동적(.so / .dll / .dylib)

실행 시 OS가 따로 로드. 파일 작음, 업데이트 쉬움, 같이 배포해야 함.

윈도우에서 "SDL2.dll이 없습니다" 에러가 나는 이유 = 동적 링크를 했는데 DLL을 같이 안 줬기 때문.

21.9 Wolf4SDL의 Makefile 한 줄씩 읽어 보기

실전 Makefile을 한 줄씩 해부합니다.

# 1) 컴파일러와 플래그
CC      ?= gcc                              # ?= : 환경 변수에 없을 때만 기본값
CFLAGS  := -Wall -O2 -g                     # 즉시 평가
CFLAGS  += $(shell pkg-config --cflags sdl2) # 누적

# 3) 최종 타깃
wolf3d: $(OBJS)
	$(CC) $(OBJS) -o $@ $(LDFLAGS)

# 4) 패턴 규칙
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

# 5) 정리
clean:
	rm -f *.o wolf3d

.PHONY: clean                               # "clean"은 파일이 아니라 작업

원본의 어셈블리 코드 ─ 무엇을 왜 ASM으로 짰나

1992년 원본 Wolf3D의 wl_asm.asm과 id_vl_a.asm은 가장 핫한 루프들을 어셈블리로 짠 파일입니다. C 포팅판은 이걸 모두 C로 다시 썼지만, 원본을 이해하면 "왜 빠른가"의 비밀이 보입니다.

22.1 어떤 함수가 ASM이었나

함수역할왜 ASM?

ScalePost한 세로열 텍스처 그리기광선당 한 번, 거기에 픽셀당 한 번씩 분기. 자가 수정 코드 사용

22.2 ScalePost의 자가 수정 코드(SMC)

한 광선 거리에 따라 텍스처를 화면 세로 N픽셀로 늘려 그릴 때, 이상적으로는 N번의 "텍스처에서 한 픽셀 읽어 화면에 쓰기"가 반복됩니다. 원본은 N의 값(예: 200)을 미리 알기 때문에, 그 자리에서 200개의 "MOV; ADD" 쌍을 동적으로 생성합니다.

호출 시점: | ┌────────────────────────┐ │ │ MOV AL,[ESI] │ ← 텍스처 색 읽기 │ │ MOV [EDI],AL │ ← 화면에 쓰기 │ │ ADD ESI,step1 │ ← 텍스처 좌표 진행 │ │ ADD EDI,80 │ ← 화면 다음 줄 │ │ ...반복 N회... │ │ └────────────────────────┘ ▼ 자가 수정 코드 영역에 위 명령을 N개 펼쳐 둠 → 점프

왜 이렇게? 루프 카운터·점프·조건 검사를 모두 없애서 매 픽셀의 비용을 최소화하기 위함입니다. 한 프레임 65,000 픽셀에서 한 픽셀에 0.5 사이클을 줄이면 30,000 사이클이 절약됩니다.

현대에서는 역효과 · 자가 수정 코드는 CPU의 명령 캐시와 분기 예측기를 무력화합니다. 1992년 386에서는 캐시가 작아서 효과적이었지만, 현대 CPU에서는 오히려 느립니다. 그래서 Wolf4SDL은 단순 C 루프로 다시 썼고, 그래도 충분히 빠릅니다.

22.3 인라인 어셈블리 ─ C 안에 ASM 한 줄

원본의 일부 함수는 별도 .asm이 아니라 C 함수 안에 asm 블록으로 들어 있습니다.

// Borland C++ 3.1 스타일
int FixedMul(int a, int b)
{
    int result;
    asm {
        mov eax, a
        imul b
        shrd eax, edx, 16     ; 64비트 결과를 16비트 시프트
        mov result, eax
    }
    return result;
}

GCC 인라인 어셈블리는 문법이 다릅니다(AT&T 또는 Intel). Wolf4SDL은 보통 이런 함수를 순수 C로 다시 씁니다.

// 순수 C 버전
static inline int32_t FixedMul(int32_t a, int32_t b)
{
    return (int32_t)(((int64_t)a * b) >> 16);
}

현대 컴파일러는 이걸 한 IMUL 명령으로 컴파일해 줍니다. ASM 직접 작성과 성능 차이가 거의 없죠.

22.4 ASM → C 포팅의 체크리스트

  1. 입력 레지스터(eax, ebx, …)가 어떤 변수에 대응하는지 파악
  2. 플래그(CF, ZF, OF) 의존이 있는지 확인 ─ C에는 없으므로 명시적 비교로 바꾸어야 함
  3. "부산 효과"(다른 레지스터 변경)가 호출자에 영향이 없는지 확인
  4. 처음에는 그대로 옮기고, 동작이 같은지 검증한 후 깔끔히 다듬기

22.5 진행 체크

  • ASM 함수가 왜 쓰였는지 한 줄로 설명할 수 있음
  • SMC의 개념을 이해
  • FixedMul이 64비트 곱셈 후 시프트임을 안다
23장

데이터 포맷 완전 해부 ─ VSWAP, RLEW, Huffman

이번 장은 Wolf3D 데이터 파일들의 정확한 바이트 단위 구조를 다룹니다. 이걸 알면 데이터 파일에서 임의의 정보를 추출하는 도구도 짤 수 있고, 자기만의 맵·텍스처를 넣을 수 있습니다.

23.1 VSWAP — 가장 큰 미디어 묶음

VSWAP는 벽 텍스처(앞), 스프라이트(중간), 디지털 사운드(끝) 세 영역으로 나뉜 한 묶음 파일입니다.

// 헤더 (6바이트)
struct VSwapHeader {
    word ChunksInFile;
    word PMSpriteStart;   // 스프라이트 시작 청크 번호
    word PMSoundStart;    // 사운드 시작 청크 번호
};
// 그 다음: 각 청크의 [offset(4) | length(2)] 배열
// 그 다음: 실제 데이터

예: ChunksInFile = 152, PMSpriteStart = 106, PMSoundStart = 135라면, 0~105는 벽, 106~134는 스프라이트, 135~151은 사운드.

23.1.1 벽 텍스처 청크

각 벽 텍스처는 정확히 4096바이트 = 64×64 픽셀. 압축 없음. 한 픽셀이 한 바이트 팔레트 인덱스. 단 저장 순서가 세로열 우선(column-major)이라 보통의 가로열 우선(row-major)과 다릅니다.

// 일반 가로 우선
pixel = data[y * 64 + x];

// VSWAP의 세로 우선
pixel = data[x * 64 + y];

23.1.2 스프라이트 청크

스프라이트는 압축됩니다. 헤더가 먼저:

struct SpriteHeader {
    word leftpix;           // 첫 비투명 열 (0~63)
    word rightpix;          // 마지막 비투명 열
    word dataofs[rightpix - leftpix + 1];  // 각 열의 데이터 오프셋
    // 그 뒤로 열별 픽셀 데이터
};

각 열은 "포스트(post)"의 리스트. 한 포스트는 (시작 Y, 길이, 픽셀들)로 표현되어 투명 영역을 건너뜁니다. Doom의 patch 포맷과 매우 비슷합니다.

23.1.3 사운드 청크

raw 8비트 부호 없는 PCM, 7000 Hz. 이걸 SDL_mixer의 Mix_Chunk로 변환합니다.

23.2 RLEW 압축 ─ 맵 데이터

GAMEMAPS의 각 평면은 RLEW(Run-Length Encoded Word)로 압축돼 있습니다. 한 워드(2바이트)가 단위입니다.

// 마커는 MAPHEAD의 첫 워드 (예: 0xABCD)
while (src < src_end) {
    word w = *src++;
    if (w == RLEW_MARKER) {
        word count = *src++;
        word value = *src++;
        for (i = 0; i < count; i++) *dst++ = value;
    } else {
        *dst++ = w;
    }
}

한 단위가 워드라서 "Run-Length Encoded WORD". 빈 공간(타일 코드 0)이 잔뜩 있는 맵을 매우 효율적으로 압축합니다.

참고: 맵 데이터는 보통 RLEW로 한 번, 그리고 그 위에 Carmack 압축이라는 또 다른 RLE로 한 번 더 압축돼 있어 두 번 풀어야 합니다.

23.3 Carmack 압축 (선택)

John Carmack이 직접 만든 RLE의 변형. "이전에 본 패턴을 다시 가리키는 백레퍼런스"가 들어가 있습니다(LZ77과 비슷).

// 두 가지 특수 바이트 0xA7, 0xA8
// 0xA7 ... → 가까운 백레퍼런스 (오프셋 1바이트)
// 0xA8 ... → 먼 백레퍼런스 (오프셋 2바이트)
// 그 외 → 그대로 출력

구현은 약 40줄. 자세한 코드는 Wolf4SDL의 CA_CarmackExpand()를 보세요.

23.4 Huffman 압축 ─ VGAGRAPH

메뉴/HUD 비트맵은 Huffman으로 압축됩니다. 트리는 VGAHEAD나 별도 헤더 파일에 임베드돼 있습니다.

// Huffman 노드 (개념)
struct HuffNode {
    word bit0;  // 0일 때 다음 노드 또는 (256+) 리터럴 + 256
    word bit1;
};
// 디코딩: 비트 하나씩 읽으면서 트리 따라 내려가, 리프(값>=256)면 출력
HuffNode *node = &tree[head];
while (out < out_end) {
    if (bit == 0) v = node->bit0; else v = node->bit1;
    if (v >= 256) { *out++ = v - 256; node = &tree[head]; }
    else            node = &tree[v];
}

전체 게임에서 한 트리만 쓰입니다. 한 번 메모리에 올려 두고 매 청크 해제마다 재사용.

23.5 작은 도구 짜기 ─ 텍스처 덤프

실습 삼아 VSWAP의 첫 텍스처를 PPM 이미지로 덤프하는 작은 도구를 짭니다.

// dump_tex.c
#include <stdio.h>
#include <stdint.h>

uint8_t pal[256][3];  // 팔레트는 별도 로드

int main(int argc, char **argv) {
    FILE *f = fopen(argv[1], "rb");
    uint16_t chunks; fread(&chunks, 2, 1, f);
    fseek(f, 6, SEEK_SET);
    uint32_t off; uint16_t len;
    fread(&off, 4, 1, f); fread(&len, 2, 1, f);
    uint8_t buf[4096]; fseek(f, off, SEEK_SET); fread(buf, 1, 4096, f);
    FILE *out = fopen("tex0.ppm", "wb");
    fprintf(out, "P6\n64 64\n255\n");
    for (int y = 0; y < 64; y++)
      for (int x = 0; x < 64; x++) {
        int idx = buf[x*64 + y];  // 세로 우선!
        fwrite(pal[idx], 1, 3, out);
      }
    return 0;
}

이 작은 도구를 띄워 "텍스처가 진짜로 어떻게 생겼는지"를 눈으로 확인하는 것 — 데이터 포맷 학습의 가장 빠른 길입니다.

23.6 진행 체크

  • VSWAP의 3영역(벽·스프라이트·사운드)을 외움
  • 벽 텍스처가 세로 우선 저장임을 안다
  • RLEW 알고리즘을 의사 코드로 적을 수 있음
  • Huffman 디코딩의 큰 그림을 안다
24장

캐시·메모리 매니저 ─ 1992년의 메모리 다이어트

1992년 PC의 메모리는 640KB. 게임 코드 + 자료 + 화면 버퍼 + 사운드 버퍼가 모두 그 안에 들어가야 했습니다. id Software는 자체 메모리 매니저(id_mm)와 캐시 매니저(id_ca)를 만들어 이 좁은 공간을 매우 영리하게 굴렸습니다.

24.1 MM ─ 메모리 풀

표준 malloc/free는 외부 단편화가 생깁니다. 작은 빈틈이 메모리에 흩어져, "총 100KB 비었지만 50KB짜리는 못 잡는" 상황. id_mm은 그 해결책으로 자체 풀을 운영합니다.

  • 시작 시 큰 덩어리를 통째로 잡음(예: 500KB).
  • 그 안에서 작은 블록을 잘라 줌(MM_GetPtr).
  • 해제는 MM_FreePtr로, 빈 공간을 합쳐 둠.
  • "이동 가능 블록(MM_BombOnError)" 개념: 메모리가 부족하면 일부 블록을 다른 위치로 옮겨 빈 공간을 만든다.

현대 Wolf4SDL은 이걸 거의 비활성화하고 malloc/free를 직접 씁니다. MM_GetPtr는 사실상 malloc의 얇은 래퍼.

24.2 CA ─ 캐시 매니저

id_ca는 데이터 파일에서 청크를 꺼내 메모리에 두는 일을 합니다.

  • CA_CacheGrChunk(chunk) ─ 그래픽 청크를 메모리에 올려라
  • CA_LoadAllSounds() ─ 모든 사운드를 메모리에
  • CA_CacheMap(level) ─ 맵을 RLEW/Carmack 풀어 평면 두 개로

같은 청크가 이미 메모리에 있으면 다시 안 읽고 그대로 씁니다. 그래서 "캐시"라는 이름.

24.3 청크 ID 시스템

모든 자원에 정수 ID가 붙어 있습니다. graphext.h 같은 자동 생성 헤더에 거대한 enum이 들어 있죠.

enum {
    H_BJPIC = 3,
    H_CASTLEPIC,
    H_KEYBOARDPIC,
    ...
    L_NOFOOD = 87,
    L_MEALANDLIGHT,
    ...
};

그래서 코드는 CA_CacheGrChunk(H_BJPIC)처럼 의미가 보이는 이름을 쓰면서, 내부적으로는 단순 정수 인덱스로 동작합니다.

24.4 페이지 매니저(id_pm)

VSWAP은 너무 커서 한꺼번에 다 못 올리던 시절이 있었습니다. id_pm은 페이지(청크) 단위로 디스크에서 읽고, LRU(least-recently-used)로 메모리에서 가장 안 쓰는 페이지를 버립니다.

현대 시스템에서는 VSWAP가 1MB도 안 되어 통째로 올려도 됩니다. 그래서 Wolf4SDL의 PM_Startup은 그냥 전체 파일을 메모리로 mmap/malloc 해 둡니다.

24.5 EMS·XMS 메모리 ─ 잊혀진 개념

DOS의 640KB 한계를 넘기 위해 만들어진 두 확장 메모리 표준.

  • EMS(Expanded Memory): 64KB짜리 페이지로 큰 메모리를 들여다 봄(뱅킹).
  • XMS(eXtended Memory): 1MB 이상의 메모리를 보호모드로 잠깐 접근.

Wolf3D는 둘 다 지원했습니다. 코드 안에 UseEMS, UseXMS 분기가 가득. 현대 포팅판은 이 분기들을 모두 "항상 메모리에 있음"으로 단순화합니다.

24.6 진행 체크

  • MM이 자체 메모리 풀임을 안다
  • CA가 디스크→메모리 캐시 역할임을 안다
  • EMS/XMS가 옛 시대 개념이라 현대에서 없어졌음을 안다

적 AI와 상태 머신 ─ wl_state.c 깊이 읽기

Wolf3D의 적 AI는 너무도 간단해서 오히려 미학이 됩니다. 적은 가만히 서 있다가, 플레이어를 보면 추격하고, 사정거리에 들어오면 쏘고, 죽습니다. 이 단순한 행동이 어떻게 코드로 표현되는지 봅시다.

25.1 모든 적은 같은 함수로 움직인다

적 AI의 모든 흐름이 다음 한 함수로 모입니다.

void DoActor(objtype *ob)
{
    if (ob->state->think) ob->state->think(ob);  // 매 틱 행동
    ob->ticcount -= tics;
    while (ob->ticcount <= 0) {                  // 상태 만료
        if (ob->state->action) ob->state->action(ob);  // 진입 액션
        ob->state = ob->state->next;             // 다음 상태로
        if (!ob->state) { /* 액터 제거 */ break; }
        ob->ticcount += ob->state->tictime;
    }
}

이 패턴이 곧 "유한 상태 머신(FSM)을 데이터로 표현"하는 방법입니다.

25.2 친위대 병사의 상태 사슬

statetype s_grdpath1   = { true, SPR_GRD_W1_1, 20,       T_Path,   NULL,        &s_grdpath1s };
statetype s_grdpath1s  = { true, SPR_GRD_W1_1, 5,        NULL,     NULL,        &s_grdpath2 };
// ... 계속

statetype s_grdshoot1  = { false,SPR_GRD_SHOOT1, 20,     NULL,     NULL,        &s_grdshoot2 };

statetype s_grdshoot3  = { false,SPR_GRD_SHOOT3, 20,     NULL,     NULL,        &s_grdchase1 };

statetype s_grddie1    = { false,SPR_GRD_DIE_1, 15,      NULL,     A_DeathScream,&s_grddie2 };

25.3 T_Stand ─ "보일 때까지 가만히"

SightPlayer는 광선을 한 번 발사해서 (DDA 검사) 플레이어가 보이면 추격 상태로 바꿉니다. 거리/각도/벽 가림을 모두 고려.

25.4 T_Chase ─ 추격

적은 격자에서 격자로만 이동합니다. 한 타일을 다 가면 다음 방향을 결정합니다.

void T_Chase(objtype *ob)
{
    int32_t move = ob->speed * tics;
    while (move) {
        if (ob->distance < 0) { /* 문 열기 */ }
        if (move < ob->distance) {
            MoveObj(ob, move);
            ob->distance -= move;
            return;
        }
        // 다음 타일 도달
        ob->x = (ob->tilex << TILESHIFT) + TILEGLOBAL/2;
        ob->y = (ob->tiley << TILESHIFT) + TILEGLOBAL/2;
        move -= ob->distance;
        SelectChaseDir(ob);  // 다음 격자 방향 결정
    }
}

25.5 가시선 검사 ─ CheckSight

적이 플레이어를 보는지 결정하는 핵심 함수. 두 점 사이에 벽이 없는지 DDA로 검사.

boolean CheckSight(objtype *from)
{
    // 거리 검사 (너무 멀면 false)
    // 시야각 검사 (등 뒤면 false)
    // 광선 발사 ─ from->x,y → player->x,y
    //   격자마다 벽이 있으면 false, 끝까지 가면 true
    return result;
}

이 함수가 한 프레임에 수십 번 호출되므로, 최적화의 핵심 지점입니다. 원본은 PVS(잠재 가시 집합)나 BSP 없이 그냥 매번 DDA — 단순함의 미학.

  • CheckSight가 DDA로 벽을 검사함을 안다
26장

HUD와 메뉴 시스템

게임 화면 아래의 체력·탄약 표시(HUD), 그리고 ESC 키로 뜨는 메뉴는 별도의 단순한 비트맵 시스템으로 동작합니다.

26.1 HUD ─ wl_main.c의 DrawStatus 함수들

  • DrawFace() ─ 체력에 따라 BJ 얼굴 그림이 바뀜(만신창이 ↔ 자신만만)
  • DrawHealth() ─ 숫자로 체력 표시
  • DrawAmmo() ─ 탄약
  • DrawWeapon() ─ 현재 무기 그림
  • DrawScore() ─ 점수
  • DrawKeys() ─ 보유 열쇠 아이콘
  • DrawLevel(), DrawLives() ─ 레벨/남은 목숨

모두 비트맵을 미리 캐시해 두고, 일정 영역에 단순 복사합니다.

26.2 LatchPic ─ 빠른 그리기를 위한 사전 변환

원본의 ModeY VGA에서는 그리기 비용을 줄이려고 "래치(latch)" 메모리 영역을 썼습니다. HUD 비트맵을 시작 시 한 번 latch 영역에 복사해 두고, 매 프레임 그릴 때는 VGA의 라텍스 복사 명령 하나로 끝.

SDL 포팅판은 단순 픽셀 복사로 충분히 빠르므로 latch 개념을 무시합니다.

26.3 메뉴 ─ wl_menu.c의 자료 주도 설계

메뉴는 코드가 아니라 데이터 구조 배열로 표현됩니다.

typedef struct {
    char        string[36];
    short       (*routine)();
    short       active;
} CP_iteminfo;

CP_iteminfo MainItems[] =
{
    {"NEW GAME",   CP_NewGame,   1},

    {"CONTROL",    CP_Control,   1},
    {"LOAD GAME",  CP_LoadGame,  1},
    {"SAVE GAME",  CP_SaveGame,  0},  // 게임 중 아닐 땐 비활성

새 메뉴 항목을 추가하려면 이 배열에 한 줄 더 넣고, 항목 처리 함수를 작성하면 끝.

독일어 버전(UPLOAD가 아니라 GOODTIMES + SPANISH 같은 매크로)이 따로 있었는데, 모든 텍스트가 foreign.h에 모여 있어 그것만 바꾸면 다른 언어 빌드가 됩니다.

// 독일어 빌드에서는
// #define STR_NG       "Neues Spiel"
// #define STR_SD       "Klang"

한국어 빌드를 직접 만들고 싶으면, foreign.h에 한국어 정의를 추가하고 폰트(VGAGRAPH)를 한국어 글자로 교체하면 됩니다.

26.6 진행 체크

  • HUD 그리기 함수들의 이름 다섯 개 안다
  • 메뉴가 자료 주도 설계임을 이해
  • 텍스트 로컬라이즈가 foreign.h 하나에 모여 있음을 안다
27장

멀티 에피소드 빌드 ─ WL1·WL6·SOD

같은 코드로 셰어웨어판(WL1), 6에피소드 풀 버전(WL6), Spear of Destiny(SOD) 등 여러 게임을 빌드할 수 있습니다. 비결은 매크로 분기입니다.

27.1 version.h ─ 빌드의 운명을 결정

// 다음 중 하나만 활성화
#define UPLOAD          // 셰어웨어 1에피소드 (WL1)
//#define GOODTIMES     // 등록판 6에피소드 (WL6)
//#define SPEAR         // Spear of Destiny (SOD)
//#define SPEARDEMO     // SOD 데모

#ifdef UPLOAD
  #define EXTENSION  "WL1"
  #define NUMEPISODES 1
#elif defined(GOODTIMES)
  #define EXTENSION  "WL6"
  #define NUMEPISODES 6
#elif defined(SPEAR)
  #define EXTENSION  "SOD"
  ...
#endif

컴파일러 명령줄에서 매크로를 정의해도 됩니다.

gcc -DGOODTIMES ...   # 풀 버전 빌드
gcc -DUPLOAD ...      # 셰어웨어 빌드

27.2 코드 내 분기들

중요한 분기는 다음 같은 형태로 흩어져 있습니다.

#ifdef SPEAR
    // Spear of Destiny에만 있는 적, 보스, 무기
    case ghostobj:
        ...
#else
    case fakeobj:
        ...
#endif

학습할 때는 한 버전(보통 UPLOAD)만 고려하고, 다른 버전 분기는 회색으로 봐 두면 코드가 훨씬 가벼워 보입니다.

27.3 데이터 파일 매칭

빌드데이터 확장자필요한 파일
UPLOAD.WL1VSWAP/MAPHEAD/GAMEMAPS/AUDIOT/AUDIOHED/VGAGRAPH.WL1
GOODTIMES.WL6같은 6파일 .WL6
SPEAR.SODVSWAP/MAPHEAD/GAMEMAPS/AUDIOT/AUDIOHED/VGAGRAPH.SOD, VSWAP.SOD

빌드 매크로와 데이터 확장자가 일치해야 합니다. 안 그러면 "MAPHEAD.WL6를 못 찾는다"는 에러.

27.4 셰어웨어로 끝까지 학습하면 충분

이 가이드는 UPLOAD(WL1) 기준으로 모든 설명이 진행됐습니다. 학습용으로는 1에피소드면 충분하고, 모든 핵심 시스템이 다 들어 있습니다.

27.5 진행 체크

  • version.h의 매크로로 빌드가 분기됨을 안다
  • 빌드 매크로와 데이터 확장자가 일치해야 함을 안다
  • 자신은 어떤 빌드(UPLOAD/GOODTIMES/SPEAR)로 학습 중인지 확인

다른 환경으로의 확장 ─ macOS, 라즈베리 파이, WebAssembly

Windows·Linux·Termux를 끝냈으니, 같은 코드를 다른 환경에서도 돌릴 수 있다는 자신감이 생겼을 겁니다. 이 장은 그 자신감을 실제 명령어로 옮깁니다.

28.1 macOS

Apple Silicon(M1/M2/…) 또는 Intel Mac 모두 동일.

# Homebrew 사용

git clone https://github.com/mozzwald/wolf4sdl

Mac은 사실상 BSD + GUI라서 리눅스 절차가 거의 그대로 통합니다.

28.2 라즈베리 파이

라즈베리 파이 OS는 데비안 기반이라 16장 절차 그대로. 단 다음 두 가지를 고려:

  • 32비트 OS(Raspbian)면 int가 32비트로 자연스럽지만, 64비트 OS면 변수 크기 가정에 주의.
  • SDL2의 OpenGL ES 백엔드를 쓰면 GPU 가속으로 매우 부드러움. SDL_HINT_RENDER_DRIVER=opengles2 환경변수.

RPi Zero W 같은 ARM11 저사양에서도 60fps 어림없이 나옵니다. 1992년 386보다 훨씬 강력하니까요.

28.3 WebAssembly ─ 브라우저에서 Wolf3D

가장 흥미로운 도전. Emscripten으로 C 코드를 wasm으로 컴파일하면 브라우저에서 직접 돌릴 수 있습니다.

git clone https://github.com/emscripten-core/emsdk
cd emsdk && ./emsdk install latest && ./emsdk activate latest
source ./emsdk_env.sh

cd ~/wolf3d-port/src
emcc *.c \
  -s USE_SDL=2 -s USE_SDL_MIXER=2 \
  -s WASM=1 \
  --preload-file ../data \
  -o wolf3d.html

결과로 wolf3d.html, wolf3d.js, wolf3d.wasm, wolf3d.data가 생깁니다. 로컬 서버를 띄워(python3 -m http.server) 브라우저에서 열면 게임이 그대로 돌아갑니다.

주의 · 메인 루프가 무한 while을 쓰면 브라우저가 멈춥니다. emscripten_set_main_loop(PlayLoop, 70, 1)로 콜백 등록 형태로 바꿔야 합니다. Wolf4SDL의 WASM 분기에 예시 있음.

28.4 Nintendo Switch, PS Vita 등 콘솔

홈브루 SDK가 갖춰진 콘솔이라면 SDL2를 통해 거의 그대로 빌드됩니다. devkitPro의 libnx 또는 vitasdk가 SDL2를 제공합니다. 자세한 절차는 각 SDK 문서를.

실습 ─ 200줄짜리 미니 레이캐스터 직접 짜기

지금까지 배운 모든 원리를 한 번에 확인하는 가장 좋은 방법은, 처음부터 자기 손으로 작은 레이캐스터를 짜는 것입니다. Wolf3D의 1%도 안 되는 코드로 핵심 환상을 재현할 수 있습니다.

29.1 목표

  • 8×8 격자 맵 안에서 1인칭 시점으로 이동
  • 화살표 키로 회전, W/S로 전후진
  • 벽에 텍스처 없이 단색만(나중에 텍스처 추가)
  • SDL2 한 라이브러리만 사용
  • 전체 200줄 이내

29.2 전체 코드

아래를 mini.c로 저장하고 빌드하세요.

// mini.c ─ 200줄짜리 Wolf-style 레이캐스터
#include <SDL.h>
#include <math.h>
#include <stdbool.h>

#define W   640
#define H   400
#define FOV (60.0 * M_PI / 180.0)

static const char map[8][9] = {
    "11111111",
    "1......1",
    "1.111..1",
    "1.1.1..1",
    "1.1.1111",
    "1......1",
    "1......1",
    "11111111",
};

int main(int argc, char **argv)
{
    SDL_Init(SDL_INIT_VIDEO);
    SDL_Window *win = SDL_CreateWindow("Mini Raycaster",
        SDL_WINDOWPOS_CENTERED, SDL_WINDOWPOS_CENTERED, W, H, 0);
    SDL_Renderer *ren = SDL_CreateRenderer(win, -1, SDL_RENDERER_ACCELERATED);

    double px = 2.5, py = 2.5;  // 플레이어 위치
    double pa = 0.0;            // 바라보는 각도 (라디안)

    bool running = true;
    Uint32 last = SDL_GetTicks();
    while (running) {
        Uint32 now = SDL_GetTicks();
        double dt = (now - last) / 1000.0;
        last = now;

        SDL_Event ev;
        while (SDL_PollEvent(&ev))
            if (ev.type == SDL_QUIT) running = false;

        const Uint8 *k = SDL_GetKeyboardState(NULL);
        if (k[SDL_SCANCODE_LEFT])  pa -= 2.0 * dt;
        if (k[SDL_SCANCODE_RIGHT]) pa += 2.0 * dt;
        double dx = cos(pa) * 2.0 * dt;
        double dy = sin(pa) * 2.0 * dt;
        if (k[SDL_SCANCODE_W]) {
            if (map[(int)py][(int)(px+dx)] == '.') px += dx;
            if (map[(int)(py+dy)][(int)px] == '.') py += dy;
        }
        if (k[SDL_SCANCODE_S]) {
            if (map[(int)py][(int)(px-dx)] == '.') px -= dx;
            if (map[(int)(py-dy)][(int)px] == '.') py -= dy;
        }
        if (k[SDL_SCANCODE_ESCAPE]) running = false;

        // 바닥/천장 단색
        SDL_SetRenderDrawColor(ren, 60, 60, 70, 255);
        SDL_Rect top = {0, 0, W, H/2}; SDL_RenderFillRect(ren, &top);
        SDL_SetRenderDrawColor(ren, 100, 80, 60, 255);
        SDL_Rect bot = {0, H/2, W, H/2}; SDL_RenderFillRect(ren, &bot);

        // 광선 W개 발사
        for (int x = 0; x < W; x++) {
            double ra = pa - FOV/2 + FOV * x / W;
            double rx = cos(ra), ry = sin(ra);
            double dist = 0;
            // 단순 스텝(DDA가 더 빠르지만 이해 위해)
            while (dist < 16.0) {
                dist += 0.01;
                int mx = (int)(px + rx * dist);
                int my = (int)(py + ry * dist);
                if (mx<0||mx>=8||my<0||my>=8) break;
                if (map[my][mx] == '1') break;
            }
            double corrected = dist * cos(ra - pa);   // 어안 보정
            int lineH = (int)(H / corrected);
            int y0 = H/2 - lineH/2, y1 = H/2 + lineH/2;
            int shade = 255 - (int)(corrected * 20);
            if (shade < 30) shade = 30;
            SDL_SetRenderDrawColor(ren, shade, shade*0.7, shade*0.4, 255);
            SDL_RenderDrawLine(ren, x, y0, x, y1);
        }
        SDL_RenderPresent(ren);
    }
    SDL_DestroyRenderer(ren);
    SDL_DestroyWindow(win);
    SDL_Quit();
    return 0;
}

30.2 가장 큰 교훈 세 가지

① 추상화는 결국 인간을 위한 것

VGA·OPL·인터럽트 같은 추상화 없는 환경의 코드를 직접 만져 보면, "OS와 라이브러리가 우리에게 얼마나 많은 일을 대신해 주는지"가 뼛속까지 와닿습니다.

② 제약이 창의성을 낳는다

640KB의 메모리, 4MHz의 CPU. 그 한계가 ModeY, SMC, FSM 같은 우아한 트릭들을 낳았습니다. 풍요한 환경에서는 발명할 필요가 없습니다.

③ 단순한 것이 강하다

레이캐스팅은 진짜 3D가 아닙니다. 그러나 그 단순한 가짜가 한 시대를 정의했습니다. 좋은 엔지니어링은 항상 "이 문제에 충분한 단순함"을 찾습니다.
