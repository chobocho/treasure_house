## 0. Non-negotiables (read twice)

1. **The deck HTML is a build artifact.** Never edit it by hand. Edit `goevo/deck/sections/*.html`
   or the sources/data they cite, then `make all`.
2. **No hand-written code, captures or numbers in the deck.** Every `<pre><code>` is a
   `<!--CODE file=… lines=A-B|sym=…-->` directive filled from a real file under `goevo/ex/`. Every
   terminal capture is `<!--OUT file=…-->` from `goevo/out/`, produced by `run_all.py` running the
   **installed go 1.27.1**. Every table of numbers (API additions per version, release dates, GODEBUG
   defaults, allocation counts) is `<!--TABLE file=…-->` generated by `make tables`/`run_all.py`
   from `data/*.tsv` or `docs/`. `verify_deck.py` re-checks deck ↔ source on every build.
3. **Two oracles, and only two.** (a) The installed `go 1.27.1` for *everything that can be run*.
   (b) The **official documents fetched into `docs/`** (§2) for *everything historical*: release
   notes `go.dev/doc/go1.N`, the release history page `go.dev/doc/devel/release` (every version
   with its date), the API files `api/go1.N.txt` from the golang/go repository (the exact list of
   exported symbols each version added — the ground truth for "X was added in 1.N"), the spec,
   `go1compat`, `godebug`, `toolchain`, the FAQ, the proposal repository, and Go blog posts.
   A statement of the form "1.N added X" must resolve to a line in `docs/api/go1.N.txt` (for API)
   or a heading/paragraph in `docs/relnotes/go1.N.txt` (for language, toolchain, runtime), and the
   slide carries a `<!--CITE key=… sec=…-->` badge that `check_claims.py` resolves. **Never write a
   version number from memory.** Nothing in this PLAN's topic lists (§6) is a source either — they
   are *candidates to verify*, and some of them are wrong on purpose of being memory.
4. **Every fact has a source** before it appears on a slide: dates, version numbers, names, quotes,
   proposal numbers, talk titles, performance claims. They go in `deck/claims.md` as
   `claim | source | verified-how | date`. Preference order: `docs/` (release notes, API files,
   release page, spec), the golang/go repository via the GitHub API / googlesource (tag dates,
   commit messages), `go.dev/blog`, the proposal repo, the FAQ; then Wikipedia **only** by following
   its own citation. A claim that cannot be sourced is dropped or marked
   `<span class="unv">미확인</span>`. Performance numbers ("GC pauses under 10 ms", "binaries 30%
   smaller") are **quoted from the release notes/blog with a CITE badge**, never measured here and
   never rounded differently from the source.
5. **Knowledge-cutoff discipline.** Go 1.26 (2026-02), 1.27 (2026-08-19 per the release page) and
   the 1.28 draft notes (`go.dev/doc/go1.28`, reachable, "Go 1.28 Release Notes" at tip) are **after
   or at the edge of the model's knowledge**. Their parts are written *only* from `docs/` fetched at
   build time, stamped "2026-09 기준", and the 1.28 part says on its cover that it describes a draft
   that may change. Re-fetch `docs/` (`make docs`) at the start of every session that touches parts
   8–9; the fetch log records the date and the notes' first heading.
6. **Old Go cannot run here — say so, never fake it.** Verified 2026-09-24: `GOTOOLCHAIN=go1.26.0
   go version` → `toolchain not available` (no android/arm64 toolchains on the module proxy), and
   there is no `golang.org/dl` binary for this platform. Therefore "before/after" is shown by:
   (a) the **language version directive** — the same file with `go 1.21` vs `go 1.22` in `go.mod`;
   the compiler enforces it (`cannot range over 3 (untyped int constant): requires go1.22 or later
   (-lang was set to go1.21; check go.mod)` — verified), so the *error message is the evidence*;
   (b) **GODEBUG** opt-outs from `go.dev/doc/godebug` (each setting's version and default are in the
   table there — cite it; `GODEBUG=x=0 go run .` captures both behaviours);
   (c) **GOEXPERIMENT** for features that are experiments in 1.27 (list them with
   `go env GOEXPERIMENT` / `go doc internal/goexperiment` at build time; verify each flag exists
   before using it);
   (d) for **removed pre-Go 1 syntax** (e.g. whatever Go 1's notes say was removed), the slide shows
   the old form as a plain `<pre>` with a caption "Go 1 이전 문법, 출처: Go 1 release notes §…" **and**
   the real `go build` error from 1.27.1 as an OUT capture — proof that it is gone, not a claim.
   Where none of (a)–(d) applies, the slide shows *current* behaviour, labelled "1.27.1 에서의 동작",
   and the historical statement stays a CITE. There is no fifth way. The reading-guide slide (part
   0) explains this policy to the reader in three sentences.
7. **Tests before code (RED → GREEN)** for every Python tool written here (`make_data.py` parsers of
   the release page / API files / godebug table, `gover.py`, capture normalisation, `gen_figs.py`
   assumptions via `need()`). Fixtures are small excerpts of the real fetched documents committed
   under `tools/tests/fixtures/`. Never loosen an assertion to pass. If a stated property of Go
   turns out to be false, fix the slide, not the oracle.
8. **This machine is a Galaxy Fold under Termux/proot with ~1 GB free and a nearly full swap**
   (`free -m` 2026-09-24: 1.2 GB free, swap 14/16 GB used). At most **2 subagents**, no `-j`,
   `GOFLAGS=-p=1`, `GOCACHE`/`GOPATH`/`GOMODCACHE` under `goevo/scratch/` (gitignored), one `go`
   process at a time, every experiment ≤ 60 s, `run_all.py` ≤ 15 min total and strictly sequential.
   No `-race` (unsupported on android/arm64 — verify once with a capture and cite it in the
   toolchain slide). This Termux build of `go tool` lists only `asm cgo compile cover fix link
   preprofile vet` (verified) — **no `pprof`, `trace`, `nm`, `objdump`, `dist`**: no profile/trace
   UI captures; `runtime/pprof` can still *write* a profile and `go build -pgo=` can consume it
   (verify before promising it on a slide). Check `free -m` before heavy steps. Checkpoint to disk;
   assume the session can be killed any moment. Long runs go in the background with a Monitor,
   never with `&` inside Bash (git/PLAN.md progress log, 2026-09-18).
9. **Foldable layout.** `<pre>` ≤ 45 lines and ≤ 72 columns (Korean counts as 2), captures ≤ 108
   columns, `<li>` ≤ 14 per list, no box-drawing characters in prose, no `①②③` inside monospace.
   Figures are SVG from `deck/gen_figs.py` reading only `data/`, `docs/`-derived tables and `out/`
   (`viewBox` width 340). Render every figure with `rsvg-convert` and **look at it**.
10. **Determinism is evidence.** Every capture in `out/` must be identical across three runs
    (`tools/record.sh --check`, sha256). Experiments run with `GOTOOLCHAIN=local GOFLAGS=-trimpath
    GOPROXY=off` and stdlib-only modules, `LANG=C`, `TZ=UTC`, `HOME=$scratch`,
    fixed `GOCACHE`; the normaliser rewrites the scratch path to `/work`, strips goroutine ids,
    addresses, temp names and **every `ns/op` column** (benchmarks may show `allocs/op` and `B/op`,
    which are deterministic; wall-clock numbers appear nowhere). Binary sizes appear only with the
    caption "이 기계(android/arm64, go1.27.1)" and only as a `TABLE`.
11. **Commit granularity:** one tool, one data batch, one experiment batch, one deck part, one
    figure batch or one review per commit. Korean, no-prefix commit subject (repo convention),
    `Co-Authored-By` trailer as the session reminder says. Never `git push` unless asked.
    `git add` always by path — other sessions may be working in this repository at the same time.
12. **Language:** deck prose in Korean 합니다체; identifiers, file names and Go source comments in
    English inside `ex/` (so captures match what readers see in the wild — but every `ex/` file
    starts with a one-line Korean comment saying which slide it serves and which feature/version);
    this file and subagent briefs in English.
13. **Scope discipline.** This deck is *history + what changed per version*. It is **not** a Go
    tutorial (that is `Go_기초.html`), not Effective Go (`Effective_Go_현대판.html`), not patterns
    (`Go_디자인패턴_슬라이드.html`). A feature slide teaches the feature only as far as needed to show
    *what changed and why*; it links to the sibling decks by name for depth. No slide may
    duplicate a sibling deck's example verbatim.

## 3. What gets written

### 3.1 `tools/fetch_docs.py` + `tools/html_text.py` → `docs/` (step 2)

- Fetch the list in §2 with `urllib` (retry ×3, 20 s timeout, `User-Agent` set, `-L` semantics).
  Write raw html/txt/json under `docs/raw/` and the text conversions next to them. Every file
  gets a line in `docs/FETCHED.txt`: `path | url | date | sha256 | first-heading`.
- `html_text.py`: `html.parser`-based; keeps headings as `§<TAB><heading text>` lines (h1–h4, and
  the release notes' `<dt>`/`<h4 id=…>` package headings), keeps `<pre>` blocks verbatim, drops nav/
  footer. Tests: three fixtures (an excerpt of `go1.22` notes, of the release page, of the
  godebug table) with expected `§` lines and expected paragraph text.
- The release-notes headings are the CITE `sec=` targets. Cite by heading text, not by number
  (the notes are not numbered).

### 3.2 `tools/make_data.py` → the generated tables (step 3)

- `releases.tsv` from `docs/release.txt`: one row per `goX.Y(.Z) (released YYYY-MM-DD)`; kind =
  major (`go1.N` / `go1`) or minor; `relnotes-key = relnotes-1.N`. Test: the fixture yields
  `go1 | 2012-03-28 | major` and a minor row.
- `api_added.tsv` from `docs/api/go1.N.txt`: count lines, count distinct `pkg <path>,` prefixes,
  and list packages that appear for the first time in that file (compare against the union of
  earlier files). Test: two tiny fixtures. This table is the **API growth figure** (§3.5).
- `godebug.tsv` from `docs/godebug.txt`: the settings table (name, "introduced in", default change).
  Test: fixture with three rows.
- `make data-check`: every `features.tsv` row's `version` must exist in `releases.tsv`; its
  `cite-key`/`cite-sec` must resolve (same resolver as `check_claims.py`); for `kind=stdlib` rows
  the named symbol must appear in `docs/api/go1.<version>.txt` (fail with the row on mismatch —
  this is the check that catches "I remembered the wrong version"); `slide-id` must be unique.

### 3.3 `ex/` and `run_all.py` (step 4)

- Every example is a directory with `go.mod` (`module ex/<part>/<slug>`, `go 1.N` — the version
  the slide is about — **no `toolchain` line**) and `main.go` (or `x_test.go`). Stdlib only. Each
  file's first line is a Korean comment: `// 슬라이드 <id> — <feature>, Go 1.N`.
- `tools/gover.py`: `run(dir, cmd, lang=None, godebug=None, goexperiment=None, env=None)` runs
  `cmd` in the deterministic environment of §0.10, optionally rewriting `go.mod`'s `go` line to
  `lang` *in a scratch copy* (never in `ex/`), captures stdout+stderr+exit code, normalises, and
  writes `out/<slug>__<variant>.txt` whose first line is `$ <the exact command line, with GODEBUG=…
  prefixes shown>`. Variants: `go1.21`, `go1.22`, `godebug-x0`, `exp-foo`. Tests: normalisation of
  the scratch path, of a `goroutine 7 [running]` id, of a `0xc000012345` address, of a
  `ns/op` column (masked to `…`), and of `allocs/op` (kept).
- Experiment kinds (each an `exps/<part>.py` module exposing `run(ctx)`):
  1. `go run .` of an example (the feature works in 1.27.1);
  2. `go vet ./...` and `gofmt -l .` on every example — **every** `ex/` directory must pass both,
     checked in `make examples-check` (a formatting-history slide may show `gofmt -d` of a
     deliberately unformatted copy under `scratch/`, generated by the experiment, never committed);
  3. lang-directive pairs: same source, `go 1.N-1` (compile error captured) vs `go 1.N` (runs);
  4. GODEBUG pairs: `GODEBUG=<setting>=<old>` vs default;
  5. GOEXPERIMENT pairs where a 1.27 experiment exists (verify the flag first);
  6. compiler evidence: `go build -gcflags=-m` (escape/inlining), `-gcflags='-d=ssa/check_bce/debug=1'`
     (bounds-check elimination), `go build -o … && ls -l`-style size **tables** (via `os.stat`, not
     `ls`), `go version -m` of a built binary (build info: 1.13+/1.18 vcs stamping — verify);
  7. tests: `go test -v`, `-run`, `-bench . -benchmem` (ns/op masked), `-cover`, `-fuzz` only if a
     deterministic `-fuzztime=1x`-style run exists (else the fuzz slide is CITE + `go test -run`
     of the seed corpus), `-json` excerpt, `testing/synctest`, `t.Context`, `B.Loop` (verify each);
  8. toolchain evidence: `go env`, `go mod init/tidy` (offline: `GOFLAGS=-mod=mod GOPROXY=off` with
     no external requirements), `go work`, `go mod vendor`, `go list -m -json`, `go doc <symbol>`,
     `go fix` (verify what 1.27's `go fix` does before promising modernizers on a slide),
     `go tool` list (the §0.8 fact, shown to the reader), `GOTOOLCHAIN=go1.26.0 go version`'s
     failure (§0.6, shown on the reading-guide slide as the reason the deck works the way it does);
  9. removed-syntax proofs (§0.6 d): `go build` errors on pre-Go 1 forms quoted from the Go 1 notes.
- Order: `exps/ORDER` follows the deck part order; `run_all.py --only <name>` reruns one batch and
  **deletes that batch's old captures first** (git/ lesson: renamed captures left ghosts).
- Budget: ≤ 60 s per experiment, ≤ 15 min total, one `go` process at a time, `GOFLAGS=-p=1`.

### 3.4 `deck/sections/*.html` (step 5) — slide anatomy

- **Part cover** (`card section`): `chnum` = "N부", `h2` = "Go 1.N — <4–6 word Korean title>",
  `chsub` = headline features · release date (from `releases.tsv`, rendered by a
  `<!--TABLE-->`-free inline `<!--REL v=1.22-->` expansion the assembler resolves from the tsv, so
  a date is never typed by hand).
- **Chapter cover** (`chnum` = "N장", **never** a part number — `check_xref` dies): one chapter per
  release inside a multi-release part; one chapter per theme inside parts 1, 2, 10.
- **Release overview slide** (one per release, first in its chapter): a `kv` table
  `날짜 | 언어 | 도구 | 런타임 | 표준 라이브러리 | 플랫폼` filled from `features.tsv` rows of that
  version (generated by `gen_tables.py` → `out/tbl_rel_1.N.html`), plus the API-growth numbers for
  that version from `api_added.tsv`. Every release from 1.0 to 1.27 has one (28 slides); the reader
  can skim the deck by these alone.
- **Feature slide(s)**: title `h3` = feature name (Korean, English in parentheses once), badge
  `<span class="vt v1NN">`, then in order: `why` (1 paragraph, ≤ 3 sentences, with the CITE badge),
  `CODE` (≤ 45 lines), `GOVER`/`OUT` capture, `warn` box with the trap, `note` with "이전엔 이렇게
  했습니다" when a lang/GODEBUG pair exists. Big features (generics, modules, range-over-func, loop
