Go 1.5 – 1.10 — C 를 떠나 지연을 줄이다

Go 로 쓴 컴파일러 · 동시 GC · SSA · context · 타입 별칭 · 빌드 캐시 · ~

이 부에서 할 일

여섯 릴리스 동안 언어는 거의 그대로였습니다. 바뀐 것은 그 아래 — 컴파일러, 런타임, 도구, 표준 라이브러리입니다.

  • 1.5 — 컴파일러·런타임이 Go 로 옮겨 가고, GC 가 동시 수집기가 됩니다.
  • 1.6 — HTTP/2 가 저절로 켜지고, cgo 포인터 규칙이 생깁니다.
  • 1.7 — SSA 백엔드, 표준 라이브러리로 들어온 context, 하위 테스트.
  • 1.8 — SSA 가 모든 아키텍처로, sort.Slice, GOPATH 기본값.
  • 1.9 — 타입 별칭, 단조 시계, math/bits, sync.Map.
  • 1.10 — 빌드 캐시와 테스트 캐시, strings.Builder.
읽는 법 — 이 시대의 기능은 대부분 go.mod 의 go 줄이 막지 않습니다. 그래서 거의 모든 캡처는 "1.27.1 에서의 동작" 이고, 역사는 문서 배지로 댑니다. go 줄로 전과 후를 보일 수 있는 것은 타입 별칭 하나입니다(0부 증거의 네 가지 꼴).

1장

Go 1.5

C 없는 툴체인 · 동시 GC · GOMAXPROCS = 코어 수 · internal · vendor 실험 ·

Go 1.5 한눈에

노트가 스스로 "구현의 구조를 크게 바꾼 릴리스" 라고 부릅니다. 언어 변경은 맵 리터럴 하나뿐이고, 준비 시간을 벌려고 여섯 달 주기에서도 벗어났습니다.

문서 근거

컴파일러와 런타임에서 C 를 걷어내다 1.5

1.4 까지는 저장소 안에 C 컴파일러가 따로 있었고, 그것으로 런타임을 빌드했습니다. C 코드가 고루틴의 스택 관리와 맞물려 돌게 하려면 전용 컴파일러가 필요했기 때문입니다. 1.5 에서 런타임이 Go 로 옮겨 가면서 그 컴파일러도 사라졌습니다.

It is in effect the same program in a different language.

"사실상 같은 프로그램을 다른 언어로 옮긴 것이다." 컴파일러는 새로 짠 것이 아니라 C 코드를 기계로 번역한 것이라, 새 버그가 거의 생기지 않았고 오히려 숨은 버그를 여럿 찾았다고 노트는 적습니다.

예외 — 어셈블러만은 번역이 아니라 Go 로 새로 쓴 프로그램입니다. 상수 계산이 C 가 아니라 Go 의 연산자 우선순위를 따르게 되었습니다.
문서 근거

Go 로 Go 를 빌드한다 — 부트스트랩 1.5

컴파일러가 Go 로 쓰였으니, 배포판을 소스에서 빌드하려면 이미 돌아가는 Go 가 있어야 합니다. 1.4 이후의 배포판(gccgo 포함)이면 됩니다. Go 코어를 고치지 않는 사람에게는 달라지는 것이 없습니다.

대가 — 번역된 코드는 Go 답지 않아 느렸습니다. 노트는 "Builds in Go 1.5 will be slower by a factor of about two", 곧 빌드가 두 배쯤 느려진다고 미리 밝혔습니다.
그 뒤 — 1.7 과 1.8 노트가 연달아 컴파일러·링커가 빨라졌다고 적습니다. 1.8 은 직전 릴리스보다 "about 15% faster" 입니다.
문서 근거

6g·8g 가 go tool compile 하나로 1.5

아키텍처마다 따로 있던 컴파일러(6g, 8g …)·어셈블러(6a, 8a …)·링커(6l, 8l …)가 GOOS·GOARCH 로 대상을 고르는 도구 하나씩으로 합쳐졌습니다. 중간 파일의 .6·.8 같은 확장자도 .o 하나가 되었습니다.

이 go 에 딸린 도구 목록 전체는 0부에 있습니다 — compile·asm·link 가 거기 있습니다.

실행 검증

링커 -X 의 새 꼴 name=value 1.5

빌드할 때 버전 문자열을 넣는 -X 는 인자 둘(-X 경로.이름 값)을 받는 별난 플래그였습니다. 1.5 가 다른 Go 플래그처럼 인자 하나(-X 경로.이름=값)를 받는 꼴을 더했습니다.

없어지기까지 — 옛 꼴은 1.5·1.6 에서 경고와 함께 받아 주다가 1.7 에서 지워졌습니다. 예고하고, 경고하고, 지우는 세 단계입니다.
실행 검증

동시 쓰레기 수집기 1.5

수집기를 다시 설계해, 되도록 사용자 고루틴과 나란히 돌게 했습니다. 목표는 처리량이 아니라 지연 — 사용자에게 응답하는 웹 사이트 같은 프로그램의 멈춤 시간입니다.

The “stop the world” phase of the collector will almost always be under 10 milliseconds and usually much less.

"세상을 멈추는 단계는 거의 언제나 10 밀리초 아래이고, 보통은 훨씬 짧다."

전체 속도 — Go 1 벤치마크 모음은 평균 "a few percent faster" 였지만, 어떤 프로그램은 빨라지고 어떤 프로그램은 느려질 수 있다고 노트는 조심스럽게 적습니다. 멈춤 시간의 뒷이야기는 1.8 장의 GC 이야기에서 이어집니다.
문서 근거

삼색 표시·쓸기, 손잡이는 GOGC 하나 1.5

새 수집기는 동시에 도는 삼색(tri-color) 표시·쓸기 수집기입니다. 사용자 코드가 포인터를 바꾸는 동안에도 "검은 객체가 흰 객체를 가리키지 않는다" 는 불변식을 쓰기 장벽(write barrier)이 지킵니다. 조정 손잡이는 여럿 두지 않고 GOGC 하나만 두었습니다.

블로그의 설명: 기본값 100 은 전체 힙이 직전 수집 뒤 살아 있는 객체의 두 배(100 % 더)까지 자라도록 두고, 200 은 세 배입니다. 1.27.1 에서의 동작입니다.

실행 검증

GOMAXPROCS 의 기본값이 코어 수로 1.5

이전 릴리스에서 동시에 Go 코드를 돌리는 스레드 수의 기본값은 1 이었습니다. 1.5 부터는 CPU 의 코어 수입니다. 여러 코어를 가정하지 않고 짠 프로그램이 깨질 수 있어 노트가 "깨질 수 있는 변경" 으로 경고했습니다.

같은 릴리스의 또 하나 — 고루틴을 스케줄하는 순서도 바뀌었습니다. 언어는 순서를 약속한 적이 없지만, 거기에 기댄 (잘못된) 프로그램이 실제로 깨졌다고 노트는 적습니다.
실행 검증

맵 리터럴 키의 타입 생략 1.5

슬라이스 리터럴은 원소의 타입을 생략할 수 있었는데, 같은 규칙이 맵의 키에는 적용되지 않았습니다. 노트는 이것을 "an oversight" — 빠뜨린 것이라 부르고 1.5 에서 바로잡았습니다.

이 변경은 go 줄로 막히지 않습니다. 그래서 go 1.5 아래로 내려도 오류가 나지 않습니다 — 보일 수 있는 것은 지금의 동작뿐입니다.

몇 릴리스 전에 지웠던 go doc 이 명령 줄에 맞춘 새 모습으로 돌아왔습니다. godoc 보다 짧게, 패키지나 기호 하나만 보여 주고, 대소문자를 가리지 않으며, 내보내지 않은 기호도 보여 줄 수 있습니다.

strings.Compare 는 bytes 패키지와 짝을 맞추려고 넣었을 뿐 "otherwise unnecessary" 라고 노트가 적습니다.

실행 검증

math/big.Float — 임의 정밀도 실수 1.5

가수의 비트 수(정밀도)를 고를 수 있는 부동소수점 수입니다. 정밀도를 24(53) 비트로 두면 float32(float64) 범위 안의 연산은 IEEE-754 연산과 같은 결과를 냅니다. 1.5 컴파일러의 상수 계산도 자체 구현 대신 math/big 을 쓰게 되었습니다.

실행 검증

flag 사용법 메시지와 `N` 표기 1.5

PrintDefaults 의 모양이 사람이 읽기 좋게 바뀌었습니다. 설명 속 역따옴표로 감싼 낱말은 플래그 인자의 이름이 되고, 기본값은 타입의 영값이 아닐 때만 보입니다.

실행 검증

cgo 없는 Go DNS 해석기 1.5

대부분의 유닉스에서 DNS 조회에 cgo 가 더는 필요 없어졌습니다. 조회 하나가 스레드가 아니라 고루틴 하나를 차지하므로, 동시에 여러 조회를 하는 프로그램이 OS 자원을 덜 씁니다. 어느 해석기를 쓸지는 빌드가 아니라 실행 때 정하고, GODEBUG=netdns 로 고를 수 있습니다.

이 덱의 실험은 cgo 를 끄고 돌리므로(CGO_ENABLED=0) 언제나 Go 해석기입니다. netdns 설정은 없앨 계획이 없다고 GODEBUG 문서가 적습니다.

Go 1.5 퀴즈

Q. 1.5 에서 GOMAXPROCS 의 기본값을 바꾼 것이 왜 "깨질 수 있는 변경" 이었을까요? 그리고 같은 릴리스의 어떤 변경이 비슷한 위험을 지녔나요?

A. 기본값이 1 이던 시절에는 고루틴이 한 스레드에서 번갈아 돌았으므로, 동기화 없이 짠 프로그램이 우연히 맞게 돌 수 있었습니다. 코어 수만큼 동시에 돌면 그 우연이 사라집니다. 같은 릴리스에서 고루틴의 스케줄 순서가 바뀐 것도 같은 종류입니다 — 언어가 약속한 적 없는 순서에 기댄 프로그램이 깨졌습니다.

Go 1.6

투명한 HTTP/2 · cgo 포인터 규칙 · 맵 오용 감지 · 템플릿 block ·

Go 1.6 한눈에

언어 명세는 한 글자도 바뀌지 않았습니다. 새 포트, 강제되는 cgo 포인터 규칙, 저절로 켜지는 HTTP/2, 템플릿 재사용 — 바뀐 것은 전부 구현과 라이브러리입니다.

문서 근거

투명한 HTTP/2 1.6

HTTPS 를 쓰는 net/http 의 클라이언트와 서버가 알아서 HTTP/2 를 씁니다. HTTP/1.1 전용 API 가 따로 없듯이 HTTP/2 전용 API 도 내보내지 않았습니다.

끄는 법 둘 — 코드로는 Transport.TLSNextProto(서버는 Server.TLSNextProto)에 nil 이 아닌 빈 맵을 넣습니다. 설정으로는 http2client·http2server 이고, 없앨 계획이 없다고 GODEBUG 문서가 적습니다.
실행 검증

cgo 포인터 공유 규칙 1.6

C 코드가 Go 의 쓰레기 수집기와 함께 살 수 있도록 규칙을 정하고, 런타임이 실행 중에 검사하게 했습니다. 어기면 진단을 찍고 프로그램을 멈춥니다.

  • Go 가 할당한 메모리의 포인터를 cgo 호출 인자로 C 에 넘길 수 있다.
  • 단, 그 메모리 안에 Go 메모리를 가리키는 포인터가 없어야 한다.
  • 그리고 C 는 호출이 끝난 뒤 그 포인터를 붙들고 있으면 안 된다.
검사를 끄지 말 것 — GODEBUG=cgocheck=0 으로 끌 수 있지만, 걸리는 코드 대부분은 어떤 식으로든 GC 와 미묘하게 어긋나 있고, 끄면 "더 알 수 없는 실패" 로 바뀔 뿐이라고 노트는 적습니다.

이 기계에서는 cgo 를 쓸 수 없어 실행 예제가 없습니다(0부).

문서 근거

맵 동시 오용 감지 1.6

한 고루틴이 맵에 쓰는 동안 다른 고루틴이 그 맵을 읽거나 쓰면 안 됩니다. 1.6 런타임은 이것을 가볍게, 최선을 다해(best-effort) 잡아내고 프로그램을 멈춥니다.

최선을 다할 뿐 — 감지는 보장이 아닙니다. 더 확실하게 잡으려면 경쟁 검출기를 쓰라고 노트가 권합니다(이 기계에서는 돌지 않습니다). 1.8 은 "쓰면서 순회" 도 잡도록 넓혔습니다.
실행 검증

패닉은 현재 고루틴만 찍는다 1.6

프로그램을 끝내는 패닉에서 런타임이 이제 기본으로 달리던 고루틴 하나의 스택만 찍습니다. 대개 그 고루틴만 관계있으니, 나머지를 빼면 충돌 메시지의 잡음이 크게 줍니다.

고칠 곳 — 시간 초과나 신호를 받고 일부러 패닉해 "전체 상태" 를 남기던 코드는 패닉 전에 debug.SetTraceback("all") 을 부르라고 노트가 적습니다.

타입 별칭 type T1 = T2 1.9

type T1 = T2 는 T2 가 가리키는 타입에 T1 이라는 다른 철자를 붙입니다. 둘은 같은 타입입니다. = 가 없는 type T1 T2 는 새롭고 다른 타입을 만듭니다.

이 부의 유일한 전과 후 — 지금의 컴파일러가 go 줄로 막는 이 시대의 언어 기능은 타입 별칭 하나입니다. 그래서 "1.9 에서 생겼다" 를 컴파일러의 거절 메시지로 보일 수 있습니다. %T 가 두 변수 모두 main.Celsius 라고 답하는 것도 보세요 — 별칭은 이름일 뿐 타입이 아닙니다.

별칭으로 점진적 이사

타입을 옛 패키지에서 새 패키지로 옮기고, 옛 자리에는 별칭 한 줄을 남깁니다. 아직 옮기지 않은 클라이언트는 그대로 컴파일되고, 옮긴 클라이언트와 값을 주고받을 수 있습니다.

표준 라이브러리 밖의 첫 큰 쓰임이 golang.org/x/net/context 였습니다. 그 패키지의 "forwarding aliases" 덕분에 1.9 부터 옛 경로가 표준 context 와 완전히 같아졌다고 1.10 노트가 적습니다.

경과 시간을 재려고 두 번의 time.Now() 를 빼면, 윤초 때 OS 가 시계를 1초 되돌리는 순간 10 밀리초짜리 일이 "negative 990 milliseconds" 로 재어질 수 있습니다. Go 1 의 시간 API 는 벽시계만 드러냈습니다.
