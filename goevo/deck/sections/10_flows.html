2장 퀴즈


Q. 네 갈래 가운데 이 기계에 옛 툴체인이 없어도 전과 후를 컴파일러 메시지로 보일 수 있는 갈래는 무엇이고, 왜입니까?



A. 언어입니다. 1.12 부터 go.mod 의 go 줄이 언어 버전이어서, 지금 컴파일러가 go 줄을 낮춘 소스를 새 문법 때문에 거절합니다.
런타임·표준 라이브러리의 옛 동작은 GODEBUG 가 남겨 둔 것만 되살릴 수 있습니다.

go.mod 사다리


go 줄 하나가 허락하는 문법 — go 1.27.1 로 전부 돌려 본 결과





go 줄의 뜻은 세 번 자랐다


    

  • 1.12 — go 줄이 언어 버전이 됩니다. 그 버전보다 새 문법은 컴파일러가 거절합니다(5부).
    • 

  • 1.21 — go 줄이 최소 요구 버전이 되고, 모자라면 go 명령이 툴체인을 받습니다(7부).
같은 판에서 go 줄이 GODEBUG 기본값도 정하게 됩니다(7부).
    • 

  • 1.22 — 문법이 아니라 의미가 go 줄을 따르는 첫 변화, 반복별 루프 변수가 옵니다(7부).
    • 



이 장은 첫째 뜻만 봅니다. 설치된 go 의 타입 검사기(types2)가 버전을 묻는 자리를 모두 찾아, 기능마다 "막는 판에서 통과, 한 판
아래에서 거절" 을 실제로 돌렸습니다.

사다리가 노트와 어긋나는 두 곳


    

  • 제네릭 타입 별칭 — 노트는 1.24 에서 완전히 지원한다고 적지만(7부), 컴파일러의 판 검사는
go1.23 을 요구합니다. 1.23 에서는 실험(GOEXPERIMENT)으로만 켜졌으니, go 1.23 모듈이 1.27.1 에서 컴파일되는 것은
"지금 컴파일러는 이 문법을 1.23 문법으로 본다" 는 뜻일 뿐입니다.
    • 

  • 겹치는 인터페이스 메서드 — 1.13 에서의 거절 메시지는 "requires go1.14" 가 아니라 옛 규칙 그대로의
duplicate method Close 입니다. 컴파일러가 판을 물은 뒤 옛 규칙으로 검사하기 때문입니다.
    • 



둘 다 표의 "필요한 go 줄" 은 노트가 아니라 컴파일러가 실제로 한 일입니다.

문서 근거






go 줄을 올릴 때 달라지는 것


go 줄을 올리는 일은 문법을 여는 것만이 아닙니다. 같은 소스라도 다음 셋이 함께 움직입니다.


    

  • 새 문법이 허락됩니다 — 이 장의 사다리.
    • 

  • 의미가 바뀔 수 있습니다 — 1.22 를 넘으면 루프 변수가 반복마다 새로 생깁니다(7부).
    • 

  • GODEBUG 기본값이 그 판의 것으로 바뀝니다(0부, 7부).
지킬 옛 동작이 있으면 go.mod 의 godebug 줄로 고정합니다(7부).
    • 



함정 — GODEBUG 기본값은 작업 모듈의 go.mod(작업 공간이면 go.work)가 정합니다. 의존 모듈의 godebug
줄은 무시됩니다. 또 1.20 보다 옛 go 줄은 1.20 으로 맞춰지고, 보안 릴리스로 생긴 설정은 판과 상관없이 새 동작입니다.

3장 퀴즈


Q. go.mod 에 go 1.21 이라고 적힌 모듈에서 for i := range 10 을 쓰면 어떻게 됩니까? 고치는 방법은?



A. 컴파일러가 "requires go1.22 or later (-lang was set to go1.21; check go.mod)" 로 거절합니다. go 줄을 1.22 이상으로
올리면 됩니다 — 다만 그러면 루프 변수의 의미와 GODEBUG 기본값도 함께 1.22 의 것이 됩니다.

코드 현대화 갤러리


같은 일, 다섯 시대의 문체, 같은 출력





한 문장에서 가장 많이 나온 낱말 셋


문장 하나의 낱말을 세어, 많이 나온 순서로(같으면 가나다 — 여기서는 알파벳 — 순서로) 셋을 찍습니다. 이 작은 일을 Go 1, 1.8,
1.18, 1.21–1.22, 1.23 의 도구만으로 다섯 번 씁니다. 판마다 go.mod 의 go 줄을 그 판으로 두었으니, 각 파일은 그 판의 문법만 씁니다.


    

  • 다섯 프로그램은 모두 이 기계의 go 1.27.1 로 돌렸고, 출력이 한 글자도 다르지 않은지 실험이 확인합니다(다르면 빌드가 멈춥니다).
    • 

  • map 을 도는 차례는 정해져 있지 않습니다(2부). 그래서 다섯 문체 모두 정렬로 차례를 고정합니다.
    •

지금의 go fix 는 무엇을 권하나


1.26 의 go fix 는 modernizer 의 집이 되었습니다. go vet 과 같은 분석 틀 위에서, 코드를 최신 관용구와 표준 라이브러리
API 로 옮기는 고침을 제안합니다.  Go 1 문체의 파일을 go 줄만 1.27 로 올린 사본에
go fix -diff 를 돌렸습니다.

않았습니다 — 갤러리의 나머지 걸음은 여전히 사람이 고를 문체입니다(2026-09 기준, go 1.27.1).

4장 퀴즈


Q. Go 1 문체 파일은 go 줄을 1.27 로 올려도 그대로 컴파일되고 같은 결과를 냅니다. 이것은 무엇 덕분이고, 이 파일에서 무엇이 달라질 수 있었습니까?



A. Go 1 호환성 약속 덕분입니다. 이 파일에는 go 줄을 따라 의미가 바뀌는 곳 — 예컨대 클로저가 붙잡는 루프 변수 — 이 없어서
출력이 같습니다. 달라진 것은 go fix 가 FieldsSeq 를 권한다는 것뿐입니다.

설명용

호환성 약속 — 비용과 이득


Go 1 문서의 한 문장이 열네 해 동안 한 일





약속의 문장


It is intended that programs written to the Go 1 specification will continue to compile and run correctly,
unchanged, over the lifetime of that specification.


"Go 1 명세대로 쓴 프로그램은 그 명세가 살아 있는 동안 고치지 않고도 계속 컴파일되고 올바르게 돌 것을 의도합니다."



약속의 범위와 예외는 2부에서 읽었습니다. 이 장은 그 뒤를 봅니다 — 약속을 지키는 데 무엇이 들었는지.
4장의 Go 1 문체 파일이 go 1.27.1 에서 그대로 돈 것이 이득의 가장 짧은 증거입니다.

문서 근거






예외 조항이 실제로 쓰인 일 — 이름 없는 구조체 리터럴


2023년 호환성 글이 드는 예입니다. Go 1 에서 net.TCPAddr 는 필드가 둘(IP·Port)이었는데, 1.1 이 Zone 을 더하자 값만 나열한
리터럴이 컴파일되지 않았습니다. 호환성 문서는 이 경우를 미리 예외로 적어 두었고, 이름을 붙인 리터럴을 쓰라고 권합니다.
 




글이 옮긴 1.1 의 메시지는 "too few initializers in struct literal" 이었고, 지금은 위처럼 적습니다.

실행 검증






그래서 go vet 이 이름 없는 리터럴을 짚는다





규칙 — 다른 패키지의 구조체는 이름을 붙여 적습니다. 새 필드는 영값을 받으므로, 표준 라이브러리가 필드를 더해도 깨지지
않습니다. 

실행 검증






빼지 못하는 API — API 파일과 시험


호환성 글은 첫째 수단으로 API 검사를 듭니다. 패키지마다 공개 API 를 따로 적은 파일을 두고, 표준 시험이 실제 API 와 그 파일을
견줍니다. 새 API 를 더하면서 파일에 적지 않아도, 있던 API 를 바꾸거나 지워도 시험이 깨집니다.



이 덱이 쓰는 api/go1.N.txt 가 바로 그 파일입니다. 호환성을 지키려고 만든 장치가, 거꾸로 "무엇이 언제 생겼나" 의 가장
믿을 만한 기록이 되었습니다(부록). 둘째 수단은 시험입니다 — 다음 판의 개발 버전을 구글 안의 모든 Go 코드의
시험에 돌려 보고, 깨지면 되돌리거나 고쳐 씁니다. 

문서 근거






비용의 장부 — 판마다 늘어난 GODEBUG



"호환되지만 누군가는 깨지는" 변화마다 옛 동작으로 돌아갈 스위치를 하나씩 남깁니다. 1.21 부터의 규칙으로는 최소 두 해(네 판)
유지합니다.  기한이 지난 스위치는 지워집니다 — 1.27.1 에 지워진
설정을 주면 프로그램이 시작하자마자 멈춥니다(7부).

실행 검증






약속이 치른 값, 얻은 것


    

  • 치른 값 — 실수한 API 도 지우지 못하고 "쓰지 마십시오" 라고만 적습니다(io/ioutil).
    • 

  • 치른 값 — 새 문법과 의미는 go 줄 뒤로 숨어야 하고, 동작 변화마다 GODEBUG 스위치를 두 해 넘게 들고 다닙니다.
    • 

  • 치른 값 — 큰 변경은 느립니다. 제네릭은 1.18 에야 들어왔습니다(6부).
    • 

  • 얻은 것 — 옛 코드가 새 툴체인에서 돕니다. 툴체인을 올리는 일이 "지루한" 일이 되었습니다.
    • 

  • 얻은 것 — 새 툴체인이 옛 판의 가장 좋은 구현이 됩니다. go 줄을 옛 판에 두면 옛 동작을 지킨 채 새 컴파일러·런타임의 개선을 받습니다.

    • 


문서 근거






"가장 중요한 설계 결정"


In fact, we believe that prioritizing compatibility was the most important design decision we made for Go 1.


"사실 우리는 호환성을 앞세운 것이 Go 1 에서 내린 가장 중요한 설계 결정이었다고 믿습니다."



같은 글이 Go 1 을 깨는 Go 2 는 결코 없다고 답한 것은 9부에서 보았습니다. 이 덱의 방법 — 옛 툴체인 없이 지금
컴파일러 하나로 열네 해를 되짚는 것 — 자체가 그 결정 위에서만 가능했습니다.

문서 근거






5장 퀴즈


Q. 표준 라이브러리의 구조체에 새 필드가 생겨도 여러분의 코드가 깨지지 않게 하려면 리터럴을 어떻게 써야 하고, 무엇이 그것을 검사해 줍니까?



A. net.TCPAddr{IP: …, Port: 80} 처럼 필드 이름을 붙여 씁니다. 빠진 필드는 영값이 됩니다. go vet 의
composites 검사가 이름 없는 리터럴을 "uses unkeyed fields" 로 짚습니다.
