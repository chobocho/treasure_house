Go 1.21 – 1.24 — 호환성을 제도로, 반복을 언어로

min·max·clear·slog·slices·툴체인 관리 · 반복별 루프 변수·정수 range·rand/v2 · 함수 range 반복자·unique·타이머 · 제네릭 별칭·Swiss Table map·os.Root·weak

이 부에서 할 일

이 네 릴리스의 줄기는 둘입니다. 하나는 호환성입니다 — 1.21 이 GODEBUG 와 go 줄을 제도로 만들어, "새 툴체인은 옛 Go 의 가장 좋은 구현" 이 되게 했습니다. 다른 하나는 반복입니다 — 루프 변수의 의미가 바뀌고(1.22), 함수를 range 할 수 있게 됩니다(1.23).

  • 1.21 — min·max·clear, 더 똑똑한 추론, log/slog·slices·maps·cmp, PGO 정식판, go 줄 = 최소 요구, toolchain 줄
  • 1.22 — 루프 변수가 반복마다 새로, range 10, math/rand/v2, ServeMux 의 메서드·와일드카드
  • 1.23 — 함수 range 와 iter 패키지, unique, 버퍼 없는 타이머 채널, 텔레메트리, go.mod 의 godebug
  • 1.24 — 제네릭 타입 별칭, Swiss Table map, weak·AddCleanup, os.Root, b.Loop, tool 지시문, 암호 패키지들
  • 언어 변화는 모두 go.mod 의 go 줄로 갈립니다. 루프 변수는 컴파일 오류가 아니라 출력이 달라지는 것이 증거입니다.
  • GODEBUG 설정도 수명이 있습니다. 1.27 에서 지워진 설정에 옛 값을 주면 프로그램이 시작하자마자 멈춥니다 — 그 캡처도 봅니다.
  • range 3 의 기본 짝과 panic(nil) 의 세 가지 실행은 0부·0부에 있습니다. 여기서는 그 너머를 봅니다.

내장 함수 min·max 1.21

왜 — 1.21 은 언어에 내장 함수 셋을 더했습니다. min·max 는 정해진 개수의 인자 가운데 가장 작은(큰) 값을 구합니다. 순서 있는 타입이면 정수·실수·문자열 모두 됩니다.

함정 — 실수 인자에 NaN 이 하나라도 있으면 결과는 NaN 입니다. sort 식의 "NaN 은 맨 앞" 이 아닙니다. 그리고 min(0.0, -0.0) 은 음의 0 입니다. 캡처의 다섯째·여섯째 줄이 그것입니다.
이전엔 — 정수는 손으로 if 문을 쓰고, 실수는 math.Min·math.Max(float64 둘만) 를 썼습니다.

내장 함수 clear 1.21

왜 — clear 는 map 의 원소를 모두 지우고, 슬라이스의 원소는 모두 0 값으로 만듭니다. map 을 비우는 흔한 관용구 — 키를 돌며 delete — 로는 지울 수 없는 키가 있습니다. NaN 은 자기 자신과도 같지 않아서, NaN 키는 delete 로 찾을 수 없습니다.

함정 — 슬라이스의 clear 는 길이를 0 으로 줄이지 않습니다. 원소를 0 값으로 덮을 뿐입니다. 길이를 줄이려면 여전히 s = s[:0] 입니다. 같은 일을 하는 reflect.Value.Clear 도 함께 들어왔습니다 (작은 변화들).

패키지 초기화 순서를 명세로 1.21

왜 — 1.21 전의 명세는 서로 import 관계가 없는 패키지들의 초기화 순서를 정확히 정하지 않았습니다. 새 규칙은 이렇습니다 — 모든 패키지를 import 경로로 정렬하고, 그 목록에서 import 한 것이 모두 초기화된 첫 패키지를 초기화해 목록에서 빼기를 반복합니다. 노트는 명시적인 import 로 표현하지 않은 순서에 기댄 프로그램은 동작이 바뀔 수 있다고 경고합니다.

정렬하면 alpha → mid → zeta 이지만, mid 는 zeta 가 끝나야 하므로 zeta 가 먼저입니다. main.go 에서 zeta 를 먼저 import 한 것은 순서에 아무 영향도 없습니다. 이 규칙은 go 줄로 갈리지 않습니다.

루프 변수 변경의 미리보기 — GOEXPERIMENT=loopvar 1.21

왜 — 1.21 은 "앞으로의 Go 에서 고려하는 언어 변경" 의 미리보기를 담았습니다. for 루프 변수를 루프당 하나가 아니라 반복마다 하나로 만드는 것입니다. 발표 글에 따르면 GOEXPERIMENT=loopvar 로 빌드하면 go 줄과 상관없이 모든 루프에 새 의미가 적용됩니다.

panic(nil) 과 recover 의 보장 1.21

왜 — 1.21 은 "고루틴이 패닉 중이고 recover 를 defer 된 함수가 직접 불렀다면 recover 의 결과는 nil 이 아니다" 를 보장하기로 했습니다. 그러려면 panic(nil) 이 문제입니다. 그래서 nil 로 패닉하면 런타임이 *runtime.PanicNilError 로 바꿔 패닉합니다. 옛 동작은 GODEBUG=panicnil=1 이고, main 패키지의 모듈이 go 1.20 이하를 선언하면 자동으로 켜집니다.

세 가지 실행(go 1.21 · go 1.20 · 설정)은 0부에서 보았습니다. 이 장의 나머지 세 장은 그 뒤의 장치 — go 줄이 GODEBUG 기본값을 정한다, 소스에 //go:debug 로 적는다, go 줄은 최소 요구다 — 를 봅니다.

한 줄 요약 — "recover() != nil 이면 패닉 중이다" 가 1.21 부터 참입니다(go 1.21 이상의 모듈에서).

호환성은 왜 GODEBUG 를 필요로 했나

Russ Cox 는 1.21 의 호환성 글에서 Go 1 약속을 지키고도 프로그램이 깨진 사례를 세 갈래로 나눴습니다.

갈래글이 든 예
출력 변화1.6 에서 sort 가 약 10% 빨라지며 같은 값의 순서가 바뀌었다. 1.8 의 compress/flate 는 더 작은 출력을 내 재현 가능한 압축본이 깨졌다
입력 변화1.17 의 net.ParseIP 가 앞자리 0 을 거절하기로 했다(C 는 8진수로 읽는다)
프로토콜 변화1.6 의 HTTP/2 자동 사용. 끄는 법으로 GODEBUG=http2client=0 을 문서화했다

1.21 은 마지막의 GODEBUG 를 모든 "허용되지만 깨질 수 있는" 변화의 표준으로 넓혔습니다 — 설정마다 옛 동작을 켜는 스위치를 두고, 최소 2년(네 릴리스) 유지하고, 기본값은 main 패키지의 go.mod go 줄을 따릅니다.

역사 근거

go 줄이 GODEBUG 기본값을 정한다 1.21

왜 — 새 툴체인으로 올려도 go 줄을 옛 버전에 두면 옛 툴체인의 동작이 보존됩니다. 노트의 말로는 "최신 Go 툴체인은 언제나 옛 버전 Go 의 가장 좋고 가장 안전한 구현" 이어야 하기 때문입니다. 빌드된 실행 파일은 그 기본값을 DefaultGODEBUG 라는 빌드 설정으로 품고 있어, 프로그램이 스스로 읽을 수 있습니다.

목록에는 툴체인 기본값과 다른 것만 나옵니다. go 1.20 이하는 모두 go 1.20 과 같게 맞춥니다 — 이 방식 자체가 1.21 에서 생겼기 때문입니다.

소스에 적는 //go:debug 1.21

왜 — go 줄보다 세밀하게, main 패키지의 소스 파일 맨 위(package 문 앞)에 //go:debug 설정=값 을 적으면 그 프로그램의 기본값이 바뀝니다. 1.21 부터 모르는 설정을 적은 //go:debug 는 잘못된 프로그램이고, 같은 설정을 두 번 적어도 잘못입니다.

go 줄은 엄격한 최소 요구 버전 1.21

왜 — 전에는 go 줄이 "거의 강제되지 않는 제안" 이었습니다. 발표 글의 예처럼 go 1.18 을 선언한 제네릭 코드를 1.17 이 컴파일하면, 진짜 문제(버전) 대신 엉뚱한 문법 오류가 먼저 나왔습니다. 1.21 부터 go 줄은 규칙이고, 점 릴리스까지 적을 수 있습니다.

번호 매기기 — 1.21 부터 첫 릴리스는 1.N.0 이고, "Go 1.21" 은 언어 버전과 릴리스 가족을 뜻합니다. 그래서 go 줄에 적는 1.21 과 1.21.0 은 다른 말입니다. 아직 나오지 않은 1.28 을 요구하는 go.mod 는 9부에서 봅니다.

toolchain 줄과 GOTOOLCHAIN — go 명령이 Go 를 받는다 1.21

왜 — go 줄을 강제하면 "Go 가 너무 옛것이라 못 빌드한다" 는 좌절이 늘어납니다. 그래서 1.21 의 go 명령은 필요한 툴체인을 모듈처럼 받아 모듈 캐시에서 실행합니다. 새 toolchain 줄은 이 모듈에서 일할 때 쓸 "권장 최소 툴체인" 이고, 다른 모듈에 요구를 걸지 않습니다. 둘 다 go get 으로 바꿉니다.

이 기계에서는 — 안드로이드 arm64 용 툴체인이 없어서 자동 받기는 늘 실패합니다. 그래서 이 덱의 실험은 GOTOOLCHAIN=local 로 돕니다(0부). GOTOOLCHAIN=go1.21.1+auto 처럼 "이 판을 기본으로, 더 새것은 허용" 도 적을 수 있습니다.

v2 는 어떻게 만드나 — 발표 글의 세 원칙

Russ Cox 는 math/rand/v2 가 앞으로의 모든 표준 라이브러리 v2 의 본보기라며 세 원칙을 적었습니다.

  • 새 판은 그/패키지/v2 라는 import 경로를 쓴다 — 바깥 모듈의 의미 있는 import 버전과 같다. 옛 판과 새 판이 한 프로그램에 함께 있을 수 있어야 차츰 옮길 수 있다.
  • 기존의 쓰임과 사용자를 존중한다 — 기존 패키지에서 출발해, 옮기는 비용을 정당화할 만한 변경만 한다.
  • v2 는 v1 사용자를 두고 가지 않는다 — 이상적으로는 v1 이 v2 위의 얇은 껍질이 된다. math/rand 에서는 자동 씨앗을 받는 v1 함수가 v2 의 생성기를 부르게 했다.

글은 v2 패키지가 쏟아지지는 않을 것이며 한 번에 하나씩, 다음 10년을 버틸 품질로 다루겠다고 했습니다. 그다음 v2 후보인 encoding/json/v2 는 1.25 의 실험입니다(8부).

루프 몸체의 defer 는 어디서 도나

함수 range 의 몸체는 컴파일러가 만든 함수 안에서 돌지만(앞 장 스택의 main.main-range1), 그 안의 defer 는 yield 가 돌아올 때가 아니라 바깥 함수가 끝날 때 돕니다. defer 는 "둘러싼 함수" 가 돌아갈 때 돈다는 규칙이 몸체를 쓴 함수 기준으로 지켜지는 것입니다.

Swiss Table 로 다시 만든 map 1.24

왜 — 런타임의 여러 개선으로 대표 벤치마크 모음의 CPU 부담이 평균 2–3% 줄었고, 그 하나가 Swiss Table 기반의 새 내장 map 입니다. Michael Pratt 의 글에 따르면 Swiss Table 은 2017년 Google 의 C++ 설계로, 슬롯 8개를 한 묶음(group)으로 두고 묶음마다 64비트 제어 워드에 슬롯별 해시의 아래 7비트를 담아 여덟 슬롯을 한 번에 비교합니다.

Go 에서는 두 가지가 까다로웠습니다. 큰 map 이 한 번에 두 배로 자라면 꼬리 지연이 커지므로, map 을 최대 1024 항목짜리 표 여러 개로 나눠 표 하나씩 자라게 했습니다. 그리고 명세가 순회 중 수정을 허용하므로 그 의미를 지켜야 했습니다.

글의 숫자로는 마이크로벤치마크에서 map 연산이 1.23 보다 최대 60% 빠르고, 전체 애플리케이션 벤치마크의 기하평균 CPU 시간은 약 1.5% 나아졌습니다. 일부 경우는 오히려 느려졌다고 밝혔습니다. 이 덱은 속도를 재지 않습니다.

왜 — 1.24 는 FIPS 140-3 준수를 돕는 장치를 표준 라이브러리에 넣었습니다. 승인된 알고리즘은 Go Cryptographic Module 이라는 내부 패키지들이 투명하게 구현하므로 애플리케이션은 바꿀 것이 없습니다. 빌드 때는 GOFIPS140 이 모듈 판을 고르고, 실행 때는 GODEBUG fips140 이 모드를 켭니다.

math/rand.Seed 는 아무 일도 하지 않는다 1.24

go:wasmexport — Go 함수를 WebAssembly 로 내보내기 1.24

왜 — 1.21 의 go:wasmimport 가 호스트 함수를 들여왔다면, 1.24 의 go:wasmexport 는 Go 함수를 호스트에 내보냅니다. wasip1 에서는 -buildmode=c-shared 로 프로그램이 아니라 "리액터"(라이브러리)를 만들 수 있습니다. Cherry Mui 의 글은 이 둘이 Go 함수를 Wasm 으로 내보내 Wasm 호스트와 더 잘 통합하게 한다고 소개합니다.
