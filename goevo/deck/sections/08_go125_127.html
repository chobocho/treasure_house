Go 1.25 – 1.27 — 가장 최근의 세 릴리스

컨테이너를 아는 GOMAXPROCS·synctest 정식판·실험 GC 와 json/v2 · · · 2026-09 기준, 받아 둔 문서와 이 기계의 go 1.27.1 로만 씁니다

이 부에서 할 일

이 부의 세 릴리스는 이 덱을 쓰는 모델이 배운 자료의 가장자리이거나 그 너머에 있습니다. 그래서 기억은 쓰지 않습니다. 모든 문장은 받아 둔 릴리스 노트·API 목록·블로그 글에서 오고, 돌릴 수 있는 것은 모두 이 기계의 go 1.27.1 로 돌려 캡처합니다.

  • 1장 — Go 1.25. 언어 변화가 없는 릴리스입니다. 대신 런타임·도구·표준 라이브러리가 크게 움직였습니다.
  • 2장 — Go 1.26: new(식), Green Tea GC 가 기본값, go fix 의 modernizer. 3장 — Go 1.27: 제네릭 메서드, encoding/json/v2, crypto/mldsa, uuid. 1.25 에서 실험으로 들어온 것들이 어떻게 되었는지는 그 장들에서 이어 봅니다.
  • 언어 변화가 없으면 go 줄 관문(0부)으로 전과 후를 가를 수 없습니다. 1장은 GODEBUG 와 GOEXPERIMENT 짝, 그리고 go 줄이 정하는 GODEBUG 기본값으로 전과 후를 보입니다.
  • 이 기계에서 보일 수 없는 것(경쟁 탐지기·cgo·다른 OS 의 실행·네트워크)은 노트를 인용하는 데서 멈춥니다.
  • "지금은 이렇다" 는 문장은 모두 2026-09 기준입니다.

Go 1.25 한눈에

노트의 첫 문단은 변화 대부분이 툴체인·런타임·라이브러리의 구현에 있다고 말합니다. 발표 글은 실험 단계의 두 가지 — 새 GC 와 encoding/json/v2 — 를 직접 켜서 시험해 달라고 부탁했습니다.

문서 근거

명세에서 core type 을 지우다 1.25

왜 — 1.25 의 언어 변화는 명세의 문장뿐입니다. 제네릭과 함께 들어온 "core type" 개념을 지우고, 필요한 곳마다 따로 쓴 문장으로 바꿨습니다. 프로그램에 영향은 없습니다. Robert Griesemer 의 글은 이유를 셋 듭니다 — 제네릭이 아닌 코드를 이해할 때도 core type 을 배워야 했고, 규칙이 지나치게 좁았고, 여러 규칙이 예외처럼 보였습니다.

글에 따르면 컴파일러 오류도 더는 "core type" 을 말하지 않고, 타입 집합의 어느 타입이 문제인지 짚도록 고쳤습니다. close 의 명세도 1.18 전의 첫 문장으로 돌아갔고, 제네릭 피연산자를 위한 문단이 뒤에 따로 붙었습니다.

실행 검증

GOMAXPROCS 와 컨테이너의 CPU 제한

GOMAXPROCS 는 고루틴을 동시에 돌릴 스레드의 최대 수입니다. 1.5 부터 1.24 까지 기본값은 기계의 논리 CPU 수였습니다(4부).

Kubernetes 의 CPU 제한은 리눅스 cgroup 의 CPU 대역폭 제한이 됩니다. Go 는 그 제한을 몰라서, 제한보다 많은 CPU 를 쓰려다 커널에 스로틀링을 당했습니다. 스로틀링은 그 주기(보통 100ms)의 남은 시간 동안 프로그램을 통째로 멈추므로 꼬리 지연에 크게 나쁩니다.

모형의 차이 — GOMAXPROCS 는 병렬도의 한계이고, CPU 제한은 처리량의 한계입니다. "CPU 8개" 제한은 100ms 마다 CPU 시간 800ms 이므로, 16개 스레드가 50ms 씩 돌아도 채울 수 있습니다. 제한은 2.5 처럼 소수일 수 있는데, Go 는 늘 올림합니다.

글은 Uber 의 go.uber.org/automaxprocs 가 오래 비슷한 동작을 제공해 왔다고 감사를 적었습니다.

역사 근거

컨테이너를 아는 GOMAXPROCS 1.25

왜 — 1.25 부터 리눅스에서는 cgroup 의 CPU 대역폭 제한이 논리 CPU 수보다 작으면 그것이 기본값이 됩니다. 그리고 모든 OS 에서 CPU 수나 제한이 바뀌면 런타임이 주기적으로 GOMAXPROCS 를 고칩니다. 환경 변수나 runtime.GOMAXPROCS 로 손수 정하면 둘 다 꺼지고, 새 runtime.SetDefaultGOMAXPROCS 는 다시 기본값으로 돌립니다.

이 기계에서는 — Termux 의 proot 안에서는 cgroup 을 읽을 권한이 없어, 제한이 걸린 컨테이너의 동작은 보이지 못했습니다. 노트는 CPU 요청(request)은 보지 않는다고 적었고, 제한 파일을 다시 읽으려고 cgroup 파일의 서술자를 프로세스가 끝날 때까지 열어 둔다고 합니다.
실행 검증

1.25 가 더한 GODEBUG 다섯 — go 줄이 기본값을 정한다

새 기본 동작은 모두 GODEBUG 로 끌 수 있고, 그 기본값은 main 모듈의 go 줄을 따릅니다(7부). 그래서 go list 로 이 패키지에 적용될 기본 설정을 물으면 go 줄 하나로 차이가 드러납니다.

1.24 줄에서 더 붙은 것뜻
containermaxprocs=0 · updatemaxprocs=0cgroup 제한을 보지 않고, 주기적으로 고치지도 않는다
decoratemappings=0익명 메모리 영역에 이름을 붙이지 않는다(뒤 장)
tlssha1=1 · x509sha256skid=0TLS 1.2 의 SHA-1 서명 허용, 키 식별자는 SHA-1(뒤 장)

두 줄에 모두 있는 나머지 설정은 1.26·1.27 이 더한 것입니다(2·3장). GODEBUG 문서의 1.25 항목에는 go 명령 자신의 설정 둘 (embedfollowsymlinks·allowmultiplevcs)도 있는데, 프로그램에 박히는 기본값이 아니라서 이 목록에는 나오지 않습니다.

실행 검증

그린티 — 객체가 아니라 페이지로

Michael Knyszek 과 Austin Clements 의 글에 따르면, GC 비용의 약 90% 가 표시(mark)이고, 표시 시간의 상당 부분 — 대개 최소 35% — 은 힙 메모리를 기다리며 멈춘 시간입니다. 지금의 표시 알고리즘은 포인터를 따라 메모리를 이리저리 뛰어다니므로 CPU 캐시가 소용없습니다.

그린티의 생각은 한 줄입니다 — 객체가 아니라 페이지로 일한다. 작업 목록에 객체 대신 페이지를 올리고, 한 페이지에 쌓인 객체들을 한 번에 훑습니다. 표시 여부도 힙 전체가 아니라 페이지마다 따로 기록합니다.

글은 벡터 가속 없이도 벤치마크 모음에서 GC CPU 비용이 10%–40% 줄었다고 적고, 한 페이지에 훑을 객체가 하나뿐인 작업은 나아지지 않거나 나빠질 수 있다고 덧붙였습니다.

역사 근거

실험 GC 그린티 1.25

왜 — 1.25 는 새 GC 를 실험으로 넣었습니다. 작은 객체의 표시와 훑기를 지역성과 CPU 확장성으로 빠르게 하는 설계이고, 노트는 GC 를 많이 쓰는 실제 프로그램에서 GC 부담이 10—40% 가량 줄 것으로 기대한다고 적었습니다. 빌드할 때 GOEXPERIMENT=greenteagc 로 켭니다.

그 뒤 — 1.27.1 에서는 아무것도 적지 않은 빌드가 이미 그린티입니다. 글은 1.26 에서 기본으로 만들되 GOEXPERIMENT=nogreenteagc 로 끌 수 있게 하겠다고 예고했습니다. 그 결과는 2장에서 봅니다.
실행 검증

비행 기록기는 왜 필요했나

실행 트레이스는 고루틴이 언제 돌았고 — 더 중요하게 — 언제 돌지 않았는지를 담아 지연 문제를 푸는 데 좋습니다. 그러나 trace.Start·Stop 은 시험이나 명령줄 도구에나 맞습니다. 며칠씩 도는 웹 서버에서 문제가 난 걸 알았을 때는 이미 Start 를 부르기에 늦습니다.

비행 기록기는 트레이스를 파일 대신 메모리에 모으고 마지막 몇 초만 남깁니다. 프로그램이 문제를 알아챈 순간 그 창을 떠 가면 됩니다. 글은 이것을 "문제 구간으로 곧장 들어가는 메스" 에 비유했습니다.

글의 예제는 HTTP 요청 하나가 100ms 넘게 걸리면 스냅숏을 뜨고, go tool trace 로 열어 defer 로 늦게 풀린 뮤텍스를 찾아냅니다. 글은 1.21 이 트레이스의 부담을 크게 줄였고, 1.22 에서 형식이 나눌 수 있게 바뀐 것이 비행 기록기로 이어졌다고 적었습니다.

역사 근거

runtime/trace.FlightRecorder 1.25

왜 — 트레이스를 메모리의 고리 버퍼에 계속 기록하다가, 의미 있는 사건이 나면 WriteTo 로 마지막 몇 초를 떠 파일에 씁니다. 필요한 트레이스만 남으므로 훨씬 작습니다. 남길 시간과 양은 FlightRecorderConfig 로 정합니다.

함정 — 비행 기록기는 한 프로그램에 하나만 켤 수 있습니다(둘째 줄). trace.Start 와는 함께 돌 수 있습니다. 설정을 비워 두면 1.27.1 소스 기준으로 최대 10 MiB, 최소 10초를 남깁니다(runtime/trace/flightrecorder.go). 머리말의 go 1.26 trace 는 툴체인 버전이 아니라 트레이스 형식의 버전입니다 — 1.27.1 의 최신 형식이 Go126 입니다 (internal/trace/version).
실행 검증

다시 던진 패닉의 출력 1.25

왜 — 패닉을 recover 했다가 같은 값으로 다시 panic 하면, 예전에는 값이 두 번 찍혔습니다. panic: PANIC [recovered] 다음 줄에 panic: PANIC 이 또 나왔습니다. 1.25 부터는 한 줄에 [recovered, repanicked] 로 적습니다.

이 변화는 go 줄로도 GODEBUG 로도 갈리지 않습니다 — 캡처는 1.27.1 에서의 동작입니다. 옛 두 줄 형식은 노트에만 남아 있습니다. 마지막 exit status 2 는 프로그램의 종료 코드이고, go run 자신은 1 로 끝납니다.

실행 검증

리눅스에서 메모리 영역에 이름을 1.25

왜 — 커널이 익명 VMA 이름(CONFIG_ANON_VMA_NAME)을 지원하면, 런타임이 익명 메모리 매핑에 용도를 적습니다 — 힙이면 [anon: Go: heap]. /proc/pid/maps 를 보는 도구에서 Go 의 메모리가 무엇인지 알 수 있게 됩니다. 끄는 설정은 GODEBUG=decoratemappings=0 입니다.

안드로이드 커널이 이 기능을 켜 두어서 폰에서도 보입니다. 1.27.1 소스에는 heap 밖에도 여러 이름이 있지만 (runtime/mem_linux.go 등), 이 작은 프로그램에서는 두 가지만 나왔습니다.

실행 검증

늦춰졌던 nil 검사를 바로잡다 1.25

왜 — 1.21 에서 생긴 컴파일러 버그로, nil 포인터 검사가 뒤로 밀리는 일이 있었습니다. 아래는 노트에 실린 프로그램 그대로입니다. os.Open 이 실패하면 f 가 nil 이므로 f.Name() 에서 패닉해야 하는데, 1.21–1.24 는 검사를 오류 확인 뒤로 미뤄서 아무 일 없이 끝났습니다. 명세 위반이었습니다.

고쳐야 할 쪽은 코드 — 노트의 처방은 오류 확인을 오류를 낸 문장 바로 뒤로 옮기는 것입니다. 이 수정은 go 줄로도 GODEBUG 로도 되돌릴 수 없습니다 — 버그를 되살리는 스위치는 없습니다.
실행 검증

디버그 정보가 DWARF 5 로 1.25

왜 — 1.25 의 컴파일러와 링커는 디버그 정보를 DWARF 버전 5 로 만듭니다. 디버그 정보가 차지하는 공간이 줄고, 큰 바이너리일수록 링크 시간도 줄어듭니다. GOEXPERIMENT=nodwarf5 로 되돌릴 수 있지만, 이 대피로는 나중에 없어질 수 있다고 했습니다.

DWARF 5 에서는 .debug_loc·.debug_ranges 가 .debug_loclists·.debug_rnglists 로 바뀌고 .debug_addr 가 더해졌습니다. go run 은 링커에 -s -w 를 넘겨 디버그 정보를 빼므로(1.27.1 의 cmd/go/internal/work/gc.go) 첫 두 실행은 그것을 되돌렸습니다. 1.27.1 소스는 darwin·ios·aix 에서는 DWARF 5 를 쓰지 않습니다 (internal/buildcfg/exp.go).

실행 검증

크기가 변수인 make 도 스택에 1.25

왜 — 컴파일러가 슬라이스의 뒷받침 배열을 스택에 두는 경우가 늘었습니다. 크기가 실행 중에야 정해지는 make 도, 결과가 함수 밖으로 새지 않고 작으면 힙 할당 없이 끝납니다. 노트는 잘못된 unsafe.Pointer 사용의 피해를 키울 수 있다고 경고하고, bisect 도구와 끄는 플래그를 알려 줍니다.

경계 32바이트는 1.27.1 소스의 기본값입니다(cmd/compile/internal/base/flag.go 의 VariableMakeThreshold). 노트는 -gcflags=all=-d=variablemakehash=n 을 적었는데, 여기서는 이 패키지만 껐습니다. [DISABLED] 줄은 컴파일러가 끈 make 자리마다 bisect 형식으로 알리는 것입니다.

실행 검증

느리거나 불안하거나 — 동시성 시험의 딜레마

Damien Neil 은 진짜 시간을 쓰는 시험은 늘 느리거나 불안정하고, 대개 둘 다라고 적었습니다. 오래 기다리면 느리고, 덜 기다리면 가끔 실패합니다. net/http 의 시험들이 그랬고, 그것이 이 일의 출발점이었다고 합니다.

동시성 코드를 시험하려면 두 가지가 필요합니다 — 가짜 시간, 그리고 배경 고루틴이 할 일을 다 마쳤는지 기다리는 방법. 가짜 시간을 인터페이스로 넘기게 하면 코드가 관용에서 벗어납니다. 글의 결론은 네트워크와 달리 가짜 시간의 구현은 하나뿐이라는 것이었습니다 — 시간은 앞으로 갈 뿐입니다. 그래서 시험 하나의 범위 안에서 time 패키지 자체가 가짜 시계를 쓰게 했습니다.

1.24 의 실험은 7부에서 보았습니다. 1.25 에서 정식이 되었습니다.

역사 근거

testing/synctest 정식판 1.25

왜 — synctest.Test 는 시험 함수를 격리된 "거품(bubble)" 에서 돌립니다. 거품 안의 time 패키지는 가짜 시계를 쓰고, 거품의 모든 고루틴이 막히면 시계가 즉시 앞으로 갑니다. synctest.Wait 는 거품의 다른 고루틴이 모두 막힐 때까지 기다립니다.

거품의 시계 — 가짜 시계는 늘 2000-01-01 자정(UTC)에서 시작합니다(go doc testing/synctest). 시험은 한 시간을 잤지만 실제로는 바로 끝났습니다. Wait 는 AfterFunc 가 띄운 고루틴이 일을 마치기를 기다립니다. 뮤텍스에 막힌 것은 "오래 막힘(durably blocked)" 으로 치지 않으므로 Wait 가 기다려 주지 않습니다(같은 문서).

Go 1.25 퀴즈

Q. go.mod 의 go 줄이 1.24 인 서비스를 1.25 툴체인으로 다시 빌드해 CPU 제한 2개인 컨테이너에 올렸습니다. GOMAXPROCS 는 제한을 따릅니까? 그리고 f, err := os.Open(p); name := f.Name() 처럼 오류 확인보다 결과를 먼저 쓴 코드는 어떻게 됩니까?

A. 따르지 않습니다 — go 줄이 1.24 면 containermaxprocs=0·updatemaxprocs=0 이 기본이라 옛 동작입니다 (go 줄을 1.25 로 올리거나 GODEBUG 로 켭니다). 두 번째 코드는 파일이 없을 때 이제 패닉합니다. nil 검사 버그 수정은 go 줄과 상관없습니다.
