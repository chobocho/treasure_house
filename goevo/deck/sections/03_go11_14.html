Go 1.1 – 1.4 — 약속을 지키며 다듬은 시기

메서드 값 · 경쟁 검출기 · 세 인덱스 슬라이스 · 시험 범위 · 연속 스택 · sync.Pool · for range · internal · go generate · Android

이 부에서 할 일

Go 1 이후 네 릴리스는 호환성 약속 안에서 움직였습니다. 언어는 조금만 바뀌었고, 대부분의 힘은 구현 — 성능, 런타임, 도구 — 에 들어갔습니다. 1.2 부터는 여섯 달마다 한 번씩 나오기 시작합니다.

  • 1.1 — 메서드 값, return 규칙 완화, 64비트 int, 경쟁 검출기, bufio.Scanner
  • 1.2 — 세 인덱스 슬라이스, nil 접근의 보장, go test -cover, %[n]
  • 1.3 — 언어 변화 없음. 연속 스택, 정밀 GC, 작은 map 의 무작위 순회, sync.Pool
  • 1.4 — for range x, **T 금지, internal 패키지, go generate, Android
  • 이 시기의 언어 변화는 go.mod 의 go 줄로 갈리지 않습니다. 그래서 예제는 모두 "1.27.1 에서의 동작" 이고, 금지된 것은 지금 컴파일러의 오류로 보입니다(0부).
설명용

1장

Go 1.1

메서드 값 · 끝나는 문장 · 64비트 int · 경쟁 검출기 · 성능 ·

Go 1.1 한눈에

Go 1 뒤 첫 큰 릴리스이고, 노트가 스스로 밝힌 초점은 성능입니다. 언어에는 뒤로 호환되는 변화 둘(메서드 값, return 규칙)과 오류 경우의 정리가 들어왔습니다. 1.0 에서 1.1 까지는 한 해가 넘게 걸렸습니다.

문서 근거

메서드 값 (method values) 1.1

왜 — w.Write 처럼 수신자를 묶은 메서드를 그대로 함수 값으로 넘기고 싶을 때, 전에는 수신자를 가두는 함수 리터럴을 손으로 써야 했습니다. 1.1 은 x.M 을 "x 에 묶인 함수" 로 만들었습니다. 수신자를 첫 인자로 받는 메서드 식((*T).M)과는 다른 것입니다.

함정 — 메서드 값을 만드는 순간 수신자가 평가됩니다. 값 수신자(Get)면 그때의 사본이 묶이므로, 뒤에 원본을 바꿔도 get() 은 옛 값(15)을 돌려줍니다.
실행 검증

끝나는 문장 — 마지막 return 이 없어도 된다 1.1

왜 — 1.1 전에는 값을 돌려주는 함수가 반드시 return 이나 panic 호출로 끝나야 했습니다. 조건 없는 for 로 끝나는 함수처럼 뻔히 필요 없는 경우에도 그랬습니다. 1.1 은 "끝나는 문장(terminating statement)" 을 정의해, 마지막 문장이 그것이면 return 을 생략하게 했습니다.

실행 검증

규칙은 값을 보지 않는다 — 문법만 본다

노트는 이 규칙이 "순수하게 문법적" 이라고 강조합니다. 값이 무엇인지 따지지 않으므로 복잡한 분석이 필요 없습니다. 거꾸로 말하면 사람 눈에는 빠짐없는 갈래도 컴파일러는 인정하지 않습니다.

고치는 법 — 마지막 if 를 else 로 바꾸거나 끝에 panic("unreachable") 을 둡니다. break 가 있는 for 는 끝나는 문장이 아닙니다.
실행 검증

상수 0 으로 나누면 컴파일 오류 1.1

왜 — Go 1 에서 x/0 은 실행하다 패닉을 냈습니다. 명세를 다지는 과정에서 1.1 은 상수 0 으로 나누는 정수 나눗셈을 "올바른 프로그램이 아니다" 로 정했습니다. 컴파일할 때 이미 알 수 있는 잘못이기 때문입니다.

함정 — 막히는 것은 상수 0 뿐입니다. 11행처럼 값이 0 인 변수로 나누면 여전히 실행 중 패닉입니다(오류가 7행 하나뿐인 것을 보십시오).
실행 검증

서로게이트 반쪽은 룬이 아니다 1.1

왜 — U+D800–U+DFFF 는 UTF-16 에서 큰 코드 포인트를 조립할 때만 쓰는 영역입니다. 1.1 은 컴파일러· 라이브러리·런타임 모두에서 이 제약을 지키게 했습니다. 룬을 UTF-8 로 바꿀 때 반쪽을 만나면 인코딩 오류로 보고 U+FFFD 를 냅니다. 노트에 따르면 같은 프로그램이 1.0 에서는 "\ud800" 을 찍었습니다.

실행 검증

64비트 플랫폼의 int 는 64비트 1.1

왜 — 명세는 int 가 32비트인지 64비트인지를 구현에 맡깁니다. 그때까지의 구현은 어디서나 32비트였고, 그래서 64비트 기계에서도 원소가 20억 개 넘는 슬라이스를 만들 수 없었습니다. 1.1 부터 gc 와 gccgo 모두 64비트 플랫폼에서 int·uint 를 64비트로 만듭니다. 같은 릴리스에서 64비트 힙 상한도 "몇 GB" 에서 "수십 GB" 로 커졌습니다.

함정 — 암묵 변환이 없으니 컴파일이 깨지는 프로그램은 없지만, "int 는 32비트" 를 가정한 코드는 조용히 다르게 돕니다. 어디서나 부호 확장을 원하면 int(int32(x)) 로 씁니다.
이어서 — Go 1 이 rune 을 따로 만든 까닭 중 하나가 바로 이 확장이었습니다 (2부).
실행 검증

경쟁 검출기 (race detector) 1.1

왜 — 같은 변수를 두 고루틴이 동기화 없이 만지고 그중 하나가 쓰기인 버그는, 배포하고 한참 뒤에야 엉뚱한 증상으로 드러납니다. 1.1 은 이를 찾는 도구를 go 명령에 넣었습니다. -race 를 붙여 빌드하거나 시험하면 됩니다. 처음에는 64비트 x86 의 리눅스·맥·윈도에서만 됐습니다.

블로그에 따르면 컴파일러가 모든 메모리 접근에 기록 코드를 넣고, 런타임 라이브러리가 동기화 없는 접근을 지켜봅니다. C/C++ 의 ThreadSanitizer 런타임 위에 지었고, 표준 라이브러리에서만 42개의 경쟁을 찾아냈습니다. 실행된 코드에서 실제로 일어난 경쟁만 잡으므로 현실적인 부하로 돌려야 합니다.

이 덱에서는 — 이 기계(android/arm64)에서는 -race 가 지원되지 않습니다. 그 캡처는 0부에 있습니다.

빌드 제약에 go1.1 태그 1.1

왜 — 새 기능을 쓰면서도 1.0.x 에서 빌드되는 패키지를 만들려면, 파일을 버전으로 골라야 합니다. 1.1 은 기본 빌드 제약 목록에 go1.1 태그를 넣었습니다. 이후 릴리스마다 자기 태그가 붙습니다.

표기 — 노트는 당시의 // +build go1.1 줄로 썼습니다. 예제는 지금 gofmt 가 쓰는 //go:build 줄입니다. 뜻은 같습니다.

왜 — 노트는 1.1 의 초점이 성능이라고 밝히고, 1.0 대비 전형적인 향상이 "about 30%-40%, sometimes much more, but occasionally less or even non-existent" 라고 적었습니다. 이 기계에서 재지 않고 노트의 말을 그대로 옮깁니다.

bufio.Scanner 1.1

왜 — 줄 단위로 읽는 간단한 일에도 ReadBytes·ReadString·특히 ReadLine 은 쓰기가 쓸데없이 복잡했습니다. Scanner 는 기본값을 "줄 단위, 끝의 줄바꿈 제거" 로 두고, 병적으로 긴 줄 같은 곤란한 입력에서는 멈추는 쪽으로 문제를 단순하게 만들었습니다.

함정 — 루프가 끝난 뒤 Err() 를 보지 않으면 "입력 끝" 과 "너무 긴 줄에서 멈춤" 을 구별할 수 없습니다. 노트도 오류를 넘어 계속 읽어야 하는 일에는 옛 인터페이스가 필요할 수 있다고 적었습니다.

Q. c 가 *Counter 이고 Get 이 값 수신자일 때, get := c.Get 다음에 c.Add(100) 을 하면 get() 은 새 값을 돌려줍니까? 그리고 x/0 과 x/zero(변수) 중 어느 쪽이 컴파일 오류입니까?

A. 아닙니다. 메서드 값을 만드는 순간 *c 가 복사되어 묶이므로 옛 값을 돌려줍니다. 컴파일 오류는 상수 0 으로 나누는 x/0 뿐이고, 변수로 나누는 쪽은 여전히 실행 중 패닉입니다.

Go 1.2

세 인덱스 슬라이스 · nil 접근 보장 · 선점 · 시험 범위 ·

Go 1.2 한눈에

1.1 뒤 약 여섯 달 만에 나온 첫 "짧은 주기" 릴리스입니다. 그래서 변화의 폭은 1.1 보다 작지만, 더 나은 스케줄러와 새 언어 기능 하나(세 인덱스 슬라이스)가 들어왔습니다.

문서 근거

세 인덱스 슬라이스 a[i:j:k] 1.2

왜 — 슬라이스의 용량은 밑 배열 끝까지입니다. 그래서 array[2:4] 를 받은 쪽이 append 하면 원래 배열의 다음 칸을 덮어씁니다. 1.2 는 둘째 콜론 뒤에 용량의 끝을 적게 해, 받은 쪽이 넘볼 수 있는 범위를 자를 수 있게 했습니다. 용량은 k-i 입니다.

함정 — 두 인덱스 슬라이스에 대한 append 가 원본 array[4] 를 -1 로 덮었습니다. cap == len 으로 자른 full 은 새 배열로 복사되어 원본이 그대로입니다.
실행 검증

세 인덱스 꼴의 생략 규칙

세 인덱스 꼴에서 첫 인덱스는 생략하면 0 이지만, 나머지 둘은 늘 적어야 합니다. 노트는 "앞으로 기본값을 줄 수도 있다" 고 적었지만 지금 컴파일러도 여전히 요구합니다.

도구도 따라 바뀌었습니다 — go/ast 의 SliceExpr 에 Slice3 필드가 생겼습니다.

실행 검증

nil 포인터를 거친 접근은 반드시 패닉 1.2

왜 — Go 1.0 에서는 큰 구조체의 nil 포인터 x 로 x.Field 를 읽으면 주소 1<<24 의 메모리를 그대로 읽을 수 있었습니다. 안전을 위해 1.2 는 nil 주소를 평가해야 하는 모든 식이 패닉하거나 올바른 값을 내도록 보장했습니다. 필요하면 컴파일러가 검사 코드를 넣습니다.

눈여겨볼 점 — len(arr) 은 nil 이어도 괜찮습니다. 배열 포인터의 길이는 타입이 정하는 상수라 주소를 평가하지 않기 때문입니다. 패닉은 arr[2] 에서 납니다.
실행 검증

선점·스레드 상한·스택 크기 1.2

왜 — 그때까지는 끝없이 도는 고루틴이 같은 스레드의 다른 고루틴을 굶길 수 있었습니다. 1.2 는 함수에 들어갈 때 가끔 스케줄러를 불러, (인라인되지 않은) 함수 호출이 있는 루프는 선점될 수 있게 했습니다. 노트 스스로 "부분적인" 해결이라고 적었습니다.

바뀐 것노트의 수
프로그램 하나의 스레드 수 상한기본 10,000. debug.SetMaxThreads 로 조정
고루틴의 최소 스택4KB → 8KB (스택 조각 전환 비용 때문)
고루틴 하나의 최대 스택64비트 1GB, 32비트 250MB. debug.SetMaxStack 으로 조정

최소 스택 크기는 오래가지 않았습니다 — 스택 방식이 바뀐 뒤 1.4 에서 다시 줄어듭니다(4장).

실행 검증

시험 범위 go test -cover 1.2

왜 — 노트가 1.2 의 go test 에서 "major new feature" 로 꼽은 것입니다. -cover 를 주면 도구가 패키지 소스를 고쳐 써서 계측 문장을 넣고, 평소처럼 컴파일·실행한 뒤 기본 통계를 보고합니다. 당시에는 cover 도구를 go.tools 저장소에서 따로 설치해야 했습니다.

방식 — 블로그에 따르면 동적 디버깅을 피하고, 컴파일 전에 소스의 실행 구간마다 GoCover.Count[n] = 1 같은 대입을 넣습니다. 이 대입은 이동 명령 하나로 컴파일되어 전형적인 시험에서 약 3% 만 더 든다고 합니다.
실행 검증

서식 지정자의 인자 번호 %[n] 1.2

왜 — 노트가 밝힌 동기는 지역화입니다. 언어마다 낱말 차례가 다르니, 인자 목록은 그대로 두고 서식 문자열만 바꿔 차례를 바꿀 수 있어야 합니다. [n] 은 1부터 세고, 그 뒤의 인자는 n+1 번째부터 이어집니다. 폭·정밀도 자리의 * 에도 쓸 수 있습니다.

쓸모 하나 더 — %v … %[1]T 처럼 비싼 식을 한 번만 적고 두 번 찍을 수 있습니다. 노트의 log.Printf 예가 그 모양입니다.
실행 검증

템플릿의 비교 함수와 else if 1.2

왜 — 템플릿 안에서 값을 비교하려면 함수 맵에 직접 함수를 넣어야 했고, 두 번째 조건은 {{else}}{{if}}…{{end}}{{end}} 로 겹쳐 써야 했습니다. 1.2 는 기본 함수 eq ne lt le gt ge 를 넣고 {{else if}} 를 허용했습니다. eq 만은 첫 인자를 뒤의 여러 인자와 견줍니다(하나라도 같으면 참).

왜 — 원자적 읽기·쓰기는 정수와 포인터에만 있었습니다. 1.4 의 atomic.Value 는 아무 타입의 값을 효율적으로 원자적으로 읽고 쓰게 합니다. 읽기가 잦고 쓰기가 드문 설정 값을 통째로 바꿔 끼우는 데 알맞습니다.

함정 — 한 Value 에 넣는 값은 늘 같은 구체 타입이어야 합니다. 다른 타입을 Store 하면 패닉입니다(마지막 줄). 담은 값은 바꾸지 말고 새 값을 만들어 통째로 넣습니다.
실행 검증

import 경로의 정리 — 정식 경로와 golang.org/x 1.4

왜 — 코드가 github.com 같은 호스팅 서비스에 있으면 한 패키지가 두 경로(호스팅 경로와 "꾸민" 경로)로 가져와질 수 있습니다. 한 프로그램에 두 벌이 들어가거나, 옛 경로를 쓰다 갱신을 놓치거나, 호스팅을 옮길 때 사용자가 깨집니다. 1.4 는 package 절에 정식 경로를 적는 주석을 도입했습니다.

노트의 예는 package pdf // import "rsc.io/pdf" 입니다. 이 주석이 있으면 그 밖의 경로(예: github.com/rsc/pdf)로 가져오는 패키지를 go 명령이 컴파일하지 않습니다.

  • Go 프로젝트의 하위 저장소가 code.google.com/p/go.tools 에서 golang.org/x/tools 같은 경로로 옮겨졌습니다.
  • syscall 은 본 저장소에 필요한 것 말고는 동결되고, 새 시스템 호출은 golang.org/x/sys 로 갑니다.
  • 본 저장소의 src/pkg 층이 없어져 fmt 의 소스가 src/fmt 로 올라왔습니다.

Go 1.4 퀴즈

Q. a/b/c/internal/d 패키지를 a/b/c/e 와 a/b/g 가 각각 가져오려 합니다. 어느 쪽이 됩니까? 그리고 windows.go 라는 파일은 1.4 부터 어느 OS 에서 컴파일됩니까?

A. internal 의 부모 a/b/c 아래에 있는 a/b/c/e 만 됩니다. windows.go 는 밑줄이 없으므로 태그가 아니고, 모든 OS 에서 컴파일됩니다(윈도 전용으로 하려면 os_windows.go 처럼 이름을 바꾸거나 빌드 제약을 답니다).
