Go 1.11 – 1.17 — 모듈의 시대가 열리다

모듈·WebAssembly · go 줄 = 언어 버전 · 숫자 리터럴·오류 감싸기 · 비동기 선점 · 링커 · embed·io/fs · 가지친 모듈 그래프·레지스터 ABI

이 부에서 할 일

이 일곱 릴리스의 줄기는 모듈입니다. 1.11 에서 실험으로 들어와, 1.14 에서 "실사용 준비 완료" 를 선언하고, 1.16 에서 기본이 되고, 1.17 에서 그래프를 가지칩니다. 그 사이 언어는 오랜만에 다시 움직이기 시작합니다.

  • 1.11 — 모듈(실험), WebAssembly, go run ., GOFLAGS
  • 1.12 — go.mod 의 go 줄이 언어 버전이 됨, fmt 의 정렬된 map, TLS 1.3(선택)
  • 1.13 — 0b·0o·1_000, 부호 있는 시프트, 오류 감싸기, 모듈 미러가 기본값
  • 1.14 — 겹치는 인터페이스, 비동기 선점, 거의 공짜인 defer, T.Cleanup
  • 1.15 — 링커 개선, vet 의 새 경고 둘, time/tzdata
  • 1.16 — //go:embed, io/fs, io/ioutil 폐기 권고, 모듈 모드가 기본
  • 1.17 — 슬라이스→배열 포인터, unsafe.Add, 가지친 모듈 그래프, //go:build
  • 1.13·1.14·1.17 의 언어 변화는 go.mod 의 go 줄로 갈립니다. 이 부에서는 그 거절 메시지가 "이전" 의 증거입니다(0부).
  • 모듈 예제는 모두 네트워크 없이 돕니다(GOPROXY=off). 이웃 디렉터리를 replace 로 붙여 의존성을 흉내 냅니다. 원격에서 받는 go get·go install pkg@v 는 돌리지 않고 노트를 인용합니다.

모듈(실험) · WebAssembly · go run . · GOFLAGS · 경계 검사 제거 ·

Go 1.11 한눈에

언어 명세는 그대로이고 변화는 도구·런타임·라이브러리에 몰렸습니다. 릴리스 공지는 그중 특히 둘 — 모듈과 WebAssembly — 을 꼽았습니다.

문서 근거

모듈은 왜 — "버전은 따로 도구가 풀겠지"

Russ Cox 의 제안 글에 따르면, goinstall(뒤의 go get)과 URL 같은 import 경로를 내놓았을 때 곧바로 "버전은 어떻게 적나" 라는 질문이 나왔고, 팀은 답을 몰랐다고 인정했습니다. 오랫동안 바깥 도구가 풀 문제로 여겼고, 공동체는 여러 도구를 만들었습니다. 그러다 해법이 너무 많아졌고, 하나의 공식 도구가 필요해졌습니다.

그 제안의 중심은 호환성입니다. "옛 패키지와 새 패키지의 import 경로가 같으면 새것은 옛것과 호환되어야 한다" 는 import 호환성 규칙과 의미 있는 버전(semver)을 함께 받아들이면, 주 버전이 다르면 경로도 달라야 한다는 결론 — my/thing/v2 같은 의미 있는 import 버전 — 이 논리로 따라 나온다고 적었습니다.

1.11 노트의 약속 — 모듈은 GOPATH 의 대안이고, 개발자는 더 이상 GOPATH 안에서만 일하지 않아도 되며, 의존성 정보는 명시적이면서 가볍고, 빌드는 더 믿을 만하고 재현됩니다.
역사 근거

go.mod 한 파일 — GOPATH 밖에서 빌드 1.11

왜 — 모듈 모드에서는 디렉터리 트리의 뿌리에 있는 go.mod 가 "이 코드는 어떤 모듈인가" 를 말합니다. 그래서 코드가 GOPATH 안에 있을 필요가 없습니다. 1.11 에서 모듈 지원은 실험이었고, 세부는 바뀔 수 있지만 1.11 로 바꾼 프로젝트는 1.12 이후에도 동작한다고 약속했습니다.

캡처 읽기 — /work 는 실험 스크립트가 예제를 베껴 둔 작업 디렉터리이고, /scratch/gopath 는 GOPATH 입니다. 둘이 겹치지 않아도 빌드됩니다.
실행 검증

go mod init, 그리고 GOPATH 모드와의 차이

go mod init 이 새 모듈의 go.mod 를 만듭니다. 같은 디렉터리를 모듈 모드와 GOPATH 모드로 각각 보면, 패키지의 이름부터 다릅니다.

_/work — GOPATH 모드는 GOPATH/src 밖의 디렉터리에 진짜 import 경로를 줄 수 없어서 _ 로 시작하는 임시 이름을 붙입니다. 모듈 모드는 go.mod 의 module 줄이 그 이름입니다. -C 는 훨씬 뒤에 생긴 플래그로, 여기서는 하위 디렉터리에서 명령을 돌리려고 썼습니다.

왜 — 노트는 실험적인 WebAssembly 포트를 더한다고만 적고, 그 결과물이 고루틴 스케줄링·GC·map 을 위한 런타임을 통째로 담아 최소 약 2 MB(압축 500 KB)라고 밝혔습니다. 자바스크립트는 새 실험 패키지 syscall/js 로 부릅니다. 새 GOOS js 와 GOARCH wasm 이 생기면서 *_js.go·*_wasm.go 파일은 그 대상일 때만 빌드됩니다.

go run . 과 GOFLAGS 1.11

왜 — 1.11 전의 go run 은 .go 파일 목록만 받았습니다. 1.11 부터는 import 경로 하나, 디렉터리, 또는 패키지 하나에 맞는 패턴을 받습니다 — 무엇보다 go run . 입니다. 이 덱의 모든 캡처가 쓰는 그 명령입니다. 같은 릴리스에서 GOFLAGS 환경 변수가 go 명령의 기본 플래그를 정하게 되었습니다. 노트가 든 예는 항상 -mod=vendor 로 빌드하고 싶은 CI 입니다.

이 덱의 실험 — 캡처는 모두 GOFLAGS='-trimpath -p=1' 로 돕니다. 경로를 지우고 빌드를 한 줄로 세우려는 것이고, 명령 줄에는 보이지 않습니다(0부).

고치는 법 — 값이 필요 없으면 switch v.(type) 로 쓰면 됩니다. 이 오류는 go 줄로 갈리지 않습니다. 둘째 캡처처럼 go 줄을 내려도 지금 컴파일러는 똑같이 거절합니다.

왜 — 자기 로그 함수가 받은 서식과 인자를 그대로 fmt.Printf 류에 넘기면, 그 함수도 사실상 printf 입니다. 1.11 의 vet 은 이런 감싸개를 더 잘 알아보고 호출하는 쪽의 서식 오류를 잡습니다. 같은 릴리스에서 vet 은 타입 검사에 실패한 패키지를 경고가 아니라 치명적 오류로 다룹니다.

Go 1.12 한눈에

이번에도 언어 명세는 그대로이고 변화는 구현에 있습니다. 모듈 쪽에서는 이 덱 전체가 기대는 규칙 — go.mod 의 go 줄이 언어 버전이다 — 이 이때 생겼습니다.

문서 근거

go 줄이 언어 버전이 되다 1.12

왜 — 1.12 부터 go.mod 의 go 지시문은 "그 모듈의 파일이 쓰는 언어의 버전" 을 뜻합니다. 컴파일러에는 -lang 플래그가 생겼고, 노트의 예는 바로 이것입니다 — -lang=go1.8 이면 1.9 에 들어온 타입 별칭을 쓴 프로그램이 오류가 됩니다.

함정 — 노트는 1.12 이전의 언어 변화는 "일관되게 강제되지 않는다" 고 적었습니다. 지금 컴파일러가 go 줄로 거르는 옛 변화도 1.9 의 별칭 하나뿐입니다. 그래서 3부의 예제는 go 줄을 내려도 컴파일됩니다.
이어서 — go 줄이 툴체인 선택까지 맡게 되는 것은 훨씬 뒤의 일이고, 이 덱이 전과 후를 보이는 방법 자체가 이 규칙 위에 서 있습니다(0부).
실행 검증

1.27.1 에서는 — 그냥 go run . 하면 go.mod 를 고치지 않고 멈춥니다. 1.16 에서 바뀐 동작이고, 그 캡처는 6장에 있습니다.

fmt 가 map 을 키 차례로 찍는다 1.12

왜 — map 의 순회 순서는 일부러 무작위입니다(3부). 그래서 map 을 찍은 출력을 비교하는 시험이 흔들렸습니다. 1.12 의 fmt 는 "시험을 쉽게 하려고" map 을 키로 정렬해 찍습니다. 정수·실수·문자열은 <, NaN 은 다른 실수보다 앞, 인터페이스 키는 먼저 구체 타입으로 가릅니다. 전에는 NaN 키가 <nil> 로 찍혔습니다.

함정 — 정렬되는 것은 fmt 의 출력뿐입니다. for k := range m 의 순서는 여전히 무작위입니다. 이 덱의 캡처가 세 번 돌려 같은 바이트여야 한다는 규칙을 지킬 수 있는 것도 이 변화 덕입니다.

A. 실행 중에 패닉합니다 — 1.17 의 이 변환은 패닉할 수 있는 첫 변환이고, 미리 알려면 reflect.Value.CanConvert 를 씁니다. 옛 문법에서 공백은 OR 이므로 //go:build linux || darwin 입니다. gofmt 가 이렇게 맞춰 줍니다.
