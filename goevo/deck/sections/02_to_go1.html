공개에서 Go 1 까지

2009-11-10 공개 · 주간 스냅숏과 r56–r60 · gofix · Go 1 이 굳힌 언어와 라이브러리 · Go 1 발표

이 부에서 할 일

공개된 Go 는 두 해 반 동안 거의 매주 바뀌었습니다. Go 1 은 그 변화를 한 번에 정리하고 "이제부터는 깨지 않는다" 고 약속한 판입니다.

  • 공개 첫해 — 무엇을 들고 나왔고 무엇에 놀랐나
  • 주간 스냅숏과 이름 붙은 릴리스(r56–r60) — 불안정을 다루는 방식
  • gofix — 깨는 변경을 도구로 옮겨 주는 방식
  • Go 1 이 언어에서 더한 것과 없앤 것 — 없앤 것은 지금 컴파일러의 거절로 확인
  • 패키지 재배치와 go 명령, 그리고 호환성 약속

공개

2009-11-10 — 오픈소스 프로젝트가 되다

2009년 11월 10일

Go 는 2009-11-10 에 공개 오픈소스 프로젝트가 되었습니다. 설계는 그보다 두 해 앞서 구글 안에서 시작했습니다(1부).

We set out to build a language for systems programming - the kinds of programs one might typically write in C or C++ - and we were surprised by Go’s utility as a general purpose language.

"우리는 시스템 프로그래밍 — 흔히 C 나 C++ 로 짜던 종류의 프로그램 — 을 위한 언어를 만들려 했고, 범용 언어로서 Go 가 쓸모 있다는 데 놀랐습니다."

같은 글은 C·C++·Java 프로그래머의 관심은 예상했지만 Python·JavaScript 같은 동적 타입 언어 사용자의 관심은 뜻밖이었다고 적습니다.

2장

스냅숏의 시대

weekly · release.rNN · gofix

거의 매주 새 판

공개 뒤 Go 는 거의 매주 한 번 판을 냈습니다. 판마다 무엇이 바뀌었는지, 호환성을 깨는 변경은 따로 표시해 노트를 달았습니다.

두 출처의 수가 다릅니다 — 스냅숏 기록 문서의 절은 89개, 저장소의 weekly.* 태그는 99개입니다. 여기서는 어느 쪽도 고치지 않고 둘 다 출처와 함께 싣습니다.

실행 검증

weekly 와 release 를 가르다

2011-03-16 의 블로그는 태그 체계를 바꿉니다. 매주 찍던 태그는 weekly 로 이름을 바꾸고, release 태그는 한두 달에 한 번 골라 붙이는 안정판에만 붙입니다.

We permit backward-incompatible changes so that we can learn from, rather than immortalize, our mistakes.

"우리는 실수를 영원히 새기는 대신 그로부터 배우려고 호환되지 않는 변경을 허락합니다." —

실행 검증

gofix — 깨는 변경을 도구가 옮긴다

안정판이 드물어지면 판 사이의 변경이 한꺼번에 몰립니다. 2011-04-15 에 소개된 gofix 는 소스를 읽어 옛 API 를 쓰는 곳을 새 API 로 고쳐 쓰고, 고칠 수 없는 곳은 파일과 줄 번호로 경고합니다.

  • API 를 크게 바꿀 때마다 그 변환을 gofix 에 더한다는 방침이었습니다.
  • Go 1 으로 옮길 때도 go fix 가 import 경로와 m[k] = v, false 삭제 문법을 고쳐 씁니다(3장·4장).

지금의 go fix — 같은 이름의 명령이 지금도 있지만 하는 일은 다릅니다. 1.26 에서 완전히 새로 짜여 코드를 요즘 관용구로 바꾸는 modernizer 의 집이 되었습니다(8부).
역사 근거

Go 1 을 예고하다

2011-10-05, 러스 콕스는 "Go version 1" 을 이듬해 초에 내겠다고 예고합니다. 요점은 새 기능이 아니라 안정입니다 — 프로그램을 몇 해 동안 고치지 않고 돌릴 수 있고, 책이 "Go 몇 판" 을 다룬다고 말할 수 있게.

같은 글은 새 언어 기능을 "위원회로" 설계하려는 시도를 일부러 막겠다고 적습니다. Go 1 은 오늘의 Go 를 굳히는 판이지, 언어를 통째로 다시 생각하는 판이 아니라는 것입니다.

역사 근거

2장 퀴즈

Q. 2011년 3월의 태그 체계 변경에서 release 태그의 뜻은 어떻게 바뀌었습니까? 그리고 그 변경이 gofix 를 필요하게 만든 까닭은?

A. 매주 찍던 태그는 weekly 로 옮기고, release 는 한두 달에 한 번 고른 안정판에만 붙였습니다. 안정판 사이가 길어지면 호환되지 않는 변경이 한꺼번에 쌓이므로, 그것을 한 번에 옮겨 주는 도구가 필요해졌습니다.
설명용

3장

Go 1 — 언어

더한 것 여섯, 없앤 것 넷 ·

Go 1 한눈에

Go 1 is a representation of Go as it used today, not a wholesale rethinking of the language.

"Go 1 은 지금 쓰이는 그대로의 Go 이지 언어를 통째로 다시 생각한 것이 아닙니다." 노트의 기준점은 직전 안정판 r60 입니다.

문서 근거

이 장의 증거는 어떻게 얻었나

Go 1 이전의 컴파일러는 이 기계에서 돌릴 수 없습니다. 그래서 둘로 나눕니다.

Go 1 이…보이는 법
더한 것지금의 go 로 그 문법을 돌린다(go.mod 는 go 1.0)
없앤 것옛 문법을 그대로 컴파일해 지금 컴파일러의 거절을 싣는다

go.mod 의 언어 버전은 이 시대의 규칙을 가르지 않습니다 — 컴파일러가 버전으로 막는 문법은 1.9 이후의 것뿐입니다. 그래서 이 장의 캡처는 "1.27.1 에서의 동작" 이고, 역사는 노트 배지가 맡습니다.

설명용

문자열을 바로 append 1.0

copy 가 문자열을 바이트로 복사할 수 있던 것처럼, Go 1 은 append 에도 문자열을 ... 로 바로 붙일 수 있게 했습니다. 변환 한 번이 빠집니다.

실행 검증

받기 전용 채널은 닫을 수 없다 1.0

close 는 보내는 쪽이 "더 없다" 고 알리는 신호입니다. Go 1 전에는 받는 쪽이 닫아도 컴파일러가 막지 않았습니다. Go 1 부터 받기 전용 채널을 닫으면 컴파일 오류입니다.

실행 검증

포인터 원소의 타입 이름 생략 1.0

구조체 값의 슬라이스에서는 원소마다 Date{...} 를 생략할 수 있었지만, 포인터 슬라이스 []*Date 에서는 &Date{...} 를 다 써야 했습니다. Go 1 은 이것도 생략하게 했습니다.

도구 — gofmt -s 가 생략할 수 있는 자리의 타입 이름을 지워 줍니다.
실행 검증

init 안의 고루틴 1.0

옛 언어는 초기화 중에 만든 고루틴을 초기화가 다 끝날 때까지 돌리지 않았습니다. 그래서 init 에서 고루틴의 답을 기다리면 멈춰 버렸습니다. Go 1 은 초기화 중에도 고루틴이 돕니다.

실행 검증

rune 타입 1.0

64비트 기계에서 int 를 64비트로 키우고 싶었는데, 코드 포인트도 int 에 담고 있어서 키우면 글자마다 32비트가 버려질 참이었습니다. 그래서 코드 포인트용 타입 rune (= int32)을 먼저 따로 만들었습니다.

그다음 — 64비트 기계에서 int 가 실제로 64비트가 된 것은 1.1 입니다(3부).
실행 검증

내장 error 와 os.Error 의 퇴장 1.0

r60 까지 오류 타입은 os.Error 였습니다. Go 1 은 Error() string 하나를 가진 내장 인터페이스 error 를 만들고 errors 패키지를 더했습니다.

실행 검증

내장 error — Go 1 식

두 번째 값의 타입은 지금 *fs.PathError 로 나옵니다 — io/fs 는 1.16 에 생긴 패키지라, 이 줄은 "1.27.1 에서의 동작" 입니다(5부).

실행 검증

delete 내장 함수 1.0

옛 언어의 map 삭제는 m[k] = value, false 였습니다 — 버려질 값 하나와 거의 늘 false 인 불리언을 넘기는, 둘을 하나에 대입하는 유일한 특수 문법이었습니다. Go 1 은 이것을 없애고 delete(m, k) 를 만들었습니다.

실행 검증

map 순회 차례는 예측할 수 없다 1.0

옛 명세는 map 순회 차례를 정하지 않았지만 실제로는 기계마다 달랐고, 한 기계에서 늘 통과하던 시험이 다른 기계에서 깨졌습니다. Go 1 은 "같은 map 을 같은 루프로 돌려도 차례를 예측할 수 없다" 고 명세에 못 박았습니다.

함정 — 차례에 기대는 코드는 도구가 고쳐 줄 수 없습니다. 노트도 map 에 대한 range 를 손으로 모두 살피라고 권합니다.
실행 검증

다중 대입의 평가 차례 1.0

오른쪽을 모두 평가한 뒤 왼쪽에 대입한다는 규칙은 있었지만, 왼쪽의 색인·함수 호출을 언제 평가하는지는 정해지지 않았습니다. Go 1 은 왼쪽의 식을 먼저 왼쪽부터 평가하고, 그다음 왼쪽부터 대입한다고 정했습니다.

실행 검증

가려진 결과 변수와 맨 return 1.0

이름 붙은 결과 변수와 같은 이름을 안쪽 블록에서 다시 선언하고 맨 return 을 쓰면, 돌려주는 것은 바깥 변수입니다. 흔한 실수라서 Go 1 컴파일러는 그런 return 을 거절합니다(명세가 아니라 컴파일러의 규칙).

실행 검증

안 보이는 필드가 있는 구조체를 값으로 1.0

옛 언어는 다른 패키지의 구조체에 소문자 필드가 있으면 값 복사를 막았습니다(메서드 받는 쪽과 copy·append 는 예외). Go 1 은 막지 않습니다. 덕분에 포인터나 인터페이스 없이 "불투명한 값" 을 돌려주는 API 가 가능해졌고, time.Time·reflect.Value 가 그렇게 바뀌었습니다.

실행 검증

같음(==)의 정리 1.0

Go 1 전에는 구조체·배열의 같음이 정의되지 않아 map 키로 쓸 수 없었고, 반대로 함수와 map 은 같음이 있었습니다 — 클로저 둘은 언제 같은가, map 의 같음은 내용이 아니라 포인터 비교였다는 문제가 있었습니다.

실행 검증

같음 — 없어진 쪽

함수와 map 의 같음은 nil 과의 비교만 남았습니다. 슬라이스의 같음은 여전히 없습니다.

실행 검증

3장 퀴즈

Q. i, sa[i] = 1, 2 를 돌리면 sa 의 몇 번째 원소가 2 가 됩니까? 그리고 rune 이 만들어진 진짜 까닭은?

A. sa[0] 입니다. 왼쪽의 색인 sa[i] 는 대입 전에(아직 i 가 0 일 때) 평가됩니다. rune 은 64비트 기계에서 int 를 64비트로 키울 수 있게, 코드 포인트를 int 에서 떼어 내려고 만들었습니다.

문서 근거

go 명령 — makefile 없이 1.0

Go 1 은 패키지를 받고 짓고 설치하는 go 명령을 내놓았습니다. 의존 관계와 빌드 조건을 makefile 이 아니라 Go 소스에서 찾으므로, 대부분의 프로그램은 makefile 이 필요 없어졌습니다.

이 덱의 모든 캡처가 쓰는 go run . 이 그 후손입니다. 다만 "소스에서 의존을 찾는다" 가 버전까지 적는 모듈로 자라기까지는 1.11 을 기다려야 했습니다(5부).

문서 근거

처음으로, 받아서 까는 배포판 1.0

Go 1 과 함께 온 가장 큰 변화 가운데 하나는 미리 지어 둔 배포판입니다. 발표 글은 리눅스·FreeBSD· 맥 OS X, 그리고 윈도용 바이너리 배포판을 알립니다.

이 기계(안드로이드)는 그 목록에 없습니다 — 안드로이드 지원은 1.4 에서 옵니다(3부).

A. "package utf8 is not in std" 로 거절됩니다. 당시에는 go fix 가 unicode/utf8 로 import 경로를 고쳐 썼습니다(표준 저장소 안에 남은 패키지라서).

Go 1 과 약속

— 그리고 1.0.x

Go 1 발표

The driving motivation for Go 1 is stability for its users.

"Go 1 을 이끈 동기는 쓰는 사람들을 위한 안정입니다."

발표 글은 앞으로의 호환성도 안정의 일부라고 말합니다 — 1.1, 1.2 같은 갱신이 나와도 Go 1 에서 컴파일되는 코드는 몇 가지 예외를 빼고 계속 컴파일되고 돌아가야 한다는 것입니다.

역사 근거

호환성 약속 — 무엇을 약속하나

  • 소스 수준의 호환입니다. 컴파일된 패키지의 이진 호환은 약속하지 않습니다 — 새 판에서는 다시 컴파일해야 합니다.
  • API 는 자랄 수 있습니다(새 패키지·새 기능). 다만 기존 Go 1 코드를 깨는 방식으로는 아닙니다.
  • 언젠가 Go 2 명세가 나올 수 있지만 그때까지는 지금 되는 프로그램이 계속 되어야 합니다.

호환성 약속 — 약속하지 않는 것

문서는 "어떤 변경도 어떤 프로그램도 깨지 않는다" 고는 약속하지 않습니다. 예외를 미리 적어 둡니다.

  • 보안 — 명세나 구현의 보안 문제를 고치려면 깨야 할 수 있습니다.
  • 명세에 없던 동작, 명세의 모순, 명세가 정하지 않은 동작에 기댄 코드.
  • 명세의 버그, 구현의 버그를 고치는 일.
  • 점 가져오기(import .)나 구조체 리터럴의 필드 이름 생략처럼, 라이브러리가 자라면 깨질 수 있는 쓰임.

이 덱의 절반은 이 예외들을 어떻게 다뤘는지의 이야기입니다 — GODEBUG(0부), 언어 버전 지시자(0부), 그리고 10부의 "호환성 약속의 비용과 이득".

5장 퀴즈

Q. Go 1 호환성 약속은 컴파일해 둔 패키지 파일(.a)을 새 판에서 그대로 쓸 수 있다는 뜻입니까?

A. 아닙니다. 약속은 소스 수준의 호환입니다. 문서는 판 사이의 이진 호환을 보장하지 않으며, 새 판에서는 다시 컴파일해야 한다고 적습니다.
