탄생 이전 — 구글에서의 설계와 그 계보

무엇이 불편했나 · 세 사람과 첫 두 해 · C·Pascal·CSP 의 계보 · 설계 원칙 · 일부러 뺀 것

이 부에서 할 일

Go 는 새 기능을 뽐내려고 만든 언어가 아니라, 큰 회사의 서버 코드를 짜는 일이 너무 힘들어져서 만든 언어입니다. 이 부는 그 "왜" 를 설계자들의 글로 따라가고, 그 원칙이 지금의 컴파일러에 어떻게 남아 있는지 돌려 봅니다.

  • 무엇이 불편했나 — 컴파일 시간, 의존 관계, 언어 선택의 딜레마
  • 2007년 화이트보드에서 2009년 공개까지
  • 계보 — 문법은 C, 선언과 패키지는 Pascal 계열, 동시성은 CSP 계열
  • 원칙 — 의존은 오류, 이름이 곧 공개 범위, 상속 대신 합성, 오류는 값, 도구가 모양을 정한다
  • 처음에 일부러 뺀 것 — 제네릭·예외·단언·암묵 변환

이 부의 캡처는 모두 1.27.1 의 동작입니다. 옛 컴파일러가 아니라, 처음의 원칙이 지금도 그대로인지를 봅니다.

문서 근거

Go 가 노린 조합

해석되는 동적 언어의 쉬움과, 정적 타입·컴파일 언어의 효율·안전을 한 언어에 담는 것. 그리고 네트워크와 다중 코어에 맞는 언어, 큰 실행 파일도 한 컴퓨터에서 몇 초 안에 짓는 언어.

FAQ 는 이 목표 때문에 나온 결정을 이렇게 꼽습니다 — 계층이 아니라 조합으로 쌓는 타입 체계, 동시성과 가비지 컬렉션, 의존 관계의 엄격한 명세. 라이브러리나 도구로는 풀 수 없어서 새 언어가 필요했다는 것입니다.

문서 근거

C 와 C++ 의 의존 관계

2012년 발표문 "Go at Google" 은 가장 큰 고통으로 의존 관계와 빌드 시간을 듭니다. 발표문이 적은 숫자를 그대로 옮깁니다.

사례발표문의 서술
1984년 ps.c<sys/stat.h> 가 전처리 끝까지 37번 포함 — 36번은 읽고 버린다
2007년 구글의 큰 C++ 바이너리파일 약 2천 개, 이어 붙이면 4.2 MB — #include 를 펼치자 컴파일러 입력이 8 GB 를 넘었다. 원본 한 바이트에 2000바이트
그 바이너리의 빌드옛 분산 빌드로 45분, 발표 당시 27분

역사 근거

Plan 9 이 먼저 보인 길

발표문은 해결의 실마리를 Plan 9 의 C 라이브러리에서 찾습니다. 헤더 파일이 다른 헤더를 포함하지 못하게 하고, 모든 #include 를 맨 위 C 파일에 한 번씩만 적게 했습니다.

  • 의존을 정확한 차례로 한 번씩 적어야 하는 수고가 들었지만,
  • 의존이 몇 개든 각 헤더는 컴파일마다 딱 한 번 읽혔고,
  • 그 결과 컴파일이 훨씬 빨랐다는 것입니다.

Go 는 이 규율을 사람의 수고가 아니라 언어 규칙으로 옮깁니다(4장).

역사 근거

1장 퀴즈

Q. 2007년의 구글 C++ 빌드에서 원본 1 MB 는 #include 를 펼친 뒤 대략 얼마가 되었다고 발표문은 적습니까?

A. 원본 한 바이트에 2000바이트이므로 약 2 GB 입니다(4.2 MB → 8 GB 넘게). 컴파일 시간을 잡아먹은 것은 코드의 양이 아니라 같은 헤더를 거듭 읽는 일이었습니다.

문서 근거

처음부터 구현이 둘

명세 초안만 보고 GCC 프런트엔드를 따로 짠 사람이 있었다는 것은, 처음부터 명세가 구현보다 앞선 언어였다는 뜻입니다. Go 1 은 명세와 함께 두 컴파일러 모음(gc 와 gccgo)을 구현으로 내놓았습니다.

이 덱에서 — 릴리스 노트마다 "Status of gccgo" 절이 이어집니다. gc 가 Go 로 다시 쓰여 자기 자신을 짓게 된 것은 1.5 입니다(4부).

문서 근거

이름이 타입보다 먼저

C 프로그래머가 놀라는 것 하나는 선언 문법이 C 보다 Pascal 쪽이라는 점입니다 — 이름이 먼저, 타입이 뒤, 그리고 키워드가 조금 더 있습니다. 함수 타입도 왼쪽에서 오른쪽으로 읽힙니다.

동시성은 호어의 CSP 에서 온 생각을 씁니다. 고루틴이 채널로 값을 주고받으며 협력합니다. 아래는 Go 명세가 완전한 예제 패키지로 싣는 소수 체 — 걸러 내는 고루틴의 사슬 — 를 줄여 쓴 것입니다.

3장 퀴즈

Q. func twice(f func(int) int) func(int) int 를 C 식 선언과 견주면 무엇이 편합니까?

A. 이름 → 매개변수 → 결과 차례로 왼쪽에서 오른쪽으로 읽힙니다. C 의 함수 포인터 선언처럼 안에서 밖으로 풀어 읽을 필요가 없습니다.

설계 원칙

원칙마다, 지금의 컴파일러가 그대로 지키는지 돌려 본다

덜 치고, 서로 겹치지 않게

  • 덜 치기 — 전방 선언도 헤더도 없고, 모든 것은 한 번만 선언합니다. := 가 반복을 줄입니다.
  • 타입 계층이 없다 — 타입은 그냥 있을 뿐, 서로의 관계를 선언하지 않습니다.
  • 직교성 — 메서드는 어느 타입에나 달 수 있고, 구조체는 데이터를, 인터페이스는 추상을 맡습니다.

문서 근거

키워드 25개

발표문은 문법이 작고 규칙적이라 타입 정보나 심볼 표 없이도 파싱된다고 적습니다. 키워드는 25개 — C99 37개, C++11 84개와 견줍니다. 지금 몇 개인지 표준 라이브러리의 go/token 으로 셉니다.

제네릭(1.18)도 이터레이터(1.23)도 키워드를 하나도 더하지 않았습니다.

실행 검증

쓰지 않는 의존은 오류

발표문이 꼽은 첫 단계: 쓰지 않는 import 는 경고가 아니라 컴파일 오류입니다. 의존 목록이 늘 정확하니, C 처럼 "지워도 되는지 모르는 #include" 가 쌓이지 않습니다.

실행 검증

이름의 첫 글자가 공개 범위

public·private 키워드 대신 이름 자체가 말합니다 — 첫 글자가 대문자면 패키지 밖에서 보이고, 아니면 안 보입니다.

실행 검증

상속 대신 합성

메서드는 어떤 타입에나 달 수 있지만 서브클래스 같은 타입 기반 상속은 없습니다. 발표문은 타입 계층이 지나치게 쓰였다고 보고 한 걸음 물러섰다고 적습니다. 인터페이스는 메서드 집합일 뿐이고, 만족은 선언하지 않습니다.

실행 검증

오류는 값

관례적인 예외 기능이 없습니다. 오류는 Error() string 을 가진 인터페이스 값이고, 여느 값처럼 돌려주고 검사합니다. panic·recover 는 일부러 거추장스럽게 두었다고 발표문은 적습니다.

뒤의 이야기 — 오류 감싸기(%w, errors.Is)는 1.13(5부), 오류 처리 문법을 더하자는 제안들의 끝은 9부.
실행 검증

암묵적인 수 변환은 없다

C 의 "보통 산술 변환" 은 편하지만 헷갈리고, 컴파일러 구현도 복잡하게 만듭니다. Go 는 서로 다른 수 타입을 섞으면 반드시 변환을 적게 합니다.

실행 검증

모양은 도구가 정한다 — gofmt

문법이 파싱하기 쉬우니 도구를 쓰기 쉽고, 그 가운데 가장 알려진 것이 gofmt 입니다. 처음부터 모든 Go 코드를 gofmt 의 모양으로 보아 왔기에 Go 프로그램에는 모두에게 익숙한 스타일이 하나 있다고 발표문은 적습니다.

모양이 흐트러져도 컴파일은 됩니다(go run . 은 0 1 2 를 찍습니다) — 모양은 규칙이 아니라 도구의 몫입니다.

실행 검증

4장 퀴즈

Q. import "os" 를 적고 쓰지 않으면 왜 경고가 아니라 오류입니까? 발표문의 논리로 답하십시오.

A. 의존 목록이 늘 정확해야 빌드가 필요 없는 것을 읽지 않고, 도구가 의존을 계산할 수 있기 때문입니다. 경고로 두면 C 의 #include 처럼 "지워도 되는지 모르는" 의존이 쌓입니다.

처음에 일부러 뺀 것

"기능 X 는 왜 없나" 에 대한 답

기능 X 는 왜 없나

FAQ 의 답은 한결같습니다 — 모든 언어는 새 기능을 담고 누군가 좋아하는 기능을 뺍니다. Go 는 편한 프로그래밍, 빠른 컴파일, 개념의 직교성, 동시성·GC 같은 기능의 지원을 눈여겨 설계했고, 빠진 것이 있다면 그것이 맞지 않거나 컴파일 속도·설계의 명료함을 해치기 때문이라는 것입니다.
