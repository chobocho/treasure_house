Go 1.26 한눈에

노트는 변화 대부분이 툴체인·런타임·라이브러리의 구현에 있다고 적었습니다. 그래도 언어가 두 군데 바뀌었고, 발표 글은 이것을 "언어 문법과 타입 체계의 의미 있는 다듬기 두 가지" 라고 불렀습니다. 이 장의 모든 사실은 받아 둔 문서와 1.27.1 의 실행에서 옵니다(2026-09 기준).

문서 근거

new(expr) — 초깃값을 주는 new 1.26

왜 — 내장 함수 new 는 새 변수를 만들어 주소를 돌려줍니다. 지금까지 인자는 타입뿐이어서 변수는 늘 0 값으로 시작했습니다. 1.26 부터는 인자가 식이어도 되고, 그 값이 새 변수의 초깃값이 됩니다. Alan Donovan 의 글은 이것이 십 년 넘게 논의된 빈틈이었고 가장 인기 있던 언어 변경 제안 가운데 하나를 해결했다고 적었습니다.

관문은 go 줄 — 컴파일러의 타입 검사기는 new(식) 을 만나면 go1.26 을 요구합니다 (1.27.1 소스 cmd/compile/internal/types2/builtins.go 의 버전 검사). 타입을 준 new(int) 는 go 1.25 에서도 그대로 통과해서, 오류 목록에 9행이 없습니다. 이 방식의 원리는 0부에 있습니다.
실행 검증

선택적 필드 — 도우미 함수가 사라지다 1.26

왜 — encoding/json 이나 프로토콜 버퍼는 "값이 없음" 을 포인터 *T 의 nil 로 나타냅니다. 이런 필드를 식 하나로 채우려고 사람들은 newInt 같은 도우미를 써 왔고, proto API 는 아예 proto.Int64·proto.String 을 제공했습니다. 글은 "Go 1.26 이 이런 도우미를 모두 필요 없게 만든다" 고 적었습니다. 노트의 예도 같은 장면입니다 — 나이를 모르면 nil, 알면 new(yearsSince(born)).

나이는 Go 의 공개일에서 1.26 의 날까지를 셌습니다. 두 날짜는 2부(공개일)와 이 장의 표지(1.26 발표일)에 있습니다.

실행 검증

new(x) 는 x 를 가리키지 않는다 1.26

왜 — new(식) 은 "새 변수" 를 만든다는 원래 뜻을 그대로 지킵니다. 그래서 new(x) 는 x 의 주소가 아니라 x 의 값을 복사해 둔 새 변수의 주소입니다.

함정 — *q = 3 은 x 를 바꾸지 않습니다. 무형 상수는 기본 타입을 얻으므로 new(1 << 70) 은 int 를 넘쳐 거절되고, 타입이 없는 nil 은 인자가 될 수 없습니다. 두 오류는 1.27.1 타입 검사기의 new 처리에서 그대로 나온 문구입니다.
실행 검증

자기 자신을 가리키는 제약 1.26

왜 — 제네릭 타입이 자기 타입 매개변수 목록에서 자기 자신을 가리키지 못하던 제한이 풀렸습니다. 노트의 예는 type Adder[A Adder[A]] interface { Add(A) A } — "나와 같은 종류의 타입으로만 인스턴스화하라" 는 제약입니다. 노트는 이 변화가 제약을 더 강하게 만들 뿐 아니라 타입 매개변수에 관한 명세 규칙도 "아주 조금" 단순하게 한다고 적었습니다.

go 줄로 갈리지 않는 변화 — new(식) 과 달리 이 규칙에는 타입 검사기의 go1.26 버전 검사가 없습니다(1.27.1 의 types2 에서 go1.26 검사는 new(식) 하나뿐). 그래서 go 1.25 로 내려도 1.27.1 은 받아 줍니다. 옛 컴파일러의 거절은 노트의 "Previously … was not allowed" 로만 확인됩니다. 제약의 바탕은 6부에 있습니다.
실행 검증

타입 검사기 안쪽 — 순환 검출을 다시 짜다 1.26

왜 — Mark Freeman 의 글은 1.26 에서 타입 검사기의 "타입 구성(type construction)" 부분을 크게 고쳤다고 소개합니다. 사용자 쪽에서는 "난해한 타입 정의를 즐기는 사람이 아니라면" 관찰할 수 있는 변화가 없고, 목적은 모서리 경우를 줄여 앞으로의 개선을 준비하는 것이었습니다.

  • 타입 검사기는 AST 를 돌며 타입마다 내부 표현을 만듭니다. 타입을 완성하려면 그것이 기대는 타입이 먼저 완성돼야 하므로 깊이 우선입니다.
  • 재귀 타입(type Node struct { next *Node })과 배열 크기처럼 값이 타입에 끼는 곳에서 "미완성" 타입이 새어 나갈 수 있습니다.
  • 새 방식은 미완성 값을 만나면 특별한 invalid 피연산자를 돌려주고 순환 오류를 알립니다. 같은 모양을 모든 경우에 적용했습니다.
  • 1.26 전에는 더 복잡한 알고리즘과 경우별 순환 검출을 썼고 "늘 동작하지는 않았다" 고 합니다. 새 방식은 (난해한) 컴파일러 패닉 여럿 — 이슈 #75918, #76383, #76384, #76478 등 — 을 없앴습니다.

바로 앞 장의 자기 참조 제약 완화와 같은 릴리스입니다. 노트가 둘을 직접 잇지는 않으므로, 이 덱도 둘을 인과로 묶지 않습니다.

역사 근거

go fix 가 다시 태어나다 — 현대화 도구 1.26

왜 — 노트는 "유서 깊은(venerable)" go fix 가 완전히 새로 짜여 Go 의 현대화 도구(modernizer)들의 집이 됐다고 적었습니다. go vet 과 똑같은 분석 틀 위에 서 있어서, vet 의 분석기가 진단 대신 고침을 제안하고 적용할 수 있습니다. 옛 fixer 들은 모두 낡아 지워졌습니다.

go 1.20 모듈에서는 1.21 의 max 와 1.22 의 정수 range 를 쓰면 안 되므로 그 두 고침이 빠지고, 1.18 의 strings.Cut·any 만 남습니다. 글이 말한 대로 도구가 파일의 실효 Go 버전을 묻기 때문입니다.

한 번으로 끝나지 않는다 — 첫 캡처의 clamp 는 max 만 받았습니다. 글은 minmax 가 먼저 max 를, 다음 실행에서 min 을 제안한다며 go fix 를 고정점에 이를 때까지 — 보통 두 번 — 돌리라고 권합니다. 이 캡처는 매번 원본의 사본에서 돌기 때문에 첫 실행만 보여 줍니다.

go fix 의 분석기들 1.26

왜 — go fix 는 go build·go vet 처럼 패키지 패턴을 받고, 성공하면 조용히 소스를 고칩니다. 기본은 모든 분석기를 돌리고, -any 처럼 이름으로 하나만 켜거나 -any=false 로 하나만 끌 수 있습니다. 목록은 go tool fix help 입니다.

1.27 노트는 atomictypes·embedlit·slicesbackward·unsafefuncs 가 새로 들어왔다고 적었으므로, 1.26 의 목록은 이것보다 넷이 적습니다. 목록 안의 newexpr 이 바로 이 장의 new(식) 을 위한 것이고, forvar 는 1.22 의 루프 변수 변경(7부) 뒤에 남은 x := x 를 지웁니다.

왜 지금 현대화 도구인가

Alan Donovan 의 글이 밝힌 동기는 뜻밖에도 LLM 입니다.

  • 1.18 의 제네릭 이후 언어와 라이브러리가 빠르게 바뀌면서, maps.Keys 한 번이면 될 흔한 루프들을 단순하게 만들 기회가 많아졌습니다.
  • 2024년 12월, LLM 코딩 도우미가 학습한 옛 Go 코드의 문체를 그대로 따르고, 새 방식을 쓰라고 해도 거부하거나 그 기능이 없다고 우기기까지 한다는 것을 알게 됐다고 합니다.
  • 그래서 앞으로의 모델이 새 관용구로 학습하도록, 공개된 Go 코드 전체에 새 관용구가 반영되게 하는 것이 목표가 됐습니다.
  • 현대화 도구는 gopls 에도 들어 있어 입력하는 동안 바로 알려 줍니다. 제안 심사 모임은 이제 언어·라이브러리 변경마다 현대화 도구가 함께 와야 하는지도 검토합니다.

go vet 과 go fix 는 구현이 거의 같아졌고, 차이는 기준뿐입니다 — vet 의 분석기는 오탐이 적어야 하고, fix 의 분석기는 정확성·성능·문체에서 퇴보 없이 적용할 수 있어야 합니다.

newexpr — 도우미를 new(식) 으로 1.26

왜 — go fix 의 newexpr 은 newInt 같은 "new 닮은" 함수를 알아보고, 본문을 return new(x) 로 바꾸고 같은 패키지든 import 하는 패키지든 모든 호출을 new(식) 으로 바꾸자고 제안합니다. 너무 이른 사용을 막으려고 go.mod 가 go 1.26 이상이거나 파일에 //go:build go1.26 이 있을 때만 고칩니다.

도우미 자체는 지우지 않고 //go:fix inline 을 달아 둡니다 — 다른 모듈의 호출자도 다음 장의 인라이너로 따라올 수 있게. 글은 호출이 모두 사라진 도우미는 지워도 되지만 공개 API 라면 남겨야 한다고 덧붙였습니다.

실행 검증

//go:fix inline — 옛 API 에서 새 API 로 1.26

왜 — 소스 수준 인라이너는 호출을 피호출 함수의 본문으로 바꾸되, 인자를 매개변수 자리에 대입해 소스에 영구히 남깁니다. 패키지 작성자가 옛 함수에 //go:fix inline 을 달면, 사용자가 go fix 를 돌릴 때 호출이 새 API 로 옮겨집니다. 글은 이것을 "셀프서비스" 현대화 도구의 첫 열매라고 불렀습니다.

글의 가상 oldmath 예를 실제 모듈로 옮긴 것입니다. 상수(Pi)에도 같은 지시문이 통합니다. 글에 따르면 인라이너는 약 7,000줄의 코드이고, Google 사내 저장소에서 이미 18,000개 넘는 변경 목록(changelist)을 준비하는 데 쓰였습니다.

함정 — defer 를 쓰는 함수는 호출을 없애면 defer 가 너무 늦게 돕니다. gopls 는 함수 리터럴로 감싸지만, go fix 의 분석기는 방침상 그런 인라인을 거절합니다.

go mod init 의 go 줄 — 노트와 1.27.1 이 다르다 1.26

왜 — 노트는 1.N.X 툴체인의 go mod init 이 go.mod 에 go 1.(N-1).0 을 적는다고 했습니다. 예로 1.26 과 그 마이너 릴리스는 go 1.25.0 을, 1.26 의 RC 는 go 1.24.0 을 씁니다. 지원 중인 Go 버전들과 호환되는 모듈을 만들도록 권하려는 것이고, 더 조절하려면 뒤이어 go get go@버전 을 쓰라고 합니다.

문서와 실행이 어긋난다 — 규칙대로면 1.27.1 은 go 1.26.0 을 적어야 하는데, 캡처는 go 1.27.1 입니다. 설치된 1.27.1 소스의 modload.CreateModFile 도 로컬 툴체인 버전(gover.Local())을 그대로 씁니다. 1.27 노트와 받아 둔 문서에는 이 동작을 되돌렸다는 말이 없어서, 이유는 미확인입니다. 이 덱은 노트를 고쳐 쓰지 않고 둘을 나란히 둡니다.

go tool doc 이 사라지다 1.26

왜 — 1.26 은 cmd/doc 와 go tool doc 을 지웠습니다. go doc 이 같은 플래그와 인자를 받고 같은 동작을 하므로 대체합니다.

Green Tea GC 가 기본값으로 1.26

왜 — 1.25 에서 실험이었던 Green Tea 가비지 컬렉터가 의견을 반영한 뒤 기본으로 켜졌습니다. 작은 객체를 표시·스캔할 때의 지역성과 CPU 확장성을 높인 설계입니다. 노트는 GC 를 많이 쓰는 실제 프로그램에서 GC 오버헤드가 "10–40%" 줄 것으로 보고, 새 amd64 CPU(Intel Ice Lake, AMD Zen 4 이후)에서는 벡터 명령으로 "10% 정도" 더 줄 것으로 예상했습니다.

시간은 재지 않았다 — 두 실행의 출력은 같습니다. 이 덱은 성능을 이 기계에서 재지 않으므로(0부), 여기서 보이는 것은 "옛 수집기로 되돌리는 스위치가 1.27.1 에도 있다" 는 사실뿐입니다. 노트는 이 스위치가 1.27 에서 지워질 것으로 예상했지만, 1.27.1 의 internal/goexperiment 에는 아직 greenteagc 가 있습니다(2026-09 기준).

Green Tea 는 무엇을 바꿨나

Michael Knyszek 과 Austin Clements 의 글(1.25 때 실험으로 나오며 쓴 글)이 설명하는 요점입니다.

  • 옛 표시 알고리즘은 포인터를 따라 힙 이곳저곳을 뛰어다니는 "그래프 범람(graph flood)" 이라 캐시를 살리지 못합니다. 글은 주 메모리가 캐시보다 최대 100배 느릴 수 있다고 적었습니다. 글은 이것을 "마이크로아키텍처의 재앙" 이라는 제목으로 다룹니다.
  • Green Tea 는 객체가 아니라 페이지 단위로 일을 모읍니다. 한 페이지에 스캔할 객체가 쌓이기를 기다렸다가 한 번에 훑습니다.
  • 벤치마크 모음에서 GC CPU 비용이 벡터 가속 없이도 10%–40% 줄었고, 10% 감소가 가장 흔한 값이었다고 합니다. 한 페이지에 객체 하나씩만 스캔하게 되는 작업량은 오히려 나빠질 수 있다고도 적었습니다.
  • 그때의 계획은 "1.26 에서 기본값, GOEXPERIMENT=nogreenteagc 로 끌 수 있게" 였고, 앞 장의 캡처가 그대로입니다.
역사 근거

힙 시작 주소의 무작위화 1.26

왜 — 64비트 플랫폼에서 런타임이 시작할 때 힙의 기준 주소를 무작위로 정합니다. cgo 를 쓰는 프로그램에서 공격자가 메모리 주소를 예측해 취약점을 이용하기 어렵게 하려는 보안 강화입니다. 빌드할 때 GOEXPERIMENT=norandomizedheapbase64 로 끌 수 있고, 이 옵트아웃은 앞으로 지워질 예정입니다.

고정 힌트 값은 1.27.1 의 runtime/malloc.go 에서 읽었습니다 — 대부분의 64비트는 0x00c0<<32, arm64 는 0x0040<<32. 그래서 "Go 의 힙 주소는 0xc000… 으로 시작한다" 는 오래된 경험칙은 1.26 부터 맞지 않습니다.

고루틴 누수 프로파일 — 1.26 의 실험 1.26

왜 — 막힌 채 다시는 깨어날 수 없는 고루틴을 GC 로 찾아냅니다. 고루틴 G 가 동시성 기본 요소 P 에서 막혀 있는데 P 가 실행 가능한 어떤 고루틴에서도 닿을 수 없다면, G 는 영원히 깨어나지 못합니다. 1.26 에서는 GOEXPERIMENT=goroutineleakprofile 로 켜는 실험이었고, 노트는 1.27 에서 기본으로 켜는 것이 목표라고 했습니다. Uber 의 Vlad Saioc 이 기여했습니다.

왜 — 1.26 에는 명시적으로 켜야만 보이는 실험이 둘 더 있습니다. GOEXPERIMENT=simd 의 simd/archsimd 는 아키텍처별 SIMD 연산(지금은 amd64 의 128·256·512비트 벡터)을, GOEXPERIMENT=runtimesecret 의 runtime/secret 은 비밀을 다룬 뒤 레지스터·스택·새 힙 할당 같은 임시값을 지우는 장치를 줍니다.

켰는데 비밀 모드가 아니다 — 노트는 linux 의 amd64·arm64 를 지원한다고 했고, 1.27.1 소스의 Do 는 GOOS/GOARCH 가 정확히 linux/amd64·linux/arm64 일 때만 비밀 모드로 들어가고 나머지에서는 f 를 그냥 부릅니다. 이 기계는 android/arm64 라 컴파일은 되지만 보호는 없습니다. simd/archsimd 는 amd64 전용이라 여기서 돌리지 못했습니다.

1.27 에서 지울 GODEBUG 의 예고 1.26

왜 — GODEBUG 설정은 영원하지 않습니다. 1.26 노트는 1.22·1.23 에서 생긴 설정들을 다음 큰 릴리스(1.27)에서 지운다고 미리 알렸습니다 — 1.27 부터는 설정이나 go 줄과 상관없이 새 동작입니다.

Go 1.26 퀴즈

Q. x := 1; p := new(x); x = 5 뒤 *p 는 얼마입니까? 그리고 같은 파일을 go 1.25 모듈에서 컴파일하면 어떻게 됩니까? 마지막으로, go 1.20 모듈에서 go fix 가 if x < 0 { x = 0 } 을 max 로 바꿔 줍니까?

A. 1 입니다 — new(x) 는 x 의 값을 복사한 새 변수를 가리킵니다. go 1.25 에서는 "requires go1.26 or later" 로 컴파일이 거절됩니다. 그리고 바꿔 주지 않습니다 — 현대화 도구는 파일의 Go 버전을 보고, max 는 1.21 의 기능이라 go 1.20 모듈에서는 제안하지 않습니다.
