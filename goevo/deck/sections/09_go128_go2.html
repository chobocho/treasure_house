Toward Go 2 — 문제를 먼저

2017-07-13, 러스 콕스는 GopherCon 에서 Go 2 를 함께 계획하자고 청합니다. 목표는 2007년과 같다고 말합니다 — 두 가지 규모, 곧 수많은 서버와 주고받는 운영 규모와, 느슨하게 협력하는 많은 엔지니어의 큰 코드베이스라는 개발 규모를 다루게 하는 것. Go 2 의 목표는 "Go 가 규모에서 실패하는 가장 큰 지점들을 고치는 것" 이었습니다.

그래서 해결책보다 먼저 경험 보고 — 무엇이 실제로 아팠는지 — 를 모으자고 했습니다.

역사 근거

초안 설계와 선정 기준

2018-08-28 의 글은 바로 전날의 기여자 모임에서 오류 처리와 제네릭의 초안 설계를 먼저 보였다고 적고, 그것을 모두에게 공개합니다. 같은 해 11월의 글은 제안이 적어도 갖춰야 할 세 가지를 적습니다.

  • 많은 사람에게 중요한 문제를 다룰 것
  • 나머지 모두에게 주는 영향이 작을 것
  • 분명하고 잘 이해된 해법이 있을 것

셋째 조건의 예로 글은 제네릭을 듭니다 — 문제는 크지만 아직 분명한 해법이 없어 설계로 돌아가야 한다고. 그 해법은 1.18 에서 옵니다(6부).

역사 근거

지금의 제안 과정

단계하는 일
1제안자가 짧은 이슈를 연다(아직 설계 문서는 필요 없다)
2이슈 논의가 셋 가운데 하나로 가른다 — 받아들임, 거절, 설계 문서 요청
3설계 문서로 세부를 풀고 논의에서 나온 걱정에 답한다
4마지막 논의로 받아들임 또는 거절

받아들인 뒤의 구현은 여느 기여와 같습니다. 언어 변경은 따로 정한 틀을 따릅니다.

문서 근거

"The answer is never."

2023-08-14 의 글은 Go 1 호환성 문서의 한 구절 — "언젠가 Go 2 명세가 나올 수도 있다" — 에 답합니다.

The answer is never. Go 2, in the sense of breaking with the past and no longer compiling old programs, is never going to happen.

"답은 '결코' 입니다. 과거와 단절하고 옛 프로그램을 더는 컴파일하지 않는다는 뜻의 Go 2 는 결코 오지 않습니다." 같은 글은 2017년에 시작한 큰 개정이라는 뜻의 Go 2 는 이미 일어났다고 덧붙입니다.

대신 호환성에 더 힘을 싣습니다 — 같은 글이 1.21 에서 GODEBUG 를 넓힌 이야기를 합니다(0부, 7부).

역사 근거

오류 처리 문법 — 멈추기로 하다

제네릭과 함께 Go 2 의 두 기둥이던 오류 처리 문법은 여러 번 제안되고 거둬졌습니다. 2025-06-03 의 글은 결론을 적습니다.

For the foreseeable future, the Go team will stop pursuing syntactic language changes for error handling.

"당분간 Go 팀은 오류 처리를 위한 문법 변경을 더 추진하지 않습니다."

그래서 1부의 오류 값 예제는 지금도 Go 의 오류 처리 그대로입니다.

A. 제네릭입니다. 문제는 크지만 해법이 분명하지 않아 설계로 돌려보냈고, 타입 매개변수로 1.18 에 들어왔습니다.

Go 1.28 — 초안

초안 노트는 2027-02 출시를 예상합니다 · 2026-09 기준

Go 1.28 초안 한눈에

초안 노트에는 아직 언어 변경이 없고, 도구(vet)·부트스트랩·표준 라이브러리의 작은 변경들이 있습니다.

문서 근거

아직 없는 판을 지금의 go 로

go.mod 가 go 1.28 을 요구하면, 1.27.1 은 모듈을 읽기를 거절합니다. 툴체인은 자기보다 새 go 줄을 선언한 모듈을 싣지 않습니다.

GOTOOLCHAIN 이 local 이 아니면 go 는 새 툴체인을 받으러 갑니다 — 이 기계에서는 받을 판이 없습니다(0부).

실행 검증

새 API 셋 1.28

초안이 더하는 API — url.MustParse, http.MethodQuery, FlagSet.All 이터레이터 — 를 1.27.1 로 컴파일합니다. 셋 다 "없다" 는 답은 1.27.1 에 아직 없다는 증거이고, 1.28 에 온다는 것은 초안 노트의 말입니다.

실행 검증

EncodedLen 이 넘치면 1.28

base64·base32 의 EncodedLen 은 결과가 int 를 넘치면 지금은 음수를 돌려줍니다. 초안은 이를 panic 으로 바꾼다고 적습니다.

함정 — 음수 길이로 버퍼를 만들면 그 자리에서 다른 panic 이 납니다. 1.28 은 원인 자리에서 멈추게 합니다.
실행 검증

프록시 변수 — 소문자가 먼저 1.28

초안은 ProxyFromEnvironment 가 http_proxy·https_proxy·no_proxy 를 대문자 쪽보다 먼저 보게 바꾼다고 적습니다(둘이 다른 값일 때).

1.28 이 나오면 같은 실행이 lower.example 을 고를 것입니다(초안의 말). 프로그램은 네트워크에 나가지 않습니다.

실행 검증

vet 의 새 분석기 1.28

scannererr 는 bufio.Scanner 의 Scan 루프 뒤에 오류를 보지 않는 코드를, sqlrowserr 는 sql.Rows.Next 루프 뒤를 잡습니다. 루프가 끝난 까닭이 "다 읽음" 인지 "오류" 인지 가르지 못하는 흔한 실수입니다 — bufio.Scanner 의 이 함정은 3부에서 보았습니다.

실행 검증

작은 변화들 1.28

패키지초안이 적은 것
embed · testing/fstest파일의 ReadAt 이 끝이나 그 너머에서 io.EOF 를 돌려준다(io.ReaderAt 의 약속대로)
net/http오래전 낡은 Transport.CancelRequest 는 아무 일도 하지 않는다. HTTP/2 서버는 할 일 없는 연결의 고루틴을 내려놓는다
testing/synctest · go/typessynctest.Subtest, Scope.Objects

그 밖에 부트스트랩에 1.26.0 이상이 필요하고, go/parser·net·syscall 에 작은 변경이 있습니다(개관 표).

문서 근거

2장 퀴즈

Q. 1.27.1 로 url.MustParse 를 부르는 프로그램을 컴파일하면 어떻게 되고, go.mod 를 go 1.28 로 올리면 어떻게 됩니까?

A. 앞의 것은 "undefined: url.MustParse" 컴파일 오류입니다. 뒤의 것은 컴파일까지 가지도 못하고 "go.mod requires go >= 1.28 (running go 1.27.1; GOTOOLCHAIN=local)" 로 거절됩니다.
