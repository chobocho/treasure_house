Go 1.18 – 1.20 — 제네릭이 들어온 세 릴리스

제네릭 · 퍼징 · 작업 공간 · 메모리 상한 · atomic 타입 · 문서 주석 · 여러 오류 감싸기 · 커버리지 · PGO 미리보기

이 부에서 할 일

Go 1 이후 가장 큰 언어 변경, 타입 매개변수가 1.18 에 들어옵니다. 발표 글은 그 설계의 일부가 "Go 를 처음 공개한 십여 년 전" 에 시작됐다고 적습니다. 그 뒤 두 릴리스는 제네릭을 다듬고, 런타임과 도구를 손봅니다.

  • 1.18 — 제네릭(왜·어떻게·무엇이 빠졌나), 퍼징, 작업 공간, 빌드 정보, net/netip
  • 1.19 — 메모리 모델 개정, atomic 타입, GOMEMLIMIT, 문서 주석 문법, unix 빌드 제약
  • 1.20 — 슬라이스→배열 변환, errors.Join, 프로그램 커버리지, PGO 미리보기, crypto/ecdh
읽는 법 — 이 시기의 언어 변경은 go.mod 의 go 줄이 막습니다. 그래서 타입 매개변수 (1.17 ↔ 1.18)와 슬라이스→배열 변환·unsafe.String(1.19 ↔ 1.20)은 같은 소스의 go 줄만 바꿔 전과 후를 보입니다(0부). GODEBUG 짝도 넷 있습니다(0부).

Go 1.18 한눈에

노트는 "a significant release" 라고 소개하고, 발표 블로그는 "our biggest change ever to the language" 라고 적었습니다. 제네릭·퍼징·작업 공간에 이어 네 번째 표제가 "최대 20% 성능 향상" 이었을 정도입니다.

문서 근거

왜 제네릭인가 — 요소 타입만 다른 같은 코드 1.18

Ian Lance Taylor 의 글은 슬라이스 뒤집기로 시작합니다. []int 판을 짜고 시험을 쓰다 버그(last := len(s))를 찾고, []string 판을 또 짭니다. 두 함수는 매개변수의 타입만 다릅니다. 정적 타입 언어인 Go 에는 "아무 슬라이스나 뒤집는 함수 하나" 를 쓸 길이 없었습니다.

오류 넷이 1.18 에 들어온 것을 하나씩 짚습니다 — 타입 매개변수, 미리 선언된 any, 그리고 호출할 때의 암묵적 인스턴스화.

제네릭 이전의 길 — 인터페이스·리플렉션·코드 생성

인터페이스도 일종의 제네릭입니다. sort.Sort 처럼 필요한 메서드를 인터페이스로 받으면 됩니다. 하지만 그 메서드를 슬라이스 타입마다 똑같이 써야 하므로, 중복을 없앤 것이 아니라 옮겨 줄인 것뿐이라고 글은 적습니다. 리플렉션은 쓰기 어렵고 느리며, 코드 생성기는 빌드에 단계를 하나 더합니다.

문서 근거

타입 매개변수와 인스턴스화 1.18

타입 매개변수 목록은 보통 매개변수 목록과 같은 꼴이되 대괄호를 씁니다. 타입 인자를 주는 것을 인스턴스화라 하고, 두 단계로 일어납니다 — 타입 인자를 대입하고, 각 인자가 제약을 만족하는지 확인합니다. 인스턴스화만 하고 부르지 않으면 보통 함수 값이 나옵니다.

실행 검증

왜 꺾쇠가 아니라 대괄호인가

Java 와 C++ 은 List<Integer> 처럼 꺾쇠를 씁니다. Go 는 그럴 수 없었습니다. 함수 안에서 < 를 만난 순간 인스턴스화인지 비교 연산인지 가를 수 없기 때문입니다. 타입 정보 없이 구문 분석이 되어야 한다는 것이 Go 의 핵심 설계 결정입니다.

꺾쇠를 쓰는 언어였다면 같은 줄이 w<x, y> 의 인스턴스화를 (z) 로 부르는 것으로도 읽힙니다. FAQ 는 Scala 처럼 대괄호를 쓰는 언어가 Go 말고도 있다고 덧붙입니다.

실행 검증

제약은 인터페이스 — 타입 집합을 적는다 1.18

타입 매개변수에도 "타입" 이 있어야 합니다. 그것이 제약이고, Go 에서 제약은 인터페이스입니다. 그런데 < 나 + 는 메서드가 아닙니다. 그래서 인터페이스를 "메서드 집합" 대신 "타입 집합" 으로 보는 눈을 들였습니다. interface{ int|string|bool } 은 세 타입만의 집합입니다.

셋째 오류가 흥미롭습니다. 타입 집합을 이해하지 못하는 판에서는 Number 가 보통 인터페이스라 + 가 정의되지 않습니다.

실행 검증

~T — "밑바탕 타입이 T 인 모든 타입" 1.18

제약을 쓸 때 관심은 대개 string 하나가 아니라 "모든 문자열 타입" 입니다. ~string 은 밑바탕 타입(underlying type)이 string 인 모든 타입 — string 자신과 type MyString string 같은 정의된 타입 — 의 집합입니다.

함정 — 제약에서 ~ 를 빼면 정의된 타입은 전부 밀려납니다. 오류는 첫 호출(Twice2)이 아니라 둘째 줄에서 납니다. 라이브러리의 제약이 ~ 없이 적혀 있으면 사용자가 만든 타입을 받을 수 없습니다.
실행 검증

any 와 comparable 1.18

any 는 빈 인터페이스의 별칭이라 interface{} 대신 어디서나 쓸 수 있습니다. comparable 은 ==·!= 로 비교할 수 있는 모든 타입의 집합이고, 제약으로만(또는 제약에 끼워서만) 씁니다.

실행 검증

제약 전용 인터페이스 1.18

합집합이나 ~T 를 담은 인터페이스, 그리고 comparable 은 제약 자리에서만 쓸 수 있습니다. 값의 타입이 될 수는 없습니다. 블로그는 "지금은" 그렇다고 적으며, 타입을 제한한 인터페이스가 일반 타입으로 쓰일 날을 상상하기 어렵지 않다고 덧붙였습니다.

실행 검증

함수 인자 타입 추론, 그리고 그 한계 1.18

대부분의 호출은 타입 인자를 적지 않습니다. 컴파일러가 보통 인자의 타입을 매개변수의 타입과 맞춰 추론합니다. 결과에만 쓰이는 타입 매개변수(MakeT[T any]() T)는 이렇게 추론할 수 없습니다.

오류 문장은 블로그가 적어 둔 것과 같습니다 — "r.String undefined (type []int32 has no field or method String)". Path 를 넣었는데 결과 타입이 []E 라 이름 붙은 타입을 잃었습니다.

실행 검증

제약 타입 추론 — S ~[]E 1.18

슬라이스 타입 자체를 타입 매개변수 S 로 받고, 제약 ~[]E 로 요소 타입 E 와 이어 줍니다. S 가 인자에서 정해지면, 제약에서 E 가 따라 나옵니다. 이것이 제약 타입 추론입니다. 블로그는 추론이 "틀린 타입을 추론하느니 차라리 실패하는 쪽" 을 택했다고 적었습니다.

그 뒤 — 1.21 노트는 타입 추론을 더 강하고 정확하게 여러 군데 고쳤다고 적습니다 . 새 slices 패키지도 같은 판입니다 (7부).
실행 검증

제네릭 타입과 그 메서드 1.18

타입도 타입 매개변수를 가질 수 있고, 메서드를 가질 수 있습니다. 쓰려면 인스턴스화해야 합니다 (Tree[string]). 값은 인터페이스로 감싸지 않고 그 타입 그대로 저장됩니다.

실행 검증

구현 — 같은 "모양" 은 코드 한 벌 1.18

인스턴스마다 따로 컴파일할 수도, 인터페이스 매개변수처럼 한 벌로 컴파일할 수도 있습니다. 표준 컴파일러는 보통 모양(shape)이 같은 타입 인자마다 한 벌을 만듭니다. 모양은 크기, 포인터의 위치 같은 성질로 정해집니다.

Largest[go.shape.int]·[go.shape.float64]·[go.shape.string] — 모양 셋에 인스턴스 넷입니다. Celsius 는 float64 모양의 코드를 나눠 씁니다. 1.27.1 에서의 동작이고, FAQ 는 앞으로 이 저울질을 바꿔 볼 수 있다고 적습니다.

실행 검증

빠진 것 — 메서드는 제 타입 매개변수를 못 가진다 1.18

제네릭 타입은 메서드를 가질 수 있지만, 수신자 말고는 메서드가 자기 타입 매개변수를 선언할 수 없었습니다. FAQ 가 든 까닭은 구현입니다 — 인터페이스에 담긴 값이 다른 인터페이스를 구현하는지 실행 중에 따질 때, 어떤 인스턴스가 필요할지 컴파일할 때 알 수 없다는 것입니다.

2026-09 기준 — 오류 문장이 이미 답을 말합니다: "requires go1.27 or later". 1.27 노트는 메서드가 자기 타입 매개변수를 선언할 수 있게 되었다고 적습니다. 그 이야기는 8부에서 합니다. 같은 날 받아 둔 FAQ 는 아직 "We do not anticipate that Go will ever add generic methods" 라는 문장을 싣고 있습니다.

"신중하게 쓰라" — 노트의 이례적인 경고 1.18

노트는 새 코드가 실제 운영 환경에서 충분히 시험되지 않았으니 운영 코드에 쓸 때 "appropriate caution" 을 당부했습니다. 호환성 약속의 예외 조항 — 명세의 모순을 고치거나 명세를 어긴 버그를 고치면 기존 프로그램이 깨질 수 있다 — 도 그대로 인용했습니다.

비용 — 타입 검사기를 통째로 바꾼 탓에 컴파일이 "roughly 15% slower" 일 수 있고, 오류 문장이 예전보다 덜 친절한 경우가 있다고 적었습니다. 만들어진 코드의 실행 시간은 그대로입니다. 빌드 속도는 1.20 에서 되찾습니다(3장).

x/exp — 표준 밖에서 먼저 1.18

언제 제네릭을 쓰나

"타입을 정의하지 말고 코드를 써라." 타입 매개변수 제약부터 설계하고 있다면 길을 잘못 든 것이라고 Ian Lance Taylor 는 적었습니다.

쓸 만한 곳쓰지 말 곳
슬라이스·맵·채널을 요소 타입과 무관하게 다룰 때값의 메서드만 부른다면 — 인터페이스로
연결 리스트·트리 같은 범용 자료 구조타입마다 메서드 구현이 다르면 — 인터페이스로
구현이 똑같은 공통 메서드메서드도 없고 동작도 타입마다 다르면 — 리플렉션(encoding/json)
avoid type parameters until you notice that you are about to write the exact same code multiple times.

"똑같은 코드를 여러 번 쓰려는 참이라는 것을 알아챌 때까지는 타입 매개변수를 피하라." 비교가 필요하면 메서드를 요구하는 제약보다 함수를 받으라는 조언도 있습니다.

블로그 근거

vet 이 제네릭 코드를 본다 1.18

vet 은 타입 매개변수를 그 타입 집합의 타입으로 바꾼 비제네릭 코드에서라면 보고했을 오류를 제네릭 코드에서도 보고합니다. 노트의 예 그대로입니다.

실행 검증

퍼징이 go test 안으로 1.18

퍼징은 입력을 자동으로 바꿔 가며 함수를 두드려 버그를 찾는 시험입니다. 발표 글은 Go 가 "퍼징을 표준 툴체인에 완전히 통합한 첫 주요 언어" 라고 적었습니다. 퍼즈 테스트는 FuzzXxx(f *testing.F) 이고, f.Add 로 넣은 씨앗은 평범한 go test 때마다 돕니다.

실행 검증

실패한 입력은 testdata/fuzz 에 남는다 1.18

퍼징 엔진이 실패하는 입력을 찾으면 그것을 testdata/fuzz/FuzzXxx/ 아래 파일로 씁니다. 커밋해 두면 앞 장처럼 평범한 go test 가 씨앗으로 돌려 회귀 시험이 됩니다. go test 의 새 플래그는 -fuzz·-fuzztime·-fuzzminimizetime 입니다.

노트의 경고 — 퍼징은 메모리를 많이 쓰고, 넓힌 입력을 $GOCACHE/fuzz 에 크기 제한 없이 쌓아 "수 GB" 가 될 수 있습니다. 비우는 명령은 go clean -fuzzcache 입니다.

android/arm64 는 -race 처럼 -fuzz 도 지원하지 않습니다 (0부). 그래서 이 덱은 씨앗과 저장된 말뭉치의 실행만 보입니다. 파일 hangul 은 손으로 적은 것이고, 형식은 엔진이 쓰는 것과 같습니다.

Go 1.18 퀴즈

Q. func Sum[N int | float64](xs ...N) N 에 type Celsius float64 의 값을 넘기면 컴파일되지 않습니다. 왜이고, 제약을 어떻게 고쳐야 할까요? 그리고 왜 이 함수를 func Sum(xs ...Number) 처럼 제약 인터페이스를 값의 타입으로 쓰는 식으로 쓸 수는 없을까요?

A. int | float64 의 타입 집합에는 int 와 float64 두 타입뿐이고, Celsius 는 float64 와 다른 정의된 타입입니다. ~int | ~float64 로 쓰면 밑바탕 타입이 float64 인 Celsius 도 들어옵니다. 합집합이나 ~ 를 담은 인터페이스는 제약 전용이라 변수·매개변수의 타입이 될 수 없습니다.

Go 1.19 한눈에

1.18 뒤 다섯 달 만에 나왔고, 변화는 대부분 툴체인·런타임·라이브러리의 구현에 있습니다. 언어 변경은 메서드 선언에서 타입 매개변수의 범위를 아주 조금 바로잡은 것 하나이고, 기존 프로그램은 영향이 없습니다.

문서 근거

메모리 모델 개정 1.19

Go 메모리 모델을 C, C++, Java, JavaScript, Rust, Swift 가 쓰는 모델에 맞춰 고쳤습니다. Go 는 순차 일관적인(sequentially consistent) 원자 연산만 제공하고, 다른 언어의 더 느슨한 형태는 두지 않습니다. 이 개정과 함께 쓰기 쉬운 atomic 타입이 들어왔습니다.

실행 예제가 없는 까닭 — 문서의 개정이라 go 명령으로 보일 동작이 없습니다. 원자 연산을 쓰는 새 모양은 다음 장에 있습니다.
문서 근거

atomic.Int64 와 atomic.Pointer[T] 1.19

새 타입들은 속의 값을 숨겨, 모든 접근이 원자 API 를 거치게 합니다. Pointer[T] 는 호출하는 자리에서 unsafe.Pointer 로 바꿀 필요를 없앱니다. Int64·Uint64 는 32비트 시스템에서도 구조체 안에서 64비트 경계에 저절로 맞춰집니다.

이전엔 — int64 필드에 atomic.AddInt64(&s.hits, 2) 를 쓰다가 어느 한 곳에서 s.hits++ 로 그냥 읽고 쓰는 실수를 막을 방법이 없었습니다. 새 타입에는 그런 필드가 없습니다. Pointer[T] 는 1.18 의 제네릭이 표준 라이브러리 API 에 쓰인 예입니다.
실행 검증

부드러운 메모리 상한 — GOMEMLIMIT 1.19

런타임이 관리하는 메모리 전체(힙과 그 밖)의 상한을 둘 수 있게 되었습니다. 바이너리 매핑, 다른 언어가 관리하는 메모리 같은 바깥 것은 빠집니다. debug.SetMemoryLimit 이나 같은 뜻의 환경 변수 GOMEMLIMIT 로 정하고, GOGC 와 함께 작동합니다.

실행 검증

GOGC=off 여도 상한 앞에서는 GC 가 돈다 1.19

상한은 GOGC=off 에서도 지켜집니다. 그래서 프로그램이 주어진 메모리를 끝까지 쓰게 할 수 있습니다. 대신 살아 있는 힙이 상한에 가까워 GC 가 헛돌지 않도록, 런타임은 GC 의 CPU 사용을 (쉬는 시간을 빼고) 50% 로 묶습니다.

함정 — 상한은 "부드러운" 것입니다. 살아 있는 데이터가 상한보다 크면 런타임은 멈추지 않고 메모리를 더 씁니다. 노트는 CPU 상한이 작동한 마지막 GC 주기를 알려 주는 지표 /gc/limiter/last-enabled:gc-cycle 도 소개합니다.
실행 검증

문서 주석이 링크, 목록, 더 분명한 제목을 지원합니다. 그리고 gofmt 가 주석을 다시 써서 렌더링될 뜻이 드러나게 합니다.

Q. 검증 함수가 errors.Join(errs...) 를 돌려줍니다. 호출하는 쪽에서 err != nil 검사가 올바르게 동작할까요? 그리고 로그에 한 줄로 남기려던 코드가 여러 줄을 찍는다면 왜일까요?

A. 목록이 비었거나 모두 nil 이면 errors.Join 은 nil 을 돌려주므로 검사는 올바릅니다. Join 한 오류의 Error() 는 감싼 오류들의 문장을 줄바꿈으로 잇기 때문에, 한 줄 로그를 원하면 따로 형식화해야 합니다. 개별 오류는 여전히 errors.Is·As 로 찾을 수 있습니다.
