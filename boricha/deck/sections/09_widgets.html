9부 · widgets — 부품

부품은 앱과 똑같은 모양이다. 값인 모델, Update, View. 다른 점은 Update 가 tea.Model 이 아니라 자기 타입을 돌려준다는 것뿐이다.

m.input, cmd = m.input.Update(msg)
//            ↑ 이 대입을 잊으면 입력이 한 글자도 안 들어간다.
//              컴파일도 되고 경고도 없다.

만드는 것 일곱

  • Binding — 키와 도움말을 한 값에
  • Help — 그 값들을 그리는 것
  • Spinner · Progress
  • TextInput — 한글을 제대로
  • List — 거르기 있는 목록
  • Viewport — 긴 글 넘기기

부품마다 계약 하나

View 는 언제나 정확히
Height 줄 × Width 칸

모양이 흔들리면 옆에 놓인 것이 전부 밀린다.

부품을 인터페이스로 묶지 않은 이유

tea.Model 로 묶으면 Update 가 tea.Model 을 돌려준다. 그러면 부모가 결과를 자기 필드에 넣으려고 매번 타입 단언을 해야 한다.

m.input = ret.(widgets.TextInput)   // ← 이걸 부품 개수만큼, 사건마다

키 배치와 도움말 문구가 갈리면

키 처리는 Update 에, 도움말 문구는 View 에 흩어져 있으면 키를 바꿀 때마다 도움말 고치는 것을 잊는다. 반드시 잊는다.

SetEnabled 가 복사본을 돌려주는 것에 주목하라. 목록이 비었을 때 "지우기" 를 막는 것과 도움말에서 숨기는 것을 한 번에 처리한다.

시험 ① 배치는 값이다

Help — 짧게 한 줄, 펼치면 표

둘 다 같은 Binding 목록에서 나온다는 것이 요점이다 — 어긋날 자리가 없다.

꺼 둔 배치는 도움말에도 없다

쓸 수 없는 키를 알려 주는 것은 거짓말이다. "눌러도 아무 일 없는 키" 를 화면에 적어 두면 사용자는 자기가 잘못했다고 생각한다.

한 줄과 표

펼친 표에서 키 칸의 폭을 맞추지 않으면 설명이 들쭉날쭉해서 표로 안 읽힌다. 그 폭도 width.StringWidth 로 잰다 — 키 이름에 화살표(↑↓)가 섞이기 때문이다.

시험 ② 도움말

Spinner — 그림 폭이 같아야 한다

한 벌 안의 그림은 폭이 모두 같아야 한다. 들쭉날쭉하면 돌 때마다 옆의 글자가 밀렸다 당겨졌다 해서, 돌아가는 것이 아니라 화면이 흔들리는 것처럼 보인다.

점자와 이모지 점자(U+2800 대) 그림은 폭이 1칸이라 안전하다. 달 이모지는 2칸이므로 옆에 글을 붙일 때 그만큼 자리를 비워야 한다 — width 패키지가 그 계산을 해 준다. (덱에 실은 D2Coding 에는 점자와 이모지가 없어 시스템 글꼴로 빠진다. 빌더가 그것도 경고한다.)

시계가 불어나는 것을 막는 번호표

Tick 을 두 번 걸면 시계가 둘이 된다 그리고 그 둘이 각각 자기를 다시 예약하므로 시계가 계속 불어난다(둘 → 넷 → 여덟). 그림이 점점 빨라지다가 CPU 가 한 코어를 먹는다. 울림마다 발행 시점의 번호를 적어 두고 지금 기대하는 번호만 받아들이면 그 자리에서 끊긴다.

시험 ③ 회전·되감기·중복 차단

시험 ④ 한 벌 안의 그림은 폭이 같다

새 그림 한 벌을 더할 때 이 시험이 지켜본다. "멋있는데 폭이 다른" 그림을 넣으면 화면이 흔들린다는 것을 만든 사람이 미리 알게 된다.

Progress — 상태가 없는 부품

진행률은 앱이 알고 있는 것이므로 그때그때 넘겨받아 그리기만 한다. Update 도 필요 없다. 부품이라고 해서 반드시 모델일 필요는 없다.

NaN 이 화면을 죽인다

if !(pct >= 0) 인 이유 pct < 0 이라고 쓰면 NaN 을 놓친다. NaN 은 어떤 비교에도 거짓이기 때문이다. 진행률은 대개 나눗셈으로 나오는데 분모가 0이면 NaN 이 나오고, 그걸 곱하면 막대 길이가 정수 변환에서 이상한 값이 되어 strings.Repeat 이 그 자리에서 죽는다.

약속한 폭을 넘기느니 자른다

필드 열하나

값 바꾸기와 초점

초점이 없으면 아무것도 안 받는다. 화면에 입력창이 둘 이상일 때 어느 쪽이 키를 가져갈지 정하는 규칙이 이 한 줄이다.

셸에서 온 관습들

ctrl+a / ctrl+e줄 처음 / 끝
ctrl+b / ctrl+f한 글자 앞 / 뒤
ctrl+u커서 앞을 전부 지우기
ctrl+k커서 뒤를 전부 지우기

bash·zsh 를 쓰는 사람의 손가락이 이미 아는 것들이다. 새 규칙을 만드는 것보다 아는 규칙을 그대로 두는 편이 언제나 낫다.

새 슬라이스를 만들어야 하는 이유

원본 배열에 append 하면 이 모델의 복사본들이 같은 배열을 나눠 갖게 되어, 값 의미론이 조용히 깨진다. 증상이 "가끔 이상한 글자가 남는다" 라서 원인을 찾기 가장 어려운 종류다.

폭이 흔들리면 옆이 밀린다

결과의 폭은 언제나 프롬프트 + Width 다. 모자라면 공백으로 채우고, 넘치면 옆으로 밀어(가로 스크롤) 커서가 보이는 구간만 그린다.

커서를 반전으로 흉내 내기

6부에서 본 대로, 우리 View 는 문자열 하나라 커서 위치를 실어 보낼 수 없다. 그래서 커서 자리의 글자를 반전 스타일로 그려 흉내 낸다. 글자가 없으면(글 끝) 반전된 공백 하나를 그린다.

스크롤 위치를 저장하지 않는 이유

상태를 하나 줄이면 버그도 하나 준다 스크롤 위치를 필드로 들고 다니면 값(value)·커서(pos)·폭(Width)이 바뀔 때마다 세 곳에서 갱신해야 한다. 하나라도 빠뜨리면 커서가 화면 밖으로 사라진다. 매번 다시 계산하면 그런 자리가 아예 없다 — 그리고 이 계산은 O(글자 수)로 충분히 싸다.

10_widgets — 실제 화면

한글 열이 딱 맞고, 거르는 중: 차 가 거르기가 살아 있다는 표시다 — 여섯 이름 모두에 '차' 가 있어 하나도 안 걸러졌고, 3/6 은 여섯 중 셋째에 커서가 있다는 뜻이다. 7부의 폭 표와 8부의 붙이기가 여기서 함께 값을 한다.

부품 하나를 더 만든다면 — 설계

확인 대화상자(예/아니오)를 만든다고 하자. 순서는 언제나 같다.

  1. 계약부터 정한다. "View 는 언제나 Height 줄 × Width 칸". 이걸 먼저 적어 두면 나머지 결정이 따라온다.
  2. 상태를 센다. 물음 글, 고른 쪽(예/아니오), 초점 여부. 셋이면 충분하다.
  3. 키 배치를 값으로 만든다. ←/→ 고르기, enter 확정, esc 취소. 이 목록이 곧 도움말이 된다.
  4. 사건을 정한다. 확정했을 때 부모가 알아야 하므로 ConfirmedMsg{Yes bool} 를 명령으로 돌려준다 — 부모의 필드를 직접 건드리지 않는다.
  5. 시험부터 쓴다. 폭 불변식, 커서 이동, 취소, 초점 없을 때 무시.

부품 하나를 더 만든다면 — 뼈대

type Confirm struct {
    Question      string
    Width, Height int
    YesLabel      string
    NoLabel       string
    Style         style.Style
    SelectedStyle style.Style

    yes     bool   // 지금 고른 쪽
    focused bool
}

type ConfirmedMsg struct{ Yes bool }

func (c Confirm) Update(msg tea.Msg) (Confirm, tea.Cmd) {
    if !c.focused {
        return c, nil
    }
    k, ok := msg.(tea.KeyMsg)
    if !ok {
        return c, nil
    }
    switch k.String() {
    case "left", "right", "tab", "h", "l":
        c.yes = !c.yes
    case "enter":
        yes := c.yes
        return c, func() tea.Msg { return ConfirmedMsg{Yes: yes} }
    case "esc":
        return c, func() tea.Msg { return ConfirmedMsg{Yes: false} }
    }
    return c, nil
}

yes := c.yes 한 줄에 주목하라. 클로저가 c 를 그대로 잡으면 변수 c 를 참조로 잡는다. 여기서는 c 가 값 수신자의 복사본이고 돌려준 뒤 아무도 안 고치니 괜찮다. 그래도 필요한 것만 꺼내 담는 습관이 나중에 슬라이스가 섞일 때 살아난다.
