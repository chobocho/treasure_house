저쪽이 확실히 나은 것 넷

  1. 윈도우. 콘솔 API 한 벌을 더 써야 하는 일이고, 저쪽은 그걸 했다. 윈도우 사용자가 있는 프로그램이라면 이것만으로 선택이 끝난다.
  2. 막힌 읽기를 끊는 것. 라이브러리로 쓸 때 중요하다 — 프로그램이 끝났는데 프로세스가 안 끝나는 경우를 우리는 못 막는다.
  3. 자소 묶음. 가족 이모지(👨‍👩‍👦)는 코드포인트 다섯이 ZWJ 로 묶인 것이다. 터미널은 2칸으로 그리는데 우리 표는 6칸으로 센다.
  4. kitty 키보드 프로토콜. Ctrl+I 와 Tab 을 구별해야 하는 프로그램이라면 우리 파서로는 안 된다.

넷 다 "우리가 못 만든 것" 이 아니라 "이 덱의 범위 밖" 이다. 그러나 범위 밖이라는 말이 없는 문제라는 뜻은 아니다.

이쪽이 단순한 것 넷

읽을 수 있다

전부 만이천 줄이고 그중 4천 줄이 시험이다. 무엇이 어디 있는지 한 사람이 다 안다.

고칠 수 있다

키 하나를 더하려면 표에 줄 하나. 색 내리기를 바꾸려면 함수 하나. 의존성을 갈아 끼우거나 상류에 이슈를 낼 일이 없다.

결정론이 있다

testkit 이 두 번 돌려 같은 바이트를 낸다. 덱의 모든 그림이 그 성질 위에 서 있다.

받아 올 것이 없다

go.mod 에 require 가 없다. 네트워크가 끊긴 기계에서도 go build 가 끝까지 간다.

성능은 느낌이 아니라 숫자로

렌더러 — 60 fps 예산의 0.5 %

한 프레임 예산 16,666 µs · 우리가 쓰는 것 86 µs

한 줄이 바뀐 프레임 하나를 만들어 내보내는 데 0.5 % 를 쓴다.

아무것도 안 바뀐 프레임도 70 µs 를 쓴다 — NewFrame 이 매번 자르기를 다시 하기 때문이다. 여기에 "View 문자열이 같으면 건너뛰기" 를 넣으면 더 줄일 수 있지만, 그러면 문자열 비교 비용이 새로 생긴다. 지금 숫자로는 고칠 이유가 없다.

글자 폭 — 이분 탐색 40 ns

영문도 한글도 같은 이분 탐색을 지나므로 둘의 시간이 같다 — 표 앞쪽에 있어도 지름길은 없다. 할당이 0인 것에 주목하라 — 표를 읽기만 하므로 힙을 건드리지 않는다.

파서 — 붙여넣기 초당 500 MB

4 KB 붙여넣기 하나에 8 µs. 사람이 아무리 빨리 쳐도 초당 스무 번을 넘기 어려우니 여유는 넘친다. ASCII 한 글자마다 할당이 생기는 것(28 allocs)은 KeyMsg 를 any 슬라이스에 담기 때문인데, 지금 숫자로는 고칠 이유가 없다.

스타일 — 값 복사는 140 ns

값 의미론의 대가를 숫자로 스타일을 여덟 번 고치는 복사가 140 ns · 할당 0 이다. "모델이 값이면 복사 비용이 걱정된다" 는 말은 대부분의 경우 근거가 없다 — 구조체가 스택에 사는 한 복사는 몇 번의 메모리 이동일 뿐이다.

보리차 앱을 Bubble Tea 로 — Model

보리차

import "treasure/boricha/tea"

func (m model) Update(msg tea.Msg) (tea.Model, tea.Cmd) {
    switch msg := msg.(type) {
    case tea.KeyMsg:
        switch msg.String() {
        case "ctrl+c": return m, tea.Quit
        case "up":     m.n++
        }
    }
    return m, nil
}

func (m model) View() string { return "…" }

Bubble Tea v2

import tea "charm.land/bubbletea/v2"

func (m model) Update(msg tea.Msg) (tea.Model, tea.Cmd) {
    switch msg := msg.(type) {
    case tea.KeyPressMsg:          // ← 이름만 다르다
        switch msg.String() {
        case "ctrl+c": return m, tea.Quit
        case "up":     m.n++
        }
    }
    return m, nil
}

func (m model) View() tea.View {   // ← 구조체
    return tea.NewView("…")
}

고칠 곳이 셋이다: import 경로, KeyMsg → KeyPressMsg, View 의 반환값. 키 이름 문자열은 그대로다 — 5부에서 표를 맞춰 둔 덕분이다.

언제 직접 만들고 언제 쓰는가

Bubble Tea 를 쓰라

  • 윈도우 사용자가 있다
  • 이모지를 제대로 다뤄야 한다
  • 부품이 많이 필요하다 (표·파일 고르기·여러 줄 입력)
  • 남이 유지보수해 주기를 바란다
  • 대부분의 경우가 여기다

직접 만들 이유가 있다면

  • 의존성을 하나도 둘 수 없는 곳(보안 심사·에어갭)
  • 바이너리 크기가 극단적으로 중요하다
  • 동작을 바이트 단위로 통제해야 한다
  • 그리고 — 배우려고

이 덱의 진짜 목적은 마지막 줄이다. 프레임워크를 만들어 보면 프레임워크를 쓸 때 무슨 일이 일어나는지 알게 된다. 그 앎은 남의 프레임워크를 쓸 때에도 그대로 값을 한다.

이 덱을 읽고 저쪽으로 갈 때 남는 것

  1. 키가 왜 그렇게 오는지 안다. KeyPressMsg 를 처음 봐도 그 안에 무엇이 있어야 하는지 짐작할 수 있다.
  2. 화면이 왜 깜빡이는지 안다. 렌더러가 무엇을 대신해 주는지 알기 때문이다.
  3. 한글이 왜 어긋나는지 안다. lipgloss.Width 를 왜 써야 하는지 설명할 수 있다.
  4. Tick 이 왜 한 번만 우는지 안다. 문서의 "Beginners' note" 를 읽기 전에 안다.
  5. 모델을 왜 값으로 두는지 안다. 그리고 그 대가가 어디서 나타나는지도 안다.

프레임워크를 쓰는 법은 문서로 배울 수 있다. 왜 그렇게 생겼는지는 만들어 보는 편이 빠르다.
