10부 · testkit·record — 시험과 기록

덱에 "이렇게 보입니다" 하고 손으로 그린 화면을 실으면 그건 거짓말이 된다. 코드가 바뀌어도 그림은 안 바뀌기 때문이다. 그래서 화면은 전부 실행에서 뽑는다.

만드는 것

  • 각본 문법 — 사람이 읽고 쓰는 한 줄
  • testkit — 시계 없이 도는 루프
  • tools/record — 프레임 남기기
  • tools/ansi2html — 덱이 읽는 HTML 로
  • apps/bugs — 함정을 코드로

이 부의 계약

두 번 돌리면
바이트까지 같다

make record 뒤 git diff 가 비어 있어야 한다.

진짜 Program 은 기록에 쓸 수 없다

Program 이 서 있는 것

  • 고루틴 셋 — 사건 도착 순서가 매번 다를 수 있다
  • 시계 — 60 fps 로 도는 렌더러
  • 진짜 time.Sleep — Tick 이 실제로 잔다

기록이 필요한 것

  • 같은 각본 → 같은 프레임
  • 같은 프레임 → 같은 바이트
  • 그래야 git diff 가 "그림이 바뀌었다" 를 알려 준다

그래서 testkit 은 Program 과 같은 규칙으로 도는 작은 루프를 다시 쓴다. 그리고 "그 규칙이 정말 같은가" 를 시험 하나가 지켜본다 — 이 부의 마지막에 나온다.

각본을 걸음 목록으로

따옴표만 특별하다

걸음은 터미널이 보낼 바이트가 된다

파서를 건너뛰면 안 된다 KeyMsg 를 바로 만들어 넣으면 편하지만, 그러면 파서에 있는 버그를 이 도구로는 영영 못 찾는다. 각본이 진짜 바이트를 만들어 진짜 파서를 지나게 하면, 기록을 뽑는 일이 곧 파서에 대한 통합 시험이 된다.

시험 ① 각본 문법

시험 ② 오류와 바이트 대응

Run — Program 과 다른 점 둘

  1. 명령을 고루틴이 아니라 그 자리에서 차례로 돌린다. 그래서 Batch 도 적힌 순서대로 돈다 — 이것이 결정론의 대가다.
  2. 시계가 없다. 명령이 돌 틈은 각본의 기다리기(.N)가 준다. 그래서 스스로를 재예약하는 시계를 넣어도 각본은 반드시 끝난다.

시작 사건은 Program 과 똑같이

Program 의 루프를 시계 없이 다시

tea.Expand 가 여기서 쓰인다. 3부에서 "문을 정확히 하나만 열어 둔다" 고 한 그 문이다.

새로 생긴 명령은 다음 차례로

이 한 줄이 없으면 안 끝난다 도는 도중에 새로 생긴 명령을 같은 차례에 돌리면, 스스로를 재예약하는 시계 하나가 이 함수를 영영 못 끝나게 한다. 다음 차례로 미루면 "각본이 준 틈만큼만" 돈다.

시험 ③ 각본대로 도는가

시험 ④ 프레임은 언제나 같은 모양

시험 ⑤ 이 도구의 존재 이유

두 번 돌리면 글자 하나까지 같아야 한다. 그래야 make record 를 다시 돌린 뒤 git diff 가 비어 있다.

시험 ⑥ 무한히 도는 시계도 끝난다

시험 ⑦ 진짜 Program 과 대조

testkit 은 Program 을 쓰지 않고 같은 규칙을 다시 쓴 것이다. 그러면 "그 규칙이 정말 같은가" 를 누군가 지켜봐야 한다. 이 시험이 그것이다 — 같은 바이트를 두 길로 흘려 넣고 끝난 모델이 같은지 본다.

함정을 글이 아니라 코드로 남긴다

"이렇게 하면 안 됩니다" 라고 글로만 적으면 읽는 사람은 그 장면을 상상해야 한다. 상상한 장면은 대개 실제보다 얌전하다.

함정 ① len 으로 칸을 세기

고친 판과 고장 난 판이 같은 모델이다. fixed 하나로 갈린다. 그래야 "이 한 줄의 차이" 라고 말할 수 있다.

함정 ③ 폭을 넘는 줄 — 프레임워크 없이

이 함정은 우리 tea 로 재현할 수 없다 render.NewFrame 이 프레임을 만들 때 이미 자르기 때문이다. 구조적으로 못 일어나게 막아 둔 것이 그 층의 값이다. 그래서 이 판만 프레임워크를 거치지 않고 터미널에 직접 그린다 — 1부의 00_raw 와 같은 자리에서.

직접 그리면 이렇게 된다

함정 셋을 띄우는 프로그램

record — 등록부에서 골라 돌린다

왜 등록부를 두나

예제는 기록할 수 없다 기록할 대상이 라이브러리 패키지의 모델이어야 한다 — 예제들은 package main 이라 여기서 import 할 수 없다. 그것은 "예제는 그 파일 하나로 완결된 프로그램이어야 한다" 는 요구와 맞바꾼 것이고, 그래서 예제의 증거는 기록이 아니라 tmux 캡처가 맡는다.

등록부

모니터의 간격을 30 ms 로 줄인 것에 주목하라. testkit 의 기다리기는 진짜 잠이라, 기본 0.7초로 두면 프레임 열 장에 7초가 걸린다.

색 수준을 못박는 이유

결정론이 죽는 가장 흔한 자리 환경 변수를 보고 색 수준을 정하게 두면 같은 명령이 기계마다 다른 파일을 만든다. TERM 이 다른 CI 에서 돌리는 순간 git diff 가 통째로 뜬다.

등록부를 볼 수 있게

ANSI 를 덱이 읽는 HTML 로

브라우저에서 안 풀고 여기서 푸는 이유: 덱 안의 재생기(deck/player.js)를 백 줄쯤으로 유지하고 싶기 때문이다. ANSI 파서는 손이 많이 가고, 한 번만 돌면 되는 일을 화면을 넘길 때마다 다시 할 이유가 없다.

색은 인라인 style 로 적는다 터미널 화면은 "그 터미널이 낸 색" 그대로여야 증거가 된다. 덱의 배색으로 바꿔치기하면 그건 더 이상 캡처가 아니다.

달라진 줄만 담는다 — 여기서도

6부의 렌더러와 같은 생각이다. 터미널 화면은 프레임 사이에 대부분 그대로다 — 조각 하나가 한 칸 내려갈 뿐인데 24줄을 전부 저장하면 파일이 열 배로 부푼다.

Makefile — 덱에 실리는 것은 전부 여기서 나온다

교차 컴파일과 표 굽기

기록과 변환

진짜 PTY 증거

go run 을 쓰면 키가 사라진다 처음 한 번 컴파일하느라 8초쯤 걸리는데, 그 사이에 보낸 키가 통째로 사라진다. 미리 빌드해 둔 실행 파일을 띄우면 이 문제가 없다 — 실제로 겪고 나서 고친 것이다.

키와 바이트를 밀어 넣기

마우스와 붙여넣기는 키 이름으로 보낼 수 없다. tmux send-keys -H 로 16진수 바이트를 직접 민다 — 5부의 캡처가 그렇게 만들어졌다.

앱 캡처와 로그

덱에 실리는 증거 네 가지

지시자무엇어디서
<!--CODE-->소스에서 잘라 온 코드실제 파일. 커버리지로 셈
<!--CAP-->진짜 터미널 한 장make tmux-smoke · make html
<!--PLAYER-->넘겨 보는 기록make record · make html
<!--RUN-->명령의 출력 그대로make logs

넷 다 사람이 손으로 적을 수 없는 것이다. 그래서 "소스를 고쳤는데 덱을 안 고쳤다" 가 조용한 거짓말이 아니라 빌드 오류가 된다.

실제 시험 결과

-race 는 이 기계(android/arm64)에서 지원하지 않는다. 그래서 동시성은 설계와 타이밍 시험으로만 논증했다 — 그 사실도 적어 둔다.
