터미널 프로그램이 어려운 진짜 이유

1부의 60줄이 왜 그렇게 불편했나? 코드가 길어서가 아니다. 세 가지 일이 한 함수 안에 뒤엉켜 있어서다.

① 읽기

바이트가 언제 올지 모른다. 읽으려면 막혀야 한다.

② 판단

이 바이트가 무슨 뜻이고, 상태가 어떻게 바뀌나.

③ 그리기

바뀐 상태를 화면으로. 언제 그릴지도 정해야 한다.

셋이 섞이면 시험할 수가 없다. "위 화살표를 누르면 셈이 1 늘어난다" 를 확인하려고 진짜 터미널을 열고 진짜 키를 눌러야 한다면, 그 시험은 자동으로 돌지 않는다.

그래서 필요한 것은 세 가지를 갈라놓는 모양이다.

Elm 아키텍처 — 갈라놓는 한 가지 방법

웹 언어 Elm 에서 나온 모양이다. 만든 사람은 Evan Czaplicki. Bubble Tea 도 이 모양을 그대로 가져왔다고 스스로 밝힌다.

고리가 하나뿐이다. 상태는 Update 를 통해서만 바뀌고, 화면은 상태에서만 나온다. 지름길이 없다는 것이 이 모양의 전부다.

인터페이스 하나, 메서드 셋

이 스물다섯 줄이 프레임워크가 사용자에게 요구하는 것의 전부다. 나머지 만이천 줄은 이 셋을 편하게 쓰게 하려고 있다.

왜 포인터가 아니라 값인가

값이면

  • "이 사건이 오면 상태가 이렇게 된다" 를 그대로 시험할 수 있다
  • 그리는 도중에 다른 고루틴이 상태를 바꿔 놓는 일이 구조적으로 없다
  • 이전 상태를 그냥 들고 있으면 되돌리기가 공짜다

대가

  • 복사 비용 — 모델이 크면 프레임마다 복사한다
  • 돌려주는 것을 잊으면 변경이 조용히 사라진다
  • 슬라이스·맵은 값이 아니다. 따로 복사해야 한다
초보자가 반드시 한 번 겪는 버그 
func (m model) Update(msg tea.Msg) (tea.Model, tea.Cmd) {
    m.n++              // 복사본을 고쳤는데
    return model{}, nil // 엉뚱한 것을 돌려준다 → 변경이 사라진다
}
컴파일도 되고 경고도 없다. 3부에서 이 버그를 시험으로 못박아 둔다.

사건(Msg)과 명령(Cmd)

Update 는 순수해야 한다. 같은 사건에 늘 같은 결과를 내야 시험할 수 있다. 그런데 파일을 읽고, 시계를 보고, 그물 너머에 묻는 일은 순수하지 않다.

MsgCmd
무엇일어난 일할 일
방향바깥 → UpdateUpdate → 바깥
타입anyfunc() Msg
누가 만드나파서·시계·명령의 결과Update 가 돌려준다
누가 실행하나—Program 이 다른 고루틴에서

그래서 Update 는 파일을 직접 읽지 않고 "이 파일을 읽어 달라" 는 함수를 돌려준다. 읽은 결과는 다시 사건이 되어 Update 로 돌아온다. 고리가 닫힌다.

명령은 그냥 함수다

type Cmd func() Msg

이보다 단순할 수 없다. 인자도 없고, 컨텍스트도 없고, 오류 반환도 없다. 필요한 것은 클로저로 담는다.

func saveCmd(path string, tasks []Task) tea.Cmd {
    snapshot := append([]Task(nil), tasks...)   // 담을 때 복사한다
    return func() tea.Msg {
        ...
        return savedMsg{err: err}               // 오류도 사건이다
    }
}
오류를 반환하지 않는 이유 오류도 "일어난 일" 이므로 사건이다. 오류를 따로 다루면 Update 밖에 또 하나의 흐름이 생기고, 그 흐름은 시험하기 어려운 곳으로 숨는다. 전부 사건으로 돌려보내면 갈래가 하나뿐이다.

고루틴 셋과 채널 하나

모델을 만지는 것은 ③뿐이다. 그래서 모델에 잠금장치가 필요 없고, "Update 가 도는 동안 상태가 바뀌어 있었다" 는 종류의 버그가 아예 생기지 않는다.

이 구조가 사는 이유

읽기는 막힌다 — 그래서 따로

os.Stdin.Read 는 다음 바이트까지 돌아오지 않는다. 이걸 주 고루틴에서 하면 그동안 시계도 못 보고 화면도 못 그린다.

명령은 오래 걸린다 — 그래서 따로

HTTP 한 번이 3초면, 그동안 키를 못 받는 프로그램은 멈춘 것으로 보인다. Cmd 하나에 고루틴 하나면 그런 일이 없다.

그리기는 자주 안 해도 된다 — 그래서 시계

키를 꾹 누르면 사건이 초당 수백 번 온다. 화면은 60번만 바뀌면 된다. 그 사이의 프레임은 자연히 버려진다.

우리가 약속하는 것

이 덱이 끝났을 때 아래 코드가 실제로 돈다. 지금 정해 두고, 나머지 부에서 지킨다.

p := tea.NewProgram(model{},
    tea.WithAltScreen(),
    tea.WithMouse(),
    tea.WithBracketedPaste(),
)
final, err := p.Run()

Program 이 지키는 것

  • 시작할 때 반드시 크기와 색 수준을 알려 준다
  • 어떤 경로로 끝나든 터미널을 되돌린다
  • 패닉을 삼키지 않는다 — 되돌린 뒤 다시 던진다
  • 끝났을 때의 모델을 돌려준다

모델이 지킬 것

  • Update 는 순수하게 (파일·시계·그물 금지)
  • 고친 복사본을 돌려줄 것
  • View 는 그리기만 할 것
  • 슬라이스·맵은 손수 복사할 것

View 를 문자열로 둔 대가

얻는 것

  • diff 가 문자열 비교로 끝난다
  • 시험이 want := "n=1" 한 줄이다
  • 기록이 그냥 문자열 배열이다
  • 부품을 붙이는 것이 문자열 붙이기다

잃는 것

  • 커서 위치를 앱이 정할 수 없다
  • 배경색을 화면 전체에 깔 방법이 없다
  • 겹쳐 그리기(레이어)를 못 한다
  • 화면 낭독기에 줄 의미 정보를 못 준다

첫 번째 손실이 제일 아프다. 입력창이 있는 앱에서 진짜 커서가 깜빡이지 않으면 사용자가 "여기 칠 수 있나?" 를 헷갈린다. 9부에서 반전 스타일로 흉내 내지만, 그건 흉내다 — 화면 낭독기를 쓰는 사용자에게는 아무 도움이 안 된다.

Bubble Tea v2 가 View 를 구조체로 바꾼 이유가 정확히 이것이다. 우리는 "단순함" 을 골랐고, 그 대가를 여기 적어 둔다.

일부러 쓰지 않은 Go 기능들

안 쓴 것왜
제네릭이 코드에서 타입을 매개변수화할 곳이 사실상 없다. Msg 는 any 여야 하고(무엇이든 사건이 될 수 있다), 부품은 각자 자기 타입을 돌려준다.
context.Context취소는 Cmd 가 끝나는 것으로 충분하다. 문맥을 Cmd 에 넣으면 모든 명령이 인자를 하나씩 더 받게 되고, 그 대가가 이득보다 크다.
인터페이스로 층 나누기Renderer 인터페이스를 두면 갈아 끼울 수 있지만, 갈아 끼울 것이 하나뿐이면 그건 쓰지 않는 유연성이다.
error 반환명령은 오류도 사건으로 돌려준다. 갈래를 하나로 두면 Update 밖에 또 하나의 흐름이 생기지 않는다.
포인터 수신자모델·스타일·부품이 전부 값이다. 그 결정이 이 프레임워크의 성격을 정한다.

"쓸 수 있는데 안 썼다" 와 "몰라서 안 썼다" 는 다르다. 이 표는 앞의 것들이다 — 각각에 대가와 이득을 견준 자국이 있다.

사건 하나의 수명

  1. 태어난다. 파서가 바이트에서 만들거나, 명령이 일을 끝내고 돌려주거나, 시계가 울리거나, 밖에서 Send 로 밀어 넣는다.
  2. 줄을 선다. msgs 채널에 들어간다. 버퍼가 128이라 대개 기다리지 않는다.
  3. 가려진다. 루프가 꺼내 종류를 본다. QuitMsg·batchMsg 같은 내부 신호는 여기서 끝난다 — 모델은 그것을 못 본다.
  4. 모델을 만든다. Update 에 들어가 새 모델과 새 명령을 낳는다. 이 순간이 이 프로그램에서 상태가 바뀌는 유일한 지점이다.
  5. 화면이 된다. View 가 불려 문자열이 되고, 렌더러에 적힌다.
  6. 사라진다. 아무도 참조하지 않으므로 가비지 컬렉터가 가져간다.

사건은 저장되지 않는다. 상태는 모델에만 있고, 사건은 그것을 바꾸고 사라진다. "지난 사건을 다시 보고 싶다" 는 요구가 생기면 그것도 모델에 담아야 한다 — 5부의 03_keys 가 정확히 그렇게 한다.

나란히 보기 ① Model 인터페이스

Bubble Tea v2

type Model interface {
    Init() Cmd
    Update(Msg) (Model, Cmd)
    View() View          // ← 구조체
}

보리차

type Model interface {
    Init() Cmd
    Update(Msg) (Model, Cmd)
    View() string        // ← 문자열
}

두 메서드는 글자까지 같다. 다른 것은 View 뿐이다. v2 의 View 는 구조체라서 커서 위치나 배경색 같은 것을 함께 실어 보낼 수 있다.

우리가 문자열로 둔 이유: diff 도 시험도 훨씬 단순해진다. "화면은 문자열 하나" 라는 가정이 6부 렌더러 전체를 지탱한다. 대신 커서 위치를 앱이 정할 수 없다 — 그것이 이 선택의 대가다.

Bubble Tea 는 어디서 왔나

  • Elm 아키텍처 — Evan Czaplicki 가 만든 Elm 언어에서 자라난 패턴
  • go-tea — TJ Holowaychuk 이 Go 로 옮긴 실험
  • Bubble Tea — Charm 이 그 위에 터미널 드라이버·렌더러·부품을 붙인 것. Go 모듈로 처음 공개된 판은 v0.7.0, 2020년 5월 26일
이 덱이 Bubble Tea 를 다루는 방식 따라 만드는 것이 아니라 참고하는 설계도로 쓴다. 각 부의 끝에 "Bubble Tea 는 이렇게 한다" 한 장을 두고, 우리 결정과 저쪽 결정을 나란히 놓는다. 저쪽이 더 나은 곳에서는 더 낫다고 적는다. 그것이 이 덱을 읽고 저쪽으로 옮겨 가는 데 도움이 된다.

2부 연습문제

  1. Update 안에서 os.ReadFile 을 부르면 무엇이 나빠지나? 두 가지를 들어 보라. 답: 시험이 파일 시스템에 매이고, 읽는 동안 화면과 키가 멈춘다
