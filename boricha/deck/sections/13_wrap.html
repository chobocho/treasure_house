한 바이트의 여정

1부에서 본 1B 5B 44 세 바이트가 화면의 한 줄이 되기까지, 우리가 만든 여덟 층을 순서대로 지난다. 이 덱 전체를 한 번에 되짚는 길이다.

여정의 각 칸에서 무엇이 결정되나

층이 층이 없으면이 덱의 어느 부
① 원시 모드엔터를 칠 때까지 아무것도 안 온다1·4부
② 파서키가 아니라 바이트 세 개로 온다5부
③ 채널과 루프읽는 동안 아무것도 못 한다3부
④ 값 모델그리는 중에 상태가 바뀐다2·3부
⑤ 부품과 스타일같은 코드를 앱마다 다시 짠다8·9부
⑥ 폭 표한글이 든 줄만 어긋난다7부
⑦ 줄 diff깜빡이고, 줄 번호가 어긋난다6부
⑧ 정리끝나면 셸이 망가진 채 남는다3·4부

여덟 칸 중 하나만 빠져도 겉으로는 비슷한데 어딘가 이상한 프로그램이 된다. 그 "어딘가" 를 짚을 수 있게 되는 것이 이 덱의 목표였다.

같은 여정을 코드로 따라가려면

# ① 바이트를 눈으로
go run ./examples/00_raw          # ← 를 눌러 1B 5B 44 를 본다

# ② 파서를 지난 뒤
go run ./examples/03_keys         # 같은 키가 "left" 로 온다

# ③ 루프와 화면
go run ./examples/02_counter      # 사건 → 상태 → 화면

# ④ 폭과 꾸미기
go run ./cmd/showcase             # 탭 3 에서 칸 세는 것을 본다

# ⑤ 렌더러가 실제로 내보내는 바이트
go test -run TestFirstPaint -v ./render/

마지막 명령이 특히 볼 만하다. 시험이 기대하는 문자열이 곧 "터미널로 나가는 바이트" 이고, 그것이 이 여정의 마지막 칸이다.

층마다 없앤 것

층없앤 문제대신 생긴 규칙
term터미널이 망가진 채 남는 것켠 것만 · 켠 순서의 역순으로
input키가 바이트로 오는 것어디서 잘려도 결과가 같다
width한글이 든 줄만 어긋나는 것화면 자리는 언제나 칸으로 센다
render깜빡임과 줄 번호 어긋남폭을 넘는 줄은 반드시 자른다
style꾸미기가 코드에 흩어지는 것여덟 단계 · 줄마다 열고 닫는다
tea읽기·판단·그리기가 뒤엉키는 것Update 는 순수하게 · 복사본을 돌려준다
widgets같은 부품을 매번 다시 짜는 것View 는 언제나 같은 크기
testkit화면을 지어내는 것두 번 돌리면 바이트까지 같다

이 덱이 지나온 함정 — 값 의미론

  1. 복사본을 안 돌려준다. m.n++ 하고 return model{}, nil. 컴파일도 되고 경고도 없다. 증상: "아무 일도 안 일어난다". 3부
  2. 슬라이스를 그냥 append. 두 복사본이 같은 배열을 나눠 갖는다. 증상이 가끔 나타나서 가장 찾기 어렵다. 3부·9부
  3. 맵도 참조다. 새 맵을 만들어 복사해야 한다. 5부 08_mouse
  4. 명령에 슬라이스를 그대로 넘긴다. 저장하는 동안 주 고루틴이 그것을 고칠 수 있다. 클로저에 담는 순간 복사한다. 11부

이 덱이 지나온 함정 — 시간과 폭

  1. Tick 을 다시 안 건다. 시계가 한 번 가고 멎는다. 증상이 "화면이 멈췄다" 라서 렌더러를 의심하게 된다. 3부·10부
  2. Tick 을 두 번 건다. 시계가 둘이 되고, 그 둘이 각각 자기를 다시 예약해 지수적으로 불어난다. 번호표가 답이다. 9부
  3. ESC 를 시간으로 판정한다. 정답이 없는 문제다. 짧으면 방향키가 쪼개지고 길면 굼뜨다. 5부
  4. 붙여넣기를 시간으로 끊는다. 큰 글이 두 동강 난다. 붙여넣기는 끝 표시로만 끝난다. 5부
  5. len 으로 칸을 센다. 한글이 든 줄만 밀린다. 7부
  6. ANSI 시퀀스를 폭에 넣어 센다. 색을 쓰는 줄만 어긋난다. 색을 안 쓰면 멀쩡해서 늦게 발견된다. 7부

이 덱이 지나온 함정 — 화면과 상태

  1. 폭을 넘는 줄을 그냥 내보낸다. 터미널이 감아서 줄 번호가 어긋나고, 그때부터 화면이 무너진다. 6부·10부
  2. 크기가 바뀌었는데 diff 를 믿는다. 화면에 무엇이 남았는지 알 수 없다. 6부
  3. 배경색이 걸린 줄의 끝 공백을 뗀다. 그 공백은 색칠된 칸이다. 6부
  4. 거르는 중에 키를 가로챈다. "java" 를 칠 때 j 가 이동으로 먹힌다. 9부·11부
  5. 거른 목록에서 값으로 찾아 지운다. 글이 같은 항목 중 앞의 것이 사라진다. 11부
  6. 누적값 하나로 비율을 낸다. 켠 지 오래된 기계에서 늘 같은 숫자가 나온다. 11부
  7. 기록의 색 수준을 환경에 맡긴다. 같은 명령이 기계마다 다른 파일을 만든다. 10부
  8. 모호 폭 글자를 정렬이 중요한 자리에 쓴다. 글꼴과 표가 갈린다. 7부

열여덟 개. 전부 이 덱을 만들면서 실제로 겪은 것이고, 대부분은 시험으로 못박혀 있다.

빌드와 배포 — 파일 하나로 끝난다

go build -o todo ./cmd/todo
GOOS=darwin  GOARCH=arm64 go build -o todo-mac ./cmd/todo
GOOS=windows GOARCH=amd64 go build -o todo.exe ./cmd/todo

딸려 보낼 파일이 없다. 글자 폭 표도, 팔레트도, 시퀀스도 전부 구워져 있다. 7부에서 표를 코드로 구운 이유가 여기서 회수된다.

4 MB 중 대부분은 Go 런타임이다. 우리 코드는 백 KB 남짓이다.

교차 컴파일은 되지만 — 정직하게

확인한 것

  • 리눅스 arm64 — 이 기계에서 전부 돌렸다
  • 여섯 플랫폼으로 컴파일이 된다
  • windows 판은 터미널을 만지는 순간 ErrUnsupported

확인 못 한 것

  • macOS 에서 실제로 도는지 — 돌려 본 적 없다
  • termios 상수는 소스에서 읽어 적었다
  • BSD 계열은 아예 안 만들었다

"컴파일이 된다" 와 "돈다" 는 다른 말이다. 이 덱은 그 둘을 섞어 적지 않는다 — deck/claims.md 의 "돌려 보지 못한 것" 항목에 그대로 남아 있다.

다음에 만들 것 — 쉬운 것부터

  1. 확인 대화상자 부품. 예/아니오. View 가 언제나 같은 크기라는 계약을 지켜 보라.
  2. 스톱워치·타이머 부품. 3부의 재예약 패턴을 부품 안으로 옮기는 연습이다.
  3. 표 부품. 열 폭을 자동으로 맞추려면 7부의 StringWidth 를 열마다 돌려야 한다.
  4. 여러 줄 입력창. 커서가 2차원이 되는 순간 무엇이 어려워지는지 보게 된다.
  5. 파일 고르기. os.ReadDir 을 명령으로 감싸는 연습.

다음에 만들 것 — 층을 건드리는 것

  1. kitty 키보드 프로토콜. ESC[>1u 로 켜고, CSI unicode-key-code;modifiers u 를 파서에 더한다. Ctrl+I 와 Tab 이 갈리는 순간이 온다.
  2. 자소 묶음. 이모지 ZWJ 열을 하나로 묶어 세는 것. 7부의 표에 규칙을 더하는 일이다.
  3. 인라인 모드. 대체 화면 없이 셸 화면 아래에 그리기. 스크롤 영역(CSI r)을 다뤄야 한다.
  4. 윈도우 콘솔 드라이버. 4부의 스텁을 채우는 일. 이 덱에서 가장 큰 미완성이다.
  5. 막힌 읽기 끊기. 리눅스라면 epoll + 파이프 하나로 된다.
