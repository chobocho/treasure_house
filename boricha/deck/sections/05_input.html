5부 · input — 입력 파서

터미널 입력에는 "키" 라는 것이 없다. 방향키 한 번이 바이트 세 개로 오고, 그 세 개가 두 번에 나뉘어 도착하기도 한다. 이 부는 그 바이트 흐름을 사건으로 바꾼다.

계약은 하나 — 어디서 잘려 들어와도 결과가 같다

상태 기계와 시계를 갈라놓는다

왜 사건 타입이 여기 사는가

의존 방향이 tea → input 이라 이 패키지에서 tea 를 import 하면 순환이 된다. Go 는 순환 import 를 아예 금지한다.

그래서 여기서 별칭으로 두고, tea 쪽에서 자기 이름을 붙인다. Bubble Tea 는 전부 한 패키지에 넣어 이 문제를 피했다 — 층을 나눈 대가가 이 한 줄이다.

특수키도 글자 하나로

왜 이렇게 하나 키 하나를 "글자냐 특수키냐" 로 나눠 두 필드에 담으면, 쓰는 쪽이 늘 두 갈래로 분기해야 한다. 유니코드가 절대 쓰지 않을 번호(마지막 코드포인트 U+10FFFF 너머)를 빌려 오면, 글자든 특수키든 Code 하나만 보면 된다. Bubble Tea v2 도 같은 방법을 쓴다(KeyExtended = unicode.MaxRune + 1).

새 번호를 만들지 않는 키들

Text 를 Code 와 따로 두는 이유: 입력창은 "이 키가 글자로 들어가야 하나" 만 알면 되는데, Code 만 봐서는 Ctrl+A 와 A 를 구별하려고 Mod 까지 봐야 한다. Text 가 비어 있는지가 곧 그 판단이다.

이름은 Bubble Tea 와 글자까지 맞춘다

이 표는 Bubble Tea v2 의 ultraviolet 소스(keyTypeString)와 하나씩 대조해 적었다. 이 덱을 읽고 저쪽으로 옮겨 갈 때 switch 문을 고치지 않아도 되게.

조합키의 순서를 고정한다

순서를 고정하지 않으면 "ctrl+shift+x" 와 "shift+ctrl+x" 가 둘 다 나온다. 그러면 case "ctrl+shift+x": 라고 쓴 비교문이 가끔만 맞는다. 가끔만 틀리는 버그가 가장 오래 산다.

순서는 ctrl → alt → shift. Bubble Tea 와 같다.

조합키와 경계

특수키 코드가 유니코드 안에 있으면 "위쪽 화살표" 와 어떤 한자가 같은 키가 된다. 그런 일이 없다는 것을 시험이 지켜본다.

Decoder — 계약은 하나뿐이다

시간 개념이 여기 없다. ESC 하나만 와 있을 때 "esc 키였다" 고 판정하는 시계는 Reader 가 들고, Decoder 는 Flush 를 받는 순간 확정한다.

넣기와 확정하기

Flush 는 "더 안 온다" 는 뜻이다. 미뤄 두었던 ESC 가 esc 키로 확정된다.

붙여넣기 도중이면 아무것도 확정하지 않는다 붙여넣기는 끝 표시로만 끝난다. 시간으로 끊으면 큰 글을 붙여넣을 때 글이 두 동강 난다. 이 부의 함정 둘 중 하나다.

해석되는 만큼만 뽑아낸다

n == 0 은 "바이트가 더 필요하다" 는 뜻이다. 그때는 그대로 두고 돌아간다 — 버퍼에 남은 것이 다음 Feed 때 이어 붙는다.

끝 표시가 걸쳐 있을 수 있다

마지막 5바이트를 남기는 이유 끝 표시는 ESC[201~ 여섯 바이트다. 지금 버퍼의 끝 5바이트가 그 앞부분일 수 있다. 그것까지 붙여넣기 내용으로 삼켜 버리면 끝 표시를 영영 못 찾는다. 그래서 "확실히 내용인 것" 만 옮기고 5바이트는 남긴다.

제어 문자는 글자에서 비트를 지운 것

0x01 + 0x60 = 0x61 = 'a'

그래서 Ctrl+A 는 0x01 이다.

0x1C~0x1F 은 0x40 을 더하면 \ ] ^ _ 가 된다. 규칙이 두 개로 갈리는 이유는 ASCII 표의 배치 때문이다.

한글 한 글자가 세 번에 나뉘어 오면

utf8.FullRune 이 이 함수의 열쇠다. "이 바이트들이 온전한 글자 하나로 시작하는가" 를 묻는다. 아니면 기다린다.

끝내 안 오는 경우도 버려야 한다 잘못된 바이트(0xFF 같은 것)를 안 버리면 그 뒤의 모든 입력이 영원히 막힌다. 파서가 그 자리에서 굳는 것이라 증상이 "갑자기 키가 안 먹는다" 로 나타난다.

ESC 다음에 무엇이 오느냐

이것이 터미널 입력의 근본적인 모호함이다. 바이트만 봐서는 esc 키와 시퀀스의 시작을 구별할 수 없다.

기다릴 필요가 없는 경우

ESC ESC 는 기다릴 필요가 없다 어떤 시퀀스도 ESC ESC 로 시작하지 않는다. 그러니 앞의 것은 그 자리에서 esc 키로 확정해도 된다 — 50 ms 를 기다리지 않아도 되는 유일한 경우다.

ESC + 무언가 = alt + 그 무언가. 8번째 비트를 못 쓰던 시절, meta 키를 ESC 접두로 흉내 낸 관례가 지금까지 남았다.

CSI — 문법을 그대로 코드로

1부에서 본 ECMA-48 의 문법을 그대로 옮겼다. 매개변수 바이트를 먹고, 중간 바이트를 먹고, 마지막 바이트에서 멈춘다.

이 문법이 파서를 구해 준다 마지막 바이트의 범위가 정해져 있으므로 모르는 시퀀스도 어디서 끝나는지는 안다. 새 터미널이 처음 보는 것을 보내도 그 길이만큼만 건너뛰고 다음 키로 넘어간다.

마지막 바이트가 명령의 이름이다

번호가 띄엄띄엄한 것은 역사의 흔적이다. 16, 22번은 애초에 배정된 적이 없다 — VT220 의 기능키 배열에서 비어 있던 자리다.

시험 ⑨ 반쪽 글자와 깨진 바이트

Reader — 50 ms 를 세는 곳

왜 하필 50 ms 인가 더 짧으면 느린 연결에서 방향키가 esc+[+A 로 쪼개진다. 더 길면 사용자가 Esc 를 누른 뒤 반응이 굼떠 보인다. 사람이 "즉시" 로 느끼는 경계가 대략 100 ms 이므로 그 절반쯤에 둔다.

고루틴이 둘인 이유

하나로 합칠 수 없다. Read 가 막혀 있는 동안에는 시계를 볼 수 없기 때문이다. 읽기만 하는 고루틴을 따로 두고, 다른 하나가 그 덩어리와 시계를 함께 기다린다.

끊을 수 없는 읽기

Close 를 불러도 이 고루틴은 안 깨어난다 os.Stdin 의 Read 를 밖에서 끊을 방법이 표준 라이브러리에 없다. Bubble Tea 가 muesli/cancelreader 를 쓰는 이유가 정확히 이것이다. 우리는 "프로그램이 끝나는 순간 이 고루틴은 버린다" 를 택했다 — 프로세스가 곧 죽으므로 새는 것이 문제가 되지 않는다. 라이브러리라면 다른 얘기다.

덩어리와 시계를 함께 기다리기

판단을 미룬 바이트가 남았을 때만 시계를 건다. 아무것도 안 미뤄 두었는데 시계를 돌리면 50 ms 마다 아무 일도 안 하는 깨어남이 생긴다 — 배터리로 도는 기계에서 그 차이가 보인다.

여러 번 닫아도 안전하게

sync.Once 하나로 끝난다. 닫힌 채널을 또 닫으면 패닉이므로, "정리는 여러 곳에서 불릴 수 있다" 를 전제로 짜 두는 편이 안전하다.

5부의 함정 둘

① ESC 하나는 알 수 없다

기다리는 수밖에 없다. 얼마나? 50 ms. 짧으면 방향키가 쪼개지고 길면 굼뜨다. 정답이 없는 문제이고, 모든 터미널 프로그램이 같은 타협을 한다.

② 붙여넣기를 시간으로 끊으면 안 된다

큰 글을 붙여넣으면 중간에 50 ms 가 지나간다. 그때 Flush 를 하면 글이 두 동강 난다. 붙여넣기는 끝 표시로만 끝난다.

둘 다 시험으로 못박혀 있다. 특히 두 번째는 TestFlushDuringPasteKeepsWaiting 이라는 이름을 그대로 읽으면 규칙이 보인다.
