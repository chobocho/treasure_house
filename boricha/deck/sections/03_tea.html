3부 · tea — 핵심 루프

이 덱의 심장이다. 2부에서 그린 그림을 코드로 옮긴다. 루프 자체는 서른 줄이 안 된다. 나머지 코드 전부가 그 서른 줄을 짧게 유지하려고 존재한다.

만드는 것

  • Msg — 사건의 타입들
  • Cmd — Batch · Sequence · Tick · Every
  • Option — 켜고 끄는 것들
  • Program — 고루틴 셋을 엮는 곳
  • 예제 01_hello … 04_tick

이 부의 함정 셋

  • 복사본을 안 돌려주면 변경이 사라진다
  • Tick 은 한 번만 울린다
  • 슬라이스는 값이 아니다

아직 input 도 render 도 안 만들었지만, 이 부에서는 그것들을 이미 있는 것으로 치고 쓴다. 만든 순서와 설명하는 순서가 다른 이유다 — 무엇을 만드는지 모른 채 바이트 파서를 보는 것은 고문이다.

사건에는 무엇이 있나

Key·MouseMsg 같은 것들은 별칭이다. 쓰는 사람이 input 패키지를 알 필요가 없어야 하기 때문이다 — tea.KeyMsg 하나만 알면 된다.

시작할 때 반드시 보내는 두 가지

WindowSizeMsg

시작할 때 한 번, 그 뒤로는 창이 바뀔 때마다.

시작할 때 반드시 보낸다는 것이 중요하다. 그래야 모델이 첫 View 를 그릴 때 이미 크기를 안다 — "처음 한 프레임만 크기가 0" 이라는 성가신 예외가 사라진다.

ColorProfileMsg

이 터미널이 낼 수 있는 색 수준(없음·16색·256색·24비트).

모델은 이걸 받아 자기 스타일들의 프로필을 정한다. 8부에서 그 값이 어떻게 가장 가까운 색으로 내려 맞춰지는지 본다.

왜 사건으로 주나 — 함수로 물어보게 하면 안 되나 p.Size() 같은 함수를 두면 모델이 Program 을 알아야 한다. 그러면 모델을 시험할 때 Program 을 만들어야 하고, 그건 터미널을 만들어야 한다는 뜻이다. 사건으로 주면 모델은 그저 사건 하나를 받는 함수로 남는다.

모델에게 주지 않는 사건

batchMsg 와 sequenceMsg 는 밖으로 내보내지 않는다. Batch/Sequence 가 만들어 내는 내부 신호이고, 루프가 가로채 처리한다.

type (
    batchMsg    []Cmd
    sequenceMsg []Cmd
)

모델의 Update 는 이것들을 영영 보지 못한다. 소문자로 시작하니 앱이 직접 만들 수도 없다. 명령을 흩뿌리고 줄 세우는 일은 Program 의 몫이라는 뜻이다.

단 하나의 예외가 10부에 있다. testkit 은 Program 밖에서 루프를 도는데, batchMsg 를 못 알아보면 Batch 를 쓴 모델을 아예 돌릴 수 없다. 그래서 tea.Expand 라는 문을 정확히 하나만 열어 두었다.

키 상수를 다시 내놓기

특수키가 왜 rune 인지, 왜 유니코드 최대값 너머의 번호인지는 5부에서 파서를 만들 때 자세히 본다. 여기서는 "tea. 만 붙이면 다 있다" 만 알면 된다.

마우스 상수도 마찬가지

대부분의 경우 msg.String() 으로 비교하는 편이 읽기 좋다 ("ctrl+c", "left press (3,4)"). 코드로 직접 견주고 싶을 때를 위해 열어 둔다.

명령 — 순수하지 않은 일을 밖으로

tea.Quit 이 func() Msg 꼴이라 그대로 Cmd 로 넘어간다. 그래서 return m, tea.Quit 라고 쓸 수 있다 — 괄호가 없는 것에 주의하라. 괄호를 붙이면(tea.Quit()) 그 자리에서 QuitMsg 가 되어 버린다.

Batch — 한꺼번에, 순서 없이

nil 을 걸러 내는 것이 실용적으로 중요하다. 조건에 따라 명령을 넣거나 빼는 코드를 쓸 때 tea.Batch(cmdA, maybeNil, cmdC) 를 그냥 쓸 수 있게 하려는 것이다.

하나만 남으면 감싸지 않고 그대로 돌려준다. 감싸면 사건이 한 번 더 오가는데, 그 왕복은 아무것도 하지 않는다.

Sequence — 차례로

Batch 를 쓸 때

서로 상관없는 일들. 파일 읽기와 시계 걸기를 동시에.

Sequence 를 쓸 때

앞의 것이 끝나야 뜻이 있는 일들. "저장하고 → 알림 띄우고 → 3초 뒤 지우기".

Batch 가 정말 동시에 도는지 어떻게 아나

느린 것을 먼저 넣고, 늦게 넣은 빠른 것이 먼저 도착하는지 본다.

순서를 보장하지 않는다는 것이 계약이므로, "순서가 이렇다" 를 시험할 수는 없다. 대신 "동시에 돌지 않으면 절대 나올 수 없는 순서" 를 확인한다.

Sequence 는 순서를 지킨다

Tick — 한 번만 울린다

이 덱에서 가장 자주 걸려 넘어지는 자리 "왜 시계가 한 번만 가지?" 는 Bubble Tea 를 처음 쓰는 사람이 거의 예외 없이 겪는다. 그리고 화면이 "멈춘" 것처럼 보여서, 원인을 렌더러에서 찾게 된다.

왜 되풀이를 기본으로 두지 않았나

되풀이가 기본이면

  • 멈추는 방법을 따로 만들어야 한다
  • 모델이 죽은 뒤에도 도는 시계가 남는다
  • 실수로 두 번 걸면 시계가 불어난다

다시 거는 것이 기본이면

  • 안 걸면 그것이 곧 멈춤이다
  • 조건을 붙일 수 있다 — "멈춤 상태면 안 건다"
  • 시계가 몇 개인지 코드에서 셀 수 있다

멈추는 장치를 따로 만들 필요가 없다는 것이 이 설계의 값이다. 11부의 시스템 모니터가 space 로 멈추는 방법이 정확히 이것이다 — 다시 걸지 않는다.

Bubble Tea 의 문서도 같은 선택을 하고, 문서에 "Beginners' note" 로 이 함정을 적어 두었다.

한 번만 울린다는 것을 시험으로

화면을 쓰는 프로그램은 println 으로 디버그할 수 없다

fmt.Println 을 부르면 그 글이 화면 한복판에 찍혀 우리가 그린 것을 망가뜨린다. 그래서 로그는 파일로 뺀다. 다른 터미널에서 tail -f debug.log 로 본다.

Bubble Tea 에는 하나 더 있다 tea.Println 은 앱 화면 위쪽에 글을 밀어 넣는다(대체 화면이 아닐 때). 스크롤 영역을 조작해야 해서 우리는 안 만들었다 — 12부의 대조표에 그렇게 적어 둔다.

옵션은 왜 함수인가

설정 구조체를 받으면 필드가 늘 때마다 부르는 쪽이 다 깨지거나, 안 쓰는 필드를 0으로 채워야 한다. 함수로 두면 필요한 것만 적으면 되고, 기본값이 "아무것도 안 적었을 때" 로 자연히 정해진다.

옵션 ① 입출력과 화면

WithInput(nil) 이 "입력을 아예 안 받는다" 인 것에 주목하라. 밖에서 Send 로만 움직이는 프로그램과, 시계만으로 도는 기록에 쓴다.

옵션 ② 시험과 기록을 위한 것들

시험을 위해 문을 여는 것은 부끄러운 일이 아니다 WithWindowSize·WithColorProfile·WithQuitAfter 는 사람이 쓸 일이 거의 없다. 그러나 이 셋이 없으면 이 프레임워크는 자동으로 시험할 수 없고, 자동으로 시험하지 못하는 프레임워크는 고칠 때마다 손으로 확인해야 한다.

Program — 고루틴 셋을 엮는 곳

Program 이 들고 있는 것

채널이 넷인데 하는 일이 다 다르다.

msgs사건이 모이는 곳. 버퍼 128
killedKill 이 닫는다 — 즉시 멈춤
done정리가 끝나면 닫힌다 — Send 가 매달리지 않게
finishedRun 이 완전히 돌아오면 닫힌다 — Wait 가 기다린다

왜 버퍼를 두나

버퍼가 없으면 명령 고루틴이 사건을 보내려는데 주 고루틴이 Update 중일 때 그 자리에서 막힌다. 잠깐 막히는 것은 괜찮지만, 사건이 몰릴 때(키 반복, 마우스 움직임) 매번 막히면 눈에 띄게 굼떠진다.

Run ① defer 를 거는 순서가 전부다

defer 는 나중에 건 것이 먼저 돈다 그래서 패닉을 가로채는 defer 를 마지막에 걸어야 한다. 그래야 패닉이 났을 때 그 안에서 터미널을 먼저 되돌리고 다시 던질 수 있다. 순서를 바꾸면 되돌리기가 패닉 뒤에 돌게 되고, 그사이에 찍히는 패닉 메시지가 원시 모드 화면 위에 계단처럼 찍힌다.

Run ② 터미널 준비

터미널이 아니면(파이프·버퍼) 원시 모드는 건너뛰지만 대체 화면 같은 시퀀스는 그대로 내보낸다. 그래야 출력을 버퍼로 받아 "정말 켜고 껐는가" 를 시험할 수 있다.

Run ③ 크기와 색을 정하고 부품을 켠다

여기서 렌더러의 시계가 돌기 시작하고, 입력 고루틴이 msgs 로 사건을 보내기 시작한다. 2부의 그림이 이 서른 줄에서 완성된다.

Run ④ 시작 사건과 첫 그림

사건 둘을 루프가 시작되기 전에 채널에 넣는다. 버퍼가 있으므로 막히지 않는다. 그래서 모델이 받는 첫 사건은 언제나 WindowSizeMsg 다.

루프 — 이 덱의 심장 서른 줄

이게 전부다. 나머지 만이천 줄은 이 서른 줄을 짧게 유지하려고 존재한다.

루프를 한 줄씩

  1. QuitMsg 면 끝낸다. 남은 정리는 defer 가 한다.
  2. ClosedMsg — 입력이 끊겼다. 파이프로 돌릴 때 여기서 끝난다.
  3. batchMsg — 내부 신호. 모델에게 주지 않고 각자 고루틴으로 흩뿌린다.
  4. sequenceMsg — 고루틴 하나에서 차례로 돌린다.
  5. WindowSizeMsg — 렌더러에게도 알린다. 그리고 모델에게도 준다(continue 가 없다).
  6. 나머지는 전부 Update 로. 돌려받은 모델을 다음 사건의 입력으로 쓴다.
  7. 화면을 적어 두고, 새 명령이 있으면 고루틴으로 띄운다.

Send · Quit · Kill · Wait

Update 안에서 Send 를 부르면 안 된다 주 고루틴이 자기 자신을 기다리게 되어, 버퍼가 차는 순간 굳는다. Update 에서 사건을 만들고 싶으면 명령을 돌려주면 된다 — 그것이 이 프레임워크의 방식이다.

명령을 실제로 돌리는 곳

여덟 줄이다. Cmd 가 그냥 함수인 덕분이다. 문맥도, 취소도, 오류 처리도 없다 — 전부 사건으로 돌려보내면 되기 때문이다.

80×24 는 VT100 이래의 기본값이고 지금도 대부분의 터미널이 그 크기로 열린다. 거짓말을 하는 것이 아니라 "모를 때의 약속" 을 지키는 것이다.

크기 감시와 마지막 정리

정리 순서에 이유가 있다 ① 렌더러를 멈춘다 — 마지막 화면을 한 번 더 그린다("안녕히" 같은 마지막 프레임). ② 켜 둔 모드를 켠 순서의 역순으로 끈다. ③ 원시 모드를 되돌린다 — 이것이 마지막이어야 한다. ③을 먼저 하면 그 뒤에 내보내는 정리 시퀀스가 줄 편집을 거쳐 나가면서 화면에 쓰레기를 남긴다.

시험 ① 세는 모델 하나로 대부분을 친다

시험 ② 3초 안에 안 끝나면 실패

고루틴을 쓰는 코드의 시험에서 가장 나쁜 실패는 매달림이다. 시간 제한을 두면 실패가 "3초 안에 안 끝났다" 라는 읽히는 문장이 된다.

시험 ③ 사건이 오면 모델이 바뀐다

입력으로 "\x1b[A\x1b[A\x1b[Bq" 라는 진짜 바이트를 준다. 파서를 건너뛰고 KeyMsg 를 바로 만들어 넣으면, 파서의 버그를 이 시험으로는 못 찾는다.

시험 ④ 시작 사건과 초기 명령

시험 ⑤ 바깥에서 사건 밀어 넣기

웹소켓·파일 감시·다른 프로그램에서 오는 사건이 전부 이 문으로 들어온다. 11부의 앱들은 안 쓰지만, 프레임워크로서는 없으면 안 되는 문이다.

시험 ⑥ 화면과 종료 정리

출력이 bytes.Buffer 라서 "무엇을 써 보냈는지" 를 바이트로 확인할 수 있다. 대체 화면을 빠져나오는 시퀀스로 끝나야 한다는 것이 계약이다.

시험 ⑦ 패닉이 나도 터미널은 되돌린다

패닉을 삼키지 않는다 가로채서 error 로 바꿔 돌려주면 편해 보이지만, 그러면 버그가 조용히 숨는다. 우리는 터미널을 되돌린 뒤 다시 던진다. 스택 트레이스는 그대로 보인다.

시험 ⑧ 복사본을 안 돌려주면 변경이 사라진다

이 시험은 버그가 없다는 것이 아니라 버그가 이렇게 생겼다는 것을 못박는다. 읽는 사람이 같은 실수를 했을 때 "아, 그 시험에서 본 거" 가 되게 하려는 것이다.

시험 ⑨ 바깥 루프를 위한 문

10부에서 testkit 이 이 문으로 들어온다. 문을 하나만, 그것도 함수 하나로 열어 두면 "누가 이 문을 쓰는가" 를 코드에서 셀 수 있다.

① 복사본을 안 돌려준다

m.n++ 하고 return model{}, nil. 컴파일도 되고 경고도 없다. 증상은 "아무 일도 안 일어난다".

② Tick 을 다시 안 건다

시계가 한 번 가고 멎는다. 증상이 "화면이 멈췄다" 라서 렌더러를 의심하게 된다.

③ 슬라이스를 그냥 append

두 복사본이 같은 배열을 나눠 갖는다. 증상이 가끔 나타나서 가장 찾기 어렵다.

셋 다 값 의미론에서 나온다. 값으로 다루기로 한 대가이고, 그 대가를 알고 쓰면 나머지 이득이 훨씬 크다.
