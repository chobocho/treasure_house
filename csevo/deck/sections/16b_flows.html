같은 프로그램 다섯 시대

C# 1.2 · 2.0 · 3.0 · 7.3 · 14 — 같은 출력, 다른 문체 · 크기의 표 · 옛 코드는 오늘도 돈다 · 퀴즈

과제 — 주문 아홉 건의 보고서

소스 안에 적어 둔 주문 아홉 건(고객 · 품목 · 수량 · 단가)을 고객별로 묶어 주문 수 · 수량 · 금액을 냅니다. 금액이 큰 차례로, 같으면 이름 차례로 찍고 합계를 붙입니다. 끝으로 금액이 1000 이상인 주문의 수와, 가장 많이 팔린 품목(같으면 이름 차례)을 찍습니다.

다섯 판은 같은 규칙을 지킵니다 — 해시 차례로 찍지 않고, 문화권에 따라 바뀌는 서식을 쓰지 않습니다. 실험 묶음이 다섯 출력을 바이트 단위로 견주고, 하나라도 다르면 멈춥니다. C# 1.2 판은 -langversion:1 로 컴파일합니다 — Roslyn 에는 1.2 라는 언어 버전이 없습니다(2부).

실행 검증

C# 1.2 판 (1/3) — 형식 넷

제네릭이 없으니 컬렉션은 object 를 담고(2부), 정렬 순서 하나를 주려면 IComparer 를 구현한 클래스가 따로 있어야 합니다. 비교는 object 둘을 받아 캐스트합니다. 조건 하나를 넘기는 데도 대리자 형식 OrderTest 를 먼저 선언합니다(2부). 금액 비교의 뺄셈은 값이 작아 넘치지 않습니다 — 큰 값이면 3부의 함정입니다(3부).

실행 검증

C# 1.2 판 (2/3) — 목록 만들기와 대리자

foreach (Order o in orders) 에는 캐스트가 숨어 있습니다(2부). 목록에 다른 형식이 섞이면 컴파일러가 아니라 실행 중의 InvalidCastException 이 알려 줍니다. new OrderTest(IsBig) 처럼 대리자는 이름 있는 메서드로만 만들 수 있습니다.

실행 검증

C# 1.2 판 (3/3) — Hashtable 과 박싱

수량 표 byItem 은 int 를 상자에 담아 넣고 (int) q 로 꺼냅니다(2부, 언박싱). 없는 키는 null 이라 q == null ? 0 : … 이 붙습니다. Hashtable 의 차례는 정해져 있지 않아서 품목은 차례에 기대지 않는 비교로 고릅니다.

실행 검증

C# 2.0 판 (1/3) — 반복기가 목록을 낸다

주문 목록은 yield return 으로 쓰는 반복기입니다(3부). 그것을 담는 Data 는 static class 입니다 — C# 1 에서는 private 생성자로 흉내 내던 것입니다(3부). 비교 클래스와 대리자 형식은 다음 장의 익명 메서드로 들어갑니다.

실행 검증

C# 2.0 판 (2/3) — 형식을 아는 컬렉션

캐스트와 박싱이 사라졌습니다 — Dictionary<string, int> 는 int 를 그대로 담습니다(3부). 없는 키는 TryGetValue 가 false 와 0 으로 알려 줍니다. 정렬 비교는 그 자리의 익명 메서드입니다(3부). Comparison<Row> 라는 제네릭 대리자 형식을 컴파일러가 대신 고릅니다(3부).

실행 검증

C# 2.0 판 (3/3) — FindAll 과 C# 1 의 거절

거절은 13개 모두 CS8022(제네릭)입니다. 반복기(yield) · static class · 익명 메서드의 게이트는 보이지 않습니다. MessageID.cs 는 이 셋의 검사에 "semantic check" 라고 적습니다 — 제네릭의 구문 오류가 먼저 나자 의미 분석의 게이트가 나오지 않은 것입니다.

실행 검증

C# 3.0 판 (1/2) — 속성과 확장 메서드

Order 는 자동 구현 속성 넷과 계산 속성 하나가 되었습니다(4부). 생성자 대신 객체 초기화자로 만들고 (4부), "큰 주문의 수" 는 IEnumerable<Order> 에 붙인 확장 메서드입니다(4부). Row 형식은 없어졌습니다.

실행 검증

C# 3.0 판 (2/2) — 쿼리 식 둘

묶고 · 합하고 · 정렬하던 반복문이 쿼리 식 하나가 되었습니다(group, let). 행은 익명 형식이고 (4부), 이름이 없으니 var 로만 받습니다(4부). 합계는 Sum 세 번입니다(4부). orderby … g.Key 는 이 판에서만 문화권 비교입니다 — 이름이 ASCII 라 이 데이터에서는 서수 비교와 같은 답입니다.

실행 검증

C# 7.3 판 — 클래스 없이 튜플로

Program 말고는 형식 선언이 없습니다. 주문은 이름 붙은 튜플이고(8부), 도우미는 Main 안의 지역 함수입니다(8부). 행은 foreach (var (name, …) in rows) 로 분해하고(8부), 쓰지 않는 칸은 _ 로 버립니다(8부). String.Format 의 {0,-6} 은 보간의 {a,-6} 이 되었습니다(7부).

실행 검증

C# 14 판 (1/2) — 최상위 문

class Program 과 Main 이 사라졌습니다(10부). 배열과 목록은 컬렉션 식으로 만들고 쿼리 결과는 .. 로 펼칩니다(13부). new("Ann", …) 는 대상 형식 new 이고(10부), 마지막 두 줄은 원시 보간 문자열 하나입니다(12부). Print 는 메서드가 아니라 지역 함수입니다(10부).

실행 검증

C# 14 판 (2/2) — 레코드와 확장 속성, 그리고 옛 버전의 거절

Order 와 Row 는 위치 레코드 한 줄씩이고(10부), "큰 주문의 수" 는 확장 속성이 되어 orders.Big 처럼 괄호 없이 읽습니다(15부). 내린 두 컴파일은 모두 파싱 오류뿐입니다. C# 13.0 은 확장 블록에서, C# 7.3 은 본문이 있는 레코드에서도 무너지고, 최상위 문 · 컬렉션 식 · 원시 문자열의 게이트는 하나도 나오지 않습니다. 파서가 길을 잃으면 뒤 단계의 게이트는 보이지 않습니다(15부).

실행 검증

선언의 오류가 본문의 게이트를 가린다

C# 3.0 판을 C# 2 로 내리면 거절이 다섯뿐입니다 — 자동 구현 속성 넷과 확장 메서드 하나. 본문의 var · 람다 · 쿼리 식은 아무 말이 없습니다. 작은 파일로 다시 봅니다.

선언에 오류가 하나 생기자 본문의 오류 둘이 사라졌습니다. 이 컴파일러는 선언 단계에서 오류가 나면 메서드 본문의 진단을 내지 않는 것으로 보입니다(관찰). 그래서 "내리면 무엇이 거절되나" 는 기능 하나씩 따로 봐야 합니다 — 이 덱이 게이트를 기능마다 따로 내린 까닭입니다(3장).

다섯 판의 크기와 첫 거절

줄 수는 C# 1.2 판에서 C# 14 판까지 절반 아래로 줄었습니다. 토큰은 C# 3.0 에서 크게 줄고, C# 7.3 판과 C# 14 판은 거의 같습니다 — 최상위 문과 레코드가 걷어 낸 것은 주로 줄이고, 식의 양은 LINQ 이후 비슷합니다. C# 7.3 판은 C# 7.0 까지 내려도 돕니다. 7.1 · 7.2 · 7.3 의 기능은 쓰지 않았습니다.

옛 코드를 오늘의 컴파일러로

네 옛 판은 -langversion:14.0 으로도 컴파일되고 같은 출력을 냅니다(표의 "C# 14.0 으로" 칸). 경고 웨이브를 모두 켜도 조용합니다.

말을 거는 것은 nullable 참조 형식을 켤 때뿐입니다(9부). C# 1.2 판은 IComparer 의 매개변수와, null 일 수 있는 값의 캐스트 · 언박싱에서(CS8767 · CS8600 · CS8605), C# 3.0 판은 초기화하지 않은 문자열 속성 둘에서(CS8618) 경고가 나옵니다. 튜플과 레코드로 쓴 두 판은 0개입니다 — 값이 모두 생성 때 채워지기 때문입니다.

4장 퀴즈

Q1. C# 1.2 판을 그대로 -langversion:14.0 으로 컴파일하면 무엇이 달라지나요?

Q2. C# 14 판을 C# 13.0 으로 내리면 오류가 둘뿐입니다. 이 판이 C# 13 에 없는 기능을 하나만 쓴다는 뜻일까요?

A1. 아무것도 — 같은 출력을 내고, 경고 웨이브를 모두 켜도 경고가 없습니다. nullable 참조 형식을 켜야 경고가 나옵니다(앞 장).
A2. 아닙니다. 확장 블록의 파싱 오류가 뒤 단계를 막아 다른 게이트가 보이지 않을 뿐입니다. 선언의 오류도 본문의 게이트를 가립니다(4장). 무엇이 거절되는지는 기능 하나씩 따로 내려야 압니다.

5장

호환성 — 깨지 않고 바꾸는 법

약속의 문장 · 문맥 키워드를 이름으로 쓴 스물한 갈래 · @ · 경고 웨이브 · 깨지는 변경 문서 · 문서와 컴파일러가 다른 곳 · 퀴즈

약속의 문장 — "거의 모든 경우"

C# 문서의 "Version and update considerations": "Compatibility is an important goal as new features are added to the C# language. In almost all cases, existing code can be recompiled with a new compiler version without any issue."

문서의 분류뜻
binary breaking change새 런타임에서 옛 바이너리의 동작이 달라진다 — 다시 컴파일해야 한다
source breaking change소스의 뜻이 달라진다 — 새 언어 버전으로 컴파일하기 전에 소스를 고쳐야 한다

"거의 모든 경우" 의 나머지가 이 장의 주제입니다. 4장의 옛 판 넷은 C# 14.0 에서 그대로 돌았습니다(4장). 깨지는 곳은 주로 새 낱말이 옛 이름과 부딪치는 자리입니다 — 그것을 어떻게 피해 왔는지 봅니다.

문서 근거

문맥 키워드 — 예약하지 않은 낱말

표준 초안: "A contextual keyword is an identifier-like sequence of characters that has special meaning in certain contexts, but is not reserved, and can be used as an identifier outside of those contexts as well as when prefaced by the @ character."

  • 예약 키워드(class, int …)는 이름으로 못 씁니다. 하나를 더하면 그 낱말을 이름으로 쓴 모든 프로그램이 깨집니다.
  • 문맥 키워드는 특정 자리에서만 뜻을 갖습니다. 초안의 목록은 add 부터 yield 까지 30개입니다(실험 묶음이 목록을 세어 확인).
  • 문법만으로 못 가르는 곳은 규칙을 둡니다 — var 라는 형식이 있으면 "the declared name takes precedence", await 는 async 메서드 안에서만 키워드입니다.

초안은 C# 8 판입니다(2장). 그 뒤의 record · init · required · field · extension 은 목록에 없습니다. C# 15 의 whats-new 도 새 한정자를 "The closed modifier is a contextual keyword." 라고 적습니다.

문서 근거

C# 2 부터 8 까지의 낱말을 이름으로

파일 하나에 낱말마다 #if 갈래 하나를 두고, 그 낱말을 형식 · 변수 · 메서드의 이름으로 씁니다. 기호 하나씩 켜서 낱말이 들어오기 한 판 앞 · 들어온 판 · C# 14.0 으로 돌립니다. 판은 손으로 적지 않고 data/langgates.tsv 의 게이트에서 읽습니다.

실행 검증

열 낱말은 오늘도 이름으로 됩니다. 깨진 것은 partial 을 반환 형식으로 쓴 꼴 하나이고, 그것도 C# 14.0 에서부터입니다 — partial 생성자가 생기며 partial Run() 이 생성자로 읽힙니다(15부). var 와 dynamic 이라는 형식은 키워드보다 이깁니다. 다만 경고 웨이브 7 은 그런 이름을 짚습니다.

csproj 의 버전은 C# 8.0 이지만 실험은 낱말마다 들어온 판의 앞뒤로 내리고 올립니다. not 갈래는 C# 8 까지 "형식 not 의 변수 x" 를 선언하던 꼴입니다(10부).

@ — 옛 이름을 지키는 한 글자

네 낱말 모두 @ 를 붙이면 C# 14.0 에서도 옛 뜻 그대로입니다 — 표준이 문맥 키워드에 약속한 탈출구입니다(앞 장). 웨이브 7 의 CS8981("may become reserved for the language")은 @ 없는 token 에만 나옵니다. 소문자 형식 이름을 미리 짚어, 다음 낱말이 들어올 자리를 비워 두려는 경고입니다.

경고 웨이브 — 새 경고는 켜야 나온다

Roslyn 문서: "When we introduce new warnings that can be reported on existing code, we do so under an opt-in system so that programmers do not see new warnings without taking action to enable them." 명령 줄의 기본 수준은 4 이고, 모두 보려면 /warn:9999 입니다.

웨이브마다 경고 하나 — 한 파일을 수준마다

기본 수준 4 에서는 경고가 없고, 수준을 하나 올릴 때마다 그 웨이브의 경고가 더해집니다. 9 는 8 과 같습니다. 11 과 9999 처럼 아직 없는 수준도 받고, 음수와 숫자 아닌 값만 거절합니다(CS1900 · CS2035). 프로젝트에서 수준을 높여 두면 다음 SDK 의 웨이브가 자동으로 켜진다는 뜻입니다.

C# 15 (미리 보기, 2026-10 기준) (1/2) — 닫힌 집합

이 덱의 SDK 10.0.112 는 C# 15 를 모릅니다 — -langversion:15 는 CS1617 이고 preview 는 14.0 과 같습니다(15부). whats-new 는 C# 15 를 "the latest C# preview release" 라고 적습니다. 그래서 이 장은 코드 없이 제안서의 까닭만 옮깁니다.

  • 유니언 — "a long-requested C# feature, which allows expressing values from a closed set of types in a way that pattern matching can trust to be exhaustive."
  • 닫힌 계층 — "Many class types are not intended to be extended by anyone but their authors, but the language provides no way to express that intent". closed 클래스의 파생은 선언한 어셈블리 안으로 묶이고, 그 덕에 switch 식이 기본 갈래 없이 완전해집니다.

둘 다 C# 7 의 패턴(8부)과 C# 8 의 switch 식 완전성 검사(9부)가 남긴 빈칸을 겨눕니다 — 열린 계층에는 "모든 경우" 가 없었습니다. 유니언 발표 글은 C# 15 의 유니언이 .NET 11 Preview 2 부터라고 적습니다.

주제 1 — 의례를 덜어 낸다

버전 기록은 C# 6 을 두고 "C# started to eliminate language boilerplate to make code more terse and readable" 이라고 적고, C# 9 와 10 의 주제로 "removing ceremony" 를 다시 꼽습니다.

  • C# 3 — var · 람다 · 자동 구현 속성(4부, 4부)
  • C# 6 · 7 — 식 본문 멤버(7부)

주제 2 — 컴파일러가 더 많이 지킨다

버전 기록: C# 2.0 의 제네릭으로 "types and methods can operate on an arbitrary type while still retaining type safety". 그 뒤로 컴파일러가 지키는 것이 늘었습니다.

  • C# 2 — 캐스트 없는 컬렉션(3부), nullable 값 형식(3부)

  • C# 11 — required 멤버(12부) · scoped 와 ref 안전 규칙(12부)
  • C# 15 미리 보기 — 닫힌 집합의 완전성, 메모리 안전(6장)

새 검사는 옛 코드를 깨지 않는 자리로 들어왔습니다 — 켜야 나오는 nullable 경고, 켜야 나오는 경고 웨이브, 언어 버전에 묶인 새 오류(5장).

주제 3 — unsafe 없이 빠르게

버전 기록은 C# 7.3 의 주제를 "features that enable safe code to be as performant as unsafe code" 라고 적습니다. C# 10 의 주제에도 "improved performance for the .NET Runtime" 이 있습니다.

  • C# 7.2 — Span<T> 와 ref struct(8부, 8부)

  • C# 11 · 12 — ref 필드(12부), 인라인 배열(13부)
