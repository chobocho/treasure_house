C# 2.0 — 제네릭이 바꾼 언어

제네릭 · nullable 값 형식 · 반복기 · 익명 메서드 · partial 형식 ·

이 부에서 할 일

C# 2.0 은 C# 1 에 없던 큰 기능을 한꺼번에 들였습니다 — 버전 기록이 주요 기능으로 꼽는 것만 제네릭, partial 형식, 익명 메서드, nullable 값 형식, 반복기, 공변·반공변 여섯입니다. 버전 기록은 이 버전을 이렇게 요약합니다. "C# began as a generic Object-Oriented (OO) language, C# version 2.0 changed that in a hurry."

  • 1장 — C# 2.0 개관. 컴파일러가 C# 2 로 묶은 기능과, 같이 온 런타임.
  • 2장 — 제네릭. 왜 생겼나, 선언과 유추, 제약, default(T), 런타임이 아는 형식 인수, 함정.
  • 3장 — nullable 값 형식. int? 의 정체, ??, 끌어올린 연산자, 박싱.
  • 4장 — 반복기. yield, 늦은 실행, 컴파일러가 만드는 클래스, 함정.
  • 5장 — 익명 메서드. 이름 없는 대리자, 잡힌 변수, 메서드 그룹 변환, 대리자의 변성.
  • 6장 — partial 형식, static 클래스, 접근자마다 다른 접근 수준, global:: 와 extern alias.
  • 7장 — 그 밖의 C# 2.0 기능. #pragma 와 고정 크기 버퍼.

이 부의 예제는 거의 전부 -langversion:2 로 컴파일합니다. 그래서 var, 람다, 자동 속성 없이 C# 2 시절의 모양 그대로 씁니다.

C# 2.0 — 한 번에 커진 언어

제네릭 · nullable · 반복기 · 같이 온 런타임 ·

C# 2.0 한눈에

C# 1 이 "자바를 많이 닮은" 객체 지향 언어였다면, C# 2.0 은 형식을 매개변수로 받는 언어가 됐습니다. 버전 기록은 제네릭과 반복기를 이 버전의 두 기둥으로 꼽습니다.

Roslyn 의 MessageID.cs 에는 C# 2 기능을 모아 둔 자리가 있습니다. 개관 표 맨 아래 줄의 게이트 수가 그 목록의 길이입니다.

문서 근거

C# 2 의 넷을 한 파일에 — 그리고 C# 1 로 내리면

거절은 한꺼번에 다 나오지 않는다 — 이 파일에는 C# 2 기능이 넷 있지만 C# 1 로 내린 캡처에는 generics 거절만 있습니다. 나머지 셋의 거절은 장마다 그 기능만 쓴 파일로 따로 보입니다. 거절 캡처는 "적어도 이 기능은 안 된다" 까지만 증명합니다.

ISO-2 — C# 2 의 다른 이름

Roslyn 은 -langversion:2 와 -langversion:ISO-2 를 같은 뜻으로 받습니다. 0부에서 본 ISO-1 과 짝을 이루는 옛 이름입니다. 앞 장의 파일을 그 이름으로 다시 컴파일합니다.

컴파일러 소스의 언어 버전 해석표에서 "2", "2.0", "iso-2" 세 철자가 같은 값 하나로 갑니다.

실행 검증

같이 온 런타임 — 형식 인수를 아는 런타임 C# 2.0

C# 2.0 의 제네릭은 컴파일러만의 기능이 아닙니다. 표준은 형식 매개변수가 "purely a compile-time construct" 이지만, 실행 중에는 각 형식 매개변수가 실제 형식 인수에 묶인다고 적습니다.

List`1 의 `1 은 형식 매개변수 수입니다. 정의는 하나(List`1[T])이고 닫힌 형식은 형식 인수마다 따로입니다.

실행 검증

같이 온 런타임 — 언어 기능이 기대는 형식 C# 2.0

C# 2.0 의 문법 몇 개는 특정 라이브러리 형식을 전제로 합니다. 반복기는 IEnumerable<T>·IEnumerator<T> 를 돌려주고, int? 는 System.Nullable<T> 의 줄임입니다.

  • IEnumerator<T> 는 IDisposable 을 물려받습니다. 반복기의 finally 가 break 뒤에도 도는 길이 이것입니다(4장).
  • Nullable<T> 는 값 형식이고 인터페이스를 하나도 구현하지 않습니다. 표준도 "implements no interfaces" 라고 적습니다.

1장 퀴즈 — C# 2.0 개관

Q. 제네릭·nullable·반복기·default 를 모두 쓴 파일을 -langversion:1 로 컴파일했더니 generics 거절만 나왔습니다. 이 캡처로 "C# 1 에서도 반복기는 됐다" 고 말할 수 있습니까?

A. 없습니다. 거절이 한 번에 다 나오지 않을 뿐입니다. 반복기만 쓴 파일을 C# 1 로 컴파일하면 Feature 'iterators' is not available in C# 1 이 따로 나옵니다 (4장). 거절 캡처는 기능 하나씩 떼어 봐야 합니다.

2장

제네릭 — 형식을 매개변수로

ArrayList 의 형 변환 · List<T> · 유추 · 제약 · default(T) · 런타임이 아는 형식 인수

제네릭 이전 — 모든 것을 object 로

버전 기록은 제네릭이 왜 나은지를 이렇게 적습니다. "Using generics is better than creating a ListInt type that derives from ArrayList or casting from Object for every operation." C# 1 의 컬렉션이 어땠는지부터 다시 봅니다(2부).

문제 둘 — 꺼낼 때마다 (int) 캐스트를 써야 하고, 엉뚱한 것을 넣어도 컴파일러는 모릅니다. Add(object) 는 무엇이든 받기 때문입니다.
실행 검증

List<int> — 같은 일을 제네릭으로 C# 2.0

형식 인수 <int> 하나로 "이 리스트에는 int 만" 이 형식이 됩니다. 캐스트가 사라집니다.

실행 검증

잘못 넣으면 이제 컴파일 오류

앞의 ArrayList 예제에서 실행 중에야 터지던 실수를 List<int> 에 그대로 해 봅니다.

"넣는 쪽" 과 "꺼내는 쪽" 이 둘 다 막힙니다. ArrayList 의 InvalidCastException 이 컴파일 시간의 CS1503·CS0029 로 옮겨 왔습니다.

실행 검증

박싱 — ArrayList 는 int 를 상자에 담는다

캐스트만의 문제가 아닙니다. ArrayList 는 object 배열에 담으므로 int 를 넣을 때마다 상자(박싱)가 하나씩 생깁니다. List<int> 는 int[] 에 그대로 담습니다.

  • ArrayList 의 a[0] 두 번은 같은 상자를 돌려줍니다(True). 넣을 때 한 번 만든 상자입니다.
  • List<int> 에서 꺼낸 값을 object 에 담으면 그때마다 새 상자가 생깁니다(False).

_items 는 .NET 10 의 내부 필드 이름입니다. 리플렉션으로 엿본 구현 세부라 다른 런타임에서는 다를 수 있습니다.

실행 검증

제네릭 클래스 선언 — class MyStack<T>

형식 매개변수 T 는 클래스 안 어디서나 형식처럼 씁니다 — 필드, 배열, 매개변수, 반환 형식. 표준은 이런 선언을 "blueprint" 라고 부릅니다. 형식 인수를 넣어야 쓸 수 있는 형식이 됩니다.

실행 검증

같은 이름, 다른 개수 — Box · Box<T> · Box<T,U>

형식 매개변수의 수가 다르면 이름이 같아도 서로 다른 형식입니다. 표준은 이것이 "mixing generic and non-generic classes" 에 쓸모 있다고 적습니다 — IEnumerable 과 IEnumerable<T> 가 나란히 있는 까닭입니다.

typeof(Box<>) 처럼 형식 인수를 비운 꼴(unbound generic type)은 typeof 안에서만 쓸 수 있습니다.

실행 검증

제네릭 클래스 안의 중첩 형식

중첩 클래스는 바깥 클래스의 T 를 그대로 씁니다. 그래서 Outer<int>.Inner 와 Outer<string>.Inner 는 다른 형식입니다.

마지막 줄이 1 입니다. 런타임의 눈에는 Inner 도 형식 매개변수를 하나 가진 제네릭 형식입니다 — 바깥의 T 를 물려받은 것입니다.

실행 검증

열린 형식과 닫힌 형식

형식 매개변수가 남아 있으면 열린 형식(open type), 전부 채워지면 닫힌 형식(closed type)입니다. 실행 중에 열린 정의에 형식 인수를 끼워 닫힌 형식을 만들 수도 있습니다.

실행 중에 만든 Dictionary<string, int> 가 컴파일 시간의 typeof(Dictionary<string, int>) 와 같은 형식입니다.

실행 검증

제네릭 형식에서 파생하기 — 닫거나, 열어 두거나

파생 클래스는 기반의 형식 인수를 정해 버리거나(Names), 자기 형식 매개변수를 그대로 넘길 수 있습니다(Logged<T>). protected 필드 items 는 닫힌 쪽에서 List<string> 으로 보입니다.

실행 검증

제네릭 메서드와 형식 유추 C# 2.0

클래스뿐 아니라 메서드 하나에도 형식 매개변수를 붙일 수 있습니다. 부를 때 형식 인수를 적지 않으면 컴파일러가 인수의 형식에서 찾아냅니다 — 형식 유추(type inference)입니다.

실행 검증

유추가 못 하는 것 — CS0411

유추는 인수만 봅니다. 인수가 없거나, 인수가 형식을 말해 주지 않거나, 두 인수가 서로 다른 답을 내면 실패합니다.

  • int n = Make(); — 대입받는 쪽의 int 는 유추에 쓰이지 않습니다.
  • Show(null) — null 리터럴에는 형식이 없습니다.
실행 검증

유추가 되는 경우, 그리고 적어 주기

주의 — Pick(1, 2L) 은 지금의 컴파일러가 -langversion:2 에서 long 으로 유추한 결과입니다. 유추 규칙은 언어 버전 게이트에 없으므로, 옛 C# 2 컴파일러가 같은 답을 냈는지는 이 기계에서 보일 수 없습니다. 미확인

막히면 Pick<object>(1, "a") 처럼 형식 인수를 적어 주면 됩니다.

실행 검증

뜻밖의 것 — C# 1 문법으로도 제네릭 메서드를 부른다

꺾쇠(<int>)를 쓰지 않으면 -langversion:1 에서도 BCL 의 제네릭 메서드를 부를 수 있습니다. Array.Resize 는 제네릭 메서드 Resize<T> 이고, T 는 유추됩니다.

컴파일러의 generics 게이트는 형식 인수 목록을 쓰는 문법에 걸려 있습니다. 그래서 "C# 1 로 내리면 제네릭을 하나도 못 쓴다" 는 틀린 말입니다. 이 덱의 C# 1 예제가 .NET 10 의 BCL 을 그대로 쓰는 것과 같은 이야기입니다(0부).

실행 검증

형식 매개변수 제약 — where C# 2.0

제약이 없는 T 에 대해 컴파일러가 아는 것은 object 의 멤버뿐입니다. where T : IComparable<T> 라고 적으면 본문에서 CompareTo 를 부를 수 있고, 대신 부르는 쪽은 그 조건을 지켜야 합니다.

제약을 어기면 — 부르는 쪽의 컴파일 오류

함정 — S<int?>() 도 거절됩니다. struct 제약은 "nullable 이 아닌" 값 형식만 받습니다. Nullable<T> 자신이 T : struct 로 선언돼 있어서 int?? 같은 겹 nullable 이 생기지 않는 것과 같은 규칙입니다 (3장).
실행 검증

제약을 적는 차례

제약 목록에도 문법 규칙이 있습니다. class·struct 는 맨 앞, new() 는 맨 뒤입니다. 표준은 값 형식 제약을 가진 형식 매개변수가 new() 제약을 함께 가질 수 없다고도 적습니다.

CS0449 의 문장에 unmanaged·notnull·default 가 보입니다. 뒤 버전에 생긴 제약들입니다 — 오류 문장은 언어 버전을 내려도 오늘의 것입니다.

실행 검증

new T() 가 던지는 예외는 감싸여 나온다

new() 제약 덕에 new T() 를 쓸 수 있습니다. 그런데 생성자가 던진 예외가 그대로 나오지 않습니다.

함정 — catch (InvalidOperationException) 으로 받으려 했다면 놓칩니다. .NET 10 에서 new T() 를 거친 예외는 TargetInvocationException 에 싸여 나오고, 원래 예외는 InnerException 에 있습니다.
실행 검증

default 연산자 C# 2.0

default(T) 는 그 형식의 기본값입니다 — 수는 0, 참조는 null, bool 은 false, 구조체는 모든 필드가 기본값. 컴파일러는 이것을 따로 게이트로 둡니다.

실행 검증

default(T) 가 필요한 까닭 — T 에는 null 을 못 준다

제네릭 안에서 "없음" 을 돌려줘야 할 때, T 가 값 형식일 수도 있으니 null 은 안 됩니다. 컴파일러가 직접 default(T) 를 권합니다.

실행 검증

구조체의 default(T) 와 new T()

값 형식에서 default(T) 와 new T() 는 같은 "모든 필드가 기본값" 입니다. Zero<int?>() 는 0 이 아니라 null 입니다 — int? 의 기본값이기 때문입니다 (3장).

실행 검증

함정 — 제약 없는 T 에는 == 가 없다

값 형식의 == 과 참조 형식의 == 는 다른 연산입니다. 어느 쪽인지 모르는 T 에는 어느 것도 고를 수 없어서, 컴파일러는 a == b 를 거절합니다.

예외가 하나 있습니다. 표준은 형식 매개변수의 값을 null 과는 ==· != 로 비교할 수 있다고 적습니다 — 다음 장의 IsNull 입니다.

함정 — where T : class 를 달면 == 가 컴파일되지만, 그것은 참조 비교입니다. 내용이 같은 두 문자열이 string 의 == 로는 True, SameRef 로는 False 입니다. 제네릭 코드는 T 의 연산자 오버로드를 모릅니다.

제네릭 인터페이스 — IComparable<T> C# 2.0

제네릭 클래스 안에서 메서드에 또 <T> 를 붙이면, 그 메서드 안의 T 는 클래스의 T 와 무관한 새 형식 매개변수입니다. 컴파일러는 오류가 아니라 경고를 냅니다.

의도가 "클래스의 T 를 받는 메서드" 였다면 메서드 쪽 <T> 를 지워야 합니다. 이 예제의 디렉터리에는 경고가 증거라는 표시(EXPECT_WARN)가 있습니다.

C# 2 의 문법 안에서는 int·double 판을 따로 쓰거나 덧셈을 대리자로 넘겨야 합니다. 인터페이스에 정적 추상 멤버를 두는 길은 C# 11 에 열립니다 — 12부.

2장 퀴즈 — 제네릭

Q. static bool Same<T>(T a, T b) where T : class { return a == b; } 에 내용이 같은 두 문자열 "ab" 와 new string(new char[] {'a','b'}) 를 넘기면 무엇이 나옵니까? 제약을 지우면 어떻게 됩니까?

nullable 값 형식 — int 에 null 을

참조 형식은 null 로 "값 없음" 을 말할 수 있지만 int·DateTime 같은 값 형식은 늘 어떤 값을 갖습니다. 표준은 값 형식에 null 을 더한 형식을 "nullable value type" 이라고 부릅니다.

실행 검증

int? — null 을 가질 수 있는 int C# 2.0

형식 이름 뒤의 ? 하나로 "값이 있거나 없거나" 를 한 변수에 담습니다.

C# 1 의 우회와 달리 "없음" 이 값 자체에 들어 있어서 따로 들고 다닐 bool 이 없습니다.

실행 검증

int? 의 정체 — Nullable<int> 구조체

표준: "This syntax is shorthand for System.Nullable<T>, and the two forms can be used interchangeably." 새 런타임 형식이 아니라 제네릭 구조체 하나입니다. 2장의 제네릭이 있어야 가능한 기능입니다.

끝에서 둘째 줄이 0 입니다. int 는 인터페이스를 여럿 구현하지만 int? 는 하나도 구현하지 않습니다 — 표준의 "implements no interfaces" 그대로입니다.

실행 검증

nullable 의 기본값은 null

Nullable<T> 도 구조체라 기본값은 "모든 필드가 기본값" 이고, 그것이 곧 HasValue == false, 즉 null 입니다. new int?() 도 같습니다. 0 은 null 이 아닙니다.

실행 검증

HasValue · Value · GetValueOrDefault

표준은 null 인 인스턴스의 Value 를 읽으면 InvalidOperationException 이라고 정합니다. 값을 꺼내는 일을 표준은 "unwrapping" 이라고 부릅니다.

실행 검증

int → int? 는 저절로, int? → int 는 캐스트로

함정 — int c = a + 1; 도 거절됩니다. int? 가 섞인 계산의 결과는 int? 입니다(끌어올린 연산자). 캐스트를 쓰면 컴파일은 되지만 null 일 때 앞 장의 예외가 납니다.

실행 검증

끌어올린 연산자 — null 이 들어가면 null 이 나온다 C# 2.0

int 의 +·*·- 를 따로 정의하지 않아도 int? 에서 쓸 수 있습니다. 표준은 이것을 lifted operator 라고 부릅니다 — 피연산자 하나라도 null 이면 결과가 null 이고, 아니면 값을 꺼내 계산한 뒤 다시 쌉니다.

함정 — 합계 루프에 null 이 하나 섞이면 그 뒤로 sum 은 계속 null 입니다. null * 0 도 0 이 아니라 null 입니다.
실행 검증

끌어올린 + 를 풀어 쓰면

표준의 정의("unwraps the operands, applies the underlying operator, and wraps the result")를 C# 2 문법으로 그대로 옮겨 적은 ByHand 를 컴파일러의 a + b 와 나란히 돌립니다.

ByHand 는 출력이 같음을 보이는 풀어 쓰기입니다. 컴파일러가 실제로 내는 IL 과 글자까지 같다는 뜻은 아닙니다.

실행 검증

직접 만든 연산자도 끌어올려진다

표준은 끌어올림이 미리 정의된 연산자뿐 아니라 "user-defined operators" 에도 적용된다고 적습니다. Money 구조체에 + 하나만 정의하면 Money? 끼리도 더해집니다.

실행 검증

null 과의 크기 비교는 언제나 false

표준: 관계 연산자의 끌어올린 꼴은 "produces the value false if one or both operands are null". 같음 비교는 다릅니다 — 두 null 은 같고, null 과 값은 다릅니다.

함정 — !(n < 1) 과 n >= 1 이 다릅니다. n == m 이 True 인데 n <= m 은 False 입니다. 조건을 뒤집어 쓰는 리팩터링이 nullable 에서는 동작을 바꿉니다.
실행 검증

bool? — 세 값 논리

bool? 의 &·| 는 "null 이면 null" 의 예외입니다. 결과가 null 과 상관없이 정해지면 그 값을 냅니다 — null & false 는 false, null | true 는 true.

if 에는 bool 만 들어갑니다. u == true 로 "확실히 참일 때만" 을 적습니다. &&·|| 는 끌어올린 꼴이 없습니다.

연산자 < 는 null 이 끼면 false 이지만, 정렬은 순서가 필요합니다. .NET 의 기본 비교자는 null 을 어떤 값보다도 작게 둡니다.

마지막 줄의 -1 False — 같은 두 값을 Nullable.Compare 는 "작다" 고 하고 < 연산자는 "작지 않다" 고 합니다. 연산자와 비교자가 다른 질문에 답하고 있습니다.

실행 검증

함정 — null 은 Dictionary 의 열쇠가 못 된다

Dictionary<int?, string> 은 컴파일되지만, 열쇠가 null 이면 실행 중에 거절됩니다. 리스트는 null 원소를 받습니다.

형식은 "null 이 될 수 있다" 고 말하는데 컬렉션은 "열쇠는 null 이면 안 된다" 고 말합니다. 형식만 보고는 알 수 없는 규칙이라 함정입니다.

실행 검증

nullable 의 박싱 — 상자에 Nullable 은 없다 C# 2.0

표준: null 인 nullable 을 박싱하면 null 참조, 값이 있으면 바탕 값을 꺼내 박싱합니다. 거꾸로 null 을 nullable 로 언박싱하면 null 이 됩니다.

  • 박싱된 int? 와 박싱된 int 는 구별할 수 없습니다. 그래서 (int?)(object)7 이 됩니다.
  • null 상자를 int 로 꺼내면 NullReferenceException, int? 로 꺼내면 null 입니다.

as 는 int 에는 안 되고 int? 에는 된다

as 는 실패를 null 로 알리는 연산자라 결과 형식이 null 을 담을 수 있어야 합니다. int? 는 담을 수 있습니다.

실행 검증

함정 — GetType 은 Nullable 을 모른다

GetType() 은 object 의 메서드라 부르는 순간 박싱이 일어납니다. 앞 장의 규칙대로 값은 Int32 상자가 되고, null 은 null 참조가 됩니다.

ToString·Equals·GetHashCode 는 Nullable<T> 가 직접 재정의해서 null 에서도 됩니다(빈 문자열, True, 0). GetType 은 재정의할 수 없는 메서드입니다.

실행 검증

nullable 의 nullable 은 없다

표준: System.Nullable<T> 는 T 에 값 형식 제약을 걸고, nullable 은 그 제약을 만족하지 않으므로 T?? 와 Nullable<Nullable<T>> 는 금지된다.

실행 검증

제네릭 안의 T? — struct 제약이 필요하다

C# 2 의 T? 는 Nullable<T> 이고, Nullable<T> 는 T 에 값 형식 제약을 겁니다. 그래서 제네릭 안에서 T? 를 쓰려면 where T : struct 가 있어야 합니다.

같은 자리를 T? 로 적으면(-define:Q) 오류가 둘로 바뀝니다. 둘째 줄이 200칸을 넘어 캡처 대신 컴파일러 출력에서 뽑은 표로 싣습니다.

CS8023 은 "nullable reference types" 게이트이고, CS8627 은 언어 버전 9.0 이상을 요구합니다. 제약 없는 T? 를 C# 2 의 Nullable<T> 로 읽지 않는 것입니다. 참조 형식의 ? 는 다음 장의 이야기이고, 본격적으로는 9부의 것입니다.

실행 검증

string? 은 C# 2 의 문법이 아니다

C# 2 의 ? 는 값 형식에만 붙습니다. 참조 형식의 ?(nullable reference types)는 C# 8 의 기능이라, C# 2 로 컴파일하면 버전 게이트가 거절합니다.

같은 ? 가 값 형식에서는 다른 형식(Nullable<int>)을, 참조 형식에서는 주석을 뜻합니다. 9부에서 다시 만납니다.

실행 검증

3장 퀴즈 — nullable 값 형식

Q. int? n = null; 일 때 n < 1, n >= 1, n == null, ((object)n) == null, n.GetType() 은 각각 무엇입니까?

A. False, False, True, True, 그리고 NullReferenceException. 크기 비교는 null 이 끼면 늘 false 이고(끌어올린 비교), null 인 nullable 을 박싱하면 null 참조가 되며 (박싱), GetType() 은 그 박싱을 거칩니다 (GetType 의 함정).

4장

반복기 — yield 가 쓰는 열거자

yield return · yield break · 늦은 실행 · 컴파일러가 만드는 클래스 · finally 와 Dispose · 함정

반복기 이전 — 열거자를 손으로

버전 기록: 반복기 덕에 "examine all the items in a List (or other Enumerable types) with a foreach loop" 가 쉬워졌고, 언어의 일급 기능이 되면서 "dramatically enhanced readability" 했다. C# 1 에서 foreach 가 도는 형식을 만들려면 이렇게 썼습니다.

하고 싶은 말은 "start 부터 count 개" 한 줄인데, 상태(i)를 담을 클래스와 MoveNext·Current·Reset 을 다 써야 합니다. Current 는 object 라 int 마다 박싱도 됩니다.

실행 검증

yield return — 같은 일을 반복기로 C# 2.0

메서드 본문에 yield return 이 있으면 반복기(iterator)입니다. 컴파일러가 앞 장의 Cursor 같은 클래스를 대신 만듭니다.

이 예제는 일부러 비제네릭 IEnumerable 을 돌려줍니다. IEnumerable<int> 을 쓰면 C# 1 의 거절이 generics 에서 먼저 나와 반복기 게이트가 가려집니다 (1장).

실행 검증

yield break — 여기서 끝 C# 2.0

yield break 는 열거를 끝냅니다. MoveNext 가 false 를 돌려주고, 그 뒤의 본문은 돌지 않습니다.

"(ran off the end)" 는 끝까지 간 둘째 호출에서만 찍힙니다. yield break 는 반복기 안의 return; 입니다 — 반복기 안에서 return 으로 값을 돌려줄 수는 없습니다 (뒤에서).

실행 검증

yield 는 문맥 키워드

표준: "yield is a contextual keyword … and has special meaning only when used immediately before a return or break keyword." 그래서 C# 1 시절의 yield 라는 이름은 지금도 그대로 컴파일됩니다.

그래서 키워드가 하나 늘어도 그 낱말을 이름으로 쓴 옛 코드가 깨지지 않습니다. 표준의 문맥 키워드 목록에는 뒤 버전의 var·async·await 도 같이 있습니다.

실행 검증

부를 때가 아니라 꺼낼 때 돈다

표준: 반복기 메서드를 부르면 "does not immediately execute the code in the iterator block". 본문은 MoveNext 가 불릴 때마다 다음 yield return 까지만 돕니다.

본문과 foreach 몸통이 한 줄씩 번갈아 찍힙니다. 값을 미리 다 만들어 두는 리스트와 다른 점이 이것이고, 뒤의 함정 대부분이 여기서 나옵니다.

실행 검증

컴파일러가 만드는 클래스 C# 2.0

표준: 반복기가 돌려주는 객체는 "typically an instance of a compiler-generated enumerator class" 이고, 그 클래스는 메서드를 담은 클래스 안에 중첩되며 컴파일러만 쓰는 이름을 갖는다.

  • 중첩 클래스이고 [CompilerGenerated] 가 붙어 있습니다. 이름(<Seq>d__… 꼴)은 컴파일러 마음이라 찍지 않았습니다.
  • 인터페이스 다섯 — 열거 가능 객체(IEnumerable)이면서 열거자(IEnumerator)이고, IDisposable 입니다.
  • Seq() 를 부른 뒤에도 ran 은 False, 첫 MoveNext 뒤에 True 입니다.
실행 검증

열거자 객체의 네 상태

표준은 반복기의 열거자 객체가 네 상태를 오간다고 정의합니다. 이 장의 함정 대부분이 이 표로 풀립니다.

상태언제MoveNext 를 부르면
before만들어진 직후본문을 처음부터 실행
running본문이 도는 중정해지지 않음(unspecified)
suspendedyield return 에서 멈춤멈춘 자리 다음부터 이어서
after끝·yield break·예외·Dispose 뒤그냥 false

yield return 이 try 안에 있어도 그때 finally 는 돌지 않습니다. finally 는 끝나거나, yield break 하거나, Dispose 될 때 돕니다.

문서 근거

첫 GetEnumerator 는 자기 자신을 돌려준다

앞에서 본 생성 클래스는 열거 가능 객체이자 열거자입니다. 표준의 주석은 이런 구현이 첫 GetEnumerator 에서 "its own instance" 를 돌려주고, 그 다음부터는 새 인스턴스를 만든다고 설명합니다.

두 열거자는 서로 간섭하지 않습니다(1 2). 첫 번째를 자기 자신으로 주는 것은 할당 하나를 아끼는 구현이고, 언어가 보장하는 성질은 아닙니다.

실행 검증

Current 와 Reset — 표준이 비워 둔 곳

표준은 before·after 상태에서 Current 를 읽은 결과를 "unspecified" 로 두고, Reset 은 NotSupportedException 을 던진다고 정합니다.

0 과 2 는 이 컴파일러가 낸 값일 뿐 기댈 것이 아닙니다. 다시 돌리고 싶으면 Reset 대신 반복기 메서드를 다시 부릅니다.

실행 검증

본문이 던지면 — 예외는 MoveNext 에서, 그 뒤는 after

표준: 예외가 반복기 본문 밖으로 나가면 열거자는 after 상태가 되고 예외는 MoveNext 를 부른 쪽으로 갑니다. 같은 열거자로 "다시 시도" 할 수는 없습니다.

실행 검증

함정 — 인수 검사가 늦게 터진다

반복기 본문의 첫 줄에 쓴 인수 검사도 본문입니다. 그래서 호출할 때가 아니라 처음 꺼낼 때 돕니다.

왜 문제인가 — 잘못된 호출을 한 곳과 예외가 난 곳이 갈라집니다. 열거를 다른 메서드에 넘기거나 나중에 하면 스택 트레이스에 원래 호출이 남지 않습니다.
실행 검증

고치기 — 검사하는 메서드와 반복기를 나눈다

바깥 메서드는 yield 가 없는 보통 메서드라 부르는 즉시 돕니다. 검사를 거기에 두고, 반복은 안쪽 반복기에 맡깁니다.

C# 2 에는 메서드 안의 메서드가 없어서 안쪽 반복기를 형제 메서드로 둡니다. 지역 함수로 한 메서드에 담는 길은 C# 7 에 생깁니다(8부).

실행 검증

break 해도 finally 는 돈다 — Dispose 덕분

foreach 는 루프를 빠져나갈 때 열거자의 Dispose 를 부릅니다. 반복기의 Dispose 는 멈춘 자리에서 yield break 한 것처럼 finally 를 실행합니다.

함정 — MoveNext 를 손으로 부르는 코드가 Dispose 를 잊으면 finally 가 영영 돌지 않습니다. foreach 가 Dispose 를 부르는 규칙은 2부의 C# 1.2 이야기입니다.
실행 검증

반복기 안의 using

using 문은 try/finally 이므로 앞 장의 규칙을 그대로 따릅니다. 파일이나 연결을 여는 반복기를 중간에 멈춰도 자원이 닫힙니다.

실행 검증

catch 가 있는 try 안에서는 yield return 못 한다

표준: yield return 은 catch 절이 있는 try 의 어디에도 올 수 없고, yield 는 finally 안에 올 수 없다.

try/finally 안의 yield return 은 됩니다(앞 장). 예외를 잡아야 하면 yield return 을 try 밖으로 빼고 값을 지역 변수에 받아 둡니다.

실행 검증

반복기가 될 수 없는 메서드

  • ref·out 매개변수는 안 됩니다. 본문은 호출이 끝난 뒤에 돌고, 표준은 열거자 객체가 인수의 사본으로 초기화된다고 적습니다.
  • C# 2 에서 반환 형식은 IEnumerable·IEnumerator 와 그 제네릭판이어야 합니다.
  • 값을 돌려주는 return 은 안 되고 yield break 를 씁니다.

실행 검증

반환 형식이 정하는 yield 형식

반복기의 반환 형식이 IEnumerable<int> 면 yield return 의 식은 int 로 변환돼야 합니다. 비제네릭 IEnumerable 이면 yield 형식은 object 라 무엇이든 됩니다.

2장의 ArrayList 와 같은 이야기입니다. 반복기도 제네릭판을 써야 형식 검사와 박싱 없음을 얻습니다.

실행 검증

함정 — 비제네릭 반복기와 foreach 의 숨은 캐스트

foreach (string s in …) 는 원소마다 (string) 캐스트를 넣습니다. 원소가 object 인 비제네릭 반복기라면 그 캐스트가 실행 중에 실패할 수 있습니다.

2장 첫머리의 ArrayList 와 같은 실패입니다. IEnumerable<string> 을 돌려주게 쓰면 이 실수는 앞 장처럼 컴파일 시간에 막힙니다.

실행 검증

IEnumerator 를 돌려주는 반복기 — GetEnumerator 를 yield 로

반복기는 IEnumerator<T> 를 돌려줄 수도 있습니다. 클래스의 GetEnumerator 를 반복기로 쓰면, 이 장 첫머리의 Cursor 같은 클래스 없이 그 클래스가 foreach 됩니다.

Countdown 은 IEnumerable 을 구현하지 않았습니다. foreach 는 GetEnumerator 라는 메서드만 있으면 됩니다(C# 1 의 규칙). IEnumerator 를 돌려주는 반복기에는 GetEnumerator 가 없어서, 그 결과를 바로 foreach 에 넣을 수는 없습니다.

실행 검증

속성의 get 접근자도 반복기가 된다

표준은 yield 가 메서드 본문뿐 아니라 연산자 본문과 접근자 본문에도 올 수 있다고 적습니다.

실행 검증

함정 — 두 번 돌리면 본문도 두 번

반복기가 돌려준 것은 값의 목록이 아니라 "값을 만드는 방법" 입니다. 다시 열거하면 본문이 처음부터 다시 돕니다.

본문이 파일을 읽거나 질의를 보낸다면 그것도 매번 다시 합니다. 한 번만 돌리려면 new List<int>(xs) 처럼 목록으로 받아 두고 그것을 씁니다.

실행 검증

함정 — 늦게 돌면 늦은 값을 본다

반복기는 부를 때의 src 참조를 기억할 뿐 그 내용을 복사하지 않습니다. 열거하는 동안 원본을 바꾸면 List<T> 의 열거자가 예외를 던집니다 — 반복기 안의 foreach 가 List<T> 를 돌고 있기 때문입니다.

실행 검증

끝없는 수열 — 끝은 부르는 쪽이 정한다

늦은 실행 덕에 끝나지 않는 반복기도 쓸 수 있습니다. 지역 변수 a·b 는 MoveNext 사이에도 값을 지킵니다 — 표준의 말로 suspended 상태가 지역 변수를 저장합니다.

실행 검증

반복기를 잇는 파이프라인

반복기를 받아 반복기를 돌려주는 메서드를 이으면, 원소가 하나씩 단계를 끝까지 통과합니다. 단계마다 중간 목록을 만들지 않습니다.

C# 3 의 LINQ(4부)가 이 모양을 라이브러리와 문법으로 굳힙니다. 여기서는 C# 2 문법만 썼습니다 — 람다 대신 new Predicate<int>(IsEven).

실행 검증

함정 — 반복기 안의 반복기

재귀 구조를 반복기로 걸으면 깊은 곳의 값이 한 층씩 다시 yield 되며 올라옵니다. 그 "올려 주기" 횟수를 셉니다.

n 개 노드에서 n(n+1)/2 번 — 노드 수의 제곱에 비례합니다. 깊이가 깊은 구조는 재귀 반복기 대신 명시적인 스택으로 걷습니다.

실행 검증

뒤 버전과의 맞물림 — 반복기 안의 ref 지역 변수

반복기 본문에 쓸 수 없던 것 중 일부가 C# 13 에서 풀립니다. yield 를 사이에 두지 않는 한 ref 지역 변수를 쓸 수 있게 된 것이 그 예입니다.

이 기능은 14부(C# 13)에서 다룹니다. try/catch 안의 yield return 은 C# 14 에서도 여전히 막혀 있습니다(앞에서).

실행 검증

4장 퀴즈 — 반복기

Q. IEnumerable<int> q = Take(null, 2); 의 Take 는 첫 줄에서 null 을 검사해 ArgumentNullException 을 던지는 반복기입니다. 이 줄에서 예외가 납니까? 나지 않는다면 어떻게 고칩니까?

A. 나지 않습니다. 반복기 본문은 첫 MoveNext 에서야 돌기 때문입니다 (인수 검사). yield 가 없는 바깥 메서드에서 검사하고 실제 반복은 안쪽 반복기에 넘깁니다(나누기).
