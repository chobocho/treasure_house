11부를 읽는 법

버전 기록은 C# 10 의 많은 기능을 한 문장으로 묶습니다 — "Many of the features mean you type less code to express the same concepts." 이 부의 제목이 거기서 왔습니다.

발표 글 "Welcome to C# 10" 을 쓴 캐슬린 돌라드(Kathleen Dollard)는 새 기능이 코드를 "prettier, more expressive, and faster" 하게 만든다고 적었습니다. 앞 조각(1장–3장)은 "덜 쓰기" 쪽, 뒤 조각(4장–7장)은 "더 빠르게" 와 람다 쪽입니다.

  • 1장 — C# 10 개관. 게이트 열여덟, .NET 6, 같이 온 형식, SDK 의 암시적 using, 경고 웨이브 6, 미리 보기 기능.
  • 2장 — 구조체와 record struct. record struct, 매개변수 없는 생성자, 필드 초기화자, 아무 구조체에나 with. 2장.
  • 3장 — global using 과 파일 범위 네임스페이스. 3장.
  • 4장 — 보간 문자열 처리기. 4장.
  • 5장 — 람다와 패턴. 람다의 자연 형식, 확장 속성 패턴. 5장.
  • 6장 — 작은 기능들. 분해, 한정 대입, CallerArgumentExpression 들. 6장.
  • 7장 — 11부 정리와 퀴즈. 7장.

이 부의 예제는 -langversion:10.0 으로 컴파일하고, 게이트가 있는 기능은 C# 9.0 으로 내린 거절을 옆에 둡니다. C# 11 이후에 이어진 것은 "뒤 버전" 이라고 밝힌 장에서만 그 버전으로 컴파일합니다.

같이 온 런타임 — C# 10 이 기대는 형식 C# 10.0

record struct 는 System.IEquatable<R> 를 구현하고, ToString 은 StringBuilder 로 만듭니다. 보간 문자열 처리기와 CallerArgumentExpression, 메서드 단위 AsyncMethodBuilder 는 특성 형식이 바탕이고, 버전 기록은 이 기능들이 ".NET Runtime to achieve performance improvements in .NET 6" 에 쓰였다고 적습니다. .NET 10 에서 그것들이 어디 있는지 봅니다.

SDK 의 암시적 using — global using 위에 선 MSBuild 기능 C# 10.0

왜 — 발표 글: 암시적 using 은 "automatically adds common global using directives for the type of project you are building" 이고, <ImplicitUsings>enable</ImplicitUsings> 로 켜며 .NET 6 템플릿이 켭니다. 언어 기능이 아니라 SDK 기능입니다. 이 덱의 csrun 은 MSBuild 를 거치지 않으므로 그 파일을 만들지 않습니다(0부). 그래서 설치된 SDK 의 목록을 직접 읽습니다.

일곱 개이고 System.Net.Http 에만 조건(.NET Framework 가 아닐 때)이 붙습니다. MSBuild 의 GenerateGlobalUsings 작업이 이 Using 항목들을 <프로젝트 이름>.GlobalUsings.g.cs 파일의 global using 줄로 써서 컴파일에 넣습니다. 지울 때는 <Using Remove="…" />, 더할 때는 <Using Include="…" /> 를 씁니다.

함정 — 예제는 SDK 경로(/usr/lib/dotnet/sdk/10.0.112)를 박아 두었습니다. SDK 를 올리면 다시 맞춰야 합니다.

Q. LangVersion 을 9.0 으로 둔 .NET 6 프로젝트에서 <ImplicitUsings>enable</ImplicitUsings> 를 켜면 어떻게 됩니까?

구조체와 record struct — 클래스와의 틈 메우기

record struct · 값 동등성과 해시 · 출력 · readonly · 위치 필드 · sealed ToString · 매개변수 없는 생성자 · 필드 초기화자 · 아무 구조체에나 with

왜 구조체인가 — "better parity between structs and classes"

발표 글은 C# 10 의 구조체 기능 넷(매개변수 없는 생성자, 필드 초기화자, record struct, with)을 한 절로 묶고, 그 목적을 "better parity between structs and classes" 라고 적습니다.

생성자 명세의 동기도 같은 말입니다 — 매개변수 없는 생성자와 필드 초기화자가 "close an obvious gap between struct and class declarations". 필드 초기화자가 있으면 record struct 가 기본 생성자를 손으로 쓰지 않고도 필드를 채울 수 있다는 것도 동기로 듭니다.

이 장의 차례 — C# 9 의 레코드는 클래스뿐이었습니다(10부의 예고). 이 장은 record struct 가 레코드 클래스와 무엇이 다른지에서 시작해(멤버 → 동등성 → 출력 → readonly → 제약), 구조체의 생성자·초기화자가 언제 돌고 언제 돌지 않는지를 거쳐, with 가 아무 구조체·익명 형식으로 넓어진 데서 끝납니다.
블로그·역사

record struct C# 10.0

왜 — whats-new: "You can declare value type records using the record struct or readonly record struct declarations." 그리고 record class 로 레코드가 참조 형식임을 밝혀 적을 수 있게 됐습니다.

record struct 는 값 형식입니다. b = a 는 복사라서 b.X 를 바꿔도 a 는 그대로입니다. 위치 속성이 set 이고 readonly record struct 면 init 이라는 것, record class 까지 'record structs' 로 거절된다는 것은 10부에서 보았습니다. 여기서는 그 한 줄이 무엇을 만드는지 엽니다.

실행 검증

record struct 와 record class — 만들어지는 멤버

명세: record struct 의 동등성 멤버는 레코드 클래스와 비슷하지만 "except for the lack of EqualityContract, null checks or inheritance" 입니다. 두 레코드의 선언된 멤버를 리플렉션으로 늘어놓습니다. - 는 public 이 아님, ro 는 readonly 멤버(IsReadOnlyAttribute), virt 는 virtual 입니다.

구조체 쪽에는 EqualityContract, <Clone>$, 복사 생성자 .ctor(R) 이 없습니다. 상속이 없으니 형식을 견줄 필요도, 복제 메서드를 virtual 로 둘 필요도 없습니다 — 구조체의 대입이 곧 복사입니다. 그 대신 set_X 를 뺀 거의 모든 멤버가 ro 입니다. 명세는 값을 바꾸는 getter 가 없으면 PrintMembers·ToString·Deconstruct 를 readonly 로 만든다고 정합니다. Equals(R) 의 virt 는 IEquatable<R> 의 구현이라 붙은 것입니다.

문서 근거

record struct 의 값 동등성 C# 10.0

왜 — 구조체는 원래 값으로 비교됩니다. 발표 글: "Record structs add IEquatable<T> support and the == operator." 보통 구조체와 견줍니다.

보통 구조체도 Equals 로는 같다고 나옵니다 — ValueType.Equals 가 필드를 견줍니다. 하지만 IEquatable<T> 가 아니고, == 는 CS0019 입니다. record struct 는 셋 다 됩니다. 명세상 == 는 Equals(R) 을 부르고, 직접 선언하면 오류입니다.

실행 검증

왜 직접 만든 Equals 인가 — 상자와 리플렉션

발표 글: "Record structs provide a custom implementation of IEquatable<T> to avoid the performance issues of reflection". 보통 구조체의 Equals(object) 는 인수를 object 로 받으니 상자(boxing)를 만듭니다. 할당이 생기는지만 봅니다.

record struct 의 Equals(RecPt) 는 값을 그대로 받아 필드마다 EqualityComparer<int>.Default 를 부르므로 할당이 없습니다. 이 덱은 성능 수치를 재지 않습니다 — 여기서 보인 것은 "할당이 있다/없다" 뿐입니다. 리플렉션 비용은 발표 글의 말로만 옮깁니다.

실행 검증

NaN 을 담은 record struct

명세의 "Answered" 절: 합성된 Equals 가 런타임의 구현과 "functionally equivalent … (e.g. float.NaN)" 인지 다시 확인했다 — "confirmed in LDM".

record struct 의 == 는 Equals 를 부르고 Equals 는 double.Equals 를 쓰므로, NaN 끼리도 같습니다. 필드의 == 는 거짓입니다. 튜플은 == 와 Equals 가 갈립니다. 레코드 클래스에서도 같았습니다 (10부) — 레코드의 == 는 "필드마다 ==" 가 아닙니다.

실행 검증

GetHashCode — 명세가 일부러 비워 둔 것

명세: 해시는 필드마다 EqualityComparer<T>.Default.GetHashCode 를 "combining" 한 값입니다. Combine 을 얼마나 정할지에는 "as little as possible", 형식 자체의 해시를 섞을지에는 "no" 라고 답했습니다. int 의 해시는 값 그대로라, 실행마다 같은 수를 찍을 수 있습니다.

형식이 다른 Meters(5) 와 Seconds(5) 의 해시가 같고, 필드가 하나면 그 필드의 해시 그대로입니다. 두 필드는 A * -1521134295 + B 로 섞였습니다 — 이 컴파일러의 구현입니다. 그래서 Pair(1, 2) 와 Pair(2, 1) 이 다릅니다.

함정 — 이 식은 명세가 정한 것이 아니므로 기대면 안 됩니다. 또 string 필드가 있으면 해시가 프로세스마다 달라집니다 (0부).
실행 검증

Equals 를 직접 쓰면 GetHashCode 도

명세: Equals(R) 은 직접 선언할 수 있지만, Equals(R) 과 GetHashCode() 가운데 하나만 직접 쓰면 경고입니다. == 와 != 를 직접 선언하면 오류입니다.

함정 — 합성된 == 는 내가 쓴 Equals 를 따라가 "Ann" == "ANN" 을 참으로 봅니다. 그런데 해시는 합성된 그대로라 두 값의 해시가 다릅니다. 같은 값의 해시가 다르면 HashSet 과 Dictionary 가 깨집니다. CS8851 은 그 경고입니다. == 를 직접 쓰면 "already defines a member called 'op_Equality'" — 합성된 연산자와 부딪칩니다. 레코드 클래스의 같은 경고는 10부에 있습니다.
실행 검증

배열 필드는 참조로 견준다

명세: 합성된 Equals(R) 은 필드마다 EqualityComparer<TN>.Default.Equals 를 부릅니다. 필드가 배열이나 리스트면 그 형식의 Equals, 곧 참조 비교입니다.

함정 — 내용이 같은 두 배열을 가진 a 와 b 는 같지 않고, 같은 배열을 가리키게 바꾸자 같아집니다. List<int> 도 마찬가지입니다. null 끼리는 같습니다. 출력도 System.Int32[] 라 내용을 보여 주지 않습니다 — "값처럼" 은 필드 하나 깊이까지입니다. 레코드 클래스도 같았습니다(10부).

실행 검증

생성자가 도는 곳과 돌지 않는 곳

명세는 C# 9 와 달라지지 않은 것을 하나씩 적습니다 — default 는 "ignores the parameterless constructor", 배열 할당도 "ignores", 다른 형식의 필드는 "zero fields rather than calling any parameterless constructors".

참조를 담은 구조체의 with — 얕은 복사

"first copied" 의 복사는 구조체의 대입과 같은 복사입니다. 필드가 배열이면 배열의 참조가 복사됩니다. 레코드 클래스의 with 도 얕은 복사였습니다 (10부).

함정 — b.Members[0] 을 바꾸자 a 에도 cid 가 보입니다. 구조체라고 깊이 복사되지 않습니다. 따로 갖고 싶으면 마지막 줄처럼 with 안에서 배열을 새로 만들어 넣어야 합니다.
실행 검증

with 의 순서 — 복사 먼저, 그다음 대입 하나씩

명세: 각 초기화자는 "the same way as an assignment to a field or property access of the result" 로 처리되고 "Assignments are processed in lexical order".

적은 차례대로 Y 의 값을 계산해 대입하고, 그다음 X 입니다 — 값 둘을 먼저 다 계산하고 나서 대입하지 않습니다. 원본 a 는 0,0 그대로입니다. 레코드 클래스는 복제 메서드를 먼저 불렀는데(10부), 구조체에는 부를 메서드가 없고 값의 복사가 그 자리를 대신합니다.

실행 검증

with 가 쓸 수 없는 멤버

with 의 대입은 보통의 대입과 같은 규칙을 따릅니다. 그래서 init 은 되고, readonly 필드와 get 전용 속성은 안 됩니다.

CS0191 의 문장이 허용되는 자리로 "init-only setter" 를 꼽는 것이 보입니다. BCL 구조체의 속성 대부분은 get 전용이라(DateTime, KeyValuePair …) with 를 쓸 수 없습니다 — "아무 구조체에나" 는 문법의 이야기이고, 바꿀 멤버가 쓸 수 있어야 합니다.

실행 검증

안쪽 구조체의 멤버를 바꾸려면 — with 안의 with

with 의 왼쪽 이름은 수신자 형식의 필드나 속성 하나여야 합니다(identifier). 점으로 이어 안쪽 멤버를 가리킬 수는 없습니다.

To.Y 는 with 의 문법이 아니라 오류 둘(CS0103, CS0747)입니다. 안쪽 값을 with 로 새로 만들어 바깥 with 에 넣습니다. C# 10 의 확장 속성 패턴({ To.Y: 9 }, 5장)은 읽는 쪽에만 점을 열었습니다.

실행 검증

형식 매개변수에 with — struct 제약이면 된다

record struct 명세의 "Answered" 절은 "with on generics?" 에 "out of scope for C# 10" 이라고 답했습니다. 컴파일러에 물어봅니다.

struct 제약이 있는 T 는 C# 10.0 에서 with 를 받습니다 — 컴파일러가 보기에 T 는 "a struct type" 입니다. 제약을 빼면 T 가 클래스일 수도 있어 CS8858 입니다. 명세의 짧은 답이 정확히 무엇을 가리켰는지는 문서에 더 적혀 있지 않습니다. 이 덱은 컴파일러가 받는 범위만 보입니다.

실행 검증

튜플에도 with — ValueTuple 은 구조체다

C# 7 의 튜플은 System.ValueTuple 구조체입니다(8부). 그러니 "any structure type" 에 들어갑니다.

원소의 이름(Age)으로도, 위치 이름(Item1)으로도 됩니다 — 튜플의 원소는 ValueTuple 의 public 필드이기 때문입니다. 거절도 튜플을 위한 따로의 기능이 아니라 'with on structs' 입니다.

실행 검증

익명 형식의 with C# 10.0

왜 — whats-new 의 말로 익명 형식은 "anonymous (reference) type" 입니다. 속성이 읽기 전용이라 with 의 결과는 언제나 새 객체입니다.

b 는 a 와 다른 객체이지만 같은 익명 형식입니다. 값을 되돌린 c 는 Equals 로 a 와 같고 == 로는 다릅니다 — 익명 형식은 Equals 만 값으로 재정의하고 == 는 참조 비교입니다(4부). 새 속성을 더할 수는 없습니다(CS0117). 4부의 예고는 여기.

C# 10 의 구조체·레코드 기능에 이어진 게이트를 컴파일러의 목록에서 모았습니다.

문서 근거

2장 퀴즈 — 구조체와 record struct

Q. struct Money { public string Currency = "KRW"; public Money(decimal a) { … } } 에서 new Money[3] 의 원소와 new Money() 의 Currency 는 각각 무엇입니까?

A. 둘 다 null 입니다. 초기화자는 선언된 생성자 안에서만 돕니다. 배열의 원소는 생성자를 거치지 않고, new Money() 는 매개변수 없는 생성자를 선언하지 않았으니 default 와 같습니다(초기화자 · 도는 곳과 돌지 않는 곳). public Money() { } 를 더하면 new Money() 만 "KRW" 가 되고, 배열과 default 는 여전히 null 입니다.

3장

global using 과 파일 범위 네임스페이스 — 파일 맨 위의 몇 줄

global using · static 과 별칭 · 순서와 범위 · 모호함과 가려짐 · namespace X; · 규칙 셋 · using 의 자리 · 같은 IL

왜 global using 인가 — 파일마다 되풀이되는 using

언어 버전 기록: "global using directives avoid repeating the same using directives across many files in your program." whats-new: global 을 붙인 지시문은 "applies to all source files in the compilation. This is typically all source files in a project."

발표 글은 둘 곳을 정하지 않습니다 — "any .cs file, including Program.cs or a specifically named file like globalusings.cs". 그리고 세 가지를 나눠 쓰라고 권합니다: 프로젝트 종류의 기본은 암시적 using, 프로젝트 전체에 더할 것은 global using, 몇 파일만 쓰는 것은 그 파일의 using.

이미 본 것 — global using static 의 한 줄(7부), 최상위 문과 만나 한 줄이 된 Program.cs (10부), SDK 의 암시적 using 목록(1장). 이 장은 규칙 — 순서, 범위, 모호함 — 을 봅니다.
문서 근거

global using 지시문 C# 10.0

왜 — 명세: global_using_directive 의 범위는 "the namespace_member_declarations of all compilation units within the program" 입니다. 지시문 하나를 모든 파일에 적은 것과 같은 효과입니다.

Program.cs 와 Report.cs 는 StringBuilder·Environment·Console 을 이름만으로 씁니다. csrun 은 디렉터리의 *.cs 를 모두 한 컴파일에 넣습니다(0부) — 그 컴파일 전체가 범위입니다. 9.0 의 거절은 지시문이 있는 파일의 두 줄에만 나옵니다.

실행 검증

세 가지 꼴 — 네임스페이스, static, 별칭

명세의 문법은 global using 뒤에 세 가지를 받습니다 — 별칭(identifier = …), 네임스페이스, static 형식. 발표 글: "You can use any feature of using within a global using directive."

별칭은 닫힌 제네릭 형식(List<int>)에도 붙습니다. 명세: 별칭은 "can name a closed constructed type, but cannot name an unbound generic type declaration". 전역 별칭은 프로젝트 전체의 이름이 되므로, 명세는 그 이름이 모든 파일의 선언 공간에서 겹치지 않아야 한다고 정합니다.

실행 검증

자리의 규칙 둘 — 맨 앞, 그리고 파일 수준

명세: "The global_using_directives, if any, must precede any using_directives." 그리고 "allowed only on the Compilation Unit level (cannot be used inside a namespace_declaration)".

두 오류 번호가 나란합니다(CS8914, CS8915). 명세는 까닭을 따로 적지 않습니다. 문법이 곧 규칙입니다 — compilation_unit 에서 global_using_directive* 는 using_directive* 바로 앞, 네임스페이스 선언 밖의 자리에만 있습니다.

실행 검증

다른 using 지시문은 global using 을 보지 않는다

명세: 파일 수준의 using 별칭은 "as if … the program had no global_using_directives" 로 풀립니다. 전역 별칭의 대상도 다른 global using 의 영향을 받지 않고, 전역 별칭을 적는 순서는 "has no significance" 입니다.

멤버 안에서는 Col.Queue<int> 가 되는데, using 별칭의 오른쪽에서는 Col 도 Console 도 찾지 못합니다 (CS0246). 보통의 using 별칭이 같은 파일의 using 을 못 보는 규칙(§14.5.2)이 global 에도 그대로 이어진 것입니다. 별칭의 오른쪽은 늘 전체 이름으로 씁니다.

실행 검증

모호함은 프로젝트 전체로 퍼진다

발표 글: "extra using directives increase the possibility of ambiguity in name resolution" — 그러면 별칭을 쓰거나, 들여오는 네임스페이스를 줄이거나, global using 을 몇 파일의 보통 using 으로 바꾸라고 권합니다.

함정 — System.Threading 과 System.Timers 가 모두 Timer 를 가집니다. 지시문이 global 이면 Timer 를 쓰는 모든 파일이 CS0104 입니다. 파일 수준의 별칭 using Timer = … 은 네임스페이스를 들여온 이름보다 먼저 찾아지므로, 그 파일의 모호함만 풉니다.
실행 검증

같은 이름의 형식이 들여온 이름을 가린다

명세: global using 이 들여온 이름은 "hidden by similarly named members in the compilation unit" — 프로그램 안에 같은 이름이 선언돼 있으면 그쪽이 이깁니다.

함정 — 오류도 경고도 없이 내가 만든 Console 이 불립니다. 모호함(앞 장)은 컴파일러가 알려 주지만, 가려짐은 조용합니다. 암시적 using 이 System.IO·System.Threading 같은 넓은 네임스페이스를 들여오는 프로젝트(1장)에서는 File, Path, Timer 같은 이름의 형식을 만들 때 이 규칙이 작동합니다.
실행 검증

global using static 과 확장 메서드

명세: global_using_static_directive 는 "does not import extension methods directly as static methods, but makes them available for extension method invocation".

Range 는 정적 멤버라 이름만으로 불리고, Where 는 확장 메서드라 xs.Where(…) 로만 보입니다 — using System.Linq; 없이도 됩니다. C# 6 의 using static 과 같은 규칙입니다(7부).

실행 검증

파일 범위 네임스페이스 namespace X; C# 10.0

왜 — whats-new: 새 꼴은 "declare that all declarations that follow are members of the declared namespace" 이고 "saves both horizontal and vertical space".

중괄호도, 한 단계의 들여쓰기도 없습니다. using System; 이 namespace 줄 뒤에 있는 것을 보십시오 — 명세의 첫 예가 이 꼴이고, 그 using 은 네임스페이스 안에 있는 것으로 읽힙니다(뒤에서).

실행 검증

왜 — "99.7% files"

명세의 동기: C# 생태계를 분석해 보니 "approximately 99.7% files" 가 네임스페이스 하나를 가진 두 꼴 가운데 하나였습니다 — using 이 네임스페이스 안에 있거나 밖에 있거나. 두 꼴 모두 "force the user to indent the majority of their code and add a fair amount of ceremony for what is effectively a very basic concept" 입니다.

명세가 정한 것뜻
namespace X.Y.Z; 는 나머지 파일 전체를 { … } 에 넣은 것과 같다새 의미가 없는 문법 — IL 이 같은지 확인한다

블록 네임스페이스와 섞을 수 없다규칙
최상위 문과 함께 쓸 수 없다 · 형식이 앞설 수 없다10부 · 규칙

목표는 한 줄로 적혀 있습니다 — "meet the needs of the majority of the ecosystem with less unnecessary boilerplate".

문서 근거

규칙 셋 — 하나만, 섞지 않기, 맨 앞에

명세: "A source file cannot contain both a file_scoped_namespace_declaration and a namespace_declaration. A source file cannot contain multiple file_scoped_namespace_declarations." 그리고 "type_declarations cannot precede" 그것을.

세 번호가 이어집니다(CS8954, CS8955, CS8956). 형식이 앞설 때의 CS8956 은 최상위 문이 앞설 때와 같은 오류입니다 (10부). "점으로 이은 이름" 은 중첩을 뜻하니(뒤에서), 중첩이 필요하면 namespace Shop.More; 처럼 한 줄에 적습니다.

실행 검증

namespace X; 뒤의 using 은 네임스페이스 안에 있다

명세: 파일 범위 선언 뒤의 using_directive 들은 "act as if they were declared in the same order inside the namespace_body". 즉 블록 꼴의 "using 이 네임스페이스 안" 과 같습니다.

함정 — 같은 using Data; 가 자리에 따라 다른 네임스페이스를 엽니다. 네임스페이스 안의 이름 Data 는 먼저 App.Data 로 풀리고, 파일 수준에서는 전역의 Data 입니다. 블록 꼴을 파일 범위로 바꾸는 도구가 using 을 어느 쪽에 두는지에 따라 프로그램의 뜻이 바뀔 수 있습니다.
실행 검증

global using 은 namespace X; 보다 앞에

앞의 두 규칙이 만납니다. global using 은 네임스페이스 안에 둘 수 없고(앞에서), namespace X; 뒤의 지시문은 네임스페이스 안에 있습니다.

블록 네임스페이스 안에 둔 것과 같은 CS8914 입니다. 파일 범위 네임스페이스에는 닫는 중괄호가 없어서 "안" 이 눈에 보이지 않을 뿐입니다.

실행 검증

점으로 이은 이름 — 바깥 네임스페이스도 생긴다

명세가 바꾼 것은 문법뿐이고, namespace Shop.Billing; 은 namespace Shop.Billing { … } 와 같습니다. 블록 꼴에서 점으로 이은 이름은 중첩된 선언과 같습니다.

Invoice 는 Shop.Billing 에, 다른 파일의 Tax 는 Shop 에 있습니다. 파일마다 하나의 파일 범위 선언을 쓰되 서로 다른 깊이를 써도 됩니다.

실행 검증

두 꼴의 IL 은 같다

"semantically equivalent" 를 확인합니다. 같은 Cart 를 블록 꼴과 파일 범위 꼴로 컴파일하고, 형식의 전체 이름과 메서드 IL 바이트의 SHA-256 을 찍습니다.

이름도, IL 의 바이트 수도, 해시도 같습니다. 견준 것은 형식과 메서드 IL 이고, 어셈블리 파일 전체는 견주지 않았습니다 — 같아야 할 것은 코드이지 원본의 글자가 아닙니다.

실행 검증

3장 퀴즈 — global using 과 파일 범위 네임스페이스

Q. 블록 꼴 파일 using Data; namespace App { … } 을 파일 범위 꼴 namespace App; using Data; … 으로 바꿨더니 다른 Store 가 불립니다. 왜입니까?

A. namespace App; 뒤의 using 은 네임스페이스 안에 있는 것으로 읽힙니다. 안에서는 Data 라는 이름이 먼저 App.Data 로 풀리므로, 전역 Data 대신 App.Data 를 엽니다(3장). 원래 뜻을 지키려면 using 을 namespace App; 줄 앞에 둡니다.
