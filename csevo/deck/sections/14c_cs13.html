오버로드 해석 우선순위 — 라이브러리가 판을 고른다

왜 · 특성 하나 · 규칙 · 상속과 확장 메서드 · 부를 수 없게 되는 판 · 음수 · 언어 버전 · .NET 10 의 쓰임 · 붙일 수 없는 곳 · 퀴즈

왜 — 새 오버로드를 더하면 모호해지거나 밀린다

제안서의 동기: 옛 멤버를 남겨 둔 채 새 멤버를 더하면 옛 멤버가 "may cause unwanted overload resolution failures when there is a perfectly good alternative" 입니다. 예로 든 것 하나가 StringValues — string 과 string[] 양쪽으로 암시적 변환이 있어 params string[] 와 params ReadOnlySpan<string> 오버로드에 넘기면 "it is ambiguous" 입니다.

배열 판은 Values → string[] 로 정상 꼴, 스팬 판은 Values → string 으로 확장 꼴에 맞습니다. 둘 다 사용자 정의 변환 하나라 컴파일러는 어느 쪽도 더 낫다고 보지 않습니다. "x", "y", "z" 는 모호하지 않습니다 — 스팬 판이 이깁니다(2장). 13부는 풀리지 않는 모호함 하나를 C# 14 에서도 CS0121 로 보았습니다(13부).

실행 검증

오버로드 해석 우선순위 (overload resolution priority) C# 13.0

왜 — whats-new: "the compiler recognizes the OverloadResolutionPriorityAttribute to prefer one overload over another. Library authors can use this attribute to ensure that a new, better overload is preferred over an existing overload." 예제는 제안서의 것 그대로입니다.

배열 변수 arr 는 보통 int[] 판(항등 변환)에 맞습니다. 특성이 붙으면 그 판은 후보에서 빠지고 Span 이 찍힙니다. 컬렉션 식 [4, 5] 는 특성이 없어도 스팬 판입니다. C# 12.0 의 거절은 특성을 붙인 자리 하나, 기능 이름은 overload resolution priority 입니다.

실행 검증

앞의 모호함을 특성 하나로 풀면

whats-new: "This feature is intended for library authors to avoid ambiguity when adding new overloads." 앞 장의 Log 에서 스팬 판에만 [OverloadResolutionPriority(1)] 을 붙입니다(#if PRI).

Log.Write(v) 가 스팬 판을 부릅니다. 원소가 하나인 것은 v 가 string 으로 바뀌어 확장 꼴로 들어갔기 때문입니다 — "a,b" 한 개입니다. 부르는 쪽 코드는 한 글자도 바뀌지 않았습니다. 라이브러리를 다시 받아 컴파일만 하면 오류가 사라지는 것, 이것이 제안서가 말한 "steering API consumers" 입니다.

실행 검증

규칙 — 적용 가능한 후보를 선언한 형식마다 묶어 거른다

제안서는 표준 §12.6.4.1 의 "가장 나은 멤버 고르기" 앞에 묶고 거르는 단계를 끼웁니다. 우선순위는 32비트 정수, 기본값은 0 입니다.

  • 적용 가능한 후보만 남긴다(전과 같다).
  • 남은 후보를 선언한 형식으로 묶는다. 묶음마다 우선순위가 가장 높은 것보다 낮은 후보를 지운다. override 의 우선순위는 "the least-derived declaration" 에서 온다.
  • 묶음들을 다시 합친다. 그다음 보통의 "더 나은 함수 멤버" 비교(§12.6.4.3)로 하나를 고른다.

거르기는 "the very end of the overload resolution process" 에 일어나므로 "a base type cannot make its members higher-priority than any derived type" 입니다 — 제안서는 이것을 의도라고 적습니다. 음수도 됩니다: "can be used to mark a specific overload as worse than all other default overloads". 다음 세 장이 묶음의 경계를 컴파일러로 확인합니다.

문서 근거

파생 형식이 이긴다 — 우선순위는 형식의 경계를 넘지 않는다

제안서의 둘째 예: Base 의 스팬 판에 우선순위 1 이 있어도 Derived 의 배열 판이 불린다 — "members from Base are not considered due to finding an applicable member in Derived".

첫 줄은 제안서대로 Derived 입니다. 우선순위를 보기 전에, 파생 형식에 적용 가능한 멤버가 있으면 기반 형식의 멤버는 후보가 되지 않습니다. Base 로 캐스트하거나 스팬을 직접 넘겨 Derived.M(int[]) 이 맞지 않게 하면 그제야 Base 의 판이 불립니다.

실행 검증

확장 메서드 — 담은 정적 클래스마다 따로

제안서의 열린 질문 하나: 확장 메서드는 같은 범위의 것을 한데 놓고 우선순위를 비교해야 할까? 답은 "We will always group. The above example will print Ext2 ReadOnlySpan".

Ext1 묶음에서는 우선순위 1 의 Span 판만 남고, Ext2 묶음에는 ReadOnlySpan 판 하나가 남습니다. 합친 둘을 보통 규칙으로 견주니 Ext2 의 ReadOnlySpan 판이 이겼습니다 — Ext1 에 우선순위 1 이 붙어 있어도 다른 클래스의 판을 누르지 못합니다. Ext1.M(…) 처럼 클래스를 적어 부르면 묶음이 하나뿐이라 Span 판입니다.

실행 검증

함정 — 부를 수 없게 되는 오버로드

제안서의 "Callability of members": 우선순위는 "can make certain members effectively uncallable from source". 우회로의 첫째로 "Converting the method to a delegate" 를 들고, M3(object) 처럼 참조 형식의 가변성이 걸리면 "this strategy will fail" 이라고 적습니다.

함정 — M1 은 대리자로도 못 부릅니다. 메서드 그룹 변환도 오버로드 해석이라 우선순위가 M1(int) 을 먼저 지우고, 남은 M1(long) 은 Action<int> 에 맞지 않아 CS0123 입니다(C# 14.0 도 같다). M3 는 제안서 말대로 오류 없이 M3(object) 로 갑니다. 남는 길은 리플렉션입니다.
실행 검증

음수 우선순위 — 옛 판을 뒤로 미는 쪽

제안서가 꼽은 BCL 의 (가상의, "hypothetical") 쓰임 첫째는 Debug.Assert 에 CallerArgumentExpression 판을 더하고 "make it preferred over the existing overload" 하는 것입니다. 새 판을 올리는 대신 옛 판을 -1 로 내려도 같습니다.

특성이 없으면 기본값을 채울 필요가 없는 That(bool) 판이 이겨 글자가 실리지 않습니다 — CallerArgumentExpression(11부) 판을 더하기만 해서는 소용이 없던 까닭입니다. -1 이 그 판을 지워 실패한 식의 글자가 찍힙니다. 이 예제를 C# 12.0 으로 내리면 특성을 붙인 자리에서 거절됩니다 — 다음 장의 BCL 과는 다릅니다.

실행 검증

게이트는 붙이는 쪽에만 — 메타데이터의 특성은 C# 12 가 조용히 무시

제안서의 "Langversion Behavior": 구현은 "only issues langversion errors when OverloadResolutionPriorityAttribute is applied, not when it actually influences anything". 참조한 라이브러리의 특성은 "silently ignoring the attribute in previous language versions" 로 정했습니다. "Debug.Assert(bool) is being de-prioritized in .NET 9" 가 그 이유로 적혀 있습니다.

같은 소스, 같은 .NET 10 참조인데 언어 버전만 바꾸니 출력이 달라집니다. C# 13 은 우선순위 -1 인 Assert(bool) 를 지우고 메시지 매개변수에 식의 글자를 채우는 판을 부릅니다. C# 12 는 특성을 모르는 척하고 옛 판을 불러 메시지가 빈 문자열입니다. 이 덱의 증거 방식 (나) — 언어 버전에 묶인 동작 — 의 한 예입니다(0부).

실행 검증

.NET 10 은 어디에 쓰나 — 모두 -1 C# 13.0

왜 — 컴파일러가 읽는 것은 참조 어셈블리입니다. 이 기계의 참조 팩(Microsoft.NETCore.App.Ref 10.0.12)에서 메서드에 붙은 OverloadResolutionPriorityAttribute 를 메타데이터로 직접 셉니다.

63개 메서드, 값은 모두 -1 입니다 — 어느 판을 올린 곳은 없고 모두 기본값 0 아래로 내린 것입니다. 56개가 MemoryExtensions 입니다. 참조 어셈블리는 실행할 수 없는 메타데이터 껍데기라 리플렉션 대신 System.Reflection.Metadata 로 읽었습니다. .NET 9 의 참조 팩은 이 기계에 없어 C# 13 이 나온 날의 수는 셀 수 없습니다(2026-10 기준).

실행 검증

붙일 수 없는 곳 — 무시될 자리면 오류

제안서: 인덱서 아닌 속성, 접근자, 변환 연산자, 람다, 지역 함수, 종료자, 정적 생성자에 붙이면 오류입니다. override 처럼 "a location it would be ignored" 도 오류입니다 — 경고나 무시보다 "the most cautious approach" 를 골랐습니다.

번호는 둘입니다. override 만 CS9261 "on an overriding member" 이고, 나머지 일곱은 모두 CS9262 "on this member" 입니다. 제안서가 "not currently blocked" 라고 적었던 지역 함수도 지금은 막혀 있습니다(같은 절의 답 "All of the locations listed above are blocked"). 갈래마다의 문장은 장 끝의 표에 있습니다.

실행 검증

override 와 인터페이스 구현 — 어디의 우선순위를 읽나

제안서: 우선순위는 "the least-derived declaration" 에서 읽고, 인터페이스 멤버를 구현한 멤버에게는 "not inherited or inferred" 입니다 — params 수식어가 하는 대로입니다.

첫 줄: Derived 의 override 에는 특성이 없지만(붙이면 CS9261) Base 선언의 1 을 물려받아 object 판이 불립니다. 둘째 줄: C 의 구현 메서드에는 우선순위가 없어 보통 규칙대로 string 판입니다. 셋째 줄: 같은 객체를 I 로 부르면 인터페이스 선언의 1 이 보여 object 판입니다. 받는 변수의 형식이 결과를 가릅니다.

6장의 진단 한눈에

이 장의 거절 캡처에서 첫 오류의 번호와 문장을 뽑았습니다.

언어 버전의 거절은 CS9202 하나이고, 특성이 놓인 자리를 따지는 새 번호는 CS9261·CS9262 둘입니다. CS0121 과 CS0123 은 오래된 오버로드 진단 그대로입니다 — 우선순위는 진단을 늘리기보다 후보를 줄이는 쪽입니다.

6장 퀴즈 — 오버로드 해석 우선순위

Q. .NET 10 을 참조하는 프로젝트를 -langversion:12.0 으로 컴파일합니다. Debug.Assert(n > 5) 가 실패하면 메시지에 식의 글자 n > 5 가 실릴까요? 같은 프로젝트에 우선순위 특성을 직접 붙인 메서드가 있다면요?

A. 실리지 않습니다. C# 12 는 참조 어셈블리의 우선순위 -1 을 조용히 무시하고 옛 판 Assert(bool) 를 불러 메시지가 빈 문자열입니다 (앞에서). 특성을 소스에 직접 붙이면 그 자리가 CS9202 로 거절됩니다(앞에서). 게이트는 특성을 "붙이는" 쪽에만 있습니다.

작은 기능들 — \e, 메서드 그룹, 초기화자의 ^

ESC 문자 · \x 의 함정 · 메서드 그룹의 자연 형식 · 범위마다 · 깨지는 변경 · 개체 초기화자의 끝에서 세는 인덱스 · 평가 순서 · 퀴즈

새 이스케이프 시퀀스 \e (escape sequence) C# 13.0

왜 — whats-new: "You can use \e as a character literal escape sequence for the ESCAPE character, Unicode U+001B. Previously, you used \u001b or \x1b." 제안서는 '\e' 가 넷과 같아야 한다고 적습니다 — (char)0x1b, '\u001b', '\U0000001b', '\x1b'.

넷 다 True, "\e[1m" 은 네 글자 1B 5B 31 6D 입니다. C# 12.0 은 \e 가 나온 두 곳을 모두 거절합니다. MessageID.cs 가 이 기능에만 "lexer check" 를 붙인 대로 어휘 분석기가 리터럴마다 확인합니다 — 그래서 같은 파일의 다른 거절을 가립니다(1장).

실행 검증

왜 \x1b 가 아닌가 — 16진 자리가 넷까지 늘어난다

whats-new: "Using \x1b wasn't recommended because if the next characters following 1b were valid hexadecimal digits, those characters became part of the escape sequence." 표준의 문법은 '\\x' Hex_Digit Hex_Digit? Hex_Digit? Hex_Digit? 이고, 같은 절의 주석이 "\x9Bad text" 가 U+9BAD 로 시작한다는 예를 듭니다.

함정 — "\x1b7" 은 두 글자가 아니라 U+01B7 한 글자이고, "\x1bE1" 은 U+1BE1 입니다. 컴파일러는 아무 말도 하지 않습니다. [ 처럼 16진 숫자가 아닌 글자가 뒤따를 때만 생각한 대로 됩니다. \u 는 언제나 네 자리라 안전하지만 길고, \e 는 짧고 뒤의 글자를 삼키지 않습니다.
실행 검증

\e 가 통하는 리터럴 — 다른 이스케이프와 같은 자리

제안서의 설계는 표준의 Simple_Escape_Sequence 에 '\\e' 하나를 더하고 표에 "Escape character" · U+001B 줄을 붙이는 것뿐입니다. 그러니 \n 이 통하는 곳에서 통하고, 통하지 않는 곳에서 통하지 않아야 합니다.

보간 문자열과 UTF-8 리터럴(12부)에서도 1B 입니다. 축자 문자열(@)과 원시 문자열(12부)은 이스케이프를 해석하지 않으니 글자 둘 \·e(5C 65)입니다. 대문자 \E 는 없는 시퀀스라 CS1009 "Unrecognized escape sequence" 입니다 — 대소문자를 가리는 것도 다른 이스케이프와 같습니다.

실행 검증

C# 12 까지의 ESC — 그리고 꺼진 #if 안의 \e

표준: 조건부 컴파일로 건너뛴 구역은 "no tokens, except those for pre-processing directives, are generated" 이고 "skipped source code ... may be lexically incorrect" 입니다. 어휘 분석 단계의 게이트인 \e 에도 그대로일까요? 이 예제는 -langversion:12.0 프로젝트입니다.

기호를 켜지 않으면 C# 12.0 이 \e 가 든 줄을 보지도 않아 거절이 없습니다. 켜는 순간 CS9202 입니다. 여러 언어 버전으로 빌드하는 라이브러리라면 \e 를 버전 기호 뒤에 둘 수 있다는 뜻입니다. 네 길 가운데 \x1b 는 앞 장의 함정을 안고 있습니다.

C# 10 은 var f = M; 처럼 대상 형식 없이 메서드 그룹을 쓸 수 있게 했습니다(11부). 그 규칙은 "A method group has a natural type if all candidate methods in the method group have a common signature" 이고, 후보에는 "the containing type and all extension method scopes" 가 다 들어갑니다.

문서 근거

메서드 그룹 자연 형식의 개선 (method group natural type) C# 13.0

왜 — whats-new: "The new behavior is to prune the set of candidate methods at each scope ... The process continues to the next outer scope only if no candidate methods are found." 인스턴스 메서드와 서명이 다른 확장 메서드가 함께 있을 때가 가장 흔한 경우입니다.

C# 13 은 인스턴스 범위에서 M(int) 하나를 찾고 멈춰 Action<int> 입니다. C# 12 는 확장 메서드까지 모아 서명이 둘이라 CS8917 입니다. 거절의 문장에 기능 이름이 없습니다 — 게이트(1장의 아홉)가 아니라 언어 버전에 따라 다른 알고리즘을 고르는 것입니다. Roslyn 문서도 "this does not affect LangVersion=13 and later because of a different delegate inference algorithm" 이라고 적습니다.

확장 메서드도 안쪽 범위부터

제안서: 첫 범위 다음은 "each scope subsequent scope of extension methods" 입니다 — 확장 메서드는 둘러싼 이름공간마다 범위가 하나씩입니다.

Program 에서 가까운 Inner 범위에 후보가 하나 있으니 C# 13 은 거기서 멈춥니다. C# 12 는 두 범위를 한데 모아 서명이 갈려 다시 CS8917 입니다. 오버로드 해석이 확장 메서드를 안쪽 범위부터 찾는 것과 같은 순서입니다.

실행 검증

함정 — 자연 형식은 확장 메서드에서, 부르는 것은 제네릭 인스턴스 메서드

제안서: 첫 범위에서는 "methods on the relevant type with arity matching the provided type arguments" 만 후보입니다 — var f = c.M; 처럼 형식 인수가 없으면 제네릭 M<T> 는 빠집니다.

함정 — Action<int> 라는 형식은 확장 메서드 E.M(int) 에서 왔는데, 불린 것은 C.M<T> 입니다. 자연 형식을 정한 뒤의 변환은 보통의 오버로드 해석이라 T = int 로 추론되는 인스턴스 메서드가 확장 메서드를 이깁니다. 확장 메서드를 지우면 후보가 하나도 없어 CS8917 입니다. C# 12.0 은 확장 메서드가 있어도 CS8917 입니다(장 끝의 표).
실행 검증

제약을 못 맞추는 제네릭 확장 메서드를 뺀다

제안서: 확장 메서드 범위의 후보는 "can be substituted with the provided type arguments and reduced using the value of the receiver while satisfying contstraints" 인 것만입니다(오타는 원문).

M<string> 이면 첫 판은 struct 제약에 걸려 빠지고, 남은 판의 서명 (string, int) 가 자연 형식 Action<string, int> 이 됩니다. C# 12 는 제약을 보지 않고 두 판을 다 후보로 둬 서명이 갈립니다.

실행 검증

깨지는 변경 — 기본값과 params 가 자연 형식을 가른다 C# 13.0

왜 — Roslyn 문서(17.13): 전에는 기본값이나 params 가 있으면 컴파일러가 "unexpectedly inferred different delegate type depending on the order of candidates in source" 였고, 이제는 모호함 오류입니다. 또 C# 12 이하에서는 "params modifier must match across all methods" 입니다. 예제의 Test1·C.M·E.M 은 문서의 것입니다.

둘째 예는 문서대로입니다 — C# 12 에서 CS8917, C# 13 은 인스턴스 범위의 C.M 하나로 정해집니다. 첫째 예(Test1, 문서: "previously Action<long[]> - now error")는 C# 13 에서도 CS8917 입니다. 두 확장 메서드가 같은 범위에 있고 하나만 params 라서입니다. 이쪽은 언어 버전이 아니라 17.13 컴파일러의 수정이라, 지금의 SDK 로는 옛 결과를 볼 수 없습니다.

개체 초기화자의 암시적 인덱스 (implicit index access) C# 13.0

왜 — whats-new: "The implicit 'from the end' index operator, ^, is now allowed in an object initializer expression for single-dimension collections." 예제는 whats-new 의 TimerRemaining 그대로입니다. "In versions before C# 13, the ^ operator can't be used in an object initializer."

9 8 … 0 — 열 칸을 뒤에서부터 채웠습니다. C# 12.0 은 열 줄 하나하나를 implicit indexer initializer 로 거절합니다. 9부는 Buffer 형식으로 같은 일을 앞당겨 봤습니다(9부). 이 장은 그다음 — 언제 길이를 읽는지, 무엇이 안 되는지를 봅니다.

실행 검증

초기화자의 ^ — 받는 쪽을 원소마다 두 번 읽는다

C# 8 의 제안서: 암시적 ^ 는 받는 쪽 → 인수 → 길이 순으로 셈하고, "The receiver and Length expressions will be spilled as appropriate to ensure any side effects are only executed once" 입니다(9부). 중첩된 개체 초기화자 B = { [^1] = … } 에서는 어떨까요?

초기화자의 [^1] 하나에 get B 가 두 번입니다 — 길이를 읽으려고 한 번, 인덱서에 쓰려고 또 한 번. 값 V(9) 는 길이를 읽은 뒤에 셈합니다. 같은 초기화자라도 [3] 이면 get B 는 한 번이고, 문장 h.B[^4] = … 도 받는 쪽을 한 번만 읽습니다(마지막 get B 는 출력 줄의 것). 제안서의 "only executed once" 와 다릅니다 — 받는 쪽 속성에 부수 효과가 있다면 C# 13 의 초기화자에서만 그 효과가 두 배입니다(2026-10 기준, SDK 10.0.112).

실행 검증

함정 — 초기화하는 순간의 길이로 센다

whats-new 는 이 기능을 "single-dimension collections" 에 대해 적고, 예제는 처음부터 길이가 10 인 배열입니다. ^1 은 "길이 − 1" 이니(9부) 초기화자가 도는 그 순간의 길이가 답을 정합니다.

함정 — new List<int> { [^1] = 5 } 는 "마지막 원소를 5 로" 가 아닙니다. 그때 Count 가 0 이라 인덱스 -1 에 쓰려다 ArgumentOutOfRangeException 입니다. 컴파일러는 경고하지 않습니다. 생성자 인수로 원소를 먼저 넣은 List 는 1 2 9 입니다. Dictionary<int, string> 는 Count 와 int 열쇠의 인덱서가 있어도 Index 를 받지 않습니다(CS1503).
실행 검증

초기화자의 범위 — Slice 의 길이 인수가 어긋난다

언어 버전 기록은 이 기능을 "allows indexers in object initializers to use implicit Index/Range indexers" 라고 적습니다 — ^ 만이 아니라 범위(..)도입니다. 암시적 범위는 Slice(start, length) 로 낮춰집니다(9부).

함정 — 문장 h.B[1..3] 은 Slice(1, 2), [2..^1](길이 8)은 Slice(2, 5) 로 맞습니다. 같은 범위를 초기화자에 쓰면 Slice(1, 1)·Slice(2, 2) — 길이 자리에 시작 값이 들어갑니다. 이 기계의 SDK 10.0.112 에서 C# 14.0 도 같습니다 (2026-10 기준). 배열의 범위는 C# 8 부터 새 배열을 만드는 복사라(9부) [0] = 7 이 사라지고, C# 12.0 도 거절하지 않습니다.

왜 — whats-new(C# 13): "The field contextual keyword is in C# 13 as a preview feature. The token field accesses the compiler synthesized backing field in a property accessor." 그리고 "We want to learn from your experiences using it." C# 14 의 whats-new 는 같은 기능을 정식 기능으로 싣습니다.

C# 13 까지의 field — 접근자 안의 보통 이름

14부 퀴즈 (1) — 게이트와 언어 버전

Q. C# 13 의 변화 가운데 CS9202 없이 C# 12.0 에서 다른 결과를 내는 것을 이 부에서 둘 고르면?

A. 예를 들어 메서드 그룹의 자연 형식(C# 12.0 은 CS8917, 7장)과 참조 어셈블리의 우선순위 특성(C# 12.0 은 조용히 무시해 Trace.Assert 의 메시지가 빈 문자열, 6장). 컬렉션 식의 더 나은 변환(2장)도 언어 버전에 묶여 있습니다. 반대로 record struct 의 [InlineArray] 오류는 C# 12.0 에서도 같습니다(1장).

14부 퀴즈 (2) — field

Q1. 필드 private int field = 7; 이 있는 클래스의 속성 A { get { return field; } } 는 C# 13 과 C# 14 에서 각각 무엇을 돌려줄까요?

Q2. 그 클래스에서 C# 14 로 올려도 7 을 돌려주게 하려면?

A1. C# 13 은 필드를 읽어 7, C# 14 는 새 뒷받침 필드를 읽어 0 이고 경고 CS9258 이 납니다(8장).
A2. this.field 나 @field 로 씁니다. 지역 변수의 이름이 field 라면 선언도 @field 로 써야 C# 14 의 CS9273 을 피합니다(8장).

14부 퀴즈 (3) — 같은 꼴, 다른 뜻

Q. 길이 4 짜리 배열 속성 Arr 를 가진 객체를 new H { Arr = { [^1] = 7 } } 로 만들면 마지막 칸이 7 일까요? { Arr = { [1..3] = { [0] = 7 } } } 이면 Arr[1] 이 7 일까요?

A. 앞의 것은 그렇습니다 — 초기화자의 ^1 은 그 순간의 길이 4 로 셈해 [3] 입니다(7장). 뒤의 것은 아닙니다. 배열의 범위는 새 배열을 만드는 복사라 7 은 그 사본에 쓰이고 사라집니다 — C# 12.0 도 거절하지 않습니다(7장의 0 0 0 0).
