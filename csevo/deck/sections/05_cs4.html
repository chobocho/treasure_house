5부를 읽는 법

버전 기록은 C# 4.0 의 기능 넷 가운데 셋을 "none of those features are exactly paradigm altering" 이라고 한 줄로 정리하고, 나머지 하나를 따로 꼽습니다. "The major feature was the introduction of the dynamic keyword."

  • 1장 — C# 4.0 개관. 문서의 목록 넷과 컴파일러의 게이트 넷, 그리고 같이 온 런타임.
  • 2장 — dynamic. 바인딩을 실행 시간으로 미루는 형식. 이 부의 절반입니다.
  • 3장 — 명명 인수와 선택적 매개변수. 오버로드 사슬을 줄이는 법과, 기본값이 사는 곳.
  • 4장 — 제네릭 인터페이스·대리자의 변성. out T 와 in T.
  • 5장 — COM 과 그 밖의 것. 내장 interop 형식, ref 생략, 인덱스 속성.

이 부의 예제는 거의 전부 -langversion:4 로 컴파일합니다. 그래서 문자열 보간, => 본문 멤버, nameof 없이 C# 4 시절의 모양 그대로 씁니다. 뒤 버전과의 맞물림을 보이는 예제만 그 버전으로 올립니다.

dynamic 은 키워드가 아니다

그렇다면 dynamic 이라는 이름의 클래스를 직접 만들면 어떻게 될까요. 표준의 키워드 목록에 dynamic 은 없고, 문맥 키워드 목록에 있습니다.

이름 찾기가 내 클래스를 먼저 찾았으므로 d 의 형식은 그 클래스이고, 동적 바인딩은 일어나지 않습니다. C# 4 는 그 이름을 찾지 못했을 때에만 dynamic 을 동적 형식으로 읽습니다. 그래서 C# 3 시절의 코드에 있던 dynamic 이라는 형식 이름은 C# 4 에서도 뜻이 바뀌지 않았습니다.

실행 중에는 object 와 같다

표준: "The type dynamic is indistinguishable from the type object at run-time." 그리고 둘 사이에는 항등 변환이 있습니다.

  • typeof(List<dynamic>) 는 List`1[System.Object] 입니다. 실행 중에 dynamic 이라는 형식은 없습니다.
  • List<object> 를 그대로 List<dynamic> 변수에 담습니다. 같은 객체입니다.
  • d.GetType() 은 정적 형식이 아니라 값의 형식을 말합니다 — object 일 때와 같습니다.

실행 중 바인딩의 실패 — 문장은 컴파일러의 것

동적 바인딩이 실패하면 예외가 납니다. 그 메시지를 모아 봅니다. 하나같이 컴파일 오류처럼 읽힙니다 — 실행 중의 바인더가 C# 의 규칙과 진단 문장을 그대로 쓰기 때문입니다.

실행 중 오버로드 해석 — 두 인자의 실제 형식으로

표준: 동적으로 바인딩된 연산에서 "A subexpression of compile-time type dynamic is considered to have the type of the actual value". 인자 둘을 dynamic 으로 바꾸면 오버로드 해석이 두 인자의 실제 형식을 보고 다시 일어납니다.

정적 호출은 네 번 다 Shape-Shape 입니다. 변수의 형식이 Shape 이기 때문입니다. dynamic 호출은 실제 짝마다 가장 잘 맞는 오버로드를 고릅니다. Square, Circle 짝에는 Hit(Shape, Shape) 와 Hit(Square, Shape) 가 맞고, 더 구체적인 Hit(Square, Shape) 가 골라집니다. 방문자(visitor) 패턴 없이 두 인자로 디스패치하는 셈입니다.

표준의 바인딩 목록에는 메서드 호출만이 아니라 단항·이항 연산자, 대입 연산자, 변환이 다 들어 있습니다. 같은 a / b 가 값에 따라 정수 나눗셈도, 실수 나눗셈도 되고, a + b 는 문자열 연결도 됩니다.

복합 대입의 평가 차례 — 고쳐진 버그

Roslyn 의 VS2019 깨지는 변경 목록 1번: "C# will now preserve left-to-right evaluation for compound assignment addition/subtraction expressions where the left-hand side is dynamic." 예전 컴파일러는 GetInt() 를 먼저 불렀습니다.

언어 버전을 4 로 내려도 차례는 문서의 "We now evaluate it as" 그대로 — 왼쪽 먼저입니다. 이 수정은 언어 버전에 묶이지 않은 컴파일러 고침이라, 옛 차례는 이 기계에서 재현할 수 없습니다.

실행 검증

dynamic 의 += — 이벤트냐 덧셈이냐

정적 코드에서 b.Click += h 와 b.Count += 1 은 컴파일러가 멤버의 종류를 보고 다르게 번역합니다. 하나는 이벤트의 add 접근자 호출, 하나는 읽고 더하고 쓰기입니다. 수신자가 dynamic 이면 그 판단을 실행 중에 해야 합니다.

Click += h 는 처리기를 붙였고 -= 는 뗐습니다(두 번째 Press() 는 조용합니다). 같은 꼴의 Count += 1 은 필드 덧셈이 됐습니다. 이벤트는 바깥에서 읽을 수 없는 멤버라, 실행 중의 바인더가 둘을 가려 처리한 것입니다.

함정 — dynamic 은 번진다

동적으로 바인딩된 연산의 결과는 대개 다시 dynamic 입니다. var 로 받으면 그 변수도 dynamic 이 되고, 그 다음 줄부터의 실수도 컴파일러가 보지 못합니다.

두 실패의 문장은 같습니다. 다른 것은 언제 알게 되느냐입니다. dynamic 의 결과는 쓸 형식을 적어 받으면 번짐이 거기서 멈춥니다.

함정 — dynamic 호출에 람다를 넘길 수 없다

표준: "An anonymous function cannot be a receiver, argument, or operand of a dynamically bound operation." 람다는 대상 형식이 있어야 형식이 정해지는데, 동적 호출에는 컴파일 시간의 대상 형식이 없습니다.

같은 까닭으로 LINQ 의 Where·Select 도 dynamic 수신자에게는 쓸 수 없습니다. 람다 문제 이전에 확장 메서드가 후보에 없기 때문입니다(4부).

함정 — void 를 값으로 받으면

컴파일러는 list.Clear() 가 무엇을 돌려주는지 모릅니다. 그래서 var r = list.Clear(); 를 받아 줍니다.

문장으로 부를 때는 통과하고, 값으로 받을 때는 void 를 object 로 바꿀 수 없어 멈춥니다. 정적 코드라면 컴파일 오류였을 실수입니다.

리플렉션 쪽은 메서드 이름을 문자열로, 인자 형식을 배열로, 인자를 object[] 로 손수 꾸립니다. 오버로드도 사람이 골랐습니다(typeof(int)). dynamic 쪽은 같은 일을 컴파일러와 바인더가 C# 의 오버로드 규칙으로 합니다 — ".0" 에는 Append(string) 이 골라졌습니다.

실행 검증

기본값이 될 수 있는 것

표준: 기본값 식은 "a constant_expression", "an expression of the form new S() where S is a value type", "an expression of the form default(S)" 셋 중 하나입니다. 그리고 "A parameter with a ref, out or this modifier cannot have a default_argument."

Math.PI 는 const 필드라 됩니다. DateTime.Now 는 속성이라, new int[0] 은 값 형식의 new S() 가 아니라 안 됩니다. 기본값이 상수여야 하는 까닭은 다음 슬라이드에 있습니다.

실행 검증

인수는 적힌 차례로 평가된다

표준: "The expressions of an argument list are always evaluated in textual order." 명명 인수로 차례를 바꿔 적으면, 평가는 적힌 차례, 짝짓기는 이름입니다. 표준의 예제 그대로에 한 줄을 더했습니다.

반공변 — 받기만 하는 T

반대 방향: "Xᵢ is contravariant and an implicit reference or identity conversion exists from Bᵢ to Aᵢ". 동물을 비교할 줄 아는 것은 고양이도 비교할 줄 압니다.

화살표가 거꾸로입니다. Cat → Animal 변환이 있으니 IComparer<Animal> → IComparer<Cat> 이 됩니다. 비교자 하나를 여러 하위 형식 목록에 다시 쓰는 것이 반공변의 흔한 쓰임입니다.

실행 검증

변성 안전성 — out T 를 받는 자리에 두면

표준: "Intuitively, an output-unsafe type is prohibited in an output position, and an input-unsafe type is prohibited in an input position." 공변 T 는 입력 쪽에 쓰면 안전하지 않습니다(input-unsafe).

이 선언이 허락된다면 IBox<string> 을 IBox<object> 로 본 뒤 Put(42) 로 문자열 상자에 정수를 넣을 수 있습니다. 배열 공변이 실행 중 확인으로 막는 그 구멍(배열 공변)을, 변성 선언은 컴파일 때 막습니다.

실행 검증

변성 안전성 — in T 를 내보내는 자리에 두면

거꾸로, 반공변 T 는 반환형이 될 수 없습니다(output-unsafe). 읽기·쓰기가 다 되는 속성은 양쪽 자리라서 불변이어야 합니다.

두 오류 문장의 차이를 보십시오. Take() 는 "must be covariantly valid", All 은 "must be invariantly valid" — List<T> 는 클래스라 변성이 없으므로 그 안의 T 는 어느 쪽으로도 움직일 수 없습니다.

실행 검증

입력의 입력은 출력

표준의 규칙은 재귀입니다. 반공변 형식 매개변수 자리에 놓인 형식은 방향이 뒤집힙니다. 그래서 공변 T 가 Action<T> 매개변수 안에는 올 수 있습니다.

Each 는 T 를 받는 메서드처럼 보이지만, 실제로는 콜백에 T 를 건네는 쪽입니다. 콜백을 받고(입력), 그 콜백이 T 를 받으니(입력의 입력) 결국 T 가 바깥으로 나갑니다.

실행 검증

변성은 인터페이스와 대리자에만

표준: "Variant type parameter lists can only occur on interface and delegate types." 클래스, 구조체, 제네릭 메서드에 붙여 봅니다.

클래스는 필드를 가질 수 있고 필드는 읽기·쓰기 양쪽 자리입니다. 그래서 List<T> 는 변성을 가질 수 없고, 변성은 IEnumerable<out T> 같은 인터페이스로 건넵니다.

실행 검증

함정 — 값 형식에는 변성이 없다

변성 변환의 조건은 "an implicit reference or identity conversion". int → object 는 참조 변환이 아니라 박싱입니다.

박싱은 원소마다 새 객체를 만드는 일이라, "같은 객체를 다른 형식으로 보기" 인 변성 변환이 될 수 없습니다. 3부의 메서드 그룹 변성도 같은 까닭으로 값 형식에서 멈췄습니다.

실행 검증

대리자 변수끼리의 변환

C# 2 는 메서드 그룹을 대리자로 바꿀 때만 변성을 허락했습니다(3부). C# 4 의 Func<in T, out TResult> 는 이미 만든 대리자 값을 다른 대리자 형식으로 봅니다.

한 번의 대입에 반공변(인자 object → string)과 공변(결과 string → object)이 함께 일어났습니다. 같은 객체이고(True), 실제 형식은 여전히 Func`2[Object,String] 입니다. 이 사실이 다음 슬라이드의 함정입니다.

실행 검증

함정 — 변성으로 담은 대리자를 합치면

대리자 + 는 Delegate.Combine 입니다. 변성 덕에 Action<string> 변수에 든 것이 실제로는 Action<object> 일 수 있습니다.

컴파일러 눈에는 둘 다 Action<string> 이라 아무 경고가 없습니다. 실행 중의 Combine 은 실제 형식이 다르다며 ArgumentException 을 냅니다. 변성 변환이 "같은 객체를 다르게 보기" 라서 생기는 틈입니다.

실행 검증

배열 공변(C# 1)과 안전한 변성(C# 4)

같은 string[] 을 세 가지 형식으로 봅니다 — object[], IEnumerable<object>, IList<object>.

  • IEnumerable<object> 는 넣는 메서드가 없어서 넣을 수가 없습니다 — out T 의 약속입니다.

  • IList<T> 는 불변인데도 string[] 이 IList<object> 로 담겼습니다. 배열이 그 인터페이스를 구현하는 길에 배열 공변이 따라 들어온 것으로 보입니다.
