var 는 왜 생겼나

표준은 var 선언을 이렇게 정의합니다. 초기화 식에 컴파일 시간 형식 T 가 있어야 하고, 변수의 형식은 그 T 입니다. 그리고 예제의 두 묶음 — var i = 5; 와 int i = 5; — 이 "precisely equivalent" 라고 적습니다.

그러면 왜 굳이 문법을 더했을까요. 같은 C# 3.0 의 익명 형식에는 적을 수 있는 이름이 없습니다. 표준: 익명 형식의 이름은 "automatically generated by the compiler and cannot be referenced in program text". 그런 값을 지역 변수에 담으려면 형식을 적지 않는 선언이 있어야 합니다.

긴 제네릭 형식 이름을 두 번 적지 않아도 되는 편리함은 덤입니다. 이 장의 차례는 그 둘을 따라갑니다 — 먼저 var, 다음에 익명 형식.

표준은 틀린 var 선언 다섯을 예로 듭니다 — 초기화 식이 없거나, 배열 초기화자만 있거나, null 이거나, 익명 함수이거나, 자기 자신을 가리키는 경우. 여기에 선언자 둘을 더했습니다.

Equals 는 값으로, == 는 참조로

표준: 익명 형식의 Equals 와 GetHashCode 는 속성들의 Equals·GetHashCode 로 정의되어, "two instances of the same anonymous type are equal if and only if all their properties are equal". 연산자 == 는 재정의하지 않았습니다.

함정 — a == b 는 False 입니다. 클래스의 == 는 참조 비교이고, 익명 형식은 연산자를 만들어 주지 않습니다. 대신 값으로 같으니 사전의 복합 열쇠로 쓸 수 있습니다 — seen[b] 가 seen[a] 를 덮었습니다. 해시값 자체는 찍지 않았습니다(문자열 해시는 프로세스마다 다릅니다).
실행 검증

같은 모양이면 같은 형식 — 이름·형식·차례

표준: 한 프로그램 안에서 속성의 이름과 컴파일 시간 형식이 "in the same order" 로 같은 두 익명 초기화자는 같은 익명 형식의 인스턴스를 만듭니다. 표준의 p1 = p2 예를 그대로 돌리고, 차례와 형식을 하나씩 바꿔 봅니다.

q 는 같은 두 속성을 순서만 바꿨는데도 다른 형식이고, 그래서 값이 같아도 Equals 가 False 입니다. r 은 Price 가 int 라 다른 형식입니다.

C# 3 시절의 "불변" 은 private set 이었습니다. 클래스 안에서는 여전히 바꿀 수 있으니 진짜 불변은 아니었습니다. { get; } 의 뒷받침 필드는 readonly 입니다(7부).

뒤 버전과의 맞물림 — 구조체 생성자와 자동 속성

구조체 생성자는 모든 필드를 확정 대입해야 합니다. 자동 속성의 숨은 필드도 마찬가지입니다. C# 11 의 새 기능 문서: "any field or auto property not initialized by a constructor is automatically initialized by the compiler."

거절 문장이 고칠 길로 "language version '11.0'" 을 권합니다. 그 전에는 생성자에서 : this() 를 불러 먼저 모두 0 으로 만들어야 했습니다. C# 11 은 12부에서 봅니다.

뒤 버전과의 맞물림 — 숨은 필드에 이름이 생기다: field

자동 속성은 "접근자에 아무 논리도 없을 때" 의 줄임이었습니다. 논리를 한 줄만 넣으려 해도 필드를 직접 선언하는 옛 꼴로 돌아가야 했습니다. C# 14: "The token field is replaced with a compiler synthesized backing field."

2026-10 기준의 최신 문법입니다. C# 3 이 숨긴 뒷받침 필드가 C# 14 에서 키워드 하나로 손에 닿게 됐습니다(15부).

실행 검증

partial 메서드는 왜 생겼나

표준: partial 메서드는 "allowing one part of a type declaration to customize the behavior of another part, e.g., one that is generated by a tool" 에 쓰입니다. 도구가 만든 조각이 갈고리 자리를 선언해 두고, 사람이 쓴 조각이 필요한 것만 구현합니다.

핵심은 구현하지 않은 갈고리의 값이 0 이라는 것입니다. 표준: 아무 조각도 구현하지 않으면 "the partial method declaration and all calls to it are removed". 빈 가상 메서드나 이벤트와 달리 호출 자체가 사라집니다.

갈고리 둘 가운데 하나만 구현한 기본 예는 3부에 있습니다. 여기서는 "호출이 사라진다" 가 정말 무엇을 뜻하는지 봅니다.

문서 근거

구현 없는 partial 메서드는 인자째 사라진다 C# 3.0

왜 — 표준: 구현이 없으면 그 호출 식은 "including any subexpressions, has no effect at run-time". 인자 식도 계산되지 않는다는 뜻입니다. 같은 파일을 IMPL 기호 없이, 그리고 있게 컴파일합니다.

함정 — 인자에 부수 효과를 넣으면, 그 효과가 다른 조각에 구현이 있는지에 따라 생기거나 사라집니다. 리플렉션도 같은 말을 합니다 — 구현이 없으면 OnLog 는 어셈블리에 없습니다. [Conditional] 메서드(2부)와 닮은 성질입니다.

C# 3 의 partial 메서드가 지킬 것

호출째 지워질 수 있어야 하니 제약이 따릅니다. 표준: 접근 한정자 없이 암시적으로 private, 반환형은 void, out 매개변수 없음. 구현이 없으면 대리자를 만들 수도 없습니다.

첫 캡처는 C# 3 의 금지를 C# 9 의 말로 합니다. int 반환과 out 매개변수는 "must have accessibility modifiers because …"(CS8796·CS8797)이고, public 은 "must have an implementation part because it has accessibility modifiers"(CS8795)와 함께 'extended partial methods' 게이트에 걸립니다. 지금의 컴파일러는 C# 3 의 제약을 "구현이 없어도 되는 partial 메서드" 의 조건으로 다시 썼습니다. C# 9 의 문서: "the compiler considers any partial method without an access modifier to follow the old rules" — 접근 한정자가 없으면 옛 규칙, 있으면 구현이 반드시 있어야 하는 새 규칙입니다(다음 장).

뒤 버전과의 맞물림 — 구현이 반드시 있는 partial 메서드

C# 9 는 partial 메서드의 C# 3 제약을 풀었습니다. 대신 접근 한정자를 붙이거나 값을 돌려주는 partial 메서드는 구현이 반드시 있어야 합니다. 소스 생성기가 "사람이 선언하고 생성기가 구현하는" 반대 방향을 쓸 수 있게 된 변화입니다.

기능 이름은 "extended partial methods" 입니다. C# 13 의 partial 속성, C# 14 의 partial 생성자·이벤트로 이어집니다(3부).

람다 — 익명 함수의 짧은 꼴

x => … · 형식 유추 · 잡힌 변수 · 오버로드 · 대리자 또는 데이터

람다는 왜 생겼나

C# 2 에는 이미 익명 메서드가 있었습니다(3부). 표준은 익명 함수에 "two syntactic flavors" 가 있는 것을 "historical reasons" 로 설명하고, 람다가 "more concise and expressive" 하며 익명 메서드는 "backwards compatibility" 로 남았다고 적습니다.

표준이 꼽은 차이익명 메서드람다
매개변수 목록 생략된다안 된다
매개변수 형식 생략(유추)안 된다된다
식 본문안 된다(블록만)된다
식 트리로 변환안 된다된다

버전 기록은 C# 3.0 이 "began to lay the groundwork for turning C# into a hybrid Object-Oriented / Functional language" 라고 적습니다. 람다가 그 바닥의 한 장입니다.

문서 근거

람다 식 C# 3.0

왜 — x => x * 2 는 "x 를 받아 x * 2 를 돌려주는 함수" 입니다. 이 예제는 C# 2 부터 있던 대리자 Converter·Predicate 에 담아 람다 하나만 C# 3 기능으로 남겼습니다.

거절 위치는 => 연산자가 있는 열입니다. 익명 메서드와 람다를 나란히 둔 예는 3부에 있습니다.

실행 검증

람다의 여러 꼴

표준의 예 목록을 그대로 대리자에 담았습니다 — 형식을 적거나 생략하고, 본문을 식이나 블록으로 쓰고, 매개변수가 둘이거나 없습니다.

  • 매개변수가 하나이고 형식을 생략했을 때만 괄호를 뺄 수 있습니다(x => …).
  • => 는 대입과 같은 우선순위이고 오른쪽 결합입니다(뒤에서 씁니다).
실행 검증

익명 메서드에만 남은 것 — 매개변수 목록 생략

표준: 시그니처가 없는 익명 메서드는 "any parameter list not containing output parameters" 인 대리자로 바뀔 수 있습니다. 람다는 매개변수를 늘 적어야 하고, 수가 대리자와 같아야 합니다.

두 번째 줄의 { x + 1; } 는 블록 본문이라 return 이 필요합니다. 식 본문 x => x + 1 과 헷갈리기 쉬운 자리입니다.

매개변수의 형식은 대상에서, 반환 형식은 본문에서

표준: 형식을 생략한 람다의 매개변수 형식은 "inferred from the context" — 람다가 바뀌어 들어가는 대리자 형식이 정합니다. 제네릭 메서드에 넘기면 형식 인자 유추가 람다의 본문까지 들여다봅니다.

Map(words, w => w.Length) 에서 TIn 은 words 에서 string 으로 정해지고, 그 다음에 람다 본문 w.Length 의 형식으로 TOut = int 가 정해집니다. 마지막 줄은 n * 0.5 라서 TOut = double 입니다. 질의 연산자들이 형식을 하나도 적지 않고 이어지는 바탕입니다.

뒤 버전과의 맞물림 — 람다의 '자연 형식'

C# 3 의 람다에는 형식이 없어 var f = x => … 가 거절됐습니다(2장). C# 10 은 "Lambda expressions may have a natural type" — 매개변수 형식을 적으면 컴파일러가 Func·Action 을 골라 줍니다.

고른 형식이 Func`2·Action 입니다. 그 대리자 형식들이 런타임 어디에 있는지는 1장에서 봤습니다. C# 10 은 11부에서 다룹니다.

표준: 익명 함수가 바깥 지역 변수를 쓰면 그 변수는 "captured" 되고, 수명이 대리자만큼 늘어납니다. 익명 메서드와 같은 규칙입니다(3부).

a 와 b 는 MakeCounter 호출마다 따로 생긴 count 를 잡았습니다. scale(3) 이 30 인 것은 람다가 부르는 순간의 factor 를 읽기 때문입니다.

함정 — for 의 변수 하나를 모든 람다가 함께 잡는다

람다가 생겨 대리자를 만드는 일이 흔해지자 이 함정도 흔해졌습니다. for 의 반복 변수는 루프 전체에 하나뿐입니다 (3부).

실행 검증

람다의 본문이 오버로드를 고른다 C# 3.0

왜 — 표준: 인자 자리의 익명 함수는 형식 유추와 오버로드 결정에 참여합니다. 표준의 예 ItemList<T>.Sum 을 그대로 돌립니다. d => d.UnitCount 는 두 Sum 에 다 맞지만 Func<Detail,int> 로의 변환이 "better" 라서 첫째가 골라집니다.

두 번째 람다는 본문이 double 이라 Func<T,int> 에 맞지 않습니다. 남은 후보가 하나입니다. 람다는 형식이 없는 대신, 넣어 볼 자리마다 본문을 다시 검사받습니다.

실행 검증

본문으로도 못 고르면 — 모호한 호출

x => 1 은 x 를 쓰지 않으니 Func<int,int> 에도 Func<string,int> 에도 맞습니다. 어느 쪽이 낫다고 할 근거도 없습니다.

둘째 줄은 x.Length 때문에 int 쪽이 실패해 string 쪽 하나만 남습니다. 셋째 줄은 매개변수 형식을 적어 고릅니다. 람다의 매개변수 형식을 적는 것은 이럴 때입니다.

실행 검증

함정 — 본문은 매개변수의 형식으로 먼저 계산된다

표준의 호환 규칙: 본문이 식이면, 매개변수에 대리자의 형식을 준 상태로 그 식이 "implicitly convertible to T" 여야 합니다. x / 2 는 int 나눗셈으로 끝난 다음에 double 로 바뀝니다.

블록 본문 람다의 return

블록 본문이면 메서드처럼 끝점에 닿을 수 없어야 하고, 모든 return 의 식이 대리자의 반환형으로 바뀔 수 있어야 합니다.

오류 문장이 "lambda expression of type 'Func<int, string>'" 라고 대상 형식을 밝힙니다. 람다를 판정할 때 컴파일러는 언제나 대상 대리자 형식을 손에 쥐고 있습니다.

실행 검증

같은 람다, 서로 바꿀 수 없는 대리자

람다 x => x > 0 은 Predicate<int> 에도 Func<int,bool> 에도 들어갑니다. 그러나 두 대리자 형식은 시그니처가 같아도 다른 형식입니다(2부 — 대리자는 클래스).

C# 2 의 Predicate·Converter 와 C# 3 시절의 Func 가 함께 남은 까닭에 지금도 만나는 어긋남입니다. 변수끼리는 안 되고, 람다나 메서드 그룹은 어느 쪽에나 넣을 수 있습니다.

실행 검증

아무것도 잡지 않은 람다는 다시 쓰인다

표준은 잡은 변수가 같고 의미가 같은 익명 함수의 변환이 "permitted (but not required) to return the same delegate instance" 라고 적습니다. 대리자의 대상 객체와 메서드가 무엇인지도 "unspecified" 입니다. 지금의 컴파일러가 실제로 무엇을 하는지 봅니다.

언어 버전에 따라 달라지지 않습니다. 같은 성질의 메서드 그룹 쪽 변화는 C# 11 에서 왔습니다(3부).

뒤 버전과의 맞물림 — 람다 매개변수가 바깥 이름을 가리기

C# 3 의 표준 규칙: 익명 함수의 매개변수 이름이 그 자리를 덮는 지역 변수·매개변수와 같으면 오류입니다. 아래 캡처의 C# 7.3 쪽이 그 오류(CS0136)입니다. 컴파일러는 이 제한을 C# 8 에서 풀었습니다.

2026-10 기준의 최신 변화입니다. C# 3 의 "형식을 생략하면 유추한다" 가 열여덟 해 뒤에 수식어 붙은 매개변수에까지 닿았습니다. C# 14 는 15부에서 봅니다.

확장 메서드는 왜 생겼나

버전 기록은 C# 3.0 의 변화를 list.Average() 로 설명하고 "The combination of query expressions and extension methods made a list of integers a whole lot smarter." 라고 적습니다. List<int> 에도, 배열에도, 반복기에도 Average 메서드는 없습니다.

문서 근거

확장 메서드 C# 3.0

왜 — 정적 클래스의 정적 메서드 첫 매개변수에 this 를 붙이면, 그 형식의 값 뒤에 점을 찍고 부를 수 있습니다.

거절은 선언의 this 에만 나옵니다. line.WordCount() 호출 줄에는 오류가 없습니다. 게이트는 선언 쪽에만 있어서, 이미 있는 확장 메서드를 부르는 쪽은 C# 2 로 내려도 막히지 않습니다(1장의 list.Average() 캡처). static 클래스가 C# 2 기능이라는 이음매는 3부에서 봤습니다.

실행 검증

그냥 정적 메서드 — IL 을 보지 않고 증명하기

표준은 확장 메서드를 쓴 프로그램이 "the same as the following, using ordinary static method calls" 라고 적습니다. 두 호출이 같은 값을 내는지, 그리고 리플렉션이 그 메서드를 무엇으로 보는지 확인합니다.

메서드는 매개변수 하나짜리 정적 메서드이고, 컴파일러가 메서드·클래스·어셈블리 세 곳에 ExtensionAttribute 를 붙였습니다. 다른 어셈블리의 컴파일러는 이 표지로 확장 메서드를 알아봅니다. 손으로 붙이는 것은 막혀 있고, 오류 문장이 "Use the 'this' keyword instead." 라고 말합니다.

실행 검증

둘 수 있는 곳 — 제네릭이 아닌, 중첩되지 않은 static 클래스

표준: "Extension methods shall only be declared in non-generic, non-nested static classes." 그리고 this 는 첫 매개변수에만 붙습니다.

이 제약이 찾기 규칙을 단순하게 만듭니다. 컴파일러는 이름공간에 바로 놓인 정적 클래스들만 훑으면 됩니다(뒤에서). 메서드 자체는 제네릭이어도 됩니다(뒤에서).

실행 검증

인스턴스 메서드가 언제나 먼저 C# 3.0

왜 — 표준: 보통의 호출 처리가 "finds no applicable methods" 일 때에만 확장 메서드를 찾습니다. 그래서 "instance methods take precedence over extension methods". 표준의 예 E.F·A·B·C 를 그대로 돌립니다.

함정 — c.F(1) 은 확장 메서드 F(object, int) 가 더 꼭 맞는데도 인스턴스 메서드 C.F(object) 로 갑니다. 인스턴스 쪽에 적용 가능한 것이 하나라도 있으면 확장 메서드는 후보에도 오르지 않습니다. 반대로, 확장 메서드와 같은 이름의 메서드를 나중에 그 클래스에 더하면 호출들이 소리 없이 그쪽으로 옮겨 갑니다.
실행 검증

using 으로 들여와야 보인다

표준: 확장 메서드는 가장 가까운 이름공간 선언부터 바깥으로, 층마다 그 자리에 선언된 형식과 그 자리의 using 지시문이 들여온 이름공간에서 찾습니다. Demo 안의 using Tools; 를 그대로 둔 판과, 기호 NOUSING 으로 뺀 판을 비교합니다. 전역 이름공간에는 아무 object 나 받는 Fallback.Shout 를 두었습니다.

using 이 있으면 Demo 층에서 Tools 의 Shout 가 후보로 잡혀 찾기가 멈춥니다. 빼면 그 층에 후보가 없어 바깥(전역)으로 나가고, string 에 더 꼭 맞는 메서드를 두고도 Fallback 이 불립니다. 정적 호출 Tools.StringExt.Shout(…) 은 using 과 상관없이 됩니다. LINQ 연산자를 쓸 때 using System.Linq; 를 적는 것도 이 규칙 때문입니다.

실행 검증

가까운 이름공간이 이긴다

표준: 가장 가까운 이름공간 선언부터 바깥으로 차례로 찾고, 처음 후보가 나온 자리에서 멈춥니다. 그래서 "extension methods available in inner namespace declarations take precedence over extension methods available in outer namespace declarations".

같은 1.Who() 가 부르는 자리의 이름공간에 따라 다른 메서드로 갑니다. 같은 층에 둘이 보이면 어느 쪽도 이기지 못합니다(다음 장).

실행 검증

같은 층에서 둘이 보이면 — 모호한 호출

using 으로 들여온 두 이름공간에 시그니처가 같은 확장 메서드가 있으면, 둘은 같은 층의 후보라 오버로드 결정이 고르지 못합니다.

가장 손쉬운 해결은 정적 호출(Left.L.Side(1))입니다. 이름 짧은 확장 메서드를 여러 라이브러리가 같은 형식에 붙이면 생기는 충돌입니다.

인터페이스에 메서드를 붙이기 — LINQ 가 서는 자리 C# 3.0

왜 — 앞의 표 셋째 줄이 막혔던 길입니다. C# 3 의 인터페이스는 구현을 가질 수 없었습니다. 확장 메서드의 첫 매개변수를 인터페이스로 두면, 그 인터페이스를 구현한 형식이 모두 메서드를 얻습니다. 표준: 수신자에서 첫 매개변수로 "An implicit identity, reference or boxing conversion" 이 있으면 후보입니다.

배열, List<int>, Queue<int>, 반복기 메서드의 결과는 서로 관계없는 형식인데 메서드 하나를 같이 씁니다. 어느 형식도 고치지 않았습니다. 1장의 list.Average() 도 Enumerable 의 확장 메서드였습니다. C# 14 문서의 예는 Enumerable 의 Where 를 IEnumerable<TSource> 에 붙인 꼴로 보여 줍니다.

실행 검증

제네릭 확장 메서드 — 표준의 Slice

표준의 예를 C# 3 의 모양으로 옮겼습니다(=> 본문만 return 문으로). 클래스는 제네릭이면 안 되지만 메서드는 제네릭이어도 됩니다. strings.Slice(1, 2) 의 T 는 수신자 string[] 에서 유추됩니다.

표준이 적은 기대 출력 "22", "333" 이 두 번 나옵니다. 두 번째 foreach 가 표준이 "The meaning of the program is the same as the following" 이라며 보인 정적 호출 꼴입니다.

정적 호출을 겹치면 마지막에 할 일을 맨 앞에 적어야 합니다. 같은 메서드를 확장 메서드로 부르면 적는 차례와 실행 차례가 같아집니다.

두 줄은 같은 정적 메서드 세 번의 호출입니다. 질의 연산자를 점으로 잇는 꼴(7장)이 읽히는 것은 이 덕분입니다.

표준의 주: "Unlike an instance method invocation, no exception is thrown when expr evaluates to a null reference. Instead, this null value is passed to the extension method". 받아 줄지 막을지는 메서드가 정합니다.

함정 — s.IsBlank() 는 인스턴스 메서드처럼 보이지만 s 가 null 이어도 돕니다. 이 줄을 보고 "여기서 s 는 null 이 아니다" 라고 짐작하면 틀립니다. null 을 받지 않을 메서드는 SafeLength 처럼 직접 검사해 ArgumentNullException 을 던집니다.

수신자 자리에는 숫자 변환이 없다

거절은 마지막 줄 하나입니다. 같은 메서드를 정적 호출로 부르면 int → long 이 되고, object 로의 boxing 은 수신자 자리에서도 됩니다. 오류 문장도 "requires a receiver of type 'long'" 이라며 수신자 자리를 따로 말합니다.

5장 퀴즈 — 확장 메서드

Q. Account a = null; 에서 확장 메서드 a.Describe() 를 부르면 호출 자리에서 예외가 납니까? 나중에 누군가 Account 에 같은 이름의 인스턴스 메서드 Describe() 를 더하면, 같은 줄은 어떻게 됩니까?

A. 처음에는 나지 않습니다. 확장 메서드는 정적 호출이라 null 이 인자로 넘어갑니다(null 수신자). 인스턴스 메서드가 생기면 같은 줄이 소리 없이 그쪽으로 옮겨 가고(인스턴스 메서드 우선), 이번에는 호출 자리에서 NullReferenceException 입니다. 소스는 한 글자도 안 바뀌었는데 동작이 바뀝니다.
