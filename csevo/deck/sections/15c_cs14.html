partial 이벤트와 생성자 — 나눌 수 있는 멤버가 둘 늘었다

왜 · 정의와 구현 · 생성기의 대역 · 생성자 초기화자 · 필드 꼴이 아닌 이벤트 · 조각의 개수 · 서명 · 특성 · 인터페이스 · 컴파일러가 죽는 꼴 · 깨지는 변경 · 퀴즈

왜 — 메서드·속성·인덱서에 이어 이벤트와 생성자

제안서의 동기는 한 줄입니다: "C# already supports partial methods, properties, and indexers. Partial events and constructors are missing." 쓰임으로 둘을 듭니다 — 약한 이벤트(weak event) 라이브러리의 소스 생성기가 이벤트 접근자를 채우는 것, 그리고 Xamarin 같은 상호 운용 코드 생성기가 생성자의 몸체를 Objective-C 호출로 채우는 것입니다.

partial 멤버버전이 덱
partial 메서드(구현 생략 가능, void 만)C# 34부
확장된 partial 메서드(반환 값·out·접근성, 구현 필수)C# 910부
partial 속성과 인덱서C# 1314부
partial 이벤트와 인스턴스 생성자C# 14이 장

제안서의 열린 질문은 연산자와 필드, 그리고 partial "primary" 생성자도 후보로 적어 두었습니다(2026-10 기준 C# 14 에는 들어오지 않았습니다).

문서 근거

partial 이벤트와 생성자 (partial events and constructors) C# 14.0

왜 — whats-new: "You can now declare instance constructors and events as partial members." 둘 다 "exactly one defining declaration and one implementing declaration" 이고, 이벤트의 구현 조각은 add·remove 를 갖춰야 합니다.

C# 13.0 의 거절이 길어진 까닭이 바로 다음 장의 깨지는 변경입니다 — public partial Sensor(string name); 을 C# 13 의 파서는 "반환 형식이 partial 인 메서드 Sensor" 로 읽어 CS0246·CS0501·CS0542 를 냅니다. 게이트 문장 CS9260 은 그 뒤에 나오고, 이벤트 쪽은 14부의 partial 속성처럼 CS8703 입니다(14부).

실행 검증

생성기가 구현하는 이벤트 — 손으로 쓴 대역으로 보기

제안서의 첫 예: 사람이 [WeakEvent] 를 단 정의 조각만 쓰고, 라이브러리의 소스 생성기가 add·remove 와 RaiseMyEvent 를 씁니다. 이 덱의 csrun 은 생성기를 싣지 않으므로 Gen.cs 는 손으로 쓴 대역입니다(14부와 같은 방식).

처음 Click 에서는 둘 다 받습니다. GC.Collect() 뒤에는 붙들린 kept 만 남아 alive 1/2 입니다 — 버려진 창은 이벤트 구독 때문에 살아 있지 않습니다. 사람이 쓴 조각에는 접근자도 필드도 없고, 부르는 쪽(b.Clicked += …)은 보통 이벤트와 같습니다. 대역의 remove 는 비워 두었습니다.

실행 검증

생성자 초기화자는 구현 조각에만

whats-new: "Only the implementing declaration of a partial constructor can include a constructor initializer: this() or base(). Only one partial type declaration can include the primary constructor syntax."

정의 조각의 초기화자는 partial 생성자 전용 번호 CS9280 "only the implementing declaration … can have an initializer" 입니다. 기본 생성자(13부)가 있는 형식의 partial 생성자도 보통 생성자와 같이 : this(…) 를 불러야 하고(CS8862), 그 초기화자 역시 구현 조각에 씁니다.

실행 검증

partial 이벤트는 필드 꼴 이벤트가 아니다

제안서: partial 이벤트는 "not field-like" — "It does not have any backing storage or accessors generated by the compiler", "It can only be used in += and -= operations, not as a value." 정의 조각 한 줄이 이벤트 여럿을 정의할 수도 있습니다.

필드는 손으로 쓴 opened 하나뿐입니다. 필드 꼴 이벤트라면 선언한 클래스 안에서 Opened?.Invoke() 가 되지만, partial 이벤트는 클래스 안에서도 CS0079 입니다. whats-new 는 "The defining declaration declares a field-like event" 라고 적는데 , 이는 정의 조각의 모양을 말한 것으로 읽어야 합니다. 그 모양을 두 번 쓰면 둘 다 정의 조각이라 CS9277·CS9275 입니다.

실행 검증

정의 하나, 구현 하나 — 그리고 안 되는 것

제안서: partial 이벤트·생성자는 "May only be declared as a member of a partial type", "Must have one defining and one implementing declaration", "Is not permitted to have the abstract modifier", "Cannot explicitly implement an interface member".

조각이 모자라면 CS9275(구현이 없다)와 CS9276(정의가 없다) — 14부 partial 속성의 CS9248·CS9249 와 문장은 같고 번호는 다릅니다(14부). NOTPARTIAL 은 CS0751, 정적 생성자(STATIC)의 CS0267 은 200칸이 넘어 장 끝의 표에 문장 전체를 옮겼습니다 — 문장이 "an instance constructor name" 을 명시합니다.

실행 검증

서명 맞추기 — 오류, 경고, 무시되는 기본값

제안서: 한정자가 다르면 오류, 다른 문법 차이는 경고. 기본값은 맞출 필요가 없지만 구현 생성자에 기본값이 있으면 경고입니다 — "only the defining declaration participates in lookup". 매개변수 이름이 달라도 경고입니다.

세 경우 모두 출력은 port 80 — 정의 조각의 기본값입니다. 구현 조각의 8080 은 무시된다는 경고가 새 번호가 아니라 오래된 CS1066 입니다. 이름 차이는 전용 문장 없이 일반 경고 CS9256 "have signature differences" 로 나옵니다. 명명 인수 host: 는 정의 조각의 이름을 씁니다.

실행 검증

메타데이터 — 멤버는 하나, 특성은 두 조각의 합

제안서: 결과 멤버의 특성은 "the combined attributes of the partial declarations", 순서는 정하지 않았고 "duplicates are not removed". 접근자의 특성은 구현 조각의 접근자에서만 옵니다.

생성자 하나, 이벤트 하나에 특성이 def impl 차례로 둘씩 붙습니다(이 컴파일러의 차례 — 제안서는 차례를 약속하지 않습니다). 컴파일러가 만든 필드는 0개입니다 — partial 이벤트는 뒷받침 필드를 만들지 않습니다(앞 장).

실행 검증

인터페이스의 partial 이벤트 — 암묵적으로 virtual·public C# 14.0

왜 — Roslyn 문서(.NET 10): partial 인터페이스 속성과 이벤트가 비 partial 멤버와 달리 암묵적으로 virtual·public 이 아니던 "inconsistency" 를 고쳤습니다. 14부는 속성 쪽을 보았습니다(14부). 이벤트 쪽은 partial 이벤트 자체가 C# 14 라 이제야 보입니다.

Bus 를 IBus 로 구독하면 Bus.add, 아무것도 구현하지 않은 Quiet 는 인터페이스의 기본 구현 IBus.add 입니다. 접근성을 쓰지 않았는데 add 가 public·virtual 입니다. 클래스가 아니라 인터페이스에 둔 것은 다음 장의 함정 때문입니다.

실행 검증

함정 — 인터페이스 이벤트를 구현하는 partial 이벤트에서 컴파일러가 죽는다

클래스의 partial 이벤트가 같은 이름의 인터페이스 이벤트를 구현하면, 이 덱의 컴파일러(SDK 10.0.112)는 진단 하나 없이 스택 넘침으로 끝납니다. 출력이 16MB 를 넘어 캡처로 싣지 못하고, 실험 묶음이 종료 코드와 되풀이되는 프레임을 확인해 표로 옮겼습니다.

고리는 이렇습니다: partial 조각을 합치며 서명을 비교 → value 매개변수의 형식을 구함 → 그 이벤트가 WinRT 이벤트인지 보려고 인터페이스 구현을 찾음 → 멤버 목록을 다시 만들며 partial 조각을 합침. C# 13.0 으로 내려도 게이트 오류를 내기 전에 죽습니다. 이벤트 이름을 바꾸고 명시적 구현으로 넘기는 FIX 는 컴파일됩니다. 이 덱의 SDK 에서 본 것이며 고쳐졌는지는 미확인입니다(2026-10 기준).

실행 검증

깨지는 변경 — partial 을 돌려주는 메서드 C# 14.0

왜 — Roslyn 문서: partial 이벤트와 생성자가 "allows the partial modifier in more places and so it cannot be a return type unless escaped". 제안서는 파서를 단순하게 하려고 "the partial modifier is accepted at any method-like declaration" 이라고 적습니다.

C# 13.0 은 메서드, C# 14.0 은 반환 형식이 없는 partial 생성자 Factory() 로 읽습니다 — 그래서 CS1520 에 이어 "partial 형식이 아니다", "정의 조각이 없다" 가 붙습니다. 깨짐은 언어 버전에 묶여 있어 이 경우는 C# 13.0 으로 두면 그대로 됩니다. 문서의 처방 @partial 은 두 버전 모두에서 됩니다.

6장의 진단 한눈에

partial 이벤트·생성자에만 나오는 번호는 CS9275–CS9277(조각의 개수)과 CS9280(초기화자) 넷입니다. 나머지는 partial 메서드·속성 때부터의 번호(CS0751· CS8799·CS9256)와 이벤트·생성자의 오래된 번호(CS0065·CS0079·CS1066·CS8862)입니다. 둘째 표의 CS0267 문장이 C# 14 에서 partial 이 놓일 수 있는 자리의 목록입니다.

6장 퀴즈 — partial 이벤트와 생성자

Q1. public partial event Action Done; 만 있는 클래스 안에서 Done?.Invoke() 를 쓸 수 있을까요?

Q2. 정의 조각이 C(int x = 1), 구현 조각이 C(int x = 2) 이면 new C() 의 x 는?

A1. 아니요. partial 이벤트는 필드 꼴이 아니라 클래스 안에서도 +=·-= 에만 나올 수 있습니다(CS0079, 앞에서). 게다가 구현 조각이 없으면 CS9275 입니다.
A2. 1 입니다. 찾아보기(lookup)에는 정의 조각만 쓰이고, 구현 조각의 기본값은 CS1066 경고와 함께 무시됩니다(앞에서).

사용자 정의 복합 대입 — x += y 를 제자리에서

왜 · 인스턴스 operator += · 할당 바이트 · 변수일 때만 · 없으면 x = x + y · null 과 ?.= · 인스턴스 ++ · checked · 메타데이터 · virtual 과 인터페이스 · .NET 10 · 규칙 · dynamic · 퀴즈

왜 — 지금까지 x += y 는 언제나 x = x + y 였다

제안서의 동기: c1 += 1 은 사용자 정의 + 를 부르고 그 반환 값을 다시 대입합니다. 그래서 연산자는 "must allocate and return a new instance", 원래 값은 대개 "lost" 입니다. "With types which have large data (such as BigInteger, Tensors, etc.) the cost of producing a net new destination, iterating, and copying the memory tends to be fairly expensive."

2부가 C# 1 에서 본 그 풀이입니다(2부). v += 1 다섯 번에 Vec 이 다섯 개 더 생겨 모두 여섯입니다. 처음 객체는 버려지고 v 는 마지막 사본을 가리킵니다. 연산자를 바꾸지 않으면 C# 14.0 으로 올려도 그대로입니다 — 바뀌는 것은 형식이 새 연산자를 선언했을 때뿐입니다.

실행 검증

사용자 정의 복합 대입 연산자 (user-defined compound assignment) C# 14.0

왜 — 제안서: 복합 대입 연산자는 "a void returning instance method that takes one parameter and has a special name in metadata", 목적은 "to adjust the value of the instance to result of <instance> <binary operator token> parameter". whats-new 의 절은 제안서로 넘깁니다.

static 이 없고, 반환은 void, 매개변수는 오른쪽 피연산자 하나입니다 — 왼쪽 피연산자는 this 입니다. 다섯 번을 더해도 객체는 하나, v 는 처음 객체 그대로입니다. 이항 v + 1 은 여전히 정적 + 라 새 객체를 만듭니다. C# 13.0 은 선언에서 CS9260 입니다.

실행 검증

얼마나 덜 할당하나 — 바이트로 센다

제안서는 수치를 내지 않습니다. 시간 대신 이 스레드가 할당한 바이트(GC.GetAllocatedBytesForCurrentThread)를 셉니다 — 실행마다 같은 수입니다.

b = b + 1 열 번은 400,480 바이트 — 한 번에 Buf 객체와 int[10000] 배열 하나씩입니다. b += 1 은 0 바이트입니다. b[0] = 11 은 첫 줄의 람다가 새 객체만 만들고 바깥의 b 를 건드리지 않았다는 뜻입니다 — 열한 번의 +=(데우기 한 번 포함)만 남았습니다.

실행 검증

함정 — 왼쪽이 "변수" 일 때만 인스턴스 연산자

제안서: "if x in x «op»= y is classified as a variable and a new language version is targeted, then the priority is given to compound assignment operators". 속성은 변수가 아니므로 옛 규칙 — get, 정적 +, set — 으로 갑니다(제안서 예의 S.P2 += 100).

지역 변수·필드·배열 원소는 인스턴스 +=, 자동 속성 h.Prop 만 [static +] 입니다. 정적 + 를 지우면 속성 줄 하나가 CS0019 로 거절됩니다 — 인스턴스 연산자만 준 형식은 속성에서 += 를 쓸 수 없습니다. 결과를 쓰는 var r = a += 10 은 변수라 인스턴스 연산자이고, 값 형식이므로 바뀐 a 의 사본이 r 입니다.

실행 검증

왼쪽은 한 번만 평가 — 그리고 읽기 전용 변수는 여전히 안 된다

제안서: "side effects in x are evaluated only once in the process." 구조체의 readonly 연산자는 허용하되 "we will not relax the target requirements at this time" — 읽기 전용 변수는 readonly 연산자로도 대입의 왼쪽이 될 수 없습니다.

Index() 는 연산마다 한 번입니다. readonly -= 는 몸체가 아무것도 바꾸지 않으니 원소는 5 그대로입니다. 그런데도 in 매개변수에 쓰면 CS8331("readonly variable") — 컴파일러는 연산자가 readonly 인지 보지 않고 왼쪽이 쓸 수 있는 변수인지만 봅니다. static readonly 필드는 CS0198 입니다.

실행 검증

없으면 옛길, 둘이 달라도 컴파일러는 모른다

제안서: 복합 대입 연산자 해석이 "no result and no error" 이면 옛 이항 연산자 규칙으로 갑니다. 그리고 += 와 + 가 어긋날 수 있다는 걱정에 대한 결론: "Checks will not be done on consistency between different forms of operators."

OnlyPlus 는 C# 13 처럼 새 객체입니다 — 이미 있는 라이브러리 형식은 C# 14 로 올려도 동작이 같습니다. Odd 는 일부러 어긋나게 쓴 것으로, o += 3 은 7, o = o + 3 은 10 입니다. 경고도 없습니다. 두 꼴이 같은 뜻이라는 것은 이제 형식을 쓴 사람의 약속입니다.

실행 검증

null 인 받는 쪽, 그리고 ?.= 와 함께

제안서: 참조 형식이면 "If x₀ is null, the operator method invocation will throw a NullReferenceException." 정적 연산자는 null 을 인수로 받을 수 있었지만 인스턴스 연산자는 받는 쪽이 null 이면 부를 수 없습니다.

정적 판은 null 을 받아 스스로 처리합니다. 인스턴스 판은 NullReferenceException 입니다 — 정적에서 인스턴스로 옮기면 null 처리가 부르는 쪽으로 넘어옵니다. 같은 C# 14 의 ?.=(5장)는 인스턴스 += 와 그대로 엮입니다 — none?.Item += 3 은 건너뜁니다. 확장 블록으로 남의 형식에 붙이는 += 는 2장에 있습니다.

실행 검증

인스턴스 ++ 와 --, 그리고 결과를 쓰는 x++

제안서: 인스턴스 증가 연산자는 "a void returning instance method that has no parameters". 후위 x++ 의 결과를 쓰면 인스턴스 판을 시도조차 하지 않습니다 — "if we are dealing with a reference type, it is not possible to produce value of x before the operation if it is mutated in-place."

문장으로 쓴 c++;·++c; 와 결과를 쓰는 a = ++c 는 인스턴스 판입니다(전위의 결과는 바뀐 뒤의 값이라 같은 객체를 돌려주면 됩니다). b = c++ 만 정적 판 — b 는 옛 객체(3), c 는 새 객체(4)가 되어 c0 와 갈라집니다. 둘을 함께 줄 때 둘이 같은 일을 해야 하는 까닭입니다.

실행 검증

checked 복합 대입 — C# 11 의 짝 규칙 그대로

제안서: "A checked operator declaration requires a pair-wise declaration of a regular operator." checked 문맥에서는 짝이 있는 보통 판을 빼고 checked 판을 고릅니다. 규칙은 C# 11 의 checked 연산자에서 왔습니다(12부).

보통 문맥에서 250 + 10 은 4 로 감기고, checked { } 안에서는 넘침입니다. -checked+ 는 파일 전체를 checked 문맥으로 만드므로 첫 줄의 m += 10 부터 op_CheckedAdditionAssignment 가 불려 처리하지 않은 예외로 끝납니다. 짝 없는 checked -= 는 C# 11 과 같은 번호 CS9025 입니다.

실행 검증

메타데이터의 이름 — op_AdditionAssignment

제안서: ECMA-335 는 op_AdditionAssignment 같은 이름을 이미 "reserved" 해 두었지만 CLS 는 그것을 두 매개변수의 정적 메서드로 보았고, 증가 연산자와 checked 판의 이름(op_IncrementAssignment, op_CheckedAdditionAssignment …)은 새로 더해야 한다고 적습니다.

인스턴스·Void·매개변수 하나(증가는 0개)·specialname — 제안서의 표 그대로입니다. 1부 이후 연산자는 언제나 static 이었으니 (2부), 메타데이터에 인스턴스 연산자가 나타난 것은 이번이 처음입니다. C# 11 의 >>>= 도 op_UnsignedRightShiftAssignment 로 붙습니다.

실행 검증

virtual·override, 그리고 인터페이스

제안서: 복합 대입 연산자는 "can override an operator with the same signature declared in a base class", 가리기(shadowing)도 "the same rules as methods". 정적 메서드 대안을 버린 까닭: 인터페이스에서는 구현이 클래스일지 구조체일지 몰라 첫 매개변수를 ref 로 할지 정할 수 없다.

Sum 형식 변수의 s += 1 이 LoudSum 의 override 로 갑니다 — 연산자에 가상 호출이 생겼습니다. AddAll 은 같은 몸체로 구조체 SSum 과 클래스 Sum 을 모두 제자리에서 6 으로 만듭니다. 제안서가 정적 메서드 대신 인스턴스 메서드를 고른 까닭이 이 한 메서드입니다.

실행 검증

.NET 10 은 어디에 쓰나 — 아직 아무 데도

제안서가 꼽은 대상은 BigInteger·텐서 같은 큰 형식입니다. 이 기계의 참조 팩 (Microsoft.NETCore.App.Ref 10.0.12)에서 이름이 op_…Assignment 인 메서드를 메타데이터로 직접 셉니다(14부의 우선순위 특성과 같은 방법).

형식 4,148개, op_Addition 43개, 복합 대입 연산자 0개입니다. 같은 코드가 이 프로그램의 Probe 는 찾으므로 셈은 맞습니다. 제네릭 수학 인터페이스(12부)도 += 를 선언하지 않습니다 — T : INumber<T> 의 x += y 는 지금도 정적 + 입니다. 라이브러리가 따라오는 것은 언어보다 늦습니다(2026-10 기준).

실행 검증

선언의 규칙 — static 아님, void, 매개변수 하나, public

제안서의 세 규칙: "shall not include a static modifier", "shall take one parameter", "shall have void return type". readonly 는 허용하기로 했지만 "we will not relax the target requirements" — 대입의 왼쪽은 여전히 변수여야 합니다.

인스턴스 연산자의 선언에만 나오는 번호는 CS9310(반환은 void)과 CS9308(public) 둘입니다. static 은 오래된 CS0106, 매개변수 둘은 파서의 CS1020, new P() += 1 은 CS0131 입니다(장 끝의 표). readonly -= 는 컴파일되지만 아무것도 바꿀 수 없으니 p -= 5 뒤에도 2 입니다.

제안서: 복합 대입에서 "The paragraph at the beginning that deals with dynamic is still applicable as is." — dynamic 이 끼면 컴파일 때가 아니라 실행 때의 바인더(Microsoft.CSharp)가 고릅니다.

왜 — whats-new: "Beginning with C# 14, the argument to nameof can be an unbound generic type. For example, nameof(List<>) evaluates to List." 제안서는 멤버 사슬도 열어 둡니다 — nameof(A<>.B.Count) 는 "Count", 형식 매개변수의 멤버는 제약이 주는 것까지 보입니다.

실행 검증

이전엔 — 결과에 쓰이지도 않을 형식 인수를 골라야 했다

제안서: 형식 인수는 "has no effect on the evaluation", 그런데도 제약을 맞추려고 "declaring a dummy class" 를 해야 할 때가 있고, 제약이 바뀌면 nameof 가 "unnecessarily" 깨집니다.

형식 없는 람다 매개변수에 한정자 (simple lambda parameters with modifiers) C# 14.0

왜 — whats-new: "You can add parameter modifiers, such as scoped, ref, in, out, or ref readonly to lambda expression parameters without specifying the parameter type." 전에는 "adding any modifiers was allowed only when the parameter declarations included the types". 예제는 whats-new 의 TryParse 그대로입니다.

같은 (text, out result) 가 대리자에 따라 int 도 되고 double 도 됩니다 — 형식을 쓰지 않으니 대리자만 바꿔 다시 씁니다. C# 13.0 은 형식 없는 두 람다만 거절합니다. 제안서의 말: 문법은 바뀌지 않았고 "This grammar already considers modifiers* identifier to be syntactically legal". 람다가 받아 온 다른 변화는 11부(11부)와 13부의 기본값(13부)에 있습니다.

실행 검증

ref·in·scoped — 그리고 C# 13 에서 scoped 는 형식 이름이었다

제안서: (scoped x) => 를 허용하지 않으면 "a user can write the full explicitly typed lambda, but not the implicitly typed version" 인 경우가 생깁니다 — 대리자의 매개변수가 scoped 이고 스팬을 돌려주면 람다에도 scoped 가 "required" 입니다.

scoped 를 빼면 CS8986 입니다 — 제안서의 "'scoped' is required" 그대로입니다. C# 13.0 의 거절은 셋이 CS9260, 넷째 (scoped s) 는 CS0246 "The type … 'scoped' could not be found" 입니다. C# 13 에게 (scoped s) 는 "형식 scoped 의 매개변수 s" 였습니다 — 다다음 장의 깨지는 변경이 바로 이 모호함입니다.

실행 검증

여전히 안 되는 꼴 — params, 섞기, 괄호 없이, 기본값

whats-new: "The params modifier still requires an explicitly typed parameter list." 제안서: 형식 있는 매개변수와 없는 매개변수를 섞을 수 없고, ref x => … 처럼 괄호 없는 람다에는 적용되지 않으며, 형식 없는 매개변수는 기본값을 가질 수 없습니다.

params 는 형식 없는 매개변수 전용 번호 CS9272 — 제안서의 열린 질문 2 가 "This will always be an error" 로 닫힌 결과입니다. 괄호 없는 ref x => { } 는 한정자 붙은 람다로 읽히지도 않고 ref 식으로 읽혀 엉뚱한 CS8171 이 납니다. 섞기는 오래된 CS0748, 기본값은 C# 12 의 CS9098 입니다 (장 끝의 표).

실행 검증

scoped 는 오버로드를 가르지 않는다 — ref·out 은 가른다

제안서: "The only modifiers that restrict compatible delegate types are ref, out, in and ref readonly." 형식을 적은 람다에서도 scoped 만 다른 두 대리자는 모호했고, 형식 없는 람다에서도 "This will remain ambiguous."

형식을 적지 않았는데도 out 과 ref 가 N 의 두 판을 정확히 가릅니다 — 한정자가 형식 대신 오버로드의 열쇠가 됩니다. scoped 는 그렇지 않아 CS0121 입니다.

실행 검증

깨지는 변경 — 람다 매개변수의 scoped 는 언제나 한정자 C# 14.0

왜 — Roslyn 문서: "scoped will always be treated as a modifier in a lambda parameter, even where it might have been accepted as a type name in the past", 예는 var v = (scoped scoped s) => { ... }; 이고 "In C# 14 this will be an error". 제안서의 열린 질문 1 은 다른 예를 듭니다 — (scoped s = default).

문서의 예 (scoped scoped s) 는 이 컴파일러에서 C# 14.0 도 오류가 아닙니다 — 앞의 scoped 를 한정자, 뒤의 것을 형식으로 읽어 3 을 찍습니다. 실제로 깨지는 것은 기본값이 붙은 (scoped s = default) 입니다. C# 13.0 은 형식 scoped 의 매개변수(경고 CS9099 하나), C# 14.0 은 형식 없는 매개변수라 CS9098 입니다. 처방 @scoped(FIX)는 경고만 남기고 3 을 찍습니다.

실행 검증

식 트리 안의 선택 인수와 명명 인수 C# 14.0

왜 — 제안서: 선택 인수를 빠뜨리거나 인수에 이름을 붙인 호출은 식 트리에서 오류였고, 새 선택 매개변수를 가진 오버로드가 생기면 기존 호출이 깨질 수 있었습니다. 처방은 "Remove the error reporting for these cases", 그리고 "It's unclear why the restrictions were added originally." whats-new 와 언어 버전 기록에는 이 기능이 없습니다 (1장).

트리에는 기본값이 상수로 들어가 인수가 늘 셋입니다 — Fmt(n, "kg", 6). 트리만 보아서는 기본값이었는지 적은 값이었는지 알 수 없습니다. C# 13.0 은 두 줄 모두 선택 인수의 CS0854 입니다(이름을 붙인 둘째 줄도 먼저 선택 인수로 걸립니다). -define:SKIP 의 Fmt(n, width: 4) 는 다음 장의 오류입니다. 식 트리의 다른 제약은 4부(4부)에 있습니다.

실행 검증

함정 — 자리를 바꾼 명명 인수는 C# 14 에서도 안 된다

제안서는 명명 인수의 오류를 없앤다고 적지만, 컴파일러는 자리를 벗어난 명명 인수에 C# 14 전용 오류 CS9307 을 냅니다. 보통 호출에서는 적은 차례로 평가하는데, 트리의 Call 노드는 인수를 매개변수 차례로만 담기 때문으로 보입니다(문서에는 이유가 없습니다).

대리자는 적은 차례 b a 로 평가하고, 자리를 지킨 명명 인수는 트리에 들어가 a b 입니다. 자리를 바꾸면 CS9307 "named argument specification out of position" 입니다. 앞 장의 Fmt(n, width: 4) 도 unit 을 건너뛰어 같은 오류입니다. C# 13.0 은 이름이 붙기만 하면 CS0853 이었습니다.

실행 검증

제안서의 예 — 스팬 판 Contains 의 선택 매개변수

제안서의 동기 예: MemoryExtensions.Contains<T>(ReadOnlySpan<T>, T, IEqualityComparer<T>? comparer = null) 가 C# 14 에서 배열에 적용되자 (a, i) => a.Contains(i) 가 "error CS0854" 를 냈다 — .NET 10 미리 보기 SDK 에서.

C# 14.0 의 두 트리는 같습니다 — 스팬 변환 op_Implicit(a) 와 상수 null. 선택 인수가 막혀 있었다면 C# 14 의 스팬 변환 (4장)이 이 람다를 깨뜨렸을 것입니다. 두 기능이 한 버전에 들어온 까닭입니다. 이 트리는 컴파일 모드로는 돌지만 해석 모드로는 못 돕니다 (4장). C# 13.0 의 첫 줄은 Enumerable.Contains 라 통과하고, 이름을 붙인 둘째 줄만 CS0853 입니다.

실행 검증

트리에 들어가는 기본값 — default 구조체, decimal, null

제안서는 기존 "method call rewriting" 이 선택 인수를 처리하게 둔다고만 적습니다. CancellationToken ct = default 같은 구조체 기본값, decimal 상수, null 이 트리에서 어떤 노드가 되는지 봅니다.

셋 다 Constant 노드이고 형식은 매개변수의 형식 그대로입니다. default 구조체는 value(System.Threading.CancellationToken) 으로 찍힙니다 — Expression.Default 가 아니라 상자에 담은 값입니다. 트리를 읽는 쪽은 "인수가 없었다" 와 "기본값을 적었다" 를 가를 수 없습니다.

실행 검증

무시되는 지시문 #: 와 #! (ignored directives) C# 14.0

왜 — 제안서: dotnet run file.cs 의 파일 기반 앱(file-based app)은 NuGet 패키지 같은 설정을 파일 안에 적어야 합니다. 언어는 #: 와 #! 로 시작하는 줄을 무시하고 도구가 읽습니다 — "These are parsed regardless of language version." whats-new 는 이를 "new preprocessor directives for File-based apps" 로 적습니다.

이 덱의 csrun 은 csc 를 직접 부르므로 dotnet run app.cs 의 도구 쪽(패키지 받기, 속성 적용)은 보일 수 없습니다. csc 는 평소 CS9298 "can be only used in file-based programs" 로 막고, SDK 가 넘기는 기능 플래그가 있으면 줄을 무시하고 컴파일합니다. C# 1 에서도 같습니다 — 게이트가 없습니다. #:property LangVersion=14 는 csc 에게 아무 뜻이 없습니다.

실행 검증

#: 가 놓일 수 있는 자리 — 첫 토큰 앞, #if 앞

제안서: 무시되는 지시문은 "must occur before the first token", 그리고 "before any #if directives" — 도구가 조건부 기호를 모른 채 읽어야 하기 때문입니다. 꺼진 영역과 문자열 안의 #: 는 오류가 아닙니다.

꺼진 #if IFFIRST 안의 #: 는 조용하고, 원시 문자열 안의 것은 그냥 글자입니다. 켜면 CS9299(#if 뒤), 파일 끝의 것은 CS9297(첫 토큰 뒤)와 CS9299 둘입니다.

#! 은 파일의 맨 첫 글자여야 — 이 덱에서는 보일 수 없는 까닭

제안서: 셸이 알아보도록 #! 은 "at the first line and the first character in the file" 이어야 하고, 아니면 컴파일러가 "should report a warning" 이라고 적습니다. 이 덱의 모든 소스는 첫 줄이 // 슬라이드 … 주석이라(0부) #! 는 둘째 줄에만 놓을 수 있습니다.

플래그가 없으면 #! 에 CS9314 "only be used in scripts or file-based programs" 가 붙습니다. 플래그가 있으면 둘째 줄의 #! 는 제안서의 "warning" 이 아니라 오래된 오류 CS1040 "Preprocessor directives must appear as the first non-whitespace character on a line" 입니다. 첫 줄의 #! 가 받아들여지는 모습은 이 덱의 규칙상 싣지 못했습니다.

Q. 프로젝트를 .NET 10 SDK 로 올리고 LangVersion 을 13.0 으로 묶었습니다. 이 부에서 본 변화 가운데 그래도 이 프로젝트에 닿는 것을 둘 고르면?

15부 퀴즈 (2) — 제자리 갱신

Q1. 인스턴스 operator += 만 가진 클래스의 변수 v 가 null 일 때 v += 1 은?

Q2. 같은 클래스 값을 dynamic d 에 담아 d += 1 을 하면?

A1. NullReferenceException 입니다 — 정적 + 는 null 을 인수로 받았지만 인스턴스 연산자는 받는 쪽이 있어야 합니다. v?.X += 1 같은 ?.= 로 피할 수 있습니다(7장).
A2. .NET 10 의 실행 때 바인더는 인스턴스 연산자를 모르므로 정적 + 를 찾고, 없으면 RuntimeBinderException 입니다(7장).

15부 퀴즈 (3) — 같은 프로그램, 다른 거절

Q. C# 14 판 프로그램을 C# 13.0 으로 내리면 거절이 둘뿐입니다. 왜 여섯 기능의 CS9260 은 보이지 않을까요?
