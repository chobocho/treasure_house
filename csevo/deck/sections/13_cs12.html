경고 웨이브 8 — async 메서드 안의 & C# 12.0

왜 — Roslyn 문서: "The compiler shipped with .NET 8 (the C# 12 compiler)" 가 수준 8 에 넣은 경고는 CS9123, "Taking address of local or parameter in async method can create a GC hole" 입니다.

함정 — async 메서드의 지역 변수는 await 를 건너 살아야 하면 상태 기계의 필드, 곧 힙으로 옮겨집니다. GC 가 옮길 수 있는 곳의 주소를 고정 없이 쥐는 셈이라 문서가 "GC hole" 이라고 부릅니다. 이 예제는 42 를 찍지만, 그것은 운이 좋아서입니다.

whats-new: 컴파일러가 매개변수마다 public 속성을 만드는 것은 레코드뿐입니다. "Nonrecord classes and structs might not always want this behavior for primary constructor parameters." 10부에서는 속성 X 가 있는지만 물었습니다(10부). 이번에는 두 형식이 선언한 멤버를 모두 꺼냅니다.

레코드는 지원 필드 둘, 속성 셋, 메서드 여럿(<Clone>$ · Deconstruct · Equals 둘 · PrintMembers …)을 얻습니다. 클래스에 컴파일러가 더한 것은 private 필드 둘뿐이고(Sum 은 직접 쓴 속성) 이름이 <X>P 처럼 소스에서 부를 수 없는 꼴입니다. 레코드의 나머지 멤버는 10부에서 보았습니다.

실행 검증

포착된 매개변수는 숨은 필드가 된다

명세: 인스턴스 멤버가 매개변수를 쓰면 그 매개변수는 "captured into the state of the enclosing type" 이고, 구현은 아마도 "a private field using a mangled name" 일 것이라고 적습니다. Roslyn 이 실제로 만든 필드를 리플렉션으로 봅니다.

필드 이름은 <start>P, private 이고 readonly 가 아닙니다. 디버거에서 숨기는 DebuggerBrowsable 이 붙어 있습니다. start++ 는 이 필드를 고치므로 두 번 부른 뒤 필드 값이 12 입니다. 람다가 지역 변수를 포착할 때 클로저 클래스의 필드를 만드는 것(3부)과 같은 생각이고, 이번에는 그 필드가 형식 자신에 놓입니다.

실행 검증

초기화에만 쓰면 포착하지 않는다

명세: 매개변수를 인스턴스 멤버 초기화자에서만 쓰면 "those can directly reference the parameter of the generated constructor" — 생성자 안에서 도는 코드이니 필드가 필요 없습니다.

InitOnly 에는 속성의 지원 필드 하나뿐이고, Captures 는 매개변수마다 숨은 필드가 생겼습니다. Mixed 에서는 b 만 포착됩니다. 그래서 명세의 "Drawbacks" 가 첫째로 꼽는 것이 객체 크기입니다 — "The allocation size of constructed objects is less obvious". 메서드 하나에서 매개변수를 한 번 읽으면 필드가 하나 늘어납니다.

실행 검증

기반 생성자보다 먼저 저장된다

명세가 적은 생성자의 순서: "1. Parameter values are stored in capture fields, if any. 2. Instance initializers are executed 3. Base constructor initializer is called". 기반 생성자에서 가상 메서드를 불러 그 순서를 엿봅니다.

보통 생성자의 몸체(this.n = n)는 기반 생성자 뒤에 돌아서 Old 는 0 을 봅니다. 포착된 매개변수는 그 전에 저장되므로 New 는 5 를 봅니다. 초기화자는 기반 인수보다도 먼저 돕니다("initializer" 가 "base argument" 앞) — 필드 초기화자가 생성자 초기화자보다 먼저 도는 것은 C# 1 부터의 규칙이고, 기본 생성자의 포착 필드는 그보다도 앞입니다.

실행 검증

함정 — 초기화에도 쓰고 포착도 하면 두 벌

명세의 "Double storage warnings": 매개변수가 포착되면서 초기화자에도 그대로 쓰이면 경고합니다. 예제는 명세의 Person 입니다.

함정 — 값이 두 곳(속성의 지원 필드와 <name>P)에 저장되고 따로 삽니다. Name 을 "Lee" 로 바꿔도 ToString 은 여전히 "Kim" 입니다. 제안서의 열린 질문은 바로 이 경우를 들어 "probably unintended" 라고 적고 경고를 승인했습니다. 고치려면 ToString 이 Name 을 읽게 합니다.
실행 검증

함정 — 기반에도 넘기고 포착도 하면

같은 절의 첫 경우입니다. 기반 생성자의 인수로 넘긴 매개변수를 파생 클래스가 또 포착하면 "there's a high risk that it is inadvertently stored twice in the object."

그냥 컴파일하면 경고 CS9107 이 나옵니다. 그 한 줄이 이 덱의 캡처 폭(200칸)을 넘어서, 실험이 경고 번호와 종료 코드 0 을 따로 확인하고 여기서는 -nowarn:9107 로 끈 결과만 싣습니다. 경고의 끝 문장은 "The value might be captured by the base class as well." 입니다. Name 은 기반의 저장소를, Badge 는 파생의 <name>P 를 읽어 둘이 갈라졌습니다.

실행 검증

매개변수는 바꿀 수 있는 변수다

명세는 포착된 매개변수를 readonly 로 만들지 않습니다(readonly 구조체만 예외, 뒤에서). 발표 글은 매개변수를 readonly 로 표시하는 방법을 "possible future work" 로 꼽습니다.

매개변수 하나가 번호표 상태가 됩니다. 의도한 것이면 필드 선언을 아끼지만, 의도하지 않은 대입도 컴파일러가 막지 않습니다. 바뀌면 안 되는 값은 private readonly 필드를 따로 두고 초기화자에서 받는 것이 확실합니다 — 그때는 몸체에서 매개변수 대신 그 필드만 읽어야 이중 저장 경고가 나지 않습니다.

실행 검증

초기화자의 람다와 메서드가 한 변수를 본다

제안서의 열린 질문: 포착된 매개변수를 초기화자 안의 람다도 쓰면 "the lambda and the state of the enclosing type should refer to the same location". 그러려면 기반 생성자 호출 전에 this 를 클로저에 담아야 하고, LDM(언어 설계 회의)은 이를 받아들였습니다.

10, 11, 12, 13 — 람다와 메서드가 같은 저장소(<p>P)를 번갈아 올립니다. 람다가 생성자 매개변수의 복사본을 따로 잡았다면 10 11 11 12 처럼 갈라졌을 것입니다.

실행 검증

다른 생성자는 this(…) 를 거친다

whats-new: 모든 매개변수가 확실히 대입되도록 "all explicitly declared constructors must call the primary constructor using this() syntax". 레코드의 규칙(10부)이 모든 형식으로 갔습니다.

사슬은 몇 단계든 됩니다 — Range() 가 Range(10) 을, 그것이 기본 생성자를 부르고, 몸체는 사슬이 끝난 뒤 돕니다. 오류 CS8862 는 C# 9 의 레코드에서 본 것과 번호도 문장("a type with parameter list")도 같습니다.

실행 검증

매개변수 없는 생성자가 사라진다

whats-new: "Adding a primary constructor to a class prevents the compiler from declaring an implicit parameterless constructor."

함정 — new T() 제약을 쓰는 제네릭 코드나 매개변수 없는 생성자를 찾는 직렬화기는 기본 생성자를 단 클래스를 만들 수 없습니다. 빈 괄호 Empty() 는 매개변수 없는 기본 생성자 하나를 명시한 것이라 목록이 Plain 과 같습니다.
실행 검증

기반 클래스에 인수 넘기기

명세: 기반 클래스 지정에 인수 목록이 붙으면 생성된 생성자가 "a base initializer with the same argument list" 를 가집니다. 기본 생성자가 없는 클래스에 인수 목록을 붙이면 오류입니다.

인수는 아무 식이나 됩니다($"square {side}"). Square 는 side 를 기반 인수에서만 써서 포착 필드가 없고, 몸체가 빈 클래스입니다. Labeled 처럼 기반에 넘긴 매개변수를 파생 클래스가 다시 읽지만 않으면 이중 저장도 없습니다.

실행 검증

함정 — 기반의 멤버가 매개변수를 가린다

명세의 이름 찾기: 매개변수는 초기화자와 기반 인수에서는 멤버를 가리고, "They are shadowed by members of the declaring type everywhere else." 기반에서 물려받은 멤버도 마찬가지라 경고를 따로 둡니다.

함정 — Get() 의 x 는 기반의 필드라서 1 이 아니라 100 을 돌려줍니다. 경고가 둘 나옵니다. CS9179 가 가려졌다고 알리고, CS9113 은 매개변수를 아무 데서도 읽지 않았다고 알립니다 — 몸체의 x 가 매개변수가 아니었다는 또 하나의 증거입니다.
실행 검증

같은 이름 — 초기화자에서는 매개변수, 몸체에서는 필드

명세가 드는 예입니다. 필드 i 의 초기화자 안의 i 는 매개변수이고, 속성 I 의 몸체 안의 i 는 필드입니다.

40 은 필드가 매개변수 4 로 초기화되고, 몸체가 그 필드를 읽었다는 뜻입니다. 매개변수는 초기화자에서만 쓰였으니 포착되지 않습니다. 레코드가 위치 매개변수와 같은 이름의 속성을 직접 쓸 때 쓰던 규칙(10부)을 일반화한 것입니다. 매개변수와 필드의 이름 규칙을 다르게 두는 팀이라면 이런 코드는 생기지 않습니다.

실행 검증

의존성 주입 — 필드와 생성자가 한 줄로

발표 글이 꼽는 넷째 쓰임이 "To remove boilerplate in dependency injection" 입니다. 서비스를 생성자로 받아 필드에 담는 코드를 견줍니다.

두 클래스가 같은 일을 하고, 컴파일된 모양도 비슷합니다 — Audit 의 clock · store 가 숨은 필드가 됩니다. 다른 점은 그 필드가 readonly 가 아니라는 것입니다(앞에서). 서비스 참조를 실수로 덮어쓸 걱정이 있다면 옛 꼴을 유지하는 팀도 있습니다.

실행 검증

몸체가 없으니 검사는 초기화자에서

제안서의 "Drawbacks": "there is no place for additional logic that might usually be expressed in constructor bodies." 기본 생성자에 몸체를 주는 안은 확장("Primary constructor bodies")으로만 남았습니다.

C# 7 의 throw 식(8부)이 이 자리를 채웁니다. 초기화자는 소스 순서대로 돌므로 Id 의 검사가 Qty 보다 먼저입니다. 검사를 거친 값은 속성에 담고, 몸체에서는 매개변수 대신 속성을 읽어야 검사를 건너뛴 원래 값이 새어 나가지 않습니다.

실행 검증

ref · in 매개변수 — 받을 수는 있지만 포착은 못 한다

명세: 클래스·구조체의 기본 생성자 매개변수는 ref · in · out 일 수 있습니다(레코드에서는 ref · out 이 여전히 안 됨). 하지만 "capturing is not allowed for ref, in or out parameters" — 람다의 제약과 같습니다.

ref counter 의 counter++ 는 호출자의 n 을 올려 두 객체가 1 과 2 를 받고 n 이 3 이 됩니다. 메서드에서 v 를 읽으면 오류 CS9109 와 함께 경고 CS9124 가 나옵니다. 경고는 v 가 "is captured" 라고 말하지만, 바로 아래 오류가 그 포착을 금합니다 — 컴파일러가 포착을 먼저 가정하고 따지는 순서가 드러나는 대목입니다.

실행 검증

특성은 어디에 붙나 — method: 와 field:

명세: 매개변수 목록이 있는 클래스 선언에 method: 대상 특성을 달면 기본 생성자에 붙습니다. 포착 필드를 노린 field: 는 LDM 이 허락하지 않아 "ignored with the warning" 입니다.

대상 없는 특성은 형식에, method: 는 생성자에, 매개변수의 특성은 매개변수에만 붙습니다. 포착 필드 <x>P 에는 아무것도 붙지 않습니다(none). 위치 레코드라면 field: 가 합성 속성의 지원 필드로 갔을 것입니다(10부).

실행 검증

partial 형식 — 매개변수 목록은 한 조각에만

명세: "At most one partial type declaration of a partial class or struct may provide a parameter_list." 목록이 없는 다른 조각에서도 매개변수는 범위 안에 있습니다.

같은 매개변수 목록을 두 번 써도 CS8863 입니다. 소스 생성기가 partial 조각을 덧붙이는 형식이라면, 생성된 조각 쪽에는 목록을 두지 않아야 합니다.

실행 검증

읽지 않은 매개변수는 경고

명세: 레코드처럼 클래스와 구조체도 값 매개변수가 "not captured and is not read within any instance initializers or base initializer" 이면 경고합니다.

경고 CS9113 입니다. 레코드에서는 같은 상황이 CS8907 이었습니다(10부). 쓰지 않는 인수를 받는 생성자는 보통 실수라서 경고로 알려 줍니다.

실행 검증

몸체 대신 세미콜론 — 그리고 C# 11 의 엉뚱한 거절

제안서의 문법은 클래스·구조체·인터페이스·열거형의 몸체가 ; 하나여도 되게 합니다 — "class_body, struct_body, interface_body and enum_body are allowed to consist of just a ;."

C# 11.0 의 거절 여섯이 모두 "primary constructors" 입니다. 매개변수 목록이 없는 class Marker; 도, 기본 생성자와 상관없는 interface IEmpty; · enum Nothing; 도 그 게이트로 거절됩니다. 세미콜론 몸체가 기본 생성자 제안서에 함께 들어온 문법이라 게이트도 함께 쓰는 것입니다. whats-new 는 세미콜론 몸체를 따로 적지 않습니다(1장).

실행 검증

구조체의 기본 생성자 C# 12.0

왜 — whats-new: "In a struct, the implicit parameterless constructor initializes all fields, including primary constructor parameters to the 0-bit pattern." 클래스와 달리 구조체에는 매개변수 없는 생성이 늘 있으니까요.

new Size() 와 default(Size) 는 둘 다 0x0 입니다. Cell 처럼 매개변수 없는 생성자를 직접 쓰면(C# 10, 11부) this(1, 1) 사슬을 거쳐야 하고, 그때 new Cell() 은 R1C1 이지만 default 와 배열 원소는 여전히 R0C0 입니다 — 11부에서 본 구분이 기본 생성자에도 그대로입니다.

실행 검증

readonly 구조체와 readonly 멤버

명세: "In a readonly struct the capture fields will be readonly." 그리고 readonly 멤버 안에서의 접근은 인스턴스 필드와 같은 제약을 받습니다.

readonly 구조체의 포착 필드만 readonly=True 입니다. 대입은 전용 오류 CS9114 로, readonly 멤버 안의 대입은 필드와 같은 CS1604 로 막힙니다. 클래스에서 바라던 "readonly 매개변수" 를 구조체는 형식 전체를 readonly 로 해서 얻습니다(8부).

실행 검증

ref struct — 스팬 매개변수는 초기화에만

명세: "Capturing is not allowed for parameters that have ref-like type". ref struct 는 기본 생성자를 가질 수 있지만, Span<int> 매개변수를 숨은 필드에 담을 수는 없습니다.

ref struct 는 Span<int> 형식의 필드를 직접 선언할 수 있으니(Rest) 초기화자에서 옮겨 담으면 됩니다. 포착만은 안 됩니다 — 컴파일러가 만드는 숨은 필드에는 ref 안전 규칙(12부)을 적용할 자리가 없기 때문으로 보입니다. 문서는 이유를 "similar to a limitation for capturing in lambdas" 라고만 적습니다.

실행 검증

함정 — 구조체의 복사와 this 대입

제안서의 열린 질문: 포착된 매개변수가 있는 구조체에서 this = s 는 그 값을 덮어씁니다. 경고할지 물었고 결론은 "Allowed, no warning" 입니다.

포착 필드도 구조체의 필드라서 복사와 함께 복사됩니다 — b 는 a.Move() 뒤에도 1 입니다. this = other 는 매개변수였던 x 를 9 로 바꿉니다. 소스에는 필드가 보이지 않으니, 매개변수가 "바뀌었다" 는 것이 읽는 사람에게 덜 뚜렷합니다.

실행 검증

네 가지 형식의 같은 괄호 — 무엇이 생기나

발표 글: 기본 생성자는 class · struct · record class · record struct 어디에나 붙고, 레코드에서만 "the compiler generates a public property for each primary constructor parameter" 입니다. 네 형식을 리플렉션으로 한 표에 놓습니다.

클래스와 구조체는 숨은 필드 <x>P 하나만 얻고, 레코드는 지원 필드와 속성, 값 동등성, ToString, Deconstruct 를 얻습니다. 마지막 칸은 구조체 둘만 yes 입니다 — 값 형식에는 늘 default 생성이 있고, 클래스 둘은 앞에서 본 대로 매개변수 없는 생성자를 잃습니다.

실행 검증

뒤 버전 — C# 14 의 partial 생성자와 만나면

C# 14 whats-new: 생성자도 partial 멤버가 될 수 있고, "Only the implementing declaration of a partial constructor can include a constructor initializer" 이며 "Only one partial type declaration can include the primary constructor syntax."

구현 선언이 this(…) 로 기본 생성자를 부릅니다 — 사슬 규칙이 partial 생성자에도 그대로입니다. C# 12.0 의 거절은 기능 이름을 대는 CS9058 이 아니라 파서의 CS1073(13행의 :) 하나뿐입니다 — 옛 문법으로는 정의 선언(7행)부터 다른 무언가로 읽히는 것으로 보입니다. C# 14 는 15부에서 다룹니다. 발표 글은 C# 12 때 "readonly" 표시와 "public property" 생성을 앞으로의 일로 꼽았습니다. 2026-10 기준 whats-new 13·14 에는 그 둘이 없습니다.

실행 검증

2장 퀴즈 — 기본 생성자

Q. class Box(int size) { public int Size { get; } = size; } 에서 Box 객체의 필드는 몇 개일까요? 여기에 public int Twice() => size * 2; 를 더하면 어떻게 될까요?

A. 처음에는 속성의 지원 필드 하나입니다 — 초기화자에서만 쓴 매개변수는 포착되지 않습니다(2장). 메서드를 더하면 size 가 포착되어 숨은 필드 <size>P 가 생기고 필드가 둘이 됩니다. 같은 값이 두 곳에 저장되므로 컴파일러가 이중 저장 경고 CS9124 를 냅니다(2장). Twice 가 Size * 2 를 쓰면 둘 다 사라집니다.

3장

형식 별칭 — 이름 없는 형식에 이름을

튜플 · 배열 · 기본 형식 · 포인터와 using unsafe · nullable · 열린 제네릭 · global using ·

왜 생겼나 — 이름 붙은 형식에만 되던 별칭

제안서: C# 은 오래전부터 네임스페이스와 이름 붙은 형식(클래스 · 대리자 · 인터페이스 · 레코드 · 구조체)에 별칭을 붙일 수 있었습니다. 그런데 "the rise of additional complex type symbols in the language" 로 별칭이 쓸모 있을 곳이 늘었습니다. 튜플과 함수 포인터는 글로 쓰면 길고 읽기 힘듭니다.

  • C# 1 의 using 별칭은 같은 이름의 두 형식을 가르는 도구였습니다(2부). 별칭::이름 과 extern 별칭은 C# 2 입니다(3부).
  • C# 10 의 global using 이 별칭을 프로젝트 전체로 넓혔습니다. 별칭이 닫힌 제네릭 형식에도 붙는 것은 거기서 보았습니다(11부).
  • C# 12 는 오른쪽의 문법을 바꿉니다 — namespace_or_type_name 이 (namespace_name | type) 이 됩니다.

버전 기록의 한 줄: "You can use the using alias directive to alias any type, not just named types."

문서 근거

모든 형식의 별칭(alias any type) C# 12.0

왜 — whats-new: 이제 "semantic aliases for tuple types, array types, pointer types, or other unsafe types" 를 만들 수 있습니다. 예제의 Point 는 제안서의 첫 예와 같은 꼴입니다.

매개변수 · 반환 형식 · 지역 변수 어디서나 Point 가 (int X, int Y) 대신 섭니다. 원소 이름 X · Y 도 별칭을 따라옵니다. C# 10 까지는 이런 튜플에 이름을 주려면 record struct(11부) 같은 새 형식을 선언해야 했습니다.

실행 검증

함정 — 별칭은 새 형식이 아니다

표준: using 별칭은 "an alias for a namespace or type" 를 들일 뿐입니다. 이름이 다른 두 별칭이 같은 튜플을 가리키면 컴파일러에게는 하나의 형식입니다.

함정 — Show(Point) 에 Size 가 아무 말 없이 들어가고, 두 오버로드는 "같은 매개변수 형식"(CS0111)입니다. 런타임 형식은 둘 다 ValueTuple`2[Int32,Int32] 입니다. 단위를 섞지 못하게 막는 형식 안전이 필요하면 별칭이 아니라 record struct 를 씁니다. 튜플 원소 이름이 대입에서 바뀌는 것은 C# 7 튜플의 규칙 그대로입니다(8부).
실행 검증

배열 · 기본 형식 키워드 · int?

언어 버전 기록: C# 12 는 별칭의 제약을 풀어 "built-in types, tuple types, pointer types, array types" 를 받습니다. int 같은 키워드는 이름이 아니라서 예전 문법(namespace_or_type_name)에 들 수 없었습니다.

using Num = double; 은 using Num = System.Double; 과 같은 형식을 가리킵니다(System.Double). 앞의 꼴만 C# 12 이고, 뒤의 꼴은 C# 1 부터 되었습니다. 별칭은 List<Num> 처럼 형식 인수 자리에도 섭니다. 마지막 별칭 Lookup 은 C# 11 까지도 되던 닫힌 제네릭 별칭입니다.

실행 검증

포인터와 함수 포인터 — using unsafe

제안서: 포인터를 담은 형식의 별칭을 위해 using 뒤에 선택적 unsafe 를 둡니다. 그 키워드는 "causes the entire textual extent of the 'type' portion ... to become an unsafe context." 발표 글의 예도 using unsafe ArrayPtr = int*; 입니다.

함수 포인터(10부)의 긴 꼴이 BinOp 한 낱말이 됩니다. unsafe 를 빼면 별칭 줄에서 CS0214, 프로젝트가 unsafe 코드를 허락하지 않으면 쓰지 않는 별칭이어도 using unsafe 자체가 CS0227 입니다. 별칭을 쓰는 쪽도 여전히 unsafe 문맥이어야 합니다(unsafe class App).

실행 검증

string? 은 별칭이 못 된다

제안서: "It is illegal for a using alias type to be a nullable reference type." 예는 셋입니다 — using X = string?; 은 안 되고, List<string?> 와 int? 는 됩니다.

거절은 전용 오류 CS9132 입니다. int? 는 Nullable<int> 라는 진짜 형식이고(Nullable`1), string? 은 같은 string 에 붙은 주석(annotation)일 뿐이라(9부) 별칭이 가리킬 형식이 따로 없습니다.

실행 검증

열린 제네릭 별칭은 여전히 없다

C# 12 의 문법 변경은 별칭의 오른쪽만 넓힙니다 — 왼쪽은 그대로 'using' identifier '=' 입니다. C# 10 명세도 별칭은 "cannot name an unbound generic type declaration" 이라고 적었습니다.

Lst<T> 는 파서가 = 앞에서 ; 를 기다리다 실패합니다(CS1002 · CS1525) — 형식 매개변수를 가진 별칭이라는 문법 자체가 없습니다. List<> 는 CS7003 입니다.

실행 검증

global using 과 함께 — 그리고 별칭의 별칭

발표 글: "Like other using aliases, these types can be used at the top of a file and in global using statements."

함정 — Line[] 의 Line 을 못 찾습니다(CS0246). 별칭의 오른쪽은 "as if the immediately containing compilation unit or namespace body had no using_directives" 로 풉니다 — 다른 별칭도, 전역 별칭도 보지 않습니다. 그래서 Lines 는 튜플을 다시 다 적었습니다.
실행 검증

함정 — 별칭의 오른쪽은 using 을 보지 않는다

같은 규칙이 네임스페이스 using 에도 적용됩니다. 제안서는 이 문장을 그대로 두고 대상만 (namespace_name | type) 으로 바꿨습니다.

바로 위에 using System.Text; 가 있고, 본문에서는 StringBuilder 가 짧은 이름으로 통하는데도(마지막 줄 "y") 별칭의 오른쪽에서는 CS0246 입니다. 키워드로 쓰는 튜플 (int A, string B) 는 이름 찾기가 필요 없어 늘 됩니다. 별칭의 오른쪽에는 System. 부터 다 적는 것이 안전합니다.

실행 검증

뜻밖의 것 — dynamic 별칭은 C# 4 부터 되었다

발표 글은 배열 · 튜플 · 포인터 별칭을 "not valid in earlier versions of C#" 의 예로 듭니다. 그 목록에 없는 dynamic 을 여러 언어 버전으로 컴파일해 봅니다.

C# 11.0 에서도, dynamic 이 처음 나온 C# 4(5부)에서도 돌아갑니다. C# 3 의 오류가 실마리입니다 — 컴파일러가 dynamic 을 이름으로 찾다가 못 찾았다고 합니다(CS0246). 예전 문법의 namespace_or_type_name 에 이름 하나가 들어가고, 그 이름이 C# 4 부터 dynamic 형식으로 풀렸던 것으로 보입니다. 문서가 이 경우를 적은 곳은 찾지 못했습니다(1장).

실행 검증

뒤 버전 — C# 14 가 가져간 별칭 이름 extension

Roslyn 의 .NET 10 깨지는 변경 문서: extension 이 문맥 키워드가 되어 "The "extension" identifier may not be used as a type name" — 첫 예가 using extension = ...; 입니다.

C# 12.0 에서는 아무 말 없이 돌고(8), 같은 소스를 C# 14.0 으로 컴파일하면 전용 오류 CS9306 입니다 — 언어 버전에 묶인 거절이라 SDK 만 올리고 언어 버전을 그대로 두면 깨지지 않습니다. 12부에서 본 required · scoped · file 과 같은 길입니다(12부). 소문자만인 이름을 미리 알려 주는 경고 웨이브 7 의 CS8981 이 이 경우에도 쓸모 있습니다. C# 14 의 확장 멤버는 15부에서 다룹니다.

3장 퀴즈 — 형식 별칭

Q. 한 파일에 using Meters = double; 과 using Feet = double; 을 두고 static void Walk(Meters m) 와 static void Walk(Feet f) 를 함께 선언하면 어떻게 될까요?

A. 두 번째 선언이 "이미 같은 매개변수 형식의 Walk 가 있다"(CS0111)로 거절됩니다. 별칭은 새 형식이 아니라 이름일 뿐이라 둘 다 double 입니다(3장). 단위를 형식으로 가르려면 readonly record struct Meters(double Value); 처럼 형식을 선언합니다.
