이 부에서 할 일

C# 의 모든 뒤 버전은 C# 1.0 위에 쌓였습니다. 이 부는 그 바닥을 봅니다 — 지금도 그대로 남아 있는 규칙과, 지금도 그대로 남아 있는 함정입니다.

  • 1장 — C# 1.0 한눈에. 무엇을 가졌고 무엇이 없었나, 그리고 그 아래의 런타임.
  • 2장 — 통합 형식 체계. 값 형식과 참조 형식, 박싱, 열거형, 배열, 문자열, decimal, 넘침 검사, const.
  • 3장 — 식과 연산자·매개변수. 연산자 오버로딩, 사용자 정의 변환, ref·out·params, 오버로드 해석, is·as, 정수 나눗셈, 수치 승격.
  • 예제는 전부 <LangVersion>1</LangVersion> 로 컴파일합니다. 지금의 컴파일러가 C# 1 의 규칙으로 받아 준다는 것 자체가 "C# 1 문법" 이라는 증거입니다(0부).
  • 뒤 버전이 그림을 바꾼 곳에서만 그 버전으로 다시 컴파일한 캡처를 하나 덧붙입니다.

C# 1.0 한눈에

버전 기록은 C# 1.0 의 주요 기능으로 클래스·구조체·인터페이스·이벤트·속성·대리자·연산자와 식·문장·특성을 꼽습니다. 이 표는 그 가운데 이 덱이 장을 따로 둔 것입니다.

문서 근거

"자바를 많이 닮았다"

공식 버전 기록은 C# 1.0 을 이렇게 돌아봅니다.

버전 기록에서 — "C# version 1.0, released with Visual Studio .NET 2002, looked a lot like Java." ECMA 에 낸 설계 목표는 "simple, modern, general-purpose object-oriented language" 였고, 그때 자바를 닮았다는 것은 그 목표를 이뤘다는 뜻이었다고 적습니다.

같은 글은 지금 눈으로 보면 어지럽다고도 적습니다. async 가 없고, 제네릭이 아예 없고, LINQ 도 없었습니다. "윈도 플랫폼에서 자바를 대신할 만한 언어" 였다는 것이 그 글의 결론입니다.

문서 근거

처음부터 표준으로

C# 은 ECMA 표준(ECMA-334)으로도 정해졌습니다. ECMA 의 표준 페이지가 판마다 나온 때와, Visual C# 버전에 대응하는 표준을 적어 둡니다.

값 형식과 참조 형식 C# 1.0

왜 — 구조체 변수는 데이터를 직접 담고, 클래스 변수는 데이터를 담은 객체를 가리키는 참조를 담습니다. 그래서 클래스는 두 변수가 한 객체를 함께 가리킬 수 있고, 구조체는 변수마다 제 복사본을 가집니다.

바뀌지 않는 문자열 C# 1.0

왜 — string 은 object 에서 바로 나온 봉인된 클래스이고, 그 인스턴스는 UTF-16 코드 단위의 열입니다. 인스턴스를 바꾸는 메서드는 없고, ToUpper·Replace 는 새 문자열을 돌려줍니다.

함정 — s.ToUpper(); 한 줄은 아무것도 바꾸지 않는데 경고도 없습니다. b += "-two" 는 b 가 새 문자열을 가리키게 할 뿐, a 는 그대로입니다.
실행 검증

Length 는 글자 수가 아니다

string 은 UTF-16 코드 단위의 열이므로, 기본 다국어 평면 밖의 글자(이모지 같은 것)는 대리 쌍 (surrogate pair) 두 단위를 차지합니다. char 하나는 2바이트입니다.

실행 검증

축자 문자열 @"…" C# 1.0

왜 — 정규 문자열 리터럴은 \t·\n 같은 단순 이스케이프를 해석합니다. 축자 (verbatim) 문자열 리터럴은 @" 로 시작하고, 큰따옴표를 두 번 쓴 "" 말고는 모든 글자를 그대로 받으며 여러 줄에 걸칠 수 있습니다.

함정 — "C:\temp\new" 는 컴파일되고 9글자입니다. \t 와 \n 은 올바른 이스케이프라 컴파일러가 의심하지 않습니다.
실행 검증

문자열로 switch C# 1.0

왜 — switch 문의 지배 형식(governing type)에 string 이 들어 있습니다. 그리고 각 절의 끝은 다음 절로 이어질 수 없어서, 이어 가려면 goto case 를 명시해야 합니다.

함정 — 비교는 대소문자를 가립니다. null 을 넣어도 예외가 아니라 default 로 갑니다.
실행 검증

switch 의 두 규칙 — 빠져 내려가기 금지, bool 은 C# 2.0 부터

break 를 빠뜨려 다음 case 로 빠져 내려가게 두면 컴파일 오류입니다. 그리고 C# 1 은 bool 로 switch 하는 것을 받지 않습니다 — 컴파일러의 기능 게이트가 "switch on boolean type" 을 C# 2 로 적어 둡니다.

실행 검증

문자열 == 은 값 비교, 리터럴은 하나로

string 의 == 는 길이와 글자를 비교합니다. 한편 상수식 "hel" + "lo" 는 컴파일할 때 접혀 리터럴 "hello" 와 같은 인스턴스가 됩니다. 실행 중에 만든 문자열은 내용이 같아도 다른 인스턴스이고, String.Intern 이 같은 내용의 인스턴스를 찾아 줍니다.

실행 검증

object 로 보면 == 은 참조 비교

한쪽이라도 정적 형식이 object 이면 문자열 비교가 아니라 참조 비교가 골라집니다. 이때는 컴파일러가 경고합니다.

참조 형식 동등 연산자로 문자열의 값이 아니라 참조를 비교할 수 있다는 것은 표준의 주석에도 있습니다.

실행 검증

합성 서식 — C# 1 시절의 문자열 만들기

보간 문자열이 없던 때는 String.Format 의 자리 표시자 {0}·{1,5}· {1:X4} 나 + 연결로 문자열을 만들었습니다. Console.WriteLine 도 같은 서식을 받습니다.

실행 검증

보간 문자열은 C# 6

표준은 보간 문자열 식의 뜻을 string.Format 호출로의 변환으로 정의합니다 — 같은 일을 하는 새 문법입니다.

실행 검증

10진 실수 decimal C# 1.0

왜 — decimal 은 금융·통화 계산에 맞춘 128비트 형식입니다. float·double 과 달리 0.1 같은 10진 소수를 정확히 나타내고, 무한대와 NaN 은 꼭 지원하지 않아도 됩니다. 그래서 0 으로 나누면 예외입니다.

함정 — 1.50m 은 끝의 0 까지 기억해 "1.50" 으로 찍히지만 1.5m 과 같습니다. double 의 출력 "0.30000000000000004" 는 이 런타임의 서식 결과입니다.
실행 검증

실수 리터럴은 double — decimal 로는 저절로 안 간다

접미사 없는 실수 리터럴은 double 입니다. double 과 decimal 사이에는 어느 쪽으로도 암시적 변환이 없습니다.

실행 검증

checked 와 unchecked C# 1.0

왜 — 정수 산술과 변환이 넘칠 때 무엇을 할지는 문맥이 정합니다. checked 문맥은 OverflowException 을 던지고, unchecked 문맥은 높은 자리 비트를 버립니다. 실행 중에 계산하는 식의 기본값은 unchecked 입니다.

실행 검증

상수식의 넘침은 컴파일 오류

상수식의 기본 문맥은 언제나 checked 입니다. 명시적으로 unchecked 에 넣지 않으면 컴파일할 때의 넘침은 컴파일 오류입니다.

그래서 int.MaxValue + 1 은 컴파일 오류인데, 변수에 담은 max + 1 은 조용히 음수가 됩니다. 같은 식, 다른 결과입니다.

실행 검증

int.MinValue 에는 짝이 없다

2의 보수 정수는 음수가 하나 더 많습니다. unchecked 문맥에서 -int.MinValue 는 자기 자신으로 돌아오고, 라이브러리의 Math.Abs 는 예외를 던집니다.

실행 검증

const 와 readonly C# 1.0

왜 — 상수(const)는 컴파일할 때 계산할 수 있는 값을 나타내는 멤버입니다. 읽기 전용 필드(readonly)는 선언이나 같은 클래스의 생성자에서만 대입할 수 있는 필드라, 실행할 때 정해지는 값과 const 에 못 쓰는 형식을 담습니다.

함정 — readonly 는 필드(참조)를 못 바꾸게 할 뿐입니다. 그 참조가 가리키는 ArrayList 에는 얼마든지 Add 할 수 있습니다.
실행 검증

컴파일러가 만드는 것 — literal 과 initonly

메타데이터에서 const 는 값을 품은 리터럴 필드이고, readonly 는 initonly 표시가 붙은 보통 필드입니다. const 는 static 이라고 쓰지 않아도 static 입니다.

실행 검증

const 의 규칙

const 는 static 으로 여겨지지만 static 을 붙일 수는 없습니다. new 는 상수식이 아니므로, string 이 아닌 참조 형식의 상수가 가질 수 있는 값은 null 하나뿐입니다.

실행 검증

case 에는 상수만

switch 의 case 레이블은 상수식이어야 합니다. const 는 되고, 값이 같아도 static readonly 는 안 됩니다.

실행 검증

readonly 구조체 필드는 복사본에 일한다

readonly 필드는 생성자 밖에서 변수가 아니라 값으로 다뤄집니다. 그래서 readonly 구조체 필드에 메서드를 부르면 복사본에서 돌고, 필드는 그대로입니다. 오류도 경고도 없습니다.

readonly 필드를 생성자 밖에서 접근하면 그 결과는 값입니다.

실행 검증

const 는 호출한 쪽에 구워진다

상수와 읽기 전용 필드는 이진 버전 관리의 뜻이 다릅니다. 식이 상수를 참조하면 그 값은 컴파일할 때 가져오고, 읽기 전용 필드를 참조하면 실행할 때 가져옵니다.

그래서 라이브러리의 public const 값을 바꾸고 라이브러리만 다시 빌드하면, 그 라이브러리를 쓰는 다른 어셈블리는 다시 컴파일할 때까지 옛 값을 씁니다. 바뀔 수 있는 값은 static readonly 로 둡니다.

이 덱에서 돌리지 않은 까닭 — csrun 은 예제 하나를 어셈블리 하나로 컴파일합니다. 두 어셈블리가 필요한 이 현상은 표준의 설명만 옮겼습니다. 앞의 리터럴 필드가 그 값이 메타데이터에 있다는 것까지는 보여 줍니다.
문서 근거

2장 퀴즈

Q. 구조체 Counter 의 Bump() 는 N++ 를 합니다. 다음 두 경우 모두 N 이 0 그대로입니다. 왜 그렇고, 둘 가운데 컴파일러가 막아 주는 꼴은 무엇입니까? (가) readonly Counter Ro; 필드에 Ro.Bump() (나) ArrayList 에 넣은 값에 ((Counter)list[0]).Bump()

A. 둘 다 복사본에서 Bump 가 돌기 때문입니다. (가)는 readonly 필드를 생성자 밖에서 읽으면 그 결과가 값이라서, (나)는 언박싱이 박스 안의 값을 복사해 꺼내기 때문입니다. 메서드 호출은 둘 다 조용히 컴파일됩니다. 막히는 것은 (나)에서 필드에 직접 대입하는 꼴 ((Counter)list[0]).N = 5 뿐입니다(CS0445).

식과 연산자·매개변수

연산자 오버로딩 · 사용자 정의 변환 · ref·out·params · 오버로드 해석 · is·as · 정수 산술

연산자 오버로딩 C# 1.0

왜 — 연산자(operator)는 클래스·구조체의 인스턴스에 식 연산자가 무슨 뜻인지 정하는 멤버입니다. 연산자 선언은 public 과 static 을 둘 다 가져야 합니다.

c += b 를 위해 따로 정의한 것은 없습니다. C# 1 에서 복합 대입은 이항 연산자로 풀립니다 (뒤에서).

실행 검증

컴파일러가 만드는 것 — op_ 이름의 정적 메서드

연산자 선언은 메타데이터에서 op_Addition·op_UnaryNegation·op_Implicit 같은 예약된 이름의 정적 메서드가 되고, 특수 이름(specialname) 표시가 붙습니다. 연산자를 모르는 다른 .NET 언어는 이 이름으로 부릅니다.

그 이름을 C# 코드에서 직접 부르는 것은 컴파일러가 막습니다.

실행 검증

짝으로 선언해야 하는 연산자

== 와 !=, < 와 >, <= 와 >= 는 짝으로 선언해야 합니다. 하나만 정의하면 컴파일 오류입니다.

경고 CS0660·CS0661 은 == 를 정의하면서 Equals·GetHashCode 를 다시 정의하지 않았다는 것입니다. 앞 장의 Money 가 둘을 함께 정의한 까닭입니다.

실행 검증

오버로딩한 == 과 null

클래스에 == 를 정의하면 v == null 도 그 연산자를 부릅니다. 연산자 안에서 null 을 생각하지 않으면 비교하다가 NullReferenceException 이 납니다.

함정 — C# 1 에서 "정말 null 인가" 를 묻는 안전한 길은 (object)v == null 처럼 object 로 바꿔 참조 비교를 고르게 하는 것입니다. 연산자 안에서도 같은 방법으로 null 을 먼저 거릅니다.
실행 검증

+= 은 새 객체를 만든다

C# 1 에서 x op= y 는 미리 정의된 연산자가 아니면 x = x op y 로 풀립니다. 클래스의 operator + 가 새 객체를 돌려주므로, += 뒤의 t 는 다른 객체입니다.

실행 검증

뒤 버전에서 — 복합 대입 연산자를 직접 (C# 14)

C# 14 는 += 를 인스턴스 연산자로 직접 정의하게 했습니다. 컴파일러의 기능 게이트가 그 버전을 적어 둡니다.

같은 t += 2 가, C# 1 의 풀이에서는 새 객체를 만들고 C# 14 의 연산자로는 alias 가 보는 객체를 고칩니다. 이 기능 자체는 15부의 몫입니다.

실행 검증

operator true·false 와 &&

사용자 형식에 && 를 쓰려면 operator & 와 함께 operator true· operator false 가 있어야 합니다. x && y 는 T.false(x) ? x : T.&(x, y) 로 계산됩니다.

a 가 거짓이면 operator false(a) 하나로 끝나고 & 는 불리지 않습니다. if (b) 는 operator true 를 부릅니다.

실행 검증

사용자 정의 변환 implicit·explicit C# 1.0

왜 — 변환 연산자는 미리 정의된 암시적·명시적 변환에 사용자 정의 변환을 더합니다. 표준의 주석은 암시적 변환은 예외를 던지지도 정보를 잃지도 않게 설계하고, 그럴 수 있는 변환은 명시적으로 두라고 권합니다.

Math.Max(body, 40.0) 는 Celsius 를 받는 오버로드가 없어도 됩니다 — 암시적 변환으로 double 판이 골라집니다.

실행 검증

언박싱에는 사용자 변환이 없다

사용자 정의 변환은 컴파일할 때 정적 형식을 보고 고릅니다. object 에서 (double) 로 캐스트하면 그것은 언박싱이고, 박스에 든 것이 Celsius 이므로 실패합니다.

함정 — (double)c 와 (double)o 는 글자가 같아 보여도 전혀 다른 변환입니다. 앞의 것은 op_Implicit 호출, 뒤의 것은 언박싱입니다.
실행 검증

사용자 변환은 한 번만 끼어든다

사용자 정의 변환의 계산에는 사용자 정의 변환 연산자가 두 개 이상 끼지 않습니다. S 에서 X 로, 다시 X 에서 T 로 가는 두 단계 변환은 없습니다.

실행 검증

ref 와 out 매개변수 C# 1.0

왜 — 참조 매개변수(ref)와 출력 매개변수(out)는 새 저장소를 만들지 않고 호출한 쪽의 변수를 가리킵니다. 둘의 차이는 확정 대입입니다 — ref 로 넘길 변수는 미리 대입되어 있어야 하고, out 매개변수는 메서드가 돌아가기 전에 반드시 대입해야 합니다.

실행 검증

확정 대입 — 컴파일러가 세는 것

C# 은 지역 변수를 읽기 전에 반드시 대입했는지 흐름을 따라 검사합니다. ref·out 의 규칙도 그 검사의 일부입니다.

호출하는 쪽에서 ref·out 을 빠뜨리는 것도 오류입니다(CS1620). 인자를 넘기는 자리에서 "이 변수는 바뀔 수 있다" 가 보입니다.

실행 검증

참조 형식을 ref 로 넘기면

참조 형식을 값으로 넘기면 참조의 복사본이 갑니다 — 객체는 함께 쓰지만, 매개변수에 새 객체를 대입해도 호출한 쪽 변수는 그대로입니다. ref 로 넘기면 호출한 쪽 변수 자체를 바꿉니다.

실행 검증

배열 원소와 필드도 ref 로

ref·out 인자는 변수여야 합니다. 배열 원소와 필드는 변수라서 그대로 넘길 수 있습니다.

실행 검증

컴파일러가 만드는 것 — ref·out·params 의 메타데이터

메타데이터에서 ref 와 out 은 같은 by-ref 형식(Int32&)이고, out 에는 표시 하나가 더 붙습니다. params 는 매개변수에 붙은 ParamArrayAttribute 입니다.

실행 검증

뒤 버전에서 — 호출 자리의 out 변수 (C# 7.0)

C# 1 은 out 으로 받을 변수를 먼저 선언해야 했습니다. 호출 자리에서 out int h2 로 선언하는 것은 C# 7.0 의 기능입니다. 컴파일러가 그 버전을 알려 줍니다.

실행 검증

params 배열 C# 1.0

왜 — 매개변수 배열(params)은 인자 개수가 정해지지 않은 메서드를 만듭니다. 오버로드 해석은 먼저 배열을 그대로 받는 정상 꼴(normal form)을 보고, 그게 안 될 때만 인자들을 배열로 묶는 확장 꼴(expanded form)을 씁니다.

String.Concat 과 Console.WriteLine 의 서식 판도 params 로 인자를 받습니다.

params object[] 의 함정

매개변수가 params object[] 이면 인자 하나가 "배열 자체" 인지 "원소 하나" 인지가 애매해집니다. 표준도 object[] 가 object 로 바뀔 수 있어서 생기는 모호함을 짚고, 캐스트로 풀라고 적습니다.

함정 — string[] 은 배열 공변성 덕에 object[] 로 받아져 원소 둘로 펼쳐지고, int[] 는 object[] 가 될 수 없어 원소 하나로 싸입니다. Show(null) 은 배열이 아예 null 입니다.

오버로드 해석의 기초 C# 1.0

왜 — 인자 목록과 후보 메서드들이 주어지면, 오버로드 해석은 적용할 수 있는 후보 가운데 가장 나은 하나를 고릅니다. 하나로 정해지지 않으면 컴파일 오류입니다. "더 나은 변환" 이 그 기준입니다.

함정 — 'a' 는 F(int), float 은 F(double), uint 는 F(long) 으로 갑니다. decimal 은 double 로 암시적으로 바뀌지 않아 F(object) 로 박싱됩니다. null 은 더 구체적인 F(string) 이 이깁니다.

조건 연산자 ?: 의 형식 C# 1.0

왜 — b ? x : y 의 형식은 두 갈래에서 정합니다. 한쪽에서 다른 쪽으로만 암시적 변환이 있으면 그 다른 쪽이 식의 형식입니다. 조건 연산자는 오른쪽 결합입니다.

함정 — yes ? 'a' : 0 은 int 라서 97 이 찍힙니다. int 상수에서 char 로 가는 암시적 변환은 없고, char 에서 int 로는 있기 때문입니다. yes ? 1 : 2.5 는 double 이라 1 이 "1" 로 찍혀도 형식은 Double 입니다.

C# 9 는 대입 대상의 형식이 있으면 그것으로 조건식을 받아 줍니다(target-typed conditional).

정수 나눗셈과 나머지의 부호 C# 1.0

왜 — 정수 나눗셈은 0 쪽으로 버립니다. 나머지 x % y 는 x – (x / y) * y 로 정의되므로 부호가 왼쪽 피연산자를 따릅니다.

함정 — 표준은 unchecked 문맥의 int.MinValue / -1 이 예외를 던질지 왼쪽 피연산자를 돌려줄지를 구현에 맡깁니다. 이 런타임(.NET 10, 이 기계)은 OverflowException 을 던졌습니다.

& 와 && C# 1.0

왜 — &&·|| 는 "단락(short-circuiting)" 논리 연산자로, 왼쪽만으로 답이 나면 오른쪽을 계산하지 않습니다. bool 에 쓴 &·|·^ 는 양쪽을 다 계산합니다.

실행 검증

정수는 조건이 될 수 없다

if 의 조건은 bool 이어야 합니다(bool 식). 정수에서 bool 로 가는 변환은 암시적이든 명시적이든 없습니다. 그래서 == 자리에 = 를 쓴 if (n = 2) 가 컴파일되지 않습니다.

함정 — flags & 2 == 2 는 == 가 & 보다 먼저 묶여 flags & true 가 되고, int 와 bool 사이의 & 는 없으므로 형식 오류(CS0019)로 드러납니다.

3장 퀴즈

Q. static void Show(params object[] args) 에 대해 Show(new string[] { "a", "b" }) 와 Show(new int[] { 1, 2 }) 의 args.Length 는 각각 얼마이고, 왜 다릅니까?

A. 2 와 1 입니다. string[] 은 배열 공변성으로 object[] 로 바뀔 수 있어 정상 꼴이 적용되고, 배열이 그대로 args 가 됩니다. int[] 는 값 형식의 배열이라 object[] 로 바뀌지 않으므로, 확장 꼴로 배열 하나를 원소 하나로 싸서 넘깁니다.
