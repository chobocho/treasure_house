ref struct 의 확장 — 제네릭·인터페이스·async 로

allows ref struct · 인터페이스를 구현하는 ref struct · 반복기와 async 안의 ref 지역 변수와 unsafe · 반복기의 안전 문맥

왜 — Span 이 .NET 의 추상화에 끼지 못했다

제안서의 동기: "The inability for ref struct to implement interfaces means they cannot participate in fairly fundamental abstraction techniques of .NET." Span<T> 는 순서 있는 목록의 성질을 다 가졌는데도 IReadOnlyList<T>·IEnumerable<T> 를 받는 메서드에 들어가지 못해 "specific methods must be coded for Span<T> that have virtually the same implementation" 이었습니다. whats-new 는 세 기능을 한 묶음으로 소개합니다 — "This feature and the following two features enable ref struct types to use new constructs."

whats-new 의 말대로 "You won't use these features unless you write your own ref struct types" — 대개는 BCL 의 스팬 API 가 넓어지는 것으로 간접 혜택을 봅니다.

문서 근거

allows ref struct 반제약 (anti-constraint) C# 13.0

왜 — whats-new: C# 13 이전에는 "ref struct types couldn't be declared as the type argument for a generic type or method." 이제 제네릭 선언이 "an anti-constraint, allows ref struct" 를 달 수 있고, 그러면 "The compiler enforces ref safety rules on all instances of that type parameter." 예제의 Identity 는 제안서의 것입니다.

Holder<Span<int>> 를 거쳐 쓴 42 가 원래 배열의 local[2] 에 보입니다 — 복사가 아니라 같은 메모리입니다. string·int 도 여전히 됩니다. 반제약을 빼면 CS9244 — 문장이 "a type parameter allowing ref structs" 를 요구합니다 (8부에서 C# 7.2 예제에 섞여 나온 그 낱말).

실행 검증

T 가 ref struct 일 수도 있으면 — 힙으로 가는 길이 모두 막힌다

제안서: 이 반제약이 붙은 형식 매개변수는 "has all of the behaviors of a ref struct type" — 박싱할 수 없고, 수명 규칙을 따르고, "cannot be used in static fields, elements of an array, etc ...", 그리고 scoped 를 붙일 수 있습니다.

네 오류 모두 8부에서 Span 에 대해 본 번호(CS8345·CS0029·CS0611)와 같은 무리이고, 대상이 구체 형식이 아니라 'T' 입니다. 람다 쪽은 "parameter 't' that has ref-like type" 이라고 부릅니다 — T 가 실제로 int 로 불려도 메서드 본문은 최악의 경우를 기준으로 검사됩니다.

실행 검증

함정 — 다른 제네릭에 넘기지도, ToString 을 부르지도 못한다

제안서: 이런 T 는 "Cannot be used as a generic argument unless the corresponding parameter is also where T: allows ref struct" 입니다. 반제약은 전염됩니다 — 부르는 쪽이 달면 불리는 쪽도 달아야 합니다.

List<T> 의 T 에는 반제약이 없어 CS9244 입니다(코드는 앞 장). 더 뜻밖인 것은 t.ToString() — Span<T> 는 ToString 을 재정의했지만 T 로는 그것을 알 수 없으므로 object 의 메서드를 부르는 박싱으로 보고 CS0029 입니다. 8부의 r.ToString() 과 같은 이유입니다(8부).

실행 검증

T 도 수명 규칙을 따른다 — 스택을 가리킬 수 있는 값은 못 돌려준다

제안서의 M2: span 이 지역 stackalloc 을 가리키므로 그것을 받아 만든 T 의 "safe-to-escape is current method" 이고, 그래서 return t; 는 오류입니다. 수명 규칙 자체는 12부의 scoped 와 같습니다.

Make 는 실제로 default 만 돌려주지만 컴파일러는 서명만 보고 "결과가 span 을 품었을 수 있다" 고 판단합니다 — CS8352. 같은 메서드가 int 로 불리면 아무 일도 없지만, 본문은 T 가 ref struct 인 경우에 맞춰 한 번만 검사됩니다. scoped T 는 "이 매개변수는 밖으로 새지 않는다" 는 약속이라 스택의 s 도 받습니다.

실행 검증

반제약을 적는 자리 — 맨 끝, class 와는 함께 못 쓴다

제안서: "The allows ref struct must be the last constraint in the where clause", class 제약이나 참조 형식 기반 제약과는 함께 쓸 수 없습니다. 그리고 "The anti-constraint is not "inherited" from a type parameter type constraint" — where S : T 의 S 는 ref struct 를 받지 않습니다.

struct, allows ref struct 는 "값 형식이면 ref struct 도 좋다" 는 뜻이라 Span<int>·int 를 다 받습니다. 셋째 거절이 T 가 아니라 S 를 짚습니다 — T 자리의 Span<int> 는 받아들여졌고, 반제약이 없는 S 가 막혔습니다.

실행 검증

new() 와 함께 — 제네릭 코드가 ref struct 를 만든다

반제약은 다른 제약과 섞을 수 있습니다(앞 장). new() 와 섞으면 제네릭 메서드가 ref struct 를 스택에 직접 만들고, .NET 10 의 Activator.CreateInstance<T> 도 이 반제약을 달았습니다(런타임 장의 Activator 1).

new T() 는 Counter 의 매개변수 없는 생성자(C# 10, 11부)를 불러 100 을 냅니다. Activator 판도 100 입니다 — 리플렉션 경로로도 ref struct 가 만들어집니다. 람다 c => c.N 이 Func<Counter, int> 가 되는 것도 이 장의 다른 결과입니다(Func).

실행 검증

메타데이터 — 형식 매개변수의 플래그 하나, 특성은 없다

제안서: 이 반제약은 "System.Reflection.GenericParameterAttributes.AllowByRefLike(0x0020)" 플래그로 적히고, 런타임이 지원하는지는 "System.Runtime.CompilerServices.RuntimeFeature.ByRefLikeGenerics" 필드로 압니다.

값은 32(0x20)이고, Box<> 에는 특성이 하나도 없어 attr 줄이 찍히지 않았습니다 — ref struct 자신에 붙던 Obsolete· CompilerFeatureRequired(8부) 같은 옛 컴파일러 막이가 형식 매개변수에는 없습니다. Func<> 는 공변(out)이면서 반제약을 달았고, Span<> 자신의 T 는 None — 그래서 Span<Span<int>> 는 여전히 CS9244 입니다. 제안서는 이것을 이 제안의 "beyond the scope" 로 남겼습니다.

실행 검증

Func 와 Action 이 Span 을 받는다 — 그리고 C# 12 의 거절

C# 10 의 람다 제안서는 "if ref struct types are allowed type arguments" 이면 더 많은 서명이 Action<>·Func<> 에 묶일 수 있다고 미뤄 두었습니다. 이 제안서가 그 문장을 인용하고, 반제약이 붙은 Action<>·Func<> 가 "will be used in more scenarios involving ref struct types" 라고 적습니다.

C# 12.0 의 거절이 9행과 12행 — Func<ReadOnlySpan<char>, int> 와 Action<Span<int>> 를 적은 자리입니다. 반제약을 단 것은 .NET 의 Func 인데, 그것을 Span 으로 채우는 쪽이 C# 13 의 기능이기 때문입니다. 그런데 18행 var len = (Span<int> s) => … 은 거절 목록에 없습니다 — 다음 장.

실행 검증

함정 — 람다의 자연 형식은 언어 버전과 상관없이 Func 가 된다

C# 10 의 규칙: 매개변수 형식이 "not valid type arguments" 이면 컴파일러가 합성한 익명 대리자 형식이 됩니다. C# 13 의 제안서: "If target runtime supports allows ref struct constraints, generic anonymous delegate types will include allows ref struct constraint for their type parameters." — 조건이 언어 버전이 아니라 대상 런타임입니다.

세 버전 모두 Func`2 입니다. 같은 컴파일러가 C# 12.0 에서 Func<Span<int>, int> 를 손으로 적으면 거절하고 (앞 장), 추론해서 고른 Func<Span<int>, int> 는 받습니다. 자연 형식(11부)을 고르는 규칙이 .NET 10 의 Func 를 보고 판단한다는 뜻입니다 — 언어 버전 짝으로는 보이지 않는 변화입니다.

실행 검증

왜 "allows" 인가 — 버린 문법과 자동 적용

제안서의 결정: "use where T: allows ref struct". 다른 제약은 받을 형식을 줄이는데 이것은 늘리므로 "a new syntax prefix, allows, to make that clearer" 입니다.

검토한 길결론
~ref struct · include ref struct · 따로 쓰는 allow T : ref struct 절"where T: allows ref struct syntax had a slightly stronger preference in LDM discussions"
대리자·인터페이스에 컴파일러가 알아서 붙이기"do not auto-apply" — 대상 프레임워크마다 결과가 갈리고, 인터페이스에 기본 구현 하나를 더하면 멀리서 깨진다
라이브러리가 나중에 떼기"Removing the allows ref struct anti-constraint is always a breaking change: source and binary."
공변·반변과 섞기"no new issues" — 보통 구조체 인수가 변성을 없애듯 ref struct 도 그렇다

그래서 반제약은 BCL 이 한 형식씩 손으로 단 것입니다. 무엇이 달렸는지는 다음 장에서 셉니다.

문서 근거

같이 온 런타임 — .NET 10 에서 반제약을 단 제네릭

제안서는 구현이 없는 정의 — 대리자, 인터페이스, abstract 메서드 — 에는 반제약을 "safely" 붙일 수 있다고 적습니다. .NET 10 의 System.Private.CoreLib 에서 최상위 공개 형식과 그 메서드를 리플렉션으로 셉니다.

형식 50개 중 40개가 Action·Func 가족 같은 대리자이고, 나머지는 IEnumerable<T>·IEquatable<T>· IComparer<T> 같은 인터페이스입니다 — 제안서의 "safe" 목록 그대로입니다. List<T> 같은 구현 형식은 없습니다(앞의 함정). 메서드 51개 중 35개가 Unsafe 입니다. 중첩 형식은 세지 않았습니다.

실행 검증

인터페이스를 구현하는 ref struct (ref struct interfaces) C# 13.0

왜 — whats-new: "Before C# 13, ref struct types weren't allowed to implement interfaces. Beginning with C# 13, they can." 제안서는 이 기능이 "only useful when combined with the ability for ref struct to participate in generic arguments" 라고 적습니다 — 인터페이스로 바꿀 수 없으니 제약을 거쳐서만 부를 수 있기 때문입니다.

Vowels 하나가 문자열을 복사하지 않는 SpanText 와 보통 클래스 StringText 를 다 받습니다 — 동기 절이 말한 "same implementation" 의 중복이 사라졌습니다. C# 12.0 은 두 게이트를 따로 짚습니다: 9행의 인터페이스 목록(ref struct interfaces)과 26행의 반제약.

실행 검증

인터페이스 형식으로는 바꿀 수 없다 — 그것이 박싱이므로

제안서: 인터페이스를 구현해도 "it cannot be directly cast to it as that represents a boxing action". whats-new 는 명시적 구현 멤버가 "can be accessed only through a type parameter where that type parameter allows ref struct" 라고 덧붙입니다.

암시적 변환은 CS0029, 명시적 캐스트도 CS0030 입니다. -define:DIRECT(t.Name())는 오류 줄이 200칸을 넘어 싣지 못했고, 실험 묶음이 CS1061 로 거절되는 것만 확인합니다 — 명시적 구현은 Tag 의 멤버로 보이지 않습니다. 남은 길은 Call<T> 하나입니다.

실행 검증

함정 — 구현했는데 t is IName 은 False

형식 검사 is 는 변환이 있는지를 묻습니다. ref struct 에서 인터페이스로 가는 변환은 박싱이라 없으므로(앞 장) 컴파일러는 이 식을 상수 false 로 봅니다.

오류가 아니라 경고 CS0184("never of the provided type")이고 프로그램은 False 를 찍습니다. Tag 는 분명히 IName 을 구현했는데도요. 같은 코드가 보통 struct 였다면 박싱 뒤 True 였을 것입니다 — "구현한다" 와 "그 형식으로 볼 수 있다" 가 ref struct 에서는 갈립니다. 경고를 끄는 프로젝트에서는 조용한 버그가 됩니다.

실행 검증

제약을 거친 호출은 박싱하지 않는다 — 할당 바이트로 보기

보통 구조체도 인터페이스 매개변수로 넘기면 박싱됩니다. 제네릭 제약을 거친 호출은 박싱 없이 구조체의 메서드를 바로 부릅니다 — 구조체가 그 메서드를 제 손으로 구현했다면(9부). ref struct 는 박싱이 아예 불가능하므로 이 길만 열려 있습니다.

IValue 매개변수로 넘긴 Num 은 부를 때마다 24바이트 박스를 만들어 1000번에 24000바이트입니다. 같은 Num 을 ViaGeneric 으로 넘기면 0, ref struct Ref 도 0 입니다. 바이트 수는 이 기계의 .NET 10 런타임에서 잰 것이고, 덱이 주장하는 것은 0 과 0 이 아닌 것의 차이입니다.

실행 검증

IEquatable<자기 자신> — ref struct 가 형식 인수이면서 구현자

.NET 10 의 IEquatable<T> 는 반제약을 달았습니다(런타임 장). 그러면 ref struct 가 자기 자신을 형식 인수로 하는 인터페이스를 구현할 수 있고, where T : IEquatable<T> 꼴의 오래된 제네릭 관용구에 그대로 들어갑니다.

"Span" 과 "span" 은 대소문자를 무시해 같고, "Spam" 과는 다릅니다. 같은 Same 이 int 에도 쓰입니다. 두 Word 는 한 문자열의 서로 다른 조각을 가리킬 뿐 복사본이 없습니다.

실행 검증

기본 구현이 있어도 ref struct 는 전부 구현해야 한다

제안서: 기본 인터페이스 메서드(9부)의 몸체 안에서 this 는 인터페이스 형식이라 "there are no protections against the default implementation boxing the this member". 그래서 "a ref struct will be forced to implement all members of an interface, even if they have default implementations."

클래스 C 는 기본 구현 "hello class" 를 쓰고, R 은 자기 구현 "hi ref" 를 씁니다. 빼먹으면 CS9245 — 기본 구현이 있는 Hello 가 "cannot implement … for ref struct" 입니다. 9부에서 기본 구현을 쓰는 구조체는 제네릭으로 불러도 호출마다 24바이트 상자를 만들었습니다 — ref struct 에는 그 상자가 허용되지 않으니 기본 구현을 쓸 길이 없습니다.

실행 검증

sealed 인터페이스 멤버는 T 로 부를 수 없다 — 런타임 예외를 막으려고

제안서: 런타임은 ref struct 에서 기본 인터페이스 멤버가 불리면 예외를 던지도록 바뀌고, 그것을 컴파일 때 막으려고 "the compiler will report an error for an invocation of a non-virtual instance method (or property) on a type parameter that allows ref struct".

sealed 멤버는 구현 형식이 대신할 수 없으므로 ref struct 에서는 반드시 기본 몸체가 돌고, 그 몸체는 this 를 박싱할 수 있습니다 — CS9246(코드는 앞 장). 막지 못하는 경우도 제안서에 적혀 있습니다: 인터페이스에 기본 구현 멤버를 나중에 더하고, 다시 컴파일하지 않은 다른 어셈블리의 ref struct 를 제네릭으로 부르면 그때 런타임 예외입니다. csrun 은 어셈블리 하나만 만들므로 이 덱은 그 예외를 보이지 못합니다.

실행 검증

using 과 foreach 가 인터페이스 구현을 쓴다

제안서: using 은 자원이 ref struct 이면 IDisposable 구현을 쓰고(C# 8 의 패턴 Dispose 가 없을 때), allows ref struct 인 T 도 유효 인터페이스에 IDisposable 이 있으면 됩니다. 다만 인터페이스는 ref struct 가 아니므로 "a pattern Dispose method will not be recognized on a type parameter that allows ref struct". foreach 도 ref struct 의 IEnumerable<T> 구현을 씁니다.

명시적으로만 구현한 Dispose 를 using 이 두 번 다 찾았습니다. IClose 에도 Dispose() 가 있지만 T 에 대해서는 패턴으로 찾지 않아 CS1674 입니다. Three 는 열거자를 클래스(List 의 것)로 돌려주므로 ref struct 를 돌면서도 열거자는 힙에 있습니다.

실행 검증

함정 — 같은 값, 다른 Dispose: 패턴이 먼저다

제안서: "preference is given to a Dispose method that implements the pattern, and only if one is not found, IDisposable implementation is used." 그런데 제네릭 T 에서는 패턴을 찾지 않습니다.

직접 쓴 using 은 공개 Dispose() 를, 제네릭 Use<T> 안의 using 은 IDisposable.Dispose 를 부릅니다. 두 메서드가 다른 일을 하면 같은 값이 어디서 쓰이느냐에 따라 정리 방식이 바뀝니다 — 둘을 같게 두는 것이 안전합니다.

실행 검증

인터페이스 멤버의 [UnscopedRef] — 받는 쪽을 가리킬 수 있다는 표시

제안서: 인터페이스가 ref struct 의 수명 문제까지 표현하도록 "the language will allow [UnscopedRef] to appear on interface methods and properties". 구현 쪽은 이 특성을 생략해도 되지만 "a member with [UnscopedRef] may not be used to implement a member that lacks the attribute". 특성 자체는 C# 11 의 것입니다(12부).

Target 은 Cell 밖의 x 를 가리키므로 돌려줄 수 있고, Pick(...) = 50 이 x 를 바꿉니다. Own 은 받는 쪽(매개변수 t) 안을 가리킬 수 있다고 인터페이스가 밝혔으므로 CS8166 입니다. 인터페이스에 없는 특성을 구현 쪽에 붙이면 CS9102 — 부르는 쪽이 인터페이스만 보고 내린 판단이 깨지기 때문입니다.

실행 검증

같이 온 런타임 — .NET 10 의 열거자들이 IEnumerator<T> 를 구현한다

whats-new 가 말한 간접 혜택("Span<T> and ReadOnlySpan<T> gain more functionality")이 어디에 있는지, System.Private.CoreLib 의 공개 ref struct 중 인터페이스를 구현한 것을 셉니다.

공개 ref struct 25개 중 다섯 — 모두 열거자이고 IEnumerator<T> 를 구현합니다. Span<int> 자신은 인터페이스가 0개입니다. 그래서 Sum<E> 하나가 Span<int>.Enumerator 와 List<int>.Enumerator 를 다 받습니다. Span 을 IEnumerable<T> 로 넘기는 일은 여전히 안 됩니다 — 그것은 박싱입니다.

실행 검증

async·반복기 안의 ref 와 Span 지역 변수 (ref in async) C# 13.0

왜 — 제안서: ref 지역 변수와 ref struct 지역 변수는 yield·await 를 넘어 쓰이지 않으면 "they do not need to be hoisted" 이므로 막을 까닭이 없습니다. whats-new: C# 13 에서 async 메서드는 ref 지역 변수와 "local variables of a ref struct type" 을 선언할 수 있고, 다만 "those variables can't be accessed across an await boundary."

stackalloc 으로 만든 스택 메모리를 async 메서드 안에서 쓰고, await 앞에서 값만 int 로 꺼냈습니다. C# 12.0 의 거절은 async 쪽 11–13행 셋 — foreach 가 만드는 Span 열거자까지 짚습니다. 그런데 반복기의 24행은 거절 목록에 없습니다(다음 장). ref 지역 변수 쪽은 8부, async 의 Span 블록은 6부에서 짧게 봤습니다.

실행 검증

무엇이 정말 막혀 있었나 — 반복기의 Span 지역 변수는 이미 됐다

whats-new 는 "Before C# 13, iterator methods … and async methods couldn't declare local ref variables" 라고 적습니다. 세 가지를 따로 떼어 C# 12.0 으로 컴파일해 봤습니다.

반복기 안의 ReadOnlySpan<char> 지역 변수는 C# 12.0 에서도 컴파일되고 돌아갑니다. 막혀 있던 것은 반복기의 ref 지역 변수와 async 메서드의 ref struct 지역 변수였습니다 — whats-new 의 문장대로입니다. 그러니 C# 13 이 반복기에 새로 연 것은 ref 지역 변수와 unsafe 블록이고, async 에는 둘 다입니다. 옛 컴파일러가 실제로 어땠는지는 이 기계에서 확인할 수 없습니다.

실행 검증

await·yield 를 넘으면 — 그 순간 "할당되지 않은" 변수가 된다

제안서의 명세 문장: await 식이나 yield return 문 뒤에서는 "all ref local variables and variables of a ref struct type in scope are considered definitely unassigned". 이 오류는 다른 ref 안전성 오류와 달리 unsafe 문맥에서도 경고로 낮춰지지 않습니다.

Span 은 CS4007("cannot be preserved across 'await' or 'yield' boundary"), ref 지역 변수는 CS9217 입니다. 둘 다 문장에 await 와 yield 가 함께 들어 있습니다 — 두 상태 기계가 같은 규칙을 쓴다는 뜻이고, 제안서의 첫 줄 "Unify behavior between iterators and async methods" 그대로입니다.

실행 검증

함정 — Span 을 foreach 하며 yield 하기

보이는 지역 변수는 하나도 yield 를 넘지 않는 것 같아도, foreach 는 컬렉션과 열거자를 숨은 지역 변수로 둡니다. 그 숨은 변수가 루프 몸체의 yield return 을 넘습니다 — 명세의 "even implicitly in compiler-synthesized code" 입니다.

오류는 10행의 foreach 자체에 붙고 형식은 ReadOnlySpan<char> 입니다. 고치는 길은 yield 를 넘어 살아남는 것을 Span 이 아닌 것 — 문자열과 인덱스 — 으로 두는 것입니다. 인덱스마다 새 Span 을 만들어도 그 Span 은 다음 yield 전에 죽습니다.

실행 검증

여전히 안 되는 것 — Span 매개변수, 그런데 반복기는 조금 다르다

C# 13 이 연 것은 지역 변수입니다. 매개변수는 그대로 막혀 있고, 제안서는 반복기의 금지 목록에 포인터 형식까지 더했습니다 — "or an parameter of a ref struct type or a pointer type".

async 는 선언에서 CS4012 입니다. 반복기는 선언이 아니라 쓰는 자리에서 CS4007("cannot be preserved across … boundary")이고, 쓰지 않는 Span 매개변수는 컴파일되어 돕니다 — 명세 문장(매개변수 목록 자체가 오류)과 다릅니다. 반복기 몸체는 첫 MoveNext 에서야 돌기 시작하므로 몸체에서 쓰는 매개변수는 그 경계를 넘는 셈이고, 컴파일러는 그 쓰임만 짚습니다. 이 차이는 Roslyn 의 표준 이탈 문서에 없습니다(2026-10 기준).

실행 검증

await 사이에서 되는 것들 — ref foreach, ref struct 의 using, Lock

제안서: 명세 변경만으로 "more constructs can work" — await 와 yield 가 없는 구간 안의 ref struct using, ref struct 열거자의 foreach, foreach (ref …), 그리고 lock (new System.Threading.Lock()).

ref 반복 변수로 배열을 열 배 하고, ref struct Scope 를 정리하고, Lock 으로 잠근 뒤 61 을 돌려줍니다. Lock 의 lock 은 ref struct Lock.Scope 를 쓰는 using 이라 async 안에서는 C# 13 이 필요합니다(3장). C# 12.0 에서 22행은 'Lock object' 게이트가 먼저 짚습니다.

실행 검증

상태 기계에 올라가지 않는다 — 필드를 들여다보기

컴파일러는 async 메서드를 상태 기계 형식으로 바꾸고, await 를 넘는 지역 변수를 그 필드로 끌어올립니다(6부). 제안서의 핵심은 넘지 않는 ref·ref struct 지역 변수는 "do not need to be hoisted" 라는 것입니다.

필드에는 keep·first·text 가 있고 s 는 없습니다 — Span 은 스택에만 있다가 await 전에 죽습니다. 디버그 IL 에서는 상태 기계가 class, -optimize+ 에서는 struct 입니다(6부와 같다). 지역 변수 번호(5__1·5__2)는 빌드마다 달라 기대면 안 됩니다.

실행 검증

반복기 안의 unsafe 블록 — 단 yield 는 그 밖에서

whats-new: "C# 13 allows unsafe contexts in iterator methods. However, all yield return and yield break statements must be in safe contexts." 제안서는 반복기에서 지역 변수·매개변수의 주소를 얻는 것도 오류로 정했습니다 — 상태 기계의 필드로 옮겨질 수 있는 변수이기 때문입니다.

C# 12.0 은 unsafe 블록과 그 안의 포인터 셋을 모두 게이트로 짚습니다. C# 13.0 안의 규칙은 둘 — CS9238(unsafe 블록 안의 yield return)과 CS9239(반복기에서 & 지역 변수). fixed 로 고정한 배열 원소는 지역 변수가 아니라 됩니다.

실행 검증

async 쪽 unsafe — 원래 됐고, 이제 명세가 await 를 막는다

제안서: async 메서드의 unsafe 블록은 "the spec has never disallowed" 이므로 바꿀 것이 없고, 대신 명세에 "It is a compile-time error for an unsafe context … to contain an await expression" 을 더합니다. async 에서 지역 변수의 주소를 얻는 것은 C# 12 의 경고 웨이브 경고입니다.

같은 프로그램이 C# 7.3 에서도 돕니다 — async 의 unsafe 블록은 이 기능과 무관합니다. unsafe 안의 await 는 CS4004. &v 는 기본 수준(4)에서 조용하고 -warn:8 에서 CS9123 경고입니다 — 반복기의 같은 코드가 오류(CS9239)인 것과 다릅니다. 제안서는 async 쪽을 오류로 올리는 것이 "a breaking change" 라 남겨 두었습니다.

실행 검증

unsafe 반복기 — 서명은 unsafe, 몸체는 safe

제안서: 반복기 선언에 unsafe 를 달면 "the signature is in an unsafe scope but the iterator block used to implement that iterator still defines a safe scope", 그리고 "in C# 12 it is an error to have an iterator method marked with the unsafe modifier, but that is allowed in C# 13".

포인터 배열 매개변수는 서명이라 받지만, 몸체에서 그 포인터를 따라가면 CS0214("only be used in an unsafe context")입니다 — 메서드에 unsafe 를 달았는데도요. 몸체에서 포인터를 쓰려면 앞 장처럼 안에 unsafe 블록을 다시 엽니다.

실행 검증

깨지는 변경 — 반복기가 안전 문맥을 연다

Roslyn 문서: 명세는 반복기가 안전 문맥을 연다고 했지만 "Roslyn does not implement that in C# 12 and lower" 였고, C# 13 에서 바로잡았습니다. 그래서 unsafe 클래스 안 반복기의 지역 함수가 물려받던 unsafe 문맥을 잃습니다. "You can work around the break simply by adding the unsafe modifier to the local function."

같은 소스가 언어 버전만으로 갈립니다 — 언어 버전에 묶인 동작(0부의 나)입니다. C# 13.0 의 오류는 게이트 문장이 아니라 CS0214 셋이라 원인을 짐작하기 어렵습니다. 고친 꼴은 C# 12.0 에서도 컴파일됩니다.

실행 검증

반대쪽 — 같은 자리의 await 는 이제 된다

제안서의 깨지는 변경 예제에는 짝이 있습니다. unsafe 클래스 안 반복기의 async 지역 함수에서 await Task.Yield(); 는 "error in C# 12, allowed in C# 13" — 지역 함수가 unsafe 문맥이 아니게 되었기 때문입니다.

C# 12.0 은 CS4004("Cannot await in an unsafe context") — 지역 함수가 클래스의 unsafe 를 물려받았다는 증거입니다. 한 가지 고침이 한쪽 코드는 깨고 다른 쪽 코드는 살렸습니다.

실행 검증

반복기의 lock 안에서 yield — 제안서의 경고는 없었다

제안서 요약의 둘째 줄: "Warn about yield inside lock." 대안 절은 이것을 오류나 경고 웨이브로 만드는 것이 "a breaking change" 라고 적고, Lock 객체의 lock 은 ref struct 를 쓰는 using 이라 오류가 난다고 적습니다.

-warn:9999 에서도 경고가 없고, 이 SDK 의 CSharpResources.resx 에도 그런 문장이 없습니다. 실행은 위험을 그대로 보여 줍니다 — 값을 받은 바깥 루프에서 잠금이 아직 잡혀 있습니다(held: True). Lock 으로 바꾸면 Lock.Scope 가 yield 를 넘는다는 CS4007 로 막힙니다(3장). 2026-10 기준.

제안서: 세미콜론 접근자 꼴을 정의 조각에 쓰기로 했으므로 "a partial property cannot be automatically implemented". 컴파일러가 선언 하나만 보고 정의인지 구현인지 알 수 있어야 하기 때문입니다 — 같은 선언을 두 번 써서 자동 속성을 만드는 길도 그래서 막았습니다.

실행 검증

서명 맞추기 — 접근성·init 은 오류, 매개변수 이름은 경고

제안서: 두 조각은 같은 한정자를 가져야 하고, 런타임에 의미 있는 형식 차이는 오류, 나머지 구문 차이는 경고입니다. 매개변수 이름이 다르면 경고이고 "The parameter names from the definition part are used at use sites and in emit." partial 메서드와 달리 불일치 진단이 "not held behind a warning wave" 입니다.

접근성 차이는 partial 메서드와 같은 CS8799, init 차이는 CS9254 입니다. 이름이 다르면 경고 CS9256 뿐이고, c[x: 21] 의 명명 인수와 리플렉션이 보는 이름은 정의 조각의 x 입니다. 제안서의 예시 문장은 "Partial property declarations …" 인데 이 컴파일러는 "Partial member declarations …" 라고 적습니다.

특성 합치기 — 두 조각의 특성이 한 멤버에 모인다

제안서: partial 메서드처럼 "the attributes in the resulting property are the combined attributes of the parts are concatenated in an unspecified order, and duplicates are not removed." 인덱서의 매개변수 특성도 합쳐집니다.

속성, 접근자, 매개변수 모두 def 와 impl 이 함께 있습니다. 차례는 명세가 정하지 않으므로 예제가 정렬해서 찍습니다. 형식의 속성은 P 와 Item 둘 — 조각이 둘이어도 메타데이터의 속성은 하나입니다. 생성기가 사용자의 정의 조각에 붙은 특성을 읽고 구현 조각을 쓰는 구성이 그래서 성립합니다.

문서 주석 — 둘 다 있으면 구현 조각의 것만 남는다

제안서: 주석이 한쪽에만 있으면 그것을 쓰고, "When doc comments are present on both parts, all the doc comments on the definition part are dropped, and only the doc comments on the implementation part are used." 예제는 제안서의 것 그대로입니다.

P:C.Prop 에는 "Implementation part comment" 하나뿐이고, 정의 조각의 <returns> 도 함께 사라졌습니다 — 한 줄씩 합치는 것이 아니라 통째로 버립니다. 생성기가 구현 조각에 주석을 달면 사람이 정의 조각에 쓴 주석은 문서 파일에 남지 않는다는 뜻입니다.

같이 온 런타임 — [GeneratedRegex] 가 속성에도 붙는다

.NET 의 정규식 소스 생성기는 partial 메서드에 붙는 특성이었습니다(10부). .NET 10 의 특성 정의가 어디에 붙을 수 있다고 적는지 리플렉션으로 읽습니다.

GeneratedRegexAttribute 는 Method, Property, P/Invoke 생성기의 LibraryImportAttribute 는 아직 Method 뿐입니다. csrun 에는 생성기가 없어서 특성을 단 partial 속성은 구현 조각이 없다는 CS9248 로 끝납니다 — 실제 빌드에서는 생성기가 그 조각을 씁니다.

인터페이스의 partial 속성 — 컴파일러가 바꾼 기본값

Roslyn 문서(.NET 10): partial 인터페이스 속성·이벤트가 비 partial 멤버와 달리 암시적으로 virtual·public 이 아니던 "inconsistency" 를 고쳤고, 예제의 출력이 "wrote 1 previously, writes 2 now" 입니다. partial 인터페이스 메서드는 더 큰 깨짐을 피하려 그대로 둡니다.

P 는 가상이라 C 의 2, M 은 비가상이라 인터페이스의 1 입니다. C# 13.0 과 14.0 의 출력이 같습니다 — 이 고침은 언어 버전이 아니라 컴파일러(Visual Studio 2026 version 18.0 preview 1 부터)에 묶였으므로, 같은 C# 13 소스가 컴파일러를 올리면 2 를 냅니다. 옛 컴파일러의 1 은 이 기계에서 보일 수 없습니다.

뒤 버전 — C# 14 의 field 가 구현 조각을 줄인다

C# 14 의 field 제안서: 초기화자는 "Either declaring or implementing property locations can use an initializer, but not both", 그리고 자동 접근자는 "At least one implementing accessor must be manually implemented, but the other accessor can be automatically implemented." partial 속성 제안서가 "the field keyword makes things simple enough" 라고 미뤄 둔 그 길입니다.

Count 의 set 만 몸체를 주고 get 은 자동입니다. C# 13.0 은 'field keyword' 게이트와 초기화자의 CS8050 을 냅니다(선언 단계 오류라 몸체 안의 field 는 짚이지 않았습니다). 앞에서 거절된 ppbad 의 HALF 는 C# 14.0 에서 컴파일되고, get 도 field 를 쓰라는 경고 CS9266 이 붙습니다. field 자체는 이 부의 8장(미리 보기)과 15부의 몫입니다.

5장의 거절 모음

실험 묶음이 각 거절 캡처의 첫 진단 줄에서 뽑은 표입니다. 게이트는 둘 — C# 12.0 의 CS8703(한정자 'partial')과 C# 13.0 의 CS9260 ('field keyword')입니다. 나머지는 partial 속성 자체의 규칙으로, 조각의 개수(CS9248–CS9251)와 서명의 일치(CS8799·CS9254· CS9256)로 나뉩니다.

5장 퀴즈 — partial 속성

Q1. C# 13 에서 public partial int N { get; set; } 를 같은 형식 안에 두 번 쓰면 자동 속성 하나가 되나?

Q2. 정의 조각은 this[int x], 구현 조각은 this[int y] 일 때 명명 인수에는 어느 이름을 쓰나?

A1. 아니요. 세미콜론 접근자 꼴은 언제나 정의 조각이라 둘 다 정의가 되고 CS9250·CS9248 입니다(앞). A2. 선언은 경고 CS9256 과 함께 컴파일되지만, 쓰는 곳과 메타데이터의 이름은 정의 조각의 것입니다 — 예제에서 c[x: 21] 이 컴파일되고 리플렉션도 x 를 봤습니다. 명명 인수에는 x 를 씁니다(앞).
