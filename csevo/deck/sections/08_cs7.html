8부를 읽는 법

C# 7.0 을 소개한 글의 첫머리는 이 버전의 초점을 셋으로 적습니다. "C# 7.0 adds a number of new features and brings a focus on data consumption, code simplification and performance." 그리고 가장 큰 기능 둘로 튜플과 패턴 매칭을 꼽습니다.

이 부는 버전 넷을 다룹니다. C# 7.0 다음의 7.1·7.2·7.3 은 C# 의 첫 점 릴리스(point release)입니다. 버전 기록은 "C# started releasing point releases with C# 7.1" 이라고 적습니다.

  • 1장 — C# 7.0 개관. 게이트 열한 개, C# 6 에서 결과 둘을 돌려주던 네 길, 같이 온 System.ValueTuple.
  • 2장 — 튜플과 분해. 이름은 어디에 남고 어디서 사라지나, 고칠 수 있는 구조체, Deconstruct, 버리기 _.
  • 3장 — 패턴 매칭. is 와 switch 의 패턴, case 의 순서, null, 패턴 변수의 범위, 뒤 버전의 패턴들.
  • 4장 — out 변수와 지역 함수. 범위가 새는 곳, 람다와 다른 점, 반복기·async 의 즉시 검사.
  • 5장 — C# 7.0 의 나머지. ref 지역 변수와 반환, throw 식, 식 본문의 확장, 숫자 리터럴, 작업 같은 형식.
  • 6장 — C# 7.1. 언어 버전 고르기, default 리터럴, 튜플 이름 유추, 제네릭과 패턴.
  • 7장 — C# 7.2. in·ref readonly·readonly struct·ref struct 와 Span.
  • 8장 — C# 7.3. 튜플의 ==, ref 재할당, 새 제약, 식 변수를 쓸 수 있는 자리.
  • 9장 — 8부 정리.

원소 이름은 컴파일 시간에만 있다

whats-new: 원소 이름은 "exist only at compile time and aren't preserved, for example when inspecting the tuple using reflection at run time."

실행 검증

그래도 이름이 다른 어셈블리로 건너가는 길 — TupleElementNamesAttribute

이름이 컴파일 시간에만 있다면, 라이브러리의 메서드가 돌려주는 튜플의 이름을 호출하는 쪽 컴파일러는 어떻게 알까요? 컴파일러는 이름을 특성으로 메타데이터에 적어 둡니다.

겹친 튜플 (string name, (int x, int y) pos) 의 이름은 바깥 것부터 차례로 펼친 배열 name, pos, x, y 가 됩니다. 이름이 하나도 없으면 특성 자체가 붙지 않습니다. 앞 장의 리플렉션이 이름을 못 찾은 것은 값에는 이름이 없기 때문이고, 메서드 시그니처에는 이렇게 남습니다.

실행 검증

고칠 수 있는 구조체 — 복사의 함정

C# 7.0 소개 글: "Tuples are value types, and their elements are simply public, mutable fields."

함정 — List<T> 의 인덱서는 원소의 복사본을 돌려줍니다. 그 복사본의 필드를 고쳐 봐야 리스트에는 남지 않으므로 컴파일러가 CS1612 로 막습니다. 배열 원소는 변수라서 arr[0].x = 5 가 됩니다. 고칠 수 있는 구조체 모두의 규칙이고, 튜플도 예외가 아닙니다.
실행 검증

같음 — C# 7.3 전에는 Equals 로

소개 글: 튜플은 "value equality" 를 가져서, 원소가 모두 짝지어 같으면 두 튜플이 같고 해시 코드도 같습니다.

같음은 ValueTuple 이 구현한 Equals 가 맡습니다. 이름이 다른 b 와도 같고(이름은 형식이 아니므로), 상자에 넣은 object 로도 같습니다. 연산자 == 는 C# 7.0 에 없습니다 — 컴파일러가 "tuple equality" 라는 이름으로 7.3 을 요구합니다. 원소별로 == 를 펼치는 그 기능은 8장에서 봅니다.

실행 검증

여러 칸짜리 열쇠

소개 글: 값으로 같음을 따지므로 "if you need a dictionary with multiple keys, use a tuple as your key and everything works out right." 리스트에서 찾기도 마찬가지라고 합니다.

같은 열쇠 (1, 'A') 에 두 번 넣으면 덮어씁니다(개수 2). C# 6 이라면 열쇠 전용 구조체를 만들고 Equals 와 GetHashCode 를 손으로 써야 했던 자리입니다. 사전을 차례로 찍지 않고 열쇠로만 찾은 것은, 해시 순서에 기대지 않기 위해서입니다.

실행 검증

이름이 달라도 자리로 바뀐다

소개 글: "as long as the individual elements are assignable, tuple types convert freely to other tuple types" — 이름과 상관없이.

함정 — 둘째 줄이 height=1920 을 찍습니다. (int height, int width) 로 받으면 첫 원소(너비)가 height 라는 이름을 얻습니다. 변환은 자리로 이루어지고 이름은 보지 않으며, 이 경우에는 경고도 없습니다.
실행 검증

리터럴의 이름이 버려질 때 — CS8123

이름을 붙인 리터럴을 다른 이름의 형식에 넣으면 컴파일러가 경고합니다. 미리보기 글은 이것을 "accidentally swapping the names of elements" 같은 흔한 실수를 잡는 제한이라고 소개했습니다.

경고는 리터럴 원소마다 하나씩, 넷입니다. 그래도 컴파일은 되고 값은 자리대로 들어가 width=1080 이 찍힙니다. 앞 장의 Size() 처럼 이름 붙은 변수나 반환 값을 바꿔 받을 때는 경고가 없고, 리터럴에 직접 쓴 이름만 검사합니다.

실행 검증

형식이 없는 원소 — 튜플 리터럴의 대상 형식

튜플 리터럴 (null, 1) 의 첫 원소에는 형식이 없습니다. 받을 형식이 정해져 있으면 원소마다 그 형식으로 바뀌고, var 처럼 받을 형식이 없으면 리터럴 자체의 형식을 정할 수 없습니다.

리터럴의 정수 1, 2 가 long·double 원소로 바로 들어가는 것도 원소별 대상 형식 덕입니다. 거절 문장은 리터럴의 모양을 (<null>, int), (lambda expression, int) 로 보여 줍니다 — 원소 하나라도 형식이 없으면 튜플 전체에 자연 형식이 없습니다.

실행 검증

object 와 dynamic 을 거치면 이름이 없다

이름은 시그니처의 특성과 컴파일러의 기억에만 있으므로, 정적 형식을 잃는 길을 지나면 사라집니다.

상자에서 꺼낼 때 이름을 다시 적으면 이름이 돌아옵니다 — 원래 이름과 같을 필요도 없습니다. dynamic 의 바인더는 실행 시간 형식 ValueTuple<string,int> 만 보므로 d.age 를 찾지 못하고, d.Item2 는 찾습니다.

형식 인수 속의 이름

제네릭 형식 인수 자리의 튜플도 이름을 가집니다. 이름은 형식 유추를 따라 흘러갑니다.

First() 의 T 도, 내 메서드 Id<T> 의 유추된 T 도 이름을 지닙니다. Select 안의 (who: p.name, p.age) 는 첫 원소에만 이름을 주었고, 둘째는 C# 7.0 에서 Item2 입니다 — p.age 에서 이름 age 를 유추하는 것은 C# 7.1 의 기능입니다(6장). 마지막 줄의 실행 시간 형식 인수에는 이름이 없습니다.

패턴 매칭 — is 의 형식 패턴 C# 7.0

왜 — 소개 글: 패턴은 "syntactic elements that can test that a value has a certain 'shape', and extract information from the value when it does." C# 7.0 은 패턴 셋(상수·형식·var)을 들이고, 기존 구문 둘 — is 와 switch 의 case — 에 붙였습니다.

명세의 이름으로는 선언 패턴(declaration pattern)입니다 — 형식을 검사하고, 맞으면 그 형식의 새 지역 변수에 값을 넣습니다. 변수 n 은 is 가 참일 때 "definitely assigned" 입니다.

실행 검증

as 와 null 검사를 한 식으로

C# 6 의 as 는 참조 형식에만 쓸 수 있어서, 값 형식은 is 로 검사하고 다시 캐스트해야 했습니다((int)o). 형식 패턴은 둘을 가리지 않고 한 번에 합니다.

상수 패턴 — 같음은 어떻게 따지나

제안서: 식과 상수가 둘 다 정수 형식이면 e == c 로, 아니면 object.Equals(e, c) 로 맞는지 봅니다. 상수는 리터럴, const, 열거형 상수, null 이 될 수 있습니다.

함정 — 상자에 든 5L 은 is 5 가 False 입니다. 상수 5 의 형식은 int 이고, 상자 속 long 은 int 가 아니기 때문입니다. 반면 정적 형식이 long 인 변수 n 은 정수끼리라 n == 5 로 비교되어 True 입니다.

C# 7.0 미리보기 글의 첫 패턴 예가 if (o is null) return; — "constant pattern null" — 이었습니다. == 를 엉터리로 정의한 클래스로 둘을 견줍니다.

w == null 은 사용자의 연산자를 불러 True 라는 거짓말을 듣습니다. w is null 은 연산자를 부르지 않고 참조가 null 인지만 봅니다 — (object)w == null 과 같은 답입니다. 사용자 정의 연산자가 있는 형식에서 "정말 null 인가" 를 물을 때 쓰는 까닭입니다.

실행 검증

제안서: 식은 var 패턴에 "always" 맞습니다. 새 변수의 형식은 식의 정적 형식입니다.

함정 — o is object 는 null 이면 False 지만 o is var x 는 null 이어도 True 입니다. var 패턴은 검사가 아니라 이름 붙이기입니다. 그래서 case var other: 는 null 까지 받는 "그 밖의 모든 것" 이 됩니다.

4장 퀴즈 — out 변수와 지역 함수

Q. if (!int.TryParse(s, out var n)) Console.WriteLine(n); 은 컴파일됩니까? if (!(o is int m)) Console.WriteLine(m); 은요? 그리고 인수를 검사하는 반복기 메서드에서 검사가 호출하는 순간에 돌게 하려면 어떻게 나눕니까?

A. 첫째는 됩니다 — out 인수는 메서드가 돌아오면 늘 대입되어 있으므로 실패한 가지에서도 n 이 확정 대입입니다 (scope). 둘째는 CS0165 입니다 — 패턴 변수는 맞았을 때만 대입됩니다. 반복기는 검사하는 바깥 메서드(반복기가 아님)와 yield 를 가진 지역 함수로 나누고, 바깥 메서드가 지역 함수의 결과를 돌려주게 합니다(iter).
