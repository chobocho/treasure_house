0부는 게이트 수만 셌습니다(0부). 여기서는 덱이 쓴 기능 행과 나란히 둡니다. 마지막 두 칸이 모든 줄에서 같습니다 — 컴파일러가 언어 버전으로 거절하는 기능은 하나도 빠짐없이 어느 부의 기능 행이 다뤘다는 뜻입니다.

실행 검증

표를 읽는 법 — 행과 게이트가 어긋나는 곳

  • C# 1.0 — 기능 행은 가장 많고 게이트는 하나입니다. 모든 것이 C# 1 의 문법이라 거절할 이전 버전이 없습니다. 남은 하나는 특성 대상 module 이고, 3장 사다리의 첫 칸이 됩니다.
  • C# 1.2 · 5.0 — 게이트가 0 과 1 입니다. 바뀐 것이 문법이 아니라 의미였습니다(0부).
  • 게이트 행 > 다룬 게이트 — C# 7.2 와 8.0 은 행 여럿이 게이트 하나를 나눠 씁니다. 한 기능을 여러 장으로 풀어 쓴 곳입니다.
  • 기능 행 > 게이트 행 — 남는 행은 게이트가 없는 것들입니다. 의미의 변화, 런타임과 라이브러리, 컴파일러의 동작, 깨지는 변경 — 다음 장의 갈래가 그것을 나눕니다(2장).

네 갈래

언어 · 런타임과 라이브러리 · 도구 · 표준 — 서로 다른 박자로 움직인 넷

부마다 어느 갈래가 움직였나

수는 이 덱이 기능 목록에 올린 행의 수이지, 문서의 모든 줄이 아닙니다. 그래도 모양은 보입니다 — 어느 부에서나 언어가 가장 크고, 런타임 행은 드뭅니다. 컴파일러 행이 뒤로 갈수록 느는 것은 깨지는 변경과 경고 웨이브를 컴파일러 행으로 적었기 때문입니다.

실행 검증

언어 — 컴파일러가 버전으로 지키는 갈래

언어 갈래는 컴파일러 안에 있습니다. 새 문법은 MessageID.RequiredVersion() 의 한 줄로 언어 버전에 묶이고(0부), -langversion 을 내리면 "Feature 'X' is not available in C# N" 으로 거절됩니다. 이 덱이 옛 컴파일러 없이 '전과 후' 를 보일 수 있는 것은 이 갈래뿐입니다 — 3장이 그 거절을 한 표에 모읍니다.

그러나 언어는 라이브러리 없이 서지 못합니다. 관계 문서: "The compiler generates code that uses these required types and members for many different language features. For this reason, C# versions are supported only for the corresponding .NET version and newer." 그리고 마지막 문장: "C# compiler tools are now decoupled from the release cycle of the .NET libraries on supported platforms."

문서 근거

컴파일러가 끌어오는 형식 — 내 어셈블리의 형식 참조

관계 문서가 예로 든 것은 C# 7.0 의 System.ValueTuple, C# 8 의 System.Index·System.Range 입니다. 몇 줄짜리 프로그램이 컴파일된 뒤 무엇을 참조하는지, 자기 메타데이터의 형식 참조(TypeRef) 표를 읽어 찍습니다. 표를 읽는 코드가 쓰는 이름공간 넷은 빼고 찍습니다.

실행 검증

형식 참조 표 — 문법 한 줄마다 라이브러리 형식

소스에 이름이 없는 형식이 여럿입니다. System.ValueTuple`2 는 튜플, System.Index·System.Range 는 ^1·1.., AsyncTaskMethodBuilder·IAsyncStateMachine·TaskAwaiter 는 async 의 상태 기계(6부), DefaultInterpolatedStringHandler 는 보간 문자열(11부), RefSafetyRulesAttribute 는 C# 11 의 ref 안전 규칙 표시입니다(12부). 점으로 시작하는 두 줄은 중첩 형식이라 이름공간 칸이 비어 있습니다. MemoryExtensions·ReadOnlySpan`1 은 거르는 코드의 Skip.Contains(…) 에서 옵니다 — C# 14 에서는 배열의 Contains 가 스팬 판으로 묶입니다(15부).

그래서 — 언어 버전만 올려서는 안 되는 까닭이 여기 있습니다. 이 형식들이 없는 라이브러리를 대상으로 하면 같은 소스가 컴파일되지 않습니다. 3장의 TFM 기본값이 그 짝을 맞춥니다.

C# 8.0 의 블로그는 .NET Framework 의 런타임을 두고 "The need to keep the runtime stable has prevented us from implementing new language features in it for more than a decade." 라고 적었습니다. 런타임이 바뀌어야 했던 언어 기능은 덱 전체에 몇 개뿐이고, C# 2.0 다음은 .NET Core 이후에 몰려 있습니다.

문서 근거

메타데이터의 표시와 RuntimeFeature — 다섯 기능을 한 줄씩

둘째 칸은 리플렉션으로 본 표시입니다 — 인터페이스의 정적 추상 메서드, 몸체가 있어 abstract 가 아닌 인터페이스 메서드, PreserveBaseOverridesAttribute 가 붙은 재정의, by-ref 형식의 필드, AllowByRefLike 가 켜진 형식 매개변수. 기본 인터페이스 구현의 제안서: "Programs that take advantage of this feature cannot run on earlier versions of the platform." 그래서 컴파일러가 대상 라이브러리에 마지막 칸의 상수가 있는지 먼저 봅니다 — allows ref struct 의 제안서도 같은 방법을 적습니다.

컴파일러의 판과 언어의 판 — #error version

같은 제안서가 지나가며 적은 한 줄: "#error version: the version part is not in the spec, but Roslyn will report its version". 그 지시문 하나만 둔 파일을 컴파일합니다.

컴파일러의 판은 5.0.0-…(Roslyn 5)이고 언어의 판은 14.0 입니다. 언어 버전을 1 로 내려도 컴파일러는 그대로입니다 — -langversion 은 지금의 컴파일러에게 옛 문법만 받으라고 시키는 것이지 옛 컴파일러를 부르는 것이 아닙니다(0부).

실행 검증

표준 — ECMA-334 의 판과 C# 버전

ECMA 페이지는 Visual C# 버전마다 대응하는 표준을 적습니다. V3·V4 는 대응하는 표준이 없고, V5 부터는 표준이 C# 보다 다섯 해 이상 늦습니다. 2부 · 3부 · 6부가 판 하나씩을 봤습니다.

실행 검증

지금의 표준 — C# 7 과 C# 8 초안, 그리고 C# 14 컴파일러

표준 위원회(ECMA TC49-TG2)의 저장소는 가지마다 판을 둡니다: "The branch standard-v7 has the ECMA C# 7 standard text", "The branch draft-v8 has the evolving draft text for C# 8", "The branch draft-v9 has Draft PRs and Issues for C# 9".

이 덱이 C# 1–5 의 기능을 인용한 표준 초안은 머리말 첫 줄이 "This specification replaces ECMA-334:2023" 이고, 바뀐 것으로 비동기 스트림·nullable 참조 형식·범위와 인덱스 같은 C# 8.0 의 기능을 듭니다.

그래서 — 2026-10 기준 이 기계의 컴파일러는 C# 14 를, 마지막 ECMA 표준은 C# 7 을, 다음 판의 초안은 C# 8 을 다룹니다. 표준은 언어를 따라가며 적는 갈래입니다. C# 9 부터의 기능은 csharplang 의 제안서가 사실상의 명세라, 이 덱도 그것을 인용했습니다.
문서 근거

2장 퀴즈

Q1. 언어 버전만 C# 8.0 으로 올리고 대상 라이브러리는 그대로 두면, a[^1] 같은 코드가 왜 컴파일되지 않을 수 있습니까?

Q2. -langversion:1 로 컴파일할 때 쓰이는 컴파일러의 판은 무엇입니까?

Q3. 공변 반환·기본 인터페이스 구현·ref 필드의 공통점은?

A1. 컴파일러가 ^1 을 System.Index 로 바꾸는데, 그 형식이 대상 라이브러리에 있어야 하기 때문입니다(형식 참조 표).
A2. 지금의 컴파일러 그대로 — 5.0.0-…. 언어 버전은 받는 문법만 바꿉니다(#error version).
A3. 런타임이 바뀌어야 했던 기능입니다. 컴파일러는 RuntimeFeature 의 상수로 대상 런타임이 그것을 아는지 확인합니다(메타데이터의 표시).

3장

langversion 사다리

프로젝트가 언어 버전을 고르는 법 · 컴파일러가 받는 이름 · 게이트 열일곱 × 언어 버전 열일곱 · 버전을 올릴 때 조용히 바뀌는 것

기본 언어 버전은 대상 프레임워크가 정한다

버전 업데이트 문서: "The language version used to compile your app typically matches the runtime target framework moniker (TFM) referenced in your project." "This default behavior ensures maximum compatibility." 그 규칙을 문서 대신 SDK 에게 직접 묻습니다. 프로젝트 하나가 자기 자신을 TFM 열한 개로 다시 평가하며, LangVersion 을 비워 둔 채 SDK 가 채운 값을 찍습니다.

실행 검증

TFM 열한 개의 기본 언어 버전

  • .NET Framework 와 .NET Standard 2.0 → 7.3. 1장의 문장 "the most recent version supported for .NET Framework-based applications" 가 SDK 의 기본값으로 그대로 있습니다(1장).
  • .NET Standard 2.1 · .NET Core 3.x → 8.0 (9부).
  • net5.0 부터 net10.0 → .NET 판마다 한 버전씩, 1장의 짝 표와 같습니다(1장).
  • net11.0 → 14.0. 이 SDK 가 아는 가장 높은 판에서 멈춥니다 — 아직 없는 버전으로 올려 주지는 않습니다.

C# 의 기본값이 TFM 을 따르므로, 프로젝트의 TargetFramework 만 올리면 언어 버전도 함께 올라갑니다. 덱의 예제는 모두 net10.0 에 LangVersion 을 따로 적어 이 연결을 끊었습니다.

실행 검증

컴파일러가 받는 이름 — 숫자 열일곱과 이름 넷

목록은 8부에서 본 것과 같습니다. 컴파일러 소스의 구문 분석은 목록에 없는 철자도 받습니다 — 1·1.0·iso-1 은 모두 C# 1 입니다. 이름 넷 가운데 default·latest·latestmajor 는 이 컴파일러에서 C# 14 로 바뀌고, preview 는 바뀌지 않습니다.

실행 검증

이름이 가리키는 버전 — 컴파일러에게 직접 묻기

2장의 #error version 은 컴파일러가 실제로 쓰는 언어 버전도 찍습니다. 같은 파일을 이름마다 컴파일합니다.

셋은 (14.0) 을 달고, preview 만 그대로 preview 입니다. 소스에서도 Preview 는 C# 14 로 바꾸는 목록에 없습니다. 이 컴파일러에는 preview 로만 여는 기능이 하나도 없어서 결과는 14.0 과 같습니다 — 15부가 C# 15 의 문법으로 확인했습니다(15부). ISO-2 는 2 로 찍힙니다.

실행 검증

<LangVersion> 에서 -langversion 으로

MSBuild 프로젝트의 <LangVersion> 은 컴파일러의 -langversion: 이 됩니다. 이 덱의 csrun 은 MSBuild 없이 같은 일을 합니다 — ex.csproj 의 첫 <LangVersion> 을 읽어 플래그로 옮기고, 명령 줄의 플래그를 그 뒤에 붙입니다(0부).

그래서 이 덱의 캡처 첫 줄 csrun -langversion:7.3 은 csproj 의 값을 덮어쓴 것입니다. 같은 이유로 -langversion:? 를 덧붙이면 목록만 찍습니다(앞 장). 앞의 TFM 실험이 LangVersion 을 조건부로 둔 것도 이 순서 때문입니다 — 안쪽 평가에서만 비워 SDK 의 기본값을 봅니다.

실행 검증

사다리 — 버전마다 게이트 하나 (1/2)

파일 하나에 C# 1 부터 14 까지, 버전마다 그 버전의 게이트에 걸리는 문장 하나를 #if 기호(R1 … R14) 뒤에 둡니다. 기호를 다 끄면 아무 기능도 쓰지 않는 C# 1 프로그램입니다.

사다리 — 버전마다 게이트 하나 (2/2)

칸마다 고른 게이트: 1 module 특성 대상 · 2 제네릭 · 3 람다 · 4 명명 인수 · 5 async · 6 보간 문자열 · 7.0 튜플 · 7.1 default 리터럴 · 7.2 private protected · 7.3 튜플 == · 8.0 ??= · 9.0 new() · 10.0 파일 범위 namespace · 11.0 원시 문자열 · 12.0 컬렉션 식 · 13.0 Lock · 14.0 ?.=. 이름은 모두 data/langgates.tsv 의 게이트이고, 그 버전의 부에서 다룬 것입니다.

실행 검증

어떻게 판정했나 — 통과는 한꺼번에, 거절은 하나씩

  • 통과 칸 — 언어 버전 V 이하의 기호를 모두 켜고 한 번 컴파일합니다. 오류가 하나도 없으면 켠 기호 전부가 V 에서 통과입니다. 경고가 나면 그 줄의 기호를 △ 로 적습니다.
  • 거절 칸 — 기호 하나만 켜고 따로 컴파일합니다. 한 컴파일에 거절이 여럿이면 구문 분석의 거절이 의미 분석의 거절을 가리기 때문입니다 (15부에서 본 일). 오류가 그 기호의 줄에서 나야 ✗ 입니다.
  • 언어 버전 17 × 기호 17. 컴파일은 통과 판정 17번과 거절 칸 수만큼이고, 그 수는 다음 장 표의 제목에 실험 스크립트가 적습니다.
  • 판정이 어긋나면 표를 만들지 않고 멈춥니다 — 통과 컴파일에 오류가 있거나, 거절 칸의 오류가 다른 기호의 줄에서 나거나, 종료 코드가 1 이 아닐 때. 실행은 하지 않고 컴파일만 합니다.

판정 코드는 exps/p16.py 의 ladder() 입니다. 게이트 한 단계 아래의 거절 열여섯은 캡처로도 남겨 뒤의 장에 싣습니다.

오류 번호는 언어 버전이 정한다

같은 언어 버전에서는 어느 기능을 거절하든 첫 오류의 번호가 하나입니다 — CS8022 는 "C# 1 에는 없다", CS9260 은 "C# 13.0 에는 없다" 입니다. 번호가 버전마다 하나씩 새로 생겼으니, 번호의 차례가 곧 컴파일러가 버전을 하나씩 더해 온 차례입니다. 14부도 한 기능(?.=)을 버전마다 내려 같은 줄을 봤습니다(14부).

더 아래로 내리면 — 다른 기능이 먼저 걸린다

튜플 == 는 C# 7.0 보다 아래에서는 튜플 자체가 먼저 거절됩니다. ?.= 는 C# 6 보다 아래에서 ?. 가 먼저 걸립니다. 기능이 앞 버전의 기능 위에 서 있다는 것을 컴파일러의 첫 오류가 보여 줍니다. 그래서 한 칸의 게이트를 확인할 때는 한 단계 아래로만 내립니다.
