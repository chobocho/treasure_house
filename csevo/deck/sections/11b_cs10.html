왜 — string.Format 번역의 네 가지 비용

제안서는 보간 문자열이 대부분 string.Format 호출로 번역된다는 데서 시작해 그 번역이 비효율적인 까닭을 넷 꼽습니다.

제안서의 문장뜻
"It boxes any struct arguments"int 구멍 하나가 상자 하나
"It has to allocate an array for the arguments in most cases."인수 배열(object[]) 하나
"There is no opportunity to avoid instantiating the instance if it's not needed."로그 수준이 꺼져 있어도 문자열은 만들어진다
"It can never use Span or other ref struct types today"스택 버퍼에 바로 쓰는 길이 없다

발표 글은 같은 문제를 이렇게 요약합니다 — "This can lead to a lot of allocations – the boxing of arguments, allocation of an argument array, and of course the resulting string itself. Also, it leaves no wiggle room in the meaning of the actual interpolation." 그리고 해법을 "a library pattern that allows an API to “take over” the handling of an interpolated string argument expression" 이라 부릅니다.

7부에서 이미 두 가지를 봤습니다 — 지금의 SDK 는 -langversion:6 으로도 DefaultInterpolatedStringHandler 로 번역하고 (7부), 처리기는 구멍을 건너뛸 수 있습니다(7부의 예고). 이 장은 그 패턴을 한 걸음씩 엽니다.

문서 근거

보간 문자열 처리기 (interpolated string handler) C# 10.0

왜 — 제안서의 규칙: 보간 문자열이 인수로 넘어갈 때 매개변수 형식이 [InterpolatedStringHandler] 이고, 정수 둘(literalLength, formattedCount)을 받는 생성자와 인스턴스 AppendLiteral·AppendFormatted 가 있으면 "then we lower the interpolation using that, instead of into a traditional call to string.Format(formatStr, args)".

literalLength 8 은 {{n}}=· s=·! 를 이스케이프를 푼 뒤 센 글자 수입니다({n}= 은 넉 자). 너비와 서식이 있는 구멍은 이름 붙은 인수 alignment·format 으로 넘어오고, string 구멍은 비제네릭 판이 이깁니다. + 로 이은 두 보간 문자열은 처리기 하나로 합쳐집니다(new(2, 2)) — 제안서가 "an additive_expression composed entirely of interpolated_string_expressions" 를 함께 받기 때문입니다.

문서 근거

bool 을 돌려주는 Append — 중간에서 멈추기

제안서: Append… 가 bool 을 돌려주면 "the result is logically anded with all preceding Fax calls". false 가 나오면 뒤의 조각을 부르지 않습니다. 이 예제의 처리기는 정해진 길이를 넘으면 ... 를 붙이고 멈춥니다. 길이는 [InterpolatedStringHandlerArgument("max")] 로 같은 메서드의 다른 인수에서 받습니다.

길이 8 에서는 Next() 가 두 번만 돌았습니다. 둘째 구멍(500)은 평가된 뒤에 Add 가 false 를 돌려줬고, 그래서 셋째 구멍은 평가조차 되지 않았습니다. 멈추는 단위는 "조각" 입니다 — 이미 평가한 구멍은 되돌리지 않습니다.

실행 검증

처리기가 받는 인수와 평가 순서

제안서의 번역 순서: 보간 문자열보다 앞에 있는 인수를 먼저 차례대로 평가해 임시 변수에 두고, 생성자를 그 값들과 out bool 로 부른 뒤, true 일 때만 Append… 를 부릅니다. 받는 객체("")와 level 을 함께 받는 로거로 그 순서를 찍습니다.

받는 객체 → level → 처리기 생성자 → 구멍 → Write 차례입니다. level 1 에서는 구멍(Say("hole", 7))이 평가되지 않았는데도 Write 는 불립니다 — 메서드는 그대로 불리고, 빈 처리기를 받습니다. 이것이 7부에서 본 "구멍을 건너뛰는 로거" 의 뼈대입니다 (7부).

실행 검증

처리기 인수의 두 규칙 — 앞에 있을 것, 받는 객체가 있을 것

제안서의 최종 검증: 생성자에 넘길 인수가 보간 문자열보다 "lexically after" 에 있으면 오류이고, static 메서드에서 받는 객체("")를 요구해도 오류입니다.

이름 붙은 인수로 n 을 먼저 적으면 됩니다. 위치 인수로 Late($"{1}", 2) 라고 쓰면(-define:LATE) CS8950 으로 거절되고, #pragma 를 빼면(-define:WARN) 선언 쪽에 경고 CS8947 이 납니다. 두 문장 모두 한 줄이 200칸을 넘어 캡처로 싣지 못했습니다 — 실험 묶음(exps/p11b.py)이 매번 종료 코드와 번호만 확인합니다.

실행 검증

string 오버로드 옆의 처리기 — 상수면 string, 아니면 처리기

제안서는 "better conversion" 규칙에 첫 줄을 더했습니다 — 상수가 아닌 보간 문자열에서는 처리기로 가는 변환이 낫다. 그래서 "Log($"{1}") Calls Log(TraceLoggerParamsInterpolatedStringHandler p), because $"{1}" is not a constant expression".

함정 — C# 9.0 에서는 오류가 없습니다. 처리기 형식이 정의된 같은 소스가, 언어 버전만 내리면 조용히 모두 string 판을 부릅니다. 처리기 오버로드만 있을 때는 9.0 이 'interpolated string handlers' 로 거절하지만(앞), 다른 길이 있으면 그 길로 갑니다. 언어 버전에 묶인 동작(0부의 꼴 (나))입니다.
실행 검증

같이 온 런타임 — .NET 10 의 처리기 형식들 C# 10.0

발표 글: "when you see parameter types of the form SomethingInterpolatedStringHandler the API author has done some work behind the scenes to handle interpolated strings more appropriately for their purposes." 예로 StringBuilder.Append, Debug.Assert, String.Create() 를 듭니다. .NET 10 의 System.Private.CoreLib 을 리플렉션으로 훑었습니다.

처리기는 여섯이고 그중 다섯이 중첩 형식입니다 — 처리기는 그것을 받는 API 옆에 삽니다. 메서드 이름마다 처리기를 받는 판이 둘씩 있습니다. DefaultInterpolatedStringHandler 를 매개변수로 받는 공개 메서드는 없습니다 — 컴파일러가 string 이 되는 보간에 직접 씁니다(7부).

실행 검증

StringBuilder.Append($"…") — 중간 문자열 없이

발표 글: sb.Append($"Hello {args[0]}, how are you?") 는 예전엔 새로 만든 문자열로 Append(string) 을 불렀지만, 이제 Append(ref StringBuilder.AppendInterpolatedStringHandler) 가 이기고 조각들이 "individually appended to the StringBuilder" 된다. 같은 일을 네 가지로 하면서 호출 한 번의 할당 바이트를 셉니다.

처리기 판만 0 입니다. 문자열 지역 변수를 거치면 그 문자열(평균 39바이트)이 생기고, AppendFormat 은 int 를 상자에 담습니다(24바이트). 시간이 아니라 할당 바이트만 셌고, JIT 이 처음에 쓰는 덜 최적화된 코드가 섞이지 않도록 DOTNET_TieredCompilation=0 으로 돌렸습니다. 속도의 이득은 문서의 숫자로만 말할 수 있는데, 받아 둔 문서에는 숫자가 없습니다.

실행 검증

Debug.Assert — 조건이 참이면 메시지를 만들지 않는다

발표 글: Debug.Assert(condition, $"{SomethingExpensiveHappensHere()}") 는 대부분 조건이 참이라 메시지가 필요 없는데도 매번 계산됐다. 이제 "Debug.Assert now has an overload with a custom interpolated string builder, which ensures that the second argument isn't even evaluated unless the condition is false."

함정 — 같은 소스가 C# 9.0 에서는 Dump 를 매번 부릅니다(1, 2, 3). 앞 장처럼 string 판이 있으니 거절 없이 그쪽으로 가기 때문입니다. 반대로 C# 10 에서는 구멍의 부수 효과가 조건에 따라 사라집니다. 메시지를 문자열 지역 변수에 먼저 담으면(msg) 처리기가 끼어들 틈이 없어 언제나 계산됩니다.
실행 검증

string.Create 와 Span.TryWrite — 문화권과 스택 버퍼

발표 글의 셋째 예: "String.Create() lets you specify the IFormatProvider used to format the expressions in the holes". 제안서의 넷째 비용(ref struct 를 쓸 수 없다)은 Span<char> 에 바로 쓰는 TryWrite 가 풉니다.

string.Create(comma, …) 은 구멍을 그 문화권으로 서식화합니다(1,5). TryWrite 는 버퍼가 모자라면 예외 대신 False 와 0 을 돌려줍니다 — 10자짜리 결과는 8칸에 들어가지 않습니다. 이 캡처의 "현재 문화권" 은 이 덱의 실행 환경(LANG=C)이라 1.5 입니다.

실행 검증

처리기 지역 변수와 캐스트 — 메서드 인수가 아니어도

제안서의 변환은 인수 자리에 묶이지 않습니다. 보간 문자열에서 처리기 형식으로 가는 암시적 변환이므로 지역 변수의 초기화자나 캐스트에서도 처리기가 만들어지고, 제안서도 "handlers can be assigned to locals (such as MyHandler handler = $"{MyCode()}";)" 라고 적습니다.

처리기는 클래스여도 됩니다. (Parts)$"{a}{b}" 는 글자 없는 구멍 둘이라 new Parts(0, 2) 입니다. var 는 여전히 string 입니다 — 보간 문자열의 자연 형식은 C# 10 에서도 바뀌지 않았습니다(7부).

실행 검증

함정 — 구멍 안의 await 와 ref struct 처리기

제안서는 ref struct 처리기가 async 메서드에서 문제가 될 수 있다고 보고, DefaultInterpolatedStringHandler 는 구멍에 await 가 없을 때만 쓰도록 여지를 남겼습니다("the current context supports using that type"). 사용자가 만든 ref struct 처리기에는 그런 여지가 없습니다.

처리기 오버로드가 이기는 자리에 await 를 넣으면 string 판으로 물러서지 않고 CS4007 입니다. 오류 위치는 await 줄이 아니라 메서드 본문의 첫 줄(25행)입니다. string 지역 변수에 먼저 담으면(28행) 그 보간은 7부에서 본 대로 구멍을 먼저 모두 평가하는 번역(string.Format 의 차례)을 받습니다(7부).

실행 검증

인덱서의 처리기 — 객체 초기화자에서는 안 된다

Roslyn 의 깨지는 변경 목록: "Indexers that take an interpolated string handler and require the receiver as an input for the constructor cannot be used in an object initializer." 아직 다 만들어지지 않은 객체를 처리기가 볼 수 있기 때문입니다. SDK 6.0.200(Visual Studio 2022 17.1)부터입니다.

보통의 인덱서 호출에서는 처리기가 받는 객체의 상태(Count)를 읽습니다. 같은 인덱서를 new Table { [$"b{2}"] = 20 } 에 쓰면 CS8976 입니다. 제안서도 중첩 초기화자의 평가 순서 때문에 "we forbid the scenario entirely" 라고 적었습니다.

실행 검증

상수 보간 문자열 (constant interpolated strings) C# 10.0

왜 — const string S3 = S1 + "…" 는 이미 되는데 같은 것을 보간으로 써 달라는 "many community requests" 가 있었습니다. 명세는 상수 식 목록에 보간 문자열을 더합니다 — "provided that all components are constant expressions of type string and all interpolated components lack alignment and format specifiers".

7부의 예고(7부)는 const 필드·특성 인수·case 를 봤습니다. 여기서는 한 걸음 더 — 축자 보간 $@, 보간 안의 보간, switch 식의 상수 패턴($"{Name}!")도 상수이고, 결과는 컴파일 때 만든 문자열 상수라 같은 글자의 리터럴과 같은 객체 (True)입니다.

실행 검증

상수가 안 되는 보간 — 숫자, 너비, 서식

whats-new: 구멍은 숫자 상수일 수 없다. "those constants are converted to strings at run time. The current culture may affect their string representation." 발표 글도 "they are sensitive to Culture, and can't be computed at compile time" 이라고 적습니다.

셋 다 같은 CS0133("must be constant")입니다. 문자열 상수에 너비(,8)나 서식(:U)을 붙여도 상수가 아닙니다 — 명세의 "lack alignment and format specifiers" 그대로입니다. 문화권을 타지 않는 string 만 상수로 남깁니다. 오버로드에서 상수 보간이 string 판을 고르는 것은 앞에서 봤습니다.

실행 검증

4장 퀴즈 — 보간 문자열 처리기

Q. Debug.Assert(x > 0, $"{Dump(x)}") 가 있는 프로젝트의 언어 버전을 10 에서 9 로 내렸습니다. 컴파일 오류는 없습니다. 무엇이 달라집니까?

A. C# 9 에서는 처리기 변환이 고려되지 않아 Debug.Assert(bool, string) 판이 골라집니다. 그래서 Dump(x) 가 조건과 상관없이 매번 평가됩니다(4장). 같은 소스, 거절 없는 다른 동작 — 오버로드 옆에 string 판이 있는 처리기 API 는 모두 그렇습니다(4장).

람다와 패턴 — 형식을 스스로 갖는 람다

자연 형식 · Delegate 와 Expression · 합성 대리자 · 형식 유추 · 반환 형식 · 특성 · 오버로드의 변화 · 확장 속성 패턴

왜 — 람다를 쓸 때마다 대리자 형식을 적어야 했다

제안서는 세 가지를 한꺼번에 제안합니다 — 람다의 특성, 명시적 반환 형식, 람다와 메서드 그룹의 자연 대리자 형식. 동기는 이렇게 적었습니다: "Requiring explicit delegate types for lambdas and method groups has been a friction point for customers, and has become an impediment to progress in ASP.NET with recent work on MapAction."

제안제안서가 댄 까닭
특성"parity with methods and local functions"
반환 형식매개변수 형식을 적을 수 있는 것과의 대칭, 그리고 겹친 람다에서 "control over compiler performance"
자연 형식var 초기화자처럼 대리자 형식 없이 람다를 쓰는 자리를 늘린다

발표 글도 "one of the driving scenarios has been to make ASP.NET Minimal APIs even more straightforward" 라고 적습니다. 그래서 이 장의 예제는 Delegate 를 받는 API 에서 끝납니다(작은 라우터).

문서 근거

람다와 메서드 그룹의 자연 형식 (natural type) C# 10.0

왜 — 제안서: 매개변수 형식이 명시되고 반환 형식을 알 수 있으면 람다는 자연 형식을 갖는다. 메서드 그룹은 "if all candidate methods in the method group have a common signature" 일 때 갖는다. 그 형식은 Func·Action 입니다.

C# 2 의 익명 메서드(delegate (object o) { })도 자연 형식을 얻습니다. Console.Read 는 오버로드가 하나라 Func<int> 입니다. C# 9.0 의 거절은 일곱 줄 모두 'inferred delegate type' 이고, 반환 형식을 적은 16행에는 'lambda return type' 이 하나 더 붙습니다(오류 8개). C# 3 의 장에서 본 예고(4부)의 var inc = (int x) => x + 1 이 이 규칙의 가장 짧은 꼴입니다.

실행 검증

아직 형식이 없는 것 — 매개변수 형식, 오버로드, default

제안서의 var 절이 그대로 오류 예로 듭니다 — var f1 = () => default; 와 var f2 = x => x; 는 "cannot infer type". 발표 글은 var write = Console.Write; 를 "Multiple overloads, can't choose" 라고 적습니다.

셋 다 같은 CS8917 입니다. C# 3 의 거절(4부)은 x => x 에서 지금도 그대로입니다 — C# 10 은 매개변수 형식을 유추해 주지 않고, 적힌 형식으로 대리자 형식을 고를 뿐입니다. 반환 형식을 정할 수 없는 default 는 반환 형식을 적어 풀 수 있습니다(뒤).

실행 검증

Delegate·object·Expression 으로 — 새 변환

제안서: 함수 형식에서 System.MulticastDelegate 와 그 기반 형식·인터페이스로, 그리고 Expression·LambdaExpression 으로 가는 암시적 변환이 생긴다. 메서드 그룹을 object 로 바꾸면 "the conversion is valid but perhaps unintentional" 이라 경고를 낸다.

함정 — C# 9.0 의 거절은 "Feature … is not available" 이 아니라 예전부터 있던 CS1660·CS0428 입니다. 언어 버전을 올리라는 말이 없으니 오류만 보고는 C# 10 의 기능이라는 것을 알 수 없습니다. object oops = Seven; 은 C# 10 에서 컴파일되고 Func`1 이 찍힙니다 — Seven() 을 쓰려던 것이라면 경고 CS8974 가 유일한 단서입니다.
실행 검증

Func·Action 로 안 되는 꼴 — 컴파일러가 대리자를 만든다

제안서: ref·out 같은 by-value 아닌 매개변수, 16개를 넘는 매개변수, 형식 인수가 될 수 없는 형식이면 "a synthesized internal anonymous delegate type" 을 만들고, 매개변수 이름은 arg1, ..., argn (하나면 arg)입니다. 서명이 같으면 같은 형식을 씁니다.

합성 형식은 모두 public=False(internal)이고 매개변수 이름은 제안서대로 arg 입니다. 이름 <>F{00000001}`2 는 반환이 있는 꼴(F)과 ref 종류의 표시를 담고, 제네릭이라 같은 꼴을 여러 형식이 함께 씁니다. 매개변수 17개는 <>F`18 — 16개까지인 Func 를 넘었습니다(런타임). 이 이름들은 컴파일러가 정하는 것이라 코드가 기댈 것이 아닙니다.

형식 유추도 자연 형식을 본다 — 배열, 제네릭, Delegate 제약

제안서: 형식 유추의 첫 단계는 매개변수 형식이 대리자가 아니어도(예: System.Delegate 로 제약한 형식 매개변수) 람다를 받아들이고, 최선 공통 형식은 형식 유추로 정의되므로 new[] { (string s) => s.Length, … } 가 Func<string, int>[] 가 된다.

함정 — 배열 초기화자는 되는데 ?: 의 두 람다는 C# 14 에서도 CS0173 입니다. 제안서가 함수 형식을 쓰는 자리로 꼽은 것은 변환, 형식 유추와 최선 공통 형식, var 초기화자뿐입니다. 버리기(_ = () => 1)도 제안서대로 거절되고, 서명이 다른 두 람다는 T 를 정하지 못합니다. C# 9.0 의 거절도 앞 장처럼 'Feature' 문장이 아닙니다(CS0826·CS0411).

람다의 명시적 반환 형식 (explicit return type) C# 10.0

왜 — 발표 글의 예: var choose = (bool b) => b ? 1 : "two"; 는 반환 형식을 유추할 수 없다. 반환 형식은 괄호로 싼 매개변수 목록 앞에 씁니다. 제안서는 명시적 반환 형식에서 메서드 형식 유추가 "exact inference" 를 한다고 정했습니다.

int? 를 적으면 null 가지가 풀리고, 적지 않으면 CS8917 입니다. ref int 를 돌려주는 람다는 Func 가 담을 수 없어 합성 형식(<>F{00000008}`2)이 되고, 그 반환에 대입한 10 이 배열에 들어갔습니다. long () => 1 은 T 를 Int64 로 고정합니다. Func<object> 에 string () 람다를 넣는 것은 제안서대로 거절됩니다(CS8934) — 반환 형식 사이의 공변 변환은 없습니다.

람다의 특성 (lambda attributes) C# 10.0

왜 — 메서드·지역 함수와의 대칭입니다(지역 함수의 특성은 C# 9, 8부). 특성은 "emitted to metadata on the method that maps to the lambda" 되고, 제안서는 Delegate 의 MethodInfo 로 그것을 읽는 쓰임을 겨냥합니다. 특성이 있으면 매개변수 목록에 괄호가 있어야 합니다.

특성은 람다가 번역된 메서드 <Main>b__1_1 에 붙어 있습니다. 제안서는 이 이름과 위치(App+<>c)에 기대지 말라고 적습니다 — "How lambdas and local functions are emitted can, and has, changed between compiler versions." 발표 글대로 특성은 람다를 부를 때 아무 효과가 없고, 코드 분석과 리플렉션을 위한 것입니다.

세 기능을 한데 — Delegate 를 받는 작은 라우터

제안서의 MapAction 예는 이 장의 세 기능이 왜 함께 왔는지 보여 줍니다 — app.MapAction([HttpGet("/")] () => new Todo(...)). 특성은 경로를, 자연 형식은 캐스트 없는 Delegate 인수를, 매개변수 형식은 바인딩을 맡습니다. 같은 모양을 BCL 만으로 흉내 냈습니다.

같이 온 런타임 — 자연 형식이 고르는 Func 와 Action

발표 글: "the compiler will use an available Func or Action delegate, if a suitable one exists. Otherwise, it will synthesize a delegate type". 그 "있는 것" 이 무엇인지 .NET 10 의 System.Private.CoreLib 에서 셌습니다.

CallerArgumentExpression — 인수의 식을 문자열로 C# 10.0

왜 — 제안서: 단언이 실패하면 어느 단언인지 알 수 없다. 특성이 가리킨 매개변수의 인수 식을 컴파일러가 문자열로 넘긴다. 확장 메서드의 this 도 가리킬 수 있고, 정적 메서드 꼴로 부르면 "it will behave as if first parameter wasn't marked this".

식은 소스의 글자 그대로입니다 — index * 2 의 공백은 남고 뒤의 주석은 빠졌습니다. 인수를 직접 주면("explicit") 그것이 이깁니다. .NET 10 의 ThrowIfGreaterThan 이 index 라는 이름을 아는 것도 같은 특성 덕입니다. C# 9.0 에서도 출력이 같습니다 — 게이트가 없다는 것은 C# 5 의 장에서도 봤습니다 (6부).

문서와 다른 곳 — 없는 매개변수 이름을 가리키면

제안서의 "Extra details": "If null or a string that is not a parameter name (e.g. "notAParameterName") is provided, the compiler will pass in an empty string." 앞 예제의 #if ODD 갈래가 그 경우입니다.

문서와 다른 곳 — 빈 문자열이 아니라 기본값 "default" 가 들어왔고, 경고 CS8963("will have no effect")가 납니다. 지금의 컴파일러는 잘못된 특성을 무시하고 보통의 선택적 매개변수로 다룹니다. 제안서는 구현 전의 설계 문서라 이런 차이가 남습니다.

확장된 #line — 줄만이 아니라 범위와 열 C# 10.0

왜 — 제안서: Razor 같은 DSL 이 만든 C# 은 #line 으로 원래 파일의 줄만 가리킬 수 있어, 디버거의 시퀀스 포인트(sequence point)가 원본의 정확한 열을 가리키지 못했다. 새 꼴 #line (줄, 열) - (줄, 열) [문자 오프셋] "파일" 은 대응할 범위를 주고, 첫 줄의 열은 "L.start.character + max(c – character offset, 0)" 으로 옮깁니다.

옛 꼴 #line 20 은 줄만 바꾸고 열 9 는 생성된 코드의 들여쓰기 그대로입니다. 범위 꼴은 열을 원본 기준으로 옮기는데, 오프셋이 없으면 들여쓰기 8칸이 더해져 11 이 되고, 오프셋 8 을 주면 생성기가 붙인 앞부분이 빠져 원본의 열 3 이 됩니다. 경고 CS0168 의 위치 page.razor(9,7) 도 같은 식으로 옮겨졌습니다. 이 문법은 C# 9.0 에서도 받아들여집니다 — 게이트가 없습니다. whats-new 의 말대로 "You likely won't use the new format, but you'll see its effects."

공개 아닌 인터페이스 멤버의 암시적 구현 C# 10.0

왜 — C# 8 의 기본 인터페이스 메서드 명세는 internal·protected 인터페이스 멤버를 두고 "You can only implement non-public interface members explicitly" 라고 정했습니다. 컴파일러의 게이트 목록에는 C# 10 의 기능으로 이름 없이 들어 있습니다(1장).

C# 10 에서는 public 클래스 멤버가 internal·protected internal 인터페이스 멤버를 암시적으로 구현합니다. C# 9.0 의 거절은 'Feature' 문장이 아니라 전용 오류 CS8704("cannot implicitly implement a non-public member in C# 9.0")이고 버전을 올리라고 말합니다. whats-new·버전 기록·발표 글에는 이 변화가 없습니다 — 받아 둔 문서 가운데 이 기능을 C# 10 의 것으로 적은 곳은 컴파일러의 게이트뿐입니다.

실행 검증

그래도 남은 규칙 — 구현하는 쪽은 public 이어야 한다

C# 8 명세의 예는 클래스 쪽도 internal void MI() {}·protected void MP() {} 로 적고 "are these implementations? Decision: NO" 라고 답합니다. 앞 예제의 #if INTERNAL 갈래가 그 꼴입니다.

C# 10 이 푼 것은 "인터페이스 쪽이 공개가 아니어도 된다" 뿐입니다. 구현하는 클래스 멤버가 internal 이면 여전히 CS0737("because it is not public")입니다. 명세의 두 결정 가운데 하나만 바뀐 셈입니다.

11부 퀴즈

Q. C# 10 프로젝트를 C# 9.0 으로 내렸더니 오류가 다섯 개였습니다. 다섯 곳만 고치면 C# 9.0 으로 컴파일됩니까? 오류 없이 동작만 바뀌는 곳은 없습니까?

A. 둘 다 아닙니다. 선언 단계의 오류(global using, record struct …)가 있으면 메서드 본문의 오류는 보고되지 않습니다 — 고치고 나면 람다의 자연 형식, 확장 속성 패턴, 섞인 분해가 새로 나옵니다(7장). 그리고 거절 없이 뜻만 바뀌는 곳도 있습니다 — 처리기와 string 오버로드가 함께 있는 API(4장), 자연 형식이 바꾼 오버로드 결정(5장).

Q. var f = (ref int x) => x++; 와 var g = (string s = "a") => s;(C# 12) 의 형식은 무엇이고, Func 변수에 넣을 수 있습니까?

A. 둘 다 Func 가 아니라 컴파일러가 합성한 internal 대리자입니다 — ref 매개변수는 Func 의 형식 인수가 될 수 없고(5장), 기본값은 Func 가 담을 수 없습니다(5장). 그래서 g 를 Func<string, string> 에 넣으면 CS0029 입니다. f 는 애초에 맞는 Func 가 없습니다.
