6부를 읽는 법

버전 기록은 C# 5.0 을 "a focused version of the language" 라고 부르고, 노력의 거의 전부가 async 와 await 에 들어갔다고 적습니다. 그리고 이렇게 맺습니다. "But async and await are the real stars of this release."

  • 1장 — C# 5.0 개관. 게이트 하나, 같이 온 런타임.
  • 2장 — 왜 async 인가. 같은 프로그램을 동기·APM·EAP·ContinueWith·await 다섯 꼴로.
  • 3장 — async/await 의 문법과 의미. 어디서 멈추고, 예외는 어디로 가나.
  • 4장 — 컴파일러가 만드는 것. 상태 기계, awaitable 패턴, 동기화 문맥.
  • 5장 — 함정. await 를 잊기, async void, 동기로 기다리기, 취소.
  • 호출자 정보 특성, foreach 변수 포착의 변화, C# 5.0 정리는 6장부터 이어집니다.

비동기 예제의 출력은 돌릴 때마다 같아야 캡처로 쓸 수 있습니다. 그래서 이 부의 예제는 스레드 번호와 시각을 찍지 않고, 줄의 차례는 await 나 직접 완료시키는 Task 나 한 스레드짜리 동기화 문맥이 정합니다. async Main 은 C# 7.1 의 기능이라 예제의 Main 은 모두 동기로 기다립니다.

C# 5.0 한눈에

버전 기록의 목록은 둘입니다 — 비동기 멤버와 호출자 정보 특성. 언어 쪽 행이 여럿인 것은 async 하나를 이 덱이 여러 면으로 나눠 보기 때문입니다.

문서 근거

async 메서드 — 컴파일러가 확인하는 단 하나 C# 5.0

왜 — 표준은 async 한정자가 붙은 메서드·익명 함수를 async 함수라 부르고, 그 몸체가 await 식으로 "suspend evaluation" 할 수 있다고 정의합니다. Roslyn 의 C# 5 자리에는 그 기능 하나만 있습니다.

거절은 async 가 붙은 줄 하나에서만 나옵니다. 몸체의 await 는 따로 거절되지 않습니다.

실행 검증

await 는 문맥 키워드 — 옛 코드의 이름을 지킨다

표준: async 함수 밖에서 await 는 "a normal identifier" 이고, 안에서는 이름으로 쓸 수 없지만 @await 는 됩니다.

await 라는 이름을 쓴 C# 4 의 메서드(Twice)는 C# 5 에서도 그대로 컴파일됩니다. await 가 연산자가 되는 곳은 async 가 붙은 함수 안뿐이라, async 는 "await 를 켜는 스위치" 이기도 합니다.

같이 온 런타임 — 컴파일러가 이름으로 찾는 형식

async 메서드를 컴파일하면 컴파일러는 라이브러리의 정해진 형식을 이름으로 찾아 씁니다. 표준의 "task builder" 와 "awaiter" 가 그 자리입니다(4장).

왜 async 인가 — 같은 프로그램, 다섯 가지 꼴

설명용

기준 — 동기 판

스트림의 Read 는 데이터가 올 때까지 부른 스레드를 붙잡아 둡니다. 메모리 스트림이라 바로 돌아오지만, 파일이나 네트워크라면 그 스레드는 그동안 아무것도 못 합니다.

이 모양 — 반복문, 지역 변수, 아래로 흐르는 차례 — 을 비동기로 옮기는 것이 이 장의 문제입니다.

실행 검증

꼴 1 — Begin/End 짝(APM)

BeginRead 는 바로 돌아오고, 읽기가 끝나면 콜백을 부릅니다. 콜백 안에서 EndRead 로 결과를 받습니다. IAsyncResult 를 쓰는 이 짝은 C# 1 의 대리자에도 컴파일러가 만들어 주던 꼴입니다(2부).

함정 — 지역 변수였던 buf·total 이 정적 필드로 나갔습니다. 콜백은 다른 메서드라 지역 변수를 나눠 쓸 수 없기 때문입니다. 끝났다는 신호도 ManualResetEvent 로 따로 만들었습니다. 같은 꼴의 대리자 BeginInvoke 는 .NET 10 에서 예외를 던지지만, 스트림의 BeginRead 는 지금도 돕니다.
실행 검증

꼴 2 — 이벤트 기반(EAP), 읽는 쪽

XxxAsync 메서드로 시작하고 XxxCompleted 이벤트로 결과를 받는 꼴입니다. 이벤트 인자는 System.ComponentModel 의 AsyncCompletedEventArgs 를 물려받아 오류를 Error 로 실어 나릅니다. BCL 의 스트림에는 이 꼴이 없어서, 같은 일을 하는 작은 클래스를 만들었습니다.

예외도 던지지 않습니다. 붙잡아 이벤트 인자에 담아 보냅니다 — 받는 쪽이 확인하지 않으면 그대로 사라집니다.

실행 검증

꼴 2 — 이벤트 기반(EAP), 부르는 쪽

APM 보다 덜 낯설지만 모양은 같습니다. 반복문은 처리기가 자기 자신을 다시 부르는 구조로 흩어지고, 끝남은 따로 알려야 합니다. 이 판은 람다(C# 3)가 지역 변수를 잡아 준 덕에 필드가 줄었을 뿐입니다.

실행 검증

꼴 3 — Task 와 ContinueWith

Task<int> 는 "나중에 올 int" 를 값으로 들고 다닙니다. FromAsync 가 APM 짝을 Task 로 감싸고, ContinueWith 가 끝난 뒤의 일을 잇습니다.

함정 — 이어 붙인 람다가 다시 Task 를 돌려주므로 결과는 Task<Task<int>> 이고, Unwrap() 으로 한 겹 벗겨야 합니다. 반복문은 여전히 재귀입니다.
실행 검증

꼴 4 — async/await

동기 판의 Read 자리에 await s.ReadAsync 가 들어갔습니다. 나머지 — while, 지역 변수, 위에서 아래로 흐르는 차례 — 는 동기 판과 같습니다.

새로 붙은 것은 셋입니다 — 메서드의 async, 반환 형식 Task<int>, 읽는 곳의 await. 반복문의 몸체는 동기 판과 같습니다. 콜백으로 나누는 일은 컴파일러가 합니다(4장).

실행 검증

옛 꼴을 Task 로 — TaskCompletionSource

APM 이나 EAP 로만 된 API 도 await 할 수 있습니다. 콜백 안에서 TaskCompletionSource 를 완료시키면, 그 Task 가 콜백을 대신합니다.

꼴 3의 FromAsync 가 하는 일을 손으로 쓴 것입니다. 이 부의 예제가 차례를 고정할 때 쓰는 TaskCompletionSource 도 같은 형식입니다 — "Task 를 내 손으로 완료시킨다".

실행 검증

실패는 어디로 오나 — ContinueWith 와 await

닫힌 스트림을 비동기로 읽으면 ReadAsync 는 실패한 Task 를 돌려줍니다. 두 꼴이 그 실패를 받는 법이 다릅니다.

ContinueWith 판은 Task 의 상태(IsFaulted)를 묻고 AggregateException 안에서 진짜 예외를 꺼냅니다. await 판은 동기 코드처럼 try/catch 로 원래 형식의 예외를 잡습니다(3장).

2장 퀴즈 — 왜 async 인가

Q. APM 판에서 buf 와 total 이 정적 필드가 된 까닭은 무엇이고, await 판에서는 왜 지역 변수로 남을 수 있습니까?

A. APM 판에서는 읽기 하나가 끝날 때마다 다른 메서드(콜백)가 불리므로, 여러 번의 호출이 나눠 쓸 값은 메서드 밖에 있어야 합니다. await 판도 실제로는 여러 번에 나뉘어 돌지만, 그 나눔을 컴파일러가 하면서 지역 변수를 자기가 만든 클래스의 필드로 옮깁니다(4장). 코드에는 지역 변수로 보일 뿐입니다.

3장

async/await — 어디서 멈추고, 무엇이 돌아오나

반환 형식 · 첫 await 까지는 동기 · 예외는 Task 에 · async void · await 가 못 가는 자리

반환 형식은 셋 — void, Task, Task<T>

표준: async 메서드의 반환 형식은 void 이거나 task 형식이고, 결과가 있으면 제네릭 task 형식이어야 합니다.

Task<int> 를 돌려주는 메서드의 return 은 int 를 돌려줍니다. 감싸는 일은 컴파일러가 합니다. 눈여겨볼 것은 첫 줄입니다 — 값 없는 Task 를 돌려주는 NoValue 의 Task 도 런타임 형식은 제네릭 Task`1 입니다. .NET 10 의 구현이 그렇게 만들 뿐, 선언된 반환 형식은 Task 입니다.

실행 검증

그 밖의 반환 형식 — 지금의 오류 문장

거절 문장이 C# 5 의 목록보다 깁니다 — "a task-like type, IAsyncEnumerable<T>, or IAsyncEnumerator<T>". 지금의 컴파일러는 뒤 버전의 허용 목록까지 한 문장에 적습니다. -langversion:5 라고 문장이 바뀌지는 않습니다.

실행 검증

뒤 버전과의 맞물림 — ValueTask 를 돌려주는 async 메서드

"What's new in C# 7.0" 은 "Generalized async return types" 를 C# 7 의 기능으로 소개합니다. async 메서드의 반환 형식이 Task·Task<T>·void 에 묶이지 않게 됐고, 그 예가 ValueTask 입니다.

문서와 다른 곳 — -langversion:5 에서도 거절이 없습니다. Roslyn 의 게이트 표에 이 기능이 없기 때문입니다(0부). 이런 경우 언어 버전 옵션은 옛 컴파일러를 흉내 내지 못합니다. 이 덱은 이 기능을 C# 7 의 것으로 셉니다(8부).
실행 검증

await 가 없는 async 메서드

async 를 붙였지만 몸체에 await 가 없으면, 메서드는 처음부터 끝까지 부른 쪽의 호출 안에서 돌고 이미 끝난 Task 를 돌려줍니다. 표준의 말로는 몸체가 "suspended" 되지 않고 "terminates" 한 것입니다.

경고가 없다 — 이 SDK 의 컴파일러는 이 코드에 아무 경고도 내지 않습니다. 받아 둔 Roslyn 자원 파일에도 "lacks 'await'" 류의 문장이 없습니다. 예전 판에서 어떤 경고가 났는지는 이 기계에서 보일 수 없습니다. 미확인
실행 검증

await 가 메서드를 둘로 나눈다

표준: 몸체는 await 에서 "suspended" 되거나 끝날 때까지 돌고, 그때 Task 와 함께 부른 쪽으로 돌아갑니다. 나머지는 나중에 "resumption delegate" 가 불릴 때 이어 돕니다.

SetResult 를 부른 그 자리에서 나머지 절반이 돌았습니다. 동기화 문맥이 없을 때 .NET 이 이어 달리기를 완료시킨 스레드에서 곧바로 부르기 때문입니다. 그 선택은 런타임의 구현이고, 표준이 정한 차례는 아닙니다.

실행 검증

첫 await 까지는 부른 스레드에서

async 메서드는 부르는 순간 새 스레드로 가지 않습니다. 끝나지 않은 Task 를 await 하는 지점까지는 보통 메서드처럼 부른 쪽의 스레드에서 돕니다.

스레드 번호는 찍지 않고 참·거짓만 찍었습니다. 앞의 줄은 언제나 참입니다. 뒤의 줄은 Task.Delay 의 타이머가 스레드 풀에서 이어 달리기를 부르는 .NET 10 의 동작입니다. "async = 새 스레드" 가 아닙니다.

실행 검증

이미 끝난 Task 는 멈추지 않는다

표준의 await 평가: 먼저 awaiter 의 IsCompleted 를 묻고, 참이면 멈추지 않고 곧바로 GetResult() 로 갑니다.

첫 호출은 돌아올 때 이미 RanToCompletion 입니다. 둘째 호출은 a 는 지나가고 b 에서 멈춥니다. await 의 비용은 "기다릴 게 있을 때만" 치릅니다.

실행 검증

Task.Yield — 일부러 한 번 멈추기

Task.Yield() 는 언제나 "아직 안 끝났다" 고 답하는 awaitable 입니다. 이어 달리기는 현재 동기화 문맥으로 갑니다. 아래 예제는 Post 된 일을 줄 세웠다가 차례로 돌리는 한 스레드짜리 문맥(Loop)을 씁니다 — 그래서 출력의 차례가 늘 같습니다.

Loop 는 이 부의 뒤 예제에서도 씁니다. 한 스레드가 일감 줄을 차례로 비우는 메시지 루프를 열 줄 남짓으로 흉내 낸 것입니다(4장).

실행 검증

return 에는 Task 가 아니라 값을

async 가 아닌 메서드에서는 return Task.FromResult(x * 2); 가 맞는 코드입니다. 같은 줄이 async 를 붙이는 순간 오류가 됩니다. 반환 형식은 같아도 return 의 뜻이 바뀌기 때문입니다.

실행 검증

await 는 식이다 C# 5.0

왜 — 표준은 await t 를 (t).GetAwaiter().GetResult() 와 같은 방식으로 분류합니다. 결과가 있으면 그 형식의 값이므로 값이 올 수 있는 곳 어디에나 쓸 수 있습니다.

인자는 왼쪽부터 평가되고, 각 await 는 다음 인자를 평가하기 전에 끝납니다. Task<Task<int>> 는 await await 로 두 겹을 벗깁니다(2장의 Unwrap 자리).

실행 검증

&& 와 ?: 의 오른쪽 await — 평가되지 않으면 기다리지도 않는다

await 는 식이므로 연산자의 평가 규칙을 그대로 따릅니다. && 의 왼쪽이 거짓이면 오른쪽의 Check("b") 는 불리지 않고, 그러니 기다릴 것도 없습니다. ?: 도 고른 쪽만 평가합니다.

실행 검증

await 의 두 얼굴 — 이름과 연산자의 경계

둘째 오류는 고치는 법까지 적습니다 — async 를 붙이고 반환 형식을 Task<int> 로. 메서드 하나를 async 로 바꾸면 그 반환 형식이 바뀌고, 부르는 쪽도 바뀌어야 합니다.

실행 검증

결과 없는 await 는 값이 아니다

표준: GetResult 의 반환 형식이 void 이면 await 식은 "classified as nothing" 입니다. 값 없는 Task 를 await 한 식은 문장으로만 쓸 수 있습니다.

오류 문장이 "void" 를 말합니다. 컴파일러가 이 식의 형식을 GetResult() 의 반환 형식으로 본다는 증거입니다.

실행 검증

예외는 던져지지 않고 Task 에 담긴다

표준: async 함수의 몸체가 잡히지 않은 예외로 끝나면 "the exception is recorded in the return task", Task 는 faulted 상태가 됩니다. 부르는 순간에는 아무것도 던져지지 않습니다.

t.Exception 은 AggregateException 으로 감싼 꼴이지만, await 는 그 안의 원래 예외를 원래 형식으로 다시 던집니다. 그래서 catch (FormatException) 이 그대로 잡습니다.

실행 검증

동기로 기다리면 — AggregateException

같은 실패한 Task 를 세 가지로 기다립니다. Result·Wait() 는 Task 의 멤버이고, GetAwaiter().GetResult() 는 await 가 쓰는 길입니다(앞).

앞의 둘은 감싼 예외를, 마지막은 원래 예외를 던집니다. 이 덱의 예제가 Main 에서 GetAwaiter().GetResult() 를 쓰는 곳이 있는 까닭입니다 — async Main 의 제안서가 바로 그 줄을 "boilerplate" 의 예로 듭니다(뒤에).

실행 검증

취소는 실패와 다른 상태

표준: 잡히지 않은 OperationCanceledException 으로 끝난 몸체는 Task 를 canceled 로, 다른 예외는 faulted 로 만듭니다.

취소된 Task 의 Exception 속성은 비어 있습니다(-). 그래도 await 쪽에서 기다리면 OperationCanceledException 이 다시 던져집니다. 취소는 시각이 아니라 Cancel() 호출로 일으켜서 출력이 늘 같습니다.

실행 검증

async void — 예외를 받을 Task 가 없다 C# 5.0

왜 — 표준: 반환 형식이 void 이면 돌려줄 Task 가 없으므로 완료와 예외를 "the current thread’s synchronization context" 에 알립니다. 문맥이 없으면 예외를 받을 곳이 없습니다.

함정 — try/catch 는 아무것도 잡지 못하고, 예외는 스레드 풀에서 다시 던져져 프로세스를 끝냅니다(종료 코드 -6). 스택의 ThrowAsync 는 .NET 10 의 내부 이름입니다. async void 는 이벤트 처리기처럼 돌려받을 곳이 정말 없는 자리에만 씁니다.
실행 검증

async void 와 동기화 문맥 — 표준이 말한 세 알림

표준은 문맥이 알림을 받는 때를 셋으로 적습니다 — "commences, completes successfully, or causes an uncaught exception to be thrown". 알림을 찍기만 하는 문맥을 걸고 확인합니다.

.NET 10 에서 시작은 OperationStarted, 끝은 OperationCompleted 이고, 예외는 문맥의 Post 로 넘어간 콜백 안에서 다시 던져집니다. 문맥이 있으면 그 예외를 문맥이 처리할 기회가 생깁니다 — 이 Spy 는 잡아서 찍었습니다.

실행 검증

await 를 잊으면 — 경고 CS4014

Task 를 돌려주는 async 메서드를 부르고 결과를 그냥 버리면 컴파일러가 경고합니다. 경고가 나지 않는 경우는 5장에서 봅니다.

함정 — Save 는 실패했지만 아무도 그 Task 를 보지 않아 예외가 조용히 사라졌습니다. "saved?" 다음에 "done" 이 나오고 종료 코드도 0 입니다. 경고 문장이 말하는 대로, 호출이 끝나기 전에 현재 메서드가 계속 갑니다.
실행 검증

try 블록 안의 await 는 C# 5 에서도 된다

C# 5 가 막은 것은 catch·finally 블록 안의 await 입니다. try 블록 안의 await 는 처음부터 되고, 이어진 뒤에 난 예외도 같은 catch 가 받습니다.

메서드는 await 에서 한 번 돌아갔다가 나중에 이어졌지만, try·catch·finally 의 차례는 동기 코드와 같습니다. 상태 기계가 try 의 모양까지 옮겨 주기 때문입니다(4장).

실행 검증

using 블록과 await — Dispose 는 이어진 뒤에

using 은 try/finally 의 줄임이므로 await 를 품을 수 있습니다. 메서드가 await 에서 돌아가도 자원은 닫히지 않습니다.

"Work returned" 가 찍힐 때 자원은 아직 열려 있고, Dispose 는 나머지 절반이 블록을 빠져나갈 때 불립니다. Dispose 자체를 await 하는 await using 은 C# 8 의 기능입니다(9부).

실행 검증

C# 5 의 제약 — catch 와 finally 안에는 await 를 못 쓴다

"What's new in C# 6": "C# 5 had several limitations around where you could place await expressions. With C# 6, you can now use await in catch or finally expressions."

게이트 표에는 "await in catch blocks and finally blocks" 가 C# 6 으로 올라 있지만, C# 5 로 내렸을 때 나오는 문장은 "Feature … is not available" 꼴이 아니라 옛 오류 CS1985·CS1984 입니다. 자세한 것은 7부에서 봅니다.

실행 검증

lock 안의 await — 지금도 거절

표준이 await 를 금하는 자리 가운데 하나가 "Inside the block of a lock_statement" 입니다.

catch·finally 의 제약은 C# 6 에서 풀렸지만 이 제약은 C# 14 에서도 그대로입니다. await 뒤의 코드가 다른 스레드에서 이어질 수 있다는 것은 앞에서 보았습니다.

실행 검증

async 메서드에는 ref·out 매개변수가 없다

표준: "It is a compile-time error for the parameter list of an async function to specify any in, out, or ref parameters".

매개변수는 상태 기계의 필드로 옮겨집니다(4장). 결과가 둘 이상이면 C# 5 에서는 결과를 담은 형식을 Task<T> 로 돌려줍니다. 튜플(8부)이 그 자리를 가볍게 만듭니다.

실행 검증

async 람다와 async 익명 메서드 C# 5.0

왜 — 표준은 메서드뿐 아니라 "anonymous function" 에도 async 를 허용합니다. 람다의 문법에도, C# 2 의 익명 메서드 문법에도 'async'? 자리가 있습니다.

async 람다는 Task·Task<T> 를 돌려주는 대리자로 바뀝니다. 대리자 형식이 void 를 돌려주면 async void 가 됩니다 — 그 함정은 5장에서 봅니다. 익명 메서드 쪽은 3부에서 C# 4 로 내린 거절까지 보았습니다.

실행 검증

await 는 가장 안쪽 함수가 async 여야

표준이 금하는 자리의 첫째: "Inside a nested (non-async) anonymous function". 바깥 메서드가 async 여도, await 를 감싼 가장 가까운 함수가 async 가 아니면 안 됩니다.

오류는 f 의 람다 하나뿐이고, 고치는 법(async 를 붙이라)까지 알려 줍니다. 표준의 주석은 같은 이유로 쿼리 식 안에서도 await 를 거의 못 쓴다고 적습니다 — 쿼리 식은 보통 람다로 번역되기 때문입니다(4부).

뒤 버전과의 맞물림 — async Main 은 C# 7.1

C# 7.1 의 제안서는 동기가 이것이라고 적습니다. Main 에서 await 를 쓰려면 "boilerplate like the following" 이 필요했다 — MainAsync().GetAwaiter().GetResult();. 이 부의 예제가 모두 그렇게 씁니다.

실행 검증

차례로 기다리기와 함께 기다리기

await 는 "여기서 기다린다" 이지 "여기서 시작한다" 가 아닙니다. Task 를 먼저 만들어 두고 나중에 await 하면 두 작업이 겹칩니다. 시간을 재는 대신 동시에 진행 중이던 작업의 최대 수를 셉니다.

셈이 실행마다 같은 까닭: Op 는 첫 await 전까지 부른 쪽에서 동기로 돌므로(앞), Together 에서는 tb 를 만들 때 이미 ta 가 진행 중입니다. OneByOne 에서는 앞의 것이 끝나야 다음 것이 시작됩니다.

실행 검증

3장 퀴즈 — async/await 의 문법과 의미

Q. Task<int> t = Parse(""); 가 예외 없이 지나갔습니다. Parse 는 빈 문자열에 FormatException 을 던지는 async 메서드입니다. 그 예외는 언제, 어떤 형식으로 나타납니까?

A. 예외는 t 에 담겨 있고 t.Status 는 Faulted 입니다. await t 나 t.GetAwaiter().GetResult() 로 기다리면 FormatException 그대로, t.Result 나 t.Wait() 로 기다리면 AggregateException 에 싸여 나옵니다. 아무도 기다리지 않으면 나타나지 않습니다 (CS4014).

4장

컴파일러가 만드는 것 — 상태 기계와 awaitable

async 메서드는 클래스 하나가 된다 C# 5.0

왜 — 표준은 컴파일러가 "task builder" 와 "a compiler-generated state machine instance" 로 멈춤과 이어짐을 구현한다고 적습니다. 그 상태 기계는 IAsyncStateMachine 을 구현해야 합니다.

메서드에는 AsyncStateMachineAttribute 가 붙고, 그 특성이 중첩 형식 <Work>d__0 을 가리킵니다. await 가 없는 NoAwait 도 상태 기계를 받습니다. <…>d__N 같은 이름은 C# 에서 쓸 수 없게 고른 구현의 세부이고, 표준이 정한 것이 아닙니다.

실행 검증

지역 변수는 필드가 된다

await 를 건너 살아남아야 하는 값은 스택에 둘 수 없습니다 — 메서드는 await 에서 돌아가 버리니까요. 그래서 상태 기계의 필드로 옮겨집니다.

상태(<>1__state), 빌더, 매개변수 x, this, 지역 변수, 그리고 awaiter (<>u__1). 최적화 빌드에서는 await 전에만 쓰인 before 가 빠집니다. 어느 쪽이든 필드의 이름과 목록은 구현의 세부입니다.

반환 형식마다 다른 빌더

실행 검증

await 가 여럿이면 — awaiter 필드는 형식마다 하나

await 가 셋인데 awaiter 필드는 둘입니다. 한 번에 멈춰 있는 await 는 하나뿐이므로, 같은 형식의 awaiter 는 필드 하나를 돌려 씁니다 — 이 컴파일러의 선택입니다. 몇 번째 await 에서 멈췄는지는 <>1__state 가 기억합니다.

실행 검증

빌더 — 표준의 목록과 .NET 10 의 AsyncTaskMethodBuilder<T>

표준은 task 빌더가 가져야 할 공개 멤버를 적습니다 — Create, Start, SetStateMachine, SetException, SetResult, AwaitOnCompleted, AwaitUnsafeOnCompleted, Task.

.NET 10 의 빌더는 표준의 목록과 정확히 같고 더 붙은 공개 메서드가 없습니다. 그리고 struct 입니다 — 상태 기계의 필드로 들어가 따로 할당되지 않습니다.

실행 검증

손으로 쓴 상태 기계 — MoveNext

표준의 빌더 사용 순서를 그대로 C# 5 코드로 옮깁니다. awaiter 를 얻고, IsCompleted 가 거짓이면 상태를 적고 AwaitUnsafeOnCompleted 에 자기를 맡긴 뒤 돌아갑니다. 다시 불리면 GetResult() 부터 잇습니다.

컴파일러의 실제 코드와 같지 않습니다 — 상태 번호와 구조는 표준의 설명을 따라 이 덱이 고른 것입니다. 뼈대(상태 필드, 빌더, awaiter 필드, try 로 감싼 MoveNext)는 앞의 필드 목록과 같습니다.

실행 검증

손으로 쓴 판과 컴파일러의 판을 나란히

AddLaterByHand 는 async 가 아닌 보통 메서드입니다. 상태 기계를 만들고 Start 로 첫 MoveNext 를 돌린 뒤 builder.Task 를 돌려줍니다. 컴파일러가 async 메서드 자리에 남기는 "스텁" 이 이 모양입니다.

실행 검증

상태 기계를 건넌 예외의 스택 트레이스

예외는 Inner 의 상태 기계에서 Task 에 담기고, await 마다 다시 던져져 바깥으로 올라옵니다. .NET 10 이 찍는 트레이스는 그 과정을 감추고 소스의 메서드 이름으로 보여 줍니다.

트레이스에는 MoveNext 도 <Inner>d__0 도 보이지 않고, 줄 번호는 소스의 throw 와 await 자리입니다. 옛 .NET Framework 에서 어떻게 보였는지는 이 기계에서 보일 수 없습니다.

실행 검증

async 람다의 상태 기계는 어디에

람다는 컴파일러가 만든 클래스 <>c 의 메서드가 되고(4부), async 이므로 그 메서드가 또 상태 기계를 받습니다. 람다 하나에 중첩 형식이 두 겹입니다. 이름은 모두 구현의 세부입니다.

실행 검증

awaitable 패턴 — Task 가 아니어도 된다 C# 5.0

왜 — 표준이 요구하는 것은 형식이 아니라 모양입니다. 인자 없는 GetAwaiter(), 그 결과가 INotifyCompletion 을 구현하고 bool IsCompleted 와 GetResult() 를 가질 것.

foreach 가 GetEnumerator 라는 이름을 찾듯(2부), await 는 GetAwaiter 를 찾습니다. Later 는 아무 인터페이스도 구현하지 않습니다.

실행 검증

awaitable 패턴 — 부르는 차례

표준의 평가 순서 그대로입니다 — GetAwaiter → IsCompleted → 거짓이면 OnCompleted 로 이어 달리기를 맡기고 돌아감 → 불리면 GetResult. 이미 끝났으면 OnCompleted 를 건너뜁니다.

실행 검증

ICriticalNotifyCompletion 이면 UnsafeOnCompleted

표준: awaiter 가 ICriticalNotifyCompletion 도 구현하면 OnCompleted 대신 UnsafeOnCompleted 가 불립니다. 이 선택은 "done at binding time" — 컴파일 때 정해집니다.

두 메서드는 이어 달리기에 실행 문맥(ExecutionContext)을 실어 보내느냐가 다르다고 알려져 있지만, 받아 둔 문서로는 확인하지 못했습니다. 미확인 확인되는 것은 어느 쪽이 불리는가뿐입니다. TaskAwaiter 는 ICriticalNotifyCompletion 을 구현합니다(1장의 목록).

실행 검증

확장 메서드 GetAwaiter — 남의 형식을 await 하기

표준의 조건은 "an accessible instance or extension method called GetAwaiter" 입니다. C# 3 의 확장 메서드(4부)로 await 할 수 있는 형식을 밖에서 늘릴 수 있습니다.

await list 가 await Task.WhenAll(list) 의 뜻이 됐습니다. await 40 은 문법이 허락한다는 것을 보이려는 예일 뿐입니다.

실행 검증

모양이 모자라면 — 컴파일러가 짚는 곳

컴파일러는 패턴의 빠진 조각을 하나씩 이름으로 짚습니다. OnCompleted 메서드가 있어도 INotifyCompletion 인터페이스를 선언하지 않으면 안 됩니다 — 표준이 요구하는 것이 "implements" 이기 때문입니다.

실행 검증

dynamic 을 await 하면 — 실행 때 확인

표준의 awaitable 조건 첫 줄은 "t is of compile-time type dynamic" 입니다. 그때는 모양 확인이 실행 때로 미뤄집니다(C# 4 의 dynamic, 5부).

string 에는 GetAwaiter 가 없지만 컴파일은 됩니다. 실행 때 런타임 바인더가 RuntimeBinderException 을 던지고, 그 예외는 async 메서드의 Task 에 담깁니다.

실행 검증

동기화 문맥 — 이어 달리기가 돌 자리 C# 5.0

왜 — 표준은 동기화 문맥을 "a representation of “where” the current thread is running" 이라 부르고, 정확한 정의는 구현에 맡깁니다. .NET 의 await 는 멈출 때 현재 SynchronizationContext 를 기억했다가, 이어 달리기를 그 문맥의 Post 로 보냅니다.

문맥이 없으면 이어 달리기는 Main 이 아닌 스레드에서 곧바로 돕니다. Loop 문맥이 있으면 Post 가 한 번 불리고, 이어 달리기는 Loop 를 돌리는 Main 의 스레드에서 돕니다. await 뒤의 코드가 "원래 있던 곳" 으로 돌아온 것입니다.

실행 검증

ConfigureAwait(false) — 문맥으로 돌아오지 않기

Task 의 ConfigureAwait(false) 는 문맥을 기억하지 않는 awaitable 을 돌려줍니다. 이어 달리기는 Task 를 완료시킨 쪽에서 돕니다.

false 쪽은 Post 가 0번이고, await 뒤의 SynchronizationContext.Current 도 비어 있습니다 — Loop 가 아닌 곳에서 이어졌기 때문입니다. ConfigureAwait 는 언어가 아니라 라이브러리의 메서드입니다. await 가 Task 말고도 모양만 맞으면 받아 주므로(앞) 이런 감싸개가 가능합니다.

실행 검증

교착 — 문맥 위에서 동기로 기다리면

한 스레드짜리 문맥 위에서 async 메서드의 결과를 Wait()·.Result 로 기다리면, 이어 달리기는 그 문맥으로 Post 되는데 문맥의 스레드는 기다리느라 멈춰 있습니다. 서로가 서로를 기다립니다.

진짜 .Result 였다면 영영 돌아오지 않습니다. 예제는 500ms 제한을 둔 Wait 로 False 를 받아 교착을 확인한 뒤, Loop 를 돌려 줄에 서 있던 이어 달리기를 풀어 줍니다. 결과는 시간에 기대지 않습니다 — 이어 달리기는 Loop 를 돌리기 전에는 돌 수 없습니다.

실행 검증

교착 풀기 — 라이브러리 쪽의 ConfigureAwait(false)

앞 예제와 한 줄만 다릅니다 — LibraryCall 의 await 에 .ConfigureAwait(false) 가 붙었습니다.

이어 달리기가 Loop 로 돌아오지 않으니 막힌 스레드와 상관없이 끝납니다. 하지만 이것은 땜질입니다 — 부르는 쪽이 Wait() 를 쓰지 않고 await 하면 문제가 처음부터 생기지 않습니다(5장).

실행 검증

4장 퀴즈 — 컴파일러가 만드는 것

Q. 직접 만든 형식 Later 를 await 할 수 있게 하려면 무엇이 필요합니까? 인터페이스를 하나 구현하면 됩니까?

A. Later 자신은 아무것도 구현하지 않아도 됩니다. 인자 없는 GetAwaiter() 인스턴스 메서드나 확장 메서드가 있으면 되고, 그것이 돌려주는 awaiter 가 INotifyCompletion 을 구현하며 bool IsCompleted 와 GetResult() 를 가지면 됩니다. 인터페이스가 요구되는 곳은 awaiter 쪽 하나뿐입니다.

잊힌 await — 경고가 나는 곳과 안 나는 곳

CS4014 는 Task 를 돌려주는 호출을 문장으로 쓰고 결과를 버릴 때 납니다. 결과를 변수에 담으면 경고가 없습니다.

함정 — var n 은 int 가 아니라 Task<int> 이고, 문자열로 찍으면 형식 이름이 나옵니다. 경고가 없습니다. var(4부)가 그 실수를 가립니다. 이 SDK 는 async 가 아닌 SyncCaller 에서도 CS4014 를 냈습니다 — 경고가 나는 범위는 버전마다 확인할 것.

async 람다가 async void 가 될 때

List<T>.ForEach 는 Action<T> 를 받습니다. 거기 넘긴 async 람다는 Task 를 돌려줄 곳이 없어 async void 가 됩니다(3장). Loop 문맥 위에서 차례를 고정해 확인합니다.

ForEach 는 일이 하나도 끝나기 전에 돌아왔고, 누구도 그 셋을 기다릴 수 없습니다. Select 는 Func<int, Task> 로 람다를 받아 Task 를 남기므로 WhenAll 로 모아 기다릴 수 있습니다.

실행 검증

Action 이냐 Func<Task> 냐 — 오버로드가 고르는 것

같은 이름의 메서드가 Action 과 Func<Task> 를 받으면, async 람다는 Func<Task> 쪽으로 갑니다. Action 하나뿐이면 async 람다는 말없이 async void 가 됩니다.

함정 — OnlyAction 은 람다가 끝나기 전에 돌아왔습니다. 받는 쪽 시그니처가 Action 이면 넘기는 쪽의 async 는 "기다릴 수 없음" 을 뜻합니다. 람다 쪽만 보고는 알 수 없습니다.

동기로 기다리기 — 문맥이 없으면 되고, 있으면 막힌다

콘솔 프로그램의 Main 에는 동기화 문맥이 없어서 .Result 가 그냥 됩니다. 같은 코드를 문맥이 있는 곳으로 옮기면 교착입니다(4장). 고치는 길은 부르는 쪽도 async 로 만들어 위로 올리는 것입니다.

"콘솔에서는 됐는데" 가 이 함정의 이름입니다. 셋째 줄의 Caller 는 Loop 의 스레드를 막지 않고 await 하므로, 이어 달리기가 Loop 로 돌아와 끝납니다.

늦게 터지는 인자 검사

async 메서드의 첫 줄에서 던진 예외도 Task 에 담깁니다(3장). 그래서 잘못된 인자가 부르는 순간이 아니라 기다리는 순간에야 드러납니다.

고치는 길은 검사를 async 가 아닌 겉 메서드로 빼는 것입니다. LengthChecked 는 Task 를 돌려주지만 async 가 아니므로 던진 예외가 그 자리에서 나갑니다. 반복기의 인자 검사 함정(3부)과 같은 모양입니다.

실행 검증

StartNew 와 async 람다 — 겉 Task 만 끝난다

Task.Factory.StartNew 는 async 를 모릅니다. Task<int> 를 돌려주는 람다를 받으면 결과는 Task<Task<int>> 이고, 겉 Task 는 람다가 안쪽 Task 를 돌려준 순간 끝납니다.

outer 는 RanToCompletion 인데 안쪽은 아직 기다리는 중입니다. Task.Run 은 Task 를 돌려주는 람다를 알아보고 한 겹으로 펴 주므로, 200ms 를 기다려도 False — 안쪽이 끝나야 끝납니다.

실행 검증

WhenAll 의 실패 여럿 — await 는 첫 번째만 던진다

await 는 Task 의 예외를 "원래 형식으로" 다시 던지므로(3장) 하나만 고릅니다. 나머지는 Task 의 Exception 안에 있습니다.

실패를 모두 기록해야 하면 catch 안에서 all.Exception.InnerExceptions 를 봅니다. 순서는 인자의 차례입니다.

실행 검증

WhenAll 의 결과는 끝난 차례가 아니라 인자 차례

Task 를 직접 완료시켜 차례를 고정했습니다. 끝난 순서와 상관없이 결과 배열은 넘긴 순서입니다. 빈 목록을 넘기면 이미 끝난 Task 를 받습니다.

실행 검증

WhenAny 는 Task 를 돌려준다 — 실패해도 던지지 않는다

WhenAny 의 결과는 "먼저 끝난 Task" 입니다. 그 Task 가 실패했어도 await any 는 던지지 않습니다. 결과를 꺼내려면 한 번 더 await 해야 합니다.

진 쪽(a)은 취소되지 않고 계속 기다립니다. 시간 제한을 WhenAny 로 만들면 늦은 작업은 그대로 남아 돕니다 — 멈추려면 취소 토큰이 따로 필요합니다.

실행 검증

취소는 협조다 — 확인하는 곳에서만 멈춘다

Cancel() 은 요청일 뿐입니다. 메서드가 토큰을 확인하는 곳에 와야 멈춥니다.

둘째 단계는 끝까지 돌았고, 셋째 단계의 맨 앞 확인에서 멈췄습니다. .Result 로 기다리면 안의 예외가 TaskCanceledException 으로 보입니다 — 메서드가 던진 것은 OperationCanceledException 이었지만 (3장), 취소된 Task 를 동기로 기다리면 .NET 10 은 이렇게 알립니다.

실행 검증

토큰을 받는 API — 기다림 자체를 끊기

BCL 의 비동기 메서드 가운데에는 토큰을 받아 기다림을 직접 끊는 것이 있습니다. Task.Delay(Timeout.Infinite, ct) 는 영원히 기다리다가 취소되면 끝납니다.

이미 취소된 토큰을 Task.Run 에 넘기면 대리자가 한 번도 돌지 않고 Task 가 Canceled 가 됩니다.

async 는 시그니처가 아니다 — 구현의 선택

인터페이스는 Task<int> 를 돌려준다고만 약속합니다. 구현은 async 로 써도 되고, 이미 끝난 Task 를 보통 메서드로 돌려줘도 됩니다. 부르는 쪽에서는 구별되지 않습니다.

null Task 를 await 하면
