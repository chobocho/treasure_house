ref readonly 매개변수 — 변수를 달라고 말하는 참조

왜 · 부르는 쪽 규칙 · 경고 넷 · 메타데이터 · API 옮기기 · C# 11 소비자 · .NET 10 · 깨지는 변경 · 오버로드 · 대리자 · 선언 규칙

왜 — in 은 임시 변수도 조용히 받는다

제안서의 동기: in 매개변수는 "allow both lvalues and rvalues and can be used without any annotation at the callsite. However, APIs which capture or return references from their parameters would like to disallow rvalues and also enforce some indication at the callsite that a reference is being captured." 받은 참조를 붙잡아 두는 API 를 C# 11 의 ref 필드(12부)로 만들어 봅니다.

x = 42 뒤에 a·b 는 42 를 봅니다 — x 자체를 붙잡았습니다. c·d 는 1 과 5 에 머뭅니다. 값(x + 0, 5)을 넘기면 컴파일러가 숨은 임시 변수를 만들어 그 참조를 넘기기 때문입니다(8부). 네 줄 모두 경고 하나 없이 컴파일됩니다. 부르는 사람은 View 가 무엇을 붙잡는지 호출 모양만으로는 알 수 없습니다.

실행 검증

ref readonly 매개변수 (ref readonly parameters) C# 12.0

왜 — whats-new: "The addition of ref readonly parameters enables more clarity for APIs that might be using ref parameters or in parameters". 발표 글은 한 줄로 줄입니다 — "An argument to a ref readonly parameter must be a variable."

부르는 쪽은 in 과 ref 를 둘 다 쓸 수 있습니다. 어느 쪽이든 읽기 전용 참조로 받습니다. static readonly 필드는 ref 로 넘길 수 없으니 in 으로 넘깁니다. C# 11.0 의 거절은 매개변수 선언 한 곳, 기능 이름은 ref readonly parameters 입니다.

실행 검증

수식어를 빼거나 값을 넘기면 — 오류가 아니라 경고

제안서의 요약표에서 ref readonly 매개변수는 수식어 없는 인수와 rvalue 에 "Warning" 입니다. 처음에는 오류로 정했다가 "later e-mail discussions relaxed this because we would lose the ability to change existing APIs without breaking users" 였습니다.

셋 다 프로그램은 돕니다. W1 은 수식어만 빠졌을 뿐 x 자체가 넘어가 마지막 값이 42 입니다. W2 는 임시 변수가 넘어가 1 입니다 — 앞에서 본 c 와 같은 일이 이번에는 CS9193 경고와 함께 일어납니다. W3 은 번호가 다릅니다(CS9195). readonly 필드에는 ref 를 쓸 수 없으니 컴파일러가 in 만 권합니다. 코드는 앞 장에 있습니다.

실행 검증

제안서의 표 — 부르는 쪽 수식어와 매개변수

제안서 첫머리의 표를 옮깁니다. 굵게 적힌 칸이 C# 12 가 바꾼 곳입니다.

부르는 쪽ref 매개변수ref readonlyinout
ref됨됨경고오류
in오류됨됨오류
out오류오류오류됨
수식어 없음오류경고됨오류
rvalue(값)오류경고됨오류

기존 규칙이 바뀐 칸은 하나입니다 — in 매개변수에 ref 인수를 쓰면 오류였는데 경고가 됐습니다. 제안서는 이 줄을 따로 "there is one change to the existing rules" 라고 적습니다. 이 한 칸이 깨지는 변경의 씨앗입니다. 다음 장이 표를 컴파일러로 확인합니다.

문서 근거

표를 컴파일러로 — 진단이 없는 조합과 있는 조합

제안서: ref 수식어를 허락해도 "nothing changes w.r.t. value kind checks" — ref 는 여전히 대입할 수 있는 변수에만, 읽기 전용 참조는 in 으로 넘깁니다.

표의 "경고" 칸인 In(ref x) 는 CS9191 이고, 문장이 직접 "Consider using 'in' instead" 라고 권합니다. A5 는 표가 아니라 값 종류 규칙에 걸립니다 — readonly 필드는 ref 로 못 넘깁니다. A2–A4 의 오류 셋(CS1615·CS1620·CS8156)은 장 끝의 표에 모았습니다.

실행 검증

메타데이터 — IsReadOnly 대신 RequiresLocation

제안서: ref readonly 는 "emitted as [in] T&, plus annotated with" RequiresLocationAttribute 이고, virtual 이면 modreq(InAttribute) 도 붙습니다. 그리고 "no [IsReadOnly] will be emitted" — "to make older compiler versions interpret ref readonly parameters as ref parameters".

in(8부)과 같은 점은 Int32&·InAttribute·virtual 쪽 modreq 입니다. 다른 점은 특성 하나 — IsReadOnlyAttribute 자리에 RequiresLocationAttribute 가 있습니다. 옛 컴파일러는 이 특성을 모르니 그저 ref 매개변수로 봅니다. 그래서 ref 를 ref readonly 로 바꾼 라이브러리를 옛 컴파일러로 불러도 소스가 깨지지 않습니다.

실행 검증

API 옮기기 — ref 와 in 을 ref readonly 로

whats-new: in 이 없던 시절의 API 가 읽기만 하면서 ref 를 받았다면 "can be updated with ref readonly. It won't be a breaking change for callers, as would be if the ref parameter was changed to in." 제안서: in → ref readonly 도 "would not be a breaking change (but no callsite annotation or rvalue would result in a warning)".

세 호출의 결과가 같고 오류도 없습니다. ref 였던 Peek 는 아무 소리도 나지 않고, in 이었던 Sum 은 수식어 없는 호출 하나에만 경고 CS9192 가 붙습니다 — "이 API 는 변수를 원한다" 는 신호입니다. 제안서는 virtual 메서드라면 메타데이터의 modreq 때문에 이진 호환이 깨진다고 덧붙입니다(앞 장).

실행 검증

C# 11 로 컴파일하는 쪽 — .NET 10 의 ref readonly 를 부르면

제안서: 새 컴파일러도 "with LangVersion <= 11" 이면 옛 컴파일러와 맞추려고 "an error will be emitted that ref readonly parameters are not supported unless the corresponding arguments are passed with the ref modifier".

선언은 라이브러리에 있고 이 파일에는 ref readonly 라는 낱말이 없는데도 거절은 기능 이름 ref readonly parameters 입니다. C# 11 의 문법으로 넘길 수 있는 길은 ref 하나입니다. 그래서 in → ref readonly 는 C# 11 이하로 컴파일하는 소비자에게는 소스가 깨지는 변경입니다. 8부가 -langversion:7.2 에서 Unsafe.AsRef(in …) 를 거절당한 것이 같은 일입니다.

실행 검증

같이 온 런타임 — .NET 10 에서 ref readonly 를 받는 API

whats-new 는 옮겨 갈 만한 API 로 셋을 꼽습니다 — Marshal.QueryInterface(ref 였던 것), ReadOnlySpan<T> 생성자(in 이었지만 변수가 필요한 것), Unsafe.IsNullRef(바꾸지 않는데 ref 였던 것).

이 기계의 .NET 10 런타임(10.0.12) System.Private.CoreLib 에서 54개 매개변수, 메서드 이름으로 26가지입니다. ReadOnlySpan 생성자와 Unsafe.IsNullRef 는 옮겨 갔지만 QueryInterface 의 iid 는 ref readonly 가 아니라 in(rr=False)입니다 — whats-new 가 "Those APIs can be updated" 의 예로 든 그 API 입니다(2026-10 기준). Volatile.Read·Interlocked.Read 처럼 "주소가 필요하지만 쓰지는 않는" 원자적 읽기도 목록에 있습니다.

실행 검증

깨지는 변경 — ref 인수가 in 매개변수에도 맞는다 C# 12.0

왜 — Roslyn 문서: 이 기능이 "relaxed overload resolution allowing ref arguments to be passed to in parameters when LangVersion is set to 12 or later" 이고, 그래서 동작도 소스도 깨질 수 있습니다. 예제의 C·E·K 는 문서의 것입니다.

같은 소스, 같은 컴파일러에서 언어 버전만 바꿨더니 첫 줄이 E 에서 C 로 바뀝니다. C# 12 에서는 인스턴스 메서드 C.M(in int) 가 경고와 함께 후보가 되고, 후보가 있으면 확장 메서드는 찾지 않습니다. BAD 는 C# 11 에서 1 을 찍다가 C# 12 에서 CS0121 로 모호해집니다. 둘 다 문서의 우회로(정적 호출, 캐스트)는 버전과 상관없이 같은 답입니다.

실행 검증

오버로드 — 값이 먼저, in 과 ref readonly 는 서로 모호

제안서: 수식어가 없으면 "By-value overloads will be preferred over ref readonly overloads" — in 과 같습니다. in 판과 ref readonly 판이 겹치는 예는 제안서가 "currently results in three ambiguity errors" 라고 적고, 풀어 줄 규칙은 "Pending LDM review" 절에 — "None of the following options were implemented in C# 12."

수식어 없는 V(i) 는 값 판, in·ref 를 쓰면 ref readonly 판입니다. 제안서의 M 은 C# 14 에서도 CS0121 입니다 — 2026-10 기준 제안된 우선순위 규칙은 들어오지 않았습니다. BAD3(수식어 없이)도 같은 오류입니다.

실행 검증

대리자 변환 — 어긋난 ref 종류는 경고 CS9198 하나로

제안서: 변환에서 ref readonly 대상은 대리자의 in·ref 와, in 대상은 ref readonly·ref 와 맞을 수 있되 "any allowed conversion between different modifiers results in a warning". 다만 "ref parameter of the target method is not allowed to match in nor ref readonly parameter of the delegate."

경고 네 개가 모두 같은 번호입니다. 막힌 쪽은 대상이 ref 인 경우 — 람다는 CS1676(BAD, 표), 메서드 그룹은 CS0123 입니다. 이유는 제안서의 "Pending LDM review" 절에 있습니다. 그것을 허락하면 in 대리자로 readonly 필드를 고칠 수 있어서 "changes value of f even though it is readonly!" 가 됩니다.

실행 검증

둘 수 있는 곳 — 인덱서는 되고 연산자는 안 된다

제안서: ref readonly 는 "allowed for indexer parameters (like in but unlike ref), but disallowed for operator parameters (like ref but unlike in)". 기본값은 rvalue 를 넘기는 것과 같아 "allowed ... with a warning" 입니다. 확장 메서드의 수신자에는 수식어 없음 경고를 내지 않습니다.

v.Get() 은 수신자에 수식어를 쓸 수 없는 자리라 경고가 없습니다. 기본값 경고 CS9200 은 "Consider declaring the parameter as 'in'" 이라고 대안을 댑니다. [RequiresLocation] 을 손으로 붙이면(BAD2) CS8335, 매개변수에 대입하면(BAD3) in 과 같은 CS8331 입니다(표).

실행 검증

6장의 진단 한눈에

이 장의 거절·경고 캡처에서 첫 오류(없으면 첫 경고)의 번호와 문장을 뽑았습니다. 새 번호는 CS919x·CS9200 대의 경고들이고, 오류는 대부분 ref·in 시절의 것을 그대로 씁니다.

C# 12 가 새로 만든 진단은 경고뿐입니다 — 제안서가 "warning" 으로 정한 칸 그대로입니다. 오류 칸은 in 매개변수(8부)의 규칙을 물려받았습니다.

실행 검증

6장 퀴즈 — ref readonly 매개변수

Q. 라이브러리가 static int Sum(in int p) 를 static int Sum(ref readonly int p) 로 바꿨습니다. 소비자의 Sum(x) 는 -langversion:12.0 과 -langversion:11.0 에서 각각 어떻게 될까요?

A. C# 12.0 에서는 경고 CS9192("should be passed with 'ref' or 'in' keyword")와 함께 컴파일되고 같은 값을 냅니다(옮기기). C# 11.0 에서는 오류 CS9058 입니다 — 옛 컴파일러와 맞추려고 ref 인수만 허락합니다(C# 11 소비자). 그래서 제안서는 in → ref readonly 를 옛 컴파일러와 C# 11 이하로 컴파일하는 소비자에게만 소스가 깨지는 변경으로 적습니다.

인라인 배열 — unsafe 없는 고정 크기 버퍼

고정 크기 버퍼의 한계 · [InlineArray] · 크기와 원소 형식 · 인덱스와 범위 · 스팬 변환 · 컴파일러의 도우미 · foreach · 규칙 · 못 하는 것 · .NET 10

왜 — C# 11 까지 구조체 안의 배열은 unsafe 였다

제안서의 동기는 첫 문장이 전부입니다 — "This proposal plans to address the many limitations of" 고정 크기 버퍼. 표준의 고정 크기 버퍼는 unsafe 문맥에서만, 원소는 기본 형식만 됩니다. 발표 글: 그런 기법은 "required that your assembly enable unsafe code."

p.Data 는 배열이 아니라 byte* 입니다. 그래서 스팬으로 바뀌지 않고 길이도 범위 검사도 없습니다. 원소 형식은 오류 문장이 늘어놓는 열둘뿐입니다. 3부가 이 버퍼의 후계자로 인라인 배열을 미리 봤습니다.

실행 검증

인라인 배열 (inline arrays) C# 12.0

왜 — whats-new: "Inline arrays enable a developer to create an array of fixed size in a struct type." 그리고 "You likely won't declare your own inline arrays, but you use them transparently when they're exposed as" Span<T>·ReadOnlySpan<T>. 예제의 Buffer 와 두 반복문은 whats-new 의 것입니다.

필드는 _element0 하나인데 원소가 열 개입니다. 개수는 특성이, 원소 형식은 그 필드가 정합니다. 스팬을 뒤집으면 buffer[0] 이 9 가 됩니다 — 스팬은 복사본이 아니라 구조체 자신을 가리킵니다. C# 11.0 의 거절은 쓰는 곳 넷이고 선언은 그대로입니다(1장).

실행 검증

크기와 원소 형식 — 런타임이 늘려 주는 구조체

제안서: 런타임이 이런 형식에 "special type layout" 을 줍니다 — 크기는 원소 N 개가 들어가게 늘리고, 원소는 "laid out sequentially in memory as though they are elements of an array", 그리고 "Runtime provides regular GC tracking for all elements in the struct." 언어는 원소 접근을 스팬으로 하므로 "element types that can be used as a type argument" 로 한정됩니다.

Ints 와 Fixed 가 똑같이 32 바이트입니다 — 메모리 모양은 고정 크기 버퍼와 같습니다. 다른 점은 원소 형식입니다. string 셋(참조 셋, 이 기계에서 24 바이트)과 제네릭 Buf<T> 도 됩니다. GC.Collect() 뒤에도 "Ada" 가 살아 있는 것은 GC 가 원소의 참조를 안다는 뜻입니다. 리플렉션이 보는 필드는 여전히 하나입니다.

실행 검증

인덱스와 범위 — 상수는 컴파일할 때, 변수는 실행할 때 검사

제안서: 인수는 int, System.Index, System.Range 로 바뀔 수 있으면 되고, 범위는 Span<T> 의 Slice 가 됩니다. "Indexing into an inline array with a constant expression outside of the declared inline array bounds is a compile time error." 범위도 "Compiler can also report an error".

길이를 컴파일러가 아니까 ^1 은 7, ^8 은 0 번 원소입니다. b[2..5] 는 같은 메모리 위의 스팬이라 mid[0] 을 고치면 b[2] 가 바뀝니다. 변수 인덱스는 배열처럼 IndexOutOfRangeException, 상수는 인덱스도 범위도 같은 CS9166 입니다.

실행 검증

스팬으로 바뀌는 규칙 — 쓸 수 있는 변수만 Span

제안서는 새 변환 "inline array conversion" 을 더합니다 — Span<T>·ReadOnlySpan<T> 으로. "However, converting a readonly variable to System.Span<T> or converting a value to either type is an error."

Sum(b) 처럼 인수 자리에서도 변환이 됩니다. 값(Get() 의 결과)은 원소 하나를 읽는 것(Get()[0])은 되지만 스팬은 안 됩니다 — 스팬이 가리킬 자리가 없기 때문입니다. 두 오류의 번호는 인라인 배열 전용(CS9164·CS9165)입니다.

실행 검증

컴파일러가 만든 도우미 — 제안서는 둘, 실제는 넷

제안서: 스팬은 MemoryMarshal.CreateSpan(ref Unsafe.As<TBuffer, TElement>(ref buffer), size) 로 얻고, IL 을 줄이려고 "two generic reusable helpers" — InlineArrayAsSpan·InlineArrayAsReadOnlySpan — 를 "private implementation detail type" 에 둘 수 있습니다.

제안서의 둘에 더해 InlineArrayElementRef·InlineArrayFirstElementRef 가 있습니다. 원소 하나에 쓰는 b[1] = 5 는 스팬을 만들지 않고 원소의 참조를 바로 얻습니다. 0 번 원소는 오프셋 계산조차 없는 따로 된 도우미입니다. 컬렉션 식이 합성하는 인라인 배열 형식은 4장이 봤습니다.

실행 검증

foreach — 스팬 위를 돈다, 그래서 ref 도 된다

제안서: 인라인 배열의 foreach 는 스팬으로 바꾼 것과 "is equivalent to" 입니다 — 값이면 임시 변수에 담아 ReadOnlySpan, 쓸 수 있는 변수면 Span, 읽기 전용이면 ReadOnlySpan.

제안서의 예에는 없지만 스팬 번역에서 따라 나오는 일 셋. 첫째, foreach (ref int x in field) 가 원소에 씁니다(21). 둘째, field 를 도는 동안 field[2] = 100 을 쓰면 세 번째 원소로 100 이 나옵니다 — 복사 없이 필드 위를 돕니다. Get() 의 결과는 시작할 때의 복사본이라 도는 동안 field[2] = 5 를 써도 100 이 나옵니다. 셋째, 값 위에서는 ref 로 돌 수 없습니다(CS1510).

실행 검증

[InlineArray] 의 규칙 — 언어 버전과 상관없이 검사한다

nameof 안의 인스턴스 멤버 C# 12.0

왜 — 언어 버전 기록: "Nameof accessing instance members: relaxes some restrictions on usage of instance members inside nameof (nameof(field.ToString))". whats-new 와 버전 기록의 C# 12 목록에는 이 항목이 없습니다(1장).

nameof 는 식을 계산하지 않으므로 인스턴스가 없는 정적 문맥에서도 이름만 꺼낼 수 있습니다. C# 11.0 은 세 곳 모두 기능 이름으로 거절합니다 — 필드 초기화자 하나, 메서드 안의 둘. 7부는 정적 메서드 안의 경우를 봤습니다.

실행 검증

특성 인수 안에서 — 쓸모가 가장 큰 자리

특성의 인수는 상수여야 하고, 특성은 형식 선언에 붙으니 인스턴스가 없습니다. nameof 의 결과는 상수 문자열이라 이 자리에 들어갈 수 있습니다. 언어 버전 기록의 예 nameof(field.ToString) 과 같은 꼴을 특성 안에 둡니다.

특성에 박힌 문자열은 "Length" 입니다. 멤버 이름을 바꾸면 컴파일러가 같이 따라오게 하려는 것이 nameof 의 목적이고, 특성 인수가 그런 문자열이 가장 많이 사는 곳입니다. 메서드에 붙인 특성 안에서 매개변수 이름을 쓰게 한 것은 C# 11 의 범위 확장이었습니다(12부).

실행 검증

형식 이름으로 시작하면 — C# 6 부터 됐다

막혀 있던 것은 "인스턴스 멤버를 거친다" 가 아니라 "단순 이름으로 시작하는 인스턴스 멤버를 거친다" 였습니다. 같은 경로를 형식 이름부터 적으면 옛 언어 버전에서도 됩니다.

Person.Name.Length 는 nameof 가 처음 나온 C# 6 에서 그대로 됩니다. 단순 이름 Name.Length 만 거절되고, C# 6 의 거절 번호는 CS8059, C# 11 은 CS9058(앞의 캡처)이지만 기능 이름은 같습니다 — 번호는 언어 버전대에 따라 다른 문장 틀입니다. C# 12 의 변화는 이 두 꼴을 같게 만든 것입니다.

실행 검증

C# 12 에서도 안 되는 nameof

풀린 것은 "인스턴스 멤버에 닿는 경로" 입니다. 경로가 아닌 식은 여전히 이름이 없습니다.

호출 결과에는 이름이 없고(CS8081), 원소 접근은 하위 식이라 안 됩니다(CS8082). this 는 nameof 밖에서와 같은 이유로 정적 문맥에서 거절됩니다(CS0026) — C# 12 는 this 없이 쓸 수 있게 했을 뿐 this 를 허락하지는 않았습니다.

[Experimental] 특성 C# 12.0

왜 — 발표 글: 피드백을 받거나 한 주기에 끝낼 수 없는 기능을 내보낼 때 "we want to make it clear that we are not yet committed to the feature or the implementation." 제안서: 진단은 "technically a warning, so that the compiler allows suppressing it" 이지만 "it is treated as an error for purpose of reporting".

진단 번호는 컴파일러의 CS 번호가 아니라 특성에 적은 MY001 이고, 줄은 error 입니다. whats-new 는 이 진단을 "issues a warning" 이라고 적지만 캡처의 줄은 error 입니다 — 위의 제안서 문장("treated as an error") 쪽이 맞습니다. 문장 끝의 "Suppress this diagnostic to proceed." 는 제안서의 문장 틀에 없는 꼬리입니다. 13부 퀴즈 (1) — 게이트

Q. C# 12 기능 가운데 -langversion:11.0 으로 내려도 똑같이 동작하는 것을 이 부에서 둘 고르면?

A. 예를 들어 인터셉터(C# 7.3 에서도 -21, 8장)와 [Experimental](C# 7.3 에서도 error MY001, 8장). 메서드 그룹의 기본값(5장)과 await using 의 새 규칙(1장)도 언어 버전에 묶이지 않았습니다. 반대로 ref 인수와 in 매개변수의 새 규칙은 언어 버전에 묶여 C# 11 에서 답이 다릅니다(6장).

13부 퀴즈 (2) — 같은 꼴, 다른 뜻

Q. [InlineArray(3)] struct B { int _e; } 의 변수 b 를 foreach (var x in b) 로 도는 동안 b[2] = 9 를 쓰면 세 번째 x 는 9 일까요? b 대신 B 를 돌려주는 메서드 Get() 을 돌면요?

A. 변수를 돌 때는 9 입니다 — foreach 가 그 변수 위의 Span 을 돌기 때문입니다. Get() 은 값이라 시작할 때 임시 변수에 복사되고 그 위의 ReadOnlySpan 을 돌므로 바뀌지 않습니다(7장의 7 7 100 | 7 7 100).

13부 퀴즈 (3) — 경고와 오류

Q. static int Peek(ref readonly int r) 에 Peek(5) 를 넘기면 오류일까요, 경고일까요? 같은 매개변수가 ref int r 이었다면요?

A. ref readonly 면 경고 CS9193 이고 임시 변수의 참조가 넘어갑니다(6장). ref 였다면 오류입니다. 제안서는 처음에 오류로 정했다가 기존 API 를 깨지 않고 옮기려고 경고로 낮췄습니다 — 그래서 ref → ref readonly 는 호출하는 쪽을 깨지 않고, in → ref readonly 는 C# 12 이상으로 컴파일하는 쪽에 경고만 늘립니다(6장, C# 11 이하는 깨짐).
