9부를 읽는 법

버전 기록은 C# 8.0 을 "the first major C# release that specifically targets .NET Core" 라고 소개합니다. 기능 몇은 새 CLR 기능에, 몇은 .NET Core 에만 들어간 라이브러리 형식에 기댑니다. 언어 버전이 런타임과 처음으로 묶인 것입니다.

그리고 이 버전의 가장 큰 기능은 문법이 아니라 경고입니다. nullable 참조 형식은 프로그램의 동작을 하나도 바꾸지 않고, 컴파일러가 null 을 따라가며 경고만 냅니다. 1장–2장의 대부분이 그 이야기입니다.

  • 1장 — C# 8.0 개관. 게이트 스물둘, 런타임에 묶인 버전, 같이 온 형식, 컴파일러에게 언어 버전 묻기.
  • 2장 — nullable 참조 형식. 켜는 법과 두 문맥, 같은 런타임 형식, 흐름 분석과 경고, !, 제네릭과 notnull, 특성, BCL 의 주석, 옮기는 법.
  • 3장 — 패턴의 확장. switch 식, 속성·위치·튜플 패턴, 재귀 패턴. switch 식부터.
  • 4장 — 인덱스와 범위. ^1 과 1..3, System.Index · System.Range. 인덱스부터.
  • 5장 — 비동기 스트림과 using. await foreach, await using, using 선언. 비동기 스트림부터.
  • 6장 — 기본 인터페이스 메서드. 6장.
  • 7장 — 작은 기능들. readonly 멤버, static 지역 함수, ??= 그리고 나머지. 7장.
  • 8장 — 9부 정리.

이 부의 예제는 -langversion:8.0 으로 컴파일하고, 게이트가 있는 기능은 C# 7.3 으로 내린 거절을 옆에 둡니다. nullable 예제는 파일 첫머리에 #nullable enable 을 적어 두어 캡처의 명령 줄만 보고도 조건을 알 수 있게 했습니다.

형식이 없는 대상에서 8.0 을 강제하면 — 여기서는 못 보인다

왜 — 시그니처가 말하지 않는 null

"Building C# 8.0" 은 이 기능의 목적을 "help prevent the ubiquitous null reference exceptions that have riddled object-oriented programming for half a century now" 라고 적었습니다. 제안서의 목표는 두 줄입니다 — 참조 형식의 변수·매개변수·결과가 null 이어도 되는지 의도를 적게 하고, 그 의도대로 쓰지 않으면 경고한다.

string Find(int) 라는 시그니처만 보고는 null 이 올 수 있는지 알 수 없습니다. 컴파일러도 모릅니다. 문제는 19행에서 실행 중에야 드러납니다. 다음 장은 같은 프로그램을 C# 8.0 으로 옮깁니다.

nullable 참조 형식 (nullable reference types) C# 8.0

왜 — whats-new: nullable 주석 문맥 안에서는 모든 참조 형식 변수가 null 이 아닌 참조 형식(nonnullable reference type)으로 여겨지고, null 일 수 있다고 적으려면 형식 이름 뒤에 ? 를 붙입니다. 컴파일러는 흐름 분석으로 그 약속을 검사합니다.

반환 형식의 ? 하나로 "null 이 올 수 있다" 가 시그니처의 일부가 됐습니다. 호출하는 쪽은 ?. 나 != null 로 확인한 뒤에만 Length 를 씁니다. C# 7.3 의 거절은 2행의 지시문 하나로 보고됩니다. 컴파일러 소스는 이 게이트에 "syntax and semantic check" 라고 적어 둡니다.

켜야 켜진다 — 프로젝트의 <Nullable>

이 기능은 기존 코드에 새 경고를 쏟아 내므로 "you have to opt in" — 프로젝트, 파일, 심지어 줄 단위로 켜도록 했다고 글은 적습니다. 프로젝트 단위는 csproj 의 속성입니다.

C# 7.3 의 거절은 소스의 줄이 아니라 옵션에 붙은 오류(CS8630)입니다 — 파일 이름도 줄 번호도 없습니다. 이 덱의 다른 예제는 <Nullable>disable 로 두고 파일마다 #nullable 을 적었습니다.

두 문맥 — 주석 문맥과 경고 문맥 C# 8.0

명세: 소스의 모든 줄에는 nullable 주석 문맥(annotation context)과 nullable 경고 문맥(warning context)이 있고, 프로젝트 설정이 없으면 둘 다 꺼져 있습니다. #nullable enable|disable|restore 뒤에 annotations 나 warnings 를 붙이면 하나만 바꿉니다.

주석만 켠 A·B 는 조용합니다 — ? 는 뜻을 갖지만 경고는 없습니다. 경고만 켠 C 는 ? 에 CS8632 를 받고도 p.Length 를 경고합니다. 경고만 켠 D 의 string 은 '모름'(oblivious)이라 null 을 돌려줘도 조용합니다. 둘 다 켠 E·F 만 두 경고를 다 받습니다.

프로젝트 단위의 네 값

명령 줄의 -nullable: 도 같은 네 가지를 받습니다 — enable, disable, warnings, annotations. 앞의 예제(string s = null; 과 string? t)를 나머지 셋으로 컴파일합니다.

꺼 두면 string s = null; 은 조용하고 string? 이 오히려 CS8632 를 받습니다. warnings 도 같은 결과입니다 — 주석 문맥이 꺼져 있어 string 이 '모름' 이기 때문입니다. annotations 는 아무 경고도 내지 않습니다. 명령 줄의 값은 csproj 값 뒤에 붙어 이깁니다(0부).

실행 검증

#nullable restore — 프로젝트 값으로 돌아가기

명세: restore 는 두 문맥을 "project settings" 로 되돌립니다. 그러니 같은 파일도 프로젝트 설정에 따라 다르게 컴파일됩니다.

restore 아래의 Name() 은 프로젝트가 꺼져 있으면 조용하고 켜져 있으면 CS8603 입니다. disable 이 아니라 restore 로 구간을 닫으면, 프로젝트가 나중에 켜졌을 때 그 파일도 같이 검사받습니다.

실행 검증

#pragma warning disable nullable — 명세에는 있지만

C# 8.0 명세는 #pragma warning 이 nullable 경고 문맥을 바꾸도록 넓혀진다고 적고, C# 9 의 명세는 #pragma warning disable nullable 을 예로 듭니다.

함정 — B(9행)는 disable nullable 안에 있는데도 경고를 받습니다. 그리고 컴파일러는 그 pragma 에 아무 말도 하지 않습니다. 경고를 실제로 끈 것은 번호를 적은 D(13행)뿐입니다. 이 컴파일러에서 소스 안의 경고를 끄려면 #nullable disable warnings 나 경고 번호를 쓰십시오.
실행 검증

명령 줄의 nullable — -nowarn 과 -warnaserror

소스의 pragma 와 달리 명령 줄의 경고 옵션은 nullable 을 경고 묶음 이름으로 받습니다. 앞 장의 파일 그대로입니다.

csproj 의 <WarningsAsErrors>nullable</WarningsAsErrors> 는 SDK 의 Microsoft.CSharp.Core.targets 가 컴파일러 작업(Csc)의 WarningsAsErrors 로 넘깁니다(SDK 10.0.112 의 162행). 이 덱의 csrun 은 csproj 의 그 속성을 읽지 않아 명령 줄 옵션으로 직접 넘겼습니다. 경고를 오류로 올려도 번호는 그대로 CS8602 입니다. 이미 옮긴 프로젝트가 다시 null 경고를 쌓지 않게 막는 장치입니다.

string? 과 string 은 같은 런타임 형식

표준: nullable 참조 형식과 그 짝의 차이는 "no semantic difference" 이고 둘은 "the same underlying type" 으로 표현됩니다. 둘 사이에는 항등 변환이 있습니다.

세 비교가 모두 True 입니다. ? 만 다른 두 메서드는 같은 시그니처라 CS0111 이고, 맨 바깥의 typeof(string?) 는 CS8639 로 거절됩니다 — 실행 중에 물을 수 있는 형식이 따로 없기 때문입니다. 형식 인수 안의 List<string?> 는 받아 줍니다.

그러면 ? 는 어디에 남나 — NullableAttribute

제안서는 nullable 표시를 메타데이터의 특성으로 남기자고 했습니다. "This means that downlevel compilers will ignore them." — 옛 컴파일러는 그냥 지나칩니다. 이 컴파일러가 실제로 남긴 것을 읽습니다.

구현의 세부라 바뀔 수 있는 것을 전제로 읽으십시오. 1 은 null 아님, 2 는 nullable 입니다. 메서드에는 가장 흔한 값(2)이 NullableContext(2) 로 한 번 붙고, 그와 같은 b 와 반환값에는 아무것도 붙지 않습니다. List<string?> 는 [1,2] — 바깥 형식부터 형식 인수 차례로 한 바이트씩입니다.

NullableAttribute 형식은 어디서 오나

앞 장의 특성 형식 자체를 따라가 봅니다. 이 어셈블리에 들어 있는 형식도 함께 늘어놓습니다.

.NET 10 에서는 NullableAttribute 가 System.Private.CoreLib 의 공개 형식이고, 컴파일러는 그것을 가져다 썼습니다 — 우리 어셈블리에는 C 와 App 뿐입니다. 그 형식 자신도 nullable 주석이 달린 채 컴파일됐고(NullableContext, Nullable), EditorBrowsable 로 편집기 목록에서 숨겨져 있습니다. 다른 대상 프레임워크에서 어떤지는 여기서 보일 수 없습니다.

실행 검증

꺼진 코드의 형식은 '모름' (oblivious)

명세: 주석 문맥이 꺼진 곳의 참조 형식은 oblivious 이고, 그런 형식은 null 을 넣어도 역참조해도 경고가 없습니다. 그 성질은 형식을 따라 "travels with it" 합니다.

켜진 Main 안에서도 Legacy 의 string 은 '모름' 이라, null 을 넘기는 것도, 그 결과를 string 에 넣고 역참조하는 것도 조용합니다. 아직 옮기지 않은 라이브러리를 부르는 코드는 nullable 을 켜도 보호받지 못합니다.

실행 검증

흐름 분석 — 변수마다 null 상태를 따라간다 C# 8.0

명세: 모든 식에는 null 상태(null state) — "not null" 또는 "maybe null" — 가 있고, 변수·필드·속성의 상태는 대입과 검사와 제어 흐름을 따라 정확한 대입 분석처럼 추적됩니다.

M 의 return p.Length 는 검사 뒤라 조용합니다. N 은 15행에서 한 번 경고를 받고, 바로 다음 줄의 string s = p; 는 조용합니다. 표준의 예가 같은 것을 설명합니다 — 15행이 지나갔다면 p 가 null 이 아니었다는 뜻이므로, 분석은 그 뒤의 p 를 "not null" 로 봅니다.

경고 번호가 셋으로 갈립니다. 무엇을 넣느냐(리터럴인가, 어쩌면 null 인 값인가)와 어디에 넣느냐(변수인가, 인수인가)에 따라서입니다.

번호무엇을 → 어디에

셋 다 경고라 프로그램은 컴파일되고 돌아갑니다. 표준은 nullable 진단이 "must be limited to warnings" 라고 못 박습니다. Environment.GetEnvironmentVariable 이 string? 을 돌려준다는 것은 .NET 10 라이브러리의 주석입니다.

돌려주는 null — CS8603

반환 형식이 string 이면 null 을 돌려주는 모든 길이 경고를 받습니다. 조건 연산자와 as 도 포함됩니다 — 명세는 as 식의 상태를 언제나 "maybe null" 로 적습니다.

경고는 셋, Find 만 조용합니다. 고치는 길은 둘 — 반환 형식을 string? 으로 바꿔 호출하는 쪽에 검사를 넘기거나, null 을 돌려주지 않게 하거나입니다. 어느 쪽이 맞는지는 컴파일러가 아니라 설계가 정합니다.

실행 검증

생성자를 나갈 때 비어 있는 필드 — CS8618

whats-new: 필드는 "must be initialized during construction" 이고, 어느 생성자나 초기화자도 채우지 않으면 경고합니다.

함정 둘 — 경고는 필드가 아니라 비운 생성자(12행)에 붙습니다. 그리고 문장이 "Consider adding the 'required' modifier" 를 권합니다. required 는 C# 11 의 기능인데, 이 캡처는 -langversion:8.0 입니다 — 진단 문장은 언어 버전이 아니라 컴파일러를 따릅니다. C# 8.0 에서는 그 권고를 따를 수 없습니다.
실행 검증

CS8618 을 푸는 네 길

필드마다 고르는 길이 다릅니다 — 초기화자, 모든 생성자에서 채우기, string? 로 인정하기, = null! 로 "나중에 채운다" 고 말하기(! 는 뒤에서 봅니다).

넷째 길은 경고만 끕니다. Init() 을 부르기 전의 D 는 여전히 null 이고, 그것을 아는 사람은 이제 컴파일러가 아니라 코드를 쓴 사람뿐입니다. C# 9 의 [MemberNotNull] 과 C# 11 의 required 가 이 자리를 줄이려고 들어옵니다.

분석이 알아듣는 null 검사들

표준은 null 검사의 예로 s == null, s?.Length, s?[4] 를 듭니다. 여덟 가지 꼴로 검사한 뒤 Length 를 씁니다.

경고가 하나도 없다는 것이 증거입니다. H 의 string.IsNullOrEmpty 는 언어가 아니라 메서드인데도 알아듣습니다 — 그 비밀은 BCL 의 주석에서 봅니다. C# 9 부터는 is not null 도 쓸 수 있습니다(10부).

실행 검증

언제나 null 이 아닌 식

명세는 null 상태가 언제나 "not null" 인 식을 늘어놓습니다 — this, 보간 문자열, new, typeof, nameof, 익명 함수, null 허용 식(x!), is 식.

o 가 null 이어도 $"{o}" 는 빈 문자열이지 null 이 아닙니다. this.ToString() 에만 ! 가 필요한 것은 그것이 식의 꼴이 아니라 .NET 10 의 주석(string?)을 따르기 때문입니다.

실행 검증

함정 — 검사가 '어쩌면 null' 을 가르친다

표준: 코드에 null 검사가 있으면 컴파일러는 그 값이 null 이었을 수도 있다고 추론할 수 있습니다. "Generally, when the code contains a null check, a compiler may infer that the value might have been null."

string s 로 선언했는데도 검사 뒤의 s.Length 가 CS8602 입니다. Len2 는 검사 결과를 출력에만 썼는데도 같습니다. 방어용 검사를 남기려면 검사한 갈래에서 끝내십시오 — throw 나 return 으로(공개 API 의 검사).

실행 검증

var 는 물음표가 붙은 형식

명세: "var infers an annotated type for reference types." — var s = ""; 의 var 는 string? 입니다. 대신 초기화 식의 null 상태(여기서는 not null)를 따라갑니다.

null 을 넣을 때 경고는 t 하나뿐입니다. var 변수에 null 을 넣는 것은 막지 않고, 다시 문자열을 넣은 뒤의 역참조도 조용합니다. var 로 선언하면 "null 을 넣지 말라" 는 약속은 사라지고, 흐름 분석만 남습니다.

실행 검증

형식 유추가 nullable 을 옮긴다

제안서: 형식 유추에서 기여하는 형식 하나라도 nullable 참조 형식이면 결과도 nullable 입니다. "In other words, nullness is propagated."

One(maybe) 는 List<string?> 를 만들어 List<string> 에 넣을 때 CS8619, new[] { "x", maybe } 는 string?[] 라 원소를 string 에 넣을 때 CS8600 입니다. 런타임의 형식은 둘 다 List<string>, string[] 그대로입니다(같은 형식).

실행 검증

함정 — 메서드 안을 들여다보지 않는 분석

분석은 메서드 하나 안에서 이뤄집니다. 부른 메서드가 필드를 바꿔도 모릅니다. 제안서의 지침도 이 기능이 "cannot guarantee" 한다고 적습니다 — 실행 중의 NullReferenceException 을 막아 준다는 보장은 없습니다.

box.Name != null 로 검사한 상태는 Clear() 를 불러도 그대로 "not null" 입니다. 명세가 추적한다고 적은 식은 box.Name 같은 멤버 접근의 사슬이고, 그 사이의 호출이 무엇을 하는지는 보지 않습니다.

실행 검증

함정 — 람다가 포착한 변수의 상태

명세: 람다와 지역 함수 안에서 포착한 변수의 상태는 그 함수를 "use" 하는 모든 곳 — 호출하거나 대리자로 바꾸는 곳 — 의 상태로 정합니다.

show 를 만드는 10행에서 s 는 not null 이라 람다 안이 조용하고, s 가 null 이 된 뒤 만든 12행의 람다만 경고를 받습니다. 그런데 터지는 것은 경고 없던 show() 입니다. 분석이 보는 것은 대리자를 만드는 순간이지 부르는 순간이 아닙니다.

실행 검증

Task<string?> 과 await

명세: await E 의 null 상태는 그 형식의 기본 상태입니다. Task<string?> 를 기다리면 maybe null, Task<string> 이면 not null 입니다.

await 한 결과를 string 에 넣으면 CS8600, 작업 자체를 Task<string> 에 넣으면 형식 인수가 어긋나 CS8619 입니다. Task<T> 는 클래스라 공변이 아니므로 List 와 같은 규칙을 받습니다.

실행 검증

형식 인수의 nullable 이 어긋날 때 — CS8619

제안서: C<S> 에서 C<T?> 로의 변환은 형식 매개변수가 공변(out)일 때를 빼고 경고하고, 반대 방향은 반변 (in)일 때를 빼고 경고합니다.

IEnumerable<out T> 로 보는 것은 조용하고, List<T> 끼리는 양쪽 다 경고입니다. 경고를 무시하고 별칭에 Add(null) 하면 — 같은 객체이므로 — "null 이 없는" names 에 null 이 들어갑니다. 런타임에는 두 형식이 같으니 아무것도 막지 않습니다.

실행 검증

함정 — Where 는 형식을 좁히지 않는다

흐름 분석은 람다 하나 안에서 끝납니다. Where(w => w != null) 의 검사는 다음 Select 람다로 이어지지 않습니다.

세 줄의 결과는 같지만 경고는 첫째에만 붙습니다. Where 의 결과는 여전히 IEnumerable<string?> 이기 때문입니다. OfType<string>() 은 형식 자체를 string 으로 바꿔 경고가 없고, 셋째는 ! 로 우리가 안다고 말한 것입니다 — ! 는 다음 장들에서 봅니다.

실행 검증

함정 — 배열 원소는 따라가지 못한다

제안서가 처음부터 인정한 구멍입니다. "We cannot adequately track that all elements of an array of non-null references are initialized."

new string[3] 은 null 셋을 담은 "null 아닌 string 의 배열" 인데 경고가 없습니다. ? 의 자리도 뜻이 다릅니다 — string?[] 는 원소가, string[]? 는 배열 자체가 null 일 수 있습니다. 표준은 nullable 주석이 배열 형식의 뜻만은 "significantly" 바꾼다고 적습니다.

실행 검증

함정 — default 와 구조체의 참조 필드

명세: default(T) 는 T 가 null 아닌 값 형식일 때만 "non-null" 이고, 그 밖에는 "maybe null" 입니다. 구조체의 기본값은 그 안의 참조 필드를 null 로 둡니다.

string s = default; 는 경고입니다. 구조체는 미묘합니다 — default 와 new Pair() 로 만든 지역 변수의 필드는 분석이 따라가 18행의 두 역참조를 경고하지만, 배열 원소 r[0].Key 는 따라가지 못해 경고 없이 터집니다.

실행 검증

.NET 10 의 주석이 경고를 정한다

버전 기록: nullable 참조 형식은 라이브러리에 null 의미가 주석으로 달려야 "much more useful" 하고, 그 주석이 .NET Core 라이브러리에 더해지는 중이라고 적었습니다. 같은 코드의 경고가 라이브러리의 주석에 따라 달라진다는 뜻입니다.

object.ToString() 도 .NET 10 에서는 string? 을 돌려준다고 주석이 달려 있어 경고를 받습니다. GetType().Name 과 string.Concat 은 null 아님으로 주석이 달려 조용합니다. 다른 버전의 라이브러리를 대상으로 하면 같은 소스의 경고 수가 다를 수 있습니다.

실행 검증

2장 중간 퀴즈 — 흐름 분석

Q. #nullable enable 인 파일에서 string s 매개변수를 받는 메서드가 첫 줄에 if (s == null) Log("null!"); 을 두고 다음 줄에 return s.Length; 를 씁니다. 경고가 있습니까? 있다면 왜입니까?

A. CS8602 경고가 있습니다. null 검사는 "이 값이 null 이었을 수 있다" 는 정보가 되어, 검사 뒤 s 의 상태가 maybe null 로 바뀝니다. 선언이 string 이어도 마찬가지입니다. 검사한 갈래를 throw 나 return 으로 끝내면 경고가 사라집니다. (검사가 가르친다)
설명용

null 허용 연산자 x! — 경고만 끈다 C# 8.0

왜 — 흐름 분석이 알아내지 못하지만 개발자는 아는 경우를 위해서입니다. 제안서는 이것을 "the 'damnit' operator" 라고도 불렀습니다. 명세: 뒤에 붙는 ! 는 "has no runtime effect" — 식의 null 상태만 바꿉니다.

경고는 하나도 없고, 약속을 어긴 b 는 15행에서 터집니다. ! 는 검사도 예외도 만들지 않습니다. 터지는 자리가 ! 를 쓴 12행이 아니라 역참조한 15행이라는 것도 눈여겨보십시오 — null 은 조용히 더 멀리 흘러갑니다.

실행 검증

null! 과 default! — 그리고 !! 는 안 된다

나중에 채울 필드의 CS8618 을 끄는 관용구가 = null! 입니다. 값은 여전히 null 이고, 컴파일러에게 "알고 있다" 고 말할 뿐입니다.

Init() 전의 Name 은 null 입니다(True). 명세는 ! 의 피연산자가 참조 형식이어야 한다고 적었지만 이 컴파일러는 int? 의 n! 도 경고 없이 받습니다. 두 번 겹친 m!! 은 CS8715 오류입니다.

실행 검증

제약 없는 T — null 일 수도, 아닐 수도

제안서: 제약 없는 형식 매개변수는 형식 인수가 nullable 일 수도 아닐 수도 있으므로 "treat the type parameter as both nullable and non-nullable, giving warnings when either is violated" 가 안전하다고 했습니다.

꼴 (나)(0부) — 언어 버전에 묶인 동작입니다. 16행 T t = default; 는 C# 8.0 에서는 조용하고 C# 9.0 에서는 CS8600 입니다. 나머지 경고는 둘이 같습니다. C# 8.0 에는 "T 의 nullable 판" 을 적을 문법이 없어서 지역 변수에 담는 것까지는 막지 않았고, T? 가 생긴 C# 9 는 그 자리를 경고합니다(다음 장).

실행 검증

뒤 버전 — 제약 없는 T? 는 C# 9

C# 9 의 제안: "In C#8, ? annotations could only be applied to type parameters that were explicitly constrained to value types or reference types. In C#9, ? annotations can be applied to any type parameter."

C# 8.0 으로 내리면 게이트 문장이 아니라 오류 CS8627 로 거절됩니다. 그 한 줄이 200칸을 넘어 이 덱의 캡처 폭에 들지 않으므로 싣지 않았습니다 — 실험 묶음은 매번 그 거절과 오류 번호를 확인만 하고 저장하지 않습니다. 형식 인수가 int 이면 T? 는 int? 가 아니라 int 입니다 — 그래서 0 이 찍힙니다. C# 8.0 에서 같은 뜻을 적는 길은 특성 [MaybeNull] 이었습니다(특성들).

실행 검증

class 와 class? 제약 C# 8.0

명세: class 제약에 nullable 짝 class? 가 생겼습니다. class 는 "nonnullable reference type", class? 는 "possibly nullable reference type" 을 뜻합니다.

명세 그대로 형식 인수의 nullable 은 제약을 만족하는지를 바꾸지 않고, 경고(CS8634)만 냅니다 — 13행도 컴파일되고 돌아갑니다. A 의 본문이 ToString()! 인 것은 .NET 10 의 ToString() 이 string? 이기 때문입니다.

실행 검증

notnull 제약 C# 8.0

왜 — class 는 참조 형식만, struct 는 값 형식만 받습니다. "값 형식이든 참조 형식이든 좋지만 null 은 안 된다" 를 적을 제약이 없었습니다. 제안 문서는 자리만 있는 "placeholder" 이고, C# 8.0 에 notnull 이라는 새 제약을 들였다는 한 문장뿐입니다.

이 파일에는 #nullable 이 없습니다. notnull 은 그래도 C# 8.0 의 문법이라 게이트에 걸리고, 컴파일러 소스는 그 게이트를 "semantic check" 라고 적습니다. 어기면 무엇이 나오는지는 다음 장에서 nullable 을 켜고 봅니다.

실행 검증

notnull 을 어기면 — 경고 CS8714

C# 9 명세: notnull 로 제약한 형식 매개변수는 "may not be a nullable type (nullable value type, nullable reference type or nullable type parameter)" 입니다. 어기면 어떻게 되는지는 컴파일러에게 묻습니다.

string? 뿐 아니라 int?(Nullable<int>)도 경고를 받습니다 — notnull 은 nullable 값 형식도 막습니다. 그래도 둘 다 만들어지고 돌아갑니다. 마지막 줄의 null! 도 그대로 들어갑니다. notnull 은 런타임 검사가 아닙니다.

실행 검증

notnull 은 메타데이터의 어디에

class 제약은 CLR 의 형식 매개변수 플래그(ReferenceTypeConstraint)입니다. notnull 은 어디에 남는지 리플렉션으로 봅니다.

NotNull<T> 의 플래그는 제약 없는 Plain<T> 와 같은 None 입니다. CLR 은 notnull 을 모르고, 컴파일러가 남긴 Nullable(1) 특성만 차이를 냅니다. Dictionary<TKey,…> 의 TKey 는 특성이 없지만 형식에 붙은 NullableContext(1) 을 물려받습니다 — .NET 10 의 Dictionary 는 열쇠에 notnull 을 단 것입니다. HashSet<T> 는 Nullable(2), 곧 제약이 없습니다.

실행 검증

제약 없는 T 에 ?? C# 8.0

왜 — C# 7.3 까지 ?? 의 왼쪽은 참조 형식이나 nullable 값 형식으로 알려져 있어야 했습니다. 제안 문서는 C# 8.0 이 "not known to be either a reference or value type (i.e. an unconstrained type parameter)" 인 왼쪽을 허락했다고 적습니다(역시 자리만 있는 문서입니다).

셋째 줄이 요점입니다. T 가 int 이면 0 은 null 이 아니므로 0 이 그대로 나옵니다 — "0 이면 기본값" 이 아닙니다. ?? 의 옛 규칙은 3부에서 봤습니다. 같은 버전의 ??= 는 7장입니다.

실행 검증

재정의 메서드에 적는 제약 C# 8.0

왜 — 재정의와 명시적 구현 메서드는 제약을 물려받으므로 적을 수 없었습니다. 그런데 nullable 참조 형식이 생기자 T? 가 Nullable<T> 인지 nullable 참조인지 가려야 했고, C# 8 은 재정의 메서드에 where T : class 와 where T : struct 를 적게 했습니다.

14행의 where 하나가 C# 7.3 에서 거절됩니다. 이 예제는 nullable 을 켜지 않으려고 struct 쪽만 적었습니다. 문서의 예는 같은 이름의 두 재정의(T? where T : struct 와 T? where T : class)를 나란히 둡니다 — 뒤쪽은 nullable 주석 문맥이 있어야 뜻을 갖습니다.

실행 검증

뒤 버전 — where T : default 는 C# 9

제약 없는 T? 가 C# 9 에서 생기자 재정의 쪽에는 class 도 struct 도 아닌 표시가 필요해졌습니다. "C#9 allows a new where T : default constraint." 재정의나 명시적 구현이 아닌 곳에 쓰면 오류입니다.

C# 8.0 으로 내리면 앞 장과 같은 CS8627 이 나와 캡처를 싣지 않았습니다(실험 묶음이 거절만 확인합니다). b.M<int>(1) 도 "any" 를 찍은 것은 M<int> 의 인수 1 이 int 라 int? 를 받는 struct 쪽보다 T 를 받는 쪽이 더 잘 맞기 때문입니다.

실행 검증

시그니처로 말할 수 없는 null 규칙 — 특성 C# 8.0

왜 — ? 하나로는 "true 를 돌려주면 null 이 아니다" 같은 규칙을 적을 수 없습니다. 언어 버전 기록은 C# 8.0 의 nullable 을 "?, notnull constraint and annotations attributes in APIs" 로 요약합니다. 특성은 System.Diagnostics.CodeAnalysis 에 있고, 표준은 그것이 "do not affect the language nor the behavior of a program" 이라고 적습니다.

out string? 이지만 TryGet 이 true 를 돌려준 갈래에서는 s.Length 가 조용합니다. 특성은 언어 기능이 아니라 라이브러리 형식이라 게이트가 없고, 컴파일러가 이름을 알아보고 분석에 씁니다.

문서 근거

AllowNull 과 DisallowNull — 속성의 get 과 set 이 다를 때

표준의 두 예를 하나로 묶었습니다 — null 을 넣으면 기본값으로 되돌리는 속성(AllowNull)과, null 로 시작하지만 null 을 넣을 수는 없는 속성 (DisallowNull).

ScreenName = null 은 조용하고, Comment = null 은 CS8625 입니다. 경고를 무시하면 setter 의 검사가 실행 중에 ArgumentNullException 을 던집니다 — 특성은 아무것도 막지 않으니, 막는 일은 여전히 코드의 몫입니다. BAD 쪽 41행의 CS8602 는 null 을 넣은 뒤라 상태가 maybe null 로 바뀐 탓입니다.

실행 검증

MaybeNull 과 NotNull — C# 8 에서 T? 대신

C# 8 에는 제약 없는 T? 가 없어서(앞에서) "T 이지만 null 일 수 있다" 는 [return: MaybeNull] 로 적었습니다. C# 9 의 제안은 반환값의 T? 가 "[MaybeNull]T 와 같다" 고 적습니다.

반환 형식은 T(여기서는 string)인데도 결과를 string 에 넣으면 CS8600 입니다. 반대로 Ensure 를 지난 s 는 string? 인데도 not null 로 바뀌어 s.Length 가 조용합니다. 본문의 default! 는 제약 없는 T 의 default 경고를 피하려는 것입니다.

실행 검증

MaybeNullWhen — Try 꼴의 제네릭 메서드

표준: MaybeNullWhen 은 MaybeNull 과 비슷하되 "includes a parameter for the specified return value" — 어느 bool 일 때인지를 받습니다. Dictionary.TryGetValue 의 out TValue 가 이 꼴입니다.

24행은 false 갈래의 v.Length 만 경고합니다. 37행의 CS8600 은 BCL 쪽입니다 — out 인수로 string z 를 넘기면, false 일 때 null 이 들어올 수 있으니 받는 변수가 string? 이어야 합니다. 같은 규칙이 우리 메서드와 BCL 에 똑같이 적용됩니다.

실행 검증

NotNullIfNotNull — null 이 들어가야 null 이 나온다

표준: 지정한 매개변수의 인수가 null 이 아니면 반환값도 null 이 아닙니다. 매개변수 이름을 문자열로 받는다는 것이 특이합니다.

문서와 다른 곳 — 메서드의 특성 안에서 그 매개변수를 nameof 로 부르는 것은 C# 11 의 "extended nameof scope" 이고, 제안은 그 동기로 바로 NotNullWhen 같은 특성을 듭니다. 그런데 이 컴파일러는 -langversion:8.0 에서도 nameof(s) 를 받습니다. 그 규칙에는 게이트가 없습니다 — 7부도 같은 것을 봤습니다. 옛 컴파일러에서는 문자열을 써야 했을 것이지만, 그 출력은 여기 없습니다.
실행 검증

DoesNotReturn 과 DoesNotReturnIf — 실패 도우미

표준: DoesNotReturn 이 붙은 메서드를 부른 뒤로는 nullable 경고를 억누를 수 있고, 다만 도달 가능성이나 정확한 대입 분석은 바꾸지 않으며 "It is used only to impact nullability warnings" 입니다.

A 와 B 의 s.Length 가 둘 다 조용합니다. 특성이 없다면 Fail() 이 돌아올 수도 있으니 경고가 남았을 것입니다. Check 는 Debug.Assert 같은 메서드의 꼴입니다 — 인수가 false 이면 돌아오지 않으므로, 돌아왔다면 s != null 이 참이었습니다.

실행 검증

특성은 메서드 몸체도 검사한다

컴파일러 변경 기록: Visual Studio 2019 16.3 의 컴파일러는 이 특성들을 API 를 부르는 쪽에만 적용했고, 16.5 부터는 "within member bodies" 에도 적용합니다. [MaybeNull] T 에서 default 를 돌려줘도 경고하지 않고, [NotNull] string? 에서 null 을 돌려주면 경고합니다.

문서의 두 문장이 그대로 나옵니다 — 9행의 [NotNull] 은 CS8603, 12행의 [MaybeNull] 은 조용합니다. [DisallowNull] string? 매개변수는 처음 읽을 때 not null 로 여겨집니다. C# 8.0 이 나온 뒤의 컴파일러 업데이트에서 경고가 늘어난 사례이고, 언어 버전으로는 되돌릴 수 없습니다.

실행 검증

같이 온 런타임 — BCL 의 주석 C# 8.0

버전 기록: 주석이 "being added in the .NET Core libraries" — C# 8.0 이 나올 때 라이브러리에 주석을 다는 일이 함께 시작됐습니다. 앞에서 string.IsNullOrEmpty 를 컴파일러가 알아들은 까닭을 리플렉션으로 봅니다.

IsNullOrEmpty(value) 에는 [NotNullWhen(false)] 가 붙어 있습니다 — false 를 돌려주면 value 는 null 이 아닙니다. 언어가 IsNullOrEmpty 를 특별히 아는 것이 아니라 라이브러리가 특성으로 알려 준 것입니다. ThrowIfNull 의 [NotNull] 도 같은 원리입니다 (공개 API 의 검사).

실행 검증

CoreLib 에는 몇 개나 붙어 있나

.NET 10 의 System.Private.CoreLib 에 있는 공개 형식의 공개 메서드 전부를 훑어, 매개변수와 반환값에 붙은 null 특성을 셉니다.

NotNullWhen 이 296 으로 압도적입니다 — TryParse·TryGetValue 같은 Try 꼴 메서드가 그만큼 많다는 뜻입니다. 속성·필드에 붙은 것과 DoesNotReturn 처럼 메서드 자체에 붙는 것은 세지 않았습니다. 이 수는 이 런타임(10.0.12)의 것이고, 버전마다 다릅니다.

실행 검증

뒤 버전 — [MemberNotNull] 은 C# 9

생성자가 도우미 메서드로 필드를 채우면 C# 8 의 분석은 그것을 모르고 CS8618 을 냅니다. C# 9 의 MemberNotNull 이 그 자리를 메웁니다 — C# 9 의 제안서는 그것을 "the behavior we have shipped for [MemberNotNull]" 이라 부릅니다.

흥미로운 점 — MemberNotNull 도 라이브러리의 특성일 뿐인데 컴파일러는 이것을 게이트로 막습니다('MemberNotNull attribute', C# 9). C# 8 의 특성들에는 게이트가 없습니다. 컴파일러 소스의 C# 9 목록에 이 특성의 줄이 따로 있습니다.

실행 검증

재정의와 구현 — nullable 이 어긋나면

제안서의 변환 규칙(CS8619)과 같은 생각이 재정의에도 적용됩니다. 매개변수는 더 너그러워도(받는 쪽이 null 을 더 받아도) 되고, 반환값은 더 엄격해도(null 을 덜 돌려줘도) 됩니다.

반환을 string? 로 넓힌 Strict.Find 는 CS8764, 매개변수를 string 으로 좁힌 Strict.Name 은 CS8765 입니다. 반대 방향인 Loose(반환은 좁히고 매개변수는 넓힌)는 조용합니다. 문장 끝의 "possibly because of nullability attributes" 는 이 비교가 특성까지 셈에 넣는다는 뜻입니다.

실행 검증

옮기는 법 — 파일 하나씩

제안서는 이 기능의 성패가 옮겨 가는 경험에 달렸다고 적었습니다 — 사용자는 "gradually" 받아들일 수 있어야 하고, 라이브러리 작성자는 고객을 깨뜨릴 걱정 없이 주석을 달 수 있어야 하며, 그러면서도 "configuration nightmare" 는 없어야 한다고.

같은 일을 하는 두 메서드인데 경고는 옮긴 쪽(New.Greet)을 부를 때만 납니다. 옮기는 일은 경고를 늘리는 일입니다. 그래서 흔한 순서는 의존이 적은 파일부터 #nullable enable 을 붙이고, 다 옮긴 뒤 프로젝트의 <Nullable> 을 켜고 파일의 지시문을 지우는 것입니다. 다 옮긴 뒤에는 -warnaserror:nullable 로 잠급니다.

공개 API 의 null 검사는 남긴다

제안서의 지침: 매개변수를 null 아닌 형식(제안서의 예에서는 Worker)으로 선언했더라도, NuGet 패키지나 공유 라이브러리 같은 공개 API 라면 "you should leave null guards in place" — 호출하는 쪽이 null 을 넘기지 않는다는 유일한 보장은 검사이기 때문입니다.

꺼진 코드(#nullable disable)에서는 null 을 넘겨도 경고가 없습니다. 검사가 없었다면 s.Length 의 NullReferenceException 이었을 것을, 검사가 매개변수 이름을 담은 ArgumentNullException 으로 바꿨습니다. 둘째 메서드의 ArgumentNullException.ThrowIfNull 은 .NET 10 에 있는 도우미이고, 매개변수에 [NotNull] 이 붙어 있어(BCL 의 주석) 그 뒤로 s 는 not null 입니다.

들어오지 않은 것 — 매개변수의 !!

제안서는 처음부터 "a shorthand T! x on parameters, that auto-generates a runtime null check" 를 생각해 볼 만한 것으로 적어 두었습니다. 매개변수 뒤의 !! 로 null 검사를 만들어 주는 문법이 그 후손입니다. 지금의 컴파일러는 그것을 어떻게 볼까요.

기능 이름도 버전도 말하지 않는 평범한 문법 오류(CS1003)입니다 — 이 컴파일러에는 그런 문법이 아예 없습니다. 이 문법이 어느 버전의 미리보기에 들어갔다가 빠졌는지는 이 덱이 받아 둔 문서에 없어 적지 않습니다. 남은 길은 앞 장의 ThrowIfNull 입니다.

2장 퀴즈 — nullable 참조 형식

Q. 동료가 말합니다. "우리 라이브러리는 nullable 을 켜고 경고를 0 으로 만들었으니, 이제 공개 메서드의 if (x is null) throw … 는 지워도 됩니다. string x 로 선언했으니 null 이 들어올 수 없잖아요." 무엇이 틀렸습니까?

A. nullable 참조 형식은 컴파일할 때의 경고일 뿐 런타임 형식도 검사도 바꾸지 않습니다(string? 과 string 은 같은 형식). nullable 을 끈 코드, 옛 컴파일러, 경고를 무시한 코드, ! 를 쓴 코드는 얼마든지 null 을 넘깁니다. 제안서의 지침도 공개 API 에는 null 검사를 남기라고 합니다. 지워도 되는 것은 호출하는 쪽까지 모두 같은 팀이 관리하는 비공개 코드뿐입니다. (공개 API 의 검사)
