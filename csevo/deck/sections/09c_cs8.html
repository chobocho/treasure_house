6장

기본 인터페이스 메서드 — 몸체를 가진 인터페이스

공개한 인터페이스에 멤버 더하기 · 가장 구체적인 구현 · 한정자 · 구조체와 상자 · 런타임 지원 · 트레이트

왜 — 한번 공개한 인터페이스는 고칠 수 없었다

제안서가 꼽은 첫째 동기: "add methods to an interface in future versions without breaking source or binary compatibility with existing implementations of that interface". 그 전에는 인터페이스에 멤버 하나를 더하면 그것을 구현한 모든 클래스가 깨졌습니다.

라이브러리 쪽의 한 줄이 사용자 쪽의 CS0535 가 됩니다. 사용자는 그 줄을 고칠 수 없고, 라이브러리는 그래서 인터페이스를 얼려 두거나 ILogger2 같은 새 인터페이스를 만들어야 했습니다.

실행 검증

기본 구현 (default interface methods) C# 8.0

왜 — whats-new: 인터페이스 멤버에 구현을 붙일 수 있게 되어, 기존 구현은 그 기본 구현을 inherit 하고 API 작성자는 "without breaking source or binary compatibility" 멤버를 더합니다.

기본 구현은 같은 인터페이스의 추상 멤버(Log)를 불러 제 일을 합니다. 7.3 의 거절은 몸체가 붙은 그 멤버 하나를 짚습니다.

실행 검증

기본 구현은 인터페이스를 거쳐야만 보인다

제안서: "a class does not inherit members from its interfaces; that is not changed by this feature". 클래스 C 의 변수로 M 을 부르면 "does not contain a member 'M'" 입니다. 인터페이스의 인스턴스 멤버 안에서 this 의 형식은 그 인터페이스입니다.

#if BAD 를 켜서 Robot 형식의 변수로 부르면 CS1061('Robot' does not contain a definition for 'Hello')입니다 — 그 오류 줄은 200칸을 넘어 캡처로 싣지 않고, 실험 스크립트가 거절과 번호만 확인합니다. 기본 구현 안의 GetType() 은 실제 객체의 형식(Robot)을 냅니다 — this 의 정적 형식은 IGreeter 이지만 가리키는 것은 Robot 객체입니다.

함정 — 기본 구현을 받은 클래스를 var r = new Robot() 으로 잡으면 그 메서드가 안 보입니다. 확장 메서드처럼 "그 형식에 붙은 것" 으로 착각하기 쉽습니다(뒤에서 견줍니다).
실행 검증

클래스가 직접 구현하면 그쪽이 이긴다

제안서의 "가장 구체적인 구현" 규칙에서 클래스의 구현은 인터페이스의 구현보다 구체적입니다("T2 is an interface type but T1 is not"). 그래서 기본 구현은 클래스가 아무것도 주지 않을 때만 쓰입니다.

셋째 줄 — Louder 는 아무것도 쓰지 않았지만 기반 클래스 Loud 의 공개 메서드가 인터페이스 멤버를 구현하므로 기본 구현까지 가지 않습니다. 기본 구현은 "구현이 하나도 없을 때의 마지막 후보" 입니다.

실행 검증

파생 인터페이스가 재정의하기 — 명시적 구현 문법으로

제안서: 인터페이스 안의 재정의는 명시적 인터페이스 구현 문법(void IA.M())이어야 하고, 이름만 같은 void M() 은 "Creates a new M, unrelated to IA.M. Warning" 입니다.

둘째 줄 — IB 에는 제 이름의 M 이 없어서 ((IB)b).M() 은 IA.M 을 부르고, 그 가장 구체적인 구현이 IB 의 것입니다. 셋째·넷째 줄 — IC 의 M 은 IA.M 과 상관없는 새 멤버라 어느 인터페이스로 부르느냐에 따라 다른 메서드가 돕니다. 경고는 클래스의 숨기기와 같은 CS0108 입니다.

실행 검증

다이아몬드 — 가장 구체적인 구현이 하나여야 한다 C# 8.0

왜 — 인터페이스는 여럿을 물려받으므로 두 갈래가 같은 멤버를 각자 재정의할 수 있습니다. 제안서는 모든 클래스와 인터페이스가 멤버마다 유일한 가장 구체적인 구현을 갖도록 요구해, 충돌을 "resolved explicitly by the programmer at the point where the conflict arises" 하게 합니다.

CS8705 는 후보 둘(IB.IA.M(), IC.IA.M())을 이름으로 짚습니다. 고치는 길은 둘 — 클래스가 직접 구현하거나, 두 갈래를 다시 묶는 인터페이스(ID)가 정하는 것입니다.

실행 검증

기반 클래스의 구현 대 인터페이스의 구현

제안서의 닫힌 질문: Base 가 IA.M 을 구현하고, Derived : Base, IB 의 IB 도 IA.M 을 재정의하면? 결정은 초안 그대로 — "a class takes priority over an interface".

경고도 오류도 없이 Base 가 이깁니다. Derived 가 IB 를 목록에 적은 것은 IB 의 몸체를 쓰겠다는 뜻이 되지 않습니다.

실행 검증

재추상화 — 파생 인터페이스가 기본 구현을 도로 빼앗기

제안서: 인터페이스의 가상 멤버는 파생 인터페이스에서 abstract void IA.M(); 으로 다시 추상이 될 수 있고, 기본 구현이 "inappropriate" 한 파생 인터페이스에서 구현 클래스에 더 알맞은 구현을 요구할 때 씁니다.

오류 문장은 재추상화한 IPolygon 이 아니라 원래 멤버 IShape.Describe() 를 짚습니다. 구현해야 할 멤버는 여전히 하나뿐이기 때문입니다.

실행 검증

인터페이스 멤버에 붙는 한정자 C# 8.0

왜 — 인터페이스에 실행 코드가 들어오자 공통 코드를 따로 떼어 둘 자리가 필요해졌습니다. 제안서: "it is useful to abstract common code into private and static methods". 허용되는 한정자는 private·protected·internal·public·virtual·abstract·sealed·static·extern·partial 입니다.

7.3 의 거절 일곱은 모두 'default interface implementation' 입니다. static 필드·static 생성자·sealed·private 도 따로 된 기능 이름이 없고, 몸체 없는 추상 속성 Count(12행)만 거절되지 않았습니다. Created 가 101 인 것은 static 생성자가 Make() 보다 먼저 돌았기 때문입니다.

실행 검증

문서 근거

protected 인터페이스 멤버 — 파생 인터페이스만 부른다

C# 8.0 의 기능 목록: 인터페이스가 "static/private/protected/internal members except for state" 를 가질 수 있습니다. 제안서는 비공개 멤버를 파생 인터페이스에서 재정의할 때 명시적 문법을 쓴다고 적습니다.

Show() 는 Tag() 를 가상으로 부르므로 Fancy 객체에서는 IFancy 의 재정의가 돕니다. 바깥의 호출은 인터페이스 형식으로 잡아도 CS0122 — 클래스의 protected 와 같은 오류 번호입니다.

실행 검증

인스턴스 상태는 여전히 금지 — 필드도, 값 있는 자동 속성도

제안서: "Interfaces may not contain instance state." static 필드는 되지만 인스턴스 필드는 안 되고, 인스턴스 자동 속성은 "would implicitly declare a hidden field" 라서 지원하지 않습니다.

함정 — 인터페이스 안의 int Max { get; set; } 은 클래스에서처럼 자동 속성이 아니라 추상 속성입니다. 그래서 셋째 오류처럼 Box 가 Max 를 구현하지 않았다는 말이 따라 나옵니다. 기본 구현이 상태를 원하면 구현 클래스에 추상 속성으로 요구하는 수밖에 없습니다(트레이트에서 그렇게 씁니다).
실행 검증

메타데이터에 남는 것 — 리플렉션으로 본 여섯 멤버

제안서: 몸체 있는 멤버는 가상이고, sealed·private 이면 가상이 아닙니다. 그 말이 IL 의 플래그로 어떻게 남는지 .NET 10 의 리플렉션으로 확인합니다.

기본 구현(Default)은 추상이 아닌 가상 메서드로 남습니다 — 몸체 없는 멤버(첫 줄)만 예전처럼 추상입니다. sealed 는 "가상이면서 final" 이 아니라 아예 가상이 아닌 메서드가 됩니다. protected 는 IL 의 family 접근입니다.

실행 검증

구조체와 기본 구현 — 상자 안의 복사본을 바꾼다

제안서의 닫힌 질문 "Interface methods vs structs": 인터페이스 멤버는 물려받지 않으므로 구조체로 기본 구현을 부르려면 상자에 넣어야 하고, 바꾸는 메서드는 "operating on a boxed copy" 라 효과가 안 보입니다. 결정은 "Not worry about it and just leave it as a wart" 였습니다.

(t as IB).Increment() 는 t 의 복사본을 담은 새 상자를 바꾸고 버립니다. 상자를 변수에 잡아 두면 그 상자의 값은 2 가 되지만 t 는 끝까지 0 입니다. 7.2 의 방어 복사와 같은 뿌리 — "어느 복사본을 바꾸는가" 의 문제입니다.

실행 검증

상자는 공짜가 아니다 — 호출 한 번에 몇 바이트

제안서는 상자에 넣는 일이 "defeats the principal benefits of a struct type" 이라고 적었습니다. 제네릭 제약(where T : IArea)으로 부르면 상자가 없을까요? 스레드가 할당한 바이트를 호출 1000번 앞뒤로 재어 나눕니다.

제네릭으로 불러도 Sq 는 호출마다 24 바이트 — 상자 하나입니다. 기본 구현의 몸체는 this 를 인터페이스 참조로 받으므로 런타임이 값을 상자에 넣어 넘깁니다. 구조체가 제 구현을 가지면(Own) 제네릭 호출은 할당이 0 입니다. 이 숫자는 시간이 아니라 할당량이라 돌릴 때마다 같습니다.

함정 — 성능 때문에 구조체를 쓰는 코드에서 인터페이스의 기본 구현에 기대면, 제네릭으로 감싸도 호출마다 상자가 생깁니다.
실행 검증

같이 온 런타임 — CLR 이 바뀌어야 했던 기능

제안서: 이 기능은 "requires corresponding support in the CLI/CLR. Programs that take advantage of this feature cannot run on earlier versions of the platform." 컴파일러는 런타임이 지원하는지를 RuntimeFeature 의 상수로 알아냅니다. 버전 기록은 그 지원이 ".NET Core 3.0 의 CLR" 에 들어갔다고 적습니다.

제안서가 적은 이름은 DefaultInterfaceImplementation 이었지만 런타임에 실린 이름은 DefaultImplementationsOfInterfaces 입니다 — 옛 이름으로 물으면 False. 제안서도 그 이름이 최선인지를 열린 질문으로 남겨 두었습니다. 목록의 나머지(공변 반환, ref 필드, 인터페이스의 static virtual …)는 뒤 버전들이 CLR 에 요구한 기능입니다.

실행 검증

다시 컴파일하지 않은 클래스는 어느 구현을 부르나

제안서의 "Binary Compatibility 1": C : I2, I2 : I1 에서 I1.M 만 기본 구현을 갖고 있었는데, 라이브러리가 I2 에 재정의를 더해 다시 컴파일하고 C 는 그대로 두면 (C as I1).M() 은 무엇을 하는가. 후보는 셋이었습니다 — I1.M, I2.M, 실행 오류. 결정(2017-04-11)은 "Runs I2.M, which is the unambiguously most specific override at runtime" 입니다.

그래서 런타임이 일한다 — 가장 구체적인 구현을 고르는 일이 컴파일 때 한 번으로 끝나지 않고 실행 때 다시 이루어집니다. 제안서가 이 기능의 단점으로 CLR 명세의 "coordinated update" 를 꼽고 그래서 fairly "expensive" 하다고 적은 까닭입니다.
이 덱에서 못 보이는 것 — 이 결정을 실제로 보이려면 어셈블리 둘을 따로 컴파일해 한쪽만 바꿔야 합니다. csrun 은 예제 하나를 어셈블리 하나로 컴파일하므로(0부) 캡처가 없습니다.
문서 근거

트레이트처럼 — 상태는 클래스가, 동작은 인터페이스가

제안서의 셋째 동기: 기본 구현은 결과적으로 "traits" 의 재료를 준다("As it turns out …"). whats-new 도 "scenarios similar to a "traits" language feature" 를 듭니다.

인스턴스 상태를 가질 수 없으므로(앞에서) 동작이 쓰는 값(Name, Legs)은 추상 속성으로 클래스에 요구합니다. 클래스 쪽에 남는 것은 그 값뿐입니다. 다만 호출은 여전히 인터페이스 형식으로 해야 합니다.

실행 검증

확장 메서드(C# 3)와 무엇이 다른가 — 정적 결합 대 가상 호출

인터페이스에 "공통 동작" 을 붙이는 옛 방법은 4부의 확장 메서드였습니다. 둘을 같은 꼴로 놓고, 구현 클래스가 더 나은 Hello 를 주려 할 때를 봅니다. 제안서가 이 기능을 "virtual extension methods" 라고 부른 까닭이 여기 있습니다.

확장 메서드는 컴파일 때 변수의 형식(IOld)만 보고 정해져서 A 의 메서드를 영영 부르지 않습니다. 기본 구현은 가상 멤버라 B 의 구현이 그것을 대신합니다. 라이브러리가 확장 메서드를 기본 구현으로 옮기면, 같은 이름의 메서드를 가진 구현 클래스에서는 출력이 바뀝니다.

실행 검증

남의 언어와 맞추기 — 자바의 default 메서드, 안드로이드와 iOS

제안서의 요약은 이 기능을 자바의 "Default Methods" 와 비슷하다고 적고, 둘째 동기로 같은 기능을 가진 Android(Java)·iOS(Swift) API 와의 상호 운용을 듭니다. whats-new 도 "interoperate with APIs that target Android or Swift" 를 적습니다.

1부에서 본 자바와의 관계가 여기서는 반대 방향입니다 — C# 이 자바의 기능을 따라 들인 것이 아니라, 자바로 쓴 API 를 C# 에서 그대로 옮겨 쓰기 위해서이기도 합니다.

문서 근거

제안서에는 있고 컴파일러에는 없는 것 — base(IB).M()

다이아몬드를 클래스가 풀 때 한쪽의 구현을 그대로 부르고 싶습니다. 제안서는 base(Interface).M() 문법을 정했지만(닫힌 질문의 결정), 같은 절에 "This decision was not implemented in C# 8" 이라고 적었고, 본문 절은 "hasn't been implemented. It remains an active proposal" 입니다.

C# 14 도 그 문법을 모릅니다 — 기능이 꺼진 것이 아니라 base 를 그 자리에 쓸 수 없다는 문법 오류입니다(2026-10 기준). 지금 할 수 있는 것은 IB 의 몸체를 베끼거나, 공통 코드를 인터페이스의 static 도우미로 빼 두고 양쪽에서 부르는 것입니다.

실행 검증

뒤 버전과의 맞물림 — static abstract 멤버, C# 11

C# 8 의 인터페이스 static 멤버는 몸체가 있어야 하고, 형식 매개변수 T 를 거쳐 부를 수 없습니다. 구현 형식마다 다른 static 멤버를 요구하는 일(T.Zero)은 C# 11 의 static abstract 멤버가 열었습니다. 자세한 것은 12부에서 봅니다.

거절 문장은 "Feature … is not available" 꼴이 아니라 "The modifier 'abstract' is not valid for this item in C# 8.0" 입니다 — 8.0 의 문법에서 static 멤버에 abstract 를 붙일 수 없다는 말이고, 고칠 버전으로 11.0 을 짚습니다. RuntimeFeature 목록의 VirtualStaticsInInterfaces(앞에서 본 런타임 기능 목록)가 그 런타임 쪽입니다.

실행 검증

6장 퀴즈 — 어느 Hello 가 도나

Q. interface I { void Hello() => Console.Write("I"); } 와 class C : I { } 가 있습니다. (가) new C().Hello(); (나) ((I)new C()).Hello(); (다) C 에 public void Hello() => Console.Write("C"); 를 더한 뒤의 (나). 각각 무엇이 일어납니까? 그리고 C 가 구조체라면 (나)에서 무엇이 더 생깁니까?

A. (가) CS1061 — 클래스는 인터페이스의 멤버를 물려받지 않습니다(기본 구현은 인터페이스로만). (나) I — 구현이 없으니 기본 구현. (다) C — 클래스의 구현이 더 구체적입니다(클래스가 이긴다). 구조체라면 (I) 변환에서 상자가 하나 생기고, 기본 구현은 그 상자 안의 복사본에서 돕니다(구조체와 상자, 24 바이트).

왜 — readonly struct 로 바꿀 수 없는 구조체들

제안서의 동기: C# 7.2 의 readonly struct 는 모든 필드를 읽기 전용으로 만들지만, 접근 가능한 필드를 이미 내놓았거나 바꾸는 멤버와 안 바꾸는 멤버가 섞인 기존 API 는 "you cannot mark the type as readonly (it would be a breaking change)". 그런 구조체를 in 으로 넘기면 컴파일러는 멤버를 부를 때마다 복사본을 만들어, 값으로 넘기는 것보다 느려질 수도 있습니다.

readonly struct (C# 7.2)readonly 멤버 (C# 8.0)
단위형식 전체메서드·속성·접근자 하나
필드모두 readonly 여야 한다그대로 둔다
약속어느 멤버도 상태를 안 바꾼다이 멤버는 상태를 안 바꾼다

제안서는 선을 긋습니다 — readonly 멤버는 "pure" 멤버가 아닙니다. 인스턴스 상태를 안 바꾼다는 약속일 뿐, 다른 상태(정적 필드 등)는 바꿀 수 있습니다.

문서 근거

readonly 멤버 (readonly members) C# 8.0

왜 — whats-new: readonly 를 구조체의 멤버에 붙여 그 멤버가 상태를 바꾸지 않음을 나타내고, "more granular than applying the readonly modifier to a struct declaration" 입니다. 컴파일러는 그 약속을 강제하고 그것을 근거로 최적화합니다.

구조체 전체는 readonly 가 아니어서 Translate 로 값을 바꿀 수 있고, Distance 와 ToString 만 읽기 전용이라고 약속합니다. 7.3 은 readonly 가 붙은 두 줄만 거절합니다.

실행 검증

readonly 멤버가 보통 멤버를 부르면 — CS8656 과 숨은 복사

whats-new: readonly ToString 이 readonly 가 아닌 Distance 를 부르면 경고 CS8656 이 나고, "The compiler warns you when it needs to create a defensive copy." 제안서도 readonly 멤버가 readonly 아닌 멤버를 부르면 "still create hidden copies" 라고 적습니다.

오류가 아니라 경고라서 컴파일은 됩니다. 그리고 Bump() 는 this 의 복사본에서 돌아 N 을 바꾸지 못합니다 — 두 줄 모두 0 입니다. readonly 멤버 안에서 바깥 값을 바꾸려는 시도가 조용히 사라지는 대신, 컴파일러가 "복사가 생긴다" 고 알려 줍니다.

실행 검증

in 매개변수에서 — 복사가 있는지 눈으로 보기

제안서의 ExistingBehavior(in Vector2) 는 컴파일러가 "var tmpVector = vector;" 를 만든다고 주석을 달고, ReadonlyBehavior 는 "emitted exactly as listed. There are no hidden copies" 라고 적습니다. 메서드가 도는 동안 원래 변수를 바꿔서 확인합니다.

보통 멤버는 in 으로 받은 S 의 복사본에서 돌아 바뀐 값(99)을 못 보고, readonly 멤버는 S 자체를 보아 99 를 읽습니다. 8부의 readonly struct 실험을 멤버 하나 단위로 옮긴 것입니다. readonly 멤버가 정적 필드를 쓰는 것은 허용됩니다 — 막는 것은 인스턴스 상태뿐입니다.

실행 검증

속성과 접근자 — 자동 getter 는 이미 readonly

whats-new: 컴파일러는 get 접근자가 상태를 안 바꾼다고 가정하지 않으므로 읽기 전용 속성에도 readonly 를 적어야 하지만, "Auto-implemented properties are an exception" — 자동 getter 는 모두 readonly 로 취급합니다. 제안서는 허용되는 꼴과 안 되는 꼴을 나열합니다.

세 오류가 각자 이유를 댑니다 — 자동 set 은 readonly 일 수 없고(CS8658), 접근자 하나에만 붙이려면 get 과 set 이 다 있어야 하고(CS8664), set 이 있는 자동 속성 전체에는 못 붙입니다(CS8659). 오류의 차례가 줄 차례와 다른 것은 컴파일러가 보고하는 차례 그대로입니다.

실행 검증

readonly 멤버가 거절되는 곳

whats-new: 상태를 바꾸는 readonly 메서드는 "won't compile". 제안서의 제한: static 메서드·생성자·소멸자·대리자에는 못 붙이고, "cannot be applied to members of class or interface".

X 는 보통 필드인데도 문장은 "because it is read-only" 입니다 — readonly 멤버 안에서는 this 가 읽기 전용 참조라서 필드 전부가 읽기 전용으로 보입니다. 클래스 멤버의 거절은 C# 8 전용 문장이 아니라 오래된 CS0106 입니다. 두 경우를 한 파일에 같이 두면 선언의 오류가 몸체의 오류를 가리므로 전처리 기호(DECL)로 나눴습니다.

실행 검증

메타데이터에서는 — IsReadOnlyAttribute 한 장

제안서: 컴파일러는 멤버를 평소대로 내보내되 "a compiler recognized attribute" 를 덧붙이고, 그것이 숨은 this 매개변수를 ref T 대신 in T 로 만든다고 적습니다.

특성은 System.Runtime.CompilerServices.IsReadOnlyAttribute — 7.2 의 in 매개변수와 readonly struct 가 쓰는 바로 그 특성입니다(8부). readonly 속성은 특성을 getter 메서드(get_Prop)에 답니다. 구조체 자신에는 특성이 없습니다 — readonly struct 가 아니기 때문입니다.

실행 검증

같이 온 런타임 — .NET 10 의 Vector2 는 멤버마다 readonly

제안서가 예로 든 형식이 Vector2 — 공개 필드 x·y 를 가진, 그래서 readonly struct 가 될 수 없는 구조체였습니다. .NET 10 의 System.Numerics.Vector2 를 같은 눈으로 봅니다.

필드 X·Y 는 바꿀 수 있어서 구조체는 readonly 가 아니고, 공개 인스턴스 메서드 14개 가운데 13개가 readonly 멤버입니다. 빠진 하나는 인덱서의 setter(set_Item) — 값을 바꾸는 유일한 멤버입니다. 이 라이브러리가 언제 이렇게 바뀌었는지는 이 덱의 문서에 없어 적지 않습니다.

실행 검증

static 지역 함수 (static local functions) C# 8.0

왜 — 제안서의 동기는 둘입니다. "Avoid unintentionally capturing state from the enclosing context", 그리고 static 메서드가 필요한 자리에 지역 함수를 쓰기. 지역 변수·매개변수·this 는 못 쓰고, static 멤버와 상수는 쓸 수 있고, nameof() 는 바깥의 지역 변수를 이름으로 가리킬 수 있습니다.

거절은 둘로 갈립니다 — qty 는 this.qty 라서 CS8422('this' or 'base'), discount 는 바깥 지역 변수라서 CS8421. 기본 문법과 7.3 의 거절은 8부에서 봤습니다.

실행 검증

static 을 붙이면 IL 이 달라지나 — 대리자로 바꿔 보기

제안서: static 지역 함수는 "emitted as a static method in metadata, even if only used in a delegate" 이고, "Removing the static modifier from a local function in a valid program does not change the meaning of the program." 포착이 없는 보통 지역 함수는 어떻게 나오는지 대리자의 Method 로 봅니다.

포착이 없으면 static 을 붙이지 않아도 이미 App 의 static 메서드입니다(첫 두 줄이 같다). 포착하는 지역 함수는 클로저 클래스(<>c__DisplayClass)의 인스턴스 메서드, 같은 일을 하는 람다는 <>c 싱글턴의 인스턴스 메서드입니다. 이 컴파일러에서 static 은 IL 을 바꾸는 장치가 아니라 포착을 막는 약속입니다.

실행 검증

첫 컴파일러가 놓친 것 — VS 2019 16.3 의 두 구멍

Roslyn 의 깨지는 변경 문서: Visual Studio 2019 16.3 은 static 지역 함수가 static 아닌 지역 함수를 부르는 것과, 포착이 필요한 대리자 생성식(new Func<int>(local.GetHashCode))을 "incorrectly allowed" 했고, 16.4 부터 오류입니다.

둘 다 같은 CS8421 입니다. 첫째는 Local 을 지역 함수가 아니라 "포착된 이름" 으로 취급합니다 — static 아닌 지역 함수는 바깥 상태를 포착했을 수 있기 때문입니다. 16.3 의 동작은 이 기계에서 재현할 수 없어 문서로만 적습니다.

실행 검증

뒤 버전과의 맞물림 — static 람다, C# 9

지역 함수에 생긴 static 은 C# 9 에서 람다와 익명 메서드로 넓어집니다. 거절 번호도 짝을 이룹니다 — 지역 함수의 CS8421, 익명 함수의 CS8820. 자세한 것은 10부에서 봅니다.

실행 검증

중첩 함수의 이름 가리기 (name shadowing) C# 8.0

왜 — 제안서: 람다와 지역 함수 안의 지역 변수·매개변수·형식 매개변수 이름이 바깥 메서드의 같은 이름을 "reuse (and shadow)" 할 수 있게 합니다. static 지역 함수는 바깥 변수를 못 쓰므로 바깥과 같은 이름의 매개변수를 쓰고 싶어지는데, 그 자리를 함께 열었습니다("Shadowing is supported for static and non-static local functions and lambdas").

7.3 은 가린 이름 셋을 모두 옛 오류 CS0136 으로 거절하고, static 지역 함수만 'Feature …' 꼴로 거절합니다(8부의 발견과 같다). 제안서 그대로, 같은 함수 안의 중첩 블록에서 가리는 것은 8.0 에서도 CS0136 입니다 — 열린 것은 함수의 경계를 넘는 가리기뿐입니다.

실행 검증

형식 매개변수를 가리면 — 게이트가 아니라 원래 있던 경고

제안서: 지역 함수의 형식 매개변수가 바깥 형식·메서드·함수의 형식 매개변수를 가리면 경고를 냅니다. "Any shadowing previously permitted is still supported" 라는 문장도 있습니다. 이 경고가 C# 8 의 것인지 두 버전으로 확인합니다.

7.3 에서도 오류가 아니라 같은 경고 CS8387 입니다 — 형식 매개변수의 가리기는 원래부터 경고로 허용되던 것이고, C# 8 의 게이트에 걸리지 않습니다. 안쪽 T 는 Int32, 바깥 T 는 String 으로 따로 삽니다.

실행 검증

null 병합 할당 (??=) C# 8.0

왜 — 제안서: if (variable == null) { variable = expression; } 는 흔한 꼴이고, 이 기능을 바라는 커뮤니티 요청이 "at least eight separate" 였습니다. 오버로드할 수 없는 이항 연산자로 들어왔습니다.

i ??= 20 은 i 가 이미 17 이라 아무것도 하지 않고 17 을 냅니다. 할당식이므로 numbers.Add(…) 의 인수로 그대로 쓸 수 있습니다.

실행 검증

오른쪽은 null 일 때만, 왼쪽은 한 번만

제안서: a ??= b 는 실행 때 a ?? (a = b) 로 평가되지만 "a is only evaluated once" 입니다. 손으로 쓰는 대안으로 (x = x ?? y) 를 들기도 합니다. 두 꼴의 차이를 호출 횟수로 셉니다.

s 가 채워진 뒤의 s ??= Make() 는 Make 를 부르지 않습니다. 배열 원소에 쓰면 인덱스 식 Slot() 이 한 번만 돌고, 손으로 쓴 x = x ?? y 꼴은 두 번 돕니다 — 게다가 이미 값이 있어도 쓰기를 한 번 더 합니다.

실행 검증

int? 에 쓰면 결과 형식은 int

제안서의 규칙 3: 왼쪽이 nullable 값 형식 A(바탕 A0)이고 오른쪽이 A0 로 바뀌면 a ??= b 의 형식은 A0 이고, GetValueOrDefault() 와 HasValue 로 번역됩니다.

상자를 거치는 GetType() 으로는 int? 와 int 가 구별되지 않으므로 형식 매개변수로 유추된 형식을 찍었습니다. i ??= 5 는 Int32 — 그래서 int j = (i ??= 7) 에 형 변환이 필요 없습니다. 둘째 줄의 i ?? 6 도 같은 Int32 입니다.

실행 검증

??= 가 안 되는 곳 — 그리고 없는 &&=

제안서의 규칙 1: 왼쪽이 null 이 될 수 없는 값 형식이면 컴파일 오류. 미결 질문에는 "Should we also support &&= and ||= operators?" 가 남아 있습니다.

&&= 는 연산자로 읽히지 않아 && 뒤의 = 가 "Invalid expression term" 이 됩니다. 구문 오류가 나면 컴파일러는 의미 검사를 하지 않으므로 9행의 CS0019 는 둘째 캡처에 없습니다.

실행 검증

비관리 생성 형식 (unmanaged constructed types) C# 8.0

왜 — whats-new: C# 7.3 까지는 형식 인수를 가진 생성 형식이 비관리 형식이 될 수 없었습니다. C# 8.0 부터는 "a constructed value type is unmanaged if it contains fields of unmanaged types only" 이고, 그런 형식은 포인터를 만들거나 스택에 할당할 수 있습니다. 제안서 파일은 자리만 잡아 둔 "placeholder" 입니다.

거절 다섯이 모두 같은 게이트입니다 — stackalloc 의 원소 형식, sizeof 둘, 포인터 형식과 주소 연산자. 크기와 7.3 의 거절 꼴은 8부에서 Pair<T> 로 먼저 봤습니다. 포인터를 쓰므로 이 예제는 AllowUnsafeBlocks 를 켰습니다(9부에서는 포인터의 null 패턴, 다음 장의 예제와 셋뿐입니다).

실행 검증

unmanaged 제약 안에서 — Coords<T> 도 비관리

7.3 의 where T : unmanaged(8부)와 겹치면, T 가 비관리인 동안 Coords<T> 도 비관리입니다. 런타임 쪽 질문 RuntimeHelpers.IsReferenceOrContainsReferences<T>() 도 같은 답을 하는지 봅니다.

Coords<byte> 는 2, Coords<double> 은 16 바이트. Coords<string> 은 참조를 품어서 런타임도 True, 컴파일러도 #if BAD 에서 CS8377("along with all fields at any level of nesting")입니다(그 줄은 200칸을 넘어 캡처 대신 실험 스크립트가 번호만 확인합니다). 7.3 의 거절은 sizeof(Coords<T>) 한 곳 — 제약 where T : unmanaged 자체는 7.3 의 것이라 걸리지 않습니다.

왜 — whats-new: stackalloc 의 결과가 Span<T> 나 ReadOnlySpan<T> 이면 "you can use the stackalloc expression in other expressions". 제안서는 문법에서 stackalloc 을 변수 초기값 전용 규칙에서 꺼내 일반 식 (primary_no_array_creation_expression)으로 옮깁니다.

7.3 이 거절한 것은 인수 자리의 두 줄(16·19행)뿐입니다. 22행의 n <= 64 ? stackalloc int[n] : new int[n] 은 거절되지 않았습니다 — 다음 장에서 그 까닭을 봅니다. 크기를 생략한 stackalloc[] { … } 은 7.3 의 초기화자입니다.

문맥이 형식을 정한다 — 선언문에서는 여전히 포인터

제안서: stackalloc 이 지역 변수 선언의 초기값(또는 for 초기화)에 바로 오면 형식은 K*, 그 밖의 자리에서는 System.Span<K> 입니다. K* 에서 Span 으로 가는 "stackalloc conversion" 도 새로 둡니다.
