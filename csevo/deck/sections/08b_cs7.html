ref 반환과 ref 지역 변수 (ref locals and returns) C# 7.0

왜 — whats-new 의 예는 큰 행렬입니다. 조건에 맞는 칸 하나를 찾아 그 저장소의 참조를 돌려주면, 호출자는 값을 복사하지 않고 그 칸을 바로 고칩니다. "avoiding copying values, or performing dereferencing operations multiple times" 가 문서가 든 이득입니다.

C# 6 의 거절은 7행(반환 형식의 ref) 하나뿐입니다. 선언의 오류가 몸체의 ref int slot 을 가린 것으로, 1장에서 본 모양 그대로입니다. 22행처럼 메서드 호출이 대입의 왼쪽에 서는 것도 ref 반환이라 됩니다.

실행 검증

복사할지 가리킬지는 호출자가 정한다

whats-new 의 규칙: "A ref return may be assigned to a value variable, or a ref variable." ref 를 빼고 받으면 "the caller wants a copy of the value" 입니다.

배열에 남은 변화는 alias(20→21)와 r(30→130) 둘뿐입니다. var v = At(2) 의 var 는 ref int 가 아니라 int 로 유추되어 복사본을 받았습니다. 가리키려면 양쪽 모두에 ref 를 적어야 합니다 — ref var r = ref At(2).

실행 검증

큰 구조체 배열 — 복사본을 고치는 실수

whats-new 는 ref 지역 변수와 반환이 값의 복사를 피하는 알고리즘을 가능하게 한다고 적습니다. 구조체를 돌려주는 메서드는 늘 복사본을 돌려주므로, 그 복사본을 고쳐도 원래 자리는 그대로입니다.

첫 원소는 그대로 0 입니다 — c 는 지역 복사본입니다. 컴파일러는 Copy(0).A = 1 처럼 버려질 복사본에 대입하는 것만은 CS1612 로 막아 주지만, c 에 받아 고치는 것은 막지 않습니다. Slot(1).A = 2 는 ref 반환이라 원래 자리를 고칩니다.

실행 검증

ref 매개변수는 돌려줄 수 있다 — 큰 쪽의 자리

ref 로 돌려줄 수 있는 것은 메서드가 끝난 뒤에도 살아 있는 저장소입니다. whats-new: "You can't return a ref to a variable whose lifetime doesn't extend beyond the execution of the method." 호출자의 변수를 가리키는 ref 매개변수는 그 조건을 만족합니다.

C# 7.0 의 Max 는 if 두 줄을 써야 합니다. ?: 의 두 가지에 ref 를 붙이는 조건 ref 식은 C# 7.2 의 기능이라 거절 문장이 7.2 를 말합니다 — 7장.

실행 검증

지역 변수와 값 매개변수는 ref 로 못 돌려준다

whats-new 의 넷째 규칙은 "you can't return a reference to a local variable or a variable with a similar scope" 입니다. 값 매개변수도 메서드의 프레임에 놓인 복사본이라 같은 처지입니다.

오류 번호가 둘로 갈립니다 — 지역 변수는 CS8168, 매개변수는 CS8166. 문장이 해법도 말합니다: ref 지역 변수나 ref 매개변수였다면 됐다는 것입니다. 필드·배열 원소·ref 매개변수(17–19행)는 오류가 없습니다.

실행 검증

구조체의 필드 — this 와 값 매개변수

구조체의 인스턴스 메서드에서 this 는 호출자의 변수일 수도, 곧 사라질 임시 복사본일 수도 있습니다. 컴파일러는 어느 쪽인지 모르므로 구조체 멤버가 자기 필드를 ref 로 내주는 것을 막습니다. 클래스의 필드는 힙에 있어 괜찮습니다.

거절은 둘입니다. 구조체 멤버의 return ref X(CS8170)와 값으로 받은 구조체 매개변수의 필드(CS8167). ref S s 로 받으면 s.X 는 호출자의 변수 안에 있으므로 됩니다. 구조체가 자기 필드를 ref 로 내주는 길은 C# 11 의 [UnscopedRef] 에서 열립니다(12부).

실행 검증

ref 지역 변수는 선언할 때 변수로 묶는다

whats-new: "You can't assign a standard method return value to a ref local variable. That disallows statements like ref int i = sequence.Count();"

초기화가 없는 ref int a; 는 CS8174, 오른쪽에 ref 를 빠뜨린 것은 CS8172 입니다. 메서드의 값·확장 메서드의 값·리터럴은 모두 같은 CS1510 — "assignable variable" 이 아니라는 문장입니다. 문서의 예(arr.Count())도 그대로 거절됩니다.

실행 검증

읽기 전용 저장소와 속성은 ref 로 못 내준다

ref 로 내준 자리는 받는 쪽이 고칠 수 있습니다. 그래서 C# 7.0 은 고치면 안 되는 저장소(readonly 필드)와 저장소가 아닌 것(속성, string 의 인덱서)을 ref 로 돌려주지 못하게 합니다.

읽기 전용 필드는 "writable reference" 로 못 내준다는 CS8161 입니다. 문장이 이미 답을 가리킵니다 — 쓸 수 없는 참조, 곧 C# 7.2 의 ref readonly 반환이 그것입니다(7장). 속성과 문자열 인덱서는 그 자체가 변수가 아니라 CS8156 입니다.

실행 검증

ref 지역 변수를 못 쓰는 곳 — 람다, async, 반복기

whats-new: "ref locals and returns can't be used with async methods. The compiler can't know if the referenced variable has been set to its final value when the async method returns." 람다가 포착하면 변수가 힙의 클로저로 옮겨지는데, 스택을 가리킬 수도 있는 ref 는 그곳에 담을 수 없습니다.

람다의 포착은 CS8175 로 막힙니다. 그런데 async 와 반복기의 두 줄은 옛 규칙의 오류가 아니라 C# 13 기능의 게이트 문장 — "ref and unsafe in async and iterator methods … use language version 13.0" — 으로 거절됩니다. 지금의 컴파일러는 이 제약을 "C# 13 에서 풀린 것" 으로 압니다. 다음 장이 그것입니다.

실행 검증

뒤 버전과의 맞물림 — async·반복기 안의 ref 지역 변수, C# 13

컴파일러의 기능 목록은 이 완화를 C# 13 에 둡니다. 다만 ref 지역 변수가 살아 있는 동안 await 나 yield 를 지나가면 안 됩니다.

12.0 은 CS9202, 7.0 은 CS8107 로 거절 번호만 다르고 문장은 같습니다(대상 버전마다 번호가 다른 것은 0부). 반복기에서 ref 로 원소를 두 배로 만든 결과 22·4·6 이 배열에 남았습니다.

실행 검증

컴파일러가 만드는 것 — 반환 형식 Int32&

ref 반환은 새 런타임 기능이 아닙니다. 메서드 시그니처의 반환 형식이 관리 포인터 형식(int&)이 될 뿐이고, 리플렉션도 그렇게 보여 줍니다. 그래서 반환 형식이 다른 Func<int, int> 에는 묶이지 않고, ref 를 돌려주는 대리자 형식을 따로 선언해야 합니다.

대리자를 통해서도 g(1) = 21 처럼 자리에 대입됩니다. 리플렉션의 Invoke 는 참조가 아니라 값(30)을 상자에 담아 돌려줍니다 — .NET 10 런타임에서의 동작입니다. 대리자의 반환 방식이 다르면 CS8189 "Ref mismatch" 입니다.

실행 검증

ref 반환은 시그니처의 일부 — 재정의와 인터페이스 구현

반환 형식이 int& 인 메서드와 int 인 메서드는 다른 시그니처입니다. 그래서 ref 를 돌려주는 가상 메서드를 값으로 돌려주며 재정의하거나, ref 를 돌려주는 인터페이스 멤버를 값 반환 메서드로 구현할 수 없습니다.

재정의는 CS8148 "must match by reference return", 인터페이스는 CS8152 입니다. 라이브러리가 공개 메서드에 ref 를 더하거나 빼면 파생 클래스와 구현체가 다시 컴파일되지 않는다는 뜻입니다. 호출자 쪽은 다릅니다 — whats-new 는 ref 를 더하는 것을 "source compatible change" 라고 적습니다.

실행 검증

ref 를 돌려주는 인덱서와 속성 — set 이 없어도 대입된다

속성과 인덱서의 getter 도 ref 를 돌려줄 수 있습니다. 돌려받은 자리에 바로 쓰므로 setter 가 필요 없고, 둘을 함께 두는 것은 컴파일러가 막습니다.

b[1] = 5 와 b[2]++ 는 setter 를 부르는 것이 아니라 getter 가 준 자리에 씁니다. ref 를 돌려주는 속성에 set 을 두면 CS8147 입니다 — 쓰기 경로가 둘이 되기 때문입니다. .NET 의 Span<T> 인덱서가 이 모양입니다(ref 를 돌려주는 BCL).

실행 검증

함정 — ref 는 배열 변수가 아니라 그 원소를 가리킨다

ref 지역 변수는 묶이는 순간의 저장소를 가리킵니다. 그 뒤에 배열 변수가 다른 배열로 바뀌어도 ref 는 옛 배열의 원소를 계속 가리킵니다.

Array.Resize 는 새 배열에 복사하므로 first = 100 은 아무도 안 보는 옛 배열에 들어갔습니다(a[0] 은 1). 둘째 줄은 keep 이 옛 배열을 붙잡고 있어 200 이 보입니다. List<T> 의 인덱서는 값을 돌려주므로 ref 로 잡을 수 없습니다(CS0206).

함정 — ref 지역 변수가 살아 있는 동안 그 배열을 바꿔치기하는 코드(크기 늘리기 등)가 끼면, 쓰기가 조용히 사라집니다. 오류도 경고도 없습니다.
실행 검증

함정 — 공변 배열의 원소를 ref 로 잡으면 실행 중에 던진다

C# 1 부터 string[] 은 object[] 로 쓸 수 있고(배열 공변성), 그래서 원소에 쓸 때마다 실행 중 형식 검사가 붙습니다. 표준은 ref 인수로 넘기는 배열 원소에도 같은 검사를 요구합니다 — 그 예가 F(ref b[1]); // ArrayTypeMismatchException 입니다. ref 지역 변수도 같은 길을 갑니다.

objs[1] = "y" 는 검사를 통과합니다(값이 진짜 string). 그러나 ref object o = ref objs[0] 은 무엇을 쓰기도 전에, 자리를 잡는 순간 ArrayTypeMismatchException 입니다. 그 ref 로 object 아무것이나 쓸 수 있게 되기 때문입니다. 제네릭 At<T> 에 string[] 을 그대로 넘기면 T 가 string 이라 괜찮습니다.

실행 검증

아무 데도 안 가리키는 ref 와 _ = r

Roslyn 의 깨지는 변경 문서(Visual Studio 2022 version 17.4): ref 지역 변수를 값으로 읽고 결과를 버리면(_ = local) 예전에는 읽기 자체를 생략했지만, 이제는 "The compiler will now dereference that local, ensuring that any side effects are observed."

-langversion:7.0 으로 컴파일해도 읽기가 일어나 NullReferenceException 이 납니다. 이 변화는 언어 버전이 아니라 컴파일러 판에 달린 것입니다. 옛 컴파일러의 출력(읽기 생략)은 여기서 재현할 수 없어 문서의 문장으로만 적습니다.

실행 검증

같이 온 런타임 — ref 를 돌려주는 BCL

ref 반환은 런타임 형식을 새로 요구하지 않았습니다. 대신 그 뒤의 .NET 라이브러리가 이 기능을 씁니다. 사전의 값 칸을 ref 로 돌려주면 "찾고, 읽고, 다시 넣는" 두 번의 조회가 한 번이 됩니다.

CollectionsMarshal 과 Span<T> 는 C# 7.0 보다 뒤의 라이브러리지만 -langversion:7.0 으로도 호출됩니다. 호출은 게이트가 아니기 때문입니다. ReadOnlySpan<T> 의 인덱서도 리플렉션에는 Int32& 로 보입니다 — C# 7.2 의 ref readonly 는 시그니처에 붙은 표시로 구별됩니다(7장). 마지막 줄의 수는 CoreLib 의 공개 형식에 있는 공개 메서드 가운데 ref 를 돌려주는 것의 개수입니다.

실행 검증

ref 의 다음 이야기 — 버전마다 풀린 제약

C# 7.0 의 ref 지역 변수는 한 번 묶이면 끝까지 같은 자리를 가리키고, 쓰기를 막을 길이 없었습니다. 그 뒤 버전들이 하나씩 넓혔습니다. 버전은 모두 컴파일러의 기능 목록에서 왔습니다.

버전무엇이 풀렸나어디서
C# 7.2ref readonly 반환, in 매개변수, 조건 ref 식7장
C# 7.3ref 지역 변수의 재할당 r = ref y, ref for·foreach8장
C# 11ref 필드, scoped, [UnscopedRef]12부
C# 13async·반복기 안의 ref 지역 변수5장
문서 근거

throw 식 (throw expression) C# 7.0

왜 — whats-new: "In C#, throw has always been a statement." 그래서 조건식, null 병합 식, 일부 람다에서 쓸 수 없었고, 식 본문 멤버가 늘면서 그런 자리가 더 많아졌습니다. 제안서는 throw 식을 허용하는 문법 자리를 정확히 셋으로 적습니다: ?: 의 둘째·셋째 피연산자, ?? 의 둘째 피연산자, 식 본문 람다·메서드의 본문.

실행 검증

이전엔 — 검사 한 줄이 문장 셋

whats-new 는 throw 식으로 "You don't need additional statements for error checking" 이라고 적습니다. 그 "additional statements" 가 C# 6 의 모양입니다.

식 본문(=>) 메서드는 C# 6 부터 있었지만, 몸체가 식 하나여야 하므로 검사가 붙으면 블록 몸체로 돌아가야 했습니다. 앞 장의 SetName 은 ?? 와 throw 식 덕분에 식 하나로 남습니다.

실행 검증

세 자리 밖에서는 — 문법 오류와 의미 오류

제안서의 문법은 throw 식을 null_coalescing_expression 단계에 둡니다. 그보다 우선순위가 높은 연산자(&&, +)의 피연산자 자리에는 문법상 들어가지 못합니다. 그 밖의 자리는 문법은 통과하고 의미 검사에서 막힙니다.

의미 단계의 오류는 CS8115 "not allowed in this context" 입니다. 괄호로 감싼 (throw …) 도 거절됩니다 — 괄호 식은 셋 중 어느 자리도 아닙니다. ?: 의 두 가지가 모두 throw 식이면 "A throw_expression has no type" 이라 결과 형식을 정할 수 없어 CS0173 입니다.

실행 검증

예외는 그 가지에 갈 때만 만들어진다, throw null 은

throw 식은 값이 아니라 "그 가지에 오면 던져라" 입니다. ?? 의 오른쪽은 왼쪽이 null 일 때만 평가됩니다. 제안서: 던질 값이 null 이면 "a System.NullReferenceException is thrown instead."

Check("x") 에서는 Make 가 불리지 않았습니다. 예외 객체를 미리 만들어 두는 비용이 없다는 뜻입니다. throw null 은 문장으로 쓸 때처럼 식으로 써도 NullReferenceException 이 됩니다.

실행 검증

throw 식 뒤에서는 모든 변수가 대입된 것으로 친다

제안서의 흐름 분석 규칙: "For every variable v, v is definitely assigned after throw_expression." throw 가지는 돌아오지 않으므로, 확정 대입은 다른 가지만 보고 판단합니다.

19행 뒤에 x 를 읽어도 됩니다. throw 대신 평범한 값 0 을 둔 BAD 줄에서는 그 가지가 z 를 대입하지 않으므로 CS0165 입니다.

실행 검증

람다의 본문 — 그리고 C# 10 의 자연 형식

제안서의 셋째 자리는 "the body of an expression-bodied lambda or method" 입니다. throw 식 하나만 있는 람다도 대상 형식이 있으면 어떤 반환 형식의 대리자로든 바뀝니다 — throw 식은 "convertible to every type" 이기 때문입니다.

C# 10 은 람다에 자연 형식을 주어 var f = () => … 를 허용하지만, 본문이 throw 식뿐이면 반환 형식을 정할 근거가 없어 CS8917 입니다. 형식이 없다는 throw 식의 성질이 뒤 버전에서도 그대로 드러나는 자리입니다.

실행 검증

일반화된 async 반환 형식 (task-like types) C# 7.0

왜 — whats-new: async 메서드가 늘 Task 를 돌려주면 동기로 끝나는 경로에서도 객체를 할당하고, 그것이 "a significant time cost in performance critical sections" 가 될 수 있다. 그래서 반환 형식이 Task·Task<T>·void 에 묶이지 않게 했습니다. 제안서의 정의: 작업 형식은 AsyncMethodBuilderAttribute 로 빌더 형식을 지정한 클래스나 구조체입니다.

default 리터럴 (target-typed default) C# 7.1

왜 — 제안서의 동기는 한 줄입니다: "The main motivation is to avoid typing redundant information." 예로 M(default(ImmutableArray<SomeType>)) 대신 M(default). 형식은 대상에서 정해지고, 그 밖에는 default(T) 와 똑같습니다.

new[] { default, "b" } 에서는 다른 원소 "b" 가 배열 형식을 정하고 default 는 그 형식(string)의 null 이 됩니다. 선택적 매개변수의 기본값 = default 는 5부에서 봤습니다.

실행 검증

대상 형식이 없으면 default 도 없다

제안서: default 리터럴의 형식 유추는 null 리터럴과 같은 방식이고, const int x = default; 는 되지만 const int? y = default; 는 안 된다. default == default 는 "illegal", 그리고 throw null; 은 되지만 default 로는 안 된다.

세 줄이 같은 CS8716 "There is no target type for the default literal" 입니다 — var, default.ToString(), throw default. const int? y 는 default 탓이 아니라 int? 가 상수 형식이 아니라서(CS0283) 거절됩니다. 7행 const int c = default 는 경고만 났습니다.
