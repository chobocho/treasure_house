  • 3장 — 최상위 문. 3장.

레코드와 init — 데이터를 값처럼

record · 컴파일러가 만드는 멤버 · 값 동등성과 EqualityContract · ToString · with · init 과 modreq · C# 10–12 에서 이어진 것

왜 레코드인가 — 정체성 대신 내용

발표 글은 고전적 객체 지향의 핵심을 "an object has strong identity and encapsulates mutable state that evolves over time" 라고 요약하고, 때로는 "pretty much the exact opposite" 를 원하는데 그때 C# 의 기본값이 "making things very laborious" 했다고 적습니다. 레코드는 "still a class" 이지만 "defined by their contents, not their identity" 입니다.

whats-new 는 손으로 쓰는 동등성의 값을 적습니다 — 클래스에서도 동등성 메서드와 연산자를 재정의할 수 있지만 "time-consuming and error-prone" 하고, 속성을 더할 때 재정의를 고치는 것을 잊는 버그를 막아 준다는 것입니다.

이 장의 차례 — 7부는 C# 6 의 불변 형식 38줄을 레코드 한 줄로 바꿔 보였습니다(7부). 이 장은 그 한 줄 뒤에서 컴파일러가 만드는 것을 하나씩 엽니다: 선언 → 만들어지는 멤버 → 값 동등성 → 출력 → with → init → 뒤 버전.
블로그·역사

레코드 선언 (record) C# 9.0

왜 — "You use the record keyword to define a reference type that provides built-in functionality for encapsulating data."

함정 — C# 8.0 의 거절에 'records' 라는 낱말이 없습니다. record 는 문맥 키워드라, 8.0 의 규칙으로 읽으면 4행은 record 형식을 돌려주는 지역 함수 Point의 선언입니다. 그래서 최상위 문(CS8400 'top-level statements'), 몸체 없는 지역 함수(CS8112), 찾을 수 없는 형식 record(CS0246)가 나옵니다. 'records' 거절이 어디서 나오는지는 다음 장에서 봅니다.
실행 검증

'records' 거절은 with 에서 나온다

선언은 8.0 에서 다른 것으로 읽히니, 게이트의 이름이 찍히는 자리는 C# 8.0 에 없던 식, with 입니다. 레코드가 아닌 클래스에 with 를 써서 두 판으로 컴파일합니다.

9.0 에서는 수신자가 레코드가 아니라는 CS8858 하나, 8.0 에서는 그 앞에 CS8400 'records' 가 붙습니다 — with 식은 'records' 게이트에 속합니다. CS8858 의 문장 끝 "and is not a struct type" 은 C# 10 에서 구조체에도 with 를 쓸 수 있게 된 것 (뒤에서)과 맞물립니다 — 문장은 지금의 컴파일러가 씁니다.

실행 검증

record 가 이름이던 코드 — C# 9 의 깨지는 변경 C# 9.0

Roslyn 의 C# 9 깨지는 변경 문서: C# 9 부터 record 가 형식 이름인지 레코드 선언인지 모호하면 레코드 선언으로 읽습니다. 문서의 예가 abstract record R3(); 입니다.

같은 소스가 두 판에서 다른 프로그램이 됩니다. 8.0 에서 R3 는 record 형식을 돌려주는 추상 메서드이고, 9.0 에서는 중첩 형식(추상 레코드)입니다. 9.0 은 형식 이름 record 에도 경고 CS8860 을 냅니다 — 컴파일은 되지만 쓰지 말라는 것입니다.

실행 검증

위치 레코드 — 매개변수 목록 하나가 만드는 것 C# 9.0

whats-new: 위치 문법이면 컴파일러가 매개변수마다 public init 전용 자동 속성, 매개변수가 같은 기본 생성자(primary constructor), 매개변수마다 out 을 가진 Deconstruct 를 만듭니다. 예제는 명세의 R 입니다.

생성자 매개변수의 기본값("xyz")과 이름 붙인 인수가 그대로 통합니다 — 기본 생성자는 보통 생성자입니다. 마지막 줄처럼 생성자를 부른 뒤 초기화자로 속성을 다시 채울 수도 있습니다. 속성이 set 이 아니라 init 이라 생성이 끝나기 전까지만입니다.

실행 검증

이름 있는 속성으로 쓰는 레코드

매개변수 목록 없이 몸체에 속성을 적어도 레코드입니다. 발표 글의 첫 레코드가 이 꼴이었습니다({ get; init; } 속성 둘).

함정 — 계산 속성 FullName 도 ToString 에 찍힙니다. 출력 대상은 "non-static public field and readable property members" 라서, 저장하지 않는 속성도 읽을 수 있으면 찍힙니다. 비어 있는 new Person() 의 마지막 칸이 공백 둘인 까닭입니다.

8.0 의 거절은 구문 오류뿐입니다 — record Person 다음의 { 를 읽을 규칙이 없습니다. 위치 레코드와 달리 Deconstruct 는 만들어지지 않습니다(뒤에서).

실행 검증

한 줄 뒤의 멤버 열일곱 — 리플렉션으로

명세는 레코드에 "synthesized members" 를 더한다고 적습니다. 위치 레코드 record P(int X) 와 sealed record S(int X) 가 실제로 가진 멤버를 늘어놓고, 접근성과 virtual 여부를 견줍니다.

명세가 정한 대로 sealed 쪽은 EqualityContract · PrintMembers · 복사 생성자가 private 이고 Equals(R) 이 virtual 이 아닙니다. <Clone>$ 라는 이름은 명세가 정한 것이 아니라 "compiler-reserved name" 의 구현입니다 — C# 으로는 부를 수 없는 이름이라 사용자 멤버와 겹치지 않습니다. init 접근자는 메타데이터에서 set_X 입니다(뒤에서).

실행 검증

명세의 "대략 이런 코드" 를 손으로

명세는 합성되는 동등성·출력 멤버를 "something like" 이라며 C# 으로 풀어 보입니다. 그 코드를 클래스 H 로 옮겨 적고, 레코드 R 과 나란히 돌립니다.

출력이 글자까지 같습니다. 레코드 한 줄이 이만큼의 코드입니다 — 복사 생성자와 복제 메서드, Deconstruct 는 아직 빠졌습니다. 손으로 쓴 쪽에서 속성 하나를 더하면 Equals · GetHashCode · PrintMembers 세 곳을 함께 고쳐야 합니다.

실행 검증

값 동등성 — ==, Equals, 해시 C# 9.0

왜 — "two variables of a record type are equal if the types match and all property and field values match. For other reference types, equality means identity." 레코드는 IEquatable<R> 을 구현하고 == != 도 갖습니다.

함정 — object 로 받아 == 를 쓰면 False 입니다. 연산자는 정적으로 고르는 것이라, 변수 형식이 object 면 참조 비교입니다. 가상 메서드인 Equals 는 어느 형식의 변수로 불러도 값 비교입니다.
실행 검증

레코드의 == 는 필드의 == 가 아니다

명세: 합성된 Equals 는 필드마다 EqualityComparer<T>.Default.Equals 를 부릅니다. double 이면 그것은 double.Equals 이고, == 와 NaN 에서 갈립니다.

NaN == NaN 은 거짓인데 NaN 을 담은 두 레코드는 == 로 같습니다. 튜플의 == 는 원소마다 == 를 써서 거짓입니다(8부). 같은 == 기호가 레코드에서는 Equals 를, 튜플에서는 원소의 == 를 뜻합니다. 0.0 과 -0.0 은 두 길 모두 같고 해시도 같습니다(.NET 10 에서).

실행 검증

배열과 리스트는 참조로 비교된다

필드마다 EqualityComparer<T>.Default — 배열과 List<T> 는 값 동등성을 재정의하지 않으니 참조 비교입니다. 출력도 "the type name of the object that the property refers to" 가 찍힙니다.

내용이 같아도 o1 == o2 는 거짓이고, 같은 배열을 나눠 가진 with 사본 o3 과는 참입니다. 레코드의 값 동등성은 얕습니다. 컬렉션을 값으로 비교하려면 Equals(R) 과 GetHashCode 를 직접 씁니다(뒤에서).

실행 검증

보이지 않는 필드도 비교된다

명세: 동등성은 "each instance field" 를, 출력은 public 멤버만 봅니다. 두 목록이 다르니 찍힌 모양은 같은데 같지 않은 레코드가 생깁니다.

함정 — 로그에 찍힌 두 값이 글자까지 같은데 == 는 거짓입니다. 캐시 번호, 지연 계산 결과 같은 내부 필드를 레코드에 두면 동등성에 끼어듭니다. with 의 초기화자가 private 필드를 바꿀 수 있는 것도 보십시오 — 형식 안이라 접근할 수 있습니다.
실행 검증

Equals(R) 을 직접 쓰면

명세: Equals(R) 은 직접 선언할 수 있고, == 는 그 메서드를 부릅니다. 다만 Equals(R) 만 쓰고 GetHashCode 를 안 쓰면 경고입니다.

함정 — 경고 CS8851 을 넘기면 "같은데 해시가 다른" 객체가 생깁니다(셋째 줄). HashSet · Dictionary 에서 같은 이름이 둘로 들어갑니다. Equals(R) 을 바꾸면 GetHashCode 도 같은 규칙으로 바꿉니다.
실행 검증

레코드 전 — 상속과 손으로 쓴 Equals

레코드가 왜 EqualityContract 라는 낯선 멤버를 갖는지는, 레코드 없이 상속 계층에 값 동등성을 손으로 넣어 보면 보입니다.

p.Equals(c) 는 참, c.Equals(p) 는 거짓 — 대칭이 깨졌습니다. Point 의 Equals 는 상대가 ColorPoint 여도 is Point 를 통과시키기 때문입니다. whats-new 가 손으로 쓰는 동등성을 "error-prone" 이라고 한 대표적인 자리입니다.

실행 검증

EqualityContract — 실행 형식이 같아야 같다

명세: 기반 레코드의 Equals 는 필드를 견주기 전에 EqualityContract == other.EqualityContract 를 봅니다. 합성된 속성은 typeof(R) 을 돌려주고, 파생 레코드는 그것을 재정의합니다.

필드가 똑같아도 Base(1) 과 Derived(1) 은 어느 쪽에서 물어도 다릅니다 — 계약이 Base 와 Derived 로 갈리기 때문입니다. 앞 장의 비대칭이 레코드에서는 생기지 않습니다.

실행 검증

EqualityContract 를 직접 쓰면 — 비대칭이 돌아온다

명세는 EqualityContract 를 "can be declared explicitly" 라고 합니다. 파생 레코드가 기반인 척 typeof(Base) 를 돌려주게 해 봅니다.

함정 — b == d 는 참, d == b 는 거짓입니다. Base 쪽은 계약만 보고 통과시키지만, Derived 쪽의 Equals(object) 는 명세대로 other as Derived 로 바꿔 보다가 null 이 됩니다. 컴파일러는 막지 않습니다. 계약을 고치는 일은 거의 언제나 대칭을 깹니다.

whats-new: 레코드는 레코드만 상속하고, 두 변수가 같으려면 "the run-time type must be equal" 입니다. 출력에는 파생과 기반의 public 멤버가 모두 들어갑니다. 예제는 whats-new 의 Person · Teacher · Student 입니다.

값이 모두 같은 Teacher 와 Student 는 다르고, Person 변수와 Student 변수에 든 두 학생은 같습니다 — 변수 형식이 아니라 실행 형식입니다. 분해는 기반의 Deconstruct(매개변수 둘)를 씁니다. 파생의 Deconstruct 는 셋입니다.

추상 레코드와 복제 메서드 — 공변 반환을 쓰는 곳

명세: 추상 레코드의 복제 메서드는 추상이고, 파생 레코드의 것은 그것을 재정의하면서 자기 형식을 돌려줍니다. 버전 기록은 공변 반환이 바로 "derived records" 를 위해 들어왔다고 적습니다.

실행 검증

컴파일러가 만드는 ToString C# 9.0

왜 — 레코드는 "public properties and fields" 의 이름과 값을 <record type name> { <property name> = <value>, … } 꼴로 찍습니다. 명세: 출력 대상은 "non-static public field and readable property members" 입니다.

첫 줄은 whats-new 가 보인 줄과 같습니다. 중첩 레코드는 그 레코드의 ToString 으로 찍히고, null 은 빈칸이며, 멤버가 없으면 Empty { } 입니다. 마지막 줄에는 public 필드 Count 만 있고 private 필드와 static 필드는 없습니다.

실행 검증

PrintMembers 를 직접 — 비밀번호 가리기

명세: ToString 은 이름과 " { " 를 적고 PrintMembers 를 부릅니다. PrintMembers 는 직접 쓸 수 있고, 파생 레코드의 합성된 PrintMembers 는 먼저 기반의 것을 부릅니다.

파생 레코드도 비밀번호를 가린 채 자기 멤버 Level 만 덧붙입니다. ToString 을 통째로 바꾸면 파생 레코드가 다시 합성한 ToString 이 그것을 덮지만(뒤에서), PrintMembers 를 바꾸면 계층 전체가 따릅니다.

실행 검증

자기를 가리키는 레코드의 ToString

명세: 합성된 PrintMembers 는 출력할 멤버가 있으면 먼저 RuntimeHelpers.EnsureSufficientExecutionStack() 을 부릅니다. 고리를 만들어 확인합니다.

함정 — 고리가 있으면 ToString 은 끝나지 않습니다. 그래도 프로세스가 스택 넘침으로 죽지 않고 잡을 수 있는 InsufficientExecutionStackException 이 납니다 — 스택 검사 덕입니다. 동등성(Equals)과 GetHashCode 의 명세에는 이 검사가 없습니다 — 이 덱은 고리를 가진 두 레코드의 비교는 돌려 보지 않았습니다.

발표 글: 같은 이름의 속성을 직접 쓰면 컴파일러가 만든 생성자와 Deconstruct 가 그것을 쓰고, 매개변수는 초기화에 쓸 수 있게 범위 안에 있습니다. 글의 예는 FirstName 을 protected 로 바꾼 것입니다.

실행 검증

다른 생성자는 this(…) 를 거친다

함정 — 대상을 적지 않은 특성은 생성자 매개변수에만 붙습니다. 속성에 붙어야 하는 특성(직렬화·검증용)을 위치 매개변수에 달 때는 property: 를 적어야 합니다.

명세: 레코드는 자기 형식 하나를 받는 복사 생성자와 이름이 예약된 복제 메서드를 가집니다. 복사 생성자는 "doesn't run any instance field/property initializers" 입니다.

with 로 만든 c 는 a 의 번호 1 을 그대로 갖고, 번호표(next)도 넘어가지 않아 다음 새 표가 3 입니다. 초기화자에 부수 효과를 두면 new 와 with 의 결과가 달라집니다.

레코드에 쓸 수 없는 것

명세가 금하는 넷을 한 파일에 넣었습니다 — 클래스 상속, 레코드를 상속하는 클래스, == 의 직접 선언, Clone 이라는 이름.

실행 검증

바뀌는 레코드를 사전의 키로

레코드는 set 속성도 가질 수 있습니다. 발표 글: "We don't disallow mutable records, but we discourage them unless you have thought through the consequences!" — 값이 바뀌면 GetHashCode 도 바뀌기 때문입니다.

함정 — 키를 바꾸자 그 키로도, 원래 값과 같은 새 키로도 못 찾습니다. 항목은 사전 안에 그대로 있습니다(Count 1). 바뀐 해시로는 다른 칸을 보고, 원래 칸에서는 값이 달라졌기 때문입니다. whats-new 가 불변의 쓸모로 "a hash code to remain the same in a hash table" 을 꼽은 까닭입니다.

class · struct · record · 튜플을 나란히

값 동등성은 구조체에도 있었습니다. whats-new 는 큰 데이터 모델에서 구조체의 단점 셋을 듭니다 — 상속이 없고, ValueType.Equals 는 리플렉션으로 필드를 찾으니 값 동등성이 덜 효율적이고(컴파일러가 만든 레코드의 Equals 가 "measurably faster" 라고 합니다), 인스턴스마다 데이터 전체를 복사해 갖는다는 것입니다.

명세: 먼저 수신자의 복제 메서드를 부르고, 그 결과에 초기화자의 대입을 "in lexical order" 로 합니다. 복사 생성자와 init 접근자가 찍게 해서 순서를 봅니다.

복사 생성자가 먼저, 그다음 적은 차례대로 B 와 A 의 init 입니다. with 는 init 접근자를 부르는 자리라, 바뀌는 멤버는 set 이나 init 이 있어야 합니다. 버전 기록이 init 을 "the capability for nondestructive mutation" 이라고 소개한 까닭입니다.

with 는 얕은 복사

발표 글: with 는 "copying the full state of the old object into a new one" 입니다. 상태가 참조라면 참조가 복사됩니다.

함정 — blue 에 넣은 bob 이 red 에도 있습니다. 두 레코드가 같은 리스트를 가리킵니다. 그래서 마지막 줄처럼 이름만 되돌린 green 이 red 와 같다고 나옵니다 — 리스트가 참조로 비교되고, 그 참조가 같으니까요.

명세: 복사 생성자는 직접 선언할 수 있고, 봉인되지 않은 레코드라면 public 이나 protected 여야 합니다. with 는 그 생성자를 거칩니다.

이번에는 red 가 그대로입니다. 대가로 필드를 하나 더할 때마다 이 생성자도 고쳐야 합니다 — 손으로 쓴 동등성에서 본 문제가 복사 쪽으로 옮겨 온 것입니다.

실행 검증

with 는 생성자의 검사를 건너뛴다

with 는 복사 생성자와 init 접근자만 부릅니다(앞에서). 그러면 기본 생성자에 넣은 검사는 어떻게 될까요.

함정 — new Percent(200) 은 막히지만 p with { Value = 200 } 은 그대로 통과합니다. 속성 초기화자는 기본 생성자에서만 돌고, 복사 생성자는 초기화자를 돌리지 않으며(앞에서), 자동 init 접근자에는 검사가 없기 때문입니다. 검사를 init 접근자 안에 두면(Checked) with 도 막힙니다.
실행 검증

with 가 거절되는 곳

명세: 수신자는 레코드여야 하고, 초기화자의 이름은 접근할 수 있는 필드나 속성이어야 하며, with 식은 문(statement)이 될 수 없습니다.

get 만 있는 Y 는 보통의 "읽기 전용" 오류(CS0200)입니다. 문으로 쓴 with 는 전용 오류가 아니라 구문 오류 (CS1002)가 됩니다 — { 앞에서 ; 를 기다리는 것은 r with 를 식으로 읽지 않았다는 뜻입니다.

실행 검증

null 에 with 를 쓰면

with 의 첫 단계는 수신자의 복제 메서드 호출입니다. 수신자가 null 이면 그 호출이 실패합니다.

컴파일러는 막지 않고 실행 중에 NullReferenceException 입니다. nullable 문맥(9부)을 켜면 Find 의 반환 형식을 Point? 로 적게 되고, 그때 경고가 이 자리를 짚습니다.

실행 검증

뒤 버전 — 구조체와 익명 형식의 with (C# 10)

C# 9 의 with 는 레코드에만 쓸 수 있었습니다. 컴파일러는 구조체와 익명 형식의 with 를 C# 10 의 두 기능으로 적습니다.

C# 9.0 으로 내린 거절의 번호는 CS8773 입니다 — "C# N 에는 없다" 는 오류는 언어 버전마다 번호가 따로 있습니다(8.0 은 CS8400). C# 10 의 명세: 구조체 수신자는 "first copied" — 복제 메서드 없이 값을 복사한 뒤 초기화자를 적용합니다.

실행 검증

init 접근자 (init-only setter) C# 9.0

왜 — 명세의 동기: 불변 데이터를 만드는 수단은 "haven't changed since 1.0" — readonly 필드와 get 만 있는 속성입니다. 그런 형식은 객체 초기화자를 쓸 수 없어 "developers must choose between ease of use and immutability" 였습니다. init 은 생성하는 동안만 쓰게 해 그 선택을 없앱니다. 예제는 명세의 Point 그대로입니다.

이전엔 — 명세가 든 C# 8 까지의 Point 는 get 만 있는 속성 둘에 그것을 채우는 생성자를 따로 썼습니다. 명세의 말로 "twice as much boiler plate code to support construction as it does to declare the type" 입니다. C# 6 의 get 전용 속성은 7부에 있습니다.
실행 검증

init 을 부를 수 있는 다섯 자리

명세가 "construction phase" 라 부르는 곳입니다 — 객체 초기화자, with 식의 초기화자, 그 형식이나 파생 형식의 인스턴스 생성자(this · base 에), 다른 init 접근자 안, 특성의 이름 붙인 인수.

파생 형식의 생성자가 기반의 init 속성을 채우는 것(3)은 get 전용 속성으로는 못 하던 일입니다. 특성(5)의 Text 도 init 이라 [Note(Text = …)] 로 채워지고, 읽어 온 특성 객체에서는 바꿀 수 없습니다.

실행 검증

init 을 부를 수 없는 자리 — CS8852

명세는 다섯 자리에 단서를 답니다 — "except when in a local function or lambda". 생성자 안의 람다와 지역 함수도 안 됩니다. whats-new 가 든 오류 번호는 CS8852 입니다.

10행(생성자)과 19행(초기화자)만 통과하고 넷이 CS8852 입니다. 람다와 지역 함수는 생성이 끝난 뒤에 불릴 수 있으니, 생성자 안에 적혔어도 생성 단계로 치지 않습니다.

실행 검증

init 과 readonly 필드

발표 글: init 접근자는 초기화 중에만 불리므로 "just like you can in a constructor" readonly 필드를 바꿀 수 있습니다. 명세: 단 "declared on the same type" 의 필드만입니다.

init 접근자에 검사를 넣을 수 있어 자동 속성이 아닌 init 도 쓸모가 있습니다. 파생 형식은 기반의 readonly 필드를 못 바꿉니다 — 명세는 그래야 "type authors remain in control" 이라고 적습니다. CS0191 의 문장에 "init-only setter of the type in which the field is defined" 가 들어 있습니다.

실행 검증

init 의 제약 — static, set 과 함께, get 없이

명세의 제약: init 은 인스턴스 속성에만, 한 속성에 init 과 set 을 함께 둘 수 없습니다.

set; init; 은 전용 오류가 아니라 "Property accessor already defined"(CS1007)입니다 — 컴파일러에게 init 은 또 하나의 set 입니다. get 없는 자동 속성은 "must have get accessors"(CS8051)입니다.

실행 검증

재정의와 인터페이스 구현 — init 은 init 으로

명세: 가상 속성이 init 이면 재정의도 모두 init 이어야 하고, set 을 init 으로 재정의할 수도 없습니다. 인터페이스 구현에도 같은 규칙입니다.

init 과 set 은 서로를 대신하지 못합니다. 메타데이터에서 둘의 시그니처가 다르기 때문입니다(뒤에서).

실행 검증

인터페이스의 init — 제네릭으로 채우기

명세의 예: 인터페이스가 { get; init; } 를 선언하면, new() 제약을 가진 T 를 초기화자로 채울 수 있습니다.

이름이 정해지지 않은 형식 T 에도 생성 단계의 규칙이 그대로 통합니다. 오타 "Jraed" 까지 명세의 예 그대로입니다.

실행 검증

readonly struct 와 init

명세: init 은 readonly struct 의 속성과 readonly 속성에 쓸 수 있지만, init 접근자 자체에 readonly 를 붙일 수는 없습니다.

컴파일러의 문장이 고칠 길을 알려 줍니다 — 접근자 대신 속성에 readonly 를 붙이라고. readonly 멤버는 9부에 있습니다.

실행 검증

init 인덱서

요약문: 이 제안은 "init only properties and indexers" 를 더합니다. 인덱서의 init 은 C# 6 의 인덱스 초기화자 [0] = … 와 짝을 이룹니다.

인덱스 초기화자는 C# 6 의 문법입니다(7부). 인덱서도 속성과 같은 CS8852 로 생성 뒤의 쓰기를 막습니다.

실행 검증

init 의 메타데이터 — modreq(IsExternalInit) C# 9.0

명세: init 접근자는 보통의 set 접근자로 내보내되, 반환 형식에 IsExternalInit 의 modreq 를 붙입니다. 특성이 아니라 modreq 를 고른 까닭은 둘 — 옛 컴파일러가 init 을 어기지 못하게 하고, 가상 멤버와 인터페이스에서 init 을 더하거나 빼는 것을 소스와 바이너리 모두 깨지는 변경으로 만들기 위해서입니다.

함정 — modreq 는 컴파일러끼리의 약속입니다. 리플렉션의 SetValue 는 생성 뒤에도 init 속성을 바꿉니다. 명세는 modreq 가 "Reflection over public members" 와 "The use of dynamic" 을 막지 못한다고 적었는데, 이 런타임(.NET 10)의 dynamic 바인더는 읽기 전용이라며 거절했습니다. 리플렉션 쪽은 명세의 말 그대로입니다.
실행 검증

IsExternalInit 을 직접 선언하면 — 옛 대상의 길

명세: 컴파일러는 이 형식을 "by full name" 으로 찾고, "There is no requirement that it appear in the core library" 입니다. 여럿이면 컴파일하는 프로젝트의 것이 코어 라이브러리의 것을 이깁니다. 그래서 이 형식이 없는 옛 대상에서도 같은 이름의 형식을 직접 선언하면 init 을 쓸 수 있습니다.

modreq 가 가리키는 형식은 이 예제 자신의 어셈블리 a(csrun 이 붙이는 이름, 0부)에 있습니다. 코어 라이브러리에도 같은 형식이 있지만(True) 프로젝트의 것이 이겼습니다. 옛 대상(.NET 5 이전)에서의 실행은 이 기계에서 보일 수 없어 명세의 문장까지만 근거로 듭니다.

실행 검증

init 은 채우기를 강제하지 않는다

명세의 "Warn on failed init" 절: init 멤버를 안 채운 생성 코드에 경고를 낼지 논의했고, 결론은 "There will be no warning on consumption of init fields and properties" 였습니다.

함정 — 경고 하나 없이 null 과 0 이 남습니다. init 은 "생성 뒤에 못 바꾼다" 이지 "생성할 때 꼭 채운다" 가 아닙니다. 위치 레코드라면 생성자 인수가 채우기를 강제하지만, 몸체에 적은 init 속성(Subject)은 아닙니다.

문서 근거

뒤 버전 — required 멤버 (C# 11)

init 의 명세는 '필수' 멤버를 따로 논의하겠다고 적었고(앞에서), 컴파일러는 'required members' 를 C# 11 의 기능으로 적습니다.

init 은 "생성 뒤 못 바꿈", required 는 "생성할 때 꼭 채움" 입니다. 둘을 함께 쓰면 앞에서 본 빈칸이 오류 (CS9035)가 됩니다. C# 10.0 으로 내린 거절 번호는 CS8936 입니다. C# 11 은 12부에서 다룹니다.

실행 검증

뒤 버전 — record struct (C# 10)

C# 9 의 레코드는 참조 형식뿐이었습니다. 컴파일러는 'record structs' 를 C# 10 의 기능으로 적습니다.

C# 10 의 명세대로 위치 record struct 의 속성은 init 이 아니라 set 이라 p.X = 10 이 됩니다. 불변을 원하면 readonly record struct 입니다. C# 9.0 으로 내리면 C# 9 의 레코드와 뜻이 같은 record class 까지 'record structs' 로 거절됩니다 — class 라고 적는 문법 자체가 C# 10 의 것입니다.

실행 검증

뒤 버전 — 클래스의 기본 생성자 (C# 12)

레코드의 매개변수 목록은 C# 12 에서 클래스와 구조체로 넓어졌습니다. 컴파일러는 'primary constructors' 를 C# 12 의 기능으로 적습니다. 같은 꼴의 두 선언을 견줍니다.

함정 — 같은 괄호인데 뜻이 다릅니다. 레코드의 X 는 public init 속성(True)이고, 클래스의 X 는 속성이 없는(False) 매개변수라 몸체가 포착해 바꿀 수도 있습니다(Move 뒤 합이 4). 클래스에는 값 동등성도 ToString 도 생기지 않습니다. C# 12 는 13부에서 다룹니다.

문서 근거

2장 퀴즈 — 레코드와 init

Q. record Team(string Name, List<string> Members); 에서 var a = new Team("x", new List<string>()); var b = a with { }; b.Members.Add("y"); 를 차례로 했습니다. a == b 는 무엇이고, a.Members 에는 무엇이 들어 있습니까?

A. True, 그리고 a.Members 에도 "y" 가 있습니다. with 는 복제 메서드로 필드를 그대로 옮기는 얕은 복사라 두 레코드가 같은 리스트를 가리킵니다. 동등성은 필드마다 EqualityComparer<T>.Default 라 리스트는 참조로 비교되고, 참조가 같으니 같습니다. 깊은 복사를 원하면 복사 생성자를 직접 씁니다.
