최상위 문 — Main 없는 프로그램

컴파일러가 만드는 Program 과 <Main>$ · 시그니처를 정하는 본문 · args 와 종료 코드 · 파일 하나 · 지역 함수 · 이름의 범위 · 뒤 버전의 using

왜 — 한 줄짜리 일에 열 줄의 의식

제안서의 동기: 가장 단순한 프로그램에도 명시적인 Main 때문에 틀(boilerplate)이 붙고, 그것이 "language learning and program clarity" 를 가로막는다는 것입니다. 목표는 "C# programs without unnecessary boilerplate around them, for the sake of learners and the clarity of code".

C# 8.0 까지의 Hello World실제로 일하는 줄
using System; · namespace · class Program · static void Main(string[] args) · 중괄호 여섯 Console.WriteLine("Hello World!"); 하나

whats-new 는 그 표준 Hello World 를 보여 주고 "There's only one line of code that does anything" 이라고 적습니다. 버전 기록은 C# 9 의 첫 주제를 "removing ceremony" 로 꼽고, 최상위 문을 그 예로 듭니다 — 네임스페이스도, Program 클래스도, static void Main() 도 필요 없다고.

문서 근거

최상위 문 (top-level statements) C# 9.0

왜 — 문법의 변화는 하나입니다. 컴파일 단위(소스 파일)의 using 지시문 뒤, 네임스페이스·형식 선언 앞에 문이 올 수 있습니다.

거절은 첫 문의 자리(4행)에서 한 번 나옵니다. 이 덱의 예제 대부분은 class App { static void Main() … } 꼴인데, 그래야 C# 8.0 이하로 내려 거절을 보일 때 그 기능 하나만 거절되기 때문입니다. 최상위 문으로 쓴 예제는 8.0 에서 늘 이 거절이 먼저 섞입니다.

실행 검증

컴파일러가 만드는 것 — Program 과 <Main>$ C# 9.0

제안서: 최상위 문은 전역 네임스페이스의 Program 클래스, 그 안의 진입점 메서드 본문에 들어간 것처럼 다룹니다. Program 은 이름으로 부를 수 있지만 메서드 이름은 "implementation dependent" 라 소스에서 부를 수 없습니다.

Roslyn 이 고른 이름은 <Main>$ — C# 식별자로는 쓸 수 없는 글자를 넣어 소스와 부딪치지 않게 했습니다. 클래스에는 CompilerGenerated 가 붙고 메서드에는 특성이 없습니다(마지막 foreach 가 아무것도 찍지 않았습니다). 매개변수의 이름은 args, typeof(Program) 은 진입점을 가진 바로 그 형식입니다.

실행 검증

진입점의 시그니처는 본문이 정한다 — void 와 int

제안서의 표: 최상위 문에 비동기 연산과 "값을 가진 return" 이 있느냐에 따라 진입점은 void, int, Task, Task<int> 를 돌려줍니다. 같은 파일을 -define 만 바꿔 컴파일해 봅니다.

return 3; 한 줄이 진입점을 Int32 <Main>$ 로 바꾸고, 그 값이 프로세스의 종료 코드가 됩니다. 시그니처를 적는 곳이 없으니 본문이 곧 시그니처입니다.

실행 검증

await 가 있으면 — Task 를 돌려주는 본문과 감싸는 진입점

whats-new: 최상위 문에는 비동기 식이 들어갈 수 있고, 그러면 합성된 진입점이 Task 나 Task<int> 를 돌려준다고 적습니다.

메서드가 둘이 됩니다. 본문은 Task <Main>$(또는 Task`1)로 컴파일되고, 실제 진입점은 이름에서 $ 가 빠진 <Main> 입니다. 이 감싸개가 작업이 끝나기를 기다려 void 나 int 를 돌려줍니다 — C# 7.1 의 async Main (8부)과 같은 짜임입니다.

실행 검증

args — 최상위 문 안에서만 보이는 매개변수

제안서: 진입점은 늘 string[] args 하나를 받고, 그 배열은 "never null" 이며 인수가 없으면 길이 0 입니다. args 는 최상위 문 안에서만 범위에 있습니다.

같은 파일 안이어도 클래스의 메서드에서는 args 가 CS0103 입니다. args 는 숨은 진입점 메서드의 매개변수일 뿐이라, 다른 멤버에 넘기려면 값으로 넘겨야 합니다.

실행 검증

return 의 값이 종료 코드 — 그리고 모든 길에 return

whats-new: 최상위 문이 정수를 돌려주면 그 값이 합성된 Main 의 "integer return code" 가 됩니다.

함정 — return 2; 가 하나라도 있으면 진입점은 int 가 되고, 그때부터 모든 길이 값을 돌려줘야 합니다. 오류는 메서드 이름 대신 '<top-level-statements-entry-point>' 를 대고, 자리도 파일의 첫 토큰(2행의 using)을 가리킵니다 — 고칠 곳은 파일 끝인데도.
실행 검증

최상위 문은 파일 하나에만

whats-new: "Only one file in your application may use top-level statements. If the compiler finds top-level statements in multiple source files, it's an error." 진입점은 하나뿐이고, 두 파일의 문을 어떤 차례로 이어 붙일지 정할 근거가 없습니다.

csrun 은 디렉터리의 *.cs 를 모두 컴파일합니다. 오류는 둘째 파일(B.cs)에 붙습니다 — 첫 파일이 자리를 차지한 뒤 나온 쪽이 틀린 것으로 칩니다.

실행 검증

Main 이 따로 있으면 — 경고, 그리고 -main

제안서: 최상위 문이 만든 메서드가 진입점이고, 관례상 진입점이 될 만한 메서드는 무시하되 경고를 냅니다. 다른 진입점은 -main:<type> 스위치로 고를 수 있습니다.

오류가 아니라 경고 CS7022 입니다 — "The entry point of the program is global code". -main:App 을 주면 경고 없이 App.Main 이 돌고, 최상위 문은 컴파일만 되고 불리지 않습니다. whats-new 는 이 조합을 "an error" 라고 적지만, 이 컴파일러에서는 경고입니다.

실행 검증

최상위의 함수는 메서드가 아니라 지역 함수

제안서의 예는 최상위 문 아래에 Fib 를 선언하고, 그것이 합성된 진입점 안의 지역 함수가 된다고 보여 줍니다.

지역 함수라서 위의 지역 변수 calls 를 붙잡을 수 있고, 그 대가로 클로저 구조체(<>c__DisplayClass0_0)가 생깁니다. 이름은 <<Main>$>g__Add|0_0 처럼 감싼 메서드의 이름을 품습니다. 메서드가 아니니 오버로드도 안 됩니다 — 같은 이름은 CS0128. 지역 함수는 C# 7.0 의 기능입니다(8부).

실행 검증

차례 — 문이 먼저, 형식 선언은 뒤에

문법은 extern_alias_directive* using_directive* global_attributes? statement* namespace_member_declaration* 입니다. 문은 형식 선언 앞에만 올 수 있습니다.

형식은 문 뒤에 선언해도 문에서 쓸 수 있습니다 — 형식 선언에는 차례가 없습니다. 거꾸로 클래스 뒤에 온 문은 CS8803 으로 거절됩니다. 지역 함수는 문이라 이 규칙과 상관없이 문 사이 어디에나 올 수 있습니다(앞 장).

실행 검증

최상위 문은 늘 전역 네임스페이스에 — 그리고 C# 10 의 namespace X;

제안서: 최상위 문은 "a Program class in the global namespace" 의 진입점에 들어갑니다. 같은 파일에 네임스페이스 블록이 있어도 Program 은 전역에 남습니다.

블록 네임스페이스 안의 Cart 는 Shop.Cart, Program 은 전역입니다. C# 10 의 파일 범위 네임스페이스는 파일 전체를 그 네임스페이스에 넣는 선언이라 최상위 문 뒤에 올 수 없습니다(CS8956) — 최상위 문을 쓴 파일은 블록 꼴을 써야 합니다.

실행 검증

최상위의 지역 이름은 프로그램 전체를 가린다 C# 9.0

제안서: 최상위 지역 변수와 지역 함수는 진입점 안에 들어가지만 이름 찾기에서는 "in scope throughout the program in every compilation unit" 입니다. 전역 네임스페이스에 닿으면 먼저 진입점 안에서 이름을 찾고, 최상위 문 밖에서 그렇게 찾은 이름은 오류입니다. 나중에 "top-level functions" 를 들일 여지를 남기려는 설계입니다.

함정 — BAD 에서 바뀐 것은 최상위 문 두 줄뿐인데, 오류는 멀리 떨어진 Report.Make(17행)에서 납니다. 클래스 Title 이 지역 변수 Title 에 가려진 것입니다. 메서드 안의 지역 변수라면 다른 클래스에 닿지 않을 텐데, 최상위의 지역은 다릅니다.
실행 검증

Program 은 partial — 내 Program 에 멤버를 더하려면

제안서: 합성되는 형식 Program 은 partial 이라, 소스에 같은 이름의 형식을 쓰려면 그것도 partial 이어야 합니다. Roslyn 의 호환성 문서는 .NET 5 와 VS 16.9 까지는 Program 이라는 형식이 따로 있어도 됐고, .NET 6 과 VS 17.0 부터 partial 이어야 한다고 적습니다.

최상위 문은 Program 의 메서드 안에 있으니 Helper(), Version 을 한정 없이 부릅니다. partial 을 빼면 -langversion:9.0 에서도 CS0260 입니다 — 문서가 말한 차이는 언어 버전이 아니라 컴파일러 버전에 묶여 있습니다 (꼴 (나)가 아닙니다 — 0부).

실행 검증

스택 트레이스에 보이는 이름

"메서드 이름은 구현 세부" 라는 말은 소스에서만 맞습니다. 실행 중의 진단 — 예외의 스택 트레이스, 호출자 정보 특성 — 에는 컴파일러가 지은 이름이 그대로 나옵니다.

[CallerMemberName] 은 <Main>$ 를 채웁니다(6부에서 본 것). 트레이스의 두 줄은 Program.<<Main>$>g__Fail|0_1 과 Program.<Main>$ — 로그를 검색할 때 소스에 없는 이름을 찾아야 합니다. 종료 코드 -6 은 처리하지 않은 예외로 런타임이 프로세스를 끝낸 것입니다.

실행 검증

누구를 위한 기능인가 — 문서의 답

whats-new 는 가장 흔한 쓰임으로 교재를 꼽습니다 — 처음 배우는 사람이 Hello World 를 "in one or two lines of code" 로 씁니다. 숙련자에게는 "a script-like experience for experimentation similar to what Jupyter notebooks provide", 작은 콘솔 프로그램과 유틸리티, 그리고 Azure Functions 를 듭니다.

명령 줄 인수와 반환값을 그대로args(길이 0, null 아님), return → 종료 코드

문서 근거

최상위 문만으로는 한 줄이 안 된다 — using

whats-new 의 한 줄짜리 프로그램은 System.Console.WriteLine 처럼 이름을 다 적거나 using System; 을 둡니다. 최상위 문은 의식의 절반만 걷어 냈습니다.

이 덱의 ex.csproj 는 모두 <ImplicitUsings>disable</ImplicitUsings> 이고, csrun 은 MSBuild 를 거치지 않으니 SDK 가 더해 주는 using 도 없습니다. 그래서 이 덱의 예제는 C# 9 문법으로 쓴 것도 using System; 으로 시작합니다. 나머지 절반은 다음 장.

실행 검증

뒤 버전 — global using 과 암시적 using, C# 10 · .NET 6

C# 10 은 global using 지시문을 더했습니다 — 한 파일에 두면 컴파일 전체에 걸립니다. .NET 6 SDK 의 암시적 using(implicit usings)은 <ImplicitUsings>enable</ImplicitUsings> 하나로 프로젝트 종류에 맞는 global using 들을 더하고, .NET 6 템플릿이 그것을 켭니다.

C# 9 의 최상위 문과 C# 10 의 global using 이 만나야 템플릿의 Program.cs 가 정말 한 줄이 됩니다. 9.0 으로 내렸을 때의 거절 번호는 CS8773 — 8.0 의 CS8400 과 다른, 9.0 을 대상으로 한 번호입니다. 자세한 것은 11부.

3장 퀴즈 — 최상위 문

Q1. 최상위 문에 await Task.Delay(1); 과 return 1; 이 있습니다. 리플렉션의 EntryPoint 는 어떤 이름과 반환 형식을 보여 줄까요?

Q2. 최상위 문에 int Count = 0; 을 두었더니, 다른 파일의 클래스가 쓰던 Count.Of(x)(static 클래스 Count)가 갑자기 오류가 났습니다. 왜일까요?

A1. Int32 <Main>. 본문은 Task<int> <Main>$ 로 컴파일되고, 진입점은 그것을 기다리는 감싸개 <Main> 입니다(비동기).
A2. 최상위의 지역 이름은 프로그램 전체의 이름 찾기에서 전역 네임스페이스보다 먼저 찾아지고, 최상위 문 밖에서 찾아지면 CS8801 입니다 (범위).

패턴 3 — 크기를 견주고, 패턴을 엮는다

관계 패턴 · and · or · not · 괄호 · 형식 패턴 · 좁혀지는 입력 · 빠짐없음 · 결정 DAG · 뒤 버전의 패턴

왜 — "0 보다 크다" 를 가드 없이

버전 기록: C# 9 는 "providing more patterns in more places" 라는 주제를 잇고, 숫자 형식에 range patterns 가 생겼으며, 패턴을 and·or·not 으로 엮고 괄호로 묶을 수 있게 됐다고 적습니다.

제안서는 여섯 가지를 "natural synergy" 를 가진 묶음으로 내놓습니다 — 형식 패턴, 괄호 패턴, and, or, not, 관계 패턴.

C# 8.0 까지C# 9.0
int a when a < 2 — 범위는 가드로< 2 — 관계 패턴
o is object, !(o is null)o is not null
case int _: — 버릴 변수라도 이름 자리case int: — 형식 패턴

앞 부에서 미리 본 것: 8부, 9부. 이 장은 거기서 멈춘 곳 — 의미, 함정, 컴파일러의 판단 — 을 이어 갑니다.

문서 근거

관계 패턴 (relational pattern) C# 9.0

왜 — 제안서의 첫 예는 나이로 생애 단계를 가르는 switch 식입니다. 입력이 상수와 견주어 <·<=·>·>= 를 만족하는지가 패턴 하나가 됩니다.

갈래는 위에서부터 처음 맞는 것이 이기므로 < 2 다음의 < 12 는 사실상 "2 이상 12 미만" 입니다. 거절은 관계 패턴마다 하나씩, 다섯 번입니다.

실행 검증

이전엔 — 같은 표를 C# 8.0 의 when 가드로

C# 8.0 의 switch 식(9부)에서 크기 비교는 패턴이 아니라 가드의 일이었습니다. 같은 표를 -langversion:8.0 으로 씁니다.

갈래마다 쓰지도 않을 변수 a 를 선언하고 다시 견줍니다. 가드는 아무 식이나 될 수 있어 컴파일러가 갈래끼리의 관계를 따질 수 없습니다 — 관계 패턴이면 뒤에서 볼 빠짐없음과 이미 다룬 갈래를 컴파일러가 셉니다.

실행 검증

입력의 형식 — 같은 형식이면 비교, 아니면 형식 검사부터

제안서: 입력이 상수와 같은 내장 비교 연산자를 가진 형식이면 그 연산자가 패턴의 뜻입니다. 아니면 입력을 상수의 형식으로 바꿔 보고, 바뀌지 않으면 맞지 않습니다 — "The relational does include an implicit type test to the type of the constant". 상수는 컴파일 때 정해져야 하고 NaN 이면 오류입니다.

함정 — object 에 담긴 50L 과 50.0 은 "0 이상 100 이하" 에 맞지 않습니다. 상수 0 과 100 이 int 이므로 패턴은 먼저 "int 인가" 를 봅니다. 제안서는 여러 형식을 받으려면 >= 0F and <= 100F or … 처럼 형식마다 따로 쓰라고 합니다. int? 의 null 도 어떤 관계 패턴에도 맞지 않습니다.
실행 검증

되는 형식, 안 되는 형식 — 열거형·nint 와 string

제안서는 관계 패턴이 되는 형식으로 정수 형식들, char, float, double, decimal, nint, nuint 를 꼽습니다 — "all of the built-in types that support such binary relational operators".

목록에 없는 열거형도 됩니다 — 열거형에는 내장 비교 연산자가 있으니 "binary relational operators" 를 가진 형식이라는 기준에 맞습니다. 이름 없는 값 (Level)7 도 크기대로 mid 에 듭니다. string 은 < 연산자가 없어 CS8781 입니다.

and 와 or — 패턴을 엮는 결합자 C# 9.0

왜 — 제안서: and 와 or 는 "useful for testing ranges of values" 이고, and 가 or 보다 단단히 묶입니다. whats-new 의 첫 예가 아래의 IsLetter 입니다.

c is >= 'a' and <= 'z' or >= 'A' and <= 'Z' 는 (… and …) or (… and …) 로 읽힙니다 — 산술의 곱셈과 덧셈처럼. i is 0 or 1 or 2 는 C# 8.0 이라면 i == 0 || i == 1 || i == 2 로 썼을 식입니다. C# 8.0 의 거절은 게이트 표.

괄호 패턴 — 결합의 차례를 바꾸거나 드러내거나 C# 9.0

왜 — 제안서: 괄호 패턴은 C# 8.0 의 패턴에는 별 쓸모가 없었지만, 새 결합자가 우선순위를 들여오면서 그것을 "override" 하거나 강조할 길이 필요해졌습니다. 문법의 우선순위는 not > and > or 입니다.

A 의 not 0 and > -5 는 "0 이 아니고 -5 보다 큰" 것, B 의 not (0 or > -5) 는 "-5 이하" 입니다. -1 과 2 에서 둘이 갈립니다. C 의 괄호는 뜻을 바꾸지 않습니다 — and 가 어차피 먼저 묶이지만, 읽는 사람을 위해 씁니다.

함정 — not 은 바로 옆 패턴 하나만 뒤집는다

not 은 가장 단단히 묶이는 결합자입니다(negated_pattern : 'not' negated_pattern | primary_pattern). 그래서 "1 도 2 도 아니다" 를 x is not 1 or 2 로 쓰면 (not 1) or 2 가 됩니다.

함정 — wrong 은 2 에서 True 입니다. or 2 는 아무것도 더하지 않는 군더더기인데, 이 컴파일러는 언어 버전을 14.0 으로 올리고 경고 수준을 끝까지 올려도 아무 말이 없습니다. 바른 꼴은 not (1 or 2), 또는 not 1 and not 2 입니다.

두 줄 모두 C# 9.0 에서 컴파일되고 돕니다. or 와 and 는 뒤에 패턴이 올 수 없는 자리(), &&)에서는 변수 이름으로 읽힙니다. 문서의 "error" 는 뒤에 패턴이 이어질 수 있는 자리의 이야기로 보입니다 — 어느 쪽이든 새 코드에서 이런 이름은 피하는 것이 맞습니다.

not 과 or 아래에는 패턴 변수를 둘 수 없다

제안서의 결론: "Pattern variables can't be declared beneath a not or or pattern." 어느 쪽이 맞았는지 모르면 변수가 확실히 대입됐다고 할 수 없기 때문입니다. 대신 if (e is not int i) return; 뒤에서는 i 를 쓸 수 있습니다.

is not string s 의 s 는 "패턴이 거짓일 때 대입됨" 이라 return 뒤 줄에서 쓸 수 있습니다 — 제안서가 꼽은 시나리오 그대로입니다. or 아래의 i 는 CS8780, not int j 의 j 를 패턴이 참일 때 쓰면 대입되지 않은 변수(CS0165)입니다.

제안서: and 의 왼쪽 패턴이 정한 "narrowed type" 이 오른쪽 패턴의 입력 형식이 됩니다. o is byte and < 100 의 < 100 은 object 가 아니라 byte 를 견줍니다. "Result: The above narrowing semantics have been implemented."

(byte)5 는 byte 로 좁혀진 뒤 < 100 과 견주어집니다. 좁히지 않은 < 10L 은 상수가 long 이라 long 인지부터 봅니다 — 7L 은 맞고 70L 은 마지막 갈래로 갑니다. int 7 은 그 전에 int i 에 잡힙니다.

범위로 따지는 빠짐없음 — 빠진 값을 컴파일러가 집는다

엮은 패턴도 검사를 나눠 쓴다 — getter 를 세어 보면

C# 8.0 의 재귀 패턴에서 본 결정 DAG(9부)는 and·or 와 관계 패턴에도 그대로 쓰입니다. 갈래 넷에 W 와 H 가 여러 번 나오지만, 컴파일러는 같은 속성을 한 번 읽고 나머지는 그 값으로 가릅니다.

4장 퀴즈 — 패턴 3

Q1. object o = 3.5; 일 때 o is > 0 and < 10 은 무엇일까요?

Q2. "0 도 아니고 음수도 아닌" 을 x is not 0 or < 0 으로 썼습니다. x = -3 이면?

Q3. if (o is not int n) return; 다음 줄에서 n 을 쓸 수 있을까요?

A1. False. 상수가 int 라 패턴은 먼저 "int 인가" 를 보고, double 은 거기서 떨어집니다 (입력의 형식).
A2. True. (not 0) or (< 0) 로 읽혀 -3 은 왼쪽에서 맞습니다. 바른 꼴은 not (0 or < 0), 곧 > 0 (not 의 범위).
A3. 쓸 수 있습니다. 패턴이 거짓일 때 대입되는 변수라, 거짓이 아니면 돌아가 버린 뒤의 줄에서는 확실히 대입돼 있습니다(패턴 변수).

문서 근거

원시 크기 정수 nint · nuint (native-sized integers) C# 9.0

왜 — 제안서의 동기는 한 줄, "interop scenarios and for low-level libraries" 입니다. nint 와 nuint 는 새 문맥 키워드이고, 기계의 원시 정수 크기(포인터 크기)를 따릅니다.

64비트 기계라 sizeof(nint) 는 8, 최댓값은 long 의 그것입니다. 32비트 기계라면 같은 프로그램이 4 와 int 의 최댓값을 찍습니다 — 그래서 문서가 여러 플랫폼에서 시험하라고 합니다. sizeof(nint) 는 상수가 아니라 unsafe 문맥이 필요합니다.

실행 검증

nint 의 정체 — System.IntPtr

제안서: nint 는 System.IntPtr 로 표현되고 컴파일러가 변환과 연산을 덧붙입니다. typeof(nint) 는 typeof(IntPtr) 이고, 메타데이터에서는 NativeIntegerAttribute 로 어느 자리가 nint 였는지 표시한다고 적습니다.

.NET 10 을 대상으로 하면 -langversion:9.0 에서도 NativeIntegerAttribute 가 붙지 않습니다. C# 11 whats-new 는 "The nint and nuint types now alias System.IntPtr" 라고 적는데, 이 변화는 언어 버전이 아니라 대상 런타임이 숫자형 IntPtr 를 지원하느냐에 묶여 있습니다(다음 장). 옛 런타임에서의 특성 부착은 이 기계에서 재현할 수 없습니다.

IntPtr 에도 산술이 — 언어 버전이 아니라 런타임이 정한다

Roslyn 의 .NET 7 호환성 문서: 플랫폼이 숫자형 IntPtr 를 지원하면(RuntimeFeature.NumericIntPtr) "the built-in operators from nint and nuint apply to those underlying types".

세 언어 버전이 모두 같습니다 — nint 라는 낱말이 없는 이 코드는 C# 8.0 에서도 컴파일됩니다. 옛 IntPtr 에는 * 연산자가 없었으니, .NET 7 이전 런타임이었다면 거절됐을 코드입니다(그 런타임은 이 기계에 없어 캡처는 없습니다). 이 동작은 언어 버전에 묶여 있지 않습니다.

실행 검증

상수는 32비트 안에서만 — 넘으면 실행 때 계산

whats-new: nint 상수는 int 범위 안에서만 쓸 수 있고, 상수 접기(constant folding)는 Int32·UInt32 로 합니다. "If the result doesn't fit in 32 bits, the operation is executed at run time and isn't considered a constant."

Small + 1 은 32비트를 넘어 상수가 아닙니다. 컴파일러는 CS8973 "may overflow 'nint' at runtime" 을 경고하고, 64비트인 이 기계에서는 2147483648 이 나옵니다. 컴파일하는 기계와 돌리는 기계의 크기가 다를 수 있으니, 결과가 기계마다 다를 수 있는 계산은 상수로 접지 않는 것입니다.

실행 검증

넘침 — checked 의 nint, 그리고 IntPtr

제안서의 연산자 표: nint 의 + 는 unchecked 에서 add, checked 에서 add.ovf 입니다. .NET 7 호환성 문서는 숫자형 IntPtr 플랫폼에서 IntPtr 의 checked 연산도 "can now throw" 라고 적습니다.

unchecked 는 MinValue 로 돌아 넘어가고, checked 는 OverflowException 입니다. 아래 절반은 IntPtr 로 쓴 같은 코드인데 역시 던집니다 — 호환성 문서가 "may now throw" 라고 경고한 동작입니다.

dynamic 은 nint 의 연산자를 모른다

제안서: 변환과 연산자는 컴파일러가 만드는 것이라 IntPtr 형식 자체에는 없고, 그래서 dynamic 의 런타임 바인더는 쓸 수 없다고 적습니다 — RuntimeBinderException: '+' cannot be applied 'System.IntPtr' and 'System.IntPtr'.

.NET 10 에서도 제안서가 적은 그대로입니다. 숫자형 IntPtr 이후 정적 컴파일러는 IntPtr 에 산술을 허락하지만(앞에서), C# 4 의 런타임 바인더 (5부)는 여전히 IntPtr 를 연산자가 없는 형식으로 봅니다.

뒤 버전 — nint 와 제네릭 수학, C# 11 · .NET 7

숫자형 IntPtr 로 IntPtr 가 숫자 형식이 되면서, .NET 의 제네릭 수학 인터페이스(INumber<T>)를 구현하는 형식에도 들어갑니다. 제네릭 수학은 C# 11 의 정적 추상 인터페이스 멤버에 기댑니다.

C# 9 의 nint 가 C# 11 의 제네릭 코드에 그대로 들어갑니다. 10.0 의 거절은 T.Zero 와 s += x — 형식 매개변수의 정적 멤버와 연산자를 부르는 자리입니다. 자세한 것은 12부.

실행 검증

함수 포인터 delegate* (function pointers) C# 9.0

왜 — 제안서: IL 명령 ldftn 과 calli 는 고성능 코드에 중요한데 C# 에서는 "efficiently, or at all" 쓸 수 없었습니다. delegate* 문법은 Func·Action 을 닮게 만들었고, 마지막 형식 인수가 반환 형식입니다.

부르는 모양은 대리자와 같습니다 — p(2, 3). &Add 는 C# 의 주소 연산자를 메서드 그룹에 쓴 것이고, 함수 포인터는 포인터 형식이라 unsafe 문맥이 필요합니다(AllowUnsafeBlocks). 8.0 의 거절은 선언 하나(9행)에서만 나옵니다 — 선언 오류가 메서드 본문의 오류를 가립니다.

실행 검증

컴파일러가 내는 것 — ldftn·calli 와 newobj·callvirt

whats-new: "Invoking the delegate* type uses calli, in contrast to a delegate that uses callvirt on the Invoke() method. Syntactically, the invocations are identical." 두 메서드의 IL 을 명령 단위로 뽑아 봅니다.

포인터 쪽은 ldftn 으로 주소를 얻어 calli 로 부르고 끝입니다. 대리자 쪽은 같은 ldftn 뒤에 Func`2 객체를 newobj 로 만들고, 그 객체의 가상 메서드 Invoke 를 callvirt 로 부릅니다. 최적화를 끄면(csrun 의 기본) nop·br.s 같은 디버그용 명령이 섞입니다(아래).

실행 검증

할당 — 대리자는 객체, 함수 포인터는 주소

버전 기록: 함수 포인터는 "delegate-like functionality while avoiding the allocations necessary to create a delegate object". 호출마다 메서드 그룹을 대리자로 바꾸는 반복문에서 할당된 바이트를 셉니다.

꼴 (나) — 언어 버전에 묶인 동작(0부) — 9.0 에서는 호출마다 64바이트짜리 Func 객체가 새로 생깁니다. 11.0 으로 올리면 대리자 쪽도 0 입니다. C# 11 컴파일러는 정적 메서드 그룹에서 만든 대리자를 캐시해 다시 씁니다 — 옛 표준이 금했던 일입니다(3부). 함수 포인터의 이점이 "할당 없음" 하나라면 C# 11 이후 그 차이는 이 자리에서 줄었고, 남는 것은 앞 장의 calli 와 대리자 객체를 거치지 않는 호출입니다.
실행 검증

호출 규약 — managed 와 unmanaged, [UnmanagedCallersOnly] C# 9.0

왜 — 제안서: 함수 포인터의 형식에는 호출 규약(calling convention)이 들어갑니다. 기본은 managed, unmanaged 는 플랫폼의 기본 규약이고 unmanaged[Cdecl] 처럼 고를 수도 있습니다. 네이티브 쪽에서 부를 C# 메서드에는 [UnmanagedCallersOnly] 를 붙이고, 그런 메서드는 C# 에서 직접 부를 수 없습니다.

delegate*<int, int> 와 delegate* managed<int, int> 는 같은 형식이라 그냥 대입됩니다. 규약이 다른 둘 사이는 암시적 변환이 없고, [UnmanagedCallersOnly] 메서드의 주소는 managed 포인터에 담기지 않습니다(CS8786). unmanaged 포인터로 부르면 런타임이 네이티브 → 관리 코드의 전환을 끼워 넣습니다.

실행 검증

함수 포인터가 못 하는 것 — 포인터 형식이라서

제안서: delegate* 는 포인터 형식의 제약을 그대로 가집니다 — object 로 바꿀 수 없고 제네릭 인수가 될 수 없습니다. & 는 static 메서드에만 쓰고, 같은 이름의 오버로드는 대상 포인터의 시그니처로 고릅니다. 같은 함수를 가리키는 두 포인터의 비교는 경고 대상입니다.

인스턴스 메서드가 안 되는 까닭은 제안서의 "Allow instance methods" 고려에 있습니다 — 정적 지역 함수로 감싸면 되는 일이라 넣지 않았습니다. 비교 경고 CS8909 는 같은 함수의 주소가 서로 다를 수 있다고 말하고, 실행 결과(True)는 이 실행에서의 우연일 뿐입니다.

실행 검증

리플렉션이 보는 함수 포인터 — .NET 10

제안서: delegate* 는 ECMA-335 의 함수 포인터 형식으로 표현됩니다. .NET 10 의 리플렉션은 그 형식을 Type 으로 돌려주고, 반환 형식·매개변수·규약을 물어볼 수 있습니다.

FieldType 은 IntPtr 가 아니라 IsFunctionPointer 가 참인 형식이고, 이름은 System.String(System.Int32) 처럼 시그니처 꼴입니다. 값을 꺼내면(GetValue) 상자에 담긴 IntPtr 가 나옵니다 — 포인터는 object 가 될 수 없으니 런타임이 주소로 바꿔 줍니다. 이 API 가 어느 .NET 에서 생겼는지는 이 덱의 문서에 없어 적지 않습니다.

실행 검증

왜 이 모양인가 — 버린 대안들

제안서의 "Considerations" 는 고르지 않은 길을 적어 둡니다.

대안버린 까닭(제안서)
Func<int>* — 대리자 형식에 별표메타데이터에 담기 어렵다. 다른 어셈블리의 Func 마다 같은 형식을 만들어야 한다
선언에서는 unsafe 를 묻지 않기포인터라는 사실이 계속 새어 나와 규칙이 어색했다

마지막 줄이 함수 포인터의 값을 정리합니다 — 언로드에 안전하려면 delegate, 그 안전을 내려놓으면 delegate*. 안전하지 않은 포인터는 struct 로 감싸 바깥에 안전한 API 를 보일 수 있다고 제안서는 덧붙입니다.

문서 근거

[SkipLocalsInit] — localsinit 플래그 빼기 C# 9.0

왜 — 제안서: C# 컴파일러는 지역 변수가 있는 모든 메서드에 localsinit 플래그를 내보내고, CLR 은 그 플래그를 보고 지역 변수와 stackalloc 메모리를 0 으로 채웁니다. 고성능 코드에서는 그 비용이 보이고 특히 stackalloc 에서 큽니다. SkipLocalsInitAttribute 가 그 플래그를 끕니다.

리플렉션의 MethodBody.InitLocals 가 메서드 머리의 그 플래그입니다. 특성 하나로 Skipped 만 False 가 됐습니다. 제안서는 이 특성을 "a compiler feature and not a language feature" 라고 못 박습니다 — 다음 장.

실행 검증

게이트가 없다 — 언어 기능이 아니라 컴파일러 기능

컴파일러의 기능 목록(MessageID)에 이 특성의 항목은 없습니다 — 제안서가 "compiler feature" 라고 한 그대로입니다. 대신 unsafe 컴파일을 요구합니다 — 0 으로 채우지 않은 메모리를 읽을 수 있게 되기 때문입니다. whats-new 도 원시 크기 정수를 뺀 둘에 "The other features require unsafe code" 라고 적습니다.

7.3 에서도 특성이 그대로 먹습니다 — 지금의 컴파일러는 언어 버전과 상관없이 이 특성을 봅니다. 그래서 "C# 9.0 의 기능" 이라는 말은 이 특성을 알아보는 컴파일러가 C# 9.0 과 함께 나왔다는 뜻입니다. 끄는 스위치는 언어 버전이 아니라 -unsafe 입니다(CS0227).

실행 검증

형식에 붙이면 — 람다와 지역 함수까지

제안서: 특성은 메서드, 속성, 생성자, 클래스, 구조체, 인터페이스, 모듈에 붙일 수 있고, 그릇에 붙이면 그 안의 모든 메서드에 걸립니다. 컴파일러가 만든 메서드는 "inherit" 합니다.

람다의 몸체는 컴파일러가 만든 중첩 클래스 <>c 의 메서드가 되지만 그것도 False — 특성을 물려받았습니다. 특성 밖의 App.Main 만 True 이고, 모듈에 붙이면 그것까지 꺼집니다.

실행 검증

보이는 차이 — 0 으로 채우지 않은 stackalloc

제안서: 지역 변수가 0 이 아닌 것은 C# 에서 "in most cases unobservable" 이지만 stackalloc 의 데이터는 "definitely observable" 입니다.

함정 — 특성 없는 Zeroed 는 늘 0 으로 채워진 메모리를 받지만, Raw 는 앞서 Dirty 가 남긴 찌꺼기를 봅니다. 몇 바이트가 남는지는 JIT 와 스택 배치에 달려 이 덱은 "모두 0 인가" 만 찍습니다. 이 특성을 붙인 코드는 stackalloc 한 메모리를 읽기 전에 반드시 써야 합니다.
실행 검증

같이 온 런타임 — 특성, 호출 규약 형식, RuntimeFeature

이 장의 기능은 런타임의 형식에 기댑니다. [SkipLocalsInit] 는 특성 형식, unmanaged 함수 포인터는 CallConv* 형식과 [UnmanagedCallersOnly], 숫자형 IntPtr 는 RuntimeFeature.NumericIntPtr 로 컴파일러에게 알려집니다.

제안서가 자리 표시 이름 "unmanaged ext" 로 부르며 런타임 지원을 확인하겠다던 것은 .NET 10 에서 UnmanagedSignatureCallingConvention 이라는 상수로 보입니다 — 이름의 대응은 이 덱의 추정입니다. 목록의 다른 상수(기본 인터페이스 메서드, 공변 반환, ref 필드 …)도 각 부의 언어 기능이 기대는 런타임 표시입니다.
