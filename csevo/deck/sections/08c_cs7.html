C# 7.2 — 복사하지 않는 안전한 코드

in · ref readonly · readonly struct · ref struct 와 Span · ref 조건식 · private protected ·

C# 7.2 한눈에

버전 기록은 C# 7.2 를 "several small language features" 를 더한 버전이라 적지만, 게이트 여덟 가운데 다섯이 한 주제 — 값 형식을 복사하지 않고 넘기되 안전하게 — 에 묶여 있습니다.

문서 근거

"안전한 코드가 unsafe 만큼 빠르게"

whats-new 는 7.2·7.3 의 성능 기능을 한 절로 묶고 이렇게 시작합니다. "You should be able to write C# code safely that performs as well as unsafe code." 안전한 코드는 "buffer overruns, stray pointers, and other memory access errors" 를 막아 주니, 그 코드가 느리지 않게 하겠다는 것입니다.

명세는 왜 이때인가에 답합니다. 문제는 오래됐지만 C# 이 새 분야에 쓰이며 커졌다고 — 계산 시간이 곧 돈인 "cloud/datacenter scenarios", 지연에 민감한 "Games/VR/AR" 를 듭니다.

문서 근거

in 매개변수 — 참조로 넘기되 고치지 못하게 C# 7.2

왜 — 명세의 동기: 값으로 넘기면 "copying, which adds unnecessary costs", 그래서 사람들은 ref 로 넘기고 "rely on comments/documentation to indicate that the data is not supposed to be mutated" 했습니다. XNA 의 벡터·행렬 연산자가 그 예입니다.

부르는 쪽의 in 은 생략할 수 있습니다. new Big(2) 처럼 변수가 아닌 값(rvalue)도 받는데, 이때 컴파일러가 임시 변수를 만들어 그 참조를 넘깁니다 — 명세의 "A reference to a temporary is passed in such case".

실행 검증

in 은 readonly 필드처럼 다뤄진다

명세: "For all purposes the in parameter is treated as a readonly variable." 구조체 in 매개변수의 필드도 "recursively classified as readonly" 입니다. 부르는 쪽에 in 을 쓰면 인수는 "readable LValue" 여야 합니다.

셋은 쓰기(CS8331·CS8332·CS8330), 둘은 "참조로 넘길 수 없는 식"(CS8156)입니다. in new Big() 은 거절되지만 in 없이 Sum(new Big()) 이라 쓰면 받아 줍니다 — 부르는 쪽의 in 은 "이 변수 그 자체를 넘긴다" 는 약속이기 때문입니다.

실행 검증

함정 — in 으로 받은 구조체의 메서드는 복사본에서 돈다

명세: 구조체 메서드는 this 를 쓰기 가능한 참조로 받으므로, 읽기 전용 변수에서 부르면 "the invocations are applied to temp copies". in 과 ref readonly 가 생기면 "the problem of defensive copying will get worse" 라고 명세 스스로 적습니다.

in 으로 받은 c 에서 Bump() 를 두 번 불러도 c.N 은 0 입니다. 호출마다 컴파일러가 몰래 복사본을 만들고 그것을 고친 뒤 버리기 때문입니다(방어 복사, defensive copy). readonly 필드와 ref readonly 지역 변수도 같습니다. 오류도 경고도 없습니다 — 큰 구조체라면 in 으로 아끼려던 복사가 오히려 호출마다 생깁니다.

이전엔 — readonly 필드에서는 C# 1 의 문법으로도 같은 일이 일어납니다. -langversion:1 로 컴파일한 2부의 예제가 같은 결과를 냅니다. 표준은 in 매개변수·readonly 필드·readonly 참조 변수를 한 목록에 두고 "a temporary local variable … is created" 라고 적습니다. C# 7.2 는 읽기 전용 변수를 흔하게 만들었을 뿐입니다. 해법은 readonly struct 입니다.
실행 검증

in 은 복사본이 아니라 별칭이다

명세: "reading an in parameter can observe different values as a side effect of other evaluations." 다만 부르는 쪽이 in 을 쓰지 않았고 인수가 변수가 아니면 "a temporary may be used".

처음 두 줄은 x 가 g 그 자체라서 42 를 봅니다 — in 을 생략해도 인수가 변수면 참조로 넘어갑니다. 아래 두 줄은 값(g + 0, (int)g)이라 임시 변수가 넘어가 1 이 남습니다. Roslyn 의 문서는 C# 7.2 까지 (x + 0) 이 x 로 줄어 참조로 넘어갈 수 있던 일을 적고, "C# 7.3 will preserve the behavior of the rvalue" 라고 고쳤습니다.

실행 검증

값과 in 으로 오버로드하면 — 7.2 와 7.3 의 답이 같다

명세: "It is permitted to overload on ordinary byval and in differences." whats-new: "The by value … overload is better than the by readonly reference version. To call the version with the readonly reference argument, you must include the in modifier".

수식어 없는 호출은 값 쪽, in 을 쓴 호출만 in 쪽입니다. 버전 기록은 C# 7.3 에서 "Method resolution when arguments differ by in was improved" 라고 적지만, 지금의 컴파일러는 이 프로그램에 7.2 와 7.3 에서 같은 답을 냅니다 — 그 개선은 언어 버전에 묶여 있지 않거나 이 경우가 아닙니다.

실행 검증

in 을 쓸 수 없는 곳 — 람다·반복기·async

명세: "For the purpose of lambda/async capturing in parameters behave the same as out and ref parameters" — 클로저에 포착할 수 없고, 반복기와 async 메서드에는 둘 수 없습니다.

async 를 한 파일에 같이 두면 CS1988 하나만 나오고 앞의 둘은 가려집니다(둘째 캡처) — 그래서 async 예제를 따로 두었습니다. 세 오류 문장 모두 ref, in or out 을 한데 말합니다 — in 은 새 기능이지만 규칙은 ref 의 것을 그대로 물려받았습니다.

실행 검증

in 은 메타데이터에서 무엇인가

명세: IsReadOnlyAttribute 가 붙은 참조 매개변수가 in 이고, abstract·virtual 메서드와 대리자의 Invoke 에는 modreq[InAttribute] 도 붙습니다 — "existing compilers cannot simply ignore readonly".

세 매개변수 모두 형식은 Int32&(참조)이고 IsReadOnlyAttribute 와 InAttribute 를 답니다. modreq 는 abstract 메서드와 대리자에만 있습니다 — 재정의·대리자 변환에서 옛 컴파일러가 in 을 ref 로 잘못 보는 일을 막는 자물쇠입니다. static 메서드는 재정의될 일이 없으니 특성만으로 충분합니다.

실행 검증

ref readonly 반환과 ref readonly 지역 변수 C# 7.2

왜 — 명세: 그전에는 "1) return by reference and be exposed to possible mutations or 2) return by value which results in copying" 둘 중 하나였습니다. ref readonly 는 "return variables by reference without exposing them to mutations" 합니다. 받는 쪽에는 짝이 되는 ref readonly 지역 변수가 생겼습니다.

r 은 원소 자체의 별칭이라 나중의 Set(1, 99) 를 보고, copy 는 받을 때 복사했으므로 2 를 지닙니다. 복사할지 말지는 부르는 쪽이 정합니다. 몸체의 return ref 에는 readonly 를 다시 쓰지 않습니다 — 명세는 그것이 "unnecessary long" 이라 했습니다.

실행 검증

ref readonly 가 막는 것 — 그리고 "값은 참조로 돌려줄 수 없다"

명세의 규칙: 읽기 전용 참조에서 쓰기 가능한 참조는 얻을 수 없습니다("but not the other way around"). 새 규칙 하나가 더 붙었습니다: "RValues are not safe to return by reference" — in 에 넘긴 임시 값이 ref readonly 로 되돌아 나가는 길을 막으려는 것입니다.

Leak 의 두 오류는 default(Big) 이 임시 변수를 거쳐 Echo 의 in 으로 들어가고, 그 참조가 메서드 밖으로 나가려 한다는 뜻입니다(CS8156·CS8347). 마지막 줄은 통과합니다 — static readonly 필드는 ref readonly 로는 가리킬 수 있습니다.

함정 — whats-new: 이미 있는 ref 반환에 readonly 를 더하는 것은 "an incompatible change" 입니다. 위의 ref Big w = ref At(0) 처럼 받던 호출자가 모두 CS8329 로 깨집니다.
실행 검증

readonly struct — this 를 in 으로 C# 7.2

왜 — 명세: "a feature that makes this parameter of all instance members of a struct, except for constructors, an in parameter." 그 대가로 인스턴스 필드는 모두 readonly, 자동 속성은 get 만, 필드 같은 이벤트는 금지입니다.

컴파일러는 readonly 를 System.Runtime.CompilerServices.IsReadOnlyAttribute 로 남깁니다. 명세는 그 특성이 없으면 컴파일러가 어셈블리에 직접 만들어 넣는다고 적었는데("embedded by the compiler"), .NET 10 에서는 System.Private.CoreLib 의 것을 씁니다.

실행 검증

readonly struct 에는 방어 복사가 없다 — 눈으로 보기

명세의 예: in 으로 받은 readonly struct 의 ToString() 은 "no need to make a copy" 입니다. 복사가 있었는지는 "메서드가 도는 동안 바깥에서 원래 변수를 바꾸면 this 가 그것을 보느냐" 로 알 수 있습니다.

in Plain 의 메서드는 복사본에서 돌아 바깥의 쓰기를 못 봅니다(False). in Frozen 은 복사 없이 F 자체에서 돌아 봅니다(True). 읽기 전용이 아닌 필드 P 에서 직접 부르면 보통 구조체도 복사가 없습니다. 메서드 하나만 골라 readonly 를 붙이는 길은 C# 8 에 생겼습니다(9부).

함정 — .NET 10 의 Unsafe.AsRef 는 C# 12 의 ref readonly 매개변수로 선언돼 있어서, in 을 붙여 부르는 코드는 -langversion:7.2 에서 CS8320 으로 거절됩니다. 언어 버전을 낮춰도 새 라이브러리의 시그니처가 그 버전의 문법을 요구할 수 있습니다.
실행 검증

왜 Span 은 스택에만 있어야 하나

span-safety 명세는 이유를 둘 듭니다. 하나, Span<T> 는 뜻으로 보면 (ref T data, int length) 인 구조체라 쓰기가 원자적이지 않고, 동시에 찢어 쓰이면(tearing) 길이와 데이터가 어긋나 "GC heap corruption in seemingly "safe" code" 에 이를 수 있습니다. 둘, 어떤 구현은 필드에 관리 포인터를 직접 담는데 "Managed pointers are not supported as fields of heap objects" 입니다.

명세의 언어 제약(줄임)이 장의 캡처
박싱 금지 — object·ValueType 변환 없음, 인터페이스 구현 없음힙에 두려는 일곱 길
배열 원소·형식 인수·튜플 원소 금지힙에 두려는 일곱 길
필드는 다른 ref struct 의 인스턴스 필드로만클래스의 필드
람다·지역 함수가 포착 금지포착·async·반복기
async·반복기의 매개변수 금지, await·yield 를 넘어 살지 못함포착·async·반복기
더 좁은 범위의 값을 넓은 곳에 대입·반환 금지스택 메모리의 탈출

이 제약을 Span 하나가 아니라 모든 "ref-like types" 에 거는 문법이 ref struct 입니다.

문서 근거

ref struct — Span 을 필드로 가질 수 있는 구조체 C# 7.2

명세: "Designating a struct as ref-like will allow the struct to have ref-like instance fields and will also make all the requirements of ref-like types applicable to the struct." Span 을 담는 더 큰 형식을 만들려면 그 형식도 같은 제약을 져야 하기 때문입니다.

new Span<int>(data, 2, 3) 은 배열의 세 칸을 복사 없이 가리킵니다. w.Items[0] = 100 이 원래 배열의 data[2] 를 바꾼 것이 그 증거입니다. Span 을 foreach 로 도는 것도 이미 됩니다.

실행 검증

ref struct 를 힙에 두려는 일곱 가지 길

명세: "A value of a ref struct type may not be boxed" — object·ValueType 로의 변환이 없고, 재정의하지 않은 object 의 메서드도 부를 수 없고, 메서드를 대리자로 만들 수도 없습니다.

r.ToString() 은 CS0029(ValueType 으로 변환 불가)입니다 — 재정의하지 않은 ToString 은 받는 쪽을 박싱해야 부를 수 있기 때문입니다. 형식 인수의 CS9244 문장에는 "a type parameter allowing ref structs" 라는, C# 13 의 낱말이 섞여 있습니다 (뒤 버전). Span 을 필드로 가지려면 담는 쪽도 ref struct 여야 합니다.

실행 검증

포착도, async 도, 반복기도 안 된다

명세: ref struct 형식의 지역 변수·매개변수는 "lifted into a lambda or local function" 될 수 없고, 그런 매개변수는 "an iterator method or an async method" 에 올 수 없습니다.

오류 문장이 s 를 "ref local" 이라 부릅니다 — 컴파일러에게 Span 지역 변수는 ref 지역 변수와 같은 무리입니다. 두 번째 파일은 async 의 CS4012 하나만 보고합니다 — 반복기 쪽은 가려진 것이 아니라, 쓰지 않은 Span 매개변수가 애초에 오류가 아닙니다. s 를 쓰는 자리에서야 CS4007 이 납니다(14부). Span 이 await 를 넘는 경우는 6부에서 봤습니다.

실행 검증

ref struct 를 옛 컴파일러에게서 지키는 법 — Obsolete

명세: ref struct 에는 IsRefLikeAttribute 를 붙이고, 이 규칙을 모르는 옛 컴파일러가 쓰지 못하도록 "an Obsolete attribute with a known string will be added to all ref-like structs" — 규칙을 아는 컴파일러는 그 특정한 Obsolete 를 무시합니다.

명세가 적은 문장 그대로의 Obsolete 가 지금도 붙습니다. 특성의 이름은 명세 초안의 IsRefLike 가 아니라 IsByRefLikeAttribute 이고, 그 옆에 CompilerFeatureRequiredAttribute("RefStructs") 가 하나 더 있습니다. .NET 10 의 Span<T> 는 IsReadOnlyAttribute 도 달고 있습니다 — readonly ref struct 입니다.

실행 검증

뒤 버전 — C# 13 이 푼 두 제약

C# 7.2 의 "인터페이스를 구현할 수 없다", "형식 인수가 될 수 없다" 는 C# 13 에서 풀렸습니다. 컴파일러는 이 둘을 각각 ref struct interfaces, allows ref struct constraint 라는 13.0 의 게이트로 확인합니다.

7.2 로 내려도 "인터페이스를 구현할 수 없다" 는 옛 오류가 아니라 "13.0 을 쓰라" 는 게이트 문장이 나옵니다. 지금의 컴파일러는 옛 규칙의 오류 문장 대신 그 규칙을 푼 버전을 알려 줍니다. 자세한 것은 14부에서 봅니다.

실행 검증

같이 온 런타임 — Span 가족 C# 7.2

언어 버전 기록은 C# 7.2 의 첫 줄을 "Span and ref-like types" 로 적습니다. 언어 기능은 ref struct 이고, 그것이 기대는 형식이 Span<T>·ReadOnlySpan<T> 입니다.

Memory<T> 는 ref 같은 형식이 아닙니다 — 힙에 둘 수 있어서 필드나 async 메서드에 Span 대신 쓰입니다. 아래 셋 (TypedReference·ArgIterator·RuntimeArgumentHandle)은 C# 7.2 전부터 있던, 같은 제약을 받던 형식들입니다. Roslyn 문서는 TypedReference 를 "a ref-like type such as" 라고 부릅니다.

실행 검증

Span 으로 자르기 — 복사가 아니라 창

Span 은 배열·문자열·스택 메모리의 한 구간을 가리키는 "창" 입니다. Slice 는 새 배열이나 문자열을 만들지 않고 창만 옮깁니다. .NET 10 의 int.Parse 는 ReadOnlySpan<char> 를 받는 오버로드를 가집니다.

이 파일은 -langversion:7.1 에서도 컴파일되고 같은 답을 냅니다. Span 을 쓰는 것은 게이트가 아닙니다 — 게이트가 걸리는 것은 ref struct 를 선언하거나, 다음 장의 stackalloc 처럼 언어가 Span 을 직접 만들어 내는 자리입니다.

실행 검증

unsafe 없는 stackalloc — Span 으로 받으면 C# 7.2

span-safety 명세: stackalloc 식의 결과는 "safe-to-escape" 가 현재 메서드의 최상위 범위입니다 — 메서드 밖으로 못 나가는 값이므로, 포인터 대신 Span 으로 받으면 안전한 코드에서 쓸 수 있습니다.

7.1 의 거절은 stackalloc 자리를 가리키고 기능 이름은 ref structs 입니다. Span 으로 받은 스택 메모리는 0 으로 채워져 있고, 범위를 넘으면 IndexOutOfRangeException 입니다 — 포인터였다면 그냥 옆 메모리를 썼을 자리입니다.

이전엔 — stackalloc 은 C# 1 부터 있었지만 int* 로만 받을 수 있어 unsafe 문맥이 필요했습니다 (2부).

스택 메모리는 메서드 밖으로 나갈 수 없다

명세의 규칙: "For a return statement return e1, the safe-to-escape of e1 must be safe-to-escape from the entire method." 대입도 같습니다 — 좁은 범위의 값을 넓은 곳에 넣을 수 없습니다.

ref 조건식 — 둘 중 한 변수의 참조 C# 7.2

왜 — 명세: ref 변수를 조건에 따라 묶는 것은 "not currently expressible in C#" 이었고, 흔한 우회로 Choice(bool, ref T, ref T) 메서드는 "all arguments must be evaluated at the call site" 라서 "will crash with NRE because 'arr[0]' will be executed unconditionally" 같은 일이 생겼습니다.

조건식 자체가 변수(LValue)라서 (big ? ref a[1] : ref b[1]) = 77 처럼 바로 대입할 수 있습니다. 보통 조건식처럼 한쪽만 계산하므로 none[0] 은 건드리지 않습니다. Choice 는 두 인수를 모두 먼저 계산해서 NullReferenceException 입니다.

ref·in 확장 메서드 — 받는 쪽을 참조로 C# 7.2

왜 — 명세가 든 이유는 둘: "Avoid copying when receiver is a large struct", "Allow mutating extension methods on structs". 오래된 요청이었지만 "what happens if receiver is not an LValue?" 가 걸림돌이었고, in 이 생기면서 풀렸습니다 — ref 는 쓰기 가능한 변수에만, in 은 임시 복사를 허용합니다.

C# 7.2 퀴즈 1 — in 은 복사를 없애나

Q. 필드 열여섯 개짜리 보통(readonly 아닌) 구조체를 in 으로 받아, 메서드 안에서 그 구조체의 인스턴스 메서드를 열 번 부릅니다. 값으로 받았을 때보다 복사가 줄어듭니까?

A. 아닐 수 있습니다. 인수를 넘길 때의 복사는 없어지지만, 읽기 전용 변수에서 부르는 인스턴스 메서드마다 방어 복사가 생깁니다 (in 과 방어 복사). 구조체를 readonly struct 로 만들면 그 복사가 사라집니다(방어 복사가 없는 readonly struct). 명세도 "the problem of defensive copying will get worse" 라고 미리 적었습니다.

C# 7.2 퀴즈 2 — 같은 Span, 다른 운명

Q. Span<int> s = new int[3]; 와 Span<int> s = stackalloc int[3]; 는 형식이 같습니다. 그런데 앞의 것은 return s; 가 되고 뒤의 것은 안 됩니다. 컴파일러는 무엇을 보고 가릅니까? 그리고 둘 다 클래스의 필드에는 둘 수 없는 까닭은?

A. 값이 어디서 왔는지(safe-to-escape)를 봅니다 — 힙 배열에서 온 Span 은 메서드 밖으로 나가도 되고, stackalloc 에서 온 것은 메서드 안에서만 삽니다(스택 메모리의 탈출). 필드 금지는 형식의 규칙입니다. Span<T> 는 ref struct 라서 어디서 왔든 힙 객체 안에 둘 수 없습니다(힙에 두려는 일곱 길).

계산 순서와 일찍 끝내기 — 그리고 == 와 Equals 는 다르다

명세: "The left-hand-side value is evaluated first, then the right-hand-side value, then the element-wise comparisons from left to right (…, and with early exit based on existing rules for conditional AND/OR operators)."

8부 퀴즈 1 — 어느 버전인가

Q. 다음 넷을 처음 받아 준 언어 버전을 고르십시오. (가) ref var r = ref (c ? ref a : ref b); (나) r = ref b; (다) if (t == (1, 2)) (라) var (x, y) = t;

A. (가) 7.2 — ref 조건식(7장). (나) 7.3 — ref 재할당(8장). (다) 7.3 — 튜플 ==(8장), 7.0 에서는 Equals 뿐이었습니다. (라) 7.0 — 분해(2장). 답을 외우지 않아도 됩니다 — 한 단계 아래 버전으로 컴파일하면 컴파일러가 "Please use language version …" 으로 알려 줍니다.

8부 퀴즈 2 — 문서와 컴파일러가 다를 때

Q. 버전 기록은 "Reassign ref local variables" 를 C# 7.2 목록에 적습니다. 이 덱이 그것을 C# 7.3 의 기능이라 하는 근거는 무엇입니까?

A. 두 가지입니다. 컴파일러의 RequiredVersion() 이 IDS_FeatureRefReassignment 를 CSharp7_3 에 두고, 실제로 -langversion:7.2 에서 "Feature 'ref reassignment' is not available in C# 7.2" 로 거절됩니다(8장). 언어 버전 기록 (csharplang)도 7.3 에 둡니다. 버전 기록의 7.2 목록에는 7.3 의 다섯 줄이 섞여 있습니다(7장).
