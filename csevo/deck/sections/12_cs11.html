같이 온 런타임 — C# 11 이 기대는 형식 C# 11.0

왜 — 버전 기록은 C# 11 의 중심을 제네릭 수학에 둡니다. "You can write numeric algorithms once for all number types." 그 알고리즘이 기대는 인터페이스, required 멤버와 ref 필드를 메타데이터에 적는 특성, 스팬 패턴이 부르는 메서드가 .NET 10 에서 어디 있는지 봅니다.

메서드 그룹 대리자의 캐시 — 컴파일러가 만드는 필드 C# 11.0

왜 — 표준의 메서드 그룹 변환에 한 줄이 생겼습니다. "The conversion is permitted (but not required) to use an existing delegate instance that already contains these references." whats-new 는 예전 표준이 이 재사용을 막았고 "The C# 11 compiler caches the delegate object" 라고 적습니다.

3부에서 본 ReferenceEquals 의 차이가 어디서 오는지 보입니다. C# 11 은 App 안에 <>O 라는 중첩 형식을 만들고, 메서드마다 정적 필드(<0>__Twice)를 둡니다. 첫 변환이 대리자를 만들어 넣고, 다음 변환부터는 그 필드를 읽습니다. C# 10.0 으로 컴파일한 같은 소스에는 중첩 형식이 없습니다. 게이트에 이름이 없는 것은 이것이 문법이 아니라 코드 생성의 선택이라서입니다.

실행 검증

어떤 변환이 캐시되나 — 정적인 것만

whats-new 의 문장은 "method group" 전체를 말하지만, 게이트의 이름은 CacheStaticMethodGroupConversion 입니다. 다섯 가지 변환을 두 번씩 하고 같은 객체인지 봅니다.

정적 메서드는 제네릭 인스턴스(Id<int>)든 정적 지역 함수든 C# 11 에서 캐시됩니다. 대상 객체가 있는 인스턴스 메서드와 확장 메서드는 그 객체를 담아야 하니 두 버전 모두 매번 새로 만듭니다. 람다는 두 버전 모두 True 입니다 — 표준은 익명 함수 변환에는 원래부터 같은 인스턴스를 돌려줄 수 있게 했습니다. C# 10 까지는 Twice 대신 x => Twice(x) 로 써야 캐시를 얻었다는 뜻입니다.

실행 검증

함정 — 대리자의 정체(identity)에 기댄 코드

== 와 -= 는 대리자를 값(메서드와 대상)으로 비교하므로 캐시와 상관이 없습니다. 객체의 정체로 비교하는 자료 구조는 다릅니다.

함정 — 언어 버전만 올렸는데 "변환할 때마다 새 객체" 를 가정한 코드가 달라집니다. 참조 비교 집합에 천 번 넣은 대리자가 천 개에서 한 개가 되고, 대리자마다 상태를 붙이던 ConditionalWeakTable 은 두 번째 등록을 "이미 있다" 로 봅니다. 표준이 재사용을 "permitted (but not required)" 로 둔 만큼, 어느 쪽에도 기대지 않는 것이 맞습니다.

호출 목록은 두 버전 모두 1 입니다 — += 두 번, -= 한 번은 값 비교라 결과가 같습니다.

문자열 — 이스케이프 없는 글, 바이트로 된 글

원시 문자열 리터럴 · $$""" · UTF-8 리터럴 u8 · 구멍 안의 줄바꿈 · ReadOnlySpan<char> 패턴 ·

원시 문자열 리터럴(raw string literal) C# 11.0

왜 — 제안서: C# 의 모든 문자열 꼴은 구분자가 고정이라 내용에 구분자가 나오면 이스케이프가 필요하고, 그래서 XML·HTML·JSON 을 담기 어렵습니다. "The crux of the problem is that all our strings have a fixed start/end delimiter." 해법은 시작과 끝 구분자를 늘일 수 있게 하는 것입니다.

따옴표 셋 이상으로 열고 같은 수로 닫습니다. 안에서는 \t 도 \\ 도 글자 그대로입니다 — JSON 의 "C:\\temp" 가 두 백슬래시 그대로 찍혔습니다. 여러 줄 꼴의 길이 41 에는 첫 줄과 끝 줄의 줄바꿈이 들어 있지 않습니다(뒤에서).

실행 검증

들여쓰기를 지우는 기준 — 닫는 따옴표의 자리

제안서: 여러 줄 꼴은 마지막 줄(닫는 따옴표 앞)의 공백을 "indentation whitespace" 로 삼아 모든 내용 줄의 앞에서 지웁니다. 코드를 들여 쓴 채로 두면서 값에는 들여쓰기가 남지 않게 하려는 것이고, 원하지 않으면 닫는 따옴표를 1열에 두면 됩니다.

닫는 따옴표를 두 칸 왼쪽에 두면 두 칸이 값에 남고, 1열에 두면 아무것도 지우지 않습니다 — 제안서의 "Example 3" 입니다. 지우는 일은 컴파일할 때 끝나므로 실행 비용이 없습니다.

실행 검증

첫 줄바꿈과 끝 줄바꿈은 값이 아니다

제안서: 여러 줄 꼴에서 여는 따옴표 뒤의 whitespace* new_line 과 닫는 따옴표 앞의 new_line whitespace* 는 값에 들지 않습니다. 끝에 줄바꿈을 두려면 빈 줄을 하나 더 씁니다. 따옴표로 시작하거나 끝나는 내용은 여러 줄 꼴이면 쓸 수 있습니다.

한 줄 꼴은 따옴표로 시작하거나 끝나는 값을 못 씁니다 — """"quoted"""" 는 따옴표 넷이 구분자가 되어 버립니다. 제안서는 그래서 ''' 꼴을 덧붙이는 안을 "Drawbacks" 에 남겨 두었습니다.

실행 검증

구분자는 내용의 어떤 따옴표 연속보다 길어야 한다

제안서의 설계 결정: "the delimiter must be longer than any sequence of quotes in the string itself". 기술적으로는 필요 없지만 커뮤니티가 헷갈린다고 해서 정한 규칙입니다.

여러 줄 꼴 안의 """"" 는 "내용" 이 아니라 닫는 따옴표로 읽힙니다. 그래서 "구분자는 제 줄에 있어야 한다"(CS9000)가 먼저 나오고, 남은 따옴표가 새 리터럴을 열어 "끝나지 않았다"(CS8997)가 이어집니다. 해법은 따옴표 여섯으로 여는 것입니다.

실행 검증

규칙을 하나씩 어기면 — 일곱 가지 틀린 꼴

제안서가 "illegal" 이라고 적은 꼴과, 거기서 한 걸음 더 간 꼴을 #if 기호 하나에 하나씩 모았습니다.

기호를 켜지 않으면 빈 Main 이라 깨끗이 컴파일됩니다. 다음 장의 표가 기호마다 컴파일한 결과입니다.

실행 검증

일곱 가지 틀린 꼴의 오류 번호

원시 문자열만의 오류가 여섯 번호(CS8997–CS9003 가운데 CS9001 을 뺀 것)로 나옵니다. OPEN 과 SIX 는 둘 다 "끝나지 않았다" 입니다 — 여는 줄에 내용이 있으면 컴파일러는 한 줄 꼴로 읽고, 줄이 끝날 때까지 닫는 따옴표가 없으니까요. 따옴표 여섯은 빈 문자열이 아닙니다. 빈 값의 가장 짧은 원시 꼴은 빈 내용 줄 하나를 둔 세 줄짜리입니다 — 내용 줄이 없으면 표의 EMPTY(CS9002)이고, 마지막 내용 줄 뒤의 줄바꿈은 값에 들지 않으므로 빈 줄 하나가 빈 값이 됩니다.

실행 검증

탭과 스페이스를 섞어도 된다 — 똑같기만 하면

제안서의 설계 결정: 들여쓰기에 공백 종류를 섞는 것을 막지 않습니다. "tab for indentation, space for alignment" 라는 흔한 방식으로 닫는 따옴표를 여는 따옴표에 맞출 수 있어야 하기 때문입니다.

형식은 ReadOnlySpan<byte> — 그리고 상수가 아니다

제안서: u8 리터럴은 개발자가 byte[] 리터럴을 쓴 것처럼 낮춰지고, 그래서 호출 지점에서 할당이 없으며 PE 파일의 .data 영역에 놓입니다. 이어 붙인 u8 은 바이트 하나로 합쳐집니다. 그리고 "A null terminator is placed beyond the last byte in memory (and outside the length of the ReadOnlySpan<byte>)".

제안서의 미결 질문 2: (string)null 과 맞추기를 허용할지 — 권고는 "should be reported as an error" 였습니다. 질문 3 의 제네릭 Span<T> 예는 "All of the preceding samples produce a compiler error."

함정 — default 스팬과 "" 의 스팬은 둘 다 is "" 에 맞고 둘 다 비었지만 == 로는 False 입니다. 스팬의 == 는 내용이 아니라 같은 메모리를 가리키는지 봅니다. 내용을 견주려면 패턴이나 SequenceEqual 을 씁니다.

제네릭 Span<T> 에는 안 된다 — 형식 검사 없음

같은 파일의 나머지 두 기호입니다. 제안서는 Span<char> 형식 패턴을 명시하면 허용하자고 권했지만 구현되지 않았습니다.

두 번째 거절은 "ABC" 가 아니라 형식 패턴 Span<char> 에서 납니다. ref struct 는 박싱이 안 되니 런타임에 "실제로는 Span<char> 인가" 를 물을 방법이 없습니다. 스팬 패턴은 입력의 정적 형식이 Span<char> 나 ReadOnlySpan<char> 일 때만 섭니다. NULL(CS9135)과 STRNULL(CS9013)의 거절은 앞 장의 캡처에 있습니다.

제안서의 미결 질문 4: { Length: 0 } 뒤의 "", ['A', ..] 뒤의 "ABC" 를 "unreachable" 오류로 볼지 — 권고는 "Same subsumption behavior as used when the expression value is string" 였습니다.

잘라 낸 조각을 바로 switch — 할당 없는 토큰 처리

제안서가 말한 쓰임입니다. 문자열을 Substring 으로 자르면 조각마다 새 문자열이 생기지만, 스팬으로 자르면 원래 메모리를 가리킬 뿐입니다. C# 10 까지는 그 조각을 switch 에 못 넣었습니다.

두 번째 계산은 할당한 바이트가 앞뒤로 같습니다 — 낱말 다섯을 잘라 비교하는 동안 힙에 아무것도 만들지 않았습니다. 바이트 수를 재지 않고 같은지만 찍습니다. 알 수 없는 낱말에서만 tok.ToString() 으로 문자열을 만듭니다.

2장 퀴즈 — 문자열

Q1. """""""(따옴표 일곱)로 시작하는 줄은 무엇입니까? 그리고 값이 빈 문자열인 원시 리터럴을 가장 짧게 쓰면?

A. 따옴표 여섯 이상도 빈 문자열이 아니라 "그만큼으로 여는" 구분자입니다. 일곱이면 따옴표 일곱으로 연 리터럴의 시작이고, 같은 줄에서 닫히지 않으면 CS8997 입니다(표의 SIX). 빈 값은 여는 줄, 빈 내용 줄 하나, 닫는 줄의 세 줄짜리 여러 줄 꼴입니다 — 물론 "" 가 낫습니다.

Q2. static readonly byte[] Crlf = "\r\n"u8; 는 컴파일될까요?

A. 안 됩니다. u8 의 형식은 ReadOnlySpan<byte> 라 byte[] 로 암시 변환되지 않습니다(CS0029, 표의 ARR). "\r\n"u8.ToArray() 로 복사하거나, 속성 static ReadOnlySpan<byte> Crlf => "\r\n"u8; 로 두면 데이터 영역을 그대로 가리킵니다.

제네릭 특성과 nameof — 특성이 형식과 이름을 받는다

class A<T> : Attribute · 형식 인수의 제약 · 리플렉션 · 못 오는 형식 · nameof 범위 확장 · nullable 특성 ·

제네릭 특성(generic attributes) C# 11.0

왜 — whats-new: System.Type 매개변수가 필요한 특성을 "a more convenient syntax" 로 쓰게 합니다. 예전에는 생성자가 Type 을 받고 쓰는 쪽이 typeof 를 넘겼습니다.

거절은 두 자리에서 납니다 — 제네릭 클래스가 Attribute 를 상속하는 선언(12행)과 그것을 붙이는 자리(22행). 리플렉션으로 꺼낸 객체의 형식은 닫힌 생성 형식 GenericAttribute`1[System.String] 입니다. 특성 인수가 없으면 괄호는 생략할 수 있습니다.

실행 검증

제약이 특성에 온다 — 제안서의 동기

제안서: typeof 로 받으면 분석기 말고는 "there's no way for an attribute author to constrain what types are allowed". 특성이 제네릭이면 기존의 형식 매개변수 제약으로 요구를 적을 수 있습니다.

옛 특성은 typeof(object) 를 아무 말 없이 받고, 실행할 때야 Parse 가 없다는 것을 압니다. 새 특성은 T.Parse 를 바로 부릅니다 — 정적 추상 멤버(4장) 덕분입니다. #if BAD 의 [ParseAs<object>] 는 컴파일러가 CS0311(제약 위반)로 거절합니다. 그 오류 줄이 200칸을 넘어 캡처를 싣지 않고, 실험 스크립트가 종료 코드와 번호를 확인합니다.

실행 검증

C# 2 부터 막혀 있던 것 — 표준 초안의 예

제안서: "When generics were introduced in C# 2.0, attribute classes were not allowed to participate." .NET Core 런타임은 이미 제네릭 특성을 지원하고 "all that's missing is support for generic attributes in the compiler" 였습니다. 이 덱이 받아 둔 표준 초안에는 아직 금지 문장과 예가 있습니다.

표준 초안의 예는 기대 오류를 CS8400 으로 적어 두었습니다 — C# 8.0 으로 컴파일할 때 이 SDK 가 내는 바로 그 번호입니다. 간접 상속도 걸립니다. C# 10 에서는 미리 보기 기능이었습니다(11부).

실행 검증

리플렉션으로 읽기 — 닫힌 형식과 열린 형식

특성 인스턴스는 언제나 닫힌 생성 형식입니다(TagAttribute<int>). 찾을 때는 그 닫힌 형식으로 찾고, 형식 인수는 인스턴스의 형식에서 꺼냅니다.

Tag<long> 은 붙이지 않았으니 False 입니다. 마지막 줄 — 열린 형식 typeof(TagAttribute<>) 로 찾으면 .NET 10 은 형식 인수와 상관없이 둘 다 돌려줍니다. 이 덱이 모은 문서에는 이 동작을 적은 곳이 없어 ".NET 10 에서의 동작" 으로만 둡니다.

실행 검증

형식 인수로 못 오는 것 — 메타데이터에 적을 수 없는 형식

whats-new: 형식 인수는 typeof 와 같은 제약을 받고, 메타데이터 주석이 필요한 형식 — dynamic, string?, (int X, int Y) — 은 안 됩니다. 대신 object · string · ValueTuple<int, int> 을 씁니다. 둘러싼 형식의 형식 매개변수도 안 됩니다.

5부는 dynamic 만 보였습니다. 제안서는 nint 도 "attribute-dependent" 라 안 된다고 적었지만, 이 SDK 는 A<nint> 를 받고 System.IntPtr 로 찍습니다 — C# 11 에서 nint 가 IntPtr 의 별칭이 되었기 때문으로 보입니다(5장). int? 는 실제 형식 Nullable<int> 라 됩니다. NULLABLE 의 오류 문장은 ? 를 떼고 "Type 'string'" 이라고 말합니다.

실행 검증

AllowMultiple = false 는 원래 정의로 센다

제안서의 미결 질문: [Attr<string>] 와 [Attr<object>] 를 함께 붙이면 "여러 개" 인가 — 결론은 "the more restrictive route", 특성 클래스의 원래 정의로 셉니다.

오류 문장이 원래 정의를 'One<>' 로 부릅니다. 형식 인수마다 하나씩 붙이고 싶으면 앞에서 본 TagAttribute처럼 AllowMultiple = true 로 둡니다.

실행 검증

생성자 매개변수가 T 인 특성

형식 인수는 특성 인수의 형식도 정합니다. 표준이 정한 특성 매개변수 형식(정수 · 실수 · string · Type · 열거형 …)이 되는지는 T 를 바꿔 넣은 뒤에 따집니다.

메타데이터에 적힌 생성자 인수의 형식은 T 가 아니라 바꿔 넣은 Double 입니다. decimal 은 특성 매개변수 형식이 아니라서, 선언은 멀쩡한데 Range<decimal> 을 붙이는 자리에서 매개변수마다 CS0181 이 납니다.

실행 검증

nameof 범위 확장(extended nameof scope) C# 11.0

왜 — 제안서: NotNullWhen 이나 CallerExpression 같은 특성은 매개변수를 가리켜야 하는데 "those parameters are currently not in scope" 였습니다. 제안서는 메서드의 형식 매개변수, 매개변수에 붙인 특성, 익명 함수와 대리자 선언의 매개변수까지 범위를 넓힙니다.

7부는 메서드 특성 안의 매개변수 이름 하나를 보였습니다. 제안서가 꼽은 다섯 자리가 모두 됩니다. 그리고 다섯 모두 C# 10.0 에서도 됩니다 — 게이트 목록(1장)에 이 기능이 없습니다.

실행 검증

게이트가 없는 기능 — C# 6 으로 내려도

람다 특성(C# 10)이나 정적 지역 함수(C# 8) 없이, 형식 매개변수 이름 하나만 쓰는 C# 6 꼴의 프로그램입니다.

이 SDK 는 C# 6 에서도 nameof(T) 를 메서드의 형식 매개변수로 읽습니다. C# 5 의 거절도 범위가 아니라 nameof 연산자(7부)에 대한 것입니다. 그래서 "C# 11 에서 됐다" 는 것은 이 컴파일러로 보일 수 없고, whats-new 와 제안서의 문장으로만 둡니다.

실행 검증

nameof 안에서만 보인다 — 같은 이름의 상수와 겨루면

제안서의 문장은 매개변수를 "Within a nameof expression in attributes" 에서만 이름으로 부를 수 있게 합니다. 특성의 다른 인수에서는 여전히 바깥 이름이 이깁니다.

[Note(Data)] 는 상수, nameof(Data.Rank) 는 매개변수입니다 — string 에는 Rank 가 없으니 상수로 읽었다면 오류였습니다. 깨지는 변경 문서는 C# 11 부터 이렇게 읽는다고 적지만, C# 10.0 의 출력도 같습니다. 7부에서 형식 매개변수로 본 것과 같은 어긋남입니다.

실행 검증

쓰임 — nullable 분석 특성과 이름이 어긋날 때

whats-new: 이 기능은 "most often useful to add attributes for nullable analysis" 입니다. 특성이 매개변수를 문자열로 가리키면, 이름을 바꿀 때 특성만 남습니다.

함정 — STALE 의 "text" 는 없는 매개변수 이름인데, 특성 쪽에는 아무 진단이 없습니다. 대신 약속이 조용히 사라져 null 이 아닌 "ada" 를 넘긴 호출에서 엉뚱하게 CS8600 이 납니다. nameof(s) 였다면 이름을 바꿀 때 같이 바뀌거나 컴파일 오류가 났을 것입니다.
실행 검증

쓰임 — CallerArgumentExpression(nameof(…))

제안서가 동기에서 같이 꼽은 특성입니다. C# 10 의 CallerArgumentExpression(11부)은 매개변수 이름을 문자열로 받는데, 그 매개변수는 같은 목록의 옆 매개변수입니다.

호출한 쪽의 식 원문이 그대로 들어옵니다. nameof(condition) 은 매개변수에 붙인 특성 안의 nameof 라 제안서의 셋째 예와 같은 꼴입니다.

3장 퀴즈 — 제네릭 특성과 nameof

Q1. class Repo<T> { [Cache<T>] public T Get() => default; } 는 C# 11 에서 컴파일될까요?

A. 안 됩니다. 특성의 형식 인수는 완전히 닫혀야 하고 둘러싼 형식의 형식 매개변수를 쓸 수 없습니다 — CS8968(표의 OPEN). 특성 인수는 메타데이터에 상수로 적히는데 T 는 인스턴스마다 다르기 때문입니다.

Q2. [return: NotNullIfNotNull("value")] string? F(string? input) 에서 무엇이 잘못되었고, 컴파일러는 알려 줍니까?

A. 매개변수 이름은 input 인데 특성은 "value" 를 가리킵니다. 컴파일러는 특성 자리에서 아무 말이 없고, 호출하는 쪽에서 null 이 아닌 인수에도 경고가 납니다(STALE). nameof(input) 으로 쓰면 이 실수가 생기지 않습니다.
