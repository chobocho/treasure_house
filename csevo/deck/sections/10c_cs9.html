문서 근거

대상 형식 new() (target-typed new) C# 9.0

왜 — 제안서: "Allow field initialization without duplicating the type", 그리고 "Instantiate an object without spelling out the type". 발표 글은 대상 형식(target typing)을 "when an expression gets its type from the context of where it's being used" 라고 풀고, null 과 람다가 원래 그렇다고 적습니다.

거절은 new() 가 쓰인 자리마다 하나, 일곱 개입니다(29행에 둘). 17행의 필드처럼 형식 이름이 길수록 이득이 큽니다 — 제안서의 첫 예도 Dictionary<string, List<int>> 필드입니다.

실행 검증

new() 가 안 되는 곳 — 대상이 없거나 만들 수 없을 때

명세: new() 는 그 자체로 형식이 없고, 모든 형식으로 가는 "object creation conversion" 만 있습니다. 단항·이항 연산자의 피연산자나, 그런 변환이 일어나지 않는 자리에 쓰면 오류입니다. 제안서가 꼽은 자리를 한 파일에 모았습니다.

오류는 세 갈래입니다. 대상이 없다(var, 멤버 접근 — CS8754), 연산자의 피연산자다(CS8310), 대상 형식이 맞지 않는다(배열·dynamic — CS8752). 열거형·인터페이스·대리자는 따로 금지되지 않고, new Color(1) 을 적었을 때와 같은 옛 오류 (CS1729·CS0144)로 거절됩니다 — 명세의 "같은 뜻의 객체 생성 식" 그대로입니다.

실행 검증

뜻밖에 되는 new() — int? 는 null 이 아니다

명세: 대상 형식 T 가 Nullable 이면 new() 는 그 바탕 형식 T0 를 만듭니다. 제안서는 throw new() 가 되고(대상은 System.Exception) 튜플 대상의 new() 는 "same as (0, 0)" 이라고 적습니다.

함정 — int? n = new(); 는 null 이 아니라 0 을 가진 값입니다(HasValue 가 True). new() 는 "기본값" 이 아니라 "바탕 형식의 생성자 호출" 이기 때문입니다. 비우고 싶으면 default 나 null 을 씁니다.
실행 검증

오버로드가 하나 늘면 — new() 의 깨지는 변경

제안서의 단점 절: 대상 형식 new 가 새 종류의 깨지는 변경을 만든다는 걱정이 있었지만, null 과 default 에 이미 있는 일이고 "that has not been a significant problem" 이었다고 적습니다. 어떤 변경인지 봅니다.

M(new()) 는 대상을 메서드의 매개변수에서 얻습니다. 매개변수 없는 생성자를 가진 형식을 받는 오버로드가 하나 더 생기면, 고치지 않은 호출 줄이 CS0121 로 깨집니다. 라이브러리가 오버로드를 더하면 그 라이브러리를 쓰는 쪽 코드가 깨질 수 있다는 뜻입니다.

실행 검증

식 트리 안의 new() — 제안서의 질문 하나

제안서의 질문 목록: "Should we forbid usages in expression trees? (no)". 식 트리가 대상 형식 new() 를 어떻게 적는지 봅니다.

트리에는 new Point(1, 2) 가 그대로 들어 있습니다 — 노드 종류 New, 형식 Point. 대상 형식은 컴파일 때 정해져 트리에 남지 않습니다. C# 3 의 식 트리가 C# 14 까지도 받지 않는 문법(?., 튜플, 패턴 …)과 달리 이것은 그냥 생성자 호출입니다 (4부).

실행 검증

static 익명 함수 (static anonymous function) C# 9.0

왜 — 제안서: "Avoid unintentionally capturing state from the enclosing context, which can result in unexpected retention of captured objects or unexpected additional allocations." 상수와 static 멤버는 쓸 수 있고, nameof() 안에서는 지역 변수도 됩니다.

거절 번호가 둘로 나뉩니다 — 지역 변수는 CS8820, 인스턴스 멤버(inst 는 this.inst)는 CS8821. C# 8 의 static 지역 함수(9부)가 익명 함수로 넓어진 것이고, 기본 꼴은 9부의 예고에서 봤습니다.

실행 검증

static 을 붙여도 생성 코드는 그대로

제안서: static 익명 함수가 메타데이터에서 static 메서드가 된다는 보장은 없고("left up to the compiler implementation"), 올바른 프로그램에서 static 을 지워도 "does not change the meaning of the program" 입니다.

static 람다와 포착 없는 보통 람다가 똑같습니다 — 둘 다 숨은 클래스 <>c 의 인스턴스 메서드이고(static=False), 두 번 만들어도 같은 대리자 객체(캐시)입니다. 포착하는 람다만 매번 새 객체입니다. static 은 할당을 줄이는 최적화 스위치가 아니라 "포착하면 오류로 알려 달라" 는 표시입니다. 포착 없는 람다의 캐시는 4부부터 같았습니다.

실행 검증

static 람다 안의 람다 — 경계는 한 겹

제안서: static 이 아닌 지역 함수나 익명 함수는 둘러싼 static 익명 함수의 상태는 포착할 수 있지만 "cannot capture state outside the enclosing static anonymous function".

안쪽 람다는 static 이 아니어도 k 를 포착합니다 — k 는 static 람다 안의 것이기 때문입니다. 한 겹 더 바깥의 outer 를 쓰면 안쪽 람다가 static 이 아니어도 같은 CS8820 입니다. 오류는 outer 를 쓴 자리에 납니다.

실행 검증

대상 형식 조건식 (target-typed ?:) C# 9.0

왜 — 두 갈래 사이에 공통 형식이 없어도, 두 갈래가 모두 대상 형식 T 로 변환되면 조건식을 T 로 받는 "conditional expression conversion" 이 생겼습니다. whats-new: "some conditional expressions that previously required casts or wouldn't compile now just work".

C# 8.0 으로 내리면 두 줄 모두 CS8957("Conditional expression is not valid in language version 8.0 because a common type was not found between 'int' and '<null>'…")로 거절됩니다. 그 한 줄이 200칸을 넘어 이 덱의 캡처 폭에 들지 않으므로 싣지 않았습니다 — 실험 묶음 (exps/p10c.py)이 매번 거절과 오류 번호만 확인합니다. C# 1 시절의 처방((object) 캐스트)과 대상이 없는 경우는 2부에 있습니다.

실행 검증

조건식과 오버로드 — 제안서가 걱정한 모호함

제안서의 설계 노트: 새 변환 때문에 M(b ? 1 : 2) 가 M(short) 로 옮겨 가지 않게 "better conversion" 규칙을 고쳤고, 그 대가로 N(b ? 1 : 2, 1) 이 "ambiguous with this feature" 가 된다고 적습니다.

처음 두 줄은 노트대로입니다 — ?: 는 M(long), switch 식은 M(short). 그러나 노트가 모호해진다고 한 N(b ? 1 : 2, 1) 은 이 컴파일러에서 모호하지 않고 8.0 과 9.0 이 똑같이 N(long) 입니다. b ? 1 : 2 에는 공통 형식 int 가 있어 새 변환이 끼어들 일이 없기 때문입니다. 새 변환이 실제로 고르는 것은 b ? 1 : null 처럼 공통 형식이 없을 때이고, 그때는 더 좁은 short? 쪽이 이깁니다.

실행 검증

공변 반환 형식 (covariant returns) C# 9.0

왜 — 제안서: "different method names have to be invented to work around the language constraint that overrides must return the same type as the overridden method." Roslyn 의 Compilation.WithOptions 를 예로 듭니다. 읽기 전용 속성의 재정의도 더 좁은 형식을 적을 수 있습니다.

호출하는 쪽이 Tiger 로 부르면 Meat 와 Tiger 를 캐스트 없이 받습니다. Animal 로 불러도 같은 재정의가 돕니다. 메서드 한 쌍의 기본 꼴은 5부(C# 4 의 변성과는 다른 기능)에서 봤고, 레코드의 복제 메서드가 이 기능을 쓰는 것은 2장에서 봤습니다.

실행 검증

공변 반환은 새 슬롯 — 메타데이터에서 보면

CLR 의 메서드 재정의는 원래 반환 형식까지 같아야 합니다. 그래서 C# 9 의 컴파일러는 좁은 형식의 재정의를 새 가상 슬롯으로 내보내고 특성 하나로 "기반의 슬롯도 이것이 맡는다" 고 표시합니다. 그것을 따르는 것이 런타임 기능 CovariantReturnsOfClasses 입니다(1장).

함정 — 리플렉션에는 Clone 이 둘입니다. Tiger.Clone 의 GetBaseDefinition() 은 자기 자신이라 "Animal.Clone 을 재정의했다" 는 사실이 보통의 재정의 관계로 드러나지 않습니다. 이어 주는 것은 PreserveBaseOverridesAttribute 뿐입니다. 이름으로 찾는 GetMethod("Clone") 은 모호하다고 던지지 않고 Tiger 쪽을 돌려줍니다.
실행 검증

공변 반환이 안 되는 세 곳

제안서의 규칙: 재정의의 반환 형식은 기반 것으로 암시적 참조 변환이 돼야 하고(값 반환일 때만), 속성은 기반이 읽기 전용일 때만 좁힐 수 있습니다. 인터페이스 멤버의 공변 반환은 "to be considered later" 로 남았습니다.

object 에서 int 는 박싱이라 참조 변환이 아니어서 옛 오류 CS0508 그대로입니다. get/set 속성은 CS1715 에 더해, 좁힌 속성의 set 이 기반의 set 을 구현하지 못해 CS0534 까지 납니다. 인터페이스 구현은 CS0738 — 반환 형식이 정확히 같아야 합니다.

실행 검증

제안서가 적은 깨지는 변경 — 일어나지 않았다

제안서의 뒷부분은 암시적 인터페이스 구현에도 공변 반환을 허용하는 안을 적고, 그러면 아래 프로그램이 "C1.M" 대신 "C2.M" 을 찍게 된다며 "Due to this breaking change, we might consider not supporting covariant return types on implicit implementations" 라고 덧붙입니다.

둘 다 "C1.M" 입니다. 설계 회의 목록의 마지막 줄 — "a decision to support overriding of class methods only in C# 9.0" — 대로, C# 9 의 공변 반환은 클래스의 override 에만 들어왔습니다. 제안서의 문장을 기능의 동작으로 읽으면 안 되는 예입니다.

실행 검증

확장 GetEnumerator (extension GetEnumerator) C# 9.0

왜 — 제안서: "This will bring foreach inline with how other features in C# are implemented, including async and pattern-based deconstruction." 단점 절은 이것이 "things that weren't designed to be foreached" — 예컨대 Range — 도 돌게 한다고 적습니다.

whats-new 는 "you can add foreach support to any type" 이라고 하면서 "You should limit its use to when enumerating an object makes sense in your design" 이라고 못 박습니다. 확장 GetAwaiter(6부)와 확장 Deconstruct(8부)는 처음부터 됐고, foreach 만 C# 9 에서야 같은 줄에 섰습니다.

실행 검증

확장은 마지막 후보 — 그리고 정수도 돈다

명세가 고친 foreach 의 순서: 인스턴스 GetEnumerator → IEnumerable<T>·IEnumerable 인터페이스 → 그래도 없을 때 확장 GetEnumerator. 원래라면 오류였을 때만 확장을 봅니다("when it would otherwise be an error").

함정 — Bag 의 확장 메서드는 경고 하나 없이 영영 불리지 않습니다. 확장으로 순회 방식을 "바꿀" 수는 없고, 순회할 수 없던 형식에 "붙일" 수만 있습니다. 반대로 foreach (int x in 3) 처럼 순회의 뜻이 모호한 코드도 컴파일됩니다 — 문서가 쓸모 있는 곳에만 쓰라고 한 까닭입니다.
실행 검증

확장 GetAsyncEnumerator — await foreach 도 같이 C# 9.0

왜 — 제안서: await foreach 의 규칙에서 "Extension methods do not contribute." 한 줄을 지우는 것이 바뀐 전부입니다. 게이트는 따로 있어서 기능 이름이 extension GetAsyncEnumerator 입니다.

ChannelReader<T> 는 ReadAllAsync() 로 IAsyncEnumerable 을 내주지만 스스로는 순회할 수 없습니다. 확장 한 줄이 그 사이를 잇습니다. Task<int[]> 에 확장을 붙인 첫 예는 6부에 있습니다.

실행 검증

람다의 버리기 매개변수 (lambda discard parameters) C# 9.0

왜 — 제안서: "Unused parameters do not need to be named." _ 가 둘 이상일 때만 버리기이고, 하나뿐이면 "for backwards compatibility reasons" 보통 매개변수입니다. 버리기 매개변수는 "do not introduce any names to any scopes" — 바깥의 _ 를 가리지도 않습니다.

함정 — 둘째 줄의 5 를 보십시오. (_, _) => _ 의 몸체에 있는 _ 는 매개변수가 아니라 바깥의 지역 변수 _(값 5)입니다. 버리기는 이름을 만들지 않으니 이름 찾기가 바깥으로 나갑니다. _ => _ * 10 의 _ 는 하나뿐이라 매개변수입니다. _ 가 이름이기도 하다는 규칙은 8부에서 봤습니다.
실행 검증

지역 함수의 특성 (local function attributes) C# 9.0

왜 — 제안서: 메서드·매개변수·형식 매개변수에 붙어 뜻이 있는 특성은 지역 함수에 붙여도 같은 뜻입니다. [Conditional] 도 되지만 "A conditional local function must also be static". whats-new 는 nullable 분석 특성을 예로 듭니다.

IsSet 의 [NotNullWhen(true)] 덕에 12행의 s.Length 에 CS8602 가 없습니다. Log 호출은 DEBUG 가 없으면 인자째 사라집니다. 특성을 리플렉션으로 읽는 예는 8부에 있습니다.

실행 검증

extern 지역 함수 C# 9.0

왜 — 같은 제안서의 둘째 절: 지역 함수에 extern 이 허용되고, 몸체 자리는 세미콜론이며, "An external local function must also be static". 특성과 짝을 이뤄야 쓸모가 있습니다 — [DllImport] 가 특성이기 때문입니다.

거절이 둘 — 특성(local function attributes)과 extern(extern local functions)이 따로 게이트를 가집니다. 문서 세 곳 어디에도 extern 지역 함수의 이름은 없고(1장), 기능 명세의 한 절과 컴파일러의 게이트에만 있습니다.

6장 퀴즈 — 다듬기

Q. 다음 세 줄은 각각 무엇을 찍습니까? (가) int? n = new(); Console.WriteLine(n.HasValue); (나) int _ = 5; Func<int, int, int> f = (_, _) => _; Console.WriteLine(f(1, 2)); (다) 포착 없는 static x => x + 1 대리자의 Method.IsStatic

A. (가) True — new() 는 바탕 형식 int 의 생성자라 0 을 가진 값입니다(뜻밖에 되는 new()). (나) 5 — 버리기 매개변수는 이름을 만들지 않아 몸체의 _ 는 바깥 지역 변수입니다(_). (다) False — 이 컴파일러는 static 람다도 숨은 클래스의 인스턴스 메서드로 내보냅니다. static 은 포착을 막을 뿐입니다 (static 람다의 캐시).

왜 — whats-new: 코드 생성기는 Roslyn 분석기와 비슷한 구성 요소로, "analyze code and write new source code files as part of the compilation process". 그리고 "Source generators can only add code; they aren't allowed to modify any existing code in the compilation." 이 장의 두 언어 기능은 그 제약 때문에 들어왔습니다. 언어 버전 기록은 C# 9.0 목록 끝에 "Source Generators" 를 한 줄로 적고 발표 글로 이어 둡니다.

모듈 초기화자 (module initializers) C# 9.0

왜 — 제안서: .NET 플랫폼에는 어셈블리(정확히는 모듈)의 초기화 코드를 쓰는 기능이 있었지만 C# 에 드러나 있지 않았습니다. 동기는 셋 — 라이브러리가 "eager, one-time initialization" 을 하게, 정적 생성자의 실행 여부 검사 비용을 피하게, 그리고 "Enable source generators to run some global initialization logic without the user needing to explicitly call anything".

Main 이 시작할 때 목록은 이미 차 있습니다. 거절은 특성이 붙은 14행 한 곳 — 게이트가 메서드의 특성에서 확인됩니다("semantic check on method attribute").

누가 먼저 도는가 — 모듈 초기화자와 정적 생성자

제안서는 초기화자가 여럿이면 컴파일러가 모두 부르되 차례는 "reserved, but deterministic" 이라고만 적습니다. whats-new 는 런타임이 "before any other field access or method invocation within the entire module" 에 부른다고 적습니다.

이 컴파일러에서는 소스에 선언된 차례(Zeta → Alpha)입니다 — 다만 명세가 약속한 차례가 아니므로 기대면 안 됩니다. Config 의 정적 생성자는 InitA 가 필드를 읽는 순간에 돌고, App 의 정적 생성자는 초기화자가 다 끝난 뒤 Main 바로 앞에 돕니다. 초기화자 안에서 건드린 형식의 정적 생성자는 초기화자 도중에 돈다는 뜻입니다.

컴파일러가 만드는 것 — <Module> 의 정적 생성자

제안서: 특성이 붙은 메서드가 있으면 "the compiler will emit a module initializer which calls each of the attributed methods". 그 모듈 초기화자가 어디에 들어가는지, 실행 중인 자기 어셈블리 파일을 System.Reflection.Metadata 로 열어 봅니다.

자리는 특별한 형식 <Module> 의 정적 생성자 .cctor 입니다. IL 은 11바이트 — 28(call)과 4바이트 토큰이 두 번, 끝의 2A(ret)입니다. 리플렉션의 GetTypes() 에는 <Module> 이 나오지 않아 메타데이터를 직접 읽었습니다. 이 예제의 IL 해석은 call 만 있다고 가정한 것이라 다른 메서드에 쓰면 안 됩니다.

모듈 초기화자가 될 수 없는 메서드 — CS8813–CS8816

제안서의 조건: static, 매개변수 없음, void 반환, 제네릭이 아니고 제네릭 형식 안에 있지 않음, 모듈 안에서 접근 가능(실효 접근성 internal 이나 public) — "This also means the method cannot be a local function".

오류 번호 넷이 조건 넷에 대응합니다 — 꼴(CS8815), 제네릭(CS8816), 접근성(CS8814), 보통 멤버 메서드가 아님 (CS8813). 지역 함수 쪽을 따로 컴파일한 것은 형식 선언의 오류가 있으면 메서드 몸체 안의 오류가 보고되지 않기 때문입니다. 지역 함수에 특성을 붙이는 것 자체는 6장의 기능으로 됩니다.

partial 메서드의 확장 (extended partial methods) C# 9.0

왜 — 제안서: C# 3 의 partial 메서드는 구현이 없으면 호출째 지워야 해서 void 반환, out 없음, 접근 한정자 없음이라는 제약이 있었습니다. C# 9 는 그 제약을 풀고, 대신 그런 선언은 "a definition must exist" 를 요구합니다. 그러면 사람이 선언하고 생성기가 구현하는 반대 방향이 됩니다.

거절은 선언 셋과 구현 셋에 하나씩, 여섯입니다. GetName 은 virtual 이면서 인터페이스 INamed 를 구현합니다 — 제안서의 IStudent 예와 같은 꼴입니다. C# 3 의 제약이 왜 있었는지와 "인자째 지워진다" 는 4부에 있습니다.

옛 규칙과 새 규칙 — 접근 한정자가 가른다

whats-new: 깨지는 변경을 피하려고 "the compiler considers any partial method without an access modifier to follow the old rules. If the partial method includes the private access modifier, the new rules govern". 제안서의 M1/M2/M3 예와 두 조각이 어긋나는 경우를 넣었습니다.

M1 은 구현이 없어도 됩니다(옛 규칙, 호출째 사라짐). 똑같이 private 인 M3 은 private 을 적었다는 것만으로 CS8795 입니다. 접근 한정자가 다르면 CS8799. 매개변수 이름(x 와 y)은 달라도 됩니다 — 제안서가 "the only aspects which can differ are parameter names and attribute lists" 라고 적은 대로입니다.

생성기가 채울 자리 — 생성기 없이 컴파일하면

제안서의 동기 절은 정규식을 예로 듭니다 — [RegexGenerated("(dog|cat|fish)")] partial bool IsPetMatch(string input); 처럼 선언만 하면 생성기가 구현을 쓰는 꼴입니다. .NET 10 의 라이브러리에는 이름이 비슷한 GeneratedRegexAttribute 가 있습니다. 같은 패턴으로 선언하고 생성기 없이 컴파일합니다.

특성 이름은 풀렸고(형식을 찾지 못했다는 오류가 없습니다), 거절은 "구현이 있어야 한다" 는 CS8795 하나입니다. 이 선언은 구현 조각을 누군가 — 여기서는 생성기 — 가 더해 줄 때만 컴파일됩니다. 이 덱은 생성기를 싣지 않으므로(앞에서) 생성기가 쓴 조각은 보이지 않습니다. partial 은 그 뒤 속성(C# 13)과 생성자·이벤트(C# 14)로 넓어집니다(3부).

제약 없는 T? (unconstrained T?) C# 9.0

왜 — 제안서: "In C#9, ? annotations can be applied to any type parameter, regardless of constraints." T 가 값 형식으로 대체되면 "T? represents an instance of T" — Nullable<T> 가 아닙니다. 반환값의 T? 는 [MaybeNull]T 와 같습니다.

Any<int> 의 반환 형식은 그냥 Int32 이고 nullable 정보도 NotNull 입니다 — 제약 없는 T? 는 형식이 아니라 주석이라 런타임 형식을 바꾸지 않습니다. where T : struct 의 T? 만 Nullable`1 입니다. C# 8.0 으로 내리면 CS8627 인데, 그 한 줄이 200칸을 넘어 싣지 않았습니다(실험 묶음이 확인만 합니다). 이 기능을 처음 소개한 장은 9부입니다.

[MemberNotNull] 과 [MemberNotNullWhen] C# 9.0

왜 — 메서드나 속성이 "이것이 끝나면(또는 true 를 돌려주면) 이 멤버는 null 이 아니다" 라고 알리는 특성입니다. 라이브러리의 특성일 뿐인데 컴파일러가 C# 9 로 확인하는 게이트를 따로 둡니다. 제안서는 메서드를 나갈 때 멤버가 아직 null 일 수 있으면 경고하는 것을 "the behavior we have shipped for [MemberNotNull]" 이라 부릅니다.

함정 — 약속을 어기면 컴파일러는 메서드를 나가는 자리(20행의 닫는 중괄호)에 CS8774 를 냅니다. 경고일 뿐이라 프로그램은 돌고, 31행에서 그 약속을 믿은 a.Text.Length 가 NullReferenceException 으로 죽습니다. 생성자에서 쓰는 기본 꼴은 9부에 있습니다.

where T : default — 재정의의 T? C# 9.0

왜 — 제안서: 재정의·명시적 구현 메서드의 T? 는 호환성 때문에 Nullable<T> 로 읽힙니다. 제약 없는 T? 를 뜻하려면 표시가 필요해 "C#9 allows a new where T : default constraint" 가 생겼습니다. 반환의 T? 는 [MaybeNull]T, 인수의 T? 는 [AllowNull]T 와 같아서 C# 8 식 특성으로 선언한 기반 메서드를 재정의할 수 있습니다.

특성([MaybeNull])과 T? 가 서로를 재정의해도 경고가 없습니다 — 둘이 같은 뜻이라는 제안서의 말 그대로입니다. 재정의가 아닌 곳의 default 제약은 CS8823. C# 8.0 으로 내리면 T? 의 CS8627 둘과 'default type parameter constraints' 거절 둘이 나오는데, 앞의 줄이 200칸을 넘어 싣지 않았습니다. 제안서의 A2/B2 꼴은 9부에 있습니다.

생성자의 nullable 분석 — 언어 버전에 묶이지 않은 변화 C# 9.0

왜 — 제안서: C# 8 의 생성자 분석은 확정 할당에 기대어, 생성자 안에서 아직 쓰지 않은 속성을 읽어도 경고가 없고(Prop.ToString()), 도우미 메서드로 채운 뒤 throw 로 확인해도 "unexpected warning" 을 냈습니다. 새 방식은 멤버를 maybe-null 로 시작해 생성자를 나갈 때 확인합니다.

두 캡처가 같습니다 — C 에는 CS8618 이 없고, D 의 24행에는 CS8602 가 납니다. 제안서가 고치려던 두 문제가 8.0 으로 컴파일해도 새 방식대로입니다. 이 분석은 언어 버전이 아니라 컴파일러 버전을 따릅니다(꼴 (나)가 아닙니다 — 0부). 옛 동작은 지금의 컴파일러로 보일 수 없습니다.

인터페이스 static 멤버의 변성 C# 9.0

왜 — 제안서: out T 인터페이스의 static 필드는 되는데 같은 꼴의 static 속성·메서드·이벤트는 CS1961 이었습니다. static 이고 가상이 아니니 "there aren't any safety issues here". 그래서 변성 안전성 규칙은 "do not apply to occurrences of types within declarations of static members".

8.0 의 거절은 기능 이름을 단 CS8400 이 아니라 전용 문장 CS8904 이고, 제안서가 적은 CS1961 도 아닙니다. 공변 T 를 받는 Echo(T t) 까지 C# 9 에서 됩니다 — 인스턴스 멤버였다면 변성이 깨지는 자리입니다. 인터페이스의 static 멤버 자체는 C# 8 의 기본 인터페이스 메서드(9부)에서 왔습니다.

10부 퀴즈 1 — 런타임이 필요한 것, 컴파일러만으로 되는 것

Q. C# 9.0 의 기능 가운데 (가) 공변 반환 (나) init 접근자 (다) 대상 형식 new() (라) [ModuleInitializer] (마) static 람다를 "런타임의 새 기능이 있어야 함", "라이브러리에 형식 하나만 있으면 됨", "컴파일러만으로 됨" 으로 나누면?

A. 런타임 기능 — (가). 좁힌 재정의는 새 슬롯과 PreserveBaseOverridesAttribute 로 나가고, 그것을 잇는 것은 런타임의 CovariantReturnsOfClasses 입니다(공변 반환의 메타데이터). 형식 하나 — (나)의 IsExternalInit(직접 선언해도 됩니다, IsExternalInit 직접 선언)와 (라)의 ModuleInitializerAttribute. 모듈 초기화자를 부르는 <Module> 의 정적 생성자 자체는 CLR 에 원래 있던 자리입니다(모듈 초기화자의 자리). 컴파일러만 — (다)와 (마). new() 는 보통의 생성자 호출로, static 람다는 보통 람다와 같은 코드로 나갑니다(식 트리 안의 new() · static 람다의 캐시).

10부 퀴즈 2 — 거절 문장 읽기

Q. C# 9 로 쓴 파일을 -langversion:8.0 으로 컴파일했더니 Feature '…' is not available in C# 8.0 이 하나도 없이 CS0116·CS0246 'record' 만 나왔습니다. 파일에는 C# 9 의 기능이 없다는 뜻입니까?

A. 아닙니다. record 는 문맥 키워드라 8.0 의 규칙으로는 record 형식을 돌려주는 메서드 선언으로 읽히고, 그 선언 오류가 메서드 몸체와 최상위 문 안의 거절(new(), with, 관계 패턴 …)을 가립니다(같은 프로그램 (2)). 기능 이름이 찍히지 않는 거절도 있습니다 — static 멤버의 변성은 CS8904, 대상 형식 조건식은 CS8957 입니다(8.0 으로 내린 표).
