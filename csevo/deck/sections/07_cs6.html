7부를 읽는 법

버전 기록은 C# 6.0 의 기능을 늘어놓은 뒤 이렇게 묶습니다. "In this version, C# started to eliminate language boilerplate to make code more terse and readable." 그리고 언어 기능은 아니지만 같이 한 일 하나를 덧붙입니다 — Roslyn, "the compiler as a service".

  • 1장 — C# 6.0 개관과 Roslyn. 게이트 열두 개, C# 으로 다시 쓴 컴파일러, 같이 온 런타임.
  • 2장 — 문자열 보간. $"…{식}…" 이 무엇으로 번역되고, 뒤 버전에서 어떻게 자랐나.
  • 3장 — nameof. 기호의 이름을 컴파일 시간 상수로.
  • 4장 — null 조건 연산자 ?. 와 ?[]. 사슬 전체의 단락, 형식의 끌어올림, C# 14 의 대입.
  • 5장부터는 식 본문 멤버·자동 속성 초기화자·using static·예외 필터·인덱스 초기화자와 C# 6.0 정리가 이어집니다.

이 부의 예제는 -langversion:6 으로 컴파일합니다. 튜플·out var·지역 함수·패턴 매칭은 C# 7 의 것이라 쓰지 않습니다. 뒤 버전과의 맞물림을 보이는 예제만 그 버전으로 올리고, 한 단계 아래의 거절을 옆에 둡니다.

문자열 보간($"…") C# 6.0

왜 — whats-new: 문자열 앞에 $ 를 붙이고 "use expressions between { and } instead of ordinals". string.Format 의 {0}·{1} 번호 자리에 식을 직접 씁니다.

실행 검증

번호로 맞추면 생기는 실수 — 실행해야 드러난다

string.Format 의 서식 문자열은 컴파일러에게 그냥 문자열입니다. 번호와 인수의 개수가 어긋나도 컴파일은 되고, 실행 중에 FormatException 이 납니다.

넷째 줄처럼 인수가 남는 실수는 예외조차 나지 않고 items 하나를 조용히 버립니다. 보간 문자열에는 번호가 없으니 이 네 가지가 처음부터 생기지 않습니다. 구멍 안의 식은 컴파일러가 보통 식처럼 검사합니다.

실행 검증

서식 지정자와 너비 — {식,너비:서식}

표준: 쉼표 뒤의 상수가 최소 너비이고, 양수면 오른쪽 정렬(앞을 채움), 음수면 왼쪽 정렬(뒤를 채움)입니다. 서식 문자열이 더 길면 자르지 않습니다.

{"abcdefg",5} 는 다섯 칸보다 길어도 그대로 나옵니다. 서식 부분(: 뒤)은 string.Format 과 같은 문법이라, 옛 서식 문자열의 지식이 그대로 쓰입니다.

실행 검증

중괄호와 따옴표

글자 그대로의 { 는 {{, } 는 }} 로 씁니다. 구멍 밖의 글자는 보통 문자열의 이스케이프를 그대로 따릅니다.

구멍 안은 문자열 밖과 같은 식의 자리라서, 따옴표 문자열도 익명 형식의 { x } 도 들어갑니다. 줄을 바꾸는 것만은 C# 11 전까지 막혀 있었습니다(뒤에서).

표준: 서식의 시작인 콜론은 "not nested within any kind of bracket" 일 때만 서식으로 읽습니다. 괄호 밖의 ? : 의 콜론은 서식의 시작이 됩니다.

진단이 넷 나오지만, 둘째 줄의 CS8361 이 원인과 고치는 법을 그대로 말합니다 — "Parenthesize the conditional expression." 13행처럼 괄호 안의 콜론은 서식이 아니므로, 괄호 뒤의 :D3 만 서식이 됩니다.

실행 검증

함정 — 서식 안의 콜론과 역슬래시

서식은 첫 콜론에서 시작해 } 까지입니다. 그래서 {d:HH:mm:ss} 의 둘째·셋째 콜론은 서식의 일부입니다. 문제는 TimeSpan 입니다. 사용자 지정 서식에서 콜론을 \: 로 이스케이프해야 하는데, 일반 $"" 안의 역슬래시는 C# 의 이스케이프 문자입니다.

11행은 \\ 로 두 번, 12행은 축자 보간 문자열 $@ 로 한 번 씁니다. 이스케이프를 빼면 컴파일은 되지만 실행 중에 FormatException 이고, 한 번만 쓰면 C# 의 이스케이프로 읽혀 CS1009 입니다.

FormattableString 으로 받기 C# 6.0

왜 — 표준: 보간 문자열을 FormattableString 이나 IFormattable 로 바꾸면 "a string value is not composed" — 문자열을 만들지 않고, 서식 문자열과 인수를 담은 객체를 만듭니다. 문자열로 만드는 일을 받는 쪽이 정합니다.

컴파일러가 만든 서식 문자열이 그대로 보입니다. 구멍 자리는 {0,-5}·{1:D4} 가 됐고, 글자 그대로의 {{x}} 는 이스케이프된 채 남았습니다. 인수는 object 로 들어가므로 int 는 상자에 담깁니다.

실행 검증

무엇이 될지는 받는 쪽이 정한다

표준: 보간 문자열이 곧바로 IFormattable·FormattableString 으로 변환되면 그 형식이고, "Otherwise, it has the type string."

var 와 object 는 문자열입니다. 대상 형식이 정확히 두 형식 가운데 하나일 때만 객체가 되고, 그 실제 형식은 1장에서 본 공개되지 않은 ConcreteFormattableString 입니다.

실행 검증

함정 — string 오버로드가 있으면 FormattableString 은 뽑히지 않는다

같은 이름에 string 판과 FormattableString 판이 함께 있으면 어느 쪽이 불릴까요.

보간 문자열의 기본 형식이 string 이라 string 판이 이깁니다. FormattableString 판을 부르려면 캐스트하거나 그 판만 두어야 합니다. 한 번 string 변수에 담은 것은 이미 완성된 문자열이라 FormattableString 으로 돌아갈 수 없습니다(CS1503). 인수를 따로 받아 안전하게 쓰려는 API 라면 이 차이가 곧 안전의 차이입니다.

실행 검증

표준이 말하는 번역 — 식 트리로 보기

표준은 보간 문자열의 뜻을 메서드 호출로의 변환으로 정의합니다. 대상이 string 이면 string.Format, 객체면 FormattableStringFactory.Create 이고, 인수는 서식 문자열과 구멍의 식들입니다.

식 트리는 컴파일러가 만든 호출을 그대로 보여 줍니다 — 표준에 적힌 대로입니다. -langversion:14.0 으로 컴파일해도 네 줄이 같습니다(둘째 캡처). 식 트리 밖에서는 이야기가 다릅니다(다음 장).

실행 검증

구멍의 평가와 ToString 의 차례

string.Format 으로 번역된다면 구멍 셋을 모두 평가해 인수 배열을 만든 뒤, Format 안에서 차례로 ToString 을 부를 것입니다. Loud 는 자기가 평가될 때와 ToString 될 때 줄을 찍습니다.

평가와 ToString 이 하나씩 엇갈립니다. string.Format 이라면 나올 수 없는 차례입니다. -langversion:6 인데도 C# 6 의 번역이 아닌 것을 쓰고 있다는 뜻입니다. 무엇인지는 IL 을 읽어 확인합니다.

실행 검증

IL 에서 호출 대상을 읽는 도우미

메서드 몸체의 IL 바이트를 GetILAsByteArray 로 받아, 연산 코드를 하나씩 건너며 call·callvirt·newobj 의 대상을 ResolveMethod 로 찾습니다. 리플렉션만 쓰므로 어느 버전으로 컴파일했든 같은 도구로 봅니다.

실행 검증

보간 문자열은 무엇을 부르나 — C# 6 으로 컴파일해도

string 이 되는 보간은 DefaultInterpolatedStringHandler 로 번역됐습니다 — C# 10 에 온 형식입니다. int 구멍은 인수 하나짜리 제네릭 AppendFormatted 라 상자에 담기지 않습니다. 구멍이 모두 문자열이면 String.Concat 이고, FormattableString 만 표준대로 Create 입니다. 구현 세부이며, 이 SDK 의 동작입니다.

실행 검증

왜 언어 버전과 상관없나 — C# 10 제안의 규칙

C# 10 의 제안은 표준의 보간 문자열 규칙을 이렇게 고칩니다. "If the type of an interpolated string is string and the type System.Runtime.CompilerServices.DefaultInterpolatedStringHandler exists, and the current context supports using that type, the string is lowered using the handler pattern." 조건에 언어 버전이 없습니다.

제안의 동기는 string.Format 번역의 비용입니다 — 구조체 인수를 상자에 담고, 대부분 인수 배열을 할당하고, 쓰지 않을 문자열도 만든다는 것.

그래서 C# 6 으로 쓴 코드를 오늘의 SDK 와 .NET 10 으로 다시 컴파일하면, 소스를 고치지 않아도 이 번역을 받습니다. 제안의 규칙대로라면 형식이 없는 옛 대상 프레임워크에서는 string.Format 이겠지만, 이 덱은 .NET 10 참조 팩만 쓰므로 그쪽은 보이지 못합니다.

문서 근거

"the current context supports" — 구멍에 await 가 있으면

제안은 그 단서의 예로 async 메서드를 듭니다. 처리기(handler)는 ref struct(8부)라 async 메서드에서 보통 허용되지 않으므로, 구멍에 await 가 없을 때만 처리기를 써도 된다고 적습니다.

첫 보간은 평가와 ToString 이 엇갈리고(처리기), await 가 든 둘째는 둘을 먼저 평가한 뒤 ToString 합니다 — string.Format 의 차례입니다. 같은 메서드 안에서도 구멍에 따라 번역이 다릅니다.

실행 검증

함정 — $ 를 빠뜨리거나, 보간한 것을 다시 서식으로 쓰거나

$ 가 없는 "Hello, {name}!" 은 경고 없이 글자 그대로 찍힙니다. 더 고약한 것은 보간한 결과를 WriteLine(format, arg) 처럼 서식 문자열을 받는 자리에 넘길 때입니다. 사용자 입력의 {0} 이 자리 표시자로 읽혀 ! 로 바뀌었고, {{{name}}} 이 만든 {Ada} 는 서식 오류가 됐습니다.

실행 검증

뒤 버전과의 맞물림 — 보간 문자열 처리기, C# 10

C# 10 제안은 보간을 받는 쪽이 정의한 "handler pattern" 으로 번역할 수 있게 했습니다. [InterpolatedStringHandler] 형식의 생성자가 글자 길이와 구멍 수를 받고, AppendLiteral·AppendFormatted 가 조각을 하나씩 받습니다.

실행 검증

뒤 버전과의 맞물림 — 컴파일러가 쓰는 코드를 손으로, C# 10

앞의 IL 에서 본 호출을 그대로 손으로 쓰면 이렇습니다. DefaultInterpolatedStringHandler 는 공개 형식이라 직접 쓸 수 있습니다.

제안은 생성자의 마지막 out bool 이 false 면 Append… 를 부르지 않게 했고, 그러면 뒤의 구멍이 평가되지 않는 것이 "very confusing" 할 수 있다고 적은 뒤 이렇게 정했습니다. "Answer: We will have conditional evaluation of the holes."

Expensive() 는 두 번 쓰였지만 한 번만 돌았습니다. C# 6 의 보간에서 "구멍은 반드시 한 번 평가된다" 는 규칙이, 받는 쪽이 처리기면 더는 성립하지 않습니다. 구멍에 부수 효과를 두지 않는 것이 안전합니다.

이것도 전용 문장(CS8967)으로 거절합니다. 줄바꿈이 있는 두 구멍마다 하나씩입니다.

실행 검증

뒤 버전과의 맞물림 — 원시 보간 문자열, C# 11

C# 11 제안은 따옴표와 중괄호가 많은 JSON 같은 글을 이스케이프 없이 쓰려고 시작 구분자를 늘일 수 있게 했습니다. 보간 문자열에서 { 와 } 를 이스케이프해야 하는 것도 "similarly frustrating" 이라고 적습니다.

$$ 로 시작하면 구멍이 {{…}} 이 되고, 한 겹 중괄호는 글자 그대로입니다. JSON 의 중괄호를 {{ 로 바꿔 쓰던 C# 6 의 방식(앞에서)이 거꾸로 된 셈입니다.

2장 퀴즈 — 문자열 보간

Q. -langversion:6 으로 컴파일한 string s = $"{a}-{b}"; 에서, a 의 ToString() 은 b 가 평가되기 전에 불립니까, 뒤에 불립니까? 같은 줄을 FormattableString f = … 로 바꾸면요?

A. 이 SDK 와 .NET 10 에서는 전입니다. string 이 되는 보간은 언어 버전과 상관없이 DefaultInterpolatedStringHandler 로 번역돼, 구멍 하나를 평가하자마자 덧붙입니다(평가와 ToString 의 차례). FormattableString 으로 받으면 FormattableStringFactory.Create 에 두 값을 모아 넘기므로(IL 의 호출 대상), ToString 은 두 구멍을 모두 평가한 뒤에야 불릴 수 있습니다. 구멍에 await 가 있어도 모두 평가한 뒤입니다.

3장

nameof — 이름을 문자열이 아니라 기호로

무엇을 돌려주나 · 평가하지 않는 상수 · 이름 바꾸기 · 함정 · C# 11·12·14 에서 넓어진 것

nameof 식 C# 6.0

왜 — whats-new: nameof 는 기호의 이름으로 평가되고, "a great way to get tools working whenever you need the name of a variable, a property, or a member field" 입니다.

결과는 언제나 string 입니다. C# 5 의 거절은 줄마다 하나씩, 일곱 번 나옵니다. nameof 라는 이름의 메서드가 없으니 연산자로 읽혔다는 뜻입니다(뒤에서).

실행 검증

돌려주는 것은 마지막 식별자 하나

표준: 값은 "the last identifier of the named_entity before the optional final type_argument_list" 이고, 앞의 @ 는 떼어 냅니다.

점으로 이은 이름은 마지막 조각만 남습니다(Generic). 형식 인수는 버려지고(List), 별칭은 원래 이름이 아니라 별칭 그대로입니다(Text). Outer.Count 처럼 인스턴스 멤버를 형식 이름으로 가리켜도 되고, 오버로드가 여럿인 WriteLine 도 됩니다. int.MaxValue 처럼 키워드 형식 뒤의 멤버도 받습니다.

실행 검증

피연산자는 평가하지 않는다

표준: nameof 식은 "has no effect at runtime" — 피연산자를 평가하지 않고, 확정 대입 분석에서도 무시합니다.

empty 는 null 인데 empty.Next.Next.Value 가 예외 없이 Value 가 됩니다. 대입한 적 없는 unassigned 도 CS0165 없이 통과합니다. 컴파일러는 이름을 확인하기만 하고 코드를 만들지 않습니다.

실행 검증

컴파일 시간 상수 — const · 특성 · case

표준: nameof 식은 "a constant expression of type string" 입니다. 상수가 들어가는 자리면 어디든 씁니다.

식 트리로 받아 보면 몸체가 Constant: "Main" 입니다 — 호출도 리플렉션도 없이 문자열 하나로 컴파일됐습니다. const string Key = nameof(Key) 처럼 자기 이름을 자기 값으로 삼는 것도 됩니다. 보간 문자열이 상수가 되려면 C# 10 을 기다려야 했지만(2장), + 로 이은 것은 C# 6 에서도 상수입니다.

실행 검증

왜 문자열이 아니라 nameof 인가 — 이름을 바꾼 뒤

whats-new 는 가장 흔한 쓰임으로 "to provide the name of a symbol that caused an exception" 을 듭니다. 문자열 리터럴은 이름 바꾸기 도구가 따라가지 못합니다.

AddOld 의 예외는 이제 없는 매개변수 name 을 가리킵니다. 컴파일러는 문자열 안을 보지 않으므로 아무 경고도 없습니다. nameof(userName) 은 매개변수와 이름이 어긋나면 컴파일이 되지 않습니다.

실행 검증

INotifyPropertyChanged — 다른 속성의 이름도

whats-new 가 드는 또 하나의 쓰임은 "XAML-based applications that implement the INotifyPropertyChanged interface" 입니다.

C# 5 의 [CallerMemberName](6부)은 지금 실행 중인 멤버의 이름만 줍니다. Age 의 setter 에서 IsAdult 의 변경을 알리려면 그 이름을 직접 적어야 하고, 그 자리가 nameof 의 자리입니다. Raise 안의 ?.Invoke 는 4장에서 봅니다.

실행 검증

함정 — nameof(T) 는 형식 인수가 아니라 "T"

표준의 예: 제네릭 메서드 안의 nameof(T) 는 "T" 입니다. 상수라서 호출마다 달라질 수 없습니다.

실제 형식의 이름이 필요하면 실행 시간의 typeof(T).Name 입니다. 그쪽은 제네릭 형식에 `1 같은 인수 개수 표시가 붙는다는 차이도 있습니다(마지막 줄).

실행 검증

함정 — nameof 라는 메서드가 있으면 그것을 부른다

표준: nameof 는 키워드가 아니라서 nameof(x) 는 늘 메서드 호출과 구문이 같습니다. "For compatibility reasons" 이름 nameof 를 찾을 수 있으면 — 호출이 맞든 틀리든 — 호출로 다룹니다.

C# 5 시절에 nameof 라는 메서드를 둔 코드는 C# 6 에서도 뜻이 바뀌지 않습니다. 1장의 구문 트리에서 nameof(p) 가 InvocationExpression 으로 나온 것(1장의 Roslyn API)이 이 규칙의 겉모습입니다.

실행 검증

nameof 가 받지 않는 것

표준: 메서드 그룹에 형식 인수 목록을 붙이면 오류이고, 표준의 예는 nameof(List<>) 와 nameof(int) 도 잘못이라고 적습니다.

눈여겨볼 것은 첫 줄입니다. C# 6 에서 nameof(List<>) 를 거절하는 메시지는 "C# 14.0 을 쓰라" 입니다 — 오늘의 컴파일러는 이 문법을 C# 14 의 기능으로 압니다(뒤에서). nameof(int) 는 의미 오류가 아니라 구문 오류라서, 켜면 그 한 줄만 남고 나머지가 가려집니다. dynamic 은 형식 이름이 아니라 그냥 찾지 못한 이름입니다.

실행 검증

뒤 버전과의 맞물림 — 특성 안에서 매개변수 이름, C# 11

C# 11 whats-new: 매개변수와 형식 매개변수의 이름이 그 메서드에 붙은 특성의 nameof 안에서 범위에 듭니다. 제안은 NotNullWhen 같은 특성이 매개변수를 가리켜야 하는데 "those parameters are currently not in scope" 였다고 적습니다.

이 기능에는 게이트가 없습니다. 이 SDK 는 C# 10 으로도 매개변수 이름을 찾아 줍니다. 그래서 "C# 11 에서 됐다" 는 것을 한 단계 아래의 거절로 보일 수 없습니다. 문서가 언어 버전에 따라 달라진다고 적은 것은 다음 장의 가림입니다.

실행 검증

뒤 버전과의 맞물림 — 형식 매개변수가 바깥 형식을 가린다

Roslyn 의 깨지는 변경 문서: "When the language version is C# 11 or later" 메서드 특성의 nameof 안에서 형식 매개변수가 범위에 들어, 같은 이름의 바깥 형식을 가리던 코드가 오류가 된다고 적고 그 예를 듭니다.

문서대로라면 C# 10 에서는 바깥 클래스 TItem 의 Code 로 읽혀 컴파일돼야 합니다. 이 SDK(10.0.112)는 세 버전 모두에서 형식 매개변수 TItem 으로 읽고 CS0704 로 거절했습니다. 문서와 오늘의 컴파일러가 다른 곳이라, 이 덱은 캡처를 따르고 문서의 문장은 인용으로만 둡니다.

뒤 버전과의 맞물림 — 인스턴스 멤버를 거쳐 가는 nameof, C# 12

C# 12 의 목록: "Nameof accessing instance members" — nameof 안의 인스턴스 멤버 사용 제약을 풀었습니다(예 nameof(field.ToString)).

C# 6 부터 nameof(Outer.Count) 처럼 형식 이름으로 가리킨 인스턴스 멤버는 정적 문맥에서도 됐습니다(마지막 식별자 하나). 막혀 있던 것은 인스턴스 멤버를 거쳐 한 단계 더 들어가는 Customer.Length 였고, 거절은 그런 자리 셋에서 나옵니다.

실행 검증

뒤 버전과의 맞물림 — nameof(List<>), C# 14

C# 14 whats-new: "the argument to nameof can be an unbound generic type". 제안은 결과에 아무 영향도 없는 형식 인수를 골라야 하는 것을 "a common frustration" 이라 부르고, 형식 매개변수의 제약을 맞추려고 더미 클래스까지 만들어야 했다고 적습니다.

Box<T> 는 T : IComparable<T> 라서 C# 6 식으로는 그 제약을 만족하는 형식(여기서는 int)을 골라 적어야 했습니다. 3장 앞의 nameof 가 받지 않는 것에서 C# 6 이 이 문법을 "14.0 을 쓰라" 며 거절한 까닭이 이것입니다. 2026-10 기준.

실행 검증

3장 퀴즈 — nameof

Q. Order o = null; 다음 줄의 nameof(o.Customer.Name) 은 무엇을 돌려줍니까? 예외가 납니까? 제네릭 메서드 Save<T> 안의 nameof(T) 는 Save<Order>() 로 부르면 무엇입니까?

A. "Name" 이고 예외는 없습니다. nameof 는 피연산자를 평가하지 않고 마지막 식별자만 상수로 남깁니다 (평가하지 않는다). nameof(T) 는 언제나 "T" 입니다 — 컴파일 시간 상수라 호출마다 달라질 수 없습니다. 실제 형식 이름은 typeof(T).Name 입니다(nameof(T) 의 함정).

null 조건 연산자 — null 이면 거기서 멈춘다

?. 와 ?[] · 사슬 전체의 단락 · T? 로의 끌어올림 · 이벤트 · 함정 · C# 8 과 C# 14

null 조건 연산자(?.) C# 6.0

왜 — whats-new: "The null conditional operator makes null checks much easier and fluid." 받는 쪽이 null 이면 NullReferenceException 대신 "it short-circuits and returns null".

C# 5 판의 && 사슬과 삼항 연산자가 p?.Home?.City 한 줄이 됐고, 출력은 같습니다. 배열의 셋째 원소는 null 이지만 p?.Name 도 예외 없이 빈 칸입니다. C# 5 로 내리면 ?. 마다 하나씩 셋입니다.

실행 검증

?[] — 원소 접근도 같은 규칙

whats-new: "You can also use a null conditional operator for array or indexer access. Replace [] with ?[]."

a?[0] 의 결과도 int? 로 끌어올려집니다(T? 로 끌어올림). 지키는 것은 받는 쪽의 null 뿐이라, 빈 배열의 [0] 은 여전히 IndexOutOfRangeException 입니다.

실행 검증

단락 — null 이면 사슬의 나머지 전체를 건너뛴다

표준: P?.A 에 이어지는 멤버 접근·원소 접근·호출(dependent_access)은 모두 하나의 식에 속합니다. P 가 null 이면 그 뒤 전체가 평가되지 않습니다.

none?.Next.Tag(Arg("a")) 는 Next 도 Tag 도, 인수 Arg("a") 도 부르지 않았습니다. 그러나 ?. 는 바로 왼쪽 하나만 지킵니다. one 은 null 이 아니고 one.Next 가 null 이라, 인수를 평가한 뒤 Tag 호출에서 예외가 납니다. 사슬의 고리마다 null 일 수 있으면 고리마다 ?. 를 씁니다(마지막 줄).

실행 검증

값 형식 결과는 T? 로 끌어올린다

표준: P.A 의 형식 T 가 null 이 될 수 없는 값 형식이면 E 의 형식은 T? 이고, 뜻은 ((object)P == null) ? (T?)null : P.A 와 같습니다 — "Except that P is evaluated only once."

s?.Sides 는 int 가 아니라 int? 입니다. 결과가 null 일 수 있으니 그렇게밖에 될 수 없습니다. s?.Origin.X 처럼 사슬 끝이 값 형식이어도 사슬 전체의 형식이 int? 가 됩니다. 참조 형식 string 은 그대로입니다.

실행 검증

?. 와 ?? — 그리고 bool? 의 함정

whats-new: ?. 의 결과는 대개 null 병합 연산자 ?? 와 함께 써서 기본값을 줍니다. 단락했을 때의 null 은 "typed to match the full expression" 입니다.

o?.Paid 는 bool? 이라 if 의 조건이 될 수 없습니다(CS0266). ?? false 로 값을 정하거나 == true 로 견줍니다. null 과 true 를 견주면 false 이므로 셋째 줄도 False 입니다.

실행 검증

받는 쪽은 한 번만 평가된다

whats-new: "The rules of the ?. operator ensure that the left-hand side of the operator is evaluated only once." 그래서 메서드 호출을 포함한 어떤 식이든 왼쪽에 둘 수 있습니다.

삼항 연산자로 옮겨 쓰면 Lookup() 이 두 번 불립니다 — 확인할 때 한 번, 쓸 때 한 번. ?. 는 C# 5 에서 임시 변수를 손으로 두던 셋째 판과 같은 일을 합니다.

실행 검증

이벤트 올리기 — Opened?.Invoke(…)

whats-new: "The most common use of member functions with the null conditional operator is to safely invoke delegates (or event handlers) that may be null." 왼쪽을 한 번만 평가한다는 규칙이 이 관용구를 가능하게 한다고 적고, C# 6 에서 권하는 꼴로 this.SomethingHappened?.Invoke(this, eventArgs); 를 듭니다.

C# 5 판은 필드를 지역 변수에 먼저 복사하고, 그 복사본을 확인하고 부릅니다. ?.Invoke 는 필드를 한 번 읽은 값으로 확인과 호출을 함께 하므로 같은 모양이 됩니다. whats-new 도 대리자를 부를 때는 ?. 로 Invoke 메서드에 접근하라고 적습니다.

실행 검증

void 를 돌려주는 호출

표준: ?. 로 끝나는 호출이 문장으로 쓰이면 "may be classified as nothing" — 결과가 없어도 됩니다. 값이 필요한 자리의 ?. 는 결과 형식이 void 이면 오류입니다.

문장으로 쓴 sb?.Clear() 와 log?.Invoke() 는 null 에서 그냥 지나갑니다. 값을 내는 Append 는 사슬로 이어 쓸 수 있습니다. void 인 Invoke() 의 결과를 변수에 담으려 하면 CS0029 입니다 — 끌어올릴 T? 가 없습니다.

실행 검증

받는 쪽이 Nullable<T> 일 때

표준: P 의 형식이 nullable 값 형식이면 P?.A 는 P.Value.A 를 뜻합니다 — .Value 를 적지 않습니다.

when?.Year 는 DateTime 의 Year 이지 Nullable<DateTime> 의 멤버가 아닙니다. null 이 될 수 없는 int 에는 ? 를 쓸 수 없습니다(CS0023) — 확인할 null 이 없기 때문입니다.

실행 검증

함정 — 정체를 모르는 T 는 T? 로 만들 수 없다

표준: 결과 형식 T 가 "a type parameter that is not known to be either a reference type or a non-nullable value type" 이면 컴파일 오류입니다. 결과를 T? 로 끌어올릴지 그대로 둘지 정할 수 없기 때문입니다.

b?.Value?.ToString() 은 사슬 끝이 string 이라 됩니다. where T : struct 이면 int? 로 끌어올리고, class 제약이면 그대로 둡니다 — Ref 는 T 를 돌려주며 컴파일되고 마지막 줄의 True 를 찍습니다. 제약이 없는 T 에서 멈추면 CS8978 입니다.

실행 검증

함정 — 사용자 정의 == 는 보지 않는다

표준이 적은 ?. 의 뜻은 ((object)P == null) ? … : P.A 입니다. (object) 캐스트 때문에 형식이 오버로드한 == 가 아니라 참조가 null 인지만 봅니다.

h == null 은 True 인데 h?.Name 은 멤버에 들어갔습니다. 형식이 == 로 "없는 것" 을 흉내 내면 ?. 와 != 판의 결과가 갈립니다. 둘을 서로 바꿔 쓸 수 있다고 가정하면 안 되는 자리입니다.

실행 검증

함정 — await c?.FetchAsync()

c 가 null 이면 c?.FetchAsync() 는 null Task 입니다. 그것을 await 하면 단락은 거기서 끝나고, null 을 기다리려다 예외가 납니다.

await 는 ?. 사슬의 일부가 아니라 그 결과에 붙는 연산자라, null 이 그대로 GetAwaiter 호출에 들어갑니다(6부). Task 를 먼저 받아 확인하는 둘째 판이 안전합니다.

실행 검증

dynamic 받는 쪽

?. 는 dynamic 에도 씁니다. null 확인은 바로 하고, 멤버 찾기는 실행 시간 바인더(5부)가 합니다.

?. 가 막아 주는 것은 null 뿐입니다. int 에 Length 가 없다는 것은 실행 중에 RuntimeBinderException 으로 드러납니다.

실행 검증

식 트리에는 못 들어간다 — C# 6 에서도, C# 14 에서도

4부에서 C# 14 로 확인한 거절(4부)이 이 기능이 온 C# 6 에서도 같습니다. 대리자로 받는 람다에는 문제가 없습니다.

식 트리가 필요하면 표준이 적은 뜻 그대로(s == null ? (int?)null : s.Length) 풀어 씁니다. 트리의 IIF 가 그 모양입니다. 같은 자리에 들어가는 보간 문자열(2장)과 대조됩니다.

뒤 버전과의 맞물림 — null 조건 대입, C# 14

C# 14 whats-new: ?. 와 ?[] 를 대입과 복합 대입의 왼쪽에 쓸 수 있고, "The right side of the = operator is evaluated only when the left side isn't null." 제안은 증감 연산자는 지원하지 않는다고 적습니다.

off?.Theme = Pick("blue") 의 오른쪽은 평가되지 않았습니다(Pick(blue) 줄이 없음). C# 13 은 대입 다섯 줄을 모두 거절하고, ++ 는 C# 14 에서도 CS1059 입니다. 2026-10 기준.

C# 6 의 ?. 는 대입의 왼쪽이 될 수 없었다

같은 파일을 이 기능이 온 C# 6 으로 컴파일하면, 거절의 문장이 "변수가 아니다" 가 아니라 "C# 14 를 쓰라" 입니다.

오늘의 컴파일러는 a?.b = c 를 C# 14 의 기능으로 알고, 그보다 낮은 버전에서는 모두 게이트로 거절합니다. C# 6 시절의 컴파일러가 어떤 문장으로 거절했는지는 이 기계에서 볼 수 없습니다(0부).

뒤 버전과의 맞물림 — nullable 참조 형식과 ?., C# 8

C# 8 whats-new: nullable 참조 형식의 변수는 "the compiler uses flow analysis to ensure that any variable of a nullable reference type is checked against null before it's accessed". ?. 를 쓴 검사도 그 흐름 분석이 읽습니다.

경고는 10행 하나뿐입니다. 9행은 if (s?.Length > 0) 안이라 경고가 없습니다 — null > 0 은 거짓이므로 그 안에서 s 는 null 일 수 없습니다. 10행의 경고대로, null 을 넘기면 실행 중에 예외가 납니다.

4장 퀴즈 — null 조건 연산자

Q. order?.Lines.Count(Log("x")) 에서 order 가 null 이면 Log 는 불립니까? order 는 있고 Lines 가 null 이면요? 그리고 이 식의 형식은 무엇입니까(Count 는 int 를 돌려줍니다)?

A. order 가 null 이면 사슬 전체를 건너뛰므로 Log 는 불리지 않습니다. Lines 가 null 이면 ?. 는 거기를 지키지 않으므로 인수 Log("x") 를 평가한 뒤 NullReferenceException 입니다 (사슬 전체의 단락). 형식은 끌어올린 int? 입니다(T? 로 끌어올림).
