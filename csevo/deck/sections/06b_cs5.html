호출자 정보 특성 — 부른 자리를 컴파일러가 적는다

CallerMemberName · CallerFilePath · CallerLineNumber · INotifyPropertyChanged · 함정 · CallerArgumentExpression

호출자 정보 특성 (caller info attributes) C# 5.0

왜 — 버전 기록: 호출자 정보 특성은 "a ton of boilerplate reflection code" 없이 지금 도는 자리의 정보를 얻게 해 주고, 진단과 로깅에 쓸 데가 많다. 표준도 "logging and reporting" 을 듭니다.

인수를 빼고 부르면 기본값 대신 부른 자리의 멤버 이름·파일 경로·줄 번호가 들어갑니다. Save 안에서 부르면 Save 와 18 이 들어갑니다. 받는 쪽은 그냥 문자열과 정수를 받을 뿐입니다.

실행 검증

게이트가 없다 — C# 4 로 내려도 채워진다

C# 5 의 게이트는 async 하나입니다(1장). 호출자 정보는 컴파일러가 특성의 이름을 알아보고 하는 일이라 언어 버전을 확인하지 않습니다.

그래서 보일 수 없는 것 — 이 특성이 없는 규칙에서 빠진 인수는 기본값("", 0)이 됩니다. 그것이 선택적 매개변수의 규칙입니다. 지금의 컴파일러는 -langversion:4 에서도 채우므로 그 차이를 흉내 내지 못합니다(0부의 꼴 (나)가 안 되는 경우). 바탕인 선택적 매개변수만 C# 4 의 게이트입니다(5부).
실행 검증

이전엔 — 실행 중에 스택을 거슬러 올라가기

버전 기록이 말하는 "boilerplate reflection code" 의 한 꼴은 StackFrame 으로 부른 쪽의 프레임을 꺼내는 것입니다. 같은 일을 두 방식으로 합니다.

람다 안에서 부르면 차이가 납니다. 스택에는 컴파일러가 만든 메서드(<Main>b__2_0)가 있고, 호출자 정보 특성은 소스에 적힌 멤버 이름 Main 을 줍니다. 앞의 방식은 실행할 때마다 스택을 걷고, 줄 번호는 PDB 가 있어야 나옵니다.

실행 검증

값은 부른 쪽에 박힌 상수

표준: 인수를 빼면 줄 번호는 "a numeric literal", 파일 경로와 멤버 이름은 "a string literal" 이 그 자리에 들어갑니다. 부른 메서드의 IL 을 읽어 확인합니다.

Log() 한 줄이 ldstr "Caller", ldc.i4.s 13, call Log 로 번역됐습니다. 실행 중에 알아내는 것이 없으니 비용도 상수를 넘기는 만큼입니다. 거꾸로, 라이브러리의 메서드에 이 특성을 더해도 이미 컴파일된 호출자에는 아무 값도 생기지 않습니다 — 값은 호출자를 컴파일할 때 정해집니다.

실행 검증

파일 경로는 컴파일한 곳의 경로 — /work 와 #line

표준은 경로의 꼴을 "implementation-dependent" 라고 두고, 줄 번호와 경로가 #line 지시문의 영향을 받을 수 있다고 적습니다.

이 덱의 캡처에서 경로가 /work 로 시작하는 것은 csrun 이 -pathmap 을 넘기기 때문입니다(0부). 둘째 줄의 True 가 문자열 자체가 /work/Program.cs 임을 보입니다 — 캡처 정규화가 바꾼 것이 아닙니다. 경로 옵션이 없으면 빌드한 기계의 절대 경로가 어셈블리에 들어갑니다.

실행 검증

쓰임 하나 — INotifyPropertyChanged

속성이 바뀌었다고 알리는 INotifyPropertyChanged 는 이벤트 인수에 속성 이름을 문자열로 담습니다. "What's new in C# 14" 의 field 예제도 setter 에서 인수 없이 OnPropertyChanged() 를 부릅니다 — 이름은 [CallerMemberName] 이 채웁니다.

setter 안의 호출은 속성 이름을 받습니다(접근자). 같은 값을 다시 넣은 셋째 대입은 알림이 없습니다. 버전 기록은 이 쓰임을 따로 들지 않으니, "이것 때문에 생겼다" 고까지는 말하지 않습니다.

실행 검증

이전엔 — 이름을 문자열로 적고, 이름을 바꾸면 어긋난다

C# 4 에서는 setter 마다 속성 이름을 문자열로 넘겼습니다. 속성 이름을 고쳐도 문자열은 따라오지 않습니다. 컴파일러는 아무 말도 하지 않습니다.

함정 — 듣는 쪽은 Name 이 바뀌었다고 듣지만 그런 속성은 없습니다. 화면이 갱신되지 않는 버그가 되고, 컴파일도 실행도 멀쩡합니다. C# 6 의 nameof 도 같은 자리를 겨냥합니다 — "What's new in C# 6" 은 그 쓰임으로 INotifyPropertyChanged 를 듭니다(7부).
실행 검증

직접 넘긴 값이 이긴다 — 그리고 감싸는 메서드

표준: 인수를 빼야 호출자 정보가 들어갑니다. 넘기면 그 값이 쓰이고, null 도 값입니다. 표준은 대리자 선언에도 이 특성을 허용합니다.

함정 — Info 처럼 감싸기만 하면 모든 로그가 Info 에서 온 것이 됩니다. 감싸는 메서드도 같은 특성의 매개변수를 받아 그대로 넘겨야 합니다(Warn). 대리자로 부를 때는 대리자 형식의 특성이 보고, 부른 자리 (Run)가 들어갑니다.
실행 검증

CallerMemberName 이 주는 이름 — 접근자·인덱서·초기화자

표준: 속성·이벤트 접근자 안이면 속성·이벤트의 이름, 인덱서면 Item(또는 IndexerName 의 이름), 필드 초기화자면 필드의 이름. 제네릭 메서드는 형식 매개변수 없이, 명시적 인터페이스 구현은 인터페이스 이름 없이 줍니다.

get_Size·set_Size·add_Changed 같은 메서드 이름이 아니라 소스의 멤버 이름이 나옵니다. 그래서 setter 하나에 OnPropertyChanged() 를 쓰면 속성 이름이 됩니다(앞).

실행 검증

생성자·연산자는 구현이 정한다 — 그리고 암시적 호출

표준: 인스턴스·정적 생성자, 종료자, 연산자 안에서의 이름은 "implementation-dependent". 또 암시적 base 생성자 호출처럼 소스에 자리가 없는 호출에는 호출자 정보가 들어가지 않고 기본값이 쓰입니다.

Roslyn 은 메타데이터 이름(.ctor, .cctor, op_Addition)을 줍니다. 표준이 정하지 않은 값이라 다른 컴파일러에서는 다를 수 있습니다. : base() 를 적은 Explicit 만 .ctor 를 받았습니다 — 같은 생성자 호출인데 적었느냐 아니냐로 값이 갈립니다.

실행 검증

람다·반복기·async 안에서 — 감싼 멤버의 이름

람다와 익명 메서드, 반복기, async 메서드의 몸체는 컴파일러가 다른 메서드나 클래스로 옮깁니다(4장). 그래도 CallerMemberName 은 소스에서 그 코드를 감싼 멤버를 줍니다.

마지막 줄이 람다가 실제로 옮겨 간 메서드의 이름입니다. 값이 소스 위치로 정해지는 상수라서(앞) 컴파일러가 코드를 어디로 옮기든 바뀌지 않습니다. 반복기의 MoveNext 나 상태 기계의 이름도 새어 나오지 않습니다.

실행 검증

dynamic 호출은 채우지 않고, 쿼리 식은 채운다

표준: "calls that are dynamically bound will not substitute caller information". 예외는 쿼리 식입니다. 번역된 호출이 특성 붙은 인수를 빼면 채우고, 위치는 그 호출을 낳은 쿼리 절입니다.

dynamic 호출은 실행 중에 결정되므로 소스 위치를 넘길 수 없어 기본값(-1)이 갑니다. 쿼리 식의 줄 번호는 from 이 있는 32 가 아니라 where 가 있는 33 입니다(4부의 번역).

실행 검증

오버로드 해석은 호출자 정보를 보지 않는다

표준: 특성 붙은 매개변수도 빠진 선택적 매개변수일 뿐이라 오버로드 해석은 다른 빠진 매개변수처럼 무시합니다. 동점이면 기본값을 채워야 하는 쪽이 집니다.

함정 — 이미 있는 Log(string) 옆에 호출자 정보를 받는 Log(string, [CallerMemberName] string) 을 더해도 Log("a") 는 옛 것을 부릅니다. 새 오버로드가 불리게 하려면 옛 것을 지워야 합니다. Trace("c") 는 string 이 object 보다 나은 변환이라 특성 쪽이 이겼습니다 — 특성 때문이 아닙니다.
실행 검증

컴파일러가 막는 자리와 경고하는 자리

표준: 줄 번호는 int.MaxValue 에서, 경로와 이름은 string 에서 표준 암시적 변환이 있는 형식에만 붙일 수 있고, 여러 특성이 겹치면 줄 번호 → 경로 → 이름 차례로 하나만 삽니다.

오류 셋, 경고 둘입니다. byte 는 줄 번호의 최대값을 담지 못해 거절됩니다(long 은 됩니다). 명시적 인터페이스 구현은 언제나 인터페이스를 통해 불리므로 그 자리의 특성은 효과가 없다는 경고(CS4026)가 납니다.

실행 검증

특성 인수 안에서, 그리고 partial 메서드

표준: 멤버 이름은 함수 멤버의 몸체뿐 아니라 "within an attribute applied to the function member itself" 에서도 채워집니다. partial 메서드는 정의하는 쪽의 특성만 살고, 구현하는 쪽에만 있는 특성은 무시됩니다.

특성의 생성자 호출은 특성을 붙인 자리에서 컴파일되므로, [Tag] 는 붙은 멤버의 이름과 그 줄을 받습니다. 그 인수는 어셈블리에 담겨 있다가 리플렉션이 특성 객체를 만들 때 생성자로 넘어갑니다. partial 의 구현부에는 특성이 없어도 정의부의 [CallerMemberName] 이 일합니다.

실행 검증

줄 번호의 형식, 그리고 여러 줄에 걸친 호출

표준: 줄 번호 특성은 int.MaxValue 에서 표준 암시적 변환이 있는 형식이면 되고, 호출이 여러 줄에 걸치면 어느 줄을 고를지는 "implementation-dependent" 입니다.

object 로 받으면 상자에 담긴 Int32 가 옵니다. 두 줄에 걸친 호출에서 Roslyn 은 Line 이 적힌 줄을 골랐습니다 — 쪼갠 호출은 괄호가 닫히는 22 가 아니라 21, 다른 호출의 인수로 들어간 호출은 문장이 시작하는 23 이 아니라 24 입니다. 표준이 정하지 않은 값이므로 기대지 않는 편이 안전합니다.

같이 온 런타임 — Caller*Attribute 형식 C# 5.0

언어 기능은 라이브러리 형식에 기댑니다. "Relationships" 문서는 C# 이 뒤 버전에서 늘린 의존의 예로 CallerFilePathAttribute 와 CallerMemberNameAttribute 를 듭니다.

.NET 10 에는 넷이 있습니다. 셋은 인수 없는 봉인된 특성이고, 넷째 CallerArgumentExpressionAttribute 는 매개변수 이름 하나를 받습니다(다음 장). 컴파일러는 이 형식을 이름으로 알아봅니다 — 특성 자체에는 아무 동작이 없습니다.

실행 검증

뒤 버전의 문법 안에서 — 컴파일러가 지은 이름이 새어 나온다

표준은 이름을 "the name of that member" 라고만 합니다. 멤버가 아닌 자리 — C# 7 의 지역 함수, C# 9 의 최상위 문 — 에서는 감싼 멤버의 이름이 나옵니다.

함정 — 최상위 문 안에서는 컴파일러가 만든 진입점의 이름 <Main>$ 가 그대로 나옵니다. 지역 함수 Local 안에서도 마찬가지입니다 — 지역 함수는 멤버가 아니기 때문입니다. init 접근자와 C# 14 의 확장 속성은 속성 이름을 줍니다.

뒤 버전과의 맞물림 — CallerArgumentExpression 은 C# 10

"What's new in C# 10" 이 이 특성을 소개합니다. 제안서의 동기: 단언이 실패하면 스택 트레이스에는 "the filename, line number, and method name" 만 남아 어느 단언인지 알 수 없다 — C# 5 의 특성 셋이 주는 바로 그 정보입니다.

문서와 다른 곳 — 게이트 표에 이 기능이 없어 -langversion:5 에서도 채워집니다. C# 5 의 특성 셋과 같은 처지입니다(앞). 이 덱은 문서대로 C# 10 의 것으로 셉니다(11부). ParamName = name 은 .NET 10 의 ThrowIfNull 이 같은 특성으로 변수 이름을 받은 결과입니다.

6장 퀴즈 — 호출자 정보 특성

Q. 라이브러리 v1 의 Log(string msg) 를 v2 에서 Log(string msg, [CallerMemberName] string m = "") 로 바꾸고, 앱은 다시 컴파일하지 않은 채 v2 DLL 만 바꿔 넣었습니다. 로그에 멤버 이름이 찍힙니까?

A. 찍히지 않습니다. 멤버 이름은 호출하는 쪽을 컴파일할 때 상수로 박히므로(상수) 옛 앱의 IL 에는 그 상수가 없습니다. 특성은 받는 쪽 선언에 붙어 있지만, 값을 만드는 일은 부르는 쪽의 컴파일러가 합니다. 앱을 다시 컴파일해야 이름이 들어갑니다.

foreach 변수 포착의 변화 — 반복마다 새 변수

문서의 한 줄 · 게이트 없음 · 풀어 쓴 두 꼴 · 클로저 객체 · for 는 그대로 · 뒤 버전의 foreach

foreach 반복 변수 — 반복마다 새 변수 C# 5.0

왜 — csharplang 의 언어 버전 기록은 C# 5 의 셋째 항목으로 적습니다: "foreach loop was changed to generates a new loop variable rather than closing over the same variable every time". 표준의 주석도 "earlier versions of C# declared v outside of the while loop" 라고 밝힙니다.

람다 셋이 각자 1, 2, 3 을 기억합니다. 표준: foreach 의 반복 변수는 수명이 반복 한 번이고 "Each iteration creates a new variable".

실행 검증

게이트가 없다 — C# 4·3 으로 내려도 1 2 3

이 변화는 문법이 아니라 의미의 변화입니다. 지금의 컴파일러는 언어 버전을 보지 않고 늘 새 규칙으로 번역합니다.

그래서 옛 동작은 풀어 써서 보인다 — -langversion 으로 옛 출력이 돌아오지 않으므로(0부의 꼴 (나)가 안 되는 경우), 다음 장은 표준이 적은 두 번역을 손으로 써서 나란히 돌립니다. "옛 컴파일러의 출력" 이 아니라 "옛 규칙대로 풀어 쓴 코드의 출력" 입니다.
실행 검증

풀어 쓴 두 꼴 — 변수가 while 밖이냐 안이냐

표준은 foreach (V v in x) 를 열거자와 while (e.MoveNext()) 로 풀어 적고, "The placement of v inside the while loop is important for how it is captured" 라고 덧붙입니다.

변수가 밖에 있으면 람다 셋이 한 변수를 나눠 갖고, 부를 때의 값 — 마지막 원소 3 — 을 봅니다. 안에 있으면 반복마다 새 변수가 생깁니다. 바뀐 것은 선언 한 줄의 자리뿐입니다.

실행 검증

컴파일러가 만드는 것 — 반복마다 클로저 객체 하나

포착된 지역 변수는 컴파일러가 만든 클래스의 필드가 되고, 람다는 그 객체를 Target 으로 가진 대리자가 됩니다 (4부). 대리자 셋이 가리키는 객체가 몇 개인지 셉니다.

foreach 는 반복마다 클로저 객체를 새로 만들고(셋), for 는 루프 밖에서 하나를 만들어 셋이 나눠 씁니다. 클래스 이름은 Roslyn 이 붙인 것이라 표준이 정하지 않습니다. 반복마다 객체가 생기는 것은 포착이 있을 때만이고, 포착이 없으면 차이가 보이지 않습니다 .

실행 검증

늦은 실행과 만나면 — 거르개가 마지막 글자만 본다

LINQ 의 Where 는 람다를 바로 돌리지 않고 결과를 꺼낼 때 돌립니다(4부). 루프에서 거르개를 쌓으면 람다는 루프가 끝난 뒤에 반복 변수를 읽습니다.

함정 — 변수가 하나면 두 거르개가 모두 마지막 값 'o' 를 보아 l 이 남습니다. 루프 안에서 char copy = c; 로 복사하는 관용구가 이 함정을 피하는 길이었습니다. C# 5 부터 foreach 에서는 필요 없고, for 에서는 지금도 필요합니다(다음 장).
실행 검증

C# 5 의 두 변화가 만나는 곳 — await 가 있는 foreach

루프 몸체에 await 가 있으면 메서드는 반복마다 멈췄다가 이어 달립니다. 지역 변수는 상태 기계의 필드로 옮겨지는데 (4장), 포착된 반복 변수는 그래도 반복마다 새 변수일까요?

람다 셋이 1·2·3 을 따로 보고, 클로저 객체도 셋입니다. 메서드가 반복마다 멈췄다 이어 달려도 컴파일러는 반복마다 클로저 객체를 새로 만듭니다. 같은 버전에 들어온 두 변화(async 와 foreach)가 서로를 깨지 않습니다.

실행 검증

for 루프는 바뀌지 않았다

표준: "If a for-loop declares an iteration variable, that variable itself is considered to be declared outside of the loop." C# 5 의 변화는 foreach 에만 해당합니다.

i 는 하나뿐이라 셋 다 루프를 빠져나온 값 3 을 봅니다. 몸체 안에 선언한 copy·inner 는 반복마다 새 변수입니다. 셋째 줄은 둘이 섞인 경우입니다 — inner 는 0·10·20 을 따로 기억하고, 밖의 n 은 모두 3 입니다.

실행 검증

뒤 버전의 foreach — 분해도 새 변수, ref 는 포착 불가

C# 7 의 분해 foreach 는 반복마다 변수 여럿을 새로 선언합니다. C# 7.3 의 ref 반복 변수는 원소 자체의 별칭입니다.

ref 지역 변수는 람다가 포착할 수 없으므로(CS8175), "반복마다 새 변수" 의 문제가 ref foreach 에는 처음부터 생기지 않습니다.

문서의 분류로 보면 같은 소스의 뜻이 달라진 변화입니다 — C# 문서의 "Version and update considerations" 는 언어 문법에서 소스 호환을 깨는 변경이 곧 "behavioral change" 라고 적습니다. 컴파일러는 경고하지 않으므로, 마지막 값을 보던 옛 코드는 조용히 다른 값을 봅니다.

7장 퀴즈 — foreach 변수 포착

Q. for (int i = 0; i < 3; i++) tasks.Add(Task.Run(() => Work(i))); 를 foreach 로 바꾸면 고쳐집니까? foreach (int i in Enumerable.Range(0, 3)) tasks.Add(Task.Run(() => Work(i)));

A. 고쳐집니다(C# 5 이후). foreach 의 i 는 반복마다 새 변수라 각 람다가 0·1·2 를 따로 봅니다. for 판에서는 하나의 i 를 나눠 써서, 작업이 시작될 때의 i 를 읽게 됩니다(for 는 그대로). for 를 그대로 두려면 int copy = i; 를 몸체에 두면 됩니다.

async 람다의 유추된 반환 형식 — T 는 Task<int>

같은 42 인데 async 하나로 T 가 Int32 에서 Task<Int32> 로 바뀝니다. C# 4 로 내리면 람다의 async 마다, 그리고 람다 안의 await 마다 거절이 나옵니다 — async 메서드에서는 async 줄 하나만 거절됐던 것(1장)과 다릅니다.

short 를 돌려주는 람다는 어느 쪽에도 정확히 맞지 않아, int 가 double 보다 나은 변환 대상이라는 규칙으로 N(Func<Task<int>>) 가 골라졌습니다. 값을 돌려주지 않는 async 람다는 제네릭 아닌 Task 쪽에 맞습니다. Action 과 겨룰 때의 함정은 5장에서 보았습니다.

C# 6 — catch 안에서 await 한 뒤 다시 던지기

C# 5 의 제약과 C# 6 의 해제는 3장에서 보았습니다. 여기서는 더 들어가, 같은 C# 6 의 예외 필터와 섞고 await 뒤에 throw; 로 다시 던집니다.

메서드가 catch 안에서 멈췄다가 이어 달린 뒤에도 throw; 가 잡았던 예외를 다시 던져, Main 이 같은 메시지를 받습니다. finally 의 await 도 그 전에 끝납니다. C# 5 로 내리면 세 줄이 거절되는데, 필터는 게이트 문장이고 await 둘은 옛 오류 번호입니다.

C# 7.1 — async Main 의 진짜 진입점

"What's new in C# 7.1": async Main 이 없을 때는 DoAsyncWork().GetAwaiter().GetResult() 를 직접 써야 했다.

어셈블리의 진입점은 우리가 쓴 Main 이 아니라 컴파일러가 더한 <Main> 이고, int 를 돌려줍니다. 제안서는 그 메서드가 Main(args).GetAwaiter().GetResult() 와 같은 일을 한다고 적습니다 — 7.1 이전의 손 코드를 컴파일러가 대신 씁니다. Task 의 결과 2 가 프로세스의 종료 코드가 됐습니다.

제안서: 지금까지 빌더는 반환 형식에 묶여 있었다 — async ValueTask<T> 는 언제나 AsyncValueTaskMethodBuilder<T>. "We need a way to have an individual async method opt-in to a specific builder."

C# 8 — 비동기 스트림과 await foreach

제안서: C# 에는 반복기도 async 메서드도 있지만 "no support for a method that is both an iterator and an async method". C# 8 은 IAsyncEnumerable<T> 를 돌려주는 async 반복기와 그것을 도는 await foreach 를 더했습니다.

만드는 쪽과 쓰는 쪽이 한 원소씩 번갈아 돕니다 — C# 2 의 반복기(3부)처럼 늦게 돌고, 원소 사이에서 await 할 수 있습니다. 거절은 선언(async IAsyncEnumerable)과 사용(await foreach) 두 자리에서 나옵니다.

실행 검증

비동기 반복기가 만드는 것 — 인터페이스 여섯을 한 클래스에

async 메서드는 상태 기계를(4장), 반복기는 열거자 클래스를 만듭니다. 둘을 합친 비동기 반복기는 무엇을 만드는지 런타임에 물어봅니다.

열거 가능, 열거자, 비동기 Dispose, 상태 기계, 그리고 MoveNextAsync 의 ValueTask<bool> 를 받쳐 줄 IValueTaskSource 까지 한 객체입니다. 처음 GetAsyncEnumerator 를 부르면 같은 객체가 열거자로 돌아옵니다 — 객체 하나를 아끼는 Roslyn 의 구현이고, 클래스 이름처럼 표준이 정한 것은 아닙니다.

일찍 빠져나오면 — await foreach 가 DisposeAsync 를 기다린다

표준은 await foreach 를 풀어 쓰면서 finally 에 await e.DisposeAsync(); 를 둡니다. 반복기 쪽에서는 그 호출이 finally 블록을 돌립니다.

break 뒤 "after the loop" 보다 반복기의 finally 가 먼저 찍힙니다. 그 finally 안의 await 는 C# 6 에서 풀린 제약(앞) 덕입니다 — 버전 셋(5·6·8)의 기능이 한 장에서 맞물립니다.

비동기 스트림의 취소 — [EnumeratorCancellation]

제안서는 취소를 넣는 다섯 방법을 견준 뒤, 반복기의 매개변수 하나에 특성을 붙이는 쪽을 골랐습니다. 남이 준 IAsyncEnumerable 에도 WithCancellation(token) 으로 토큰을 넣을 수 있게 하려는 것입니다.

Ticks() 를 부를 때는 토큰을 주지 않았지만, WithCancellation 의 토큰이 GetAsyncEnumerator 를 거쳐 특성 붙은 매개변수 ct 로 들어갔습니다. 특성이 없으면 반복기 몸체는 그 토큰을 볼 길이 없습니다.

비동기 스트림의 ConfigureAwait — 스트림을 감싸는 구조체

"What's new in C# 8.0": 스트림의 원소는 기본으로 포착한 문맥에서 처리되고, 그것을 끄려면 TaskAsyncEnumerableExtensions.ConfigureAwait 를 씁니다. 제안서도 ConfigureAwait 를 따로 다룹니다.

둘 다 스트림을 바꾸지 않고 설정을 담은 구조체로 감쌉니다. 그 구조체는 IAsyncEnumerable<int> 가 아닌데도 await foreach 가 돕니다 — 표준의 비동기 foreach 는 GetAsyncEnumerator 를 이름으로 찾기 때문입니다 . 인터페이스가 아니라 이름으로 찾는 것은 C# 5 의 awaitable 패턴(4장)과 같은 방식입니다.

C# 9 — 확장 메서드 GetAsyncEnumerator

제안서: foreach 가 패턴을 만족하는 확장 GetEnumerator 도 알아보게 하자 — "This will bring foreach inline with how other features in C# are implemented, including async". await 가 확장 GetAwaiter 를 받아 온 것(4장)과 같은 일을 foreach 에도 한 것입니다.

확장 메서드 자체도 비동기 반복기입니다 — IAsyncEnumerator<int> 를 돌려주는 async 메서드 안에서 배열을 await 한 뒤 하나씩 yield return 합니다.

선언 꼴의 b 는 "end of Main" 뒤, 메서드를 빠져나갈 때 닫힙니다. C# 5 의 using 블록 안에서도 await 는 됐지만 Dispose 자체는 기다릴 수 없었습니다(3장). C# 7.3 으로 내리면 'asynchronous using', 'using declarations' 에 더해 'pattern-based disposal' 까지 거절됩니다.

C# 13 — async 안의 Span 지역 변수, 단 await 를 건너지 않게

"What's new in C# 13": 그 전에는 async 메서드가 ref 지역 변수를 선언할 수 없었다. C# 13 부터는 되지만 "those variables can't be accessed across an await boundary".

await 를 건너면 Span 이 상태 기계의 필드가 되어야 하는데(4장), 힙에 놓일 수 없는 ref struct 는 필드가 될 수 없습니다. C# 5 의 "async 에는 ref 매개변수가 없다"(3장)와 같은 뿌리입니다.

9장 퀴즈 — 비동기의 그 뒤

Q. await foreach (var x in Numbers()) { if (x == 2) break; } 에서 Numbers 는 try/finally 를 가진 비동기 반복기입니다. break 뒤에 반복기의 finally 는 돕니까? 돈다면 누가 부릅니까?

A. 돕니다. await foreach 를 풀어 쓴 finally 가 await e.DisposeAsync() 를 부르고, 그 호출이 반복기의 finally 를 돌립니다(일찍 빠져나오기). 그 finally 안에서 await 할 수 있는 것은 C# 6 부터입니다.

6부 퀴즈 1 — 컴파일러가 거절하는 것

Q. C# 5 판 프로그램을 -langversion:4 로 컴파일하면 async 두 줄만 거절됩니다. 그러면 [CallerMemberName] 과 foreach 의 변화는 "C# 4 에서도 됐다" 고 말해도 됩니까?

A. 안 됩니다. 둘 다 게이트가 없을 뿐입니다. 지금의 컴파일러는 언어 버전과 상관없이 특성을 알아보고 foreach 를 새 규칙으로 번역하므로 -langversion 으로 옛 동작을 흉내 내지 못합니다. 문서는 둘을 C# 5 의 변화로 적습니다 (1장).

6부 퀴즈 2 — 어디서 이어 달리나

Q. C# 5 판의 Total 안 26행 Log("sizes …") 는 await Task.WhenAll 뒤에 있습니다. 이 줄의 [CallerMemberName] 은 Total 을 줍니까, 상태 기계의 MoveNext 를 줍니까? 이 줄은 어느 스레드에서 돕니까?

A. Total 입니다. 값은 소스의 자리로 정해지는 상수라 몸체가 MoveNext 로 옮겨져도 바뀌지 않습니다 (6장). 스레드는 정해지지 않습니다. 콘솔 프로그램에는 동기화 문맥이 없어 이어 달리기가 Main 이 아닌 스레드에서 곧바로 돌기 때문입니다(4장). 그래서 이 덱의 예제는 스레드 번호를 찍지 않습니다.
