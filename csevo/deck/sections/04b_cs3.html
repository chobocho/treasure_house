쿼리 식 — 언어 안으로 들어온 질의

from · where · select · orderby · let · group · join · into — 그리고 그것이 번역되는 메서드 호출

쿼리 식 이전 — 거르고, 정렬하고, 바꾸기

버전 기록은 C# 3.0 의 중심을 이렇게 적습니다: "This C# version's killer feature was the query expression, also known as Language-Integrated Query (LINQ)." 그 전에는 같은 일을 이렇게 했습니다.

하고 싶은 말은 "걸러서, 길이로 정렬해, 대문자로" 한 줄인데, 중간 리스트와 비교 메서드가 그 사이를 채웁니다. 다음 장이 같은 일을 쿼리 식으로 씁니다.

실행 검증

쿼리 식 (query expression) C# 3.0

표준: 쿼리 식은 "a language-integrated syntax for queries that is similar to relational and hierarchical query languages such as SQL and XQuery" 입니다. 컴파일러는 이 문법을 C# 3 의 기능으로 확인합니다.

이 예제는 일부러 var 를 쓰지 않았습니다. 한 예제에 C# 3 기능을 하나만 두어야 거절도 하나로 모입니다. 번역된 쿼리 안에는 람다가 셋 생기지만(번역은 조금 뒤에 봅니다) 거절은 'query expression' 하나뿐입니다 — 그 람다들은 소스에 쓰인 람다가 아닙니다.

실행 검증

절(clause) 여덟 가지

표준의 문법: 쿼리 식은 from 으로 시작해 select 나 group 으로 끝납니다. 그 사이에 from·let·where·join·orderby 가 몇 개든 올 수 있고, 끝에 into 로 다음 쿼리를 이어 붙일 수 있습니다.

절하는 일 (표준의 설명)이 장

let y = f앞의 범위 변수로 계산한 값을 새 범위 변수로let
where b조건에 맞지 않는 항목을 거른다번역
join … on … equals …두 시퀀스의 키를 견주어 짝을 낸다join

문서 근거

쿼리의 낱말은 문맥 키워드

표준: from·where·select·group·into 같은 열세 낱말은 문맥 키워드(contextual keyword)입니다. 쿼리 식 밖에서는 보통 이름입니다.

키워드를 늘리면서도 그 낱말을 이름으로 쓴 옛 코드를 깨지 않는 방법입니다. C# 2 의 yield 가 같은 길을 먼저 갔습니다(3부).

실행 검증

함정 — 쿼리 안에서는 그 이름이 키워드가 된다

표준: 이 낱말들은 쿼리 식 안에서는 어디서든 키워드이고, 이름으로 쓰려면 @ 를 붙입니다.

진단이 셋이지만 원인은 하나입니다. 컴파일러는 in 뒤의 into 를 이어 쓰기 절의 시작으로 읽고, 그 앞에 select 가 없다고 봅니다.

실행 검증

쿼리 식은 메서드 호출로 번역된다

표준: "The C# language does not specify the execution semantics of query expressions. Rather, query expressions are translated into invocations of methods" — Where·Select·SelectMany·Join·GroupJoin·OrderBy·OrderByDescending·ThenBy·ThenByDescending·GroupBy·Cast 열한 이름입니다.

증거의 꼴 — 컴파일러가 실제로 무엇을 만들었는지는 이 출력만으로 보이지 않습니다. 그래서 이 장은 표준의 번역 규칙을 손으로 풀어 쓴 코드와 나란히 돌려 결과가 같음을 보입니다(0부의 꼴 (나)). 번역이 실제로 어떤 메서드를 부르는지는 조금 뒤에 호출을 찍어 확인합니다.
실행 검증

번역은 형식을 보기 전에 — 그래서 오류도 메서드 이름으로

표준: 번역은 "a syntactic mapping that occurs before any type binding or overload resolution has been performed" 입니다. 번역된 호출을 보통 호출처럼 처리하다가 오류가 드러납니다.

오류가 "쿼리를 지원하지 않는 형식" 이 아니라 "'Select' not found", "'Where' not found" 입니다. 컴파일러는 형식이 쿼리 가능한지 따로 묻지 않고, 번역한 호출을 해 보고 실패를 알릴 뿐입니다.

실행 검증

쿼리 식 패턴 — 이름만 맞으면 된다 C# 3.0

표준은 쿼리 식이 기대하는 메서드의 모양을 "query-expression pattern" 으로 정합니다. 인터페이스가 아니라 모양입니다 — 인스턴스 메서드든 확장 메서드든, 대리자를 받든 식 트리를 받든 됩니다.

Box 는 IEnumerable 도 아니고 원소도 하나뿐입니다. 대리자도 직접 선언한 Fn 입니다. 그래도 Where·Select 라는 이름과 알맞은 모양이 있으니 쿼리 식이 됩니다.

실행 검증

호출을 찍는 쿼리 형식 Q<T>

번역이 실제로 어떤 메서드를 부르는지 보려고, 패턴의 메서드마다 자기 이름을 찍고 일은 System.Linq 에 넘기는 형식을 만듭니다. 인스턴스 메서드라 같은 이름의 확장 메서드보다 먼저 골라집니다.

Join·GroupJoin·Cast·ThenBy·OrderByDescending 는 넣지 않았습니다. 다음 장의 쿼리들이 그 이름을 부르지 않기 때문입니다. 패턴은 쓰는 만큼만 있으면 됩니다 (앞에서).

실행 검증

쿼리 여덟 개, 호출된 메서드 여덟 줄

  • 1 — select x 뿐인 쿼리도 Select 를 부릅니다(다음 장).
  • 2 — where 뒤의 select x 는 사라집니다. 표준 12.22.3.6 의 규칙입니다.
  • 4 — orderby a, b descending 은 OrderBy 다음 ThenByDescending.
  • 5 — let 은 Select 하나가 됩니다(let).
  • 7·8 — group x by k 는 인수 하나, group v by k 는 인수 둘인 GroupBy.

쿼리를 만드는 순간에 메서드들이 불립니다. 원소를 꺼내는 일은 아직 하나도 하지 않았습니다 — 그것은 7장의 이야기입니다.

실행 검증

select x 뿐인 쿼리는 왜 Select 를 부르나

표준: from x in e select x 는 e.Select(x => x) 로 번역됩니다. 이유도 적혀 있습니다 — 쿼리의 결과가 원본 객체 자체이면 "might inadvertently expose private data (e.g., an element array) to a caller".

표준은 나머지를 라이브러리에 맡깁니다: Select 를 구현하는 쪽이 원본 객체를 그대로 돌려주지 않아야 한다. .NET 10 의 Enumerable.Select 가 돌려준 것은 int[] 로 캐스트되지 않았습니다.

실행 검증

인스턴스 메서드가 먼저, 그리고 정적 형식이 정한다

번역된 x.Where(…) 는 보통 메서드 호출이라, 보통의 규칙대로 인스턴스 메서드를 먼저 찾고 없을 때만 확장 메서드를 봅니다.

같은 객체라도 IEnumerable<string> 형식의 변수로 쿼리하면 Enumerable.Where 가 불립니다. 메서드 고르기는 실행 중의 형식이 아니라 컴파일 시간의 형식으로 정해집니다.

실행 검증

시퀀스가 아니어도 — SelectMany 만 가진 Maybe

표준의 주석: 번역이 문법의 대응이라 "types have considerable flexibility in how they implement any or all of the query-expression pattern" 이고, 패턴의 일부만 구현한 형식은 그 부분에 해당하는 쿼리만 지원합니다.

from a in … from b in … select … 는 표준 12.22.3.5 대로 결과 선택자가 있는 SelectMany 하나로 번역됩니다. 그래서 Maybe 에는 Select 조차 없어도 됩니다.

실행 검증

orderby — 쉼표 하나와 orderby 두 번은 다르다

표준: orderby k1, k2 는 OrderBy(k1) 다음 ThenBy(k2) 이고, descending 이 붙은 기준은 …Descending 이 됩니다. ascending 은 적어도 안 적어도 같습니다.

  • 첫 줄 — 성으로, 같은 성 안에서는 이름의 역순입니다.
  • 둘째 줄 — orderby 를 두 번 쓰면 두 번째 OrderBy 가 처음부터 다시 정렬합니다. 이름이 첫 기준이 됩니다.
  • 둘째와 셋째의 차이는 Ann 둘의 차례뿐입니다. 이 런타임의 OrderBy 는 같은 키의 원래 차례를 지키므로(7장), 앞의 성 정렬이 동점 처리로만 살아남았습니다.
실행 검증

함정 — 비교할 수 없는 키는 실행 중에야 터진다

번역된 OrderBy(b => b) 는 키 형식에 아무 제약이 없어 컴파일됩니다. 비교는 정렬이 실제로 돌 때 합니다.

예외는 쿼리를 만든 줄이 아니라 string.Join 이 쿼리를 열거한 줄에서 납니다. 비교할 수 있는 속성(b.W)을 키로 주면 됩니다.

실행 검증

let 과 투명 식별자 C# 3.0

표준: from x in e let y = f 는 e.Select(x => new { x, y = f }) 로 번역되고, 뒤의 절은 그 익명 객체를 받는 "transparent identifier"(표준의 표기로는 *)를 통해 x·y 를 봅니다. 표준은 익명 형식 대신 다른 방법을 써도 된다고 열어 둡니다.

where n > 3 의 람다가 받은 것은 낱말이 아니라 { w = …, n = … } — 익명 형식의 객체입니다. 투명 식별자는 소스에서 이름을 부를 수 없지만, 그 값은 이렇게 패턴 메서드 쪽에서 보입니다. 이 모양은 Roslyn 의 선택입니다.

실행 검증

let 은 원소마다 한 번만 계산한다

같은 식을 where 와 select 에 두 번 쓰면 원소마다 두 번 계산합니다. let 으로 받아 두면 앞 장의 익명 객체에 값이 담겨 한 번으로 끝납니다.

낱말 넷 모두 where 에서 한 번씩, 통과한 둘이 select 에서 한 번 더 — 6 번. let 을 쓰면 넷입니다.

실행 검증

from 두 개는 SelectMany

표준: 둘째 from 과 select 는 e1.SelectMany(x1 => e2, (x1, x2) => v) 로 번역됩니다. 둘째 원천 e2 가 첫 범위 변수를 써도 됩니다.

실행 검증

함정 — select 는 펴 주지 않는다

원소마다 배열을 만드는 select 는 "배열의 시퀀스" 를 냅니다. 원소들을 한 줄로 펴려면 from 을 하나 더 씁니다 — 곧 SelectMany 입니다.

System.String[] 두 줄은 배열의 ToString() 입니다. 컴파일 오류도 경고도 없이 엉뚱한 출력이 납니다.

실행 검증

범위 변수의 이름은 겹칠 수 없다

범위 변수는 람다의 매개변수로 번역되므로, 둘레의 지역 변수나 앞의 범위 변수와 이름이 같으면 안 됩니다.

진단이 "range variable" 이라는 낱말을 씁니다. 컴파일러는 범위 변수를 번역 뒤의 람다 매개변수가 아니라 쿼리의 개념으로 다룹니다.

실행 검증

group … by 와 IGrouping C# 3.0

표준: group v by k 는 GroupBy(x => k, x => v), v 가 범위 변수 자체면 GroupBy(x => k) 입니다. 결과는 "a sequence of sequences, where each inner sequence has an additional Key property" 라는 모양을 권합니다.

묶음의 차례는 키가 처음 나온 차례(b, a, c)이고, 묶음 안의 원소는 원래 차례입니다. 이 출력은 .NET 10 의 Enumerable.GroupBy 가 낸 것이고, 표준이 정하는 것은 번역까지입니다.

실행 검증

여러 칸으로 묶기 — 익명 형식이 키가 된다

키가 둘 이상이면 익명 형식으로 묶습니다. 익명 형식은 속성 값으로 같음을 판단하므로(2장) 같은 지역·같은 분기가 한 묶음이 됩니다.

Key 클래스는 Equals 를 재정의하지 않아 참조로 비교합니다. 원소 넷이 네 묶음이 됩니다. 키의 ToString() 이 { Region = N, Q = 1 } 로 찍히는 것도 익명 형식이 컴파일러가 만든 클래스라서입니다.

실행 검증

into — 쿼리 뒤에 쿼리를 잇는다

표준: from x1 in e1 b1 into x2 b2 는 from x2 in (from x1 in e1 b1) b2 로 번역됩니다. group 이나 select 로 끝난 쿼리를 다시 거르고 정렬할 때 씁니다.

실행 검증

쿼리는 select 나 group 으로 끝나야 한다

표준의 문법에서 쿼리 몸통은 반드시 select_or_group_clause 로 끝납니다. SQL 처럼 거르기만 하고 멈출 수 없습니다.

거르기만 하는 쿼리라도 select x 를 적습니다. 적어도 비용은 없습니다 — where 뒤의 select x 는 번역에서 사라집니다(쿼리 2).

실행 검증

join … on … equals C# 3.0

표준: join x2 in e2 on k1 equals k2 와 select v 는 e1.Join(e2, x1 => k1, x2 => k2, (x1, x2) => v) 로 번역됩니다. 키가 같은 짝만 나오는 안쪽 조인(inner join)입니다.

Lee 와 cup 은 짝이 없어 빠집니다. 결과는 바깥(고객) 차례이고, 한 고객 안에서는 주문의 원래 차례입니다 — 이 차례는 .NET 10 의 Enumerable.Join 이 낸 것입니다.

실행 검증

함정 — equals 의 왼쪽은 바깥, == 는 안 된다

equals 가 연산자가 아닌 이유는 번역에 있습니다. 왼쪽 식은 x1 => k1, 오른쪽 식은 x2 => k2 라는 서로 다른 람다가 되므로, 양쪽이 각자 자기 범위 변수만 볼 수 있습니다.

실행 검증

함정 — 여러 칸으로 join 할 때 속성 이름이 다르면

키가 둘 이상이면 양쪽에 익명 형식을 만듭니다. 그런데 두 익명 형식은 속성의 이름·형식·차례가 모두 같아야 같은 형식입니다 (2장). 이름이 Store 와 Shop 으로 다르면 키의 형식이 달라집니다.

진단은 "어느 이름이 다르다" 가 아니라 형식 유추의 실패를 말합니다. 번역된 Join<…, TKey, …> 의 TKey 를 두 키 선택자에서 하나로 정할 수 없기 때문입니다.

실행 검증

고치기 — 한쪽에 이름을 붙여 맞춘다

익명 형식의 속성 이름은 투영한 멤버의 이름을 따르므로(2장) 이름이 다른 쪽에만 Shop = 을 붙였습니다. 결과의 차례는 바깥(주문)의 차례입니다.

실행 검증

join … into — 짝을 묶음으로, 그리고 바깥 조인

표준: join … into g 와 select v 는 GroupJoin(e2, x1 => k1, x2 => k2, (x1, g) => v) 로 번역됩니다. 바깥 원소마다 짝의 묶음 하나 — 짝이 없으면 빈 묶음입니다.

C# 에는 left join 이라는 낱말이 없습니다. into 로 묶은 뒤 from o in os.DefaultIfEmpty() 로 다시 펴면, 빈 묶음이 null 하나가 되어 왼쪽 원소가 살아남습니다.

실행 검증

범위 변수에 형식을 적으면 Cast C# 3.0

표준: from T x in e 는 from x in (e).Cast<T>() 로 번역됩니다. 표준의 주석은 쓰임새도 적습니다 — 제네릭이 아닌 IEnumerable 만 구현한 컬렉션, 예를 들어 ArrayList.

string 이라고 적은 것은 검사가 아니라 약속입니다. 지킬 수 없는 원소가 들어오면 C# 1 의 foreach 와 같은 InvalidCastException 이 납니다(3부).

실행 검증

범위 변수는 읽기 전용

표준: 쿼리 식 안에서 범위 변수에 대입하거나 ref·out 인수로 넘기면 컴파일 오류입니다.

번역 뒤의 x 는 람다의 매개변수일 뿐이지만, 이 금지는 번역 전의 쿼리에 걸린 규칙입니다. 그래서 진단도 "Range variable" 이라는 쿼리의 말로 나옵니다.

실행 검증

키워드가 없는 연산자는 메서드로 잇는다

쿼리 식의 낱말은 표준이 정한 열한 메서드에만 대응합니다. Count·Distinct·Take·First 같은 나머지는 쿼리를 괄호로 싸고 메서드로 부릅니다.

한 식에 두 문법이 섞이는 것이 C# 3 의 LINQ 코드에서 흔한 모양입니다. 둘이 같은 메서드 호출이라 섞어도 아무것도 바뀌지 않습니다.

쿼리는 값이다 — 조건에 따라 이어 붙이기

쿼리 식의 결과는 IEnumerable<T> 값이라 변수에 담아 두었다가 다음 쿼리의 원천으로 쓸 수 있습니다. 조건에 따라 거르기·정렬을 붙였다 뗐다 하는 검색 코드가 이렇게 짜입니다.

붙인 단계는 아직 하나도 돌지 않았습니다. Search 가 돌려준 것은 "어떻게 거를지" 의 설명이고, 실제로 거르는 것은 string.Join 이 열거할 때입니다(7장).

뒤 버전과의 맞물림 — 쿼리 절 안의 out 변수

C# 7 의 out int v 같은 선언 식은 처음에는 쿼리 절 안에서 쓸 수 없었고, C# 7.3 에서 허용됩니다.

v 의 범위는 그 절의 람다 안뿐이라 select 에서는 보이지 않습니다. 그래서 값을 let n 으로 받아 넘깁니다. 이 기능은 8부(C# 7.x)에서 다룹니다.

LINQ to Objects 와 늦은 실행

쿼리 식이 부르는 쪽 — System.Linq.Enumerable · 늦은 실행과 즉시 실행 · 다시 돌기 · 잡힌 변수 · 연산자의 함정

LINQ to Objects — 쿼리 식이 부르는 쪽 C# 3.0

표준의 주석: "The System.Linq namespace provides an implementation of the query-expression pattern for any type that implements the System.Collections.Generic.IEnumerable<T> interface." 그 구현이 Enumerable 정적 클래스의 확장 메서드들입니다.

이 숫자는 .NET 10 의 것입니다. C# 3 과 함께 온 처음의 Enumerable 이 몇 개였는지는 이 기계로 보일 수 없어 적지 않습니다. 쿼리 식이 쓰는 이름은 아래 열한 개뿐이고, 나머지는 메서드로 부릅니다(6장). Enumerable 이 어느 어셈블리에 사는지는 1장에서 보았습니다.

실행 검증

반복기 + 확장 메서드 = LINQ to Objects

C# 2 의 반복기(3부)와 C# 3 의 확장 메서드를 합치면 Where·Select 를 직접 쓸 수 있습니다. System.Linq 를 빼면 쿼리 식은 이쪽으로 번역됩니다.

"MyLinq.Where" 가 "query built" 보다 뒤에 찍힙니다. 반복기 메서드의 본문은 부를 때가 아니라 처음 꺼낼 때 돌기 때문입니다(3부). Enumerable 의 연산자도 같은 원리로 늦게 돕니다 — 다음 장부터 그것을 봅니다.

실행 검증

늦은 실행 — Where 는 부를 때 돌지 않는다

Where 는 조건을 검사하지 않고 "검사할 방법" 을 담은 객체만 돌려줍니다. 검사는 foreach 가 원소를 하나씩 꺼낼 때마다 합니다.

"query built" 가 먼저이고, 검사와 받기가 한 원소씩 번갈아 나옵니다. 메서드 그룹 IsOdd 를 넘겼으니 람다가 없어도 같은 일이 벌어집니다 — 늦은 실행은 람다가 아니라 연산자의 성질입니다.

실행 검증

연산자마다 — 부를 때 몇 개, 첫 원소에서 몇 개

원천에서 원소를 꺼낼 때마다 수를 세는 반복기에 연산자를 하나씩 붙여 봅니다. "call" 은 연산자를 부른 직후, "first item" 은 결과에서 첫 원소를 꺼낸 직후의 수입니다.

  • call 이 0 인 것 — 늦게 도는 연산자입니다. 그 가운데 OrderBy·Reverse·GroupBy 는 첫 원소를 내기 전에 원천을 끝까지 읽습니다.
  • call 이 0 이 아닌 것 — 부르는 즉시 돕니다. ToList·Count 는 끝까지, First·Any 는 하나만, Contains(2) 는 찾을 때까지 읽습니다.
실행 검증

OrderBy 는 늦게 돌지만 한꺼번에 읽는다

정렬은 마지막 원소를 보기 전에는 무엇이 첫째인지 알 수 없습니다. 그래서 OrderBy 는 첫 원소를 달라는 순간 원천을 전부 읽어 둡니다.

끝없는 시퀀스에 OrderBy 를 붙이면 첫 원소조차 나오지 않습니다. 원천이 크면 메모리도 그만큼 씁니다. "늦은 실행" 이 곧 "한 원소씩" 은 아닙니다.

실행 검증

GroupBy 는 늦게, ToLookup 은 바로

쿼리 식의 group … by 는 GroupBy 로 번역됩니다(6장). 같은 묶음을 즉시 만들어 두는 짝이 ToLookup 입니다.

GroupBy 는 "built" 뒤, 첫 묶음을 꺼낼 때 원천을 다 읽습니다. ToLookup 은 부르는 줄에서 다 읽고, 그 뒤에는 키로 바로 찾을 수 있는 ILookup 을 줍니다. l[true] 로 찾을 때는 원천을 다시 읽지 않습니다.

실행 검증

Join 은 안쪽을 한 번에, 바깥은 하나씩

바깥 첫 원소를 꺼낸 다음 안쪽(inner)을 끝까지 읽고, 그 뒤로는 바깥만 하나씩 읽습니다. 안쪽을 키로 찾을 수 있게 모아 두는 것입니다. 그래서 join 의 두 원천 가운데 작은 쪽을 안쪽(join … in 쪽)에 두는 것이 메모리에 유리합니다.

실행 검증

함정 — 두 번 열거하면 원천도 두 번

쿼리는 결과가 아니라 결과를 만드는 방법입니다. Count() 와 Sum() 을 따로 부르면 쿼리가 두 번 처음부터 돕니다. 3부의 반복기 함정이 LINQ 에서 그대로 나옵니다.

원천이 파일이나 네트워크면 그것도 두 번 읽습니다. 여러 번 쓸 결과는 ToList()·ToArray() 로 한 번 받아 둡니다.

실행 검증

람다는 값이 아니라 변수를 잡는다

표준: 람다가 쓰는 바깥 지역 변수는 "captured" 되고, 그 수명은 람다가 살아 있는 동안 늘어납니다. 쿼리가 늦게 돌면 그 변수의 그때 값을 읽습니다.

같은 쿼리 객체가 두 번 다른 결과를 냅니다. 람다의 잡기 규칙은 4장의 이야기이고, 여기서는 늦은 실행과 만나 "언제 읽느냐" 가 문제가 됩니다.

실행 검증

쿼리는 원천을 복사하지 않는다

쿼리는 리스트의 참조를 들고 있다가 열거할 때 그 순간의 내용을 읽습니다. 그 순간을 고정하고 싶으면 ToArray()·ToList() 로 받아 둡니다.

실행 검증

함정 — for 변수를 잡은 쿼리를 루프 뒤에 돌리면

모음 다섯을 하나씩 빼는 Where 를 루프에서 이어 붙입니다. 4장의 함정이 늦은 실행과 만난 모양입니다. 람다 다섯이 잡은 것은 같은 변수 i 이고, 쿼리는 루프가 끝난 뒤에 돕니다. 그때 i 는 5 입니다.

루프 안에서 새 지역 변수(v)에 옮겨 담으면 회차마다 다른 변수가 생겨 의도대로 돕니다. for 의 변수는 C# 14 에서도 루프 전체에 하나뿐입니다(3부). foreach 의 변수는 C# 5 에서 회차마다 새 변수가 되도록 바뀌었습니다(6부).

실행 검증

OrderBy 는 같은 키의 차례를 지킨다

키가 0 과 1 뿐인 원소 스물을 원래 차례 번호와 함께 정렬합니다. 같은 키 안에서 번호가 그대로 이어지면 안정 정렬(stable sort)입니다.

OrderBy 의 결과는 0, 2, 4 … 로 원래 차례를 지킵니다. List<T>.Sort 는 같은 키의 차례를 섞었습니다. orderby 를 두 번 쓴 쿼리가 앞의 기준을 동점 처리로 남긴 것이 이 성질 덕분입니다. 이 덱은 그것을 문서로 확인하지 않았으므로 ".NET 10 이 이렇게 한다" 까지만 말합니다.

실행 검증

Distinct 는 Equals 로 고른다

처음 나온 차례로 남깁니다(3 1 2). 익명 형식은 값이 같으면 같은 원소라 둘이 되고(2장), Point 는 참조로 비교되어 셋이 그대로 남습니다. Distinct·GroupBy·Join·Union 은 모두 같은 같음 규칙을 씁니다.

실행 검증

Union·Intersect·Except 는 집합 연산

함정은 Except 입니다. "a 에서 b 를 뺀 것" 이 1 1 2 가 아니라 1 2 입니다 — 결과에서 중복까지 없어집니다. 원소를 그대로 두고 빼기만 하려면 a.Where(x => !b.Contains(x)) 를 씁니다.

실행 검증

Aggregate — 씨앗이 있느냐 없느냐

씨앗(seed)이 없는 Aggregate 는 첫 원소를 씨앗으로 씁니다. 원소가 없으면 시작할 값이 없어 InvalidOperationException 입니다. 빈 시퀀스가 올 수 있으면 씨앗을 줍니다.

함정 — 루프는 조용히 넘치고 Sum 은 던진다

C# 의 정수 덧셈은 checked 문맥이 아니면 넘쳐도 조용히 돌아갑니다(2부). Enumerable.Sum 은 다르게 행동합니다.

같은 합인데 루프는 음수가 되고 Sum() 은 OverflowException 을 던집니다. 손으로 쓴 루프를 Sum() 으로 바꾸면 예외가 새로 생길 수 있다는 뜻입니다. 넘칠 수 있으면 long 으로 더합니다.

빈 시퀀스 — Sum 은 0, Max 와 Average 는 예외

"없음" 을 나타낼 수 없는 int 의 Max·Average 는 던지고, int? 판은 null 을 돌려줍니다. C# 2 의 nullable 값 형식(3부)이 여기서 "값 없음" 의 답이 됩니다.

First · FirstOrDefault · Single

  • First 는 없으면 던지고, Single 은 없거나 둘 이상이면 던집니다.

람다 안의 10 / x 는 Select 를 부를 때가 아니라 원소를 꺼낼 때 계산됩니다. 그래서 0 으로 나누기도 그때 일어납니다.

스택 트레이스를 아래에서 위로 읽으면 Main 의 foreach 줄(14) → 런타임의 열거자 → 람다(컴파일러가 붙인 이름)의 순서입니다. 줄 11 은 람다 자신의 자리로만 나오고, Main 이 쿼리를 만든 순간은 트레이스에 없습니다. 쿼리를 다른 메서드로 넘긴 뒤 돌리면 예외가 난 곳과 원인이 멀어집니다.

Enumerable 은 인수 검사를 바로 한다

3부에서 반복기의 인수 검사가 늦게 터지는 것을 보았습니다. 같은 일을 Enumerable.Where 에 시켜 봅니다.

반복기로만 쓴 MyWhere 는 조용히 돌아오고, Enumerable.Where 는 부르는 줄에서 source 가 null 이라고 던집니다. 검사하는 바깥 메서드와 반복기를 나누는 3부의 고치기를 라이브러리가 하고 있는 것입니다.

실행 검증

함정 — 쿼리를 돌리며 원천을 고치면

쿼리를 foreach 로 도는 동안 원천 리스트에서 원소를 지웁니다. 쿼리 안쪽에서 List<T> 의 열거자가 돌고 있으므로, 그 열거자가 변경을 알아챕니다.

예외가 나기 전에 2 는 이미 지워졌습니다(after: 1 3 4). 반쯤 고쳐진 채 멈춘 것입니다. ToList() 로 지울 목록을 먼저 다 뽑아 두면 원천과 열거가 분리됩니다.

끝없는 시퀀스 — Take 와 Any 는 끝난다

3부의 끝없는 반복기에 연산자를 붙입니다. 한 원소씩 흐르는 연산자는 필요한 만큼만 꺼냅니다.

Count()·OrderBy·ToList() 처럼 끝까지 읽는 연산자(앞의 표)는 끝나지 않습니다. 이 예제는 그 줄을 주석으로만 남겼습니다.

쿼리 식의 from string s in … 은 Cast 로 번역됩니다(6장). 형식이 섞인 컬렉션이면 OfType 을 메서드로 불러야 합니다 — 쿼리 식에는 OfType 의 낱말이 없습니다.

실행 검증

함정 — Cast<long>() 은 변환이 아니다

long direct = xs[0]; 은 컴파일러가 넣는 int → long 변환입니다. Cast<long>() 은 원소를 object 로 보고 long 으로 꺼내려 하는데, 상자 안에 든 것은 int 라 실패합니다. 숫자 변환은 Select(x => (long)x) 로 씁니다.

키가 겹치면 ToDictionary 는 던지고, ToLookup 은 한 키에 여럿을 담습니다. 없는 키를 물으면 ToLookup 은 예외 대신 빈 시퀀스를 줍니다.

쿼리 문법에 없는 오버로드들

쿼리 식은 연산자마다 정해진 꼴 하나로만 번역됩니다(6장). 원소의 위치(index)를 받는 오버로드처럼 그 꼴에 없는 것은 메서드로 부릅니다.

실행 검증

문자열은 IEnumerable<char> 라 바로 쿼리됩니다. 사전은 KeyValuePair 의 시퀀스인데, 그 열거 차례는 기댈 것이 아니라서 이 예제는 사전을 찍기 전에 orderby 로 차례를 정했습니다.

실행 검증

함정 — 쿼리를 찍으면 형식 이름이 나온다

쿼리는 값의 목록이 아니라 열거자를 만드는 객체라, ToString() 은 그 객체의 형식 이름입니다. 이름에서 .NET 10 의 구현이 보입니다 — 원천이 배열인지 리스트인지에 따라, 그리고 Where 뒤에 Select 가 붙었는지에 따라 다른 클래스를 씁니다. 이름은 구현의 사정이라 버전마다 다를 수 있습니다.

7장 퀴즈 — 늦은 실행

Q. var q = list.Where(x => x > min); 다음에 min 을 바꾸고 list 에 원소를 더한 뒤 q.Count() 를 두 번 부릅니다. 두 결과는 어느 시점의 min 과 list 로 계산됩니까?

A. 둘 다 Count() 를 부른 그 순간의 값입니다. 람다는 변수를 잡고(잡기), 쿼리는 리스트의 참조만 들고 있으며(원천), Count() 를 부를 때마다 쿼리가 처음부터 다시 돕니다(두 번 열거).

식 트리 (expression tree) C# 3.0

표준: 식 트리는 "permits a lambda expression to be represented as a data structure instead of executable code" 입니다. 람다가 대리자 형식 D 로 바뀔 수 있으면 Expression<D> 로도 바뀝니다. 버전 기록은 식 트리를 람다·익명 형식과 함께 "the foundation upon which LINQ is constructed" 로 꼽습니다.

값은 표준이 말한 대로 둘 다 2 입니다. 차이는 메서드가 사는 곳입니다. del 의 메서드는 컴파일러가 어셈블리에 써 둔 <Main>b__0_0 이고, del2 의 메서드는 형식에 속하지 않은 DynamicMethod — 실행 중에 트리에서 지은 것입니다. 맛보기는 4장에서 보았습니다.

실행 검증

표준이 식 트리에 요구하는 것은 Compile 하나

표준이 Expression<TDelegate> 에 정한 API 는 Compile 메서드뿐이고, 나머지는 구현이 정합니다. 그래도 구현이 해 주리라 기대하는 일 둘을 주석으로 적었습니다.

  • "Enable code to inspect and respond to the structure of an expression tree" — 트리를 읽고 그 모양에 따라 행동하기 (마디 읽기, SQL 장난감).
  • "Enable expression trees to be created programmatically within user code" — 코드로 트리를 짓기 (손으로 짓기).

트리의 정확한 모양과 그것을 만드는 과정도 표준의 부록 B 가 꼽은 "구현이 정하는 것" 입니다. 그래서 이 장의 출력은 모두 .NET 10 의 System.Linq.Expressions 가 낸 것입니다.

문서 근거

마디(node)를 하나씩 — NodeType · Parameters · Body

트리의 뿌리는 Lambda 마디, 그 몸통은 GreaterThan, 왼쪽은 Parameter, 오른쪽은 Constant 입니다. 마지막 줄이 중요합니다. 몸통 안의 x 는 매개변수 목록의 x 와 같은 객체입니다 — 매개변수는 이름이 아니라 객체로 이어집니다(함정).

실행 검증

트리를 걸으며 찍기

마디는 자식 마디를 속성으로 가집니다. 이항 연산은 Left·Right, 람다는 Parameters·Body. 재귀 함수 하나로 트리 전체를 걸을 수 있습니다.

연산자 우선순위가 트리의 깊이가 되었습니다. a * 2 가 가장 깊고, > 가 뿌리 바로 아래입니다. 마디마다 형식(Int32·Boolean)이 붙어 있는 것도 보입니다 — 컴파일러가 형식을 다 정한 뒤에 지은 트리입니다.

실행 검증

컴파일러가 쓴 것은 트리가 아니라 팩토리 호출

람다를 식 트리로 바꾸면 컴파일러는 그 자리에 트리를 짓는 코드를 넣습니다. 메서드 Make 의 IL 에서 call 명령을 찾아 불리는 메서드를 찍어 봅니다.

Expression.Parameter → Constant → GreaterThan → Lambda — 안쪽부터 짓는 차례입니다. 그러니 Make() 를 부를 때마다 트리가 새로 지어집니다(뒤에서). 이 IL 읽기는 0x28 바이트를 순진하게 찾는 장난감이라 다른 메서드에는 맞지 않을 수 있습니다.

실행 검증

팩토리로 손수 짓기

앞 장에서 컴파일러가 부른 메서드를 직접 부르면 같은 트리가 나옵니다. 표준 주석이 기대한 "created programmatically" 입니다.

두 트리가 매개변수 이름만 빼고 같게 찍힙니다. 손으로 지은 트리도 Compile() 하면 대리자가 됩니다. 실행 중에 조건을 이어 붙여 거르기 조건을 만드는 코드가 이 방법을 씁니다.

실행 검증

같이 온 런타임 — System.Linq.Expressions C# 3.0

식 트리 변환은 언어의 일이지만, 트리를 이루는 형식들은 라이브러리에 있습니다. C# 3.0 은 그 라이브러리와 함께 왔고, 버전 기록은 언어 기능의 "full boat" 가 .NET Framework 3.5 와 함께 왔다고 적습니다.

Expression<TDelegate> → LambdaExpression → Expression 의 상속 사슬이고, 실제 객체는 Expression1`1 이라는 숨은 하위 클래스입니다. 마디 종류 수는 .NET 10 의 ExpressionType 값의 수이며, 처음의 수가 몇이었는지는 이 기계로 보일 수 없어 적지 않습니다.

실행 검증

Compile 은 부를 때마다 새 대리자를 짓는다

결과는 같지만 대리자는 서로 다른 객체이고, 대리자의 == 도 거짓입니다 — 둘은 서로 다른 DynamicMethod 를 가리킵니다(앞에서). 같은 트리를 여러 번 돌릴 거라면 Compile() 의 결과를 받아 두고 다시 씁니다. 트리 자신은 Compile 뒤에도 그대로입니다.

실행 검증

람다 대리자는 캐시되고, 식 트리는 매번 새로

아무것도 잡지 않은 람다의 대리자는 Roslyn 이 정적 필드에 받아 두고 다시 내줍니다(4장). 식 트리는 팩토리 호출이 그 자리에서 돌므로 평가할 때마다 새 트리입니다. 루프 안에서 식 트리를 만들면 그만큼 객체가 생깁니다.

실행 검증

함정 — 모양이 같아도 같은 트리가 아니다

글자로 찍으면 같지만 Equals 는 참조로 비교합니다. "이 조건은 이미 컴파일해 두었다" 를 트리 객체를 키로 기억하려 하면 매번 놓칩니다. 트리를 견주려면 마디를 걸으며 직접 비교해야 합니다.

실행 검증

트리에는 컴파일러가 넣은 것도 보인다

소스에 적지 않은 암시적 변환, 미리 계산한 상수, checked 문맥이 트리에서는 마디로 드러납니다. 대리자로 컴파일하면 IL 속에 묻히는 것들입니다.

  • int → long, 정수 나눗셈 뒤의 double 승격, 1 → int? 가 모두 Convert 마디입니다.
  • 60 * 60 은 트리에 3600 하나로 들어갑니다. 상수 식은 트리를 짓기 전에 계산됩니다.
  • 함정 — checked(x + 1) 는 찍으면 (x + 1) 이지만 마디 종류는 AddChecked 입니다. ToString() 만 보고 트리를 판단하면 안 됩니다.
실행 검증

C# 3 의 다른 조각도 마디가 된다 — 익명 형식과 초기화자

같은 버전의 익명 형식(2장)과 초기화자(3장)는 식이라서 식 트리에 들어갈 수 있습니다. 쿼리의 select new { … } 가 트리가 되려면 이것이 필요합니다.

세 가지가 각자의 마디 종류 New·MemberInit·ListInit 로 남습니다. 컬렉션 초기화자는 문법이 아니라 Add 호출의 목록으로 기록됩니다(3장). 익명 형식의 진짜 이름 <>f__AnonymousType0`2 도 보입니다.

실행 검증

식 트리가 될 수 없는 람다

표준: 람다를 식 트리로 바꾸는 변환은 늘 "존재" 하지만 구현이 정한 이유로 컴파일 시간에 실패할 수 있습니다. 흔한 이유로 블록 몸통, async(6부), 대입 연산자, out·ref 매개변수, 동적 바인딩(5부)을 꼽습니다. 식 트리로 바뀌는 것은 람다뿐입니다.

대리자로는 같은 람다가 문제없습니다(ok). d 는 void 를 돌려주는 호출이지만 식 하나라서 Expression<Action<string>> 이 됩니다. 진단의 차례가 줄 차례와 다른 것은 이 컴파일러가 그렇게 보고한 것입니다.

실행 검증

API 로는 문장도 짓는다 — C# 람다로는 못 쓴다

.NET 10 의 팩토리에는 Block·Assign·Loop·Break 같은 문장 마디도 있습니다. 앞 장에서 거절된 블록 몸통과 대입을 손으로는 지을 수 있습니다.

언어와 라이브러리가 따로 움직인 흔적입니다. 라이브러리는 문장까지 표현하지만, C# 컴파일러가 람다에서 지어 주는 트리는 여전히 식뿐입니다. 이 마디들이 언제 생겼는지는 이 덱의 문서에 없어 적지 않습니다.

실행 검증

뒤 버전의 문법은 대부분 트리에 못 들어간다 — C# 14 에서도

C# 3 뒤에 생긴 식 문법 일곱 가지를 -langversion:14.0 으로 식 트리에 넣어 봅니다.

줄 10 의 보간 문자열만 통과했습니다. 나머지는 기능마다 전용 진단 번호가 있고, xs[^1] 은 인덱서와 ^ 로 두 번 거절됩니다. 이 덱은 각 제약의 이유를 문서로 확인하지 못했으므로, 표준이 실패를 "implementation-defined reasons" 로 둔다는 것까지만 말합니다.

실행 검증

C# 14 에서 풀린 것 — 선택적 인수와 명명 인수

C# 14 의 제안: 식 트리 안의 호출이 선택적 매개변수의 인수를 빼거나 인수에 이름을 붙이면 오류였는데, 이것이 "unnecessary code and differences" 를 낳고, 새 오버로드에 선택적 매개변수가 붙으면 기존 호출이 깨질 수 있었습니다. 제안은 이 제약이 왜 생겼는지도 "unclear" 라고 적습니다.

C# 13 의 거절은 "Feature … is not available" 꼴이 아니라 옛 진단 CS0854·CS0853 그대로입니다. C# 14 의 트리에는 빠진 인수가 Scale(x, 10) 으로 채워져 들어갑니다. C# 14 는 15부에서 다루고, 같은 풀림을 명명 인수 쪽에서 다시 보는 실험은 5부에 있습니다.

실행 검증

C# 10 — 형식을 적지 않은 식 트리

C# 10 의 람다는 "자연 형식" 을 가집니다. 대상이 LambdaExpression 이나 제네릭이 아닌 Expression 이면, 람다의 자연 대리자 형식 D 로 Expression<D> 를 만듭니다.

C# 9 의 거절도 기능 이름을 대지 않고 "대리자 형식이 아니다"(CS1660) 라고 합니다. C# 9 까지는 대상 형식에 Expression<D> 의 D 를 적어야 했습니다. 람다의 자연 형식은 4장에서 보았습니다.

실행 검증

함정 — 잡힌 변수는 상수가 아니라 필드 접근 마디

표준의 구현 예: 지역 변수를 잡는 기법이 식 트리에도 쓰여, 트리에는 컴파일러가 만든 객체의 참조가 담기고 그 지역 변수는 "field accesses on these objects" 로 나타납니다.

limit 는 값 3 이 아니라 value(…DisplayClass0_0).limit — 상수로 담긴 클로저 객체의 필드를 읽는 마디입니다. 그래서 컴파일한 뒤에 limit 를 바꾸면 결과도 바뀝니다(7장과 같은 일). 트리를 읽는 쪽은 Constant 하나가 아니라 이 모양을 풀 줄 알아야 값을 얻습니다.

실행 검증

함정 — 트리 안의 대리자는 열어 볼 수 없다

같은 조건을 세 가지로 적습니다. 람다 안에 직접, 메서드 호출로, 미리 만든 Func 변수를 불러서.

셋째 트리에는 >= 가 없습니다. 남은 것은 "잡힌 변수 adult 를 부른다"(Invoke) 뿐입니다. 대리자는 이미 코드라서 트리로 되돌릴 수 없습니다. 트리를 다른 언어로 옮기는 쪽에서 보면 둘째·셋째는 속을 알 수 없는 호출입니다 (SQL 장난감의 "not supported").

실행 검증

함정 — 이름이 같아도 다른 매개변수

두 조건 x > 1 과 x < 5 를 AndAlso 로 이어 붙여 봅니다. 찍은 모양은 그럴듯합니다.

두 람다의 x 는 서로 다른 ParameterExpression 객체입니다(마디 읽기). b 의 몸통이 가리키는 x 는 새 람다의 매개변수 목록에 없어서 Compile 이 거절합니다. Invoke 로 b 를 통째로 부르면 돕니다. 매개변수를 바꿔 끼운 새 트리를 짓는 방법은 다음 장입니다.

실행 검증

트리는 고치지 않고 새로 짓는다 — ExpressionVisitor

마디의 속성은 읽기 전용입니다. 트리를 바꾸려면 마디를 걸으며 바꿀 곳만 새 마디로 바꾼 새 트리를 짓습니다. .NET 10 의 ExpressionVisitor 가 그 걷기를 해 줍니다.

원래 트리 e 는 그대로이고 e2 만 곱셈입니다. Visit 은 바뀐 자식이 없으면 원래 마디를 그대로 돌려주므로, 바뀐 길을 따라서만 새 마디가 생깁니다.

실행 검증

트리를 다른 언어로 — SQL 조각을 만드는 장난감

표준은 쿼리 식을 SQL 과 비슷한 문법이라 소개하고, 패턴의 메서드가 대리자 대신 식 트리를 받아도 된다고 적습니다. 식 트리를 받으면 메서드가 람다를 실행하지 않고 읽을 수 있습니다.

이 덱은 데이터베이스용 LINQ 공급자(provider)의 문서를 갖고 있지 않습니다. 그래서 원리만 이 장난감으로 보입니다.

실행 검증

장난감 돌리기 — 모르는 마디는 거절한다

&&·|| 는 AndAlso·OrElse 마디라 AND·OR 로 옮겨집니다. p.Name.StartsWith("K") 는 메서드 호출(Call) 마디라 번역기가 거절합니다. 실제 공급자도 옮길 수 없는 마디를 만나면 실패할 수밖에 없습니다 — 컴파일은 되는데 실행에서 터지는 LINQ 코드의 뿌리가 여기 있습니다.

실행 검증

IQueryable — 쿼리 식이 통째로 트리가 된다 C# 3.0

같은 쿼리 식을 배열과 AsQueryable() 에 씁니다. 번역은 같은 Where·Select 호출이지만 (6장), Queryable 의 메서드는 Expression<Func<…>> 를 받으므로 람다가 트리로 바뀝니다.

결과는 같습니다. 다른 것은 q.Expression — 쿼리 전체가 Where·Select 호출의 트리로 남아 있고, 람다 인수는 Quote 마디로 싸여 있습니다. 트리를 받는 쪽은 이 트리를 실행하든 다른 언어로 옮기든 (SQL 장난감) 고를 수 있습니다.

실행 검증

함정 — Func 를 넘기면 IQueryable 에서 빠져나온다

Func 변수는 식 트리로 바뀔 수 없어 Queryable.Where 가 맞지 않고, IQueryable<T> 도 IEnumerable<T> 이므로 Enumerable.Where 가 골라집니다. 결과는 같아도 그 뒤의 연산자는 모두 메모리에서 돕니다. 컴파일 오류도 경고도 없습니다. 람다를 바로 적으면 Queryable 쪽이 골라집니다.

실행 검증

Func 오버로드와 Expression 오버로드는 서로 우열이 없다

앞 장의 람다가 Queryable.Where 로 간 것은 첫 인수 IQueryable<T> 가 더 맞았기 때문입니다. 받는 쪽만 다르고 나머지가 같은 두 오버로드라면 어떨까요.

람다는 두 형식 모두로 바뀔 수 있고, 이 컴파일러는 어느 쪽도 낫다고 보지 않습니다. 대리자를 원하면 Func 변수에 담아 넘기고, 트리를 원하면 Expression 변수에 담아 넘겨야 합니다.

8장 퀴즈 — 식 트리

Q. int min = 3; Expression<Func<int, bool>> e = x => x > min; 의 트리에서 min 은 어떤 마디입니까? 그리고 e = x => { return x > min; }; 로 바꾸면 무슨 일이 생깁니까?

A. min 은 상수 3 이 아니라, 컴파일러가 만든 클로저 객체(Constant)의 필드를 읽는 MemberAccess 마디입니다(잡힌 변수). 블록 몸통으로 바꾸면 CS0834 로 컴파일이 거절됩니다 — 블록 몸통 람다는 식 트리가 될 수 없습니다(될 수 없는 람다).

4부 퀴즈 1 — 번역

Q. from p in people where p.Age >= 18 select p.Name 을 -langversion:2 로 컴파일하면 거절은 무엇에 대해 나옵니까? 번역된 호출 안에는 람다가 둘이나 있는데요.

A. 'query expression' 하나뿐입니다. 람다는 쿼리를 번역한 결과일 뿐 소스에 쓰인 람다가 아니라서, 람다 게이트에 걸리지 않습니다(6장).
설명용

4부 퀴즈 2 — 언제 도는가

Q. IQueryable<Person> src 에 대해 Func<Person, bool> adult = p => p.Age >= 18; 을 만들고 src.Where(adult).Count() 를 부릅니다. 거르기는 어디서, 언제 돕니까?

A. Func 는 식 트리로 바뀔 수 없어 Enumerable.Where 가 골라지므로(8장) 거르기는 메모리에서, Count() 가 원소를 꺼낼 때 돕니다(7장). 공급자가 읽을 트리에는 거르기가 들어가지 않습니다.
