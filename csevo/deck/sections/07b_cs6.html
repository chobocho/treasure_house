식 본문 멤버 — 한 줄짜리 멤버의 중괄호를 걷다

메서드 · 속성 · 인덱서 · 연산자 · C# 6 이 막은 자리 · 같은 IL · => 와 { get; } = 의 차이

식 본문 메서드 (expression-bodied method) C# 6.0

왜 — C# 6 의 새 기능 문서: "Many members that you write are single statements that could be single expressions." 그런 멤버는 { return …; } 대신 => 뒤에 식 하나를 적습니다. 문서가 드는 첫 후보는 ToString() 의 재정의입니다.

C# 5 로 내리면 => 를 쓴 메서드 셋이 모두 CS8026 으로 거절됩니다. 게이트 이름은 expression-bodied method 입니다. 람다에서 이미 쓰던 => 를 멤버 선언으로 가져온 것이라, 새 기호는 없습니다(4부).

실행 검증

식 본문 속성 — get 만 있는 속성 C# 6.0

왜 — 표준: 속성의 => E; 는 "exactly equivalent to the statement body { get { return E; } }" 이고, 그래서 읽기 전용 속성에만 쓸 수 있습니다. 컴파일러는 이것을 메서드와 따로 확인합니다.

get 이라는 낱말 없이 get 접근자가 생겼습니다. 대입은 CS0200 입니다 — set 접근자가 없는 보통의 읽기 전용 속성과 같은 오류입니다.

실행 검증

식 본문 인덱서 C# 6.0

왜 — 인덱서도 속성과 같은 규칙입니다. 표준: 인덱서의 => E; 는 { get { return E; } } 와 같고 읽기 전용 인덱서에만 쓸 수 있습니다. 게이트는 셋째 이름 expression-bodied indexer 를 씁니다.

한 기능처럼 보이는 식 본문 멤버가 컴파일러 안에서는 게이트 셋(메서드·속성·인덱서)입니다. 그래서 1장의 표에서 C# 6 의 게이트를 셀 때 이 셋을 따로 셉니다(1장).

실행 검증

연산자와 변환 연산자도 =>

표준: 연산자의 몸체는 블록이나 "an expression body" 입니다. 사용자 정의 변환도 연산자 선언이라 같은 규칙입니다.

C# 5 의 거절을 보면 연산자 셋에 따로 게이트가 없고 expression-bodied method 를 함께 씁니다. 생성자는 이 자리에 끼지 못했습니다 — 조금 뒤에서 봅니다.

실행 검증

void 메서드 — 문장이 될 수 있는 식만

표준: 반환 형식이 void 이면 E 는 "a statement_expression" 이어야 하고, 몸체는 { E; } 와 같습니다. 대입·호출·증감·new·await 만 됩니다.

함정 — => 뒤에는 문이 올 수 없습니다. if 를 쓰면 파서가 길을 잃고 오류가 아홉 줄 나오는데, 그중에는 ( … ) 를 C# 7 의 튜플로 읽으려다 낸 CS8124 까지 있습니다. -langversion:6 이어도 파서는 지금의 문법으로 읽습니다.
실행 검증

void 식 본문과 ?.Invoke — 문법이 따로 챙긴 자리

표준의 메서드 몸체 문법에는 => 뒤에 올 것으로 expression 말고 null_conditional_invocation_expression 이 따로 있고, 둘 다 맞으면 뒤의 것을 고르라고 적습니다. Click?.Invoke(…) 는 값이 없을 수도 있는 호출이라 void 몸체로 쓰려면 그 자리가 필요합니다.

처리기가 없을 때의 첫 Fire() 는 아무것도 하지 않고, 처리기를 단 뒤에만 찍습니다. C# 6 의 두 기능 — 식 본문과 ?. (4장) — 이 한 줄에서 만납니다. 문서가 권하는 이벤트 호출 꼴이기도 합니다.

실행 검증

C# 6 이 막은 자리 — 생성자·종료자·접근자

C# 6 의 새 기능 문서는 식 본문이 "methods and read-only properties" 에 된다고만 적습니다. 나머지 자리는 C# 7.0 이 열었습니다. 제안서: "In C# 7.0, we added support for expression-bodied constructors, destructors, and accessors."

C# 6 으로 내리면 게이트 둘이 보입니다 — expression body constructor and destructor 와 expression body property accessor. 17행의 Fahrenheit 는 C# 6 의 식 본문 속성이라 거절되지 않습니다. 그래서 C# 6 에서 set 이 있는 속성은 => 로 쓸 수 없었습니다. C# 7.0 은 8부에서 봅니다.

실행 검증

블록 본문과 무엇이 같고 무엇이 다른가

표준은 "exactly equivalent" 라고 합니다. 리플렉션으로 확인합니다 — 속성의 접근자, 메서드의 IL 바이트, 숨은 필드의 수.

set 이 없고, 필드가 생기지 않았습니다(n 하나). 최적화 빌드에서는 IL 이 바이트까지 같습니다. 디버그 빌드에서는 블록 본문 쪽에만 00(nop)과 0A-2B-00-06(지역 변수에 저장 → 다음 줄로 분기 → 다시 읽기)이 더 붙습니다 — 디버거가 return 줄에 멈출 자리입니다. 의미는 같고 디버그 IL 만 다릅니다.

실행 검증

함정 — => 는 읽을 때마다, { get; } = 은 한 번

둘 다 C# 6 에서 왔고 생김새가 비슷합니다. => E 는 get 접근자의 몸체이고, { get; } = E 는 객체를 만들 때 한 번 도는 초기화자입니다(6장).

Init 은 생성할 때 받은 1 을 계속 돌려줍니다. Expr 은 읽을 때마다 Issue() 를 다시 불러 2, 3, 4 가 됩니다. Expr 이 2 부터인 것은 생성자에서 Init 의 초기화자가 1 을 먼저 가져갔기 때문입니다.

실행 검증

함정 — => new 는 읽을 때마다 새 객체

같은 실수가 컬렉션에서는 조용한 데이터 손실이 됩니다. 컴파일러는 경고하지 않습니다.

o.Lines.Add("tea") 는 방금 만든 리스트에 더하고, 그 리스트는 곧 버려집니다. 다음에 읽는 o.Lines 는 또 새 빈 리스트입니다. ReferenceEquals 가 그 차이를 보입니다.

실행 검증

= 와 => — 한 글자로 필드가 속성이 된다

세 줄 모두 5 를 줍니다. 멤버의 종류는 다릅니다.

B 만 속성입니다. C 의 => 는 람다라서 C 는 대리자 형식의 필드입니다. 필드와 속성은 리플렉션에서 다른 종류로 보이므로, 공개 멤버에서 이 한 글자는 API 의 모양을 바꿉니다. 반면 블록 본문을 식 본문으로 바꾸는 것은 문서가 "a binary compatible change" 라고 적습니다 — 앞 장에서 본 대로 같은 get 접근자가 되기 때문입니다.

실행 검증

=> x => … — 람다를 돌려주는 식 본문 속성

화살표 둘이 이어지면 앞의 것은 속성의 몸체, 뒤의 것은 람다입니다. 속성을 읽을 때마다 람다 식이 다시 계산됩니다 — 대리자가 매번 새로 생기는가는 람다가 무엇을 붙잡느냐에 달렸습니다.

Inc 는 두 번 읽어도 같은 대리자입니다 — 붙잡는 것이 없는 람다는 컴파일러가 한 번 만들어 캐시합니다(4부). AddN 은 n 을 쓰려고 this 를 붙잡으므로 읽을 때마다 새 대리자가 할당됩니다. 루프 안에서 읽는 속성이라면 비용이 됩니다.

실행 검증

async 메서드는 되고, 반복기는 안 된다

식 본문은 몸체의 모양만 바꾸므로 async 와 함께 쓸 수 있습니다. 반복기는 yield return 문이 있어야 하므로 식 본문으로 쓸 수 없습니다.

TwiceAsync 는 상태 기계를 만드는 async 메서드이고, Twice 는 Task 를 그냥 돌려주는 보통 메서드입니다 (6부). => yield return 1; 은 문법 오류 두 줄입니다.

실행 검증

뒤 버전과의 맞물림 — => throw 는 C# 7.0

"항상 예외를 던지는 메서드" 는 몸체가 throw 문 하나입니다. C# 6 에서 throw 는 문이라 => 뒤에 올 수 없었습니다. C# 7.0 의 throw 식이 그 자리를 열었습니다.

거절의 게이트 이름은 식 본문이 아니라 throw expression 입니다. 식 본문 메서드는 C# 6 에 이미 있었고, 모자랐던 것은 throw 를 식으로 쓰는 문법이었습니다.

실행 검증

뒤 버전과의 맞물림 — => ref (C# 7.0)

표준의 속성 문법에는 => ref V; 가 있고, 그것은 { get { return ref V; } } 와 같습니다. ref 반환은 C# 7.0 의 기능입니다.

set 이 없는데도 b.First = 10 이 됩니다. get 이 변수 자체(items[0])를 돌려주기 때문입니다. 10 이 된 뒤 f++ 로 11, 합은 11 + 2 + 3 = 16 입니다. C# 6 의 "식 본문 속성은 읽기 전용" 이 ref 를 만나면 "get 만 있지만 쓸 수 있는" 속성이 됩니다.

실행 검증

뒤 버전과의 맞물림 — 인터페이스의 => (C# 8)

C# 8 의 기본 인터페이스 메서드는 인터페이스 멤버에 구현을 붙입니다. 문서: API 작성자가 "add methods to an interface in later versions without breaking source or binary compatibility". 그 구현도 식 본문으로 씁니다.

Square 는 Describe 를 쓰지 않았는데 인터페이스를 통해 부를 수 있습니다. C# 6 의 => 가 C# 8 에서 인터페이스 안까지 들어갔습니다(9부).

5장 퀴즈 — 식 본문 멤버

Q. C# 6 으로 컴파일할 때 다음 넷 가운데 거절되는 것은 무엇입니까? (가) public int Age => age; (나) public Person(int a) => age = a; (다) public static Money operator -(Money m) => new Money(-m.Cents); (라) public int this[int i] => data[i];

A. (나)입니다. 생성자의 식 본문은 C# 7.0 의 expression body constructor and destructor 게이트입니다 (생성자·종료자·접근자). (가)는 속성, (라)는 인덱서, (다)는 메서드 게이트로 C# 6 에서 됩니다 (연산자).

자동 속성 — 초기값과 진짜 읽기 전용

초기화자 · 도는 차례 · get 만 있는 자동 속성 · readonly 뒷받침 필드 · 구조체 · 레코드 이전의 불변 형식 · field

자동 속성 초기화자 (auto-property initializer) C# 6.0

왜 — C# 3 의 자동 속성(4부)은 초기값을 줄 자리가 없어서, 생성자에 대입을 따로 써야 했습니다. C# 6 의 새 기능 문서: 초기화자는 "easier to perform the initialization exactly once" 이고, 초기화가 선언에 붙어 있어 저장 공간과 공개 인터페이스를 한눈에 맞춰 볼 수 있다.

표준: 초기화자는 "applied directly to the backing field" 입니다 — set 접근자를 부르지 않고 숨은 필드에 바로 들어갑니다. 정적 자동 속성에도 됩니다.

실행 검증

도는 차례 — 필드와 섞여 적힌 순서대로, 기반 생성자보다 먼저

표준: 필드 초기화자는 생성자에 들어서자마자 "before the implicit invocation of the direct base class constructor" 에 돌고, 순서는 "the textual order" 입니다. 자동 속성의 초기화자도 숨은 필드의 초기화자라 같은 줄에 섭니다.

속성 P 의 초기화자가 두 필드 사이에서, 그리고 Base() 보다 먼저 돕니다. C# 14 의 field 제안서도 이 차례를 들어 초기화자가 set 접근자를 부를 수 없는 까닭을 댑니다 — 기반 생성자 전에는 인스턴스 메서드를 부를 수 없다(뒤에서).

실행 검증

초기화자에서는 this 를 못 쓴다

그래서 초기화자는 만들고 있는 객체를 볼 수 없습니다. 표준: 인스턴스 필드의 초기화자는 "cannot reference the instance being created".

오류 문장은 "A field initializer" 라고 말합니다. 자동 속성의 초기화자가 컴파일러에게는 필드 초기화자이기 때문입니다. 다른 속성에서 값을 계산하려면 Area 처럼 get 접근자(또는 식 본문 속성)에 두어, 읽을 때 계산하게 합니다.

실행 검증

함정 — 초기화자는 재정의된 set 을 부르지 않는다

표준: 초기화자는 숨은 필드에 바로 들어갑니다. 그래서 가상 자동 속성을 파생 클래스가 재정의해도 기반 클래스의 초기화자는 그 set 을 거치지 않습니다. C# 14 의 field 제안서가 "previous versions of the language" 의 예로 드는 경우를 C# 6 모양으로 옮겼습니다.

값은 True 인데 재정의된 set 은 한 번도 돌지 않았습니다. 생성자에서 IsActive = active 로 대입하면 가상 호출이라 재정의된 set 이 돕니다. "초기값" 이라는 같은 뜻을 두 방식으로 쓰면 부수 효과가 달라집니다.

실행 검증

this(…) 로 이어진 생성자 — 초기화자는 한 번

표준: 필드 초기화자를 실행하는 것은 생성자 초기화자가 없거나 base(…) 인 생성자입니다. this(…) 로 다른 생성자에 넘기는 생성자는 직접 돌리지 않습니다.

초기화자는 Order(note) 의 몸체 앞에서 한 번만 돌았습니다. 생성자 몸체는 안쪽(넘겨받은 쪽)부터 끝납니다. 생성자가 여럿이어도 자동 속성의 초기화자가 두 번 도는 일은 없습니다.

실행 검증

get 만 있는 자동 속성 (read-only auto-property) C# 6.0

왜 — C# 6 의 새 기능 문서: "Read-only auto-properties provide a more concise syntax to create immutable types." C# 3 의 대용 { get; private set; } 은 클래스 안에서 여전히 바꿀 수 있었습니다(4부). 문서는 이것을 "true language support for creating immutable types" 라고 부릅니다.

게이트 이름이 컴파일러 안의 정식 이름을 드러냅니다 — readonly automatically implemented properties. 초기화자와는 따로인 게이트라, { get; } = 값 은 두 기능을 함께 씁니다.

실행 검증

대입은 생성자 안에서만 — 람다도 안 된다

문서: 다른 메서드에서 대입하면 "generates a CS0200 compilation error". 생성자 안에서는 여러 번 대입해도 됩니다 — readonly 필드와 같은 규칙입니다.

함정 — 람다는 생성자 안에 적혀 있어도 거절됩니다. 람다의 몸체는 컴파일러가 만든 다른 메서드가 되고, 그 메서드는 생성자가 끝난 뒤에도 불릴 수 있기 때문입니다(4부). 오류 번호는 메서드에서와 같은 CS0200 입니다.
실행 검증

숨은 필드는 정말 readonly 인가

표준: set 이 없으면 "the backing field is considered readonly". 리플렉션의 IsInitOnly 가 IL 의 initonly 표지를 읽습니다.

{ get; } 쪽만 readonly=True 입니다. 그러니 C# 3 의 private set 과 달리 런타임도 이 필드를 읽기 전용으로 압니다. 필드 이름 <A>k__BackingField 는 표준이 정한 것이 아니라 Roslyn 의 구현 세부입니다(4부).

실행 검증

함정 — 리플렉션은 인스턴스 readonly 를 넘는다

readonly 는 컴파일러가 지키는 약속입니다. 리플렉션으로 숨은 필드에 직접 쓰면 어떻게 되는지 .NET 10 에서 봅니다.

인스턴스 필드는 바뀌었습니다 — "불변" 객체의 Value 가 42 입니다. 정적 readonly 필드는 형식이 초기화된 뒤라 런타임이 FieldAccessException 으로 막았습니다. 불변 형식이 지켜 주는 것은 C# 코드의 대입이지, 리플렉션을 쓰는 직렬화기 같은 코드가 아닙니다. 게다가 필드 이름은 구현 세부입니다(앞 장).

실행 검증

뒤 버전과의 맞물림 — 숨은 필드에 특성 (C# 7.3)

숨은 필드에 이름이 없으니 특성을 붙일 자리도 없었습니다. C# 7.3 의 새 기능 문서: [field: …] 로 쓴 특성은 "applied to the compiler generated backing field" 이다.

뜻밖의 것 — 7.2 로 내려도 거절되지 않고 경고 CS8371 하나이며, 출력이 보이듯 특성은 그래도 필드에 붙습니다. 이 게이트는 게이트 표에서 기능 이름 칸이 비어 있는 아홉 가운데 하나입니다 — 리소스에 사람이 읽을 이름이 없고, 거절 대신 자기 경고 문장을 씁니다 (0부).

6장 퀴즈 — 자동 속성

Q. class C : B { public int P { get; } = F(); public C() { G(); } } 에서 F(), B 의 생성자, G() 는 어떤 차례로 돕니까? 그리고 G 라는 인스턴스 메서드 안에서 P = 1; 이라고 쓰면 어떻게 됩니까?

A. F() → B() → G() 입니다. 초기화자는 기반 생성자보다 먼저 돕니다(도는 차례). G 안의 대입은 CS0200 입니다 — get 만 있는 자동 속성은 생성자 몸체에서만 대입할 수 있고, 생성자가 부르는 메서드라도 안 됩니다 (생성자 안에서만).

using static — 형식 이름 없이 정적 멤버를 C# 6.0

왜 — C# 6 의 새 기능 문서: "The using static enhancement enables you to import the static methods of a single class." 수학 식처럼 Math. 가 줄마다 붙던 코드가 첫 예입니다. 표준: 형식에 "directly" 들어 있는 정적 멤버와 중첩 형식을 가져온다.

거절은 지시문 한 줄에서만 납니다. 아래의 Sqrt 같은 이름은 보고되지 않았습니다 — 선언 쪽 오류가 몸체의 검사를 가린 것입니다 (1장).

실행 검증

String 은 되고 string 은 안 된다

문서: 정적·인스턴스 멤버가 섞인 클래스에도 쓸 수 있고 가장 쓸모 있는 예가 String 이다. 단 "You cannot use the string keyword instead."

함정 — 오류 문장이 엉뚱합니다. 지금의 파서는 using static string; 을 지시문이 아니라 C# 8 의 using 선언 (using var x = …;)에 한정자 static 이 붙은 것으로 읽고 CS9229 를 냅니다. -langversion:6 이어도 파서는 지금의 문법을 씁니다.
실행 검증

확장 메서드는 확장 호출로만 들어온다

표준: using static 은 확장 메서드를 "directly as static methods" 로 가져오지 않고 확장 메서드 호출에만 쓸 수 있게 한다. 문서: LINQ 의 패턴을 Enumerable 하나로 가져오는 데 쓴다.

보통 정적 메서드 Range 는 이름만으로 불리고, 확장 메서드 Where 는 nums.Where(…) 로만 불립니다. using System.Linq; 없이도 nums.Where 가 된 것은 using static 이 그 클래스의 확장 메서드를 확장 호출용으로 들여왔기 때문입니다 — 네임스페이스의 다른 클래스는 들여오지 않습니다.

실행 검증

열거형 멤버와 중첩 형식도

열거형의 멤버는 정적 상수이고, 문서: "The static using directive also imports any nested types." 둘 다 이름만으로 씁니다.

Saturday 가 DayOfWeek.Saturday 이고, Square 가 Shapes.Square 입니다. 열거형 이름을 빼면 짧아지지만, 같은 멤버 이름을 가진 열거형을 함께 가져오면 None 이 어느 쪽인지 정할 수 없어 CS0229 입니다.

같은 이름이 둘 이상이면

using static 으로 들어온 메서드들은 한 오버로드 묶음이 됩니다. 이름이 겹치면 매개변수로 고르고, 고를 수 없으면 모호하다고 합니다.

F(1) 과 F("s") 는 서로 다른 클래스의 메서드인데도 오버로드처럼 골라졌습니다. 자기 클래스의 H 는 가져온 A.H 보다 먼저 찾아져서 경고 없이 이깁니다. G() 는 CS0121 이고, 형식 이름을 붙이면 풀립니다 — 문서도 확장 메서드를 정적 호출로 부르는 경우에 "Adding the class name … resolves ambiguity" 라고 적습니다.

실행 검증

함정 — 같은 이름의 내 멤버는 가져온 오버로드를 모두 가린다

앞 장의 H 는 매개변수까지 같아서 내 것이 이긴 것이 당연해 보였습니다. 매개변수가 달라도 마찬가지입니다. 이름을 찾는 단계에서 자기 클래스의 WriteLine 이 먼저 찾아지면, using static 이 들여온 Console.WriteLine 들은 후보에 들지 못합니다.

Console.WriteLine(string) 이 있는데도 CS1503 — int 하나를 받는 내 메서드만 후보였습니다. Write 는 Program 에 없으니 들여온 것이 쓰였습니다. 오버로드가 클래스를 넘어 합쳐지는 것(앞 장)은 using static 으로 들여온 것들끼리의 일입니다.

닫힌 제네릭 형식도 using static

using static 의 대상은 형식 이름이라, Counter<int> 처럼 형식 인자를 채운 제네릭 형식도 됩니다.

Hits 는 Counter<int>.Hits 입니다. 닫힌 형식마다 정적 필드가 따로라서 Counter<string>.Hits 는 0 입니다(3부). 이름만 보고는 어느 닫힌 형식의 것인지 알 수 없다는 점이 using static 의 대가입니다.

뒤 버전과의 맞물림 — global using static

C# 6 의 using static 은 파일 하나에만 걸렸습니다. C# 10 부터는 프로젝트의 한 파일에 모아 둘 수 있습니다(11부).

예외 필터 (exception filter) C# 6.0

왜 — C# 6 의 새 기능 문서: 필터는 catch 절을 "when a given catch clause should be applied" 로 정하고, 식이 false 면 "the catch clause is skipped". 쓰임은 예외의 정보를 보고 이 catch 가 처리할 수 있는지 고르는 것입니다.

404 는 첫 catch 가, 500 은 필터가 false 라 건너뛰고 둘째 catch 가 받습니다. 필터가 없던 시절에는 한 catch 안에서 if 로 나누고, 해당하지 않으면 throw; 로 다시 던졌습니다 — 그 둘이 같지 않다는 것을 다음 장에서 봅니다.

실행 검증

필터는 스택을 풀기 전에 돈다

표준의 예: 예외가 나면 먼저 바깥 catch 들의 필터를 돌리고, "Then, the finally clause in Method executes" — 그 뒤에야 catch 로 갑니다. 같은 일을 catch 안의 if 로 하면 차례가 다릅니다.

필터는 inner finally 보다 먼저 돌았습니다. 예외가 난 자리의 스택이 그대로 남아 있을 때 판단한다는 뜻입니다. catch 에 들어가서 판단하면 이미 안쪽 finally 가 돈 뒤입니다. "잡을지 말지" 를 필터로 옮기면 그 판단이 스택이 풀리기 전으로 당겨집니다.

실행 검증

필터 안에서는 던진 메서드가 아직 스택에 있다

"스택을 풀기 전" 을 차례가 아니라 스택 자체로 확인합니다. 필터와 catch 몸체에서 각각 지금의 호출 스택에 Inner 의 프레임이 있는지 봅니다.

필터가 도는 동안에는 예외를 던진 Inner 가 호출 스택에 그대로 있고, catch 몸체에 들어오면 없습니다. 필터는 예외가 난 자리의 상태를 그대로 둔 채 판단합니다. 이 예제는 최적화하지 않은 빌드라 Inner 가 인라인되지 않습니다(csrun 의 기본, 0부).

실행 검증

false 를 돌려주는 필터 — 잡지 않고 기록만

필터는 식이라 메서드를 부를 수 있습니다. 늘 false 를 돌려주는 메서드를 필터로 쓰면, 예외를 보기만 하고 그대로 지나가게 할 수 있습니다.

Work 의 catch 몸체는 돌지 않았고, 예외는 Main 까지 그대로 갔습니다. 잡았다가 throw; 로 다시 던지는 것과 달리, 이 예외는 Work 에서 한 번도 잡히지 않았습니다. 기록하는 쪽이 예외의 흐름을 바꾸지 않습니다.

실행 검증

함정 — 필터 안에서 난 예외는 삼켜진다

표준: 필터를 계산하다 예외가 나면 "that exception is caught, and the exception filter evaluates to false".

바깥 catch 가 받은 것은 필터의 NullReferenceException 이 아니라 원래의 TimeoutException 입니다. 필터의 버그는 아무 흔적도 남기지 않고 "이 catch 는 아니다" 가 됩니다. 필터 식은 짧고 던지지 않게 써야 합니다.

실행 검증

같은 형식의 catch 를 여럿 — 필터가 있을 때만

표준: catch 는 적힌 차례로 살피고, 필터 없이 어떤 형식을 잡은 뒤에 같은 형식(또는 파생 형식)을 다시 잡으면 컴파일 오류다.

2 는 첫 필터에서 떨어지고 둘째에서 잡힙니다. 필터가 붙은 catch 는 "이 형식 전부" 를 잡는다고 볼 수 없으니 뒤에 같은 형식이 와도 됩니다. 필터 없는 셋째 뒤의 넷째는 CS0160 입니다.

실행 검증

형식 없는 catch 에도 when

표준의 문법은 'catch' exception_filter block — 형식을 적지 않은 catch 에도 필터를 붙일 수 있습니다.

필터는 예외 객체가 아니라 둘레의 상태(n)만 보고 고를 수도 있습니다. 형식 없는 catch 는 모든 예외에 맞는 절이라 원래는 맨 끝에만 올 수 있지만, 필터가 붙으면 "모두" 가 아니므로 뒤에 다른 catch 가 와도 됩니다.

실행 검증

인덱스 초기화자 (index initializer) C# 6.0

왜 — C# 6 의 새 기능 문서: 그전에도 사전은 { key, value } 로 초기화할 수 있었지만, 새 문법은 "assignment using an index into the collection" 이고, 덕분에 연관 컨테이너를 순차 컨테이너와 비슷한 문법으로 초기화한다.

게이트의 이름은 "dictionary initializer" 이지만, 다음 장들에서 보듯 사전에만 쓰는 문법은 아닙니다. C# 3 의 { k, v } 꼴은 4부에서 봤습니다.

실행 검증

{ k, v } 는 Add, [k] = v 는 인덱서 대입

두 꼴은 다른 멤버를 부릅니다. 부르는 것을 찍는 클래스 Spy 로 확인하고, 진짜 Dictionary 에서 같은 열쇠를 두 번 넣어 봅니다.

[k] = v 는 인덱서의 set 을 부르므로 같은 열쇠의 나중 값이 이깁니다. { k, v } 는 Add 라서 Dictionary 에서는 ArgumentException 입니다. 표준도 객체 초기화자가 같은 속성을 두 번 정할 수는 없지만 인덱서는 "may even use the same indexer arguments multiple times" 라고 적습니다. C# 6 판과 C# 5 판을 나란히 둔 짧은 예는 4부에 있습니다.

IEnumerable 이 필요한가 — { k, v } 꼴은 컬렉션 초기화자라 형식이 IEnumerable 이어야 해서 Spy 에 붙였습니다(4부). [k] = v 꼴은 객체 초기화자의 한 갈래라서 인덱서만 있으면 됩니다 — 다음 장의 Grid 가 그렇습니다.
실행 검증

인덱서라면 무엇이든 — 그리고 두 함정

인덱스 초기화자는 객체 초기화자 안에서 속성 대입과 섞어 쓸 수 있고, 인자가 둘인 인덱서에도 됩니다. 값 자리에 컬렉션 초기화자를 두는 꼴도 문법에 있습니다.

함정 둘 — ["a"] = { 1 } 은 새 리스트를 넣는 것이 아니라 d["a"] 를 읽어서 거기에 Add(1) 합니다. 빈 사전이라 읽기가 KeyNotFoundException 입니다. 그리고 한 초기화자에 두 꼴을 섞으면 CS0747 입니다 — 객체 초기화자와 컬렉션 초기화자는 서로 다른 문법이기 때문입니다.
실행 검증

인덱서 인자는 한 번, get 은 원소마다

표준: 초기화 대상이 인덱서이면 "the arguments to the indexer shall always be evaluated exactly once" — 중첩 초기화자가 비어 있어도 부수 효과를 위해 계산한다.

Key(0) 은 한 번, 그 결과로 get 은 원소 셋마다 한 번씩 세 번 불렸습니다. 빈 { } 에서도 Key(1) 은 불렸지만 get 은 불리지 않았습니다. 마지막 줄의 get 둘은 Count 를 읽는 Main 의 것입니다.

실행 검증

함정 — List 에 [0] = … 은 더하지 않는다

인덱스 초기화자는 인덱서의 set 을 부를 뿐이라 "없는 자리를 만든다" 는 뜻이 없습니다. 사전의 인덱서는 없는 열쇠를 더하지만, List<T> 의 인덱서는 있는 원소만 바꿉니다.

원소가 둘 있는 리스트에서는 [0] = 1 이 첫 원소를 바꿨고 개수는 그대로 2 입니다. 용량을 5 로 잡은 빈 리스트에서는 ArgumentOutOfRangeException 입니다 — 용량은 개수가 아닙니다. 게이트 이름이 "dictionary initializer" 인 까닭이 여기서 보입니다.

실행 검증

컬렉션 초기화자의 확장 메서드 Add C# 6.0

왜 — C# 6 의 새 기능 문서: "This feature was added for parity with Visual Basic." 항목을 더하는 메서드의 이름이 Add 가 아닌 컬렉션(예: Push)에 쓸모가 있다.

초기화자의 1, 2, 3 이 차례로 Push 되어 꺼낼 때는 3 2 1 입니다. 4부가 먼저 찾은 대로 지금의 컴파일러는 이것을 C# 3 에서도 받아들입니다 (4부). 문서의 버전은 C# 6 이고, 옛 컴파일러의 동작은 이 기계에서 보일 수 없습니다.

실행 검증

개선된 오버로드 해석 — Task.Run(DoThings) C# 6.0

왜 — C# 6 의 새 기능 문서: 예전 컴파일러는 Task 를 돌려주는 메서드를 메서드 그룹으로 넘긴 Task.Run(DoThings) 에서 Task.Run(Action) 과 Task.Run(Func<Task>()) 를 가르지 못해 람다로 감싸야 했고, "The C# 6 compiler correctly determines that Task.Run(Func<Task>()) is a better choice."

문서 스스로 "one you probably won't notice" 라고 부르는 변화입니다. 지금의 컴파일러는 C# 5 에서도 Func<Task> 를 고릅니다 — 오버로드 해석의 규칙은 언어 버전으로 갈리지 않습니다. 그래서 옛 컴파일러의 모호 오류는 이 기계에서 보일 수 없습니다 (0부의 꼴 (나)가 안 되는 경우).

Roslyn 이 지킨 옛 컴파일러의 동작

Roslyn 저장소의 문서 하나는 "known breaking changes in Roslyn (VS2015 and later) from the native C# compiler (VS2013 and previous)" 를 모읍니다 — C# 6 과 함께 온 새 컴파일러(1장)가 옛 컴파일러와 다른 자리입니다. 그중에는 명세와 어긋나도 옛 동작을 지킨 것들이 있습니다.

문서와 다른 하나 — 같은 문서의 "Reserved Members" 절은 형식 매개변수 Item 과 인덱서가 함께 있는 클래스를 옛 컴파일러는 거절했지만 "Roslyn does not reject this code" 라고 적습니다. 지금의 Roslyn 은 CS0102 로 거절합니다(2026-10 기준). 문서가 낡았거나 그 뒤에 바뀐 것인데, 어느 쪽인지는 미확인입니다.
실행 검증

Roslyn 이 새로 잡은 것 — 경고 하나, 그리고 풀린 오류 하나

같은 문서의 "Breaking Change" 목록에는 Roslyn 이 새로 보고하게 된 진단이 있습니다. 둘을 골라 지금의 컴파일러에 넣어 봅니다: null 과 비교한 값 형식(CS0472), 그리고 참조 형식인지 모르는 형식 매개변수에 lock(CS0185).

CS0472 는 문서대로 나옵니다. 그런데 lock (t) 는 CS0185 없이 컴파일됐습니다 — 지금의 컴파일러는 이 경우를 막지 않습니다(2026-10 기준). CS0185 자체는 남아 있어서 int 에 거는 lock 은 거절됩니다. 문서의 목록은 VS2015 당시의 기록이고, 그 뒤의 변화는 이 덱이 보인 캡처가 말합니다.
