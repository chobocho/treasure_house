virtual·override · new 숨김 · sealed · abstract · 생성자 사슬 · 정적 생성자 · 접근 수준 · object 재정의 · 소멸자

virtual 과 override C# 1.0

왜 — 가상 메서드 호출에서는 인스턴스의 실행 시간 형식이 실제로 돌 구현을 고르고, 가상이 아닌 메서드 호출에서는 컴파일 시간 형식이 고릅니다. C# 의 메서드는 virtual 을 적어야 가상이 됩니다.

함정 — Name 은 기반 형식 참조로 부르면 Shape.Name 이 돕니다. 객체는 Circle 인데도 그렇습니다. 가상이 아닌 메서드는 변수의 형식을 따릅니다.
실행 검증

new 로 숨기기 — 사슬이 둘로 갈린다 C# 1.0

왜 — 파생 클래스는 상속받은 멤버와 같은 이름·시그니처의 멤버를 선언할 수 있고, 그러면 기반의 멤버를 숨깁니다. new 는 그 숨김이 뜻한 것임을 밝히는 한정자입니다. new virtual 은 같은 이름으로 새 가상 사슬을 시작합니다.

A·B 참조로 부르면 B.F, C·D 참조로 부르면 D.F 입니다. D 의 override 는 가장 가까운 사슬인 C.F 를 재정의합니다. 표준의 예가 같은 꼴을 듭니다.

실행 검증

new 를 빠뜨리면 — 오류가 아니라 경고

표준은 숨김을 오류로 보지 않습니다. 대신 new 가 없으면 컴파일러가 경고를 내야 한다고 적습니다.

함정 — 기반의 Load 가 virtual 이어도, 파생 쪽에 override 를 빠뜨리면 재정의가 아니라 숨김입니다. 경고(CS0114)만 남기고 컴파일은 되며, 기반 참조로 부르면 Base.Load 가 돕니다.
실행 검증

왜 기본이 비가상인가 — 설계자의 답

C# 의 수석 설계자 앤더스 하일스버그(Anders Hejlsberg)는 2003년 Artima 인터뷰에서, 자바와 달리 인스턴스 메서드가 기본으로 비가상인 까닭을 성능보다 버전 관리로 설명했습니다.

인터뷰에서 — "A more important issue is versioning." (더 중요한 문제는 버전 관리입니다.)
인터뷰에서 — "To declare a new virtual method, you just mark it virtual. But to override an existing virtual method, you must say override." (새 가상 메서드는 virtual 만 붙이면 되지만, 있는 가상 메서드를 재정의하려면 override 라고 말해야 합니다.)

같은 답에서 그는 기반 클래스의 새 버전이 파생 클래스에 이미 있는 이름의 가상 메서드를 들여와도 "VTBL 칸이 둘" 이 될 뿐 기존 코드가 그대로 돈다고 말합니다 — 앞 장의 경고만 내는 숨김이 그 장면입니다.

역사 근거

override 가 지켜야 할 것

재정의는 기반 메서드와 접근 수준·반환 형식·시그니처가 같아야 하고, 기반 쪽이 virtual·abstract·override 여야 합니다.

sealed — 더는 물려줄 수 없다 C# 1.0

왜 — sealed 는 뜻하지 않은 파생을 막으려고 씁니다. 표준은 덧붙여, 파생 클래스가 없다는 것을 알기 때문에 봉인된 클래스 인스턴스에 대한 가상 호출을 비가상 호출로 바꾸는 최적화도 가능하다고 적습니다. sealed override 는 재정의 사슬을 그 자리에서 끊습니다.

-parallel- 은 왜 — csc 는 형식들을 나란히 컴파일해서, 서로 다른 형식에서 나온 진단은 찍히는 순서가 실행마다 바뀝니다(이 기계에서 같은 소스를 여섯 번 돌려 두 가지 순서를 봤습니다). -parallel- 은 진단을 소스 순서로 고정할 뿐, 판정은 바꾸지 않습니다. 이 부에서 진단이 여러 형식에 걸친 캡처에만 붙입니다.

추상 클래스와 추상 메서드 C# 1.0

왜 — 추상 클래스는 그 자체로 불완전해서 기반 클래스로만 쓰입니다. 인스턴스를 만들 수 없고, 추상 멤버를 가질 수 있으며, 추상이 아닌 파생 클래스는 상속받은 추상 멤버를 모두 구현해야 합니다.

추상 메서드는 암시적으로 가상이지만 virtual 을 붙일 수는 없습니다. Speak 안의 Sound() 호출이 실제 객체의 구현으로 갑니다.

실행 검증

추상 멤버의 규칙 — 컴파일러가 세는 넷

추상 메서드는 본문이 없어야 하고, 추상 클래스 안에만 있을 수 있습니다. 구현을 빠뜨린 파생 클래스와, 추상 클래스의 new 도 거절됩니다.

왜 파일이 둘인가 — 같은 파일에 new Animal() 을 함께 두었더니 CS0144 가 나오지 않았습니다. 이 컴파일러는 선언에 오류가 있으면 메서드 본문의 오류를 보고하지 않았습니다. 거절 예제를 만들 때는 오류의 층을 나눠야 합니다.
실행 검증

base 로 부르면 가상 호출이 아니다 C# 1.0

왜 — base.M() 은 바로 위 기반 클래스의 멤버를 가리킵니다. 그 멤버가 가상이어도 어떤 함수 멤버를 부를지는 컴파일할 때 정해집니다. 그래서 재정의한 메서드 안에서 기반 구현을 부를 수 있습니다.

생성자 사슬과 필드 초기화의 순서 C# 1.0

왜 — 생성자 초기화자 : this(…) 와 : base(…) 는 본문보다 먼저 다른 생성자를 부릅니다. 필드의 변수 초기화자는 대입문으로 바뀌어 기반 클래스 생성자를 부르기 전에 실행됩니다.

Derived() 는 this("x") 로 넘기므로 필드 초기화는 base() 를 부르는 Derived(string) 쪽에서 한 번만 돕니다. 본문은 안쪽 생성자부터 끝납니다.

실행 검증

기반 생성자 안의 가상 호출

기반 생성자가 가상 메서드를 부르면, 아직 파생 생성자의 본문이 돌지 않은 객체에서 파생 쪽 재정의가 돕니다. 표준이 같은 예로 설명하는 순서입니다.

함정 — 초기화자로 준 fromInit 은 이미 채워져 있지만, 생성자 본문에서 대입하는 fromBody·count 는 아직 null 과 0 입니다. 생성자에서 가상 메서드를 부르지 않는 것이 안전합니다.
실행 검증

기본 생성자가 사라질 때

인스턴스 생성자 선언이 하나도 없는 클래스에만 기본 생성자가 자동으로 생깁니다. 생성자 초기화자가 없는 생성자에는 base() 가 암시적으로 붙습니다.

오류 문장이 "required parameter 'x'" 로 매개변수 이름을 짚는 것은 지금의 Roslyn 의 말투입니다. 언어 버전이 1 이어도 진단 문장은 지금 컴파일러의 것입니다.

정적 생성자는 처음 쓸 때 한 번 C# 1.0

왜 — 정적 생성자는 한 응용 도메인에서 많아야 한 번 돕니다. 인스턴스를 처음 만들거나 정적 멤버를 처음 참조하는 것 가운데 먼저 일어나는 일이 실행을 일으킵니다. 정적 생성자가 있으면 정적 필드 초기화자는 그 바로 앞에 돕니다.

정적 생성자가 없는 클래스라면 정적 필드 초기화자는 "첫 사용 전, 구현이 정하는 때" 에 돕니다 — 그래서 이 예제는 일부러 정적 생성자를 두었습니다.

실행 검증

정적 생성자가 던지면 — 그 형식은 끝이다

정적 생성자에서 처리하지 않은 예외는 TypeInitializationException 으로 감싸여 정적 생성자를 일으킨 자리로 던져집니다.

함정 — 두 번째 시도에서 정적 생성자는 다시 돌지 않습니다("static constructor runs" 는 한 번). 그런데도 같은 예외가 다시 납니다. 정적 생성자는 많아야 한 번 돌고, 그 한 번이 실패한 형식은 이 런타임에서 계속 같은 예외를 냅니다.

접근 수준 다섯 가지 C# 1.0

왜 — 선언된 접근 수준은 public·protected·internal·protected internal·private 다섯입니다. protected internal 은 "같은 어셈블리 또는 파생 클래스" 입니다. 클래스 멤버는 적지 않으면 private 입니다.

메타데이터의 이름은 C# 과 다릅니다 — protected 는 family, internal 은 assembly, protected internal 은 family or assembly 입니다. 최상위 클래스는 적지 않으면 internal 이라 IsNotPublic 이 True 입니다.

실행 검증

protected 는 "내 쪽" 참조로만

파생 클래스 안에서도 protected 인스턴스 멤버는 자기 형식(또는 그 파생)의 인스턴스를 통해서만 건드릴 수 있습니다. 한 파생 클래스가 다른 파생 클래스의 protected 멤버에 접근하는 것을 막는 규칙입니다.

중첩 형식 C# 1.0

왜 — 클래스 안에 선언한 형식은 바깥 형식의 private 멤버에 접근할 수 있습니다. 중첩 형식의 기본 접근 수준은 private 입니다.

C# 소스에서는 Outer.Inner 로 쓰지만 리플렉션의 FullName 은 Outer+Inner 입니다. 문자열로 형식을 찾을 때(Type.GetType) 흔히 걸리는 차이입니다.

실행 검증

object 의 세 메서드를 함께 재정의 C# 1.0

왜 — object 는 모든 형식의 궁극적인 기반 클래스라, 모든 클래스가 ToString·Equals·GetHashCode 를 물려받습니다. 물려받은 것은 참조를 비교하므로, 값이 같은 객체를 Hashtable 의 같은 열쇠로 쓰려면 Equals 와 GetHashCode 를 함께 재정의합니다.

함정 — Equals 를 재정의해도 클래스의 == 는 여전히 참조 비교입니다. 문자열 연결의 key 는 재정의한 ToString 을 부릅니다.
실행 검증

Equals 와 GetHashCode 는 짝 — 컴파일러가 짚는다

한쪽만 재정의하거나, == 만 정의하고 Equals 를 그대로 두면 컴파일러가 경고합니다. 컴파일은 되므로 놓치기 쉽습니다.

소멸자는 Finalize 가 된다 C# 1.0

왜 — 소멸자(finalizer, ~Handle())는 System.Object 의 가상 메서드 Finalize 를 재정의하는 것으로 구현됩니다. C# 프로그램이 이 메서드를 직접 재정의하거나 부르는 것은 허용되지 않습니다.

소멸자가 언제 도는지는 가비지 수집기가 정하므로 이 덱은 찍지 않습니다. 예제의 "finalizing" 은 한 번도 찍히지 않았습니다.

속성과 이벤트를 언어에 — 설계자의 답

속성·이벤트가 왜 문법이 되었느냐는 물음에 하일스버그는 "컴포넌트" 를 듭니다. 그에게 컴포넌트는 속성·메서드·이벤트로 자신을 드러내는 클래스입니다.

인터뷰에서 — "It is a class that exposes itself through properties, methods, and events." (속성과 메서드와 이벤트로 자신을 드러내는 클래스입니다.)
인터뷰에서 — "With properties, they're not really properties, they're a getBla and a setBla." (C++ 나 자바에서 속성은 진짜 속성이 아니라 getBla 와 setBla 입니다.)

재미있는 것은 C# 도 속을 열면 get_Name·set_Name 이라는 점입니다 — 다음 장들이 그 모습을 꺼내 봅니다. 차이는 그 짝을 언어가 하나의 멤버로 다룬다는 데 있습니다.

역사 근거

속성 — 필드처럼 쓰는 메서드 C# 1.0

왜 — 속성은 필드를 자연스럽게 넓힌 것입니다. 읽고 쓰는 문법은 필드와 같지만 저장 위치를 뜻하지 않고, 읽기와 쓰기에 돌 문장을 정하는 접근자(accessor)를 가집니다. 그래서 값을 검사하거나 계산할 수 있습니다.

뒤 버전에서 — C# 1 에서는 속성마다 뒷받침 필드를 손으로 둡니다. get·set 의 접근 수준을 다르게 하는 것은 C# 2 의 기능입니다.
실행 검증

컴파일러가 만드는 것 — get_·set_ 메서드

메타데이터에서 속성은 접근자 메서드 get_이름·set_이름 과 그 둘을 묶는 속성 항목입니다. 리플렉션으로 선언된 public 메서드를 모두 꺼내 봅니다.

세 메서드 모두 IsSpecialName 이 True — 일반 메서드가 아니라 속성의 일부라는 표시입니다. 읽기 전용 Age 에는 set_Age 가 없습니다.

실행 검증

속성이 예약하는 이름

형식 T 의 속성 P 는 시그니처 T get_P() 와 void set_P(T value) 를 예약합니다. 읽기 전용 속성이어도 둘 다 예약됩니다.

실행 검증

속성은 변수가 아니다

속성은 저장 위치가 아니라서 ref·out 인자가 될 수 없습니다. 구조체를 돌려주는 속성의 필드에 대입하면, 돌려받은 복사본을 고치는 셈이라 컴파일러가 막습니다.

CS0206 의 "non ref-returning" 은 ref 반환이 생긴 뒤의 문장입니다(C# 7.0 ). C# 1 프로그램에도 지금의 문장이 찍힙니다.

실행 검증

인덱서 C# 1.0

왜 — 인덱서는 객체를 배열처럼 첨자로 다룰 수 있게 하는 멤버입니다. 이름 대신 this 로 선언하고, 매개변수 목록이 다르면 여럿 둘 수 있습니다.

실행 검증

인덱서의 이름은 Item

다른 언어와 함께 쓰려고 인덱서는 인덱스가 있는 속성으로 구현됩니다. IndexerName 특성이 없으면 이름은 Item 입니다.

string 의 인덱서는 Chars 입니다. 그래서 typeof(string).GetProperty("Item") 은 null 입니다.

실행 검증

정적 멤버는 형식에 하나 C# 1.0

왜 — 정적 필드는 인스턴스가 몇 개든 형식에 하나뿐입니다. 정적 멤버는 E.M 꼴에서 E 가 형식일 때만 부를 수 있고, 정적 함수 멤버 안에서는 this 를 쓸 수 없습니다.

뒤 버전에서 — C# 1 에는 정적 클래스(static class)가 없었습니다. 정적 멤버만 모으는 클래스는 private 생성자로 인스턴스를 막는 것이 관용구였습니다. 정적 클래스는 C# 2 의 기능입니다.

5장 퀴즈

Q. Base 가 인터페이스 IGreet 를 가상이 아닌 Hello() 로 구현합니다. Derived : Base 가 public new string Hello() 를 선언하면, ((IGreet)new Derived()).Hello() 는 어느 구현을 부릅니까? Derived : Base, IGreet 라면요?

A. 앞의 경우는 Base.Hello 입니다. 인터페이스 대응은 Base 가 구현할 때 정해졌고, new 숨김은 그것을 바꾸지 않습니다. 뒤의 경우는 인터페이스를 다시 구현한 것이라 대응을 새로 정하므로 Derived.Hello 입니다.

대리자와 이벤트

대리자 선언이 만드는 클래스 · 멀티캐스트 · -= 의 규칙 · event 가 막는 것 · add·remove · (sender, e) 관례

대리자 — 메서드를 담는 객체 C# 1.0

왜 — 대리자 선언은 System.Delegate 에서 나오는 클래스를 정의합니다. 대리자 인스턴스는 호출 목록(invocation list)을 감쌉니다. 인스턴스 메서드라면 인스턴스와 메서드가, 정적 메서드라면 메서드만이 목록의 한 칸입니다.

C# 1 의 꼴 — 대리자는 언제나 new Op(Add) 로 만듭니다. 메서드 이름만 쓰는 Op add = Add; 는 뒤 버전의 변화라 3부에서 봅니다.
실행 검증

왜 인터페이스가 아니라 대리자인가 — 설계자의 답

자바는 이벤트를 리스너 인터페이스로 받습니다. 왜 C# 은 대리자를 두었느냐는 물음에 하일스버그는 "모양만 맞으면 꽂힌다" 는 점을 듭니다.

인터뷰에서 — "With a delegate, by contrast, as long as the signatures are compatible, you can just slot them together." (대리자라면 시그니처만 맞으면 그냥 끼워 맞출 수 있습니다.)
인터뷰에서 — "Multicast is a completely orthogonal feature." (멀티캐스트는 완전히 별개의 기능입니다.)

같은 답에서 그는 멀티캐스트에 대해 "중립" 이라며, 대리자 대부분은 하나만 담는다고 덧붙입니다. 이 장은 그 "별개의 기능" 이 어떤 규칙으로 도는지를 봅니다.

역사 근거

컴파일러가 만드는 것 — 봉인된 대리자 클래스

대리자 형식은 암시적으로 sealed 이고, 선언과 같은 매개변수 목록의 Invoke 를 가져야 합니다. 구현은 그 밖의 멤버를 더 둘 수 있습니다.

기반은 MulticastDelegate, 그 위가 Delegate 입니다. Invoke 말고도 비동기 호출용 BeginInvoke·EndInvoke 가 만들어지고, 생성자는 대상 객체와 메서드 포인터(IntPtr)를 받습니다.

실행 검증

BeginInvoke 는 있지만 — .NET 10 에서는

앞 장에서 본 BeginInvoke 는 지금도 컴파일러가 만들어 줍니다. 그런데 이 런타임에서 부르면 어떻게 될까요.

함정 — 컴파일은 되고 실행에서 PlatformNotSupportedException 입니다. C# 1 시절의 비동기 대리자 호출 코드는 언어로는 지금도 맞지만 이 런타임에서는 돌지 않습니다. 언어 버전과 런타임은 따로 움직입니다(0부).
실행 검증

멀티캐스트 대리자 C# 1.0

왜 — 호출 목록에 여러 칸이 있는 대리자를 부르면 목록의 메서드를 차례대로, 같은 인자로 동기적으로 부릅니다. += 는 두 목록을 이은 새 대리자를 만듭니다.

마지막 두 줄: a += … 뒤에도 b 는 칸이 하나입니다. 대리자 객체는 바뀌지 않고, += 는 변수에 새 객체를 대입할 뿐입니다.

실행 검증

반환값은 마지막 것만, ref 는 이어진다

여러 칸의 대리자 호출이 값을 돌려주면 그 값은 목록의 마지막 메서드의 것입니다. ref 매개변수는 모든 호출이 같은 변수를 가리키므로 앞의 변경이 뒤로 이어집니다.

값을 모두 받으려면 GetInvocationList() 로 칸을 꺼내 하나씩 부릅니다.

실행 검증

하나가 던지면 뒤는 불리지 않는다

목록 중간의 메서드가 처리하지 않은 예외를 던지면, 예외는 대리자를 부른 쪽으로 가고 목록의 나머지는 불리지 않습니다.

실행 검증

-= 는 마지막으로 나온 것부터

대리자 제거(-)는 오른쪽의 목록이 왼쪽 목록 안에 연속으로 들어 있을 때만 그것을 뺍니다. 여러 곳에서 맞으면 마지막 것을 뺍니다. 목록이 같으면 결과는 null 입니다.

함정 — abab - (a + a) 는 아무것도 빼지 않습니다. A 가 둘 있어도 "A A" 가 연속으로 있지 않기 때문입니다. 반대로 새로 만든 new Act(A) 로도 뺄 수 있습니다 — 같은 메서드·같은 대상이면 같은 칸입니다.
실행 검증

빈 대리자는 null 이다

호출 목록이 빈 대리자는 없습니다. 마지막 칸을 빼면 null 이 되고, null 대리자를 부르면 NullReferenceException 입니다.

null 에 += 는 됩니다. 그래서 C# 1 의 이벤트는 "구독자가 없으면 null" 이고, 올리기 전에 null 을 검사해야 했습니다(다음 장).

실행 검증

이벤트 C# 1.0

왜 — 이벤트는 객체나 클래스가 알림을 주게 하는 멤버입니다. 필드처럼 선언한 이벤트는 선언한 클래스 안에서는 대리자 필드처럼 쓰이고, 처리기가 없으면 그 필드는 null 입니다.

C# 1 의 관용구 — PriceChanged h = Changed; if (h != null) h(…); 의 세 줄이 이벤트를 올리는 정석이었습니다. 이 세 줄은 뒤 버전(C# 6)의 null 조건 연산자로 한 줄이 됩니다.
실행 검증

밖에서는 += 와 -= 뿐

이벤트를 선언한 형식 밖의 코드가 할 수 있는 일은 += 와 -= 뿐입니다. 처리기를 더하고 뺄 수는 있어도 밑의 목록을 직접 얻거나 바꿀 수는 없습니다.

실행 검증

event 가 없으면 생기는 일

event 한 낱말을 빼면 같은 코드가 public 대리자 필드가 됩니다. 앞 장에서 막혔던 넷이 모두 컴파일됩니다.

함정 — = 한 글자 실수로 앞서 구독한 logger 와 saver 가 사라졌습니다. 경고도 없습니다. 아무 코드나 이벤트를 "올릴" 수도 있습니다. event 는 이 둘을 막으려고 있습니다.
실행 검증

이벤트 접근자 add·remove C# 1.0

왜 — 이벤트 선언에 add·remove 접근자를 직접 쓰면 처리기를 어디에 어떻게 둘지 스스로 정합니다. +=·-= 는 그 접근자를 부르는 것으로 바뀝니다. 필드처럼 선언한 이벤트에는 컴파일러가 저장소와 접근자를 자동으로 만듭니다.

필드처럼 선언한 Click 은 같은 이름의 private 필드와 add_Click·remove_Click 이 됩니다. 손으로 쓴 Hover 에는 필드가 생기지 않고, 저장소는 직접 둔 hover 입니다.

실행 검증

(object sender, EventArgs e) 관례

표준의 이벤트 예도 EventHandler(object sender, EventArgs e) 꼴을 씁니다. 보낸 객체와, EventArgs 를 물려받은 인자 객체 둘을 넘기는 관례입니다. 제네릭이 없던 C# 1 에서는 인자 형식마다 대리자를 새로 선언했습니다.

protected virtual void OnProgress 는 파생 클래스가 이벤트를 올리거나 가로챌 수 있게 하는 관용 자리입니다.

실행 검증

올리는 중에 구독을 끊으면

대리자 객체는 바뀌지 않으므로, 지역 변수에 복사한 목록은 이벤트를 올리는 동안 그대로입니다. 처리기 안에서 구독을 끊어도 이번 호출의 목록에는 영향이 없습니다.

C# 1 관용구의 "복사" 가 안전한 까닭이 이것입니다. 복사한 뒤 다른 곳에서 목록이 바뀌어도 손에 든 대리자는 그대로입니다.

6장 퀴즈

Q. 대리자 d 의 호출 목록이 A, B, A, B 입니다. d - (a + b) 와 d - (b + a) 와 d - (a + a) 의 목록은 각각 무엇입니까?

A. A B, A B, A B A B 입니다. 제거는 연속으로 맞는 부분 목록 가운데 마지막 것을 뺍니다. A B 는 3·4번째, B A 는 2·3번째가 빠집니다. A A 는 연속으로 들어 있지 않으므로 아무것도 빠지지 않습니다.

예외와 자원

try·catch·finally · catch 순서 · throw; 와 throw e; · finally 의 규칙 · 검사 예외가 없다 · using · lock

try·catch·finally 의 순서 C# 1.0

왜 — 예외가 나면 가장 가까운 try 의 catch 절을 위에서부터 차례로 보고, 없으면 부른 메서드로 올라가며 찾습니다. 맞는 catch 를 찾으면 그 catch 를 실행하기 전에, 그보다 안쪽 try 들의 finally 를 먼저 실행합니다.

mode 2 에서 "inner finally" 가 "outer catch" 보다 먼저 찍힙니다. "after inner try" 는 찍히지 않습니다.

실행 검증

넓은 catch 가 앞에 오면

catch 절은 쓴 차례대로 검사합니다. 그래서 앞의 catch 가 이미 잡는 형식(또는 그 파생 형식)을 뒤의 catch 가 다시 적으면 컴파일 오류입니다.

닿을 수 없는 처리기를 경고가 아니라 오류로 다룹니다. 좁은 형식을 먼저 쓰면 통과합니다.

실행 검증

throw; 와 throw e; C# 1.0

왜 — 식이 없는 throw; 는 catch 블록 안에서만 쓸 수 있고, 지금 처리 중인 예외를 다시 던집니다. throw e; 는 같은 객체를 새로 던지는 문장입니다.

함정 — throw e; 쪽 추적에는 예외가 처음 난 Parse 가 없습니다. 예외를 다시 던진 자리부터 추적이 새로 시작되기 때문입니다. 받아서 다시 던질 때는 throw; 를 씁니다.
실행 검증

return 뒤에도 finally 는 돈다

return x; 는 돌려줄 값을 먼저 계산해 두고 finally 를 실행합니다. finally 에서 지역 변수를 바꿔도 이미 정한 반환값은 그대로입니다. 반면 finally 에서 return 하거나 break 로 빠져나가는 것은 컴파일 오류입니다.

실행 검증

finally 가 던지면 원래 예외는 사라진다

finally 블록에서 예외가 나서 그 안에서 잡히지 않으면, 그 예외가 바깥으로 퍼집니다. 그때 퍼지던 다른 예외가 있었다면 그 예외는 사라집니다.

함정 — 잡힌 것은 정리 중에 난 ObjectDisposedException 뿐이고 "the real problem" 은 어디에도 남지 않았습니다. finally 의 정리 코드는 던지지 않게 써야 합니다.
실행 검증

던지고 잡을 수 있는 것은 Exception 뿐

throw 의 식은 System.Exception 으로 암시적으로 바뀔 수 있어야 합니다. catch 절이 적는 형식도 같은 규칙을 따릅니다.

실행 검증

내 예외 클래스와 InnerException

예외 클래스는 Exception 을 물려받는 보통 클래스라 필드를 더할 수 있습니다. 낮은 층의 예외를 잡아 뜻이 담긴 예외로 바꿔 던질 때 원인을 InnerException 으로 넘기면 사슬이 남습니다.

실행 검증

검사 예외가 없다

C# 의 메서드 선언에는 던질 수 있는 예외를 적는 자리가 없습니다. 부르는 쪽도 아무것도 하지 않아도 됩니다 — 컴파일러는 잠자코 있고, 실행에서 처리하지 않은 예외로 끝날 뿐입니다.

파서는 throws 를 모르는 이름으로 보고 길을 잃습니다 — 속성 접근자를 기대하다가(CS1014) 언어 버전 1 인데도 튜플(CS8124)까지 짐작합니다. 진단 문장은 지금의 Roslyn 의 것입니다.

왜 검사 예외를 넣지 않았나 — 설계자의 답

자바의 검사 예외(checked exception)를 왜 따르지 않았느냐는 물음에, 하일스버그는 두 가지를 듭니다.

인터뷰에서 — "I see two big issues with checked exceptions: scalability and versionability." (검사 예외에는 큰 문제가 둘 있습니다. 확장성과 버전 관리입니다.)
인터뷰에서 — "In a well-written application there's a ratio of ten to one, in my opinion, of try finally to try catch." (잘 쓴 응용 프로그램이라면 try finally 와 try catch 의 비율이 10 대 1 이라고 봅니다.)

같은 답에서 그는 C# 의 using 문을 "try finally 같은 것" 이라고 부릅니다. 예외는 잡는 것보다 자원을 정리하며 흘려보내는 것이 먼저라는 생각이 다음 장의 using 으로 이어집니다.

역사 근거

using 문과 IDisposable C# 1.0

왜 — using 문은 자원을 얻고, 문장을 실행하고, 자원을 처분합니다. 사용 부분은 암시적으로 finally 가 있는 try 로 감싸이고, 그 finally 가 Dispose 를 부릅니다.

예외가 나도 "c: dispose" 가 catch 의 "caught" 보다 먼저 찍힙니다 — using 의 finally 가 안쪽 try 이기 때문입니다.

실행 검증

using 을 풀어 쓰면

얻은 값이 null 이면 Dispose 를 부르지 않고 예외도 없습니다. using 의 지역 변수는 읽기 전용입니다.

실행 검증

lock 은 Monitor 의 줄임 C# 1.0

왜 — lock 은 주어진 객체의 상호 배제 잠금을 얻고, 문장을 실행하고, 잠금을 풉니다. 식은 참조 형식이어야 하고, 값 형식이면 컴파일 오류입니다. 표준은 Monitor.Enter·Monitor.Exit 와 try·finally 로 펼친 꼴을 보입니다.

표준의 지금 문장은 Monitor.Enter(x, ref __lockWasTaken) 꼴로 펼칩니다. 이 덱은 한 스레드에서 보이는 것만 캡처합니다 — 여러 스레드의 경합은 출력이 실행마다 달라 증거가 되지 못합니다.

7장 퀴즈

Q. try { return x; } finally { x = 99; } 에서 x 가 1 이었다면 메서드는 무엇을 돌려줍니까? x 가 StringBuilder 이고 finally 에서 x.Append("b") 를 한다면요?

A. 1 입니다. 반환값은 finally 전에 정해집니다. StringBuilder 라면 돌려줄 값은 같은 객체를 가리키는 참조이고, finally 가 그 객체를 고치므로 호출한 쪽은 "b" 가 붙은 내용을 봅니다.

C# 1.2 — foreach 가 정리까지

foreach 와 IDisposable · 문법 게이트 0개 · 표준의 펼친 꼴 ·

C# 1.2 한눈에

버전 기록은 C# 1.2 가 Visual Studio .NET 2003 과 함께 나왔고 "a few small enhancements" 를 담았다고 적습니다. 가장 눈에 띄는 것은 foreach 가 만드는 코드가, 열거자가 IDisposable 을 구현하면 Dispose 를 부르게 된 것입니다.

문서 근거

foreach 가 열거자의 Dispose 를 부른다 C# 1.2

왜 — 열거자는 파일·연결 같은 자원을 붙잡고 있을 수 있습니다. C# 1.2 부터 foreach 가 만드는 코드는 열거자가 IDisposable 을 구현하면 Dispose 를 부릅니다. 지금의 표준은 그것을 finally 로 적습니다.

break 로 나가도, 예외로 나가도 Dispose 가 불립니다. 예외일 때는 Dispose 가 catch 보다 먼저입니다 — foreach 의 finally 가 안쪽 try 이기 때문입니다(7장).

실행 검증

1.2 라는 언어 버전은 없다

Roslyn 의 언어 버전 목록은 CSharp1 = 1 다음이 곧 CSharp2 = 2 입니다. 그래서 앞 장의 예제도 -langversion:1 로 컴파일했는데 Dispose 가 불렸습니다. -langversion:1.2 를 주면 옵션부터 거절됩니다.

그래서 증거의 꼴은 (나) — 이 변화는 컴파일러가 언어 버전에 묶어 두지 않았습니다. Dispose 를 부르지 않던 1.0 의 동작은 지금 컴파일러로 재현할 수 없으므로, 다음 장에서 손으로 풀어 쓴 코드로 보이고 그렇다고 밝힙니다 (0부). 기능 게이트 표에서 C# 1.2 가 0 인 것도 같은 까닭입니다(0부).
실행 검증

손으로 풀어 쓴 두 foreach

같은 열거자를 두 가지로 풀어 썼습니다. 앞의 것은 finally 가 없는 꼴로, 버전 기록이 1.2 에서 생겼다고 적은 Dispose 호출이 빠져 있습니다. 뒤의 것은 표준이 적은 펼친 꼴 그대로입니다.

이것은 재현이 아니라 풀이입니다 — 위 코드는 옛 컴파일러의 출력이 아닙니다. 옛 컴파일러가 실제로 만든 IL 은 이 기계에서 볼 수 없습니다. 보이는 것은 "finally 가 없으면 Dispose 가 불리지 않는다" 는 차이뿐입니다.
실행 검증

Dispose 가 불리는 조건 — 형식이 아니라 객체

표준의 finally 는 열거자 형식 E 에 따라 셋으로 갈립니다. E 가 IDisposable 로 바뀔 수 있으면 부르고, 봉인된 형식이면 빈 finally, 그 밖이면 실행 중에 e as IDisposable 로 검사합니다.

함정 — Dispose() 라는 메서드가 있어도 IDisposable 을 구현하지 않으면 foreach 는 부르지 않습니다. 반대로 정적 형식은 Cursor 인데 실제 객체가 IDisposable 이면, 실행 중 검사로 그쪽 구현이 불립니다.
실행 검증

뒤 버전에서 — 반복기의 finally 가 이 위에 선다

C# 2 의 반복기(yield return)는 컴파일러가 만드는 열거자 클래스이고, 그 열거자는 IDisposable 입니다. 멈춰 있던 열거자의 Dispose 는 남은 finally 블록을 실행합니다. 그래서 foreach 가 break 로 일찍 끝나도 1.2 의 Dispose 호출이 반복기 안의 finally 를 실행합니다.

반복기 자체는 3부의 이야기입니다. 여기서 볼 것은 연결입니다 — break 로 나간 foreach 가 Dispose 를 부르고, 그 Dispose 가 반복기 안의 finally 를 실행합니다.

같이 온 런타임 — IEnumerator 는 IDisposable 이 아니다

이 변화가 실행 중 검사(as IDisposable)를 거쳐야 하는 까닭은 런타임의 인터페이스에 있습니다. 제네릭이 없는 IEnumerator 는 IDisposable 을 물려받지 않습니다. 이 기계의 .NET 10 에서 열거자들을 열어 봅니다.

제네릭 IEnumerator`1 은 IDisposable 을 물려받습니다(제네릭은 3부). 이 런타임에서 string 의 열거자는 IDisposable 이고, ArrayList·Hashtable·배열의 열거자는 아닙니다. Visual Studio .NET 2003 과 함께 나온 런타임의 모습은 받아 둔 문서에 없어 이 덱은 적지 않습니다.

C# 1.2 퀴즈

Q. GetEnumerator() 가 봉인되지 않은 클래스 Cursor 를 돌려줍니다. Cursor 는 public void Dispose() 를 가졌지만 IDisposable 은 구현하지 않습니다. foreach 가 break 로 끝나면 Dispose 가 불립니까? 실제 객체가 IDisposable 을 구현한 파생 클래스라면요?

A. 앞의 경우는 불리지 않습니다. foreach 의 finally 는 이름이 아니라 IDisposable 인지로 판단합니다. 뒤의 경우는 불립니다 — Cursor 가 봉인되지 않았으므로 finally 는 실행 중에 e as IDisposable 을 검사하고, 파생 클래스의 IDisposable.Dispose 를 부릅니다.
