제네릭 수학 — 연산자를 인터페이스에

static abstract · static virtual · TSelf · 제약된 호출 · INumber<T> · CreateChecked · 직접 만든 수 형식

왜 — 연산자는 static 이라 추상화할 수 없었다

제안서의 동기: "There is currently no way to abstract over static members and write generalized code that applies across types that define those static members. This is particularly problematic for member kinds that only exist in a static form, notably operators." 발표 글은 더 짧게 묻고 답합니다 — "How do you abstract over operations that are inherently static – such as operators? The traditional answer is “poorly”."

제약 없는 T 에는 + 가 없습니다. C# 2 의 제약(3부)으로는 "T 에 + 가 있다" 를 말할 길이 없었습니다. 지금의 컴파일러도 같은 CS0019 입니다 — 고치는 길은 새 연산자 문법이 아니라 새 제약입니다. 그 제약이 이 장의 주제입니다.

실행 검증

이전엔 — 연산을 값으로 넘기거나, dynamic 으로

C# 11 이전의 우회로 둘을 같은 프로그램에 담았습니다. 하나는 호출하는 쪽이 0 과 + 를 대리자로 넘기는 것, 다른 하나는 C# 4 의 dynamic(5부)으로 + 를 실행 중에 찾는 것입니다. 발표 글은 셋째 길을 "forests of overloads containing essentially the same code" 라고 부릅니다.

대리자 판은 부를 때마다 0 과 + 를 알려 줘야 합니다. dynamic 판은 알려 줄 것이 없지만 원소마다 실행 중에 연산자를 찾고, + 가 없는 DateTime 은 컴파일이 아니라 실행 중에 RuntimeBinderException 으로 무너집니다. 제네릭 수학은 이 확인을 컴파일 때로 되돌려 놓습니다.

실행 검증

인터페이스의 static abstract 멤버 (static abstract members) C# 11.0

왜 — 제안서의 요약: "An interface is allowed to specify abstract static members that implementing classes and structs are then required to provide an explicit or implicit implementation of. The members can be accessed off of type parameters that are constrained by the interface." 예제는 발표 글의 IMonoid 를 그대로 옮겼습니다.

AddAll<MyInt> 안의 T.Zero 와 += 가 MyInt 의 static 멤버로 갑니다. 원소가 없으면 T.Zero 가 그대로 결과입니다. C# 10.0 의 거절은 기능 이름이 아니라 "The modifier 'abstract' is not valid for this item" 꼴이고 선언 두 줄만 짚습니다 — 11부의 미리 보기 장에서 같은 컴파일러에 -langversion:10.0 을 주어 본 것과 같은 문장입니다.

실행 검증

필요한 연산자만 요구하는 제약 — BCL 의 수 형식에 그대로

whats-new: "you can implement the System.IAdditionOperators<TSelf, TOther, TResult> interface in a type that implements operator +. Other interfaces define other mathematical operations or well-defined values." 이 Sum 은 + 와 덧셈의 항등원(0) 두 가지만 요구합니다.

int·double·decimal·BigInteger 가 한 Sum 을 지납니다. .NET 의 수 형식들이 이 인터페이스들을 이미 구현하기 때문입니다(뒤). C# 10.0 에서는 쓰는 자리(T.AdditiveIdentity, s += x)가 'static abstract members in interfaces' 로 거절됩니다. 같은 기능이 선언 쪽(CS8703)과 쓰는 쪽(CS8936)에서 다른 번호로 거절됩니다. 10부의 예고는 INumber<T> 하나로 썼고, 여기서는 두 인터페이스만 요구했습니다.

실행 검증

TSelf — "자기 자신" 을 형식 매개변수로

발표 글: "Notice how the interface takes a type parameter for “itself”. That’s because static members don’t have a this." 제안서는 연산자의 피연산자 자리에 T 를 허락하는 조건을 적습니다 — T 가 "directly constrained by what the spec calls the "instance type"" 이어야 합니다.

함정 — where TSelf : IAdd<TSelf> 는 "TSelf 가 바로 그 구현 형식" 이라고 강제하지 않습니다. Odd : IAdd<Cm> 은 경고 없이 컴파일되고(True), Odd 는 Cm 둘을 더하는 연산자를 명시적으로 구현합니다. 제약은 Cm 이 IAdd<Cm> 이기만 하면 만족됩니다 — TSelf 는 규칙이 아니라 관례입니다.
실행 검증

클래스 계층 — static 구현은 물려받지만 TSelf 는 물려받지 않는다

제안서: static 멤버가 static abstract 멤버를 구현하는 규칙은 "the same as for instance members" 이고, 실행 때 쓰이는 구현은 "the one that exists on the actual type provided as a type argument" 입니다.

Cat 은 Animal 의 Kind 를 물려받아 "animal" 이고, 인터페이스를 다시 적은 Dog 는 자기 Kind 로 "dog" 입니다. 그러나 Sub : Base 는 IMk<Base> 일 뿐 IMk<Sub> 가 아니라서 M<Sub>() 은 제약에서 거절됩니다(CS0311). TSelf 패턴은 상속 한 단계를 넘어가지 못합니다.

실행 검증

부르는 자리 — 형식 매개변수 위에서만

제안서: "A static abstract interface member M may be accessed on a type parameter T using the expression T.M when T is constrained by an interface I". 명시적 구현은 "a qualified name along with the static modifier" 로 씁니다.

인터페이스 이름으로 부르면 CS8926 입니다 — 어느 구현인지 정해 줄 형식 인수가 없기 때문입니다. 명시적으로 구현한 Name 은 Dog 의 이름으로는 보이지 않고(CS0117) T 를 거쳐야만 불립니다. 인스턴스 멤버의 명시적 구현과 같은 규칙입니다.

실행 검증

요구할 수 있는 멤버 — 메서드부터 변환 연산자까지

제안서: "Static interface members other than fields are allowed to also have the abstract modifier." 예로 메서드·속성·이벤트· +·==·!=·implicit·explicit 변환을 듭니다. 변환 연산자를 찾는 규칙도 형식 매개변수의 "effective interface set" 까지 넓혔습니다.

제네릭 메서드 안의 T a = 5 가 인터페이스의 implicit operator T(int) 로 풀리고, a == 5 도 5 를 T 로 바꾼 뒤 T 의 == 를 부릅니다. 필드는 안 됩니다(CS0681). N 이 Equals·GetHashCode 를 함께 정의한 것은 == 를 정의하면 나는 경고 CS0660·CS0661 을 피하려는 것입니다(2부).

실행 검증

static virtual — 기본 구현이 있는 static 멤버 C# 11.0

왜 — 제안서: "Virtual static members are required to have a body." 기본 구현 절은 다른 static virtual 멤버를 인터페이스 이름이 아니라 "self" 형식 매개변수로 부르게 했습니다 — "other static virtual members could just be called on that self type".

Cm 은 기본 Twice(4 + 4 = 8)를, Loud 는 자기 Twice(-1)를 씁니다. C# 10.0 은 'virtual' 에도 CS8703 을 냅니다 — 컴파일러의 기능 목록(MessageID)에 static virtual 만의 항목은 없습니다. 기본 구현은 Cm 의 멤버가 되지 않습니다(CS0117). C# 8 의 기본 인터페이스 메서드(9부)와 같은 규칙입니다.

실행 검증

형식 인수가 될 수 없는 인터페이스 — CS8920

제안서: "An interface containing or inheriting a static abstract/virtual member that does not have most specific implementation in the interface cannot be used as a type argument. If all static abstract/virtual members have most specific implementation, the interface can be used as a type argument." 설계 회의는 이 구멍을 "type hole" 이라고 불렀습니다.

List<IHello> 는 되고, H<IHello>() 는 T.Hi 로 인터페이스의 기본 구현을 부릅니다. List<IZero<Cm>> 는 거절됩니다 — T 가 IZero<Cm> 라면 T.Zero 를 부를 구현이 어디에도 없기 때문입니다. 제약이 있든 없든, 어느 제네릭 형식의 형식 인수로도 쓸 수 없습니다.

실행 검증

작은 규칙들 — sealed, 클래스, 이름 겹침

제안서는 instance 멤버와 맞추려고 static 멤버(필드 제외)에 "an optional sealed modifier, even though they are non-virtual by default" 를 허락했습니다.

실행 검증

IL 을 들여다볼 작은 도구

다음 두 장은 컴파일러가 T.One 이나 x + y 를 무엇으로 번역하는지 IL 로 봅니다. 리플렉션으로 메서드 몸체의 바이트를 읽고, System.Reflection.Emit.OpCodes 의 표로 명령을 풀어, 형식이나 메서드를 가리키는 명령만 찍는 도구입니다.

tools/csrun 은 -optimize 없이 컴파일합니다. 그래서 보이는 것은 최적화하지 않은 IL 이고, 그중 형식·메서드를 가리키는 줄만 걸러 찍습니다.

실행 검증

제약된 호출 — constrained. T

제안서: "At runtime, the actual member implementation used is the one that exists on the actual type provided as a type argument." 그 "실제 형식" 이 IL 의 어디에 실리는지 봅니다.

T.One 과 + 는 둘 다 인터페이스의 static 메서드(INumberBase`1::get_One, IAdditionOperators`3::op_Addition)를 가리키는 call 이고, 앞에 constrained. T 접두사가 붙습니다. 어느 형식의 구현으로 갈지는 실행 때의 T 가 정합니다 — int 로 부르면 42, double 로 부르면 1.5 입니다.

실행 검증

함정 — 인터페이스 형식으로 받으면 상자가 생긴다

INumber<int> 는 형식 인수로는 못 쓰지만(앞) 매개변수 형식으로는 쓸 수 있습니다. 그때 int 는 상자에 담깁니다(3부의 박싱). 같은 비교를 두 가지로 쓰고 호출하는 쪽까지 IL 을 찍었습니다.

CallI 는 PosI 를 부르기 전에 box Int32 를 하고, PosI 안의 CompareTo 는 인터페이스를 거친 callvirt 입니다. CallG 에는 box 가 없고, PosG 의 CompareTo 앞에는 constrained. T 가 붙습니다. static 멤버는 형식 매개변수로만 부를 수 있으니(앞) 제네릭 수학은 늘 아래쪽 길을 탑니다.

실행 검증

런타임이 보는 static abstract

제안서가 적은 C# 11 이전의 규칙: "Static interface members today are implicitly non-virtual, and do not allow abstract, virtual or sealed modifiers." 런타임 쪽 표시는 9부에서 본 RuntimeFeature 목록의 VirtualStaticsInInterfaces 입니다(9부).

get_Zero 는 static 이면서 abstract·virtual 인 메서드입니다. GetInterfaceMap 은 static 슬롯도 채워 보여 줍니다. int 의 op_Addition 은 IAdditionOperators<…>.op_Addition 이라는 이름의 명시적 구현입니다 — int 에 공개 op_Addition 은 없고, int 끼리의 + 는 여전히 컴파일러가 아는 기본 제공 연산자입니다.

실행 검증

수학 밖의 쓰임 — static 팩터리

발표 글: "static virtual members are useful for other things than math. For instance you can abstract over factory methods for a hierarchy of types."

Make<T> 는 생성자가 private 인 형식도 T.Create 로 만들고, 형식의 이름 같은 static 정보도 T.Kind 로 얻습니다. C# 2 의 new() 제약(3부)이 부를 수 있는 것은 매개변수 없는 공개 생성자 하나뿐이었습니다.

문서 근거

같이 온 런타임 — .NET 7 의 수학 인터페이스 C# 11.0

발표 글: ".NET 7 comes with a new namespace System.Numerics chock-full of math interfaces … All the numeric types in .NET now implement these new interfaces – and you can add them for your own types too!" System.Int32 이 구현하는 인터페이스를 리플렉션으로 셌습니다.

int 하나가 인터페이스 32개를 구현합니다. 연산자마다 하나(IAdditionOperators, IShiftOperators …), 항등원 (IAdditiveIdentity), 범위(IMinMaxValue), 구문 분석(IParsable)이 따로 있습니다. 하나는 공개가 아닌 인터페이스입니다.

실행 검증

INumber<T> 를 통째로 구현하면 — static abstract 메서드 58개

인터페이스의 상속 사슬을 모두 모으고, 그 안의 static abstract·static virtual 메서드를 셉니다(속성 접근자와 연산자도 메서드로 셉니다).

IAdditionOperators 는 abstract 하나(op_Addition)와 virtual 하나(op_CheckedAddition — 기본 구현이 있다)입니다. INumber 는 인터페이스 24개, abstract 58개입니다. 직접 만든 형식이 INumber<T> 를 통째로 구현하려면 static 쪽만 58개를 채워야 합니다(CompareTo·Equals·ToString 같은 인스턴스 멤버는 이 셈에 없습니다). 그래서 알고리즘은 필요한 인터페이스만 요구하는 편이 낫습니다(앞, 뒤).

실행 검증

형식마다 다른 묶음 — Complex 는 INumber 가 아니다

제네릭 알고리즘이 요구하는 인터페이스가 곧 받을 수 있는 형식의 목록입니다. 대표 인터페이스 일곱을 형식 여덟에 맞춰 봤습니다.

Complex 는 일곱 가운데 INumberBase 와 ISignedNumber 뿐이고 INumber 가 아닙니다 — INumber 는 비교 연산자(IComparisonOperators)를 요구하기 때문입니다 (int 의 인터페이스 목록). 크기 한계가 없는 BigInteger 에는 IMinMaxValue 가 없습니다. char 는 부호 없는 이진 정수(IBinaryInteger·IUnsignedNumber)로 구현돼 있어, INumber<T> 를 요구하는 알고리즘에 char 가 들어갑니다.

실행 검증

TSelf·TOther·TResult — 세 자리의 연산자 인터페이스

IAdditionOperators<TSelf, TOther, TResult> 는 더하는 쪽과 결과의 형식을 따로 둡니다. 직접 만든 Day + int → Day 로 써 보고, CoreLib 의 값 형식이 이 세 자리를 어떻게 채웠는지 리플렉션으로 봅니다.

CoreLib 의 제네릭 아닌 값 형식 18개는 모두 TOther == TSelf 입니다. DateTime 은 System.Numerics 인터페이스를 하나도 구현하지 않습니다 — DateTime + TimeSpan 연산자가 있어도 이 Step 에는 넣을 수 없습니다. 세 자리가 다른 조합은 직접 만든 형식의 몫입니다.

실행 검증

다른 수에서 T 로 — CreateChecked·Saturating·Truncating

INumberBase<T> 의 static 메서드 셋은 다른 수 형식의 값을 T 로 바꿉니다. 셋은 넘치는 값을 다루는 방법만 다릅니다.

Checked 는 던지고, Saturating 은 끝값에 붙고, Truncating 은 정수끼리면 높은 비트를 버립니다(300 → 44, -5 → 251). double → int 는 셋 다 소수부를 버리는데, 1e10 은 Truncating 도 2147483647 이고 NaN 은 0 입니다 — 부동소수점에서 온 Truncating 은 이름과 달리 끝값에 붙습니다.

실행 검증

제네릭 코드 안의 숫자 상수 — 2 는 T 가 아니다

제네릭 코드에서 T 를 다룰 때 가장 먼저 걸리는 것은 리터럴입니다. 평균을 내려면 개수(int)로 나눠야 하고, 절반을 내려면 2 로 나눠야 합니다.

x / 2 는 T 와 int 사이의 / 를 찾다 실패하고(CS0019), (T)2 같은 캐스트도 없습니다 (CS0030). 상수는 T.One + T.One 이나 T.CreateChecked(2) 처럼 T 의 static 멤버로 만듭니다. int 의 평균은 정수 나눗셈이라 2 입니다.

실행 검증

INumberBase 의 static 도우미 — Abs·IsNegative·Radix

예전 같으면 Math.Abs 의 오버로드 숲이었을 것들이 T.Abs(x) 처럼 형식으로 부르는 static 멤버가 됐습니다.

decimal 의 Radix 는 10, 나머지는 2 입니다. Complex 의 Abs 는 크기 5 이고, MaxMagnitude(x, 1) 은 크기가 큰 쪽을 그대로 돌려줍니다(-7 은 -7). Half -0.5 와 1 에서는 1 입니다.

실행 검증

부동소수점만의 인터페이스 — IRootFunctions·IFloatingPointConstants

제곱근이나 π 처럼 정수에는 없는 것은 따로 인터페이스가 있습니다. 필요한 것만 요구하면 double·float·Half 가 한 소스로 돕니다.

세 형식 모두 5 이고, π 는 형식마다 자기 정밀도입니다(Half 는 3.14). int 로 부르면(-define:BAD) int 가 IRootFunctions<int> 가 아니라서 CS0315 로 거절됩니다. 이 오류 줄은 200칸을 넘어 캡처로 싣지 못했고, 실험 묶음이 매번 종료 코드와 번호만 확인합니다.

실행 검증

제네릭 코드 안의 checked — op_CheckedAddition 으로

제네릭 코드의 checked(a + b) 는 인터페이스의 checked 연산자를 부릅니다. 5장의 checked 사용자 정의 연산자(5장)가 제네릭 수학에 필요했던 까닭이 여기 있습니다.

int 는 기본 문맥에서 감싸 돌고 checked 에서 던집니다. double 은 checked 에서도 Infinity 입니다. + 만 정의한 W 는 checked(a + b) 에서도 [W.+] 를 찍습니다 — op_CheckedAddition 이 virtual 이고 기본 몸체가 보통 + 로 되돌아가기 때문입니다(앞의 셈: abstract 1, virtual 1).

실행 검증

함정 — T.Parse 에는 인수 하나짜리가 없다

IParsable<T> 는 수 밖의 형식도 구현하는 구문 분석 인터페이스이고, INumberBase<T> 는 NumberStyles 판을 더합니다.

int.Parse("12") 처럼 형식에 직접 있는 한 인수 판은 인터페이스에 없습니다. 그래서 T.Parse(s) 는 CS1501 이고, IFormatProvider 를 함께 넘겨야 합니다. DateOnly·TimeSpan 같은 수 아닌 형식도 같은 P<T> 를 지납니다.

실행 검증

함정 — T 에는 숫자 상수 패턴을 쓸 수 없다

제안서: T : INumberBase<T> 에 t is 1 을 쓰면 "the constant 1 pattern will first type check the incoming T against int. This is unintuitive, so it is blocked".

-define:BAD 의 t is 1 은 CS9060 으로 막힙니다(오류 줄이 200칸을 넘어 캡처 대신 실험 묶음이 번호를 확인합니다). 막지 않았다면 무슨 일이 났을지는 object 로 받은 BoxedOne(1.0) 이 보여 줍니다 — "int 1 인가" 를 물어 False 입니다.

실행 검증

직접 만든 수 형식 — 필요한 인터페이스 넷만

발표 글의 말대로 "you can add them for your own types too" 입니다. 7 로 나눈 나머지의 수 Mod7 은 INumber<T> 의 58개 대신 알고리즘이 쓰는 넷만 구현합니다.

Mod7 이 int·double·BigInteger 와 나란히 같은 Sum·Pow 를 지납니다. 5 + 4 = 9 ≡ 2, 36 = 729 ≡ 1 (mod 7) 입니다.

실행 검증

제네릭 수 위의 제네릭 형식 — Vec2<T>

수 형식을 받는 쪽만이 아니라 만드는 쪽도 제네릭이 될 수 있습니다. Vec2<T> 는 T 의 +·* 로 자기 연산을 정의합니다.

Vec2<T> 는 자신도 IAdditionOperators 를 구현해 앞의 Sum 에 그대로 들어갑니다. int·double· decimal 벡터가 한 소스에서 나옵니다.

실행 검증

4장의 거절 모음

실험 묶음이 각 거절 캡처의 첫 오류 줄에서 뽑은 표입니다. C# 10.0 의 거절이 선언 쪽은 CS8703("modifier … not valid"), 쓰는 쪽은 CS8936("Feature …")으로 갈린다는 점과, 나머지는 모두 C# 11.0 으로 컴파일해도 나는, 새 기능을 잘못 쓴 자리의 거절이라는 점을 봅니다.

실행 검증

4장 퀴즈 — 제네릭 수학

Q. static T Half<T>(T x) where T : INumber<T> => x / 2; 는 왜 컴파일되지 않고, 어떻게 고칩니까?

A. 2 는 int 이고 T 와 int 사이의 / 가 없어서 CS0019 입니다. (T)2 캐스트도 CS0030 입니다. T.CreateChecked(2) 나 T.One + T.One 으로 2 를 T 로 만들어 나눕니다(앞).
설명용

5장

연산자와 정수 — 제네릭 수학이 요구한 것

checked 연산자 · >>> · 시프트의 둘째 피연산자 · 숫자형 IntPtr

왜 — "Generic math created other requirements on the language"

whats-new 는 4장의 static abstract 멤버 다음에 이 문장을 적고 언어 기능 셋을 더 꼽습니다. 각 제안서의 동기는 모두 제네릭 수학 인터페이스에서 출발합니다.

기능제안서의 동기
checked 사용자 정의 연산자"impossible to expose a type such as Int128 or UInt128 without the language simultaneously shipping its own support"
부호 없는 오른쪽 시프트 >>>"the type might not necessary have an unsigned counterpart defined or known upfront by the generic math code"
시프트 연산자 요구 완화"the conversion to int may not be possible or even well-defined"

숫자형 IntPtr(뒤)는 언어 기능이라기보다 런타임의 변화입니다. 이 장의 끝에서 봅니다.

문서 근거

checked 사용자 정의 연산자 (checked user-defined operators) C# 11.0

왜 — 제안서: "There is no way for a user to declare a type and support both checked and unchecked versions of an operator." 그래서 operator 뒤에 checked 를 붙인 판을 따로 선언하게 했습니다. checked 판은 넘치면 던지고, 보통 판은 "a truncated result" 를 돌려주리라고 가정합니다.

이전엔 — C# 1 부터 checked 문맥은 기본 제공 정수 연산의 넘침만 바꿨습니다(2부). 사용자 정의 연산자는 문맥과 상관없이 하나뿐이었습니다.
실행 검증

-checked 스위치 — 기본 문맥이 바뀌면 고르는 연산자도 바뀐다

2부에서 본 csc 의 -checked 스위치(2부)는 표시가 없는 식의 문맥을 checked 로 바꿉니다. 같은 소스를 그 스위치로 돌립니다.

이번엔 맨 처음의 x + y 부터 op_CheckedAddition 이 불려 처리되지 않은 예외로 끝납니다. 사용자 정의 연산자도 기본 제공 연산처럼 빌드 설정에 따라 다른 메서드로 컴파일된다는 뜻입니다.

실행 검증

짝 규칙 — checked 판만 둘 수는 없다

제안서: "a checked operator declaration requires a pair-wise declaration of a regular operator (the return type should match as well)." checked 문맥에서는 checked 판과, 짝이 없는 보통 판이 후보입니다.

checked(x - y) 는 checked 판이 없으니 보통 - 로 되돌아가 246 입니다 — 예외가 없습니다. checked 판만 있는 * 는 CS9025 로 거절됩니다.

실행 검증

checked 명시적 변환 — implicit 은 안 된다

명시적 변환 연산자도 checked 판을 가질 수 있습니다. 암시적 변환은 제외됐습니다 — "In general, implicit conversion operators are not supposed to throw."

200 은 보통 판에서 -56, checked((sbyte)…) 에서는 넘침입니다. implicit operator checked 는 CS9024 입니다.

실행 검증

함정 — checked 연산자의 몸체는 checked 문맥이 아니다

제안서: "Checked/unchecked context within the body of a checked operator is not affected by the presence of the checked keyword. In other words, the context is the same as immediately at the beginning of the operator declaration."

기본 빌드에서는 [checked +] 가 불렸는데도 -2147483648 입니다 — 몸체 안의 int 덧셈은 기본 문맥(unchecked)입니다. 프로젝트 전체를 -checked+ 로 빌드해야 같은 몸체가 던집니다. checked 판의 몸체에는 checked(…) 를 직접 적어야 합니다.

실행 검증

메타데이터 이름과 식 트리

제안서는 ECMA-335 의 연산자 이름에 op_CheckedIncrement·op_CheckedUnaryNegation·op_CheckedAddition·op_CheckedExplicit 등을 더했고, 식 트리에서는 AddChecked 같은 팩터리를 MethodInfo 와 함께 쓰기로 했습니다.

연산자마다 op_… 와 op_Checked… 가 짝으로 생깁니다(2부의 op_ 이름). 식 트리의 checked(a + b) 는 AddChecked 노드이고 그 메서드가 op_CheckedAddition 입니다.

실행 검증

함정 — dynamic 은 checked 연산자를 고르지 않는다

제안서의 dynamic 절은 약속이 아니라 계획입니다 — "We will investigate the cost of adding support for checked operators in dynamic invocation in CoreCLR and pursue an implementation if the cost is not too high."

함정 — dynamic 으로 묶인 checked(d + y) 는 보통 + 를 불러 44 를 냅니다. 같은 런타임 바인더가 int 의 checked 는 지킵니다(int Overflow, 5부) — 사용자 정의 checked 연산자만 .NET 10 의 바인더에 닿지 않습니다.
실행 검증

같이 온 런타임 — Int128 과 BCL 의 checked 연산자 C# 11.0

제안서가 이 기능 없이는 내놓을 수 없다고 한 형식이 Int128·UInt128 입니다. CoreLib 에서 checked 연산자를 공개 메서드로 선언한 형식을 리플렉션으로 찾았습니다.

공개 checked 연산자를 가진 형식은 넷 — Half·Int128·NFloat·UInt128 입니다. int 같은 기본 제공 형식은 인터페이스의 checked 연산자를 명시적으로 구현할 뿐 공개 메서드로 두지 않습니다(4장). 언어가 직접 아는 형식이 아니라서 연산자를 메서드로 가져야 하는 형식들입니다.

실행 검증

부호 없는 오른쪽 시프트 >>> (unsigned right shift) C# 11.0

왜 — 제안서: 부호 있는 정수를 높은 비트 복제 없이 밀려면 "a cast to an unsigned type before the shift operation and a cast back after it is required". >>> 는 "the high-order empty bit positions are set to zero" 이고 상수식에도 쓸 수 있습니다.

-8 >> 1 은 부호 비트를 채워 -4, -8 >>> 1 은 0 을 채워 2147483644 입니다(두 이진 줄의 첫 자리). nint(60번 밀어 15)와 int?(올린 꼴)에도 있습니다. C# 10.0 은 >>> 가 여러 번 나와도 첫 자리(const) 하나만 짚었습니다.

실행 검증

이전엔 캐스트 두 번 — 그리고 작은 형식의 함정

whats-new: "Before C# 11, to force an unsigned right-shift, you would need to cast any signed integer type to an unsigned type, perform the shift, then cast the result back to a signed type." 제안서는 >>> 의 왼쪽 피연산자도 int·uint· long·ulong 중 하나로 올린다고 적습니다.

함정 — sbyte -8 의 >>> 1 은 8비트 답 124 가 아니라 2147483644(Int32)입니다. int 로 올린 뒤 32비트에서 밀기 때문입니다. 8비트 답은 여전히 byte 로 바꿔 >> 해야 나옵니다. 시프트 횟수도 >> 처럼 & 31 로 잘립니다 (1 >>> 33 은 0, 2부).
실행 검증

사용자 정의 >>> — 예약돼 있던 op_UnsignedRightShift

제안서: >>> 는 오버로드할 수 있는 이항 연산자가 되고, 메타데이터 이름은 ECMA-335 가 이미 예약해 둔 op_UnsignedRightShift 입니다. Roslyn 의 호환성 문서는 그 결과 다른 언어로 만든 op_UnsignedRightShift 를 메서드로 부르던 코드가 CS0571 이 된다고 적습니다.

Word 는 자기 폭(16비트)에서 0 을 채우므로 -8 의 >>> 1 이 32764 입니다 — 앞 장의 승격 함정이 없습니다. 복합 대입 >>>= 도 따라옵니다.

실행 검증

식 트리와 dynamic 에는 없는 >>>

제안서: 식 트리는 "semantics of predefined >>> operators on signed types cannot be accurately represented without adding conversions to an unsigned type and back" 이라서 지원하지 않고, dynamic 도 ExpressionType 에 해당 값이 없어 지원하지 않습니다.

대리자로 컴파일하는 람다는 되지만, 식 트리는 CS7053, dynamic 은 컴파일 때 바로 CS0019 입니다 — 실행 중에 조용히 보통 연산자로 가는 checked 연산자와 달리 컴파일러가 거절합니다.

실행 검증

시프트 연산자의 둘째 피연산자 — int 가 아니어도 C# 11.0

왜 — 제안서: 시프트 횟수가 "the result of another computation, such as shifting based on the leading zero count" 인 경우가 흔하고, 그 결과의 자연스러운 형식은 입력과 같은 형식입니다. 그래서 둘째 피연산자가 int 여야 한다는 제한만 지웠습니다.

1011 이 64비트의 맨 위로 올라갑니다(선행 0 은 60개). 횟수가 Big 이라 int 로 바꾸는 캐스트가 없습니다. 첫 피연산자가 그 형식이어야 한다는 제한은 남았습니다(다음 장).

실행 검증

제안서가 걱정한 쓰임 — cout << "string"

제안서의 단점 절: "Users will be able to define operators that do not follow the recommended guidelines, such as implementing cout << "string" in C#." 남은 규칙은 "the restriction that the first operand be the class or struct containing the operator declaration remains" 입니다.

C# 11 에서는 정말로 됩니다. 시프트의 후보 연산자는 왼쪽 형식에서만 찾으므로 "x" << cout 은 CS0019 입니다.

실행 검증

BCL 의 IShiftOperators — 횟수는 그래도 int

제안서가 든 동기(TSelf 형식의 선행 0 개수로 밀기)를 BCL 의 인터페이스로 써 봅니다. .NET 의 시프트 인터페이스가 둘째 자리에 무엇을 뒀는지도 봅니다.

BCL 의 정수 형식은 모두 IShiftOperators<TSelf, Int32, TSelf> 입니다. 그래서 T.LeadingZeroCount(x)(형식 T)를 int.CreateChecked 로 바꿔야 합니다. 둘째 피연산자의 해방은 BCL 이 아니라 직접 만든 형식(앞)에서 쓰입니다.

실행 검증

숫자형 IntPtr — nint 는 System.IntPtr 의 별칭 C# 11.0

whats-new: "The nint and nuint types now alias System.IntPtr and System.UIntPtr, respectively." 제안서는 int 와 System.Int32 의 관계와 같다고 하고, 그 동작을 켜는 것이 "The System.Runtime.CompilerServices.RuntimeFeature.NumericIntPtr runtime feature flag" 라고 적습니다.

세 언어 버전의 출력이 같습니다. C# 9 의 명세는 nint.Zero·nint.Size 를 "explicitly excluded" 라고 적었지만 , .NET 10 을 대상으로 하면 -langversion:9.0 에서도 보입니다. 바뀐 것을 정하는 것은 언어 버전이 아니라 대상 런타임의 플래그입니다(10부, 10부의 IntPtr 산술).

실행 검증

IntPtr 도 checked 에서 넘친다 — C# 8.0 으로 컴파일해도

Roslyn 의 .NET 7 호환성 문서: 숫자형 IntPtr 플랫폼에서는 "IntPtr and UIntPtr have built-in checked operators, which can now throw when an overflow occurs." 예제의 Add 는 문서의 예 그대로입니다.

10부는 C# 9.0 의 nint 로 같은 넘침을 봤습니다. 여기서는 한 걸음 더 내려 nint 가 없던 C# 8.0 으로 컴파일해도 IntPtr + int 와 (int)IntPtr 가 checked 에서 던집니다. 호환성 문서가 권하는 길은 unchecked 를 적거나 숫자형 IntPtr 이 없는 대상으로 내리는 것입니다.

실행 검증

깨지는 변경 — UIntPtr + int 는 이제 모호하다

호환성 문서: 숫자형 IntPtr 플랫폼에서는 "the operator +(UIntPtr, int) defined in System.UIntPtr can no longer be used" — 대신 "Operator '+' is ambiguous on operands of type 'nuint' and 'int'" 입니다. 고치는 길로 UIntPtr.Add 와 unchecked((nuint)y) 를 듭니다.

거절 문장이 C# 8.0 에서도 'nuint' 라는 이름을 씁니다 — 그 버전에는 없는 낱말인데, 컴파일러가 숫자형 UIntPtr 를 그렇게 부르기 때문입니다. 이 거절도 언어 버전이 아니라 대상 런타임에 묶여 있습니다.

실행 검증

dynamic 이 아는 IntPtr 연산 — 형식에 선언된 것만

C# 9 의 명세는 nint 의 연산자가 컴파일러가 만드는 것이라 런타임 바인더에는 없다고 적었습니다. 10부가 그 동작을 확인했고, 여기서는 무엇이 바인더에 보이는지를 리플렉션으로 봅니다.

IntPtr 형식에 실제로 선언된 + 는 op_Addition(IntPtr, Int32) 하나입니다. 그래서 d + 1 은 되고 d + x (IntPtr + IntPtr)는 실행 중에 거절됩니다. 숫자형 IntPtr 로 바뀐 것은 정적 컴파일러가 아는 연산이고, 런타임 바인더의 눈에는 그대로입니다.
