컬렉션 식 — 대괄호 하나로 모든 컬렉션을

[1, 2, 3] · 대상 형식 · 빈 [] · 펼침 ..e · [CollectionBuilder] · 오버로드 · 할당과 IL · 스팬

왜 — 컬렉션마다 만드는 문법이 달랐다

발표 글: "Prior to C# 12, creating collections required different syntax for different scenarios. Initializing a List<int> required different syntax than an int[] or Span<int>." 제안서는 문법의 가짓수만이 아니라 성능도 짚습니다 — 컬렉션 초기화자는 "can cause multiple reallocations of memory because they use N .Add invocations without supplying an initial capacity" 입니다.

배열은 new int[] { … }·new[] { … }, 빈 배열은 Array.Empty<int>(), 목록은 new() { … }, 스택의 스팬은 stackalloc 입니다. byte[] 인수에는 원소마다 (byte) 캐스트가 붙었습니다 — new[] 가 원소에서 형식을 유추하기 때문입니다.

실행 검증

컬렉션 식 (collection expressions) C# 12.0

왜 — 제안서의 요약: "Collection expressions introduce a new terse syntax, [e1, e2, e3, etc], to create common collection values." 배열·Span<T>·ReadOnlySpan<T>·컬렉션 초기화자를 받는 형식은 "without requiring external BCL support" 로 만들 수 있습니다. 그리고 "Collection literals are target-typed" — 무엇을 만들지는 받는 쪽이 정합니다.

같은 […] 가 다섯 가지 형식이 됩니다. WriteBytes([1, 2, 3]) 에는 캐스트가 없습니다 — 원소가 매개변수의 원소 형식 byte 로 바로 바뀝니다. C# 11.0 의 거절은 대괄호마다 하나씩, 안쪽 대괄호까지 일곱 개입니다. 0부의 게이트 예제가 바로 이 기능이었습니다.

실행 검증

대상이 인터페이스면 — 실제로 무엇이 만들어지나

제안서: 읽기 전용 인터페이스(IEnumerable<T>·IReadOnlyCollection<T>·IReadOnlyList<T>)가 대상이면 구현은 "free to" 기존 형식을 쓰거나 형식을 합성할 수 있습니다. 바꿀 수 있는 ICollection<T>·IList<T> 이면 "The value must be an instance of List<T>." 입니다.

읽기 전용 인터페이스 셋은 컴파일러가 이 어셈블리 안에 합성한 <>z__ReadOnlyArray`1 이고, 바꿀 수 있는 둘은 보통의 List`1 입니다. 같은 식이 대상 형식에 따라 다른 형식의 객체가 됩니다.

실행 검증

합성된 읽기 전용 형식 — 바꾸는 창은 있지만 던진다

제안서의 요구: 합성 형식은 ICollection<T>·IList<T> 와 제네릭 아닌 ICollection·IList 까지 구현하고, IsReadOnly·IsFixedSize 는 true, "The value must throw on any call to a mutation method" 입니다. 데이터 바인딩 같은 "dynamic introspection" 을 위해서입니다.

세 속성이 모두 True, Add 는 NotSupportedException 입니다. 인터페이스는 여덟 개입니다 — 제안서가 꼽은 일곱(제네릭 다섯과 제네릭 아닌 ICollection·IList)에 그 기반인 IEnumerable 이 더해졌습니다. 제안서가 "ensures maximal compatibility with existing libraries" 라며 권하는 그대로입니다. IList<int> 대상은 진짜 List<int> 라서 Add 가 됩니다.

실행 검증

빈 컬렉션 식 [] — 언제 같은 객체를 다시 쓰나

제안서의 결정: "The compiler should emit Array.Empty<T>() for any case where this is legal and the final result is non-mutable." ICollection<T>·IList<T> 처럼 바꿀 수 있는 대상에는 쓰지 않습니다. List<int> z = []; 는 "Must not be a singleton" 입니다.

int[] 와 IEnumerable<int> 의 [] 는 Array.Empty<int>() 와 같은 객체입니다 — 원소가 있으면 합성 형식이던 IEnumerable 이 비었을 때는 Int32[] 입니다. List·IList 는 부를 때마다 새 객체입니다.

실행 검증

자연 형식이 없다 — var 도, 점(.)도 안 된다

제안서: "A collection expression does not have a natural type" 이라서 확장 메서드의 첫 인수로 바로 쓸 수 없습니다. var v = []; 도 "illegal" 입니다. 발표 글은 "support for var (natural types)" 를 다음 버전의 검토 거리로 남겼습니다.

셋 모두 같은 CS9176 입니다. 고치는 길은 대상 형식을 주는 것 — 변수의 형식을 적거나 (int[])[1, 2, 3] 처럼 캐스트합니다. 캐스트 뒤의 [ 가 원소 접근으로 읽히지 않는 것도 확인됩니다.

실행 검증

함정 — Enumerable.Sum([1, 2, 3]) 는 C# 12 에서 모호하다

C# 12 의 규칙은 대상이 둘 다 스팬이 아니면 "an implicit conversion exists from T₁ to T₂" 일 때만 한쪽을 낫다고 봅니다. C# 13 은 원소 형식의 변환까지 비교하는 규칙으로 바꿨습니다(14부) — "improves overload resolution to account for the element type of collection expressions".

IEnumerable<int> 와 IEnumerable<double> 사이엔 변환이 없어서(값 형식엔 공변성이 없다) C# 12 는 int·long· float·double·decimal 판 중 어느 것도 고르지 못합니다. 같은 컴파일러가 -langversion:13.0 에서는 원소 1, 2, 3 이 int 와 정확히 맞는 판을 골라 6 을 냅니다 — 언어 버전으로 갈리는 동작입니다(코드는 앞 장).

실행 검증

형식 유추 — 원소에서 T 를 찾는다

제안서는 형식 유추의 첫 단계에 규칙을 더했습니다. 컬렉션 식의 원소마다 매개변수의 원소 형식 쪽으로 유추하고, 펼침 요소는 "a lower-bound inference is made from Sᵢ to Tₑ" 입니다. 예제의 AsArray·AsListOfArray 는 제안서의 것입니다.

[1L, 2] 는 long 과 int 에서 T = long 을 고르고, 바깥 List<T[]> 안의 [] 도 int[] 가 됩니다. 원소가 하나도 없으면 유추할 재료가 없어 CS0411 입니다.

실행 검증

들쭉날쭉 배열은 되고 다차원 배열은 안 된다

제안서: "There is no collection expression conversion from a collection expression to a multi dimensional array type." 대괄호 안에 대괄호를 쓰면 배열의 배열, 목록의 목록이 됩니다.

컴파일러는 int[,] 를 int[*,*] 로 적고 "not constructible" 이라 합니다. 2차원 배열은 C# 1 의 { { 1, 2 }, { 3, 4 } } 가 여전히 유일한 초기화 문법입니다.

실행 검증

펼침 요소 ..e (spread element) C# 12.0

whats-new: "The spread element, ..e in a collection expression adds all the elements in that expression. The argument must be a collection type." 발표 글은 "The implementation of any spread expression is optimized, and will often be better than the code you might write to combine collections." 라고 적습니다.

펼칠 수 있는 것은 foreach 로 돌 수 있는 것 전부입니다. 거절 문장도 그 말을 합니다 — int 에는 GetEnumerator 가 없다. [.. all] 로 만든 copy 는 새 목록이라 Add 해도 all 은 그대로 6개입니다.

실행 검증

원소를 계산하는 차례 — 펼침은 언제 도나

제안서: 원소는 "evaluated in order, left to right" 이고, 다만 "A spread element may be iterated before or after the subsequent elements in the collection expression are evaluated." 입니다. 또 컬렉션 초기화자와 달리 "element evaluation and Add calls are not necessarily interleaved" 입니다.

지금의 컴파일러는 배열이든 List 든 Gen() 을 그 자리에서 끝까지 돌린 뒤 Log(2) 를 부릅니다. 명세는 이 차례를 약속하지 않습니다 — 반복기 안의 부수 효과에 기대는 코드는 명세 밖에 있습니다.

실행 검증

.. 으로 시작하면 언제나 펼침 — 범위와의 모호함

제안서: .. expr 는 펼침 요소로도, C# 8 의 범위 식으로도 읽힐 수 있습니다. 규칙은 하나 — "if the element lexically starts with .. then it is always treated as a spread_element". 그래서 ..x ? y : z 는 .. (x ? y : z) 입니다.

범위를 원소로 넣으려면 괄호로 감싸거나 1..3 처럼 앞을 채웁니다. [..2] 는 Range[] 대상이라도 "2 를 펼쳐라" 로 읽혀 CS9212 입니다. 원소 자리의 .. 하나만 쓰면 피연산자가 없어 구문 오류이므로 "처음부터 끝까지" 범위는 (..) 로 적었습니다.

실행 검증

조건부로 펼치기 — 두 갈래가 다 컬렉션 식이면 형식이 없다

제안서는 빈 리터럴을 펼치는 예로 List<int> l = [x, y, .. b ? [1, 2, 3] : []]; 를 들고, b 가 거짓이면 빈 컬렉션을 만들지 않아도 된다고 적습니다. 그 꼴을 그대로 써 봤습니다.

함정 — 펼침의 피연산자에는 대상 형식이 없습니다. ?: 의 두 쪽이 모두 컬렉션 식이면 CS0173 이고, C# 14 에서도 같습니다. 한쪽에 형식이 있는 식(Verbose 배열)을 두면 됩니다. 대상이 있는 자리 — switch 식의 갈래나 int[] s = … ? [x] : [] — 에서는 갈래마다 컬렉션 식을 써도 됩니다.
실행 검증

내 형식에 [CollectionBuilder] (create methods) C# 12.0

왜 — 배열·스팬·컬렉션 초기화자 형식 밖의 컬렉션을 위해 제안서는 "a new attribute and API pattern that can be adopted directly on the type itself" 를 둡니다. 특성이 빌더 형식과 메서드 이름을 가리키고, 그 메서드는 "a single parameter of type System.ReadOnlySpan<E>, passed by value" 를 받는 static 메서드입니다.

세 컬렉션 식마다 Create 가 한 번씩 불립니다. Bag 에는 Count 가 없어 [.. a, .. more] 의 길이를 미리 알 수 없는데도 빌더는 원소 5개짜리 스팬을 받습니다 — 모으는 일은 컴파일러가 하고 빌더는 완성된 스팬만 봅니다. 빈 [] 도 Create(0) 를 부릅니다. 빌더의 Create<T> 에는 대상 형식의 형식 인수가 차례대로 들어갑니다.

실행 검증

빌더 메서드의 규칙 — 이름과 ReadOnlySpan

제안서의 조건: 특성에 적힌 이름, 빌더 형식에 직접 선언, static, 접근 가능, 대상 형식과 같은 형식 매개변수 수, ReadOnlySpan<E> 매개변수 하나, 그리고 반환 형식에서 대상 형식으로의 항등·참조·박싱 변환. "An error is reported if the [CollectionBuilder] attribute does not refer to an invokable method with the expected signature."

두 거절이 같은 CS9187 이고 문장이 기대한 시그니처를 그대로 알려 줍니다. 오류는 특성이 아니라 컬렉션 식을 쓴 줄(33행)에 붙습니다 — 아무도 […] 로 만들지 않으면 잘못된 특성도 조용히 지나갑니다.

실행 검증

불변 컬렉션 — ImmutableArray.Create(...) 대신 [..]

제안서의 동기: 불변 컬렉션은 "require syntax like ImmutableArray.Create(...) to initialize the values, and which can cause intermediary allocations and data copying." 제안서는 ImmutableArray<T> 의 빌더를 예로 들고, [1, 2, 3] 이 인라인 배열 위의 스팬으로 Create 를 부를 수 있다고 적습니다.

.NET 10 의 불변 컬렉션들은 이미 빌더를 달고 있어 […] 가 그대로 됩니다. 인터페이스 IImmutableList<int> 를 대상으로 해도 빌더가 정한 ImmutableList`1 이 나옵니다. [.. ia, 4] 는 새 배열을 만들고 ia 는 3개 그대로입니다. 어떤 BCL 형식이 빌더를 가졌는지는 뒤에서 셉니다.

실행 검증

인터페이스에 붙인 빌더 — 구현 형식은 숨긴다

제안서: 특성은 "a class, struct, ref struct, or interface" 에 붙일 수 있고, 빌더의 반환 형식에서 대상 형식으로의 변환은 참조 변환이어도 됩니다.

호출하는 쪽은 ISeq<int> 만 알고 [1, 2, 3]·Total([4, 5]) 로 값을 만듭니다. 실제 형식 ArraySeq`1 은 빌더 안에 숨어 있습니다. ArraySeq 는 기본 생성자로 스팬을 받아 바로 배열로 옮깁니다 — 스팬은 필드에 담을 수 없습니다.

실행 검증

컬렉션 초기화자 형식 — IEnumerable 과 Add

제안서: System.Collections.IEnumerable 을 구현한 클래스·구조체는 인수 없는 생성자가 있고, 원소가 있으면 "an instance or extension method Add" 가 있을 때 대상이 됩니다. C# 3 의 컬렉션 초기화자와 같은 조건입니다.

Log 는 new Log() 뒤에 Add 두 번입니다. HashSet 은 Add 가 중복을 버려 3개가 아니라 2개입니다 — 컬렉션 식이 원소 수를 정하지 않습니다. IEnumerable 이 없으면 Add 가 있어도 "not constructible"(CS9174)입니다.

실행 검증

깨지는 변경 — string 은 대상이 아니다

Roslyn 의 호환성 문서(VS 17.10): IEnumerable 을 구현하고 빌더가 없는 대상은 "an accessible constructor that can be called with no arguments" 와 Add 가 있어야 변환이 존재합니다. 전에는 이 조건이 변환이 아니라 생성 단계에만 있어서 Print(['a', 'b', 'c']) 가 char[] 와 string 사이에서 모호했습니다.

지금은 char[] 판이 골라집니다. 문자열은 펼칠 수는 있습니다([.. "hey", '!']) — IEnumerable<char> 이기 때문입니다. -define:BAD 의 string s = ['a', 'b'] 는 CS1729(인수 없는 생성자 없음)와 CS1061(Add 없음) 두 줄로 거절됩니다 — 실험 묶음이 번호를 확인하지만, 둘째 줄이 200칸을 넘어 캡처는 싣지 않았습니다.

실행 검증

깨지는 변경 — 원소는 object 로 바뀌어야 한다

호환성 문서(VS 17.10): 강한 형식의 GetEnumerator() 가 없는 IEnumerable 대상이면 원소가 object 로 암시적으로 바뀌어야 합니다. 그래서 문서의 Actions a = [_ => { }]; 는 CS8917 이고, 고치는 길로 매개변수에 형식을 적거나 캐스트하라고 합니다.

컬렉션 식의 원소 형식은 Add 의 매개변수가 아니라 반복 형식(여기선 object)입니다. 같은 람다가 C# 3 의 컬렉션 초기화자 new Actions { x => … } 에서는 됩니다 — 초기화자는 원소마다 Add 를 바로 고르기 때문입니다. 두 문법이 같은 형식에 다르게 반응합니다.

실행 검증

길이를 알면 capacity — List 는 받고 내 형식은 못 받는다

제안서의 길이를 아는 번역: 대상 형식에 "an accessible constructor with a single parameter int capacity" 가 있으면 new T(capacity: __len) 으로 만든다고 적습니다(매개변수 이름이 capacity 여야 한다).

함정 — 지금의 컴파일러는 직접 만든 Box 의 Box(int capacity) 를 부르지 않습니다. 길이가 3 으로 정해진 [1, 2, 3] 에서도 Box() 입니다. 반면 List<int> 는 원소 5개짜리 컬렉션 식에서 Capacity 가 정확히 5 이고, 컬렉션 초기화자는 Add 가 4 → 8 로 늘린 8 입니다. 명세의 "translated as" 는 허용된 번역의 하나일 뿐 — List 가 어떻게 만들어지는지는 IL 에서 봅니다.
실행 검증

펼침과 Add — AddRange 가 있어도 하나씩

제안서는 펼침 요소를 넣는 길로 원소마다 Add, 또는 "An applicable AddRange instance or extension method" 를 허락하고 , 결정 사항에서 "An implementation should take advantage in the cases where there are no downsides. For example, with an .AddRange(ReadOnlySpan<T>) method." 라고 적습니다.

[0, .. xs] 는 Add 세 번입니다 — IEnumerable<int> 를 받는 AddRange 는 쓰이지 않았습니다. 사용자 형식의 메서드가 "well behaved" 인지 컴파일러는 알 수 없으니, 지금의 구현은 명세가 허락한 가장 보수적인 길을 갑니다.

실행 검증

사전은 아직 — Add(key, value) 는 원소 하나가 아니다

발표 글: "We are considering expanding collection expressions to include dictionaries … in a future version of C#." C# 12 의 조건은 "an instance or extension method Add … invoked with a single value argument" 입니다.

빈 [] 는 Add 가 필요 없어 됩니다. KeyValuePair 를 받는 Add 는 Dictionary 에서 명시적 인터페이스 구현이라 보이지 않아 CS9215 입니다. 그런데 .NET 10 의 ImmutableDictionary 는 KeyValuePair 를 원소로 받는 빌더를 가져서 C# 12 로도 됩니다 — 같은 키 "a" 가 두 번이면 뒤의 값 2 가 남습니다. FrozenDictionary 도 빌더 특성이 있지만 C# 12·14 모두 CS0144·CS1061 로 거절합니다(실험 묶음이 번호만 확인 — 줄이 200칸을 넘는다). 빌더 메서드가 C# 12 의 규칙에 맞지 않으면 컴파일러는 컬렉션 초기화자 길로 갑니다.

실행 검증

오버로드 해석 — 컬렉션 식은 스팬을 고른다

제안서는 더 나은 변환 규칙에 컬렉션 식 전용 조항을 넣었습니다 — "T₁ is System.ReadOnlySpan<E₁> or System.Span<E₁>, and T₂ is an array_or_array_interface". 예제의 세 메서드 짝과 결과 주석은 제안서의 것입니다.

C# 12 에서는 제안서의 표가 그대로입니다 — 같은 "" 하나가 new[] { "" } 이면 T[], [""] 이면 Span<T> 이고, 모호한 쪽도 서로 엇갈립니다. C# 13.0 으로 올리면 ArrayDerived([""]) 의 모호함이 풀려 string[] 판이 불립니다 — 원소 "" 가 object 보다 string 에 더 잘 맞기 때문입니다.

실행 검증

ReadOnlySpan · Span · List · IEnumerable — 넷의 서열

같은 규칙의 나머지 두 조항: ReadOnlySpan<E₁> 이 Span<E₂> 보다 낫고, 둘 다 스팬이 아니면 한쪽에서 다른 쪽으로 암시적 변환이 있는 쪽(더 구체적인 쪽)이 낫습니다.

ReadOnlySpan 이 Span 을, List 가 IEnumerable 을, int[] 가 IEnumerable 을 이깁니다. 그러나 ReadOnlySpan<int> 과 List<int> 사이엔 해당하는 조항이 없어 모호합니다 — 스팬이 이기는 것은 상대가 배열이나 배열이 구현하는 인터페이스일 때뿐입니다.

실행 검증

할당을 센다 — [..xs, ..ys] 는 배열 하나

발표 글: "In many cases, the compiler sets the collection capacity and avoids copying data." 시간을 재는 대신 GC.GetAllocatedBytesForCurrentThread() 로 각 꼴이 힙에 잡은 바이트를 셉니다(첫 호출은 JIT 를 위해 버린다).

48바이트는 원소 6개짜리 int[] 하나의 크기입니다(원소 3개짜리는 40 — 뒤의 측정). 두 배열의 길이를 더해 한 번에 잡았다는 뜻입니다. LINQ 의 Concat().ToArray() 는 104, 컬렉션 식의 List 는 80, 빈 List 에 AddRange 두 번은 128 입니다. IEnumerable 대상은 배열에 읽기 전용 포장이 더해져 72 입니다. 이 덱의 csrun 은 -optimize 없이 컴파일하지만 이 다섯 줄은 -optimize+ 에서도 같습니다(뒤에서 영향이 있는 경우를 봅니다).

실행 검증

무엇을 만들었나 보는 도구 — IL 의 호출만 뽑기

제안서는 번역을 정하지 않습니다 — "An implementation is not required to translate literals exactly as specified below. Any translation is legal if the same result is produced". 그래서 실제 번역은 컴파일된 IL 에서 봅니다. 이 도구는 MethodBody.GetILAsByteArray() 를 연산 코드 표로 훑어 메서드·형식·토큰을 가리키는 명령만 찍습니다. BCL 만 씁니다.

이 장의 메서드에는 switch 명령이 없어서 피연산자 크기 표를 그만큼 줄였습니다. 긴 이름(데이터 필드의 해시 이름)은 앞 8자만 찍습니다.

실행 검증

번역을 IL 로 — 배열·List·반복기·상수·지역 스팬

제안서의 길이를 아는 번역은 배열을 "new T1[__len]" 로 잡고 "efficient bulk-copy methods like .CopyTo()" 를 써도 된다고 하고, 길이를 모르면 중간 저장소를 거칩니다. 상수만 든 ReadOnlySpan 은 "a reference to portion of the data segment" 일 수 있습니다.

Concat 은 newarr 한 번 뒤 스팬의 Slice·CopyTo 두 번 — 원소별 반복이 없습니다. AddZero 는 Count 를 먼저 읽어 List 를 만들고 CollectionsMarshal.SetCount·AsSpan 으로 내부 배열에 바로 복사합니다(앞의 Capacity 5 의 정체). 길이를 모르는 IEnumerable 은 Enumerable.ToArray 하나에 맡깁니다. Consts 는 데이터 필드를 ldtoken 해 RuntimeHelpers.CreateSpan 으로, Vars 는 합성된 인라인 배열 <>y__InlineArray2`1 을 지역 변수로 둡니다 — 인라인 배열 자체는 7장에서 다룹니다.

실행 검증

스팬 대상은 힙을 쓰지 않는다 — 단, 최적화했을 때

제안서: 상수만 든 원시 형식의 ReadOnlySpan 은 "does not need its data to be on the heap, or on the stack", 스팬은 stackalloc 이나 인라인 배열을 써도 됩니다. 반복문 안의 스팬도 "allowed to translate that using stackalloc" 입니다.

함정 — 최적화한 빌드에서 상수 ReadOnlySpan 과 반복문 안의 Span 은 0 바이트입니다. 데이터는 HasFieldRVA 필드 — 어셈블리 파일 안의 데이터 영역 — 에 있습니다. 그런데 -optimize 없이(디버그) 컴파일하면 상수 스팬 하나가 72바이트를 잡습니다. int[] 도 계층 컴파일의 첫 단계에서는 112 이고, 처음부터 최적화하게 하면 배열 크기 그대로 40 입니다. 할당을 잴 때는 Release 로 빌드해야 합니다.
실행 검증

스팬을 돌려줄 수 있나 — 컬렉션 식의 ref 안전성

제안서: 상수만 든 원시 형식의 ReadOnlySpan 은 safe-context 가 caller-context 라 돌려줄 수 있고, 그 밖의 스팬 대상은 declaration-block 이라 돌려줄 수 없습니다. 힙으로 보내려면 "it may be necessary to cast the expression to another type". 예제의 세 메서드는 제안서의 것입니다.

값이 변수에서 오는 [x, y] 는 스택에 놓일 수 있어 CS9203 입니다. (T[])[x, y, z] 는 힙의 배열이 되고, 배열에서 스팬으로의 암시적 변환으로 돌려줍니다. 지역 Span<int> local = [4, 5] 는 메서드 안에서는 자유롭게 씁니다. ref 안전성 규칙은 C# 7.2 의 것입니다.

실행 검증

쓰는 자리 — 인수·반환은 되고, foreach·기본값은 안 된다

whats-new: "You can use collection expressions anywhere you need a collection of elements. They can specify the initial value for a collection or be passed as arguments to methods that take collection types." 단, 어디서나 대상 형식이 있어야 합니다.

foreach 의 컬렉션 자리는 대상 형식을 주지 않아 CS9176 입니다 — 반복 변수의 형식 int 를 적어도 마찬가지입니다. 매개변수 기본값 = [] 는 컴파일 때 상수가 아니라서 CS1736 입니다 — 빈 배열이 Array.Empty 로 같은 객체여도 상수는 아닙니다.

실행 검증

목록 패턴과 짝 — 가르고 다시 짓기

제안서의 동기 셋째: 목록 패턴에는 "the corresponding construction syntax" 가 없었고, 그래서 문법을 패턴의 [p1, ..p2, p3] 에 맞춰 [e1, ..c2, e2] 로 정했습니다. 12부는 그 짝을 한 번 맞춰 봤고, 여기서는 재귀 함수 두 개를 짝만으로 씁니다.

[var head, .. var tail] 로 가른 것을 [.. Rev(tail), head] 로 다시 짓습니다. Merge 는 튜플 패턴 안에 목록 패턴을 넣은 switch 식입니다. 단, 재귀마다 새 배열을 만들고 .. var tail 도 배열을 잘라 복사하므로(12부) 이 꼴은 짧은 목록용입니다.

실행 검증

같이 온 런타임 — 빌더를 단 BCL 형식들

컬렉션 식이 기대는 형식은 1장이 이름을 늘어놓았습니다. 여기서는 .NET 10 의 BCL 에서 [CollectionBuilder] 를 단 공개 형식을 리플렉션으로 세고, 번역이 쓰는 형식들이 어느 어셈블리에 있는지 봅니다.

정렬 사전(ImmutableSortedDictionary)과 IImmutableDictionary 를 뺀 불변 컬렉션, Frozen 둘, 그리고 ReadOnlyCollection·ReadOnlySet 이 빌더를 가졌습니다. 사전 형식 둘의 빌더는 KeyValuePair 를 원소로 받습니다(앞). 특성 둘과 CollectionsMarshal 은 모두 System.Private.CoreLib 에 있습니다 — 컴파일러가 List 를 채울 때 쓴 SetCount 도 그 안에 있습니다.

실행 검증

뒤 버전 — C# 13 의 params 컬렉션

C# 13: "The params modifier isn't limited to array types. You can now use params with any recognized collection type, including Span<T>, ReadOnlySpan<T>". 인터페이스 대상이면 "the compiler synthesizes the storage for the arguments supplied" — 컬렉션 식이 대상 형식을 만드는 규칙을 params 가 그대로 빌려 씁니다.

Sum(1, 2, 3) 과 Sum([.. a, 3]) 이 같은 스팬을 받습니다. params IEnumerable<int> 는 ICollection<int> 로 보이는 값을 받아 개수를 바로 압니다 — 앞에서 본 합성 형식의 성질입니다. C# 12.0 의 거절은 선언 두 곳만 짚습니다. 이 기능은 14부에서 다룹니다.

실행 검증

4장의 거절 모음

실험 묶음이 각 거절 캡처의 첫 오류 줄에서 뽑은 표입니다. 언어 버전 게이트는 첫 줄의 CS9058 하나뿐이고, 나머지는 C# 12 안에서의 규칙 — 대상 형식이 없다(CS9176), 만들 수 없다(CS9174), 펼칠 수 없다(CS9212) — 입니다.

실행 검증

4장 퀴즈 — 컬렉션 식

Q1. IReadOnlyList<int> a = [1, 2]; 와 IList<int> b = [1, 2]; 에서 a 를 ICollection<int> 로 캐스트해 Add 하면? b 는?

Q2. var xs = [1, 2, 3]; 가 안 되는 까닭과 고치는 길 두 가지는?

A1. a 는 합성된 읽기 전용 형식이라 NotSupportedException, b 는 진짜 List<int> 라 3개가 됩니다 (앞). A2. 컬렉션 식에는 자연 형식이 없어 대상 형식이 필요합니다(CS9176). int[] xs = … 로 형식을 적거나 (int[])[1, 2, 3] 처럼 캐스트합니다(앞).
설명용

5장

람다의 기본값과 params — 지역 함수와 같은 매개변수

(int x = 1) => x · 합성 대리자 형식 · CS9099·CS9100 · 메서드 그룹의 자연 형식 · (params int[] xs) => …

왜 — 엔드포인트 람다에 기본값을 주고 싶었다

제안서의 동기는 웹 프레임워크입니다. "App frameworks in the .NET ecosystem leverage lambdas heavily to allow users to quickly write business logic associated with an endpoint." 기본값이 없으니 "they're left to either use local functions or set the default values within the lambda body" 였습니다.

또 하나는 람다와 지역 함수의 차이를 줄이는 것입니다 — "reducing confusing differences between lambdas and local functions, making it easier to reason about constructs and "grow up" lambdas to functions without compromising features". params 를 함께 넣은 까닭도 이것입니다. 11부는 C# 10 제안서가 이 질문을 열린 문제로 남긴 것을 봤습니다.

문서 근거

람다 매개변수의 기본값 (default lambda parameters) C# 12.0

whats-new: "You can now define default values for parameters on lambda expressions. The syntax and rules are the same as adding default values for arguments to any method or local function." 발표 글은 기본값이 "lets you add parameters to existing lambda expressions without breaking calling code" 라고 덧붙입니다. 예제의 incrementBy 는 발표 글의 것입니다.

제안서는 C# 12 이전의 오류를 CS1065(Default values are not valid in this context)로 적지만 , 지금의 컴파일러는 -langversion:11.0 에서 기능 이름을 대는 CS9058 로 거절합니다. CS1065 는 지금도 익명 메서드에 남아 있습니다(뒤). 5부가 이 기능의 첫 모습을 C# 4 의 선택적 매개변수 옆에서 봤습니다.

실행 검증

기본값은 형식의 일부 — 같은 기본값이면 같은 대리자

제안서: 기본값이나 params 가 있으면 대리자는 "a synthesized internal anonymous delegate type" 이고 매개변수 이름은 arg1, ..., argn 입니다. 합성 대리자끼리는 "unified when the same parameter (based on position) has the same default value, regardless of parameter name" 입니다.

이름이 i 와 k 로 달라도 기본값이 13 이면 같은 형식이라 a = c 가 됩니다. 기본값이 0 인 b 는 다른 형식이라 CS0029 입니다 — 오류 문장은 두 형식을 똑같이 <anonymous delegate> 로 불러 무엇이 다른지 말해 주지 않습니다. 대리자의 Invoke 는 arg=13, 람다 메서드는 원래 이름 k=13 을 갖습니다.

실행 검증

함정 — 명명 인수는 람다의 이름이 아니라 arg1, arg2 …

제안서가 적은 합성 대리자의 매개변수 이름 "arg1, ..., argn or arg if a single parameter" 는 호출하는 쪽에 보입니다. 대리자 호출은 대리자 형식의 Invoke 를 부르기 때문입니다.

둘째 기본값을 건너뛰고 셋째만 주려면 명명 인수가 필요한데, 람다에 적은 fill 은 CS1746 이고 arg3 이어야 합니다. 메서드 그룹 Pad 를 var 로 받아도 같습니다. 메서드를 직접 부를 때만 fill: 이 됩니다 — 기본값은 람다로 옮겨 왔지만 이름은 옮겨 오지 않았습니다.

실행 검증

쓸 수 있는 기본값 — 메서드와 같은 규칙

제안서: 람다 매개변수에도 메서드 매개변수(§15.6.2)와 같은 규칙이 적용됩니다 — "A parameter with a ref, out or this modifier cannot have a default_argument." 값은 C# 4 의 선택적 매개변수처럼 상수·default·new() 입니다(5부).

세 거절의 번호(CS1736·CS1741·CS1737)가 메서드에서 나는 것과 같습니다 — 람다를 위한 새 규칙이 없다는 뜻입니다. Two * 3 같은 상수식은 됩니다.

실행 검증

기본값을 못 쓰는 두 자리 — 형식 없는 매개변수, 익명 메서드

제안서: 문법은 "default parameter values and params arrays only for lambdas, not for anonymous methods declared with delegate { } syntax" 입니다. (x = 3) => … 처럼 형식 없는 매개변수의 기본값은 열린 질문이고, 파서가 (x = 를 볼 때마다 => 까지 내다봐야 하는 비용도 짚었습니다.

형식 없는 매개변수에는 전용 오류 CS9098 이 있습니다. 익명 메서드는 C# 12 이전의 문장 CS1065 그대로입니다. 대리자 M1 이 기본값을 가지면 형식만 적은 람다 (int x) => … 로도 m() 이 됩니다 — 기본값은 대리자 쪽에서 옵니다.

실행 검증

대리자와 기본값이 어긋나면 — CS9099 · CS9100

제안서: 람다를 이름 있는 대리자로 바꿀 때 기본값이나 params 가 다르면 람다 쪽 것은 쓰이지 않습니다 — "the lambda cannot be called in any other way". 그래서 "a warning will be emitted when the source default value or params modifier is present and different from the target one", 원본이 메서드 그룹이면 경고하지 않습니다. 예제의 d1…d9 는 제안서의 것입니다.

d2() 는 메서드의 기본값 2 가 아니라 대리자의 1 입니다 — 호출은 대리자 형식의 선언을 봅니다(5부). 람다 d5 의 기본값 2 도 같은 이유로 버려지고 컴파일러가 CS9099 로 알립니다. 경고는 셋 다 경고일 뿐이라 프로그램은 돕니다.

실행 검증

[DefaultParameterValue] 를 람다에 — 제안서는 "구현 안 됨"

제안서의 열린 질문: 기존 DefaultParameterValue 특성을 람다에 허락하고 "ensure that the delegate generation behavior matches for default parameter values supported via the syntax" 하자는 답을 내놓고, 문단 머리에 "Neither of these have been implemented. They remain open proposals." 라고 적었습니다. 예제는 그 문단의 a·b 입니다.

지금의 컴파일러에서는 제안서가 바란 대로 됩니다 — 특성으로 적은 b 도 b() 로 부를 수 있고, a 와 같은 합성 형식이라 b = a 가 컴파일됩니다. 문서가 "구현 안 됨" 이라 적은 것을 컴파일러가 이미 하고 있는 경우입니다(2026-10 기준의 문서).

실행 검증

메서드 그룹의 자연 형식도 기본값·params 를 담는다 C# 12.0

제안서: C# 10 의 자연 함수 형식 규칙에 "including default values and params modifiers" 를 더해, var add1 = AddWithDefault; 뒤의 add1() 이 기본값을 씁니다. 전에는 Action<int> 로 유추돼 CS7036 이었습니다.

함정 — 이 동작은 언어 버전에 묶여 있지 않습니다. -langversion:10.0 에서도 add1() 이 기본값으로 불리고 형식은 합성 대리자입니다. 람다의 기본값(CS9058)과 달리 메서드 그룹 쪽은 컴파일러의 게이트 목록에 없고, 제안서도 그 변화를 "part of C# 12" 라 부르면서, 깨지는 시점은 언어 버전이 아니라 ".NET SDK 7.0.200 or later" 로 적습니다.
실행 검증

깨지는 변경 — var 로 받은 메서드 그룹은 더는 Action 이 아니다

제안서의 "Breaking change" 절: C# 12 이전에는 var writeInt = WriteInt; 가 Action<int> 이라 DoAction(writeInt, 3) 이 됐지만, 이제는 "Inferred as anonymous delegate type" 이라 Action 으로 바뀌지 않습니다. 다행히 메서드 그룹을 var 로 받는 것은 C# 10 부터라 "only code which has been written since then" 이 깨진다고 적습니다.

제안서의 예가 그대로 CS1503 입니다. -langversion:10.0 으로 내려도 똑같이 깨집니다 — 앞 장의 함정이 곧 깨지는 변경의 범위입니다. 메서드 그룹을 인수로 바로 넘기면(DoAction(WriteInt, 3)) 대상 형식이 있어 예전처럼 변환됩니다. 11부는 C# 10 이 자연 형식을 들이며 생긴 깨지는 변경을 봤습니다.

실행 검증

람다의 params 배열 (lambda params array) C# 12.0

왜 — 제안서는 기본값과 함께 params 를 넣었고, 그 동기를 람다를 함수로 "grow up" 시킬 때 잃는 것이 없게 하려는 것이라 적습니다. 예제의 counter 는 제안서 요약의 것입니다.

인수 0개·3개·배열 하나를 모두 받습니다. 컴파일러의 게이트에서 기본값(lambda optional parameters)과 params(lambda params array)는 다른 기능입니다 — 한 버전에 같이 왔을 뿐입니다.

실행 검증

params 는 메타데이터의 ParamArrayAttribute

제안서의 IL 절: 합성 대리자의 Invoke 는 기본값이면 .param 지시자를, params 면 "System.ParamArrayAttribute" 를 갖습니다 — "just as would be the case for a standard named delegate". 통합 규칙은 "the last parameter has the same params modifier and array type" 일 때 같은 형식입니다.

특성은 대리자의 Invoke 와 람다 메서드 둘 다에 붙습니다. params 없는 (int[] xs) => … 는 합성 형식이 아니라 그냥 Func<int[], int> 이고, 그래서 a = b 의 거절 문장에 Func 가 보입니다. 거꾸로 params 형식의 변수 b 에 params 없는 람다를 넣는 것은 됩니다(제안서의 d = (int[] xs) => …).

실행 검증

기본값과 params 를 한 람다에 — 차례의 규칙

제안서: "A parameter_array may occur after an optional parameter, but cannot have a default value – the omission of arguments for a parameter_array would instead result in the creation of an empty array." 문법도 params 를 목록의 끝에만 둡니다.

log("x={0} y={1}", 2, 10, 20) 에서 2 는 level, 나머지가 args 입니다. 거절 문장은 params 를 "parameter collection" 이라 부릅니다 — 같은 컴파일러가 C# 13 의 params 컬렉션까지 아는 낱말로 말하기 때문입니다.

실행 검증

같이 온 런타임 — 프레임워크는 리플렉션으로 기본값을 읽는다

제안서: "These delegate types can be inspected at runtime, as normal. In code, users can introspect the DefaultValue in the ParameterInfo associated with the lambda or method group by using the associated MethodInfo." 동기의 MapPost 가 하는 일을 BCL 리플렉션만으로 흉내 냈습니다(실제 ASP.NET Core 코드가 아니다).

task 가 없으면 람다에 적은 "foo" 가 들어가고, 기본값이 없는 id 가 없으면 거절합니다. 프레임워크 쪽 코드는 C# 12 이전의 리플렉션 API(HasDefaultValue·DefaultValue·DynamicInvoke) 그대로입니다 — 바뀐 것은 람다가 그 메타데이터를 만들 수 있게 된 것뿐입니다.

실행 검증

뒤 버전 — C# 14 의 형식 없는 수식어, params 는 여전히

C# 14: "You can add parameter modifiers, such as scoped, ref, in, out, or ref readonly to lambda expression parameters without specifying the parameter type". 같은 절의 끝: "The params modifier still requires an explicitly typed parameter list." 예제의 TryParse<T> 는 그 절의 것입니다.

C# 14 에서 out 은 형식 없이 되지만 params 는 CS9272 입니다. params 가 필요하면 대리자 형식이 갖고 있으면 됩니다 — Count c = xs => xs.Length; 의 c(1, 2, 3) 이 그렇습니다. 형식 없는 매개변수의 기본값(앞)도 C# 14 문서에 없습니다(2026-10 기준). 이 기능은 15부에서 다룹니다.

5장의 거절과 경고 모음

실험 묶음이 각 캡처의 첫 진단 줄에서 뽑은 표입니다. 언어 버전 게이트 둘(CS9058)은 기능 이름이 컴파일러의 MessageID 와 같습니다. 나머지는 메서드 매개변수와 같은 번호(CS1736·CS1741·CS1737·CS0231)와 람다 전용 번호(CS9098· CS9099·CS9100·CS9272)로 나뉩니다.

실행 검증

5장 퀴즈 — 람다의 기본값과 params

Q1. var f = (int x, int y = 2, int z = 3) => x + y + z; 에서 y 는 그대로 두고 z 만 10 으로 주려면?

Q2. -langversion:11.0 프로젝트에서 SDK 를 올렸더니 var w = WriteInt; DoAction(w, 3); 이 깨졌습니다. 언어 버전을 그대로 뒀는데 왜?

A1. f(1, arg3: 10) — 합성 대리자의 매개변수 이름은 arg1…arg3 입니다(앞). A2. 메서드 그룹의 자연 형식이 기본값을 담는 변화는 언어 버전이 아니라 컴파일러에 묶여 있어, C# 10·11 에서도 w 가 합성 대리자가 됩니다 (앞).
