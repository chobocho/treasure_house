C# 1 — 대리자에는 이름 있는 메서드가 필요했다

C# 1 의 대리자는 이미 선언된 메서드를 가리킬 뿐입니다. "기준값 4 보다 큰 것" 을 거르는 대리자를 만들려면 기준값을 담을 클래스부터 만들어야 했습니다.

하고 싶은 말은 x > limit 한 식인데, Above 클래스와 생성자와 필드와 Check 메서드가 따라붙습니다. 이 장의 익명 메서드는 바로 이 클래스를 컴파일러가 대신 만들게 합니다.

실행 검증

익명 메서드 — delegate (int x) { … } C# 2.0

버전 기록은 익명 메서드(anonymous methods)를 C# 2.0 의 주요 기능으로 꼽습니다. 대리자가 필요한 자리에 메서드 본문을 그대로 적고, 본문은 바깥의 지역 변수 limit 를 씁니다.

이 예제는 제네릭을 쓰지 않습니다. List<int> 나 Predicate<int> 를 쓰면 C# 1 의 거절이 generics 에서 먼저 나와 익명 메서드의 게이트가 가려지기 때문입니다(1장).

실행 검증

익명 메서드의 꼴

표준의 문법은 delegate 뒤에 매개변수 목록(생략 가능)과 블록 본문입니다. 매개변수에는 형식을 반드시 적고, 본문은 식이 아니라 블록이어야 합니다.

delegate { } 는 매개변수 목록을 통째로 뺀 꼴입니다. 표준: 목록이 없으면 "convertible to a delegate with any parameter list not containing output parameters". 그래서 Log 에도 EventHandler 에도 들어갑니다.

실행 검증

목록을 뺀 꼴의 두 한계

목록을 빼면 어떤 매개변수 목록에도 맞지만, 대신 매개변수를 본문에서 쓸 수 없습니다. 그리고 out 매개변수가 있는 대리자에는 맞지 않습니다 — out 은 본문이 값을 넣어야 하는데 이름이 없기 때문입니다.

실행 검증

함정 — 목록을 뺀 꼴은 오버로드를 가리지 못한다

무엇에나 맞는다는 것은 오버로드 해석에서는 약점입니다. Run 이 두 대리자 형식으로 오버로드돼 있으면 delegate { } 는 둘 다에 맞아서 고를 수가 없습니다.

고치는 길은 목록을 적는 것입니다 — delegate() { } 는 NoArg 에만, delegate(int x) { } 는 OneArg 에만 맞습니다. 첫 두 줄이 그렇게 해서 통과했습니다.

실행 검증

함정 — 익명 메서드의 매개변수 형식은 정확히 같아야 한다

표준: 익명 함수의 시그니처가 있으면 대리자와 "the same parameter types and modifiers in the same order" 여야 하고, 메서드 그룹 변환과 달리 매개변수 형식의 반공변은 허락하지 않는다.

Show a = ShowObj; 는 object 를 받는 메서드를 string 대리자에 담습니다 — 뒤에서 볼 메서드 그룹의 반공변입니다. 같은 일을 익명 메서드로 하면 CS1661 입니다. 반환 쪽은 본문의 return 식이 대리자의 반환형으로 암시적으로 변환돼야 합니다(d).

실행 검증

return 은 익명 메서드에서 나간다 — break 는 못 나간다

표준: 본문의 return 은 "returns control from an invocation of the nearest enclosing anonymous function, not from the enclosing function member". 본문 밖을 겨냥한 break·continue·goto 는 컴파일 오류입니다.

실행 검증

익명 메서드에는 형식이 없다

표준: 익명 함수는 "does not have a value or type in and of itself, but is convertible to a compatible delegate" 입니다. 그래서 받는 쪽이 구체적인 대리자 형식이어야 합니다. object 는 물론 System.Delegate 도 대리자 형식이 아닙니다.

C# 14 의 진단은 CS8917 "could not be inferred" 입니다. C# 10 부터 람다와 메서드 그룹에 "자연 형식"이 생겨 컴파일러가 대리자 형식을 추론하려 하고, 목록을 뺀 delegate { } 에서는 그것이 실패한 것입니다.

실행 검증

잡힌 바깥 변수 — 메서드가 끝나도 산다 C# 2.0

익명 메서드가 바깥 지역 변수를 쓰면 그 변수는 "잡힌다(captured)". 표준: 잡힌 변수의 수명은 "extended at least until the delegate … becomes eligible for garbage collection". 표준의 예제를 익명 메서드로 옮겼습니다.

세 번째 호출 때 Make 는 이미 돌아왔지만 x 는 남아 있습니다. Make 를 다시 부르면 새 x 가 생겨서 b 는 1 부터 셉니다. 이런 대리자를 흔히 클로저(closure)라고 부릅니다 — 앤더스 헤일스버그(Anders Hejlsberg)도 대리자의 여러 이름을 꼽으며 "In LISP they are closures." 라고 말합니다.

실행 검증

값이 아니라 변수를 잡는다

익명 메서드는 만들 때의 값을 베끼지 않습니다. 같은 변수를 두 익명 메서드가 잡으면 둘은 그 변수로 "통신" 하고, 바깥의 Main 도 같은 변수를 봅니다. 표준의 Setter/Getter 예제입니다.

실행 검증

컴파일러가 만드는 클래스 C# 2.0

표준의 구현 예(informative)는 잡힌 지역 변수를 "hoisting" 해서 컴파일러가 만든 클래스의 필드로 옮긴다고 설명합니다. 이 장 첫머리의 Above 클래스를 컴파일러가 대신 쓰는 셈입니다. 대리자의 Target 을 리플렉션으로 들여다봅니다.

  • 대리자의 대상은 App 안에 중첩된 [CompilerGenerated] 클래스의 인스턴스입니다. 그 클래스 이름은 컴파일러 마음이라 찍지 않았습니다.
  • 지역 변수 n 은 그 클래스의 필드 n 이 됐고, 대리자를 두 번 부르자 필드 값이 12 가 됐습니다.

표준의 구현 예는 잡힌 y 를 __Locals1 클래스의 필드로 옮기고 본문을 그 클래스의 메서드로 만듭니다. 그 번역을 C# 2 문법으로 그대로 적어 익명 메서드 판과 나란히 돌립니다.

블록마다 따로 — 바깥 변수와 안쪽 변수

표준: 컴파일러가 만드는 클래스는 "for each block in which locals are captured" 하나씩이라, 블록마다 변수의 수명이 따로일 수 있습니다. 안쪽 블록의 객체는 바깥 블록의 객체를 필드로 가리킵니다.

두 대리자는 서로 다른 안쪽 객체(z 가 0 과 10)를 갖지만 바깥 객체(y)는 하나를 나눠 씁니다. 그래서 루프가 끝난 뒤 y = 200 이 둘 모두에 보입니다 — 200 과 210.

함정 — 잡힌 변수는 대리자만큼 오래 산다

잡힌 변수가 큰 배열을 가리키면, 그 배열도 대리자가 살아 있는 동안 수거되지 않습니다. 약한 참조 (WeakReference)로 지켜봅니다.

수거 시점은 런타임이 정합니다. 이 예제는 결과가 흔들리지 않도록 대리자를 정적 필드 하나에만 담고, 배열을 만드는 메서드를 인라인되지 않게 떼어 두었습니다.

같은 스코프에서 잡힌 변수는 한 생성 객체에 모입니다(블록마다 하나). 그래서 큰 배열을 잡지 않은 대리자도 그 배열을 붙잡고 있을 수 있습니다.

실행 검증

함정 — 구조체를 잡을 때 무엇이 사본인가

익명 메서드는 변수를 잡습니다. 구조체 변수 자체를 잡으면 나중의 변경이 보이지만, 매개변수나 다른 변수에 베낀 사본을 잡으면 사본만 봅니다.

Printer(pt) 의 p 는 값 매개변수라 호출 때 베낀 사본이고, 익명 메서드는 그 사본 변수를 잡았습니다. 참조 형식이었다면 세 줄이 모두 같은 객체를 봤을 것입니다.

실행 검증

잡을 수 없는 것 — ref·out 매개변수, 구조체의 this

표준: 본문은 by-reference 매개변수를 쓸 수 없고, this 가 구조체 형식이면 this(와 그 멤버)를 쓸 수 없습니다. 둘 다 호출하는 쪽의 저장소를 가리키는데, 대리자는 그 호출보다 오래 살 수 있습니다.

copy 대신 Value 를 바로 쓰면 CS1673 입니다(그 문장은 200칸이 넘어 싣지 않았습니다). 베낀 사본은 앞 장의 매개변수 사본처럼 만든 때의 값에 머뭅니다 — 2 1.

실행 검증

제네릭 메서드 안의 익명 메서드 — 생성 클래스도 제네릭

익명 메서드가 형식 매개변수 T 의 변수를 잡으면, 그 변수를 담을 생성 클래스도 T 를 알아야 합니다. 2장의 제네릭과 이 장의 클로저가 만나는 자리입니다.

대상 객체의 형식이 닫힌 제네릭 형식이고, 그 형식 인자가 호출마다 Int32·String 입니다. 정적 필드처럼 생성 클래스도 형식 인자마다 따로입니다(2장).

함정 — 반복기가 내는 클로저와 늦은 실행

4장의 반복기와 이 장의 for 캡처가 겹치면, 같은 코드가 꺼내 쓰는 방식에 따라 다른 답을 냅니다.

실행 검증

익명 메서드는 반복기가 될 수 없다

반복기 본문은 메서드·연산자·접근자의 본문입니다(4장). 익명 메서드 안의 yield 는 컴파일러가 거절합니다.

익명 메서드가 반복기를 부르는 것은 됩니다. 반복기를 대리자로 넘기고 싶으면 반복기를 이름 있는 메서드로 쓰고 그 메서드 그룹을 넘깁니다. 이 제약은 C# 14 의 람다에도 그대로입니다(둘째 캡처, 같은 CS1621).

함정 — 이 컴파일러는 명령 줄에 파일이 놓인 차례를 따릅니다. csrun 은 *.cs 를 알파벳 차례로 넘기므로 A.cs 가 먼저입니다. 둘째 캡처는 Program.cs 를 앞에 한 번 더 적었습니다 — 겹친 파일은 경고(CS2002)와 함께 한 번만 읽히고, 차례가 뒤집힙니다. 그러니 A.cs 를 Z.cs 로 바꾸는 것만으로도 차례가 바뀝니다. 파일 이름을 바꾸는 리팩터링이 동작을 바꿀 수 있으니, 조각 사이의 필드끼리 서로 기대지 않게 씁니다.
실행 검증

함정 — 이름공간이 다르면 다른 형식

표준: 각 조각은 "declared in the same namespace or containing type as the other parts" 여야 합니다. 그런데 한 조각만 이름공간을 빠뜨리면 오류가 아니라, 조각 하나짜리 partial 형식이 둘 생깁니다.

표준은 partial 선언이 하나뿐이어도 된다고 합니다("it is valid for the only declaration … to include the partial modifier"). 그래서 컴파일러는 경고도 없이 두 형식을 만듭니다. 멤버가 "없다" 는 오류가 나서야 알게 됩니다.

실행 검증

partial struct · partial interface — 그리고 enum 은 안 된다

표준: partial 은 class·struct·interface 바로 앞에서만 뜻을 가집니다.

구조체는 필드의 차례가 메모리 배치이므로 앞 장의 "차례 없음" 이 경고로 올라옵니다. partial enum 은 CS0267 로 거절됩니다. 그 문장(200칸이 넘어 싣지 않았습니다)이 꼽는 자리에는 record·event·생성자처럼 뒤 버전에 partial 이 붙게 된 것들이 보입니다.

실행 검증

제네릭 partial — 형식 매개변수와 제약도 맞춘다

표준: 조각들은 "the same name for each type parameter, in order" 를 적어야 하고, 제약을 적은 조각끼리는 제약이 "agree" 해야 합니다.

제약을 한 조각에만 적는 것은 됩니다. 도구가 만든 조각은 제약 없이 두고 사람이 제약을 다는 식입니다.

실행 검증

표준: 여러 조각으로 선언된 형식의 특성은 "combining, in an unspecified order, the attributes of each of its parts" 로 정해집니다.

실행 검증

표준: #pragma 는 "used to specify contextual information to a compiler" 이고, 그 예로 "Enable or disable particular warning messages" 를 듭니다. 내용은 컴파일러가 정하며, 프로그램의 의미를 바꾸어서는 안 됩니다.

고정 크기 버퍼의 규칙

표준: 고정 크기 버퍼는 구조체에만, static 은 안 되고, 원소 형식은 정해진 기본 형식 열둘 중 하나여야 하며, 길이는 양의 상수여야 합니다.

CS1663 의 문장이 허락된 원소 형식 열둘을 그대로 나열합니다. 원소 형식의 제약을 푸는 것은 C# 12 의 인라인 배열입니다 (뒤에서).

함정 — 범위 검사가 없다

표준: "Unlike access to arrays, access to the elements of a fixed-size buffer is an unsafe operation and is not range checked." 길이 2 의 버퍼에 A[2] 를 쓰면 바로 뒤의 필드가 바뀝니다.

예외도 경고도 없이 After 가 99 가 됐습니다. 같은 실수를 배열에 하면 IndexOutOfRangeException 입니다. 버퍼의 원소는 "laid out sequentially" 라는 것까지만 표준이 정하고, 뒤의 필드가 어디 있는지는 이 런타임의 배치입니다.

뒤 버전과의 맞물림 — C# 7.3, 고정하지 않고 인덱싱

클래스의 필드처럼 GC 가 옮길 수 있는 곳에 있는 버퍼는, C# 7.2 까지 fixed 문으로 먼저 고정해야 인덱싱할 수 있었습니다. C# 7.3 의 제안서 제목이 그 변화를 그대로 말합니다 — "Indexing fixed fields should not require pinning regardless of the movable/unmovable context."

제안서는 덧붙입니다 — 여전히 unsafe 문맥이 필요하고 "It is possible to read uninitialized data or even out of range. That is not changing." 앞 장의 함정은 그대로입니다. C# 7.3 은 8부입니다.

뒤 버전과의 맞물림 — C# 12 의 인라인 배열

C# 12 의 인라인 배열 제안서는 첫 문장에서 고정 크기 버퍼를 가리킵니다 — "This proposal plans to address the many limitations of" 고정 크기 버퍼. unsafe 없이, 범위 검사와 함께, 아무 원소 형식으로나 쓸 수 있는 구조체 안 배열입니다.

제안서가 꼽는 목표에는 "the declaration of inline arrays for managed and unmanaged types" 도 있습니다 — 고정 크기 버퍼의 "기본 형식만" 제약을 푸는 것입니다. 인라인 배열은 13부에서 다룹니다.

7장 퀴즈 — #pragma 와 고정 크기 버퍼

Q. unsafe struct P { public fixed int A[2]; public int B; } 에서 p.A[2] = 1; 은 컴파일됩니까? 돌리면 예외가 납니까? 그리고 Quiet.cs 맨 위에 #pragma warning disable 168 을 적으면 Program.cs 의 CS0168 도 사라집니까?

A. 컴파일되고 예외도 나지 않습니다. 고정 크기 버퍼의 원소 접근은 범위를 검사하지 않아서 이 런타임에서는 B 를 덮어씁니다(범위 검사 없음). #pragma 는 그 파일 안에서만 듣습니다 — Program.cs 의 경고는 그대로입니다(파일 단위).
