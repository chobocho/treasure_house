같이 온 런타임 — C# 14 가 기대는 형식 C# 14.0

왜 — 확장 블록은 메타데이터에 새 특성을 씁니다. 제안서는 그 특성의 이름을 ExtensionMarkerNameAttribute 로 적고 "The type declaration is synthesized by the compiler if not already included in the compilation." 이라고 합니다. .NET 10 의 System.Private.CoreLib 에서 이름으로 찾아봅니다.

런타임에 있는 것은 ExtensionMarkerAttribute 이고 제안서의 ExtensionMarkerNameAttribute 는 없습니다. 컴파일러가 실제로 붙이는 것도 ExtensionMarker 입니다(2장). Enumerable.Reverse(TSource[]) 는 .NET 10 에 새로 생긴 배열 오버로드로, 암묵적 Span 변환이 낳을 깨짐을 막는 자리입니다(4장). MemoryExtensions 의 스팬 오버로드가 그 반대편입니다.

.NET 10 의 BCL 은 확장 블록을 쓰나 — 센다

블로그는 .NET 10 의 성능 향상이 "the runtime and BCL adopting new C# 14 capabilities" 에서 온다고 적습니다. 확장 블록은 묶음 형식(이름이 <G>$ 로 시작, 2장)을 남기므로, 공유 런타임의 System*.dll 에서 그 형식과 옛 꼴의 공개 확장 메서드를 셉니다.

.NET 10.0.12 의 164 개 어셈블리에 확장 블록은 하나도 없고, 공개 확장 메서드는 모두 C# 3 의 this 꼴입니다. 블로그가 말한 "adopting" 은 4장의 스팬 변환 쪽입니다 — 7장의 복합 대입 연산자도 .NET 10 참조 팩에는 아직 하나도 없습니다(7장). 확장 멤버는 아직 BCL 의 공개 API 에 쓰이지 않았습니다(2026-10 기준, 이 기계의 런타임).

경고 웨이브 10 — CS9265 하나 C# 14.0

왜 — Roslyn 의 경고 웨이브 문서: "The compiler shipped with .NET 10 (the C# 14 compiler) contains the following warnings which are reported only under /warn:10 or higher." 표의 줄은 CS9265 하나입니다. 14부는 이 경고가 C# 12.0 에서도 난다는 것을 보았습니다(14부). 여기서는 무엇이 "ref 대입" 으로 치이는지, 언어 버전을 어디까지 내릴 수 있는지 봅니다.

개체 초기화자의 B = ref n 도 ref 대입으로 쳐서, 경고는 C 하나입니다. 경고는 언어 버전이 아니라 경고 수준에 묶여 있어 ref 필드가 있는 가장 낮은 버전 C# 11.0 에서도 나오고, C# 10.0 에서는 ref 필드 자체가 거절됩니다(12부). C 는 null 참조라 Unsafe.IsNullRef 가 True 입니다.

버린 열거자는 다시 돌지 않는다 C# 14.0

왜 — 문서: "The state machine for enumerators incorrectly allowed resuming execution after the enumerator was disposed. Now, MoveNext() on a disposed enumerator properly returns false without executing any more user code."

확장 블록 · 옛 꼴과 같은 결과물 · 메타데이터 · 확장 속성 · 수신자 · 정적 확장 멤버 · 해석 규칙 · 확장 연산자 · 문맥 키워드 ·

왜 생겼나 — 메서드밖에 붙일 수 없었다

C# 3 의 확장 메서드는 남의 형식에 메서드를 붙이는 길이었습니다(4부). 붙일 수 있는 것은 인스턴스 메서드 꼴 하나뿐이었습니다.

바란 것C# 13 까지C# 14
seq.IsEmpty 같은 속성seq.IsEmpty() 메서드로 흉내확장 속성
List<int>.Of(1, 2) 같은 형식의 정적 멤버도우미 클래스의 정적 메서드 ListUtil.Of정적 확장 멤버
array * 2 같은 연산자그 형식 안에서만 선언 가능확장 연산자

whats-new: "The new syntax enables you to declare extension properties in addition to extension methods. You can also declare extension members that extend the type, rather than an instance of the type." 새 문법은 옛것을 버리지 않습니다 — 블로그의 말로 "fully compatible with existing extension methods" 입니다.

C# 3 이후 확장 메서드의 선언 꼴에 더해진 것은 C# 7.2 의 ref this·in this(8부)였고, C# 9 에서는 foreach 가 확장 GetEnumerator 를 찾게 되었습니다(4부). 둘 다 메서드였습니다. 인터페이스에 구현을 붙이는 다른 길은 C# 8 의 기본 구현(9부), 형식에 정적 연산자를 요구하는 길은 C# 11 의 static abstract(12부)가 열었습니다. 확장 멤버는 그 어느 것도 아닌 "남의 형식" 쪽을 넓힙니다.

문서 근거

확장 블록 (extension block) C# 14.0

왜 — 제안서: 확장 선언은 "anonymous" 이고 "a receiver specification … followed by a set of extension member declarations" 입니다. 수신자(receiver)를 멤버마다 this 매개변수로 적는 대신 블록 머리에 한 번 적습니다.

블록 안의 메서드는 this 없이 s 를 씁니다. 마지막 줄 TextExt.Initials(line) 처럼 정적 메서드로도 부를 수 있습니다 — 옛 확장 메서드와 같습니다(뒤에서). C# 13.0 의 거절은 게이트 문장이 아니라 구문 오류 둘입니다. 4부의 앞당긴 장이 같은 것을 보았고 (4부), 왜 그런지는 다음 장에서 봅니다.

실행 검증

C# 13.0 의 파서가 확장 블록을 읽는 세 길

같은 자리의 확장 블록을 세 꼴로 바꿔 C# 13.0 으로 컴파일합니다 — 멤버가 든 블록, 제네릭 블록, 빈 블록.

extension(int n) { … } 는 C# 13 의 문법으로도 뜻이 있는 줄입니다 — extension 이라는 이름의 생성자처럼 읽힙니다. 그래서 빈 블록은 게이트 문장 CS9260 과 함께 "Static classes cannot have instance constructors"(CS0710)가 나고, 멤버가 든 블록은 몸체 안의 public 에서 구문 오류가 납니다. 생성자로 읽힐 수 없는 제네릭 블록만 깔끔하게 CS9260 하나입니다. 1장의 게이트 시연이 extension<T> 를 쓴 까닭입니다.

실행 검증

옛 꼴과 새 꼴이 만드는 정적 메서드

제안서: "Instance extension methods generate artifacts that match those produced by classic extension methods." 정적 메서드의 형식 매개변수와 매개변수는 "concatenated from the extension declaration and the method declaration in that order" 입니다.

두 메서드 모두 static String X(String s, Int32 n) 이고 [Extension] 이 붙습니다. 블록의 수신자 s 가 첫 매개변수가 되고, 이름도 수신자 매개변수의 이름 그대로입니다. 그래서 C# 3 의 소비자(4부)에게는 둘이 구별되지 않습니다.

실행 검증

한 메서드씩 옮겨도 된다

블로그: "Because extension blocks are source and binary compatible with existing extension methods, you can migrate one method at a time. Dependent assemblies don't need to be recompiled and continue to bind to the original symbol." 같은 메서드를 옛 꼴과 새 꼴로 컴파일해 결과물을 견줍니다.

메서드의 서명, 매개변수 이름, 특성, 호출 결과가 글자까지 같습니다. 이 덱의 csrun 은 어셈블리 하나만 만들어서 "다른 어셈블리가 다시 컴파일하지 않아도" 는 직접 보일 수 없지만, 그 어셈블리가 보는 것 — 이 정적 메서드 — 이 같다는 것은 보입니다.

실행 검증

확장 블록이 남기는 메타데이터

제안서의 설계: 블록은 "extension grouping type" 과 그 안의 "extension marker type" 으로 남고, 표지 형식에는 수신자를 담은 "extension marker method" 하나가 있습니다. 멤버의 몸체는 바깥 정적 클래스의 "implementation method" 로 갑니다.

묶음 형식 <G>$… 는 공개·봉인·SpecialName 이고 [Extension] 이 붙습니다. 표지 형식 <M>$… 는 정적 클래스 (Abstract, Sealed)이고 그 안의 <Extension>$(String) 이 수신자 string s 를 기억합니다. 묶음 형식의 get_Len()·Twice() 는 매개변수가 없는 원래 서명으로 남고, 실제 일은 E 의 get_Len(String)·Twice(String) 이 합니다. 속성의 구현 메서드에는 [Extension] 이 없습니다 — 제안서 말대로 "instance ordinary method" 만 붙습니다.

실행 검증

묶음은 CLR 서명으로, 표지는 C# 서명으로

제안서: 묶음 형식은 같은 "CLR-level signature" 의 블록마다 하나, 표지 형식은 같은 "C#-level signature" 마다 하나입니다. CLR 서명에서는 매개변수 이름과 notnull 제약이 지워지고, 형식 매개변수는 "T0, T1, etc" 로 정규화됩니다.

블록 다섯이 묶음 둘, 표지 넷이 됩니다. s 와 t 는 한 묶음의 다른 표지이고, 같은 extension(string s) 를 두 번 쓴 블록은 표지 하나로 합쳐집니다. where T : notnull 인 블록과 제약 없는 블록도 한 묶음입니다. 묶음 형식의 형식 매개변수 이름은 제안서의 T0 이 아니라 $T0 이고, 표지 형식이 원래 이름 T·U 를 다시 선언합니다.

실행 검증

뼈대 멤버를 억지로 부르면

제안서: 묶음 형식 안의 멤버는 서명만 남고 "their bodies are replaced with throw NotImplementedException(). Those should not be referenced in IL." 리플렉션으로 그 뼈대의 IL 을 읽고 불러 봅니다.

IL 은 14 7A 두 바이트 — ldnull, throw 입니다. null 을 던지면 런타임이 NullReferenceException 을 냅니다. 제안서가 적은 NotImplementedException 이 아닙니다(1장). 어느 쪽이든 뼈대는 C# 컴파일러가 이름과 서명을 읽기 위한 것이고, 호출은 언제나 마지막 줄처럼 구현 메서드로 갑니다.

실행 검증

확장 속성 (extension property) C# 14.0

왜 — whats-new 의 첫 예제가 public bool IsEmpty => !source.Any(); 입니다. 제안서: 확장 멤버의 선언은 "syntactically identical to corresponding instance and static members in class and struct declarations (with the exception of constructors)" 입니다. 속성에는 get 과 set 이 다 됩니다.

sb.Text += "def" 는 get_Text 로 읽고 set_Text 로 씁니다. 구현 메서드는 수신자를 첫 매개변수로 받는 정적 get_X(StringBuilder)·set_X(StringBuilder, String) 입니다 — 속성 하나가 정적 메서드 한두 개로 내려갑니다(앞에서).

실행 검증

확장 블록에는 상태를 둘 곳이 없다

확장 속성은 남의 객체에 붙는 계산일 뿐이고, 값을 담을 칸을 객체에 더하지 못합니다. 칸이 필요한 꼴 넷을 하나씩 넣어 봅니다. 제안서는 그중 init 만 "may not have init accessors" 로 따로 적습니다.

자동 속성, 필드, field 를 쓴 속성(3장)은 모두 같은 CS9282 "This member is not allowed in an extension block" 입니다 — 셋 다 뒷받침 필드를 만들어야 하는 꼴입니다. init 만 전용 오류 CS9304 입니다. 상태가 꼭 필요하면 예전처럼 ConditionalWeakTable 같은 바깥 표를 써야 하고, 그것은 언어가 아니라 라이브러리의 일입니다.

실행 검증

함정 — 값 형식 수신자는 복사본이다

제안서: "By default the receiver is passed to instance extension members by value, just like other parameters." 구조체 수신자에 setter 를 붙이면 무슨 일이 생기는지 봅니다.

pt.Reset() 과 pt.Left = 9 는 복사본을 고치고 버려서 3,4 가 그대로입니다. 컴파일러는 아무 말도 하지 않습니다 — 구조체 반환 값의 필드에 대입할 때의 CS1612 같은 진단이 확장 setter 에는 없습니다. extension(ref Point p) 의 First 와 Clear() 만 원본을 바꿉니다. C# 3 의 확장 메서드도 같은 함정이었습니다(4부); 속성 대입 꼴이 더해져 더 그럴듯해 보일 뿐입니다.

실행 검증

ref · in · ref readonly 수신자

제안서: 수신자는 "ref, ref readonly and in" 을 쓸 수 있지만 "as long as the receiver type is known to be a value type" 입니다. C# 7.2 의 ref this·in this(8부)를 블록 머리로 옮긴 것입니다.

in 수신자는 new Big { A = 5 } 같은 값에도 붙고, ref 수신자는 변수가 아니면 CS1510 입니다 — 8부의 ref this 와 같은 규칙입니다. 참조 형식이나 제약 없는 T 에는 CS9300 이고, 문장이 "a generic type constrained to struct" 라는 길을 알려 줍니다.

실행 검증

수신자의 null 가능성과 특성

제안서: "Receiver types can be or contain nullable reference types, and receiver specifications that are in the form of parameters can specify attributes". 예제의 두 블록은 제안서의 NullableExtensions 를 줄인 것입니다.

if (!name.IsMissing) 안에서는 경고가 없습니다 — 수신자에 붙인 [NotNullWhen(false)] 가 흐름 분석에 쓰입니다. 확인하지 않은 줄에는 CS8602 가 나고, 실제로 null 이라 그 줄에서 예외입니다. 확장 속성의 수신자가 null 이어도 호출 자체는 정적 메서드라 문제없습니다([]) — 이것은 4부의 확장 메서드와 같습니다.

실행 검증

whats-new 의 예제 그대로 — IsEmpty 와 Identity

whats-new 의 Enumerable 예제에서 IsEmpty, 정적 속성 Identity, 연산자 + 를 옮겼습니다. 블로그는 같은 블록을 data + [ 4, 5 ] 로 부릅니다.

int[]·List<int> 에도 IsEmpty 가 붙습니다 — 수신자 형식 IEnumerable<TSource> 로의 변환과 형식 추론은 옛 확장 메서드와 같습니다. 눈여겨볼 줄은 data + new[] { 6 } 입니다. 연산자 + 는 IEnumerable<TSource> 의 확장인데 두 배열에 적용되고, data + [4, 5] 의 컬렉션 식도 그 매개변수 형식으로 만들어집니다. 남의 배열에 + 가 생긴 것입니다.

실행 검증

제네릭 수신자와 제약 — 형식 인수는 블록의 것부터

제안서: 명시적 형식 인수는 "used to substitute the type parameters of the extension declaration and the extension member declaration" — 블록의 것과 멤버의 것을 합친 목록입니다. 또 속성처럼 메서드가 아닌 멤버는 블록의 형식 매개변수를 모두 써야 합니다("Inferrability").

To<R>() 에 형식 인수를 적으려면 300.To<int, long>() 처럼 블록의 T 부터 다 적어야 합니다. R 만 적은 300.To<long>()(-define:ONE)은 CS1061, 제약을 못 맞춘 "text".IsZero(-define:STR)는 CS9286 입니다 — 두 문장은 200칸이 넘어 뒤의 표에 옮겼습니다. 정적 호출 NumExt.To<int, byte>(200) 도 같은 차례입니다.

실행 검증

블록의 이름이 보이는 범위

제안서: 블록의 형식 매개변수와 수신자 매개변수는 블록 몸체 전체에서 보이지만, "It is an error to refer to the receiver parameter from within a static member, except within a nameof expression." 멤버가 같은 이름을 다시 쓰는 것도 오류입니다.

정적 멤버 Name() 의 nameof(ts) 는 되고, 몸체에서 ts 를 쓰면 CS9293 입니다. 이름을 다시 쓰면 매개변수는 CS9290, 형식 매개변수는 CS9289 입니다. 정적 확장 멤버를 형식 이름으로 부르는 꼴(int[].Name())은 C# 의 문법에 없어서, 이 예제는 구현 메서드 E.Name<int>() 로 부릅니다.

실행 검증

null 수신자 · 대리자 · 속성 패턴 · nameof · dynamic

확장 속성과 블록의 메서드가 언어의 다른 자리에서 어떻게 쓰이는지 한 번에 봅니다. 제안서는 nameof 를 열린 문제로 남겼습니다 — "Needs design, likely punt from .NET 10."

메서드 그룹 "x".Wrap 은 수신자를 대리자의 Target 으로 묶습니다 — 4부의 확장 메서드 대리자와 같습니다(4부). 속성 패턴 { IsBlank: true } 는 확장 속성을 찾습니다. nameof(none.IsBlank) 는 CS9316 "Extension members are not allowed as an argument to 'nameof'" 이고, 구현 메서드 이름 nameof(Ext.get_IsBlank) 은 됩니다. dynamic 은 확장 속성을 못 찾아 실행 중에 RuntimeBinderException — 확장 메서드 때와 같습니다(4부).

실행 검증

2장 퀴즈 (1) — 블록과 속성

Q. struct Point { public int X; } 에 extension(Point p) { public int Left { get => p.X; set => p.X = value; } } 을 붙이고 pt.Left = 9; 라고 썼습니다. 컴파일러는 무엇이라 하고, pt.X 는 얼마입니까? 고치려면 어디를 바꿉니까?

A. 아무 진단도 없고 pt.X 는 그대로입니다. 수신자가 값으로 넘어가 setter 가 복사본을 고치기 때문입니다(값 형식 수신자). 블록 머리를 extension(ref Point p) 로 바꾸면 원본이 바뀝니다. ref 수신자는 값 형식에만 되고, 참조 형식에 쓰면 CS9300 입니다 (ref 수신자).
설명용

정적 확장 멤버 (static extension members) C# 14.0

왜 — whats-new: "You can also declare extension members that extend the type, rather than an instance of the type. In other words, these new extension members can appear as static members of the type you extend." 수신자에 이름이 없으면 그 블록에는 정적 멤버만 둘 수 있습니다.

List<int>.Of(1, 2, 3), int.Parse2("21"), 정적 클래스 Math 의 Math.Twice(4) 가 모두 됩니다 — 제안서가 금지한 것은 이름 있는 수신자의 정적 형식뿐입니다. 인스턴스로 부르면 보통의 정적 멤버와 같은 CS0176 이고, 오류 문장은 멤버를 ListExt.extension<int>(List<int>).Of(params int[]) 로 부릅니다 — 확장 멤버의 C# 쪽 이름입니다.

실행 검증

정적 확장 멤버의 구현 메서드

제안서: 구현 메서드는 "If it implements a static method, it has the same parameters and return type." 수신자 매개변수가 붙지 않고, [Extension] 도 인스턴스 메서드에만 붙습니다.

정적 Made 의 구현은 매개변수가 없는 get_Made[T]() 입니다. 블록의 T 는 그대로 메서드의 형식 매개변수가 되는데, 매개변수 어디에도 T 가 없으니 직접 부를 때는 get_Made<string>() 처럼 적어야 합니다. 셋 모두 [Extension] 이 없습니다 — C# 3 의 소비자에게 이 셋은 확장 메서드가 아니라 그냥 정적 메서드입니다.

실행 검증

함정 — 열거형의 정적 확장 속성은 멤버에 가려진다

정적 확장 멤버는 남의 열거형에도 붙습니다 — DayOfWeek.First 같은 이름을 만들 수 있습니다. 확장 멤버는 보통의 멤버 찾기가 실패한 뒤에만 찾으므로 (인스턴스 멤버가 먼저), 같은 이름의 열거형 멤버가 있으면 그쪽이 이깁니다.

DayOfWeek.First 는 Monday 이고, 그 결과에 다시 확장 속성 IsWeekend 가 붙습니다. Size.Large 는 확장 판(Small)이 아니라 열거형 멤버 Large 입니다 — 컴파일러는 가려진 확장 멤버에 경고하지 않습니다. 남의 열거형에 나중에 같은 이름의 값이 더해지면 호출하는 줄이 소리 없이 그쪽으로 옮겨 갑니다(4부의 이야기와 같다).

실행 검증

인스턴스 멤버가 먼저다

제안서: 확장 멤버를 찾는 것은 "When an extension member lookup is attempted" — 보통의 멤버 찾기가 실패했을 때입니다. 확장 속성도 "resolved like extension methods" 입니다. C# 3 의 규칙(4부)이 속성에도 그대로입니다.

확장 Length 와 ToUpper() 는 인스턴스 멤버에 가려 불리지 않고, 컴파일러는 경고도 하지 않습니다. 구현 메서드로 직접 부르면 비로소 -1 ext 입니다. list.Count 는 인스턴스 속성, list.Count(2) 는 확장 메서드 — 이름이 같아도 하나는 호출할 수 없는 속성이라 둘이 공존합니다. LINQ 의 Count() 와 같은 사정입니다.

실행 검증

가까운 범위가 이긴다 — 옛 꼴과 새 꼴이 섞여도

확장 연산자 제안서는 "Like other extension members" 라며, 찾기가 "the innermost namespace" 부터 "scope by scope" 로 나간다고 적습니다. C# 3 의 규칙(4부)에 C# 14 의 블록을 섞어 봅니다.

5.Tag() 는 안쪽 이름공간의 블록이 이기고, 바깥의 this 꼴은 정적 호출로만 닿습니다. 옛 꼴이냐 새 꼴이냐는 순위에 들지 않고, 범위만 봅니다. 안쪽에 없는 Kind 는 바깥에서 찾습니다.

실행 검증

모호함과, 구현 메서드로 고르기

제안서: "Similarly to classic extension methods, the emitted implementation methods can be invoked statically. This allows the compiler to disambiguate between extension members with the same name and arity." 예제는 제안서의 E1·E2 를 따르되 수신자에 이름 o 를 붙였습니다 — 제안서의 extension(object) 처럼 이름이 없으면 인스턴스 멤버 M2·P 를 둘 수 없습니다(CS9303).

정적 멤버와 메서드는 CS0121 "The call is ambiguous" 입니다. 속성 x.P(-define:A3)는 다릅니다 — 모호하다는 말 대신 CS9286 "'object' does not contain a definition for 'P'" 가 나옵니다(문장 전체는 뒤의 표). 제안서의 주석은 "ambiguous" 입니다 (1장). 속성을 고르는 길은 제안서가 보이는 대로 접근자의 구현 메서드 E1.get_P(x) 입니다.

실행 검증

같은 수신자의 블록은 한 선언 공간

제안서: 한 정적 클래스 안에서 수신자 형식이 같은 블록들의 멤버는 "a single declaration space" 로 다뤄지고, 이 규칙은 "includes classic extension methods within the same static class."

수신자 이름(xs·ys)이 달라도 형식이 같으면 한 공간이라, 메서드 Last() 와 속성 Last 가 부딪칩니다(CS0102). this 꼴의 First 와 블록의 First() 는 구현 메서드의 서명이 같아 CS0111 입니다. 옛 꼴을 새 꼴로 옮길 때 둘을 함께 두면 안 되는 까닭입니다.

실행 검증

using static 이 들여오는 것

제안서: using static 은 블록의 멤버를 확장 접근용으로 들여오고, 구현 메서드는 "(except those that are extension methods) can be used directly as static methods".

정적 확장 멤버의 구현 Hello(), 정적 속성의 접근자 get_Answer() 는 이름만으로 불립니다. 인스턴스 확장 메서드 Who 의 구현은 [Extension] 이 붙은 메서드라 C# 3 때처럼 들여오지 않습니다(CS0103) — Tools.E.Who(5) 로 불러야 합니다.

실행 검증

확장 블록을 둘 수 있는 곳, 붙일 수 없는 수식어

제안서: 확장은 "declared inside top-level non-generic static classes, just like extension methods today" 이고, 멤버에는 virtual·override·new· protected 같은 수식어를 쓸 수 없습니다.

세 자리 모두 같은 CS9283 "Extensions must be declared in a top-level, non-generic, static class" 이고, 문장이 규칙 셋을 다 적습니다 — C# 3 의 확장 메서드에 걸던 제한(4부)과 같습니다. virtual 은 오래된 CS0106 입니다.

실행 검증

확장 블록과 오버로드 해석 우선순위

제안서: "Extension members within an enclosing static class are subject to prioritization according to ORPA values. The enclosing static class is considered the 'containing type'". C# 13 의 [OverloadResolutionPriority](14부)를 블록 사이에 겁니다.

특성이 없으면 배열에는 배열 판이 더 나은 변환이라 array 입니다. 우선순위 1 을 붙이면 두 블록이 한 "containing type" 으로 묶여 스팬 판이 이깁니다 — 배열에서 스팬으로 가는 변환은 C# 14 의 암묵적 Span 변환입니다(4장). 정적 호출 Ext.Describe(xs) 도 같은 판을 고릅니다.

실행 검증

쿼리 식은 새 꼴의 확장 메서드도 찾는다

C# 3 의 쿼리 식은 Select·Where 라는 이름의 메서드 호출로 번역됩니다(4부). 제안서의 열린 문제 목록은 패턴 기반 구문에서 새 확장 메서드가 "same places where classic extension methods come into play" 라고 답합니다.

from x in b where x > 10 select … 가 블록의 Where·Select 로 번역됩니다. 쿼리 식은 이름과 모양만 보는 패턴이라, 메서드가 어느 꼴로 선언됐는지 묻지 않습니다.

실행 검증

확장 블록 안의 async 와 반복기

제안서의 메타데이터 예제에는 extension(IAsyncEnumerable<int> values) { public async Task<int> SumAsync() … } 가 있습니다. 블록의 메서드도 보통 메서드처럼 async 와 yield 를 쓸 수 있고, 상태 기계는 구현 메서드를 따라갑니다.

4.Upto().SumAsync() 는 1+2+3+4 = 10 입니다. 숨은 상태 기계 형식 <SumAsync>d__1·<Upto>d__3 은 묶음 형식이 아니라 바깥 정적 클래스 AsyncExt 에 중첩됩니다 — 몸체를 가진 것이 구현 메서드이기 때문입니다(메타데이터). 수신자 n 은 상태 기계의 필드로 붙잡힙니다(6부).

실행 검증

인터페이스의 기본 구현과 확장 속성

C# 8 의 기본 구현 멤버(9부)도 인터페이스에 멤버를 더하는 길이었습니다. 같은 인터페이스에 확장 속성을 붙여 둘을 나란히 둡니다.

확장 속성은 클래스 변수 sq 에서 바로 보이고, 기본 구현 Kind 는 IShape 로 바꿔야 보입니다 — sq.Kind(-define:DIM)는 CS1061 입니다(뒤의 표). 대신 기본 구현은 구현 클래스가 덮어쓸 수 있는 가상 멤버이고, 확장 멤버는 인스턴스 멤버에 늘 집니다 (앞에서). 인터페이스를 고칠 수 있는 쪽은 기본 구현, 남의 인터페이스에는 확장입니다.

실행 검증

확장 연산자 (extension operators) C# 14.0

왜 — 보통의 사용자 정의 연산자는 피연산자 형식 안에서만 선언할 수 있어서, 남의 형식(배열, 인터페이스)에는 붙일 수 없었습니다. 확장 연산자도 블록 안에 선언하는데, 제안서는 그 까닭을 "This allows type parameters to be declared and inferred" 라고 적습니다. 예제는 제안서의 INumber<TElement> 배열 연산자를 옮긴 것입니다.

int[] 과 double[] 에 같은 블록의 연산자가 붙습니다 — T 는 피연산자에서 추론됩니다. operator true·false 덕분에 배열이 ?: 의 조건이 됩니다. 구현 메서드 이름은 보통 연산자와 같은 op_Multiply 입니다. 제약을 못 맞춘 string[] 은 연산자가 없는 것으로 보여 CS0019 입니다. 12부의 제네릭 수학(12부)이 형식 안에서 요구하던 연산자를, 이제 남의 형식 바깥에서 줍니다.

실행 검증

확장 복합 대입 — 그리고 미리 정의된 연산자가 먼저다

C# 14 의 인스턴스 operator +=(7장)도 확장으로 붙습니다. 제안서의 제한: 수신자가 값 형식이면 "the receiver parameter must be a 'ref' parameter", 참조 형식이면 "a value parameter". 그리고 확장 연산자는 "only considered if no applicable predefined or non-extension user-defined operators were found".

list += 1 은 같은 리스트를 고칩니다(True). 함정은 StringBuilder 입니다 — 확장 += 를 선언했는데도 sb += "b" 는 CS0029 입니다. object + string 이라는 미리 정의된 문자열 연결이 적용되므로 확장 연산자는 찾지도 않고, 결과 string 을 StringBuilder 에 넣을 수 없습니다.

실행 검증

확장 연산자가 거절되는 자리, 거절되지 않는 자리

제안서: 확장 연산자는 "at least one parameter of type S" — 확장되는 형식 — 을 받아야 하고, 짝으로 선언하는 연산자는 짝이 있어야 합니다. 변환 연산자는 "not yet designed or planned" 입니다. 미리 정의된 연산자와 서명이 같은 것을 막는 규칙은 논의 끝에 "Rule is abandoned." 로 정리됐습니다.

extension(int) 의 int + int 는 오류도 경고도 없이 컴파일되지만 1 + 2 는 미리 정의된 덧셈이라 3 입니다 — 확장 판은 Ops.op_Addition(1, 2) 로만 불려 -1 입니다. 변환 연산자는 자리 자체가 없어 확장 블록의 공통 오류 CS9282 이고, 나머지 셋은 보통 연산자의 규칙(CS0558·CS0216)이나 새 오류 CS9319 입니다.

실행 검증

확장 &·true·false 로 쓰는 && — 짝은 다른 블록에 있어도 된다

제안서: &&·|| 의 사용자 정의 규칙을 확장에 옮겨, "The enclosing static class shall contain declarations of extension operator true and extension operator false". 짝으로 선언하는 연산자는 "allowed to occur in separate extension blocks … as long as … the extension blocks occur in the same static class."

첫 줄은 operator false(f) 가 참이라 오른쪽 Trace 를 부르지 않고 끝납니다 — 확장 연산자로도 && 의 단락 평가가 됩니다. < 와 > 는 서로 다른 블록에 있지만 한 정적 클래스라 짝이 맞습니다. 짝이 없을 때의 오류는 == 만 둔 앞 장의 CS0216 입니다(거절되는 자리).

실행 검증

식 트리 안의 확장 멤버

제안서: 식 트리의 연산자 노드에 확장 연산자를 쓰면 "Use MethodInfo referring to a corresponding implementation method in the enclosing class." 확장 속성은 어떤지 함께 봅니다.

확장 메서드는 트리에서 s.Twice() 로 보이고, 연산자 노드의 Method 는 구현 메서드 op_Addition(Money, Money) 입니다 — 제안서 그대로입니다. 확장 속성만 CS9296 "An expression tree may not contain an extension property access" 입니다. LINQ 공급자(EF 같은)에게 넘길 식에서는 확장 속성 대신 메서드를 써야 합니다.

실행 검증

extension 은 이제 문맥 키워드 C# 14.0

왜 — Roslyn 의 .NET 10 깨지는 변경: "Starting with C# 14, the extension keyword serves a special purpose in denoting extension containers." 생성자처럼 보이던 extension(object o) { } 는 확장 블록으로, 반환 형식 extension 의 메서드는 구문 오류로, 형식 이름 extension 은 오류가 됩니다. 제안서의 "Breaking changes" 절도 "Types and aliases may not be named "extension"." 한 줄입니다.

C# 13.0 에서는 넷 다 돌고(3), C# 14.0 에서는 @ 를 붙인 꼴만 됩니다. 생성자였던 줄은 확장 블록으로 읽혀 몸체의 N = n; 에서 CS1519, 반환 형식은 "Extension declarations may not have a name"(CS9281)부터 다섯 줄, 이름은 전용 오류 CS9306 입니다. 셋 다 언어 버전에 묶여 있어 SDK 만 올리면 깨지지 않습니다. 13부가 별칭 이름으로 같은 CS9306 을 보았습니다(13부).

실행 검증

C# 14 에 없는 것 — 인덱서·이벤트·생성자

제안서의 "Add support for more member kinds" 는 차례를 "1. Properties and methods … 2. Operators 3. Indexers … 4. Anything else" 로 적습니다. C# 14 는 둘째까지입니다. C# 15 (미리 보기)의 whats-new 는 "Starting with C# 15, you can declare indexers in an extension block." 이라고 적습니다.

인덱서, 이벤트(접근자마다 한 줄씩), 생성자 모두 CS9282 입니다. -langversion:preview 로도 같습니다 — 이 SDK 10.0.112 에는 C# 15 의 확장 인덱서가 들어 있지 않습니다. C# 15 는 16부에서 다룹니다(2026-10 기준, 미리 보기).

실행 검증

2장의 거절 모음 (1) — 블록 · 수신자 · 속성

이 장의 거절 캡처에서 실험 묶음이 뽑은 진단입니다. 확장 블록의 전용 오류는 CS92xx·CS93xx 에 모여 있습니다.

CS9282 "This member is not allowed in an extension block" 이 가장 넓습니다 — 자동 속성, 필드, field 에 더해 다음 표의 변환 연산자, 인덱서, 이벤트, 생성자도 이 한 번호입니다.

실행 검증

2장의 거절 모음 (2) — 정적 멤버 · 해석 · 연산자 · 키워드

해석 규칙과 연산자 쪽은 오래된 번호(CS0121·CS0111·CS0019·CS0216 …)를 그대로 쓰고, 확장에만 있는 규칙에 새 번호가 붙습니다.

옛 번호가 나온다는 것은 확장 멤버가 보통 멤버의 규칙을 그대로 빌린다는 뜻입니다 — 같은 선언 공간, 같은 연산자 짝, 같은 오버로드 모호함.

실행 검증

200칸이 넘는 진단 넷

컴파일러의 줄이 200칸을 넘어 캡처로 싣지 못한 진단입니다. 실험 묶음이 따로 컴파일해 종료 코드와 오류 번호를 확인하고, 문장 전체를 표로 옮겼습니다.

"accepting a first argument"(CS1061)는 C# 3 이후의 확장 메서드 문장이고, "for receiver of type"(CS9286)은 확장 멤버 전체를 가리키는 C# 14 의 새 문장입니다. 네 줄에서 보이는 갈림은 이렇습니다 — 이름과 형식 인수 개수가 맞는 확장 멤버가 아예 없으면(To<long>, Kind) 옛 번호, 후보는 있는데 고를 수 없으면(제약 위반, 둘이 똑같음) 새 번호. 문서가 적은 규칙이 아니라 이 캡처들에서 읽은 것입니다.

조금 큰 예제 — 확장 멤버로 만든 장바구니

남의 형식(IReadOnlyList<Item>, decimal)에 이 장의 네 가지를 다 씁니다 — 확장 속성(IsEmpty·Total·Won), 확장 메서드(Over), 정적 확장 속성(Empty), 확장 연산자(+).

IReadOnlyList<Item>.Empty + a + b 는 정적 확장 속성에서 시작해 확장 연산자로 이어 붙입니다. 합계 9,700 은 1200×3 + 800×2 + 4500 입니다. 금액 형식은 "N0" 이라 문화권에 따라 쉼표가 달라질 수 있지만, 이 덱의 실행 환경은 불변 문화권(LANG=C)입니다(7부).

실행 검증

2장 퀴즈 (2) — 정적 멤버와 연산자

Q. 두 가지를 맞혀 보세요. (가) 두 정적 클래스가 모두 extension(object o) { public int P => …; } 를 선언했을 때 x.P 의 오류와, 한쪽을 고르는 방법. (나) extension(StringBuilder sb) { public void operator +=(string s) => sb.Append(s); } 가 있을 때 sb += "b"; 가 컴파일되지 않는 까닭.

A. (가) "모호하다"(CS0121)가 아니라 CS9286 "does not contain a definition for 'P'" 입니다. 구현 메서드 E1.get_P(x) 로 고릅니다(모호함). (나) 확장 연산자는 미리 정의된 연산자가 없을 때만 찾습니다. object + string 문자열 연결이 먼저 적용되어 string 이 나오고, 그것을 StringBuilder 에 넣을 수 없어 CS0029 입니다(확장 복합 대입).
