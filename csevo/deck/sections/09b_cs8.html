패턴의 확장 — 식이 된 switch

switch 식 · 속성 패턴 · 위치 패턴 · 튜플 패턴 · 재귀 패턴 · 포인터의 null 패턴 · 결정 DAG · 뒤 버전의 패턴

왜 — "데이터와 기능이 떨어져 사는" 설계

whats-new 의 설명: C# 7.0 의 형식 패턴과 상수 패턴은 "the first tentative steps" 였고, 마이크로서비스와 클라우드 구조로 가면서 다른 도구가 필요해졌다는 것입니다. C# 8.0 은 "more pattern expressions in more places" 를 더하고, 패턴 안에 패턴을 넣는 재귀 패턴을 들여옵니다.

제안서는 목표를 함수형 언어의 대수적 데이터 형식과 패턴 매칭에서 얻는 이점이라고 적고, 영감을 준 언어로 F# 과 Scala 를 듭니다.

switch 식 (switch expression) C# 8.0

왜 — whats-new: switch 문은 case 마다 값을 하나씩 내는 일이 많은데, switch 식은 "fewer repetitive case and break keywords, and fewer curly braces" 로 같은 일을 합니다. 변수가 switch 앞에 오고, case 와 : 는 => 로, default 는 _ 로 바뀌며, 몸체는 문이 아니라 식입니다.

거절 문장이 말하는 기능은 'switch expression' 이 아니라 'recursive patterns' 입니다. 컴파일러의 기능 목록에는 switch 식의 항목이 따로 있지만(IDS_FeatureSwitchExpression), 그 자원 문자열은 꺾쇠로 감싼 <switch expression> 이고 이 덱의 어느 캡처에도 나오지 않았습니다. switch 식은 재귀 패턴과 한 기능으로 확인됩니다 — 아래 게이트 표.

실행 검증

문과 식 — 같은 일을 두 번 써 보기

whats-new 는 같은 무지개 변환을 switch 문으로 다시 써서 견줍니다. 여기서는 HTTP 상태 코드로 같은 대비를 해 봅니다.

switch 식은 값을 내는 식이라 홀로 문이 될 수 없습니다. 제안서도 "not permitted as an expression_statement" 라고 적고, 나중에 풀어 볼 수 있다는 메모를 남겼습니다. 갈래 사이를 넘어가는(fall-through) 일도 없습니다 — 갈래 하나가 식 하나이기 때문입니다.

실행 검증

switch 식의 형식 — 갈래들의 공통 형식, 없으면 대상 형식

제안서: switch 식의 형식은 => 오른쪽 식들의 "best common type" 이고, 그런 형식이 없으면 새로 생긴 switch 식 변환(switch expression conversion)이 대상 형식으로 각 갈래를 바꿉니다.

1 과 2.5 의 공통 형식은 double 이라 a 는 Double 입니다. null 은 형식이 없는 갈래라 "yes" 의 형식을 따릅니다. object c 처럼 대상 형식이 있으면 1 과 "one" 이 각각 object 로 바뀌지만, var 에는 대상이 없어 CS8506 입니다.

실행 검증

빠뜨린 갈래 — 컴파일은 경고, 실행은 예외

whats-new: "A switch expression must either produce a value or throw an exception. If none of the cases match, the switch expression throws an exception. The compiler generates a warning for you if you don't cover all possible cases"

함정 — CS8509 는 오류가 아니라 경고라 빌드는 성공합니다. 문장이 빠진 값(Suit.Club)까지 짚어 주는데도, 경고를 지나치면 실행 중 SwitchExpressionException 으로 프로세스가 죽습니다. 같은 일을 switch 문으로 쓰면 아무 일도 없이 지나갔을 자리입니다.
실행 검증

열거형의 이름을 다 써도 — 이름 없는 값

열거형 변수에는 이름 붙은 값 말고도 그 바탕 형식의 어떤 값이든 들어갈 수 있습니다((B)7). 그래서 이름을 전부 갈래로 써도 switch 식은 "모든 값" 을 덮지 못합니다.

경고 번호가 앞 장과 다른 CS8524 입니다 — "involving an unnamed enum value" 와 반례 (B)2 까지 적습니다. 실행에서 잡은 예외는 System.Runtime.CompilerServices.SwitchExpressionException, 바탕은 InvalidOperationException 이고, UnmatchedValue 로 맞지 않은 값(7)을 들고 옵니다. 제안서가 이름까지 정해 둔 형식입니다.

실행 검증

when 가드와 _ — 갈래에 조건을 더하기

갈래에는 C# 7.0 의 case … when 처럼 가드(case guard)를 붙일 수 있습니다. 제안서의 문법은 pattern case_guard? '=>' expression 이고, 실행 때는 패턴이 맞고 가드가 true 인 첫 갈래가 값을 냅니다.

가드가 거짓이면 다음 갈래로 넘어갑니다 — -5 는 int n 에는 맞지만 n > 0 이 거짓이라 _ 에 닿습니다. _ 는 "default" 의 자리이고, 마지막 갈래로 두면 앞 두 장의 경고와 예외가 생길 여지가 없습니다.

실행 검증

속성 패턴 (property pattern) C# 8.0

왜 — whats-new 의 예는 주소로 판매세를 셈하는 일입니다. 세금 계산은 Address 클래스의 핵심 책임이 아니고 "It will change over time, likely more often than address format changes". 규칙을 클래스 밖에 두고, 객체의 속성을 패턴으로 맞춥니다. 여기서는 배송비로 다시 씁니다.

갈래는 위에서 아래로 처음 맞는 것이 이깁니다 — 제주가 일반 한국 갈래보다 위에 있어야 합니다. 7.3 의 거절은 속성 패턴마다 하나씩, 이름은 다시 'recursive patterns' 입니다.

실행 검증

{ } — null 이 아니면 무엇이든

제안서: 속성 패턴은 먼저 입력이 null 이 아닌지 확인합니다. 그래서 하위 패턴이 하나도 없는 { } 는 "null-checking pattern" 이 되고, 제안서는 s is {} x 를 s is string x, s is object o 와 나란히 듭니다.

null 은 { Length: 0 } 에도 { } t 에도 맞지 않아 셋째 줄에 닿습니다. int? 에서는 "값이 있는가" 가 되고, 맞으면 v 는 int? 가 아니라 int 로 묶입니다. { } t 는 이름을 붙여도 정적 형식이 그대로라 t 는 string 입니다 — is object o 와 다른 점입니다.

실행 검증

속성 패턴 안의 속성 패턴

속성 패턴의 하위 패턴 자리에는 어떤 패턴이든 올 수 있습니다 — 다시 속성 패턴도, var 도, null 도. "Patterns may be recursive so that parts of the data may be matched against sub-patterns."

셋째 주문(부산)은 셋째 갈래 { Home: null } 에 맞지 않고 넷째 { Buyer: { } } 로 갑니다. Qty: var q 처럼 속성 하나를 맞추면서 꺼내 쓸 수도 있습니다. 중괄호가 세 겹 쌓인 첫 갈래가 이 문법의 불편한 곳입니다 — 다음 장.

실행 검증

뒤 버전 — 확장 속성 패턴 A.B, C# 10

겹친 중괄호 { Home: { Name: … } } 를 점 하나로 줄이는 꼴은 C# 10 의 기능입니다. 컴파일러가 버전을 확인하는 기능 목록에 'extended property patterns' 로 들어 있습니다.

셋째 줄 — Home 이 null 이면 Home.Name 을 읽다 죽지 않고 그냥 False 입니다. 점 꼴도 중첩 꼴과 똑같이 각 단계의 null 검사를 품습니다. 자세한 것은 11부에서 봅니다.

실행 검증

형식 + 속성 + 이름 — 한 패턴에 셋

제안서의 문법은 type? property_subpattern simple_designation? 입니다. 형식을 앞에 쓰면 그 형식인지 먼저 보고, 뒤에 이름을 쓰면 맞은 값을 그 형식의 변수로 받습니다. 제안서의 예가 o is string { Length: 5 } s 이고, 익명 형식에도 쓸 수 있다고 적습니다.

필드(Size.W)도 속성처럼 맞춥니다. "hi" 는 두 string 갈래에 모두 맞지 않아 마지막 _ 에서 형식 이름(String)으로 나옵니다. 마지막 줄은 이름이 없는 익명 형식의 속성을 패턴으로 맞춘 것입니다.

실행 검증

위치 패턴 (positional pattern) C# 8.0

왜 — C# 7.0 의 분해(Deconstruct, 8부)가 이미 객체를 낱개의 변수로 풀어 줍니다. whats-new: "When a Deconstruct method is accessible, you can use positional patterns to inspect properties of the object and use those properties for a pattern." 문서의 사분면 예를 체스판 칸으로 다시 씁니다.

제안서: 위치 패턴은 입력이 null 이 아닌지 보고, Deconstruct 를 불러 나온 값마다 하위 패턴을 맞춥니다. var (r, k) 는 (var r, var k) 의 줄임입니다. 7.3 의 거절은 위치 패턴마다 하나, 그 안의 _ 마다 또 하나라 22·23행에서는 둘씩 나옵니다.

실행 검증

Deconstruct 가 없어도 — object 와 ITuple C# 8.0

제안서의 셋째 규칙: 형식을 적지 않았고 입력이 object 나 ITuple 이면, 실행 때 그 객체가 System.Runtime.CompilerServices.ITuple 을 구현하는지 보고 Length 와 인덱서로 원소를 꺼내 맞춥니다.

Tuple<int, int>(클래스)와 상자에 든 (3, 4)(구조체) 모두 맞고, Deconstruct 가 하나도 없는 Pair 도 ITuple 만으로 맞습니다. 배열은 ITuple 이 아니라 맞지 않습니다. 원소 수가 다른 패턴(셋)은 Length 로 걸러집니다.

실행 검증

위치 패턴에 이름 붙이기 — 이름은 검사된다

하위 패턴에는 identifier ':' pattern 처럼 이름을 붙일 수 있습니다. 제안서: 튜플이면 그 이름이 그 자리의 튜플 원소를 가리켜야 하고, Deconstruct 면 그 매개변수 이름과 맞아야 합니다.

이름은 순서를 바꾸는 장치가 아니라 읽는 이를 위한 확인입니다. low 는 Deconstruct 의 lo 와 달라 CS8517, 첫 자리에 Height 를 쓰면 그 자리 원소(Item1, 이름 Width)가 아니라 CS8516 입니다.

실행 검증

튜플 패턴 (tuple pattern) C# 8.0

왜 — "Some algorithms depend on multiple inputs." 입력 여럿을 튜플 하나로 묶어 switch 하면 됩니다. whats-new 는 가위바위보의 승자를 고르는 switch 식을 예로 듭니다. 같은 놀이를 열거형으로 다시 씁니다.

아홉 경우를 갈래 다섯이 덮습니다 — A 가 이기는 셋, var (x, y) when x == y 의 무승부 셋, 나머지는 _. 튜플 패턴은 따로 있는 문법이 아니라 입력이 튜플 형식일 때의 위치 패턴입니다(제안서의 첫 규칙). 컴파일러도 C# 7.3 에서 같은 'recursive patterns' 로 거절합니다 — 게이트 표.

실행 검증

튜플 리터럴을 고를 때 — 원소는 한 번씩, 문은 괄호 하나

제안서는 switch 문에서 튜플 리터럴을 고를 때 쓰던 겹괄호 switch ((a, b)) 를 switch (a, b) 로 줄일 수 있게 했습니다.

갈래 넷이 첫 원소를 살펴봐도 A 와 B 는 한 번씩, 왼쪽부터 불립니다. 원소를 한 번 셈해 둔 뒤 패턴을 맞추기 때문입니다. 아래 switch 문은 괄호가 한 겹인데도 튜플을 고릅니다.

실행 검증

재귀 패턴 (recursive patterns) C# 8.0

왜 — whats-new: "Recursive patterns are patterns that can contain other patterns." 위치·속성 패턴의 하위 패턴 자리에 다시 위치·속성·형식·상수· var 패턴이 들어갑니다. 제안서가 말한 "대수적 데이터 형식" 쪽의 쓰임 — 식 트리 다듬기 — 를 해 봅니다.

Op('+', Num(0), var x) 한 줄이 "덧셈이고, 왼쪽이 Num 이고, 그 값이 0" 이라는 세 겹의 검사입니다. 둘째 식은 덧셈 둘을 먼저 줄인 뒤 곱셈을 남겼습니다(마지막 Op(var s, …) 갈래). C# 7.3 으로 내리면 이 파일 하나에 오류 17개 — 바깥 패턴과 안쪽 패턴마다 하나씩입니다.

실행 검증

컴파일러가 대는 기능 이름 — 거의 전부 'recursive patterns'

이 장의 예제 아홉을 그대로 -langversion:7.3 으로 컴파일해, 오류 문장의 기능 이름만 뽑았습니다.

switch 식도, 튜플 패턴도, { } 도 모두 'recursive patterns' 로 거절됩니다. 괄호 하나짜리 switch (A(), B()) 줄(pattupleval 22행)에는 오류가 없고, 그 아래 case (1, 2) 의 위치 패턴(24행)이 거절됩니다. 따로 이름이 나온 것은 포인터의 null 패턴 하나뿐입니다. 컴파일러의 기능 목록에는 switch 식(IDS_FeatureSwitchExpression)이 따로 있지만, 이 아홉 캡처에서는 한 번도 쓰이지 않았습니다. 8부가 찾은 것(switch 식과 throw)과 같은 결과입니다.

실행 검증

var 패턴과 무시 패턴 _

제안서: var 패턴은 언제나 맞고, var (x, (y, z)) 는 (var x, (var y, var z)) 와 같습니다. 무시 패턴 _ 도 언제나 맞지만 "may not be used as the pattern of an is_pattern_expression".

var v 는 null 에도 맞아 True, 형식 패턴 is string 은 False 입니다. s is _ 는 무시 패턴이 아니라 _ 라는 형식을 찾다가 CS0246 입니다 — C# 7 이전부터 is 의 오른쪽은 형식이었기 때문입니다. Roslyn 의 문서는 그런 형식이 실제로 있을 때 경고(CS8413)를 낸다고 적습니다.

실행 검증

포인터의 null 상수 패턴 C# 8.0

C# 7.0 의 상수 패턴 null 은 포인터 형식에는 쓸 수 없었습니다. C# 8.0 은 이것을 'null pointer constant pattern' 이라는 별도의 기능으로 열었습니다. 문서의 설명은 컴파일러의 기능 목록 한 줄뿐입니다.

7.3 의 거절에 이름이 둘 섞입니다 — switch 식 자체(6행)와 _(9행)는 'recursive patterns', 포인터에 쓴 null (8행·19행)은 'null pointer constant pattern'. q == null 의 비교 연산은 옛날부터 됐으므로 거절되지 않습니다.

실행 검증

가려진 갈래는 오류 — CS8510

제안서: "It is an error if some switch_expression_arm's pattern cannot affect the result because some previous pattern and guard will always match." 순서가 결과를 정하므로, 결과에 닿을 수 없는 갈래는 실수로 봅니다.

switch 식에서는 CS8510, switch 문에서는 C# 7.0 부터 있던 CS8120 입니다. { } 는 null 이 아닌 모든 것이라 그 뒤의 string s 는 닿을 수 없습니다. 반대로 { } 다음의 _ 는 남은 null 을 받으므로 오류가 아닙니다(10행).

실행 검증

byte 의 256 갈래 — 문서의 "C# 8 과 9" 를 다시 재 보면

Roslyn 의 C# 9 호환성 문서: byte 의 값을 모두 갈래로 쓴 switch 식은 "Would produce a warning when compiled in C# 8.0 … but produces no warning in C# 9.0", 거기에 대체 갈래를 더하면 C# 8.0 에선 경고가 사라지지만 C# 9.0 에선 오류라고 적습니다.

꼴 (나) 의 확인 — 지금의 컴파일러는 -langversion:8.0 에서도 C# 9 처럼 굽니다. 경고는 어느 쪽에도 없고, _ 를 더하면 둘 다 CS8510 오류입니다. 문서가 말한 차이는 언어 버전이 아니라 컴파일러 버전의 차이였던 것입니다 — 이 동작은 언어 버전에 묶여 있지 않습니다(0부).
실행 검증

컴파일러가 만드는 것 — 검사를 나눠 쓰는 결정 DAG

제안서: 패턴이 속성을 읽는 차례는 정해져 있지 않고, 컴파일러는 Deconstruct 와 속성 읽기의 차례를 바꾸거나 "may assume that returned values are the same from multiple calls" 라는 언어 설계 회의(LDM)의 결정이 있습니다. 그래서 여러 갈래에 같은 검사가 나오면 한 번만 할 수 있습니다.

위에서 아래로 갈래를 하나씩 해 보는 것이라면 Box(2, 9) 는 Kind 를 다섯 번쯤 읽어야 합니다. 실제로는 어느 상자든 Kind 한 번, 필요하면 Size 한 번입니다. Roslyn 은 갈래 전체를 검사들의 그래프(결정 DAG, decision DAG)로 바꾸고 같은 검사의 결과를 나눠 씁니다. 그래서 패턴에서 읽는 속성은 부작용이 없어야 합니다 — 몇 번 읽힐지는 컴파일러가 정합니다.

실행 검증

Deconstruct 도 한 번 — 갈래가 몇 개든

같은 결정이 Deconstruct 에도 적용됩니다. 위치 패턴 다섯 갈래가 모두 같은 Deconstruct 를 쓰면, 컴파일러는 한 번 불러 나온 값을 모든 갈래에 씁니다.

맨 끝 _ 에 닿은 (-1, 4) 도 한 번입니다. 제안서는 그 뒤에 "we will be very careful before making any changes to the compiler-generated order of evaluation" 이라고 덧붙였습니다 — 이 캡처는 지금의 Roslyn 이 그렇게 한다는 것이지 언어가 약속한 횟수가 아닙니다.

실행 검증

문자열 갈래가 많으면 — 해시로 가르기

제안서의 "가능한 최적화": 패턴이 정수나 문자열이면 컴파일러는 옛 switch 문과 같은 코드를 낼 수 있다. 무엇을 냈는지는 메서드의 IL 에서 호출 명령만 뽑아 보면 보입니다.

갈래가 둘이면 string.op_Equality 로 하나씩 견줍니다. 여덟이면 먼저 ComputeStringHash 를 부르는 코드가 되고, 같음 비교 여덟은 갈래마다 하나씩 남습니다. switch 식(Many)과 C# 1 문법의 switch 문(Stmt)이 같은 호출 목록을 냅니다 — 제안서가 말한 "the same kind of code" 입니다. 몇 개부터 해시를 쓰는지는 Roslyn 의 구현 세부입니다.

실행 검증

뒤 버전 — 관계 패턴과 and·or·not, C# 9

C# 8.0 에서 "0 보다 크다" 는 int n when n > 0 처럼 가드로만 쓸 수 있었습니다. C# 9 는 < 0, >= 90 같은 관계 패턴과 패턴을 묶는 and·or·not 을 더했습니다.

한 줄에서 기능 이름이 넷으로 갈립니다 — 'relational pattern', 'or pattern', 'and pattern', 'not pattern'. C# 8.0 의 패턴이 모두 'recursive patterns' 하나로 묶였던 것과 대조됩니다. 10부에서 다시 봅니다.

실행 검증

뒤 버전 — 목록 패턴, C# 11

C# 8.0 의 위치 패턴은 원소 수가 정해진 것(Deconstruct, 튜플)만 맞춥니다. 배열·목록의 길이와 원소를 맞추는 [first, .., last] 는 C# 11 의 목록 패턴입니다. 이것은 다음 장의 인덱스·범위(Length, 인덱서, 슬라이스)에 기댑니다.

.. var mid 가 가운데 조각을 배열로 받습니다(2 between). 갈래마다 'list pattern' 하나씩 거절됩니다. 12부에서 다시 봅니다.

실행 검증

같이 온 런타임 — SwitchExpressionException 과 ITuple C# 8.0

3장의 패턴 가운데 런타임 형식에 기대는 것은 둘입니다. 빠짐없지 않은 switch 식이 던지는 예외와, 형식 없는 위치 패턴이 쓰는 ITuple 입니다. 제안서가 둘 다 이름으로 적습니다.

둘 다 System.Private.CoreLib 의 System.Runtime.CompilerServices 이름공간에 있습니다. Tuple 과 ValueTuple 은 ITuple 을 구현하지만 KeyValuePair 는 아닙니다 — KeyValuePair 를 object 로 받아 형식 없는 (k, v) 로 맞추면 실패합니다.

실행 검증

3장 퀴즈 — 패턴의 확장

Q1. 열거형 B { Off, On } 의 두 값을 모두 갈래로 쓴 switch 식이 경고를 냅니다. 왜이고, 경고를 무시하면 무슨 일이 생깁니까?

Q2. { Kind: 1, … } 갈래 다섯이 있는 switch 식에서 Kind getter 는 몇 번 불립니까?

A1. 열거형 변수에는 (B)7 처럼 이름 없는 값도 들어갈 수 있어서입니다(CS8524). 그런 값이 들어오면 SwitchExpressionException 이 던져지고 UnmatchedValue 에 그 값이 실립니다. 끝에 _ 갈래를 두면 됩니다.
A2. 이 덱의 캡처에서는 한 번입니다. 컴파일러가 갈래를 결정 DAG 로 바꿔 같은 검사를 나눠 쓰기 때문입니다. 다만 횟수는 언어가 약속한 것이 아니라 — 제안서는 컴파일러가 순서를 바꾸고 같은 값을 가정해도 된다고 적습니다 — getter 에 부작용을 두면 안 됩니다.
설명용

4장

인덱스와 범위 — ^ 와 ..

끝에서 세는 인덱스 · 범위 연산자 · System.Index 와 System.Range · 복사와 공유 · Length·Slice 로 얻는 암시적 지원 · 뒤 버전

왜 — 끝에서 세기, 조각 잘라 내기

범위 제안서의 두 문장이 동기입니다. "C# has no way of indexing a collection from the end, but rather most indexers use the "from start" notion, or do a "length - i" expression." 그리고 "C# has no syntactic way to access "ranges" or "slices" of collections" — 그래서 list.Skip(5).Take(2) 같은 LINQ 에 기대야 했다는 것입니다.

C# 7.3C# 8.0
a[a.Length - 1]a[^1]
s.Substring(2, 3), a.Skip(2).Take(3).ToArray()s[2..5], a[2..5]
(없음)Index i = ^1; Range r = 1..^1; — 값으로 들고 다닌다

버전 기록은 이 기능을 "Ranges, indexes, and asynchronous streams require new types in the .NET Core 3.0 libraries" 라고 적습니다 — 언어 기능이 라이브러리 형식(System.Index, System.Range)에 기대는 C# 8.0 의 첫 사례입니다.

문서 근거

끝에서 세는 인덱스 ^ (index from end) C# 8.0

whats-new: ^0 은 sequence[sequence.Length] 와 같고, "For any number n, the index ^n is the same as sequence.Length - n." 문서는 단어 배열에 앞·뒤 번호를 주석으로 달아 보입니다. 요일로 다시 씁니다.

^1 이 마지막, ^7(= ^Length)이 첫 원소입니다. 끝에서 세는 번호가 1 부터인 까닭은 ^0 이 Length — 끝 바로 뒤 — 이기 때문입니다. ^n 처럼 변수도 됩니다.

실행 검증

^1 은 System.Index 라는 값이다

제안서: ^ 는 "It will be lowered into the appropriate System.Index factory method call" 이고, int 에서 Index 로의 암시적 변환도 있습니다. Index 는 음수로 만들면 예외를 던집니다.

last 는 "끝에서 1" 이라는 뜻만 들고 있고, 어느 배열에 쓰느냐에 따라 30 도 5 도 됩니다. GetOffset(10) 이 그 셈(10 − 1 = 9)입니다. ^n 에 −1 을 주면 Index 생성자의 value 매개변수가 ArgumentOutOfRangeException 을 던집니다.

실행 검증

^0 은 끝 바로 뒤 — 원소가 아니다

whats-new: "Note that sequence[^0] does throw an exception, just as sequence[sequence.Length] does." 반면 범위의 끝으로는 ^0 이 자연스럽습니다 — 범위의 끝은 포함하지 않기 때문입니다.

함정 — ^0 의 예외는 Index 가 아니라 배열 접근이 던지는 IndexOutOfRangeException 입니다. 제안서도 "^0 does not throw" — Index 값 자체는 멀쩡하고 그것을 원소로 쓰는 순간에 실패합니다. ^4 는 3 − 4 = −1 번 원소라 같은 예외입니다.
실행 검증

범위 연산자 .. (range operator) C# 8.0

whats-new: "The start of the range is inclusive, but the end of the range is exclusive". 양쪽 끝은 생략할 수 있고, 범위도 변수에 담을 수 있습니다.

w[3..3] 처럼 시작과 끝이 같으면 빈 배열이지 오류가 아닙니다. 7.3 의 거절은 .. 마다 'range operator', 그 안의 ^ 마다 'index operator' 가 따로 나옵니다 — 두 기능은 컴파일러의 목록에서도 따로입니다.

실행 검증

1..^1 은 System.Range 라는 값이다

제안서: .. 는 Range 생성자나 팩토리(StartAt, EndAt, All)로 낮춰집니다. 생성자만 있어도 모든 꼴을 만들 수 있고, 다른 멤버가 있으면 그것으로 바꿔 쓸 수 있습니다.

같은 2..^1 이 길이 5 에서는 (2, 2개), 길이 10 에서는 (2, 7개)입니다 — Range 는 길이를 모르는 채 두 Index 를 들고 있다가 길이를 받을 때 셈합니다. .. 와 Range.All 은 같은 값입니다.

실행 검증

함정 — .. 는 + 보다 먼저 묶인다

제안서의 문법은 범위 연산자를 위해 새 우선순위를 만듭니다: "This new precedence group is lower than the unary operators and higher than the multiplicative arithmetic operators." 덧셈은 그보다 더 아래입니다.

a[i..i + 3] 는 (i..i) + 3 으로 읽혀 Range 에 int 를 더하려다 CS0019 입니다. 단항 연산자인 ^ 는 .. 보다 먼저 묶이므로 ^3.. 은 괄호가 필요 없습니다.

실행 검증

배열의 범위는 복사, Span 의 범위는 공유

제안서: 배열의 범위는 System.Runtime.CompilerServices.RuntimeHelpers.GetSubArray 로, 그 밖의 형식은 Slice 로 낮춰집니다. GetSubArray 는 새 배열을 돌려주고, Span<T>.Slice 는 같은 메모리를 가리키는 창을 돌려줍니다.

함정 — a[1..3] 은 볼 때마다 할당입니다. 전체 범위 a[..] 도 원래 배열이 아니라 새 사본입니다. 조각을 고쳐 원래 배열을 바꾸려 했다면 AsSpan() 을 거쳐야 합니다(8부의 Span 조각).
실행 검증

문자열의 범위는 Substring

제안서는 string 을 특별히 다룹니다: "the method Substring will be used instead of Slice."

배열과 반대로 s[..] 는 원래 문자열 그 객체입니다(True). Substring(0, Length) 이 자기 자신을 돌려주는 .NET 의 구현 때문입니다 — 문자열은 바꿀 수 없으니 같은 객체여도 문제가 없습니다. 새 문자열을 만들지 않으려면 AsSpan() 을 잘라 int.Parse 에 바로 넘깁니다.

실행 검증

컴파일러가 부르는 것 — 형식마다 다른 메서드

제안서: 두 연산자는 "lowered to regular indexer/method calls, with no change in subsequent compiler layers". 3장의 IL 도구로 Slice 메서드의 호출만 뽑아 봅니다.

배열의 범위는 Index 두 개로 Range 를 만든 뒤 GetSubArray, 문자열은 Range 없이 길이를 읽어 Substring, Span 은 Slice 입니다. 배열의 a[^1] 은 호출이 하나도 없습니다 — a[a.Length - 1] 로 바로 바뀌어 ldlen 명령만 씁니다.

실행 검증

Length 와 this[int] 만 있으면 — 암시적 Index 지원 C# 8.0

제안서: Length 나 Count 속성(Countable)과 int 하나를 받는 인덱서가 있는 형식이면, 언어가 this[Index] 가 있는 것처럼 다뤄 줍니다. "This allows developers to use the Index feature on existing types without the need for modification." 제안서의 부작용 예(Get → Length 순서)를 다시 써 봅니다.

Get()[^1] 은 Get() 한 번, Length 한 번, this[3] 입니다 — 제안서가 정한 순서(받는 쪽 → 인수 → 길이 → 인덱서) 그대로입니다. 변수에 담은 Index 도 같은 꼴(GetOffset(Length))이고, 보통의 [1] 은 Length 를 읽지 않습니다. C# 7.3 으로 내리면 이 암시적 지원도 같은 'index operator' 로 거절됩니다 — ^1 하나에 두 번(27행의 35·41열).

실행 검증

Slice(int, int) 가 있으면 — 암시적 Range 지원

범위도 같은 방식입니다: Countable 이고 int 두 개를 받는 Slice 가 있으면 됩니다. 시작과 길이로 바꿔 넘기며, "In case both Length and Count are present, Length will be preferred."

log[1..4] 는 길이를 읽지 않고 바로 Slice(1, 3) — 두 끝이 앞에서 센 int 라 4 − 1 로 셈이 끝납니다. ^2.. 처럼 끝에서 세면 길이가 필요하고, 이때 Count 가 아니라 Length 를 읽습니다. 제안서가 Slice 라는 이름을 고른 까닭은 Span 류가 이미 그 이름을 썼기 때문입니다.

실행 검증

List<T> — ^ 는 되고, 범위는 .NET 10 에서 된다

whats-new 는 인덱스·범위를 지원하는 형식으로 배열, string, Span<T>, ReadOnlySpan<T> 를 듭니다. List<T> 는 Count 와 this[int] 가 있으니 암시적 Index 지원으로 ^1 이 됩니다. 제안서는 List<T> 가 Slice 를 가졌다면 좋았을 형식이라고 적었습니다.

.NET 10 의 List<T> 에는 Slice(Int32, Int32) 가 있어(마지막 줄) list[1..3] 이 컴파일되고 새 List<int> 를 돌려줍니다 — 사본이라 part[0] = 99 가 원래 목록에 닿지 않습니다. 언어는 그대로인데 라이브러리가 메서드 하나를 더해 범위가 생긴 것입니다. 이 메서드가 어느 .NET 에서 생겼는지는 받아 둔 문서에 없어 적지 않습니다.

실행 검증

^ 가 안 되는 곳 — 다차원 배열, Dictionary, IEnumerable

제안서의 구현 결정: "The indexer used for the Index pattern must have exactly one int parameter", 그리고 "we look for original definitions, not constructed members".

다차원 배열은 CS0029. Dictionary<int, string> 은 Count 도 this[int] 도 있어 보이지만, 원래 정의의 인덱서는 this[TKey] 라 패턴에 들지 않습니다(CS1503) — 들었다면 d[^1] 이 "마지막 원소" 가 아니라 "키가 Count − 1 인 값" 이 됐을 것입니다. 인덱서가 없는 IEnumerable·Queue 는 CS0021 입니다.

실행 검증

범위가 어긋나면 — 모두 ArgumentOutOfRangeException

범위는 실행 때 길이에 맞춰 시작과 길이로 바뀝니다(GetOffsetAndLength). 시작이 끝보다 뒤이거나 길이를 넘으면 그 셈에서 실패합니다.

배열·문자열·Span 모두 같은 예외입니다. 앞 장의 a[^0](원소 접근, IndexOutOfRangeException)과 예외 형식이 다르다는 것이 함정입니다. 빈 범위 a[1..1] 은 예외가 아닙니다.

실행 검증

라이브러리가 받는 Index·Range — 길이 없는 시퀀스에도

언어의 ^·.. 는 인덱서가 있는 형식에만 붙습니다(앞 장의 IEnumerable). 그러나 Index 와 Range 는 보통의 값이라 메서드 인수로도 넘길 수 있고, .NET 10 의 LINQ 에는 그것을 받는 오버로드가 있습니다.

언어 버전은 8.0 그대로입니다 — 쓴 문법은 C# 8 의 ^ 와 .. 뿐이고, 나머지는 라이브러리의 메서드입니다. 이 오버로드들이 어느 .NET 에서 생겼는지는 받아 둔 문서에 없어 적지 않습니다.

실행 검증

같이 온 런타임 — System.Index, System.Range, GetSubArray C# 8.0

제안서가 "well-known types and members" 로 적은 것은 Index(int, bool) 생성자, GetOffset, Range 의 생성자와 StartAt·EndAt·All, 그리고 배열용 RuntimeHelpers.GetSubArray 입니다. 버전 기록은 이것을 .NET Core 3.0 라이브러리의 새 형식이라고 적습니다.

둘 다 System.Private.CoreLib 의 값 형식입니다 — ^1 과 1..2 는 힙 할당이 없습니다. 제안서의 목록에 더해 .NET 10 에는 Index.Start·Index.End, FromStart·FromEnd 같은 멤버도 있습니다.

실행 검증

뒤 버전 — 객체 초기화자 안의 ^, C# 13

C# 8.0 의 ^ 는 객체 초기화자의 인덱서 자리({ [^1] = 9 })에서는 쓸 수 없었습니다. 컴파일러의 기능 목록은 이것을 C# 13 의 'implicit indexer initializer' 로 둡니다.

초기화자에서도 ^1 이 Length − 1 로 셈해져 마지막 칸에 9 가 들어갔습니다. 14부에서 다시 봅니다.

실행 검증

4장 퀴즈 — 인덱스와 범위

Q1. int[] a 에 대해 a[a.Length..] 와 a[^0] 은 각각 어떻게 됩니까?

Q2. var x = a[i..i + 2]; 는 왜 컴파일되지 않습니까?

Q3. a[1..3][0] = 9; 와 a.AsSpan()[1..3][0] = 9; 중 a 를 바꾸는 것은?

A1. a[a.Length..] 은 빈 배열입니다(시작과 끝이 모두 길이 — a[1..1] 처럼). a[^0] 은 원소 접근이라 IndexOutOfRangeException 입니다.
A2. .. 가 + 보다 먼저 묶여 (i..i) + 2 가 되기 때문입니다(CS0019). a[i..(i + 2)] 로 씁니다.
A3. 뒤의 것입니다. 배열의 범위는 GetSubArray 가 만든 사본이고, Span 의 범위는 같은 메모리를 가리킵니다.

비동기 스트림과 using — 기다리며 돌고, 기다리며 닫는다

IAsyncEnumerable 과 await foreach · 취소 · ConfigureAwait · 상태 기계 · await using · using 선언 · ref struct 의 Dispose 패턴

비동기 스트림 (asynchronous streams) C# 8.0

왜 — 제안서: C# 에는 반복기도 async 메서드도 있지만 "no support for a method that is both an iterator and an async method". whats-new 가 꼽는 세 조건은 async 한정자, IAsyncEnumerable<T> 반환, 그리고 yield return 입니다. 쓰는 쪽은 foreach 앞에 await 를 붙입니다. 첫 모습은 6부에서 봤습니다 — 여기서는 더 깊이 봅니다.

Pages(3) 를 불러도 몸체는 한 줄도 돌지 않습니다 — "[Pages starts]" 는 첫 MoveNextAsync, 곧 await foreach 가 시작될 때 찍힙니다. 동기 반복기(3부)와 같은 늦은 실행입니다.

실행 검증

C# 7.3 이라면 — Task<List<T>> 는 다 모은 뒤에야

C# 7.3 에서 "비동기로 여러 값을 돌려주기" 는 보통 Task<List<T>> 였습니다. 값 하나하나는 비동기로 만들어도 호출자는 마지막 값까지 기다려야 첫 값을 봅니다.

위는 "made" 셋 다음에 "got" 셋, 아래는 made·got 이 번갈아 나옵니다. 비동기 스트림은 첫 값을 바로 쓰게 하고, 목록 전체를 메모리에 모을 필요도 없습니다.

실행 검증

await foreach 를 풀어 쓰면

제안서가 적은 "typical consumption (without additional language features)" 이 await foreach 의 뜻입니다: GetAsyncEnumerator, while (await e.MoveNextAsync()), Current, 그리고 finally 의 await e.DisposeAsync().

두 번 모두 반복기의 finally 가 끝에 돕니다 — DisposeAsync 가 그것을 부릅니다. MoveNextAsync 가 Task<bool> 이 아니라 ValueTask<bool> 인 것은 할당을 줄이려는 선택이라고 제안서가 적습니다.

실행 검증

인터페이스 없이 await foreach — 이름으로 찾는다

제안서: await foreach 는 IAsyncEnumerable<T> 말고도 같은 모양의 공개 멤버(GetAsyncEnumerator, MoveNextAsync, Current, DisposeAsync)를 패턴으로 받습니다. 할당을 피하는 구조체 열거자를 쓸 수 있게 하려는 것입니다.

DisposeAsync 도 이름으로 찾아 불렀습니다. 동기 foreach 가 C# 1 부터 GetEnumerator 를 이름으로 찾던 방식(2부)을 비동기로 옮긴 것입니다.

실행 검증

취소 토큰 두 개 — [EnumeratorCancellation] 이 합친다 C# 8.0

제안서: 특성이 붙은 매개변수가 있으면 "if a token is passed to the GetAsyncEnumerator method, that token should be used instead of the value originally passed". 6부는 WithCancellation 하나만 봤습니다. 호출에도 토큰을 주고 WithCancellation 에도 주면 어떻게 될까요?

특성이 있으면 a 를 취소하든 b 를 취소하든 2 에서 멈춥니다 — 반복기가 보는 ct 는 둘을 이은 토큰입니다(다음 장의 combinedTokens 필드). 특성을 빼면 b 는 버려져 5 까지 돕니다. 이때 컴파일러는 경고를 냅니다 — 자원 파일의 문장 그대로 "…none of them is decorated with the 'EnumeratorCancellation' attribute, so the cancellation token parameter from the generated 'IAsyncEnumerable<>.GetAsyncEnumerator' will be unconsumed". 이 문장이 캡처의 200칸을 넘어, 위 캡처는 -nowarn:8425 로 껐습니다.

실행 검증

break 하면 — finally 가 기다려 가며 돈다

제안서가 IAsyncDisposable 이 꼭 필요하다고 본 까닭: "Since finally blocks may contain awaits, and since finally blocks need to be run as part of disposing of iterators, we need async disposal."

break 가 루프를 끝내면 await foreach 의 finally 가 DisposeAsync 를 기다리고, 그것이 반복기의 finally — 안의 await Task.Delay 까지 — 를 돌립니다. "after the loop" 는 커서가 닫힌 뒤에야 찍힙니다.

실행 검증

ConfigureAwait 와 WithCancellation — 인터페이스가 아닌 래퍼

whats-new: "By default, stream elements are processed in the captured context. If you want to disable capturing of the context, use the …ConfigureAwait extension method." 제안서는 이 래퍼가 패턴 기반 await foreach 로 돌게 설계했습니다.

.NET 10 에서 둘 다 ConfiguredCancelableAsyncEnumerable<T> 라는 구조체이고, 구현한 인터페이스가 0 개입니다. 그래도 await foreach 가 도는 것은 앞의 패턴 규칙 덕분입니다. 대신 IAsyncEnumerable<T> 를 받는 메서드에는 넘길 수 없습니다.

실행 검증

컴파일러가 만드는 것 — 비동기 반복기 클래스의 필드

6부는 생성된 클래스가 구현하는 인터페이스를 봤습니다. 이번엔 그 클래스가 무엇을 들고 다니는지 필드를 봅니다. 이름과 형식은 Roslyn 의 구현 세부이고 언어가 정한 것이 아닙니다.

상태(<>1__state)와 현재 값, 매개변수의 원본(<>3__n)과 작업용 사본(n) — 동기 반복기와 같은 뼈대입니다. 거기에 async 의 빌더(AsyncIteratorMethodBuilder), MoveNextAsync 의 ValueTask<bool> 를 받쳐 줄 ManualResetValueTaskSourceCore, 취소를 위한 <>x__combinedTokens, 그리고 Dispose 중인지를 적는 <>w__disposeMode 가 더해졌습니다.

LINQ — 제안서는 미뤘고, .NET 10 에는 있다

제안서: Enumerable 의 오버로드가 200 개쯤인데 비동기판을 따로 만들면 또 그만큼이라, 언어·코어 라이브러리에서는 하지 않고 커뮤니티의 Interactive Extensions(Ix)를 돕겠다고 적었습니다 — "the proposal is to do nothing additional here right now".

.NET 10 의 참조 팩에는 System.Linq.AsyncEnumerable 이라는 어셈블리가 있고, 패키지 없이 이 코드가 돕니다. 언제 들어왔는지는 받아 둔 문서에 없어 적지 않습니다 — "2026-10 기준, .NET 10 에는 있다" 까지입니다.

실행 검증

비동기 스트림의 규칙 — 네 가지 거절

whats-new: await foreach 를 쓰는 메서드는 async 여야 하고, 비동기 스트림을 만드는 메서드는 async 한정자와 yield return 을 함께 가져야 합니다.

yield 가 없으면 반복기가 아니라 보통의 async 메서드가 되어, 반환 값이 없다는 CS0161 이 나옵니다. catch 가 있는 try 안의 yield return 은 C# 2 의 규칙(CS1626)이 비동기 반복기에도 그대로입니다. 파일 이름이 A.cs 인 것은 CS4033 의 긴 문장이 캡처의 줄 한도에 들어가게 하려는 것입니다.

await using (asynchronous using) C# 8.0

왜 — whats-new: C# 8.0 은 IAsyncDisposable 을 구현한 형식을 지원하고 "You use the await using statement" 로 씁니다. 제안서의 말로는 닫는 일 자체가 시간이 걸릴 수 있기 때문입니다 — "closing files (requiring flushes)" 같은. 블록 꼴과 선언 꼴이 있다는 것은 6부에서 봤고, 여기서는 닫는 차례를 봅니다.

연 차례의 거꾸로 닫힙니다 — a, b 를 열면 b, a. 선언 꼴의 c, d 는 Main 이 끝날 때 d, c 입니다. 동기 using 의 규칙이 그대로이고, 다른 점은 DisposeAsync 의 ValueTask 를 기다린다는 것뿐입니다. C# 7.3 의 거절에는 'asynchronous using'·'using declarations' 마다 'pattern-based disposal' 이 하나씩 따라옵니다 — await using 이 DisposeAsync 를 이름(패턴)으로 찾기 때문으로 보이며, 6부도 같은 것을 봤습니다.

실행 검증

Dispose 와 DisposeAsync 를 다 가진 형식

제안서: 한 형식이 IDisposable 과 IAsyncDisposable 을 함께 구현해도 되고, 어느 쪽을 먼저 부르든 처음 것만 의미가 있어야 합니다. Roslyn 의 호환성 문서는 await using 이 인터페이스 구현보다 공개 DisposeAsync() 를 고르도록 바뀌었다고 적습니다("Introduced in Visual Studio 2022 version 17.10p3").

using 은 Dispose, await using 은 공개 DisposeAsync 하나만 부릅니다 — 둘 다 부르지 않습니다. 변수의 형식이 IAsyncDisposable 이면 공개 메서드가 보이지 않으니 인터페이스 구현이 불립니다. 같은 객체라도 정적 형식에 따라 다른 메서드가 불리는 셈이라, 두 구현은 같은 일을 해야 합니다.

using 선언 (using declaration) C# 8.0

왜 — 제안서: using 문은 좋은 도구지만 "requires quite a bit of ceremony". 자원이 여럿이면 문이 겹겹이 쌓이고, 그래서 코딩 지침들이 이 경우만 중괄호 규칙에 예외를 둘 정도였다는 것입니다. using 을 지역 변수 선언 앞에 붙이면 둘러싼 범위가 끝날 때 닫힙니다.

제안서의 규칙 그대로 "disposed in the reverse order in which they are declared" — d, c, b, a 입니다. 반환 값 42 는 닫기 전에 셈해집니다: "body" 다음에 Dispose 넷이 돌고, 그 뒤에 호출자가 "Work() = 42" 를 찍습니다.

실행 검증

"둘러싼 범위" — 루프 몸체, if 블록, 메서드

whats-new: "the file is disposed when the closing brace for the method is reached. That's the end of the scope in which file is declared." 범위는 메서드만이 아니라 선언이 놓인 블록입니다.

루프 몸체 안의 r 은 바퀴마다 열리고 닫힙니다. outer 는 "end of Main" 뒤, 메서드를 나갈 때 닫힙니다.

함정 — 블록 안에서 일찍 닫혀야 하는 자원(잠금, 파일 핸들)에 메서드 범위의 using 선언을 쓰면, 메서드가 끝날 때까지 쥐고 있게 됩니다. 그럴 땐 옛 using 문이나 블록 { } 을 씁니다.
실행 검증

제안서의 goto 예제 — 지금의 컴파일러는 거절한다

제안서: "There are no restrictions around goto, or any other control flow construct in the face of a using declaration." 그리고 레이블 뒤의 using 선언으로 goto 를 되돌리면 "Causes f2 to be disposed but has no effect on f1" 이라는 예를 듭니다.

Roslyn 은 CS8649 — "A goto cannot jump to a location before a using declaration within the same block" — 로 거절합니다. 제안서의 문장과 실제 컴파일러가 어긋나는 곳입니다. 이 덱은 컴파일러를 따릅니다: using 선언 앞으로 되돌아가는 goto 는 C# 14 / .NET 10 에서 오류입니다.

실행 검증

using 선언을 못 쓰는 곳

제안서의 제약: case 레이블 바로 안에는 못 오고(블록 안이어야 함), 선언마다 초기화가 있어야 하며, 형식은 IDisposable 이거나 패턴을 만족해야 합니다. 지역 변수는 "implicitly read-only" 입니다.

case 바로 안은 CS8647 — 문장이 "consider using braces" 라고 해법까지 말합니다. 제안서는 그 까닭을 수명 문제로 들고, 중괄호 하나면 되는 우회가 쉬워 따로 규칙을 만들지 않았다고 적습니다. using var t; 는 오류가 둘(CS0818, CS0210)입니다.

실행 검증

null 이면 건너뛰고, 예외가 나도 닫는다

제안서: using 선언은 같은 자리의 using 문과 "the same effect" 이고, using 의 규칙 — "a null value will not cause an exception to be thrown" — 이 그대로입니다.

첫 호출은 r 이 null 이라 "dispose" 가 없고 예외도 없습니다. 둘째 호출은 몸체가 던졌지만 "dispose" 가 먼저 찍히고, 그 뒤에 바깥의 catch 가 받습니다 — try/finally 로 바뀌기 때문입니다.

ref struct 의 Dispose 패턴 (disposable ref structs) C# 8.0

왜 — whats-new: ref 로 선언한 구조체는 인터페이스를 구현할 수 없어 IDisposable 도 구현할 수 없습니다 (8부). 그래서 "it must have an accessible void Dispose() method" 이면 using 에 쓸 수 있게 했습니다.

C# 7.3 은 ref struct 를 쓴 using 문(26행)을 'pattern-based disposal' 하나로 거절합니다. 패턴은 ref struct 에만 열렸습니다. Dispose 가 있는 보통 구조체 Plain 은 여전히 CS1674 입니다 — 제안서가 "the notion of a disposable pattern for ref struct types" 라고 범위를 그었습니다. 인터페이스를 구현할 수 있는 형식은 인터페이스를 쓰라는 것입니다.

실행 검증

foreach 도 ref struct 열거자의 Dispose 를 부른다

Roslyn 의 VS2019 호환성 문서: "A ref struct enumerator with an accessible void Dispose() instance method will now have it invoked at the end of enumeration", 그 예의 메서드 이름이 "Called in C# 8.0 only" 입니다.

ref struct 열거자는 끝에 Dispose 가 불리고, IDisposable 이 아닌 클래스 열거자는 불리지 않습니다. C# 7.3 으로 내리면 foreach 문이 'pattern-based disposal' 로 거절됩니다 — 조용히 동작이 바뀌는 대신, 옛 버전에서는 컴파일 자체를 막습니다. ref struct 가 IDisposable 을 구현할 수 있게 된 것은 C# 13 입니다(8부).

같이 온 런타임 — IAsyncEnumerable, IAsyncDisposable 과 그 도우미 C# 8.0

제안서는 두 인터페이스와 IAsyncDisposable 을 "the core .NET libraries" 에 더한다고 적고, 버전 기록은 비동기 스트림이 .NET Core 3.0 라이브러리의 새 형식에 기댄다고 적습니다.

인터페이스 셋, 특성, 컴파일러용 빌더(AsyncIteratorMethodBuilder), ConfigureAwait·WithCancellation 의 래퍼와 확장 메서드까지 모두 System.Private.CoreLib 에 있습니다. LINQ(앞 장)만 별도 어셈블리입니다.

5장 퀴즈 — 비동기 스트림과 using

Q1. 비동기 반복기를 부른 직후, 첫 await foreach 전에 몸체의 첫 줄은 돌았습니까?

Q2. using var a = …; using var b = …; 가 있는 메서드가 return F(a); 로 끝납니다. F, a.Dispose, b.Dispose 의 차례는?

Q3. Dispose() 가 있지만 IDisposable 을 구현하지 않은 보통 구조체를 using var 에 쓸 수 있습니까?

A1. 아닙니다. 몸체는 첫 MoveNextAsync 에서 시작합니다 — 동기 반복기와 같은 늦은 실행입니다.
A2. F 가 먼저 셈해지고, 그 뒤 선언의 거꾸로 b, a 순으로 닫힙니다.
A3. 없습니다(CS1674). C# 8.0 의 Dispose 패턴은 인터페이스를 구현할 수 없는 ref struct 에만 열렸습니다.
