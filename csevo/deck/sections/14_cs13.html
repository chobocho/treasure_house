BCL 은 params 컬렉션을 얼마나 쓰나 — .NET 10 에서 센다

params 컬렉션 제안서의 동기 하나는 "add a params span overload and have it take precedence over the array version" 입니다. 어셈블리 셋의 공개 메서드·생성자에서 마지막 매개변수가 params 인 것을 셉니다.

이 수는 .NET 10.0.12 의 것입니다. .NET 9 의 BCL 은 이 기계에 없어서 C# 13 이 나온 날의 수는 셀 수 없습니다. 눈여겨볼 것은 둘입니다 — 센 세 어셈블리의 params 컬렉션은 모두 ReadOnlySpan<T> 이고, System.Collections.Immutable 에서는 스팬 판(18)이 배열 판(10)보다 많습니다. 같은 이름의 배열 판과 스팬 판이 함께 있을 때 무엇이 불리는지는 2장에서 봅니다.

1장 퀴즈 — C# 13 개관

Q. C# 13 기능 넷을 몸체에 쓴 파일을 -langversion:12.0 으로 컴파일했더니 \e 하나만 거절됐습니다. 나머지 셋은 C# 12 에서도 되는 기능일까요?

A. 아닙니다. \e 는 어휘 분석 단계에서 확인하는 게이트라, 그 오류가 나면 의미 분석의 거절이 나오지 않습니다. \e 를 \u001b 로 바꾸면 ref 지역 변수, ^ 인덱스, Lock 이 모두 CS9202 로 거절됩니다(앞 장). 거절 시연은 기능 하나씩 해야 믿을 수 있습니다.

params 컬렉션 — 배열 밖으로 나온 params

동기 · 스팬 · 인터페이스와 구체 형식 · 할당과 IL · 오버로드 · 다시 컴파일한 BCL 호출 · 메타데이터 · 제약 · 더 나은 변환 ·

왜 생겼나 — 배열 오버로드가 치르던 할당

제안서의 요약은 한 문장입니다 — C# 12 의 컬렉션 식이 배열 아닌 컬렉션을 만들게 되었으니, "This proposal extends params support to all such collection types."

  • 지금까지 params 는 배열뿐이었습니다(2부). 컬렉션을 받는 API 는 배열을 받는 params 오버로드를 하나 더 두고 그 안에서 대상 컬렉션을 만들었고, 쓰는 쪽은 "trade an extra array allocation for convenience" 였습니다.
  • 컴파일러가 배열 할당을 아예 피할 수 있는 형식이 있습니다 — ImmutableArray<T>, ReadOnlySpan<T>.
  • 라이브러리가 스팬 판 오버로드를 더하면, 쓰는 쪽은 "just by recompiling" 새 판을 부르게 됩니다(뒤에서).

C# 12 의 컬렉션 식(13부)이 만드는 규칙을 params 가 빌려 씁니다. 13부의 앞당긴 장(13부)에서 스팬과 IEnumerable 을 잠깐 보았습니다. 이 장은 그다음 — 무엇이 만들어지고, 어떤 오버로드가 이기고, 어디서 막히는지를 봅니다.

왜 — whats-new: "The params modifier isn't limited to array types. You can now use params with any recognized collection type". 예제의 Concat<T> 는 whats-new 의 것 그대로입니다.

인수가 없으면 빈 스팬(셋째 줄의 빈 출력)이고, 배열은 스팬으로 바뀌어 정상 꼴(normal form)로 넘어갑니다. 거절은 선언의 params 한 곳입니다. 배열을 넘기는 줄에 <int> 를 적은 까닭은 다음 장에 있습니다.

실행 검증

함정 — 배열 하나를 넘기면 T 는 int[]

whats-new 의 Concat<T> 에 형식 인수 없이 배열을 넘깁니다. C# 13 의 형식 추론은 int[] 에서 ReadOnlySpan<T> 의 T 를 끌어내지 못하고, 확장 꼴(expanded form)에서 배열 자체를 원소 하나로 봅니다.

함정 — C# 13 에서 Concat(arr) 는 컴파일 오류도 경고도 없이 T = int[], 원소 하나입니다. params T[] 였다면 T = int 로 원소 둘이었을 호출입니다.

C# 14 의 "first-class support for Span<T> and ReadOnlySpan<T>" 가 이 추론을 고칩니다 — 같은 소스가 C# 14.0 에서는 Int32 x2 입니다. 그 기능은 15부에서 다룹니다.

생성자·Add·생성 메서드는 "at least as accessible as the declaring member" 이어야 합니다. 확장 메서드 Add 는 세지 않습니다. 선택적 매개변수 뒤에 올 수는 있지만 기본값은 가질 수 없습니다 — 인수를 빼면 빈 컬렉션이 만들어지기 때문입니다(뒤에서).

문서 근거

인터페이스로 받으면 무엇이 오나

whats-new: "When an interface type is used, the compiler synthesizes the storage for the arguments supplied." 다섯 인터페이스로 받아 실제 형식과 IsReadOnly 를 찍습니다.

읽기 전용 인터페이스 셋은 컴파일러가 합성한 <>z__ReadOnlyArray`1 을 받고, 원소가 하나면 <>z__ReadOnlySingleElementList`1, IEnumerable 에 인수가 없으면 빈 Int32[] 입니다. ICollection<T> · IList<T> 는 고칠 수 있는 List`1 입니다. 컬렉션 식이 같은 인터페이스를 대상으로 할 때와 같은 규칙입니다(13부). 받는 쪽이 형식을 캐스트해 고치는 코드는 이 차이에 걸립니다.

실행 검증

구체 형식 — List, HashSet, ImmutableArray, Span

whats-new 는 스팬과 "types that implement IEnumerable<T> and have an Add method" 를 꼽습니다. ImmutableArray<T> 는 Add 대신 빌더 특성으로 만들어집니다.

함정 — Set(1, 2, 2, 3) 은 인수 넷을 넘겼는데 Count=3 입니다. params HashSet<T> 는 원소를 Add 하므로 중복이 조용히 사라집니다. 받는 형식의 의미가 그대로 호출에 스며듭니다.

List 는 인수 개수만큼 Capacity 를 잡습니다(3, 빈 것은 0). Span<T> 는 고칠 수 있어서 메서드가 원소를 바꿀 수 있지만, 그 저장소는 호출한 쪽이 이 호출만을 위해 만든 것이라 바깥에 보이지 않습니다.

[CollectionBuilder] 형식을 params 로

제안서: 생성 메서드가 "can be invoked with no additional arguments" 인 형식도 params 가 됩니다. 13부의 Bag<T> 꼴(13부)을 그대로 씁니다.

실행 검증

정상 꼴과 확장 꼴 — null 과 캐스트

제안서: 인수가 매개변수 형식으로 바로 바뀌면 "acts precisely like a value parameter"(정상 꼴), 아니면 원소들로 컬렉션을 만듭니다(확장 꼴). 둘 다 되는 모호함은 "can be resolved by inserting a cast or using a collection expression" 입니다.

E(list) 는 그 List 자체를, (object)list 는 원소 하나짜리 합성 목록을 받습니다. E(null) 은 정상 꼴이라 매개변수가 null 입니다. 그런데 스팬은 다릅니다 — S(null) 은 null 배열이 스팬으로 바뀌어 길이 0 이고, null 원소 하나를 넘기려면 (string)null 이라고 써야 합니다. params object[] 의 같은 함정(2부)과 견주어 보십시오.

실행 검증

params 스팬 — 배열 없는 가변 인수 C# 13.0

왜 — 제안서의 동기: "Especially in cases when compiler is able to avoid an implicit array allocation for the purpose of creating the collection". 시간을 재지 않고, 같은 호출을 100번 하는 동안 힙에 잡힌 바이트를 GC.GetAllocatedBytesForCurrentThread() 로 셉니다.

최적화하면 배열 판은 호출마다 원소 3개짜리 int[] 40바이트, 8개짜리 56바이트를 잡고 스팬 판은 0 입니다. 인수가 없으면 둘 다 0 — 빈 배열도 새로 만들지 않습니다. 받는 메서드에 NoInlining 을 단 것은 호출이 펼쳐지지 않은 그대로를 재기 위해서입니다.

함정 — 최적화 없이(디버그) 컴파일하면 상수 스팬이 호출마다 72바이트를 잡습니다. 13부에서 본 컬렉션 식의 상수 스팬과 같은 현상입니다 (13부). 할당을 재려면 Release 로.

컴파일러가 만든 것은 IL 에서 봅니다. 도구는 13부에서 쓴 것(13부)을 그대로 가져왔습니다 — MethodBody.GetILAsByteArray() 를 연산 코드 표로 훑어 메서드·형식·토큰을 가리키는 명령만 찍습니다. 3장의 lock 도 이것으로 봅니다.

긴 이름(데이터 필드의 해시 이름 등)은 앞 8자만 찍고 … 를 붙입니다.

실행 검증

params 호출이 만드는 것 — IL 로

제안서: 확장 꼴은 인수들로 "as though the arguments were used as expression elements in a collection expression" 컬렉션을 만듭니다. 그래서 번역도 컬렉션 식의 번역(13부)과 같아야 합니다.

배열 판은 newarr. 상수 스팬은 어셈블리의 데이터 필드를 ldtoken 해 RuntimeHelpers.CreateSpan 으로 — 힙을 쓰지 않습니다. 변수 스팬은 합성된 인라인 배열 <>y__InlineArray3`1 을 지역 변수로 두고 원소 셋을 채운 뒤 스팬으로 바꿉니다(마지막 InlineAr… 는 InlineArrayAsReadOnlySpan). 빈 호출은 기본값 스팬, IEnumerable 은 배열에 <>z__ReadOnlyArray`1 포장을 씌웁니다.

실행 검증

배열 판과 스팬 판이 함께 있으면

제안서는 "Better function member" 의 끝에 새 동점 규칙을 둡니다 — 둘 다 확장 꼴로만 맞으면 ReadOnlySpan 이 Span 을, 스팬이 배열(과 배열의 인터페이스)을, 스팬 아닌 둘 사이에서는 암시적 변환이 있는 쪽이 이깁니다.

원소를 낱낱이 넘기든, 빈 호출이든, 컬렉션 식이든 스팬 판이 이깁니다. 배열 변수를 그대로 넘긴 M(arr) 만은 정상 꼴의 정확한 일치라 int[] 판입니다. N 은 ReadOnlySpan, P 는 더 구체적인 List 입니다. 제안서가 이 규칙을 목록의 맨 끝에 둔 까닭은 "performing the tie-break earlier will introduce a behavior change for existing scenarios" 입니다.

실행 검증

다시 컴파일만 해도 스팬 판으로 — BCL 호출

제안서의 동기: "add a params span overload and have it take precedence over the array version, just by recompiling existing source code." 그리고 "If parameter collection is not an array, an expanded form is not applicable for language versions C# 12 and below." 같은 소스를 C# 12.0 과 13.0 으로 컴파일해 호출 한 번의 할당을 셉니다.

차이가 곧 인수 배열입니다 — 원소 셋이면 48, 다섯이면 64바이트. string.Join(",", a) 는 C# 13.0 에서 0 바이트이고 C# 12.0 에서는 원소 하나짜리 배열 32바이트입니다. 배열 변수 abc 를 넘긴 마지막 줄은 두 버전 모두 32 — 결과 문자열뿐이고 새 배열이 없습니다. 소스도, 런타임도 같고 언어 버전만 다릅니다. 언어 버전을 올리는 순간 호출하는 메서드가 바뀌는 것이니, 두 판이 다른 일을 하는 라이브러리라면 동작도 바뀝니다.

실행 검증

스팬 params 를 얻은 BCL 메서드 — .NET 10 에서

리플렉션으로 메서드 넷의 params 오버로드를 찍습니다. [] 는 ParamArrayAttribute, {} 는 ParamCollectionAttribute 가 붙은 마지막 매개변수입니다.

네 메서드 모두 배열 판마다 ReadOnlySpan 판이 짝으로 있습니다. 제안서는 다른 언어가 배열 아닌 params 를 "any time soon" 쓰지 못하리라고 적습니다 — 그런 언어에서 부를 수 있는 것은 배열 판입니다. 이 오버로드들이 정확히 .NET 9 에서 들어왔는지는 이 덱의 문서로 확인할 수 없습니다 — .NET 10 에 있다는 것만 보입니다.

실행 검증

메타데이터 — ParamArray 와 ParamCollection

제안서: 배열 아닌 params 에 기존 ParamArrayAttribute 를 붙이면 "the current VB compiler will not be able to consume them" — 그래서 새 특성 System.Runtime.CompilerServices.ParamCollectionAttribute 를 씁니다.

배열만 ParamArrayAttribute 입니다. ReadOnlySpan 매개변수에는 ScopedRefAttribute 도 붙어 있습니다 — scoped 라고 쓰지 않았는데도 그렇습니다. 직접 scoped 라고 쓴 N 과 같은 특성입니다. 다음 장이 그 뜻을 봅니다.

실행 검증

params 스팬은 저절로 scoped

제안서: "Params parameters are implicitly scoped when their type is a ref struct. UnscopedRefAttribute can be used to override that." scoped 자체는 12부에서 보았습니다(12부).

확장 꼴의 스팬은 호출한 쪽의 스택(인라인 배열)에 있을 수 있어서 돌려줄 수 없습니다(CS8352). 제안서는 BCL 을 살펴보니 거의 모든 경우가 scoped 였다며 이것을 기본으로 정했습니다. [UnscopedRef] 를 달면 돌려줄 수 있지만, 그 대신 호출한 쪽이 결과의 수명을 떠안습니다.

실행 검증

재정의에서 params 와 scoped

제안서의 결정: 재정의가 params 매개변수를 다시 적을 때 "explicitly stating scoped or params" 를 요구합니다 — params 를 뺀 매개변수가 scoped 를 적어야 했을 자리에서만. 예제의 꼴은 제안서의 M1 입니다.

params 를 다시 적든, scoped 만 적든 됩니다. 둘 다 빼면 CS8987 — 기반의 매개변수는 저절로 scoped 였기 때문입니다. 오류 문장은 params 를 말하지 않고 scoped 의 불일치만 말합니다.

실행 검증

람다와 대리자의 params 컬렉션

C# 12 가 람다에 params 배열을 허락했고(13부), C# 13 의 params 컬렉션은 매개변수가 놓이는 모든 자리 — 람다, 대리자 선언, 메서드 그룹의 자연 형식 — 로 그대로 갑니다.

람다 sum 과 메서드 그룹 count 는 같은 합성 대리자 <>f__AnonymousDelegate0 를 씁니다 — C# 12 의 params 배열 람다가 Func 가 아닌 합성 대리자를 받았던 것과 같은 길입니다(13부). 그 Invoke 의 매개변수에도 ScopedRef 와 ParamCollection 특성이 붙습니다. C# 12.0 의 거절은 선언 두 곳뿐이고 13행의 람다는 보고되지 않습니다 — 선언의 오류가 몸체의 거절을 가립니다.

실행 검증

dynamic 은 확장 꼴을 모른다

제안서: "Expanded forms of candidates utilizing non-array params collections won't be considered as valid candidates by the current C# runtime binder." 후보가 하나뿐이고 그 후보가 그런 확장 꼴로만 맞으면 컴파일할 때 오류입니다.

배열 판은 실행 때 바인더가 확장 꼴로 묶어 줍니다. List 판은 수신자의 형식을 아는 p.L(d, d) 면 컴파일러가 CS9218 로 미리 막고, 수신자까지 dynamic 이면 실행 때 RuntimeBinderException 입니다. dynamic 의 바인더 자체는 5부를 보십시오.

실행 검증

식 트리에도 담기지 않는다

제안서: 컬렉션 식처럼 "expanded forms of non-array params collections will not be supported in expression trees."

배열 판은 트리 안에서 new [] {1, 2} 노드가 됩니다. List 판의 확장 꼴은 CS9226 입니다. 식 트리가 C# 3 이후의 문법을 얼마나 못 담는지는 4부에 모아 두었습니다.

실행 검증

컬렉션은 언제 만들어지나 — 평가 순서

제안서: 이름 붙은 인수가 있으면 컬렉션은 "after the lexically previous argument is evaluated, but before the lexically following argument" 에 만들어지고 채워집니다. 배열은 "created right before the target method is invoked, after all arguments are evaluated" 입니다. 첫 호출은 제안서의 것입니다.

첫 줄이 제안서의 순서 그대로입니다 — B, 컬렉션 생성과 C, 그리고 A. 둘째 줄은 원소마다 평가하고 바로 Add 합니다. 배열 판(셋째 줄)은 넷을 모두 평가한 뒤 배열을 만듭니다. 제안서는 이 차이를 "an implementation artifact" 로 두고 배열의 동작은 바꾸지 않는다고 적습니다.

실행 검증

params 로 쓸 수 없는 것

규칙(앞에서)을 벗어난 넷을 기호 하나에 오류 하나로 봅니다.

IDictionary 는 컬렉션이지만 허락된 인터페이스 다섯에 없어서 int 와 같은 CS0225 입니다. Add 없는 형식은 CS0225 가 아니라 CS0117 — "Add 의 정의가 없다" 는 오류가 선언에 납니다. 기본값 오류 CS1751 의 문장은 이제 "parameter collection" 이라고 부릅니다.

실행 검증

async 메서드의 params 스팬

C# 13 은 반복기와 async 메서드 안의 ref 지역 변수를 허락합니다(4장). 그러나 매개변수는 그 대상이 아닙니다.

스팬 매개변수는 params 이든 아니든 async 메서드에서 CS4012 입니다. 표준이 async 함수의 매개변수로 금하는 것에 "any parameter of a ref struct type" 이 들어 있습니다. 매개변수는 상태 기계의 필드로 옮겨지기 때문입니다(6부). async 메서드에 가변 인수가 필요하면 IReadOnlyList<T> 처럼 힙에 사는 형식으로 받습니다. async 메서드의 ref 매개변수 금지는 6부에서 보았습니다.

실행 검증

required 멤버가 있는 컬렉션

제안서의 결정: params 자격을 주는 생성자가 required 멤버를 채우지 않으면 "at the declaration site" 에서 확인합니다.

확장 꼴은 개체 초기화자를 붙일 자리가 없어서 Tag 를 채울 수 없습니다. 그래서 오류 CS9225 는 호출이 아니라 매개변수 선언에 납니다. required 멤버는 12부에서 보았습니다.

실행 검증

컬렉션 식의 더 나은 변환 — 원소가 정확한 쪽 C# 13.0

왜 — 제안서: 더 나은 변환 규칙을 "more consistent with params" 하게 고치고, 이를테면 [""] 에 대한 ReadOnlySpan<string> 과 ReadOnlySpan<object> 의 모호함을 풉니다. Roslyn 은 이것을 C# 13 의 깨지는 변경으로 적습니다 — "we prefer an exact element type match". 예제의 M1 은 그 문서의 것입니다.

M1([1]) 은 C# 12 에서 스팬의 종류(ReadOnlySpan 이 Span 을 이긴다)로 ReadOnlySpan<byte>, C# 13 에서는 원소 1 이 int 에 정확히 맞아 Span<int> 입니다. 컴파일도 실행도 되면서 다른 메서드를 부르는 변경입니다 — 게이트가 없어 언어 버전만 보고 고르는 동작입니다. [""] 는 C# 12 에서 CS0121, C# 13 에서 string 쪽입니다. 13부의 앞당긴 확인(13부)과 같은 규칙입니다.

실행 검증

빈 [] 는 더 이상 스팬이라서 이기지 않는다

Roslyn 문서: 원소 형식이 분명하지 않은 빈 컬렉션 식에서 "we no longer use whether an API takes a ReadOnlySpan<T> or a Span<T> to decide". 예제는 문서의 C.M 입니다.

문서의 주석 그대로 — "C.M(ReadOnlySpan<int>) in C# 12, error in C# 13." 이쪽은 컴파일되던 코드가 오류가 되는 변경입니다. 원소가 있는 [1] · [""] 는 두 버전 모두 원소의 형식으로 갈립니다. 제안서의 노트는 이것이 의도라고 적습니다 — 원소 형식이 다르고 컬렉션 형식끼리 변환이 없으면 "ambiguous for empty collection expressions".

실행 검증

확장 꼴과 컬렉션 식이 다른 답을 낼 때

제안서: 앞쪽의 동점 규칙(제네릭이 아닌 쪽이 낫다 등)이 먼저 걸리면 "the overload resolution result can be different by comparison to the case when an explicit collection expression is used". 빈 인수 목록은 원소 형식이 다른 두 params 사이에서 "Ambiguous in C# 13" 입니다. 두 예제 모두 제안서의 것입니다.

M2([1]) 은 컬렉션 식의 더 나은 변환으로 Span<T>, M2(1) 은 매개변수 형식이 같아진 뒤 제네릭이 아닌 쪽이 낫다는 규칙이 먼저 걸려 int[] 입니다. 괄호 두 개가 부를 메서드를 바꿉니다. E(1) 은 원소가 정하지만 E() 는 정할 원소가 없어 CS0121 입니다.

실행 검증

버린 대안 — ReadOnlySpan 만, 또는 아무것도

제안서의 "Alternatives" 는 두 길을 적습니다.

  • params 를 ReadOnlySpan<T> 에만 넓히는 앞선 제안이 있었습니다(proposals/rejected/params-span.md, 이름 그대로 버려진 제안).
  • 컬렉션 식이 생겼으니 아예 넓히지 않을 수도 있었습니다 — "a developer simply needs to add two characters, [ before the expanded list of arguments, and ] after it." 제안서도 이 길이 "an overkill" 일 수 있다고 인정합니다.
  • 채택된 것은 컬렉션 식의 대상 형식 전부입니다. 그 대가가 이 장의 뒤쪽 — dynamic·식 트리의 제약, 평가 순서의 차이, 새 동점 규칙입니다.

1장에서 센 세 어셈블리의 params 컬렉션은 ReadOnlySpan<T> 뿐이었습니다(1장) — .NET 10 에서 센 결과입니다.

문서 근거

2장 퀴즈 — params 컬렉션

Q. 라이브러리가 Log(params string[] xs) 옆에 Log(params ReadOnlySpan<string> xs) 를 더했습니다. 쓰는 쪽의 소스 Log("a", "b") 와 Log(names)(names 는 string[])를 C# 12.0 과 C# 13.0 으로 각각 다시 컴파일하면 무엇이 불릴까요?

A. Log("a", "b") 는 C# 12.0 에서 배열 판(배열 아닌 params 의 확장 꼴은 C# 12 이하에서 쓸 수 없다), C# 13.0 에서 스팬 판입니다 (앞에서). Log(names) 는 정상 꼴이라 넘긴 배열을 그대로 씁니다 — 두 버전의 할당이 같고(abc 줄), C# 13.0 에서도 배열 판이 이깁니다. 정확한 일치이기 때문입니다(앞에서의 M(arr)).

3장

Lock 객체 — lock 문이 형식을 알아본다

동기 · EnterScope 로의 번역 · Lock 의 API · object 로 바꾸면 · 제네릭 · async · 스레드 ·

왜 생겼나 — Monitor 를 대신할 형식

제안서: ".NET 9 is introducing a new System.Threading.Lock type as a better alternative to existing monitor-based locking." 문제는 lock 키워드입니다. 손대지 않으면 컴파일러는 이 형식도 "any other object" 로 보고 Monitor 로 잠급니다 — 새 형식의 뜻대로 잠기지 않습니다.

  • C# 1 의 lock (x) 는 Monitor.Enter·Monitor.Exit 와 try·finally 의 줄임이었습니다(2부).
  • C# 13 은 x 의 형식이 System.Threading.Lock 일 때만 번역을 바꿉니다. 일반 패턴(어떤 형식이든 lock 에 참여)은 LDM 이 "rejected the general pattern, accepted only special-casing the Lock type" 했습니다.
  • whats-new: "This feature allows you to get the benefits of the new library type by changing the type of object you lock. No other code needs to change."
문서 근거

Lock 객체 (Lock object) C# 13.0

왜 — whats-new: "The C# lock statement recognizes if the target of the lock is a Lock object. If so, it uses the updated API, rather than the traditional API using System.Threading.Monitor."

소스는 C# 1 의 lock 과 같은 꼴이고, 필드의 형식만 object 에서 Lock 으로 바뀌었습니다. C# 12.0 은 lock (gate) 를 CS9202 로 거절합니다 — 조용히 Monitor 로 잠그지 않습니다. 같은 소스가 언어 버전에 따라 다른 잠금이 되는 일을 컴파일러가 막는 셈입니다.

실행 검증

무엇으로 번역되나 — EnterScope 와 Dispose

제안서: x 가 System.Threading.Lock 이면 lock (x) { ... } 는 "precisely equivalent to" using (x.EnterScope()) { ... } 입니다. 2장의 IL 도구(2장)로 확인합니다.

Lock 을 잠그는 메서드에는 Monitor 호출이 하나도 없고 Lock.EnterScope 와 Scope.Dispose 만 있습니다. object 는 C# 1 그대로 Monitor.Enter·Monitor.Exit 입니다. 제안서는 Enter·Exit 를 쓰지 않는 까닭을 Exit 가 "contains a thread lookup which is avoided when using the Scope" 라고 적습니다.

실행 검증

Lock 의 API — lock 문 없이도

제안서가 보이는 형식의 꼴은 Enter, Exit, EnterScope 와 ref struct Scope 입니다. lock 문이 하는 일을 손으로 합니다.

같은 스레드가 두 번 들어갈 수 있고, 나올 때도 두 번 나와야 풀립니다 — Monitor 와 같은 재진입입니다. 잡지 않고 Exit 하면 SynchronizationLockException 입니다. 이 파일은 C# 12.0 에서도 컴파일되고 같은 결과를 냅니다. Lock 은 그냥 런타임의 클래스이고, 게이트가 걸린 것은 lock 문의 번역뿐입니다.

실행 검증

Lock 을 object 로 바꾸면 — 경고 CS9216 C# 13.0

왜 — 제안서: Lock 을 object·기반 클래스·인터페이스로 바꾸는 암시적 참조 변환에 경고를 더합니다. 바뀐 값을 잠그면 Monitor 로 잠기기 때문입니다. 단, ==·!= 의 피연산자로 바뀔 때는 경고하지 않습니다.

lock (o) 안에서는 Monitor 가 잡혀 있고 Lock 은 잡혀 있지 않습니다 — 같은 객체를 다른 방식으로 잠근 것입니다. 경고는 11행의 대입뿐 아니라 22행 Monitor.IsEntered(gate) 에도 납니다. 인수로 넘기는 것도 object 로의 변환이기 때문입니다. gate != null 은 조용합니다.

실행 검증

형식 매개변수로 넘기면 — 경고 없이 Monitor

제안서의 "Alternatives": Lock 을 형식 인수로 넘길 때도 경고할 수 있었습니다 — 형식 매개변수를 잠그면 늘 Monitor 이고 where T : Lock 도 소용없습니다. 하지만 그러면 List<Lock> 에 담기만 해도 경고가 나서 넣지 않았습니다.

함정 — 경고 하나 없이 컴파일되고, Guard 안에서 잡힌 것은 Monitor 입니다. 같은 Lock 을 다른 곳에서 lock (gate) 로 잠그면 두 곳은 서로를 막지 못합니다. Lock 은 그 형식 그대로 lock 문에 써야 합니다.
실행 검증

async 메서드 안의 lock (Lock)

제안서의 "Alternatives" 는 lock 이 ref struct 를 자원으로 하는 using 이 되므로 async 메서드에서는 "this results in a compile-time error" 라고 적습니다. 같은 C# 13 이 async 안의 ref 지역 변수를 허락했습니다 — await 를 넘지 않는 한에서입니다(4장).

C# 13.0 은 await 가 없는 lock (gate) 를 async 메서드 안에서 컴파일합니다 — 제안서의 문장보다 컴파일러가 앞서 있습니다. lock 안의 await 는 C# 5 부터의 CS1996(6부), 손으로 쓴 using (gate.EnterScope()) 를 await 가 가로지르면 ref struct 의 CS4007 입니다. -define:USING 을 C# 12.0 으로 내리면 거절이 둘입니다 — lock 문의 Lock object 와, async 메서드 안에 ref struct 지역 (Scope)을 둔 ref and unsafe in async and iterator methods.

실행 검증

네 스레드, 하나의 Lock

여러 스레드의 경합은 실행마다 순서가 달라 캡처의 증거가 되지 못합니다(2부). 그러나 잠근 덕에 늘 같은 최종 값은 찍을 수 있습니다.

합은 400000 이고, 모든 스레드가 끝난 뒤 주 스레드는 잠금을 쥐고 있지 않습니다. 이 덱은 성능을 재지 않습니다 — Lock 이 Monitor 보다 얼마나 빠른지는 이 덱의 문서에 수치가 없어서 싣지 않습니다. 제안서가 말하는 것은 "better alternative" 와 Scope 가 피하는 스레드 조회까지입니다.

실행 검증

3장 퀴즈 — Lock 객체

Q. private readonly object sync = new Lock(); 으로 필드를 바꾸고 lock (sync) { … } 는 그대로 두었습니다. C# 13 에서 이 잠금은 Lock.EnterScope 로 번역될까요?

A. 아닙니다. lock 문은 식의 컴파일 시점 형식을 봅니다. 필드의 형식이 object 이므로 Monitor.Enter·Exit 로 번역되고, 대입에서 Lock 이 object 로 바뀌므로 경고 CS9216 이 납니다(앞에서). 필드의 형식을 Lock 으로 써야 합니다.
