field 키워드 — 자동 속성과 손으로 쓴 속성 사이

get; 과 몸체 있는 접근자 섞기 · 뒷받침 필드의 정체 · 초기화자와 생성자 · init · nullable 분석 · [field: …] · 키워드가 되는 자리 · 람다·정적·구조체·override · 필드 경고 · 아직 손으로 쓰는 필드

왜 — 한 줄의 논리 때문에 필드를 통째로 선언해야 했다

제안서의 동기: 접근자에 논리를 조금 넣으려 해도 "this confronts users with the overhead of declaring a backing field", 그리고 그 필드는 "scoped to the entire class which can result in accidental bypassing of the accessors from within the class." 블로그는 이 기능을 "a bridge between auto‑implemented and fully hand‑written properties" 라고 부릅니다.

앞에서 본 것이 장에서 더 가는 곳
C# 3 자동 속성, C# 14 의 field 미리 보기(4부)접근자의 꼴과 뒷받침 필드의 정체
C# 6 의 get 만 있는 자동 속성과 초기화자(4부)초기화자는 setter 를 부르지 않는다
C# 9 의 init 접근자(10부)init => field = … 과 with
C# 13 미리 보기 — CS9260·CS0103(14부)정식 기능의 규칙 — nullable · 특성 · 구조체
field 라는 멤버·지역 변수(14부)키워드가 되는 자리와 되지 않는 자리
partial 속성과 field(14부)— (그대로)

14부 8장이 "들어온 길" 을 보았다면, 이 장은 C# 14 에서 정식이 된 규칙을 하나씩 돌려 봅니다.

문서 근거

field 키워드 (the field keyword) C# 14.0

왜 — whats-new: "The token field is replaced with a compiler synthesized backing field." 전에는 값 하나를 거르려 해도 "you had to declare a backing field and implement both accessors" 였습니다. 예제는 whats-new 의 Email 을 줄인 것입니다.

null 을 넣으면 빈 문자열이 되고, 아무것도 넣지 않은 처음 값은 null 입니다 — 뒷받침 필드의 기본값이지 set 을 거친 값이 아닙니다. C# 13.0 의 거절은 get; 과 몸체 있는 set 을 섞은 선언 자리 한 줄입니다(14부와 같은 CS9260).

실행 검증

접근자의 다섯 꼴 — 게으른 get, 둘 다 몸체, set 만, 읽기만, private set

제안서: 두 접근자 모두 몸체를 가져도 되고, "Expression-bodied properties and properties with only a get accessor may also use field", 그리고 "Set-only properties may also use field".

Title 은 Compute 를 한 번만 부릅니다(computed=1). Version 은 쓸 때 1 을 더해 2 입니다. Tag 는 set 만 있어 읽을 길이 없는데도 컴파일됩니다. Tag2 는 아무도 쓰지 않아 늘 null — 경고도 없습니다(뒤에서). Count 의 private set 은 field 와 견주어 큰 값만 남겨 5 다음에 3 을 넣어도 5 입니다.

실행 검증

뒷받침 필드의 정체 — 자동 속성과 같은 이름, 같은 특성

제안서가 바꾼 표준 문장: 자동 속성에는 "a hidden unnamed backing field" 가 있고, "only a semicolon-only get accessor" 인 자동 속성의 필드는 readonly 입니다. 그리고 Debug.Assert 처럼 빠지는 호출 안에서만 field 를 써도 "The backing field is generated" 입니다.

이름 없는 필드라지만 메타데이터에는 이름이 있습니다 — 자동 속성 Auto 와 똑같은 <이름>k__BackingField 에 같은 두 특성입니다. field 를 쓰지 않는 Plain 에는 필드가 없고, { get; } 인 Fixed 만 initonly 입니다. Checked 는 DEBUG 기호 없이 컴파일해 Debug.Assert 호출이 빠졌는데도 필드가 남았습니다.

실행 검증

초기화자는 setter 를 부르지 않는다 C# 14.0

제안서: "The backing field is directly initialized rather than the setter being called." 초기화자는 기반 생성자보다 먼저 돌기 때문에 인스턴스 메서드인 setter 를 부를 수 없습니다. 그래서 setter 를 거치려면 생성자에서 대입하라고 합니다. 예제는 제안서의 뷰 모델에 생성자에서 대입하는 Name 을 더한 것입니다.

= true 는 Set 을 거치지 않아 HasPendingChanges 가 False 로 남습니다. 생성자에서 Name 에 "x" 를 대입하면 setter 가 돌아 True 가 됩니다. null 은 기본값과 같아 Set 이 바꾼 것이 없다고 봅니다. C# 6 의 자동 속성 초기화자도 뒷받침 필드에 바로 들어가는 같은 길이었습니다 — 제안서가 이전 버전의 가상 자동 속성으로 그 차이를 보입니다.

실행 검증

생성자의 대입 — setter 가 있으면 setter, 없으면 필드

제안서: "assignment in the constructor calls the (potentially virtual) setter if it exists, and if there is no setter it falls back to directly assigning to the backing field." 예제의 P1~P4 는 제안서의 것에 로그를 단 것입니다.

로그는 P3·P4 두 줄뿐이고 P4 는 setter 가 10 을 곱해 40 입니다. get 만 있는 P1 은 생성자 안에서는 대입되지만 밖에서는 CS0200 — 읽기 전용 자동 속성(C# 6)과 같은 규칙입니다.

실행 검증

init 접근자의 field — with 식도 같은 접근자를 지난다

제안서: "For properties with an init accessor, everything that applies below to set would apply instead to the init accessor." 블로그의 Before/After 도 init => field = value ?? throw … 입니다.

함정 — m with { Text = "bye" } 의 Upper 가 HI 입니다. with 는 레코드를 복사하는데, Upper 의 뒷받침 필드도 복사되어 옛 캐시가 따라옵니다. field ??= 캐시는 레코드의 다른 속성에 기대면 안 됩니다. null 은 init 의 검사에 걸리고, 밖에서의 대입은 C# 9 의 CS8852 그대로입니다(10부).
실행 검증

field 의 nullable 분석 — get 이 null 에 견디는가 C# 14.0

제안서의 핵심 장면은 게으른 초기화입니다 — public C() { } 에서 "It would be undesirable to warn about 'Prop' being uninitialized here". 그래서 get 을 두 번 분석합니다. 필드를 nullable 로 보았을 때만 생기는 경고가 있으면 "the property is not null-resilient", 없으면 필드는 nullable 로 다룹니다.

Lazy 의 get 은 필드가 null 이어도 null 을 돌려주지 않으므로(null-resilient) 빈 생성자에 경고가 없습니다. get => field 인 Strict·Bad 는 견디지 못해 생성자 끝에서 CS9264 를 받습니다 — 200칸이 넘는 문장은 표에 있고, "safely handling the case where 'field' is null in the 'get' accessor" 를 권합니다. Bad 의 빈 set 은 따로 CS9266 입니다.

실행 검증

setter 는 작은 생성자 — 제안서의 경고는 나오지 않았다

제안서의 setter 분석: 필드가 null 에 견디지 못하는 속성의 setter 는 끝에서 필드를 채워야 하고, 예제의 set { } 에 "We should warn here that field may be null when exiting." — "the setter is treated as a 'mini-constructor' for the backing field." 예제는 제안서의 것에 조건부 대입(PARTIAL)과 예외 잡기를 더한 것입니다.

함정 — Nullable 을 켰는데도 nullable 경고는 없고 실행은 NullReferenceException 입니다. 빈 set 에 붙은 CS9266 은 "set 이 field 를 쓰지 않는다" 는 별개의 경고이고, field 를 조건부로만 채우는 PARTIAL 은 경고가 하나도 없습니다. 제안서가 그린 setter 의 null 검사는 이 컴파일러(Roslyn 5.0)에 없습니다(2026-10 기준). C# 13.0 에서는 이 파일의 field 가 CS0103 입니다(표).
실행 검증

[field: …] — 뒷받침 필드에 특성 달기 C# 14.0

제안서: "any property that uses a backing field in one of its accessors will be able to use field-targeted attributes". 필드가 없는 속성에 달면 "❌ Error, will not compile" 이라고 적습니다.

특성은 리플렉션에서 <Name>k__BackingField 에 붙어 보입니다. 필드가 없는 Plain 에 다는 -define:BAD 는 제안서의 말과 달리 오류가 아니라 경고 CS0657 이고, 특성을 버린 채 실행됩니다(문장 전체는 표). C# 13.0 은 Level 선언에서 CS9260 을 내고, 키워드가 아닌 Name => field ??= … 쪽에도 같은 CS0657 을 냅니다 — 그 버전에서는 뒷받침 필드가 없는 속성이기 때문입니다.

실행 검증

field 가 키워드가 되는 자리 — 접근자 몸체뿐

제안서의 문법: field 는 "primary expression" 으로 쓰일 때, "In method bodies of get, set, and init accessors in properties but not indexers" 와 그 안의 람다·지역 함수에서만 키워드입니다. 속성 초기화자는 "as in previous versions of C#", 이벤트 접근자에서는 "field is not a keyword".

다섯 자리 모두 상수 -1 을 읽고, 두 버전의 출력이 같으며 CS9258 도 없습니다. 인덱서(9 = -1 + 10)와 이벤트 접근자에는 뒷받침 필드가 생기지 않으니 field 는 그냥 이름입니다. 키워드가 되는 곳은 속성 접근자의 몸체 하나입니다 (다음 장).

실행 검증

깨지는 변경 — field 라는 멤버를 쓰던 접근자 C# 14.0

Roslyn: "The warning CS9258 is reported when the identifier would have bound to a different symbol with language version 13 or earlier." 피하려면 "use 'this.field' or '@field' instead" 또는 이름을 바꿉니다. 14부는 같은 변화를 세 속성으로 보였습니다(14부). 여기서는 고친 판과 컴파일러의 둘째 신호를 봅니다. 이 예제의 프로젝트 버전은 옛 코드의 것인 C# 13.0 이고, 같은 소스를 C# 14.0 으로 올려 컴파일합니다.

C# 14.0 에서 Value 는 새 뒷받침 필드에 5 를 쓰고 읽으므로 그대로 5 이지만, 메서드 Raw() 의 field 는 여전히 멤버라 0 입니다. 그래서 컴파일러는 CS9258 말고도 "Legacy.field 는 대입되지 않는다" 는 CS0649 를 냅니다 — 경고를 꺼도 남는 신호입니다. this.field·@field 로 고친 판은 C# 14.0 에서도 C# 13.0 과 같은 5 5 입니다.

실행 검증

람다와 지역 함수 안의 field

제안서: "field should be able to be captured in local functions and lambdas", 예제는 정적 속성 안의 static () => field 입니다. 그리고 nameof(field) 는 nameof(nint) 처럼 "will fail to compile".

Ticks 는 정적 뒷받침 필드라 static 람다가 잡을 수 있고, 인스턴스 속성에서는 this 를 거쳐야 해 CS8821 입니다. 람다 매개변수 이름 field 는 CS9273(문서는 CS9272 — 14부), 그리고 본문의 field 는 매개변수가 아니라 bool 속성 Any 의 뒷받침 필드에 묶여 bool > int 의 CS0019 입니다. nameof(field) 는 CS8081(표).

실행 검증

정적 속성과 인터페이스 — 정적은 되고 인스턴스는 안 된다

제안서: 인터페이스의 속성에서도 자동 접근자는 뒷받침 필드를 뜻하고, 인스턴스 속성이면 "an error is reported that instance fields are not supported" — 정적이면 됩니다.

정적 뒷받침 필드도 같은 <이름>k__BackingField 이고, 인터페이스 ISettings 안에 정적 필드로 생깁니다. 인스턴스 속성은 문장 그대로 "Interfaces cannot contain instance fields" — 오류가 속성이 아니라 필드에서 납니다. 인터페이스의 정적 멤버는 C# 8 의 기본 구현 무리입니다(9부).

실행 검증

구조체의 field — readonly 면 필드도 initonly

제안서: "The synthesized backing field is read-only when the containing type is a struct and the property or containing type is declared readonly." 그러면 필드는 메타데이터에서 initonly 이고 초기화자·생성자 밖의 수정은 오류입니다. 예제의 P0~P4 는 제안서의 것입니다.

함정 — P1 의 field ??= Load() 캐시는 지역 변수에서는 한 번만 부르지만(Loads=1), static readonly 필드에 담긴 구조체에서는 읽을 때마다 부릅니다(Loads=3). 읽기 전용 위치의 구조체는 방어 복사본 위에서 get 이 돌아 캐시가 버려지기 때문입니다. readonly 인 P3 는 set 이 필드를 읽기만 하므로 허용되고, 필드에 쓰는 P2·P4 는 CS0191(표)입니다.
실행 검증

override 속성의 field — 기반과 따로인 필드

제안서: 재정의한 속성의 field 는 "the backing field for the overriding property, separate from the backing field of the base property", 그리고 자동 속성처럼 "must override all accessors".

Derived 는 50 을 들고 있고, base.N 은 기반의 초기화자 값 1 그대로입니다 — 두 클래스에 같은 이름의 필드 <N>k__BackingField 가 하나씩 있습니다. get 만 재정의하면 CS8080 "must override all accessors" 입니다.

실행 검증

필드 경고 — 제안서는 CS0414·CS0649 라 했지만

제안서: field 를 쓰면 "the compiler's existing analysis of unassigned or unread fields will include that field", 그리고 두 문장을 적습니다 — CS0414 "The backing field for property 'Xyz' is assigned but its value is never used", CS0649 "… is never assigned to". { set; } 만은 "Disallowed today, continue disallowing" 입니다.

보통 필드 x·y 는 CS0649·CS0414 를 받습니다. 그런데 쓰기만 하는 A 는 CS0414 대신 "get 이 field 를 쓰지 않는다" 는 CS9266 이고, 한 번도 쓰지 않는 B 는 아무 경고도 없습니다. 뒷받침 필드의 CS0414·CS0649 는 이 컴파일러에서 나오지 않았습니다(2026-10 기준). { set; } 는 자동 속성의 규칙 그대로 CS8051 입니다.

실행 검증

아직 손으로 쓰는 필드 — 함께 쓰는 상태, 메서드, ref

field 는 그 속성의 접근자 안에서만 보입니다 — 제안서가 동기로 든 장점("only have it be available to the bodies of the accessors")의 뒷면입니다. ref 를 돌려주는 속성에는 "the field keyword will not be available".

함정 — t.C = 0 뒤에도 Label 은 T=100 입니다. field ??= 캐시를 비울 길이 접근자 밖에 없고, 메서드에서 field 를 쓰면 CS0103 — 그 자리에서는 그냥 없는 이름입니다. 두 속성이 나누는 상태, 캐시 무효화, ref 반환에는 여전히 이름 있는 필드가 필요합니다.
실행 검증

3장의 진단 — 거절과 경고를 한 표에

이 장의 거절 캡처에서 첫 오류(없으면 첫 경고)의 번호와 문장 앞부분을 실험 묶음이 뽑았습니다.

문장에 field 를 담은 번호는 CS9273(지역·매개변수 이름)과 경고 CS9258·CS9264·CS9266 입니다. 나머지는 모두 자동 속성·읽기 전용 필드·인터페이스의 일반 번호를 그대로 씁니다 — 컴파일러가 field 를 쓰는 속성을 "자동 속성의 한 종류" 로 다룬다는 흔적입니다(CS8051·CS8080·CS8145 의 "Auto-implemented properties").

실행 검증

3장 퀴즈 — field 키워드

Q1. public bool IsActive { get; set => Set(ref field, value); } = true; 에서 = true 는 Set 을 부를까요?

Q2. 클래스에 int field; 가 있고 속성 접근자가 return field; 입니다. C# 14 로 올렸을 때 이 접근자가 읽는 것은? 같은 클래스의 메서드 int Raw() => field; 는?

A1. 부르지 않습니다. 초기화자는 뒷받침 필드에 바로 들어갑니다. setter 를 거치려면 생성자에서 대입합니다(앞에서).
A2. 접근자는 새 뒷받침 필드(경고 CS9258), 메서드는 여전히 멤버 field 입니다. 둘이 갈라져 멤버에는 CS0649 도 붙습니다 (앞에서).

문서 근거

암묵적 Span 변환 (implicit span conversions) C# 14.0

왜 — 제안서의 첫 예는 arr.StartsWith(1) 입니다 — 배열이 ReadOnlySpan<T> 를 받는 확장 메서드의 받는 쪽(receiver)이 되는 것. 전에는 "user-defined conversions … are not considered for extension receivers" 였습니다.

인수 자리의 Sum(arr)·Sum(span) 는 C# 13.0 에서도 컴파일됩니다 — 형식이 정의한 사용자 정의 변환 연산자 덕입니다. C# 13.0 이 거절하는 것은 받는 쪽 두 줄이고, 번호는 CS1929 "requires a receiver of type 'System.ReadOnlySpan<int>'" 입니다(줄이 200칸을 넘어 표로). 제안서 주석의 "CS8773 in C# 13" 도, 게이트의 CS9260 도 아닙니다(뒤에서).

실행 검증

다섯 가지 변환 — 넷은 원래 있던 연산자, 하나가 새것

제안서의 목록: 배열 → Span<T>, 배열 → ReadOnlySpan<U>, Span<T> → ReadOnlySpan<U>, ReadOnlySpan<T> → ReadOnlySpan<U>(T 가 U 로 공변 변환될 때), string → ReadOnlySpan<char>. 그리고 이것을 "the list of standard implicit conversions" 에 넣습니다.

기본 판은 C# 13.0 에서도 같은 출력입니다. Span·ReadOnlySpan·string 에 op_Implicit 가 있고, string[] → ReadOnlySpan<object> 도 배열 공변(string[] → object[])을 먼저 거쳐 그 연산자에 닿습니다. C# 13.0 이 거절하는 것은 스팬에서 스팬으로의 공변 둘뿐입니다. 바뀐 것은 "변환이 있느냐" 보다 "어떤 종류의 변환이냐" — 사용자 정의에서 표준 암묵적 변환으로입니다.

실행 검증

ReadOnlySpan 의 공변 — 읽기만 하니까

제안서: 이 규칙의 목표는 "to replicate some amount of covariance for System.ReadOnlySpan<T>" — 런타임을 고치지 않고 .NET 9 의 API 하나로 "as if the T was declared as out T in some scenarios" 처럼 다룹니다.

C# 13.0 은 Span<string>·ReadOnlySpan<string> 에서 ReadOnlySpan<object> 로 가는 세 곳을 CS1503·CS0029 로 거절하고, string[] 하나만 배열 공변으로 통과시킵니다. 변환된 스팬의 원소는 여전히 String 입니다 — 복사가 아니라 같은 메모리를 다른 형식으로 보는 것입니다. 이 변환이 부르는 메서드는 코드 생성에서 봅니다.

실행 검증

쓸 수 있는 Span 에는 공변이 없다 — 실행 오류가 컴파일 오류로

제안서: 명시적 스팬 변환에는 "From an array_type with element type Ti to System.Span<Ui> … provided an explicit reference conversion exists" 가 있고, "User-defined conversions are not considered when converting between types for which an implicit or an explicit span conversion exists."

함정 — C# 13 은 string[] → object[] → op_Implicit 로 받아 놓고 실행에서 ArrayTypeMismatchException 을 냅니다(Span<T> 생성자의 검사). C# 14 는 명시적 스팬 변환이 있으니 사용자 정의 연산자를 보지 않고 CS0266 "An explicit conversion exists" 로 거절합니다. 캐스트를 쓰면 다시 실행 예외입니다. 이 변화는 Roslyn 의 깨지는 변경 문서에 없습니다 (목록).
실행 검증

스팬을 지나는 형식 추론 C# 14.0

제안서는 정확 추론과 하한 추론에 "V is a ReadOnlySpan<V₁> and U is an array type U₁[] or a Span<U₁> or ReadOnlySpan<U₁>" 같은 줄을 더합니다. 배열에서 Span<Vᵢ> 로는 "an exact inference", ReadOnlySpan<Vᵢ> 로는 "a lower-bound inference" 입니다.

C# 13.0 의 거절은 CS0411 넷입니다. Fill(nums, 0) 은 둘째 인수에서 T = int 를 얻고 배열은 연산자로 넘어가 C# 13.0 에서도 통과합니다. MIXED 의 Span<T> 는 정확 추론이라 T 가 string 이어야 하는데 둘째 인수가 object 라 C# 14 에서도 CS0411 입니다. 14부의 params 함정(Concat(arr) 의 T = int[])이 C# 14 에서 풀린 것도 이 규칙입니다 (14부).

실행 검증

사용자 정의 변환과 이어진다 — string 이 바로 Word 로

동기의 둘째 항목 "cannot compose with other user-defined conversions" 입니다. 사용자 정의 변환은 앞뒤에 표준 변환을 하나씩 붙일 수 있는데, 스팬 변환이 표준 암묵적 변환 목록에 들어가 그 앞자리에 설 수 있게 됐습니다.

Word b = " yo "; 는 string → ReadOnlySpan<char>(스팬 변환) → Word(사용자 정의) 입니다. C# 13 에서는 첫 단계도 사용자 정의 연산자라, 사용자 정의 변환 둘을 잇지 않는 규칙에 걸려 CS0029 입니다. .AsSpan() 을 직접 부른 줄은 두 버전 모두 됩니다.

실행 검증

오버로드 해석 — 스팬 변환이, 그중에서도 ReadOnlySpan 이 이긴다 C# 14.0

제안서는 "better conversion from expression" 에 "C₁ is an implicit span conversion and C₂ is not" 을, "better conversion target" 에 "T₁ is System.ReadOnlySpan<E₁>, T₂ is System.Span<E₂>" 를 더합니다. 새로 적용 가능해진 판이 "any potential ambiguity with another overload is avoided" 하도록 한 규칙입니다.

함정 — N(a) 는 오류도 경고도 없이 C# 13 의 Span 판에서 C# 14 의 ReadOnlySpan 판으로 옮겨 갑니다. 두 판이 같은 일을 하면 괜찮지만 다르면 동작이 조용히 바뀝니다. Span 변수를 넘기면 두 버전 모두 Span 판 — 항등 변환이 먼저입니다. C# 13 에서 모호하던 M(a) 는 C# 14 에서 스팬 판으로 풀립니다.
실행 검증

확장 메서드 찾기 — 안쪽 범위의 ReadOnlySpan 판에서 멈춘다

제안서: "By allowing implicit span conversions in extension method lookup, we can potentially change what extension method is resolved". 예제는 제안서의 N1·N2 그대로이고 주석은 "Prints N2 today, N1 tomorrow" 입니다.

확장 메서드는 안쪽 이름 공간(N1)부터 찾고, 맞는 후보가 있는 첫 범위에서 멈춥니다. C# 13 에서 Span<string> 은 N1 의 ReadOnlySpan 받는 쪽이 될 수 없어 using N2 까지 나갔고, C# 14 는 N1 에서 멈춥니다. 오버로드 해석의 "더 나은 판" 이 아니라 찾기 범위가 결과를 바꿉니다 — Span 판이 항등 변환인데도 집니다.

제안서: 스팬 변환이 표준 변환이 되면 "we can potentially change behavior when user-defined conversions are involved in a type hierarchy." 예제는 제안서 그대로이고 int 쪽은 "already behaves as the new C# 14 behavior will" 입니다.

오버로드 해석은 가장 파생된 형식의 메서드를 먼저 보고, 거기 적용 가능한 것이 있으면 기반의 메서드는 보지 않습니다. C# 14 에서 Span<string> → ReadOnlySpan<string>(표준) → Derived(사용자 정의) 가 이어져 Derived.M 이 적용 가능해졌고, Base.M(Span<string>) 의 항등 변환은 보이지도 않습니다. int 는 이미 int → long → Derived 로 그랬습니다.

null 조건 대입 — ?. 가 대입의 왼쪽으로

오른쪽은 받는 쪽이 null 이 아닐 때만 · ?[ ] 대입 · 복합 대입과 ??= · ++/-- 는 아직 · 식의 값과 형식 · 사슬 · 이벤트 · 안 되는 자리

왜 — 메서드는 되는데 속성 대입은 안 되던 비대칭

제안서의 동기는 둘입니다 — "Parity between properties and Set() methods", 그리고 "Attaching event handlers in UI code". 블로그의 Before 는 if (customer is not null) { customer.Order = …; customer.Total += …; }, After 는 그 두 줄을 customer?. 로 쓴 것입니다.

문서 근거

null 조건 대입 (null-conditional assignment) C# 14.0

왜 — whats-new: "The right side of the = operator is evaluated only when the left side isn't null. If customer is null, the code doesn't call GetCurrentOrder." 제안서는 문장으로 쓰인 P?.A = B 를 "equivalent to if (P is not null) P.A = B;, except that P is only evaluated once" 로 정의합니다.

Find 는 문장마다 한 번씩 불리고, bob 이 null 이면 GetOrder("B1") 은 불리지 않습니다. 이것은 C# 6 부터 메서드 호출 ?.SetOrder(GetOrder("B2")) 의 인수에 적용되던 규칙과 같습니다 — 제안서가 말한 "parity" 입니다. C# 13.0 은 대입 두 줄을 게이트 그대로 CS9260 "Feature 'null conditional assignment'" 로 거절하고, 메서드 호출 줄은 받습니다.

실행 검증

?[ ] 의 왼쪽 대입 — 배열과 사전

제안서의 세 번째 예는 arr?[42] = new object(); 이고, 문법은 "null_conditional_element_access assignment_operator expression" 입니다.

Update(null, null) 은 아무것도 하지 않고 예외도 없습니다. 진짜 배열·사전에는 =·+=·-= 가 모두 먹고, 사전의 인덱서 setter 는 없는 키 ink 를 더합니다(둘째 줄이 pen·ink 의 값 2 7). ?[] 가 막는 것은 받는 쪽의 null 뿐이라 범위를 벗어난 인덱스는 그대로 IndexOutOfRangeException 입니다.

실행 검증

복합 대입과 ??= — 되고, ++ 와 -- 는 안 된다

제안서: "All forms of compound assignment are allowed." 그리고 a?.b ??= c 를 "if (a is not null) { if (a.b is null) { a.b = c; } }" 로 풉니다. 증감 연산자는 "not supported" — a?.b++ 와 --a?.b 둘 다 오류입니다.

off?.Hits += Step(4) 의 Step(4) 는 불리지 않습니다 — 복합 대입의 오른쪽도 같은 규칙입니다. 3 * 2 = 6, 그리고 ??= 는 첫 값 first 만 남깁니다. 앞에 붙인 -- 도 뒤에 붙인 ++(7부)와 같은 CS1059 "must be a variable, property or indexer" 입니다 — 게이트가 아니라 C# 14 에서도 막혀 있는 자리입니다.

실행 검증

대입식의 값 — null 이 될 수 있는 형식으로

제안서: 문장이 아닌 자리의 P?.A = B 는 "(P is null) ? (T?)null : (P.A = B)" 입니다. 그래서 값을 쓰려면 "the expression's type must be known to be of a value type or a reference type" — 제약 없는 T 는 "'T' cannot be made nullable" 입니다.

int 필드에 대입한 식의 형식은 Nullable`1(int?)이고, 받는 쪽이 null 이면 값도 null 입니다. string 은 그대로 String 입니다. 복합 대입 none?.N += 1 도 int? 로 받을 수 있습니다. 같은 대입을 문장으로만 쓰면 제약 없는 T 에도 됩니다 — CS8978 은 값을 쓸 때만 납니다. C# 6 의 ?. 읽기와 같은 규칙입니다(7부).

실행 검증

사슬과 겹친 대입 — 어디서 멈추나

제안서의 복잡한 예: a?.b?.c = d 는 a, 그다음 a.b 가 null 이면 멈추고, a?.b = c?.d = e?.f 는 오른쪽부터 "a?.b = (c?.d = e?.f)" 입니다.

lone?.Next?.Name 은 lone.Next 가 null 이라 멈춰 lone 은 그대로입니다. 세 겹 대입은 e.Tag 를 c.Tag 에, 그 값을 a.Tag 에 넣습니다. 마지막 줄의 함정 — 오른쪽이 none?.Tag 처럼 null 로 끝나도 왼쪽 a 가 null 이 아니면 대입은 일어나 a.Tag 가 null 이 됩니다. ?. 는 받는 쪽만 봅니다.

실행 검증

이벤트 처리기 붙이기와 떼기 — UI 코드의 동기

제안서의 둘째 예가 c?.E += () => { … }; 이고, 동기 둘째가 "Attaching event handlers in UI code" 입니다.

버튼이 없는 empty 에는 아무 일도 없고, 붙인 처리기는 한 번 불린 뒤 -= 로 떨어집니다. 이벤트는 ?. 가 붙어도 선언한 형식 밖에서는 +=·-= 만 됩니다 — = 는 이벤트의 규칙 그대로 CS0070 입니다.

실행 검증

안 되는 자리 (1) — 받는 쪽이 값 형식이면

제안서: 이 기능은 "generally doesn't work when the receiver of the conditional access is a value type" — null 이 될 수 없는 구조체에는 ?. 자체가 안 되고, MyStruct? 는 "a.Value is not a variable" 이라 대입할 곳이 없습니다.

구조체 p 에는 ?. 자체가 안 되어 CS0023 이고, Point? 는 ?. 는 되지만 q.Value 의 복사본에 쓰게 되므로 CS0131 입니다. 구조체를 고칠 거라면 지역 변수로 꺼내 고친 뒤 다시 넣어야 합니다.

실행 검증

안 되는 자리 (2) — 여전히 변수는 아니다

제안서: "Conditional access expressions are still not lvalues, and it's still not allowed to e.g. take a ref to them", 분해 대입의 왼쪽도 안 됩니다. 한편 ref 를 돌려주는 메서드 호출 c?.M() = 42 는 "equivalent to: if (c is not null) c.M() = 42;" 입니다.

c?.Slot() = 42 는 c 의 숨은 필드에 42 를 쓰고, null 인 d 에는 Slot() 을 부르지도 않습니다. ?. 가 들어간 식은 대입의 왼쪽이 될 수 있을 뿐 변수가 되지는 않아, ref 인수는 CS1510, 분해 대입은 CS0131 입니다.
