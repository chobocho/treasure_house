목록 패턴 — 배열의 모양을 패턴으로

[1, .., 3] · 슬라이스 패턴 · 받는 형식 · 낮춤 · 겹친 패턴 · 빠짐없는 switch · 복사 · C# 12 의 짝

왜 — 패턴 매칭 이야기의 다음 장

발표 글: "Pattern matching is one of the ongoing stories in C# that we just keep filling out." 그리고 "C# 11 adds list patterns to the story. With list patterns you can apply patterns recursively to the individual elements of list-like input – or to a range of them."

Old 는 길이를 먼저 묻고 인덱서로 원소를 꺼내 비교합니다. 길이 검사와 인덱싱의 차례를 틀리면 IndexOutOfRangeException 입니다. New 는 배열의 모양 자체를 적습니다. [1, 9] 도 [1, .., 9] 에 맞습니다 — .. 는 원소 0개에도 맞습니다. 앞 부들의 예고 (8부, 9부, 10부)를 여기서 이어 받습니다.

실행 검증

목록 패턴 (list patterns) C# 11.0

왜 — whats-new: "List patterns extend pattern matching to match sequences of elements in a list or an array." 원소 자리에는 아무 패턴이나 오고, "The discard pattern (_) matches any single element, and the new range pattern (..) matches any sequence of zero or more elements."

[1, 9, 9, 9] 는 [1, ..] 에서 멈춥니다 — switch 는 위에서부터입니다. object 에는 먼저 형식 패턴(int[] and)을 붙여야 목록 패턴을 쓸 수 있습니다. C# 10.0 의 거절은 갈래마다 하나씩, 일곱 줄 모두 CS8936 'list pattern' 입니다.

실행 검증

슬라이스 패턴 — .. var rest 의 형식은 무엇인가

제안서: 슬라이스 패턴의 입력 형식은 "the return type of the underlying this[Range] or Slice method with two exceptions: For string and arrays, string.Substring and RuntimeHelpers.GetSubArray will be used, respectively."

잘라 낸 조각은 원래와 같은 형식입니다 — 배열은 Int32[], 문자열은 String, 목록은 List`1 이고, Span 의 조각도 Span 입니다(ref struct 라 GetType() 을 부를 수 없어 캡처에는 길이만 찍었습니다). List<T> 의 조각은 .NET 10 의 List<T>.Slice 에서 옵니다(9부). [.., var a, var b] 처럼 슬라이스를 앞에 두면 끝의 원소에 이름을 붙입니다.

실행 검증

받는 형식 — 셀 수 있고 인덱싱할 수 있으면

제안서: 목록 패턴은 "any type that is countable as well as indexable" 에 쓰이고, 하위 패턴이 있는 슬라이스는 "countable as well as sliceable" 이어야 합니다. 이 규칙은 C# 8 의 "range indexer pattern" 에서 왔습니다(9부).

함정 — 자를 수 없는 형식의 .. var r 는 목록 패턴 전용 문장이 아니라 CS1503 "cannot convert from 'System.Range' to 'int'" 입니다. 컴파일러가 Range 를 int 인덱서에 넘겨 보다 실패한 것입니다. 반면 IEnumerable<int> 에는 전용 오류 CS8985("No suitable 'Length' or 'Count' property")가 나옵니다. 하위 패턴 없는 .. 만 쓰면 Bag 도 됩니다.
실행 검증

Slice(int, int) 를 달면 — 시작과 길이로 불린다

제안서: 자를 수 있다는 것은 "an accessible indexer that takes a Range as an argument or otherwise an accessible Slice method with two int parameters" 가 있다는 뜻입니다. 하위 패턴 없는 슬라이스는 "acts like a proper discard" 라 아무것도 부르지 않습니다.

[_, .. var mid, _] 는 Slice(1, 3) — 끝 인덱스가 아니라 길이입니다. [.. var all] 도 통째로 Slice(0, 5) 를, [var f, .. var rest] 는 Slice(1, 4) 를 부르고, 조각 안에 다시 목록 패턴을 겹칠 수 있습니다. 마지막 줄 [1, .., 5] 는 Slice 를 부르지 않았습니다.

실행 검증

낮춤(lowering) — Count 는 몇 번 읽히나

제안서의 낮춤: expr is [1, 2, 3] 은 "expr.Length is 3 && expr[new Index(0, fromEnd: false)] is 1 …" 과 같습니다. 그리고 "[..] will not emit a Length check". 원소를 맞추는 차례는 "unspecified" 입니다.

Count 는 패턴마다 한 번입니다. ^1 은 Index 를 받는 인덱서가 없으니 Count - 1, 곧 [2] 로 바뀌어 불립니다. [1, 2, 4] 는 앞에서부터 셋을 다 읽고 실패했고, [..] 는 아무것도 읽지 않았습니다. switch 의 두 갈래는 [0] 을 한 번만 읽습니다 — 결정 그래프(DAG)가 같은 검사를 나눠 쓰기 때문입니다.

실행 검증

겹친 패턴 — 속성 패턴 안의 목록, 목록 안의 목록

whats-new: "You can match elements using any pattern, including constant, type, property and relational patterns." 제안서: 슬라이스의 하위 패턴이 목록이면 "subpatterns are treated as if they were a direct subpattern of the containing list".

Id: ['A', ..] 는 문자열의 첫 글자를, Qty: [> 0, ..] 는 첫 수량을 봅니다 — C# 9 의 관계 패턴이 원소 자리에 들어갑니다. A8 은 첫 수량이 0 이라 "plain" 입니다. Qty.Length 는 C# 10 의 확장 속성 패턴입니다(11부). 슬라이스 뒤에는 목록 패턴도, 속성 패턴 { Length: 2 } 도 옵니다.

실행 검증

빠짐없는 switch — 컴파일러가 빠진 모양을 예로 든다

제안서: 목록 패턴의 포섭 검사는 "just like positional patterns with ITuple" — 자리마다의 하위 패턴에 "an additional node for testing length" 가 더해집니다.

함정 — CS8509 의 예는 목록 패턴 모양이 아닐 수 있습니다. [_] 를 빼면 "{ Length: 1 }" 이라고 길이로 말하고, [_, .., < 0] 을 빼면 "[0, -1]" 이라는 구체적인 배열을 듭니다. 어느 쪽이든 경고일 뿐이라 프로그램은 돌고, 그 모양이 들어오면 SwitchExpressionException 으로 끝납니다(종료 코드 -6).
실행 검증

같은 원소를 두 번 묻는 패턴 — 도달할 수 없는 case

제안서의 예: case [_, .., 1]: 다음의 case [.., _, 1]: 는 "produces an error because both patterns yield the same DAG". 반면 [_, 1, ..] 와 [.., 1, _] 는 다릅니다 — 길이에 따라 같은 원소일 수도, 아닐 수도 있습니다.

[.., _, 1] 은 CS8120(도달할 수 없는 case)입니다. 길이가 3 인 { 5, 7, 9 } 에서는 [1] 과 [^2] 가 같은 원소라 b 와 c 가 둘 다 7 입니다. 제안서가 "a test for this value is inserted into the decision DAG" 라고 적은 경우입니다.

실행 검증

깨지는 변경 — Length·Count 는 음수가 아니라고 본다

Roslyn 의 호환성 문서: Length 와 Count 는 "are assumed to be non-negative for purpose of subsumption and exhaustiveness analysis of patterns and switches." 문서의 예 i is { Length: -1 } 은 오류가 됐고, 이 변경은 "made as part of adding list patterns" 입니다.

Count: < 0 갈래 없이도 CS8509 가 없고, { Length: -1 } 은 CS8518(결코 맞을 수 없다)입니다. C# 10.0 으로 내려도 같습니다 — 문서가 이 변경을 언어 버전이 아니라 컴파일러 판(SDK 6.0.200)에 묶었기 때문입니다. or 의 한쪽만 불가능한 { Length: < 0 } or [_] 은 아무 진단 없이 컴파일됩니다.

실행 검증

함정 — 배열의 .. var rest 는 매번 새 배열

발표 글은 목록 패턴의 예로 [var first, ..var rest] => first + AddAll<T>(rest) 라는 재귀를 듭니다. 배열의 조각은 GetSubArray 가 만든 새 배열입니다(9부). 같은 재귀를 배열과 ReadOnlySpan<int> 로 견줘 봅니다.

배열의 조각에 쓴 99 는 원래 배열에 닿지 않고, Span 의 조각에 쓴 99 는 닿습니다. 원소 100개의 재귀 합에서 배열 판은 조각 원소 4950개를 베끼며 22376바이트를 할당했고, Span 판은 0바이트입니다. 재귀로 쪼개는 알고리즘이라면 슬라이스 패턴의 입력을 Span 으로 받는 편이 맞습니다.

실행 검증

뒤 버전 — C# 12 의 컬렉션 식은 목록 패턴의 짝

C# 12 의 컬렉션 식 제안서: 목록 패턴은 "matching and deconstruction of list-like values" 를 주지만 "unlike almost all other pattern constructs, this matching/deconstruction syntax lacks the corresponding construction syntax." 그래서 만드는 문법을 [e1, ..c2, e2] 로, 패턴의 [p1, ..p2, p3] 에 맞췄습니다.

C# 11.0 으로 내리면 거절은 만드는 쪽(collection expressions) 넷뿐이고, 목록 패턴 두 줄은 통과합니다. 패턴이 한 버전 먼저 왔습니다. 컬렉션 식은 13부에서 다룹니다.

실행 검증

6장 퀴즈 — 목록 패턴

Q. Count 와 this[int] 만 있는 형식 Bag 에 b is [var first, .. var rest] 를 쓰면 어떻게 됩니까? 컴파일되게 하려면 무엇을 더하고, 그때 Bag 의 원소가 5개라면 무엇이 불립니까?

A. Range 를 받는 인덱서도 Slice 도 없어서 CS1503(Range 를 int 로 바꿀 수 없다)입니다(앞). Slice(int start, int length) 를 더하면 되고, 이때 Slice(1, 4) 가 불립니다 — 두 번째 인수는 끝이 아니라 길이입니다 (앞).

required 와 구조체 기본값 — 만들 때의 약속

required · SetsRequiredMembers · new() 제약 · 붙일 수 없는 곳 · 상속 · 메타데이터 · nullable · 구조체 필드의 자동 기본값 · 숨은 경고

왜 — 생성자 매개변수를 층마다 되풀이하던 일

제안서의 동기: "Object hierarchies today require a lot of boilerplate to carry data across all levels of the hierarchy." 발표 글: "When creating types that used object initializers, you used to be unable to specify that some properties must be initialized."

생성자로 강제하면 파생 클래스 Student 가 부모의 매개변수를 모두 다시 받아 넘겨야 합니다. C# 9 의 init 은 초기화자로 쓰게 해 줬지만 빠뜨린 Last 는 조용히 null 입니다. 이 빈칸은 7부와 10부에서 예고했습니다.

실행 검증

required 멤버 (required members) C# 11.0

왜 — whats-new: "You can add the required modifier to properties and fields to enforce constructors and callers to initialize those values." 예제는 발표 글의 Person 그대로이고, 글은 "It is now an error to create a Person without initializing both the required properties" 라고 적습니다.

빠뜨린 멤버마다 CS9035 가 하나씩 나오고, 문장이 채울 곳을 "object initializer or attribute constructor" 둘로 말합니다(뒤). C# 10.0 의 거절은 선언한 두 줄에만 나옵니다. MiddleName 처럼 required 가 없는 멤버는 예전처럼 빠뜨려도 됩니다.

실행 검증

[SetsRequiredMembers] — 생성자가 다 채운다는 약속

제안서: 이 특성은 생성자에서 요구를 없애지만 "The constructor body is not validated to ensure that it definitely sets the required members of the type." 그리고 이 특성이 붙은 생성자로 잇는(: this(…)) 생성자에도 붙여야 합니다.

함정 — Person(int) 는 아무것도 채우지 않는데도 오류가 없고 Last 는 null 입니다. nullable 을 켜야 CS8618 이 나오는데, 그 문장은 이미 required 인 속성에게 "Consider adding the 'required' modifier" 를 권합니다. 특성이 요구를 지우면 컴파일러에게는 보통 생성자와 같아집니다.
실행 검증

new() 제약과 default — 약속을 지킬 수 없는 곳

제안서: 계약을 내건 매개변수 없는 생성자를 가진 형식은 new() 제약의 형식 인수가 될 수 없습니다 — "there is no way for the generic instantiation to ensure that the requirements are satisfied." 구조체는 "not enforced on instances of struct types created with default" 이지만 new StructType() 에는 적용됩니다.

default 와 배열의 원소는 0 으로 채워진 채 아무 진단이 없습니다. new Point() 는 구조체에 직접 쓴 생성자가 없어도 CS9035 입니다. CS9040 문장에는 "generic type or or method" 라고 "or" 가 두 번 들어 있습니다 — 컴파일러 문장 그대로입니다.

실행 검증

required 를 붙일 수 없는 곳 — 채울 길이 없으면 안 된다

제안서: "It is an error to mark a member required if the member cannot be set in any context where the containing type is visible." 필드는 readonly 일 수 없고, 속성은 형식만큼 보이는 setter 나 initer 가 있어야 합니다. static 과 함께 쓸 수 없고 인덱서·인터페이스에는 붙지 않으며, 가리는 것(hide)도 오류입니다.

여덟 갈래를 하나씩 켜서 컴파일한 결과는 상속·특성의 거절과 함께 뒤의 표에 모았습니다.

실행 검증

상속 — 목록은 물려받고, override 는 required 를 다시 적는다

제안서: 형식은 "inherit these lists from their base types automatically". required 멤버를 override 할 때는 "the required keyword must be included", 그리고 required 가 아니던 멤버를 override 에서 required 로 만들 수 있습니다.

앞의 Student 와 달리 Cat 은 생성자 하나 없이 Name 의 약속을 물려받습니다. Dog 는 기본값 "?" 가 있던 Sound 를 override 로 required 로 올렸고, 그래서 빠뜨리면 CS9035 입니다.

실행 검증

채우는 다른 두 길 — 특성의 이름 붙은 인수, 그리고 with

제안서: 소비자는 required 멤버를 객체 초기화자에서, 또는 "via the named_argument_list section of an attribute_target" 에서 채웁니다. 레코드는 합성된 복사 생성자에 SetsRequiredMembersAttribute 를 답니다.

특성을 적는 [Tag(…)] 도 객체 생성이라 Name 을 빠뜨리면 CS9035 입니다. r1 with { } 는 X 를 적지 않아도 됩니다 — 복사 생성자가 [SetsRequiredMembers] 라서입니다. 값은 원본에서 베껴 오므로 약속도 지켜집니다.

실행 검증

required 의 거절 모음

앞의 세 장 — 붙일 수 없는 곳, 상속, 특성 — 에서 본 거절을 한 표로 모읍니다.

실험 묶음이 각 캡처의 첫 오류 줄에서 뽑았습니다. 전용 번호는 CS9030–CS9040 사이에 모여 있지만, static·인덱서·인터페이스는 전용 문장 없이 옛 CS0106("not valid for this item")입니다. readonly 필드와 setter 없는 속성은 같은 CS9034("must be settable")로 묶였습니다.

실행 검증

메타데이터 — 옛 컴파일러를 막는 Obsolete

제안서: required 멤버와 그 형식에는 RequiredMemberAttribute, 특성 없는 생성자에는 CompilerFeatureRequiredAttribute("RequiredMembers") 와 오류로 표시된 ObsoleteAttribute 를 답니다 — "to prevent any older compilers from using these constructors". modreq 를 쓰지 않은 까닭은 "to maintain binary compat" 입니다.

문서와 다른 점 — 제안서가 적은 Obsolete 문장은 "Types with required members are not supported in this version of your compiler" 인데, 지금의 컴파일러가 단 것은 "Constructors of types with required members …" 입니다. True 는 오류로 다루라는 뜻입니다. ref struct 를 지킨 방법(8부)과 같은 두 겹입니다. 옛 컴파일러가 실제로 거절하는 모습은 보이지 못했습니다 — 그러려면 따로 컴파일한 라이브러리와 옛 컴파일러가 있어야 하는데, csrun 은 어셈블리 하나만 만들고 이 덱은 옛 컴파일러 없이 돕니다(0부).
실행 검증

nullable 과 함께 — = null! 이 필요 없어진다

제안서: required 멤버는 "not required to be initialized to a valid nullable state at the end of a constructor" — 채우는 일이 생성자에서 호출자로 넘어갔기 때문입니다. nullable 경고 CS8618 은 9부에서 봤습니다.

= null! 은 경고만 끄고 null 을 그대로 남깁니다(True). required 는 경고를 끄는 대신 채울 책임을 호출자에게 지웁니다. 그래도 그 자리에 null 을 넣으면 nullable 경고 CS8625 가 납니다 — required 는 "채웠는가" 를, nullable 은 "무엇으로 채웠는가" 를 봅니다.

실행 검증

구조체 필드의 자동 기본값 (auto-default structs) C# 11.0

왜 — 제안서: C# 1.0 부터 구조체 생성자는 this 를 out 매개변수처럼 모두 대입해야 했고, 그래서 setter 에 검사가 있는 속성은 "assign some value in the constructor before "really" assigning through the property setter" 같은 되풀이가 필요했습니다. 바뀐 규칙은 대입하지 않은 필드를 "initialize them implicitly to default instead of giving definite assignment errors" 입니다.

C# 10.0 은 MagnitudeVector3d() 에 필드마다 CS0171, Celsius 의 setter 호출에 CS0188 을 냅니다. 둘 다 문장 끝에서 11.0 을 권합니다. 2부·4부·11부가 이 거절을 C# 1·3·10 에서 봤고, 여기서는 그 규칙이 막던 코드 — setter 에 검사를 둔 속성 — 가 되는 것을 봅니다.

실행 검증

무엇이 들어가나 — 생성자의 IL 을 읽는 도구

제안서는 대입이 "inserted at the beginning of the constructor" 라고 적습니다. 확인하려고 4장의 해독기를 고쳐 생성자의 IL 을 nop 만 빼고 모두 찍게 했습니다. 필드·형식·메서드 토큰은 이름으로 바꿉니다.

실행 검증

제안서의 예 1·2·4·5 — 필드마다 0 을 먼저 대입한다

제안서의 예: (1) 아무것도 대입하지 않으면 "Compiler inserts an assignment of this = default", (2) x 만 대입하면 "y = default", (4) 갈래마다 다른 필드면 다시 this = default, (5) 메서드 호출 앞에 x 만 대입했으면 "y = default". 그리고 "the compiler should probably be free to implement whatever heuristic it wants".

제안서가 this = default 라고 적은 예 1·4 에서도 지금의 컴파일러는 initobj 대신 stfld x·stfld y 에 0 을 하나씩 넣습니다. 예 2·5 는 y 만 0 으로 만든 뒤 본문이 시작됩니다. 예 4 는 갈래 뒤에 다시 대입하니 같은 필드에 두 번 쓰는 셈이고, 제안서가 말한 "double assignments" 가 이것입니다.

실행 검증

꺼져 있는 경고 — 옛 오류는 사라지지 않고 숨었다

제안서: 두 번 대입이 신경 쓰이는 사용자를 위해 예전의 확정 대입 오류를 "disabled-by-default warning diagnostics" 로 남긴다. 그 심각도를 오류로 올리면 "opt in to the pre-C# 11 behavior" 입니다. 경고 문장은 컴파일러 자원에 있습니다.

기본 빌드는 조용합니다. 설정 파일로 심각도를 warning 으로 주면 CS9018–CS9022 다섯 가지가 여섯 줄로 나옵니다. 출력은 같습니다 — 경고는 컴파일러가 0 을 넣은 자리를 알려 줄 뿐입니다.

실행 검증

C# 10 의 오류와 C# 11 의 숨은 경고는 짝이다

같은 S.cs 를 -langversion:10.0 으로 컴파일한 오류와 C# 11 에서 켠 경고를 줄마다 맞댔습니다. 실험 묶음은 위치가 하나라도 어긋나면 표를 만들지 않습니다.

여섯 오류가 여섯 경고로 하나씩 옮겨 갔습니다. 이 경고들은 -warn:9999 로도 나오지 않습니다 — 경고 웨이브가 아니라 꺼진 채 태어난 진단입니다. 하나를 -warnaserror+ 로 올리면 그 하나만 C# 10 의 규칙으로 돌아갑니다.

실행 검증

7장 퀴즈 — required 와 자동 기본값

Q1. required 속성을 가진 Box 를 static T Make<T>() where T : new() 에 넘길 수 있습니까? [SetsRequiredMembers] 를 단 생성자가 아무것도 채우지 않으면 무엇이 알려 줍니까?

Q2. C# 11 에서 구조체 생성자가 필드 하나를 대입하지 않아도 조용합니다. 그 자리를 알고 싶으면 어떻게 합니까?

A1. 넘길 수 없습니다 — CS9040(앞). 특성이 붙은 생성자의 본문은 검사하지 않으므로 오류는 없고, nullable 을 켜야 CS8618 이 납니다(앞). A2. 꺼져 있는 CS9018–CS9022 의 심각도를 분석기 설정이나 -warnaserror+ 로 올립니다. -warn:9999 로는 켜지지 않습니다 (앞).
설명용

8장

ref 필드와 scoped — Span 을 직접 만든다

ref 필드 · 작은 Span · readonly 조합 · null ref · scoped 매개변수와 지역 변수 · out 의 변화 · [UnscopedRef] · 깨지는 변경 · RefSafetyRules

왜 — 런타임만 쓰던 ByReference<T>

제안서의 동기: "Today Span<T> is accomplished by using the internal type ByReference<T> which the runtime effectively treats as a ref field." 언어가 그 안전을 검사하지 못했고, "only dotnet/runtime can use this type as it's internal, so 3rd parties can not design their own primitives based on ref fields." 그래서 제안서가 세운 목표와 C# 11 이 실제로 담은 것은 이렇습니다.

제안서의 목표C# 11
ref struct 가 ref 필드를 선언하게들어옴 — ref 필드와 scoped
struct 가 자기 필드를 ref 로 돌려주게들어옴 — [UnscopedRef]
ref 필드가 ref struct 를 가리키게남은 제안("open proposals")
안전한 fixed 버퍼"not delivered in C# 11"

ref 의 앞 이야기 — ref 지역 변수와 반환, ref struct, Span — 는 8부와 8부의 ref struct에 있습니다.

문서 근거

ref 필드 (ref fields) C# 11.0

왜 — whats-new: "You can declare ref fields inside a ref struct. This supports types such as System.Span<T> without special attributes or hidden internal types." 제안서: ref 필드는 "ELEMENT_TYPE_BYREF" 시그니처로 기록되며 "no different than how we emit ref locals or ref arguments".

r.Value = 5 는 x 에 쓰고, r.Value = ref y 는 필드가 가리키는 곳을 바꿉니다 — C# 7.3 의 ref 재할당(8부)이 필드에도 됩니다. 배열의 원소도 가리킬 수 있습니다. C# 10.0 의 거절은 필드 선언 한 줄뿐입니다.

실행 검증

작은 Span 을 직접 — ref T 와 길이 하나

제안서는 이 설계가 끝나면 Span<T> 가 "readonly ref T _field; readonly int _length;" 두 필드로 정의된다고 적고, 값 하나를 감싸는 생성자 Span(ref T value) 를 예로 듭니다.

s[1] = 20 이 배열에 닿고, 지역 변수 하나 위의 MySpan 도 됩니다. 원소 위치는 Unsafe.Add, 배열의 첫 칸은 MemoryMarshal.GetArrayDataReference 가 주는데 둘 다 unsafe 문맥 없이 부르는 BCL 메서드입니다. 범위 검사는 직접 해야 합니다.

실행 검증

같이 온 런타임 — .NET 10 의 Span<T> 는 ref 필드다

제안서: 이 기능은 "requires runtime support and changes to the ECMA spec. As such these will only be enabled when the corresponding feature flag is set in corelib."

Span<int> 의 _reference 는 System.Int32&, 곧 ref 필드입니다. CoreLib 에는 System.ByReference 라는 형식이 아직 있지만 제네릭이 아니고 Span 은 그것을 쓰지 않습니다. 제안서가 "does not exist today but will be added" 라고 한 Span(ref T) 생성자도 있어서 지역 변수 위의 길이 1 짜리 Span 을 만듭니다.

실행 검증

readonly 와의 조합 — 가리키는 곳과 값, 둘 중 무엇이 고정인가

제안서: readonly ref 는 "cannot be ref reassigned outside a constructor or init methods", ref readonly 는 "can be ref reassigned but cannot be value assigned". readonly ref struct 의 ref 필드는 readonly ref 여야 합니다. ref 필드는 ref struct 안에만 둡니다.

Uses 가 Field1 을 a[1] 로 옮기고 Field2 로 a[1] 에 1 을 써서 합이 5 가 됐습니다. 다섯 갈래의 오류는 8장의 거절 표에 있습니다. ref struct 를 가리키는 ref 필드(CS9050)는 C# 14.0 에서도 거절됩니다 — 제안서가 남긴 과제 그대로입니다.

실행 검증

함정 — default 의 ref 필드는 null 을 가리킨다

제안서: default 로 만든 ref struct 의 ref 필드는 "will have the value null. Any attempt to use such fields will result in a NullReferenceException being thrown." 그래서 ref 필드는 Unsafe.IsNullRef 로 확인하라고 권합니다.

언어는 ref 가 null 일 수 없는 것처럼 다루지만 런타임 수준에서는 합법입니다. default 처럼 생성자를 거치지 않는 길이 있는 한(ref struct 는 배열의 원소가 될 수 없으니 남는 길은 주로 default 입니다), ref 필드를 가진 형식은 쓰기 전에 확인해야 합니다.

실행 검증

ref 필드는 ref 로 내줄 수 있다 — 보통 필드는 아니다

제안서: ref e.F 의 ref-safe-context 는 "If F is a ref field its ref-safe-context is the safe-context of e." 그래서 "ref fields can be returned as ref from a ref struct but normal fields cannot."

Pass 의 rs 는 메서드와 함께 사라지지만 그것이 가리키는 x 는 호출자의 것이라 반환할 수 있습니다. 같은 코드라도 rs 가 지역 변수를 가리키면 CS8352 입니다. 컴파일러는 ref struct 값이 "무엇을 가리킬 수 있는가" 를 따라갑니다(8부).

실행 검증

scoped 매개변수 — "이 ref 는 밖으로 나가지 않는다" C# 11.0

왜 — whats-new: "You can add the scoped modifier to any ref declaration. This limits the scope where the reference can escape to." 제안서: ref 매개변수가 반환되는 ref struct 에 담길 수 있게 되자, scoped 로 "the same rules as C# 10" 을 되돌릴 수 있게 했습니다.

Wrap(ref p) 는 .NET 10 의 Span(ref T) 로 p 를 결과에 담습니다. 그래서 지역 변수를 넘긴 결과는 반환할 수 없습니다(CS8347). Bump 는 scoped 라서 지역 변수를 받아도 결과를 반환할 수 있고, 대신 안에서 p 를 담으려 하면 CS9075 입니다. C# 10.0 의 거절은 'scoped' 가 아니라 'ref fields' 라는 이름으로 나옵니다 — 컴파일러는 둘을 한 게이트로 봅니다.

실행 검증

scoped 지역 변수 — 힙과 스택을 한 변수에

제안서: 지역 변수의 scoped 는 "sets the lifetime … to of function-member irrespective of the initializer lifetime." 그래서 default 로 시작한 scoped Span<int> 는 반환할 수 없고, scoped 없는 Span<int> span2 = default 는 반환할 수 있습니다.

buf 는 new int[n] 로 시작해도 scoped 라서 나중에 stackalloc 을 받을 수 있습니다. scoped 가 없으면 초기화자가 정한 넓은 수명 때문에 stackalloc 이 CS8353 입니다. 작은 크기는 스택, 큰 크기는 힙 — 이 흔한 꼴도 ?: 초기화자 한 줄로는 C# 7.2 부터 됐습니다(9부). scoped 가 새로 연 것은 초기화한 뒤에 stackalloc 을 다시 대입하는 길입니다.

실행 검증

out 은 이제 암시적으로 scoped — 그리고 언어 버전을 보지 않는다

제안서: "out parameters are implicitly scoped out going forward. From a compat perspective this means they cannot be returned by ref." 되돌리는 길은 [UnscopedRef] out 입니다. Roslyn 의 호환성 문서는 조건을 "With language version C# 11 or later, or with .NET 7.0 or later" 라고 적습니다.

문서와 다른 점 — 호환성 문서의 예는 CS8166("because it is not a ref parameter")인데 지금의 컴파일러는 CS9075("because it is scoped to the current method")입니다. 그리고 C# 7.3 으로 내려도 같은 오류입니다. .NET 10 을 대상으로 하면 ref 안전 규칙은 언어 버전과 상관없이 C# 11 의 것입니다(뒤).
실행 검증

[UnscopedRef] — 구조체가 자기 필드를 ref 로 C# 11.0

제안서: 구조체의 인스턴스 멤버가 필드를 ref 로 돌려주지 못하는 것은 "simply the default chosen by the ref safe context rules" 이고, UnscopedRefAttribute 는 "the opposite of the scoped lifetime annotation" 입니다. 인스턴스 멤버에 붙이면 this 의 ref-safe-context 가 한 단계 넓어집니다.

8부가 C# 7.0 에서 본 CS8170 이 특성 하나로 풀립니다. 속성에 쓰고, ref 로 받아 더하고, ref 지역 변수로 올려서 16 이 됐습니다. 그래도 사라질 임시 값(new Counter())의 필드를 메서드 밖으로 내보내는 것은 CS8156 으로 막힙니다.

실행 검증

깨지는 변경 — 문서의 예 둘을 지금의 컴파일러로

호환성 문서는 C# 11 의 ref 안전 규칙이 낳은 변경으로 "Instance method on ref struct may capture unscoped ref parameters"(CS8350)와 "Method ref struct return escape analysis depends on ref escape of ref arguments" — 숨은 in 기본 인수를 포함해 — 를 듭니다.

문서와 다른 점 — 첫 예 r.MayCaptureArg(ref i) 는 오류 없이 돕니다. 대신 ref struct 의 메서드가 ref 매개변수를 자기 ref 필드에 담으려 하면 그 자리에서 CS9079 입니다 — 호출하는 쪽이 아니라 메서드 쪽에서 막힙니다. 둘째 예는 그대로 거절되지만 오류가 둘이고 첫 줄은 CS8156 입니다.
실행 검증

메타데이터 — Int32&, IsReadOnly, ScopedRef

제안서: readonly ref 는 initonly, ref readonly 는 IsReadOnlyAttribute 로 기록합니다. scoped 는 ScopedRefAttribute 로 남기되 "only be emitted when the syntax causes the value to differ from its default state. For example scoped out will cause no attribute to be emitted."

세 필드 모두 형식이 System.Int32& 입니다. scoped ref p 와 scoped Span<int> s 에는 ScopedRefAttribute 가 있고, scoped out o 에는 원래 있던 OutAttribute 뿐입니다 — out 은 이미 scoped 라서입니다.

실행 검증

RefSafetyRules(11) — 어느 언어 버전으로 컴파일해도

제안서: 컴파일러는 "[module: RefSafetyRules(11)] attribute when the module is compiled with -langversion:11 or higher or compiled with a corlib containing the feature flag for ref fields" 를 내보내고, 다른 모듈의 메서드를 부를 때 이 표시로 C# 11 규칙과 C# 7.2 규칙 가운데 하나를 고릅니다.

네 언어 버전 모두 RefSafetyRulesAttribute 11 입니다. .NET 10 의 CoreLib 에 ref 필드 플래그가 있으니 둘째 조건이 늘 참입니다. 앞에서 C# 7.3 으로 내려도 out 규칙이 바뀌지 않은 까닭이 이것입니다.

실행 검증

8장의 거절 모음 — ref 안전

실험 묶음이 각 캡처의 첫 오류 줄에서 뽑았습니다. ref 필드의 선언 규칙에는 CS9050·CS9059 같은 새 번호가 생겼지만, readonly 와 수명의 거절은 CS0191·CS8170·CS8352 처럼 C# 7 시절의 번호를 그대로 씁니다. readonly ref 를 다시 가리킬 때의 문장은 "cannot be assigned to" — ref 재할당도 대입으로 부릅니다.

실행 검증

8장 퀴즈 — ref 필드와 scoped

Q1. static Span<int> F(ref int p) 에 지역 변수를 넘긴 결과를 반환하려니 CS8347 입니다. F 가 p 를 결과에 담지 않는다면 무엇을 고치면 됩니까?

Q2. 이 프로젝트를 -langversion:10.0 으로 내리면 out 매개변수를 ref 로 반환할 수 있게 됩니까?

A1. 매개변수를 scoped ref int p 로 선언합니다. 그러면 호출하는 쪽은 지역 변수를 넘기고도 결과를 반환할 수 있습니다(앞). A2. 아닙니다. .NET 10 을 대상으로 하면 C# 7.3 에서도 CS9075 입니다. 되돌리려면 [UnscopedRef] out 을 씁니다(앞, 앞).

9장

file 형식과 12부 정리

file 형식 · 메타데이터 이름 · 시그니처의 규칙 · 예약된 이름 · C# 11 기능 장 · 같은 프로그램 두 판 · 문서와 컴파일러 · C# 12 로 · 12부 퀴즈

file 형식 (file-local types) C# 11.0

왜 — 제안서: "Our primary motivation is from source generators." 생성기가 넣는 파일은 "implementation details which are hidden from the rest of the compilation" 을 담을 수 있어야 하고, 사용자 코드와 겹치지 않을 이름을 "search" 하는 일을 줄이려 했습니다. whats-new: "This feature helps source generator authors avoid naming collisions."

같은 이름의 형식 셋이 한 어셈블리에 있고 서로 부딪치지 않습니다. A.cs 안에서는 file 형식이 보통 Widget 을 가립니다 — 제안서가 "permit a file-local type to shadow … a non-file-local type" 이라고 적은 규칙입니다. 소스 생성기는 이 덱의 csrun 으로 돌릴 수 없어서(10부) 손으로 쓴 파일 둘로 보였습니다.

실행 검증

메타데이터의 이름 — <파일>F + 해시 + __이름

제안서: 이름이 같은 file 형식들은 런타임에게 서로 다른 형식이고 "The type's accessibility and name in metadata is implementation-defined." 특성으로 쓴 file 형식을 "detecting … by a hard-coded string name is likely to be impractical" 하니 typeof 로 찾으라고 하며 예제를 듭니다.

지금의 컴파일러는 <Program>F 뒤에 16진 64자리를 붙이고 __Helper 로 끝냅니다. 앞의 Program 은 파일 이름이고, internal 이라 IsPublic 은 False 입니다. 소스에 적은 이름 "Helper" 로는 GetType 이 찾지 못합니다. 이 이름 짓기는 "implementation-defined" 이므로 문자열로 기대지 말아야 합니다.

실행 검증

시그니처에는 나올 수 없다 — file 형식은 file 형식 안에서만

제안서: file 형식이 쓰이는 곳에서 보이지 않을 수 있으므로 "file-local types can only appear in signatures or as base types of other file-local types". 보통 형식이 file 인터페이스를 구현하는 것은 됩니다. 접근성 한정자는 함께 쓸 수 없고, 최상위 형식에만 붙으며, global using static 에도 쓸 수 없습니다.
