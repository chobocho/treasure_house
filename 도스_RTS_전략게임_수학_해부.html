왜 타일인가

1992년의 기계가 320×200 화면을 매 프레임 다시 그릴 수는 없었습니다. 64,000픽셀을 18.2 Hz 로 채우려면 초당 116만 번의 메모리 쓰기가 필요합니다.

답은 화면을 같은 크기의 조각으로 나누고, 조각 하나를 통째로 복사하는 것이었습니다. 픽셀 단위 계산이 타일 단위 계산으로 줄어듭니다.

단위개수비고
화면 픽셀320 × 200 = 64,000Mode 13h
뷰포트 픽셀256 × 176 = 45,056우측 패널 64px 제외
뷰포트 타일16 × 11 = 176364배 적다
맵 타일64 × 64 = 4,096맵 전체

경로 탐색·시야·충돌이 전부 4,096칸 위에서 벌어집니다. 6만 픽셀이 아니라요.

16×16 인가 32×32 인가

Dune II(1992)와 Command & Conquer(1995)는 320×200 에 16×16 타일을 썼습니다. Warcraft II(1995)는 640×480 SVGA 에 32×32 를 썼습니다.

둘은 화면에 보이는 타일 수가 거의 같습니다.

320×200, 16×16  →  가로 20칸 (뷰포트 16칸)
640×480, 32×32  →  가로 20칸

해상도가 두 배가 되자 타일도 두 배가 된 것입니다. 화면에 몇 칸이 보이느냐가 게임의 시야를 정하고, 그것은 해상도와 무관하게 지켜야 할 설계값이었습니다.

이 엔진은 320×200 · 16×16 을 고릅니다. 2부에서 본 대로 Dune II 와 Warcraft I 의 정확한 타일 픽셀 크기는 1차 자료로 확인하지 못했습니다. 그래서 이 덱의 선택이라고 적습니다.

한 칸에 두 바이트

한 칸의 정보를 비트로 우겨 넣지 않습니다. 두 배열로 나눕니다.

terrain[i]   지형 종류 (0..7)
pass[i]      통행 비트 4개

pass 가 terrain 에서 파생되는 값인데도 따로 두는 이유는 건물 때문입니다. 건물이 서면 그 칸이 막히고, 부서지면 다시 열립니다. 지형은 그대로인데 통행만 바뀝니다.

비트 번호 0 과 1 이 이동 종류 번호와 같습니다(0 = 보병, 1 = 차량). 그래서 bit(pass[i], kind) 한 줄로 두 종류를 함께 다룹니다.

경로 탐색은 점유 비트를 보지 않습니다. 움직이는 유닛 때문에 경로가 매 틱 흔들리면 무리 이동이 통째로 무너집니다. 점유는 14부의 예약 규칙이 국소적으로 처리합니다.

맵 밖은 바위다

    def terrain_at(self, x, y):
        """맵 밖은 ROCK 이다 — 호출자가 경계 검사를 하지 않아도 되고,
           오토타일 마스크가 가장자리에서 자연스럽게 닫힌다."""

맵 밖을 물어보면 ROCK 을 돌려줍니다. 이 한 줄이 두 가지를 동시에 해결합니다.

  • 호출자가 경계 검사를 하지 않아도 됩니다. 오토타일 마스크는 이웃 여덟 칸을 무조건 읽습니다.
  • 맵 가장자리에서 그림이 자연스럽게 닫힙니다. 밖이 바위이므로 가장자리 타일이 "경계가 있는" 그림을 고릅니다.
§11.4 의 브러시파이어도 같은 규약을 씁니다 — 맵 밖을 막힌 칸으로 보므로 가장자리 칸의 "장애물까지의 거리"가 10 이 되고, AI 가 맵 끝에 건물을 붙이지 않습니다.

건물이 선 칸

건물은 유닛과 다릅니다. 비키지 않습니다.

    def set_building(self, x, y, on):
        """건물이 선 칸 — 통행 비트를 내리고 점유 비트를 세운다 (SPEC §4.3).

           유닛과 달리 건물은 비키지 않는다. 예약(§13.2)만으로 막으면 유닛이
           건물을 향해 24틱을 두드리다 포기하므로, 경로 그래프에서 아예 뺀다.
           `version` 이 오르니 경로 캐시와 연결 성분이 함께 무효가 된다.
        """
        i = y * self.w + x
        if on:
            self.pass_[i] = 8                      # 점유 비트만 남긴다

처음에는 건물도 유닛처럼 예약만으로 막으려 했습니다. 그러면 경로 탐색이 건물을 지나가는 경로를 만들고, 유닛이 벽 앞에서 24틱을 두드리다 명령을 포기합니다.

이것은 명세 초안의 오류였고 구현하면서 드러났습니다. 건물은 경로 그래프에서 아예 빠져야 합니다. 부서질 때는 그 칸을 RUBBLE 로 바꾸는 것만으로 통행이 복구됩니다 — 잔해는 통행 가능한 지형이니까요.

version 이 오르는 것도 중요합니다. 경로 캐시와 연결 성분이 함께 무효가 됩니다. 낡은 경로는 곧 디싱크입니다.

오토타일 — 이웃 여덟 칸이 정한다

모래밭과 흙밭이 만나는 자리에 경계 그림이 필요합니다. 그 그림을 어떻게 고를까요?

한 칸이 어떤 그림을 쓸지는 이웃 여덟 칸이 나와 같은 지형인가로 결정됩니다. 방향 번호(§2.7)를 그대로 비트 번호로 씁니다.

     7  0  1        NW  N  NE
     6  ·  2         W  ·  E
     5  4  3        SW  S  SE

    # ── SPEC §4.4 이웃 마스크 ──────────────────────────────────────────────
    def mask(self, x, y):
        """이웃 8칸 중 나와 같은 지형인 방향의 비트합."""
        t = self.terrain_at(x, y)
        m = 0
        for d in range(8):
            if self.terrain_at(x + F.DX[d], y + F.DY[d]) == t:
                m = F.setbit(m, d)
        return m

정리 4.1 — 모서리는 언제 보이는가

정리 4.1. 모서리 이웃 c 는 그 양옆의 변 이웃 두 개가 모두 같을 때만 그림에 영향을 준다. 이 규칙으로 정규화한 마스크는 정확히 47가지다.

이유. 변 이웃 하나라도 다르면 그 방향에 이미 경계선이 그려집니다. 모서리 칸의 상태는 그 선에 가려 보이지 않습니다.

def canon(m):
    """모서리 비트는 양옆 변이 둘 다 있을 때만 살린다 (SPEC 정리 4.1)."""
    r = m
    for c, a, b in _CORNERS:
        if not (F.bit(m, a) and F.bit(m, b)):
            r = F.clrbit(r, c)
    return r

py/rts/tmap.py154–192유니온-파인드, 경로 압축
    # ── SPEC §4.6 연결 성분 (유니온–파인드) ────────────────────────────────
    def labels(self, kind):
        """통행 가능 칸을 8방향으로 묶은 대표 원소 배열. 막힌 칸은 -1.

           지형이 바뀌면 통째로 다시 계산한다. 증분 삭제가 되는 유니온–파인드는
           복잡하고, 4096칸 재계산은 측정상 1 ms 미만이다.
        """
        if kind in self._labels:
            return self._labels[kind]
        n = self.w * self.h
        parent = list(range(n))

        def find(a):
            root = a
            while parent[root] != root:
                root = parent[root]
            while parent[a] != root:               # 경로 압축
                parent[a], a = root, parent[a]
            return root

        for y in range(self.h):
            for x in range(self.w):
                if not self.passable_terrain(x, y, kind):
                    continue
                a = find(y * self.w + x)
                for d in range(8):
                    u, v = x + F.DX[d], y + F.DY[d]
                    if self.passable_terrain(u, v, kind):
                        b = find(v * self.w + u)
                        if a != b:
                            parent[b] = a
                            a = find(a)
        out = [-1] * n
        for y in range(self.h):
            for x in range(self.w):
                if self.passable_terrain(x, y, kind):
                    out[y * self.w + x] = find(y * self.w + x)
        self._labels[kind] = out
        return out

이 덱이 30년 뒤에도 같은 선택을 하는 이유는 FPU 가 없어서가 아닙니다. 세 언어가 같은 답을 내야 하기 때문입니다. 19부에서 보겠지만, 실수 한 줄이 락스텝을 무너뜨립니다.

16.16 — 정의

32비트 정수 하나를 상위 16비트(정수부)와 하위 16비트(소수부)로 나눠 읽습니다.

실수 v  ↔  정수 x = v · 65536
1.0   = 65536      0.5  = 32768      1.5  = 98304
1/√2  = 46341      √2−1 = 27146     −1.0  = −65536
연산16.16 구현왜
정수 → 고정x = n · 65536곱셈 하나
고정 → 정수floordiv(x, 65536)내림이지 자름이 아니다
더하기·빼기그냥 + −단위가 같으므로
곱하기floordiv(a·b, 65536)단위가 두 번 곱해졌으므로 한 번 나눈다
나누기floordiv(a·65536, b)먼저 올려놓고 나눈다

덧셈과 뺄셈은 손댈 것이 없습니다. 값의 범위를 |x| < 2³¹ 로 제한해 두면 |a| + |b| < 2³² 이라 세 언어 모두 정확합니다.

왜 자름이 아니라 내림인가

−1.5 를 정수로 바꾸면 −1 입니까, −2 입니까?

C 의 / 는 0 쪽으로 자릅니다(−1). 파이썬의 // 는 −∞ 쪽으로 내립니다(−2). 둘 다 맞지만 하나만 골라야 합니다.

py/rts/fixed.py33–36명세는 내림이다

    """b > 0 일 때 -무한대 방향 내림. 파이썬의 // 가 이미 그렇다."""

내림을 고른 이유는 타일 좌표 때문입니다. 월드 픽셀 −1 은 타일 −1 에 속해야 합니다. 자름을 쓰면 −15…−1 이 전부 타일 0 이 되어 맵 왼쪽 가장자리에서 한 칸이 두 배로 넓어집니다.

루아 5.1 에는 정수 나눗셈이 없고, 자바스크립트의 / 는 실수 나눗셈입니다. 두 언어 모두 floordiv 를 손으로 만들어 모든 나눗셈에 써야 합니다. Math.floor(a/b) 는 큰 값에서 정밀도를 잃습니다.

곱셈의 함정 — 2⁵³

정의는 floordiv(a·b, 65536) 입니다. 그런데 a·b 는 최대 2⁶² 입니다.

루아 5.1 의 숫자와 자바스크립트의 숫자는 배정밀도 실수이고, 가수는 53비트입니다. 2⁵³ 을 넘는 정수는 더 이상 정확하지 않습니다.

2^53     = 9007199254740992
2^53 + 1 = 9007199254740992   ← 배정밀도에서는 같은 수다

파이썬은 임의 정밀도라 아무 문제가 없습니다. 그래서 파이썬만 보고 만들면 이 함정이 보이지 않습니다. 세 언어를 동시에 맞추기로 한 이유 중 하나입니다.

정리 2.1 — 분할 곱

a 를 상·하위로 쪼개면 중간값이 2⁵³ 아래로 내려옵니다.

ah = floordiv(a, 65536)     −32768 ≤ ah < 32768
al = fmod(a, 65536)              0 ≤ al < 65536
fpmul(a, b) = ah·b + floordiv(al·b, 65536)

정리 2.1. 위 식은 floordiv(a·b, 65536) 과 항상 같다.

증명. a = ah·2¹⁶ + al 이므로 a·b = ah·b·2¹⁶ + al·b. 양변을 2¹⁶ 으로 나누고 바닥함수를 취하면 ⌊a·b/2¹⁶⌋ = ah·b + ⌊al·b/2¹⁶⌋ 입니다. 첫 항이 정수이므로 바닥함수 밖으로 나올 수 있습니다. ∎

크기. |ah·b| < 2¹⁵·2³¹ = 2⁴⁶, |al·b| < 2¹⁶·2³¹ = 2⁴⁷. 둘 다 2⁵³ 아래이므로 세 언어가 정확히 같은 값을 냅니다.

정수 제곱근 — 뉴턴

거리를 재려면 제곱근이 필요합니다. 그런데 sqrt 는 실수 함수입니다.

py/rts/fixed.py125–135초기값과 종료 조건까지 명세다
# ── SPEC §2.5 정수 제곱근 ───────────────────────────────────────────────────
def isqrt(n):
    """뉴턴 반복. 초기값과 종료 조건까지 명세다 — 세 언어가 같은 횟수를 돈다."""
    if n < 2:
        return n
    x = n
    y = (x + 1) // 2
    while y < x:
        x = y
        y = (x + n // x) // 2
    return x

정리 2.2. 위 반복은 ⌊√n⌋ 에서 멈춘다.

증명 스케치. x > ⌊√n⌋ 인 동안 f(x) = ⌊(x + ⌊n/x⌋)/2⌋ < x 이므로 수열은 순감소합니다. 정수 하한이 있으므로 유한 번에 멈춥니다. 멈추는 지점 x 는 ⌊n/x⌋ ≥ x, 즉 x² ≤ n 을 만족하고, 순감소성에서 직전 값이 > ⌊√n⌋ 였으므로 x = ⌊√n⌋ 입니다. ∎

초기값과 종료 조건을 명세에 박은 이유는 결과가 아니라 횟수 때문입니다. 결과는 어느 초기값에서든 같지만, 23부의 성능 표를 세 언어에서 비교하려면 같은 횟수를 돌아야 합니다.

거리 다섯 가지

제곱근 없이 거리를 재는 방법은 하나가 아닙니다. 다섯 가지를 모두 갖추고, 자리마다 다른 것을 씁니다.

d1(dx, dy)   = |dx| + |dy|                    L1 · 맨해튼 · 4방향 이동
dinf(dx, dy) = max(|dx|, |dy|)                L∞ · 체비셰프 · 8방향 이동
d83(dx, dy)  = mx + floordiv(3·mn, 8)         옥타일 8분의 3 근사
doct(dx, dy) = 10·mx + 4·mn                   경로 비용 단위 (직선 10 · 대각 14)
dab(dx, dy)  = floordiv(62943·mx + 26072·mn + 32768, 65536)   α-max β-min

여기서 mx = max(|dx|,|dy|), mn = min(|dx|,|dy|) 입니다.

    ax = dx if dx >= 0 else -dx

def d1(dx, dy):
    """L1 (맨해튼) — 4방향 이동의 정확한 걸음 수."""
    return (dx if dx >= 0 else -dx) + (dy if dy >= 0 else -dy)


def dinf(dx, dy):
    """L∞ (체비셰프) — 8방향 이동의 정확한 걸음 수. 사거리 판정은 전부 이것."""
    mx, _mn = _mxmn(dx, dy)
    return mx

체비셰프가 정확한 자리

dinf 는 근사가 아닙니다. 8방향으로 한 칸씩 움직이는 격자에서 (0,0) 에서 (dx,dy) 까지의 걸음 수가 정확히 max(|dx|,|dy|) 입니다.

대각 한 걸음이 x 와 y 를 동시에 1 씩 줄이므로, 짧은 쪽은 긴 쪽을 줄이는 김에 공짜로 줄어듭니다.

그래서 사거리 판정은 전부 dinf 입니다(§15.1). "사거리 4" 는 "네 걸음 안"과 같은 뜻이 되고, 플레이어가 화면에서 세는 것과 정확히 일치합니다.

반면 거리 비교에는 쓰기 어렵습니다. (4,4) 와 (4,0) 이 둘 다 4 니까요. 그래서 "가장 가까운 적"에는 다른 척도를 씁니다.

d83 — √2−1 을 3/8 로

45° 방향에서 참값 1.41421 대신 1.375 — −2.8 % 입니다. 항상 과소평가합니다.

원 마스크 — 고전 알고리즘이 틀리는 자리

시야 반경 4 의 유닛이 보는 칸은 어디까지입니까? "미드포인트 원 알고리즘"이 답일 것 같지만 아닙니다.

정리 6.2 — 덧셈만으로 행 span 구하기

필요한 것은 외곽선이 아니라 채워진 원판입니다. 행마다 "원 안에 드는 최대 |i|" 하나만 알면 됩니다.

span[j] = ⌊√(r² − j²)⌋

제곱근을 행마다 부르는 대신, x 가 결코 늘지 않는다는 성질을 씁니다.

py/rts/circle.py14–32곱셈도 제곱근도 없다
def spans(r):
    """span[j] = 행 j 에서 원 안에 드는 최대 |i|. 덧셈과 뺄셈만 쓴다.

       불변식은 t = r² − j² − x² >= 0 이고 x 가 그 조건을 만족하는 최대값이다.
       x 는 결코 늘지 않으므로 전체 비용이 O(r) 이다 (SPEC 정리 6.2).
    """
    if r in _span_cache:
        return _span_cache[r]
    out = [0] * (r + 1)
    out[0] = r
    x, t = r, 0
    for j in range(1, r + 1):
        t -= 2 * (j - 1) + 1
        while t < 0:
            t += 2 * x - 1
            x -= 1
        out[j] = x
    _span_cache[r] = out
    return out

정리 6.2. 매 j 마다 span[j] = ⌊√(r²−j²)⌋ 이다. 따라서 전체 비용은 O(r) 이다.

증명 스케치. 불변식은 t = r² − j² − x² ≥ 0 이고 x 가 그 조건을 만족하는 최대값이라는 것입니다. j 가 1 늘면 t 가 2j−1 만큼 줄고, x 를 1 줄이면 2x−1 만큼 늡니다. 내부 while 이 도는 총 횟수는 x 가 r 에서 0 까지 내려가는 횟수뿐이므로 전체 O(r) 입니다. ∎

    """걸음 수(가중치 없음). 대각도 한 걸음이다."""
    if not (m.passable_terrain(s[0], s[1], kind)
            and m.passable_terrain(t[0], t[1], kind)):
        return -1

    seen = [-1] * (w * m.h)

def dijkstra(m, kind, starts, goal=None):
    """모든 칸까지의 비용 배열. 간선 비용이 10 과 14 뿐이라 힙이 필요 없다.

       정리 8.3 이 보장한다 — 처리 중인 거리 cur 와 새 거리 nd 는 항상
       cur <= nd < cur + 15 이므로 원형 양동이 15개면 충돌하지 않는다.
    """
    w, h = m.w, m.h
    dist = [INF] * (w * h)
    buckets = [[] for _ in range(NB)]
    pending = 0
    for s in starts:
        if dist[s] > 0:
            dist[s] = 0
            buckets[0].append(s)
            pending += 1
    cur = 0
    while pending:
        b = buckets[cur % NB]
        while not b:
            cur += 1
            b = buckets[cur % NB]
        p = b.pop()
        pending -= 1
        if dist[p] != cur:                 # 낡은 항목 — 감소키를 구현하지 않는다

        for d, u, v in neighbours(m, x, y, kind):
            j = v * w + u
            nd = cur + F.DCOST[d]
            if nd < dist[j]:

                pending += 1
    return dist

        for d, u, v in neighbours(m, x, y, kind):

            if nd < dist.get(j, INF):
                dist[j] = nd
                prev[j] = p
                hn = h_oct(u, v, t[0], t[1])
                heap.push(nd + hn, hn, j)
    return -1, [], expanded

정리 8.1 — 허용성

정리 8.1. 어떤 경로든 비용이 h 이상이다.

증명. 직선 이동 s 회, 대각 이동 d 회로 이루어진 경로를 봅니다.

한 번의 이동이 max(|dx|,|dy|) 를 1 이상 줄이지 못한다   →  s + d  ≥ mx
한 번의 이동이 |dx| + |dy| 를 2 이상 줄이지 못한다      →  s + 2d ≥ mx + mn

두 부등식에 각각 6 과 4 를 곱해 더하면

6(s + d) + 4(s + 2d) = 10s + 14d ≥ 6·mx + 4·(mx + mn) = 10·mx + 4·mn = h

좌변이 정확히 경로 비용입니다. ∎

계수 6, 4 는 우연이 아닙니다. λ + μ ≤ 10, λ + 2μ ≤ 14 를 만족하면서 λ·mx + μ·(mx+mn) 을 최대로 하는 선형계획의 해가 (6, 4) 입니다. 즉 옥타일 휴리스틱은 이 형태에서 가능한 가장 강한 허용 휴리스틱입니다.

정리 8.2 — 일관성, 그리고 없어도 되는 코드

정리 8.2. h 는 일관적이다: 인접한 두 칸에 대해 h(n) ≤ c(n,n') + h(n').

증명. h 자체가 옥타일 거리이고 옥타일 거리는 삼각부등식을 만족합니다. 한 걸음의 비용은 그 걸음의 옥타일 거리와 같습니다(직선 10, 대각 14). 따라서 h(n) ≤ d_oct(n,n') + h(n') = c(n,n') + h(n'). ∎

일관적이면 A* 는 닫힌 노드를 다시 열 필요가 없습니다.

확인 문제 2

양동이를 15개가 아니라 14개로 두면 어떤 버그가 생기는가? 언제 드러나는가?

nd = cur + 14 일 때 nd mod 14 == cur mod 14 입니다. 지금 처리 중인 양동이에 새 항목이 들어갑니다.

파이썬 리스트로 구현하면 while not b: 루프가 그 항목을 지금 거리에서 꺼냅니다. 거리 cur + 14 인 칸이 cur 로 확정되고, 그 칸에서 뻗은 모든 거리가 14 씩 작아집니다.

                heap.push(nd + P.h_oct(n[0], n[1], t[0], t[1]), 0, len(nodes) - 1)
    return -1, []

JPS — 볼 필요 없는 이웃을 버린다

동쪽으로 들어온 유닛은 동쪽만 보면 됩니다. 서쪽 이웃으로 가는 경로는 이미 부모가 더 싸게 갈 수 있으니까요.

그 규칙이 깨지는 자리가 강제 이웃(forced neighbour)입니다. 막힌 칸이 있어서 부모가 돌아갈 수 없는 방향이 생기면, 그 대각 이웃만 살려 둡니다.

def _forced(m, x, y, dx, dy, kind):
    """(x,y) 에 방향 (dx,dy) 로 들어왔을 때 강제 이웃이 있는가 (SPEC §10.1)."""
    ok = m.passable_terrain
    if dx and dy:
        return ((not ok(x - dx, y, kind) and ok(x - dx, y + dy, kind)) or
                (not ok(x, y - dy, kind) and ok(x + dx, y - dy, kind)))
    if dx:
        for s in (-1, 1):
            if not ok(x, y + s, kind) and ok(x + dx, y + s, kind):
                return True
        return False
    for s in (-1, 1):
        if not ok(x + s, y, kind) and ok(x + s, y + dy, kind):
            return True
    return False

def jump(m, x, y, dx, dy, t, kind):
    """방향 (dx,dy) 로 계속 나아가다 점프점을 만나면 그 칸을 돌려준다.

       대각 점프가 먼저 두 성분 방향을 재귀로 훑는 것이 핵심이다. 그 방향에서
       점프점이 나오면 지금 서 있는 대각 칸 자체가 점프점이 된다.
    """
    u, v = x + dx, y + dy
    if not m.passable_terrain(u, v, kind):
        return None
    if (u, v) == t:
        return (u, v)
    if _forced(m, u, v, dx, dy, kind):
        return (u, v)
    if dx and dy:
        if (jump(m, u, v, dx, 0, t, kind) is not None or
                jump(m, u, v, 0, dy, t, kind) is not None):
            return (u, v)
    return jump(m, u, v, dx, dy, t, kind)

가지치기하고 남은 방향으로 한 방향으로 계속 달립니다. 강제 이웃이나 목표를 만나면 거기가 점프점이고, 그 점만 열린 목록에 넣습니다.

대각으로 달릴 때는 매 칸에서 두 직교 방향으로 먼저 점프해 봅니다. 그쪽에 점프점이 있으면 지금 칸도 점프점입니다 — 그 갈림길을 건너뛰면 최적해를 놓칩니다.

정리 10.1 — 증명 대신 전수 검사

정리 10.1. 코너 컷을 허용하는 균일 비용 8방향 격자에서 JPS 가 찾은 경로의 비용은 A* 의 최적 비용과 같다.

증명 방침. 가지치기된 이웃에 대해 항상 같은 비용의 대칭 경로가 존재합니다. 따라서 최적해 하나는 반드시 점프점만 거치는 형태로 다시 쓸 수 있습니다. 자세한 논증은 원 논문(Harabor–Grastien 2011)의 정리 1–3 에 있습니다.

이 저장소의 증명은 전수 검사입니다. 정리를 옮겨 적는 대신, 골든 맵 여섯 장에서 무작위 720쌍을 뽑아 A* 비용과 JPS 비용을 전부 비교합니다. 한 건이라도 다르면 시험이 실패합니다.

왜 그렇게 했을까요. 우리가 코너 컷을 허용하기로 했기 때문입니다(12부). 금지하는 격자였다면 강제 이웃 조건이 통째로 달라지고, 논문의 정리를 그대로 쓸 수 없습니다.

# ── SPEC §11.2 경사장 ───────────────────────────────────────────────────────
def flow_dirs(m, kind, integ):
    """각 칸에서 갈 방향. 후보가 없으면 255(정지).

       동점은 **방향 번호가 작은 쪽**이다. 언어별 min 구현에 맡기면 대칭 맵에서
       무리가 좌우로 갈리고, 그 갈림은 PPM 바이트 비교에서 바로 잡힌다.
    """
    w, h = m.w, m.h
    out = [STOP] * (w * h)
    for y in range(h):
        for x in range(w):
            i = y * w + x
            if integ[i] >= INF or not m.passable_terrain(x, y, kind):
                continue
            best, bd = INF, STOP
            for d in range(8):
                u, v = x + F.DX[d], y + F.DY[d]
                if not m.passable_terrain(u, v, kind):
                    continue
                c = integ[v * w + u]
                if c < best:               # 등호를 빼면 작은 d 가 이긴다
                    best, bd = c, d
            out[i] = bd
    return out

각 칸에서 가장 싼 이웃 쪽으로 화살표를 둡니다. 동점이면 방향 번호가 작은 쪽입니다.

동점 규칙이 명세인 이유가 여기서 특히 분명합니다. 대칭적인 맵에서는 동점이 흔하고, 언어별 min 구현이 동점을 다르게 처리하면 유닛 무리가 좌우로 갈립니다. 그 갈림은 화면에서 바로 보이고 PPM 바이트 비교에서 잡힙니다.

그림에서 목표 칸(비용 0)이 이웃을 가리키는 것에 주의하세요. 목표 자신은 "가장 싼 이웃"을 고르므로 오르막을 가리킵니다. 유닛은 이미 도착했으므로 그 화살표를 읽지 않습니다.

손익분기

A* 를 n 번        vs        다익스트라 1번 + 화살표 읽기 n 번

흐름장은 맵 전체를 채우므로 한 번의 비용이 A* 한 번보다 큽니다. 유닛이 적으면 손해입니다.

그런데 무리 이동에서는 다른 이득이 더 큽니다 — 모든 유닛이 같은 장을 읽으므로 서로 어긋나지 않습니다. A* 를 마흔 번 부르면 마흔 개의 경로가 조금씩 다르고, 그 차이가 14부의 예약 충돌을 늘립니다.

이 엔진의 무리 이동은 여전히 유닛별 A* 를 씁니다. 흐름장은 모듈로 갖추고 골든으로 검증하되, 시나리오에서는 쓰지 않습니다 — 40기가 한 곳으로 몰리는 상황이 이 시나리오에 없기 때문입니다. 쓰지 않는 것을 쓴다고 적지 않습니다.

클리어런스 — 큰 유닛은 어디를 지나는가

정리 11.1. clear[x][y] 는 (x,y) 를 좌상단으로 하는 모두 통행 가능한 정사각형의 최대 변 길이와 같다.

증명. 귀납. k × k 정사각형이 (x,y) 에 놓이려면 (x+1,y), (x,y+1), (x+1,y+1) 각각에 (k−1) × (k−1) 이 놓여야 하고, 역도 성립합니다. ∎

# ── SPEC §11.3 클리어런스 ───────────────────────────────────────────────────
def clearance(m, kind):
    """clear[i] = (x,y) 를 좌상단으로 하는 통행 가능 정사각형의 최대 변 (정리 11.1).

       O(칸수) 시간, O(칸수) 공간 — 오른쪽 아래에서 한 번만 훑는다.
       맵 밖은 0 이므로 오른쪽·아래 가장자리의 자유 칸은 1 이 된다.
    """
    w, h = m.w, m.h
    c = [0] * (w * h)
    for y in range(h - 1, -1, -1):
        for x in range(w - 1, -1, -1):
            if not m.passable_terrain(x, y, kind):
                continue
            if x + 1 >= w or y + 1 >= h:
                c[y * w + x] = 1
            else:
                r = c[y * w + x + 1]
                d = c[(y + 1) * w + x]
                q = c[(y + 1) * w + x + 1]
                c[y * w + x] = 1 + min(r, d, q)
    return c

크기 s 인 유닛은 clear[i] ≥ s 인 칸만 지납니다. 맵 한 번 훑기로 2×2 유닛의 통행 그래프가 나옵니다.

# ── SPEC §13.5 회전과 대형 ──────────────────────────────────────────────────
def rot8(d, ox, oy):
    """이동 방향 d 로 오프셋을 돌린다. 행렬이 아니라 8방향 표다.

       45° 회전은 정수 격자를 보존하지 않으므로 대각은 이웃한 두 직교 방향의
       결과를 더해 2로 내림 나눗셈한다 — 근사이며, 그렇다고 적어 둔다.
    """
    if d == 0:
        return ox, oy
    if d == 2:
        return -oy, ox
    if d == 4:
        return -ox, -oy
    if d == 6:
        return oy, -ox
    ax, ay = rot8(d - 1, ox, oy)
    bx, by = rot8((d + 1) % 8, ox, oy)
    return F.floordiv(ax + bx, 2), F.floordiv(ay + by, 2)

회전은 행렬이 아니라 8방향 표입니다. 직교 넷은 정확하고, 대각 넷은 이웃한 두 직교 방향의 결과를 더해 2로 내림 나눗셈합니다.

대각 회전이 근사인 이유는 45° 회전이 정수 격자를 보존하지 않기 때문입니다. 정확한 회전은 소수 좌표를 낳고, 그것을 반올림하면 두 슬롯이 같은 칸에 겹칩니다. 근사가 겹침보다 낫습니다.

def formation(n, shape, d, gx, gy, m, kind):
    """목표 주위 n 개의 슬롯 타일. 슬롯 순서 = 핸들 오름차순으로 나눠 준다.

       맵 밖이거나 통행 불가인 슬롯은 목표 타일 자체로 접는다. 슬롯을 다시
       찾아 주지는 않는다 — 반쯤 성공하는 재배치가 교착보다 나쁜 그림을 만든다.
    """
    out = []
    if n <= 0:
        return out
    side = F.isqrt(n - 1) + 1                  # ceil(sqrt(n)) — §2.5 정수 제곱근
    for k in range(n):
        if shape == LINE:
            ox, oy = k - F.floordiv(n - 1, 2), 0
        elif shape == COLUMN:
            ox, oy = 0, k
        else:
            ox = F.fmod(k, side) - F.floordiv(side - 1, 2)
            oy = F.floordiv(k, side)
        rx, ry = rot8(d, ox, oy)
        x, y = gx + rx, gy + ry
        if not m.passable_terrain(x, y, kind):
            x, y = gx, gy
        out.append((x, y))
    return out

확인 문제 1

걸음을 시작할 때 도착 칸을 예약하지 않고, 도착한 뒤에 예약한다면 어떤 장면이 나오는가?

마주 오는 두 유닛이 서로의 칸으로 동시에 들어갑니다. A 는 b 로, B 는 a 로. 둘 다 도착 시점에 예약을 시도하고, 둘 다 성공합니다 — 상대가 그 칸을 이미 떠났으니까요.

화면에서는 두 유닛이 서로를 통과합니다. 겹치지도 않고 부딪히지도 않고 그냥 지나갑니다. 그리고 그 뒤로는 "왜 벽이 유닛을 못 막지?" 를 묻게 됩니다.

먼저 쥐는 규칙은 이 장면을 원천적으로 막습니다. A 가 b 를 쥐는 순간 B 는 b 로 들어갈 수 없고, B 는 막힘 카운터를 올리다가 밀어내기나 재탐색으로 넘어갑니다.

확인 문제 2

교착을 24틱이 아니라 200틱에 포기하게 하면 게임이 어떻게 달라지는가? 더 참을성 있는 유닛이 더 좋은 유닛 아닌가?

두 유닛이 통로에서 11초 동안 마주 본 채 서 있습니다. 플레이어는 그 사이 명령을 다시 내리고, 그 명령도 같은 자리에서 막힙니다.

더 나쁜 것은 포기가 곧 재계획이라는 점입니다. 포기해야 상위 로직(AI 나 채집기 FSM)이 다른 목표를 잡습니다. 24틱이 길면 채집기가 200틱 동안 아무것도 캐지 않습니다 — 17부의 수입률이 그만큼 떨어집니다.

왜 참조 카운트인가

유닛 하나가 반경 4 를 봅니다. 두 유닛의 시야가 겹치면 어떻게 됩니까?

유닛 A 가 칸 X 를 본다   →  X 는 가시
유닛 B 도 칸 X 를 본다   →  X 는 여전히 가시
유닛 A 가 떠난다         →  X 는 ?

0/1 로만 두면 A 가 떠날 때 X 를 꺼야 할지 알 수 없습니다. B 가 아직 보고 있으니까요. 매번 전체를 다시 계산하면 4,096칸 × 유닛 수 입니다.

답은 세는 것입니다. 몇 명이 보고 있는지 숫자로 들고, 들어오면 +1, 나가면 −1 합니다.

이 문제는 참조 카운팅 가비지 컬렉션과 정확히 같은 모양입니다. 그리고 같은 약점을 공유합니다 — 한 번 어긋나면 영원히 어긋납니다.

세 평면

explored[p][i]   0/1     한 번이라도 봤는가
count[p][i]      0..255  지금 이 칸을 보고 있는 유닛 수
visible(p, i)    count[p][i] > 0

플레이어마다 한 벌씩입니다. 4인이면 여덟 배열, 각 4,096바이트 — 32 KB 입니다. 640 KB 짜리 기계에서 5 % 입니다.

왜 칸당 1바이트인가

비트 플레인이면 8배 작습니다. 도스 시절이라면 당연히 비트를 썼을 텐데요.

  • 참조 카운트는 비트로 담을 수 없습니다. 겹쳐 보는 유닛이 최대 몇인지 미리 알 수 없으니까요. count 가 바이트여야 한다면, explored 만 비트로 접어 봐야 4,096바이트를 아끼는 것이 전부입니다.
  • 루아 5.1 과 타입스크립트에서 비트 연산을 산술로 흉내내면(§1.1) 칸 하나 읽는 데 나눗셈과 나머지가 붙습니다. 안개는 매 틱 수천 칸을 읽습니다.
비트 플레인 자체는 다룹니다. fog.pack_bits() 가 저장·전송용으로 8칸을 1바이트로 접습니다. 시뮬레이션 중에 쓰지 않을 뿐입니다.

    def recount(self, world):
        """불변식 F 를 전수로 검증하고 **어긋난 칸 수만** 돌려준다.

           고치지 않는 이유는 하나다. 증분 갱신이 새면 그것은 버그이고,
           조용히 고쳐 버리면 그 버그는 영원히 드러나지 않는다.
           O(플레이어 × 칸수 + 엔티티 × r²) 이라 매 틱 돌릴 수는 없다 —
           세이브 직후와 100틱마다 돌린다.
        """
        want = [[0] * (self.w * self.h) for _ in range(len(self.count))]
        for i in range(1, C.MAX_ENT):
            if world.alive[i] == 0:
                continue
            r = C.SIGHT[world.kind[i]]
            p = world.owner[i]
            if p >= len(want):
                continue
            for dx, dy in CI.offsets(r):        # 건물의 시야 중심은 좌상단이다
                x, y = world.tx[i] + dx, world.ty[i] + dy
                if 0 <= x < self.w and 0 <= y < self.h:
                    want[p][y * self.w + x] += 1
        bad = 0
        for p in range(len(self.count)):
            for i in range(self.w * self.h):
                if self.count[p][i] != want[p][i]:
                    bad += 1
        return bad

증분 갱신은 빠르지만 한 번 어긋나면 영원히 어긋납니다. 그리고 그 증상은 "보이지 않는 적"이나 "영원히 밝은 칸" 으로 나타납니다 — 둘 다 게임을 망가뜨리지만 크래시는 아닙니다.

recount 가 고치지 않는 것이 설계입니다. 조용히 고치면 그 버그는 영원히 드러나지 않습니다. 세이브 직후와 100틱마다 돌려 어긋난 칸 수를 보고합니다. 시험에서는 매 틱 돌립니다.

    # ── SPEC §14.4 4단계 렌더 ──────────────────────────────────────────────
    def level(self, p, x, y):
        """0 미탐험 · 1 탐험 · 2 경계 · 3 가시.

           2단계는 순전히 눈을 위한 것이다. 1과 3만 있으면 안개 경계가
           계단처럼 보인다. 명암 단계는 팔레트 명암표(§22.2)의 행 번호다.
        """
        if not (0 <= x < self.w and 0 <= y < self.h):
            return 0
        i = y * self.w + x
        if self.count[p][i] > 0:
            return 3
        if self.explored[p][i] == 0:
            return 0
        for dy in (-1, 0, 1):
            for dx in (-1, 0, 1):
                u, v = x + dx, y + dy
                if (0 <= u < self.w and 0 <= v < self.h
                        and self.count[p][v * self.w + u] > 0):
                    return 2
        return 1

명세가 틀렸던 자리

초안은 "안개 속 유닛은 5단계(안개 오버레이)에서 숨긴다"고 적고 있었습니다. 구현해 보니 불가능했습니다.

명암표는 색을 어둡게 만들 뿐입니다. 탐험된 칸(1·2단계)의 유닛은 어둡게 비쳐 보입니다. 숨기려면 그리지 말아야 합니다.

2단계 (스프라이트)  →  visible 인 칸의 유닛만 그린다   ← 여기서 숨긴다
5단계 (안개)        →  지형을 어둡게 한다              ← 여기서는 못 한다
이런 오류는 명세만 읽어서는 보이지 않습니다. 그려 봐야 보입니다. 그래서 이 저장소는 매 단계 PPM 을 뽑아 눈으로 확인합니다 — 23부에서 그 프레임들을 봅니다.

기술 트리는 DAG 다

노드는 유닛·건물, 간선은 "X 를 만들려면 Y 가 있어야 한다"입니다. 이 그래프가 비순환이어야 하고, 그것은 위상 정렬이 존재하는 것과 동치입니다.

선행이 둘인 노드는 공장 하나뿐입니다(병영 + 발전소). 위상 정렬이 실제로 필요한 유일한 자리이고, 그래서 일부러 넣었습니다.

칸 알고리즘

py/rts/econ.py45–73진입차수 0 을 번호 오름차순으로 꺼낸다
# ── SPEC §16.6 기술 트리 = DAG (정리 16.2) ──────────────────────────────────
def topo_order(extra=None):
    """칸(Kahn) 위상 정렬. 진입차수 0 은 **번호 오름차순**으로 꺼낸다.

       순환이 있으면 None 을 돌려준다 — 조용히 넘어가지 않는다. 기술 트리는
       데이터이고, 데이터가 잘못되면 터지는 편이 낫다.
    """
    pre = [list(C.PREREQ[k]) for k in range(C.KIND_COUNT)]
    for (k, p) in (extra or []):
        pre[k] = pre[k] + [p]
    indeg = [len(pre[k]) for k in range(C.KIND_COUNT)]
    out = []
    done = [0] * C.KIND_COUNT
    while True:
        pick = -1
        for k in range(C.KIND_COUNT):          # 오름차순 선형 탐색 — 16개다
            if done[k] == 0 and indeg[k] == 0:
                pick = k
                break
        if pick < 0:
            break
        done[pick] = 1
        out.append(pick)
        for k in range(C.KIND_COUNT):
            if done[k] == 0 and pick in pre[k]:
                indeg[k] -= 1
    if len(out) != C.KIND_COUNT:
        return None                            # 남은 노드가 있으면 순환이다
    return out

진입차수 0 인 노드를 번호 오름차순으로 꺼냅니다. 순서를 고정하지 않으면 세 언어가 다른 순서를 내고, 그것이 화면에 나오는 순간 갈립니다.

순환이 있으면 남은 노드가 생기고, 그때는 즉시 실패합니다.

기술 트리는 데이터입니다. 데이터가 잘못되면 조용히 넘어가는 것보다 터지는 편이 낫습니다. 조용히 넘어가면 "왜 전차가 안 나오지?" 를 게임 중에 알게 됩니다.

선행은 "살아 있는가"를 본다

py/rts/econ.py175–186완성된 채 살아 있어야 한다
    def can_build(self, w, p, kind):
        """선행이 **완성된 채 살아 있는지** 본다. 병영이 부서지면 보병을 못 뽑는다."""
        for need in C.PREREQ[kind]:
            found = False
            for j in range(1, C.MAX_ENT):
                if (w.alive[j] == 1 and w.owner[j] == p
                        and w.kind[j] == need and w.hp[j] > 0):
                    found = True
                    break
            if not found:
                return False
        return True

병영이 부서지면 보병을 못 뽑습니다. 짓는 중인 병영으로도 못 뽑습니다 — hp > 0 만으로는 부족하고 완성 여부를 봐야 합니다.

이 규칙이 기지 공격의 값어치를 만듭니다. 병영 하나를 부수면 상대의 보병 생산이 멈춥니다. 유닛을 죽이는 것과 다른 종류의 이득입니다.

    def placeable(self, w, m, mv, kind, x, y, p):

    def _shove(self, p, kind, x, y):
        """발자국을 막은 내 유닛들에게 바깥으로 한 걸음 명령을 준다 (§16.5).

           밀면서 동시에 짓지는 않는다 — 아직 그 칸에 선 유닛 위에 건물을
           얹으면 불변식 R 이 깨진다. 다음 재시도에서 자리가 빈다.
        """
        w, m = self.w, self.m
        f = C.FOOT[kind]
        cx, cy = x + f // 2, y + f // 2
        for dy in range(f):
            for dx in range(f):
                u, v = x + dx, y + dy
                if not m.in_map(u, v):
                    continue
                h = self.mv.resv[v * m.w + u]
                if not w.valid(h):
                    continue
                j = S.index(h)
                if w.owner[j] != p or C.IS_BUILDING[w.kind[j]]:
                    continue
                out = F.atan8(w.tx[j] - cx, w.ty[j] - cy)
                pd = M.push_dir(self.mv, j, F.fmod(out + 4, 8))
                if pd != M.STOP_DIR:
                    t = ((w.ty[j] + F.DY[pd]) * m.w + w.tx[j] + F.DX[pd])
                    self.mv.path[j] = [t]
                    self.mv.goal[j] = t

밀면서 동시에 짓지 않는 이유는 불변식 R 입니다(14부). 아직 그 칸에 서 있는 유닛 위에 건물을 얹으면 한 칸을 둘이 쥐게 됩니다.

빈 턴 패킷은 몇 바이트입니다. 18.2 Hz × 2명 × 8바이트 = 초당 291바이트 — 28.8 kbps 의 8 % 입니다.

난수는 하나뿐이다

시뮬레이션의 RNG 는 정확히 하나입니다. 렌더나 UI 가 그것을 한 번이라도 뽑으면 두 기계의 수열이 갈립니다.

그런데 네트워크 지터에도 난수가 필요합니다. 그래서 Net 은 전용 RNG 를 따로 듭니다.

sim.rng    시뮬레이션용 — 피해량·맵 생성
net.rng    지터용 — 시뮬레이션 상태에 영향을 주지 않는다
둘을 합치면 네트워크 사정이 게임 내용을 바꿉니다. 지연이 큰 날에 전차가 더 아프게 때립니다. 그것이야말로 디싱크의 정의입니다.

상태 해시 — FNV-1a

두 기계가 같은 상태인지 어떻게 압니까? 상태 전체를 보내면 애초에 명령만 보낼 이유가 없습니다.

해시 하나(4바이트)를 매 틱 주고받습니다.

py/rts/fixed.py227–233XOR 도 곱셈도 비트 연산자 없이
def fnv1a_step(h, b):
    """바이트 하나. XOR 은 하위 8비트만 바뀌므로 xor8 로 끝나고,
       곱셈은 분할한다 — hl * 16777619 < 2^40 이라 53비트 가수에 담긴다."""
    h = xor_low8(h, b)
    hh = h // 65536
    hl = h % 65536
    return (hl * FNV_PRIME + (hh * FNV_PRIME % 65536) * 65536) % 4294967296

XOR 은 하위 8비트만 바뀌므로 xor8 로 끝나고, 곱셈은 6부의 분할 곱과 같은 이유로 쪼갭니다. hl · 16777619 < 2⁴⁰ 이라 53비트 가수에 담깁니다.

무엇을 해시에 넣는가

순서가 명세입니다. 한 필드라도 순서가 다르면 두 언어의 해시가 다르고, 그러면 락스텝 검증이 아무것도 증명하지 못합니다.

cool(재장전)과 timer(반납·건설 카운트다운)를 빠뜨리면 안 됩니다. 둘은 매 틱 바뀌는 상태이고, 빠져 있으면 두 기계의 재장전이 한 틱 어긋나도 해시가 같습니다. 그러면 디싱크가 첫 발이 어긋난 다음 틱에야 잡힙니다.

명세 초안에는 이 둘이 없었습니다. 골든 해시를 만들기 직전에 넣었습니다 — 한 번 얼리고 나면 고치는 값이 비싸집니다.

디싱크를 일부러 만들어 본다

"부동소수점을 쓰면 디싱크한다"는 말은 자주 인용됩니다. 그런데 정말 그런지 확인해야 합니다.

명세 초안은 이렇게 적고 있었습니다.

fpmul(a, b)  →  floor(a · b / 65536.0)      실수로 계산한다
|a·b| 가 2^53 을 넘는 순간 하위 비트가 잘리고 ...

그래서 그대로 구현하고 두 시뮬을 붙여 보았습니다. 1,200틱 내내 한 비트도 어긋나지 않았습니다.

왜 어긋나지 않았는가

양크기
16.16 값의 실제 범위|x| ≤ 2²² (fp(64) = 4,194,304)
두 값의 곱≤ 2⁴⁴
배정밀도 가수53비트
65536 으로 나누기2 의 거듭제곱 — 오차 없음

곱이 2⁵³ 아래에 있으면 실수 곱셈은 정확합니다. 나누는 수가 2의 거듭제곱이면 나눗셈도 정확합니다. 바닥함수도 정확합니다.

시험이 24쌍에 대해 fp_mul(a,b) == int(a·b/65536.0) 을 확인합니다. 전부 같습니다.

검증하지 않고 적었으면 거짓말이 될 뻔했습니다. 명세를 고치고, 그 정정을 이 덱에 그대로 싣습니다.

실제로 어긋나는 것 — 누적

곱셈 한 번은 정확합니다. 그런데 끝나지 않는 소수를 계속 더하면 이야기가 다릅니다.

    """방향 d 로 한 틱에 늘어나는 진행률 (16.16).

       대각 보정을 빼면 유닛이 대각으로 √2 = 41 % 빨라진다. 도스 시절에도

그 차이가 px·py 를 통해 상태 해시에 즉시 나타납니다.

이 실험이 증명하지 않는 것

일부러 넣은 버그입니다. 덱에 그렇게 적습니다.

말할 수 있는 것은 "이 조건에서 이렇게 어긋났다" 뿐입니다. 말할 수 없는 것은 이렇습니다.

  • "부동소수점을 쓰면 반드시 디싱크한다" — 아닙니다. 위에서 곱셈 하나는 세 언어가 비트 단위로 같은 답을 냈습니다.
  • "IEEE 754 면 안전하다" — 아닙니다. 같은 규격이라도 컴파일러가 곱셈 순서를 바꾸거나 확장 정밀도를 쓰면 갈립니다.
  • "정수만 쓰면 안전하다" — 아닙니다. 정렬 순서 하나만 달라도 갈립니다. 12부의 손으로 쓴 힙이 그 이야기입니다.

정확히 말하면 이렇습니다 — 결정론은 산술의 성질이 아니라 명세의 성질입니다. 실수를 쓰면 명세할 것이 늘어날 뿐입니다.

지터가 커서 상대의 턴 패킷이 실행 틱보다 늦게 도착했다. 내 시뮬은 무엇을 하는가? 그리고 화면은 무엇을 하는가?
