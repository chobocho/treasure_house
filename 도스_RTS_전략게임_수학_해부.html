왜 소수를 정수로 다루는가

1992년의 386SX 에는 부동소수점 장치가 없었습니다. 387 코프로세서는 별매였고, 게이머의 기계에 그것이 꽂혀 있으리라고 가정할 수 없었습니다.

그런데 유닛은 한 틱에 1.5픽셀씩 움직여야 합니다. 정수만으로는 1 아니면 2 뿐이고, 1 로 두면 느리고 2 로 두면 빠릅니다. 소수가 필요합니다.

답은 단위를 바꾸는 것이었습니다. 1픽셀을 65,536 으로 세면 1.5픽셀은 98,304 이라는 정수가 됩니다.

이 덱이 30년 뒤에도 같은 선택을 하는 이유는 FPU 가 없어서가 아닙니다. 세 언어가 같은 답을 내야 하기 때문입니다. 19부에서 보겠지만, 실수 한 줄이 락스텝을 무너뜨립니다.

16.16 — 정의

32비트 정수 하나를 상위 16비트(정수부)와 하위 16비트(소수부)로 나눠 읽습니다.

실수 v  ↔  정수 x = v · 65536
1.0   = 65536      0.5  = 32768      1.5  = 98304
1/√2  = 46341      √2−1 = 27146     −1.0  = −65536
연산16.16 구현왜
정수 → 고정x = n · 65536곱셈 하나
고정 → 정수floordiv(x, 65536)내림이지 자름이 아니다
더하기·빼기그냥 + −단위가 같으므로
곱하기floordiv(a·b, 65536)단위가 두 번 곱해졌으므로 한 번 나눈다
나누기floordiv(a·65536, b)먼저 올려놓고 나눈다

덧셈과 뺄셈은 손댈 것이 없습니다. 값의 범위를 |x| < 2³¹ 로 제한해 두면 |a| + |b| < 2³² 이라 세 언어 모두 정확합니다.

왜 자름이 아니라 내림인가

−1.5 를 정수로 바꾸면 −1 입니까, −2 입니까?

C 의 / 는 0 쪽으로 자릅니다(−1). 파이썬의 // 는 −∞ 쪽으로 내립니다(−2). 둘 다 맞지만 하나만 골라야 합니다.

py/rts/fixed.py33–36명세는 내림이다
# ── SPEC §1 정수 연산 규약 ──────────────────────────────────────────────────
def floordiv(a, b):
    """b > 0 일 때 -무한대 방향 내림. 파이썬의 // 가 이미 그렇다."""
    return a // b

내림을 고른 이유는 타일 좌표 때문입니다. 월드 픽셀 −1 은 타일 −1 에 속해야 합니다. 자름을 쓰면 −15…−1 이 전부 타일 0 이 되어 맵 왼쪽 가장자리에서 한 칸이 두 배로 넓어집니다.

루아 5.1 에는 정수 나눗셈이 없고, 자바스크립트의 / 는 실수 나눗셈입니다. 두 언어 모두 floordiv 를 손으로 만들어 모든 나눗셈에 써야 합니다. Math.floor(a/b) 는 큰 값에서 정밀도를 잃습니다.

곱셈의 함정 — 2⁵³

정의는 floordiv(a·b, 65536) 입니다. 그런데 a·b 는 최대 2⁶² 입니다.

루아 5.1 의 숫자와 자바스크립트의 숫자는 배정밀도 실수이고, 가수는 53비트입니다. 2⁵³ 을 넘는 정수는 더 이상 정확하지 않습니다.

2^53     = 9007199254740992
2^53 + 1 = 9007199254740992   ← 배정밀도에서는 같은 수다

파이썬은 임의 정밀도라 아무 문제가 없습니다. 그래서 파이썬만 보고 만들면 이 함정이 보이지 않습니다. 세 언어를 동시에 맞추기로 한 이유 중 하나입니다.

정리 2.1 — 분할 곱

a 를 상·하위로 쪼개면 중간값이 2⁵³ 아래로 내려옵니다.

ah = floordiv(a, 65536)     −32768 ≤ ah < 32768
al = fmod(a, 65536)              0 ≤ al < 65536
fpmul(a, b) = ah·b + floordiv(al·b, 65536)

정리 2.1. 위 식은 floordiv(a·b, 65536) 과 항상 같다.

증명. a = ah·2¹⁶ + al 이므로 a·b = ah·b·2¹⁶ + al·b. 양변을 2¹⁶ 으로 나누고 바닥함수를 취하면 ⌊a·b/2¹⁶⌋ = ah·b + ⌊al·b/2¹⁶⌋ 입니다. 첫 항이 정수이므로 바닥함수 밖으로 나올 수 있습니다. ∎

크기. |ah·b| < 2¹⁵·2³¹ = 2⁴⁶, |al·b| < 2¹⁶·2³¹ = 2⁴⁷. 둘 다 2⁵³ 아래이므로 세 언어가 정확히 같은 값을 냅니다.

py/rts/fixed.py106–115쪼개는 쪽은 a 다
# ── SPEC §2.3 곱셈 (분할 곱) ────────────────────────────────────────────────
def fp_mul(a, b):
    """floor(a*b / 65536). a 를 상·하위로 쪼개 중간값을 2^53 아래로 붙든다.

       a = ah·2^16 + al 이므로 a·b/2^16 = ah·b + al·b/2^16 이고,
       첫 항이 정수라 바닥함수 밖으로 나온다 (SPEC 정리 2.1).
    """
    ah = a // FP_ONE
    al = a % FP_ONE
    return ah * b + (al * b) // FP_ONE

나눗셈은 쪼갤 필요가 없다

py/rts/fixed.py118–122b == 0 은 호출자의 버그다
def fp_div(a, b):
    """floor(a*65536 / b). b == 0 은 호출자의 버그이므로 그냥 터진다."""
    if b == 0:
        raise ZeroDivisionError('fp_div: b == 0')
    return (a * FP_ONE) // b

|a| < 2³¹ 이므로 |a·65536| < 2⁴⁷ — 이미 안전합니다.

b == 0 에서 조용히 0 을 돌려주지 않습니다. 세 언어 모두 즉시 실패합니다. 0 을 돌려주면 유닛 하나가 이상한 자리로 순간이동하고, 그 원인을 1,200틱 뒤에 찾게 됩니다.

정수 제곱근 — 뉴턴

거리를 재려면 제곱근이 필요합니다. 그런데 sqrt 는 실수 함수입니다.

py/rts/fixed.py125–135초기값과 종료 조건까지 명세다
# ── SPEC §2.5 정수 제곱근 ───────────────────────────────────────────────────
def isqrt(n):
    """뉴턴 반복. 초기값과 종료 조건까지 명세다 — 세 언어가 같은 횟수를 돈다."""
    if n < 2:
        return n
    x = n
    y = (x + 1) // 2
    while y < x:
        x = y
        y = (x + n // x) // 2
    return x

정리 2.2. 위 반복은 ⌊√n⌋ 에서 멈춘다.

증명 스케치. x > ⌊√n⌋ 인 동안 f(x) = ⌊(x + ⌊n/x⌋)/2⌋ < x 이므로 수열은 순감소합니다. 정수 하한이 있으므로 유한 번에 멈춥니다. 멈추는 지점 x 는 ⌊n/x⌋ ≥ x, 즉 x² ≤ n 을 만족하고, 순감소성에서 직전 값이 > ⌊√n⌋ 였으므로 x = ⌊√n⌋ 입니다. ∎

초기값과 종료 조건을 명세에 박은 이유는 결과가 아니라 횟수 때문입니다. 결과는 어느 초기값에서든 같지만, 23부의 성능 표를 세 언어에서 비교하려면 같은 횟수를 돌아야 합니다.

거리 다섯 가지

제곱근 없이 거리를 재는 방법은 하나가 아닙니다. 다섯 가지를 모두 갖추고, 자리마다 다른 것을 씁니다.

d1(dx, dy)   = |dx| + |dy|                    L1 · 맨해튼 · 4방향 이동
dinf(dx, dy) = max(|dx|, |dy|)                L∞ · 체비셰프 · 8방향 이동
d83(dx, dy)  = mx + floordiv(3·mn, 8)         옥타일 8분의 3 근사
doct(dx, dy) = 10·mx + 4·mn                   경로 비용 단위 (직선 10 · 대각 14)
dab(dx, dy)  = floordiv(62943·mx + 26072·mn + 32768, 65536)   α-max β-min

여기서 mx = max(|dx|,|dy|), mn = min(|dx|,|dy|) 입니다.

py/rts/fixed.py143–158두 값을 한 번만 구해 돌려 쓴다
# ── SPEC §2.6 거리 척도 ─────────────────────────────────────────────────────
def _mxmn(dx, dy):
    ax = dx if dx >= 0 else -dx
    ay = dy if dy >= 0 else -dy
    return (ax, ay) if ax >= ay else (ay, ax)


def d1(dx, dy):
    """L1 (맨해튼) — 4방향 이동의 정확한 걸음 수."""
    return (dx if dx >= 0 else -dx) + (dy if dy >= 0 else -dy)


def dinf(dx, dy):
    """L∞ (체비셰프) — 8방향 이동의 정확한 걸음 수. 사거리 판정은 전부 이것."""
    mx, _mn = _mxmn(dx, dy)
    return mx

체비셰프가 정확한 자리

dinf 는 근사가 아닙니다. 8방향으로 한 칸씩 움직이는 격자에서 (0,0) 에서 (dx,dy) 까지의 걸음 수가 정확히 max(|dx|,|dy|) 입니다.

대각 한 걸음이 x 와 y 를 동시에 1 씩 줄이므로, 짧은 쪽은 긴 쪽을 줄이는 김에 공짜로 줄어듭니다.

그래서 사거리 판정은 전부 dinf 입니다(§15.1). "사거리 4" 는 "네 걸음 안"과 같은 뜻이 되고, 플레이어가 화면에서 세는 것과 정확히 일치합니다.

반면 거리 비교에는 쓰기 어렵습니다. (4,4) 와 (4,0) 이 둘 다 4 니까요. 그래서 "가장 가까운 적"에는 다른 척도를 씁니다.

d83 — √2−1 을 3/8 로

옥타일 거리의 참값은 mx + (√2−1)·mn 이고 √2−1 = 0.41421356… 입니다. 이것을 3/8 = 0.375 로 바꾼 것이 d83 입니다.

√2−1 의 연분수는 [0;2,2,2,…] 이고 수렴분수는 1/2, 2/5, 5/12, 12/29, 29/70 … (펠 수의 비)입니다. 3/8 은 그 중 어느 것도 아닙니다. 5/12 가 훨씬 정확한데도 3/8 을 쓴 이유는 하나입니다 — 8 로 나누는 것이 시프트 세 번이기 때문입니다.

3·mn / 8   →  (mn + mn + mn) >> 3     곱셈도 나눗셈도 없다
5·mn / 12  →  12 로 나누려면 나눗셈이 필요하다

45° 방향에서 참값 1.41421 대신 1.375 — −2.8 % 입니다. 항상 과소평가합니다.

α-max β-min — 오차를 0 중심으로

d83 이 늘 짧게 나오는 것이 싫다면 계수 둘을 모두 조정하면 됩니다.

d ≈ α·mx + β·mn      α = 0.96043387, β = 0.39782473
16.16 으로 반올림하면  62943, 26072

최대 상대오차 ±3.96 %. d83(−0 %…−8.6 %)과 달리 오차가 0 을 중심으로 흩어집니다.

마지막에 32768 을 더하는 것(반올림)이 없으면 안 됩니다. 내림으로 두면 dab(1,0) = ⌊62943/65536⌋ = 0 입니다. 거리 1 이 0 으로 나오고 사거리 판정과 타깃 선택이 통째로 무너집니다. 이 버그는 골든 벡터를 처음 만들 때 오차 −100 % 로 드러났습니다.
py/rts/fixed.py173–180반올림 항 32768 이 핵심이다
def dab(dx, dy):
    """alpha-max-beta-min. 마지막 반올림(+32768)이 없으면 dab(1,0) = 0 이 된다.

       거리 1 이 0 으로 나오면 사거리 판정과 타깃 선택이 통째로 무너진다.
       골든 벡터를 처음 만들 때 오차 −100 % 로 드러난 자리다(SPEC §2.6).
    """
    mx, mn = _mxmn(dx, dy)
    return (62943 * mx + 26072 * mn + FP_HALF) // FP_ONE

def atan8(dx, dy):
    """비교만으로 8방향을 고른다. 나눗셈도 삼각함수도 없다.

       경계는 22.5°이고 tan 22.5° = √2−1 = 0.414214 다. 5/12 = 0.416667 로
       바꾸면 경계각이 22.62° — 0.12° 넓어질 뿐이다. √2−1 의 연분수 수렴분수가
       1/2, 2/5, 5/12, 12/29 … (펠 수의 비)이므로 5/12 는 우연이 아니다.
    """
    if dx == 0 and dy == 0:
        return 2                                   # 규약: 정지 상태는 E 를 본다
    ax = dx if dx >= 0 else -dx
    ay = dy if dy >= 0 else -dy
    mx, mn = (ax, ay) if ax >= ay else (ay, ax)
    diag = 12 * mn > 5 * mx
    if ax >= ay:                                   # 동서가 주축
        if dx > 0:
            if diag:
                return 1 if dy < 0 else 3
            return 2
        if diag:
            return 7 if dy < 0 else 5
        return 6
    if dy < 0:                                     # 남북이 주축
        if diag:
            return 1 if dx > 0 else 7
        return 0
    if diag:
        return 3 if dx > 0 else 5
    return 4
여기서는 3/8 이 아니라 5/12 를 씁니다. 나눗셈이 없기 때문입니다 — 부등식의 양변에 12 를 곱해 버리면 분모가 사라집니다. 같은 상수를 근사하는데 자리마다 다른 분수를 쓰는 것이 이상해 보이지만, 각 자리의 연산 비용이 다릅니다.

원 마스크 — 고전 알고리즘이 틀리는 자리

시야 반경 4 의 유닛이 보는 칸은 어디까지입니까? "미드포인트 원 알고리즘"이 답일 것 같지만 아닙니다.

미드포인트 원은 외곽선을 그리는 알고리즘입니다. 참원에 가장 가까운 격자점을 고르므로, 그 점이 원 안이라는 보장이 없습니다.

r = 2 에서 (2,1) 을 찍는데 2² + 1² = 5 > 4 입니다. 시야 마스크로 쓰면 칸 수가 가우스 원 문제의 값과 어긋납니다.

이 반례는 골든 벡터를 처음 만들 때 개수가 맞지 않아 드러났습니다. 화면으로는 알아채기 어렵습니다 — 한 칸이 더 보일 뿐이니까요.

정리 6.2 — 덧셈만으로 행 span 구하기

필요한 것은 외곽선이 아니라 채워진 원판입니다. 행마다 "원 안에 드는 최대 |i|" 하나만 알면 됩니다.

span[j] = ⌊√(r² − j²)⌋

제곱근을 행마다 부르는 대신, x 가 결코 늘지 않는다는 성질을 씁니다.

py/rts/circle.py14–32곱셈도 제곱근도 없다
def spans(r):
    """span[j] = 행 j 에서 원 안에 드는 최대 |i|. 덧셈과 뺄셈만 쓴다.

       불변식은 t = r² − j² − x² >= 0 이고 x 가 그 조건을 만족하는 최대값이다.
       x 는 결코 늘지 않으므로 전체 비용이 O(r) 이다 (SPEC 정리 6.2).
    """
    if r in _span_cache:
        return _span_cache[r]
    out = [0] * (r + 1)
    out[0] = r
    x, t = r, 0
    for j in range(1, r + 1):
        t -= 2 * (j - 1) + 1
        while t < 0:
            t += 2 * x - 1
            x -= 1
        out[j] = x
    _span_cache[r] = out
    return out

정리 6.2. 매 j 마다 span[j] = ⌊√(r²−j²)⌋ 이다. 따라서 전체 비용은 O(r) 이다.

증명 스케치. 불변식은 t = r² − j² − x² ≥ 0 이고 x 가 그 조건을 만족하는 최대값이라는 것입니다. j 가 1 늘면 t 가 2j−1 만큼 줄고, x 를 1 줄이면 2x−1 만큼 늡니다. 내부 while 이 도는 총 횟수는 x 가 r 에서 0 까지 내려가는 횟수뿐이므로 전체 O(r) 입니다. ∎

def offsets(r):
    """(dx, dy) 목록. dy 오름차순, 같은 dy 안에서 dx 오름차순으로 **고정**한다.

       순서가 다르면 참조 카운트 결과는 같지만 이벤트 로그의 순서가 달라지고,
       그 차이가 상태 해시를 가른다(SPEC §6.3).
    """
    if r in _off_cache:
        return _off_cache[r]
    sp = spans(r)
    out = []
    for j in range(-r, r + 1):
        w = sp[j if j >= 0 else -j]
        for i in range(-w, w + 1):
            out.append((i, j))
    _off_cache[r] = out
    return out

참조 카운트(15부)는 순서와 무관하게 같은 결과를 냅니다. 그런데도 순서를 명세로 고정하는 이유는 이벤트 로그 때문입니다.

시야가 켜지는 순서가 다르면 트레이스의 줄 순서가 달라지고, 세 언어의 trace.jsonl 이 바이트 단위로 갈립니다. 결과는 같은데 파일이 다르면, 그 파일로는 아무것도 증명할 수 없습니다.

캐시를 두는 것도 명세의 일부입니다. 반경은 최대 8 이고 종류가 여덟 개뿐이라, 한 번 만든 오프셋 목록을 계속 돌려 씁니다. 매 틱 유닛마다 다시 만들면 그것만으로 시뮬 시간이 두 배가 됩니다.

시야에는 시선 판정이 없다

벽 뒤가 보입니다. 일부러 그렇게 두었습니다.

시선(line of sight) 판정을 넣으면 유닛마다 반경 안 모든 칸에 브레젠험 선을 그어야 합니다. 반경 5 면 81칸, 유닛 40기면 매 틱 3,240번의 선긋기입니다.

도스 시절 RTS 대부분이 같은 선택을 했습니다. 시선 판정이 있던 것은 고저차가 있는 게임들이었고, 이 엔진에는 고저차가 없습니다.

이것은 성능 때문에 정확도를 포기한 자리입니다. 15부에서 시선 판정을 넣으면 얼마나 느려지는지 실측으로 보입니다 — 그리고 그것이 왜 안개의 모양을 바꾸는지도요.

확인 문제 1

dab 의 반올림 항 32768 을 빼면 dab(1,0) 이 0 이 된다. 그런데 dab(0,1) 도 0 인가? 그리고 그 버그가 게임에서 어떻게 보이는가?

mx 와 mn 은 부호도 축도 보지 않고 큰 쪽·작은 쪽만 봅니다. (0,1) 도 mx=1, mn=0 이므로 똑같이 0 입니다.

게임에서는 붙어 있는 적을 못 때리는 것이 아니라 그 반대입니다. 거리가 0 이면 "가장 가까운 것" 비교에서 모든 인접 후보가 동점이 되고, 타이브레이크(핸들 오름차순)가 전부를 결정합니다. 그러면 유닛이 등 뒤의 적을 놔두고 핸들이 작은 먼 적을 쫓습니다.

더 나쁜 것은 이 버그가 대칭이라 결정론을 깨지 않는다는 점입니다. 세 언어가 똑같이 틀리므로 파리티 검사를 전부 통과합니다. 골든 벡터의 오차 열(dabpm = −1000)이 아니었으면 못 봤을 것입니다.

확인 문제 2

시야 반경을 8 에서 9 로 늘리면 마스크의 칸 수는 몇 개가 되는가? 그리고 spans 의 while 문은 몇 번 더 도는가?

칸 수는 N(9) = 253 입니다(197 → 253, +28 %). 넓이 π·81 = 254.5 와 1.5칸 차이입니다.

while 은 전체를 통틀어 r 번 돕니다 — x 가 r 에서 0 까지 내려가는 횟수가 전부이기 때문입니다(정리 6.2). r=8 에서 8번, r=9 에서 9번. 바깥 for 도 r 번이므로 총 비용은 여전히 O(r) 입니다.

실제로 늘어나는 비용은 마스크를 쓰는 쪽입니다. 시야 갱신은 칸마다 카운트를 올리므로 197 → 253 만큼 더 듭니다. 반경 하나를 올리는 결정이 시야 비용을 28 % 올린다는 뜻이고, 그래서 SIGHT_MAX = 8 이 상수표에 있습니다.
