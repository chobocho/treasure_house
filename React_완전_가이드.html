CHAPTER 01

강물처럼 흐르는 화면

React는 “화면을 어떻게 고칠까”라는 질문을 “지금 상태가 무엇인가”로 바꾼다. 이 장은 코드보다 사고방식이다.

  • 명령형으로 테트리스를 그리면 무엇이 무너지는가
  • 화면 = f(상태) 라는 한 줄
  • 가상 DOM과 재조정이 실제로 하는 일
  • 왜 TypeScript를 함께 쓰는가

왜 예제가 테트리스인가

튜토리얼에서 흔한 “할 일 목록”은 React의 절반만 보여 준다. 테트리스는 나머지 절반을 강제로 만나게 한다.

  • 시간이 흐른다. 아무도 누르지 않아도 조각이 떨어진다 — 타이머, 정리(cleanup), 의존성 배열이 필요해진다.
  • 상태가 복잡하다. 판·현재 조각·다음 조각·홀드·점수·레벨이 서로 맞물린다 — useState 일곱 개로는 감당이 안 되고 useReducer가 필요해진다.
  • 200칸을 60번/초 다시 그린다. 성능 이야기가 이론이 아니라 눈에 보인다.
  • 규칙이 순수하다. 회전·충돌·줄 삭제는 입력만 보고 답이 나오는 함수다 — 테스트하기 좋은 코드가 무엇인지 보여 준다.
  • 타입이 이득을 준다. 조각은 일곱 종뿐이고 액션도 여덟 개뿐이다 — 유니온 타입이 빛나는 딱 그 상황이다.
테트리스는 “상태 하나가 바뀌면 화면 전체가 달라지는” 프로그램이다. React가 정확히 그 문제를 위해 만들어졌다.

화면은 상태의 함수다

React의 전부를 한 줄로 줄이면 이렇다.

화면 = f( 상태 )

f가 컴포넌트다. 당신은 “지금 상태가 이러면 화면은 이렇게 생겼다”만 적는다. 그 상태에서 저 상태로 가려면 DOM을 어떻게 고쳐야 하는지는 적지 않는다.

상태
score: 1200 → 컴포넌트
f(state) → 화면
<div>1200</div>

상태가 1300으로 바뀌면 f를 다시 부른다. 끝이다. “1200을 1300으로 고치는 코드”는 세상에 존재하지 않는다.

명령형으로 그리면 이렇게 된다

DOM을 직접 만지는 방식 — 조각이 한 칸 내려갈 때

// 지웠다 → 다시 칠했다 → 그런데 고스트는? 점수는? 게임오버는?
function moveDown() {
  clearCells(piece);            // 옛 위치 지우기
  piece.y += 1;
  if (collides(board, piece)) {
    piece.y -= 1;
    lockPiece();                // 여기서 줄 삭제가 일어날 수도 있다
    updateScoreLabel();         // 점수 DOM도 손으로 고쳐야 하고
    updateNextPreview();        // 미리보기도 손으로
    if (topOut()) showGameOver();
  }
  paintCells(piece);            // 새 위치 칠하기
  paintGhost();                 // 고스트도 지웠다 다시
}

기능이 늘 때마다 “어디를 지우고 어디를 칠할지” 목록이 길어진다. 홀드 기능을 넣으면 이 함수와 다섯 군데를 함께 고쳐야 한다. 버그는 늘 그 “함께 고쳐야 했는데 잊은 곳”에서 나온다.

선언형으로 그리면 이렇게 된다

React 방식 — 같은 기능

// 상태를 어떻게 바꿀지만 적는다. 화면은 알아서 따라온다.
dispatch({ type: 'TICK' });

// 리듀서: (상태, 액션) → 새 상태. DOM은 한 글자도 없다.
function reducer(state: GameState, action: Action): GameState {
  if (action.type === 'TICK') return move(state, 0, 1);
  // ...
}

// 화면: 지금 상태를 그리는 방법만 적는다.
<Board board={state.board} active={state.active} />
<Score value={state.score} />
<Next kind={state.nextKind} />

홀드 기능을 넣고 싶으면 리듀서에 case 'HOLD'를 더하고 <Hold> 한 줄을 쓴다. “지워야 할 곳” 목록은 애초에 없다.

강물 비유 — 이 교재의 그림

이 교재는 React를 강물로 본다. 용어가 헷갈릴 때마다 이 그림으로 돌아오면 된다.

강물React뜻
수원(샘)state모든 흐름이 시작되는 곳. 여기만 바꾼다
물줄기props위에서 아래로만 흐른다. 거꾸로 오르지 않는다
물길컴포넌트 트리물이 지나가는 지형
수위 변화렌더수원이 바뀌면 물길 전체가 다시 계산된다
강바닥실제 DOM실제로 깎이는 곳. 바뀐 데만 깎인다
지류이벤트 핸들러아래에서 수원으로 신호를 보낸다(물이 아니라 신호다)
보(洑)memo흐름이 그대로면 아래로 안 흘려보낸다
바다바깥 세계(API·타이머)useEffect로만 닿는다

다시 그린다 ≠ 다 지우고 다시 만든다

“상태가 바뀌면 화면을 통째로 다시 그린다”는 말은 DOM을 다 버린다는 뜻이 아니다. React가 다시 만드는 것은 설계도이지 건물이 아니다.

1. 상태가 바뀐다 score: 1200 → 1300 ↓ 2. 컴포넌트 함수를 다시 부른다 → 새 설계도(엘리먼트 트리)가 나온다 ↓ 3. 옛 설계도와 비교한다 (재조정 · reconciliation) ↓ 4. 다른 곳만 실제 DOM에 반영한다 (커밋) — 이 경우 텍스트 노드 하나

테트리스 200칸 중 조각이 한 칸 내려가면 실제로 바뀌는 DOM은 8칸 안팎이다. 나머지 192칸은 손대지 않는다.

가상 DOM은 “빠른 DOM”이 아니다

흔한 오해 — “가상 DOM이 빨라서 React가 빠르다.” 사실이 아니다. 손으로 최적화한 명령형 코드가 언제나 더 빠르다.

가상 DOM이 파는 것은 속도가 아니라 “느려지지 않는 상한선”과 사람의 시간이다.

  • 사람이 직접 최적화하면 빠르다. 대신 기능이 늘 때마다 다시 최적화해야 하고, 한 군데를 빠뜨리면 화면이 어긋난다.
  • React는 “충분히 빠른” 결과를 기능이 늘어도 계속 낸다. 최악의 경우가 예측 가능하다는 뜻이다.
  • 정말 빠듯한 부분(캔버스 게임의 렌더 루프 등)은 React 밖으로 빼면 된다. 9장에서 다룬다.
React는 “가장 빠른 코드”가 아니라 “틀리기 어려운 코드”를 준다. 그리고 대부분의 화면에서 그 결과는 충분히 빠르다.

단방향 데이터 흐름

물은 위에서 아래로만 흐른다. 자식이 부모의 값을 직접 바꿀 수는 없다.

Tetris — state를 가진다 (board, score, ...) ↓ props (값) Board — 받은 board를 그린다 ↓ props (값) Cell — 받은 kind로 색만 정한다

아래에서 위로 올라가는 것은 물이 아니라 신호다. 부모가 내려 준 함수를 자식이 부르는 방식이다.

// 부모
<Controls onMove={(dx) => dispatch({ type: dx < 0 ? 'LEFT' : 'RIGHT' })} />

// 자식 — 상태를 모른다. 그냥 “왼쪽 눌렸어요”라고 알릴 뿐이다.
<button onClick={() => props.onMove(-1)}>←</button>

덕분에 버그를 찾을 때 “이 값이 어디서 왔나”를 위로만 따라가면 된다. 옆에서 몰래 바꾸는 코드가 없다.

React가 아닌 것

React는 프레임워크가 아니라 UI 라이브러리다. 화면을 그리는 일 하나만 한다. 나머지는 전부 당신이 고른다.

라우팅없다. React Router, TanStack Router, 또는 Next.js가 대신한다
HTTP 통신없다. fetch, TanStack Query 등을 쓴다
전역 상태없다(Context는 전달 수단이지 상태 관리자가 아니다). Zustand, Redux 등
스타일없다. CSS Modules, Tailwind, CSS-in-JS 무엇이든
빌드없다. Vite가 사실상 표준이다
폼 검증없다. React Hook Form + Zod 조합이 흔하다
이 자유가 초보에게는 부담이다. 처음에는 Vite + TypeScript만으로 시작하고, 필요할 때 하나씩 더해라. 이 교재는 300장 내내 추가 라이브러리를 하나도 쓰지 않는다.

왜 TypeScript와 함께 쓰는가

React 컴포넌트는 결국 “props를 받아 화면을 만드는 함수”다. 함수에 타입이 붙으면 무엇이 좋은지는 테트리스에서 즉시 드러난다.

// 조각은 일곱 종뿐이다. 이 사실을 타입으로 적어 두면…
type PieceKind = 'I' | 'J' | 'L' | 'O' | 'S' | 'T' | 'Z';

<Piece kind="X" />
//        ~~~ 오류: '"X"' 형식은 'PieceKind' 형식에 할당할 수 없습니다.

// 액션도 여덟 개뿐이다.
type Action =
  | { type: 'LEFT' } | { type: 'RIGHT' } | { type: 'ROTATE' }
  | { type: 'TICK' } | { type: 'HARD' } | { type: 'HOLD' }
  | { type: 'PAUSE' } | { type: 'START' };

dispatch({ type: 'ROTATO' });  // 오타를 컴파일 시점에 잡는다
  • props 이름과 개수를 편집기가 자동완성해 준다.
  • 리듀서의 switch에서 빠뜨린 액션을 컴파일러가 알려 준다(15장 never 기법).
  • 리팩터링할 때 이름을 바꾸면 고쳐야 할 파일을 전부 짚어 준다.

이 교재의 데모는 진짜다

아래 상자를 눌러 보라. 실제로 useState가 돌고 있다. 그림도, 녹화도 아니다.

이 데모의 소스는 5장에서 그대로 나온다. 지금은 “값으로 두 번”과 “함수로 두 번”의 결과가 다르다는 것만 눈에 담아 두면 된다.

1장 요약

  • 화면 = f(상태). 상태만 바꾸면 화면은 따라온다.
  • “다시 그린다”는 설계도를 다시 만든다는 뜻이고, DOM은 달라진 부분만 바뀐다.
  • 가상 DOM은 최고 속도가 아니라 예측 가능한 속도와 사람의 시간을 판다.
  • 데이터는 아래로, 신호는 위로. 옆으로 새는 길은 없다.
  • React는 화면만 담당한다. 나머지는 고르는 것이고, 처음엔 안 골라도 된다.
  • TypeScript는 “조각은 일곱 종”, “액션은 여덟 개” 같은 이미 알고 있는 사실을 컴파일러에게 알려 주는 일이다.
다음 장에서 실제로 프로젝트를 만든다. 명령 세 줄이면 된다.

CHAPTER 02

시작하기 — Vite + TypeScript

명령 세 줄이면 개발 서버가 뜬다. 이 장에서는 그 세 줄이 만들어 낸 파일들을 한 줄씩 읽는다.

  • 프로젝트 생성과 파일 구조
  • tsconfig.json에서 실제로 중요한 옵션
  • createRoot와 StrictMode
  • 테트리스 프로젝트의 폴더 배치

세 줄로 시작한다

npm create vite@latest tetris-react -- --template react-ts
cd tetris-react
npm install && npm run dev

--template react-ts가 핵심이다. React + TypeScript 조합이 이미 맞춰진 상태로 나온다.

명령하는 일
npm run dev개발 서버. 파일을 고치면 브라우저가 상태를 유지한 채 갱신된다(HMR)
npm run builddist/에 배포용 정적 파일 생성 + 타입 검사
npm run preview빌드 결과를 실제와 비슷하게 띄워 확인
HMR 덕분에 테트리스를 만들 때 게임을 진행한 채로 색상이나 점수 공식을 고쳐 볼 수 있다. 판이 초기화되지 않는다.

파일이 열 개도 안 된다. Webpack 시절의 설정 지옥은 없다. vite.config.ts는 대개 손대지 않는다.

index.html

  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />

React 앱의 HTML은 이게 전부다. <div id="root"> 하나가 비어 있고, 그 안을 React가 채운다.

StrictMode가 하는 일

개발 모드에서만 동작하는 검사기다. 화면에는 아무것도 그리지 않는다.

  • 컴포넌트 함수를 두 번 호출한다 → 렌더 중에 바깥 값을 건드리는 “불순한” 코드를 드러낸다.
  • useEffect를 등록 → 정리 → 다시 등록 순서로 한 번 더 돌린다 → 정리 함수를 안 쓴 이펙트를 드러낸다.
  • 지원 종료 예정 API 사용을 경고한다.
테트리스에서 이걸 모르면 이렇게 당한다 — setInterval을 걸고 clearInterval을 안 쓰면, StrictMode에서 타이머가 두 개 돌아 조각이 두 배 속도로 떨어진다. 버그가 아니라 당신의 버그를 StrictMode가 크게 키워 보여 준 것이다.
production 빌드에서는 이중 호출이 사라진다. “개발에서만 이상하다”면 StrictMode를 의심하되, 끄지 말고 원인을 고쳐라.

function first<T>(arr: T[]) { return arr[0]; }

CHAPTER 03

JSX와 TSX

JSX는 언어가 아니다. 함수 호출을 보기 좋게 쓴 것뿐이다. 그 사실을 알고 나면 규칙들이 전부 당연해진다.

  • JSX가 변환되면 무엇이 되는가
  • 중괄호·Fragment·속성 이름 규칙
  • 조건과 반복을 표현식으로 쓰는 법
  • 테트리스 판을 JSX로 그리기

JSX는 문법 설탕이다

왼쪽을 쓰면 컴파일러가 오른쪽으로 바꾼다

// 당신이 쓰는 것
<div className="tt-board">
  <Cell kind="T" />
</div>

// 컴파일러가 만드는 것 (jsx: "react-jsx")
_jsx("div", {
  className: "tt-board",
  children: _jsx(Cell, { kind: "T" })
});

즉 JSX 한 조각은 객체 하나다. 이 객체를 React 엘리먼트라고 부른다. 화면이 아니라 화면의 설명서다.

const el = <Cell kind="T" />;
console.log(el);
// { type: Cell, props: { kind: 'T' }, key: null, ... }
JSX가 객체라는 사실에서 나머지가 따라온다 — 변수에 담을 수 있고, 배열에 넣을 수 있고, 함수가 반환할 수 있고, 조건 연산자의 양쪽에 놓을 수 있다.

이 교재의 데모가 h()로 쓰인 이유

이 문서는 빌드 도구 없이 브라우저에서 그대로 열린다. 그래서 JSX 변환기를 쓸 수 없다. 대신 변환 결과를 손으로 적었다.

// 슬라이드에 실린 TSX
<div className="tt-panel">
  <span className="tt-lab">NEXT</span>
  <Mini kind={next} />
</div>

// 이 문서의 데모가 실제로 실행하는 코드 — 같은 것이다
h('div', { className: 'tt-panel' },
  h('span', { className: 'tt-lab' }, 'NEXT'),
  h(Mini, { kind: next })
)

규칙은 셋뿐이다. 첫 인자 = 태그 또는 컴포넌트, 둘째 = props 객체, 나머지 = 자식.

JSX가 “마법”처럼 느껴진다면 이 대응표를 몇 번 눈으로 따라가 보라. 마법이 사라지고 나면 오류 메시지가 훨씬 잘 읽힌다.

규칙 1 — 반환값은 하나여야 한다

// 오류: JSX 식에는 부모 요소가 하나 있어야 합니다
function Panel() {
  return (
    <span>NEXT</span>
    <Mini kind="T" />
  );
}

함수가 값 두 개를 return할 수 없으니 당연하다. 감싸면 되는데, 쓸데없는 <div>를 만들고 싶지 않다면 Fragment를 쓴다.

function Panel() {
  return (
    <>
      <span>NEXT</span>
      <Mini kind="T" />
    </>
  );
}
Fragment에 key를 줘야 할 때(리스트 안)는 축약형을 못 쓴다. <Fragment key={id}>처럼 정식 이름으로 쓰고 import { Fragment } from 'react'가 필요하다.

규칙 2 — 중괄호 안은 “값을 만드는 식”

const kind = 'T';
const score = 1200;

<div className="cell">
  {kind}                      {/* 변수 */}
  {score * 2}                 {/* 계산식 */}
  {score > 1000 ? '고득점' : ''}  {/* 삼항 연산자 */}
  {pieces.map(p => <Cell key={p.id} kind={p.kind} />)}  {/* 배열 */}

중괄호 안에는 식(expression)만 들어간다. if, for, switch 같은 문(statement)은 못 쓴다. 그래서 React 코드에 삼항 연산자와 &&가 많은 것이다.
// 안 된다
<div>{ if (over) { ... } }</div>

// 이렇게 한다 — 함수 본문(문이 허용되는 곳)에서 계산하고 결과만 끼운다
function Board({ state }: { state: GameState }) {
  let overlay = null;
  if (state.status === 'over') overlay = <GameOver score={state.score} />;
  return <div>{overlay}</div>;
}

테트리스 판을 JSX로 그리기

components/Board.tsx — 20×10을 어떻게 200개의 엘리먼트로 만드는가

interface BoardProps {
  board: Board;
  active: Piece;
  ghost: Piece | null;
}

export function BoardView({ board, active, ghost }: BoardProps) {
  // 1. 굳어진 판을 복사한 뒤 현재 조각과 고스트를 겹쳐 그린 "보이는 판"을 만든다
  const view = board.map(row => [...row]);
  const ghostAt = new Set<number>();

  if (ghost) for (const [x, y] of cellsOf(ghost)) if (y >= 0) ghostAt.add(y * COLS + x);
  for (const [x, y] of cellsOf(active)) if (y >= 0) view[y][x] = active.kind;

  // 2. 2차원 배열을 1차원 엘리먼트 배열로 편다
  return (
    <div className="tt-board">
      {view.flatMap((row, y) =>
        row.map((kind, x) => (
          <Cell
            key={y * COLS + x}
            kind={kind}
            ghost={kind === '' && ghostAt.has(y * COLS + x)}
          />
        )),
      )}
    </div>
  );
}

CSS Grid가 10열을 잡아 주므로 JSX는 평평한 200개만 내놓으면 된다.

CHAPTER 04

컴포넌트와 Props

컴포넌트는 props를 받아 화면을 반환하는 함수다. 이 장에서 테트리스 화면을 이루는 다섯 컴포넌트를 전부 만든다.

  • props에 타입을 붙이는 방법과 고르는 기준
  • children과 합성
  • 컴포넌트를 언제 쪼개는가
  • “순수해야 한다”가 실제로 뜻하는 것

컴포넌트는 그냥 함수다

// 이것이 컴포넌트다. 특별한 상속도, 등록도 없다.
function Score(props: { value: number }) {
  return <dd>{props.value}</dd>;
}

// 쓰는 쪽
<Score value={1200} />

조건은 둘뿐이다.

  • 이름이 대문자로 시작한다. 소문자면 JSX가 <score>라는 HTML 태그로 해석해 버린다.
  • React 엘리먼트(또는 null 등)를 반환한다.
대문자 규칙은 스타일이 아니라 문법이다. <score value={1} />는 오류도 안 나고 조용히 알 수 없는 HTML 태그를 만든다. 이 버그는 찾기 오래 걸린다.

첫 컴포넌트 — Cell

  kind: Cell;        // '' | 'I' | 'J' | ... | 'Z'

상태도 없고 이펙트도 없다. 입력(props) → 출력(엘리먼트)이 전부다. 이런 컴포넌트가 가장 좋은 컴포넌트다.

const PREVIEW_SIZE = 4;

export function MiniPiece({ kind }: { kind: PieceKind | null }) {
  // 홀드가 비어 있으면 빈 격자를 그린다 — null을 반환하면 자리가 흔들린다
  const filled = new Set<number>();
  if (kind) {
    for (const [x, y] of PIECES[kind].cells) filled.add(y * PREVIEW_SIZE + x);
  }

  return (
    <div className="tt-mini">
      {Array.from({ length: PREVIEW_SIZE * PREVIEW_SIZE }, (_, i) => (
        <div key={i} className={filled.has(i) ? `tt-cell k${kind}` : 'tt-cell'} />
      ))}
    </div>
  );
}
Array.from({ length: n }, (_, i) => ...)는 “n개짜리 배열을 만들어 인덱스로 채운다”는 관용구다. new Array(n).map()은 동작하지 않는다 — 빈 슬롯은 map이 건너뛴다.

props로 조각을 바꿔 보자

위 버튼은 부모의 state를 바꾸고, 그 값이 props로 <Piece>에 내려간다. Piece 자신은 state가 없다 — 무엇을 그릴지는 전적으로 부모가 정한다.

컴포넌트는 순수해야 한다

“순수하다”는 같은 props를 주면 같은 결과가 나오고, 렌더 도중에 바깥 세계를 건드리지 않는다는 뜻이다.

let renderCount = 0;

// 순수하지 않다 — 렌더할 때마다 바깥 변수를 바꾼다
function Cell({ kind }: CellProps) {
  renderCount++;                  // ← StrictMode에서 두 배로 센다
  document.title = `조각 ${kind}`; // ← 렌더 중에 DOM을 만졌다
  return <div className={kind} />;
}
// 순수하다 — 바깥 세계와의 접촉은 useEffect로 미룬다
function Cell({ kind }: CellProps) {
  useEffect(() => { document.title = `조각 ${kind}`; }, [kind]);
  return <div className={kind} />;
}
순수해야 하는 이유는 도덕이 아니라 실리다. React는 컴포넌트를 언제, 몇 번, 어떤 순서로 부를지 스스로 정한다(17장 동시성). 순수하지 않으면 그 자유가 곧 버그가 된다.

컴포넌트를 언제 쪼개는가

  • 이름이 붙는가. “이 부분은 점수판이다”라고 말할 수 있으면 컴포넌트다.
  • 따로 다시 그려지길 바라는가. 200개의 칸은 각자 memo로 막고 싶다 → 별도 컴포넌트여야 한다(13장).

  • 함수가 화면 밖으로 넘치는가. 100줄이 넘으면 대개 두세 개다.

CHAPTER 05

state — 변하는 것

React를 어렵게 만드는 것은 문법이 아니라 “언제 어떤 값이 보이는가”다. 이 장은 그 감각을 만드는 장이다.

  • state가 지역 변수와 무엇이 다른가
  • 스냅샷과 함수형 업데이트, 배칭
  • 객체·배열 state를 불변으로 다루는 법
  • 상태를 어디에 둘 것인가

지역 변수로는 왜 안 되는가

동작하지 않는다

function Counter() {
  let level = 1;                       // 렌더될 때마다 1로 초기화된다
  return <button onClick={() => level++}>레벨 {level}</button>;
}

두 가지가 동시에 잘못됐다.

  • 기억하지 못한다. 컴포넌트 함수는 렌더할 때마다 처음부터 다시 실행된다. level은 매번 1이다.
  • 알리지 못한다. 지역 변수를 바꿔도 React는 “다시 그려야 한다”는 사실을 모른다.

  return <button onClick={() => setLevel(level + 1)}>레벨 {level}</button>;

state는 스냅샷이다

이것이 React에서 가장 자주 사람을 넘어뜨리는 개념이다.

function Demo() {
  const [n, setN] = useState(0);

  function handleClick() {
    setN(n + 1);
    console.log(n);        // 0  ← 방금 바꿨는데 그대로다
    setN(n + 1);
    console.log(n);        // 0  ← 여전히
  }
  // 클릭 한 번에 n은 1이 된다. 2가 아니다.
}

n은 이번 렌더가 시작될 때 찍힌 사진이다. 사진 속 숫자는 바뀌지 않는다. setN은 사진을 고치는 게 아니라 “다음 사진은 이렇게 찍어 달라”는 예약이다.

렌더 #1 — n은 0으로 고정. 이 렌더에서 만든 모든 함수가 0을 기억한다 ↓ setN(0+1) 두 번 → 둘 다 “다음엔 1” 렌더 #2 — n은 1

함수형 업데이트

// 값을 넘기면: "다음 값은 n+1" — 이번 렌더의 n을 쓴다
setN(n + 1);
setN(n + 1);      // 결과: +1

// 함수를 넘기면: "직전 결과에 1을 더해 달라" — 큐에 쌓여 순서대로 적용된다
setN(prev => prev + 1);
setN(prev => prev + 1);   // 결과: +2
고르는 기준 — 새 값이 이전 값에 의존하면 함수형을 쓴다. 그렇지 않으면(예: setStatus('over')) 값을 그냥 넘긴다.

테트리스에서 이게 결정적인 순간이 있다. 타이머 콜백은 등록될 때의 스냅샷을 붙들고 있기 때문이다.

useEffect(() => {
  const id = setInterval(() => {
    setTick(tick + 1);        // 항상 등록 당시의 tick + 1 → 1에서 멈춘다
    setTick(t => t + 1);      // 올바르다
  }, 500);
  return () => clearInterval(id);
}, []);

직접 확인해 보라

“값으로 두 번”과 “함수로 두 번”의 차이가 곧 위 슬라이드의 내용이다. 증가폭을 바꿔 가며 눌러 보라.

배칭 — 여러 setState가 한 번의 렌더로

React는 한 이벤트 핸들러 안에서 일어난 상태 변경을 모아서 한 번에 처리한다.

  setBoard(nextBoard);     //
  setScore(s => s + 100);  //  세 번 호출했지만
  setLines(l => l + 1);    //

덕분에 “점수만 먼저 바뀌고 판은 아직 옛날인” 어중간한 화면이 사람 눈에 보이지 않는다.

React 18부터는 타이머·Promise 안에서도 배칭된다(자동 배칭). 위 데모에서 타이머 두 개로 나누면 각각이 별개의 작업이라 렌더가 두 번 일어난다.

객체 state — 새로 만든다

이러지 말 것

piece.x += 1;
setPiece(piece);        // 같은 객체다 → React는 "안 바뀌었다"고 판단, 렌더 안 함

새 객체를 만든다

setPiece({ ...piece, x: piece.x + 1 });
// 또는 이전 값에 의존하므로 함수형으로
setPiece(p => ({ ...p, x: p.x + 1 }));
화살표 함수가 객체를 반환할 때는 괄호로 감싸야 한다. p => { ... }는 함수 본문으로 해석되어 undefined를 반환한다.

React는 Object.is로 옛 값과 새 값을 비교한다. 얕은 비교조차 하지 않는다 — 참조가 같으면 끝이다. 이것이 불변성을 요구하는 이유이자, 동시에 200칸 판 비교가 순식간에 끝나는 이유다.

중첩 배열 — 테트리스 판 갱신

얕은 복사만으로는 부족하다

next[y][x] = 'T';             // 안쪽 행은 원본과 같은 객체 → 원본이 오염된다

바뀌는 경로만 새로 만든다

function setCell(board: Board, x: number, y: number, kind: Cell): Board {
  return board.map((row, ry) =>
    ry !== y ? row : row.map((c, rx) => (rx === x ? kind : c)),
  );
}

여러 칸을 한 번에 바꿀 때는 통째로 복사가 낫다

export function merge(board: Board, piece: Piece): Board {
  const next = board.map(row => [...row]);      // 20번의 얕은 복사
  for (const [x, y] of cellsOf(piece)) {
    if (y >= 0) next[y][x] = piece.kind;        // 내가 방금 만든 배열이므로 OK
  }
  return next;
}

20×10 복사는 200번의 참조 복사다. 초당 60번 해도 아무 문제 없다. 불변성이 느릴까 봐 걱정할 규모가 아니다.

테트리스에서 진짜 state는 놀랍도록 적다 — 판, 현재 조각, 다음 가방, 홀드, 점수, 지운 줄, 상태값. 레벨·속도·고스트 위치·게임오버 여부는 전부 계산 결과다.

상태를 어디에 둘 것인가

기본은 가능한 한 아래다. 그리고 두 형제가 같은 값이 필요해지는 순간 가장 가까운 공통 부모로 올린다. 이것을 상태 끌어올리기(lifting state up)라고 한다.

점수판과 버튼은 형제다. 둘 다 score가 필요하니 부모가 들고, 값과 함수를 각각 내려 준다.

key로 상태를 초기화하기

“새 게임”을 누르면 모든 하위 상태를 처음으로 되돌리고 싶다. 상태를 하나하나 초기화하는 대신, React에게 다른 컴포넌트라고 말하면 된다.

const [gameId, setGameId] = useState(0);

<button onClick={() => setGameId(id => id + 1)}>새 게임</button>
<Tetris key={gameId} />   {/* key가 바뀌면 옛 것을 버리고 새로 마운트한다 */}
이 기법은 폼 초기화, 탭 전환, 모달 재사용에서도 그대로 쓰인다. “상태를 지우고 싶다”가 아니라 “이건 다른 것이다”라고 말하는 쪽이 언제나 더 안전하다.
단, 마운트가 다시 일어나므로 useEffect도 전부 다시 돈다. 타이머·구독이 있다면 정리 함수가 제대로 있는지 확인하라.

useState 일곱 개로 테트리스를 짜면

const [active, setActive] = useState(spawn('T'));
const [nextKind, setNextKind] = useState<PieceKind>('I');

function lock() {
  const merged = merge(board, active);
  const { board: cleared, n } = clearLines(merged);
  setBoard(cleared);
  setScore(s => s + SCORE[n] * level);
  setLines(l => l + n);
  setCanHold(true);
  const k = draw();          // 이 안에서 setBag도 부른다
  setActive(spawn(nextKind));
  setNextKind(k);

마지막 줄이 이 방식의 사형 선고다. 스냅샷 규칙 때문에 방금 설정한 값을 같은 함수 안에서 읽을 수 없다. 상태들이 서로를 참조하는 순간 useState 여러 개는 무너진다.

답은 10장이다 — 상태 아홉 개가 아니라 상태 하나와 전이 함수 하나로 바꾼다.

5장 요약

  • state = 렌더 사이에 기억 + 바뀌면 알림. 지역 변수는 둘 다 못 한다.
  • 이번 렌더의 state는 사진이다. setX 직후에 읽어도 옛 값이다.
  • 새 값이 이전 값에 의존하면 setX(prev => ...).
  • 한 핸들러 안의 여러 setX는 한 번의 렌더로 묶인다.
  • 객체·배열은 새로 만들어 넣는다. 판 200칸 복사는 걱정할 비용이 아니다.
  • 계산할 수 있는 값은 state가 아니다. 레벨·속도·고스트는 전부 계산 결과다.
  • 상태들이 서로를 참조하기 시작하면 useReducer로 갈 때다.

이벤트와 폼

사용자의 손가락이 상태에 닿는 지점. 테트리스의 키보드 조작이 이 장의 결승점이다.

  • 합성 이벤트와 타입

  • 제어 컴포넌트와 비제어 컴포넌트

핸들러는 “함수 자체”를 넘긴다

// 함수를 넘긴다 — 클릭할 때 React가 부른다
<button onClick={handleDrop}>드롭</button>

// 함수를 부른다 — 렌더 중에 즉시 실행된다! (무한 루프의 단골)

렌더마다 새 화살표 함수가 만들어지는 것은 거의 항상 괜찮다. 함수 하나 만드는 비용은 무시할 수준이다. 이게 문제가 되는 정확한 조건은 13장에서 다룬다.

합성 이벤트(SyntheticEvent)

React가 넘겨주는 e는 브라우저의 네이티브 이벤트가 아니라 같은 모양으로 감싼 객체다. 브라우저마다 다른 동작을 맞춰 준다.

function onKeyDown(e: React.KeyboardEvent<HTMLDivElement>) {
  e.key;              // 'ArrowLeft'
  e.code;             // 'ArrowLeft' (물리 키 위치)
  e.repeat;           // 꾹 눌러 자동 반복 중인가
  e.preventDefault(); // 기본 동작(스크롤) 막기
  e.nativeEvent;      // 진짜 브라우저 이벤트가 필요하면 여기
}

  ' ': 'HARD',          // 스페이스바의 e.key는 공백 한 칸이다
  c: 'HOLD',
  C: 'HOLD',
  p: 'PAUSE',
  Escape: 'PAUSE',
};

function onKeyDown(e: React.KeyboardEvent<HTMLDivElement>) {
  const type = KEY_MAP[e.key];
  if (!type) return;                 // 우리가 쓰는 키가 아니면 그냥 흘려보낸다
  e.preventDefault();                // 방향키·스페이스의 스크롤을 막는다
  dispatch({ type });
}
모르는 키에는 손대지 마라. 무조건 preventDefault()를 부르면 Tab 이동, F5, Ctrl+C까지 막혀 버린다. 반드시 “내 키일 때만” 막아야 한다.
e.key는 글자('z', 한글 자판이면 'ㅋ'), e.code는 물리적 위치('KeyZ')다. 게임 조작은 e.code가 더 안전할 때가 많다.

리스트·조건부 렌더링과 key

200개의 칸을 그리는 일. 그리고 React에서 가장 많이 오해받는 한 글자, key.

  • 배열을 엘리먼트로 바꾸는 법
  • key가 “경고 없애는 법”이 아니라 정확성 문제인 이유
  • index를 key로 써도 되는 정확한 조건
  • 빈 상태와 중첩 리스트

배열 → 엘리먼트

const KINDS: PieceKind[] = ['I', 'J', 'L', 'O', 'S', 'T', 'Z'];

key는 왜 필요한가

React는 이전 트리와 새 트리를 비교할 때, 형제들 중 “누가 누구인지”를 알아야 한다. key가 그 신원증이다.

key 없이(위치로 판단)key 있음
리스트 앞에 항목 추가전부 한 칸씩 밀렸다고 보고 모든 항목의 내용을 고친다새 항목 하나만 삽입
항목 삭제뒤의 모든 항목이 앞으로 당겨져 갱신해당 노드만 제거
항목 순서 변경내용만 서로 바뀐다 → 내부 state가 엉뚱한 곳에 남는다DOM 노드를 옮긴다. state가 따라간다
key가 없을 때의 문제는 “느리다”가 아니라 “틀린다”이다. 각 항목이 자체 state(입력값, 애니메이션, 스크롤 위치)를 가질 때 즉시 드러난다.

직접 겪어 보라

각 칸에 아무 글자나 넣고 순서 섞기를 눌러 보라. key={index}일 때는 글자가 조각을 따라가지 않고 제자리에 남는다. key={조각 이름}이면 함께 움직인다.

좋은 key 고르기

  • 안정적이어야 한다 — 렌더가 바뀌어도 같은 항목이면 같은 key.
  • 형제 사이에서 유일해야 한다. 전역 유일일 필요는 없다.
  • 데이터에 이미 있는 id가 최선이다.

이러지 말 것

<Row key={Math.random()} />      // 매 렌더 새 key → 매번 통째로 새로 만든다
<Row key={JSON.stringify(row)} /> // 내용이 바뀌면 신원도 바뀐다 → state 날아감

이렇게

<Row key={row.id} />
<Cell key={y * COLS + x} />      // 격자의 좌표는 안정적인 신원이다
key={Math.random()}는 “경고를 없애려고” 쓰는 대표적 안티패턴이다. 경고는 사라지고 성능은 최악이 되며 내부 state는 매번 초기화된다.

index를 key로 써도 되는 때

다음 세 조건이 모두 참일 때만 안전하다.

  • 리스트 순서가 절대 바뀌지 않는다.
  • 항목이 중간에 삽입·삭제되지 않는다(끝에 추가만 하거나 고정 길이).
  • 항목이 자체 state를 갖지 않는다.
// 테트리스 판 — 세 조건을 모두 만족한다
{view.flatMap((row, y) =>
  row.map((kind, x) => <Cell key={y * COLS + x} kind={kind} />),
)}

20×10 격자는 크기가 고정이고 순서가 없고 칸에 state가 없다. 좌표에서 만든 인덱스가 완벽한 key다.

반대로 “점수 기록”, “최근 플레이 목록”, “드래그로 순서를 바꾸는 설정”은 index를 쓰면 안 된다. id를 만들어라 — crypto.randomUUID()를 생성 시점에 한 번 부르면 된다(렌더 중이 아니라).

key는 props가 아니다

<Cell key={id} id={id} kind={kind} />

useEffect — 바깥 세계와의 동기화

React 밖에 있는 것들(타이머, 이벤트, 네트워크, DOM)에 닿는 유일한 통로. 그리고 초보자가 가장 많이 남용하는 훅.

  • 이펙트의 세 가지 형태와 정리 함수
  • 의존성 배열과 낡은 클로저
  • 테트리스 낙하 타이머를 세 번 고쳐 완성하기
  • 이펙트가 필요 없는 경우들

이펙트는 “동기화”다

useEffect를 “렌더 후에 실행되는 코드”로 외우면 반드시 헤맨다. 정확한 정의는 이렇다.

바깥 시스템의 상태를 React 상태에 맞춰 두는 일

의존성 배열의 진짜 규칙

이펙트 함수 안에서 쓰는 모든 “컴포넌트 안의 값”을 넣는다
useEffect(() => {
  const id = setInterval(() => {
    if (status === 'playing') dispatch({ type: 'TICK' });
  }, speedOf(level));
  return () => clearInterval(id);
}, [status, level, dispatch]);   // ← 안에서 쓴 것 전부
넣어야 하나?예
넣는다props, state, 그것들로 계산한 값, 컴포넌트 안에서 만든 함수
안 넣어도 된다useState의 setter, useReducer의 dispatch, ref 객체 자체(ref), 모듈 최상위 상수·함수
의존성 배열은 “언제 실행할지 고르는 스위치”가 아니다. 실행 시점을 조절하려고 값을 일부러 빼면, 그 이펙트는 낡은 값을 보게 된다. 다음 슬라이드가 그 이야기다.

낡은 클로저(stale closure)

1차 시도 — 조각이 한 칸만 내려가고 멈춘다

useEffect(() => {
  const id = setInterval(() => {
    setPiece({ ...piece, y: piece.y + 1 });   // piece는 마운트 당시의 값에 고정
  }, 500);
  return () => clearInterval(id);
}, []);                                       // ← piece를 안 넣었다

빈 배열은 “이펙트를 한 번만 만든다”는 뜻이고, 그 안의 함수는 첫 렌더의 piece를 영원히 붙들고 있다. y는 언제나 0 + 1 = 1이다.

렌더 #1 — piece.y = 0. 이 값을 기억한 콜백이 setInterval에 등록됨 ↓ 500ms setPiece({y: 0+1}) → 렌더 #2 (piece.y = 1) ↓ 500ms — 하지만 콜백은 여전히 렌더 #1의 것 setPiece({y: 0+1}) → 값이 같다 → 아무 일도 일어나지 않는다

고치는 세 가지 길

A. 함수형 업데이트 — 최신 값을 React에게 물어본다

useEffect(() => {
  const id = setInterval(() => {
    setPiece((p) => ({ ...p, y: p.y + 1 }));   // 의존성이 사라진다
  }, 500);
  return () => clearInterval(id);
}, []);

B. dispatch — 리듀서라면 애초에 값을 읽을 필요가 없다

useEffect(() => {
  const id = setInterval(() => dispatch({ type: 'TICK' }), 500);
  return () => clearInterval(id);
}, [dispatch]);   // dispatch는 절대 안 바뀐다 → 사실상 []

C. 의존성에 넣는다 — 매번 타이머를 다시 건다

useEffect(() => {
  const id = setInterval(() => setPiece({ ...piece, y: piece.y + 1 }), 500);
  return () => clearInterval(id);
}, [piece]);      // 동작은 하지만 500ms 주기가 매번 리셋된다 — 게임에는 부적합
테트리스가 B를 고르는 이유가 여기 있다. dispatch는 상태를 읽지 않으므로 의존성이 아예 생기지 않는다. 10장에서 리듀서를 만드는 진짜 동기가 이것이다.

속도가 바뀌는 타이머 — 최종형

// 레벨이 오르면 주기가 짧아져야 한다 → delay가 의존성이 된다
useEffect(() => {
  if (status !== 'playing') return;          // 멈춤 상태면 타이머를 아예 안 건다
  const delay = speedOf(level);
  const id = setInterval(() => dispatch({ type: 'TICK' }), delay);
  return () => clearInterval(id);
}, [status, level, dispatch]);

레벨이 오르면 정리 → 새 타이머가 자동으로 일어난다. if (...) return;으로 조건부로 아무것도 하지 않는 것도 정상적인 이펙트다.

이펙트를 if 안에 넣으면 안 된다 — 훅은 항상 같은 순서로 호출돼야 한다. 조건은 이펙트 함수 안에 둔다.
// 안 된다: 훅 호출 자체가 조건부
if (status === 'playing') { useEffect(...); }

이 로직을 훅으로 뽑으면

src/hooks/useInterval.ts — Dan Abramov가 소개해 널리 쓰이는 패턴

import { useEffect, useRef } from 'react';

export function useInterval(callback: () => void, delay: number | null) {
  const saved = useRef(callback);

  // 콜백은 매 렌더 최신으로 갈아 끼운다 (타이머는 건드리지 않는다)
  useEffect(() => { saved.current = callback; });

  // 타이머는 delay가 바뀔 때만 다시 건다
  useEffect(() => {
    if (delay === null) return;              // null = 멈춤
    const id = setInterval(() => saved.current(), delay);
    return () => clearInterval(id);
  }, [delay]);
}
// 쓰는 쪽 — 한 줄이 된다
useInterval(
  () => dispatch({ type: 'TICK' }),
  status === 'playing' ? speedOf(level) : null,
);
“최신 콜백은 ref에, 재구독 조건은 의존성에” — 이 분리가 이 패턴의 전부다. 11장에서 커스텀 훅을 본격적으로 다룬다.

속도 곡선을 직접 만져 보라

레벨을 올리면 delay가 바뀌고, 이펙트가 정리 → 재등록된다. 멈춤을 누르면 delay = null이 되어 타이머 자체가 걸리지 않는다.

8장 요약

  • 건 것은 반드시 정리한다. 순서는 정리 → 새 이펙트.
  • 의존성을 빼면 낡은 클로저가 생긴다. 스위치로 쓰지 마라.
  • 타이머에서 상태를 읽어야 한다면 setX(prev => ...) 또는 dispatch.
  • 계산으로 되는 일, 이벤트 핸들러로 되는 일은 이펙트가 아니다.
  • StrictMode를 견디지 못하면 그건 그 코드의 버그다.

useRef — 렌더 밖에 두는 값

화면에 그려지지 않지만 기억해야 하는 값들. 그리고 DOM에 직접 손을 대야 할 때의 탈출구.

  • ref는 “렌더를 일으키지 않는 state”
  • DOM 노드 잡기와 포커스 관리
  • 최신 값을 붙들어 두는 패턴
  • React 밖으로 나가는 법 — 캔버스

ref는 상자다

const ref = useRef(0);
ref.current;        // 읽기
ref.current = 5;    // 쓰기 — 렌더가 일어나지 않는다

useRef(초기값)은 { current: 초기값 }이라는 객체 하나를 만들어 컴포넌트가 살아 있는 내내 같은 객체를 돌려준다.

한 줄 판단법 — “이 값이 바뀌면 화면이 달라져야 하는가?” 그렇다면 state, 아니면 ref.

둘의 차이를 눈으로

ref +1을 여러 번 눌러도 화면은 그대로다. 그다음 state +1을 누르면 그동안 쌓인 ref 값이 함께 나타난다 — 값은 이미 바뀌어 있었지만 아무도 다시 그리지 않았을 뿐이다.

테트리스에서 ref로 두는 것들

// 1) 타이머 id — 화면과 무관

// 2) 마지막 낙하 시각 — requestAnimationFrame 방식일 때

// 4) 게임판 DOM — 포커스를 주기 위해
const boxRef = useRef<HTMLDivElement>(null);

// 5) 이전 렌더의 값 — "이번에 줄이 지워졌는가" 판정
const prevLinesRef = useRef(0);
반대로 ref에 두면 안 되는 것: 점수, 판, 현재 조각, 게임 상태. 화면이 그것들을 보여 주므로 반드시 state여야 한다. “렌더가 너무 자주 일어나서”라는 이유로 state를 ref로 바꾸면, 화면이 갱신되지 않는 유령 버그가 생긴다.

9장 요약

  • ref = 렌더를 일으키지 않는 기억 상자. .current는 즉시 바뀐다.
  • 화면에 보이는 값은 state, 안 보이는 값은 ref.
  • DOM ref는 커밋 이후에 채워진다 — 이펙트나 핸들러에서만 쓴다.
  • React 19에서는 ref가 그냥 props다. forwardRef는 옛 코드용.
  • “최신 콜백은 ref, 재구독 조건은 의존성”이 useInterval의 핵심.

조각의 좌표와 회전

interface Shape { n: number; cells: readonly (readonly [number, number])[] }

export const PIECES: Record<PieceKind, Shape> = {
  I: { n: 4, cells: [[0, 1], [1, 1], [2, 1], [3, 1]] },
  J: { n: 3, cells: [[0, 0], [0, 1], [1, 1], [2, 1]] },
  L: { n: 3, cells: [[2, 0], [0, 1], [1, 1], [2, 1]] },
  O: { n: 2, cells: [[0, 0], [1, 0], [0, 1], [1, 1]] },
  S: { n: 3, cells: [[1, 0], [2, 0], [0, 1], [1, 1]] },
  T: { n: 3, cells: [[1, 0], [0, 1], [1, 1], [2, 1]] },
  Z: { n: 3, cells: [[0, 0], [1, 0], [1, 1], [2, 1]] },
};

/** n×n 상자 안에서 시계 방향 90도: (x, y) → (n-1-y, x) */
export function rotate(cells: Shape['cells'], n: number, times: number) {
  let out = cells.map((c) => [c[0], c[1]] as [number, number]);
  for (let t = 0; t < ((times % 4) + 4) % 4; t++) {
    out = out.map(([x, y]) => [n - 1 - y, x] as [number, number]);
  }
  return out;
}

/** 조각을 판 좌표계의 절대 좌표 네 개로 편다 */
export function cellsOf(p: Piece): [number, number][] {
  const s = PIECES[p.kind];
  return rotate(s.cells, s.n, p.rot).map(([x, y]) => [x + p.x, y + p.y]);
}

회전 행렬 한 줄이면 네 방향이 전부 나온다. 조각마다 네 개의 모양을 손으로 적을 필요가 없다.

export const COLS = 10, ROWS = 20;

export const emptyBoard = (): Board =>
  Array.from({ length: ROWS }, () => Array.from({ length: COLS }, () => '' as Cell));

/** 판 안이고 빈 칸이면 놓을 수 있다. 천장 위(y < 0)는 허용한다 */
export function valid(board: Board, p: Piece): boolean {
  return cellsOf(p).every(([x, y]) =>
    x >= 0 && x < COLS && y < ROWS && (y < 0 || board[y][x] === ''),
  );
}

/** 조각을 판에 굳힌 새 판을 만든다 */
export function merge(board: Board, p: Piece): Board {
  const next = board.map((row) => [...row]);
  for (const [x, y] of cellsOf(p)) if (y >= 0) next[y][x] = p.kind;
  return next;
}

/** 가득 찬 줄을 없애고 위에서 빈 줄을 채워 넣는다 */
export function clearLines(board: Board): { board: Board; cleared: number } {
  const kept = board.filter((row) => row.some((c) => c === ''));
  const cleared = ROWS - kept.length;
  const fresh = Array.from({ length: cleared }, () =>
    Array.from({ length: COLS }, () => '' as Cell));
  return { board: [...fresh, ...kept], cleared };
}
clearLines가 특히 예쁘다. “가득 찬 줄을 찾아 지우고 나머지를 내린다”가 아니라 “빈칸이 있는 줄만 남기고 위를 채운다”로 뒤집으면 인덱스 조작이 사라진다.

const KICKS = [0, -1, 1, -2, 2] as const;   // 제자리 → 왼쪽 → 오른쪽 → 더 멀리

function tryRotate(state: GameState, dir: 1 | -1 = 1): GameState {
  const a = state.active;
  const rot = (((a.rot + dir) % 4) + 4) % 4 as Piece['rot'];
  for (const dx of KICKS) {
    const candidate: Piece = { ...a, rot, x: a.x + dx };
    if (valid(state.board, candidate)) return { ...state, active: candidate };

  return state;      // 다섯 자리 모두 막혔으면 회전하지 않는다
}

7-bag 랜더마이저

const KINDS: PieceKind[] = ['I', 'J', 'L', 'O', 'S', 'T', 'Z'];

function shuffled(): PieceKind[] {
  const a = [...KINDS];
  for (let i = a.length - 1; i > 0; i--) {          // 피셔–예이츠
    const j = Math.floor(Math.random() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
}

/** 가방이 비었으면 새로 채우고 한 개를 꺼낸다 */
function pull(state: GameState): { kind: PieceKind; bag: PieceKind[] } {
  const bag = state.bag.length ? state.bag : shuffled();
  return { kind: bag[0], bag: bag.slice(1) };
}

액션 설계 원칙

  • 의도를 담아라. { type: 'SET_X', x: 4 }가 아니라 { type: 'LEFT' }. 전자는 규칙이 컴포넌트로 새어 나간다.
  • 액션은 사건이지 명령이 아니다. 같은 TICK이 상황에 따라 이동이 되기도 고정이 되기도 한다 — 그 판단은 리듀서의 몫이다.
  • 액션 하나가 화면 하나를 바꾸도록. 한 번의 dispatch가 한 번의 렌더다. 세 개를 연달아 보내면 화면이 세 번 바뀐다(배칭되긴 하지만 중간 상태가 만들어진다).
  • 데이터는 최소로. 리듀서가 계산할 수 있는 것은 액션에 담지 않는다.

규칙이 새어 나간 액션

10장 요약

  • 여러 값이 함께 바뀌면 그것은 하나의 상태다.
  • 리듀서는 (상태, 액션) → 새 상태인 순수 함수다.
  • 액션은 판별 유니온으로. default의 never가 빠뜨림을 잡는다.
  • 충돌·회전·줄삭제는 React를 모르는 순수 함수로 떼어 둔다.
  • 고스트·속도·게임오버는 상태가 아니라 계산이다.
  • dispatch는 절대 바뀌지 않는다 — 이펙트 의존성 문제가 통째로 사라진다.
  • 규칙이 React 밖에 있으므로 테스트가 함수 호출 한 줄이다.

export function useLocalStorage<T>(key: string, initial: T) {
  const [value, setValue] = useState<T>(() => {
    try {
      const raw = localStorage.getItem(key);
      return raw === null ? initial : (JSON.parse(raw) as T);
    } catch {
      return initial;             // JSON이 깨졌거나 저장소가 막혔을 때
    }
  });

  useEffect(() => {
    try { localStorage.setItem(key, JSON.stringify(value)); } catch { /* 무시 */ }
  }, [key, value]);

  return [value, setValue] as const;
}

export function useMediaQuery(query: string): boolean {
  const [matches, setMatches] = useState(
    () => typeof window !== 'undefined' && window.matchMedia(query).matches,
  );

    const mq = window.matchMedia(query);
    const onChange = () => setMatches(mq.matches);
    onChange();                                    // 마운트 시점의 값도 반영
    mq.addEventListener('change', onChange);
    return () => mq.removeEventListener('change', onChange);
  }, [query]);

  return matches;
}

  useKeyboard(boxRef, KEY_MAP, dispatch, focused);

  useEffect(() => {
    if (state.status === 'over' && state.score > best) setBest(state.score);
  }, [state.status, state.score, best, setBest]);

  return { state, dispatch, ghost, best, focused };
}
훅 합성이 클래스 상속을 대체한다. 상속과 달리 순서를 바꾸거나 일부만 골라 쓸 수 있고, 이름 충돌이 없다.

언제 훅으로 뽑는가

  • 같은 훅 조합이 두 컴포넌트에 나타났을 때. 한 번 나온 것은 그냥 둔다.
  • 컴포넌트 안에 useEffect가 셋 이상일 때. 대개 두세 가지 관심사가 섞여 있다.
  • 이름을 붙일 수 있을 때. useTetris, useInterval처럼 한 단어로 설명되면 좋은 경계다.
  • 테스트하고 싶을 때. 훅만 따로 검증할 수 있다.
거꾸로 뽑지 말아야 할 때 — 한 곳에서만 쓰는데 인자가 다섯 개 필요하고, 반환값도 다섯 개라면 그냥 컴포넌트 안에 두는 게 낫다. 파일만 늘고 읽기는 더 어려워진다.

CHAPTER 12

Context — 멀리 있는 값

물줄기를 한 단계씩 내려보내는 대신, 물길 전체에 스며들게 하는 방법. 편리한 만큼 오해도 많다.

  • props 사슬(prop drilling)이 언제 문제인가
  • 타입 안전한 Context 만들기
  • Provider 값이 바뀔 때 무슨 일이 일어나는가
  • Context가 상태 관리자가 아닌 이유

props 사슬 문제

// theme이 필요한 곳은 Cell 하나뿐인데, 세 단계가 전부 들고 날라야 한다
<Tetris theme={theme}>
  <BoardView theme={theme}>
    <Row theme={theme}>
      <Cell theme={theme} />   {/* ← 여기서만 쓴다 */}

중간 컴포넌트들은 theme에 관심이 없다. 그저 배달만 한다. 이 상태에서 theme에 필드를 하나 더하면 네 파일을 고쳐야 한다.

다만 두세 단계는 문제가 아니다. props 사슬은 명시적이고 추적하기 쉽다. Context는 그 명시성을 대가로 지불한다 — 값이 어디서 왔는지 코드만 봐서는 알 수 없게 된다.

세 조각으로 끝난다

// 1) 만들기
const ThemeContext = createContext<Theme>(defaultTheme);

// 2) 값 내려보내기
<ThemeContext.Provider value={theme}>
  <Tetris />
</ThemeContext.Provider>

// 3) 어디서든 읽기 — 중간 단계는 아무것도 몰라도 된다
function Cell({ kind }: CellProps) {
  const theme = useContext(ThemeContext);
  return <div style={{ background: theme.colors[kind] }} />;
}
React 19부터는 <ThemeContext value={theme}>처럼 .Provider를 생략할 수 있다. 옛 코드에는 .Provider가 있으니 둘 다 알아 두면 된다.
읽는 쪽은 가장 가까운 위쪽 Provider의 값을 받는다. Provider가 하나도 없으면 createContext에 준 기본값을 받는다.

직접 확인해 보라

A와 B는 theme을 모른다. props도 받지 않는다. 그런데 C가 값을 읽는다 — Provider가 위에 있기 때문이다.

타입 안전하게 만들기

이 관용구가 사실상의 표준이다. 얻는 것이 셋이다 — 가짜 기본값을 안 지어내도 되고, 타입에서 null이 사라지고, Provider를 빠뜨리면 명확한 메시지로 터진다.

Provider 만들기

interface GameApi {
  state: GameState;
  dispatch: React.Dispatch<Action>;
  ghost: Piece | null;
}

export function GameProvider({ children }: { children: React.ReactNode }) {
  const { state, dispatch, ghost } = useTetris();

  // 매 렌더 새 객체를 만들면 아래 전부가 다시 그려진다 → useMemo로 고정
  const value = useMemo(
    () => ({ state, dispatch, ghost }),
    [state, dispatch, ghost],
  );

  return <GameContext value={value}>{children}</GameContext>;
}
value={{ state, dispatch, ghost }}처럼 인라인 객체를 넘기면 Provider가 렌더될 때마다 새 참조가 되어, 값이 실제로 바뀌지 않았어도 모든 소비자가 다시 그려진다. Context에서 가장 흔한 성능 사고다.

Context가 바뀌면 무슨 일이

Provider의 value가 Object.is 기준으로 달라진다 ↓ 그 Context를 useContext로 읽는 모든 컴포넌트가 다시 렌더된다 ↓ (중간 컴포넌트는 건너뛴다 — memo가 걸려 있다면) 읽지 않는 컴포넌트는 영향받지 않는다
핵심 한계 — “값의 일부만 구독”이 안 된다. { state, dispatch }를 한 Context에 담으면, dispatch만 쓰는 버튼도 state가 바뀔 때마다 다시 그려진다. 테트리스에서는 초당 수십 번이다.

해법 — 자주 바뀌는 것과 안 바뀌는 것을 나눈다

  • 값이 undefined다 → Provider 밖에서 읽고 있다. 위의 throw 패턴을 쓰면 즉시 알 수 있다.
  • 바꿨는데 화면이 그대로다 → value가 같은 객체를 계속 가리키고 있다. 안쪽 필드만 바꿨을 가능성이 높다.

  • 2~3단계 전달이면 그냥 props가 낫다.

CHAPTER 13

성능 — memo · useMemo · useCallback

200칸을 초당 수십 번 갱신하는 화면. 여기서 최적화가 이론이 아니라 눈에 보이는 것이 된다. 다만 순서가 중요하다 — 측정이 먼저다.

  • 왜 다시 그려지는가, 세 가지 이유
  • memo가 먹히고 안 먹히는 조건
  • useMemo·useCallback을 언제만 쓰는가
  • 구조를 바꿔서 해결하는 법

먼저: 리렌더는 나쁜 게 아니다

“다시 그려진다”는 컴포넌트 함수를 다시 호출했다는 뜻이지, DOM을 다시 만들었다는 뜻이 아니다.

단계비용
컴포넌트 함수 호출매우 싸다 (객체 몇 개)
엘리먼트 트리 비교싸다
DOM 변경비싸다 — 하지만 달라진 것만 한다
레이아웃·페인트가장 비싸다
초보자가 흔히 하는 실수 — DevTools에서 “다시 그려짐” 하이라이트를 보고 놀라 모든 컴포넌트에 memo를 씌운다. memo 자체도 비용(props 비교)이 있다. 얻는 것보다 잃는 것이 많을 수 있다.

다시 그려지는 세 가지 이유

  1. 자기 state가 바뀌었다 — 필연이다. 피할 수 없다.
  2. 부모가 다시 그려졌다 — 기본 동작이다. props가 같아도 다시 그려진다.
  3. 구독 중인 Context가 바뀌었다 — 12장.
여기 없는 것 — “props가 바뀌었다”는 이유가 아니다. props가 바뀌려면 부모가 먼저 다시 그려져야 하니 결국 ②다. 이 구분이 최적화의 출발점이다.
function Parent() {
  const [n, setN] = useState(0);
  return (
    <>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <Child text="고정" />   {/* props가 늘 같아도 매번 다시 그려진다 */}
    </>
  );
}

memo — 부모 때문에 그려지는 것을 막는다

import { memo } from 'react';

export const Cell = memo(function Cell({ kind, ghost }: CellProps) {
  return <div className={classFor(kind, ghost)} />;
});

memo는 이전 props와 새 props를 얕게 비교해 같으면 함수 호출 자체를 건너뛴다. 자기 state가 바뀌거나 Context가 바뀌면 여전히 다시 그려진다.

무관한 state +1을 눌러 보라. 보통 컴포넌트의 렌더 횟수만 오른다. props 바꾸기를 누르면 둘 다 오른다 — memo는 “props가 같을 때만” 막는다.

memo가 안 먹히는 이유 ①

매 렌더 새 객체

<Cell kind={kind} style={{ width: 20 }} />
//                      ^^^^^^^^^^^^^^ 값은 같지만 참조가 매번 다르다

매 렌더 새 함수

<Cell kind={kind} onClick={() => select(x, y)} />

매 렌더 새 배열

<Board rows={board.map((r) => [...r])} />

memo는 Object.is로 비교한다. 내용이 같아도 참조가 다르면 “바뀌었다”고 본다. 그래서 memo를 씌운 뒤에는 부모 쪽 props를 함께 손봐야 한다.

문제해법
객체·배열 propsuseMemo로 고정하거나, 원시값으로 쪼개서 넘긴다
함수 propsuseCallback 또는 dispatch를 그대로 넘긴다
childrenchildren은 매번 새 엘리먼트다 — memo가 거의 안 먹힌다

원시값으로 쪼개는 것이 최선이다

객체 하나를 통째로

<Cell cell={{ kind, ghost }} />      // 매번 새 객체 → memo 무력화

원시값 두 개로

<Cell kind={kind} ghost={ghost} />   // 문자열·불리언 비교 → 안정적

테트리스의 Cell이 kind: string과 ghost: boolean만 받는 것은 우연이 아니다. props를 원시값으로 유지하면 memo가 저절로 잘 동작한다.

이것은 성능 기법이기 이전에 좋은 설계다. “이 컴포넌트가 정말 필요한 최소한의 정보는 무엇인가”를 묻게 만든다.

useCallback

// 렌더마다 새 함수가 만들어진다
const handleSelect = (x: number, y: number) => dispatch({ type: 'SELECT', x, y });

// 정체성을 유지한다 — 의존성이 같으면 같은 함수를 돌려준다
const handleSelect = useCallback(
  (x: number, y: number) => dispatch({ type: 'SELECT', x, y }),

  • 리렌더 ≠ DOM 갱신. 함수 호출은 싸다.
  • 다시 그려지는 이유는 셋 — 자기 state, 부모, Context.

import type { PieceKind, Piece, Rot } from './types';

type Coord = readonly [number, number];
interface Shape { readonly n: number; readonly cells: readonly Coord[] }

export const PIECES: Record<PieceKind, Shape> = {
  I: { n: 4, cells: [[0, 1], [1, 1], [2, 1], [3, 1]] },
  J: { n: 3, cells: [[0, 0], [0, 1], [1, 1], [2, 1]] },
  L: { n: 3, cells: [[2, 0], [0, 1], [1, 1], [2, 1]] },
  O: { n: 2, cells: [[0, 0], [1, 0], [0, 1], [1, 1]] },
  S: { n: 3, cells: [[1, 0], [2, 0], [0, 1], [1, 1]] },
  T: { n: 3, cells: [[1, 0], [0, 1], [1, 1], [2, 1]] },
  Z: { n: 3, cells: [[0, 0], [1, 0], [1, 1], [2, 1]] },
};

export const KINDS = Object.keys(PIECES) as PieceKind[];

/** n×n 상자 안의 시계 방향 90도 회전을 times번 */
export function rotate(cells: readonly Coord[], n: number, times: number): Coord[] {
  let out: Coord[] = cells.map(([x, y]) => [x, y]);
  for (let t = 0; t < ((times % 4) + 4) % 4; t++) {
    out = out.map(([x, y]) => [n - 1 - y, x] as Coord);
  }
  return out;
}

/** 조각을 판 좌표계의 절대 좌표 네 개로 */
export function cellsOf(p: Piece): Coord[] {
  const s = PIECES[p.kind];
  return rotate(s.cells, s.n, p.rot).map(([x, y]) => [x + p.x, y + p.y] as Coord);
}

/** 새 조각을 천장 위에 놓는다 */
export function spawn(kind: PieceKind): Piece {
  return { kind, rot: 0 as Rot, x: kind === 'O' ? 4 : 3, y: -1 };
}

import type { Board, Cell, Piece } from './types';
import { cellsOf } from './pieces';

export const COLS = 10;
export const ROWS = 20;

export const emptyBoard = (): Board =>
  Array.from({ length: ROWS }, () =>
    Array.from({ length: COLS }, () => '' as Cell));

export function valid(board: Board, p: Piece): boolean {
  return cellsOf(p).every(([x, y]) =>
    x >= 0 && x < COLS && y < ROWS && (y < 0 || board[y][x] === ''));
}

export function merge(board: Board, p: Piece): Board {
  const next = board.map((row) => [...row]);
  for (const [x, y] of cellsOf(p)) if (y >= 0) next[y][x] = p.kind;
  return next;
}

export function clearLines(board: Board): { board: Board; cleared: number } {
  const kept = board.filter((row) => row.some((c) => c === ''));
  const cleared = ROWS - kept.length;
  const fresh = Array.from({ length: cleared }, () =>
    Array.from({ length: COLS }, () => '' as Cell));
  return { board: [...fresh, ...kept], cleared };
}

/** 지금 자리에서 바닥까지 내린 위치 (고스트 · 하드드롭 공용) */
export function drop(board: Board, piece: Piece): Piece {
  let p = piece;
  while (valid(board, { ...p, y: p.y + 1 })) p = { ...p, y: p.y + 1 };
  return p;
}

import type { Action, GameState, Piece, PieceKind } from './types';
import { KINDS, cellsOf, spawn } from './pieces';
import { clearLines, drop, emptyBoard, merge, valid } from './board';
import { SCORE, levelOf } from './level';

function shuffled(): PieceKind[] {
  const a = [...KINDS];
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
}

function pull(bag: PieceKind[]): { kind: PieceKind; bag: PieceKind[] } {
  const b = bag.length ? bag : shuffled();
  return { kind: b[0], bag: b.slice(1) };
}

export function initGame(): GameState {
  const first = pull([]);
  const second = pull(first.bag);
  return {
    board: emptyBoard(), active: spawn(first.kind), nextKind: second.kind,
    bag: second.bag, hold: null, canHold: true,
    score: 0, lines: 0, level: 1, status: 'ready',
  };
}

game/reducer.ts ② — 전이 함수

function lock(state: GameState, piece: Piece): GameState {
  const { board, cleared } = clearLines(merge(state.board, piece));
  const lines = state.lines + cleared;
  const { kind, bag } = pull(state.bag);
  const active = spawn(state.nextKind);
  return {
    ...state,
    board, active, nextKind: kind, bag,
    score: state.score + SCORE[cleared] * state.level,
    lines, level: levelOf(lines), canHold: true,
    status: valid(board, active) ? 'playing' : 'over',
  };
}

function move(state: GameState, dx: number, dy: number): GameState {
  const next: Piece = { ...state.active, x: state.active.x + dx, y: state.active.y + dy };
  if (valid(state.board, next)) return { ...state, active: next };
  return dy > 0 ? lock(state, state.active) : state;
}

const KICKS = [0, -1, 1, -2, 2] as const;

function tryRotate(state: GameState, dir: 1 | -1): GameState {
  const a = state.active;
  const rot = ((((a.rot + dir) % 4) + 4) % 4) as Piece['rot'];
  for (const dx of KICKS) {
    const c: Piece = { ...a, rot, x: a.x + dx };
    if (valid(state.board, c)) return { ...state, active: c };
  }
  return state;
}

game/reducer.ts ③ — 리듀서

export function gameReducer(state: GameState, action: Action): GameState {
  switch (action.type) {
    case 'START':
      return { ...initGame(), status: 'playing' };

    case 'PAUSE':
      if (state.status === 'playing') return { ...state, status: 'paused' };
      if (state.status === 'paused') return { ...state, status: 'playing' };
      return state;

    case 'LEFT':
      return state.status === 'playing' ? move(state, -1, 0) : state;
    case 'RIGHT':
      return state.status === 'playing' ? move(state, 1, 0) : state;
    case 'TICK':
    case 'SOFT':
      return state.status === 'playing' ? move(state, 0, 1) : state;
    case 'ROTATE':
      return state.status === 'playing' ? tryRotate(state, action.dir ?? 1) : state;

    case 'HARD': {
      if (state.status !== 'playing') return state;
      const landed = drop(state.board, state.active);
      const bonus = (landed.y - state.active.y) * 2;
      const next = lock(state, landed);
      return { ...next, score: next.score + bonus };
    }

    case 'HOLD': {
      if (state.status !== 'playing' || !state.canHold) return state;
      if (state.hold === null) {
        const { kind, bag } = pull(state.bag);
        return { ...state, hold: state.active.kind, active: spawn(state.nextKind),
                 nextKind: kind, bag, canHold: false };
      }
      return { ...state, hold: state.active.kind,
               active: spawn(state.hold), canHold: false };
    }

    default: {
      const _never: never = action;   // 액션을 추가하면 여기서 잡힌다
      return state;
    }
  }
}

import { useEffect, useRef } from 'react';

/**
 * delay가 null이면 타이머를 걸지 않는다(일시정지).
 * 콜백은 매 렌더 최신으로 갈아 끼우되, 타이머는 delay가 바뀔 때만 다시 건다.
 */
export function useInterval(callback: () => void, delay: number | null) {
  const saved = useRef(callback);

  useEffect(() => { saved.current = callback; });

  useEffect(() => {
    if (delay === null) return;
    const id = window.setInterval(() => saved.current(), delay);
    return () => window.clearInterval(id);
  }, [delay]);
}

15장 요약

무엇을 테스트하지 말까

  • state 값 자체 — expect(state.score).toBe(100)은 컴포넌트 테스트가 아니라 리듀서 테스트에서 할 일이다.
  • CSS 클래스 이름 — 스타일을 바꾸면 깨진다. 눈에 보이는 결과를 검증하라.
  • 구현 세부 — “useEffect가 두 번 불렸는가”는 사용자와 무관하다.
  • 서드파티 라이브러리 — 그쪽이 이미 테스트했다.
  • 얻는 것 없는 스냅샷 — 200칸짜리 DOM 스냅샷은 아무도 읽지 않고 매번 갱신만 한다.
좋은 기준 — “이 테스트가 깨졌을 때 사용자에게 실제로 문제가 있는가?” 아니라면 그 테스트는 유지 비용만 만든다.

React 내부 — 재조정과 파이버

이 문서의 데모를 돌리는 350줄짜리 미니 React를 열어 본다. 진짜 React와 다른 점도 함께 짚는다.

  • 엘리먼트에서 DOM까지 — 렌더 단계와 커밋 단계
  • 훅이 저장되는 방식
  • 재조정 알고리즘의 실제 코드
  • 동시성 렌더링이 바꾼 것

세 가지 물건

무엇수명
엘리먼트{ type, props, key } — 화면의 설명서렌더 한 번. 즉시 버려진다
파이버(인스턴스)엘리먼트에 대응하는 작업 단위. 훅·이전 상태·DOM 참조를 갖는다컴포넌트가 트리에 있는 동안
DOM 노드브라우저의 진짜 물건파이버가 살아 있는 동안
컴포넌트 함수 호출 → 엘리먼트 트리 (새로 만든 설명서) ↓ 재조정 — 옛 파이버 트리와 비교 파이버 트리 갱신 + 변경 목록 작성 ↓ 커밋 DOM에 변경 목록 반영 → 이펙트 실행
state가 “컴포넌트에 붙어 있다”는 말은 정확히는 파이버에 붙어 있다는 뜻이다. 파이버가 버려지면(언마운트) state도 사라진다. 5장의 key 기법이 통하는 이유다.

재조정의 규칙

  1. 같은 위치, 같은 type, 같은 key → 파이버를 재사용한다. state·훅이 유지된다. props만 갈아 끼운다.
  2. type이나 key가 다르다 → 옛 서브트리를 통째로 버리고 새로 만든다. state가 사라진다.
  3. 형제들 사이에서는 key로 짝을 찾는다. key가 없으면 순서(인덱스)로 짝짓는다.
// 같은 자리에 다른 컴포넌트를 두면 state가 사라진다
{mode === 'game' ? <Tetris /> : <Settings />}
// mode가 바뀌면 Tetris의 파이버가 통째로 버려진다 → 게임이 초기화된다

// 같은 컴포넌트라면 유지된다
{mode === 'game' ? <Tetris theme="dark" /> : <Tetris theme="light" />}
// 위치·type이 같다 → 같은 파이버 → 판이 그대로다
두 번째 예가 반직관적이다. “다른 분기니까 다른 컴포넌트”가 아니라, React는 트리에서의 위치로 판단한다. 판을 초기화하고 싶다면 key를 다르게 줘야 한다.

휴리스틱이라는 것

두 트리의 최소 차이를 정확히 구하는 알고리즘은 O(n³)이다. 1000개 노드면 10억 번이다. React는 두 가지 가정으로 이것을 O(n)으로 낮춘다.

  • 타입이 다르면 트리도 완전히 다르다 — 그러니 비교하지 말고 버린다.
  • 개발자가 key로 힌트를 준다 — 어느 자식이 어느 자식인지는 사람이 안다.
이 두 가정 덕분에 실용적인 속도가 나온다. 그리고 두 번째 가정이 key를 “선택 사항”이 아니라 알고리즘의 입력으로 만든다. 7장에서 key가 정확성 문제라고 한 이유다.

function useReducer(reducer, initial, init) {
  const inst = current;
  const s = slot(() => ({ v: init ? init(initial) : initial }));
  s.r = reducer;
  if (!s.d) {
    s.d = (action) => {                      // dispatch — 한 번만 만든다
      const next = s.r ? s.r(s.v, action)
                       : (typeof action === 'function' ? action(s.v) : action);

      s.v = next;
      inst.dirty = true;

}

function schedule(root) {

  root.pending = true;

    render(root);
  });
}

function patch(parentDom, inst, vnode) {
  // 규칙 1: type이나 key가 다르면 통째로 갈아 치운다
  if (inst.vnode.type !== vnode.type || inst.key !== vnode.key) {
    const fresh = mount(vnode, inst.root);
    parentDom.replaceChild(fresh.dom, inst.dom);
    unmount(inst);                       // 정리 함수들이 여기서 돈다
    return fresh;
  }
  // 컴포넌트면: memo 검사 후 다시 호출하고, 그 결과를 이어서 patch
  if (typeof vnode.type === 'function') {
    const skip = vnode.type._memo && !inst.dirty
                 && vnode.type._memo(inst.vnode.props, vnode.props);
    inst.vnode = vnode;
    if (skip) return inst;               // ← memo가 하는 일 전부
    inst.dirty = false;
    inst.child = patch(parentDom, inst.child, renderComponent(inst));
    inst.dom = inst.child.dom;
    return inst;
  }
  // 호스트 엘리먼트면: 자식 먼저, 그다음 속성
  inst.children = patchChildren(inst.dom, inst.children, vnode.children);
  setProps(inst.dom, inst.vnode.props, vnode.props);
  inst.vnode = vnode;
  return inst;
}

function patchChildren(dom, olds, news) {
  const byKey = new Map();
  olds.forEach((o, i) => { if (o.key !== null) byKey.set(o.key + '|' + name(o), i); });

  const out = news.map((v, i) => {
    // key가 있으면 key로 짝을 찾고, 없으면 같은 타입의 다음 것과 짝짓는다
    const oi = v.key !== null ? byKey.get(v.key + '|' + name(v.type)) : nextSameType(i);
    return oi !== undefined ? patch(dom, olds[oi], v) : mount(v);
  });

  // 짝을 못 찾은 옛 인스턴스는 제거 (여기서 정리 함수가 돈다)
  olds.forEach((o) => { if (!used.has(o)) { dom.removeChild(o.dom); unmount(o); } });

  // 순서 맞추기 — 이미 제자리인 노드는 건드리지 않는다(포커스·입력 보존)
  let ref = null;
  for (let i = out.length - 1; i >= 0; i--) {
    if (out[i].dom.nextSibling !== ref) dom.insertBefore(out[i].dom, ref);
    ref = out[i].dom;
  }
  return out;
}

17장 요약

  • 엘리먼트는 버려지고, 파이버는 남고, DOM은 최소한만 바뀐다.
  • 재조정은 위치 + type + key로 판단하는 O(n) 휴리스틱이다.
  • 훅은 파이버에 붙은 배열의 인덱스로 구분된다.
  • 배칭은 “이미 예약돼 있으면 무시”하는 다섯 줄이다.
  • memo는 재조정에서 skip 한 줄이다.
  • 동시성 렌더링이 가능한 이유는 컴포넌트가 순수하기 때문이다.

React는 화면만 담당한다. 나머지를 언제 무엇으로 채울지에 대한 지도.

  • 필요해지기 전에는 더하지 않는다
  • 영역별 표준 선택지
  • 메타프레임워크를 고려할 시점
  • 다음 학습 순서

더하는 순서

0단계 Vite + TypeScript — 이 교재의 전부 ↓ 화면이 여러 개가 되면 1단계 라우팅 ↓ 서버에서 데이터를 가져오기 시작하면 2단계 서버 상태 관리 ↓ 여러 화면이 같은 클라이언트 상태를 보면 3단계 전역 상태 ↓ SEO·초기 로딩이 중요해지면 4단계 메타프레임워크(Next.js 등)
거꾸로 가는 사람이 많다. 튜토리얼을 보고 Next.js + Redux + Tailwind로 시작해 무엇이 무엇을 해결하는지 모르는 채 코드를 쓴다. 필요를 먼저 겪고 도구를 더해라.

const schema = z.object({

function SettingsForm() {
  const { register, handleSubmit, formState: { errors } } =
    useForm<FormValues>({ resolver: zodResolver(schema) });

  return (
    <form onSubmit={handleSubmit((v) => start(v))}>
      <input {...register('name')} />
      {errors.name && <p>{errors.name.message}</p>}
      <button type="submit">시작</button>
    </form>
  );
}
React Hook Form은 기본적으로 비제어(6장)로 동작해 타이핑마다 리렌더가 없다. 입력이 스무 개 넘는 폼에서 체감 차이가 크다. 그리고 Zod 스키마 하나가 검증 + 타입 + 서버 공유를 모두 담당한다.

접근성 — 게임에도 해당된다

  • 키보드만으로 전부 조작 가능한가. 테트리스는 원래 그렇다. 시작 버튼도 Tab으로 닿아야 한다.
  • 포커스가 보이는가. outline: none만 하고 대체 표시를 안 두면 키보드 사용자가 길을 잃는다.
  • 색만으로 정보를 전달하지 않는가. 조각 색 외에 모양으로도 구분된다 — 이 교재의 디자인 원칙과 같다.
  • 상태 변화를 알리는가. 점수 영역에 aria-live="polite"를 두면 스크린 리더가 읽는다.
  • 움직임을 줄일 수 있는가. prefers-reduced-motion을 존중한다.

18장 요약

  • 필요를 겪은 뒤에 도구를 더한다. 순서는 라우팅 → 서버 상태 → 전역 상태 → 메타프레임워크.
  • 서버 상태와 클라이언트 상태는 다른 문제다. 캐시가 필요하면 전용 도구를 써라.
  • 전역 상태 라이브러리가 파는 것은 대부분 부분 구독이다.
  • 레이아웃은 CSS에게. JS로 크기를 계산하기 시작하면 되돌리기 어렵다.
  • Next.js는 “요즘 다 쓰니까”가 아니라 SEO·초기 로딩이 중요할 때 고른다.
  • 규칙을 화면에서 분리해 두면 렌더러가 바뀌어도 살아남는다.

  • 이펙트에 정리 함수가 있는가. 두 번 돌려도 괜찮은가
  • 의존성 배열을 린트 무시로 넘기지 않았는가
  • 이벤트로 될 일을 이펙트로 하고 있지 않은가
  • 리스트에 안정적인 key가 있는가
  • {n && ...} 형태로 0을 흘리고 있지 않은가
  • 제어 컴포넌트에 value와 onChange가 한 쌍인가
  • 리듀서가 순수한가. 변화 없으면 같은 객체를 반환하는가
  • 유니온 state에 제네릭을 적었는가 (useState<Status>)
  • as와 !가 한 함수 안에 갇혀 있는가
  • 키보드만으로 조작 가능한가. 포커스가 보이는가
