전역 상태 — thread_local! + RefCell

왜 static mut 이 아닌가 — 2024 에디션

Go·Java 라면 그냥 전역 변수를 씁니다. Rust 에서 static mut 은 모든 접근이 unsafe 이고, 2024 에디션부터는 참조를 만드는 것 자체가 기본 오류입니다. 스레드 둘이 동시에 고치면 정의되지 않은 동작이기 때문입니다.

RefCell — 빌림 검사를 실행 시점으로

조각하는 일
thread_local!스레드마다 따로인 전역. WASM 은 스레드가 하나라 사실상 전역 하나
RefCell<T>&/&mut 규칙을 실행 중에 센다. 겹치면 패닉
Option<App>tt_init 전에는 None
with_borrow_mut(|app| ...)잠깐 &mut 로 빌려 클로저를 돌리고 돌려준다
const { RefCell::new(None) }초기값이 상수식이라 지연 초기화 검사가 빠진다
with_app 의 서명뜻
fn with_app<R>(default: R, f: impl FnOnce(&mut App) -> R) -> R상태가 있으면 f 의 결과, 없으면 default. 제네릭 R 이라 u32·()·포인터 어느 것이든

내보내기 ① — tt_init

#[unsafe(no_mangle)] 와 extern "C"

조각뜻
no_mangle이름을 tt_init 그대로 내보낸다(보통은 _ZN...h3f4 처럼 꾸며진다)
unsafe(...)2024 에디션부터 필수. 같은 이름의 심볼이 둘이면 링커가 아무거나 고를 수 있어 "안전하지 않은 속성"이 됐다
extern "C"C 호출 규약. WASM 에서는 인자·반환이 i32/i64/f32/f64 로 내려간다

u64 씨앗을 32비트 둘로

Rust (tt_init)
let seed = (seed_hi as u64) << 32 | seed_lo as u64;
JS (tetris.js)
const lo = seed >>> 0,
      hi = Math.floor(seed / 2 ** 32) >>> 0;

WASM 의 i64 는 JS 에서 BigInt 로 와야 합니다. JS 의 Number 는 2⁵³ 까지만 정확해서 Date.now() 는 괜찮지만 일반 u64 는 깨집니다. 32비트 둘로 쪼개면 양쪽 다 평범한 정수로 끝납니다.

FFI 경계 밖으로 패닉을 내보내면

extern "C" 함수는 되감을 수 없다 — 패닉이 경계를 넘으려 하면 catch_unwind 로도 못 잡고 프로세스가 끝납니다(종료 코드 134, SIGABRT). 그래서 tt_init 은 잘못된 cell 에 패닉하는 Frame::new 를 부르기 전에 범위를 검사하고 0 을 돌려줍니다. 브라우저라면 RuntimeError: unreachable 로 인스턴스가 죽습니다.

WASM 함수를 네이티브에서 시험하기

rlib 덕분 — extern "C" 함수도 Rust 에서는 보통 함수처럼 부를 수 있습니다. 시험은 스레드마다 돌고 thread_local 이라, 시험끼리 전역 상태가 섞이지 않습니다(파일 첫 주석).
