성능 측정과 해석

같은 정적 장면을 두 가지 방식으로 그려 호출 수와 시간을 기록합니다. 측정 조건과 제외한 비용을 확인하고 결과를 해석합니다.

비교 질문

탄환 1000개를 같은 위치에 그릴 때 개별 Mesh와 InstancedMesh의 호출 수와 완료 대기 시간이 어떻게 달라질까요? 이번 실험은 정적 장면의 그리기 비용을 다루며 게임 FPS를 측정하지 않습니다.

three-ts/performance/benchmark.ts

같은 기하

두 경로 모두 반지름 3, 분할 수 12인 CircleGeometry 하나를 공유합니다. 인스턴스 쪽만 단순한 도형을 쓰면 객체 묶음 방식과 도형 복잡도가 동시에 달라져 비교하기 어렵습니다.

three-ts/performance/benchmark.ts

같은 재질

같은 색의 불투명 MeshBasicMaterial 하나를 공유합니다. 조명과 투명 정렬을 추가하지 않은 조건입니다. 재질을 공유해도 개별 Mesh의 그리기 호출이 자동으로 하나가 되는 것은 아닙니다.

three-ts/performance/benchmark.ts

같은 배치

인덱스를 64열 격자의 좌표로 바꿉니다. 두 경로에서 같은 식을 쓰고 화면 밖 컬링을 모두 끕니다. 화면 크기는 480×640, 픽셀 비율은 1로 고정하여 그릴 픽셀 수를 맞춥니다.

three-ts/performance/benchmark.ts

개별 Mesh

개별 경로는 탄환마다 Mesh를 생성하고 같은 기하와 재질을 연결합니다. 각 객체에 위치를 지정해 장면에 추가합니다. 이 객체 생성 반복문은 측정 타이머보다 앞에 있습니다.

three-ts/performance/benchmark.ts

인스턴스

인스턴스 경로는 같은 도형을 여러 변환 행렬로 배치합니다. count는 실제 그릴 개수입니다. 0개 실험에서도 할당 용량을 최소 1로 두되 count를 0으로 설정하여 아무 탄환도 그리지 않습니다.

three-ts/performance/benchmark.ts

측정 전 생성

장면·배치·행렬 기록을 먼저 끝내고 표본 반복을 시작합니다. 따라서 이 결과로 생성 속도나 매 프레임 행렬 갱신 비용을 판단할 수 없습니다. 첫 업로드와 셰이더 준비는 준비 실행에서 일어납니다.

three-ts/performance/benchmark.ts

준비 실행

각 경로에서 처음 두 번은 렌더링하되 표본 배열에 넣지 않습니다. 최초 컴파일과 버퍼 생성의 영향을 줄이는 절차입니다. 준비 두 번으로 모든 실행 환경이 완전히 안정된다고 보장하지는 않습니다.

three-ts/performance/benchmark.ts

완료 동기화

시작 전에 gl.finish로 앞선 명령을 기다리고 타이머를 켭니다. render 뒤에도 gl.finish를 호출하여 제출한 작업 완료까지 기다립니다. 이 대기 방식은 실제 게임의 비동기 프레임 루프와 다릅니다.

three-ts/performance/benchmark.ts

표본 배열

준비 실행 뒤의 경과 시간을 실행 순서대로 보관합니다. 브라우저 타이머 해상도 때문에 작은 표본이 0으로 나올 수 있으며 무한한 속도를 뜻하지 않습니다. 중앙값과 함께 원시 표본의 변동을 살펴봅니다.

three-ts/performance/benchmark.ts

중앙값

원시 표본을 복사해 숫자 오름차순으로 정렬한 뒤 가운데 값을 고릅니다. 짝수 개면 중앙 두 값의 평균입니다. 원본 배열을 보존하므로 준비 이후 표본이 어떤 순서로 달라졌는지도 확인할 수 있습니다.

three-ts/performance/benchmark.ts

짝수 중앙값

표본이 두 개이고 값이 2ms와 6ms라면 중앙값은 4ms입니다. 배열 가운데 한 값만 고르면 표본 수의 짝홀에 따라 의미가 달라집니다. 측정 도구 테스트는 두 표본의 평균과 보고된 중앙값이 같은지 검사합니다.

three-ts/performance/benchmark.ts

호출 수

renderer.info.render.calls는 직전 렌더의 그리기 호출 수입니다. 같은 원 7개를 그린 검사에서 개별 Mesh는 7회, 인스턴스는 1회였습니다. 호출 수가 줄어든 비율을 화면 시간의 개선 비율로 해석하지 않습니다.

three-ts/performance/benchmark.ts

CPU 소프트웨어 드라이버

PRoot 실행 명령은 Xvfb와 Mesa 소프트웨어 렌더링을 사용합니다. 이 환경에서는 CPU가 그래픽 작업도 수행합니다. 출력된 드라이버 이름을 확인하고 다른 기기의 하드웨어 GPU에서도 같은 시간이 나올 것이라고 기대하지 않습니다.

three-ts/commands.sh

환경 기록

Node 버전·CPU 아키텍처·Chromium 버전과 WebGL 드라이버 이름을 함께 남깁니다. 브라우저의 사용자 에이전트 문자열만으로 실제 머신 아키텍처를 단정하지 않습니다. 비교할 때는 표본과 환경을 한 묶음으로 보관합니다.

three-ts/profile.mjs

프레임 속도와 구분

실험은 정적 장면 한 번의 render와 완료 대기 시간을 잽니다. 실제 게임 프레임에는 입력·업데이트·충돌·표시 데이터 갱신도 들어갑니다. 여기서 얻은 밀리초의 역수를 게임 FPS라고 소개하지 않습니다.

three-ts/performance/benchmark.ts

브라우저 시작 제외

Chromium 시작, 페이지 읽기와 번들 실행은 브라우저 안의 타이머보다 앞에 있습니다. CLI 명령이 끝날 때까지의 전체 대기 시간과 보고서의 표본 시간은 서로 다릅니다. 시작 속도가 궁금하면 별도 구간을 측정해야 합니다.

three-ts/profile.mjs

정적 장면 한계

행렬은 장면 구성 중 한 번 기록하고 측정 중에는 바꾸지 않습니다. 각 경로는 준비 두 번 뒤 같은 장면을 반복합니다. 개별 Mesh를 먼저 측정하므로 실행 순서와 환경 변동의 영향도 남으며 작은 시간 차이를 일반화하지 않습니다.

three-ts/performance/benchmark.ts

충돌 비용 제외

측정 페이지에는 게임 상태와 충돌 반복문이 없습니다. 탄환 개수만 늘려 그리기 비용을 비교합니다. 인스턴스로 화면 호출을 줄여도 게임 로직이 검사하는 충돌 쌍의 개수가 함께 줄어드는 것은 아닙니다.

three-ts/performance/benchmark.ts

전송과 드로우

게임에서는 탄환을 보간하고 행렬·색을 기록한 뒤 GPU 속성에 갱신을 알립니다. 정적 실험은 준비 이후 이런 변경이 없으므로 실제 게임의 반복 전송 비용을 포함하지 않습니다. 그리기 호출 수와 갱신할 데이터 양을 따로 살핍니다.

three-ts/lv7/render.ts

활성 범위

실제 렌더러는 활성 탄환 수에 행렬 16성분, 색 3성분을 곱해 갱신 범위를 정합니다. 범위 단위는 바이트가 아니라 배열 성분입니다. 활성 탄환이 영이면 갱신을 알리지 않으며 최초 버퍼 생성과 후속 부분 갱신도 구분합니다.

three-ts/lv7/render.ts

HUD 업로드

점수·목숨·보스 체력·단계·파워·폭탄을 문자열 키로 비교합니다. 값이 같으면 HUD를 다시 그리지 않고, 바뀌면 캔버스를 갱신해 텍스처 업로드를 알립니다. 이 캐시의 효과는 정적 원 탄환 실험으로 측정한 값이 아닙니다.

three-ts/lv7/render.ts

투명 정렬

이번 실험의 원은 불투명 재질입니다. 투명 효과를 추가하면 겹침과 그리는 순서를 별도로 확인해야 합니다. 하나의 InstancedMesh 안에 있는 탄환이 각각 독립 객체처럼 자동 정렬된다고 가정하지 말고 실제 겹친 화면을 검사합니다.

three-ts/performance/benchmark.ts

컬링

이번 비교는 두 경로 모두 frustumCulled를 꺼서 보이지 않는 객체 제거의 영향을 통제합니다. 게임에서 컬링을 켜면 인스턴스 묶음의 경계가 이동한 탄환을 포함하는지 확인해야 합니다. 호출 수와 함께 화면 가장자리의 누락도 검사합니다.

three-ts/performance/benchmark.ts

기하 재사용

탄환마다 새 기하를 만들지 않고 하나의 CircleGeometry를 공유합니다. 공유와 인스턴싱은 별개 선택입니다. 두 비교 경로가 같은 기하를 사용하므로 결과에 기하 생성 비용이 섞이지 않습니다. 생성 속도는 다른 구간에서 측정해야 합니다.

three-ts/performance/benchmark.ts

텍스처 재사용

게임의 우주선 이미지는 캔버스에 그린 뒤 CanvasTexture로 만듭니다. 이런 텍스처는 초기화 때 만들고 프레임마다 재생성하지 않습니다. 정적 원 실험에는 이미지 텍스처가 없으므로 텍스처를 쓰는 게임 전체의 비용을 대표하지 않습니다.

three-ts/lv7/render.ts

해제

게임 렌더러를 폐기할 때 공유 기하·재질·텍스처와 인스턴스 자원을 해제합니다. 장면에서 객체를 지우는 일과 GPU 자원을 해제하는 일은 구분해야 합니다. 다른 객체가 계속 쓰는 공유 자원은 마지막 사용이 끝난 뒤 해제합니다.

three-ts/lv7/render.ts

컨텍스트 손실

측정 중 WebGL 컨텍스트가 손실되면 시간을 정상 결과로 반환하지 않고 오류를 냅니다. 드라이버가 중단된 뒤의 짧은 시간을 성능 개선으로 오해하지 않게 합니다. 이 도구는 자동 복구를 구현하지 않으며 실행 환경을 확인한 뒤 다시 시작합니다.

three-ts/performance/benchmark.ts

셰이더 오류

브라우저의 pageerror와 오류 수준 콘솔 메시지를 수집합니다. 셰이더 컴파일 오류가 있으면 보고서 대신 오류를 반환합니다. 그림이 누락되었는데 호출 시간이 작다는 이유로 성공이라고 판단하지 않도록 화면 검사와 함께 사용합니다.

three-ts/profile.mjs

검사 순서

strict 빌드로 타입을 확인하고 실제 WebGL에서 오류와 호출 수를 검사한 뒤 표본을 해석합니다. 성능 수정이 게임 규칙을 바꾸지 않았는지는 기존 pygame 기준 기록 비교로 따로 확인합니다. 이번 측정은 렌더링만 다루므로 게임 기준 검사를 대신하지 않습니다.

three-ts/commands.sh

three-ts/build.mjs

다음 트랙에서는 C++ 로직과 JavaScript 어댑터 사이의 메모리·호출 규약을 배웁니다. 같은 입력과 체크포인트를 유지하며 언어 경계를 추가합니다. 이번 정적 WebGL 측정만으로 C++와 JavaScript의 게임 실행 속도를 비교하지 않습니다.

성능 측정 · 이해 확인

1000개 탄환의 그리기 호출이 1000회에서 1회로 줄면 게임 FPS도 1000배가 될까요?

호출 수는 시간의 비율이 아닙니다. 정적 실험은 게임 로직과 매 프레임 데이터 갱신을 제외하며, 소프트웨어 드라이버와 완료 대기 방식도 실제 플레이 환경과 다릅니다.
