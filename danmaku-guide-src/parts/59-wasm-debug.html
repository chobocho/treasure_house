파일·모듈·ABI·실행·메모리·화면의 경계를 실제 오류와 보고서로 확인합니다.

바이너리부터 확인하기

화면이 나오지 않으면 먼저 생성된 wasm 파일을 읽고 컴파일할 수 있는지 확인합니다. 진단 도구는 파일 크기·가져오기·내보내기·메모리·ABI를 실제 모듈에서 읽습니다. 소스에 함수가 있어도 실제 내보내기에 없을 수 있습니다.

컴파일 오류 구분

잘린 바이트나 잘못된 wasm 형식은 WebAssembly.compile에서 CompileError가 됩니다. 로딩 예제의 오류 표시와 별개로 먼저 파일 경로와 빌드 산출물을 확인합니다. 진단 CLI는 실패 이름과 메시지를 표준 오류에 남깁니다.

cpp-wasm/inspect.mjs

가져오기와 내보내기

직접 빌드한 게임은 외부 가져오기가 없습니다. 진단 도구는 가져오기가 있으면 목록만 확인하고 임의의 함수를 연결하지 않습니다. dm_step과 memory가 실제 내보내기에 있는지 확인한 뒤 JS의 호출 이름을 맞춥니다.

cpp-wasm/inspect.mjs

ABI와 메모리 보고서

ABI 버전은 1이고 게임 메모리는 1MiB입니다. 이 값은 실행한 빌드의 보고서이며 다른 모듈의 일반 조건은 아닙니다. 내보낸 memory와 ABI 함수를 실제로 읽어 문서와 코드의 약속이 같은지 확인합니다.

cpp-wasm/inspect.mjs

명시적인 실행 트랩

진단 전용 dm_trap은 의도적으로 unreachable을 실행합니다. 이 함수는 게임에 넣지 않습니다. 바이트 컴파일은 성공했어도 함수를 호출하는 도중 RuntimeError가 생길 수 있음을 실제로 확인합니다.

cpp-wasm/traps.cpp

선형 메모리 범위 밖 읽기

진단 모듈의 dm_read에 메모리 밖 주소를 주면 실행 중 트랩이 됩니다. 게임 어댑터는 이런 호출에 의존하지 않고 읽기 전에 주소·정렬·배열 끝을 검사합니다. 논리 배열 범위와 wasm 전체 메모리 범위를 구분합니다.

cpp-wasm/memory-glue.mjs

메모리 성장과 오래된 뷰

게임은 초기 크기와 최대 크기를 같게 링크하여 성장을 거부합니다. 성장 가능한 다른 모듈에서는 기존 뷰가 새 버퍼를 가리키지 않을 수 있습니다. 어댑터는 버퍼가 바뀌면 다시 연결하도록 오류를 냅니다.

cpp-wasm/memory-glue.mjs

네이티브 검사와 wasm 검사

같은 게임 소스를 네이티브와 wasm으로 각각 빌드합니다. 네이티브의 경계 검사·경고 오류 처리와 wasm의 기준 기록 비교를 함께 사용합니다. 네이티브 성공만으로 브라우저 로딩이나 내보내기까지 성공했다고 판단하지 않습니다.

진단과 디버깅 · 이해 확인

wasm 컴파일이 성공하면 함수 호출 중에는 오류가 나지 않을까요?

컴파일 뒤에도 명시적 트랩이나 범위 밖 메모리 접근으로 RuntimeError가 발생할 수 있습니다. 모듈 로딩과 실제 함수 실행을 각각 검사해야 합니다.
