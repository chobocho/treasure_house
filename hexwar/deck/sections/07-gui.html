도스에는 툴킷이 없었다

버튼도, 대화상자도, 이벤트 시스템도 없었습니다. 게임마다 직접 만들었고, 그래서 GUI 코드가 게임 코드의 30~40%를 차지하는 일이 흔했습니다.

이벤트 루프의 모양

도스식 (폴링)

↓ 관용구 발췌 — 이 저장소에서 실행되지 않습니다

for (;;) {
  mouse_read(&mx, &my, &btn);
  if (btn & 1 && !prev_btn)
     on_click(mx, my);
  if (kbhit()) on_key(getch());
  if (dirty) redraw();
  prev_btn = btn;
}

이 문서 (이벤트 재생)

구조는 같습니다 — 입력 하나가 들어오면 상태를 바꾸고, 바뀌었으면 다시 그립니다. 다른 것은 입력이 어디서 오는가뿐입니다. 도스는 마우스 드라이버에서, 우리는 문자열 목록에서 옵니다. 이 분리가 나중에 재생 가능한 테스트를 공짜로 만들어 줍니다(14부).

배치는 코드에 박는다

왜 리소스 파일로 빼지 않는가 — 지원 해상도가 320×200 하나뿐이기 때문입니다. 해상도가 여럿이거나 지역화가 필요하면 그때 빼는 것이 맞습니다. 도스 게임에서도 대화상자 좌표를 .RES 파일로 빼는 경우는 여러 언어판을 낼 때가 대부분이었습니다.

히트 테스트 — 뒤에서 앞으로

그리기
부모 → 자식 앞에서 뒤로 (너비 우선)
⇄
히트 테스트
자식 → 부모 뒤에서 앞으로 (깊이 우선 · 역순)
이 대칭 하나가 모달 대화상자를 공짜로 만듭니다. 대화상자를 자식 목록의 맨 뒤에 두면, 그리기에서는 마지막에 그려져 위에 얹히고, 히트 테스트에서는 가장 먼저 검사되어 클릭을 가로챕니다. 별도의 '모달 플래그'가 없어도 겹침이 자연스럽게 처리됩니다.
단, 대화상자 밖 클릭은 따로 막아야 합니다. 대화상자가 화면 전체를 덮지 않으므로, 그 바깥을 누르면 히트 테스트가 아래 위젯을 돌려줍니다. 그래서 상태가 DIALOG일 때는 대화상자 안의 버튼이 아니면 전부 버립니다.

모달 처리

클릭 처리의 첫 분기가 상태 검사인 것이 핵심입니다. 위젯을 찾는 것보다 먼저, '지금 무엇을 받을 수 있는 상태인가'를 봅니다.

prev_state를 저장했다 되돌리는 것이 요령입니다. 대화상자를 닫으면 열기 전 상태로 돌아가야 합니다 — 유닛을 고른 채로 '턴 종료?'를 열었다가 취소하면 선택이 유지되어야 합니다.

상태 기계

지도 클릭 — 상태별 분기

순서가 규칙입니다. SELECTED에서 공격을 이동보다 먼저 검사합니다. 적이 서 있는 칸은 이동 오버레이에 들어가지 않으므로 실제로는 겹치지 않지만, 순서를 명시해 두면 나중에 규칙이 바뀌어도 의도가 남습니다.
마지막 deselect()가 중요합니다 — 어떤 분기에도 걸리지 않은 클릭(빈 땅, 적 유닛, 안 보이는 칸)은 선택 해제입니다. 이 '기본 동작'을 빼먹으면 잘못 누른 뒤 빠져나갈 방법이 없어집니다.

선택 — 오버레이를 여기서 계산한다

계산언제비용
이동 범위선택할 때 한 번O(V+E+maxMP)
공격 대상선택할 때 한 번O(유닛 수)
그리기매 프레임집합 조회 O(1)
'선택할 때 한 번'이 핵심입니다. 매 프레임 이동 범위를 다시 계산하면 도스에서는 프레임이 죽습니다. 선택은 사람이 클릭할 때만 일어나므로, 그 순간에 비싼 계산을 몰아넣고 그 뒤로는 조회만 합니다.
안개에 가려진 적은 공격 대상이 아닙니다 — fog[i] != FOG_VISIBLE이면 건너뜁니다. 이 검사를 빼면 '보이지 않는 적을 클릭해서 위치를 알아내는' 치트가 생깁니다.

다음 유닛 — 워게임의 관용 조작

이동력이 남은 아군을 아이디 순으로 돌면서 카메라를 그 유닛에 맞춥니다. 유닛이 20개를 넘어가면 마우스로 하나씩 찾는 것이 고역이라, 이 키가 사실상 주 조작이 됩니다.

순환의 시작점을 현재 선택에서 잡는 것이 요령입니다. 매번 첫 유닛으로 돌아가면 TAB을 눌러도 제자리입니다. ids.index(self.sel_unit)가 없으면(선택이 없거나 이미 다 움직였으면) 첫 번째부터 시작합니다.

상태 기계 없이 짜면

✘ 플래그 지옥
if (selected && !targeting
    && !dialog_open
    && !animating
    && !game_over) {
  ...
}

플래그가 n개면 조합이 2ⁿ입니다. 대부분의 조합은 불가능한 상태인데 코드는 그것을 모릅니다.

✔ 상태 하나
switch (state) {
  case SELECTED: ...
  case TARGETING: ...
  case DIALOG: ...
}

가능한 상태가 정확히 열거되고, 전이가 눈에 보입니다.

불가능한 상태를 표현할 수 없게 만드는 것이 이 설계의 요점입니다. '선택되어 있으면서 동시에 대화상자가 열린' 상태는 존재하지 않아야 하는데, 플래그로는 그것을 표현할 수 있어 버립니다.

유닛의 이동력·참호·이동 여부이동으로 바뀌므로
출발·도착 인덱스위치를 되돌리려고

난수를 되돌리지 않으면 생기는 일

공격 → 결과가 나쁨 → 무르기 → 다시 공격. 난수 상태를 되돌리지 않으면 두 번째 공격의 주사위가 다릅니다. 플레이어는 원하는 결과가 나올 때까지 무르고 다시 하면 됩니다. 언두 기능이 그대로 치트가 됩니다.
해법은 간단합니다 — 명령을 만들 때 rng.save()로 상태를 적어 두고, 언두에서 rng.restore()합니다. LCG의 상태가 32비트 정수 하나라서 4바이트면 됩니다. 이것이 도스 게임들이 메르센 트위스터 같은 것을 쓰지 않은 실무적 이유이기도 합니다 — 상태가 크면 언두와 세이브가 모두 무거워집니다.

되돌리기 구현

죽은 유닛을 되살리는 것이 가장 까다롭습니다. 유닛 풀은 죽은 아이디를 프리 리스트에 넣어 재사용하므로, 부활시키려면 프리 리스트에서 그 아이디를 빼내야 합니다. 단일 연결 리스트라 앞 노드를 찾아 이어 줘야 합니다.
더 간단한 대안은 죽은 유닛을 지우지 않고 alive=False로만 두는 것입니다. 그러면 부활이 플래그 하나이고, 대신 아이디가 재사용되지 않아 풀이 계속 자랍니다. 한 판이 20턴인 게임에서는 그쪽이 낫습니다 — 이 문서가 프리 리스트를 쓴 것은 그 기법을 보여 주기 위해서이고, 그 대가로 이 20줄이 생겼습니다.

안개는 복원하지 않는다 — 의도된 구멍

언두 뒤에 안개를 다시 계산하면, 정찰이 밝힌 지역은 그대로 남습니다. 유닛은 제자리로 돌아갔는데 지도는 밝아진 채입니다.

이것은 버그가 아니라 결정입니다. 안개를 되돌리려면 432바이트를 명령마다 저장해야 하고, 그러면 언두 스택이 순식간에 커집니다. 도스 워게임들도 대부분 이 상태였고, '정찰 보내고 무르기'는 알려진 악용이었습니다. 중요한 것은 이것이 알려지지 않은 버그가 아니라 문서화된 성질이라는 점입니다 — 테스트가 그 사실을 못 박습니다.
제대로 막으려면 안개를 '유닛이 본 것'이 아니라 '턴 시작 시점의 스냅샷 + 이번 턴의 관측'으로 나눠 두면 됩니다. 그러면 언두는 이번 턴 관측만 되돌리면 되고, 저장할 것도 훨씬 적습니다.

턴이 넘어가면 언두 스택을 버린다

이유가 셋입니다.

  1. 적의 수를 보고 무를 수 없어야 합니다. 적 턴이 끝난 뒤 내 턴 행동을 무르면 완전한 치트입니다.
  2. 턴 시작 처리가 여러 유닛을 한꺼번에 바꿉니다(이동력 회복·참호·안개). 이것을 되돌리려면 명령 하나에 전체 상태가 들어가야 합니다.
  3. 메모리 — 도스에서는 이것이 결정적이었습니다. 20턴 × 12유닛 × 명령 하나 100바이트면 24KB이고, 640KB에서 무시할 수 없습니다.

입력을 문자열로 정의한 대가는 파싱 비용뿐이고, 얻는 것은 셋입니다. ① 테스트가 사람의 조작을 그대로 재현할 수 있다. ② 세 언어가 같은 입력을 먹는다는 것이 자명해진다. ③ 데모 리플레이가 공짜로 생긴다.

스크립트 녹화 = 도스의 데모 리플레이

도스 게임의 데모(자동 시연)는 대개 화면을 저장한 것이 아니라 입력만 저장한 것이었습니다. 엔진이 결정적이면 같은 입력에서 같은 화면이 나오므로, 리플레이 파일이 수십 KB면 충분했습니다.

여기서 한 번 사고가 났습니다. 처음 녹화기는 계획을 세우려고 ui.select()와 ui.center_on()을 직접 불렀습니다. 그 호출은 이벤트로 남지 않으므로, 재생할 때 카메라가 다른 자리에 있고 클릭 좌표가 엉뚱한 헥스를 가리켰습니다. 규칙은 하나입니다 — 상태를 바꾸는 모든 것은 이벤트를 거친다.

미니맵 클릭

물림(clamp)이 center_on 안에 있는 것이 중요합니다. 지도 구석을 클릭하면 카메라가 범위를 벗어나는데, 호출자마다 물리게 하면 언젠가 한 곳을 빠뜨립니다. 카메라를 바꾸는 모든 경로가 같은 함수를 지나가게 두는 편이 안전합니다.

모달 대화상자가 뜬 화면

72번째 입력(key E) 직후 — 대화상자가 지도 위에 얹히고, 오른쪽 패널의 상태 표시가 DIALOG를 보여 준다

패널 아래쪽에 IDLE·SELECTED 같은 상태 이름을 그대로 찍어 두었습니다. 디버그용이지만 실제로도 유용합니다 — 사용자가 '왜 클릭이 안 먹지'라고 느낄 때, 상태가 TARGETING이라는 것이 보이면 답이 됩니다.

퀴즈 1

Q. 히트 테스트를 '앞에서 뒤로'(그리기와 같은 순서) 하면 무엇이 깨지는가?

A. 겹친 위젯 중 아래 것이 클릭을 먹습니다. 대화상자가 지도 위에 떠 있어도 지도가 먼저 검사되어, 대화상자 뒤의 지도를 클릭하게 됩니다. 나아가 부모를 자식보다 먼저 검사하면 자식이 영원히 클릭을 못 받습니다 — 패널을 누르면 언제나 패널이지 버튼이 아닙니다. 그리기와 히트 테스트가 정확히 역순이어야 하는 이유입니다.

퀴즈 2

Q. 언두를 '전체 상태 스냅샷'으로 구현하면 무엇이 좋고 무엇이 나쁜가?

A. 좋은 점은 정확성입니다 — 안개든 무엇이든 빠짐없이 되돌아가고, 새 필드를 추가해도 언두 코드를 고칠 필요가 없습니다. 나쁜 점은 크기입니다. 이 게임의 전체 상태는 맵 432 + 안개 432 + 점유 864 + 유닛 64×~20 ≈ 3KB이고, 명령마다 3KB면 20턴에 수백 KB입니다. 640KB에서는 불가능했습니다. 지금이라면 스냅샷이 옳은 선택일 수 있습니다 — 메모리가 남고, 버그가 훨씬 적기 때문입니다. 제약이 사라지면 설계도 바뀌어야 합니다.
