왜 배열 하나인가

맵을 정수 인덱스 하나로 접근하는 배열에 담는 것은 도스 시절의 필연이었습니다.

대안도스에서의 문제
2차원 포인터 배열포인터 하나가 4바이트(far) · 세이브할 때 전부 변환해야 함
좌표를 키로 한 해시해시 계산이 매 접근마다 · 메모리 조각화
칸마다 동적 할당640KB에서 조각화가 나면 복구 불가
배열 하나인덱스 = row×W + col · 세이브는 덤프 한 번
맵 밖을 -1로 돌려주는 규약이 중요합니다. 예외를 던지거나 None을 쓰면 호출부마다 분기가 생깁니다. 정수 하나로 '없음'을 표현하면 if i < 0 한 줄로 끝납니다 — 도스 코드가 -1을 사랑한 이유입니다.

셀 바이트

필드비트범위왜 그만큼인가
지형40–15실제로 쓰는 것은 8종 — 확장 여지를 절반 남김
고도30–7시야 계산에 필요한 단계 수. 8단계면 산과 평지를 충분히 가른다
도로10/1있거나 없거나
패킹의 진짜 이유는 메모리가 아닙니다 — 432바이트가 864바이트가 되어도 도스에서조차 문제가 안 됩니다. 이유는 접근 횟수입니다. 렌더링은 칸마다 지형·고도·도로를 다 봅니다. 따로 두면 메모리를 세 번 읽고, 한 바이트에 담으면 한 번 읽고 시프트합니다. 8086에서 메모리 읽기는 8사이클, 시프트는 2사이클이었습니다.

지형표 — 규칙을 데이터로

표에서 열을 뽑아 병렬 튜플로 만들어 둡니다. 뜨거운 경로에서 TERRAIN[t][2] 대신 T_MOVE[t]를 쓰기 위해서입니다 — 간접 참조 한 단계가 줄어듭니다.

표 주도 설계가 도스 워게임의 표준이었습니다. 지형 하나를 추가하는 일이 '표에 한 줄'로 끝나고, 밸런스 조정이 코드 수정이 아니라 숫자 수정이 됩니다. 이 문서의 엔진에서 지형·병종·전투 결과가 전부 표입니다.

센티넬 패딩 — 경계 검사를 없애는 기법

이웃을 볼 때마다 0 <= col < W를 검사하는 것이 아깝다면, 맵 둘레에 가짜 칸 한 줄을 둘러 두는 방법이 있습니다. 가짜 칸의 지형을 '통행 불가'로 해 두면 경계 검사 없이 그냥 읽어도 안전합니다.

패딩 없음센티넬 패딩
배열 크기24×18 = 43226×20 = 520 (+20%)
이웃 조회비교 4번 + 분기없음
인덱스 계산row*24+col(row+1)*26+(col+1)
디버깅범위 넘으면 즉시 티가 남조용히 가짜 칸을 읽음
이 문서는 센티넬을 쓰지 않습니다. 이유는 두 가지입니다. ① 헥스는 행 홀짝에 따라 이웃이 다르므로 패딩이 사각 격자만큼 깔끔하지 않습니다. ② 패딩을 쓰면 인덱스 계산이 어긋났을 때 조용히 틀립니다 — 세 언어를 맞춰야 하는 이 프로젝트에서는 시끄럽게 실패하는 쪽이 낫습니다. 도스에서는 반대 선택이 합리적이었습니다.

평행 배열(SoA)과 구조체 배열(AoS)

이 문서의 맵은 세 개의 평행 배열입니다 — 지형·고도·도로가 들어 있는 cells, 안개 fog, 점유 occupant.

배열바뀌는 빈도읽히는 빈도
cells시나리오 로드 때 한 번매 프레임 · 경로 탐색마다
fog턴마다 · 이동마다매 프레임
occupant이동·사망 때만경로 탐색마다
바뀌는 빈도가 다른 것을 한 구조체에 묶으면 손해입니다. 경로 탐색은 지형만 보는데, 한 구조체에 넷을 담으면 캐시 라인의 3/4가 쓰이지 않는 필드로 채워집니다.

그래서 얼마나 빨라지는가 — 재 보면

Uint8Array가 객체 배열보다 2~3배 빠릅니다. 예상대로입니다. 그런데 같은 것을 파이썬에서 재면 결과가 뒤집힙니다.

왜 뒤집히는가 — 파이썬에서는 bytearray[i] & 0x0F도, dict['terrain']도 둘 다 인터프리터 바이트코드입니다. 캐시 지역성의 이득이 인터프리터 오버헤드에 완전히 묻힙니다. 게다가 마스킹 연산 하나가 더 붙어 오히려 근소하게 느립니다.
교훈 — 자료구조 최적화는 연산의 비용 구조가 드러나는 층위에서만 효과가 있습니다. 도스의 어셈블리와 현대의 JIT에서는 SoA가 이깁니다. 인터프리터 위에서는 '무엇을 배열에 담는가'보다 '루프를 몇 번 도는가'가 훨씬 중요합니다.

좌표를 무엇으로 키 삼을 것인가

헥스 좌표를 다루다 보면 dict[(col,row)]나 Map<"c,r">이 편해 보입니다. 얼마나 비싼지 재 봤습니다.

데이터를 코드에서 떼어내기

시나리오 파일

블록 다섯 개입니다 — [terrain], [elev], [road], [units], [objectives]. 지형·고도·도로를 세 겹으로 겹쳐 놓은 것이 핵심입니다. 한 글자가 한 헥스라, 텍스트 편집기로 지도를 그릴 수 있습니다.

주석이 ;인 이유 — #을 주석으로 쓰면 지형 글자 #(바다)와 충돌합니다. 처음에 #으로 만들었다가 바다가 있는 세 줄이 통째로 사라지는 것을 파서가 잡아냈습니다. 형식을 정할 때 데이터에 쓸 글자와 메타 문자를 겹치지 않게 하는 것은 지금도 같은 원칙입니다.

파서

로더가 검증까지 합니다 — 높이가 18이 아니거나 어느 줄의 너비가 24가 아니면 즉시 예외입니다. 시나리오 파일은 사람이 손으로 고치는 파일이라, 조용히 잘못 읽는 것이 가장 나쁩니다.

실제 지도

가운데를 가로지르는 R(도로)이 강 위를 지나는 지점이 다리입니다. 도로에서 도로로 이동하면 지형과 무관하게 1MP이므로, 강(6MP)을 건너는 유일하게 싼 길이 됩니다 — 지도를 이렇게 그리면 규칙이 자동으로 전술을 만듭니다.

실제 바이트

0x84는 1000 0100입니다 — 도로 비트 1, 고도 0, 지형 4(도시). 목표 헥스인 북쪽 도시가 도로로 연결되어 있다는 사실이 바이트 하나에 들어 있습니다.

산은 0x33 = 0011 0011 — 도로 없음, 고도 3, 지형 3(산). 고도와 지형이 같은 숫자인 것은 우연입니다.

점유 배열은 반드시 유닛과 일치해야 한다

맵의 occupant는 유닛 좌표의 역인덱스입니다. 둘이 어긋나면 유닛이 유령이 되거나 두 유닛이 한 칸에 겹칩니다 — 도스 워게임의 고전적 버그입니다.

이 검사를 명령마다 돌립니다. 성능이 문제 되지 않는 규모(432칸, 12유닛)라서 가능한 사치이고, 대신 어긋남이 발생한 그 명령에서 즉시 잡힙니다. 세 언어를 맞출 때 이 검사가 여러 번 사고를 잡았습니다.

퀴즈

Q. 지형에 4비트를 배정했는데 실제로는 8종만 쓴다. 3비트로 줄이고 고도를 4비트로 늘리는 게 나을까?

A. 대개 아닙니다. 고도 8단계는 시야 판정에 충분하고(산 3, 언덕 1–2, 평지 0), 남는 지형 8종은 확장 여지입니다 — 사막·눈·다리·참호·도시 외곽 같은 것을 나중에 넣게 됩니다. 반면 고도를 16단계로 늘려도 시야 규칙이 그만큼 정교해지지는 않습니다. 비트 배분은 '지금 쓰는 값'이 아니라 '늘어날 축'에 맞춰야 합니다. 도로 비트를 하나만 둔 것도 같은 판단인데, 이쪽은 나중에 '철도'가 생기면 후회할 수 있습니다.
