1장

비트 단위로 써야 하는 이유

바이트는 너무 굵다

3비트짜리 부호를 바이트에 담으면

1부에서 본 것처럼, 좋은 부호는 기호마다 길이가 다르다. a 에 1비트, b 에 3비트를 주었는데 바이트 단위로만 쓸 수 있다면 어떻게 될까.

비트 단위바이트 단위
abracadabra 부호화23비트 = 3바이트11바이트
손해—3.7배

부호 길이를 아무리 잘 골라도 바이트 경계에 맞추는 순간 전부 사라진다. 그래서 압축기의 가장 밑바닥에는 비트를 한 개씩 쌓는 도구가 있어야 한다.

문서 근거

쌓는 방향을 정해야 한다

비트를 바이트에 채우는 방향은 두 가지다. 둘 다 맞는 방법이고, 섞어 쓰면 틀린다.

MSB 먼저

첫 비트가 바이트의 7번(가장 높은) 자리에 앉는다. 사람이 읽는 순서와 같아 손으로 따라가기 쉽다.

이 책이 만드는 형식은 전부 이쪽

LSB 먼저

첫 비트가 0번(가장 낮은) 자리에 앉는다. 값을 그대로 |= 하고 시프트하면 되어 구현이 조금 싸다.

DEFLATE 가 이쪽 — 9부에서 다시 만난다

설명용

명세에 못 박아야 하는 것 셋

비트 writer 는 코드가 스무 줄인데, 다섯 언어가 갈릴 자리는 셋이다.

  1. 비트 순서 — MSB 먼저인가 LSB 먼저인가
  2. 채움 비트 — 마지막 바이트의 남은 자리를 0 으로 채우나 1 로 채우나
  3. 빈 상태의 flush — 쌓인 비트가 없을 때 바이트를 내보내나 마나
셋 다 자기들끼리는 왕복이 된다. 1 로 채우는 구현도 자기가 쓴 것은 잘 읽는다. 그래서 골든 벡터를 맞춰 보기 전에는 아무도 틀린 줄 모른다.

자바 — byte 가 부호 있는 수다

자바의 byte 는 −128~127 이다. 0x80 을 담으면 -128 로 읽힌다. 그래서 쌓는 통을 int 로 두고, 내보낼 때만 (byte) 로 자른다. 되읽을 때는 & 0xFF 를 붙인다 — 한 군데만 빠뜨려도 파일이 갈린다.
실행 검증

TypeScript — 비트 연산이 부호를 만든다

TypeScript(자바스크립트)의 <<·|·& 는 피연산자를 32비트 부호 있는 정수로 바꾼다. 비트 writer 는 8비트 안에서만 놀아서 무사하지만, 5부의 레인지 코더는 이 규칙 때문에 비트 연산을 아예 쓰지 못한다.

골든 코덱 — 압축기가 아니다

비트 writer 자체는 아무것도 줄이지 않는다. 그런데 골든 벡터로 묶어 두고 싶다. 그래서 껍데기 코덱을 하나 둔다.

앞의 0비트 셋이 모든 바이트를 바이트 경계 밖으로 민다. 몰래 memcpy 로 베끼는 구현은 여기서 다른 파일을 낸다.

1·2장 퀴즈

Q. 어떤 사람이 비트 writer 의 flush 에서 if self._n: 검사를 빼먹었다. 왕복 시험은 전부 통과한다. 무엇이 언제 드러날까?

A. 빈 입력에서만 드러난다. 쌓인 비트가 0 인데도 바이트를 하나 내보내므로 출력이 1바이트 길어진다. 자기 복호기는 그 여분을 그냥 안 읽으니 왕복은 통과한다.
골든 벡터(empty.bin)를 맞춰 보거나, 다른 언어가 만든 파일을 풀어 볼 때 비로소 드러난다. 코퍼스에 빈 파일이 들어 있는 이유가 정확히 이것이다.

varint — 작은 수를 작게

LEB128, 이어짐 비트 하나로

길이를 어떻게 적을 것인가

압축 형식은 길이·개수·거리 같은 수를 끝없이 적는다. 그런데 이런 수는 대개 작고, 가끔 아주 크다.

방법3 을 적으면1,000,000 을 적으면
4바이트 고정4바이트4바이트
8바이트 고정8바이트8바이트
varint1바이트3바이트

고정 폭은 최악을 기준으로 자리를 잡는다. varint 는 값의 크기에 따라 자리를 늘린다.

문서 근거

LEB128 — 7비트씩, 맨 앞 비트가 이어짐

  • 한 바이트에 값 7비트 + 이어짐 1비트
  • 이어짐 비트가 1 이면 "뒤에 더 있다", 0 이면 여기까지
  • 낮은 자리부터 싣는다 — 읽는 쪽이 한 번에 훑으며 자리올림만 하면 된다
설명용

쓰기

고리 하나가 전부다. value >>= 7 뒤에 남은 것이 있으면 앞 비트에 0x80 을 세운다.

실행 검증

읽기 — 여기서 형식이 깨질 수 있다

상한 검사가 없으면 무한 루프가 된다. 손상된 파일이 0x80 만 늘어놓으면 읽는 쪽이 영원히 돈다. 10바이트에서 자르는 것은 64비트 값을 다 담고도 남는 길이라서다.
실행 검증

길이 전용 읽기를 따로 둔 이유

길이는 메모리를 미리 잡는 데 쓰인다. 손상된 파일이 "길이 263" 이라고 말하면, 검사 없는 구현은 그 자리에서 죽는다. 형식이 허용하는 상한(4 GiB−1)에서 자른다.

같은 함수를 두 번 쓰지 않는 이유 — "그냥 정수" 와 "길이" 는 믿을 수 있는 범위가 다르다. 한 함수로 합치면 둘 중 하나에서 검사가 느슨해진다.

비트 스트림 안에서 쓰는 정수 부호

varint 를 못 쓰는 자리가 있다

varint 는 바이트 단위다. 비트 스트림 한가운데서 정수를 적어야 할 때는 바이트 경계로 돌아갈 수 없다. 그래서 비트 단위 정수 부호가 따로 필요하다.

6장

골롬–라이스

치우친 값에 딱 맞는 부호 — 손실 오디오가 쓰는 것

값을 둘로 쪼갠다

값 v 와 매개변수 k 를 정하면, 몫 v>>k 는 단항으로, 나머지 k비트는 그대로 적는다.

  • k 가 크면 나머지가 길어지고 몫이 짧아진다
  • k 가 작으면 몫의 단항이 길어진다
  • 가장 좋은 k 는 값의 평균에 달려 있다 — 평균이 2k 근처일 때 최적
설명용

코드

단항 상한 4096 이 있는 이유 — k=0 일 때 값 100 은 101비트다. 손상된 파일이 큰 값을 말하면 단항이 끝없이 길어진다. 상한을 안 두면 그 자리에서 메모리가 터진다. 상한을 얼마로 두느냐가 형식의 일부라 명세에 적혀 있다.
실행 검증

어디에 쓰나

  • FLAC·Shorten — 오디오 표본의 예측 오차. 0 근처에 몰려 있어 딱 맞는다
  • JPEG-LS·CALIC — 무손실 사진의 화소 오차
  • 역색인 — 검색 엔진의 문서 번호 차이
공통점은 값이 0 근처에 지수적으로 몰려 있다는 것이다. 그런 분포에서는 라이스 부호가 허프만만큼 좋으면서 표가 필요 없다.

첫 파서티 — 다섯 언어가 같은 바이트를 낸다

실행 검증

3~6장 퀴즈

Q. 어떤 형식이 "거리" 를 varint 로 적는다. 거리는 대부분 1~수백이고, 아주 가끔 30,000 근처다. 누군가 "고정 2바이트가 더 낫다" 고 한다. 맞을까?

A. 대개 varint 가 이긴다. 거리가 127 이하면 1바이트, 16,383 이하면 2바이트다. 30,000 짜리만 3바이트로 손해를 본다.
값의 90%가 127 이하라면 평균 1.1바이트 대 2바이트로 varint 가 낫다. 반대로 값이 고르게 0~65535 에 퍼져 있다면 고정 2바이트가 낫다 — 분포를 모르면 어느 쪽도 고를 수 없다는 것이 요점이다.

Go — 시프트 값에 부호가 있으면 안 된다

Go 는 시프트 폭이 음수면 실행 중에 죽는다(패닉). C 계열은 미정의 동작이라 조용히 이상한 값이 나온다. 죽는 쪽이 낫다 — 조용한 쪽은 골든 대조 전까지 안 보인다.

실행 검증

TypeScript — 39비트를 어떻게 적나

자바스크립트의 비트 연산은 32비트에서 잘린다. Elias γ 로 큰 값을 적으려면 << 를 쓸 수가 없다.

Math.floor(v / 2 ** i) & 1 — 시프트를 나눗셈으로 바꾸면 53비트까지 안전하다. 이 덱의 TypeScript 코드에서 >> 가 드문 이유다.
실행 검증

C++ — 부호 있는 시프트는 피한다

C++20 부터 부호 있는 왼쪽 시프트가 정의되긴 했지만, 이 책은 부호 없는 형으로 올려서 푼다. 표준 판이 바뀌어도 같은 바이트가 나오는 쪽을 고른다.

실행 검증

파이썬 — 넘침이 없어서 생기는 문제

파이썬 정수는 무한히 커진다. 편해 보이지만 참조 구현으로는 위험하다 — 다른 언어에서 넘칠 연산이 여기서는 조용히 맞는 답을 낸다.

그래서 참조 구현은 마스크를 일부러 명시한다. 5부 레인지 코더의 & 0xFFFFFFFF 가 그것이다. 파이썬에는 필요 없지만, 명세를 코드로 적어 두는 자리다.
