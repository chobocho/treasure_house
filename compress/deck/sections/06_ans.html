2장

rANS 의 생각

상태 하나에 정보를 쌓아 올린다

자릿수 올리기의 일반화

10진수에 숫자 하나를 붙이는 일을 생각해 보자. x = x*10 + d 다. 확률이 모두 1/10 인 기호 열 개를 적는 셈이다.

확률이 제각각이면? 기호마다 곱하는 수가 달라야 한다. 확률 p 인 기호를 붙이면 상태가 1/p 배가 되어야 한다 — 그래야 −log₂p 비트가 든다.

rANS 의 식이 바로 그것이다. 빈도 f, 누적 c, 합 M 일 때:

x' = ⌊x / f⌋ · M + (x mod f) + c

x 가 대략 M/f = 1/p 배가 된다. 나머지(x mod f)와 누적(c)이 "어느 기호였는지" 를 그 안에 숨긴다.

문서 근거

실제로 상태가 자라는 모습

드문 기호(B)를 넣을 때 상태가 크게 뛴다. 그 뜀이 곧 "비트를 더 썼다" 는 뜻이다.

상태가 무한정 커질 수는 없으니, 어느 한계를 넘으면 아래 바이트를 내보내고 상태를 줄인다 — 레인지 코더의 정규화와 같은 일이다. 다만 방향이 반대다.
설명용

복호는 정확히 거꾸로

s = 슬롯[x mod M]   →    x' = f·⌊x/M⌋ + (x mod M) − c

상태의 아래 12비트가 곧 "어느 기호" 인지를 말해 준다. 슬롯 표 한 번 찾고 곱셈 한 번이면 끝이다.

그래서 rANS 는 스택이다. 마지막에 넣은 기호가 먼저 나온다. 부호기는 입력을 뒤에서부터 밀어 넣어야 복호기가 앞에서부터 읽는다. 이 방향을 헷갈리면 왕복은 되는데 바이트가 달라진다.

정규화 — 상태를 범위 안에 두기

상태 x 는 늘 [L, L·256) 안에 있어야 한다. 기호를 넣기 전에 x 가 너무 커질 것 같으면 아래 바이트를 먼저 내보낸다.

while x >= ((L >> 12) << 8) · f:   바이트 내보내고 x >>= 8

문턱이 f 에 비례하는 것이 요점이다. 빈도가 큰 기호는 상태를 조금만 키우므로 더 오래 버틸 수 있다.

5장

tANS — 표를 만들어 두면 덧셈만 남는다

FSE 라는 이름으로 zstd 안에 들어 있는 것

생각

rANS 의 상태가 [L, L·256) 이라 값이 크다. 그런데 상태를 작은 범위(예: 4096) 로 묶고, 그 안에서 일어나는 모든 전이를 미리 표로 만들어 두면 어떨까?

부호화가 "표 보고 다음 상태 읽기 + 비트 몇 개 내보내기" 로 줄어든다. 곱셈도 나눗셈도 없다.

대가는 표를 만드는 값이다. 블록마다 빈도가 바뀌면 표도 다시 만들어야 한다.

문서 근거

퍼뜨리기 — 상수 하나가 이상해 보이는 이유

SPREAD_STEP = (M>>1) + (M>>3) + 3 = 2048 + 512 + 3 = 2563

홀수라서 2의 거듭제곱 칸을 빠짐없이 한 번씩 돈다. 같은 기호의 칸들이 표 전체에 고루 흩어지게 하는 것이 목적이다 — 뭉쳐 있으면 상태가 한쪽으로 쏠려 압축비가 떨어진다.

zstd 가 쓰는 값 그대로다. 이론적으로 최적인 배치는 따로 있지만, 이 걸음이 충분히 좋으면서 계산이 없다.

6부 퀴즈

Q. rANS 부호기를 앞에서부터(정방향) 돌리도록 고쳤다. 자기 복호기도 같이 고쳤더니 왕복이 통과한다. 무엇이 잘못됐나?

A. 잘못된 것은 없다 — 다른 형식이 되었을 뿐이다. rANS 는 스택이라 정방향으로 밀어 넣으면 복호기도 뒤에서부터 읽어야 하고, 그러면 스트림 전체를 메모리에 들고 있어야 한다.
진짜 문제는 남의 파일을 못 푼다는 것이다. zstd 가 만든 블록도, 이 책의 다른 언어 구현이 만든 파일도 못 읽는다. 왕복 시험은 이것을 절대 잡아 주지 않는다 — 골든 벡터와 교차 복호가 있어야 잡힌다.
