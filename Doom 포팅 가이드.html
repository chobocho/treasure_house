1장. 시작하기 전에 — 왜 Doom 포팅인가

난이도 ★☆☆☆☆예상 시간 20분키워드: 역사·동기·로드맵

1.1 한 줄 요약

1993년에 발매된 DOOM은 1997년 id Software가 GPL로 소스 코드를 공개한 이래, 전 세계 개발자들이 가장 많이 포팅(porting)한 게임입니다. 토스터·계산기·임산부 초음파 기계까지 돌아간다는 농담이 있을 정도죠. 이 가이드의 목표는 그 농담을 여러분의 손으로 사실로 만드는 것입니다.

1.2 왜 하필 Doom인가?

🧠 학습 관점

  • 크지도 작지도 않은 코드베이스(약 4만 줄 C). 며칠이면 전체 흐름을 잡을 수 있는 분량.
  • 고정소수점 연산, BSP 트리, Z_Malloc 메모리 풀 등 교과서 같은 시스템 프로그래밍 패턴이 살아있음.
  • 플랫폼 추상화(i_*.c)가 명확하게 분리되어 있어 포팅 실습 교본으로 최고.

🛠 실용 관점

  • 이미 수백 개의 포트(소스포트)가 존재 → 비교 학습이 쉽다.
  • SDL2를 끼우는 순간 Windows/Linux/macOS/Android가 거의 공짜로 따라온다.
  • WAD 파일 포맷을 이해하면 레벨 에디터·모드 제작까지 자연스럽게 연결된다.

이 가이드는 위 화살표를 왼쪽에서 오른쪽으로 한 칸씩 같이 걸어갈 것입니다. 중간에 막혀도 괜찮습니다. 사실 막히는 게 정상이에요. 포팅은 "에러 메시지와의 대화"라는 말이 있을 정도니까요.

2장. 포팅이라는 작업의 본질

난이도 ★☆☆☆☆예상 시간 30분키워드: 이식·추상화·ABI·HAL

2.1 포팅의 정의

포팅(Porting)이란 "같은 프로그램을 다른 환경에서 동작하게 만드는 일"입니다. 여기서 "환경"은 보통 4가지 축으로 나뉩니다.

축예시Doom에서 주로 부딪히는 부분
CPU 아키텍처x86 → ARM, RISC-V엔디안, 정렬, int 크기
운영체제DOS → Linux, Windows, Android파일 I/O, 시그널, fork 없음
하드웨어 인터페이스VGA Mode 13h → SDL/OpenGLI_FinishUpdate, 색팔레트
표준 라이브러리/툴체인djgpp → gcc, clang, MSVCPOSIX vs Win32, #include

2.2 두 가지 포팅 전략

① 최소 변경 포팅

원본 코드를 최대한 그대로 두고, 플랫폼 의존 함수(I_*)만 새 환경에 맞게 재작성합니다.

  • 장점: 동작이 원본과 똑같음. 학습용으로 최고.
  • 단점: 옛 가정(320x200, 8bit 팔레트 등)을 떠안음.

이 가이드의 기본 전략입니다.

② 전면 재작성 포팅

렌더러를 OpenGL로 갈아끼우고, 입력을 게임패드로 바꾸고, 네트워크를 다시 짜는 방식.

  • 장점: 현대적 기능 풀가동.
  • 단점: 사실상 새 게임 만들기. GZDoom이 이 길.

2.3 추상화 계층(HAL)이라는 개념

Doom의 천재성은 1993년에 이미 HAL(Hardware Abstraction Layer) 구조를 갖췄다는 점입니다. 모든 플랫폼 의존 코드는 i_ 접두사로 시작합니다.

┌────────────────────────────────┐ │ 순수 게임 로직 (G_*, P_*, R_*) │ ← 어떤 OS에서도 똑같이 동작 ├────────────────────────────────┤ │ 플랫폼 추상화 (I_*) │ ← 여기를 갈아끼우는 게 "포팅" ├────────────────────────────────┤ │ 실제 OS / SDL / Win32 / Termux │ └────────────────────────────────┘

즉 i_video.c, i_sound.c, i_system.c, i_net.c 네 개 파일이 우리의 주된 전쟁터입니다.

2.4 포팅에서 자주 만나는 5가지 장벽

  1. 없는 헤더 — DOS의 conio.h, dos.h 같은 건 리눅스/안드로이드에 없습니다.
  2. 없는 함수 — itoa, strlwr, _kbhit 등.
  3. 타입 크기 차이 — 32bit/64bit에서 long이 4/8바이트로 다름.
  4. 엔디안 — WAD 파일은 리틀엔디안이라 빅엔디안 CPU에선 변환 필요.
  5. 경로/권한 — 대소문자, 슬래시 방향, 안드로이드 권한 모델.
심화: ABI(Application Binary Interface)란?

ABI는 컴파일된 코드가 OS·라이브러리와 약속한 이진 수준 규약입니다. 함수 호출 시 인자를 레지스터에 둘지 스택에 둘지, 구조체 정렬을 어떻게 할지 등을 규정합니다. 포팅 시에는 주로 구조체 패킹(__attribute__((packed)))에서 마주칩니다. WAD 파일의 디스크 레이아웃을 메모리 구조체로 그대로 캐스팅할 때 ABI를 알아야 합니다.

Q. Doom의 "i_" 접두사가 붙은 파일이 의미하는 것은?
게임 로직(input)을 처리한다
플랫폼 의존(interface/implementation) 코드다
id Software 내부용(internal)이다
정답은 2번. 보통 "interface" 또는 "implementation-specific"으로 해석합니다. 포팅 시 가장 많이 손대는 부분입니다.

3.2 SDL2가 핵심인 이유

SDL(Simple DirectMedia Layer)은 "창 띄우고, 키보드 받고, 소리 내고"를 OS마다 똑같은 API로 해주는 라이브러리입니다. SDL2를 끼우는 순간 우리는 다음을 동시에 얻습니다.

  • Windows: Win32 + WASAPI 처리
  • Linux: X11/Wayland + ALSA/PulseAudio 처리
  • Android(Termux): EGL + OpenSL ES 처리

덕분에 i_video.c를 SDL2로 단 한 번만 작성하면 세 플랫폼이 모두 돕니다. 굉장하죠.

3.3 빌드 시스템 한눈에

# Make: 가장 고전적, Makefile에 직접 규칙을 적음
CC=gcc
CFLAGS=-Wall -O2 `sdl2-config --cflags`
doom: doomdef.o r_main.o g_game.o
	$(CC) -o doom $^ `sdl2-config --libs`

# CMake: 메타 빌드 시스템. CMakeLists.txt → Makefile/Ninja/MSVC 자동 생성
project(chocolate-doom)
find_package(SDL2 REQUIRED)
add_executable(chocolate-doom src/i_main.c ...)
target_link_libraries(chocolate-doom SDL2::SDL2)

Chocolate Doom·DSDA-Doom 같은 현대 포트는 CMake를 씁니다. 한 번 익혀두면 거의 모든 C/C++ 오픈소스 프로젝트를 빌드할 수 있어요.

3.4 플랫폼별 환경 요약 (자세한 설치는 13~15장)

  • 방법 A: MSYS2 + MinGW-w64 (가장 추천. 리눅스스럽게 빌드)
  • 방법 B: Visual Studio 2022 + vcpkg (정식 MS 툴체인)
  • 방법 C: WSL2 Ubuntu (사실상 리눅스 빌드)

이 가이드는 방법 A(MSYS2)를 메인으로 사용합니다. 명령어가 리눅스/Termux와 거의 같아서 학습 효율이 좋기 때문이에요.

  • Ubuntu/Debian 계열: apt
  • Fedora/RHEL: dnf
  • Arch: pacman

대부분 build-essential(혹은 등가물) + cmake + libsdl2-dev면 끝납니다.

  • Termux는 안드로이드 위의 정식 리눅스 환경(루팅 불필요).
  • pkg install로 clang, cmake, sdl2를 설치.
  • 그래픽 출력은 X11(Termux:X11) 또는 SDL2 직접 윈도우로 처리.
⚠️ 흔한 함정
  • 32bit/64bit 혼용: Windows에서 32bit MinGW로 SDL을 받고 64bit MinGW로 컴파일하면 링크 에러가 납니다. 툴체인과 라이브러리의 비트수를 반드시 통일하세요.
  • 경로의 공백/한글: Windows에서 C:\사용자\내 문서\doom 같은 경로는 빌드 도구가 깨질 수 있습니다. C:\dev\doom 같은 짧은 ASCII 경로를 추천.

4.4 고정소수점(Fixed-point) 산술 — Doom의 정체성

1993년 PC에는 FPU(부동소수점 유닛)가 옵션이었습니다. 그래서 Doom은 모든 소수를 정수 안에 소수부를 박아 넣어 표현합니다.

표현의미
fixed_t = int32_t상위 16bit 정수부, 하위 16bit 소수부
FRACUNIT = 1.00x00010000 (즉 65536)
FixedMul(a,b)(int64_t)a*b >> 16
FixedDiv(a,b)((int64_t)a<<16)/b
fixed_t speed = 2*FRACUNIT;       // 초당 2 유닛
fixed_t dx = FixedMul(speed, cosine);
왜 16/16 분할인가? 다른 비트는 왜 안 됐을까?

16비트면 소수부 정밀도 1/65536로 충분히 매끄럽고, 정수부 ±32768은 Doom 맵 크기(±32k 단위)와 정확히 맞아떨어집니다. 더 줄이면 좌표가 모자라고, 더 늘리면 정밀도가 낮아집니다. 즉 설계 의도가 담긴 숫자입니다.

6장. 아키텍처 개요 — 한 프레임이 그려지는 여정

난이도 ★★★☆☆예상 시간 60분키워드: 메인루프·tic·렌더 파이프라인

6.1 35Hz라는 마법의 숫자

Doom의 게임 로직은 1초에 35번(약 28.57ms마다) 갱신됩니다. 이걸 1 tic이라고 부릅니다. 왜 하필 35Hz? 1993년 VGA 70Hz 리프레시의 정확히 절반이라 화면 동기화가 깔끔했기 때문이에요.

6.2 메인 루프 한눈에

// d_main.c (요지)
void D_DoomLoop (void)
{
    while (1) {
        TryRunTics ();           // 1) 누적된 tic만큼 게임 로직 실행
        S_UpdateSounds (...);    // 2) 사운드 업데이트
        D_Display ();            // 3) 화면 그리기
    }
}
입력 큐 ──▶ TryRunTics ──▶ G_Ticker ──▶ P_Ticker ──▶ AI/물리/충돌 │ └▶ HU_Ticker (HUD), ST_Ticker (상태바) D_Display ──▶ R_RenderPlayerView ──▶ R_RenderBSPNode ──▶ R_DrawColumn (벽) ├▶ R_DrawSpan (바닥/천장) └▶ R_DrawSprite (적/아이템) ──▶ ST_Drawer, HU_Drawer, M_Drawer (메뉴) ──▶ I_FinishUpdate ← 여기서 SDL2가 실제로 픽셀을 화면에 올림

6.3 TryRunTics가 하는 일

네트워크 게임에서도 결과가 결정적이도록, Doom은 모든 플레이어의 입력을 수집한 뒤에야 한 tic을 진행합니다. 싱글플레이에서도 같은 구조를 씁니다.

  1. I_StartTic()로 OS 이벤트 → events[] 큐
  2. D_ProcessEvents()로 메뉴/콘솔이 먼저 소비
  3. 나머지는 G_BuildTiccmd()가 틱 명령(전진/회전/사격)으로 변환
  4. 네트워크 동기화 후 G_Ticker() 실행

6.4 D_Display의 분기 구조

7장. 렌더링 파이프라인 — BSP, 컬럼, 스팬

난이도 ★★★★☆예상 시간 90분키워드: BSP·컬럼렌더링·시저·스팬

7.1 왜 Doom은 빠른가? — 한 줄 요약

Doom은 1993년에 3D처럼 보이는 2.5D를 그렸습니다. 비밀은 세 가지입니다.

  1. BSP 트리로 "지금 화면에 보이는 벽"만 골라낸다.
  2. 벽은 세로 한 줄(column)씩, 바닥/천장은 가로 한 줄(span)씩 그린다.
  3. 모든 좌표는 고정소수점 정수로 처리해 FPU 없이도 빠르다.

7.2 BSP(Binary Space Partitioning) 트리

WAD 안에는 맵을 이진 트리로 미리 쪼개 둔 데이터가 있습니다(NODES 럼프). 트리의 각 노드는 "이 선의 앞/뒤"를 가립니다. 카메라 위치에서 트리를 앞쪽 자식부터 순회하면, 가까운 것부터 자연스럽게 그려져 Painter 알고리즘이 거꾸로 작동합니다.

void R_RenderBSPNode (int bspnum)
{
    if (bspnum & NF_SUBSECTOR) {
        R_Subsector (bspnum & ~NF_SUBSECTOR);
        return;
    }
    node_t* bsp = &nodes[bspnum];
    int side = R_PointOnSide (viewx, viewy, bsp);
    R_RenderBSPNode (bsp->children[side]);          // 가까운 쪽 먼저
    if (R_CheckBBox (bsp->bbox[side^1]))            // 반대편이 보이면
        R_RenderBSPNode (bsp->children[side^1]);
}

7.3 컬럼 렌더링(Column Rendering)

벽은 텍스처를 세로 한 픽셀 열씩 잘라서 화면 한 열에 매핑합니다. 이걸 아핀(affine) 수직 매핑이라 부르고, 핵심 함수가 R_DrawColumn입니다.

void R_DrawColumn (void)
{
    int     count = dc_yh - dc_yl;
    byte*   dest  = ylookup[dc_yl] + columnofs[dc_x];
    fixed_t frac  = dc_texturemid + (dc_yl - centery)*dc_iscale;
    do {
        *dest = dc_colormap[dc_source[(frac >> FRACBITS) & 127]];
        dest += SCREENWIDTH;
        frac += dc_iscale;
    } while (count--);
}

한 줄씩 보면:

  • ylookup[y] + columnofs[x] = 화면 (x,y) 바이트 주소 (곱셈 회피!)
  • dc_source = 텍스처 패치의 한 컬럼 (128픽셀, 그래서 & 127)
  • dc_colormap = 거리/조명에 따른 팔레트 변환표 (256바이트)
  • frac += dc_iscale = 한 픽셀 내려갈 때 텍스처 좌표 증가량

7.4 스팬 렌더링(바닥/천장)

바닥과 천장은 카메라 평면에 평행한 visplane으로 모은 뒤, 가로 한 줄(span)씩 그립니다. R_DrawSpan은 컬럼과 거의 대칭 구조예요.

7.5 스프라이트(적/아이템)

3D 모델이 아니라 각도별 2D 이미지 8장을 카메라 각도에 맞춰 선택합니다(SPR_*_A1 ~ A8). 그래서 적을 한 바퀴 돌면 옆모습/뒷모습이 자연스럽게 보이는 거죠. 스프라이트도 결국 R_DrawColumn으로 그립니다(투명 픽셀 처리 버전).

7.6 시저(scissor) — visplane 마스킹

벽이 화면을 가리면 그 뒤의 바닥/천장은 그리면 안 됩니다. Doom은 floorclip[], ceilingclip[] 두 배열로 화면 각 컬럼의 그릴 수 있는 범위를 좁혀나갑니다. 매우 영리한 자료구조예요.

📐 BSP 트리는 누가 만들까?

맵 디자이너가 만든 원본 맵(VERTEXES, LINEDEFS)을 nodebuilder라는 도구가 컴파일하여 NODES, SEGS, SSECTORS 럼프로 변환합니다. 즉 BSP는 빌드 타임 자료구조입니다. 런타임에는 트리를 만들지 않고 순회만 합니다. 이래서 빨라요.

8.3 MUS → MIDI → OPL2

  • OPL2 에뮬레이션 — 90년대 Sound Blaster의 FM 합성 칩을 소프트웨어로 흉내. 가장 "그 시절" 소리.
  • SDL_mixer로 일반 MIDI — OS의 MIDI 신디사이저로 출력.
  • 외부 합성기(fluidsynth + SoundFont) — 가장 풍부한 음색.

11장. 메모리 관리 — Z_Malloc Zone 시스템

난이도 ★★★★☆예상 시간 50분키워드: zone·태그·purgeable

11.1 왜 자체 메모리 풀인가?

1993년의 malloc은 느렸고, DOS 메모리 구조도 까다로웠습니다. 그래서 Doom은 부팅 직후 큰 메모리 블록 하나(zone)을 잡고, 그 안에서 자체적으로 잘라 씁니다. 모든 동적 할당은 Z_Malloc으로 통일됩니다.

11.2 태그(tag) 개념

태그의미
PU_STATIC명시적으로 풀기 전엔 절대 해제 안 됨
PU_LEVEL맵을 떠나면 일괄 해제
PU_LEVSPEC레벨 특수효과(승강기 등)와 함께 해제
PU_CACHE공간 부족하면 가장 먼저 버려도 됨 (purgeable)

11.3 Z_Malloc 사용 패턴

void* p = Z_Malloc(size, PU_STATIC, NULL);

// 캐시용으로 잡되, 나중에 사라져도 추적 가능하게 user 포인터를 줌
byte* lump;

// 내부적으로: Z_Malloc(size, PU_CACHE, &lumpcache[i])

11.4 zone 디버깅

원본은 화면 픽셀 320×200×8bit를 X11 SHM 또는 VGA에 직접 썼습니다. 우리는 SDL2 텍스처에 업로드합니다.

void I_FinishUpdate (void)
{
    SDL_UpdateTexture (texture, NULL, screens[0], SCREENWIDTH);
    SDL_RenderClear   (renderer);
    SDL_RenderCopy    (renderer, texture, NULL, NULL);
    SDL_RenderPresent (renderer);
}

12.3 팔레트 변환 — 8bit를 32bit로

Doom 화면 버퍼는 픽셀당 1바이트(팔레트 인덱스)입니다. SDL2 텍스처는 보통 ARGB8888이므로 매 프레임 인덱스→RGB 변환이 필요합니다.

16장. 포팅 실습 ① — 헬로 SDL 윈도우

난이도 ★★☆☆☆예상 시간 40분키워드: SDL_CreateWindow·이벤트루프

본격적인 Doom 포팅에 앞서 SDL2로 320×200 검은 창을 띄우고 ESC로 종료시키는 미니 프로그램부터 만들어 봅니다. 이 코드가 사실상 i_video.c의 뼈대가 됩니다.

16.1 minidoom.c

#include <SDL.h>
#include <stdio.h>
#define SCREENWIDTH  320
#define SCREENHEIGHT 200

int main(int argc, char* argv[])
{
    SDL_Init(SDL_INIT_VIDEO);
    SDL_Window*   win = SDL_CreateWindow("minidoom",
        SDL_WINDOWPOS_CENTERED, SDL_WINDOWPOS_CENTERED,
        SCREENWIDTH*3, SCREENHEIGHT*3, 0);
    SDL_Renderer* ren = SDL_CreateRenderer(win, -1, SDL_RENDERER_ACCELERATED);
    SDL_Texture*  tex = SDL_CreateTexture(ren,
        SDL_PIXELFORMAT_ARGB8888, SDL_TEXTUREACCESS_STREAMING,
        SCREENWIDTH, SCREENHEIGHT);

    uint32_t pixels[SCREENWIDTH*SCREENHEIGHT] = {0};
    int running = 1;
    while (running) {
        SDL_Event e;
        while (SDL_PollEvent(&e)) {
            if (e.type == SDL_QUIT) running = 0;
            if (e.type == SDL_KEYDOWN && e.key.keysym.sym == SDLK_ESCAPE) running = 0;
        }
        // 매 프레임 색이 변하는 그라데이션
        static int t = 0; t++;
        for (int y=0; y<SCREENHEIGHT; y++)
            for (int x=0; x<SCREENWIDTH; x++)
                pixels[y*SCREENWIDTH+x] = (x+t)^(y+t);
        SDL_UpdateTexture(tex, NULL, pixels, SCREENWIDTH*4);
        SDL_RenderClear(ren);
        SDL_RenderCopy(ren, tex, NULL, NULL);
        SDL_RenderPresent(ren);
        SDL_Delay(16);
    }
    SDL_Quit();
    return 0;
}

17.1 목표

1997년 X11/SVGAlib 코드를 최소한의 수정으로 현대 64bit Linux에서 빌드·실행시키는 것. 이 실습이 끝나면 여러분은 "포팅이란 이런 거구나"를 몸으로 알게 됩니다.

17.6 팔레트 처리 핵심

static uint32_t pal32[256];
void I_SetPalette (byte* palette)   // palette = PLAYPAL 럼프의 R,G,B 768바이트
{
    byte* g = gammatable[usegamma];   // 감마 보정표 (v_video.c, WAD 럼프 아님)
    for (int i=0; i<256; i++) {
        byte r = g[*palette++];
        byte gC = g[*palette++];
        byte b = g[*palette++];
        pal32[i] = (0xFF<<24) | (r<<16) | (gC<<8) | b;
    }
}

감마 보정은 WAD가 아니라 코드 쪽 데이터입니다. v_video.c의 byte gammatable[5][256]에서 usegamma(F11로 토글) 단계의 표를 골라 쓰는 구조예요. 감마를 생략하려면 g[...] 없이 *palette++를 그대로 쓰면 됩니다.

💡 안심 — fixed point 곱셈은 이미 안전
DOS 버전의 FixedMul은 어셈으로 짜여 있었지만, linuxdoom-1.10의 m_fixed.c는 이미 (long long) 기반 순수 C라 64bit에서도 그대로 컴파일됩니다. 참고용 표준 구현은 아래와 같습니다(원본과 사실상 동일). 이 실습의 진짜 최대 함정은 단계 2(17.4)의 포인터→int 캐스팅이니 그쪽에 시간을 쓰세요. 
fixed_t FixedMul (fixed_t a, fixed_t b)
{
    return ((int64_t)a * b) >> FRACBITS;
}
fixed_t FixedDiv (fixed_t a, fixed_t b)
{
    if ((abs(a) >> 14) >= abs(b)) return (a^b)<0 ? INT_MIN : INT_MAX;
    return ((int64_t)a << 16) / b;
}

18장. 포팅 실습 ③ — 사운드·네트워크

난이도 ★★★★☆예상 시간 3시간키워드: SDL_OpenAudio·SDL_net

18.1 가장 간단한 사운드 — SDL_OpenAudio

static void sdl_callback(void* ud, Uint8* stream, int len) {
    // Doom의 8채널 믹스를 16bit signed로 변환해서 stream에 채움
    memset(stream, 0, len);
    DoomMix((int16_t*)stream, len/4);  // 스테레오 → 샘플 수 = len/4
}
void I_InitSound (void) {
    SDL_AudioSpec want = { .freq=44100, .format=AUDIO_S16, .channels=2,
                           .samples=1024, .callback=sdl_callback };
    SDL_OpenAudio(&want, NULL);
    SDL_PauseAudio(0);
}

18.2 채널 믹싱 알고리즘

void DoomMix(int16_t* out, int nframes) {
    for (int i=0; i<nframes; i++) {
        int L=0, R=0;
        for (int c=0; c<8; c++) {
            if (!chan[c].active) continue;
            int s = (int)chan[c].data[chan[c].pos >> 16] - 128;
            L += s * chan[c].lvol;  R += s * chan[c].rvol;
            chan[c].pos += chan[c].step;
            if ((chan[c].pos >> 16) >= chan[c].len) chan[c].active = 0;
        }
        out[i*2+0] = (int16_t)CLAMP(L, -32768, 32767);
        out[i*2+1] = (int16_t)CLAMP(R, -32768, 32767);
    }
}

18.3 음악(MUS)은 일단 OFF

MUS→MIDI→OPL2 파이프라인은 분량이 큽니다. 학습용 포트에서는 I_PlaySong 등을 빈 함수로 두고 효과음만 살리는 게 합리적입니다. 나중에 OPL2 에뮬레이터를 끼우거나, SDL_mixer의 Mix_PlayMusic으로 우회할 수 있습니다.

19장. 디버깅·트러블슈팅

19.1 출력 디버깅 5계명

  1. printf는 fflush(stdout)와 함께 — 크래시 직전 출력이 사라지지 않게.
  2. 한 줄에 한 변수 — 어디서 죽었는지 즉시 보임.
  3. 출력엔 항상 함수명 — printf("[R_DrawColumn] x=%d\n", x);
  4. 조건부 매크로 — #define DBG(...) fprintf(stderr,"DBG: "__VA_ARGS__)
  5. 완료된 디버그 출력은 지우지 말고 끄세요: #if 0 … #endif
