1장

앱마다 비밀번호를 주면

위임이라는 발상이 나온 자리

민지의 다음 질문

"학적부가 어디 있는지는 알았다. 그러면 학식 예약 앱이 직접 AD 에 물어보면 되는 것 아닌가?"

할 수는 있다. 3부의 코드를 앱에 넣으면 된다. 그런데 그 순간 앱이 비밀번호를 받게 된다. 그게 문제의 전부다.

사용자가 앱의 화면에 학교 비밀번호를 친다는 것은, 그 앱을 만든 사람을 학교만큼 믿는다는 뜻이다. 앱이 열 개면 열 곳을 그렇게 믿어야 한다.

비밀번호 복사본이 늘어난다

앱이 직접 받으면무슨 일이 생기나
앱 서버가 비밀번호를 한 번은 본다 로그에 실수로 찍히면 그대로 유출이다
앱마다 로그인 화면이 다르다 사용자가 가짜 화면을 구별할 수 없다
비밀번호를 바꾸면앱마다 따로 겪는다
2단계 인증을 넣으려면앱을 전부 고쳐야 한다
퇴사자를 막으려면앱을 전부 뒤져야 한다

앱이 하나일 때는 안 보이는 문제다. 셋만 돼도 보인다.

실수 박물관 — 로그에 찍힌 비밀번호

흔한 사고 — 디버깅하려고 폼 전체를 로그로 남겼다. user=minji&pass=… 가 그대로 파일에 쌓였고, 그 로그는 개발자 전원이 볼 수 있는 곳으로 모이고 있었다.

비밀번호를 받지 않는 앱은 이 사고를 낼 수 없다. "조심해서 다루자" 가 아니라 아예 손에 쥐지 않는 것이 이 부에서 배울 방식이다.

1부 5장에서 "어느 쪽이 틀렸는지 말하지 않는다" 를 배웠다. 그건 받은 뒤의 조심이다. 여기서는 그 앞 단계를 없앤다.

호텔 카드키

호텔에 묵을 때 주인의 마스터키를 받지 않는다. 프런트에서 신분증을 보이고, 내 방만 · 사흘만 열리는 카드를 받는다.

호텔여기
신분증학교 비밀번호
프런트IdP — 신분을 확인하는 곳
카드키토큰
내 방만 · 사흘만범위(scope)와 기한(exp)
객실 문앱
객실 문은 신분증을 본 적이 없다. 카드만 본다. 앱이 비밀번호를 안 보는 것이 이와 같다.

SSO — 한 번 확인하고 여러 곳에서 쓴다

Single Sign-On. 프런트에서 한 번 신분증을 보이면 그 호텔 안의 여러 문이 열리는 것.

SSO 인 것SSO 가 아닌 것
확인은 IdP 한 곳에서만 한다 앱마다 같은 비밀번호를 친다 (그건 그냥 같은 비밀번호다)
둘째 앱은 비밀번호를 안 묻는다 비밀번호 관리자가 대신 쳐 주는 것
계정을 끄면 모든 앱이 막힌다 앱마다 계정이 따로 살아 있는 것
"둘째 앱에서 비밀번호를 안 묻는" 이유는 뒤에 나온다 — 브라우저와 IdP 사이의 세션이 살아 있기 때문이다(8장).

흔한 오해 — "액세스 토큰으로 로그인하면 되지 않나". 액세스 토큰은 앱에게 하는 말이 아니다. 자원 서버에 보이라고 준 것이라, 앱이 그 안을 들여다볼 권리가 없다. 로그인에 쓰라고 만든 것이 ID 토큰이다.

1장 퀴즈

Q. 어떤 팀이 "우리는 SSO 를 쓴다" 고 말한다. 들어 보니 앱 다섯 개가 같은 AD 계정과 비밀번호로 각각 로그인한단다. 이것은 SSO 인가? 아니라면 무엇이 빠졌나?

A. SSO 가 아니다. 같은 비밀번호를 쓰는 것일 뿐, 확인하는 곳은 여전히 앱 다섯 곳이다.
증거는 두 가지로 확인할 수 있다. ① 둘째 앱에서 비밀번호를 다시 묻는가 — 물으면 SSO 가 아니다. ② 앱 다섯 곳이 여전히 비밀번호를 손에 쥐는가 — 쥐면 1장에서 센 문제가 그대로 다섯 배다.
빠진 것은 확인을 한 곳으로 모으는 일이다. 그게 IdP 이고, 그 다음 장부터 만든다.

2장

인가 코드 흐름

리다이렉트를 한 걸음씩 따라간다

일곱 걸음

  1. 민지가 앱에서 로그인을 누른다
  2. 앱이 브라우저를 IdP 로 보낸다 (리다이렉트)
  3. IdP 가 자기 화면에서 비밀번호를 받는다
  4. IdP 가 뒤에서 AD 에 묻는다 (3부의 LDAP)
  5. IdP 가 브라우저를 앱으로 돌려보낸다 — 주소에 인가 코드를 실어
  6. 앱이 브라우저를 거치지 않고 IdP 에 코드를 내밀어 토큰을 받는다
  7. 앱이 토큰을 확인하고 자기 세션 쿠키를 심는다 — 그 뒤로는 1부 6장 그대로
2·5 는 브라우저를 통한 이동이고(1부 4장의 302), 6 은 앱과 IdP 가 직접 주고받는 것이다. 이 둘이 다르다는 것이 이 흐름의 뼈대다 — 비밀은 6 에서만 오간다.

2장 퀴즈

Q. 어떤 앱이 로그인 뒤 브라우저 주소창에 ?code=Uv38ByGC…&state=st-demo-123 이 잠깐 떴다가 사라지는 것을 보고 "코드가 노출됐다, 위험하다" 고 보고했다. 정말 위험한가?

A. 그 자체로는 설계대로다. 코드는 원래 주소창을 지나가라고 만든 값이다.
코드 하나로는 토큰을 못 받는다 — client_secret 과 code_verifier 가 더 있어야 하고(3장), 게다가 1분 안에, 한 번만 쓸 수 있다.
정말 위험한 것은 토큰이 주소창에 뜨는 경우다. 그건 옛 implicit 흐름이고, 지금은 쓰지 않는다.

3장

가로채기를 막는 세 장치

state · nonce · PKCE — 셋이 막는 것이 서로 다르다

셋을 한 줄로

장치누가 만드나막는 것
state앱 남의 코드를 내 콜백에 밀어 넣는 것 (로그인 CSRF)
nonce앱 옛 ID 토큰을 다시 밀어 넣는 것 (재생)
code_verifier앱 가로챈 코드를 남이 토큰으로 바꾸는 것
셋 다 앱이 만들고 앱이 기억한다. IdP 는 받아 두었다가 그대로 돌려주거나(state·nonce) 견줘 줄(PKCE) 뿐이다. 그래서 앱이 기억하지 않으면 세 장치가 전부 무용지물이 된다.

state — "내가 시작한 로그인인가"

공격자가 자기 계정으로 로그인해 코드를 하나 얻은 다음, 그 코드가 실린 콜백 주소를 남에게 클릭하게 만든다. 막지 않으면 피해자가 공격자의 계정으로 로그인된 채 앱을 쓰게 된다.

왜 그게 피해인가 — 피해자가 올린 사진·적은 메모·등록한 카드가 전부 공격자의 계정에 쌓인다. 공격자는 나중에 자기 계정으로 들어가 그걸 본다.
막는 법은 간단하다. 앱이 찍어 맞힐 수 없는 값을 하나 만들어 보내 두고, 돌아온 값이 그것과 같은지 본다. 그 값이 state 다.

앱이 기억해 두는 자리

실행 검증 실행 검증

PKCE — 코드를 훔쳐도 못 쓰게

코드는 브라우저의 주소창을 지나간다. 그 순간을 누가 볼 수 있다면? 그러라고 만든 것이 PKCE (Proof Key for Code Exchange, RFC 7636)다.

  1. 앱이 아무도 모르는 값 verifier 를 만든다
  2. 그 값의 해시(challenge)만 IdP 에 미리 보낸다
  3. 코드를 바꿀 때 verifier 원본을 낸다
  4. IdP 가 해시를 다시 계산해 견준다

3장 퀴즈

4장 퀴즈

Q. 어떤 앱이 예약 API 를 부를 때 ID 토큰을 Authorization: Bearer 에 실어 보냈다. API 는 서명이 맞으니 통과시켰다. 무엇이 문제인가?

A. 서명이 맞는 것과 그 자리에 쓸 토큰인지는 다른 문제다.
ID 토큰은 앱에게 "이 사람이 누구다" 를 알리려고 발급된 것이고, aud 가 그 앱을 가리킨다. API 는 자기에게 발급된 토큰만 받아야 한다 — 아니면 다른 앱에 발급된 멀쩡한 토큰이 우리 API 에서 통한다.
그래서 확인할 것이 셋이다. ① 서명 ② aud 가 나인가 ③ typ 이 at+jwt 인가. 우리 IdP 는 셋을 다 본다.

5장 퀴즈

Q. 어떤 팀이 "토큰 안에 주민등록번호를 넣으면 DB 조회를 줄일 수 있다" 고 제안했다. 서명이 있으니 안전하지 않나?

A. 안전하지 않다. 서명은 고치지 못하게 할 뿐, 못 읽게 하지 않는다. 토큰을 받은 사람은 누구나 base64url 을 되돌려 읽는다 — 이 장의 데모가 열쇠 없이 한 그 일이다.
토큰은 브라우저의 저장소·프록시 로그·오류 보고 도구를 지나간다. 민감한 값은 넣지 않고, 필요할 때 userinfo 로 물어본다(4장).
정말 담아야 한다면 서명이 아니라 암호화가 필요하다(JWE, RFC 7516). 이 덱은 거기까지 가지 않는다 — Keycloak 의 기본값도 서명뿐이다.

6장

공개키와 안내문

앱이 IdP 에 대해 알아야 할 것은 주소 하나뿐이다

확인하는 쪽은 공개키만 있으면 된다

서명은 개인키로 만들고 공개키로 확인한다(1부 8장). 그래서 IdP 는 공개키를 대놓고 걸어 둔다.

이것이 SSO 가 여러 앱으로 퍼질 수 있는 이유다. 앱이 백 개여도 IdP 는 비밀을 백 번 나눠 줄 필요가 없다. 공개키 하나를 걸어 두면 백 개가 각자 가져가 확인한다.

JWKS — 공개키를 JSON 으로

실행 검증
RSA 공개키는 숫자 둘로 이뤄진다 — n(아주 큰 수)과 e(보통 65537). AQAB 는 65537 을 base64url 로 적은 것이다.

내거는 코드

실행 검증
여기 개인키가 섞이면 끝이다. JWK 에는 개인키 자리(d·p·q)도 있어서, 라이브러리를 잘못 쓰면 통째로 내걸 수 있다. 우리 코드는 n·e 만 담는다.

kid — 열쇠가 여럿일 때

실행 검증
열쇠를 바꾸는 날을 위해 있는 칸이다. 새 열쇠를 JWKS 에 먼저 얹어 두고, 그 다음부터 새 열쇠로 서명하면 이미 나간 옛 토큰도 만료될 때까지 확인된다. 10부의 키 회전이 이 이야기다.

안내문 — 주소를 손으로 안 적는 이유

실행 검증
주소는 /.well-known/openid-configuration. .well-known 은 "약속된 자리" 라는 뜻의 표준 경로다(RFC 8615).
JSON 의 칸 순서는 알파벳순이라 주소와 목록이 섞여 있다. 여기서는 뒷부분을, 다음 장에서 앞부분을 본다.

무엇을 할 줄 아는지도 함께

실행 검증
code_challenge_methods_supported 에 S256 만 있다. 앱은 이 목록을 보고 무엇을 쓸지 정할 수 있다. 주소를 손으로 적어 두면 이런 것을 알 길이 없다.

앱이 아는 것은 issuer 하나

실행 검증
안내문의 issuer 가 우리가 부른 주소와 같아야 한다. 아니면 남의 안내문을 읽은 것이다. 이 한 줄이 없으면 "안내문 주소만 바꿔치기하면 토큰 검증이 통째로 넘어가는" 길이 열린다 (OIDC Discovery §4.3).

8부에서 바꾸는 것은 이 한 줄뿐이다

실행 검증 예제용
4부의 미니 IdP 를 5부의 진짜 Keycloak 으로 바꿀 때, 앱에서 고치는 것은 -issuer 하나다. 나머지 주소는 안내문에서 따라온다 — 그게 표준을 쓰는 이유다.

6장 퀴즈

Q. 어떤 앱이 성능을 위해 JWKS 를 한 번 받아 영원히 캐시했다. 반년 뒤 갑자기 모든 로그인이 "서명이 맞지 않습니다" 로 실패했다. 무슨 일이 있었나?

A. IdP 가 열쇠를 바꿨다(키 회전). 새 토큰의 kid 가 앱이 들고 있는 옛 JWKS 에 없어서 전부 막힌 것이다.
바르게는 kid 를 못 찾았을 때 JWKS 를 다시 받아 본다 (그리고 그때도 없으면 거절한다). 다시 받는 것에도 상한을 둬야 한다 — 아니면 아무 토큰이나 던져 IdP 를 두드리게 만드는 통로가 된다.
우리 코드는 뜰 때 한 번만 받는다. 모형이라 그렇게 뒀고, 진짜 라이브러리는 이 재시도를 갖고 있다.

여기 실린 것은 비밀번호를 틀리게 넣어 본 쪽이다. 마지막 줄의 invalidCredentials 가 3부 5장에서 본 그 응답이고, 진짜 AD 라면 진단 문구에 data 52e 가 붙어 온다.

실행 검증

그리고 LDAP 은 연결마다 신분이 붙으므로, 사용자 확인은 반드시 다른 연결에서 한다.

7장 퀴즈

Q. 어떤 앱이 로그인 뒤 액세스 토큰을 브라우저 쿠키에 담아 두고, 화면을 그릴 때마다 그 쿠키에서 꺼내 썼다. 무엇이 나빠지나?

A. 두 가지가 나빠진다.
① 토큰이 브라우저로 나간다. 브라우저 안에서 도는 스크립트, 확장 프로그램, 공유 컴퓨터의 다음 사람이 모두 후보가 된다. 서버 안에 두면 그 후보가 없다.
② 토큰이 짧다. 5분마다 만료되므로 화면이 5분마다 깨진다. 그때마다 리프레시를 하려면 그 토큰도 브라우저에 둬야 하고, 문제가 커진다.
우리 앱처럼 세션 쿠키 하나를 심고 토큰은 서버에 두면 둘 다 안 생긴다. 쿠키에는 아무 뜻도 없는 번호만 들어 있다(1부 6장).

8장

세 세션과 로그아웃

"로그아웃했는데 왜 그냥 들어가지나" 의 정체

세션이 셋이다

누구와 누구실제 물건끊는 사람
A브라우저 ↔ IdP IdP 가 심은 쿠키 (MINIIDP_SESSION)IdP
B브라우저 ↔ 앱 앱이 심은 쿠키 (lunch_app_session)앱
C앱 ↔ IdP 토큰 (ID·액세스·리프레시)아무도 — 시간이 끊는다
0부에서 이름을 정해 둔 그 셋이다. 이제 실제 물건이 손에 잡힌다 — A 와 B 는 쿠키 두 개, C 는 토큰이다.
5부에서 진짜 Keycloak 을 켜면 A 의 쿠키 이름이 KEYCLOAK_IDENTITY 로 바뀔 뿐, 하는 일은 같다.

앱만 끊으면 생기는 일

  1. 사용자가 앱에서 로그아웃을 누른다
  2. 앱이 자기 세션 B 를 지운다
  3. 사용자가 다시 로그인을 누른다
  4. IdP 로 갔는데 세션 A 가 살아 있다
  5. 비밀번호를 안 묻고 그냥 통과 — 다시 로그인된다
사용자 눈에는 "로그아웃이 안 됐다" 로 보인다. 공용 컴퓨터에서 이러면 사고다.
그런데 4단계의 그 동작은 고장이 아니다 — SSO 가 바로 그것이다. 둘째 앱에서 비밀번호를 안 묻는 것과 완전히 같은 일이다.

로그아웃 주소

실행 검증
id_token_hint 는 "누구의 세션을 끊는지" 를 알려 준다. 없으면 IdP 가 사용자에게 "정말 로그아웃할까요" 를 되물어야 한다 — 아무나 남의 로그아웃을 시킬 수 있으면 안 되기 때문이다.

돌아온 곳

실행 검증

실수 박물관 — 로그아웃이 400 으로 끝났다

이 덱을 만들다 실제로 겪은 일이다. 앱이 post_logout_redirect_uri 를 자기 콜백 주소로 뒀다. 등록된 주소가 콜백 하나뿐이었으니 그게 자연스러워 보였다.
그런데 로그아웃 뒤 콜백에 도착하면 code 도 state 도 없다. 앱은 "내가 시작한 로그인이 아닙니다" 로 400 을 냈다.
고침은 목록을 따로 두는 것이다. 로그인은 콜백으로 돌아오고, 로그아웃은 첫 화면으로 돌아간다. Keycloak 의 클라이언트 설정에도 칸이 따로 있다 — "Valid redirect URIs" 와 "Valid post logout redirect URIs"(5·7부).

돌아갈 주소는 왜 등록제인가

실행 검증
"앞부분이 같으면 통과" 는 안 된다. https://lunch.campus.example 를 등록해 두면 공격자가 https://lunch.campus.example.공격자.kr 을 만들어 통과시킨다. 글자 그대로 같은지 봐야 한다.

C 는 못 끊는다

이미 나간 토큰은 회수할 수 없다. JWT 는 그 자체로 완결돼 있어서, IdP 가 "그건 취소" 라고 말할 자리가 없다.

방법대가
수명을 짧게 둔다 (5분)가장 흔한 답. 최대 5분은 남는다
부를 때마다 IdP 에 물어본다
(introspection)		 JWT 의 장점(혼자 확인)이 사라진다
취소 목록을 둔다모든 자원 서버가 그 목록을 봐야 한다
그래서 액세스 토큰이 짧고 리프레시 토큰이 긴 것이다(4장). 취소는 리프레시 쪽에서 한다 — 그건 IdP 가 들고 있으니 지울 수 있다.

8장 퀴즈

Q. 도서관 공용 컴퓨터에서 학식 예약 앱을 쓰고 로그아웃했다. 다음 사람이 앱에 들어갔더니 내 이름이 떠 있었다. 세 세션 중 무엇이 안 끊긴 것인가?

A. A(브라우저 ↔ IdP)다. 앱의 세션 B 는 끊겼지만, 로그인 단추를 누르는 순간 IdP 가 A 를 보고 비밀번호 없이 통과시킨 것이다.
앱이 IdP 로도 로그아웃을 보냈어야 한다 — 이 장의 handleLogout 이 하는 일이다.
그리고 브라우저를 아예 닫는 것이 확실하다. 세션 쿠키는 브라우저가 살아 있는 동안만 유효하게 둘 수 있고(1부 6장), 공용 컴퓨터에서는 그 편이 낫다.

캡처를 재현하는 깃발

실행 검증

이 덱의 검은 화면은 두 번 떠서 md5 가 같아야 실린다. 토큰에는 발급 시각과 일련번호가 들어가므로, 그것을 묶어 두지 않으면 같은 명령이 매번 다른 글자를 낸다.

이 IdP 가 안 하는 것

안 하는 것진짜 Keycloak 은
저장소가 메모리뿐데이터베이스에 둔다(6부)
클라이언트가 하나뿐수십 개, 각자 설정
사용자 등록·비밀번호 변경 없음계정 콘솔이 따로 있다
2단계 인증 없음OTP·WebAuthn
감사 로그 없음이벤트로 남긴다(10부)
역할·매퍼 없음9부의 주제
토큰 취소·백채널 로그아웃 없음둘 다 한다
그래도 흐름은 같다. 5부에서 진짜 Keycloak 을 켜면 지금 눌러 본 주소가 그대로 나온다 — 그게 이 장을 만든 이유다.

4부에서 배운 것

  • 앱은 비밀번호를 보지 않는다 — 확인은 IdP 한 곳에서
  • 인가 코드 흐름: 브라우저로 두 번 이동하고, 토큰은 뒤로만 오간다
  • state·nonce·PKCE 는 각각 다른 것을 막는다
  • 토큰 세 장의 쓰임이 다르다 — typ 과 aud 로 갈린다
  • JWT 는 읽히지만 못 고친다. 읽는 것과 믿는 것은 다른 일이다
  • 서명만으로 부족하다 — iss·aud·exp 를 함께 본다
  • 앱이 아는 것은 issuer 하나, 나머지는 안내문에서 온다
  • 세션이 셋이고, 로그아웃은 둘을 끊고 하나는 기다린다
