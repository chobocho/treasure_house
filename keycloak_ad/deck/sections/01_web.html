1장

주소 한 줄에서 시작한다

브라우저 주소창에 무언가를 치면, 그다음에 벌어지는 일

기숙사에 신청서를 넣는다

HTTP 를 처음 만나는 사람에게 가장 잘 통하는 비유는 기숙사 행정실이다.

내가 하는 일

  • 정해진 양식에 적는다
  • 창구에 낸다
  • 답을 받는다
  • 끝. 창구는 나를 기억하지 않는다

브라우저가 하는 일

  • 정해진 모양의 요청을 만든다
  • 서버에 보낸다
  • 응답을 받는다
  • 끝. 서버는 나를 기억하지 않는다
기억하지 않는다(stateless) — 이 한 가지가 이 덱 전체의 출발점이다. 서버는 방금 온 사람과 지금 온 사람이 같은 사람인지 모른다. 그래서 6장에서 손목밴드(쿠키)를 채우게 되고, 4부에서는 그 손목밴드를 남의 건물(Keycloak)에서 받아 오게 된다.

이름을 번호로 — DNS

컴퓨터끼리는 이름이 아니라 번호로 찾아간다. sso.campus.example 같은 이름을 10.1.2.3 같은 번호로 바꿔 주는 것이 DNS(Domain Name System)다.

DNS — 전화번호부다. "김민지" 를 대면 번호를 알려 준다. 브라우저는 요청을 보내기 전에 반드시 한 번 물어본다.
이 덱에서 DNS 가 문제가 되는 곳어디서
Ingress 가 lunch.campus.example 을 받으려면 그 이름이 클러스터 입구를 가리켜야 한다6부
Keycloak 이 AD 를 찾을 때 ldap.ad.campus.example 이 풀려야 한다7부
클러스터 안에서는 keycloak.lunch.svc.cluster.local 같은 이름이 따로 있다2부·6부
실습에서는 DNS 없이 curl --resolve 이름:포트:번호 로 대신한다7장
왜 이름을 쓰나 — 번호는 바뀐다. 서버를 옮기면 번호가 바뀌지만 이름은 그대로 둘 수 있다. 그리고 인증서는 이름에 발급된다(7장) — 번호로 접속하면 자물쇠가 깨지는 이유가 그것이다.

경로와 질의 문자열

경로는 "무엇을", 질의는 "어떤 조건으로" 다. 둘 다 주소의 일부라서 브라우저 기록에도 남고 서버 로그에도 남는다 — 그래서 비밀번호를 여기 실으면 안 된다.

GET /me?week=2026-09-14      그 주의 예약을 보여 달라
GET /login?user=minji        ← 이렇게 만들면 안 된다 (5장에서 이유)
설명용

퍼센트 인코딩 — 주소에는 아스키만 담을 수 있다. 한글이나 빈칸은 %EC%97%86 처럼 바이트를 16진수로 적어 실어 보낸다. 잠시 뒤 404 캡처에서 실물을 본다.

1장 퀴즈

Q. https://sso.campus.example/auth 로 접속했는데 "인증서가 유효하지 않습니다" 가 떴다. 서버를 https://10.1.2.3/auth 로 번호를 직접 쳐서 들어가면 이 오류가 사라질까?

A. 아니다. 오히려 더 확실히 실패한다. 인증서는 이름에 발급된다. 번호로 접속하면 브라우저는 "내가 부른 이름이 10.1.2.3 인데 인증서에는 sso.campus.example 이라고 적혀 있다" 며 거절한다. 7장에서 이 실패를 실제로 만들어 본다.

2장

요청과 응답 — HTTP 는 글자다

오가는 것이 사람이 읽을 수 있는 줄이라는 사실을, 바이트로 확인한다

요청 한 통의 생김새

HTTP 요청은 글자다. 암호도 이진수도 아니다. 줄 몇 개를 순서대로 늘어놓은 것이 전부다.

GET /me HTTP/1.1
Host: lunch.campus.example
User-Agent: curl/8.22.0
Accept: */*
설명용
부분뜻
GET방법(method) — 무엇을 하려는지. 가져오기
/me대상 — 이 서버 안에서 어디를
HTTP/1.1규약 판번호 — 어떤 판으로 말할지
Host: …여기부터 헤더. 한 줄에 하나, 이름: 값
(빈 줄)헤더가 끝났다는 신호. 이게 없으면 서버는 계속 기다린다
헤더(header) — 본문에 앞서 붙이는 쪽지들. "나는 이런 브라우저다", "이런 형식을 받고 싶다", "이 손목밴드를 갖고 있다". 로그인 이야기의 거의 전부가 헤더에서 벌어진다.

진짜 바이트를 본다

curl --trace-ascii 는 선을 타고 오간 바이트를 그대로 보여 준다. 왼쪽 숫자는 그 줄이 시작하는 자리(16진수)다.

실행 검증
  • => 는 내가 보낸 것, <= 는 받은 것이다.
  • 82바이트 — 요청 한 통의 크기가 이만하다.
  • 0050: 줄이 비어 있다. 이 빈 줄이 "헤더 끝" 신호다.
줄 끝은 \r\n 이다 — 눈에는 안 보이지만 캐리지리턴과 라인피드 두 글자다. 그래서 GET /echo HTTP/1.1 18글자 뒤 다음 줄이 0014(=20)에서 시작한다. 18 + 2 = 20.

응답도 같은 모양이다

실행 검증
  • 첫 줄은 상태 줄: HTTP/1.1 200 OK. 다음 장의 주제다.
  • 상태 줄 하나, 헤더 셋, 그리고 빈 줄(2 bytes), 그다음이 본문 76바이트.
  • 본문 안의 . 은 줄바꿈 글자다 — --trace-ascii 가 안 보이는 글자를 점으로 찍는다.
Content-Length — 본문이 몇 바이트인지 미리 알려 준다. 받는 쪽은 이만큼만 읽고 멈춘다. 이 값이 틀리면 브라우저가 영원히 기다리거나 본문이 잘린다.

가장 작은 서버 — 무엇을 만드나

이제 이 대화의 서버 쪽을 직접 짠다. 아는 주소가 둘뿐인 서버다.

실행 검증
import 에 남의 라이브러리가 하나도 없다 — net/http 는 Go 에 들어 있는 표준 라이브러리다. 이 덱의 Go 프로그램은 끝까지 이 원칙을 지킨다. 남의 코드를 부르면 그 안에서 무슨 일이 일어나는지 볼 수 없기 때문이다.

주소 표 하나가 웹 서버의 심장이다

실행 검증
ServeMux — "주소 → 처리 함수" 표. 요청이 오면 이 표에서 맞는 줄을 찾아 그 함수를 부른다. Keycloak 도, 학식 예약 앱도, 크기만 다를 뿐 안쪽은 이 표다.
"/" 는 특별하다 — 다른 어느 줄에도 안 걸린 요청이 전부 여기로 온다. 그래서 handleHello 안에서 직접 404 를 내야 한다. 빼먹으면 오타 난 주소가 조용히 첫 페이지를 보여 준다.

헤더는 여러 개일 수 있다

실행 검증
왜 정렬하나 — 헤더는 지도(map)라 Go 가 돌 때마다 순서를 바꾼다. 그대로 찍으면 같은 요청도 매번 다르게 보여서, "두 번 돌려 같은지" 로 캡처를 검사하는 이 덱의 규칙을 통과할 수 없다.

Host 는 왜 따로 있는가

헤더인데도 Go 는 Host 만 따로 빼서 다른 자리에 담는다. 초심자가 가장 자주 걸려 넘어지는 자리다.

fmt.Fprintf(&b, "Host: %s\n", r.Host)   // 다시 넣어 준다
설명용
가상 호스트 — 컴퓨터 하나에 사이트가 여럿 있을 수 있다. 번호는 하나인데 이름이 여럿인 것이다. 그래서 요청은 "나는 어느 이름으로 왔다" 를 Host 헤더로 알린다.
6부의 복선 — Keycloak 이 자기 주소를 만들 때 이 Host 를 본다. 클러스터 안에서 keycloak:8080 으로 불리는데 바깥 사용자에게는 sso.campus.example 로 답해야 하므로, KC_HOSTNAME 과 프록시 헤더 설정이 필요해진다. "로그인 눌렀더니 내부 주소로 튕겼다" 는 민원의 정체가 이것이다.

상태 번호 사전

401 · 403 · 302 · 307 · 502 를 넣어 보라. 모르는 번호를 넣어도 백 자리 뜻은 알려 준다 — 그게 이 장의 요점이다.

3장 퀴즈

Q. 학식 예약 앱이 갑자기 502 Bad Gateway 를 낸다. 사용자에게 "로그인을 다시 해 보세요" 라고 안내하는 것이 맞을까?

A. 아니다. 5xx 는 서버 쪽 문제다. 게다가 502 는 "앞에 있는 서버(Ingress)는 살아 있는데 뒤(앱 Pod)가 이상한 답을 줬다" 는 뜻이라, 사용자가 할 수 있는 일이 없다. 볼 곳은 Pod 의 상태와 로그다 — 10부.

3xx 는 답이 아니라 안내다

4장 퀴즈

Q. 장바구니에 담기 POST 를 처리한 뒤 302 로 장바구니 화면에 보냈다. 사용자가 그 화면에서 새로고침을 눌렀다. 무슨 일이 일어날까? 그리고 어떻게 고쳐야 할까?

A. 302 는 지금 규약상 브라우저가 GET 으로 바꿔도 되고(MAY) 실제로 그렇게 한다 — 그래서 대개는 무사하다. 하지만 "허용" 이지 "보장" 이 아니라 그 동작에 기대면 안 된다. 303 See Other 를 쓰면 "GET 으로 가라" 가 규약으로 못 박힌다. 우리 02_form_cookie 가 로그인 뒤에 303 을 쓰는 이유가 이것이다. (만약 307 을 썼다면 새로고침이 담기를 한 번 더 보낸다.)

5장 퀴즈

Q. 로그인 폼을 method="get" 으로 만들고 HTTPS 를 쓰면, 선을 타고 가는 값은 암호화되니까 안전하지 않을까?

A. 아니다. HTTPS 는 선 위만 지킨다. 주소는 그 양 끝에서 평문으로 다뤄진다 — 브라우저 기록, 서버의 접근 로그, 중간 프록시의 로그, 그리고 다른 사이트로 넘어갈 때 붙는 Referer 헤더. 네 군데에 비밀번호가 복사된다. 4부에서 토큰을 주소에 싣던 옛 방식이 사라진 이유도 똑같다.

6장 퀴즈

Q. 세션 쿠키의 값을 minji 라고 두면 장부를 안 만들어도 되니까 서버가 훨씬 간단해진다. 왜 그러면 안 될까? 그리고 "값을 서명해서 넣으면" 어떨까?

A. 앞의 것은 안 된다 — 누구나 자기 쿠키를 admin.lee 로 고쳐 보내면 관리자가 된다. 쿠키는 사용자 손에 있는 값이라 절대 그대로 믿으면 안 된다.
뒤의 것은 된다. 값에 서명을 붙이면 고쳤는지 알 수 있어서, 서버가 장부를 들고 있지 않아도 된다. 그것이 바로 4부의 JWT 다 — "장부 없는 세션" 을 만드는 방법. 대신 취소하기 어렵다는 대가가 따라온다.

② 상대가 누군지 확인한다

신원 확인. "내가 부른 그 이름이 맞나?"

이 덱에서 훨씬 중요한 쪽.

"인증서가 신뢰되지 않습니다" 는 암호가 약하다는 말이 아니다. "이 사람이 자기가 말하는 그 사람인지 내가 확인할 길이 없다" 는 말이다. 3부의 LDAPS, 6부의 Ingress, 7부의 truststore 에서 막히는 일이 전부 ②번 때문이지 ①번 때문이 아니다.

확인 순서실패하면 나오는 말

공인 CA 와 사내 CA — 인터넷 사이트는 기기에 미리 들어 있는 공인 CA 가 서명한다. 회사·학교의 도메인 컨트롤러는 대개 사내 CA 가 서명하는데, 그 CA 는 아무 기기에도 미리 들어 있지 않다. 그래서 "이 CA 를 믿어라" 고 따로 알려 줘야 한다 — 7부의 truststore 가 하는 일이 정확히 이것이다.

서버 인증서 — 이름이 전부다

실행 검증
SAN 을 빼먹으면 실패한다 — Go 와 브라우저는 CN 을 아예 보지 않고 subjectAltName(SAN)만 본다. 자바는 SAN 이 없을 때만 CN 으로 물러선다(RFC 6125 §6.4.4 가 허용하는 예외). 어느 쪽이든 CN 만 채운 인증서는 "이름이 안 맞는다" 로 거절당할 수 있다 — 사내 CA 로 발급받을 때 가장 흔한 실수다.

같은 자리에서 만드는 열쇠 하나 — 4부에서 쓴다

실행 검증

실행 검증

이름이 다르면, CA 를 믿어도 거절한다

실행 검증
같은 서버, 같은 인증서, 같은 CA — 이름만 바꿨다. sso.campus.example 대신 lunch.campus.example 로 불렀더니 거절당했다. 인증서는 "암호를 걸어 주는 물건" 이 아니라 "이름을 증명하는 물건" 이라는 뜻이다. 1장 퀴즈의 답이 여기 있다.

-k 는 무엇을 포기하는가

실행 검증
-k(또는 --insecure)는 ②번만 끈다 — 암호화는 그대로다. 대신 상대가 누군지 확인하지 않는다. 중간에서 누가 가로채 자기 인증서를 내밀어도 그냥 붙는다. 그래서 -k 로 문제가 "해결" 됐다면, 해결된 것이 아니라 감시가 꺼진 것이다.
그래도 진단에는 쓴다 — -k 로는 되는데 그냥은 안 된다면 원인이 신원 확인 쪽임을 1초 만에 알 수 있다. 10부의 진단 순서에 이 수가 들어간다.

7장 퀴즈

Q. Keycloak 이 사내 AD 에 LDAPS 로 붙는데 "PKIX path building failed" 로 실패한다. 개발자가 "인증서 검증을 끄면 되지 않나요?" 라고 묻는다. 무엇이라고 답해야 할까?

A. 그 오류는 "이 인증서를 서명한 CA 를 못 믿겠다" 는 뜻이다 (자바판 unable to get local issuer certificate). 검증을 끄면 붙기는 하지만, 그때부터 Keycloak 은 가짜 AD 에게도 비밀번호를 보낸다 — 사내망 안에서 누가 가로채도 알 수 없다. 바른 해법은 사내 CA 인증서를 Keycloak 의 truststore 에 넣는 것이다. 7부에서 그 방법을 그대로 다룬다.

해시 — 되돌릴 수 없는 지문

실행 검증

1부 퀴즈 ①

Q. 학식 예약 앱을 https 로 옮겼더니 로그인이 안 된다. 로그인 POST 는 303 을 잘 내고 Set-Cookie 도 보이는데, 다음 요청에 Cookie 헤더가 안 붙는다. 무엇을 먼저 볼까?

A. 쿠키의 속성과 주소가 맞는지 본다. 가장 흔한 둘 — ① Secure 를 켰는데 어딘가에서 http 로 접속하고 있다. ② Path 가 /login 으로 좁게 잡혀 있어 /me 에서는 안 붙는다. 브라우저 개발자 도구의 저장소 탭에서 쿠키가 실제로 저장됐는지부터 확인하면 ①·② 중 어느 쪽인지 바로 갈린다.

1부 퀴즈 ②

Q. 이 부에서 만든 02_form_cookie 를 그대로 학교에 올리면 안 되는 이유를 셋만 들어 보라.

A. 얼마든지 들 수 있지만, 이 덱이 뒤에서 해결하는 것들은 이렇다.
① 비밀번호가 소스에 있다 — 사람이 늘어나면 손으로 못 관리한다 → 3부에서 AD 로.
② 서비스마다 회원가입을 다시 해야 한다 — 앱이 열 개면 비밀번호가 열 개 → 4부의 SSO.
③ 장부가 서버 메모리에 있다 — 서버를 껐다 켜면 전원 로그아웃되고, 서버가 두 대면 반씩만 로그인된다 → 6부(Postgres)와 4부(토큰).
④ Secure 를 껐고, 비밀번호를 평문으로 비교하고, 잠금 정책이 없다 → 7부.
