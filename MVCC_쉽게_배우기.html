도서관에 사서가 한 명뿐이라면

  • 도서관에 이용자가 한 명뿐이라면 규칙이 필요 없다. 아무 책이나 꺼내 읽고, 메모하고, 꽂으면 된다.
  • 하지만 수천 명이 동시에 드나들면? 누가 책을 고쳐 쓰는 동안 다른 사람이 그 책을 읽으면 무엇을 보게 되는가?
  • 데이터베이스가 매일 마주하는 상황이 정확히 이것이다 — 수천 개의 연결이 같은 데이터를 읽고 쓴다.
  • 이 문제를 다루는 분야가 동시성 제어(concurrency control), 그중 가장 우아한 답이 오늘의 주인공 MVCC다.

은행 잔액이 증발하는 마술

계좌 잔액 100만 원. 월급 50만 원 입금과 보너스 30만 원 입금이 동시에 실행됐다. 기대 잔액은 180만 원 — 그런데 통장에는 130만 원만 남았다. 50만 원은 어디로 갔을까?
  • 두 입금 프로그램 모두 "잔액을 읽고 → 더하고 → 저장"하는 3단계로 동작한다.
  • 둘 다 잔액을 100만 원으로 읽은 뒤 각자 계산해서 저장하면, 나중에 저장한 쪽(100+30=130)이 먼저 저장한 쪽(100+50=150)을 덮어쓴다.
  • 먼저 쓴 갱신이 흔적도 없이 사라진다 — 이것이 갱신 손실(Lost Update)이다.
  • 버그처럼 안 보이는 게 무서운 점이다: 각 프로그램은 완벽하게 옳다. 문제는 오직 "동시에" 실행됐다는 것뿐.

Lost Update를 표로 보기

시각T1 (월급 +50)T2 (보너스 +30)
t1read(잔액) → 100
t2read(잔액) → 100
t3write(잔액 = 150)
t4write(잔액 = 130)
t5최종 잔액 130 — T1의 갱신 증발!
  • 이 표를 스케줄(schedule)이라 부른다 — 여러 트랜잭션의 연산이 실제로 실행된 순서.
  • t2가 문제의 씨앗이다: T1이 아직 쓰지 않은 시점에 T2가 같은 값을 읽었다.
  • 이 덱 내내 이런 표가 계속 나온다. 읽는 법을 지금 익혀 두자: 위에서 아래로 시간이 흐른다.

레이스 컨디션이란

  • 레이스 컨디션(race condition): 실행 타이밍(경주의 승자)에 따라 결과가 달라지는 상황.
  • 스레드 프로그래밍의 mutex, OS의 세마포어, DB의 트랜잭션 — 전부 같은 적과 싸우는 다른 무기다.
  • DB가 특히 어려운 이유: 참여자가 수천 명이고, 네트워크 건너편에 있고, 언제 죽을지 모르고, 데이터는 디스크에 영구 보존돼야 한다.

충돌의 3가지 유형

유형이름무슨 일이 생기나
W-W쓰기-쓰기 충돌두 트랜잭션이 같은 데이터를 쓴다 → Lost Update, Dirty Write
W-R쓰기-읽기 충돌커밋 안 된 쓰기를 읽는다 → Dirty Read
R-W읽기-쓰기 충돌읽은 값이 뒤에서 바뀐다 → Non-repeatable Read, Phantom
  • 동시성 문제는 결국 이 세 종류 충돌의 조합이다. 4장에서 각각을 이름 붙여 정밀하게 분류한다.
  • 주목: 읽기끼리(R-R)는 충돌하지 않는다. 아무도 값을 바꾸지 않으니까.
  • 이 관찰이 MVCC의 출발점이 된다 — "읽기가 이렇게 무해하다면, 읽기를 기다리게 하지 말자."

트랜잭션이라는 약속

  • 트랜잭션(transaction): 여러 읽기·쓰기를 묶어 "전부 되거나, 전부 안 되거나"로 취급하는 실행 단위.
  • 계좌이체가 고전 예시다: "A에서 10만 원 빼기"와 "B에 10만 원 넣기"는 반드시 한 몸이어야 한다.
BEGIN;
  UPDATE accounts SET balance = balance - 100000 WHERE id = 'A';
  UPDATE accounts SET balance = balance + 100000 WHERE id = 'B';
COMMIT;  -- 여기 도달해야 비로소 전체가 확정된다
  • 중간에 서버가 죽으면? ROLLBACK — 아무 일도 없던 것처럼 되돌린다.
  • 동시성 제어의 질문은 이것이다: "여러 트랜잭션이 겹쳐 실행될 때도 이 약속을 지킬 수 있는가?"

ACID 네 글자

글자이름뜻
A원자성 (Atomicity)전부 실행되거나 전혀 실행되지 않거나
C일관성 (Consistency)제약 조건(잔액 ≥ 0 등)이 항상 유지된다
I격리성 (Isolation)동시 실행돼도 혼자 실행된 것처럼 보인다
D지속성 (Durability)커밋된 결과는 장애가 나도 살아남는다
  • 이 덱의 주인공은 I(격리성)다. MVCC는 격리성을 구현하는 기술이다.
  • 격리성은 all-or-nothing이 아니라 단계가 있다 — 완벽한 격리는 비싸서, DB들은 "적당한 격리"를 판다. 그 등급표가 4장의 격리 수준이다.

트랜잭션의 아버지, Jim Gray

  • 1970년대 IBM System R 프로젝트에서 트랜잭션 개념과 락 이론(granular locking)을 정립했다.
  • 격리 수준의 원형인 "Degrees of Consistency"(1975)도 그의 작품 — 4장에서 다시 만난다.
  • 1998년 "데이터베이스와 트랜잭션 처리에 대한 공헌"으로 튜링상 수상.
  • 2007년 요트 항해 중 실종 — 전 세계 데이터베이스 연구자들이 수색에 나선 일화로도 유명하다.

가장 쉬운 해법: 한 줄로 세우기

  • 동시성 문제의 유일하고 완벽한 해법은 사실 자명하다: 동시에 실행하지 않으면 된다.
  • 트랜잭션을 한 줄로 세워 하나씩 실행하면(직렬 실행) 겹침이 없으니 어떤 이상 현상도 생길 수 없다.
  • SQLite의 기본 모드가 실제로 이 전략에 가깝다 — 쓰기는 한 번에 하나만.
  • Redis도 명령을 단일 스레드로 처리한다 — 명령 하나하나가 원자적인 이유.
  • 그런데 왜 모든 DB가 이렇게 안 할까? 다음 슬라이드.

직렬 실행이 느린 이유

  • 트랜잭션은 대부분의 시간을 기다리며 보낸다: 디스크 I/O, 네트워크 왕복, 애플리케이션의 다음 쿼리 대기.
  • 한 줄 세우기는 이 대기 시간에 다른 모든 트랜잭션을 세워 둔다 — CPU와 디스크가 놀면서 처리량이 바닥난다.
  • 비유: 계산대가 30개인 마트에서 계산대 1개만 열고, 손님이 지갑을 찾는 동안에도 줄 전체가 기다리는 꼴.
  • 수천 TPS를 처리해야 하는 실전 DB에서 순수 직렬 실행은 선택지가 아니다.
  • 예외: 인메모리 DB(VoltDB 등)는 대기가 거의 없어 직렬 실행이 오히려 유리하기도 하다

직렬가능성이라는 목표

직렬가능성(serializability): 트랜잭션들을 겹쳐 실행하더라도, 그 결과가 어떤 순서로든 하나씩 실행한 것과 같으면 그 스케줄은 직렬가능하다고 한다.
  • 핵심 통찰: 겹쳐 실행하는 것 자체는 죄가 아니다. 결과가 직렬 실행과 같기만 하면 된다.
  • 즉 "동시에 돌리되, 직렬로 돌린 척하기"가 동시성 제어의 성배다.
  • 겹침은 최대화하고(성능), 결과는 직렬과 동일하게(정확성) — 이 두 마리 토끼를 쫓는 기술이 락, 그리고 MVCC다.
  • 이론적 판정 도구: 선행 그래프(precedence graph)에 사이클이 없으면 직렬가능 — 11장 SSI에서 재등장

스케줄이란 무엇인가

시각T1 (이체)T2 (잔액 조회)
t1read(A) → 100
t2write(A = 90)
t3read(A) → 90
t4read(B) → 50
t5write(B = 60)
t6T2가 본 합계 140 — 실제로는 언제나 150이어야 한다!
  • T2는 "A에서 빠진 뒤, B에 들어가기 전"이라는 존재한 적 없어야 할 중간 세계를 봤다.
  • 이 스케줄은 직렬가능하지 않다 — T1을 먼저 해도, T2를 먼저 해도 합계는 150이기 때문.
  • MVCC는 이 문제를 "T2에게 t1 이전의 세계를 통째로 보여 주는" 방식으로 푼다. 3장에서 확인하자.

두 학파: 비관주의 vs 낙관주의

비관적 (Pessimistic)낙관적 (Optimistic)
철학"충돌은 흔하다. 미리 막자""충돌은 드물다. 일단 하고 나중에 확인"

  • MVCC는 낙관주의 쪽 도구지만, 실전 DB는 둘을 섞어 쓴다 (예: InnoDB = MVCC 읽기 + 락 쓰기).

1장 정리

  • 여러 트랜잭션이 같은 데이터를 겹쳐 다루면 Lost Update 같은 이상 현상이 생긴다 — 각 프로그램이 완벽해도.
  • 충돌은 W-W, W-R, R-W 세 종류. 읽기끼리는 충돌하지 않는다 (MVCC의 씨앗).
  • 완벽한 해법인 직렬 실행은 너무 느리다. 목표는 "겹쳐 돌리되 직렬처럼 보이기" = 직렬가능성.
  • 접근법은 두 갈래: 미리 잠그는 비관주의(락), 일단 진행하고 검증하는 낙관주의(MVCC).
  • 다음 장: 락 방식을 제대로 이해하고, 그 한계에서 MVCC의 필요성을 끌어낸다.

공유 락과 배타 락

  • 공유 락(S, shared): "나 이거 읽는 중" — 여러 트랜잭션이 동시에 잡을 수 있다.
  • 배타 락(X, exclusive): "나 이거 고치는 중" — 오직 한 트랜잭션만. 읽기도 못 들어온다.
  • 규칙: 읽기 전엔 S락, 쓰기 전엔 X락을 얻어야 한다. 못 얻으면? 줄 서서 기다린다.
  • 도서관 비유: S락 = 열람석에서 같이 보기, X락 = 책을 수리실로 가져가 문 잠그기.

S 걸려 있음허용 — 같이 읽기 OK대기 — 읽는 사람 있음
X 걸려 있음대기 — 고치는 중대기 — 고치는 중
  • 표에서 허용은 딱 한 칸, S+S뿐이다 — 1장의 "읽기끼리는 충돌 안 함"이 표에 그대로 반영돼 있다.
  • 나머지 세 칸이 전부 "대기"라는 것, 이것이 락 방식의 모든 비용의 근원이다.
  • 특히 S가 걸려 있으면 X가 기다린다에 밑줄을 긋자 — 읽기가 쓰기를 막는다는 뜻이다.

2단계 잠금 (Two-Phase Locking)

확장 단계: 락을 얻기만 한다 → 축소 단계: 락을 놓기만 한다
  • 락을 걸고 푸는 것만으로는 부족하다 — 언제 걸고 푸는지가 정확성을 좌우한다.
  • 2PL 규칙: 트랜잭션은 락을 하나라도 놓은 뒤에는 새 락을 얻을 수 없다.
  • 즉 트랜잭션의 삶은 두 단계로 나뉜다: 얻기만 하는 전반전, 놓기만 하는 후반전.
  • 이 단순한 규칙 하나로 직렬가능성이 수학적으로 보장된다 (1976년, Eswaran·Gray 등이 증명).

2PL은 왜 옳은가 (직관)

  • 각 트랜잭션에는 "모든 락을 다 모은 순간"(lock point)이 존재한다 — 전반전의 끝.
  • 두 트랜잭션이 같은 데이터를 다뤘다면, 락 때문에 반드시 한쪽이 다른 쪽을 기다렸고, lock point의 순서가 갈린다.
  • 따라서 전체 실행은 lock point 순서로 직렬 실행한 것과 결과가 같다.
  • 비유: 요리사들이 필요한 재료를 전부 확보한 뒤에만 요리를 시작한다면, 결과는 "재료 확보 완료 순서"로 한 명씩 요리한 것과 같다.
  • 엄밀한 증명은 선행 그래프에 사이클이 생길 수 없음을 보이는 것 — 데이터베이스 교과서의 고전 정리

Strict 2PL과 연쇄 롤백

  • 순수 2PL의 함정: 축소 단계에서 락을 놓은 뒤 롤백하면, 그 값을 이미 읽은 다른 트랜잭션도 연쇄로 롤백해야 한다 (cascading abort).
  • 해결: Strict 2PL — 모든 X락(실무에선 대개 모든 락)을 커밋/롤백 순간까지 쥐고 있는다.
  • 커밋 전의 쓰기를 아무도 못 봤으니 연쇄 롤백이 원천 차단된다.
  • 실제 락 기반 DB(전통적 SQL Server, DB2)가 쓰는 방식이 바로 이것이다.
  • 대가: 락을 더 오래 쥔다 → 대기는 더 길어진다. 정확성과 동시성의 맞교환.

데드락 — 서로를 기다리는 두 사람

  • T1이 A를 잠그고 B를 기다리는데, T2는 B를 잠그고 A를 기다린다 — 둘 다 영원히 못 움직인다.
  • 락이 있는 곳에 데드락이 있다. 락 방식의 숙명적 동반자.

데드락 스케줄 예시

시각T1 (A → B 이체)T2 (B → A 이체)
t1X-lock(A) 획득
t2X-lock(B) 획득
t3X-lock(B) 요청 → 대기
t4X-lock(A) 요청 → 대기
t5서로가 서로를 기다림 — 데드락 성립
  • 맞이체(A→B와 B→A 동시 실행)는 데드락 교과서 1페이지 사례이자, 실제 장애 보고서 단골손님이다.
  • 두 트랜잭션 모두 규칙(2PL)을 완벽히 지켰다는 점이 핵심 — 규칙 준수가 데드락을 막아 주지 않는다.

락 입자성 — 어디까지 잠글까

  • 무엇을 잠그나: 행 하나? 페이지? 테이블 전체? DB 전체? — 이것이 락 입자성(granularity).
  • 잘게 잠그면(행) 동시성은 좋지만 락 개수가 폭발하고, 굵게 잠그면(테이블) 관리는 싸지만 다 막힌다.
  • 현대 DB의 답: 평소엔 행 락, 락이 너무 많아지면 테이블 락으로 승격(escalation) — SQL Server가 대표적.
  • 의도 락(intent lock, IS/IX): "이 테이블 안 어딘가의 행을 잠글 예정"이라는 예고 표지판. 행 락과 테이블 락이 공존하게 해 준다.
  • Jim Gray의 granular locking 논문(1975)이 이 체계의 원전이다

읽기가 쓰기를 막는다 — 진짜 문제

시각T1 (월간 매출 집계, 10분)T2 (주문 1건 갱신, 1ms)
t1S-lock(orders) … 집계 시작
t2X-lock(orders의 행) 요청 → 대기
t3… 아직 집계 중 …… 계속 대기 …
t4완료, 락 해제 (10분 후)이제야 실행 — 10분 걸린 1ms 갱신
  • 단지 읽기였을 뿐인 T1이 초고속 갱신 T2를 10분간 세워 놨다.
  • 반대 방향도 성립: 쓰는 중인 행은 읽기가 전부 대기한다. 락 세계에서 읽기와 쓰기는 서로의 적이다.

사례: 야간 리포트 vs 주문 처리

  • 2000년대 초 락 기반 DB 운영의 일상: 야간 배치 리포트가 도는 동안 서비스 응답이 죽는다.
  • 현장의 땜질 처방들이 등장했다:
  • 리포트 전용 복제본(read replica)을 따로 두기 — 돈과 지연으로 해결
  • SQL Server의 NOLOCK 힌트 — 락을 무시하고 읽기. 대신 커밋 안 된 쓰레기 값(dirty read)을 읽을 각오
  • 새벽 2시로 배치 옮기기 — 글로벌 서비스엔 새벽이 없다는 게 함정
  • 전부 "읽기와 쓰기가 서로를 막는다"는 근본 구조를 피해 가는 우회로일 뿐이었다.
  • 근본 해법은 구조를 바꾸는 것 — 그것이 MVCC다.

락 방식의 비용 청구서

  • 대기: 충돌하면 무조건 줄을 선다. 긴 트랜잭션 하나가 뒤의 전부를 세운다.
  • 데드락: 탐지 비용 + 희생자 롤백 + 재시도. 부하가 오를수록 기하급수로 는다.
  • 락 관리 오버헤드: 락 테이블 메모리, 획득/해제 CPU, 락 승격의 급정거.
  • 읽기·쓰기 상호 봉쇄: 분석 쿼리와 OLTP가 한 DB에 못 산다.
  • 그럼에도 락의 장점은 분명하다: 개념이 단순하고, 충돌이 극심한 워크로드에선 "미리 줄 세우기"가 오히려 낭비(롤백 재시도)가 없다.

꿈의 선언

읽기는 쓰기를 막지 않는다 (Readers don't block writers)
쓰기는 읽기를 막지 않는다 (Writers don't block readers)
  • 락의 세계에서 이건 모순이다 — 같은 데이터를 동시에 읽고 쓰면 반드시 한쪽이 이상한 값을 본다.
  • 탈출구는 전제를 의심하는 것: "같은 데이터"가 꼭 하나여야 하는가?
  • 데이터의 과거 버전들을 버리지 않고 쌓아 두면, 읽는 쪽은 안정된 과거를, 쓰는 쪽은 새 버전을 각자 만지면 된다.
  • 서로 다른 것을 만지니 막을 일이 없다 — 이 발상의 전환이 3장의 주제, MVCC다.

2장 정리

  • 락은 S/X 두 종류, 호환은 S+S뿐. 2PL(얻는 단계와 놓는 단계 분리)이 직렬가능성을 보장한다.
  • 실무는 Strict 2PL — 커밋까지 락을 쥐어 연쇄 롤백을 막는다. 대신 대기가 길어진다.
  • 데드락은 락의 숙명. 탐지-처형이 표준 대응이고, 애플리케이션엔 재시도 코드가 필요하다.
  • 최대 약점: 읽기와 쓰기가 서로를 막는다. 긴 분석 쿼리와 OLTP가 공존 불가.
  • 돌파구는 "데이터를 하나로 유지해야 한다"는 전제를 버리는 것 — 버전을 쌓자.

한 문장 정의

UPDATE는 덮어쓰기가 아니라
"새 버전 추가 + 옛 버전에 은퇴 도장"이다
  • MVCC(Multi-Version Concurrency Control): 데이터 항목마다 여러 버전을 유지하고, 각 트랜잭션에게는 자신의 시점에 맞는 버전을 골라 보여 주는 동시성 제어 방식.
  • 읽는 트랜잭션은 이미 확정된 과거 버전을 본다 — 누가 지금 고치고 있어도 상관없다.
  • 쓰는 트랜잭션은 새 버전을 만든다 — 누가 지금 읽고 있어도 그들의 버전은 건드리지 않는다.
  • 그래서 읽기와 쓰기가 서로를 기다릴 이유가 사라진다. 2장 끝의 "꿈의 선언"이 이렇게 실현된다.

덮어쓰기의 역사 — 팔림프세스트

  • 중세엔 양피지가 비싸서 옛 문서를 지우고 재활용했다 — 덮어쓰기(update-in-place)의 원형.
  • 초기 DB도 같았다: 디스크가 금값이라 옛 값을 지우고 그 자리에 새 값을 썼다. 그래서 락이 필수였다.
  • 저장 공간이 싸진 순간, 전제가 무너진다: 굳이 지울 필요가 있나? 역사를 다 남겨 두면 안 되나?

당신은 이미 MVCC를 쓰고 있다: Git

  • Git에서 커밋은 절대 수정되지 않는다. 파일을 고치면 새 커밋(새 버전)이 생길 뿐.
  • 당신이 옛 커밋을 체크아웃해 읽는 동안, 동료가 새 커밋을 푸시해도 당신의 화면은 1비트도 안 바뀐다.
  • "읽는 사람은 자기 시점의 버전을, 쓰는 사람은 새 버전을" — MVCC 그 자체다.
  • DB의 MVCC는 이 아이디어를 행(row) 단위로, 자동으로, 훨씬 짧은 수명으로 굴리는 것이라 보면 된다.

위키백과의 문서 역사

  • 위키백과 문서를 편집해도 이전 판은 사라지지 않는다 — "역사 보기"에 모든 리비전이 남는다.
  • 당신이 문서를 읽는 중에 누가 편집해도, 읽던 페이지가 눈앞에서 바뀌진 않는다. 새로고침해야 새 판이 보인다.
  • "내가 페이지를 연 순간의 판"이 바로 다음에 배울 스냅샷이다.
  • 구글 문서의 버전 기록, 맥의 타임머신 백업, 법전의 개정 이력 — 버전 개념은 어디에나 있다.

버전에 이름표 붙이기

  • 버전을 구분하려면 이름표가 필요하다. MVCC DB는 트랜잭션 ID(txid)를 쓴다 — 트랜잭션마다 부여되는 증가하는 번호.
  • 각 버전에 두 개의 필드를 새긴다:
  • xmin — 이 버전을 만든 트랜잭션의 ID (출생 신고)
  • xmax — 이 버전을 지우거나 대체한 트랜잭션의 ID (은퇴 도장. 현역이면 비어 있음)
  • 이 두 숫자만으로 "이 버전은 어느 시점의 세계에 속하는가"를 판별할 수 있다.
  • 용어는 PostgreSQL 기준. InnoDB는 DB_TRX_ID 등 다른 이름을 쓰지만 원리는 같다 (8장)

버전 체인 그려 보기

계좌 A의 잔액을 txid 100이 생성 → 105가 150으로 → 112가 130으로 갱신한 상태:

잔액 = 100
v1xmin=100 xmax=105
→
잔액 = 150
v2xmin=105 xmax=112
→
잔액 = 130
v3xmin=112 xmax=∅
  • 한 행의 여러 버전이 사슬처럼 이어진다 — 버전 체인(version chain).
  • v1의 xmax와 v2의 xmin이 둘 다 105인 것에 주목: 105의 UPDATE가 "v1 은퇴 + v2 출생"을 동시에 처리했다.
  • DELETE는 새 버전 없이 은퇴 도장(xmax)만 찍는 것. INSERT는 출생 신고(xmin)만 있는 새 버전.

스냅샷 — 시점을 얼리는 사진

스냅샷(snapshot): 트랜잭션이 시작하는 순간 찍는 "세계의 사진". 구체적으로는 그 순간까지 커밋 완료된 트랜잭션의 집합이다.
  • 사진에 찍힌 것(내 시작 전에 커밋된 변경)만 보인다. 사진 이후의 일은 없는 셈 친다.
  • 스냅샷을 표현하는 데 필요한 정보는 의외로 작다:
  • 지금까지 발급된 txid 범위 + 아직 진행 중인 트랜잭션 목록
  • "진행 중 목록에 있으면 아직 안 끝난 것 → 안 보임"으로 판정
  • 트랜잭션 내내 같은 사진을 쓰면 반복 읽기가 일관되고(5장 SI), 문장마다 새로 찍으면 READ COMMITTED가 된다.

읽기 규칙: 내 스냅샷에 맞는 버전 찾기

# 버전 v가 스냅샷 S를 가진 나에게 보이는가?
visible(v, S):
    return committed_before(v.xmin, S)      # 출생이 내 사진에 찍혔고
       and not committed_before(v.xmax, S)  # 은퇴는 아직 안 찍혔다
  • 버전 체인을 따라가며 이 조건을 만족하는 버전을 찾는다 — 있으면 그것이 "내가 보는 값".
  • 만족하는 버전이 하나도 없으면? 내 세계에 그 행은 존재하지 않는 것이다 (아직 안 태어났거나, 이미 지워졌거나).
  • 중요: 이 판정에 락이 전혀 필요 없다. 숫자 비교 몇 번이면 끝.
  • committed_before의 정확한 구현(커밋 로그 조회)은 6장에서 해부한다

쓰기 규칙: 새 버전 추가

  • UPDATE의 실제 동작:
  • ① 현재 버전에 내 txid로 은퇴 도장(xmax)을 찍고
  • ② 새 값으로 새 버전을 만들어 내 txid로 출생 신고(xmin)한다
  • 내가 커밋하기 전까지, 다른 트랜잭션의 스냅샷엔 내 새 버전이 "미확정"이라 안 보인다 — Dirty Read 원천 차단.
  • 내가 롤백하면? 새 버전은 "커밋 안 된 출생"이라 영원히 아무에게도 안 보인다. 지울 필요도 없이 그냥 쓰레기가 된다.
  • 단, 쓰기끼리는 여전히 조율이 필요하다 — 같은 행을 두 트랜잭션이 동시에 갱신하려 하면 락 또는 충돌 검사가 개입한다 (5장).

1장의 사고를 MVCC로 다시 풀기

시각T1 (이체: A−10, B+10)T2 (합계 조회, 스냅샷 S₂)
t1A: 새 버전 90 생성 (미커밋)
t2read(A) → 스냅샷 S₂엔 T1 미커밋 → 100
t3B: 새 버전 60 생성, COMMIT
t4read(B) → S₂ 시점 버전 → 50
t5T2가 본 합계 150 — 일관된 과거! (기다린 사람도 없음)
  • 1장에서 합계 140이 나오던 스케줄이다. 같은 타이밍인데 이제 150이 나온다.
  • 비결: t4에서 T2는 커밋 완료된 B=60이 아니라 자기 사진에 찍힌 B=50을 읽었다.

공짜가 아니다 — 청소 문제

  • 버전을 쌓기만 하면 디스크가 무한히 필요하다. 언젠간 버려야 한다.
  • 버려도 되는 버전의 조건: 어떤 현재·미래 스냅샷에서도 보일 가능성이 없는 버전.
  • = 은퇴 도장이 찍혔고, 그 은퇴가 지금 살아 있는 가장 오래된 스냅샷보다도 과거인 버전
  • 이 청소를 PostgreSQL은 VACUUM(7장), InnoDB는 purge(8장), Oracle은 undo 재사용(9장)이라 부른다.
  • MVCC 운영 사고의 90%는 청소 문제다: 청소가 밀리면 디스크 폭발, 청소가 급하면 "snapshot too old".
  • 미리 기억해 둘 공식: 오래 사는 스냅샷 = 청소 불가 = MVCC의 천적.

역사 1978: David Reed의 박사논문

  • 1978년 MIT 박사논문 "Naming and Synchronization in a Decentralized Computer System"에서 다중 버전 동기화를 처음 체계화했다.
  • "객체의 역사(버전 열)를 유지하고 트랜잭션은 일관된 시점을 본다"는 뼈대가 이미 여기 있다.
  • 1981년 Bernstein·Goodman의 동시성 제어 서베이가 MVCC를 3대 기법(락·타임스탬프·다중버전)의 하나로 자리매김했다.
  • Reed는 TCP/IP 설계 논쟁의 "end-to-end argument" 논문 공저자이기도 하다 — 컴퓨터과학 두 분야에 발자국

데모: 버전 체인 관찰경

  • UPDATE를 누를 때마다 새 버전이 체인에 붙고, 이전 버전엔 은퇴 도장(xmax)이 찍힌다.
  • 슬라이더로 "과거 시점의 관찰자"가 되어 보자 — 관찰자마다 다른 버전이 노랗게 빛난다.
  • VACUUM은 관찰자 슬라이더보다 과거로 은퇴한(아무도 볼 수 없는) 버전만 지운다. 슬라이더를 과거에 두면 그 버전은 청소되지 않는다 — 긴 트랜잭션이 청소를 막는 원리다.

3장 정리

  • MVCC = 덮어쓰기 대신 버전 쌓기. 각 버전은 xmin(출생)·xmax(은퇴)를 갖고 체인으로 이어진다.
  • 트랜잭션은 시작 시 스냅샷(커밋 완료 집합의 사진)을 찍고, 자기 사진에 맞는 버전만 본다.
  • 읽기는 락 없이 숫자 비교만으로 일관된 과거를 본다. 쓰기는 새 버전을 만들 뿐 읽기를 방해하지 않는다.
  • 대가는 청소: 안 보이게 된 버전을 회수해야 하고, 오래 사는 스냅샷이 청소를 막는다.
  • 1978년 이론(Reed) → 1984년 상용화(InterBase, Oracle) → 오늘날 사실상 표준.

격리를 왜 등급으로 파는가

  • 완벽한 격리(직렬가능성)는 가장 비싼 상품이다 — 대기든 롤백이든 반드시 비용을 치른다.
  • 그런데 모든 애플리케이션이 완벽을 요구하진 않는다: 조회수 집계가 1 어긋나는 것과 계좌 잔액이 어긋나는 것은 무게가 다르다.
  • 그래서 표준은 "얼마나 이상한 현상까지 참을 수 있는가"로 4개 등급을 만들었다 — 싸고 이상한 것부터 비싸고 완벽한 것까지.
  • 등급을 고르는 것은 DBA가 아니라 애플리케이션 개발자의 책임이다. 그래서 이 장이 이 덱에서 가장 실용적인 장이다.
  • 뿌리는 Jim Gray의 1975년 "Degrees of Consistency" — 표준화되며 SQL-92에 들어왔다

ANSI SQL-92의 4단계

수준한 줄 설명
READ UNCOMMITTED커밋 안 된 남의 쓰기도 보인다 — 사실상 무법지대
READ COMMITTED커밋된 것만 보인다. 단, 문장마다 세상이 바뀔 수 있다
REPEATABLE READ한 번 읽은 행은 트랜잭션 내내 같은 값 — 새 행(팬텀)은 보장 밖
SERIALIZABLE직렬 실행과 동일한 결과 보장 — 최고 등급
  • 아래로 갈수록 비싸고 안전하다. 표준의 정의는 "어떤 이상 현상을 금지하는가"로 서술된다.
  • 이제 그 이상 현상들을 하나씩 도감처럼 수집하자 — 면접 단골이자 실무 버그의 이름들이다.

이상 현상 도감 ① Dirty Write (더티 라이트)

시각T1T2
t1write(A = 1) (미커밋)
t2write(A = 2) ← 미커밋 값을 덮어씀!
t3ROLLBACK — A를 뭘로 되돌리지?
  • 커밋 안 된 쓰기를 다른 트랜잭션이 덮어쓰는 것. 롤백 처리가 불가능해진다.
  • 이것만은 모든 격리 수준에서, 모든 DB가 금지한다 — READ UNCOMMITTED조차도.
  • 구현: 같은 행에 대한 쓰기는 커밋까지 락으로 직렬화한다. MVCC DB도 쓰기 락만큼은 쓴다.

이상 현상 도감 ② Dirty Read (더티 리드)

시각T1 (이체 중)T2 (잔액 확인)
t1write(A = 900) (미커밋)
t2read(A) → 900 ← 미커밋 값!
t3ROLLBACK (이체 취소)
t4T2는 존재한 적 없는 잔액 900으로 의사결정을 했다
  • 커밋되지 않은(어쩌면 취소될) 값을 읽는 것. READ UNCOMMITTED에서만 허용된다.
  • MVCC에선 공짜로 방지된다: 미커밋 버전은 어떤 스냅샷에도 "커밋 전"이라 안 보인다.
  • SQL Server의 NOLOCK 힌트가 정확히 이 현상을 사서 성능을 얻는 장치다

이상 현상 도감 ③ Non-repeatable Read (반복 불가능 읽기)

시각T1 (보고서)T2
t1read(A) → 100
t2write(A = 200), COMMIT
t3read(A) → 200 ← 아까랑 다르다!
  • 같은 행을 두 번 읽었는데 값이 달라진 것. 사이에 낀 커밋된 갱신 때문이다 (더티 리드와 구분!).
  • READ COMMITTED까지 허용, REPEATABLE READ부터 금지.
  • MVCC식 해법: 트랜잭션 내내 같은 스냅샷을 쓰면 두 번째 읽기도 같은 버전을 본다.

이상 현상 도감 ④ Phantom Read (유령 읽기)

시각T1 (감사)T2
t1SELECT count(*) WHERE 급여>500 → 3명
t2INSERT (급여=900), COMMIT
t3같은 SELECT → 4명 ← 유령 등장!
  • 행 하나의 값이 변한 게 아니라, 조건에 걸리는 행의 집합이 변했다 — 새 행이 유령처럼 나타난다.
  • 행 단위 락으론 못 막는다: 아직 존재하지 않는 행엔 락을 걸 수 없으니까. (해법: 범위 락, 프레디킷 락, 또는 스냅샷)
  • 표준상 REPEATABLE READ에서도 허용되고 SERIALIZABLE에서만 금지 — 하지만 스냅샷 기반 DB는 REPEATABLE READ에서도 대부분 막아 준다 (다음 장).

이상 현상 도감 ⑤ Lost Update (갱신 손실)

  • 1장의 잔액 증발 사건 — read-modify-write 두 개가 겹치며 한쪽 갱신이 사라지는 것.
  • 흥미롭게도 ANSI 표준의 공식 3대 현상(더티/반복불가/팬텀)에 없다. 표준의 구멍 중 하나.
  • DB별 대응이 갈린다:
  • PostgreSQL REPEATABLE READ: 감지하고 한쪽을 에러로 중단 ("could not serialize access due to concurrent update")
  • MySQL InnoDB REPEATABLE READ: 막아 주지 않는다! SELECT FOR UPDATE나 원자적 UPDATE를 써야 한다
  • 애플리케이션 레벨: UPDATE t SET n = n + 1처럼 DB 안에서 계산하면 원천 차단

이상 현상 도감 ⑥ Read Skew (읽기 왜곡)

  • 1장 스케줄 슬라이드에서 본 "합계 140" 사건의 정식 이름이다.
  • 여러 행을 읽는 도중 다른 트랜잭션의 커밋이 끼어들어, 행마다 다른 시점의 값을 읽게 되는 것.
  • 각 읽기는 전부 "커밋된 값"이라 READ COMMITTED 규칙 위반이 아니다 — 그런데 조합하면 존재한 적 없는 세계다.
  • 피해 단골: 백업(테이블 앞쪽과 뒤쪽이 다른 시점), 집계 리포트, 불변식 검사(A+B=총액).
  • 해법이 바로 스냅샷: 모든 읽기를 한 시점의 사진에 고정한다. MVCC가 가장 빛나는 지점.

이상 현상 도감 ⑦ Write Skew (쓰기 왜곡)

시각T1 (김 박사 퇴근)T2 (이 박사 퇴근)
t1당직 의사 수 확인 → 2명 (OK)
t2당직 의사 수 확인 → 2명 (OK)
t3나(김) 퇴근 처리, COMMIT
t4나(이) 퇴근 처리, COMMIT
t5규칙 "당직 최소 1명" 붕괴 — 병원이 비었다
  • 둘 다 읽은 것도 옳고, 서로 다른 행을 썼으니 쓰기 충돌도 없다 — 그런데 조합하면 규칙이 깨진다.
  • 같은 행을 다투는 Lost Update의 사촌이지만 훨씬 교활하다. 스냅샷 격리로도 못 막는다 — 5장과 11장의 핵심 떡밥.

1995년의 반란 — ANSI 비판 논문

"A Critique of ANSI SQL Isolation Levels" (1995) — Berenson, Bernstein, Gray, Melton, O'Neil, O'Neil. 표준 격리 수준 정의가 모호하고 불완전함을 조목조목 격파한 전설의 논문.
  • 지적 1: 표준의 현상 정의가 모호해 넓게/좁게 두 가지로 읽힌다 — 좁게 읽으면 막아도 데이터가 깨진다.
  • 지적 2: Lost Update, Read/Write Skew 같은 중요한 현상이 표에 아예 없다.
  • 지적 3: 락이 아닌 방식(다중 버전)으로 구현된 격리는 표준의 틀로 분류가 안 된다.
  • 그래서 이 논문이 새 이름을 만들었다 — 스냅샷 격리(Snapshot Isolation). 다음 장 전체가 이 이야기다.

같은 이름, 다른 뜻

"REPEATABLE READ"라는 같은 간판 아래에서 PostgreSQL과 MySQL은 다르게 동작한다. 이식할 때 최다 발생 함정.
  • PostgreSQL REPEATABLE READ: 진짜 스냅샷 격리. 팬텀도 안 보이고, 동시 갱신 충돌 시 에러를 낸다.
  • MySQL REPEATABLE READ: 일반 SELECT는 스냅샷을 읽지만, UPDATE·SELECT FOR UPDATE는 최신 커밋 값을 본다(locking read) — Lost Update 가능, 갭 락으로 팬텀 일부 차단.
  • Oracle SERIALIZABLE: 이름은 최고 등급인데 실체는 SI — Write Skew가 뚫린다.
  • 교훈: 격리 수준은 이름이 아니라 "무엇을 막아 주는가"로 확인해야 한다. 그 확인 도구가 이상 현상 도감이다.

4장 정리

  • 격리는 등급제 상품: READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE.
  • 이상 현상 도감 7종: Dirty Write/Read, Non-repeatable, Phantom, Lost Update, Read Skew, Write Skew.
  • ANSI 표는 반쪽짜리 — 1995년 비판 논문이 구멍(Lost Update, Skew류)을 밝히고 "스냅샷 격리"를 명명했다.
  • 같은 격리 이름도 DB마다 실체가 다르다. 이름 말고 "막아 주는 현상 목록"으로 판단하라.
  • 다음 장: MVCC가 자연스럽게 도달하는 그 지점, 스냅샷 격리를 정밀 해부.

스냅샷 격리의 두 가지 규칙

① 읽기: 시작 순간의 스냅샷만 본다
② 쓰기: 같은 데이터에 먼저 커밋한 자가 이긴다
  • 1995년 비판 논문이 정식화한 격리 수준. MVCC 엔진이 "트랜잭션당 스냅샷 1장"을 주면 자연히 얻어진다.
  • 규칙 ①이 읽기의 일관성을, 규칙 ②가 쓰기의 안전(Lost Update 차단)을 담당한다.
  • PostgreSQL의 REPEATABLE READ, Oracle의 SERIALIZABLE, SQL Server의 SNAPSHOT이 전부 이것이다.

규칙 1: 시작 시점 스냅샷

  • 트랜잭션의 첫 문장이 실행되는 순간 스냅샷을 찍고, 커밋/롤백까지 그 사진만 본다.
  • 효과: 트랜잭션 안의 모든 SELECT가 한 시점의 일관된 세계를 본다.
  • 반복 읽기가 항상 같고(Non-repeatable 차단), 집계 도중 세상이 안 바뀌고(Read Skew 차단), 새 행도 안 나타난다(Phantom 차단)
  • 자기 자신의 쓰기는 예외적으로 보인다 — 내가 방금 넣은 행을 내가 못 보면 곤란하니까.
  • 비유: 트랜잭션 시작 = 도서관 전체를 통째로 복사해 개인 열람실을 받는 것. 남들이 원본을 고쳐도 내 열람실은 고요하다.

규칙 2: 첫 커밋자 승리 (First-Committer-Wins)

  • 1장의 잔액 증발(Lost Update)이 이 규칙으로 차단된다 — 증발 대신 명시적 에러 + 재시도.

  • PostgreSQL의 실제 순서: UPDATE 시도 → 상대가 그 행을 쓰는 중이면 대기 → 상대가 커밋하면 "could not serialize access due to concurrent update" 에러, 롤백하면 계속 진행.
  • 어느 쪽이든 애플리케이션의 의무는 같다: 이 에러는 재시도하라는 신호다.

SI가 차단하는 현상들

  • Dirty Read — 미커밋 버전은 스냅샷에 없다. 차단.
  • Non-repeatable Read — 내내 같은 사진을 보니 두 번째 읽기도 같다. 차단.
  • Read Skew — 모든 행을 같은 시점으로 읽는다. 차단.
  • Phantom — 새로 커밋된 행은 내 사진에 없다. 차단 (표준 REPEATABLE READ보다 강하다!).
  • Lost Update — 첫 커밋자 승리가 차단.
  • 락 없이, 대기 없이 이만큼을 막는다 — 1995년 논문이 SI에 주목한 이유다.

구멍 1: Write Skew 재방문

  • 당직 의사 사건을 SI 규칙으로 검산해 보자:
  • 규칙 ① 위반? 아니오 — 둘 다 자기 스냅샷(당직 2명)을 정직하게 읽었다
  • 규칙 ② 위반? 아니오 — 김 박사는 김 박사 행을, 이 박사는 이 박사 행을 썼다. 같은 데이터가 아니다
  • SI의 충돌 검사는 쓰기 집합의 겹침만 본다. "읽은 것에 기반해 다른 곳에 썼다"는 연결 고리는 못 본다.
  • 실전 변형: 재고 마감, 예산 한도 검사, 중복 예약 방지, 아이디 중복 검사 — "조건을 읽고, 조건 밖에 쓰는" 모든 패턴.
  • 대응은 11장에서: 명시적 락으로 충돌을 만들거나(SELECT FOR UPDATE), SSI로 격상하거나.

구멍 2: 읽기 전용 트랜잭션도 이상해진다

  • 2004년 Fekete·O'Neil·O'Neil이 발견한 충격적 사례: 읽기만 하는 제3의 트랜잭션이 "직렬 실행으론 불가능한 순서"의 세계를 목격할 수 있다.
  • 시나리오 뼈대: 잔액 두 계좌(당좌 0, 저축 0), T1은 저축+20 입금, T2는 당좌−10 인출(합계가 음수면 수수료 1 부과), T3은 잔액 조회.
  • T3이 "입금은 됐는데 인출은 안 된" 스냅샷을 봤는데, 최종 결과는 "수수료가 부과된" 세계가 될 수 있다 — 어떤 직렬 순서로도 설명 불가.
  • 교훈: SI의 스냅샷은 언제나 일관된 과거처럼 보이지만, 그 과거가 "실제 일어난 역사"와 모순일 수 있다.
  • 이 발견이 SSI(직렬화 가능한 SI) 연구에 불을 붙였다 — 11장

SI는 SERIALIZABLE이 아니다

Oracle에서 SET TRANSACTION ISOLATION LEVEL SERIALIZABLE을 실행하면 얻는 것은 진짜 직렬가능성이 아니라 스냅샷 격리다. 2000년대 내내 논쟁을 일으킨 유명한 사실.
  • PostgreSQL도 9.0까지는 SERIALIZABLE = SI였다. 9.1(2011)에서 진짜 직렬화(SSI)로 교체했다.
  • 실무 점검법: 당직 의사 시나리오(Write Skew)를 두 세션으로 직접 돌려 보면 된다. 둘 다 커밋되면 그 DB의 "SERIALIZABLE"은 SI다.
  • 은행·정산처럼 불변식이 생명인 도메인에선 이 차이가 돈 사고로 직결된다.

그래도 SI가 사랑받는 이유

  • 읽기 전용 작업(리포트, 백업, 분석)에 완벽한 일관성 + 제로 대기 — pg_dump가 서비스 중에 돌 수 있는 이유.
  • 대부분의 OLTP 패턴(한 행 읽고 그 행 고치기)에서 Write Skew가 아예 성립하지 않는다.
  • 이상 현상 중 가장 흔하고 치명적인 것들(더티, 반복불가, 팬텀, 갱신손실)을 전부 잡는다.
  • 비용은 버전 저장 공간과 청소뿐 — 락 대기·데드락 비용보다 대개 싸다.
  • 공학적 판단: "완벽하진 않지만 충분히 좋고 매우 빠른" 스위트 스팟. 그래서 30년째 업계 표준 지위다.

READ COMMITTED도 MVCC다

  • PostgreSQL·Oracle의 기본값인 READ COMMITTED도 락으로 읽기를 막는 게 아니라 스냅샷으로 구현된다.
  • 차이는 딱 하나 — 사진을 찍는 주기:
  • READ COMMITTED: 문장(statement)마다 새 스냅샷 — 문장 하나는 일관되게, 문장 사이엔 세상이 바뀔 수 있음
  • SI (REPEATABLE READ): 트랜잭션에 스냅샷 한 장
  • 그래서 READ COMMITTED에서도 Dirty Read는 없고, 문장 단위 Read Skew도 없다 — 락 기반 READ COMMITTED보다 강하다.
  • 단, 트랜잭션 안에서 문장을 여러 번 실행하면 값이 변할 수 있다(Non-repeatable) — 기본값의 함정.

5장 정리

  • SI = 시작 시점 스냅샷(읽기) + 첫 커밋자 승리(쓰기). MVCC 엔진의 자연스러운 격리 수준.
  • 더티·반복불가·팬텀·읽기왜곡·갱신손실을 전부 차단 — 표준 REPEATABLE READ보다 강하다.
  • 구멍은 Write Skew와 읽기 전용 이상 — "읽은 곳과 쓴 곳이 다른" 패턴은 못 본다.
  • Oracle의 SERIALIZABLE은 SI다. 이름에 속지 말 것.
  • 이제 이론은 끝. 다음 다섯 장은 실제 DB들이 이걸 어떻게 구현했는지 뜯어 본다 — 먼저 PostgreSQL.

왜 PostgreSQL부터인가

  • PostgreSQL의 MVCC는 3장의 개념도와 구현이 거의 1:1로 대응한다 — 배우기에 최고의 표본.
  • xmin/xmax라는 용어 자체가 PostgreSQL의 실제 시스템 컬럼 이름이다.
  • 모든 것이 문서화·오픈소스라 직접 눈으로 확인할 수 있다 — 이 장 끝에서 실습한다.

혈통: Berkeley와 Stonebraker

  • UC 버클리의 Stonebraker는 Ingres(1970년대)에 이어 1986년 POSTGRES 프로젝트를 시작했다.
  • POSTGRES의 급진적 설계: "덮어쓰기 없는 스토리지" — 과거를 전부 남겨 타임트래블 쿼리("3월 1일 시점의 이 테이블")까지 지원했다.
  • 타임트래블은 성능 문제로 훗날 제거됐지만, "버전을 테이블에 쌓는" 뼈대는 살아남아 1999년(6.5) 오늘의 MVCC가 됐다.

튜플 = 행의 한 버전

  • PostgreSQL 용어로 튜플(tuple)은 "행의 물리적 버전 하나"다. 논리적 행 하나에 튜플 여러 개가 있을 수 있다.
  • 모든 튜플은 힙(heap) 파일의 8KB 페이지 안에 산다 — 옛 버전도 새 버전도 같은 테이블 공간에 섞여 있다.
  • 이것이 PostgreSQL 방식의 첫 특징: 버전 보관소가 따로 없다. 테이블 자체가 보관소다.
  • 비교 예고: InnoDB·Oracle은 옛 버전을 별도 공간(undo)에 보관한다 — 8·9장에서 장단점 대결

INSERT의 발자국

-- txid 100이 실행:
INSERT INTO accounts VALUES ('A', 1000);
('A', 1000)
xmin=100 xmax=0
  • 새 튜플 하나가 페이지의 빈자리에 적힌다. xmin=100, xmax=0(현역).
  • txid 100이 커밋하기 전: 다른 트랜잭션의 가시성 판정에서 "출생 미확정" → 안 보인다.
  • 롤백하면? 튜플은 그대로 남지만 "출생이 취소된" 상태 — 영원히 아무에게도 안 보이는 쓰레기가 되고, 나중에 VACUUM이 회수한다.
  • 즉 PostgreSQL엔 INSERT를 되돌리는 undo 작업이 없다 — 롤백이 순간인 이유.

UPDATE의 발자국

-- txid 105가 실행:
UPDATE accounts SET balance = 1500 WHERE id = 'A';
('A', 1000)
xmin=100 xmax=105 ctid→
→
('A', 1500)
xmin=105 xmax=0
  • UPDATE = 옛 튜플에 xmax 도장 + 새 튜플 INSERT. 제자리 수정이 아니다.
  • 옛 튜플의 ctid가 새 튜플을 가리켜 체인이 이어진다.
  • 한 글자만 바꿔도 행 전체가 복사된다 — 이것이 PostgreSQL 쓰기 증폭 논쟁의 뿌리 (13장).

DELETE의 발자국

-- txid 112가 실행:
DELETE FROM accounts WHERE id = 'A';
('A', 1500)
xmin=105 xmax=112
  • DELETE는 데이터를 지우지 않는다 — xmax 도장 하나 찍는 게 전부다.
  • 112 커밋 후에도 튜플은 디스크에 그대로 있다. 다만 새 스냅샷들에게 "은퇴 확정"으로 판정돼 안 보일 뿐.
  • 112보다 먼저 시작한 트랜잭션의 스냅샷에는? 여전히 보인다 — 그래서 지울 수 없는 것이다.
  • 진짜 삭제는 "아무 스냅샷도 이 튜플을 볼 수 없게 된 후" VACUUM의 몫 — 7장.

공식 그림으로 복습

  • 가로축이 시간, 상자들이 튜플(버전), 각 트랜잭션이 어느 버전을 보는지가 화살표로 그려져 있다.
  • 이 그림 한 장을 설명할 수 있으면 6장 전반부를 통과한 것이다.

txid — 32비트 시계

  • txid는 32비트 부호 없는 정수로, 쓰기 트랜잭션마다 1씩 증가하며 발급된다.
  • 읽기 전용 트랜잭션은 txid를 아예 안 받는다 — 번호 절약 + 성능
  • 32비트 = 약 42억. 초당 1만 쓰기 트랜잭션이면 5일마다 21억(반환점)을 돈다 — 언젠가 반드시 순환한다.
  • PostgreSQL의 비교 규칙은 "모듈로 시계": 각 txid에서 앞으로 21억은 미래, 뒤로 21억은 과거.
  • 순환을 방치하면 "과거가 미래로 둔갑"하는 대참사가 난다 — freeze라는 안전장치가 7장에 등장한다.
  • 특수 txid: 0=Invalid, 1=Bootstrap, 2=Frozen("영원한 과거")

스냅샷의 실제 구조

-- 지금 내 스냅샷을 구경하기
SELECT pg_current_snapshot();
-- 결과 예: 748:754:748,751,752
--          xmin:xmax:진행중 목록(xip)
필드뜻판정
xmin진행 중인 것 중 가장 오래된 txid이보다 과거 = 무조건 결판남
xmax아직 발급 안 된 첫 txid이상이면 = 미래, 무조건 안 보임
xip 목록스냅샷 순간 진행 중이던 txid들목록에 있으면 = 미커밋, 안 보임
  • 주의: 스냅샷의 xmin/xmax와 튜플의 xmin/xmax는 이름만 같은 다른 것이다 — 혼동 최다 지점.

가시성 판정 전체 알고리즘

# 튜플 t가 스냅샷 s에서 보이는가 (단순화)
def visible(t, s):
    # 1. 출생 확인
    if t.xmin == my_txid:  pass            # 내가 만든 건 보임
    elif not committed(t.xmin): return False   # 롤백/진행중
    elif in_snapshot_future(t.xmin, s): return False  # 사진 이후 출생
    # 2. 은퇴 확인
    if t.xmax == 0: return True            # 현역
    if t.xmax == my_txid: return False     # 내가 지운 것
    if not committed(t.xmax): return True  # 지운 놈이 미확정 → 아직 보임
    return in_snapshot_future(t.xmax, s)   # 은퇴가 사진 이후면 보임
  • 모든 SELECT의 모든 행마다 이 판정이 돈다. 그런데도 빠른 이유가 다음 슬라이드.

커밋 로그(clog)와 힌트 비트

  • "txid 105는 커밋됐나?"의 답은 clog(커밋 로그)에 있다 — txid당 2비트(진행/커밋/롤백)를 기록하는 배열.
  • 매 행마다 clog를 찾아가면 느리다. 그래서 힌트 비트: 한 번 판정한 결과("xmin 커밋 확정" 등)를 튜플 헤더의 infomask에 캐시한다.
  • 다음 방문자부터는 clog 조회 없이 비트만 보면 끝.
  • 부작용: 대량 INSERT 직후의 첫 SELECT가 느리고 쓰기 I/O까지 발생하는 미스터리의 정체 — 첫 방문자가 힌트 비트를 다 써 주고 있는 것.
  • 그래서 대량 적재 후엔 VACUUM(또는 자동청소)을 한 번 돌려 주는 것이 관례다

직접 관찰 실습 ①: xmin/xmax 보기

CREATE TABLE t (id int, v text);
INSERT INTO t VALUES (1, 'a');

SELECT xmin, xmax, ctid, * FROM t;
--  xmin | xmax | ctid  | id | v
--   748 |    0 | (0,1) |  1 | a      ← 현역 버전

UPDATE t SET v = 'b';
SELECT xmin, xmax, ctid, * FROM t;
--   749 |    0 | (0,2) |  1 | b      ← 새 버전 (옛 버전은 안 보임)
  • 모든 테이블에서 숨은 컬럼 xmin, xmax, ctid를 그냥 SELECT할 수 있다 — 지금 아무 PostgreSQL에서 해 보라.
  • UPDATE 후 ctid가 (0,1)에서 (0,2)로 바뀌었다: 행이 "이사"했다. 새 튜플이 생겼다는 물증이다.

직접 관찰 실습 ②: 죽은 버전까지 보기

-- pageinspect 확장으로 페이지 속 모든 튜플(죽은 것 포함) 열람
CREATE EXTENSION pageinspect;
SELECT lp, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('t', 0));
--  lp | t_xmin | t_xmax | t_ctid
--   1 |    748 |    749 | (0,2)   ← 은퇴한 v1, 아직 디스크에!
--   2 |    749 |      0 | (0,2)   ← 현역 v2
  • 일반 SELECT엔 안 보이던 옛 버전이 페이지 안에 그대로 있다 — "DELETE/UPDATE는 지우지 않는다"의 실증.
  • lp 1의 t_ctid가 (0,2)를 가리킨다: 버전 체인의 화살표를 눈으로 확인.
  • 이 죽은 튜플(dead tuple)들의 운명이 다음 장 주제다.

6장 정리

  • PostgreSQL은 버전(튜플)을 테이블 힙에 그대로 쌓는다 — 별도 undo 공간이 없다.
  • 튜플 헤더의 xmin/xmax/ctid가 출생·은퇴·체인을 기록. UPDATE = xmax 도장 + 새 튜플.
  • 스냅샷은 xmin:xmax:진행중목록 세 값. 가시성은 이 값들과 clog(+힌트 비트)로 판정한다.
  • 롤백이 순간인 대신, 쓰레기(죽은 튜플)가 테이블 안에 쌓인다.
  • txid는 32비트 순환 시계 — 그리고 쌓인 쓰레기와 시계 순환, 두 가지 청구서가 7장에서 날아온다.

죽은 튜플이 쌓인다

  • 죽은 튜플(dead tuple): 은퇴(xmax 커밋)했고, 이제 어떤 스냅샷에서도 보이지 않는 버전.
  • UPDATE가 많은 테이블은 죽은 튜플 공장이다: 행 100만 개를 10번 갱신하면 죽은 튜플 1000만 개.
  • 롤백된 INSERT, 실패한 COPY의 잔해도 전부 죽은 튜플로 남는다.

블로트 — 뚱뚱해진 테이블

실화 패턴: 행 10만 개짜리 "작은" 상태 테이블이 디스크 40GB를 차지한다. 매초 전 행을 UPDATE하는 잡이 있었고, VACUUM이 따라잡지 못했다. 살아 있는 데이터는 8MB.
  • 블로트(bloat): 죽은 튜플과 회수 안 된 빈자리가 차지하는 헛살.
  • 해악 1 — 디스크 낭비는 차라리 약과다.
  • 해악 2 — 스캔이 느려진다: 8MB 읽을 일을 40GB 읽는다. 캐시도 쓰레기로 채워진다.
  • 해악 3 — 인덱스도 같이 붓는다: 죽은 튜플을 가리키는 포인터가 인덱스에도 쌓인다.
  • 블로트율 추정: pgstattuple 확장, 또는 커뮤니티의 블로트 추정 쿼리로 정기 점검하는 것이 관례.

VACUUM이 하는 일

  • ① 죽은 튜플을 찾아 빈자리로 표시한다 — 그 공간은 같은 테이블의 새 튜플이 재사용 (파일 크기는 대개 안 줄어든다!).
  • ② 그 튜플들을 가리키던 인덱스 엔트리 제거.
  • ③ 힌트 비트 정리, 가시성 지도·공간 지도 갱신.
  • ④ 오래된 튜플 freeze (뒤에서 설명).
  • 중요한 성질: 일반 VACUUM은 읽기·쓰기와 동시에 돌 수 있다 — 테이블을 잠그지 않는다.
  • "VACUUM 돌리면 서비스 멈추지 않나요?"의 답: 일반 VACUUM은 아니오. FULL이 문제 — 다음 슬라이드

무엇을 지워도 되는가 — xmin horizon

지울 수 있다 ⟺ xmax < 모든 살아 있는 스냅샷의 xmin
  • 시스템 전체에서 가장 오래된 활성 스냅샷의 xmin을 horizon(지평선)이라 부른다.
  • 지평선보다 과거에 은퇴한 튜플만 안전하게 지울 수 있다 — 누군가의 사진에 아직 찍혀 있을 수 있으니.
  • 따라서 3시간짜리 트랜잭션 하나가 열려 있으면, 그 3시간 동안 전체 DB의 청소가 지평선에 묶인다.
  • 3장의 예고("오래 사는 스냅샷 = MVCC의 천적")가 여기서 현실이 된다.
  • 확인: SELECT backend_xmin FROM pg_stat_activity — 지평선을 붙잡은 범인 찾기

autovacuum — 자동 청소부

  • PostgreSQL 8.3(2008)부터 기본 탑재된 백그라운드 데몬. 테이블별 통계를 보고 알아서 VACUUM/ANALYZE를 돌린다.
  • 발동 조건(기본값): 죽은 튜플이 전체 행의 20% + 50개를 넘으면.
  • 흔한 오해와 진실:
  • "autovacuum이 느려서 껐어요" — 최악의 수. 청소가 밀리면 블로트·wraparound로 더 큰 대가를 치른다
  • 올바른 방향은 끄기가 아니라 더 자주, 더 세게 돌게 만드는 것
  • 대형 테이블 함정: 20%면 1억 행 테이블에서 2000만 죽은 튜플 — 발동이 너무 늦다. 테이블별로 비율을 낮춰야 한다.

autovacuum 튜닝 다이얼

# 발동 시점: 대형 테이블은 비율 대신 절대 수치로
ALTER TABLE big SET (autovacuum_vacuum_scale_factor = 0.01);

# 청소 속도: I/O 제한(기본 200) 완화 — 요즘 SSD면 과감히
autovacuum_vacuum_cost_limit = 2000

# 일꾼 수 (기본 3) — 테이블 많으면 증원
autovacuum_max_workers = 6
  • 철학: autovacuum이 쓰기 속도를 따라잡을 수 있게 만드는 것이 전부다.
  • PostgreSQL 13+에선 인덱스 병렬 VACUUM, 17에선 메모리 관리 개선 등 매 버전 빨라지고 있다 — 업그레이드 자체가 튜닝.

가시성 지도와 공간 지도

  • 테이블마다 두 개의 보조 파일이 따라다닌다:
  • 가시성 지도(visibility map, _vm): "이 페이지의 모든 튜플은 모두에게 보임" 비트를 페이지당 기록
  • 공간 지도(free space map, _fsm): 페이지별 빈 공간 크기 기록 — INSERT가 자리를 빨리 찾게
  • 가시성 지도의 두 가지 보은:
  • VACUUM이 "전부 보임" 페이지를 통째로 건너뛴다 — 대형 테이블 청소가 견딜 만한 이유
  • index-only scan이 가능해진다 — 13장에서 상세히

freeze — 시계 순환 대비

  • 6장의 복선 회수: txid는 32비트 시계라 21억 차이가 나면 과거·미래 판정이 뒤집힌다.
  • 이대로면 20억 트랜잭션 전에 만든 행은 "미래에 만들어진 행"으로 둔갑해 안 보이게 된다 — 데이터 증발.
  • 해법: 충분히 늙은 튜플의 xmin을 "영원한 과거" 표시(frozen)로 바꿔 시계 비교에서 제외한다 — 이것이 freeze.
  • VACUUM이 겸업한다: vacuum_freeze_min_age(기본 5000만)보다 늙은 튜플을 얼린다.
  • 테이블 나이(relfrozenxid 기준)가 autovacuum_freeze_max_age(기본 2억)에 달하면, autovacuum이 꺼져 있어도 강제 aggressive vacuum이 발동한다.

wraparound 공포 사례

최후 방어선: 남은 여유가 300만 txid 아래로 떨어지면 PostgreSQL은 새 쓰기 트랜잭션을 거부하기 시작한다. "database is not accepting commands to avoid wraparound data loss" — 서비스 전면 중단이다.
  • 2015년 Sentry: wraparound 방어 VACUUM 때문에 수 시간 쓰기 중단 — 사후 분석 블로그가 업계 교과서가 됐다.
  • 2019년 Mailchimp/Mandrill: 같은 계열 장애로 대규모 메일 발송 중단.
  • 공통 패턴: 초대형 테이블 + 청소 지연 누적 + 어느 날 갑자기 강제 VACUUM 폭풍.
  • 예방 지표 딱 하나만 외우자: SELECT max(age(relfrozenxid)) FROM pg_class — 2억에 접근하면 경보.
  • 64비트 txid로의 전환이 오래 논의 중이지만, 튜플 헤더 호환성 때문에 아직 32비트다

데모: 블로트 실험실

  • UPDATE를 누를 때마다 살아 있는 튜플(초록)이 죽은 튜플(회색)로 바뀌며 페이지가 부풀어 오른다.
  • VACUUM을 누르면 죽은 튜플이 빈칸(재사용 가능)으로 바뀐다 — 파일(칸 수)은 안 줄어드는 것도 관찰하자.
  • "긴 트랜잭션 열어 두기"를 켠 채 VACUUM을 눌러 보라 — 지평선에 걸린 죽은 튜플은 청소되지 않는다.

-- 지평선을 붙잡은 세션 수배
SELECT pid, state, age(backend_xmin), xact_start
FROM pg_stat_activity WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC;

-- wraparound 거리
SELECT datname, age(datfrozenxid) FROM pg_database;
  • 이 세 쿼리를 대시보드에 올려 두면 PostgreSQL MVCC 사고의 대부분을 사전에 본다.

7장 정리

  • 죽은 튜플은 UPDATE/DELETE/롤백의 필연적 부산물. 방치하면 블로트로 스캔·캐시·인덱스가 병든다.
  • VACUUM은 지평선(가장 오래된 활성 스냅샷) 아래의 죽은 튜플만 회수한다. FULL은 최후 수단.
  • autovacuum은 끄는 게 아니라 세게 트는 것. 대형 테이블은 scale_factor를 낮춰라.
  • 32비트 txid 순환은 freeze로 방어. age(relfrozenxid) 2억 접근 = 경보.
  • 긴 트랜잭션, idle in transaction, 버려진 복제 슬롯 — 오래된 xmin을 남기는 모든 것이 적이다.

InnoDB 간단 연대기

  • 핀란드의 Heikki Tuuri가 1990년대에 개발한 스토리지 엔진. 2001년 MySQL에 탑재됐다.
  • 당시 MySQL 기본 엔진 MyISAM은 트랜잭션도 MVCC도 없었다 — InnoDB가 "진짜 DB" 기능을 가져왔다.
  • 2005년 Oracle이 InnoDB(Innobase)를, 2010년엔 MySQL(Sun)까지 인수 — 지금은 둘 다 Oracle 소유.
  • MySQL 5.5(2010)부터 기본 엔진. 오늘날 "MySQL의 MVCC" = InnoDB의 MVCC다.

설계 철학: 제자리 갱신 + undo

PostgreSQL: 새 버전을 테이블에, 옛 버전도 테이블에
InnoDB: 최신 버전만 테이블에, 옛 버전은 undo 로그에
  • InnoDB의 UPDATE는 제자리 갱신이다: 테이블(클러스터드 인덱스)의 행을 직접 새 값으로 고친다.
  • 대신 고치기 직전, "되돌리는 데 필요한 정보"를 undo 로그라는 별도 공간에 적어 둔다.
  • undo 로그의 원래 용도는 롤백(되돌리기)이다 — MVCC는 이를 재활용해 "과거 버전 읽기"에 쓴다.
  • 결과: 테이블은 항상 날씬하고(최신만), 과거는 별채에 쌓인다. 장단점이 PostgreSQL과 정확히 반대로 갈린다.

히든 컬럼 3형제

DB_ROW_ID6BPK가 없을 때 쓰는 내부 행 번호 (MVCC와는 무관)
  • InnoDB의 모든 행 뒤에 몰래 붙는 컬럼들이다. SELECT로는 안 보인다.
  • xmax에 해당하는 필드가 없다는 점이 눈에 띈다 — 삭제는 행에 delete 마크를 찍고 역시 undo에 기록한다.
  • 트랜잭션 ID가 48비트라 PostgreSQL의 32비트 wraparound 같은 문제가 사실상 없다.

  • 더 과거가 필요하면 체인을 더 따라간다 — 필요한 시점의 버전이 나올 때까지.
  • 비용 구조: 최신을 읽으면 공짜, 과거로 갈수록 복원 비용 증가. "최신 읽기가 대부분"인 OLTP에 최적화된 도박이다.

버전 체인 방향이 반대다

  • PostgreSQL의 ctid 체인: 옛 버전 → 새 버전 (앞으로 걷기).
  • InnoDB의 ROLL_PTR 체인: 최신 버전 → 옛 버전 (뒤로 걷기).
  • 이 방향 차이가 성능 특성을 가른다:
  • PostgreSQL: 어떤 버전이든 힙에서 직접 만난다. 대신 스캔이 죽은 버전까지 밟는다
  • InnoDB: 최신은 즉시, 과거는 복원 비용. 대신 스캔은 항상 날씬한 최신만 밟는다
  • 기억법: PostgreSQL은 "역사책을 본문에 끼워 두는" 방식, InnoDB는 "본문은 최신판, 개정 이력은 부록"인 방식.

Read View — InnoDB의 스냅샷

필드뜻
m_ids생성 순간 활성(미커밋)이던 트랜잭션 ID 목록
m_up_limit_idm_ids의 최솟값 — 이보다 작으면 무조건 커밋 완료
m_low_limit_id다음에 발급될 ID — 이상이면 미래
m_creator_trx_id이 뷰를 만든 트랜잭션 자신
  • 이름만 다를 뿐 PostgreSQL 스냅샷(xmin:xmax:xip)과 완전히 같은 3요소다.
  • 개념이 같으니 당연하다 — 스냅샷을 표현하는 최소 정보가 원래 이 세 가지다.
  • up/low라는 이름이 직관과 반대라 악명 높다: up_limit이 아래쪽 경계다. 시험에 나오면 필드 뜻으로 기억하라

가시성 판정 규칙

# 행(또는 undo 버전)의 TRX_ID가 Read View에서 보이는가
def visible(trx_id, view):
    if trx_id == view.creator:      return True   # 내 쓰기
    if trx_id < view.up_limit:      return True   # 확실한 과거
    if trx_id >= view.low_limit:    return False  # 미래
    return trx_id not in view.m_ids               # 활성 목록 검사

# 안 보이면: ROLL_PTR 따라 undo 체인을 거슬러 보이는 버전까지
  • 6장의 PostgreSQL 알고리즘과 나란히 놓고 보라 — 구조가 판박이다.
  • 차이는 "안 보일 때 무엇을 하는가"뿐: PostgreSQL은 힙의 다른 튜플을 검사, InnoDB는 undo를 거슬러 복원.

RR과 RC의 차이는 한 줄

  • InnoDB에서 REPEATABLE READ와 READ COMMITTED의 구현 차이는 단 하나다:
  • REPEATABLE READ: Read View를 첫 SELECT 때 1회 만들고 끝까지 재사용
  • READ COMMITTED: SELECT마다 새 Read View
  • 5장의 "문장 스냅샷 vs 트랜잭션 스냅샷" 표가 코드 한 줄의 차이로 구현되는 것.
  • MySQL 기본값은 REPEATABLE READ — 복제(binlog) 일관성의 역사적 사정 때문에 메이저 중 유일하게 높은 기본값을 쓴다.

일관 읽기 vs 잠금 읽기

  • InnoDB의 이중생활: 같은 트랜잭션 안에서도 일반 SELECT는 스냅샷을, UPDATE는 최신을 본다.
  • 그래서 "SELECT로는 있었는데 UPDATE 해 보니 없다(또는 값이 다르다)"는 미스터리가 발생한다 — 버그가 아니라 설계다.

주의: RR에서도 Lost Update

시각T1T2

t2UPDATE 잔액=150, COMMIT

  • PostgreSQL RR이라면 t3에서 에러가 났을 자리다. InnoDB는 조용히 통과시킨다 — first-committer-wins 검사가 없다.
  • InnoDB에서의 처방: SELECT ... FOR UPDATE로 처음부터 잠그거나, UPDATE t SET n=n+50처럼 DB 안 계산으로.

갭 락 — 팬텀을 락으로 잡기

  • InnoDB RR의 잠금 읽기는 스냅샷의 보호를 못 받는다 — 그럼 팬텀은? 답: 갭 락(gap lock).
  • 갭 락: 인덱스 레코드 "사이의 빈틈"을 잠가, 그 범위에 새 행이 INSERT되는 것을 막는다.
  • next-key lock = 레코드 락 + 그 앞 갭 락. RR에서 범위 조건 잠금 읽기의 기본 동작
  • 효과: SELECT ... WHERE k BETWEEN 10 AND 20 FOR UPDATE 후엔 그 범위에 아무도 INSERT 못 한다 — 팬텀 차단.
  • 부작용: 예상 밖의 락 대기와 데드락의 단골 원인. READ COMMITTED로 내리면 갭 락이 대부분 사라진다 — 이것이 RC로 내려 쓰는 팀이 많은 이유.

purge — InnoDB의 청소부

  • 어떤 Read View에서도 더 이상 필요 없어진 undo 레코드를 지우는 백그라운드 스레드가 purge다.
  • PostgreSQL VACUUM과의 결정적 차이: 청소 대상이 테이블이 아니라 undo 공간이다. 테이블은 애초에 안 부푼다.
  • delete 마크된 행의 실제 제거와 인덱스 정리도 purge가 담당한다.
  • 같은 아킬레스건: 오래된 Read View(긴 트랜잭션)가 있으면 purge가 밀린다 — undo가 자라고, 과거 복원 체인이 길어져 읽기까지 느려진다.
  • 플랫폼은 달라도 병명은 같다: "긴 트랜잭션 = MVCC 청소 방해죄"

  • PostgreSQL의 n_dead_tup + backend_xmin 조합과 정확히 대응하는 운영 루틴이다.

8장 정리

  • InnoDB는 최신 버전만 테이블에 두고, 과거는 undo 로그 체인(ROLL_PTR)으로 복원한다.
  • Read View(m_ids, up/low limit)는 PostgreSQL 스냅샷과 동일 개념. RR/RC 차이는 뷰 생성 주기 하나.
  • 일반 SELECT는 스냅샷, UPDATE·FOR UPDATE는 최신+락 — 이중생활을 이해해야 미스터리가 풀린다.
  • RR에서도 Lost Update는 통과된다. 갭 락은 팬텀을 막지만 데드락의 단골.
  • purge와 history list length는 VACUUM과 n_dead_tup의 InnoDB 버전이다.

Oracle — 대중화의 원조

  • Oracle V4(1984)의 "read consistency"는 MVCC식 읽기를 대중 시장에 처음 가져온 기능이다.
  • "쿼리는 시작 시점의 데이터를 본다, 락 없이" — 당시 락 기반 경쟁자들에 대한 강력한 차별화 무기였다.
  • 수십 년간 Oracle DBA 교육의 제1장이 이 읽기 일관성이었고, 용어(undo, SCN)도 업계 표준어가 됐다.

undo 세그먼트와 SCN

  • 구조는 InnoDB의 원형이다 (정확히는 InnoDB가 Oracle을 참고했다):
  • 행은 제자리 갱신, 직전 이미지는 undo 세그먼트(옛 이름 롤백 세그먼트)에 보관
  • 블록 헤더에 어떤 트랜잭션이 언제 고쳤는지(ITL 슬롯) 기록
  • SCN(System Change Number): 시스템 전역에서 단조 증가하는 논리 시계. 커밋마다 증가한다.
  • 트랜잭션/문장은 "시작 SCN"을 기억하고, 그보다 나중에 바뀐 블록을 만나면 undo를 적용해 과거 블록을 복원해 읽는다.
  • txid 목록 대신 단일 시계값으로 스냅샷을 표현하는 셈 — 12장 분산 MVCC의 타임스탬프 방식과 통한다.

읽기 일관성의 동작

  • 블록을 읽을 때: "이 블록, 내 시작 SCN 이후에 수정됐나?"
  • 수정됐다면 undo에서 변경 전 정보를 가져와 일관 읽기용 블록 사본(CR block)을 메모리에 만들어 그걸 읽는다.
  • 여러 단계 과거가 필요하면 undo를 여러 번 적용 — InnoDB의 체인 거슬러 걷기와 동일.
  • 기본 격리는 READ COMMITTED(문장 SCN), SERIALIZABLE을 고르면 트랜잭션 SCN 고정 = 스냅샷 격리 (5장에서 본 그 사실).
  • Oracle엔 진짜 SERIALIZABLE(SSI류)이 아예 없다 — write skew는 개발자가 SELECT FOR UPDATE로 직접 막아야 한다.

ORA-01555: snapshot too old

Oracle DBA라면 악몽처럼 아는 에러. 몇 시간째 돌던 대형 리포트가 막판에 "ORA-01555 snapshot too old"로 사망한다 — 처음부터 다시.
  • 원인: undo 공간은 유한하고 순환 재사용된다. 오래된 undo가 새 트랜잭션에 덮어써지면, 긴 쿼리가 과거 복원에 필요한 재료를 잃는다.
  • PostgreSQL과의 대조가 흥미롭다:
  • PostgreSQL: 과거를 지키느라 청소를 멈춘다 → 블로트로 고통 (읽는 자가 이긴다)
  • Oracle: 청소(재사용)를 강행한다 → 긴 쿼리가 죽는다 (쓰는 자가 이긴다)
  • "오래된 스냅샷을 누가 이기는가"라는 정책 선택의 문제 — 정답은 없고 트레이드오프만 있다.
  • 현대 Oracle은 undo_retention과 자동 튜닝으로 완화하지만 원리는 그대로다

Oracle 방식의 성격

  • 강점: 테이블이 절대 안 부푼다. VACUUM 같은 전면 청소 작업 자체가 없다. OLTP 최신 읽기가 가장 빠른 축.
  • 약점: 긴 분석 쿼리와 대량 갱신이 공존하면 ORA-01555 리스크. CR 블록 생성이 CPU·메모리를 먹는다.
  • 롤백이 비싸다: undo를 실제로 적용해 되돌려야 한다. 거대 트랜잭션 롤백은 몇 시간짜리 이벤트가 되기도.
  • PostgreSQL 롤백은 0초(버리면 끝) — 6장에서 본 대조점
  • 운영 격언: "Oracle에선 undo를 여유 있게, 쿼리는 짧게."

SQL Server — 락 왕국

  • SQL Server는 전통적으로 순수 락 기반(Strict 2PL)의 대표 주자였다 — 2장에서 배운 방식 그대로.
  • READ COMMITTED에서도 읽기가 S락을 잡았고, 읽기-쓰기 봉쇄와 데드락이 일상이었다.
  • 그래서 현장엔 NOLOCK 힌트(= READ UNCOMMITTED, 더티 리드 감수)가 만연했다 — "빠르지만 가끔 틀린 리포트"의 시대.
  • 2장의 "락 방식의 비용 청구서"를 그대로 지불하며 사는 왕국이었던 셈.

개종: 2005년의 스냅샷 도입

  • SQL Server 2005가 행 버전 관리(row versioning)를 도입하며 MVCC 진영에 합류했다.
  • 두 가지 옵트인 모드가 생겼다:
  • RCSI (Read Committed Snapshot Isolation): READ COMMITTED의 구현을 락에서 문장 스냅샷으로 교체
  • SNAPSHOT 격리: 트랜잭션 스냅샷 — 5장의 SI 그 자체
  • 기본값은 여전히 락 기반 READ COMMITTED다 (Azure SQL Database는 RCSI가 기본!) — 하위 호환 때문.
  • 같은 DB가 락 모드와 MVCC 모드를 스위치로 오간다는 점에서, 두 진영의 차이를 몸으로 보여 주는 표본이다.

  • SQL Server는 옛 버전을 어디 두는가? 테이블도 undo도 아닌 제3의 답: tempdb의 버전 스토어.

  • 결과: 버전 부담이 tempdb로 집중된다 — RCSI를 켠 서버의 tempdb 용량·I/O 설계가 운영 포인트.

9장 정리

  • Oracle은 1984년부터 undo+SCN으로 읽기 일관성을 제공한 MVCC 대중화의 원조. SERIALIZABLE은 SI다.
  • undo 재사용이 긴 쿼리를 죽이는 ORA-01555는 "과거 보존 vs 청소"의 정책 선택을 보여 준다.
  • SQL Server는 락 왕국이었으나 2005년 RCSI/SNAPSHOT으로 개종 — 버전은 tempdb에 보관.
  • MVCC 구현은 append형 / undo형 / 별도 스토어형 세 가족. 공통 천적은 긴 트랜잭션.
  • 방식 간 우열은 워크로드가 결정한다 — "어디에 버전을 두고 누가 청소하나"로 모든 구현을 읽어라.

Firebird — 원조의 후예

  • 3장에서 만난 1984년 InterBase의 직계 오픈소스 후손이다 (2000년 소스 공개 후 포크).
  • Jim Starkey의 "multi-generational architecture"를 그대로 잇는다 — 행 버전을 테이블에 쌓는 append형.
  • 재미있는 설계: 전용 청소 데몬 대신 지나가던 읽기가 청소를 겸한다 (cooperative garbage collection) + sweep 주기.
  • PostgreSQL과 독립적으로 같은 결론(버전 쌓기 + 청소)에 도달한 평행 진화 사례로, 비교 학습 가치가 크다.

SQLite — WAL이라는 우회로

  • 기본 모드의 SQLite는 DB 파일 하나 + 통 락 — 쓰는 동안 읽기도 막히는 1장식 세계였다.
  • 2010년 WAL(Write-Ahead Log) 모드가 게임을 바꿨다: 변경을 원본에 덮어쓰지 않고 별도 WAL 파일에 append한다.
  • 읽기는 "WAL의 어느 지점까지 반영된 세계"라는 스냅샷을 잡고 읽는다 — 쓰기와 동시에, 막힘 없이.
  • "덮어쓰지 않고 옆에 쌓는다 + 시점 고정" — 형태는 달라도 MVCC의 핵심 공식 그대로다.

SQLite WAL의 한계와 미덕

  • 한계: 쓰기는 여전히 한 번에 하나다. 다중 라이터 동시성은 없다 — 필요하면 서버형 DB로 갈 때다.
  • 체크포인트: WAL이 자라면 내용을 본 파일에 반영하고 줄인다 — 여기서도 오래 열린 읽기가 체크포인트를 막는다 (네 번째 반복. 확정적으로 법칙이다).
  • 미덕: 이 단순한 구조로 "읽기는 절대 안 막힘 + 직렬 쓰기 = 공짜 SERIALIZABLE"을 얻는다.
  • 모바일 앱(당신의 폰 안 수십 개 앱)이 대부분 이 모드로 돈다 — 아마 지구에서 가장 많이 실행되는 MVCC 유사물.

LMDB — copy-on-write 트리

  • LMDB(OpenLDAP의 키-밸류 스토어)는 B+트리를 copy-on-write로 다룬다: 페이지를 고칠 때 새 페이지에 복사해 쓰고, 루트까지 새 경로를 만든다.
  • 옛 루트에서 내려가면 옛 세계 전체가, 새 루트에서 내려가면 새 세계가 보인다 — 루트 포인터 하나가 스냅샷.
  • 읽기 트랜잭션은 락 제로, 쓰기는 단일 라이터. 구조가 단순해 극도로 빠르고 견고하다.

RocksDB — LSM과 시퀀스 번호

  • RocksDB(LevelDB 계열, 페이스북)는 LSM 트리: 모든 쓰기가 append이고, 덮어쓰기가 원래 없다.
  • 모든 키-밸류 항목에 전역 증가 시퀀스 번호가 붙는다 — 사실상 자동 버전 번호.
  • 스냅샷 = "시퀀스 번호 N 이하만 보기". 같은 키의 여러 버전 중 N 이하 최신을 고른다.
  • 컴팩션이 청소부 역할: 활성 스냅샷이 필요로 하는 버전은 남기고 나머지 옛 버전을 병합·폐기한다.
  • MySQL의 MyRocks, CockroachDB(구 스토리지), TiKV 등이 이 위에 MVCC를 얹는다 — LSM과 MVCC는 천생연분이다.

키-밸류들의 버전: HBase·Cassandra

  • HBase: 셀(row, column) 하나가 타임스탬프별 다중 버전을 갖는 게 데이터 모델 자체다. "최근 3개 버전 유지" 같은 정책을 테이블에 선언한다.
  • Cassandra: 모든 쓰기에 타임스탬프가 붙고, 읽기는 "가장 최근 타임스탬프 승리"로 병합한다. 삭제도 tombstone(묘비) 기록 = xmax의 사촌.
  • 둘 다 트랜잭션 격리는 약하지만, "버전 + 타임스탬프 + 나중에 청소(컴팩션)"라는 MVCC의 뼈대는 공유한다.
  • 관찰: 분산 세계로 갈수록 "락으로 합의"보다 "버전으로 공존"이 압도적으로 유리해진다 — 12장의 예고편.

인메모리 DB: HANA와 Hekaton

  • 디스크가 사라지면 락의 비용(캐시 미스, 컨텍스트 스위치)이 상대적으로 거대해진다 — 인메모리 DB가 MVCC에 올인하는 이유.
  • SAP HANA: 컬럼 스토어 + MVCC. 델타 저장소에 새 버전을 쌓고 주기적으로 병합한다.
  • SQL Server Hekaton(In-Memory OLTP): 완전 락-프리 MVCC — 버전을 메모리에 체인으로 두고, 타임스탬프 검증으로 커밋. 락도 래치도 없다.
  • 학계 연구(Hekaton, HyPer, 그리고 CMU의 비교 논문들)가 2010년대 MVCC 르네상스를 이끌었다.
  • 최신 경향: 낙관적 MVCC + 하드웨어 친화(캐시 라인, NUMA) 설계가 표준 레시피

파일시스템의 MVCC: ZFS·Btrfs

  • ZFS·Btrfs·APFS는 블록을 덮어쓰지 않는 copy-on-write 파일시스템이다 — LMDB의 대형판.
  • 스냅샷 기능이 공짜에 가깝다: 현재 루트 포인터를 복사해 두면 그 순간의 파일시스템 전체가 보존된다.
  • 맥의 타임머신(APFS 스냅샷), Docker 이미지 레이어, VM 스냅샷 — 전부 같은 원리의 산물.
  • Git까지 포함하면 그림이 완성된다: "불변 버전 + 포인터 이동 + 가비지 컬렉션"은 데이터 관리의 범용 패턴이고, DB의 MVCC는 그중 트랜잭션에 특화된 갈래다.

애플리케이션 레벨 MVCC

  • DB 밖에서도 같은 패턴을 직접 구현하는 경우가 많다:
  • 이벤트 소싱: 상태를 덮어쓰지 않고 사건(이벤트)을 append — 상태는 이벤트의 누적으로 재구성
  • 불변 자료구조(Clojure, Immutable.js): 수정 = 새 버전 생성, 옛 참조는 안전
  • 협업 문서(Google Docs류): 작업 로그 + 버전으로 동시 편집 병합
  • 언제 직접 하나: 감사 이력이 업무 요구일 때(누가 언제 뭘 바꿨나), 도메인이 "정정"을 개념으로 가질 때(회계의 붉은 줄 정정).
  • DB의 MVCC 버전은 청소되는 임시물이다 — 감사 이력이 필요하면 별도 테이블에 스스로 쌓아야 한다는 것, 의외로 자주 헷갈리는 지점.

낙관적 락 — 가난한 자의 MVCC

-- 행에 version 컬럼을 두고
SELECT id, data, version FROM doc WHERE id = 7;   -- version=3 읽음

-- 갱신 때 "내가 읽은 버전 그대로일 때만" 조건부 갱신
UPDATE doc SET data = '...', version = 4
WHERE id = 7 AND version = 3;
-- 영향 행 수 0이면 → 누가 먼저 고쳤다 → 다시 읽고 재시도
  • ORM(JPA @Version, Rails lock_version)의 낙관적 락이 정확히 이 패턴이다.
  • first-committer-wins를 UPDATE 한 줄로 구현한 것 — 5장 SI 규칙 ②의 수제 버전.
  • 웹의 stateless 요청 사이(폼 열어 두고 10분 뒤 저장)처럼 DB 트랜잭션으로 못 묶는 구간에서 특히 유용하다.

10장 정리

  • Firebird는 원조 InterBase의 후예로 PostgreSQL과 평행 진화한 append형.
  • SQLite WAL, LMDB CoW 트리, RocksDB 시퀀스 번호 — 형태는 달라도 "덮지 않고 쌓고, 시점을 고정"은 같다.
  • HBase·Cassandra의 타임스탬프 버전, 인메모리 DB의 락-프리 MVCC, ZFS·Git의 스냅샷까지 — 범용 패턴이다.
  • version 컬럼 낙관적 락은 애플리케이션에서 손수 굴리는 미니 SI다.
  • 구현 전체를 관통한 법칙 재확인: 버전을 쌓는 자, 반드시 청소 문제를 만난다.

문제 복습: SI의 구멍

  • 5장의 결론: SI는 Write Skew와 읽기 전용 이상을 통과시킨다.
  • 공통 구조: 두 트랜잭션이 서로가 읽은 것을 서로가 바꾼다 — 그런데 쓰는 곳이 달라 충돌 검사에 안 걸린다.
  • 당직 의사, 재고 마감, 한도 검사, 중복 예약, 아이디 중복 검사 — 전부 이 구조다.
  • 목표: 이 패턴까지 잡아 진짜 직렬가능성을 얻되, 락 왕국(2장)으로 돌아가진 않기.
  • 세 가지 처방이 있다 — 싼 것부터 차례로 보자.

처방 1: 충돌을 수제작한다 (materialize conflict)

-- 당직 규칙을 지키는 자물쇠 행을 하나 만든다
CREATE TABLE oncall_guard (ward int PRIMARY KEY, dummy int);

-- 퇴근 트랜잭션마다 이 행을 먼저 갱신
BEGIN;
UPDATE oncall_guard SET dummy = dummy + 1 WHERE ward = 3;
-- 이제 같은 병동의 두 퇴근은 "같은 행을 쓰는" 사이가 됐다
-- → SI의 first-committer-wins가 자동으로 한쪽을 잡는다
...
COMMIT;
  • 쓰기 집합이 안 겹쳐서 문제라면, 일부러 겹치게 만들면 된다 — 충돌의 물질화.
  • 거칠지만 효과 확실, 모든 MVCC DB에서 동작한다. 단, 그 자물쇠 행이 병목·핫스팟이 되는 게 대가다.

처방 2: 락을 명시한다 (SELECT FOR UPDATE)

BEGIN;
-- 조건을 "읽기만" 하지 말고 잠그면서 읽는다
SELECT count(*) FROM doctors
WHERE ward = 3 AND on_call FOR UPDATE;
-- 다른 퇴근 트랜잭션은 여기서 대기 → 순차 실행 강제
UPDATE doctors SET on_call = false WHERE name = '김';
COMMIT;
  • 읽은 근거가 바뀌면 안 되는 행들을 X락으로 묶는다 — 국소적으로 2장 방식을 빌려 오는 것.
  • 범위(팬텀) 문제엔 부족할 수 있다: 새 행 INSERT는 못 막는다 (InnoDB는 갭 락이 보완).
  • 실무에서 가장 흔한 처방이다. 단점: 개발자가 위험 지점을 스스로 알아내야 한다 — 놓친 곳이 사고 난다.

처방 3: DB가 감시한다 — SSI

SSI(Serializable Snapshot Isolation): SI로 일단 달리게 두고, DB가 트랜잭션 간 의존 관계를 추적하다가 "직렬화가 깨질 수 있는 패턴"이 보이면 한쪽을 중단시키는 낙관적 기법. Michael Cahill 등의 2008년 SIGMOD 논문(및 박사논문)이 원전.
  • 발상: 위험한 스케줄은 드물다. 전부 막지(락) 말고, 일어나려는 순간만 잡자.
  • PostgreSQL 9.1(2011)이 세계 최초로 상용 수준 구현 — SET TRANSACTION ISOLATION LEVEL SERIALIZABLE이 곧 SSI다.
  • 덕분에 PostgreSQL의 SERIALIZABLE은 이름값을 하는 진짜다 (Oracle과의 차별점).

이론 도구: rw-의존성

  • 트랜잭션 사이 의존(간선)의 세 종류:
  • ww: T1이 쓴 것을 T2가 또 씀 — SI가 이미 잡는다 (first-committer-wins)
  • wr: T1이 쓴 것을 T2가 읽음 — 스냅샷 순서로 자연 정렬됨
  • rw (반의존): T1이 읽은 것을 T2가 나중에 씀 — "T1은 T2 이전 세계를 봤다"는 뜻
  • 직렬가능성 판정: 이 간선들로 그래프를 그려 사이클이 없으면 직렬가능 (1장의 선행 그래프 재등장).
  • 핵심 정리(Fekete 등): SI에서 직렬화가 깨지는 모든 사이클에는 연속한 rw 간선 두 개가 반드시 들어 있다.

위험한 구조 정리

T_A --rw--> T_pivot --rw--> T_B
연속한 rw 간선 2개 = 위험 구조 (dangerous structure)
  • SSI의 감시 대상은 오직 이 모양이다: 어떤 트랜잭션(pivot)이 rw 간선을 들어오는 쪽과 나가는 쪽 모두 가질 때.
  • 이 구조가 생기면 사이클이 "생길 수 있다" — SSI는 안전하게 셋 중 하나를 중단시킨다.
  • 사이클이 "확실할 때만" 잡는 게 아니라는 점이 중요하다 — 그래서 억울한 중단(오탐)이 존재한다. 곧 다시 나온다.

당직 의사 사건에 적용

시각T1 (김 퇴근)T2 (이 퇴근)
t1당직 목록 읽음 (이 박사 행 포함)
t2당직 목록 읽음 (김 박사 행 포함)
t3김 행 UPDATE → T2가 읽은 것을 씀: T2 --rw--> T1
t4이 행 UPDATE → T1이 읽은 것을 씀: T1 --rw--> T2
t5rw 간선 2개 연속 성립 → SSI가 한쪽을 중단! 규칙 사수
  • SI가 놓치던 사건이 rw 간선의 언어로는 선명하게 보인다 — 감시 장치만 있으면 잡을 수 있는 것이다.

PostgreSQL의 SSI 구현

  • "누가 무엇을 읽었나"를 기록하는 특수 락, SIREAD 락을 도입했다.
  • 이름은 락이지만 아무도 막지 않는다 — 순수한 흔적 기록용. 튜플/페이지/릴레이션 단위로 승격되며 메모리를 아낀다
  • 쓰기가 발생하면 그 대상에 SIREAD 흔적이 있는지 확인 → 있으면 rw 간선 기록.
  • 커밋 시점에 위험 구조(들어오고 나가는 rw)가 완성되면 누군가를 "serialization failure"(40001)로 중단.
  • 흔적은 트랜잭션이 끝나도 바로 못 지운다 — 겹쳤던 트랜잭션들이 끝날 때까지 유지 (여기서도 긴 트랜잭션이 민폐다).

SIREAD 락과 오탐

  • SSI는 안전 초과 판정이다: 실제로 사이클이 안 생겼어도 위험 구조만 보이면 중단시킬 수 있다 (false positive).
  • 오탐을 키우는 것들:
  • 순차 스캔 — 테이블 전체에 SIREAD가 잡혀 "모든 쓰기와 관련됨"이 된다 → 인덱스 스캔 유도가 중요
  • 락 승격 — 메모리가 부족하면 행 단위가 페이지·테이블 단위로 뭉개져 정밀도 하락 (max_pred_locks_per_* 설정)
  • 오탐이어도 정확성은 안전한 쪽으로만 틀린다 — 억울하게 재시도할 뿐, 데이터는 절대 안 깨진다.
  • 벤치마크(원 논문·PostgreSQL 문서): 대부분 워크로드에서 오버헤드 한 자릿수 % — 2PL식 SERIALIZABLE보다 월등히 싸다.

SSI의 비용과 튜닝

  • 비용 1 — 메모리: SIREAD 추적 공간. 긴 트랜잭션·대형 스캔이 있으면 폭증.
  • 비용 2 — 재시도: 충돌·오탐만큼 트랜잭션이 중단된다. 재시도 코드가 없으면 사용자 에러로 새어 나간다.
  • 실전 수칙:
  • SERIALIZABLE 트랜잭션은 짧게, 건드리는 행은 적게, 가능하면 인덱스로 접근
  • 읽기 전용 트랜잭션엔 SET TRANSACTION READ ONLY, DEFERRABLE — 안전한 스냅샷을 기다렸다 잡아 SSI 추적에서 완전히 빠진다 (리포트·백업에 최고)
  • 전부 SERIALIZABLE로 통일하는 것이 오히려 단순하고 안전하다는 것이 PostgreSQL 커뮤니티의 일반적 권고

재시도 루프 — 필수 장비

# SI/SSI 시대의 표준 트랜잭션 래퍼 (의사코드)
def run_tx(work, retries=5):
    for i in range(retries):
        try:
            with db.transaction(isolation='serializable'):
                return work()
        except SerializationFailure:     # 40001, 40P01
            sleep(random_backoff(i))         # 지수 백오프 + 지터
    raise TooManyRetries
  • "could not serialize access", "deadlock detected", InnoDB 1213 — 전부 재시도가 정답인 에러다.
  • 주의 1: 트랜잭션 전체를 다시 실행해야 한다 — 절반만 다시 하면 지옥문이 열린다.
  • 주의 2: 트랜잭션 안에서 이메일 발송 같은 부수효과를 일으키면 재시도 때 두 번 발송된다 — 부수효과는 커밋 후로.

격리 수준 선택 전략

상황권장
단건 조회·갱신 위주 웹 OLTPREAD COMMITTED + 원자적 UPDATE 습관
여러 읽기의 일관성 필요 (리포트, 내보내기)REPEATABLE READ(SI), 가능하면 READ ONLY
불변식이 생명 (돈, 재고, 정원, 중복 방지)SERIALIZABLE(SSI) + 재시도 루프

  • 기본 철학: 격리는 보험이다. 사고의 단가가 높은 곳부터 비싼 보험을 든다.
  • 그리고 어떤 수준을 고르든 재시도 루프는 공통 장비다 — 데드락은 READ COMMITTED에도 있으니까.

11장 정리

  • SI의 구멍(Write Skew류)을 막는 3처방: 충돌 물질화, SELECT FOR UPDATE, 그리고 SSI.
  • 이론 열쇠는 rw-반의존: 연속한 rw 간선 2개(위험 구조)가 모든 SI 이상 현상의 지문이다.
  • PostgreSQL 9.1의 SSI는 SIREAD 흔적으로 위험 구조를 탐지, 오탐이 있지만 데이터는 안전한 쪽으로만 틀린다.
  • SERIALIZABLE 운용의 필수품: 짧은 트랜잭션, 인덱스 접근, 그리고 지수 백오프 재시도 루프.
  • 격리는 보험 — 사고 단가로 등급을 정하라.

분산에서 무엇이 깨지는가

  • 지금까지의 암묵적 전제: txid든 SCN이든 한 기계 안의 단일 카운터가 있었다.
  • 데이터가 100대에 쪼개지면(샤딩) 이 전제가 무너진다:
  • 전역 카운터를 한 대가 발급하면 → 그 한 대가 병목이자 단일 장애점
  • 각자 발급하면 → "서울의 tx 500번과 부산의 tx 500번, 누가 먼저인가?"에 답이 없다
  • 스냅샷의 정의 자체가 "시점"인데, 분산엔 공유된 시점이 없다.
  • 결론: 분산 MVCC의 본질 문제는 데이터가 아니라 시간이다.

진실 1: 시계는 다 다르다

  • "그냥 각 서버의 벽시계를 쓰면 되잖아?" — 안 된다. NTP로 맞춰도 서버 간 수 ms~수백 ms씩 어긋난다.
  • 어긋난 시계로 스냅샷을 자르면: 시계가 빠른 서버의 커밋이 "미래"로 밀리고, 인과가 뒤집힌 스냅샷(원인 없이 결과만 보이는)이 찍힌다.
  • 램포트의 고전적 통찰(1978): 분산에서 믿을 것은 벽시계가 아니라 인과 관계(happens-before)다 — 논리 시계의 탄생.
  • 그래서 분산 MVCC 진영은 두 갈래로 갈린다: 시계를 고치는 쪽(Spanner)과 시계를 포기하고 논리로 가는 쪽(HLC, Percolator).

Spanner의 도발 — TrueTime

  • 구글의 2012년 OSDI 논문 Spanner: 데이터센터마다 GPS 수신기와 원자시계를 설치해 시계 문제를 하드웨어로 공격했다.
  • TrueTime API: "지금 몇 시?"에 시각 대신 구간으로 답한다 — TT.now() = [최소, 최대], "진짜 현재는 이 구간 어딘가".
  • 구간 폭(오차 ε)은 보통 수 ms 이내로 관리된다 — 불확실성을 없애는 대신 정직하게 정량화한 것.

commit wait의 마법

커밋 타임스탬프 s = TT.now().max로 찍고,
진짜 시각이 s를 지날 때까지 (~ε) 기다렸다가 결과를 공개한다
  • 이 짧은 대기(commit wait)가 보장하는 것: 커밋이 공개된 후 시작하는 어떤 트랜잭션도 반드시 더 큰 타임스탬프를 받는다.
  • 효과: 타임스탬프 순서 = 실제 시간 순서. 전 지구 어디서 커밋해도 외부 일관성(external consistency)이 성립한다.
  • 외부 일관성: "내가 커밋 완료를 보고 나서 시작한 트랜잭션이 내 커밋을 못 보는 일은 없다" — 직렬가능성보다도 강한 보장
  • 시계 오차를 없앨 수 없으니, 오차만큼 기다려서 오차를 무해하게 만든다 — 문제를 뒤집는 발상.

Spanner가 산 것과 낸 돈

  • 산 것: 전 지구 분산 + SQL + 진짜 직렬가능성(외부 일관성) + MVCC 스냅샷 읽기. "CAP을 이겼다"는 마케팅이 나올 정도의 상품성.
  • 낸 돈:
  • 모든 쓰기에 commit wait ε — 시계 인프라가 나쁘면 대기가 길어진다
  • GPS·원자시계 인프라 — 구글이라서 가능한 투자
  • 쓰기는 여전히 Paxos 합의 + 2PC — 물리 법칙(빛의 속도)은 못 이긴다
  • 읽기의 보상이 크다: 과거 타임스탬프 스냅샷 읽기는 합의 없이 가까운 복제본에서 바로 — MVCC 덕이다.

HLC — 가난한 자의 TrueTime

  • 원자시계가 없는 회사는? HLC(Hybrid Logical Clock) — 벽시계와 논리 시계의 잡종.
  • 구조: (물리 시각, 논리 카운터) 쌍. 메시지를 주고받을 때마다 상대의 HLC와 max를 취하고 카운터를 올린다.
  • 보장: 인과 관계가 있으면 HLC 순서가 반드시 그것을 따른다 + 값은 벽시계에 가깝게 유지된다.
  • 보장 못 하는 것: 통신하지 않은 두 사건의 실제 시간 순서 — 여기가 TrueTime과의 결정적 격차.
  • 비유: TrueTime은 전 직원에게 지급된 원자시계, HLC는 "만날 때마다 서로 시계를 맞추는" 약속.

CockroachDB의 타협

  • CockroachDB는 HLC + MVCC로 Spanner를 오픈소스 세계에 재현한 대표작이다.
  • commit wait가 불가능하므로(오차 보장이 없다) 다른 안전장치를 쓴다:
  • 최대 시계 오차(max offset, 기본 500ms)를 가정하고, 읽기가 그 "불확실 구간" 안의 버전을 만나면 타임스탬프를 밀어 올려 재시도한다 (uncertainty restart)
  • 오차 가정을 실제로 초과한 노드는 스스로 클러스터에서 탈락한다
  • 격리는 기본 SERIALIZABLE — 낙관적 재시도 문화가 프로토콜에 배어 있다.
  • 교훈: 같은 목표라도 인프라 전제(원자시계 유무)가 프로토콜 모양을 완전히 바꾼다.

Percolator — SI를 조립하다

  • 구글의 또 다른 발명(2010): Bigtable(단일 행 원자성만 있는 스토리지) 위에 범용 SI 트랜잭션을 얹는 프로토콜.
  • 재료: 중앙 타임스탬프 발급기(TSO) + 데이터에 심는 lock/write 컬럼.
  • 쓰기(2단계): ① prewrite — 모든 대상 행에 락 기록 + 새 버전 임시 기록, ② commit — primary 행의 락을 커밋 기록으로 바꾸면 그 순간 전체가 원자적으로 확정.
  • 읽기: 시작 타임스탬프로 스냅샷 읽기. 락을 만나면 잠시 대기하거나 죽은 트랜잭션의 락을 청소해 준다.
  • 중앙 TSO가 병목이라 전 지구엔 부적합, 한 리전 안에선 단순하고 강력하다 — 원래 용도도 구글 검색 색인의 증분 갱신.

TiDB와 후예들

  • TiDB(PingCAP)는 Percolator 모델을 그대로 산업화한 대표작이다 — TSO는 PD 컴포넌트가, 스토리지는 TiKV(RocksDB 기반)가 맡는다.
  • MySQL 프로토콜 호환이라 "InnoDB 애플리케이션의 수평 확장판"으로 쓰인다 — 격리도 SI(낙관/비관 모드).
  • 그 밖의 지형 한눈에:
  • YugabyteDB: PostgreSQL 호환 + HLC 계열 — CockroachDB와 같은 어족
  • Amazon Aurora: 스토리지만 분산, 쓰기는 단일 노드 — 단일 시계라 전통 MVCC 유지. "분산의 어려움을 회피한" 영리한 설계
  • 선택 기준도 시간이 결정한다: 단일 리전이면 TSO/단일 라이터로 충분, 다중 리전이면 HLC 또는 TrueTime급이 필요.

읽기 전용의 공짜 점심

  • 분산 MVCC의 최대 보상은 읽기에서 나온다:
  • 팔로워 읽기(follower read): 몇 초 전 타임스탬프로 스냅샷을 잡으면, 리더 합의 없이 가까운 복제본에서 일관된 읽기
  • 시점 조회(AS OF SYSTEM TIME): "5분 전 상태"를 쿼리 — 백업, 디버깅, 실수 복구에 즉효
  • 글로벌 분석 쿼리가 운영 트래픽을 전혀 방해하지 않음 — 2장 야간 리포트 문제의 분산판 해결
  • 1986년 POSTGRES가 꿈꾸다 접었던 타임트래블(6장)이 분산 시대에 필수 기능으로 부활한 것 — 역사의 재미있는 원환.

12장 정리

  • 분산 MVCC의 본질 난제는 "공유된 시점(시계)이 없다"는 것.
  • Spanner는 원자시계+GPS(TrueTime)와 commit wait로 외부 일관성까지 달성 — 오차를 기다림으로 무해화.
  • CockroachDB는 HLC+불확실성 재시도로, TiDB는 Percolator(TSO+2단계 쓰기)로 같은 목표에 접근.
  • 보상은 읽기: 팔로워 읽기, 시점 조회 등 스냅샷의 힘이 분산에서 배가된다.
  • 설계 선택은 결국 시계 인프라의 전제에서 갈린다.

인덱스는 버전을 모른다

  • 지금까지 테이블만 봤지만, 실전 행에는 인덱스가 3~10개씩 붙어 있다.
  • 문제: 행에 새 버전이 생길 때 인덱스는 어떻게 하나?
  • 인덱스에도 버전을 두나? 아니면 인덱스는 항상 한 곳만 가리키나?
  • 인덱스만 보고 "이 버전이 내 스냅샷에 보이는가"를 알 수 있나?
  • 이 질문에 대한 답이 PostgreSQL과 InnoDB에서 정반대로 갈리고, 그 차이가 2016년 업계 최대 논쟁(Uber 사건)을 낳는다.

PostgreSQL: 인덱스 폭발 문제

  • PostgreSQL 인덱스 엔트리는 튜플의 물리 주소(ctid)를 가리키고, 가시성 정보는 없다.
  • UPDATE로 새 튜플이 생기면 → 주소가 바뀌었으니 모든 인덱스에 새 엔트리가 필요하다.
  • 인덱스 10개인 테이블에서 관심 없는 컬럼 하나만 고쳐도 인덱스 10개가 전부 갱신된다
  • 읽기 쪽 비용도 있다: 인덱스는 죽은 버전도 가리키므로, 힙에 가서 가시성을 확인해야 한다.
  • 이것이 PostgreSQL 쓰기 증폭(write amplification)의 정체 — append형 설계의 그림자다.

HOT — 구원의 지름길

HOT(Heap-Only Tuple), PostgreSQL 8.3(2008): 갱신된 컬럼이 어떤 인덱스에도 안 걸리고, 새 버전이 같은 페이지에 들어갈 수 있으면 — 인덱스는 건드리지 않고 옛 튜플에서 새 튜플로 페이지 내 체인만 잇는다.
  • 인덱스는 계속 옛 자리를 가리키고, 도착한 읽기가 체인을 한 칸 따라가면 된다.
  • 효과가 극적이다: 인덱스 10개 갱신 → 0개. "카운터, 상태, 타임스탬프" 같은 자주 갱신되는 컬럼엔 인덱스를 안 거는 것이 그래서 중요하다.
  • 페이지 내 청소(HOT pruning)도 겸한다 — VACUUM 없이도 체인이 정리되는 미니 청소.
  • 확인: pg_stat_user_tables의 n_tup_hot_upd / n_tup_upd 비율 — HOT 적중률

fillfactor 튜닝

-- 페이지를 90%만 채우고 10%는 HOT용 여유로 남긴다
ALTER TABLE hot_table SET (fillfactor = 90);
-- (기본값 100 = 빈틈없이 채움 = 같은 페이지에 새 버전 못 넣음)
  • HOT의 조건 ②("같은 페이지에 자리")를 인위적으로 확보하는 다이얼이다.
  • UPDATE가 잦은 테이블은 fillfactor 90~70으로 낮춰 HOT 적중률을 끌어올리는 것이 정석.
  • 대가는 저장 공간(빈틈만큼)과 스캔 시 페이지 수 증가 — 갱신 빈도에 맞춰 저울질한다.
  • "디스크를 조금 낭비해 쓰기 증폭을 줄인다" — MVCC 튜닝은 늘 이런 교환의 연속이다.

index-only scan과 가시성 지도

  • "인덱스에 필요한 컬럼이 다 있는데 왜 힙까지 가나?" — 가시성 확인 때문이다 (인덱스는 버전을 모르니까).
  • 구원자는 7장의 가시성 지도: 페이지의 비트가 "전부 보임"이면 힙 확인을 생략해도 된다!
  • index-only scan = 커버링 인덱스 + 가시성 지도 합작품. EXPLAIN의 "Heap Fetches" 수치가 생략 실패 횟수다.
  • 따라서 index-only scan의 성능은 VACUUM 상태에 좌우된다 — 청소가 밀리면 "전부 보임" 비트가 꺼져 힙행이 부활한다.
  • 인덱스 설계와 VACUUM 운영이 한 몸이라는 것 — PostgreSQL 성능 튜닝의 숨은 연결 고리다.

InnoDB: 세컨더리 인덱스의 사정

  • InnoDB 세컨더리 인덱스는 물리 주소가 아니라 PK 값을 가리킨다 — 행이 "이사"해도 인덱스는 무사하다.
  • 비인덱스 컬럼 갱신 시 세컨더리 인덱스는 무갱신 — PostgreSQL이 HOT으로 겨우 얻는 것을 구조적으로 공짜로 얻는다.
  • 대가는 읽기에서: 세컨더리 인덱스 조회는 PK 인덱스를 한 번 더 타야 한다 (이중 조회).
  • 버전 처리: 세컨더리 인덱스도 가시성을 모르므로, 커버링 조회라도 의심스러우면 클러스터드 인덱스+undo로 확인한다.
  • 요약: 쓰기 증폭은 InnoDB가 작고, 읽기 경로는 PostgreSQL이 짧다 — 또 하나의 정직한 트레이드오프.

2016년 Uber 사건

2016년 7월, Uber 엔지니어링 블로그 "Why Uber Engineering Switched from Postgres to MySQL" — PostgreSQL의 MVCC 설계를 정면 비판하며 MySQL로 이주했음을 공개, 업계가 몇 달간 들끓었다.
  • 비판의 골자 (지금까지 배운 언어로 번역하면):
  • 쓰기 증폭 — 갱신마다 행 전체 새 버전 + 모든 인덱스 갱신 (HOT 미적중 워크로드)
  • 그 쓰기가 전부 WAL을 타고 복제로 전파 — 복제 대역폭·지연 부담
  • 복제본에서 긴 쿼리 vs WAL 재생 충돌, 커넥션 모델 등
  • 반론(Robert Haas 등 커뮤니티 시니어들): 워크로드 특수성, 튜닝(HOT·fillfactor) 미적용, MySQL 쪽 약점 미언급을 지적.

사건의 교훈 — 논쟁 정리

  • 기술적으로 양쪽 다 맞았다: Uber의 워크로드(소수 컬럼 초고빈도 갱신 + 인덱스 다수)는 정확히 append형의 아픈 곳이었다.
  • 이 덱의 언어로 한 줄 요약: 그들은 8장 표의 오른쪽 열(undo형)이 유리한 워크로드를 갖고 있었다.
  • 일반화는 금물이라는 것도 배웠다 — 같은 시기 수많은 회사는 반대로 MySQL에서 PostgreSQL로 갔다.
  • 진짜 교훈: DB 선택 논쟁에서 "MVCC를 어디에 쌓고 누가 청소하나"를 짚을 수 있으면, 마케팅이 아니라 공학으로 판단할 수 있다.
  • 이 사건 이후 PostgreSQL 진영의 개선 작업(아래)이 눈에 띄게 가속됐다 — 좋은 논쟁의 순기능

대안 실험: zheap과 OrioleDB

  • "PostgreSQL에 undo형 스토리지를 이식하자"는 시도가 이어지고 있다:
  • zheap (EDB, 2018~): undo 로그 기반 새 힙 포맷 — 제자리 갱신, 블로트 최소화. 본선 합류는 미완
  • OrioleDB: 스토리지 확장으로 undo + 행 단위 WAL — 활발히 개발 중
  • 발판은 이미 있다: PostgreSQL 12+의 테이블 접근 방법(table AM) API — 힙 포맷을 갈아 끼울 수 있는 플러그인 구조.
  • InnoDB 쪽도 정지해 있지 않다: MySQL 8.x의 언두 관리 개선 등 서로의 장점을 흡수 중.
  • 수렴 진화의 시대 — "append냐 undo냐"는 언젠가 테이블별 선택 옵션이 될지도 모른다.

13장 정리

  • 인덱스는 가시성을 모른다 — 버전 확인은 결국 힙/undo의 몫.
  • PostgreSQL: 갱신마다 전 인덱스 갱신 위험 → HOT(비인덱스 컬럼 + 페이지 여유)과 fillfactor가 처방.
  • index-only scan은 가시성 지도 의존 — VACUUM 상태가 곧 읽기 성능이다.
  • InnoDB는 PK 간접 참조로 쓰기 증폭이 작고, 대신 이중 조회 비용을 낸다.
  • Uber 사건은 두 설계의 트레이드오프가 현실 비즈니스를 움직인 사례 — 워크로드가 정답을 정한다.

제1계명: 트랜잭션은 짧게

  • 이 덱에서 다섯 번 반복된 법칙을 계명으로 승격하자: 긴 트랜잭션(오래된 스냅샷)은 MVCC 시스템 전체의 공공의 적이다.
  • 죄목 총정리: VACUUM 지평선 고정(PG), undo/히스토리 폭주(InnoDB·Oracle), 버전 스토어 폭주(SQL Server), 체크포인트 방해(SQLite), SIREAD 유지(SSI).
  • 구체 지침:
  • 트랜잭션 안에서 외부 API 호출·사용자 입력 대기 금지 — DB 트랜잭션은 "계산과 쿼리만"
  • 리포트·마이그레이션은 서비스 DB가 아닌 복제본/시점 스냅샷에서
  • 어쩔 수 없는 긴 작업은 새벽·저부하 창에, 감시하에

긴 트랜잭션 헌팅

-- PostgreSQL: 5분 넘게 달리는 트랜잭션
SELECT pid, now() - xact_start AS dur, state, query
FROM pg_stat_activity
WHERE xact_start < now() - interval '5 min'
ORDER BY dur DESC;

-- MySQL: 오래 달리는 InnoDB 트랜잭션
SELECT trx_id, trx_started, trx_mysql_thread_id
FROM information_schema.innodb_trx
WHERE trx_started < now() - INTERVAL 5 MINUTE;
  • 이 쿼리를 알림으로 걸어 두는 것이 MVCC 운영의 최소 안전장치다 — "5분 이상 트랜잭션 발견 시 슬랙 호출".
  • 처형 도구: SELECT pg_terminate_backend(pid) / KILL <thread_id> — 물론 원인 제거(코드 수정)가 본론이다.

idle in transaction — 조용한 살인자

pg_stat_activity에 state가 "idle in transaction"인 커넥션: BEGIN은 했는데 아무것도 안 하며 스냅샷만 쥐고 있는 좀비다. 쿼리가 안 도니 슬로우 쿼리 모니터링에도 안 잡힌다.
  • 흔한 발생 경로: 예외 처리에서 commit/rollback 누락, 트랜잭션 열고 외부 API 대기, 디버거로 중단해 둔 개발자 세션.
  • 방어선:
  • SET idle_in_transaction_session_timeout = '60s' — PostgreSQL의 자동 처형 타이머
  • 프레임워크의 트랜잭션 컨텍스트(with 블록, @Transactional)로 누락 원천 차단
  • 이 설정 하나가 수많은 새벽 장애를 예방한다 — 신규 DB 셋업 체크리스트에 넣어 두자.

대량 UPDATE/DELETE의 함정

  • "행 5000만 개 일괄 UPDATE" 한 방이 일으키는 연쇄:
  • PostgreSQL: 죽은 튜플 5000만 개 즉조 생산 → 블로트 + autovacuum 폭주 + WAL 폭풍(복제 지연)
  • InnoDB: 거대 undo 생성 → 롤백하면 몇 시간짜리 되돌리기 + 히스토리 리스트 폭발
  • 공통: 그 시간 내내 긴 트랜잭션으로서 제1계명 위반
  • 게다가 실패하면 처음부터 다시 — 대량 작업은 원자성이 오히려 저주가 된다.
  • 원칙: 대량 작업은 잘게 쪼개 커밋한다. 구체 처방은 다음 슬라이드.

배치 작업 처방전

-- 청크 단위 삭제 (PostgreSQL) — 끝날 때까지 반복 실행
DELETE FROM logs
WHERE id IN (SELECT id FROM logs
             WHERE created < now() - interval '90 days'
             LIMIT 5000);
-- 각 반복이 짧은 트랜잭션 → 스냅샷 지평선이 계속 전진
  • 청크 사이에 짧은 sleep을 넣어 autovacuum·복제가 따라올 틈을 준다.
  • 더 좋은 설계는 삭제를 안 하는 것: 파티셔닝 후 오래된 파티션을 DROP — 죽은 튜플 0개, 순간 완료.
  • "DELETE는 튜플을 남기지만 DROP/TRUNCATE는 파일을 지운다" — MVCC 비용 구조의 차이
  • 대량 UPDATE도 동일: 키 범위로 쪼개고, 진행 상황을 별도 테이블에 기록해 재시작 가능하게.

핫 로우와 카운터

  • 핫 로우(hot row): 모두가 갱신하는 한 행 — 조회수 카운터, 재고 수량, 잔액 집계 행.
  • MVCC라도 쓰기끼리는 직렬화된다(행 락) — 핫 로우는 초당 갱신 수에 상한이 생기고, 죽은 버전을 초당 그만큼 생산한다.
  • 처방 모음:
  • 샤딩 카운터: 카운터를 N행으로 쪼개 무작위 갱신, 읽을 때 SUM
  • 지연 집계: 이벤트를 append 테이블에 쌓고 주기적으로 롤업 (이벤트 소싱의 축소판)
  • Redis 등 인메모리로 흡수 후 주기 flush — 정확도 요구와 맞바꿈
  • 구조 신호: 특정 행의 락 대기가 상위에 보이면 설계를 의심할 때다.

커넥션 풀과 트랜잭션 스코프

  • 커넥션 풀(PgBouncer 등)의 transaction 모드는 "트랜잭션 단위로 커넥션을 빌려 준다" — 트랜잭션 밖 세션 상태(SET, 임시 테이블)가 증발하는 이유.
  • MVCC 관점 이점: 애플리케이션이 커넥션을 쥐고 놀아도 트랜잭션만 안 열려 있으면 스냅샷 지평선은 무사하다.
  • 반대로 최악 조합: 풀 없이 커넥션마다 BEGIN 남발 + 예외 시 방치 — idle in transaction 양식장.
  • 수칙: "커넥션은 오래, 트랜잭션은 짧게. 트랜잭션 경계는 코드에서 명시적으로."

ORM이 파는 함정들

  • ORM은 트랜잭션과 락을 숨긴다 — 편리하지만 MVCC 관점의 지뢰가 몇 개 있다:
  • 세션 = 트랜잭션 장기화: 뷰 렌더링까지 트랜잭션을 물고 가는 설정(open session in view) — 제1계명 위반 제조기
  • read-modify-write 패턴: 객체 읽고 → 필드 고치고 → save = Lost Update의 정석 코스. 낙관적 락(@Version)이나 원자적 UPDATE로
  • N+1 쿼리로 트랜잭션이 길어짐 — 성능 문제가 MVCC 문제로 전이
  • ORM을 쓰든 안 쓰든, 최종 방어선은 같다: 실제 발행되는 SQL과 트랜잭션 경계를 로그로 눈으로 확인하는 습관.

자료구조 — Version과 Tx

from dataclasses import dataclass, field

@dataclass
class Version:
    val: object
    xmin: int                 # 만든 트랜잭션 (출생)
    xmax: int = 0             # 대체/삭제한 트랜잭션 (0=현역)

@dataclass
class Tx:
    txid: int
    snap_active: set          # 시작 순간 진행 중이던 txid들
    snap_max: int             # 시작 순간의 다음 txid (미래 경계)
    writes: dict = field(default_factory=dict)  # 미커밋 쓰기

class Conflict(Exception): pass
  • Version은 6장의 튜플 헤더, Tx의 (snap_active, snap_max)는 스냅샷(xip 목록, xmax)의 축소판이다.

begin — 스냅샷 찍기

class MiniMVCC:
    def __init__(self):
        self.store = {}        # key → [Version, ...] 버전 체인
        self.next_txid = 1
        self.active = set()    # 진행 중 트랜잭션
        self.aborted = set()   # 롤백된 트랜잭션

    def begin(self):
        txid = self.next_txid; self.next_txid += 1
        tx = Tx(txid, snap_active=set(self.active), snap_max=txid)
        self.active.add(txid)
        return tx
  • begin의 전부는 "지금 진행 중인 트랜잭션 명단의 복사"다 — 스냅샷이 사진인 이유가 코드로 보인다.
  • 커밋 여부는 별도 표에 없다: active에도 aborted에도 없으면 커밋된 것으로 취급한다 (clog의 축소판).

visible — 가시성 판정

    def _committed_in_snap(self, x, tx):
        # 트랜잭션 x의 결과가 tx의 사진에 찍혀 있는가?
        if x == tx.txid:          return True   # 내 것은 보임
        if x >= tx.snap_max:      return False  # 사진 이후 시작
        if x in tx.snap_active:   return False  # 사진 순간 미완
        return x not in self.aborted            # 롤백만 아니면

    def visible(self, v, tx):
        if not self._committed_in_snap(v.xmin, tx): return False
        if v.xmax == 0: return True
        return not self._committed_in_snap(v.xmax, tx)
  • 6장의 알고리즘 그대로: 출생은 찍혔고, 은퇴는 안 찍힌 버전만 보인다.
  • InnoDB의 Read View 판정(8장)과 비교해 보라 — 사실상 같은 코드다.

read — 체인에서 고르기

    def read(self, tx, key):
        if key in tx.writes:              # 내 미커밋 쓰기 먼저
            return tx.writes[key]
        for v in reversed(self.store.get(key, [])):
            if self.visible(v, tx):
                return v.val
        return None                        # 내 세계엔 없는 행
  • 체인을 최신부터 거슬러 "내 사진에 찍힌 첫 버전"을 돌려준다 — 락도, 대기도 없다.
  • 자기 쓰기 우선 규칙(tx.writes 먼저)은 6장 t_cid의 초간단 버전이다.
  • read가 store를 전혀 수정하지 않는다는 점을 눈여겨보라 — 읽기가 쓰기를 못 막는 이유가 코드 구조로 자명하다.

write와 commit — 첫 커밋자 승리

    def write(self, tx, key, val):
        tx.writes[key] = val               # 커밋까지 내 주머니에

    def commit(self, tx):
        for key in tx.writes:             # ① 충돌 검사
            for v in self.store.get(key, []):
                fresh = v.xmin >= tx.snap_max or v.xmin in tx.snap_active
                done = v.xmin not in self.active and v.xmin not in self.aborted
                if fresh and done:        # 내 사진 이후 남이 커밋함
                    self.abort(tx)
                    raise Conflict(key)
        for key, val in tx.writes.items():  # ② 반영
            chain = self.store.setdefault(key, [])
            if chain: chain[-1].xmax = tx.txid   # 은퇴 도장
            chain.append(Version(val, tx.txid))  # 새 버전
        self.active.discard(tx.txid)

    def abort(self, tx):
        self.active.discard(tx.txid); self.aborted.add(tx.txid)
  • 충돌 검사 한 문장 요약: "내가 쓰려는 키에, 내 사진 이후 커밋된 새 버전이 있는가?" — 5장 규칙 ②의 직역.

실험 1: Dirty Read 차단

db = MiniMVCC()
t0 = db.begin(); db.write(t0, 'A', 100); db.commit(t0)

t1 = db.begin()
db.write(t1, 'A', 900)          # 미커밋 쓰기

t2 = db.begin()
print(db.read(t2, 'A'))          # → 100  (900이 안 보인다!)

db.abort(t1)                     # t1이 마음을 바꿔도
print(db.read(t2, 'A'))          # → 100  (아무 일도 없다)
  • t1의 900은 t1.writes 주머니에만 있다가 버려졌다 — 세계는 오염된 적이 없다.
  • 커밋 후에 쓰기를 반영하는 이 구조에선 Dirty Read가 원리적으로 불가능하다.

실험 2: 반복 읽기와 Lost Update

t1 = db.begin(); t2 = db.begin()
db.read(t1, 'A')                 # → 100
db.read(t2, 'A')                 # → 100

db.write(t1, 'A', 150)
db.commit(t1)                    # 성공 (첫 커밋자)

print(db.read(t2, 'A'))          # → 100  반복 읽기 일관! ✓

db.write(t2, 'A', 130)
db.commit(t2)                    # → Conflict('A') 발생! ✓
  • 1장의 잔액 증발 스케줄이 그대로 들어왔는데: t2는 끝까지 자기 사진(100)을 보고, 커밋에서 잡힌다.
  • PostgreSQL REPEATABLE READ의 "could not serialize access" 에러를 우리 손으로 재현했다.

실험 3: Write Skew는 뚫린다

# 당직: 김=1(당직), 이=1(당직). 규칙: 합이 1 이상 유지
t1 = db.begin(); t2 = db.begin()
if db.read(t1, '김') + db.read(t1, '이') >= 2:
    db.write(t1, '김', 0)        # 김 퇴근
if db.read(t2, '김') + db.read(t2, '이') >= 2:
    db.write(t2, '이', 0)        # 이 퇴근
db.commit(t1)                    # 성공
db.commit(t2)                    # 역시 성공! ← 문제
# 최종: 김=0, 이=0 — 당직 0명. 불변식 붕괴
  • 충돌 검사는 '김'과 '이'라는 서로 다른 키라 통과 — 5장에서 배운 SI의 구멍이 코드로 증명됐다.
  • 연습 문제: 11장의 처방 1(충돌 물질화)을 이 코드로 재현해 보라 — 두 트랜잭션이 공통 키 'guard'에 write하게 하면 된다.

vacuum 붙이기

    def vacuum(self):
        horizon = min(self.active | {self.next_txid})  # 지평선
        removed = 0
        for key, chain in self.store.items():
            keep = []
            for v in chain:
                dead = (v.xmax != 0 and v.xmax < horizon
                        and v.xmax not in self.aborted)
                garbage = v.xmin in self.aborted   # 롤백의 잔해
                if dead or garbage: removed += 1
                else: keep.append(v)
            self.store[key] = keep
        return removed
  • 지평선 = 살아 있는 가장 오래된 트랜잭션 — 그보다 과거에 은퇴한 버전만 지운다 (7장 그대로).
  • 실험: 긴 트랜잭션 하나를 begin만 하고 방치한 채 vacuum을 불러 보라 — removed가 0에 머문다. 제1계명의 코드 증명.

15장 정리

  • 버전 체인 + 스냅샷 + 가시성 판정 + 커밋 검사 = 스냅샷 격리. 전부 합쳐 60줄이었다.
  • Dirty Read 차단과 반복 읽기 일관성은 구조에서 공짜로 나왔고, Lost Update는 충돌 검사가 잡았다.

  • vacuum과 지평선, 그리고 긴 트랜잭션의 해악도 몇 줄로 증명됐다.
  • 개념을 코드로 접어 본 사람은 어떤 DB 문서를 읽어도 길을 잃지 않는다.

  • ③ MVCC는 덮어쓰기 대신 버전을 쌓아, 읽기와 쓰기가 서로 다른 것을 만지게 한다.
  • ④ 스냅샷은 "커밋 완료 집합의 사진"이고, 가시성은 xmin/xmax와 사진의 비교 연산이다.
  • ⑤ SI = 트랜잭션당 사진 1장 + 첫 커밋자 승리 — 팬텀까지 막지만 Write Skew는 통과시킨다.

열 문장 요약 (뒤 5)

  • ⑥ 구현은 세 가족: append형(PostgreSQL), undo형(Oracle·InnoDB), 별도 스토어형(SQL Server).
  • ⑦ 버전을 쌓는 자, 반드시 청소한다 — VACUUM, purge, undo 재사용. 그리고 청소의 적은 긴 트랜잭션.
  • ⑧ 진짜 SERIALIZABLE이 필요하면 SSI(rw 간선 2연속 탐지) 또는 명시적 락 — 그리고 재시도 루프.
  • ⑨ 분산 MVCC의 난제는 시간이다 — TrueTime은 기다리고, HLC는 만나서 맞추고, TSO는 한 명이 발급한다.
  • ⑩ 격리는 보험이다 — 사고 단가로 등급을 고르고, 이름이 아니라 "막아 주는 현상"으로 검증하라.
