18장

설치와 버전 관리

nvm · .nvmrc · engines 필드

버전 관리자부터 깔고 시작한다

Node를 운영체제 패키지 관리자로 한 벌만 설치하면, 다른 버전을 요구하는 프로젝트를 만나는 날 곤란해집니다. 버전 관리자를 먼저 깔면 그 문제가 아예 생기지 않습니다.

# 설치된 버전만 본다 (--no-alias 를 빼면 별칭 목록까지 길게 나온다)
nvm ls --no-colors --no-alias

# 그 셸에서만 버전을 바꾼다
nvm use 26 --silent
node -v

nvm use 24 --silent
node -v
->     v24.19.0 *
        v26.8.1 *
         system *
v26.8.1
v24.19.0
그 셸에서만 — nvm use는 현재 셸의 PATH만 바꿉니다. 새 터미널을 열면 기본 버전으로 돌아갑니다. 이게 버그가 아니라 요점입니다.

.nvmrc — 팀원 모두가 같은 버전을 쓰게 한다

버전을 각자 기억하게 두면 반드시 어긋납니다. 저장소에 파일로 적어 두면 기억할 필요가 없어집니다.

# 프로젝트 루트에 쓸 버전을 적어 둔다
echo "24" > .nvmrc

# 인자 없이 부르면 nvm 이 .nvmrc 를 찾아 읽는다
nvm use --no-colors
node -v
Found '/…/examples/pkg/nvmrc/.nvmrc' with version <24>
Now using node v24.19.0 (npm v11.17.0)
v24.19.0
메이저만 적으세요 — 24라고 적으면 설치된 24.x 중 가장 높은 것을 씁니다. 24.19.0처럼 못 박으면 팀원이 패치 버전을 올릴 때마다 파일을 고쳐야 합니다.

engines — 어긋난 버전에서 설치 자체를 막는다

.nvmrc는 권유일 뿐, 무시하고 설치해도 아무 일도 일어나지 않습니다. 정말 막고 싶다면 package.json에 조건을 걸고 강제 옵션을 켜야 합니다.

{
  "name": "engines-demo",
  "version": "1.0.0",
  "private": true,
  "engines": {
    "node": ">=30.0.0"
  }
}

같은 폴더의 .npmrc에 engine-strict=true 한 줄을 넣고 npm install을 돌리면:

npm error code EBADENGINE
npm error engine Unsupported engine
npm error engine Not compatible with your version of node/npm: engines-demo@1.0.0
npm error notsup Not compatible with your version of node/npm: engines-demo@1.0.0
npm error notsup Required: {"node":">=30.0.0"}
npm error notsup Actual:   {"node":"v24.19.0","npm":"11.17.0"}
engine-strict 이 없으면 경고로 끝납니다 — engines만 적어 두면 npm은 맞지 않는 버전에서도 설치를 진행하고 경고 한 줄만 남깁니다. 막으려면 .npmrc를 함께 커밋하세요.

어느 버전을 고를 것인가

짝수 버전만 LTS가 됩니다. 홀수 버전은 다음 짝수 버전을 위한 실험대라, 오래 굴릴 서비스에 올릴 물건이 아닙니다.

// "언제까지 쓸 수 있나"는 기억이 아니라 nodejs/Release 의 schedule.json 에서 읽는다.
import { readFileSync } from 'node:fs';

const schedule = JSON.parse(readFileSync('../facts/schedule.json', 'utf8'));
const today = new Date('2026-09-01');
const on = (d) => d && new Date(d) <= today;

for (const [ver, s] of Object.entries(schedule)) {
  if (new Date(s.end) < today || !on(s.start)) continue;
  let phase = 'Current';
  if (on(s.maintenance)) phase = 'Maintenance';
  else if (on(s.lts)) phase = 'Active LTS';
  console.log(ver.padEnd(4), phase.padEnd(12), '지원 종료', s.end);
}
v22  Maintenance  지원 종료 2027-04-30
v24  Active LTS   지원 종료 2028-04-30
v26  Current      지원 종료 2029-04-30
고르는 법 — 새 프로젝트는 Active LTS를, 굴러가는 서비스는 지원 종료일까지 버티다 다음 짝수 LTS로. Current는 새 기능을 미리 만져 볼 때만 씁니다.

REPL 제대로 쓰기

_ 변수 · .load · .save · 자동완성

_ 는 직전 결과를 담고 있다

인자 없이 node를 치면 REPL이 뜹니다. 값을 하나 계산할 때마다 그 결과가 _에 담겨서, 방금 나온 값을 변수에 담아 둘 필요가 없습니다.

Welcome to Node.js v24.19.0.
Type ".help" for more information.
> 1 + 1
2
> _ * 3
6
> _ + 100
106
왜 REPL을 쓰나 — 문서를 뒤지는 것보다 빠릅니다. 함수 이름이 기억나지 않으면 os.까지 치고 Tab을 두 번 누르면 그 객체의 속성이 전부 나옵니다.

점 명령 — 세션을 파일로 남긴다

REPL에서 무언가를 알아냈는데 창을 닫으면 사라집니다. .save는 그 세션에서 입력한 줄들을 그대로 파일로 씁니다.

Welcome to Node.js v24.19.0.
Type ".help" for more information.
> const port = 3000
undefined
> const host = 'localhost'
undefined
> .save session.js
Session saved to: session.js
> .exit
--- session.js ---
const port = 3000
const host = 'localhost'

.save 파일지금까지 입력한 줄을 파일로 저장
.load 파일파일 내용을 한 줄씩 입력한 것처럼 실행
.editor여러 줄 입력 모드. Ctrl+D로 끝내고 실행
.break여러 줄 입력 도중 빠져나오기

REPL에서는 await를 그냥 쓴다 — 단, 진짜 터미널에서만

REPL은 입력을 async 함수로 감싸 주기 때문에 await를 최상위에서 바로 쓸 수 있습니다. 그런데 이 기능은 표준 입력이 터미널일 때만 켜집니다.

터미널에서 직접 친 경우 — 된다
> const os = await import('node:os')
undefined
> typeof os
'object'
> os.EOL === '\n'
true
> const res = await Promise.resolve(42)
undefined
> res + 1
43
파일이나 파이프로 밀어 넣은 경우 — 조용히 다르게 동작한다
Welcome to Node.js v24.19.0.
Type ".help" for more information.
> 'undefined'
> undefined
>

같은 두 줄을 node -i < 파일로 넣었더니 typeof os가 'undefined'입니다. await가 처리되지 않아 os가 아예 만들어지지 않았습니다.

스크립트를 REPL에 파이프로 먹이지 마세요 — 이 덱의 REPL 화면은 전부 script(1)로 유사 터미널을 만들어 채록한 것입니다. 그러지 않으면 위처럼 실제와 다른 결과를 보게 됩니다.

REPL이 스크립트와 다르게 구는 두 지점

> const x = 1
undefined
> const x = 2
Uncaught SyntaxError: Identifier 'x' has already been declared
> x
1
> [1, 2, 3].map((n) => n * 2)
[ 2, 4, 6 ]
> _
[ 2, 4, 6 ]
> const y = 5
undefined
> _
undefined
  • 선언이 실패해도 세션은 죽지 않습니다. 스크립트였다면 파일 전체가 파싱조차 되지 않았을 SyntaxError인데, REPL은 그 줄만 버리고 x는 원래 값 1을 그대로 지킵니다.
  • _는 표현식의 값만 받습니다. const y = 5 같은 선언문은 값이 undefined라, 애써 계산해 둔 직전 결과가 이 한 줄에 날아갑니다.
날리기 싫으면 — 선언문을 치기 전에 const saved = _로 먼저 옮겨 두거나, 아예 .save로 세션을 파일에 남기세요.

스크립트 실행하기

--watch · --run · --env-file · 종료 코드

실행하는 네 가지 방법

# -e 는 넘긴 문자열을 그대로 실행한다
node -e "console.log(process.argv)" a b

# -p 는 실행하고 결과까지 자동으로 찍는다
node -p "process.versions.v8"

# 표준 입력으로 넘겨도 된다
echo "console.log('stdin 에서 왔다')" | node
[ '/…/node/bin/node', 'a', 'b' ]
13.6.233.17-node.51
stdin 에서 왔다
argv를 보세요 — 파일을 실행할 때는 argv[1]이 스크립트 경로지만, -e로 실행하면 그 자리가 없어서 인자가 바로 argv[1]부터 시작합니다. slice(2)를 습관처럼 쓰면 인자 하나를 잃습니다.

--watch — 고치면 알아서 다시 돈다 v22 정식

nodemon 같은 도구를 따로 깔 이유가 없어졌습니다. 파일이 바뀌면 Node가 스스로 프로세스를 다시 띄웁니다.

# 감시할 스크립트를 하나 만든다
echo "console.log('첫 번째 버전')" > watched.mjs

# 백그라운드로 감시 실행을 띄운다

exports 필드가 없던 시절에는 남의 패키지 내부 파일을 마음대로 require할 수 있었습니다. 그래서 패키지 저자는 내부 구조를 영원히 바꿀 수 없었습니다.

SemVer 와 공급망

락파일 · audit · 설치 스크립트의 위험

범위 기호가 실제로 무엇을 허용하는가

^와 ~를 감으로 쓰지 말고, npm이 쓰는 바로 그 semver 구현에 직접 물어봅시다.

// npm 이 실제로 쓰는 semver 구현을 그대로 불러 확인한다
import semver from 'semver';

const versions = ['1.2.3', '1.2.9', '1.3.0', '2.0.0'];
const ranges = ['^1.2.3', '~1.2.3', '1.2.x', '>=1.2.3', '1.2.3'];

for (const range of ranges) {
  const ok = versions.filter((v) => semver.satisfies(v, range));
  console.log(range.padEnd(9), '->', ok.join(' '));
}
^1.2.3    -> 1.2.3 1.2.9 1.3.0
~1.2.3    -> 1.2.3 1.2.9
1.2.x     -> 1.2.3 1.2.9
>=1.2.3   -> 1.2.3 1.2.9 1.3.0 2.0.0
1.2.3     -> 1.2.3
한 줄 요약 — ^는 마이너까지 올리고(메이저 고정), ~는 패치까지만 올립니다. npm install이 기본으로 붙이는 것은 ^입니다.
0.x는 규칙이 다릅니다 — ^0.2.3은 0.3.0을 허용하지 않습니다. 1.0 이전에는 마이너 인상도 파괴적 변경으로 보기 때문입니다.

락파일 — 범위가 아니라 사실을 적는다

package.json에는 희망(^7.8.5)이 적히고, package-lock.json에는 실제로 깔린 것이 해시까지 함께 적힙니다.

integrity가 핵심입니다 — 내려받은 tarball의 해시입니다. 레지스트리가 같은 버전에 다른 내용을 돌려주면 설치가 실패합니다. 락파일은 편의가 아니라 무결성 장치입니다.
애플리케이션은 커밋하고, 라이브러리는 하지 않습니다 — 앱은 재현 가능한 배포가 목적이라 커밋합니다. 라이브러리의 락파일은 설치하는 쪽에서 무시되므로 커밋해도 소용이 없습니다.

libuv 스레드풀 — 사실 스레드가 더 있다

"Node는 싱글 스레드"는 자바스크립트가 싱글 스레드라는 뜻입니다. 파일 I/O나 암호 연산 같은 것은 뒤에서 스레드풀이 처리합니다. 크기를 바꿔 보면 드러납니다.

// pbkdf2 는 libuv 스레드풀에서 돈다. 풀 크기만큼만 동시에 진행된다.
import { pbkdf2 } from 'node:crypto';

const N = 4;
const started = Date.now();
const times = [];

console.log('UV_THREADPOOL_SIZE =', process.env.UV_THREADPOOL_SIZE ?? '(기본 4)');

for (let i = 0; i < N; i++) {
  pbkdf2('password', 'salt', 200000, 32, 'sha512', () => {
    times.push(Date.now() - started);
    if (times.length < N) return;

    const spread = Math.max(...times) - Math.min(...times);
    console.log('완료 개수:', times.length);
    console.log(spread < 100
      ? '첫 완료와 마지막 완료의 간격 100ms 미만 — 넷이 사실상 동시에 끝났다'
      : '첫 완료와 마지막 완료의 간격 100ms 이상 — 하나씩 차례로 끝났다');
  });
}

마이크로태스크

nextTick 대 Promise, 기아 현상 실측

단계 사이에 끼어드는 두 개의 큐

30장의 여섯 단계는 매크로태스크입니다. 그 사이사이에 훨씬 급한 두 줄이 따로 있습니다. Node는 한 단계를 마칠 때마다 이 둘을 완전히 비운 뒤에야 다음 단계로 갑니다.

큐무엇이 들어가나우선순위

기아 — 큐를 비울 수 없게 만들기

"큐가 빌 때까지 처리한다"는 규칙에는 함정이 있습니다. 처리하는 도중에 계속 새로 넣으면 영원히 비지 않습니다.

// nextTick 을 재귀로 걸면 루프가 다음 단계로 넘어가지 못한다
let ticks = 0;

setTimeout(() => console.log('타이머가 드디어 돌았다. 그때까지 tick 수:', ticks), 0);

function spin() {
  if (++ticks < 1000) process.nextTick(spin);
}

재귀로 일을 나눠 처리해야 한다면 process.nextTick이 아니라 setImmediate를 쓰세요. setImmediate는 check 단계라 루프가 한 바퀴 돌 기회를 줍니다.

에러 우선 콜백 — Node가 정한 약속

프로미스가 생기기 전, Node의 모든 비동기 함수는 이 규약 하나로 통일돼 있었습니다. 첫 인자는 에러, 결과는 그다음.

const { readFile } = require('node:fs');

// Node 의 콜백 규약: 첫 인자가 에러, 그 다음이 결과
readFile('./cb-convention.cjs', 'utf8', (err, data) => {
  if (err) return console.error('실패:', err.code);
  console.log('성공. 첫 줄:', data.split('\n')[0]);
});

readFile('./없는파일.txt', 'utf8', (err, data) => {
  if (err) return console.error('실패:', err.code);
  console.log('여기는 오지 않는다');
});
성공. 첫 줄: const { readFile } = require('node:fs');

실패: ENOENT
try/catch로는 못 잡습니다 — 콜백은 나중에, 완전히 다른 스택에서 불립니다. 그때 try 블록은 이미 끝나 있습니다. 그래서 에러를 인자로 넘기는 것입니다.

때로는 동기, 때로는 비동기 — 가장 고약한 버그

캐시를 붙이면서 흔히 저지르는 실수입니다. 캐시 적중이면 즉시 콜백을 부르고, 아니면 나중에 부릅니다. 이렇게 만들면 호출 순서가 상황에 따라 달라집니다.

// 캐시가 있으면 동기로, 없으면 비동기로 부르는 함수 — 절대 이렇게 만들면 안 된다
const cache = new Map();

function fetchValue(key, cb) {
  if (cache.has(key)) return cb(null, cache.get(key));   // 동기 호출
  setTimeout(() => { cache.set(key, key.toUpperCase()); cb(null, cache.get(key)); }, 0);
}
첫 번째: 첫 호출 다음 줄 -> 첫 호출 콜백 A
두 번째: 두 번째 호출 콜백 A -> 두 번째 호출 다음 줄
두 줄의 순서가 뒤집혔습니다 — 첫 호출에서는 콜백이 나중에, 두 번째 호출에서는 먼저 불렸습니다. 콜백 안에서 초기화한 변수를 그 아래 줄에서 쓰고 있었다면, 캐시가 차는 순간부터 동작이 달라집니다.
고치는 법은 한 줄입니다 — 동기 경로도 process.nextTick(() => cb(null, 값))으로 감싸 항상 비동기로 만드세요. "일관성 있게 느린" 것이 "가끔 빠른" 것보다 낫습니다.

promisify — 규약을 지켰다면 기계적으로 바뀐다

에러 우선 규약의 진짜 값어치가 여기서 나옵니다. 형태가 정해져 있으니 자동 변환이 가능합니다.

const { promisify } = require('node:util');
const { readFile } = require('node:fs');

// 에러 우선 규약을 지키는 함수는 기계적으로 프로미스로 바꿀 수 있다
const readFileAsync = promisify(readFile);

readFileAsync('./cb-promisify.cjs', 'utf8')
  .then((data) => console.log('promisify 성공, 길이:', data.length > 0))
  .catch((err) => console.error('실패:', err.code));

내장 모듈에는 이미 프로미스판이 있습니다 — node:fs/promises, node:dns/promises, node:timers/promises. promisify는 남의 오래된 라이브러리를 감쌀 때 씁니다.

콜백을 다룰 때의 네 가지 규칙

  1. 에러를 먼저 처리하고 return하세요. if (err) return cb(err). return을 빠뜨리면 아래 코드가 그대로 이어 돕니다.
  2. 콜백은 정확히 한 번만 부르세요. 두 번 부르면 그 뒤 로직이 두 번 돕니다. 프로미스는 두 번째 resolve를 무시하지만, 콜백에는 그런 보호 장치가 없습니다.
  3. 동기와 비동기를 섞지 마세요. 앞 장에서 본 그것입니다.
  4. 콜백 안에서 던지지 마세요. 아무도 못 잡고 uncaughtException으로 갑니다.
새 코드라면 콜백을 직접 쓸 일은 거의 없습니다 — 프로미스와 async/await가 위 네 가지를 문법 차원에서 막아 줍니다. 이 장이 필요한 이유는 남의 코드를 읽고 감싸야 하기 때문입니다. 다음 장에서 그 프로미스를 제대로 봅니다.

프로미스가 고친 것

앞 장의 네 가지 규칙을 다시 보면, 프로미스는 그것들을 지킬 수밖에 없게 만든 장치입니다.

콜백의 문제프로미스의 답
콜백을 두 번 부를 수 있다한 번 확정되면 다시 바뀌지 않는다
동기·비동기가 섞인다.then은 언제나 마이크로태스크로
에러를 인자로 날라야 한다try/catch가 통한다
중첩이 깊어진다체이닝·await로 평평해진다
"언제나 마이크로태스크"가 조용한 핵심입니다 — 이미 확정된 프로미스에 .then을 붙여도 콜백은 즉시 불리지 않고, 현재 동기 코드가 끝난 뒤에 불립니다. 앞 장에서 본 그 버그가 문법상 불가능해집니다.

네 가지 조합기

const ok = (v, ms) => new Promise((r) => setTimeout(() => r(v), ms));
const fail = (e, ms) => new Promise((_, j) => setTimeout(() => j(new Error(e)), ms));

console.log('all       :', await Promise.all([ok('a', 10), ok('b', 20)]));
console.log('allSettled:', (await Promise.allSettled([ok('a', 10), fail('b', 20)]))
  .map((r) => r.status).join(', '));
console.log('race      :', await Promise.race([ok('빠름', 10), ok('느림', 50)]));
console.log('any       :', await Promise.any([fail('먼저 실패', 10), ok('나중 성공', 30)]));

try {
  await Promise.all([ok('a', 10), fail('b', 20)]);
} catch (e) {
  console.log('all 은 하나만 실패해도 전체가 실패:', e.message);
}
all       : [ 'a', 'b' ]
allSettled: fulfilled, rejected
race      : 빠름
any       : 나중 성공
all 은 하나만 실패해도 전체가 실패: b
any와 race의 차이 — race는 먼저 끝난 것(실패여도)을 택하고, any는 먼저 성공한 것을 택합니다. 위에서 any는 10ms의 실패를 건너뛰고 30ms의 성공을 골랐습니다.

await를 반복문에 넣으면 병렬이 아니다

가장 자주 보는 성능 실수입니다. 문법이 너무 자연스러워서, 순차로 도는 줄 모른 채 지나갑니다.

const work = (name) => new Promise((r) => setTimeout(() => r(name), 100));

// 순차: 앞의 것이 끝나야 다음이 시작된다
const t1 = Date.now();
for (const n of ['a', 'b', 'c']) await work(n);
const seq = Date.now() - t1;

// 병렬: 셋을 한꺼번에 띄우고 모두 끝나기를 기다린다
const t2 = Date.now();
await Promise.all(['a', 'b', 'c'].map(work));
const par = Date.now() - t2;

console.log('순차가 병렬보다 오래 걸렸나:', seq > par * 2);
console.log('순차는 대략 3배:', Math.round(seq / par));
순차가 병렬보다 오래 걸렸나: true
순차는 대략 3배: 3
세 개라서 3배입니다. 백 개면 100배입니다 — 서로 의존하지 않는 작업이라면 먼저 전부 시작해 두고 Promise.all로 모으세요. 앞의 결과가 뒤의 입력일 때만 반복문 안의 await가 옳습니다.
다만 무한정 병렬은 답이 아닙니다 — 1만 개를 한꺼번에 띄우면 파일 핸들이나 상대 서버가 먼저 무너집니다. 동시 개수를 제한하는 방법은 11부에서 다룹니다.

아무도 잡지 않은 거부

거부된 프로미스에 .catch가 없으면 Node는 그것을 치명적으로 취급합니다. 기본 동작은 프로세스 종료입니다.

// 아무도 잡지 않은 거부는 프로세스를 죽인다
process.on('unhandledRejection', (reason) => {
  console.log('unhandledRejection 훅이 잡았다:', reason.message);
  process.exitCode = 0;
});

Promise.reject(new Error('아무도 안 잡음'));
console.log('동기 코드는 그대로 끝난다');
동기 코드는 그대로 끝난다
unhandledRejection 훅이 잡았다: 아무도 안 잡음
훅은 로그를 남기는 용도지, 무시하는 용도가 아닙니다 — 여기서는 보여 주려고 exitCode = 0으로 덮었지만, 실제 서비스에서는 기록을 남기고 우아하게 종료하는 것이 맞습니다. 잡히지 않은 거부가 있다는 것은 이미 어딘가 상태가 어긋났다는 뜻입니다.
가장 흔한 원인 — async 함수를 await 없이 부르는 것입니다. doWork()라고만 쓰면 그 안의 실패는 아무도 받지 못합니다. 일부러 기다리지 않는 것이라면 .catch(log)를 반드시 붙이세요.

Promise.withResolvers — 밖에서 풀어야 할 때

이벤트 하나를 기다리는 프로미스를 만들 때, 예전에는 let resolve;를 밖에 두고 생성자 안에서 대입하는 군더더기가 필요했습니다. 이제 한 줄입니다.

// resolve / reject 를 밖으로 꺼내야 할 때 쓴다 (ES2024)
const { promise, resolve } = Promise.withResolvers();

setTimeout(() => resolve('밖에서 풀었다'), 10);

console.log('withResolvers 가 준 키:', Object.keys(Promise.withResolvers()).join(', '));
console.log('결과:', await promise);
withResolvers 가 준 키: promise, resolve, reject
결과: 밖에서 풀었다
어디에 쓰나 — 이벤트 에미터의 한 번짜리 이벤트를 기다릴 때, 큐에 넣은 작업의 완료를 나중에 알려 줄 때처럼 프로미스를 만드는 곳과 확정하는 곳이 다를 때입니다. ES2024 표준이며 이 덱의 기준 런타임 v24에서 그대로 동작합니다.

AbortController — 취소를 위한 표준 손잡이 v15

프로미스에는 취소가 없습니다. 대신 브라우저에서 온 AbortController가 그 자리를 맡습니다. 컨트롤러가 스위치, 시그널이 배선입니다.

// AbortController 하나로 여러 작업을 한꺼번에 끊는다
const ac = new AbortController();

const sleep = (ms, signal) => new Promise((resolve, reject) => {
  const t = setTimeout(resolve, ms);
  signal.addEventListener('abort', () => { clearTimeout(t); reject(signal.reason); }, { once: true });
});

setTimeout(() => ac.abort(new Error('사용자가 취소함')), 20);

try {
  await sleep(1000, ac.signal);
  console.log('여기는 오지 않는다');
} catch (err) {
  console.log('취소됨:', err.message);
  console.log('signal.aborted:', ac.signal.aborted);
}
취소됨: 사용자가 취소함
signal.aborted: true
1초짜리 대기가 20밀리초 만에 끝났습니다 — 시그널 하나를 여러 작업에 나눠 주면 abort() 한 번으로 전부 끊깁니다. fetch · fs · timers/promises · events.once가 모두 signal 옵션을 받습니다.

AbortSignal.timeout — 시간 제한만 필요할 때 v17.3

타이머를 만들고, 지우고, 컨트롤러를 붙이는 상투적인 코드를 한 줄이 대신합니다.

import { setTimeout as delay } from 'node:timers/promises';

// 시간 제한만 필요하면 컨트롤러를 만들 필요가 없다
try {
  await delay(1000, undefined, { signal: AbortSignal.timeout(20) });
} catch (err) {
  console.log('name:', err.name);
  console.log('code:', err.code);
}
name: AbortError
code: ABORT_ERR
취소를 구분해서 다루세요 — 취소는 name === 'AbortError'(코드는 ABORT_ERR)로 옵니다. 사용자가 창을 닫아서 생긴 취소를 서버 장애로 집계하면 대시보드가 거짓말을 하게 됩니다.

AbortSignal.any — 사유가 여럿일 때 v20.3

"사용자가 취소하거나, 30초가 지나거나, 서버가 종료되면" 같은 조건은 시그널 여러 개를 하나로 묶어 표현합니다.

import { setTimeout as delay } from 'node:timers/promises';

// 여러 취소 사유 중 무엇이든 먼저 오면 끊는다
const userCancel = new AbortController();
const combined = AbortSignal.any([userCancel.signal, AbortSignal.timeout(500)]);

setTimeout(() => userCancel.abort(new Error('사용자가 먼저 눌렀다')), 20);

try {
  await delay(1000, undefined, { signal: combined });
} catch (err) {
  // delay 는 자기 몫의 AbortError 를 던진다
  console.log('던져진 오류:', err.name);
  // 진짜 사유는 신호에 남아 있다
  console.log('신호에 적힌 사유:', combined.reason.message);
}
던져진 오류: AbortError
신호에 적힌 사유: 사용자가 먼저 눌렀다
던져진 오류에는 사유가 안 담깁니다 — timers/promises는 자기 몫의 AbortError를 던집니다. 왜 취소됐는지 알려면 signal.reason을 직접 읽어야 합니다. 타임아웃과 사용자 취소를 나눠 기록하려면 이 구분이 필요합니다.

AsyncLocalStorage — 인자로 나르지 않고 문맥을 잇는다 v16 안정

요청 id를 로그에 남기려고 모든 함수에 인자를 하나씩 더한 적이 있다면, 그 문제를 푸는 도구입니다. 비동기 경계를 넘어가며 값이 따라다닙니다.

import { AsyncLocalStorage } from 'node:async_hooks';

// 비동기 호출을 건너가며 따라다니는 문맥 저장소
const als = new AsyncLocalStorage();

function deepInside() {
  // 인자로 넘기지 않았는데도 요청 id 를 알 수 있다
  console.log('  깊은 곳에서 본 요청 id:', als.getStore()?.requestId);
}

async function handle(id) {
  await als.run({ requestId: id }, async () => {
    await new Promise((r) => setTimeout(r, 10));
    deepInside();
  });
}

await Promise.all([handle('req-1'), handle('req-2')]);
console.log('바깥에서 본 저장소:', als.getStore());

  깊은 곳에서 본 요청 id: req-2

fs는 세 벌의 API를 가지고 있다

같은 일을 하는 함수가 셋씩 있습니다. 역사적 이유로 쌓인 것이고, 지금 새로 쓴다면 답은 정해져 있습니다.

// 같은 일을 세 벌의 API 로 — Node 의 fs 는 세 얼굴을 가지고 있다
import { readFileSync } from 'node:fs';
import { readFile as readFileCb } from 'node:fs';
import { readFile } from 'node:fs/promises';

const target = 'fs-three.mjs';

// 1. 동기 — 루프를 막는다
const a = readFileSync(target, 'utf8');
console.log('동기:', a.split('\n').length, '줄');

// 2. 콜백 — 에러 우선 규약
readFileCb(target, 'utf8', (err, b) => {
  if (err) throw err;
  console.log('콜백:', b.split('\n').length, '줄');

  // 3. 프로미스 — 지금 쓸 기본값
  readFile(target, 'utf8').then((c) => {
    console.log('프로미스:', c.split('\n').length, '줄');
    console.log('세 결과가 같은가:', a === b && b === c);
  });
});

청크 경계는 아무 의미가 없습니다 — 줄 단위도, 글자 단위도 아닙니다. 38장에서 본 대로 한글 3바이트 한가운데가 잘릴 수 있습니다. 줄로 나누려면 43장의 변환 스트림이 필요합니다.

쓰기 — _write 하나면 된다

받는 쪽을 직접 만들 일도 생깁니다. 구현할 것은 _write 하나이고, 마무리가 필요하면 _final을 더합니다.

    collected.push(chunk.toString());

    callback();
  },
  final(callback) {
    collected.push('[끝]');
    callback();
  },

sink.write('나');

end()는 "닫는다"입니다 — 마지막 청크를 함께 쓸 수 있고, 이후 write는 오류입니다. 완전히 끝났는지는 await finished(스트림)으로 기다리는 것이 가장 안전합니다.

상태를 가진 변환 — 줄 나누기

41장에서 "청크 경계는 줄 경계와 무관하다"고 했습니다. 그래서 줄 단위로 자르려면 남은 조각을 기억해야 합니다. 이것이 가장 자주 쓰이는 변환 스트림입니다.

// 청크 경계는 줄 경계와 아무 상관이 없다. 남은 조각을 스스로 들고 있어야 한다.
class LineSplitter extends Transform {
  #tail = '';

  constructor() { super({ readableObjectMode: true }); }

  _transform(chunk, encoding, callback) {
    const parts = (this.#tail + chunk).split('\n');
    this.#tail = parts.pop();          // 마지막 조각은 아직 줄이 아닐 수 있다
    for (const line of parts) this.push(line);
    callback();
  }

  _flush(callback) {
    if (this.#tail) this.push(this.#tail);   // 끝에 남은 것을 흘려보낸다
    callback();
  }
}

8부를 마치며 — 배관공의 규칙

  1. 잇는 것은 await pipeline(...). 배압과 정리를 함께 해결합니다.
  2. 읽는 것은 for await. 배압이 공짜로 지켜집니다.
  3. 변환은 비동기 제너레이터부터. 상태나 _flush가 필요할 때만 클래스로.
  4. 청크 경계를 믿지 마세요. 줄·글자·레코드 어느 것과도 일치하지 않습니다.
  5. write()의 반환값을 보세요. 직접 배관할 때 이것을 무시하면 스트림을 쓰는 의미가 사라집니다.
스트림은 "일정한 메모리"를 사는 대가로 복잡도를 지불하는 도구입니다 — 데이터가 작으면 그 대가가 아깝습니다. 크거나, 얼마나 클지 모르거나, 끝이 없다면(소켓·로그) 다른 선택지가 없습니다. 9부의 네트워크가 바로 그 세계입니다.

const server = createServer((req, res) => {

  const byPath = routes.filter((r) => r.pattern.test({ pathname: url.pathname }));

  if (byPath.length === 0) return send(res, 404, { error: '그런 경로 없음' });

    return send(res, 405, { error: '그 메서드는 안 됨' });

  route.handler(req, res, groups);
});

재시도와 지수 백오프

두 번 실패한 뒤 성공하는 서버를 세워 두면, 재시도 로직을 결정적으로 시험할 수 있습니다.

async function withRetry(url, { tries = 4, baseMs = 10 } = {}) {
  for (let attempt = 1; attempt <= tries; attempt++) {
    const res = await fetch(url);
    if (res.ok) return { res, attempt };
    // 5xx 만 재시도한다. 4xx 는 다시 해도 같은 결과다.
    if (res.status < 500 || attempt === tries) return { res, attempt };
    const wait = baseMs * 2 ** (attempt - 1);
    console.log(`${attempt}번째 시도 실패(${res.status}) — ${wait}ms 뒤 재시도`);
    await new Promise((r) => setTimeout(r, wait));
  }
}

2번째 시도 실패(503) — 20ms 뒤 재시도
최종 상태: 200 성공
시도 횟수: 3 | 서버가 받은 요청 수: 3

const GUID = '258EAFA5-E914-47DA-95CA-C5AB0DC85B11';

// 핸드셰이크: 클라이언트 키에 고정 GUID 를 붙여 SHA-1 하고 base64 로 돌려준다
function acceptKey(key) {
  return createHash('sha1').update(key + GUID).digest('base64');
}
server.on('upgrade', (req, socket) => {
  socket.write([
    'HTTP/1.1 101 Switching Protocols',

    '\r\n',

101 Switching Protocols 뒤부터는 HTTP가 아닙니다 — 그 소켓은 44장에서 본 그냥 TCP 소켓이 되고, 이후로는 WebSocket 프레임이 오갑니다. GUID는 RFC 6455에 박혀 있는 상수로, "정말 WebSocket을 이해하는 서버인가"를 증명하는 장치입니다.

프레임 하나 풀고 만들기

44장에서 본 대로 TCP에는 경계가 없으므로, WebSocket이 자기 경계를 직접 정합니다. 그것이 프레임입니다.

// 프레임 하나를 푼다 (텍스트, 클라이언트→서버라 마스킹되어 있다)
function decodeFrame(buf) {
  const opcode = buf[0] & 0x0f;
  const masked = (buf[1] & 0x80) !== 0;
  let len = buf[1] & 0x7f;
  let offset = 2;
  if (len === 126) { len = buf.readUInt16BE(2); offset = 4; }
  const mask = masked ? buf.subarray(offset, offset + 4) : null;
  if (masked) offset += 4;
  const payload = Buffer.from(buf.subarray(offset, offset + len));
  if (mask) for (let i = 0; i < payload.length; i++) payload[i] ^= mask[i % 4];
  return { opcode, text: payload.toString() };
}
자리뜻
첫 바이트 하위 4비트opcode — 0x1 텍스트, 0x2 이진, 0x8 닫기, 0x9/0xA 핑/퐁
둘째 바이트 최상위 비트마스킹 여부. 클라이언트→서버는 반드시 마스킹
둘째 바이트 하위 7비트길이. 126이면 다음 2바이트, 127이면 다음 8바이트가 진짜 길이
이 코드는 교육용입니다 — 조각난 프레임(연속 opcode 0x0), 64비트 길이, 핑/퐁 자동 응답, 여러 프레임이 한 data에 붙어 오는 경우를 다루지 않습니다. 44장의 경계 문제가 여기에도 그대로 있습니다. 실무에서는 검증된 라이브러리를 쓰세요.

  • 'inherit'는 로그를 그대로 흘려보낼 때 편합니다. 빌드 도구를 감싸는 스크립트에서 특히 그렇습니다.

절대 시간을 싣지 않은 이유 — 기기와 부하에 따라 달라져 재실행할 때마다 값이 바뀝니다. 그래서 비율로만 판정했고, 이 판정은 네 번 연속 같은 결과를 냈습니다.

workerData와 MessageChannel

워커에 값을 전하는 길이 셋입니다. 시작할 때 한 번(workerData), 기본 통로(parentPort), 그리고 따로 놓는 선(MessageChannel).

// workerData 는 워커가 시작될 때 한 번 건네는 초기 설정이다
const worker = new Worker(new URL('./worker-port.mjs', import.meta.url), {
  workerData: { greeting: '설정으로 받은 값' },
});

// MessageChannel 은 별도의 통신 선을 하나 더 놓는다
const { port1, port2 } = new MessageChannel();
worker.postMessage({ port: port2 }, [port2]);

const viaChannel = await new Promise((resolve) => {
  port1.on('message', resolve);
  port1.postMessage('전용 선으로 보냄');
});

console.log('워커가 답한 것:', viaChannel);
워커가 답한 것: 전용 선으로 보냄 / 설정으로 받은 값
포트도 transferList로 넘깁니다 — port2는 복제할 수 없는 물건이라 반드시 이전해야 합니다. 앞 장의 ArrayBuffer 이전과 같은 문법입니다.
선을 나누면 코드가 깔끔해집니다 — 한 통로에 여러 종류의 메시지를 섞으면 switch (msg.type)가 길어집니다. 용도별로 채널을 따로 두면 각 핸들러가 한 가지만 다룹니다. 워커끼리 직접 이야기하게 만들 때도 이 포트를 서로에게 넘깁니다.
