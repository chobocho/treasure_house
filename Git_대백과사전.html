왜 Git 을 밑바닥까지 보는가

Git 은 명령 몇 개를 외우면 쓸 수 있습니다. 그런데 사고가 나는 순간 — 리베이스가 꼬이고, 브랜치가 사라지고, 푸시가 거절당하는 순간 — 외운 명령은 아무것도 설명해 주지 않습니다.

그때 필요한 것은 Git 이 디스크에 무엇을 적는가에 대한 그림입니다. 객체 네 종류, 이름표 몇 장, 인덱스 파일 하나. 이 그림이 머리에 있으면 명령은 외울 것이 아니라 읽을 것이 됩니다.

이 덱의 약속 — Git 이 어떻게 동작한다고 적은 자리에는 그것을 보여 주는 진짜 git 의 실행 캡처가 붙어 있습니다. 코드는 전부 실제로 돌아가고, 형식·프로토콜을 인용한 자리에는 공식 문서와 절 제목이 배지로 붙습니다.
설명용

이 덱이 흔한 Git 해설과 다른 점

흔한 방식이 덱
"커밋은 스냅숏이다" 라고 말로 설명합니다 커밋 객체의 바이트를 git cat-file 로 꺼내 보이고, 손으로 만든 객체를 git 이 읽는지 실험합니다
명령 출력을 기억으로 옮겨 적습니다 빈 저장소에서 스크립트가 진짜 git 을 돌려 남긴 캡처만 싣고, 세 번 돌려 바이트까지 같은 것만 씁니다
형식 설명을 블로그에서 가져옵니다 git 저장소의 공식 형식 문서를 받아 두고, 인용한 절 제목이 그 문서에 진짜 있는지를 빌드가 검사합니다
"직접 만들어 보기" 는 한 언어, 한 번입니다 같은 규격서로 다섯 언어가 같은 미니 Git 을 만들고, 그 결과를 진짜 git 이 검사합니다
설명용

진짜 git 이 심판이다

이 덱에서 "Git 은 이렇게 한다" 는 문장의 근거는 사람의 기억이 아니라 이 기계에 설치된 git 2.55.0 입니다.

  • 원리를 설명하는 장은 run_all.py 가 빈 저장소를 새로 만들고 진짜 git 을 돌려 남긴 캡처를 싣습니다. 캡처 첫 줄이 곧 그 명령입니다.
  • 부록의 미니 Git(mygit)이 만든 객체·인덱스·팩은 git fsck --strict, git cat-file, git index-pack --strict 가 받아들여야 통과입니다.
  • 시험에 쓰는 기준 바이트(golden/)도 진짜 git 이 먼저 만듭니다. 그래서 구현을 한 줄도 쓰기 전에 시험이 올바른 까닭으로 실패합니다.
  • 설명과 git 이 어긋나면 고치는 쪽은 설명입니다. 심판을 고치지 않습니다.
설명용

다섯 언어, 규격서 하나

부록 A 는 같은 미니 Git 을 다섯 언어로 만듭니다. 다섯 구현은 모두 git/SPEC.md 한 장을 따르고, 같은 기준 바이트로 시험받습니다.

언어맡은 일
Python이야기의 앞장 — 단계마다 파이썬으로 먼저 걸어 봅니다
Go · TypeScript · Java같은 단계를 같은 함수 이름으로 — 넷을 한 화면에 나란히 봅니다
C++zlib 도 없이 — inflate 와 deflate(저장 블록)까지 손으로 짭니다

SHA-1 은 다섯 언어 모두 손으로 짭니다. 표준 라이브러리의 해시는 시험에서 답을 맞춰 보는 데만 씁니다.

이 책을 읽는 법

한 장에 한 가지만 담았습니다. 모르는 낱말이 나오면 부록 B 의 용어집을 보십시오 — 낱말마다 "처음 나온 자리" 로 가는 화살표가 붙어 있습니다.

  • 2~6부가 뼈대입니다. 객체·참조·인덱스를 알고 나면 뒤의 모든 명령이 그 셋을 움직이는 일로 읽힙니다.
  • 7~11부는 머지·리베이스·diff·팩·전송, 12~14부는 협업·도구·한계입니다.
  • 15·16부는 활용 가이드 — 일상 레시피와 사고 복구 장면입니다. 급하면 여기부터 봐도 됩니다.
  • 코드 블록 위의 회색 줄은 어느 파일 몇 번째 줄인지를 말합니다. 옮겨 적은 코드가 아닙니다.
  • 어두운 바탕의 블록은 진짜 git 을 돌린 출력이고, 첫 줄이 그 명령입니다.
  • 남색 둥근 배지는 근거가 된 공식 문서와 절 제목입니다. 배지는 조립기만 만들 수 있습니다.
  • 열다섯 장쯤마다 퀴즈가 한 장씩 나옵니다. 답은 단추를 누르면 펼쳐집니다.
  • 이 문서는 자기완결형입니다 — 외부 스크립트·글꼴·이미지를 하나도 부르지 않습니다.

증거 등급 — 이 장을 얼마나 믿어도 되나

기술 문서가 틀리는 자리는 대개 "확인하지 않고 적은 문장" 입니다. 그래서 장마다 무엇으로 확인했는지를 배지로 붙였습니다.

배지뜻

근거를 못 찾으면 — 문장을 빼거나 미확인 을 붙여 모른다고 적습니다.

실험 환경 — 캡처를 세 번 똑같이 뜨려면

실행 검증

캡처 읽는 법 — 첫 줄이 명령이다

어두운 블록은 실험 스크립트가 빈 저장소를 만들고 진짜 git 을 돌려 남긴 것입니다. 블록의 첫 줄은 $ 와 그때 돌린 명령 그대로이고, 그 아래가 화면에 찍힌 전부입니다.

out/hello__init-b-main.txt전체 2줄이 덱의 첫 캡처
$ git init -b main
Initialized empty Git repository in /work/hello/.git/
  • 실험 저장소는 이 기계의 긴 경로 대신 /work/<실험 이름> 으로 바꿔 적습니다. 바꾸는 것은 이 한 가지뿐이고, 바꾼 자리는 캡션이 밝힙니다.
  • 표준 출력과 표준 오류는 섞어서(2>&1 처럼) 한 블록에 담습니다.
실행 검증

실패도 캡처한다

명령이 0 이 아닌 코드로 끝나면 블록 끝에 [exit N] 이 붙습니다. 거절·충돌·오류 메시지도 지어내지 않고 git 이 낸 그대로 싣습니다.

out/proto_work.nonff__c-v2-push-origin-main-2-1.txt전체 5줄빨리 감기가 아닌 push 의 거절
$ git -C v2 push origin main 2>&1
To file:///work/proto_work/../proto_origin
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'file:///work/proto_work/../proto_origin'
[exit 1]

이 거절이 왜 일어나는지는 11부(전송)와 12부(협업)에서 다룹니다. 여기서는 모양만 봐 두십시오 — ! 로 시작하는 줄과 끝의 종료 코드.

실행 검증

직접 다시 떠 보려면

캡처는 전부 git/run_all.py 한 파일이 만듭니다. 덱을 만드는 과정도, 독자가 다시 떠 보는 과정도 같은 make 대상을 씁니다.

Makefile195–205실험을 돌리고, 세 번 떠서 견준다
run:                    ## 실험을 전부 직렬로 돌려 out/ 를 채운다
	$(PY) run_all.py

run-check:              ## 캡처의 폭과 manifest 가 맞는지만 본다
	@if test -f run_all.py; then $(PY) run_all.py --check; \
	else echo '  run_all.py 아직 없다 (PLAN.md §5 7단계)'; fi

# 세 번 떠서 md5 가 같아야 한다. 캡처가 그 실행의 우연(시각·경로·
# 딕셔너리 차례)에 기대면 여기서 걸린다. 25분쯤 걸리니 뒤에서 돌린다.
record:                 ## 캡처를 세 번 돌려 같은지 본다
	sh tools/record.sh --check

make run 한 번은 이 기계에서 8분 남짓입니다. make record 는 두 번을 더 돌려 파일마다 md5 를 견줍니다.

실행 검증

세 번 떠서 같아야 싣는다

캡처가 그 실행의 우연 — 시각, 난수, 해시 테이블의 차례 — 에 기대면 독자가 같은 명령을 돌렸을 때 다른 답이 나옵니다. 그런 장은 증거가 아니라 그림입니다.

tools/record.sh29–48첫 결과를 두고 두 번 더 돌려 견준다
if [ "${1:-}" = '--check' ]; then
  first=$(md5_all)
  echo "  1회차 — 지금 out/ 에 있는 것"
  n=2
  while [ "$n" -le 3 ]; do
    echo "  ${n}회차 — 다시 돌린다"
    $PY run_all.py >/dev/null
    later=$(md5_all)
    if [ "$first" != "$later" ]; then
      echo '  ✗ 두 번 돌린 결과가 다르다:'
      printf '%s\n' "$first" > out/.md5_1
      printf '%s\n' "$later" > "out/.md5_$n"
      diff out/.md5_1 "out/.md5_$n" || true
      exit 1
    fi
    n=$((n + 1))
  done
  echo "  ✓ 캡처 $(md5_all | wc -l)개가 3회차까지 같다"
  exit 0
fi

그래서 이 덱에는 걸린 시간을 적은 캡처가 없습니다. 크기는 바이트와 객체 수로, 속도는 비율로만 싣습니다.

실행 검증

기준 바이트 — golden/

부록 A 의 다섯 구현은 구현을 한 줄도 쓰기 전에 시험부터 가집니다. 그 시험의 답은 사람이 적지 않고, 진짜 git 이 먼저 만들어 golden/ 에 넣어 둡니다.

tools/make_golden.py268–290인덱스 픽스처 — 진짜 git add 가 쓴 파일을 그대로 담는다
def g_index(env):
    """git 이 쓴 인덱스 세 가지 — 확장 없음, TREE 확장, 판 3."""
    r = Repo('index', env)
    r.write('hello.txt', b'hello\n')
    r.write('run.sh', b'#!/bin/sh\n', 0o755)
    r.write('src/a.py', b'print(1)\n')
    r.write('한글.txt', '가\n'.encode())
    r.git('add', '.')
    idx = os.path.join(r.path, '.git', 'index')
    plain = open(idx, 'rb').read()
    out('index/plain.raw', plain)
    out('index/plain.bin', normalize_index(plain), 'stat 0 으로 정규화',
        'git add . (확장 없음)')
    out('index/ls-stage.txt', r.git('ls-files', '--stage').decode())
    r.git('commit', '-q', '-m', 'c')
    tree = open(idx, 'rb').read()
    assert b'TREE' in tree
    out('index/tree-ext.raw', tree, 'TREE 확장 포함', 'git commit')
    r.git('update-index', '--skip-worktree', 'run.sh')
    v3 = open(idx, 'rb').read()
    assert struct.unpack('>I', v3[4:8])[0] == 3
    out('index/v3.raw', v3, '판 3 · skip-worktree',
        'git update-index --skip-worktree run.sh')

시험이 맨 처음 실패할 때 그 까닭이 "아직 안 만들었다" 여야 합니다. "답이 틀렸다" 로 실패하면 시험이 아니라 답을 의심해야 하니까요.

0부 퀴즈

Q. 어떤 장에 "실행 검증" 배지가 붙어 있는데, 그 장의 캡처 끝에 [exit 1] 이 찍혀 있습니다. 이 캡처는 믿어도 됩니까? 그리고 이 덱에 걸린 시간(초)을 적은 캡처가 없는 까닭은 무엇입니까?

A. 믿어도 됩니다. [exit 1] 은 명령이 실패했다는 기록이지 캡처가 잘못됐다는 뜻이 아닙니다 — 거절·충돌도 git 이 낸 그대로 싣습니다. 걸린 시간은 돌릴 때마다 달라 세 번 떠서 바이트까지 같아야 한다는 규칙을 통과할 수 없어서 싣지 않습니다. 크기는 바이트·객체 수로, 속도는 비율로 적습니다.
설명용

이 덱을 만든 기계

이 덱의 모든 실행은 접는 폰 한 대에서 돌았습니다. 그 제약이 실험의 크기를 정했습니다.

  • 남는 메모리가 적어, 기록 실행은 하나씩 차례로 돌립니다.
  • 큰 저장소 실험(수만 개 파일, 큰 바이너리)은 몇 분 안에 끝나는 크기로 줄였고, 그 크기는 표가 out/ 에서 가져와 보여 줍니다 — 본문에 손으로 적지 않습니다.
  • 걸린 시간은 본문에 적지 않습니다. 기계마다 다르기 때문입니다. 속도는 같은 기계에서 잰 비율로만 싣습니다.
  • git 저장소 자체의 역사는 전체를 받지 않고, 커밋과 트리만 담은 부분 복제(--filter=blob:none)로 살펴봅니다.
