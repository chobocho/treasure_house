왜 Git 을 밑바닥까지 보는가

Git 은 명령 몇 개를 외우면 쓸 수 있습니다. 그런데 사고가 나는 순간 — 리베이스가 꼬이고, 브랜치가 사라지고, 푸시가 거절당하는 순간 — 외운 명령은 아무것도 설명해 주지 않습니다.

그때 필요한 것은 Git 이 디스크에 무엇을 적는가에 대한 그림입니다. 객체 네 종류, 이름표 몇 장, 인덱스 파일 하나. 이 그림이 머리에 있으면 명령은 외울 것이 아니라 읽을 것이 됩니다.

이 덱의 약속 — Git 이 어떻게 동작한다고 적은 자리에는 그것을 보여 주는 진짜 git 의 실행 캡처가 붙어 있습니다. 코드는 전부 실제로 돌아가고, 형식·프로토콜을 인용한 자리에는 공식 문서와 절 제목이 배지로 붙습니다.

설명용

진짜 git 이 심판이다

이 덱에서 "Git 은 이렇게 한다" 는 문장의 근거는 사람의 기억이 아니라 이 기계에 설치된 git 2.55.0 입니다.

  • 원리를 설명하는 장은 run_all.py 가 빈 저장소를 새로 만들고 진짜 git 을 돌려 남긴 캡처를 싣습니다. 캡처 첫 줄이 곧 그 명령입니다.
  • 부록의 미니 Git(mygit)이 만든 객체·인덱스·팩은 git fsck --strict, git cat-file, git index-pack --strict 가 받아들여야 통과입니다.
  • 시험에 쓰는 기준 바이트(golden/)도 진짜 git 이 먼저 만듭니다. 그래서 구현을 한 줄도 쓰기 전에 시험이 올바른 까닭으로 실패합니다.
  • 설명과 git 이 어긋나면 고치는 쪽은 설명입니다. 심판을 고치지 않습니다.

어두운 블록은 실험 스크립트가 빈 저장소를 만들고 진짜 git 을 돌려 남긴 것입니다. 블록의 첫 줄은 $ 와 그때 돌린 명령 그대로이고, 그 아래가 화면에 찍힌 전부입니다.

실행 검증

실패도 캡처한다

명령이 0 이 아닌 코드로 끝나면 블록 끝에 [exit N] 이 붙습니다. 거절·충돌·오류 메시지도 지어내지 않고 git 이 낸 그대로 싣습니다.

out/proto_work.nonff__c-v2-push-origin-main-2-1.txt전체 5줄빨리 감기가 아닌 push 의 거절
$ git -C v2 push origin main 2>&1
To file:///work/proto_work/../proto_origin
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'file:///work/proto_work/../proto_origin'
[exit 1]

이 거절이 왜 일어나는지는 11부(전송)와 12부(협업)에서 다룹니다. 여기서는 모양만 봐 두십시오 — ! 로 시작하는 줄과 끝의 종료 코드.

직접 다시 떠 보려면

캡처는 전부 git/run_all.py 한 파일이 만듭니다. 덱을 만드는 과정도, 독자가 다시 떠 보는 과정도 같은 make 대상을 씁니다.

	$(PY) run_all.py

run-check:              ## 캡처의 폭과 manifest 가 맞는지만 본다
	@if test -f run_all.py; then $(PY) run_all.py --check; \
	else echo '  run_all.py 아직 없다 (PLAN.md §5 7단계)'; fi

# 세 번 떠서 md5 가 같아야 한다. 캡처가 그 실행의 우연(시각·경로·
# 딕셔너리 차례)에 기대면 여기서 걸린다. 25분쯤 걸리니 뒤에서 돌린다.

실행 검증

세 번 떠서 같아야 싣는다

캡처가 그 실행의 우연 — 시각, 난수, 해시 테이블의 차례 — 에 기대면 독자가 같은 명령을 돌렸을 때 다른 답이 나옵니다. 그런 장은 증거가 아니라 그림입니다.

tools/record.sh29–48첫 결과를 두고 두 번 더 돌려 견준다
if [ "${1:-}" = '--check' ]; then
  first=$(md5_all)
  echo "  1회차 — 지금 out/ 에 있는 것"
  n=2
  while [ "$n" -le 3 ]; do
    echo "  ${n}회차 — 다시 돌린다"
    $PY run_all.py >/dev/null
    later=$(md5_all)
    if [ "$first" != "$later" ]; then
      echo '  ✗ 두 번 돌린 결과가 다르다:'
      printf '%s\n' "$first" > out/.md5_1
      printf '%s\n' "$later" > "out/.md5_$n"
      diff out/.md5_1 "out/.md5_$n" || true
      exit 1
    fi
    n=$((n + 1))
  done
  echo "  ✓ 캡처 $(md5_all | wc -l)개가 3회차까지 같다"
  exit 0
fi

그래서 이 덱에는 걸린 시간을 적은 캡처가 없습니다. 크기는 바이트와 객체 수로, 속도는 비율로만 싣습니다.

기준 바이트 — golden/

부록 A 의 다섯 구현은 구현을 한 줄도 쓰기 전에 시험부터 가집니다. 그 시험의 답은 사람이 적지 않고, 진짜 git 이 먼저 만들어 golden/ 에 넣어 둡니다.

tools/make_golden.py268–290인덱스 픽스처 — 진짜 git add 가 쓴 파일을 그대로 담는다
def g_index(env):
    """git 이 쓴 인덱스 세 가지 — 확장 없음, TREE 확장, 판 3."""
    r = Repo('index', env)
    r.write('hello.txt', b'hello\n')
    r.write('run.sh', b'#!/bin/sh\n', 0o755)
    r.write('src/a.py', b'print(1)\n')
    r.write('한글.txt', '가\n'.encode())
    r.git('add', '.')
    idx = os.path.join(r.path, '.git', 'index')
    plain = open(idx, 'rb').read()
    out('index/plain.raw', plain)
    out('index/plain.bin', normalize_index(plain), 'stat 0 으로 정규화',
        'git add . (확장 없음)')
    out('index/ls-stage.txt', r.git('ls-files', '--stage').decode())
    r.git('commit', '-q', '-m', 'c')
    tree = open(idx, 'rb').read()
    assert b'TREE' in tree
    out('index/tree-ext.raw', tree, 'TREE 확장 포함', 'git commit')
    r.git('update-index', '--skip-worktree', 'run.sh')
    v3 = open(idx, 'rb').read()
    assert struct.unpack('>I', v3[4:8])[0] == 3
    out('index/v3.raw', v3, '판 3 · skip-worktree',
        'git update-index --skip-worktree run.sh')

시험이 맨 처음 실패할 때 그 까닭이 "아직 안 만들었다" 여야 합니다. "답이 틀렸다" 로 실패하면 시험이 아니라 답을 의심해야 하니까요.

이 부의 목표 — 그림 한 장

Git 을 오래 써도 헷갈리는 까닭은 대개 하나입니다. 명령 이름이 머릿속의 그림과 맞지 않기 때문입니다.

이 부는 그 그림을 그립니다. 일곱 가지 생각이면 충분합니다.

  • Git 은 판마다 전체의 스냅숏을 적는다
  • 모든 것의 이름은 내용의 해시다
  • 저장소는 객체 네 종류가 서로를 가리키는 그래프다

  • 편집은 작업 트리 · 인덱스 · HEAD 세 영역 사이를 오간다
  • 모든 복제본이 온전한 저장소다
  • 명령에는 사람용(porcelain)과 도구용(plumbing) 두 층이 있다

실험 — 셋 중 하나만 바꾸기

파일 셋(a.txt · b.txt · c.txt)을 커밋하고, b.txt 하나만 고쳐 다시 커밋했습니다. 첫 커밋의 트리부터 봅니다.

100644 blob af17f6cc87e4d5e4adec0018cbb73d3e2bd008c8	c.txt

"판마다 전체를 적는다" 는 말은 비싸게 들립니다. 실제로 싼 까닭은 앞의 실험에 다 있습니다.

그래서 커밋 하나의 비용은 바뀐 것의 크기에 비례하고, 프로젝트 전체의 크기와는 거의 무관합니다.

이름이 곧 내용의 해시

이름을 붙이지 않고 계산한다

보통의 파일 시스템에서 이름은 사람이 붙입니다. Git 의 객체 저장소에서는 이름을 계산합니다 — 객체의 바이트를 SHA-1 에 넣은 결과가 이름입니다.

  • 같은 바이트 → 언제, 어디서, 누가 계산해도 같은 이름
  • 한 바이트라도 다르면 → 전혀 다른 이름
  • 이름을 알면 → 받은 내용이 맞는지 다시 계산해서 확인할 수 있음

이런 저장소를 내용 주소 저장소(content-addressable storage)라고 부릅니다.

실행 검증

내용 주소가 강제하는 것 — 불변

이름이 내용에서 나오므로, 객체를 "고친다" 는 말이 성립하지 않습니다. 고친 내용은 다른 이름을 가진 다른 객체입니다.

  • 파일을 고치면 → 새 blob
  • 새 blob 을 가리키는 트리 → 새 트리
  • 새 트리를 가리키는 커밋 → 새 커밋
  • 부모가 달라진 커밋 → 새 커밋(부모의 이름이 커밋 바이트에 들어 있으므로)

그래서 커밋 하나의 이름은 그 커밋까지 이르는 역사 전체를 봉인합니다. 역사의 어느 한 바이트를 바꿔도 그 뒤의 모든 커밋 이름이 바뀝니다.

커밋 메시지에 오타가 있어 git commit --amend 로 고쳤습니다. 고치기 전:

"역사를 고친다" 의 실제 뜻

amend·rebase·filter-repo 같은 "역사 고치기" 명령은 모두 같은 일을 합니다.

  1. 원하는 모습의 새 커밋들을 만든다
  2. 브랜치 이름표를 새 커밋으로 옮긴다
  3. 옛 커밋은 그대로 둔다 — 닿지 않게 될 뿐

그래서 "고친" 역사를 이미 가져간 사람이 있으면 두 역사가 갈라집니다. 옛 커밋이 여전히 그 사람 저장소에서 살아 있기 때문입니다(8·12부).

A. 지워지지 않았습니다. amend 는 새 커밋을 만들고 브랜치 이름표를 옮겼을 뿐이라, 옛 커밋은 객체 저장소에 남아 있고 reflog(HEAD@{1} 등)로 찾을 수 있습니다 — gc 가 닿지 않는 객체를 치우기 전까지는. 브랜치에 속한 커밋 목록은 어디에도 없습니다. main 파일에는 커밋 이름 하나뿐이고, 역사는 거기서 부모 화살표를 따라가며 계산합니다.
설명용

5장

세 영역

작업 트리 · 인덱스 · HEAD

파일이 사는 세 곳

세 영역과 그 사이를 옮기는 명령

  • 작업 트리 — 편집기로 여는 디스크의 파일
  • 인덱스 — .git/index. "다음 커밋은 이렇게 생길 것" 이라는 초안
  • HEAD 의 커밋 — 마지막으로 커밋한 스냅숏

명령은 거의 모두 이 셋 사이에서 무엇을 어느 쪽으로 옮기는 일입니다. 화살표와 명령의 대응은 6부에서 명령 하나씩 캡처로 확인합니다.

설명용

작업 트리에만 있을 때

빈 저장소에 hello.txt 를 만들기만 했습니다.

out/hello__status.txt전체 9줄아직 커밋도 add 도 없다
$ git status
On branch main

No commits yet

Untracked files:
	hello.txt

nothing added to commit but untracked files present

git 은 이 파일을 "추적하지 않는 파일" 이라고 부릅니다. 인덱스에도 HEAD 에도 없기 때문입니다. .git 안에는 아직 이 파일의 흔적이 전혀 없습니다.

실행 검증

add 가 하는 일 — blob 을 지금 만든다

out/hello.added__status-short.txt전체 2줄git add hello.txt 뒤
$ git status --short
A  hello.txt
out/hello.added__find-.git-objects-type-d-sort.txt전체 2줄그 순간의 객체 저장소
$ find .git/objects ! -type d | sort
.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a

git add 는 목록에 이름을 적어 두는 명령이 아닙니다. 그 순간의 내용으로 blob 을 만들어 저장소에 넣고, 인덱스에 "이 경로 = 이 blob" 을 적습니다. 그래서 add 뒤에 파일을 또 고치면, 커밋되는 것은 add 했을 때의 내용입니다.

-type f 가 아니라 ! -type d 인 까닭 — 이 기계의 find 가 읽기 전용 객체 파일을 파일로 못 알아봐서입니다. 뜻은 같습니다.

인덱스에 적힌 것

작업 트리만 바뀌었을 때

왜 인덱스가 따로 있나

  • 커밋을 고른다 — 고친 파일 열 개 가운데 셋만, 한 파일 안에서도 일부만 (add -p, 15부) 다음 커밋에 넣을 수 있습니다.
  • 빠르다 — 인덱스는 파일마다 크기·시각을 기억해 두어, status 가 파일을 다 읽지 않고 바뀐 것만 골라냅니다(5부).
  • 머지의 작업대 — 충돌한 경로는 인덱스에 세 판(공통 조상·우리·그쪽)으로 올라갑니다(7부).

5장 퀴즈

Q. notes.txt 를 고치고 git add notes.txt 한 뒤 한 줄을 더 고쳤습니다. git status --short 는 무엇을 보이고, 지금 git commit 하면 두 번째 고침이 들어갑니까?

A. MM notes.txt 입니다 — 왼쪽 M(인덱스가 HEAD 와 다름), 오른쪽 M(작업 트리가 인덱스와 다름). 커밋에는 들어가지 않습니다. add 는 그 순간의 내용으로 blob 을 만들어 인덱스에 적었고, 커밋은 인덱스를 트리로 만들 뿐 작업 트리를 다시 읽지 않기 때문입니다.

분산

모든 복제본이 온전한 저장소다

중앙 서버가 없어도 되는 까닭

중앙 집중형 도구에서 역사는 서버에 있고, 사용자의 디스크에는 작업 사본만 있습니다. Git 의 clone 은 객체 저장소를 통째로 복사합니다.

  • 역사 보기·브랜치·커밋·diff·머지 — 전부 네트워크 없이 됩니다
  • "서버" 는 모두가 약속한 복제본 하나일 뿐, 기술적으로 특별하지 않습니다
  • 서버가 사라져도 아무 복제본에서 다시 세울 수 있습니다

층예성격

Q. 사내 Git 서버의 디스크가 망가졌습니다. 개발자 노트북의 복제본으로 무엇을 되살릴 수 있고, 무엇은 되살릴 수 없을 수 있습니까? 그리고 사내 도구가 git status 의 출력을 파싱한다면 어떤 옵션을 써야 합니까?

A. 복제본이 마지막으로 받아 온 시점까지의 모든 커밋·트리·blob 과 그 브랜치들은 되살릴 수 있습니다 — 복제본이 온전한 저장소이기 때문입니다. 누구도 받아 가지 않은, 서버에만 푸시된 커밋이나 서버 쪽 설정·훅은 되살리지 못할 수 있습니다. 파싱에는 사람용 출력 대신 --porcelain(또는 --porcelain=v2)을 씁니다 — 판이 바뀌어도 형식을 지키기로 약속한 출력입니다.

3부

객체 모델

blob · tree · commit · tag 의 바이트, 이름 짓기, 그리고 깨졌을 때

이 부에서 할 일

2부에서 "객체는 네 종류, 이름은 내용의 해시" 라고 했습니다. 이 부는 그 문장을 바이트 하나하나로 확인합니다.

  • 객체 파일 하나를 열어 압축을 풀고 머리와 몸을 나눈다
  • 네 종류마다 몸의 형식 — 특히 트리의 이진 형식과 정렬 규칙
  • 커밋 이름을 정하는 것 — 무엇이 한 글자만 달라도 새 이름이 되는가
  • 객체를 이름으로 부르는 여러 방법과, 짧은 이름이 겹칠 때
  • fsck 가 잡아내는 형식 오류들
  • SHA-1 에서 SHA-256 으로

부록 A 의 미니 Git 이 이 부의 규칙을 그대로 구현합니다. 이 부에는 그 Python 판의 핵심 몇 줄만 싣습니다.

def header(type_, body):
    return b'%s %d\0' % (type_.encode(), len(body))


def hash_object(type_, body):
    """객체 이름(16진 40글자). 저장소를 건드리지 않는다."""
    return sha1_hex(header(type_, body) + body)

def write_object(gitdir, type_, body):
    """느슨한 객체 하나를 쓰고 이름을 돌려준다.

    이미 있으면 아무것도 하지 않는다 — 이름이 같으면 내용도 같기
    때문이다(0444 라 덮어쓰려 하면 실패하기도 한다). 임시 파일에 다
    쓴 뒤 이름을 바꿔 넣어, 도중에 죽어도 반쯤 쓴 객체가 남지 않는다.
    """
    oid = hash_object(type_, body)
    path = object_path(gitdir, oid)
    if os.path.exists(path):
        return oid
    d = os.path.dirname(path)
    os.makedirs(d, exist_ok=True)
    fd, tmp = tempfile.mkstemp(dir=d, prefix='tmp_obj_')
    try:
        with os.fdopen(fd, 'wb') as f:
            f.write(zlib.compress(header(type_, body) + body))
        os.chmod(tmp, 0o444)
        os.rename(tmp, path)
    except BaseException:
        if os.path.exists(tmp):
            os.remove(tmp)
        raise
    return oid
  • 이미 있으면 쓰지 않습니다 — 이름이 같으면 내용도 같기 때문입니다.
  • 임시 파일에 다 쓴 뒤 이름을 바꿔 넣습니다. 도중에 죽어도 깨진 객체가 남지 않습니다.
  • 권한을 읽기 전용(0444)으로 둡니다. git 이 만든 객체 파일도 그렇습니다.

def serialize_tree(entries):
    """[(모드, 이름, 객체 이름)] → 트리 몸. 정렬은 여기서 한다.

    모드는 앞에 0 을 붙이지 않는다 — 디렉터리는 '40000' 다섯 글자다.
    '040000' 은 cat-file -p 가 찍어 보일 때의 꼴일 뿐이다.
    """
    ents = sorted(entries, key=lambda e: tree_entry_key(e[0], e[1]))
    return b''.join(b'%s %s\0' % (m.encode(), n) + bytes.fromhex(o)
                    for m, n, o in ents)

def find_object(gitdir, prefix):
    """앞부분(4글자 이상)으로 찾는다: 하나면 그 이름, 없으면 None.

    둘 이상이면 git 처럼 모호하다고 멈춘다. 4글자보다 짧으면 찾지
    않는다(git 의 최소 줄임 길이와 같다). O(느슨한 객체 수).
    """
    p = prefix.lower()
    if len(p) < 4 or any(c not in '0123456789abcdef' for c in p):
        return None
    ids = set(all_loose(gitdir)) | set(packed_objects(gitdir))
    if len(p) == 40:
        return p if p in ids else None
    hits = [o for o in ids if o.startswith(p)]
    if len(hits) > 1:
        raise GitError('error: short object ID %s is ambiguous'
                       % prefix)
    return hits[0] if hits else None
