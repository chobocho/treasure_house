시간·애니메이션·저장

18.2 Hz 짜리 시계로 게임을 만드는 법.
그리고 GF(2) 위의 다항식 나눗셈으로 세이브를 지키는 법

PIT 을 다시 프로그램하기

도스가 준 시계는 초당 18.2번. 게임에는 너무 느립니다.

8253/8254 타이머 칩은 입력 클럭 14.31818 MHz ÷ 12 = 1,193,181.818… Hz 를 분주값으로 나눠 인터럽트를 냅니다. 도스가 넣어 둔 기본 분주값이 65,536 이고, 그래서 18.2065 Hz 입니다.

채널 0 의 분주값을 바꾸면 주파수가 바뀐다

   19,886  → 60.0 Hz     부드러운 스크롤
    9,943  → 120.0 Hz    사운드 믹싱
   65,536  → 18.2065 Hz  도스 기본값
도스와 공존해야 합니다. 도스의 시계(40:6C 의 틱 카운터)와 디스크 타임아웃이 18.2 Hz 를 전제로 돕니다. 그래서 게임들은 빠른 인터럽트를 걸되, 누적 카운터가 18.2 Hz 몫을 넘길 때마다 원래 핸들러를 불러 주었습니다. 이것을 잊으면 게임 도중 시스템 시계가 느려집니다.
1,193,182 라고 반올림해 적지 마세요. 정확한 값은 1,193,181.8181… 입니다. 실용적으로는 차이가 없습니다 — 1초가 어긋나려면 76일을 연속으로 돌려야 합니다. 그래도 출처가 있는 값을 그대로 적는 편이 낫습니다. 반올림한 숫자가 문서를 건너다니면 어디서부터 근사였는지 아무도 모르게 됩니다.

고정 타임스텝

이 문서의 엔진은 한 틱을 18.2065 Hz 로 고정합니다. 프레임을 몇 장 그리든 게임 상태는 같습니다.

TICK_US = 54925        한 틱의 마이크로초

  65536 / 1,193,181.818…  =  0.0549254 초  =  54,925.4 µs
  → 54925 로 고정한다 (오차 0.0007%)

가변 타임스텝

dt = 지난 프레임 시간
pos += vel * dt

기계가 빠르면 dt 가 작아진다
→ 결과가 기계마다 다르다
→ 재현 불가, 리플레이 불가

고정 타임스텝 (이 문서)

while (누적 >= TICK_US) {
    tick();
    누적 -= TICK_US;
}
render();

→ 결과가 언제나 같다
→ 트레이스를 바이트로 비교 가능
이 결정 하나가 이 문서 전체를 가능하게 합니다. 고정 타임스텝이 아니면 세 언어의 트레이스를 비교할 수 없고, 그러면 이식이 맞는지 증명할 방법이 없습니다.

한 틱의 순서

  1. 입력을 적용하고 플레이어를 움직인다
  2. 몬스터를 갱신한다 — 추적·공격
  3. 플레이어의 공격·상호작용 명령을 처리한다
  4. 안개와 조명을 갱신한다
  5. 카메라를 따라가게 한다
  6. 틱 카운터를 늘린다
순서를 바꾸면 게임이 달라집니다. 예를 들어 몬스터를 플레이어보다 먼저 움직이면, 플레이어가 도망칠 때 몬스터가 한 틱 먼저 따라붙습니다. 눈에 띌 만큼 다릅니다. 그래서 순서를 명세에 박아 두었습니다.

몬스터 경로는 PATH_EVERY = 8 틱마다 다시 계산합니다. 매 틱 계산하면 여섯 마리 × 222틱 = 1,332번의 A* 입니다. 8틱마다면 167번.

tick_n % PATH_EVERY == 0 을 쓰므로 모든 몬스터가 같은 틱에 동시에 경로를 다시 계산합니다. 몬스터마다 다른 위상을 주면((tick_n + eid) % 8) 부하가 분산되지만, 이 규모에서는 차이가 없어 단순한 쪽을 택했습니다.

애니메이션 — 틱에서 프레임 번호로

대상식주기
플레이어 걸음(anim / 4) % 24번 움직일 때마다
몬스터(tick / 6 + eid) % 26틱 = 0.33초
물결 (팔레트)tick / 44틱 = 0.22초

플레이어는 tick 이 아니라 anim 으로 셉니다. anim 은 실제로 움직인 틱에만 늘어나므로, 서 있을 때 다리가 움직이지 않습니다.

몬스터에 eid 를 더한 것은 여섯 마리가 동시에 같은 자세를 취하지 않게 하려는 것입니다. 한 줄로 군무를 막습니다.

팔레트 사이클링은 프레임버퍼를 건드리지 않으므로 render() 밖에 있습니다. 그래서 "같은 상태를 두 번 그리면 같은 인덱스가 나오는데 PPM 색은 다르다"는 테스트가 성립합니다.

CRC — GF(2) 위의 다항식 나눗셈

세이브 파일이 손상됐는지 어떻게 아는가. 답은 나머지 연산인데, 보통의 나눗셈이 아닙니다.

바이트열을 GF(2) 계수 다항식으로 봅니다. 비트 b₀b₁b₂… 는 b₀xⁿ + b₁xⁿ⁻¹ + …. 계수가 0 또는 1 이고, 덧셈이 배타적 논리합입니다(1+1 = 0).

GF(2) 에서는 뺄셈이 곧 덧셈이고, 둘 다 xor 다.
자리 올림이 없다. 그래서 하드웨어에서 시프트 레지스터 하나면 끝난다.

CRC 는 메시지 다항식을 생성 다항식으로 나눈 나머지입니다. CCITT-FALSE 의 생성 다항식은

0x1021  =  x¹⁶ + x¹² + x⁵ + 1

최고차항 x¹⁶ 은 암묵적입니다(16비트 레지스터에 안 들어가므로).

왜 이 다항식인가 — 생성 다항식의 선택이 검출 능력을 정합니다. 이 다항식은 모든 1비트·2비트 오류, 모든 홀수 개 오류, 16비트 이내의 모든 버스트 오류를 검출합니다.

표 구동 CRC

비트 단위로 돌리면 바이트당 8번의 시프트와 조건 xor 입니다. 바이트 단위로 미리 접어 두면 표 조회 한 번이 됩니다.

(c×256) mod 65536 은 하위 바이트가 0 이므로 16비트 xor 가 필요 없습니다. 상위 바이트만 8비트로 xor 하면 됩니다. 그래서 xor16 대신 xor8 을 씁니다.

구현바이트당 연산890바이트 세이브
비트 루프 + xor1616×2 비트 연산약 28,000 루프
표 + xor8 (니블 표)표 조회 3번약 2,700 조회
매 틱 세이브를 만들어 CRC 를 트레이스에 싣기 때문에 이 비용이 그대로 드러납니다. 5부의 xor8 과 11부의 원형 시야, 둘을 합쳐 틱 시간이 한 자릿수 배 줄었습니다.

crc16("123456789") == 0x29B1 은 CRC 카탈로그가 정의하는 공식 검증값입니다. 이 한 줄이 맞으면 다항식·초기값·반전 여부가 전부 맞다는 뜻입니다.

테스트는 여기에 더해 "ISORPG-SAVE" 의 88가지 1비트 변형이 전부 다른 CRC 를 내는지 확인합니다.

함정 — 자기 자신을 포함해 CRC 하면 0 이 나온다

트레이스에 세이브의 CRC 를 싣고 싶었습니다. 그런데 처음에 이렇게 썼습니다.

crc = crc16(pack_state(g))          ← 언제나 0 이 나온다

pack_state 는 끝에 이미 CRC 두 바이트를 붙여 놓습니다. CRC 를 포함해 다시 CRC 를 돌리면 수학적으로 반드시 0 이 나옵니다 — 나머지를 뺀 다항식은 생성 다항식으로 나누어떨어지니까요.

M(x) 의 나머지가 R(x) 라면,  M(x)·x^16 + R(x) 는 나누어떨어진다
→ 그 CRC 는 0
이 성질은 유용합니다. 수신 측이 "받은 것 전체의 CRC 가 0 인가"만 보면 되니까요. 실제 통신 프로토콜이 그렇게 씁니다. 그런데 값으로는 쓸모가 없습니다. 그래서 이 문서는 pack_state 가 붙여 둔 마지막 두 바이트를 그대로 읽습니다.

CCITT-FALSE 는 xorout 이 0 이라 이 성질이 그대로 나타납니다. xorout 이 0xFFFF 인 변종에서는 0 대신 다른 고정값이 나옵니다.

전부 빅 엔디언입니다. 리틀 엔디언을 쓰면 언어마다 바이트 순서 함수가 달라 같은 세이브를 만들었는지 확인하기 번거로워집니다. 손으로 시프트하면 어디서든 같습니다.

그리고 골든 시나리오 자체가 save → 진행 → load → 다시 진행 을 포함합니다. 트레이스 233줄 중 뒷부분이 되돌린 뒤 다시 진행한 몫입니다. 세 언어가 이 233줄을 바이트 단위로 똑같이 냅니다.

트레이스 형식 — 정수만

{"t":45,"px":1605632,"py":1671177,"ph":2,"hp":60,"lv":1,"xp":0,
 "rng":3137477811,"cam":[-225,308],"seen":357,"vis":156,"mon":6,"crc":17492}

(실제 출력은 한 줄입니다.) 위는 golden/trace.jsonl 의 45번째 틱을 그대로 옮긴 것입니다. 키 순서와 공백 없음까지 명세입니다.

부동소수점을 한 개도 싣지 않습니다. 실수를 문자열로 바꾸는 규칙이 언어마다 다르기 때문입니다. 0.1 이 파이썬에서는 0.1, 자바스크립트에서도 0.1 이지만 루아 5.1 에서는 0.1 또는 1e-01 일 수 있습니다. 정수만 실으면 그 문제가 아예 없습니다.

테스트는 트레이스의 모든 숫자 토큰이 정수 정규식에 맞는지 확인합니다. 실수 표기가 하나라도 섞이면 잡힙니다.

루아 이식에서 실제로 걸린 부분이 있습니다 — CORDIC 의 1사분면 결과가 -0 이 될 수 있는데, tostring(-0) 은 "-0" 이고 string.format("%d", -0) 은 "0" 입니다. 그래서 루아 이식은 어디서든 %d 를 씁니다.
