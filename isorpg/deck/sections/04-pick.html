4부

픽셀에서 타일로

마우스가 짚은 픽셀은 어느 타일인가.
대수적으로 푸는 길과, 도스가 실제로 쓴 표 조회

문제

투영은 쉽습니다. 곱셈 두 번이면 끝나니까요. 어려운 것은 그 반대입니다 — 화면 픽셀 하나가 주어졌을 때 그 픽셀을 품은 마름모를 찾는 것.

직사각 격자였다면 floor(px/W), floor(py/H) 로 끝났을 겁니다. 마름모는 서로 맞물려 있어서 그렇게 되지 않습니다. 한 픽셀 열에 두 타일이 걸치고, 한 픽셀 행에도 두 타일이 걸칩니다.

이것이 진짜 문제였습니다 — 도스 시절 쿼터뷰 게임의 조작은 대부분 마우스였고, 클릭 한 번마다 이 계산이 돌아야 했습니다. 그리고 나눗셈은 수십 사이클이었던 반면 시프트는 몇 사이클이었습니다. 정확한 사이클 수는 CPU 세대마다 다르고 이 문서에서는 확인하지 못했으므로 숫자를 적지 않습니다.

착상 — 좌표를 갈아타면 마름모가 정사각형이 된다

3부에서 마름모는 |u| + 2|v| ≤ 16 이라는 L1 공이었습니다. L1 공은 좌표를 45° 돌리면 L∞ 공, 즉 정사각형이 됩니다.

a = px + 2·py
b = 2·py - px

이 변환의 야코비 행렬식은 1·2 - 2·(-1) = 4 ≠ 0 이라 가역입니다. 그리고 타일 (tx, ty) 의 중심 (16(tx-ty), 8(tx+ty)+8) 을 넣어 보면

a_c = 32·tx + 16
b_c = 32·ty + 16

타일 중심들이 (a, b) 공간에서 간격 32의 정사각 격자 위에 놓입니다. 마름모 하나가 변 32짜리 정사각형이 되는 것이죠.

그러면 답은 자명합니다. tx = ⌊a/32⌋, ty = ⌊b/32⌋.

정리 3.2 — 대수적 역투영

정리. 화면 픽셀 (px, py) 를 품는 타일은 정확히 하나이고,

tx = floordiv(px + 2·py, 32)
ty = floordiv(2·py - px, 32)

증명. a = px + 2py, b = 2py - px 로 두면 가역 선형변환입니다. 타일 중심에서 a_c = 32tx + 16, b_c = 32ty + 16 입니다.

중심 기준 상대 좌표 u = px - cx, v = py - cy 에 대해 마름모 내부 조건은 |u| + 2|v| ≤ 16 입니다. A = u + 2v, B = 2v - u 로 두면 u = (A-B)/2, 2v = (A+B)/2 이므로

|u| + |2v| = |A-B|/2 + |A+B|/2 = max(|A|, |B|)

(마지막 등식은 |p|+|q| = max(|p+q|, |p-q|) 의 다른 표기입니다.) 따라서 내부 조건은 max(|A|, |B|) ≤ 16 이고, A = a - a_c, B = b - b_c 이므로

타일 (tx,ty) = { (a,b) : 32tx ≤ a ≤ 32tx+32,  32ty ≤ b ≤ 32ty+32 }

변 32짜리 정사각형들이 격자를 이뤄 평면을 덮습니다. 반개구간으로 자르면 내림 나눗셈이 정확히 하나를 줍니다. ∎

경계 픽셀은 a, b 가 큰 쪽 타일이 가져갑니다. 겹침도 빈틈도 없습니다 — 뒤에서 64,000 픽셀 전수로 확인합니다.

코드는 두 줄이다

나눗셈 두 번. 곱셈은 2·py 하나인데 그것도 시프트입니다.

여기서 floordiv 를 쓰는 것이 중요합니다. C 의 / 는 0 방향 절단이라 음수에서 답이 틀립니다.

0 방향 절단 (C, 자바)
-1 / 32 = 0       ← 틀렸다
-33 / 32 = -1     ← 틀렸다

카메라가 원점 왼쪽으로 가면
타일 인덱스가 0 근처에서 두 번 나온다
내림 (파이썬 //, math.floor)
floordiv(-1, 32) = -1
floordiv(-33, 32) = -2

경계가 균일하게 이어진다
이 버그는 조용합니다 — 맵 안쪽에서는 절대 나타나지 않고, 카메라가 맵 왼쪽 위 바깥으로 나갈 때만 타일 하나가 두 번 선택됩니다. 그래서 테스트에 반드시 음수 픽셀을 넣어야 합니다.

믿지 말고 세어 보기

두 줄짜리 식이 정말 마름모를 나타내는지, 마름모 정의로 직접 찾은 결과와 비교합니다.

후보 25개를 훑으며 |u| + 2|v| ≤ 16 을 만족하는 것을 찾습니다. 경계에서는 여러 타일이 조건을 만족하므로, floor 규칙과 같은 것을 고르려면 a, b 가 큰 쪽을 택해야 합니다.

마지막 줄이 핵심입니다. 스무 개 전부 두 방법이 같은 답을 냈습니다. 테스트는 129×81 = 10,449 픽셀에 대해 같은 비교를 합니다.

도스는 다르게 했다 — 사각형 + 모서리 마스크

나눗셈 두 번도 아까웠습니다. 도스 게임들은 512바이트짜리 표를 들고 다녔습니다.

화면을 32×16 사각형으로 나눕니다. px = 32·rc + ox, py = 16·rr + oy 로 쓰면 정리 3.2 의 식은

tx = (rc + rr) + floordiv(ox + 2·oy, 32)
ty = (rr - rc) + floordiv(2·oy - ox, 32)

가 됩니다. 그런데 ox ∈ [0,32), oy ∈ [0,16) 이므로

ox + 2·oy  ∈ [0, 61]    →  A = floordiv(..., 32) ∈ {0, 1}
2·oy - ox  ∈ [-31, 30]  →  B = floordiv(..., 32) ∈ {-1, 0}

네 가지 경우뿐입니다. 사각형 안의 위치가 어느 경우인지만 알면 되고, 그것은 32×16 = 512칸짜리 표에 미리 적어 둘 수 있습니다.

이것이 도스 시절 "코너 마스크" 또는 "픽 마스크"의 정체입니다. 나눗셈 두 번이 표 조회 한 번이 됩니다.

마스크의 모양

두 직선 ox + 2oy = 32(기울기 -1/2)와 2oy - ox = 0(기울기 +1/2)이 사각형 중심 (16, 8) 에서 만나 넷으로 자릅니다.

영역AB마스크 값타일
왼쪽001(rc+rr, rr-rc)
위0-10(rc+rr, rr-rc-1)
아래103(rc+rr+1, rr-rc)
오른쪽1-12(rc+rr+1, rr-rc-1)

네 조각의 넓이는 각각 512/4 = 128 픽셀 — 마름모 넓이 256 의 절반입니다. 사각형 하나에 마름모 두 개 몫이 들어간다는 계산과 정확히 맞습니다.

마름모 하나가 사각형 두 개에 걸쳐 있습니다. 그래서 사각형 넷으로 나눈 조각이 반쪽짜리인 것이죠.

표 만들기와 쓰기

도스 게임은 이 표를 파일로 들고 다녔습니다. 우리는 시작할 때 만듭니다 — 왜 네 값뿐인지가 코드에 남아야 하기 때문입니다. 상수 배열로 박아 두면 그 이유가 사라집니다.

마스크 값을 2A + (B+1) 로 인코딩한 것은 0..3 에 담기 위해서입니다. 두 비트면 충분하니 도스 시절에는 네 칸을 한 바이트에 넣어 128바이트로 줄이기도 했습니다.

표 자체

열여섯 줄, 서른두 글자. 계단이 가로 2칸에 세로 1칸씩 지는 것이 보입니다 — 2:1 기울기가 표에 그대로 새겨져 있습니다.

값 분포가 136/136/120/120 으로 정확히 128씩은 아닙니다. 경계 픽셀 소유권이 floor 규칙에 따라 한쪽으로 쏠리기 때문입니다. 합은 정확히 512 입니다.

전수 확인 — 카메라 오프셋 다섯 개(양수·음수·큰 값)에 대해 화면 64,000 픽셀 전부에서 두 방법이 일치했습니다. 총 320,000 픽셀, 불일치 0.

그런데 표가 더 느리다

도스에서는 표 조회가 나눗셈보다 압도적으로 빨랐습니다. 지금은 아닙니다.

파이썬에서 마스크 방식이 대수적 방식보다 약 1.6배 느립니다(854 µs 대 530 µs). 이유는 셋입니다.

  1. 나눗셈이 싸졌다 — 현대 CPU 의 정수 나눗셈은 20~40 사이클이고, 컴파일러는 상수 나눗셈을 곱셈과 시프트로 바꿔 버립니다. 32 로 나누는 것은 시프트 한 번입니다.
  2. 메모리가 비싸졌다 — 512바이트 표는 L1 캐시에 들어가지만, 캐시 히트도 4~5 사이클입니다. 시프트는 1 사이클입니다.
  3. 인터프리터 오버헤드 — 파이썬·루아·자바스크립트에서는 배열 인덱싱 자체가 함수 호출급 비용입니다.
"룩업 표가 빠르다"는 통념은 유효기간이 있었습니다. 그런데 그 유효기간이 언어마다 다릅니다 — 파이썬과 LuaJIT 에서는 대수적 방식이 빠르고, node 에서는 마스크가 여전히 빠릅니다. 17부에서 세 언어의 실측을 나란히 놓고 다시 봅니다.

타일 하나가 정확히 256픽셀인가

이론상 마름모 넓이는 256 입니다. 실제로 세어 봅시다.

화면 영역 [-160, 160) × [0, 160) 의 모든 픽셀을
screen_to_tile 로 분류해 타일마다 개수를 센다.
영역에 마름모가 통째로 들어오는 타일만 골라 보면 —

    전부 256픽셀.

가장자리 타일은 잘려서 적게 나오므로 제외합니다. 안쪽 타일이 모두 정확히 256 이라는 것은 겹침도 빈틈도 없다는 뜻입니다.

행 yx 범위폭
016 ~ 161
114 ~ 185
48 ~ 2417
72 ~ 3029
81 ~ 3131
93 ~ 2927
1515 ~ 173

폭이 1, 5, 9, …, 29, 31, 27, …, 3 으로 갑니다. 합이 정확히 256 입니다. 가운데 행이 33 이 아니라 31 인 것은, 양 끝 픽셀 x=0 과 x=32 가 이웃 타일 몫이기 때문입니다.

스프라이트도 이 모양이어야 합니다. 손으로 그린 예쁜 마름모를 쓰면 그리는 모양과 고르는 모양이 한 픽셀씩 어긋납니다. 이 문서의 지형 스프라이트는 screen_to_tile 규칙에서 그대로 뽑아 만듭니다.

확인 문제

픽셀 (-17, 8) 은 어느 타일인가? 그리고 C 의 / 를 썼다면 어떤 답이 나왔을까?

a = -17 + 16 = -1 → tx = ⌊-1/32⌋ = -1
b = 16 + 17 = 33 → ty = ⌊33/32⌋ = 1
답은 (-1, 1).

C 의 / 로는 -1/32 = 0 이 되어 (0, 1) 이 나옵니다. 타일 (0,1) 은 화면 오른쪽에 있는 다른 타일입니다. 카메라가 맵 왼쪽 바깥에 있을 때만 나타나는 버그라 눈에 잘 띄지 않습니다.
