7부

그리기 순서

뒤에 있는 것부터 그린다 — 그런데 '뒤'가 부분순서일 뿐이고,
그 부분순서에는 순환이 생긴다

화가 알고리즘

z 버퍼가 없던 시절의 답은 단순했습니다. 뒤에 있는 것부터 순서대로 덮어 그린다. 화가가 배경부터 칠하듯이.

바닥 타일에 대해서는 이것이 완벽하게 작동합니다.

정리 6.1. 높이가 모두 0 이면 d = tx + ty 오름차순(같으면 tx 오름차순)이 올바른 화가 순서다.

증명. 4부에서 봤듯 마름모들은 평면을 빈틈없이, 겹치지 않게 덮습니다. 그러므로 높이 0 에서는 어떤 순서로 그려도 결과가 같고, 정렬이 아예 필요 없습니다. ∎

그런데 순서가 왜 중요한가 — 마름모 위에 얹히는 것들(캐릭터·나무·기둥 옆면) 때문입니다. 그것들은 자기 타일의 마름모 밖으로 삐져나가므로, 뒤쪽 타일을 먼저 그려야 앞쪽 타일이 덮습니다. d 가 큰 타일은 화면 y 좌표 8(tx+ty) 가 크므로 아래에 있고, 아래에 있는 것이 앞입니다. 그래서 d 오름차순이면 됩니다.
정렬이 필요 없습니다. 이중 반복문의 순서만 맞추면 됩니다. for d in ...: for tx in ...: 이면 끝. 이것이 도스 시절 바닥 렌더링이 그렇게 빨랐던 이유입니다.

그런데 물체가 들어오면 깨진다

바닥은 1×1 이고 평평합니다. 물체는 그렇지 않습니다.

깨지는 경우 1 — 여러 칸을 차지

가로 4칸짜리 성벽은 tx+ty 하나로 대표할 수 없습니다. 어느 칸을 기준으로 삼든 다른 칸에서 틀립니다.

깨지는 경우 2 — 높이

높이 3 인 절벽 위의 캐릭터와, 그 앞 낮은 땅의 나무. 타일 좌표로는 캐릭터가 뒤인데 화면에서는 캐릭터가 아래에 그려집니다.

그래서 정렬 대상을 축 정렬 상자로 일반화합니다. 타일 단위 반개구간 [x0,x1) × [y0,y1) 과 높이 반개구간 [z0,z1).

1×1 물체:   x1 = x0+1,  y1 = y0+1
캐릭터:     높이 3칸짜리 상자 (z1 = z0+3)
지형 기둥:  [0, h+1) 만큼의 높이
이 문서의 렌더러는 지형 기둥까지 같은 통에 넣어 정렬합니다. 지형을 빼고 물체끼리만 정렬하면 절벽 뒤에 선 캐릭터가 절벽 위로 떠 보입니다 — 도스 시절 게임들이 실제로 겪던 문제입니다.

'뒤에 있다' 관계

셋 중 하나만 성립해도 참입니다. 세 축 중 하나에서 완전히 뒤에 있으면 뒤라는 뜻이죠.

조건뜻
A.x1 ≤ B.x0A 가 x 축으로 완전히 뒤 (화면 왼쪽-위)
A.y1 ≤ B.y0A 가 y 축으로 완전히 뒤 (화면 오른쪽-위)
A.z1 ≤ B.z0A 가 B 보다 완전히 아래 (더 낮음)

이 느슨함이 화면에서는 대개 옳습니다. 그런데 반대칭이 아닙니다.

A.x1 ≤ B.x0 이면서 B.y1 ≤ A.y0 이면 behind(A,B) 와 behind(B,A) 가 둘 다 참입니다. 이것을 그냥 비교 함수로 써서 정렬을 돌리면, 언어에 따라 예외가 나거나(파이썬의 sorted 는 아니지만 C++ std::sort 는 UB) 조용히 엉뚱한 순서가 나옵니다.

보조정리 6.2 — x/y 상호는 겹칠 수 없다

다행히 A.x1 ≤ B.x0 과 B.y1 ≤ A.y0 이 동시에 성립하면, 두 상자의 화면 경계상자가 절대 겹치지 않습니다.

증명. A.x1 ≤ B.x0 이고 B.y1 ≤ A.y0 라 하자. 그러면

A.x1 - A.y0  ≤  B.x0 - B.y1

양변에 16을 곱하면 좌변은 A 의 화면 x 최대값, 우변은 B 의 화면 x 최소값입니다(투영식 sx = 16(x-y)). 따라서 A.maxsx ≤ B.minsx — 겹치지 않습니다. ∎

겹치지 않으면 그리는 순서가 화면에 영향을 주지 않습니다. 그러므로 간선을 걸지 않아도 됩니다. 그래서 이 엔진은 화면 경계상자가 겹치는 쌍에만 간선을 만듭니다.

그럼 남는 상호 관계는 x-z 나 y-z 조합뿐입니다. 예를 들어 A 가 x 로는 뒤인데 z 로는 B 가 뒤인 경우. 이때는 어느 쪽도 명백하지 않으므로 간선을 걸지 않고 깊이 키로 정합니다.

5번 mutual 이 그 경우입니다 — 겹침쌍 1, 상호쌍 1. 6번은 겹침쌍 3 에 순환 절단 1.

3-순환이 실제로 존재한다

둘 사이의 순환은 보조정리로 막았습니다. 그런데 셋이 돌아가는 순환은 막을 수 없습니다.

A = [3,6) × [1,4) × [1,3)
B = [2,5) × [4,6) × [0,2)
C = [2,3) × [3,5) × [2,4)

behind(A,B):  A.y1 = 4 ≤ B.y0 = 4   ✓   (y 조건)
behind(B,C):  B.z1 = 2 ≤ C.z0 = 2   ✓   (z 조건)
behind(C,A):  C.x1 = 3 ≤ A.x0 = 3   ✓   (x 조건)

세 반대 방향은 전부 거짓. 셋의 화면 경계상자는 서로 겹친다.

정확히 한 방향씩만 성립해 순환이 닫힙니다. 이 배치를 올바르게 그릴 방법은 없습니다. 어떤 순서로 그려도 하나는 틀립니다.

실제 게임에서 이런 배치가 나오는가 — 나옵니다. L자로 꺾인 성벽, 계단 옆의 기둥, 다리 아래를 지나는 캐릭터. Ultima VIII 과 Crusader 의 유명한 렌더링 결함들이 대부분 이 문제입니다.
해결책은 두 가지뿐입니다. (1) 상자를 잘라 순환을 없앤다. (2) 순환을 감지하고 임의로 하나를 골라 끊는다. 이 엔진은 (2) 를 씁니다 — 잘라 내면 상자 개수가 늘어 정렬이 더 느려지고, 잘린 조각의 스프라이트를 다시 만들어야 하기 때문입니다.

위상 정렬

'뒤에 있다' 관계를 방향 그래프로 보면, 그리는 순서는 위상 정렬입니다.

id 가 마지막에 들어가는 것이 중요합니다. 그러면 키에 동점이 없고, 어떤 우선순위 큐 구현을 써도 결과가 같습니다. 세 언어가 각자의 힙을 써도 되는 이유입니다.

단계하는 일복잡도
경계상자상자마다 여덟 꼭짓점 투영O(n)
간선화면 x 로 훑으며 겹치는 쌍만O(n log n + k)
정렬칸 알고리즘 + 이진 힙O((V+E) log V)
순환 절단남은 것 중 깊이 키 최소절단마다 O(n)

간선 만들기가 병목이다

한 화면의 상자는 카메라에 따라 1,700~2,100개입니다(지형 기둥까지 넣으므로). 모든 쌍을 보면 200만 번이 넘습니다.

해법은 화면 x 로 훑는 쓸어내기입니다. 상자를 경계상자의 왼쪽 끝으로 정렬해 두고, 각 상자에 대해 bj.minx < bi.maxx 인 동안만 앞으로 나아갑니다.

idx = 상자를 bbox.minx 로 정렬
for a in 0..n-1:
    i = idx[a]
    for b in a+1..n-1:
        j = idx[b]
        if bb[j].minx >= bb[i].maxx: break     ← 이후는 전부 오른쪽
        ...
비교 횟수파이썬 실측
모든 쌍2,206,050847 ms
x 쓸어내기99,63841 ms

상자 2,101개(틱 97의 카메라) 기준. 비교 횟수가 22분의 1로 줄고, 위상정렬까지 포함한 시간이 41 ms 입니다.

더 줄이려면 화면을 격자로 나눠 같은 칸의 상자끼리만 보면 됩니다. 그런데 격자 관리 비용이 붙고, 이 규모에서는 쓸어내기가 충분히 빠릅니다. 루아와 타입스크립트에서는 한 프레임 전체가 11~12 ms입니다(17부).
화면에 무엇이 있느냐에 따라 상자 수가 크게 달라집니다 — 마을 안에서는 2,100개, 탁 트인 들판에서는 1,700개쯤입니다. 그래서 프레임 시간도 두 배 가까이 출렁입니다. out/bench.txt 의 render frame 은 시작 위치의 카메라에서 잰 값입니다.

여섯 가지 사례

골든 벡터에 손으로 짠 배치 여섯 개가 들어 있습니다. 세 언어가 전부 같은 순서를 내야 합니다.

번호이름무엇을 시험하는가기대

2depth-xx 로 앞뒤가 갈리는 둘0 1, 절단 0

4번이 실전 배치입니다. 성벽은 0번 상자인데도 2번 캐릭터가 먼저 나옵니다 — 그 캐릭터가 성벽보다 뒤에 있기 때문입니다.

테스트는 여기에 더해 무작위 상자 60,000쌍을 만들어 보조정리 6.2 의 반례가 있는지 확인합니다. x/y 상호 사례가 8,152건 생성됐고 반례는 0 이었습니다.

렌더 순서 전체

한 프레임에 정렬 대상이 무엇인지 봅시다.

지형 기둥이 [0, h+1) 인 것에 주의하세요. 높이 0 인 평지도 [0,1) 짜리 상자를 가집니다. 그래야 그 위에 선 캐릭터([h, h+3))와 z 조건으로 순서가 잡힙니다.

장식(나무·바위)의 배치는 좌표만으로 정합니다 — (tx·7 + ty·13) % 5 == 0. 난수를 쓰지 않는 이유는 결정적이어야 하기 때문입니다. 난수를 쓰면 렌더가 게임 상태를 바꾸게 되고, 그러면 프레임을 몇 장 그렸느냐에 따라 게임이 달라집니다.

렌더는 상태를 바꾸면 안 된다 — 이 원칙을 어기면 파리티 검증이 불가능해집니다. 테스트가 "같은 상태를 두 번 그리면 같은 그림"을 확인하는 이유입니다.

그런데 반투명에서는 지금도 같은 문제가 남습니다. 알파 블렌딩은 순서에 의존하므로 반투명 물체는 여전히 뒤에서 앞으로 정렬해야 하고, 그 정렬은 여전히 부분순서이며, 여전히 순환이 생깁니다. 1994년의 문제가 2026년에도 그대로 있습니다.

확인 문제

상자 A 가 [0,2)×[0,2)×[0,1), B 가 [1,3)×[1,3)×[0,1) 이다. behind(A,B) 는?

A.x1 = 2 ≤ B.x0 = 1? 아니오.
A.y1 = 2 ≤ B.y0 = 1? 아니오.
A.z1 = 1 ≤ B.z0 = 0? 아니오.
→ 거짓. 반대도 마찬가지로 거짓입니다.

두 상자가 겹쳐 있어서 어느 쪽도 명백히 뒤가 아닙니다. 간선이 없으므로 깊이 키로 정해집니다: A: (0+0, 0, id), B: (1+1, 0, id) → A 가 먼저.

실전에서 상자가 겹치는 것은 대개 버그입니다. 두 물체가 같은 공간을 차지하고 있다는 뜻이니까요. 렌더러는 그래도 결정적인 답을 내야 합니다.
