고정소수점

정수 x 가 실수 x / 65536 을 뜻한다고 약속합니다. 덧셈은 그냥 덧셈, 곱셈은 정수 곱셈 하나와 시프트 하나.

16.16 형식      정수부 16비트 . 소수부 16비트

  1.0    = 65536
  0.5    = 32768
  0.2    = 13107   ← 이 엔진의 SPEED
  1/√2   = 46341
  -1.0   = -65536
 최소 단위 = 1/65536 ≈ 0.0000153
DOOM 도 16.16 이었습니다 — m_fixed.h 의 FRACBITS 16. 90년대 3D·의사3D 엔진의 사실상 표준이었습니다.

표현과 변환

주의할 곳은 음수입니다. fp_floor(-1) 은 -1 입니다. 실수 -1/65536 을 내림하면 -1 이니까요. 0 이 아닙니다.

이 다섯 값이 fp_floor(65536), fp_floor(-1), fp_floor(-65536), fp_floor(-65537), fp_floor(131071) 입니다. -65536 은 정확히 -1.0 이라 -1 이고, -65537 은 그보다 조금 작아 -2 입니다.

C 로 옮길 때 가장 흔한 버그 — x >> 16 은 부호 있는 정수에서 산술 시프트라 내림이 맞지만, x / 65536 은 0 방향 절단이라 음수에서 틀립니다. 두 표기가 양수에서만 같습니다.

정리 2.1 — 곱셈이 넘치지 않게 하는 법

여기가 이 문서에서 가장 실용적인 정리입니다.

16.16 곱셈은 floor(a·b / 65536) 입니다. 그런데 a 와 b 가 각각 231 근처면 곱이 262 까지 커집니다. C 에서는 64비트 정수로 받으면 되지만—

루아 5.1 과 자바스크립트에는 64비트 정수가 없습니다. 수는 배정밀도 실수 하나뿐이고, 가수가 53비트입니다. 262 는 조용히 반올림됩니다. 오류도 경고도 없이 틀린 값이 나옵니다.

정리 2.1. a = ah·2¹⁶ + al (0 ≤ al < 2¹⁶) 로 쪼개면

floor(a·b / 2^16) = ah·b + floor(al·b / 2^16)

이고, |a| < 2³¹, |b| < 2³⁷ 이면 모든 중간값이 253 미만이다.

증명. a·b = ah·b·2¹⁶ + al·b. 양변을 216 으로 나눠 내림하면 ah·b 가 정수이므로 그대로 빠져나옵니다. 중간값은 |ah| < 2¹⁵ 이라 |ah·b| < 2⁵², al < 2¹⁶ 이라 |al·b| < 2⁵³. ∎

파이썬만 있었다면 이 정리는 필요 없었습니다. 파이썬 정수는 자릿수 제한이 없으니까요. 이식이 검증 수단이라는 말은 이런 뜻입니다 — 다른 언어로 옮겨 보지 않으면 암묵적으로 기대고 있던 것이 무엇인지 알 수 없습니다.

분할 곱이 정말 같은가

테스트는 경계값 14개와 무작위 4,000쌍에 대해 fp_mul(a,b) == (a*b)//65536 을 확인합니다. 파이썬의 큰 정수 곱과 대조하는 것이므로, 분할이 틀리면 즉시 잡힙니다.

내림인가 반올림인가

fp_mul 은 내림입니다. 곱할 때마다 평균 0.5 LSB 씩 아래로 치우칩니다. 곱셈을 연달아 하면 그 편향이 쌓입니다.

내림 곱을 n번 연달아 하면
   기대 오차 = -n/2 LSB = -n / 131072  (타일 단위)

이동에 쓰는 곱은 한 틱에 한 번이므로
   200틱 후 평균 -100/65536 ≈ -0.0015 타일 = -0.05 픽셀
             최악 -200/65536 ≈ -0.003  타일 = -0.10 픽셀

이동에서는 무시할 만합니다. 그런데 명암 계산에서는 다릅니다 — 색을 16단계로 나눌 때 매번 내림하면 전체가 어두워집니다. 그래서 반올림 곱을 따로 둡니다.

둘을 섞어 쓰지 않는 것이 중요합니다. 어느 자리에 어느 것을 쓰는지가 명세에 박혀 있어야 세 언어가 같은 값을 냅니다. 이 엔진은 fp_mulr 을 광원 감쇠에서만 씁니다.

나눗셈

먼저 65,536 을 곱해 소수부를 만들고 나눕니다. 순서가 반대면 소수부가 전부 날아갑니다.

범위 조건은 |a| < 2³⁷ 입니다. a·65536 < 2⁵³ 이어야 하니까요. 이 엔진의 모든 좌표는 |a| < 2²⁷ 이라 여유가 큽니다.

b = 0 은 검사하지 않습니다. 게임 코드에서 0 으로 나누는 자리가 없다는 것이 전제이고, 그 전제가 깨지면 예외가 나야 옳습니다. 방어 코드를 넣으면 버그가 숨습니다.

정리 2.2 — 정수 제곱근

거리 계산에 제곱근이 필요합니다. 실수 sqrt 없이 ⌊√n⌋ 을 구합니다.

정리 2.2. 이 반복은 ⌊√n⌋ 에서 멈추고, 수열 x 는 단조 감소한다.

증명 스케치. f(x) = (x + n/x)/2 는 산술-기하 평균 부등식에 의해 x ≥ √n 이면 f(x) ≥ √n 입니다. 그리고 x > √n 이면 f(x) < x 입니다. 정수 내림을 넣어도 이 성질이 유지되므로, 단조 감소하는 정수열은 반드시 멈춥니다. 멈춘 지점 x 는 x ≤ (x + ⌊n/x⌋)/2, 즉 x² ≤ n 을 만족하고, 직전 값이 x 보다 컸으므로 (x+1)² > n 입니다. ∎

math.isqrt 를 쓰지 않은 이유는 루아와 타입스크립트에 그런 함수가 없어서입니다. 세 언어가 같은 코드를 돌아야 결과가 같다는 것이 자명해집니다.
반복 횟수는 O(log n) 입니다. 뉴턴법 자체는 자릿수를 배로 늘리지만, 이 구현은 초기값을 n 그대로 잡습니다. 그래서 √n 근처까지 내려오는 동안 한 걸음에 대략 반씩만 줄어듭니다. 실측: 65,536 에서 10번, 106 에서 12번, 232−1 에서 20번, 243−1 에서 25번. 초기값을 비트 길이로 잡으면 다섯 번이면 끝나지만, 그러려면 비트 길이를 구하는 코드가 세 언어에 또 필요해집니다 — 여기서는 단순한 쪽을 골랐습니다.

제곱근을 아예 피하기 — 팔각 거리

거리를 비교만 하는 자리에서는 제곱근이 필요 없습니다. 그런데 "반경 안인가"를 넘어 실제 거리 값이 필요할 때가 있습니다(조명 감쇠).

도스 시절의 답은 알파 맥스 플러스 베타 민입니다.

√(dx² + dy²)  ≈  α·max(|dx|,|dy|) + β·min(|dx|,|dy|)

최소최대오차 최적:  α = 0.960434, β = 0.397825
1024배 해서 반올림:  α → 983,  β → 407

이름이 "팔각"인 것은, 이 근사의 등거리선이 원이 아니라 정팔각형이기 때문입니다.

실측 오차는 -4.1% ~ +3.9% 입니다. 문헌이 말하는 최적 계수의 최대 오차 3.96% 와 맞는 자리이고, 음수 쪽이 조금 더 큰 것은 계수를 1024배 해 정수로 반올림했기 때문입니다. 문헌값을 옮겨 적지 않고 우리 코드로 재서 싣습니다.

사인·코사인 — 표를 만들되 알고리즘으로

각도 단위는 brad(binary radian)입니다. 한 바퀴가 256. 그래야 각도 덧셈이 바이트 덧셈이 되고 모듈러가 공짜입니다.

표를 상수 배열로 박아 두면 세 언어가 같은 값을 갖는 것은 확실합니다. 그런데 그러면 이식이 맞는지 검사가 안 됩니다. 그래서 실행 시각에 정수 CORDIC 으로 만듭니다.

CORDIC — 회전을 arctan(2^-i) 단위로 쪼갠다

  각 단계에서 벡터를 ±arctan(2^-i) 만큼 돌린다
  그 회전은  x' = x - d·(y >> i),  y' = y + d·(x >> i)
  즉 시프트와 덧셈뿐. 곱셈이 없다.

  누적 배율 K = Π √(1 + 4^-i) 를 처음에 미리 나눠 둔다
ATAN_BRAD[0] = 32 × 65536 인 것에 주목하세요. 45도가 정확히 32 brad 라서 첫 항이 딱 떨어집니다. 그리고 Σ ATAN_BRAD / 65536 = 71.03 brad > 64 brad 이므로 1사분면 전체를 덮습니다 — 이것이 CORDIC 의 수렴 조건입니다.

가드 비트 8개가 오차를 5에서 1로 줄인다

CORDIC 안쪽에서 y >> i 를 할 때마다 내림이 일어납니다. 20번 반복하면 그 내림이 쌓입니다.

가드 없이 16회를 돌리면 sin(0) 이 2 로 나오고 45도에서 사인과 코사인이 1 차이 납니다. 대칭이 깨지는 것이죠. 가드 8비트에 20회를 돌리면 오차가 1 이 되고 대칭이 정확히 회복됩니다.

45도에서 46341 이 나오는 것이 인상적입니다. cos 45° = sin 45° = 1/√2 이고, 16.16 으로 round(65536/√2) = 46341. 그런데 이 수는 10부의 대각 이동 계수와 똑같은 수입니다. 같은 상수가 두 곳에서 독립적으로 나오는 것은 우연이 아닙니다 — 둘 다 "대각선 한 걸음의 길이"를 묻고 있으니까요.

표 검산

sum COS = 0, sum SIN = 0 이 나오는 것이 좋은 신호입니다. 한 주기를 더하면 0 이어야 하는데, 오차가 한쪽으로 쏠려 있으면 0 이 되지 않습니다.

max |sin² + cos² - 1| = 2/65536 — 피타고라스 항등식이 16.16 단위로 2 이내에서 성립합니다. 상대 오차로는 3×10-5 입니다.

테스트는 여기에 더해 모든 256개 항목이 round(65536·sin) 과 ±1 이내임을 확인합니다. 이 확인에서만 부동소수점을 씁니다 — 테스트는 엔진이 아니니까요.

비트 연산이 없는 언어에서 xor 하기

13부의 CRC 에는 배타적 논리합이 필요합니다. 그런데 루아 5.1 에는 비트 연산자가 없습니다. LuaJIT 의 bit 라이브러리는 있지만 LÖVE 환경까지 늘 보장되지는 않습니다.

한 비트씩 16번. O(16) 이고 표도 필요 없습니다. 테스트는 표본 67,072쌍(262 × 256)에 대해 ^ 와 같은지 확인합니다.

그런데 CRC 는 바이트마다 xor 를 두 번 합니다. 세이브 하나가 890바이트니 890 × 2 × 16 = 28,480 번의 루프. 매 틱마다 그러면 느립니다. 그래서 8비트 전용 버전을 따로 둡니다.

CRC 를 표 기반으로 바꾼 것과 시야 계산을 원 안으로 한정한 것, 둘을 합쳐 틱 시간이 한 자릿수 배 줄었습니다. 지금 실측값은 out/bench.txt 의 game tick 줄에 있습니다 — 17부에서 세 언어를 나란히 놓고 봅니다.

16.16 곱셈을 반복하면 얼마나 밀리는가

실수 계산과 16.16 내림 계산을 나란히 돌려 차이를 봅니다. 값이 1 에 가까울수록, 횟수가 많을수록 벌어집니다.

확인 문제

fp_mul(a, b) 를 b 쪽을 쪼개도록 바꾸면 범위 조건이 어떻게 달라지는가?

대칭이므로 |b| < 2³¹, |a| < 2³⁷ 이 됩니다. 즉 쪼개는 쪽의 범위가 더 좁아집니다(2³¹ 대 2³⁷).

그러므로 두 인자 중 작은 쪽을 쪼개야 합니다. 속도 × 방향계수 라면 방향계수가 작으니 방향계수를 쪼개는 자리에 두는 것이 안전합니다.

이 엔진은 a 쪽을 쪼갭니다. 실제로 쓰이는 값이 전부 |x| < 2²⁷ 이라 어느 쪽에 무엇을 두든 두 상계를 모두 만족하므로, 명세에 순서 규칙을 따로 두지 않았습니다. 상계에 가까운 값을 다루게 되면 그때는 규칙이 필요해집니다.
