스프라이트와 블릿

64,000바이트를 CPU 가 직접 채운다.
RLE·클리핑·명암표·더티 렉트·팔레트 사이클링

프레임버퍼

모드 13h 를 그대로 흉내 냅니다. 길이 64,000 짜리 바이트 배열 하나. 인덱스 y·320 + x.

언어자료형인덱스
파이썬bytearray(64000)0-기반
루아 5.1정수 테이블1-기반
타입스크립트Uint8Array(64000)0-기반

루아만 1-기반입니다. 그래서 좌표 계산은 세 언어가 완전히 같게 두고, 테이블을 짚는 순간에만 +1 을 붙입니다. 규칙을 그렇게 정해 두지 않으면 어디서 어긋났는지 찾을 수 없습니다.

색은 팔레트 인덱스입니다. 실제 RGB 는 프런트엔드가 정합니다. 이 분리 덕분에

  1. 팔레트만 돌려 물결 애니메이션을 공짜로 얻고
  2. 명암도 표 한 번 조회로 끝나며
  3. 세 언어의 결과를 바이트 단위로 비교할 수 있습니다

팔레트를 램프로 짜는 이유

이 문서의 팔레트는 VGA 기본 16색 + 램프 15개 × 16단계 = 256 입니다.

구간내용
0–15VGA 기본 16색 (0번은 투명으로도 씀)
16–31물 — 팔레트 사이클링 구간
32–47모래
48–63풀
…흙·바위·숲·길·바닥·벽·나무·눈·늪·용암·살색·옷

램프 안에서 어두운 끝과 밝은 끝을 균등 보간합니다. +7 은 +0.5 단계 반올림입니다(RAMP_LEN-1 = 15 이므로).

중복 색이 있으면 안 됩니다. 이 문서를 만들면서 두 번 걸렸습니다. 처음에는 눈 램프의 밝은 끝을 순백 (63,63,63) 으로 둬서 VGA 15번과 겹쳤고(LIGHT[15][191] 이 191 대신 15 를 가리킴), 나중에 길 램프 색을 고치다가 116번이 흙 램프의 71번과 같아졌습니다. 둘 다 최대 밝기에서도 다른 색으로 그려지는 증상입니다.

두 번째는 테스트가 빨간데도 make py 가 실패를 삼켜 한동안 보이지 않았습니다. 지금은 gen_palette.py 가 중복을 발견하면 스스로 멈춥니다.

명암표 — 16단계 × 256색

타일마다 밝기가 다릅니다. 그린 뒤에 색을 어둡게 하려면 픽셀마다 계산이 필요한데, 도스에서는 그럴 여유가 없었습니다.

답은 미리 만들어 둔 표입니다. LIGHT[단계][색] = 그 색을 그만큼 어둡게 한 것에 가장 가까운 팔레트 색.

항목값
표 크기16 × 256 = 4,096 바이트
만드는 비용16 × 256 × 256 = 1,048,576 번의 거리 계산
쓰는 비용픽셀마다 배열 조회 한 번
동점 처리인덱스가 작은 쪽

램프로 짠 팔레트가 여기서 값을 합니다. 어둡게 만든 색을 다시 찾을 때 대개 같은 램프 안에서 아래로 내려갑니다. 무작위 팔레트였다면 명암 단계마다 엉뚱한 색조로 튈 겁니다.

"대개"입니다. 아주 어두운 단계에서는 같은 램프의 바닥보다 다른 램프의 어두운 색이나 검정이 더 가까워집니다. 그것이 다음 슬라이드의 측정값이 선형보다 어두운 이유입니다.
15단계는 항등이어야 합니다 — LIGHT[15][c] == c. 어둡게 하지 않은 색은 자기 자신이 가장 가깝기 때문입니다. 테스트가 256개 전부 확인합니다.

밝기가 실제로 줄어드는가

테스트는 같은 타일을 세 단계로 그려 팔레트 값의 합을 잽니다.

같은 타일 밝기 합 — 15단계 19641, 8단계 9533, 2단계 1232

선형이라면 8단계에서 10,475, 2단계에서 2,619 여야 합니다. 실제로는 그보다 더 어둡습니다(9,533 과 1,232).

이유는 최근접 탐색의 결과입니다. 8단계에서는 풀 램프의 색 일부가 숲 램프로 넘어가고, 2단계에서는 지배적인 두 색이 아예 검정(0번)으로 떨어집니다. 램프의 어두운 끝이 0 이 아니라면 오히려 선형보다 밝아야 하는데, 실제로는 램프를 벗어나 버리는 쪽이 이깁니다.

프레임버퍼 인덱스의 합을 재면 안 됩니다. 처음에 그렇게 짰다가 세 단계가 전부 같은 값이 나왔습니다. 인덱스는 색의 이름일 뿐 밝기가 아닙니다. 팔레트를 통해 실제 RGB 를 봐야 합니다. 테스트 코드의 버그였고, 엔진은 멀쩡했습니다.

RLE 스프라이트

스프라이트의 상당 부분은 투명입니다. 마름모 32×16 의 512 픽셀 중 실제로 그리는 것은 256 개 — 정확히 절반이죠.

도스식 답은 런 렝스입니다. 같은 색이 이어지는 구간을 (개수, 색) 로 묶습니다.

golden/tiles.rle 의 첫 스프라이트 (tile_0, 물)

SPRITE 0 tile_0 32 16 16 0
16:0 1:27 15:0                        ← 0행: 투명 16, 색27 하나, 투명 15
14:0 1:24 1:25 1:22 1:25 1:24 13:0    ← 1행: 5픽셀짜리 띠
...

색 0 은 투명이라 약속했습니다. 그래서 색 0 인 런은 건너뛰기만 하면 됩니다 — 비교도 필요 없습니다.

런 합이 폭과 정확히 같은지 적재할 때 확인합니다. 이런 검사는 데이터가 손상됐을 때 조용히 이상한 그림이 나오는 것을 막습니다.

클리핑은 런 단위로

여기가 도스식 사고의 정수입니다. 픽셀마다 화면 안인지 검사하지 않습니다.

  1. 세로는 행 통째로 건너뜁니다. py < 0 or py ≥ 200 이면 continue.
  2. 가로는 런 하나를 [a, b) 로 자릅니다. a = max(px, 0), b = min(px+count, 320).
  3. 오른쪽 끝을 넘으면 그 행의 나머지 런은 볼 필요가 없습니다 — break.

그래서 화면 밖으로 크게 벗어난 스프라이트는 거의 공짜입니다. 세로로 벗어나면 행 검사 열여섯 번, 가로로 벗어나면 런 몇 개만 보고 끝납니다.

상황테스트결과
완전히 왼쪽 위 바깥blit(-1000,-1000)화면에 한 픽셀도 안 남음
완전히 오른쪽 아래 바깥blit(1000,1000)화면에 한 픽셀도 안 남음
안쪽blit(16, 0)정확히 256 픽셀
왼쪽으로 걸침blit(0, 0)0 < n < 256
아래로 걸침blit(16, 196)0 < n < 256
버퍼 크기가 변하지 않는지도 확인합니다 — 가로세로 각각 화면 밖까지 훑으며 len(fb) == 64000 을 검사합니다. 클리핑 버그의 전형적 증상이 배열 뒤에 원소가 붙는 것이니까요.

스프라이트를 그리는 코드가 스프라이트를 만든다

지형 마름모를 손으로 그리면 그리는 모양과 고르는 모양이 어긋납니다. 그래서 screen_to_tile 규칙에서 그대로 뽑아냅니다.

이 함수가 돌려주는 행별 x 범위가 4부에서 손으로 센 것(1, 5, 9, …, 31, 27, …, 3)과 정확히 같습니다. 합은 256.

큐브는 마름모에 옆면을 붙여 만듭니다.

왼쪽 면을 더 어둡게, 오른쪽 면을 조금 어둡게 칠합니다. 광원이 왼쪽 위에 있다고 보는 것이죠. 이 한 줄이 평평한 마름모를 입체로 보이게 만듭니다.

디더링 — 64단계로 그라데이션 만들기

VGA DAC 가 6비트라 한 램프에 쓸 수 있는 밝기가 64단계뿐입니다. 그중 16단계만 팔레트에 넣으니 계단이 보입니다.

도스식 답은 베이어 행렬입니다. 4×4 문턱값 표로 두 색을 섞습니다.

BAYER 4x4          지형마다 문턱을 다르게 준다

  0   8   2  10      물   문턱 8  → 절반씩
 12   4  14   6      풀   문턱 5  → 어두운 쪽이 많다
  3  11   1   9      바닥 문턱 3  → 거의 단색
 15   7  13   5      늪  문턱 10 → 밝은 쪽이 많다

모서리 처리도 있습니다. 위쪽 모서리는 한 단계 밝게, 아래쪽 모서리는 한 단계 어둡게. 마름모 하나가 평면이 아니라 면으로 보이게 하는 최소한의 장치입니다.

베이어 행렬을 쓰는 이유는 공간적으로 균일하기 때문입니다. 무작위 디더는 얼룩이 지고, 순서 디더는 줄무늬가 집니다. 베이어는 4×4 안에서 0..15 를 최대한 흩어 놓습니다.

팔레트 사이클링 — 공짜 애니메이션

프레임버퍼를 건드리지 않고 물결을 흐르게 하는 법.

비용은 0 입니다. 그리는 코드는 아무것도 하지 않고, DAC 레지스터 16개만 다시 쓰면 됩니다. 도스 시절 물·용암·폭포가 전부 이 방식이었습니다.

방식프레임당 비용메모리
스프라이트 애니메이션스프라이트 다시 그리기프레임 수 × 크기
팔레트 사이클링DAC 레지스터 16개0
테스트가 확인하는 것 — 사이클링을 해도 프레임버퍼의 인덱스는 하나도 바뀌지 않고, PPM 으로 뽑은 색은 바뀐다. 이 두 가지가 동시에 성립해야 진짜 팔레트 애니메이션입니다.

더티 렉트

화면 전체를 매 프레임 다시 올리면 64,000바이트를 옮겨야 합니다. 바뀐 곳만 올리면 훨씬 적습니다.

핵심은 언제 합칠 것인가입니다. 사각형 두 개를 합치면 갱신 호출이 하나 줄지만, 합친 결과가 지나치게 크면 오히려 손해입니다.

합친 넓이 × 2  ≤  (넓이1 + 넓이2) × 3

즉 낭비가 1.5배를 넘지 않을 때만 합친다
사례결과
겹치는 20×20 둘하나로 합쳐짐
화면 양 끝의 둘그대로 둘
화면 밖으로 걸친 것잘려서 들어옴
완전히 화면 밖버려짐
결과가 결정적이어야 합니다. 합치는 순서에 따라 결과가 달라지므로, 마지막에 (y, x) 로 정렬합니다. 그리고 table.sort 는 안정 정렬이 아니므로 비교자가 전순서여야 합니다 — 루아 이식에서 걸리는 부분입니다.

PPM 으로 뽑기 — 파리티의 근거

세 언어가 같은 그림을 그렸는지 확인하려면 파일로 뽑아 cmp 해야 합니다.

"P6\n320 200\n255\n"   15바이트
픽셀 320×200×3        192,000바이트
                      ─────────────
                      192,015바이트

6→8비트 확장은 v·4 + v/16 입니다. 1부에서 봤듯 0 은 0, 63 은 정확히 255 가 됩니다.

왜 PNG 가 아니라 PPM 인가 — PNG 는 압축 파라미터에 따라 같은 그림도 다른 바이트가 나옵니다. PPM 은 무압축이라 같은 그림이면 반드시 같은 바이트입니다. 파리티 검증에는 이쪽이 옳습니다. 문서에 실을 때만 PNG 로 바꿉니다.
