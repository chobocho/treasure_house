브라우저에서 같은 엔진 돌리기

이 문서 안에서 도는 미니 RPG 는 다시 만든 것이 아닙니다. 위에 실린 그 타입스크립트 엔진을 tsc 로 옮긴 결과를 그대로 묶어 넣은 것입니다.

엔진이 파일을 읽는 곳은 세 군데뿐입니다 — 팔레트, 스프라이트, 시나리오. 브라우저에는 파일이 없으니 그 셋을 문자열로 박아 넣고, 읽기 함수와 파싱 함수를 나눴습니다.

이 분리는 노드 쪽 동작을 하나도 바꾸지 않습니다. 파리티 검사가 그대로 통과하는 것이 그 증거입니다 — 리팩터링 뒤에도 208줄·233줄·192,015바이트가 전부 같습니다.

번들러 없이 묶기

덱은 자기완결형 파일 하나여야 하므로 번들러를 쓸 수 없습니다(그리고 쓰고 싶지도 않습니다). tsc 가 낸 CommonJS 모듈들을 스무 줄짜리 로더로 감싸 이어 붙입니다.

여기서 이름 충돌에 걸렸습니다. 엔진에도 path 라는 모듈이 있습니다(경로 탐색). 노드 내장 path 와 이름이 같죠. 상대 경로인지 아닌지를 구분하지 않으면 game.ts 가 경로 스텁을 경로탐색 모듈로 착각해 P.astar is not a function 으로 터집니다.

번들이 정말 같은 엔진인가

묶는 과정에서 무언가 어긋났을 수 있습니다. 확인 방법은 하나입니다 — 번들로 골든 트레이스를 다시 만들어 보는 것.

이 검사가 통과하면 이 문서 안에서 걸어 다니는 캐릭터의 좌표는 골든 트레이스를 만든 것과 같은 코드가 계산한 값입니다. 데모가 본문과 다른 이야기를 할 수 없습니다.

캔버스 프런트엔드

하는 일은 모드 13h 시절 VGA DAC 와 정확히 같습니다 — 인덱스를 RGB 로 바꾸는 것.

  1. 팔레트를 RGBA 룩업으로 미리 펴 둡니다. 픽셀마다 세 번 조회하는 것보다 쌉니다.
  2. 캔버스는 320×200 그대로 두고 확대는 CSS 로 합니다. 캔버스를 크게 잡고 그리면 픽셀마다 비용이 배로 듭니다.
  3. image-rendering: pixelated 로 보간을 끕니다. 켜 두면 도스 픽셀이 뭉갭니다.
  4. 배율은 정수만 씁니다. 1.5배로 늘리면 픽셀이 들쭉날쭉해집니다.
팔레트 사이클링은 위상이 바뀔 때만 룩업을 다시 만듭니다. 매 프레임 만들면 256×4 바이트를 초당 예순 번 쓰게 됩니다.
