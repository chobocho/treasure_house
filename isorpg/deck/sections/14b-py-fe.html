pygame 프런트엔드

엔진은 320×200 짜리 8비트 인덱스 배열만 만듭니다. 프런트엔드가 하는 일은 그것을 팔레트로 풀어 창에 올리는 것뿐입니다 — 모드 13h 시절 VGA DAC 가 하던 일과 정확히 같습니다.

pygame.Surface(depth=8) 를 만들고 set_palette() 로 팔레트를 넣은 뒤, 프레임버퍼를 get_buffer().write() 로 통째로 밀어 넣습니다. 픽셀 하나하나를 파이썬에서 만지지 않으므로 프레임당 비용이 거의 0 입니다.

numpy 를 쓰지 않았습니다. surfarray.pixels2d 가 더 편하지만 numpy 가 필요하고, 이 엔진의 "표준 라이브러리만" 약속이 깨집니다. 폭 320 이 4의 배수라 get_pitch() == 320 이고, 그래서 버퍼 전체 쓰기가 유효합니다 — 생성 시점에 확인합니다.

확대에서 걸린 것

pygame.transform.scale(src, size, dest) 로 8비트 서피스를 32비트 창에 바로 확대하려 하면

ValueError: Source and destination surfaces need to be compatible formats

가 납니다. 그래서 창 크기의 8비트 임시 서피스를 하나 캐시해 두고 거기로 확대한 뒤, 그것을 창에 블릿합니다. 8→32비트 변환이 블릿 안에서 C 로 한 번에 일어납니다.

HUD(체력 막대)도 프레임버퍼 안에 그립니다. pygame 폰트를 쓰면 8비트 세계 밖으로 나가고, 그러면 화면 캡처가 PPM 과 바이트 비교가 되지 않습니다. 캡처할 때는 HUD 를 끕니다.

헤드리스 캡처와 그 검증

이 문서에 실린 화면은 이 코드가 만든 진짜 프레임버퍼입니다. 그것을 증명하려면 캡처가 CLI 렌더와 같은지 확인해야 합니다.

  1. SDL_VIDEODRIVER=dummy 로 창 없이 렌더하고 pygame.image.save() 로 PNG 를 만든다.
  2. 그 PNG 를 다시 읽어 RGB 바이트로 편다.
  3. 별도 프로세스가 python3 -m isorpg.main render out/frame_N.ppm N 로 만든 PPM 과 바이트 비교한다.
별도 프로세스를 쓰는 것이 중요합니다. 같은 프로세스 안에서 만든 두 이미지를 비교하면 같은 실수를 두 번 하고 통과할 수 있습니다.
