왜 핀볼 게임인가?

  • 핀볼은 2D 게임 물리의 거의 모든 주제를 한 화면에 담고 있는 교과서다.
  • 중력·반발·감쇠 — 연속적인 힘과 적분
  • 벽·범퍼·플리퍼 — 원, 선분, 회전체와의 충돌
  • 발사 스프링·점수 — 게임 상태 관리와 UI
  • 외부 라이브러리 없이 순수 자바스크립트만으로 물리 엔진의 원리를 밑바닥부터 이해할 수 있다.
  • 완성 코드는 약 500줄 — 하나의 HTML 파일로 어디서든 실행된다.
8

학습 목표

  • 벡터(Vec2) 클래스를 직접 설계하고 내적·정규화·반사를 코드로 구현한다.
  • 삼각함수(sin, cos, atan2)로 회전하는 플리퍼와 곡면 벽을 만든다.
  • 반암시적 오일러 적분으로 중력과 속도를 시뮬레이션한다.
  • 원-원, 원-선분 충돌을 감지하고 침투를 해소한다.
  • requestAnimationFrame 기반 게임 루프와 delta time을 다룬다.
9

기술 스택 — 정말 '바닐라'다

  • HTML5 <canvas> 요소와 2D 렌더링 컨텍스트만 사용한다.
  • 빌드 도구 없음: 번들러, 트랜스파일러, npm 패키지 전부 불필요.
  • 물리 엔진 없음: matter.js, box2d 같은 라이브러리를 쓰지 않고 직접 만든다.
  • 필요한 것: 텍스트 에디터와 모던 브라우저(Chrome, Edge, Firefox, Safari) 하나.
  • ES2020+ 문법(클래스, 화살표 함수, ||= 등)을 사용하므로 최신 브라우저 권장.

<canvas> 요소란?

  • HTML5가 도입한 비트맵 도화지. 자바스크립트로 픽셀 단위 그리기가 가능하다.
  • DOM 요소를 움직이는 방식과 달리, 매 프레임 전체를 다시 그리는 즉시 모드(immediate mode) 렌더링.
  • 게임처럼 수십 개 객체가 매 프레임 움직이는 경우 DOM보다 훨씬 빠르고 단순하다.
  • 우리 게임: <canvas id="game" width="480" height="800"></canvas>
18

캔버스 준비 코드

getContext("2d") 가 반환하는 ctx 객체가 모든 그리기의 창구다.

<canvas id="game" width="480" height="800"></canvas>
<script>
const canvas = document.getElementById("game");
const ctx = canvas.getContext("2d");   // 2D 렌더링 컨텍스트
 
ctx.fillStyle = "#e2534f";
ctx.fillRect(10, 10, 100, 50);         // (10,10)에 100×50 사각형
</script>
19

width/height 속성 vs CSS 크기

  • width/height HTML 속성 = 실제 픽셀 버퍼의 크기(논리 해상도).
  • CSS width/height = 화면에 표시되는 크기. 둘이 다르면 늘어나 보인다.
  • 우리 게임은 속성으로 480×800을 지정하고 CSS는 건드리지 않아 1:1 매칭.
  • 흐릿하게 보인다면 대부분 CSS로만 크기를 키웠기 때문이다.
20

캔버스 좌표계 — y축이 아래로!

  • 원점 (0,0)은 왼쪽 위 모서리.
  • x는 오른쪽으로 증가 — 수학과 같다.
  • y는 아래로 증가 — 수학 좌표계와 반대! 이것이 게임 수학의 최대 함정.
  • 따라서 중력은 +y 방향: GRAVITY = new Vec2(0, 1400).
  • 각도의 회전 방향도 화면상 시계 방향이 양수가 된다(5장에서 자세히).
21

사각형 API — 가장 단순한 도형

  • fillRect(x, y, w, h): 채운 사각형. 발사 게이지 바에 사용.
  • strokeRect(x, y, w, h): 테두리만.
  • clearRect(x, y, w, h): 해당 영역을 투명하게 지운다.
  • 매 프레임 시작에 ctx.clearRect(0, 0, W, H)로 전체 화면을 지우고 다시 그린다.
22

경로(Path) API — 자유 곡선의 기본

  • beginPath(): 새 경로 시작. 잊으면 이전 도형과 이어져 버린다(대표적 버그).
  • moveTo(x, y): 펜을 떼서 이동.
  • lineTo(x, y): 현재 위치에서 직선 경로 추가.
  • arc(x, y, r, start, end): 원호 경로 추가.
  • closePath(): 시작점으로 닫기(선택).
  • 경로를 만든 뒤 fill() 또는 stroke()를 호출해야 실제로 그려진다.
23

공 그리기 — arc()와 원

arc의 각도 단위는 '라디안'. 2π = 360°. 5장에서 자세히 다룬다.

// 원 = 중심 (x,y), 반지름 r, 0 ~ 2π 라디안의 호
ctx.beginPath();
ctx.arc(ball.pos.x, ball.pos.y, BALL_RADIUS, 0, Math.PI * 2);
ctx.fill();
 
// 벽(선분) 그리기
ctx.beginPath();
ctx.moveTo(wall.a.x, wall.a.y);
ctx.lineTo(wall.b.x, wall.b.y);
ctx.stroke();

스타일 속성

  • fillStyle / strokeStyle: 색. "#f5b942", "rgba(255,0,0,.5)" 등 CSS 색 문법 그대로.
  • lineWidth: 선 두께(px). 우리 벽은 4, 플리퍼는 20.
  • lineCap: "round"로 하면 선 끝이 둥글어진다 — 플리퍼가 캡슐처럼 보이는 이유.
  • 스타일은 상태로 유지된다: 한 번 설정하면 바꿀 때까지 모든 도형에 적용.
25

그라디언트 — 공의 입체감

  • createRadialGradient(x0,y0,r0, x1,y1,r1): 원형 그라디언트 객체 생성.
  • addColorStop(위치 0~1, 색)으로 색 지점을 추가.
  • 우리 공: 중심에서 살짝 왼쪽 위(-4,-4)에 흰색 하이라이트 → 금속 공 느낌.
  • 그라디언트 생성은 비용이 있으므로 성능이 아쉬우면 캐싱을 고려(13장).
26

공의 금속 질감

const g = ctx.createRadialGradient(
  this.pos.x - 4, this.pos.y - 4, 2,   // 하이라이트 중심(작은 원)
  this.pos.x, this.pos.y, BALL_RADIUS  // 공 전체(큰 원)
);
g.addColorStop(0, "#ffffff");   // 중심: 흰색 하이라이트
g.addColorStop(1, "#8a94b8");   // 가장자리: 어두운 은색
ctx.fillStyle = g;
ctx.beginPath();
ctx.arc(this.pos.x, this.pos.y, BALL_RADIUS, 0, Math.PI * 2);
ctx.fill();

텍스트 API — HUD 만들기

  • font: CSS font 축약형. 예: "bold 22px monospace".
  • fillText(문자열, x, y): 텍스트 그리기. y는 베이스라인 기준.
  • textAlign: "left" | "center" | "right" — x 기준점이 바뀐다.
  • 점수는 왼쪽 정렬, 남은 공은 오른쪽 정렬, 안내 문구는 가운데 정렬로 사용.
28

변환(Transform) API — 이 게임에서 안 쓴 이유

  • translate/rotate/scale로 좌표계 자체를 옮기고 돌릴 수 있다.
  • 회전체를 그릴 때 자주 쓰지만, 우리는 플리퍼 끝점을 삼각함수로 직접 계산한다.
  • 이유: 그리기뿐 아니라 '충돌 계산'에도 같은 끝점 좌표가 필요하기 때문.
  • 변환은 그리기에만 적용되고 수학 계산에는 적용되지 않는다
  • 수학을 한 곳(tip() 메서드)에서 처리하면 그리기와 물리가 항상 일치한다.
29

save() / restore()

  • 캔버스 상태(스타일, 변환, 클리핑)를 스택에 저장/복원한다.
  • 복잡한 장면에서 상태 오염을 막는 표준 패턴.
  • 우리 게임은 상태 변경이 단순해 매번 명시적으로 스타일을 지정하는 쪽을 택했다.
  • 규칙: save/restore를 쓰든, 매번 스타일을 다시 지정하든 하나만 일관되게.
30

즉시 모드 렌더링의 핵심 규칙

  • 캔버스에는 '객체'가 없다 — 그려진 픽셀만 있다.
  • 공을 움직이려면: 지우고(clearRect) → 새 위치에 다시 그린다.
  • 따라서 게임 상태(위치, 속도)는 반드시 자바스크립트 객체로 따로 관리한다.
  • 그리기 순서 = 쌓이는 순서: 나중에 그린 것이 위에 보인다.
  • 우리 순서: 벽 → 슬링샷 → 범퍼 → 플리퍼 → 공 → HUD
31

고해상도(레티나) 디스플레이 대응

  • devicePixelRatio(DPR)가 2면 CSS 1px에 실제 픽셀 4개가 들어간다.
  • 선명하게 하려면: canvas.width = 표시폭 × DPR, ctx.scale(DPR, DPR).
  • 이 튜토리얼은 단순함을 위해 DPR 처리를 생략했다 — 13장 최적화에서 확장 과제로.
32

게임 루프란?

  • 모든 실시간 게임의 뼈대: 입력 처리 → 상태 갱신(update) → 그리기(render)를 무한 반복.
  • 초당 60회 반복되면 60fps — 사람 눈에 부드러운 움직임으로 보인다.
  • 핵심 질문 두 가지: ① 언제 반복할 것인가 ② 한 번에 시간이 얼마나 흘렀다고 볼 것인가.
39

setInterval이 아니라 requestAnimationFrame

  • setInterval(fn, 16)은 모니터 주사율과 어긋나 화면 찢김·버벅임이 생긴다.
  • requestAnimationFrame(rAF)은 브라우저의 다음 화면 갱신 직전에 콜백을 실행한다.
  • 60Hz 모니터면 약 16.7ms마다, 144Hz면 약 6.9ms마다 호출
  • 탭이 백그라운드로 가면 자동으로 멈춰 배터리를 아낀다.
  • rAF는 1회용이다 — 콜백 안에서 다시 rAF를 호출해야 루프가 된다.
40

게임 루프의 골격

생성자에서 this.last = performance.now() 로 초기화 후 첫 rAF를 건다.

frame(now) {                      // now: 브라우저가 넘겨주는 ms 타임스탬프
  let dt = Math.min((now - this.last) / 1000, 1 / 30);
  this.last = now;
  this.update(dt);                // 물리·게임 상태 갱신
  this.render();                  // 화면 다시 그리기
  requestAnimationFrame(t => this.frame(t));   // 다음 프레임 예약
}
41

delta time(dt)이 필요한 이유

  • 프레임마다 '지난번 이후 흐른 시간'은 일정하지 않다 — 60Hz와 144Hz 모니터, 렉 걸린 순간 모두 다르다.
  • 이동량을 '프레임당 5px'로 하드코딩하면 144Hz 사용자에겐 2.4배 빠른 게임이 된다.
  • 해결: 이동량 = 속도(px/초) × dt(초). 어떤 주사율에서도 같은 속도.
  • 우리 게임의 모든 물리량은 초 단위: 중력 1400px/s², 발사 속도 최대 1600px/s.
42

시간 기반 이동

새 위치 = 현재 위치 + 속도 × dt
pos = pos + vel · dt
  • dt는 초 단위(ms를 1000으로 나눔).
  • 60fps라면 dt ≈ 0.0167초 → 속도 600px/s인 공은 프레임당 약 10px 이동.
  • 이 식이 바로 6장에서 배울 '오일러 적분'의 한 줄이다.
43

dt 클램프 — 죽음의 나선 방지

  • 탭을 오래 벗어났다 돌아오면 dt가 수 초가 될 수 있다.
  • 그대로 적분하면 공이 한 번에 수천 px 이동 → 벽을 뚫고 우주로.
  • 해결: dt = Math.min(실제 경과, 1/30). 최악에도 33ms 프레임으로 취급.
  • 결과: 렉이 걸리면 게임이 느려질 뿐, 물리가 깨지지는 않는다.
44

고정 timestep vs 가변 timestep

  • 가변(우리 방식): dt를 그대로 사용. 구현이 단순하고 대부분의 캐주얼 게임에 충분.
  • 고정: 물리를 항상 일정 dt(예: 1/120초)로 여러 번 돌리고 남는 시간은 이월. 완전한 재현성.
  • 네트워크 동기화나 리플레이가 필요하면 고정이 정답.
  • 우리는 가변 + 서브스텝(dt를 4등분)의 절충안을 쓴다 — 6장에서 상세히.
45

update와 render의 분리

  • update(dt): 물리, 충돌, 점수 — '세계의 진실'을 갱신. 그리기 코드가 없다.
  • render(): 현재 상태를 화면에 표현만 한다. 상태를 바꾸지 않는다.
  • 분리의 이점 ① 테스트: 캔버스 없이도 update만 돌려 물리를 검증할 수 있다(12장).
  • 분리의 이점 ② 유연성: 렌더러를 WebGL로 교체해도 물리는 그대로.
46

performance.now() vs Date.now()

  • performance.now(): 페이지 로드 기준 ms, 소수점 이하 마이크로초 정밀도, 단조 증가 보장.
  • Date.now(): 벽시계 시간. OS 시간 동기화로 갑자기 튈 수 있다 — 게임 루프에 부적합.
  • rAF 콜백의 인자(now)는 performance.now()와 같은 시간축이라 그대로 쓰면 된다.

입력 처리 — 이벤트와 상태 플래그

벡터란 무엇인가

  • 크기와 방향을 함께 갖는 양. 화살표로 그린다.
  • 게임에서의 용도: 위치(원점에서의 화살표), 속도(1초당 이동 화살표), 힘, 법선….
  • 스칼라는 크기만 갖는 수(질량 5, 점수 100). 벡터와 구분하는 것이 출발점.
  • 2D 게임의 벡터는 성분 두 개짜리 순서쌍: v = (x, y).

왜 벡터로 코드를 짜는가

  • x, y를 따로 다루면: ball.vx += gx*dt; ball.vy += gy*dt; — 모든 식을 두 번씩 쓴다.
  • 벡터로 다루면: ball.vel = ball.vel.add(GRAVITY.scale(dt)); — 수학책의 식과 코드가 1:1.
  • 충돌 반사 같은 공식은 성분별로 풀어 쓰면 알아볼 수 없게 된다.
  • 버그의 절반은 'x는 고쳤는데 y는 빼먹은' 비대칭에서 온다 — 벡터가 원천 차단.

Vec2 클래스의 뼈대

게임 전체가 이 클래스 하나 위에 서 있다. 이 장에서 한 메서드씩 해부한다.

class Vec2 {
  constructor(x = 0, y = 0) { this.x = x; this.y = y; }
  add(v)   { return new Vec2(this.x + v.x, this.y + v.y); }
  sub(v)   { return new Vec2(this.x - v.x, this.y - v.y); }
  scale(s) { return new Vec2(this.x * s, this.y * s); }
  dot(v)   { return this.x * v.x + this.y * v.y; }
  len()    { return Math.hypot(this.x, this.y); }
  norm()   { const l = this.len();
             return l > 1e-9 ? this.scale(1 / l) : new Vec2(); }
  perp()   { return new Vec2(-this.y, this.x); }
}

불변(immutable) 스타일 — 설계 결정

  • 모든 메서드가 자신을 수정하지 않고 '새 Vec2'를 반환한다.
  • 장점: a.add(b)가 a를 바꾸지 않으므로 수식처럼 안전하게 체이닝 가능.
  • ball.vel.sub(surfaceVel) 를 계산해도 ball.vel은 그대로
  • 단점: 프레임마다 작은 객체가 많이 생성된다 — GC 부담(13장에서 완화책).
  • 교육용·중소규모 게임엔 불변이 압도적으로 버그가 적다. 우리의 선택.

벡터 덧셈

a + b = (aₓ + bₓ, a_y + b_y)
  • 기하학적 의미: a 화살표 끝에 b 화살표를 이어 붙인 결과.
  • 물리적 의미: 이동의 누적. '속도에 중력을 더한다', '위치에 이동량을 더한다'.
  • 교환법칙 성립: a + b = b + a.
59

덧셈이 게임에서 하는 일

  • 위치 갱신: pos = pos.add(vel.scale(dt)) — 매 프레임의 핵심 한 줄.
  • 속도 갱신: vel = vel.add(GRAVITY.scale(dt)) — 중력이 속도를 조금씩 아래로 민다.
  • 침투 해소: pos = pos.add(n.scale(깊이)) — 벽에 박힌 공을 법선 방향으로 밀어낸다.
  • 덧셈만으로 '적분'과 '충돌 응답'의 절반이 끝난다.
60

벡터 뺄셈 = 상대 위치

b − a = 'a에서 b를 향하는 화살표'
  • 게임에서 가장 많이 쓰는 연산. '무엇에서 무엇을 향하는 방향'은 전부 뺄셈이다.
  • 공 − 범퍼중심 = 범퍼가 공을 밀어낼 방향(법선).
  • 공 − 최근접점 = 벽이 공을 밀어낼 방향.
  • 머리로 외우는 법: '도착지 − 출발지'.
61

스칼라배

s·v = (s·vₓ, s·v_y)
  • 방향은 유지(음수면 반대), 길이만 s배.
  • GRAVITY.scale(dt): '초당 가속도'를 '이번 프레임 몫'으로 축소.
  • n.scale(BALL_RADIUS - dist): 단위 법선을 침투 깊이만큼 늘려 보정 벡터로.
  • vel.scale(0.999): 공기저항 — 매 프레임 0.1%씩 감속.
62

벡터의 길이 (피타고라스)

|v| = √(vₓ² + v_y²)
  • 속도 벡터의 길이 = 속력(스칼라). 방향을 버리고 크기만 남긴다.
  • 코드: Math.hypot(x, y) — x*x+y*y의 sqrt보다 오버플로에 안전하고 읽기 좋다.
  • 쓰임: 최고 속도 제한, 충돌 거리 판정, '공이 거의 멈췄나' 판단.
63

lenSq() — sqrt를 피하는 최적화

  • 제곱근은 곱셈보다 느리다. 비교만 할 거면 제곱끼리 비교해도 결과가 같다.
  • |v| < r ⇔ |v|² < r² (양수끼리는 순서 보존)
  • closestPointOnSegment에서 ab.lenSq()로 나누는 것도 같은 이유(길이의 제곱이 필요).
  • 습관: 거리 '비교'는 lenSq, 거리 '값'이 필요할 때만 len.
64

정규화 (Normalize)

v̂ = v / |v|, |v̂| = 1
  • 방향은 그대로, 길이를 1로 만든 '단위 벡터'.
  • 왜 필요한가: '방향'과 '크기'를 분리해서 다루기 위해.
  • 예: 법선 방향으로 정확히 420px/s — n̂.scale(420)
  • 반사 공식의 n은 반드시 단위 벡터여야 한다. 아니면 반사가 과장/축소된다.
65

정규화의 함정 — 0벡터

  • 길이가 0인 벡터는 방향이 없다. 0으로 나누면 NaN — 물리 전체가 오염된다.
  • NaN은 전염된다: NaN과의 모든 연산이 NaN. 공이 화면에서 사라지는 미스터리 버그의 주범.
  • 우리 코드: l > 1e-9 체크 후 아니면 영벡터 반환.
  • 충돌 코드에도 dist < 1e-9 가드가 있다 — 공 중심이 벽 위에 '정확히' 올라간 극단 케이스.
66

내적 (Dot Product)

a · b = aₓbₓ + a_yb_y = |a||b|cosθ
  • 두 정의가 같다는 것이 내적의 기적 — 좌표 계산 두 번의 곱셈으로 '각도 정보'를 얻는다.
  • θ는 두 벡터 사이의 각.
  • 결과는 벡터가 아니라 스칼라(숫자) 하나다.
67

내적의 부호 읽는 법

  • a·b > 0: 두 벡터가 대체로 같은 방향(θ < 90°).
  • a·b = 0: 정확히 수직(θ = 90°).
  • a·b < 0: 대체로 반대 방향(θ > 90°).
  • 핀볼에서: vel·n < 0 이면 '공이 표면을 향해 들어오는 중' → 반사해야 함.
  • vel·n ≥ 0 이면 이미 떠나는 중 → 건드리면 오히려 표면에 다시 붙는 버그가 생긴다.
68

내적으로 하는 투영 (Projection)

a의 b방향 성분 = (a · b̂) b̂
성분 크기 = a · b̂
  • a를 b 방향 성분과 수직 성분으로 분해할 수 있다.
  • b̂가 단위 벡터일 때 a·b̂ 는 'a의 그림자 길이'.
  • 핀볼에서의 두 사용처: ① 최근접점 계산(7장) ② 반사 공식 유도(이번 장).
69

투영 직관 훈련

  • 태양이 b̂ 방향에 수직으로 비출 때 a 화살표의 그림자가 투영이다.
  • 속도 (300, 400)이고 법선이 (0, -1)이면: vel·n = -400.
  • 해석: 표면을 향해 400px/s로 접근 중 (부호가 방향, 크기가 속도)
  • 가로 성분 300은 법선과 수직이라 내적에 전혀 기여하지 않는다.
  • 이 분해 능력이 반사 공식을 이해하는 열쇠다.
70

수직 벡터 perp()

perp(v) = (−v_y, vₓ)
  • v를 90° 회전한 벡터. 길이는 그대로.
  • 확인: v·perp(v) = x(−y) + yx = 0 — 항상 수직.
  • 쓰임 ① 선분의 법선: 선분 방향 d의 perp가 벽의 법선 후보.
  • 쓰임 ② 회전 속도: 원운동하는 점의 속도 방향은 반지름의 perp (8장 플리퍼).
71

2D 외적 (Cross Product)

a × b = aₓb_y − a_yb_x
  • 2D에서는 스칼라 하나가 나온다(3D 외적의 z성분).
  • 부호의 의미: b가 a의 왼쪽에 있으면 +, 오른쪽이면 − (좌표계 기준).
  • 쓰임: 점이 선의 어느 쪽인지 판정, 회전 방향 판단.
  • 우리 게임에선 직접 쓰진 않지만 Vec2에 포함 — 확장(공 스핀) 시 필수가 된다.
72

반사 공식 유도 ① — 속도의 분해

  • 공이 법선 n̂(단위벡터)인 표면에 속도 v로 충돌한다.
  • v를 두 성분으로 나눈다:
  • 법선 성분 v_n = (v·n̂)n̂ — 표면을 뚫고 들어가는 성분
  • 접선 성분 v_t = v − v_n — 표면을 따라 미끄러지는 성분
  • 반사의 본질: 접선 성분은 그대로, 법선 성분만 뒤집는다.
73

반사 공식 유도 ② — 완전 탄성 반사

  • 새 속도 v' = v_t − v_n (접선 유지, 법선 반전)
  • 대입: v' = (v − v_n) − v_n = v − 2v_n
  • 따라서 v' = v − 2(v·n̂)n̂ — 거울 반사 공식.
  • 에너지 손실이 없는 이상적인 반사. 현실의 공은 튕길 때마다 조금씩 죽는다 → 반발계수.
74

반발계수를 포함한 최종 반사 공식

v' = v − (1 + e)(v·n̂)n̂
  • e = 1: 완전 탄성(2를 곱하는 거울 반사와 동일).
  • e = 0: 법선 성분 완전 소멸 — 공이 표면에 '철퍼덕' 붙어 미끄러지기만 한다.
  • 우리 게임: 벽 0.55, 플리퍼 0.35, 범퍼 1.15(!) — 1보다 크면 에너지를 얻는다.
  • 범퍼가 공을 '쏘아 보내는' 비결이 바로 e > 1 이다.
75

reflect() — 게임 물리의 심장

세 줄이 전부다. 벽, 범퍼, 슬링샷, 플리퍼가 전부 이 함수 하나로 튕긴다.

/* 반사 공식: v' = v - (1+e)(v·n)n  (n은 단위 법선, e는 반발계수) */
function reflect(v, n, e) {
  const vn = v.dot(n);
  if (vn >= 0) return v;   // 이미 표면에서 멀어지는 중이면 그대로
  return v.sub(n.scale((1 + e) * vn));
}
76

vn >= 0 가드가 막아주는 버그

  • 충돌 판정은 '겹침'으로 하므로, 반사 직후 프레임에도 아직 겹쳐 있을 수 있다.
  • 가드가 없으면: 떠나는 공을 또 반사 → 공이 표면으로 유턴 → 다시 반사 → 무한 진동.
  • 증상: 공이 벽에 붙어 부들부들 떨거나, 벽 속으로 파고든다.
  • '멀어지는 중이면 손대지 않는다'는 물리 엔진의 보편 원칙이다.
77

게임 속 벡터 사용처 지도

  • pos, vel — 공의 상태 (위치·속도).
  • GRAVITY — 상수 가속도 벡터.
  • b − a, sub — 법선 방향, 상대 위치 계산 전부.
  • dot — 접근/이탈 판정, 투영, 최근접점.
  • norm — 모든 충돌 법선의 단위화.
  • perp — 플리퍼 표면 속도의 방향.
  • scale — dt 적분, 침투 보정, 속도 제한.

예제 풀이 ① 범퍼 법선

  • 범퍼 중심 (215, 340), 공 중심 (245, 300)일 때 밀어낼 방향은?
  • d = 공 − 범퍼 = (30, −40). |d| = √(900+1600) = 50.
  • n̂ = d/50 = (0.6, −0.8) — 오른쪽 위 방향으로 밀어낸다.
  • 침투 해소: 공 위치 = 범퍼중심 + n̂ × (범퍼r + 공r) — 정확히 접하는 위치로 이동.

예제 풀이 ② 내적으로 접근 판정

  • 바닥 법선 n̂ = (0, −1), 공 속도 v = (200, 500).
  • v·n̂ = 200×0 + 500×(−1) = −500 < 0 → 접근 중, 반사 필요.
  • 반사(e=0.55): v' = v − 1.55×(−500)×(0,−1) = (200, 500) + (0, −775) = (200, −275).
  • 검산: 가로 200 유지(접선), 세로는 500 → −275 = 500×0.55 반전. 공식이 살아 있다.

핀볼에서 삼각함수가 필요한 순간

  • 플리퍼: 피벗을 중심으로 '각도'가 변하는 막대 — 끝점 좌표가 매 프레임 필요하다.

  • 공통점: '각도와 거리(극좌표)'를 '화면 좌표(x, y)'로 바꿔야 한다 — 그 변환기가 sin/cos다.

각도의 두 단위 — 도(°)와 라디안

  • 도: 한 바퀴 = 360°. 사람에게 익숙하다.
  • 라디안: 한 바퀴 = 2π ≈ 6.283. '반지름 몇 개 길이의 호를 감았나'.
  • 자바스크립트 Math의 모든 삼각함수는 라디안만 받는다. canvas arc()도 라디안.
  • 우리 코드: 사람이 읽는 곳은 도로 쓰고 즉시 변환한다 — const D = Math.PI/180; 32*D.

도 ↔ 라디안 변환

rad = deg × π / 180
deg = rad × 180 / π
  • 암기용 기준점: 180° = π, 90° = π/2, 360° = 2π.
  • 32° ≈ 0.559 rad (우리 플리퍼의 대기 각도).
  • 코드 팁: 변환 상수를 D라는 이름으로 한 번만 정의하면 오타가 사라진다.

단위원 — sin과 cos의 정의

  • 반지름 1인 원 위에서 각도 θ만큼 돈 점의 좌표가 (cosθ, sinθ)다. 이것이 '정의'.
  • cosθ = 점의 x좌표, sinθ = 점의 y좌표. 삼각형 암기보다 이 그림이 실전적이다.
  • θ=0: (1,0) 오른쪽. θ=90°: (0,1). θ=180°: (−1,0) 왼쪽.
  • 반지름이 r이면 좌표는 (r·cosθ, r·sinθ) — 곧바로 플리퍼 끝점 공식이 된다.

캔버스에서 각도의 방향 — 주의!

  • 수학책: y가 위, 각도는 반시계 방향으로 증가.
  • 캔버스: y가 '아래', 그래서 화면상 각도는 '시계 방향'으로 증가한다.
  • θ=90°의 점 (0,1)은 캔버스에서 '아래쪽'이다.
  • 우리 왼쪽 플리퍼: 대기 +32°(끝점이 오른쪽 '아래'), 작동 −34°(오른쪽 '위') — 이 규칙 그대로.
  • 혼란스러울 땐 항상 '작은 각도를 넣고 어디에 그려지나' 실험하는 것이 최고다.

극좌표 → 직교좌표

x = r·cosθ, y = r·sinθ
Vec2.fromAngle(θ, r) = (r·cosθ, r·sinθ)
  • '각도 θ 방향으로 거리 r' 을 화면 좌표로 바꾸는 만능 공식.
  • 플리퍼 끝점, 아치 벽 정점, 파티클 분사 — 전부 이 한 줄.
  • 역변환은 r = |v|, θ = atan2(y, x).

fromAngle과 rotate — Vec2의 삼각함수 도구

// 극좌표 → 직교좌표
static fromAngle(theta, len = 1) {
  return new Vec2(Math.cos(theta) * len, Math.sin(theta) * len);
}
 
// 회전행렬 [cosθ -sinθ; sinθ cosθ] 를 이용한 회전
rotate(theta) {
  const c = Math.cos(theta), s = Math.sin(theta);
  return new Vec2(this.x * c - this.y * s,
                  this.x * s + this.y * c);
}
 
angle() { return Math.atan2(this.y, this.x); }  // 벡터 → 방향각

회전행렬 유도 ① — 기저의 회전

  • 점 (x, y)는 x·(1,0) + y·(0,1) — 두 기본 화살표의 조합이다.
  • 좌표계를 θ만큼 돌리면 기본 화살표가 이렇게 움직인다:
  • (1,0) → (cosθ, sinθ)
  • (0,1) → (−sinθ, cosθ) (90° 앞선 위치)
  • 따라서 회전 결과 = x·(cosθ, sinθ) + y·(−sinθ, cosθ).
94

회전행렬 유도 ② — 최종 공식

x' = x·cosθ − y·sinθ
y' = x·sinθ + y·cosθ
  • rotate() 코드의 두 줄과 정확히 일치한다.
  • θ=90° 대입: (x, y) → (−y, x) — perp()와 같다! perp는 rotate(90°)의 특수화였던 것.
  • cos/sin을 지역변수 c, s에 캐싱하는 것은 관용구 — 두 번 계산하지 않는다.

atan2 — 각도를 되찾는 함수

  • atan(y/x)의 문제: x가 0이면 폭발, (−1,−1)과 (1,1)을 구분 못 함(같은 비율).
  • atan2(y, x): 부호를 각각 받아 4개 사분면을 전부 구분. 결과는 −π ~ +π.
  • 인자 순서가 (y, x)인 것에 주의 — 수십 년 역사의 관례다.
  • 쓰임: 공이 날아가는 방향각, 조준, 두 점 사이의 각도.

플리퍼의 기하학적 모델

  • 플리퍼 = 피벗(고정점) + 길이 L의 막대 + 두께(캡슐 반경) 10px.
  • 상태는 각도 θ 하나로 완전히 결정된다 — 위치가 아닌 '각도'가 상태라는 것이 핵심.
  • 왼쪽 플리퍼: pivot (140, 726), L=72, 대기 32° ↔ 작동 −34°.
  • 오른쪽 플리퍼: pivot (288, 726), 대기 148° ↔ 작동 214° — 거울 대칭 각도.

플리퍼 끝점 공식

tip = pivot + L·(cosθ, sinθ)
  • 이 슬라이드가 5장의 존재 이유다.
  • θ가 바뀌면 tip이 피벗 중심의 원호를 따라 움직인다 — 회전의 본질.
  • 코드: this.pivot.add(Vec2.fromAngle(this.angle, this.length))
  • 그리기와 충돌 계산이 같은 tip()을 쓰므로 보이는 것과 물리가 절대 어긋나지 않는다.

오른쪽 플리퍼는 왜 148°인가

  • 왼쪽 플리퍼가 +32°(오른쪽 아래로 뻗음)라면 오른쪽 플리퍼는 좌우 거울상이어야 한다.
  • 거울 대칭 공식: θ' = 180° − θ. 180 − 32 = 148°.
  • 작동 각도: 180 − (−34) = 214°.
  • cos(148°) < 0 이므로 끝점이 피벗의 '왼쪽'으로 뻗는다 — 정확히 원하는 모양.

각속도 ω — 회전의 속도

  • ω(오메가) = 초당 회전 라디안(rad/s). 선속도의 회전 버전.
  • 우리 플리퍼의 회전 속도: 22 rad/s ≈ 1260°/s — 대기→작동(66°)을 약 0.05초에 주파.
  • 플리퍼가 '때리는 맛'은 전적으로 ω에서 나온다: 정지한 플리퍼는 그냥 벽이다.
  • 8장에서 ω로 접촉점의 표면 속도를 계산해 공을 후려치게 만든다.

각속도와 선속도의 관계

|v| = ω · r
v = ω · perp(r) (2D)
  • 피벗에서 r만큼 떨어진 점은 ω·r 의 속력으로 움직인다 — 끝점일수록 빠르다.
  • 방향은 반지름에 수직(원의 접선) — perp(r)가 그 방향을 준다.
  • 플리퍼 끝(r=72)에서: 22 × 72 ≈ 1584 px/s — 발사 속도급의 타격이 나오는 이유.

곡선 벽 만들기 — 호의 선분 근사

아치 벽 생성 코드

π(180°)에서 2π(360°)까지 = 캔버스 좌표계에서 '위쪽 반원'이다.

// 상단 반원 아치: 중심 (W/2, 240), 반경 W/2-6
const cx = W / 2, cy = 240, R = W / 2 - 6, SEG = 22;
for (let i = 0; i < SEG; i++) {
  const t0 = Math.PI + (Math.PI * i) / SEG;       // 이번 조각 시작각
  const t1 = Math.PI + (Math.PI * (i + 1)) / SEG; // 이번 조각 끝각
  this.walls.push(new Wall(
    cx + R * Math.cos(t0), cy + R * Math.sin(t0),
    cx + R * Math.cos(t1), cy + R * Math.sin(t1)));
}

뉴턴 운동 법칙의 게임 번역

  • 1법칙(관성): 힘이 없으면 속도 유지 → 코드에서 '아무것도 안 하면' 등속.
  • 2법칙(F=ma): 힘은 가속도를 만든다 → vel += acc × dt.
  • 3법칙(작용반작용): 충돌 반작용 → 우리는 공만 움직이므로 반사로 단순화.
  • 게임 물리는 '그럴듯함'이 목표다. 정확한 뉴턴 역학의 근사면 충분하다.

중력 상수 정하기 — px/s²의 세계

  • 현실: 9.8 m/s². 게임: 화면 크기에 맞는 픽셀 단위로 스스로 정한다.
  • 우리 값: GRAVITY = (0, 1400) px/s² — +y가 아래인 것을 기억하라.
  • 감각적 의미: 정지한 공이 1초 후 1400px/s — 화면(800px)을 금방 가로지르는 속도.
  • 튜닝 기준: 크면 공이 무겁고 급하게, 작으면 달 표면처럼 둥실둥실.
  • 핀볼은 실제보다 '과장된 중력'이 손맛이 좋다.

오일러 적분 — 미분방정식의 이산화

v(t+dt) ≈ v(t) + a·dt
p(t+dt) ≈ p(t) + v·dt
  • 연속적인 물리 법칙(dv/dt = a)을 프레임 단위 덧셈으로 근사한다.
  • dt가 작을수록 정확 — 60fps의 16.7ms면 캐주얼 게임에 충분.
  • 적분 순서에 따라 두 유파가 갈린다: 명시적 vs 반암시적.
116

명시적 vs 반암시적 오일러

  • 명시적(explicit): 위치 먼저(옛 속도로), 속도 나중. p += v·dt; v += a·dt.
  • 반암시적(semi-implicit): 속도 먼저, '새 속도'로 위치. v += a·dt; p += v·dt.
  • 명시적은 에너지가 서서히 증가하는 경향 — 공이 튕길 때마다 더 높이 올라가는 괴현상.
  • 반암시적은 안정적이고 구현 난이도는 동일 — 게임 업계 표준. 우리의 선택.
117

Ball.update — 반암시적 오일러 + 감쇠 + 속도 제한

물리 적분의 전부. 벡터 덕분에 x/y 중복 없이 다섯 줄이다.

update(dt) {
  if (!this.inPlay) return;
  // 반암시적 오일러: v += a·dt, p += v·dt (새 속도로!)
  this.vel = this.vel.add(GRAVITY.scale(dt));
  this.vel = this.vel.scale(AIR_DRAG);          // 공기저항 0.999
  const sp = this.vel.len();
  if (sp > MAX_SPEED)                            // 속도 상한 1600px/s
    this.vel = this.vel.scale(MAX_SPEED / sp);
  this.pos = this.pos.add(this.vel.scale(dt));
}

공기저항(감쇠) — 게임을 '수렴'시키는 장치

  • 매 스텝 vel × 0.999 — 0.1%씩 에너지를 깎는다.
  • 없으면: 반발계수 1.15인 범퍼 때문에 공이 무한히 빨라질 수 있다.
  • 있으면: 범퍼가 주는 에너지와 감쇠가 균형을 이뤄 게임 템포가 안정된다.
  • 주의: 프레임 횟수에 곱해지므로 엄밀히는 dt 의존적이다 — 서브스텝 수를 바꾸면 체감이 미묘하게 달라진다. 정석은 Math.pow(drag, dt) 방식(13장 참고).
119

최고 속도 제한(MAX_SPEED)의 세 가지 이유

  • ① 터널링 방지: 너무 빠른 공은 한 스텝에 벽을 건너뛴다.
  • ② 게임성: 눈으로 좇을 수 없는 공은 재미가 아니라 스트레스.
  • ③ 수치 안정성: 속도가 폭주하면 충돌 보정량도 폭주해 연쇄 붕괴.
  • 구현: 속력이 1600을 넘으면 방향은 유지한 채 크기만 1600으로 — scale(MAX/sp).
120

반발계수 (Coefficient of Restitution)

e = (튕겨나가는 속력) / (들어온 속력) — 법선 방향 기준
  • 충돌의 '탄력'을 0~1+ 숫자 하나로 표현.
  • 농구공 ≈ 0.8, 진흙 ≈ 0, 슈퍼볼 ≈ 0.9.
  • 반사 공식의 (1+e)에 들어가는 그 e다 — 4장과 연결.
121

우리 게임의 반발계수 설계표

  • 벽 WALL_E = 0.55 — 적당히 죽어야 공이 필드에 머문다.
  • 플리퍼 FLIPPER_E = 0.35 — 반발은 낮게, 대신 ω×r 타격으로 속도를 준다(8장).
  • 범퍼 BUMPER_E = 1.15 — 에너지를 '주입'하는 능동 요소.
  • 슬링샷 e = 1.0 + 최소 속도 보장 — 쏘아 보내는 느낌.
  • 이 네 숫자가 게임의 성격을 결정한다. 물리 튜닝 = 게임 디자인.
122

에너지 관점으로 본 핀볼

  • 중력은 위치에너지↔운동에너지를 왕복시킬 뿐 총량을 늘리지 않는다.
  • 에너지 공급원: 발사 스프링, 범퍼(e>1), 슬링샷, 플리퍼(ω×r).
  • 에너지 소비처: 벽(e<1), 공기저항, 플리퍼의 낮은 e.
  • 공급 > 소비면 공이 날뛰고, 공급 < 소비면 금방 축 처진다 — 균형이 곧 레벨 디자인.

터널링(Tunneling) — 빠른 공의 유령화

  • 충돌 검사는 '이산적인 순간'에만 한다. 스텝 사이의 이동은 순간이동이다.
  • 공이 한 스텝에 벽 두께보다 멀리 가면 겹침이 감지되지 않고 통과한다.
  • 우리 수치: MAX 1600px/s × 16.7ms = 프레임당 26.7px — 공 지름(22px)보다 크다! 위험.
  • 대책 ① 속도 제한(했음) ② 서브스텝(핵심) ③ CCD(고급, 개요만).

CCD(연속 충돌 감지) — 개요만

  • 이동 경로 전체(선분)와 충돌체의 교차를 해석적으로 계산하는 방식.
  • 장점: 아무리 빨라도 절대 안 뚫는다. 단점: 수학과 코드가 급격히 복잡해진다.
  • 총알, 골프공 시뮬 등 극단적 속도의 게임에서 필수.
  • 핀볼은 속도 상한 + 서브스텝으로 충분하다는 것이 실무적 결론.

충돌 처리의 2단계

  • 감지(Detection): 겹쳤는가? 겹쳤다면 어디서, 얼마나?
  • 응답(Response): 겹침을 어떻게 해소하고 속도를 어떻게 바꿀 것인가?
  • 감지의 산출물 세 가지: 충돌 여부, 법선 n̂, 침투 깊이.
  • 응답은 4장에서 이미 완성했다(reflect) — 이 장의 주인공은 감지다.

우리 게임의 충돌 조합

  • 공(원) vs 범퍼(원) — 원-원 충돌.
  • 공(원) vs 벽(선분) — 원-선분 충돌.
  • 공(원) vs 플리퍼(회전하는 캡슐) — 원-선분 + 표면 속도(8장).
  • 공(원) vs 슬링샷 — 원-선분 + 최소 반발 속도.
  • 결국 두 가지 기본기(원-원, 원-선분)로 모든 것이 만들어진다.

원-원 충돌 감지

충돌 ⇔ |c₁ − c₂| < r₁ + r₂
  • 두 중심 사이 거리가 반지름 합보다 작으면 겹친 것. 이보다 단순할 수 없다.
  • 법선: n̂ = (c₁ − c₂) / |c₁ − c₂| — 중심을 잇는 방향.
  • 침투 깊이: (r₁ + r₂) − |c₁ − c₂|.

Bumper.collide — 원-원의 전형

d.norm() 대신 d.scale(1/dist)를 쓴 이유: dist를 이미 계산했으므로 sqrt 재계산 회피.

collide(ball, game) {
  const d = ball.pos.sub(this.pos);      // 범퍼 → 공 벡터
  const dist = d.len();
  const minDist = this.r + BALL_RADIUS;  // 반지름 합
  if (dist >= minDist || dist < 1e-9) return false;  // 안 겹침 / 퇴화
  const n = d.scale(1 / dist);           // 단위 법선 (직접 나눔)
  ball.pos = this.pos.add(n.scale(minDist));  // 침투 해소: 표면 위로
  ball.vel = reflect(ball.vel, n, BUMPER_E);  // 반사 (e = 1.15)
  // ... 최소 튕김 속도 + 점수는 다음 슬라이드
}

sqrt 비교 최적화 — 실전 감각

  • 판정만 필요하면 dist² < minDist² 로 sqrt를 아예 피할 수 있다.
  • 그러나 겹쳤을 때는 어차피 법선과 깊이 계산에 실제 거리가 필요하다.
  • 우리 선택: 명료함 우선으로 len() 사용. 충돌체 35개 규모에선 차이가 없다.
  • 수천 개 입자 시뮬이라면: lenSq로 1차 거르기 → 겹친 것만 sqrt.

침투(Penetration) — 왜 반드시 위치를 보정하나

  • 이산 시뮬레이션에서 공은 항상 '이미 파고든 상태'로 발견된다.
  • 속도만 반사하고 위치를 안 고치면: 다음 스텝에도 여전히 겹침 → vn 가드에 걸려 방치 → 공이 벽 속을 미끄러진다.
  • 보정 방법: 법선 방향으로 침투 깊이만큼 밀어내 '정확히 접하는' 위치로 옮긴다.
  • 원-원: pos = 상대중심 + n̂ × (r₁+r₂). 원-선분: pos += n̂ × (r − dist).

원-선분 충돌 — 문제의 재구성

  • 질문: '원과 선분이 겹쳤나?'
  • 변환: '선분 위에서 공 중심에 가장 가까운 점(최근접점)과의 거리가 반지름보다 작나?'
  • 이 변환 덕에 원-선분 문제가 '점-선분 최근접점' 문제 하나로 줄어든다.
  • 최근접점은 투영(4장 내적)으로 구한다 — 수학이 연결되는 순간.
141

점-선분 최근접점

t = clamp( (p−a)·(b−a) / |b−a|² , 0, 1 )
최근접점 = a + t·(b−a)
  • t는 '선분 위 어디쯤'을 나타내는 비율: 0이면 a, 1이면 b, 0.5면 중점.
  • 분자 (p−a)·(b−a): p를 선분 방향으로 투영한 그림자 길이 × |b−a|.
  • 분모 |b−a|²로 나누면 0~1 스케일의 비율이 된다.
  • clamp가 핵심 — 다음 슬라이드.
142

clamp(0,1)의 기하학적 의미

  • 투영점이 선분 '연장선' 위에 떨어질 수 있다 — t < 0 또는 t > 1.
  • t를 [0,1]로 자르면 최근접점이 끝점 a 또는 b로 스냅된다.
  • 효과: 선분의 '끝'에 부딪히는 공이 끝점(모서리)을 중심으로 자연스럽게 둥글게 튕긴다.
  • clamp 한 줄이 '모서리 충돌'을 공짜로 해결한다 — 이 알고리즘의 백미.
143

closestPointOnSegment — 4줄의 만능 도구

벽, 플리퍼, 슬링샷 모두 이 함수로 충돌한다. 게임에서 재사용률 1위.

/* 점 p에서 선분 a-b 위의 최근접점
 * t = clamp(((p-a)·(b-a)) / |b-a|², 0, 1) */
function closestPointOnSegment(p, a, b) {
  const ab = b.sub(a);
  const t = Math.max(0, Math.min(1, p.sub(a).dot(ab) / ab.lenSq()));
  return a.add(ab.scale(t));
}

법선은 어느 방향? — 선분 충돌의 미묘한 점

  • 선분의 법선은 두 방향(양쪽 면)이 있다. 어느 쪽으로 밀어낼 것인가?
  • 정답: '최근접점에서 공 중심을 향하는 방향' — 공이 있는 쪽이 곧 밀어낼 쪽.
  • n̂ = (공중심 − 최근접점) / 거리.
  • 이 방식은 공이 선분의 어느 면에서 오든 자동으로 옳다 — if문이 필요 없다.
145

Wall.collide — 원-선분의 완성형

감지 → 법선 → 보정 → 반사. 모든 충돌 함수가 이 4박자를 따른다.

collide(ball) {
  const cp = closestPointOnSegment(ball.pos, this.a, this.b);
  const d  = ball.pos.sub(cp);          // 최근접점 → 공 중심
  const dist = d.len();
  if (dist >= BALL_RADIUS || dist < 1e-9) return false;
  const n = d.scale(1 / dist);          // 충돌 법선 (공이 있는 쪽)
  ball.pos = ball.pos.add(n.scale(BALL_RADIUS - dist)); // 침투 해소
  ball.vel = reflect(ball.vel, n, this.e);              // 반사
  return true;
}
146

dist < 1e-9 가드 — 퇴화 케이스

  • 공 중심이 '정확히' 선분 위에 있으면 d가 0벡터 — 법선을 정할 수 없다.
  • 0으로 나누면 (NaN, NaN) → 공 위치·속도 전체가 NaN으로 오염.
  • 발생 확률은 낮지만 서브스텝 4회 × 60fps × 벽 30개면 언젠가 일어난다.
  • 가드의 대가: 그 스텝은 충돌을 건너뛴다 — 다음 스텝에 공이 살짝 움직여 정상 처리된다.

충돌의 4박자 — 패턴으로 암기

  • ① 감지: 거리 < 임계값?
  • ② 법선: 밀어낼 단위 방향 n̂.
  • ③ 보정: 위치를 표면 밖으로 (침투 해소).
  • ④ 반사: reflect(v, n̂, e).
  • Wall, Bumper, Slingshot, Flipper의 collide가 전부 이 구조다 — 코드를 읽을 때 이 틀에 끼워 보라.

범퍼의 추가 규칙 — 최소 튕김 속도

  • 문제: 힘없이 굴러온 공은 반사해 봤자 힘없이 떠난다 — 범퍼답지 않다.
  • 해결: 반사 후 법선 방향 속도 성분(vn)이 420px/s 미만이면 그만큼 채워 준다.
  • vn = vel·n̂; if (vn < 420) vel += n̂ × (420 − vn)
  • 결과: 아무리 살짝 스쳐도 최소 420px/s로 쏘아 보낸다 — '킥'의 정체.
  • 점수(+100~150)와 플래시 이펙트도 이 순간 발동한다.

슬링샷 — 벽과 범퍼의 하이브리드

  • 구조적으로는 Wall(선분, e=1.0)을 내부에 품고 있다 — 합성(composition).

여러 충돌체를 순서대로 검사하기

  • 한 스텝에서 벽 → 범퍼 → 슬링샷 → 플리퍼 순으로 모두 검사한다.
  • 앞의 충돌이 공 위치를 옮기면 뒤의 검사는 '옮겨진 위치' 기준 — 순차 해소 방식.
  • 장점: 구현 단순, 대부분 자연스러움. 단점: 좁은 틈에 끼면 양쪽으로 번갈아 밀릴 수 있다.
  • 본격 엔진은 모든 접촉을 모아 동시에 푸는 솔버를 쓴다 — 핀볼엔 과잉.

한 프레임 다중 충돌과 서브스텝의 합

  • 서브스텝 덕분에 한 프레임 안에서 최대 4번의 독립적 충돌 기회가 있다.
  • 코너에 몰린 공: 스텝1에 왼벽 반사 → 스텝2에 바닥 반사 — 자연스러운 코너 탈출.
  • 서브스텝 없이 한 번에 처리하면 코너에서 떨림이나 파묻힘이 훨씬 잦다.
  • 충돌 시스템과 적분 시스템은 이렇게 서로를 보완한다.

캡슐 충돌 — 두꺼운 선분

플리퍼가 어려운 이유

  • 벽·범퍼는 정지해 있다 — 공의 속도만 생각하면 됐다.
  • 플리퍼는 '움직이는 표면'이다 — 표면 자체의 속도를 무시하면 공을 '때릴' 수 없다.
  • 필요한 재료: ① 회전 상태 관리(각도·각속도) ② 캡슐 충돌(7장) ③ 표면 속도(이번 장의 핵심).
  • 이 장을 이해하면 '움직이는 플랫폼', '회전 장애물' 등 모든 동적 충돌체를 만들 수 있다.

플리퍼의 상태 설계

  • angle: 현재 각도 — 유일한 위치 상태 (tip은 매번 계산).
  • omega: 현재 각속도(rad/s) — 타격 계산의 핵심.
  • pressed: 키 입력 플래그 (3장의 이벤트→플래그 패턴).
  • restAngle / activeAngle: 대기·작동 목표 각도. speed: 회전 속도 22rad/s.
  • 위치(x,y)를 저장하지 않는 것에 주목 — '각도가 곧 상태'가 회전체 설계의 정석.

Flipper.update — 목표각 추종

눌림 여부 → 목표각 결정 → 일정 속도로 접근 → 도달하면 ω=0.

update(dt) {
  const target = this.pressed ? this.activeAngle : this.restAngle;
  const diff = target - this.angle;
  const step = Math.sign(diff) * this.speed * dt;   // 이번 프레임 회전량
  if (Math.abs(step) >= Math.abs(diff)) {
    this.omega = diff / dt;      // 마지막 프레임의 '실제' 각속도
    this.angle = target;         // 목표 도달 (오버슛 방지)
  } else {
    this.omega = Math.sign(diff) * this.speed;
    this.angle += step;
  }
  if (Math.abs(diff) < 1e-4) this.omega = 0;  // 도달 후 정지
}
165

update 코드의 섬세한 부분들

  • Math.sign(diff): 목표가 위든 아래든 같은 코드로 처리 — 왼쪽/오른쪽 플리퍼 공용.
  • 오버슛 방지: 남은 각도보다 step이 크면 정확히 target에 스냅.
  • 스냅하는 프레임의 ω = diff/dt — 실제로 돈 만큼만 기록해 타격이 과장되지 않는다.
  • 도달 후 ω=0: 눌린 채 유지 중인 플리퍼는 '정지한 벽'으로 취급된다 — 올바른 물리.

회전체 위 점의 속도

v = ω × r (3D 외적)
2D 구현: v = ω · perp(r)
  • r: 피벗에서 접촉점까지의 벡터.
  • perp(r): r을 90° 돌린 벡터 — 원운동의 접선 방향(5장).
  • ω의 부호가 방향을 결정: 양수면 화면상 시계 방향 회전.
  • 피벗에서 멀수록(|r|↑) 빠르다 — 플리퍼 끝이 가장 아픈 이유.

움직이는 표면과의 충돌 — 상대속도 기법

  • 원리: '표면이 보는 세상'으로 들어가면 표면은 정지해 있다.
  • ① 접촉점의 표면 속도 v_s를 구한다.
  • ② 공의 상대속도 v_rel = v − v_s 를 계산한다.
  • ③ 정지 표면과 똑같이 반사: v_rel' = reflect(v_rel, n̂, e).
  • ④ 다시 세상 좌표로: v' = v_rel' + v_s.
  • 이 4단계가 '움직이는 물체와의 충돌'의 보편 공식이다 — 플리퍼, 무빙 플랫폼, 차량 전부.

Flipper.collide — 이 게임에서 가장 물리적인 함수

collide(ball) {
  const a = this.pivot, b = this.tip();
  const cp = closestPointOnSegment(ball.pos, a, b);   // 캡슐 축 최근접점
  const d = ball.pos.sub(cp);
  const dist = d.len();
  const minDist = BALL_RADIUS + this.thick;           // 공 + 캡슐 반두께
  if (dist >= minDist || dist < 1e-9) return false;
  const n = d.scale(1 / dist);
  ball.pos = ball.pos.add(n.scale(minDist - dist));   // 침투 해소
  const r = cp.sub(this.pivot);                       // 피벗 → 접촉점
  const surfaceVel = r.perp().scale(this.omega);      // v = ω·perp(r)
  const relVel = ball.vel.sub(surfaceVel);            // 상대속도로 전환
  ball.vel = reflect(relVel, n, FLIPPER_E).add(surfaceVel); // 반사 후 복귀
  return true;
}

왜 반발계수가 0.35로 낮은가

  • 플리퍼의 '힘'은 반발이 아니라 표면 속도에서 나온다.
  • 정지 플리퍼(ω=0): surfaceVel=0 → 그냥 e=0.35짜리 부드러운 벽 — 공 받기(trap)가 가능.
  • 회전 중 플리퍼: 표면 속도 최대 ~1584px/s가 상대속도 반사에 실려 폭발적 타격.
  • e를 높이면 정지 플리퍼조차 공을 튕겨내 컨트롤이 불가능해진다 — 실제 핀볼 감각과의 타협점.

수치로 보는 플리퍼 타격

  • 상황: 공이 300px/s로 낙하, 플리퍼 끝 부근(r=60)을 ω=22로 후려침.
  • 표면 속도 = 22 × 60 = 1320px/s (위 방향 성분 포함).
  • 상대속도 ≈ 300 + 1320 = 1620px/s로 표면에 접근하는 셈.
  • 반사 후 공 속도 ≈ 0.35 × 1620 + 1320 ≈ 1887 → MAX_SPEED(1600)로 클램프.
  • 즉 풀스윙 정타는 거의 항상 최고 속도 — 손맛의 수학적 근거.

타이밍이 게임성이 되는 이유

  • 일찍 누름: 공이 올 때 이미 도달(ω=0) → 약한 벽 반사만.
  • 정타: 회전 중(ω=22)에 접촉 → 최대 타격.
  • 이 차이가 코드 한 줄 없이 '타이밍 스킬'을 만든다 — 물리에서 창발한 게임성.
  • update에서 도달 프레임의 ω를 diff/dt로 정확히 기록한 것이 여기서 빛을 발한다.

Vec2 설계 리뷰

  • 8개 연산 + 회전 3종(rotate, angle, fromAngle) — 필요한 것만 담은 최소 API.
  • 불변 스타일: 모든 메서드가 새 객체 반환. 버그 표면적 최소화가 최우선 가치.
  • 정규화의 1e-9 가드, hypot 사용 — 수치 안전을 기본값으로.
  • 아쉬운 점(의도된 타협): 프레임당 수백 개의 임시 객체 — 13장에서 개선안을 논한다.
244

reflect / closestPointOnSegment 리뷰

  • 클래스 밖 순수 함수로 둔 이유: 상태가 없고, 모든 충돌체가 공유하기 때문.
  • 순수 함수는 테스트가 쉽다 — 12장의 단위 테스트가 이 둘을 직접 검증한다.
  • reflect의 vn≥0 가드는 '정책'이 함수 안에 있는 것 — 호출자가 잊을 수 없다.
  • 교훈: 재사용되는 수학은 클래스 메서드보다 순수 함수가 낫다.
245

Ball 리뷰 — 가장 단순한 물리체

  • 상태는 pos, vel, inPlay 셋뿐. 충돌 로직이 하나도 없다!
  • 충돌은 전부 '상대방(벽·범퍼·플리퍼)'의 collide가 처리 — 책임의 역전.
  • 이 구조 덕에 공을 여러 개로 늘리는 것(멀티볼)이 쉬워진다: 루프만 추가.
  • reset()이 초기화를 독점 — 시작 위치가 바뀌면 한 곳만 고친다.
246

Wall 리뷰 — 4박자의 교과서

  • 감지→법선→보정→반사가 아홉 줄에 정확히 들어 있다.
  • 반발계수를 생성자 인자로 받아(기본 0.55) 슬링샷이 e=1.0 벽을 재사용한다.
  • collide가 불리언을 반환 — 호출자가 '맞았는지' 알 수 있어 확장(사운드 등)에 유리.
  • draw까지 합쳐 25줄 — 한 클래스는 한 화면을 넘지 않게.
247

Bumper 리뷰 — 능동적 충돌체

  • Wall과의 차이: 원-원 충돌, e>1, 최소 킥 속도, 점수, 플래시.
  • collide(ball, game) — game을 인자로 받아 점수를 준다. 의존성이 명시적.
  • 침투 해소를 '표면 위 정확한 위치'로 스냅(pos = 중심 + n̂·합반지름) — 원-원의 정석.
  • flash 타이머가 update/draw로 분리 — 상태와 표현의 분리 원칙 유지.
248

Flipper 리뷰 ① — update

  • 목표각 추종은 사실 P제어(비례 제어)의 단순형 — 일정 속도 접근 + 스냅.
  • diff/dt로 마지막 프레임 ω를 보정하는 디테일이 타격 물리의 정확성을 지킨다.
  • 1e-4 라디안 데드존으로 도달 후 미세 진동 차단.
  • 왼쪽/오른쪽이 같은 코드 — Math.sign 덕분. 대칭을 데이터(각도)로 밀어낸 설계.
249

Flipper 리뷰 ② — collide

  • 7장 캡슐 충돌 + 8장 상대속도 반사의 결합 — 이 게임 최고 밀도의 12줄.
  • surfaceVel 계산에 접촉점(cp)을 쓰는 것이 중요 — 끝점이 아니라 '실제 닿은 곳'의 속도.
  • reflect를 재사용하므로 vn 가드도 자동 상속 — 코드 재사용이 버그 가드도 재사용.
  • 침투 해소가 반사보다 먼저 — 순서가 바뀌면 보정된 위치와 속도가 불일치.

Slingshot 리뷰 — 합성의 본보기

  • Wall을 상속하지 않고 내부에 품는다(composition over inheritance).
  • 이유: 슬링샷은 벽의 '일종'이 아니라 벽을 '이용하는' 장치 — is-a가 아닌 has-a.
  • 충돌 후 처리(킥, 점수, 플래시)만 자신이 담당.
  • before 속력을 기억해 '충분히 튕겼나' 판단하는 소박한 휴리스틱도 눈여겨보라.

Game.buildTable 리뷰

  • 모든 좌표 상수가 여기 모여 있다 — 사실상의 레벨 데이터 파일.
  • 아치 생성 루프는 '데이터를 코드로 생성'하는 예 — 22개 좌표를 손으로 쓰지 않는다.
  • 개선 아이디어: walls/bumpers 배열을 JSON으로 빼면 테이블 에디터(14장)로 가는 길.

Game.update 리뷰

  • 게이지 → 오브젝트 자체 갱신 → 서브스텝(적분+충돌) → 레인 복귀 → 드레인.
  • 충돌 검사 순서(벽→범퍼→슬링샷→플리퍼)는 순차 해소 — 7장에서 논의한 타협.
  • gameOver·!inPlay 조기 반환으로 불필요한 물리를 건너뛴다.
  • update에는 그리기가, render에는 상태 변경이 한 줄도 없다 — 3장 원칙 준수 확인.
253

Game.render 리뷰

  • clearRect → 오브젝트 draw 위임 → 게이지 → HUD → 오버레이. 40줄.
  • 각 오브젝트가 자기 draw를 소유 — render는 순서만 지휘하는 지휘자.
  • 조건부 UI(게이지, 안내문, 게임오버)는 전부 상태 검사로 — 별도 씬 시스템 불필요.
  • 이 규모에서 씬 매니저를 도입하는 것은 과설계다 — 단순함도 설계다.

입력 처리 리뷰

  • 이벤트→플래그 패턴(3장)이 유일한 입력 창구.
  • 발사가 keyup에서 일어나는 디테일 — '눌러서 조준, 떼서 발사'의 표준 감각.
  • 게임오버 상태에서 SPACE의 의미가 재시작으로 바뀐다 — 상태별 입력 해석.
  • 개선 여지: 키 매핑 객체로 빼면 커스터마이징 가능(14장 과제).

  • ① 수학은 순수 함수로, 상태는 클래스로.
  • ② update와 render의 완전 분리.
  • ③ 모든 충돌은 감지→법선→보정→반사의 4박자.
  • ④ 수치 가드 5종 세트(dt 클램프, 속도 상한, 0나눗셈, 재반사, 침투 해소).
  • ⑤ 데이터(좌표·상수)와 로직의 분리.
  • 이 다섯을 지키면 어떤 2D 아케이드 물리 게임도 같은 골격으로 만들 수 있다.

  • 5장 삼각함수 → tip(), fromAngle, 아치 생성, ω.
  • 6장 물리 → Ball.update, 서브스텝, 상수들.
  • 7장 충돌 → closestPointOnSegment, 4종 collide.
  • 8장 플리퍼 → Flipper 전체. 9장 → buildTable, Game 규칙.

무엇을 검사하나 — 불변식(invariant)

  • 불변식 = 어떤 순간에도 참이어야 하는 조건. 테스트의 뼈대.
  • 우리 게임의 불변식:

  • 공은 외벽 밖으로 나가지 않는다 (±공 반지름 여유)

단위 테스트 — 순수 함수부터

최적화의 제1원칙 — 측정 먼저

병목 후보 ① — 벡터 객체 할당

  • 불변 Vec2: 연산마다 new — 프레임당 수백 개, 초당 수만 개의 단명 객체.
  • 현대 JS 엔진의 세대별 GC는 단명 객체에 강하다 — 그래서 우리 규모는 무사.
  • 그러나 입자 수천 개 규모면 GC 일시정지(수 ms)가 프레임 드랍으로 보인다.
  • 대책 두 가지: 가변(mutable) API 추가, 또는 객체 풀링.

가변 API — 할당 없는 핫패스

규칙: 기본은 불변, 프로파일러가 지목한 곳만 가변으로.

// 불변(기존): 새 객체 반환 — 읽기 좋다
add(v) { return new Vec2(this.x + v.x, this.y + v.y); }
 
// 가변(추가): 자신을 수정 — 핫패스 전용
iadd(v)   { this.x += v.x; this.y += v.y; return this; }
iscale(s) { this.x *= s;  this.y *= s;  return this; }
 
// 핫패스 예: 적분 루프
this.vel.iadd(_tmp.set(GRAVITY).iscale(dt));  // 할당 0회

병목 후보 ② — 충돌 검사 O(n)

  • 매 서브스텝 × 충돌체 35개 = 프레임당 140회 검사 — 전혀 문제없다.
  • 멀티볼 10개 + 충돌체 200개면 8000회/프레임 — 슬슬 구조가 필요하다.
  • 공간 그리드: 화면을 셀(예: 64px)로 나누고 충돌체를 셀에 등록, 공이 있는 셀 주변만 검사.

  • 그라디언트 캐싱: 공 그라디언트를 매 프레임 생성 중 — 오프스크린 스프라이트로.

  • 여기서부터 객체 풀링(13장)이 실전 의미를 갖기 시작한다.

틸트(Tilt) 시스템

  • 실제 핀볼의 '기계 흔들기'를 재현: T 키로 GRAVITY에 순간 수평 성분 추가.
  • 남용 방지: 3회 누르면 TILT — 플리퍼 비활성화 + 현재 공 무효.
  • 구현: 흔들기 카운터 + 쿨다운 타이머, 화면에 경고 표시.
  • 물리 상수를 '실시간으로 조작'하는 첫 경험으로 좋은 과제.

미션·콤보 시스템

우리가 만든 것

  • 외부 의존성 0, 단일 HTML 파일, 약 500줄의 완전한 핀볼 게임.
  • 직접 구현한 것: 벡터 라이브러리, 물리 적분기, 충돌 시스템, 회전체 역학, 게임 루프.

핵심 수학 요약 ① — 벡터

  • 뺄셈 = 도착지 − 출발지 = 방향.
  • 내적 = 투영과 각도의 만능 도구. 부호로 접근/이탈 판정.
  • 정규화 = 방향과 크기의 분리 (0벡터 주의).
  • 반사 v' = v − (1+e)(v·n̂)n̂ — 이 한 줄이 게임의 심장.
300

핵심 수학 요약 ② — 삼각함수

  • (cosθ, sinθ) = 단위원 위의 점 = 각도의 좌표화.
  • tip = pivot + L(cosθ, sinθ) — 모든 회전체의 공식.
  • 곡선 = 삼각함수로 뽑은 점 + 선분 근사.
  • v = ω·perp(r) — 회전이 만드는 속도. 플리퍼 타격의 정체.
301

핵심 수학 요약 ③ — 물리와 충돌

  • 반암시적 오일러: v += a·dt → p += v·dt.
  • 충돌 4박자: 감지 → 법선 → 침투 해소 → 반사.
  • 최근접점 = 투영 + clamp — 원-선분 충돌의 열쇠.
  • 움직이는 표면 = 상대속도로 반사 후 복귀.
  • 터널링 = 속도 상한 + 서브스텝으로 제압.

아키텍처 회고

  • 다시 만든다면 바꿀 것: 좌표 데이터의 JSON 분리, 감쇠의 dt 독립화.
